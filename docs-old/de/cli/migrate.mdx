```bash
failproofai migrate --dry-run   # Plan ausgeben, nichts ändern
failproofai migrate             # ausführen
```

Die meisten Personen tippen diesen Befehl nie. Er läuft automatisch beim ersten
Befehl nach einem Upgrade, und [`failproofai update`](/de/cli/update) schließt ihn
ein. Greifen Sie direkt darauf zurück, wenn Sie den Plan vor der Ausführung sehen
möchten oder die Migration eigenständig durchführen wollen.

## Am Layout orientiert, nicht an der Version

`~/.failproofai/VERSION` speichert eine **Layout**-Nummer — die Struktur des
Verzeichnisses, nicht das Release, das sie geschrieben hat. Migrationen werden
anhand dieser Nummer verwaltet, was große Sprünge günstig macht:

- npm-Versionen ändern sich bei jedem Release, Dutzende davon zwischen zwei Layouts.
- Eine Maschine, die dreißig Releases mit **keiner Layout-Änderung** überspringt,
  führt **null** Migrationen aus, nicht dreißig Leerdurchläufe.
- Eine Maschine, die mehrere Layouts auf einmal überspringt, führt jeden Schritt
  der Reihe nach aus, wobei jeder Schritt nur seine eigenen zwei Endpunkte kennt.

Das ist wichtig, weil npm ein installiertes Paket nicht von selbst aktualisieren
kann. Eine Maschine, die monatelang auf einer Version verharrt und dann mehrere
Layouts auf einmal überspringt, ist der Normalfall — nicht die Ausnahme.

## Der Trockenlauf

`--dry-run` gibt die genaue Kette und die Dateien aus, die zuerst gesichert würden,
und ändert überhaupt nichts — keine Migration, kein Backup, kein Ledger-Eintrag:

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## Was übertragen und was neu aufgebaut wird

Jeder Pfad im Home-Verzeichnis gibt an, welche Art von Daten er enthält, und das
entscheidet, ob eine Migration ihn verwerfen darf. Die Regel: **Abgeleitete und
neu abrufbare Daten dürfen verworfen werden; alles, was Sie getippt haben, alles
noch nicht Zugestellte und alles, was die Maschine identifiziert, wird übertragen.**

| Übertragen | Neu aufgebaut oder neu abgerufen |
|---|---|
| `config.json` — Einstellungen, `daemon.configured`, zusätzliche Capture-Pfade | Der Audit-Cache |
| `credentials.json` — Ihre Cloud-Registrierung | Cloud-verwaltete Deployments (beim nächsten Poll neu abgerufen und digest-verifiziert) |
| `policies-config.json` — Ihre Policy-Auswahl und Parameter | Daemon-Scratch-Status |
| `policies/` — Ihre eigenen Policy-Dateien und die von ihnen importierten Hilfsdateien | |
| `hook-activity/` — das Entscheidungsprotokoll, das das Dashboard liest | |
| Noch nicht zugestellte Events in der Upload-Warteschlange | |
| `cursors/` — Collector-Wasserzeichen | |
| Das Daemon-Binary in `bin/` | |

<Note>
  Nicht zugestellte Events werden übertragen statt verworfen, weil der Verlust
  dauerhaft wäre und nicht nur eine Verzögerung: Das Wasserzeichen des Collectors
  ist bereits über alles hinausgegangen, was im Spool liegt, sodass dieser
  Bereich eines Transkripts nie wieder gelesen werden würde. Die Migration fordert
  den Daemon auch auf, das Gespoolte sofort nach Abschluss zuzustellen, sodass
  im Normalfall nichts zu übertragen übrig bleibt.
</Note>

Schlüssel, die eine *neuere* Version in `config.json`, `credentials.json` oder
`policies-config.json` geschrieben hat, werden ebenfalls beibehalten und nicht
von einem älteren Leser verworfen.

## Das hinterlassene Protokoll

```
~/.failproofai/migrations/
  applied.json                 ein Eintrag pro Schritt: Layout, CLI, Zeitstempel, Dauer, Ergebnis
  backup-layout<n>/            Kopien der unersetzlichen Dateien, vor dem ersten Schritt erstellt
```

`applied.json` beantwortet die Frage „Was hat diese Maschine tatsächlich
durchgemacht" — die erste Frage, die sich stellt, wenn nach einem Upgrade etwas
nicht stimmt. Fügen Sie sie einem Bug-Report bei.

Das Backup ist bewusst klein gehalten statt eine Kopie des gesamten Verzeichnisses
zu sein: Die Migration löscht per Design nichts Unersetzliches mehr, sodass das
Absichernswerte ein *Defekt in einem Schritt* ist — und diese wenigen Dateien sind
es, wo ein solcher Defekt schaden würde.

## Wenn ein Schritt fehlschlägt

Die Kette stoppt an dieser Stelle. `VERSION` wird nur von einem erfolgreich
abgeschlossenen Schritt aktualisiert, sodass das Home mit seinem alten Layout
markiert bleibt und der nächste Befehl es erneut versucht — ein Home wird nie
auf Basis einer unvollständigen Migration als aktuell markiert. Der Schritt wird
in `applied.json` mit `"ok": false` eingetragen, und das Backup befindet sich
dort, wo es erstellt wurde.

## Ein neueres Home wird abgelehnt, nicht migriert

Wenn `~/.failproofai/` von einer **neueren** failproofai-Version geschrieben wurde
als der aktuell verwendeten, stoppt der Befehl und fordert Sie auf, stattdessen
ein Upgrade durchzuführen. Diese Daten sind in Ordnung und eine neuere CLI liest
sie; eine Migration „vorwärts" davon existiert nicht, und ein Reset würde etwas
Wiederherstellbares zerstören.

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

Der Daemon wendet dieselbe Regel an: `failproofaid` verweigert den Start mit einem
Layout, das er nicht kennt, anstatt Pfade zu lesen und zu schreiben, die
verschoben wurden.
