---
title: Actualizar tras una actualización de versión
description: "Completa la mitad de una actualización que npm no puede hacer: migra el directorio de inicio y sincroniza el daemon"
---

```bash
npm install -g failproofai@latest && failproofai update
```

Eso es todo lo que necesitas para actualizar. `npm` reemplaza la CLI; `failproofai update` hace el resto.

## Por qué existe un segundo comando

`npm install -g` reemplaza una sola cosa: la CLI. Otras dos partes de una instalación de failproofai viven fuera del paquete de forma intencionada, y ninguna se mueve cuando npm se ejecuta:

- **`~/.failproofai/`**, tu configuración, inscripción en la nube, selección de políticas e historial. Una nueva versión puede organizarlo de manera diferente, y esa reorganización debe realizarla código que conozca ambas estructuras.
- **El binario del daemon `failproofaid`**, ubicado en `~/.failproofai/bin/failproofaid-<version>`. No está dentro de `node_modules` de forma deliberada: una actualización que reemplazara el archivo bajo un servicio en ejecución redirigiría un daemon activo hacia un binario compilado a partir de código fuente diferente, y eliminar el paquete lo borraría de debajo de un servicio que luego entraría en un bucle de fallos en cada arranque.

Por tanto, tras ejecutar solo `npm install -g`, la CLI es nueva pero el daemon no lo es. `failproofaid` se niega a iniciarse con una estructura de directorio de inicio que no reconoce —la versión ruidosa de ese desajuste, en lugar de la silenciosa— así que ambas mitades deben sincronizarse. `failproofai update` es ese paso.

## Qué hace

<Steps>
  <Step title="Ejecuta las migraciones de estructura pendientes">
    Lee la estructura registrada en `~/.failproofai/VERSION` y ejecuta los pasos necesarios para llevarla a la que esta versión utiliza. Normalmente ninguno — consulta [`failproofai migrate`](/es/cli/migrate).
  </Step>
  <Step title="Coloca el binario del daemon correspondiente">
    Desde el paquete de plataforma que npm ya descargó cuando es posible (sin red), o bien desde el recurso de lanzamiento para esta versión exacta, verificado con SHA-256 antes de usarlo.
  </Step>
  <Step title="Reinicia el servicio y confirma que arrancó correctamente">
    Se verifica mediante sondeo, no por suposición — un gestor de servicios reporta un proceso activo en el momento en que hace fork, lo cual no es lo mismo que estar funcionando correctamente.
  </Step>
</Steps>

## Opciones

| Opción | Efecto |
|--------|--------|
| `--no-daemon` | Migra solo el directorio de inicio, dejando el daemon en su versión actual. |

<Warning>
  `--no-daemon` deja en su lugar un daemon con versión desincronizada. En una máquina configurada para requerir el daemon, cada evento de hook **falla en modo cerrado** si el daemon no puede responder — y un daemon que se niega a iniciarse con un directorio de inicio migrado no puede responder. Es preferible dejar que también se ejecute la mitad del daemon.
</Warning>

## Si algo sale mal

El comando termina con código de salida distinto de cero e indica qué mitad falló. Dos casos que conviene conocer:

- **Un paso de migración no terminó.** El directorio de inicio se deja marcado con su estructura *anterior*, de modo que el próximo comando la reintentará — ningún directorio de inicio se marca como actualizado basándose en una migración parcial. Se guardaron copias de tu configuración e inscripción antes de ejecutar nada, en `~/.failproofai/migrations/backup-layout<n>/`.
- **El daemon no pudo reiniciarse sin contraseña.** Se usa `sudo -n` de forma deliberada, para que nada solicite credenciales desde debajo de una pantalla de progreso. El comando imprime la línea exacta que debes ejecutar tú mismo.

<Note>
  Nada de esto requiere el asistente de configuración interactivo. Tu configuración, inscripción en la nube y selección de políticas sobreviven a una actualización, por lo que una máquina migrada aplica exactamente las mismas reglas que antes — lo que importa sobre todo en las máquinas en las que no hay nadie delante: un runner de CI, una máquina de una flota, una pasarela sin interfaz gráfica.
</Note>

## Automatización

`failproofai update` es no interactivo y es seguro ejecutarlo cuando no hay nada que hacer — reporta "no se necesitaba ninguna migración" y termina con código 0. Añadirlo después de cada actualización en un script de aprovisionamiento o en un Dockerfile es el uso previsto:

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

(`--no-daemon` en una construcción de imagen, donde todavía no hay ningún servicio que reiniciar.)
