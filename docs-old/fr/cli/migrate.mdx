```bash
failproofai migrate --dry-run   # afficher le plan, sans rien modifier
failproofai migrate             # exécuter la migration
```

La plupart des utilisateurs n'ont jamais besoin de taper cette commande. Elle s'exécute automatiquement au premier lancement après une mise à niveau, et [`failproofai update`](/fr/cli/update) l'inclut déjà. Utilisez-la directement lorsque vous souhaitez voir le plan avant son exécution, ou effectuer la migration de manière isolée.

## Indexé sur la structure, pas sur la version

`~/.failproofai/VERSION` enregistre un numéro de **structure** — la forme du répertoire, et non la version qui l'a écrit. Les migrations sont indexées sur ce numéro, ce qui rend un grand écart peu coûteux :

- Les versions npm changent à chaque publication, potentiellement des dizaines entre deux structures.
- Ainsi, une machine qui saute trente publications **sans changement de structure** exécute **zéro** migration, et non trente opérations inutiles.
- Et une machine qui saute plusieurs structures d'un coup exécute chaque étape dans l'ordre, chaque étape ne connaissant que ses deux extrémités.

C'est important parce que npm ne peut pas mettre à jour automatiquement un paquet installé. Une machine restée sur une version pendant des mois puis passant plusieurs structures d'un coup est le cas normal, pas l'exception.

## Le mode dry run

`--dry-run` affiche la chaîne exacte et les fichiers qui seraient sauvegardés au préalable, sans rien modifier — ni migration, ni sauvegarde, ni entrée dans le registre :

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## Ce qui est conservé et ce qui est reconstruit

Chaque chemin du répertoire personnel déclare le type de données qu'il contient, ce qui détermine si une migration peut le supprimer. La règle : **ce qui est dérivé ou récupérable peut être abandonné ; tout ce que vous avez saisi, tout ce qui n'a pas encore été transmis, et tout ce qui identifie la machine est conservé.**

| Conservé | Reconstruit ou récupéré |
|---|---|
| `config.json` — paramètres, `daemon.configured`, chemins de capture supplémentaires | Le cache d'audit |
| `credentials.json` — votre enrôlement cloud | Les déploiements gérés dans le cloud (récupérés et vérifiés par condensat au prochain sondage) |
| `policies-config.json` — votre sélection de politiques et leurs paramètres | L'état temporaire du daemon |
| `policies/` — vos propres fichiers de politiques et les helpers qu'ils importent | |
| `hook-activity/` — le journal de décisions lu par le tableau de bord | |
| Les événements non transmis encore en file d'attente pour l'envoi | |
| `cursors/` — les repères du collecteur | |
| Le binaire du daemon dans `bin/` | |

<Note>
  Les événements non transmis sont conservés plutôt que supprimés car la perte serait permanente, pas seulement différée : le repère du collecteur a déjà avancé au-delà de tout ce qui se trouve dans la file d'attente, donc rien ne lirait jamais cette plage d'une transcription. La migration demande également au daemon de transmettre ce qui est en file d'attente dès qu'elle se termine, de sorte que le résultat habituel est qu'il ne reste rien à conserver.
</Note>

Les clés qu'une version *plus récente* a écrites dans `config.json`, `credentials.json` ou `policies-config.json` sont également préservées, plutôt que supprimées par un lecteur plus ancien.

## Le registre qu'elle laisse

```
~/.failproofai/migrations/
  applied.json                 une entrée par étape : structure, CLI, horodatage, durée, résultat
  backup-layout<n>/            copies des fichiers irremplaçables, prises avant la première étape
```

`applied.json` est ce qui répond à la question « par quoi cette machine est-elle réellement passée » — la première chose à vérifier lorsque quelque chose semble anormal après une mise à niveau. Joignez-le à un rapport de bug.

La sauvegarde est délibérément petite plutôt qu'une copie de l'ensemble du répertoire : la migration ne supprime plus rien d'irremplaçable par conception, donc ce contre quoi il vaut la peine de se prémunir est un *défaut dans une étape*, et ces quelques fichiers sont là où un tel défaut ferait mal.

## Si une étape échoue

La chaîne s'arrête là. `VERSION` n'est mis à jour que par une étape qui s'est terminée avec succès, donc le répertoire personnel reste marqué avec son ancienne structure et la prochaine commande réessaie — un répertoire personnel n'est jamais marqué comme à jour sur la base d'une migration partielle. L'étape est enregistrée dans `applied.json` avec `"ok": false`, et la sauvegarde reste à l'endroit où elle a été prise.

## Un répertoire plus récent est refusé, pas migré

Si `~/.failproofai/` a été écrit par une version **plus récente** de failproofai que celle que vous exécutez, la commande s'arrête et vous indique de mettre à niveau à la place. Ces données sont valides et une CLI plus récente les lit normalement ; migrer « en avant » à partir de celles-ci n'est pas une opération qui existe, et les réinitialiser détruirait quelque chose de récupérable.

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

Le daemon applique la même règle : `failproofaid` refuse de démarrer avec une structure qu'il ne comprend pas, plutôt que de lire et d'écrire des chemins qui ont changé.
