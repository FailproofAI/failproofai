---
title: Mise à jour après une montée de version
description: "Finaliser ce que npm ne peut pas faire : migrer le répertoire personnel et synchroniser le daemon"
---

```bash
npm install -g failproofai@latest && failproofai update
```

C'est tout ce qu'il y a à faire pour une mise à jour. `npm` remplace le CLI ; `failproofai update` s'occupe du reste.

## Pourquoi une deuxième commande est nécessaire

`npm install -g` ne remplace qu'une seule chose — le CLI. Deux autres composants d'une installation failproofai résident intentionnellement en dehors du package, et aucun des deux n'est déplacé lors de l'exécution de npm :

- **`~/.failproofai/`**, vos paramètres, l'inscription cloud, la sélection des politiques et l'historique. Une nouvelle version peut organiser ce répertoire différemment, et cette réorganisation doit être effectuée par du code qui connaît les deux structures.
- **Le binaire du daemon `failproofaid`**, situé dans `~/.failproofai/bin/failproofaid-<version>`. Il ne se trouve délibérément *pas* dans `node_modules` : une mise à jour qui remplacerait le fichier sous un service en cours d'exécution redirigerait un daemon actif vers un binaire construit à partir d'une source différente, et la suppression du package le retirerait d'un service qui entrerait alors en boucle de crash à chaque démarrage.

Ainsi, après `npm install -g` seul, le CLI est à jour mais pas le daemon. `failproofaid` refuse de démarrer avec une structure de répertoire qu'il ne reconnaît pas — une incompatibilité signalée de façon explicite plutôt que silencieuse — et les deux parties doivent donc être synchronisées. `failproofai update` est cette étape.

## Ce que la commande fait

<Steps>
  <Step title="Exécute les migrations de structure en attente">
    Lit la structure enregistrée dans `~/.failproofai/VERSION` et exécute les étapes nécessaires pour la mettre au niveau attendu par cette version. En général, aucune migration n'est nécessaire — voir [`failproofai migrate`](/fr/cli/migrate).
  </Step>
  <Step title="Met en place le binaire du daemon correspondant">
    À partir du package de plateforme déjà téléchargé par npm si possible (sans réseau), sinon depuis l'artefact de publication pour cette version exacte, vérifié par SHA-256 avant utilisation.
  </Step>
  <Step title="Redémarre le service et confirme qu'il est opérationnel">
    Vérifié par sondage plutôt que supposé — un gestionnaire de service signale un processus actif dès qu'il est forké, ce qui ne signifie pas pour autant qu'il fonctionne correctement.
  </Step>
</Steps>

## Options

| Option | Effet |
|--------|-------|
| `--no-daemon` | Migre uniquement le répertoire personnel, en laissant le daemon à sa version actuelle. |

<Warning>
  `--no-daemon` laisse en place un daemon dont la version est désynchronisée. Sur une machine configurée pour exiger le daemon, chaque événement de hook **échoue en sécurité** si le daemon ne peut pas répondre — et un daemon qui refuse de démarrer avec un répertoire migré ne peut pas répondre. Il est préférable de laisser la partie daemon s'exécuter.
</Warning>

## En cas de problème

La commande se termine avec un code non nul et indique quelle partie a échoué. Deux cas méritent attention :

- **Une étape de migration ne s'est pas terminée.** Le répertoire est conservé avec son *ancienne* structure, de sorte que la prochaine commande la réessaie — aucun répertoire n'est jamais marqué comme à jour sur la base d'une migration partielle. Des copies de vos paramètres et de votre inscription ont été sauvegardées avant toute exécution, dans `~/.failproofai/migrations/backup-layout<n>/`.
- **Le daemon n'a pas pu être redémarré sans mot de passe.** `sudo -n` est utilisé délibérément, afin que rien ne demande jamais de saisie depuis un affichage de progression. La commande affiche la ligne exacte à exécuter vous-même.

<Note>
  Rien dans ce processus ne nécessite l'assistant de configuration interactif. Vos paramètres, votre inscription cloud et votre sélection de politiques survivent à une mise à jour — une machine migrée applique donc exactement les mêmes règles qu'avant, ce qui importe surtout sur les machines sans utilisateur présent : un runner CI, une machine de flotte, une passerelle sans interface graphique.
</Note>

## Automatisation

`failproofai update` est non interactif et peut être exécuté sans risque même s'il n'y a rien à faire — il indique qu'aucune migration n'était nécessaire et se termine avec le code 0. L'intégrer après chaque mise à jour dans un script de provisionnement ou un Dockerfile est l'usage prévu :

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

(`--no-daemon` dans une construction d'image, où il n'y a pas encore de service à redémarrer.)
