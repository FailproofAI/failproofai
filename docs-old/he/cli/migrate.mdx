```bash
failproofai migrate --dry-run   # print the plan, change nothing
failproofai migrate             # run it
```

רוב האנשים לעולם לא מקלידים את זה. הוא רץ באופן אוטומטי בפקודה הראשונה לאחר שדרוג, וגם [`failproofai update`](/he/cli/update) כולל אותו. השתמש בו ישירות כשאתה רוצה לראות את התוכנית לפני שזה קורה, או כדי להריץ את ההעברה בעצמה.

## מבוסס על התצורה, לא על הגרסה

`~/.failproofai/VERSION` מתעד מספר **תצורה** — צורת הספריה, לא הגרסה שכתבה אותה. העברות מופעלות לפי המספר הזה, וזה מה שהופך פער ארוך לזול:

- גרסאות npm משתנות בכל הוצאה לאור, עשרות אלה בין שתי תצורות.
- אז מכונה שדילגה על שלוש עשרה הוצאות לאור ללא **שינוי תצורה** מריצה **אפס** העברות, לא שלוש עשרה בלא-פעולה.
- ומכונה שדילגה על כמה תצורות בבת אחת מריצה כל שלב בסדר, כשכל שלב יודע רק על שני הקצוות שלו.

זה חשוב כי npm לא יכול לעדכן חבילה מותקנת בעצמו. מכונה שישבה על גרסה אחת למשך חודשים ואז קפצה כמה תצורות הלאה היא המקרה הרגיל, לא המוזר.

## הריצת ניסיון

`--dry-run` מדפיס את השרשרת המדויקת והקבצים שיושמרו תחילה, ולא משנה כלל — לא העברה, לא גיבוי, לא ערך רישום:

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## מה מועבר ומה בנוי מחדש

כל נתיב בספריית הבית מצהיר איזה סוג נתונים הוא מכיל, וזה קובע אם העברה יכולה להשליך אותו. הכלל: **נגזר ו-re-fetchable אפשר להוריד; כל דבר שהקלדת, כל דבר שעדיין לא סופק, וכל דבר שמזהה את המכונה מועבר.**

| מועבר | בנוי מחדש או re-fetched |
|---|---|
| `config.json` — הגדרות, `daemon.configured`, נתיבי capture נוספים | cache האודיט |
| `credentials.json` — הרישום שלך בענן | הפריסות המנוהלות בענן (re-fetched ו-digest-verified בסקר הבא) |
| `policies-config.json` — בחירת המדיניות שלך והפרמטרים שלה | מצב scratch של ה-daemon |
| `policies/` — קבצי המדיניות שלך וה-helpers שהם מייבאים | |
| `hook-activity/` — יומן ההחלטות שהדשבורד קורא | |
| אירועים שלא סופקו עדיין בתור להעלאה | |
| `cursors/` — סימניות של collector | |
| binary ה-daemon ב-`bin/` | |

<Note>
  אירועים שלא סופקו מועברים במקום להיות מושמטים כי ההפסד יהיה קבוע, לא איטי: סימנית ה-collector כבר התקדמה מעבר לכל דבר שיושב ב-spool, כך שלא היה קורא כלום בטווח הזה של טרנסקריפציה שוב. ההעברה גם מבקשת מה-daemon להעביר מה שב-spool בהקדם שהוא מסיים, אז התוצאה הרגילה היא שלא נשאר כלום להעביר.
</Note>

מפתחות שגרסה *חדשה יותר* כתבה ל-`config.json`, `credentials.json` או `policies-config.json` גם כן משמרים, במקום להיות מושמטים על ידי קורא ישן יותר.

## הרישום שהוא משאיר

```
~/.failproofai/migrations/
  applied.json                 ערך אחד לשלב: layout, CLI, timestamp, duration, result
  backup-layout<n>/            עותקים של הקבצים שלא ניתן להחליף, שנלקחו לפני השלב הראשון
```

`applied.json` זה מה שעונה "מה המכונה הזו באמת עברה" — השאלה הראשונה שכדאי לשאול כשמשהו נראה לא בסדר לאחר שדרוג. צרף אותו לדוח באג.

הגיבוי בעלי גודל קטן בכוונה במקום עותק של כל הספריה: ההעברה כבר לא מוחקת כלום שלא ניתן להחליף בתכנון, אז מה שכדאי לבטח נגדו הוא *פגם בשלב*, וקבצים ספורים אלה הם המקום שבו פגם כזה יכול להוציא נזק.

## אם שלב נכשל

השרשרת עוצרת שם. `VERSION` מתועד רק על ידי שלב שהושלם, אז הבית נשאר מסומן עם התצורה הישנה שלו והפקודה הבאה מנסה אותה שוב — בית לעולם לא מסומן כעדכני על כוח העברה חלקית. השלב נרשם ב-`applied.json` עם `"ok": false`, והגיבוי הוא המקום בו הוא נלקח.

## בית חדש יותר מורחק, לא מוקצה

אם `~/.failproofai/` נכתב על ידי failproofai **חדש יותר** מה-CLI שאתה מריץ, הפקודה עוצרת ואומרת לך לשדרג במקום. הנתונים הללו בסדר וקורא חדש יותר קורא אותם; ביצוע "מעבר קדימה" מזה לא דבר שקיים, והגדרה מחדש של זה תהרוס משהו שניתן לשחזר.

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

ה-daemon מחיל את אותו הכלל: `failproofaid` מסרב להתחיל נגד layout שהוא לא מדבר עליו, במקום לקרוא ולכתוב נתיבים שהעברו.
