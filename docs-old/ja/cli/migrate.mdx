---
title: ホームディレクトリを移行する
description: "~/.failproofai をこのバージョンが対応するレイアウトに更新する。まず実行内容を確認することも可能"
---

```bash
failproofai migrate --dry-run   # 計画を表示するだけで、何も変更しない
failproofai migrate             # 実際に実行する
```

ほとんどの場合、このコマンドを手動で入力する必要はありません。アップグレード後の最初のコマンド実行時に自動的に動作し、[`failproofai update`](/ja/cli/update) にも含まれています。実行前に計画を確認したい場合や、移行処理だけを単独で実行したい場合に直接使用してください。

## バージョンではなくレイアウトに基づく管理

`~/.failproofai/VERSION` には**レイアウト**番号が記録されています。これはリリースバージョンではなく、ディレクトリの構造を表す番号です。移行処理はこの番号をキーとしているため、バージョンを大幅にスキップしてもコストが低く抑えられます。

- npm のバージョンはリリースごとに変わり、2つのレイアウト間に数十ものバージョンが存在します。
- そのため、**レイアウト変更なし**で30回のリリースをスキップしたマシンは、意味のない処理を30回実行するのではなく、**移行処理をゼロ回**実行します。
- 複数のレイアウトをまとめてスキップした場合は、各ステップが順番に実行されます。各ステップは自身の前後の状態だけを把握します。

npm はインストール済みパッケージを単独で更新できないため、この設計は重要です。あるバージョンを何ヶ月も使い続けた後、一気に複数のレイアウトを飛び越えるケースは珍しいことではなく、むしろ通常のケースです。

## ドライラン

`--dry-run` は実行されるステップのチェーンと、事前に保存されるファイルを表示するだけで、何も変更しません。移行処理、バックアップ、台帳への記録はいずれも行われません。

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## 引き継がれるものと再構築されるもの

ホームディレクトリ内の各パスが保持するデータの種類によって、移行時に削除できるかどうかが決まります。ルールは次のとおりです：**派生データや再取得可能なデータは削除してよい。ユーザーが入力したもの、未配信のもの、マシンを識別するものは引き継ぐ。**

| 引き継がれる | 再構築または再取得 |
|---|---|
| `config.json` — 設定、`daemon.configured`、追加のキャプチャパス | 監査キャッシュ |
| `credentials.json` — クラウド登録情報 | クラウド管理のデプロイメント（次回のポーリング時に再取得してダイジェスト検証） |
| `policies-config.json` — ポリシーの選択とパラメータ | デーモンのスクラッチ状態 |
| `policies/` — 独自のポリシーファイルとそこでインポートするヘルパー | |
| `hook-activity/` — ダッシュボードが読む決定ログ | |
| アップロードキューに残っている未配信イベント | |
| `cursors/` — コレクターのウォーターマーク | |
| `bin/` 内のデーモンバイナリ | |

<Note>
  未配信イベントを削除せず引き継ぐのは、失うと取り返しのつかない損失になるからです。単に遅延が生じるだけでなく、コレクターのウォーターマークがスプール内のデータより先に進んでしまっているため、そのトランスクリプトの範囲は二度と読まれることがありません。移行処理はデーモンに対して、完了次第スプールを配信するよう指示するため、通常は引き継ぐべきデータが残っていない状態になります。
</Note>

新しいバージョンが `config.json`、`credentials.json`、`policies-config.json` に書き込んだキーは、古いバージョンで読み込む際も削除されずに保持されます。

## 残されるレコード

```
~/.failproofai/migrations/
  applied.json                 ステップごとに1エントリ：レイアウト、CLI、タイムスタンプ、所要時間、結果
  backup-layout<n>/            最初のステップ実行前に取得した、置き換え不可能なファイルのコピー
```

`applied.json` は「このマシンで実際に何が行われたか」を示すものです。アップグレード後に問題が発生した場合、最初に確認すべき情報です。バグレポートにはこのファイルを添付してください。

バックアップはディレクトリ全体のコピーではなく、意図的に小さく保たれています。移行処理は設計上、置き換え不可能なものを削除しません。そのため、保険をかける必要があるのは**ステップのバグ**に対してであり、そのようなバグが影響を与えるのはこれらのわずかなファイルだけです。

## ステップが失敗した場合

ステップが失敗した時点でチェーンが停止します。`VERSION` は完了したステップによってのみ更新されるため、ホームディレクトリは古いレイアウトのままとなり、次のコマンド実行時にリトライされます。部分的な移行が完了したとしてホームが最新状態とみなされることはありません。ステップは `applied.json` に `"ok": false` として記録され、バックアップは取得された場所に残ります。

## 新しいホームは移行されず拒否される

`~/.failproofai/` が現在実行中の failproofai よりも**新しい**バージョンによって書き込まれた場合、コマンドは停止し、代わりにアップグレードするよう指示します。そのデータに問題はなく、新しい CLI で正常に読み込めます。そこから「前方に」移行するという概念は存在せず、リセットすると回復可能なデータが失われます。

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

デーモンも同じルールを適用します。`failproofaid` は対応していないレイアウトに対しては起動を拒否します。移動したパスを読み書きするのではなく、起動しないという選択をします。
