```bash
failproofai migrate --dry-run   # exibe o plano, sem alterar nada
failproofai migrate             # executa a migração
```

A maioria das pessoas nunca precisa digitar isso. O comando roda automaticamente no primeiro uso após uma atualização, e o [`failproofai update`](/pt-br/cli/update) já o inclui. Use-o diretamente quando quiser ver o plano antes de executá-lo, ou para rodar a migração de forma isolada.

## Baseado no layout, não na versão

`~/.failproofai/VERSION` registra um número de **layout** — a estrutura do diretório, não a versão que o criou. As migrações são vinculadas a esse número, o que torna saltos longos baratos:

- As versões do npm mudam a cada release, podendo haver dezenas delas entre dois layouts.
- Assim, uma máquina que pula trinta releases **sem mudança de layout** executa **zero** migrações, e não trinta operações sem efeito.
- E uma máquina que pula vários layouts de uma vez executa cada etapa em ordem, sendo que cada etapa conhece apenas suas próprias duas extremidades.

Isso importa porque o npm não consegue atualizar um pacote instalado sozinho. Uma máquina que fica em uma versão por meses e depois avança vários layouts é o caso normal, não o excepcional.

## O dry run

`--dry-run` exibe a cadeia exata e os arquivos que seriam salvos antes, sem alterar absolutamente nada — sem migração, sem backup, sem registro no ledger:

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## O que é preservado e o que é reconstruído

Cada caminho no diretório home declara que tipo de dado contém, e isso determina se uma migração pode descartá-lo. A regra: **dados derivados e que podem ser obtidos novamente podem ser descartados; qualquer coisa que você digitou, qualquer coisa ainda não entregue e qualquer coisa que identifica a máquina é preservada.**

| Preservado | Reconstruído ou obtido novamente |
|---|---|
| `config.json` — configurações, `daemon.configured`, caminhos de captura extras | O cache de auditoria |
| `credentials.json` — seu registro na nuvem | Deployments gerenciados na nuvem (obtidos novamente e verificados por digest na próxima consulta) |
| `policies-config.json` — sua seleção de políticas e parâmetros | Estado temporário do daemon |
| `policies/` — seus próprios arquivos de política e os helpers que eles importam | |
| `hook-activity/` — o log de decisões que o dashboard lê | |
| Eventos não entregues ainda na fila para upload | |
| `cursors/` — marcadores d'água do coletor | |
| O binário do daemon em `bin/` | |

<Note>
  Os eventos não entregues são preservados em vez de descartados porque a perda seria permanente, não apenas lenta: o marcador d'água do coletor já avançou além de qualquer coisa no spool, então nada jamais leria aquele intervalo de uma transcrição novamente. A migração também solicita ao daemon que entregue o que está no spool assim que terminar, então o resultado habitual é que não há nada a preservar.
</Note>

Chaves que uma versão *mais recente* gravou em `config.json`, `credentials.json` ou `policies-config.json` também são preservadas, em vez de serem descartadas por um leitor mais antigo.

## O registro que fica

```
~/.failproofai/migrations/
  applied.json                 uma entrada por etapa: layout, CLI, timestamp, duração, resultado
  backup-layout<n>/            cópias dos arquivos insubstituíveis, tiradas antes da primeira etapa
```

`applied.json` é o que responde à pergunta "o que esta máquina realmente passou" — a primeira coisa a verificar quando algo parece errado após uma atualização. Anexe-o a um relatório de bug.

O backup é deliberadamente pequeno em vez de uma cópia do diretório inteiro: a migração não exclui mais nada insubstituível por design, então o que vale proteger é um *defeito em uma etapa*, e esses poucos arquivos são onde tal defeito causaria dano.

## Se uma etapa falhar

A cadeia para ali. `VERSION` é atualizado apenas por uma etapa concluída com sucesso, então o diretório home permanece marcado com seu layout antigo e o próximo comando tenta novamente — um diretório home nunca é marcado como atual com base em uma migração parcial. A etapa é registrada em `applied.json` com `"ok": false`, e o backup permanece onde foi criado.

## Um diretório home mais novo é recusado, não migrado

Se `~/.failproofai/` foi escrito por um failproofai **mais novo** do que o que você está executando, o comando para e pede para você fazer upgrade. Esses dados estão íntegros e uma CLI mais nova os lê; migrar "para frente" a partir deles não é algo que existe, e reiniciá-los destruiria algo recuperável.

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

O daemon aplica a mesma regra: `failproofaid` se recusa a iniciar com um layout que não conhece, em vez de ler e escrever em caminhos que foram movidos.
