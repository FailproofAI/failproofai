---
title: Atualizar após um upgrade
description: "Conclua a metade de um upgrade que o npm não consegue fazer: migrar o diretório home e sincronizar o daemon"
---

```bash
npm install -g failproofai@latest && failproofai update
```

Esse é o upgrade completo. O `npm` substitui o CLI; o `failproofai update` cuida do restante.

## Por que existe um segundo comando

O `npm install -g` substitui apenas uma coisa — o CLI. Outras duas partes de uma instalação do failproofai ficam fora do pacote propositalmente, e nenhuma delas é movida quando o npm é executado:

- **`~/.failproofai/`**, suas configurações, registro na nuvem, seleção de políticas e histórico. Uma nova versão pode organizá-los de forma diferente, e essa reorganização precisa ser feita por código que conhece ambos os formatos.
- **O binário do daemon `failproofaid`**, em `~/.failproofai/bin/failproofaid-<version>`. Ele deliberadamente *não* fica dentro de `node_modules`: um upgrade que substituísse o arquivo enquanto o serviço está em execução apontaria um daemon ativo para um binário compilado a partir de um código-fonte diferente, e remover o pacote o excluiria de baixo de um serviço que passaria a entrar em loop de falha a cada inicialização.

Portanto, após apenas o `npm install -g`, o CLI está atualizado, mas o daemon não está. O `failproofaid` se recusa a iniciar com um layout de diretório home que não reconhece — a versão ruidosa dessa incompatibilidade, e não a silenciosa — então as duas metades precisam ser sincronizadas. O `failproofai update` é essa etapa.

## O que ele faz

<Steps>
  <Step title="Executa quaisquer migrações de layout pendentes">
    Lê o layout registrado em `~/.failproofai/VERSION` e executa as etapas necessárias para atualizá-lo para o que esta versão utiliza. Normalmente nenhuma — consulte [`failproofai migrate`](/pt-br/cli/migrate).
  </Step>
  <Step title="Instala o binário do daemon correspondente">
    A partir do pacote de plataforma que o npm já baixou, quando possível (sem necessidade de rede), ou do asset de release desta versão exata, verificado via SHA-256 antes do uso.
  </Step>
  <Step title="Reinicia o serviço e confirma que ele voltou a funcionar">
    Verificado ativamente, não assumido — um gerenciador de serviços reporta um processo como ativo no momento em que ele é criado, o que não é o mesmo que estar funcionando corretamente.
  </Step>
</Steps>

## Opções

| Flag | Efeito |
|------|--------|
| `--no-daemon` | Migra apenas o diretório home, deixando o daemon na sua versão atual. |

<Warning>
  O `--no-daemon` deixa um daemon com versão desatualizada em execução. Em uma máquina configurada para exigir o daemon, cada evento de hook **falha de forma fechada** se o daemon não conseguir responder — e um daemon que se recusa a iniciar com um diretório home migrado não conseguirá responder. Prefira deixar a metade do daemon ser executada.
</Warning>

## Se algo der errado

O comando termina com código diferente de zero e informa qual metade falhou. Dois casos que vale conhecer:

- **Uma etapa de migração não foi concluída.** O diretório home é mantido marcado com seu layout *antigo*, para que o próximo comando tente novamente — nenhum diretório home é marcado como atual com base em uma migração parcial. Cópias das suas configurações e registro foram salvas antes de qualquer execução, em `~/.failproofai/migrations/backup-layout<n>/`.
- **O daemon não pôde ser reiniciado sem uma senha.** O `sudo -n` é usado deliberadamente, para que nada solicite uma senha a partir de uma tela de progresso. O comando imprime a linha exata para você executar manualmente.

<Note>
  Nada aqui requer o assistente de configuração interativo. Suas configurações, registro na nuvem e seleção de políticas sobrevivem a um upgrade, portanto uma máquina migrada aplica exatamente as mesmas regras de antes — o que é mais importante nas máquinas sem ninguém à frente delas: um runner de CI, uma máquina em uma frota, um gateway headless.
</Note>

## Automatizando

O `failproofai update` é não interativo e seguro para executar quando não há nada a fazer — ele reporta "nenhuma migração foi necessária" e termina com código 0. Adicioná-lo após cada upgrade em um script de provisionamento ou Dockerfile é o uso pretendido:

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

(`--no-daemon` em uma build de imagem, onde ainda não há serviço para reiniciar.)
