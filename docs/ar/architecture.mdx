تشرح هذه الوثيقة كيف يعمل failproofai داخليًا: كيف يعترض نظام الخطاف استدعاءات أداة الوكيل، وكيف يتم تحميل الإعدادات ودمجها، وكيف يتم تقييم السياسات، وكيف تراقب لوحة المعلومات نشاط الوكيل.

---

## نظرة عامة

failproofai يتضمن نظامين فرعيين مستقلين:

1. **معالج الخطاف** - عملية CLI سريعة يستدعيها Claude Code عند كل استدعاء أداة وكيل. يقيّم السياسات ويعيد قرارًا.
2. **مراقب الوكيل (لوحة المعلومات)** - تطبيق ويب Next.js لمراقبة جلسات الوكيل وإدارة السياسات.

كلا النظامين يشتركان في ملفات الإعدادات في `~/.failproofai/` وفي دليل `.failproofai/` بالمشروع، لكنهما يعملان كعمليات منفصلة ويتواصلان فقط عبر نظام الملفات.

## معالج الخطاف

### التكامل مع Claude Code

عند تشغيل `failproofai policies --install`، تتم كتابة إدخالات مثل هذه في `~/.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "failproofai --hook PreToolUse"
          }
        ]
      }
    ],
    "PostToolUse": [ ... ]
  }
}
```

ثم يستدعي Claude Code `failproofai --hook PreToolUse` كعملية فرعية قبل كل استدعاء أداة، ويمرر بيانات JSON على stdin.

### تنسيق الحمل

```json
{
  "session_id": "abc123",
  "transcript_path": "/home/user/.claude/projects/myproject/sessions/abc123.jsonl",
  "cwd": "/home/user/myproject",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "sudo apt install nodejs" }
}
```

لأحداث `PostToolUse`، يتضمن الحمل أيضًا `tool_result` بمخرجات الأداة.

يفرض المعالج حد أقصى بحجم 1 MB لـ stdin. الحمول التي تتجاوز هذا الحد يتم تجاهلها وجميع السياسات تسمح ضمنيًا.

### تنسيق الاستجابة

**الرفض (PreToolUse):**
```json
{
  "hookSpecificOutput": {
    "permissionDecision": "deny",
    "permissionDecisionReason": "Blocked by failproofai: sudo command blocked"
  }
}
```

**الرفض (PostToolUse):**
```json
{
  "hookSpecificOutput": {
    "additionalContext": "Blocked by failproofai because: API key detected in output"
  }
}
```

**التعليمات (أي حدث ما عدا Stop):**
```json
{
  "hookSpecificOutput": {
    "additionalContext": "Instruction from failproofai: Verify tests pass before committing."
  }
}
```

**تعليمات حدث التوقف:**
- رمز الخروج: `2`
- السبب مكتوب على stderr (وليس stdout)

**السماح:**
- رمز الخروج: `0`
- stdout فارغ

**السماح برسالة:**

`allow(message)` يسمح لسياسة بإرسال سياق معلومات إلى Claude حتى عند السماح بالعملية. يكتب معالج الخطاف JSON التالي إلى **stdout** (وليس ملف إعدادات — هذه استجابة المعالج إلى Claude Code، تماماً كاستجابات الرفض والتعليمات أعلاه):

```json
// مكتوب على stdout بواسطة عملية معالج الخطاف
{
  "hookSpecificOutput": {
    "additionalContext": "All CI checks passed on branch 'feat/my-feature'."
  }
}
```
- رمز الخروج: `0` (العملية مسموحة)
- عندما تعيد سياسات متعددة `allow` برسالة، يتم دمج رسائلها بفواصل أسطر في سلسلة `additionalContext` واحدة
- إذا لم توفر أي سياسة رسالة، يكون stdout فارغًا (نفس الحالة السابقة)

### خط معالجة

`src/hooks/handler.ts` ينفذ خط المعالجة الكامل:

```text
stdin JSON
  → parse payload (max 1 MB)
  → extract session metadata (session_id, cwd, tool_name, tool_input, etc.)
  → readMergedHooksConfig(cwd)    ← merges project + local + global config
  → register enabled builtin policies with resolved params
  → load custom policies from customPoliciesPath (if set)
  → register custom policies into policy registry
  → evaluate all policies (builtins first, then custom)
      → first deny short-circuits
      → instruct decisions accumulate
      → allow messages accumulate
  → write JSON decision to stdout
  → persist event to ~/.failproofai/hook-activity/current.jsonl
  → exit
```

تعمل العملية بأكملها في أقل من 100ms للحمول النموذجية بدون استدعاءات LLM.

## تحميل الإعدادات

`src/hooks/hooks-config.ts` ينفذ تحميل إعدادات النطاق الثلاثي.

```text
[1] {cwd}/.failproofai/policies-config.json        ← project  (highest priority)
[2] {cwd}/.failproofai/policies-config.local.json  ← local
[3] ~/.failproofai/policies-config.json             ← global   (lowest priority)
```

منطق الدمج:
- `enabledPolicies` - اتحاد منزوع الجكاف عبر جميع الملفات الثلاثة
- `policyParams` - لكل سياسة، أول ملف يحددها يفوز بالكامل
- `customPoliciesPath` - أول ملف يحددها يفوز
- `llm` - أول ملف يحددها يفوز

لوحة المعلومات الويب تستخدم `readHooksConfig()` (عام فقط) للقراءة والكتابة، حيث أنها لا تُستدعى بـ cwd للمشروع.

## تقييم السياسة

`src/hooks/policy-evaluator.ts` يشغّل السياسات بالترتيب.

لكل سياسة:

1. ابحث عن مخطط `params` للسياسة (إن كان لديها واحد).
2. اقرأ `policyParams[policy.name]` من الإعدادات المدمجة.
3. دمج القيم التي يوفرها المستخدم على قيم المخطط الافتراضية لإنتاج `ctx.params`.
4. استدعِ `policy.fn(ctx)` مع السياق المحل.
5. إذا كانت النتيجة `deny`، توقف فوراً وأرجع هذا القرار.
6. إذا كانت النتيجة `instruct`، اجمع الرسالة واستمر.
7. إذا كانت النتيجة `allow`، انتقل للسياسة التالية.

بعد تشغيل جميع السياسات:
- إذا تم إرجاع أي `deny`، أرسل استجابة الرفض.
- إذا تم جمع أي عودات `instruct`، أرسل استجابة تعليمات واحدة مع جميع الرسائل المجمعة.
- وإلا، أرسل استجابة السماح (stdout فارغ، خروج 0).

## السياسات المدمجة

`src/hooks/builtin-policies.ts` يعرّف جميع 39 سياسة مدمجة كائنات `BuiltinPolicyDefinition`:

```typescript
interface BuiltinPolicyDefinition {
  name: string;
  description: string;
  fn: (ctx: PolicyContext) => PolicyResult;
  match: {
    events: HookEventType[];
    tools?: string[];
  };
  defaultEnabled: boolean;
  category: string;
  beta?: boolean;
  params?: PolicyParamsSchema;
}
```

السياسات التي تقبل `params` تعلن عن `PolicyParamsSchema` بأنواع وقيم افتراضية لكل معامل. يحقن مقيم السياسة القيم المحلة في `ctx.params` قبل استدعاء `fn`. وظائف السياسة تقرأ `ctx.params` بدون حماية null لأن القيم الافتراضية يتم تطبيقها دائماً أولاً.

مطابقة النمط داخل السياسات تستخدم رموز الأوامر المحللة (argv)، وليس مطابقة السلسلة الخام. هذا يمنع التحايل عبر حقن عامل shell (على سبيل المثال، لا يمكن تجاوز نمط `sudo systemctl status *` بإضافة `; rm -rf /` للأمر).

## السياسات المخصصة

`src/hooks/custom-hooks-registry.ts` ينفذ سجل مدعوم بـ `globalThis`:

```typescript
const REGISTRY_KEY = "__failproofai_custom_hooks__";

export const customPolicies = {
  add(hook: CustomHook): void { ... }
};

export function getCustomHooks(): CustomHook[] { ... }
export function clearCustomHooks(): void { ... }  // used in tests
```

`src/hooks/custom-hooks-loader.ts` يحمل ملف سياسة المستخدم:

1. اقرأ `customPoliciesPath` من الإعدادات؛ تخطّ إذا كان غائباً.
2. حل المسار المطلق؛ تحقق من وجود الملف.
3. أعد كتابة جميع استيراد `from "failproofai"` للمسار dist الفعلي بحيث يتم حل `customPolicies` لنفس سجل `globalThis`.
4. أعد كتابة الاستيرادات المحلية العابرة بشكل متكرر لضمان التوافق مع ESM.
5. اكتب ملفات `.mjs` مؤقتة و `import()` ملف الإدخال.
6. استدعِ `getCustomHooks()` لاسترجاع الخطافات المسجلة.
7. نظّف جميع الملفات المؤقتة في كتلة `finally`.

في أي خطأ (ملف غير موجود، خطأ بناء جملة، فشل استيراد)، يتم تسجيل الخطأ في `~/.failproofai/hook.log` ويعيد المحمل مصفوفة فارغة. السياسات المدمجة لا تتأثر.

تُقيّم السياسات المخصصة بعد جميع السياسات المدمجة. رفض السياسة المخصصة يقطع السياسات المخصصة الأخرى (لكن جميع السياسات المدمجة قد تم تشغيلها بالفعل).

## تسجيل النشاط

بعد كل حدث خطاف، يضيف المعالج سطر JSONL إلى `~/.failproofai/hook-activity/current.jsonl`، والذي يدور إلى `page-<timestamp>-<seq>.jsonl` بمجرد الوصول إلى صفحة:

```json
{
  "timestamp": "2026-04-06T12:34:56.789Z",
  "sessionId": "abc123",
  "eventType": "PreToolUse",
  "toolName": "Bash",
  "policyName": "block-sudo",
  "decision": "deny",
  "reason": "sudo command blocked by failproofai",
  "durationMs": 12
}
```

سطر واحد لكل سياسة اتخذت قراراً غير سماح. قرارات السماح لا يتم تسجيلها (للحفاظ على حجم الملف صغيراً).

## معمارية لوحة المعلومات

لوحة المعلومات هي تطبيق **Next.js 16** يستخدم App Router مع React Server Components و Server Actions.

```text
app/
  layout.tsx                  ← Root layout (theme, telemetry, nav)
  projects/page.tsx           ← Server component: list all Claude projects
  project/[name]/page.tsx     ← Server component: list sessions in a project
  project/[name]/session/
    [sessionId]/page.tsx      ← Server component: render session viewer
  policies/page.tsx           ← Client component: policy management + activity log
  actions/
    get-hooks-config.ts       ← Read config + policy list
    update-hooks-config.ts    ← Toggle policy on/off
    update-policy-params.ts   ← Update policy parameters
    get-hook-activity.ts      ← Paginate/search activity log
    install-hooks-web.ts      ← Install/remove hooks from the browser
  api/
    download/[project]/[session]/route.ts   ← Per-CLI session export (JSONL or JSON)
```

**تدفق البيانات:**

- مكونات الصفحة تستدعي `lib/projects.ts` و `lib/log-entries.ts` لقراءة بيانات المشروع/الجلسة مباشرة من نظام الملفات (بدون طبقة API للقراءات).
- صفحة السياسات تستخدم Server Actions لجميع التغييرات (تبديل، تحديث المعاملات، التثبيت/الإزالة).
- عارض الجلسة يحلل تنسيق نسخ Claude JSONL ويرسل خط زمني للرسائل واستدعاءات الأداة.

**قرارات التصميم الرئيسية:**

- بدون قاعدة بيانات - جميع الحالة الدائمة في ملفات عادية (`~/.failproofai/`, `~/.claude/projects/`).
- Server Actions للتغييرات - لا توجد حاجة لـ REST API لعمليات CRUD.
- React Server Components لصفحات القراءة - تحميل أولي أسرع، بدون bundle عميل لجلب البيانات.
- مكونات العميل فقط حيث تكون التفاعلية مطلوبة (تبديلات السياسة، بحث النشاط، عارض السجل).
