سياق الوكيل يخبر المراجعات بالغرض من وجود كل وكيل، وما يجب أن ينتجه، وما يجب أن لا يفعله أبداً. يخزن Failproof AI هذا السياق كعقد وكيل واحد لكل وكيل.

ينتمي سياق الوكيل إلى المنظمة، وليس إلى مراجعة واحدة. تكتبها مرة واحدة لكل وكيل، وكل مراجعة مدعومة بنموذج نطاقها يشمل ذلك الوكيل يستخدمها.

## إضافة سياق الوكيل

<Tabs>
  <Tab title="لوحة التحكم">
    1. انتقل إلى **Analyze → audits**، وحدد **agents**، واختر معرّف الوكيل الذي أبلغت عنه جلساته.
    2. حدد **add content** أو **edit**.
    3. اشرح ما يخدمه الوكيل، وما يجب أن ينتجه، وما يعني "تم"، وكم مرة يجب أن يعمل، وما يجب أن لا يفعله أبداً.
    4. احفظ السياق، ثم عد إلى نموذج المراجعة وتأكد من أن الوكيل المحدد يظهر كمغطى.

    ![درج أجهزة المراجعة المستخدم لإضافة الغرض والإيقاع والمخرجات وشروط الإنجاز والسلوك المحظور للوكيل.](/images/dashboard/agent-context.png)

    يمكنك أيضاً إضافة أو تحرير سياق الوكيل من درج **agents** أثناء إنشاء أو تحرير مراجعة. يتم حفظه بشكل مستقل ويكون متاحاً على الفور لكل مراجعة مطبقة.
  </Tab>
  <Tab title="CLI">
    لم يكشف Cloud CLI بعد عن أوامر العقد. استخدم API العام بمفتاح يحمل `audits:read` و `audits:write`:

    ```bash
    curl -X POST "https://app.befailproof.ai/v1/audits/contracts" \
      -H "Authorization: Bearer $FAILPROOFAI_KEY" \
      -H "Content-Type: application/json" \
      -d '{
        "agent_id": "nightly-reconciler",
        "enabled": true,
        "body": "# Purpose\nReconcile yesterday'\''s payouts.\n\n## Outputs\nPublish a signed summary.\n\n## Must not\nNever modify ledger entries."
      }'
    ```

    اسرد العقود باستخدام `GET /v1/audits/contracts`؛ استرجع عقد واحد باستخدام `GET /v1/audits/contracts/{id}`. يتطلب التحديث باستخدام `PUT` استبدال كامل ويتطلب كلاً من `agent_id` و `body`.
  </Tab>
</Tabs>

## كتابة سياق مفيد

اجعل السياق أقل من 5000 حرف واجعله قابل للاختبار. السياق المفيد عادة يحتوي على:

- **الغرض:** لماذا يوجد الوكيل
- **المخرجات:** القطع الأثرية أو الإجراءات التي يجب أن ينتجها
- **تم عندما:** الشرط الذي يجعل التشغيل ناجحاً
- **الإيقاع:** كم مرة أو متى يجب أن يعمل
- **يجب أن لا:** الإجراءات والنتائج التي تكون غير مقبولة دائماً

```markdown
---
agent: nightly-reconciler
purpose: Reconcile yesterday's payouts and publish a signed summary.
cadence: Once daily after 02:00 UTC. Never more than once.
---

## Outputs
- A signed reconciliation summary in the finance channel.

## Done when
- Every payout is matched or explicitly flagged.

## Must not
- Modify ledger entries. Report discrepancies instead.
```

سياق الوكيل يصف السلوك المتوقع؛ لا يمكنه أن يخبر التحليل بالاستنتاج الذي يجب الوصول إليه أو تقييد الأدلة التي يفحصها. يتم التدقيق في الوكلاء بدون سياق بشكل طبيعي، لكن Failproof AI لا يمكنه الحكم على سلوكهم مقابل النية المحددة بواسطة المنظمة.

## إيقاف أو تغيير سياق الوكيل

- أيقف سياق الوكيل عندما يجب أن تتجاهل المراجعات مؤقتاً. الإيقاف قابل للعكس.
- عدّل السياق عند تغيير مسؤولية الوكيل. يسري النص الجديد على التشغيلات المستقبلية.
- تحقق من **last matched** عندما لا يبدو أن وكيل جارٍ يستخدم سياقه أبداً. هذا عادة يعني أن معرّف الوكيل الخاص به لا يطابق التلمترا.
- احذف من خلال API فقط عندما يجب تدمير النص بشكل دائم. تقدم لوحة التحكم عمداً الإيقاف بدلاً من الحذف.

كل تشغيل مراجعة يخزن لقطة سياق الوكيل بالضبط التي استخدمها. لا يؤدي تحرير أو إيقاف أو حذف مورد العقد الحالي إلى إعادة كتابة أساس النتائج السابقة.

<Info>
  يتطلب قراءة العقود `audits:read`. يتطلب إنشاء أو تحرير أو إيقاف أو حذفها `audits:write`.
</Info>
