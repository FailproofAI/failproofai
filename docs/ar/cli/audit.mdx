  **ميزة تجريبية.** يتم شحن التدقيق كإصدار تجريبي بينما نجمع التعليقات المبكرة.
  قد يتغير كتالوج الكاشف وتنسيق التقرير قبل الإصدار المستقر التالي.

يعيد التدقيق تشغيل نصوص agent-CLI السابقة من خلال محرك السياسة في failproofai ويعرض تقرير مرئي قابل للمشاركة على **صفحة لوحة المعلومات `/audit`** — نمط الوكيل الخاص بك، درجة من 0 إلى 100، والسياسات التي كان ستلتقط بالضبط.

## قم بتشغيله

ثلاث طرق للدخول — جميعها تؤدي إلى نفس تقرير `/audit`.

<CodeGroup>

```bash npx (no install)
npx -y failproofai audit
```

```bash failproofai audit
failproofai audit
```

```bash failproofai (dashboard)
failproofai
```

</CodeGroup>

<Tip>

</Tip>

تفحص لوحة المعلومات نصوص agent CLI السابقة على هذا الجهاز (Claude Code و Codex و Copilot و Cursor و OpenCode و Pi) وتقرر عدد المرات التي قام فيها الوكيل بأشياء بُني failproofai للتوقف عنها — فحوصات متغيرات البيئة، عمليات الدفع القسرية، بادئات `cd <cwd>` الزائدة، حلقات sleep-polling، إعادة قراءة الملفات المحررة للتو، والمزيد.

لكل نص، يتم إعادة تشغيل كل حدث tool-use من خلال 39 سياسة مدمجة **و** من خلال 8 كاشفات مخصصة للتدقيق فقط تلتقط أنماط لم تغطيها السياسات الوقتية بعد. يتم تجميع الأعداد لكل سياسة / كاشف عبر جميع الجلسات.

## ما الذي ستحصل عليه

صفحة `/audit` عبارة عن **ملصق** بشاشة واحدة وقابل للمشاركة متبوعاً بأربعة أقسام أسفل الطية:

1. **الملصق** — هوية الوكيل في نظرة سريعة: **النمط الخاص به** (واحد من 8 — `متفائل`، `متهور`، `مستكشف`، `سمكة ذهبية`، `معماري متخوف`، `بناء دقيق`، `مطرقة`، `شبح`)، كلمات شخصيته الرئيسية، ندرة هذا النمط، و**درجة من 0 إلى 100** مع نطاق تصنيف (`S` إلى `المستوى الأدنى`). مبني للمشاركة — نشره على X أو LinkedIn، أو قم بتنزيله كصورة PNG.
2. **`// strengths`** — ما يفعله الوكيل بالفعل بشكل جيد، كأرقام حقيقية من الفحص (مثل نسبة clean-tool-call ٪، `0` محاولات push-to-main)، يُعرض فقط حيث تحتفظ السياسة ذات الصلة بسجل نظيف.
3. **`// quirks`** — ما مرّ: جدول مرتب حسب الأولوية للسلوكيات التي كان failproofai سيلتقطها — *متى* حدثت آخر مرة، *ما مرّ* (والمدمج الذي كان سيوقفه)، *شدتها*، وعدد مرات *مشاهدتها* (`جديد` / `متكرر` / `N× شوهد`).
4. **`// how to improve`** — قائمة الإصلاح الموصوفة: صف واحد لكل سياسة مع نسخ و لصق `failproofai policy add <slug>`، بالإضافة إلى زر **تثبيت الكل** الذي يمكّن كل التوصيات في نفس الوقت ويظهر **درجتك المتوقعة** إذا فعلت ذلك.
5. **`// come back better`** — بناء العادة: قم بتعيين إعادة تدقيق البريد الإلكتروني **الذكرى** (`3d` / `7d` / `14d` / `30d`) أو أعد التدقيق الآن، و**اطلب من صديق** تشغيل التدقيق الخاص به (مرسل من failproof.ai، Cc لك). تتطلب الذكريات والدعوات تسجيل الدخول.

## التدقيقات المجدولة

إذا قمت بتشغيل **daemon failproofaid** (انظر [`failproofai config`](/ar/cli/install-policies))،
يمكنه إعادة تشغيل التدقيق لك وفقاً لجدول زمني وتحديث تقرير `/audit` في الخلفية. إنها **معطلة بشكل افتراضي**، لأن الفحص يقرأ *محتويات* كل نص جلسة وكيل على هذا الجهاز — لا شيء يفحص على مؤقت حتى تطلب ذلك.

قم بتشغيله في `~/.failproofai/config.json` — أضف مفتاح `audit` بجانب أي شيء آخر قد يحتويه الملف:

```json
{
  "audit": {
    "auto": true,
    "interval_days": 7
  }
}
```

| المفتاح | المعنى |
|---|---|
| `auto` | `true` يمكّن الفحص المجدول. أي شيء آخر — غير موجود، `false`، `"yes"` — معطل. |
| `interval_days` | الأيام بين الفحوصات. مثبتة على 1–90؛ `0`، رقم سالب أو قيمة غير رقمية يعود إلى `7`. |

- الجدول **wall-clock**، لذا فهو يبقى سليماً من التعليق وإعادة التشغيل: يقوم جهاز كمبيوتر محمول كان نائماً بعد وقته المحدد بالتشغيل **مرة واحدة** عند الاستيقاظ، أبداً متراكم الفحوصات.
- كل عملية تشغيل عبارة عن عملية منفصلة ذات أولوية منخفضة (`nice 19`) — أبداً مسار hook للـ daemon، الذي يبقى حراً للإجابة على استدعاءات الأدوات.
- يتم تخطي الفحص إذا كان `failproofai audit` أو إعادة التشغيل من لوحة المعلومات قيد التشغيل بالفعل؛ يتم إعادة محاولته قريباً بدلاً من اعتباره فشلاً.
- يتم كتابة التقدم إلى `~/.failproofai/state/audit-schedule.json` (آخر عملية تشغيل، المستحقة بعد ذلك). يملك daemon هذا الملف — غيّر الإيقاع في `config.json`.

<Note>
إذا قمت بتمكين هذا على جهاز تم إعداده بواسطة failproofai أقدم، قم بتشغيل
`failproofai config` مرة واحدة. يحتاج تعريف خدمة daemon إلى إدخال إضافي واحد
قبل أن يتمكن من تشغيل CLI، والتحديث جزء من هذا الأمر.
</Note>

## كاشفات مخصصة للتدقيق فقط

تكتشف هذه أنماط السلوك "الحمقاء" التي لا يتم (بعد) فرضها في الوقت الفعلي. تعمل فقط أثناء التدقيق ولا تمنع أبداً استدعاء أداة مباشرة.

| الكاشف | ما يعده |
|---|---|
| `redundant-cd-cwd` | أوامر Bash تبدأ بـ `cd <cwd> && …` على الرغم من أن الأوامر تعمل بالفعل في `cwd`. |
| `prefer-edit-over-read-cat` | `cat`/`head`/`tail`/`less`/`more` على ملف مصدر واحد — استخدم أداة `Read`. |
| `prefer-edit-over-sed-awk` | تحريرات في المكان لـ `sed -i` / `awk … > file` — استخدم أداة `Edit`. |
| `prefer-write-over-heredoc` | Heredoc / كتابة الملفات متعددة الأسطر `echo > file` — استخدم أداة `Write`. |
| `sleep-polling-loop` | `sleep N` طويل (≥ 30s) أو حلقات polling `while …; sleep …; done`. |
| `find-from-root` | `find /`، `find /home`، `find /usr`، إلخ. — اقصر على `cwd` بدلاً من ذلك. |
| `git-commit-no-verify` | `git commit … --no-verify` / `-n`، تخطي الخطافات. |
| `reread-after-edit` | `Read` لملف تم `Edit`/`Write` للتو في نفس الجلسة. |

## ذاكرات التخزين المؤقت

- **ذاكرة تخزين مؤقت لكل نص** في `~/.failproofai/cache/audit/<sha1>.json` مفهرسة بـ `(mtime, size, engineVersion, detectorVersion)` — تبطل تلقائياً عندما يتغير النص أو كود السياسة/الكاشف. تخزن كل إدخالة أيضاً **طابع زمني TTL** `cachedAt` (ليس جزء من مفتاح الذاكرة); يتم رفض الإدخالات الأقدم من **7 أيام** عند القراءة حتى لا تتجاوز النتائج طويلة الأجل نية الكاشف المتطورة.
- **ذاكرة تخزين مؤقت للنتيجة الكاملة** في `~/.failproofai/audit-dashboard.json` (mode 0600). يسمح لوحة المعلومات بالتصيير فوراً عند التنقل دون إعادة التشغيل. يتم رفضها أيضاً عند القراءة بعد **TTL بـ 7 أيام** — يقع `/audit` بعد ذلك في حالته الفارغة ويدعوك لتشغيل جديد. انقر فوق `[ re-audit now ]` بالقرب من أسفل التقرير للتحديث — تُرسل إعادة التدقيق `noCache: true`، لذلك فهو يتجاوز ذاكرة التخزين المؤقت لكل نص ويعاد فحص كل نص بدلاً من إرجاع النتيجة المخزنة مؤقتاً؛ يتدفق التشغيل التقدم عبر شريط ثابت في الأعلى ويستبدل النتيجة في مكانها عند النجاح (بدون إعادة تحميل الصفحة؛ تحتفظ إعادة تدقيق فاشلة بالتقرير السابق).

## ملاحظات

- **بدون تغيير.** يعاد التدقيق في وضع القراءة فقط. يتم تخطي `warn-repeated-tool-calls` لأن ملف مرافق في الجلسة سيتم تعديله وإلا.
- **سياسات سير العمل المخطوطة.** تُطلق سياسات `require-*-before-stop` فقط على أحداث `Stop` و `execSync` مقابل حالة git المباشرة — ليس لديها تفسير معنوي "ماذا كان سيحدث في 2025"، لذا لا تظهر في عدد التدقيق.
- **السياسات المخصصة المخطوطة.** لا يتم إعادة تشغيل الخطافات المخصصة التي يوفرها المستخدم (قد تكون قد تغيرت منذ الجلسة الأصلية).
