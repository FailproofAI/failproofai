يستخدم failproofai ملفات تكوين JSON للتحكم في السياسات النشطة وكيفية تصرفها وحيث يتم تحميل السياسات المخصصة. تم تصميم التكوين ليكون سهل المشاركة مع فريقك - قم بالتزامه في المستودع الخاص بك وسيحصل كل مطور على نفس شبكة الأمان للوكيل.

---

## نطاقات التكوين

هناك ثلاثة نطاقات تكوين، يتم تقييمها حسب أولويتها:

| النطاق | مسار الملف | الغرض |
|-------|-----------|---------|
| **المشروع** | `.failproofai/policies-config.json` | إعدادات لكل مستودع، ملتزمة بالتحكم بالإصدار |
| **محلي** | `.failproofai/policies-config.local.json` | تجاوزات شخصية لكل مستودع، مُستثناة من git |
| **عام** | `~/.failproofai/policies-config.json` | إعدادات افتراضية على مستوى المستخدم عبر جميع المشاريع |

عندما يتلقى failproofai حدث hook، يقوم بتحميل ودمج جميع الملفات الثلاثة الموجودة للدليل الحالي.

### قواعد الدمج

**`enabledPolicies`** - اتحاد جميع النطاقات الثلاثة. السياسة المُفعلة في أي مستوى نشطة.

```text
project:  ["block-sudo"]
local:    ["block-rm-rf"]
global:   ["block-sudo", "sanitize-api-keys"]

resolved: ["block-sudo", "block-rm-rf", "sanitize-api-keys"]  ← اتحاد مُزال التكرار
```

**`policyParams`** - النطاق الأول الذي يحدد معاملات لسياسة معينة يفوز تماماً. لا يوجد دمج عميق للقيم داخل معاملات السياسة.

```text
project:  block-sudo → { allowPatterns: ["sudo apt-get update"] }
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo apt-get update"] }   ← المشروع يفوز، العام مُتجاهل
```

```text
project:  (لا توجد إدخالات block-sudo)
local:    (لا توجد إدخالات block-sudo)
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo systemctl status"] }  ← السقوط إلى العام
```

**`customPoliciesPaths` / `customPoliciesPath`** - النطاق الأول الذي يحدد أي شكل يفوز.

**`disabledCustomPolicies`** - اتحاد عبر جميع النطاقات. لوحة التحكم تكتب معرفاً مؤهلاً بالمصدر هنا عند إيقاف سياسة فردية من ملف سياسة صريح أو اتفاقي. السياسات غير المدرجة تبقى مُفعلة افتراضياً؛ المعرفات تتضمن ملف المصدر حتى يمكن التحكم في السياسات ذات الأسماء المتطابقة في ملفات متعددة بشكل مستقل.

**`llm`** - النطاق الأول الذي يحدده يفوز.

## تنسيق ملف التكوين

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "sanitize-jwt",
    "block-env-files",
    "block-read-outside-cwd"
  ],
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release", "prod"]
    },
    "block-rm-rf": {
      "allowPaths": ["/tmp"]
    },
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company"]
    },
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo API key" }
      ]
    },
    "warn-large-file-write": {
      "thresholdKb": 512
    }
  },
  "customPoliciesPath": "/home/alice/myproject/my-policies.js"
}
```

## مرجع الحقول

### `enabledPolicies`

النوع: `string[]`

قائمة أسماء السياسات المراد تفعيلها. يجب أن تطابق الأسماء بدقة معرفات السياسات التي يظهرها `failproofai policies`. راجع [السياسات المدمجة](/ar/built-in-policies) للحصول على القائمة الكاملة.

السياسات غير الموجودة في `enabledPolicies` غير نشطة، حتى لو كان لديها إدخالات في `policyParams`.

### `policyParams`

النوع: `Record<string, Record<string, unknown>>`

تجاوزات معاملات لكل سياسة. المفتاح الخارجي هو اسم السياسة؛ المفاتيح الداخلية خاصة بالسياسة. توثق كل سياسة معاملاتها المتاحة في [السياسات المدمجة](/ar/built-in-policies).

إذا كانت لدى السياسة معاملات لكنك لم تحددها، يتم استخدام القيم الافتراضية المدمجة للسياسة. المستخدمون الذين لا يقومون بتكوين `policyParams` على الإطلاق يحصلون على نفس السلوك من الإصدارات السابقة.

المفاتيح غير المعروفة داخل كتلة معاملات السياسة يتم تجاهلها بصمت في وقت حريق hook لكن يتم وضع علم لها كتحذيرات عند تشغيل `failproofai policies`.

#### `hint` (شامل)

النوع: `string` (اختياري)

رسالة مضافة إلى السبب عند عودة السياسة `deny` أو `instruct`. استخدمه لإعطاء Claude إرشادات قابلة للتنفيذ دون تعديل السياسة نفسها.

يعمل مع أي نوع سياسة — مدمجة أو مخصصة (`custom/`) أو اتفاقية مشروع (`.failproofai-project/`) أو اتفاقية مستخدم (`.failproofai-user/`).

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "جرب إنشاء فرع جديد بدلاً من ذلك."
    },
    "block-sudo": {
      "allowPatterns": ["sudo apt-get"],
      "hint": "استخدم apt-get مباشرة بدون sudo."
    },
    "custom/my-policy": {
      "hint": "اطلب موافقة المستخدم أولاً."
    }
  }
}
```

عند رفض `block-force-push`، يرى Claude: *"دفع القوة مسدود. جرب إنشاء فرع جديد بدلاً من ذلك."*

القيم غير النصية والنصوص الفارغة يتم تجاهلها بصمت. إذا لم يتم تعيين `hint`، السلوك لم يتغير (متوافق للخلف).

### `customPoliciesPath`

النوع: `string` (مسار مطلق)

مسار ملف JavaScript يحتوي على سياسات hook مخصصة. يتم تعيين هذا تلقائياً بواسطة `failproofai policies --install --custom <path>` (يتم حل المسار إلى مطلق قبل التخزين).

يتم تحميل الملف بشكل جديد في كل حدث hook - لا يوجد تخزين مؤقت. راجع [السياسات المخصصة](/ar/custom-policies) لتفاصيل التأليف.

### السياسات القائمة على الاتفاقيات

بالإضافة إلى `customPoliciesPath` الصريح، يكتشف failproofai تلقائياً ويحمل ملفات السياسات من أدلة `.failproofai/policies/`:

| المستوى | الدليل | النطاق |
|-------|----------|--------|
| المشروع | `.failproofai/policies/` | مشترك مع الفريق عبر التحكم بالإصدار |
| المستخدم | `~/.failproofai/policies/custom-policies/` | شخصي، ينطبق على جميع المشاريع |

<Note>
  تم نقل دليل مستوى المستخدم نزولاً على مستوى واحد في إعادة تنظيم دليل المنزل.
  الملفات المتروكة في `~/.failproofai/policies/` القديم يتم نقلها إلى `custom-policies/` تلقائياً
  في المرة الأولى التي تقوم فيها بتشغيل أي أمر `failproofai` بعد الترقية، والأمر يخبرك
  بأي ملفات تم نقلها.
</Note>

**مطابقة الملفات:** يتم تحميل الملفات فقط التي تطابق `*policies.{js,mjs,ts}` (على سبيل المثال `security-policies.mjs`، `workflow-policies.js`). الملفات الأخرى في الدليل يتم تجاهلها.

**لا توجد حاجة للتكوين:** سياسات الاتفاقيات لا تتطلب إدخالات في `policies-config.json`. فقط ضع الملفات في الدليل وسيتم التقاطها في حدث hook التالي.

**تحميل الاتحاد:** يتم مسح كل من دليل اتفاقيات المشروع والمستخدم. يتم تحميل جميع الملفات المطابقة من كلا المستويين (على عكس `customPoliciesPath` الذي يستخدم نطاق أول يفوز).

راجع [السياسات المخصصة](/ar/custom-policies) لمزيد من التفاصيل والأمثلة.

### `llm`

النوع: `object` (اختياري)

تكوين عميل LLM للسياسات التي تقوم باستدعاءات AI. غير مطلوب لمعظم الإعدادات.

```json
{
  "llm": {
    "model": "claude-sonnet-4-6",
    "apiKey": "sk-ant-..."
  }
}
```

## إدارة التكوين من CLI

تكتب أوامر `policies --install` و `policies --uninstall` إلى ملف إعدادات hook لـ CLI الوكيل الخاص بك (نقاط دخول hook)، بينما `policies-config.json` هو الملف الذي تدير مباشرة. الاثنان منفصلان:

- **إعدادات Agent CLI** — تخبر الوكيل باستدعاء `failproofai --hook <event>` في كل استخدام أداة:
  - **Claude Code**: `~/.claude/settings.json` (مستخدم)، `<cwd>/.claude/settings.json` (مشروع)، `<cwd>/.claude/settings.local.json` (محلي)
  - **OpenAI Codex**: `~/.codex/hooks.json` (مستخدم)، `<cwd>/.codex/hooks.json` (مشروع) — Codex ليس لديه نطاق محلي
  - **GitHub Copilot CLI _(beta)_**: `~/.copilot/hooks/failproofai.json` (مستخدم)، `<cwd>/.github/hooks/failproofai.json` (مشروع) — Copilot ليس لديه نطاق محلي. إدخالات Hook تستخدم حقول أوامر Copilot المفتاح-OS `bash`/`powershell` مع `timeoutSec`؛ الملف يحمل علامة `version: 1` على المستوى الأعلى. دعم Copilot CLI في **beta** بينما نتحقق من مخطط سجل `events.jsonl` (الذي لا تحدده الوثائق العامة) مقابل جلسات العالم الحقيقي الأخرى. **وضع وكيل VS Code Copilot Chat (معاينة)** يقرأ تكوينات hook من `.github/hooks/*.json`، `~/.copilot/hooks/*.json`، و `~/.claude/settings.json` (يتحكم بها الإعداد `chat.hookFilesLocations`) باستخدام نفس عقد Claude-shaped `{hookSpecificOutput:{permissionDecision:"deny",…}}` — المسارات الدقيقة التي تكتبها بالفعل دمج `copilot` و `claude` (`~/.claude/settings.json`)، لذا `failproofai policies --install --cli copilot` (أو `--cli claude`) **بالفعل ينفذ في وضع وكيل VS Code** بدون دمج منفصل `vscode` مطلوب (مؤكد مباشرة من سجلات اكتشاف VS Code).
  - **Cursor Agent _(beta)_**: `~/.cursor/hooks.json` (مستخدم)، `<cwd>/.cursor/hooks.json` (مشروع) — Cursor ليس لديه نطاق محلي. إدخالات Hook تستخدم النموذج Claude-shaped `{type, command, timeout}` (بدون انقسام `bash`/`powershell`)، لكن مخزنة تحت مفاتيح camelCase (`preToolUse`، `beforeSubmitPrompt`، …) في مصفوفة مسطحة لكل مخطط hook Cursor؛ الملف يحمل علامة `version: 1` على المستوى الأعلى. المعالج يطبيع camelCase → PascalCase عبر `CURSOR_EVENT_MAP` حتى تطلق السياسات المدمجة الموجودة دون تغيير. دعم Cursor Agent في **beta** بينما نتحقق من نص Cursor على تنسيق القرص (غير محدد في الوثائق العامة) مقابل عمليات تثبيت العالم الحقيقي الأخرى.
  - **OpenCode _(beta)_**: `~/.config/opencode/opencode.json` + `~/.config/opencode/plugins/failproofai.mjs` (مستخدم)، `<cwd>/.opencode/opencode.json` + `<cwd>/.opencode/plugins/failproofai.mjs` (مشروع) — OpenCode ليس لديه نطاق محلي. على عكس الخمسة CLIs الأخرى، OpenCode ليس لديه **نظام hook أمر خارجي**: يحمل في العملية JS/TS plugins بشكل صريح تم تسجيله عبر مصفوفة `plugin: []` في `opencode.json` (الاكتشاف التلقائي من `.opencode/plugins/` **ليس** كيف يتم تحميل plugins على opencode v1.14.33). Install ينزل شيم plugin صغير مُنتج يستدعي الملف الثنائي failproofai بـ subprocess ويترجم استجابة JSON على شكل Claude الثنائي مرة أخرى إلى دلالات plugin: `throw new Error()` لأداة رفع أداة الحدث (يلغي استدعاء الأداة)، `client.session.prompt(...)` ل instruct و للرفض `Stop` / `SubagentStop` (يرسل سبب الرفض كرسالة المستخدم التالية — قناة إعادة المحاولة الوحيدة القسرية منذ أن `session.idle` إخطار فقط ورمي من ذلك لا عملية)، وبدون عملية للسماح. شيم يطبيع أسماء أداة (حروف صغيرة → PascalCase عبر `OPENCODE_TOOL_MAP`) ومفاتيح arg للأداة (camelCase → snake_case عبر `OPENCODE_TOOL_INPUT_MAP` ل `Read` / `Write` / `Edit`، مثل `filePath` → `file_path`، `oldString` → `old_string`) قبل الإرسال إلى الملف الثنائي، لذا مسار التحقق builtins مثل `block-read-outside-cwd`، `block-env-files`، و `block-secrets-write` تطلق دون تغيير في استدعاءات OpenCode. الجلسات تعيش في قاعدة بيانات SQLite OpenCode في `~/.local/share/opencode/opencode.db`؛ عارض الجلسة لوحة التحكم يقرأها عبر `opencode db --format json` و `opencode export <id>`. دعم OpenCode في **beta** بينما نتحقق من السلوك عبر الإصدارات وضد جلسات العالم الحقيقي الأخرى. راجع [وثائق OpenCode plugins](https://opencode.ai/docs/plugins/).
  - **Pi _(beta)_**: `~/.pi/agent/settings.json` (مستخدم)، `<cwd>/.pi/settings.json` (مشروع) — Pi ليس لديه نطاق محلي. Pi يحمل حزم TypeScript extension في بدء التشغيل؛ ملف الإعدادات هو مصفوفة نصية مسطحة `{"packages": ["./relative/path", …]}`. failproofai يكتب إدخال مصفوفة packages واحد يشير إلى دليل `pi-extension/` المجمع الخاص به. الامتداد داخلياً يشترك في `tool_call` / `user_bash` / `input` / `session_start` أحداث Pi ويشغل `failproofai --hook <Event> --cli pi`؛ معالج يطبيع underscore_lower_snake_case → PascalCase عبر `PI_EVENT_MAP` حتى تطلق السياسات المدمجة الموجودة دون تغيير. args مدخلات الأداة يطبيعها أيضاً عبر `PI_TOOL_INPUT_MAP` (Pi's Read / Write / Edit توصل `path` بدلاً من `file_path`؛ mapping مفتاح المستوى الأعلى يترك `block-env-files` و `block-secrets-write` تطلق — `block-read-outside-cwd` بالفعل كان لديها `path` fallback). دعم Pi في **beta** بينما Pi's extension API وتخطيط session-log يستقر.
  - **Hermes (hermes-agent)**: `~/.hermes/config.yaml` (**نطاق مستخدم فقط** — Hermes ليس لديه تكوين مشروع/محلي). Hermes هو **بوابة** Slack/Telegram، لذا تثبيت واحد يعترض استدعاءات أداة من كل منصة (Slack/Telegram/cli/cron) **و** subagents داخلي. إدخالات Hook هي زوج `{command, timeout}` (المهلة بـ **ثوان**) تحت خريطة `hooks:` مفتاح بأحداث Hermes snake_case (`pre_tool_call` / `post_tool_call` / `on_session_start` / `on_session_end` / `subagent_stop`); معالج يطبيع الأحداث عبر `HERMES_EVENT_MAP` وأسماء أداة عبر `HERMES_TOOL_MAP` حتى تطلق السياسات المدمجة دون تغيير. التكوين يتم تحريره عبر YAML `Document` round-trip محفوظ التعليقات حتى الإعدادات الأخرى للمشغل تبقى، وinstall يعين `hooks_auto_accept: true` حتى بوابة بدون رأس (بدون TTY) تشغل hooks بدون موجه موافقة. المقيم يطلق عقد stdout Hermes `{"decision":"block","reason"}` (Hermes يتجاهل أكواد الخروج). **القيود:** Hermes ليس لديها حدث نهاية turn `Stop`، لذا builtins `require-*-before-stop` لا تطلق لها أبداً (غير قابل للتطبيق، وليس مكسور)؛ `instruct` يقلل إلى allow-with-logged-note (لا توجد قناة سياق إضافي)؛ و output-secret redaction (`sanitize-*`) لا يمكنها إعادة كتابة output أداة على عقد shell-hook. Hermes هو **أيضاً** مصدر **تدقيق** محلي — لوحة التحكم تقرأ جلسات البوابة مباشرة من `~/.hermes/state.db`.
  - **OpenClaw (openclaw gateway)**: `~/.openclaw/openclaw.json` (**نطاق مستخدم فقط** — OpenClaw ليس لديه تكوين مشروع/محلي). مثل Hermes، OpenClaw هو **بوابة** متعددة قنوات **self-hosted**، لذا تثبيت واحد يعترض استدعاءات أداة من كل قناة وsubagents داخلي. الإنفاذ يعمل عبر **hooks في العملية** OpenClaw (hooks قائم على ملف الخاص به للملاحظة فقط ولا يمكن حظر)، لذا — مثل OpenCode/Pi — failproofai يشحن حزمة `openclaw-plugin/` ثابتة التي async-spawns الملف الثنائي failproofai وتترجم الحكم. Install تسجل دليل plugin المشحون في مصفوفة `openclaw.json`'s `plugins.load.paths[]` وتفعلها تحت `plugins.entries.failproofai` (مع `hooks.allowConversationAccess: true`، مطلوب لـ raw-conversation hooks). المقيم يطلق حكم مسطح `{permission, reason}` وشيم يخريطه إلى شكل native لكل hook: `before_tool_call → {block:true, blockReason}` (**PreToolUse**), `before_agent_run → {outcome:"block", reason}` (**UserPromptSubmit**), و `before_agent_finalize → {action:"revise", reason}` (**Stop** — بوابة turn-end حقيقية، حتى builtins `require-*-before-stop` **ينفذ** على OpenClaw، على عكس Hermes). الأحداث وأسماء الأداة تطبيع ثنائي-جانب عبر `OPENCLAW_EVENT_MAP` / `OPENCLAW_TOOL_MAP` (`exec→Bash`، `read→Read`، …) حتى تطلق السياسات المدمجة دون تغيير؛ شيم يفشل مفتوح على أي spawn/parse/timeout خطأ. OpenClaw هو **أيضاً** مصدر **تدقيق** محلي — لوحة التحكم تقرأ جلسات JSONL الخاصة به على `~/.openclaw/agents/<agentId>/sessions/<uuid>.jsonl`.
  - **Factory Droid (`droid`)**: `~/.factory/hooks.json` (مستخدم)، `<cwd>/.factory/hooks.json` (مشروع) — Factory ليس لديها نطاق محلي. droid يشحن نظام hook أمر خارجي على شكل Claude، لكن مع twists اثنين تحقق مباشرة ضد droid v0.171.0: (1) أسماء الأحداث تعيش على **المستوى الأعلى** من `hooks.json` — لا توجد **لا `"hooks"` wrapper** (droid يرفض واحد)؛ أحداث أداة (`PreToolUse`/`PostToolUse`) تحمل `"matcher": "*"`، أحداث غير أداة حذفها. (2) Deny يقود بواسطة hook **الخروج كود 2 + stderr**، وليس قرار JSON — فرع `factory` المقيم يرجع الخروج 2 للأداة/أحداث الموجه و `{decision:"block", reason}` فقط على حدث turn-end `Stop` (قناة Force-retry الوحيدة droid). الأحداث بالفعل PascalCase (لا event map) والحمولة هي Claude snake_case؛ فقط أسماء الأداة تطبيع عبر `FACTORY_TOOL_MAP` (`Execute→Bash`, `Create→Write`, `FetchUrl→WebFetch`, …). Factory هو **أيضاً** مصدر **تدقيق** محلي — لوحة التحكم تقرأ جلسات JSONL على جهاز الكمبيوتر الخاص بها على `~/.factory/sessions/<encoded-cwd>/<sessionId>.jsonl`.
  - **Devin CLI (`devin`, Cognition)**: `~/.config/devin/config.json` (مستخدم)، `<cwd>/.devin/config.json` (مشروع) — Devin ليس لديه نطاق محلي. Devin هو **clone Pure Claude** تحقق مباشرة ضد devin v3000.1.27: يستخدم مخطط Claude القياسي `"hooks"`-wrapper (الكتابات محفوظة دمج حتى مفاتيح الملف الآخرى للتكوين — `org_id`، `theme_mode`، … — البقاء)، أسماء أحداث بالفعل PascalCase (لا event map، لا فرع معالج)، و حمولة stdin Claude snake_case (لا تطبيع). فرع `devin` المقيم يرفع مع `{"decision":"block","reason"}` JSON على stdout في الخروج 0 لـ **كل** حدث (تحقق — الكتلة تجاوز `--permission-mode dangerous`); على حدث turn-end `Stop` السبب يحمل wording force-retry الإجباري حتى builtins `require-*-before-stop` ينفذ. فقط أسماء الأداة تطبيع عبر `DEVIN_TOOL_MAP` (`exec→Bash`; `tool_input.command` بالفعل canonical). Devin هو **أيضاً** مصدر **تدقيق** محلي — لوحة التحكم تقرأ جلسات SQLite الخاصة به على `~/.local/share/devin/cli/sessions.db` (كل صف `sessions` يحمل real `working_directory`، حتى جلسات مجموعة بـ project cwd مثل Claude).
  - **Antigravity CLI (`agy`)**: `~/.gemini/config/hooks.json` (مستخدم)، `<cwd>/.agents/hooks.json` (مشروع) — Antigravity ليس لديه نطاق محلي. على عكس Factory/Devin، Antigravity لديه **عقد خاص بها** (ليس clone Claude)، تحقق مباشرة ضد agy v1.1.2. `hooks.json` يستخدم **مخطط hook مسمى**: المفتاح المستوى الأعلى هو hook *اسم* (`"failproofai"`) قيمته event→handlers map — أحداث الأداة (`PreToolUse`/`PostToolUse`) wrap handlers في `{matcher:"*", hooks:[…]}`، بينما `PreInvocation`/`Stop` هي **مسطحة** arrays handler (named hooks أخرى محفوظة). الحمولة stdin هي **camelCase protojson** (`toolCall:{name,args}`، `conversationId`، `workspacePaths`، `transcriptPath`) — failproofai تطبيعها إلى snake_case قبل تشغيل السياسات، و تخريط `run_command`'s PascalCase args (`CommandLine`/`Cwd`) عبر `ANTIGRAVITY_TOOL_INPUT_MAP`. فرع `antigravity` المقيم يستخدم أشكال استجابة **خاصة** Antigravity: `{decision:"deny", reason}` حظر أداة/prompt (exit 0), `{decision:"continue", reason}` على turn-end `Stop` إعادة-دخول loop (حتى builtins `require-*-before-stop` ينفذ), و `{injectSteps:[{ephemeralMessage}]}` حقن تعليمات على `PreInvocation` (→ `UserPromptSubmit`). أسماء الأداة تطبيع عبر `ANTIGRAVITY_TOOL_MAP` (`run_command→Bash`, `view_file→Read`, …). Antigravity هو **أيضاً** مصدر **تدقيق** محلي — لوحة التحكم تقرأ نسخ plain-JSONL الخاصة به على `~/.gemini/antigravity-cli/brain/<conversationId>/.system_generated/logs/transcript_full.jsonl` (فهرس محادثة في `conversation_summaries.db`).
  - **Goose (codename goose, Block)**: `~/.agents/plugins/failproofai/hooks/hooks.json` (مستخدم)، `<cwd>/.agents/plugins/failproofai/hooks/hooks.json` (مشروع) — Goose ليس لديه نطاق محلي. الإنفاذ يستخدم نظام **hooks** Goose، spec **Open Plugins** عبر الوكيل: المثبت ينزل فقط دليل plugin `failproofai` و Goose auto-discovers ذلك عند بدء التشغيل (self-registering ذلك إلى `~/.config/goose/config.yaml`). `hooks.json` يستخدم schema **Open Plugins** **مع** wrapper `"hooks"` المستوى الأعلى، و matcher هو **حذف** على كل حدث — bare `"*"` هو regex غير صحيح لا يطابق شيء (تحقق مباشرة ضد goose v1.43.0). أسماء الأحداث بالفعل PascalCase (لا event map)؛ الحمولة stdin تستخدم `event`/`working_dir`، الذي معالج يطبيعها إلى `hook_event_name`/`cwd`. فرع `goose` المقيم يرفع مع `{"decision":"block","reason"}` JSON على stdout في الخروج 0، كرام على **`PreToolUse`** حدث فقط (مشحون في goose ≥ v1.37.0) — الذي يطلق لـ shell tool **و inside delegated subagents**، حتى ذلك واحد كافي deny point؛ أي خطأ hook آخر يفشل **مفتوح**. Goose ليس لديه **`Stop` حدث**، حتى builtins `require-*-before-stop` لا تنطبق (كما مع Hermes). أسماء الأداة تطبيع عبر `GOOSE_TOOL_MAP` (`shell→Bash`, `write→Write`, `todo__todo_write→TodoWrite`, …) ومفاتيح path عبر `GOOSE_TOOL_INPUT_MAP` (`path`/`source` → `file_path`). Goose هو **أيضاً** مصدر **تدقيق** محلي — لوحة التحكم تقرأ جلسات SQLite الخاصة به على `~/.local/share/goose/sessions/sessions.db` (كل صف `sessions` يحمل real `working_dir`، حتى جلسات مجموعة بـ project cwd مثل Devin؛ `--no-session` خدوش يتم تصفيتها).
- **`policies-config.json`** — تخبر failproofai أي سياسات تقيمها ومع ما params (مشترك عبر جميع agent CLIs)

Pass `--cli claude|codex|copilot|cursor|opencode|pi|hermes|openclaw|factory|devin|antigravity|goose` لاستهداف وكيل محدد (مفصول بمسافات أو مكرر لأي subset):

```bash
failproofai policies --install --cli codex --scope project
failproofai policies --install --cli copilot --scope project
failproofai policies --install --cli cursor --scope project
failproofai policies --install --cli opencode --scope project
failproofai policies --install --cli pi --scope project
failproofai policies --install --cli hermes --scope user
failproofai policies --install --cli openclaw --scope user
failproofai policies --install --cli factory --scope project
failproofai policies --install --cli devin --scope project
failproofai policies --install --cli antigravity --scope project
failproofai policies --install --cli goose --scope project
failproofai policies --install --cli claude codex copilot cursor opencode pi hermes openclaw factory devin antigravity goose
```

عند حذف `--cli`، يكتشف `failproofai` أي agent CLIs مثبت (`which claude` / `which codex` / `which copilot` / `which cursor-agent` / `which opencode` / `which pi` / `which hermes` / `which openclaw` / `which droid` / `which devin` / `which agy` / `which goose`):

- **واحد CLI مكتشف** — auto-selects ذلك CLI بدون prompting.
- **ملتقطة CLIs متعددة** في محطة تفاعلية — يظهر موجه single-select مفتاح arrow مجمعة في قسم `Detected (N)` (مع صف aggregate `Install for all N detected` + كل CLI مكتشف بشكل فردي) و قسم `Not installed (M) · install hooks ahead of time` عائدة كل supported CLI غير مكتشف كخيار forward-install (↑↓ للتحرك، Enter لـ select، ^C لـ quit). تدفق الإلغاء يظهر قسم Detected فقط.
- **ملتقطة CLIs متعددة** في non-interactive run (CI، بدون TTY) — يثبت لجميع CLIs مكتشفة بدون prompting.
- **لا شيء مكتشف** — يسقط إلى `claude`، مع تحذير لم يوجد binary wkiagent في PATH؛ أمر hook لا تزال كتب حتى يفعل بمجرد تثبيت واحد.

يمكنك تحرير `policies-config.json` مباشرة في أي وقت؛ التغييرات دخول الفور على حدث hook التالي بدون إعادة تشغيل مطلوبة.

## مثال: تكوين مستوى المشروع مع إعدادات الفريق

Commit `.failproofai/policies-config.json` إلى مستودع الخاص بك:

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "block-env-files"
  ],
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "release", "hotfix"]
    }
  }
}
```

يمكن لكل مطور إنشاء `.failproofai/policies-config.local.json` (gitignored) للحصول على تجاوزات شخصية بدون التأثير على زملائهم.
