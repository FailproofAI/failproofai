يستخدم failproofai ملفات إعدادات JSON للتحكم في السياسات النشطة، وكيفية سلوكها، ومن أين يتم تحميل السياسات المخصصة. تم تصميم الإعدادات لسهولة المشاركة مع فريقك - قم بإيداعها في المستودع الخاص بك وكل مطور سيحصل على نفس شبكة الأمان للوكيل.

---

## نطاقات الإعدادات

هناك ثلاثة نطاقات إعدادات، يتم تقييمها حسب ترتيب الأولوية:

| النطاق | مسار الملف | الغرض |
|-------|-----------|---------|
| **project** | `.failproofai/policies-config.json` | إعدادات لكل مستودع، موضوعة تحت التحكم في الإصدار |
| **local** | `.failproofai/policies-config.local.json` | التجاوزات الشخصية لكل مستودع، مدرجة في gitignore |
| **global** | `~/.failproofai/policies-config.json` | الإعدادات الافتراضية على مستوى المستخدم عبر جميع المشاريع |

عند استقبال failproofai لحدث hook، يقوم بتحميل ودمج جميع الملفات الثلاثة الموجودة في دليل العمل الحالي.

### قواعد الدمج

**`enabledPolicies`** - اتحاد جميع النطاقات الثلاثة. السياسة المفعلة في أي مستوى تكون نشطة.

```text
project:  ["block-sudo"]
local:    ["block-rm-rf"]
global:   ["block-sudo", "sanitize-api-keys"]

resolved: ["block-sudo", "block-rm-rf", "sanitize-api-keys"]  ← اتحاد مزال التكرار
```

**`policyParams`** - النطاق الأول الذي يحدد المعاملات لسياسة معينة يفوز بالكامل. لا يوجد دمج عميق للقيم داخل معاملات السياسة.

```text
project:  block-sudo → { allowPatterns: ["sudo apt-get update"] }
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo apt-get update"] }   ← project يفوز، global مُتجاهل
```

```text
project:  (no block-sudo entry)
local:    (no block-sudo entry)
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo systemctl status"] }  ← ينحدر إلى global
```

**`customPoliciesPaths` / `customPoliciesPath`** - النطاق الأول الذي يحدد أحد النماذج يفوز.

**`disabledCustomPolicies`** - اتحاد عبر جميع النطاقات. لوحة التحكم تكتب معرّفًا مؤهلًا بالمصدر هنا عندما تقوم بإيقاف تشغيل سياسة فردية من ملف سياسة واضح أو مدعوم بالاتفاقية. السياسات غير المدرجة تبقى مفعلة بشكل افتراضي؛ المعرّفات تتضمن ملف المصدر بحيث يمكن التحكم في السياسات التي تحمل نفس الاسم في ملفات متعددة بشكل مستقل.

**`llm`** - النطاق الأول الذي يحدده يفوز.

## تنسيق ملف الإعدادات

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "sanitize-jwt",
    "block-env-files",
    "block-read-outside-cwd"
  ],
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release", "prod"]
    },
    "block-rm-rf": {
      "allowPaths": ["/tmp"]
    },
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company"]
    },
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo API key" }
      ]
    },
    "warn-large-file-write": {
      "thresholdKb": 512
    }
  },
  "customPoliciesPath": "/home/alice/myproject/my-policies.js"
}
```

## مرجع الحقول

### `enabledPolicies`

النوع: `string[]`

قائمة بأسماء السياسات المراد تفعيلها. يجب أن تطابق الأسماء بالضبط معرّفات السياسات التي تعرضها `failproofai policies`. انظر [السياسات المدمجة](/ar/built-in-policies) للحصول على القائمة الكاملة.

السياسات غير المدرجة في `enabledPolicies` غير نشطة، حتى لو كان لديها إدخالات في `policyParams`.

### `policyParams`

النوع: `Record<string, Record<string, unknown>>`

تجاوزات المعاملات لكل سياسة. المفتاح الخارجي هو اسم السياسة؛ المفاتيح الداخلية خاصة بالسياسة. توثق كل سياسة معاملاتها المتاحة في [السياسات المدمجة](/ar/built-in-policies).

إذا كان لدى السياسة معاملات ولم تحددها، يتم استخدام القيم الافتراضية المدمجة للسياسة. المستخدمون الذين لا يقومون بإعداد `policyParams` على الإطلاق يحصلون على سلوك مطابق للإصدارات السابقة.

المفاتيح المجهولة داخل كتلة معاملات السياسة يتم تجاهلها بصمت عند تشغيل hook، لكن يتم الإبلاغ عنها كتحذيرات عند تشغيل `failproofai policies`.

#### `hint` (عبر النطاق)

النوع: `string` (اختياري)

رسالة يتم إضافتها إلى السبب عندما تعيد السياسة `deny` أو `instruct`. استخدمها لمنح Claude توجيهًا قابلًا للتنفيذ دون تعديل السياسة نفسها.

يعمل مع أي نوع سياسة — مدمجة، مخصصة (`custom/`)، اتفاقية المشروع (`.failproofai-project/`)، أو اتفاقية المستخدم (`.failproofai-user/`).

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "جرب إنشاء فرع جديد بدلاً من ذلك."
    },
    "block-sudo": {
      "allowPatterns": ["sudo apt-get"],
      "hint": "استخدم apt-get مباشرة بدون sudo."
    },
    "custom/my-policy": {
      "hint": "اطلب موافقة المستخدم أولاً."
    }
  }
}
```

عندما يرفض `block-force-push`، يرى Claude: *«Push بالقوة محظور. جرب إنشاء فرع جديد بدلاً من ذلك.»*

القيم غير النصية والسلاسل الفارغة يتم تجاهلها بصمت. إذا لم تُعيّن `hint`، يبقى السلوك كما هو (متوافق مع الإصدارات السابقة).

### `customPoliciesPath`

النوع: `string` (المسار المطلق)

مسار ملف JavaScript يحتوي على سياسات hook مخصصة. يتم تعيينه تلقائيًا بواسطة `failproofai policies --install --custom <path>` (يتم حل المسار إلى مطلق قبل التخزين).

يتم تحميل الملف بشكل جديد في كل حدث hook - لا يوجد تخزين مؤقت. انظر [السياسات المخصصة](/ar/custom-policies) للحصول على تفاصيل التأليف.

### السياسات المبنية على الاتفاقية

بالإضافة إلى `customPoliciesPath` الصريح، يكتشف failproofai تلقائيًا ويحمل ملفات السياسات من أدلة `.failproofai/policies/`:

| المستوى | الدليل | النطاق |
|--------|--------|--------|
| المشروع | `.failproofai/policies/` | مشترك مع الفريق عبر التحكم في الإصدار |
| المستخدم | `~/.failproofai/policies/custom-policies/` | شخصي، ينطبق على جميع المشاريع |

<Note>
  تم نقل دليل مستوى المستخدم مستوى واحد لأسفل في إعادة التنظيم الدليل. الملفات المتبقية في `~/.failproofai/policies/` القديم يتم نقلها إلى `custom-policies/` تلقائيًا في المرة الأولى التي تقوم فيها بتشغيل أي أمر `failproofai` بعد الترقية، والأمر يخبرك بالملفات التي تم نقلها.
</Note>

**مطابقة الملف:** يتم تحميل الملفات فقط التي تطابق `*policies.{js,mjs,ts}` (مثل `security-policies.mjs`, `workflow-policies.js`). يتم تجاهل الملفات الأخرى في الدليل.

**لا إعدادات مطلوبة:** سياسات الاتفاقية لا تتطلب إدخالات في `policies-config.json`. ما عليك سوى إسقاط الملفات في الدليل وسيتم اختيارها في حدث hook التالي.

**تحميل الاتحاد:** يتم فحص كل من أدلة اتفاقية المشروع والمستخدم. يتم تحميل جميع الملفات المطابقة من كلا المستويين (بخلاف `customPoliciesPath` الذي يستخدم first-scope-wins).

انظر [السياسات المخصصة](/ar/custom-policies) لمزيد من التفاصيل والأمثلة.

### `llm`

النوع: `object` (اختياري)

إعدادات عميل LLM للسياسات التي تجري استدعاءات AI. غير مطلوب لمعظم الإعدادات.

```json
{
  "llm": {
    "model": "claude-sonnet-4-6",
    "apiKey": "sk-ant-..."
  }
}
```

## إدارة الإعدادات من واجهة سطر الأوامر

تقوم أوامر `policies --install` و `policies --uninstall` بالكتابة إلى ملف إعدادات hook لـ CLI الوكيل الخاص بك (نقاط دخول hook)، بينما `policies-config.json` هو الملف الذي تديره مباشرة. الاثنان منفصلان:

- **إعدادات Agent CLI** — يخبر الوكيل باستدعاء `failproofai --hook <event>` في كل استخدام أداة:
  - **Claude Code**: `~/.claude/settings.json` (مستخدم)، `<cwd>/.claude/settings.json` (مشروع)، `<cwd>/.claude/settings.local.json` (محلي)
  - **OpenAI Codex**: `~/.codex/hooks.json` (مستخدم)، `<cwd>/.codex/hooks.json` (مشروع) — Codex ليس لديه نطاق `local`
  - **GitHub Copilot CLI _(beta)_**: `~/.copilot/hooks/failproofai.json` (مستخدم)، `<cwd>/.github/hooks/failproofai.json` (مشروع) — Copilot ليس لديه نطاق `local`. تستخدم إدخالات Hook حقول الأوامر `bash`/`powershell` المفتاحة بـ OS في Copilot مع `timeoutSec`؛ يحمل الملف علامة `version: 1` على المستوى الأعلى. دعم Copilot CLI هو **beta** بينما نتحقق من مخطط سجل `events.jsonl` (الذي لا تحدده الوثائق العامة) مقابل المزيد من الجلسات الحقيقية. **وضع عامل VS Code Copilot Chat (Preview)** يقرأ تكوينات hook من `.github/hooks/*.json`، `~/.copilot/hooks/*.json`، و `~/.claude/settings.json` (يُحكم به بواسطة إعداد `chat.hookFilesLocations`) باستخدام نفس عقد Claude الذي يشبه `{hookSpecificOutput:{permissionDecision:"deny",…}}` — المسارات الدقيقة التي كتبتها بالفعل هذه المدمجة `copilot` والمدمجة `claude` (`~/.claude/settings.json`)، لذا `failproofai policies --install --cli copilot` (أو `--cli claude`) **بالفعل ينفذ في وضع عامل VS Code** بدون تكامل `vscode` منفصل مطلوب (مؤكد مباشرة من سجلات اكتشاف VS Code).
  - **Cursor Agent _(beta)_**: `~/.cursor/hooks.json` (مستخدم)، `<cwd>/.cursor/hooks.json` (مشروع) — Cursor ليس لديه نطاق `local`. تستخدم إدخالات Hook النموذج الذي يشبه Claude `{type, command, timeout}` (بدون تقسيم `bash`/`powershell`)، لكن مخزن تحت مفاتيح الحدث camelCase (`preToolUse`, `beforeSubmitPrompt`, …) في صفيف مسطح لكل [مخطط hooks](https://cursor.com/docs/hooks) في Cursor. يحمل الملف علامة `version: 1` على المستوى الأعلى. معالج يوحد camelCase → PascalCase عبر `CURSOR_EVENT_MAP` بحيث السياسات المدمجة الموجودة تعمل بدون تغيير. دعم Cursor Agent هو **beta** بينما نتحقق من نص Cursor على قرص (غير محدد في الوثائق العامة) مقابل المزيد من التثبيتات الحقيقية.
  - **OpenCode _(beta)_**: `~/.config/opencode/opencode.json` + `~/.config/opencode/plugins/failproofai.mjs` (مستخدم)، `<cwd>/.opencode/opencode.json` + `<cwd>/.opencode/plugins/failproofai.mjs` (مشروع) — OpenCode ليس لديه نطاق `local`. بخلاف أنظمة hook الخمسة الأخرى، OpenCode **لا يوجد لديه نظام hook للأوامر الخارجية**: يحمل المكونات الإضافية JS/TS في العملية والمسجلة بشكل صريح عبر صفيف `plugin: []` في `opencode.json` (الاكتشاف التلقائي من `.opencode/plugins/` **ليس** كيف تحميل المكونات الإضافية على opencode v1.14.33). التثبيت ينسق shimmer صغير مولد يستدعي failproofai binary في عملية فرعية ويترجم استجابة JSON الثنائية للشكل Claude إلى دلالات المكون الإضافي: `throw new Error()` لأداة رفض الحدث (ينسخ استدعاء الأداة)، `client.session.prompt(...)` لـ instruct **و** لـ `Stop` / `SubagentStop` رفض (يقدم سبب الرفض كرسالة المستخدم التالية — القناة الوحيدة لفرض إعادة المحاولة حيث `session.idle` هي إخطار فقط والرمي من ذلك هو no-op)، و no-op للسماح. Shimmer يوحد أسماء الأدوات (أحرف صغيرة → PascalCase عبر `OPENCODE_TOOL_MAP`) ومفاتيح arg الإدخال للأداة (camelCase → snake_case عبر `OPENCODE_TOOL_INPUT_MAP` لـ `Read` / `Write` / `Edit`، مثل `filePath` → `file_path`, `oldString` → `old_string`) قبل إعادة التوجيه إلى الملف الثنائي، بحيث builtins التحقق من المسار مثل `block-read-outside-cwd`, `block-env-files`, و `block-secrets-write` تعمل بدون تغيير على استدعاءات OpenCode. تعيش الجلسات في SQLite DB في opencode على `~/.local/share/opencode/opencode.db`؛ عارض الجلسة في لوحة التحكم يقرأها عبر `opencode db --format json` و `opencode export <id>`. دعم OpenCode هو **beta** بينما نتحقق من السلوك عبر الإصدارات والمزيد من الجلسات الحقيقية. انظر [وثائق المكونات الإضافية OpenCode](https://opencode.ai/docs/plugins/).
  - **Pi _(beta)_**: `~/.pi/agent/settings.json` (مستخدم)، `<cwd>/.pi/settings.json` (مشروع) — Pi ليس لديه نطاق `local`. يحمل Pi حزم ملحقات TypeScript عند البدء؛ ملف الإعدادات هو صفيف سلسلة مسطح `{"packages": ["./relative/path", …]}`. يكتب failproofai إدخال صفيف حزم واحد يشير إلى دليل `pi-extension/` المجمع الخاص به. المحرك داخليًا ينسخ أحداث `tool_call` / `user_bash` / `input` / `session_start` في Pi ويعود إلى `failproofai --hook <Event> --cli pi`؛ معالج يوحد underscore_lower_snake_case → PascalCase عبر `PI_EVENT_MAP` بحيث السياسات المدمجة الموجودة تعمل بدون تغيير. يتم توحيد args إدخال الأداة أيضًا عبر `PI_TOOL_INPUT_MAP` (يوفر Pi Read / Write / Edit `path` بدلاً من `file_path`؛ تخطيط المفتاح على المستوى الأعلى يسمح `block-env-files` و `block-secrets-write` بالعمل — `block-read-outside-cwd` بالفعل كان لديه fallback `path`). دعم Pi هو **beta** بينما تستقر API المحرك في Pi ومخطط سجل الجلسة.
  - **Hermes (hermes-agent)**: `~/.hermes/config.yaml` (**نطاق مستخدم فقط** — Hermes ليس لديه إعدادات مشروع/محلي). Hermes هو بوابة **Slack/Telegram**، لذا تثبيت واحد يقطع استدعاءات الأداة من كل منصة (Slack/Telegram/cli/cron) **و** الوكلاء الداخليين. إدخالات Hook هي زوج `{command, timeout}` (timeout في **seconds**) تحت خريطة `hooks:` مفتاحة بأحداث snake_case في Hermes (`pre_tool_call` / `post_tool_call` / `on_session_start` / `on_session_end` / `subagent_stop`); معالج يوحد الأحداث عبر `HERMES_EVENT_MAP` وأسماء الأدوات عبر `HERMES_TOOL_MAP` بحيث السياسات المدمجة تعمل بدون تغيير. يتم تحرير الإعدادات من خلال حفظ YAML `Document` الذي يحافظ على التعليقات بحيث إعدادات المشغل الأخرى تبقى، والتثبيت يعيّن `hooks_auto_accept: true` بحيث البوابة بدون رؤوس (بدون TTY) تشغل hooks بدون موافقة. المقيِّم يصدر عقد Hermes `{"decision":"block","reason"}` stdout (يتجاهل Hermes رموز الخروج). **القيود:** Hermes ليس لديه حدث turn-end `Stop`، لذا builtins `require-*-before-stop` لا تعمل أبداً (غير قابل للتطبيق، ليس مكسور)؛ `instruct` يضعف إلى allow-with-logged-note (لا توجد قناة سياق إضافي)؛ وإخفاء السر في الإخراج (`sanitize-*`) لا يمكن إعادة كتابة إخراج الأداة عبر عقد shell-hook. Hermes هو **أيضا** مصدر تدقيق offline — لوحة التحكم تقرأ جلسات البوابة الخاصة به مباشرة من `~/.hermes/state.db`.
  - **OpenClaw (openclaw gateway)**: `~/.openclaw/openclaw.json` (**نطاق مستخدم فقط** — OpenClaw ليس لديه إعدادات مشروع/محلي). مثل Hermes، OpenClaw هي بوابة متعددة القنوات **self-hosted**، لذا تثبيت واحد يقطع استدعاءات الأداة من كل قناة والوكلاء الداخليين الخاصة به. يجري الإنفاذ من خلال **في العملية plugin hooks** في OpenClaw (hooks الداخلية المستندة على الملف هي observation-only ولا يمكنها الحجب)، بحيث — مثل OpenCode/Pi — يُشحن failproofai حزمة `openclaw-plugin/` ثابتة التي async-spawns الثنائي failproofai وتترجم الحكم. التثبيت يسجل دليل المكون الإضافي المُشحون في `openclaw.json`'s `plugins.load.paths[]` ويمكّنه تحت `plugins.entries.failproofai` (مع `hooks.allowConversationAccess: true`، مطلوب لـ hooks المحادثة الخام). المقيِّم يصدر حكم مسطح `{permission, reason}` و shimmer يخطئها إلى شكل العودة الأصلي لكل hook: `before_tool_call → {block:true, blockReason}` (**PreToolUse**)، `before_agent_run → {outcome:"block", reason}` (**UserPromptSubmit**)، و `before_agent_finalize → {action:"revise", reason}` (**Stop** — بوابة turn-end حقيقية، بحيث builtins `require-*-before-stop` **ينفذ** على OpenClaw، بخلاف Hermes). الأحداث وأسماء الأدوات يوحدها Binary-side عبر `OPENCLAW_EVENT_MAP` / `OPENCLAW_TOOL_MAP` (`exec→Bash`, `read→Read`, …) بحيث السياسات المدمجة تعمل بدون تغيير؛ shimmer يفشل مفتوح على أي spawn/parse/timeout خطأ. OpenClaw هو **أيضا** مصدر تدقيق offline — لوحة التحكم تقرأ جلسات JSONL الخاصة به على `~/.openclaw/agents/<agentId>/sessions/<uuid>.jsonl`.
  - **Factory Droid (`droid`)**: `~/.factory/hooks.json` (مستخدم)، `<cwd>/.factory/hooks.json` (مشروع) — Factory ليس لديه نطاق `local`. droid يُشحن نظام hook أوامر خارجي بنمط Claude، لكن مع نكات اثنين تم التحقق منها مباشرة ضد droid v0.171.0: (1) أسماء الأحداث تعيش على **المستوى الأعلى** من `hooks.json` — **لا `"hooks"` wrapper** (droid يرفضها)؛ أحداث الأداة (`PreToolUse`/`PostToolUse`) حمل `"matcher": "*"`، أحداث غير الأداة تحذفها. (2) الرفض محكوم hook **exit code 2 + stderr**، ليس قرار JSON — فرع `factory` للمقيِّم يعيد exit 2 لأحداث أداة/prompt وقرار `{decision:"block", reason}` فقط على حدث turn-end `Stop` (القناة الوحيدة لفرض إعادة المحاولة في droid). الأحداث بالفعل PascalCase (بدون event map) والحمل Snake_case Claude؛ فقط أسماء الأدوات توحد عبر `FACTORY_TOOL_MAP` (`Execute→Bash`, `Create→Write`, `FetchUrl→WebFetch`, …). Factory هو **أيضا** مصدر تدقيق offline — لوحة التحكم تقرأ جلسات JSONL على القرص الخاصة به على `~/.factory/sessions/<encoded-cwd>/<sessionId>.jsonl`.
  - **Devin CLI (`devin`, Cognition)**: `~/.config/devin/config.json` (مستخدم)، `<cwd>/.devin/config.json` (مشروع) — Devin ليس لديه نطاق `local`. Devin هو **نسخة Claude النقية** التي تم التحقق منها مباشرة ضد devin v3000.1.27: يستخدم مخطط `"hooks"`-wrapper القياسي Claude (الكتابات محفوظة الدمج بحيث مفاتيح ملف الإعدادات الأخرى — `org_id`, `theme_mode`, … — تبقى)، أسماء أحداث بالفعل PascalCase (بدون event map، بدون فرع handler)، و stdin حمل Snake_case Claude (بدون تطبيع). فرع `devin` للمقيِّم يرفض مع `{"decision":"block","reason"}` JSON على stdout عند exit 0 لـ **كل** حدث (تم التحقق — الرفض تجاوز `--permission-mode dangerous`); على حدث turn-end `Stop` السبب يحمل صياغة MANDATORY-ACTION لإعادة المحاولة القسرية بحيث builtins `require-*-before-stop` ينفذ. فقط أسماء الأدوات توحد عبر `DEVIN_TOOL_MAP` (`exec→Bash`; `tool_input.command` بالفعل قانوني). Devin هو **أيضا** مصدر تدقيق offline — لوحة التحكم تقرأ جلسات SQLite الخاصة به على `~/.local/share/devin/cli/sessions.db` (كل صف `sessions` يحمل حقيقي `working_directory`، بحيث جلسات مجموعة بـ cwd مشروع مثل Claude).
  - **Antigravity CLI (`agy`)**: `~/.gemini/config/hooks.json` (مستخدم)، `<cwd>/.agents/hooks.json` (مشروع) — Antigravity ليس لديه نطاق `local`. بخلاف Factory/Devin، Antigravity لديها **عقدها الخاص** (ليس نسخة Claude)، تم التحقق منها مباشرة ضد agy v1.1.2. `hooks.json` يستخدم **مخطط hook مسمى**: المفتاح على المستوى الأعلى هو *اسم* hook (`"failproofai"`) قيمته خريطة الحدث → handlers — أحداث الأداة (`PreToolUse`/`PostToolUse`) wrap handlers في `{matcher:"*", hooks:[…]}`، بينما `PreInvocation`/`Stop` هي **مسطح** صفائف handler (الأخرى تُحافظ hooks مسماة). stdin حمل هو **camelCase protojson** (`toolCall:{name,args}`, `conversationId`, `workspacePaths`, `transcriptPath`) — failproofai يطبّع ذلك إلى snake_case قبل تشغيل السياسات، ويخطئ args `run_command`'s PascalCase (`CommandLine`/`Cwd`) عبر `ANTIGRAVITY_TOOL_INPUT_MAP`. فرع `antigravity` للمقيِّم يستخدم **أشكال Antigravity الخاصة** للاستجابة: `{decision:"deny", reason}` يحجب أداة/prompt (exit 0)، `{decision:"continue", reason}` على حدث turn-end `Stop` يُعاد دخول الحلقة (بحيث builtins `require-*-before-stop` ينفذ)، و `{injectSteps:[{ephemeralMessage}]}` ينسخ تعليمة على `PreInvocation` (→ `UserPromptSubmit`). أسماء الأدوات توحد عبر `ANTIGRAVITY_TOOL_MAP` (`run_command→Bash`, `view_file→Read`, …). Antigravity هو **أيضا** مصدر تدقيق offline — لوحة التحكم تقرأ نصوصها JSONL الخام على `~/.gemini/antigravity-cli/brain/<conversationId>/.system_generated/logs/transcript_full.jsonl` (مؤشر المحادثة في `conversation_summaries.db`).
  - **Goose (codename goose, Block)**: `~/.agents/plugins/failproofai/hooks/hooks.json` (مستخدم)، `<cwd>/.agents/plugins/failproofai/hooks/hooks.json` (مشروع) — Goose ليس لديه نطاق `local`. الإنفاذ يستخدم نظام **hooks** Goose، المواصفات **Open Plugins** عبر الوكيل: المثبِّت يسقط فقط دليل المكون الإضافي `failproofai` و Goose auto-discovers ذلك عند البدء (ينسجله ذاتيًا في `~/.config/goose/config.yaml`). `hooks.json` يستخدم مخطط Open Plugins **مع** wrapper `"hooks"` على المستوى الأعلى، و matcher هو **مُحذوف** على كل حدث — `"*"` عارية هي regex غير صالح يطابق لا شيء (تم التحقق مباشرة ضد goose v1.43.0). أسماء الأحداث بالفعل PascalCase (بدون event map)؛ stdin حمل يستخدم `event`/`working_dir`، الذي يطبّع Handler إلى `hook_event_name`/`cwd`. فرع `goose` للمقيِّم يرفض مع `{"decision":"block","reason"}` JSON على stdout عند exit 0، يُشرّف على حدث **`PreToolUse`** فقط (مُشحون في goose ≥ v1.37.0) — الذي ينطلق لـ shell tool **وداخل الوكلاء المُعهودين**، لذا هو نقطة رفض واحدة كافية؛ أي خطأ hook آخر فشل **مفتوح**. Goose **لا توجد لديه حدث `Stop`**، بحيث builtins `require-*-before-stop` لا تنطبق (مثل Hermes). أسماء الأدوات توحد عبر `GOOSE_TOOL_MAP` (`shell→Bash`, `write→Write`, `todo__todo_write→TodoWrite`, …) ومفاتيح المسار عبر `GOOSE_TOOL_INPUT_MAP` (`path`/`source` → `file_path`). Goose هو **أيضا** مصدر تدقيق offline — لوحة التحكم تقرأ جلسات SQLite الخاصة به على `~/.local/share/goose/sessions/sessions.db` (كل صف `sessions` يحمل حقيقي `working_dir`، بحيث جلسات مجموعة بـ cwd مشروع مثل Devin؛ خدش `--no-session` تشغيلات يتم تصفيتها).
- **`policies-config.json`** — يخبر failproofai بأي السياسات المراد تقييمها وبأي params (مشترك عبر جميع agent CLIs)

مرر `--cli claude|codex|copilot|cursor|opencode|pi|hermes|openclaw|factory|devin|antigravity|goose` لاستهداف وكيل معين (space-separated أو مكرر لأي مجموعة فرعية):

```bash
failproofai policies --install --cli codex --scope project
failproofai policies --install --cli copilot --scope project
failproofai policies --install --cli cursor --scope project
failproofai policies --install --cli opencode --scope project
failproofai policies --install --cli pi --scope project
failproofai policies --install --cli hermes --scope user
failproofai policies --install --cli openclaw --scope user
failproofai policies --install --cli factory --scope project
failproofai policies --install --cli devin --scope project
failproofai policies --install --cli antigravity --scope project
failproofai policies --install --cli goose --scope project
failproofai policies --install --cli claude codex copilot cursor opencode pi hermes openclaw factory devin antigravity goose
```

عندما يُحذف `--cli`، يكتشف `failproofai` أي agent CLIs مثبّتة (`which claude` / `which codex` / `which copilot` / `which cursor-agent` / `which opencode` / `which pi` / `which hermes` / `which openclaw` / `which droid` / `which devin` / `which agy` / `which goose`):

- **تم كشف CLI واحد** — auto-selects ذلك CLI بدون موافقة.
- **تم كشف CLIs متعددة** في محطة تفاعلية — يعرض prompt single-select بـ arrow-key مجموعة في قسم `Detected (N)` (مع صف aggregate `Install for all N detected` + كل CLI مكتشفة بشكل فردي) وقسم `Not installed (M) · install hooks ahead of time` يسرد كل CLI مدعومة غير مكتشفة كخيار forward-install (↑↓ للتحرك، Enter للانتقاء، ^C للإنهاء). تدفق الإلغاء يعرض قسم Detected فقط.
- **تم كشف CLIs متعددة** في run non-interactive (CI، بدون TTY) — التثبيت لكل CLI مكتشفة بدون موافقة.
- **لا شيء مكتشف** — ينحدر إلى `claude`، مع تحذير بأنه لم يتم العثور على وكيل binary في PATH؛ أمر hook لا يزال مكتوب بحيث ينشط بمجرد تثبيت واحد.

يمكنك تحرير `policies-config.json` مباشرة في أي وقت؛ التغييرات تأخذ التأثير الفوري على حدث hook التالي بدون الحاجة إلى إعادة تشغيل.

## مثال: إعدادات مستوى المشروع مع الإعدادات الافتراضية للفريق

التزم `.failproofai/policies-config.json` إلى المستودع الخاص بك:

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "block-env-files"
  ],
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "release", "hotfix"]
    }
  }
}
```

يمكن لكل مطور بعد ذلك إنشاء `.failproofai/policies-config.local.json` (مُدرج في gitignore) للتجاوزات الشخصية دون التأثير على زملائهم.
