تحقق من [الكتالوج المدمج](/ar/policies/builtin-catalog) قبل كتابة سياسة. القاعدة المراجعة عادة ما تكون أأمن من واحدة جديدة.

## ابدأ من سياسة تعمل

```bash
failproofai publish --init guards.mjs
failproofai policies -i -c ./guards.mjs
```

الكتل الأساسية تحجب `git push --force`. عدّلها، اطلب من وكيلك أن يحاول الإجراء المحجوب، وافحص **Policies → Activity**.

```js
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production",
  description: "Production changes need a human",
  match: { events: ["PreToolUse"], toolNames: ["Bash"] },
  fn: async (ctx) =>
    String(ctx.toolInput?.command ?? "").includes("production")
      ? deny("Ask a human before changing production.")
      : allow(),
});
```

تعيد السياسة `allow()` أو `deny(message)` أو `instruct(message)`. استخدم `deny` عندما يجب إيقاف الإجراء؛ لا يمكن لكل نطاق توصيل تعليمات مرة أخرى للوكيل.

## تحميل تلقائي

ضع الملفات المسماة `*policies.js` أو `*policies.mjs` أو `*policies.ts` تحت:

- `.failproofai/policies/` لمشروع واحد.
- `~/.failproofai/policies/` لمستخدمك.

## اختبر مسارات الفشل

اختبر كلاً من الإجراء غير الآمن والعمل المشروع الذي يبدو مشابهاً. تأكد من أن القرار جاء من سياستك وليس من قاعدة أخرى.

أزل ملفات الاختبار الصريحة باستخدام:

```bash
failproofai policies -u -c
```

عندما تكون السياسة جاهزة، [انشر حزمة](/ar/policies/publish-a-pack) أو [نشرها عبر Cloud](/ar/policies/deploy).
