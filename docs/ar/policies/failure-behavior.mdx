Failproof AI مصمم بحيث يكون فشل الإجراء مرئياً بدلاً من السماح صامتاً بعمل محفوف بالمخاطر.

## تشخيص كتلة مغلقة عند الفشل

<Tabs>
  <Tab title="Dashboard">
    1. انتقل إلى **Admin → enforcement** وافتح الجهاز.
    2. تحقق من آخر تسجيل دخول له والنشر المعين والنشر المبلغ عنه.
    3. انتقل إلى **Observe → policy** وافتح جلسة القرار المرفوض.
    4. تأكد مما إذا كان السبب يشير إلى إمكانية الوصول إلى المستقل أو عدم توافق الإصدار أو السياسة نفسها.

  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai config --status
    npm install -g failproofai@latest
    failproofai config
    ```

    إعادة تشغيل `failproofai config` يحدث ويعيد تشغيل المستقل بعد ترقية الحزمة.
  </Tab>
</Tabs>

على جهاز مكون لاستخدام `failproofaid`، يكون المستقل هو المقيّم الوحيد. إذا كان غير قابل للوصول أو إذا كان إصدار بروتوكوله لا يتطابق مع CLI، يفشل تقييم hook بشكل مغلق. يتم رفض الإجراء مع سبب يوجه المشغل للتحقق من المستقل أو تحديثه.

قبل تكوين المستقل، تقيم hooks السياسات في العملية. بمجرد تسجيل تكوين المستقل، لا يعود Failproof AI للعودة صامتة إلى محيّم ثانٍ عند فشل المستقل.

## الاستجابة لقرار مغلق عند الفشل

1. قم بتشغيل `failproofai config --status`.
2. إذا اختلفت الإصدارات، أعد تشغيل `failproofai config` بعد تحديث الحزمة.
3. إذا كان المستقل غير قابل للوصول، فتفحص حالة الخدمة والسجلات المحلية.
4. استأنف عمل agent فقط بعد التأكد من أن مسار تقييم السياسة معروف وسليم.

<Warning>
  لا تحاول مراراً إعادة محاولة الإجراء المحظور. رد مغلق عند الفشل يعني أن النظام لم يتمكن من إثبات أن الإجراء كان آمناً.
</Warning>
