الاستعادة تغيير النسخة المنتشرة أو تزيل تعيين السياسة؛ إنها لا تمحو سجل القرارات الذي يشرح الحادثة.

## استعادة آلة

<Tabs>
  <Tab title="لوحة التحكم">
    1. انتقل إلى **Admin → enforcement**، وسّع الآلة المتأثرة، وحدد مجموعة السياسات الأخيرة المعروفة الجيدة.
    2. حدد **edit**، واستعد تلك النسخ والتأثيرات، وطبق النشر الجديد.
    3. انتظر تسجيل الآلة، ثم تحقق من النشر المبلغ عنه.
    4. افتح **Observe → policy** والجلسات المتأثرة للتأكد من عدم حظر العمل الصحيح بعد الآن.

  </Tab>
  <Tab title="CLI">
    ابحث عن الجيل المراد العودة إليه، وأعد تفعيله، ثم أكد وصوله:

    ```bash
    fp fleet history ci-runner-01
    fp fleet rollback ci-runner-01 3
    fp fleet diff ci-runner-01
    failproofai config --status
    ```

    `fp fleet rollback` ينشئ جيل **جديد** يحمل المجموعة القديمة بدلاً من التراجع عن العداد، لذلك يبقى السجل مضافة فقط. يرفضها إذا كان ذلك الجيل يسمي سياسة تم تعطيلها أو حذفها منذ ذلك الحين — يقول الخادم ذلك بدلاً من إعادة تفعيل مجموعة لا يمكن تسليمها.

    `fp fleet diff` يعرض النية مقابل التسليم. تُقرأ الآلة على أنها انجرفت حتى يتم الاستقصاء التالي، لذا تحقق من الفرق قبل الخروج بنتيجة أن الاستعادة لم تتم. `failproofai config --status` يؤكد ذلك على الآلة نفسها.
  </Tab>
</Tabs>

## الإيقاف ليس استعادة

الإيقاف يعلق كل سياسة مثبتة محليًا لـ **جلسة واحدة**، وينتهي دائمًا من تلقاء نفسه — الحزم والملفات المخصصة وملفات الاتفاقية والمدمجات على حد سواء. فقط السياسات المدارة من السحابة وحارس `block-failproofai-commands` الذي يعمل دائمًا يستمران في الإنفاذ. لذلك الإيقاف ليس حلاً بديلاً لنشر سياسة سحابة سيئة، وهو نطاق انفجار أوسع مما يبدو: الحزمة هي حيث يعيش جميع الإنفاذ المحلي في الأساس، وحارس فشل الحزمة المغلق يتم تخطيه طوال المدة.

| الأمر | التأثير |
|---|---|
| `failproofai config --pause` | أحدث جلسة وكيل في هذا الدليل، لمدة 30 دقيقة |
| `failproofai config --pause 10m` | وقت معين. الحد الأقصى 8 ساعات؛ بادئات `s`/`m`/`h`، والرقم الفارغ يعني الدقائق |
| `failproofai config --pause --session <id>` | استهدف جلسة محددة |
| `failproofai config --resume` | أنهِ الإيقاف مبكرًا |
| `failproofai config --resume --all` | أنهِ كل إيقاف نشط |
| `failproofai config --status` | ما يتم إيقافه، ومتى يرفع |

## متى تستعيد

- تحظر السياسة إجراءً إنتاجيًا متوقعًا.
- حجم المطابقة أعلى بشكل ملحوظ مما توقعه الطرح المرصود.
- تعتمد السياسة على حقول لا توفرها التكامل.
- تغيير نسخة جديدة السلوك خارج وضع الفشل المقصود.

بعد الاستعادة، افتح الجلسات المتأثرة وحدد الشرط الذي تسبب في الإيجابية الخاطئة. أنشئ نسخة جديدة، واختبر كلاً من الحالة غير الآمنة والشرعية محليًا، ثم مرر من جديد عبر المراقبة قبل الإنفاذ مرة أخرى:

```bash
fp policies test ./policy.mjs --tool Bash --command '<the legitimate case>' --expect allow
fp policies publish my-policy ./policy.mjs
fp fleet deploy ci-runner-01 --add my-policy:observe
fp guardrails summary --since 24h --machine ci-runner-01
```

`:observe` هو ما يجعل ذلك طرحًا في الظل. `fp fleet deploy ... --add my-policy` بدون هيكل **ينفذ فورًا** — تأثير محذوف يُحل إلى التأثير المنتشر بالفعل، ثم إلى `enforce` — وهذا على سياسة استعدتها للتو يعني إعادة تفعيل الحادثة. وضع المراقبة لا يزال يقيّم السياسة بشكل حقيقي ويسجل كل قرار غير مسموح؛ فقط الإنفاذ يتم حجبه، لذا `fp guardrails summary` يقيس النسخة الجديدة مقابل نفس حركة المرور التي فشلت على القديمة. ارقِ باستخدام `--add my-policy:enforce` عندما تقول الأرقام ذلك.

<Warning>
  يمكن أن يكون إيقاف الإنفاذ مناسبًا أثناء حادثة، لكنه يوسع التعرض لكل سياسة نشطة في هذا النطاق. فضّل استعادة نسخة السياسة المحددة عند الإمكان.
</Warning>
