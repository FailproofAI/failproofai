FailproofAI writes to exactly two places: `~/.failproofai/` and a `.failproofai/` directory
in any project you configure. The only exception is the hook entry it adds to each agent
CLI's own settings file, so that CLI knows to call it.

---

## `~/.failproofai/` — the machine

A fresh install creates only what it needs. Most of the rows below are **conditional** — if
you have never connected to the cloud, never run an audit, or never upgraded across a layout
change, those paths simply do not exist. That is normal, not a broken install.

| Path | Holds | When it appears | Safe to delete? |
|---|---|---|---|
| `VERSION` | Layout version, CLI version, daemon version | Always | No — it is how upgrades know what to migrate |
| `config.json` | Machine settings: daemon, collector, capture paths, audit schedule | Always | Only if you want to re-run setup |
| `policies-config.json` | Your global policy selection and parameters | Always | Only if you want to lose your setup |
| `run/` | The service's runtime socket and lock | While the daemon is set up | Yes — recreated at start |
| `state/` | Launcher marker, last-seen version, telemetry id, shims, daemon run record — plus the upload spool for events not yet delivered | Always | **No** — deleting it discards undelivered events |
| `hook-activity/` | The decision log the dashboard reads | After the first hook fires | Yes — you lose local history |
| `bin/` | The daemon binary, versioned | After `failproofai config` installs the daemon | Yes — reinstalled by `failproofai config` |
| `policies/` | **Your own policy files.** Drop `*policies.mjs` in; no config needed | Only if you create it | No — this is your code |
| `policies/cloud-policies/` | Policies your organization deployed here | Only when connected to a deployment | Yes — re-fetched and verified on the next poll |
| `credentials.json` | Cloud tokens. **Owner-only (`0600`)** | Only after `failproofai config --connect` | Yes — you will need to reconnect |
| `audit/` | `dashboard.json` (the report) and `cache/` (per-transcript cache) | Only after an audit runs | Cache yes — the next audit is just slower. The report is your results |
| `logs/hooks.log` | Debug output from custom policy errors | Only when `FAILPROOFAI_HOOK_LOG_FILE` is set | Yes |
| `migrations/` | `applied.json` and pre-migration backups | Only after a migration actually runs | Keep until you are sure an upgrade went well |
| `custom-agents/` | Events from agents you instrumented yourself | Only if you use the SDK spool | **No** — may hold undelivered events |

<Note>
  **A fresh, cloud-free machine has seven entries** — `VERSION`, `config.json`,
  `policies-config.json`, `bin/`, `run/`, `state/`, `hook-activity/`. Everything else is
  created on demand. `migrations/` in particular only appears once a migration has run: the
  steps are *layout* steps, so installing at the current layout runs none at all.
</Note>

<Note>
  Put your own policy files **directly** in `policies/`. The `cloud-policies/` folder
  beside them is managed for you, and discovery does not descend into subdirectories — so
  the two can never collide.
</Note>

## `.failproofai/` — the project

| Path | Holds | Commit it? |
|---|---|---|
| `policies-config.json` | Project policy selection and parameters | **Yes** — this is your team's standard |
| `policies-config.local.json` | Your personal overrides for this repo | **No** — gitignore it |
| `policies/` | Convention policy files for this repo | **Yes** |

A project's config layers over your global one. [Merge rules →](/ar/configuration)

## Agent CLI settings files

FailproofAI adds a hook entry to each agent CLI's own configuration, in that CLI's own
schema, preserving everything else in the file. [The full list of paths, per
CLI →](/ar/agent-support#where-the-hooks-get-written)

These are the only files outside `~/.failproofai/` and `.failproofai/` that FailproofAI
writes to, and `failproofai uninstall` removes exactly what it added.

---

## Agent transcripts — read, never written

Each agent CLI writes its own session records, in its own format and location. FailproofAI
**reads** them to render session replay, to run the [audit](/ar/audit), and — on a connected
machine — to give the cloud a picture of the run.

They are never modified, moved, or deleted. If your transcripts live somewhere
non-standard, [`failproofai harness add-path`](/ar/cli/harness) points at them.

---

## Permissions

- `credentials.json` is written `0600`, and the directory around it is tightened to match. A
  `0600` file inside a world-readable directory is still reachable by every local user.
- Cloud tokens are deliberately **not** placed in the service definition file, which is
  installed world-readable. That is also why connecting, rotating a token, and disconnecting
  all work without `sudo`.

---

## What an upgrade does to all of this

A new version may reorganize `~/.failproofai/`. When it does, the first command after the
upgrade migrates it and **carries your configuration across** — policy selection, machine
settings, cloud connection, your own policy files and the helpers they import, the decision
log, and anything not yet delivered.

Rebuilt rather than migrated: the audit cache, cloud deployments (re-fetched and verified),
and service scratch state.

Irreplaceable files are copied to a backup directory before anything runs, and every
migration is recorded. See [`failproofai migrate --dry-run`](/ar/cli/migrate).
