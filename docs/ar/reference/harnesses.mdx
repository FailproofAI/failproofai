جهاز التشغيل هو ما يعمل الوكيل بداخله فعليًا. يدعم Failproof AI اثني عشر منها، في فئتين:

- **واجهات سطر الأوامر لترميز الأكواد** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **بوابات الدردشة والمساعد** (2) — Hermes (Slack, Telegram, cron), OpenClaw (مساعد ذاتي الاستضافة)

تنطبق نفس السياسات ونفس سجل الجلسة بغض النظر عن الجهاز الذي يعمل فيه الوكيل. تخطط طبقة محول واحدة أسماء الأحداث الأصلية لكل جهاز وأسماء الأدوات ومجالات إدخال الأدوات على 29 حدثًا قانونيًا قبل تشغيل أي سياسة.

الوكيل الذي لا يعمل في **أي واحد** من الاثني عشر يتم تجهيزه مباشرة باستخدام [Python SDK](/ar/reference/custom-agents). هذا عقد مختلف، ومن المهم توضيحه: يوفر SDK التتبع والجلسات والتقييمات والتدقيقات — **لكنه لا يفرض السياسات من تلقاء نفسه.** منع إجراء غير آمن قبل تنفيذه يتطلب hook فرض عند حدود الأداة في وقت التشغيل الخاص بك؛ [اتصل بنا](mailto:support@befailproof.ai) وسنقوم بتعيينها.

| جهاز التشغيل | نطاقات hook المدعومة |
| --- | --- |
| Claude Code | المستخدم، المشروع، محلي |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | المستخدم، المشروع |

يقوم كل تكامل بتوحيد أسماء أحداث hook الأصلية وأسماء الأدوات ومجالات إدخال الأدوات قبل تشغيل السياسات. لا يمكن للسياسة أن تعمل إلا على الأحداث التي يفضحها جهاز التشغيل؛ اختبر سلوك نهاية الدور والتعليمات على جهاز التشغيل والإصدار المحدد الذي تنشره.

## قدرة الفرض

"حظر" يعني أن الحكم الذي أرجعته محول التكيف الحالي يتم استهلاكه من قبل جهاز التشغيل المسمى. قد يستبدل الحظر بعد الأداة النتيجة المعروضة للنموذج لكنه لا يمكن أن يتراجع عن آثار جانبية للأداة حدثت بالفعل.

| جهاز التشغيل | أحداث الحظر المُتحقق منها | تحذيرات الملاحظة فقط أو عدم الحظر |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact`, وعدة أحداث مهام/إعدادات | `PostToolUse`, دورة حياة الجلسة، الإشعارات، وأحداث ما بعد الفشل هي ملاحظات. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | الحظر بعد الأداة يستبدل النتيجة بعد التنفيذ؛ أحداث بداية الجلسة والضغط هي ملاحظات في التكيف الحالي. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | الحظر بعد الأداة يستبدل النتيجة بعد التنفيذ؛ أحداث الجلسة والإشعارات هي ملاحظات. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` وأحداث الجلسة هي ملاحظات. |
| OpenCode | `PreToolUse` | أحداث ما بعد الأداة ودورة الحياة هي ملاحظات؛ معالجة التوقف الحالية هي إرشادات لدور لاحق وليست بوابة موثوقة. |
| Pi | `PreToolUse`, `UserPromptSubmit` | أحداث ما بعد الأداة ودورة الحياة هي ملاحظات؛ إرشادات التوقف تنطبق على دور لاحق. |
| Hermes | `PreToolUse` | `deny()` يحظر. `instruct()` لا توقف الاستدعاء: يتم تشغيله، والإرشادات توضع في بداية نتيجته. أحكام ما بعد الأداة والجلسة وإيقاف الوكيل الفرعي ليست بوابات. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | أحداث ما بعد الأداة والجلسة وإيقاف الوكيل الفرعي والضغط هي ملاحظات. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | أحكام ما بعد الأداة وإيقاف الوكيل الفرعي هي ملاحظات. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, مشروط `PermissionRequest` | hooks الأذونات لا تعمل في كل وضع أذونات؛ أحداث ما بعد الأداة والجلسة هي ملاحظات. |
| Antigravity CLI | `PreToolUse`, `Stop` | أحكام رسالة المستخدم وما بعد الأداة هي ملاحظات؛ لا يزال بإمكان حقن تعليمات الرسالة. |
| Goose | `PreToolUse` | أحداث رسالة المستخدم وما بعد الأداة والجلسة هي ملاحظات. يوجد hook توقف حظر أصلي في المنبع لكن لا يتم تثبيته من قبل التكيف الحالي. |

القدرات حساسة للإصدار. أعد الاختبار بعد ترقية CLI الوكيل، خاصة عندما تعتمد السياسة على سلوك الرسالة أو الإيقاف أو الأذن أو ما بعد الأداة بدلاً من بوابة ما قبل الأداة الشائعة.

### plugin Hermes الأصلي

يتم دمج Hermes من خلال plugin أصلي خاص بالملف الشخصي وليس من خلال أمر shell. يربط التثبيت كل ملف شخصي Hermes افتراضي ومسمى `plugins/failproofai` بالplugin المرسل في حزمة npm (نسخة حيث لا يمكن إنشاء رابط رمزي)، ويفعله في ملف `config.yaml` لذلك الملف الشخصي، وينقل فقط إدخالات hook FailproofAI الموروثة. لأن الplugin مرتبط، `npm install -g failproofai@latest` يحدثه بدون إعادة تثبيت. هذا يتجنب spawn العملية على كل hook. يدعم الplugin Hermes 0.20.0 والإصدارات الأحدث.

Hooks shell الموروثة (التي تم تثبيتها بواسطة 1.0.5 والإصدارات الأقدم) **لا** تتحقق من مهام Hermes cron: كل تشغيل cron ينشئ نطاق hook خاص به، الذي ينضم إليه الplugin الأصلي و shell hooks في `config.yaml` لا. `failproofai update` ينقل كل ملف شخصي يستخدم بالفعل FailproofAI إلى الplugin المرتبط. إذا لم تتمكن daemon المشغلة من خدمة الplugin، `update` يترك shell hooks في مكانها ويخرج بقيمة غير صفر؛ قم بتشغيل `failproofai config` لتحديث daemon، ثم `failproofai update` مرة أخرى. تحمل مهام Cron الplugin عند تشغيلها التالي؛ أعد تشغيل الbranches المفعلة والجلسات التفاعلية لتحميله هناك.

على Hermes، `deny()` يحظر الاستدعاء و `instruct()` لا: يتم تشغيل الاستدعاء، والإرشادات توضع في بداية نتيجته — كمفتاح أول، `failproof_policy_reminder`، لنتيجة JSON، أو كسطر `[FailproofAI policy reminder (...)]` رائد — بحيث يقرأه النموذج مع الإخراج، والبرامج النصية التي تحلل النتيجة تستمر في العمل. يتم عرض تذكير السياسة مرة واحدة لكل دور، وتحتفظ بها قصيرة على نتيجة كبيرة. استخدم `deny()` عندما يجب ألا يحدث إجراء على الإطلاق: `instruct()` لا يوقف الإجراء أولاً بعد الآن. استدعاءات الأداة التي تتم من برنامج نصي `execute_code` ضع تذكيرها على النتيجة `execute_code` التي يقرأها النموذج؛ نسخة البرنامج النصي الخاصة به من النتيجة تُترك دون تغيير. يتم إخبار النموذج بعدم الاستشهاد بالتذكير في ردوده.

يعود build Hermes بدون middleware plugin إلى الاحتفاظ بالاستدعاء المطابق مرة واحدة مع إرشادات سياسة FailproofAI؛ قد تكرر استجابة النموذج التالية ذلك، أو تقوم بنفس العمل بأداة أخرى، دون أن يتم الاحتفاظ بها مرة أخرى.

تتم مطابقة أسماء الأدوات عبر إصدارات Hermes: `process_manage`، `cronjob_manage`، و `todo_list` (Hermes 0.21) يتم التعامل معها مثل `process`، `cronjob`، و `todo` (Hermes 0.20). في كل مرة يقوم Hermes بتحميل الplugin، يكتب `heartbeat.json` في دليل `plugin-data/agent-plugin-failproofai-5296f299/` للملف الشخصي، مسجلاً إصدار Hermes، وحيث Pluig ومسار الإصدار، وhooks التي قبلها Hermes. قم بتشغيل `failproofai config --status` للكشف عن ملف شخصي معطل أو غير كامل أو مكرر أو تم تكوينه مؤخرًا بدون، أو لا يزال على shell hooks الموروثة (يتم الإبلاغ عنه كـ "لا يتم فحص مهام Hermes cron").

### OpenClaw plugin

يقوم OpenClaw بتحميل FailproofAI كplugin gateway معالج في الذاكرة، مسجل في ملف `openclaw.json` لكل ملف شخصي. مثل plugin Hermes، فإنه يطلب من daemon `failproofaid` المحلي الحكم على كل استدعاء فوق socker الخاص به، لذلك يحتاج إلى daemon مشغل: يرفض التثبيت بدون واحد، وإذا لم تتمكن daemon من الإجابة، يتم حظر استدعاءات الأداة والرسائل والسبب مكتوب في سجل gateway. بعد `npm install -g failproofai@latest`، أعد تشغيل bran OpenClaw بحيث يحمل الplugin المحدث.

### Codex hook trust

يقوم Codex 0.129 والإصدارات الأحدث بتشغيل hook من `~/.codex/hooks.json` فقط بعد الموافقة عليه في `codex` التفاعلي (استعراض Hooks)؛ حتى ذلك الحين، كل جلسة Codex — بما في ذلك headless `codex exec` — تتخطيها. تعمل Hooks في إعدادات Codex النظام، `/etc/codex/config.toml` على Linux و macOS، بدون هذه الموافقة.

لذا عندما `failproofai config` (أو `policies --install --cli codex` في نطاق المستخدم) يمكنها استخدام sudo، تكتب Codex hooks في `/etc/codex/config.toml`، بين `# >>> failproofai managed hooks >>>` و `# <<< failproofai managed hooks <<<`، وتترك بقية الملف كما هي.

هذا الملف ينطبق على كل حساب على الآلة، لذا فإن كل hook فيه يقوم بتشغيل `/opt/failproofai-codex/codex-hook`، وهو برنامج نصي قصير يملكه root. البرنامج النصي يسلم الحدث إلى failproofai الخاص به لكل حساب قام بإعداد hooks هناك، ولا يفعل شيئًا لأي حساب آخر. حساب آخر يريد Codex hooks من FailproofAI يقوم بإعداده لنفسه.

قبل كتابة الكتلة، وفي كل مرة `failproofai update`، يتحقق failproofai من أن `/etc/codex/config.toml` نفسه والبرنامج النصي وكل دليل أعلاهم والـ `sh`, `id` و `cat` التي يقوم بتشغيلها تخص root ولا يمكن كتابتها من قبل أي شخص آخر، وأن failproofai لكل حساب ينتمي إلى هذا الحساب أو root. عند التثبيت، عندما يفشل هذا الفحص، تبقى hooks الخاصة بك في `~/.codex/hooks.json`. عند التحديث، يأخذ البرنامج النصي الذي يفشل فيه الكتلة، وحساب فشل failproofai الخاص به يتم إخراجه من البرنامج النصي؛ قم بتشغيل `failproofai config` مرة أخرى بمجرد إصلاحه. `failproofai update` يعيد كتابة أيضًا كتلة كتبت بواسطة إصدار سابق لاستخدام البرنامج النصي، الذي يحتاج sudo.

`failproofai uninstall` وعدم التحقق من Codex في `failproofai config` يخرج حسابك مرة أخرى، والكتلة معها بمجرد عدم بقاء أي حساب.

بدون sudo، وعلى Windows، تبقى hooks في `~/.codex/hooks.json`. `failproofai config` و `failproofai config --status` ثم لا تعتبر Codex كفرض حتى يتم الموافقة على hooks، وقل كيفية إصلاحه: أعد تشغيل `failproofai config` وسمح بـ sudo، أو افتح `codex` مرة واحدة والموافقة على hooks.

## تثبيت capture وhooks السياسة

<Tabs>
  <Tab title="لوحة المعلومات">
    1. افتح **الإعدادات → مفاتيح API** وأنشئ مفتاحًا بـ `events:add` و `policies:pull`، مع اسم للآلة أو البيئة.
    2. على الآلة المستهدفة، قم بتوصيل CLI المحلي بالمفتاح المعروض وثبت hooks جهاز التشغيل.
    3. ابدأ جلسة وكيل جديدة، ثم أكد أحداث hook والجلسة تحت **trace → أحداث مباشرة**.
    4. افتح **fix → النشاط** للنافذة الزمنية نفسها وأكد أن قرار السياسة ينسب إلى الآلة.

    يبدأ الاتصال بمفتاح آلة. تأكد من أنه يتضمن أذونات الإدخال وتسليم السياسة قبل نسخ السري.

    ![درج مفتاح API الجديد المستخدم لمنح إذونات إدخال الأحداث وتسليم السياسة.](/images/dashboard/key-create.png)

    بعد تثبيت hooks، يجب أن يظهر تدفق الأحداث أحداثًا جديدة من الآلة والبيئة التي متصلة بها.

    ![تدفق الأحداث المباشرة المستخدمة للتأكد من أن جهاز التشغيل المثبت حديثًا يتم الإبلاغ عنه.](/images/dashboard/events-stream.png)

    أخيرًا، تحقق من أن قرارات السياسة ينسبها إلى نفس الآلة. هذا يؤكد أن جهاز التشغيل يبلغ عن نشاط السياسة بالإضافة إلى أحداث التتبع.

    ![صفحة السياسة المستخدمة للتحقق من قرارات السياسة من جهاز تشغيل متصل حديثًا.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    اقرأ مفتاح الآلة في shell. `read -s` يأخذه في موجه لا يصدر صدى، لذا لم يظهر أبدًا في أمر أو في سجل shell:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    ثم قم بإعداد الآلة — هذا يسلك hooks لكل جهاز تشغيل مكتشف، وثبت daemon، وتابع إلى Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    الإعداد لا يمكن السياسة بحد ذاته، وهو ما الأمر الثاني لأجله.

    أو استهدف أجهزة التشغيل المسماة ونطاق التكوين:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    نطاق المشروع يحتفظ بتكوين hook مع مستودع. النطاق المستخدم يغطي العمل عبر المستودعات. Claude Code يدعم أيضًا النطاق المحلي؛ يختلف الدعم حسب جهاز التشغيل والـ CLI يرفض المجموعات غير المدعومة.

    تحقق من الآلة وأحداثها:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## أضف مسار جلسة غير افتراضي

<Tabs>
  <Tab title="لوحة المعلومات">
    المسارات الإضافية مسجلة على الآلة، وليس في Cloud. بعد إضافة واحد، افتح **trace → الجلسات**، رشح إلى بيئة الآلة، وأكد أن الجلسات من المسار الجديد تظهر. افتح جلسة والتحقق من الوكيل وجهاز التشغيل وطوابع زمن الحدث قبل الاعتماد عليها في عملية تدقيق.

    ![قائمة الجلسات مرشحة إلى البيئة التي تتلقى البيانات من مسار الالتقاط الإضافي.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    أضف مسارًا مع تسمية اختيارية، ثم افحص المسارات المكونة:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    أزل مسارًا بـ `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  قم بتشغيل جلسة جديدة واحدة بعد التثبيت. تحقق من كل من تدفق الأحداث المباشرة وقرار السياسة الفعلي قبل توسيع التطبيق.
</Tip>
