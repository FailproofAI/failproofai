يتم تقديم واجهة برمجة التطبيقات العامة ضمن `/v1` على أصل لوحة تحكم Failproof AI الخاصة بك. على Failproof AI Cloud، هذا الأصل هو `https://app.befailproof.ai`، لذا المسار الأساسي هو `https://app.befailproof.ai/v1`. على نشر موزع ذاتياً، يكون مضيف لوحة التحكم الخاص بك متبوعاً بـ `/v1`؛ مرر هذا المضيف إلى `fp` باستخدام `--base-url <url>` أو `FP_DASHBOARD_URL`.

## إنشاء مفتاح وإجراء طلب

<Tabs>
  <Tab title="Dashboard">
    1. افتح **Administration → Keys**، حدد **new key**، واختر أضيق إعدادية أذونات تغطي التكامل.
    2. أضف منح فردية فقط عند الحاجة، أنشئ المفتاح، وانسخ سره لمرة واحدة.
    3. قم بإجراء طلب اختبار إلى `/v1/sessions` وأكد بقاء المفتاح نشطاً في صفحة المفاتيح.
    4. قم بتدوير المفتاح أو تعطيله من قائمة إجراءاته عند تغيير ملكية التكامل.

    ![درج مفتاح API الجديد مع إعدادية الأذونات والمنح الفردية.](/images/dashboard/key-create.png)

    يظهر درج الإنشاء أعلاه. السر لمرة واحدة يظهر فقط بعد إنشاء المفتاح؛ انسخه قبل إغلاق هذا التأكيد.
  </Tab>
  <Tab title="CLI">
    أنشئ مفتاح قراءة واستخدمه مباشرة مع `fp` أو `curl`. يقرأ `fp` المفتاح من `--api-key` أو من `FP_API_KEY`:

    ```bash
    fp keys create reliability-reader \
      --permission-set read-only

    export FP_API_KEY="<one-time-secret>"
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/sessions?limit=20" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

تكون المفاتيح محدودة بمنظمة وقائمة مسطحة من الأذونات. تقوم مجموعة الأذونات فقط بتأسيس تلك القائمة وقت الإنشاء — يخزن المفتاح المنح الموسعة، لذا تغيير المجموعة بعد ذلك لا يغير المفتاح. طلب بدون الأذن المطلوبة للنقطة النهائية يرجع `403` ويحدد الأذن المفقودة.

## اختيار المنظمة

مفتاح المنظمة يعمل على منظمته تلقائياً. مفتاح محدود بالمثيل يختار منظمة لكل طلب، والمستأجر الذي يملك أكثر من منظمة واحدة يجب أن يسمي منظمة واحدة دائماً في وضع المفتاح — لا يرسل `fp` أبداً منظمة محفوظة عندما يتم المصادقة باستخدام مفتاح.

| المستدعي | كيفية تسمية المنظمة |
| --- | --- |
| `fp`، لكل استدعاء | `--org <slug>`، قبل الأمر الفرعي |
| `fp`، من البيئة | `FP_ORG` |
| HTTP خام | رأس الطلب `X-AgentEye-Org: <slug>` |

`X-AgentEye-Org` يحتفظ بتهجئته الأصلية على السلك. إنه الرأس الذي تقرأه لوحة التحكم لحل المنظمة النشطة، وإعادة تسمية اسمه في عميل تكسر الطلب.

<Tabs>
  <Tab title="Dashboard">
    استخدم محول المنظمة في رأس لوحة التحكم قبل فتح **Administration → Keys**. المفاتيح المُنشأة هناك تنتمي إلى المنظمة المحددة. أكد slug المنظمة في عنوان URL وتفاصيل المفتاح قبل نسخ بيانات الاعتماد إلى الأتمتة.

  </Tab>
  <Tab title="CLI">
    استخدم `--org` قبل الأمر، أو أرسل رأس المنظمة لمفتاح API محدود بالمثيل. `fp orgs list` لا يكتشف slug لك هنا — يرفض في وضع المفتاح؛ اقرأ slug من محول المنظمة في لوحة التحكم بدلاً من ذلك.

    ```bash
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/usage" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

## الترقيم

نقاط نهاية القائمة مرقمة بـ keyset، والعقد نفسه ينطبق سواء استدعيتها عبر `fp` أو عبر `curl`.

| العنصر | المعنى |
| --- | --- |
| معامل استعلام `limit` | الصفوف المطلوبة في هذا الاستدعاء. يحد `fp` طلب واحد إلى 200 صف على كل نقطة نهاية. الطلب الخام يرتبط بسقف الخادم الخاص به لكل نقطة نهاية بدلاً من ذلك. |
| معامل استعلام `cursor` | رمز معتم يستأنف التغذية بعد صفحة سابقة. |
| حقل الاستجابة `next_cursor` | الرمز للصفحة التالية. `null` يعني أن التغذية استنفدت. |

تختلف تلك الأسقف حسب النقطة النهائية، وكل صفحة نقطة نهاية تسمي الإعداد الافتراضي والحد الأقصى الخاص بها:

| النقطة النهائية | الافتراضي | الحد الأقصى |
| --- | --- | --- |
| `/events`, `/events/summary` | 50 | 1000 |
| `/issues`, `/alerts/{id}/issues` | 200 | 1000 |
| `/evaluation-jobs` | 100 | 500 |
| `/audits/findings` | 100 | 500 |
| `/sessions`, `/evaluations` | 50 | 200 |
| `/audits/{id}/runs` | 50 | 200 |

اقرأ تغذية كاملة بإعادة إصدار الطلب نفسه مع `cursor` معين إلى `next_cursor` من الاستجابة السابقة حتى يعود `next_cursor` `null`. أعلام `fp` المكافئة — `--all`, `--cursor` و `--page-size` — موثقة في [مرجع Cloud CLI](/ar/reference/cloud-cli).

## مرجع النقطة النهائية ومعالجة الأخطاء

استخدم صفحات النقطة النهائية المُنشأة في هذا القسم للحصول على المسارات والمعاملات والمتطلبات والرموز الحالية. يتم إنشاء الموصفة من تعليقات مسار الخادم وفحصها مقابل جهاز التوجيه `/v1`.

تحتوي الموصفة الحالية على تغطية كاملة للمسار والطريقة والمعامل والإذن ورموز الحالة. يتم كتابة أجسام الطلبات؛ أجسام الاستجابات لا — الموصفة لا تحمل مخططات استجابة اليوم، لأن الخادم لا يزال ينشئها كـ JSON ديناميكي. افحص استجابة حقيقية قبل توليد عميل بنوع قوي.

استخدم `Content-Type: application/json` لكتابات JSON. تعامل مع `401` كمصادقة مفقودة أو غير صحيحة، `403` كهوية صحيحة بدون الأذن المطلوبة، `404` كمورد مفقود أو غير قابل للوصول من المنظمة، `409` كتعارض في الحالة، `400` كمعامل مرفوض — قيمة تصفية غير معروفة، معامل استعلام معطوب، بيان لن يعمل — و `422` كقيمة حقل أو إذن غير صحيحة في جسم الطلب. تتضمن استجابات الخطأ رسالة يمكن قراءتها؛ فشل الأذونات أيضاً يسمي المنحة المطلوبة.

## الأسطح التي لا يحملها `/v1`

السياسات المُدارة بالسحابة والأسطول وتغذية قرار الحماية هي أسطح المشغلين — القراءات والكتابات على حد سواء. هي جذر فقط على الخادم وغائبة بشكل متعمد عن `/v1`، التي تواجه الإنترنت. نشر إصدار سياسة أو نشره على آلة، على سبيل المثال، ليس شيئاً يمكن لمفتاح API فعله، وقراءة ما قررته الأسطول على نفس الأسطح.

لذا يحصل مفتاح API على رفض بالتصميم على تلك المسارات، و `fp` يرفض قبل فتح اتصال بدلاً من ترك الطلب 404 بدون تفسير:

| الأمر | السلوك تحت مفتاح API |
| --- | --- |
| `fp policies` | يرفض بـ exit `2` ويسمي السياسات المُدارة بالسحابة كسطح للمشغلين |
| `fp fleet` | يرفض بـ exit `2` ويسمي الأسطول كسطح للمشغلين |
| `fp guardrails` | يرفض بـ exit `2` ويسمي تغذية الحماية كسطح للمشغلين |
| `fp agent` | يرفض بـ exit `2`؛ المساعد مُنفذ بواسطة لوحة التحكم، وليس API |
| `fp orgs` | يرفض بـ exit `2`؛ عضوية المنظمة تنتمي إلى مستخدم مسجل دخول، ومفتاح يعمل بالفعل لمنظمة واحدة |

قم بتشغيل هذه تحت جلسة مستخدم مسجل دخول (`fp login`) بدلاً من ذلك، أو استخدم لوحة التحكم. عائلات القراءة والإدارة — الجلسات والأحداث والتقييمات والتدقيقات والمشاكل والتنبيهات والمفاتيح ومجموعات الأذونات والمستخدمين والإعدادات والاستعلامات والاستخدام — لكل منها مسار `/v1` وتعمل مع مفتاح. الفجوة الوحيدة هي `fp keys update`: تحتاج إلى `keys:update`، إذن لا يمكن لأي مفتاح API أن يمتلكه، لذا يمكن لمفتاح أن ينشئ ويعطل المفاتيح ولكن لا يحرر أذونات أحدها أبداً. `fp login` و `fp logout` أيضاً يرفضان في وضع المفتاح، لسبب مختلف: المفتاح بالفعل هو بيانات الاعتماد، وهو لم يتم حفظه على القرص أبداً.
