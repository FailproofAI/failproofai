تترك حالات فشل الشبكة المؤقتة واستجابات HTTP 408 و 429 و 5xx القياس عن بُعد مؤهلاً للإعادة التلقائية، حتى بعد انقطاع طويل. يحافظ daemon على الدفعة حتى يتم تأكيد التسليم. يتطلب الرفض `event_too_large` حمولة حدث أصغر قبل إعادة المحاولة. الملفات المُوسومة بالفعل بـ `.poison` تحتاج إلى استرجاع يدوي؛ التحديث لا يعيد إرسالها تلقائياً.

<AccordionGroup>
  <Accordion title="لا تظهر جلسات في Cloud">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **Administration → Keys** وأكّد أن مفتاح الجهاز نشط وله `events:add`. ثم افتح **Observe → Events**، وسّع نطاق الوقت، وامسح عوامل تصفية البيئة والوكيل. إذا كانت هناك أحداث، ابحث عن معرّف الجلسة ثم تحقق من **Observe → Sessions** من أجل التجميع. إذا لم تكن هناك أحداث، شخّص daemon Failproof من CLI.

        ![دفق الأحداث المباشر مع عوامل التصفية الأساسية الخاصة به وأحداث الوكيل الأخيرة الواصلة.](/images/dashboard/events-stream-current.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait --timeout 60
        fp list envs
        fp events --since 24h --limit 20
        fp sessions --since 24h --limit 20
        ```

        أكّد أن الالتقاط مُفعّل والمفتاح المُكوّن له `events:add`، وأن عامل تصفية لوحة التحكم يطابق البيئة المُرسلة.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="أحداث Python SDK تبقى على القرص">
    <Tabs>
      <Tab title="لوحة التحكم">
        امسح عوامل التصفية في **Observe → Events** وابحث عن معرّف جلسة SDK الدقيق. إذا لم يظهر شيء، افحص spool SDK و daemon Failproof على الجهاز المصدر.
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait
        ```

        أكّد أن daemon يعمل ومتصل — SDK يرسل إلى spool سواء كان موجوداً أم لا. دليل spool **لا** يحتاج إلى الموجود مسبقاً (الكاتب ينشئه)، ولا يوجد متغير بيئة يختاره: `$FAILPROOFAI_HOME/custom-agents`، وإلا `~/.failproofai/custom-agents`، هو الجذر الوحيد، و `configure(base_dir=...)` هو الاستثناء الوحيد. إذا تم قتل العملية بـ `SIGKILL` أو OOM-killed، فقد ضاع كل ما كان في الطابور — تعامل مع `SIGTERM` لتحديد ذلك.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="الجهاز لا يستقبل السياسات">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **Admin → enforcement**، حدد الجهاز، وقارن إصداراته المخصصة والمُبلّغ عنها والسابقة. أكّد أن نطاق النشر يتضمن الجهاز ومفتاحه له `policies:pull`. يمكن للبث أن يعمل حتى عندما لا يعمل تسليم السياسة.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config --status
        ```

        أكّد أن معرّف الجهاز والتسمية تطابق هدف لوحة التحكم. أعد الاتصال بمفتاح قادر على السياسة إذا كان بيانات الاعتماد الموجودة تمنح فقط بث الأحداث.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Cloud ذاتي الاستضافة برسالة خاصة لسلطة التصديق لا يحصل على أحداث أو سياسات">
    <Tabs>
      <Tab title="لوحة التحكم">
        تم اتصال الجهاز وخطافاته تعمل، لكن **Observe → Events** تبقى فارغة و **Admin → enforcement** أبداً لا تُظهر نشره مُطبقاً. CLI و daemon Failproof يثقان بالشهادات بشكل مختلف. CLI يعمل على Node ويحترم `NODE_EXTRA_CA_CERTS`. `failproofaid`، الذي يرسل الأحداث ويسحب السياسات، يثق بالشهادات المجمّعة معه بالإضافة إلى متجر الثقة الخاص بنظام التشغيل، ويتجاهل `NODE_EXTRA_CA_CERTS`. ثبّت CA الخاص بك في متجر النظام على الجهاز.
      </Tab>
      <Tab title="CLI">
        ```bash
        # Debian / Ubuntu
        sudo cp company-ca.pem /usr/local/share/ca-certificates/company-ca.crt
        sudo update-ca-certificates
        # RHEL / Fedora
        sudo cp company-ca.pem /etc/pki/ca-trust/source/anchors/ && sudo update-ca-trust
        # macOS
        sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain company-ca.pem

        # then restart the daemon, which loads trusted certificates at start
        sudo systemctl restart failproofaid@$USER                           # Linux
        sudo launchctl kickstart -k system/ai.failproof.failproofaid.$USER  # macOS
        ```

        يُسمّي سجل daemon السبب: `sudo journalctl -u failproofaid@$USER | grep UnknownIssuer` على Linux. `SSL_CERT_FILE` أو `SSL_CERT_DIR` في بيئة الخدمة يستبدل متجر النظام للـ daemon، والشهادات المجمّعة لا تزال تنطبق. الدفعات التي فشلت بينما كانت CA غير موثوقة يتم الاحتفاظ بها في `~/.failproofai/state/failed` وإعادة محاولتها تلقائياً، تقريباً كل ساعة وعند إعادة تشغيل daemon.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="يتم رفض إجراء لأن daemon غير متاح">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **Admin → enforcement** وافحص آخر وقت ظهور الجهاز والإصدار المُبلّغ عنه. إذا كان الجهاز قديماً، تعامل معه كمشكلة daemon محلية. لا تضعّف السياسة المنشورة فقط لتجاوز daemon غير متاح.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        أعد تشغيل أو حدّث `failproofaid`؛ أعد تشغيل التكوين عندما تختلف إصدارات بروتوكول CLI و daemon. يفشل مسار daemon المُكوّن بالتصميم.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="سياسة مخصصة لا تُحمّل">
    <Tabs>
      <Tab title="لوحة التحكم">
        بالنسبة لسياسة مُؤلّفة في Cloud، افتح **Admin → policy editor**، حدد المسودة، واستعرض أخطاء التحقق قبل النشر. بالنسبة لسياسة محلية، استخدم CLI للتحقق منها، ثم افتح **Observe → policy** بعد إجراء اختبار لتأكيد وصول القرارات.

      </Tab>
      <Tab title="CLI">
        أكّد أن اسم الملف ينتهي بـ `policies.js` أو `policies.mjs` أو `policies.ts`، وتستدعي الوحدة `customPolicies.add(...)`، والواردات تُحل من ملف السياسة.

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="تدقيق لا يُرجع نتائج">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **Analyze → audits**، حدد الدورة، وتحقق ما إذا كانت تحليل النموذج قد تم تشغيله. ثم قارن نطاقه والنافذة الخاصة به مع **Observe → sessions** وافتح آثار ممثلة من تلك السكان.

        النتيجة الصفرية ذات معنى فقط عندما يعمل التحليل بنجاح. إذا تم تخطي التحليل أو فشل، لا تُرجع الدورة أي نتائج وتبقي النافذة غير المُحللة مفتوحة لدورة ناجحة مستقبلية. إذا تم تعطيل تحليل النموذج، لا تُرجع المراجعة أيضاً أي نتائج لأن المسح الحتمي للبيانات الاعتماديّة والمعرّفة الشخصية يسجل الإحصائيات فقط ولا يرفع النتائج بعد الآن.

        ![نموذج التدقيق حيث تحدد البيئة والوكيل والتكرار ونافذة الكسح سكان الجلسة.](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        إذا بقيت الدورة في الطابور، انتظر سعة audit-agent أو اطلب من مشغل النشر فحص أسطول التدقيق. يُعاد محاولة التدقيق في الطابور؛ لم يتم تخطيه فوراً.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="التقييمات عبر الإنترنت لا تعمل تلقائياً">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح جلسة مكتملة وتحقق ما إذا كان التقييم اليدوي ناجحاً. Hosted Cloud حالياً لا يوجد فيه تحكم في نقطة نهاية المقيّم في لوحة التحكم؛ يجب على مشغل الخادم تكوينه.
      </Tab>
      <Tab title="CLI">
        تحقق من المقيّم نفسه، ثم افحص حالات التقييم الأخيرة:

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        في Cloud ذاتي الاستضافة، أكّد أن `EVALUATOR_ENDPOINT` موجود على الخادم و `EVALUATOR_TOKEN` يطابق المقيّم. يتم تعطيل التقييم التلقائي عندما تكون نقطة النهاية غائبة.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="مصادقة Cloud CLI تستهدف المنظمة الخاطئة">
    <Tabs>
      <Tab title="لوحة التحكم">
        استخدم محول المنظمة وأكّد الـ slug والأذونات المتوقعة قبل مقارنة النتائج مع CLI.
      </Tab>
      <Tab title="CLI">
        ```bash
        fp whoami
        fp orgs current
        fp orgs perms
        ```

        في وضع مفتاح API، حدّد `fp --org <slug> --api-key <key> ...` أو اضبط `AGENTEYE_ORG`. تُتجاهل حالة منظمة جلسة الإنسان المحفوظة بقصد لطلبات مفتاح API.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="سياسة تحجب عملاً صحيحاً">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **Observe → policy**، احفظ القرار والجلسة المرتبطة، وحدد شرط الموجب الكاذب. ثم افتح **Admin → enforcement** وعد الأجهزة المتأثرة إلى الإصدار السابق. أنشئ نسخة أضيق في **Policy editor**، اختبرها على نطاق صغير، وقسّمها فقط بعد نجاح العمل الصحيح.

      </Tab>
      <Tab title="CLI">
        عودة نشر Cloud محصورة لوحة التحكم فقط. إيقاف جلسة محلية لا يعطّل السياسات المدارة بواسطة Cloud. إذا كانت لوحة التحكم غير متاحة، التقط حالة الجهاز والنشر واستعد لوحة التحكم بدلاً من إعادة محاولة الإجراء المحجوب بشكل متكرر.

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="يعرض خطأ ref">
    <Tabs>
      <Tab title="لوحة التحكم">
        تنتهي الأخطاء في لوحة التحكم بمرجع قصير، على سبيل المثال `ref 4bf92f35`. يحدد تلك الطلب الواحد، ويمكن للدعم استخدامه لإيجاد ما حدث بالضبط على الخادم. انسخه في التقرير الخاص بك كما يظهر.

        إذا فشلت صفحة كاملة في التحميل، توضح صفحة الخطأ `digest` بدلاً من ذلك. أدرجها.
      </Tab>
      <Tab title="CLI">
        أخطاء `fp` سهلة القراءة تنتهي بـ `ref` نفسه. مع `--json`، يحمل كائن الخطأ `request_id` كاملاً:

        ```bash
        fp --json sessions --since 24h
        ```
      </Tab>
      <Tab title="Daemon">
        عند فشل التحميل، يُسمّي سجل daemon `request_id` و `batch_id`: على Linux، `sudo journalctl -u failproofaid@$USER | grep batch_id`. كل محاولة تحصل على `request_id` خاصة بها؛ `batch_id` يبقى كما هو عبر محاولات إعادة المحاولة، لذلك يربط محاولات دفعة واحدة معاً. أدرج كليهما.
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

عند الاتصال بالدعم، أدرج إصدار CLI والـ harness والبيئة والمعرّف الذي يتعلق بالجلسة أو النشر، أي `ref` أو `request_id` من الخطأ، وإخراج `failproofai config --status` مع إزالة الأسرار.
