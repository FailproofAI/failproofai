<AccordionGroup>
  <Accordion title="لا تظهر جلسات في السحابة">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **الإدارة → المفاتيح** وتأكد من أن مفتاح الجهاز نشط ويحتوي على `events:add`. ثم افتح **مراقبة → الأحداث**، وسّع نطاق الوقت، وامسح المرشحات البيئية والوكيل. إذا كانت هناك أحداث، ابحث عن معرف الجلسة ثم تحقق من **مراقبة → الجلسات** لتجميعها. إذا لم تكن هناك أحداث، شخّص مراقب Failproof من واجهة سطر الأوامر.

        ![تدفق الأحداث الحية مع المرشحات الأساسية الخاصة به وأحداث الوكيل الحديثة الوصول.](/images/dashboard/events-stream-current.png)
      </Tab>
      <Tab title="واجهة سطر الأوامر">
        ```bash
        failproofai config --status
        failproofai flush --wait --timeout 60
        fp list envs
        fp events --since 24h --limit 20
        fp sessions --since 24h --limit 20
        ```

        تأكد من تفعيل الالتقاط والمفتاح المكوّن له `events:add` ومرشح لوحة التحكم يطابق البيئة المُصدَّرة.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="أحداث Python SDK تبقى على القرص">
    <Tabs>
      <Tab title="لوحة التحكم">
        امسح المرشحات في **مراقبة → الأحداث** وابحث عن معرف جلسة SDK الدقيق. إذا لم يظهر شيء، افحص ملف الانتظار ومراقب Failproof على الجهاز المصدر.
      </Tab>
      <Tab title="واجهة سطر الأوامر">
        ```bash
        failproofai config --status
        failproofai flush --wait
        ```

        تأكد من أن عملية الوكيل تعيّن `AGENTEYE_SPOOL_TO_FAILPROOFAI=1` وأن `$FAILPROOFAI_HOME/custom-agents` أو بخلاف ذلك `~/.failproofai/custom-agents` موجود قبل بدء SDK.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="الجهاز لا يستقبل السياسات">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **الإدارة → الإنفاذ**، حدد الجهاز، وقارن إصداراته المُسندة والمُبلَّغ عنها والسابقة. تأكد من أن نطاق النشر يشمل الجهاز ومفتاحه له `policies:pull`. يمكن للالتقاط أن يعمل حتى عندما لا يعمل تسليم السياسة.
      </Tab>
      <Tab title="واجهة سطر الأوامر">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config --status
        ```

        تأكد من تطابق معرف الجهاز والتصنيف مع هدف لوحة التحكم. أعِد الاتصال باستخدام مفتاح قادر على السياسة إذا كان بيانات الاعتماد الحالية توفر فقط الالتقاط في الأحداث.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="يتم حجب إجراء لأن المراقب غير متاح">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **الإدارة → الإنفاذ** وافحص وقت آخر ظهور للجهاز والإصدار المُبلَّغ عنه. إذا كان الجهاز قديم الطراز، عامله كمشكلة محلية في المراقب. لا تضعّف السياسة المنشورة فقط لتجاوز مراقب غير متاح.
      </Tab>
      <Tab title="واجهة سطر الأوامر">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        أعِد تشغيل أو تحديث `failproofaid`؛ أعِد تشغيل التكوين عندما تختلف إصدارات بروتوكول واجهة سطر الأوامر والمراقب. مسار المراقب المكوّن يفشل بقفل بالتصميم.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="سياسة مخصصة لا تُحمَّل">
    <Tabs>
      <Tab title="لوحة التحكم">
        بالنسبة للسياسة المُنشأة على السحابة، افتح **الإدارة → محرر السياسة**، حدد المسودة، واستعرض أخطاء التحقق قبل النشر. بالنسبة للسياسة المحلية، استخدم واجهة سطر الأوامر للتحقق منها، ثم افتح **مراقبة → السياسة** بعد إجراء اختبار لتأكيد وصول القرارات.
      </Tab>
      <Tab title="واجهة سطر الأوامر">
        تأكد من أن اسم الملف ينتهي بـ `policies.js` أو `policies.mjs` أو `policies.ts`، والوحدة تستدعي `customPolicies.add(...)`، والواردات تُحلّل من ملف السياسة.

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="التدقيق لا يرجع النتائج">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **تحليل → التدقيقات**، حدد التشغيل، وتحقق مما إذا كان تحليل النموذج قد تم تشغيله. ثم قارن نطاقه والنافذة مع **مراقبة → الجلسات** وافتح الآثار التمثيلية من تلك المجموعة.

        النتيجة الصفرية ذات معنى فقط عندما يتم تشغيل التحليل بنجاح. إذا تم تخطي التحليل أو فشل، يُنتج التشغيل لا نتائج ويبقي النافذة غير محللة مفتوحة لتشغيل ناجح في المستقبل. إذا تم تعطيل تحليل النموذج، يُنتج التدقيق أيضاً لا نتائج لأن فحص بيانات الاعتماد والمعلومات الشخصية الحتمي يسجل الإحصائيات لكن لا يعود يرفع النتائج.

        ![نموذج التدقيق حيث تحدد البيئة والوكيل والتكرار ونافذة الكنس مجموعة الجلسات.](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="واجهة سطر الأوامر">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        إذا ظل التشغيل في قائمة الانتظار، انتظر سعة وكيل التدقيق أو اطلب من مشغّل النشر فحص أسطول التدقيق. يعيد التدقيق في قائمة الانتظار المحاولة؛ لا يتم تخطيه فوراً.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="التقييمات على الإنترنت لا تُشغَّل تلقائياً">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح جلسة مكتملة وتحقق مما إذا كان التقييم اليدوي يُنجح. السحابة المضيافة حالياً لا تحتوي على تحكم نقطة نهاية المقيِّم في لوحة التحكم؛ يجب على مشغّل الخادم تكوينها.
      </Tab>
      <Tab title="واجهة سطر الأوامر">
        تحقق من المقيِّم نفسه، ثم افحص حالات التقييم الحديثة:

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        على السحابة المستضافة ذاتياً، تأكد من وجود `EVALUATOR_ENDPOINT` على الخادم و`EVALUATOR_TOKEN` يطابق المقيِّم. يتم تعطيل التقييم التلقائي عندما تكون النقطة النهائية غائبة.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="مصادقة واجهة سطر أوامر السحابة تستهدف المنظمة الخاطئة">
    <Tabs>
      <Tab title="لوحة التحكم">
        استخدم محول المنظمة وتأكد من الاختصار والأذونات المتوقعة قبل مقارنة النتائج مع واجهة سطر الأوامر.
      </Tab>
      <Tab title="واجهة سطر الأوامر">
        ```bash
        fp whoami
        fp orgs current
        fp orgs perms
        ```

        في وضع مفتاح API، حدد `fp --org <slug> --api-key <key> ...` أو اضبط `AGENTEYE_ORG`. حالة المنظمة المحفوظة للجلسة البشرية يتم تجاهلها عن قصد لطلبات مفتاح API.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="السياسة تحجب العمل الصحيح">
    <Tabs>
      <Tab title="لوحة التحكم">
        افتح **مراقبة → السياسة**، احفظ القرار والجلسة المرتبطة، وحدد شرط الموجب الخاطئ. ثم افتح **الإدارة → الإنفاذ** وأرجع الأجهزة المتأثرة إلى الإصدار السابق. أنشئ إصدار أضيق في **محرر السياسة**، اختبره على نطاق صغير، وتوسّع فقط بعد نجاح العمل الصحيح.
      </Tab>
      <Tab title="واجهة سطر الأوامر">
        التراجع عن نشر السحابة لا يتعلق إلا بلوحة التحكم. إيقاف جلسة محلية لا يعطّل السياسات المُدارة على السحابة. إذا كانت لوحة التحكم غير متاحة، احفظ حالة الجهاز والنشر واستعِد وصول لوحة التحكم بدلاً من إعادة محاولة الإجراء المحجوب بشكل متكرر.

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

عند التواصل مع الدعم، أرفق إصدار واجهة سطر الأوامر والعتاد والبيئة ومعرف الجلسة أو النشر ذا الصلة وإخراج `failproofai config --status` مع إزالة الأسرار.
