تجمع لوحات المعلومات الاستعلامات المحفوظة في عرض تشغيلي. قم ببناء واحدة حول قرار تتوقع أن يتخذه شخص ما—وليس حول كل مقياس متاح.

لوحات المعلومات هي سطح Cloud. لوحة المعلومات المحلية على `localhost:8020` تغطي نشاط السياسة والمشاريع والجلسات ونتائج التدقيق، لكنها لا تحتوي على استعلامات محفوظة ولا تجانب — لذا فإن الجهاز الذي لم يتصل ليس لديه شيء لبناؤه هنا. انظر [لوحة المعلومات المحلية](/ar/reference/local-dashboard).

## بناء لوحة معلومات

<Tabs>
  <Tab title="Dashboard">
    1. انتقل إلى **Analyze → Queries**، أنشئ أو افتح استعلاماً محفوظاً، والتحقق من نتيجته.
    2. حدد **add to dashboard**، ثم اختر لوحة معلومات موجودة أو أنشئ واحدة تحت **Analyze → Dashboards**.
    3. افتح لوحة المعلومات، ادخل وضع التحرير، رتب التجانب، واحفظ التخطيط.
    4. عد إلى الاستعلام عندما تحتاج إلى تغيير البيانات أو المرشحات خلف تجنب معين.

    ![لوحة معلومات مكونة من استعلامات محفوظة لحجم الأحداث والأخطاء والكمون واستخدام رموز النموذج.](/images/dashboard/dashboard-fleet.png)
  </Tab>
  <Tab title="CLI">
    لا يتم كشف CRUD لوحة المعلومات بواسطة Cloud CLI الحالي. استخدم CLI لكتابة والتحقق من الاستعلام المحفوظ، ثم أضفه إلى لوحة معلومات في واجهة المستخدم.

    ```bash
    fp query schema
    fp query run --sql "select count(*) from analytics.events"
    fp query create "event volume" --sql "select count(*) from analytics.events"
    fp query run "event volume"
    ```

    قم بتشغيل SQL باستخدام `--sql` أولاً: فهو ينفذ ضد نفس مجموعة التحليلات للقراءة فقط دون حفظ أي شيء، لذا ستجد اسم عمود خاطئ قبل أن تفعله تجنب. يقرأ `--sql @file.sql` البيان من ملف بدلاً من ذلك. يسرد `fp query schema` الجداول القابلة للاستعلام وأعمدتها؛ مرر اسم جدول لتضييقه على واحد.

    يتم معالجة الاستعلامات المحفوظة بواسطة **name**، وليس بواسطة id — `fp query run "event volume"` — لأن `fp query list` يخفي المعرف الخام ما لم تمرر `--show-id`. يتم قبول معرف بشكل UUID أيضاً.

    بالنسبة للتجنب المعبر عنه، اربط كل `$1..$N` موضعي باستخدام `--arg`، وهو قابل للتكرار ويربط بالترتيب: `fp query run <name> --arg checkout-agent`.

    يعدّل `--limit` و `--all` حد معاينة الجدول فقط؛ `--json` يعيد دائماً كل صف، مثل `{columns: [{name, type}], rows: [[...]], truncated, elapsed_ms}`.

    | الأمر الفرعي | الإذن |
    | --- | --- |
    | `query list`، `query show`، `query schema` | `queries:read` |
    | `query create`، `query update` | `queries:write` |
    | `query run` | `queries:run` |
    | `query delete` | `queries:delete` |

    كل أمر فرعي يأخذ **name** استعلام يحله بإدراج استعلامات المنظمة أولاً، لذا `query create`، `query update`، `query delete` و `query run <name>` بحاجة إلى `queries:read` بالإضافة إلى الإذن أعلاه. فقط `fp query run --sql` و `fp query schema` لا.

    لا يتم حظر أي من `fp query` في وضع مفتاح API، لذا يمكن إنشء والتحقق من استعلامات لوحة المعلومات من CI.
  </Tab>
</Tabs>

تتضمن مجموعات لوحات المعلومات المفيدة:

- **Models:** الحجم والكمون واستخدام الرموز ومعدل الخطأ ودرجات التقييم.
- **Evaluations:** معدل النجاح واتجاهات الدرجات حسب الوكيل أو البيئة.
- **Tools:** حجم المكالمات ومعدل الفشل والمدة والمكالمات المتكررة.
- **Hooks and policies:** القرارات والرفض ومعدل مطابقة السياسة.
- **Custom workflow metrics:** النتائج من حقول الأحداث والـ SQL الخاصة بك.

ابدأ باستعلام محفوظ والتحقق من نتيجته ثم أضفه كتجنب. حافظ على مرشحات الإنتاج والتطوير صريحة حتى لا يخفي حركة المرور الاختبارية انحدار.

<Warning>
  تجنب hook الذي يعد الصفوف يبلغ عن المقسوم الخاطئ. بالتفاصيل hook الافتراضي، يتم بث كل deny و instruct كزوج `hook_triggered` / `hook_completed`، وكذلك كل allow في وضع observe؛ يتم دمج allows العادي لكل جلسة وحدث وأداة ونسبة السياسة في الدقيقة إلى واحد `hook_completed` يحمل `failproofai_allow_count`. اجمع هذا الحقل بدلاً من عد الصفوف، أو ستبدو أسطول الذي قيّم عشرات الآلاف من المكالمات وكأنه قيّم بضع مئات. انظر [قرارات السياسة](/ar/sessions/policy-decisions) و [Hooks](/ar/sessions/hooks).
</Warning>

<Tip>
  أعط كل لوحة معلومات مالكاً وسؤال استجابة، مثل "هل موثوقية checkout-agent أسوأ من الأسبوع الماضي؟"
</Tip>
