يوجهك هذا البدء السريع لتشغيل جهاز واحد يرسل الجلسات، وتشغيل تدقيق، ونشر سياسة. استخدم المهارة لإعداد Failproof AI، أو اتبع الخطوات اليدوية.

**أي طريق هو طريقك؟** إذا كان الوكيل الخاص بك يعمل في أحد [الأطر](/ar/reference/harnesses) الـ 12 المدعومة — واجهة سطر أوامر للبرمجة، أو بوابة مثل Hermes أو OpenClaw — اتبع الخطوات أدناه؛ تحتاج إلى Node.js 20.9 أو إصدار أحدث. إذا لم يكن لدى وكيلك أي إطار، فقم بتوصيله بـ [Python SDK](/ar/reference/custom-agents) للتتبع والتدقيق، ثم انضم إلى [تشغيل فحص الفشل الأول](/ar/start/first-audit)؛ الفرض على تلك الطريقة يحتاج إلى hook في وقت التشغيل الخاص بك.

      <Step title="اطلب من الوكيل الخاص بك إعداد كل شيء">


        يفحص الوكيل الخاص بك المشروع، ويختار التكامل ذي الصلة، ويقوم بالإعداد، ويتحقق منه. اطلع على [مستودع مهارات FailproofAI](https://github.com/FailproofAI/skills) للحصول على المهارات الفردية وخيارات التثبيت المتقدمة.
      </Step>
    </Steps>

  <Tab title="الإعداد اليدوي">
    ## التثبيت

<Steps>
  <Step title="تثبيت وربط Failproof AI">
    ```bash
    npm install -g failproofai
    failproofai config
    ```

    هذا الأمر الواحد هو كل الإعداد: فهو يثبت خيط المراقب المحلي (الجذر مرة واحدة)، ويوصل hooks في كل واجهة سطر أوامر وكيل يجدها، ويربط هذا الجهاز بـ Cloud.

    في **الاتصال بـ cloud**، يبدأ الإعداد بتسجيل دخولك إلى FailproofAI Cloud على الفور (اضغط على Tab للخيارات الأخرى: لصق مفتاح API، أو استخدام المصدر المفتوح). يفتح رابطًا في متصفحك (عبر SSH، أو على جهاز بدون عرض، يطبع الرابط حتى تتمكن من فتحه على أي جهاز). قم بالتسجيل أو تسجيل الدخول، وأكد المؤسسة — أو أنشئ واحدة هناك — وانقر على **Authorize**. يتم تعيين اسم المفتاح والأذونات لك. لا تحتاج إلى حساب مسبقًا.

    ينتبه المحطة الطرفية بنفسها ويعرض من وافق عليها وللمؤسسة التي وافقت عليها. أكد الوكلاء الذين يتم تتبعهم، وينتهي الإعداد. يتم إنشء مفتاح الجهاز فقط في تلك النقطة، بعد تثبيت خيط المراقب، لذا فإن التشغيل الذي تهجره لا يترك مفتاحًا؛ يظهر ضمن **Administration → Keys** موضوع **cli login**، حيث يمكنك إلغاء صلاحيته.

    <Accordion title="بدون متصفح أو محطة طرفية في متناول اليد؟ استخدم مفتاح (CI، حاويات، سكريبتات التوفير)">
      في [لوحة معلومات Failproof AI](https://app.befailproof.ai)، انتقل إلى **Administration → Keys** وأنشئ مفتاحًا بـ `events:add` و `policies:pull`. إذا كنت تخطط لاستخدام [Jev من خلال FailproofAI Cloud](/ar/reference/jev-cloud)، اختر مسبقة **machine**، والتي تمنح أيضًا `jev:evaluate`. انسخ السر لمرة واحدة واقرأه إلى shell على الجهاز المستهدف — `read -s` يأخذه في موجه لا يعكس:

      ```bash
      read -rs FAILPROOFAI_KEY && export FAILPROOFAI_KEY
      FAILPROOFAI_CLOUD_TOKEN="$FAILPROOFAI_KEY" failproofai config
      ```

      يحافظ على تمرير المفتاح عبر البيئة بدلاً من `--token` على عدم ظهوره في `ps`، حيث يمكن لكل مستخدم على الجهاز قراءة حجج الأمر. لا يبقيه بعيدًا عن محفوظات shell — قراءته بـ `read -s` هو ما يفعل ذلك. في CI، قم بحقنه كسر مقنع وأبقِ تتبع shell (`set -x`) مطفأ، وإلا فسيطبعها التتبع. في تشغيل تفاعلي، يمكنك أيضًا اختيار **Paste an API key** في **Connect to cloud** بدلاً من ذلك.
    </Accordion>

    يتم إرسال النصوص المنقولة للجلسات بشكل افتراضي. أضف `--no-transcripts` للإبلاغ عن نشاط الـ hook وقرارات السياسة بدون محتوى النص.

    <Warning>
      لا تصل إلى `failproofai config --connect <url>` هنا. تقوم هذه العلامة بتسجيل جهاز **بالفعل** تم إعداده وتعود على الفور — لا daemon، لا hooks — لذا فإن الجهاز سيظهر في Cloud بينما لا يتم جمع وفرض أي شيء.
    </Warning>

    إذا كان لدى هذا الجهاز سجل وكيل سابق، فقم بمعاينة وتجميع آخر سبعة أيام، ثم انتظر انتهاء التسليم. تخطي هذه الخطوة على جهاز جديد.

    ```bash
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    failproofai flush --wait
    ```

    افتح **Sessions** في Failproof AI واختر جلسة مستوردة.
  </Step>
  <Step title="ربط Failproof AI بإطار عمل">
    قام الخطوة السابقة بالفعل بتوصيل كل واجهة سطر أوامر وكيل اكتشفها. أعد تشغيلها لإطار واحد بشكل صريح عند الحاجة، أو لإضافة إطار تم تثبيته لاحقًا. كل واحد من الـ 12 هو قيمة `--cli` صحيحة — `claude`، `codex`، `copilot`، `cursor`، `opencode`، `pi`، `hermes`، `openclaw`، `factory`، `devin`، `antigravity`، `goose`.

    ```bash
    failproofai policies --install --cli claude --scope user     # a coding CLI
    failproofai policies --install --cli hermes --scope user     # a Slack/Telegram gateway
    ```

    تم التحقق من حظر استدعاء أداة قبل تشغيلها على الـ 12 جميعها. يتم التحقق من بوابات نهاية الدور على 8 — راجع [القدرة الإنفاذية](/ar/reference/harnesses#enforcement-capability) لمصفوفة لكل إطار.
  </Step>
  <Step title="اختر ما تفرضه">
    يؤدي توصيل hooks إلى عدم تفعيل أي سياسة. يختار الإعداد بعد الحذر بلا أحد — هذا القرار لك — لذا خذ حزمة:

    ```bash
    failproofai policies add FailproofAI/policies
    ```

    يتم جلب الحزمة من إصدار GitHub الخاص بها، والتحقق من المجموع الاختباري، والتثبيت بـ tag بالضبط الذي تم حله. يحمل 39 سياسة ويقوم بتشغيل 10 من بيانها الوصفية يضع علامة عليها كآمنة للتفعيل بدون حضور. استخدمها لرؤية قرارات السياسة المحلية وتجربة الفرض قبل أن يقوم Failproof AI بتدقيق جلساتك وكتابة السياسات للوكلاء الخاص بك.

    اقرأ أي حزمة قبل أخذها باستخدام `failproofai policies show <owner>/<repo>`، واطلع على [حزم السياسات](/ar/policies/packs) لأخذ جزء واحد فقط من واحدة.

    حتى يعمل هذا، الشيء الوحيد الذي ينفذه هو `block-failproofai-commands` — الحارس الذي يعمل دائمًا والذي يوقف وكيل إيقاف تشغيل Failproof AI. يسرد `failproofai policies` ما هو قيد التشغيل.
  </Step>
  <Step title="تدقيق السلوك">
    اتبع [تشغيل فحص الفشل الأول](/ar/start/first-audit). استخدم هدفًا ملموسًا مثل "ابحث عن جلسات حاول فيها الوكيل أداة فاشلة مرة أخرى دون تغيير نهجه."
  </Step>
  <Step title="منع الفشل">
    اتبع [منع أول فشل لك باستخدام سياسة](/ar/start/first-policy). ابدأ بوضع الملاحظة، وافحص المطابقات، ثم فرض النسخة المراجعة.
  </Step>
</Steps>

<Check>
  قم بتشغيل `failproofai config --status`. يرسل الإعداد الصحي اتصال السحابة وحالة daemon وما إذا كان الفرض موقوفًا.
</Check>

## إعداد Jev

استخدم [Jev](/ar/start/use-jev) للتصرف الجلسات المنتهية مقابل سؤال بإجابات معروفة، أو لمراجعة استدعاءات الأدوات في السياق قبل تشغيلها. الصفحة **Use Jev** بها كلا مسارات الإعداد.
