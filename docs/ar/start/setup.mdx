## الفرض المحلي

شغّل `failproofai config` بدون مفتاح، ثم خذ حزمة باستخدام `failproofai policies add FailproofAI/policies`. في الطرفية، اختر **Not now — stay local** عندما يطلب الإعداد الاتصال بـ Cloud؛ بدون طرفية وبدون `FAILPROOFAI_CLOUD_TOKEN`، يبقى محليًا من تلقاء نفسه. يفرض الخيط الخلفي والخطافات على الجهاز، ولا يتم إرسال بيانات الجلسة إلى Cloud. للاتصال لاحقًا، اتبع الخطوات أدناه.

## مسار الإنتاج الموصى به

1. قم بتوصيل جهاز غير إنتاجي مع تمكين التقاط النصوص.
2. تحقق من الجلسات والتقييمات في Cloud.
3. أنشئ تدقيقًا لحالة فشل معروفة.
4. انشر السياسة الأولى في وضع المراقبة.
5. قم بالتوسع إلى الإنتاج بعد مراجعة المطابقات والإيجابيات الكاذبة.

## توصيل جهاز بـ Cloud

<Tabs>
  <Tab title="لوحة التحكم">
    1. انتقل إلى **Administration → Keys** وأنشئ مفتاحًا باستخدام `events:add` و `policies:pull`.
    2. انسخ السر لمرة واحدة إلى الجهاز الهدف.
    3. بعد تشغيل أمر اتصال CLI، انتقل إلى **Admin → enforcement** وأكد ظهور الجهاز.
    4. انتقل إلى **Observe → Events** وأكد وصول حدثه الأول.

    يعرض درج المفتاح المنحتين اللذين يحتاجهما جهاز متصل: استيعاب الأحداث وتوصيل السياسة.

    ![درج مفتاح API الجديد المستخدم لمنح أذونات استيعاب الأحداث وتوصيل السياسة.](/images/dashboard/key-create.png)

    بعد الاتصال، يجب أن يظهر الجهاز في الفرض مع حالة السياسة المرغوبة وحالة النشر.

    ![أسطول الفرض مع جهاز مسجل موسع لإظهار حالة السياسة المرغوبة وحالة النشر.](/images/dashboard/enforcement-fleet.png)

    يؤكد الحدث الأول الذي يصل على أن الخيط الخلفي يمكنه تسليم البيانات إلى Cloud، بشكل مستقل عن نشر السياسة.

    ![دفق الأحداث المباشر يعرض أحداث الوكيل والنموذج والأداة الأخيرة.](/images/dashboard/events-stream-current.png)

    تابع فقط بعد أن يكون الجهاز وحدثه الأول مرئيين.
  </Tab>
  <Tab title="CLI">
    اقرأ السر لمرة واحدة في الشل. `read -s` يأخذه في موجه لا يتم صداه، لذلك لا يظهر أبدًا في أمر أو في سجل الشل:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    ثم قم بإعداد الجهاز واختر سياساته وسمّه:

    ```bash
    failproofai config

    failproofai policies add FailproofAI/policies
    failproofai config --machine-label checkout-runner-01
    failproofai config --status
    ```

    `failproofai config` يقوم بالإعداد بالكامل — الخيط الخلفي والخطافات لكل CLI وكيل يجده والاتصال بـ Cloud — ثم لا يختار أي سياسات، وهو ما الأمر الثاني موجود له.

    يأتي التسمية **بعد** الاتصال وليس أثناء: `failproofai config --machine-label <name>` يعيد تسمية جهاز متصل بالفعل، وعلى جهاز غير متصل فإنه لا يفعل شيئًا سوى قول ذلك.

    أضف `--no-transcripts` عندما يجب أن تبقى محتويات النصوص محلية.

    في CI، قم بتعيين `FAILPROOFAI_CLOUD_TOKEN` من مخزن الأسرار بدلاً من `read -s`، واحتفظ بتتبع الشل (`set -x`) إيقاف، أو التتبع يطبع المفتاح.

    <Warning>
      على جهاز **بالفعل** تم إعداده، `failproofai config --connect <url>` يسجله وشيء آخر فقط. لا تستخدم هذا النموذج للتثبيت الأول: يعود قبل وجود الخيط الخلفي أو أي خطاف، تاركًا جهازًا يظهر في Cloud لكن لا يجمع أو يفرض شيئًا.
    </Warning>
  </Tab>
</Tabs>

يتحقق الاتصال بـ Cloud من استيعاب الأحداث وتوصيل السياسة بشكل مستقل. قد يكون المفتاح صحيحًا إذن لكن ينقصه إذن واحد مطلوب. استخدم `failproofai config --status` لمعرفة القدرة المكونة.

<Info>
  يكتب إعداد Cloud بيانات اعتماد محلية فقط بعد نجاح القدرة ذات الصلة. التحقق الفاشل لا يترك جهازًا يبدو متصلاً عندما لا يكون كذلك.
</Info>
