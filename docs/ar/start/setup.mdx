يمكن لـ Failproof AI أن يعمل بالكامل على جهاز واحد أو الاتصال بـ Cloud للجلسات المشتركة وإدارة السياسات.

## محلي، بدون حساب

```bash
npm install -g failproofai
failproofai config
failproofai policies add FailproofAI/policies
failproofai
```

يقوم هذا بتثبيت الخدمة، وتوصيل الوكلاء المدعومين، وإضافة مجموعة سياسات، وفتح لوحة التحكم على `http://localhost:8020`.

قم بتشغيل `failproofai audit` لمسح سجل الوكيل الموجود بالفعل على الجهاز.

## توصيل Failproof AI Cloud

أنشئ مفتاح جهاز في Cloud، ثم قم بتشغيل:

```bash
failproofai config --token <machine-key>
failproofai config --machine-label checkout-runner-01
failproofai policies add FailproofAI/policies
failproofai config --status
```

أو قم بتصدير `FAILPROOFAI_CLOUD_TOKEN=<machine-key>` وقم بتشغيل `failproofai config` العادي. فضّل متغير البيئة على الأجهزة المشتركة وفي CI بحيث لا تصل المفتاح إلى سجل shell أو قوائم العمليات.

يستخدم Cloud اتصالاً واحدًا لوظيفتين منفصلتين:

- سحب السياسات المعينة لهذا الجهاز.
- إرسال قرارات السياسة ونصوص الجلسات.

لإرسال القرارات فقط، قم بالاتصال أولاً، ثم عيّن `collector.sessions` إلى `false` في `~/.failproofai/config.json`. لا تعتمد على `--no-transcripts`: مسار الإعداد الحالي يحلل العلم لكنه لا يطبقه. انظر [الأحداث والإعدادات](/ar/reference/events-and-configuration#machine-configuration).

<Note>
  `--machine-label` يعيد تسمية جهاز متصل بالفعل. قم بتشغيله بعد أمر الإعداد، وليس كجزء من الاتصال الأول.
</Note>

## إعداد غير مراقب

`failproofai config` لا يتطلب علم خاص غير تفاعلي. في CI أو حاوية، فإنه يطبق الإعداد المطلوب دون طلب تأكيد.

```bash
export FAILPROOFAI_CLOUD_TOKEN="<key>"
failproofai config
```

هناك حاجة لصلاحية المسؤول مرة واحدة لتثبيت خدمة الخلفية. لا يفتح الإعداد أبدًا موجه كلمة مرور تفاعلي `sudo`: فإما ينجح بدونها أو يطبع الأوامر التي يجب على المسؤول تشغيلها.
