A finding is the audit's evidence-backed statement about a failure. An insight — an issue, in the Cloud CLI and API — is the durable workflow for responding to it.

## Triage and assign the work

<Tabs>
  <Tab title="Dashboard">
    1. Open **analyse → checks → audits**, open the audit, choose a completed run, and select a finding to inspect its analysis, recommendation, sessions, and evidence queries.
    2. Acknowledge, assign, dismiss, mute, resolve, or reopen the finding after checking its evidence.
    3. Go to **analyse → insights** and filter the durable inbox by status (**open**, **acknowledged**, **resolved**), severity, found-by, or owner.
    4. Open the insight to assign it, add comments or subscribers, and resolve it after the fix is verified.

    Start with the finding summary. Confirm that the failure description, recommended response, severity, and ranking agree with the sessions you expected the audit to examine.

    ![An audit finding with severity, occurrence count, root-cause analysis, recommended action, ranking factors, and evidence.](/images/dashboard/audit-finding.png)

    Next, open an affected session rather than deciding from the summary alone. The linked trace should show the exact event and payload that support the finding.

    ![A session linked from an audit finding, opened at the relevant error with its event metadata and raw payload.](/images/dashboard/audit-linked-session.png)

    After verifying the evidence, use insights to give the response an owner and track it independently of future audit runs.

    ![The insights inbox showing firing, acknowledged, and resolved work with severity and ownership.](/images/dashboard/incidents.png)

    Open the insight to record investigation notes, notify subscribers, and preserve the response history. Resolve it only after the remediation is deployed and verified.

    ![An insight detail view with its source, breach evidence, assignees, subscribers, timeline, and comments.](/images/dashboard/incident-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits findings --audit checkout-reliability --status open
    fp audits finding <finding-id>
    fp audits ack <finding-id> --reason "owner assigned"
    fp audits assign <finding-id> --to engineer@example.com

    fp issues list
    fp issues show <issue-id>
    fp issues assign <issue-id> --assignee engineer@example.com
    fp issues comment-add <issue-id> --body "policy is in observe mode"
    fp issues resolve <issue-id> --yes
    fp issues close <issue-id> --yes
    fp issues archive <issue-id>
    ```

    Use `fp issues subscribe <issue-id>`, `fp issues unsubscribe <issue-id>`, and `fp issues subscribers <issue-id>` to manage watchers.

    See the [Cloud CLI audit and issue reference](/reference/cloud-cli#audits) for audit findings and [`fp issues`](/reference/cloud-cli#issues) for issue management.
  </Tab>
</Tabs>

## Review a finding

Confirm that it contains:

- A stable failure mode, not only a one-off title
- Severity and operational impact
- Affected session IDs or supporting queries
- Enough context to reproduce the behavior
- A proposed response that matches the evidence

## Use an insight to manage the response

Create or link an insight when the finding needs assignment, discussion, status changes, comments, or subscribers. Insights can also come from alerts and from failures reported by hand (**report a failure** on the inbox).

Resolve the insight when remediation is deployed and verified. Resolve the finding when the failure mode has been addressed for the audit population. Those moments may differ.

## End an insight: resolve, close, or archive

An insight ends once, and how you end it decides what happens the next time the audit
sees the same pattern.

| Action | Means | If the pattern comes back |
| --- | --- | --- |
| **Resolve** | You fixed it. | The insight **reopens**, so you find out the fix did not hold. |
| **Close** | You are done with it: won't fix, not a problem, or no longer relevant. | It **stays closed**. |
| **Archive** | Take it off the board. Says nothing about how it ended. | A live insight returns to the board automatically. |

Resolve and close are both final and neither can overwrite the other, so an insight
someone resolved keeps that record. Archiving is separate from both: you can archive
an insight in any state, and it keeps whatever state it ended in. If an archived insight
is still live and the problem recurs, it comes back to the board on its own — archive
hides history, it cannot hide an active problem.

Closing an insight that came from an audit also dismisses the finding behind it. It
does not silence that pattern in your other audits; for that, **mute this pattern** or
**dismiss** it.

## Start fresh after changing your agents

When you ship a round of changes to your agents, the insights an audit already raised
describe the behavior you just replaced. Clearing ends them in one step: they are closed
and archived, and the audit findings behind them are resolved. Clearing covers one audit
at a time.

<Tabs>
  <Tab title="Dashboard">
    1. Go to **analyse → checks → audits** and open the audit.
    2. Select **more ▾**, then **clear its open failures…**. The confirmation shows how many insights and findings it covers before you commit to it.
    3. Confirm. Nothing is deleted: cleared insights stay readable under the inbox's archived view.
  </Tab>
  <Tab title="CLI">
    ```bash
    fp issues clear --audit <audit-id> --dry-run
    fp issues clear --audit <audit-id> --yes
    ```

    `--dry-run` reports what would change without changing it. The command still
    offers `--all-audits` and `--everything`, but Failproof AI Cloud accepts only a single
    audit's scope and answers those two with `422`.
  </Tab>
</Tabs>

**Clearing suppresses nothing.** A pattern your changes genuinely fixed stays gone. A
pattern that survived them opens a **new** insight on the next audit run, so a fresh start
cannot quietly hide a problem you still have; the cleared ones stay closed. When you do
want a pattern silenced for good, mute or dismiss it instead.

Clearing needs permission to both close issues (`issues:close`) and write audits
(`audits:write`), because it resolves the findings as well as closing the insights.

## Turn an insight into a policy draft

<Tabs>
  <Tab title="Dashboard">
    1. Open the insight and verify its finding, cited sessions, root cause, and recommendation.
    2. Read the **prevent it with a policy** card: it says whether a policy can stop this failure (**a policy can stop this**) and how, or that **no policy fits this one** — the behavior may need an alert, a workflow change, or a human response instead. The check can be wrong, so the next step stays open either way.
    3. Select **prevent this →**. It opens **fix → policies → new policy** with a draft from the insight: review the rule, test it on past calls, and turn it on — **observing first** until its decisions under **fix → activity** separate unsafe actions from valid ones. See [Write a policy](/policies/editor).

    The insight's title, finding, root cause, and recommendation help compose the draft. Nothing is published from the insight page.
  </Tab>
  <Tab title="CLI">
    Use the CLI to inspect the evidence before opening the insight in the dashboard:

    ```bash
    fp issues show <issue-id>
    fp audits finding <finding-id>
    fp events --session-id <session-id> --full --all
    ```

    Policy candidacy, Cloud publication, and fleet deployment are dashboard workflows. Use `failproofai policies --install --custom <file>` when you want to validate equivalent policy source locally first.
  </Tab>
</Tabs>

## Catch it in every new session

An insight an audit raised can also become an evaluation, so every new session is scored for the same failure. On the insight, the **catch it every session** card's **turn into eval** drafts the rule from what the audit saw. Pick how it checks (**code**, **decision model**, or **llm as judge**), test it on the sessions the audit cited plus recent ones, then select **turn on only**, or **turn on and write policy →** to go straight on to a policy. See [Write an evaluation](/evaluations/write).
