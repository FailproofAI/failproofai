FailproofAI keeps two kinds of configuration, and they answer different questions:

| File | Question it answers | Who writes it |
|---|---|---|
| `policies-config.json` | **Which policies run, and how?** | You, the dashboard, or `failproofai policy add` |
| Each agent CLI's own settings file | **When does FailproofAI get called at all?** | `failproofai config` / `policies --install` |

You edit the first one freely. The second is managed for you — see [Supported
agents](/agent-support) for what gets written where.

---

## The three scopes

Policy configuration is loaded from three places and merged, in priority order:

| Scope | Path | Purpose |
|---|---|---|
| **project** | `.failproofai/policies-config.json` | Per-repo settings, committed to version control |
| **local** | `.failproofai/policies-config.local.json` | Personal per-repo overrides, gitignored |
| **global** | `~/.failproofai/policies-config.json` | Your defaults across every project |

All three that exist for the current working directory are read on every hook event.
Changes take effect immediately — nothing to restart.

### Merge rules

**`enabledPolicies` — deduplicated union.** A policy enabled at any scope is on.

```text
project:  ["block-sudo"]
local:    ["block-rm-rf"]
global:   ["block-sudo", "sanitize-api-keys"]

resolved: ["block-sudo", "block-rm-rf", "sanitize-api-keys"]
```

**`policyParams` — first scope that defines a policy wins, entirely.** There is no deep
merge inside one policy's parameter block, which keeps the resolved value something you
can predict by reading one file rather than three.

```text
project:  block-sudo → { allowPatterns: ["sudo apt-get update"] }
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo apt-get update"] }     ← project wins outright
```

```text
project:  (no block-sudo entry)
local:    (no block-sudo entry)
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo systemctl status"] }   ← falls through to global
```

**`customPoliciesPaths` / `customPoliciesPaths` — first scope that defines either form wins.**

**`disabledCustomPolicies` — union across all scopes.** The dashboard writes a
source-qualified id here when you switch off an individual policy from a custom or
convention file. Policies not listed stay enabled; the id includes its source file, so
same-named policies in different files are controlled independently.

**`llm` — first scope that defines it wins.**

## File format

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "sanitize-jwt",
    "block-env-files",
    "block-read-outside-cwd"
  ],
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release", "prod"]
    },
    "block-rm-rf": {
      "allowPaths": ["/tmp"]
    },
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company"]
    },
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo API key" }
      ]
    },
    "warn-large-file-write": { "thresholdKb": 512 }
  },
  "customPoliciesPaths": ["/home/alice/myproject/my-policies.js"]
}
```

## Field reference

### `enabledPolicies`

`string[]` — the policy names to enable. Names must match exactly what `failproofai
policies` prints. See [Built-in policies](/built-in-policies) for the catalogue.

A policy not listed here is inactive, even if it has an entry in `policyParams`.

### `policyParams`

`Record<string, Record<string, unknown>>` — per-policy parameter overrides, keyed by policy
name. Each policy documents its own parameters.

Omit a parameter and the policy's built-in default applies. Unknown keys inside a
policy's block are ignored at evaluation time and flagged as warnings when you run
`failproofai policies` — so a typo surfaces when you look, not never.

#### `hint` — accepted by every policy

`string` — appended to the reason whenever a policy denies or instructs. It is the
zero-code way to make a generic rule speak your team's language:

```json
{
  "policyParams": {
    "block-force-push": { "hint": "Branch off and open a PR instead." },
    "block-sudo": {
      "allowPatterns": ["sudo apt-get"],
      "hint": "Use apt-get directly, without sudo."
    },
    "custom/my-policy": { "hint": "Ask the user for approval first." }
  }
}
```

The agent then reads *"Force-pushing is blocked. Branch off and open a PR instead."*

Works on built-in, custom (`custom/…`), project-convention (`.failproofai-project/…`), and
user-convention (`.failproofai-user/…`) policies. Non-string and empty values are ignored.

### `customPoliciesPaths`

`string[]` — absolute paths to your own policy files, loaded in order. Set for you by
`failproofai policies --install --custom <path>` (repeat the flag for several files). The
older single-value `customPoliciesPaths` still works.

Files are loaded fresh on every hook event — no caching, so editing a policy takes effect
on the next tool call.

### `llm`

`object`, optional — connection details for policies that make model calls. Not needed for
most setups.

```json
{ "llm": { "model": "claude-sonnet-4-6", "apiKey": "sk-ant-..." } }
```

## Convention policies need no configuration at all

Alongside the explicit paths above, FailproofAI discovers policy files by location:

| Level | Directory | Shared how |
|---|---|---|
| Project | `.failproofai/policies/` | Committed to git — the whole team gets it |
| User | `~/.failproofai/policies/` | Personal, applies to every project |

- **Matching:** only files named `*policies.{js,mjs,ts}` are loaded. Everything else in the
  directory is ignored.
- **Union, not first-wins:** both directories are scanned and all matching files load.
- **No config entry needed.** Drop the file in; it is picked up on the next hook event.

<Note>
  Put your own files directly in `~/.failproofai/policies/`. The `cloud-policies/` folder
  beside them holds policies your organization deployed to this machine — discovery does
  not descend into subdirectories, so the two can never collide.
</Note>

## Machine settings

Policy configuration is about rules. A second file — `~/.failproofai/config.json` — holds
settings about *this machine*: whether the daemon is configured, what the collector sends,
extra session-capture paths, telemetry, and the audit schedule.

You rarely edit it by hand; `failproofai config`, `failproofai harness`, and the connect
flow write it. Two blocks are worth knowing:

```json
{
  "audit": { "auto": true, "interval_days": 7 },
  "collector": { "sessions": true, "hooks": true, "environment": "production" }
}
```

| Key | Meaning |
|---|---|
| `audit.auto` | Run the [audit](/audit) on a schedule. Off unless you set it, because it reads the contents of every transcript on the machine. |
| `audit.interval_days` | Days between scans. Clamped to 1–90; anything invalid falls back to 7. |
| `collector.sessions` | Ship session transcripts to the cloud. Set by `--no-transcripts` at connect time. |
| `collector.hooks` | Ship policy decisions to the cloud. |
| `collector.environment` | The environment label stamped on everything this machine reports. |

## Upgrades keep your configuration

A new version may organize `~/.failproofai/` differently. When it does, the first command
after the upgrade migrates the directory and **carries your configuration across**:

| Kept | Rebuilt |
|---|---|
| Your policy selection and parameters | The audit cache |
| Your machine settings, including extra capture paths | Cloud-managed deployments — re-fetched and digest-verified on the next poll |
| Your cloud connection | Daemon scratch state |
| Your own policy files, and the helpers they import | |
| The decision log, and anything not yet delivered | |

Keys written by a *newer* version are preserved rather than dropped by an older reader, so
moving between versions does not silently discard settings in either direction. You do not
need to re-run setup: a migrated machine enforces exactly as it did before.

See [`failproofai update`](/cli/update) and [`failproofai migrate`](/cli/migrate).

## Example: a team standard, committed

`.failproofai/policies-config.json`, checked in:

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "block-env-files"
  ],
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "release", "hotfix"],
      "hint": "Open a PR from a feature branch."
    }
  }
}
```

Each developer can add `.failproofai/policies-config.local.json` (gitignored) for personal
overrides without touching anyone else's setup.

Running this across many machines? [Deploy it from the cloud](/cloud/policy-editor)
instead and skip the git round-trip entirely.
