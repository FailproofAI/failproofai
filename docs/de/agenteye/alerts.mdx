Erfahren Sie sofort, wenn eine Grenze überschritten wird – über den Kanal, den Ihr Team bereits nutzt, statt es von einem Kunden zu hören. Legen Sie eine Regel einmal fest, und Failproof AI Observability prüft sie nach einem Zeitplan und benachrichtigt Sie per E-Mail, Slack, Webhook oder direkt im Dashboard.

![Die Alerts-Seite: ein Raster von Alert-Regel-Karten, die jeweils den Auslöser, das Auswertungsfenster, die Kanäle und ein Info-, Warn- oder Kritisch-Schweregrad-Badge anzeigen](/agenteye/images/alerts.png)
*Alle Alert-Regeln auf einen Blick: was sie beobachten, wie oft, wohin sie benachrichtigen und wie dringend.*

## Erfahren Sie von Problemen, bevor Ihre Nutzer es tun

Hören Sie auf, ein Dashboard zu aktualisieren und auf eine Regression zu hoffen. Richten Sie einen Alert immer dann ein, wenn es ein Signal gibt, über das Sie auch dann informiert sein möchten, wenn niemand hinschaut – und lassen Sie es dort ankommen, wo Sie ohnehin schon sind:

- **E-Mail**, an alle, die es wissen sollten.
- **Slack**, eine umfangreiche Nachricht mit einer Schaltfläche, die direkt zum Vorfall führt.
- **Webhook**, ein JSON-POST für PagerDuty, Opsgenie oder Ihren eigenen Endpunkt, mit einer optionalen Signatur, damit der Empfänger ihn verifizieren kann.
- **Im Dashboard**, bewusst unauffällig, für den Fall, dass Sie eine Regel einstellen und noch niemanden benachrichtigen möchten.

Kombinieren Sie beliebige dieser Optionen für eine einzelne Regel, und der Schweregrad (Info, Warnung oder Kritisch) wird mitgeliefert, damit dringende Alerts auch dringend aussehen.

## Regel in einem Formular erstellen, nicht in JSON

Sie beschreiben in einem Formular, was „fehlerhaft" bedeutet, und Failproof AI Observability erstellt die zugrunde liegende Regel für Sie. Die JSON-Spezifikation ist lediglich das, was das Formular intern erzeugt – Sie können sie lesen, um eine Regel zu verstehen, aber Sie müssen sie kaum eintippen.

![Das Formular für neue Alerts: Name und Beschreibung, ein Aktivierungs-Toggle und eine Trigger-Auswahl mit Metrik-Schwellenwert, benutzerdefiniertem SQL, Auswertungsscore, zusammengesetzter Auswertung und ereignisbezogenen Bedingungen](/agenteye/images/alert-new.png)
*Wählen Sie einen Trigger, und das Formular zeigt die passenden Felder an; Speichern schreibt die Regel.*

Der Standardweg ist schnell: Benennen Sie die Regel, wählen Sie einen **Trigger** (was beobachtet werden soll), legen Sie **Schwellenwert und Fenster** fest (wie stark, über welchen Zeitraum), fügen Sie mindestens einen **Kanal** hinzu, klicken Sie auf **Speichern** und dann auf **Testen**, um eine synthetische Benachrichtigung auszulösen und zu bestätigen, dass jedes Ziel korrekt konfiguriert ist. Im Hintergrund entsteht dabei eine kleine Spezifikation wie:

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

Sie sind nicht auf eine Art von Signal beschränkt. Wählen Sie den Trigger, der zu Ihrer Vorstellung des Fehlers passt:

| Trigger | Löst aus, wenn |
|---|---|
| **Metrik-Schwellenwert** | eine vordefinierte Metrik (Fehlerrate, p95- oder p99-Latenz, Ereignis- oder Fehlerzähler, Token-Verbrauch) innerhalb eines Zeitfensters Ihre Grenze überschreitet |
| **Benutzerdefiniertes SQL** | Ihre eigene schreibgeschützte Abfrage eine Zeile zurückgibt oder ein berechneter Wert einen Schwellenwert überschreitet |
| **Auswertungsscore** | der Durchschnitt eines Evaluator-Scores (z. B. Halluzination) einen Schwellenwert überschreitet |
| **Zusammengesetzte Auswertung** | mehrere Score-Prüfungen mit Any-, All- oder Mindestens-N-Logik kombiniert werden, um eine Regression zu erkennen, die sich nur über mehrere Scores zeigt |
| **Pro Ereignis** | ein einzelnes passendes Ereignis eintrifft: ein bestimmter Agent, ein bestimmter Fehlertyp oder ein Nachrichten-Substring |

Sie sehen sich bereits einen Fehler auf der [Fehler-Seite](/de/agenteye/error-tracking) an? Jede Zeile dort hat eine Schaltfläche **+ Alert**, die dieses Formular vorausgefüllt öffnet, um genau diesen Fehler künftig abzufangen – der Vorfall, den Sie gerade triagiert haben, wird so zum nächsten, der Sie benachrichtigt.

**Wo Sie es finden:** Alerts befinden sich unter `/<org-slug>/alerts`. Für das Erstellen, Bearbeiten, Löschen und Testen von Regeln ist **`alerts:write`** erforderlich; `alerts:read` reicht zum Anzeigen. Die Empfängerauswahl listet die Mitglieder Ihrer Organisation namentlich auf, sodass Sie eine Person benachrichtigen können, ohne das Formular zu verlassen.

## Nur benachrichtigen, wenn es wirklich ernst ist

Eine einzelne fehlerhafte Messung sollte Sie nicht aufwecken. Der **M von N**-Rauschfilter steuert, wie viele der letzten Prüfungen fehlschlagen müssen, bevor der Alert tatsächlich ausgelöst wird. Stellen Sie ihn auf **3 von 5** ein, und die Regel löst nur aus, wenn drei der letzten fünf Prüfungen verletzt wurden – ein unzuverlässiges Signal gibt so keine falschen Alarme mehr. Belassen Sie es beim Standardwert **1 von 1**, um beim ersten Verstoß auszulösen. Sie wählen auch, wie oft die Regel ausgeführt wird, aus Voreinstellungen von 1m, 5m, 15m und 1h, abgestimmt darauf, wie schnell sich das Signal tatsächlich verändert.

## Was passiert, wenn ein Alert ausgelöst wird

Ein Verstoß öffnet einen **Incident** und benachrichtigt Ihre Kanäle einmalig. Von dort aus bestätigt Ihr Team ihn, weist einen Verantwortlichen zu, diskutiert ihn und löst ihn auf – alles in einem übersichtlichen, nachvollziehbaren Protokoll. Dieser Triage-Workflow hat seinen eigenen Bereich: siehe [Incidents](/de/agenteye/incidents).
