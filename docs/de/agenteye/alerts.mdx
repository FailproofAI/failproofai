Erfahren Sie sofort, wenn eine Grenze überschritten wird – über den Kanal, den Ihr Team bereits nutzt, statt es erst von einem Kunden zu hören. Legen Sie eine Regel einmalig fest, und Failproof AI Observability prüft sie nach einem Zeitplan und benachrichtigt Sie per E-Mail, Slack, Webhook oder direkt im Dashboard.

![Die Benachrichtigungsseite: ein Raster aus Regelkarten, jede mit Auslöser, Auswertungszeitraum, Kanälen und einem Schweregrad-Badge (info, warning oder critical)](/agenteye/images/alerts.png)
*Alle Benachrichtigungsregeln auf einen Blick: was überwacht wird, wie oft, wohin gemeldet wird und wie dringend.*

## Erfahren Sie von Problemen, bevor Ihre Nutzer es tun

Hören Sie auf, Dashboards zu aktualisieren in der Hoffnung, eine Regression zu entdecken. Richten Sie eine Benachrichtigung ein, wenn es ein Signal gibt, über das Sie auch dann informiert werden möchten, wenn niemand hinschaut – und lassen Sie es dort ankommen, wo Sie sowieso sind:

- **E-Mail**, an alle, die es wissen sollten.
- **Slack**, als ansprechende Nachricht mit einem Button, der direkt zum Incident führt.
- **Webhook**, ein JSON-POST für PagerDuty, Opsgenie oder Ihren eigenen Endpunkt, optional mit Signatur, damit der Empfänger die Herkunft verifizieren kann.
- **Im Dashboard**, bewusst unauffällig – für den Fall, dass Sie eine Regel noch feinabstimmen und noch niemanden benachrichtigen möchten.

Kombinieren Sie beliebige Kanäle für eine einzige Regel. Der Schweregrad (info, warning oder critical) wird dabei mitgeliefert, damit dringende Meldungen auch dringend aussehen.

## Regeln im Formular erstellen, nicht in JSON

Sie beschreiben in einem Formular, was „fehlerhaft" bedeutet, und Failproof AI Observability erzeugt die zugrunde liegende Regel für Sie. Die JSON-Spezifikation ist lediglich das, was das Formular intern erzeugt – Sie können sie lesen, um eine Regel zu verstehen, müssen sie aber selten manuell eingeben.

![Das Formular für neue Benachrichtigungen: Name und Beschreibung, ein Aktivierungsschalter und eine Auslöserauswahl mit den Optionen Metrisch, Benutzerdefiniertes SQL, Auswertungsscore, Zusammengesetzter Score und Einzelereignis](/agenteye/images/alert-new.png)
*Wählen Sie einen Auslöser, und das Formular blendet die passenden Felder ein. Speichern schreibt die Regel.*

Der Standardweg ist schnell: Geben Sie einen Namen ein, wählen Sie einen **Auslöser** (was überwacht werden soll), legen Sie **Schwellenwert und Zeitfenster** fest (wie schwerwiegend, über welchen Zeitraum), fügen Sie mindestens einen **Kanal** hinzu, klicken Sie dann auf **Speichern** und anschließend auf **Testen**, um eine synthetische Benachrichtigung auszulösen und zu prüfen, ob alle Ziele korrekt eingerichtet sind. Intern erzeugt das eine kleine Spezifikation wie:

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

Sie sind nicht auf eine Art von Signal beschränkt. Wählen Sie den Auslöser, der dazu passt, wie Sie über den Fehler nachdenken:

| Auslöser | Wird ausgelöst, wenn |
|---|---|
| **Metrischer Schwellenwert** | eine voreingestellte Metrik (Fehlerrate, p95- oder p99-Latenz, Ereignis- oder Fehlerzähler, Token-Verbrauch) innerhalb eines Zeitfensters Ihren Grenzwert überschreitet |
| **Benutzerdefiniertes SQL** | Ihre eigene schreibgeschützte Abfrage eine Zeile zurückgibt oder ein berechneter Wert einen Schwellenwert überschreitet |
| **Auswertungsscore** | der Durchschnittswert eines Evaluators (z. B. für Halluzinationen) einen Schwellenwert überschreitet |
| **Zusammengesetzter Score** | mehrere Score-Prüfungen mit einer Logik wie „beliebige", „alle" oder „mindestens N" kombiniert werden, um eine Regression zu erkennen, die sich nur über mehrere Scores zeigt |
| **Einzelereignis** | ein einzelnes passendes Ereignis eintrifft: ein bestimmter Agent, ein bestimmter Fehlertyp oder ein Nachrichtentext-Teilstring |

Schauen Sie sich gerade einen Fehler auf der [Fehlerseite](/de/agenteye/error-tracking) an? Jede Zeile dort hat einen **+ alert**-Button, der dieses Formular vorausgefüllt öffnet, um genau diesen Fehler künftig abzufangen – der Incident, den Sie gerade untersucht haben, wird so zum nächsten, der Sie benachrichtigt.

**Wo Sie es finden:** Benachrichtigungen befinden sich unter `/<org-slug>/alerts`. Zum Erstellen, Bearbeiten, Löschen und Testen von Regeln wird **`alerts:write`** benötigt; `alerts:read` reicht zum Anzeigen. Die Empfängerauswahl listet die Mitglieder Ihrer Organisation namentlich auf, sodass Sie eine Person benachrichtigen können, ohne das Formular zu verlassen.

## Nur benachrichtigen, wenn es wirklich relevant ist

Ein einzelner schlechter Messwert sollte Sie nicht wecken. Der **M von N**-Rauschfilter steuert, wie viele der letzten Prüfungen fehlschlagen müssen, bevor die Benachrichtigung tatsächlich ausgelöst wird. Stellen Sie ihn auf **3 von 5** ein, und die Regel wird erst ausgelöst, nachdem drei der letzten fünf Prüfungen den Grenzwert überschritten haben – so hört ein instabiles Signal auf, falschen Alarm zu schlagen. Belassen Sie den Standardwert **1 von 1**, um beim ersten Überschreiten zu feuern. Sie legen außerdem fest, wie oft die Regel ausgeführt wird – aus Voreinstellungen von 1m, 5m, 15m und 1h, abgestimmt auf die tatsächliche Dynamik des Signals.

## Was passiert, wenn eine Benachrichtigung ausgelöst wird

Eine Überschreitung öffnet einen **Incident** und benachrichtigt Ihre Kanäle einmalig. Von dort aus kann Ihr Team ihn bestätigen, einen Verantwortlichen zuweisen, ihn besprechen und auflösen – alles in einem übersichtlichen, nachvollziehbaren Protokoll. Dieser Triage-Workflow hat sein eigenes Zuhause: siehe [Incidents](/de/agenteye/incidents).
