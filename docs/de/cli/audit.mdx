Die Prüffunktion ist jetzt als **/audit-Dashboard-Seite** verfügbar, nicht als CLI-Unterbefehl. Öffnen Sie sie über die Dashboard-Navigationsleiste (zwischen Policies und Projects) oder besuchen Sie `http://localhost:8020/audit` direkt, wenn Sie `failproofai` lokal ausführen.

```bash
failproofai          # open the dashboard, then click "Audit"
```

Das Dashboard scannt vergangene Agent-CLI-Transkripte auf diesem Computer (Claude Code, Codex, Copilot, Cursor, OpenCode, Pi, Gemini) und zeigt an, wie oft der Agent Dinge getan hat, die failproofai verhindern soll — Prüfungen von Umgebungsvariablen, erzwungene Pushes, redundante `cd <cwd>`-Präfixe, Sleep-Polling-Schleifen, erneutes Lesen von gerade bearbeiteten Dateien und mehr.

Für jedes Transkript wird jedes Tool-Use-Ereignis durch die 39 eingebauten Policies **und** durch 8 nur für die Prüfung vorgesehene Detektoren abgespielt, die Muster erkennen, die noch nicht durch Laufzeit-Policies abgedeckt sind. Die Zählungen werden pro Policy / Detektor über alle Sitzungen hinweg aggregiert.

## Was Sie erhalten

Die `/audit`-Seite besteht aus sechs Abschnitten:

1. **Identität** — Ihr Agent wird anhand des gewichteten Signals über alle geprüften Transkripte in einen von 8 Archetypen eingeteilt (`optimist`, `cowboy`, `explorer`, `goldfish`, `paranoid architect`, `precision builder`, `hammer`, `ghost`).
2. **Stärken** — Echte Zahlen aus dem Scan (Anteil sauberer Aufrufe, „0 credential leaks" usw.), die davon abhängen, dass die relevanten Sanitize-Policies tatsächlich ausgelöst werden.
3. **Bewertung** — 0–100 mit den Stufen S/A/B/C/D/F und eine projizierte Verbesserung, wenn alle empfohlenen Policies aktiviert wären.
4. **Befunde** — Karten pro Policy mit Beschreibung des Vorfalls, Kosten, erfassten Belegen und dem genauen `failproofai policy add <slug>`-Befehl, um das eingebaute Live-Gegenstück zu aktivieren, das den Vorfall abgefangen hätte.
5. **Empfohlene Policies** — Aggregierte Installationsliste mit einem einzeiligen `failproofai policies --install`-Befehl.
6. **Erinnerung zur erneuten Prüfung** — „Komm verbessert zurück." Stellen Sie eine 7-tägige E-Mail-Erinnerung über den API-Server ein (Anmeldung erforderlich; siehe [`failproofai auth`](/de/cli/auth)).

## Nur-Prüf-Detektoren

Diese erkennen Muster für „unnötiges Verhalten", die (noch) nicht in Echtzeit durchgesetzt werden. Sie laufen nur während der Prüfung und blockieren niemals einen Live-Tool-Aufruf.

| Detektor | Was gezählt wird |
|---|---|
| `redundant-cd-cwd` | Bash-Befehle, die mit `cd <cwd> && …` beginnen, obwohl Befehle bereits in `cwd` ausgeführt werden. |
| `prefer-edit-over-read-cat` | `cat`/`head`/`tail`/`less`/`more` auf einer einzelnen Quelldatei — verwenden Sie stattdessen das `Read`-Tool. |
| `prefer-edit-over-sed-awk` | `sed -i` / `awk … > file` In-Place-Bearbeitungen — verwenden Sie stattdessen das `Edit`-Tool. |
| `prefer-write-over-heredoc` | Heredoc / mehrzeiliges `echo > file` zum Schreiben von Dateien — verwenden Sie stattdessen das `Write`-Tool. |
| `sleep-polling-loop` | Lange `sleep N`-Pausen (≥ 30s) oder `while …; sleep …; done`-Polling-Schleifen. |
| `find-from-root` | `find /`, `find /home`, `find /usr` usw. — Suche auf `cwd` einschränken. |
| `git-commit-no-verify` | `git commit … --no-verify` / `-n`, um Hooks zu überspringen. |
| `reread-after-edit` | `Read` einer Datei, die in derselben Sitzung gerade mit `Edit`/`Write` bearbeitet wurde. |

## Caches

- **Transkript-spezifischer Cache** unter `~/.failproofai/cache/audit/<sha1>.json`, schlüsselt nach `(mtime, size, engineVersion, detectorVersion)` — wird automatisch invalidiert, wenn sich das Transkript oder der Policy-/Detektor-Code ändert. Jeder Eintrag speichert außerdem einen `cachedAt`-Zeitstempel als **TTL-Metadaten** (nicht Teil des Cache-Schlüssels); Einträge, die älter als **7 Tage** sind, werden beim Lesen abgelehnt, damit langlebige Ergebnisse nicht die Weiterentwicklung der Detektoren überdauern.
- **Gesamtergebnis-Cache** unter `~/.failproofai/audit-dashboard.json` (Modus 0600). Ermöglicht eine sofortige Darstellung des Dashboards beim Navigieren, ohne die Prüfung erneut durchzuführen. Wird beim Lesen ebenfalls nach der **7-tägigen TTL** abgelehnt — `/audit` fällt dann auf seinen leeren Zustand zurück und fordert zur Durchführung einer neuen Prüfung auf. Klicken Sie auf `[ re-audit now ]` am unteren Ende des Berichts, um die Ergebnisse zu aktualisieren; die neue Prüfung zeigt den Fortschritt über einen fixierten Banner am oberen Rand an und ersetzt das Ergebnis bei Erfolg direkt (ohne Seitenneuladung).

## Hinweise

- **Keine Änderungen.** Die Prüfung läuft im Nur-Lese-Modus ab. `warn-repeated-tool-calls` wird übersprungen, da dessen sitzungsbezogene Hilfsdatei sonst verändert würde.
- **Workflow-Policies werden übersprungen.** `require-*-before-stop`-Policies werden nur bei `Stop`-Ereignissen ausgelöst und führen `execSync` gegen den Live-Git-Status aus — sie haben keine sinnvolle Interpretation im Sinne von „was wäre 2025 passiert", daher erscheinen sie nicht in den Prüfzählungen.
- **Benutzerdefinierte Policies werden übersprungen.** Vom Benutzer bereitgestellte benutzerdefinierte Hooks werden nicht erneut abgespielt (sie können sich seit der ursprünglichen Sitzung geändert haben).
