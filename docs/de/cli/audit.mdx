Das Audit spielt deine vergangenen Agent-CLI-Transkripte durch die failproofai-Policy-Engine
ab und rendert einen teilbaren, visuellen Bericht auf der **`/audit`-Dashboard-Seite** —
das Archetyp deines Agenten, einen Score von 0–100 und genau welche Policies was
abgefangen hätten.

## Ausführen

Drei Einstiegswege — alle landen im gleichen `/audit`-Bericht.

<CodeGroup>

```bash npx (keine Installation)
npx -y failproofai audit
```

```bash failproofai audit
failproofai audit
```

```bash failproofai (Dashboard)
failproofai
```

</CodeGroup>

Das Dashboard scannt vergangene Agent-CLI-Transkripte auf diesem Rechner (Claude Code, Codex, Copilot, Cursor, OpenCode, Pi) und meldet, wie oft der Agent Dinge getan hat, die failproofai zu verhindern entwickelt wurde — Env-Var-Prüfungen, Force Pushes, redundante `cd <cwd>`-Präfixe, Sleep-Polling-Schleifen, erneutes Lesen gerade bearbeiteter Dateien und mehr.

Für jedes Transkript wird jedes Tool-Use-Event durch die 39 eingebauten Policies **und** durch 8 auditspezifische Detektoren abgespielt, die Muster erkennen, die noch nicht durch Laufzeit-Policies abgedeckt sind. Die Zählungen werden pro Policy / Detektor über alle Sitzungen aggregiert.

## Was du erhältst

Die `/audit`-Seite ist ein einseitiges, teilbares **Poster** gefolgt von vier Abschnitten unterhalb des sichtbaren Bereichs:

1. **Poster** — die Identität deines Agenten auf einen Blick: sein **Archetyp** (einer von 8 — `optimist`, `cowboy`, `explorer`, `goldfish`, `paranoid architect`, `precision builder`, `hammer`, `ghost`), seine Persona-Schlüsselwörter, wie selten dieser Archetyp ist, und ein **0–100-Score** mit einem Tier-Band (`S` bis `bottom tier`). Zum Teilen gedacht — auf X oder LinkedIn posten oder als PNG herunterladen.
2. **`// strengths`** — was dein Agent bereits gut macht, als echte Zahlen aus dem Scan (z. B. Clean-Tool-Call-%, `0` Push-to-Main-Versuche), nur angezeigt, wo die relevante Policy eine saubere Bilanz hat.
3. **`// quirks`** — was durchgeschlüpft ist: eine sortierte Tabelle von Verhaltensweisen, die failproofai abgefangen hätte — *wann* es zuletzt passiert ist, *was durchgeglitten ist* (und das eingebaute Feature, das es blockiert hätte), seine *Schwere* und wie oft es *gesehen* wurde (`new` / `recurring` / `N× seen`).
4. **`// how to improve`** — die empfohlene Fehlerbehebungsliste: eine Zeile pro Policy mit einem kopierbaren `failproofai policy add <slug>`, plus einem **Alle installieren**-Button, der alle Empfehlungen auf einmal aktiviert und deinen **projizierten Score** anzeigt.
5. **`// come back better`** — bau dir eine Gewohnheit auf: Setze eine E-Mail-**Erinnerung** für einen erneuten Audit (`3d` / `7d` / `14d` / `30d`) oder führe ihn jetzt erneut durch, und **lade einen Freund ein**, seinen eigenen Audit durchzuführen (versendet von failproof.ai, in CC an dich). Erinnerungen und Einladungen erfordern eine Anmeldung.

## Geplante Audits

Wenn du den **failproofaid-Daemon** ausführst (siehe [`failproofai config`](/de/cli/install-policies)),
kann er das Audit nach einem Zeitplan erneut ausführen und den `/audit`-Bericht
im Hintergrund aktualisieren. Dies ist **standardmäßig deaktiviert**, da der Scan
den *Inhalt* jedes Agent-Sitzungstranskripts auf diesem Rechner liest — nichts
wird auf einem Timer gescannt, bis du es anforderst.

Aktiviere es in `~/.failproofai/config.toml`:

```toml
[audit]
auto = true
interval_days = 7
```

| Schlüssel | Bedeutung |
|---|---|
| `auto` | `true` aktiviert den geplanten Scan. Alles andere — fehlend, `false`, `"yes"` — bedeutet deaktiviert. |
| `interval_days` | Tage zwischen den Scans. Auf 1–90 begrenzt; `0`, ein negativer Wert oder kein Zahlenwert fällt auf `7` zurück. |

- Der Zeitplan ist **wanduhrbasiert**, übersteht also Ruhezustand und Neustarts:
  ein Laptop, der über seinen fälligen Zeitpunkt hinaus geschlafen hat, läuft
  **einmal** beim Aufwachen, nie mit einem Rückstau.
- Jede Ausführung ist ein separater, niedrig priorisierter (`nice 19`) Prozess —
  niemals der Hook-Pfad des Daemons, der für Tool-Call-Antworten frei bleibt.
- Ein Scan wird übersprungen, wenn `failproofai audit` oder der erneute Durchlauf
  des Dashboards bereits läuft; er wird kurz danach wiederholt und nicht als
  Fehler behandelt.
- Der Fortschritt wird in `~/.failproofai/state/audit-schedule.json` geschrieben
  (letzter Lauf, nächste Fälligkeit). Der Daemon besitzt diese Datei — ändere
  den Zeitplan in `config.toml`.

<Note>
Wenn du dies auf einem Rechner aktiviert hast, der mit einem älteren failproofai
eingerichtet wurde, führe einmal `failproofai config` aus. Die Service-Definition
des Daemons benötigt einen zusätzlichen Eintrag, bevor er die CLI starten kann,
und die Aktualisierung ist Teil dieses Befehls.
</Note>

## Auditspezifische Detektoren

Diese erkennen Muster für „dummes Verhalten", die (noch) nicht in Echtzeit
durchgesetzt werden. Sie laufen nur während des Audits und blockieren niemals
einen Live-Tool-Call.

| Detektor | Was er zählt |
|---|---|
| `redundant-cd-cwd` | Bash-Befehle, die mit `cd <cwd> && …` beginnen, obwohl Befehle bereits in `cwd` ausgeführt werden. |
| `prefer-edit-over-read-cat` | `cat`/`head`/`tail`/`less`/`more` auf einer einzelnen Quelldatei — verwende stattdessen das `Read`-Tool. |
| `prefer-edit-over-sed-awk` | `sed -i` / `awk … > file` In-Place-Bearbeitungen — verwende stattdessen das `Edit`-Tool. |
| `prefer-write-over-heredoc` | Heredoc / mehrzeiliges `echo > file` zum Schreiben von Dateien — verwende stattdessen das `Write`-Tool. |
| `sleep-polling-loop` | Lange `sleep N` (≥ 30s) oder `while …; sleep …; done` Polling-Schleifen. |
| `find-from-root` | `find /`, `find /home`, `find /usr` usw. — Bereich auf `cwd` einschränken. |
| `git-commit-no-verify` | `git commit … --no-verify` / `-n`, wodurch Hooks übersprungen werden. |
| `reread-after-edit` | `Read` einer Datei, die gerade erst mit `Edit`/`Write` in derselben Sitzung bearbeitet wurde. |

## Caches

- **Transkriptspezifischer Cache** unter `~/.failproofai/cache/audit/<sha1>.json`, gehasht nach `(mtime, size, engineVersion, detectorVersion)` — wird automatisch invalidiert, wenn sich das Transkript oder der Policy-/Detektor-Code ändert. Jeder Eintrag speichert auch einen `cachedAt`-Zeitstempel als **TTL-Metadaten** (nicht Teil des Cache-Schlüssels); Einträge, die älter als **7 Tage** sind, werden beim Lesen abgelehnt, damit langlebige Ergebnisse nicht die Weiterentwicklung der Detektor-Logik überdauern.
- **Gesamtergebnis-Cache** unter `~/.failproofai/audit-dashboard.json` (Modus 0600). Ermöglicht dem Dashboard, beim Navigieren sofort zu rendern, ohne einen erneuten Scan durchzuführen. Wird beim Lesen ebenfalls nach der **7-Tage-TTL** abgelehnt — `/audit` fällt dann in seinen leeren Zustand zurück und fordert einen neuen Scan an. Klicke auf `[ re-audit now ]` unten im Bericht, um zu aktualisieren — ein erneuter Audit sendet `noCache: true`, umgeht also den transkriptspezifischen Cache und scannt alle Transkripte neu, anstatt das gecachte Ergebnis zurückzugeben; der Lauf streamt den Fortschritt über einen fixierten oberen Balken und tauscht das Ergebnis bei Erfolg direkt aus (kein Seitenneulade; ein fehlgeschlagener erneuter Audit behält den vorherigen Bericht bei).

## Hinweise

- **Keine Mutation.** Das Audit läuft im schreibgeschützten Modus. `warn-repeated-tool-calls` wird übersprungen, da sonst das sitzungsspezifische Begleitelement geändert würde.
- **Workflow-Policies übersprungen.** `require-*-before-stop`-Policies werden nur bei `Stop`-Events ausgelöst und führen `execSync` gegen den Live-Git-Status aus — sie haben keine sinnvolle Interpretation im Sinne von „Was wäre 2025 passiert", daher erscheinen sie nicht in den Audit-Zählungen.
- **Benutzerdefinierte Policies übersprungen.** Benutzerdefinierte Hooks werden nicht abgespielt (sie könnten sich seit der ursprünglichen Sitzung geändert haben).
