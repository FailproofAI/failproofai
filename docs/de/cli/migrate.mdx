```bash
failproofai migrate --dry-run   # Plan anzeigen, nichts ändern
failproofai migrate             # ausführen
```

Die meisten Nutzer tippen das nie. Es läuft nach einem Upgrade automatisch beim
ersten Befehl, und [`failproofai update`](/de/cli/update) schließt es ein. Verwende
es direkt, wenn du den Plan vorab sehen möchtest oder die Migration eigenständig
ausführen willst.

## Basiert auf dem Layout, nicht der Version

`~/.failproofai/VERSION` speichert eine **Layout**-Nummer — die Struktur des
Verzeichnisses, nicht die Release, die sie geschrieben hat. Migrationen sind auf
diese Nummer ausgerichtet, was einen großen Versionssprung günstig macht:

- npm-Versionen ändern sich bei jedem Release, Dutzende davon zwischen zwei Layouts.
- Eine Maschine, die dreißig Releases mit **keiner Layout-Änderung** überspringt,
  führt **null** Migrationen aus — keine dreißig Leerlauf-Schritte.
- Eine Maschine, die mehrere Layouts auf einmal überspringt, führt jeden Schritt
  der Reihe nach aus, wobei jeder Schritt nur seine eigenen beiden Enden kennt.

Das ist wichtig, weil npm ein installiertes Paket nicht eigenständig aktualisieren
kann. Eine Maschine, die monatelang auf einer Version bleibt und dann mehrere
Layouts überspringt, ist der Normalfall — keine Ausnahme.

## Der Trockenlauf

`--dry-run` gibt die genaue Kette und die Dateien aus, die zuerst gesichert würden,
und ändert überhaupt nichts — keine Migration, kein Backup, kein Ledger-Eintrag:

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## Was übernommen und was neu aufgebaut wird

Jeder Pfad im Home-Verzeichnis deklariert, welche Art von Daten er enthält, und
das entscheidet, ob eine Migration ihn verwerfen darf. Die Regel: **Abgeleitetes
und Wiederholbares darf verworfen werden; alles, was du eingegeben hast, noch nicht
Zugestelltes und alles, was die Maschine identifiziert, wird übernommen.**

| Übernommen | Neu aufgebaut oder erneut abgerufen |
|---|---|
| `config.json` — Einstellungen, `daemon.configured`, zusätzliche Capture-Pfade | Der Audit-Cache |
| `credentials.json` — deine Cloud-Registrierung | Cloud-verwaltete Deployments (werden beim nächsten Poll erneut abgerufen und Digest-verifiziert) |
| `policies-config.json` — deine Policy-Auswahl und Parameter | Daemon-Scratch-Zustand |
| `policies/` — deine eigenen Policy-Dateien und die von ihnen importierten Hilfsdateien | |
| `hook-activity/` — das Entscheidungslog, das das Dashboard liest | |
| Noch nicht zugestellte Events in der Upload-Warteschlange | |
| `cursors/` — Collector-Wasserzeichen | |
| Das Daemon-Binary in `bin/` | |

<Note>
  Nicht zugestellte Events werden übernommen statt verworfen, weil der Verlust
  dauerhaft wäre — nicht nur langsam: Das Wasserzeichen des Collectors ist bereits
  über alles hinausgegangen, was noch im Spool liegt, sodass dieser Bereich eines
  Transkripts nie mehr gelesen werden würde. Die Migration fordert den Daemon
  außerdem auf, den Spool unmittelbar nach Abschluss zuzustellen, sodass in der
  Regel nichts mehr zu übernehmen bleibt.
</Note>

Schlüssel, die eine *neuere* Version in `config.json`, `credentials.json` oder
`policies-config.json` geschrieben hat, werden ebenfalls bewahrt — anstatt von
einem älteren Reader verworfen zu werden.

## Der hinterlassene Datensatz

```
~/.failproofai/migrations/
  applied.json                 ein Eintrag pro Schritt: Layout, CLI, Zeitstempel, Dauer, Ergebnis
  backup-layout<n>/            Kopien der unersetzlichen Dateien, vor dem ersten Schritt erstellt
```

`applied.json` beantwortet die Frage „Was hat diese Maschine tatsächlich
durchlaufen" — die erste Frage, die sich lohnt zu stellen, wenn nach einem Upgrade
etwas nicht stimmt. Füge sie einem Bug-Report bei.

Das Backup ist bewusst klein gehalten statt eine Kopie des gesamten Verzeichnisses
zu sein: Die Migration löscht per Design keine unersetzlichen Daten mehr, daher
geht es beim Absichern um einen *Fehler in einem Schritt* — und diese wenigen
Dateien sind dort, wo ein solcher Fehler schaden würde.

## Wenn ein Schritt fehlschlägt

Die Kette stoppt dort. `VERSION` wird nur von einem erfolgreich abgeschlossenen
Schritt gestempelt, sodass das Home mit seinem alten Layout markiert bleibt und
der nächste Befehl es erneut versucht — ein Home wird nie auf der Grundlage einer
unvollständigen Migration als aktuell markiert. Der Schritt wird in `applied.json`
mit `"ok": false` erfasst, und das Backup befindet sich an der Stelle, wo es
erstellt wurde.

## Ein neueres Home wird abgelehnt, nicht migriert

Wenn `~/.failproofai/` von einem **neueren** failproofai geschrieben wurde als dem,
das du gerade ausführst, stoppt der Befehl und fordert dich auf, stattdessen ein
Upgrade durchzuführen. Diese Daten sind in Ordnung, und eine neuere CLI liest sie;
„vorwärts" von dort zu migrieren ist keine Option, und ein Zurücksetzen würde
etwas Wiederherstellbares zerstören.

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

Der Daemon wendet dieselbe Regel an: `failproofaid` weigert sich, gegen ein Layout
zu starten, das er nicht versteht, anstatt Pfade zu lesen und zu schreiben, die
verschoben wurden.
