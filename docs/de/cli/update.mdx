---
title: Aktualisierung nach einem Upgrade
description: "Die zweite Hälfte eines Upgrades abschließen, die npm nicht erledigen kann: Home migrieren und Daemon abgleichen"
---

```bash
npm install -g failproofai@latest && failproofai update
```

Das ist das vollständige Upgrade. `npm` ersetzt die CLI; `failproofai update` erledigt
den Rest.

## Warum ein zweiter Befehl notwendig ist

`npm install -g` ersetzt nur eine Sache — die CLI. Zwei weitere Bestandteile einer failproofai-
Installation befinden sich bewusst außerhalb des Pakets und werden beim npm-Lauf nicht verschoben:

- **`~/.failproofai/`**, Ihre Einstellungen, Cloud-Registrierung, Richtlinienauswahl und
  Verlauf. Eine neue Version kann diese anders organisieren, und die Reorganisation muss
  durch Code erfolgen, der beide Strukturen kennt.
- **Die `failproofaid`-Daemon-Binärdatei** unter
  `~/.failproofai/bin/failproofaid-<version>`. Sie befindet sich bewusst *nicht* in
  `node_modules`: Ein Upgrade, das die Datei unter einem laufenden Dienst austauscht, würde
  einen aktiven Daemon auf eine Binärdatei aus anderem Quellcode umleiten — und das Entfernen
  des Pakets würde sie unter einem Dienst wegnehmen, der dann bei jedem Start in eine Absturzschleife gerät.

Nach einem reinen `npm install -g` ist daher die CLI neu, der Daemon jedoch nicht.
`failproofaid` verweigert den Start bei einem Home-Layout, das er nicht versteht — die
laute Variante dieser Diskrepanz statt der stillen —, sodass beide Hälften zusammengeführt
werden müssen. `failproofai update` erledigt genau diesen Schritt.

## Was der Befehl tut

<Steps>
  <Step title="Führt ausstehende Layout-Migrationen durch">
    Liest das in `~/.failproofai/VERSION` aufgezeichnete Layout und führt die Schritte aus, die
    es auf das Layout dieser Version bringen. In der Regel keine — siehe
    [`failproofai migrate`](/de/cli/migrate).
  </Step>
  <Step title="Installiert die passende Daemon-Binärdatei">
    Aus dem Plattformpaket, das npm bereits heruntergeladen hat, wenn möglich (ohne Netzwerkzugriff),
    andernfalls aus dem Release-Asset für genau diese Version, SHA-256-verifiziert bevor es verwendet wird.
  </Step>
  <Step title="Startet den Dienst neu und bestätigt die Verfügbarkeit">
    Durch aktive Prüfung statt Annahme — ein Dienst-Manager meldet einen Prozess als aktiv,
    sobald er geforkt wird, was nicht dasselbe ist wie funktionsfähig.
  </Step>
</Steps>

## Optionen

| Flag | Wirkung |
|------|---------|
| `--no-daemon` | Migriert nur das Home und lässt den Daemon bei seiner aktuellen Version. |

<Warning>
  `--no-daemon` belässt einen versionsabweichenden Daemon. Auf einem Rechner, der für die
  Nutzung des Daemons konfiguriert ist, **schlägt jedes Hook-Ereignis fehlsicher** fehl, wenn
  der Daemon nicht antwortet — und ein Daemon, der nach einer migrierten Home-Struktur nicht
  starten kann, antwortet nicht. Es empfiehlt sich, den Daemon-Teil ebenfalls auszuführen.
</Warning>

## Bei Problemen

Der Befehl beendet sich mit einem Fehlercode und gibt an, welche Hälfte fehlgeschlagen ist. Zwei Fälle sind wichtig zu kennen:

- **Ein Migrationsschritt wurde nicht abgeschlossen.** Das Home verbleibt mit seinem *alten*
  Layout markiert, sodass der nächste Befehl es erneut versucht — kein Home wird jemals
  auf Grundlage einer unvollständigen Migration als aktuell markiert. Kopien Ihrer Einstellungen
  und Registrierung wurden vor dem Start gespeichert, in `~/.failproofai/migrations/backup-layout<n>/`.
- **Der Daemon konnte ohne Passwort nicht neu gestartet werden.** `sudo -n` wird bewusst
  verwendet, damit nie etwas aus einer Fortschrittsanzeige heraus abgefragt wird. Der Befehl
  gibt die genaue Zeile aus, die Sie selbst ausführen müssen.

<Note>
  Hier wird kein interaktiver Einrichtungsassistent benötigt. Ihre Einstellungen, Cloud-
  Registrierung und Richtlinienauswahl bleiben nach einem Upgrade erhalten, sodass ein
  migrierter Rechner genauso durchsetzt wie zuvor — was auf Rechnern ohne Benutzer am
  wichtigsten ist: ein CI-Runner, ein Fleet-Rechner, ein headless Gateway.
</Note>

## Automatisierung

`failproofai update` ist nicht-interaktiv und sicher auszuführen, wenn nichts zu tun ist —
er meldet „keine Migration war erforderlich" und beendet sich mit 0. Die Empfehlung ist,
ihn nach jedem Upgrade in einem Bereitstellungsskript oder Dockerfile einzufügen:

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

(`--no-daemon` in einem Image-Build, wo noch kein Dienst zum Neustart vorhanden ist.)
