Erstelle eine Datei mit der Endung `policies.js`, `policies.mjs` oder `policies.ts` unter `.failproofai/policies/`. Konventionsdateien werden automatisch auf Projekt- und Benutzerebene geladen.

## Richtlinie vor der Cloud-Veröffentlichung testen

<Tabs>
  <Tab title="Dashboard">
    1. Installiere die benutzerdefinierte Richtlinie auf einem Testrechner und löse sowohl eine übereinstimmende Aktion als auch eine legitime Nicht-Übereinstimmung aus.
    2. Gehe zu **Beobachten → Richtlinie** und vergleiche die beiden Entscheidungen.
    3. Öffne jede verknüpfte Sitzung und überprüfe, ob der Event-Payload ausreichend Belege für die Regel enthält.
    4. Sobald das Verhalten korrekt ist, übertrage den geprüften Quellcode in **Admin → Richtlinien-Editor** und veröffentliche eine Version.

  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai policies --install --custom ./security.policies.ts \
      --cli claude --scope project
    failproofai policies
    ```

    Konventionsdateien unter `.failproofai/policies/` werden ohne `--custom` geladen. Behalte einen expliziten Installationsbefehl in CI, wenn die Validierung bei einem fehlerhaften Modul fehlschlagen soll.
  </Tab>
</Tabs>

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production-paths",
  description: "Block writes to production configuration",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Write" && ctx.toolName !== "Edit") return allow();
    const path = String(ctx.toolInput?.file_path ?? "").replaceAll("\\", "/");
    if (path.split("/").includes("production")) {
      return deny("Writes to production configuration require approval.");
    }
    return allow();
  },
});
```

Dies trifft auf `production/config.yml`, `/srv/production/config.yml`, `/srv/production` und `C:\\production\\config.yml` für sowohl `Write` als auch `Edit` zu. Namen wie `production-backup` werden nicht erfasst, da `production` ein vollständiges Pfadsegment sein muss.

Eine explizite Datei validieren und installieren:

```bash
failproofai policies --install --custom ./security.policies.ts
```

Der Richtlinienkontext enthält den Event-Typ, normalisierten Payload, Tool-Namen und -Eingabe, Sitzungsmetadaten, Parameter und die Quell-CLI, sofern verfügbar.

## Fehlerpfade testen

Führe die Validierung nach dem Ändern der Einstiegsdatei oder eines lokalen Moduls aus, das sie importiert:

```bash
failproofai policies --install --custom ./security.policies.ts --scope project
```

Der strikte CLI-Pfad schlägt fehl bei fehlenden Dateien, Syntaxfehlern, nicht aufgelösten Importen, Ausnahmen auf oberster Ebene und Modul-Lade-Timeouts. Zum Durchsetzungszeitpunkt wird eine fehlerhafte benutzerdefinierte Datei protokolliert und übersprungen, damit die eingebauten Richtlinien weiter ausgeführt werden können. Behandle jede Ladewarnung als Verlust der erwarteten Durchsetzung und löse in Produktionsprotokollen einen Alarm aus.

Verwende global eindeutige Namen für explizite, Konventions- und Cloud-verwaltete Richtlinien. Halte Richtlinienfunktionen deterministisch, begrenze externe Aufrufe mit kurzen Timeouts, und gib auf jedem Pfad ein bewusstes `allow`, `instruct` oder `deny` zurück.

<Warning>
  Eine benutzerdefinierte Richtlinie ist Durchsetzungscode. Teste fehlende Felder, alternative Tool-Namen und fehlerhafte Eingaben – nicht nur den erwarteten Übereinstimmungsfall.
</Warning>
