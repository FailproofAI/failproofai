Failproof AI trennt die Richtlinienauswahl von Maschinen- und Daemon-Einstellungen. Dadurch bleiben Repository-Richtlinien überprüfbar, während Zugangsdaten und Daemon-Status außerhalb des Repositorys verbleiben.

## Einen Richtlinien-Scope wählen

<Tabs>
  <Tab title="Dashboard">
    Führen Sie `failproofai` ohne Argumente aus, um das lokale Richtlinien-Dashboard zu öffnen. Wählen Sie den Benutzer-, Projekt- oder lokalen Scope, bevor Sie eine Richtlinie aktivieren, damit die Änderung in die vorgesehene Konfigurationsdatei geschrieben wird.

    - **Benutzer** gilt projektübergreifend auf dieser Maschine.
    - **Projekt** gehört zum Repository und kann committet werden.
    - **Lokal** überschreibt ein Projekt für einen einzelnen Benutzer und sollte in der `.gitignore` eingetragen bleiben.

  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai policy add block-rm-rf --scope user
    failproofai policy add block-force-push --scope project
    failproofai policy add warn-large-file-write --scope local
    failproofai policies
    ```

    Nicht jeder Harness unterstützt den lokalen Scope. Die CLI lehnt einen Scope ab, den der gewählte Harness nicht abbilden kann.
  </Tab>
</Tabs>

| Scope | Richtlinien-Konfigurationsdatei |
| --- | --- |
| Projekt | `<project>/.failproofai/policies-config.json` |
| Lokal | `<project>/.failproofai/policies-config.local.json` |
| Benutzer | `~/.failproofai/policies-config.json` |

Aktivierte Richtlinien werden als Vereinigungsmenge zusammengeführt. Richtlinienparameter verwenden den ersten Scope, der Parameter für die jeweilige Richtlinie definiert – in der Reihenfolge Projekt → Lokal → Benutzer. Explizite benutzerdefinierte Richtlinienpfade verwenden ebenfalls den ersten Scope, der sie definiert.

## Richtlinienparameter konfigurieren

<Tabs>
  <Tab title="Dashboard">
    Öffnen Sie die Richtlinie im lokalen Dashboard, bearbeiten Sie die unterstützten Parameter und speichern Sie im gewählten Scope. Führen Sie dann eine passende und eine nicht passende Agent-Aktion aus, und prüfen Sie die Entscheidung unter **Beobachten → Richtlinie**.

  </Tab>
  <Tab title="CLI">
    Bearbeiten Sie die `policies-config.json` des gewählten Scopes und führen Sie anschließend `failproofai policies` aus, um unbekannte Richtliniennamen oder Parameterschlüssel zu erkennen.

    ```json
    {
      "enabledPolicies": ["block-rm-rf", "block-force-push"],
      "policyParams": {
        "block-rm-rf": {
          "allowPaths": ["/tmp/build-output"]
        }
      }
    }
    ```

    ```bash
    failproofai policies
    ```
  </Tab>
</Tabs>

## Die Maschinendateien verstehen

`~/.failproofai` enthält separate Dateien für separate Vertrauensbereiche:

| Pfad | Zweck |
| --- | --- |
| `config.json` | Nicht-geheime Daemon-, Audit- und Telemetrie-Einstellungen |
| `credentials.json` | Cloud-Zugangsdaten; gespeichert mit Berechtigungen nur für den Eigentümer |
| `policies-config.json` | Benutzer-Scope: integrierte Auswahl, Parameter und explizite benutzerdefinierte Pfade |
| `policies/` | Benutzerkonventions-Richtlinien und Cloud-verwaltete Richtlinien-Artefakte |
| `hook-activity/` | Lokales Protokoll der Richtlinienentscheidungen |
| `state/` | Daemon-Spool, Gesundheitsstatus, Pause und Laufzeitzustand |

Verwenden Sie `FAILPROOFAI_HOME`, um das gesamte Maschinen-Layout für einen Container oder isolierten Test zu verschieben. Verschieben Sie keine einzelnen Statusverzeichnisse unabhängig voneinander.

<Warning>
  Committen Sie niemals `credentials.json`. Committen Sie Projektkonfigurations- und Projektkonventions-Richtlinien erst, nachdem Sie sie als Durchsetzungscode überprüft haben.
</Warning>
