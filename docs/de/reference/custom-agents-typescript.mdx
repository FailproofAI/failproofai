## Installation

```bash
npm install @failproofai/sdk
```

```ts
import * as failproofai from "@failproofai/sdk";

await failproofai.agent("planner", { goal: question }, async () => {
  const hits = await failproofai.toolCall("web_search", { input: { q } }, () => search(q));
});
```

Die Framework-Adapter sind im Paket selbst enthalten. Die Frameworks sind **optionale Peer-Dependencies** — deklariert, damit die unterstützten Versionen sichtbar sind, werden aber nie automatisch installiert und nur beim Aufruf von `instrument()` importiert.

## Den Failproof-Daemon verbinden

Identisch zum Python SDK: einen `events:add`-Schlüssel unter **Einstellungen → API-Schlüssel** anlegen und dann den [Daemon verbinden](/de/start/setup#connect-a-machine-to-cloud) auf dem Agenten-Rechner. Das SDK schreibt auf die Festplatte; der Daemon versendet die Daten.

## Konfiguration

### OpenTelemetry-Spans (opt-in)

OpenTelemetry separat installieren mit `npm install @opentelemetry/api @opentelemetry/sdk-trace-base`.
Dann FailproofAI den Prozessoren des Providers hinzufügen:

```ts
import * as failproofai from "@failproofai/sdk";
import { BasicTracerProvider } from "@opentelemetry/sdk-trace-base";
import type { SpanProcessor } from "@opentelemetry/sdk-trace-base";

const spanProcessors: SpanProcessor[] = [];
await failproofai.instrument("otel", { spanProcessors });
const provider = new BasicTracerProvider({ spanProcessors });
const span = provider.getTracer("my-agent").startSpan("agent", {
  attributes: { "gen_ai.operation.name": "invoke_agent" },
});
span.end();
await provider.forceFlush();
```

Für einen bestehenden Provider die anderen Prozessoren in derselben Liste behalten. Provider,
die `addSpanProcessor` anbieten, können stattdessen als `{ provider }` übergeben werden. Ohne
Optionen wird ein neuer Provider registriert, sofern noch keiner registriert ist.
`OtelSpanExporter` kann auch direkt mit einem eigenen Prozessor verwendet werden.

Exporte laufen über den verbundenen FailproofAI-Daemon; das SDK sendet keine Netzwerkanfragen
und benötigt weder Schlüssel noch einen lokalen Listener. [OpenTelemetry-Ingest](/de/agenteye/opentelemetry)
ist in Cloud immer aktiv. Ein bloßes `instrument()` aktiviert diesen Exporter nicht.
`uninstrument("otel")` deaktiviert nur den eigenen Prozessor. Der Inhalt wird durch Span-Attribute
gesteuert; vor dem Beenden den Provider flushen. OpenTelemetry bleibt eine optionale
Anwendungsabhängigkeit, keine feste SDK-Abhängigkeit.

```ts
failproofai.configure({
  environment: "production",
  flushInterval: 0.5,
  baseDir: undefined,
});
```

| Option | Beschreibung |
| --- | --- |
| `environment` | Das Label für jeden Event — `production`, `staging`, `prod-eu`. Standard: `dev`. |
| `flushInterval` | Wie oft der Timer auf die Festplatte schreibt, in Sekunden. Standard: `0.5`. |
| `baseDir` | Schreibziel. Standard ist der Spool des Daemons, was in der Regel korrekt ist. |

Nichts wird angewendet, wenn die Validierung fehlschlägt — ein abgelehnter Aufruf lässt das SDK genau im bisherigen Zustand, statt es mit einem neuen `baseDir` und dem alten Intervall zu hinterlassen.

Konfiguration per Umgebungsvariable:

| Variable | Beschreibung |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | Setzt `environment` ohne Codeänderung. Eine `configure()`-Option hat Vorrang. |
| `FAILPROOFAI_HOME` | Verschiebt das Failproof AI-Stammverzeichnis, das den Spool enthält. |
| `FAILPROOFAI_SDK_LOG_LEVEL` | `debug`, `info`, `warn` (Standard), `error`, `silent`. |
| `FAILPROOFAI_SDK_STRICT` | `1` lässt Instrumentierungsfehler werfen statt sie zu protokollieren. |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | `1` lässt ein Framework-Kompatibilitätsproblem werfen statt zu warnen und fortzufahren. |

<Warning>
  **Kein Komma in `environment`.** Der Ingest teilt dieses Feld an Kommas auf, um Filter zu erstellen, und überspringt jeden Event, dessen Label ein Komma enthält — damit verschwindet ein ganzer Lauf stillschweigend. `prod-eu` schreiben, nicht `prod,eu`.

  `configure({ environment: "prod,eu" })` wirft einen Fehler, damit das sofort auffällt. `AGENTEYE_ENVIRONMENT` kann nicht werfen — es gibt keine Rückmeldekanal — daher wird einmal gewarnt und auf `dev` zurückgefallen.
</Warning>

Die eigenen Log-Zeilen des SDK in einen Logger leiten mit `failproofai.setLogger({ debug, info, warn, error })`.

## Herunterfahren

Gepufferte Events werden bei `process.on("exit")` geschrieben.

Ein durch ein Signal beendeter Prozess erreicht diesen Handler nie, und Node beendet sich bei `SIGTERM` standardmäßig ohne Ausführen der Exit-Handler — ein containerisierter Agent verliert dabei alles, was das letzte Intervall noch nicht geschrieben hat.

<Warning>
  **Dieses SDK installiert keinen Signal-Handler.** Das Registrieren eines Handlers verändert das Prozessverhalten: Ein Listener unterdrückt Nodes Standardbeendigung, sodass eine Bibliothek, die einen solchen registriert, Ctrl-C stillschweigend außer Kraft setzen würde. Eigenen Handler hinzufügen:

  ```ts
  for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.once(signal, () => {
      failproofai.flushSync();
      process.exit(0);
    });
  }
  ```
</Warning>

Ein kurzlebiges Skript oder ein Serverless-Handler sollte `await failproofai.flush()` aufrufen, bevor es zurückkehrt — das Intervall allein garantiert keine Zustellung.

## Identität

Jeder Event gehört zu einer Session und einem Agenten. **Die Scopes füllen beides aus**, sodass sie selten manuell übergeben werden müssen:

```ts
await failproofai.session(async () => {
  await failproofai.agent("planner", async () => {
    failproofai.event.toolUse({ toolName: "search", toolCallId: "c1" });
  });
});
```

`sessionId` oder `agentId` explizit zu übergeben funktioniert weiterhin und hat Vorrang. Ist weder gebunden noch übergeben, wirft der Aufruf einen Fehler, statt einen Event zu emittieren, den Cloud stillschweigend verwerfen würde.

<Note>
  Identität wird über `AsyncLocalStorage` übertragen. Sie folgt `await`, `.then()`, Timern und jedem Callback, der innerhalb des Scopes erstellt wurde. Sie folgt **nicht** einem Callback, der in einem Lauf gespeichert und in einem anderen aufgerufen wird, oder Arbeit, die über eine `worker_threads`-Grenze übergeben wird — solche Fälle in `failproofai.propagate()` einwickeln, sonst landen die Events ohne Zuordnung.
</Note>

### Scopes

| Scope | Emittiert | Gibt zurück |
| --- | --- | --- |
| `session(body)` | nichts — nur Identität | was `body` zurückgibt |
| `agent(id, options?, body)` | `agent_start`, dann `agent_end` | was `body` zurückgibt |
| `toolCall(name, options?, body)` | `tool_use`, dann `tool_result` | was `body` zurückgibt |

Ein synchroner Body bleibt synchron: `agent("x", () => 1)` gibt `1` zurück, kein Promise.

`toolCall` zeichnet den aufgelösten Rückgabewert des Bodys als `output` des Tools auf, sofern `call.output` nicht manuell gesetzt wird.

<Accordion title="Exit-Semantik" icon="arrow-right-from-bracket">

| Was passiert ist | Events | `outcome` |
| --- | --- | --- |
| Der Block hat zurückgegeben | `agent_end` | `"success"`, oder das eigene `outcome` |
| Der Block hat geworfen | `error`, dann `agent_end` | `"failed"` |
| Ein `AbortError` | nur `agent_end` | `"cancelled"` |

Der Fehler wird immer erneut geworfen.

Ein Tool-Fehler wird auf dem Blatt aufgezeichnet — `tool_result` mit einem `error`-String — und emittiert **keinen** `error`-Event auf Run-Ebene. Einer, den die Agentenschleife abfängt, ist kein Run-Fehler; einer, der sich propagiert, wird genau einmal gemeldet, vom umschließenden `agent()`.

</Accordion>

<Accordion title="Die `using`-Form" icon="brackets-curly">

Wenn die Arbeit keine einzelne Funktion ist — ein Scope, der in einem Konstruktor geöffnet und in einem Teardown geschlossen wird, oder einer, der bestehenden Kontrollfluss überspannt:

```ts
{
  using span = failproofai.agent.open("planner", { goal });
  using call = failproofai.toolCall.open("search", { input: { q } });
  call.call.output = await search(q);
}  // tool_result, then agent_end
```

Beide Formen emittieren byte-identische Events. Die Callback-Form ist vorzuziehen: sie läuft innerhalb von `AsyncLocalStorage.run()`, es gibt also nichts rückzuwickeln, und die gesamte Klasse von „hier geöffnet, dort geschlossen"-Fehlern ist unerreichbar.

Ein `using`-Block, der seinen eigenen Fehler abfängt, meldet ihn mit `span.fail(error)` — der Disposer hat keinen eigenen Exception-Kanal.

</Accordion>

## Event-Katalog

Dieselben fünfzehn Methoden wie im Python SDK, in camelCase. Die meisten kommen in **Paaren** — der Öffner wird aufgerufen, dann der Schließer, und das SDK misst die Zeitspanne dazwischen.

| | Öffnet | Schließt |
| --- | --- | --- |
| **Agenten** | `agentStart` | `agentEnd` |
| | `agentPause` | `agentResume` |
| **Modelle** | `modelRequest` | `modelResponse` |
| **Tools** | `toolUse` | `toolResult` |
| **Hooks** | `hookTriggered` | `hookCompleted` |
| **Menschen** | `humanWait` | `humanInput` |

Drei stehen allein: `error`, `humanPause`, `humanInterrupt`.

<Accordion title="Jedes Feld, pro Methode" icon="table">

Jede Methode nimmt außerdem `sessionId` und `agentId` an, die die Scopes automatisch befüllen. Ausgelassene Felder werden verworfen, statt als JSON `null` gesendet zu werden.

| Methode | Erforderlich | Optional |
| --- | --- | --- |
| `agentStart` | — | `goal`, `parentId` |
| `agentEnd` | — | `outcome`, `summary` |
| `agentPause` | `pauseId` | `reason`, `userId` |
| `agentResume` | `pauseId` | `reason`, `userId` |
| `modelRequest` | — | `model`, `messages`, `system`, `tools`, `requestId` |
| `modelResponse` | — | `model`, `stopReason`, `inputTokens`, `outputTokens`, `content`, `role`, `requestId` |
| `toolUse` | `toolName`, `toolCallId` | `input` |
| `toolResult` | `toolName`, `toolCallId` | `output`, `error` |
| `hookTriggered` | `hookName`, `hookId` | `triggerEvent`, `input` |
| `hookCompleted` | `hookName`, `hookId` | `outcome`, `output`, `error` |
| `error` | `errorType`, `message` | `traceback` |
| `humanWait` | `inputId` | `prompt`, `options`, `reason` |
| `humanInput` | `inputId` | `response` |
| `humanPause` | — | `reason`, `userId` |
| `humanInterrupt` | — | `reason`, `userId`, `atStep` |

Jeder weitere Schlüssel wird zu einem benutzerdefinierten Payload-Feld. Framework-spezifische Namen mit `fw_*` präfixieren; ein Name, der mit einem deklarierten Feld kollidiert, wird abgelehnt statt stillschweigend eine beförderte Spalte zu überschreiben.

</Accordion>

<Warning>
  **`duration_ms` wird berechnet, nicht akzeptiert.** Die vier schließenden Methoden messen die Zeitspanne seit dem Öffner und lehnen ein vom Aufrufer übergebenes `duration_ms` ab — eine gemeldete Dauer muss unveränderlich sein.

  Paare werden anhand der **Session** und der ID abgeglichen, nie anhand des Agenten. Ein Tool, das unter `planner` geöffnet und unter `worker` geschlossen wird, bildet trotzdem ein Paar — genau das tun verschachtelte Multi-Agenten-Runs.
</Warning>

## Framework-Adapter

```ts
await failproofai.instrument();              // whatever it can find
await failproofai.instrument("langchain");   // exactly one
failproofai.uninstrument();                  // put everything back
```

| Framework | Unterstützt | Einbindung |
| --- | --- | --- |
| **LangChain.js / LangGraph.js** | `@langchain/core` 0.3 – 1.x, LangGraph.js 0.4 – 1.x | `CallbackManager.configure`, sodass jeder `invoke`/`stream`/`batch`-Aufruf abgedeckt ist, ohne `callbacks:` übergeben zu müssen — oder `langchainHandler()` selbst übergeben und nichts patchen. |
| **Vercel AI SDK** | `ai` 4 – 7 | `telemetry()` an der Aufrufstelle, oder `instrument("ai")` prozessweit für `ai` 7 (auf 4–6 ist das opt-in — siehe unten). |
| **Mastra** | `@mastra/core` 0.20 – 1.x | `Agent.generate`/`.stream`, die Modell- und Tool-Auflösung des Agenten sowie die Workflow-Run/Step-Engine. |
| **LlamaIndex.TS** | `llamaindex` 0.11.4 – 0.x | `Settings.callbackManager` (abonniert) plus `AgentWorkflow.runStream`, für Workflow-Runs und deren Schritte. |

Jeder Versionsbereich wird gegen echte Framework-Releases getestet — an beiden Enden, als ES-Modul und als CommonJS, bei jedem CI-Lauf.

Das Mapping entspricht dem Python SDK, sodass dasselbe Programm in beiden Sprachen denselben Baum zeichnet. Ein Konstrukt ist nur dann ein **Agent**, wenn es eine eigene LLM-Entscheidungsschleife besitzt — ein Graph- oder Chain-Run, ein AI SDK `generateText`/`streamText`-Aufruf, ein Mastra-Agent, ein LlamaIndex-Agenten-Run. Ein LangGraph-Knoten oder ein Workflow-Schritt ist ein **Hook** (`hook_triggered`/`hook_completed`), kein verschachtelter Agent. Modellaufrufe sind `model_request`/`model_response`-Paare mit Token-Zählern; Tool-Calls tragen die eigene Tool-Call-ID des Modells. Ein Fehler wird einmal aufgezeichnet, beim Event, bei dem er aufgetreten ist.

Ein Adapter, der sich nicht installieren lässt, wird protokolliert und übersprungen; die anderen werden trotzdem installiert, da ein defektes LlamaIndex nicht zu Lasten von LangGraph gehen soll.

<Note>
  `instrument()` ohne Argument erkennt ein Framework daran, ob es sich **auflösen** lässt, nicht daran, ob es bereits importiert wurde — Node bietet kein Äquivalent zu Pythons `sys.modules` für ES-Module. Ein installiertes, aber nicht verwendetes Framework wird importiert und gepatcht. Den gewünschten Framework-Namen angeben, wenn das relevant ist.
</Note>

<Note>
  Die meisten dieser Frameworks liefern sowohl einen ES-Modul-Build als auch einen CommonJS-Build, die Node als zwei unabhängige Kopien lädt. Die Adapter patchen die Kopie, die die Anwendung lädt (sowie die CommonJS-Kopie, falls bereits `require`d), sodass beide Modulsysteme funktionieren. Ein Framework, das von esbuild oder webpack **in das eigene Ausgabebundle gepackt** wurde, ist nicht erreichbar — dort die Aufrufstellen-Helfer verwenden: `langchainHandler()`, `telemetry()`, `wrapTool()`.
</Note>

### LangChain ohne Patching

```ts
import { langchainHandler } from "@failproofai/sdk/langchain";
await graph.invoke(input, { callbacks: [langchainHandler()] });
```

Der Handler funktioniert mit oder ohne `instrument()` und zeichnet nichts doppelt auf. `instrument("langchain")` akzeptiert `sessionId`, `captureContent`, `includeChains`, `graphCallbacks` und `captureLimit`, wie der Python-Adapter; `metadata: { failproofai_sdk_session_id }` bei einem Aufruf wählt die Session für diese Ausführung.

### Vercel AI SDK

Das AI SDK exportiert einfache Funktionen aus einem ES-Modul, und ein ES-Modul-Namespace ist laut Spezifikation unveränderlich — es gibt keine Stelle zum Patchen. Es werden die Erweiterungspunkte genutzt, die das SDK selbst dokumentiert:

```ts
import { telemetry } from "@failproofai/sdk/ai";

const { text } = await generateText({
  model,
  prompt,
  experimental_telemetry: telemetry({ functionId: "answer-question" }),
  // on ai 7, `telemetry: telemetry({ … })` — the same object, the new name
});
```

Das ist die vollständige Integration: ein Agent-Span, ein Modell-Request/Response-Paar pro Schritt mit Token-Zählern und jeder Tool-Call. Eine Aufrufstelle funktioniert auf jeder Major-Version — `ai` 4–6 liest den mitgeführten Tracer, `ai` 7 die Telemetrie-Integration.

`instrument("ai")` macht dasselbe prozessweit **auf `ai` 7**: jeden Aufruf, über die globale Telemetrie-Integrationsliste des AI SDK, die additiv ist und niemandem etwas wegnimmt.

**Auf `ai` 4–6 zeichnet `instrument("ai")` allein nichts auf und gibt einmal eine entsprechende Warnung aus.** Der einzige prozessweite Hook dieser Major-Versionen ist der globale OpenTelemetry-Tracer-Provider — ein einzelner Slot, den OpenTelemetry nach der Vergabe nicht mehr herausgibt. Den eigenen Provider zu registrieren würde ein späteres `NodeSDK.start()` beim Start stillschweigend abweisen und HTTP-/Datenbankspans an einen Tracer senden, der nichts exportiert. `telemetry()` an der Aufrufstelle oder `wrapModel` dort verwenden. Läuft im Prozess kein eigenes OpenTelemetry, mit `instrument("ai", { registerGlobalTracer: true })` opt-in: dann werden alle Aufrufe mit `experimental_telemetry: { isEnabled: true }` aufgezeichnet, und der Slot wird nur belegt, wenn er noch frei ist. `registerGlobalTracer: false` behält das Standardverhalten bei und unterdrückt die Warnung.

Wer das Modell lieber einmal einwickeln möchte: `wrapModel` sieht nur Modellaufrufe, da Tool-Calls oberhalb der Modell-Ebene stattfinden. Ein eingewickeltes Modell, das ohne umgebenden Kontext aufgerufen wird, wird als eigener Run aufgezeichnet. Ein gestreamter Aufruf schließt, wie der Stream endet — `stop_reason: "cancelled"`, wenn der Consumer abbricht, `"error"` mit dem Fehler bei einem teilweisen Fehlschlag:

```ts
import { wrapModel } from "@failproofai/sdk/ai";
const model = await wrapModel(openai("gpt-4o"));
```

Beides gleichzeitig zu verwenden ist in Ordnung: die Middleware erkennt, dass der Aufruf bereits aufgezeichnet wird, und tritt zurück — jeder Aufruf wird genau einmal aufgezeichnet.

`functionId` benennt den Agent-Span. Niedrige Kardinalität anstreben — der Wert landet in `agent_id`, der primären Dashboard-Facette.

### Next.js

`next build` bündelt standardmäßig die Server-Abhängigkeiten, und ein ins Build gepacktes Framework ist für `instrument()` unerreichbar. Die Konfiguration einmal wrappen und `instrument()` aus Nexts Startup-Hook aufrufen:

```ts
// next.config.ts
import { withFailproofai } from "@failproofai/sdk/next";
export default withFailproofai({ /* your config */ });
```

```ts
// instrumentation.ts
export async function register() {
  if (process.env.NEXT_RUNTIME !== "nodejs") return;
  const failproofai = await import("@failproofai/sdk");
  await failproofai.instrument();
}
```

`withFailproofai` fügt LangChain, Mastra, LlamaIndex und das SDK selbst zu `serverExternalPackages` hinzu und behält dabei die eigene Liste. Ohne das gibt `instrument()` einmal pro nicht erreichbarem Framework eine Warnung aus statt still zu scheitern; wer die Pakete selbst auflistet, setzt `FAILPROOFAI_NEXT_EXTERNALS=1`. Das Vercel AI SDK und die Aufrufstellen-Helfer funktionieren in jedem Fall. Eine Edge-Route erhält einen No-Op-Build: das SDK importieren ist sicher und zeichnet nichts auf.

### Token-Zähler bei gestreamten Aufrufen

OpenAI-kompatible APIs melden die Nutzung bei einem Stream nur, wenn der Client es anfordert. LangChain und das Vercel AI SDK fordern das an; für LlamaIndex `additionalChatOptions: { stream_options: { include_usage: true } }` an das `OpenAI`-LLM übergeben, und für Mastra das Modell mit aktivierter Nutzungsmessung erstellen (zum Beispiel `createOpenAICompatible({ includeUsage: true })`). Andernfalls enthalten gestreamte Modellaufrufe keine Token-Zähler.

### Laufzeitumgebungen

Node ≥ 20.9, Bun und Deno — jedes Framework, als ES-Modul und als CommonJS, wird auf jeder dieser Umgebungen gegen Nodes Trace getestet. Das SDK läuft neben dem `failproofaid`-Daemon, der die geschriebenen Daten versendet.

## Eigener Agent — kein Framework

Für eine selbst geschriebene Agentenschleife oder ein Framework ohne Adapter. Die Events werden mit derselben API emittiert, die die Adapter intern verwenden — der Trace hat damit dieselbe Form und Qualität.

Die Organisation des Agenten muss nicht bekannt sein. Jeder handgebaute Agent hat bereits drei Stellen, unabhängig davon, wie seine Funktionen heißen, und diese drei bilden die gesamte Integration:

| Stelle | Was hinzuzufügen ist | Emittiert |
| --- | --- | --- |
| Wo **ein Run** beginnt und endet | `failproofai.agent("name", { goal }, async () => …)` | `agent_start` / `agent_end` |
| Die **eine Funktion, die das Modell aufruft** | `event.modelRequest` davor, `event.modelResponse` danach — beide Hälften, auch bei Fehler | ein Paar pro Modell-Runde |
| Die **eine Funktion, die Tools ausführt** | `failproofai.toolCall(name, { toolCallId, input }, () => run())` | `tool_use` / `tool_result` |

```ts
async function callModel(messages) {
  const requestId = randomUUID();
  const started = Date.now();
  failproofai.event.modelRequest({ model: MODEL, requestId, messages });
  try {
    const reply = await client.chat.completions.create({ model: MODEL, messages, tools });
    failproofai.event.modelResponse({
      model: reply.model, requestId, stopReason: reply.choices[0].finish_reason,
      inputTokens: reply.usage?.prompt_tokens, outputTokens: reply.usage?.completion_tokens,
      duration_ms: Date.now() - started,
    });
    return reply.choices[0].message;
  } catch (error) {
    failproofai.event.modelResponse({ model: MODEL, requestId, stopReason: "error",
      error: String(error), duration_ms: Date.now() - started });
    throw error;
  }
}

async function dispatch(call) {
  const input = JSON.parse(call.function.arguments);
  return failproofai.toolCall(call.function.name, { toolCallId: call.id, input },
    () => runTool(call.function.name, input));
}

await failproofai.agent("inventory", { goal: question }, async () => {
  for (;;) {
    const message = await callModel(messages);
    if (!message.tool_calls?.length) return message.content;
    for (const call of message.tool_calls) await dispatch(call);
  }
});
```

Identität ist ambient: alles innerhalb von `agent()` landet in der Session dieses Runs ohne eine ID zu übergeben, und nichts anderes im Programm ändert sich — einschließlich dessen, was der Agent bereits in seine eigene Datenbank schreibt.

- **Ein Service oder ein Worker:** die eigene Request- oder Job-ID als `sessionId` übergeben, damit eine Session im Dashboard und der Datensatz in den eigenen Logs oder in der Datenbank denselben String teilen.
- **Sub-Agenten:** `agent()`-Aufrufe verschachteln. Der innere tritt der Session mit dem äußeren als `parent_id` bei.
- **Die Paare emittieren.** Ein `modelRequest` ohne `modelResponse` ist ein Span, den das Dashboard als ewig laufend anzeigt — daher das `catch`.

[`sdk/typescript/examples/research-agent.ts`](https://github.com/FailproofAI/failproofai/blob/main/sdk/typescript/examples/research-agent.ts) im Repository ist die vollständige, ausführbare Version: eine echte OpenAI-Tool-Schleife, genau so instrumentiert, bei jedem Commit in CI als ES-Modul und als CommonJS ausgeführt.

## Auswertungen

```ts
import { Evaluator, EvalResult, Score } from "@failproofai/sdk/evaluator";

export const app = new Evaluator({ name: "my-evals", version: "1" });

app.eval("tool_success_rate", { version: "1" }, (session) => {
  const results = session.eventsOfType("tool_result");
  const failures = results.filter((event) => event.payload.error != null).length;
  return new EvalResult({
    score: new Score(results.length === 0 ? 1 : 1 - failures / results.length),
    reasoning: `${failures} of ${results.length} tool calls failed`,
  });
});
```

## Was das SDK dem Prozess nicht antut

| | |
| --- | --- |
| **Die Agentenschleife blockieren** | Events werden in eine In-Memory-Queue geschrieben; ein Timer persistiert sie. Der Timer ist `unref`'d, sodass das Importieren dieses Pakets das Beenden eines Skripts nie verhindert. |
| **Unbegrenzt wachsen** | Die Queue ist sowohl nach Anzahl *als auch* nach gemessenen Bytes begrenzt. Wird eine Grenze überschritten, werden die ältesten Events verworfen und eine Warnung ausgegeben — ein Telemetrie-Ausfall darf kein OOM-Kill werden. |
| **Den Prozess beenden** | Ein nicht kodierbarer Event wird einzeln verworfen, nicht der umgebende Batch. Ein werfender Getter, eine zirkuläre Referenz, ein `BigInt`, ein einzelnes Surrogat: jedes wird behandelt statt propagiert. |
| **Einen halb geschriebenen Batch hinterlassen** | Inhalt wird vor einem atomaren Umbenennen `fsync`'t, das Verzeichnis danach, und ein fehlgeschlagener Schreibvorgang bereinigt seine temporäre Datei. |
| **Transkripte lesbar lassen** | Batches haben `0600`-Rechte in einem `0700`-Verzeichnis. Sie enthalten Ziele, Prompts, Tool-Argumente und Tool-Ausgaben. |
| **Zugangsdaten versenden** | API-Schlüssel, Tokens, JWTs, Bearer-Header und secret-artige Zuweisungen werden redigiert, bevor die Bytes auf die Festplatte gelangen. Der Daemon redigiert erneut vor dem Upload. |
