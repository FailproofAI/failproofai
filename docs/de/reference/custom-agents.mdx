Python 3.11 oder neuer. Keine Laufzeitabhängigkeiten. Nutzen Sie ein Framework? [LangChain, CrewAI, LlamaIndex und Pydantic AI](/de/start/integrations) instrumentieren sich selbst mit einem einzigen Aufruf.

<Note>
  Es gibt auch ein **TypeScript SDK**, und beide schreiben dieselben Events in denselben Spool. Eine Flotte mit Node-Agenten und Python-Agenten erzeugt einen einzigen Satz von Sessions, nicht zwei. Wählen Sie pro Service, nicht pro Unternehmen.
</Note>

## Installation

```bash
pip install failproofai-sdk
```

Das Paket wird als `failproofai-sdk` installiert und in Python als `failproofai_sdk` importiert. Framework-Extras wie `failproofai-sdk[langgraph]` installieren das Framework selbst; die Adapter werden immer im Basis-Wheel mitgeliefert.

## Konfiguration

### OpenTelemetry-Spans (opt-in)

Installieren Sie `opentelemetry-sdk` separat und hängen Sie dann den optionalen Exporter an:

```python
import failproofai_sdk
from opentelemetry.sdk.trace import TracerProvider

provider = TracerProvider()
failproofai_sdk.instrument("otel", provider=provider)
with provider.get_tracer("my-agent").start_as_current_span(
    "agent", attributes={"gen_ai.operation.name": "invoke_agent"}
):
    pass
provider.force_flush()
```

Das Setup verwendet Ihren registrierten Provider, wenn Sie `provider` weglassen, und erstellt nur dann einen neuen, wenn keiner registriert ist. Sie können `failproofai_sdk.OtelSpanExporter()` auch direkt an Ihren eigenen Span-Prozessor übergeben. Andere Exporter bleiben unverändert.

Der verbundene FailproofAI-Daemon übernimmt die Auslieferung der Exporte; das SDK benötigt kein Netzwerk-Setup, keinen Schlüssel und keinen lokalen Listener. Ein Administrator muss [OpenTelemetry-Ingest](/de/agenteye/opentelemetry) aktivieren. Ein bloßes `instrument()` aktiviert OTEL nie. `uninstrument("otel")` deaktiviert nur den eigenen Prozessor. Ihre Instrumentierung steuert die Inhaltserfassung. Leeren Sie den Provider vor dem Beenden. Das SDK deklariert weiterhin null harte Laufzeitabhängigkeiten und importiert OpenTelemetry nur bei Bedarf.

```python
import failproofai_sdk

failproofai_sdk.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| Argument | Funktion |
| --- | --- |
| `environment` | Die Bezeichnung für jedes Event – `production`, `staging`, `prod-eu`. Standard ist `dev`. |
| `flush_interval` | Wie oft der Hintergrund-Thread auf die Festplatte schreibt, in Sekunden. Standard ist `0.5`. |
| `base_dir` | Wohin geschrieben wird. Standard ist der Spool des Daemons, was in der Regel das Richtige ist. |

Stattdessen per Umgebungsvariable setzen:

| Variable | Funktion |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | Setzt `environment` ohne Code-Änderung, wenn die Bezeichnung zur Deployment-Umgebung statt zur App gehört. Ein `configure()`-Argument hat Vorrang. |
| `FAILPROOFAI_HOME` | Verschiebt das Failproof AI-Stammverzeichnis, das den Spool enthält. |
| `FAILPROOFAI_SDK_STRICT` | `1` lässt Instrumentierungsfehler auslösen statt sie zu protokollieren. |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | `1` lässt ein Framework-Kompatibilitätsproblem auslösen statt zu warnen und weiterzumachen. |

<Warning>
  **Keine Kommas in `environment`.** Ingest teilt dieses Feld an Kommas auf, um Filter zu erstellen, und überspringt jeden Event, dessen Bezeichnung eines enthält – so verschwindet ein ganzer Lauf lautlos. Schreiben Sie `prod-eu`, nicht `prod,eu`.

  `configure(environment="prod,eu")` löst sofort eine Ausnahme aus. `AGENTEYE_ENVIRONMENT` kann keine Ausnahme auslösen – niemand ruft Sie zurück – daher wird einmalig gewarnt und auf `dev` zurückgefallen.
</Warning>

Events werden im Speicher eingereiht und alle `flush_interval` Sekunden im Hintergrund geschrieben, mit einem abschließenden Flush beim Beenden des Interpreters. Ein abrupt beendeter Prozess verliert alles, was noch nicht geschrieben wurde.

## Identität

Jeder Event gehört zu einer Session und einem Agenten. **Die Scopes füllen beides aus**, sodass Sie sie selten manuell übergeben müssen:

```python
with failproofai_sdk.session():
    with failproofai_sdk.agent("planner"):
        failproofai_sdk.event.tool_use(tool_name="search", tool_call_id="c1")
```

`session_id` oder `agent_id` explizit zu übergeben funktioniert weiterhin und hat Vorrang. Wenn weder gebunden noch übergeben, löst der Aufruf `TypeError` aus, anstatt einen Event zu senden, den Cloud stillschweigend verwerfen würde.

<Note>
  Identität wird über Kontextvariablen weitergegeben. Sie folgt `asyncio`-Tasks automatisch, aber **nicht** neuen Threads – umschließen Sie einen Worker mit `failproofai_sdk.propagate()`, sonst landen seine Events ohne Zuordnung.
</Note>

## Event-Katalog

Fünfzehn Methoden. Die meisten kommen in **Paaren** – Sie rufen den Öffner auf, dann den Schließer, und das SDK misst den Zeitabstand.

| | Öffnet | Schließt |
| --- | --- | --- |
| **Agenten** | `agent_start` | `agent_end` |
| | `agent_pause` | `agent_resume` |
| **Modelle** | `model_request` | `model_response` |
| **Tools** | `tool_use` | `tool_result` |
| **Hooks** | `hook_triggered` | `hook_completed` |
| **Menschen** | `human_wait` | `human_input` |

Drei stehen allein: `error`, `human_pause`, `human_interrupt`.

<Accordion title="Alle Felder, pro Methode" icon="table">

Jede Methode akzeptiert auch `session_id` und `agent_id`, die die Scopes für Sie ausfüllen. Alles, was als `None` belassen wird, wird weggelassen statt als JSON `null` gesendet, und jede Methode gibt `None` zurück.

| Methode | Erforderlich | Optional |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools`, `request_id` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role`, `request_id`, `duration_ms` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

</Accordion>

<Warning>
  Um einen Lauf als fehlgeschlagen zu markieren, muss `outcome` eines der folgenden Werte sein: `failed`, `error`, `timeout` oder `rejected`. Alles andere – einschließlich des ähnlichen `"failure"` – gilt als Erfolg.
</Warning>

## Paarung und Dauer

**Eine Regel: Geben Sie dem schließenden Event dieselbe ID wie dem öffnenden.** Das ist, was sie verknüpft und was dem SDK ermöglicht, den Zeitabstand zu messen.

| Paar | Abgeglichen anhand |
| --- | --- |
| `tool_use` → `tool_result` | `tool_call_id` |
| `hook_triggered` → `hook_completed` | `hook_id` |
| `agent_pause` → `agent_resume` | `pause_id` |
| `human_wait` → `human_input` | `input_id` |
| `model_request` → `model_response` | `request_id` |

**Übergeben Sie `duration_ms` nicht selbst.** Das SDK misst es, und die Übergabe löst `ValueError` aus.

Die einzige Ausnahme ist `model_response`, wo nur Sie die tatsächliche Provider-Latenz kennen. Übergeben Sie eine ganze Zahl in Millisekunden – ein Float löst eine Ausnahme aus, da die Spalte ein 32-Bit-Integer ist und sonst leer bliebe.

<Accordion title="Sonderfälle" icon="circle-help">

- **IDs müssen nur pro Art und pro Session eindeutig sein.** Ein Tool-Aufruf und ein Hook können dieselbe ID teilen; zwei gleichzeitig laufende Sessions können dieselben IDs wiederverwenden, ohne zu kollidieren.
- **Sie sind nicht an einen Agenten gebunden.** Ein Paar, das unter einem Agenten geöffnet und unter einem anderen geschlossen wird, wird trotzdem abgeglichen – was der Normalfall in Multi-Agenten-Code ist.
- **`request_id` ist optional, aber empfohlen.** Ohne sie werden Model-Events in der Reihenfolge ihres Eintreffens gepaart, sodass zwei gleichzeitige Aufrufe im selben Agenten falsch gepaart werden können.
- **Ein über Prozesse hinweg aufgeteiltes Paar** wird in Cloud trotzdem abgeglichen, aber das SDK kann es nicht messen – kein Prozess hat beide Hälften gesehen.
- **Maximal 10.000 Öffner warten gleichzeitig auf einen Schließer.** Darüber hinaus wird der älteste verworfen, sodass ein Leck nicht unbegrenzt wachsen kann.

</Accordion>

## Eigene Felder

Jedes zusätzliche Schlüsselwort, das Sie übergeben, wird mit dem Event gespeichert:

```python
failproofai_sdk.event.tool_use(
    tool_name="search", tool_call_id="c1",
    fw_tenant="acme", fw_region="eu-west-1",     # eigene Felder
)
```

Bevorzugen Sie JSON-Typen, wenn Sie sie später abfragen möchten. Alles andere – eine UUID, ein Datetime, ein `Decimal`, ein Set, Bytes, ein Modellobjekt – wird als Zeichenkette gespeichert.

<Warning>
  **Versehen Sie Ihre Feldnamen mit einem Präfix.** Extras werden zuletzt angewendet, sodass ein Feld namens `model`, `tool_name` oder `outcome` das echte stillschweigend überschreibt. Die Framework-Adapter verwenden `fw_`; tun Sie dasselbe, und es kann keine Kollision entstehen.

  Das ist auch der Grund, warum ein falsch geschriebenes optionales Feld nie einen Fehler auslöst – es wird einfach zu einem neuen benutzerdefinierten Feld. Wenn ein Standardfeld in Cloud fehlt, prüfen Sie zuerst die Schreibweise.
</Warning>

Diese fünf Namen sind reserviert und werden direkt abgelehnt: `timestamp`, `session_id`, `agent_id`, `type`, `environment`.

## Auslieferung und Überprüfung

<Tabs>
  <Tab title="Dashboard">
    Überprüfen Sie unter **Observe → Events**, ob `agent_start` als erstes und `agent_end` als letztes vorhanden ist. Öffnen Sie dann **Observe → Sessions** und bestätigen Sie, dass Model-, Tool-, Human-, Hook- und Error-Events in der gewünschten Reihenfolge erscheinen. Verwenden Sie die Session-ID als primären Troubleshooting-Schlüssel.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

Wenn Cloud leer ist, prüfen Sie `$FAILPROOFAI_HOME/custom-agents/events`, andernfalls `~/.failproofai/custom-agents/events`. JSONL-Dateien belegen die SDK-Emission; ein wachsender Spool deutet auf ein Daemon-Konfigurations- oder Auslieferungsproblem hin, während ein leerer Spool auf Instrumentierung oder Prozess-Lebensdauer hindeutet.

<Note>
  Prüfen Sie den Spool nur, wenn der Daemon gestoppt ist. Während er läuft, sammelt und löscht er jeden Stapel innerhalb von Millisekunden, sodass eine Verzeichnisauflistung mit dem Collector konkurriert und weit weniger Events anzeigt, als tatsächlich emittiert wurden.
</Note>

## Fehler in einer benutzerdefinierten Laufzeitumgebung verhindern

Verwenden Sie Audit-Befunde und verknüpfte Traces, um die unsichere Aktion, erforderliche Nachweise und die beabsichtigte Reaktion zu definieren. Eine benutzerdefinierte Durchsetzungsintegration muss die Aktion vor der Ausführung offenlegen, ihre strukturierte Eingabe an die Policy-Engine übergeben und die resultierende allow-, instruct- oder deny-Entscheidung anwenden.

[Kontaktieren Sie Failproof AI](mailto:support@befailproof.ai) und wir helfen Ihnen dabei, die Modell-, Tool- und Lebenszyklus-Grenzen Ihrer Laufzeitumgebung auf Policy-Hooks abzubilden und die Integration gemeinsam mit Ihnen zu validieren.
