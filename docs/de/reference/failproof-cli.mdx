Installiere die lokale CLI mit `npm install -g failproofai`. Ohne Argumente aufgerufen öffnet sie das lokale Richtlinien-Dashboard.

Das Paket erfordert Node.js 20.9 oder neuer. Bun 1.3 oder neuer wird für Entwicklungs- und Quellinstallationen unterstützt. `failproofai configure` und `failproofai setup` sind Aliase für `failproofai config`. `failproofai policy`, `failproofai pack` und `failproofai p` sind allesamt Schreibweisen von `failproofai policies` — Packs und einzelne Richtlinien waren drei Befehle für eine Idee und sind nun einer. Die älteren Schreibweisen funktionieren weiterhin, mit zwei Ausnahmen: `pack list <source>` heißt jetzt `policies show <source>`, und `pack build` heißt jetzt `publish`.

## Eine Maschine einrichten

Installiere die CLI, dann lies den Maschinenschlüssel in die Shell ein. `read -s` nimmt ihn über eine Eingabeaufforderung entgegen, die keine Ausgabe anzeigt, sodass er nie in einem Befehl erscheint:

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

Dann richte die Maschine ein und wähle, was sie durchsetzt:

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` umfasst die gesamte Einrichtung: Es installiert den `failproofaid`-Dienst (einmalig als Root — im Terminal fragt es nach deinem sudo-Passwort und fragt erneut, falls dieses vor Abschluss der Einrichtung abgelaufen ist; ohne Terminal verwendet es `sudo -n` und fragt nie nach), verdrahtet Hooks in jede gefundene Agent-CLI und verbindet sich mit Cloud. Ohne Terminal — CI, ein Container, ein Agent, der es steuert — wendet es an, anstatt zu fragen, und beendet sich mit 1, wenn etwas, das es tun sollte, nicht stattgefunden hat.

Im Terminal startet der Schritt **Mit Cloud verbinden** auf einer Maschine, die noch nicht verbunden ist, sofort mit der **Anmeldung bei FailproofAI Cloud**; drücke Tab für die anderen Optionen, **API-Schlüssel einfügen** oder **Open Source verwenden**. Die Anmeldung öffnet einen Link — oder gibt ihn über SSH oder ohne Display aus, zum Öffnen auf einem beliebigen Gerät —, wo du dich anmeldest oder registrierst, eine Organisation auswählst oder erstellst und die Maschine autorisierst; das Terminal nimmt die Genehmigung selbstständig entgegen und zeigt an, wer sie genehmigt hat und für welche Organisation. Der Schlüssel wird erst gemint, wenn die Einrichtung abgeschlossen ist, nachdem der Daemon installiert wurde. Auf einer Maschine, die bereits mit einem funktionierenden Schlüssel verbunden ist, ist der Schritt ein Menü mit **Aktuelle Verbindung beibehalten** an erster Stelle, sodass die erneute Ausführung der Einrichtung nie selbst einen Browser öffnet; ein gespeicherter Schlüssel, der nicht mehr funktioniert, startet sofort wieder mit der Anmeldung und erklärt den Grund. Eine erneute Anmeldung erstellt einen neuen Schlüssel und lässt den alten funktionieren, bis du ihn widerrufst. Eine Cloud von vor der Browser-Anmeldung sagt dies und bietet die anderen Optionen an.

Es wählt **keine** Richtlinien. Das ist die Aufgabe des zweiten Befehls, und ohne ihn setzt eine frisch konfigurierte Maschine nichts außer dem immer aktiven Schutz durch.

Bevorzuge die Umgebungsvariable gegenüber `--token`: Ein Befehlszeilenargument ist über `ps` für jeden Benutzer auf dem System lesbar. Das ist alles, wovor die Variable schützt — ein in einen Befehl eingetippter Schlüssel, einschließlich `export`, landet trotzdem in der Shell-History, weshalb er oben mit `read -s` eingelesen wird. In CI setzt du ihn aus dem Secret-Store und hältst Shell-Tracing (`set -x`) deaktiviert, sonst gibt der Trace ihn aus.

<Warning>
  `--connect <url>` meldet eine Maschine an, die **bereits eingerichtet** ist. Es kehrt zurück, sobald die Anmeldung erfolgreich ist — es installiert weder den Daemon noch verdrahtet es Hooks. Verwende das normale `failproofai config` (oder `failproofai config --token <key>`) auf einer Maschine, die noch nicht eingerichtet wurde, sonst erscheint sie als verbunden, während sie nichts erfasst oder durchsetzt.
</Warning>

Führe `failproofai` ohne Argumente aus, um das lokale Richtlinien-Dashboard zu öffnen.

| Befehl | Ergebnis |
| --- | --- |
| `failproofai config` | Maschine einrichten: Agents, Daemon und Cloud — über den Browser anmelden, einen Schlüssel einfügen oder Open Source bleiben. Jeder Agent auf der Maschine erhält außerdem eine kleine `failproofai`-Skill, die ihn auf die [FailproofAI skills](https://github.com/FailproofAI/skills) online verweist |
| `failproofai config --token <key>` | Einrichten und verbinden in einem Schritt, ohne Rückfragen. Ein Schlüssel mit `jev:evaluate` aktiviert auch [Jev über FailproofAI Cloud](/de/reference/jev-cloud) im Beobachtungsmodus, es sei denn, eine `jev.json` existiert bereits oder `--no-transcripts` wurde angegeben |
| `failproofai config --connect <url>` | Eine Maschine anmelden, die **bereits** eingerichtet ist — kein Daemon, keine Hooks |
| `failproofai config --status` | Verbindungs-, Daemon-, Liefer- und Pausenzustand anzeigen |
| `failproofai policies` | Eingebaute, benutzerdefinierte, konventionsbasierte, Pack- und Cloud-verwaltete Richtlinien auflisten |
| `failproofai policies --install` | Hooks in Agent-CLIs verdrahten. Aktiviert selbst keine Richtlinie |
| `failproofai policies add <name>` | Eine Richtlinie aktivieren — eine eingebaute oder `<pack-id>:<name>` aus einem installierten Pack |
| `failproofai policies remove <name>` | Eine Richtlinie deaktivieren, gleiche Benennung |
| `failproofai policies --uninstall` | Richtlinien deaktivieren oder Harness-Hooks entfernen |
| `failproofai policies show <owner>/<repo>` | Was ein Pack enthält, aus seinem Manifest gelesen, bevor du ihn verwendest |
| `failproofai policies show <owner>/<repo> --releases` | Jede veröffentlichte Version und welche hier vorhanden ist |
| `failproofai policies add <source>` | Ein Richtlinien-Pack aus einem GitHub-Release installieren; ohne Tag wird das neueste genommen und angepinnt |
| `failproofai publish` | Eigene Richtlinien als Pack veröffentlichen; `--init` erstellt eine Ausgangsdatei, und `--min-cli-version <version>` legt die älteste CLI fest, die es installieren darf ([Jev prüft in einem Pack](/de/policies/publish-a-pack#jev-checks-in-a-pack)) |
| `failproofai policies remove <publisher/name>` | Ein Pack deinstallieren |
| `failproofai audit` | Lokale Agent-History scannen und die lokale Audit-Ansicht öffnen |
| `failproofai audit --schedule [days] --email <address>` | Wiederkehrende lokale Scans planen und deren Ergebnisse per E-Mail senden |
| `failproofai audit --status` | Berichtsadresse, Intervall und nächsten geplanten Scan anzeigen |
| `failproofai audit --no-schedule` | Wiederkehrende Scans stoppen ohne Audit-History zu löschen |
| `failproofai harness list` | Zusätzliche Erfassungspfade auflisten |
| `failproofai otel status` | Optionale [OpenTelemetry-Berichterstattung](/de/reference/otel) prüfen |
| `failproofai jev --url <url> --key-stdin` | Jev in einem Schritt einrichten; der Anbieter wird aus dem Host der URL entnommen |
| `failproofai jev setup --provider <kind> --key-stdin` | [Jev](/de/reference/jev-providers) Tool-Aufrufe über deinen eigenen Endpunkt und Schlüssel beurteilen lassen |
| `failproofai jev setup --provider failproofai` | Jev Tool-Aufrufe [über FailproofAI Cloud](/de/reference/jev-cloud) mit dem Cloud-Schlüssel dieser Maschine beurteilen lassen |
| `failproofai jev setup --mode <m>` | Jevs Modus wechseln: `enforce`, `observe` oder `off` (behält die Konfiguration, fragt Jev nicht mehr) |
| `failproofai jev status` | Jev-Konfiguration, Berechtigungen und aktuelle Fallbacks anzeigen; nie den Schlüssel |
| `failproofai jev test` | Eine Live-Jev-Anfrage senden und Latenz und Version anzeigen; beendet sich mit 1, wenn die Antwort für Hooks zu spät oder falsch ist |
| `failproofai jev models` | Modell-IDs auflisten, die `GET <base>/models` für einen Endpunkt zurückgibt |
| `failproofai jev remove` | Jev deaktivieren; Hooks führen die Regex-Richtlinien genau wie zuvor aus |
| `failproofai flush --wait` | Den aktuellen Ereignis-Spool liefern |
| `failproofai backfill --since 30d` | Zuvor übertragene History erneut einlesen |
| `failproofai config --pause [duration]` | Eine lokale Sitzung für standardmäßig 30 Minuten pausieren, bis zu 8 Stunden |
| `failproofai config --resume` | Eine pausierte lokale Sitzung fortsetzen; `--all` hinzufügen, um alle Pausen zu beenden |
| `failproofai update` | Paketmigrationen abschließen und den Daemon aktualisieren |
| `failproofai migrate --dry-run` | Ausstehende Home-Layout-Migrationen in der Vorschau ansehen oder ausführen |
| `failproofai uninstall` | Hooks, die `failproofai`-Skill und den Daemon entfernen, bevor das Paket entfernt wird |
| `failproofai --version` | Installierte Paketversion ausgeben |
| `failproofai --help` | Befehle und allgemeine Verwendung anzeigen |

## Konfigurationsflags

| Flag | Verwendung |
| --- | --- |
| `--token <key>` | Nicht-interaktiv einrichten und verbinden; wird auch aus `FAILPROOFAI_CLOUD_TOKEN` gelesen |
| `--url <url>` | Verbindung zu einem anderen Ziel als `app.befailproof.ai`; wird auch aus `FAILPROOFAI_CLOUD_URL` gelesen |
| `--connect <url>` | Nur anmelden, auf einer bereits eingerichteten Maschine. Überspringt den Daemon und alle Hooks |
| `--machine-id <id>` | Die stabile Maschinen-ID festlegen |
| `--machine-label <name>` | Eine Maschine umbenennen, die **bereits verbunden** ist. Allein führt es nie ein Setup aus, daher nach `failproofai config` angeben, nicht während |
| `--no-transcripts` | Entscheidungen ohne Transkriptinhalt senden und Cloud Jev nicht aktivieren, das jeden geprüften Tool-Aufruf und die aktuelle Eingabeaufforderung senden würde; eine laufende `jev.json`, die Jev über FailproofAI Cloud betreibt, wird entfernt |
| `--disconnect` | Cloud-Richtlinien-Pulls und Ereignislieferung stoppen. Entfernt auch den Cloud-Jev-Schlüssel und eine `jev.json`, die FailproofAI Cloud benennt; deine eigene Jev-Einrichtung bleibt erhalten |
| `--status` | Aktuellen Maschinenzustand anzeigen |
| `--pause [duration]` | Die neueste Sitzung im aktuellen Verzeichnis pausieren; akzeptiert Sekunden, Minuten oder Stunden, Standardwert 30 Minuten |
| `--resume` | Eine passende Pause vorzeitig beenden |
| `--session <id>` | Eine explizite Sitzung für Pause oder Fortsetzen angeben |
| `--all` | Mit `--resume` alle aktiven Pausen beenden |

Lokale Pausen unterbrechen eingebaute, benutzerdefinierte, konventionsbasierte und Pack-Richtlinien für eine Sitzung. Sie laufen immer ab und deaktivieren keine Cloud-verwalteten Richtlinien. `block-failproofai-commands` — das immer aktiv ist und selbst nicht deaktiviert oder pausiert werden kann — verhindert, dass ein instrumentierter Agent diesen Ausweichweg selbst nutzt.

## Richtlinienflags

| Flag | Verwendung |
| --- | --- |
| `--install`, `-i` | Harness-Hooks installieren. Nachfolgende Namen aktivieren diese Richtlinien; ohne Namen keine Richtlinienänderungen |
| `--uninstall`, `-u` | Richtlinien deaktivieren oder Hooks entfernen |
| `--cli <names...>` | Einen oder mehrere unterstützte Harnesses gezielt ansprechen |
| `--scope user\|project\|local\|all` | Den Konfigurationsbereich auswählen; `all` ist für die Deinstallation |
| `--beta` | Beta-Richtlinien einschließen |
| `--custom`, `-c <path>` | Eine benutzerdefinierte Richtliniendatei validieren und laden; wiederholbar |

## Liefer- und Wartungsflags

| Befehl | Flags |
| --- | --- |
| `backfill` | `--since <30d\|6m\|YYYY-MM-DD>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` |

`failproofai update` sollte nach `npm install -g failproofai@latest` ausgeführt werden; es führt Home-Layout-Migrationen durch, installiert das passende Daemon-Binary und startet den Dienst neu. Anschließend verschiebt es jedes Hermes-Profil, das bereits FailproofAI verwendet, auf das verknüpfte native Plugin und gibt eine Zeile pro Profil aus. `--no-daemon` überspringt den Daemon-Schritt. `update` beendet sich mit einem Fehlercode, wenn der Daemon nicht ersetzt werden konnte, eine Migration fehlgeschlagen ist oder ein Hermes-Profil nicht migriert werden konnte (beispielsweise weil der laufende Daemon das native Plugin nicht bedienen kann, in diesem Fall bleiben seine Shell-Hooks bestehen).

## Harness-Pfade

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

Unterstützte Harness-Namen sind `claude`, `codex`, `copilot`, `cursor`, `opencode`, `pi`, `hermes`, `openclaw`, `factory`, `devin`, `antigravity` und `goose`.

Labels erstellen Namensräume für abgeleitete Agent-IDs, wenn zwei Wurzelverzeichnisse Kopien desselben Projekts enthalten. Überlappende Wurzeln und doppelte Labels werden abgelehnt, um doppelte Erfassung oder Cursor-Beschädigung zu verhindern. Konfigurationsänderungen an Extra-Pfaden werden ohne Daemon-Neustart neu geladen.

Container-Umgebungen können datei-konfigurierte Extra-Pfade durch eine kommagetrennte Variable namens `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` ersetzen, zum Beispiel:

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## Umgebungsvariablen

Verwende Konfigurationsdateien für dauerhaftes Maschinenverhalten. Umgebungsvariablen sind am nützlichsten für Container, Tests und einzelne Prozesse.

| Variable | Verwendung |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | Der Cloud-Schlüssel, anstelle von `--token`. Dies ist vorzuziehen: Ein Argument ist über `ps` für jeden Benutzer lesbar. Mit `read -s` oder aus einem CI-Secret-Store setzen, nie durch Eintippen des Schlüssels in einen Befehl, der so oder so in der Shell-History landet |
| `FAILPROOFAI_CLOUD_URL` | Die Cloud-URL, anstelle von `--url`. Dieselbe Variable, die der Daemon liest |
| `FAILPROOFAI_HOME` | Das vollständige `~/.failproofai`-Layout verschieben |
| `FAILPROOFAI_LOG_LEVEL` | Lokale Protokollierungsausführlichkeit festlegen |
| `FAILPROOFAI_HOOK_LOG_FILE` | Hook-Diagnosedaten in eine ausgewählte Datei schreiben |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | Anonyme Telemetrie für diesen Prozess deaktivieren |
| `FAILPROOFAI_NO_FIRST_RUN=1` | Interaktive Ersteinrichtung überspringen |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | Lokales Audit nach der Einrichtung überspringen |
| `FAILPROOFAI_LLM_BASE_URL` | Den von LLM-Richtlinien verwendeten OpenAI-kompatiblen Endpunkt überschreiben |
| `FAILPROOFAI_LLM_API_KEY` | Den von LLM-Richtlinien verwendeten API-Schlüssel bereitstellen |
| `FAILPROOFAI_LLM_MODEL` | Das von LLM-Richtlinien verwendete Modell auswählen |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | Das Laden benutzerdefinierter Richtlinienmodule zeitlich begrenzen |
| `FAILPROOFAI_NO_DOWNLOAD=1` | Abrufen von Packs und Daemon-Binaries ablehnen; was installiert ist, setzt weiterhin durch |
| `FAILPROOFAI_PACK_BASE_URL` | Packs von einem Mirror statt von `github.com` abrufen |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | Konfigurierte Extra-Erfassungspfade für einen Harness ersetzen |
| `NO_COLOR` | Farbige Terminalausgabe deaktivieren |

Agent-spezifische Home-Variablen wie `CLAUDE_PROJECTS_PATH`, `CURSOR_HOME`, `HERMES_HOME` und `OPENCLAW_HOME` überschreiben, wo Failproof AI lokale Sitzungen für diesen Harness findet.

## Eine Maschine sicher pausieren oder entfernen

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

Eine lokale Sitzungspause deaktiviert keine Cloud-verwalteten Richtlinien. Stelle Cloud-Deployments über den Cloud-Enforcement-Workflow wieder her, wenn das Rollout selbst das Problem ist.

Bevor du das npm-Paket entfernst, entferne die installierten Hooks und den Daemon:

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

Führe `failproofai <command> --help` für versionsspezifische Details aus.

<Warning>
  Führe `failproofai uninstall` vor `npm rm -g failproofai` aus; npm entfernt weder installierte Agent-Hooks noch die `failproofai`-Skill noch den Daemon-Dienst.
</Warning>
