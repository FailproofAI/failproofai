Installiere die lokale CLI mit `npm install -g failproofai`. Starte sie ohne Argumente, um das lokale Richtlinien-Dashboard zu öffnen.

Das Paket erfordert Node.js 20.9 oder neuer. Bun 1.3 oder neuer wird für Entwicklung und Quell-Installationen unterstützt. `failproofai configure` und `failproofai setup` sind Aliase für `failproofai config`. `failproofai policy`, `failproofai pack` und `failproofai p` sind allesamt Schreibweisen für `failproofai policies` — Packs und einzelne Richtlinien waren drei Befehle für eine Idee und sind jetzt einer. Die älteren Schreibweisen funktionieren weiterhin, mit zwei Ausnahmen: `pack list <source>` heißt jetzt `policies show <source>`, und `pack build` heißt jetzt `publish`.

## Eine Maschine einrichten

Installiere die CLI, dann lese den Maschinenschlüssel in die Shell ein. `read -s` nimmt ihn an einer Eingabeaufforderung entgegen, die keine Zeichen anzeigt, sodass er nie in einem Befehl erscheint:

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

Richte dann die Maschine ein und lege fest, was sie durchsetzt:

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` übernimmt die gesamte Einrichtung: Es installiert den `failproofaid`-Dienst (einmalig als Root — in einem Terminal fragt es nach dem sudo-Passwort und erneut, wenn dieses vor Abschluss der Einrichtung abgelaufen ist; ohne Terminal verwendet es `sudo -n` und fragt nie nach), verdrahtet Hooks in jede gefundene Agent-CLI und stellt eine Verbindung zur Cloud her. Ohne Terminal — CI, ein Container, ein Agent, der es steuert — wendet es Einstellungen an, anstatt zu fragen, und beendet sich mit 1, wenn irgendetwas, was ausgeführt werden sollte, nicht stattgefunden hat.

In einem Terminal startet der Schritt **Mit Cloud verbinden** auf einer noch nicht verbundenen Maschine sofort den **Anmeldevorgang bei FailproofAI Cloud**; drücke Tab für die anderen Optionen, **API-Schlüssel einfügen** oder **Open Source verwenden**. Die Anmeldung öffnet einen Link — oder gibt ihn über SSH oder ohne Display aus, um ihn auf einem beliebigen Gerät zu öffnen — wo du dich registrierst oder anmeldest, eine Organisation auswählst oder erstellst und die Maschine autorisierst; das Terminal erkennt die Genehmigung selbständig und zeigt an, wer genehmigt hat und für welche Organisation. Der Schlüssel wird erst erstellt, wenn die Einrichtung abgeschlossen ist, nachdem der Daemon installiert wurde. Auf einer Maschine, die bereits mit einem funktionierenden Schlüssel verbunden ist, zeigt dieser Schritt ein Menü mit **Aktuelle Verbindung beibehalten** zuerst, sodass ein erneutes Ausführen der Einrichtung nie von selbst einen Browser öffnet; ein gespeicherter Schlüssel, der nicht mehr funktioniert, startet sofort wieder den Anmeldevorgang und erklärt warum. Eine erneute Anmeldung erstellt einen neuen Schlüssel und lässt den alten funktionieren, bis du ihn widerrufst. Eine Cloud ohne Browser-Anmeldung zeigt dies an und bietet die anderen Optionen.

Sie wählt **keine** Richtlinien aus. Das ist die Aufgabe des zweiten Befehls, und ohne ihn setzt eine frisch konfigurierte Maschine nichts durch außer dem immer aktiven Schutz.

Bevorzuge die Umgebungsvariable gegenüber `--token`: Ein Befehlszeilenargument ist über `ps` von jedem Benutzer auf der Maschine lesbar. Das ist alles, wovor die Variable schützt — ein in einen Befehl eingetippter Schlüssel, `export` eingeschlossen, landet trotzdem in der Shell-Historie, weshalb er oben mit `read -s` eingelesen wird. In CI sollte er aus dem Secret-Store gesetzt werden, und Shell-Tracing (`set -x`) sollte deaktiviert sein, da der Trace ihn andernfalls ausgibt.

<Warning>
  `--connect <url>` meldet eine Maschine an, die **bereits eingerichtet** ist. Es kehrt zurück, sobald die Anmeldung erfolgreich ist — es installiert weder den Daemon noch verdrahtet es Hooks. Verwende das normale `failproofai config` (oder `failproofai config --token <key>`) auf einer Maschine, die noch nicht eingerichtet wurde, da sie sonst als verbunden angezeigt wird, aber nichts erfasst oder durchsetzt.
</Warning>

Starte `failproofai` ohne Argumente, um das lokale Richtlinien-Dashboard zu öffnen.

| Befehl | Ergebnis |
| --- | --- |
| `failproofai config` | Maschine einrichten: Agents, Daemon und Cloud — über den Browser anmelden, einen Schlüssel einfügen oder Open Source bleiben. Jeder Agent auf der Maschine erhält außerdem eine kleine `failproofai`-Fähigkeit, die ihn auf die [FailproofAI skills](https://github.com/FailproofAI/skills) online verweist |
| `failproofai config --token <key>` | Einrichten und verbinden in einem Schritt, ohne Rückfragen. Ein Schlüssel mit `jev:evaluate` aktiviert außerdem [Jev über FailproofAI Cloud](/de/reference/jev-cloud) im Beobachtungsmodus, es sei denn, es existiert bereits eine `jev.json` oder `--no-transcripts` ist angegeben |
| `failproofai config --connect <url>` | Eine Maschine anmelden, die **bereits** eingerichtet ist — kein Daemon, keine Hooks |
| `failproofai config --status` | Verbindungs-, Daemon-, Zustellungs- und Pause-Status anzeigen |
| `failproofai policies` | Eingebaute, benutzerdefinierte, konventionelle, Pack- und Cloud-verwaltete Richtlinien auflisten |
| `failproofai policies --install` | Hooks in Agent-CLIs verdrahten. Aktiviert allein keine Richtlinie |
| `failproofai policies add <name>` | Eine Richtlinie aktivieren — eine eingebaute oder `<pack-id>:<name>` aus einem installierten Pack |
| `failproofai policies remove <name>` | Eine Richtlinie deaktivieren, gleiche Benennung |
| `failproofai policies --uninstall` | Richtlinien deaktivieren oder Harness-Hooks entfernen |
| `failproofai policies show <owner>/<repo>` | Was ein Pack enthält, aus seinem Manifest gelesen, bevor man ihn übernimmt |
| `failproofai policies show <owner>/<repo> --releases` | Alle veröffentlichten Versionen und welche installiert ist |
| `failproofai policies add <source>` | Ein Richtlinien-Pack von einem GitHub-Release installieren; ohne Tag wird das neueste genommen und angeheftet |
| `failproofai publish` | Eigene Richtlinien als Pack veröffentlichen; `--init` erstellt eine Vorlage, und `--min-cli-version <version>` legt die älteste CLI-Version fest, die ihn installieren darf ([Jev checks in a pack](/de/policies/publish-a-pack#jev-checks-in-a-pack)) |
| `failproofai policies remove <publisher/name>` | Ein Pack deinstallieren |
| `failproofai audit` | Lokale Agent-Historie scannen und die lokale Audit-Ansicht öffnen |
| `failproofai audit --schedule [days] --email <address>` | Wiederkehrende lokale Scans planen und deren Ergebnisse per E-Mail senden |
| `failproofai audit --status` | Berichtsadresse, Intervall und nächsten geplanten Scan anzeigen |
| `failproofai audit --no-schedule` | Wiederkehrende Scans stoppen, ohne die Audit-Historie zu löschen |
| `failproofai harness list` | Zusätzliche Erfassungspfade auflisten |
| `failproofai otel status` | Optionale [OpenTelemetry-Berichterstattung](/de/reference/otel) prüfen |
| `failproofai jev --url <url> --key-stdin` | Jev in einem Schritt einrichten; der Anbieter wird aus dem Host der URL entnommen |
| `failproofai jev setup --provider <kind> --key-stdin` | [Jev](/de/reference/jev-providers) Tool-Aufrufe über den eigenen Endpunkt und Schlüssel beurteilen lassen |
| `failproofai jev setup --provider failproofai` | Jev Tool-Aufrufe [über FailproofAI Cloud](/de/reference/jev-cloud) mit dem Cloud-Schlüssel dieser Maschine beurteilen lassen |
| `failproofai jev setup --mode <m>` | Jev-Modus wechseln: `enforce`, `observe` oder `off` (behält die Konfiguration, fragt Jev nicht mehr) |
| `failproofai jev status` | Jev-Konfiguration, Berechtigungen und aktuelle Fallbacks anzeigen; nie den Schlüssel |
| `failproofai jev test` | Eine Live-Jev-Anfrage senden und Latenz und Version anzeigen; beendet sich mit 1, wenn die Antwort für Hooks zu spät oder falsch ist |
| `failproofai jev models` | Die Modell-IDs auflisten, die `GET <base>/models` für einen Endpunkt liefert |
| `failproofai jev remove` | Jev deaktivieren; Hooks führen die Regex-Richtlinien genau wie zuvor aus |
| `failproofai flush --wait` | Den aktuellen Event-Spool zustellen |
| `failproofai backfill --since 30d` | Zuvor verarbeitete Historie erneut einlesen |
| `failproofai config --pause [duration]` | Eine lokale Sitzung standardmäßig 30 Minuten lang pausieren, bis zu 8 Stunden |
| `failproofai config --resume` | Eine pausierte lokale Sitzung fortsetzen; `--all` hinzufügen, um alle Pausen aufzuheben |
| `failproofai update` | Paket-Migrationen abschließen und den Daemon aktualisieren |
| `failproofai migrate --dry-run` | Ausstehende Home-Layout-Migrationen in der Vorschau anzeigen oder ausführen |
| `failproofai uninstall` | Hooks, die `failproofai`-Fähigkeit und den Daemon entfernen, bevor das Paket entfernt wird |
| `failproofai --version` | Installierte Paketversion ausgeben |
| `failproofai --help` | Befehle und allgemeine Nutzung anzeigen |
| `failproofai help <command>` | Optionen und Beispiele eines Befehls anzeigen, wie `failproofai <command> --help` |

## Konfigurations-Flags

| Flag | Verwendung |
| --- | --- |
| `--token <key>` | Nicht-interaktiv einrichten und verbinden; auch aus `FAILPROOFAI_CLOUD_TOKEN` gelesen |
| `--oss` | Open Source ohne Cloud-Verbindung verwenden; eine bestehende Verbindung bleibt unverändert |
| `--agents <a,b>` | Diese Agents oder `all` ohne Rückfrage tracen |
| `--url <url>` | Verbindung zu einem anderen Ort als `app.befailproof.ai`; auch aus `FAILPROOFAI_CLOUD_URL` gelesen |
| `--connect <url>` | Nur anmelden, auf einer bereits eingerichteten Maschine. Überspringt Daemon und alle Hooks |
| `--machine-id <id>` | Maschinen-ID für `--connect`; standardmäßig eine stabile ID |
| `--machine-label <name>` | Allein: eine **bereits verbundene** Maschine umbenennen; führt nie Setup aus. Mit `--token`: unter diesem Namen verbinden; ein nur in `FAILPROOFAI_CLOUD_TOKEN` gesetzter Schlüssel reicht nicht aus, da `--machine-label` ohne `--token` eine Umbenennung ist. Mit `--oss` oder `--agents`: benennt eine bereits verbundene Maschine um und wird vor dem Setup auf einer nicht verbundenen abgelehnt: `--oss` verbindet sich nie, und `--agents` benötigt einen Schlüssel oder eine interaktive Cloud-Anmeldung zum Verbinden |
| `--no-transcripts` | Entscheidungen ohne Transkriptinhalt senden und Cloud Jev nicht aktivieren, das jeden geprüften Tool-Aufruf und die aktuelle Eingabeaufforderung senden würde; eine `jev.json`, die Jev über FailproofAI Cloud ausführt, wird entfernt |
| `--disconnect` | Cloud-Richtlinien-Pulls und Event-Zustellung stoppen. Entfernt außerdem den Cloud-Jev-Schlüssel und eine `jev.json`, die FailproofAI Cloud benennt; das eigene Jev-Setup bleibt bestehen |
| `--status` | Aktuellen Maschinenstatus anzeigen |
| `--pause [duration]` | Die neueste Sitzung im aktuellen Verzeichnis pausieren; akzeptiert Sekunden, Minuten oder Stunden, standardmäßig 30 Minuten |
| `--resume` | Eine passende Pause vorzeitig beenden |
| `--session <id>` | Eine explizite Sitzung für Pause oder Fortsetzen auswählen |
| `--all` | Mit `--resume`: alle aktiven Pausen beenden |

Lokale Pausen unterbrechen eingebaute, benutzerdefinierte, konventionelle und Pack-Richtlinien für eine Sitzung. Sie laufen immer ab, höchstens 8 Stunden nach der ersten Pause in einem Lauf, und sie deaktivieren keine Cloud-verwalteten Richtlinien oder `block-failproofai-commands`, das immer aktiv ist und selbst nicht deaktiviert oder pausiert werden kann. Dieser Schutz verweigert die direkten Wege, auf denen ein instrumentierter Agent sich selbst pausieren könnte: `failproofai config --pause` ausführen oder die Pause-Datei unter `~/.failproofai/state/sessions/` schreiben. Er liest Befehle, nicht was ein Skript tut, wenn es ausgeführt wird, sodass ein vom Agent geschriebenes und dann ausgeführtes Skript dennoch denselben Zustand erreichen kann. Eine Pause-Datei wird auf ein begrenztes Ablaufdatum und einen Startpunkt nicht mehr als eine Minute in der Zukunft geprüft, nicht darauf, wer sie geschrieben hat.

## Richtlinien-Flags

| Flag | Verwendung |
| --- | --- |
| `--install`, `-i` | Harness-Hooks installieren. Nachfolgende Namen aktivieren diese Richtlinien; ohne Angabe werden keine Richtlinien geändert |
| `--uninstall`, `-u` | Richtlinien deaktivieren oder Hooks entfernen |
| `--cli <names...>` | Einen oder mehrere unterstützte Harnesses auswählen |
| `--scope user\|project\|local\|all` | Den Konfigurationsbereich wählen; `all` ist für die Deinstallation |
| `--beta` | Beta-Richtlinien einschließen |
| `--custom`, `-c <path>` | Mit `--install`: eine benutzerdefinierte Richtliniendatei validieren und laden; wiederholbar. `--uninstall -c` entfernt alle benutzerdefinierten Richtliniendateien |
| `--policy`, `--only <a,b>` | Nur diese Richtlinien aus einem Pack installieren |
| `--category <x,y>` | Nur diese Kategorien aus einem Pack installieren |
| `--all` | Alle Richtlinien auflisten; bei einem Pack: alles installieren |
| `--releases` | Mit `show`: Releases eines Packs und welches installiert ist auflisten |

## Zustellungs- und Wartungs-Flags

| Befehl | Flags |
| --- | --- |
| `backfill` | `--since <30d\|6m\|1y\|YYYY-MM-DD>`, `--agents <a,b>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` (`-y`) |

### Backfill pro Harness

`backfill` sendet auf einer mit Cloud verbundenen Maschine bereits gelesene Historie erneut. `--since` legt das Zeitfenster für die meisten Harnesses fest, mit zwei Ausnahmen:

- **Goose, OpenCode und Devin** senden ihre gesamte Historie, unabhängig von `--since`: ihre Historie liegt in einer Datenbank, die der Collector ohne Zeitfenster liest, sodass `--dry-run` sie als alle Sitzungen meldet.
- **Hermes**-Historie wird durch `backfill` nicht erneut gesendet.

`failproofai update` sollte nach `npm install -g failproofai@latest` ausgeführt werden; es führt Home-Layout-Migrationen durch, installiert das passende Daemon-Binary und startet den Dienst neu. Anschließend verschiebt es jedes Hermes-Profil, das bereits FailproofAI verwendet, zum verknüpften nativen Plugin und gibt eine Zeile pro Profil aus. `--no-daemon` überspringt den Daemon-Schritt. `update` beendet sich mit einem Fehlercode, wenn der Daemon nicht ersetzt werden konnte, eine Migration fehlgeschlagen ist oder ein Hermes-Profil nicht migriert werden konnte (z. B. weil der laufende Daemon das native Plugin nicht bedienen kann — in diesem Fall bleiben seine Shell-Hooks bestehen).

## Harness-Pfade

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

Unterstützte Harness-Namen sind `claude`, `codex`, `copilot`, `cursor`, `opencode`, `pi`, `hermes`, `openclaw`, `factory`, `devin`, `antigravity` und `goose`.

Labels vergeben Namensräume für abgeleitete Agent-IDs, wenn zwei Wurzelverzeichnisse Kopien desselben Projekts enthalten. Überlappende Wurzeln und doppelte Labels werden abgelehnt, um doppelte Erfassung oder Cursor-Korruption zu verhindern. Die Konfiguration zusätzlicher Pfade wird ohne Daemon-Neustart neu geladen.

Container-Umgebungen können datei-konfigurierte zusätzliche Pfade durch eine kommagetrennte Variable namens `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` ersetzen, zum Beispiel:

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## Umgebungsvariablen

Verwende Konfigurationsdateien für dauerhaftes Maschinenverhalten. Umgebungsvariablen sind am nützlichsten für Container, Tests und einzelne Prozesse.

| Variable | Verwendung |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | Der Cloud-Schlüssel, anstelle von `--token`. Bevorzuge dies: Ein Argument ist über `ps` von jedem Benutzer lesbar. Mit `read -s` oder aus einem CI-Secret-Store setzen, nie durch Eintippen des Schlüssels in einen Befehl, da er so oder so in der Shell-Historie landet |
| `FAILPROOFAI_CLOUD_URL` | Die Cloud-URL, anstelle von `--url`. Dieselbe Variable, die der Daemon liest |
| `FAILPROOFAI_HOME` | Das gesamte `~/.failproofai`-Layout verschieben |
| `FAILPROOFAI_LOG_LEVEL` | Lokale Logging-Ausführlichkeit festlegen |
| `FAILPROOFAI_HOOK_LOG_FILE` | Hook-Diagnosen in eine ausgewählte Datei schreiben |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | Anonyme Telemetrie für diesen Prozess deaktivieren |
| `FAILPROOFAI_NO_FIRST_RUN=1` | Interaktives Erststart-Setup überspringen |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | Lokales Audit nach der Einrichtung überspringen |
| `FAILPROOFAI_LLM_BASE_URL` | Den von LLM-Richtlinien verwendeten OpenAI-kompatiblen Endpunkt überschreiben |
| `FAILPROOFAI_LLM_API_KEY` | Den von LLM-Richtlinien verwendeten API-Schlüssel bereitstellen |
| `FAILPROOFAI_LLM_MODEL` | Das von LLM-Richtlinien verwendete Modell auswählen |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | Das Laden benutzerdefinierter Richtlinienmodule zeitlich begrenzen |
| `FAILPROOFAI_NO_DOWNLOAD=1` | Abrufen von Packs und Daemon-Binaries ablehnen; was installiert ist, setzt weiterhin durch |
| `FAILPROOFAI_PACK_BASE_URL` | Packs von einem Mirror statt von `github.com` abrufen |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | Konfigurierte zusätzliche Erfassungspfade für einen Harness ersetzen |
| `NO_COLOR` | Farbige Terminal-Ausgabe deaktivieren |

Agent-spezifische Home-Variablen wie `CLAUDE_PROJECTS_PATH`, `CURSOR_HOME`, `HERMES_HOME` und `OPENCLAW_HOME` überschreiben, wo Failproof AI lokale Sitzungen für diesen Harness erkennt.

## Eine Maschine sicher pausieren oder entfernen

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

Eine lokale Sitzungspause deaktiviert keine Cloud-verwalteten Richtlinien. Stelle Cloud-Deployments über **fix → deploy policies** in der Cloud wieder her, wenn der Rollout selbst das Problem ist.

Bevor das npm-Paket entfernt wird, installierte Hooks und den Daemon entfernen:

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

Führe `failproofai <command> --help` für versionsspezifische Details aus.

<Warning>
  Führe `failproofai uninstall` vor `npm rm -g failproofai` aus; npm entfernt weder installierte Agent-Hooks noch die `failproofai`-Fähigkeit oder den Daemon-Dienst.
</Warning>
