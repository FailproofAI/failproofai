Ein Harness ist die Umgebung, in der Ihr Agent tatsächlich ausgeführt wird. Failproof AI unterstützt zwölf davon, in zwei Klassen:

- **Coding CLIs** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Chat- und Assistent-Gateways** (2) — Hermes (Slack, Telegram, Cron), OpenClaw (selbst gehosteter Assistent)

Dieselben Richtlinien und dieselbe Sitzungshistorie gelten unabhängig davon, in welchem Harness ein Agent läuft. Eine Adapterschicht bildet die nativen Ereignisnamen, Werkzeugnamen und Werkzeug-Eingabefelder jedes Harness auf 29 kanonische Ereignisse ab, bevor eine Richtlinie ausgeführt wird.

Ein Agent, der in **keinem** der zwölf läuft, wird direkt mit dem [Python SDK](/de/reference/custom-agents) instrumentiert. Das ist ein anderer Vertrag, und es lohnt sich, ihn klar zu benennen: Das SDK liefert Tracing, Sitzungen, Auswertungen und Audits — **es setzt Richtlinien nicht eigenständig durch.** Um eine unsichere Aktion vor ihrer Ausführung zu blockieren, ist ein Enforcement-Hook an der Tool-Grenze Ihrer Laufzeitumgebung erforderlich; [kontaktieren Sie uns](mailto:support@befailproof.ai) und wir werden es abbilden.

| Harness | Unterstützte Hook-Bereiche |
| --- | --- |
| Claude Code | User, project, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | User, project |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | User, project |
| Hermes, OpenClaw | User |

Jede Integration normalisiert ihre nativen Hook-Ereignisnamen, Werkzeugnamen und Werkzeug-Eingabefelder, bevor Richtlinien ausgeführt werden. Eine Richtlinie kann nur auf Ereignisse reagieren, die der Harness bereitstellt; testen Sie das End-of-Turn- und Instruktionsverhalten auf dem genauen Harness und der Version, die Sie einsetzen.

## Enforcement-Fähigkeit

„Block" bedeutet, dass das zurückgegebene Urteil des aktuellen Adapters vom genannten Harness verarbeitet wird. Post-Tool-Blocking kann das dem Modell angezeigte Ergebnis ersetzen, aber einen bereits eingetretenen Werkzeug-Seiteneffekt nicht rückgängig machen.

| Harness | Verifizierte Blocking-Ereignisse | Nur-Beobachtungs- oder nicht-blockierende Einschränkungen |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact` und mehrere Task/Config-Ereignisse | `PostToolUse`, Sitzungs-Lebenszyklus, Benachrichtigungen und Post-Failure-Ereignisse sind beobachtend. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Post-Tool-Blocking ersetzt das Ergebnis nach der Ausführung; Sitzungsstart- und Compact-Ereignisse sind im aktuellen Adapter beobachtend. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Post-Tool-Blocking ersetzt das Ergebnis nach der Ausführung; Sitzungs- und Benachrichtigungsereignisse sind beobachtend. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` und Sitzungsereignisse sind beobachtend. |
| OpenCode | `PreToolUse` | Post-Tool- und Lebenszyklus-Ereignisse sind beobachtend; die aktuelle Stop-Behandlung ist eine Anleitung für einen späteren Turn, kein verifiziertes Gate. |
| Pi | `PreToolUse`, `UserPromptSubmit` | Post-Tool- und Lebenszyklus-Ereignisse sind beobachtend; Stop-Anleitung gilt für einen späteren Turn. |
| Hermes | `PreToolUse` | `deny()` blockiert. `instruct()` stoppt den Aufruf nicht: er wird ausgeführt, und die Anleitung wird an den Anfang seines Ergebnisses gesetzt. Post-Tool-, Sitzungs- und Subagent-Stop-Urteile sind keine Gates. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Post-Tool-, Sitzungs-, Subagent-Stop- und Compaction-Ereignisse sind beobachtend. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Post-Tool- und Subagent-Stop-Urteile sind beobachtend. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, bedingtes `PermissionRequest` | Permission-Hooks laufen nicht in jedem Permission-Modus; Post-Tool- und Sitzungsereignisse sind beobachtend. |
| Antigravity CLI | `PreToolUse`, `Stop` | User-Prompt- und Post-Tool-Urteile sind beobachtend; Prompt-Instruktionen können dennoch injiziert werden. |
| Goose | `PreToolUse` | User-Prompt-, Post-Tool- und Sitzungsereignisse sind beobachtend. Ein nativer blockierender Stop-Hook existiert upstream, wird aber vom aktuellen Adapter nicht installiert. |

Fähigkeiten sind versionsabhängig. Führen Sie nach einem Upgrade einer Agent-CLI erneut Tests durch, insbesondere wenn eine Richtlinie auf Prompt-, Stop-, Permission- oder Post-Tool-Verhalten statt auf das übliche Pre-Tool-Gate angewiesen ist.

### Hermes-nativer Plugin

Hermes wird über ein profillocales natives Plugin statt über einen Shell-Befehl integriert. Bei der Installation wird jedes Standard- und benannte Hermes-Profil unter `plugins/failproofai` mit dem im npm-Paket mitgelieferten Plugin verknüpft (eine Kopie, wenn kein Symlink erstellt werden kann), in der `config.yaml` des jeweiligen Profils aktiviert und ausschließlich veraltete FailproofAI Shell-Hook-Einträge migriert. Da das Plugin verknüpft ist, aktualisiert `npm install -g failproofai@latest` es ohne Neuinstallation. Dadurch wird ein Prozess-Spawn bei jedem Hook vermieden. Das Plugin unterstützt Hermes 0.20.0 und höher.

Veraltete Shell-Hooks (installiert mit Version 1.0.5 und früher) überprüfen **keine** Hermes-Cron-Jobs: Jeder Cron-Lauf erstellt seinen eigenen Hook-Bereich, dem das native Plugin beitritt, was `config.yaml`-Shell-Hooks nicht tun. `failproofai update` migriert jedes Profil, das bereits FailproofAI verwendet, zum verknüpften Plugin. Wenn der laufende Daemon das Plugin nicht bedienen kann, belässt `update` die Shell-Hooks und beendet sich mit einem Fehlercode; führen Sie `failproofai config` aus, um den Daemon zu aktualisieren, und anschließend erneut `failproofai update`. Cron-Jobs laden das Plugin beim nächsten Lauf; starten Sie laufende Gateways und interaktive Sitzungen neu, damit es dort geladen wird.

Auf Hermes blockiert `deny()` den Aufruf, `instruct()` hingegen nicht: Der Aufruf wird ausgeführt, und die Anleitung wird an den Anfang seines Ergebnisses gesetzt — als erster Schlüssel `failproof_policy_reminder` eines JSON-Ergebnisses oder als führende `[FailproofAI policy reminder (...)]`-Zeile —, sodass das Modell sie zusammen mit der Ausgabe liest und Skripte, die das Ergebnis parsen, weiterhin funktionieren. Der Hinweis einer Richtlinie wird einmal pro Turn angezeigt und bei umfangreichen Ergebnissen kurz gehalten. Verwenden Sie `deny()`, wenn eine Aktion keinesfalls stattfinden darf: `instruct()` stoppt die Aktion nicht mehr vorab. Werkzeugaufrufe aus einem `execute_code`-Skript setzen ihren Hinweis auf das `execute_code`-Ergebnis, das das Modell liest; die eigene Kopie des Ergebnisses im Skript bleibt unberührt. Das Modell wird angewiesen, einen Hinweis in seinen Antworten niemals zu zitieren.

Ein Hermes-Build ohne Plugin-Middleware greift darauf zurück, den passenden Aufruf einmalig mit „FailproofAI policy guidance" zurückzuhalten; die nächste Modellantwort kann ihn wiederholen oder dieselbe Arbeit mit einem anderen Werkzeug durchführen, ohne erneut zurückgehalten zu werden.

Werkzeugnamen werden über Hermes-Versionen hinweg abgeglichen: `process_manage`, `cronjob_manage` und `todo_list` (Hermes 0.21) werden wie `process`, `cronjob` und `todo` (Hermes 0.20) behandelt. Jedes Mal, wenn Hermes das Plugin lädt, schreibt es `heartbeat.json` in das Verzeichnis `plugin-data/agent-plugin-failproofai-5296f299/` des Profils und zeichnet die Hermes-Version, den Pfad und die Version des Plugins sowie die von Hermes akzeptierten Hooks auf. Führen Sie `failproofai config --status` aus, um ein deaktiviertes, unvollständiges, dupliziertes oder neu unkonfiguriertes Profil zu erkennen, oder eines, das noch veraltete Shell-Hooks verwendet (gemeldet als „Hermes cron jobs are not checked").

### OpenClaw-Plugin

OpenClaw lädt FailproofAI als In-Process-Gateway-Plugin, das in der `openclaw.json` jedes Profils registriert ist. Wie das Hermes-Plugin fragt es den lokalen `failproofaid`-Daemon für jedes Urteil über seinen Socket ab, benötigt also einen laufenden Daemon: Die Installation wird ohne einen solchen verweigert, und wenn der Daemon nicht antworten kann, werden Werkzeugaufrufe und Prompts blockiert und der Grund ins Gateway-Log geschrieben. Starten Sie nach `npm install -g failproofai@latest` das OpenClaw-Gateway neu, damit es das aktualisierte Plugin lädt.

### Codex-Hook-Vertrauen

Codex 0.129 und höher führt einen Hook aus `~/.codex/hooks.json` nur aus, nachdem Sie ihn im interaktiven `codex` genehmigt haben („Review hooks"); bis dahin überspringt jede Codex-Sitzung — einschließlich `codex exec` ohne Interaktion — ihn. Hooks in Codex' Systemkonfiguration, `/etc/codex/config.toml` unter Linux und macOS, laufen ohne diese Genehmigung.

Wenn `failproofai config` (oder `policies --install --cli codex` im User-Scope) sudo verwenden kann, schreibt es daher die Codex-Hooks in `/etc/codex/config.toml`, zwischen `# >>> failproofai managed hooks >>>` und `# <<< failproofai managed hooks <<<`, und lässt den Rest der Datei unverändert.

Diese Datei gilt für jeden Account auf der Maschine, sodass jeder darin enthaltene Hook `/opt/failproofai-codex/codex-hook` ausführt, ein kurzes Skript im Besitz von root. Das Skript übergibt das Ereignis für jeden Account, der die Hooks dort eingerichtet hat, an dessen eigenes failproofai und tut für alle anderen Accounts nichts. Ein anderer Account, der failproofais Codex-Hooks möchte, richtet sie für sich selbst ein.

Vor dem Schreiben des Blocks und bei jedem `failproofai update` prüft failproofai, dass `/etc/codex/config.toml` selbst, das Skript, alle übergeordneten Verzeichnisse sowie das verwendete `sh`, `id` und `cat` root gehören und von niemandem sonst beschreibbar sind, und dass das failproofai jedes Accounts diesem Account oder root gehört. Bei der Installation, wenn diese Prüfung fehlschlägt, verbleiben Ihre Hooks in `~/.codex/hooks.json`. Bei einem Update wird ein Skript, das die Prüfung nicht besteht, aus dem Block entfernt, und ein Account, dessen failproofai sie nicht besteht, wird aus dem Skript entfernt; führen Sie `failproofai config` erneut aus, sobald es behoben ist. `failproofai update` schreibt außerdem einen von einer früheren Version erstellten Block um, um das Skript zu verwenden, was sudo erfordert.

`failproofai uninstall` und das Deaktivieren von Codex in `failproofai config` entfernen Ihren Account wieder, und den Block, sobald kein Account mehr verbleibt.

Ohne sudo und unter Windows verbleiben die Hooks in `~/.codex/hooks.json`. `failproofai config` und `failproofai config --status` zählen Codex dann nicht als durchsetzend, bis die Hooks genehmigt sind, und zeigen an, wie das behoben werden kann: Führen Sie `failproofai config` erneut aus und erlauben Sie sudo, oder öffnen Sie `codex` einmal und genehmigen Sie die Hooks.

## Capture- und Richtlinien-Hooks installieren

<Tabs>
  <Tab title="Dashboard">
    1. Öffnen Sie **settings → api keys** und erstellen Sie einen Schlüssel mit `events:add` und `policies:pull`, benannt nach der Maschine oder Umgebung.
    2. Verbinden Sie auf der Zielmaschine die lokale CLI mit dem angezeigten Schlüssel und installieren Sie die Harness-Hooks.
    3. Starten Sie eine neue Agent-Sitzung und bestätigen Sie deren Hook- und Sitzungsereignisse unter **trace → live events**.
    4. Öffnen Sie **fix → activity** für dasselbe Zeitfenster und bestätigen Sie, dass eine Richtlinienentscheidung der Maschine zugeordnet ist.

    Die Verbindung beginnt mit einem Maschinenschlüssel. Stellen Sie sicher, dass er sowohl Ingestion- als auch Policy-Delivery-Berechtigungen enthält, bevor Sie sein Secret kopieren.

    ![Die neue API-Key-Schublade zum Erteilen von Ereigniserfassungs- und Richtlinienlieferungsberechtigungen.](/images/dashboard/key-create.png)

    Nach der Installation der Hooks sollte der Events-Stream neue Ereignisse von der verbundenen Maschine und Umgebung anzeigen.

    ![Der Live-Events-Stream zur Bestätigung, dass ein neu installierter Harness berichtet.](/images/dashboard/events-stream.png)

    Überprüfen Sie abschließend, dass Richtlinienentscheidungen derselben Maschine zugeordnet sind. Dies bestätigt, dass der Harness sowohl Richtlinienaktivitäten als auch Trace-Ereignisse meldet.

    ![Die Policy-Seite zur Überprüfung von Richtlinienentscheidungen eines neu verbundenen Harness.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Lesen Sie den Maschinenschlüssel in die Shell ein. `read -s` nimmt ihn an einer Eingabeaufforderung entgegen, die keine Ausgabe anzeigt, sodass er nie in einem Befehl oder in der Shell-History erscheint:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    Richten Sie dann die Maschine ein — dies verdrahtet Hooks für jeden erkannten Harness, installiert den Daemon und verbindet sich mit Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    Das Setup aktiviert keine Richtlinie von sich aus — dafür ist der zweite Befehl da.

    Oder geben Sie benannte Harnesses und einen Konfigurationsbereich an:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    Der Project-Scope bewahrt die Hook-Konfiguration bei einem Repository. Der User-Scope deckt die Arbeit über Repositories hinweg ab. Claude Code unterstützt zusätzlich den Local-Scope; die Unterstützung variiert je nach Harness, und die CLI lehnt nicht unterstützte Kombinationen ab.

    Überprüfen Sie die Maschine und ihre Ereignisse:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## Einen nicht standardmäßigen Sitzungspfad hinzufügen

<Tabs>
  <Tab title="Dashboard">
    Zusätzliche Pfade werden auf der Maschine registriert, nicht in Cloud. Öffnen Sie nach dem Hinzufügen eines Pfads **trace → sessions**, filtern Sie nach der Umgebung der Maschine und bestätigen Sie, dass Sitzungen aus dem neuen Pfad erscheinen. Öffnen Sie eine Sitzung und überprüfen Sie Agent, Harness und Ereignis-Zeitstempel, bevor Sie sie in einem Audit verwenden.

    ![Die Sitzungsliste gefiltert nach der Umgebung, die Daten vom zusätzlichen Capture-Pfad empfängt.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Fügen Sie einen Pfad mit einem optionalen Label hinzu und überprüfen Sie dann die konfigurierten Pfade:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Entfernen Sie einen Pfad mit `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  Führen Sie nach der Installation eine neue Sitzung aus. Überprüfen Sie sowohl den Live-Event-Stream als auch eine tatsächliche Richtlinienentscheidung, bevor Sie den Rollout ausweiten.
</Tip>
