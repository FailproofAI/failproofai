Ein Harness ist die Umgebung, in der ein Agent tatsächlich ausgeführt wird. Failproof AI unterstützt zwölf davon, in zwei Klassen:

- **Coding-CLIs** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Chat- und Assistent-Gateways** (2) — Hermes (Slack, Telegram, Cron), OpenClaw (selbst gehosteter Assistent)

Dieselben Richtlinien und dieselbe Sitzungshistorie gelten unabhängig davon, in welchem Harness ein Agent läuft. Eine Adapter-Schicht ordnet die nativen Ereignisnamen, Werkzeugnamen und Werkzeug-Eingabefelder jedes Harnesses 29 kanonischen Ereignissen zu, bevor eine Richtlinie ausgeführt wird.

Ein Agent, der in **keinem** der zwölf läuft, wird direkt mit dem [Python SDK](/de/reference/custom-agents) instrumentiert. Das ist ein anderer Vertrag, der klar benannt werden sollte: Das SDK liefert Tracing, Sitzungen, Auswertungen und Audits — **es erzwingt jedoch keine Richtlinien eigenständig.** Um eine unsichere Aktion zu blockieren, bevor sie ausgeführt wird, ist ein Enforcement-Hook an der Tool-Grenze Ihrer Laufzeitumgebung erforderlich. [Kontaktieren Sie uns](mailto:support@befailproof.ai), und wir werden es einrichten.

| Harness | Unterstützte Hook-Geltungsbereiche |
| --- | --- |
| Claude Code | User, project, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | User, project |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | User, project |
| Hermes, OpenClaw | User |

Jede Integration normalisiert ihre nativen Hook-Ereignisnamen, Werkzeugnamen und Werkzeug-Eingabefelder, bevor Richtlinien ausgeführt werden. Eine Richtlinie kann nur auf Ereignisse reagieren, die der Harness bereitstellt. Testen Sie das End-of-Turn- und Anweisungsverhalten auf dem genauen Harness und der Version, die Sie einsetzen.

## Durchsetzungsfähigkeit

„Blockieren" bedeutet, dass das vom aktuellen Adapter zurückgegebene Urteil vom genannten Harness verarbeitet wird. Post-Tool-Blockierung kann das dem Modell angezeigte Ergebnis ersetzen, kann jedoch keine Tool-Seiteneffekte rückgängig machen, die bereits eingetreten sind.

| Harness | Verifizierte blockierende Ereignisse | Nur-Beobachtungs- oder nicht-blockierende Einschränkungen |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact` und mehrere Task-/Konfigurations-Ereignisse | `PostToolUse`, Sitzungs-Lifecycle, Benachrichtigungen und Post-Failure-Ereignisse sind beobachtend. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Post-Tool-Blockierung ersetzt das Ergebnis nach der Ausführung; Sitzungsstart- und Compact-Ereignisse sind im aktuellen Adapter beobachtend. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Post-Tool-Blockierung ersetzt das Ergebnis nach der Ausführung; Sitzungs- und Benachrichtigungsereignisse sind beobachtend. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` und Sitzungsereignisse sind beobachtend. |
| OpenCode | `PreToolUse` | Post-Tool- und Lifecycle-Ereignisse sind beobachtend; die aktuelle Stop-Behandlung ist eine Anleitung für einen späteren Turn, kein verifiziertes Gate. |
| Pi | `PreToolUse`, `UserPromptSubmit` | Post-Tool- und Lifecycle-Ereignisse sind beobachtend; Stop-Anleitung gilt für einen späteren Turn. |
| Hermes | `PreToolUse` | `deny()` blockiert. `instruct()` stoppt den Aufruf nicht: Er wird ausgeführt, und die Anleitung wird am Anfang des Ergebnisses platziert. Post-Tool-, Sitzungs- und Subagent-Stop-Urteile sind keine Gates. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Post-Tool-, Sitzungs-, Subagent-Stop- und Compaction-Ereignisse sind beobachtend. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Post-Tool- und Subagent-Stop-Urteile sind beobachtend. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, bedingtes `PermissionRequest` | Permission-Hooks laufen nicht in jedem Permission-Modus; Post-Tool- und Sitzungsereignisse sind beobachtend. |
| Antigravity CLI | `PreToolUse`, `Stop` | User-Prompt- und Post-Tool-Urteile sind beobachtend; Prompt-Anweisungen können dennoch injiziert werden. |
| Goose | `PreToolUse` | User-Prompt-, Post-Tool- und Sitzungsereignisse sind beobachtend. Ein nativer blockierender Stop-Hook existiert im Upstream, wird jedoch vom aktuellen Adapter nicht installiert. |

Die Fähigkeiten sind versionsabhängig. Testen Sie nach dem Upgrade einer Agent-CLI erneut, insbesondere wenn eine Richtlinie auf Prompt-, Stop-, Permission- oder Post-Tool-Verhalten statt auf das gängige Pre-Tool-Gate angewiesen ist.

### Natives Hermes-Plugin

Hermes wird über ein profilweit natives Plugin statt über einen Shell-Befehl integriert. Die Installation verknüpft jedes Standard- und benannte Hermes-Profil's `plugins/failproofai` mit dem im npm-Paket enthaltenen Plugin (eine Kopie, wo kein Symlink erstellt werden kann), aktiviert es in der `config.yaml` dieses Profils und migriert nur veraltete FailproofAI Shell-Hook-Einträge. Da das Plugin verknüpft ist, aktualisiert `npm install -g failproofai@latest` es ohne Neuinstallation. Dies vermeidet das Erzeugen eines Prozesses bei jedem Hook. Das Plugin unterstützt Hermes 0.20.0 und höher.

Veraltete Shell-Hooks (installiert mit Version 1.0.5 und früher) prüfen **keine** Hermes-Cron-Jobs: Jeder Cron-Lauf erstellt seinen eigenen Hook-Geltungsbereich, dem das native Plugin beitritt, den `config.yaml`-Shell-Hooks jedoch nicht. `failproofai update` migriert jedes Profil, das bereits FailproofAI verwendet, zum verknüpften Plugin. Wenn der laufende Daemon das Plugin nicht bedienen kann, belässt `update` die Shell-Hooks und beendet sich mit einem Fehlercode. Führen Sie `failproofai config` aus, um den Daemon zu aktualisieren, und dann erneut `failproofai update`. Cron-Jobs laden das Plugin beim nächsten Lauf; starten Sie laufende Gateways und interaktive Sitzungen neu, um es dort zu laden.

In Hermes blockiert `deny()` den Aufruf, `instruct()` hingegen nicht: Der Aufruf wird ausgeführt, und die Anleitung wird am Anfang des Ergebnisses platziert — als erster Schlüssel `failproof_policy_reminder` eines JSON-Ergebnisses oder als führende `[FailproofAI policy reminder (...)]`-Zeile — sodass das Modell sie mit der Ausgabe liest und Skripte, die das Ergebnis parsen, weiterhin funktionieren. Die Erinnerung einer Richtlinie wird einmal pro Turn angezeigt und bei einem großen Ergebnis kurzgehalten. Verwenden Sie `deny()`, wenn eine Aktion überhaupt nicht stattfinden darf: `instruct()` stoppt die Aktion nicht mehr zuerst. Tool-Aufrufe aus einem `execute_code`-Skript platzieren ihre Erinnerung auf dem `execute_code`-Ergebnis, das das Modell liest; die eigene Kopie des Ergebnisses im Skript bleibt unverändert. Dem Modell wird mitgeteilt, eine Erinnerung niemals in seinen Antworten zu zitieren.

Ein Hermes-Build ohne Plugin-Middleware fällt darauf zurück, den passenden Aufruf einmal mit „FailproofAI policy guidance" zurückzuhalten; die nächste Modellantwort kann ihn wiederholen oder dieselbe Arbeit mit einem anderen Tool erledigen, ohne erneut zurückgehalten zu werden.

Tool-Namen werden über Hermes-Versionen hinweg abgeglichen: `process_manage`, `cronjob_manage` und `todo_list` (Hermes 0.21) werden wie `process`, `cronjob` und `todo` (Hermes 0.20) behandelt. Jedes Mal, wenn Hermes das Plugin lädt, schreibt es `heartbeat.json` in das Verzeichnis `plugin-data/agent-plugin-failproofai-5296f299/` des Profils und zeichnet die Hermes-Version, den Pfad und die Version des Plugins sowie die von Hermes akzeptierten Hooks auf. Führen Sie `failproofai config --status` aus, um ein deaktiviertes, unvollständiges, dupliziertes oder neu unkonfiguriertes Profil oder eines, das noch veraltete Shell-Hooks verwendet, zu erkennen (wird als „Hermes cron jobs are not checked" gemeldet).

### OpenClaw-Plugin

OpenClaw lädt FailproofAI als In-Process-Gateway-Plugin, das in jeder `openclaw.json` eines Profils registriert ist. Wie das Hermes-Plugin fragt es den lokalen `failproofaid`-Daemon über dessen Socket nach jedem Urteil, sodass ein laufender Daemon erforderlich ist: Die Installation verweigert sich ohne einen solchen, und wenn der Daemon nicht antwortet, werden Tool-Aufrufe und Prompts blockiert und der Grund ins Gateway-Log geschrieben. Starten Sie nach `npm install -g failproofai@latest` das OpenClaw-Gateway neu, damit es das aktualisierte Plugin lädt.

### Codex-Hook-Vertrauen

Codex 0.129 und höher führt einen Hook aus `~/.codex/hooks.json` nur aus, nachdem Sie ihn im interaktiven `codex` genehmigt haben („Review hooks"). Bis dahin überspringt jede Codex-Sitzung — einschließlich headless `codex exec` — ihn. Hooks in der Systemkonfiguration von Codex, `/etc/codex/config.toml` unter Linux und macOS, laufen ohne diese Genehmigung.

Wenn `failproofai config` (oder `policies --install --cli codex` im User-Scope) sudo verwenden kann, schreibt es die Codex-Hooks daher in `/etc/codex/config.toml`, zwischen `# >>> failproofai managed hooks >>>` und `# <<< failproofai managed hooks <<<`, und belässt den Rest der Datei unverändert. Die Datei gilt für jedes Konto auf dem Rechner. `failproofai uninstall` und das Deaktivieren von Codex in `failproofai config` entfernen den Block wieder.

Ohne sudo und unter Windows verbleiben die Hooks in `~/.codex/hooks.json`. `failproofai config` und `failproofai config --status` zählen Codex dann nicht als durchsetzend, bis die Hooks genehmigt wurden, und erklären, wie das behoben werden kann: Führen Sie `failproofai config` erneut aus und erlauben Sie sudo, oder öffnen Sie `codex` einmal und genehmigen Sie die Hooks.

## Capture- und Richtlinien-Hooks installieren

<Tabs>
  <Tab title="Dashboard">
    1. Öffnen Sie **Administration → Keys** und erstellen Sie einen Schlüssel mit `events:add` und `policies:pull`, benannt nach dem Rechner oder der Umgebung.
    2. Verbinden Sie auf dem Zielrechner die lokale CLI mit dem angezeigten Schlüssel und installieren Sie die Harness-Hooks.
    3. Starten Sie eine neue Agenten-Sitzung und bestätigen Sie deren Hook- und Sitzungsereignisse unter **Observe → Events**.
    4. Öffnen Sie **Observe → policy** für dasselbe Zeitfenster und bestätigen Sie, dass eine Richtlinienentscheidung dem Rechner zugeordnet wird.

    Die Verbindung beginnt mit einem Maschinenschlüssel. Stellen Sie sicher, dass er sowohl Ingestion- als auch Richtlinien-Lieferberechtigungen enthält, bevor Sie sein Secret kopieren.

    ![Das Drawer zum Erstellen neuer API-Schlüssel, mit dem Berechtigung für Ereignis-Ingestion und Richtlinienlieferung erteilt wird.](/images/dashboard/key-create.png)

    Nach der Installation der Hooks sollte der Ereignisstream neue Ereignisse vom verbundenen Rechner und der Umgebung anzeigen.

    ![Der Live-Ereignisstream zur Bestätigung, dass ein neu installierter Harness Berichte sendet.](/images/dashboard/events-stream.png)

    Überprüfen Sie abschließend, ob Richtlinienentscheidungen demselben Rechner zugeordnet werden. Dies bestätigt, dass der Harness sowohl Richtlinienaktivität als auch Trace-Ereignisse meldet.

    ![Die Policy-Seite zur Überprüfung von Richtlinienentscheidungen eines neu verbundenen Harnesses.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Lesen Sie den Maschinenschlüssel in die Shell. `read -s` nimmt ihn über eine Eingabeaufforderung entgegen, die keine Ausgabe macht, sodass er nie in einem Befehl oder der Shell-Historie erscheint:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    Richten Sie dann den Rechner ein — dies verdrahtet Hooks für jeden erkannten Harness, installiert den Daemon und verbindet mit Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    Das Setup aktiviert selbst keine Richtlinie; dafür ist der zweite Befehl da.

    Oder zielen Sie auf bestimmte Harnesses und einen Konfigurationsbereich:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    Der Project-Scope bewahrt die Hook-Konfiguration bei einem Repository. Der User-Scope deckt die Arbeit über Repositories hinweg ab. Claude Code unterstützt auch den Local-Scope; die Unterstützung variiert je nach Harness, und die CLI lehnt nicht unterstützte Kombinationen ab.

    Überprüfen Sie den Rechner und seine Ereignisse:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## Einen nicht standardmäßigen Sitzungspfad hinzufügen

<Tabs>
  <Tab title="Dashboard">
    Zusätzliche Pfade werden auf dem Rechner registriert, nicht in Cloud. Öffnen Sie nach dem Hinzufügen **Observe → Sessions**, filtern Sie nach der Umgebung des Rechners und bestätigen Sie, dass Sitzungen aus dem neuen Pfad erscheinen. Öffnen Sie eine Sitzung und prüfen Sie den Agenten, den Harness und die Ereignis-Zeitstempel, bevor Sie ihn in einem Audit verwenden.

    ![Die Sitzungsliste, gefiltert nach der Umgebung, die Daten aus dem zusätzlichen Capture-Pfad empfängt.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Fügen Sie einen Pfad mit einer optionalen Bezeichnung hinzu und prüfen Sie dann die konfigurierten Pfade:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Entfernen Sie einen Pfad mit `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  Führen Sie nach der Installation eine neue Sitzung aus. Überprüfen Sie sowohl den Live-Ereignisstream als auch eine tatsächliche Richtlinienentscheidung, bevor Sie den Rollout ausweiten.
</Tip>
