Dies ist die Cloud-Routenreferenz für [Jev-Richtlinien](/de/policies/jev). Jev, TypeSafes Classifier, liest jeden Tool-Aufruf im Vergleich zu dem, was Sie tatsächlich angefordert haben, und antwortet neben Ihren Richtlinien, nie anstelle von ihnen. Über **FailproofAI Cloud** verwendet eine verbundene Maschine Jev mit demselben Schlüssel, mit dem sie sich bereits verbindet: kein TypeSafe-Konto, kein zweiter Schlüssel, kein zu konfigurierender Endpunkt. Jeder Aufruf wird dem bestehenden Plankontingent Ihrer Organisation belastet.

Alles, was Jev tut, ist gegenüber dem [Bring-your-own-Key-Setup](/de/reference/jev-providers) unverändert: Harte Richtlinien bleiben endgültig, das Deny einer überprüfbaren Richtlinie wird nur dann aufgehoben, wenn Jev genau zu diesem Anliegen befragt wurde, und jeder Fehler fällt für diesen Aufruf auf das Regex-Ergebnis zurück.

<Note>
Erfordert **failproofai 1.0.8-beta.0** oder höher. 1.0.7 hat kein Jev, auch wenn es über den 1.0.7-Betas sortiert. Ohne eine Jev-Konfiguration ändert sich nichts: Hooks führen die Regex-Richtlinien genau wie bisher aus.
</Note>

## Voraussetzungen

Installieren Sie Failproof AI auf der Maschine, auf der Ihr Agent läuft, und hängen Sie dessen Hooks an einen [unterstützten Harness](/de/reference/harnesses) an. Wenn Sie von Grund auf neu beginnen, folgen Sie dem [Quickstart](/de/start/quickstart) bis zur Hook-Installation. Überprüfen Sie die installierte CLI mit `failproofai --version`; aktualisieren Sie sie, wenn sie vor Jev liegt. Sie benötigen außerdem Zugriff auf die Seite **Administration → Keys** Ihrer Organisation, um einen Maschinenschlüssel zu erstellen.

Jev überprüft benannte Tool-Aufrufe am `PreToolUse`- oder `PermissionRequest`-Gate. Es überprüft nicht jedes Ereignis in einer Sitzung. Um zu sehen, wie Jev ein Richtlinien-Deny aufhebt, benötigen Sie eine installierte Richtlinie, die als [reviewable](/de/policies/authority) markiert ist; alle anderen Richtlinien-Denys bleiben endgültig.

## Einschalten

1. **Erstellen Sie einen Schlüssel mit Jev.** Öffnen Sie im FailproofAI Cloud-Dashboard **Administration → Keys → Create key** und wählen Sie das **machine**-Preset. Es gewährt die drei Berechtigungen, die eine Maschine benötigt: `events:add` (Aktivität senden), `policies:pull` (Richtlinien empfangen) und `jev:evaluate` (Jev, dem Plan Ihrer Organisation in Rechnung gestellt). Ein Schlüssel kann `jev:evaluate` nicht ohne die anderen beiden tragen.
2. **Verbinden Sie die Maschine** mit diesem Schlüssel. Lesen Sie dessen Einmal-Secret an einer Eingabeaufforderung, dann führen Sie den vollständigen Setup-Befehl aus:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` installiert den Daemon, hängt Hooks für die gefundenen Agent-CLIs an und verbindet die Maschine. Die Umgebungsvariable hält den Schlüssel aus den Argumenten des Befehls und Ihrer Shell-Historie heraus. Wenn Ihr Harness später installiert wurde, [hängen Sie ihn explizit an](/de/start/quickstart).

   Wenn Ihre Organisation ihre eigene FailproofAI Cloud anstatt der gehosteten betreibt, fügen Sie deren Adresse hinzu: `--url https://<your dashboard host>` (oder exportieren Sie `FAILPROOFAI_CLOUD_URL`). Ohne diese Angabe wird der Schlüssel gegen den gehosteten Dienst geprüft und die Verbindung schlägt fehl. Wenn das Zertifikat dieses Hosts von einer privaten CA stammt, installieren Sie die CA im System-Trust-Store der Maschine (zum Beispiel mit `update-ca-certificates`), nicht nur in `NODE_EXTRA_CA_CERTS`: Der Daemon, der Ereignisse sendet und Richtlinien abruft, liest den System-Store. Siehe [Troubleshooting](/de/reference/troubleshooting).

Das ist alles. Beim Verbinden wird der Schlüssel gespeichert, und wenn die Maschine **noch keine** Jev-Konfiguration hat, wird eine für FailproofAI Cloud geschrieben. Ab der ersten Deployment der Maschine (innerhalb von etwa 30 s) legt FailproofAI Cloud den Modus fest: `enforce`, während eine Jev-Richtlinie für sie deployt ist, `off`, wenn keine deployt ist (siehe [Wer den Modus festlegt](#who-sets-the-mode)). Die Ausgabe zeigt dies an:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Prüfungen, die FailproofAI Cloud deployt, laufen auf Cloud. Um eigene Prüfungen auf der Maschine hinzuzufügen, installieren Sie ein Pack:

```bash
failproofai policies add FailproofAI/jev-policies
```

**Mit `--no-transcripts` schaltet das Verbinden Jev nicht ein.** Jev sendet jeden geprüften Tool-Aufruf und den aktuellen Prompt an FailproofAI Cloud, was mehr ist als eine Verbindung, die nur Entscheidungen senden soll. Der Schlüssel wird dennoch gespeichert, und die Ausgabe zeigt an, dass Jev verfügbar ist und wie man es einschaltet:

```bash
failproofai jev setup --provider failproofai
```

Es schaltet Jev über FailproofAI Cloud auch **aus**. Eine `jev.json`, die Jev über FailproofAI Cloud ausführt (hinterlassen von einer früheren Verbindung mit eingeschalteten Transkripten), wird nach derselben Regel wie `config --disconnect` entfernt, und die Ausgabe zeigt an, dass Jev über FailproofAI Cloud auf dieser Maschine ausgeschaltet bleibt. Eine `jev.json` für Ihren eigenen Jev-Endpunkt wird so belassen, wie sie ist, ebenso wie eine FailproofAI Cloud-Instanz, die Sie ausgeschaltet haben (`--mode off`).

<Warning>
Das Verbinden **überschreibt niemals** eine vorhandene `~/.failproofai/jev.json`. Wenn Sie bereits Ihren eigenen Jev-Endpunkt verwenden, wird er weiterhin verwendet, und die Ausgabe zeigt an, dass die Datei so belassen wurde, wie sie konfiguriert ist — und wenn diese Datei Jev ausgeschaltet lässt (abgelehnt oder ausgeschaltet), wird dies und die Behebung angezeigt. Um diese Maschine auf FailproofAI Cloud umzustellen, führen Sie `failproofai jev setup --provider failproofai` aus.
</Warning>

## Wer den Modus festlegt

Auf einer mit FailproofAI Cloud verbundenen Maschine **legt FailproofAI Cloud den Jev-Modus fest**; nichts auf der Maschine tut dies:

- `enforce`, während eine beliebige Jev- (oder Regex + Jev-) Richtlinie für die Maschine deployt ist: Jeder geprüfte Tool-Aufruf eines Agenten, auf den eine dieser Richtlinien abzielt, wird an FailproofAI Cloud gesendet, das seine Prüfungen zusammen mit den Prüfungen der dort installierten Packs ausführt. Ein Aufruf eines Agenten, auf den keine Cloud-Jev-Richtlinie abzielt und der keine eigene Pack-Prüfung hat, wird überhaupt nicht gesendet. Im `enforce`-Modus blockieren Jevs eigene Deny-Prüfungen Aufrufe und heben auch die Regex-Urteile auf, die sie überprüfen.
- `off`, wenn keine deployt ist: kein Jev, unabhängig davon, was `jev.json` sagt.

Um eine Jev-Richtlinie zu testen, bevor sie wirkt, deployen Sie sie mit Effekt **observe**: Ihre Prüfungen werden weiterhin ausgeführt, und was sie getan hätten, wird als **would-have** auf der Richtlinienseite aufgezeichnet, aber es blockiert nie einen Aufruf und hebt keinen auf. `failproofai jev setup --mode` und der **Settings → Jev**-Schalter im Dashboard zeigen an, dass der Modus von FailproofAI Cloud verwaltet wird, und ändern nichts. `jev.json` wird nicht für Cloud-Prüfungen verwendet, auch wenn sie einen anderen Anbieter nennt. `failproofai config --disconnect` gibt Jev an die eigene `jev.json` der Maschine zurück.

`failproofai jev status` zeigt dann `Jev checks run on FailproofAI Cloud (mode: enforce)` an. Es nennt auch die Prüfungen, die jede `both`-Richtlinie überprüfen. Die Fleet-Seite zeigt, warum eine Maschine mit einem Modus nicht fragen kann:

- `transcripts_disabled`: Die Maschine wurde mit `--no-transcripts` verbunden, was Jev nie einschaltet.
- `jev_unconfigured`: Der Schlüssel der Maschine trägt kein `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud hat einige Aufrufe der Maschine aufgrund des Jev-Rate-Limits der Organisation abgelehnt, und diese Aufrufe wurden allein durch die Regex-Richtlinien entschieden.
- `jev_unavailable`: Mehrere Aufrufe in Folge sind fehlgeschlagen, sodass die Maschine Jevs FailproofAI Cloud jeweils für eine Minute überspringt. Sie versucht es selbstständig erneut.

Wenn FailproofAI Cloud nicht innerhalb von 5 Sekunden antwortet, entscheiden die Regex-Richtlinien allein, wie bei jedem Jev-Ausfall. Nach 3 aufeinanderfolgenden Fehlern hört die Maschine jeweils für eine Minute auf zu fragen, damit ein Cloud-Ausfall nicht jeden Tool-Aufruf verlangsamt.

Eine Sitzungspause (`failproofai config --pause`) stoppt nicht die Jev-Prüfungen von FailproofAI Cloud, genau wie sie die Cloud-verwalteten Richtlinien nicht stoppt. Sie pausiert jedoch die Jev-Prüfungen der auf der Maschine installierten Packs.

## Überprüfen, was es tut

```bash
failproofai jev status
failproofai jev test
```

`status` zeigt den Anbieter als **FailproofAI Cloud**, den Cloud-Host, mit dem die Maschine verbunden ist, den Modus und die Schlüsselquelle als **FailproofAI Cloud connection** an, niemals den Schlüssel selbst. Wenn eine FailproofAI Cloud `jev.json` vorhanden ist, Jev aber nicht ausgeführt werden kann, wird der Grund angegeben:

| `status` zeigt | `status --json` | Bedeutung |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Die Maschine ist verbunden, aber es ist kein Jev-Schlüssel für sie gespeichert: Der Schlüssel hat kein `jev:evaluate`, oder die Verbindung konnte es nicht bestätigen. Führen Sie `failproofai config` erneut mit dem Schlüssel in `FAILPROOFAI_CLOUD_TOKEN` aus; wenn ihm die Berechtigung fehlt, verwenden Sie einen **machine**-Schlüssel. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Es gibt keine FailproofAI Cloud-Verbindung auf dieser Maschine, zu der der Jev-Schlüssel gehören könnte. |

Nach `failproofai config --disconnect` gibt es keine FailproofAI Cloud `jev.json` mehr (es sei denn, sie wurde ausgeschaltet, was beibehalten wird), sodass `status` Jev einfach als ausgeschaltet meldet. `status --json` enthält dieselben Fakten (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), auch wenn die Konfiguration fehlt oder abgelehnt wurde. `permissions` ist immer die von `jev.json`; eine Ablehnung bezüglich `credentials.json` fügt `credentialsPermissions` hinzu, und `fix`, wenn ein Befehl es behebt. `test` sendet eine Live-Anfrage und meldet deren Latenz und die Jev-Version, die geantwortet hat. Es beendet sich mit 1 und zeigt dies in seinem Titel an, wenn die Antwort nach dem Hook-Timeout eintrifft (Hooks würden `timeout` aufzeichnen) oder ihre Prüffrage falsch beantwortet.

Das **Settings → Jev**-Panel im Dashboard zeigt auch die **FailproofAI Cloud connection**: welche Organisation die Maschine meldet und ob ihr Schlüssel Jev trägt. Es wird aus den eigenen Dateien der Maschine gelesen, ohne Netzwerkaufruf.

## Einen echten Aufruf verifizieren

Starten Sie eine neue Sitzung im eingehängten Agenten. Bitten Sie ihn, sein Datei-Lese-Tool auf `README.md` zu verwenden und den Titel zu melden. Bestätigen Sie, dass die Sitzung diesen Tool-Aufruf enthält, und führen Sie dann `failproofai jev status` erneut aus: Die Anzahl der kürzlich ausgewerteten Aufrufe sollte steigen. Öffnen Sie **Policies → Activity** im [lokalen Dashboard](/de/reference/local-dashboard#review-policy-activity), um das Jev-Urteil und den Modus dieses Aufrufs zu untersuchen. In Cloud zeigt die **Policies**-Seite der Organisation Jev-Ergebnisse für gelieferte Aktivitäten. Im observe-Modus wird das Urteil als **would-have** aufgezeichnet und das Richtlinienergebnis entscheidet weiterhin den Aufruf. Eine Aufhebung erscheint nur, wenn eine überprüfbare Richtlinie übereinstimmte und Jev ihre benannten Prüfungen aufhob.

## Was die Richtlinienseite erreicht

Die Maschine sendet ihre Hook-Aktivität bereits an FailproofAI Cloud (`events:add`). Mit eingeschaltetem Jev enthält der Datensatz jedes gesperrten Aufrufs auch, welcher Evaluator gelaufen ist, was Jev entschieden hat, welche Richtlinien es aufgehoben hat, warum es zurückgefallen ist, wenn es das tat, seine Latenz und das Modell, das geantwortet hat — Entscheidungen, Codes und Namen, niemals den Befehl oder Ihren Prompt. Auf der **Policies**-Seite Ihrer Organisation:

- Ein Aufruf, den Jevs eigenes Urteil entschieden hat (enforce-Modus), wird **Jev** zugeschrieben, und wenn die entscheidende Prüfung von einem Pack kam, nennt der Datensatz auch dieses Pack und seine Version;
- Im observe-Modus erscheint Jevs Deny oder Warnung als **would-have**, neben den Rollouts, die Sie beobachten;
- Die Richtlinien, die Jev aufgehoben hat oder im observe-Modus aufgehoben hätte, werden pro Richtlinie gezählt.
- Eine Entscheidung, an der Jev beteiligt war (eine Blockierung, eine Warnung, eine Aufhebung oder ein would-have im observe-Modus), listet jede Prüfung auf, die es gestellt hat, und was diese Prüfung ergab: Urteil, Warum (`not-detected`, `exempt`, `fired`, `op-requested`, …), sein Beweis `p`, die `exempt`-Antwort und die Antwort jeder Sonde. Eine Prüfung einer Richtlinie, die zum Beobachten (observe) deployt wurde, wird ebenfalls aufgelistet, als beobachtet markiert; sie blockiert nie. Jev antwortet mit Wahrscheinlichkeiten, nicht mit Prosa, daher gibt es keinen Freitext-Grund. Einfache Erlaubnisse werden in Zählungen zusammengefasst und tragen diese Liste nicht.

## Wenn Jev nicht antworten kann

Jeder dieser Fälle fällt auf das Ergebnis Ihrer Richtlinien für diesen Aufruf zurück und wird mit seinem Grund aufgezeichnet:

| Grund | Ursache |
| --- | --- |
| `out-of-credits` | Ihre Organisation hat ihr Plankontingent aufgebraucht. |
| `http-401`, `http-403` | Der Schlüssel wurde widerrufen oder trägt kein `jev:evaluate`. Verbinden Sie sich erneut mit einem Schlüssel, der es trägt. |
| `http-429` | FailproofAI Cloud begrenzt Jev für Ihre Organisation. Bis das angeforderte Wartezeitraum abgelaufen ist (sein `Retry-After`, höchstens 60 Sekunden), sendet die Maschine nichts und jeder Aufruf fällt sofort zurück. Auf diese Weise zurückgehaltene Aufrufe werden als `http-429` aufgezeichnet oder als `rate-limited`, wenn das eigene Rate-Limit der Maschine sie zuerst zurückhält. |
| `http-429` (Tageslimit) | Ihre Organisation hat ihr tägliches Jev-Aufruf-Kontingent aufgebraucht: **10.000 pro UTC-Tag**, es sei denn, derjenige, der Ihre FailproofAI Cloud betreibt, hat ein anderes Limit festgelegt. Jeder Aufruf fällt zurück, bis der Zähler um 00:00 UTC zurückgesetzt wird; die Maschine fragt dennoch höchstens einmal pro Minute erneut an, sodass sie den Reset innerhalb einer Minute erkennt. `failproofai jev test` zeigt an: „Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev hat die Anfrage dieses Aufrufs abgelehnt, in der Regel weil der Tool-Aufruf dichten Text (Base64, Hex, minimierten Code) über Jevs Token-Budget enthielt. Dieser Aufruf fällt immer zurück; es handelt sich nicht um einen Ausfall. |
| `http-502` | Jev ist gerade nicht verfügbar. |
| `http-503` | Diese Cloud kann Jev für Ihre Organisation nicht bedienen: kein Modell-Gateway, eine noch nicht bereitgestellte Organisation oder das Gateway ist ausgefallen. Fragen Sie Ihren Administrator; Hooks fragen höchstens einmal pro Minute erneut. |
| `http-404` | Diese FailproofAI Cloud bedient Jev noch nicht. |
| `timeout` | Keine Antwort innerhalb von `timeoutMs` (Standard 3000). Während FailproofAI Cloud den Jev-Modus der Maschine festlegt, beträgt die Wartezeit 5000 ms und `jev.json`'s `timeoutMs` wird nicht verwendet. |
| `model-mismatch` | Eine andere Jev-Version als 1.13 hat geantwortet. |

## Wo der Schlüssel gespeichert wird und wohin er geht

- Der Schlüssel wird einmal gespeichert, in `~/.failproofai/credentials.json` (`0600`, in einem nur dem Eigentümer zugänglichen Verzeichnis), neben den anderen FailproofAI Cloud-Zugangsdaten. `jev.json` enthält für diese Route keinen Schlüssel; ein dort eingetragener macht die Konfiguration ungültig.
- Wenn `credentials.json` eine **beliebige** Berechtigung für jemand anderen als Sie trägt (Gruppe oder andere, Lesen oder Schreiben) oder sein Verzeichnis von jemand anderem als Ihnen **beschrieben** werden kann, wird es **abgelehnt**, nicht gelesen, und Jev ist ausgeschaltet, bis Sie es beheben: `chmod 600` für die Datei, `chmod 700` für das Verzeichnis (oder erneut verbinden, was die Datei mit `0600` neu schreibt und das Verzeichnis nur dem Eigentümer zugänglich macht). Ein Verzeichnis, das andere nur lesen können, ist in Ordnung; eines, das sie beschreiben können, ermöglicht ihnen, die Datei auszutauschen.
- Der Schlüssel zählt nur, solange die Verbindung, mit der er kam, auf der Maschine ist: ein Richtlinien- oder Melde-Zugangsdaten für dieselbe FailproofAI Cloud **mit demselben Schlüssel**, in derselben Datei. Ein hinterlassener Jev-Schlüssel ohne eine solche Verbindung wird ignoriert, und Jev bleibt ausgeschaltet. Dies passiert, wenn ein älteres `failproofai`'s `config --disconnect` den Jev-Schlüssel nicht entfernt (es weiß nicht, wie), oder wenn ein älteres `failproofai`'s `config --token` sich mit einem anderen Schlüssel verbindet, der auf FailproofAI Cloud einer anderen Organisation gehören kann. Um Jev wieder einzuschalten, verbinden Sie sich erneut mit einem **machine**-Schlüssel.
- Der Schlüssel wird nur an den Cloud-Ursprung gesendet, gegen den er verifiziert wurde. Eine `jev.json`, die woanders hinzeigt, wird abgelehnt.
- **Ein Agent auf der Maschine kann ihn lesen.** `credentials.json` ist nur dem Eigentümer zugänglich, und der Agent läuft als dieser Eigentümer. Das Lesen von Failproofais eigenen Dateien ist absichtlich erlaubt (nur das Ändern ist blockiert, durch `block-failproofai-commands`), sodass das Einzige zwischen einem Agenten und dieser Datei `block-read-outside-cwd` ist — eine *reviewable*-Richtlinie — und von einer Sitzung aus, die in Ihrem Home-Verzeichnis gestartet wurde, nichts. Ein Schlüssel mit `jev:evaluate` verbraucht das Jev-Kontingent Ihrer Organisation (bis zur Tageshöchstgrenze) von überall, wo er verwendet wird. Behandeln Sie daher einen Maschinenschlüssel wie jede andere Ausgaben-Zugangsdaten: Wenn ein Agent ihn möglicherweise gelesen hat, deaktivieren Sie ihn auf der Keys-Seite und verbinden Sie sich mit einem neuen erneut.
- Nur Ihre globalen Dateien entscheiden dies. Ein Repository kann Cloud Jev nicht einschalten, nicht woanders hinzeigen oder seinen Schlüssel bereitstellen, und `FAILPROOFAI_JEV_API_KEY` wird für diese Route ignoriert.
- Für jeden von Jev ausgewerteten Aufruf geht eine Anfrage an FailproofAI Cloud, die das enthält, was die [Bring-your-own-Key-Seite](/de/reference/jev-providers#what-leaves-the-machine) auflistet (Secrets geschwärzt). FailproofAI Cloud leitet es an TypeSafe weiter und protokolliert oder speichert es nicht.

## Ausschalten

Auf einer verbundenen Maschine ist Jev ausgeschaltet, wenn FailproofAI Cloud keine Jev-Richtlinie für sie deployt: Entfernen oder archivieren Sie die Jev-Richtlinien dort.

| Befehl | Ergebnis |
| --- | --- |
| Entfernen Sie die Jev-Richtlinien der Maschine in FailproofAI Cloud | Der Modus von Cloud wird beim nächsten Poll (etwa 30 s) zu `off`: kein Jev, unabhängig davon, was `jev.json` sagt. |
| `failproofai config --disconnect` | Trennen Sie die Maschine: Der Schlüssel wird entfernt, und `jev.json` ebenfalls, wenn sie FailproofAI Cloud nennt und nicht ausgeschaltet ist. Eine `jev.json` für Ihren eigenen Endpunkt bleibt bestehen. |

Ab dem nächsten Tool-Aufruf führen Hooks die Regex-Richtlinien genau wie zuvor aus.
