Dies ist die Cloud-Routenreferenz für [Jev-Richtlinien](/de/policies/jev). Jev, der Classifier von TypeSafe, prüft jeden Tool-Call gegen das, was Sie tatsächlich angefordert haben, und antwortet zusammen mit Ihren Richtlinien – niemals anstelle von ihnen. Über **FailproofAI Cloud** nutzt eine verbundene Maschine Jev mit demselben Schlüssel, mit dem sie bereits verbunden ist: kein TypeSafe-Konto, kein zweiter Schlüssel, kein Endpunkt zum Konfigurieren. Jeder Call wird dem bestehenden Plankontingent Ihrer Organisation angerechnet.

Alles, was Jev tut, ist gegenüber dem [Bring-your-own-key-Setup](/de/reference/jev-providers) unverändert: Harte Richtlinien bleiben endgültig, das Deny einer prüfbaren Richtlinie wird nur dann aufgehoben, wenn Jev genau zu diesem Anliegen befragt wurde, und jeder Fehler fällt auf das Regex-Ergebnis für diesen Call zurück.

<Note>
Erfordert **failproofai 1.0.8-beta.0** oder neuer. 1.0.7 hat kein Jev, auch wenn es in der Sortierung über den 1.0.7-Betas erscheint. Ohne eine Jev-Konfiguration ändert sich nichts: Hooks führen die Regex-Richtlinien genau wie bisher aus.
</Note>

## Vor dem Start

Installieren Sie Failproof AI auf der Maschine, auf der Ihr Agent läuft, und binden Sie die Hooks an ein [unterstütztes Harness](/de/reference/harnesses). Wenn Sie von vorne beginnen, folgen Sie dem [Quickstart](/de/start/quickstart) bis zur Hook-Installation. Prüfen Sie die installierte CLI mit `failproofai --version`; aktualisieren Sie sie, falls sie älter als Jev ist. Sie benötigen außerdem Zugriff auf die **Administration → Keys**-Seite Ihrer Organisation, um einen Maschinenschlüssel zu erstellen.

Jev prüft benannte Tool-Calls am `PreToolUse`- oder `PermissionRequest`-Gate. Es prüft nicht jedes Ereignis in einer Sitzung. Um zu sehen, wie Jev ein Richtlinien-Deny aufhebt, benötigen Sie eine installierte Richtlinie, die als [prüfbar](/de/policies/authority) markiert ist; alle anderen Richtlinien-Denys bleiben endgültig.

## Aktivierung

1. **Erstellen Sie einen Schlüssel mit Jev.** Öffnen Sie im FailproofAI Cloud-Dashboard **Administration → Keys → Create key** und wählen Sie das **machine**-Preset. Es gewährt die drei Berechtigungen, die eine Maschine benötigt: `events:add` (Aktivität senden), `policies:pull` (Richtlinien empfangen) und `jev:evaluate` (Jev, wird dem Plan Ihrer Organisation angerechnet). Ein Schlüssel kann `jev:evaluate` nicht ohne die anderen beiden tragen.
2. **Verbinden Sie die Maschine** mit diesem Schlüssel. Lesen Sie das einmalige Geheimnis bei einer Eingabeaufforderung aus und führen Sie dann den vollständigen Setup-Befehl aus:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` installiert den Daemon, bindet Hooks für die gefundenen Agent-CLIs ein und verbindet die Maschine. Die Umgebungsvariable hält den Schlüssel aus den Befehlsargumenten und Ihrem Shell-Verlauf heraus. Wenn Ihr Harness später installiert wurde, [binden Sie es explizit ein](/de/start/quickstart).

   Wenn Ihre Organisation eine eigene FailproofAI Cloud statt des gehosteten Dienstes betreibt, fügen Sie deren Adresse hinzu: `--url https://<your dashboard host>` (oder exportieren Sie `FAILPROOFAI_CLOUD_URL`). Ohne diese Angabe wird der Schlüssel gegen den gehosteten Dienst geprüft und die Verbindung schlägt fehl. Wenn das Zertifikat dieses Hosts von einer privaten CA stammt, installieren Sie die CA im System-Trust-Store der Maschine (z. B. mit `update-ca-certificates`), nicht nur in `NODE_EXTRA_CA_CERTS`: Der Daemon, der Ereignisse sendet und Richtlinien abruft, liest den System-Store. Siehe [Fehlerbehebung](/de/reference/troubleshooting).

Das ist alles. Beim Verbinden wird der Schlüssel gespeichert, und wenn die Maschine noch **keine** Jev-Konfiguration hat, wird eine für FailproofAI Cloud geschrieben. Ab der ersten Bereitstellung der Maschine (innerhalb von etwa 30 s) legt FailproofAI Cloud den Modus fest: `enforce`, solange eine Jev-Richtlinie für sie bereitgestellt ist, `off`, wenn keine vorhanden ist (siehe [Wer den Modus festlegt](#who-sets-the-mode)). Die Ausgabe zeigt dies an:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Checks, die FailproofAI Cloud bereitstellt, laufen in Cloud. Um eigene Checks auf der Maschine hinzuzufügen, installieren Sie ein Pack:

```bash
failproofai policies add FailproofAI/jev-policies
```

**Mit `--no-transcripts` schaltet das Verbinden Jev nicht ein.** Jev sendet jeden geprüften Tool-Call und die aktuellen Prompts an FailproofAI Cloud – das ist mehr, als eine Nur-Entscheidungen-Verbindung senden soll. Der Schlüssel wird dennoch gespeichert, und die Ausgabe zeigt an, dass Jev verfügbar ist und wie man es einschaltet:

```bash
failproofai jev setup --provider failproofai
```

Damit wird Jev über FailproofAI Cloud auch **ausgeschaltet**. Eine `jev.json`, die Jev über FailproofAI Cloud betreibt (hinterlassen von einer früheren Verbindung mit aktivierten Transkripten), wird nach derselben Regel entfernt, die `config --disconnect` verwendet, und die Ausgabe zeigt an, dass Jev über FailproofAI Cloud auf dieser Maschine ausgeschaltet bleibt. Eine `jev.json` für Ihren eigenen Jev-Endpunkt bleibt unverändert, ebenso eine FailproofAI Cloud-Konfiguration, die Sie ausgeschaltet haben (`--mode off`).

<Warning>
Das Verbinden **überschreibt niemals** eine vorhandene `~/.failproofai/jev.json`. Wenn Sie bereits Ihren eigenen Jev-Endpunkt verwenden, wird er weiterhin verwendet, und die Ausgabe zeigt an, dass die Datei unverändert gelassen wurde – und wenn diese Datei Jev ausschaltet (verweigert oder ausgeschaltet), wird dies ebenfalls angezeigt sowie wie man es behebt. Um diese Maschine auf FailproofAI Cloud umzustellen, führen Sie `failproofai jev setup --provider failproofai` aus.
</Warning>

## Wer den Modus festlegt

Auf einer mit FailproofAI Cloud verbundenen Maschine **legt FailproofAI Cloud den Jev-Modus fest**; nichts auf der Maschine selbst tut dies:

- `enforce`, solange eine Jev- (oder Regex + Jev-) Richtlinie auf der Maschine bereitgestellt ist: Jeder geprüfte Tool-Call von einem Agent, auf den eine dieser Richtlinien abzielt, wird an FailproofAI Cloud gesendet, das seine Checks zusammen mit den Checks der dort installierten Packs ausführt. Ein Call von einem Agent, auf den keine Cloud-Jev-Richtlinie abzielt und der keinen eigenen Pack-Check hat, wird gar nicht gesendet. Im `enforce`-Modus blockieren Jevs eigene Deny-Checks Calls ebenso, wie sie die Regex-Verdicts aufheben, die sie prüfen.
- `off`, wenn keine vorhanden ist: Kein Jev, unabhängig von dem, was `jev.json` sagt.

Um eine Jev-Richtlinie vor dem Wirksamwerden auszuprobieren, stellen Sie sie mit dem Effekt **observe** bereit: Ihre Checks werden weiterhin ausgeführt, und was sie getan hätten, wird als **would-have** auf der Richtlinienseite aufgezeichnet, aber es blockiert niemals einen Call und hebt auch keinen auf. `failproofai jev setup --mode` und der **Settings → Jev**-Schalter im Dashboard zeigen an, dass der Modus von FailproofAI Cloud verwaltet wird, und ändern nichts. `jev.json` wird nicht für Cloud-Checks verwendet, auch wenn sie einen anderen Provider nennt. `failproofai config --disconnect` gibt Jev an die eigene `jev.json` der Maschine zurück.

`failproofai jev status` zeigt dann `Jev checks run on FailproofAI Cloud (mode: enforce)` an. Es nennt auch die Checks, die jede `both`-Richtlinie prüfen. Die Fleet-Seite zeigt, warum eine Maschine mit einem Modus nicht fragen kann:

- `transcripts_disabled`: Die Maschine wurde mit `--no-transcripts` verbunden, was Jev nie einschaltet.
- `jev_unconfigured`: Der Schlüssel der Maschine trägt kein `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud hat einige Calls der Maschine aufgrund des Jev-Rate-Limits der Organisation abgelehnt, und diese Calls wurden allein durch die Regex-Richtlinien entschieden.
- `jev_unavailable`: Mehrere Calls in Folge sind fehlgeschlagen, daher überspringt die Maschine das Jev von FailproofAI Cloud für jeweils eine Minute. Sie wiederholt die Anfrage selbstständig.

Wenn FailproofAI Cloud nicht innerhalb von 5 Sekunden antwortet, entscheiden die Regex-Richtlinien allein, wie bei jedem Jev-Ausfall. Nach 3 aufeinanderfolgenden Fehlern hört die Maschine auf zu fragen, jeweils für eine Minute, damit ein Cloud-Ausfall nicht jeden Tool-Call verlangsamt.

Eine Sitzungspause (`failproofai config --pause`) stoppt die Jev-Checks von FailproofAI Cloud nicht, ebenso wenig wie sie Cloud-verwaltete Richtlinien stoppt. Sie pausiert jedoch die Jev-Checks von auf der Maschine installierten Packs.

## Überprüfen der Funktion

```bash
failproofai jev status
failproofai jev test
```

`status` zeigt den Provider als **FailproofAI Cloud**, den Cloud-Host, mit dem die Maschine verbunden ist, den Modus und die Schlüsselquelle als **FailproofAI Cloud connection** an – niemals den Schlüssel selbst. Wenn eine FailproofAI Cloud-`jev.json` vorhanden ist, Jev aber nicht ausgeführt werden kann, zeigt es den Grund an:

| `status` zeigt | `status --json` | Bedeutung |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Die Maschine ist verbunden, aber es ist kein Jev-Schlüssel für sie gespeichert: Der Schlüssel fehlt `jev:evaluate`, oder die Verbindung konnte es nicht bestätigen. Führen Sie `failproofai config` erneut mit dem Schlüssel in `FAILPROOFAI_CLOUD_TOKEN` aus; wenn die Berechtigung fehlt, verwenden Sie einen **machine**-Schlüssel. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Es gibt keine FailproofAI Cloud-Verbindung auf dieser Maschine, zu der der Jev-Schlüssel gehören könnte. |

Nach `failproofai config --disconnect` gibt es keine FailproofAI Cloud-`jev.json` mehr (es sei denn, sie wurde ausgeschaltet, was beibehalten wird), daher meldet `status` Jev einfach als ausgeschaltet. `status --json` enthält dieselben Fakten (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), auch wenn die Konfiguration fehlt oder abgelehnt wurde. `permissions` gehört immer zu `jev.json`; eine Ablehnung bezüglich `credentials.json` fügt `credentialsPermissions` hinzu, und `fix`, wenn ein Befehl es behebt. `test` sendet eine Live-Anfrage und meldet die Latenz und die Jev-Version, die geantwortet hat. Es beendet sich mit 1 und zeigt dies im Titel an, wenn die Antwort nach dem Hook-Timeout eintrifft (Hooks würden `timeout` aufzeichnen) oder die Check-Frage falsch beantwortet.

Das **Settings → Jev**-Panel im Dashboard zeigt auch die **FailproofAI Cloud-Verbindung**: in welche Organisation die Maschine berichtet und ob ihr Schlüssel Jev trägt. Es wird aus den eigenen Dateien der Maschine gelesen, ohne Netzwerkaufruf.

## Einen echten Call verifizieren

Starten Sie eine neue Sitzung im eingebundenen Agent. Fordern Sie ihn auf, sein Datei-Lese-Tool auf `README.md` zu verwenden und den Titel zu melden. Bestätigen Sie, dass die Sitzung diesen Tool-Call enthält, und führen Sie dann `failproofai jev status` erneut aus: Die Anzahl der kürzlich ausgewerteten Calls sollte steigen. Öffnen Sie **Policies → Activity** im [lokalen Dashboard](/de/reference/local-dashboard#review-policy-activity), um das Jev-Verdict und den Modus dieses Calls zu prüfen. In Cloud zeigt die **Policies**-Seite der Organisation Jev-Ergebnisse für übermittelte Aktivitäten an. Im Observe-Modus wird das Verdict als **would-have** aufgezeichnet und das Richtlinienergebnis entscheidet den Call weiterhin. Eine Aufhebung erscheint nur, wenn eine prüfbare Richtlinie übereinstimmte und Jev ihre benannten Checks aufhob.

## Was die Richtlinienseite erreicht

Die Maschine sendet ihre Hook-Aktivität bereits an FailproofAI Cloud (`events:add`). Mit aktiviertem Jev enthält der Datensatz jedes gesperrten Calls auch, welcher Evaluator ausgeführt wurde, was Jev entschieden hat, welche Richtlinien es aufgehoben hat, warum es beim Fallback war, seine Latenz und das Modell, das geantwortet hat – Entscheidungen, Codes und Namen, niemals den Befehl oder Ihren Prompt. Auf der **Policies**-Seite Ihrer Organisation:

- Ein Call, über den Jevs eigenes Verdict entschieden hat (Enforce-Modus), wird **Jev** zugeordnet, und wenn der entscheidende Check von einem Pack stammte, nennt der Datensatz auch dieses Pack und seine Version;
- Im Observe-Modus erscheint Jevs Deny oder Warnung als **would-have**, neben den Rollouts, die Sie beobachten;
- Die von Jev aufgehobenen Richtlinien – oder die im Observe-Modus aufgehoben worden wären – werden pro Richtlinie gezählt.
- Eine Entscheidung, an der Jev beteiligt war (eine Blockierung, eine Warnung, eine Aufhebung oder ein would-have im Observe-Modus), listet jeden ausgeführten Check und dessen Schlussfolgerung auf: Verdict, Grund (`not-detected`, `exempt`, `fired`, `op-requested`, …), seine Evidenz `p`, die `exempt`-Antwort und die Antwort jeder Probe. Ein Check einer im Watch (Observe)-Modus bereitgestellten Richtlinie wird ebenfalls aufgelistet, als watched markiert; er blockiert nie. Jev antwortet mit Wahrscheinlichkeiten, nicht mit Prosa, daher gibt es keinen Freitext-Grund. Normale Allows werden zu Zählungen zusammengefasst und tragen diese Liste nicht.

## Wenn Jev nicht antworten kann

Jeder der folgenden Fälle fällt auf das Richtlinienergebnis dieses Calls zurück und wird mit seinem Grund aufgezeichnet:

| Grund | Ursache |
| --- | --- |
| `out-of-credits` | Ihre Organisation hat ihr Plankontingent aufgebraucht. |
| `http-401`, `http-403` | Der Schlüssel wurde widerrufen oder trägt kein `jev:evaluate`. Verbinden Sie sich erneut mit einem Schlüssel, der dies tut. |
| `http-429` | FailproofAI Cloud begrenzt Jev für Ihre Organisation per Rate-Limit. Bis die angeforderte Wartezeit abgelaufen ist (sein `Retry-After`, maximal 60 Sekunden), sendet die Maschine nichts und jeder Call fällt sofort zurück. Auf diese Weise zurückgehaltene Calls werden als `http-429` aufgezeichnet, oder als `rate-limited`, wenn das eigene Rate-Limit der Maschine sie zuerst hält. |
| `http-429` (tägliches Limit) | Ihre Organisation hat ihr tägliches Jev-Call-Kontingent aufgebraucht: **10.000 pro UTC-Tag**, es sei denn, der Betreiber Ihrer FailproofAI Cloud hat ein anderes Limit festgelegt. Jeder Call fällt zurück, bis der Zähler um 00:00 UTC zurückgesetzt wird; die Maschine fragt weiterhin höchstens einmal pro Minute, sodass sie den Reset innerhalb einer Minute erkennt. `failproofai jev test` zeigt „Daily Jev limit for this org reached; resets at 00:00 UTC." an. |
| `http-422` | Jev hat die Anfrage dieses Calls abgelehnt, meist weil der Tool-Call dichten Text (Base64, Hex, minifizierten Code) über Jevs Token-Budget enthielt. Dieser Call fällt jedes Mal zurück; es handelt sich nicht um einen Ausfall. |
| `http-502` | Jev ist derzeit nicht verfügbar. |
| `http-503` | Diese Cloud kann Jev für Ihre Organisation nicht bereitstellen: kein Modell-Gateway, eine noch nicht bereitgestellte Organisation oder das Gateway ist ausgefallen. Wenden Sie sich an Ihren Admin; Hooks fragen höchstens einmal pro Minute erneut an. |
| `http-404` | Diese FailproofAI Cloud stellt Jev noch nicht bereit. |
| `timeout` | Keine Antwort innerhalb von `timeoutMs` (Standard 3000). Während FailproofAI Cloud den Jev-Modus der Maschine festlegt, beträgt die Wartezeit 5000 ms und `jev.json`s `timeoutMs` wird nicht verwendet. |
| `model-mismatch` | Eine andere Jev-Version als 1.13 hat geantwortet. |

## Wo der Schlüssel liegt und wohin er geht

- Der Schlüssel wird einmal gespeichert, in `~/.failproofai/credentials.json` (`0600`, in einem Nur-Eigentümer-Verzeichnis), neben den anderen FailproofAI Cloud-Anmeldeinformationen. `jev.json` enthält für diese Route keinen Schlüssel; ein dort eingetragener macht die Konfiguration ungültig.
- Wenn `credentials.json` **irgendeine** Berechtigung für jemanden außer Ihnen trägt (Gruppe oder andere, Lesen oder Schreiben), oder wenn in das Verzeichnis **geschrieben** werden kann von jemandem außer Ihnen, wird sie **abgelehnt**, nicht gelesen, und Jev ist ausgeschaltet, bis Sie es beheben: `chmod 600` auf die Datei, `chmod 700` auf das Verzeichnis (oder erneut verbinden, was die Datei mit `0600` neu schreibt und das Verzeichnis Nur-Eigentümer macht). Ein Verzeichnis, das andere nur lesen können, ist in Ordnung; eines, in das sie schreiben können, ermöglicht das Austauschen der Datei.
- Der Schlüssel zählt nur, solange die Verbindung, von der er stammt, auf der Maschine aktiv ist: Eine Richtlinien- oder Berichts-Anmeldeinformation für dieselbe FailproofAI Cloud **mit demselben Schlüssel**, in derselben Datei. Ein ohne eine solche Verbindung hinterlassener Jev-Schlüssel wird ignoriert, und Jev bleibt ausgeschaltet. Das passiert, wenn ein älteres failproofai `config --disconnect` den Jev-Schlüssel zurücklässt (es weiß nicht, dass es ihn entfernen soll), oder wenn ein älteres failproofai `config --token` sich mit einem anderen Schlüssel verbindet, der in FailproofAI Cloud möglicherweise zu einer anderen Organisation gehört. Um Jev wieder einzuschalten, verbinden Sie sich erneut mit einem **machine**-Schlüssel.
- Der Schlüssel wird nur an den Cloud-Origin gesendet, gegen den er verifiziert wurde. Eine `jev.json`, die auf einen anderen Ort verweist, wird abgelehnt.
- **Ein Agent auf der Maschine kann ihn lesen.** `credentials.json` ist Nur-Eigentümer, und der Agent läuft als dieser Eigentümer. Das Lesen von failproofais eigenen Dateien ist absichtlich erlaubt (nur das Ändern ist blockiert, durch `block-failproofai-commands`), sodass das Einzige zwischen einem Agent und dieser Datei `block-read-outside-cwd` ist – eine *prüfbare* Richtlinie – und aus einer Sitzung, die in Ihrem Home-Verzeichnis gestartet wurde, nichts. Ein Schlüssel mit `jev:evaluate` verbraucht das Jev-Kontingent Ihrer Organisation (bis zur täglichen Obergrenze) von wo auch immer er verwendet wird, also behandeln Sie einen Maschinenschlüssel wie jede andere Ausgaben-Anmeldeinformation: Wenn ein Agent ihn möglicherweise gelesen hat, deaktivieren Sie ihn auf der Keys-Seite und verbinden Sie sich mit einem neuen erneut.
- Nur Ihre globalen Dateien entscheiden dies. Ein Repository kann Cloud-Jev nicht einschalten, es woanders hinzeigen oder seinen Schlüssel bereitstellen, und `FAILPROOFAI_JEV_API_KEY` wird für diese Route ignoriert.
- Für jeden von Jev ausgewerteten Call geht eine Anfrage an FailproofAI Cloud, die enthält, was die [Bring-your-own-key-Seite](/de/reference/jev-providers#what-leaves-the-machine) auflistet (Geheimnisse werden redigiert). FailproofAI Cloud leitet es an TypeSafe weiter und protokolliert oder speichert es nicht.

## Deaktivierung

Auf einer verbundenen Maschine ist Jev ausgeschaltet, wenn FailproofAI Cloud keine Jev-Richtlinie für sie bereitstellt: Entfernen oder archivieren Sie die Jev-Richtlinien dort.

| Befehl | Ergebnis |
| --- | --- |
| Entfernen Sie die Jev-Richtlinien der Maschine in FailproofAI Cloud | Der Cloud-Modus wird beim nächsten Poll (etwa 30 s) `off`: Kein Jev, unabhängig von dem, was `jev.json` sagt. |
| `failproofai config --disconnect` | Trennt die Maschine: Der Schlüssel wird entfernt, ebenso `jev.json`, wenn sie FailproofAI Cloud nennt und nicht ausgeschaltet ist. Eine `jev.json` für Ihren eigenen Endpunkt bleibt. |

Ab dem nächsten Tool-Call führen Hooks die Regex-Richtlinien genau wie zuvor aus.
