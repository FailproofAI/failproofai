Dies ist die Cloud-Routenreferenz für [Jev-Richtlinien](/de/policies/jev). Jev, TypeSafes Classifier, prüft jeden Tool-Aufruf gegen das, was tatsächlich angefragt wurde, und gibt seine Einschätzung neben Ihren Richtlinien aus – niemals anstelle von ihnen. Über **FailproofAI Cloud** verwendet eine verbundene Maschine Jev mit demselben Key, mit dem sie bereits verbunden ist: kein TypeSafe-Konto, kein zweiter Key, kein Endpoint zum Konfigurieren. Jeder Aufruf wird dem bestehenden Plan-Kontingent Ihrer Organisation angerechnet.

Alles, was Jev tut, ist identisch mit dem [Bring-your-own-Key-Setup](/de/reference/jev-providers): Harte Richtlinien bleiben endgültig, das Deny einer überprüfbaren Richtlinie wird nur aufgehoben, wenn Jev ausdrücklich zu genau diesem Anliegen befragt wurde, und jeder Fehler fällt für diesen Aufruf auf das Regex-Ergebnis zurück.

<Note>
Erfordert **failproofai 1.0.8-beta.0** oder neuer. Version 1.0.7 enthält kein Jev, obwohl sie lexikalisch über den 1.0.7-Betas sortiert. Ohne Jev-Konfiguration ändert sich nichts: Hooks führen die Regex-Richtlinien exakt wie bisher aus.
</Note>

## Voraussetzungen

Installieren Sie Failproof AI auf der Maschine, auf der Ihr Agent läuft, und verbinden Sie deren Hooks mit einem [unterstützten Harness](/de/reference/harnesses). Wenn Sie von Grund auf neu beginnen, folgen Sie dem [Quickstart](/de/start/quickstart) bis zur Hook-Installation. Prüfen Sie die installierte CLI mit `failproofai --version`; aktualisieren Sie sie, wenn sie älter als Jev ist. Sie benötigen außerdem Zugriff auf die **Einstellungen → API-Keys**-Seite Ihrer Organisation, um einen Machine-Key zu erstellen.

Jev prüft benannte Tool-Aufrufe am `PreToolUse`- oder `PermissionRequest`-Gate. Es prüft nicht jedes Event in einer Session. Damit Jev ein Richtlinien-Deny aufhebt, benötigen Sie eine installierte Richtlinie, die als [reviewable](/de/policies/authority) markiert ist; alle anderen Richtlinien-Denys bleiben endgültig.

## Aktivierung

1. **Erstellen Sie einen Key mit Jev.** Öffnen Sie im FailproofAI Cloud-Dashboard **Einstellungen → API-Keys** und wählen Sie im Formular **Neuer Key** die Option **eine Maschine, die failproofai ausführt**. Dies gewährt die drei Berechtigungen, die eine Maschine benötigt: `events:add` (Aktivität senden), `policies:pull` (Richtlinien empfangen) und `jev:evaluate` (Jev, dem Plan Ihrer Organisation angerechnet). Ein Key kann `jev:evaluate` nicht ohne die anderen beiden tragen.
2. **Verbinden Sie die Maschine** mit diesem Key. Lesen Sie das einmalige Secret an einer Eingabeaufforderung, dann führen Sie den vollständigen Setup-Befehl aus:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` installiert den Daemon, verbindet Hooks für die gefundenen Agent-CLIs und stellt die Verbindung der Maschine her. Die Umgebungsvariable hält den Key aus den Befehlsargumenten und Ihrem Shell-Verlauf heraus. Wenn Ihr Harness später installiert wurde, [verbinden Sie ihn explizit](/de/start/quickstart).

   Wenn Ihre Organisation eine eigene FailproofAI Cloud anstelle des gehosteten Dienstes betreibt, fügen Sie deren Adresse hinzu: `--url https://<your dashboard host>` (oder exportieren Sie `FAILPROOFAI_CLOUD_URL`). Ohne diese Angabe wird der Key gegen den gehosteten Dienst geprüft und die Verbindung schlägt fehl. Wenn das Zertifikat dieses Hosts von einer privaten CA stammt, installieren Sie die CA im System-Truststore der Maschine (z. B. mit `update-ca-certificates`), nicht nur in `NODE_EXTRA_CA_CERTS`: Der Daemon, der Events sendet und Richtlinien abruft, liest den System-Truststore. Siehe [Fehlerbehebung](/de/reference/troubleshooting).

Das ist alles. Die Verbindung speichert den Key und schreibt – wenn die Maschine noch **keine** Jev-Konfiguration hat – eine für FailproofAI Cloud. Ab dem ersten Deployment der Maschine (innerhalb von ca. 30 s) legt FailproofAI Cloud den Modus fest: `enforce`, solange eine Jev-Richtlinie auf ihr deployed ist, `off`, wenn keine vorhanden ist (siehe [Wer setzt den Modus](#wer-setzt-den-modus)). Die Ausgabe bestätigt dies:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Prüfungen, die FailproofAI Cloud deployed, laufen auf Cloud. Um eigene Prüfungen auf der Maschine hinzuzufügen, installieren Sie ein Pack:

```bash
failproofai policies add FailproofAI/jev-policies
```

**Mit `--no-transcripts` schaltet die Verbindung Jev nicht ein.** Jev sendet jeden geprüften Tool-Aufruf und den aktuellen Prompt an FailproofAI Cloud – das ist mehr, als eine nur-Entscheidungen-Verbindung senden soll. Der Key wird dennoch gespeichert, und die Ausgabe zeigt an, dass Jev verfügbar ist und wie es eingeschaltet werden kann:

```bash
failproofai jev setup --provider failproofai
```

Dieser Befehl schaltet Jev über FailproofAI Cloud auch **aus**. Eine `jev.json`, die Jev über FailproofAI Cloud ausführt (hinterlassen von einer früheren Verbindung mit aktivierten Transcripts), wird entfernt – nach derselben Regel wie `config --disconnect` – und die Ausgabe zeigt an, dass Jev über FailproofAI Cloud auf dieser Maschine deaktiviert bleibt. Eine `jev.json` für Ihren eigenen Jev-Endpoint bleibt unverändert, ebenso eine FailproofAI Cloud-Konfiguration, die Sie deaktiviert haben (`--mode off`).

<Warning>
Die Verbindung **überschreibt niemals** eine vorhandene `~/.failproofai/jev.json`. Wenn Sie bereits Ihren eigenen Jev-Endpoint verwenden, wird dieser weiterhin verwendet, und die Ausgabe zeigt an, dass die Datei unverändert blieb – und wenn diese Datei Jev deaktiviert lässt (verweigert oder ausgeschaltet), wird dies und der Lösungsweg angezeigt. Um diese Maschine auf FailproofAI Cloud umzustellen, führen Sie `failproofai jev setup --provider failproofai` aus.
</Warning>

## Wer setzt den Modus

Auf einer mit FailproofAI Cloud verbundenen Maschine **legt FailproofAI Cloud den Jev-Modus fest**; nichts auf der Maschine tut das:

- `enforce`, solange eine Jev-Richtlinie (oder Regex + Jev) auf der Maschine deployed ist: Jeder geprüfte Tool-Aufruf eines Agents, auf den eine dieser Richtlinien zielt, geht an FailproofAI Cloud, das seine Prüfungen zusammen mit den Prüfungen der dort installierten Packs durchführt. Ein Aufruf eines Agents, auf den keine Cloud-Jev-Richtlinie zielt und der keine eigene Pack-Prüfung hat, wird überhaupt nicht gesendet. Im `enforce`-Modus können Jevs eigene Deny-Prüfungen Aufrufe blockieren und Regex-Urteile aufheben.
- `off`, wenn keine vorhanden ist: kein Jev, unabhängig davon, was `jev.json` angibt.

Um eine Jev-Richtlinie zu testen, bevor sie wirkt, deployen Sie sie mit Effekt **observe**: Ihre Prüfungen werden weiterhin ausgeführt, und was sie getan hätten, wird als **would-have** unter **Fix → Aktivität** aufgezeichnet, aber sie blockiert niemals einen Aufruf und hebt keinen auf. `failproofai jev setup --mode` und der **Einstellungen → Jev**-Schalter im lokalen Dashboard zeigen an, dass der Modus von FailproofAI Cloud verwaltet wird, und ändern nichts. `jev.json` wird nicht für Cloud-Prüfungen verwendet, auch wenn sie einen anderen Provider benennt. `failproofai config --disconnect` übergibt Jev zurück an die eigene `jev.json` der Maschine.

`failproofai jev status` zeigt dann `Jev checks run on FailproofAI Cloud (mode: enforce)`. Es benennt auch die Prüfungen, die jede `both`-Richtlinie überprüfen. Die Fleet-Seite zeigt, warum eine Maschine mit einem Modus nicht anfragen kann:

- `transcripts_disabled`: Die Maschine wurde mit `--no-transcripts` verbunden, was Jev nie einschaltet.
- `jev_unconfigured`: Der Key der Maschine trägt kein `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud hat einige Aufrufe der Maschine aufgrund des Jev-Rate-Limits der Organisation abgelehnt, und diese Aufrufe wurden allein durch die Regex-Richtlinien entschieden.
- `jev_unavailable`: Mehrere aufeinanderfolgende Aufrufe sind fehlgeschlagen, sodass die Maschine das Jev von FailproofAI Cloud jeweils für eine Minute überspringt. Sie versucht es selbstständig erneut.

Antwortet FailproofAI Cloud nicht innerhalb von 5 Sekunden, entscheiden die Regex-Richtlinien allein – wie bei jedem Jev-Ausfall. Nach 3 aufeinanderfolgenden Fehlern hört die Maschine jeweils für eine Minute auf zu fragen, damit ein Cloud-Ausfall nicht jeden Tool-Aufruf verlangsamt.

Eine Session-Pause (`failproofai config --pause`) stoppt die Jev-Prüfungen von FailproofAI Cloud nicht, genau wie sie Cloud-verwaltete Richtlinien nicht stoppt. Sie pausiert jedoch die Jev-Prüfungen von auf der Maschine installierten Packs.

## Überprüfen der Funktion

```bash
failproofai jev status
failproofai jev test
```

`status` zeigt den Provider als **FailproofAI Cloud**, den Cloud-Host, mit dem die Maschine verbunden ist, den Modus und die Key-Quelle als **FailproofAI Cloud-Verbindung** – niemals den Key selbst. Wenn eine FailproofAI Cloud `jev.json` vorhanden ist, Jev aber nicht ausgeführt werden kann, wird der Grund angegeben:

| `status` zeigt | `status --json` | Bedeutung |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Die Maschine ist verbunden, aber es ist kein Jev-Key für sie gespeichert: dem Key fehlt `jev:evaluate`, oder die Verbindung konnte es nicht bestätigen. Führen Sie `failproofai config` erneut mit dem Key in `FAILPROOFAI_CLOUD_TOKEN` aus; falls die Berechtigung fehlt, verwenden Sie einen **Machine**-Key. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Auf dieser Maschine besteht keine FailproofAI Cloud-Verbindung, der der Jev-Key gehören könnte. |

Nach `failproofai config --disconnect` gibt es keine FailproofAI Cloud `jev.json` mehr (außer sie wurde deaktiviert, was beibehalten wird), sodass `status` Jev schlicht als deaktiviert meldet. `status --json` enthält dieselben Informationen (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), auch wenn die Konfiguration fehlt oder verweigert wurde. `permissions` gilt immer für `jev.json`; eine Verweigerung bezüglich `credentials.json` fügt `credentialsPermissions` hinzu sowie `fix`, wenn ein Befehl das Problem behebt. `test` sendet eine echte Live-Anfrage und meldet deren Latenz sowie die Jev-Version, die geantwortet hat. Es beendet sich mit Exit-Code 1 und zeigt dies im Titel an, wenn die Antwort nach dem Hook-Timeout eintrifft (Hooks würden `timeout` aufzeichnen) oder die Prüffrage falsch beantwortet.

Das **Einstellungen → Jev**-Panel im lokalen Dashboard zeigt auch die **FailproofAI Cloud-Verbindung**: welcher Organisation die Maschine angehört und ob ihr Key Jev trägt. Die Daten werden aus den eigenen Dateien der Maschine gelesen, ohne Netzwerkanfrage.

## Einen echten Aufruf verifizieren

Starten Sie eine neue Session im verbundenen Agent. Bitten Sie ihn, sein Dateilese-Tool auf `README.md` anzuwenden und den Titel zurückzugeben. Bestätigen Sie, dass die Session diesen Tool-Aufruf enthält, und führen Sie dann erneut `failproofai jev status` aus: Der Zähler der zuletzt ausgewerteten Aufrufe sollte gestiegen sein. Öffnen Sie **Richtlinien → Aktivität** im [lokalen Dashboard](/de/reference/local-dashboard#review-policy-activity), um das Jev-Urteil und den Modus für diesen Aufruf zu prüfen. In Cloud zeigt **Fix → Aktivität** die Jev-Ergebnisse für gelieferte Aktivität. Im Observe-Modus wird das Urteil als **would-have** aufgezeichnet und das Richtlinienergebnis entscheidet weiterhin den Aufruf. Eine Aufhebung erscheint nur, wenn eine überprüfbare Richtlinie übereinstimmte und Jev deren benannte Prüfungen aufhob.

## Was die Richtlinienseite anzeigt

Die Maschine sendet ihre Hook-Aktivität bereits an FailproofAI Cloud (`events:add`). Mit aktiviertem Jev enthält der Datensatz jedes gegateten Aufrufs zusätzlich: welcher Evaluator ausgeführt wurde, was Jev entschied, welche Richtlinien aufgehoben wurden, warum ein Fallback erfolgte, die Latenz und das Modell, das antwortete – Entscheidungen, Codes und Namen, niemals den Befehl oder Ihren Prompt. In Cloud unter **Fix → Aktivität**:

- Ein Aufruf, den Jevs eigenes Urteil entschied (Enforce-Modus), wird **Jev** zugeordnet; wenn die entscheidende Prüfung von einem Pack stammte, benennt der Datensatz auch dieses Pack und seine Version.
- Im Observe-Modus erscheint Jevs Deny oder Warning als **would-have**, neben den Rollouts, die Sie beobachten.
- Die von Jev aufgehobenen Richtlinien – oder die, die im Observe-Modus aufgehoben worden wären – werden pro Richtlinie gezählt.
- Eine Entscheidung, an der Jev beteiligt war (ein Block, eine Warnung, eine Aufhebung oder ein would-have im Observe-Modus), listet jede gestellte Prüfung und deren Schlussfolgerung auf: Urteil, Grund (`not-detected`, `exempt`, `fired`, `op-requested`, …), die Evidenz `p`, die `exempt`-Antwort und die Antwort jeder Sonde. Eine Prüfung einer im Watch-Modus (observe) deployten Richtlinie wird ebenfalls aufgelistet, als beobachtet markiert; sie blockiert niemals. Jev antwortet mit Wahrscheinlichkeiten, nicht mit Prosatext, daher gibt es keine Freitext-Begründung. Einfache Allows werden zu Zählungen zusammengefasst und tragen diese Liste nicht.

## Wenn Jev nicht antworten kann

Jeder der folgenden Fälle fällt für diesen Aufruf auf das Ergebnis Ihrer Richtlinien zurück und wird mit seinem Grund aufgezeichnet:

| Grund | Ursache |
| --- | --- |
| `out-of-credits` | Ihre Organisation hat ihr Plan-Kontingent aufgebraucht. |
| `http-401`, `http-403` | Der Key wurde widerrufen oder trägt kein `jev:evaluate`. Verbinden Sie erneut mit einem Key, der dies tut. |
| `http-429` | FailproofAI Cloud begrenzt Jev für Ihre Organisation per Rate-Limit. Bis die angeforderte Wartezeit abgelaufen ist (dessen `Retry-After`, höchstens 60 Sekunden) sendet die Maschine nichts und jeder Aufruf fällt sofort zurück. Auf diese Weise zurückgehaltene Aufrufe werden als `http-429` aufgezeichnet oder als `rate-limited`, wenn das eigene Rate-Limit der Maschine sie zuerst zurückhält. |
| `http-429` (Tageslimit) | Ihre Organisation hat ihr tägliches Jev-Aufruflimit erreicht: **10.000 pro UTC-Tag**, sofern der Betreiber Ihrer FailproofAI Cloud kein anderes Limit gesetzt hat. Jeder Aufruf fällt zurück, bis der Zähler um 00:00 UTC zurückgesetzt wird; die Maschine fragt höchstens einmal pro Minute erneut an und erkennt den Reset damit innerhalb einer Minute. `failproofai jev test` zeigt: „Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev hat die Anfrage dieses Aufrufs abgelehnt, in der Regel weil der Tool-Aufruf dichten Text (Base64, Hex, minifizierten Code) enthielt, der Jevs Token-Budget überstieg. Dieser Aufruf fällt immer zurück; es handelt sich nicht um einen Ausfall. |
| `http-502` | Jev ist aktuell nicht verfügbar. |
| `http-503` | Diese Cloud kann Jev für Ihre Organisation nicht bedienen: kein Model-Gateway, eine noch nicht provisionierte Organisation oder das Gateway ist ausgefallen. Wenden Sie sich an Ihren Admin; Hooks fragen höchstens einmal pro Minute erneut an. |
| `http-404` | Diese FailproofAI Cloud stellt Jev noch nicht bereit. |
| `timeout` | Keine Antwort innerhalb von `timeoutMs` (Standard: 3000). Während FailproofAI Cloud den Jev-Modus der Maschine festlegt, beträgt die Wartezeit 5000 ms und `jev.json`s `timeoutMs` wird nicht verwendet. |
| `model-mismatch` | Eine andere Jev-Version als 1.13 hat geantwortet. |

## Wo der Key gespeichert wird und wohin er gelangt

- Der Key wird einmalig in `~/.failproofai/credentials.json` gespeichert (`0600`, in einem nur dem Eigentümer zugänglichen Verzeichnis), neben den anderen FailproofAI Cloud-Credentials. `jev.json` enthält für diese Route keinen Key; ein dort hinterlassener Key macht die Konfiguration ungültig.
- Wenn `credentials.json` **irgendeine** Berechtigung für jemand anderen als Sie enthält (Gruppe oder Andere, lesen oder schreiben), oder sein Verzeichnis von jemand anderem als Ihnen **beschrieben** werden kann, wird es **verweigert**, nicht gelesen, und Jev ist deaktiviert, bis Sie das beheben: `chmod 600` für die Datei, `chmod 700` für das Verzeichnis (oder erneut verbinden, was die Datei mit `0600` neu schreibt und das Verzeichnis auf den Eigentümer beschränkt). Ein Verzeichnis, das andere nur lesen können, ist in Ordnung; eines, das sie beschreiben können, erlaubt das Austauschen der Datei.
- Der Key zählt nur, solange die Verbindung, mit der er kam, auf der Maschine aktiv ist: ein Richtlinien- oder Reporting-Credential für dieselbe FailproofAI Cloud **mit demselben Key** in derselben Datei. Ein hinterlassener Jev-Key ohne eine solche Verbindung wird ignoriert, und Jev bleibt deaktiviert. Das passiert, wenn ein älteres `failproofai config --disconnect` den Jev-Key hinterlässt (es weiß nicht, ihn zu entfernen), oder wenn ein älteres `failproofai config --token` mit einem anderen Key verbindet, der bei FailproofAI Cloud einer anderen Organisation gehören kann. Um Jev wieder einzuschalten, verbinden Sie erneut mit einem **Machine**-Key.
- Der Key wird ausschließlich an den Cloud-Origin gesendet, gegen den er verifiziert wurde. Eine `jev.json`, die auf einen anderen Ort zeigt, wird verweigert.
- **Ein Agent auf der Maschine kann ihn lesen.** `credentials.json` ist nur dem Eigentümer zugänglich, und der Agent läuft als dieser Eigentümer. Das Lesen von Failproof AIs eigenen Dateien ist absichtlich erlaubt (nur das Ändern wird durch `block-failproofai-commands` blockiert), sodass das Einzige zwischen einem Agent und dieser Datei `block-read-outside-cwd` ist – eine *reviewable*-Richtlinie – und von einer im Home-Verzeichnis gestarteten Session aus: nichts. Ein Key mit `jev:evaluate` verbraucht das Jev-Kontingent Ihrer Organisation (bis zum Tageslimit) von überall, wo er verwendet wird. Behandeln Sie daher einen Machine-Key wie jedes andere Ausgaben-Credential: Wenn ein Agent ihn möglicherweise gelesen hat, widerrufen Sie ihn unter **Einstellungen → API-Keys** und verbinden Sie erneut mit einem neuen.
- Nur Ihre globalen Dateien entscheiden dies. Ein Repository kann Cloud-Jev nicht einschalten, nicht auf einen anderen Ort verweisen oder seinen Key bereitstellen, und `FAILPROOFAI_JEV_API_KEY` wird für diese Route ignoriert.
- Für jeden von Jev ausgewerteten Aufruf geht eine Anfrage an FailproofAI Cloud, die das enthält, was die [Bring-your-own-Key-Seite](/de/reference/jev-providers#what-leaves-the-machine) auflistet (Secrets geschwärzt). FailproofAI Cloud leitet es an TypeSafe weiter und protokolliert oder speichert es nicht.

## Deaktivierung

Auf einer verbundenen Maschine ist Jev deaktiviert, wenn FailproofAI Cloud keine Jev-Richtlinie auf ihr deployed: Entfernen oder archivieren Sie die Jev-Richtlinien dort.

| Befehl | Ergebnis |
| --- | --- |
| Entfernen der Jev-Richtlinien der Maschine in FailproofAI Cloud | Clouds Modus wird beim nächsten Poll (ca. 30 s) zu `off`: kein Jev, unabhängig davon, was `jev.json` angibt. |
| `failproofai config --disconnect` | Maschine trennen: Der Key wird entfernt, ebenso `jev.json`, wenn sie FailproofAI Cloud benennt und nicht deaktiviert ist. Eine `jev.json` für Ihren eigenen Endpoint bleibt erhalten. |

Ab dem nächsten Tool-Aufruf führen Hooks die Regex-Richtlinien exakt wie zuvor aus.
