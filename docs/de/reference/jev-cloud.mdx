Dies ist die Cloud-Routenreferenz für [Jev-Richtlinien](/de/policies/jev). Jev, TypeSafes Klassifikator, liest jeden Tool-Aufruf im Kontext Ihrer tatsächlichen Anfrage und arbeitet ergänzend zu Ihren Richtlinien, ersetzt diese aber nie. Über **FailproofAI Cloud** verwendet eine verbundene Maschine Jev mit demselben Schlüssel, mit dem sie sich bereits verbindet: kein TypeSafe-Konto, kein zweiter Schlüssel, kein Endpunkt zum Konfigurieren. Jeder Aufruf wird dem bestehenden Plankontingent Ihrer Organisation belastet.

Alles, was Jev tut, verhält sich identisch zur [Bring-your-own-key-Einrichtung](/de/reference/jev-providers): Harte Richtlinien bleiben endgültig, das Deny einer überprüfbaren Richtlinie wird nur dann aufgehoben, wenn Jev ausdrücklich zu genau diesem Aspekt befragt wurde, und bei einem Fehler wird auf das Regex-Ergebnis für diesen Aufruf zurückgegriffen.

<Note>
Erfordert **failproofai 1.0.8-beta.0** oder höher. 1.0.7 enthält kein Jev, obwohl es in der Sortierung über den 1.0.7-Betas erscheint. Ohne eine Jev-Konfiguration ändert sich nichts: Hooks führen die Regex-Richtlinien exakt wie bisher aus.
</Note>

## Voraussetzungen

Installieren Sie Failproof AI auf der Maschine, auf der Ihr Agent läuft, und binden Sie dessen Hooks an ein [unterstütztes Harness](/de/reference/harnesses) an. Falls Sie von Grund auf neu starten, folgen Sie der [Schnellstartanleitung](/de/start/quickstart) bis zur Hook-Installation. Prüfen Sie die installierte CLI mit `failproofai --version`; aktualisieren Sie sie, falls sie älter als Jev ist. Sie benötigen außerdem Zugriff auf die Seite **Administration → Keys** Ihrer Organisation, um einen Maschinenschlüssel zu erstellen.

Jev überprüft benannte Tool-Aufrufe am `PreToolUse`- oder `PermissionRequest`-Gate. Es überprüft nicht jedes Ereignis in einer Sitzung. Um zu sehen, wie Jev ein Richtlinien-Deny aufhebt, benötigen Sie eine installierte Richtlinie, die als [reviewable](/de/policies/authority) markiert ist; alle anderen Richtlinien-Denys bleiben endgültig.

## Aktivierung

1. **Schlüssel mit Jev erstellen.** Öffnen Sie im FailproofAI Cloud-Dashboard **Administration → Keys → Create key** und wählen Sie das **machine**-Preset. Es erteilt die drei Berechtigungen, die eine Maschine benötigt: `events:add` (Aktivität senden), `policies:pull` (Richtlinien empfangen) und `jev:evaluate` (Jev, dem Organisationsplan belastet). Ein Schlüssel kann `jev:evaluate` nicht ohne die anderen beiden tragen.
2. **Maschine verbinden** mit diesem Schlüssel. Lesen Sie dessen einmaligen Geheimwert bei einer Eingabeaufforderung aus und führen Sie dann den vollständigen Setup-Befehl aus:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` installiert den Daemon, bindet Hooks für die gefundenen Agent-CLIs an und verbindet die Maschine. Die Umgebungsvariable hält den Schlüssel aus den Befehlsargumenten und Ihrem Shell-Verlauf heraus. Falls Ihr Harness später installiert wurde, [binden Sie es explizit an](/de/start/quickstart).

   Wenn Ihre Organisation eine eigene FailproofAI Cloud anstelle des gehosteten Dienstes betreibt, fügen Sie deren Adresse hinzu: `--url https://<your dashboard host>` (oder exportieren Sie `FAILPROOFAI_CLOUD_URL`). Ohne diese Angabe wird der Schlüssel gegen den gehosteten Dienst geprüft und die Verbindung schlägt fehl. Falls das Zertifikat dieses Hosts von einer privaten CA stammt, installieren Sie die CA im System-Truststore der Maschine (z. B. mit `update-ca-certificates`), nicht nur in `NODE_EXTRA_CA_CERTS`: Der Daemon, der Ereignisse sendet und Richtlinien empfängt, liest den System-Truststore. Siehe [Fehlerbehebung](/de/reference/troubleshooting).

Das ist alles. Die Verbindung speichert den Schlüssel, und wenn die Maschine **noch keine** Jev-Konfiguration hat, wird eine für FailproofAI Cloud erstellt. Ab der ersten Bereitstellung der Maschine (innerhalb von ca. 30 s) legt FailproofAI Cloud den Modus fest: `enforce`, solange eine Jev-Richtlinie auf ihr bereitgestellt ist, `off`, wenn keine vorhanden ist (siehe [Wer den Modus festlegt](#who-sets-the-mode)). Die Ausgabe gibt darüber Auskunft:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Prüfungen, die FailproofAI Cloud bereitstellt, werden in Cloud ausgeführt. Um eigene Prüfungen auf der Maschine hinzuzufügen, installieren Sie ein Pack:

```bash
failproofai policies add FailproofAI/jev-policies
```

**Mit `--no-transcripts` schaltet die Verbindung Jev nicht ein.** Jev sendet jeden geprüften Tool-Aufruf und die aktuelle Eingabeaufforderung an FailproofAI Cloud, was mehr ist, als eine reine Entscheidungsverbindung senden soll. Der Schlüssel wird dennoch gespeichert, und die Ausgabe zeigt an, dass Jev verfügbar ist und wie es eingeschaltet werden kann:

```bash
failproofai jev setup --provider failproofai
```

Dies schaltet Jev über FailproofAI Cloud auch **aus**. Eine `jev.json`, die Jev über FailproofAI Cloud ausführt (hinterlassen von einer früheren Verbindung mit aktivierten Transkripten), wird nach derselben Regel entfernt, die `config --disconnect` verwendet, und die Ausgabe meldet, dass Jev via FailproofAI Cloud auf dieser Maschine deaktiviert bleibt. Eine `jev.json` für Ihren eigenen Jev-Endpunkt bleibt unverändert, ebenso wie eine FailproofAI Cloud-Konfiguration, die Sie deaktiviert haben (`--mode off`).

<Warning>
Die Verbindung **überschreibt niemals** eine vorhandene `~/.failproofai/jev.json`. Wenn Sie bereits Ihren eigenen Jev-Endpunkt verwenden, wird dieser weiterhin genutzt, und die Ausgabe meldet, dass die Datei unverändert blieb — und wenn diese Datei Jev deaktiviert lässt (verweigert oder ausgeschaltet), wird dies ebenfalls angezeigt zusammen mit der Behebung. Um diese Maschine auf FailproofAI Cloud umzustellen, führen Sie `failproofai jev setup --provider failproofai` aus.
</Warning>

## Wer den Modus festlegt

Auf einer mit FailproofAI Cloud verbundenen Maschine **legt FailproofAI Cloud den Jev-Modus fest**; nichts auf der Maschine selbst tut dies:

- `enforce`, solange eine Jev- (oder Regex + Jev-) Richtlinie auf der Maschine bereitgestellt ist: Jeder geprüfte Tool-Aufruf eines Agents, auf den eine dieser Richtlinien zielt, geht an FailproofAI Cloud, das seine Prüfungen zusammen mit den Prüfungen der dort installierten Packs durchführt. Ein Aufruf eines Agents, auf den keine Cloud-Jev-Richtlinie zielt und der keine eigene Pack-Prüfung hat, wird überhaupt nicht gesendet. Im `enforce`-Modus können Jevs eigene Deny-Prüfungen Aufrufe sowohl blockieren als auch die von ihnen überprüften Regex-Urteile aufheben.
- `off`, wenn keine vorhanden ist: kein Jev, unabhängig davon, was `jev.json` angibt.

Um eine Jev-Richtlinie zu testen, bevor sie wirksam wird, stellen Sie sie mit dem Effekt **observe** bereit: Ihre Prüfungen werden weiterhin durchgeführt, und was sie bewirkt hätten, wird als **would-have** auf der Richtlinienseite aufgezeichnet, aber es blockiert oder hebt nie einen Aufruf auf. `failproofai jev setup --mode` und der Schalter **Settings → Jev** im Dashboard zeigen an, dass der Modus von FailproofAI Cloud verwaltet wird, und ändern nichts. `jev.json` wird für Cloud-Prüfungen nicht verwendet, selbst wenn darin ein anderer Anbieter angegeben ist. `failproofai config --disconnect` übergibt Jev zurück an die eigene `jev.json` der Maschine.

`failproofai jev status` meldet dann `Jev checks run on FailproofAI Cloud (mode: enforce)`. Es nennt auch die Prüfungen, die jede `both`-Richtlinie überprüfen. Die Fleet-Seite zeigt, warum eine Maschine mit einem Modus nicht anfragen kann:

- `transcripts_disabled`: Die Maschine wurde mit `--no-transcripts` verbunden, was Jev nie einschaltet.
- `jev_unconfigured`: Der Schlüssel der Maschine trägt nicht `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud hat einige Aufrufe der Maschine aufgrund des Jev-Ratelimits der Organisation abgelehnt, und diese Aufrufe wurden allein durch die Regex-Richtlinien entschieden.
- `jev_unavailable`: Mehrere aufeinanderfolgende Aufrufe sind fehlgeschlagen, sodass die Maschine das Jev von FailproofAI Cloud jeweils für eine Minute überspringt. Sie versucht es selbstständig erneut.

Antwortet FailproofAI Cloud nicht innerhalb von 5 Sekunden, entscheiden die Regex-Richtlinien allein, wie bei jedem Jev-Ausfall. Nach 3 aufeinanderfolgenden Fehlern hört die Maschine jeweils für eine Minute auf zu fragen, damit ein Cloud-Ausfall nicht jeden Tool-Aufruf verlangsamt.

Eine Sitzungspause (`failproofai config --pause`) stoppt die Jev-Prüfungen von FailproofAI Cloud nicht, genau wie sie von Cloud verwaltete Richtlinien nicht stoppt. Sie pausiert jedoch die Jev-Prüfungen von auf der Maschine installierten Packs.

## Prüfen, was passiert

```bash
failproofai jev status
failproofai jev test
```

`status` zeigt den Anbieter als **FailproofAI Cloud**, den Cloud-Host, mit dem die Maschine verbunden ist, den Modus und die Schlüsselquelle als **FailproofAI Cloud connection** — niemals den Schlüssel selbst. Wenn eine FailproofAI Cloud-`jev.json` vorhanden ist, Jev aber nicht ausgeführt werden kann, wird der Grund angegeben:

| `status` meldet | `status --json` | Bedeutung |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Die Maschine ist verbunden, aber es ist kein Jev-Schlüssel für sie gespeichert: dem Schlüssel fehlt `jev:evaluate`, oder die Verbindung konnte dies nicht bestätigen. Führen Sie `failproofai config` erneut mit dem Schlüssel in `FAILPROOFAI_CLOUD_TOKEN` aus; falls die Berechtigung fehlt, verwenden Sie einen **machine**-Schlüssel. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Auf dieser Maschine besteht keine FailproofAI Cloud-Verbindung, der der Jev-Schlüssel zugeordnet werden könnte. |

Nach `failproofai config --disconnect` gibt es keine FailproofAI Cloud-`jev.json` mehr (außer sie war deaktiviert, was beibehalten wird), sodass `status` Jev schlicht als deaktiviert meldet. `status --json` enthält dieselben Informationen (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), auch wenn die Konfiguration fehlt oder verweigert wurde. `permissions` gilt immer für `jev.json`; eine Verweigerung bezüglich `credentials.json` fügt `credentialsPermissions` hinzu, und `fix`, wenn ein Befehl das Problem behebt. `test` sendet eine Live-Anfrage und meldet deren Latenz sowie die Jev-Version, die geantwortet hat. Es beendet sich mit 1 und zeigt dies im Titel an, wenn die Antwort nach dem Hook-Timeout eintrifft (Hooks würden `timeout` aufzeichnen) oder die Prüffrage falsch beantwortet.

Das Panel **Settings → Jev** im Dashboard zeigt auch die **FailproofAI Cloud connection**: in welche Organisation die Maschine eingebunden ist und ob ihr Schlüssel Jev trägt. Die Daten werden aus den eigenen Dateien der Maschine gelesen, ohne Netzwerkaufruf.

## Echten Aufruf verifizieren

Starten Sie eine neue Sitzung im eingebundenen Agent. Bitten Sie ihn, sein Datei-Lese-Tool auf `README.md` anzuwenden und den Titel zu berichten. Bestätigen Sie, dass die Sitzung diesen Tool-Aufruf enthält, und führen Sie dann erneut `failproofai jev status` aus: Der Zähler der zuletzt ausgewerteten Aufrufe sollte gestiegen sein. Öffnen Sie **Policies → Activity** im [lokalen Dashboard](/de/reference/local-dashboard#review-policy-activity), um das Jev-Urteil und den Modus dieses Aufrufs zu prüfen. In Cloud zeigt die **Policies**-Seite der Organisation Jev-Ergebnisse für gelieferte Aktivitäten. Im Observe-Modus wird das Urteil als **would-have** aufgezeichnet, und das Richtlinienergebnis entscheidet den Aufruf weiterhin. Eine Freigabe erscheint nur, wenn eine überprüfbare Richtlinie übereinstimmte und Jev deren benannte Prüfungen aufhob.

## Was auf der Richtlinienseite erscheint

Die Maschine sendet ihre Hook-Aktivität bereits an FailproofAI Cloud (`events:add`). Mit aktiviertem Jev enthält der Datensatz jedes gesperrten Aufrufs zusätzlich: welcher Evaluator ausgeführt wurde, was Jev entschieden hat, welche Richtlinien aufgehoben wurden, warum ein Fallback erfolgte, die Latenz und das verwendete Modell — Entscheidungen, Codes und Namen, niemals den Befehl oder Ihre Eingabeaufforderung. Auf der **Policies**-Seite Ihrer Organisation:

- Ein Aufruf, der durch Jevs eigenes Urteil entschieden wurde (Enforce-Modus), wird **Jev** zugeschrieben; kam die entscheidende Prüfung aus einem Pack, nennt der Datensatz auch das Pack und dessen Version;
- im Observe-Modus erscheint Jevs Deny oder Warnung als **would-have**, neben den Rollouts, die Sie beobachten;
- die von Jev aufgehobenen Richtlinien — oder im Observe-Modus die, die aufgehoben worden wären — werden pro Richtlinie gezählt;
- Eine Entscheidung, an der Jev beteiligt war (eine Blockierung, eine Warnung, eine Freigabe oder ein would-have im Observe-Modus), listet jede durchgeführte Prüfung und deren Ergebnis auf: Urteil, Grund (`not-detected`, `exempt`, `fired`, `op-requested`, …), Evidenz `p`, die `exempt`-Antwort und die Antwort jeder Probe. Eine Prüfung einer im Watch-Modus (observe) bereitgestellten Richtlinie wird ebenfalls aufgelistet, als solche markiert und blockiert nie. Jev antwortet mit Wahrscheinlichkeiten, nicht mit Fließtext, daher gibt es keine Freitextbegründung. Einfache Freigaben werden zusammengezählt und tragen diese Liste nicht.

## Wenn Jev nicht antworten kann

Jeder der folgenden Fälle fällt auf das Ergebnis Ihrer Richtlinien für diesen Aufruf zurück und wird mit seinem Grund aufgezeichnet:

| Grund | Ursache |
| --- | --- |
| `out-of-credits` | Ihre Organisation hat ihr Plankontingent aufgebraucht. |
| `http-401`, `http-403` | Der Schlüssel wurde widerrufen oder trägt nicht `jev:evaluate`. Verbinden Sie sich erneut mit einem Schlüssel, der dies tut. |
| `http-429` | FailproofAI Cloud begrenzt Jev für Ihre Organisation per Rate-Limit. Bis das angeforderte Wartezeitfenster abgelaufen ist (sein `Retry-After`, höchstens 60 Sekunden) sendet die Maschine nichts und jeder Aufruf fällt sofort zurück. Zurückgehaltene Aufrufe werden als `http-429` aufgezeichnet oder als `rate-limited`, wenn das eigene Rate-Limit der Maschine sie zuerst zurückhält. |
| `http-429` (Tageslimit) | Ihre Organisation hat ihr tägliches Jev-Aufrufkontingent aufgebraucht: **10.000 pro UTC-Tag**, sofern der Betreiber Ihrer FailproofAI Cloud kein anderes Limit gesetzt hat. Jeder Aufruf fällt zurück, bis der Zähler um 00:00 UTC zurückgesetzt wird; die Maschine fragt höchstens einmal pro Minute erneut an, sodass sie den Reset innerhalb einer Minute erkennt. `failproofai jev test` meldet: "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev hat die Anfrage dieses Aufrufs abgelehnt, in der Regel weil der Tool-Aufruf dichten Text (Base64, Hex, minifizierten Code) über Jevs Token-Budget enthielt. Dieser Aufruf fällt immer zurück; es handelt sich nicht um einen Ausfall. |
| `http-502` | Jev ist derzeit nicht verfügbar. |
| `http-503` | Diese Cloud kann Jev für Ihre Organisation nicht bedienen: kein Model-Gateway, eine noch nicht provisionierte Organisation oder das Gateway ist ausgefallen. Wenden Sie sich an Ihren Administrator; Hooks fragen höchstens einmal pro Minute erneut an. |
| `http-404` | Diese FailproofAI Cloud unterstützt Jev noch nicht. |
| `timeout` | Keine Antwort innerhalb von `timeoutMs` (Standard: 3000). Während FailproofAI Cloud den Jev-Modus der Maschine festlegt, beträgt die Wartezeit 5000 ms und `jev.json`s `timeoutMs` wird nicht verwendet. |
| `model-mismatch` | Eine andere Jev-Version als 1.13 hat geantwortet. |

## Wo der Schlüssel liegt und wohin er geht

- Der Schlüssel wird einmalig in `~/.failproofai/credentials.json` gespeichert (`0600`, in einem nur dem Eigentümer zugänglichen Verzeichnis), neben den anderen FailproofAI Cloud-Zugangsdaten. `jev.json` enthält für diese Route keinen Schlüssel; ein darin geschriebener macht die Konfiguration ungültig.
- Wenn `credentials.json` **irgendwelche** Berechtigungen für andere als Sie enthält (Gruppe oder andere, Lesen oder Schreiben), oder wenn ihr Verzeichnis von anderen als Ihnen **beschreibbar** ist, wird sie **verweigert**, nicht gelesen, und Jev ist deaktiviert, bis Sie das beheben: `chmod 600` auf die Datei, `chmod 700` auf das Verzeichnis (oder erneut verbinden, was die Datei mit `0600` neu schreibt und das Verzeichnis auf den Eigentümer beschränkt). Ein Verzeichnis, das andere nur lesen können, ist in Ordnung; eines, das sie beschreiben können, ermöglicht das Austauschen der Datei.
- Der Schlüssel gilt nur, solange die Verbindung, mit der er kam, auf der Maschine aktiv ist: eine Richtlinien- oder Reporting-Zugangsdaten für dieselbe FailproofAI Cloud **mit demselben Schlüssel**, in derselben Datei. Ein hinterlassener Jev-Schlüssel ohne eine solche Verbindung wird ignoriert, und Jev bleibt deaktiviert. Das passiert, wenn `config --disconnect` einer älteren failproofai-Version den Jev-Schlüssel beibehält (sie weiß nicht, ihn zu entfernen), oder wenn `config --token` einer älteren Version mit einem anderen Schlüssel verbindet, der bei FailproofAI Cloud einer anderen Organisation gehören kann. Um Jev wieder einzuschalten, verbinden Sie sich erneut mit einem **machine**-Schlüssel.
- Der Schlüssel wird ausschließlich an den Cloud-Ursprung gesendet, gegen den er verifiziert wurde. Eine `jev.json`, die auf einen anderen Ort zeigt, wird verweigert.
- **Ein Agent auf der Maschine kann ihn lesen.** `credentials.json` ist nur dem Eigentümer zugänglich, und der Agent läuft als dieser Eigentümer. Das Lesen von Failproof AIs eigenen Dateien ist absichtlich erlaubt (nur das Ändern wird durch `block-failproofai-commands` blockiert), sodass zwischen einem Agent und dieser Datei nur `block-read-outside-cwd` steht — eine *reviewable*-Richtlinie — und bei einer Sitzung, die im Home-Verzeichnis gestartet wird, nichts. Ein Schlüssel mit `jev:evaluate` verbraucht das Jev-Kontingent Ihrer Organisation (bis zur Tageshöchstgrenze) von überall aus, wo er verwendet wird. Behandeln Sie einen Maschinenschlüssel daher wie jede andere Ausgaben-Zugangsdaten: Wenn ein Agent ihn möglicherweise gelesen hat, deaktivieren Sie ihn auf der Keys-Seite und verbinden Sie sich mit einem neuen.
- Nur Ihre globalen Dateien entscheiden dies. Ein Repository kann Cloud-Jev nicht einschalten, nicht auf einen anderen Ort verweisen oder seinen Schlüssel liefern, und `FAILPROOFAI_JEV_API_KEY` wird für diese Route ignoriert.
- Für jeden von Jev ausgewerteten Aufruf geht eine Anfrage an FailproofAI Cloud, die das enthält, was die [Bring-your-own-key-Seite](/de/reference/jev-providers#what-leaves-the-machine) auflistet (Geheimnisse geschwärzt). FailproofAI Cloud leitet diese an TypeSafe weiter und protokolliert oder speichert sie nicht.

## Deaktivierung

Auf einer verbundenen Maschine ist Jev deaktiviert, wenn FailproofAI Cloud keine Jev-Richtlinie auf ihr bereitstellt: Entfernen oder archivieren Sie die Jev-Richtlinien dort.

| Befehl | Ergebnis |
| --- | --- |
| Jev-Richtlinien der Maschine in FailproofAI Cloud entfernen | Der Cloud-Modus wird beim nächsten Poll (ca. 30 s) zu `off`: kein Jev, unabhängig davon, was `jev.json` angibt. |
| `failproofai config --disconnect` | Maschine trennen: Der Schlüssel wird entfernt, ebenso `jev.json`, wenn sie FailproofAI Cloud benennt und nicht deaktiviert ist. Eine `jev.json` für Ihren eigenen Endpunkt bleibt erhalten. |

Ab dem nächsten Tool-Aufruf führen Hooks die Regex-Richtlinien exakt wie zuvor aus.
