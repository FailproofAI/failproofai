Diese Seite beschreibt die Frageformen und Bewertungsregeln hinter [Jev-Auswertungen](/de/evaluations/jev). Manche Fragen erfordern, dass ein Modell das Gespräch *liest*, aber nicht darüber *schreibt*. „Hat der Kunde Dringlichkeit ausgedrückt?" hat zwei mögliche Antworten. „Wie frustriert waren sie?" hat eine Handvoll, in einer bestimmten Reihenfolge. Du kennst jede Antwort, bevor du fragst.

Eine **Klassifikatorauswertung** ist genau dafür gedacht. Du schreibst die Frage und die möglichen Antworten, und ein kleines, speziell für die Klassifikation entwickeltes Modell gibt eine kalibrierte Zahl zurück — niemals Freitext.

<Note>
Wie ein Richter kostet eine Klassifikatorauswertung einen Modellaufruf pro Sitzung. Anders als ein Richter ist es jedoch ein kleines, zweckgebundenes Modell statt eines allgemeinen — es ist also schneller und günstiger, erklärt sich aber niemals selbst. Wenn du die Begründung brauchst, verwende einen [Judge](/de/evaluations/judge).
</Note>

## Was brauche ich?

| Frage | Methode |
| --- | --- |
| Wie viele Tool-Aufrufe gab es? | Code |
| War die Sitzung unter 30 Sekunden? | Code |
| Hat der Kunde Dringlichkeit ausgedrückt? | **Klassifikator** |
| Welches Team soll sich darum kümmern: Abrechnung, Technik oder Vertrieb? | **Klassifikator** |
| Wie frustriert war der Kunde? | **Klassifikator** |
| War die Antwort tatsächlich korrekt? | **Judge** |
| Hat es unsere Eskalationsrichtlinie befolgt, und warum denkst du das? | **Judge** |

Die Faustregel: **Zählbares → Code, auflistbare Antworten → Klassifikator, Begründung erforderlich → Judge.**

Du musst dich nicht im Voraus entscheiden. Beschreibe, was gemessen werden soll, und der Assistent wählt aus, teilt dir mit, was er gewählt hat und warum — und du kannst es jederzeit ändern.

## Die zwei Fragetypen

### `noul` — Ist das wahr?

Zwei Antworten, und du beschreibst beide. Das Ergebnis ist die Wahrscheinlichkeit, dass die „wahre" Beschreibung zutrifft:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

Beschreibe beide Seiten. „Keine Dringlichkeit ausgedrückt" ist eine echte Antwort, und sie zu formulieren macht die andere schärfer.

### `score` — Wie stark ist das ausgeprägt?

Eine geordnete Rubrik, **schlechteste zuerst**. Das Ergebnis zeigt, wo die Sitzung auf der Skala liegt, auf 0–1 umskaliert:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**Eine Rubrik hat drei bis fünf Stufen, und alle müssen sich voneinander unterscheiden.** Beide Grenzen sind messtechnisch begründet, nicht stilistischer Natur:

- **Zwei Stufen** kollabiert zu dem, was `noul` bereits besser leistet, und **mehr als fünf** verleitet das Modell dazu, zur Mitte zu tendieren, statt sich festzulegen. Dieselbe Frage über dieselbe Sitzung ergab 0,00 bei zwei Stufen, 0,01 bei drei und 0,55 bei zehn.
- **Wiederholte Stufen** verteilen die Antwort willkürlich zwischen ihnen. Eine Sitzung, die eindeutig wütend war, wurde mit 1,00 gegen `["Calm", "Frustrated", "Very angry"]` bewertet und mit 0,66 gegen `["Angry", "Angry", "Angry"]` — eine wohlgeformte Zahl, die nichts bedeutet.

Kategorien ohne Reihenfolge — „Abrechnung, Technik oder Vertrieb" — sind keine Rubrik. Stelle sie als `noul` pro Kategorie oder verwende einen Judge.

## Ergebnisse lesen

Ein Klassifikator erzeugt einen **Score** von 0 bis 1 — genau wie ein Judge. Er lässt sich daher genauso in Diagrammen darstellen, filtern und für Alerts verwenden. Zwei Unterschiede sind wichtig:

- **Es gibt keine Begründung.** Das Feld ist absichtlich leer. Dieses Modell erklärt sich nicht selbst, und eine Erklärung zu erfinden wäre eine Verfälschung, kein Feature.
- **Unsicherheit wird gekennzeichnet.** Bei einer `score`-Frage wird die eigene Konfidenz angegeben, und ein Ergebnis, bei dem das Modell unsicher war, wird mit `low_confidence` markiert — „welche davon sollte ein Mensch prüfen" ist damit eine Filterfrage statt eine Raterei. Bei einer `noul`-Frage wird keine Konfidenz angegeben, daher wird sie nie markiert.

Sehr lange Sitzungen werden in Auszügen gelesen und zusammengeführt. Wenn eine Sitzung zu lang ist, um vollständig gelesen zu werden, gibt das Ergebnis an, wie viele Gesprächsrunden ausgelassen wurden — du wirst nie eine Beurteilung sehen, die auf einem Teil einer Sitzung basiert, aber als vollständige präsentiert wird.

## Limits

- **Drei bis fünf Rubrikstufen, alle verschieden.** Siehe oben; beide Grenzen werden beim Erstellen durchgesetzt.
- **Eine Frage pro Auswertung.** Wenn du zwei Dinge fragst, erhältst du zwei Auswertungen — was auch genau das ist, was du in einem Diagramm möchtest.
- **Das Bearbeiten der Frage veröffentlicht eine neue Version.** Alte und neue Scores sind nicht vergleichbar und werden daher getrennt gehalten, statt in eine gemeinsame Trendlinie gemischt zu werden.
- **Ein Klassifikator erzeugt immer einen Score**, niemals eine Metrik oder eine Aussage.
- **Keine Begründung**, wie oben beschrieben. Wenn eine Zahl jemanden zu einem „Warum?" verleitet, schreibe stattdessen einen Judge.

## Testen und Backfill

Anders als ein Judge **kann** eine Klassifikatorauswertung getestet werden, bevor du sie einführst — [teste sie](/de/evaluations/test) an echten Sitzungen genauso wie eine Code-Auswertung, und lies die Scores, bevor etwas live geht.

Sie kann auch für bereits vorhandene Sitzungen [nachträglich berechnet werden](/de/evaluations/deploy#score-sessions-you-already-have). Da pro Sitzung ein Modellaufruf anfällt, solltest du das Zeitfenster gezielt eingrenzen, statt alles erneut zu verarbeiten.
