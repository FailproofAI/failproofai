Diese Seite beschreibt die Frageformen und Bewertungsregeln hinter [Jev-Evaluierungen](/de/evaluations/jev). Manche Fragen erfordern ein Modell, das das Gespräch *liest*, aber nicht darüber *schreibt*. „Hat der Kunde Dringlichkeit ausgedrückt?" hat zwei Antworten. „Wie frustriert war er?" hat eine Handvoll, in einer bestimmten Reihenfolge. Alle Antworten sind bekannt, bevor man fragt.

Eine **Klassifikatorevaluierung** ist genau dafür gedacht. Man schreibt die Frage und die möglichen Antworten, und ein kleines, speziell für die Klassifikation entwickeltes Modell gibt eine kalibrierte Zahl zurück – niemals Freitext.

<Note>
Wie ein Richter kostet eine Klassifikatorevaluierung pro Sitzung einen Modellaufruf. Anders als ein Richter ist es jedoch ein kleines, zweckgebundenes Modell statt eines allgemeinen – daher ist es schneller und günstiger, erklärt sich aber nie selbst. Wenn die Begründung benötigt wird, sollte ein [Richter](/de/evaluations/judge) verwendet werden.
</Note>

## Was ist das Richtige für mich?

| Frage | Verwende |
| --- | --- |
| Wie viele Tool-Aufrufe gab es? | Code |
| Dauerte die Sitzung unter 30 Sekunden? | Code |
| Hat der Kunde Dringlichkeit ausgedrückt? | **Klassifikator** |
| Welches Team sollte sich darum kümmern: Abrechnung, Technik oder Vertrieb? | **Klassifikator** |
| Wie frustriert war der Kunde? | **Klassifikator** |
| War die Antwort tatsächlich korrekt? | **Richter** |
| Hat es unsere Eskalationsrichtlinie befolgt, und warum denkst du das? | **Richter** |

Die Faustregel: **zählbar → Code, auflistbare Antworten → Klassifikator, Erklärung erforderlich → Richter.**

Eine Vorabentscheidung ist nicht nötig. Beschreibe, was gemessen werden soll, und der Assistent wählt, teilt die Wahl und die Begründung mit, und es kann jederzeit gewechselt werden.

## Die zwei Fragetypen

### `noul` – ist das wahr?

Zwei Antworten, beide werden beschrieben. Das Ergebnis ist die Wahrscheinlichkeit, dass die „wahr"-Beschreibung zutrifft:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

Beide Seiten sollten beschrieben werden. „Keine Dringlichkeit ausgedrückt" ist eine echte Antwort, und diese explizit zu formulieren macht die andere Seite schärfer.

### `score` – wie viel davon?

Ein geordnetes Rubrik, **schlechtestes zuerst**. Das Ergebnis zeigt, wo die Sitzung darauf landet, auf 0–1 umskaliert:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**Eine Rubrik hat drei bis fünf Stufen, die alle unterschiedlich sein müssen.** Beide Grenzen sind gemessen, nicht stilistisch:

- **Zwei Stufen** kollabieren zu dem, was `noul` bereits besser macht, und **mehr als fünf** bringen das Modell dazu, zur Mitte hin auszuweichen statt sich festzulegen. Dieselbe Frage über dieselbe Sitzung ergab 0,00 mit zwei Stufen, 0,01 mit drei und 0,55 mit zehn.
- **Wiederholte Stufen** teilen die Antwort willkürlich auf. Eine eindeutig wütende Sitzung erzielte 1,00 gegen `["Calm", "Frustrated", "Very angry"]` und 0,66 gegen `["Angry", "Angry", "Angry"]` – eine formal korrekte Zahl, die jedoch nichts bedeutet.

Kategorien ohne Reihenfolge – „Abrechnung, Technik oder Vertrieb" – sind keine Rubrik. Sie sollten als `noul` pro Kategorie gefragt oder ein Richter verwendet werden.

## Ergebnisse lesen

Ein Klassifikator erzeugt eine **Bewertung** von 0 bis 1, genau wie ein Richter, und lässt sich daher genauso in Diagrammen darstellen, filtern und für Benachrichtigungen nutzen. Zwei Unterschiede sind wichtig:

- **Es gibt keine Begründung.** Das Feld ist absichtlich leer. Dieses Modell erklärt sich nicht selbst, und eine Erklärung zu erfinden wäre eine Fälschung und kein Feature.
- **Unsicherheit wird gekennzeichnet.** Eine `score`-Frage meldet ihre eigene Konfidenz, und ein Ergebnis, bei dem das Modell unsicher war, wird mit `low_confidence` markiert – so ist „welche davon sollte ein Mensch prüfen" ein Filter statt eine Schätzung. Eine `noul`-Frage meldet keine Konfidenz und wird daher nie markiert.

Sehr lange Sitzungen werden in Ausschnitten gelesen und zusammengeführt. Wenn eine Sitzung zu lang ist, um vollständig gelesen zu werden, gibt das Ergebnis an, wie viele Gesprächsrunden ausgelassen wurden – eine auf einem Teil der Sitzung basierende Beurteilung wird nie als vollständige Beurteilung dargestellt.

## Grenzen

- **Drei bis fünf Rubrikstufen, alle unterschiedlich.** Siehe oben; beide Grenzen werden zum Erstellungszeitpunkt erzwungen.
- **Eine Frage pro Evaluierung.** Werden zwei Dinge gefragt, entstehen zwei Evaluierungen – was in einem Diagramm ohnehin sinnvoller ist.
- **Das Bearbeiten der Frage veröffentlicht eine neue Version.** Alte und neue Bewertungen sind nicht vergleichbar und werden daher getrennt gehalten, statt in eine gemeinsame Trendlinie zu fließen.
- **Ein Klassifikator erzeugt immer eine Bewertung**, niemals eine Metrik oder eine Aussage.
- **Keine Begründung**, wie oben beschrieben. Wenn eine Zahl jemanden zu einem „Warum?" veranlassen wird, sollte stattdessen ein Richter geschrieben werden.

## Testen und Backfill

Anders als ein Richter **kann** eine Klassifikatorevaluierung getestet werden, bevor sie eingesetzt wird – [teste sie](/de/evaluations/test) gegen echte Sitzungen genauso wie eine Code-Evaluierung, und lese die Bewertungen, bevor etwas live geht.

Sie kann auch [zurückgefüllt](/de/evaluations/deploy#score-sessions-you-already-have) werden über Sitzungen, die bereits vorhanden sind. Es kostet pro Sitzung einen Modellaufruf, daher sollte das Zeitfenster gezielt eingegrenzt werden, statt alles zu wiederholen.
