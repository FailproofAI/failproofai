Diese Seite beschreibt die Frageformen und Bewertungsregeln hinter [Jev-Evaluierungen](/de/evaluations/jev). Manche Fragen erfordern, dass ein Modell das Gespräch *liest*, aber nicht darüber *schreibt*. „Hat der Kunde Dringlichkeit ausgedrückt?" hat zwei Antworten. „Wie frustriert waren sie?" hat einige, in einer bestimmten Reihenfolge. Alle Antworten kennt man, bevor man fragt.

Eine **Klassifizierungsevaluierung** ist genau dafür gedacht. Sie schreiben die Frage und die möglichen Antworten, und ein kleines, speziell für die Klassifizierung entwickeltes Modell gibt eine kalibrierte Zahl zurück – niemals Freitext.

<Note>
Wie ein Richter kostet eine Klassifizierungsevaluierung pro Sitzung einen Modellaufruf. Anders als ein Richtermodell ist es ein kleines, zweckgebundenes Modell statt eines allgemeinen – daher schneller und günstiger – es wird sich jedoch nie erklären. Wenn Sie die Begründung benötigen, verwenden Sie einen [Judge](/de/evaluations/judge).
</Note>

## Welche Variante brauche ich?

| Frage | Verwenden |
| --- | --- |
| Wie viele Tool-Aufrufe gab es? | Code |
| Dauerte die Sitzung unter 30 Sekunden? | Code |
| Hat der Kunde Dringlichkeit ausgedrückt? | **Klassifizierung** |
| Welches Team sollte sich darum kümmern: Abrechnung, Technik oder Vertrieb? | **Klassifizierung** |
| Wie frustriert war der Kunde? | **Klassifizierung** |
| War die Antwort tatsächlich korrekt? | **Judge** |
| Hat es unsere Eskalationsrichtlinie befolgt, und warum meinen Sie das? | **Judge** |

Die Faustregel lautet: **Zählbar → Code, aufzählbare Antworten → Klassifizierung, erfordert Begründung → Judge.**

Sie müssen sich nicht im Voraus entscheiden. Beschreiben Sie, was gemessen werden soll, und der Assistent wählt aus, teilt Ihnen mit, was er gewählt hat und warum – und Sie können jederzeit wechseln.

## Die zwei Fragetypen

### `noul` — Ist das wahr?

Zwei Antworten, und Sie beschreiben beide. Das Ergebnis ist die Wahrscheinlichkeit, dass die Beschreibung „wahr" zutrifft:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

Beschreiben Sie beide Seiten. „Keine Dringlichkeit ausgedrückt" ist eine echte Antwort – und sie zu formulieren macht die andere Seite schärfer.

### `score` — Wie viel davon?

Ein geordnetes Bewertungsraster, **schlechtester Wert zuerst**. Das Ergebnis gibt an, wo die Sitzung auf diesem Raster liegt, skaliert auf 0–1:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**Ein Bewertungsraster hat drei bis fünf Stufen, die alle unterschiedlich sein müssen.** Beide Grenzen sind messbar begründet, nicht stilistisch:

- **Zwei Stufen** reduzieren sich auf das, was `noul` bereits besser macht, und **mehr als fünf** veranlassen das Modell, zur Mitte hin zu tendieren, anstatt sich festzulegen. Dieselbe Frage über dieselbe Sitzung ergab 0,00 mit zwei Stufen, 0,01 mit drei und 0,55 mit zehn.
- **Wiederholte Stufen** verteilen die Antwort willkürlich zwischen ihnen. Eine eindeutig wütende Sitzung erzielte 1,00 gegenüber `["Calm", "Frustrated", "Very angry"]` und 0,66 gegenüber `["Angry", "Angry", "Angry"]` – eine formal korrekte Zahl ohne jede Aussagekraft.

Kategorien ohne Rangfolge – „Abrechnung, Technik oder Vertrieb" – sind kein Bewertungsraster. Stellen Sie sie als separate `noul`-Fragen pro Kategorie oder verwenden Sie einen Judge.

## Ergebnisse lesen

Eine Klassifizierung liefert einen **Score** von 0 bis 1, genau wie ein Judge – er lässt sich also genauso in Diagrammen darstellen, filtern und für Benachrichtigungen nutzen. Zwei Unterschiede sind erwähnenswert:

- **Es gibt keine Begründung.** Das Feld ist absichtlich leer. Dieses Modell erklärt sich nicht, und eine Begründung zu erfinden wäre eine Verfälschung, kein Feature.
- **Unsicherheit wird gekennzeichnet.** Eine `score`-Frage meldet ihre eigene Konfidenz; ein Ergebnis, bei dem das Modell unsicher war, wird mit `low_confidence` markiert – so ist „Welche davon sollte ein Mensch prüfen?" eine Filter- und keine Ratefrage. Eine `noul`-Frage meldet keine Konfidenz und wird daher nie so markiert.

Sehr lange Sitzungen werden in Ausschnitten gelesen und zusammengeführt. Wenn eine Sitzung zu lang ist, um vollständig gelesen zu werden, gibt das Ergebnis an, wie viele Gesprächsrunden ausgelassen wurden – eine Beurteilung auf Basis eines Ausschnitts wird nie als vollständige Beurteilung dargestellt.

## Einschränkungen

- **Drei bis fünf Bewertungsstufen, alle unterschiedlich.** Siehe oben; beide Grenzen werden beim Erstellen durchgesetzt.
- **Eine Frage pro Evaluierung.** Wenn Sie zwei Dinge abfragen möchten, erstellen Sie zwei Evaluierungen – das ist auch für Diagramme sinnvoller.
- **Das Bearbeiten der Frage veröffentlicht eine neue Version.** Alte und neue Scores sind nicht vergleichbar, daher werden sie getrennt gehalten und nicht in eine gemeinsame Trendlinie gemischt.
- **Eine Klassifizierung liefert immer einen Score**, nie eine Metrik oder Aussage.
- **Keine Begründung**, wie oben beschrieben. Wenn eine Zahl jemanden zu einem „Warum?" verleiten wird, schreiben Sie stattdessen einen Judge.

## Testen und Backfill

Anders als ein Judge kann eine Klassifizierungsevaluierung **bereits vor der Bereitstellung** getestet werden – [testen Sie sie](/de/evaluations/test) gegen echte Sitzungen, genau wie eine Code-Evaluierung, und lesen Sie die Scores, bevor etwas live geht.

Sie kann auch [nachträglich](/de/evaluations/deploy#score-sessions-you-already-have) auf bereits vorhandene Sitzungen angewendet werden. Da jede Sitzung einen Modellaufruf kostet, sollten Sie das Zeitfenster bewusst eingrenzen, anstatt alles erneut zu verarbeiten.
