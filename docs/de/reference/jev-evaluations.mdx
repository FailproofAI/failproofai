Diese Seite beschreibt die Fragenformate und Bewertungsregeln hinter [Jev-Evaluierungen](/de/evaluations/jev). Manche Fragen erfordern, dass ein Modell die Konversation *liest*, aber nicht *darüber schreibt*. „Hat der Kunde Dringlichkeit ausgedrückt?" hat zwei Antworten. „Wie frustriert waren sie?" hat eine Handvoll, in einer bestimmten Reihenfolge. Alle möglichen Antworten sind bekannt, bevor man fragt.

Eine **Classifier-Evaluierung** ist genau dafür gemacht. Sie schreiben die Frage und die möglichen Antworten, und ein kleines, speziell für Klassifikation entwickeltes Modell gibt eine kalibrierte Zahl zurück — niemals Freitext.

<Note>
Wie ein Richter benötigt auch eine Classifier-Evaluierung einen Modellaufruf pro Session. Im Unterschied dazu ist es jedoch ein kleines, zweckgebundenes Modell statt eines allgemeinen, was es schneller und günstiger macht — aber es wird sich niemals erklären. Wenn Sie die Begründung benötigen, verwenden Sie einen [Richter](/de/evaluations/judge).
</Note>

## Welche Option ist die richtige?

| Frage | Verwendung |
| --- | --- |
| Wie viele Tool-Aufrufe gab es? | Code |
| Dauerte die Session weniger als 30 Sekunden? | Code |
| Hat der Kunde Dringlichkeit ausgedrückt? | **Classifier** |
| Welches Team soll sich darum kümmern: Abrechnung, Technik oder Vertrieb? | **Classifier** |
| Wie frustriert war der Kunde? | **Classifier** |
| War die Antwort tatsächlich korrekt? | **Richter** |
| Hat es unsere Eskalationsrichtlinie befolgt, und warum denken Sie das? | **Richter** |

Die Faustregel: **Zählbares → Code, auflistbare Antworten → Classifier, Begründung erforderlich → Richter.**

Sie müssen sich nicht vorab entscheiden. Beschreiben Sie, was gemessen werden soll, und der Assistent wählt, teilt Ihnen mit, was er gewählt hat und warum — und Sie können es jederzeit ändern.

## Die zwei Fragentypen

### `noul` — ist das wahr?

Zwei Antworten, und Sie beschreiben beide. Das Ergebnis ist die Wahrscheinlichkeit, dass die „wahre" Beschreibung zutrifft:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

Beschreiben Sie beide Seiten. „Keine Dringlichkeit ausgedrückt" ist eine echte Antwort, und diese explizit zu formulieren schärft die andere.

### `score` — wie viel davon?

Eine geordnete Rubrik, **schlechtestes zuerst**. Das Ergebnis ist, wo die Session auf dieser Skala liegt, neu skaliert auf 0–1:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**Eine Rubrik umfasst drei bis fünf Stufen, die alle unterschiedlich sein müssen.** Beide Grenzen sind sachlich begründet, nicht stilistisch:

- **Zwei Stufen** reduzieren sich auf das, was `noul` bereits besser leistet, und **mehr als fünf** veranlassen das Modell dazu, zur Mitte hin auszuweichen statt sich festzulegen. Dieselbe Frage zur gleichen Session ergab 0,00 bei zwei Stufen, 0,01 bei drei und 0,55 bei zehn.
- **Wiederholte Stufen** teilen die Antwort willkürlich auf. Eine eindeutig wütende Session wurde mit 1,00 gegen `["Calm", "Frustrated", "Very angry"]` bewertet und mit 0,66 gegen `["Angry", "Angry", "Angry"]` — eine formal korrekte Zahl, die jedoch nichts bedeutet.

Kategorien ohne Reihenfolge — „Abrechnung, Technik oder Vertrieb" — sind keine Rubrik. Stellen Sie sie als separate `noul`-Fragen pro Kategorie oder verwenden Sie einen Richter.

## Ergebnisse interpretieren

Ein Classifier liefert einen **Score** von 0 bis 1, genau wie ein Richter, und lässt sich daher auf dieselbe Weise in Diagrammen darstellen, filtern und für Alerts verwenden. Zwei Unterschiede sind wichtig:

- **Es gibt keine Begründung.** Das Feld ist absichtlich leer. Dieses Modell erklärt sich nicht, und eine Erklärung zu erfinden wäre eine Fälschung statt ein Feature.
- **Unsicherheit wird gekennzeichnet.** Eine `score`-Frage meldet ihre eigene Konfidenz, und ein Ergebnis, bei dem das Modell unsicher war, wird als `low_confidence` markiert — „welche davon sollte ein Mensch prüfen" ist damit ein Filter statt eine Schätzung. Eine `noul`-Frage meldet keine Konfidenz und wird daher nie entsprechend markiert.

Sehr lange Sessions werden in Auszügen gelesen und zusammengeführt. Wenn eine Session zu lang ist, um sie vollständig zu lesen, gibt das Ergebnis an, wie viele Gesprächsrunden ausgelassen wurden — eine Bewertung, die nur auf einem Teil der Session basiert, wird niemals als Gesamtbewertung dargestellt.

## Grenzen

- **Drei bis fünf Rubrikstufen, alle unterschiedlich.** Siehe oben; beide Grenzen werden beim Erstellen durchgesetzt.
- **Eine Frage pro Evaluierung.** Wenn Sie zwei Dinge abfragen möchten, erstellen Sie zwei Evaluierungen — was auch für Diagramme sinnvoller ist.
- **Das Bearbeiten einer Frage veröffentlicht eine neue Version.** Alte und neue Scores sind nicht vergleichbar und werden daher getrennt gehalten, statt in einer gemeinsamen Trendlinie vermischt zu werden.
- **Ein Classifier liefert immer einen Score**, niemals eine Metrik oder eine Assertion.
- **Keine Begründung**, wie oben beschrieben. Wenn eine Zahl jemanden zu einem „Warum?" veranlassen wird, schreiben Sie stattdessen einen Richter.

## Tests und Backfill

Anders als ein Richter **kann** eine Classifier-Evaluierung getestet werden, bevor Sie sie einsetzen — [testen Sie sie](/de/evaluations/test) an echten Sessions auf dieselbe Weise wie eine Code-Evaluierung, und lesen Sie die Scores, bevor etwas live geht.

Sie kann auch [nachträglich](/de/evaluations/deploy#score-sessions-you-already-have) auf bereits vorhandene Sessions angewendet werden. Da pro Session ein Modellaufruf anfällt, sollten Sie das Zeitfenster bewusst eingrenzen, statt alles erneut zu verarbeiten.
