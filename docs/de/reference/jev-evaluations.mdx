Diese Seite beschreibt die Frageformen und Bewertungsregeln hinter [Jev-Evaluierungen](/de/evaluations/jev). Manche Fragen erfordern, dass ein Modell das Gespräch *liest*, aber nicht darüber *schreibt*. „Hat der Kunde Dringlichkeit signalisiert?" hat zwei Antworten. „Wie frustriert war er?" hat eine Handvoll, in einer bestimmten Reihenfolge. Alle Antworten sind bekannt, bevor man fragt.

Eine **Klassifikationsevaluierung** ist genau dafür gedacht. Man schreibt die Frage und die möglichen Antworten, und ein kleines, speziell für die Klassifikation entwickeltes Modell gibt eine kalibrierte Zahl zurück — niemals Freitext.

<Note>
Wie ein Richter kostet eine Klassifikationsevaluierung einen Modellaufruf pro Session. Anders als ein Richter ist es jedoch ein kleines, zweckgebundenes Modell statt eines allgemeinen — daher schneller und günstiger, aber es wird sich nie erklären. Wenn die Begründung benötigt wird, ist ein [Judge](/de/evaluations/judge) die richtige Wahl.
</Note>

## Welche Variante ist die richtige?

| Frage | Verwendung |
| --- | --- |
| Wie viele Tool-Aufrufe gab es? | Code |
| War die Session kürzer als 30 Sekunden? | Code |
| Hat der Kunde Dringlichkeit signalisiert? | **Klassifikation** |
| Welches Team sollte sich darum kümmern: Abrechnung, Technik oder Vertrieb? | **Klassifikation** |
| Wie frustriert war der Kunde? | **Klassifikation** |
| War die Antwort tatsächlich korrekt? | **Judge** |
| Hat es unsere Eskalationsrichtlinie eingehalten, und warum denkst du das? | **Judge** |

Die Faustregel: **Zählbares → Code, aufzählbare Antworten → Klassifikation, braucht eine Begründung → Judge.**

Diese Entscheidung muss nicht im Voraus getroffen werden. Man beschreibt, was gemessen werden soll, und der Assistent wählt aus, teilt mit, welche Variante gewählt wurde und warum — und man kann jederzeit wechseln.

## Die zwei Fragetypen

### `noul` — ist das wahr?

Zwei Antworten, und beide werden beschrieben. Das Ergebnis ist die Wahrscheinlichkeit, dass die Beschreibung von „wahr" zutrifft:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

Beide Seiten sollten beschrieben werden. „Keine Dringlichkeit geäußert" ist eine echte Antwort, und sie zu formulieren macht die andere schärfer.

### `score` — wie viel davon?

Ein geordnetes Rubrik-Schema, **beginnend mit dem schlechtesten Wert**. Das Ergebnis gibt an, wo die Session darauf landet, neu skaliert auf 0–1:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**Eine Rubrik umfasst drei bis fünf Stufen, die sich alle voneinander unterscheiden müssen.** Beide Grenzwerte sind messbar begründet, nicht stilistisch:

- **Zwei Stufen** kollabieren zu dem, was `noul` bereits besser leistet, und **mehr als fünf** veranlassen das Modell dazu, zur Mitte hin auszuweichen statt sich festzulegen. Dieselbe Frage über dieselbe Session ergab 0,00 mit zwei Stufen, 0,01 mit drei und 0,55 mit zehn.
- **Wiederholte Stufen** teilen die Antwort willkürlich unter ihnen auf. Eine Session, die eindeutig wütend war, erzielte 1,00 gegenüber `["Calm", "Frustrated", "Very angry"]` und 0,66 gegenüber `["Angry", "Angry", "Angry"]` — eine wohlgeformte Zahl, die nichts bedeutet.

Kategorien ohne Reihenfolge — „Abrechnung, Technik oder Vertrieb" — sind keine Rubrik. Sie sollten als `noul` pro Kategorie gestellt werden oder ein Judge verwendet werden.

## Ergebnisse interpretieren

Ein Klassifikator erzeugt einen **Score** von 0 bis 1, genau wie ein Judge — er lässt sich also auf dieselbe Weise in Diagrammen darstellen, filtern und für Alerts verwenden. Zwei Unterschiede sind relevant:

- **Es gibt keine Begründung.** Das Feld ist absichtlich leer. Dieses Modell erklärt sich nicht, und eine Erklärung zu erfinden wäre eine Fehlinformation, kein Feature.
- **Unsicherheit wird gekennzeichnet.** Eine `score`-Frage gibt ihre eigene Konfidenz an, und ein Ergebnis, bei dem das Modell unsicher war, wird als `low_confidence` markiert — „welche davon sollte ein Mensch prüfen" ist damit eine Filteroperation, keine Schätzung. Eine `noul`-Frage gibt keine Konfidenz an und wird daher nie markiert.

Sehr lange Sessions werden in Ausschnitten gelesen und zusammengeführt. Wenn eine Session zu lang ist, um vollständig gelesen zu werden, gibt das Ergebnis an, wie viele Turns ausgelassen wurden — es wird nie ein Urteil, das auf einem Teil einer Session basiert, als eines präsentiert, das auf der gesamten Session beruht.

## Grenzwerte

- **Drei bis fünf Rubrik-Stufen, alle unterschiedlich.** Siehe oben; beide Grenzen werden beim Erstellen durchgesetzt.
- **Eine Frage pro Evaluierung.** Bei zwei Fragen entstehen zwei Evaluierungen — was auch für Diagramme die richtige Vorgehensweise ist.
- **Das Bearbeiten einer Frage veröffentlicht eine neue Version.** Alte und neue Scores sind nicht vergleichbar und werden daher getrennt gehalten, anstatt in einer gemeinsamen Trendlinie vermischt zu werden.
- **Ein Klassifikator erzeugt immer einen Score**, niemals eine Metrik oder eine Aussage.
- **Keine Begründung**, wie oben. Wenn eine Zahl jemanden dazu veranlassen wird zu fragen „warum?", sollte stattdessen ein Judge erstellt werden.

## Testen und Backfill

Anders als ein Judge **kann** eine Klassifikationsevaluierung getestet werden, bevor sie eingesetzt wird — [testen](/de/evaluations/test) Sie sie gegen echte Sessions auf dieselbe Weise wie eine Code-Evaluierung, und lesen Sie die Scores, bevor etwas live geht.

Sie kann auch über bereits vorhandene Sessions [zurückgefüllt werden](/de/evaluations/deploy#score-sessions-you-already-have). Da pro Session ein Modellaufruf anfällt, sollte das Zeitfenster bewusst eingegrenzt werden, anstatt alles neu zu verarbeiten.
