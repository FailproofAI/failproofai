Diese Seite beschreibt die Frageformen und Bewertungsregeln hinter [Jev-Evaluationen](/de/evaluations/jev). Manche Fragen erfordern ein Modell, das das Gespräch *liest*, aber nicht *darüber schreibt*. „Hat der Kunde Dringlichkeit ausgedrückt?" hat zwei Antworten. „Wie frustriert war er?" hat eine Handvoll, in einer bestimmten Reihenfolge. Jede Antwort ist bekannt, bevor man fragt.

Eine **Klassifizierer-Evaluation** ist genau dafür gedacht. Du schreibst die Frage und die möglichen Antworten, und ein kleines, speziell für Klassifizierung entwickeltes Modell liefert eine kalibrierte Zahl zurück – niemals Freitext.

<Note>
Wie ein Richter kostet eine Klassifizierer-Evaluation einen Modellaufruf pro Sitzung. Im Unterschied zu einem Richter handelt es sich jedoch um ein kleines, zweckgebundenes Modell statt eines allgemeinen – es ist daher schneller und günstiger, erklärt sich aber nie selbst. Wenn du die Begründung benötigst, verwende einen [Judge](/de/evaluations/judge).
</Note>

## Was brauche ich?

| Frage | Verwende |
| --- | --- |
| Wie viele Tool-Aufrufe gab es? | Code |
| Dauerte die Sitzung weniger als 30 Sekunden? | Code |
| Hat der Kunde Dringlichkeit ausgedrückt? | **Klassifizierer** |
| Welches Team soll sich darum kümmern: Abrechnung, Technik oder Vertrieb? | **Klassifizierer** |
| Wie frustriert war der Kunde? | **Klassifizierer** |
| War die Antwort tatsächlich korrekt? | **Judge** |
| Hat es unsere Eskalationsrichtlinie befolgt, und warum glaubst du das? | **Judge** |

Die Faustregel: **Zählbares → Code, auflistbare Antworten → Klassifizierer, braucht eine Erklärung → Judge.**

Du musst dich nicht im Voraus entscheiden. Beschreibe, was gemessen werden soll, und der Assistent wählt aus, teilt dir mit, was er gewählt hat und warum – und du kannst es jederzeit ändern.

## Die zwei Fragetypen

### `noul` — Ist das wahr?

Zwei Antworten, und du beschreibst beide. Das Ergebnis ist die Wahrscheinlichkeit, dass die Beschreibung „wahr" zutrifft:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

Beschreibe beide Seiten. „Keine Dringlichkeit ausgedrückt" ist eine echte Antwort – sie zu formulieren macht die andere schärfer.

### `score` — Wie stark ist das ausgeprägt?

Ein geordnetes Rubric, **schlechteste Stufe zuerst**. Das Ergebnis gibt an, wo die Sitzung auf der Skala liegt, neu skaliert auf 0–1:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**Ein Rubric hat drei bis fünf Stufen, und alle müssen sich unterscheiden.** Beide Grenzen sind messbar begründet, nicht stilistisch:

- **Zwei Stufen** kollabieren zu dem, was `noul` bereits besser macht, und **mehr als fünf** verleiten das Modell dazu, sich zur Mitte hin zu orientieren statt klar zu entscheiden. Dieselbe Frage über dieselbe Sitzung ergab 0,00 bei zwei Stufen, 0,01 bei drei und 0,55 bei zehn.
- **Wiederholte Stufen** teilen die Antwort willkürlich zwischen ihnen auf. Eine Sitzung, die eindeutig wütend war, erzielte 1,00 gegen `["Calm", "Frustrated", "Very angry"]` und 0,66 gegen `["Angry", "Angry", "Angry"]` – eine wohldefinierte Zahl, die nichts bedeutet.

Kategorien ohne Reihenfolge – „Abrechnung, Technik oder Vertrieb" – bilden kein Rubric. Stelle sie als `noul` pro Kategorie, oder verwende einen Judge.

## Ergebnisse interpretieren

Ein Klassifizierer liefert einen **Score** von 0 bis 1, genau wie ein Judge – er lässt sich also genauso in Diagrammen darstellen, filtern und für Benachrichtigungen nutzen. Zwei Unterschiede sind wichtig:

- **Es gibt keine Begründung.** Das Feld ist absichtlich leer. Dieses Modell erklärt sich nicht selbst, und eine Erklärung zu erfinden wäre eine Fälschung, keine Funktion.
- **Unsicherheit wird gekennzeichnet.** Eine `score`-Frage meldet ihr eigenes Konfidenzmaß, und ein Ergebnis, bei dem das Modell unsicher war, wird mit `low_confidence` markiert – so ist „welche davon sollte ein Mensch prüfen" eine Filterfunktion statt eine Schätzung. Eine `noul`-Frage meldet keine Konfidenz und wird daher nie so markiert.

Sehr lange Sitzungen werden in Ausschnitten gelesen und zusammengeführt. Wenn eine Sitzung zu lang ist, um sie vollständig zu lesen, gibt das Ergebnis an, wie viele Gesprächsrunden ausgelassen wurden – du wirst nie eine Auswertung sehen, die auf einem Teil einer Sitzung basiert, aber als vollständige präsentiert wird.

## Grenzen

- **Drei bis fünf Rubric-Stufen, alle unterschiedlich.** Siehe oben; beide Grenzen werden beim Erstellen durchgesetzt.
- **Eine Frage pro Evaluation.** Stelle zwei Fragen, erhältst du zwei Evaluationen – was auch das ist, was du in einem Diagramm möchtest.
- **Das Bearbeiten der Frage veröffentlicht eine neue Version.** Alte und neue Scores sind nicht vergleichbar und werden daher getrennt gehalten, statt in einer Trendlinie vermischt zu werden.
- **Ein Klassifizierer liefert immer einen Score**, niemals eine Metrik oder eine Aussage.
- **Keine Begründung**, wie oben beschrieben. Wenn eine Zahl jemanden zu einem „Warum?" veranlasst, schreibe stattdessen einen Judge.

## Testen und Backfill

Anders als ein Judge **kann** eine Klassifizierer-Evaluation getestet werden, bevor du sie einführst – [teste sie](/de/evaluations/test) an echten Sitzungen genauso wie eine Code-Evaluation, und lies die Scores, bevor etwas live geht.

Sie kann außerdem über bereits vorhandene Sitzungen [rückwirkend angewendet werden](/de/evaluations/deploy#score-sessions-you-already-have). Da pro Sitzung ein Modellaufruf anfällt, sollte das Zeitfenster gezielt eingegrenzt werden, statt alles nochmals zu verarbeiten.
