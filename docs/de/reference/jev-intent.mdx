Wenn Sie [Jev Policy Review](/de/policies/jev) konfigurieren, bewertet der Evaluator jeden gesperrten Tool-Aufruf anhand von **dem, wonach der Mensch gefragt hat** – nicht anhand des Textes, den das Harness dem Agenten vorgelegt hat. Eine Antwort wie „ja, force-push it" kann eine **reviewable**-Policy freigeben – genau das ist der Zweck des Evaluators, denn ein Regex, der die Anfrage nicht lesen kann, blockiert ein Drittel aller realen Aufgaben.

Dieser Text stammt aus einer einzigen Quelle: **dem Prompt, den das Harness selbst beim Prompt-Submit-Ereignis an den Hook übergibt**. Failproof AI zeichnet den Teil davon auf, den der Mensch getippt hat – Harness-Wrapper entfernt, Geheimnisse geschwärzt, auf eine maximale Länge begrenzt – in einer `0600`-Datei unter seinem eigenen Zustandsverzeichnis. Nichts auf der Festplatte wird als Beweismittel herangezogen: Das Sitzungsprotokoll ist eine Datei, die der Agent mit einem einzigen Befehl überschreiben kann, daher wird nie danach gefragt, wer einen Prompt verfasst hat.

## Das akzeptierte Risiko, klar benannt

Ein Agent, der bereits Befehle ausführen kann, kann ein Harness dazu bringen, einen Prompt einzureichen. `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` und `pi -p` lösen alle dasselbe Prompt-Submit-Ereignis mit demselben Payload aus – genauso wie eine tippende Person –, und zwar in einer Kind-Sitzung, die der Agent kontrolliert. Er kann auch das Hook-Binary von Failproof AI selbst ausführen und ihm einen selbst geschriebenen Payload übergeben. Failproof AI kann das eine nicht vom anderen unterscheiden – beides ist dasselbe Programm, das dasselbe stdin liest.

**Ein Agent mit Shell-Zugriff kann also seine eigene Zustimmung fälschen.** Das ist ein bewusster Kompromiss, der am 2026-09-23 eingegangen wurde. Hier sind beide Seiten davon:

- **Was dadurch gewonnen wird.** Die Alternative wurde gebaut und gemessen: Ein Feld verlangen, in dem das Harness einen Menschen als Autor des Prompts benennt, und andernfalls nichts aufzeichnen. Kein ausgeliefertes Harness sendet ein solches Feld, sodass diese Version **auf jedem Harness nichts aufgezeichnet hat** – Jev beurteilte jeden Aufruf ohne angegebene Absicht und konnte nie eine einzige Policy freigeben. Eine Erfassung, die nie auslöst, ist kein sichereres Produkt, sondern gar kein Produkt.
- **Was dadurch nicht möglich ist.** Ein aufgezeichneter Prompt kann nur eine Policy freigeben, die bereits als **reviewable** markiert ist. Eine **hard**-Policy wird durch nichts, was Jev sagt, freigegeben – ein gefälschter Prompt kann also aus einem harten Deny kein Allow machen. Das Überspringen des Hooks bringt einem Agenten ebenfalls nichts: Das Harness ruft Failproof AI für den Tool-Aufruf unabhängig davon auf.
- **Was im schlimmsten Fall möglich ist.** Das Schlimmste ist, eine der fünfzehn reviewable Built-in-Policies freizugeben – und **zwölf dieser fünfzehn blockieren**. `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` und die sechs Infrastruktur-CLI-Sperren (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) sind Denies – eine gefälschte Zustimmung kann also aus einem echten Deny ein Allow machen beim Ausgeben von Umgebungsgeheimnissen, Lesen einer `.env`-Datei, Lesen außerhalb des Projekts, `rm -rf`, einem Force-Push, dem Schreiben einer Secrets-Datei oder dem Ändern von Live-Infrastruktur. Nur `warn-git-amend`, `warn-destructive-sql` und `warn-global-package-install` sind Hinweise. Eine Standard-Installation aktiviert zwei der zwölf: `protect-env-vars` und `block-env-files`; die anderen zehn sind nur auf Maschinen aktiv, auf denen jemand sie explizit aktiviert hat. Was kein Prompt erreichen kann, ist alles Harte – `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, der Guard, der einen Agenten daran hindert, Failproof AI zu deaktivieren, und alle anderen Built-ins, die nicht als reviewable markiert sind. [Policy Authority](/de/policies/authority) listet alle fünfzehn und was jede einzelne bewertet.

Was weiterhin abgelehnt wird, ist alles, was günstig zu prüfen ist und was ein Agent nicht allein durch Fragen erhalten kann: ein Turn, den der eigene Payload des Harness als maschinell eingereicht kennzeichnet, ein Payload, der einen Sub-Agenten benennt, eine Sitzungs-ID, die kein einfacher Name ist, ein Ereignis, das kein Prompt-Submit ist, und Text, der nur aus Harness-Wrapping besteht – einschließlich der eigenen Stop-Gate-Wörter von Failproof AI, die mehrere Harnesses als nächsten User-Turn zurückgeben.

## Tabelle pro Harness

„Text field" ist das stdin-Payload-Feld nach der harnessspezifischen Normalisierung von Failproof AI. „Recorded" gibt an, ob der Prompt als Anfrage des Menschen gespeichert wird.

| Harness | `--cli` | Prompt-Ereignis → kanonisch | Text-Feld | Aufgezeichnet | Letzte Agentennachricht gelesen aus |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | Ja, es sei denn, der `source`-Wert des Payloads benennt einen Turn, den niemand eingereicht hat (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`). `user`, `sdk`, ein unbekannter Wert und ein Build, der überhaupt kein `source` sendet, werden alle aufgezeichnet | das Sitzungsprotokoll (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | Ja | das Rollout-JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | Ja | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | Ja, mit abgestreiftem `<user_query>`-Wrapper, wenn dieser der gesamte Prompt ist | das Agenten-Transkript-JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | Ja – aber das aktuelle OpenCode enthält keinen Text in diesem Ereignis, sodass in der Praxis nichts aufgezeichnet wird; eine Wiederholung derselben Nachricht wird einmal aufgezeichnet | keine (Sitzungen sind SQLite) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | Ja, es sei denn, `input_source` ist `extension` – ein `sendUserMessage()` einer anderen Extension, deren Text modellgeneriert oder repository-abgeleitet sein kann | das Pi-Sitzungs-JSONL |
| Hermes | `hermes` | keine | — | Nein – Hermes hat überhaupt kein Prompt-Submit-Ereignis | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | Ja, es sei denn, die Run-Metadaten kennzeichnen den Run als maschinell: ein `trigger` außer `user`, ein `inputProvenance.kind` außer `external_user`, oder `senderIsOwner: false` | keine (`before_agent_run` enthält keinen Transkriptpfad) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | Ja | das Droid-Sitzungs-JSONL |

| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | keine | Nein – `PreInvocation` wird vor *jedem* Modellaufruf in einem Turn ausgelöst und enthält keinen Prompt-Text | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | Ja | keine (Sitzungen sind SQLite) |

Zwei Harnesses zeichnen nichts auf, und aus demselben Grund in beiden Fällen: Ihr Ereignis liefert keinen menschlichen Text. Hermes hat kein Prompt-Submit-Ereignis – sein natives Plugin verarbeitet `pre_llm_call` selbst und leitet nur Tool-, Sitzungs- und Sub-Agenten-Ereignisse weiter. Antigravitys `PreInvocation` wird vor jedem Modellaufruf ausgelöst, bei einem menschlichen Turn und bei den fünf, die ihm folgen, und enthält kein Prompt-Feld; Hooks können auch `userMessage`-Schritte in dieselbe Konversation injizieren. In keinem der beiden Ereignisse gibt es etwas aufzuzeichnen.

## Was einen Prompt zum menschlichen macht

1. **Das Ereignis.** Failproof AI wurde für das Prompt-Submit-Ereignis des Harness aufgerufen, das der Handler zu `UserPromptSubmit` kanonisiert.
2. **Der Payload.** Das Harness schreibt ihn auf stdin des Hooks und enthält den Text im oben genannten Feld. Ein Aufruf, der Failproof AI ohne Payload erreicht, zeichnet nichts auf.
3. **Nichts im Payload schließt den Turn aus.** Ein Payload, der einen Sub-Agenten benennt (`agent_id`), ist der Agent, der sich selbst promptet. Ein `source`-, `input_source`- oder OpenClaw-Run-Marker, der einen maschinell eingereichten Turn kennzeichnet, wird abgelehnt. Ein **fehlender** Marker schließt nichts aus – das ist der Unterschied zur Version, die nichts aufgezeichnet hat, da jeder Marker hier auf jedem ausgelieferten Build fehlt.
4. **Nach dem Entfernen des Wrappers bleibt etwas übrig** (siehe unten).

**Das Sitzungsprotokoll ist kein Beweis dafür, wer einen Prompt verfasst hat.** Frühere Versionen dieser Seite beschrieben eine Protokoll-Gegenprüfung: Der Prompt wurde abgelehnt, wenn das Protokoll zeigte, dass das Modell ihn eingeplant hatte, und das Protokoll musste das des vorherigen Prompts fortsetzen. Diese Prüfung ist weggefallen. Ein Protokoll ist eine Datei, über die der Agent bereits Shell-Zugriff hat – es kann abgeschnitten, ersetzt, über das Lesebudget hinaus aufgefüllt, am Anfang eines Turns als Snapshot gespeichert und am Ende wiederhergestellt oder mit vom Agenten geschriebenen Einträgen wieder plausibel gemacht werden. Auf jede Verschärfung folgte eine weitere Variante derselben Fälschung, daher wurde der gesamte Mechanismus entfernt statt repariert.

Das Protokoll wird noch für eine Sache gelesen: **die letzte sichtbare Nachricht des Agenten**. Diese Nachricht ist per Definition vom Agenten geschrieben, Jev wird darüber informiert, und sie ist für sich allein nie eine Zustimmung.

## Was von einem Prompt behalten wird

Harnesses fügen einem Prompt mehr als die Worte des Menschen hinzu. Bevor etwas gespeichert wird:

- `<system-reminder>`-Blöcke werden entfernt, die Worte des Menschen drumherum bleiben erhalten.
- Eine Sitzungsfortsetzungs-Zusammenfassung („This session is being continued from a previous conversation…") wird vollständig verworfen.
- Aufgabenbenachrichtigungen, lokale Befehlsausgaben und Unterbrechungsmarkierungen werden vollständig verworfen.
- Ein Turn, den ein anderer Agent oder eine andere Sitzung verfasst hat, wird vollständig verworfen: Claude Code umschließt diese in `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` oder `<channel source=…>`.
- Eigene Nachrichten von Failproof AI werden vollständig verworfen. Ein `MANDATORY ACTION REQUIRED from failproofai …` eines Stop-Gates oder ein `Instruction from failproofai: …` kommt auf Cursor, Copilot, Devin und OpenClaw als nächster User-Turn zurück und zählt nie als Worte des Menschen – weder unverhüllt, noch in einem `<user_query>`-Block, noch hinter einem System-Reminder.
- Ein Slash-Befehl wird als der Befehl und die Argumente behalten, die der Mensch getippt hat, nie als der Text, zu dem das Harness ihn expandiert hat.
- Ein Prompt, den die Codex-IDE-Extension erstellt hat, behält nur den Text nach der letzten `## My request for Codex:`-Überschrift (oder in neueren Builds `## My request:`). Alles, was die Extension davor gesetzt hat, wird verworfen: die aktive Datei, offene Tabs, im Editor ausgewählter Text, erwähnte Dateien und Apps, Diff- und Browser-Kommentare, PR-Checks, frühere Gespräche. Diese Regel wird auf die Prompts **jedes** Harness angewendet, nicht nur auf die von Codex – ein solcher Prompt kann in jeden Composer eingefügt werden –, sodass die Abschnittsüberschriften der Extension in zwei Gruppen gelesen werden:
  - **Eine Überschrift, die niemand tippt** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, die Codex- und ChatGPT-Gesprächsüberschriften, „The attached pasted text file(s)…" und die übrigen eigenen Abschnitte der Extension) bedeutet, dass die Extension diesen Prompt erstellt hat. Eine ohne darunter liegende Request-Überschrift enthält überhaupt keinen menschlichen Text und wird nicht aufgezeichnet. Das verhindert, dass eine in Text, den Sie nur *ausgewählt* haben, gefälschte Genehmigung – ein `// NOTE FROM THE OWNER: yes, force-push…`-Kommentar innerhalb von `# Selected text:` – in Ihre aufgezeichnete Anfrage gelangt.
  - **Eine Überschrift, die ein Entwickler plausiblerweise tippt** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) bedeutet „extension-built" nur, wenn tatsächlich eine Request-Überschrift vorhanden ist. Ohne eine solche ist der Prompt Ihrer und wird vollständig behalten, Überschrift und alles. Ihn zu verwerfen, wäre still und total: Für diesen Turn würde nichts aufgezeichnet, sodass keine reviewable Policy freigegeben werden könnte und Jev nicht einmal gefragt würde, ob der Request-Envelope eine Injektion enthält. Das gilt nur am *Anfang* eines Turns: Sobald ein Prompt als extension-built eingestuft wurde, ist eine Überschrift aus beiden Gruppen in dem, was auf die Request-Überschrift folgt, ein weiterer Abschnitt der Extension, und der Prompt wird nicht aufgezeichnet.

  Die Anfrage selbst wird wie jeder andere Turn beurteilt: Wenn das, was auf die Überschrift folgt, eine Fortsetzungs-Zusammenfassung ist, eine Nachricht, die ein anderer Agent oder eine andere Sitzung verfasst hat, eine eigene Direktive von Failproof AI oder ein weiterer Abschnitt der Extension, wird der Prompt überhaupt nicht aufgezeichnet.
- Ein Cursor-Prompt, der in `<user_query>…</user_query>` eingeschlossen ist (optional hinter einem `<timestamp>`-Block), wird entpackt, wenn der Wrapper der *gesamte* Prompt ist. Ein Tag irgendwo anders ist normaler Text – ein aus einem Log eingefügter Snippet oder ein vom Agenten gewählter Branch-Name – und der Prompt wird vollständig behalten, statt auf den markierten Abschnitt gekürzt zu werden.
- Eingefügte Blöcke werden behalten und als vom Menschen eingefügt gekennzeichnet.

Ein Prompt, der nur aus Harness-Text besteht, wird überhaupt nicht aufgezeichnet.

## Die letzte Nachricht des Agenten

Eine Antwort wie „ja" bedeutet nichts ohne die Frage, die sie beantwortet. Wenn ein Prompt aufgezeichnet wird, liest Failproof AI auch die letzte sichtbare Nachricht des Agenten aus dem Sitzungsprotokoll **in diesem Moment** und speichert sie zusammen mit dem Prompt. Jev erhält sie in einem eigenen Feld, als vom Agenten geschrieben gekennzeichnet: Sie erklärt eine kurze Antwort und zählt für sich allein nie als Anfrage des Menschen. Sie ist das Einzige, wofür das Protokoll gelesen wird, und das Schlimmste, was ein umgeschriebenes Protokoll bewirken kann, ist, eine vom Agenten geschriebene Nachricht dort zu platzieren, wo eine vom Agenten geschriebene Nachricht erwartet wird.

Sie wird vom Ende des Protokolls gelesen, höchstens die letzten 4 MB. Unterstützte Transkriptformate sind Claude Code, Codex-Rollouts (ältere `agent_message`-Ereignisse und neuere `AgentMessage`-Elemente), Cursor, Copilot `events.jsonl` sowie das Pi-, Factory- und OpenClaw-Sitzungs-JSONL. Die eigenen synthetischen Nachrichten und API-Fehlermeldungen von Claude Code sowie Sub-Agenten-Nachrichten (Sidechain) werden übersprungen. Es gibt keinen Snapshot für Goose und OpenCode, die Sitzungen in SQLite speichern, für Devin, dessen Transkript ein einzelnes JSON-Dokument ist, oder für OpenClaw, dessen `before_agent_run`-Ereignis keinen Transkriptpfad enthält.

## Speicherung

| Eigenschaft | Wert |
| --- | --- |
| Speicherort | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, wobei `<profile>` das Agentenprofil ist, in das der Prompt eingegeben wurde: `<integration>.<instance-id>` für einen Agenten, den FailproofAI kennt (die Identität, auf die Cloud-Policies abzielen), oder andernfalls nur `<integration>` |
| Berechtigungen | Datei `0600`, Verzeichnis `0700`. Jedes Verzeichnis darüber bis `~/.failproofai` unterliegt derselben Regel wie das Verzeichnis von `jev.json`: Eines, in das jemand anderes **schreiben** kann, könnte umbenannt und ersetzt werden – daher entfernt der Lesepfad diese Schreibbits, wo er kann, und liest **nichts**, wo er es nicht kann. Ein aufgezeichneter Prompt ist dann abwesend statt gefälscht, und nichts wird freigegeben |
| Gespeichert pro Sitzung | die letzten 5 Prompts; ein Prompt, der mit dem vorherigen identisch ist, ersetzt ihn, statt einen neuen Slot zu belegen |
| Zeitfenster | Prompts, die älter als 6 Stunden sind, werden ignoriert |
| Größe | jeder Prompt und jede Agentennachricht ist auf 6.000 Zeichen begrenzt, wobei Anfang und Ende behalten werden |
| Geheimnisse | vor dem Schreiben mit denselben Mustern wie die `sanitize-*`-Policies geschwärzt. Ein Text länger als 48.000 Zeichen wird als seine ersten 28.800 und letzten 19.200 Zeichen geschwärzt, und der Text neben diesen Schnittstellen, wo ein Geheimnis aufgeteilt worden sein könnte, wird nie gespeichert |

Eine Sitzungs-ID, die etwas anderes als Buchstaben, Ziffern, `.`, `_` und `-` enthält oder länger als 128 Zeichen ist, wird nie als Dateiname verwendet, sodass für sie nichts aufgezeichnet wird.

Eine Sitzungsdatei existiert erst, nachdem ein Prompt darin aufgezeichnet wurde. Sie enthält nur Prompts und sonst nichts – keinen Ursprungszustand, keine Transkriptmarkierung – und wird gelöscht, sobald sie länger als das Sechs-Stunden-Fenster inaktiv war, beim nächsten Mal, wenn eine neue Sitzung ihren ersten Prompt schreibt.

Ein Prompt wird nur für dasselbe Agentenprofil und dieselbe Sitzungs-ID zurückgelesen, unter der er aufgezeichnet wurde. Sitzungs-IDs stammen vom Agenten, sodass zwei Profile dieselbe verwenden können; die Schlüsselung nach Profil verhindert, dass die Worte eines Profils je als Anfrage eines anderen gelten. Dateien aus früherer Zeit dieses Layouts (`sessions/<session-id>.json`) können nicht angeben, welches Profil sie geschrieben hat, werden daher nie gelesen und laufen mit dem Sechs-Stunden-Fenster ab.

Es wird nichts aufgezeichnet, solange kein Jev-Endpoint konfiguriert ist. Im FailproofAI Cloud Jev-Modus wird nichts für ein Agentenprofil aufgezeichnet, dem keine Cloud-Jev-Prüfung zugewiesen ist und dessen keine installierten Pack-Prüfungen prüft.

### Das Projektstammverzeichnis

„Innerhalb des Projekts" – was `read-outside-workspace` und die anderen Pfadprüfungen beurteilen – bedeutet innerhalb des Projekts, in dem sich die Sitzung beim **ersten überprüften Aufruf** befand. Das Stammverzeichnis wird dann festgelegt, und ein späteres `cd` verschiebt es nie; ein `cd` ändert aber immer noch, wie ein relativer Pfad aufgelöst wird. Würde es dem `cd` folgen, würde `cd ~/.ssh` in einem Aufruf `~/.ssh` zum Projekt für den nächsten machen.

Die Festlegung erfolgt in `~/.failproofai/state/semantic/roots/<session-id>.json` mit dem Inhalt `{root, at}`: Datei `0600`, Verzeichnis `0700`, und dieselbe Sitzungs-ID-Regel wie oben. Dateien, die älter als 7 Tage sind, werden gelöscht, wenn eine neue Sitzung ihr Stammverzeichnis festlegt. Ein `roots`-Verzeichnis, in das andere Benutzer schreiben können, wird ignoriert, und stattdessen wird das Stammverzeichnis des Live-Verzeichnisses verwendet. Um eine Sitzung neu festzulegen, löschen Sie ihre Datei.

## Bekannte Einschränkungen

- **Ein Prompt ist nur so vertrauenswürdig wie der Hook-Aufruf.** Alles hier liest den Payload, den das Harness auf stdin des Hooks geschrieben hat. Ein Agent, der Befehle ausführen kann, kann das Harness headless starten (`claude -p` und die sieben anderen oben aufgelisteten) oder das Hook-Binary von Failproof AI selbst mit einem selbst geschriebenen Payload ausführen und einen Prompt aufzeichnen, den niemand getippt hat. Das ist der am Anfang dieser Seite beschriebene akzeptierte Kompromiss: Es werden nur reviewable Policies freigegeben, nie eine harte – aber zwölf der fünfzehn reviewable Built-ins sind Denies, sodass ein gefälschter Prompt bei diesen zwölf aus einem echten Block ein Allow machen kann.
- **Sub-Agenten-Erkennung ist Claude-förmig.** Ein Payload mit `agent_id` wird auf keinem Harness aufgezeichnet. Das ist das Feld, das Claude Code, Factory Droid und Devin verwenden würden. Codex löst sein Prompt-Ereignis innerhalb von Sub-Agenten-Threads aus, Copilot betreibt In-Process-Sidekicks, Goose hat ein `delegate`-Tool und OpenClaw betreibt Personas – keines davon markiert den Payload auf eine Weise, die dies erkennt, sodass ein Sub-Agenten-Prompt auf diesen Harnesses als sitzungseigener aufgezeichnet wird. OpenClaws `openclaw.agentId` ist **nicht** diese Markierung: das ausgelieferte Plugin setzt es bei jedem Run, einschließlich dem des Eigentümers.
- **Scheduler ohne Marker.** Claude Codes `schedule_wakeup` und `loop_wakeup` sowie OpenClaws `cron`- und `heartbeat`-Trigger werden abgelehnt, weil diese Harnesses das im Payload angeben. Gooses eigener Scheduler (`goose schedule add`) und Codex' `codex exec` geben nichts an, sodass ein von ihnen gestarteter Run wie jeder andere aufgezeichnet wird.
- **Die letzte Nachricht eines Agenten kann eine selbst gewählte Nachricht sein.** Das Transkript ist nicht authentifiziert, sodass ein Agent, der sein eigenes Transkript schreibt, entscheiden kann, was seine „letzte Nachricht" besagt. Sie ist als agentengeschrieben gekennzeichnet und gibt für sich allein nichts frei – beachten Sie jedoch, dass der v1-Pfad von `decide.ts` es ermöglicht, die deterministische Prüfung „hat der Benutzer dieses Ziel benannt" zu erfüllen, sodass ein Agent, der sein Transkript kontrolliert, einen Zielnamen angeben kann, den ein Override benötigt.
- **Ein Prompt, der mit einer der maschinellen Extension-Überschriften beginnt, wird vollständig verworfen.** Beginnen Sie einen Prompt mit `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` oder einer anderen Abschnittsüberschrift aus der ersten Gruppe oben, und schreiben Sie keine `## My request:`-Überschrift, wird für diesen Turn nichts aufgezeichnet – also auch nichts freigegeben. Das ist beabsichtigt: Diese Abschnitte enthalten Text, den jemand anderes kontrolliert (Code, den Sie ausgewählt haben, der Diff-Kommentar eines Reviewers, ein Seitentitel), und diesen als Ihre Worte aufzuzeichnen, wäre das schlechtere Versagen. Überschriften, die ein Entwickler plausiblerweise tippt, befinden sich in der zweiten Gruppe und verwerfen einen Prompt nie für sich allein.
- **OpenCode zeichnet in der Praxis nichts auf.** Sein `message.updated`-Ereignis enthält im aktuellen OpenCode keinen Text und wird auch für die Kind-Sitzungen ausgelöst, die sein Task-Tool erstellt, deren „user"-Nachricht der übergeordnete Agent geschrieben hat.
- **`CODEX_HOME` wird nicht berücksichtigt** von der Rollout-Discovery in `lib/codex-sessions.ts`. Dies betrifft nur den Ort, wo nach einem Agentennachrichten-Snapshot gesucht wird, nie ob ein Prompt aufgezeichnet wird.
