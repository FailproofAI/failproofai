Wenn Sie die [Jev-Richtlinienprüfung](/de/policies/jev) konfigurieren, beurteilt der Evaluator jeden gesperrten Tool-Aufruf anhand von **dem, was der Nutzer angefragt hat** – nicht anhand des Textes, den das Harness dem Agenten präsentiert hat. Eine Antwort wie „ja, force-push es" kann eine **reviewable**-Richtlinie freigeben – und genau das ist der Zweck des Evaluators, da ein Regex, der die Anfrage nicht lesen kann, ein Drittel aller echten Aufgaben blockiert.

Dieser Text stammt aus einer einzigen Quelle: **dem Prompt, den das Harness selbst beim Prompt-Submit-Ereignis an den Hook übergibt**. Failproof AI zeichnet den vom Menschen eingegebenen Teil auf – Harness-Verpackung entfernt, Geheimnisse geschwärzt, auf ein Maximum begrenzt – und speichert ihn in einer `0600`-Datei in seinem eigenen Zustandsverzeichnis. Nichts auf der Festplatte wird zu Rate gezogen: Das Sitzungsprotokoll ist eine Datei, die der Agent mit einem einzigen Befehl überschreiben kann, daher wird nie gefragt, wer einen Prompt verfasst hat.

## Das damit verbundene Risiko, klar benannt

Ein Agent, der bereits Befehle ausführen kann, kann ein Harness veranlassen, einen Prompt einzureichen. `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` und `pi -p` lösen alle dasselbe Prompt-Submit-Ereignis mit derselben Nutzlast aus – genauso wie eine Person, die eintippt – und zwar in einer untergeordneten Sitzung, die der Agent kontrolliert. Er kann auch Failproof AIs eigenes Hook-Binary ausführen und ihm eine selbst verfasste Nutzlast übergeben. Nichts innerhalb von Failproof AI kann beides vom Original unterscheiden – beides ist dasselbe Programm, das denselben stdin liest.

**Ein Agent mit Shell-Zugang kann also seine eigene Zustimmung fälschen.** Das ist ein bewusster Kompromiss, der am 2026-09-23 eingegangen wurde. Hier sind beide Seiten davon:

- **Was es bringt.** Die Alternative wurde entwickelt und gemessen: ein Feld verlangen, in dem das Harness einen Menschen als Verfasser des Prompts benennt, und andernfalls nichts aufzeichnen. Kein ausgeliefertes Harness sendet ein solches Feld, sodass diese Version **nichts, bei jedem Harness** aufgezeichnet hat – Jev beurteilte jeden Aufruf ohne angegebene Absicht und konnte keine einzige Richtlinie freigeben. Eine Erfassung, die niemals auslöst, ist kein sichereres Produkt, sondern überhaupt kein Produkt.
- **Was es nicht leisten kann.** Ein aufgezeichneter Prompt kann immer nur eine Richtlinie freigeben, die bereits als **reviewable** markiert ist. Eine **hard**-Richtlinie wird durch nichts, was Jev sagt, jemals aufgehoben, sodass ein gefälschter Prompt einen hard-deny niemals in ein allow umwandeln kann – und das Überspringen des Hooks bringt einem Agenten ebenfalls nichts: Das Harness ruft Failproof AI für den Tool-Aufruf unabhängig davon auf.
- **Was er im schlimmsten Fall bewirken kann.** Das Schlimmste ist, eine der fünfzehn reviewable eingebauten Richtlinien freizugeben – und **zwölf dieser fünfzehn blockieren**. `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` und die sechs Infrastruktur-CLI-Blöcke (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) sind Denials, sodass eine gefälschte Zustimmung einen echten Deny in ein Allow verwandeln kann für: das Ausgeben von Umgebungsgeheimnissen, das Lesen einer `.env`-Datei, das Lesen außerhalb des Projekts, `rm -rf`, einen Force-Push, das Schreiben einer Secrets-Datei oder das Ändern von Live-Infrastruktur. Nur `warn-git-amend`, `warn-destructive-sql` und `warn-global-package-install` sind Hinweise. Eine Standardinstallation aktiviert zwei der zwölf, `protect-env-vars` und `block-env-files`; die anderen zehn sind nur auf einem Rechner erreichbar, wo jemand sie aktiviert hat. Was kein Prompt erreicht, ist alles Harte – `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, der Schutz, der einen Agenten daran hindert, Failproof AI zu deaktivieren, und alle anderen eingebauten Richtlinien, die nicht als reviewable markiert sind. [Richtlinienkompetenz](/de/policies/authority) listet alle fünfzehn auf und was jede davon prüft.

Was dennoch abgelehnt wird, ist alles, was günstig zu prüfen ist und was ein Agent nicht einfach durch Fragen erlangen kann: ein Turn, den die eigene Nutzlast des Harness als maschinell eingereicht kennzeichnet, eine Nutzlast, die einen Sub-Agenten benennt, eine Sitzungs-ID, die kein einfacher Name ist, ein Ereignis, das nicht das Prompt-Submit-Ereignis ist, und Text, der nur aus Harness-Verpackung besteht – einschließlich Failproof AIs eigener Stop-Gate-Wörter, die mehrere Harnesses als nächsten Nutzerturn zurückgeben.

## Tabelle nach Harness

„Textfeld" ist das stdin-Nutzlastfeld nach Failproof AIs harness-spezifischer Normalisierung. „Aufgezeichnet" gibt an, ob der Prompt als Nutzeranfrage gespeichert wird.

| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | Ja, es sei denn, der `source`-Wert der Nutzlast benennt einen Turn, den niemand eingereicht hat (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`). `user`, `sdk`, ein unbekannter Wert und ein Build, der gar kein `source`-Feld sendet, werden alle aufgezeichnet | das Sitzungsprotokoll (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | Ja | das Rollout-JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | Ja | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | Ja, wobei der `<user_query>`-Wrapper entfernt wird, wenn er den gesamten Prompt umfasst | das Agenten-Protokoll-JSONL |
| OpenCode | `opencode` | `message.updated` (Nutzer-Rolle) → `UserPromptSubmit` | `prompt` | Ja – aber aktuelles OpenCode überträgt keinen Text in diesem Ereignis, sodass in der Praxis nichts aufgezeichnet wird; eine Wiederholung derselben Nachricht wird einmal aufgezeichnet | keines (Sitzungen sind SQLite) |

| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | Ja, es sei denn, die Run-Metadaten kennzeichnen den Run als maschinell: ein `trigger` ungleich `user`, ein `inputProvenance.kind` ungleich `external_user`, oder `senderIsOwner: false` | keines (`before_agent_run` enthält keinen Protokollpfad) |

Zwei Harnesses zeichnen nichts auf, und das aus demselben Grund: Ihr Ereignis liefert keinen menschlichen Text. Hermes hat kein Prompt-Submit-Ereignis – sein natives Plugin verarbeitet `pre_llm_call` selbst und leitet nur Tool-, Sitzungs- und Sub-Agenten-Ereignisse weiter. Antigravitys `PreInvocation` löst vor jedem Modellaufruf aus – bei einem Nutzerturn und bei den fünf darauf folgenden – und enthält kein Prompt-Feld; Hooks können auch `userMessage`-Schritte in dasselbe Gespräch injizieren. In keinem der beiden Ereignisse gibt es etwas aufzuzeichnen.

## Was einen Prompt zum Prompt des Menschen macht

1. **Das Ereignis.** Failproof AI wurde für das Prompt-Submit-Ereignis des Harness aufgerufen, das der Handler zu `UserPromptSubmit` kanonisiert.
2. **Die Nutzlast.** Das Harness schreibt sie auf den stdin des Hooks und trägt den Text in dem oben genannten Feld. Ein Aufruf, der Failproof AI ohne Nutzlast erreicht, zeichnet nichts auf.
3. **Nichts in der Nutzlast schließt den Turn aus.** Eine Nutzlast, die einen Sub-Agenten benennt (`agent_id`), ist der Agent, der sich selbst eingibt. Ein `source`-, `input_source`- oder OpenClaw-Run-Marker, der einen maschinell eingereichten Turn benennt, wird abgelehnt. Ein **fehlender** Marker schließt nichts aus – das ist der Unterschied zur Version, die nichts aufgezeichnet hat, da jeder dieser Marker bei jedem ausgelieferten Build fehlt.
4. **Nach dem Entfernen der Verpackung bleibt noch etwas übrig** (siehe unten).

**Das Sitzungsprotokoll ist kein Beweis dafür, wer einen Prompt verfasst hat.** Frühere Versionen dieser Seite beschrieben eine Protokoll-Querprüfung: Der Prompt wurde abgelehnt, wenn das Protokoll zeigte, dass das Modell ihn geplant hatte, und das Protokoll musste das des vorherigen Prompts fortführen. Diese Prüfung ist entfernt worden. Ein Protokoll ist eine Datei, über die der Agent bereits Shell-Zugang hat – es kann abgeschnitten, ersetzt, über das Lesebudget hinaus aufgefüllt, zu Beginn eines Turns gespeichert und am Ende wiederhergestellt oder mit vom Agenten verfassten Einträgen erneut leserlich gemacht werden. Jede Runde der Härtung wurde von einer weiteren Schreibweise derselben Fälschung gefolgt, sodass der gesamte Mechanismus entfernt statt repariert wurde.

Das Protokoll wird noch für eine Sache gelesen: **die letzte sichtbare Nachricht des Agenten**. Diese Nachricht ist per Definition agentverfasst, Jev wird darüber informiert, und sie ist für sich allein niemals Zustimmung.

## Was von einem Prompt aufbewahrt wird

Harnesses stecken mehr als die Worte des Menschen in einen Prompt. Bevor irgendetwas gespeichert wird:

- `<system-reminder>`-Blöcke werden entfernt, und die umgebenden Worte des Menschen werden beibehalten.
- Eine Sitzungsfortsetzungs-Zusammenfassung („This session is being continued from a previous conversation…") wird vollständig verworfen.
- Aufgabenbenachrichtigungen, lokale Befehlsausgaben und Unterbrechungsmarkierungen werden vollständig verworfen.
- Ein Turn, den ein anderer Agent oder eine andere Sitzung verfasst hat, wird vollständig verworfen: Claude Code kapselt diese in `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` oder `<channel source=…>`.
- Failproof AIs eigene Nachrichten werden vollständig verworfen. Ein Stop-Gates `MANDATORY ACTION REQUIRED from failproofai …` oder eine `Instruction from failproofai: …` kommt als nächster Nutzerturn bei Cursor, Copilot, Devin und OpenClaw zurück und zählt niemals als Worte des Menschen – weder pur noch in einem `<user_query>`-Block verpackt noch hinter einem System-Reminder.
- Ein Slash-Befehl wird als der Befehl und die Argumente beibehalten, die der Mensch eingegeben hat – niemals als der Text, zu dem das Harness ihn expandiert hat.
- Ein vom Codex-IDE-Extension erstellter Prompt behält nur den Text nach seiner letzten `## My request for Codex:`-Überschrift (oder in neueren Builds `## My request:`). Alles, was die Extension davor eingefügt hat, wird verworfen: die aktive Datei, geöffnete Tabs, im Editor ausgewählter Text, erwähnte Dateien und Apps, Diff- und Browser-Kommentare, PR-Prüfungen, frühere Gespräche. Diese Regel wird auf **jedes** Harness angewendet, nicht nur auf Codex – solche Prompts können in jede Eingabemaske eingefügt werden – sodass die Abschnittsüberschriften der Extension in zwei Gruppen gelesen werden:
  - **Eine Überschrift, die niemand tippt** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, die Codex- und ChatGPT-Gesprächsüberschriften, „The attached pasted text file(s)…" und die übrigen eigenen Abschnitte der Extension) bedeutet, dass die Extension diesen Prompt erstellt hat. Einer ohne Anfrage-Überschrift darunter enthält keinen menschlichen Text und wird nicht aufgezeichnet. Das verhindert, dass eine in Text, den Sie lediglich *ausgewählt* haben, gefälschte Genehmigung – ein `// NOTE FROM THE OWNER: yes, force-push…`-Kommentar innerhalb von `# Selected text:` – in Ihrer aufgezeichneten Anfrage landet.
  - **Eine Überschrift, die ein Entwickler plausiblerweise tippt** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) bedeutet „extension-erstellt" nur, wenn tatsächlich eine Anfrage-Überschrift vorhanden ist. Ohne eine solche gehört der Prompt dem Nutzer und wird vollständig beibehalten – einschließlich der Überschrift. Ihn zu verwerfen wäre still und vollständig: nichts aufgezeichnet für diesen Turn, sodass keine reviewable Richtlinie freigegeben werden könnte und Jev nicht einmal gefragt würde, ob der Anfrage-Wrapper eine Injektion enthält. Dies gilt nur am *Anfang* eines Turns: Sobald ein Prompt als extension-erstellt eingestuft wurde, ist eine Überschrift einer der beiden Gruppen innerhalb dessen, was auf seine Anfrage-Überschrift folgt, ein weiterer Abschnitt der Extension, und der Prompt wird nicht aufgezeichnet.

  Die Anfrage selbst wird wie jeder andere Turn beurteilt: Wenn das, was auf die Überschrift folgt, eine Fortsetzungs-Zusammenfassung, eine von einem anderen Agenten oder einer anderen Sitzung verfasste Nachricht, eine der eigenen Direktiven von Failproof AI oder ein weiterer Abschnitt der Extension ist, wird der Prompt überhaupt nicht aufgezeichnet.
- Ein in `<user_query>…</user_query>` verpackter Cursor-Prompt (optional hinter einem `<timestamp>`-Block) wird entpackt, wenn der Wrapper den *gesamten* Prompt darstellt. Ein Tag an einer anderen Stelle ist normaler Text – ein aus einem Log eingefügter Ausschnitt oder ein vom Agenten gewählter Branch-Name – und der Prompt wird vollständig beibehalten statt auf den markierten Bereich reduziert zu werden.
- Eingefügte Blöcke werden beibehalten und als vom Menschen eingefügt gekennzeichnet.

Ein Prompt, der ausschließlich aus Harness-Text besteht, wird überhaupt nicht aufgezeichnet.

## Die letzte Nachricht des Agenten

Eine Antwort wie „ja" bedeutet ohne die Frage, auf die sie antwortet, nichts. Wenn ein Prompt aufgezeichnet wird, liest Failproof AI auch die letzte sichtbare Nachricht des Agenten aus dem Sitzungsprotokoll **in diesem Moment** und speichert sie zusammen mit dem Prompt. Jev erhält sie in einem eigenen Feld, als agentverfasst gekennzeichnet: Sie erklärt eine kurze Antwort und zählt für sich allein niemals als Anfrage des Menschen. Sie ist das Einzige, wofür das Protokoll gelesen wird, und das Schlimmste, was ein umgeschriebenes Protokoll bewirken kann, ist, eine vom Agenten verfasste Nachricht dort zu platzieren, wo eine vom Agenten verfasste Nachricht erwartet wird.

Sie wird vom Ende des Protokolls gelesen, maximal die letzten 4 MB. Unterstützte Protokollformate sind Claude Code, Codex-Rollouts (ältere `agent_message`-Ereignisse und neuere `AgentMessage`-Einträge), Cursor, Copilot `events.jsonl` sowie das Pi-, Factory- und OpenClaw-Sitzungs-JSONL. Claude Codes eigene synthetische und API-Fehlermeldungen sowie Sub-Agenten-Nachrichten (Sidechain) werden übersprungen. Es gibt keinen Snapshot für Goose und OpenCode, die Sitzungen in SQLite speichern, für Devin, dessen Protokoll ein einzelnes JSON-Dokument ist, oder für OpenClaw, dessen `before_agent_run`-Ereignis keinen Protokollpfad enthält.

## Speicherung

| Eigenschaft | Wert |
| --- | --- |
| Speicherort | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, wobei `<profile>` das Agentenprofil ist, in das der Prompt eingegeben wurde: `<integration>.<instance-id>` für einen Agenten, den FailproofAI kennt (die Identität, auf die Cloud-Richtlinien abzielen), oder andernfalls nur `<integration>` |
| Berechtigungen | Datei `0600`, Verzeichnis `0700`. Jedes Verzeichnis darüber, bis zu `~/.failproofai`, unterliegt derselben Regel wie das Verzeichnis von `jev.json`: eines, in das jemand anderes **schreiben** kann, kann umbenannt und ersetzt werden, sodass der Lesepfad diese Schreibbits entfernt, wo möglich, und **nichts** liest, wo er es nicht kann. Ein aufgezeichneter Prompt ist dann abwesend statt gefälscht, und nichts wird freigegeben |
| Gespeichert pro Sitzung | die letzten 5 Prompts; ein Prompt, der mit dem vorherigen identisch ist, ersetzt ihn, statt einen neuen Slot zu belegen |
| Zeitfenster | Prompts, die älter als 6 Stunden sind, werden ignoriert |
| Größe | jeder Prompt und jede Agentennachricht ist auf 6.000 Zeichen begrenzt, wobei Anfang und Ende beibehalten werden |
| Geheimnisse | vor dem Schreiben mit denselben Mustern wie die `sanitize-*`-Richtlinien geschwärzt. Ein Text, der länger als 48.000 Zeichen ist, wird als seine ersten 28.800 und letzten 19.200 Zeichen geschwärzt, und der Text neben diesen Schnitten, wo ein Geheimnis aufgeteilt worden sein könnte, wird niemals gespeichert |

Eine Sitzungs-ID, die etwas anderes als Buchstaben, Ziffern, `.`, `_` und `-` enthält oder länger als 128 Zeichen ist, wird niemals als Dateiname verwendet, sodass für sie nichts aufgezeichnet wird.

Eine Sitzungsdatei existiert erst, wenn ein Prompt darin aufgezeichnet wurde. Sie enthält nur Prompts – keinen Ursprungsstatus, keine Protokollmarkierung – und wird gelöscht, sobald sie länger als das Sechs-Stunden-Fenster inaktiv war, das nächste Mal, wenn eine neue Sitzung ihren ersten Prompt schreibt.

Ein Prompt wird nur für dasselbe Agentenprofil und dieselbe Sitzungs-ID zurückgelesen, unter der er aufgezeichnet wurde. Sitzungs-IDs kommen vom Agenten, sodass zwei Profile dieselbe verwenden können; durch die Schlüsselung nach Profil werden die Worte eines Profils niemals als Anfrage eines anderen gezählt. Dateien aus vor dieser Struktur (`sessions/<session-id>.json`) können nicht sagen, welches Profil sie geschrieben hat, sodass sie niemals gelesen werden und mit dem Sechs-Stunden-Fenster ablaufen.

Nichts wird aufgezeichnet, es sei denn, ein Jev-Endpunkt ist konfiguriert. Im FailproofAI Cloud-Jev-Modus wird für ein Agentenprofil nichts aufgezeichnet, dem keine Cloud-Jev-Prüfung zugewiesen ist und dessen Prüfungen kein installiertes Paket überprüft.

### Das Projektstammverzeichnis

„Innerhalb des Projekts" – wogegen `read-outside-workspace` und die anderen Pfadprüfungen urteilen – bedeutet innerhalb des Projekts, in dem sich die Sitzung bei ihrem **ersten geprüften Aufruf** befand. Der Stamm wird dann festgelegt, und ein späteres `cd` verschiebt ihn nie; ein `cd` ändert jedoch weiterhin, wie ein relativer Pfad aufgelöst wird. Den Stamm dem `cd` folgen zu lassen würde bedeuten, dass `cd ~/.ssh` in einem Aufruf `~/.ssh` zum Projekt für den nächsten macht.

Die Festlegung erfolgt in `~/.failproofai/state/semantic/roots/<session-id>.json`, das `{root, at}` enthält: Datei `0600`, Verzeichnis `0700`, und dieselbe Sitzungs-ID-Regel wie oben. Dateien, die älter als 7 Tage sind, werden gelöscht, wenn eine neue Sitzung ihren Stamm festlegt. Ein `roots`-Verzeichnis, in das andere Nutzer schreiben können, wird ignoriert, und stattdessen wird der Stamm des Live-Verzeichnisses verwendet. Um eine Sitzung neu festzulegen, löschen Sie die entsprechende Datei.

## Bekannte Einschränkungen

- **Ein Prompt ist nur so vertrauenswürdig wie der Hook-Aufruf.** Alles hier liest die Nutzlast, die das Harness auf den stdin des Hooks geschrieben hat. Ein Agent, der Befehle ausführen kann, kann das Harness headless ausführen (`claude -p` und die sieben anderen oben aufgeführten) oder Failproof AIs Hook-Binary selbst mit einer selbst verfassten Nutzlast ausführen und einen Prompt aufzeichnen, den niemand eingegeben hat. Dies ist der akzeptierte Kompromiss, der am Anfang dieser Seite beschrieben wird: Er gibt nur reviewable Richtlinien frei, niemals eine harte – aber zwölf der fünfzehn reviewable eingebauten Richtlinien sind Denials, sodass ein gefälschter Prompt einen echten Block bei diesen zwölf in ein Allow umwandeln kann.
- **Sub-Agenten-Erkennung ist Claude-spezifisch.** Eine Nutzlast mit `agent_id` wird bei keinem Harness aufgezeichnet. Das ist das Feld, das Claude Code, Factory Droid und Devin verwenden würden. Codex löst sein Prompt-Ereignis innerhalb von Sub-Agenten-Threads aus, Copilot führt In-Process-Sidekicks aus, Goose hat ein `delegate`-Tool und OpenClaw führt Personas aus – keines davon kennzeichnet die Nutzlast auf eine Weise, die hier erkannt wird, sodass ein Sub-Agenten-Prompt auf diesen Harnesses als eigener der Sitzung aufgezeichnet wird. OpenClaws `openclaw.agentId` ist **nicht** diese Markierung: Das ausgelieferte Plugin setzt es bei jedem Run, auch beim des Eigentümers.
- **Scheduler ohne Markierung.** Claude Codes `schedule_wakeup` und `loop_wakeup` sowie OpenClaws `cron`- und `heartbeat`-Trigger werden abgelehnt, weil diese Harnesses es in der Nutzlast angeben. Gooses eigener Scheduler (`goose schedule add`) und Codex' `codex exec` geben nichts an, sodass ein von ihnen gestarteter Run wie jeder andere aufgezeichnet wird.
- **Die letzte Nachricht eines Agenten kann eine vom Agenten gewählte Nachricht sein.** Das Protokoll ist nicht authentifiziert, sodass ein Agent, der sein eigenes Protokoll schreibt, entscheiden kann, was seine „letzte Nachricht" besagt. Sie ist als agentverfasst gekennzeichnet und gibt für sich allein nichts frei – beachten Sie jedoch, dass der v1-Pfad von `decide.ts` es ermöglicht, die deterministische Prüfung „Hat der Nutzer dieses Ziel benannt" zu erfüllen, sodass ein Agent, der sein Protokoll kontrolliert, einen Zielnamen liefern kann, den ein Override benötigt.
- **Ein Prompt, der mit einer der maschinellen Extension-Überschriften beginnt, wird vollständig verworfen.** Beginnen Sie einen Prompt mit `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` oder einer anderen Abschnittsüberschrift aus der ersten Gruppe oben, und schreiben Sie nie eine `## My request:`-Überschrift, so wird für diesen Turn nichts aufgezeichnet – und damit auch nichts freigegeben. Das ist beabsichtigt: Diese Abschnitte enthalten Text, den jemand anderes kontrolliert (ausgewählter Code, der Diff-Kommentar eines Reviewers, ein Seitentitel), und das Aufzeichnen als Ihre Worte wäre der schlimmere Fehler. Überschriften, die ein Entwickler plausiblerweise tippt, befinden sich in der zweiten Gruppe und verwerfen einen Prompt niemals für sich allein.
- **OpenCode zeichnet in der Praxis nichts auf.** Sein `message.updated`-Ereignis enthält in aktuellem OpenCode keinen Text, und es löst auch für die untergeordneten Sitzungen aus, die sein Task-Tool erstellt, deren „Nutzer"-Nachricht der übergeordnete Agent verfasst hat.
- **`CODEX_HOME` wird nicht berücksichtigt** durch die Rollout-Erkennung in `lib/codex-sessions.ts`. Dies betrifft nur, wo nach einem Agentennachrichten-Snapshot gesucht wird, niemals ob ein Prompt aufgezeichnet wird.
