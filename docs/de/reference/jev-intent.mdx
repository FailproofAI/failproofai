Wenn Sie die [Jev-Richtlinienprüfung](/de/policies/jev) konfigurieren, beurteilt der Evaluator jeden gesperrten Tool-Aufruf anhand **dessen, was der Mensch angefragt hat** — nicht anhand des Textes, den das Harness dem Agenten vorgelegt hat. Eine Antwort wie „ja, force-pushe es" kann eine **reviewable**-Richtlinie freigeben — das ist genau der Sinn des Evaluators, da ein Regex, der die Anfrage nicht lesen kann, ein Drittel der realen Arbeit blockiert.

Dieser Text kommt von einer einzigen Stelle: **dem Prompt, den das Harness selbst beim Prompt-Submit-Event an den Hook übergibt**. Failproof AI zeichnet den vom Menschen eingetippten Teil davon auf — Harness-Ummantelung entfernt, Geheimnisse redigiert, begrenzt — in einer `0600`-Datei unter seinem eigenen Statusverzeichnis. Es wird nichts auf der Festplatte nachgeschlagen: Das Sitzungsprotokoll ist eine Datei, die der Agent mit einem einzigen Befehl überschreiben kann, daher wird nie nachgefragt, wer einen Prompt verfasst hat.

## Das damit verbundene Risiko, klar ausgedrückt

Ein Agent, der bereits Befehle ausführen kann, kann ein Harness dazu bringen, einen Prompt einzureichen. `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` und `pi -p` lösen alle dasselbe Prompt-Submit-Event aus — mit demselben Payload wie eine tippende Person —, und zwar in einer Kindersitzung, die der Agent kontrolliert. Er kann auch die Hook-Binärdatei von Failproof AI selbst ausführen und ihr einen selbst erstellten Payload übergeben. Nichts innerhalb von Failproof AI kann beides vom Echten unterscheiden — beides ist dasselbe Programm, das denselben stdin liest.

**Ein Agent mit Shell-Zugriff kann also seine eigene Einwilligung fälschen.** Das ist ein bewusster Kompromiss, der am 2026-09-23 eingegangen wurde, und hier sind beide Seiten davon:

- **Was er einbringt.** Die Alternative wurde gebaut und gemessen: Man könnte ein Feld verlangen, in dem das Harness einen Menschen als Verfasser des Prompts benennt, und andernfalls nichts aufzeichnen. Kein lieferbares Harness sendet ein solches Feld, daher zeichnete diese Version **nichts, auf jedem Harness** auf — Jev beurteilte jeden Aufruf ohne angegebene Absicht und konnte keine einzige Richtlinie freigeben. Eine Erfassung, die nie auslöst, ist kein sichereres Produkt, sondern gar kein Produkt.
- **Was er nicht kann.** Ein aufgezeichneter Prompt kann nur eine Richtlinie freigeben, die bereits als **reviewable** markiert ist. Eine **hard**-Richtlinie wird durch nichts, was Jev sagt, jemals freigegeben; ein gefälschter Prompt kann also ein hartes Deny niemals in ein Allow umwandeln — und das Überspringen des Hooks bringt einem Agenten ebenfalls nichts: Das Harness ruft Failproof AI für den Tool-Aufruf unabhängig auf.
- **Was er im schlimmsten Fall kann.** Das Schlimmste ist die Freigabe einer der fünfzehn reviewable eingebauten Richtlinien — und **zwölf der fünfzehn blockieren**. `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` sowie die sechs Infrastruktur-CLI-Blockierungen (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) sind Denies; eine gefälschte Einwilligung kann also ein echtes Deny in ein Allow auf Ausgabe von Umgebungsgeheimnissen, Lesen einer `.env`-Datei, Lesen außerhalb des Projekts, `rm -rf`, einen Force-Push, das Schreiben einer Secrets-Datei oder das Ändern von Live-Infrastruktur umwandeln. Nur `warn-git-amend`, `warn-destructive-sql` und `warn-global-package-install` sind Hinweise. Eine Standardinstallation aktiviert zwei der zwölf: `protect-env-vars` und `block-env-files`; die anderen zehn greifen nur auf einem Rechner, auf dem sie jemand aktiviert hat. Was kein Prompt erreicht, ist alles Harte — `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, die Schutzregel, die einen Agenten daran hindert, Failproof AI zu deaktivieren, und jede andere nicht als reviewable markierte eingebaute Richtlinie. [Richtlinienautorität](/de/policies/authority) listet alle fünfzehn und deren jeweilige Überprüfungsinstanz auf.

Was weiterhin abgelehnt wird, ist alles, was günstig zu prüfen ist und was ein Agent nicht einfach durch Fragen erhalten kann: ein Turn, den der eigene Payload des Harnesses als maschinell eingereicht markiert, ein Payload, der einen Subagenten benennt, eine Sitzungs-ID, die kein einfacher Name ist, ein Event, das nicht das Prompt-Submit-Event ist, sowie Text, der nichts außer Harness-Ummantelung ist — einschließlich der Stop-Gate-Wörter von Failproof AI selbst, die mehrere Harnesses als nächsten User-Turn zurückspielen.

„Text field" ist das stdin-Payload-Feld nach der harnessspezifischen Normalisierung durch Failproof AI. „Recorded" gibt an, ob der Prompt als Anfrage des Menschen gespeichert wird.

Zwei Harnesses zeichnen nichts auf, und aus demselben Grund: Ihr Event liefert keinen menschlichen Text. Hermes hat kein Prompt-Submit-Event — sein natives Plugin verarbeitet `pre_llm_call` selbst und leitet nur Tool-, Sitzungs- und Subagenten-Events weiter. Das `PreInvocation`-Event von Antigravity löst vor jedem Modellaufruf aus, sowohl beim menschlichen Turn als auch bei den fünf darauffolgenden, und enthält kein Prompt-Feld; Hooks können auch `userMessage`-Schritte in dieselbe Konversation injizieren. In keinem der beiden Events gibt es etwas aufzuzeichnen.

## Was einen Prompt zum menschlichen Prompt macht

1. **Das Event.** Failproof AI wurde für das Prompt-Submit-Event des Harnesses aufgerufen, das der Handler zu `UserPromptSubmit` kanonisiert.
2. **Der Payload.** Das Harness schreibt ihn auf den stdin des Hooks, und er enthält den Text im oben genannten Feld. Ein Aufruf, der Failproof AI ohne den Payload erreicht, zeichnet nichts auf.
3. **Nichts im Payload schließt den Turn aus.** Ein Payload, der einen Subagenten benennt (`agent_id`), ist der Agent, der sich selbst eine Eingabe macht. Ein `source`-, `input_source`- oder OpenClaw-Run-Marker, der einen maschinell eingereichten Turn benennt, wird abgelehnt. Ein **fehlender** Marker schließt nichts aus — das ist der Unterschied zur Version, die nichts aufzeichnete, da jeder Marker hier bei jedem lieferbaren Build fehlt.
4. **Nach dem Entfernen der Ummantelung bleibt noch etwas übrig** (siehe unten).

**Das Sitzungsprotokoll ist kein Beweis dafür, wer einen Prompt verfasst hat.** Frühere Versionen dieser Seite beschrieben eine Protokoll-Kreuzprüfung: Der Prompt wurde abgelehnt, wenn das Protokoll zeigte, dass das Modell ihn geplant hatte, und das Protokoll musste das des vorherigen Prompts fortsetzen. Diese Prüfung ist weggefallen. Ein Protokoll ist eine Datei, über die der Agent bereits Shell-Kontrolle hat — es kann gekürzt, ersetzt, über das Lesebudget hinaus aufgefüllt, zu Beginn eines Turns gespeichert und am Ende wiederhergestellt oder mit vom Agenten geschriebenen Einträgen neu aufbereitet werden. Auf jede Härtungsrunde folgte eine weitere Variante derselben Fälschung, daher wurde der gesamte Mechanismus entfernt statt repariert.

Das Protokoll wird noch für eine Sache gelesen: **die letzte sichtbare Nachricht des Agenten**. Diese Nachricht ist per Definition vom Agenten verfasst, Jev wird darüber informiert, und sie ist allein niemals eine Einwilligung.

## Was von einem Prompt gespeichert wird

Harnesses fügen einem Prompt mehr als nur die Worte des Menschen ein. Bevor etwas gespeichert wird:

- `<system-reminder>`-Blöcke werden entfernt, und die Worte des Menschen darum herum werden beibehalten.
- Eine Sitzungsfortsetzungszusammenfassung („This session is being continued from a previous conversation…") wird vollständig verworfen.
- Aufgabenbenachrichtigungen, lokale Befehlsausgaben und Unterbrechungsmarkierungen werden vollständig verworfen.
- Ein Turn, den ein anderer Agent oder eine andere Sitzung verfasst hat, wird vollständig verworfen: Claude Code umhüllt diese in `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` oder `<channel source=…>`.
- Eigene Nachrichten von Failproof AI werden vollständig verworfen. Ein `MANDATORY ACTION REQUIRED from failproofai …` eines Stop-Gates oder ein `Instruction from failproofai: …` kommt bei Cursor, Copilot, Devin und OpenClaw als nächster User-Turn zurück und zählt nie als Worte des Menschen — weder pur, noch in einem `<user_query>`-Block eingebettet, noch hinter einem System-Reminder.
- Ein Slash-Befehl wird als der vom Menschen eingetippte Befehl mit Argumenten beibehalten, nie als der vom Harness expandierte Rumpf.
- Ein vom Codex-IDE-Extension erstellter Prompt behält nur den Text nach der letzten Überschrift `## My request for Codex:` (oder bei neueren Builds `## My request:`). Alles, was die Extension davor eingefügt hat, wird verworfen: die aktive Datei, geöffnete Tabs, im Editor ausgewählter Text, erwähnte Dateien und Apps, Diff- und Browser-Kommentare, PR-Prüfungen, frühere Gespräche. Diese Regel wird auf **alle** Harness-Prompts angewendet, nicht nur auf Codex — ein solcher Prompt kann in jede Kompositions-UI eingefügt werden —, daher werden die Abschnittsüberschriften der Extension in zwei Gruppen gelesen:
  - **Eine Überschrift, die niemand tippt** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, die Konversationsüberschriften von Codex und ChatGPT, „The attached pasted text file(s)…" und die übrigen eigenen Abschnitte der Extension) bedeutet, dass die Extension diesen Prompt erstellt hat. Ein Prompt ohne nachfolgende Anfrage-Überschrift enthält keinen menschlichen Text und wird nicht aufgezeichnet. Das verhindert, dass eine im reinen Text gefälschte Genehmigung aus einer lediglich *ausgewählten* Textstelle — ein `// NOTE FROM THE OWNER: yes, force-push…`-Kommentar innerhalb von `# Selected text:` — in Ihre aufgezeichnete Anfrage gelangt.
  - **Eine Überschrift, die ein Entwickler plausiblerweise tippt** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) bedeutet „extension-erstellt" nur, wenn tatsächlich eine Anfrage-Überschrift vorhanden ist. Ohne eine solche ist der Prompt Ihres und wird vollständig beibehalten, Überschrift und alles. Ihn zu verwerfen wäre still und total: Für diesen Turn würde nichts aufgezeichnet, keine reviewable-Richtlinie könnte freigegeben werden, und Jev würde nicht einmal gefragt, ob der Anfrage-Umschlag eine Injektion enthält. Dies gilt nur am *Anfang* eines Turns: Sobald ein Prompt als extension-erstellt eingestuft wurde, ist eine Überschrift einer der beiden Gruppen innerhalb dessen, was auf die Anfrage-Überschrift folgt, ein weiterer Abschnitt der Extension, und der Prompt wird nicht aufgezeichnet.

  Die Anfrage selbst wird wie jeder andere Turn beurteilt: Wenn das, was auf die Überschrift folgt, eine Fortsetzungszusammenfassung ist, eine Nachricht, die ein anderer Agent oder eine andere Sitzung verfasst hat, eine eigene Direktive von Failproof AI oder ein weiterer Abschnitt der Extension, wird der Prompt überhaupt nicht aufgezeichnet.
- Ein Cursor-Prompt, der in `<user_query>…</user_query>` eingebettet ist (optional hinter einem `<timestamp>`-Block), wird entpackt, wenn die Ummantelung der *gesamte* Prompt ist. Ein Tag an anderer Stelle ist gewöhnlicher Text — ein aus einem Log eingefügter Schnipsel oder ein vom Agenten gewählter Branch-Name — und der Prompt wird vollständig beibehalten, anstatt auf die getaggte Spanne reduziert zu werden.
- Eingefügte Blöcke werden beibehalten und als vom Menschen eingefügt markiert.

Ein Prompt, der nur aus Harness-Text besteht, wird überhaupt nicht aufgezeichnet.

## Die letzte Nachricht des Agenten

Eine Antwort wie „ja" bedeutet nichts ohne die Frage, die sie beantwortet. Wenn ein Prompt aufgezeichnet wird, liest Failproof AI auch die letzte sichtbare Nachricht des Agenten aus dem Sitzungsprotokoll **zu diesem Zeitpunkt** und speichert sie zusammen mit dem Prompt. Jev erhält sie in einem eigenen Feld, als vom Agenten verfasst gekennzeichnet: Sie erklärt eine kurze Antwort und zählt allein nie als Anfrage des Menschen. Es ist das Einzige, wofür das Protokoll gelesen wird, und das Schlimmste, was ein überschriebenes Protokoll tun kann, ist, eine vom Agenten verfasste Nachricht dorthin zu setzen, wo eine vom Agenten verfasste Nachricht erwartet wird.

Sie wird vom Ende des Protokolls gelesen, höchstens die letzten 4 MB. Unterstützte Protokollformate sind Claude Code, Codex-Rollouts (ältere `agent_message`-Events und neuere `AgentMessage`-Elemente), Cursor, Copilot `events.jsonl` sowie die Pi-, Factory- und OpenClaw-Sitzungs-JSONL. Eigene synthetische Nachrichten und API-Fehlermeldungen von Claude Code sowie Subagenten-(Sidechain-)Nachrichten werden übersprungen. Für Goose und OpenCode, die Sitzungen in SQLite speichern, für Devin, dessen Protokoll ein einzelnes JSON-Dokument ist, und für OpenClaw, dessen `before_agent_run`-Event keinen Protokollpfad enthält, gibt es keinen Snapshot.

## Speicherung

| Eigenschaft | Wert |
| --- | --- |
| Speicherort | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, wobei `<profile>` das Agentenprofil ist, in das der Prompt eingegeben wurde: `<integration>.<instance-id>` für einen Agenten, den FailproofAI kennt (die Identität, auf die Cloud-Richtlinien abzielen), oder andernfalls nur `<integration>` |
| Berechtigungen | Datei `0600`, Verzeichnis `0700`. Jedes übergeordnete Verzeichnis bis zu `~/.failproofai` unterliegt derselben Regel wie das Verzeichnis von `jev.json`: Ein Verzeichnis, in das jemand anderes **schreiben** kann, kann umbenannt und ersetzt werden; daher entfernt der Lesepfad diese Schreibbits, wo es möglich ist, und liest **nichts**, wo es nicht möglich ist. Ein aufgezeichneter Prompt ist dann abwesend statt gefälscht, und nichts wird freigegeben |
| Pro Sitzung gespeichert | die letzten 5 Prompts; ein mit dem vorherigen identischer Prompt ersetzt diesen, anstatt einen neuen Slot zu belegen |
| Zeitfenster | Prompts, die älter als 6 Stunden sind, werden ignoriert |
| Größe | jeder Prompt und jede Agentennachricht ist auf 6.000 Zeichen begrenzt, wobei Anfang und Ende beibehalten werden |
| Geheimnisse | vor dem Schreiben mit denselben Mustern wie die `sanitize-*`-Richtlinien redigiert. Ein Text länger als 48.000 Zeichen wird als seine ersten 28.800 und letzten 19.200 Zeichen redigiert, und der Text neben diesen Schnitten, wo ein Geheimnis möglicherweise aufgeteilt wurde, wird nie gespeichert |

Eine Sitzungs-ID, die andere Zeichen als Buchstaben, Ziffern, `.`, `_` und `-` enthält oder länger als 128 Zeichen ist, wird nie als Dateiname verwendet, daher wird für sie nichts aufgezeichnet.

Eine Sitzungsdatei existiert erst, wenn ein Prompt darin aufgezeichnet wurde. Sie enthält nur Prompts — keinen Ursprungsstatus, keine Protokollmarkierung — und wird gelöscht, sobald sie länger als das sechsstündige Zeitfenster inaktiv war, das nächste Mal, wenn eine neue Sitzung ihren ersten Prompt schreibt.

Ein Prompt wird nur für dasselbe Agentenprofil und dieselbe Sitzungs-ID zurückgelesen, unter der er aufgezeichnet wurde. Sitzungs-IDs kommen vom Agenten, daher können zwei Profile dieselbe verwenden; die Schlüsselung nach Profil verhindert, dass die Worte eines Profils jemals als Anfrage eines anderen zählen. Dateien vor diesem Layout (`sessions/<session-id>.json`) können nicht angeben, welches Profil sie verfasst hat, werden daher nie gelesen und verfallen mit dem sechsstündigen Zeitfenster.

Nichts wird aufgezeichnet, sofern kein Jev-Endpunkt konfiguriert ist. Im FailproofAI-Cloud-Jev-Modus wird nichts für ein Agentenprofil aufgezeichnet, dem keine Cloud-Jev-Prüfung zugewiesen ist und das von keiner installierten Pack-Prüfung überprüft wird.

### Das Projektstamm-Verzeichnis

„Innerhalb des Projekts" — wonach `read-outside-workspace` und die anderen Pfadprüfungen urteilen — bedeutet innerhalb des Projekts, in dem sich die Sitzung bei ihrem **ersten überprüften Aufruf** befand. Das Stammverzeichnis wird dann festgehalten, und ein späteres `cd` verschiebt es nie; ein `cd` ändert jedoch weiterhin, wie ein relativer Pfad aufgelöst wird. Würde es dem `cd` folgen, würde `cd ~/.ssh` in einem Aufruf `~/.ssh` zum Projekt für den nächsten machen.

Die Fixierung ist `~/.failproofai/state/semantic/roots/<session-id>.json`, das `{root, at}` enthält: Datei `0600`, Verzeichnis `0700`, und dieselbe Sitzungs-ID-Regel wie oben. Dateien, die älter als 7 Tage sind, werden gelöscht, wenn eine neue Sitzung ihr Stammverzeichnis fixiert. Ein `roots`-Verzeichnis, in das andere Benutzer schreiben können, wird ignoriert, und stattdessen wird das Stammverzeichnis des Live-Verzeichnisses verwendet. Um eine Sitzung neu zu fixieren, löschen Sie ihre Datei.

## Bekannte Einschränkungen

- **Ein Prompt ist nur so vertrauenswürdig wie der Hook-Aufruf.** Alles hier liest den Payload, den das Harness auf den stdin des Hooks geschrieben hat. Ein Agent, der Befehle ausführen kann, kann das Harness headless ausführen (`claude -p` und die sieben anderen oben aufgeführten) oder die Hook-Binärdatei von Failproof AI selbst mit einem selbst erstellten Payload ausführen und einen Prompt aufzeichnen, den niemand eingegeben hat. Das ist der oben beschriebene akzeptierte Kompromiss: Er gibt nur reviewable-Richtlinien frei, nie eine harte — aber zwölf der fünfzehn reviewable eingebauten Richtlinien sind Denies, sodass ein gefälschter Prompt auf diesen zwölf einen echten Block in ein Allow umwandeln kann.
- **Subagenten-Erkennung ist Claude-förmig.** Ein Payload, der `agent_id` enthält, wird auf keinem Harness aufgezeichnet. Das ist das Feld, das Claude Code, Factory Droid und Devin verwenden würden. Codex löst sein Prompt-Event innerhalb von Subagenten-Threads aus, Copilot führt In-Process-Sidekicks aus, Goose hat ein `delegate`-Tool und OpenClaw führt Personas aus — keines davon markiert den Payload auf eine Weise, die hier erkannt wird; daher wird ein Subagenten-Prompt auf diesen Harnesses als eigener der Sitzung aufgezeichnet. OpenClaws `openclaw.agentId` ist **nicht** diese Markierung: Das mitgelieferte Plugin setzt sie auf jeden Run, auch auf den des Eigentümers.
- **Scheduler ohne Marker.** Claude Codes `schedule_wakeup` und `loop_wakeup` sowie OpenClaws `cron`- und `heartbeat`-Trigger werden abgelehnt, weil diese Harnesses es im Payload angeben. Gooses eigener Scheduler (`goose schedule add`) und Codexs `codex exec` geben nichts an, sodass ein von ihnen gestarteter Run wie jeder andere aufgezeichnet wird.
- **Die letzte Nachricht eines Agenten kann eine vom Agenten gewählte Nachricht sein.** Das Protokoll ist nicht authentifiziert, sodass ein Agent, der sein eigenes Protokoll schreibt, entscheiden kann, was seine „letzte Nachricht" aussagt. Sie wird als vom Agenten verfasst gekennzeichnet und gibt allein nichts frei — beachten Sie jedoch, dass der v1-Pfad von `decide.ts` es ihr ermöglicht, die deterministische Prüfung „Hat der Benutzer dieses Ziel benannt" zu erfüllen; ein Agent, der sein Protokoll kontrolliert, kann also einen Zielnamen angeben, den ein Override benötigt.
- **Ein Prompt, der mit einer der maschinellen Überschriften der Extension beginnt, wird vollständig verworfen.** Beginnen Sie einen Prompt mit `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` oder einer anderen Abschnittsüberschrift aus der ersten Gruppe oben, und schreiben Sie keine `## My request:`-Überschrift, wird für diesen Turn nichts aufgezeichnet — daher wird auch nichts dafür freigegeben. Das ist beabsichtigt: Diese Abschnitte enthalten Text, den jemand anderes kontrolliert (von Ihnen ausgewählter Code, der Diff-Kommentar eines Reviewers, ein Seitentitel), und diesen als Ihre Worte aufzuzeichnen wäre das schlimmere Versagen. Überschriften, die ein Entwickler plausiblerweise tippt, befinden sich in der zweiten Gruppe und verwerfen einen Prompt nie allein.
- **OpenCode zeichnet in der Praxis nichts auf.** Sein `message.updated`-Event enthält im aktuellen OpenCode keinen Text, und es wird auch für die Kindersitzungen ausgelöst, die sein Task-Tool erstellt und deren „user"-Nachricht der übergeordnete Agent verfasst hat.
- **`CODEX_HOME` wird** von der Rollout-Erkennung in `lib/codex-sessions.ts` **nicht berücksichtigt**. Dies betrifft nur, wo nach einem Agentennachrichten-Snapshot gesucht wird, nie ob ein Prompt aufgezeichnet wird.
