Wenn Sie die [Jev-Richtlinienprüfung](/de/policies/jev) konfigurieren, beurteilt der Evaluator jeden kontrollierten Tool-Aufruf anhand von **dem, was der Mensch angefragt hat** – nicht anhand des Textes, den das Harness dem Agenten präsentiert hat. Eine Antwort wie „ja, force-push it" kann eine **reviewable**-Richtlinie freischalten – genau das ist der Zweck des Evaluators, da ein Regex, der die Anfrage nicht lesen kann, ein Drittel der echten Arbeit blockiert.

Dieser Text stammt aus einer einzigen Quelle: **dem Prompt, den das Harness selbst beim Prompt-Submit-Ereignis an den Hook übergibt**. Failproof AI zeichnet den vom Menschen eingetippten Teil davon auf – Harness-Umrahmung entfernt, Secrets redigiert, begrenzt – und speichert ihn in einer `0600`-Datei in seinem eigenen Zustandsverzeichnis. Nichts auf der Festplatte wird für die Autorenschaft herangezogen: Das Sitzungsprotokoll ist eine Datei, die der Agent mit einem einzigen Befehl überschreiben kann, daher wird nie gefragt, wer einen Prompt verfasst hat.

## Das damit eingegangene Risiko, klar formuliert

Ein Agent, der bereits Befehle ausführen kann, kann ein Harness veranlassen, einen Prompt zu übermitteln. `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` und `pi -p` lösen alle dasselbe Prompt-Submit-Ereignis aus, mit derselben Nutzlast, wie eine tippende Person – in einer untergeordneten Sitzung, die der Agent kontrolliert. Er kann auch das eigene Hook-Binary von Failproof AI ausführen und ihm eine selbst verfasste Nutzlast übergeben. Nichts innerhalb von Failproof AI kann beides vom Original unterscheiden – beides ist dasselbe Programm, das denselben stdin liest.

**Ein Agent mit Shell-Zugriff kann also seine eigene Zustimmung fälschen.** Das ist ein bewusster Kompromiss, der am 2026-09-23 eingegangen wurde, und hier sind beide Seiten davon:

- **Was er bringt.** Die Alternative wurde gebaut und gemessen: ein Feld verlangen, in dem das Harness einen Menschen als Autor des Prompts benennt, und andernfalls nichts aufzeichnen. Kein verfügbares Harness sendet ein solches Feld, sodass diese Version **auf jedem Harness nichts aufgezeichnet** hat – Jev beurteilte jeden Aufruf ohne angegebene Absicht und konnte nie eine einzige Richtlinie freischalten. Eine Erfassung, die niemals auslöst, ist kein sichereres Produkt, sondern überhaupt kein Produkt.
- **Was er nicht kann.** Ein aufgezeichneter Prompt kann nur eine Richtlinie freischalten, die bereits als **reviewable** markiert ist. Eine **hard**-Richtlinie wird durch nichts, was Jev sagt, jemals freigeschalten, sodass ein gefälschter Prompt niemals ein hartes Deny in ein allow umwandeln kann – und das Überspringen des Hooks bringt einem Agenten ebenfalls nichts: Das Harness ruft Failproof AI für den Tool-Aufruf unabhängig davon auf.
- **Was er im schlimmsten Fall kann.** Das Schlimmste, was er tun kann, ist eine der fünfzehn reviewable eingebauten Richtlinien freizuschalten – und **zwölf dieser fünfzehn blockieren**. `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` und die sechs Infrastruktur-CLI-Blöcke (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) sind Denies; eine gefälschte Zustimmung kann also ein echtes Deny in ein allow umwandeln für das Ausgeben von Umgebungs-Secrets, das Lesen einer `.env`-Datei, das Lesen außerhalb des Projekts, `rm -rf`, einen Force-Push, das Schreiben einer Secrets-Datei oder das Ändern der Live-Infrastruktur. Nur `warn-git-amend`, `warn-destructive-sql` und `warn-global-package-install` sind Hinweise. Eine Standard-Installation schaltet zwei der zwölf ein, `protect-env-vars` und `block-env-files`; die anderen zehn erreichen nur einen Rechner, auf dem jemand sie aktiviert hat. Was kein Prompt erreicht, ist alles Harte – `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, der Schutz, der einen Agenten daran hindert, Failproof AI zu deaktivieren, und jede andere eingebaute Richtlinie, die nicht als reviewable markiert ist. [Richtlinien-Autorität](/de/policies/authority) listet alle fünfzehn und was jeweils geprüft wird.

Was weiterhin abgelehnt wird, ist alles, was günstig zu prüfen ist und was ein Agent nicht allein durch Fragen erlangen kann: ein Turn, den die eigene Nutzlast des Harnesses als maschinell übermittelt markiert, eine Nutzlast, die einen Sub-Agenten benennt, eine Sitzungs-ID, die kein einfacher Name ist, ein Ereignis, das nicht das Prompt-Submit-Ereignis ist, und Text, der nur aus Harness-Umrahmung besteht – einschließlich der eigenen Stop-Gate-Wörter von Failproof AI, die mehrere Harnesses als nächsten User-Turn zurückspielen.

## Harness-Tabelle

„Textfeld" ist das stdin-Nutzlastfeld nach der harnessspezifischen Normalisierung durch Failproof AI. „Aufgezeichnet" gibt an, ob der Prompt als menschliche Anfrage gespeichert wird.

| Harness | `--cli` | Prompt-Ereignis → kanonisch | Textfeld | Aufgezeichnet | Letzte Agent-Nachricht gelesen aus |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | Ja, es sei denn, das `source`-Feld der Nutzlast benennt einen Turn, den niemand übermittelt hat (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`). `user`, `sdk`, ein unbekannter Wert und ein Build, der gar kein `source` sendet, werden alle aufgezeichnet | das Sitzungsprotokoll (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | Ja | das Rollout-JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | Ja | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | Ja, wobei der `<user_query>`-Wrapper entfernt wird, wenn er den gesamten Prompt ausmacht | das Agent-Transkript-JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | Ja – aber aktuelles OpenCode enthält keinen Text in diesem Ereignis, sodass in der Praxis nichts aufgezeichnet wird; eine Wiederholung derselben Nachricht wird einmal aufgezeichnet | keines (Sitzungen sind SQLite) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | Ja, es sei denn, `input_source` ist `extension` – das `sendUserMessage()` einer anderen Extension, deren Text modellgeneriert oder repo-abgeleitet sein kann | das Pi-Sitzungs-JSONL |
| Hermes | `hermes` | keines | — | Nein – Hermes hat überhaupt kein Prompt-Submit-Ereignis | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | Ja, es sei denn, die Run-Metadaten markieren den Run als maschinell: ein `trigger` ungleich `user`, ein `inputProvenance.kind` ungleich `external_user` oder `senderIsOwner: false` | keines (`before_agent_run` enthält keinen Transkriptpfad) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | Ja | das Droid-Sitzungs-JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | Ja | keines (Sitzungen sind SQLite) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | keines | Nein – `PreInvocation` löst vor *jedem* Modellaufruf in einem Turn aus und enthält keinen Prompt-Text | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | Ja | keines (Sitzungen sind SQLite) |

Zwei Harnesses zeichnen nichts auf, und aus demselben Grund in beiden Fällen: Ihr Ereignis liefert keinen menschlichen Text. Hermes hat kein Prompt-Submit-Ereignis – sein natives Plugin verarbeitet `pre_llm_call` selbst und leitet nur Tool-, Sitzungs- und Sub-Agenten-Ereignisse weiter. Antigravitys `PreInvocation` löst vor jedem Modellaufruf aus, sowohl bei einem menschlichen Turn als auch bei den fünf, die darauf folgen, und enthält kein Prompt-Feld; Hooks können auch `userMessage`-Schritte in dasselbe Gespräch injizieren. In keinem der beiden Ereignisse gibt es etwas aufzuzeichnen.

## Was einen Prompt zum menschlichen macht

1. **Das Ereignis.** Failproof AI wurde für das Prompt-Submit-Ereignis des Harnesses aufgerufen, das der Handler zu `UserPromptSubmit` kanonisiert.
2. **Die Nutzlast.** Das Harness schreibt sie auf den stdin des Hooks, und sie enthält den Text im oben genannten Feld. Ein Aufruf, der Failproof AI ohne die Nutzlast erreicht, zeichnet nichts auf.
3. **Nichts in der Nutzlast schließt den Turn aus.** Eine Nutzlast, die einen Sub-Agenten benennt (`agent_id`), ist der Agent, der sich selbst promptet. Ein `source`, `input_source` oder OpenClaw-Run-Marker, der einen maschinell übermittelten Turn benennt, wird abgelehnt. Ein **fehlender** Marker schließt nichts aus – das ist der Unterschied zur Version, die nichts aufzeichnete, da hier jeder Marker in jedem verfügbaren Build fehlt.
4. **Nach dem Entfernen der Umrahmung bleibt etwas übrig** (siehe unten).

**Das Sitzungsprotokoll ist kein Beweis dafür, wer einen Prompt verfasst hat.** Frühere Versionen dieser Seite beschrieben eine Transkript-Querprüfung: Der Prompt wurde abgelehnt, wenn das Transkript zeigte, dass das Modell ihn geplant hatte, und das Transkript musste das des vorherigen Prompts fortsetzen. Diese Prüfung wurde entfernt. Ein Transkript ist eine Datei, über die der Agent bereits Shell-Zugriff hat – es kann gekürzt, ersetzt, über das Lesebudget hinaus aufgefüllt, zu Beginn eines Turns gesichert und am Ende wiederhergestellt oder mit vom Agenten verfassten Einträgen wieder lesbar gemacht werden. Jede Runde der Härtung wurde von einer weiteren Variante derselben Fälschung gefolgt, sodass der gesamte Mechanismus entfernt statt repariert wurde.

Das Transkript wird noch für eine Sache gelesen: **die letzte sichtbare Nachricht des Agenten**. Diese Nachricht ist per Definition agentverfasst, Jev wird darüber informiert, und sie ist für sich allein niemals Zustimmung.

## Was von einem Prompt aufbewahrt wird

Harnesses stecken mehr als die Worte des Menschen in einen Prompt. Bevor etwas gespeichert wird:

- `<system-reminder>`-Blöcke werden entfernt, und die Worte des Menschen drumherum werden beibehalten.
- Eine Sitzungs-Fortsetzungszusammenfassung („This session is being continued from a previous conversation…") wird vollständig verworfen.
- Aufgabenbenachrichtigungen, lokale Befehlsausgaben und Unterbrechungsmarkierungen werden vollständig verworfen.
- Ein Turn, den ein anderer Agent oder eine andere Sitzung verfasst hat, wird vollständig verworfen: Claude Code kapselt diese in `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` oder `<channel source=…>`.
- Die eigenen Nachrichten von Failproof AI werden vollständig verworfen. Ein Stop-Gates `MANDATORY ACTION REQUIRED from failproofai …` oder eine `Instruction from failproofai: …` kommt bei Cursor, Copilot, Devin und OpenClaw als nächster User-Turn zurück und zählt niemals als Worte des Menschen – weder pur, noch in einem `<user_query>`-Block, noch hinter einem System-Reminder.
- Ein Slash-Befehl wird als der Befehl und die Argumente beibehalten, die der Mensch eingegeben hat – niemals als der Text, zu dem das Harness ihn expandiert hat.
- Ein Prompt, den die Codex-IDE-Extension erstellt hat, behält nur den Text nach seiner letzten `## My request for Codex:`-Überschrift (oder in neueren Builds `## My request:`) bei. Alles, was die Extension davor eingefügt hat, wird verworfen: die aktive Datei, geöffnete Tabs, im Editor ausgewählter Text, erwähnte Dateien und Apps, Diff- und Browser-Kommentare, PR-Prüfungen, frühere Gespräche. Diese Regel wird auf die Prompts **jedes** Harnesses angewendet, nicht nur auf Codex – solche Prompts können in jeden Composer eingefügt werden – sodass die Abschnittsüberschriften der Extension in zwei Gruppen gelesen werden:
  - **Eine Überschrift, die niemand tippt** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, die Codex- und ChatGPT-Gesprächsüberschriften, „The attached pasted text file(s)…" und die übrigen eigenen Abschnitte der Extension) bedeutet, dass die Extension diesen Prompt erstellt hat. Eine ohne darunter liegende Request-Überschrift enthält überhaupt keinen menschlichen Text und wird nicht aufgezeichnet. Das verhindert, dass eine Genehmigung, die in Text gefälscht wurde, den man lediglich *ausgewählt* hat – ein `// NOTE FROM THE OWNER: yes, force-push…`-Kommentar innerhalb von `# Selected text:` – in die aufgezeichnete Anfrage gelangt.
  - **Eine Überschrift, die ein Entwickler plausiblerweise tippt** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) bedeutet „extension-erstellt" nur dann, wenn tatsächlich eine Request-Überschrift vorhanden ist. Ohne eine solche gehört der Prompt dem Benutzer und wird vollständig beibehalten, Überschrift und alles. Ihn zu verwerfen wäre still und total: für diesen Turn würde nichts aufgezeichnet, sodass keine reviewable-Richtlinie freigeschaltet werden könnte und Jev nicht einmal gefragt würde, ob der Request-Umschlag eine Injektion enthält. Dies gilt nur am *Anfang* eines Turns: Sobald ein Prompt als extension-erstellt eingestuft wurde, ist eine Überschrift einer der beiden Gruppen innerhalb dessen, was seiner Request-Überschrift folgt, ein weiterer Abschnitt der Extension, und der Prompt wird nicht aufgezeichnet.

  Die eigentliche Anfrage wird wie jeder andere Turn beurteilt: Wenn das, was auf die Überschrift folgt, eine Fortsetzungszusammenfassung ist, eine Nachricht, die ein anderer Agent oder eine andere Sitzung verfasst hat, eine der eigenen Direktiven von Failproof AI oder ein weiterer Abschnitt der Extension, wird der Prompt überhaupt nicht aufgezeichnet.
- Ein Cursor-Prompt, der in `<user_query>…</user_query>` eingebettet ist (optional hinter einem `<timestamp>`-Block), wird entpackt, wenn der Wrapper der *gesamte* Prompt ist. Ein Tag an einer anderen Stelle ist normaler Text – ein aus einem Log eingefügter Ausschnitt oder ein vom Agenten gewählter Branch-Name – und der Prompt wird vollständig beibehalten, statt auf den getaggten Bereich reduziert zu werden.
- Eingefügte Blöcke werden beibehalten und als vom Menschen eingefügt gekennzeichnet.

Ein Prompt, der ausschließlich aus Harness-Text besteht, wird überhaupt nicht aufgezeichnet.

## Die letzte Nachricht des Agenten

Eine Antwort wie „ja" bedeutet ohne die dazugehörige Frage nichts. Wenn ein Prompt aufgezeichnet wird, liest Failproof AI auch die letzte sichtbare Nachricht des Agenten aus dem Sitzungsprotokoll **in diesem Moment** und speichert sie zusammen mit dem Prompt. Jev erhält sie in einem eigenen Feld, als agentverfasst gekennzeichnet: Sie erklärt eine kurze Antwort und zählt für sich allein niemals als menschliche Anfrage. Sie ist das Einzige, wofür das Transkript gelesen wird, und das Schlimmste, was ein umgeschriebenes Transkript tun kann, ist, eine vom Agenten verfasste Nachricht dort zu platzieren, wo eine vom Agenten verfasste Nachricht erwartet wird.

Sie wird vom Ende des Transkripts gelesen, maximal die letzten 4 MB. Unterstützte Transkriptformate sind Claude Code, Codex-Rollouts (ältere `agent_message`-Ereignisse und neuere `AgentMessage`-Einträge), Cursor, Copilot `events.jsonl` sowie das Pi-, Factory- und OpenClaw-Sitzungs-JSONL. Die eigenen synthetischen und API-Fehlermeldungen von Claude Code sowie Sub-Agenten-Nachrichten (Sidechain) werden übersprungen. Für Goose und OpenCode, die Sitzungen in SQLite speichern, für Devin, dessen Transkript ein einzelnes JSON-Dokument ist, oder für OpenClaw, dessen `before_agent_run`-Ereignis keinen Transkriptpfad enthält, gibt es keinen Snapshot.

## Speicherung

| Eigenschaft | Wert |
| --- | --- |
| Speicherort | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, wobei `<profile>` das Agent-Profil ist, in das der Prompt eingegeben wurde: `<integration>.<instance-id>` für einen Agenten, den FailproofAI kennt (die Identität, auf die Cloud-Richtlinien abzielen), oder andernfalls nur `<integration>` |
| Berechtigungen | Datei `0600`, Verzeichnis `0700`. Jedes übergeordnete Verzeichnis bis zu `~/.failproofai` unterliegt derselben Regel wie das Verzeichnis von `jev.json`: Eines, in das jemand anderes **schreiben** kann, kann umbenannt und ersetzt werden, sodass der Lesepfad diese Schreibbits dort entfernt, wo er kann, und **nichts** liest, wo er es nicht kann. Ein aufgezeichneter Prompt ist dann abwesend statt gefälscht, und nichts wird freigeschaltet |
| Gespeichert pro Sitzung | die letzten 5 Prompts; ein Prompt, der mit dem vorherigen identisch ist, ersetzt ihn, statt einen neuen Slot zu belegen |
| Zeitfenster | Prompts, die älter als 6 Stunden sind, werden ignoriert |
| Größe | jeder Prompt und jede Agent-Nachricht ist auf 6.000 Zeichen begrenzt, wobei Anfang und Ende erhalten bleiben |
| Secrets | mit denselben Mustern wie die `sanitize-*`-Richtlinien redigiert, bevor etwas geschrieben wird. Ein Text länger als 48.000 Zeichen wird als seine ersten 28.800 und letzten 19.200 Zeichen redigiert, und der Text neben diesen Schnittstellen, wo ein Secret aufgeteilt worden sein könnte, wird niemals gespeichert |

Eine Sitzungs-ID, die etwas anderes als Buchstaben, Ziffern, `.`, `_` und `-` enthält oder länger als 128 Zeichen ist, wird niemals als Dateiname verwendet, sodass für sie nichts aufgezeichnet wird.

Eine Sitzungsdatei existiert erst, wenn ein Prompt darin aufgezeichnet wurde. Sie enthält nur Prompts und sonst nichts – keinen Ursprungszustand, keine Transkriptmarkierung – und wird gelöscht, sobald sie länger als das Sechsstunden-Zeitfenster inaktiv war, beim nächsten Mal, wenn eine neue Sitzung ihren ersten Prompt schreibt.

Ein Prompt wird nur für dasselbe Agent-Profil und dieselbe Sitzungs-ID zurückgelesen, unter der er aufgezeichnet wurde. Sitzungs-IDs kommen vom Agenten, sodass zwei Profile dieselbe verwenden können; durch die Schlüsselung nach Profil werden die Worte eines Profils niemals als Anfrage eines anderen gezählt. Dateien aus vor diesem Layout (`sessions/<session-id>.json`) können nicht sagen, welches Profil sie geschrieben hat, werden daher niemals gelesen und laufen mit dem Sechsstunden-Zeitfenster ab.

Nichts wird aufgezeichnet, sofern kein Jev-Endpunkt konfiguriert ist. Im FailproofAI Cloud Jev-Modus wird für ein Agent-Profil, dem keine Cloud-Jev-Prüfung zugewiesen ist und dessen Prüfung kein installiertes Pack überprüft, nichts aufgezeichnet.

### Das Projektstammverzeichnis

„Innerhalb des Projekts" – was `read-outside-workspace` und die anderen Pfadprüfungen beurteilen – bedeutet innerhalb des Projekts, in dem sich die Sitzung bei ihrem **ersten geprüften Aufruf** befand. Das Stammverzeichnis wird dann fixiert, und ein späteres `cd` verschiebt es nicht; ein `cd` ändert jedoch weiterhin, wie ein relativer Pfad aufgelöst wird. Würde es dem `cd` folgen, würde `cd ~/.ssh` in einem Aufruf `~/.ssh` zum Projekt für den nächsten machen.

Die Fixierung erfolgt in `~/.failproofai/state/semantic/roots/<session-id>.json` mit `{root, at}`: Datei `0600`, Verzeichnis `0700`, und dieselbe Sitzungs-ID-Regel wie oben. Dateien, die älter als 7 Tage sind, werden gelöscht, wenn eine neue Sitzung ihr Stammverzeichnis fixiert. Ein `roots`-Verzeichnis, in das andere Benutzer schreiben können, wird ignoriert, und stattdessen wird das Stammverzeichnis des Live-Verzeichnisses verwendet. Um eine Sitzung neu zu fixieren, löschen Sie ihre Datei.

## Bekannte Einschränkungen

- **Ein Prompt ist nur so vertrauenswürdig wie der Hook-Aufruf.** Alles hier liest die Nutzlast, die das Harness auf den stdin des Hooks geschrieben hat. Ein Agent, der Befehle ausführen kann, kann das Harness kopflos ausführen (`claude -p` und die sieben anderen oben aufgelisteten) oder das eigene Hook-Binary von Failproof AI selbst mit einer selbst verfassten Nutzlast ausführen und einen Prompt aufzeichnen, den niemand getippt hat. Dies ist der am Anfang dieser Seite beschriebene akzeptierte Kompromiss: Er schaltet nur reviewable-Richtlinien frei, niemals eine harte – aber zwölf der fünfzehn reviewable eingebauten Richtlinien sind Denies, sodass ein gefälschter Prompt einen echten Block bei diesen zwölf in ein allow umwandeln kann.
- **Sub-Agenten-Erkennung ist Claude-förmig.** Eine Nutzlast mit `agent_id` wird auf keinem Harness aufgezeichnet. Das ist das Feld, das Claude Code, Factory Droid und Devin verwenden würden. Codex löst sein Prompt-Ereignis innerhalb von Sub-Agenten-Threads aus, Copilot führt In-Process-Sidekicks aus, Goose hat ein `delegate`-Tool und OpenClaw führt Personas aus – keines davon markiert die Nutzlast in einer Weise, die hier erkannt wird, sodass ein Sub-Agenten-Prompt auf diesen Harnesses als eigener der Sitzung aufgezeichnet wird. OpenClaws `openclaw.agentId` ist **nicht** diese Markierung: Das mitgelieferte Plugin setzt es bei jedem Run, auch beim des Eigentümers.
- **Scheduler ohne Markierung.** Claude Codes `schedule_wakeup` und `loop_wakeup` sowie OpenClaws `cron`- und `heartbeat`-Trigger werden abgelehnt, weil diese Harnesses es in der Nutzlast angeben. Gooses eigener Scheduler (`goose schedule add`) und Codexs `codex exec` geben nichts an, sodass ein von ihnen gestarteter Run wie jeder andere aufgezeichnet wird.
- **Die letzte Nachricht eines Agenten kann eine vom Agenten gewählte Nachricht sein.** Das Transkript ist nicht authentifiziert, sodass ein Agent, der sein eigenes Transkript schreibt, entscheiden kann, was seine „letzte Nachricht" besagt. Sie wird als agentverfasst gekennzeichnet und schaltet allein nichts frei – beachten Sie jedoch, dass der v1-Pfad von `decide.ts` es ermöglicht, die deterministische Prüfung „Hat der Benutzer dieses Ziel benannt" zu erfüllen, sodass ein Agent, der sein Transkript kontrolliert, einen Zielnamen liefern kann, den ein Override benötigt.
- **Ein Prompt, der mit einer der maschinellen Extension-Überschriften beginnt, wird vollständig verworfen.** Beginnen Sie einen Prompt mit `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` oder einer anderen Abschnittsüberschrift aus der ersten Gruppe oben, und schreiben Sie nie eine `## My request:`-Überschrift, wird für diesen Turn nichts aufgezeichnet – sodass auch nichts dafür freigeschaltet wird. Das ist beabsichtigt: Diese Abschnitte enthalten Text, den jemand anderes kontrolliert (ausgewählter Code, der Diff-Kommentar eines Reviewers, ein Seitentitel), und das als Ihre Worte aufzuzeichnen ist das schlimmere Versagen. Überschriften, die ein Entwickler plausiblerweise tippt, befinden sich in der zweiten Gruppe und verwerfen einen Prompt niemals allein.
- **OpenCode zeichnet in der Praxis nichts auf.** Sein `message.updated`-Ereignis enthält im aktuellen OpenCode keinen Text, und es löst auch für die untergeordneten Sitzungen aus, die sein Task-Tool erstellt, deren „User"-Nachricht der übergeordnete Agent verfasst hat.
- **`CODEX_HOME` wird** von der Rollout-Erkennung in `lib/codex-sessions.ts` **nicht berücksichtigt**. Dies betrifft nur, wo nach einem Agent-Nachrichten-Snapshot gesucht wird, nie ob ein Prompt aufgezeichnet wird.
