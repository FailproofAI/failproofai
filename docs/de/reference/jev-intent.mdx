Wenn Sie die [Jev-Richtlinienprüfung](/de/policies/jev) konfigurieren, beurteilt der Evaluator jeden gesperrten Tool-Aufruf anhand von **dem, was der Mensch angefragt hat** – nicht anhand des Textes, den das Harness dem Agenten präsentiert hat. Eine Antwort wie „ja, force-pushe es" kann eine **reviewable**-Richtlinie freigeben – genau das ist der Zweck des Evaluators, da ein Regex, der die Anfrage nicht lesen kann, ein Drittel der echten Arbeit blockiert.

Dieser Text stammt aus einer einzigen Quelle: **dem Prompt, den das Harness selbst beim Prompt-Submit-Ereignis an den Hook übergibt**. Failproof AI zeichnet den vom Menschen eingegebenen Teil auf – Harness-Umrahmung entfernt, Secrets redigiert, begrenzt – in eine `0600`-Datei in seinem eigenen Zustandsverzeichnis. Nichts auf dem Datenträger wird konsultiert: Das Sitzungsprotokoll ist eine Datei, die der Agent mit einem einzigen Befehl überschreiben kann, daher wird nie gefragt, wer einen Prompt geschrieben hat.

## Das damit verbundene Risiko, offen benannt

Ein Agent, der bereits Befehle ausführen kann, kann ein Harness veranlassen, einen Prompt zu übermitteln. `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` und `pi -p` lösen alle dasselbe Prompt-Submit-Ereignis aus, mit derselben Nutzlast wie ein Mensch, der tippt – in einer untergeordneten Sitzung, die der Agent kontrolliert. Es kann auch Failproof AIs eigene Hook-Binary ausführen und ihr eine selbst erstellte Nutzlast übergeben. Nichts innerhalb von Failproof AI kann beides vom Original unterscheiden – beide sind dasselbe Programm, das dasselbe stdin liest.

**Ein Agent mit Shell-Zugriff kann also seine eigene Zustimmung fälschen.** Das ist ein bewusster Kompromiss, getroffen am 2026-09-23, und hier sind beide Seiten davon:

- **Was es bringt.** Die Alternative wurde gebaut und gemessen: ein Feld verlangen, in dem das Harness einen Menschen als Autor des Prompts nennt, und andernfalls nichts aufzeichnen. Kein ausgeliefertes Harness sendet ein solches Feld – diese Version zeichnete also **nichts, bei jedem Harness** auf. Jev beurteilte jeden Aufruf ohne angegebene Absicht und konnte keine einzige Richtlinie freigeben. Eine Erfassung, die nie auslöst, ist kein sichereres Produkt – sie ist kein Produkt.
- **Was es nicht kann.** Ein aufgezeichneter Prompt kann nur eine Richtlinie freigeben, die als **reviewable** markiert ist. Eine **hard**-Richtlinie wird durch nichts, was Jev sagt, jemals freigegeben – ein gefälschter Prompt kann also ein hartes deny niemals in ein allow verwandeln. Und den Hook zu überspringen bringt einem Agenten ebenfalls nichts: Das Harness ruft Failproof AI für den Tool-Aufruf unabhängig davon auf.
- **Was es im schlimmsten Fall kann.** Das Schlimmste, was es tun kann, ist eine der fünfzehn reviewable eingebauten Richtlinien freizugeben – und **zwölf dieser fünfzehn blockieren**. `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` und die sechs Infrastruktur-CLI-Blöcke (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) sind Verweigerer. Eine gefälschte Zustimmung kann also ein echtes deny in ein allow verwandeln beim Ausgeben von Umgebungs-Secrets, Lesen einer `.env`-Datei, Lesen außerhalb des Projekts, `rm -rf`, einem Force-Push, Schreiben einer Secrets-Datei oder Ändern von Live-Infrastruktur. Nur `warn-git-amend`, `warn-destructive-sql` und `warn-global-package-install` sind Hinweise. Eine Standardinstallation aktiviert zwei der zwölf: `protect-env-vars` und `block-env-files`; die anderen zehn erreichen nur einen Rechner, auf dem jemand sie aktiviert hat. Was kein Prompt erreicht, ist alles Harte – `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, der Schutz, der einen Agenten daran hindert, Failproof AI zu deaktivieren, und alle anderen eingebauten Richtlinien, die nicht als reviewable markiert sind. [Richtlinien-Autorität](/de/policies/authority) listet alle fünfzehn auf und was jede einzelne prüft.

Was weiterhin abgelehnt wird, ist alles, was günstig zu prüfen ist und was ein Agent nicht allein durch Fragen erlangen kann: ein Turn, den die eigene Nutzlast des Harness als maschinell eingereicht kennzeichnet, eine Nutzlast, die einen Sub-Agenten benennt, eine Sitzungs-ID, die kein einfacher Name ist, ein Ereignis, das kein Prompt-Submit-Ereignis ist, und Text, der nur aus Harness-Umrahmung besteht – einschließlich der eigenen Stop-Gate-Wörter von Failproof AI, die mehrere Harnesses als nächsten Benutzer-Turn zurückliefern.

## Harness-Tabelle

„Text field" ist das stdin-Nutzlastfeld nach der harnessspezifischen Normalisierung von Failproof AI. „Recorded" gibt an, ob der Prompt als Anfrage des Menschen gespeichert wird.

| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | Ja, es sei denn, das `source`-Feld der Nutzlast benennt einen Turn, den niemand eingereicht hat (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`). `user`, `sdk`, ein unbekannter Wert und ein Build, der gar kein `source` sendet, werden alle aufgezeichnet | das Sitzungsprotokoll (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | Ja | das Rollout-JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | Ja | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | Ja, mit abgestreifter `<user_query>`-Umrahmung, wenn sie der gesamte Prompt ist | das Agenten-Protokoll-JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | Ja – aber aktuelles OpenCode überträgt keinen Text in diesem Ereignis, daher wird in der Praxis nichts aufgezeichnet; eine Wiederholung derselben Nachricht wird nur einmal aufgezeichnet | keines (Sitzungen sind SQLite) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | Ja, es sei denn, `input_source` ist `extension` – das `sendUserMessage()` einer anderen Erweiterung, deren Text modell-geschrieben oder repo-abgeleitet sein kann | das Pi-Sitzungs-JSONL |

| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | Ja, es sei denn, die Run-Metadaten kennzeichnen den Run als maschinell: ein `trigger` ungleich `user`, ein `inputProvenance.kind` ungleich `external_user` oder `senderIsOwner: false` | keines (`before_agent_run` enthält keinen Protokollpfad) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | Ja | das Droid-Sitzungs-JSONL |

| Goose | `goose` | `UserPromptSubmit` | `message` | Ja | keines (Sitzungen sind SQLite) |

Zwei Harnesses zeichnen nichts auf, und aus demselben Grund: Ihr Ereignis liefert keinen menschlichen Text. Hermes hat kein Prompt-Submit-Ereignis – sein natives Plugin verarbeitet `pre_llm_call` selbst und leitet nur Tool-, Sitzungs- und Subagenten-Ereignisse weiter. Antigravitys `PreInvocation` löst vor jedem Modellaufruf aus – bei einem menschlichen Turn und bei den fünf darauffolgenden – und enthält kein Prompt-Feld; Hooks können auch `userMessage`-Schritte in dasselbe Gespräch injizieren. In keinem der Ereignisse gibt es etwas aufzuzeichnen.

## Was einen Prompt zum menschlichen macht

1. **Das Ereignis.** Failproof AI wurde für das Prompt-Submit-Ereignis des Harness aufgerufen, das der Handler zu `UserPromptSubmit` kanonisiert.
2. **Die Nutzlast.** Das Harness schreibt sie in das stdin des Hooks, und sie enthält den Text im oben genannten Feld. Ein Aufruf, der Failproof AI ohne Nutzlast erreicht, zeichnet nichts auf.
3. **Nichts in der Nutzlast schließt den Turn aus.** Eine Nutzlast, die einen Sub-Agenten nennt (`agent_id`), ist der Agent, der sich selbst promptet. Ein `source`, `input_source` oder OpenClaw-Run-Marker, der einen maschinell eingereichten Turn benennt, wird abgelehnt. Ein **fehlender** Marker schließt nichts aus – das ist der Unterschied zur Version, die nichts aufzeichnete, da jeder Marker hier bei jedem ausgelieferten Build fehlt.
4. **Nach dem Entfernen der Umrahmung bleibt etwas übrig** (siehe unten).

**Das Sitzungsprotokoll ist kein Beweis dafür, wer einen Prompt geschrieben hat.** Frühere Versionen dieser Seite beschrieben eine Protokoll-Querprüfung: Der Prompt wurde abgelehnt, wenn das Protokoll zeigte, dass das Modell ihn geplant hatte, und das Protokoll musste das des vorherigen Prompts fortsetzen. Diese Prüfung ist entfernt worden. Ein Protokoll ist eine Datei, über die der Agent bereits Shell-Zugriff hat – es kann abgeschnitten, ersetzt, über das Lesebudget hinaus aufgefüllt, zu Beginn eines Turns gespeichert und am Ende wiederhergestellt oder mit vom Agenten geschriebenen Einträgen neu lesbar gemacht werden. Jede Runde der Härtung wurde von einer weiteren Variante derselben Fälschung gefolgt, sodass der gesamte Mechanismus entfernt statt repariert wurde.

Das Protokoll wird noch für eine Sache gelesen: **die letzte sichtbare Nachricht des Agenten**. Diese Nachricht ist per Definition vom Agenten geschrieben, Jev wird darüber informiert, und sie zählt niemals allein als Zustimmung.

## Was von einem Prompt aufbewahrt wird

Harnesses stecken mehr als die Worte des Menschen in einen Prompt. Bevor etwas gespeichert wird:

- `<system-reminder>`-Blöcke werden entfernt, und die Worte des Menschen darum herum bleiben erhalten.
- Eine Sitzungsfortsetzungs-Zusammenfassung („This session is being continued from a previous conversation…") wird vollständig verworfen.
- Aufgabenbenachrichtigungen, lokale Befehlsausgaben und Unterbrechungsmarkierungen werden vollständig verworfen.
- Ein Turn, den ein anderer Agent oder eine andere Sitzung geschrieben hat, wird vollständig verworfen: Claude Code umhüllt diese in `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` oder `<channel source=…>`.
- Failproof AIs eigene Nachrichten werden vollständig verworfen. Ein Stop-Gates `MANDATORY ACTION REQUIRED from failproofai …` oder eine `Instruction from failproofai: …` kommt als nächster Benutzer-Turn bei Cursor, Copilot, Devin und OpenClaw zurück – und zählt niemals als Worte des Menschen, weder pur, noch in einem `<user_query>`-Block, noch hinter einer System-Erinnerung.
- Ein Slash-Befehl wird als der Befehl und die Argumente beibehalten, die der Mensch eingegeben hat – niemals als der Text, zu dem das Harness ihn expandiert hat.
- Ein Prompt, den die Codex-IDE-Erweiterung erstellt hat, behält nur den Text nach dem letzten `## My request for Codex:`-Heading (oder in neueren Builds `## My request:`) bei. Alles, was die Erweiterung davor gesetzt hat, wird verworfen: die aktive Datei, geöffnete Tabs, im Editor ausgewählter Text, erwähnte Dateien und Apps, Diff- und Browser-Kommentare, PR-Prüfungen, frühere Gespräche. Diese Regel wird auf die Prompts **jedes** Harness angewendet, nicht nur auf Codex – solche Prompts können in jede Eingabemaske eingefügt werden – sodass die Abschnitts-Headings der Erweiterung in zwei Gruppen gelesen werden:
  - **Ein Heading, das niemand tippt** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, die Codex- und ChatGPT-Gespräch-Headings, „The attached pasted text file(s)…" und die übrigen eigenen Abschnitte der Erweiterung) bedeutet, dass die Erweiterung diesen Prompt erstellt hat. Einer ohne Request-Heading darunter enthält keinen menschlichen Text und wird nicht aufgezeichnet. Das verhindert, dass eine Genehmigung, die in Text gefälscht wurde, den man lediglich *ausgewählt* hat – ein `// NOTE FROM THE OWNER: yes, force-push…`-Kommentar innerhalb von `# Selected text:` – in die aufgezeichnete Anfrage gelangt.
  - **Ein Heading, das ein Entwickler plausiblerweise tippt** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) bedeutet „erweiterungserstellt" nur, wenn tatsächlich ein Request-Heading vorhanden ist. Ohne eines gehört der Prompt dem Menschen und wird vollständig beibehalten. Ihn zu verwerfen wäre still und total: für diesen Turn würde nichts aufgezeichnet, sodass keine reviewable-Richtlinie freigegeben werden könnte und Jev nicht einmal gefragt würde, ob der Anfrage-Umschlag eine Injektion enthält. Dies gilt nur für den *Anfang* eines Turns: Sobald ein Prompt als erweiterungserstellt eingestuft wurde, ist ein Heading beider Gruppen innerhalb dessen, was auf sein Request-Heading folgt, ein weiterer Abschnitt der Erweiterung – und der Prompt wird nicht aufgezeichnet.

  Die Anfrage selbst wird wie jeder andere Turn beurteilt: Wenn das, was auf das Heading folgt, eine Fortsetzungs-Zusammenfassung ist, eine Nachricht, die ein anderer Agent oder eine andere Sitzung geschrieben hat, eine der eigenen Direktiven von Failproof AI oder ein weiterer Abschnitt der Erweiterung, wird der Prompt überhaupt nicht aufgezeichnet.
- Ein Cursor-Prompt, der in `<user_query>…</user_query>` eingebettet ist (optional hinter einem `<timestamp>`-Block), wird entpackt, wenn die Umrahmung der *gesamte* Prompt ist. Ein Tag an einer anderen Stelle ist normaler Text – ein aus einem Log eingefügter Ausschnitt oder ein vom Agenten gewählter Branch-Name – und der Prompt wird vollständig beibehalten, statt auf den markierten Bereich reduziert zu werden.
- Eingefügte Blöcke werden beibehalten und als vom Menschen eingefügt gekennzeichnet.

Ein Prompt, der ausschließlich aus Harness-Text besteht, wird überhaupt nicht aufgezeichnet.

## Die letzte Nachricht des Agenten

Eine Antwort wie „ja" bedeutet ohne die Frage, auf die sie antwortet, nichts. Wenn ein Prompt aufgezeichnet wird, liest Failproof AI auch die letzte sichtbare Nachricht des Agenten aus dem Sitzungsprotokoll **in diesem Moment** und speichert sie zusammen mit dem Prompt. Jev erhält sie in einem eigenen Feld, als vom Agenten geschrieben gekennzeichnet: Sie erklärt eine kurze Antwort und zählt niemals allein als Anfrage des Menschen. Sie ist das Einzige, wofür das Protokoll gelesen wird – und das Schlimmste, was ein umgeschriebenes Protokoll tun kann, ist, eine vom Agenten geschriebene Nachricht dort zu platzieren, wo eine vom Agenten geschriebene Nachricht erwartet wird.

Sie wird vom Ende des Protokolls gelesen, maximal die letzten 4 MB. Unterstützte Protokollformate sind Claude Code, Codex-Rollouts (ältere `agent_message`-Ereignisse und neuere `AgentMessage`-Einträge), Cursor, Copilot `events.jsonl` sowie das Pi-, Factory- und OpenClaw-Sitzungs-JSONL. Synthetische Nachrichten und API-Fehlermeldungen von Claude Code sowie Subagenten-(Sidechain-)Nachrichten werden übersprungen. Es gibt keinen Snapshot für Goose und OpenCode, die Sitzungen in SQLite halten, für Devin, dessen Protokoll ein einzelnes JSON-Dokument ist, oder für OpenClaw, dessen `before_agent_run`-Ereignis keinen Protokollpfad enthält.

## Speicherung

| Eigenschaft | Wert |
| --- | --- |
| Speicherort | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, wobei `<profile>` das Agentenprofil ist, in das der Prompt eingegeben wurde: `<integration>.<instance-id>` für einen Agenten, den FailproofAI kennt (die Identität, auf die Cloud-Richtlinien abzielen), oder andernfalls nur `<integration>` |
| Berechtigungen | Datei `0600`, Verzeichnis `0700`. Jedes Verzeichnis darüber, bis zu `~/.failproofai`, unterliegt derselben Regel wie das Verzeichnis von `jev.json`: eines, in das andere schreiben können, kann umbenannt und ersetzt werden – daher entfernt der Lesepfad diese Schreibbits, wo möglich, und liest **nichts**, wo er es nicht kann. Ein aufgezeichneter Prompt ist dann abwesend statt gefälscht, und nichts wird freigegeben |
| Pro Sitzung gespeichert | die letzten 5 Prompts; ein Prompt, der mit dem vorherigen identisch ist, ersetzt ihn, statt einen neuen Platz zu belegen |
| Zeitfenster | Prompts, die älter als 6 Stunden sind, werden ignoriert |
| Größe | jeder Prompt und jede Agentennachricht ist auf 6.000 Zeichen begrenzt, wobei Anfang und Ende erhalten bleiben |
| Secrets | mit denselben Mustern wie die `sanitize-*`-Richtlinien redigiert, bevor etwas geschrieben wird. Ein Text länger als 48.000 Zeichen wird als seine ersten 28.800 und letzten 19.200 Zeichen redigiert, und der Text neben diesen Schnitten, wo ein Secret aufgeteilt worden sein könnte, wird niemals gespeichert |

Eine Sitzungs-ID, die etwas anderes als Buchstaben, Ziffern, `.`, `_` und `-` enthält oder länger als 128 Zeichen ist, wird niemals als Dateiname verwendet – es wird also nichts für sie aufgezeichnet.

Eine Sitzungsdatei existiert erst, wenn ein Prompt darin aufgezeichnet wurde. Sie enthält nur Prompts – keinen Ursprungszustand, keine Protokollmarkierung – und wird gelöscht, sobald sie länger als das Sechs-Stunden-Fenster inaktiv war, das nächste Mal, wenn eine neue Sitzung ihren ersten Prompt schreibt.

Ein Prompt wird nur für dasselbe Agentenprofil und dieselbe Sitzungs-ID zurückgelesen, unter der er aufgezeichnet wurde. Sitzungs-IDs kommen vom Agenten, sodass zwei Profile dieselbe verwenden können; die Schlüsselung nach Profil verhindert, dass die Worte eines Profils jemals als Anfrage eines anderen zählen. Dateien aus der Zeit vor diesem Layout (`sessions/<session-id>.json`) können nicht sagen, welches Profil sie geschrieben hat – sie werden daher niemals gelesen und laufen mit dem Sechs-Stunden-Fenster ab.

Nichts wird aufgezeichnet, es sei denn, ein Jev-Endpunkt ist konfiguriert. Im FailproofAI Cloud Jev-Modus wird nichts für ein Agentenprofil aufgezeichnet, dem keine Cloud-Jev-Prüfung zugewiesen ist und das von keiner installierten Pack-Prüfung überprüft wird.

### Das Projektstammverzeichnis

„Innerhalb des Projekts" – wogegen `read-outside-workspace` und die anderen Pfadprüfungen urteilen – bedeutet innerhalb des Projekts, in dem sich die Sitzung bei ihrem **ersten überprüften Aufruf** befand. Der Stamm wird dann festgelegt, und ein späteres `cd` verschiebt ihn nie; ein `cd` ändert jedoch weiterhin, wie ein relativer Pfad aufgelöst wird. Würde er dem `cd` folgen, würde `cd ~/.ssh` in einem Aufruf `~/.ssh` zum Projekt für den nächsten machen.

Die Festlegung erfolgt in `~/.failproofai/state/semantic/roots/<session-id>.json`, das `{root, at}` enthält: Datei `0600`, Verzeichnis `0700`, und dieselbe Sitzungs-ID-Regel wie oben. Dateien, die älter als 7 Tage sind, werden gelöscht, wenn eine neue Sitzung ihren Stamm festlegt. Ein `roots`-Verzeichnis, in das andere Benutzer schreiben können, wird ignoriert, und stattdessen wird der Stamm des Live-Verzeichnisses verwendet. Um eine Sitzung neu festzulegen, löschen Sie ihre Datei.

## Bekannte Grenzen

- **Ein Prompt ist nur so vertrauenswürdig wie der Hook-Aufruf.** Alles hier liest die Nutzlast, die das Harness in das stdin des Hooks geschrieben hat. Ein Agent, der Befehle ausführen kann, kann das Harness headless ausführen (`claude -p` und die sieben anderen oben aufgeführten) oder Failproof AIs Hook-Binary selbst mit einer selbst erstellten Nutzlast ausführen und einen Prompt aufzeichnen, den niemand getippt hat. Dies ist der am Anfang dieser Seite beschriebene akzeptierte Kompromiss: Er gibt nur reviewable-Richtlinien frei, niemals eine harte – aber zwölf der fünfzehn reviewable eingebauten Richtlinien sind Verweigerer, sodass ein gefälschter Prompt einen echten Block bei diesen zwölf in ein allow verwandeln kann.
- **Sub-Agenten-Erkennung ist Claude-förmig.** Eine Nutzlast mit `agent_id` wird niemals aufgezeichnet, bei keinem Harness. Das ist das Feld, das Claude Code, Factory Droid und Devin verwenden würden. Codex löst sein Prompt-Ereignis innerhalb von Sub-Agenten-Threads aus, Copilot führt In-Process-Sidekicks aus, Goose hat ein `delegate`-Tool und OpenClaw führt Personas aus – keines davon markiert die Nutzlast auf eine Weise, die hier erkannt wird. Ein Sub-Agenten-Prompt auf diesen Harnesses wird also als sitzungseigener aufgezeichnet. OpenClaws `openclaw.agentId` ist **nicht** diese Markierung: Das ausgelieferte Plugin setzt sie bei jedem Run, einschließlich dem des Eigentümers.
- **Scheduler ohne Markierung.** Claude Codes `schedule_wakeup` und `loop_wakeup` sowie OpenClaws `cron`- und `heartbeat`-Trigger werden abgelehnt, weil diese Harnesses es in der Nutzlast angeben. Gooses eigener Scheduler (`goose schedule add`) und Codexs `codex exec` geben nichts an, sodass ein von ihnen gestarteter Run wie jeder andere aufgezeichnet wird.
- **Die letzte Nachricht eines Agenten kann eine vom Agenten gewählte Nachricht sein.** Das Protokoll ist nicht authentifiziert, sodass ein Agent, der sein eigenes Protokoll schreibt, entscheiden kann, was seine „letzte Nachricht" besagt. Sie ist als agentengeschrieben gekennzeichnet und löscht niemals etwas allein – beachten Sie jedoch, dass der v1-Pfad von `decide.ts` es ermöglicht, die deterministische Prüfung „Hat der Benutzer dieses Ziel benannt" zu erfüllen. Ein Agent, der sein Protokoll kontrolliert, kann also einen Zielnamen liefern, den ein Override benötigt.
- **Ein Prompt, der mit einem der maschinellen Headings der Erweiterung beginnt, wird vollständig verworfen.** Beginnen Sie einen Prompt mit `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` oder einem anderen Abschnitts-Heading aus der ersten Gruppe oben, und schreiben Sie nie ein `## My request:`-Heading, so wird für diesen Turn nichts aufgezeichnet – und nichts dafür freigegeben. Das ist beabsichtigt: Diese Abschnitte enthalten Text, den jemand anderes kontrolliert (ausgewählter Code, der Diff-Kommentar eines Reviewers, ein Seitentitel), und diesen als Ihre Worte aufzuzeichnen wäre das schlimmere Versagen. Headings, die ein Entwickler plausiblerweise tippt, befinden sich in der zweiten Gruppe und verwerfen einen Prompt niemals allein.
- **OpenCode zeichnet in der Praxis nichts auf.** Sein `message.updated`-Ereignis enthält im aktuellen OpenCode keinen Text, und es löst auch für die untergeordneten Sitzungen aus, die sein Task-Tool erstellt, deren „user"-Nachricht der übergeordnete Agent geschrieben hat.
- **`CODEX_HOME` wird nicht berücksichtigt** bei der Rollout-Erkennung in `lib/codex-sessions.ts`. Dies betrifft nur den Ort, an dem nach einem Agentennachrichten-Snapshot gesucht wird, nie ob ein Prompt aufgezeichnet wird.
