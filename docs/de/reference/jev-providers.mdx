Dies ist die Anbieter- und Konfigurationsreferenz für [Jev-Richtlinien](/de/policies/jev) mit eigenem Schlüssel. Regex-Richtlinien gleichen Zeichenketten ab. Sie können nicht unterscheiden, ob `rm -rf build/` von Ihnen angefordert wurde oder ob `rm -rf ~` in einen Plan gerutscht ist – deshalb blockieren sie an einer Stelle zu viel und an einer anderen zu wenig. **Jev**, der Klassifikator von TypeSafe, liest den Aufruf im Kontext Ihrer tatsächlichen Anfrage und beantwortet dabei eine Reihe von Ja/Nein-Fragen in einer einzigen schnellen Anfrage.

Wenn ein eigener Jev-Endpunkt und -Schlüssel konfiguriert sind, fragt Failproof AI Jev zu jedem Tool-Call **zusätzlich** zu den Regex-Richtlinien ab – niemals stattdessen:

- Ein **hartes** Policy-Deny ist endgültig. Jev kann es nicht aufheben. Jede Richtlinie ist hart, es sei denn, sie ist ausdrücklich als prüfbar markiert und benennt die Jev-Prüfungen, die sie abdecken. Eine benutzerdefinierte, aus einem Paket stammende oder Cloud-Richtlinie, die nichts angibt, ist hart, und der immer aktive Selbstschutz ist ebenfalls immer hart.
- Ein **prüfbares** Policy-Deny kann aufgehoben werden – aber nur, wenn Jev explizit zu dem genauen Anliegen befragt wurde, das diese Richtlinie abdeckt, und mit „nichts hier" oder „der Benutzer hat darum gebeten" geantwortet hat. Eine Prüfung, die das Anliegen als tatsächlich vorhanden identifiziert, wenn der Benutzer den Aufruf nicht angefordert hat, hält das Deny aufrecht – selbst wenn ihr eigenes Urteil nur eine Warnung ist, denn vor einem Tool-Call hält eine Warnung den Agenten nicht auf. Und wenn diese Prüfung eine ist, die ein Deny auslösen kann (Secret-Exposition, Credential-Exfiltration, destruktives Löschen, …), wird für diesen Aufruf nichts aufgehoben.
- Eine Blockierung kann dennoch zur **Warnung** werden, wenn der Aufruf ein Schritt der von Ihnen gestellten Aufgabe ist und nicht weiter reicht: Jev mildert sein eigenes Deny zu einer Warnung ab, und diese Warnung – die benennt, was tatsächlich mit dem Aufruf nicht stimmt – ersetzt die Blockierung der Richtlinie.
- Jev kann auch eigenständig warnen oder ablehnen, bei Schäden, die kein Regex beschreibt.
- Wenn Jev nicht antworten kann (Timeout, Rate-Limit, Serverfehler, kein Guthaben, eine unerwartete Modellversion), erhält dieser Aufruf das Regex-Ergebnis – genau wie ohne Jev.
- Jev macht einen Aufruf nie zulässiger als Ihre Richtlinien allein, es sei denn, es hat den gesamten Aufruf gelesen und wurde zu genau dem relevanten Anliegen befragt. Alles darunter – ein zu großer Aufruf, ein vermuteter Injection-Versuch – zieht die Freigaben zurück und hält jedes Deny aufrecht.

<Note>
Ohne Jev-Konfiguration ändert sich nichts: Hooks führen die Regex-Richtlinien exakt so aus wie bisher. Die Konfiguration ist der vollständige Opt-in.
</Note>

<Tip>
Nutzen Sie FailproofAI Cloud? Sie benötigen keinen eigenen Schlüssel: Eine Maschine, die mit einem Schlüssel mit `jev:evaluate`-Berechtigung verbunden ist, kann Jev im Rahmen des Organisationsplans verwenden. Siehe [Jev über FailproofAI Cloud](/de/reference/jev-cloud).
</Tip>

## Vorbereitung

Installieren Sie **failproofai 1.0.8-beta.0 oder höher** und hängen Sie die Hooks an ein [unterstütztes Harness](/de/reference/harnesses) auf der Maschine an, auf der Ihr Agent läuft. Folgen Sie dem [Quickstart](/de/start/quickstart) für eine neue Maschine oder richten Sie [lokale Durchsetzung ein](/de/start/setup#enforce-locally), wenn Sie Cloud nicht verwenden. Prüfen Sie die installierte CLI mit `failproofai --version`.

Holen Sie sich einen API-Schlüssel von einem der unten aufgeführten Anbieter, oder halten Sie einen kompatiblen Endpunkt und dessen Schlüssel bereit. Jev prüft benannte Tool-Calls am `PreToolUse`- oder `PermissionRequest`-Gate. Es kann ein eigenes Urteil abgeben, aber das Aufheben eines bestehenden Policy-Denys erfordert außerdem eine installierte, als [prüfbar](/de/policies/authority) markierte Richtlinie. Harte Policy-Denys bleiben endgültig.

## Anbieter wählen

Jev ist über fünf Wege erreichbar. Bringen Sie für einen davon einen Schlüssel mit.

| Anbieter | `--provider` | Endpunkt | Standardmodell | Hinweise |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Exakte Versionsangabe. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | Anfragen werden ausschließlich an Endpunkte ohne Datenspeicherung weitergeleitet, ohne Fallback zu einem anderen Anbieter. Meldet eine datierte Version wie `typesafe/jev-1.13-20260917`. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Benennt Jev nur per Alias, daher wird die antwortende Version als nicht verifiziert aufgezeichnet. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | Benötigt `--account-id`. Gemessen wurden etwa sechs Anfragen pro Sekunde je Schlüssel, bevor HTTP 429 auftrat. |
| Eigener Endpunkt | `custom` | `<base-url>/systemone` | `jev-1.13.0` | Jeder Endpunkt, der den TypeSafe-Request-Body akzeptiert und meldet, welches Modell geantwortet hat. Nur `https`; einfaches `http` zu einem Loopback-Host (`localhost`, `127.0.0.1`, `::1`) wird für lokale Tests akzeptiert. |

<Warning>
Mit Vercels eigenem Bring-your-own-key-Feature wird eine fehlgeschlagene Anfrage stillschweigend mit Vercels Zugangsdaten wiederholt. Wenn Sie sicherstellen möchten, dass jeder Aufruf ausschließlich Ihrem eigenen TypeSafe-Konto in Rechnung gestellt und von ihm gesehen wird, nutzen Sie TypeSafe direkt.
</Warning>

## Einrichten

Ein Befehl, der Endpunkt und der Schlüssel. Starten Sie im `observe`-Modus, damit Sie Jevs Urteile prüfen können, während die bestehenden Richtlinien weiterhin über Aufrufe entscheiden:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### Die URL bestimmt den Anbieter

Sie müssen den Anbieter nicht explizit benennen: Der **Host** der URL entscheidet, welcher es ist.

| URL-Host | Anbieter | Zusätzlich benötigt |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| beliebiger anderer Host | `custom` | — die angegebene URL ist die Basis-URL |

Daraus folgen drei Dinge:

- **Eine URL, die der eigene API des Anbieters ist, schreibt keine Überschreibung.** `--url https://api.typesafe.ai/v1` erzeugt exakt die Konfiguration, die `--provider typesafe` erzeugt hätte. Geben Sie einen anderen Pfad oder Host bei einem bekannten Anbieter an, wird er als Basis-URL gespeichert, genau wie es `--base-url` tun würde.
- **`--provider` überschreibt weiterhin die Ableitung**, was die Möglichkeit bietet, einen Proxy zu erreichen, der die API eines Anbieters von einem eigenen Host aus spricht: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **Ein `--provider`, der dem Host widerspricht, wird abgelehnt** – ohne Rätselraten. `--provider openrouter --url https://api.typesafe.ai/v1` schreibt nichts und erklärt warum: Die beiden Angaben stimmen darüber nicht überein, wohin Ihr Schlüssel geschickt werden soll. Dasselbe Paar wird auch von `jev setup --base-url` und den Jev-Einstellungen im Dashboard abgelehnt. (`--provider custom` ist kein Widerspruch – es bedeutet „behandle diese URL als sich selbst" – außer beim Cloudflare-Host, dessen kontospezifischen Endpunkt eine Custom-Route nicht erreichen kann.)

`--url` wird genauso validiert wie `baseUrl` in der Konfigurationsdatei und mit denselben Worten abgelehnt: `https`, oder einfaches `http` zu einem Loopback-Host (`localhost`, `127.0.0.1`, `::1`) in jedem Modus. Risiko: Ein Loopback-Server wird nicht authentifiziert; solange er ausgefallen ist, könnte ein anderer lokaler Prozess seinen Port übernehmen und antworten. Verwenden Sie außerhalb lokaler Tests `https`.

### Der Schlüssel

Leiten Sie ihn mit `--key-stdin` ein, oder führen Sie den Befehl ohne dieses Flag in einem Terminal aus und fügen Sie den Schlüssel an einer verdeckten Eingabeaufforderung ein. In beiden Fällen landet er direkt in der Konfigurationsdatei und wird nie zurückgegeben.

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` akzeptiert dieselben Flags und ist die Langform für alles: `setup --provider <kind>`, wenn Sie lieber den Anbieter als die URL angeben möchten.

### `--token` und die Kosten

`--token <token>` übergibt den Schlüssel als Kommandozeilenargument – der schnellste Weg, eine Maschine zu konfigurieren, aber auch die einzige Variante, bei der der Schlüssel außerhalb der Konfigurationsdatei landet:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
Ein Kommandozeilenargument landet anschließend in der Shell-History und ist während der Ausführung in der Prozessliste sichtbar – von `/proc` aus lesbar für alles, was als Sie ausgeführt wird. `setup` weist bei jeder Verwendung von `--token` darauf hin. Bevorzugen Sie `--key-stdin` auf einer gemeinsam genutzten Maschine, in aufgezeichneten Sitzungen oder überall dort, wo die History-Datei synchronisiert wird. Rotieren Sie einen so übergebenen Schlüssel, wenn dies sicherheitsrelevant ist.
</Warning>

`--token`, `--key-stdin` und `--key-from-env` schließen sich gegenseitig aus: Geben Sie genau eine Option an.

Senden Sie dann eine kleine Live-Anfrage, um den Schlüssel, den Endpunkt und die antwortende Jev-Version zu prüfen:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` beendet sich mit Exit-Code 1 und zeigt dies im Titel an, wenn die Antwort nach dem Timeout eintrifft (jeder Hook würde dann auf Regex zurückfallen, Grund: `timeout`) oder die Prüffrage falsch beantwortet.

Hooks lesen die Konfiguration bei jedem Tool-Call neu, sie greift also ab dem nächsten Aufruf. Es muss nichts neu gestartet werden – weder mit noch ohne Daemon.

## Aktivität prüfen

```bash
failproofai jev status
failproofai jev status --json
```

`status` zeigt Anbieter, Endpunkt, Modell, Modus, Konfigurationsdatei und deren Berechtigungen – niemals den Schlüssel. Darunter fasst es die letzte Aktivität zusammen: wie viele Aufrufe Jev ausgewertet hat, wie oft es auf Regex zurückgefallen ist und warum, die Latenz und welche prüfbaren Richtlinien aufgehoben wurden.

## Einen echten Aufruf verifizieren

Starten Sie eine neue Sitzung im Hook-Agenten. Bitten Sie ihn, sein File-Reading-Tool auf `README.md` anzuwenden und den Titel zurückzugeben. Vergewissern Sie sich, dass die Sitzung diesen Tool-Call enthält, und führen Sie dann erneut `failproofai jev status` aus: Der Zähler der ausgewerteten Aufrufe sollte gestiegen sein. Öffnen Sie **Policies → Activity** im [lokalen Dashboard](/de/reference/local-dashboard#review-policy-activity), um das Jev-Urteil und den Modus für diesen Aufruf zu inspizieren. Im Observe-Modus entscheidet weiterhin das Richtlinien-Ergebnis. Eine Freigabe erscheint nur, wenn eine prüfbare Richtlinie anschlug und Jev jede benannte Prüfung bestanden hat; ein einfacher Lesevorgang hat möglicherweise keine aufzuhebende Richtlinie.

## Observe-Modus

`enforce` ist der Standard. Um Jev zu beobachten, ohne dass es Entscheidungen beeinflusst, wechseln Sie zu `observe`: Jev wird weiterhin befragt und seine Urteile aufgezeichnet, aber das Regex-Ergebnis wird durchgesetzt.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` behält die Konfiguration – Endpunkt und Schlüssel – und stellt die Jev-Abfragen ein: Hooks führen die Regex-Richtlinien exakt wie ohne Konfiguration aus, und `failproofai jev status` meldet „off (switched off)". Wechseln Sie mit `--mode observe` oder `--mode enforce` zurück.

Ein erneuter `setup`-Aufruf für denselben Anbieter behält den gespeicherten Schlüssel, ein Moduswechsel erfordert also nur ein einziges Flag. Ein Anbieterwechsel startet neu und fordert den Schlüssel für den neuen Anbieter an. Dasselbe gilt für eine `--base-url`, die Anfragen zu einem anderen Host umleitet: Ein gespeicherter Schlüssel wird nur an den Host gesendet, für den er eingegeben wurde, oder an die eigene API des Anbieters.

## Die Konfigurationsdatei

Alles liegt in einer Datei, `~/.failproofai/jev.json`, die von `setup` geschrieben wird:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Feld | Bedeutung |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` oder `custom` – oder `failproofai`, dessen Schlüssel aus der FailproofAI Cloud-Verbindung statt aus dieser Datei kommt (siehe [Jev über FailproofAI Cloud](/de/reference/jev-cloud)). |
| `apiKey` | Wird als `Authorization: Bearer <key>` gesendet. |
| `baseUrl` | Für `custom` erforderlich; ersetzt andernfalls die API-Basis des Anbieters. Muss `https` sein. Einfaches `http` zu `localhost` wird nur mit `mode: observe` akzeptiert: Ein lokaler Port wird nicht authentifiziert; solange Ihr Proxy ausgefallen ist, könnte jeder Prozess auf der Maschine – einschließlich des zu beurteilenden Agenten – an seiner Stelle antworten. |
| `accountId` | Nur für Cloudflare: 32 hexadezimale Kleinbuchstaben. |
| `model` | Ersetzt die Standard-Modell-ID des Anbieters. Eine versionierte ID muss Jev 1.13 benennen. Ein Wert in der Form eines API-Schlüssels wird abgelehnt (und nicht zurückgegeben), damit ein versehentlich als Modell eingetragener Schlüssel weder gespeichert noch gesendet wird. |
| `timeoutMs` | Wie lange ein Tool-Call auf Jev wartet, bevor das Regex-Ergebnis verwendet wird. 100–10000, Standard 3000. |
| `mode` | `enforce` (Standard), `observe` oder `off` (Konfiguration behalten, kein Jev ausführen). |

Drei Regeln schützen die Datei:

- **Nur für den Besitzer.** Sie wird mit Berechtigungen `0600` geschrieben. Eine Kopie, die ein anderer Benutzer oder eine andere Gruppe lesen oder schreiben kann, wird **abgelehnt**, und Hooks fallen auf Regex zurück, bis Sie `chmod 600 ~/.failproofai/jev.json` oder erneut `setup` ausführen. Das Verzeichnis wird ebenfalls geprüft: `~/.failproofai` darf von niemandem anderen **beschreibbar** sein, denn wer dort schreiben kann, kann die Datei unabhängig von ihren eigenen Berechtigungen ersetzen. `setup` entfernt solche Schreibbits, wenn es sie findet. `failproofai jev status` zeigt an, wenn eine Konfiguration abgelehnt wurde, und zeigt den Endpunkt an, den die Datei benennt: Jemand anderes könnte sie geändert haben, prüfen Sie also, ob sie Ihnen gehört, bevor Sie `chmod` ausführen. Ein erneuter `setup`-Aufruf für eine solche Datei überträgt den gespeicherten Schlüssel nur an die eigene API des Anbieters; für jeden anderen Endpunkt, den die Datei nennt, wird der Schlüssel erneut benötigt (`--key-stdin`), oder `--base-url default` leitet Anfragen zurück zum Anbieter.
- **Nur global.** Ein Repository kann Jev weder aktivieren noch auf einen anderen Endpunkt zeigen noch ein Modell auswählen: Eine `.failproofai/jev.json` innerhalb eines Projekts wird ignoriert, und Anbieter, URL, Modell und Account-ID werden ausschließlich aus dieser Datei gelesen – nie aus der Umgebung, die die Agenten-Einstellungen eines Repositories setzen können. (`FAILPROOFAI_HOME` ist kein Umweg: Es verschiebt das gesamte failproofai-Verzeichnis einschließlich Ihrer Richtlinien, anstatt Jev gezielt umzuleiten.)
- **Nur der Schlüssel kann aus der Umgebung kommen.** Enthält die Datei kein `apiKey`, liefert `FAILPROOFAI_JEV_API_KEY` ihn für diese Sitzung (`setup --key-from-env` schreibt eine solche Datei). Es ersetzt nie einen in der Datei enthaltenen Schlüssel und kann Jev ohne die Datei nicht aktivieren. Ist die Variable nicht gesetzt, ist Jev für diese Shell schlicht deaktiviert: `failproofai jev status` meldet dies, beendet sich mit Exit-Code 0 und lässt die Konfiguration unberührt (`status --json` meldet `"status": "key-missing"` mit `"reason": "no-env-key"`). Der `failproofaid`-Daemon sieht Ihre Shell-Umgebung nicht; halten Sie den Schlüssel auf einer mit `failproofai config` eingerichteten Maschine daher in der Datei.

## Welches Jev antwortet

Die Entscheidungsschwellen von Failproof AI wurden auf Jev 1.13 kalibriert, daher wird eine Antwort nur dann verwendet, wenn sie aus dieser Familie stammt: `jev-1.13.x` oder OpenRouters `typesafe/jev-1.13-<date>`. Wo ein Anbieter Jev nur per Alias benennt und keine Version meldet (Vercel und Cloudflare, wenn keine Version angegeben wird), wird die Antwort verwendet und als nicht verifiziert aufgezeichnet. Ein `custom`-Endpunkt muss das antwortende Modell melden; die einzige Ausnahme ist ein unversionierter `--model`-Name, den Sie für ihn konfiguriert haben, der – wenn er zurückgemeldet wird – ebenfalls als nicht verifiziert aufgezeichnet wird. Eine Antwort, die eine andere Version meldet, oder eine `custom`-Antwort ohne Versionsangabe wird nicht verwendet: Dieser Aufruf fällt auf Regex zurück mit dem Grund `model-mismatch`.

## Wenn Jev nicht antworten kann

Jeder der folgenden Fälle führt für diesen Aufruf zum Regex-Fallback und wird mit seinem Grund aufgezeichnet, den `failproofai jev status` zusammenfasst:

| Grund | Ursache |
| --- | --- |
| `timeout` | Keine Antwort innerhalb von `timeoutMs`. |
| `http-429` | Der Anbieter hat den Schlüssel rate-limitiert. |
| `rate-limited` | Der eigene Begrenzer von Failproof AI hat den Aufruf zurückgehalten, bevor er gesendet wurde: 5 Anfragen pro Sekunde in Bursts von bis zu 5, und eine kurze Pause nach einer `429`-Antwort des Anbieters. Nicht der Anbieter. |
| `http-500`, `http-502`, `http-503`, … | Ein Serverfehler beim Anbieter. Der genaue Status wird aufgezeichnet. |
| `out-of-credits` | HTTP 402: Das Anbieterkonto hat kein Guthaben mehr. |
| `provider-refused` | HTTP 402 von Cloudflare mit der Meldung „Model execution failed (Payment error)": Der Anbieter hat es abgelehnt, das Modell für diese Anfrage auszuführen. Meist kein Abrechnungsproblem, das durch Aufladen behoben werden könnte. |
| `http-401`, `http-403` | Der Schlüssel wurde abgelehnt. |
| `http-404` | Unter `<base>/systemone` wird nichts bereitgestellt, die Basis-URL ist also falsch – `/systemone` wird an sie angehängt, und jeder Anbieter stellt es an seinem Versions-Root bereit. `failproofai jev models` zeigt, was der Endpunkt tatsächlich bereitstellt. |
| `network` | Der Endpunkt war nicht erreichbar. |
| `http-301`, `http-302`, `http-307`, `http-308` | Der Endpunkt antwortete mit einer Weiterleitung. Weiterleitungen werden nie gefolgt; die Antwort kommt also immer von der in Ihrer Konfiguration hinterlegten URL. Setzen Sie `--base-url` auf die endgültige URL. |
| `malformed` | Der Endpunkt antwortete, aber nicht mit einer Jev-Antwort – ein Body, der kein JSON ist, oder einer ohne Antworten darin. |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflares Envelope meldete einen Fehler oder einen noch nicht abgeschlossenen Job. |
| `model-mismatch` | Eine Jev-Version außer 1.13 antwortete, oder ein `custom`-Endpunkt gab nicht an, welches Modell geantwortet hat. |
| `request-cut` | **Kein Ausfall.** Jev antwortete; es sah aber nur einen Teil des Aufrufs, daher hob seine Antwort nichts auf. Siehe [Wenn Jev antwortete, aber nicht auf den gesamten Aufruf](#wenn-jev-antwortete-aber-nicht-auf-den-gesamten-aufruf). |

`failproofai jev status` kann auch einige seltenere Gründe anzeigen, wie `upstream-error` (die Antwort enthielt den eigenen Fehler des Anbieters) oder `config`, und fasst jeden nicht benennbaren Grund als `other` zusammen.

`request-cut` ist in dieser Tabelle aufgeführt, weil `failproofai jev status` es zusammen mit den übrigen zählt und weil es ebenfalls jedes Deny aufrechterhält. Es ist der einzige Grund hier, der nichts über Ihren Anbieter aussagt: Die Anfrage kam an und Jev hat geantwortet. Anders als bei allen Zeilen darüber zählt diese Antwort noch – Jevs eigenes Deny oder seine Warnung gilt zusätzlich zum Regex-Ergebnis, statt verworfen zu werden. Eine Häufung solcher Fälle bedeutet also, dass Aufrufe den Evaluator in einer Größe erreichen, die nicht vollständig gesendet werden kann – nicht dass Ihr Endpunkt nicht in Ordnung ist. Guthaben aufzuladen oder die URL zu ändern, wird die Zahl nicht reduzieren.

## Wenn Jev antwortete, aber nicht auf den gesamten Aufruf

Zwei weitere Situationen können eintreten, bei denen es sich nicht um einen Jev-Ausfall handelt. Beide betreffen, wie viel des Aufrufs oder des Gesprächsverlaufs in eine einzige Anfrage passte.

**Ein Teil des Aufrufs selbst passte nicht hinein.** Ein Tool-Call wird innerhalb eines festen Budgets gesendet, und ein überdimensionierter – ein sehr großes `Write`, ein riesiger MCP-Body, ein bis zum Limit aufgefüllter Befehl – wird mit dem gesendeten, was gepasst hat. Jev antwortet dennoch, und seine Antwort zählt weiterhin: sein eigenes Deny oder seine Warnung gilt wie gewohnt. Was es nicht tun kann, ist etwas **aufzuheben**, denn ein Urteil über einen Teil eines Aufrufs ist kein Urteil über den gesamten Aufruf. Jedes Policy-Deny bleibt also bestehen, und der Aufruf wird als Fallback mit dem Grund `request-cut` aufgezeichnet, den `failproofai jev status` zusammen mit den obigen Gründen zählt. Die Regel, die sich daraus ergibt: Einen Aufruf größer zu machen kann seine Freigaben kosten und kann nie eine hinzugewinnen.

**Eine Nachricht passte nicht hinein.** Ein langer eingefügter Prompt, die letzte Nachricht des Agenten oder ein Prompt, den der eigene Store dieses Evaluators bereits beschnitten hatte. **Es ändert sich nichts**: Der Aufruf wird genauso beurteilt, freigegeben und aufgezeichnet wie jeder andere und wird nicht als Fallback gezählt. Die Länge Ihrer Eingabe entscheidet nie über ein Urteil, und ein Beschnitt kann keine Zustimmung herstellen: Wenn ein Prompt bereits beschnitten ankam, ist „Sie haben das nicht angefordert" eine Schlussfolgerung, die gar nicht mehr gezogen werden kann – sie wird nicht einfach zur Schlussfolgerung.

Die Grenze zwischen beiden Fällen liegt darin, wer den Text verfasst hat. Der Aufruf gehört dem Agenten, und eine Regel, die seine Länge den Schweregrad verringern lässt, wäre eine Regel, die der Agent ausnutzen kann; Ihr Prompt gehört Ihnen, und seine Länge als Signal zu behandeln würde nur dazu führen, dass das Einfügen einer Spezifikation oder eines Stack-Trace bestraft wird.

## Was die Maschine verlässt

Für jeden Tool-Call, den Jev auswertet, wird eine Anfrage an Ihren Anbieter gesendet, die enthält:

- den Tool-Call selbst, wobei Secrets wie API-Schlüssel, Bearer-Token und `KEY=`-Zuweisungen geschwärzt sind;
- die zuletzt von Ihnen eingegebenen Prompts, ohne den Text, den das Harness Ihres Agenten hinzugefügt hat;
- die letzte Nachricht des Agenten vor Ihrem neuesten Prompt, als agentenverfasst gekennzeichnet;
- lokal berechnete Fakten, z. B. ob ein Pfad innerhalb des Projekts liegt – des Projekts, in dem die Sitzung beim ersten geprüften Aufruf war, [für die Sitzung fixiert](/de/reference/jev-intent#the-project-root) – und den aktuellen Git-Branch.

Sie geht ausschließlich an den Endpunkt in Ihrer Konfiguration, unter Ihrem Schlüssel.

## Deaktivieren

```bash
failproofai jev remove
```

Dies löscht `~/.failproofai/jev.json`. Ab dem nächsten Tool-Call führen Hooks die Regex-Richtlinien exakt wie zuvor aus. Die sitzungsspezifischen Stores unter `~/.failproofai/state/semantic/` (aufgezeichnete Prompts in `sessions/`, Projektwurzeln in `roots/`) bleiben erhalten und laufen ab. Um Jev zu stoppen, aber die Konfiguration zu behalten, verwenden Sie stattdessen `failproofai jev setup --mode off`.

## Befehlsreferenz

| Befehl | Ergebnis |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | In einem Befehl konfigurieren; der Anbieter ergibt sich aus dem URL-Host |
| `failproofai jev --url <url> --token <token>` | Dasselbe, mit dem Schlüssel in der Kommandozeile – History und Prozessliste sehen ihn |
| `failproofai jev setup --provider <kind> --key-stdin` | Konfiguration aus einem per stdin eingeleiteten Schlüssel schreiben |
| `failproofai jev setup --provider <kind>` | Dasselbe, Schlüssel an verdeckter Eingabeaufforderung eingeben |
| `failproofai jev setup --key-from-env` | Keinen Schlüssel speichern; `FAILPROOFAI_JEV_API_KEY` pro Sitzung lesen |
| `failproofai jev setup --mode observe` | Modus wechseln (`enforce`, `observe` oder `off`), gespeicherter Schlüssel bleibt erhalten |
| `failproofai jev setup --model <id>` / `--base-url <url>` | Modell oder API-Basis überschreiben; `default` hebt die Überschreibung auf |
| `failproofai jev setup --timeout-ms <n>` | Budget pro Aufruf ändern |
| `failproofai jev status [--json]` | Konfiguration, Berechtigungen und letzte Aktivität; niemals der Schlüssel |
| `failproofai jev test [--json]` | Eine Live-Anfrage: Latenz und die antwortende Version |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | Die Modell-IDs, die das `/models`-Verzeichnis des Endpunkts meldet, mit Markierung des konfigurierten |
| `failproofai jev remove` | Konfiguration löschen; Jev ist deaktiviert |
