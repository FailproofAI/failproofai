Dies ist die Provider- und Konfigurationsreferenz für [Jev-Richtlinien](/de/policies/jev) mit eigenem Schlüssel. Regex-Richtlinien prüfen Zeichenketten. Sie können nicht unterscheiden, ob `rm -rf build/` auf Ihre Anfrage zurückgeht oder ob `rm -rf ~` unbemerkt in einen Plan geschlüpft ist – sie blockieren an einer Stelle zu viel und an anderer zu wenig. **Jev**, der Klassifikator von TypeSafe, liest den Aufruf im Kontext Ihrer tatsächlichen Anfrage und beantwortet in einer schnellen Anfrage eine Reihe von Ja/Nein-Fragen dazu.

Mit konfiguriertem Jev-Endpunkt und eigenem Schlüssel fragt Failproof AI Jev zu jedem Werkzeugaufruf **zusätzlich** zu den Regex-Richtlinien – niemals anstelle von ihnen:

- Ein **harter** Richtlinien-Deny ist endgültig. Jev kann ihn nicht aufheben. Jede Richtlinie ist hart, sofern sie nicht ausdrücklich als prüfbar markiert ist und die Jev-Prüfungen benennt, die sie abdecken. Eine benutzerdefinierte, Pack- oder Cloud-Richtlinie ohne entsprechende Angaben ist daher hart, und der immer aktive Selbstschutz ist stets hart.
- Ein **prüfbarer** Richtlinien-Deny kann aufgehoben werden – jedoch nur, wenn Jev explizit zur betreffenden Sorge befragt wurde und mit „nichts gefunden" oder „der Benutzer hat das angefragt" geantwortet hat. Eine Prüfung, die die Sorge als real einstuft und die der Benutzer nicht angefordert hat, hält den Deny aufrecht – selbst wenn ihr eigenes Urteil nur eine Warnung ist, denn vor einem Werkzeugaufruf stoppt eine Warnung den Agenten nicht. Und wenn diese Prüfung eine ist, die einen Deny auslösen kann (Preisgabe von Geheimnissen, Exfiltration von Anmeldedaten, destruktives Löschen …), wird bei diesem Aufruf nichts aufgehoben.
- Ein Block kann dennoch zur **Warnung** werden, wenn der Aufruf ein Schritt der von Ihnen gestellten Aufgabe ist und nicht weiter reicht: Jev mildert seinen eigenen Deny zu einer Warnung ab, und diese Warnung – die benennt, was am Aufruf tatsächlich problematisch ist – ersetzt den Block der Richtlinie.
- Jev kann auch eigenständig warnen oder ablehnen, bei Schäden, die kein Regex beschreibt.
- Wenn Jev nicht antworten kann (Timeout, Rate-Limit, Serverfehler, kein Guthaben, unerwartete Modellversion), erhält dieser Aufruf das Regex-Ergebnis – genau wie ohne Jev.
- Jev macht einen Aufruf nie freizügiger als Ihre Richtlinien allein, es sei denn, es hat den gesamten Aufruf gelesen und wurde zur genauen Sorge befragt. Alles darunter – ein zu großer Aufruf, ein vermutetes Injection – zieht die Freigaben zurück und hält jeden Deny aufrecht.

<Note>
Ohne eine Jev-Konfiguration ändert sich nichts: Hooks führen die Regex-Richtlinien genau wie bisher aus. Die Konfiguration ist der vollständige Opt-in.
</Note>

<Tip>
Sie nutzen FailproofAI Cloud? Sie benötigen keinen eigenen Schlüssel: Eine Maschine, die mit einem Schlüssel mit `jev:evaluate` verbunden ist, kann Jev im Rahmen des Organisationsplans nutzen. Siehe [Jev über FailproofAI Cloud](/de/reference/jev-cloud).
</Tip>

## Voraussetzungen

Installieren Sie **failproofai 1.0.8-beta.0 oder neuer** und verbinden Sie dessen Hooks mit einem [unterstützten Harness](/de/reference/harnesses) auf der Maschine, auf der Ihr Agent läuft. Befolgen Sie die [Schnellstartanleitung](/de/start/quickstart) bei einer neuen Maschine oder richten Sie die [lokale Durchsetzung ein](/de/start/setup#enforce-locally), wenn Sie Cloud nicht verwenden. Prüfen Sie die installierte CLI mit `failproofai --version`.

Besorgen Sie sich einen API-Schlüssel von einem der unten aufgeführten Provider, oder halten Sie einen kompatiblen Endpunkt und dessen Schlüssel bereit. Jev prüft benannte Werkzeugaufrufe am `PreToolUse`- oder `PermissionRequest`-Gate. Es kann ein eigenes Urteil fällen, aber die Aufhebung eines bestehenden Richtlinien-Denys setzt außerdem eine installierte, als [prüfbar](/de/policies/authority) markierte Richtlinie voraus. Harte Richtlinien-Denys bleiben endgültig.

## Provider auswählen

Jev ist über fünf Wege erreichbar. Bringen Sie einen Schlüssel für einen davon mit.

| Provider | `--provider` | Endpunkt | Standardmodell | Hinweise |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Exakte Versionsangabe. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | Anfragen werden ausschließlich an Endpunkte ohne Datenspeicherung weitergeleitet, ohne Fallback auf einen anderen Provider. Meldet eine datierte Version wie `typesafe/jev-1.13-20260917`. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Benennt Jev nur per Alias, daher wird die antwortende Version als ungeprüft aufgezeichnet. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | Benötigt `--account-id`. Gemessen wurden etwa sechs Aufrufe pro Sekunde und Schlüssel vor HTTP 429. |
| Eigener Endpunkt | `custom` | `<base-url>/systemone` | `jev-1.13.0` | Jeder Endpunkt, der den TypeSafe-Request-Body akzeptiert und meldet, welches Modell geantwortet hat. Nur `https`; einfaches `http` zu einem Loopback-Host (`localhost`, `127.0.0.1`, `::1`) wird für lokale Tests akzeptiert. |

<Warning>
Bei Vercels eigenem Bring-your-own-key-Feature wird eine fehlgeschlagene Anfrage stillschweigend mit Vercels Zugangsdaten wiederholt. Wenn jeder Aufruf Ihrem eigenen TypeSafe-Konto zugerechnet und nur von diesem gesehen werden soll, verwenden Sie TypeSafe direkt.
</Warning>

## Einrichtung

Ein Befehl, der Endpunkt und der Schlüssel. Starten Sie im `observe`-Modus, um Jevs Urteile zu inspizieren, während die bestehenden Richtlinien weiterhin Aufrufe entscheiden:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### Die URL bestimmt den Provider

Sie müssen den Provider nicht explizit benennen: Der **Host** der URL entscheidet, welcher es ist.

| URL-Host | Provider | Zusätzlich benötigt |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| beliebiger anderer Host | `custom` | — die angegebene URL ist die Basis-URL |

Daraus folgen drei Dinge:

- **Eine URL, die der eigene API-Endpunkt des Providers ist, schreibt keine Überschreibung.** `--url https://api.typesafe.ai/v1` erzeugt exakt dieselbe Konfiguration wie `--provider typesafe`. Ein abweichender Pfad oder Host bei einem bekannten Provider wird als Basis-URL gespeichert, wie es `--base-url` tun würde.
- **`--provider` überschreibt trotzdem die Erkennung**, so lässt sich ein Proxy erreichen, der die API eines Providers unter eigenem Host spricht: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **Ein `--provider`, der dem Host widerspricht, wird abgelehnt** – ohne Rätselraten. `--provider openrouter --url https://api.typesafe.ai/v1` schreibt nichts und erklärt warum: Die beiden Angaben widersprechen sich darin, wohin Ihr Schlüssel gesendet werden soll. Dasselbe gilt für `jev setup --base-url` und die Jev-Einstellungen im Dashboard. (`--provider custom` ist kein Widerspruch – es bedeutet „behandle diese URL als sich selbst" – außer auf Cloudflares Host, dessen kontospezifischen Endpunkt eine Custom-Route nicht erreichen kann.)

`--url` wird genauso validiert wie `baseUrl` in der Konfigurationsdatei und mit denselben Worten abgelehnt: `https`, oder einfaches `http` zu einem Loopback-Host (`localhost`, `127.0.0.1`, `::1`) in jedem Modus. Risiko: Ein Loopback-Server wird nicht authentifiziert; solange er ausgefallen ist, könnte ein anderer lokaler Prozess seinen Port übernehmen und antworten. Verwenden Sie außerhalb lokaler Tests `https`.

### Der Schlüssel

Leiten Sie ihn mit `--key-stdin` ein, oder führen Sie den Befehl ohne diesen Parameter in einem Terminal aus und fügen Sie den Schlüssel an einer verdeckten Eingabeaufforderung ein. In beiden Fällen wird er direkt in die Konfigurationsdatei geschrieben und nie zurückgegeben.

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` akzeptiert dieselben Flags und ist die ausführliche Form für all das: `setup --provider <kind>`, wenn Sie den Provider lieber direkt benennen als die URL.

### `--token` und die Kosten

`--token <token>` übergibt den Schlüssel auf der Kommandozeile – das ist der schnellste Weg zur Maschinenkonfiguration und die einzige Schreibweise, die den Schlüssel außerhalb der Konfigurationsdatei hinterlässt:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
Ein Kommandozeilenargument landet anschließend in der Shell-Verlaufsdatei, und während der Befehl läuft, steht es in der Prozessliste – aus `/proc` von allem lesbar, das als Sie läuft. `setup` weist bei jeder Verwendung von `--token` darauf hin. Bevorzugen Sie `--key-stdin` auf einer gemeinsam genutzten Maschine, in aufgezeichneten Sitzungen oder überall dort, wo die Verlaufsdatei synchronisiert wird; rotieren Sie einen so übergebenen Schlüssel, wenn dies relevant ist.
</Warning>

`--token`, `--key-stdin` und `--key-from-env` schließen sich gegenseitig aus: Geben Sie genau eine Option an.

Senden Sie dann eine kleine Live-Anfrage, um den Schlüssel, den Endpunkt und die antwortende Jev-Version zu prüfen:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` beendet sich mit Exit-Code 1 und zeigt dies im Titel an, wenn die Antwort nach dem Timeout eintrifft (jeder Hook würde dann auf Regex zurückfallen, Ursache `timeout`) oder die Prüffrage falsch beantwortet.

Hooks lesen die Konfiguration bei jedem Werkzeugaufruf, daher gilt sie ab dem nächsten Aufruf. Es ist kein Neustart erforderlich, weder mit noch ohne den Daemon.

## Aktivität überwachen

```bash
failproofai jev status
failproofai jev status --json
```

`status` zeigt Provider, Endpunkt, Modell, Modus, Konfigurationsdatei und deren Berechtigungen – niemals den Schlüssel. Darunter fasst es die jüngste Aktivität zusammen: wie viele Aufrufe Jev ausgewertet hat, wie oft es auf Regex zurückgefallen ist und warum, die Latenz sowie welche prüfbaren Richtlinien es freigegeben hat.

## Einen echten Aufruf prüfen

Starten Sie eine neue Sitzung im Hook-gebundenen Agenten. Bitten Sie ihn, sein Dateilese-Werkzeug auf `README.md` anzuwenden und den Titel zu berichten. Vergewissern Sie sich, dass die Sitzung diesen Werkzeugaufruf enthält, und führen Sie dann erneut `failproofai jev status` aus: Die Anzahl der kürzlich ausgewerteten Aufrufe sollte gestiegen sein. Öffnen Sie **Richtlinien → Aktivität** im [lokalen Dashboard](/de/reference/local-dashboard#review-policy-activity), um das Jev-Urteil und den Modus des Aufrufs zu prüfen. Im Beobachtungsmodus entscheidet weiterhin das Richtlinienergebnis. Eine Freigabe erscheint nur, wenn eine prüfbare Richtlinie anschlug und Jev jede benannte Prüfung freigegeben hat; bei einem gewöhnlichen Lesevorgang gibt es möglicherweise keine Richtlinie zum Freigeben.

## Beobachtungsmodus

`enforce` ist der Standard. Um Jev zu beobachten, ohne Entscheidungen zu beeinflussen, wechseln Sie zu `observe`: Jev wird weiterhin befragt und seine Urteile aufgezeichnet, aber das Regex-Ergebnis wird durchgesetzt.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` behält die Konfiguration – Endpunkt und Schlüssel – und stellt die Jev-Anfragen ein: Hooks führen die Regex-Richtlinien genau wie ohne Konfiguration aus, und `failproofai jev status` meldet „off (switched off)". Wechseln Sie mit `--mode observe` oder `--mode enforce` zurück.

Ein erneutes Ausführen von `setup` für denselben Provider behält den gespeicherten Schlüssel, ein Moduswechsel erfordert also nur ein Flag. Der Wechsel des Providers beginnt von vorn und fordert den Schlüssel des neuen Providers an. Dasselbe gilt für eine `--base-url`, die Anfragen auf einen anderen Host verlagert: Ein gespeicherter Schlüssel wird nur an den Host gesendet, für den er eingegeben wurde, oder an die eigene API des Providers.

## Die Konfigurationsdatei

Alles liegt in einer Datei, `~/.failproofai/jev.json`, die von `setup` geschrieben wird:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Feld | Bedeutung |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` oder `custom` – oder `failproofai`, dessen Schlüssel aus der FailproofAI-Cloud-Verbindung statt aus dieser Datei stammt (siehe [Jev über FailproofAI Cloud](/de/reference/jev-cloud)). |
| `apiKey` | Wird als `Authorization: Bearer <key>` gesendet. |
| `baseUrl` | Für `custom` erforderlich; ersetzt andernfalls die API-Basis des Providers. Muss `https` sein. Einfaches `http` zu `localhost` wird nur mit `mode: observe` akzeptiert: Ein lokaler Port wird nicht authentifiziert, daher könnte jeder Prozess auf der Maschine – einschließlich des zu beurteilenden Agenten – bei Ausfall Ihres Proxys antworten. |
| `accountId` | Nur Cloudflare: 32 Kleinbuchstaben-Hexadezimalzeichen. |
| `model` | Ersetzt die Standard-Modell-ID des Providers. Eine versionierte ID muss Jev 1.13 benennen. Ein Wert in Form eines API-Schlüssels wird abgelehnt (und nicht zurückgegeben), damit ein versehentlich in `--model` eingefügter Schlüssel nie gespeichert oder als Modell gesendet wird. |
| `timeoutMs` | Wie lange ein Werkzeugaufruf auf Jev wartet, bevor das Regex-Ergebnis verwendet wird. 100–10000, Standard 3000. |
| `mode` | `enforce` (Standard), `observe` oder `off` (Konfiguration beibehalten, kein Jev ausführen). |

Drei Regeln schützen die Datei:

- **Nur für den Eigentümer.** Sie wird mit den Berechtigungen `0600` geschrieben. Eine Kopie, die ein anderer Benutzer oder eine Gruppe lesen oder schreiben kann, wird **abgelehnt**, und Hooks fallen auf Regex zurück, bis Sie `chmod 600 ~/.failproofai/jev.json` oder `setup` erneut ausführen. Das Verzeichnis wird ebenfalls geprüft: `~/.failproofai` darf von niemandem sonst **beschreibbar** sein, da wer dort schreiben kann, die Datei unabhängig von ihren eigenen Berechtigungen ersetzen kann. `setup` entfernt solche Schreibbits, wenn es sie vorfindet. `failproofai jev status` meldet, wenn eine Konfiguration abgelehnt wurde, und zeigt den in der Datei genannten Endpunkt: Jemand anderes könnte sie geändert haben, prüfen Sie also, ob sie Ihnen gehört, bevor Sie `chmod` ausführen. Ein erneutes Ausführen von `setup` für eine solche Datei überträgt den gespeicherten Schlüssel nur an die eigene API des Providers; jeder andere darin genannte Endpunkt benötigt den Schlüssel erneut (`--key-stdin`), oder `--base-url default`, um Anfragen zurück zum Provider zu leiten.
- **Nur global.** Ein Repository kann Jev nicht aktivieren, auf einen anderen Endpunkt verweisen oder sein Modell auswählen: Eine `.failproofai/jev.json` innerhalb eines Projekts wird ignoriert, und Provider, URL, Modell und Konto-ID werden nur aus dieser Datei gelesen – niemals aus der Umgebung, die die Agenteneinstellungen eines Repositorys setzen können. (`FAILPROOFAI_HOME` ist kein Umweg: Es verschiebt das gesamte failproofai-Verzeichnis einschließlich Ihrer Richtlinien, anstatt nur Jev umzuleiten.)
- **Nur der Schlüssel darf aus der Umgebung kommen.** Enthält die Datei kein `apiKey`, liefert `FAILPROOFAI_JEV_API_KEY` ihn für diese Sitzung (`setup --key-from-env` schreibt eine solche Datei). Er ersetzt nie einen in der Datei gespeicherten Schlüssel und kann Jev ohne die Datei nicht aktivieren. Ist die Variable nicht gesetzt, ist Jev für diese Shell schlicht deaktiviert: `failproofai jev status` meldet dies, beendet sich mit Exit-Code 0 und lässt die Konfiguration unberührt (`status --json` meldet `"status": "key-missing"` mit `"reason": "no-env-key"`). Der `failproofaid`-Daemon sieht Ihre Shell-Umgebung nicht; halten Sie den Schlüssel auf einer mit `failproofai config` eingerichteten Maschine daher in der Datei.

## Welches Jev antwortet

Die Entscheidungsschwellen von Failproof AI wurden auf Jev 1.13 kalibriert, daher wird eine Antwort nur verwendet, wenn sie aus dieser Familie stammt: `jev-1.13.x` oder OpenRouters `typesafe/jev-1.13-<date>`. Wenn ein Provider Jev nur per Alias benennt und keine Version meldet (Vercel und Cloudflare, wenn keine Angabe erfolgt), wird die Antwort verwendet und als ungeprüft aufgezeichnet. Ein `custom`-Endpunkt muss das antwortende Modell melden; die einzige Ausnahme ist ein unversionierter `--model`-Name, den Sie dafür konfiguriert haben und der – zurückgespiegelt – ebenfalls als ungeprüft aufgezeichnet wird. Eine Antwort, die eine andere Version meldet, oder eine `custom`-Antwort ohne Versionsangabe, wird nicht verwendet: Dieser Aufruf fällt mit dem Grund `model-mismatch` auf Regex zurück.

## Wenn Jev nicht antworten kann

Jeder dieser Fälle fällt für diesen Aufruf auf das Regex-Ergebnis zurück und wird mit seinem Grund aufgezeichnet, den `failproofai jev status` zusammenfasst:

| Grund | Ursache |
| --- | --- |
| `timeout` | Keine Antwort innerhalb von `timeoutMs`. |
| `http-429` | Der Provider hat den Schlüssel rate-limitiert. |
| `rate-limited` | Der eigene Begrenzer von Failproof AI hat den Aufruf zurückgehalten, bevor er gesendet wurde: 5 Anfragen pro Sekunde in Bursts von bis zu 5, und kurze Pause nach einer 429-Antwort des Providers. Nicht der Provider. |
| `http-500`, `http-502`, `http-503`, … | Ein Serverfehler beim Provider. Der genaue Status wird aufgezeichnet. |
| `out-of-credits` | HTTP 402: Das Provider-Konto hat kein Guthaben mehr. |
| `provider-refused` | HTTP 402 von Cloudflare mit „Model execution failed (Payment error)": Der Provider hat die Ausführung des Modells für diese Anfrage verweigert. In der Regel kein Abrechnungsproblem, Aufladen hilft daher nicht weiter. |
| `http-401`, `http-403` | Der Schlüssel wurde abgelehnt. |
| `http-404` | Unter `<base>/systemone` wird nichts bereitgestellt, die Basis-URL ist also falsch – `/systemone` wird daran angehängt, und jeder Provider stellt es am Versionsstamm bereit. `failproofai jev models` zeigt, was der Endpunkt tatsächlich bereitstellt. |
| `network` | Der Endpunkt war nicht erreichbar. |
| `http-301`, `http-302`, `http-307`, `http-308` | Der Endpunkt antwortete mit einer Weiterleitung. Weiterleitungen werden nie gefolgt, die Antwort kommt also immer nur von der URL in Ihrer Konfiguration; setzen Sie `--base-url` auf die endgültige URL. |
| `malformed` | Der Endpunkt antwortete, aber nicht mit einer Jev-Antwort – ein Body, der kein JSON ist oder keine Antworten enthält. |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflares Envelope meldete einen Fehler oder einen nicht abgeschlossenen Job. |
| `model-mismatch` | Eine andere Jev-Version als 1.13 antwortete, oder ein `custom`-Endpunkt meldete nicht, welches Modell antwortete. |
| `request-cut` | **Kein Ausfall.** Jev hat geantwortet; es sah nur einen Teil des Aufrufs, daher hat seine Antwort nichts freigegeben. Siehe [Wenn Jev geantwortet hat, aber nicht auf den gesamten Aufruf](#wenn-jev-geantwortet-hat-aber-nicht-auf-den-gesamten-aufruf). |

`failproofai jev status` kann auch einige seltenere Gründe anzeigen, wie `upstream-error` (die Antwort enthielt den eigenen Fehler des Providers) oder `config`, und fasst jeden nicht namentlich bekannten Grund als `other` zusammen.

`request-cut` steht in dieser Tabelle, weil `failproofai jev status` ihn mit den übrigen zusammenzählt und weil auch er jeden Deny bestehen lässt. Es ist der einzige Grund hier, der nichts über Ihren Provider aussagt: Die Anfrage kam an und Jev hat geantwortet. Anders als alle Zeilen darüber zählt diese Antwort trotzdem – Jevs eigener Deny oder seine Warnung gelten zusätzlich zum Regex-Ergebnis, statt verworfen zu werden. Eine Serie davon bedeutet also, dass Aufrufe den Auswerter zu groß für eine vollständige Übertragung erreichen – nicht, dass Ihr Endpunkt gestört ist. Guthaben aufzuladen oder die URL zu ändern wird daran nichts ändern.

## Wenn Jev geantwortet hat, aber nicht auf den gesamten Aufruf

Zwei weitere Dinge können passieren, und keines davon bedeutet, dass Jev nicht antworten konnte. Beide betreffen den Umfang des Aufrufs oder des Gesprächs, der in eine Anfrage passte.

**Ein Teil des Aufrufs selbst hat nicht gepasst.** Ein Werkzeugaufruf wird innerhalb eines festen Budgets gesendet, und ein überdimensionierter – ein sehr großes `Write`, ein riesiger MCP-Body, ein Befehl, der bis zur Obergrenze aufgefüllt wurde – wird mit dem gesendet, was gepasst hat. Jev antwortet trotzdem, und seine Antwort gilt: Sein eigener Deny oder seine Warnung werden wie gewohnt angewendet. Was es nicht kann, ist etwas **freizugeben**, denn ein Urteil über einen Teil eines Aufrufs ist kein Urteil über den Aufruf. Daher bleibt jeder Richtlinien-Deny bestehen, und der Aufruf wird als Fallback mit dem Grund `request-cut` aufgezeichnet, den `failproofai jev status` neben den obigen Gründen zusammenzählt. Die Regel, die sich daraus ergibt: Einen Aufruf größer zu machen kann seine Freigaben kosten, aber nie eine erkaufen.

**Eine Nachricht hat nicht gepasst.** Eine lange eingefügte Eingabeaufforderung, die letzte Nachricht des Agenten oder eine Eingabeaufforderung, die der eigene Speicher dieses Auswerters bereits gekürzt hatte. **Es ändert sich nichts**: Der Aufruf wird genauso beurteilt, freigegeben und aufgezeichnet wie jeder andere und nicht als Fallback gezählt. Die Länge Ihrer Eingabe entscheidet nie über ein Urteil, und eine Kürzung kann keine Zustimmung herstellen: Wenn eine Eingabeaufforderung bereits gekürzt ankam, lässt sich „Sie haben das nicht angefragt" daraus überhaupt nicht mehr schlussfolgern, statt zur Schlussfolgerung zu werden.

Die Grenze zwischen beidem liegt darin, wer den Text verfasst hat. Der Aufruf gehört dem Agenten, und eine Regel, die seine Länge den Schweregrad verringern ließ, wäre eine Regel, die der Agent ausnutzen könnte; Ihre Eingabeaufforderung gehört Ihnen, und ihre Länge als Signal zu behandeln würde nur das Einfügen einer Spezifikation oder eines Stack-Traces bestrafen.

## Was die Maschine verlässt

Für jeden Werkzeugaufruf, den Jev auswertet, geht eine Anfrage an Ihren Provider, die Folgendes enthält:

- den Werkzeugaufruf selbst, mit redigierten Geheimnissen wie API-Schlüsseln, Bearer-Tokens und `KEY=`-Zuweisungen;
- die kürzlichen von Ihnen eingegebenen Eingabeaufforderungen, bereinigt um Text, den das Harness Ihres Agenten hinzugefügt hat;
- die letzte Nachricht des Agenten vor Ihrer neuesten Eingabeaufforderung, als agentengeschrieben gekennzeichnet;
- lokal berechnete Fakten, z. B. ob ein Pfad innerhalb des Projekts liegt – desjenigen, in dem die Sitzung beim ersten geprüften Aufruf war, [für die Sitzung fixiert](/de/reference/jev-intent#the-project-root) – und den aktuellen Git-Branch.

Sie geht nur an den Endpunkt in Ihrer Konfiguration, unter Ihrem Schlüssel.

## Deaktivierung

```bash
failproofai jev remove
```

Dies löscht `~/.failproofai/jev.json`. Ab dem nächsten Werkzeugaufruf führen Hooks die Regex-Richtlinien genau wie zuvor aus. Die sitzungsbezogenen Speicher unter `~/.failproofai/state/semantic/` (aufgezeichnete Eingabeaufforderungen in `sessions/`, Projektstammpfade in `roots/`) bleiben erhalten und laufen ab. Um Jev-Anfragen zu stoppen, aber die Konfiguration zu behalten, verwenden Sie stattdessen `failproofai jev setup --mode off`.

## Befehlsreferenz

| Befehl | Ergebnis |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | In einem Befehl konfigurieren; der Provider ergibt sich aus dem Host der URL |
| `failproofai jev --url <url> --token <token>` | Dasselbe, mit dem Schlüssel auf der Kommandozeile – Shell-Verlauf und Prozessliste sehen ihn |
| `failproofai jev setup --provider <kind> --key-stdin` | Konfiguration aus einem per stdin eingeleiteten Schlüssel schreiben |
| `failproofai jev setup --provider <kind>` | Dasselbe, Schlüsseleingabe an verdeckter Eingabeaufforderung |
| `failproofai jev setup --key-from-env` | Keinen Schlüssel speichern; `FAILPROOFAI_JEV_API_KEY` pro Sitzung lesen |
| `failproofai jev setup --mode observe` | Modus wechseln (`enforce`, `observe` oder `off`), gespeicherter Schlüssel bleibt erhalten |
| `failproofai jev setup --model <id>` / `--base-url <url>` | Modell oder API-Basis überschreiben; `default` hebt die Überschreibung auf |
| `failproofai jev setup --timeout-ms <n>` | Budget pro Aufruf ändern |
| `failproofai jev status [--json]` | Konfiguration, Berechtigungen und jüngste Aktivität; niemals der Schlüssel |
| `failproofai jev test [--json]` | Eine Live-Anfrage: Latenz und die antwortende Version |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | Die Modell-IDs, die `/models` des Endpunkts meldet, mit Markierung der konfigurierten |
| `failproofai jev remove` | Konfiguration löschen; Jev ist deaktiviert |
