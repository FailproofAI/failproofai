`failproofai otel` konfiguriert die optionale OpenTelemetry-Berichterstattung an FailproofAI Cloud. Verbinde zunächst deinen Rechner mit `failproofai config` und bitte einen Organisations-Admin, **Settings → OpenTelemetry** zu aktivieren.

Die interaktive Einrichtung fragt nach dem Cloud-Schlüsselfeld und der Agent-Auswahl nach OpenTelemetry. Dieser optionale Schritt ist standardmäßig auf „Nein" gesetzt. Wähle „Ja", um OTEL-Agents auszuwählen; derselbe Aktivierungscode wird nach dem Speichern der Verbindung ausgeführt. Ein Abbruch mit Esc vor der Einrichtung ändert nichts. Unbeaufsichtigte Einrichtung, ein angegebener Schlüssel, der Open-Source-Modus sowie das Beibehalten einer gespeicherten Verbindung aktivieren OTEL nicht automatisch.

## Einen Agent aktivieren

```bash
failproofai otel enable claude
failproofai otel enable codex --local
failproofai otel enable codex --no-content
failproofai otel enable copilot
failproofai otel enable all --yes
```

Die unterstützten Agents sind `claude`, `codex` und `copilot` (VS Code). Für die Copilot-Einrichtung ist eine VS-Code-Programmdatei oder eine installierte Copilot-Erweiterung erforderlich. Ein verwaistes Einstellungsverzeichnis allein reicht nicht aus; die Einrichtung überspringt Copilot, wenn keines von beidem gefunden wird.

`--local` sendet an das lokale Relay statt direkt an Cloud. Copilot nutzt das Relay automatisch, da seine Einstellungen den Authentifizierungs-Header nicht speichern können.

Das Relay lauscht ausschließlich auf deinem Rechner. Dein konfigurierter FailproofAI-Daemon übernimmt die Änderung innerhalb von Sekunden; ein Neustart ist nicht erforderlich. Belegt eine andere Anwendung den Relay-Port, meldet der Status ihn als inaktiv, während der Daemon weiterläuft.

<Warning>
Die Texterfassung ist standardmäßig aktiviert. Füge `--no-content` hinzu, um Prompts und Tool-Details wegzulassen. Verschiedene Agent-Versionen können unterschiedliche Inhaltskontrollen bereitstellen; prüfe, was dein Agent exportiert, bevor du ihn mit sensiblen Daten verwendest.
</Warning>

Codex exportiert ausschließlich Konversationsprotokolle, keine internen Laufzeit-Traces oder Metriken. Ein explizit gesetztes `log_user_prompt = false` in deiner Codex-Konfiguration bleibt deaktiviert; bei der Aktivierung wird ein Hinweis ausgegeben, wenn diese Einstellung beibehalten wird.

### Einen Übertragungsweg wählen

Ist die Transkript-Berichterstattung für einen Agent aktiv, stellt die Einrichtung folgende Frage:

> failproofai already sends Claude Code sessions to Cloud. Send them with OTEL instead? Transcript upload for Claude Code stops.

Der Standardwert ist „Nein". `--yes` bestätigt den Wechsel ohne Nachfrage. Andere Agents und die Richtliniendurchsetzung sind davon nicht betroffen.

Die Codex-Einrichtung wartet auf die Bestätigung der Collector-Änderung durch den Daemon, bevor die Exporter-Einstellungen geschrieben werden. Läuft die Bestätigung ab, warnt die Einrichtung davor, Codex sofort zu starten.

Config v2 speichert die Tracing-Liste unter `agents.selected` (und den Erkennungsverlauf unter `agents.seen`). Die agentbezogene Transkript-Einstellung verbleibt unter `collector.agents.<agent>.sessions`, der OTEL-Besitz unter `otel.agents` und die Relay-Einstellungen unter `collector.otlp.enabled` / `collector.otlp.port`. Diese getrennten Schlüssel stellen sicher, dass ältere OTEL-Konfigurationen lesbar bleiben: Die Einrichtung kann die Tracing-Liste ändern, ohne die Transportpräferenz oder den für die Wiederherstellung der Agent-Einstellungen benötigten Zustand zu verlieren.

## Einrichtung prüfen

```bash
failproofai otel status
```

Der Status zeigt für jeden Agent: ob seine Einstellungen von FailproofAI verwaltet werden, das Ziel, den Organisations-Ingest-Schalter, den Relay-Zustand und das letzte Relay-Upload-Ergebnis.

`unknown` beim Organisations-Schalter bedeutet, dass der Server diesen Wert nicht geliefert hat oder nicht erreichbar war. Dies ist kein Fehler und verhindert keine Konfiguration bei einer älteren Cloud-Version.

Unterstützt Cloud OTEL noch nicht, behält das Relay abgelehnte Exporte anstatt sie zu verwerfen. Ist der Organisations-Ingest deaktiviert, schreibt `enable` nichts und beendet sich mit einem Fehler; bitte einen Admin, diesen zunächst zu aktivieren.

## Konfiguration für eine Anwendung ausgeben

```bash
failproofai otel env --service my-agent
failproofai otel env --service my-agent --local
```

Die Ausgabe ist ein Shell-Umgebungsblock für einen OTLP/HTTP-Exporter. Die Cloud-Ausgabe setzt `OTEL_EXPORTER_OTLP_ENDPOINT` auf den OTLP-Basispfad von Cloud, `https://<cloud>/otel`, und der Exporter hängt `/v1/<signal>` an; eine signalspezifische Variable wie `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` benötigt die vollständige URL `https://<cloud>/otel/v1/logs`. Die lokale Ausgabe verweist auf das Relay, `http://127.0.0.1:<port>`. Die Cloud-Ausgabe enthält den konfigurierten API-Schlüssel; behandle ihn als Geheimnis. Die lokale Ausgabe enthält den Schlüssel nicht. Um die lokale Ausgabe zu verwenden, aktiviere zunächst einen lokalen Agent, damit das Relay läuft.

## Frühere Einstellungen wiederherstellen

```bash
failproofai otel disable claude
failproofai otel disable all
```

Disable stellt ausschließlich die von FailproofAI geschriebenen Einstellungen wieder her, behält nicht verwandte Änderungen bei und stellt für jeden Agent die vorherige Transkript-Berichterstattungs-Einstellung wieder her. Wird der letzte verwaltete lokale Agent deaktiviert, nimmt das Relay keine Exporte mehr an.

Für Codex schreibt disable zusätzlich `collector.agents.codex.sessions_resume_after` (Epoch-Millisekunden). Vorhandene Rollout-Bytes gelten als zugestellt, sodass mit OTEL erfasste Sessions nicht erneut hochgeladen werden; spätere Ergänzungen fließen weiterhin über die Transkript-Berichterstattung.

Jeder Befehl unterstützt `--help`. Siehe [OpenTelemetry in Cloud](/de/agenteye/opentelemetry) für Beispiele zu Anwendungen und Coding-Agents.
