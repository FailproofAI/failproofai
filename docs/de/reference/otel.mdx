`failproofai otel` konfiguriert optionales OpenTelemetry-Reporting an FailproofAI Cloud. Verbinde deine Maschine zunächst mit `failproofai config`. Die OpenTelemetry-Verarbeitung ist in Cloud immer aktiv – es gibt keinen organisationsweiten Schalter zum Einschalten.

Das interaktive Setup fragt nach OpenTelemetry, nachdem der Cloud-Schlüssel und die Agent-Auswahl abgeschlossen sind. Dieser optionale Schritt ist standardmäßig auf „Nein" gesetzt. Wähle „Ja", um OTEL-Agents auszuwählen; danach läuft derselbe Aktivierungscode wie nach dem Verbindungsaufbau. Wenn du vor dem Setup Esc drückst, werden keine Änderungen übernommen. Unbeaufsichtigtes Setup, ein mitgelieferter Schlüssel, der Open-Source-Modus sowie das Beibehalten einer gespeicherten Verbindung aktivieren OTEL nicht automatisch.

## Einen Agent aktivieren

```bash
failproofai otel enable claude
failproofai otel enable codex --local
failproofai otel enable codex --no-content
failproofai otel enable copilot
failproofai otel enable all --yes
```

Die unterstützten Agents sind `claude`, `codex` und `copilot` (VS Code). Für das Copilot-Setup wird eine VS Code-Executable oder eine installierte Copilot-Erweiterung benötigt. Ein verwaistes Einstellungsverzeichnis allein genügt nicht; das Setup überspringt Copilot, wenn keines von beidem vorhanden ist.

`--local` sendet Daten an den lokalen Relay statt direkt an Cloud. Copilot verwendet den Relay automatisch, da seine Einstellungen den Authentifizierungs-Header nicht speichern können.

Der Relay lauscht ausschließlich auf deiner Maschine. Dein konfigurierter FailproofAI-Daemon übernimmt die Änderung innerhalb von Sekunden – ein Neustart ist nicht erforderlich. Wenn eine andere Anwendung den Relay-Port belegt, zeigt der Status „off" an, und der Daemon läuft weiter.

<Warning>
Texterfassung ist standardmäßig aktiviert. Füge `--no-content` hinzu, um Prompts und Tool-Details wegzulassen. Agent-Versionen können unterschiedliche Inhaltskontrollen bereitstellen; prüfe, was dein Agent exportiert, bevor du ihn mit sensiblen Daten verwendest.
</Warning>

Codex exportiert ausschließlich Konversationsprotokolle – keine internen Laufzeit-Traces oder Metriken. Ein explizites `log_user_prompt = false` in deiner Codex-Konfiguration bleibt deaktiviert; beim Aktivieren erscheint ein Hinweis, wenn diese Einstellung beibehalten wird.

### Einen Übertragungsweg wählen

Wenn das Transcript-Reporting für einen Agent aktiv ist, fragt das Setup:

> failproofai sendet Claude Code-Sitzungen bereits an Cloud. Stattdessen per OTEL senden? Der Transcript-Upload für Claude Code wird deaktiviert.

Der Standardwert ist „Nein". `--yes` akzeptiert den Wechsel ohne Rückfrage. Andere Agents und die Policy-Durchsetzung sind davon nicht betroffen.

Das Codex-Setup wartet, bis der Daemon die Collector-Änderung bestätigt, bevor die Exporter-Einstellungen geschrieben werden. Wenn die Bestätigung das Timeout überschreitet, warnt das Setup davor, Codex erst nach einer kurzen Wartezeit zu starten.

Config v2 speichert die Tracing-Liste unter `agents.selected` (und den Erkennungsverlauf unter `agents.seen`). Die agent-spezifische Transcript-Einstellung verbleibt unter `collector.agents.<agent>.sessions`, der OTEL-Besitz unter `otel.agents` und die Relay-Einstellungen unter `collector.otlp.enabled` / `collector.otlp.port`. Diese getrennten Schlüssel stellen sicher, dass alte OTEL-Konfigurationen weiterhin lesbar sind: Das Setup kann die Tracing-Liste ändern, ohne die Transporteinstellung oder den für die Wiederherstellung der Agent-Einstellungen benötigten Zustand zu verlieren.

## Setup prüfen

```bash
failproofai otel status
```

Der Status zeigt für jeden Agent: ob seine Einstellungen von FailproofAI verwaltet werden, das Ziel, den organisations­weiten Ingest-Schalter, den Relay-Zustand und das letzte Relay-Upload-Ergebnis.

`unknown` beim Organisations-Schalter bedeutet, dass der Server keinen Wert geliefert hat oder nicht erreichbar war. Das ist kein Fehler und verhindert keine Konfiguration bei einer älteren Cloud-Version.

Wenn Cloud OTEL noch nicht unterstützt, behält der Relay abgelehnte Exports, anstatt sie zu verwerfen. Wenn eine ältere Cloud-Version den organisations­weiten Ingest als deaktiviert meldet, schreibt `enable` nichts und beendet sich mit einem Fehler.

## Konfiguration für eine Anwendung ausgeben

```bash
failproofai otel env --service my-agent
failproofai otel env --service my-agent --local
```

Die Ausgabe ist ein Shell-Umgebungsblock für einen OTLP/HTTP-Exporter. Die Cloud-Ausgabe setzt `OTEL_EXPORTER_OTLP_ENDPOINT` auf den OTLP-Basispfad von Cloud, `https://<cloud>/otel`; der Exporter hängt `/v1/<signal>` an. Eine signal­spezifische Variable wie `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` benötigt die vollständige URL `https://<cloud>/otel/v1/logs`. Die lokale Ausgabe zeigt auf den Relay: `http://127.0.0.1:<port>`. Die Cloud-Ausgabe enthält den konfigurierten API-Schlüssel – behandle ihn als Geheimnis. Die lokale Ausgabe lässt den Schlüssel weg. Um die lokale Ausgabe zu nutzen, aktiviere zuerst einen lokalen Agent, damit der Relay läuft.

## Frühere Einstellungen wiederherstellen

```bash
failproofai otel disable claude
failproofai otel disable all
```

Disable stellt nur die von FailproofAI geschriebenen Einstellungen wieder her, behält unabhängige Änderungen und stellt die vorherige Transcript-Reporting-Einstellung jedes Agents wieder her. Wenn der letzte verwaltete lokale Agent deaktiviert wird, stellt der Relay keine Exports mehr zu.

Für Codex schreibt disable zusätzlich `collector.agents.codex.sessions_resume_after` (Epoch-Millisekunden). Vorhandene Rollout-Bytes werden als zugestellt markiert, sodass mit OTEL erfasste Sitzungen nicht erneut hochgeladen werden. Spätere Anhänge fließen weiterhin über das Transcript-Reporting.

Jeder Befehl unterstützt `--help`. Weitere Informationen und Beispiele für Anwendungen und Coding-Agents findest du unter [OpenTelemetry in Cloud](/de/agenteye/opentelemetry).
