Instrumentiere Traces eines benutzerdefinierten Agenten mit `failproofai-sdk`, damit Failproof AI jede Ausführung rekonstruieren, das Verhalten prüfen und belegbare Fehler finden kann. Das SDK schreibt strukturierte Events, die der Failproof-Daemon an Cloud übermittelt. Es setzt Python 3.10 oder neuer voraus.

Tracing macht benutzerdefinierte Agenten beobachtbar und auditierbar. Um eine unsichere Aktion vor ihrer Ausführung zu verhindern, ist zusätzlich ein Enforcement-Hook in deiner Runtime erforderlich.

<Info>
  Um Richtlinien in einer benutzerdefinierten Agenten-Umgebung durchzusetzen, [kontaktiere Failproof AI](mailto:support@befailproof.ai). Wir helfen dabei, die Modell-, Tool- und Lifecycle-Grenzen deiner Runtime auf Policy-Hooks abzubilden.
</Info>

## `failproofai-sdk` installieren

Das SDK wird derzeit als privates Wheel ausgeliefert. Wende dich an deine Failproof AI-Kontaktperson für die aktuelle Version und den Download-Zugang.

```bash
VERSION=<sdk-version>
pip install "./failproofai_sdk-${VERSION}-py3-none-any.whl"
python -c "import failproofai; print(failproofai.__version__)"
```

Mit `uv` lädst du das Wheel zunächst herunter und führst dann `uv add ./failproofai_sdk-${VERSION}-py3-none-any.whl` aus. Verankere das Wheel in einem privaten Artefakt-Repository oder einem Dependency-Lock.

Das Paket wird als `failproofai-sdk` installiert und in Python als `failproofai` importiert.

## Eine vollständige Ausführung instrumentieren

Rufe `configure()` einmalig beim Prozessstart auf. Jeder Event-Aufruf verwendet ausschließlich Keyword-Argumente und erfordert eine stabile `session_id` sowie eine `agent_id`.

```python
import traceback
import uuid

import failproofai

failproofai.configure(environment="production")

session_id = uuid.uuid4().hex
agent_id = "checkout-agent"

failproofai.event.agent_start(
    session_id=session_id,
    agent_id=agent_id,
    goal="Resolve a failed checkout",
)

try:
    tool_call_id = uuid.uuid4().hex
    failproofai.event.tool_use(
        session_id=session_id,
        agent_id=agent_id,
        tool_name="lookup_order",
        tool_call_id=tool_call_id,
        input={"order_id": "ord_8421"},
    )
    result = {"status": "payment_failed"}
    failproofai.event.tool_result(
        session_id=session_id,
        agent_id=agent_id,
        tool_name="lookup_order",
        tool_call_id=tool_call_id,
        output=result,
    )
except Exception as exc:
    failproofai.event.error(
        session_id=session_id,
        agent_id=agent_id,
        error_type=type(exc).__name__,
        message=str(exc),
        traceback=traceback.format_exc(),
    )
    failproofai.event.agent_end(
        session_id=session_id,
        agent_id=agent_id,
        outcome="failed",
    )
    raise
else:
    failproofai.event.agent_end(
        session_id=session_id,
        agent_id=agent_id,
        outcome="success",
        summary="Escalated the failed payment",
    )
```

Emittiere `agent_start` einmal pro Akteur. Für Sub-Agenten wird die `session_id` des übergeordneten Agenten wiederverwendet, jeder Akteur erhält eine eindeutige `agent_id`, und `parent_id` wird auf die **agent ID** des übergeordneten Agenten gesetzt – nicht auf die Session-ID.

## Konfigurationsreferenz

```python
failproofai.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| Einstellung | Verhalten |
| --- | --- |
| `base_dir` | Explizites Spool-Verzeichnis. Hat Vorrang vor allen Umgebungsvariablen. |
| `flush_interval` | Sekunden zwischen Hintergrund-Schreibvorgängen von Speicher nach JSONL. Standard: `0.5`. |
| `environment` | Deployment-Label für jeden Event. Standardwert: `dev`. |
| `FAILPROOFAI_HOME` | Ändert das Failproof AI-Stammverzeichnis, das das `custom-agents`-Spool enthält. |

Das SDK schreibt in das explizit angegebene `base_dir`, sofern gesetzt. Andernfalls verwendet es das `custom-agents`-Spool des Failproof-Daemons unter `FAILPROOFAI_HOME` oder `~/.failproofai`.

Das SDK reiht Aufrufe im Speicher ein und schreibt Batches in einem Hintergrund-Thread. Außerdem wird beim Beenden des Prozesses ein abschließender Flush über Pythons `atexit`-Mechanismus versucht. Für kurzlebige Worker sollte der normale Interpreter-Shutdown abgewartet werden; ein erzwungener Prozessabbruch kann Events verlieren, die sich noch im Speicher befinden.

## Event-Katalog

Alle Methoden geben `None` zurück. Felder, die als `None` belassen werden, werden ausgelassen statt als JSON `null` geschrieben.

| Methode | Pflichtfelder (zusätzlich zu Identitätsfeldern) | Optionale Felder |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

Verwende `outcome="failed"`, `"error"`, `"timeout"` oder `"rejected"`, wenn eine Ausführung als Fehler gewertet werden soll. Andere Werte, einschließlich `"failure"`, werden vom aktuellen Backend nicht als Fehler klassifiziert.

## Korrelations- und Dauerregeln

- Dieselbe `tool_call_id`, `hook_id`, `pause_id` oder `input_id` für das zugehörige Abschluss-Event wiederverwenden.
- Das SDK berechnet `duration_ms` für `tool_result`, `hook_completed`, `agent_resume` und `human_input`. Wird dieser Wert manuell an diese Methoden übergeben, wird ein `ValueError` ausgelöst.
- Tool- und Hook-IDs teilen sich eine prozessweit gültige Pending-Map. Sie müssen global eindeutig sein – über gleichzeitige Sessions hinweg und über beide Namespaces hinweg; Provider-IDs oder UUIDs sind am sichersten.
- Ein über Prozesse aufgeteiltes Paar korreliert nachgelagert trotzdem, aber das SDK kann seine prozessinterne Dauer nicht berechnen.
- Die Pending-Map hält maximal 10.000 Starts vor und entfernt den ältesten Eintrag, wenn sie voll ist.

## Benutzerdefinierte Felder und Payloads

Jedes Event akzeptiert zusätzliche Keyword-Felder. Für Felder, die in nachgelagerten Abfragen strukturiert auswertbar sein sollen, JSON-kompatible Werte verwenden. Nicht unterstützte Typen wie UUIDs, Datetimes, Decimals, Sets, Bytes und Model-Objekte werden vom Writer in Strings umgewandelt.

Reservierte benutzerdefinierte Namen sind `timestamp`, `session_id`, `agent_id`, `type` und `environment`. Tippfehler in optionalen Feldern werden als neue benutzerdefinierte Felder akzeptiert; daher sollte der emittierte JSON überprüft werden, wenn ein Standardfeld in Cloud nicht erscheint.

## Zustellung und Überprüfung

<Tabs>
  <Tab title="Dashboard">
    Prüfe unter **Observe → Events**, ob `agent_start` als erstes und `agent_end` als letztes Event vorhanden ist. Öffne anschließend **Observe → Sessions** und überprüfe, ob Modell-, Tool-, Human-, Hook- und Error-Events in der erwarteten Reihenfolge erscheinen. Verwende die Session-ID als primären Troubleshooting-Schlüssel.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

Wenn Cloud leer ist, prüfe `$FAILPROOFAI_HOME/custom-agents/events`, andernfalls `~/.failproofai/custom-agents/events`. JSONL-Dateien belegen, dass das SDK Events emittiert; ein wachsendes Spool deutet auf ein Problem mit der Daemon-Konfiguration oder der Zustellung hin, während ein leeres Spool auf ein Instrumentierungs- oder Prozesslebensdauer-Problem hindeutet.

## Fehler in einer benutzerdefinierten Runtime verhindern

Nutze Audit-Befunde und verknüpfte Traces, um die unsichere Aktion, die erforderlichen Belege und die beabsichtigte Reaktion zu definieren. Eine benutzerdefinierte Enforcement-Integration muss die Aktion vor der Ausführung offenlegen, ihre strukturierten Eingaben an die Policy-Engine übergeben und die resultierende allow-, instruct- oder deny-Entscheidung anwenden.

Schreibe an [support@befailproof.ai](mailto:support@befailproof.ai), um diese Integration für deine Runtime zu entwerfen und zu validieren.
