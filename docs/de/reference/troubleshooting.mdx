---
title: "Fehlerbehebung"
description: "Diagnose fehlender Sitzungen, fehlender Richtlinien, fehlgeschlagener Übermittlung und blockierter Agentenaktionen."
icon: "wrench"
---

Vorübergehende Netzwerkausfälle sowie HTTP-Antworten 408, 429 oder 5xx lassen Telemetriedaten
für den automatischen Wiederholungsversuch in der Warteschlange, auch nach längeren Ausfällen. Der Daemon bewahrt den
Batch, bis die Zustellung bestätigt wurde. Eine `event_too_large`-Ablehnung erfordert vor dem erneuten Versuch eine kleinere Ereignis-Payload. Dateien, die bereits als `.poison` markiert sind, müssen manuell wiederhergestellt werden; ein Update sendet sie nicht automatisch erneut.

<AccordionGroup>
  <Accordion title="In der Cloud erscheinen keine Sitzungen">
    <Tabs>
      <Tab title="Dashboard">
        Öffnen Sie **Administration → Schlüssel** und bestätigen Sie, dass der Maschinenschlüssel aktiv ist und `events:add` besitzt. Öffnen Sie dann **Beobachten → Ereignisse**, erweitern Sie den Zeitraum und löschen Sie Umgebungs- und Agentenfilter. Falls Ereignisse vorhanden sind, suchen Sie nach der Sitzungs-ID und prüfen Sie dann **Beobachten → Sitzungen** für die Gruppierung. Falls keine Ereignisse vorhanden sind, diagnostizieren Sie den Failproof-Daemon über die CLI.

        ![Der Live-Ereignisstream mit seinen primären Filtern und eingehenden Agentenereignissen.](/images/dashboard/events-stream-current.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait --timeout 60
        fp list envs
        fp events --since 24h --limit 20
        fp sessions --since 24h --limit 20
        ```

        Bestätigen Sie, dass die Erfassung aktiviert ist, der konfigurierte Schlüssel `events:add` besitzt und der Dashboard-Filter mit der ausgegebenen Umgebung übereinstimmt.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Python-SDK-Ereignisse verbleiben auf dem Datenträger">
    <Tabs>
      <Tab title="Dashboard">
        Löschen Sie Filter unter **Beobachten → Ereignisse** und suchen Sie nach der genauen SDK-Sitzungs-ID. Falls nichts angezeigt wird, prüfen Sie den SDK-Spool und den Failproof-Daemon auf dem Quellrechner.
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait
        ```

        Bestätigen Sie, dass ein Daemon läuft und verbunden ist – das SDK schreibt in den Spool, unabhängig davon ob einer läuft oder nicht. Das Spool-Verzeichnis muss **nicht** vorab existieren (der Writer erstellt es), und keine Umgebungsvariable wählt es aus: `$FAILPROOFAI_HOME/custom-agents`, ansonsten `~/.failproofai/custom-agents`, ist das einzige Stammverzeichnis, und `configure(base_dir=...)` ist die einzige Überschreibungsmöglichkeit. Falls der Prozess per `SIGKILL` oder OOM-Kill beendet wurde, ging alles verloren, was noch in der Warteschlange war – behandeln Sie `SIGTERM`, um das zu begrenzen.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Der Rechner erhält keine Richtlinien">
    <Tabs>
      <Tab title="Dashboard">
        Öffnen Sie **Admin → Durchsetzung**, wählen Sie den Rechner aus und vergleichen Sie seine zugewiesenen, gemeldeten und vorherigen Versionen. Bestätigen Sie, dass der Deployment-Scope den Rechner einschließt und sein Schlüssel `policies:pull` besitzt. Die Ereignisaufnahme kann funktionieren, auch wenn die Richtlinienübermittlung es nicht tut.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config --status
        ```

        Bestätigen Sie, dass die Maschinen-ID und das Label mit dem Dashboard-Ziel übereinstimmen. Verbinden Sie sich erneut mit einem richtlinienfähigen Schlüssel, wenn die vorhandenen Zugangsdaten nur die Ereignisaufnahme erlauben.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Eine selbst gehostete Cloud mit privater Zertifizierungsstelle erhält keine Ereignisse oder Richtlinien">
    <Tabs>
      <Tab title="Dashboard">
        Der Rechner hat sich verbunden und seine Hooks funktionieren, aber **Beobachten → Ereignisse** bleibt leer und **Admin → Durchsetzung** zeigt nie an, dass das Deployment angewendet wurde. Die CLI und der Failproof-Daemon vertrauen Zertifikaten unterschiedlich. Die CLI läuft unter Node und berücksichtigt `NODE_EXTRA_CA_CERTS`. `failproofaid`, das Ereignisse sendet und Richtlinien abruft, vertraut den mitgelieferten Zertifikaten sowie dem Trust-Store des Betriebssystems und ignoriert `NODE_EXTRA_CA_CERTS`. Installieren Sie Ihre Zertifizierungsstelle im System-Store des Rechners.
      </Tab>
      <Tab title="CLI">
        ```bash
        # Debian / Ubuntu
        sudo cp company-ca.pem /usr/local/share/ca-certificates/company-ca.crt
        sudo update-ca-certificates
        # RHEL / Fedora
        sudo cp company-ca.pem /etc/pki/ca-trust/source/anchors/ && sudo update-ca-trust
        # macOS
        sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain company-ca.pem

        # then restart the daemon, which loads trusted certificates at start
        sudo systemctl restart failproofaid@$USER                           # Linux
        sudo launchctl kickstart -k system/ai.failproof.failproofaid.$USER  # macOS
        ```

        Das Daemon-Protokoll nennt die Ursache: `sudo journalctl -u failproofaid@$USER | grep UnknownIssuer` unter Linux. `SSL_CERT_FILE` oder `SSL_CERT_DIR` in der Umgebung des Dienstes ersetzt den System-Store für den Daemon, wobei die mitgelieferten Zertifikate weiterhin gelten. Batches, die fehlgeschlagen sind, während die Zertifizierungsstelle nicht vertrauenswürdig war, werden in `~/.failproofai/state/failed` aufbewahrt und automatisch wiederholt, ungefähr stündlich und beim Neustart des Daemons.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Eine Aktion wird abgelehnt, weil der Daemon nicht verfügbar ist">
    <Tabs>
      <Tab title="Dashboard">
        Öffnen Sie **Admin → Durchsetzung** und prüfen Sie den Zeitpunkt des letzten Kontakts und die gemeldete Version des Rechners. Wenn der Rechner veraltet ist, behandeln Sie dies als lokales Daemon-Problem. Schwächen Sie die bereitgestellte Richtlinie nicht ausschließlich ab, um einen nicht verfügbaren Daemon zu umgehen.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        Starten Sie `failproofaid` neu oder aktualisieren Sie es; führen Sie die Konfiguration erneut aus, wenn die Protokollversionen von CLI und Daemon voneinander abweichen. Der konfigurierte Daemon-Pfad schlägt konstruktionsbedingt im sicheren Modus fehl.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Eine benutzerdefinierte Richtlinie wird nicht geladen">
    <Tabs>
      <Tab title="Dashboard">
        Öffnen Sie bei einer Cloud-erstellten Richtlinie **Admin → Richtlinien-Editor**, wählen Sie den Entwurf aus und überprüfen Sie Validierungsfehler vor der Veröffentlichung. Validieren Sie bei einer lokalen Richtlinie diese über die CLI und öffnen Sie dann nach einer Testaktion **Beobachten → Richtlinie**, um zu bestätigen, dass Entscheidungen ankommen.

      </Tab>
      <Tab title="CLI">
        Bestätigen Sie, dass der Dateiname auf `policies.js`, `policies.mjs` oder `policies.ts` endet, das Modul `customPolicies.add(...)` aufruft und Importe aus der Richtliniendatei auflösbar sind.

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Ein Audit liefert keine Ergebnisse">
    <Tabs>
      <Tab title="Dashboard">
        Öffnen Sie **Analysieren → Audits**, wählen Sie den Lauf aus und prüfen Sie, ob die Modellanalyse ausgeführt wurde. Vergleichen Sie dann Umfang und Zeitfenster mit **Beobachten → Sitzungen** und öffnen Sie repräsentative Traces aus dieser Population.

        Ein Null-Ergebnis ist nur dann aussagekräftig, wenn die Analyse erfolgreich abgeschlossen wurde. Wenn die Analyse übersprungen wurde oder fehlgeschlagen ist, liefert der Lauf keine Ergebnisse und hält das nicht analysierte Zeitfenster für einen zukünftigen erfolgreichen Lauf offen. Wenn die Modellanalyse deaktiviert ist, liefert der Audit ebenfalls keine Ergebnisse, da der deterministische Zugangsdaten- und PII-Scan nur Statistiken erfasst, aber keine Befunde mehr meldet.

        ![Das Audit-Formular, in dem Umgebung, Agent, Rhythmus und Sweep-Fenster die Sitzungspopulation definieren.](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        Wenn der Lauf in der Warteschlange verblieben ist, warten Sie auf verfügbare Audit-Agent-Kapazität oder bitten Sie den Deployment-Operator, die Audit-Flotte zu prüfen. Ein Audit in der Warteschlange wird wiederholt; es wird nicht sofort übersprungen.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Online-Evaluierungen laufen nicht automatisch">
    <Tabs>
      <Tab title="Dashboard">
        Öffnen Sie eine abgeschlossene Sitzung und prüfen Sie, ob eine manuelle Evaluierung erfolgreich ist. Die gehostete Cloud verfügt derzeit über keine Evaluator-Endpunkt-Steuerung im Dashboard; der Server-Operator muss diese konfigurieren.
      </Tab>
      <Tab title="CLI">
        Überprüfen Sie zunächst den Evaluator selbst und prüfen Sie dann aktuelle Evaluierungszustände:

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        Bestätigen Sie bei einer selbst gehosteten Cloud, dass `EVALUATOR_ENDPOINT` auf dem Server vorhanden ist und `EVALUATOR_TOKEN` mit dem Evaluator übereinstimmt. Die automatische Evaluierung ist deaktiviert, wenn der Endpunkt fehlt.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Die Cloud-CLI-Authentifizierung richtet sich an die falsche Organisation">
    <Tabs>
      <Tab title="Dashboard">
        Verwenden Sie den Organisations-Umschalter und bestätigen Sie den erwarteten Slug und die Berechtigungen, bevor Sie die Ergebnisse mit der CLI vergleichen.
      </Tab>
      <Tab title="CLI">
        ```bash
        fp whoami
        fp orgs current
        fp orgs perms
        ```

        Im API-Schlüssel-Modus geben Sie `fp --org <slug> --api-key <key> ...` an oder setzen Sie `AGENTEYE_ORG`. Gespeicherter Organisations-Status einer menschlichen Sitzung wird für API-Schlüssel-Anfragen absichtlich ignoriert.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Eine Richtlinie blockiert gültige Arbeit">
    <Tabs>
      <Tab title="Dashboard">
        Öffnen Sie **Beobachten → Richtlinie**, sichern Sie die Entscheidung und die verknüpfte Sitzung und identifizieren Sie die falsch-positive Bedingung. Öffnen Sie dann **Admin → Durchsetzung** und setzen Sie die betroffenen Rechner auf die vorherige Version zurück. Erstellen Sie eine engere Version im **Richtlinien-Editor**, testen Sie sie in einem kleinen Umfang und erweitern Sie erst, nachdem gültige Arbeit erfolgreich ist.

      </Tab>
      <Tab title="CLI">
        Das Zurücksetzen einer Cloud-Deployment-Version ist ausschließlich über das Dashboard möglich. Eine lokale Sitzungspause deaktiviert keine Cloud-verwalteten Richtlinien. Falls das Dashboard nicht verfügbar ist, erfassen Sie den Rechner- und Deployment-Zustand und stellen Sie den Dashboard-Zugang wieder her, anstatt die blockierte Aktion wiederholt zu versuchen.

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Ein Fehler zeigt eine Referenz an">
    <Tabs>
      <Tab title="Dashboard">
        Fehler im Dashboard enden mit einer kurzen Referenz, zum Beispiel `ref 4bf92f35`. Sie identifiziert genau diese eine Anfrage, und der Support kann sie nutzen, um herauszufinden, was genau auf dem Server passiert ist. Kopieren Sie sie genau so in Ihren Bericht, wie sie angezeigt wird.

        Wenn eine ganze Seite nicht geladen werden kann, zeigt die Fehlerseite stattdessen einen `digest`. Fügen Sie diesen ebenfalls ein.
      </Tab>
      <Tab title="CLI">
        Für Menschen lesbare `fp`-Fehler enden mit derselben `ref`. Mit `--json` enthält das Fehlerobjekt die vollständige `request_id`:

        ```bash
        fp --json sessions --since 24h
        ```
      </Tab>
      <Tab title="Daemon">
        Wenn ein Upload fehlschlägt, nennt das Daemon-Protokoll eine `request_id` und eine `batch_id`: unter Linux `sudo journalctl -u failproofaid@$USER | grep batch_id`. Jeder Versuch erhält eine eigene `request_id`; die `batch_id` bleibt über alle Wiederholungsversuche hinweg gleich und verknüpft so die Versuche eines Batches miteinander. Fügen Sie beide ein.
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

Wenn Sie den Support kontaktieren, geben Sie die CLI-Version, den Harness, die Umgebung, die relevante Sitzungs- oder Deployment-ID, alle `ref`- oder `request_id`-Angaben aus dem Fehler sowie die Ausgabe von `failproofai config --status` mit entfernten Geheimnissen an.
