Instala el CLI local con `npm install -g failproofai`. Ejecútalo sin argumentos para abrir el panel de políticas local.

El paquete requiere Node.js 20.9 o superior. Bun 1.3 o superior es compatible para desarrollo e instalaciones desde fuente. `failproofai configure` y `failproofai setup` son alias de `failproofai config`. `failproofai policy`, `failproofai pack` y `failproofai p` son todas variantes de `failproofai policies` — los packs y las políticas individuales eran tres comandos para una misma idea y ahora son uno solo. Las variantes antiguas siguen funcionando, con dos excepciones: `pack list <source>` ahora es `policies show <source>`, y `pack build` ahora es `publish`.

## Configurar una máquina

Instala el CLI y luego carga la clave de máquina en el shell. `read -s` la solicita en un prompt que no la muestra en pantalla, por lo que nunca aparece en un comando:

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

A continuación, configura la máquina y elige qué enforcea:

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` es todo el proceso de configuración: instala el servicio `failproofaid` (como root una vez — en una terminal solicita tu contraseña de sudo, y la vuelve a pedir si caducó antes de que la configuración terminara; sin terminal usa `sudo -n` y nunca solicita nada), conecta los hooks en cada CLI de agente que encuentra y se conecta a Cloud. Sin terminal — CI, un contenedor, un agente que lo dirige — aplica la configuración en lugar de preguntar, y termina con código 1 si algo que se le pidió hacer no ocurrió.

En una terminal, el paso **Conectar a Cloud** en una máquina que aún no está conectada inicia **el inicio de sesión en FailproofAI Cloud** de inmediato; pulsa Tab para ver las otras opciones, **Pegar una clave API** o **Usar código abierto**. Al iniciar sesión se abre un enlace — o se imprime por SSH o sin pantalla, para abrirlo en cualquier dispositivo — donde te registras o inicias sesión, eliges o creas una organización y autorizas la máquina; la terminal detecta la aprobación por sí sola y muestra quién la aprobó y para qué organización. La clave solo se genera cuando la configuración finaliza, después de que se instala el daemon. En una máquina que ya está conectada con una clave válida, el paso muestra un menú con **Mantener la conexión actual** en primer lugar, de modo que volver a ejecutar la configuración nunca abre un navegador por sí solo; una clave guardada que ya no funciona vuelve a iniciar sesión de inmediato e indica el motivo. Volver a iniciar sesión genera una nueva clave y deja la antigua activa hasta que la revoques. Un Cloud anterior al inicio de sesión por navegador lo indica y ofrece las otras opciones.

Elige **sin** políticas. Eso es tarea del segundo comando, y sin él una máquina recién configurada no enforcea nada excepto la protección siempre activa.

Prefiere la variable de entorno en lugar de `--token`: un argumento de línea de comandos es legible desde `ps` por cualquier usuario del sistema. Eso es todo lo que protege la variable — una clave escrita en cualquier comando, incluido `export`, igualmente queda en el historial del shell, por eso se lee con `read -s` como se muestra arriba. En CI, configúrala desde el almacén de secretos y mantén el trazado del shell (`set -x`) desactivado, o el trazado la imprimirá.

<Warning>
  `--connect <url>` registra una máquina que **ya está configurada**. Retorna en cuanto el registro tiene éxito — no instala el daemon ni conecta ningún hook. Usa `failproofai config` a secas (o `failproofai config --token <key>`) en una máquina que aún no ha sido configurada, o aparecerá como conectada sin recopilar ni enforzar nada.
</Warning>

Ejecuta `failproofai` sin argumentos para abrir el panel de políticas local.

| Comando | Resultado |
| --- | --- |
| `failproofai config` | Configura la máquina: agentes, daemon y Cloud — inicia sesión mediante el navegador, pega una clave o continúa con código abierto. Cada agente en la máquina también recibe una pequeña habilidad `failproofai` que lo apunta a las [FailproofAI skills](https://github.com/FailproofAI/skills) en línea |
| `failproofai config --token <key>` | Configura y conecta en un solo paso, sin hacer preguntas. Una clave que incluye `jev:evaluate` también activa [Jev a través de FailproofAI Cloud](/es/reference/jev-cloud) en modo observación, a menos que ya exista un `jev.json` o se pase `--no-transcripts` |
| `failproofai config --connect <url>` | Registra una máquina que **ya** está configurada — sin daemon, sin hooks |
| `failproofai config --status` | Muestra el estado de conexión, daemon, entrega y pausa |
| `failproofai policies` | Lista las políticas integradas, personalizadas, convencionales, de pack y gestionadas por Cloud |
| `failproofai policies --install` | Conecta los hooks en tus CLIs de agentes. Por sí solo no activa ninguna política |
| `failproofai policies add <name>` | Activa una política — una integrada, o `<pack-id>:<name>` de un pack instalado |
| `failproofai policies remove <name>` | Desactiva una política, con la misma nomenclatura |
| `failproofai policies --uninstall` | Desactiva políticas o elimina los hooks del harness |
| `failproofai policies show <owner>/<repo>` | Qué contiene un pack, leído desde su manifiesto, antes de instalarlo |
| `failproofai policies show <owner>/<repo> --releases` | Cada versión que ha publicado y cuál está instalada |
| `failproofai policies add <source>` | Instala un pack de políticas desde una release de GitHub; sin etiqueta toma la más reciente y la fija |
| `failproofai publish` | Publica tus propias políticas como un pack; `--init` escribe uno inicial, y `--min-cli-version <version>` define el CLI más antiguo que puede instalarlo ([Jev checks in a pack](/es/policies/publish-a-pack#jev-checks-in-a-pack)) |
| `failproofai policies remove <publisher/name>` | Desinstala un pack |
| `failproofai audit` | Escanea el historial local del agente y abre la vista de auditoría local |
| `failproofai audit --schedule [days] --email <address>` | Programa escaneos locales periódicos y envía sus resultados por correo electrónico |
| `failproofai audit --status` | Muestra la dirección del informe, el intervalo y el próximo escaneo programado |
| `failproofai audit --no-schedule` | Detiene los escaneos periódicos sin eliminar el historial de auditoría |
| `failproofai harness list` | Lista las rutas de captura adicionales |
| `failproofai otel status` | Inspecciona el [reporte OpenTelemetry](/es/reference/otel) opcional |
| `failproofai jev --url <url> --key-stdin` | Configura Jev en un solo paso; el proveedor se toma del host de la URL |
| `failproofai jev setup --provider <kind> --key-stdin` | Permite que [Jev](/es/reference/jev-providers) evalúe llamadas a herramientas a través de tu propio endpoint y clave |
| `failproofai jev setup --provider failproofai` | Permite que Jev evalúe llamadas a herramientas [a través de FailproofAI Cloud](/es/reference/jev-cloud), con la clave Cloud de esta máquina |
| `failproofai jev setup --mode <m>` | Cambia el modo de Jev: `enforce`, `observe` u `off` (conserva la configuración, deja de consultar a Jev) |
| `failproofai jev status` | Muestra la configuración de Jev, sus permisos y fallbacks recientes; nunca la clave |
| `failproofai jev test` | Envía una solicitud Jev en vivo y muestra su latencia y versión; termina con código 1 si la respuesta llega tarde para los hooks o es incorrecta |
| `failproofai jev models` | Lista los IDs de modelos que un endpoint expone en `GET <base>/models` |
| `failproofai jev remove` | Desactiva Jev; los hooks ejecutan las políticas regex exactamente como antes |
| `failproofai flush --wait` | Entrega el spool de eventos actual |
| `failproofai backfill --since 30d` | Relee el historial previamente procesado |
| `failproofai config --pause [duration]` | Pausa una sesión local durante 30 minutos por defecto, hasta 8 horas |
| `failproofai config --resume` | Reanuda una sesión local en pausa; añade `--all` para limpiar todas las pausas |
| `failproofai update` | Completa las migraciones de paquetes y actualiza el daemon |
| `failproofai migrate --dry-run` | Previsualiza o ejecuta las migraciones de estructura de home pendientes |
| `failproofai uninstall` | Elimina los hooks, la habilidad `failproofai` y el daemon antes de desinstalar el paquete |
| `failproofai --version` | Imprime la versión del paquete instalado |
| `failproofai --help` | Muestra los comandos y el uso global |

## Flags de configuración

| Flag | Uso |
| --- | --- |
| `--token <key>` | Configura y conecta de forma no interactiva; también se lee desde `FAILPROOFAI_CLOUD_TOKEN` |
| `--url <url>` | Conecta a un lugar distinto de `app.befailproof.ai`; también se lee desde `FAILPROOFAI_CLOUD_URL` |
| `--connect <url>` | Solo registra, en una máquina ya configurada. Omite el daemon y todos los hooks |
| `--machine-id <id>` | Establece el ID estable de la máquina |
| `--machine-label <name>` | Renombra una máquina que **ya está conectada**. Por sí solo nunca ejecuta la configuración, así que úsalo después de `failproofai config`, no durante |
| `--no-transcripts` | Envía decisiones sin el contenido del transcript y no activa Cloud Jev, que enviaría cada llamada a herramienta verificada y el prompt reciente; un `jev.json` que ejecute Jev a través de FailproofAI Cloud es eliminado |
| `--disconnect` | Detiene las descargas de políticas de Cloud y la entrega de eventos. También elimina la clave Cloud de Jev y un `jev.json` que apunte a FailproofAI Cloud; tu configuración propia de Jev se conserva |
| `--status` | Muestra el estado actual de la máquina |
| `--pause [duration]` | Pausa la sesión más reciente en el directorio actual; acepta segundos, minutos u horas y tiene por defecto 30 minutos |
| `--resume` | Finaliza anticipadamente una pausa coincidente |
| `--session <id>` | Apunta a una sesión explícita para pausar o reanudar |
| `--all` | Con `--resume`, finaliza todas las pausas activas |

Las pausas locales suspenden las políticas integradas, personalizadas, convencionales y de pack para una sesión. Siempre caducan y no desactivan las políticas gestionadas por Cloud. `block-failproofai-commands` — que siempre está activo y no puede desactivarse ni pausarse — impide que un agente instrumentado use esta vía de escape por sí mismo.

## Flags de políticas

| Flag | Uso |
| --- | --- |
| `--install`, `-i` | Instala los hooks del harness. Los nombres que le siguen activan esas políticas; sin ninguno, no hay cambios en las políticas |
| `--uninstall`, `-u` | Desactiva políticas o elimina hooks |
| `--cli <names...>` | Apunta a uno o más harnesses compatibles |
| `--scope user\|project\|local\|all` | Elige el ámbito de configuración; `all` es para desinstalar |
| `--beta` | Incluye políticas en beta |
| `--custom`, `-c <path>` | Valida y carga un archivo de política personalizado; se puede repetir |

## Flags de entrega y mantenimiento

| Comando | Flags |
| --- | --- |
| `backfill` | `--since <30d\|6m\|YYYY-MM-DD>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` |

`failproofai update` debe ejecutarse después de `npm install -g failproofai@latest`; realiza las migraciones de estructura de home, instala el binario del daemon correspondiente y reinicia el servicio. Luego migra cada perfil de Hermes que ya usa FailproofAI al plugin nativo vinculado e imprime una línea por perfil. `--no-daemon` omite el paso del daemon. `update` termina con código distinto de cero cuando el daemon no pudo reemplazarse, una migración falló o un perfil de Hermes no pudo migrarse (por ejemplo, porque el daemon en ejecución no puede servir el plugin nativo, en cuyo caso sus hooks de shell se conservan).

## Rutas de harness

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

Los nombres de harness compatibles son `claude`, `codex`, `copilot`, `cursor`, `opencode`, `pi`, `hermes`, `openclaw`, `factory`, `devin`, `antigravity` y `goose`.

Las etiquetas asignan un espacio de nombres a los IDs de agentes derivados cuando dos raíces contienen copias del mismo proyecto. Las raíces superpuestas y las etiquetas duplicadas se rechazan para evitar recopilación duplicada o corrupción del cursor. La configuración de rutas adicionales se recarga sin necesidad de reiniciar el daemon.

Los entornos de contenedores pueden reemplazar las rutas adicionales configuradas en archivos con una variable separada por comas llamada `FAILPROOFAI_<HARNESS>_EXTRA_PATHS`, por ejemplo:

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## Variables de entorno

Usa archivos de configuración para el comportamiento persistente de la máquina. Las variables de entorno son más útiles para contenedores, pruebas y procesos individuales.

| Variable | Uso |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | La clave Cloud, en lugar de `--token`. Prefiere esta opción: un argumento es legible desde `ps` por cualquier usuario. Configúrala con `read -s` o desde un almacén de secretos de CI, nunca escribiendo la clave directamente en un comando, que igualmente queda en el historial del shell |
| `FAILPROOFAI_CLOUD_URL` | La URL de Cloud, en lugar de `--url`. La misma variable que lee el daemon |
| `FAILPROOFAI_HOME` | Reubica el layout completo de `~/.failproofai` |
| `FAILPROOFAI_LOG_LEVEL` | Establece la verbosidad del registro local |
| `FAILPROOFAI_HOOK_LOG_FILE` | Escribe los diagnósticos de hooks en un archivo seleccionado |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | Desactiva la telemetría anónima para este proceso |
| `FAILPROOFAI_NO_FIRST_RUN=1` | Omite la configuración interactiva de primer uso |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | Omite la auditoría local posterior a la configuración |
| `FAILPROOFAI_LLM_BASE_URL` | Reemplaza el endpoint compatible con OpenAI usado por las políticas LLM |
| `FAILPROOFAI_LLM_API_KEY` | Proporciona la clave API usada por las políticas LLM |
| `FAILPROOFAI_LLM_MODEL` | Selecciona el modelo usado por las políticas LLM |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | Limita el tiempo de carga de módulos de políticas personalizadas |
| `FAILPROOFAI_NO_DOWNLOAD=1` | Rechaza descargar packs y binarios del daemon; lo que está instalado sigue enforzando |
| `FAILPROOFAI_PACK_BASE_URL` | Descarga packs desde un espejo en lugar de `github.com` |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | Reemplaza las rutas de captura adicionales configuradas para un harness |
| `NO_COLOR` | Desactiva la salida de terminal con colores |

Las variables de home específicas de cada agente, como `CLAUDE_PROJECTS_PATH`, `CURSOR_HOME`, `HERMES_HOME` y `OPENCLAW_HOME`, reemplazan dónde Failproof AI descubre sesiones locales para ese harness.

## Pausar o eliminar una máquina de forma segura

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

Una pausa de sesión local no desactiva las políticas gestionadas por Cloud. Restaura los despliegues de Cloud a través del flujo de trabajo de enforcement de Cloud cuando el problema es el propio rollout.

Antes de eliminar el paquete npm, elimina los hooks instalados y el daemon:

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

Ejecuta `failproofai <command> --help` para obtener detalles específicos de la versión.

<Warning>
  Ejecuta `failproofai uninstall` antes de `npm rm -g failproofai`; npm no elimina los hooks de agentes instalados, la habilidad `failproofai` ni el servicio del daemon.
</Warning>
