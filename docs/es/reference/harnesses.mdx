Un entorno es el contexto donde tu agente realmente se ejecuta. Failproof AI admite doce de ellos, en dos categorías:

- **CLIs de programación** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Pasarelas de chat y asistentes** (2) — Hermes (Slack, Telegram, cron), OpenClaw (asistente autohospedado)

Las mismas políticas y el mismo historial de sesiones se aplican independientemente del entorno en que corra un agente. Una capa de adaptador asigna los nombres de eventos nativos, nombres de herramientas y campos de entrada de herramientas de cada entorno a 29 eventos canónicos antes de que se ejecute cualquier política.

Un agente que no corra en **ninguno** de los doce se instrumenta directamente con el [SDK de Python](/es/reference/custom-agents). Ese es un contrato diferente, y vale la pena indicarlo claramente: el SDK ofrece trazado, sesiones, evaluaciones y auditorías — **no aplica políticas por sí solo.** Bloquear una acción no segura antes de que se ejecute requiere un hook de aplicación en el límite de herramientas de tu entorno de ejecución; [contáctanos](mailto:support@befailproof.ai) y lo mapearemos.

| Entorno | Ámbitos de hook compatibles |
| --- | --- |
| Claude Code | Usuario, proyecto, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | Usuario, proyecto |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | Usuario, proyecto |
| Hermes, OpenClaw | Usuario |

Cada integración normaliza sus nombres de eventos de hook nativos, nombres de herramientas y campos de entrada de herramientas antes de que se ejecuten las políticas. Una política solo puede actuar sobre los eventos que el entorno expone; prueba el comportamiento al final del turno y de las instrucciones en el entorno y versión exactos que despliegues.

## Capacidad de aplicación

«Bloquear» significa que el veredicto devuelto por el adaptador actual es consumido por el entorno indicado. El bloqueo posterior a la herramienta puede reemplazar el resultado mostrado al modelo, pero no puede deshacer un efecto secundario de herramienta que ya ocurrió.

| Entorno | Eventos de bloqueo verificados | Solo observación o advertencias de no bloqueo |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact` y varios eventos de tarea/configuración | `PostToolUse`, ciclo de vida de sesión, notificaciones y eventos post-fallo son observacionales. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | El bloqueo post-herramienta reemplaza el resultado tras la ejecución; los eventos de inicio de sesión y compactación son observacionales en el adaptador actual. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | El bloqueo post-herramienta reemplaza el resultado tras la ejecución; los eventos de sesión y notificación son observacionales. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` y los eventos de sesión son observacionales. |
| OpenCode | `PreToolUse` | Los eventos post-herramienta y de ciclo de vida son observacionales; el manejo de stop actual es una guía para un turno posterior, no una puerta verificada. |
| Pi | `PreToolUse`, `UserPromptSubmit` | Los eventos post-herramienta y de ciclo de vida son observacionales; la guía de stop se aplica a un turno posterior. |
| Hermes | `PreToolUse` | `deny()` bloquea. `instruct()` no detiene la llamada: se ejecuta y la guía se coloca al inicio de su resultado. Los veredictos post-herramienta, de sesión y de subagente-stop no son puertas. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Los eventos post-herramienta, de sesión, subagente-stop y compactación son observacionales. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Los veredictos post-herramienta y subagente-stop son observacionales. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PermissionRequest` condicional | Los hooks de permisos no se ejecutan en todos los modos de permiso; los eventos post-herramienta y de sesión son observacionales. |
| Antigravity CLI | `PreToolUse`, `Stop` | Los veredictos de prompt de usuario y post-herramienta son observacionales; las instrucciones de prompt aún pueden inyectarse. |
| Goose | `PreToolUse` | Los eventos de prompt de usuario, post-herramienta y de sesión son observacionales. Existe un hook de stop nativo con bloqueo en etapas anteriores, pero el adaptador actual no lo instala. |

Las capacidades dependen de la versión. Vuelve a probar después de actualizar un CLI de agente, especialmente cuando una política depende del comportamiento de prompt, stop, permisos o post-herramienta en lugar de la puerta pre-herramienta común.

### Plugin nativo de Hermes

Hermes se integra mediante un plugin nativo local al perfil en lugar de un comando de shell. La instalación vincula el directorio `plugins/failproofai` de cada perfil predeterminado y con nombre de Hermes al plugin incluido en el paquete npm (una copia cuando no se puede crear un enlace simbólico), lo habilita en el `config.yaml` de ese perfil y migra solo las entradas de hook de shell de FailproofAI heredadas. Como el plugin está vinculado, `npm install -g failproofai@latest` lo actualiza sin necesidad de reinstalarlo. Esto evita la creación de un proceso en cada hook. El plugin es compatible con Hermes 0.20.0 y versiones posteriores.

Los hooks de shell heredados (instalados por la versión 1.0.5 y anteriores) **no** verifican los trabajos cron de Hermes: cada ejecución cron construye su propio ámbito de hook, al que se une el plugin nativo, pero los hooks de shell de `config.yaml` no. `failproofai update` migra cada perfil que ya usa FailproofAI al plugin vinculado. Si el daemon en ejecución no puede servir el plugin, `update` deja los hooks de shell en su lugar y sale con código distinto de cero; ejecuta `failproofai config` para actualizar el daemon y luego `failproofai update` nuevamente. Los trabajos cron cargan el plugin en su próxima ejecución; reinicia las pasarelas en ejecución y las sesiones interactivas para cargarlo allí.

En Hermes, `deny()` bloquea la llamada e `instruct()` no: la llamada se ejecuta y la guía se coloca al inicio de su resultado — como primera clave, `failproof_policy_reminder`, de un resultado JSON, o como una línea inicial `[FailproofAI policy reminder (...)]` — de modo que el modelo lo lee junto con la salida, y los scripts que analizan el resultado siguen funcionando. El recordatorio de una política se muestra una vez por turno y se mantiene breve en resultados extensos. Usa `deny()` cuando una acción no debe ocurrir en absoluto: `instruct()` ya no detiene la acción primero. Las llamadas a herramientas realizadas desde un script `execute_code` colocan su recordatorio en el resultado de `execute_code` que lee el modelo; la propia copia del resultado del script no se modifica. Se le indica al modelo que nunca cite un recordatorio en sus respuestas.

Una compilación de Hermes sin middleware de plugin recurre a retener la llamada coincidente una vez con «FailproofAI policy guidance»; la siguiente respuesta del modelo puede repetirla o realizar el mismo trabajo con otra herramienta sin ser retenida nuevamente.

Los nombres de herramientas se asignan entre versiones de Hermes: `process_manage`, `cronjob_manage` y `todo_list` (Hermes 0.21) se tratan igual que `process`, `cronjob` y `todo` (Hermes 0.20). Cada vez que Hermes carga el plugin, escribe `heartbeat.json` en el directorio `plugin-data/agent-plugin-failproofai-5296f299/` del perfil, registrando la versión de Hermes, la ruta y versión del plugin y los hooks que Hermes aceptó. Ejecuta `failproofai config --status` para detectar un perfil deshabilitado, incompleto, duplicado o recién sin configurar, o uno que aún usa hooks de shell heredados (reportado como «Hermes cron jobs are not checked»).

### Plugin de OpenClaw

OpenClaw carga FailproofAI como un plugin de pasarela en proceso, registrado en el `openclaw.json` de cada perfil. Al igual que el plugin de Hermes, consulta al daemon `failproofaid` local por cada veredicto a través de su socket, por lo que necesita un daemon en ejecución: la instalación se rechaza sin uno, y si el daemon no puede responder, las llamadas a herramientas y los prompts se bloquean y el motivo se escribe en el log de la pasarela. Después de `npm install -g failproofai@latest`, reinicia la pasarela OpenClaw para que cargue el plugin actualizado.

### Confianza de hooks en Codex

Codex 0.129 y versiones posteriores ejecuta un hook de `~/.codex/hooks.json` solo después de que lo apruebes en `codex` interactivo («Review hooks»); hasta entonces, cada sesión de Codex — incluido `codex exec` sin cabeza — lo omite. Los hooks en la configuración del sistema de Codex, `/etc/codex/config.toml` en Linux y macOS, se ejecutan sin esa aprobación.

Por eso, cuando `failproofai config` (o `policies --install --cli codex` en ámbito de usuario) puede usar sudo, escribe los hooks de Codex en `/etc/codex/config.toml`, entre `# >>> failproofai managed hooks >>>` y `# <<< failproofai managed hooks <<<`, y deja el resto del archivo tal como estaba.

Ese archivo se aplica a todas las cuentas de la máquina, por lo que cada hook en él ejecuta `/opt/failproofai-codex/codex-hook`, un script breve que pertenece a root. El script entrega el evento al failproofai propio de cada cuenta para cada cuenta que configuró los hooks allí, y no hace nada para ninguna otra cuenta. Otra cuenta que quiera los hooks de Codex de failproofai los configura para sí misma.

Antes de escribir el bloque, y nuevamente en cada `failproofai update`, failproofai verifica que `/etc/codex/config.toml` en sí mismo, el script, cada directorio por encima de ellos, y `sh`, `id` y `cat` que ejecuta pertenezcan a root y no puedan ser escritos por nadie más, y que el failproofai de cada cuenta pertenezca a esa cuenta o a root. En la instalación, cuando esa verificación falla, tus hooks permanecen en `~/.codex/hooks.json`. En la actualización, un script que falla la verificación elimina el bloque, y una cuenta cuyo failproofai falla la verificación se elimina del script; ejecuta `failproofai config` nuevamente una vez que se corrija. `failproofai update` también reescribe un bloque escrito por una versión anterior para usar el script, lo que requiere sudo.

`failproofai uninstall` y desmarcar Codex en `failproofai config` eliminan tu cuenta nuevamente, y el bloque con ella cuando no queda ninguna cuenta.

Sin sudo, y en Windows, los hooks permanecen en `~/.codex/hooks.json`. `failproofai config` y `failproofai config --status` entonces no cuentan Codex como aplicando hasta que los hooks sean aprobados, e indican cómo solucionarlo: vuelve a ejecutar `failproofai config` y permite sudo, o abre `codex` una vez y aprueba los hooks.

## Instalar captura y hooks de políticas

<Tabs>
  <Tab title="Panel de control">
    1. Abre **configuración → claves de API** y crea una clave con `events:add` y `policies:pull`, con un nombre para la máquina o entorno.
    2. En la máquina de destino, conecta el CLI local con la clave mostrada e instala los hooks del entorno.
    3. Inicia una nueva sesión de agente y luego confirma sus eventos de hook y sesión en **traza → eventos en vivo**.
    4. Abre **fix → actividad** para la misma ventana de tiempo y confirma que una decisión de política se atribuye a la máquina.

    La conexión comienza con una clave de máquina. Confirma que incluye permisos tanto de ingesta como de entrega de políticas antes de copiar su secreto.

    ![El panel de nueva clave de API usado para conceder permisos de ingesta de eventos y entrega de políticas.](/images/dashboard/key-create.png)

    Después de instalar los hooks, el flujo de Eventos debería mostrar nuevos eventos de la máquina y el entorno que conectaste.

    ![El flujo de Eventos en vivo usado para confirmar que un entorno recién instalado está reportando.](/images/dashboard/events-stream.png)

    Por último, verifica que las decisiones de política se atribuyan a la misma máquina. Esto confirma que el entorno está reportando actividad de políticas además de eventos de traza.

    ![La página de Políticas usada para verificar decisiones de política de un entorno recién conectado.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Lee la clave de máquina en el shell. `read -s` la solicita en un prompt que no hace eco, por lo que nunca aparece en un comando ni en el historial del shell:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    Luego configura la máquina — esto conecta hooks para cada entorno detectado, instala el daemon y se conecta a Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    La configuración no habilita ninguna política por sí sola; para eso es el segundo comando.

    O apunta a entornos específicos y un ámbito de configuración:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    El ámbito de proyecto mantiene la configuración de hooks con un repositorio. El ámbito de usuario cubre el trabajo entre repositorios. Claude Code también admite ámbito local; la compatibilidad varía según el entorno y el CLI rechaza combinaciones no admitidas.

    Verifica la máquina y sus eventos:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## Agregar una ruta de sesión no predeterminada

<Tabs>
  <Tab title="Panel de control">
    Las rutas adicionales se registran en la máquina, no en Cloud. Después de agregar una, abre **traza → sesiones**, filtra por el entorno de la máquina y confirma que las sesiones de la nueva ruta aparecen. Abre una sesión y verifica el agente, el entorno y las marcas de tiempo de los eventos antes de usarla en una auditoría.

    ![La lista de Sesiones filtrada al entorno que recibe datos de la ruta de captura adicional.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Agrega una ruta con una etiqueta opcional, luego inspecciona las rutas configuradas:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Elimina una ruta con `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  Ejecuta una sesión nueva después de la instalación. Verifica tanto el flujo de eventos en vivo como una decisión de política real antes de ampliar el despliegue.
</Tip>
