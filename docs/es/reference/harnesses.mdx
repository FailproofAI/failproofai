Un entorno es el contexto en el que tu agente se ejecuta realmente. Failproof AI es compatible con doce de ellos, en dos categorías:

- **CLIs de codificación** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Gateways de chat y asistente** (2) — Hermes (Slack, Telegram, cron), OpenClaw (asistente autoalojado)

Las mismas políticas y el mismo historial de sesiones se aplican independientemente del entorno en que se ejecute un agente. Una capa adaptadora mapea los nombres de eventos nativos, nombres de herramientas y campos de entrada de herramientas de cada entorno a 29 eventos canónicos antes de que se ejecute cualquier política.

Un agente que no se ejecuta en **ninguno** de los doce se instrumenta directamente con el [SDK de Python](/es/reference/custom-agents). Este es un contrato diferente y vale la pena dejarlo claro: el SDK ofrece trazabilidad, sesiones, evaluaciones y auditorías — **pero no aplica políticas por sí solo.** Bloquear una acción insegura antes de que se ejecute requiere un hook de aplicación en el límite de herramientas de tu entorno de ejecución; [contáctanos](mailto:support@befailproof.ai) y lo mapeamos.

| Entorno | Ámbitos de hook compatibles |
| --- | --- |
| Claude Code | Usuario, proyecto, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | Usuario, proyecto |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | Usuario, proyecto |
| Hermes, OpenClaw | Usuario |

Cada integración normaliza los nombres de eventos de hook nativos, nombres de herramientas y campos de entrada de herramientas antes de que se ejecuten las políticas. Una política solo puede actuar sobre los eventos que expone el entorno; prueba el comportamiento al final del turno e instrucciones en el entorno y versión exactos que despliegues.

## Capacidad de aplicación

"Bloquear" significa que el veredicto devuelto por el adaptador actual es consumido por el entorno indicado. El bloqueo posterior a la herramienta puede reemplazar el resultado mostrado al modelo, pero no puede deshacer un efecto secundario de la herramienta que ya ocurrió.

| Entorno | Eventos de bloqueo verificados | Observación únicamente o advertencias de no bloqueo |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact` y varios eventos de tarea/configuración | `PostToolUse`, ciclo de vida de sesión, notificaciones y eventos post-fallo son observacionales. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | El bloqueo post-herramienta reemplaza el resultado tras la ejecución; los eventos de inicio de sesión y compactación son observacionales en el adaptador actual. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | El bloqueo post-herramienta reemplaza el resultado tras la ejecución; los eventos de sesión y notificación son observacionales. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` y los eventos de sesión son observacionales. |
| OpenCode | `PreToolUse` | Los eventos post-herramienta y de ciclo de vida son observacionales; el manejo de stop actual es orientación para un turno posterior, no una compuerta verificada. |
| Pi | `PreToolUse`, `UserPromptSubmit` | Los eventos post-herramienta y de ciclo de vida son observacionales; la orientación de stop se aplica a un turno posterior. |
| Hermes | `PreToolUse` | `deny()` bloquea. `instruct()` no detiene la llamada: esta se ejecuta y la orientación se coloca al inicio de su resultado. Los veredictos post-herramienta, de sesión y de subagent-stop no son compuertas. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Los eventos post-herramienta, de sesión, subagent-stop y compactación son observacionales. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Los veredictos post-herramienta y subagent-stop son observacionales. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PermissionRequest` condicional | Los hooks de permiso no se ejecutan en todos los modos de permiso; los eventos post-herramienta y de sesión son observacionales. |
| Antigravity CLI | `PreToolUse`, `Stop` | Los veredictos de prompt de usuario y post-herramienta son observacionales; las instrucciones de prompt aún pueden inyectarse. |
| Goose | `PreToolUse` | Los eventos de prompt de usuario, post-herramienta y de sesión son observacionales. Existe un hook de stop de bloqueo nativo en upstream pero no está instalado por el adaptador actual. |

Las capacidades dependen de la versión. Vuelve a probar después de actualizar un CLI de agente, especialmente cuando una política depende del comportamiento de prompt, stop, permiso o post-herramienta en lugar de la compuerta común de pre-herramienta.

### Plugin nativo de Hermes

Hermes se integra mediante un plugin nativo local al perfil en lugar de un comando de shell. La instalación vincula el directorio `plugins/failproofai` de cada perfil Hermes predeterminado y con nombre al plugin incluido en el paquete npm (una copia cuando no se puede crear un enlace simbólico), lo habilita en el `config.yaml` de ese perfil y migra únicamente las entradas de hook de shell de FailproofAI heredadas. Como el plugin está vinculado, `npm install -g failproofai@latest` lo actualiza sin necesidad de reinstalación. Esto evita un proceso adicional en cada hook. El plugin es compatible con Hermes 0.20.0 y versiones posteriores.

Los hooks de shell heredados (instalados por la versión 1.0.5 y anteriores) **no** comprueban los trabajos cron de Hermes: cada ejecución cron construye su propio ámbito de hook, al que el plugin nativo se une y los hooks de shell de `config.yaml` no. `failproofai update` migra cada perfil que ya usa FailproofAI al plugin vinculado. Si el daemon en ejecución no puede servir el plugin, `update` deja los hooks de shell en su lugar y sale con código no cero; ejecuta `failproofai config` para actualizar el daemon y luego `failproofai update` de nuevo. Los trabajos cron cargan el plugin en su próxima ejecución; reinicia los gateways en ejecución y las sesiones interactivas para cargarlo allí.

En Hermes, `deny()` bloquea la llamada e `instruct()` no: la llamada se ejecuta y la orientación se coloca al inicio de su resultado — como la primera clave, `failproof_policy_reminder`, de un resultado JSON, o como una línea inicial `[FailproofAI policy reminder (...)]` — para que el modelo la lea junto con la salida, y los scripts que analizan el resultado sigan funcionando. El recordatorio de una política se muestra una vez por turno y se mantiene breve en resultados grandes. Usa `deny()` cuando una acción no debe ocurrir en absoluto: `instruct()` ya no detiene la acción primero. Las llamadas a herramientas realizadas desde un script `execute_code` colocan su recordatorio en el resultado de `execute_code` que lee el modelo; la copia del resultado del propio script no se modifica. Se le indica al modelo que nunca cite un recordatorio en sus respuestas.

Una compilación de Hermes sin middleware de plugin recurre a retener la llamada coincidente una vez con el mensaje "FailproofAI policy guidance"; la siguiente respuesta del modelo puede repetirla o realizar el mismo trabajo con otra herramienta sin ser retenida de nuevo.

Los nombres de herramientas se hacen coincidir entre versiones de Hermes: `process_manage`, `cronjob_manage` y `todo_list` (Hermes 0.21) se tratan como `process`, `cronjob` y `todo` (Hermes 0.20). Cada vez que Hermes carga el plugin, escribe `heartbeat.json` en el directorio `plugin-data/agent-plugin-failproofai-5296f299/` del perfil, registrando la versión de Hermes, la ruta y versión del plugin, y los hooks que Hermes aceptó. Ejecuta `failproofai config --status` para detectar un perfil deshabilitado, incompleto, duplicado o recién sin configurar, o uno que aún usa hooks de shell heredados (reportado como "Hermes cron jobs are not checked").

### Plugin de OpenClaw

OpenClaw carga FailproofAI como un plugin de gateway en proceso, registrado en el `openclaw.json` de cada perfil. Al igual que el plugin de Hermes, solicita el veredicto al daemon `failproofaid` local a través de su socket, por lo que necesita un daemon en ejecución: la instalación se rechaza sin uno, y si el daemon no puede responder, las llamadas a herramientas y los prompts se bloquean y el motivo se escribe en el log del gateway. Tras `npm install -g failproofai@latest`, reinicia el gateway de OpenClaw para que cargue el plugin actualizado.

### Confianza de hooks en Codex

Codex 0.129 y versiones posteriores ejecutan un hook de `~/.codex/hooks.json` solo después de que lo apruebes en `codex` interactivo ("Review hooks"); hasta entonces, cada sesión de Codex — incluido `codex exec` sin cabeza — lo omite. Los hooks en la configuración del sistema de Codex, `/etc/codex/config.toml` en Linux y macOS, se ejecutan sin esa aprobación.

Por eso, cuando `failproofai config` (o `policies --install --cli codex` en ámbito de usuario) puede usar sudo, escribe los hooks de Codex en `/etc/codex/config.toml`, entre `# >>> failproofai managed hooks >>>` y `# <<< failproofai managed hooks <<<`, y deja el resto del archivo tal como estaba. El archivo se aplica a todas las cuentas del equipo. `failproofai uninstall` y desmarcar Codex en `failproofai config` eliminan el bloque de nuevo.

Sin sudo, y en Windows, los hooks permanecen en `~/.codex/hooks.json`. En ese caso, `failproofai config` y `failproofai config --status` no cuentan Codex como aplicando políticas hasta que se aprueben los hooks, e indican cómo solucionarlo: vuelve a ejecutar `failproofai config` y permite sudo, o abre `codex` una vez y aprueba los hooks.

## Instalar hooks de captura y políticas

<Tabs>
  <Tab title="Panel de control">
    1. Abre **Administración → Claves** y crea una clave con `events:add` y `policies:pull`, nombrada según el equipo o entorno.
    2. En el equipo de destino, conecta el CLI local con la clave mostrada e instala los hooks del entorno.
    3. Inicia una nueva sesión de agente y confirma sus eventos de hook y sesión en **Observar → Eventos**.
    4. Abre **Observar → Política** para el mismo intervalo de tiempo y confirma que una decisión de política está atribuida al equipo.

    La conexión comienza con una clave de equipo. Confirma que incluye permisos de ingesta y entrega de políticas antes de copiar su secreto.

    ![El panel de nueva clave API usado para otorgar permisos de ingesta de eventos y entrega de políticas.](/images/dashboard/key-create.png)

    Tras instalar los hooks, el flujo de Eventos debería mostrar nuevos eventos del equipo y entorno que conectaste.

    ![El flujo de Eventos en vivo usado para confirmar que un entorno recién instalado está reportando.](/images/dashboard/events-stream.png)

    Por último, verifica que las decisiones de política están atribuidas al mismo equipo. Esto confirma que el entorno está reportando actividad de políticas además de eventos de traza.

    ![La página de Política usada para verificar decisiones de política de un entorno recién conectado.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Lee la clave del equipo en el shell. `read -s` la solicita en un prompt que no la muestra en pantalla, para que nunca aparezca en un comando ni en el historial del shell:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    Luego configura el equipo — esto conecta hooks para cada entorno detectado, instala el daemon y se conecta a Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    La configuración no habilita ninguna política por sí sola; para eso es el segundo comando.

    O apunta a entornos específicos y un ámbito de configuración:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    El ámbito de proyecto mantiene la configuración de hooks junto a un repositorio. El ámbito de usuario cubre el trabajo en múltiples repositorios. Claude Code también es compatible con el ámbito local; la compatibilidad varía según el entorno y el CLI rechaza las combinaciones no admitidas.

    Verifica el equipo y sus eventos:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## Añadir una ruta de sesión no predeterminada

<Tabs>
  <Tab title="Panel de control">
    Las rutas adicionales se registran en el equipo, no en Cloud. Después de añadir una, abre **Observar → Sesiones**, filtra al entorno del equipo y confirma que aparecen sesiones de la nueva ruta. Abre una sesión y comprueba el agente, el entorno y las marcas de tiempo de los eventos antes de usarla en una auditoría.

    ![La lista de Sesiones filtrada al entorno que recibe datos de la ruta de captura adicional.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Añade una ruta con una etiqueta opcional, luego inspecciona las rutas configuradas:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Elimina una ruta con `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  Ejecuta una sesión nueva tras la instalación. Verifica tanto el flujo de eventos en vivo como una decisión de política real antes de ampliar el despliegue.
</Tip>
