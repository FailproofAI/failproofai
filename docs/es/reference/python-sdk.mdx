Instrumenta trazas de un agente personalizado con `failproofai-sdk` para que Failproof AI pueda reconstruir cada ejecución, auditar su comportamiento y encontrar fallos respaldados por evidencia. El SDK escribe eventos estructurados para que el daemon de Failproof los entregue a Cloud. Requiere Python 3.10 o superior.

La instrumentación hace que los agentes personalizados sean observables y auditables. Prevenir una acción insegura antes de que se ejecute también requiere un hook de cumplimiento en tu runtime.

<Info>
  Para aplicar políticas en una configuración de agente personalizado, [contacta con Failproof AI](mailto:support@befailproof.ai). Te ayudaremos a mapear los límites del modelo, las herramientas y el ciclo de vida de tu runtime a hooks de política.
</Info>

## Instalar `failproofai-sdk`

El SDK se distribuye actualmente como una wheel privada. Solicita a tu contacto de Failproof AI la versión actual y el acceso de descarga.

```bash
VERSION=<sdk-version>
pip install "./failproofai_sdk-${VERSION}-py3-none-any.whl"
python -c "import failproofai; print(failproofai.__version__)"
```

Con `uv`, descarga la wheel primero y ejecuta `uv add ./failproofai_sdk-${VERSION}-py3-none-any.whl`. Fija la wheel en un repositorio de artefactos privado o en un lock de dependencias.

El paquete se instala como `failproofai-sdk` y se importa en Python como `failproofai`.

## Instrumentar una ejecución completa

Llama a `configure()` una vez durante el inicio del proceso. Cada llamada a evento es solo por palabra clave y requiere un `session_id` y un `agent_id` estables.

```python
import traceback
import uuid

import failproofai

failproofai.configure(environment="production")

session_id = uuid.uuid4().hex
agent_id = "checkout-agent"

failproofai.event.agent_start(
    session_id=session_id,
    agent_id=agent_id,
    goal="Resolve a failed checkout",
)

try:
    tool_call_id = uuid.uuid4().hex
    failproofai.event.tool_use(
        session_id=session_id,
        agent_id=agent_id,
        tool_name="lookup_order",
        tool_call_id=tool_call_id,
        input={"order_id": "ord_8421"},
    )
    result = {"status": "payment_failed"}
    failproofai.event.tool_result(
        session_id=session_id,
        agent_id=agent_id,
        tool_name="lookup_order",
        tool_call_id=tool_call_id,
        output=result,
    )
except Exception as exc:
    failproofai.event.error(
        session_id=session_id,
        agent_id=agent_id,
        error_type=type(exc).__name__,
        message=str(exc),
        traceback=traceback.format_exc(),
    )
    failproofai.event.agent_end(
        session_id=session_id,
        agent_id=agent_id,
        outcome="failed",
    )
    raise
else:
    failproofai.event.agent_end(
        session_id=session_id,
        agent_id=agent_id,
        outcome="success",
        summary="Escalated the failed payment",
    )
```

Emite `agent_start` una vez por actor. Para sub-agentes, reutiliza el `session_id` del padre, asigna a cada actor un `agent_id` distinto y establece `parent_id` en el **agent ID** del padre, no en el session ID.

## Referencia de configuración

```python
failproofai.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| Parámetro | Comportamiento |
| --- | --- |
| `base_dir` | Raíz de spool explícita. Tiene precedencia sobre todas las variables de entorno. |
| `flush_interval` | Segundos entre escrituras en segundo plano de memoria a JSONL. Por defecto: `0.5`. |
| `environment` | Etiqueta de despliegue en cada evento. Por defecto: `dev`. |
| `FAILPROOFAI_HOME` | Cambia la raíz de Failproof AI que contiene el spool de `custom-agents`. |

El SDK escribe en el `base_dir` explícito cuando está configurado. En caso contrario, usa el spool `custom-agents` del daemon de Failproof bajo `FAILPROOFAI_HOME` o `~/.failproofai`.

El SDK encola las llamadas en memoria y escribe lotes en un hilo en segundo plano. También intenta un flush final a través del manejo `atexit` de Python. Para workers de corta duración, permite el cierre normal del intérprete; la terminación forzada del proceso puede perder eventos que aún estén en memoria.

## Catálogo de eventos

Todos los métodos devuelven `None`. Los campos con valor `None` se omiten en lugar de escribirse como `null` en JSON.

| Método | Campos requeridos además de identidad | Campos opcionales |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

Usa `outcome="failed"`, `"error"`, `"timeout"` o `"rejected"` cuando una finalización deba contarse como fallo. Otros valores, incluido `"failure"`, no son clasificados como fallos por el backend actual.

## Reglas de correlación y duración

- Reutiliza el mismo `tool_call_id`, `hook_id`, `pause_id` o `input_id` para el evento de finalización correspondiente.
- El SDK calcula `duration_ms` para `tool_result`, `hook_completed`, `agent_resume` y `human_input`. Pasarlo manualmente a esos métodos lanza un `ValueError`.
- Los IDs de herramientas y hooks comparten un mapa de pendientes a nivel de proceso. Hazlos globalmente únicos entre sesiones concurrentes y entre ambos espacios de nombres; los IDs de proveedor o UUIDs son la opción más segura.
- Un par dividido entre procesos sigue correlacionándose en el backend, pero el SDK no puede calcular su duración en proceso.
- El mapa de pendientes almacena como máximo 10 000 inicios y desaloja la entrada más antigua cuando está lleno.

## Campos y payloads personalizados

Cada evento acepta campos adicionales por palabra clave. Usa valores compatibles con JSON cuando las consultas en el backend necesiten estructura. Las hojas no compatibles, como UUIDs, fechas y horas, decimales, conjuntos, bytes y objetos de modelo, son convertidas a cadena por el writer.

Los nombres personalizados reservados son `timestamp`, `session_id`, `agent_id`, `type` y `environment`. Los errores tipográficos en campos opcionales se aceptan como nuevos campos personalizados, así que revisa el JSON emitido cuando un campo estándar no aparezca en Cloud.

## Entregar y verificar

<Tabs>
  <Tab title="Dashboard">
    En **Observe → Events**, verifica que `agent_start` aparezca primero y `agent_end` aparezca último. Luego abre **Observe → Sessions** y confirma que los eventos de modelo, herramienta, humano, hook y error aparecen en el orden previsto. Usa el session ID como clave principal para la resolución de problemas.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

Si Cloud está vacío, inspecciona `$FAILPROOFAI_HOME/custom-agents/events`; de lo contrario, `~/.failproofai/custom-agents/events`. Los archivos JSONL prueban que el SDK emitió los eventos; un spool en crecimiento apunta a un problema de configuración o entrega del daemon, mientras que un spool vacío apunta a un problema de instrumentación o de tiempo de vida del proceso.

## Prevenir fallos en un runtime personalizado

Usa los hallazgos de auditoría y las trazas vinculadas para definir la acción insegura, la evidencia requerida y la respuesta prevista. Una integración de cumplimiento personalizada debe exponer la acción antes de su ejecución, pasar su entrada estructurada al motor de políticas y aplicar la decisión resultante de allow, instruct o deny.

Envía un correo a [support@befailproof.ai](mailto:support@befailproof.ai) para diseñar y validar esta integración para tu runtime.
