Utilisez les audits récurrents pour les modes d'échec susceptibles de réapparaître à mesure que les agents, les prompts, les outils et les modèles évoluent.

## Modifier le planning

<Tabs>
  <Tab title="Tableau de bord">
    1. Accédez à **Analyser → Audits** et ouvrez l'audit.
    2. Sélectionnez **modifier les paramètres** et changez la cadence, la fenêtre, la sensibilité ou le nombre de résultats par exécution.
    3. Enregistrez l'audit et confirmez l'heure de la prochaine exécution dans l'en-tête de l'audit.
    4. Mettez en pause et reprenez le planning depuis le même en-tête, à côté de **exécuter maintenant**.
    5. Utilisez **exécuter maintenant** une fois après un changement majeur de périmètre ou de contexte.

    ![En-tête d'audit affichant son état de pause, les résultats ouverts, la dernière exécution, la prochaine exécution, la fenêtre de balayage et la sensibilité, avec les contrôles exécuter maintenant, modifier les paramètres et reprendre.](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits edit checkout-reliability \
      --schedule-interval-secs 86400 \
      --schedule-anchor 2026-08-15T09:00:00Z \
      --window-mode since_last \
      --lookback-window-secs 86400 \
      --yes

    fp audits edit checkout-reliability --disabled --yes
    fp audits edit checkout-reliability --enabled --yes
    ```

    `fp audits edit` demande confirmation avant d'effectuer toute modification, c'est pourquoi chaque exemple ici utilise `--yes`. Le serveur remplace la définition complète à chaque modification ; ainsi, le CLI renvoie l'audit actuel avec vos changements appliqués — une modification par indicateur seul nécessite `audits:read` **en plus de** `audits:write`. Configurez une clé CI avec les deux permissions.

    Consultez la [référence `fp audits`](/fr/reference/cloud-cli#audits) pour connaître les limites de planning, le comportement des fenêtres et toutes les commandes d'audit.
  </Tab>
</Tabs>

## Les deux bornes de planning

Chaque recommandation ci-dessous doit s'inscrire dans ces limites. Les plages sont celles du serveur, et `fp` les reflète côté client — une valeur hors plage provoque une sortie avec code 2 en local plutôt qu'un aller-retour 422.

| Champ | Indicateur | Plage | Défaut |
| --- | --- | --- | --- |
| Intervalle de planning | `--schedule-interval-secs` | 3 600–604 800 secondes (1 heure à 7 jours) | 86 400 (quotidien) |
| Fenêtre de rétroaction | `--lookback-window-secs` | 3 600–7 776 000 secondes (1 heure à 90 jours) | 604 800 (7 jours) |

Sept jours est le plafond de la cadence. Il n'existe pas d'audit Cloud mensuel.

## Choisir une cadence

Sélectionnez en fonction de la vitesse et du coût du risque :

| Schéma de risque | Cadence de départ |
| --- | --- |
| Action de production à fort impact | Quotidienne, ou horaire pendant le déploiement d'un changement risqué |
| Régression de workflow ou de modèle | Hebdomadaire |
| Revue de gouvernance ou d'accès | Hebdomadaire — l'intervalle le plus long disponible |

Alignez la fenêtre de rétroaction sur la cadence afin que les exécutions ne laissent ni lacunes ni n'examinent inutilement une population trop large.

Il n'existe pas d'audit ponctuel ; chaque audit porte un intervalle de planning. Pour une investigation lors d'une release, créez-le activé, laissez la première exécution se déclencher — la première exécution est mise en file d'attente immédiatement à la création, quelle que soit l'ancre — puis mettez-le en pause avec `fp audits edit <name> --disabled --yes`. Réactivez-le avant d'utiliser **exécuter maintenant** : un audit désactivé n'a pas de ligne en file d'attente, et une exécution manuelle sur un audit désactivé est refusée avec un 409.

## Mode de fenêtre et ancre

`--window-mode` détermine quelle fenêtre chaque exécution balaye :

| Mode | Comportement |
| --- | --- |
| `since_last` | Continue depuis la fin de la dernière fenêtre entièrement analysée, de sorte qu'une exécution manquée ne laisse aucune lacune. |
| `fixed` | Réexamine un `lookback_window_secs` glissant à chaque exécution, quelle que soit la couverture de la dernière exécution. |

`--schedule-anchor` fixe la phase plutôt que la fréquence : les exécutions se produisent à `anchor + N × interval`. Si elle est omise, l'ancre prend par défaut le prochain 09:00 UTC ; une ancre de plus de 365 jours dans le futur est rejetée. La modification de l'intervalle ou de l'ancre prend effet au prochain replanification, pas sur l'exécution déjà en file d'attente, et une exécution échouée ne déplace pas l'ancre.

Après avoir modifié l'objectif ou le contexte d'un audit, exécutez-le manuellement une fois avant de vous fier au prochain résultat planifié.

<Note>
  Cette page concerne les plannings d'audit Cloud, qui opèrent sur les sessions Cloud. L'audit local possède son propre minuteur : `failproofai audit --schedule [days]` accepte de 1 à 90 jours et utilise 7 par défaut, analyse l'historique de l'agent sur cette machine uniquement, et est la seule interface offrant une option mensuelle. Ses résultats et sa propriété sont distincts de tout ce qui est décrit ici — consultez [Auditer l'historique local de l'agent](/fr/audits/local-audit).
</Note>
