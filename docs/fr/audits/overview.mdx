## Local ou Cloud

| | Audit local | Audit Cloud |
| --- | --- | --- |
| Commande | `failproofai audit` | `fp audits` |
| Lit | L'historique des agents sur cette machine | Les sessions de votre organisation Cloud |
| Produit | Résultats locaux sur `localhost:8020/audit` | Résultats, problèmes et alertes partagés |
| Nécessite | Aucun compte | Connexion Cloud et clé API |

Utilisez un audit local pour une vérification rapide sur une seule machine. Utilisez le Cloud lorsqu'une équipe a besoin d'un audit récurrent sur plusieurs agents et machines.

## Questions auxquelles un audit peut répondre

- À quel endroit les agents s'arrêtent-ils sans escalader ?
- Quels échecs d'outils entraînent des nouvelles tentatives inefficaces ?
- Les agents accèdent-ils à des données en dehors du workflow prévu ?
- Qu'est-ce qui a changé après une mise à jour du modèle, du prompt ou d'un outil ?

## Ouvrir les audits Cloud

Accédez à **Analyser → Audits**, ou utilisez :

```bash
fp audits list
fp audits show <audit-name>
fp audits findings --status open --limit 20
```

Les commandes d'audit utilisent le nom de l'audit ou son ID complet. Les résultats sont référencés par leur propre ID.

## Du résultat à la prévention

```text
Session → Audit → Finding → Issue → Policy
                         ↘ Alert
```

Un résultat pointe vers des preuves. Un problème détermine la réponse à apporter. Une policy empêche un schéma d'action connu ; une alerte surveille les récurrences.

Chaque résultat ne devrait pas nécessairement devenir une policy. Un résultat de type `policy` décrit une règle applicable. Un résultat de type `failure` ou `improvement` peut nécessiter à la place une modification du workflow, du prompt, du modèle ou d'un outil.
