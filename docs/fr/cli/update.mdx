---
title: Mise à jour après une montée de version
description: "Finalisez ce que npm ne peut pas faire seul : migrer le répertoire home et synchroniser le daemon"
---

```bash
npm install -g failproofai@latest && failproofai update
```

C'est tout ce qu'il faut faire pour la mise à jour. `npm` remplace le CLI ; `failproofai update` se charge du reste.

## Pourquoi une deuxième commande est nécessaire

`npm install -g` ne remplace qu'une seule chose — le CLI. Deux autres éléments d'une installation failproofai vivent intentionnellement en dehors du package, et aucun des deux ne bouge quand npm s'exécute :

- **`~/.failproofai/`**, vos paramètres, l'enregistrement cloud, la sélection des politiques et l'historique. Une nouvelle version peut les organiser différemment, et cette réorganisation doit être effectuée par du code qui connaît les deux structures.
- **Le binaire du daemon `failproofaid`**, situé à `~/.failproofai/bin/failproofaid-<version>`. Il n'est délibérément *pas* dans `node_modules` : une mise à jour qui remplacerait le fichier sous un service en cours d'exécution pointerait un daemon actif vers un binaire compilé depuis une source différente, et la suppression du package le retirerait sous un service qui bouclerait en crash à chaque démarrage.

Ainsi, après `npm install -g` seul, le CLI est nouveau mais pas le daemon. `failproofaid` refuse de démarrer avec une structure de répertoire home qu'il ne reconnaît pas — il signale bruyamment l'incompatibilité plutôt que de l'ignorer silencieusement — les deux moitiés doivent donc être synchronisées. `failproofai update` est cette étape.

## Ce que ça fait

<Steps>
  <Step title="Exécute les migrations de structure en attente">
    Lit la structure enregistrée dans `~/.failproofai/VERSION` et applique les étapes nécessaires pour la mettre au niveau attendu par cette version. En général, il n'y en a aucune — voir [`failproofai migrate`](/fr/cli/migrate).
  </Step>
  <Step title="Met en place le binaire daemon correspondant">
    Depuis le package de plateforme déjà téléchargé par npm si possible (sans accès réseau), sinon depuis l'archive de release pour cette version exacte, vérifiée par SHA-256 avant utilisation.
  </Step>
  <Step title="Redémarre le service et confirme qu'il est opérationnel">
    Vérifié par sondage, et non par hypothèse — un gestionnaire de services signale un processus actif dès qu'il est forké, ce qui n'est pas la même chose qu'il fonctionne correctement.
  </Step>
</Steps>

## Options

| Option | Effet |
|--------|-------|
| `--no-daemon` | Migre uniquement le répertoire home, en laissant le daemon à sa version actuelle. |

<Warning>
  `--no-daemon` laisse en place un daemon dont la version ne correspond pas. Sur une machine configurée pour exiger le daemon, chaque événement de hook **échoue en mode fermé** si le daemon ne répond pas — et un daemon qui refuse de démarrer avec un répertoire home migré ne peut pas répondre. Laissez de préférence la partie daemon s'exécuter.
</Warning>

## En cas de problème

La commande se termine avec un code non nul et indique quelle moitié a échoué. Deux cas à connaître :

- **Une étape de migration ne s'est pas terminée.** Le répertoire home est conservé avec sa *précédente* structure, de sorte que la commande suivante la retentera — aucun répertoire home n'est jamais marqué comme à jour sur la base d'une migration partielle. Des copies de vos paramètres et de votre enregistrement ont été sauvegardées avant toute exécution, dans `~/.failproofai/migrations/backup-layout<n>/`.
- **Le daemon n'a pas pu être redémarré sans mot de passe.** `sudo -n` est utilisé délibérément, afin qu'aucune invite de saisie n'apparaisse depuis un affichage de progression. La commande affiche la ligne exacte à exécuter vous-même.

<Note>
  Rien ici ne nécessite l'assistant de configuration interactif. Vos paramètres, l'enregistrement cloud et la sélection des politiques survivent à une mise à jour. Une machine migrée applique donc exactement les mêmes règles qu'auparavant — ce qui compte surtout sur les machines sans personne devant l'écran : un runner CI, une machine dans un parc, une passerelle headless.
</Note>

## Automatisation

`failproofai update` est non interactif et sans risque à exécuter même quand il n'y a rien à faire — il indique « aucune migration n'était nécessaire » et se termine avec le code 0. L'intégrer après chaque mise à jour dans un script de provisionnement ou un Dockerfile est l'utilisation prévue :

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

(`--no-daemon` lors d'une construction d'image, où il n'y a pas encore de service à redémarrer.)
