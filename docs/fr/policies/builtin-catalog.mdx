38 des 39 politiques intégrées sont fournies sous forme de pack `FailproofAI/policies` ; `block-failproofai-commands` est compilée directement dans le package, car un pack ne peut pas déclarer `alwaysOn`. Le pack installé fait foi pour ce que cette machine peut appliquer :

```bash
failproofai policies show FailproofAI/policies   # le catalogue, tel que publié
failproofai policies                             # ce qui est activé ici
```

`failproofai policies` liste les fichiers personnalisés, les fichiers de convention, les packs installés et les assignations Cloud. Il ne comporte pas de section pour les politiques intégrées, et ne peut donc pas répondre à la question « quelles politiques intégrées existent » — `policies show` et le [Policy Hub](https://befailproof.ai/policy-hub/FailproofAI/policies/) sont les sources pour répondre à cette question.

## Valeurs par défaut et sélection

Un simple `failproofai policies add FailproofAI/policies` active les valeurs par défaut du pack — les 10 lignes marquées **on** ci-dessous. `block-failproofai-commands` est activée en permanence et ne fait pas partie de cette sélection. `--all` prend tout ; `--category <slug>` et `--policy <name>` en prennent une partie. Le slug indiqué à côté de chaque titre est celui que `--category` utilise :

```bash
failproofai policies add FailproofAI/policies --category git,database
```

`block-failproofai-commands` est **toujours activée**. Elle s'enregistre à chaque évaluation, qu'elle figure ou non dans votre sélection, et ne peut être ni désactivée ni mise en pause — une protection contre la désactivation de l'application par l'agent qui peut elle-même être désactivée par l'agent n'est pas une protection. Un pack ne peut pas déclarer `alwaysOn`, c'est pourquoi cette politique est compilée dans le package plutôt que dans le pack.

## Assainissement — `sanitize`

Ces politiques s'exécutent sur `PostToolUse`, après que l'outil a déjà été exécuté. Elles **détectent et rejettent le résultat de l'outil** ; elles ne suppriment pas une sous-chaîne pour renvoyer le reste.

Un refus ici n'atteint le modèle que sur les harnais qui consomment un verdict `PostToolUse` — **codex** et **copilot**, où la raison remplace l'intégralité du résultat de l'outil. Sur claude, cursor, opencode, pi, hermes, openclaw, factory, devin, antigravity et goose, `PostToolUse` est en mode observation uniquement : la détection est enregistrée et la sortie parvient quand même au modèle.

| Politique | Déclencheur | Par défaut | Résultat |
| --- | --- | --- | --- |
| `sanitize-jwt` | `PostToolUse` | on | Refuse un résultat d'outil contenant un JWT. |
| `sanitize-api-keys` | `PostToolUse` | on | Refuse un résultat d'outil contenant une clé OpenAI, Anthropic, GitHub, AWS, Stripe ou Google. |
| `sanitize-connection-strings` | `PostToolUse` | on | Refuse un résultat d'outil contenant une chaîne de connexion à une base de données avec des identifiants intégrés. |
| `sanitize-private-key-content` | `PostToolUse` | on | Refuse un résultat d'outil contenant du contenu de clé privée PEM. |
| `sanitize-bearer-tokens` | `PostToolUse` | on | Refuse un résultat d'outil contenant un jeton `Authorization: Bearer`. |

| `block-aws-cli` | `PreToolUse` sur `Bash` | off | Contrôle les commandes CLI `aws`. |

## Workflow — `workflow`

Les cinq politiques s'exécutent sur `Stop` et sont désactivées par défaut.

| Politique | Par défaut | Résultat |
| --- | --- | --- |
| `require-commit-before-stop` | off | Refuse la complétion tant que des modifications suivies restent non commitées. |
| `require-push-before-stop` | off | Refuse la complétion tant que des commits restent uniquement locaux. |
| `require-pr-before-stop` | off | Exige une pull request pour la branche courante. |
| `require-no-conflicts-before-stop` | off | Exige un merge propre par rapport à la branche de base configurée. |
| `require-ci-green-before-stop` | off | Exige que les vérifications CI sur le commit HEAD courant passent, en ignorant les exécutions obsolètes sur les commits précédents. |

Ces politiques nécessitent un harnais dont le verdict `Stop` est consommé. Ce n'est pas le cas de tous les harnais :

| Harnais | `Stop` |
| --- | --- |
| claude, codex, copilot, cursor, openclaw, factory, devin, antigravity | Vérifié pour bloquer : le refus force un nouveau tour |
| pi | Observation. La raison est transmise au tour suivant comme instruction, et non comme verrou |
| goose, hermes | Aucun hook `Stop` n'est installé, ces cinq politiques ne s'y déclenchent donc jamais |
| opencode | Non vérifié. `Stop` ne fait pas partie des événements dont opencode consomme un verdict |

Les VM Cloud Agent de Cursor n'exécutent aucun hook stop, donc une session Cursor sur ces machines n'est pas couverte, même si Cursor en local l'est.

<Note>
  Les politiques `warn-*` retournent `instruct`, et non `deny`. (`prefer-package-manager` fait exception parmi les noms non `block-*` : elle retourne `deny`, et bloque donc sur tout harnais qui consomme un verdict `PreToolUse` — soit les douze.) Sur Hermes et Goose, sur Pi, OpenClaw et Factory en dehors du canal `Stop`, et sur Antigravity en dehors de `Stop` et `UserPromptSubmit`, `instruct` se dégrade en allow avec une note sur stderr — l'agent n'est pas informé. Le canal `UserPromptSubmit` d'Antigravity est un vrai second canal : l'instruction est injectée en tant que message transitoire avant l'exécution du modèle.
</Note>

## Référence des paramètres

Configurez les paramètres dans l'objet `policyParams` du scope sélectionné. Les types sont validés par chaque politique.

| Politique | Paramètre | Type et valeur par défaut |
| --- | --- | --- |
| `sanitize-api-keys` | `additionalPatterns` | `pattern[]`, `[]` ; les entrées contiennent `regex` et `label` |
| `block-read-outside-cwd` | `allowPaths` | `string[]`, `[]` |
| `block-sudo` | `allowPatterns` | `string[]`, `[]` |
| `block-rm-rf` | `allowPaths` | `string[]`, `[]` |
| Bloqueurs d'infrastructure | `allowPatterns` | `string[]`, `[]` |
| `block-secrets-write` | `additionalPatterns` | `string[]`, `[]` |
| `block-push-master` | `protectedBranches` | `string[]`, `["main", "master"]` |
| `block-work-on-main` | `protectedBranches` | `string[]`, `["main", "master"]` |
| `prefer-package-manager` | `allowed`, `blocked` | `string[]`, `[]` |
| `warn-large-file-write` | `thresholdKb` | `number`, `1024` |
| `require-push-before-stop` | `remote`, `baseBranch` | `string`, `"origin"` ; `string`, `"main"` |
| `require-pr-before-stop` | `baseBranch` | `string`, `"main"` |
| `require-no-conflicts-before-stop` | `baseBranch` | `string`, `"main"` |

```json
{
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release"]
    }
  }
}
```

<Note>
  Un nom de politique nu utilisé comme clé dans `policyParams` est pris en charge uniquement pour `FailproofAI/policies`. Pour tout autre pack, la clé est `pack/<owner>/<repo>/<policy>` — un pack tiers déclarant le même nom de politique reçoit les valeurs par défaut du schéma, et non vos paramètres.
</Note>

<Warning>
  Un motif d'autorisation élargit ce qu'un agent peut faire. Testez la tokenisation exacte et les variantes de commandes sur le harnais cible avant de le déployer à l'échelle d'une flotte.
</Warning>
