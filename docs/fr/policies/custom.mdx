Consultez le [catalogue intégré](/fr/policies/builtin-catalog) avant d'écrire une politique. Une règle déjà vérifiée est généralement plus sûre qu'une nouvelle.

## Partir d'une politique fonctionnelle

```bash
failproofai publish --init guards.mjs
failproofai policies -i -c ./guards.mjs
```

Le modèle de départ bloque `git push --force`. Modifiez-le, demandez à votre agent d'essayer l'action bloquée, puis inspectez **Politiques → Activité**.

```js
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production",
  description: "Production changes need a human",
  match: { events: ["PreToolUse"], toolNames: ["Bash"] },
  fn: async (ctx) =>
    String(ctx.toolInput?.command ?? "").includes("production")
      ? deny("Ask a human before changing production.")
      : allow(),
});
```

Une politique retourne `allow()`, `deny(message)` ou `instruct(message)`. Utilisez `deny` lorsque l'action doit être stoppée ; tous les environnements d'exécution ne sont pas en mesure de transmettre une instruction à l'agent.

## Chargement automatique

Placez les fichiers nommés `*policies.js`, `*policies.mjs` ou `*policies.ts` dans :

- `.failproofai/policies/` pour un seul projet.
- `~/.failproofai/policies/` pour votre compte utilisateur.

## Tester les cas d'échec

Testez à la fois l'action non sécurisée et les opérations légitimes qui lui ressemblent. Vérifiez que la décision provient bien de votre politique et non d'une autre règle.

Supprimez les fichiers de test explicites avec :

```bash
failproofai policies -u -c
```

Lorsque la politique est prête, [publiez un pack](/fr/policies/publish-a-pack) ou [déployez-la via Cloud](/fr/policies/deploy).
