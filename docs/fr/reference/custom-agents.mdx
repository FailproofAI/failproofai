Python 3.11 ou version ultérieure. Aucune dépendance d'exécution. Vous utilisez un framework ? [LangChain, CrewAI, LlamaIndex et Pydantic AI](/fr/start/integrations) s'instrumentent eux-mêmes en un seul appel.

<Note>
  Il existe également un **SDK TypeScript**, et les deux écrivent les mêmes événements dans le même spool. Une flotte avec des agents Node et des agents Python produit un seul ensemble de sessions, pas deux. Choisissez par service, pas par entreprise.
</Note>

## Installation

```bash
pip install failproofai-sdk
```

Le package est installé sous le nom `failproofai-sdk` et importé en Python sous le nom `failproofai_sdk`. Les extras de framework tels que `failproofai-sdk[langgraph]` installent le framework lui-même ; les adaptateurs sont toujours inclus dans le wheel de base.

## Configuration

### Spans OpenTelemetry (opt-in)

Installez `opentelemetry-sdk` séparément, puis attachez l'exporteur optionnel :

```python
import failproofai_sdk
from opentelemetry.sdk.trace import TracerProvider

provider = TracerProvider()
failproofai_sdk.instrument("otel", provider=provider)
with provider.get_tracer("my-agent").start_as_current_span(
    "agent", attributes={"gen_ai.operation.name": "invoke_agent"}
):
    pass
provider.force_flush()
```

La configuration utilise votre provider enregistré si vous omettez `provider`, et n'en crée un que si aucun n'est enregistré. Vous pouvez également passer `failproofai_sdk.OtelSpanExporter()` directement à votre propre processeur de spans. Les autres exporteurs restent inchangés.

Le daemon FailproofAI connecté se charge des exports ; le SDK n'a besoin d'aucune configuration réseau, clé ou écouteur local. Un administrateur doit activer [l'ingestion OpenTelemetry](/fr/agenteye/opentelemetry). Un `instrument()` nu n'active jamais OTEL. `uninstrument("otel")` désactive uniquement son propre processeur. Votre instrumentation contrôle la capture du contenu. Videz le provider avant de quitter. Le SDK ne déclare toujours aucune dépendance d'exécution stricte et n'importe OpenTelemetry que lorsqu'il est demandé.

```python
import failproofai_sdk

failproofai_sdk.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| Argument | Ce qu'il fait |
| --- | --- |
| `environment` | Le libellé sur chaque événement — `production`, `staging`, `prod-eu`. Par défaut `dev`. |
| `flush_interval` | La fréquence à laquelle le thread d'arrière-plan écrit sur le disque, en secondes. Par défaut `0.5`. |
| `base_dir` | L'emplacement d'écriture. Par défaut le spool du daemon, ce qui convient dans la plupart des cas. |

Définissez-les via des variables d'environnement à la place :

| Variable | Ce qu'elle fait |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | Définit `environment` sans modification du code, pour les cas où le libellé appartient au déploiement plutôt qu'à l'application. Un argument de `configure()` a la priorité sur elle. |
| `FAILPROOFAI_HOME` | Déplace la racine Failproof AI qui contient le spool. |
| `FAILPROOFAI_SDK_STRICT` | `1` fait lever une exception sur les erreurs d'instrumentation au lieu de les journaliser. |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | `1` fait lever une exception sur un problème de compatibilité de framework au lieu d'avertir et de continuer. |

<Warning>
  **Pas de virgules dans `environment`.** L'ingestion découpe ce champ sur les virgules pour construire ses filtres, et ignore tout événement dont le libellé en contient une — ce qui fait silencieusement disparaître toute une exécution. Écrivez `prod-eu`, pas `prod,eu`.

  `configure(environment="prod,eu")` lève une exception immédiatement. `AGENTEYE_ENVIRONMENT` ne peut pas lever d'exception — rien ne vous appelle — elle avertit donc une fois et revient à `dev`.
</Warning>

Les événements sont mis en file d'attente en mémoire et écrits en arrière-plan toutes les `flush_interval` secondes, avec un vidage final à la sortie de l'interpréteur. Un processus tué brutalement perd tout ce qui n'avait pas encore été écrit.

## Identité

Chaque événement appartient à une session et à un agent. **Les scopes remplissent les deux**, vous n'avez donc rarement besoin de les passer :

```python
with failproofai_sdk.session():
    with failproofai_sdk.agent("planner"):
        failproofai_sdk.event.tool_use(tool_name="search", tool_call_id="c1")
```

Passer `session_id` ou `agent_id` explicitement fonctionne toujours et a la priorité. Si aucun n'est lié ni passé, l'appel lève `TypeError` plutôt que d'émettre un événement que Cloud ignorerait silencieusement.

<Note>
  L'identité repose sur des variables de contexte. Elle suit automatiquement les tâches `asyncio`, mais **pas** les nouveaux threads — enveloppez un worker dans `failproofai_sdk.propagate()` ou ses événements seront perdus sans rattachement.
</Note>

## Catalogue d'événements

Quinze méthodes. La plupart viennent par **paires** — vous appelez l'ouvreur, puis le fermeur, et le SDK mesure l'intervalle.

| | Ouvre | Ferme |
| --- | --- | --- |
| **Agents** | `agent_start` | `agent_end` |
| | `agent_pause` | `agent_resume` |
| **Modèles** | `model_request` | `model_response` |
| **Outils** | `tool_use` | `tool_result` |
| **Hooks** | `hook_triggered` | `hook_completed` |
| **Humains** | `human_wait` | `human_input` |

Trois sont indépendantes : `error`, `human_pause`, `human_interrupt`.

<Accordion title="Tous les champs, par méthode" icon="table">

Chaque méthode accepte également `session_id` et `agent_id`, que les scopes remplissent pour vous. Tout ce qui est laissé à `None` est supprimé plutôt qu'envoyé comme `null` JSON, et chaque méthode retourne `None`.

| Méthode | Requis | Optionnel |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools`, `request_id` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role`, `request_id`, `duration_ms` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

</Accordion>

<Warning>
  Pour marquer une exécution comme échouée, `outcome` doit être l'une des valeurs suivantes : `failed`, `error`, `timeout` ou `rejected`. Toute autre valeur — y compris la quasi-correspondance `"failure"` — est comptée comme un succès.
</Warning>

## Appariement et durée

**Une seule règle : donnez à l'événement de fermeture le même identifiant que son ouvreur.** C'est ce qui les apparie et ce qui permet au SDK de mesurer l'intervalle.

| Paire | Appariée sur |
| --- | --- |
| `tool_use` → `tool_result` | `tool_call_id` |
| `hook_triggered` → `hook_completed` | `hook_id` |
| `agent_pause` → `agent_resume` | `pause_id` |
| `human_wait` → `human_input` | `input_id` |
| `model_request` → `model_response` | `request_id` |

**Ne passez pas `duration_ms` vous-même.** Le SDK le mesure, et le passer lève `ValueError`.

La seule exception est `model_response`, où vous seul connaissez la latence réelle du fournisseur. Passez un nombre entier de millisecondes — un float lève une exception, car la colonne est un entier 32 bits et serait sinon vide.

<Accordion title="Cas limites" icon="circle-help">

- **Les identifiants n'ont besoin d'être uniques que par type et par session.** Un appel d'outil et un hook peuvent partager le même ; deux sessions s'exécutant simultanément peuvent réutiliser les mêmes identifiants sans collision.
- **Ils ne sont pas limités à un agent.** Une paire ouverte sous un agent et fermée sous un autre correspond quand même — ce qui est le cas normal dans le code multi-agents.
- **`request_id` est optionnel mais recommandé.** Sans lui, les événements de modèle s'apparient dans l'ordre d'arrivée, donc deux appels simultanés dans le même agent peuvent être mal appariés.
- **Une paire répartie entre processus** correspond quand même dans Cloud, mais le SDK ne peut pas la chronométrer — aucun des deux processus n'a vu les deux moitiés.
- **Au plus 10 000 ouvreurs peuvent attendre un fermeur simultanément.** Au-delà, le plus ancien est supprimé, de sorte qu'une fuite ne peut pas croître indéfiniment.

</Accordion>

## Vos propres champs

Tout mot-clé supplémentaire que vous passez est stocké avec l'événement :

```python
failproofai_sdk.event.tool_use(
    tool_name="search", tool_call_id="c1",
    fw_tenant="acme", fw_region="eu-west-1",     # les vôtres
)
```

Préférez les types JSON si vous souhaitez les interroger ultérieurement. Tout le reste — un UUID, un datetime, un `Decimal`, un ensemble, des octets, un objet modèle — est stocké sous forme de chaîne.

<Warning>
  **Préfixez vos noms de champs.** Les extras sont appliqués en dernier, donc un champ nommé `model`, `tool_name` ou `outcome` écrase silencieusement le vrai. Les adaptateurs de framework utilisent `fw_` ; faites de même et rien ne pourra entrer en collision.

  C'est aussi pourquoi un champ optionnel mal orthographié ne génère jamais d'erreur — il devient simplement un nouveau champ personnalisé. Si un champ standard est absent dans Cloud, vérifiez d'abord l'orthographe.
</Warning>

Ces cinq noms sont réservés et rejetés d'emblée : `timestamp`, `session_id`, `agent_id`, `type`, `environment`.

## Livraison et vérification

<Tabs>
  <Tab title="Tableau de bord">
    Dans **Observer → Événements**, vérifiez que `agent_start` existe en premier et `agent_end` en dernier. Ouvrez ensuite **Observer → Sessions** et confirmez que les événements de modèle, d'outil, humains, de hook et d'erreur apparaissent dans l'ordre prévu. Utilisez l'identifiant de session comme clé principale pour le débogage.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

Si Cloud est vide, inspectez `$FAILPROOFAI_HOME/custom-agents/events`, sinon `~/.failproofai/custom-agents/events`. Les fichiers JSONL prouvent l'émission par le SDK ; un spool en croissance pointe vers la configuration ou la livraison du daemon, tandis qu'un spool vide pointe vers l'instrumentation ou la durée de vie du processus.

<Note>
  N'inspectez le spool que lorsque le daemon est arrêté. Pendant son fonctionnement, il collecte et supprime chaque lot en quelques millisecondes, de sorte qu'une liste du répertoire est en compétition avec le collecteur et affiche bien moins d'événements que ce qui a été émis.
</Note>

## Prévenir les défaillances dans un runtime personnalisé

Utilisez les résultats d'audit et les traces liées pour définir l'action non sûre, la preuve requise et la réponse prévue. Une intégration d'application des politiques personnalisée doit exposer l'action avant son exécution, transmettre son entrée structurée au moteur de politiques et appliquer la décision allow, instruct ou deny qui en résulte.

[Contactez Failproof AI](mailto:support@befailproof.ai) et nous vous aiderons à mapper les limites de modèle, d'outil et de cycle de vie de votre runtime aux hooks de politique, puis à valider l'intégration avec vous.
