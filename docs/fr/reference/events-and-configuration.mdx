## Familles d'événements

- Démarrage, fin, pause et reprise d'agent
- Requête et réponse du modèle
- Utilisation et résultat d'outil
- Déclenchement et complétion de hook
- Attente, saisie, pause et interruption humaine
- Erreurs explicites

Chaque événement porte un horodatage, un ID de session, un ID d'agent, un type d'événement et un environnement. Les champs spécifiques à chaque événement contiennent des données relatives au modèle, à l'outil, à la corrélation, au résultat, au contenu, à la durée ou à l'erreur.

## Inspecter un contrat d'événement

<Tabs>
  <Tab title="Tableau de bord">
    1. Ouvrez **Observer → Événements**.
    2. Définissez une fenêtre temporelle courte et filtrez par environnement, agent et type d'événement.
    3. Sélectionnez un événement pour inspecter ses champs normalisés et sa charge brute, puis ouvrez sa session pour voir le contexte d'exécution.
    4. Si une durée associée est manquante, vérifiez que les événements de début et de fin utilisent le même ID de corrélation.

    Utilisez le flux d'événements pour restreindre les données à une seule exécution d'agent et inspecter les champs d'événements normalisés.

    ![Le flux d'événements en direct avec des filtres pour l'environnement, l'agent, la session et le type d'événement.](/images/dashboard/events-stream.png)

    Suivez ensuite l'événement dans sa session. La trace montre ce qui s'est produit immédiatement avant et après, ce qui est nécessaire lorsque la charge seule est ambiguë.

    ![La trace de session liée utilisée pour inspecter l'événement dans son contexte d'exécution.](/images/dashboard/session-detail.png)

    Comparez les IDs de corrélation et les horodatages dans les deux vues lorsqu'un événement associé ou une durée est manquant.
  </Tab>
  <Tab title="CLI">
    Découvrez les valeurs de filtre valides, puis récupérez les charges complètes des événements pour une session :

    ```bash
    fp list event_types
    fp list envs
    fp events --since 1h \
      --env production \
      --event-type tool_use,tool_result \
      --session-id <session-id> \
      --full
    ```

    Utilisez `fp --json events ... --fields ts,event_type,session_id,payload` pour une inspection lisible par machine.
  </Tab>
</Tabs>

## Champs SDK réservés

N'utilisez pas `timestamp`, `session_id`, `agent_id`, `type` ou `environment` comme champs personnalisés du SDK Python. Les durées d'événements associés, telles que la durée du résultat d'outil, sont calculées par le SDK et ne peuvent pas être fournies manuellement.

## Limites locales

- L'état de Failproof AI réside sous `~/.failproofai`, sauf configuration explicite différente.
- `failproofai-sdk` utilise `AGENTEYE_HOME` pour son remplacement de répertoire de base hérité.
- Les étiquettes d'environnement peuvent être définies via la configuration du SDK ou `AGENTEYE_ENVIRONMENT`.
- Les identifiants du daemon sont stockés séparément des paramètres non secrets.

Utilisez des noms d'environnement stables et à faible cardinalité. Les virgules ne sont pas prises en charge dans les étiquettes d'environnement du daemon.

## Modifier une étiquette d'environnement

<Tabs>
  <Tab title="Tableau de bord">
    Les étiquettes d'environnement sont assignées par le SDK émetteur ou le daemon Failproof. Après en avoir modifié une, ouvrez **Observer → Sessions** et utilisez le filtre d'environnement pour confirmer que les nouvelles sessions portent la nouvelle valeur. Les sessions existantes conservent leur environnement d'origine.

  </Tab>
  <Tab title="CLI">
    Pour `failproofai-sdk`, configurez l'environnement dans le code ou avec sa variable d'environnement héritée. Relancez la configuration du daemon lors de la modification des paramètres au niveau machine.

    ```bash
    export AGENTEYE_ENVIRONMENT=production-us-east
    failproofai config
    failproofai config --status
    fp sessions --since 1h --env production-us-east
    ```
  </Tab>
</Tabs>
