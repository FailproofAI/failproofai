Installez le CLI local avec `npm install -g failproofai`. Lancez-le sans arguments pour ouvrir le tableau de bord des politiques locales.

Le package nécessite Node.js 20.9 ou une version plus récente. Bun 1.3 ou une version plus récente est pris en charge pour le développement et les installations depuis les sources. `failproofai configure` et `failproofai setup` sont des alias de `failproofai config`. `failproofai policy`, `failproofai pack` et `failproofai p` sont toutes des graphies de `failproofai policies` — les packs et les politiques individuelles constituaient trois commandes pour une seule idée, désormais regroupées en une seule. Les anciennes graphies fonctionnent toujours, à deux exceptions près : `pack list <source>` est maintenant `policies show <source>`, et `pack build` est maintenant `publish`.

## Configurer une machine

Installez le CLI, puis lisez la clé machine dans le shell. `read -s` la saisit via une invite qui n'affiche rien, elle n'apparaît donc jamais dans une commande :

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

Configurez ensuite la machine et choisissez ce qu'elle applique :

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` couvre l'intégralité de la configuration : il installe le service `failproofaid` (une fois en root — dans un terminal, il demande votre mot de passe sudo, et le redemande si celui-ci a expiré avant la fin de la configuration ; sans terminal, il utilise `sudo -n` et ne demande jamais rien), câble les hooks dans chaque CLI d'agent trouvé, et se connecte au Cloud. Sans terminal — CI, conteneur, agent qui le pilote — il applique les paramètres sans demander et quitte avec le code 1 si l'une des actions demandées n'a pas abouti.

Dans un terminal, l'étape **Connect to cloud** sur une machine qui n'est pas encore connectée démarre immédiatement la **connexion à FailproofAI Cloud** ; appuyez sur Tab pour accéder aux autres options, **Paste an API key** ou **Use open source**. La connexion ouvre un lien — ou l'affiche via SSH ou sans écran, pour l'ouvrir sur n'importe quel appareil — où vous vous inscrivez ou vous connectez, choisissez ou créez une organisation, et autorisez la machine ; le terminal capte l'approbation automatiquement et indique qui l'a accordée et pour quelle organisation. La clé n'est générée qu'une fois la configuration terminée, après l'installation du daemon. Sur une machine déjà connectée avec une clé valide, l'étape se présente sous forme de menu avec **Keep current connection** en premier, de sorte que relancer la configuration n'ouvre jamais de navigateur automatiquement ; une clé enregistrée qui ne fonctionne plus relance immédiatement la connexion en indiquant la raison. Se reconnecter génère une nouvelle clé et laisse l'ancienne active jusqu'à sa révocation. Un Cloud antérieur à la connexion via navigateur l'indique et propose les autres options.

La configuration choisit **aucune** politique. C'est le rôle de la deuxième commande : sans elle, une machine fraîchement configurée n'applique rien d'autre que la protection toujours active.

Préférez la variable d'environnement à `--token` : un argument de ligne de commande est lisible depuis `ps` par tous les utilisateurs de la machine. C'est la seule protection qu'offre la variable — une clé saisie dans n'importe quelle commande, `export` inclus, se retrouve quand même dans l'historique du shell, d'où l'utilisation de `read -s` ci-dessus. En CI, définissez-la depuis le gestionnaire de secrets et désactivez le traçage shell (`set -x`), sinon la trace l'affichera.

<Warning>
  `--connect <url>` enrôle une machine **déjà configurée**. La commande se termine dès que l'enrôlement réussit — elle n'installe pas le daemon et ne câble aucun hook. Utilisez simplement `failproofai config` (ou `failproofai config --token <key>`) sur une machine qui n'a pas encore été configurée, sinon elle apparaîtra comme connectée sans rien collecter ni appliquer.
</Warning>

Lancez `failproofai` sans arguments pour ouvrir le tableau de bord des politiques locales.

| Commande | Résultat |
| --- | --- |
| `failproofai config` | Configure la machine : agents, daemon et Cloud — connexion via le navigateur, collage d'une clé, ou utilisation en open source. Chaque agent de la machine reçoit également une petite compétence `failproofai` pointant vers les [FailproofAI skills](https://github.com/FailproofAI/skills) en ligne |
| `failproofai config --token <key>` | Configure et connecte en une seule passe, sans aucune interaction. Une clé portant `jev:evaluate` active également [Jev via FailproofAI Cloud](/fr/reference/jev-cloud) en mode observation, sauf si un fichier `jev.json` existe déjà ou si `--no-transcripts` est spécifié |
| `failproofai config --connect <url>` | Enrôle une machine **déjà** configurée — sans daemon ni hooks |
| `failproofai config --status` | Affiche l'état de la connexion, du daemon, de la livraison et de la pause |
| `failproofai policies` | Liste les politiques intégrées, personnalisées, de convention, de pack et gérées par Cloud |
| `failproofai policies --install` | Câble les hooks dans vos CLI d'agents. N'active aucune politique par lui-même |
| `failproofai policies add <name>` | Active une politique — intégrée, ou `<pack-id>:<name>` depuis un pack installé |
| `failproofai policies remove <name>` | Désactive une politique, même nomenclature |
| `failproofai policies --uninstall` | Désactive les politiques ou supprime les hooks du harnais |
| `failproofai policies show <owner>/<repo>` | Ce que contient un pack, lu depuis son manifeste, avant de l'adopter |
| `failproofai policies show <owner>/<repo> --releases` | Toutes les versions qu'il a publiées, et celle qui est installée |
| `failproofai policies add <source>` | Installe un pack de politiques depuis une release GitHub ; sans tag, prend la plus récente et l'épingle |
| `failproofai publish` | Publie vos propres politiques sous forme de pack ; `--init` en crée un point de départ, et `--min-cli-version <version>` définit la version minimale du CLI pouvant l'installer ([Jev checks in a pack](/fr/policies/publish-a-pack#jev-checks-in-a-pack)) |
| `failproofai policies remove <publisher/name>` | Désinstalle un pack |
| `failproofai audit` | Analyse l'historique local des agents et ouvre la vue d'audit locale |
| `failproofai audit --schedule [days] --email <address>` | Planifie des analyses locales récurrentes et envoie leurs résultats par e-mail |
| `failproofai audit --status` | Affiche l'adresse du rapport, l'intervalle et la prochaine analyse planifiée |
| `failproofai audit --no-schedule` | Arrête les analyses récurrentes sans supprimer l'historique d'audit |
| `failproofai harness list` | Liste les chemins de capture supplémentaires |
| `failproofai otel status` | Inspecte le [reporting OpenTelemetry](/fr/reference/otel) optionnel |
| `failproofai jev --url <url> --key-stdin` | Configure Jev en une étape ; le fournisseur est déduit de l'hôte de l'URL |
| `failproofai jev setup --provider <kind> --key-stdin` | Laisse [Jev](/fr/reference/jev-providers) juger les appels d'outils via votre propre endpoint et clé |
| `failproofai jev setup --provider failproofai` | Laisse Jev juger les appels d'outils [via FailproofAI Cloud](/fr/reference/jev-cloud), avec la clé Cloud de cette machine |
| `failproofai jev setup --mode <m>` | Change le mode de Jev : `enforce`, `observe`, ou `off` (conserve la config, cesse d'interroger Jev) |
| `failproofai jev status` | Affiche la configuration Jev, ses permissions et les récents replis ; jamais la clé |
| `failproofai jev test` | Envoie une requête Jev en direct et affiche sa latence et sa version ; quitte avec le code 1 si la réponse est en retard pour les hooks ou incorrecte |
| `failproofai jev models` | Liste les identifiants de modèles que `GET <base>/models` indique comme servis par un endpoint |
| `failproofai jev remove` | Désactive Jev ; les hooks exécutent les politiques regex exactement comme avant |
| `failproofai flush --wait` | Livre le spool d'événements actuel |
| `failproofai backfill --since 30d` | Relit l'historique précédemment traité |
| `failproofai config --pause [duration]` | Met en pause une session locale pendant 30 minutes par défaut, jusqu'à 8 heures maximum |
| `failproofai config --resume` | Reprend une session locale en pause ; ajoutez `--all` pour effacer toutes les pauses |
| `failproofai update` | Finalise les migrations de packages et met à jour le daemon |
| `failproofai migrate --dry-run` | Prévisualise ou exécute les migrations de disposition du répertoire personnel en attente |
| `failproofai uninstall` | Supprime les hooks, la compétence `failproofai` et le daemon avant de désinstaller le package |
| `failproofai --version` | Affiche la version du package installé |
| `failproofai --help` | Affiche les commandes et l'utilisation globale |
| `failproofai help <command>` | Affiche les options et exemples d'une commande, identique à `failproofai <command> --help` |

## Options de configuration

| Option | Utilisation |
| --- | --- |
| `--token <key>` | Configure et connecte de manière non interactive ; également lu depuis `FAILPROOFAI_CLOUD_TOKEN` |
| `--oss` | Utilise l'open source sans connexion Cloud ; une connexion existante est conservée telle quelle |
| `--agents <a,b>` | Trace ces agents, ou `all`, sans demander |
| `--url <url>` | Se connecte ailleurs qu'à `app.befailproof.ai` ; également lu depuis `FAILPROOFAI_CLOUD_URL` |
| `--connect <url>` | Enrôlement uniquement, sur une machine déjà configurée. Ignore le daemon et tous les hooks |
| `--machine-id <id>` | Identifiant machine pour `--connect` ; utilise par défaut un ID stable |
| `--machine-label <name>` | Seul, renomme une machine **déjà connectée** ; n'exécute jamais la configuration. Avec `--token`, se connecte sous ce nom ; une clé définie uniquement dans `FAILPROOFAI_CLOUD_TOKEN` ne suffit pas, car `--machine-label` sans `--token` est un renommage. Avec `--oss` ou `--agents`, renomme une machine déjà connectée et est refusé avant la configuration sur une machine qui ne l'est pas : `--oss` ne se connecte jamais, et `--agents` nécessite une clé ou une connexion Cloud interactive |
| `--no-transcripts` | Envoie les décisions sans le contenu des transcriptions, et n'active pas Cloud Jev, qui enverrait chaque appel d'outil vérifié et l'invite récente ; un fichier `jev.json` faisant tourner Jev via FailproofAI Cloud est supprimé |
| `--disconnect` | Arrête les récupérations de politiques Cloud et la livraison d'événements. Supprime également la clé Cloud Jev et un fichier `jev.json` qui nomme FailproofAI Cloud ; votre propre configuration Jev est conservée |
| `--status` | Affiche l'état actuel de la machine |
| `--pause [duration]` | Met en pause la session la plus récente dans le répertoire courant ; accepte des secondes, minutes ou heures, avec une valeur par défaut de 30 minutes |
| `--resume` | Termine une pause correspondante prématurément |
| `--session <id>` | Cible une session explicite pour la mise en pause ou la reprise |
| `--all` | Avec `--resume`, termine toutes les pauses actives |

Les pauses locales suspendent les politiques intégrées, personnalisées, de convention et de pack pour une session. Elles expirent toujours, au plus 8 heures après la première pause d'une exécution, et elles ne désactivent pas les politiques gérées par Cloud ni `block-failproofai-commands`, qui est toujours active et ne peut elle-même être désactivée ni mise en pause. Cette protection refuse les moyens directs par lesquels un agent instrumenté pourrait se mettre lui-même en pause : exécuter `failproofai config --pause`, ou écrire le fichier de pause sous `~/.failproofai/state/sessions/`. Elle lit les commandes, pas ce qu'un script fait lorsqu'il s'exécute, donc un script que l'agent écrit puis exécute peut toujours atteindre le même état. Un fichier de pause est vérifié pour une expiration bornée et un début au plus une minute dans le futur, pas pour savoir qui l'a écrit.

## Options de politique

| Option | Utilisation |
| --- | --- |
| `--install`, `-i` | Installe les hooks du harnais. Les noms qui suivent activent ces politiques ; sans nom, aucun changement de politique |
| `--uninstall`, `-u` | Désactive les politiques ou supprime les hooks |
| `--cli <names...>` | Cible un ou plusieurs harnais pris en charge |
| `--scope user\|project\|local\|all` | Choisit la portée de configuration ; `all` est pour la désinstallation |
| `--beta` | Inclut les politiques bêta |
| `--custom`, `-c <path>` | Avec `--install`, valide et charge un fichier de politique personnalisée ; répétable. `--uninstall -c` supprime tous les fichiers de politique personnalisée |
| `--policy`, `--only <a,b>` | Installe uniquement ces politiques depuis un pack |
| `--category <x,y>` | Installe uniquement ces catégories depuis un pack |
| `--all` | Liste toutes les politiques ; avec un pack, installe l'intégralité |
| `--releases` | Avec `show`, liste les releases d'un pack et celle qui est installée |

## Options de livraison et de maintenance

| Commande | Options |
| --- | --- |
| `backfill` | `--since <30d\|6m\|1y\|YYYY-MM-DD>`, `--agents <a,b>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` (`-y`) |

### Backfill par harnais

`backfill` renvoie l'historique déjà lu par le collecteur, sur une machine connectée au Cloud. `--since` définit la fenêtre pour la plupart des harnais, avec deux exceptions :

- **Goose, OpenCode et Devin** envoient l'intégralité de leur historique, quelle que soit la valeur de `--since` : leur historique réside dans une base de données que le collecteur lit sans fenêtre temporelle, donc `--dry-run` les signale comme toutes les sessions.
- L'historique **Hermes** n'est pas renvoyé par `backfill`.

`failproofai update` doit être exécuté après `npm install -g failproofai@latest` ; il effectue les migrations de disposition du répertoire personnel, installe le binaire daemon correspondant et redémarre le service. Il déplace ensuite chaque profil Hermes utilisant déjà FailproofAI vers le plugin natif lié et affiche une ligne par profil. `--no-daemon` ignore l'étape du daemon. `update` quitte avec un code non nul lorsque le daemon n'a pas pu être remplacé, qu'une migration a échoué, ou qu'un profil Hermes n'a pas pu être migré (par exemple parce que le daemon en cours d'exécution ne peut pas servir le plugin natif, auquel cas ses hooks shell sont conservés).

## Chemins du harnais

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

Les noms de harnais pris en charge sont `claude`, `codex`, `copilot`, `cursor`, `opencode`, `pi`, `hermes`, `openclaw`, `factory`, `devin`, `antigravity`, et `goose`.

Les labels permettent de distinguer les identifiants d'agents dérivés lorsque deux racines contiennent des copies du même projet. Les racines qui se chevauchent et les labels en double sont rejetés pour éviter la collecte en double ou la corruption du curseur. La configuration des chemins supplémentaires se recharge sans redémarrage du daemon.

Les environnements de conteneurs peuvent remplacer les chemins supplémentaires configurés par fichier avec une variable séparée par des virgules nommée `FAILPROOFAI_<HARNESS>_EXTRA_PATHS`, par exemple :

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## Variables d'environnement

Utilisez les fichiers de configuration pour le comportement persistant de la machine. Les variables d'environnement sont plus utiles pour les conteneurs, les tests et les processus individuels.

| Variable | Utilisation |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | La clé Cloud, à la place de `--token`. Préférez cette méthode : un argument est lisible depuis `ps` par tous les utilisateurs. Définissez-la avec `read -s` ou depuis un gestionnaire de secrets CI, jamais en saisissant la clé dans une commande, ce qui la place de toute façon dans l'historique du shell |
| `FAILPROOFAI_CLOUD_URL` | L'URL Cloud, à la place de `--url`. La même variable que lit le daemon |
| `FAILPROOFAI_HOME` | Reloger l'intégralité de la disposition `~/.failproofai` |
| `FAILPROOFAI_LOG_LEVEL` | Définir la verbosité de la journalisation locale |
| `FAILPROOFAI_HOOK_LOG_FILE` | Écrire les diagnostics des hooks dans un fichier sélectionné |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | Désactiver la télémétrie anonyme pour ce processus |
| `FAILPROOFAI_NO_FIRST_RUN=1` | Ignorer la configuration interactive au premier lancement |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | Ignorer l'audit local post-configuration |
| `FAILPROOFAI_LLM_BASE_URL` | Remplacer l'endpoint compatible OpenAI utilisé par les politiques LLM |
| `FAILPROOFAI_LLM_API_KEY` | Fournir la clé API utilisée par les politiques LLM |
| `FAILPROOFAI_LLM_MODEL` | Sélectionner le modèle utilisé par les politiques LLM |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | Limiter le chargement des modules de politique personnalisée |
| `FAILPROOFAI_NO_DOWNLOAD=1` | Refuser de récupérer des packs et des binaires daemon ; ce qui est installé continue d'appliquer les politiques |
| `FAILPROOFAI_PACK_BASE_URL` | Récupérer les packs depuis un miroir à la place de `github.com` |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | Remplacer les chemins de capture supplémentaires configurés pour un harnais |
| `NO_COLOR` | Désactiver la sortie terminal en couleur |

Les variables de répertoire personnel spécifiques aux agents, telles que `CLAUDE_PROJECTS_PATH`, `CURSOR_HOME`, `HERMES_HOME` et `OPENCLAW_HOME`, remplacent l'emplacement où Failproof AI découvre les sessions locales pour ce harnais.

## Mettre en pause ou supprimer une machine en toute sécurité

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

Une pause de session locale ne désactive pas les politiques gérées par Cloud. Restaurez les déploiements Cloud depuis **fix → deploy policies** dans Cloud lorsque le déploiement lui-même est en cause.

Avant de supprimer le package npm, supprimez les hooks installés et le daemon :

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

Exécutez `failproofai <command> --help` pour des détails spécifiques à la version.

<Warning>
  Exécutez `failproofai uninstall` avant `npm rm -g failproofai` ; npm ne supprime pas les hooks d'agents installés, la compétence `failproofai` ni le service daemon.
</Warning>
