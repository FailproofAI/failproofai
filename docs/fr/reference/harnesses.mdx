Un harnais est l'environnement dans lequel votre agent s'exécute réellement. Failproof AI en prend en charge douze, répartis en deux catégories :

- **CLI de codage** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Passerelles de chat et d'assistant** (2) — Hermes (Slack, Telegram, cron), OpenClaw (assistant auto-hébergé)

Les mêmes politiques et le même historique de session s'appliquent quel que soit le harnais utilisé par un agent. Une couche d'adaptation unique mappe les noms d'événements natifs, les noms d'outils et les champs d'entrée d'outils de chaque harnais sur 29 événements canoniques avant l'exécution de toute politique.

Un agent qui ne s'exécute dans **aucun** des douze harnais est instrumenté directement avec le [SDK Python](/fr/reference/custom-agents). Il s'agit d'un contrat différent, qu'il convient d'énoncer clairement : le SDK fournit le traçage, les sessions, les évaluations et les audits — **il n'applique pas les politiques de lui-même.** Bloquer une action non sécurisée avant son exécution nécessite un hook d'application au niveau de la frontière d'outil de votre runtime ; [contactez-nous](mailto:support@befailproof.ai) et nous nous chargerons du mapping.

## Portées des hooks

| Harnais | Portées de hook prises en charge |
| --- | --- |
| Claude Code | Utilisateur, projet, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | Utilisateur, projet |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | Utilisateur, projet |
| Hermes, OpenClaw | Utilisateur |

Claude Code est le seul harnais disposant d'une portée **locale**. Hermes et OpenClaw n'ont aucune configuration de projet — ils fonctionnent uniquement en portée utilisateur, et le CLI refuse `--scope project` pour eux.

Chaque intégration normalise les noms d'événements de hook natifs, les noms d'outils et les champs d'entrée d'outils avant l'exécution des politiques. Une politique ne peut agir que sur les événements que le harnais expose ; testez le comportement de fin de tour et des instructions sur le harnais exact et la version que vous déployez.

## Capacité d'application

« Bloquer » signifie que le verdict retourné par l'adaptateur actuel est consommé par le harnais désigné. Le blocage post-outil peut remplacer le résultat présenté au modèle, mais ne peut pas annuler un effet de bord d'outil qui s'est déjà produit.

| Harnais | Événements de blocage vérifiés | Remarques d'observation seule ou de non-blocage |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact` et plusieurs événements de tâche/configuration | `PostToolUse`, le cycle de vie des sessions, les notifications et les événements post-échec sont observationnels. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Le blocage post-outil remplace le résultat après exécution ; les événements de démarrage de session et de compactage sont observationnels dans l'adaptateur actuel. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Le blocage post-outil remplace le résultat après exécution ; les événements de session et de notification sont observationnels. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` et les événements de session sont observationnels. |
| OpenCode | `PreToolUse` | Les événements post-outil et de cycle de vie sont observationnels ; la gestion actuelle des arrêts constitue une guidance pour un tour ultérieur plutôt qu'une barrière vérifiée. `PermissionRequest` ne s'exécute jamais. |
| Pi | `PreToolUse`, `UserPromptSubmit` | Les événements post-outil et de cycle de vie sont observationnels ; la guidance d'arrêt s'applique à un tour ultérieur. |
| Hermes | `PreToolUse` | Les verdicts post-outil, de session et d'arrêt de sous-agent ne sont pas des barrières. Aucun événement `Stop` n'est installé. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Les événements post-outil, de session, d'arrêt de sous-agent et de compactage sont observationnels. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Les verdicts post-outil et d'arrêt de sous-agent sont observationnels. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PermissionRequest` conditionnel | Les hooks de permission ne s'exécutent pas dans tous les modes de permission ; les événements post-outil et de session sont observationnels. |
| Antigravity CLI | `PreToolUse`, `Stop` | Les verdicts d'invite utilisateur et post-outil sont observationnels ; les instructions d'invite peuvent toujours être injectées. |
| Goose | `PreToolUse` | Les événements d'invite utilisateur, post-outil et de session sont observationnels. Un hook d'arrêt bloquant natif existe en amont mais n'est pas installé par l'adaptateur actuel. |

Un événement absent des deux colonnes n'est **pas vérifié** — traitez-le comme inconnu, jamais comme bloquant.

### Conditions sur une barrière répertoriée

Plusieurs lignes ci-dessus sont de vraies barrières qui sont néanmoins limitées ou conditionnelles. Une politique qui dépend de l'une d'elles a autant besoin de la condition que de la ligne elle-même.

| Harnais | Événement | Condition |
| --- | --- | --- |
| Claude Code | `Stop`, `SubagentStop` | Plafonné par `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`, par défaut 8. Ignoré sur les chemins de fin de tour |
| Cursor | `Stop` | Plafonné par `loop_limit`, par défaut 5, et consommé uniquement à la fin du tour — une interruption utilisateur ou une erreur de tour le rejette |
| Cursor | `Stop` | **Les VM Cursor Cloud Agent n'exécutent aucun hook `stop` ni `subagentStop`.** La barrière couvre uniquement les sessions locales |
| Codex | `SubagentStop` | Seuls les sous-agents ThreadSpawn le déclenchent ; toutes les autres sources de sous-agents n'exécutent jamais le hook |
| GitHub Copilot CLI | `SubagentStop` | Ignoré entièrement pour les sous-agents `isSidekick` |
| Devin CLI | `PermissionRequest` | Ne se déclenche jamais sous `--permission-mode dangerous`, ni pour les outils en lecture seule approuvés automatiquement |
| OpenCode | `PermissionRequest` | Hook mort : `permission.ask` est déclaré et documenté en amont mais jamais invoqué, donc la politique ne s'exécute même pas |
| Hermes | `Stop` | Aucun événement `Stop` n'est installé, par choix. Les cinq builtins `require-*-before-stop` ne sont pas applicables sur Hermes |
| Goose | `Stop` | Même résultat : aucun `Stop` n'est installé, donc les cinq builtins `require-*-before-stop` ne sont pas applicables |

### Cas de dégradation de `instruct()`

`deny` n'est pas le seul verdict qu'une politique peut retourner. `instruct()` transmet une directive à l'agent et laisse l'action se poursuivre — mais tous les harnais ne disposent pas d'un canal pour la véhiculer. Lorsqu'il n'en existe pas, failproofai autorise l'action et écrit l'instruction sur stderr pour les journaux de l'opérateur ; le modèle ne la voit jamais.

| Harnais | Événements où `instruct()` se dégrade en note sur stderr |
| --- | --- |
| Hermes | Tous les événements |
| Goose | Tous les événements |
| Pi | Tous les événements sauf `Stop` |
| OpenClaw | Tous les événements sauf `Stop` |
| Factory Droid | Tous les événements sauf `Stop` |
| Antigravity CLI | Tous les événements sauf `Stop` et `UserPromptSubmit` |

Partout ailleurs, l'instruction est retournée via le canal de contexte additionnel propre au harnais.

## Mode agent VS Code

Le mode agent Copilot Chat intégré à VS Code n'est **pas une treizième intégration**. Il découvre la configuration des hooks depuis `.github/hooks/*.json`, `~/.copilot/hooks/*.json` et `~/.claude/settings.json` — exactement les chemins que les installations `copilot` et `claude` écrivent déjà — et utilise le même contrat de refus de type Claude. L'installation de l'un ou l'autre applique déjà les politiques dans les sessions en mode agent de VS Code.

Cette fonctionnalité est en préversion et nécessite un abonnement GitHub Copilot actif ainsi que le mode agent.

## Installer les hooks de capture et de politique

<Tabs>
  <Tab title="Tableau de bord">
    1. Ouvrez **Administration → Clés** et créez une clé avec `events:add` et `policies:pull`, nommée d'après la machine ou l'environnement.
    2. Sur la machine cible, connectez le CLI local avec la clé affichée.
    3. Démarrez une nouvelle session d'agent, puis confirmez ses événements de hook et de session sous **Observer → Événements**.
    4. Ouvrez **Observer → politique** pour la même fenêtre temporelle et confirmez qu'une décision de politique est attribuée à la machine.

    La connexion démarre avec une clé machine. Confirmez qu'elle inclut les permissions d'ingestion et de distribution de politiques avant de copier son secret.

    ![Le tiroir de nouvelle clé API utilisé pour accorder les permissions d'ingestion d'événements et de distribution de politiques.](/images/dashboard/key-create.png)

    Après l'installation des hooks, le flux d'événements devrait afficher de nouveaux événements en provenance de la machine et de l'environnement connectés.

    ![Le flux d'événements en direct utilisé pour confirmer qu'un harnais nouvellement installé envoie bien des données.](/images/dashboard/events-stream.png)

    Enfin, vérifiez que les décisions de politique sont attribuées à la même machine. Cela confirme que le harnais rapporte à la fois l'activité de politique et les événements de trace.

    ![La page Politique utilisée pour vérifier les décisions de politique d'un harnais nouvellement connecté.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    `failproofai config` connecte les hooks à chaque CLI d'agent pris en charge qu'il trouve, installe le daemon et se connecte au Cloud lorsqu'une clé est présente :

    ```bash
    failproofai config --token <machine-key>
    failproofai policies add FailproofAI/policies
    ```

    La configuration ne choisit aucune politique par défaut, d'où la présence de la deuxième commande.

    Pour connecter un seul harnais manuellement — sans `--cli`, `--install` détecte ce qui est installé et propose un choix :

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    La portée projet conserve la configuration des hooks avec un dépôt. La portée utilisateur couvre le travail sur plusieurs dépôts. Consultez le tableau des portées ci-dessus avant de combiner `--cli` et `--scope` ; le CLI rejette une combinaison non prise en charge.

    Vérifiez la machine et ses événements :

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

<Warning>
  Dans les exécutions headless `copilot -p` lancées depuis un répertoire vierge, le fichier `.github/hooks/failproofai.json` de portée projet n'a **pas** été chargé. Considérez la portée utilisateur comme le point d'application fiable pour Copilot en CI, jusqu'à vérification contraire.
</Warning>

## Ajouter un chemin de session non par défaut

<Tabs>
  <Tab title="Tableau de bord">
    Les chemins supplémentaires sont enregistrés sur la machine, pas dans le Cloud. Après en avoir ajouté un, ouvrez **Observer → Sessions**, filtrez par l'environnement de la machine et confirmez que les sessions du nouveau chemin apparaissent. Ouvrez une session et vérifiez l'agent, le harnais et les horodatages des événements avant de l'utiliser dans un audit.

    ![La liste des sessions filtrée par l'environnement recevant des données du chemin de capture supplémentaire.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Ajoutez un chemin avec un label optionnel, puis inspectez les chemins configurés :

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Supprimez un chemin avec `failproofai harness remove-path claude checkout`.

    Le label espace de noms les identifiants d'agent dérivés. Deux emplacements contenant des copies du même projet dérivent le même identifiant à partir de la transcription ; sans label, ils fusionnent en un seul agent. Les racines qui se chevauchent et les labels en double sont refusés — consultez [la référence CLI](/fr/reference/failproof-cli) pour comprendre chaque motif de rejet.
  </Tab>
</Tabs>

<Tip>
  Exécutez une nouvelle session après l'installation. Vérifiez à la fois le flux d'événements en direct et une décision de politique effective avant d'élargir le déploiement.
</Tip>
