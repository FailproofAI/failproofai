Un harnais est l'environnement dans lequel votre agent s'exécute réellement. Failproof AI en prend en charge douze, répartis en deux catégories :

- **CLI de codage** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Passerelles de chat et d'assistant** (2) — Hermes (Slack, Telegram, cron), OpenClaw (assistant auto-hébergé)

Les mêmes politiques et le même historique de session s'appliquent quel que soit le harnais utilisé par l'agent. Une couche d'adaptation unique mappe les noms d'événements natifs, les noms d'outils et les champs d'entrée d'outils de chaque harnais vers 29 événements canoniques, avant toute exécution de politique.

Un agent qui ne s'exécute dans **aucun** des douze harnais est instrumenté directement avec le [SDK Python](/fr/reference/custom-agents). Il s'agit d'un contrat différent, qu'il convient d'énoncer clairement : le SDK fournit le traçage, les sessions, les évaluations et les audits — **il n'applique pas les politiques par lui-même.** Bloquer une action non sûre avant son exécution nécessite un hook d'application à la frontière des outils de votre environnement d'exécution ; [contactez-nous](mailto:support@befailproof.ai) et nous l'adapterons.

| Harnais | Périmètres de hook pris en charge |
| --- | --- |
| Claude Code | Utilisateur, projet, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | Utilisateur, projet |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | Utilisateur, projet |
| Hermes, OpenClaw | Utilisateur |

Chaque intégration normalise ses noms d'événements de hook natifs, ses noms d'outils et ses champs d'entrée d'outils avant l'exécution des politiques. Une politique ne peut agir que sur les événements exposés par le harnais ; testez le comportement en fin de tour et en matière d'instructions sur le harnais et la version exacts que vous déployez.

## Capacités d'application

« Bloquer » signifie que le verdict retourné par l'adaptateur actuel est consommé par le harnais désigné. Le blocage post-outil peut remplacer le résultat présenté au modèle, mais ne peut pas annuler un effet de bord d'outil déjà survenu.

| Harnais | Événements de blocage vérifiés | Mises en garde observationnelles ou non bloquantes |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact`, et plusieurs événements de tâche/configuration | `PostToolUse`, le cycle de vie de session, les notifications et les événements post-échec sont observationnels. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Le blocage post-outil remplace le résultat après exécution ; les événements de démarrage de session et de compaction sont observationnels dans l'adaptateur actuel. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Le blocage post-outil remplace le résultat après exécution ; les événements de session et de notification sont observationnels. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` et les événements de session sont observationnels. |
| OpenCode | `PreToolUse` | Les événements post-outil et de cycle de vie sont observationnels ; la gestion des arrêts actuelle constitue une orientation pour un tour ultérieur plutôt qu'une véritable barrière. |
| Pi | `PreToolUse`, `UserPromptSubmit` | Les événements post-outil et de cycle de vie sont observationnels ; l'orientation d'arrêt s'applique à un tour ultérieur. |
| Hermes | `PreToolUse` | `deny()` bloque. `instruct()` n'arrête pas l'appel : il s'exécute, et l'orientation est placée au début de son résultat. Les verdicts post-outil, de session et d'arrêt de sous-agent ne sont pas des barrières. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Les événements post-outil, de session, d'arrêt de sous-agent et de compaction sont observationnels. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Les verdicts post-outil et d'arrêt de sous-agent sont observationnels. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PermissionRequest` conditionnel | Les hooks de permission ne s'exécutent pas dans tous les modes de permission ; les événements post-outil et de session sont observationnels. |
| Antigravity CLI | `PreToolUse`, `Stop` | Les verdicts de prompt utilisateur et post-outil sont observationnels ; les instructions de prompt peuvent toutefois être injectées. |
| Goose | `PreToolUse` | Les événements de prompt utilisateur, post-outil et de session sont observationnels. Un hook d'arrêt bloquant natif existe en amont, mais n'est pas installé par l'adaptateur actuel. |

Les capacités sont sensibles aux versions. Effectuez de nouveaux tests après la mise à niveau d'un CLI d'agent, en particulier lorsqu'une politique repose sur le comportement du prompt, de l'arrêt, de la permission ou post-outil plutôt que sur la barrière pré-outil commune.

### Plugin natif Hermes

Hermes est intégré via un plugin natif local au profil plutôt que par une commande shell. L'installation relie le répertoire `plugins/failproofai` de chaque profil Hermes par défaut et nommé au plugin fourni dans le package npm (une copie lorsqu'un lien symbolique ne peut pas être créé), l'active dans le `config.yaml` de ce profil, et migre uniquement les entrées de hooks shell FailproofAI héritées. Comme le plugin est lié, `npm install -g failproofai@latest` le met à jour sans réinstallation. Cela évite de créer un processus fils à chaque hook. Le plugin prend en charge Hermes 0.20.0 et versions ultérieures.

Les hooks shell hérités (installés par la version 1.0.5 et antérieures) ne vérifient **pas** les tâches cron Hermes : chaque exécution cron construit son propre périmètre de hook, auquel le plugin natif se joint, contrairement aux hooks shell `config.yaml`. `failproofai update` migre chaque profil utilisant déjà FailproofAI vers le plugin lié. Si le démon en cours d'exécution ne peut pas servir le plugin, `update` laisse les hooks shell en place et se termine avec un code non nul ; exécutez `failproofai config` pour mettre à jour le démon, puis `failproofai update` à nouveau. Les tâches cron chargent le plugin à leur prochaine exécution ; redémarrez les passerelles en cours d'exécution et les sessions interactives pour le charger dans celles-ci.

Sur Hermes, `deny()` bloque l'appel et `instruct()` ne le fait pas : l'appel s'exécute, et l'orientation est placée au début de son résultat — en tant que première clé, `failproof_policy_reminder`, d'un résultat JSON, ou sous forme d'une ligne `[FailproofAI policy reminder (...)]` en tête — afin que le modèle la lise avec la sortie, et que les scripts qui analysent le résultat continuent de fonctionner. Le rappel d'une politique est affiché une fois par tour, et reste court pour un résultat volumineux. Utilisez `deny()` lorsqu'une action ne doit absolument pas se produire : `instruct()` n'arrête plus l'action au préalable. Les appels d'outils effectués depuis un script `execute_code` placent leur rappel sur le résultat `execute_code` que le modèle lit ; la propre copie du résultat du script reste intacte. Le modèle est invité à ne jamais citer un rappel dans ses réponses.

Une version de Hermes sans middleware de plugin se replie sur une mise en attente unique de l'appel correspondant avec le message « FailproofAI policy guidance » ; la réponse suivante du modèle peut le répéter, ou effectuer le même travail avec un autre outil, sans être mise en attente à nouveau.

Les noms d'outils sont mis en correspondance entre les versions de Hermes : `process_manage`, `cronjob_manage` et `todo_list` (Hermes 0.21) sont traités comme `process`, `cronjob` et `todo` (Hermes 0.20). Chaque fois que Hermes charge le plugin, il écrit `heartbeat.json` dans le répertoire `plugin-data/agent-plugin-failproofai-5296f299/` du profil, en enregistrant la version de Hermes, le chemin et la version du plugin, ainsi que les hooks acceptés par Hermes. Exécutez `failproofai config --status` pour détecter un profil désactivé, incomplet, dupliqué ou récemment non configuré, ou encore un profil toujours sur les hooks shell hérités (signalé comme « Hermes cron jobs are not checked »).

### Plugin OpenClaw

OpenClaw charge FailproofAI en tant que plugin de passerelle en cours de processus, enregistré dans le fichier `openclaw.json` de chaque profil. Comme le plugin Hermes, il interroge le démon `failproofaid` local pour chaque verdict via son socket, ce qui nécessite un démon en cours d'exécution : l'installation échoue sans lui, et si le démon ne répond pas, les appels d'outils et les prompts sont bloqués, et la raison est écrite dans le journal de la passerelle. Après `npm install -g failproofai@latest`, redémarrez la passerelle OpenClaw afin qu'elle charge le plugin mis à jour.

### Approbation des hooks Codex

Codex 0.129 et versions ultérieures n'exécute un hook de `~/.codex/hooks.json` qu'après votre approbation dans `codex` interactif (« Review hooks ») ; jusqu'alors, chaque session Codex — y compris `codex exec` sans tête — le ignore. Les hooks dans la configuration système de Codex, `/etc/codex/config.toml` sur Linux et macOS, s'exécutent sans cette approbation.

Ainsi, lorsque `failproofai config` (ou `policies --install --cli codex` au périmètre utilisateur) peut utiliser sudo, il écrit les hooks Codex dans `/etc/codex/config.toml`, entre `# >>> failproofai managed hooks >>>` et `# <<< failproofai managed hooks <<<`, en laissant le reste du fichier tel quel.

Ce fichier s'applique à tous les comptes de la machine, donc chaque hook qu'il contient exécute `/opt/failproofai-codex/codex-hook`, un court script appartenant à root. Le script transmet l'événement au failproofai propre à chaque compte, pour chaque compte ayant configuré les hooks à cet endroit, et ne fait rien pour les autres comptes. Un autre compte souhaitant les hooks Codex de failproofai les configure pour lui-même.

Avant d'écrire le bloc, et à chaque `failproofai update`, failproofai vérifie que `/etc/codex/config.toml` lui-même, le script, chaque répertoire au-dessus d'eux, ainsi que les commandes `sh`, `id` et `cat` qu'il exécute appartiennent à root et ne peuvent être écrits par personne d'autre, et que le failproofai de chaque compte appartient à ce compte ou à root. Lors de l'installation, si cette vérification échoue, vos hooks restent dans `~/.codex/hooks.json`. Lors d'une mise à jour, un script qui échoue à cette vérification est retiré du bloc, et un compte dont le failproofai échoue est retiré du script ; exécutez à nouveau `failproofai config` une fois le problème corrigé. `failproofai update` réécrit également un bloc écrit par une version antérieure pour utiliser le script, ce qui nécessite sudo.

`failproofai uninstall` et la désactivation de Codex dans `failproofai config` retirent votre compte, et le bloc avec lui une fois qu'il ne reste plus aucun compte.

Sans sudo, et sur Windows, les hooks restent dans `~/.codex/hooks.json`. `failproofai config` et `failproofai config --status` ne considèrent alors pas Codex comme appliquant les politiques tant que les hooks ne sont pas approuvés, et indiquent comment corriger cela : réexécutez `failproofai config` en autorisant sudo, ou ouvrez `codex` une fois et approuvez les hooks.

## Installer les hooks de capture et de politique

<Tabs>
  <Tab title="Tableau de bord">
    1. Ouvrez **paramètres → clés API** et créez une clé avec `events:add` et `policies:pull`, nommée pour la machine ou l'environnement.
    2. Sur la machine cible, connectez le CLI local avec la clé affichée et installez les hooks du harnais.
    3. Démarrez une nouvelle session d'agent, puis confirmez ses événements de hook et de session sous **trace → événements en direct**.
    4. Ouvrez **fix → activité** pour la même fenêtre temporelle et confirmez qu'une décision de politique est attribuée à la machine.

    La connexion démarre avec une clé machine. Vérifiez qu'elle inclut à la fois les permissions d'ingestion et de livraison de politique avant de copier son secret.

    ![Le tiroir de création de clé API utilisé pour accorder les permissions d'ingestion d'événements et de livraison de politique.](/images/dashboard/key-create.png)

    Après l'installation des hooks, le flux d'événements devrait afficher de nouveaux événements provenant de la machine et de l'environnement connectés.

    ![Le flux d'événements en direct utilisé pour confirmer qu'un harnais nouvellement installé signale bien des données.](/images/dashboard/events-stream.png)

    Enfin, vérifiez que les décisions de politique sont attribuées à la même machine. Cela confirme que le harnais signale bien l'activité de politique ainsi que les événements de trace.

    ![La page de politique utilisée pour vérifier les décisions de politique d'un harnais nouvellement connecté.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Lisez la clé machine dans le shell. `read -s` la demande à une invite qui n'affiche pas la saisie, elle n'apparaît donc jamais dans une commande ni dans l'historique du shell :

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    Configurez ensuite la machine — cette commande câble les hooks pour chaque harnais détecté, installe le démon et se connecte au Cloud :

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    La configuration n'active aucune politique par elle-même, c'est à cela que sert la seconde commande.

    Ou ciblez des harnais spécifiques et un périmètre de configuration :

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    Le périmètre projet conserve la configuration des hooks avec un dépôt. Le périmètre utilisateur couvre le travail sur plusieurs dépôts. Claude Code prend également en charge le périmètre local ; la prise en charge varie selon le harnais et le CLI rejette les combinaisons non prises en charge.

    Vérifiez la machine et ses événements :

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## Ajouter un chemin de session non standard

<Tabs>
  <Tab title="Tableau de bord">
    Les chemins supplémentaires sont enregistrés sur la machine, pas dans le Cloud. Après en avoir ajouté un, ouvrez **trace → sessions**, filtrez sur l'environnement de la machine et confirmez que les sessions du nouveau chemin apparaissent. Ouvrez une session et vérifiez l'agent, le harnais et les horodatages des événements avant de vous y fier dans un audit.

    ![La liste des sessions filtrée sur l'environnement recevant des données du chemin de capture supplémentaire.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Ajoutez un chemin avec un libellé optionnel, puis inspectez les chemins configurés :

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Supprimez un chemin avec `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  Exécutez une nouvelle session après l'installation. Vérifiez à la fois le flux d'événements en direct et une décision de politique effective avant d'élargir le déploiement.
</Tip>
