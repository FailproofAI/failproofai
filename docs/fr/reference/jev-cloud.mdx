Ceci est la référence de la route Cloud pour les [politiques Jev](/fr/policies/jev). Jev, le classificateur de TypeSafe, analyse chaque appel d'outil par rapport à ce que vous avez réellement demandé et répond conjointement avec vos politiques, sans jamais les remplacer. Via **FailproofAI Cloud**, une machine connectée utilise Jev avec la même clé qu'elle utilise déjà pour se connecter : pas de compte TypeSafe, pas de seconde clé, pas d'endpoint à configurer. Chaque appel est débité sur l'enveloppe du plan existant de votre organisation.

Tout ce que fait Jev reste identique à la [configuration avec votre propre clé](/fr/reference/jev-providers) : les politiques strictes restent définitives, le refus d'une politique révisable n'est levé que lorsque Jev a été interrogé précisément sur cette préoccupation, et tout échec revient au résultat regex pour cet appel.

<Note>
Nécessite **failproofai 1.0.8-beta.0** ou une version ultérieure. La version 1.0.7 ne dispose pas de Jev, même si elle apparaît au-dessus des versions 1.0.7 bêta dans le tri. Sans configuration Jev, rien ne change : les hooks exécutent les politiques regex exactement comme ils l'ont toujours fait.
</Note>

## Avant de commencer

Installez Failproof AI sur la machine où votre agent s'exécute et attachez ses hooks à un [harness supporté](/fr/reference/harnesses). Si vous partez de zéro, suivez le [démarrage rapide](/fr/start/quickstart) jusqu'à l'installation des hooks. Vérifiez la version de la CLI installée avec `failproofai --version` ; mettez-la à jour si elle est antérieure à Jev. Vous avez également besoin d'accéder à la page **paramètres → clés API** de votre organisation pour créer une clé machine.

Jev examine les appels d'outils nommés à la porte `PreToolUse` ou `PermissionRequest`. Il n'examine pas chaque événement d'une session. Pour voir Jev lever un refus de politique, vous devez avoir une politique installée marquée comme [révisable](/fr/policies/authority) ; tous les autres refus de politique restent définitifs.

## Activation

1. **Créez une clé avec Jev.** Dans le tableau de bord FailproofAI Cloud, ouvrez **paramètres → clés API** et, dans le formulaire **nouvelle clé**, choisissez **une machine exécutant failproofai**. Cela accorde les trois permissions dont une machine a besoin : `events:add` (envoi d'activité), `policies:pull` (réception des politiques) et `jev:evaluate` (Jev, débité sur le plan de votre organisation). Une clé ne peut pas porter `jev:evaluate` sans les deux autres.
2. **Connectez la machine** avec cette clé. Lisez son secret à usage unique à l'invite, puis exécutez la commande de configuration complète :

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` installe le daemon, attache les hooks pour les CLI d'agents qu'il trouve et connecte la machine. La variable d'environnement permet de ne pas exposer la clé dans les arguments de la commande ni dans l'historique de votre shell. Si votre harness a été installé ultérieurement, [attachez-le explicitement](/fr/start/quickstart).

   Si votre organisation exploite sa propre instance FailproofAI Cloud plutôt que la version hébergée, ajoutez son adresse : `--url https://<votre hôte de tableau de bord>` (ou exportez `FAILPROOFAI_CLOUD_URL`). Sans cela, la clé est vérifiée auprès du service hébergé et la connexion échoue. Si le certificat de cet hôte provient d'une CA privée, installez la CA dans le magasin de confiance système de la machine (par exemple avec `update-ca-certificates`), et pas uniquement dans `NODE_EXTRA_CA_CERTS` : le daemon qui envoie les événements et récupère les politiques lit le magasin système. Consultez la section [Dépannage](/fr/reference/troubleshooting).

C'est tout. La connexion stocke la clé et, lorsque la machine ne dispose **pas encore** de configuration Jev, en écrit une pour FailproofAI Cloud. Dès le premier déploiement de la machine (en moins de 30 s environ), FailproofAI Cloud définit le mode : `enforce` lorsqu'une politique Jev est déployée dessus, `off` lorsqu'aucune ne l'est (voir [Qui définit le mode](#who-sets-the-mode)). La sortie l'indique :

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Les vérifications déployées par FailproofAI Cloud s'exécutent sur Cloud. Pour ajouter vos propres vérifications sur la machine, installez un pack :

```bash
failproofai policies add FailproofAI/jev-policies
```

**Avec `--no-transcripts`, la connexion n'active pas Jev.** Jev envoie chaque appel d'outil examiné ainsi que l'invite récente à FailproofAI Cloud, ce qui représente plus qu'une connexion en mode décisions uniquement. La clé est quand même stockée, et la sortie indique que Jev est disponible et comment l'activer :

```bash
failproofai jev setup --provider failproofai
```

Cela désactive également Jev via FailproofAI Cloud. Un `jev.json` qui fait fonctionner Jev via FailproofAI Cloud (laissé par une connexion antérieure avec les transcripts activés) est supprimé, selon la même règle utilisée par `config --disconnect`, et la sortie indique que Jev via FailproofAI Cloud reste désactivé sur cette machine. Un `jev.json` pointant vers votre propre endpoint Jev est conservé tel quel, tout comme un `jev.json` FailproofAI Cloud que vous avez désactivé (`--mode off`).

<Warning>
La connexion **n'écrase jamais** un `~/.failproofai/jev.json` existant. Si vous utilisez déjà votre propre endpoint Jev, il continue d'être utilisé, et la sortie indique que le fichier a été laissé tel que configuré — et, lorsque ce fichier laisse Jev désactivé (refusé ou désactivé manuellement), l'indique et explique comment y remédier. Pour faire basculer cette machine vers FailproofAI Cloud, exécutez `failproofai jev setup --provider failproofai`.
</Warning>

## Qui définit le mode

Sur une machine connectée à FailproofAI Cloud, **c'est FailproofAI Cloud qui définit le mode Jev** ; rien sur la machine ne le fait :

- `enforce` tant qu'une politique Jev (ou regex + Jev) est déployée sur la machine : chaque appel d'outil examiné provenant d'un agent ciblé par l'une de ces politiques est envoyé à FailproofAI Cloud, qui applique ses vérifications conjointement avec celles des packs installés localement. Un appel provenant d'un agent qu'aucune politique Jev Cloud ne cible, et sans vérification de pack propre, n'est pas envoyé du tout. En mode `enforce`, les vérifications de refus propres à Jev bloquent les appels mais aussi lèvent les verdicts regex qu'elles examinent.
- `off` lorsqu'aucune n'est déployée : pas de Jev du tout, quoi qu'indique `jev.json`.

Pour tester une politique Jev avant qu'elle n'agisse, déployez-la avec l'effet **observe** : ses vérifications sont toujours effectuées, et ce qu'elles auraient fait est enregistré comme **would-have** sous **fix → activity**, mais elle ne bloque jamais un appel et n'en lève aucun. `failproofai jev setup --mode` et le commutateur **Paramètres → Jev** du tableau de bord local indiquent que le mode est géré par FailproofAI Cloud et ne modifient rien. `jev.json` n'est pas utilisé pour les vérifications Cloud, même s'il nomme un autre fournisseur. `failproofai config --disconnect` restitue la gestion de Jev au `jev.json` propre à la machine.

`failproofai jev status` indique alors `Jev checks run on FailproofAI Cloud (mode: enforce)`. Il liste également les vérifications qui examinent chaque politique `both`. La page de flotte indique pourquoi une machine ayant un mode ne peut pas interroger :

- `transcripts_disabled` : la machine a été connectée avec `--no-transcripts`, ce qui n'active jamais Jev.
- `jev_unconfigured` : la clé de la machine ne porte pas `jev:evaluate`.
- `jev_rate_limited` : FailproofAI Cloud a refusé certains appels de la machine en raison de la limite de débit Jev de l'organisation, et ces appels ont été traités par les seules politiques regex.
- `jev_unavailable` : plusieurs appels consécutifs ont échoué, la machine suspend donc les interrogations de Jev via FailproofAI Cloud pendant une minute à la fois. Elle réessaie automatiquement.

Si FailproofAI Cloud ne répond pas dans les 5 secondes, les politiques regex décident seules, comme pour toute panne Jev. Après 3 échecs consécutifs, la machine cesse d'interroger pendant une minute à la fois, afin qu'une panne Cloud ne ralentisse pas chaque appel d'outil.

Une pause de session (`failproofai config --pause`) n'arrête pas les vérifications Jev de FailproofAI Cloud, tout comme elle n'arrête pas les politiques gérées par Cloud. Elle met en pause les vérifications Jev des packs installés sur la machine.

## Vérifier son fonctionnement

```bash
failproofai jev status
failproofai jev test
```

`status` affiche le fournisseur comme **FailproofAI Cloud**, l'hôte Cloud auquel la machine est connectée, le mode, et la source de la clé comme **connexion FailproofAI Cloud**, jamais la clé elle-même. Lorsqu'un `jev.json` FailproofAI Cloud est en place mais que Jev ne peut pas s'exécuter, il en indique la raison :

| Ce que dit `status` | `status --json` | Signification |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | La machine est connectée, mais aucune clé Jev n'est stockée pour elle : la clé ne porte pas `jev:evaluate`, ou la connexion n'a pas pu le confirmer. Exécutez à nouveau `failproofai config` avec la clé dans `FAILPROOFAI_CLOUD_TOKEN` ; si elle ne dispose pas de la permission, utilisez une clé **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Il n'y a pas de connexion FailproofAI Cloud sur cette machine à laquelle rattacher la clé Jev. |

Après `failproofai config --disconnect`, il n'y a plus de `jev.json` FailproofAI Cloud (sauf s'il avait été désactivé, auquel cas il est conservé), donc `status` signale simplement Jev comme désactivé. `status --json` porte les mêmes informations (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), y compris lorsque la configuration est absente ou refusée. `permissions` correspond toujours à celles de `jev.json` ; un refus concernant `credentials.json` ajoute `credentialsPermissions`, et `fix` lorsqu'une commande permet de le corriger. `test` envoie une requête en direct et rapporte sa latence ainsi que la version de Jev qui a répondu. Il se termine avec le code 1, et l'indique dans son titre, lorsque la réponse arrive après le délai d'expiration du hook (les hooks enregistreraient `timeout`) ou répond incorrectement à sa question de vérification.

Le panneau **Paramètres → Jev** du tableau de bord local affiche également la **connexion FailproofAI Cloud** : l'organisation dans laquelle la machine est enregistrée et si sa clé porte Jev. Ces informations sont lues depuis les fichiers propres à la machine, sans appel réseau.

## Vérifier un appel réel

Démarrez une nouvelle session dans l'agent avec les hooks. Demandez-lui d'utiliser son outil de lecture de fichiers sur `README.md` et de rapporter le titre. Confirmez que la session contient cet appel d'outil, puis exécutez à nouveau `failproofai jev status` : son compteur d'appels récemment évalués devrait augmenter. Ouvrez **Politiques → Activité** dans le [tableau de bord local](/fr/reference/local-dashboard#review-policy-activity) pour inspecter le verdict Jev et le mode de cet appel. Dans Cloud, **fix → activity** affiche les résultats Jev pour l'activité transmise. En mode observe, le verdict est enregistré comme **would-have** et le résultat de la politique décide toujours de l'appel. Une levée n'apparaît que lorsqu'une politique révisable a correspondu et que Jev a levé ses vérifications nommées.

## Ce qui apparaît sur la page des politiques

La machine envoie déjà son activité de hook à FailproofAI Cloud (`events:add`). Avec Jev activé, l'enregistrement de chaque appel filtré indique également quel évaluateur a été utilisé, ce que Jev a décidé, quelles politiques il a levées, pourquoi il est revenu en arrière le cas échéant, sa latence et le modèle qui a répondu — des décisions, des codes et des noms, jamais la commande ni votre invite. Dans Cloud, sous **fix → activity** :

- un appel dont le verdict a été rendu par Jev (mode enforce) est attribué à **Jev**, et lorsque la vérification décisive provient d'un pack, l'enregistrement mentionne également ce pack et sa version ;
- en mode observe, le refus ou l'avertissement de Jev apparaît comme **would-have**, à côté des déploiements que vous observez ;
- les politiques que Jev a levées, ou aurait levées en mode observe, sont comptabilisées par politique ;
- une décision à laquelle Jev a participé (un blocage, un avertissement, une levée, ou un would-have en mode observe) liste chaque vérification qu'il a effectuée et sa conclusion : verdict, raison (`not-detected`, `exempt`, `fired`, `op-requested`, …), sa probabilité (`p`), la réponse `exempt` et la réponse de chaque sonde. Une vérification d'une politique déployée en observation est également listée, marquée comme observée ; elle ne bloque jamais. Jev répond avec des probabilités, non de la prose, donc il n'y a pas de raison en texte libre. Les autorisations simples sont regroupées en compteurs et ne portent pas cette liste.

## Lorsque Jev ne peut pas répondre

Chacun des cas suivants revient au résultat de vos politiques pour cet appel, et est enregistré avec sa raison :

| Raison | Cause |
| --- | --- |
| `out-of-credits` | Votre organisation a épuisé son enveloppe de plan. |
| `http-401`, `http-403` | La clé a été révoquée, ou ne porte pas `jev:evaluate`. Reconnectez-vous avec une clé qui le fait. |
| `http-429` | FailproofAI Cloud applique une limitation de débit Jev pour votre organisation. Tant que le délai d'attente demandé n'est pas écoulé (son `Retry-After`, au maximum 60 secondes), la machine n'envoie rien et chaque appel revient immédiatement au fallback. Les appels retenus de cette façon sont enregistrés comme `http-429`, ou comme `rate-limited` lorsque la limite de débit propre à la machine les retient en premier. |
| `http-429` (limite journalière) | Votre organisation a épuisé ses appels Jev journaliers : **10 000 par jour UTC**, sauf si l'opérateur de votre FailproofAI Cloud a défini une autre limite. Chaque appel revient au fallback jusqu'à la réinitialisation du compteur à 00:00 UTC ; la machine réessaie tout de même au moins une fois par minute, donc elle détecte la réinitialisation en moins d'une minute. `failproofai jev test` indique « Daily Jev limit for this org reached; resets at 00:00 UTC. » |
| `http-422` | Jev a refusé la requête de cet appel, généralement parce que l'appel d'outil contenait du texte dense (base64, hexadécimal, code minifié) dépassant le budget de tokens de Jev. Cet appel revient toujours au fallback ; ce n'est pas une panne. |
| `http-502` | Jev est actuellement indisponible. |
| `http-503` | Ce Cloud ne peut pas servir Jev pour votre organisation : pas de passerelle de modèle, une organisation pas encore provisionnée, ou la passerelle est hors service. Contactez votre administrateur ; les hooks réessaient au plus une fois par minute. |
| `http-404` | Ce FailproofAI Cloud ne sert pas encore Jev. |
| `timeout` | Aucune réponse dans `timeoutMs` (par défaut 3000). Lorsque FailproofAI Cloud définit le mode Jev de la machine, l'attente est de 5000 ms et le `timeoutMs` de `jev.json` n'est pas utilisé. |
| `model-mismatch` | Une version de Jev autre que 1.13 a répondu. |

## Où est stockée la clé et où elle va

- La clé est stockée une seule fois, dans `~/.failproofai/credentials.json` (permissions `0600`, dans un répertoire réservé au propriétaire), aux côtés des autres identifiants FailproofAI Cloud. `jev.json` ne contient aucune clé pour cette route ; une clé écrite là rend la configuration invalide.
- Si `credentials.json` porte **quelque** permission que ce soit pour quelqu'un d'autre que vous (groupe ou autres, lecture ou écriture), ou si son répertoire peut être **écrit** par quelqu'un d'autre que vous, il est **refusé**, non lu, et Jev est désactivé jusqu'à ce que vous y remédiiez : `chmod 600` sur le fichier, `chmod 700` sur le répertoire (ou reconnectez-vous, ce qui réécrit le fichier avec les permissions `0600` et rend le répertoire réservé au propriétaire). Un répertoire que d'autres peuvent seulement lire convient ; un répertoire qu'ils peuvent écrire leur permet de remplacer le fichier.
- La clé ne compte que tant que la connexion dont elle provient est sur la machine : un identifiant de politique ou de rapport pour le même FailproofAI Cloud **avec la même clé**, dans le même fichier. Une clé Jev laissée sans connexion associée est ignorée, et Jev reste désactivé. Cela se produit lorsqu'un ancien `config --disconnect` de failproofai laisse la clé Jev en place (il ne sait pas la supprimer), ou lorsqu'un ancien `config --token` de failproofai se connecte avec une autre clé, qui sur FailproofAI Cloud peut appartenir à une autre organisation. Pour réactiver Jev, reconnectez-vous avec une clé **machine**.
- La clé n'est jamais envoyée qu'à l'origine Cloud contre laquelle elle a été vérifiée. Un `jev.json` pointant ailleurs est refusé.
- **Un agent sur la machine peut la lire.** `credentials.json` est réservé au propriétaire, et l'agent s'exécute en tant que ce propriétaire. La lecture des fichiers propres à failproofai est intentionnellement autorisée (seule leur modification est bloquée, par `block-failproofai-commands`), donc la seule chose entre un agent et ce fichier est `block-read-outside-cwd` — une politique *révisable* — et depuis une session démarrée dans votre répertoire personnel, rien. Une clé portant `jev:evaluate` consomme l'enveloppe Jev de votre organisation (jusqu'au plafond journalier) depuis n'importe quel endroit où elle est utilisée, donc traitez une clé machine comme tout autre identifiant de dépense : si un agent peut l'avoir lue, révoquez-la dans **paramètres → clés API** et reconnectez-vous avec une nouvelle.
- Seuls vos fichiers globaux régissent cela. Un dépôt ne peut pas activer Jev Cloud, le rediriger ailleurs ni fournir sa clé, et `FAILPROOFAI_JEV_API_KEY` est ignoré pour cette route.
- Pour chaque appel évalué par Jev, une requête est envoyée à FailproofAI Cloud, contenant ce que liste la [page bring-your-own-key](/fr/reference/jev-providers#what-leaves-the-machine) (secrets expurgés). FailproofAI Cloud la transmet à TypeSafe et ne la journalise ni ne la conserve.

## Désactivation

Sur une machine connectée, Jev est désactivé lorsque FailproofAI Cloud ne lui déploie aucune politique Jev : supprimez ou archivez les politiques Jev dans Cloud.

| Commande | Résultat |
| --- | --- |
| Supprimer les politiques Jev de la machine dans FailproofAI Cloud | Le mode de Cloud devient `off` lors du prochain sondage (environ 30 s) : plus de Jev du tout, quoi qu'indique `jev.json`. |
| `failproofai config --disconnect` | Déconnecte la machine : la clé est supprimée, ainsi que `jev.json` lorsqu'il nomme FailproofAI Cloud et n'est pas désactivé. Un `jev.json` pour votre propre endpoint est conservé. |

Dès l'appel d'outil suivant, les hooks exécutent les politiques regex exactement comme auparavant.
