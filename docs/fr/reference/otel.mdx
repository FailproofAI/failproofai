`failproofai otel` configure le reporting OpenTelemetry optionnel vers FailproofAI Cloud. Commencez par connecter votre machine avec `failproofai config`. L'ingestion OpenTelemetry est toujours active dans Cloud ; il n'y a donc aucun interrupteur organisationnel à activer.

La configuration interactive propose OpenTelemetry après le champ de clé Cloud et le sélecteur d'agent. Cette étape facultative est désactivée par défaut. Choisissez Oui pour sélectionner les agents OTEL ; le même code d'activation s'exécute une fois la connexion enregistrée. Appuyer sur Échap avant la configuration n'applique aucune modification. La configuration non interactive, une clé fournie manuellement, le mode open source et la conservation d'une connexion existante ne vous inscrivent pas.

## Activer un agent

```bash
failproofai otel enable claude
failproofai otel enable codex --local
failproofai otel enable codex --no-content
failproofai otel enable copilot
failproofai otel enable all --yes
```

Les agents pris en charge sont `claude`, `codex` et `copilot` (VS Code). La configuration de Copilot nécessite un exécutable VS Code ou une extension Copilot installée. Un répertoire de paramètres résiduel seul ne suffit pas ; la configuration ignore Copilot si ni l'un ni l'autre n'est trouvé.

`--local` envoie les données vers le relais local plutôt que directement vers Cloud. Copilot utilise automatiquement le relais, car ses paramètres ne peuvent pas stocker l'en-tête d'authentification.

Le relais écoute uniquement sur votre machine. Le daemon FailproofAI configuré prend en compte la modification en quelques secondes ; aucun redémarrage n'est nécessaire. Si une autre application occupe le port du relais, le statut l'indique comme inactif et le daemon continue de fonctionner.

<Warning>
La capture de texte est activée par défaut. Ajoutez `--no-content` pour omettre les invites et les détails des outils. Les versions des agents peuvent exposer différents contrôles de contenu ; vérifiez ce que votre agent exporte avant de l'utiliser avec des données sensibles.
</Warning>

Codex exporte uniquement les journaux de conversation, non les traces d'exécution internes ni les métriques. Un paramètre explicite `log_user_prompt = false` dans votre configuration Codex reste désactivé ; lors de l'activation, une note s'affiche si ce choix est préservé.

### Choisir un seul chemin de reporting

Si le reporting de transcription est activé pour un agent, la configuration demande :

> failproofai envoie déjà les sessions Claude Code vers Cloud. Les envoyer via OTEL à la place ? L'envoi de transcription pour Claude Code sera arrêté.

La valeur par défaut est Non. `--yes` accepte le changement sans invite. Les autres agents et l'application des politiques ne sont pas affectés.

La configuration de Codex attend que le daemon confirme le changement de collecteur avant d'écrire ses paramètres d'exportation. Si la confirmation expire, la configuration vous avertit d'attendre avant de démarrer Codex.

La config v2 conserve la liste de traçage mémorisée dans `agents.selected` (et l'historique de détection dans `agents.seen`). La préférence de transcription par agent reste dans `collector.agents.<agent>.sessions`, la gestion OTEL dans `otel.agents`, et les paramètres du relais dans `collector.otlp.enabled` / `collector.otlp.port`. Ces clés séparées maintiennent la lisibilité des anciennes configurations OTEL : la configuration peut modifier la liste de traçage sans perdre la préférence de transport ni l'état nécessaire à la restauration des paramètres d'agent.

## Inspecter la configuration

```bash
failproofai otel status
```

Le statut affiche chaque agent, indique si ses paramètres sont gérés par FailproofAI, sa destination, l'interrupteur d'ingestion de l'organisation, l'état du relais et le dernier résultat d'envoi du relais.

La valeur `unknown` pour l'interrupteur organisationnel signifie que le serveur n'a pas fourni cette information ou n'était pas joignable. Ce n'est pas une erreur et cela n'empêche pas la configuration sur une ancienne version de Cloud.

Si Cloud ne prend pas encore en charge OTEL, le relais conserve les exports rejetés plutôt que de les supprimer. Si une ancienne version de Cloud signale que l'ingestion organisationnelle est désactivée, `enable` n'écrit rien et se termine avec une erreur.

## Afficher la configuration pour une application

```bash
failproofai otel env --service my-agent
failproofai otel env --service my-agent --local
```

La sortie est un bloc d'environnement shell pour un exportateur OTLP/HTTP. La sortie Cloud définit `OTEL_EXPORTER_OTLP_ENDPOINT` sur la base OTLP de Cloud, `https://<cloud>/otel`, et l'exportateur ajoute `/v1/<signal>` ; une variable par signal telle que `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` nécessite l'URL complète `https://<cloud>/otel/v1/logs`. La sortie locale pointe vers le relais, `http://127.0.0.1:<port>`. La sortie Cloud inclut la clé API configurée ; traitez-la comme un secret. La sortie locale omet la clé. Pour utiliser la sortie locale, activez d'abord un agent local afin que le relais soit en cours d'exécution.

## Restaurer les paramètres précédents

```bash
failproofai otel disable claude
failproofai otel disable all
```

La désactivation restaure uniquement les paramètres écrits par FailproofAI, conserve les modifications non liées et rétablit le choix de reporting de transcription précédent de chaque agent. Lorsque le dernier agent local géré est désactivé, le relais cesse d'accepter des exports.

Pour Codex, la désactivation enregistre également `collector.agents.codex.sessions_resume_after` (millisecondes epoch). Les octets de déploiement existants sont considérés comme livrés, de sorte que les sessions capturées avec OTEL ne sont pas téléchargées à nouveau ; les ajouts ultérieurs continuent de transiter par le reporting de transcription.

Chaque commande accepte `--help`. Consultez [OpenTelemetry dans Cloud](/fr/agenteye/opentelemetry) pour des exemples d'applications et d'agents de codage.
