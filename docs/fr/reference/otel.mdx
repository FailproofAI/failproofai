`failproofai otel` configure le reporting OpenTelemetry optionnel vers FailproofAI Cloud. Commencez par connecter votre machine avec `failproofai config` et demandez à un administrateur de l'organisation d'activer **Paramètres → OpenTelemetry**.

La configuration interactive vous interroge sur OpenTelemetry après le champ de clé Cloud et le sélecteur d'agent. Cette étape optionnelle est désactivée par défaut. Choisissez Oui pour sélectionner les agents OTEL ; le même code d'activation s'exécute une fois la connexion écrite. Appuyer sur Échap avant la configuration n'applique aucune modification. La configuration non interactive, une clé fournie manuellement, le mode open source et la conservation d'une connexion enregistrée ne vous inscrivent pas automatiquement.

## Activer un agent

```bash
failproofai otel enable claude
failproofai otel enable codex --local
failproofai otel enable codex --no-content
failproofai otel enable copilot
failproofai otel enable all --yes
```

Les agents pris en charge sont `claude`, `codex` et `copilot` (VS Code). La configuration de Copilot nécessite un exécutable VS Code ou une extension Copilot installée. Un simple répertoire de paramètres existant ne suffit pas ; la configuration ignore Copilot si aucune des deux conditions n'est remplie.

`--local` envoie les données au relais local plutôt que directement vers Cloud. Copilot utilise automatiquement le relais, car ses paramètres ne peuvent pas stocker l'en-tête d'authentification.

Le relais écoute uniquement sur votre machine. Votre daemon FailproofAI configuré prend en compte la modification en quelques secondes ; aucun redémarrage n'est nécessaire. Si une autre application occupe le port du relais, le statut l'indique comme désactivé et le daemon continue de fonctionner.

<Warning>
La capture de texte est activée par défaut. Ajoutez `--no-content` pour exclure les invites et les détails des outils. Les versions des agents peuvent exposer différents contrôles de contenu ; examinez ce que votre agent exporte avant de l'utiliser avec des données sensibles.
</Warning>

Codex n'exporte que les journaux de conversation, pas les traces d'exécution internes ni les métriques. Un `log_user_prompt = false` explicite dans votre configuration Codex reste désactivé ; enable affiche une note lorsqu'il préserve ce choix.

### Choisir un chemin de reporting

Si le reporting de transcription est activé pour un agent, la configuration demande :

> failproofai envoie déjà les sessions Claude Code vers Cloud. Les envoyer via OTEL à la place ? L'upload de transcription pour Claude Code s'arrêtera.

La valeur par défaut est Non. `--yes` accepte le changement sans invite. Les autres agents et l'application des politiques ne sont pas affectés.

La configuration de Codex attend que le daemon confirme le changement de collecteur avant d'écrire les paramètres de l'exporteur. En cas d'expiration du délai de confirmation, la configuration vous avertit d'attendre avant de démarrer Codex.

La config v2 conserve la liste de traçage mémorisée dans `agents.selected` (et l'historique de détection dans `agents.seen`). La préférence de transcription par agent reste dans `collector.agents.<agent>.sessions`, la propriété OTEL dans `otel.agents`, et les paramètres du relais dans `collector.otlp.enabled` / `collector.otlp.port`. Ces clés séparées préservent la lisibilité des anciennes configurations OTEL : la configuration peut modifier la liste de traçage sans perdre la préférence de transport ni l'état nécessaire à la restauration des paramètres de l'agent.

## Inspecter la configuration

```bash
failproofai otel status
```

Le statut affiche chaque agent, si ses paramètres sont gérés par FailproofAI, sa destination, le commutateur d'ingestion de l'organisation, l'état du relais et le dernier résultat d'upload du relais.

`unknown` pour le commutateur de l'organisation signifie que le serveur ne l'a pas fourni ou n'a pas pu être atteint. Ce n'est pas une erreur et cela n'empêche pas la configuration sur une version Cloud plus ancienne.

Si Cloud ne prend pas encore en charge OTEL, le relais conserve les exports rejetés plutôt que de les supprimer. Si l'ingestion de l'organisation est désactivée, `enable` n'écrit rien et se termine avec une erreur ; demandez à un administrateur de l'activer d'abord.

## Afficher la configuration pour une application

```bash
failproofai otel env --service my-agent
failproofai otel env --service my-agent --local
```

La sortie est un bloc d'environnement shell pour un exporteur OTLP/HTTP. La sortie Cloud définit `OTEL_EXPORTER_OTLP_ENDPOINT` sur la base OTLP de Cloud, `https://<cloud>/otel`, et l'exporteur ajoute `/v1/<signal>` ; une variable par signal telle que `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` nécessite l'URL complète `https://<cloud>/otel/v1/logs`. La sortie locale pointe vers le relais, `http://127.0.0.1:<port>`. La sortie Cloud inclut la clé API configurée ; traitez-la comme un secret. La sortie locale n'inclut pas la clé. Pour utiliser la sortie locale, activez d'abord un agent local afin que le relais soit en cours d'exécution.

## Restaurer les paramètres précédents

```bash
failproofai otel disable claude
failproofai otel disable all
```

Disable restaure uniquement les paramètres écrits par FailproofAI, conserve les modifications non liées et restaure le choix de reporting de transcription précédent de chaque agent. Lorsque le dernier agent local géré est désactivé, le relais cesse d'accepter les exports.

Pour Codex, disable enregistre également `collector.agents.codex.sessions_resume_after` (millisecondes epoch). Les octets de rollout existants sont traités comme livrés afin que les sessions capturées avec OTEL ne soient pas uploadées à nouveau ; les ajouts ultérieurs continuent de transiter par le reporting de transcription.

Chaque commande prend en charge `--help`. Consultez [OpenTelemetry dans Cloud](/fr/agenteye/opentelemetry) pour des exemples d'applications et d'agents de codage.
