אמור ל-coding agent שלך *"הוסף Failproof AI Observability ל-agent הזה"* והנח לו לקרוא את ה-loop שלך, להבין היכן ה-instrumentation צריך להיות, לכתוב אותו ולאמת את האירועים לפני שהוא מסיים את העבודה.

ה-**Python SDK skill** (`agenteye-python-sdk`) הוא *Agent Skill*: תיקייה של הוראות ש-coding agent כמו Claude Code או Codex טוען לפי הצורך כאשר משימה תואמת לה. היא מלמדת את ה-agent לשימוש ב-[Python SDK](/he/agenteye/python-sdk) — היא לא ספריה, והיא לא משנה כלום בדרך שה-SDK עובד.

## Instrumentation קל לכתיבה וקל להתבלבל בו בשקט

ה-SDK קטן: שלוש עשרה שיטות אירועים, כולן keyword-only. coding agent יכול לקרוא את [Python SDK](/he/agenteye/python-sdk) reference ולייצר instrumentation סביר בדקה.

המלכוד הוא שה-SDK הזה לא זורק exception כשאתה טועה, ו-instrumentation לא נכון נראה בדיוק כמו instrumentation נכון עד שמישהו פותח דאשבורד ומוצא אותו ריק. הטעויות שעולות עלות בזמן אמיתי הן כולן שתיקות:

| הטעות | מה אתה רואה |
|---|---|
| אין `agent_start` | כל אירוע נוחת. אפס sessions. |
| Environment מעולם לא הוגדר | הכל עובד, מתויק תחת `dev`. |
| `outcome="failure"` | ה-run מופיע ירוק — רק `failed`, `error`, `timeout`, `rejected` סופרים. |
| שם שדה בעל typo | מקובל ומאוחסן כשדה חדש. |
| אירועים שנפלטו מ-thread pool | מושמטים בשקט. |

אף אחד מאלה לא זורק exception. אף אחד לא מופיע בבדיקות. כל אחד נמצא ב-skill, מתואר כחוזה עם הבדיקה שתופסת אותו.

## מה זה עושה, בסדר

ה-skill מריץ את אותן שלוש שלבים שמהנדס זהיר היה עושה:

1. **Plan.** זה קורא את ה-loop של ה-agent שלך ושואל את שתי השאלות שרק אתה יכול לענות עליהן: מה נחשב לרן אחד (ה-`session_id` שלך), ומי הכנים השונים (ה-`agent_id` שלך). זה מקבל הסכמה על אלה לפני כתיבת קוד, כי שינוי אותם מאוחר יותר מפצל את ההיסטוריה שלך ושוברק את המגמות.
2. **Write.** זה קושר זהות פעם אחת לכל רן ולא חוטים אותה דרך כל אתר קריאה, וזה בוחר צורה בטוחה לבו-concurrency — פרט שחשוב, כי הקיצור הברור בשקט מערבב שני runs חופפים לרן אחד.
3. **Verify.** זה מריץ את ה-agent שלך וקורא את קובצי האירועים שהתקבלו, בודק ש-`agent_start` קיים, ה-environment נכון, ורן אחד ייצר session אחד.

השלב השלישי הוא זה שאנשים מדלגים עליו. ה-SDK כותב אירועים לקבצים מקומיים, כך שאינטגרציה שלמה יכולה להיות מוכחת על laptop עם אין שרת, אין API key, ואין רשת — וזה בדיוק למה ה-skill מתעקש על כך.

## איך זה קשור לשאר ה-skills

שלוש skills, פיצול אחד נקי:

| Skill | הגע לזה כאשר | מה זה משפיע |
|---|---|---|
| **Python SDK skill** (עמוד זה) | אתה רוצה שה-agent שלך *ישדר* telemetry — "הוסף observability", "למה ה-agent שלי לא מופיע?" | כותב קוד בתיקייה של ה-agent שלך. לא קורא כלום. |
| **[Evaluator skill](/he/agenteye/evaluator-skill)** | אתה רוצה *לדרג* runs — "מה אנחנו בכלל צריכים למדוד?" | כותב קוד בתיקייה שלך; קורא telemetry |
| **[CLI skill](/he/agenteye/cli-skill)** | אתה רוצה *לקרוא* מה קרה, או להפעיל את ה-deployment שלך | מנהל את ה-CLI כמוך, כולל שינויים |

הם עוברים זה לזה בסדר הזה: ה-skill הזה מניע אירועים, ה-evaluator מדרג אותם, ה-CLI קורא אותם חזרה. אין כלום להערכה ואין כלום לקריאה עד שה-agent שלך פולט sessions, כך שאם אתה מתחיל מאפס, התחל כאן.

## דרישות קדם

1. **Python 3.10+** וה-codebase של ה-agent שאתה רוצה לעשות instrumentation ל-.
2. **ה-SDK.** הוא מופץ ללקוחות כ-private wheel ולא מ-public index — ה-onboarding שלך מכסה איך להשיג אותו ולהתקין אותו. ה-skill יודע את נתיב ההתקנה וישאל אותך במקום לנחש אם הוא לא יכול למצוא אותו.
3. **כלום עוד.** אין login לדאשבורד, אין API key, אין רשת. ה-skill מאמת מול קובצי האירועים שה-SDK כותב, כך שהוא יכול לסיים ולהוכיח את עבודתו offline.

## איפה להשיג אותו

ה-skill חי בקולקציה הציבורית [`FailproofAI/skills`](https://github.com/FailproofAI/skills):

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

הוסף `-g` כדי להתקין אותו לכל פרויקט במקום רק לפעולה הנוכחית, ו-`--copy` אם הסביבה שלך לא עוקבת אחר symlinks. עבור Codex, עבור `-a codex`.

## התקנה ידנית

Agent Skills הם תיקיות המכילות `SKILL.md` פלוס הפניות. אם אתה מעדיף לא להשתמש בהתקן:

- **Claude Code**: העתק את תיקיית `agenteye-python-sdk/` לתוך `~/.claude/skills/` (כל פרויקט) או `<your-repo>/.claude/skills/` (רק המאגר הזה). Claude Code מגלה אותו באופן אוטומטי — בדוק את רשימת `/skills`, או פשוט שאל משהו שתואם לו.
- **Codex**: Codex קורא את אותו `SKILL.md`. ה-`agents/openai.yaml` המצורף קובע `allow_implicit_invocation: true`, כך שהוא נבחר אוטומטית כשמשימה תואמת; אחרת אתה מעורר אותו כ-`$agenteye-python-sdk`.

הרץ את ה-agent שלך **בתיקייה המחזיקה את הקוד שאתה רוצה לעשות לו instrumentation** — ה-skill קורא את ה-loop של ה-agent שלך לפני שהוא מציע כלום.

## איך session נראה

```text
you   ▸ הוסף Failproof AI Observability לא-agent הזה.

agent ▸ קרא את ה-loop שלך — dispatcher כלים אחד ב-tools.py, wrapper
        אחד של Anthropic ב-llm.py. שתי שאלות לפני שכותב כלום.

        מה נחשב לרן אחד? אתה מטפל בבקשות במקביל, כך שהיית משתמש
        ב-request id שיש לך כבר ב-ctx.request_id — אז session כאן
        והבקשה בלוגים שלך הם אותו string.

        ומי הכנים? אני רואה נתיב של planner ונתיב researcher. תייג אותם
        בנפרד, או זה כן agent אחד בעיניך?

you   ▸ Request id נכון. הם agent אחד, קרא לזה "assistant".

agent ▸ בוצע. עטפת את ה-dispatcher ולקוח ה-LLM; agent_start ו-agent_end
        בסוגריים handle_request, כולל נתיב השגיאה. השתמשת בcontext-local
        לזהות — ה-dispatcher שלך מריץ כלים בthread pool, והגישה
        הפשוטה יותר היתה מערבבת concurrent runs לרן אחד בלי להתלונן.

        אומת מול רן אמיתי: 11 אירועים על פני 4 קבצים —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, session אחד
        לכל בקשה, משכי זמן משויכים.

        דבר אחד שלא עשיתי: ה-worker pool שלך ב-batch.py שולח ישר
        ל-executor, כך שאירועים משם יהיו מושמטים. אתה רוצה שאני
        אתקן גם את אלה?
```

הדפוס שצריך להבחין בו: זה קרא את הקוד לפני הצעה, שאל רק את השאלות שאתה יכול לענות עליהן, השתמש חוזר ב-id שכבר היה לך, בחר בצורה בטוחה לבו-concurrency *כי* זה ראה thread pool, וגם **אומת בקריאת האירועים בפועל** במקום להכריז על הצלחה — אז סימן את מקום אחד שהוא ידע שיכשל בשקט.

## מה אתה יכול לשאול

- *"למה ה-agent שלי לא מופיע בדאשבורד?"* → הולך בסולם: האם אירועים נכתבים, האם `agent_start` שם, האם ה-environment נכון, האם ה-collector קורא את אותו מקום.
- *"הכל נוחת תחת dev."* → ה-environment מעולם לא הוגדר, או הוא הוגדר מחדש על ידי קריאה מאוחרת יותר.
- *"הוסף token tracking."* → מוצא את ה-LLM wrapper שלך ורושם model, stop reason, ו-usage.
- *"עשה instrumentation גם ל-sub-agents."* → session אחד, תוויות agent נפרדות, מקונן תחת ההורה שלהם.
- *"כתוב בדיקות ל-instrumentation."* → מצביע את ה-SDK לתיקייה זמנית וקורא תביעות על האירועים שהוא כתב.

## מה לשמור עיניים עליו

**תן לזה לאמת.** השלב שעושה את ה-skill הזה שווה להשתמש בו הוא האחרון — הרצת ה-agent שלך וקריאת אירועים בחזרה. agent שכתב instrumentation ועצר עשה את המחצית הקלה, והמחצית שנכשלת בשקט היא האחרת.

**הסכם על השמות לפני הקוד.** `session_id` ו-`agent_id` הם הצירים שכל משטח מקבץ לפיהם. שינוי שם להם מאוחר יותר מפצל את ההיסטוריה: runs ישנים שומרים על התוויות הישנות והמגמות שלך שוברות. ה-skill ישאל; התשובה שווה דקה של חשיבה.

**אם ה-agent שלך מציע להתקין את ה-SDK מ-public index, ה-skill לא טעון.** ה-SDK מופץ בפרטיות. ההצעה הזו היא סימן אמין שה-coding agent שלך מנחש במקום לעקוב אחר ה-skill — עצור את זה שם ובדוק שה-skill מותקן.

מעבר לזה blast radius שלו קטן: זה כותב קוד בתיקייה עבודה שלך וקובצי אירועים שם שאתה אומר לו. זה קורא כלום מה-deployment שלך ולא משנה כלום בגידול.
