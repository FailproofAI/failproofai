ספור לסוכן הקוד שלך *"הוסף Failproof AI Observability לסוכן זה"* והנח לו לקרוא את הלולאה שלך, להבין איפה הקידוד שייך, לכתוב אותו ולאמת את האירועים לפני שהוא מסיים את העבודה.

**Python SDK skill** (`agenteye-python-sdk`) הוא *Agent Skill*: תיקייה של הוראות שסוכן קוד כמו Claude Code או Codex טוען לפי דרישה כשמשימה תואמת אותה. זה מלמד את הסוכן להשתמש ב-[Python SDK](/he/agenteye/python-sdk) — זה לא ספרייה, וזה לא משנה דבר בנוגע לאופן שבו ה-SDK עובד.

## קידוד קל לכתיבה וקל להשתבש בשקט

ה-SDK קטן: שלוש עשרה שיטות אירוע, כולן keyword-only. סוכן קוד יכול לקרוא את התיעוד של [Python SDK](/he/agenteye/python-sdk) וליצור קידוד סביר תוך דקה.

הבעיה היא שה-SDK הזה לא זורק שגיאות כשאתה טועה, וקידוד שגוי נראה בדיוק כמו קידוד נכון עד שמישהו פותח לוח מחוונים ומגלה שהוא ריק. הטעויות שעולות זמן אמיתי כולן שתיקות:

| הטעות | מה אתה רואה |
|---|---|
| אין `agent_start` | כל אירוע מגיע. אפס sessions. |
| הסביבה לא הוגדרה | הכל עובד, תחת `dev`. |
| `outcome="failure"` | ההרצה מופיעה בירוק — רק `failed`, `error`, `timeout`, `rejected` נספרים. |
| שם שדה עם טעות הקלדה | מתקבל ומאוחסן כשדה חדש. |
| אירועים שנשלחו מ-thread pool | מושמטים בשקט. |

אחד מאלה לא זורק שגיאות. אחד לא מופיע בבדיקות. כל אחד נמצא בـ skill, המובא כהסכם עם הבדיקה שתופסת אותו.

## מה זה עושה, לפי סדר

ה-skill מריץ את אותן שלוש השלבים שמהנדס זהיר היה עושה:

1. **תכנון.** הוא קורא את לולאת הסוכן שלך ושואל את שתי השאלות שרק אתה יכול לענות: מה נחשב להרצה אחת (`session_id` שלך), ומי הפעילים ניתנים להבחנה (`agent_id` שלך). הוא מקבל הסכמה לגבי אלה לפני כתיבת קוד, כי שינוי שלהם מאוחר יותר מפצל את ההיסטוריה שלך ומשבר את המגמות.
2. **כתיבה.** הוא קושר זהות פעם אחת בהרצה ולא משדר אותה דרך כל אתר קריאה, והוא בוחר בצורה בטוחה לתרמילות — פרט שחשוב, כי הקיצור הברור בשקט מערבב שתי הרצות חופפות לsession אחד.
3. **אימות.** הוא מריץ את הסוכן שלך וקורא את קבצי האירוע שהתקבלו, ובודק ש-`agent_start` קיים, הסביבה נכונה, והרצה אחת יצרה session אחד.

השלב השלישי הוא זה שאנשים דילגים עליו. ה-SDK כותב אירועים לקבצים מקומיים, כך שאינטגרציה שלמה יכולה להיות מוכחת על נייד ללא שרת, ללא API key, וללא רשת — וזה בדיוק למה ה-skill מתעקש לעשות את זה.

## איך זה קשור לskills האחרים

שלוש skills, חלוקה נקייה אחת:

| Skill | הגע לזה כשאתה | מה זה משפיע |
|---|---|---|
| **Python SDK skill** (עמוד זה) | אתה רוצה שהסוכן שלך *שלח* telemetry — "הוסף observability", "למה הסוכן שלי לא מופיע?" | כותב קוד בrepo של הסוכן שלך. לא קורא כלום. |
| **[Evaluator skill](/he/agenteye/evaluator-skill)** | אתה רוצה *לתן ניקוד* להרצות — "מה בכלל אנחנו צריכים למדוד?" | כותב קוד ב-repo שלך; קורא telemetry |
| **[CLI skill](/he/agenteye/cli-skill)** | אתה רוצה *לקרוא* מה קרה, או להפעיל את הdeployment שלך | מנהל את ה-CLI כמוך, כולל שינויים |

הם מעבירים בסדר הזה: skill זה מקבל אירועים זורמים, המעריך נותן להם ניקוד, ה-CLI קורא אותם חזרה. אין כלום להערכה ואין כלום לקרוא עד שהסוכן שלך שולח sessions, כך שאם אתה מתחיל מאפס, התחל כאן.

## דרישות מוקדמות

1. **Python 3.10+** וה-codebase של הסוכן שאתה רוצה לקודד.
2. **ה-SDK.** הוא מופץ ללקוחות כ-wheel פרטי ולא מאינדקס ציבורי — ה-onboarding שלך מכסה כיצד להשיג אותו והתקן אותו. ה-skill יודע את נתיב ההתקנה וישאל אותך אם הוא לא יכול למצוא אותו.
3. **כלום אחר.** אין כניסה ללוח מחוונים, אין API key, אין רשת. ה-skill מאמת כנגד קבצי האירוע שה-SDK כותב, כך שהוא יכול להסתיים ולהוכיח את עבודתו offline.

## איפה להשיג את זה

ה-skill חי בקולקציה הציבורית [`FailproofAI/skills`](https://github.com/FailproofAI/skills):

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

הוסף `-g` כדי להתקין אותו לכל project במקום רק לזה הנוכחי, ו-`--copy` אם הסביבה שלך לא עוקבת אחר symlinks. עבור Codex, עבור `-a codex`.

## התקנה ידנית

Agent Skills הם תיקיות המכילות `SKILL.md` ופניות. אם אתה מעדיף לא להשתמש בתקן:

- **Claude Code**: העתק את התיקייה `agenteye-python-sdk/` ל-`~/.claude/skills/` (כל project) או `<your-repo>/.claude/skills/` (רק repo זה). Claude Code מגלה זאת באופן אוטומטי — בדוק את רשימת `/skills`, או פשוט שאל משהו שתואם אותו.
- **Codex**: Codex קורא את אותו `SKILL.md`. ה-`agents/openai.yaml` המצורף מציב `allow_implicit_invocation: true`, כך שהוא נבחר באופן אוטומטי כשמשימה תואמת; אחרת הזמן אותו כ-`$agenteye-python-sdk`.

הרץ את הסוכן שלך **בrepository המחזיק את הקוד שאתה רוצה לקודד** — ה-skill קורא את לולאת הסוכן שלך לפני שהוא מציע משהו.

## איך session נראה

```text
אתה   ▸ הוסף Failproof AI Observability לסוכן זה.

סוכן ▸ קרא את הלולאה שלך — dispatcher כלים אחד ב-tools.py, wrapper Anthropic
        אחד ב-llm.py. שתי שאלות לפני שאני כותב כלום.

        מה נחשב להרצה אחת? אתה מטפל בבקשות בו זמנית, כך שהייתי משתמש
        בתחום request id שאתה כבר יש לך ב-ctx.request_id — אז session
        כאן ובקשה בלוגים שלך הם אותו string.

        ומי הפעילים? אני רואה נתיב planner ונתיב researcher.
        תייגו אותם בנפרד, או זה סוכן אחד עבורך?

אתה   ▸ Request id נכון. הם סוכן אחד, קרא לזה "assistant".

סוכן ▸ בוצע. עטפתי את ה-dispatcher ו-LLM client; agent_start ו-
        agent_end bracketing handle_request, כולל error path. השתמשתי
        context-local לזהות — ה-dispatcher שלך מריץ tools בthread pool, והגישה
        הפשוטה יותר היתה מערבבת הרצות בו זמנית לsession אחד ללא קבלת תלונות.

        אומת כנגד הרצה אמיתית: 11 אירועים על פני 4 קבצים —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, session אחד
        לבקשה, משכי זמן זוגיים.

        דבר אחד שעשיתי לא: pool worker שלך ב-batch.py מגיש ישירות לexecutor,
        כך שאירועים משם היו מושמטים. אתה רוצה שאני יתקן את אלה גם?
```

ה-pattern שכדאי להשים לב אליו: הוא קרא את הקוד לפני שהציע, שאל רק את השאלות שאתה יכול לענות, שימוש חוזר בתחום שכבר היה לך, בחר בצורה בטוחה לתרמילות *כי* הוא ראה thread pool, ו**אומת על ידי קריאה של אירועים בפועל** במקום הכרזה על הצלחה — אז דגל במקום אחד שהוא ידע שיכשל בשקט.

## מה אתה יכול לשאול אותו

- *"למה הסוכן שלי לא מופיע בלוח המחוונים?"* → הולך בסולם: האם אירועים נכתבים, האם `agent_start` שם, האם הסביבה נכונה, האם ה-collector קורא את אותו מקום.
- *"הכל נוחת תחת dev."* → הסביבה לא הוגדרה, או אופסה על ידי קריאה מאוחרת יותר.
- *"הוסף token tracking."* → מוצא את ה-LLM wrapper שלך וחומר model, stop reason, usage.
- *"קודדו את תת-הסוכנים גם."* → session אחד, תוויות agent מובחנות, קיננו תחת ההורה שלהם.
- *"כתוב בדיקות לקידוד."* → מצביע על ה-SDK בתיקייה זמנית וטוען על אירועים שהוא כתב.

## מה להיזהר

**תן לזה לאמת.** השלב שעושה את ה-skill הזה שווה לשימוש הוא האחרון — הרצת הסוכן שלך וקריאת האירועים חזרה. סוכן שכותב קידוד ועוצר עשה את החצי הקל, והחצי שנכשל בשקט הוא השני.

**הסכמו על השמות לפני הקוד.** `session_id` ו-`agent_id` הם הצירים שכל משטח מקבצות לפיהם. שינוי שם מאוחר יותר מפצל את ההיסטוריה: הרצות ישנות שמרו את התוויות הישנות והמגמות שלך שוברות. ה-skill ישאל; התשובה שווה דקה של חשיבה.

**אם הסוכן שלך מציע התקנת ה-SDK מאינדקס ציבורי, ה-skill לא נטען.** ה-SDK מופץ בפרטיות. ההצעה הזו היא דרך אמינה לומר שסוכן הקוד שלך מנחש במקום לעקוב אחר ה-skill — עצור את זה שם ובדוק שה-skill מותקן.

מעבר לכך radius ההתפרצות שלו קטן: הוא כותב קוד בתיקיית העבודה שלך וקבצי אירוע איפה שאתה אומר. הוא לא קורא כלום מה-deployment שלך ולא משנה כלום בו.
