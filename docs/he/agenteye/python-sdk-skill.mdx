ספרו לcoding agent שלכם *"add Failproof AI Observability to this agent"* והשאירו אותו לקרוא את הloop שלכם, להבין לאיפה האינסטרומנטציה שייכת, לכתוב אותה, ולאמת את האירועים לפני שהוא מסיים את העבודה.

ה-**Python SDK skill** (`agenteye-python-sdk`) הוא *Agent Skill*: תיקייה של הוראות שcoding agent כמו Claude Code או Codex טוען לפי הצורך כשמשימה תואמת אליו. הוא מלמד את ה-agent להשתמש ב-[Python SDK](/he/agenteye/python-sdk) — זה לא ספרייה, והוא לא משנה שום דבר בדרך שה-SDK עובד.

## Instrumentation קל לכתוב וקל להיות בו טעות בשקט

ה-SDK קטן: שלוש עשרה שיטות אירועים, כולן keyword-only. coding agent יכול לקרוא את ה-[Python SDK](/he/agenteye/python-sdk) reference וליצור instrumentation סביר בדקה.

הבעיה היא שה-SDK הזה לא מעלה חריגה כשאתם טועים, instrumentation שגוי נראה בדיוק כמו instrumentation נכון עד שמישהו פותח dashboard ומוצא אותו ריק. הטעויות שעולות זמן אמיתי כולן שתיקות:

| הטעות | מה אתם רואים |
|---|---|
| אין `agent_start` | כל אירוע נחת. אפס sessions. |
| Environment לא הוגדר אי פעם | הכל עובד, מתויק תחת `dev`. |
| `outcome="failure"` | ההרצה מופיעה בירוק — רק `failed`, `error`, `timeout`, `rejected` סופרים. |
| שם שדה עם typo | מקובל ו-stored כשדה חדש. |
| אירועים שנשלחו מthread pool | נושרים בשקט. |

אף אחד מאלה לא מעלה חריגה. אף אחד לא מופיע בבדיקות. כל אחד נמצא בskill, מוצהר כחוזה עם הבדיקה שתופסת אותו.

## מה זה עושה, לפי הסדר

ה-skill עובר את אותן שלוש שלבים שמהנדס זהיר היה עובר:

1. **Plan.** הוא קורא את agent loop שלכם ושואל את שתי השאלות שרק אתם יכולים לענות עליהן: מה נחשב להרצה אחת (ה-`session_id` שלכם), ומי השחקנים המובחנים (ה-`agent_id` שלכם). הוא מקבל הסכמה על אלה לפני כתיבת קוד, כי שינוי שלהם מאוחר יותר מפצל את ההיסטוריה שלכם ושובר את המגמות.
2. **Write.** הוא קושר זהות פעם אחת ליחידת עבודה ולא בחוטים דרך כל call site, וזה בוחר צורה בטוחה לתרגיל — פרט שחשוב, כי הקיצור הברור בשקט מערבב שתי הרצות חופפות לsession אחד.
3. **Verify.** הוא מריץ את ה-agent שלכם וקורא את קובצי האירועים שהתקבלו, בדק שיש `agent_start`, ש-environment נכון, וש-run אחד יוצר session אחד.

את שלב שלוש הזה אנשים דילגים עליו. ה-SDK כותב אירועים לקבצים מקומיים, כך שintegration שלם יכול להיות מוכח על laptop ללא server, ללא API key, וללא network — שזו בדיוק הסיבה שה-skill מעקש על כך.

## איך זה קשור לskills האחרים

שלוש skills, חלוקה אחת נקייה:

| Skill | הגעו אליו כאשר | מה זה משנה |
|---|---|---|
| **Python SDK skill** (דף זה) | אתם רוצים שה-agent שלכם *ישלח* telemetry — "add observability", "why isn't my agent showing up?" | כותב קוד בrepo של ה-agent שלכם. לא קורא שום דבר. |
| **[Evaluator skill](/he/agenteye/evaluator-skill)** | אתם רוצים *לדרג* runs — "what should we even measure?" | כותב קוד בrepo שלכם; קורא telemetry |
| **[CLI skill](/he/agenteye/cli-skill)** | אתם רוצים *לקרוא* מה קרה, או להפעיל את ה-deployment שלכם | מנהל את ה-CLI כמו אתכם, כולל שינויים |

הם מעבירים לפי הסדר הזה: skill זה מקבל אירועים זורמים, ה-evaluator מדרג אותם, ה-CLI קורא אותם חזרה. אין כלום להערכה ואין כלום לקריאה עד שה-agent שלכם שולח sessions, אז אם אתם מתחילים מ-scratch, התחילו כאן.

## דרישות מוקדמות

1. **Python 3.10+** וה-agent codebase שאתם רוצים להכניס לו instrumentation.
2. **ה-SDK.** הוא מחולק ללקוחות כ-private wheel ולא מ-public index — ה-onboarding שלכם מכסה איך להשיג אותו ולהתקין אותו. ה-skill יודע את נתיב ההתקנה ושיאל אתכם אם הוא לא יכול למצוא אותו.
3. **שום דבר אחר.** אין dashboard login, אין API key, אין network. ה-skill מאמת מול קובצי האירועים שה-SDK כותב, כך שהוא יכול להסיים ולהוכיח את עבודתו offline.

## איפה להשיג אותו

ה-skill גר בקולקציה ציבורית [`FailproofAI/skills`](https://github.com/FailproofAI/skills):

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

הוסיפו `-g` כדי להתקין אותו לכל פרויקט במקום רק לפעולה הנוכחית, ו-`--copy` אם הסביבה שלכם לא עוקבת אחר symlinks. עבור Codex, השתמשו ב-`-a codex`.

## התקנה ידנית

Agent Skills הם תיקיות המכילות `SKILL.md` ועוד הפניות. אם אתם מעדיפים לא להשתמש בגדול:

- **Claude Code**: העתיקו את התיקייה `agenteye-python-sdk/` ל-`~/.claude/skills/` (כל פרויקט) או ל-`<your-repo>/.claude/skills/` (רק הrepo הזה). Claude Code מגלה אותו באופן אוטומטי — בדקו את `/skills` list, או פשוט שאלו משהו שתואם.
- **Codex**: Codex קורא את אותו `SKILL.md`. ה-`agents/openai.yaml` התיקייה מגדיר `allow_implicit_invocation: true`, כך שהוא נבחר באופן אוטומטי כאשר משימה תואמת; אחרת, הפעילו אותו כ-`$agenteye-python-sdk`.

הריצו את ה-agent שלכם **בrepo שמכיל את הקוד שאתם רוצים להכניס לו instrumentation** — ה-skill קורא את agent loop שלכם לפני שהוא מציע משהו.

## איך session נראה

```text
you   ▸ Add Failproof AI Observability to this agent.

agent ▸ Read your loop — one tool dispatcher in tools.py, one Anthropic
        wrapper in llm.py. Two questions before I write anything.

        What counts as one run? You handle requests concurrently, so I'd
        use the request id you already have in ctx.request_id — then a
        session here and a request in your logs are the same string.

        And who are the actors? I see a planner path and a researcher
        path. Label them separately, or is that one agent to you?

you   ▸ Request id is right. They're one agent, call it "assistant".

agent ▸ Done. Wrapped the dispatcher and the LLM client; agent_start and
        agent_end bracket handle_request, including the error path. Used
        a context-local for identity — your dispatcher runs tools in a
        thread pool, and the simpler approach would have mixed concurrent
        runs into one session without complaining.

        Verified against a real run: 11 events across 4 files —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, one session
        per request, durations paired.

        One thing I did NOT do: your worker pool in batch.py submits
        straight to the executor, so events from there would be dropped.
        Want me to fix those too?
```

התבנית שיש להשים לב אליה: היא קראה את הקוד לפני הצעה, שאלה רק את השאלות שאתם יכולים לענות עליהן, שימוש חוזר בid שכבר היה לכם, בחרה צורה בטוחה לתרגיל *כי* היא ראתה thread pool, ו**אמתה בקריאת האירועים הממשיים** במקום להצהיר על הצלחה — ואז סימנה את המקום היחיד שהיא ידעה יכול להיכשל בשקט.

## מה אתם יכולים לשאול אותו

- *"Why isn't my agent showing up on the dashboard?"* → הולך במדרגות: האם אירועים נכתבים, האם יש `agent_start`, האם ה-environment נכון, האם ה-collector קורא את אותו מקום.
- *"Everything's landing under dev."* → ה-environment לא הוגדר אי פעם, או הוא אופס על ידי קריאה מאוחרת יותר.
- *"Add token tracking."* → מוצא את ה-LLM wrapper שלכם ומתעד model, stop reason, ו-usage.
- *"Instrument the sub-agents too."* → session אחד, agent labels מובחנים, קן תחת ההורה שלהם.
- *"Write tests for the instrumentation."* → מכוונן את ה-SDK לתיקייה זמנית והוא asserts על האירועים שכתב.

## מה צריך להישמר

**תנו לו לאמת.** השלב שמעשיר skill זה שווה הוא האחרון — הרצה של ה-agent שלכם וקריאה של האירועים חזרה. agent שכתב instrumentation וחדל עשה את החצי הקל, והחצי שנכשל בשקט הוא השני.

**הסכימו על השמות לפני הקוד.** `session_id` ו-`agent_id` הם הצירים שכל משטח מקבץ לפיהם. שינוי שם שלהם מאוחר יותר מפצל את ההיסטוריה: runs ישנות שומרות על התוויות הישנות והמגמות שלכם שוברות. ה-skill ישאל; התשובה שווה דקה של חשיבה.

**אם ה-agent שלכם מציע התקנת ה-SDK מ-public index, ה-skill לא נטען.** ה-SDK מחולק בפרטיות. הצעה זו היא תזכורת אמינה שcoding agent שלכם מנחש במקום לעקוב אחרי ה-skill — עצרו את זה שם ובדקו שה-skill מותקן.

מעבר לכך רדיוס ההפוצץ שלו קטן: הוא כותב קוד בספריית ההפעלה שלכם וקובצי אירועים איפה שאתם אומרים. הוא לא קורא שום דבר מה-deployment שלכם ולא משנה שום דבר בו.
