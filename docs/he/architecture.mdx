מסמך זה מסביר כיצד failproofai פועל באופן פנימי: כיצד מערכת Hook חוטפת קריאות כלי agent, כיצד קונפיגורציה נטענת ומתמזגת, כיצד מדיניות מוערכת, וכיצד הדashboard עוקב אחרי פעילות agent.

---

## סקירה כללית

ל-failproofai יש שתי תת-מערכות עצמאיות:

1. **Hook handler** - תהליך CLI מהיר שClaude Code משדך בכל קריאת כלי agent. מערך מדיניות ומחזיר החלטה.
2. **Agent Monitor (Dashboard)** - יישום Next.js לניטור של פעילויות agent וניהול מדיניות.

שתי התת-מערכות חולקות קובצי קונפיגורציה ב-`~/.failproofai/` ובתיקייה `.failproofai/` של הפרויקט, אך הן פועלות כתהליכים נפרדים ותקשרו רק דרך מערכת הקבצים.

## Hook handler

### שילוב עם Claude Code

כאשר אתה מריץ `failproofai policies --install`, הוא כותב ערכים כמו אלה ל-`~/.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "failproofai --hook PreToolUse"
          }
        ]
      }
    ],
    "PostToolUse": [ ... ]
  }
}
```

Claude Code לאחר מכן משדך את `failproofai --hook PreToolUse` כתהליך משנה לפני כל קריאת כלי, תוך העברת payload JSON ב-stdin.

### פורמט Payload

```json
{
  "session_id": "abc123",
  "transcript_path": "/home/user/.claude/projects/myproject/sessions/abc123.jsonl",
  "cwd": "/home/user/myproject",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "sudo apt install nodejs" }
}
```

ל-`PostToolUse` events, ה-payload מכיל גם `tool_result` עם הפלט של הכלי.

ה-handler אוכף מגבלת stdin של 1 MB. Payloads העולים על זה נמחקים וכל המדיניות באופן סתום מאפשרת.

### פורמט תגובה

**Deny (PreToolUse):**
```json
{
  "hookSpecificOutput": {
    "permissionDecision": "deny",
    "permissionDecisionReason": "Blocked by failproofai: sudo command blocked"
  }
}
```

**Deny (PostToolUse):**
```json
{
  "hookSpecificOutput": {
    "additionalContext": "Blocked by failproofai because: API key detected in output"
  }
}
```

**Instruct (כל event מלבד Stop):**
```json
{
  "hookSpecificOutput": {
    "additionalContext": "Instruction from failproofai: Verify tests pass before committing."
  }
}
```

**Stop event instruct:**
- קוד יציאה: `2`
- סיבה כתובה ל-stderr (לא stdout)

**Allow:**
- קוד יציאה: `0`
- stdout ריק

**Allow with message:**

`allow(message)` מאפשר למדיניות לשלוח קשר מידע חזרה ל-Claude גם כאשר הפעולה מותרת. ה-hook handler כותב את ה-JSON הבא ל-**stdout** (לא קובץ config — זו תגובת ה-handler ל-Claude Code, בדיוק כמו deny ו-instruct responses למעלה):

```json
// Written to stdout by the hook handler process
{
  "hookSpecificOutput": {
    "additionalContext": "All CI checks passed on branch 'feat/my-feature'."
  }
}
```
- קוד יציאה: `0` (הפעולה מותרת)
- כאשר מדיניויות מרובות מחזירות `allow` עם הודעה, ההודעות שלהן מצטרפות עם שורות חדשות ל-`additionalContext` יחיד
- אם אף מדיניות לא מספקת הודעה, stdout ריק (כמו קודם)

### Processing pipeline

`src/hooks/handler.ts` מיישם את ה-pipeline המלא:

```text
stdin JSON
  → parse payload (max 1 MB)
  → extract session metadata (session_id, cwd, tool_name, tool_input, etc.)
  → readMergedHooksConfig(cwd)    ← merges project + local + global config
  → register enabled builtin policies with resolved params
  → load custom policies from customPoliciesPath (if set)
  → register custom policies into policy registry
  → evaluate all policies (builtins first, then custom)
      → first deny short-circuits
      → instruct decisions accumulate
      → allow messages accumulate
  → write JSON decision to stdout
  → persist event to ~/.failproofai/hook-activity/current.jsonl
  → exit
```

כל התהליך מתנהל תחת 100ms עבור payloads טיפוסיים ללא קריאות LLM.

## טעינת קונפיגורציה

`src/hooks/hooks-config.ts` מיישם טעינת config בתלת-סקופ.

```text
[1] {cwd}/.failproofai/policies-config.json        ← project  (highest priority)
[2] {cwd}/.failproofai/policies-config.local.json  ← local
[3] ~/.failproofai/policies-config.json             ← global   (lowest priority)
```

לוגיקת merge:
- `enabledPolicies` - union דדופליקציה על פני כל שלוש הקבצים
- `policyParams` - per-policy key, הקובץ הראשון שמגדיר אותו זוכה לגמרי
- `customPoliciesPath` - הקובץ הראשון שמגדיר אותו זוכה
- `llm` - הקובץ הראשון שמגדיר אותו זוכה

ה-web dashboard משתמש ב-`readHooksConfig()` (global only) לקריאה וכתיבה, מכיוון שהוא לא משדך עם project cwd.

## הערכת מדיניות

`src/hooks/policy-evaluator.ts` מריץ מדיניות בסדר.

עבור כל מדיניות:

1. חפש את ה-`params` schema של המדיניות (אם יש לה אחד).
2. קרא את `policyParams[policy.name]` מה-merged config.
3. מזג ערכים שסופקו על ידי המשתמש על ברירות מחדל של schema כדי לייצר `ctx.params`.
4. קרא ל-`policy.fn(ctx)` עם ההקשר שנוסחה.
5. אם התוצאה היא `deny`, עצור מייד והחזר את ההחלטה הזו.
6. אם התוצאה היא `instruct`, צבור את ההודעה והמשך.
7. אם התוצאה היא `allow`, המשך למדיניות הבאה.

לאחר שכל המדיניות תרוץ:
- אם הוחזר כל `deny`, פלוט את תגובת ה-deny.
- אם נאספו `instruct` returns, פלוט תגובת instruct אחת עם כל ההודעות מצטרפות.
- אחרת, פלוט תגובת allow (stdout ריק, exit 0).

## מדיניות builtin

`src/hooks/builtin-policies.ts` מגדיר את כל 39 המדיניויות המובנות כ-`BuiltinPolicyDefinition` objects:

```typescript
interface BuiltinPolicyDefinition {
  name: string;
  description: string;
  fn: (ctx: PolicyContext) => PolicyResult;
  match: {
    events: HookEventType[];
    tools?: string[];
  };
  defaultEnabled: boolean;
  category: string;
  beta?: boolean;
  params?: PolicyParamsSchema;
}
```

מדיניויות המקבלות `params` מצהירות על `PolicyParamsSchema` עם סוגים וברירות מחדל לכל פרמטר. ה-policy evaluator משדך ערכים שנוסחו ל-`ctx.params` לפני הקרא ל-`fn`. פונקציות מדיניות קוראות `ctx.params` ללא null-guarding מכיוון שברירות מחדל תמיד מיושמות תחילה.

התאמת דוגמה בתוך מדיניויות משתמשת בטוקנים פורסמים (argv), לא התאמה גולמית של מחרוזות. זה מונע עקיפה דרך הזרקת shell operator (למשל דוגמה עבור `sudo systemctl status *` לא יכולה להיות עקיפה על ידי הצמדת `; rm -rf /` לפקודה).

## מדיניויות מותאמות אישית

`src/hooks/custom-hooks-registry.ts` מיישם registry תומך ב-`globalThis`:

```typescript
const REGISTRY_KEY = "__failproofai_custom_hooks__";

export const customPolicies = {
  add(hook: CustomHook): void { ... }
};

export function getCustomHooks(): CustomHook[] { ... }
export function clearCustomHooks(): void { ... }  // used in tests
```

`src/hooks/custom-hooks-loader.ts` טוען את קובץ המדיניות של המשתמש:

1. קרא את `customPoliciesPath` מה-config; דלג אם חסר.
2. פתור לנתיב מוחלט; בדוק שהקובץ קיים.
3. כתוב מחדש את כל `from "failproofai"` imports לנתיב dist בפועל כדי `customPolicies` יפתור ל-registry `globalThis` זהה.
4. כתוב מחדש באופן רקורסיבי local imports חוצים כדי להבטיח תאימות ESM.
5. כתוב קבצים זמניים `.mjs` ו-`import()` את קובץ הכניסה.
6. קרא ל-`getCustomHooks()` לשליפת hooks רשומים.
7. נקה את כל קבצי הטמפ בבלוק `finally`.

בכל שגיאה (קובץ לא נמצא, שגיאת syntax, כישלון import), השגיאה מתורגלת ל-`~/.failproofai/hook.log` והטוען מחזיר מערך ריק. מדיניויות מובנות אינן מושפעות.

מדיניויות מותאמות אישית מוערכות לאחר כל המדיניויות המובנות. custom policy `deny` עדיין מקצר עוד custom policies (אך כל ה-builtins כבר רצו בנקודה זו).

## רישום פעילות

לאחר כל hook event, ה-handler מוסיף שורת JSONL ל-`~/.failproofai/hook-activity/current.jsonl`, שמסתובב ל-`page-<timestamp>-<seq>.jsonl` ברגע שהוא מגיע לעמוד:

```json
{
  "timestamp": "2026-04-06T12:34:56.789Z",
  "sessionId": "abc123",
  "eventType": "PreToolUse",
  "toolName": "Bash",
  "policyName": "block-sudo",
  "decision": "deny",
  "reason": "sudo command blocked by failproofai",
  "durationMs": 12
}
```

שורה אחת לכל מדיניות שהנתה החלטה שאינה allow. החלטות Allow לא מתורגלות (כדי להחזיק את הקובץ קטן).

## ארכיטקטורת Dashboard

ה-dashboard הוא יישום **Next.js 16** תוך שימוש ב-App Router עם React Server Components ו-Server Actions.

```text
app/
  layout.tsx                  ← Root layout (theme, telemetry, nav)
  projects/page.tsx           ← Server component: list all Claude projects
  project/[name]/page.tsx     ← Server component: list sessions in a project
  project/[name]/session/
    [sessionId]/page.tsx      ← Server component: render session viewer
  policies/page.tsx           ← Client component: policy management + activity log
  actions/
    get-hooks-config.ts       ← Read config + policy list
    update-hooks-config.ts    ← Toggle policy on/off
    update-policy-params.ts   ← Update policy parameters
    get-hook-activity.ts      ← Paginate/search activity log
    install-hooks-web.ts      ← Install/remove hooks from the browser
  api/
    download/[project]/[session]/route.ts   ← Per-CLI session export (JSONL or JSON)
```

**זרימת נתונים:**

- קומפוננטות עמוד קוראות `lib/projects.ts` ו-`lib/log-entries.ts` לקריאת נתוני פרויקט/session ישירות ממערכת הקבצים (אין API layer לקריאות).
- דף ה-Policies משתמש ב-Server Actions לכל המוטציות (toggle, params update, install/remove).
- ה-session viewer מפענח את פורמט ה-JSONL transcript של Claude וער מחדש ציר הזמן של הודעות וקריאות כלים.

**החלטות עיצוב מרכזיות:**

- אין מסד נתונים - כל המצב קבוע נמצא בקבצים רגילים (`~/.failproofai/`, `~/.claude/projects/`).
- Server Actions למוטציות - אין צורך ב-REST API עבור פעולות CRUD.
- React Server Components לדפי קריאה - טעינה ראשונית מהירה יותר, אין client bundle עבור fetch של נתונים.
- קומפוננטות client רק כאשר יש צורך באינטראקטיביות (policy toggles, activity search, log viewer).
