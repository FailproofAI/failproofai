מסמך זה מסביר כיצד failproofai עובד באופן פנימי: כיצד מערכת ה-hook מיירטת קריאות כלים של סוכנים, כיצד הקונפיגורציה נטענת ומוזגת, כיצד מדיניויות מוערכות, וכיצד לוח הבקרה מנטר פעילות סוכנים.

---

## סקירה כללית

ל-failproofai שתי תת-מערכות עצמאיות:

1. **Hook handler** - תהליך CLI מהיר שClaude Code מפעיל בכל קריאת כלי סוכן. מערך מדיניויות ומחזיר החלטה.
2. **Agent Monitor (Dashboard)** - יישומון ווב Next.js לניטור מפעילי סוכנים וניהול מדיניויות.

שתי התת-מערכות חולקות קבצי קונפיגורציה ב-`~/.failproofai/` ובתיקייה `.failproofai/` של הפרויקט, אך הן פועלות כתהליכים נפרדים ותקשרות רק דרך מערכת הקבצים.

## Hook handler

### אינטגרציה עם Claude Code

כאשר אתה מפעיל `failproofai policies --install`, הוא כותב ערכים כמו זה לתוך `~/.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "failproofai --hook PreToolUse"
          }
        ]
      }
    ],
    "PostToolUse": [ ... ]
  }
}
```

Claude Code אז מפעיל את `failproofai --hook PreToolUse` כתהליך משנה לפני כל קריאת כלי, תוך העברת payload JSON על stdin.

### פורמט Payload

```json
{
  "session_id": "abc123",
  "transcript_path": "/home/user/.claude/projects/myproject/sessions/abc123.jsonl",
  "cwd": "/home/user/myproject",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "sudo apt install nodejs" }
}
```

עבור אירועי `PostToolUse`, ה-payload מכיל גם `tool_result` עם פלט הכלי.

ה-handler אוכף הגבלת stdin של 1 MB. Payloads שחוצים זאת מושלכים וכל המדיניויות מרשות באופן משתמע.

### פורמט תגובה

**Deny (PreToolUse):**
```json
{
  "hookSpecificOutput": {
    "permissionDecision": "deny",
    "permissionDecisionReason": "Blocked by failproofai: sudo command blocked"
  }
}
```

**Deny (PostToolUse):**
```json
{
  "hookSpecificOutput": {
    "additionalContext": "Blocked by failproofai because: API key detected in output"
  }
}
```

**Instruct (כל אירוע חוץ Stop):**
```json
{
  "hookSpecificOutput": {
    "additionalContext": "Instruction from failproofai: Verify tests pass before committing."
  }
}
```

**אירוע Stop instruct:**
- קוד יציאה: `2`
- סיבה כתובה ל-stderr (לא stdout)

**Allow:**
- קוד יציאה: `0`
- stdout ריק

**Allow עם הודעה:**

`allow(message)` מאפשר למדיניות לשלוח הקשר מידע חזרה ל-Claude גם כאשר הפעולה מורשית. ה-hook handler כותב את ה-JSON הבא ל-**stdout** (לא קובץ קונפיגורציה — זה תגובת ה-handler ל-Claude Code, בדיוק כמו תגובות deny ו-instruct למעלה):

```json
// Written to stdout by the hook handler process
{
  "hookSpecificOutput": {
    "additionalContext": "All CI checks passed on branch 'feat/my-feature'."
  }
}
```
- קוד יציאה: `0` (הפעולה מורשית)
- כאשר מדיניויות מרובות מחזירות `allow` עם הודעה, ההודעות שלהן מחוברות עם שורות חדשות ל-`additionalContext` יחיד
- אם אף מדיניות לא מספקת הודעה, stdout ריק (כמו קודם)

### Pipeline עיבוד

`src/hooks/handler.ts` מיישם את ה-pipeline המלא:

```text
stdin JSON
  → parse payload (max 1 MB)
  → extract session metadata (session_id, cwd, tool_name, tool_input, etc.)
  → readMergedHooksConfig(cwd)    ← merges project + local + global config
  → register enabled builtin policies with resolved params
  → load custom policies from customPoliciesPath (if set)
  → register custom policies into policy registry
  → evaluate all policies (builtins first, then custom)
      → first deny short-circuits
      → instruct decisions accumulate
      → allow messages accumulate
  → write JSON decision to stdout
  → persist event to ~/.failproofai/hook-activity/current.jsonl
  → exit
```

התהליך כולו פועל בפחות מ-100ms עבור payloads טיפוסיים ללא קריאות LLM.

## טעינת קונפיגורציה

`src/hooks/hooks-config.ts` מיישם טעינת קונפיגורציה בעלת שלוש-סקופ.

```text
[1] {cwd}/.failproofai/policies-config.json        ← project  (highest priority)
[2] {cwd}/.failproofai/policies-config.local.json  ← local
[3] ~/.failproofai/policies-config.json             ← global   (lowest priority)
```

לוגיקת מיזוג:
- `enabledPolicies` - איחוד מפוזר בכל שלושת הקבצים
- `policyParams` - לכל מדיניות מפתח, הקובץ הראשון שמגדיר אותו מנצח לחלוטין
- `customPoliciesPath` - הקובץ הראשון שמגדיר אותו מנצח
- `llm` - הקובץ הראשון שמגדיר אותו מנצח

לוח הבקרה ווב משתמש ב-`readHooksConfig()` (גלובלי בלבד) לקריאה וכתיבה, מכיוון שהוא לא מופעל עם cwd של פרויקט.

## הערכת מדיניות

`src/hooks/policy-evaluator.ts` מפעיל מדיניויות לפי סדר.

עבור כל מדיניות:

1. חפש את סכימת ה-`params` של המדיניות (אם יש לה כזו).
2. קרא את `policyParams[policy.name]` מהקונפיגורציה המוזגת.
3. מזוג ערכים שסופקו על ידי משתמש על ברירות מחדל של סכימה לייצור `ctx.params`.
4. קרא ל-`policy.fn(ctx)` עם ההקשר שנפתר.
5. אם התוצאה היא `deny`, עצור מיד והחזר את ההחלטה הזו.
6. אם התוצאה היא `instruct`, צבור את ההודעה והמשך.
7. אם התוצאה היא `allow`, המשך למדיניות הבאה.

לאחר שכל המדיניויות פעלו:
- אם `deny` כלשהו הוחזר, פלוט את תגובת ה-deny.
- אם התאספו `instruct` החזרות, פלוט תגובת instruct יחידה עם כל ההודעות חיברו.
- אחרת, פלוט תגובת allow (stdout ריק, יציאה 0).

## מדיניויות מובנות

`src/hooks/builtin-policies.ts` מגדיר את כל 39 המדיניויות המובנות כאובייקטי `BuiltinPolicyDefinition`:

```typescript
interface BuiltinPolicyDefinition {
  name: string;
  description: string;
  fn: (ctx: PolicyContext) => PolicyResult;
  match: {
    events: HookEventType[];
    tools?: string[];
  };
  defaultEnabled: boolean;
  category: string;
  beta?: boolean;
  params?: PolicyParamsSchema;
}
```

מדיניויות שמקבלות `params` מצהירות על `PolicyParamsSchema` עם סוגים וברירות מחדל עבור כל פרמטר. מערך הערכת המדיניות מזריק ערכים שנפתרו ל-`ctx.params` לפני קריאה ל-`fn`. פונקציות מדיניות קוראות ל-`ctx.params` ללא null-guarding מכיוון שברירות מחדל תמיד מיושמות קודם.

התאמת דפוס בתוך מדיניויות משתמשת בטוקנים של פקודה מנותחים (argv), לא התאמה של מחרוזות גולמיות. זה מונע עקיפה דרך הזרקת מפעילי קליפה (למשל, דפוס עבור `sudo systemctl status *` לא יכול להיות עוקף על ידי הוספת `; rm -rf /` לפקודה).

## מדיניויות מותאמות

`src/hooks/custom-hooks-registry.ts` מיישם רושם המאומת ברגיסטרציה של `globalThis`:

```typescript
const REGISTRY_KEY = "__failproofai_custom_hooks__";

export const customPolicies = {
  add(hook: CustomHook): void { ... }
};

export function getCustomHooks(): CustomHook[] { ... }
export function clearCustomHooks(): void { ... }  // used in tests
```

`src/hooks/custom-hooks-loader.ts` טוען את קובץ המדיניות של המשתמש:

1. קרא את `customPoliciesPath` מהקונפיגורציה; דלג אם חסר.
2. פתור לנתיב מוחלט; בדוק את קיום הקובץ.
3. כתוב מחדש את כל `from "failproofai"` import לנתיב dist בפועל כדי ש-`customPolicies` יוביל לרושם `globalThis` זהה.
4. כתוב מחדש ברקורסיה יבוא מקומי טרנזיטיבי כדי להבטיח תאימות ESM.
5. כתוב קבצי `.mjs` זמניים ו-`import()` את קובץ הכניסה.
6. קרא ל-`getCustomHooks()` כדי לאחזר קוקי רשומים.
7. נקה את כל הקבצים הזמניים בבלוק `finally`.

בכל שגיאה (קובץ לא נמצא, שגיאת תחביר, כשל import), השגיאה מתועדת ל-`~/.failproofai/hook.log` והטוען מחזיר מערך ריק. מדיניויות מובנות אינן מושפעות.

מדיניויות מותאמות מוערכות לאחר כל המדיניויות המובנות. `deny` של מדיניות מותאמת עדיין מקצר מדיניויות מותאמות נוספות (אך כל המובנות כבר פעלו בשלב זה).

## רישום פעילות

לאחר כל אירוע hook, ה-handler מוסיף שורת JSONL ל-`~/.failproofai/hook-activity/current.jsonl`, שמסתובבת ל-`page-<timestamp>-<seq>.jsonl` ברגע שהיא מגיעה לעמוד:

```json
{
  "timestamp": "2026-04-06T12:34:56.789Z",
  "sessionId": "abc123",
  "eventType": "PreToolUse",
  "toolName": "Bash",
  "policyName": "block-sudo",
  "decision": "deny",
  "reason": "sudo command blocked by failproofai",
  "durationMs": 12
}
```

שורה אחת לכל מדיניות שנתנה החלטה שאינה מרשה. החלטות Allow לא מתועדות (כדי לשמור את הקובץ קטן).

## ארכיטקטורת Dashboard

Dashboard הוא יישומון **Next.js 16** המשתמש ב-App Router עם React Server Components ו-Server Actions.

```text
app/
  layout.tsx                  ← Root layout (theme, telemetry, nav)
  projects/page.tsx           ← Server component: list all Claude projects
  project/[name]/page.tsx     ← Server component: list sessions in a project
  project/[name]/session/
    [sessionId]/page.tsx      ← Server component: render session viewer
  policies/page.tsx           ← Client component: policy management + activity log
  actions/
    get-hooks-config.ts       ← Read config + policy list
    update-hooks-config.ts    ← Toggle policy on/off
    update-policy-params.ts   ← Update policy parameters
    get-hook-activity.ts      ← Paginate/search activity log
    install-hooks-web.ts      ← Install/remove hooks from the browser
  api/
    download/[project]/[session]/route.ts   ← Per-CLI session export (JSONL or JSON)
```

**זרימת נתונים:**

- רכיבי עמוד קוראים ל-`lib/projects.ts` ו-`lib/log-entries.ts` כדי לקרוא נתוני פרויקט/מפעיל ישירות מאת מערכת הקבצים (אין שכבת API לקריאות).
- עמוד המדיניויות משתמש ב-Server Actions לכל מוטציות (toggle, עדכון params, התקנה/הסרה).
- מנצח מפעיל מנתח את פורמט תמליל JSONL של Claude ומעביר אפיון של הודעות וקריאות כלים.

**החלטות עיצוב מפתח:**

- אין מסד נתונים - כל מצב קבוע הוא בקבצים רגילים (`~/.failproofai/`, `~/.claude/projects/`).
- Server Actions למוטציות - אין צורך ב-REST API לפעולות CRUD.
- React Server Components לעמודי קריאה - טעינה ראשונית מהירה יותר, ללא צרור client לעיבוד נתונים.
- רכיבי client רק שבו אינטראקטיביות נדרשת (toggles מדיניות, חיפוש פעילות, מנצח log).
