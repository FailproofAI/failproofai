התראה עוקבת אחר תנאי ניתן למדידה ופותחת בעיה כאשר היא מופעלת. השתמש בה כאשר כשל צריך להניב תגובה בזמן, בין אם מדיניות יכולה לחסום אותו או לא.

## יצירה ובדיקה של התראה

<Tabs>
  <Tab title="Dashboard">
    1. עבור אל **Analyze → Alerts** ובחר **new alert**. אתה יכול גם להתחיל מפעמון בשגיאה מייצגת.
    2. הזן את השם, החומרה, סוג הטריגר, התנאי, מרווח הערכה, ספירת ההפרה, חלון, וערוצים.
    3. שמור את ההתראה, פתח את עמוד הפרטים שלה, והפעל **test**.
    4. עבור אל **Analyze → Issues** כדי להודות, להקצות, לדון, להירשם, ולפתור את הבעיות שההתראה פותחת.

    החלק הראשון של הטופס מזהה את ההתראה והאות שצריכה להפעיל אותה.

    ![החלק הראשון של טופס new-alert עם שם, תיאור, מצב מאופשר, וסוג טריגר.](/images/dashboard/alert-new-trigger.png)

    החלק השני שולט כמה זמן התנאי חייב להישמר, כמה לעתים קרובות הוא מוערך, והיכן משלחות הודעות מועברות.

    ![החלק השני של טופס new-alert עם לוגיקה הפרה, לוח זמנים, חומרה, ערוצי משלוח, ויצירת פעולה.](/images/dashboard/alert-new-routing.png)

    לאחר שמירה, השתמש ברשימת ההתראות כדי לאשר שהכלל מאופשר וש-trigger, חלון, חומרה וערוצים שלו תואמים את המתוכננים. כרטיס שיש לו בעיות פתוחות מציג את הספירה; כרטיס ללא ספירה משמיט את השורה לגמרי, כך שעדותו של אי-נוכחותה אומרת לך כלום. כדי לקרוא את הנתון לכל כלל כולל אפסים, השתמש ב-`fp alerts show <name>`, שתמיד מדפיס אותו.

    ![עמוד התראות המציג כללי התראה עם triggers, חלונות הערכה, ערוצים וחומרה.](/images/dashboard/alerts.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp alerts create high-errors \
      --trigger-kind metric_threshold \
      --severity warning \
      --trigger-spec '{"metric":"error_count","op":">","value":50,"window_secs":900}' \
      --eval-interval-secs 300 \
      --min-breaches 2 \
      --eval-window 3

    fp alerts show high-errors
    fp alerts test high-errors
    fp alerts update high-errors --severity critical --yes
    ```

    התראות חדשות מתחילות **enabled**, וההתנגשות של שם נדחית לפני שיוצר משהו.

    `fp alerts update` מחליף את כל ההגדרה בצד השרת, כך שהCLI קורא מחדש את ההתראה ושוכב את הדגלים שלך על גבי — עדכון דגל בלבד צריך `alerts:read` **כמו גם** `alerts:write`, והוא מאשר אלא אם תעביר `--yes`.

    השתמש ב-`fp alerts list` לסקירת כללים ו-`fp alerts delete <name>` להסרת כלל אחד. מחיקה משפירה את הכלל — כולל ספירת הבעיות הפתוחות שלו — ומאשרת לפני פעולה, מכיוון שלא ניתן לבטל זאת.

    מחיקה היא לא הדרך להשתיק כלל רועם. `DELETE /alerts/{id}` מדורגות: כל בעיה שההתראה פתחה אי פעם הולכת איתה, לוקחת את התגובות, המנויים וההיסטוריה של הפעילות שלה. קופסת האישור של ה-CLI מנסחת זאת בבעיות הפתוחות מיותמות; חוזה ה-API הוא מחיקה דרוגה, כך שתייחס להיסטוריה כאבודה. כדי להפסיק כלל חיזוי וליצור את מה שנרשם, כבה אותו במקום זאת — טופס ההתראה של הלוח המחוונים יש את כפתור enabled, ולא `fp alerts create` ולא `fp alerts update` חושפים דגל `--enabled`, כך שנתיב ה-CLI הוא `fp alerts update <name> --file` עם הגדרה מלאה נושא `enabled: false`.

    ראה את ה-[`fp alerts` reference](/he/reference/cloud-cli#alerts) לקבוצת הפקודות המלאה של ההתראה.
  </Tab>
</Tabs>

<Warning>
  **test** מספק הודעות אמיתיות. זה שולח לערוצי דוא"ל, Slack וwebhook אמיתיים של ההתראה ופותח בעיה סינתטית, כך שזה יכול לעמוד למי שנמצא בתורנות. הוא מאשר תחילה במסוף אינטראקטיבי; `--yes`, `--json`, וstdin מופנה הכל דילוג על הנושא ההוא. השרת גם מדווח על הצלחה ברגע שהוא משדר, כך שבדיקה ירוקה מוכיחה שההודעה עזבה, לא שהגיעה.
</Warning>

## הגדרת ה-Trigger

ישנם חמישה סוגי טריגר:

| `--trigger-kind` | מופעל כאשר |
| --- | --- |
| `metric_threshold` | מטרי חוצה סף — שגיאות, השהייה, עלות, או כל דבר אחר שאתה יכול למדוד. |
| `per_event` | אירוע משחק יחיד מגיע. |
| `evaluation_score` | ניקוד של מעריך חוצה סף. |
| `eval_compound` | כמה תנאי ניקוד משתלבים, כגון שנים משלוש ניקודים נכשלים. |
| `custom_sql` | שאילתה שכתבת מחזירה הפרה. |

התנאי עצמו הולך ל-`--trigger-spec`, מעוצב לסוג שבחרת.

## הגדר את מספרי ההערכה

טופס הלוח המחוונים וה-CLI מבקשים את אותם ארבע ערכים.

| הגדרה | דגל | ערכים מקובלים |
| --- | --- | --- |
| חומרה | `--severity` | `info`, `warning`, `critical` |
| מרווח הערכה | `--eval-interval-secs` | 30–86,400 שניות |
| ספירת הפרה | `--min-breaches` | לפחות 1, ולא יותר מהחלון |
| חלון הערכה | `--eval-window` | לפחות 1, נספר ב-**intervals**, לא שניות |

אז `--eval-interval-secs 300 --min-breaches 2 --eval-window 3` פירושו "הערוך כל חמש דקות, וירוי כששנים מן שלוש ההערכות האחרונות הופרו".

## עיצוב התראה טוב

- שם את התנאי וזרימת העבודה המושפעת.
- תחום את הסביבה באופן מפורש.
- הגדר חלון וסף המונעים תגובה לאירוע חסר משמעות יחיד.
- כלול קישור או שאילתה שמובילה משיבים לפגישות.
- הקצה בעלים לפני הפעלת הכלל.
- בדוק `fp alerts show <name>` לספירת הבעיות הפתוחות לפני הוספת כלל אחר לאותו סימפטום. כרטיס הלוח המחוונים מדפיס את השורה ההיא רק כאשר הספירה אינה אפס.

<Tip>
  לאחר פתרון ממצא ביקורת, הוסף התראה כאשר אותו כשל יכול להתרחש שוב מחוץ לכיסוי המדיניות.
</Tip>
