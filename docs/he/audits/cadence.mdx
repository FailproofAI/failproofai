השתמש בביקורות חוזרות עבור מצבי כשל שיכולים להופיע מחדש כאשר סוכנים, הנחיות, כלים ומודלים משתנים.

## שינוי לוח הזמנים

<Tabs>
  <Tab title="Dashboard">
    1. עבור ל-**Analyze → Audits** ופתח את הביקורת.
    2. בחר **edit settings** והשנה את הקצב, החלון, הרגישות, או את מספר הממצאים בכל הרצה.
    3. שמור את הביקורת ואשר את זמן ההרצה הבא בכותרת הביקורת.
    4. השהה וחזור לתזמן מאותה כותרת, ליד **run now**.
    5. השתמש ב-**run now** פעם אחת לאחר שינוי טווח או קשר משמעותי.

    ![כותרת ביקורת המציגה את מצבה המושהה, ממצאים פתוחים, הרצה אחרונה, הרצה הבאה, חלון סריקה ורגישות, עם בקרות run now, edit settings ו-resume.](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits edit checkout-reliability \
      --schedule-interval-secs 86400 \
      --schedule-anchor 2026-08-15T09:00:00Z \
      --window-mode since_last \
      --lookback-window-secs 86400 \
      --yes

    fp audits edit checkout-reliability --disabled --yes
    fp audits edit checkout-reliability --enabled --yes
    ```

    `fp audits edit` מבקש אישור לפני שינוי משהו, וזו הסיבה שכל דוגמה כאן מעבירה `--yes`. השרת מחליף את כל ההגדרה בכל עריכה, ולכן ה-CLI שולח מחדש את הביקורת הנוכחית עם השינויים שלך המיושמים — עריכה שמשתמשת רק בדגלים דורשת `audits:read` **וגם** `audits:write`. הגדר מפתח CI לשניהם.

    ראה את ה-[`fp audits` reference](/he/reference/cloud-cli#audits) עבור גבולות לוח הזמנים, התנהגות החלון, וכל פקודות הביקורת.
  </Tab>
</Tabs>

## שני גבולות לוח הזמנים

כל המלצה להלן חייבת להתאים בתוכם. הטווחים הם של השרת, ו-`fp` משקף אותם בצד הלקוח, כך שערך מחוץ לטווח יוצא עם קוד 2 מקומי ולא עולה בעלות של סבב 422.

| שדה | דגל | טווח | ברירת מחדל |
| --- | --- | --- | --- |
| Schedule interval | `--schedule-interval-secs` | 3,600–604,800 שניות (שעה אחת עד 7 ימים) | 86,400 (יומי) |
| Lookback window | `--lookback-window-secs` | 3,600–7,776,000 שניות (שעה אחת עד 90 ימים) | 604,800 (7 ימים) |

שבעה ימים הם הגבול העליון על הקצב. אין ביקורת Cloud חודשית.

## בחר קצב

בחר מבחינת מהירות ועלות של הסיכון:

| דפוס סיכון | קצב התחלה |
| --- | --- |
| פעולת ייצור בעלת השפעה גבוהה | יומי, או כל שעה בזמן שינוי מסוכן נוחת |
| רגרסיה של זרימת עבודה או מודל | שבועי |
| ביקורת ממשל או גישה | שבועי — הפרק הזמני הארוך ביותר זמין |

יישר את חלון ההחזר אחורה עם הקצב כך שהריצות לא יוותרו פערים וגם לא בחנו מחדש באופן מיותר אוכלוסייה גדולה.

אין ביקורת חד-פעמית; כל ביקורת נושאת מרווח לוח זמנים. לחקירת שחרור, צור אותה מופעלת, תן לריצה הראשונה לירות — הריצה הראשונה מתורגמת מיד ב-create, ללא קשר לעוגן — ואז השהה אותה עם `fp audits edit <name> --disabled --yes`. הפעל מחדש לפני שימוש ב-**run now**: ביקורת מושהה אין לה שורת תור, וריצה ידנית כנגד אחת מסורבת עם 409.

## חלון mode ו-anchor

`--window-mode` מחליט איזה חלון כל ריצה סורקת:

| Mode | התנהגות |
| --- | --- |
| `since_last` | המשך מסוף החלון שנותח לחלוטין בעבר, כך שריצה דלוגה לא תוותר פער. |
| `fixed` | בחן מחדש `lookback_window_secs` מתגלגל בכל ריצה, ללא קשר למה שהריצה האחרונה כיסתה. |

`--schedule-anchor` קובע את הפאזה ולא את התדירות: ריצות נוחתות ב-`anchor + N × interval`. השמט אותו והעוגן מתגדר ברירת מחדל לשעה 09:00 UTC הבאה; עוגן למעלה מ-365 ימים חוצה מעוגן מדורג. שינוי הרווח או העוגן נכנסים לתוקף בהזמנה הבאה, לא בריצה כבר מעומדת בתור, וריצה כושלת אינה מעבירה את העוגן.

לאחר שינוי המטרה או ההקשר של ביקורת, הרץ אותה ידנית פעם אחת לפני שתסתמך על תוצאת זמן הלוח הבאה.

<Note>
  דף זה עוסק בלוח זמנים ביקורת Cloud, אשר פועלים בתוך ישיבות Cloud. לביקורת המקומית יש טיימר משלה: `failproofai audit --schedule [days]` לוקח 1–90 ימים וברירת מחדל 7, סורק את היסטוריית הסוכן באותה מכונה אחת, וזה המשטח היחיד עם אפשרות חודשית. התוצאות והבעלות שלה נפרדות מכל דבר כאן — ראה [Audit local agent history](/he/audits/local-audit).
</Note>
