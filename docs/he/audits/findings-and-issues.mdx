ממצא הוא הצהרה מגובה עדויות של הביקורת על כשל. סוגיה היא זרימת עבודה עמידה להתגובה אליה.

שני האובייקטים משתמשים בווקבולריון שונה, והם נמצאים זה לצד זה, ולכן כדאי לתקן אותם בראש קודם כל:

| | ממצא | סוגיה |
| --- | --- | --- |
| מצבים | `open`, `recurring`, `resolved`, `dismissed`, `muted` | `firing`, `acknowledged`, `resolved` |
| דגל סינון | `--status` | `--state` |
| הנדל | מזהה ממצא | מזהה סוגיה |
| רשימה ברירת מחדל | הסט החי: פתוח בתוספת חוזר | החדש ביותר שנפתח קודם |

## סיווג והקצאת העבודה

<Tabs>
  <Tab title="Dashboard">
    1. פתח **Analyze → Audits**, בחר הרצה שהושלמה, ובחר ממצא כדי לבחון את הניתוח, ההמלצה, ההפעלות והשאילתות הראיות שלו.
    2. הודע, הקצה, דחה, השתק, פתור או פתח מחדש את הממצא לאחר בדיקת הראיות שלו.
    3. עבור ל**Analyze → Issues** ופלטר את תיבת הדואר העמידה לפי מצב, חומרה או מוקצה.
    4. פתח את הסוגיה כדי להקצות אותה, הוסף הערות או מנויים, ופתור אותה לאחר אימות התיקון.

    התחל בסיכום הממצא. אשר שתיאור הכשל, התגובה המומלצת, החומרה והדירוג מסכימים עם ההפעלות שציפית שהביקורת תבחן.

    לאחר מכן, פתח הפעלה מושפעת במקום להחליט רק מהסיכום. המעקב המקושר צריך להציג את האירוע המדויק ותוכן העומס התומכים בממצא.

    לאחר אימות הראיות, השתמש בסוגיות כדי להעניק לתגובה בעלים ולעקוב אחריה ללא תלות בהרצות ביקורת עתידיות.

    פתח את הסוגיה כדי להקליט הערות חקירה, להודיע למנויים ולשמור על היסטוריית התגובה. פתור אותה רק לאחר שהתיקון פורס ואומת.

  <Tab title="CLI">
    ```bash
    fp audits findings --audit checkout-reliability --status open
    fp audits finding <finding-id>
    fp audits ack <finding-id> --reason "owner assigned"
    fp audits assign <finding-id> --to engineer@example.com
    fp audits mute <finding-id> --reason "expected in staging" --yes
    fp audits dismiss <finding-id> --reason "false positive" --yes
    fp audits resolve <finding-id> --yes
    fp audits reopen <finding-id>

    fp issues list --state firing
    fp issues show <issue-id>
    fp issues ack <issue-id>
    fp issues assign <issue-id> --assignee engineer@example.com
    fp issues comment-add <issue-id> --body "policy is in observe mode"
    fp issues resolve <issue-id> --yes
    ```

    `mute`, `dismiss` ו-`resolve` דוכאים או סוגרים ממצא, כך שכל אחד מאשר קודם — עבור `--yes` בסקריפטים. `ack`, `reopen` ו-`assign` הם רישום הפיך ופועלים מיד. `ack`, `mute` ו-`dismiss` לוקחים `--reason`, וכדאי להעביר: זה נשמר כעדות עמידה על הממצא, לא כתוב ביומן וזכור. `resolve`, `reopen` ו-`assign` לא לוקחים סיבה.

    הקצאה פועלת בצורה שונה בכל אובייקט. `fp audits assign` דורש `--to <email>` וקובע בעלים אחד; הרצה חוזרת מקצה מחדש. `fp issues assign` לוקח חזיק חוזר `--assignee` ו**מחליף** את הרשימה כולה, כך שהשמטה שלו מוחקת כל מוקצה.

    השתמש ב-`fp issues comment-list <issue-id>`, `fp issues count --state firing`, ו-`fp issues subscribe`/`unsubscribe`/`subscribers <issue-id>` עבור שאר משטח הסוגיה.

    ראה את ה-[Cloud CLI audit and issue reference](/he/reference/cloud-cli#audits) עבור ממצאי ביקורת ו-[`fp issues`](/he/reference/cloud-cli#issues) לניהול סוגיות.

## בדוק ממצא

שני שדות מחליטים מה לעשות איתו לפני שום דבר אחר.

**`kind`** מפריד בין `failure` (משהו השתבש) ל-`policy` violation (כלל שנשבר) ו-`improvement` (העבודה יכולה להיעשות טוב יותר). הוא מוצג כתגית בממצא. ממצא `policy` הוא זה שמדיניות יכולה לסגור; שני האחרים בדרך כלל צריכים שינוי זרימת עבודה, התראה או אדם.

**`priority`** היא ציון 0–1, מחושב מחדש לכל הרצה, וזה הסדר שתור הממצא ממוין בו. דף הממצא מפרק את זה תחת **why it ranks here**, כערך × משקל:

| גורם | משקל |
| --- | --- |
| Coverage | 0.30 |
| Severity | 0.25 |
| Magnitude | 0.25 |
| Recency | 0.20 |

לאחר מכן אשר שהממצא מכיל:

- מצב כשל יציב, לא רק כותרת חד פעמית
- חומרה והשפעה תפעולית
- מזהי הפעלה מושפעים או שאילתות תומכות
- הקשר מספיק לשחזור ההתנהגות
- תגובה מוצעת התואמת את הראיות

כדי לשחזר ממצא, משוך את זה במלואו: `fp --json audits finding <id>` מחזיר את הרשומה המלאה עם `evidence`, `evidence_queries` ו-`scope` שלה ללא שינוי, וזה מה שהניתוח בעצם הרץ. `--json` הוא אפשרות גלובלית, כך שהוא הולך לפני הפקודה.

## השתמש בסוגיה לניהול התגובה

צור או קשר סוגיה כאשר הממצא צריך הקצאה, דיון, שינויי מצב, הערות או מנויים. `source` של סוגיה רושם מכיוון היא באה — `audit`, `alert`, או `manual` — וזו הסיבה שהלוח נותן לסוגיות את התצוגה **Issues** שלהן בעצמן במקום ההנדסה שלהן מתחת לביקורת.

רישום חניכה הוא בחלקו אוטומטי. אנשים נרשמים כאשר הם מודים בסוגיה, מגיבים עליה, מוקצים אליה, או פותחים אותה — `fp issues subscribers` מפרט מנויים פעילים בלבד, כך שזה לא רק רשימת ההרשמות הידניות. הערה משדרת דוא"ל לכל מנוי פעיל, והערה זקוקה רק ל-`issues:read`, כך שצופה לקריאה בלבד לא מעולם צופה שקט.

פתור את הסוגיה כאשר התיקון פורס ואומת. פתור את הממצא כאשר מצב הכשל התייחס לאוכלוסיית הביקורת. רגעים אלה עשויים להיות שונים.

## הפוך סוגיה לטיוטת מדיניות

<Tabs>
  <Tab title="Dashboard">
    1. פתח את הסוגיה ואמת את הממצא שלה, הפעלות מצוטטות, גורם שורש והמלצה.
    2. בחר **generate policy** ובדוק את תוצאת הכשירות והכוונת האכיפה המוצעת. תוצאה **no policy** פירושה שההתנהגות עשויה לדרוש התראה, שינוי זרימת עבודה או תגובה אנושית במקום זאת.
    3. בחר **write this policy**, ואז בדוק ובדוק את המקור שנוצר ב**Admin → policy editor** לפני בחירת **publish version**. השתמש ב-**open the editor anyway** כאשר אתה לא מסכים עם בדיקת הכשירות.
    4. עבור ל**Admin → enforcement**, פרוס את הגרסה ב**observe** mode, ואמת את הההחלטות שלה תחת **Observe → policy** לפני אכיפה.

    כותרת הסוגיה, תיאור הממצא, גורם השורש, ההמלצה וכוונת הכשירות עוזרים להרכיב את הטיוטה. כלום אינו פורסם או פורס באופן אוטומטי.
  </Tab>
  <Tab title="CLI">
    השתמש ב-CLI לבדוק את הראיות לפני פתיחת הסוגיה בלוח:

    ```bash
    fp issues show <issue-id>
    fp --json audits finding <finding-id>
    fp events --session-id <session-id> --full --all
    ```

    הלוח הוא נתיב אחד; ה-CLI הוא השני. `fp policies compose "<what it should do>"` משכות מדיניות, `fp policies publish <id> ./policy.mjs` טבע גרסה (הפרסום לא פורס כלום), ו-`fp fleet deploy <machine> --add <id>:observe` שם אותה על מכונה בצל. הסיומת `:observe` נדרשת — `--add <id>` חשוף אכיפה מיד. קרא מה זה היה עושה עם `fp guardrails summary --since 24h`, ואז קדם עם `--add <id>:enforce`.

    כדי לנסות מקור מדיניות שווה ערך על המכונה שלך קודם כל, הצבע את ה-CLI המקומי בקובץ:

    ```bash
    failproofai policies -i -c ./checkout-policies.js
    ```

    קובץ ששמו מסתיים ב-`policies.js`, `policies.mjs` או `policies.ts`, שנשמט לתוך `.failproofai/policies/` בפרויקט או תחת `~/`, הוא טעון בכל אירוע hook ללא דגלים בכלל.
  </Tab>
</Tabs>
