הפעל ביקורת לאחר שהמטרה והאוכלוסייה שלה ספציפיות מספיק כך שמפעיל אחר יידע איך נראה ממצא תקף.

## הפעלה וסקירה

<Tabs>
  <Tab title="Dashboard">
    1. עבור אל **Analyze → Audits**, פתח את הביקורת, ובחר **run now**. תשובה בתור פירושה שה-dispatcher יתחיל אותה בקרוב.
    2. פתח את ההפעלה החדשה כדי לסקור את הסטטוס שלה, החלון, הזמן, ספירת הממצאים, והדוח.
    3. בחר בהפעלת הוכחה כדי לפתוח את העקבות המדויקות.
    4. חזור לעמוד הביקורת כדי לערוך הגדרות, להשבית את לוח הזמנים, או לבדוק הפעלות ישנות יותר.

    ![עמוד פרטי ביקורת עם ממצאים פתוחים, מצב ההפעלה האחרון והבא, חלון הסריקה, הקשר, בקרת run-now, וממצאים מדורגים.](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits run checkout-reliability
    fp audits runs checkout-reliability --limit 10
    fp --json audits runs checkout-reliability
    fp audits findings --audit checkout-reliability
    ```

    `fp audits run` מציב את הביקורת בתור; היא לא מחכה לה. עקוב זאת עם `fp audits runs <name>` וקרא את הממצאים לאחר שהפעלה הסתיימה. `--limit` לעולם לא מחזיר יותר מ-50 ההפעלות האחרונות ביותר, לא משנה מה אתה מבקש.

    Triage פועל על מזהה ממצא, לא על הביקורת:

    ```bash
    fp audits finding <finding-id>
    fp audits ack <finding-id> --reason "owner assigned"
    fp audits assign <finding-id> --to engineer@example.com
    fp audits mute <finding-id> --reason "expected in staging" --yes
    fp audits dismiss <finding-id> --reason "false positive" --yes
    fp audits resolve <finding-id> --yes
    fp audits reopen <finding-id>
    ```

    `mute`, `dismiss`, ו-`resolve` מאשרים לפני פעולה, אז עבור `--yes` בסקריפטים. `ack`, `assign`, ו-`reopen` פועלים מיד.

    ראה את [`fp audits` reference](/he/reference/cloud-cli#audits) לרשומת הפעלה, ממצאים, ופקודות triage.
  </Tab>
</Tabs>

**run now** יכול להיות מסורב. הפעלה כבר בתהליך וביקורת משבתת שניהם עונים `409`, כשהסיבה בשדה `error` של התגובה; ביקורת שאינה קיימת, או ששייכת לארגון אחר, עונה `404`.

| סירוב | המשמעות | מה לעשות |
| --- | --- | --- |
| ביקורת לא ידועה | הביקורת אינה קיימת, או היא שייכת לארגון אחר. | אשר את השם עם `fp audits list`. |
| הביקורת משבתת | לביקורת משבתת אין שורת תור, אז אין מה להפוך לדחוף. ביקורת מושהית עדיין מציגה בקרת **run now**. | חזור להפעיל אותה קודם, או `fp audits edit <name> --enabled --yes`. |
| הפעלה כבר בתהליך | הפעלה אחת לכל ביקורת בכל פעם; ההפעלה הנוכחית חייבת להסתיים לפני שהפעלה אחרת תוצב בתור. | בדוק זאת עם `fp audits runs <name>`. |

## לפני ההפעלה

- אשר שסשנים קיימים בחלון הזמן הנבחר.
- אמת את מסנני הסביבה והסוכן.
- בדוק שהקשר הרפרנס עדכני. כל הפעלה קוראת מחדש את עמודי הביקורת וחוזרת לעותק המאוחסן כשלא ניתן להגיע אליו, כך שעמוד שהועבר או הורד ממשיך להציג טקסט ישן עד שתתקן את ה-URL.
- וודא שהמטרה מתארת מצב כישלון, לא מסקנה רצויה.

## סקור את ההפעלה

עמוד פרטי הביקורת נפתח עם חמש אריחים: **ממצאים פתוחים** המחכים ל-triage, **הפעלה אחרונה**, **הפעלה הבאה**, **חלון** (כמה אחורה כל הפעלה קוראת), ו-**sensitivity** (כמה בחריפות הפעלה מדגילה דפוס: `low`, `medium`, `high`). כובלת N-findings-לכל-הפעלה היא הגדרה נפרדת, findings per run (`--top-k`, ברירת מחדל 50). אלה חמישה עונים על שאלת הכיסוי מהר יותר מאשר פתיחת הפעלה.

לאחר מכן בדוק את ה-severity, התיאור, הפעלות הוכחה, השאילתות התומכות, ונתיב המניעה המוצע של כל ממצא. ממצאים מסודרים לפי ציון **priority** בין 0 ל-1, מדורגים לכל הפעלה, וכל ממצא מציג את ארבעת הגורמים המשוקללים מאחוריו:

| גורם דירוג | משקל |
| --- | --- |
| Coverage | 0.30 |
| Magnitude | 0.25 |
| Severity | 0.25 |
| Recency | 0.20 |

ממצא נמצא בדיוק באחד מחמישה סטטוסים: `open`, `recurring`, `resolved`, `dismissed`, או `muted`. שאילתת `findings` ללא סינון סטטוס מחזירה את הקבוצה החיה — `open` בתוספת `recurring`. ממצא שאתה משתיק, משלל או פותר משאיר קבוצה זו; `ack` ו-`assign` משאירים את הסטטוס בלבד, אז הממצא נשאר בתור — מופחת עדיפות או בבעלות, לא נעלם. בקש סטטוס במפורש כדי לראות אלה שעזבו.

השתמש בסטטוס הממצא כדי להודות, להשתיק, להשלל, לפתור, לפתוח מחדש, או להקצות עבודה. שמור על ההוכחות גם כשהממצא משולל; זה מסביר מדוע קבלת ההחלטה. [Findings and issues](/he/audits/findings-and-issues) מכסה מה כל פועל עושה להפעלות עתידיות.

## פירוש הפעלה ריקה או מושהית

| תנאי הפעלה | המשמעות | מה לעשות |
| --- | --- | --- |
| ניתוח רץ והפיק אפס ממצאים | הוכחות שנבחרו לא תמכו בממצא בה-sensitivity המוגדר. | אשר שהטווח מכיל סשנים מייצגים, ואז התייחס לתוצאה כבריאה אלא אם המטרה או ההקשר היו עמומים מדי. |
| ניתוח מודל דולג או נכשל | ההפעלה מסתיימת עם אפס ממצאים, אך היא לא ביצעה את החקירה הממונעת. סריקת הכרטיסים וה-PII הדטרמיניסטית עדיין מדווחת ספירות התאמות בסטטיסטיקות הפעלה אך לא יוצרת ממצאים. | תקן את שירות הניתוח או את התצורה והפעל מחדש. אל תפרש את התוצאה הריקה כהוכחה שהאוכלוסייה בריאה. |
| ניתוח מודל משבית | ההפעלה מצליחה עם אפס ממצאים. הסריקה הדטרמיניסטית לא מחליפה ניתוח מודל או פותחת ממצאים. | הפעל ניתוח מודל או השבת את הביקורת במקום להסתמך על ביקורת שלא יכולה להפיק ממצאים. |
| אין קיבולת ניתוח זמינה מיד | הביקורת נשארת בתור ובוצעת ניסיון חוזר במקום דילוג על האוכלוסייה. | חכה לקיבולת או פזר עוגנים בביקורת. מפעילים בעלות עצמית צריכים לתשנן את ה-audit-agent replicas וקיבולת ה-dispatcher המתאימה. |
| קיבולת נשארת לא זמינה לחלון ניסיון חוזר | ההפעלה מוותרת עם אפס ממצאים ושולחת הודעת כשל כשמסירת דוא"ל זמינה. | בדוק אם צי הביקורת רוויה או מתחיל מחדש בקביעות. |

שלוש השורות האחרונות מתארות התנהגות של Cloud API server וה-dispatcher שלו. ב-managed Cloud הם של Failproof AI לתיקון; בהנדסה בעלות עצמית הם שלך.

כאשר ניתוח לא רץ, ביקורות `since_last` שומרות את החלון הלא מנותח לשנות ההפעלה הבאה. ממצאים קיימים לא מיושנים כי ניתוח מדולג אינו הוכחה שהכישלון נעלם.

## הבנת הודעות

הפעלה מוצלחת מודיעה רק כשהיא מוצאת משהו **חדש**. שקט מביקורת בריאה הוא המקרה הנורמלי, לא סימן שום דבר לא רץ — בדוק **last run** בעמוד הביקורת, או `fp audits runs <name>`, כדי לראות שכן. ביקורת ללא ערוצים שנבחרו תיקוד את הממצאים שלה ולא מודיעה לאיש.

הפעלה שנכשלה או שלב ניתוח מודל שנכשל משתמש בנמענים הדוא"ל של הביקורת. אם לביקורת אין ערוץ דוא"ל, Failproof AI חוזר להגדרת `alerts.email_default_recipients` של הארגון כך שביקורת שבורה בשקט עדיין יש לה נתיב הסלמה.

דוא"ל חייב להיות מופעל לארגון וה-SMTP חייב להיות מוגדר. אחרת הכישלון נרשם אך לא ניתן להציע דוא"ל. כשלי הפעלה לא מעבירים את עוגן הלוח הקבוע של הביקורת.

כל הפעלה גם אוחסנת בהקשר [agent context](/he/audits/agent-contracts) המדויק המשמש לכל סוכן כמצילום חוזה. עריכות מאוחרות יותר לא משנים את תקן הוכחות המוקלד עם הפעלה מוקדמת יותר.
