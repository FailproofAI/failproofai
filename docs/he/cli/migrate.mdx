---

```bash
failproofai migrate --dry-run   # print the plan, change nothing
failproofai migrate             # run it
```

רוב האנשים לעולם לא מקלידים את זה. הוא רץ בעצמו בפקודה הראשונה אחרי שדרוג, וגם [`failproofai update`](/he/cli/update) כולל אותו. השתמש בו ישירות כשאתה רוצה לראות את התוכנית לפני שזה קורה, או להריץ את ההעברה בעצמה.

## מופעל על ידי הפורמט, לא הגרסה

`~/.failproofai/VERSION` רושם מספר **פורמט** — צורת הספרייה, לא ההוצאה שכתבה אותה. העברות מופעלות על ידי המספר הזה, וזה מה שעושה פער ארוך זול:

- גרסאות npm משתנות בכל הוצאה, עשרות ביניהן בין שני פורמטים.
- כך שמכונה שדילגה על שלושים הוצאות עם **ללא שינוי פורמט** תריץ **אפס** העברות, לא שלושים פעולות חסרות תוכן.
- ומכונה שדילגה על כמה פורמטים בבת אחת תריץ כל שלב בתור, כל שלב יודע רק על שתי הקצוות שלו.

זה חשוב כי npm לא יכול לעדכן חבילה מותקנת בעצמה. מכונה שיושבת על גרסה אחת לחודשים ואז קופצת כמה פורמטים הלאה היא המקרה הנורמלי, לא זה אקזוטי.

## ההרצה בניסיון

`--dry-run` מדפיס את השרשרת המדויקת והקבצים שיישמרו קודם, ולא משנה כלום בכלל — ללא העברה, ללא גיבוי, ללא ערך ברישום:

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## מה נשמר ומה בנוי מחדש

כל נתיב בבית מצהיר איזה סוג נתונים הוא מחזיק, וזה קובע האם העברה יכולה להשליך אותו. הכלל: **הנגזר וניתן לשליפה שוב עשוי להישלך; כל דבר שהקלדת, כל דבר שעדיין לא הועבר, וכל דבר שמזהה את המכונה נשמר.**

| נשמר | בנוי מחדש או שאוחזר |
|---|---|
| `config.json` — הגדרות, `daemon.configured`, נתיבי capture נוספים | cache ההדיקט |
| `credentials.json` — ההרשמה בענן שלך | פריסות מנוהלות בענן (שוחזרו וחתימת-אומתו בסקר הבא) |
| `policies-config.json` — בחירת המדיניות והפרמטרים שלך | מצב scratch של Daemon |
| `policies/` — קבצי המדיניות שלך והעוזרים שהם מייבאים | |
| `hook-activity/` — יומן ההחלטה שהלוח קורא | |
| אירועים שלא הועברו עדיין בתור להעלאה | |
| `cursors/` — סימני מים של collector | |
| ה-binary של daemon ב-`bin/` | |

<Note>
  אירועים שלא הועברו נשמרים ולא משלכים כי ההפסד היה קבוע, לא איטי: סימן המים של ה-collector כבר התקדם מעבר לכל דבר יושב ב-spool, כך שלא היה קורא שום דבר את הטווח הזה של טרנסקריפט שוב. ההעברה גם שואלת את ה-daemon להעביר את מה שנמצא ב-spool בהקדם שהוא מסיים, כך שהתוצאה הרגילה היא שאין כלום שנותר לשמור.
</Note>

מפתחות שגרסה **חדשה יותר** כתבה ל-`config.json`, `credentials.json` או `policies-config.json` נשמרים גם כן, ולא משלכים על ידי קורא ישן.

## הרשומה שהיא משאירה

```
~/.failproofai/migrations/
  applied.json                 ערך אחד לכל שלב: layout, CLI, timestamp, duration, result
  backup-layout<n>/            עותקים של הקבצים שאי אפשר להחליף אותם, שצולמו לפני השלב הראשון
```

`applied.json` הוא מה שעונה על "מה בדיוק עברה מכונה זו" — השאלה הראשונה שכדאי לשאול כשמשהו נראה לא בסדר אחרי שדרוג. צרף אותו לדוח באג.

הגיבוי הוא בכוונון קטן ולא עותק של כל הספרייה: ההעברה כבר לא מוחקת כלום שאי אפשר להחליף על ידי עיצוב, כך שמה שכדאי ביטוחון נגדו הוא **פגם בשלב**, וקבצים ספורים אלה הם המקום שבו פגם כזה יפגע.

## אם שלב נכשל

השרשרת עוצרת שם. `VERSION` חותום רק על ידי שלב שהושלם, כך שהבית נשאר מסומן עם הפורמט הישן שלו והפקודה הבאה מנסה שוב — בית לעולם לא מסומן כעדכני על כוח של העברה חלקית. השלב מתועד ב-`applied.json` עם `"ok": false`, והגיבוי הוא היכן שהוא צולם.

## בית חדש יותר נדחה, לא מועבר

אם `~/.failproofai/` נכתב על ידי **חדש יותר** failproofai מזה שאתה מריץ, הפקודה עוצרת ואומרת לך לעדכן במקום. הנתונים האלה בסדר וCLI חדש יותר קורא אותם; העברה "קדימה" מהם איננה דבר קיים, וריסטרט היה הורס משהו שניתן להחזיר.

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

ה-daemon מיישם את אותו כלל: `failproofaid` מסרב להתחיל נגד layout שהוא לא מדבר, ולא לקרוא ולכתוב לנתיבים שהזיזו.
