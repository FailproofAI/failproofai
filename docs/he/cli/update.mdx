title: עדכון לאחר שדרוג
description: "סיימו את החצי השני של שדרוג שלא יכול npm לעשות: העברו את הבית והתאימו את ה-daemon"
---

```bash
npm install -g failproofai@latest && failproofai update
```

זהו כל השדרוג. `npm` מחליף את ה-CLI; `failproofai update` עושה את השאר.

## למה פקודה שנייה קיימת

`npm install -g` מחליף דבר אחד בלבד — את ה-CLI. שני דברים נוספים בהתקנת failproofai חיים מחוץ לחבילה בכוונה, ואף אחד מהם לא זז כשנפעיל npm:

- **`~/.failproofai/`**, ההגדרות שלכם, הרשמה בענן, בחירת מדיניות והיסטוריה. גרסה חדשה עשויה לארגן אותה בצורה שונה, והיצירה מחדש של הארגון חייבת להיעשות על ידי קוד שיודע שתי צורות.
- **בינרי ה-daemon `failproofaid`**, ב-`~/.failproofai/bin/failproofaid-<version>`. הוא בכוונה *לא* בתוך `node_modules`: שדרוג שהחליף את הקובץ תחת שירות פעיל היה מצביע ל-daemon חי בקובץ בינרי שנבנה מקוד שונה, והסרת החבילה היתה מוחקת אותו מתחת לשירות שאחריו crash-loops בכל אתחול.

אז אחרי `npm install -g` בלבד, ה-CLI חדש וה-daemon לא. `failproofaid` מסרב להתחיל מול פריסת בית שהוא לא מדבר איתה — הגרסה הקולנית של חוסר התאימות הזה ולא השקטה — אז שני החצאים חייבים להתחבר. `failproofai update` היא אותה שלב.

## מה זה עושה

<Steps>
  <Step title="מריץ כל העברות פריסה בהמתנה">
    קורא את הפריסה שהוקלדה ב-`~/.failproofai/VERSION` ומריץ את השלבים שמביאים אותה לזו שגרסה זו מדברת איתה. בדרך כלל אף אחד — ראו [`failproofai migrate`](/he/cli/migrate).
  </Step>
  <Step title="שם את בינרי ה-daemon התואם במקום">
    מחבילת הפלטפורמה שכבר הורידו npm בעדיפות (ללא רשת), אחרת מנכס השחרור לגרסה מדויקת זו, מאומת SHA-256 לפני שהוא בשימוש.
  </Step>
  <Step title="מפעיל מחדש את השירות ומאשר שהוא חזר">
    בדיקה ולא הנחה — מנהל שירות מדווח על תהליך פעיל ברגע שהוא מתפצל, וזה לא אותו דבר כמו שזה עובד.
  </Step>
</Steps>

## אפשרויות

| דגל | השפעה |
|------|--------|
| `--no-daemon` | העברו את הבית בלבד, והשאירו את ה-daemon בגרסה הנוכחית שלו. |

<Warning>
  `--no-daemon` משאיר daemon בגרסה שונה במקום. במכונה המוגדרת להדרוש את ה-daemon, כל אירוע hook **נכשל סגור** אם ה-daemon לא יכול להשיב — וכן daemon שמסרב להתחיל מול בית שהועבר לא יכול להשיב. עדיפות תן ל-daemon למרוץ חצי.
</Warning>

## אם משהו הולך לא כן

הפקודה תצא עם ערך לא אפס ותגיד איזה חצי נכשל. שני מקרים שכדאי לדעת עליהם:

- **שלב העברה לא הסתיים.** הבית משאר מסומן עם הפריסה *הישנה* שלו, כך שהפקודה הבאה חוזרת עליה — בית לא אי פעם מסומן כעדכני על חוזק של העברה חלקית. עותקים של ההגדרות והרשמה שלכם נשמרו לפני שהכל רץ, ב-`~/.failproofai/migrations/backup-layout<n>/`.
- **ה-daemon לא יכול להיות מורם מחדש ללא סיסמה.** `sudo -n` משמש בכוונה, כך שלא מעולם נשאל מתחת לתצוגת התקדמות. הפקודה מדפיסה את השורה המדויקת שתוכלו להריץ בעצמכם.

<Note>
  כלום כאן לא צריך את איזשהו-wizard הגדרה אינטראקטיבית. ההגדרות, הרשמה בענן והבחירה במדיניות שלכם שורדות שדרוג, כך שמכונה שהועברה אוכפת בדיוק כמו שעשתה לפני — וזה חשוב ביותר במכונות שלא אחד יושב בהן: מריץ CI, תיבה בפלוט, שער headless.
</Note>

## אוטומציה של זה

`failproofai update` הוא לא-אינטראקטיבי וזה בטוח להריץ כשאין שום דבר לעשות — זה מדווח "לא נדרשה העברה" ויצא 0. הצבעה אחרי כל שדרוג בתסריט הספקה או Dockerfile היא השימוש בכוונה:

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

(`--no-daemon` בבנייה של תמונה, שם אין שירות להתחיל עדיין.)
