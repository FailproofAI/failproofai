description: "השלם את החצי של שדרוג שנpm לא יכול לעשות: העבר את בית השימוש והתאם את ה-daemon"
---

```bash
npm install -g failproofai@latest && failproofai update
```

זהו כל השדרוג. `npm` מחליף את CLI; `failproofai update` עושה את
השאר.

## למה קיימת פקודה שנייה

`npm install -g` מחליף דבר אחד בלבד — את CLI. שני דברים נוספים של התקנת failproofai
חיים מחוץ לחבילה בכוונה, ושום אחד מהם לא זז כאשר npm רץ:

- **`~/.failproofai/`**, ההגדרות שלך, רישום ענן, בחירת מדיניות והיסטוריה. גרסה חדשה
  עשויה לארגן את זה בצורה שונה, והארגון החוזר צריך להיעשות על ידי קוד שמכיר
  שתי הצורות.
- **Binary daemon של `failproofaid`**, ב-
  `~/.failproofai/bin/failproofaid-<version>`. זה *намеренно* לא בתוך
  `node_modules`: שדרוג שהחליף את הקובץ תחת שירות פעיל היה מפנה daemon חי
  לbinary שנבנה מקוד שונה, והסרת החבילה היתה מוחקת אותו מתחת לשירות שלאחר מכן
  crash-loops בכל אתחול.

אז אחרי `npm install -g` בלבד, CLI הוא חדש והdaemon אינו.
`failproofaid` מסרב להתחיל מול פריסת בית שהוא לא דובר — הגרסה הגלויה
של אי-התאמה זו ולא הדוממת — אז שני החצאים צריכים להיות מובאים יחד.
`failproofai update` הוא שלב זה.

## מה זה עושה

<Steps>
  <Step title="מריץ מיגרציות פריסה בהמתנה">
    קורא את הפריסה המוקלטת ב-`~/.failproofai/VERSION` ומריץ את השלבים שמביאים
    אותה לזו שגרסה זו דובר. בדרך כלל אף אחת — ראה
    [`failproofai migrate`](/he/cli/migrate).
  </Step>
  <Step title="מציב את binary daemon התואם במקום">
    מחבילת הפלטפורמה שnpm כבר הורידה כאשר אפשר (ללא רשת),
    אחרת מנכס ההוצאה לגרסה מדויקת זו, מאומת SHA-256
    לפני שהוא משמש.
  </Step>
  <Step title="מפעיל מחדש את השירות ומאשר שהוא חזר">
    בדוק במקום להניח — מנהל שירות מדווח על תהליך פעיל ברגע שהוא fork,
    וזה לא אותו דבר כמו שזה עובד.
  </Step>
</Steps>

## אפשרויות

| דגל | השפעה |
|------|--------|
| `--no-daemon` | העבר את הבית בלבד, השאר את ה-daemon בגרסה הנוכחית שלו. |

<Warning>
  `--no-daemon` משאיר daemon בעל פער גרסא במקום. על מכונה שהוגדרה
  לדרוש את ה-daemon, כל אירוע hook **נכשל סגור** אם ה-daemon לא יכול
  לענות — ודaemon שמסרב להתחיל מול בית מהוגרר לא יכול לענות.
  העדף לתת לחצי daemon להריץ.
</Warning>

## אם משהו הולך לא בסדר

הפקודה יוצאת ב-non-zero ואומרת איזה חצי נכשל. שתי מקרים ראויים ידע:

- **שלב מיגרציה לא סיים.** הבית משמר עם *הישן* שלו
  פריסה, כך שהפקודה הבאה מנסה שוב — כל בית אף פעם לא מוקלט כעדכני
  בחוזקו של מיגרציה חלקית. עותקים של ההגדרות והרישום שלך נשמרו
  לפני שכל דבר רץ, ב-`~/.failproofai/migrations/backup-layout<n>/`.
- **ה-daemon לא יכול להיות מופעל מחדש ללא סיסמה.** `sudo -n` משמש
  בכוונה, כך שכלום אף פעם לא מעוררת מתחת להצג התקדמות. הפקודה
  מדפיסה את הקו המדויק להריץ בעצמך.

<Note>
  כלום כאן לא צריך את אשף ההגדרה האינטראקטיבי. ההגדרות שלך, רישום ענן
  ובחירת מדיניות שורדים שדרוג, כך שמכונה מהוגררת משדרת בדיוק כמו
  לפני — וזה חשוב ביותר על המכונות ללא אף אחד יושב בהם: CI runner,
  אלון fleet, gateway headless.
</Note>

## אוטומציה שלו

`failproofai update` אינו אינטראקטיבי ובטוח להריץ כאשר אין שום דבר לעשות
— זה מדווח "אין צורך בהעברה" ויוצא 0. הצבתו אחרי כל
שדרוג בתסריט provisioning או Dockerfile הוא השימוש המכוון:

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

(`--no-daemon` בבנייה תמונה, כאשר אין שירות להיות מופעל מחדש עדיין.)
