בדוק את [הקטלוג המובנה](/he/policies/builtin-catalog) לפני כתיבת מדיניות. כלל שנבדק בדרך כלל בטוח יותר מכלל חדש.

## התחל מתוך מדיניות שעובדת

```bash
failproofai publish --init guards.mjs
failproofai policies -i -c ./guards.mjs
```

בלוק ההתחלה חוסם את `git push --force`. ערוך אותו, בקש מהסוכן שלך לנסות את הפעולה החסומה, ובדוק את **Policies → Activity**.

```js
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production",
  description: "Production changes need a human",
  match: { events: ["PreToolUse"], toolNames: ["Bash"] },
  fn: async (ctx) =>
    String(ctx.toolInput?.command ?? "").includes("production")
      ? deny("Ask a human before changing production.")
      : allow(),
});
```

מדיניות מחזירה `allow()`, `deny(message)` או `instruct(message)`. השתמש ב-`deny` כאשר על הפעולה להיעצר; לא כל מנגנון יכול להעביר הנחיה חזרה לסוכן.

## טען באופן אוטומטי

שים קבצים בשם `*policies.js`, `*policies.mjs` או `*policies.ts` תחת:

- `.failproofai/policies/` עבור פרויקט אחד.
- `~/.failproofai/policies/` עבור המשתמש שלך.

## בדוק נתיבי כשל

בדוק גם את הפעולה הלא בטוחה וגם את העבודה הלגיטימית שנראית דומה. אשר שההחלטה באה מהמדיניות שלך ולא מכלל אחר.

הסר קבצי בדיקה מפורשים באמצעות:

```bash
failproofai policies -u -c
```

כאשר המדיניות מוכנה, [פרסם חבילה](/he/policies/publish-a-pack) או [פרוס אותה דרך Cloud](/he/policies/deploy).
