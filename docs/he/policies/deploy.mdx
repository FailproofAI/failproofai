פרוס מציב גרסאות מדיניות שפורסמו על מכונה, כל אחת עם אחת משתי השפעות:

- **Observe** רושם את מה שהמדיניות הייתה עושה, ולא חוסם כלום.
- **Enforce** פועל על ההחלטה: `deny` חוסם את הקריאה ו-`instruct` מכוונת את הסוכן.

## הוסף מכונה

מכונה מופיעה תחת **Admin → enforcement** לאחר שהיא מתחברת ל-Cloud. אם זו שאתה רוצה עדיין לא שם:

<Tabs>
  <Tab title="Dashboard">
    1. עבור ל-**Administration → Keys** וצור מפתח עם `policies:pull`, כדי שהמכונה תוכל לקבל פרוסים, ו-`events:add`, כדי שההחלטות שלה יגיעו ל-Cloud.
    2. חבר את המכונה עם המפתח הזה — [Connect a machine to Cloud](/he/start/setup#connect-a-machine-to-cloud) מדריך דרך זה.
    3. אשר שהיא מופיעה תחת **Admin → enforcement**.
  </Tab>
  <Tab title="CLI">
    על המכונה:

    ```bash
    npm install -g failproofai
    failproofai config
    failproofai config --status
    ```

    בטרמינל, `failproofai config` שואל אם להתחבר ל-Cloud ולוקח את המפתח בהנחיה מסוכנת. לאחר מכן אשר שהמכונה נרשמה, מכל מקום, עם `fp fleet list`.
  </Tab>
</Tabs>

## פרוס במצב תצפית

<Tabs>
  <Tab title="Dashboard">
    1. עבור ל-**Admin → enforcement**, מצא את המכונה והרחב את השורה שלה.
    2. בחר **edit**, הוסף את גרסת המדיניות שנבדקה, ובחר **observe**.
    3. החל את השינוי, ואז חכה לבדיקת הכניסה הבאה של המכונה והאשר את מצב הפרוס והכיסוי שלה.
    4. עבור ל-**Observe → policy** כדי לבדוק החלטות חיות.

    ![עורך פרוס המכונה עם גרסאות מדיניות, השפעות enforce ו-observe, ופעולת החלת הפרוס.](/images/dashboard/enforcement-editor.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp fleet list
    fp fleet show <machine-id>
    fp fleet deploy <machine-id> --add no-force-push:observe
    ```

    הסיומת `:observe` היא מה שהופכת זאת לתצפית: `--add no-force-push` חשוף שומר על ההשפעה שיש למכונה כבר לאותה מדיניות, ואחרת אוכף. החלף אותה לאכיפה מאוחר יותר עם `--add no-force-push:enforce`.

    `deploy` **מחליף את כל קבוצת המדיניות של המכונה** בתוצאה. הוא מדפיס את התוכנית, לאחר מכן שואל לפני החלת — אך רק על טרמינל אינטראקטיבי. עם `--yes`, תחת `fp --json`, או עם stdin מעבר (שלב CI, סקריפט, סוכן שולח צדף) הוא מיישם ללא שאלה; התוכנית עדיין מודפסת, או מוחזרת כ-`plan` תחת `--json`.

    על המכונה, `failproofai policies` מרשים את המדיניויות המנוהלות ב-Cloud שהיא מפעילה ו-`failproofai config --status` מציג את התחברותה. השתמש ב-`fp sessions --env production --since 24h` וב-`fp events --event-type hook_completed` כדי להאשיר שפעילותה מגיעה ל-Cloud.
  </Tab>
</Tabs>

<Steps>
  <Step title="בחר את הגרסה והמכונות">
    בחר את הגרסה המפורסמת והמכונות שעליהן היא צריכה לפעול.
  </Step>
  <Step title="תצפית">
    בדוק התאמות, סיבות, כלים מושפעים וחיוביים כוזבים בעודו כלום לא נחסם.
  </Step>
  <Step title="אכיפה">
    החלף את ההשפעה לאכיפה לאחר שההתאמות המתבוננות מפרידות בין פעולות לא בטוחות לבין תקפות, ואז אשר שכל מכונה מעוניינת משכה את השינוי וחוקרת החלטות.
  </Step>
</Steps>

## כוון סוכן על מכונה

גרסאות מדיניות שפורסמו אינן מכילות כללי ניתוב סוכן. כברירת מחדל, הקצאה חלה על **כל הסוכנים על המכונה שלה**. בעת פרוס גרסה, אתה יכול במקום זאת לכוון אינטגרציה (כולל פרופילים שנוספו מאוחר יותר) או פרופיל מסוים שדווח על ידי אותה מכונה. הבחירה שייכת להקצאת המכונה: אותה גרסה שפורסמה יכולה לכוון סוכנים שונים על מכונות שונות.

<Tabs>
  <Tab title="Dashboard">
    1. ב-**Admin → enforcement**, הרחב את המכונה ובחר **edit**.
    2. בבקרת **agents** של המדיניות, שמור על **all agents**, בחר **all hermes profiles** (לדוגמה), או חפש פרופיל דווח לפי התווית שלו ו-ID של `agt_`. אתה יכול לבחור כמה חלופות; קריאה תואמת אם היא שייכת לאחת מהן.
    3. בדוק את היעד המופיע עבור **כל** הקצאה בתוכנית הפרוס, החל את השינוי, לאחר מכן בדוק את הפרוס המדווח של המכונה לאחר בדיקת הכניסה הבאה שלה. ההיסטוריה והחזרה שומרות על היעדים שנבחרו.
  </Tab>
  <Tab title="CLI">
    ```bash
    fp fleet show <machine-id>
    fp fleet deploy <machine-id> --add no-force-push --target no-force-push=hermes
    fp fleet deploy <machine-id> --target no-force-push=hermes/agt_1234567890abcdef
    fp fleet deploy <machine-id> --all-agents no-force-push
    ```

    `--target POLICY=INTEGRATION[/agt_ID]` קובע את ההיקף של מדיניות אחת. חזור על `--target` לעוד חלופות באותה הקצאה. השתמש ב-`--all-agents POLICY` כדי לנקות את היעד של הקצאה זו. `fp fleet show` ו-`fp fleet history` מציגים את ההיקף שנבחר. בדוק את תוכנית ההחלפה המלאה לפני החלת, במיוחד בעת פרוס משסקריפט.
  </Tab>
</Tabs>

המכונה חייבת לדווח לאחרונה על תמיכה בניתוב סוכן לפני שתוכל להגדיר יעד חדש. אתה יכול לבחור פרופיל מדויק רק אם אותה מכונה דווחה עליו עם hook מותקן וזה לא ישן. אם המלאי זמינה באופן זמני, היעדים הקיימים נשארים מוקצים; הם לא מתרחבים בשקט לכל הסוכנים. התקן מחדש קליפות ישנות יותר כדי לספק את רמז הפרופיל המשמש התקנות חדשות. לאחר שדרוג ה-CLI, הרץ `failproofai config` כדי לעדכן ולהפעיל מחדש את השד שלו גם: daemon ישן לא יכול להעריך קריאות חדשות בהיקף פרופיל וה-hook מסרב לחוסר התאמה.
אם לא ניתן לזהות את הפרופיל של הסוכן הפועל (לדוגמה, כאשר כמה היקפי הגדרות מותקנים אך ה-hook לא מדווח איזה אחד פעל), **הקצאות יעודיות לא תואמות**; מדיניויות ללא היקף עדיין חלות. חפש `agent_scope_unresolved` תחת שגיאות המדיניות של אותה מכונה.

מכונה מדווחת רק על סוכנים שהיא עוקבת אחריהם: ערך אחד לכל פרופיל שתצורתו נושאת את ה-hook של FailproofAI (Hermes ו-OpenClaw מקבלים אחד לכל פרופיל, שנקרא לפי התווית שלו). סוכן CLI שהוא פשוט מותקן לא מופיע ברשימה.

כל מכונה שומרת עד 256 פרופילים ברשימת הנושים שלה. ה-ID של פרופיל לא משתנה כל עוד הוא ברשימה. כאשר הרשימה מלאה וזהו פרופיל חדש עם hook של FailproofAI (ה-hook שלו פועל, או התצורה שלו נושאת את ה-hook), ה-daemon משחרר מקום על ידי הורדת פרופיל אחד העומד בכל אלה:

- אין לו hook מותקן;
- אף הקצאה לא שמה לב אליו;
- FailproofAI Cloud לא יקבל אותו כיעד חדש.

ה-daemon מעדיף פרופיל שלא נמצא עוד על המכונה, לאחר מכן זה שלא בשימוש הכי ארוך. הוא לעולם לא מוריד פרופיל שיעד מדויק משתמש, כדי שיעדים אלה יישארו בתוקף. אם לא ניתן להוריד פרופיל, לפרופיל החדש עדיין אין ID, והקצאות יעודיות לא תואמות אותו עד שמקום משתחרר.

## פרוס בדיקות Jev

מדיניות של Cloud יכולה לשאת בדיקות Jev כמו גם, או במקום, JavaScript. הסוג שלה הוא `jev` (רק בדיקות Jev) או `both` (JavaScript שהוודאות שלו עשויות לנקות). זה פורס, מעביר באפקט וחוזר בדיוק כמו כל מדיניות אחרת.

בדיקות Jev פועלות על FailproofAI Cloud; כלום לא מותקן על המכונה. המכונה מקבלת רק את ה-JavaScript של מדיניות `both`. בעודו `jev` או מדיניות `both` מפורסת אליו, FailproofAI Cloud מפעיל את Jev עבור המכונה, וכל קריאת כלי שנבדקה של סוכן שהמדיניות מכוונת אליו הולכת ל-FailproofAI Cloud, המבקש את הבדיקות שפורסמו לאותו סוכן ומחזיר את הפסק שלהם. ללא פרוס, Jev כבוי שם. אין מצב Jev להגדיר ביד.

```bash
fp policies publish prod-db-intent --kind jev --semantic ./checks.json
fp fleet deploy <machine-id> --add prod-db-intent:observe
```

כדי לנסות בדיקות Jev ללא להחליט משהו, פרוס את המדיניות עם `:observe`: הבדיקות שלה מתבקשות והתשובות שלהן מוקלטות כ-מה שהן הייתה עושות, והן לא חוסמות ולא מנקות כלום. עדכן את הפרוס כ-`enforce` לאחר שדף המדיניות מציג מה הם הייתה עושים; לאחר מכן בדיקות Jev **חוסמות** קריאות כמו גם נקוי הפסקי ה-JavaScript שהם בדקו. מדיניות `both` שפורסמה עם `:observe` משקיפה על שני החלקים.

ה-JavaScript של מדיניות `both` יכול להיקנות רק על ידי תשובות הבדיקות שלה מ-FailproofAI Cloud. בדיקה של חבילה מותקנת באותו שם לעולם לא מנקה אותה. אם לא ניתן להגיע ל-FailproofAI Cloud, או קובע אף מצב ששואל, המדיניות נשארת **hard**: כל deny של ה-JavaScript שלה עומד.

ניתוב סוכן עובד גם עבור מדיניויות של Jev בלבד. עבור מדיניות `both`, היעד של הקצאה שולט **בשני** ה-JavaScript המקומי שלה ובדיקות Jev Cloud שלה; קריאה מחוץ ליעד זה אינה מריצה אף חלק. שמור על המדיניות ב-`observe` בזמן שנסיון בדקות בהיקף, בדיוק כפי שהייתה עושה עבור הגרסה הראשונית של Jev ללא היקף.

מכונה מדווחת מה עוצר אותה מלשאול, ו-`fp fleet show <machine-id>` מרשים אותה תחת שגיאות מדיניות:

- `transcripts_disabled`: המכונה הוצמדה עם `--no-transcripts`. אותה מכונה לא משלחת קריאות כלים ל-Jev.
- `jev_unconfigured`: המפתח של המכונה לא נושא את Jev.
- `jev_rate_limited`: כמה קריאות סוררו עבור הגבול של Jev של הארגון והחליטו על ידי מדיניויות regex בלבד.
- `jev_unavailable`: ה-Jev של FailproofAI Cloud נכשל בכמה קריאות ברציפות, כך שהמכונה דולגת עליו דקה בכל פעם.

בקשת Jev אחת נושאת כמות מוגבלת של טקסט שאלה. בדיקות Cloud של FailproofAI באות לפני בדיקות חבילות שהותקנו על המכונה. בדיקת חבילה שלא משתלבת יוסרה ותדווח כ-`jev_budget`. בדיקת חבילה באותו שם כמו אחת מבדיקות Cloud של הארגון שלך תודח גם כן, ותדווח כ-`jev_name_clash`: בדיקת ה-Cloud מתבקשת במקומה.

## בדוק כיסוי

כיסוי משיב אם מדיניות פועלת במקום שבו הסיכון הוא.

1. עבור ל-**Admin → enforcement** ובדוק את סכומי ההאכיפה והתצפית.
2. חפש מכונה לפי ID או תווית, או סנן למכונות שחסרה להן מדיניות.
3. הרחב שורה כדי להשוות מדיניויות מוקצות, פרוס דווח, בדיקת כניסה אחרונה, והיסטוריה.
4. רענן לאחר מרווח הסקירה של המכונה כאשר פרוס מיושם עדיין בהמתנה.

![צי Enforcement המציג כיסוי מדיניות, מצב פרוס מכונה, והקצאות observe ו-enforce.](/images/dashboard/enforcement-fleet.png)

חפש מכונות שלא משכו את הפרוס האחרון, מכונות רשומות שהפסיקו דיווח, מדיניות מוקצית לסביבה הלא נכונה, וסחיפת גרסה לאחר עדכון הופסק.

תווית מכונות לפי עומס עבודה וסביבה — שמות מחשבים בלבד נדירים שורדים אוטו-סקלינג או החלפה:

```bash
failproofai config --machine-label checkout-runner-03
```

<Warning>
  ניהול אכיפה הוא זרימת עבודה Cloud מנהלית. אל תתייחס לנתיבי אכיפה שרק-root כנקודות קצה API רגילות `/v1`.
</Warning>
