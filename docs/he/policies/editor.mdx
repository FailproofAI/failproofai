השתמש בעורך המדיניות כדי להפוך ממצא או בעיה לכלל ניתן לפריסה. שמור על הפרדה בין יצירת התוכן לבין פריסה, כך שטיוטה לא תשנה בשקט התנהגות פעילה.

כאשר לבעיה יש דפוס פעולה חוזר, פתח אותה תחת **Analyze → issues** ובחר **generate policy**. Failproof AI תסביר תחילה האם מדיניות יכולה להביע את הבעיה, ואז תעביר את הכוונה המבוקרת והקשר הממצא לעורך. הקוד שנוצר נשאר כטיוטה עד שתפרסם אותו.

## פרסום גרסת מדיניות

<Tabs>
  <Tab title="Dashboard">
    1. עבור אל **Admin → policy editor** ובחלק **compose**, תאר את מצב הכישלון או הדבק את קוד ה-JavaScript של המדיניות.
    2. אמת את הקוד ותקן כל שגיאה שדווחה.
    3. הזן את זהות המדיניות ופרסם אותה, ואז השתמש ב-**library** כדי להשוות או להשבית גרסאות.
    4. בחר **enforcement** כאשר הגרסה מוכנה לגלגול מכונה.

    ![תצוגת compose של עורך המדיניות עם זהות המדיניות, יצירה בעזרת AI, אימות קוד והגדרות פרסום.](/images/dashboard/policy-editor.png)
  </Tab>
  <Tab title="CLI">
    ה-Cloud CLI אינו מפרסם גרסאות של מדיניות. אמת את הקוד באופן מקומי לפני העתקתו לעורך:

    ```bash
    failproofai policies --install --custom ./checkout.policies.ts \
      --cli claude --scope project
    ```

    פרסם את הגרסה המבוקרת מ-**Admin → policy editor**.
  </Tab>
</Tabs>

## רשימת בדיקה לכתיבה

1. תן שם למצב הכישלון בשפה תפעולית.
2. בחר את אירועי ה-hook והכלים המכילים ראיות מספיקות להחלטה.
3. כתוב את התנאי הצר ביותר התואם התנהגות לא בטוחה.
4. החזר סיבה שתגיד לסוכן או למפעיל מה לעשות בשלב הבא.
5. הוסף דוגמאות שצריכות להתאים ודוגמאות שחייבות להישמר כמותרות.
6. שמור גרסה חדשה ובקש ביקורת.

השתמש ב-`instruct` כאשר הסוכן יכול לתקן בבטחה את המסלול. השתמש ב-`deny` כאשר אישור הפעולה יהווה סיכון לא קביל או בלתי הפיך.

<Info>
  גרסאות מדיניות הן קלטים פריסה בלתי שינויים. עריכת טיוטה יוצרת גרסה חדשה; היא לא צריכה לכתוב מחדש את הגרסה שכבר הוקצתה למכונות.
</Info>
