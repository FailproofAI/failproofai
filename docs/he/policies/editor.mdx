השתמש בעורך המדיניות כדי להפוך ממצא או בעיה לכלל הניתן להפעלה. שמור על הפרדה בין הכתיבה להפעלה כך שטיוטה לא תוכל לשנות בשקט את ההתנהגות בעלויות.

כאשר לבעיה יש דפוס פעולה חוזר, פתח אותה תחת **Analyze → issues** ובחר **generate policy**. Failproof AI תחילה מסביר האם מדיניות יכולה להביע את הבעיה, ואז מעביר את הכוונה הנבדקת והקשר הממצא לעורך. הקוד המופק נשאר כטיוטה עד שתפרסם אותו.

## פרסום גרסת מדיניות

<Tabs>
  <Tab title="Dashboard">
    1. עבור אל **Admin → policy editor** וב-**compose** תאר את режים הכשל או הדבק את קוד המדיניות ב-JavaScript.
    2. אמת את הקוד ותקן כל שגיאה שדווחה.
    3. הזן את זהות המדיניות ופרסם אותה, ואז השתמש ב-**library** כדי להשוות או להשבית גרסאות.
    4. בחר **enforcement** כאשר הגרסה מוכנה לגלגול מכונה.

    ![תצוגת compose של עורך המדיניות עם זהות מדיניות, טיוטה בעזרת AI, אימות קוד ובקרי פרסום.](/images/dashboard/policy-editor.png)
  </Tab>
  <Tab title="CLI">
    Cloud CLI לא מפרסם גרסאות מדיניות. אמת את הקוד באופן מקומי לפני העתקתו לעורך:

    ```bash
    failproofai policies --install --custom ./checkout.policies.ts \
      --cli claude --scope project
    ```

    פרסם את הגרסה הנבדקת מ-**Admin → policy editor**.
  </Tab>
</Tabs>

## רשימת בדיקה לכתיבה

1. תן שם לrežim הכשל בשפה תפעולית.
2. בחר את אירועי ה-hook והכלים המכילים ראיות מספיקות להחלטה.
3. כתוב את התנאי הצר ביותר התואם התנהגות לא בטוחה.
4. החזר נימוק שמספר לסוכן או למפעיל מה לעשות בשלב הבא.
5. הוסף דוגמאות שצריכות להתאים ודוגמאות שחייבות להישאר מותרות.
6. שמור גרסה חדשה ובקש סקירה.

השתמש ב-`instruct` כאשר הסוכן יכול בכל בטחון לתקן את הקורס. השתמש ב-`deny` כאשר היתרת הפעולה תיצור סיכון בלתי מקובל או בלתי הפיך.

<Info>
  גרסאות מדיניות הן קלטי הפעלה בלתי משתנים. עריכת טיוטה יוצרת גרסה חדשה; היא לא צריכה לשכתב את הגרסה שכבר הוקצתה למכונות.
</Info>
