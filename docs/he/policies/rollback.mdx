חזרה לגרסה קודמת משנה את הגרסה המפורסת או מסירה הקצאת מדיניות; היא לא מוחקת את היסטוריית ההחלטות המסבירה את התקרית.

## חזרה לגרסה קודמת של מכונה

<Tabs>
  <Tab title="Dashboard">
    1. עבור ל-**Admin → enforcement**, הרחב את המכונה המושפעת וזהה את מערך המדיניות של הגרסה הידועה האחרונה שלה.
    2. בחר **edit**, שחזר את הגרסאות והשפעות אלה, והחל את הפריסה החדשה.
    3. המתן לבדיקת מכונה, ואז אמת את הפריסה המדווחת.
    4. פתח **Observe → policy** ואת הסשנים המושפעים כדי לאשר שעבודה תקינה כבר לא חסומה.

  </Tab>
  <Tab title="CLI">
    חזרה לגרסה קודמת בפריסת Cloud היא זרימת עבודה של dashboard. השתמש בסטטוס מקומי כדי לאשר שהפריסה המתוקנת הגיעה למכונה:

    ```bash
    failproofai config --status
    ```

    `failproofai config --pause` משהה מדיניויות builtin, custom וconvention עבור סשן מקומי אחד. היא לא משהה מדיניויות המנוהלות על ידי Cloud, ולכן היא לא דרך עקיפה לפריסת Cloud גרועה.
  </Tab>
</Tabs>

## מתי לחזור לגרסה קודמת

- מדיניות חוסמת פעולת production צפויה.
- נפח התאמה גדול משמעותית יותר מהחזוי של הרולאוט שנצפה.
- מדיניות תלויה בשדות שאינטגרציה לא מספקת.
- גרסה חדשה משנה התנהגות מחוץ למצב הכשל המיועד.

לאחר חזרה לגרסה קודמת, פתח את הסשנים המושפעים וזהה את התנאי שגרם לחיובי כוזב. צור גרסה חדשה, בדוק גם cases לא בטוחים וגם legit cases, ואז חזור על שלב ה-observe.

<Warning>
  השהיה של enforcement יכולה להיות מתאימה במהלך תקרית, אך היא מרחיבה חשיפה עבור כל מדיניות פעילה בטווח זה. העדיפו חזרה לגרסה קודמת של גרסת המדיניות הספציפית כאשר זה אפשרי.
</Warning>
