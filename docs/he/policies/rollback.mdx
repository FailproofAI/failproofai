חזרה לגרסה קודמת משנה את הגרסה המפורסמת או מסירה הקצאת מדיניות; היא אינה מוחקת את היסטוריית ההחלטות המסבירה את התקרית.

## חזרה לגרסה קודמת של מכונה

<Tabs>
  <Tab title="Dashboard">
    1. עברו ל-**Admin → enforcement**, הרחיבו את המכונה המושפעת, וזהו את מערכת המדיניות הטובה האחרונה הידועה שלה.
    2. בחרו **edit**, שחזרו את הגרסאות וההשפעות הללו, והחילו את הפריסה החדשה.
    3. חכו לבדיקת מכונה, ואז אמתו את הפריסה המדווחת.
    4. פתחו **Observe → policy** וביקרו בהפעלות המושפעות כדי לאשר שעבודה תקינה כבר לא חסומה.

  </Tab>
  <Tab title="CLI">
    חזרה לגרסה קודמת של פריסה בענן היא זרימת עבודה של dashboard. השתמשו במצב מקומי כדי לאשר שהפריסה המתוקנת הגיעה למכונה:

    ```bash
    failproofai config --status
    ```

    `failproofai config --pause` מעצור מדיניות מובנות, מותאמות אישית וקונבנציה בהפעלה מקומית אחת. היא אינה מעצורת מדיניות המנוהלות בענן, ולכן היא אינה פתרון חלופי לפריסה רעה בענן.
  </Tab>
</Tabs>

## מתי לחזור לגרסה קודמת

- מדיניות חוסמת פעולה ייצור צפויה.
- נפח התאמה גבוה משמעותית מהחיזוי של הגלילה הנצפתה.
- מדיניות תלויה בשדות שאינטגרציה לא מספקת.
- גרסה חדשה משנה התנהגות מחוץ למצב הכשל הכוונון.

לאחר חזרה לגרסה קודמת, פתחו את ההפעלות המושפעות וזהו את התנאי שגרם לחיוב חיובי שגוי. צרו גרסה חדשה, בחנו גם את המקרים הלא בטוחים והלגיטימיים, ואז חזרו על שלב ה-Observe.

<Warning>
  עצירת אכיפה יכולה להיות מתאימה במהלך תקרית, אך היא מרחיבה חשיפה עבור כל מדיניות פעילה בטווח זה. בחרו חזרה לגרסה קודמת של גרסת המדיניות הספציפית כאשר זה אפשרי.
</Warning>
