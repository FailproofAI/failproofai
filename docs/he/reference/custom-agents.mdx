## התקנה

```bash
pip install failproofai-sdk
```

החבילה מותקנת בשם `failproofai-sdk` ויובאת בPython כ-`failproofai_sdk`. extras של framework כמו `failproofai-sdk[langgraph]` מתקינים את ה-framework עצמו; ה-adapters תמיד משוגרים ב-base wheel.

## תצורה

### OpenTelemetry spans (opt in)

התקן את `opentelemetry-sdk` בנפרד, ואז צרף את ה-exporter האופציונלי:

```python
import failproofai_sdk
from opentelemetry.sdk.trace import TracerProvider

provider = TracerProvider()
failproofai_sdk.instrument("otel", provider=provider)
with provider.get_tracer("my-agent").start_as_current_span(
    "agent", attributes={"gen_ai.operation.name": "invoke_agent"}
):
    pass
provider.force_flush()
```

ההגדרה משתמשת בprovider הרשום שלך אם תשמיט את `provider`, ויוצרת אחד רק
כשאין אחד רשום. אתה יכול גם להעביר את `failproofai_sdk.OtelSpanExporter()`
ישירות ל-span processor שלך. exporters אחרים נשארים ללא שינוי.

ה-FailproofAI daemon המחובר משדר exports; ל-SDK לא צריך network
setup, מפתח, או local listener. ממשל חייב להפעיל
[OpenTelemetry ingest](/he/agenteye/opentelemetry). `instrument()` בחוץ אף פעם
לא מפעיל OTEL. `uninstrument("otel")` מכבה רק את ה-processor שלו.
כיווליך שלך שולטים ב-content capture. flush את ה-provider לפני יציאה.
ל-SDK עדיין יש אפס hard runtime dependencies ויובא את OpenTelemetry
רק בעת בקשה.

```python
import failproofai_sdk

failproofai_sdk.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| ארגומנט | מה זה עושה |
| --- | --- |
| `environment` | התווית בכל אירוע — `production`, `staging`, `prod-eu`. ברירת מחדל ל-`dev`. |
| `flush_interval` | כמה פעמים הthread ברקע כותב לדיסק, בשניות. ברירת מחדל ל-`0.5`. |
| `base_dir` | איפה לכתוב. ברירת מחדל ל-spool של ה-daemon, שזה מה שאתה רוצה אלא אם אתה יודע אחרת. |

הגדר דרך משתנה סביבה במקום:

| משתנה | מה זה עושה |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | קובע את `environment` ללא שינוי קוד, עבור כשהתווית שייכת להטמעה ולא לאפליקציה. ארגומנט `configure()` ניצח עליו. |
| `FAILPROOFAI_HOME` | מעביר את root Failproof AI שמחזיק את ה-spool. |
| `FAILPROOFAI_SDK_STRICT` | `1` גורם לשגיאות כיול להעלות במקום להיות מרשמו. |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | `1` גורם לבעיית תאימות framework להעלות במקום להתריע והמשך. |

<Warning>
  **אין פסיקים ב-`environment`.** Ingest מפצל את השדה הזה על פסיקים כדי לבנות את המסננים שלו, ודולג על כל אירוע שהתווית שלו מכילה אחד — כל run שקול משתנה. כתוב `prod-eu`, לא `prod,eu`.

  `configure(environment="prod,eu")` מעלה כך תגלה מיד. `AGENTEYE_ENVIRONMENT` לא יכול להעלות — כלום לא קורא לך — כך שהוא מתריע פעם אחת וחוזר לברירת מחדל `dev`.
</Warning>

אירועים מתוויית בזיכרון וכתובים ברקע כל `flush_interval` שניות, עם flush סופי ביציאת מפרש. תהליך שנהרג בכוח מאבד כל מה שלא היה כתוב עדיין.

## זהות

כל אירוע שייך ל-session וסוכן. **ההיקפים ממלאים את שניהם**, כך שאתה בדרך כלל לא מעביר אותם:

```python
with failproofai_sdk.session():
    with failproofai_sdk.agent("planner"):
        failproofai_sdk.event.tool_use(tool_name="search", tool_call_id="c1")
```

עברת `session_id` או `agent_id` במפורש עדיין עובד וניצח. ללא קשורה או עברת, הקריאה מעלה `TypeError` במקום לשדר אירוע שCloud היה דולג בשקט.

<Note>
  הזהות רוכבת על משתנים בהקשר. היא עוקבת אחר tasks של `asyncio` באופן אוטומטי, אך **לא** threads חדשים — עטוף עובד ב-`failproofai_sdk.propagate()` או את האירועים שלו נחות unattached.
</Note>

## קטלוג אירועים

חמש עשרה שיטות. רובן מגיעות בזוגות — אתה קורא ל-opener, ואז ה-closer, וה-SDK מודד את הפער.

| | פותח | סוגר |
| --- | --- | --- |
| **סוכנים** | `agent_start` | `agent_end` |
| | `agent_pause` | `agent_resume` |
| **מודלים** | `model_request` | `model_response` |
| **כלים** | `tool_use` | `tool_result` |
| **hooks** | `hook_triggered` | `hook_completed` |
| **בני אדם** | `human_wait` | `human_input` |

שלושה עומדים לבדם: `error`, `human_pause`, `human_interrupt`.

<Accordion title="כל שדה, לכל שיטה" icon="table">

כל שיטה גם לוקחת `session_id` ו-`agent_id`, שההיקפים ממלאים עבורך. כל מה שנותר כ-`None` מושמט ולא נשלח כ-JSON `null`, וכל שיטה מחזירה `None`.

| שיטה | נדרש | אופציונלי |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools`, `request_id` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role`, `request_id`, `duration_ms` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

</Accordion>

<Warning>
  כדי לסמן ריצה כנכשלה, `outcome` חייב להיות אחד מ-`failed`, `error`, `timeout` או `rejected`. כל דבר אחר — כולל הכמעט-miss `"failure"` — נחשב להצלחה.
</Warning>

## זוגות ומשך

**כלל אחד: תן לאירוע הסוגר את אותו id כמו ה-opener שלו.** זה מה שמזווג אותם, וזה מה שמאפשר ל-SDK למדוד את הפער.

| זוג | התאם ב |
| --- | --- |
| `tool_use` → `tool_result` | `tool_call_id` |
| `hook_triggered` → `hook_completed` | `hook_id` |
| `agent_pause` → `agent_resume` | `pause_id` |
| `human_wait` → `human_input` | `input_id` |
| `model_request` → `model_response` | `request_id` |

**אל תעביר את `duration_ms` בעצמך.** ה-SDK מודד אותו, והעברה שלו מעלה `ValueError`.

ההיוצא מן הכלל הוא `model_response`, שם רק אתה יודע את latency של ה-provider האמיתי. עביר מספר שלם של אלפיות שנייה — float מעלה, כי העמודה היא מספר שלם 32-bit והייתה אחרת נחתת ריקה.

<Accordion title="Edge cases" icon="circle-help">

- **Ids רק צריכים להיות ייחודיים לפי סוג, לפי session.** כלי call וhook יכולים לשתף אחד; שתי sessions שרצות בו-זמנית יכולות להשתמש חוזר באותם ids ללא התנגשות.
- **הם לא בהיקף סוכן.** זוג שנפתח תחת סוכן אחד וסגור תחת אחר עדיין תואם — שזה המקרה הנורמלי בקוד רב-סוכנים.
- **`request_id` אופציונלי אך מומלץ.** ללא זה, אירועי מודל מזווגים בסדר שהם מגיעים, כך ששתי קריאות קונקורנטיות באותו סוכן יכולות להתעוות בטעות.
- **זוג מפוצל על פני תהליכים** עדיין תואם ב-Cloud, אך ה-SDK לא יכול למדוד אותו — כלום בשום תהליך לא ראה את שני החצים.
- **לכל היותר 10,000 openers מחכים ל-closer בו-זמנית.** מעבר לכך הקדום ביותר מושמט, כך שניקוז לא יכול לגדול ללא קשור.

</Accordion>

## השדות שלך

כל מילה חדשה שאתה עובר מאוחסנת עם האירוע:

```python
failproofai_sdk.event.tool_use(
    tool_name="search", tool_call_id="c1",
    fw_tenant="acme", fw_region="eu-west-1",     # שלך
)
```

בחר סוגי JSON אם אתה רוצה לשאול אותם מאוחר יותר. כל דבר אחר — UUID, datetime, `Decimal`, set, bytes, אובייקט מודל — מאוחסן כמחרוזת.

<Warning>
  **הקדימו את שמות השדה שלך.** Extras מיושמות אחרונות, כך ששדה בשם `model`, `tool_name` או `outcome` שקט דורס את האמיתי. ה-framework adapters משתמשים ב-`fw_`; עשה את אותו דבר ולא כלום יכול להתנגש.

  זה גם למה שדה אופציונלי שגוי לעולם לא שגיאה — זה פשוט הופך לשדה מותאם חדש. אם שדה סטנדרטי חסר ב-Cloud, בדוק תחילה את האיות.
</Warning>

חמישת השמות הללו שמורים ודחויים בחוץ: `timestamp`, `session_id`, `agent_id`, `type`, `environment`.

## הסב ותאמת

<Tabs>
  <Tab title="Dashboard">
    ב-**Observe → Events**, אמת `agent_start` קיים תחילה ו-`agent_end` קיים אחרון. ואז פתח את **Observe → Sessions** ואשר שמודל, כלי, אדם, hook, ואירועי שגיאה מופיעים בסדר המיועד. השתמש ב-session ID כמפתח פתרון בעיות ראשוני.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

אם Cloud ריק, בדוק `$FAILPROOFAI_HOME/custom-agents/events`, אחרת `~/.failproofai/custom-agents/events`. קובצי JSONL מוכיחים פליטת SDK; spool גדל מצביע על תצורת daemon או הסבה, בעוד spool ריק מצביע על כיול או חיי תהליך.

<Note>
  בדוק את ה-spool רק כשה-daemon עצור. בזמן שהוא רץ, הוא אוסף ודולק כל batch בתוך אלפיות השנייה, כך שרשימת ספרייה מתחרה בקולטור ומציגה הרבה פחות אירועים מאשר התפנו.
</Note>

## מנע כשלונות בruntime מותאם

השתמש בממצאי ביקורת ובעקבות מקושרות כדי להגדיר את הפעולה הלא בטוחה, הראיות הנדרשות, והתגובה המיועדת. אינטגרציית אכיפה מותאמת חייבת לחשוף את הפעולה לפני ביצוע, להעביר את הקלט המובנה שלה למנוע המדיניות, ויישום את ההחלטה allow, instruct, או deny.

[צור קשר עם Failproof AI](mailto:support@befailproof.ai) ונעזור למפות את מודל ה-runtime שלך, כלי וגבולות החיים לhooks מדיניות, ואז אמת את האינטגרציה איתך.
