התקן את ה-CLI המקומי עם `npm install -g failproofai`. הרץ אותו ללא ארגומנטים כדי לפתוח את לוח המחוונים של מדיניות מקומית.

החבילה דורשת Node.js 20.9 ופי חדשה יותר. Bun 1.3 ופי חדשה יותר נתמך לפיתוח והתקנות ממקור. `failproofai configure` ו-`failproofai setup` הם כינויים לـ `failproofai config`. `failproofai policy`, `failproofai pack` ו-`failproofai p` הם כל הצמדים של `failproofai policies` — packs ומדיניות בודדות היו שלוש פקודות לרעיון אחד והם כעת אחד. הצמדים הישנים יותר עדיין עובדים, עם שתי חריגויות: `pack list <source>` הוא כעת `policies show <source>`, ו-`pack build` הוא כעת `publish`.

## הגדרת מכונה

התקן את ה-CLI, ואז קרא את מפתח המכונה לתוך ה-shell. `read -s` לוקח אותו בהנמקה שלא מדפיסה, כך שהוא לעולם לא מופיע בפקודה:

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

ואז הגדר את המכונה ובחר מה היא אוכפת:

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` הוא כל ההגדרה: הוא מתקין את שירות `failproofaid` (root פעם אחת — בטרמינל הוא מבקש את סיסמת sudo שלך, ושואל שוב אם זה פג לפני שההגדרה הסתיימה; ללא טרמינל הוא משתמש ב-`sudo -n` ולעולם לא מנוסה), מחבר hooks לכל CLI של agent שהוא מוצא, ומתחבר לענן. ללא טרמינל — CI, container, agent המנהל אותו — הוא מחיל במקום לשאול, ויוצא 1 אם משהו שנשאל לעשות לא קרה.

בטרמינל, שלב **Connect to cloud** על מכונה שעדיין לא מחוברת מתחיל **logging in to FailproofAI Cloud** מיד; לחץ על Tab עבור האפשרויות האחרות, **Paste an API key** או **Use open source**. ההתחברות פותחת קישור — או מדפיסה אותו על SSH או ללא תצוגה, לפתיחה על כל מכשיר — שם אתה מנרמל או מתחבר, בוחר או יוצר ארגון, ומאשר את המכונה; הטרמינל קולט את האישור בעצמו ומציג מי אישר זאת ולאיזה ארגון. המפתח מוטבע רק כאשר ההגדרה מסתיימת, לאחר שה-daemon מותקן. על מכונה שכבר מחוברת עם מפתח עובד, השלב הוא תפריט עם **Keep current connection** ראשון, כך שהרצה מחדש של setup לעולם לא פותחת דפדפן בעצמו; מפתח שמור שכבר לא עובד מתחיל להתחבר מחדש מיד, ואומר למה. התחברות שוב יוצרת מפתח חדש ומשאירה את הישן עובד עד שתבטל אותו. Cloud מלפני browser login אומר כן ומציע את האפשרויות האחרות.

הוא בוחר **no** policies. זו עבודתה של הפקודה השנייה, וללא זה מכונה שהוגדרה זה עתה לא אוכפת כלום חוץ מה-always-on guard.

העדף משתנה סביבה על פני `--token`: טיעון שורת פקודה קריא מ-`ps` על ידי כל משתמש בקופסה. זה כל מה שהמשתנה מגן עליו — מפתח שהוקלד לכל פקודה, `export` כלול, עדיין נוחת בהיסטוריית shell, וזו הסיבה שהוא נקרא עם `read -s` למעלה. ב-CI, הגדר אותו מחנות הסודות ושמור על follow-up של shell (`set -x`) כבוי, או העקיבה תדפיס אותו.

<Warning>
  `--connect <url>` רושם מכונה שכבר **set up**. הוא חוזר ברגע שההרשמה מצליחה — הוא לא מתקין את ה-daemon ולא מחבר כל hook. השתמש ב-`failproofai config` רגיל (או `failproofai config --token <key>`) על מכונה שעדיין לא הוגדרה, או היא תקרא כמחוברת בזמן שאוספת ואוכפת כלום.
</Warning>

הרץ `failproofai` ללא ארגומנטים כדי לפתוח את לוח המחוונים של מדיניות מקומית.

| פקודה | תוצאה |
| --- | --- |
| `failproofai config` | הגדר את המכונה: agents, daemon, וענן — היכנס דרך הדפדפן, הדבק מפתח, או הישאר open source. כל agent במכונה גם מקבל skill קטן של `failproofai` המצביע אליו בـ [FailproofAI skills](https://github.com/FailproofAI/skills) באינטרנט |
| `failproofai config --token <key>` | הגדר וחבר בפעם אחת, ללא שאלות. מפתח הנושא `jev:evaluate` גם הופך [Jev through FailproofAI Cloud](/he/reference/jev-cloud) למצב observe, אלא אם `jev.json` כבר קיים או `--no-transcripts` ניתן |
| `failproofai config --connect <url>` | רשום מכונה שכבר **set up** — ללא daemon, ללא hooks |
| `failproofai config --status` | הציג חיבור, daemon, משלוח, ומצב השהייה |
| `failproofai policies` | רשימת builtin, custom, convention, pack, ומדיניויות מנוהלות בענן |
| `failproofai policies --install` | חבר hooks לאגפי agent שלך. לא מאפשר כל מדיניות בעצמו |
| `failproofai policies add <name>` | אפשר מדיניות אחת — builtin, או `<pack-id>:<name>` מחבילה מותקנת |
| `failproofai policies remove <name>` | השבת מדיניות אחת, אותה שמות |
| `failproofai policies --uninstall` | השבת מדיניויות או הסר harness hooks |
| `failproofai policies show <owner>/<repo>` | מה חבילה נושאת, קרא מהמנिפסט שלה, לפני שתקח אותה |
| `failproofai policies show <owner>/<repo> --releases` | כל גרסה שפרסמה, ואיזו כאן |
| `failproofai policies add <source>` | התקן חבילת מדיניות מ-GitHub release; ללא tag לוקח את החדשה ביותר ומתעד אותה |
| `failproofai publish` | שלח את המדיניויות שלך כחבילה; `--init` כותב אחת להתחלה, ו-`--min-cli-version <version>` מגדיר את ה-CLI הישן ביותר שעשוי להתקין אותה ([Jev checks in a pack](/he/policies/publish-a-pack#jev-checks-in-a-pack)) |
| `failproofai policies remove <publisher/name>` | הסר התקנה של חבילה |
| `failproofai audit` | סרוק את היסטוריית agent מקומית ופתח את תצוגת ה-audit המקומית |
| `failproofai audit --schedule [days] --email <address>` | תזמן סריקות מקומיות חוזרות וודי את הממצאים שלהן |
| `failproofai audit --status` | הציג את כתובת הדוח, המרווח, וה-scan הממוזמן הבא |
| `failproofai audit --no-schedule` | עצור סריקות חוזרות ללא מחיקת היסטוריית audit |
| `failproofai harness list` | רשימת נתיבי התקפה נוספים |
| `failproofai otel status` | בחן דיווח [OpenTelemetry](/he/reference/otel) אופציונלי |
| `failproofai jev --url <url> --key-stdin` | הגדר את Jev בשלב אחד; הספק נלקח מ-host של ה-URL |
| `failproofai jev setup --provider <kind> --key-stdin` | תן ל-[Jev](/he/reference/jev-providers) לשפוט קריאות כלי דרך נקודת הסיום שלך ומפתח |
| `failproofai jev setup --provider failproofai` | תן ל-Jev לשפוט קריאות כלי [through FailproofAI Cloud](/he/reference/jev-cloud), עם מפתח Cloud של המכונה הזו |
| `failproofai jev setup --mode <m>` | החלף את מצב Jev: `enforce`, `observe`, או `off` (שמור את התצורה, הפסק לשאול את Jev) |
| `failproofai jev status` | הציג את תצורת Jev, ההרשאות שלה וכישלונות אחרונים; לעולם לא את המפתח |
| `failproofai jev test` | שלח בקשת Jev חיה אחת והציג את latency וגרסתה; יוצא 1 כאשר התשובה מאוחרת עבור hooks או שגויה |
| `failproofai jev models` | רשימת מזהי מודל `GET <base>/models` אומר לנקודת סיום |
| `failproofai jev remove` | כבה את Jev; hooks מריצים את מדיניויות ה-regex בדיוק כמו קודם |
| `failproofai flush --wait` | משלוח את זיקוק האירוע הנוכחי |
| `failproofai backfill --since 30d` | קרא מחדש היסטוריה שעברה קודם לכן |
| `failproofai config --pause [duration]` | השהה סשן מקומי אחד במשך 30 דקות כברירת מחדל, עד 8 שעות |
| `failproofai config --resume` | התייחס לסשן מקומי מושהה; הוסף `--all` כדי לנקות את כל ההשהיות |
| `failproofai update` | סיים נדידות חבילה וכדי לעדכן את ה-daemon |
| `failproofai migrate --dry-run` | עיין או הרץ נדידות מתכננות של בית |
| `failproofai uninstall` | הסר hooks, את ה-`failproofai` skill וה-daemon לפני הסרת החבילה |
| `failproofai --version` | הדפס את גרסת החבילה המותקנת |
| `failproofai --help` | הציג פקודות ושימוש גלובלי |
| `failproofai help <command>` | הציג אפשרויות של פקודה אחת וודוגמאות, כמו `failproofai <command> --help` |

## דגלי תצורה

| דגל | שימוש |
| --- | --- |
| `--token <key>` | הגדר וחבר באופן לא אינטראקטיבי; גם קרא מ-`FAILPROOFAI_CLOUD_TOKEN` |
| `--oss` | השתמש ב-open source ללא חיבור Cloud; חיבור קיים נשאר כما הוא |
| `--agents <a,b>` | עקוב אחרי agents אלה, או `all`, ללא שאלות |
| `--url <url>` | התחבר למקום אחר מאשר `app.befailproof.ai`; גם קרא מ-`FAILPROOFAI_CLOUD_URL` |
| `--connect <url>` | רשום בלבד, על מכונה שכבר הוגדרה. דלג על ה-daemon וכל hook |
| `--machine-id <id>` | מזהה מכונה עבור `--connect`; ברירת מחדל למזהה יציב |
| `--machine-label <name>` | בעצמו, שנה שם למכונה שכבר **connected**; זה לעולם לא מריץ setup. עם `--token`, התחבר תחת שם זה; מפתח שנקבע רק ב-`FAILPROOFAI_CLOUD_TOKEN` לא מספיק, כי `--machine-label` ללא `--token` הוא שינוי שם. עם `--oss` או `--agents`, הוא משנה שם למכונה שכבר מחוברת ודחוי לפני setup בזה שלא: `--oss` לעולם לא מתחבר, ו-`--agents` צריך מפתח או התחברות Cloud אינטראקטיבית כדי להתחבר |
| `--no-transcripts` | שלח החלטות ללא תוכן תמלול, ואל תהפוך את Cloud Jev, שישלח כל בדיקת כלי וההנחה האחרונה; `jev.json` שהותיר את Jev עובד דרך FailproofAI Cloud מוסר |
| `--disconnect` | עצור משיכות מדיניות Cloud ומשלוח אירוע. גם מסיר את המפתח של Cloud Jev ו-`jev.json` ששמותו FailproofAI Cloud; הגדרת Jev שלך נשארת במקום |
| `--status` | הציג מצב מכונה נוכחי |
| `--pause [duration]` | השהה את הסשן החדש ביותר בתיקייה הנוכחית; מקבל שניות, דקות, או שעות וברירת מחדל ל-30 דקות |
| `--resume` | סיים השהיה תואמת מוקדם |
| `--session <id>` | סט עקיף סשן עבור השהיה או חזרה |
| `--all` | עם `--resume`, סיים כל השהיה פעילה |

השהיות מקומיות מעלימות מדיניויות builtin, custom, convention, וpack עבור סשן אחד. הם תמיד פוקדים, לכל היותר 8 שעות אחרי ההשהיה הראשונה בריצה, והם לא מנטרלים מדיניויות מנוהלות בענן או `block-failproofai-commands`, שתמיד פעיל ולא יכול להיות משוננה או מושהה בעצמו. כי הגנה מסרבת את הדרכים הישירות שבהן agent מכשור יכול להשהות את עצמו: הרצת `failproofai config --pause`, או כתיבת קובץ ההשהיה תחת `~/.failproofai/state/sessions/`. הוא קורא פקודות, לא מה שתוכנית עושה כאשר היא רצה, כך שתוכנית שה-agent כותב ואז מריץ עדיין יכולה להגיע לאותו מצב. קובץ השהיה נבדק לתוקף תחום וכתחילה לא יותר מדקה בעתיד, לא למי כתב אותו.

## דגלי מדיניות

| דגל | שימוש |
| --- | --- |
| `--install`, `-i` | התקן harness hooks. שמות אחריו אפשרו את המדיניויות הללו; ללא אחד, ללא שינויי מדיניות |
| `--uninstall`, `-u` | השבת מדיניויות או הסר hooks |
| `--cli <names...>` | סט עקיף harness אחד או יותר |
| `--scope user\|project\|local\|all` | בחר את תחום התצורה; `all` עבור uninstall |
| `--beta` | כלול מדיניויות בטא |
| `--custom`, `-c <path>` | עם `--install`, אמת וטען קובץ מדיניות מותאם אישית; חוזר. `--uninstall -c` מסיר כל קובץ מדיניות מותאם אישית |
| `--policy`, `--only <a,b>` | התקן רק מדיניויות אלה מחבילה |
| `--category <x,y>` | התקן רק קטגוריות אלה מחבילה |
| `--all` | רשימת כל מדיניות; עם חבילה, התקן הכל |
| `--releases` | עם `show`, רשימת גרסאות חבילה וחיזוק אחד מותקן |

## דגלי משלוח ותחזוקה

| פקודה | דגלים |
| --- | --- |
| `backfill` | `--since <30d\|6m\|1y\|YYYY-MM-DD>`, `--agents <a,b>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` (`-y`) |

### Backfill per harness

`backfill` שולח מחדש היסטוריה שהאוסף כבר קרא, על מכונה מחוברת לענן. `--since` קובע את החלון עבור רוב harnesses, עם שתי חריגויות:

- **Goose, OpenCode וDevin** שלח את כל היסטוריית שלהם, מה גם `--since` אומר: היסטוריית שלהם חיה במסד נתונים שהאוסף קורא ללא חלון זמן, כך `--dry-run` מדווח עליהם כעל כל הסשנים.
- **Hermes** היסטוריה לא נשלחת מחדש על ידי `backfill`.

`failproofai update` צריך להיות מורץ אחרי `npm install -g failproofai@latest`; הוא מבצע נדידות של תכנון בית, מתקין את ה-daemon הבינארי התואם, ומפעיל מחדש את השירות. הוא אז מעביר כל פרופיל Hermes שכבר משתמש ב-FailproofAI לתוסף הילידי המקושר ודפס שורה אחת לכל פרופיל. `--no-daemon` דלג על שלב daemon. `update` יוצא non-zero כאשר ה-daemon לא יכול להחליף, נדידה נכשלה, או פרופיל Hermes לא יכול להיות מועבר (למשל כי ה-daemon הפעיל לא יכול להגיש את התוסף הילידי, ובמקרה זה hooks הקליפה שלו נשארים במקום).

## נתיבי Harness

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

שמות harness נתמכים הם `claude`, `codex`, `copilot`, `cursor`, `opencode`, `pi`, `hermes`, `openclaw`, `factory`, `devin`, `antigravity`, ו-`goose`.

תווית משנה מזהי agent נגזר כאשר שתי שורשים מכילות עותקים של אותו פרויקט. שורשים חופפים ותוויות כפולות דחויות כדי למנוע אוסף כפול או שחיתות cursor. תצורת נתיבים נוספים טוענת מחדש ללא הפעלה מחדש של daemon.

סביבות מכולה יכולות להחליף נתיבים נוספים שהוגדרו בקובץ עם משתנה מופרד בפסיקים בשם `FAILPROOFAI_<HARNESS>_EXTRA_PATHS`, לדוגמה:

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## משתני סביבה

השתמש בקבצי תצורה להתנהגות מכונה קבועה. משתני סביבה הם השימושי ביותר עבור מכולות, בדיקות, ותהליך אחד.

| משתנה | שימוש |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | המפתח Cloud, במקום `--token`. העדף זאת: טיעון קריא מ-`ps` על ידי כל משתמש. הגדר אותו עם `read -s` או מחנות סודות CI, לעולם לא על ידי הקלדת מפתח לפקודה, שנוחת בהיסטוריית shell כך או כך |
| `FAILPROOFAI_CLOUD_URL` | ה-URL של Cloud, במקום `--url`. אותו משתנה שה-daemon קורא |
| `FAILPROOFAI_HOME` | העבר את התכנית המלאה של `~/.failproofai` |
| `FAILPROOFAI_LOG_LEVEL` | הגדר מילות דיווח מקומיות |
| `FAILPROOFAI_HOOK_LOG_FILE` | כתוב אבחון hook לקובץ שנבחר |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | השבת טלמטריה אנונימית עבור תהליך זה |
| `FAILPROOFAI_NO_FIRST_RUN=1` | דלג על setup first-run אינטראקטיבי |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | דלג על ה-audit מקומי לאחר setup |
| `FAILPROOFAI_LLM_BASE_URL` | בטל את נקודת הסיום התואמת ל-OpenAI המשמשת למדיניויות LLM |
| `FAILPROOFAI_LLM_API_KEY` | ספק את מפתח ה-API המשמש למדיניויות LLM |
| `FAILPROOFAI_LLM_MODEL` | בחר את המודל המשמש למדיניויות LLM |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | טבילת טעינת מודול מדיניות מותאמת אישית |
| `FAILPROOFAI_NO_DOWNLOAD=1` | סרב להביא חבילות ו-daemon בינאריות; מה שהותקן משמר אכיפה |
| `FAILPROOFAI_PACK_BASE_URL` | אחזר חבילות מכינה במקום `github.com` |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | החלף נתיבי התקפה נוספים שהוגדרו עבור harness אחד |
| `NO_COLOR` | השבת פלט טרמינל בצבע |

משתני בית ספציפיים לאגנט כמו `CLAUDE_PROJECTS_PATH`, `CURSOR_HOME`, `HERMES_HOME`, ו-`OPENCLAW_HOME` בטלו איפה Failproof AI גילה סשנים מקומיים עבור harness זה.

## הושהה או הסר מכונה בבטחה

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

השהיית סשן מקומית לא מנטרלת מדיניויות מנוהלות בענן. שחזר פריסות Cloud מ-**fix → deploy policies** בCloud כאשר הגלגול עצמו הוא הבעיה.

לפני הסרת החבילה npm, הסר hooks מותקנות וה-daemon:

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

הרץ `failproofai <command> --help` לפרטים ספציפיים לגרסה.

<Warning>
  הרץ `failproofai uninstall` לפני `npm rm -g failproofai`; npm לא מסיר agent hooks מותקנות, את ה-`failproofai` skill או שירות daemon.
</Warning>
