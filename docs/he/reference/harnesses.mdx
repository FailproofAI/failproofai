ממשק הוא כל דבר שהסוכן שלך למעשה מפעיל בתוכו. Failproof AI תומך בשנים עשר מהם, בשתי קטגוריות:

- **CLIs קידוד** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **שערי צ'אט ועוזרים** (2) — Hermes (Slack, Telegram, cron), OpenClaw (עוזר בעצמאית אירוח)

אותן מדיניויות והיסטוריית הישיבה הזהה חלות על איזה ממשק מפעיל הסוכן. שכבת מתאם אחת ממפה את שמות האירועים המקוריים של כל ממשק, שמות הכלים ושדות קלט הכלים ל-29 אירועים קנוניים לפני הפעלת מדיניות כלשהי.

סוכן שמפעיל ב**אף אחד** מהשנים עשר מחוברים ישירות עם [Python SDK](/he/reference/custom-agents). זה חוזה שונה, וראוי להצהיר בבהירות: SDK מספק ניתוח מסלול, ישיבות, הערכות וביקורות — **הוא לא מטיל מדיניויות בעצמו.** חסימת פעולה בלתי בטוחה לפני הביצוע שלה דורשת קרס אכיפה בגבול הכלים של ה-runtime שלך; [צור איתנו קשר](mailto:support@befailproof.ai) ואנחנו נממפה אותה.

כל אינטגרציה מנרמלת את שמות אירועי הקרס המקוריים שלה, שמות כלים ושדות קלט כלים לפני הפעלת מדיניויות. מדיניות יכולה לפעול רק על אירועים שהממשק חושף; בדוק התנהגות סוף תור והוראה על הממשק והגרסה המדוקדקת שאתה מפרוס.

## יכולת אכיפה

"חסימה" פירושו שהפסק של מתאם זה מנוצל על ידי הממשק הנקוב. חסימת ما-לאחר-כלי עשויה להחליף את התוצאה המוצגת למודל אך אינה יכולה להשמיד השפעה צדדית של כלי שכבר התרחשה.

יכולות תלויות בגרסה. בדוק מחדש לאחר שדרוג CLI של סוכן, במיוחד כשמדיניות מסתמכת על התנהגות הנחיה, עצירה, הרשאה או ما-بعد-الأداة ולא על שער ما-قبل-الأداة הנפוץ.

### תוסף Hermes מקומי

Hermes משולבת דרך תוסף מקומי מקומי ולא דרך פקודה shell. התקנה מקשרת כל פרופיל Hermes ברירת-מחדל ובשם `plugins/failproofai` לתוסף המשודר בחבילת npm (עותק שבו לא ניתן ליצור סימלינק), מפעילה אותו בקובץ `config.yaml` של פרופיל זה, ומוציאה רק ערכי קרס shell VersionControl ה-FailproofAI. מכיוון שהתוסף קשור, `npm install -g failproofai@latest` מעדכן אותו ללא התקנה מחדש. זה מונע ביצוע תהליך בכל קרס. התוסף תומך ב-Hermes 0.20.0 ואילך.

קרסי shell עתיקים (מותקנים על ידי 1.0.5 ומוקדם יותר) לא **בודקים** עבודות cron של Hermes: כל הפעלת cron בונה טווח קרס משלה, אותו התוסף המקומי מצטרף וקרסי shell `config.yaml` לא. `failproofai update` מוציא כל פרופיל שכבר משתמש ב-FailproofAI לתוסף הקשור. אם הדמון הרץ לא יכול להציע את התוסף, `update` משאיר את קרסי ה-shell במקום ויוצא עם ערך שאינו אפס; הפעל `failproofai config` להעדכן את הדמון, ואז `failproofai update` שוב. עבודות Cron טוענות את התוסף בהפעלה הבאה שלהם; הפעל מחדש שערים ופעילויות אינטראקטיביות רצות לטעום אותו שם.

ב-Hermes, `deny()` חוסם את הקריאה ו-`instruct()` לא: הקריאה מתנהלת, והנחיה מוצבת בתחילת התוצאה — כמפתח ראשון, `failproof_policy_reminder`, של תוצאה JSON, או כשורה `[FailproofAI policy reminder (...)]` מובילה — כך שהמודל קורא אותה עם הפלט, וסקריפטים המחלקים את התוצאה ממשיכים לעבוד. זיכרון מדיניות מוצג פעם אחת לתור, ונשמר קצר בתוצאה גדולה. השתמש `deny()` כאשר פעולה חייבת שלא תתרחש בכלל: `instruct()` כבר לא עוצר את הפעולה תחילה. קריאות כלים שנעשו משסקריפט `execute_code` שמות זיכרונם על תוצאת `execute_code` שהמודל קורא; העותק שלו של התוצאה משאיר ללא נגע. המודל נאמר לעולם לא לצטט זיכרון בתשובותיו.

בנייה של Hermes ללא middleware תוסף חוזרת להחזקת קריאה תואמת פעם אחת עם הנחיית מדיניות FailproofAI; התגובה הבאה של המודל עשויה לחזור עליה, או לעשות את אותה עבודה עם כלי אחר, ללא החזקה שוב.

שמות כלים תואמים בגרסאות Hermes: `process_manage`, `cronjob_manage` ו-`todo_list` (Hermes 0.21) מטופלים כמו `process`, `cronjob` ו-`todo` (Hermes 0.20). בכל פעם Hermes טוען את התוסף הוא כותב `heartbeat.json` בתיקיה `plugin-data/agent-plugin-failproofai-5296f299/` של הפרופיל, ומתעד את גרסת Hermes, נתיב ותוקף התוסף, וקרסי Hermes קיבל. הפעל `failproofai config --status` כדי לגלות פרופיל מופסק, לא שלם, משוכפל או חדש שלא הוגדר, או עדיין בקרסי shell קדומים (דווח כ-"ללא בדיקה לעבודות cron של Hermes").

### תוסף OpenClaw

OpenClaw טוען את FailproofAI כתוסף שער תוך-תהליך, רשום בקובץ `openclaw.json` של כל פרופיל. כמו תוסף Hermes, הוא שואל את הדמון `failproofaid` המקומי לכל פסק דין על הקובץ שלו, אז הוא זקוק לדמון רץ: התקנה מסרבת ללא אחד, ואם הדמון לא יכול להשיב, קריאות כלים והנחיות חסומות והסיבה נכתבת ליומן השער. לאחר `npm install -g failproofai@latest`, הפעל מחדש את שער OpenClaw כדי שיטען את התוסף המעודכן.

### אמון קרס Codex

Codex 0.129 ואילך מריצה קרס מ-`~/.codex/hooks.json` רק לאחר שתאשר אותו ב`codex` אינטראקטיבי ("סקור קרסים"); עד אז, כל ישיבת Codex — `codex exec` headless כלול — מדלג עליו. קרסים בתצורה מערכת של Codex, `/etc/codex/config.toml` ב-Linux ו-macOS, מתנהלים ללא אישור זה.

אז כאשר `failproofai config` (או `policies --install --cli codex` בטווח משתמש) יכול להשתמש ב-sudo, הוא כותב קרסי Codex ל-`/etc/codex/config.toml`, בין `# >>> failproofai managed hooks >>>` ל-`# <<< failproofai managed hooks <<<`, ויעזוב את שאר הקובץ הזה כמו שהיה. הקובץ חל על כל חשבון במכונה. `failproofai uninstall` וביטול סימון Codex ב-`failproofai config` מסירים את הבלוק שוב.

ללא sudo, וב-Windows, הקרסים נשארים ב-`~/.codex/hooks.json`. `failproofai config` ו-`failproofai config --status` אז לא סופרים Codex כ-enforcing עד שהקרסים אושרו, ואומרים כיצד לתקן זאת: הפעל מחדש `failproofai config` והרשה sudo, או פתח את `codex` פעם אחת ואשר את הקרסים.

## התקנת קרסי תפיסה ומדיניות

<Tabs>
  <Tab title="לוח בקרה">
    1. פתח **Administration → Keys** וצור מפתח עם `events:add` ו-`policies:pull`, בשם המכונה או הסביבה.
    2. במכונת היעד, חבר את ה-CLI המקומי עם המפתח המוצג והתקן את קרסי הממשק.
    3. התחל ישיבת סוכן חדשה, ואז אשר את קרסיה ואירועי הישיבה שלה תחת **Observe → Events**.
    4. פתח **Observe → policy** לאותו חלון זמן ואשר שהחלטת מדיניות מיוחסת למכונה.

    החיבור מתחיל עם מפתח מכונה. אשר שהוא כולל הן הרשאות ספיגה והן הרשאות משלוח מדיניות לפני העתקת הסוד שלו.

    ![מגירת המפתח החדשה של API המשמשת להעניית הרשאות ספיגת אירוע והרשאות משלוח מדיניות.](/images/dashboard/key-create.png)

    לאחר התקנת הקרסים, זרם Events צריך להיות מוצג אירועים חדשים מהמכונה והסביבה שחיברת.

    ![זרם Events חי המשמש לאישור שממשק שהותקן לאחרונה מדווח.](/images/dashboard/events-stream.png)

    לבסוף, אמת שהחלטות מדיניות מיוחסות לאותה מכונה. זה מאשר שהממשק מדווח על פעילות מדיניות וכן על אירועי עקיבה.

    ![עמוד המדיניות המשמש לאימות החלטות מדיניות מממשק שזה עתה חובר.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    קרא את מפתח המכונה ל-shell. `read -s` לוקח אותו בהנחיה שאינה מהדהדת, כך שהוא לעולם לא מופיע בפקודה או בהיסטוריית shell:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    ואז הגדר את המכונה — זה חוטי קרסים עבור כל ממשק גילה, מתקין את הדמון, ומתחבר ל-Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    ההתקנה אינה מפעילה מדיניות בעצמה, וזה מה שהפקודה השנייה היא.

    או מטרה ממשקים בעלי שם וטווח תצורה:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    טווח פרויקט שומר תצורת קרס עם מאגר. טווח משתמש מכסה עבודה על פני מאגרים. Claude Code תומך גם בטווח מקומי; התמיכה משתנה לפי ממשק ו-CLI דוחה שילובים שאינם נתמכים.

    אמת את המכונה ואירועיה:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## הוסף נתיב ישיבה שאינו ברירת-מחדל

<Tabs>
  <Tab title="לוח בקרה">
    נתיבים נוספים רשומים במכונה, לא ב-Cloud. לאחר הוספת אחד, פתח **Observe → Sessions**, סנן לסביבה של המכונה, ואשר שישיבות מהנתיב החדש מופיעות. פתח ישיבה ובדוק את הסוכן, הממשק וחותמות זמן אירוע לפני התוכנו בביקורת.

    ![רשימת הישיבות מסוננת לסביבה המקבלת נתונים מנתיב התפיסה הנוסף.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    הוסף נתיב עם תווית אופציונלית, ואז בדוק את הנתיבים המוגדרים:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    הסר נתיב עם `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  הפעל ישיבה חדשה אחת לאחר התקנה. אמת הן את זרם האירוע החי והן החלטת מדיניות בפועל לפני הרחבת ההטלה.
</Tip>
