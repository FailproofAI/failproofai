ה-API הציבורי מוגש תחת `/v1` בבסיס ה-Failproof AI שלך.

## יצירת מפתח וביצוע בקשה

<Tabs>
  <Tab title="Dashboard">
    1. פתח את **Administration → Keys**, בחר **Create key**, ובחר את ערכת ההרשאות המצומצמת ביותר המכסה את האינטגרציה.
    2. הוסף הענקות בודדות רק בעת הצורך, צור את המפתח, והעתק את הסוד החד-פעמי שלו.
    3. בצע בקשת בדיקה ל-`/v1/sessions` וודא שהמפתח נשאר פעיל בעמוד Keys.
    4. סובב או השבת את המפתח מתפריט הפעולות שלו כאשר אחזקת האינטגרציה משתנה.

    ![תיקיית מפתח API חדש עם ערכות הרשאות והענקות בודדות.](/images/dashboard/key-create.png)

    מגירת היצירה מוצגת למעלה. הסוד החד-פעמי מופיע רק לאחר שתבחר **create**; העתק אותו לפני סגירת האישור הזה.
  </Tab>
  <Tab title="CLI">
    צור מפתח קריאה והשתמש בו ישירות עם `fp` או `curl`:

    ```bash
    fp keys create reliability-reader \
      --permission-set read-only

    fp --api-key <key> sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/sessions?limit=20" \
      -H "Authorization: Bearer $FAILPROOFAI_KEY"
    ```
  </Tab>
</Tabs>

מפתחות מוגדרים לארגון וערכת הרשאות. בקשה ללא ההרשאה הנדרשת של הנקודה הקצה מחזירה `403` ומזהה את ההרשאה החסרה.

## בחירת ארגון

מפתח ארגון פועל על הארגון שלו באופן אוטומטי. מפתח בהיקף מופע יכול לבחור ארגון לכל בקשה:

<Tabs>
  <Tab title="Dashboard">
    השתמש בממיר הארגון בכותרת ה-dashboard לפני פתיחת **Administration → Keys**. מפתחות שנוצרו שם שייכים לארגון שנבחר. אשר את slug הארגון בכתובת URL ופרטי המפתח לפני העתקת התביעה לאוטומציה.

  </Tab>
  <Tab title="CLI">
    השתמש ב-`--org` לפני הפקודה, או שלח את כותרת הארגון למפתח API בהיקף מופע.

    ```bash
    fp orgs list
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/usage" \
      -H "Authorization: Bearer $FAILPROOFAI_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

השתמש בעמודי הנקודות הקצה שנוצרו בסעיף זה לנתיבים עדכניים, פרמטרים, דרישות הרשאה וקודי מצב. המפרט נוצר מהערות מסלול השרת ובדוק מול ניתוב `/v1`.

המפרט הנוכחי כולל כיסוי מלא של מסלול, שיטה, פרמטר, הרשאה וקוד מצב. גופי תגובה מסוימים נותרים ללא סוג בכוונת תכנון מכיוון שהשרת עדיין בנה אותם כ-JSON דינמי. בדוק תגובה אמיתית לפני יצירת קליינט שנוקד בחוזקה סביב נקודת קצה ללא סכמת תגובה.

השתמש ב-`Content-Type: application/json` לכתיבות JSON. התייחס ל-`401` כהתחברות חסרה או לא תקפה, `403` כזהות תקפה ללא ההרשאה הנדרשת, `404` כמשאב חסר או לא נגיש בארגון, `409` כקונפליקט מצב, ו-`422` כערך שדה או הרשאה לא תקפה. תגובות שגיאה כוללות הודעה קריאה לאדם; כשלים בהרשאה גם שמות את ההענקה הנדרשת.

<Warning>
  אכיפת מדיניות הפריסה מנוהלת בכוונת תכנון מחוץ לפני `/v1` הציבוריים הרגילים. השתמש בזרימת הפריסה של Cloud התומכת.
</Warning>
