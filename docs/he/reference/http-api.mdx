ה-API הציבורי מוגש תחת `/v1` במקור לוח הבקרה של Failproof AI. ב-Failproof AI Cloud המקור הזה הוא `https://app.befailproof.ai`, ולכן נתיב הבסיס הוא `https://app.befailproof.ai/v1`. בהפעלה עצמית, זה שם המארח של לוח הבקרה שלך ואחריו `/v1`; העבר את המארח הזה ל-`fp` עם `--base-url <url>` או `FP_DASHBOARD_URL`.

## יצירת מפתח וביצוע בקשה

<Tabs>
  <Tab title="Dashboard">
    1. פתח את **Administration → Keys**, בחר **new key**, ובחר את קביעת ההרשאות הצרה ביותר המכסה את האינטגרציה.
    2. הוסף הענקות בודדות רק כשנדרש, צור את המפתח, והעתק את הסוד החד-פעמי שלו.
    3. בצע בקשת בדיקה ל-`/v1/sessions` והשתכנע שהמפתח נשאר פעיל בעמוד Keys.
    4. סובב או השבת את המפתח מתפריט הפעולות שלו כאשר קניין האינטגרציה משתנה.

    ![תיקיה חדשה של מפתח API עם קביעות הרשאות והענקות בודדות.](/images/dashboard/key-create.png)

    התיקייה של היצירה מוצגת לעיל. הסוד החד-פעמי מופיע רק לאחר יצירת המפתח; העתק אותו לפני סגירת הדבר.
  </Tab>
  <Tab title="CLI">
    צור מפתח קריאה והשתמש בו ישירות עם `fp` או `curl`. `fp` קורא את המפתח מ-`--api-key` או מ-`FP_API_KEY`:

    ```bash
    fp keys create reliability-reader \
      --permission-set read-only

    export FP_API_KEY="<one-time-secret>"
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/sessions?limit=20" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

מפתחות מוגבלים לארגון ולרשימה שטוחה של הרשאות. קביעת הרשאות רק משתלת את הרשימה הזו בזמן יצירה — המפתח מאחסן את ההענקות המורחבות, כך ששינוי הקביעה לאחר מכן לא משנה את המפתח. בקשה ללא ההרשאה הנדרשת של נקודת הקצה מחזירה `403` ומזהה את ההרשאה החסרה.

## בחירת ארגון

מפתח ארגוני פועל על הארגון שלו באופן אוטומטי. מפתח בהיקף מופע בוחר ארגון לכל בקשה, וכל דיירים עם יותר מארגון אחד חייבים תמיד לשם אחד במצב מפתח — `fp` לעולם לא שולח ארגון שמור כאשר הוא מאמת עם מפתח.

| מתקשר | איך אתה שם את הארגון |
| --- | --- |
| `fp`, לכל הפעלה | `--org <slug>`, לפני תת-הפקודה |
| `fp`, מהסביבה | `FP_ORG` |
| HTTP גולמי | כותרת הבקשה `X-AgentEye-Org: <slug>` |

`X-AgentEye-Org` שומר על הכתיב המקורי על החוט. זו הכותרת שלוח הבקרה קורא כדי לפתור את הארגון הפעיל, והשינוי שלה בלקוח מפרק את הבקשה.

<Tabs>
  <Tab title="Dashboard">
    השתמש במעבר הארגון בכותרת לוח הבקרה לפני פתיחת **Administration → Keys**. מפתחות שנוצרו שם שייכים לארגון הנבחר. אשר את slugי הארגון בכתובת URL ובפרטי המפתח לפני העתקת האישור להתאמה אוטומטית.

  </Tab>
  <Tab title="CLI">
    השתמש ב-`--org` לפני הפקודה, או שלח את כותרת הארגון עבור מפתח API בהיקף מופע. `fp orgs list` לא מגלה את ה-slug עבורך כאן — הוא מסרב במצב מפתח; קרא את ה-slug מן מעבר הארגון של לוח הבקרה במקום זאת.

    ```bash
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/usage" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

## דפדוף

נקודות קצה של רשימה הן דפדוף מבוסס keyset, והחוזה זהה בין אם אתה קורא להן דרך `fp` או דרך `curl`.

| אלמנט | משמעות |
| --- | --- |
| פרמטר שאילתה `limit` | שורות המבוקשות בקריאה זו. `fp` מוגבל לבקשה יחידה של 200 שורות בכל נקודת קצה. בקשה גולמית מוגבלת על ידי תקרה שלוקחת בשרת במקום זה. |
| פרמטר שאילתה `cursor` | אסימון אטום המשחזר את הזנת החדשות לאחר עמוד קודם. |
| שדה תגובה `next_cursor` | האסימון לעמוד הבא. `null` פירושו שהזנת החדשות מותשה. |

התקרות הללו שונות לפי נקודת קצה, וכל עמוד נקודת קצה שם את ברירת המחדל וההיקף שלו:

| נקודת קצה | ברירת מחדל | תקרה |
| --- | --- | --- |
| `/events`, `/events/summary` | 50 | 1000 |
| `/issues`, `/alerts/{id}/issues` | 200 | 1000 |
| `/evaluation-jobs` | 100 | 500 |
| `/audits/findings` | 100 | 500 |
| `/sessions`, `/evaluations` | 50 | 200 |
| `/audits/{id}/runs` | 50 | 200 |

קרא הזנה מלאה על ידי הנפקה מחדש של אותה בקשה עם `cursor` מוגדר ל-`next_cursor` של התגובה הקודמת עד ש-`next_cursor` חוזר `null`. הדגלים המקבילים ל-`fp` — `--all`, `--cursor` ו-`--page-size` — מתועדים ב-[Cloud CLI reference](/he/reference/cloud-cli).

## ייחוס נקודת קצה וטיפול בשגיאות

השתמש בעמודי נקודת הקצה שנוצרו בסעיף זה לנתיבים נוכחיים, פרמטרים, דרישות הרשאות וקודי סטטוס. המפרט נוצר מהערות מסלול השרת ובדוק מול נתב `/v1`.

המפרט הנוכחי כולל כיסוי מלא של נתיב, שיטה, פרמטר, הרשאה וקוד סטטוס. גופי בקשה מוקלדים; גופי תגובה אינם — המפרט לא נושא סכימות תגובה כיום, מכיוון שהשרת עדיין בונה אותם כ-JSON דינמי. בחן תגובה אמיתית לפני יצירת לקוח מוקלד חזק.

השתמש ב-`Content-Type: application/json` לכתיבות JSON. התייחס ל-`401` כאל אימות חסר או לא תקף, `403` כאל זהות תקפה ללא ההרשאה הנדרשת, `404` כאל משאב חסר או לא נגיש של ארגון, `409` כאל סכסוך מצב, `400` כנתון שנדחה — ערך סינון לא ידוע, פרמטר שאילתה שגוי, אמירה שלא היתה פועלת — ו-`422` כשדה לא תקף או ערך הרשאה בגוף בקשה. תגובות שגיאה כוללות הודעה קריאה לאדם; כשלי הרשאה גם שמות את ההנחה הנדרשת.

## משטחים שאינם נשאים `/v1`

מדיניות מנוהלת בענן, הצי והזנת החלטת ההגבלה הן משטחי מפעיל — קריאות וכתיבות כאחד. הם root-only בשרת והם בכוונה חסרים ב-`/v1`, שהוא פונה לאינטרנט. פרסום גרסת מדיניות או פריסתה למכונה, למשל, אינו משהו שמפתח API יכול לעשות, וקריאה חזרה למה שהצי החליט היא על אותו משטח.

מפתח API מקבל דחייה על ידי עיצוב בנתיבים אלה, ו-`fp` מסרב לפני פתיחת חיבור במקום לתת לבקשה 404 ללא הסבר:

| פקודה | התנהגות תחת מפתח API |
| --- | --- |
| `fp policies` | מסרב עם יציאה `2` וקוראים למדיניות מנוהלת בענן כמשטח מפעיל |
| `fp fleet` | מסרב עם יציאה `2` ושם הצי כמשטח מפעיל |
| `fp guardrails` | מסרב עם יציאה `2` ושם הזנת ההגבלה כמשטח מפעיל |
| `fp agent` | מסרב עם יציאה `2`; העוזר מיושם על ידי לוח הבקרה, לא ה-API |
| `fp orgs` | מסרב עם יציאה `2`; חברות ארגון שייכה למשתמש מחובר, ומפתח כבר פועל עבור ארגון אחד |

הריץ את אלה תחת הפעלת משתמש מחובר (`fp login`) במקום זאת, או השתמש בלוח הבקרה. משפחות הקריאה וההנהלה — הפעלות, אירועים, הערכות, ביקורות, בעיות, התראות, מפתחות, קביעות הרשאות, משתמשים, הגדרות, שאילתות והשימוש — כל אחד מהם יש נתיב `/v1` ופעול עם מפתח. הפער האחד הוא `fp keys update`: זה צריך `keys:update`, הרשאה שום מפתח API לא יכול להחזיק, אז מפתח יכול להטבע והשבת מפתחות אך לא ערוך את ההרשאות של אחד. `fp login` ו-`fp logout` גם מסרבים במצב מפתח, לסיבה שונה: מפתח כבר הוא האישור, והוא לעולם לא נשמר לדיסק.

<Warning>
  פריסת אכיפת מדיניות מנוהלת בכוונה מחוץ למשטח `/v1` הציבורי הרגיל. השתמש בזרימת Cloud פריסה תמיכה המתוארת ב-[Deploy policies](/he/policies/deploy).
</Warning>
