ה-API הציבורי מוגש תחת `/v1` במקור לוח הבקרה של Failproof AI שלך.

## יצירת מפתח וביצוע בקשה

<Tabs>
  <Tab title="Dashboard">
    1. פתח את **Administration → Keys**, בחר ב-**Create key**, ובחר את הגדר ההרשאות הצר ביותר המכסה את האינטגרציה.
    2. הוסף הענקות בודדות רק כשדרוש, צור את המפתח, והעתק את הסוד החד-פעמי שלו.
    3. בצע בקשת בדיקה ל-`/v1/sessions` ובטא שהמפתח נשאר פעיל בעמוד המפתחות.
    4. סובב או השבת את המפתח מתפריט הפעולות שלו כשהאינטגרציה משנה בעלות.

    ![תיקיית יצירת המפתח החדש של API עם הגדרות הרשאות והענקות בודדות.](/images/dashboard/key-create.png)

    תיקיית היצירה מוצגת לעיל. הסוד החד-פעמי מופיע רק לאחר בחירת **create**; העתק אותו לפני סגירת ההאשרה הזו.
  </Tab>
  <Tab title="CLI">
    צור מפתח קריאה והשתמש בו ישירות עם `fp` או `curl`:

    ```bash
    fp keys create reliability-reader \
      --permission-set read-only

    fp --api-key <key> sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/sessions?limit=20" \
      -H "Authorization: Bearer $FAILPROOFAI_KEY"
    ```
  </Tab>
</Tabs>

מפתחות מוגבלים לארגון וגדר הרשאות. בקשה ללא ההרשאה הנדרשת של הנקודה הקצה תחזיר `403` ותזהה את ההרשאה החסרה.

## בחירת ארגון

מפתח ארגוני פועל בארגון שלו באופן אוטומטי. מפתח המוגבל לתיקייה יכול לבחור ארגון לכל בקשה:

<Tabs>
  <Tab title="Dashboard">
    השתמש במחליף הארגון בכותרת לוח הבקרה לפני פתיחת **Administration → Keys**. מפתחות שנוצרו שם שייכים לארגון שנבחר. אשר את slug הארגון בכתובת ה-URL ופרטי המפתח לפני העתקת האישור להנדסה.

  </Tab>
  <Tab title="CLI">
    השתמש ב-`--org` לפני הפקודה, או שלח את כותרת הארגון עבור מפתח API המוגבל לתיקייה.

    ```bash
    fp orgs list
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/usage" \
      -H "Authorization: Bearer $FAILPROOFAI_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

השתמש בעמודי נקודות הקצה שנוצרו בסעיף זה עבור נתיבים עדכניים, פרמטרים, דרישות הרשאה וקודי מצב. המפרט נוצר מהערות המסלול של השרת ובדוק מול נתב `/v1`.

למפרט הנוכחי יש כיסוי מלא של מסלול, שיטה, פרמטר, הרשאה וקוד מצב. חלק מגופי התגובה נשארים בעיצוב כוונתי לא מוקלד מכיוון שהשרת עדיין בונה אותם כ-JSON דינמי. בדוק תגובה אמיתית לפני יצירת לקוח מוקלד בחוזקה סביב נקודת קצה ללא סכימת תגובה.

השתמש ב-`Content-Type: application/json` לכתיבת JSON. התייחס ל-`401` כאל אימות חסר או לא חוקי, `403` כהזהות תקפה ללא ההרשאה הנדרשת, `404` כמשאב חסר או בלתי נגיש בארגון, `409` כסכסוך מצב, ו-`422` כערך שדה או הרשאה לא חוקי. תגובות שגיאה כוללות הודעה קריאה לאדם; כשלים בהרשאה גם שמות את ההענקה הנדרשת.

ספיגת אירועים משתמשת ב-JSON מתוחם בשורות חדשות: אובייקט שלם אחד לכל שורה. בדוק גם `accepted` וגם `skipped` בתגובה מוצלחת. נסה שוב את כל הקבוצה לאחר כשל ברשת או תגובת HTTP 408, 429, או 5xx; השמעה מחדש של אותם אירועים בטוחה. קבוצות היסטוריות יכולות להימשך חודשים רבים. אם ספיגה תחזיר `422` עם `error: "event_too_large"`, הקטן את המטען של האירוע הפוגע לפני ניסיון חוזר.
חלוקת קבוצה לבקשות קטנות יותר אינה משחזת אירוע בודד.
לייבוא קבצים, השתמש שוב בגבול `existing_before` המקורי בניסיונות חוזרים כך שניתן יהיה לסיים סשן שנשמר חלקית.

## מזהי בקשה

כל תגובה נושאת כותרת `X-Request-Id`, וכל גוף שגיאת JSON כולל את אותו ערך כ-`request_id`. ציטט אותו כשאתה יוצר קשר עם התמיכה: הוא מזהה את הבקשה הזו.

אתה יכול לשלוח את `X-Request-Id` שלך כדי לתאם בקשה עם רישומים שלך. השתמש ב-32 תווי הקסדצימלי קטנים, כגון UUID v4 עם המקפים הוסרו. כל ערך אחר מוחלף ב-ID חדש, המוחזר בתגובה.

<Warning>
  פריסת אכיפת מדיניות מנוהלת בכוונה מחוץ לפני `/v1` הציבורי הרגיל. השתמש בזרימת עבודת הפריסה בענן הנתמכת.
</Warning>
