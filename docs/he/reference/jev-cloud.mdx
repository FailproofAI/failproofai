זהו הייחוס של מסלול Cloud עבור [מדיניות Jev](/he/policies/jev). Jev, המסווג של TypeSafe, קורא כל קריאת כלי מול מה שבאמת ביקשת וענה לצד המדיניות שלך, לעולם לא במקומן. דרך **FailproofAI Cloud**, מכונה מחוברת משתמשת ב-Jev עם אותו מפתח שכבר מתחברת איתו: ללא חשבון TypeSafe, ללא מפתח שני, ללא endpoint להגדרה. כל קריאה תשולמת לגביל התכנית הקיים של הארגון שלך.

כל מה שـ Jev עושה לא משתנה מ[ההגדרה של הבאת המפתח שלך](/he/reference/jev-providers): המדיניות הקשה נשארת סופית, ההכחשה של מדיניות שניתן לבדוק מתומחקת רק כאשר Jev נשאל בדיוק על אותו חשש, וכל כשל חוזר לתוצאת regex עבור אותה קריאה.

<Note>
דורש **failproofai 1.0.8-beta.0** או מאוחר יותר. ל-1.0.7 אין Jev, אפילו שזה מסתדר מעל בטא 1.0.7. ללא תצורת Jev, שום דבר לא משתנה: hooks מריצים את מדיניות regex בדיוק כפי שהם תמיד עשו.
</Note>

## לפני שתתחיל

התקן את Failproof AI על המכונה שבה האגנט שלך רץ וחבר את ה-hooks שלו ל[harness תומך](/he/reference/harnesses). אם אתה מתחיל מאפס, עקוב אחרי [ההתחלה המהירה](/he/start/quickstart) דרך התקנת hook. בדוק את CLI המותקן עם `failproofai --version`; עדכן אותו אם הוא קדום מ-Jev. אתה גם צריך גישה לדף **Administration → Keys** של הארגון שלך ליצירת מפתח מכונה.

Jev בודק קריאות כלים בשם בשער `PreToolUse` או `PermissionRequest`. הוא לא בודק כל אירוע בסשן. כדי לראות Jev למחוק הכחשת מדיניות, אתה זקוק למדיניות מותקנת המסומנת [בדיקה](/he/policies/authority); כל שאר הכחשות המדיניות נשארות סופיות.

## הפעל את זה

1. **צור מפתח עם Jev.** בלוח הבקרה של FailproofAI Cloud, פתח **Administration → Keys → Create key** ובחר בתצוגה המקדימה של **machine**. זה מעניק את שלוש ההרשאות שמכונה צריכה: `events:add` (שלח פעילות), `policies:pull` (קבל מדיניות) ו-`jev:evaluate` (Jev, תשולם לתכנית של הארגון שלך). מפתח לא יכול לשאת `jev:evaluate` ללא שני האחרים.
2. **חבר את המכונה** עם אותו מפתח. קרא את הסוד החד-פעמי שלו בהנחיה, ואז הרץ את פקודת ההגדרה המלאה:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` מתקין את ה-daemon, מחבר hooks עבור CLI ה-agent שהוא מוצא, ומחבר את המכונה. משתנה הסביבה משמר את המפתח מחוץ לטיעוני הפקודה וממיקומך. אם ה-harness שלך הותקן מאוחר יותר, [חבר אותו בעלי כוח](/he/start/quickstart).

   אם הארגון שלך מריץ את FailproofAI Cloud שלו בעצמו ולא את זה המארח, הוסף את הכתובת: `--url https://<your dashboard host>` (או ייצא `FAILPROOFAI_CLOUD_URL`). ללא זה, המפתח מאומת כנגד השירות המארח והחיבור נכשל. אם התעודה של אותו מארח באה מ-CA פרטי, התקן את ה-CA באחסון אמון המערכת של המכונה (לדוגמה עם `update-ca-certificates`), לא רק ב-`NODE_EXTRA_CA_CERTS`: ה-daemon ששולח אירועים ומשך מדיניות קורא את חנות המערכת. ראה [פתרון בעיות](/he/reference/troubleshooting).

זה הכל. חיבור אחסן את המפתח וכאשר למכונה **אין** תצורת Jev עדיין, כותב אחד עבור FailproofAI Cloud. מהפריסה הראשונה של המכונה (תוך כ-30 שניות), FailproofAI Cloud קובע את המצב: `enforce` בזמן פריסת מדיניות Jev אליה, `off` כאשר לא (ראה [מי קובע את המצב](#who-sets-the-mode)). הפלט אומר כך:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

בדיקות ש-FailproofAI Cloud מפרסמת רצות בענן. כדי להוסיף בדיקות משלך על המכונה, התקן חבילה:

```bash
failproofai policies add FailproofAI/jev-policies
```

**עם `--no-transcripts`, חיבור לא הופך את Jev על.** Jev שולח כל קריאת כלי שבדוקה וההנמקה האחרונה ל-FailproofAI Cloud, שזה יותר מכל מה שחיבור בהחלטות בלבד הוזמן לשלוח. המפתח עדיין מאוחסן, והפלט אומר Jev זמין וכיצד להפעיל אותו:

```bash
failproofai jev setup --provider failproofai
```

זה גם הופך Jev דרך FailproofAI Cloud **off**. `jev.json` שמריץ Jev דרך FailproofAI Cloud (שנוצר בחיבור קודם עם תמלול על) מוסר, לפי אותו כלל `config --disconnect` משתמש, והפלט אומר Jev דרך FailproofAI Cloud נשאר כבוי על המכונה הזו. `jev.json` עבור ה-endpoint שלך שלך מושאר כפי שהוא, וכן אחד של FailproofAI Cloud שהיצאת כבוי (`--mode off`).

<Warning>
חיבור **לעולם לא משנה** `~/.failproofai/jev.json` קיים. אם אתה כבר משתמש ב-Jev endpoint משלך, הוא ממשיך לשמש, והפלט אומר הקובץ הושאר כמכונה — ו, כאשר אותו קובץ משאיר Jev כבוי (סירוב, או הופעל כבוי), אומר כך וכיצד לתקן זאת. כדי להחליף את המכונה הזו ל-FailproofAI Cloud, הרץ `failproofai jev setup --provider failproofai`.
</Warning>

## מי קובע את המצב

על מכונה מחוברת ל-FailproofAI Cloud, **FailproofAI Cloud קובע את מצב Jev**; שום דבר על המכונה לא:

- `enforce` בזמן שכל מדיניות Jev (או regex + Jev) מפורסמת למכונה: כל קריאת כלי שבדוקה מאגנט שאחד מאותן מדיניות מכוונות אליו הולכת ל-FailproofAI Cloud, שאוגד את הבדיקות שלה עם בדיקות החבילות המותקנות שם. קריאה מאגנט שלא Cloud Jev policy מכוונת אליו, ללא בדיקת pack משלה, לא נשלח בכלל. ב-`enforce`, בדיקות ההכחשה של Jev עצמן חוסמות קריאות כמו גם ניקוי ההחלטות regex שהם משוקללים.
- `off` כאשר לא: אין Jev בכלל, כמו שגם `jev.json` אומר.

כדי לנסות מדיניות Jev לפני שהיא פועלת, פרסם אותה עם השפעה **observe**: הבדיקות שלה עדיין שואלות, ומה הן היו עושות מתועדות כ-**would-have** בדף המדיניות, אבל זה לעולם לא חוסם קריאה ולעולם לא ממחק אחד. `failproofai jev setup --mode` ודשבורד **Settings → Jev** אומרים המצב מנוהל על ידי FailproofAI Cloud ואינו משנה דבר. `jev.json` לא משמש לבדיקות של Cloud, גם אם הוא מציין ספק אחר. `failproofai config --disconnect` מחזיר את Jev לקובץ `jev.json` של המכונה שלה.

`failproofai jev status` אז אומר `Jev checks run on FailproofAI Cloud (mode: enforce)`. זה גם שם את הבדיקות שבודקות כל מדיניות `both`. דף הצי מראה למה מכונה עם מצב לא יכולה לשאול:

- `transcripts_disabled`: המכונה הורחקה עם `--no-transcripts`, שלעולם לא הופך Jev על.
- `jev_unconfigured`: המפתח של המכונה לא נושא `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud סירב כמה מקריאות המכונה עבור גבול קצב Jev של הארגון, וקריאות אלה הוחלטו על ידי מדיניות regex בלבד.
- `jev_unavailable`: מספר קריאות ברציפות נכשלו, כך שהמכונה דולגת על Jev של FailproofAI Cloud לדקה בכל פעם. זה מנסה שוב בעצמו.

אם FailproofAI Cloud לא עונה תוך 5 שניות, מדיניות regex מחליטות לבדן, כמו עבור כל הפסקת Jev. לאחר 3 כשלים ברציפות, המכונה מפסיקה לשאול לדקה בכל פעם, כך שהפסקת Cloud לא מאטה כל קריאת כלי.

השהיית סשן (`failproofai config --pause`) לא עוצרת את בדיקות Jev של FailproofAI Cloud, בדיוק כפי שהיא לא עוצרת מדיניות מנוהלות בענן. זה כן משהה את בדיקות Jev של חבילות מותקנות על המכונה.

## בדוק מה זה עושה

```bash
failproofai jev status
failproofai jev test
```

`status` מראה את הספק כ-**FailproofAI Cloud**, את מארח Cloud שהמכונה התחברה אליו, את המצב, ותמקור המפתח כ-**FailproofAI Cloud connection**, לעולם לא את המפתח. כאשר `jev.json` של FailproofAI Cloud קיים אבל Jev לא יכול להריץ, זה אומר למה:

| `status` אומר | `status --json` | משמעות |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | המכונה מחוברת, אבל אין מפתח Jev מאוחסן עבורה: המפתח חסר `jev:evaluate`, או החיבור לא יכול היה לאשר זאת. הרץ `failproofai config` שוב עם המפתח ב-`FAILPROOFAI_CLOUD_TOKEN`; אם הוא חסר בהרשאה, השתמש ב-**machine** key. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | אין חיבור FailproofAI Cloud על המכונה הזו עבור מפתח Jev שייך אליו. |

לאחר `failproofai config --disconnect` אין `jev.json` של FailproofAI Cloud יותר (אלא אם הוא הופעל כבוי, שמוחזק), כך ש-`status` פשוט מדווח על Jev כבוי. `status --json` נושא את אותם עובדות (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), גם כאשר התצורה היא נעדרת או סירוב. `permissions` הוא תמיד של `jev.json`; סירוב על `credentials.json` מוסיף `credentialsPermissions`, ו-`fix` כאשר פקודה אחת מתקנת זאת. `test` שולח בקשה חיה אחת ודיווחים על הקביעות שלה וגרסת Jev שענתה. זה יוצא 1, ואומר כך בכותרת שלו, כאשר התשובה מגיעה לאחר timeout hook (hooks היה רשום `timeout`) או עונה לשאלת הבדיקה שלו בצורה שגויה.

לוח הבקרה של **Settings → Jev** גם מראה את **FailproofAI Cloud connection**: איזה ארגון המכונה דיווחת אליו וממפתח שלה נושא Jev. זה נקרא מקבצי המכונה שלה, ללא קריאה לרשת.

## אמת קריאה אמיתית

התחל סשן חדש באגנט מחובר. בקש ממנו להשתמש בכלי הקריאה של הקובץ שלו ב-`README.md` והדווח על הכותרת. אשר שהסשן מכיל את קריאת הכלי הזו, ואז הרץ `failproofai jev status` שוב: ספר קריאת ההערכה האחרונה שלה צריך לעלות. פתח **Policies → Activity** ב-[לוח הבקרה המקומי](/he/reference/local-dashboard#review-policy-activity) כדי לבדוק את פסק הדין של Jev של אותה קריאה ומצב. בענן, דף **Policies** של הארגון מראה תוצאות Jev עבור פעילות משודרת. במצב observe, פסק הדין מתועד כ-**would-have** וכתוצאת המדיניות עדיין מחליטה על הקריאה. פנייה מופיעה רק כאשר מדיניות שניתן לבדוק תאמה ו-Jev פינה את הבדיקות בשם שלה.

## מה הגיע לדף המדיניות

המכונה כבר שולחת את פעילות ה-hook שלה ל-FailproofAI Cloud (`events:add`). עם Jev על, גם רשומת של קריאה בשער אומרת איזה מעריך רץ, מה Jev החליט, אילו מדיניות זה פינה, למה זה חזר לאחור כאשר הוא עשה, הקביעה שלו והדגם שענה — החלטות, קודים ושמות, לעולם לא את הפקודה או את ההנמקה שלך. בדף **Policies** של הארגון שלך:

- קריאה שפסק הדין שלה של Jev החליט (מצב enforce) יוחסת ל-**Jev**, וכאשר בדיקת ההחלטה באה מחבילה, הרשומה גם שם את החבילה הזו וגרסתה;
- במצב observe, Jev's deny or warning מופיע כ-**would-have**, לצד rollouts שאתה מצפה;
- מדיניות שJev פינה, או היו פינה במצב observe, נספרות לכל מדיניות.
- החלטה שJev השתתף בה (בלוק, אזהרה, ניקוי, או would-have במצב observe) רשומה כל בדיקה שהיא שאלה ומה בדיקה זו סיכמה: פסק דין, למה (`not-detected`, `exempt`, `fired`, `op-requested`, …), הראיה שלה `p`, התשובה `exempt` וכל תשובת בדיקה. בדיקה של מדיניות פרוסה להשגחה (observe) רשומה גם, מסומנת בשמירה; זה לעולם לא חוסם. Jev עונה עם הסתברויות, לא פרוז'ה, כך שאין סיבה בטקסט חופשי. allowances פשוטות מתגלגלות לספירות ואינן נושאות את הרשימה הזו.

## כאשר Jev לא יכול לענות

כל אחד מאלה חוזר לתוצאה של המדיניות שלך עבור אותה קריאה, ורשום עם סיבתו:

| סיבה | גורם |
| --- | --- |
| `out-of-credits` | הארגון שלך השתמש בגביל התכנית שלו. |
| `http-401`, `http-403` | המפתח בוטל, או לא נושא `jev:evaluate`. התחבר שוב עם מפתח שעושה זאת. |
| `http-429` | FailproofAI Cloud מהווה קצב Jev עבור הארגון שלך. עד שהפסק שהוא מבקש הוא בחוץ (שלו `Retry-After`, לכל היותר 60 שניות), המכונה שולחת לה כלום וכל קריאה חוזרת לאחור כשנתיים. קריאות שנעצרו כך מתועדות כ-`http-429`, או כ-`rate-limited` כאשר גבול הקצב של המכונה משלה משהה אותן תחילה. |
| `http-429` (מגבלה יומית) | הארגון שלך השתמש בקריאות Jev היומיות שלו: **10,000 ליום UTC**, אלא אם מי שמפעיל את FailproofAI Cloud שלך קבע גבול אחר. כל קריאה חוזרת לאחור עד שהספירה מאומתת ב-00:00 UTC; המכונה עדיין שואלת שוב לכל היותר פעם בדקה, כך שהיא חוטפת את ההגדרה מחדש תוך דקה. `failproofai jev test` אומר "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev סירב לבקשה של הקריאה הזו, בדרך כלל כי קריאת הכלי החזיקה בטקסט צפוף (base64, hex, קוד מינימייזציה) מעבר לתקציב הטוקן של Jev. קריאה זו חוזרת לאחור בכל פעם; זה לא הפסקה. |
| `http-502` | Jev לא זמין כרגע. |
| `http-503` | Cloud זה לא יכול להציע Jev עבור הארגון שלך: אין שער מודל, ארגון שלא מוזן עדיין, או השער כבוי. שאל את הנהלך; hooks שואל שוב לכל היותר פעם בדקה. |
| `http-404` | FailproofAI Cloud זה עדיין לא משרת Jev. |
| `timeout` | אין תשובה תוך `timeoutMs` (ברירת מחדל 3000). בזמן ש-FailproofAI Cloud קובע את מצב Jev של המכונה, ההמתנה היא 5000 ms ו-`jev.json`'s `timeoutMs` לא משמש. |
| `model-mismatch` | גרסת Jev שונה מ-1.13 ענתה. |

## איפה המפתח חי, ולאן הוא הולך

- המפתח מאוחסן פעם אחת, ב-`~/.failproofai/credentials.json` (`0600`, בספריית קנייה בלבד), לצד הרישומים האחרים של FailproofAI Cloud. `jev.json` לא מחזיק מפתח לנתיב זה; אחד שנכתב שם עושה את התצורה לא תקינה.
- אם `credentials.json` נושא **כל** הרשאה עבור מישהו אחר מלבדך (קבוצה או אחר, קריאה או כתיבה), או הספריה שלה יכולה להיות **כתובה** על ידי מישהו אחר מלבדך, זה **סורב**, לא קרא, וJev כבוי עד שתתקן זאת: `chmod 600` בקובץ, `chmod 700` בספריה (או התחבר שוב, שכותב את הקובץ ב-`0600` ועושה את הספריה בעלות בלבד). ספריה אחרים יכולים רק לקרוא בסדר; אחד שהם יכולים כתוב תן להם להחליף את הקובץ.
- המפתח נספר רק בזמן שהחיבור שהגיע ממנו נמצא על המכונה: מדיניות או הרשעיים דיווח עבור אותו FailproofAI Cloud **עם אותו מפתח**, באותו קובץ. מפתח Jev שנשאר מאחור ללא אחד מתעלם, וJev נשאר כבוי. זה קורה כאשר failproofai ישנה של `config --disconnect` משאיר את מפתח Jev במקום (הוא לא יודע להסיר אותו), או כאשר failproofai ישנה של `config --token` מתחבר עם מפתח אחר, שעל FailproofAI Cloud עשוי להשתייך לארגון אחר. כדי להפוך את Jev בחזרה על, התחבר שוב עם **machine** key.
- המפתח נשלח רק אי פעם למקור ענן שבו אומת לעומתו. `jev.json` מצביע בכל מקום אחר סורב.
- **סוכן על המכונה יכול לקרוא אותו.** `credentials.json` הוא בעלות בלבד, והסוכן רץ כבעל זה. קריאת קבצים משלה של failproofai מותרת במטרה (רק שינוי אותם חוסם, על ידי `block-failproofai-commands`), כך שהדבר היחיד בין סוכן לקובץ זה הוא `block-read-outside-cwd` — מדיניות **reviewable** — וממושב התחיל בספרייה הביתית שלך, כלום. מפתח עם `jev:evaluate` משקיע בגביל Jev של הארגון שלך (עד למכסה יומית) מכל מקום שהוא משמש, אז התייחס למפתח מכונה כמו כל הרשעיים הוצאות אחרות: אם סוכן יכול היה לקרוא אותו, השבת אותו בדף Keys ולחברת שוב עם אחד חדש.
- רק הקבצים הגלובליים שלך מחליטים זאת. הפקדון לא יכול להפוך Cloud Jev על, להצביע אליו במקום אחר או לספק את המפתח שלו, ו-`FAILPROOFAI_JEV_API_KEY` מתעלם נתיב זה.
- עבור כל קריאה Jev מעריך, בקשה אחת הולכת ל-FailproofAI Cloud, נושא מה [דף bring-your-own-key](/he/reference/jev-providers#what-leaves-the-machine) רשימות (סודות redacted). FailproofAI Cloud משדרת אותה ל-TypeSafe ואינה רושמת או שומרת אותה.

## כבה את זה

על מכונה מחוברת, Jev כבוי כאשר FailproofAI Cloud משדרת אל בעיה מדיניות Jev: הסר או ארכיון את מדיניות Jev שם.

| פקודה | התוצאה |
| --- | --- |
| הסר את מדיניות Jev של המכונה בـ FailproofAI Cloud | מצב Cloud הופך `off` בדיקה הבאה (כ-30 שניות): לא Jev בכלל, כמו שגם `jev.json` אומר. |
| `failproofai config --disconnect` | נתק את המכונה: המפתח מוסר, וכך גם `jev.json` כאשר זה שם FailproofAI Cloud ואינו הופעל כבוי. `jev.json` עבור ה-endpoint שלך שלך נשאר. |

מהקריאה הבאה בכלי, hooks מריץ את מדיניות regex בדיוק כמו קודם.
