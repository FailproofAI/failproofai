זה ההתייחסות לנתיב Cloud עבור [מדיניות Jev](/he/policies/jev). Jev, המסווג של TypeSafe, קורא כל קריאת כלי מול מה שבעצם ביקשת וממציא תשובות לצד המדיניות שלך, לעולם לא במקום שלהן. דרך **FailproofAI Cloud**, מכונה מחוברת משתמשת ב-Jev עם אותו מפתח שהוא כבר מתחבר איתו: אין חשבון TypeSafe, אין מפתח שני, אין endpoint להגדרה. כל קריאה מחויבת להקצבת התוכנית הקיימת של הארגון שלך.

כל מה ש-Jev עושה לא משתנה מה[הגדרת bring-your-own-key](/he/reference/jev-providers): מדיניות קשות נשארות סופיות, הדחייה של מדיניות בחינה מתבררת רק כאשר Jev נשאל בדיוק על אותו חשש, וכל כשל חוזר לתוצאת ה-regex של הקריאה ההיא.

<Note>
דורש **failproofai 1.0.8-beta.0** או מאוחר יותר. ל-1.0.7 אין Jev, אפילו כשהוא מעל 1.0.7 betas. ללא הגדרת Jev לא קורה שום דבר: hooks מריצים את מדיניות ה-regex בדיוק כפי שהם עושים תמיד.
</Note>

## לפני שאתה מתחיל

התקן את Failproof AI על המכונה שבה ה-agent שלך פועל וחבר את ה-hooks שלו ל[harness נתמך](/he/reference/harnesses). אם אתה מתחיל מאפס, עקוב אחר ה[quickstart](/he/start/quickstart) דרך התקנת hook. בדוק את ה-CLI המותקן עם `failproofai --version`; עדכן אותו אם הוא קדום ל-Jev. אתה צריך גם גישה לעמוד **Administration → Keys** של הארגון שלך כדי ליצור מפתח מכונה.

Jev בוחן קריאות כלים בשם בשער `PreToolUse` או `PermissionRequest`. הוא לא בוחן כל אירוע בהפעלה. כדי לראות את Jev מנקה את הדחייה של מדיניות, אתה צריך מדיניות מותקנת המסומנת [בחינה](/he/policies/authority); כל שאר הדחיות של מדיניות נשארות סופיות.

## הפוך אותו להיות פעיל

1. **צור מפתח עם Jev.** בדashboard של FailproofAI Cloud, פתח **Administration → Keys → Create key** ובחר את preset **machine**. זה מעניק את שלוש ההרשאות שמכונה צריכה: `events:add` (שלח פעילות), `policies:pull` (קבל מדיניות) ו-`jev:evaluate` (Jev, בחיוב לתוכנית הארגון שלך). מפתח לא יכול לשאת `jev:evaluate` ללא שתי האחרות.
2. **חבר את המכונה** עם המפתח הזה. קרא את הסוד החד-פעמי שלו בהנחיה, ואז הרץ את פקודת ההגדרה המלאה:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` מתקין את ה-daemon, מחבר hooks עבור ה-CLIs של ה-agent שהוא מוצא, ומחבר את המכונה. משתנה הסביבה שומר את המפתח הרחק מהארגומנטים של הפקודה ותיוג הקליפה שלך. אם ה-harness שלך הותקן מאוחר יותר, [חבר אותו בעמידה](/he/start/quickstart).

   אם הארגון שלך מריץ את שלו FailproofAI Cloud במקום את זה המרוח, הוסף את הכתובת שלו: `--url https://<your dashboard host>` (או יצא `FAILPROOFAI_CLOUD_URL`). בלי זה המפתח מעודכן כנגד השירות המרוח והחיבור נכשל. אם התעודה של host זה מגיעה מ-CA פרטי, התקן את ה-CA בחנות האמון של המערכת של המכונה (לדוגמה עם `update-ca-certificates`), לא רק ב-`NODE_EXTRA_CA_CERTS`: ה-daemon ששולח אירועים ומשך מדיניות קורא את החנות של המערכת. ראה [Troubleshooting](/he/reference/troubleshooting).

זה הכל. חיבור שומר את המפתח וכאשר למכונה אין **ללא** הגדרת Jev עדיין, כותב אחד עבור FailproofAI Cloud. מההפעלה הראשונה של המכונה (בתוך כ-30 שניות) FailproofAI Cloud מגדיר את הצורה: `enforce` בזמן שמדיניות Jev מפורסמת אליה, `off` כאשר לא (ראה [Who sets the mode](#who-sets-the-mode)). הפלט אומר כך:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

בדיקות FailproofAI Cloud מפעילות על Cloud. כדי להוסיף בדיקות משלך במכונה, התקן חבילה:

```bash
failproofai policies add FailproofAI/jev-policies
```

**עם `--no-transcripts`, חיבור לא הופך Jev להיות פעיל.** Jev שולח כל קריאת כלי מעודכנת והנושא האחרון ל-FailproofAI Cloud, שזה יותר מ-decisions-only שנשאל לשלוח. המפתח עדיין מאוחסן, והפלט אומר Jev זמין וכיצד להפעיל אותו:

```bash
failproofai jev setup --provider failproofai
```

זה גם הופך Jev דרך FailproofAI Cloud **off**. `jev.json` שמריץ Jev דרך FailproofAI Cloud (השאור בחיבור קודם עם transcripts פעיל) הוא הוסר, על ידי אותו כלל `config --disconnect` משתמש, והפלט אומר Jev דרך FailproofAI Cloud נשאר off במכונה זו. `jev.json` עבור endpoint Jev שלך משאור כפי שהוא, וכן גם אחד FailproofAI Cloud שהושבת off (`--mode off`).

<Warning>
חיבור **לעולם לא מחליף** `~/.failproofai/jev.json` קיים. אם אתה כבר משתמש ב-endpoint Jev משלך, זה נשמר להיות משמש, והפלט אומר הקובץ היה משאור כמו מוגדר — וכאשר הקובץ ההוא משאור Jev off (נדחה, או הושבת off), אומר כך וכיצד לתקן זאת. כדי להחליף את המכונה הזו ל-FailproofAI Cloud, הרץ `failproofai jev setup --provider failproofai`.
</Warning>

## מי קובע את הצורה

על מכונה המחוברת ל-FailproofAI Cloud, **FailproofAI Cloud קובע את צורת Jev**; שום דבר במכונה לא:

- `enforce` בזמן שמדיניות Jev (או regex + Jev) כלשהיא פורסמת למכונה: כל קריאת כלי מעודכנת מ-agent שאחת מהמדיניויות ההיא מכוונת אליה עוברת ל-FailproofAI Cloud, אשר שואל את הבדיקות שלה יחד עם בדיקות החבילות המותקנות שם. קריאה מ-agent שאין Cloud Jev מדיניות מכוונת אליה, עם אין בדיקה מהחבילה משלה, לא נשלחת בכלל. ב-`enforce`, בדיקות הדחייה של Jev עצמו חוסמות קריאות וגם מנקות את הפסקי ה-regex שהם בוחנים.
- `off` כאשר אין: אין Jev בכלל, מה שנ-`jev.json` אומר.

כדי לנסות מדיניות Jev לפני שהיא פועלת, פרסם אותה עם השפעה **observe**: הבדיקות שלה עדיין נשאלות, ומה שהם היו עושים מתועדות כ-**would-have** בעמוד המדיניות, אך לעולם לא חוסמת קריאה ולעולם לא מנקה אחד. `failproofai jev setup --mode` ודashboard של **Settings → Jev** אומרים הצורה מנוהלת על ידי FailproofAI Cloud ולא משנים דבר. `jev.json` לא משמש עבור בדיקות Cloud, אפילו אם זה שם ספק אחר. `failproofai config --disconnect` מחזיר Jev ל-`jev.json` של המכונה.

`failproofai jev status` אומר אז `Jev checks run on FailproofAI Cloud (mode: enforce)`. זה גם שמות את הבדיקות שבוחנות כל מדיניות `both`. עמוד הצי מראה למה מכונה עם צורה לא יכול לשאול:

- `transcripts_disabled`: המכונה הוחברה עם `--no-transcripts`, אשר לעולם לא הופכת Jev להיות פעיל.
- `jev_unconfigured`: המפתח של המכונה לא נושא `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud סירבה בכמה מהקריאות של המכונה ל-Jev rate limit של הארגון, וקריאות אלה הוחלטו על ידי מדיניות ה-regex בלבד.
- `jev_unavailable`: כמה קריאות ברציפות נכשלו, כך שהמכונה דלג Jev של FailproofAI Cloud בכל פעם דקה אחת. זה מחדש בעצמו.

אם FailproofAI Cloud לא מענה בתוך 5 שניות, מדיניות ה-regex מחליטה בלבדה, כמו לכל outage Jev. לאחר 3 כשלים ברציפות המכונה מפסיקה לשאול בכל פעם דקה אחת, כך שoutage Cloud לא מאט כל קריאת כלי.

הפסקת הפעלה (`failproofai config --pause`) לא עוצרת בדיקות Jev של FailproofAI Cloud, בדיוק כמו שהיא לא עוצרת מדיניות מנוהלות Cloud. זה כן מעצור את בדיקות Jev של חבילות המותקנות במכונה.

## בדוק מה זה עושה

```bash
failproofai jev status
failproofai jev test
```

`status` מראה את הספק כ-**FailproofAI Cloud**, Cloud host המכונה חיברה אליו, הצורה, ומקור המפתח כ-**FailproofAI Cloud connection**, לעולם לא המפתח. כאשר `jev.json` של FailproofAI Cloud נמצא בעמידה אך Jev לא יכול להריץ, זה אומר למה:

| `status` אומר | `status --json` | משמעות |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | המכונה מחוברת, אך אין Jev key מאוחסן עבורה: המפתח חסר `jev:evaluate`, או חיבור לא יכול היה לאשר אותו. הרץ `failproofai config` שוב עם המפתח ב-`FAILPROOFAI_CLOUD_TOKEN`; אם זה חסר ההרשאה, השתמש ב-**machine** key. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | אין FailproofAI Cloud connection במכונה זו ל-Jev key להשתייך אליה. |

אחרי `failproofai config --disconnect` אין FailproofAI Cloud `jev.json` עוד (אלא אם הוחסם off, שהוא נשמר), כך ש`status` פשוט מדווח Jev off. `status --json` נושא את אותם עובדות (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), גם כשהקונפיג חסר או נדחה. `permissions` היא תמיד שלה של `jev.json`; סירוב על `credentials.json` מוסיף `credentialsPermissions`, ו-`fix` כאשר פקודה אחת מתקנת זאת. `test` שולח בקשה חיה אחת ומדווח את החזקת שלה ו-Jev version שענה. זה יוצא 1, ואומר כך בכותרת שלו, כאשר התשובה מגיעה אחרי hook timeout (hooks היה מתעדים `timeout`) או עונה על שאלת בדיקה שלו בצורה לא נכונה.

דashboard של **Settings → Jev** מראה גם את **FailproofAI Cloud connection**: איזה ארגון המכונה מדווחת אליו ואם המפתח שלו נושא Jev. זה קורא מהקבצים שלך שלך, ללא קריאה רשת.

## אמת קריאה אמיתית

התחל הפעלה חדשה ב-agent מחובר. בקש ממנו להשתמש בכלי קריאה הקבצים שלו על `README.md` ודווח את הכותרת. אשר שההפעלה מכילה את הקריאה הזו של כלי, ואז הרץ `failproofai jev status` שוב: הספירה הערוכה-שלה-recent-evaluated-call צריכה להיות גבוהה יותר. פתח **Policies → Activity** ב-[local dashboard](/he/reference/local-dashboard#review-policy-activity) כדי לתבחן את Jev verdict של קריאה זו וצורה. בCloud, הארגון של הארגון **Policies** עמוד מראה Jev תוצאות עבור פעילות מועברת. בצורת observe, פסק הדין מתועד כ-**would-have** והתוצאה של המדיניות עדיין החליט בקריאה. ניקיון מופיע רק כאשר מדיניות בחינה עשר והופעלה והצה מנקה את הבדיקות שלה בשם.

## מה מגיע לעמוד המדיניות

המכונה שלך כבר שולחת את פעילות ה-hook שלה ל-FailproofAI Cloud (`events:add`). עם Jev בעמידה, תיעוד של קריאה gated כל גם אומר איזה evaluator רץ, מה Jev החליט, אילו מדיניויות זה מנוקה, למה זה נפל בחזרה כאשר עשה, החזקה שלו וה-model שענה — החלטות, קודים ושמות, לעולם לא הפקודה או הנושא שלך. בעמוד **Policies** של הארגון שלך:

- קריאה פסק הדין Jev זה של Jev החליט (צורת enforce) יוחס **Jev**, וכאשר בדיקה החליטה בא מחבילה, תיעוד גם שמות את החבילה והגרסה שלה;
- בצורת observe, הדחייה או אזהרה של Jev מופיעה כ-**would-have**, לצד ה-rollouts שאתה צופה;
- מדיניויות ה-Jev מנוקה, או היו מנוקה בצורת observe, סופרות לכל מדיניות.
- החלטה Jev לקח חלק בו (בלוק, אזהרה, ניקיון, או would-have בצורת observe) רשימות כל בדיקה זה שאל ומה בדיקה זו מסקנה: פסק דין, למה (`not-detected`, `exempt`, `fired`, `op-requested`, …), הוכחה שלה `p`, התשובה `exempt` וכל תשובת בדיקה. בדיקה של מדיניות פרוסה לצפות (צפייה) רשומה גם, מסומנת צפויה; לעולם לא חוסמת. Jev מענה בהסתברות, לא בפרוזה, כך שאין סיבה טקסט חופשי. מאפשרים רגיל רול מעלה לספירות ואל תשא רשימה זו.

## כאשר Jev לא יכול לענות

כל אחד מהם חוזר למדיניות התוצאה שלך עבור הקריאה הזו, ומתועדות עם הסיבה שלו:

| סיבה | קורה |
| --- | --- |
| `out-of-credits` | הארגון שלך השתמש בהקצבת התוכנית שלו. |
| `http-401`, `http-403` | המפתח עוקל או לא נושא `jev:evaluate`. התחבר שוב עם מפתח שעושה. |
| `http-429` | FailproofAI Cloud היא rate-limiting Jev עבור הארגון שלך. עד שההמתנה זה שואל עבור עבר (שלו `Retry-After`, לכל היותר 60 שניות), המכונה שולחת אותו כלום וכל קריאה חוזרת ישר הרחק. קריאות החזקות בדרך זו מתועדות כ-`http-429`, או כ-`rate-limited` כאשר rate limit של המכונה מחזיק אותם ראשון. |
| `http-429` (יומי limit) | הארגון שלך השתמש בקריאות Jev יומיות שלו: **10,000 per UTC day**, אלא אם מה שמפעיל את FailproofAI Cloud שלך קבע גבול אחר. כל קריאה חוזרת עד שהספירה אפס ב-00:00 UTC; המכונה עדיין שואל שוב לכל היותר פעם בדקה, כך שזה בוחר את האפס עד בתוך דקה. `failproofai jev test` אומר Daily Jev limit for this org reached; resets at 00:00 UTC. |
| `http-422` | Jev סירבה לבקשה קריאה זו, בדרך כלל כי הקריאה כלי החזיק טקסט צפוף (base64, hex, minified code) על Jev token budget. קריאה זו חוזרת בכל פעם; זה לא outage. |
| `http-502` | Jev אינו זמין כרגע. |
| `http-503` | Cloud זה לא יכול להשרת Jev עבור הארגון שלך: לא model gateway, ארגון לא בהוקדמה עדיין, או gateway בחוסר זמינות. שאל מנהל שלך; hooks שואל שוב לכל היותר פעם בדקה. |
| `http-404` | FailproofAI Cloud לא משרת Jev עדיין. |
| `timeout` | לא תשובה בתוך `timeoutMs` (ברירת מחדל 3000). בזמן FailproofAI Cloud קובע Jev צורת המכונה, ההמתנה היא 5000 ms ו`jev.json`'s `timeoutMs` לא משמש. |
| `model-mismatch` | Jev גרסה אחרת מאשר 1.13 ענה. |

## איפה המפתח חי, ולאן הוא הולך

- המפתח אוחסן פעם אחת, בתוך `~/.failproofai/credentials.json` (`0600`, בספריית בעל-בעל בלבד), לצד ההוראות האחרות של FailproofAI Cloud. `jev.json` מחזיקה אין מפתח ל-route זה; אחד כתוב שם עושה הקונפיג בלתי חוקי.
- אם `credentials.json` נושא **כל** הרשאה עבור כל אחד אבל אתה (קבוצה או אחרת, קרא או כתוב), או הספריה שלה יכול להיות **כתוב** על ידי כל אחד אבל אתה, זה **סירוב**, לא קרא, ו-Jev הוא off עד שאתה מתקן: `chmod 600` על הקובץ, `chmod 700` בספריה (או reconnect, אשר rewrite הקובץ ב-`0600` ועושה את ספריה בעל-בעל בלבד). ספריה אחרים יכול רק קרא בסדר; אחד שהם יכולים כתוב יתן להם להחליף את הקובץ.
- המפתח ספירה רק בזמן חיבור זה בא עם מופעל במכונה: מדיניות או דיווח הוראות עבור אותו FailproofAI Cloud **עם אותו מפתח**, בתוך אותו קובץ. Jev key משאור ללא אחד בחוסר דעת, ו-Jev נשאר off. זה קורה כאשר `config --disconnect` של failproofai קדום משאור Jev key בעמידה (זה לא יודע להסיר אותו), או כאשר `config --token` של failproofai קדום חיבור עם מפתח אחר, שעל FailproofAI Cloud אפילו לא להשתייך לארגון אחר. כדי להחליף Jev חזרה, חיבור שוב עם **machine** key.
- המפתח הוא רק אי פעם שלח Cloud origin זה היה מאומת נגד. `jev.json` פונה בכל מקום אחר סירוב.
- **אג'נט במכונה יכול לקרוא אותו.** `credentials.json` בעל-בעל בלבד, והאג'נט מריץ כ-owner. קריאה של קובצי failproofai שלך משודך מתורגם בכוונה (רק שינוי להם מחסום על ידי `block-failproofai-commands`), אז הדבר היחיד בין אג'נט לקובץ זה היא `block-read-outside-cwd` — מדיניות **בחינה** — וממושב התחלה בספריית הבית שלך, כלום. מפתח עם `jev:evaluate` הוצאות הבדלתך של הארגון Jev הבדלה (עד יומי כובע) מכל מקום זה משמש, אז תייחס מכונה key כמו כל אחר הוצאות הוראות: אם אג'נט אפילו יכול היה לקרוא אותו, לא זה ב-Keys עמוד וconnect שוב עם חדש.
- רק הקבצים הגלובליים שלך להחליט זה. מאגר לא יכול להפעיל Cloud Jev, נקודה זה במקום אחר או לספק מפתח שלו, ו`FAILPROOFAI_JEV_API_KEY` בחוסר דעת ל-route זה.
- כל קריאה Jev מעריך, אחד בקשה הולכת ל-FailproofAI Cloud, נושא מה [bring-your-own-key עמוד](/he/reference/jev-providers#what-leaves-the-machine) רשומות (סודות redacted). FailproofAI Cloud קדימה זה TypeSafe ו-not כתב או שמור אותו.

## הופך אותו להיות off

על מכונה מחוברת, Jev הוא off כאשר FailproofAI Cloud פרסמות לא Jev מדיניות זה: להסיר או לתעד Jev מדיניויות שם.

| פקודה | התוצאה |
| --- | --- |
| להסיר מדיניויות Jev של המכונה בFailproofAI Cloud | צורת Cloud הופך `off` בבדיקה הבאה (כ-30 ש): לא Jev בכלל, מה שנ-`jev.json` אומר. |
| `failproofai config --disconnect` | התנתק מהמכונה: המפתח הוא הוסר, וכך גם `jev.json` כאשר זה שמות FailproofAI Cloud ו-not הושבת off. `jev.json` עבור endpoint שלך נשאור. |

מהקריאה כלי הבאה, hooks מריצים את מדיניות ה-regex בדיוק כמו קודם לכן.
