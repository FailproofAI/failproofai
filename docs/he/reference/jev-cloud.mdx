זהו הפניה לנתיב Cloud עבור [מדיניות Jev](/he/policies/jev). Jev, המסווג של TypeSafe, קורא כל קריאת כלי מול מה שאתה בעצם ביקשת ומשיב לצד המדיניות שלך, לעולם לא במקומן. דרך **FailproofAI Cloud**, מכונה מחוברת משתמשת ב-Jev עם אותו המפתח שכבר משתמשת בו להתחברות: ללא חשבון TypeSafe, ללא מפתח שני, ללא נקודת קצה להגדרה. כל קריאה מחויבת להקצאת התוכנית הקיימת של הארגון שלך.

הכל שהוא עושה Jev נשאר ללא שינוי מ[התקנת הביתוק שלך](/he/reference/jev-providers): מדיניות קשיחה נשארת סופית, המטען של מדיניות סקירה מתבטל רק כאשר שאלו את Jev על בדיוק אותו הדאגה, וכל כשל חוזר למצב ההתאמה לתבנית לאותה קריאה.

<Note>
דורש **failproofai 1.0.8-beta.0** או מאוחר יותר. 1.0.7 אין לו Jev, גם כי הוא מסודר מעל לבטא 1.0.7. ללא הגדרת Jev, שום דבר לא משתנה: hook ריצה במדיניות regex בדיוק כפי שהיו תמיד.
</Note>

## לפני שתתחילו

התקן את Failproof AI על המכונה שבה האג'נט שלך פועל והצמד את hook שלו ל[harness נתמך](/he/reference/harnesses). אם אתה מתחיל מאפס, עקוב אחר ה[quickstart](/he/start/quickstart) דרך התקנת hook. בדוק את CLI המותקן עם `failproofai --version`; עדכן אותו אם הוא קדם ל-Jev. אתה גם צריך גישה לעמוד **Administration → Keys** של הארגון שלך כדי ליצור מפתח מכונה.

Jev בודק קריאות כלי בשם בשער `PreToolUse` או `PermissionRequest`. הוא לא בודק כל אירוע בהפעלה. כדי לראות את Jev ניקוי של מטען מדיניות, אתה צריך מדיניות מותקנת מסומנת [סקירה](/he/policies/authority); כל שאר מטענים של מדיניות נשארים סופיים.

## הפעלה

1. **צור מפתח עם Jev.** בדשבורד FailproofAI Cloud, פתח את **Administration → Keys → Create key** ובחר את הגדרת **machine**. זה מעניק את שלוש ההרשאות שמכונה צריכה: `events:add` (שלח פעילות), `policies:pull` (קבל מדיניות) ו-`jev:evaluate` (Jev, מחויב לתוכנית של הארגון שלך). מפתח לא יכול לשאת `jev:evaluate` ללא השניים האחרים.
2. **חבר את המכונה** עם אותו המפתח. קרא את הסוד החד-פעמי שלו בהנחיה, ואז הרץ את פקודת ההתקנה המלאה:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` מתקין את ה-daemon, מצמיד hook עבור CLI של הסוכן שהוא מוצא, ומחבר את המכונה. משתנה הסביבה שומר את המפתח מחוץ לטיעוני הפקודה וההיסטוריה של קליפת העור שלך. אם ה-harness שלך הותקן מאוחר יותר, [צמידו בצורה מפורשת](/he/start/quickstart).

   אם הארגון שלך מריץ את FailproofAI Cloud שלו בעצמו במקום ה-hosted, הוסף את הכתובת שלו: `--url https://<your dashboard host>` (או ייצוא `FAILPROOFAI_CLOUD_URL`). ללא זה, המפתח מתבדק כנגד השירות המארח וההתחברות נכשלת. אם ה-certificate של אותו מארח מגיע מ-CA פרטי, התקן את CA במאגר הנאמנות של המערכת של המכונה (לדוגמה עם `update-ca-certificates`), לא רק ב-`NODE_EXTRA_CA_CERTS`: ה-daemon ששולח אירועים ומושך מדיניות קורא את חנות המערכת. ראה [Troubleshooting](/he/reference/troubleshooting).

זהו הכל. התחברות שומרת את המפתח וכאשר למכונה **אין** עדיין הגדרת Jev, כותבת אחת עבור FailproofAI Cloud. מההטמעה הראשונה של המכונה (תוך כ-30 שניות) FailproofAI Cloud קובע את המצב: `enforce` בזמן שמדיניות Jev מפוזרת אליה, `off` כאשר אין (ראה [מי קובע את המצב](#who-sets-the-mode)). הפלט אומר כך:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

בדוקים שפועלים FailproofAI Cloud בענן. כדי להוסיף בדוקים שלך בעצמך במכונה, התקן חבילה:

```bash
failproofai policies add FailproofAI/jev-policies
```

**עם `--no-transcripts`, התחברות לא הופכת את Jev.** Jev שולח כל קריאת כלי שנבדקה וההנחיה האחרונה ל-FailproofAI Cloud, שזה יותר מהתחברות שהתבקש רק החלטות לשלוח. המפתח עדיין מאוחסן, והפלט אומר Jev זמין וכיצד להפעיל אותו:

```bash
failproofai jev setup --provider failproofai
```

זה גם הופך את Jev דרך FailproofAI Cloud **off**. `jev.json` שמריץ את Jev דרך FailproofAI Cloud (שנוצר על ידי התחברות קודמת עם טרנסקריפציות פעולות) מוסר, על ידי אותו כלל `config --disconnect` משתמש, והפלט אומר Jev דרך FailproofAI Cloud נשאר כבוי במכונה זו. `jev.json` עבור נקודת הקצה של Jev שלך משאיר אותה כמו שהיא, וכך גם אחת בענן שהשבתה (`--mode off`).

<Warning>
התחברות **לעולם לא דורסת** קיימת `~/.failproofai/jev.json`. אם אתה כבר משתמש בנקודת קצה של Jev שלך, היא ממשיכה לשמש, והפלט אומר שהקובץ הושאר כמו שהוגדר — וכאשר קובץ זה משאיר את Jev כבוי (סירוב, או הושבתה), אומר כך וכיצד לתקן זאת. כדי להחליף את המכונה הזו ל-FailproofAI Cloud, הרץ `failproofai jev setup --provider failproofai`.
</Warning>

## מי קובע את המצב

במכונה המחוברת ל-FailproofAI Cloud, **FailproofAI Cloud קובע את מצב Jev**; שום דבר במכונה לא:

- `enforce` בזמן שמדיניות Jev כלשהו (או regex + Jev) מפוזרת למכונה: כל קריאת כלי שנבדקה מסוכן אחד שאלה מדיניות מטרגט עוברת ל-FailproofAI Cloud, שמבקשת את הבדוקים שלה יחד עם בדוקי החבילות המותקנות שם. קריאה מסוכן שאף מדיניות Cloud Jev לא מטרגטת אותה, ללא בדוק חבילה משלה, אינה נשלחת כלל. ב-`enforce`, בדוקי ההכחשה של Jev עצמו חוסמים קריאות וכן מנקים את גזרי ה-regex שהם בודקים.
- `off` כאשר אין: שום Jev בכלל, מה שגם `jev.json` אומר.

כדי לנסות מדיניות Jev לפני שהיא משפיעה, פרוס אותה עם אפקט **observe**: הבדוקים שלה עדיין מבוקשים, ומה שהיו עושים מתועדים כ-**would-have** בעמוד המדיניות, אך זה לעולם לא חוסם קריאה ולעולם לא מנקה אחת. `failproofai jev setup --mode` ודשבורד **Settings → Jev** אומרים המצב מנוהל על ידי FailproofAI Cloud ואינם משנים כלום. `jev.json` אינו משמש לבדוקי Cloud, גם אם הוא שם ספק אחר. `failproofai config --disconnect` מחזיר את Jev ל-`jev.json` של המכונה שלה.

`failproofai jev status` ואז אומר `Jev checks run on FailproofAI Cloud (mode: enforce)`. זה גם שם את הבדוקים שבודקים כל מדיניות `both`. דף הצי מראה למה מכונה עם מצב לא יכולה לשאול:

- `transcripts_disabled`: המכונה התחברה עם `--no-transcripts`, שלעולם לא הופכת את Jev.
- `jev_unconfigured`: מפתח המכונה אינו נושא `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud סירבה לחלק מקריאות המכונה לגבול קצב Jev של הארגון, וקריאות אלה הוחלטו על ידי מדיניות regex בלבד.
- `jev_unavailable`: מספר קריאות בשורה נכשלו, כך שהמכונה דולגת על Jev של FailproofAI Cloud כل דקה בכל פעם. זה מנסה שוב בעצמו.

אם FailproofAI Cloud לא משיב תוך 5 שניות, מדיניות ה-regex מחליטה לבדה, כמו לכל הפסקה של Jev. לאחר 3 כישלונות בשורה, המכונה מפסיקה לשאול כל דקה בכל פעם, כך שהפסקה בענן לא מאטה כל קריאת כלי.

השהיית הפעלה (`failproofai config --pause`) לא עוצרת בדוקי Jev של FailproofAI Cloud, בדיוק כמו שהיא לא עוצרת מדיניות מנוהלת בענן. זה אכן מעכב בדוקי Jev של חבילות המותקנות במכונה.

## בדוק מה הוא עושה

```bash
failproofai jev status
failproofai jev test
```

`status` מציג את הספק כ-**FailproofAI Cloud**, את מארח ה-Cloud שהמכונה התחברה אליו, את המצב, ואת מקור המפתח כ-**FailproofAI Cloud connection**, לעולם לא המפתח. כאשר `jev.json` של FailproofAI Cloud בעמדה אך Jev לא יכול לרוץ, זה אומר למה:

| `status` אומר | `status --json` | משמעות |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | המכונה מחוברת, אך אף מפתח Jev לא מאוחסן עבורה: המפתח חסר `jev:evaluate`, או ההתחברות לא יכלה לאשר זאת. הרץ `failproofai config` שוב עם המפתח ב-`FAILPROOFAI_CLOUD_TOKEN`; אם הוא חסר ההרשאה, השתמש במפתח **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | אין התחברות FailproofAI Cloud במכונה זו כדי שמפתח Jev יהיה לו. |

לאחר `failproofai config --disconnect` אין יותר `jev.json` של FailproofAI Cloud (אלא אם הוא הושבתה, אשר נשאר), אז `status` פשוט מדווח על Jev כשאנו כבויים. `status --json` נושא אותן עובדות (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), גם כשהקונפיג חסר או סירוב. `permissions` הוא תמיד של `jev.json`; סירוב על `credentials.json` מוסיף `credentialsPermissions`, ו-`fix` כשפקודה אחת מתקנת זאת. `test` שולח בקשה חיה אחת ודיווחים שלה זמן השהיה וגרסת Jev שענתה. זה יוצא 1, ואומר כך בכותרת שלו, כאשר התשובה מגיעה לאחר timeout של hook (hook יתעדו `timeout`) או משיבים לשאלת הבדיקה שלו בעיסוי.

דשבורד **Settings → Jev** פנל גם מראה את **FailproofAI Cloud connection**: איזה ארגון המכונה מדווחת אליו ואם מפתחו נושא Jev. זה קורא מהקבצים הגלובליים של המכונה שלו, ללא קריאת רשת.

## אימות קריאה אמיתית

התחל הפעלה חדשה בסוכן המחובר. בקש ממנו להשתמש בכלי הקריאה בקובץ שלו על `README.md` וודא את הכותרת. אשר שהקריאה מכילה את קריאת הכלי הזו, ואז הרץ `failproofai jev status` שוב: ספירת הקריאות שהוערכו לאחרונה שלה צריכה להגדיל. פתח את **Policies → Activity** ב-[local dashboard](/he/reference/local-dashboard#review-policy-activity) כדי לבדוק את גזר Jev של קריאה זו וקריאה. בענן, עמוד **Policies** של הארגון מציג תוצאות Jev עבור פעילות שסופקה. במצב observe, הפסק מתועד כ-**would-have** והתוצאה של המדיניות עדיין מחליטה את הקריאה. ניקיון מופיע רק כאשר מדיניות סקירה התאימה וJev ניקתה בדוקי שמה.

## מה מגיע לעמוד המדיניות

המכונה כבר שולחת את פעילות hook שלה ל-FailproofAI Cloud (`events:add`). עם Jev פעיל, רשומת כל קריאה שסגור גם אומר איזה מערכת הערכה הריצה, מה Jev החליט, אילו מדיניות היא ניקתה, למה היא חזרה למצב כאשר היא כן, זמן השהיה שלה וגם המודל שענה — החלטות, קודים ושמות, לעולם לא הפקודה או ההנחיה שלך. בעמוד **Policies** של הארגון שלך:

- קריאה שהחלטתו של Jev החליטה (כוח enforce) מיוחסת ל-**Jev**, וכאשר הבדיקה המחליטה באה מחבילה, הרשומה גם שם חבילה זו וגרסה שלה;
- במצב observe, Jev דחה או אזהרה מופיעה כ-**would-have**, ליד ההטלות שאתה צופה;
- המדיניות Jev ניקתה, או היו ניקה במצב observe, נספרו לפי מדיניות.
- החלטה Jev לקחה חלק בה (בלוק, אזהרה, ניקוי, או would-have במצב observe) מוצגת כל בדיקה שהיא שאלה ומה בדיקה זו הסיקה: גזר, למה (`not-detected`, `exempt`, `fired`, `op-requested`, …), ראיות `p` שלה, תשובת `exempt` וכל תשובת בדיקה. בדיקה של מדיניות שפועלת כדי לצפות (observe) מוצגת גם, מסומנת צפוי; זה לעולם לא חוסם. Jev משיב עם הסתברויות, לא פרוזה, אז אין סיבה בטקסט חופשי. Plain מאפשרות roll up לספירות ואינן נושאות רשימה זו.

## כאשר Jev לא יכול לענות

כל אחד מאלה חוזר למצב מדיניות שלך עבור קריאה זו, ותועד עם סיבה:

| סיבה | גורם |
| --- | --- |
| `out-of-credits` | הארגון שלך השתמש בהקצאת התוכנית שלו. |
| `http-401`, `http-403` | המפתח בוטל, או אינו נושא `jev:evaluate`. התחבר מחדש עם מפתח שעושה. |
| `http-429` | FailproofAI Cloud מגביל קצב Jev לארגון שלך. עד שה-wait שהוא מבקש הוא חוזה (שלו `Retry-After`, לכל היותר 60 שניות), המכונה לא שולחת לו כלום וכל קריאה חוזרת מיד. קריאות שהוחזקו בדרך זו מתועדות כ-`http-429`, או כ-`rate-limited` כאשר גבול קצב משלה של המכונה מחזיק אותן קודם. |
| `http-429` (גבול יומי) | הארגון שלך השתמש בקריאות Jev היומיות שלו: **10,000 ביום UTC**, אלא אם מי שמפעיל את FailproofAI Cloud שלך קבע גבול אחר. כל קריאה חוזרת עד שהספירה מאפסת ב-00:00 UTC; המכונה עדיין שואלת שוב לכל היותר פעם בדקה, כך שהיא בוחרת את ההגדרה מחדש תוך דקה. `failproofai jev test` אומר "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev סירבה בקשת קריאה זו, בדרך כלל משום שקריאת הכלי החזיקה טקסט צפוף (base64, hex, קוד minified) על פני תקציב הטוקנים של Jev. קריאה זו חוזרת בכל פעם; זה לא הפסקה. |
| `http-502` | Jev אינו זמין כרגע. |
| `http-503` | ענן זה לא יכול לשרת Jev עבור הארגון שלך: אין שער מודל, ארגון שטרם סופק או השער כבוי. שאל את מנהל שלך; hook שאל שוב לכל היותר פעם בדקה. |
| `http-404` | FailproofAI Cloud זה לא משרת Jev עדיין. |
| `timeout` | אף תשובה לא בתוך `timeoutMs` (ברירת מחדל 3000). בזמן FailproofAI Cloud קובע מצב Jev של המכונה, ההמתנה היא 5000 ms ו-`jev.json` של `timeoutMs` אינו משומש. |
| `model-mismatch` | גרסת Jev אחרת מ-1.13 משיבה. |

## איפה המפתח חי, ולאן הוא הולך

- המפתח מאוחסן פעם אחת, ב-`~/.failproofai/credentials.json` (`0600`, בספריית בעלים בלבד), ליד הפרטים הנוספים של FailproofAI Cloud. `jev.json` לא מחזיק מפתח עבור מסלול זה; אחד שנכתב שם הופך את הקונפיג לבלתי חוקי.
- אם `credentials.json` נושא **כל** הרשאה לכל אחד מלבדך (קבוצה או אחר, קריאה או כתיבה), או ספריית שלו ניתנת **לכתוב** על ידי כל אחד מלבדך, היא **סירוב**, לא קרא, וJev כבוי עד שתוקן: `chmod 600` בקובץ, `chmod 700` בספריה (או התחבר מחדש, שכותב מחדש את הקובץ ב-`0600` ועושה את הספריה בעלות בלבד). ספריה שאחרים יכולים רק לקרוא בסדר; אחד שהם יכולים לכתוב מאפשר להם להחליף את הקובץ.
- המפתח נספר רק בזמן ההתחברות שהוא הגיע איתה בעמדה במכונה: מדיניות או בעדן דיווח עבור אותה FailproofAI Cloud **עם אותו המפתח**, בקובץ זהה. מפתח Jev שנותר בעדר ללא אחד מתעלם, וJev נשאר כבוי. זה קורה כאשר failproofai ישנה `config --disconnect` משאיר את מפתח Jev בעמדה (זה לא יודע להסיר אותו), או כאשר failproofai ישנה `config --token` מתחבר עם מפתח אחר, אשר ב-FailproofAI Cloud עשוי להשתייך לארגון אחר. כדי להפעיל Jev שוב, התחבר שוב עם מפתח **machine**.
- המפתח נשלח רק לעולם למקור Cloud שהוא אוושר כנגדו. `jev.json` המצביע לכל מקום אחר סירוב.
- **סוכן במכונה יכול לקרוא אותו.** `credentials.json` הוא בעלות בלבד, והסוכן פועל כבעלים זה. קריאת קבצים של failproofai שלו משותפת בכוונה (רק שינוי אותם חסום, על ידי `block-failproofai-commands`), אז הדבר היחיד בין סוכן וקובץ זה הוא `block-read-outside-cwd` — מדיניות *סקירה* — ומהפעלה שהתחילה בספריית הבית שלך, שום דבר. מפתח עם `jev:evaluate` מוציא את הקצאת Jev של הארגון שלך (עד לכל היומי) מכל מקום בו משתמשים, אז התייחס למפתח מכונה כמו כל פרטי הוצאות אחרים: אם סוכן עשוי היה קורא אותו, בטל אותו בעמוד Ke וההתחברות שוב עם חדש.
- רק הקבצים הגלובליים שלך מחליטים זאת. מאגר לא יכול להפעיל Cloud Jev, להצביע אליו במקום אחר או לספק את המפתח שלו, ו-`FAILPROOFAI_JEV_API_KEY` מתעלמים עבור מסלול זה.
- עבור כל קריאה Jev מעריך, בקשה אחת עוברת ל-FailproofAI Cloud, נושאת מה [עמוד bring-your-own-key](/he/reference/jev-providers#what-leaves-the-machine) רשימות (סודות שחזרו). FailproofAI Cloud משדר אותה ל-TypeSafe ואינה רשומה או שומרת אותה.

## כיבוי

במכונה מחוברת, Jev כבוי כאשר FailproofAI Cloud לא פוזרת מדיניות Jev אליה: הסר או ארכיון את מדיניות Jev שם.

| פקודה | תוצאה |
| --- | --- |
| הסר את מדיניות Jev של המכונה ב-FailproofAI Cloud | מצב Cloud הופך `off` בסקר הבא (כ-30 שניות): Jev בכלל, מה שגם `jev.json` אומר. |
| `failproofai config --disconnect` | נתק את המכונה: המפתח מוסר, ו-`jev.json` גם כאשר הוא שם FailproofAI Cloud ואינו הושבתה. `jev.json` לנקודת קצה של Jev שלך נשאר. |

מן קריאת הכלי הבאה, hook ריצה מדיניות regex בדיוק כמו קודם.
