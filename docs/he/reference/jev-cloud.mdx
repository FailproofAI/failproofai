זהו עדכון התייחסות Cloud עבור [מדיניויות Jev](/he/policies/jev). Jev, מסווג TypeSafe, קורא כל קריאת כלי מול מה שבעצם ביקשת וענה לצד המדיניויות שלך, לעולם לא במקום שלהן. דרך **FailproofAI Cloud**, מכונה מחוברת משתמשת ב-Jev באותו מפתח שכבר מתחברת איתו: אין חשבון TypeSafe, אין מפתח שני, אין נקודת קצה להגדרה. כל קריאה נגבית לקצבת התוכנית הקיימת של הארגון שלך.

כל מה ש-Jev עושה נשאר ללא שינוי מ[התקנת ההביאה-על-המפתח-שלך](/he/reference/jev-providers): מדיניויות קשות נשארות סופיות, הכחשת מדיניות הניתנת לבדיקה מתבררת רק כאשר בוקש Jev לגבי אותה בדיוק, וכל כשל חוזר לתוצאת הביטוי הרגולרי לאותה קריאה.

<Note>
דורש **failproofai 1.0.8-beta.0** או מאוחר יותר. ל-1.0.7 אין Jev, למרות שהוא מסודר מעל ה-1.0.7 בטא. ללא תצורת Jev לא משתנה דבר: וו עולם יעברו על מדיניויות הביטוי הרגולרי בדיוק כפי שהם תמיד עשו.
</Note>

## לפני שתתחיל

התקן את Failproof AI במכונה שבה העוזר שלך פועל וחבור את הווים שלו ל[harnais שנתמך](/he/reference/harnesses). אם אתה מתחיל מאפס, עקוב אחר [הקצר](/he/start/quickstart) דרך התקנת וו. בדוק את ה-CLI המותקן עם `failproofai --version`; עדכן אם הוא קדום מ-Jev. אתה גם צריך גישה לעמוד **Administration → Keys** של הארגון שלך כדי ליצור מפתח מכונה.

Jev בוקר קריאות כלי בשם בשער `PreToolUse` או `PermissionRequest`. הוא לא בוקר כל אירוע בהפעלה. כדי לראות את Jev מנקה כחשת מדיניות, אתה צריך מדיניות מותקנת המסומנת [ניתנת לבדיקה](/he/policies/authority); כל כחישות מדיניות אחרות נשארות סופיות.

## הפעל את זה

1. **צור מפתח עם Jev.** בלוח הבקרה של FailproofAI Cloud, פתח **Administration → Keys → Create key** ובחר בטרם **machine**. זה מעניק את שלוש ההרשאות שמכונה צריכה: `events:add` (שלח פעילות), `policies:pull` (קבל מדיניויות) ו-`jev:evaluate` (Jev, נגבות מקצבת הארגון שלך). מפתח לא יכול לשאת `jev:evaluate` ללא שני.
2. **חבר את המכונה** עם אותו מפתח. קרא את הסוד החד-פעמי שלו בהנחיה, ואז הפעל את פקודת ההגדרה המלאה:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` מותקן את הדיימון, מחבר וו עבור ה-CLI של וכלי שהוא מוצא, וחיבור המכונה. משתנה הסביבה מצביע על המפתח מחוץ לטיעונים של הפקודה והיסטוריית הקליפה שלך. אם התקנות שלך התקנה מאוחר יותר, [חבר אותו במפורש](/he/start/quickstart).

   אם הארגון שלך מנהל FailproofAI Cloud משלו ולא את האחד המתארח, הוסף את כתובתו: `--url https://<your dashboard host>` (או ייצא `FAILPROOFAI_CLOUD_URL`). ללא זה מפתח נבדק נגד השירות המתארח והחיבור נכשל. אם התעודה של המארח הזה באה מ-CA פרטי, התקן את ה-CA ב-trust store של המכונה (לדוגמה עם `update-ca-certificates`), לא רק ב-`NODE_EXTRA_CA_CERTS`: הדיימון ששולח אירועים ומשיך מדיניויות קורא את חנות המערכת. ראה [Troubleshooting](/he/reference/troubleshooting).

זה הכל. חיבור אוחסן מפתח ו, כאשר למכונה **אין** תצורת Jev עדיין, כותב אחד עבור FailproofAI Cloud. מהמימוש הראשון של המכונה (בתוך כ-30 שניות), FailproofAI Cloud מוגדר במצב: `enforce` בעוד מדיניות Jev פורסם לה, `off` כשאיש (ראה [מי קובע את המצב](#who-sets-the-mode)). הפלט אומר כך:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

בדיקות FailproofAI Cloud פרס על ענן. כדי להוסיף בדיקות משלך על המכונה, התקן חבילה:

```bash
failproofai policies add FailproofAI/jev-policies
```

**עם `--no-transcripts`, חיבור לא מפעיל Jev.** Jev שולח כל קריאת כלי שנבדקה והזמנה אחרונה ל-FailproofAI Cloud, וזה יותר מחיבור החלטות בלבד שביקש לשלוח. המפתח עדיין מאוחסן, והפלט אומר Jev זמין וכיצד להדליק:

```bash
failproofai jev setup --provider failproofai
```

זה גם מדליק Jev דרך FailproofAI Cloud **off**. `jev.json` ש-Jev דרך FailproofAI Cloud (משמאל על ידי חיבור קודם עם תמלילים פועם) מוסר, על ידי אותו כלל `config --disconnect` משתמש, והפלט אומר Jev דרך FailproofAI Cloud נשאר כבוי במכונה זו. `jev.json` עבור נקודת הקצה Jev שלך משמאל, וכך גם FailproofAI Cloud אחד שכיבית (`--mode off`).

<Warning>
חיבור **לעולם לא יעלול** `~/.failproofai/jev.json` קיים. אם כבר משתמש בנקודת הקצה Jev משלך, הוא ממשיך להיות בשימוש, והפלט אומר הקובץ הוא משמאל כמו מוגדר — ו, כאשר הקובץ הזה משאיר Jev כבוי (סירב, או הדליק), אומר כך וכיצד לתקן. כדי להחליף את המכונה הזו ל-FailproofAI Cloud, הפעל `failproofai jev setup --provider failproofai`.
</Warning>

## מי קובע את המצב

במכונה מחוברת ל-FailproofAI Cloud, **FailproofAI Cloud קובע את מצב Jev**; שום דבר על המכונה לא:

- `enforce` בעוד כל מדיניות Jev (או regex + Jev) פורסם למכונה: כל קריאת כלי שנבדקה מ-עוזר שאחת המדיניויות הללו מטרה הולכת ל-FailproofAI Cloud, אשר שואל את הבדיקות שלה יחד עם בדיקות החבילות המותקנות שם. קריאה מ-עוזר ללא מדיניות Cloud Jev משנה, ללא בדיקת חבילה משלו, לא נשלחת בכלל. ב-`enforce`, הכחשת Jev עצמה בודקה קריאות חוסמות כמו גם ניקוי הפסקים הרגולריים שהם בוקרים.
- `off` כשאיש לא: לא Jev בכלל, מה שכדי `jev.json` אומר.

כדי לנסות מדיניות Jev לפני שהיא פועלת, פרסם אותה עם השפעה **observe**: בדיקות שלה עדיין שואלות, ומה היה עשוי לעשות נרשם כ-**would-have** בעמוד המדיניות, אך זה לעולם לא חוסם קריאה ולעולם לא מנקה. `failproofai jev setup --mode` ולוח הבקרה **Settings → Jev** החלף אומר המצב מנוהל על ידי FailproofAI Cloud ולא משנה דבר. `jev.json` אינו משמש לבדיקות Cloud, אפילו אם הוא שם ספק אחר. `failproofai config --disconnect` מחזיר Jev ל-`jev.json` משלך.

`failproofai jev status` ואז אומר `Jev checks run on FailproofAI Cloud (mode: enforce)`. זה גם שם הבדיקות שבוקרים כל מדיניות `both`. דף הצי מראה למה למכונה עם מצב לא יכול לשאול:

- `transcripts_disabled`: המכונה חוברה עם `--no-transcripts`, אשר לעולם לא מפעיל Jev.
- `jev_unconfigured`: מפתח המכונה לא נוצא `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud סירבה כמה מקריאות המכונה עבור מגבלת הקצב של Jev של הארגון, וקריאות אלה הוחלטו על ידי מדיניויות הביטוי הרגולרי לבדן.
- `jev_unavailable`: כמה קריאות בשורה כשלו, כך המכונה דלגה על Jev של FailproofAI Cloud לדקה בכל פעם. זה חוזר על עצמו בעצמו.

אם FailproofAI Cloud לא משיב תוך 5 שניות, מדיניויות הביטוי הרגולרי מחליטות לבדן, כמו לכל הפסקת Jev. לאחר 3 כשלים בשורה המכונה מפסיקה לשאול לדקה בכל פעם, כך הפסקת Cloud אינה מאטה כל קריאת כלי.

הפסקת הפעלה (`failproofai config --pause`) אינה עוצרת בדיקות Jev של FailproofAI Cloud, בדיוק כפי שהיא אינה עוצרת מדיניויות מנוהלות בענן. זה כן מעצור בדיקות Jev של חבילות המותקנות על המכונה.

## בדוק מה זה עושה

```bash
failproofai jev status
failproofai jev test
```

`status` מציג את הספק כ-**FailproofAI Cloud**, מארח ה-Cloud שהמכונה חוברה אליו, מצב, ומקור מפתח כ-**FailproofAI Cloud connection**, לעולם לא המפתח. כאשר `jev.json` של FailproofAI Cloud נמצא במקום אך Jev לא יכול לרוץ, זה אומר למה:

| `status` אומר | `status --json` | משמעות |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | המכונה מחוברת, אך לא Jev מפתח מאוחסן עבורו: המפתח חסר `jev:evaluate`, או החיבור לא יכול לאשר. הפעל `failproofai config` שוב עם המפתח ב-`FAILPROOFAI_CLOUD_TOKEN`; אם זה חסר ההרשאה, השתמש במפתח **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | אין חיבור FailproofAI Cloud על המכונה הזו על מפתח Jev שייך. |

אחרי `failproofai config --disconnect` אין עוד `jev.json` של FailproofAI Cloud (אלא אם כן הוא כובה, אשר נשמר), כך `status` פשוט דו"ח Jev כבוי. `status --json` נושא את אותם עובדות (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), גם כאשר התצורה היא בהעדר או סירבה. `permissions` הוא תמיד ש-`jev.json`; סיור לגבי `credentials.json` מוסיף `credentialsPermissions`, ו-`fix` כאשר פקודה אחת קובעת זה. `test` שולח בקשה חיה אחת ודו"ח latency שלה וה-Jev גרסה שענה. זה יוצא 1, ותגיד כך בכותרתו, כאשר התשובה מגיעה אחרי hook timeout (וו היה דו"ח `timeout`) או תשובות שאלת בדיקה שלה wrongly.

לוח הבקרה **Settings → Jev** פנל גם מראה את ה-**FailproofAI Cloud connection**: איזה ארגון המכונה דו"ח לתוך ובאם מפתח שלה נוצא Jev. זה נקרא מקבצי המכונה שלך, ללא קריאת רשת.

## אמת קריאה אמיתית

התחל הפעלה חדשה ב-עוזר מחובר. בקש ממנו להשתמש בכלי קריאת הקבצים שלו ב-`README.md` ודו"ח הכותרת. אשר שההפעלה מכילה את קריאת הכלי הזאת, ואז הפעל `failproofai jev status` שוב: ספירת הקריאה המוערכת האחרונה שלה צריך להגדיל. פתח **Policies → Activity** ב-[לוח הבקרה המקומי](/he/reference/local-dashboard#review-policy-activity) כדי לבדוק את הפסק של Jev של קריאה זאת ומצב. בענן, ארגוני **Policies** בעמוד מציג Jev תוצאות עבור הפעילות סופקה. באופי ملاحظة, הפסק נרשם כ-**would-have** ודבר תוצאה מדיניות עדיין מחליטה את הקריאה. הניקוי מופיע רק כאשר מדיניות הניתנת לבדיקה תואמה ו-Jev מנקה בדיקותיה שנקבעו.

## מה מגיע לעמוד המדיניות

המכונה כבר שולחת את פעילות הווית שלה ל-FailproofAI Cloud (`events:add`). עם Jev פועם, רשומת כל קריאה גדורית גם אומר איזה evaluator רץ, מה Jev החליט, אילו מדיניויות זה מנקה, למה זה חזור כאשר זה עשה, latency שלה והמודל שענה — החלטות, קודים ושמות, אף פעם לא הפקודה או הזמנה שלך. בארגוני **Policies** בעמוד:

- קריאה ש-Jev הפסק שלה החליטה (כפוף במצב) מיוחסת ל-**Jev**, וכאשר בדיקה הכריעה באה מחבילה, רשומה גם שם את חבילה זו וגרסתה;
- באופי observe, הכחשת Jev או אזהרה מופיעה כ-**would-have**, לצד rollouts שאתה צופה;
- מדיניויות ש-Jev מנוקות, או היה מנקה באופי observe, נספרות לכל מדיניות.
- החלטה ש-Jev נטל חלק (בלוק, אזהרה, ניקוי, או would-have באופי observe) רשימות כל בדיקה זה שאל ומה בדיקה זאת סיכמה: פסק, למה (`not-detected`, `exempt`, `fired`, `op-requested`, …), ראיית שלה `p`, `exempt` תשובה וכל בדיקת בדיקה. בדיקה מדיניות פרסום כדי צפייה (observe) רשומה גם, marked צפוי; זה לעולם לא בלוקים. Jev תשובות עם הסתברויות, לא יוצקה, כך אין סיבה טקס חופשי. plain מאפשר רולינו לתוך ספירות ואינו נוצא בדיקה זה רשומה.

## כאשר Jev לא יכול להשיב

כל אחת מאלה חוזרת לתוצאת המדיניויות שלך לאותה קריאה, ורשומה עם סיבתה:

| סיבה | סיבה |
| --- | --- |
| `out-of-credits` | הארגון שלך השתמש בקצבת התוכנית שלו. |
| `http-401`, `http-403` | המפתח בוטל, או אינו נוצא `jev:evaluate`. חבר מחדש עם מפתח שעושה. |
| `http-429` | FailproofAI Cloud הוא ערימה מגבלה של קצב Jev עבור הארגון שלך. עד שיישא לחכות עבורו (שלו `Retry-After`, לכל היותר 60 שניות), המכונה שולחת זה כלום וכל קריאה חוזרת מטבע. קריאות במנת דרך זאת נרשמות כ-`http-429`, או כ-`rate-limited` כאשר קצב המכונה משלה מחזיקה אותן ראשון. |
| `http-429` (daily limit) | הארגון שלך השתמש בקריאות Jev יומיות שלו: **10,000 לכל יום UTC**, אלא אם כן מי פועל FailproofAI Cloud שלך קבע מגבלה אחרת. כל קריאה חוזרת עד שהספירה מרשת ב-00:00 UTC; המכונה עדיין שואלת שוב לכל היותר פעם בדקה, כך זה בוחר את הריסט בתוך דקה. `failproofai jev test` אומר "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev סירב בקשה קריאה זאת, בדרך כלל כי קריאת הכלי החזיקה טקסט צפוף (base64, hex, קוד minified) מעל תקציב טוקן Jev. קריאה זאת חוזרת כל פעם; זה אינו הפסקה. |
| `http-502` | Jev אינו זמין עכשיו. |
| `http-503` | ענן זה לא יכול להגיש Jev עבור הארגון שלך: לא gateway מודל, ארגון לא סיפק עדיין, או gateway הוא למטה. שאל את המנהל שלך; וו שואל שוב לכל היותר פעם בדקה. |
| `http-404` | FailproofAI Cloud זה אינו משרת Jev עדיין. |
| `timeout` | לא תשובה בתוך `timeoutMs` (ברירת מחדל 3000). בזמן FailproofAI Cloud קובע מצב Jev של המכונה, ההמתנה 5000 אמס וש-`jev.json` ש-`timeoutMs` לא משמש. |
| `model-mismatch` | גרסה Jev אחרת מאשר 1.13 ענה. |

## איפה המפתח חי, ואיפה זה הולך

- המפתח מאוחסן פעם אחת, ב-`~/.failproofai/credentials.json` (`0600`, בספרייה בבעלות בלבד), לצד אישורי FailproofAI Cloud האחרים. `jev.json` מחזיק לא מפתח לנתיב זה; אחד נכתב שם עושה את התצורה פקוד.
- אם `credentials.json` נושא **כל** הרשאה לכל אחד אלא אתה (קבוצה או אחרת, קרא או כתוב), או התיקייה שלה יכול להיות **כתוב** על ידי כל אחד אלא אתה, זה **סירבה**, לא קרא, וJev הוא כבוי עד שתתקן זה: `chmod 600` על הקובץ, `chmod 700` בספרייה (או חבר מחדש, אשר rewrites הקובץ ב-`0600` וחיזר הספרייה בבעלות בלבד). ספרייה אחרים יכולים רק לקרוא בסדר; אחד שהם יכולים כתוב מאפשר להם להחליף את הקובץ.
- המפתח ספור רק בזמן החיבור שהוא הגיע עם במכונה: מדיניות או דו"ח אישור עבור אותו FailproofAI Cloud **עם אותו מפתח**, באותו קובץ. מפתח Jev שנשאר מאחור ללא אחד מתעלמים, וJev נשאר כבוי. זה קורה כאשר failproofai ישן `config --disconnect` משאיר מפתח Jev במקום (זה לא יודע להסיר), או כאשר failproofai ישן `config --token` חיבור עם מפתח אחר, אשר על FailproofAI Cloud אולי שייך לארגון אחר. כדי לחזור Jev על, חבור שוב עם מפתח **machine**.
- המפתח הוא רק אי פעם שלח למקור ענן זה היה מאומת נגד. `jev.json` להצביע בכל מקום אחר סירב.
- **עוזר על המכונה יכול לקרוא זה.** `credentials.json` הוא בבעלות בלבד, והעוזר רץ כאותו בעלים. קריאה failproofai שלו קבצים משלו מותר בכוונה (רק שינוי אותם בלוק, על ידי `block-failproofai-commands`), כך הדבר היחיד בין עוזר וקובץ זה הוא `block-read-outside-cwd` — מדיניות *ניתנת לבדיקה* — ומהפעלה החל בספריית הבית שלך, כלום. מפתח עם `jev:evaluate` גוזל הקצבה Jev של הארגון שלך (עד ל-daily כובעים) מ-everywhere זה משמש, אז התייחס מפתח מכונה כמו כל אחר גוזל אישור: אם עוזר אולי קרא זה, השבית אותו בעמוד Keys וחבור עם אחד חדש.
- רק את קבצי worldwide שלך להחליט זה. מחסן לא יכול להפוך Cloud Jev על, להוביל אותו למקום אחר או לספק מפתח שלו, ו-`FAILPROOFAI_JEV_API_KEY` מתעלם עבור נתיב זה.
- עבור כל קריאה Jev מעריך, בקשה אחת הולכת ל-FailproofAI Cloud, נושא מה [זמן-your-own-key דף](/he/reference/jev-providers#what-leaves-the-machine) רשומות (סודות redacted). FailproofAI Cloud קדם זה ל-TypeSafe ולא כנופיות או להחזיק זה.

## כבה את זה

על מכונה מחוברת, Jev הוא כבוי כאשר FailproofAI Cloud פורסם לא Jev מדיניות לה: להסיר או לארכיב את Jev מדיניויות שם.

| פקודה | תוצאה |
| --- | --- |
| הסר מדיניויות Jev של המכונה ב-FailproofAI Cloud | מצב Cloud הופך `off` ב-הבדיקה הבאה (כ-30 שניות): לא Jev בכלל, מה שכדי `jev.json` אומר. |
| `failproofai config --disconnect` | נתק את המכונה: מפתח מוסר, וכך `jev.json` כאשר זה שם FailproofAI Cloud ואינו כובה. `jev.json` עבור נקודת הקצה Jev משלך נשאר. |

מהקריאה הבאה של כלי, וו הפעל מדיניויות הביטוי הרגולרי בדיוק כמו לפני.
