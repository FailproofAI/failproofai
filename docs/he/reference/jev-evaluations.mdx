עמוד זה מתאר את צורות השאלות וכללי הניקוד מאחורי [הערכות Jev](/he/evaluations/jev). חלק מהשאלות דורשות ממודל *לקרוא* את השיחה, אך לא *לכתוב* עליה. "האם הלקוח הביע דחיפות?" יש לה שתי תשובות. "עד כמה הם היו תסכולים?" יש לה קומץ, בסדר. אתה יודע כל תשובה לפני שאתה שואל.

**הערכת מסווג** היא בדיוק לאלה. אתה כותב את השאלה והתשובות שהיא עשויה לתת, וגם מודל קטן שנבנה לסיווג מחזיר מספר מכיול — לא עולם טקסט חופשי.

<Note>
כמו שופט, הערכת מסווג עולה קריאה לומודל לכל הפעלה. בשונה משופט, זהו מודל קטן ויחיד-מטרתי ולא כללי, כך שהוא מהיר וזול יותר — אך הוא לעולם לא יסביר את עצמו. אם אתה צריך את ההיגיון, השתמש ב-[judge](/he/evaluations/judge).
</Note>

## איזה אחד אני רוצה?

| שאלה | שימוש |
| --- | --- |
| כמה קריאות כלים היו? | code |
| האם ההפעלה הייתה פחות מ-30 שניות? | code |
| האם הלקוח הביע דחיפות? | **מסווג** |
| איזה צוות צריך להטפל בזה: חיוב, טכני או מכירות? | **מסווג** |
| עד כמה תסכול לקוח? | **מסווג** |
| האם התשובה הייתה בעצם נכונה? | **judge** |
| האם זה עקב את מדיניות ההעלאה שלנו, ולמה אתה חושב שכן? | **judge** |

הכלל הזהוב: **ניתן לספור → code, תשובות שאתה יכול לרשום → מסווג, צריך הסבר → judge.**

אתה לא צריך להחליט קדימה. תאר מה אתה רוצה שיימדד והעוזר בוחר, אומר לך איזה הוא בחר ולמה, ואתה יכול להחליף אותו.

## שני סוגי השאלות

### `noul` — האם זה נכון?

שתי תשובות, ואתה מתאר את שתיהן. התוצאה היא ההסתברות שתיאור "האמת" מתאים:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

תאר את שני הצדדים. "לא הביעו דחיפות" היא תשובה אמיתית ואמירה כזו הופכת את השנייה לחדה יותר.

### `score` — כמה מזה?

רובריקה מסודרת, **הגרוע ביותר ראשון**. התוצאה היא היכן ההפעלה נוחתת עליה, מוקדשה ל-0–1:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**רובריקה לוקחת שלוש עד חמש רמות, וכולן חייבות להיות שונות.** שני הגבולות נמדדים, לא סטייליים:

- **שתי רמות** מתמוטטות למה `noul` כבר עושה טוב יותר, **ויותר מחמש** גורמות למודל להזדקף לכיוון האמצע במקום להתחייב. אותה שאלה על אותה הפעלה קיבלה ניקוד 0.00 עם שתי רמות, 0.01 עם שלוש, ו-0.55 עם עשר.
- **רמות חוזרות** מפצלות את התשובה בחוסר שרירותי ביניהן. הפעלה שהייתה ללא שך כעוסה קיבלה 1.00 מול `["Calm", "Frustrated", "Very angry"]` ו-0.66 מול `["Angry", "Angry", "Angry"]` — מספר טוב שלא מתכוונת דבר.

קטגוריות ללא סדר — "חיוב, טכני או מכירות" — אינן רובריקה. שאל אותן כ-`noul` לכל קטגוריה, או השתמש בשופט.

## קריאת התוצאות

מסווג מייצר **ניקוד** מ-0 ל-1, בדיוק כמו שופט, כך שהוא מחוווה, סוננת והדק התרעות באותו אופן. שתי הבדלים כדאי לדעת:

- **אין הגיון.** השדה ריק, בכוונה. מודל זה לא מסביר את עצמו, והמצאת הסבר תהיה זיוף ולא תכונה.
- **אי-ודאות תויגת.** שאלת `score` מדווחת על ביטחונה שלה, והתוצאה שהמודל היה לא בטוח בה תוייגה `low_confidence` — כך "אילו מאלה אדם צריך להסתכל עליו" הוא מסנן ולא ניחוש. שאלת `noul` לא מדווחת על ביטחון, כך שהיא לעולם לא תוייגת.

הפעלות ארוכות מאוד נקראות בקטעים ומשולבות. כאשר הפעלה ארוכה מדי לקריאה במלואה, התוצאה אומרת כמה תורות הושמטו — לעולם לא תראה שיפוט שנעשה על חלק מהפעלה המוצג כעל הכל.

## גבולות

- **שלוש עד חמש רמות רובריקה, כולן ברורות.** ראה למעלה; שני הגבולות אנוצים בזמן הכתיבה.
- **שאלה אחת לכל הערכה.** שאל שתי דברים ותקבל שתי הערכות, וזה גם מה שאתה רוצה בתרשים.
- **עריכת השאלה מפרסמת גרסה חדשה.** ניקודים ישנים וחדשים אינם השוואים, כך שהם מוחזקים בנפרד במקום לערבב לקו מגמה אחד.
- **מסווג תמיד מייצר ניקוד**, לא מדד או קביעה.
- **ללא הגיון**, כמו למעלה. אם מספר יגרום למישהו לשאול "למה?", כתוב שופט במקום.

## בדיקה והחזר

בשונה משופט, הערכת מסווג **יכולה** להיבדק לפני שתפרוס אותה — [בדוק אותה](/he/evaluations/test) מול הפעלות אמיתיות באותו אופן שהיית בודק הערכת קוד, וקרא את הניקודים לפני שדבר כלשהו יכנס לשידור חי.

זה יכול גם להיות [מחובזר](/he/evaluations/deploy#score-sessions-you-already-have) על הפעלות שכבר יש לך. זה עולה קריאה לומודל לכל הפעלה, כך שהיקף את החלון בכוונה במקום להשמיע כל דבר.
