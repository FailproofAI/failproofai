זהו ההתייחסות לספקים ותצורה של [מדיניויות Jev](/he/policies/jev) עם המפתח שלך. מדיניויות Regex משווה מחרוזות. הן לא יכולות להבדיל בין `rm -rf build/` שביקשת ל`rm -rf ~` שחדר לתוכנית, אז הן חוסמות יותר מדי במקום אחד וקצת מדי במקום אחר. **Jev**, המסווג של TypeSafe, קוראה את הקריאה מול מה שבאמת ביקשת ועונה על קבוצת שאלות כן/לא בקשה אחת מהירה.

עם נקודת הקצה וההפתח של Jev שלך מוגדרים, Failproof AI שואל את Jev לגבי כל קריאת כלי **לצד** מדיניויות ה-regex, לעולם לא במקום שלהן:

- הדחייה של מדיניות **קשה** היא סופית. Jev לא יכול לנקות אותה. כל מדיניות היא קשה אלא אם היא מסומנת בהסכמה כניתנת לבדיקה ושמות את בדיקות Jev המכסות אותה, כך שמדיניות מותאמת, חבילה או Cloud שלא אומרת דבר היא קשה, והשמירה העצמית שתמיד פעילה היא תמיד קשה.
- הדחייה של מדיניות **ניתנת לבדיקה** עשויה להיות מנוקה, אך רק כאשר Jev הוזמן לדעת על הדאגה המדויקת שהמדיניות מכסה וענה "אין כאן שום דבר" או "המשתמש ביקש את זה". בדיקה שמגלה שהדאגה אמיתית, כאשר המשתמש לא ביקש את הקריאה, שומרת את הדחייה — אפילו כאשר הפסק שלה הוא רק אזהרה, כי לפני קריאת כלי אזהרה לא עוצרת את הסוכן. וכאשר הבדיקה הזו היא אחת שיכולה להדחות (חשיפת סוד, זליגת אישור, מחיקה הרסנית, ...), שום דבר לא נוקה בקריאה זו.
- חסימה עדיין יכולה להפוך לאזהרה כאשר הקריאה היא שלב של המשימה שנתת ולא מגיעה רחוק יותר: Jev משנה את דחיית שלה לאזהרה, והאזהרה הזו — שם מה שבאמת לא בסדר בקריאה — מחליפה את החסימה של המדיניות.
- Jev יכול גם להזהיר או להדחות בעצמו, לנזק שרגקס לא מתאר.
- אם Jev לא יכול לענות (timeout, rate limit, שגיאת שרת, אין credits, גרסת מודל לא צפויה), הקריאה הזו מקבלת את התוצאה של regex, בדיוק כמו ללא Jev.
- Jev לעולם לא עושה קריאה יותר פרמיסיבית מהמדיניויות שלך לבדן אלא אם היא קראה את כל הקריאה והוזמנה לדעת על הדאגה המדויקת. כל דבר פחות — קריאה גדולה מדי לשליחה שלימה, זריקה חשודה — מסיר את האישורים ושומר את כל דחייה.

<Note>
ללא תצורת Jev כלום לא משתנה: hook מריצים את מדיניויות ה-regex בדיוק כפי שהם תמיד עשו. התצורה היא כל ה-opt-in.
</Note>

<Tip>
ב-FailproofAI Cloud? אתה לא צריך מפתח משלך: מכונה המחוברת עם מפתח השומל `jev:evaluate` יכולה להשתמש ב-Jev בתוכנית של הארגון שלך. ראה [Jev דרך FailproofAI Cloud](/he/reference/jev-cloud).
</Tip>

## לפני שתתחיל

התקן **failproofai 1.0.8-beta.0 או מאוחר יותר** וצרף את hook שלו ל[harness תומך](/he/reference/harnesses) במכונה שבה הסוכן שלך רץ. עקוב אחר [quickstart](/he/start/quickstart) אם זו מכונה חדשה, או [הגדר אכיפה מקומית](/he/start/setup#enforce-locally) אם אתה לא משתמש ב-Cloud. בדוק את CLI המותקן עם `failproofai --version`.

קבל מפתח API מספק למטה, או הכן endpoint תואם ואת המפתח שלו. Jev בודק קריאות כלי בשם בשער `PreToolUse` או `PermissionRequest`. זה יכול להנפיק את הפסק שלו, אך ניקוי דחייה מדיניות קיימת דורש גם מדיניות מותקנת המסומנת [ניתנת לבדיקה](/he/policies/authority). דחיות מדיניות קשה נשארות סופיות.

## בחר ספק

Jev ניתן להשגה דרך חמש דרכים. הביא מפתח לכל אחד מהם.

| Supplier | `--provider` | Endpoint | Default model | Notes |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Exact version pin. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | בקשות מנותבות לנקודות קצה עם אחסון נתונים אפס בלבד, ללא fallback לספק אחר. דיווח גרסה מתוארכת כגון `typesafe/jev-1.13-20260917`. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | שמות Jev רק לפי כינוי, ולכן הגרסה השומלת רשומה כלא מאומתת. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | צריך `--account-id`. בערך שש קריאות לשנייה לכל מפתח נמדדו לפני HTTP 429. |
| Endpoint משלך | `custom` | `<base-url>/systemone` | `jev-1.13.0` | כל endpoint המקבל את גוף הבקשה של TypeSafe ודיווח איזה מודל ענה. `https` בלבד; רגיל `http` לhostly loopback (`localhost`, `127.0.0.1`, `::1`) מקובל לבדיקה מקומית. |

<Warning>
עם התכונה bring-your-own-key של Vercel, בקשה כושלת מנוסה בשקט מחדש עם credentials של Vercel. אם אתה צריך כל קריאה שתתחייב, והיא נראית, על ידי חשבון TypeSafe שלך בלבד, השתמש ב-TypeSafe ישירות.
</Warning>

## הגדר את זה

פקודה אחת, ה-endpoint והמפתח. התחל במצב `observe` כדי שתוכל בדוק את הפסקי Jev בזמן שהמדיניויות הקיימות ממשיכות להחליט קריאות:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### ה-URL בוחר את הספק

אתה לא צריך לשם את הספק: ה**host** של ה-URL הוא איזה אחד זה.

| URL host | Supplier | גם צריך |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| כל host אחר | `custom` | — ה-URL שנתת הוא ה-base URL |

שלוש דברים נובעים מזה:

- **URL שהוא ה-API של הספק עצמו לא כותב override.** `--url https://api.typesafe.ai/v1` מייצר בדיוק את התצורה שהיא הייתה `--provider typesafe`. תן דרך שונה או host בספק ידוע וזה מאוחסן כ-base URL, כפי ש`--base-url` היה מאחסן אותו.
- **`--provider` עדיין דורס את ההסקה**, וזה איך אתה מגיע ל-proxy שמדבר API של ספק מ-host של שלך: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **`--provider` שמנוגד ל-host הוא סירוב**, לא ניחוש. `--provider openrouter --url https://api.typesafe.ai/v1` לא כותב כלום ואומר למה: שני ההקלדות חולקות דעות לגבי היכן המפתח שלך עומד להישלח. אותו זוג סיורב מ`jev setup --base-url` ומהחיווי הפעל של Jev. (`--provider custom` לא סתירה — זה אומר "תייחס ל-URL הזה ככל שהוא" — חוץ מעל host של Cloudflare, שהנקודה הקצה לכל חשבון של נתיב מותאם לא יכול להגיע.)

`--url` מאומת בדיוק כמו ה`baseUrl` בקובץ תצורה, וסיורב באותו דברים: `https`, או רגיל `http` ל-host loopback (`localhost`, `127.0.0.1`, `::1`) בכל מצב. סיכון: כלום לא מאמת שרת loopback, אז בזמן שהוא כבוי תהליך מקומי אחר יכול לקחת את ה-port שלו ולענות; השתמש ב`https` מחוץ לבדיקה מקומית.

### המפתח

צינור זה עם `--key-stdin`, או הרץ את הפקודה בטרמינל ללא זה וכתוב את המפתח בשאילתה מוסווית. בכל דרך זה נכנס ישר לקובץ תצורה ולעולם לא מודפס חזרה.

`failproofai jev setup` לוקח את אותות הדגלים ו-longhand לכל זה: `setup --provider <kind>` שם היית מעדיף לשם את הספק מאשר ה-URL.

### `--token`, וכמה זה עולה

`--token <token>` שם את המפתח בשורת הפקודה, שהיא הדרך המהירה ביותר להגדיר מכונה ותיקיית ההקלטות היחידה שמשאירה את המפתח כלום אלא בקובץ התצורה:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
אחר כך argument של שורת פקודה נמצא בקובץ ההיסטוריה של shell שלך, וכאשר הפקודה רצה זה בתהליך רשימה — ניתן לקריאה מ`/proc` על ידי כלום הפעלת כמוך. `setup` אומר את זה בכל פעם `--token` משמש. העדיף `--key-stdin` במכונה אתה חולק, בסשן מוקלט, או בכל מקום קובץ ההיסטוריה מסונכרן; סובב מפתח שעברת בדרך זו אם זה חשוב.
</Warning>

`--token`, `--key-stdin` ו`--key-from-env` הם בלעדיים זה לזה: תן אחד.

ואז שלח קריאה חיה קטנה אחת לבדוק את המפתח, את endpoint ואיזה Jev ענה:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` יציאות 1, ואומר את זה בכותרת שלו, כאשר התשובה מגיעה אחרי ה-timeout (כל hook היה חוזר ל-regex כ`timeout`) או עונה על שאלת הבדיקה שלו בצורה שגויה.

Hooks קורא את התצורה בכל קריאת כלי, אז זה חל מהבא. אין כלום להתחיל מחדש, עם או בלי daemon.

## בדוק מה זה עושה

```bash
failproofai jev status
failproofai jev status --json
```

`status` מראה את הספק, endpoint, מודל, מצב, קובץ תצורה וההרשאות שלו, ולעולם לא את המפתח. תחת זה הוא מסכם פעילות אחרונה: כמה קריאות Jev הערך, כמה פעמים זה חוזר ל-regex ולמה, הזמן ההשהייה שלו, ואילו מדיניויות ניתנות לבדיקה שהוא נקה.

## אימות קריאה אמיתית

התחל סשן חדש בסוכן המחובר. בקש מאלו להשתמש בכלי הקריאה של הקובץ שלו ב`README.md` ודווח את הכותרת. אשר שהסשן מכיל את קריאת הכלי הזו, ואז הרץ `failproofai jev status` שוב: ספירת קריאתו להערכה האחרונה צריכה להגדיל. פתוח **Policies → Activity** ב[local dashboard](/he/reference/local-dashboard#review-policy-activity) לבדוק את הפסק Jev של הקריאה ומצב. במצב observe, תוצאת המדיניות עדיין מחליטה את הקריאה. אישור מופיע רק אם מדיניות ניתנת לבדיקה תואמה ו-Jev נקה כל בדיקה בשם; קריאה רגילה עשויה להיות ללא מדיניות לניקוי.

## צפה במצב

`enforce` הוא ברירת המחדל. להשגחה ב-Jev ללא מתן אישור לשנות החלטה כלשהי, עבור ל`observe`: Jev עדיין נשאל וההפסקים שלו רשומים, אך תוצאת ה-regex היא מה שנאכף.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` שומר את התצורה — ה-endpoint והמפתח — ומפסיק להשאל Jev: hooks מריץ את מדיניויות ה-regex בדיוק כמו ללא תצורה, ו`failproofai jev status` אומר "off (switched off)". החלף חזרה עם `--mode observe` או `--mode enforce`.

Re-running `setup` לאותו ספק שומר את המפתח המאוחסן, אז מצב עם קצר הוא דגל אחד. החלפת ספק מתחילה מחדש וביקשות עבור המפתח של הספק הזה. כך גם `--base-url` שמעביר בקשות לhostly שונה: מפתח מאוחסן נשלח רק לhost שהוא ניתן עבור, או ל-API של הספק שלו.

## קובץ התצורה

הכל חי בקובץ אחד, `~/.failproofai/jev.json`, כתוב על ידי `setup`:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Field | Meaning |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` או `custom` — או `failproofai`, שהמפתח שלו בא מחיבור FailproofAI Cloud במקום קובץ זה (ראה [Jev דרך FailproofAI Cloud](/he/reference/jev-cloud)). |
| `apiKey` | שלח כ`Authorization: Bearer <key>`. |
| `baseUrl` | דרוש עבור `custom`; מחליף את base API של הספק אחרת. חייב להיות `https`. Plain `http` ל`localhost` מקובל רק עם `mode: observe`: כלום לא מאמת שרת מקומי, אז בזמן ה-proxy שלך הוא כבוי כל תהליך במכונה, כולל הסוכן שיתפקד, יכול לענות במקום שלו. השתמש ב`https` מחוץ לבדיקה מקומית. |
| `accountId` | Cloudflare בלבד: 32 רובה hex. |
| `model` | מחליף את מודל ID ברירת המחדל של הספק. מודל ID גרוסי חייב שם Jev 1.13. ערך בעל צורה כמו מפתח API הוא סיורב (וגם לא חזר), אז מפתח הדבוק ל`--model` לעולם לא מאוחסן או נשלח כמודל. |
| `timeoutMs` | כמה זמן קריאת כלי מחכה ל-Jev לפני השימוש בתוצאה ה-regex. 100–10000, ברירת מחדל 3000. |
| `mode` | `enforce` (ברירת מחדל), `observe`, או `off` (שמור את התצורה, הרץ בלא Jev). |

שלוש כללים מגנים עליה:

- **רק בעלים.** זה כתוב עם הרשאות `0600`. עותק שכל משתמש או קבוצה אחרים יכולים לקרוא או לכתוב הוא **סיורב**, ו-hooks חוזר ל-regex עד שתרץ `chmod 600 ~/.failproofai/jev.json` או `setup` שוב. הספרייה בדוקה גם: `~/.failproofai` חייב שלא להיות **כתוב** על ידי אחרים, כי מי שיכול לכתוב שם יכול להחליף את הקובץ תוך לא משנה את ההרשאות שלו. `setup` לוקח את ביטות הכתיבה האלה אם זה מוצא אותן. `failproofai jev status` אומר כאשר תצורה חדר לסיורב ומראה את endpoint שהקובץ שמות: מישהו אחר יכול היה לשנות את זה, אז בדוק זה שלך לפני שתעשה `chmod`. Re-running `setup` על קובץ כזה נושא את המפתח המאוחסן שלו רק ל-API של הספק; כל endpoint אחר זה שמות צריך את המפתח שוב (`--key-stdin`), או `--base-url default` לשלוח בקשות חזרה לספק.
- **רק גלובאלי.** מחסן לא יכול להפוך Jev, להצביע אליו בnother endpoint או לבחור במודל שלו: `.failproofai/jev.json` בתוך פרויקט הוא התעלם, והספק, URL, מודל וחשבון id נקרא רק מקובץ זה — לעולם לא מהסביבה, שהגדרות סוכן של מחסן יכול לקבוע. (`FAILPROOFAI_HOME` לא דרך סביב זה: זה מעביר את כל ספרייה failproofai, המדיניויות שלך כולל, במקום להפעיל Jev על שלו.)
- **המפתח לבדו עשוי לבוא מהסביבה.** אם לקובץ אין `apiKey`, `FAILPROOFAI_JEV_API_KEY` מסופק זה עבור הסשן הזה (`setup --key-from-env` כתב קובץ כזה). זה לעולם לא מחליף מפתח הקובץ מחזיק, וזה לא יכול להפוך Jev ללא הקובץ. היכן המשתנה לא הוא קבוע, Jev הוא פשוט בחוץ עבור קליפת זו: `failproofai jev status` אומר את זה, יציאות 0 ועזוב את התצורה לבד (`status --json` דיווח `"status": "key-missing"` עם `"reason": "no-env-key"`). `failproofaid` daemon לא רואה את סביבת shell שלך, אז במכונה מוגדרת עם `failproofai config`, שמור את המפתח בקובץ.

## איזה Jev עונה

הרגעות החלטה של Failproof AI חוברו על Jev 1.13, אז תשובה משמשת רק כאשר היא בא מהמשפחה הזו: `jev-1.13.x`, או OpenRouter's `typesafe/jev-1.13-<date>`. היכן ספק שמות Jev רק על ידי כינוי ודיווחים לא גרסה (Vercel, ו-Cloudflare כאשר זה לא), התשובה משמשת ורשומה כלא מאומתת. `custom` endpoint חייב דיווח המודל שענה; החריג היחיד הוא שם `--model` לא גרוסי שתצורת עבור זה, שהוצא חזרה, הוא רשום כלא מאומת באותו אופן. תשובה דיווח גרסה אחרת, או `custom` תשובה דיווח כלום, לא משמשת: הקריאה הזו חוזרת ל-regex עם הסיבה `model-mismatch`.

## כאשר Jev לא יכול לענות

כל אחד מאלה חוזר לתוצאת ה-regex להקריאה וזה ורשום עם סיבתו, אשר `failproofai jev status` סכומים:

| Reason | Cause |
| --- | --- |
| `timeout` | לא תשובה בתוך `timeoutMs`. |
| `http-429` | הספק שיעור-הגבל את המפתח. |
| `rate-limited` | Failproof AI's שלו limiter העכה את הקריאה לפני שליחה אותה: 5 בקשות שנייה, בפרצים עד 5, וכלום לרגע לאחר הספק עונה `429`. לא הספק. |
| `http-500`, `http-502`, `http-503`, … | שגיאת שרת בספק. הסטטוס המדויק הוא רשום. |
| `out-of-credits` | HTTP 402: חשבון הספק אין credits שנותר. |
| `provider-refused` | HTTP 402 מ-Cloudflare קריאה עבור "Model execution failed (Payment error)": הספק סיורב להרות המודל בבקשה זו. בדרך כלל לא חיובי, אז טופין יא לא יעביר אותו. |
| `http-401`, `http-403` | המפתח היה סיורב. |
| `http-404` | כלום הוא הוגש ב`<base>/systemone`, אז ה-base URL הוא טעות — `/systemone` הוא יתווסף, וכל ספק משרת אותו בגרסה שלו root. `failproofai jev models` מראה מה endpoint does serve. |
| `network` | endpoint לא יכול להגיע. |
| `http-301`, `http-302`, `http-307`, `http-308` | endpoint ענה עם הפניה. הפניות לעולם לא ואחריות, אז התשובה רק אי פעם בא מה-URL בתצורה; קבוע `--base-url` ל-URL סופית. |
| `malformed` | endpoint ענה, אבל לא עם Jev תשובה — גוף זה לא JSON, או אחד עם לא תשובות בו. |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflare של מעטפת דיווח כשל, או עבודה שלא הייתה סיימה. |
| `model-mismatch` | Jev גרסה אחרת מ-1.13 ענה, או `custom` endpoint לא אומרת איזה מודל ענה. |
| `request-cut` | **לא הפסקה.** Jev ענה; זה היה מראה רק חלק מהקריאה, אז תשובתו נקה כלום. ראה [כאשר Jev ענה, אבל לא על כל הקריאה](#when-jev-answered-but-not-on-the-whole-call). |

`failproofai jev status` יכול הציג כמה סיבות ונדירות גם כן, כגון `upstream-error` (התשובה נשאה שגיאה של הספק שלו) או `config`, וסכומי כל סיבה זה לא יכול שם כ`other`.

`request-cut` הוא בטבלה זו כי `failproofai jev status` סכומי זה עם בקי, וכי גם זה עוזב כל דחייה עומדת. זה הסיבה היחידה כאן שאומרת כלום לגבי הספק שלך: הבקשה הגיעה ו-Jev ענה אותה. בשום ריו עבור כל שורה מעליה, התשובה עדיין סופרת — Jev של דחייה משלו או אזהרה חלה על גבי תוצאת ה-regex במקום להיזרקו. אז מהלך שלהם אומר קריאות מגיעות המהערך גדול מדי לשליחה שלימה, לא את הספק שלך endpoint הוא רוע, וטופין credits או שינוי ה-URL לא יעביר את המספר.

## כאשר Jev ענה, אבל לא על כל הקריאה

שתיים יותר דברים יכול להתרחש, וגם ניהולם לא על Jev כושל לענות. שתיהן על כמה מהקריאה, או מהשיחה, נכנסו לקשר אחד.

**חלק מהקריאה עצמה לא נכנס.** קריאת כלי הוא שלח בתוך תקציב קבוע, ואחד גדול — גדול מאוד `Write`, גדול MCP גוף, פקודה cushioned שלא cap — הוא שלח עם מה זה מתאים. Jev עדיין עונה, והתשובה עדיין סופרת: דחייה משלו או אזהרה חלה כרגיל. מה זה לא יכול לעשות הוא **נקה** כלום, כי פסק נתון על חלק מקריאה לא פסק על קריאה. אז כל מדיניות דחייה עומדת, והקריאה הוא רשום כ fallback עם הסיבה `request-cut`, אשר `failproofai jev status` סכומים לצד הסיבות למעלה. הכלל זה נותן לך: ביצוע קריאה גדול יותר יכול לעלות לו קליאנסים, וכן לעולם קנה אחד.

**הודעה לא נכנסה.** הנושא ארוך אתה הדבקת, ההודעה האחרונה של הסוכן, או הנושא מהערך קבוע שלו עצמו היה כבר capped. **כלום לא משתנה**: קריאה הוא שיפוט, נקה ורשום בדיוק כמו כל אחר, וזה לא סופר כ fallback. אורך מה אתה הקלד לעולם מחליט פסק, וקצץ לא יכול ייצור הסכמה: איפה הנושא הגיע כבר capped, לך לא ביקש את זה כבר תופס ללא להיות מסקנה שיכול היה להיות משוך מזה בכלל, במקום להיות אחד.

הקו בין השתיים הוא שכתב את הטקסט. הקריאה היא של הסוכן, וכלל שתן אורך שלו סיבה לחסור חומרה תהיה כלל הסוכן יכול להשתמש; הנושא שלך הוא שלך, וטיפול אורך שלו ככל אחד רק אי פעם עונש הדבקה ס"ה או ערימת עקבות.

## מה עוזב המכונה

עבור כל קריאת כלי Jev הערך, קריאה אחת הולכת לספק, בעל:

- קריאת כלי עצמו, עם סודות כגון מפתחות API, נושאי סוגים וtasks `KEY=` הקצב;
- הנושאים האחרונים שאתה הקלדת, עם טקסט הארנס של הסוכן הוסיף הוסר;
- הודעת ההודעה האחרונה לפני הנושא המאוחר שלך, התווית כסוכן-כתובים;
- עובדות מחושבות מקומית, כגון האם נתיב נמצא בתוך הפרויקט — את אחד הסשן היה בנושא בראשון הוקבע קריאה, [פנו עבור הסשן](/he/reference/jev-intent#the-project-root) — והענף git הנוכחי.

זה הולך רק ל-endpoint בתצורה שלך, תחת המפתח שלך.

## כבה את זה

```bash
failproofai jev remove
```

זה מוחק `~/.failproofai/jev.json`. מהקריאה הבאה לכלי, hooks מריץ את מדיניויות ה-regex בדיוק כמו לפני. ה-per-session חנויות תחת `~/.failproofai/state/semantic/` (רשום נושאים ב`sessions/`, פרויקט שורשים ב`roots/`) הם שמאלה במקום וגיל החוצה. כדי להפסיק להשאל Jev אבל שמור את התצורה, השתמש `failproofai jev setup --mode off` במקום.

## ציון פקודה

| Command | Outcome |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | תצורה אותו בפקודה אחת; הספק בא מ-host של ה-URL |
| `failproofai jev --url <url> --token <token>` | אותו דבר, עם המפתח בשורת הפקודה — הרשימה ותהליך הרשימה שלך ראה אותו |
| `failproofai jev setup --provider <kind> --key-stdin` | כתוב את התצורה מ-stdin של צינור מפתח |
| `failproofai jev setup --provider <kind>` | אותו דבר, בהנחת מפתח בשאילתה מוסווית |
| `failproofai jev setup --key-from-env` | אל מטמון מפתח; קריאה `FAILPROOFAI_JEV_API_KEY` לכל סשן |
| `failproofai jev setup --mode observe` | מצב סוויץ (`enforce`, `observe` או `off`), שמירת המפתח המאוחסן |
| `failproofai jev setup --model <id>` / `--base-url <url>` | דריס את המודל או API base; `default` נקה הדריס |
| `failproofai jev setup --timeout-ms <n>` | שנה לכל-קריאה תקציב |
| `failproofai jev status [--json]` | תצורה, הרשאות ופעילות אחרונה; לעולם המפתח |
| `failproofai jev test [--json]` | קריאה חיה אחת: הזמן ההשהייה וגרסה שענה |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | מודל IDs שה-endpoint `/models` דיווחים, סימון זה מוגדר |
| `failproofai jev remove` | מחק את התצורה; Jev הוא כבוי |
