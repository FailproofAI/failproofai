זהו ההנחיה לספק ותצורה עבור [מדיניות Jev](/he/policies/jev) עם המפתח שלך. מדיניות Regex משווה מחרוזות. הן לא יכולות להבדיל בין `rm -rf build/` שביקשת לבין `rm -rf ~` שהחליק לתוך תוכנית, כך שהן חוסמות יותר מדי במקום אחד ויותר מדי מעט במקום אחר. **Jev**, המסווג של TypeSafe, קורא את הקריאה מול מה שבעצם ביקשת וענה על סט שאלות כן/לא עליה בקריאה אחת מהירה.

עם נקודת הקצה וה-Jev שלך וחשמום המפתח שלך, Failproof AI שאל את Jev לגבי כל קריאת כלי **לצד** מדיניות regex, לעולם לא במקום שלהן:

- ה-deny של מדיניות **קשה** הוא סופי. Jev לא יכול לחסל אותו. כל מדיניות היא קשה אלא אם כן היא מסומנת במפורש כ"ניתנת לבדיקה" וקוראת לבדיקות Jev המכסות אותה, ולכן מדיניות מותאמת, חבילה או Cloud שלא אומרת דבר היא קשה, והשומר הגנה עצמית שתמיד פועל הוא תמיד קשה.
- ה-deny של מדיניות **ניתנת לבדיקה** עשוי להיות חסול, אך רק כאשר Jev נשאל לגבי הדאגה המדויקת שמדיניות זו מכסה וענה "אין כאן שום דבר" או "המשתמש ביקש את זה". בדיקה שמוצאת את הדאגה כאמיתית, כאשר המשתמש לא ביקש את הקריאה, שומרת על ה-deny — אפילו כאשר הפסק שלה הוא רק אזהרה, מכיוון שלפני קריאת כלי אזהרה לא עוצרת את ה-agent. וכאשר בדיקה זו היא כזו שיכולה להחזיר deny (חשיפת סוד, גניבת אישורים, מחיקה הרסנית, ...), שום דבר לא מיוחסן בקריאה זו.
- בלוק עדיין יכול להיות **אזהרה** כאשר הקריאה היא שלב של המשימה שנתת ואינה מגיעה רחוק יותר: Jev משנה את ה-deny שלו לאזהרה, והאזהרה הזו — תיאור מה בעצם לא בסדר עם הקריאה — מחליפה את החסימה של המדיניות.
- Jev יכול גם להזהיר או להחזיר deny בכוחות עצמיים, לפי נזק שאף regex לא מתאר.
- אם Jev לא יכול לענות (timeout, rate limit, שגיאת שרת, אין קרדיט, גרסת מודל בלתי צפויה), הקריאה הזו מקבלת את תוצאת ה-regex, בדיוק כמו ללא Jev.
- Jev לעולם לא הופך קריאה מחופזקת יותר מהמדיניויות שלך לבדן אלא אם קרא את כל הקריאה ונשאל לגבי הדאגה המדויקת. כל דבר פחות — קריאה גדולה מדי להשליח כמכלול, injection חשוד — מטיל רכיסות ושומר על כל deny.

<Note>
ללא תצורת Jev כלום לא משתנה: hooks מריצים את מדיניות regex בדיוק כפי שתמיד. התצורה היא כל הבחירה.
</Note>

<Tip>
ב-FailproofAI Cloud? אתה לא צריך מפתח משלך: מכונה המחוברת עם מפתח שנושא `jev:evaluate` יכולה להשתמש ב-Jev בתוכנית של הארגון שלך. ראה [Jev דרך FailproofAI Cloud](/he/reference/jev-cloud).
</Tip>

## לפני שתתחיל

התקן **failproofai 1.0.8-beta.0 או חדש יותר** וחבר את ה-hooks שלו ל-[harness נתמך](/he/reference/harnesses) על המכונה שבה ה-agent שלך פועל. עקוב אחר ה-[quickstart](/he/start/quickstart) אם זו מכונה חדשה, או [הגדר אכיפה מקומית](/he/start/setup#enforce-locally) אם אתה לא משתמש ב-Cloud. בדוק את ה-CLI המותקן עם `failproofai --version`.

קבל API key מספק להלן, או הכן endpoint תואם ואת ה-key שלו. Jev בודק קריאות כלי בשם בשער `PreToolUse` או `PermissionRequest`. הוא יכול להנפיק פסק דין משלו, אך חיסול הנכחי של deny של מדיניות דורש גם מדיניות מותקנת המסומנת [ניתנת לבדיקה](/he/policies/authority). דחיות מדיניות קשות נשארות סופיות.

## בחר ספק

Jev ניתן להגעה דרך חמש נתיבים. הבא key לאחד מהם.

| Provider | `--provider` | Endpoint | Default model | Notes |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Exact version pin. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | בקשות מועברות רק לנקודות קצה של שמירת אפס נתונים, ללא fallback לספק אחר. דיווחים בגרסה מתוארכת כגון `typesafe/jev-1.13-20260917`. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | מכנה את Jev רק בכינוי, כך שהגרסה המענה נרשמת כ-unverified. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | צריך `--account-id`. כשש קריאות לשנייה לכל key נמדדו לפני HTTP 429. |
| Your own endpoint | `custom` | `<base-url>/systemone` | `jev-1.13.0` | כל endpoint המקבל את גוף הבקשה של TypeSafe וקורא לדעת איזה מודל ענה. `https` בלבד; `http` תקני ללוקלהוסט (`localhost`, `127.0.0.1`, `::1`) מתקבל לבדיקה מקומית. |

<Warning>
עם התכונה bring-your-own-key משלה של Vercel, בקשה שלא הצליחה מחדשת בשקט עם ה-credentials של Vercel. אם אתה צריך שכל קריאה תחויב, ותתראה, לחשבון TypeSafe שלך בלבד, השתמש ב-TypeSafe ישירות.
</Warning>

## הגדר את זה

פקודה אחת, ה-endpoint והמפתח. התחל בספח `observe` כדי שתוכל לבחון את הפסקי דין של Jev בזמן שהמדיניויות הקיימות ממשיכות להחליט על קריאות:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### ה-URL בוחר את הספק

אתה לא צריך לקרא לספק: ה-**host** של ה-URL הוא מי זה.

| URL host | Provider | Also needs |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| any other host | `custom` | — the URL you gave is the base URL |

שלוש דברים נובעים מזה:

- **URL שהוא API של הספק עצמו לא כותב override.** `--url https://api.typesafe.ai/v1` מייצר בדיוק את התצורה שיש `--provider typesafe` היה יוצר. תן נתיב שונה או host על ספק ידוע והוא נשמר כ-base URL, כפי ש-`--base-url` היה שומר אותו.
- **`--provider` עדיין עוקף את ההסקה**, שזו הדרך להגיע לפרוקסי המדבר ב-API של ספק מ-host משלך: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **`--provider` שסותר את ה-host מסורב**, לא נחזה. `--provider openrouter --url https://api.typesafe.ai/v1` לא כותב כלום ומגיד למה: שתי ההיות לא מסכימות לגבי היכן ה-key שלך עומד להיות שלוח. אותו זוג מסורב מ-`jev setup --base-url` ומ-dashboard של Jev settings. (`--provider custom` איננו סתירה — זה אומר "התייחס ל-URL זה כ-itself" — פחות על host של Cloudflare, שהendpoint לכל-חשבון שלו custom route לא יכול להגיע.)

`--url` מאומת בדיוק כמו `baseUrl` בקובץ התצורה, ודחוי באותן מילים: `https`, או `http` תקני ללוקלהוסט (`localhost`, `127.0.0.1`, `::1`) בכל מצב. סיכון: כלום לא מאמת שרת loopback, אז בעוד שהוא למטה תהליך מקומי אחר יכול לקחת את הפורט שלו וענה; השתמש ב-`https` מחוץ לבדיקה מקומית.

### המפתח

צינור בו עם `--key-stdin`, או הפעל את הפקודה בטרמינל ללא אתה והדבק את המפתח בהנחיה מסוכסכת. כך או כך זה הולך ישר לקובץ התצורה ולעולם לא מודפס בחזרה.

  </Tab>
  <Tab title="OpenRouter">

  </Tab>

`failproofai jev setup` לוקח את אותו דגלים והוא הלונגהנד עבור כל זה: `setup --provider <kind>` כאשר אתה מעדיף לקרא לספק מאשר ל-URL.

### `--token`, וכמה זה עולה

`--token <token>` שם את המפתח בשורת הפקודה, שהוא הדרך המהירה ביותר להגדיר מכונה וההיגיון היחיד שמשאיר את המפתח בכל מקום מלבד קובץ התצורה:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
טיעון של שורת פקודה נמצא בקובץ ההיסטוריה של shell שלך אחרי כן, וכאשר הפקודה פועלת היא בתוך רשימת התהליכים — ניתנת לקריאה מ-`/proc` על ידי כל דבר פועל כמוך. `setup` אומר כך בכל פעם ש-`--token` משמש. עדיף `--key-stdin` במכונה שתחלוק, בסשן מוקלט, או בכל מקום שקובץ ההיסטוריה מסונכרן; סובב מפתח שעברת בדרך זו אם זה חשוב.
</Warning>

`--token`, `--key-stdin` ו-`--key-from-env` זוכות בהדדיות: תן אחד.

ואז שלח בקשה חיה קטנה אחת לבדיקת המפתח, ה-endpoint ואיזה Jev ענה:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` יוצא 1, ואומר כך בכותרת שלו, כאשר התשובה מגיעה אחרי timeout (כל hook היה fallback ל-regex כ-`timeout`) או עונה לשאלת הבדיקה שלו בצורה שגויה.

Hooks קורים את התצורה בכל קריאת כלי, ולכן היא חלה מהבאה. אין כלום שיש להפעיל מחדש, עם או ללא daemon.

## בדוק מה זה עושה

```bash
failproofai jev status
failproofai jev status --json
```

`status` מציג את הספק, endpoint, מודל, מצב, קובץ התצורה והרשויות שלו, ולעולם לא את המפתח. מתחתיו זה מסכם פעילות אחרונה: כמה קריאות Jev הערך, כמו פי שהוא חזר ל-regex ולמה, הlatency שלו, ואיזה מדיניויות ניתנות לבדיקה הוא טיהר.

## אמת קריאה אמיתית

התחל סשן חדש ב-agent המחובר. בקש ממנו להשתמש בכלי קריאת הקובץ שלו ב-`README.md` ודווח על הכותרת. אשר כי הסשן מכיל את קריאת הכלי הזו, ואז הרץ `failproofai jev status` שוב: כמות הקריאות המוערכות האחרונות שלו צריכה להיות מוגברת. פתח **Policies → Activity** ב-[local dashboard](/he/reference/local-dashboard#review-policy-activity) כדי לבחון את פסק הדין של Jev של הקריאה ואת המצב. בספח observe, תוצאת המדיניות עדיין החליטה על הקריאה. אישור מופיע רק אם מדיניות ניתנת לבדיקה תאמה וJev טיהר כל בדיקה בשם; קריאה רגילה אולי אין לה מדיניות לטיהור.

## Observe mode

`enforce` הוא ברירת המחדל. כדי להצפות את Jev בלי להרשות לו לשנות כל החלטה, עבור ל-`observe`: Jev עדיין נשאל וההיסטוריה שלו נרשמת, אך תוצאת ה-regex היא מה שמוגבל.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` שומר על התצורה — ה-endpoint והמפתח — וחוסם את בקשות Jev: hooks מריצים את מדיניות regex בדיוק כמו ללא תצורה, ו-`failproofai jev status` אומר "off (switched off)". חזור עם `--mode observe` או `--mode enforce`.

הרצה מחדש של `setup` לאותו ספק שומרת את המפתח שנשמר, אז החלפת מצב היא דגל אחד. החלפת ספק מתחילה מחדש ושואלת עבור המפתח של הספק הזה. כך גם `--base-url` שמעביר בקשות ללוקלהוסט שונה: מפתח מוזן נשלח רק להוסט שהוא ניתן עבור, או ל-API משלו של הספק.

## קובץ התצורה

הכל חי בקובץ אחד, `~/.failproofai/jev.json`, כתוב על ידי `setup`:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Field | Meaning |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` או `custom` — או `failproofai`, שהמפתח שלו מגיע מחיבור FailproofAI Cloud במקום מקובץ זה (ראה [Jev דרך FailproofAI Cloud](/he/reference/jev-cloud)). |
| `apiKey` | נשלח כ-`Authorization: Bearer <key>`. |
| `baseUrl` | נדרש עבור `custom`; מחליף את base API של הספק אחרת. חייב להיות `https`. `http` תקני ל-`localhost` מתקבל רק עם `mode: observe`: כלום לא מאמת שרת מקומי, אז בעוד שה-proxy שלך למטה כל תהליך במכונה, כולל ה-agent נדון, יכול לענות במקומו. |
| `accountId` | Cloudflare בלבד: 32 תווים hex קטנים. |
| `model` | מחליף את מזהה מודל ברירת המחדל של הספק. מזהה גרוש חייב לשם Jev 1.13. ערך המעוצב כמו API key מסורב (ולא חוזר), אז מפתח המודבק ל-`--model` לעולם לא נשמר או נשלח כמודל. |
| `timeoutMs` | כמה זמן קריאת כלי מחכה ל-Jev לפני שימוש בתוצאת ה-regex. 100–10000, ברירת מחדל 3000. |
| `mode` | `enforce` (ברירת מחדל), `observe`, או `off` (שמור על התצורה, הרץ לא Jev). |

שלוש כללים מגנים עליו:

- **Owner-only.** הוא כתוב עם הרשויות `0600`. עותק שכל משתמש או קבוצה אחרת יכול לקרוא או לכתוב **מסורב**, ו-hooks חוזרים ל-regex עד שאתה מריץ `chmod 600 ~/.failproofai/jev.json` או `setup` שוב. הספרייה נבדקת גם: `~/.failproofai` חייב להיות **not writable** על ידי כל אחד אחר, כי מי שיכול לכתוב שם יכול להחליף את הקובץ כל הרשויות שלו. `setup` מוציא את בצי הכתיבה האלה אם הוא מוצא אותם. `failproofai jev status` אומר כאשר תצורה סורבת ומציג את ה-endpoint שהקובץ מכנה: מישהו אחר יכול היה לשנות את זה, אז בדוק שזה שלך לפני שאתה `chmod`. הרצה מחדש של `setup` בקובץ כזה נושא את המפתח המוזן שלו רק ל-API של הספק; כל endpoint אחר שהוא קורא צריך את המפתח שוב (`--key-stdin`), או `--base-url default` כדי לשלוח בקשות בחזרה לספק.
- **Global only.** リポジトリ יכול הפעל Jev, לעצור אותו בendpoint אחר או לבחור בmodele: `.failproofai/jev.json` בתוך פרויקט מתוכנן, והספק, URL, מודל וחשבון id נקראים רק מקובץ זה — לעולם לא מהסביבה, שהגדרות agent של מאגר יכול להגדיר. (`FAILPROOFAI_HOME` איננו דרך סביב זה: זה מעביר את כל הספרייה failproofai, המדיניויות שלך כלול, במקום להפנות Jev על עצמו.)
- **המפתח לבדו עשוי להגיע מהסביבה.** אם הקובץ אין `apiKey`, `FAILPROOFAI_JEV_API_KEY` מספק זה לסשן זה (`setup --key-from-env` כותב קובץ כזה). הוא לעולם לא מחליף מפתח שהקובץ מחזיק, והוא לא יכול להדליק Jev ללא הקובץ. כאשר המשתנה לא הוגדר, Jev הוא פשוט off עבור shell זה: `failproofai jev status` אומר כך, יוצא 0 ועוזב את התצורה לבדה (`status --json` דיווחים `"status": "key-missing"` עם `"reason": "no-env-key"`). ה-`failproofaid` daemon לא רואה את הסביבה של shell שלך, אז במכונה הגדרת עם `failproofai config`, שמור את המפתח בקובץ.

## איזה Jev עונה

סף ההחלטה של Failproof AI כיילו ב-Jev 1.13, אז תשובה משמשת רק כאשר היא מגיעה מהמשפחה הזו: `jev-1.13.x`, או OpenRouter של `typesafe/jev-1.13-<date>`. כאשר ספק קורא ל-Jev רק בכינוי ודיווחים לא גרסה (Vercel, וCloudflare כאשר זה לא אומר), התשובה משמשת ונרשמת כ-unverified. `custom` endpoint חייב לדווח בmodele שענה; החריג היחיד הוא unversioned `--model` כינוי אתה שנויות עבורו, שנחזר, נרשם כ-unverified באותו אופן. תשובה דיווח כל גרסה אחרת, או תשובה `custom` דיווח לא, איננו משומש: הקריאה הזו חוזרת ל-regex עם הסיבה `model-mismatch`.

## כשJev לא יכול לענות

כל אחד מהם חוזר לתוצאת ה-regex לקריאה זו ונרשם עם הסיבה שלו, אשר `failproofai jev status` סכום:

| Reason | Cause |
| --- | --- |
| `timeout` | אין תשובה בתוך `timeoutMs`. |
| `http-429` | הספק קצב-מגביל את המפתח. |
| `rate-limited` | מחדל של Failproof AI שלו קצב-מגביל החזיק את הקריאה בחזרה לפני שליחה: 5 בקשות לשנייה, בפרצים של עד 5, ואף אחד לרגע אחרי הספק עונה `429`. לא הספק. |
| `http-500`, `http-502`, `http-503`, … | שגיאת שרת בספק. הסטטוס המדויק נרשם. |
| `out-of-credits` | HTTP 402: חשבון הספק אין קרדיט שמאל. |
| `provider-refused` | HTTP 402 מCloudflare קריאה "Model execution failed (Payment error)": הספק סירב לנהל את המודל בבקשה זו. בדרך כלל לא הוצאה, אז טופס יהיה לא לזוז את זה. |
| `http-401`, `http-403` | המפתח נסורב. |
| `http-404` | כלום לא משרת ב-`<base>/systemone`, אז ה-base URL הוא שגוי — `/systemone` מוספת אליו, וכל ספק משרת אותו בשורש הגרסה שלו. `failproofai jev models` מציג מה ה-endpoint משרת בעצם. |
| `network` | ה-endpoint לא יכול להיות מגיע. |
| `http-301`, `http-302`, `http-307`, `http-308` | ה-endpoint ענה עם הפניה. הפניות לעולם לא עוקבות, אז התשובה מגיעה רק מ-URL בתצורה שלך; קבע `--base-url` ל-URL הסופי. |
| `malformed` | ה-endpoint ענה, אך לא עם תשובת Jev — גוף שאיננו JSON, או אחד ללא תשובות בו. |
| `cloudflare-error`, `cloudflare-incomplete` | מעטפת Cloudflare דיווחה כשל, או עבודה שלא סיימה. |
| `model-mismatch` | גרסת Jev אחרת מ-1.13 ענה, או `custom` endpoint לא אמר איזה מודל ענה. |
| `request-cut` | **לא הפסקה.** Jev ענה; הוא הראה רק חלק של הקריאה, אז התשובה שלו טיהרה כלום. ראה [כשJev ענה, אך לא על כל הקריאה](#when-jev-answered-but-not-on-the-whole-call). |

`failproofai jev status` יכול להראות כמה סיבות נדירות יותר, כגון `upstream-error` (התשובה נשאה את השגיאה של הספק עצמו) או `config`, וסכום כל סיבה שהוא לא יכול לשם כ-`other`.

`request-cut` נמצא בטבלה זו מכיוון ש-`failproofai jev status` סכום אותו עם השאר, וכי זה גם עוזב כל deny עומד. זו הסיבה היחידה כאן שאומרת כלום לגבי הספק שלך: הבקשה הגיעה וJev ענה. בניגוד לכל שורה מעליה, התשובה הזו עדיין סופרת — Jev שלו deny או אזהרה חל על גבי תוצאת ה-regex במקום לשלוח לאשפה. אז ריצה של אלה אומר קריאות מגיעות המדחה גדול מדי שיש לשלוח כמכלול, לא שה-endpoint שלך אינו בריא, וטופס קרדיט או שינוי ה-URL לא יוציא את המספר.

## כשJev ענה, אך לא על כל הקריאה

שתי דברים עוד יכול לקרות, וגם כלום לא Jev כשל לענות. שתיהן על כמה הקריאה, או של השיחה, התאימה לבקשה אחת.

**חלק מהקריאה עצמה לא התאימה.** קריאת כלי נשלחת בתוך תקציב קבוע, ואחד חריג — כתובה גדולה מאוד, גוף MCP ענק, פקודה מרופדת לקחת — נשלח עם מה שהתאים. Jev עדיין עונה, והתשובה שלו עדיין סופרת: שלו deny או אזהרה חל כרגיל. מה שזה לא יכול לעשות הוא **טיהור** דבר מה, כי פסק דין על חלק של קריאה איננו פסק דין בקריאה. אז כל מדיניות deny עומד, והקריאה נרשמת כ-fallback עם הסיבה `request-cut`, אשר `failproofai jev status` סכום לצד הסיבות מעלה. הכלל זה נותן לך: ביצוע קריאה גדולה יותר יכול לעלות אותה clearances, ולעולם לא קנות אחד.

**הודעה לא התאימה.** בקצר שלחת, ההודעה האחרונה של ה-agent, או בקצר זה evaluator משלו יחסן כבר סגור. **כלום לא משתנה**: הקריאה נשפטת, בטוחה ונרשמת בדיוק כמו כל אחד אחר, והוא לא סופר כ-fallback. אורך מה שאתה טיפול אי פעם החליטה פסק דין, וקט לא יוצר הסכמה: איפה בקצר הגיע כבר סגור, "לא ביקשת את זה" מפסיק להיות מסקנה שיכלו להיות נמשכות מזה בכלל, במקום להיות אחד.

הקו בין השניים הוא מי כתב את הטקסט. הקריאה היא של ה-agent, וכלל שתן אורך שלה חיסול חומרה היה כלל ה-agent יכול להשתמש; הבקצר שלך הוא שלך, וטיפול אורך שלה כסימן רק כל פעם מענישה הדבקה של פרטון או stack trace.

## מה עוזב את המכונה

לכל קריאת כלי Jev משפט, בקשה אחת הולכת לספק שלך, נושא:

- קריאת הכלי עצמה, עם סודות כגון API מפתחות, bearer tokens ו-`KEY=` מקצות redacted;
- ה-prompts אחרון שלך טיפול, עם טקסט harness של ה-agent שלך הוסיף הוסרו;
- הודעת ה-agent האחרונה לפני הטיפול האחרון שלך, קרא כ-agent-written;
- עובדות מחושבת מקומי, כגון אם נתיב יש פנימי לפרויקט — האחד הסשן היה בראשון עם בדיקה קריאה, [pinned לסשן](/he/reference/jev-intent#the-project-root) — ובעומק הנוכחי.

זה הולך רק ל-endpoint בתצורה שלך, תחת המפתח שלך.

## כבה את זה

```bash
failproofai jev remove
```

זה מוחק `~/.failproofai/jev.json`. מהקריאה הבאה, hooks מריצים את מדיניות regex בדיוק כמו קודם. ה-per-session חנויות תחת `~/.failproofai/state/semantic/` (prompts נרשם בתוך `sessions/`, project roots בתוך `roots/`) יוח בעמדה וגיל. כדי להפסיק לשאול Jev אך שמור על התצורה, השתמש `failproofai jev setup --mode off` במקום.

## Command reference

| Command | Outcome |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | תצור אותו בפקודה אחת; הספק מגיע מ-host של ה-URL |
| `failproofai jev --url <url> --token <token>` | זהה, עם המפתח בשורת הפקודה — ההיסטוריה שלך וה-process list רואים את זה |
| `failproofai jev setup --provider <kind> --key-stdin` | כתב את התצורה מ-key צינור ב-stdin |
| `failproofai jev setup --provider <kind>` | זהה, שואל עבור המפתח בהנחיה מסוכסכת |
| `failproofai jev setup --key-from-env` | אל תאזין מפתח; קרא `FAILPROOFAI_JEV_API_KEY` לכל סשן |
| `failproofai jev setup --mode observe` | החלף מצב (`enforce`, `observe` או `off`), שמור על המפתח המוזן |
| `failproofai jev setup --model <id>` / `--base-url <url>` | Override את המודל או API בסיס; `default` מחק את ה-override |
| `failproofai jev setup --timeout-ms <n>` | שנה את תקציב ה-per-call |
| `failproofai jev status [--json]` | תצורה, הרשויות וכמות אחרונה; לעולם לא את המפתח |
| `failproofai jev test [--json]` | בקשה חיה אחת: latency וגרסה שענה |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | מזהה המודל כי endpoint של `/models` דיווחים, סימון אחד שנקבע |
| `failproofai jev remove` | מחק את התצורה; Jev הוא off |
