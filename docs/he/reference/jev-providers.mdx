זהו החומר ההתייחסות לספק וקביעת התצורה של [Jev policies](/he/policies/jev) עם המפתח שלך. מדיניות Regex משווה מחרוזות. הן לא יכולות להבדיל בין `rm -rf build/` שביקשת ל`rm -rf ~` שהחליק לתכנית, כך שהן חוסמות יותר מדי במקום אחד והשקט מדי במקום אחר. **Jev**, מסווג של TypeSafe, קורא את הקריאה מול מה שאתה בעצם ביקשת ועונה על קבוצה של שאלות כן/לא על זה בקריאה אחת מהירה.

כשיש לך Jev endpoint שלך וקביעת מפתח, Failproof AI שואל את Jev על כל קריאת כלי **ובמקביל** למדיניות regex, לעולם לא במקום שלהן:

- הדחיה של מדיניות **hard** היא סופית. Jev לא יכול לנקות אותה. כל מדיניות היא hard אלא אם היא מסומנת במפורש כ-reviewable ושם את בדיקות Jev שמכסות אותה, כך שמדיניות מותאמת, pack או Cloud שלא אומרת כלום היא hard, וה-always-on self-protection guard הוא תמיד hard.
- הדחיה של מדיניות **reviewable** עשויה להיות מנוקה, אך רק כאשר Jev נשאל על הדאגה המדויקת שהמדיניות מכסה וענה "כלום כאן" או "המשתמש ביקש את זה". בדיקה שמוצאת את הדאגה אמיתית, כשהמשתמש לא ביקש את הקריאה, משמרת את הדחיה — אפילו כשהפסק שלה הוא רק אזהרה, כי לפני קריאת כלי אזהרה לא עוצרת את הסוכן. וכשבדיקה זו היא אחת שיכולה לדחות (חשיפת סוד, גניבת הצפנים, מחיקה הרסנית, ...), כלום לא מנוקה בקריאה הזו.
- בלוק עדיין עשוי להפוך ל**אזהרה** כאשר הקריאה היא שלב של המשימה שנתת ולא מגיע הלאה: Jev משנה את הדחיה שלו לאזהרה, והאזהרה הזו — המתארת מה בעצם לא בסדר בקריאה — מחליפה את הבלוק של המדיניות.
- Jev יכול גם להזהיר או לדחות בעצמו, בשביל נזק שאף regex לא מתאר.
- אם Jev לא יכול לענות (timeout, rate limit, server error, no credits, unexpected model version), הקריאה הזו מקבלת את תוצאת regex, בדיוק כמו ללא Jev.
- Jev לא יעשה קריאה יותר permissive מהמדיניות שלך בלבד אלא אם קרא את הקריאה כולה והשאל על הדאגה המדויקת. כל דבר אחר — קריאה גדולה מדי לשליחה כחלוטין, injection חשוד — משוך את ההרשאות ושומר על כל דחיה.

<Note>
ללא קביעת Jev כלום לא משתנה: hooks מריצים את מדיניות regex בדיוק כמו תמיד. הקביעה היא הcopt-in כולו.
</Note>

<Tip>
ב-FailproofAI Cloud? אתה לא צריך מפתח משלך: מכונה המחוברת עם מפתח שנושא `jev:evaluate` יכולה להשתמש ב-Jev בתכנית של הארגון שלך. ראה [Jev through FailproofAI Cloud](/he/reference/jev-cloud).
</Tip>

## לפני שאתה מתחיל

התקן **failproofai 1.0.8-beta.0 או חדש יותר** וצרף את ה-hooks שלו ל-[supported harness](/he/reference/harnesses) על המכונה שבה הסוכן שלך רץ. עקוב אחר [quickstart](/he/start/quickstart) אם זו מכונה חדשה, או [הגדר local enforcement](/he/start/setup#enforce-locally) אם אתה לא משתמש ב-Cloud. בדוק את ה-CLI שהותקן עם `failproofai --version`.

קבל API key מספק למטה, או יש endpoint תואם ו-key שלו מוכן. Jev בודק קריאות כלי בשם ב-`PreToolUse` או `PermissionRequest` gate. הוא יכול להוציא פסק דין משלו, אך ניקוי דחיה קיימת של מדיניות דורש גם מדיניות מותקנת המסומנת [reviewable](/he/policies/authority). דחיות מדיניות hard נשארות סופיות.

## בחר ספק

Jev זמין דרך חמש נתיבים. תביא מפתח לאחת מהן.

| Provider | `--provider` | Endpoint | Default model | Notes |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Exact version pin. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | Requests are routed to zero-data-retention endpoints only, with no fallback to another provider. Reports a dated version such as `typesafe/jev-1.13-20260917`. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Names Jev only by an alias, so the answering version is recorded as unverified. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | Needs `--account-id`. About six calls a second per key were measured before HTTP 429. |
| Your own endpoint | `custom` | `<base-url>/systemone` | `jev-1.13.0` | Any endpoint that accepts TypeSafe's request body and reports which model answered. `https` only; plain `http` to a loopback host (`localhost`, `127.0.0.1`, `::1`) is accepted for local testing. |

<Warning>
עם התכונה bring-your-own-key שלך של Vercel, בקשה שנכשלה מחדש בשקט עם הפרטי הצביעו של Vercel. אם אתה צריך כל קריאה חויבת, וראה, על ידי החשבון TypeSafe שלך בלבד, השתמש ב-TypeSafe ישירות.
</Warning>

## הגדר את זה

פקודה אחת, ה-endpoint וה-key. התחל ב-`observe` mode כדי שתוכל לבדוק את פסקי הדין של Jev בעוד המדיניות הקיימת ממשיכה להחליט על קריאות:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### ה-URL בוחר בספק

אתה לא צריך לשם את הספק: ה-**host** של ה-URL זה איזה.

| URL host | Provider | Also needs |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| any other host | `custom` | — the URL you gave is the base URL |

שלוש דברים נובעות מזה:

- **URL שהוא ה-API שלעצמו של הספק לא כותב override.** `--url https://api.typesafe.ai/v1` מייצר בדיוק את הקביעה שהיא `--provider typesafe`. תן נתיב או host שונה בספק ידוע והוא מאוחסן כ-base URL, כמו `--base-url` היה אוחסן.
- **`--provider` עדיין משקף את ההגיון**, שהיא איך אתה מגיע proxy שמדברת ה-API של ספק מ-host משלך: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **`--provider` שסותר ה-host מסורב**, לא נחשמו. `--provider openrouter --url https://api.typesafe.ai/v1` כותב כלום ואומר למה: שתי ההיקפים לא מסכימים היכן המפתח שלך עומד להישלח. אותו זוג מסורב מ`jev setup --base-url` ומה-dashboard של הגדרות Jev. (`--provider custom` אינה סתירה — זה אומר "התייחס ל-URL הזה כאל עצמו" — חוץ מ-Cloudflare's host, שלא יכול להגיע endpoint לכל חשבון שלאחר custom.

`--url` מאומת בדיוק כמו `baseUrl` בקובץ הקביעה, מסורב באותן מילים: `https`, או plain `http` ל-loopback host (`localhost`, `127.0.0.1`, `::1`) בכל mode. סיכון: כלום לא מאמת שרת loopback, כך שבעוד הוא למטה תהליך מקומי אחר יכול לקחת את היציאה שלו וענה; השתמש `https` מחוץ לבדיקה מקומית.

### המפתח

צנור אותו עם `--key-stdin`, או הפעל את הפקודה בטרמינל ללא זה והדבק את המפתח בבקשה כיסוי. כל שהוא הולך ישר לקובץ הקביעה ולא מעולם הודפס חזרה.

  </Tab>

`failproofai jev setup` לוקח אותו flags וזה הlonghand לכולו: `setup --provider <kind>` איפה שאתה רוצה שם את הספק מאשר את ה-URL.

### `--token`, וכמה זה עלות

`--token <token>` שם את המפתח על שורת הפקודה, שהיא הדרך המהירה ביותר להגדיר מכונה וה-only spelling שנוקי את המפתח בכל מקום אך הקובץ של הקביעה:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
טיעון שורת הפקודה נמצא בקובץ ההיסטוריה של הקליפה שלך בעדיין, ובעוד הפקודה רצה זה בתהליך list — קריא מ-`/proc` על ידי כלום הרץ כמוך. `setup` אומר כל פעם `--token` משמש. אנוח `--key-stdin` על מכונה שאתה משתף, בתוך session מוקלטת, או בכל מקום קובץ ההיסטוריה מסונכרן; סובב מפתח שיש לך עביר דרך זו אם זה חשוב.
</Warning>

`--token`, `--key-stdin` ו-`--key-from-env` הם בעלות הדדית: תן אחד.

אחרי זה שלח בקשה אחת חיה קטנה כדי לבדוק את המפתח, ה-endpoint וזה Jev ענה:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` יציאה 1, ואומר בכותרת שלה, כאשר התשובה מגיעה אחרי ה-timeout (כל hook היה fallback ל-regex כ-`timeout`) או תשובה שלה לשאול בצורה הלא נכון.

Hooks קורא את הקביעה בכל קריאת כלי, כך שזה חל מהבא. אין כלום לשנות מחדש, עם או ללא ה-daemon.

## בדוק מה זה עושה

```bash
failproofai jev status
failproofai jev status --json
```

`status` מציג את הספק, endpoint, model, mode, קובץ הקביעה והרשאות שלו, ולא מעולם המפתח. להלן זה מסכם פעילות אחרונה: כמה קריאות Jev הערכנו, כמה פעמים זה חזר ל-regex ולמה, שלו latency, ואילו מדיניות reviewable זה ניקה.

## אימות קריאה אמיתית

התחל session חדש ב-hooked agent. בקש ממנו להשתמש בכלי הקריאה שלו ב-`README.md` ודווח על הכותרת. אישור שה-session מכיל את קריאה כלי הזה, ואז הפעל `failproofai jev status` שוב: הhealing evaluated-call count שלו צריך להגביר. פתח **Policies → Activity** ב-[local dashboard](/he/reference/local-dashboard#review-policy-activity) כדי לבדוק את פסק הדין של Jev של הקריאה ו-mode. בobserve mode, תוצאת המדיניות עדיין מחליטה על הקריאה. clearance מופיע רק אם מדיניות reviewable עונה והוא ניקה כל בדיקה בשם; קריאה רגילה עלול להיות אין מדיניות כדי לנקות.

## Observe mode

`enforce` הוא ברירת המחדל. כדי לצפות ב-Jev ללא שיתן לו לשנות החלטה, החלף ל-`observe`: Jev עדיין שואל וגם פסקי הדין שלו מוקלטים, אך תוצאת ה-regex זה שנוכח.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` שומר על הקביעה — ה-endpoint וה-key — ועוצר שאל Jev: hooks מריץ את מדיניות regex בדיוק כמו ללא קביעה, ו-`failproofai jev status` אומר „off (switched off)". החלף חזרה עם `--mode observe` או `--mode enforce`.

Re-running `setup` על אותו ספק שומר את המפתח שמאוחסן, כדי mode מתג הוא one flag. החלפה ספק מתחיל מחדש ואומר בשביל המפתח של הספק הזה. כן גם `--base-url` שזז בקשות אל host שונה: מפתח מאוחסן הוא רק שלח ל-host שהיא ניתנה עבור, או ל-API שלעצמו של הספק.

## קובץ הקביעה

הכל חי בקובץ אחד, `~/.failproofai/jev.json`, כתוב על ידי `setup`:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Field | Meaning |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` או `custom` — או `failproofai`, שאת המפתח שלה מגיע מה-FailproofAI Cloud connection במקום קובץ זה (ראה [Jev through FailproofAI Cloud](/he/reference/jev-cloud)). |
| `apiKey` | שלח כ-`Authorization: Bearer <key>`. |
| `baseUrl` | דרוש לכל `custom`; משתנה את ה-API base של הספק כל אחרת. חייב להיות `https`. Plain `http` לכל `localhost` מקובל רק עם `mode: observe`: כלום לא מאמת שרת loopback, כך שבעוד proxy שלך למטה כל תהליך על המכונה, כולל הסוכן להישפט, יכול לענות במקומו. |
| `accountId` | Cloudflare רק: 32 תווים hex קטנים. |
| `model` | משנה את מזהה ה-model ברירת המחדל של הספק. מזהה גרסה חייב לשם Jev 1.13. ערך בצורה כמו API key נסורב (והלא חזר חזרה), כדי מפתח הדבקנו `--model` הוא לא מעולם אוחסן או שלח כ-model. |
| `timeoutMs` | כמה זמן קריאה כלי מחכה Jev לפני השימוש בתוצאת regex. 100–10000, ברירת מחדל 3000. |
| `mode` | `enforce` (default), `observe`, או `off` (שמור קביעה, הרץ אף Jev). |

שלוש כללים להגן עליו:

- **Owner-only.** זה כתוב עם הרשאות `0600`. עותק שכל משתמש אחר או קבוצה יכול קורא או לכתוב נסורב, hooks fallback ל-regex עד שאתה מריץ `chmod 600 ~/.failproofai/jev.json` או `setup` שוב. התיקייה בדוקה גם כן: `~/.failproofai` חייב לא להיות **writable** על ידי אף אחד אחר, כי מי שיכול לכתוב שם יכול להחליף את הקובץ מה הרשאות שלו הם. `setup` לוקח את write bits האלה אם זה מוצא. `failproofai jev status` אומר כאשר קביעה נסורב וזה מציג ה-endpoint קובץ שמות: מישהו אחר יכול שינה אותו, אנוח זה הוא שלך לפני שאתה `chmod`. Re-running `setup` בקובץ כזה נושא מפתח מאוחסן רק ל-API של הספק; כל endpoint אחר זה שמות צריך את המפתח שוב (`--key-stdin`), או `--base-url default` לשליחה בקשות חזרה לספק.
- **Global only.** מאגר לא יכול להפוך Jev על, תוך כדי ציון endpoint אחר או pick its model: `.failproofai/jev.json` בתוך פרויקט הוא בן הזלל, וספק, URL, model וחשבון id קרא רק מקובץ זה — לא מעולם מה סביבה, סוכן אשר settings של מאגר יכול להגדיר. (`FAILPROOFAI_HOME` לא דרך סביב זה: זה זוז failproofai כל תיקייה, מדיניות שלך כלולה, במקום מעבר Jev בעצמו.)
- **המפתח בלבד עשוי להגיע מ-environment.** אם קובץ זה אין `apiKey`, `FAILPROOFAI_JEV_API_KEY` ספק את זה עבור session הזה (`setup --key-from-env` כותב קובץ כזה). זה לא מעולם משתנה מפתח הקובץ מחזיק, וזה לא יכול להפוך Jev על ללא הקובץ. איפה משתנה זה לא הגדר, Jev הוא בפשטות off לתוך shell זה: `failproofai jev status` אומר כן, יציאה 0 ותוך השאר קביעה (`status --json` תוצאות `"status": "key-missing"` עם `"reason": "no-env-key"`). ה-`failproofaid` daemon לא ראה shell של סביבה שלך, אנוח על מכונה הקבוע עם `failproofai config`, שמור את מפתח בקובץ.

## איזה Jev ענה

סף ההחלטה של Failproof AI היה מכיילים ב-Jev 1.13, כדי תשובה היא משמש רק כאשר בא מ-Family הזה: `jev-1.13.x`, או OpenRouter's `typesafe/jev-1.13-<date>`. איפה ספק שמות Jev רק על ידי שם כינויי וארוע גרסה לא (Vercel, ו-Cloudflare כאשר זה לא אומר), התשובה משמש ותוך הוקלט כ-unverified. A `custom` endpoint חייב דווח את model זה ענה; זה חריג אחד הוא unversioned `--model` שם אתה קביעה, איזה, חזר, הוקלט כ-unverified בדרך זהה. תשובה החזה כל גרסה אחרת, או `custom` תשובה מדווח לא, לא משמש: זה קריאה fallback ל-regex עם הטעם `model-mismatch`.

## כאשר Jev לא יכול לענות

כל אלה fallback לתוך regex תוצאה זה קריאה וזה מוקלט עם סיבה שלה, אשר `failproofai jev status` totals:

| Reason | Cause |
| --- | --- |
| `timeout` | אין תשובה בתוך `timeoutMs`. |
| `http-429` | הספק rate-limited את המפתח. |
| `rate-limited` | Failproof AI's משלו limiter היה אחזקה הקריאה חזרה לפני שליחה זה: 5 בקשות שנייה, בפרץ של עד 5, וזה לא עבור רגע אחרי ספק תשובות `429`. לא ספק. |
| `http-500`, `http-502`, `http-503`, … | שגיאה שרת בספק. סטטוס המדויק מוקלט. |
| `out-of-credits` | HTTP 402: חשבון ספק אין אשראי משאר. |
| `provider-refused` | HTTP 402 מ-Cloudflare קריאה „Model execution failed (Payment error)": ספק דחה כדי הפעל את model בבקשה זו. בדרך כלל לא חיוב, כדי topping עד לא יזוז זה. |
| `http-401`, `http-403` | המפתח נסורב. |
| `http-404` | כלום לא משרת ב-`<base>/systemone`, כדי base URL הוא הלא נכון — `/systemone` הוא appended ל-it, וכל ספק משרת זה ב-version שלה root. `failproofai jev models` מציג מה endpoint כן משרת. |
| `network` | Endpoint לא יכול להגיע. |
| `http-301`, `http-302`, `http-307`, `http-308` | Endpoint ענה עם הפניה. הפניות לא מעולם בעקבות, תשובה רק פעם אחת בא מ-URL בקביעה שלך; הגדר `--base-url` ל-URL הסופי. |
| `malformed` | Endpoint ענה, אך לא עם תשובה Jev — גוף זה לא JSON, או אחד עם לא תשובות בו. |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflare's envelope דיווח כישלון, או עבודה זה לא הסתיים. |
| `model-mismatch` | Jev גרסה אחרת מ-1.13 ענה, או `custom` endpoint לא אומר איזה model ענה. |
| `request-cut` | **לא outage.** Jev ענה; זה הראה רק חלק קריאה, כדי תשובה שלה ניקה כלום. ראה [When Jev answered, but not on the whole call](#when-jev-answered-but-not-on-the-whole-call). |

`failproofai jev status` יכול לה גם כן רarer סיבות, כגון `upstream-error` (התשובה נישא הטעות שלעצמו של ספק) או `config`, ו-totals כל סיבה זה לא יכול שם כ-`other`.

`request-cut` הוא בטבלה זו כי `failproofai jev status` totals זה עם כל השאר, וכי זה גם כן עוזב כל דחיה עומדת. זה סיבה אחת כאן שאומר כלום בשביל הספק שלך: הבקשה הגיעה ו-Jev ענה זה. בניגוד כל שורה מעל זה, תשובה זה עדיין ספרים — Jev's משלו דחיה או אזהרה חלים על גבי regex תוצאה במקום להיות בן הזלל. כדי כללים שלהם אומר קריאות מגיעות ה-evaluator גדול מדי שלח כולו, לא כי endpoint שלך הוא unwell, וtopping עד אשראי או שינוי ה-URL לא יזוז המספר.

## כאשר Jev ענה, אך לא בקריאה כל

שתיים דברים נוספים יכול לקרות, ולא כל אחד הוא Jev כשלה לענות. שניהם על כמה קריאה, או של השיחה, התאים לתוך בקשה אחת.

**חלק קריאה עצמה לא התאימה.** קריאה כלי שלח בתוך תקציב קבוע, וחיצוני אחד — מאוד גדול `Write`, ענקי MCP גוף, פקודה padded לכל cap — הוא שלח עם מה התאים. Jev עדיין ענה, ותשובה שלה עדיין ספרים: משלו דחיה או אזהרה חלים כרגיל. מה זה לא יכול כן הוא **clear** דבר, כי פסק דין ניתן בחלק קריאה לא פסק דין בקריאה. כדי כל דחיה מדיניות עומדת, וקריאה הוא מוקלט כ-fallback עם סיבה `request-cut`, אשר `failproofai jev status` totals ליד סיבות מעל. הכלל זה נותן לך: ביצוע קריאה גדול יכול עלות זה clearances שלה, ויכול לא מעולם קנה אחד.

**הודעה לא התאימה.** prompt ארוך אתה הדבקנו, הודעה בן הסוכן, או prompt זה evaluator זה's משלו חנות כבר capped. **כלום שינויים**: הקריאה הוא שפט, ניקה ותוך מוקלט בדיוק כמו כל אחר, וזה לא ספר כ-fallback. אורך של מה סוג לא מחליט פסק דין, וcut לא יכול ייצור הסכמה: איפה prompt הגיע כבר capped, „אתה לא ביקשת את זה" עוצר להיות מסקנה זה יכול להיות משוות מ-it בכל פעם, במקום הופכת אחד.

הקו בין שניים הוא מי כתב הטקסט. הקריאה הוא הסוכן's, ותחוק שתן אורך שלה להחסר חומרה היה תחוק הסוכן יכול להשתמש; prompt שלך הוא שלך, וטריטוריה אורך שלו כאות רק פעם אחת מענישים הדבקנו spec או stack trace.

## מה עוזב את המכונה

לכל קריאה כלי Jev מעריך, בקשה אחת הולכת לספק שלך, נישא:

- קריאה הכלי עצמו, עם סודות כגון API keys, bearer tokens וטוקנים `KEY=` הקצבות;
- prompts הקרובים אתה הקלדנו, עם טקסט הסוכן's harness הוסיף הוסר;
- הודעה אחרון סוכן לפני prompt הקרובים שלך, מתויג כ-agent-written;
- עובדות מחושבות מקומי, כגון אם נתיב בתוך פרויקט — אחד session הוא בראשון סקור קריאה, [קבוע עבור ה-session](/he/reference/jev-intent#the-project-root) — וסניף git הנוכחי.

זה הולכת רק ל-endpoint בקביעה שלך, תחת מפתח שלך.

## כבה את זה

```bash
failproofai jev remove
```

זה מחיקות `~/.failproofai/jev.json`. מהקריאה כלי הבא, hooks הפעול regex מדיניות בדיוק כמו לפני. הper-session חנויות תחת `~/.failproofai/state/semantic/` (מוקלט prompts בתוך `sessions/`, שורשים פרויקט ב`roots/`) הושארו מקום וגיל חוצה. כדי עצור שאל Jev אך שמור קביעה, השתמש `failproofai jev setup --mode off` במקום.

## ייחוס פקודה

| Command | Outcome |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | קביעה זה בפקודה אחת; ספק בא מ-host של ה-URL |
| `failproofai jev --url <url> --token <token>` | זהה, עם מפתח על שורת הפקודה — היסטוריה שלך ותהליך רשימה לראות זה |
| `failproofai jev setup --provider <kind> --key-stdin` | לכתוב קביעה מ-key piped על stdin |
| `failproofai jev setup --provider <kind>` | זהה, שאל בשביל מפתח בבקשה כיסוי |
| `failproofai jev setup --key-from-env` | אוחסן לא מפתח; קרא `FAILPROOFAI_JEV_API_KEY` לכל session |
| `failproofai jev setup --mode observe` | החלף mode (`enforce`, `observe` או `off`), שמור מפתח |
| `failproofai jev setup --model <id>` / `--base-url <url>` | משנה את model או API base; `default` ברור את override |
| `failproofai jev setup --timeout-ms <n>` | שינוי לכל בקשה תקציב |
| `failproofai jev status [--json]` | קביעה, הרשאות ופעילות אחרונה; לא מעולם מפתח |

| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | Model ids הקצבות endpoint's `/models`, סימון בקביעה |
| `failproofai jev remove` | מחק הקביעה; Jev הוא off |
