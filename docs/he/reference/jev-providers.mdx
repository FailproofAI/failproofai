זה הרפרנס של ספקי וקונפיגורציה עבור [Jev policies](/he/policies/jev) עם המפתח שלך. Regex policies תואמים מחרוזות. הם לא יכולים להבחין בין `rm -rf build/` שביקשת ובין `rm -rf ~` שהחליק לתוך תוכנית, כך שהם חוסמים יותר מדי במקום אחד והעט מדי במקום אחר. **Jev**, המסווג של TypeSafe, קורא את הקריאה מול מה שבאמת ביקשת ועונה לסט של שאלות כן/לא עליה בבקשה אחת מהירה.

כאשר Jev endpoint שלך והמפתח שלך מוגדרים, Failproof AI שואל את Jev על כל קריאת כלי **במקביל** ל-regex policies, לא במקום שלהם:

- **hard** policy של deny הוא סופי. Jev לא יכול לנקות אותו. כל policy הוא hard אלא אם כן הוא מסומן explicitly כ-reviewable וקובע את בדיקות Jev שמכסות אותו, כך שcustom, pack או Cloud policy שאומר כלום הוא hard, וה-always-on self-protection guard הוא תמיד hard.
- **reviewable** policy של deny עשוי להיות מנוקה, אך רק כשJev נשאל על הדאגה הבדוקה שcovering זה policy ופתר את הבעיה "אין כאן דבר" או "המשתמש ביקש את זה". בדיקה שמוצאת את הדאגה ממשית, כשהמשתמש לא ביקש את הקריאה, שומרת את deny — אפילו כשהגזר שלה הוא רק warning, כי לפני קריאת כלי warning לא עוצר את agent. וכשהבדיקה הזו היא אחת שיכולה deny (secret exposure, credential exfiltration, destructive deletion, …), שום דבר לא מנוקה על הקריאה הזו.
- block עשוי עדיין להפוך **warning** כשהקריאה היא שלב של המשימה שנתת והגיעה לא רחוק יותר: Jev משנה את הdeny שלו שלעצמו ל-warning, וה-warning הזה — שם מה שבאמת לא בסדר עם הקריאה — מחליף את block של ה-policy.
- Jev יכול גם להזהיר או לעשות deny בעצמו, על הנזק שאף regex לא מתאר.
- אם Jev לא יכול לענות (timeout, rate limit, server error, no credits, unexpected model version), הקריאה הזו מקבלת את regex result, בדיוק כמו בלעדי Jev.
- Jev לעולם לא עושה קריאה permissive יותר מ-policies שלך לבד אלא אם היא קראה את כל הקריאה ונשאלה על הדאגה המדוקדקת. כל דבר פחות — קריאה גדולה מדי לשליחה כך, injection חשודה — משולל את clearances ושומר על כל deny.

<Note>
בלי Jev config כלום לא משתנה: hooks מריצים את regex policies בדיוק כמו שהם תמיד עשו. ה-config הוא כל ה-opt-in.
</Note>

<Tip>
בـ FailproofAI Cloud? אתה לא צריך מפתח משלך: מכונה המחוברת עם מפתח שנושא `jev:evaluate` יכולה להשתמש ב-Jev בתוכנית של הארגון שלך. ראה [Jev through FailproofAI Cloud](/he/reference/jev-cloud).
</Tip>

## לפני שאתה מתחיל

התקן **failproofai 1.0.8-beta.0 או אחרון יותר** ותיצור את hooks שלו ל-[supported harness](/he/reference/harnesses) על המכונה שבה ה-agent שלך פועל. עקוב אחרי [quickstart](/he/start/quickstart) אם זה מכונה חדשה, או [set up local enforcement](/he/start/setup#enforce-locally) אם אתה לא משתמש ב-Cloud. בדוק את ה-CLI המותקן עם `failproofai --version`.

קבל API key מספק למטה, או יש לך endpoint תואם והמפתח שלו מוכן. Jev משנה את קריאות הכלים הנקראות ב-`PreToolUse` או `PermissionRequest` gate. זה יכול להנפיק גזר משלו, אך ניקיון של existing policy deny דורש גם policy מותקן מסומן [reviewable](/he/policies/authority). hard policy denies נשארים סופיים.

## בחר ספק

Jev ניתן להגעה דרך חמש מסלולים. הבא מפתח לכל אחד מהם.

| Provider | `--provider` | Endpoint | Default model | Notes |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Exact version pin. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | Requests are routed to zero-data-retention endpoints only, with no fallback to another provider. Reports a dated version such as `typesafe/jev-1.13-20260917`. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Names Jev only by an alias, so the answering version is recorded as unverified. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | Needs `--account-id`. About six calls a second per key were measured before HTTP 429. |
| Your own endpoint | `custom` | `<base-url>/systemone` | `jev-1.13.0` | Any endpoint that accepts TypeSafe's request body and reports which model answered. `https` only; plain `http` to a loopback host (`localhost`, `127.0.0.1`, `::1`) is accepted for local testing. |

<Warning>
עם תכונת ה-bring-your-own-key של Vercel, בקשה שנכשלה מנסה מחדש בשקט עם credentials של Vercel. אם אתה צריך כל קריאה לחייב ל-, ולהיראות על ידי, TypeSafe account שלך בלבד, השתמש ב-TypeSafe ישירות.
</Warning>

## הגדר את זה

פקודה אחת, endpoint והמפתח. התחל ב-`observe` mode כדי שתוכל לבדוק את הגזרים של Jev בזמן שה-policies הקיימות שומרות על ההחלטות:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### ה-URL בוחר את הספק

אתה לא חייב לשם את הספק: **host** של ה-URL הוא איזה אחד זה.

| URL host | Provider | Also needs |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| any other host | `custom` | — the URL you gave is the base URL |

שלוש דברים נובעים מזה:

- **URL שהוא ה-API של הספק לא כותב override.** `--url https://api.typesafe.ai/v1` מייצר בדיוק את ה-config ש-`--provider typesafe` היה עושה. תן path או host אחר על ספק ידוע וזה מאוחסן כ-base URL, כמו שהיה `--base-url` מאחסן.
- **`--provider` עדיין עוקף את ההסקה**, שזו איך אתה מגיע proxy שמדבר API של ספק מ-host משלך: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **`--provider` שסותר את ה-host מסורב**, לא ניחש. `--provider openrouter --url https://api.typesafe.ai/v1` לא כותב שום דבר ואומר למה: שתי הכתיבות לא מסכימות היכן המפתח שלך עומד להיות שלוח. אותו זוג מסורב מ-`jev setup --base-url` ומלוח המחוונים של Jev settings. (`--provider custom` לא סתירה — זה אומר "תחשוב על ה-URL הזה כעל עצמו" — למעט ב-host של Cloudflare, שה-endpoint שלו per-account custom route לא יכול להגיע.)

`--url` מתואמת בדיוק כמו ה-`baseUrl` בקובץ ה-config, ומסורבת באותם הקולות: `https`, או `http` רגיל ל-loopback host (`localhost`, `127.0.0.1`, `::1`) בכל mode. סיכון: כלום לא מאמת server loopback, כך שבזמן שהוא למטה תהליך מקומי אחר יכול לקחת את ה-port שלו ולענות; השתמש ב-`https` מחוץ לבדיקה מקומית.

### המפתח

זרימה עם `--key-stdin`, או הרץ את הפקודה בטרמינל בלעדיו והדבק את המפתח ב-masked prompt. כך או כך זה הולך ישר לקובץ ה-config ולא מודפס אי פעם חזרה.

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash

    ```

`failproofai jev setup` לוקח את אותם flags והוא ה-longhand לכל זה: `setup --provider <kind>` שבו היית מעדיף שם את הספק מאשר ה-URL.

### `--token`, וכמה זה עולה

`--token <token>` שם את המפתח בשורת הפקודה, שהוא הדרך המהירה ביותר להגדיר מכונה והוא ה-spelling היחיד שמשאיר את המפתח בכל מקום אבל קובץ ה-config:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
טיעון שורת פקודה הוא בקובץ ההיסטוריה של ה-shell שלך לאחר מכן, ובזמן שהפקודה פועלת היא נמצאת ברשימת התהליכים — readable מ-`/proc` על ידי כל דבר שפועל כמוך. `setup` אומר כן בכל פעם ש-`--token` משמש. העדיפות `--key-stdin` על מכונה שאתה משתף, בהקלטה, או בכל מקום שקובץ ההיסטוריה מסונכרן; סובב מפתח שהעברת בדרך זו אם זה משנה.
</Warning>

`--token`, `--key-stdin` ו-`--key-from-env` בלעדיים זה לזה: תן אחד.

אז שלח בקשה חיה קטנה אחת כדי לבדוק את המפתח, ה-endpoint וב-Jev ענה:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` יוצא 1, ואומר כן בכותרת שלו, כשהתשובה מגיעה אחרי ה-timeout (כל hook היה נופל בחזרה ל-regex כמו `timeout`) או עונה לשאלת הבדיקה שלו בצורה שגויה.

Hooks קורא את ה-config בכל קריאת כלי, כך שזה חל מהבא. אין כלום להפעיל מחדש, עם או בלעדי daemon.

## בדוק מה זה עושה

```bash
failproofai jev status
failproofai jev status --json
```

`status` מראה את הספק, endpoint, model, mode, קובץ ה-config ואת ההיתרים שלו, ולעולם לא את המפתח. מתחתיה היא מסכמת פעילות אחרונה: כמה קריאות Jev הערך, כמה פעמים זה נפל בחזרה ל-regex ולמה, ה-latency שלו, וב-reviewable policies שזה ניקה.

## אמת קריאה אמיתית

התחל סשן חדש ב-hooked agent. בקש ממנו להשתמש בכלי קריאת הקובץ שלו ב-`README.md` ודווח את הכותרת. אשר שהסשן מכיל את הקריאה הזו, אז הרץ `failproofai jev status` שוב: את ספירת ה-evaluated-call האחרונה שלו צריכה להגדיל. פתח **Policies → Activity** ב-[local dashboard](/he/reference/local-dashboard#review-policy-activity) כדי לבדוק את גזר Jev של הקריאה וב-mode. ב-observe mode, תוצאת ה-policy עדיין מחליטה על הקריאה. clearance מופיע רק אם reviewable policy תאם ו-Jev ניקה כל בדיקה בשם; רו רגיל עשוי לא להיות policy לנקות.

## Observe mode

`enforce` הוא ברירת המחדל. כדי לצפות ב-Jev בלי לתת לו לשנות כל החלטה, עבור ל-`observe`: Jev עדיין שואל וגזריו מתועדים, אך תוצאת ה-regex היא מה שנאכף.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` שומר את ה-config — ה-endpoint והמפתח — ועוצר לשאול Jev: hooks מריצים את regex policies בדיוק כמו בלעדי config, ו-`failproofai jev status` אומר "off (switched off)". החזר בחזרה עם `--mode observe` או `--mode enforce`.

Re-running `setup` לאותו ספק שומר את המפתח המאוחסן, כך שמעבר mode הוא flag אחד. switching provider מתחיל מחדש ודורש את המפתח של הספק הזה. כך גם `--base-url` שמעביר בקשות ל-host אחר: מפתח מאוחסן משלח רק ל-host שהוא ניתן עבורו, או ל-API שלו של הספק.

## קובץ ה-config

הכל גר בקובץ אחד, `~/.failproofai/jev.json`, כתוב על ידי `setup`:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Field | Meaning |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` או `custom` — או `failproofai`, שהמפתח שלו בא מה-FailproofAI Cloud connection בדל מקובץ זה (ראה [Jev through FailproofAI Cloud](/he/reference/jev-cloud)). |
| `apiKey` | שלח כ-`Authorization: Bearer <key>`. |
| `baseUrl` | נדרש ל-`custom`; מחליף את API base של הספק אחרת. חייב להיות `https`. `http` רגיל ל-`localhost` מקובל רק עם `mode: observe`: שום דבר לא מאמת local port, כך שבזמן ש-proxy שלך למטה כל תהליך על המכונה, כולל agent שנשפט, יכול לענות במקומו. |
| `accountId` | Cloudflare רק: 32 lowercase hex characters. |
| `model` | מחליף את model id של ברירת המחדל של הספק. versioned id חייב לשם Jev 1.13. ערך שצורתו כמו API key מסורב (ולא חוזר בחזרה), כך מפתח מודבק ל-`--model` לעולם לא מאוחסן או נשלח כמו model. |
| `timeoutMs` | כמה זמן קריאת כלי חיכתה עבור Jev לפני שימוש ב-regex result. 100–10000, default 3000. |
| `mode` | `enforce` (default), `observe`, או `off` (שמור את ה-config, הרץ ללא Jev). |

שלושה כללים שומרים על זה:

- **Owner-only.** זה כתוב עם היתרים `0600`. עותק שכל משתמש או קבוצה אחרת יכול קרוא או כתוב הוא **סורב**, וhooks נופלים בחזרה ל-regex עד שתריץ `chmod 600 ~/.failproofai/jev.json` או `setup` שוב. ה-directory בדוק גם: `~/.failproofai` לא חייב להיות **writable** על ידי מישהו אחר, כי מי שיכול לכתוב שם יכול להחליף את הקובץ מה עם היתרים שלו. `setup` לוקח את write bits האלה עם אם זה מוצא אותם. `failproofai jev status` אומר כשconfig מורכב בחזרה ומציג את endpoint שהקובץ שם: מישהו אחר יכול היה לשנות אותו, כך לבדוק שזה שלך לפני שאתה `chmod`. Re-running `setup` על קובץ כזה נושא את המפתח המאוחסן שלו רק ל-API שלו של הספק; כל endpoint אחר שהוא שם צריך את המפתח שוב (`--key-stdin`), או `--base-url default` לשלוח בקשות בחזרה ל-הספק.
- **Global only.** Repository לא יכול להפוך Jev, להצביע אותו על endpoint אחר או לבחור את model שלו: `.failproofai/jev.json` בתוך פרויקט מתעלם, והספק, URL, model וAccount id נקראים רק מהקובץ הזה — אף פעם מהסביבה, אשר repository's agent settings יכול להגדיר. (`FAILPROOFAI_HOME` לא הוא דרך סביב זה: זה מעביר את כל ה-failproofai directory, policies שלך כלול, במקום לעבור Jev על עצמו.)
- **המפתח לבד עשוי לבוא מהסביבה.** אם לקובץ אין `apiKey`, `FAILPROOFAI_JEV_API_KEY` מספק אותו לסשן הזה (`setup --key-from-env` כותב קובץ כזה). זה לעולם לא מחליף מפתח שהקובץ מחזיק, וזה לא יכול להפוך Jev ללא הקובץ. שבו המשתנה לא הגדרו, Jev פשוט off עבור ה-shell הזה: `failproofai jev status` אומר כן, יוצא 0 ורך את ה-config לבד (`status --json` דוחים `"status": "key-missing"` עם `"reason": "no-env-key"`). ה-daemon `failproofaid` לא רואה את סביבתו של ה-shell שלך, כך על מכונה הגדרת עם `failproofai config`, שמור את המפתח בקובץ.

## ב-Jev ענה

סף ההחלטות של Failproof AI כיול על Jev 1.13, כך תשובה משמשת רק כשהיא בא מהמשפחה הזו: `jev-1.13.x`, או `typesafe/jev-1.13-<date>` של OpenRouter. שם ספק שם Jev רק על ידי דמות כנוי ודוחים כל גרסה (Vercel, וCloudflare כשזה לא אומר), התשובה משמשת ורשומה בתור unverified. `custom` endpoint חייב לדווח את model שענה; ה-חריג היחיד הוא unversioned `--model` name שהגדרת לה, אשר, echoed בחזרה, מתועדת כunverified באותו דרך. תשובה דיווח על כל גרסה אחרת, או `custom` תשובה דיווח כל, לא משמשת: הקריאה הזו חזרה ל-regex עם הסיבה `model-mismatch`.

## כשJev לא יכול לענות

כל אחד מאלה נופל בחזרה ל-regex result לקריאה הזו ומתועדת עם הסיבה שלו, אשר `failproofai jev status` סך הכל:

| Reason | Cause |
| --- | --- |
| `timeout` | אין תשובה בתוך `timeoutMs`. |
| `http-429` | ספק מגביל את המפתח. |
| `rate-limited` | Failproof AI's own limiter הרך את הקריאה בחזרה לפני שליחתה: 5 בקשות שנייה, בפרצים של עד 5, ואף לרגע אחרי הספק ענה `429`. לא הספק. |
| `http-500`, `http-502`, `http-503`, … | שגיאת שרת בספק. הדיוק סטטוס מתועדת. |
| `out-of-credits` | HTTP 402: חשבון הספק אין credits שנותרו. |
| `provider-refused` | HTTP 402 מCloudflare קריאה עם "Model execution failed (Payment error)": הספק סירב להרוץ את model על בקשה זו. בדרך כלל לא חיוב, כך כתיבה למעלה לא זז. |
| `http-401`, `http-403` | המפתח מורכב בחזרה. |
| `http-404` | כלום לא משרת בـ`<base>/systemone`, כך base URL הוא כרח — `/systemone` מופץ אליו, וכל ספק משרת אותו בגרסה root. `failproofai jev models` מראה מה ה-endpoint כן משרת. |
| `network` | ה-endpoint לא יכול להגיע. |
| `http-301`, `http-302`, `http-307`, `http-308` | ה-endpoint ענה עם redirect. Redirects לא עקבו, כך התשובה באה רק מה-URL ב-config שלך; הגדר `--base-url` ל-final URL. |
| `malformed` | ה-endpoint ענה, אך לא עם תשובת Jev — גוף שלא JSON, או אחד בלא תשובות בו. |
| `cloudflare-error`, `cloudflare-incomplete` | ה-envelope של Cloudflare דיווח כשל, או עבודה שלא סיימה. |
| `model-mismatch` | Jev version אחר מ-1.13 ענה, או `custom` endpoint לא אמר איזה model ענה. |
| `request-cut` | **לא הפסקה.** Jev ענה; היא הראתה רק חלק מהקריאה, כך התשובה שלה ניקתה כלום. ראה [When Jev answered, but not on the whole call](#when-jev-answered-but-not-on-the-whole-call). |

`failproofai jev status` יכול להציג כמה סיבות רחוקות יותר גם, כמו `upstream-error` (התשובה נשאה שגיאה משלה של הספק) או `config`, וסך הכל כל סיבה היא לא יכול שם כמו `other`.

`request-cut` בטבלה זו כי `failproofai jev status` סך הכל אתה עם השאר, וכי זה גם השאיר כל deny עומד. זה סיבה היחידה כאן שאומר שום דבר על הספק שלך: הבקשה הגיעה וJev ענה אותה. בניגוד לכל שורה מעליה, התשובה הזו עדיין ספור — Jev's deny או warning משלו חל על קודקוד של ה-regex result במקום להיות בזבוז. כן ריצה של אלה אומר קריאות מגיעות ל-evaluator גדול מדי לשלוח כל, לא שה-endpoint שלך לא טוב, וטופים עד credits או שינוי ה-URL לא זז את המספר.

## כשJev ענה, אך לא על כל הקריאה

שתי דברים נוספים יכול להתרחש, ואף כלום לא על Jev משהו לענות. שניהם על כמה מהקריאה, או מהשיחה, התאים לבקשה אחת.

**חלק מהקריאה עצמה לא התאים.** קריאת כלי נשלחה בתוך תקציב קבוע, ו-outsized אחד — כתיבה גדולה מאוד, גוף MCP ענק, פקודה padded לכל כובע — נשלח עם מה התאים. Jev עדיין ענה, והתשובה שלו עדיין ספור: את deny או warning משלה חל כרגיל. מה זה יכול לא עשות הוא **ברור** שום דבר, כי גזר נתן על חלק מקריאה לא גזר על הקריאה. כן כל deny policy עומד, והקריאה מתועדת כ-fallback עם הסיבה `request-cut`, אשר `failproofai jev status` סך הכל לצד הסיבות מעל. הכלל זה נותן לך: יצור קריאה גדולה יותר יכול לעלות את ה-clearances שלה, וולא יכול אי פעם לקנות אחד.

**הודעה לא התאימה.** prompt ארוך אתה הדבקת, הודעה האחרונה של ה-agent, או prompt ה-evaluator הזה מחנות שלה כבר כתם. **שום דבר לא משתנה**: הקריאה משפטה, ברור ומתועדת בדיוק כמו כל אחר, וזה לא ספור כ-fallback. ה-length של מה אתה סוג לעולם מחליט גזר, וחתוך לא יכול ייצור הסכמה: שבו prompt הגיע כבר כתום, "אתה לא ביקשת זה" חדל להיות סיכום שיכול מוגדר מה, במקום להפוך אחד.

ה-line בין השניים הוא מי כתב את הטקסט. הקריאה היא של ה-agent, וכלל שתן את ה-length שלה להחסיר חומרה היא כלל ה-agent יכול להשתמש; prompt שלך זה שלך, וטיפול בה-length כמו סימן רק אי פעם ענש הדבקה spec או stack trace.

## מה עוזב את המכונה

עבור כל קריאת כלי Jev משנה, בקשה אחת הולכת ל-provider שלך, נושאת:

- את הקריאה כלי עצמה, עם סודות כמו API keys, bearer tokens ו-`KEY=` מטלות שנמחקו;
- הודעות חדשות אתה הקלדת, עם טקסט ה-agent's harness שלך הוסיף הוסר;
- ה-agent's האחרון הודעה לפני prompt האחרון שלך, תווית כ-agent-written;
- עובדות מחושבות מקומית, כמו האם path בתוך פרויקט — הוא הסשן היה בו בראשון מבדק קריאה, [pinned לסשן](/he/reference/jev-intent#the-project-root) — וה-current git branch.

זה הולך רק ל-endpoint ב-config שלך, בחובה המפתח שלך.

## תן את זה

```bash
failproofai jev remove
```

זה מחק `~/.failproofai/jev.json`. מהקריאה הבאה כלי, hooks מריצים את regex policies בדיוק כמו לפני. ה-per-session חנויות תחת `~/.failproofai/state/semantic/` (הודעות מתועדות ב-`sessions/`, פרויקט roots ב-`roots/`) נשארים במקום וגיל. לעצור לשאול Jev אך שומר את ה-config, השתמש `failproofai jev setup --mode off` במקום.

| Command | Outcome |
