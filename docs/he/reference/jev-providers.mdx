זהו הרeferenceה של הספק והתצורה עבור [מדיניויות Jev](/he/policies/jev) עם המפתח שלך. מדיניויות regex תואמות מחרוזות. הן לא יכולות להבדיל בין `rm -rf build/` שביקשת ובין `rm -rf ~` שהחליק לתוך plan, כך שהן חוסמות יותר מדי במקום אחד וקצת מדי במקום אחר. **Jev**, המסווג של TypeSafe, קורא את הקריאה מול מה שבעצם ביקשת וענה על מערכת של שאלות כן/לא עליה בבקשה אחת מהירה.

עם נקודת קצה של Jev משלך ומפתח מוגדרים, Failproof AI שואל את Jev על כל קריאת כלי **לצד** מדיניויות ה-regex, לעולם לא במקום שלהן:

- הדחייה של מדיניות **קשה** היא סופית. Jev לא יכול לנקות אותה. כל מדיניות היא קשה אלא אם כן היא מסומנת במפורש כניתנת לבדיקה ושמה את בדיקות ה-Jev שמכסות אותה, כך שמדיניות מותאמת, pack או Cloud שאינה אומרת כלום היא קשה, והשמירה העצמית שתמיד פעילה היא תמיד קשה.
- הדחייה של מדיניות **ניתנת לבדיקה** עשויה להיות נמחקת, אך רק כאשר Jev נשאל על הדאגה המדויקת שמדיניות זו מכסה וענה "כלום כאן" או "המשתמש ביקש זאת". בדיקה שמוצאת את הדאגה ממשית, כאשר המשתמש לא ביקש את הקריאה, שומרת את הדחייה — אפילו כשפסק שלה הוא רק אזהרה, כי לפני קריאת כלי אזהרה לא עוצרת את הסוכן. וכאשר בדיקה זו היא אחת שיכולה להסיר (חשיפת סוד, יניקה של אישורים, מחיקה הרסנית, ...), כלום לא נמחק בקריאה זו.
- בלוק עשוי עדיין להפוך ל**אזהרה** כאשר הקריאה היא שלב של המשימה שנתת וגם לא מגיע יותר הרחק: Jev משנה את הדחייה שלה לאזהרה, ואת האזהרה הזו — שמתארת מה בעצם לא בסדר בקריאה — מחליפה את הבלוק של המדיניות.
- Jev יכול גם להתריע או להסיר בעצמו, לפי נזק שאין regex מתאר.
- אם Jev לא יכול לענות (timeout, מגבלת שיעור, שגיאה בשרת, ללא נקודות זכות, גרסה דגם לא צפויה), הקריאה הזו מקבלת את תוצאת ה-regex, בדיוק כמו ללא Jev.
- Jev לעולם לא עושה קריאה permissive יותר מהמדיניויות שלך לבדן אלא אם קרא את כל הקריאה והושאל על הדאגה המדויקת. כל דבר פחות — קריאה גדולה מדי לשליחה כוללת, injection חשוד — משוך את ה-clearances ושומר כל דחייה.

<Note>
ללא תצורת Jev כלום לא משתנה: hooks מריצים את מדיניויות ה-regex בדיוק כפי שתמיד עשו. התצורה היא ה-opt-in כולו.
</Note>

<Tip>
ב-FailproofAI Cloud? אתה לא צריך מפתח משלך: מכונה המחוברת עם מפתח שנושא `jev:evaluate` יכולה להשתמש ב-Jev בתוכנית של הארגון שלך. ראה [Jev דרך FailproofAI Cloud](/he/reference/jev-cloud).
</Tip>

## לפני שתתחיל

התקן **failproofai 1.0.8-beta.0 או מאוחר יותר** וצרף את ה-hooks שלו לתרן [תומך](/he/reference/harnesses) ב-machine בו פועל הסוכן שלך. עקוב אחר [ה-quickstart](/he/start/quickstart) אם זו מכונה חדשה, או [הגדר enforcement מקומי](/he/start/setup#enforce-locally) אם אתה לא משתמש ב-Cloud. בדוק את ה-CLI המותקן עם `failproofai --version`.

קבל מפתח API מספק למטה, או הכן נקודת קצה תואמת והמפתח שלה. Jev סוקר קריאות כלים ששמותן בשער `PreToolUse` או `PermissionRequest`. הוא יכול להוציא פסק דין משלו, אך ניקוי דחייה של מדיניות קיימת דורש גם מדיניות מותקנת המסומנת [ניתנת לבדיקה](/he/policies/authority). דחיות מדיניות קשות נשארות סופיות.

## בחר ספק

Jev קיים דרך חמש נתיבים. הביא מפתח לכל אחד מהם.

| ספק | `--provider` | נקודת קצה | דגם ברירת מחדל | הערות |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | pin גרסה מדויקת. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | בקשות מנותבות רק לנקודות קצה בשמירת zero-data-retention, ללא fallback לספק אחר. דיווח גרסה מתוארכת כמו `typesafe/jev-1.13-20260917`. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | שומות ל-Jev רק לפי alias, כך שהגרסה המענה נרשמת כלא מאומתת. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | צריך `--account-id`. כשש קריאות לשנייה לכל מפתח נמדדו לפני HTTP 429. |
| נקודת קצה משלך | `custom` | `<base-url>/systemone` | `jev-1.13.0` | כל נקודת קצה שמקבלת גוף בקשה של TypeSafe ודיווחת איזה דגם ענה. רק `https`; plain `http` ללוקלהוסט (`localhost`, `127.0.0.1`, `::1`) מקובל לבדיקה מקומית. |

<Warning>
עם תכונת bring-your-own-key משלך של Vercel, בקשה שנכשלה מחודשת בשקט עם אישורים של Vercel. אם אתה צריך את כל קריאה חויבת לחשבון TypeSafe משלך בלבד, השתמש ב-TypeSafe ישירות.
</Warning>

## הגדר זאת

פקודה אחת, נקודת הקצה והמפתח. התחל במצב `observe` כדי שתוכל לבדוק את פסקי הדין של Jev בזמן שהמדיניויות הקיימות ממשיכות להחליט קריאות:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### ה-URL בוחר את הספק

אתה לא צריך לשמות את הספק: **host** של ה-URL זה איזה אחד זה.

| URL host | ספק | גם צריך |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| כל host אחר | `custom` | — ה-URL שנתת הוא ה-base URL |

שלוש דברים נובעים מזה:

- **URL שהוא ה-API של הספק עצמו לא כותב override.** `--url https://api.typesafe.ai/v1` מייצר בדיוק את התצורה שהיתה `--provider typesafe`. תן נתיב שונה או host על ספק ידוע והוא מאוחסן כ-base URL, כפי ש-`--base-url` היה אוחסן.
- **`--provider` עדיין משנה את ה-inference**, שכך אתה מגיע לproxy שמדבר API של ספק מhost משלך: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **`--provider` שמנוגד ל-host מסורב**, לא ניחוש. `--provider openrouter --url https://api.typesafe.ai/v1` כותב כלום ואומר למה: שתי הקביעות לא מסכימות היכן המפתח שלך עומד להישלח. אותו זוג מסורב מ-`jev setup --base-url` וממעדון Jev settings. (`--provider custom` אינו סתירה — זה אומר "החל את ה-URL הזה כמו הוא עצמו" — אלא בhost של Cloudflare, שמסלול custom לא יכול להגיע לנקודת הקצה הלכל-חשבון שלו.)

`--url` מאומת בדיוק כמו `baseUrl` בקובץ התצורה, ודחוי באותם דברים: `https`, או plain `http` ללוקלהוסט (`localhost`, `127.0.0.1`, `::1`) בכל מצב. סיכון: כלום לא מאמת שרת loopback, כך שבזמן שהוא פעול תהליך מקומי אחר יכול להחזיק את ה-port שלו ולענות; השתמש ב-`https` מחוץ לבדיקה מקומית.

### המפתח

צנור אותו עם `--key-stdin`, או הפעל את הפקודה בטרמינל ללא כך והדבק את המפתח בprompt מוסווה. בכל מקרה הוא נכנס ישר לקובץ התצורה ותמיד לא מודפס חזרה.

`failproofai jev setup` לוקח את אותו flags ותיקייה לכל זה: `setup --provider <kind>` שבו תעדיף לשמות את הספק מאשר את ה-URL.

### `--token`, וכמה זה עולה

`--token <token>` שם את המפתח בשורת הפקודה, שזה הדרך המהירה ביותר להגדרת machine והאיות היחיד שמשאיר את המפתח בכל מקום אלא בקובץ התצורה:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
טיעון command-line נמצא בקובץ היסטוריה של shell אחרי כן, וכאשר הפקודה פועלת זה ברשימת התהליכים — ניתן לקריאה מ-`/proc` לכל דבר הפועל כמוך. `setup` אומר זאת בכל פעם שמשתמשים ב-`--token`. העדיף `--key-stdin` ב-machine שאתה חולק, בסשן מוקלט, או בכל מקום בו קובץ ההיסטוריה מסונכרן; סובב מפתח שעברת בדרך זו אם זה משנה.
</Warning>

`--token`, `--key-stdin` ו-`--key-from-env` בלעדיים זה מזה: תן אחד.

ואז שלח בקשה חיה קטנה אחת כדי לבדוק את המפתח, את נקודת הקצה ואיזה Jev ענה:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` יוצא 1, ואומר זאת בכותרת שלו, כאשר התשובה מגיעה אחרי ה-timeout (כל hook היה חוזר ל-regex כ-`timeout`) או עונה לשאלת ה-check שלו בצורה לא נכונה.

Hooks קוראים את התצורה בכל קריאת כלי, כך שהיא חלה מהבאה. אין כלום להפעיל מחדש, עם או בלי ה-daemon.

## בדוק מה זה עושה

```bash
failproofai jev status
failproofai jev status --json
```

`status` מציג את הספק, נקודת הקצה, הדגם, המצב, קובץ התצורה והרשויות שלו, ולעולם לא את המפתח. מתחתיו זה מסכם פעילות אחרונה: כמה קריאות Jev הערך, כמה פעמים זה חזר ל-regex ולמה, הlatency שלו, ואילו מדיניויות ניתנות לבדיקה הוא נקה.

## אמת קריאה אמיתית

התחל session חדש בסוכן המחוברת. בקש ממנו להשתמש בכלי קריאת הקובץ שלו ב-`README.md` ודווח על כותרת. אשר שה-session מכיל את קריאת הכלי הזו, ואז הפעל `failproofai jev status` שוב: ספירת ה-evaluated-call האחרונה שלו צריכה להיות מעלה. פתח **Policies → Activity** ב-[local dashboard](/he/reference/local-dashboard#review-policy-activity) בדיקת פסק הדין של Jev של הקריאה והמצב. במצב observe, תוצאת המדיניות עדיין מחליטה את הקריאה. clearance מופיע רק אם מדיניות ניתנת לבדיקה תאם ו-Jev נקה כל בדיקה בשם; קריאה רגילה עשויה שלא תהיה מדיניות לנקות.

## מצב Observe

`enforce` הוא ברירת המחדל. כדי לצפות ב-Jev בלי להניח לו לשנות כל החלטה, החלף ל-`observe`: Jev עדיין נשאל ופסקי הדין שלו נרשמים, אך תוצאת ה-regex היא מה שנינוכים.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` שומר על התצורה — נקודת הקצה והמפתח — ומפסיק לשאול את Jev: hooks מריצים את מדיניויות ה-regex בדיוק כמו ללא תצורה, ו-`failproofai jev status` אומר "off (switched off)". החזור עם `--mode observe` או `--mode enforce`.

הפעלה מחדש של `setup` לאותו ספק שומרת את המפתח המאוחסן, כך שהחלפת מצב היא flag אחד. הסתובבות ספק מתחילה מחדש ושואלת את המפתח של הספק הזה. כך גם ה-`--base-url` שמעביר בקשות ל-host אחר: מפתח מאוחסן רק נשלח ל-host שהוא ניתן עבורו, או ל-API של ספקו משלו.

## קובץ התצורה

כל דבר חי בקובץ אחד, `~/.failproofai/jev.json`, כתוב על ידי `setup`:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| שדה | משמעות |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` או `custom` — או `failproofai`, שהמפתח שלו מגיע מחיבור FailproofAI Cloud במקום קובץ זה (ראה [Jev דרך FailproofAI Cloud](/he/reference/jev-cloud)). |
| `apiKey` | שלח כ-`Authorization: Bearer <key>`. |
| `baseUrl` | נדרש עבור `custom`; מחליף את base ה-API של הספק אחרת. חייב להיות `https`. Plain `http` ל-`localhost` מקובל רק עם `mode: observe`: כלום לא מאמת שרת מקומי, כך שבזמן שה-proxy שלך קטן כל תהליך ב-machine, כולל הסוכן שמשפט, יכול לענות במקומו. |
| `accountId` | רק Cloudflare: 32 תווי hex קטנים. |
| `model` | מחליף את מזהה הדגם של ברירת המחדל של הספק. מזהה גרסה חייב לשמות Jev 1.13. ערך שצורתו כמו מפתח API מסורב (ולא חוזר), כך שמפתח שהודבק ל-`--model` לעולם לא מאוחסן או נשלח כדגם. |
| `timeoutMs` | כמה זמן קריאת כלי חכה ל-Jev לפני שימוש בתוצאת ה-regex. 100–10000, ברירת מחדל 3000. |
| `mode` | `enforce` (ברירת מחדל), `observe`, או `off` (שמור את התצורה, הפעל בלי Jev). |

שלוש חוקים שומרות עליו:

- **בעלים-בלבד.** זה כתוב עם הרשויות `0600`. עותק שכל משתמש או קבוצה אחרים יכולים לקרוא או לכתוב **סורב**, ו-hooks חוזרים ל-regex עד שתפעיל `chmod 600 ~/.failproofai/jev.json` או `setup` שוב. המדריך נבדק גם: `~/.failproofai` חייב לא להיות **writable** על ידי אף אחד אחר, כי מי שיכול לכתוב שם יכול להחליף את הקובץ מה שהם הרשויות שלו. `setup` מוציא את ביטי הכתיבה האלה אם הוא מוצא אותם. `failproofai jev status` אומר כאשר תצורה סורבת ומציגה את נקודת הקצה שהקובץ מתעד: מישהו אחר יכול להיות שינה אותה, כך שבדוק שזה שלך לפני שאתה `chmod`. הפעלה מחדש של `setup` על קובץ כזה תוביל את המפתח המאוחסן רק ל-API של הספק; כל נקודת קצה אחרת שהוא שומה צריכה את המפתח שוב (`--key-stdin`), או `--base-url default` לשליחת בקשות חזרה לספק.
- **עולמי בלבד.** repository לא יכול להפוך את Jev, להצביע עליו בנקודת קצה אחרת או לבחור את הדגם שלו: `.failproofai/jev.json` בתוך פרויקט מתעלם, והספק, ה-URL, הדגם וה-account id נקראים רק מאותו קובץ — לעולם לא מהסביבה, שהגדרות סוכן של repository יכול להגדיר. (`FAILPROOFAI_HOME` אינו דרך סביב זה: זה מעביר את כל ספריית failproofai, המדיניויות שלך כלולות, במקום לנתב אותו Jev בעצמו.)
- **המפתח לבדו עשוי להגיע מהסביבה.** אם לקובץ אין `apiKey`, `FAILPROOFAI_JEV_API_KEY` מספק אותו לסשן הזה (`setup --key-from-env` כותב קובץ כזה). זה לעולם לא מחליף מפתח שהקובץ מחזיק, ואינו יכול להפוך את Jev בלי הקובץ. כאשר המשתנה לא מוגדר, Jev פשוט off לאותו shell: `failproofai jev status` אומר זאת, יוצא 0 ומשאיר את התצורה בלי שינוי (`status --json` דיווח `"status": "key-missing"` עם `"reason": "no-env-key"`). ה-daemon `failproofaid` לא רואה את הסביבה של shell שלך, כך שב-machine שהוגדר עם `failproofai config`, שמור את המפתח בקובץ.

## איזה Jev עונה

הגבולות ההחלטה של Failproof AI ועוצבו על Jev 1.13, כך שתשובה משמשת רק כשהיא מגיעה מהמשפחה הזו: `jev-1.13.x`, או `typesafe/jev-1.13-<date>` של OpenRouter. כאשר ספק שומה את Jev רק לפי alias וודיווחים ללא גרסה (Vercel, וCloudflare כשלא אומר), התשובה משמשת ונרשמת כלא מאומתת. endpoint `custom` חייב לדווח על הדגם שענה; היוצא דופן היחיד הוא שם דגם `--model` לא מגוברר שהגדרת לו, שחוזר, נרשם כלא מאומת באותה דרך. תשובה שדיווחים לכל גרסה אחרת, או תשובה `custom` שלא דיווחה, לא משמשת: הקריאה הזו חוזרת ל-regex עם הסיבה `model-mismatch`.

## כאשר Jev לא יכול לענות

כל אחת מהאלה חוזרת לתוצאת ה-regex לקריאה זו ונרשמת עם הסיבה שלה, אשר `failproofai jev status` מסכומת:

| סיבה | סיבה |
| --- | --- |
| `timeout` | אין תשובה בתוך `timeoutMs`. |
| `http-429` | הספק הגביל את שיעור המפתח. |
| `rate-limited` | הגבלה משלה של Failproof AI החזיקה את הקריאה לפני שליחתה: 5 בקשות לשנייה, בפרץ של עד 5, וכלום לרגע אחרי שהספק עונה `429`. לא הספק. |
| `http-500`, `http-502`, `http-503`, ... | שגיאה בשרת בספק. הסטטוס המדויק נרשם. |
| `out-of-credits` | HTTP 402: לחשבון הספק אין קרדיט יותר. |
| `provider-refused` | HTTP 402 מ-Cloudflare קריאה "Model execution failed (Payment error)": הספק סירב להפעיל את הדגם בבקשה זו. בדרך כלל לא חיוב, כך שהשלמת חיוב לא תזוז אותו. |
| `http-401`, `http-403` | המפתח סורב. |
| `http-404` | כלום אינו מוגש ב-`<base>/systemone`, כך ש-base URL לא נכון — `/systemone` מוסף אליו, וכל ספק משרת אותו בשורש הגרסה שלו. `failproofai jev models` מציג מה נקודת הקצה משרתת. |
| `network` | נקודת הקצה לא הייתה ניתנת להשגה. |
| `http-301`, `http-302`, `http-307`, `http-308` | נקודת הקצה ענתה עם ניתוב מחדש. הניתובים מחדש לעולם לא עקובים, כך שהתשובה מגיעה רק מה-URL בתצורה שלך; הגדר `--base-url` לה-URL הסופי. |
| `malformed` | נקודת הקצה ענתה, אך לא עם תשובת Jev — גוף שאינו JSON, או אחד ללא תשובות בו. |
| `cloudflare-error`, `cloudflare-incomplete` | מעטפת ה-Cloudflare דיווחה על כשל, או עבודה שלא הסתיימה. |
| `model-mismatch` | גרסה Jev אחרת מ-1.13 ענתה, או endpoint `custom` לא אמר איזה דגם ענה. |
| `request-cut` | **לא הפסקה.** Jev ענה; זה הוצג רק חלק מהקריאה, כך שהתשובה לא נקתה כלום. ראה [כאשר Jev ענה, אך לא בכל הקריאה](#when-jev-answered-but-not-on-the-whole-call). |

`failproofai jev status` יכול להציג גם כמה סיבות נדירות יותר, כמו `upstream-error` (התשובה נשאה את השגיאה של הספק) או `config`, ומסכומות כל סיבה שלא יכול לשמות כ-`other`.

`request-cut` בטבלה הזו מכיוון `failproofai jev status` מסכומת אותה עם השאר, ומכיוון שגם היא משאירה כל דחייה עומדת. זו הסיבה היחידה כאן שלא אומרת כלום על הספק שלך: הבקשה הגיעה ו-Jev ענה עליה. בניגוד לכל שורה למעלה, התשובה הזו עדיין נספרת — deny משלך או אזהרה של Jev חלות על גבי תוצאת ה-regex במקום להיות מושלכת. כך ריצה שלהם משמעה קריאות מגיעות למעריך גדול מדי לשליחה כוללת, לא שנקודת הקצה שלך בתוך בעיות, והשלמת קרדיט או שינוי ה-URL לא יזיז את המספר.

## כאשר Jev ענה, אך לא בכל הקריאה

שני דברים נוספים יכולים להקרות, וכלום מהם אינו Jev כשל לענות. שניהם על כמה מהקריאה, או מהשיחה, התאימו בבקשה אחת.

**חלק מהקריאה עצמה לא התאימה.** קריאת כלי נשלחת בתוך תקציב קבוע, וקריאה גדולה בהרבה — כתיבה גדולה מאוד, גוף MCP ענק, פקודה מרופדת לה-cap — נשלחת עם מה שהתאים. Jev עדיין עונה, והתשובה שלו עדיין נספרת: deny משלו או אזהרה חלה כרגיל. מה זה לא יכול לעשות הוא **לנקות** כלום, מכיוון שפסק דין שנמסר בחלק מקריאה אינו פסק דין בקריאה. כך כל דחייה של מדיניות עומדת, והקריאה נרשמת כ-fallback עם הסיבה `request-cut`, אשר `failproofai jev status` מסכומת לצד הסיבות למעלה. הכלל זה נותן לך: הגדלת קריאה יכול לעלות לה את ה-clearances שלה, ותמיד לא יכול לקנות אחד.

**הודעה לא התאימה.** הנחיה ארוכה שהדבקת, ההודעה האחרונה של הסוכן, או הנחיה שמפקד המעריך הזה כבר הוגבלה. **כלום לא משתנה**: הקריאה שפוטה, נמחקה ונרשמה בדיוק כמו כל אחרת, וזה לא נספר כ-fallback. אורך מה שאתה הקלדת לעולם לא מחליט פסק דין, וחתך לא יכול לייצור הסכמה: כאשר הנחיה הגיעה כבר מוגבלת, "לא ביקשת זאת" מפסיק להיות מסקנה שיכולה להיות שנמשכה מזה בכלל, במקום שתהפוך לאחת.

הקו בין השניים הוא מי כתב את הטקסט. הקריאה היא של הסוכן, וכלל שתן את אורכו לחסר חומרה היה כלל הסוכן יכול להשתמש; ההנחיה שלך היא שלך, ולטיפול בעורך שלה כאות רק אי פעם מועד הדבקת spec או stack trace.

## מה עוזב את ה-machine

לכל קריאת כלי Jev מעריך, בקשה אחת הולכת לספק שלך, נושא:

- קריאת הכלי עצמה, עם סודות כמו מפתחות API, bearer tokens והקצאות `KEY=` משומרות;
- ההנחיות האחרונות שהקלדת, עם טקסט שה-harness של הסוכן שלך הוסיף הוסרו;
- ההודעה האחרונה של הסוכן לפני ההנחיה האחרונה שלך, שמותג כסוכן-כתוב;
- עובדות מחושבות באופן מקומי, כגון אם נתיב בפנים הפרויקט — האחד שה-session היה בו בקריאה ראשונה ממש, [קבוע לסשן](/he/reference/jev-intent#the-project-root) — והענף git הנוכחי.

זה הולך רק לנקודת הקצה בתצורה שלך, תחת המפתח שלך.

## כבה את זה

```bash
failproofai jev remove
```

זה מוחק את `~/.failproofai/jev.json`. מהקריאה הבאה, hooks מריצים את מדיניויות ה-regex בדיוק כפי שלפני. ה-per-session stores תחת `~/.failproofai/state/semantic/` (הנחיות מוקלטות ב-`sessions/`, roots פרויקט ב-`roots/`) משארים במקום וגיל החוצה. כדי להפסיק לשאול את Jev אך לשמור את התצורה, השתמש `failproofai jev setup --mode off` במקום.

## Commandה reference

| פקודה | תוצאה |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | הגדר זאת בפקודה אחת; הספק מגיע מה-URL's host |
| `failproofai jev --url <url> --token <token>` | אותו דבר, עם המפתח בשורת הפקודה — ההיסטוריה וה-process list שלך רואים אותו |
| `failproofai jev setup --provider <kind> --key-stdin` | כתוב את התצורה מ-key צנור ב-stdin |
| `failproofai jev setup --provider <kind>` | אותו דבר, בשאילת המפתח ב-prompt מוסווה |
| `failproofai jev setup --key-from-env` | אל תאחסן מפתח; קרא `FAILPROOFAI_JEV_API_KEY` לכל סשן |
| `failproofai jev setup --mode observe` | החלף מצב (`enforce`, `observe` או `off`), שומר את המפתח המאוחסן |
| `failproofai jev setup --model <id>` / `--base-url <url>` | משנה את הדגם או ה-API base; `default` מנקה את ה-override |
| `failproofai jev setup --timeout-ms <n>` | שנה את התקציב לכל-קריאה |
| `failproofai jev status [--json]` | תצורה, הרשויות ופעילות אחרונה; לעולם לא המפתח |
| `failproofai jev test [--json]` | בקשה חיה אחת: latency והגרסה שענתה |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | מזהי הדגם שה-`/models` של נקודת הקצה דיווחים, סימון הקונפיגורציה |
| `failproofai jev remove` | מחק את התצורה; Jev off |
