הרץ את `failproofai` ללא ארגומנטים כדי להפעיל את לוח הבקרה המובנה ב-`http://localhost:8020`. הוא קורא היסטוריות סוכנים מקומיות, תצורת מדיניויות, תוצאות ביקורות ופעילות hook ישירות מהמכונה.

במכונה שלא הוגדרה, הפקודה הישירה מבצעת הגדרה לראשונה לפני שהיא פותחת את לוח הבקרה. היא עושה זאת רק בטרמינל אינטראקטיבי: בצינור או ב-CI, היא הדפסת רמז חד-שורה ופותחת את לוח הבקרה, מכיוון שאשף שלא מישהו יכול לענות עליו לעולם לא צריך לחסום את הפקודה שהקלדת. הגדר `FAILPROOFAI_NO_FIRST_RUN=1` כדי לדלג על החיתוי לחלוטין ולעבור ישירות ללוח הבקרה.

לוח הבקרה המקומי הוא נפרד מ-Failproof AI Cloud. הוא פועל ללא חשבון Cloud ואינו מוכיח שאירועים הועברו לארגון שלך. במכונה שסיימה הגדרה, ההחלטות שהוא מציג נעשו על ידי ה-daemon של `failproofaid`, שהוא ההערך היחיד שם; במכונה שלא הוגדרה, hook מעריכים בתוך התהליך.

## אזורי לוח הבקרה

| אזור | מה אתה יכול להשיג |
| --- | --- |
| Policies → Activity | בדוק החלטות מקומיות של allow, instruct ו-deny; סנן לפי החלטה, אירוע, CLI, מקור, מדיניות והפעלה. |
| Policies → Configure | הפעל מדיניויות מחבילה מותקנת, ערוך פרמטרים נתמכים, החלף מדיניויות מקובלות וקנוניות שהתגלו, ובחר harnesses יעד. |
| Projects | דפדף בפרויקטים שהתגלו בכל היסטוריות הסוכנים הנתמכות והשווה את ההפעלות העדכניות ביותר שלהם. |
| Project sessions | פתח תדיווח מקומי אחד, בדוק ערכים מסודרים גולמיים ותת-סוכנים, הורד אותו וקשור את פעילות המדיניות. |
| Audit | בדוק את הסריקה הלא מקוונת האחרונה, דפוסים מסוכנים, חוזקות, פרויקטים מושפעים ומדיניויות builtin מוצעות. |
| Settings | קביעת תצורה של סריקות מקומיות מתוזמנות ודוחות ביקורת בדוא״ל כאשר ה-daemon/platform תומכים בהם. |

## בדוק את פעילות המדיניות

<Tabs>
  <Tab title="Dashboard">
    1. פתח **Policies → Activity** והגדר את מסננים ההחלטה והמקור.
    2. צמצם לפי אירוע, harness, שם מדיניות או הפעלה.
    3. השורה נושאת את ההחלטה, האירוע, ה-harness, הכלי, המדיניות, מצב ההרשאה ומשך הזמן. הרחב אותה כדי לקבל את הסיבה המלאה, כל מדיניות תואמת, המקור המחליט, פריסת הענן והספרייה העובדת של ההפעלה ונתיב התדיווח. שם הכלי מוצג בשורה אך אינו מסנן.
    4. עקוב אחר קישור ההפעלה כדי למקם את ההחלטה בהקשר תדיווח.

    שורה שנראית כמו denied עדיין יכולה להיות תצפיתית על צמד harness/event שלא צורך פסקי דין חוסמים. תצוגת הפרטים מדגישה יכולת אכיפה מאומתת.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai config --status
    failproofai policies
    failproofai
    ```

    פעילות מקומית מאוחסנת תחת `~/.failproofai/hook-activity`. השתמש בלוח הבקרה במקום לערוך קבצים אלה.
  </Tab>
</Tabs>

## קביעת תצורה של מדיניויות באופן מקומי

<Tabs>
  <Tab title="Dashboard">
    1. פתח **Policies → Configure** ובחר את ה-harnesses ותחום התצורה. הכרטיסייה ניתנת לטיפול ישירה ב-`http://localhost:8020/policies?tab=policies`.
    2. הפעל מדיניות מחבילה מותקנת, או מדיניות מקובלת או קנונית שהתגלתה.
    3. עבור מדיניות פרמטרית, פתח את בקרת התצורה שלה והצל ערכים נתמכים.
    4. חזור ל-Activity והפעל פעולות תואמות ושאינן תואמות.

    הרשימה ריקה עד שחבילה מותקנת — בנייה זו אינה מהדרת מדיניויות משלה, אז הרץ קודם `failproofai policies add FailproofAI/policies`. מדיניויות קנוניות מציגות את המקור של הפרויקט או המשתמש שלהם. שינויים בנתיב מקום מפורש עשויים לדרוש הפעלה מחדש של קונפיגורציית CLI כך שהנתיב הנבחר יתועד.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai policies show FailproofAI/policies
    failproofai policies add block-sudo --scope project
    failproofai policies --install --custom ./security.policies.ts --scope project
    failproofai policies
    ```

    `policies show <owner>/<repo>` קורא את תוכן החבילה לפני התקנתה. `--scope` לוקח `user`, `project` או `local`; רק Claude Code תומך ב-`local`, ו-Hermes ו-OpenClaw לוקחים `user` בלבד.
  </Tab>
</Tabs>

## עיון בפרויקטים והפעלות

עמוד הפרויקטים משלב חנויות היסטוריה מקומיות נתמכות. בחר פרויקט כדי לרשום את ההפעלות שלו, ואז פתח הפעלה עבור בתצוגת יומן גולמית, קטעי תת-סוכנים, פעולת הורדה ופעילות מדיניות בהיקף הפעלה.

אם פרויקט או הפעלה חסרים, אשר שה-harness משתמש בנתיב ההיסטוריה שלו כברירת מחדל או רשום שורש נוסף עם `failproofai harness add-path <harness> [<label>=]<path>`.

## תזמון ביקורות לא מקוונות

<Tabs>
  <Tab title="Dashboard">
    פתח **Settings**, הפעל סריקה מתוזמנת, בחר את המרווח הנתמך שלו, וקביעת תצורה של משלוח דוחות כשזה זמין. הדף דיווחים על ההרצה הבאה, ההרצה האחרונה, קוד היציאה ואם ה-daemon בשימוש배경י נתמך בפלטפורמה.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai audit --schedule 7 --email reliability@example.com
    failproofai audit --status
    ```

    שנה את מספר הימים כדי להגדיר מרווח שונה של 1-90 ימים. בטל סריקות חוזרות ונשנות עם `failproofai audit --no-schedule`, המוקדש את הטיימר ומשאיר אותך מחובר; הרץ `failproofai audit` עבור סריקה אינטראקטיבית מיידית.

    תזמון חותם אותך בפעם הראשונה, מכיוון שהממצאים נשלחים בדוא״ל. `--email <address>` מספק את הכתובת מראש והדלג על הנתיב כניסה.
  </Tab>
</Tabs>

<Note>
  ניתוח וממצאים נשארים במכונה זו. טלמטריית CLI אנונימית נשלחת כברירת מחדל אלא אם תגדיר `FAILPROOFAI_TELEMETRY_DISABLED=1`. סריקות מתוזמנות גם שולחות מטאנתונים של מכונה ועשויות לשלוח עדכון מוגבל של ממצאים לאחר הסכמת בחירה.
</Note>

<Warning>
  לוח הבקרה המקומי יכול להציג הנמקות, קלט כלי, תוכן קובץ וקצה מחוברות מהיסטוריות סוכנים מקומיות. כבול אותו רק לממשקים מהימנים ועצור את התהליך כאשר הביקורת הסתיימה.
</Warning>
