מדיניות מותאמת אישית הופכת דפוס כישלון מהעקבות או ביקורות שלך להחלטה שפועלת בזמן שסוכן עובד. מדיניות יכולה לאשר פעולה, לתת הנחיות לסוכן, או לשלול את הפעולה לפני שהיא גורמת לתקרית נוספת.

השתמש במדיניות מותאמת אישית כאשר ההתנהגות תלויה בכלים שלך, בנתיבים, בפקודות, בסביבות, או בכללי ההפעלה שלך. בדוק את [קטלוג המדיניות המובנה](/he/policies/builtin-catalog) תחילה כדי שלא תיצור בחזרה שליטה קיימת.

## התחל עם כלל צר

מדיניות זו חוסמת פקודות Kubernetes הרסניות רק כאשר הפקודה מכוונת לייצור. כל דבר אחר מחוץ לדפוס כישלון זה בדיוק מחזיר `allow()`.

```ts
import { customPolicies, allow, deny } from "failproofai";

const DESTRUCTIVE_KUBECTL = /\bkubectl\s+(delete|replace)\b/i;
const PRODUCTION_TARGET = /(?:--context|--namespace|-n)\s+(prod|production)\b/i;

customPolicies.add({
  name: "block-destructive-production-kubectl",
  description: "Block destructive Kubernetes commands against production",
  match: { events: ["PreToolUse"] },
  fn: async ({ toolName, toolInput }) => {
    if (toolName !== "Bash") return allow();

    const command = String(toolInput?.command ?? "");
    if (!DESTRUCTIVE_KUBECTL.test(command)) return allow();
    if (!PRODUCTION_TARGET.test(command)) return allow();

    return deny(
      "Destructive production Kubernetes commands require the approved deployment workflow.",
    );
  },
});
```

מדיניות טובות צרות מספיק כדי להסביר במשפט אחד. תאם את הפעולה הניתנת לצפייה — לא את הכוונה שאתה מקווה שהסוכן היה בעל — והחזר `allow()` ברגע שהכלל לא חל.

## בחר החלטה

| עוזר | תוצאה | השתמש בו כאשר |
| --- | --- | --- |
| `allow(reason?)` | הפעולה ממשיכה. | המדיניות לא חלה או הפעולה בטוחה. |
| `instruct(reason)` | הפעולה ממשיכה, והסיבה מועברת לסוכן בהרנסים שיש להם ערוץ לכך. | אתה רוצה להנחות את הסוכן לכיוון גישה טובה יותר מבלי להטיל משתנה. |
| `deny(reason)` | הפעולה חסומה בהרנס ובזוגות אירועים המאומתים לצריכת פסק דין חוסם. | הפעולה חייבת שלא תתקדם. |

כתוב את הסיבה לסוכן שחייב להתאושש. הסבר מה זוהה ומה הוא צריך לעשות במקום זאת.

### היכן `instruct()` בעצם מגיע

`instruct()` זקוק לערוץ הקשר נוסף בהרנס. שישה הרנסים אין לפחות באירועים מסוימים או בכל אירועים; שם הפעולה מותרת וההודעה נכתבת ל־stderr, שם הסוכן לעולם לא קורא אותה.

| הרנס | אירועים המספקים את ההנחיה |
| --- | --- |
| Claude, Codex, Copilot, Cursor, Devin, OpenCode | `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, and `PermissionRequest` נושאים אותה כהקשר נוסף. `Stop` ו־`SubagentStop` נושאים אותה דרך ערוץ ההנסה במקום זאת. כל אירוע אחר פולט הודעה שהרנס מתעלם ממנה. |
| Antigravity | `UserPromptSubmit` and `Stop` בלבד. |
| Factory, Pi, OpenClaw | `Stop` בלבד. |
| Hermes, Goose | אין. תמיד אפשר בתוספת הערה stderr. |

שום הרנס לא יורה את כל 29 האירועים הקנוניים, כך שהשורה הראשונה מוגבלת על ידי מה שכל אחד מתקין — הנחיה מגיעה רק לאירוע שהרנס זה בעצם יורה. בדוק את קבוצת האירועים המותקנת לכל הרנס ב־[Agent harnesses](/he/reference/harnesses) לפני שאתה מסתמך על אחד.

<Warning>
  אל תשתמש ב־`instruct()` לגבול בטיחות. בהרמס וגוז הוא לעולם לא מגיע לסוכן כלל, ובـ Antigravity, Factory, Pi, and OpenClaw הוא לא מגיע אליו לאירועי כלים. השתמש ב־`deny()` כאשר הפעולה חייבת להיות מונעת.
</Warning>

## אובייקט מדיניות

```ts
customPolicies.add({
  name: "policy-name",
  description: "What this policy prevents",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => allow(),
});
```

| שדה | נדרש | תיאור |
| --- | --- | --- |
| `name` | כן | מזהה יציב עבור המדיניות. שמור על שמות ייחודיים בקבצים. |
| `description` | לא | מטרה קריאה לאדם המוצגת בתיאורים ובהחלטות של מדיניות. |
| `match.events` | לא | סוגי אירועים המוזמנים את המדיניות. השמטת `match` מזומנת זה לכל אירוע זמין. |
| `fn` | כן | פונקציה סינכרונית או אסינכרונית החוזרת לתוצאה `allow`, `instruct`, או `deny`. |

סנן כלים בתוך `fn`. `match.toolNames` אינו חלק מסוג המדיניות המותאמת אישית הציבורי.

מדיניות שפורסמה בתוך חבילה עשויה להכיל שני שדות נוספים, `category` ו־`defaultEnabled`. ראה [From a file to a pack](#from-a-file-to-a-pack).

## הקשר מדיניות

כל מדיניות מקבלת `PolicyContext`.

| שדה | סוג | מה הוא מכיל |
| --- | --- | --- |
| `eventType` | `HookEventType` | אירוע מנורמל המוערך כרגע. |
| `toolName` | `string \| undefined` | שם כלי קנוני כגון `Bash`, `Read`, `Write`, or `Edit`. |
| `toolInput` | `Record<string, unknown> \| undefined` | קלט קנוני עבור קריאת הכלי הנוכחית. |
| `payload` | `Record<string, unknown>` | עומס אירוע מנורמל מלא. |
| `session` | `SessionMetadata \| undefined` | מזהה הפגישה, ספריית עבודה, נתיב תמלול, מצב הרשאה, וונתונים מטא של הרנס כאשר זמין. |
| `cli` | `string \| undefined` | סוכן הרנס המקור, כגון `claude`, `codex`, או `cursor`. |
| `params` | `Record<string, unknown>` | פרמטרים עבור מדיניות זו. מדיניות מובנית או חבילה מצהירה סכמה, והערכים שהמשתמש הגדיר מתמזגים על ברירות המחדל שלה. מדיניות בקובץ מותאם אישית לא מצהירה סכמה, כך שהיא מקבלת כל מה שהמשתמש הגדיר תחת שמה, ו־`{}` כאשר כלום לא הוגדר. |

התייחס לכל ערך אופציונלי כאלטרנטיבי באמת. גרסאות סוכן וסוגי אירועים לא כולם מספקים את אותם שדות.

### קלטי כלים נפוצים

Failproof AI מנרמל כלים נפוצים על פני הרנסים נתמכים כדי שמדיניות בדרך כלל יכולה להשתמש בצורת קלט אחת.

| כלי | שדות נפוצים |
| --- | --- |
| `Bash` | `command` |
| `Read` | `file_path` |
| `Write` | `file_path`, `content` |
| `Edit` | `file_path`, `old_string`, `new_string` |
| `Grep` | `pattern`, `path` |

השתמש בהכפשה הגנה כי ערכי קלט כלים מוקלדים כ־`unknown`:

```ts
const command = String(ctx.toolInput?.command ?? "");
const filePath = String(ctx.toolInput?.file_path ?? "");
```

## בחר את האירוע

| אירוע | מתי הוא רץ | שימוש טיפוסי |
| --- | --- | --- |
| `PreToolUse` | לפני שכלי מבצע. | חסום או הנחה פקודות, כתיבות, קריאות, ופעולות חיצוניות. זה השומר. |
| `PostToolUse` | לאחר שהכלי כבר בוצע. | בדוק או החלף את התוצאה שהמודל קורא. זה לא יכול לבטל את ההשפעה הצדדית — הכתיבה או הפקודה כבר התרחשו — ובעשרה משנים עשרה הרנסים הפסק דין לא יכול לעצור כלום. רק Codex ו־Copilot צורכים אותה, ואפילו שם היא מחליפה את התוצאה שהמודל קורא במקום למנוע את הקריאה. אל תשתמש בה בתור שומר. |
| `PermissionRequest` | כאשר הסוכן מבקש הרשאה. | החל כללי הרשאה ספציפיים לארגון. |
| `UserPromptSubmit` | לפני שהנושא שהוגש ממשיך. | דחה הנחיות אסורות או הוסף הנחיית זרימת עבודה. |
| `Stop` | כאשר הסוכן מנסה לסיים. | דרוש תנאי השלמה ניתן להשגה, כגון שלב אימות מקומי. |
| `SubagentStop` | כאשר תת־סוכן מנסה לסיים. | שער עבודה משתנה לפני שהוא חוזר להורה. |
| `SessionStart` / `SessionEnd` | בגבולות הפגישה. | תיעוד או בדיקת מצב ברמת הפגישה. |

זמינות אירוע וההתנהגות החוסמת תלויה בסוכן הרנס, וההבדלים גדולים: Failproof AI לא מתקין ווי `Stop` עבור Goose או Hermes, כך ששער עצור לעולם לא יורה לאחד מהם. ראה [Agent harnesses](/he/reference/harnesses) לפני שאתה מסתמך על אירוע על פני fleet מעורבב.

<Accordion title="כל שמות אירועי המדיניות">
  `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `Elicitation`, `ElicitationResult`, `UserPromptExpansion`, `PostToolBatch`, and `Setup`. זה הסט המלא של 29 שמות אירועים קנוניים שכל קבוצת אירועים משלו של הרנס מנורמלת אליו.
</Accordion>

## כתוב דפוסי מדיניות נפוצים

### חסום כתיבות לנתיבים מוגנים

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "block-generated-file-edits",
  description: "Require generated files to be changed through their generator",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();

    const filePath = String(ctx.toolInput?.file_path ?? "");
    if (!/(^|\/)(dist|generated)\//.test(filePath)) return allow();

    return deny("Edit the source and run the generator instead of changing generated output.");
  },
});
```

### תן הנחיות שאינן חוסמות

```ts
import { customPolicies, allow, instruct } from "failproofai";

customPolicies.add({
  name: "prefer-reviewed-deploy-command",
  description: "Guide agents toward the reviewed deployment wrapper",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();

    const command = String(ctx.toolInput?.command ?? "");
    if (!/^kubectl\s+apply\b/.test(command.trim())) return allow();

    return instruct("Use ./scripts/deploy-reviewed instead of invoking kubectl directly.");
  },
});
```

### סגור השלמת הפגישה

```ts
import { execFileSync } from "node:child_process";
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "require-clean-typecheck",
  description: "Require the project typecheck to pass before the agent finishes",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow();

    try {
      execFileSync("bunx", ["tsc", "--noEmit"], {
        cwd,
        stdio: "ignore",
        timeout: 8_000,
      });
      return allow();
    } catch {
      return deny("Fix the typecheck errors before finishing the task.");
    }
  },
});
```

<Warning>
  אירוע `Stop` שנדחה יכול לגרום לסוכן להנסות שוב. סגור רק על תנאי שהסוכן יכול לספק בסביבה הנוכחית, וחסום כל קריאה לתת־תהליך או לרשת.
</Warning>

## טעון קבצי מדיניות

### קבצי כינוס

קבצי כינוס טוענים באופן אוטומטי:

```text
<project>/.failproofai/policies/security-policies.ts
~/.failproofai/policies/personal-policies.mjs
```

- ספריות מדיניות של פרויקט ומשתמש טוענות שתיהן.
- קבצים טוענים באופן אלפביתי בתוך כל ספרייה.
- קובץ חייב להסתיים ב־`policies.js`, `policies.mjs`, או `policies.ts`.
- מספר קריאות `customPolicies.add()` בקובץ אחד נתמכות.
- יבוא יחסי מודולים מקומיים נתמכים.
- מדיניות פרויקט יכולות להיות מחויבות כך שאותם כללים עוקבים אחר המאגר.

<Warning>
  קובץ בספרייה שלא שמו מסתיים ב־`policies.{js,mjs,ts}` מדולג. הוא נראה מותקן ולא אוכף כלום. הטוען רשימה כל קובץ מדולג עם השם לשינוי שם אליו; קרא את האזהרה זו במקום להניח שמדיניות היא חיה. מאגר זה נמסר `block-version-bumps.mjs` בצורה זו, והשומר הכתוב לאחר בדיקת גרסה גרועה מעולם לא רץ פעם אחת.
</Warning>

`~/.failproofai/policies/` גם מכיל שתי תיקיות שלא שמת שם: `cloud-policies/` להפצות מנוהלות ב־fleet ו־`packs/` לחבילות מותקנות. הטוען לעולם לא יורד לשניהם, כך שכלום בהם לא נעשה בחזקה כמדיניות כינוס לא מאומתת.

### כבה מדיניות מגולה

שני מפתחות ב־`policies-config.json` מנתקים מדיניות כינוס ללא מחיקה או שינוי שם הקובץ:

| מפתח | השפעה |
| --- | --- |
| `disabledCustomPolicies` | מערך של מזהי מדיניות מוקבעי מקור שלא רשומים. |
| `customPoliciesEnabled` | קבע ל־`false` כדי להפסיק את טעינת `.failproofai/policies/` לחלוטין. ההעדרות פירושה מופעל. |

הכרטיסייה **Policies → Configure** של [לוח המחוונים המקומי](/he/reference/local-dashboard) כותבת `disabledCustomPolicies` עבורך. `customPoliciesEnabled` כתוב על ידי `failproofai config`, או ביד.

### קבצים מפורשים

השתמש בנתיבים מפורשים כאשר אימות או תצורה צריכה לשנות את קובץ הרשומה ישירות:

```bash
failproofai policies --install \
  --custom ./security.policies.ts \
  --custom ./workflow.policies.ts \
  --scope project
```

קבצים מפורשים טוענים ראשונים, ואחריהם קבצי כינוס של פרויקט וקבצי כינוס של משתמש. קובץ שהתגלה דרך שני נתיבים טוען פעם אחת.

## אימות ובדיקה

`-c` היא הצורה הקצרה של `--custom`, ו־`-i` של `--install`. הוא אוכף את הקובץ כעת, בכל נתיב וללא שם קובץ:

```bash
failproofai policies -i -c ./checkout-policies.ts
failproofai policies
```

בקש מהסוכן שלך לעשות את הדבר שחסמת וראה שהוא מסרב. כלום לא פורסם ולשום מכונה אחרת זה לא משפיע עליה.

אימות מבצע את המודול דרך הטוען בייצור ומאשר שהוא רושם לפחות מדיניות אחת. זה תופס קבצים חסרים, שגיאות תחביר, יבואים לא פתורים, חריגים ברמה העליונה, וחיכויים של טעינת מודולים. זה לא מוכיח שהוגיקה ההתאמה שלך נכונה.

בדוק לפחות במקרים אלה:

- פעולה אחת שחייבת להתאים ולייצר את הסיבה המדיניות המיועדת.
- פעולה סמוכה אך בטוחה שחייבת להחזיר `allow()`.
- שדות כלים חסרים או מעוותים.
- תחביר פקודה חלופי, נתיבים, ציטוטים, רישוי, ורווחים.
- תת־תהליך או תלות רשת לא זמינה.

ייחס את התוצאה למדיניות המותאמת אישית שלך תחת **Policies → Activity** ב־dashboard המקומי. בדיקה חסומה לא מספיקה אם מדיניות מובנית אחרת קיבלה את ההחלטה.

## התנהגות זמן ריצה

- מדיניות מובנית מעריכה לפני מדיניות מותאמת אישית.
- הראשון `deny` מעצור הערכת מדיניות נוספת.
- מספר תוצאות `instruct` יכול להיות משולב כאשר שום מדיניות לא שולל את האירוע.
- לפונקציה מדיניות יש מועד ביצוע של 10 שניות. טעינת מודול ברמה העליונה יש את אותו הדבר.
- חריג שהוטל או חיכוי מנוהל ומטופל כ־`allow()`.
- קובץ כינוס שנכשל בטעינה מדולג; קבצים מותאמים אישית אחרים ומדיניות מובנית המשכו.
- Observe mode מריץ את המדיניות בפועל ורושם כל פסק דין שאינו אפשור ללא אכיפתו. שתי שכבות קובעות זאת: `failproofai publish --effect observe` על חבילה שאתה מפרסם, ו־`fp fleet deploy <machine> --add <id>:observe` בהפצת ענן. כל דרך המדיניות מוערכת תחת אותו מועד 10 שניות כמו אחת אוכפת, כך שמדיניות שחיכוי רושמת כאפשור.

### היכן הטוען נכשל בחסום במקום

כלל הגיע-פתוח לעיל מכסה קובץ שירדת לעצמך. שני נתיבים כוונה עושים את ההיפך, כי שניהם מתכוונים שמכונה זו נאמרה לה שיש לה אכיפה שאין לה.

| מצב | תוצאה |
| --- | --- |
| לא ניתן לטעון חבילה שנבחרה, או הדיגסט המקובע שלה לא תואם | כל אירוע בתחום שהחבילה הצהירה שלו מדולג, המיוחס ל־`pack/failproofai-pack-unavailable`. `UserPromptSubmit` מנחה במקום שליל, כך שלעולם לא נעול מחוץ לסוכן שאתה זקוק אליו כדי לתקן אותו. מטא נתונים חבילה לא קריאים מרחיבים את התחום שלל במקום לצמצם אותו. |
| ה־`failproofaid` daemon לא יכול להיות מושג על מכונה שסיימה התקנה | כל אירוע מדולג. אף קונפיג לא נקרא ואף מדיניות מותאמת אישית לא רצה, כי daemon שלא יכול היה להיות מושג לא היה יכול לרוץ אותם. חוסר התאמה של גרסת פרוטוקול שולל גם, עם הודעה שמנויה `failproofai config`. |

על מכונה שסיימה התקנה, `failproofaid` הוא המעריך היחיד, כך ש־`fn` שלך רץ בתוך העובד החם של דומון במקום בתהליך התפס. לקוח ההתפס מאפשר 150 ms להתחבר ו־30 שניות לתשובה, בנוחות מעל מועד 10 שניות קבוע שכל פונקציה מדיניות מקבלת.

שמור מודולי מדיניות דטרמיניסטיים ומהירים. הימנע מקריאות רשת ברמה העליונה או התחלת שרת. עבודה קשורה בתוך `fn`, תופס כשלים בתלות, בחר בזהירות אם כשל זה צריך להאיר או לשלול את הפעולה.

## מקובץ לחבילה

חבילה היא כיצד קובץ מדיניות הופך למשהו שמכונות אחרות יכול להתקין. שתי פקודות לוקחות אותך מכלום לחבילה שפורסמה:

```bash
failproofai publish --init
failproofai publish
```

`--init` שואל מה החבילה נקראת, כותבת `<name>.mjs`, ועוצרת. הקובץ אינו תבנית עם ריקים — היא מדיניות אחת שכבר חוסמת `git push --force`, כך שהדבר הראשון שאתה עורך היא משהו שעובד. הוכח את זה ברמה עם `failproofai policies -i -c ./<name>.mjs`, ואז הרץ `failproofai publish` מתוך מאגר ה־git החוזק לו.

שני שדות חשובים ברגע שמדיניות נמסרת בחבילה:

| שדה | מה הוא עושה |
| --- | --- |
| `category` | מה `failproofai policies add <owner>/<repo> --category git,database` בוחר. |
| `defaultEnabled` | האם `failproofai policies add <owner>/<repo>` פשוט מנעה מדיניות זו על. ברירות למחדל ל־`false`. |

`--effect` קבוע לכל חבילה במקום לכל מדיניות: `failproofai publish --effect observe` מפרסמת חבילה שתיעוד מה המדיניות שלה היה החליט וחוסמת כלום. ברירת המחדל היא `enforce`. זה observe mode על מכונה יחידה ללא חיבור ענן — קרא את הפסקות השומר חזרה תחת **Policies → Activity** ב־dashboard המקומי.

גרסת החבילה היא ה־12-תו sha קצר לתת־זקיפה שנבנתה ממנו, כך ש־`publish` מסרבת מחוץ לעיון git וב עץ עמום. ראה [Publish a pack](/he/policies/publish-a-pack) לזרימה המלאה, ו־[Policy packs](/he/policies/packs) לאופן פתרון בתקן גרסה.

## ייצוא API

| ייצוא | מטרה |
| --- | --- |
| `customPolicies.add(policy)` | הרשם מדיניות מותאמת אישית כאשר המודול טוען. |
| `allow(reason?)` | אפשור את הפעולה. |
| `instruct(reason)` | אפשור את הפעולה וספק הנחיה כשנתמך. |
| `deny(reason)` | חסום את הפעולה כשנתמך. |
| `getCustomHooks()` | החזר את המדיניות שנרשמה כרגע בתמליל רישום המודול. |
| `clearCustomHooks()` | נקה תמליל זה, בעיקר לבדיקות וטוענים. |

TypeScript ייצוא `PolicyContext`, `PolicyResult`, `CustomHook`, `PolicyDecision`, and `PolicyFunction`.
