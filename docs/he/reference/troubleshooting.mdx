כשלים רשתיים זמניים ותגובות HTTP 408, 429 או 5xx משאירות טלמטריה זכאית לניסיון חוזר אוטומטי, אפילו לאחר הפסקה ארוכה. הדמון שומר את ההצגה עד להכרה בהעברה. דחיית `event_too_large` דורשת עומס אירוע קטן יותר לפני ניסיון חוזר. קבצים שכבר סומנו כ`.poison` זקוקים לשחזור ידני; עדכון אינו שולח אותם מחדש באופן אוטומטי.

  <Accordion title="המכונה לא מקבלת מדיניות">
    <Tabs>
      <Tab title="Dashboard">
        פתח **Admin → enforcement**, בחר את המכונה, והשווה את הגרסאות המוקצות, המדווחות והקודמות שלה. אשר שהיקף ההצבה כולל את המכונה ולמפתח שלה יש `policies:pull`. ספיגה יכולה לעבוד גם כשהעברת מדיניות לא.

      </Tab>

        ```bash

        failproofai update
        failproofai config --status
        ```

        אשר שמזהה המכונה והתווית תואמים את היעד של לוח המחוונים. התחבר מחדש עם מפתח המסוגל למדיניות אם התביעה הקיימת מעניקה רק ספיגה של אירועים.
      </Tab>

  <Accordion title="Cloud עצמי המאופשר עם רשות הנפקה פרטית לא מקבל אירועים או מדיניות">
    <Tabs>
      <Tab title="Dashboard">
        המכונה התחברה וההוקים שלה עובדים, אך **Observe → Events** נשאר ריק ו-**Admin → enforcement** לעולם לא מציג את ההצבה שלו כמיושם. ממשק שורת הפקודה והדמון Failproof סומכים על תעודות בצורה שונה. ממשק שורת הפקודה פועל ב-Node ומכבד `NODE_EXTRA_CA_CERTS`. `failproofaid`, המשלח אירועים ומושך מדיניות, סומך על התעודות המאופשרות איתו בתוספת חנות האמון של מערכת ההפעלה, והתעלם מ-`NODE_EXTRA_CA_CERTS`. התקן את CA שלך בחנות המערכת במכונה.
      </Tab>
      <Tab title="CLI">
        ```bash
        # Debian / Ubuntu
        sudo cp company-ca.pem /usr/local/share/ca-certificates/company-ca.crt
        sudo update-ca-certificates
        # RHEL / Fedora
        sudo cp company-ca.pem /etc/pki/ca-trust/source/anchors/ && sudo update-ca-trust
        # macOS
        sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain company-ca.pem

        # then restart the daemon, which loads trusted certificates at start
        sudo systemctl restart failproofaid@$USER                           # Linux
        sudo launchctl kickstart -k system/ai.failproof.failproofaid.$USER  # macOS
        ```

        רישום הדמון קורא את הסיבה: `sudo journalctl -u failproofaid@$USER | grep UnknownIssuer` ב-Linux. `SSL_CERT_FILE` או `SSL_CERT_DIR` בסביבת השירות מחליפים את חנות המערכת לדמון, והתעודות המאופשרות עדיין חלות. הצגות שנכשלו בזמן שה-CA לא היה סמוך נשמרות ב-`~/.failproofai/state/failed` ומנסות שוב באופן אוטומטי, בערך שעה וכאשר הדמון מופעל מחדש.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="פעולה מוסכמת מכיוון שהדמון אינו זמין">
    <Tabs>
      <Tab title="Dashboard">
        פתח **Admin → enforcement** ובדוק את זמן הראייה האחרונה של המכונה וגרסה מדווחת. אם המכונה מיושנת, התייחס לזה כבעיה דמון מקומית. אל תחליש את המדיניות המוכנסת רק כדי לעקוף דמון לא זמין.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        הפעל מחדש או עדכן את `failproofaid`; הפעל קביעה מחדש כאשר גרסאות פרוטוקול CLI ודמון שונות. נתיב הדמון המוגדר נכשל בעיצוב סגור.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="מדיניות מותאמת אישית אינה נטענת">
    <Tabs>
      <Tab title="Dashboard">
        למדיניות שנכתבה ב-Cloud, פתח **Admin → policy editor**, בחר את הטיוטה, וסקור שגיאות אימות לפני פרסום. למדיניות מקומית, השתמש בממשק שורת הפקודה כדי לאמתו, ולאחר מכן פתח **Observe → policy** לאחר פעולת בדיקה כדי לאשר שההחלטות מגיעות.

      </Tab>
      <Tab title="CLI">
        אשר שאם השם של הקובץ מסתיים ב-`policies.js`, `policies.mjs`, או `policies.ts`, המודול קורא ל-`customPolicies.add(...)`, ויבוא מפרוק מקובץ המדיניות.

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>

  <Accordion title="ביקורת חוזרת ללא ממצאים">
    <Tabs>
      <Tab title="Dashboard">
        פתח **Analyze → audits**, בחר את הריצה, ובדוק אם ניתוח מודל בוצע. לאחר מכן השווה את ההיקף והחלון שלו עם **Observe → sessions** ופתח עקבות מייצגים מאוכלוסיה זו.

        תוצאה של אפס משמעותית רק כאשר הניתוח בוצע בהצלחה. אם הניתוח דולג או נכשל, הריצה אינה מייצרת ממצאים ושומרת על החלון שלא בוצע ניתוח עבורו עבור ריצה עתידית מוצלחת. אם ניתוח מודל מושבת, הביקורת גם אינה מייצרת ממצאים מכיוון שסריקת הוכחות ראיות ו-PII דטרמיניסטית מתעדת סטטיסטיקה אך כבר אינה מעלה ממצאים.

        ![טופס הביקורת בו סביבה, סוכן, קדנציה וחלון כוח סוח מגדירים את אוכלוסיית ההפעלות.](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        אם הריצה נשארה בתור, המתן לקיבולת ביקורת-סוכן או בקש מהמפעיל של הפריסה לבדוק את צי הביקורת. ביקורת בתור מנסה שוב; היא לא מדולגת מיד.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="הערכות מקוונות אינן פועלות באופן אוטומטי">
    <Tabs>
      <Tab title="Dashboard">
        פתח הפעלה שהושלמה ובדוק אם הערכה ידנית מצליחה. Cloud המארח כרגע אין שליטה בנקודות קצה של מעריך בלוח המחוונים; מפעיל השרת חייב להגדיר אותה.
      </Tab>
      <Tab title="CLI">
        אמת את המעריך עצמו, ולאחר מכן בדוק מצבי הערכה אחרונים:

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        ב-Cloud עצמי, אשר ש-`EVALUATOR_ENDPOINT` קיים בשרת ו-`EVALUATOR_TOKEN` תואם את המעריך. הערכה אוטומטית מושבתת כאשר נקודת הקצה היא חסרה.
      </Tab>
    </Tabs>
  </Accordion>

  <Accordion title="מדיניות חוסמת עבודה תקפה">
    <Tabs>
      <Tab title="Dashboard">
        פתח **Observe → policy**, שמור על ההחלטה וההפעלה המקושרת, וזהה את תנאי החיוב השקרי. לאחר מכן פתח **Admin → enforcement** והחזר את המכונות המושפעות לגרסה הקודמת. יצור גרסה צרה יותר ב-**Policy editor**, בדוק אותה בהיקף קטן, והרחב רק לאחר הצלחה של עבודה תקפה.

      </Tab>
      <Tab title="CLI">
        שחזור פריסה Cloud הוא רק לוח מחוונים. השהיית הפעלה מקומית אינה משבתת מדיניות שמנוהלת ב-Cloud. אם לוח המחוונים אינו זמין, תפוס את מצב המכונה וההצבה והחזר גישה ללוח המחוונים ולא חזור שוב ושוב על הפעולה החסומה.

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="שגיאה מציגה הפניה">
    <Tabs>
      <Tab title="Dashboard">
        שגיאות בלוח המחוונים מסתיימות בהפניה קצרה, למשל `ref 4bf92f35`. זה מזהה את הבקשה היחידה ההיא, וההנהלה יכולה להשתמש בה כדי למצוא בדיוק מה קרה בשרת. העתק אותה לתוך הדוח שלך כמו שהוא מופיע.

        אם עמוד שלם נכשל לטעון, דף השגיאה מציג `digest` במקום זאת. כלול את זה.
      </Tab>
      <Tab title="CLI">
        שגיאות `fp` הניתנות לקריאה של בני אדם מסתיימות באותה `ref`. עם `--json`, אובייקט השגיאה נושא את ה-`request_id` המלא:

        ```bash
        fp --json sessions --since 24h
        ```
      </Tab>
      <Tab title="Daemon">
        כאשר העלאה נכשלת, רישום הדמון מציין `request_id` ו-`batch_id`: ב-Linux, `sudo journalctl -u failproofaid@$USER | grep batch_id`. כל ניסיון מקבל `request_id` משלו; ה-`batch_id` נשאר זהה על פני ניסיונות חוזרים, לכן הוא קושר את הניסיונות של הצגה אחת ביחד. כלול שניהם.
      </Tab>
    </Tabs>
  </Accordion>

בעת יצירת קשר עם התמיכה, כלול את גרסת ממשק שורת הפקודה, הכנס, הסביבה, מזהה הפעלה או פריסה רלוונטי, כל `ref` או `request_id` מהשגיאה, ופלט של `failproofai config --status` עם סודות הוסרו.
