  <Accordion title="אין הפעלות בCloud">
    <Tabs>
      <Tab title="Dashboard">
        פתח **Administration → Keys** ובדוק שמפתח המכונה פעיל ויש לו הרשאת `events:add`. לאחר מכן פתח **Observe → Events**, הרחב את טווח הזמן, והסר מסננים של סביבה וסוכן. אם קיימים אירועים, חפש את ID ההפעלה ולאחר מכן בדוק את **Observe → Sessions** לקיבוץ. אם אין אירועים, בצע אבחון של ה-Failproof daemon מה-CLI.

        ![ה-Events stream החי עם המסננים הראשיים שלו גלויים ואירועי סוכן עדכניים מגיעים.](/images/dashboard/events-stream-current.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait --timeout 60
        fp list envs
        fp events --since 24h --limit 20
        fp sessions --since 24h --limit 20
        ```

        בדוק שהקיפול מופעל, ללמפתח המוגדר יש `events:add`, והמסנן ב-dashboard תואם את הסביבה שנשלחה.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="אירועי Python SDK נותרים בדיסק">
    <Tabs>
      <Tab title="Dashboard">
        הסר מסננים ב-**Observe → Events** וחפש את ID ההפעלה המדויק של ה-SDK. אם שום דבר לא מופיע, בדוק את ה-SDK spool ו-Failproof daemon במכונת המקור.
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait
        ```

        בדוק ש-daemon מורץ ומחובר — ה-SDK משמור תמיד בין אם כן או לא. תיקיית ה-spool **לא** צריכה להתקיים מראש (הכותב יוצר אותה), ואף משתנה סביבה לא בוחר בה: `$FAILPROOFAI_HOME/custom-agents`, או `~/.failproofai/custom-agents`, היא הרק שורש, ו-`configure(base_dir=...)` הוא ההחלפה היחידה. אם התהליך נעצר ב-`SIGKILL` או הוצא מהזיכרון, כל מה שעדיין בתור הושמד — טפל ב-`SIGTERM` כדי להגביל זאת.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="המכונה לא מקבלת מדיניויות">
    <Tabs>
      <Tab title="Dashboard">
        פתח **Admin → enforcement**, בחר את המכונה, והשווה בין הגרסאות המוקצות, המדווחות והקודמות שלה. בדוק שטווח ההצבה כולל את המכונה וההרשאה `policies:pull` למפתח שלה. ספיגה יכולה לעבוד גם כאשר העברת מדיניות לא.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config --status
        ```

        בדוק שה-ID והתווית של המכונה תואמים את היעד ב-dashboard. התחבר מחדש עם מפתח המסוגל להתמודד עם מדיניויות אם הפנייה הקיימת מעניקה רק ספיגת אירועים.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="פעולה נדחתה כי ה-daemon לא זמין">
    <Tabs>
      <Tab title="Dashboard">
        פתח **Admin → enforcement** ובדוק את זמן הראייה האחרון והגרסה המדווחת של המכונה. אם המכונה ישנה, התייחס לכך כבעיה ב-daemon מקומי. אל תחלול את המדיניות המפוותרת רק כדי לעקוף daemon לא זמין.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        הפעל מחדש או עדכן את `failproofaid`; הרץ תצורה מחדש כאשר גרסאות פרוטוקול CLI ו-daemon שונות. נתיב ה-daemon המוגדר נכשל בעיצוב סגור.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="מדיניות מותאמת אישית לא נטענת">
    <Tabs>
      <Tab title="Dashboard">
        למדיניות שנכתבה בענן, פתח **Admin → policy editor**, בחר את הטיוטה, ובדוק שגיאות אימות לפני פרסום. למדיניות מקומית, השתמש ב-CLI לאימות שלה, לאחר מכן פתח **Observe → policy** אחרי פעולת בדיקה כדי לאשר שהחלטות מגיעות.

      </Tab>
      <Tab title="CLI">
        בדוק שהשם הקובץ מסתיים ב-`policies.js`, `policies.mjs`, או `policies.ts`, המודול מקרא את `customPolicies.add(...)`, וההורדות מתחברות מקובץ המדיניות.

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="ביקורת חוזרת ללא ממצאים">
    <Tabs>
      <Tab title="Dashboard">
        פתח **Analyze → audits**, בחר את ההרצה, ובדוק אם ניתוח דגם רץ. לאחר מכן השווה את ההיקף והחלון שלו עם **Observe → sessions** ופתח עקבות מייצגות מאותה אוכלוסייה.

        תוצאה של אפס היא משמעותית רק כאשר הניתוח רץ בהצלחה. אם הניתוח דולג או נכשל, ההרצה לא מייצרת ממצאים ושומרת את החלון שלא נותח פתוח להרצה מוצלחת בעתיד. אם ניתוח דגם מכובה, הביקורת גם לא מייצרת ממצאים מכיוון שסריקת פנייה וPII קובעת סטטיסטיקות אבל כבר לא מעלה ממצאים.

        ![טופס הביקורת שבו סביבה, סוכן, קצב וחלון הסריקה מגדירים את אוכלוסיית ההפעלה.](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        אם ההרצה נשארה בתור, המתן לקיבולת audit-agent או בקש מפעיל ההצבה לבדוק את צי הביקורת. ביקורת בתור מנסה שוב; היא לא דלגה מיד.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="הערכות מקוונות לא רצות באופן אוטומטי">
    <Tabs>
      <Tab title="Dashboard">
        פתח הפעלה שהושלמה ובדוק אם הערכה ידנית הצליחה. Cloud המתוחזקת בענן כרגע אין שליטה של נקודת קצה מעריך בדאשבורד; על מפעיל השרת להגדיר אותה.
      </Tab>
      <Tab title="CLI">
        אמת את המעריך עצמו, ולאחר מכן בדוק מצבי הערכה עדכניים:

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        בענן Cloud המכובד עצמי, בדוק ש-`EVALUATOR_ENDPOINT` קיים על השרת ו-`EVALUATOR_TOKEN` תואם את המעריך. הערכה אוטומטית מכובה כאשר נקודת הקצה חסרה.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="אימות Cloud CLI פונה לארגון שגוי">
    <Tabs>
      <Tab title="Dashboard">
        השתמש במחליף הארגון וודא את ה-slug וההרשאות הצפויים לפני השוואת תוצאות עם ה-CLI.
      </Tab>
      <Tab title="CLI">
        ```bash
        fp whoami
        fp orgs current
        fp orgs perms
        ```

        במצב מפתח API, ציין `fp --org <slug> --api-key <key> ...` או הגדר את `AGENTEYE_ORG`. מצב ארגון הפעלות אדם שמור מתעלמים כוונה לבקשות מפתח API.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="מדיניות חוסמת עבודה תקפה">
    <Tabs>
      <Tab title="Dashboard">
        פתח **Observe → policy**, שמור את ההחלטה וההפעלה המקושרת, וזהה את תנאי החיובי השקר. לאחר מכן פתח **Admin → enforcement** והחזר את המכונות המושפעות לגרסה הקודמת. צור גרסה צרה יותר ב-**Policy editor**, בדוק אותה על היקף קטן, והרחב רק אחרי שעבודה תקפה הצליחה.

      </Tab>
      <Tab title="CLI">
        רולבק של הצבת ענן הוא רק דאשבורד. השהיית הפעלה מקומית לא מבטלת מדיניויות שמנוהלות בענן. אם הדאשבורד לא זמין, תפוס את מצב המכונה וההצבה והחזר גישה לדאשבורד במקום להשתמש ללא הרף בפעולה החסומה.

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

כאשר פונים לתמיכה, כלול את גרסת CLI, הכלי, הסביבה, ID הפעלה או הצבה רלוונטי, והפלט של `failproofai config --status` עם סודות שהוסרו.
