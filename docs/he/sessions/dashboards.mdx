לוחות מחוונים משלבים שאילתות שמורות לתצוגה תפעולית. בנה לוח סביב החלטה שאתה מצפה שמישהו יקבל—לא סביב כל מדד זמין.

לוחות מחוונים הם משטח בענן. לוח המחוונים המקומי ב-`localhost:8020` מכסה פעילות מדיניות, פרויקטים, הפעלות ותוצאות ביקורת, אך אין בו שאילתות שמורות ואין בו אריחים—כך שמכונה שלא התחברה אין בה דבר לבנות כאן. ראה [לוח מחוונים מקומי](/he/reference/local-dashboard).

## בנה לוח מחוונים

<Tabs>
  <Tab title="לוח מחוונים">
    1. עבור ל-**Analyze → Queries**, צור או פתח שאילתה שמורה, ואמת את התוצאה שלה.
    2. בחר **add to dashboard**, ואז בחר לוח קיים או צור אחד תחת **Analyze → Dashboards**.
    3. פתח את לוח המחוונים, היכנס למצב עריכה, סדר מחדש את האריחים, ושמור את הפריסה.
    4. חזור לשאילתה כאשר אתה צריך לשנות את הנתונים או הסינונים שמאחורי אריח.

    ![לוח מחוונים המורכב משאילתות שמורות לנפח אירועים, שגיאות, עיכוב וצריכת token של מודל.](/images/dashboard/dashboard-fleet.png)
  </Tab>
  <Tab title="CLI">
    CRUD של לוח מחוונים אינו חשוף ב-CLI של הענן הנוכחי. השתמש ב-CLI כדי לכתוב ולאמת את השאילתה השמורה, ואז הוסף אותה ללוח מחוונים בממשק המשתמש.

    ```bash
    fp query schema
    fp query run --sql "select count(*) from analytics.events"
    fp query create "event volume" --sql "select count(*) from analytics.events"
    fp query run "event volume"
    ```

    הרץ את SQL עם `--sql` ראשון: הוא מתבצע כנגד בריכת האנליטיקה קריאה-בלבד זהה ללא שמירת כלום, כך שאתה מוצא שם עמודה גרוע לפני שאריח עושה זאת. `--sql @file.sql` קורא את ההצהרה מקובץ במקום. `fp query schema` מוקד את הטבלאות שאפשר לשאול והעמודות שלהן; העבר שם טבלה כדי להצר לאחד.

    שאילתות שמורות מטופלות לפי **שם**, לא לפי id—`fp query run "event volume"`—כי `fp query list` מסתיר את ה-id הגלם אלא אם אתה מעביר `--show-id`. id בעל צורה UUID מתקבל גם כן.

    לאריח עם פרמטרים, קשור כל `$1..$N` פוזיציוני עם `--arg`, שניתן לחזור עליו וקושר לפי סדר: `fp query run <name> --arg checkout-agent`.

    `--limit` ו-`--all` מתאימים את כובע תצוגה הטבלה בלבד; `--json` תמיד מחזיר כל שורה, כ-`{columns: [{name, type}], rows: [[...]], truncated, elapsed_ms}`.

    | תת-פקודה | הרשאה |
    | --- | --- |
    | `query list`, `query show`, `query schema` | `queries:read` |
    | `query create`, `query update` | `queries:write` |
    | `query run` | `queries:run` |
    | `query delete` | `queries:delete` |

    כל תת-פקודה שלוקחת **שם** שאילתה פותרת אותו על ידי רישום שאילתות הארגון ראשון, כך `query create`, `query update`, `query delete` ו-`query run <name>` צריכים `queries:read` בנוסף להרשאה למעלה. רק `fp query run --sql` ו-`fp query schema` לא.

    כלום ב-`fp query` אינו חסום במצב API-key, כך שאפשר ליצור ולאמת שאילתות של לוח מחוונים מ-CI.
  </Tab>
</Tabs>

קבוצות לוח מחוונים שימושיות כוללות:

- **מודלים:** נפח, עיכוב, צריכת token, שיעור שגיאה וציוני הערכה.
- **הערכות:** שיעור הצלחה ומגמות ציון לפי סוכן או סביבה.
- **כלים:** נפח קריאה, שיעור כשלון, משך ופניות חוזרות.
- **ווקים ומדיניויות:** החלטות, שלילות ודירוג תאימות מדיניות.
- **מדדי זרימת עבודה מותאמים:** תוצאות משדות אירועים שלך וSQL.

התחל עם שאילתה שמורה, אמת את התוצאה שלה, ואז הוסף אותה כאריח. שמור סינונים של ייצור ופיתוח מפורשים כך שתעבורת בדיקה לא תחביא ירידה.

<Warning>
  אריח ווק שסופר שורות מדווח על המכנה הלא נכון. בפירוט ווק ברירת המחדל, כל deny ו-instruct פולטים כזוג `hook_triggered` / `hook_completed`, וכל allow במצב observe; allow פשוט מגולגל לכל הפעלה, אירוע, כלי וייחוס מדיניות לדקה לתוך `hook_completed` אחיד הנושא `failproofai_allow_count`. סכום שדה זה במקום ספירת שורות, או fleet שהערך עשרות אלפי קריאות ייראה כאילו הערך כמה מאות. ראה [החלטות מדיניות](/he/sessions/policy-decisions) ו-[Hooks](/he/sessions/hooks).
</Warning>
