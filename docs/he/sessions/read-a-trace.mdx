trace הופך זרם אירועים שטוח לסיפור סיבתי של הריצה. קרא אותו מהסטייה הראשונה, לא לאחור מהשגיאה האחרונה.

## פתח את ה-trace

<Tabs>
  <Tab title="Dashboard">
    1. עבור ל-**Observe → Sessions** ופתח סשן.
    2. השתמש בסיכום הפרופיל כדי לבדוק תוצאה, תזמון, שגיאות וציוני הערכה.
    3. סרוק את התיר (timeline) ו-minimap. סנן סוגי אירועים או זמן כאשר הסשן גדול.
    4. בחר אירוע כדי לבדוק אותו. השתמש ב-**export** עבור JSON של evaluator, או העתק את כתובת ה-URL של הדף כדי לשתף קישור עמוק לראיה שנבחרה.

    ![תצוגה של פרטי סשן עם גרף ביצוע, ציר הזמן של האירועים, פאנל הערכה, וחלוקת כלים, מודל וו-hook.](/images/dashboard/session-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp --json sessions --session-id <session-id>
    fp events --session-id <session-id> --order asc --all
    fp --json events --full --session-id <session-id> --all
    ```

    השתמש תחילה בפיד האירועים הקל. בקש payload מלא רק כאשר סיכומי האירועים לא מכילים מספיק ראיות.
  </Tab>
</Tabs>

<Steps>
  <Step title="התמצא">
    אשר את ה-agent, הסביבה, התזמון, התוצאה ומשך הזמן, ואז סרוק לחיפוש שגיאות, טווחים ארוכים, כלים חוזרים, המתנה אנושית והחלטות מדיניות שנדחו.
  </Step>
  <Step title="הרחב את האירוע החשוד הראשון">
    בדוק את הבקשה, התגובה, קלט הכלי, פלט וה-correlation ID. תוכן רגיש גלוי רק כאשר ללכידת תמלול מופעלת וההרשאות שלך מאפשרות זאת.
  </Step>
  <Step title="בדוק את ההקשר שקדם">
    הסיבה לעתים קרובות מופיעה אירוע אחד קודם לכן: תגובה מודל שגויה, תוצאת כלי חסרה או הנחה ישנה.
  </Step>
  <Step title="הפוך את הראיות לפעולה">
    הוסף את הסשן לאפיקוד ביקורת, קשר אותו לבעיה, או השתמש בדפוס הכישלון כדי לחבור מדיניות.
  </Step>
</Steps>

<Warning>
  משך זמן ארוך לא תמיד אומר זיכרון עיכוב של המודל. הפרד זמן מודל, כלי, hook והמתנה אנושית לפני שתחליט מה לתקן.
</Warning>
