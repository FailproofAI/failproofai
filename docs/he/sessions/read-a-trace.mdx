עקבות הופך זרם אירועים שטוח לסיפור סיבתי של ההרצה. קרא אותו מנקודת ההסתעפות הראשונה, לא לאחור מהשגיאה האחרונה.

## פתח את העקבות

<Tabs>
  <Tab title="Dashboard">
    1. עבור אל **Observe → Sessions** ופתח הפעלה.
    2. השתמש בסיכום הפרופיל כדי לבדוק תוצאה, תזמון, שגיאות וציוני הערכה.
    3. סרוק את ציר הזמן ומפת המיני. סנן סוגי אירועים או זמן כאשר ההפעלה גדולה.
    4. בחר אירוע כדי לבדוק אותו. השתמש ב-**export** לקבלת JSON של המעריך, או העתק את כתובת הדף כדי לשתף קישור עמוק לעדות הנבחרת.

    ![תצוגת פרטי הפעלה עם גרף הביצוע שלה, ציר זמן אירועים, לוח הערכה, וניתוח כלים, מודל וקטגוריות.](/images/dashboard/session-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp --json sessions --session-id <session-id>
    fp events --session-id <session-id> --order asc --all
    fp --json events --full --session-id <session-id> --all
    ```

    השתמש בהזנת אירועים קלה תחילה. בקש עומסי מלאים רק כאשר סיכומי האירועים אינם מכילים מספיק עדות.
  </Tab>
</Tabs>

<Steps>
  <Step title="התמצא">
    אשר את הסוכן, הסביבה, התזמון, התוצאה והמשך זמן, ואז סרוק לחפש שגיאות, משכי זמן ארוכים, כלים חוזרים, המתנות אנושיות והחלטות מדיניות מסורבות.
  </Step>
  <Step title="הרחב את האירוע החשוד הראשון">
    בדוק את בקשתו, תגובתו, קלט הכלי, פלט וקוד המתאם. תוכן רגיש גלוי רק כאשר לכידת תמלול מופעלת והרשאותיך מאפשרות זאת.
  </Step>
  <Step title="בדוק את ההקשר הקודם">
    הגורם לעתים קרובות מתיישב בואירוע אחד קודם לכן: תגובת מודל שגויה, תוצאת כלי חסרה, או הנחה ישנה.
  </Step>
  <Step title="הפוך את העדות לפעולה">
    הוסף את ההפעלה לטווח ביקורת, קשור אותה לבעיה, או השתמש במצב הכישלון כדי לחבר מדיניות.
  </Step>
</Steps>

<Warning>
  משך זמן ארוך לא תמיד פירושו זיהום מודל. הפרד בין זמן מודל, כלי, קטגוריה והמתנה אנושית לפני שתחליט מה לתקן.
</Warning>
