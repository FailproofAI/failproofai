ביקורת הופכת קבוצה של הפעלות למציאות כשל מדורגות ותומכות בעדויות. התחל בשאלת כשל אחת צרה.

יש שתי ביקורות. הן קוראות נתונים שונים ומענות לכלים שונים:

| ביקורת | קוראת | צריכה חשבון | ממצאים מופיעים ב |
| --- | --- | --- | --- |
| מקומית — `failproofai audit` | היסטוריית הסוכנים כבר בשפ זו | לא | `http://localhost:8020/audit` |
| ענן — **Analyze → Audits**, או ה-CLI `fp` | ההפעלות המאוחסנות בענן Failproof AI | כן | לוח הבקרה בענן |

הרץ את המקומית קודם. היא לא צריכה כלום מלבד ה-CLI. הממצאים נשארים מקוביים, בעוד שטלמטריה CLI אנונימית נשלחת כברירת מחדל אלא אם תגדיר `FAILPROOFAI_TELEMETRY_DISABLED=1`.

<Tabs>
  <Tab title="מקומית">
    ```bash
    failproofai audit
    ```

    היא סורקת כל היסטוריית סוכנים נתמכת שהיא מוצאת במכונה זו, מהדה את פעילות הכלים דרך קטלוג המדיניות המובנה, ואז פותחת **http://localhost:8020/audit**. שמור על התהליך פועל בזמן שאתה קורא את התוצאות; לחץ <kbd>Ctrl</kbd>+<kbd>C</kbd> כאשר תסיים.

    ניתוח וממצאים נשארים במכונה זו. טלמטריה CLI אנונימית נשלחת כברירת מחדל אלא אם מבוטלת. לאחר שתסכים לתזמון, כל סריקה גם שולחת מטא-נתונים של מכונה ועשויה לשלוח תקציר ממצאים מוגבל.

    | דגל | מה הוא עושה |
    | --- | --- |
    | `--schedule [days]` | סרוק בטיימר ולשלח את הממצאים בדוא"ל. ברירת מחדל 7 ימים, טווח 1–90. מחתם אותך בפעם הראשונה. |
    | `--email <address>` | עם `--schedule`, מסדיר את כתובת הדוח במקום לבקש. |
    | `--no-schedule` | עצור את הטיימר. משאיר אותך מחותם. |
    | `--status` | האם התזמון פעיל, לאן הדוחות הולכים, מצב הדיימון, ומתי הסריקה הבאה עומדת. |

    ```bash
    failproofai audit --schedule 7 --email reliability@example.com
    failproofai audit --status
    ```

    ראה [ביקורת יסטוריית סוכנים מקומית](/he/audits/local-audit) לקבלת מידע אודות היסטוריות שכל מתאם קורא וכיצד הסריקה המתוזמנת פועלת.
  </Tab>
  <Tab title="לוח בקרה בענן">
    <Steps>
      <Step title="פתח ביקורות">
        בסרגל הצד של הענן, עבור אל **Analyze → Audits**. בחר **new audit**.
      </Step>
      <Step title="הגדר את הביקורת">
        הזן שם ויעד כשל ישיר, כגון "מצא הפעלות ייצור שחוזרות על אותו קריאת תשלום שנכשלה ללא שינוי קלט או הסלמה." בחר את הסוכן, הסביבה, חלון הזמן והלוח הזמנים. הוסף תיאור קצר וכתובות URL התייחסות כאשר המבקר זקוק לכללי הזרימה שלך.
      </Step>
      <Step title="צור והמתן לריצה">
        בחר **create audit**. הריצה הראשונה מתורה מיד. פתח את כרטיס הביקורת כדי לצפות בה כשהיא עברה מתור להפעלה למלא.
      </Step>
    </Steps>

    לאחר השלמת הריצה, פתח ממצא וסקור את עדויות ההפעלה שלו. לאחר מכן תוכל להודות, להקצות, לדחות, להשקט או לפתור זאת.

    ![ממצא ביקורת השלום המציג את תיאור הכשל שלו, הפעולה המומלצת, עדויות תומכות והפעלות מושפעות.](/images/dashboard/audit-finding.png)
  </Tab>
  <Tab title="CLI בענן">
    `fp` הוא ה-CLI בענן Failproof AI. היא קוראת בחזרה את מה שהענן אחסן; היא תוכנית שונה מ-`failproofai`, שאוכפת במכונה זו.

    ```bash
    fp audits create payment-retry-failures \
      --description "Find production sessions that retry a failed payment call without changing input or escalating" \
      --scope '{"environments":["production"]}' \
      --text "Escalate after two unchanged payment failures"

    fp audits list
    fp audits runs payment-retry-failures
    fp audits findings --audit payment-retry-failures
    fp audits finding <finding-id>
    ```

    הוסף הקשר התייחסות, ואז רענן אותו כאשר המקור משתנה:

    ```bash
    fp audits context-set payment-retry-failures --url https://example.com/payment-runbook
    fp audits context-refresh payment-retry-failures
    fp audits run payment-retry-failures
    ```

    השתמש ב-`fp audits ack <finding-id>`, `fp audits assign <finding-id> --to <email>`, `fp audits dismiss <finding-id>`, `fp audits mute <finding-id>`, `fp audits resolve <finding-id>`, או `fp audits reopen <finding-id>` כדי להעביר ממצא דרך הסינון.
  </Tab>
</Tabs>

לאחר מכן, [תגבור את הכשל הראשון שלך עם מדיניות](/he/start/first-policy) לפעולה ניתנת לשחזור מאומת.
