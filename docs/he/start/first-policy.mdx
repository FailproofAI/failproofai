השתמשו במדיניות רק לאחר שתוכלו לתאר את הפעולה הלא בטוחה ואת הפעולות החוקיות שחייבות להישאר מותרות.

<Tabs>
  <Tab title="Dashboard">
    <Steps>
      <Step title="כתבו את המדיניות">
        עברו אל **Admin → policy editor**. התחילו עם מדיניות ההדגמה, בדקו או ערכו את קוד המקור שלה, ואז בחרו **publish version**. פרסום יוצר את הגרסה הבלתי ניתנת לשינוי שתוכלו לפרוס למכונות.

        ![תצוגת ההרכבה של עורך המדיניות עם מדיניות הדגמה מוכנה לפרסום כגרסה בלתי ניתנת לשינוי.](/images/dashboard/policy-editor.png)
      </Step>
      <Step title="פרסמו אותה למכונה">
        עברו אל **Admin → enforcement**, הרחיבו את המכונה היעד, ובחרו **edit this machine**. הוסיפו את מדיניות ההדגמה המפורסמת, קבעו את גרסתה, בחרו **observe**, והחילו את הפרסום.

        ![עורך פרסום המכונה עם גרסת מדיניות מפורסמת שנבחרה במצב צפייה לפני החלת הפרסום.](/images/dashboard/enforcement-editor.png)
      </Step>
      <Step title="אימתו את המדיניות">
        הריצו סשן סוכן חדש באותה מכונה, ואז פתחו את **Observe → policy**. בחרו את המכונה וודאו שמדיניות ההדגמה מופיעה במיפוי המדיניות ובציר הזמן של ההחלטות. מצב צפייה רושם מה המדיניות הייתה עושה ללא חסימת הפעולה.

        ![עמוד Policy המציג סכומי החלטות, פעילות אכיפה לאורך זמן, ומיפויי מדיניות מנוהלים מקומיים וקלאוד.](/images/dashboard/policy-observe.png)
      </Step>
    </Steps>
  </Tab>
  <Tab title="CLI">
    כתיבת מדיניות קלאוד ופרסום צי הן זרימות עבודה ניהוליות. השתמשו ב-CLI המקומי לאימות של אותה מדיניות לפני פרסומה:

    ```bash
    failproofai policies --install --custom ./payment-retry.policies.ts \
      --cli claude --scope project
    failproofai config --status
    ```

    השתמשו ב-`fp` לבדיקת החלטות מדיניות גלויות בקלאוד:

    ```bash
    fp events --event-type hook_completed --env production --since 24h
    fp sessions --env production --since 24h
    ```

    שני השלבים זמינים גם מה-CLI: `fp policies publish <id> <file>` יוצר גרסה ו-`fp fleet deploy <machine-id> --add <id>` שם אותה על מכונה. השקילים של לוח הבקרה הם **Admin → policy editor** ו-**Admin → enforcement**.
  </Tab>
</Tabs>
