## אכיפה מקומית

הריצו `failproofai config` ללא מפתח, ואז קחו חבילה עם `failproofai policies add FailproofAI/policies`. בטרמינל, בחרו **Not now — stay local** כאשר ההגדרה שואלת להתחבר ל-Cloud; ללא טרמינל וללא `FAILPROOFAI_CLOUD_TOKEN`, היא תישאר מקומית מעצמה. ה-daemon והחיבורים מאכיפים את המכונה, ואף נתוני הפעלה לא נשלחים ל-Cloud. כדי להתחבר מאוחר יותר, עקבו אחר השלבים למטה.

## נתיב הפקה מומלץ

1. חברו מכונה שאינה בייצור עם הקטעת שדר מופעלת.
2. אמתו הפעלות והערכות ב-Cloud.
3. צרו ביקורת לצורך מצב כשל ידוע.
4. הפעילו את המדיניות הראשונה ב-observe mode.
5. הרחיבו לייצור לאחר בדיקת התאמות וחיובי שווא.

## חברו מכונה ל-Cloud

<Tabs>
  <Tab title="Dashboard">
    1. עברו ל-**Administration → Keys** וצרו מפתח עם `events:add` ו-`policies:pull`.
    2. העתיקו את הסוד החד פעמי למכונה היעד.
    3. לאחר הרצת פקודת ה-CLI של החיבור, עברו ל-**Admin → enforcement** ואשרו שהמכונה מופיעה.
    4. עברו ל-**Observe → Events** ואשרו שהאירוע הראשון שלה הגיע.

    מגירת המפתח מציגה את שתי ההרשאות הנדרשות על ידי מכונה מחוברת: ספיגת אירועים והעברת מדיניות.

    ![מגירת מפתח ה-API החדשה המשמשת להעניית הרשאות ספיגת אירועים והעברת מדיניות.](/images/dashboard/key-create.png)

    לאחר החיבור, המכונה צריכה להופיע באכיפה עם מצב המדיניות הרצוי והמדווח שלה.

    ![ה-fleet בעינה עם מכונה רשומה המורחבת כדי להציג את מצב המדיניות הרצוי שלה וסטטוס ההפעלה.](/images/dashboard/enforcement-fleet.png)

    האירוע הראשון שהגיע מאשר שה-daemon יכול להעביר נתונים ל-Cloud, בנפרדות מהפעלת המדיניות.

    ![זרם האירועים הקי מציג אירועי סוכן, מודל וכלים עדכניים.](/images/dashboard/events-stream-current.png)

    המשיכו רק לאחר שהמכונה והאירוע הראשון שלה גלויים.
  </Tab>
  <Tab title="CLI">
    קראו את הסוד החד פעמי לתוך ה-shell. `read -s` לוקח אותו בהנחיה שאינה משדרת, כך שהוא לעולם לא מופיע בפקודה או בהיסטוריית shell:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    לאחר מכן הגדירו את המכונה, בחרו את המדיניויות שלה ותנו לה שם:

    ```bash
    failproofai config

    failproofai policies add FailproofAI/policies
    failproofai config --machine-label checkout-runner-01
    failproofai config --status
    ```

    `failproofai config` עושה את כל ההגדרה — daemon, חיבורים לכל CLI סוכן שהוא מוצא, והחיבור ל-Cloud — לאחר מכן בוחר אפס מדיניויות, שזה מה שהפקודה השנייה היא בשביל.

    התווית מגיעה **לאחר** החיבור, לא במהלכו: `failproofai config --machine-label <name>` משנה את שם מכונה שכבר מחוברת, ועל אחת שאינה, היא לא עושה דבר אלא לומר זאת.

    הוסיפו `--no-transcripts` כאשר תוכן הקלטות חייב להישאר מקומי.

    ב-CI, הגדירו `FAILPROOFAI_CLOUD_TOKEN` מחנות הסודות במקום `read -s`, והשאירו את עקבוב ה-shell (`set -x`) כבוי, או העקבוב מדפיס את המפתח.

    <Warning>
      על מכונה שכבר **מוגדרת**, `failproofai config --connect <url>` רושמת אותה ושום דבר אחר. אל תשתמשו בצורה זו לעבור ראשון: היא חוזרת לפני שה-daemon או איזה חיבור יש במקום, ומשאירה מכונה שמופיעה ב-Cloud אך לא אוספת ולא אוכפת שום דבר.
    </Warning>
  </Tab>
</Tabs>

התחברות ל-Cloud מאמתת ספיגת אירועים והעברת מדיניות בנפרדות. מפתח עשוי אפוא להיות תקף אך חסר הרשאה נדרשת אחת. השתמשו ב-`failproofai config --status` כדי לראות איזו יכולת מוגדרת.

<Info>
  הגדרת Cloud כותבת אישורים מקומיים רק לאחר שהיכולת הרלוונטית הצליחה. אימות כשל אינו משאיר מכונה שנראית מחוברת כשהיא לא כן.
</Info>
