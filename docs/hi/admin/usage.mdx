Usage दिखाता है कि वर्तमान संगठन ने अपनी वर्तमान 30-दिन की विंडो के दौरान क्या मीटर किया है। विंडो प्रति संगठन निश्चित और एंकर की गई है, और उपयोग केवल-पठनीय है: यह कोई सीमा, कोटा, या योजना थ्रेशोल्ड लागू नहीं करता या प्रदर्शित नहीं करता। दोनों सतहें यह कहती हैं — CLI पैनल "read-only usage, no limits applied" प्रिंट करता है।

## उपयोग की समीक्षा करें

<Tabs>
  <Tab title="Dashboard">
    1. **admin → usage** पर जाएं।
    2. संगठन और मीटरिंग विंडो की पुष्टि करें — हेडर विंडो की शुरुआत और अंत, इसके अंदर का दिन, और कितना समय बीत चुका है, यह दिखाता है।
    3. हीरो ब्लॉक पढ़ें: events ingested, sessions, agents, और environments।
    4. दो पाइपलाइनें पढ़ें: evaluations (scores और metrics के साथ) और audits (issues और alerts के साथ), प्रत्येक शुरू की गई रन के विरुद्ध पूर्ण रन दिखा रहा है।
    5. workspace और access ब्लॉक पढ़ें: saved queries, dashboards, alerts, unique issues, members, और API keys।

    आंकड़े कैश किए गए हैं, लाइव नहीं हैं। किसी परिवर्तन के बाद जो आप देखने की उम्मीद करते हैं, शीर्ष दाईं ओर refresh control का उपयोग करें।

    ![मीटरिंग विंडो, कैप्चर किए गए events, evaluation और audit पाइपलाइन, workspace resources, members, और API keys दिखाने वाला usage पेज।](/images/dashboard/usage-overview.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp usage
    fp --json usage
    fp --org reliability-team --json usage
    ```

    `fp usage` को `usage:read` की आवश्यकता है और एक API key के अंतर्गत चलता है, जो इसे एक रिपोर्टिंग cron के लिए सही कमांड बनाता है।

    `--json` के साथ यह dashboard response को अपरिवर्तित रूप से लौटाता है: `org_id`, `billing_anchor`, `window`, `usage`, `calculated_at`, और `stale_after`। `calculated_at` और `stale_after` यह बताते हैं कि एक आंकड़ा कितना पुराना है।

    `fp usage` के अपने कोई फ़्लैग नहीं हैं — केवल global `--json` और `--org`। यह वर्तमान विंडो की रिपोर्ट करता है और इससे पहले कुछ भी नहीं, इसलिए इसे एक शेड्यूल पर चलाकर और `--json` payload को स्टोर करके अपना स्वयं का इतिहास रखें, न कि बाद में एक पहले की विंडो को क्वेरी करने की अपेक्षा करें।

    ```bash
    fp --json usage | jq '.usage.events_ingested'
    ```
  </Tab>
</Tabs>

### मीट्रिक कुंजियाँ

JSON payload में `usage` के तहत सब कुछ, इसलिए एक script एक पैनल को पार्स करने के बजाय एक फ़ील्ड का नाम दे सकता है।

| Group | Keys |
| --- | --- |
| Telemetry | `events_ingested`, `sessions`, `agents`, `environments` |
| Evaluations | `evaluation_runs`, `evaluation_finishes`, `evaluations`, `metrics` |
| Audits | `audit_runs`, `audit_finishes`, `issues_created`, `alerts_created` |
| Workspace | `queries_created`, `dashboards_created` |
| Access | `users_active`, `users_created`, `keys_active`, `keys_created` |

प्रत्येक पाइपलाइन started और finished counts को अलग से रिपोर्ट करता है, इसलिए `audit_runs` और `audit_finishes` के बीच एक अंतराल का मतलब है कि काम शुरू हुआ लेकिन पूरा नहीं हुआ — इसे issue counts में कुछ भी पढ़ने से पहले जांचने के लायक है।

## एक परिवर्तन की जांच करें

Ingest volume प्रति मशीन तय किया जाता है, न कि केंद्रीय रूप से। संगठन और विंडो से शुरू करें, फिर यह काम करें कि मशीनों पर क्या बदला है जो इसमें रिपोर्ट करती हैं।

| Cause | कहाँ जाँचें | क्या बदलें |
| --- | --- | --- |
| एक मशीन सत्र प्रतिलेख भेज रही है | उस मशीन के `~/.failproofai/config.json` में `collector.sessions` | इसे `false` पर सेट करें केवल निर्णय भेजने के लिए |
| Hook activity पूरी तरह भेजी जा रही है | उसी फ़ाइल में `collector.hooks_verbosity` | `decisions` aggregates प्रति मिनट की अनुमति देता है; `off` hook events को पूरी तरह रोकता है |
| एक नया capture location जोड़ा गया था | `failproofai harness list` | इसे `failproofai harness remove-path <harness> <path or label>` से हटाएं |
| History फिर से भेजी गई थी | मशीन के `failproofai backfill` चलता है | Re-sends content hash पर deduplicate करते हैं और पहले से वहां की rows में collapse करते हैं, इसलिए वे double-count नहीं करते |
| एक नया integration रिपोर्ट करना शुरू कर रहा है | `agents` और `environments` counts, और sessions list | इसे रोल आउट करने से पहले नई मशीन की collector settings को scope करें |

Usage किसी योजना के विरुद्ध कुछ भी तुलना नहीं करता। यह उत्पाद के बाहर करें।
