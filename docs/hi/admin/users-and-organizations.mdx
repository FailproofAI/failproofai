संगठन सत्र, मूल्यांकन, ऑडिट, समस्याओं, सतर्कताओं, प्रश्नों, डैशबोर्ड, उपयोगकर्ताओं और कुंजियों को अलग रखते हैं। किसी भी प्रशासनिक संसाधन को बदलने से पहले सक्रिय संगठन की पुष्टि करें।

## संगठन का चयन करें

<Tabs>
  <Tab title="Dashboard">
    Cloud साइडबार के शीर्ष पर संगठन स्विचर का उपयोग करें। इसके नीचे सब कुछ — **admin** में प्रत्येक पृष्ठ सहित — फिर उस संगठन को पढ़ता और लिखता है।
  </Tab>
  <Tab title="CLI">
    ```bash
    fp orgs list
    fp orgs switch reliability-team
    fp orgs current
    fp orgs perms
    ```

    बिना slug के `fp orgs switch` एक तीर-कुंजी पिकर खोलता है जो आपके वर्तमान संगठन से शुरू होता है; एक गैर-इंटरैक्टिव रन एक क्रमांकित प्रॉम्प्ट पर वापस आता है, और `--json` के तहत एक slug आवश्यक है। यह पसंद `~/.failproofai/fpcli/cli-auth.json` में बनी रहती है, इसलिए बाद की कमांडें इसे सक्रिय tenant के रूप में भेजती हैं। `--org <slug>` या `FP_ORG` के साथ एक कमांड के लिए इसे ओवरराइड करें।
  </Tab>
</Tabs>

<Note>
  प्रत्येक `fp orgs` कमांड को साइन-इन किए गए मनुष्य की आवश्यकता है और API कुंजी के तहत अस्वीकार करता है, क्योंकि संगठन सदस्यता एक व्यक्ति से संबंधित है और एक कुंजी पहले से ही एक संगठन के लिए कार्य करती है। नीचे `fp users` कमांड दोनों तरीकों से काम करते हैं।
</Note>

## सदस्यों को प्रबंधित करें

<Tabs>
  <Tab title="Dashboard">
    1. **admin → users** पर जाएं और ईमेल द्वारा सदस्यों को खोजें, या `protected`, `admin`, `standard` और `read-only` फ़िल्टर चिप्स के साथ सूची को संकीर्ण करें।
    2. **new user** का चयन करें, ईमेल दर्ज करें, अनुमति सेट चुनें, और यदि आवश्यक हो तो प्रति-सदस्य ओवरराइड को समायोजित करें।
    3. अनुदान बदलने, साइन-इन को अक्षम करने, या खाते को फिर से सक्षम करने के लिए बाद में किसी सदस्य को खोलें।

    ![ईमेल खोज बॉक्स, फ़िल्टर चिप्स, और संसाधन द्वारा समूहीकृत अनुदान दिखाने वाला सदस्य कार्ड के साथ उपयोगकर्ता पृष्ठ।](/images/dashboard/users.png)

    इस फ्रेम में अनुदान चिप्स `incidents:*` से `issues:*` नाम परिवर्तन से पहले की हैं; [सामान्य अनुमतियां](/hi/admin/keys-and-permissions#common-permissions) सूची वर्तमान है।
  </Tab>
  <Tab title="CLI">
    ```bash
    fp users list
    fp users list --active-only
    fp users create engineer@example.com --permission-set standard
    fp users show engineer@example.com
    fp users update engineer@example.com --add audits:write
    fp users disable engineer@example.com
    fp users enable engineer@example.com
    ```

    सदस्यों को ईमेल द्वारा संबोधित किया जाता है और केस-असंवेदनशील रूप से हल किया जाता है, इसलिए `fp users show Alice.Chen@Example.com` और `fp users create alice.chen@example.com` एक ही व्यक्ति को संदर्भित करते हैं।
  </Tab>
</Tabs>

### अनुदान, और प्रत्येक क्रिया को क्या चाहिए

सदस्य अनुदान कुंजियों के समान अंकगणित का उपयोग करते हैं: प्रभावी अनुदान `(set ∪ added) − removed` हैं, और `--add` / `--remove` कॉम्पैक्ट `slug:action.action` टोकन लेते हैं जहां डॉटेड क्रियाएं विस्तारित होती हैं। [कुंजियां और अनुमतियां](/hi/admin/keys-and-permissions) देखें।

| क्रिया | अनुमति | नोट्स |
| --- | --- | --- |
| `fp users list` / `show` | `users:read` | `--active-only` अक्षम सदस्यों को छुपाता है। |
| `fp users create` | `users:create` | `--permission-set` भूमिका बीज; `--add` / `--remove` ओवरराइड लेयर। |
| `fp users update` | `users:update` | `--permission-set` सदस्य के प्रति-सदस्य ओवरराइड को **प्रतिस्थापित** करता है; `--add` / `--remove` अकेले उनके वर्तमान अनुदानों के विरुद्ध वर्धनशील हैं। |
| `fp users disable` / `enable` | `users:delete` | दोनों, सक्षम करने सहित — इसे जानबूझकर प्रदान करें। |

अक्षम करना दो मामलों को तुरंत अस्वीकार करता है, सत्यापन संदेश के बजाय निषिद्ध त्रुटि के रूप में: एक **protected** सदस्य को अक्षम नहीं किया जा सकता, और आप अपने स्वयं के खाते को अक्षम नहीं कर सकते। पहले से अक्षम सदस्य को अक्षम करना, या पहले से सक्रिय को सक्षम करना, एक शांत no-op है। API अक्षम करने के लिए एक delete ऑपरेशन का उपयोग करता है, लेकिन यह न तो खाता हटाता है और न ही इसके सदस्यता रिकॉर्ड को।

दो संगठन सेटिंग्स सदस्यता को नियंत्रित करती हैं: `default_user_permissions` नई आमंत्रण के लिए अनुमति सेट को पूर्वनिर्धारित करता है, और `allowed_sign_ins` नियंत्रित करता है कि कौन से पते बिल्कुल साइन-इन कोड प्राप्त कर सकते हैं। [सेटिंग्स पृष्ठ](/hi/admin/settings-and-security) से उन्हें प्रबंधित करें।

<Warning>
  किसी उपयोगकर्ता को अक्षम करना उस पहचान को केवल वर्तमान चयनित संगठन नहीं, बल्कि प्रत्येक संगठन में साइन इन करने से रोकता है। पुनः सक्षम करना वैश्विक साइन-इन और इस संगठन में सदस्य की अनुमतियों को बहाल करता है।
</Warning>

<Tip>
  सेवा खातों को कार्यभार और मालिक से जुड़े वर्णनात्मक नामों से दें। संगठनों के बीच, या किसी व्यक्ति और मशीन के बीच एक कुंजी साझा न करें।
</Tip>
