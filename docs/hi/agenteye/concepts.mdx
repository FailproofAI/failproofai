यह पृष्ठ Failproof AI Observability द्वारा उपयोग की जाने वाली शब्दावली को परिभाषित करता है। यदि किसी अन्य गाइड में कोई शब्द अपरिचित है, तो यह यहाँ परिभाषित है। आपको इसे अंत तक पढ़ने की आवश्यकता नहीं है: इसे स्किम करें, या जब आप कोई ऐसा शब्द देखें जिसे आप स्पष्ट करना चाहते हैं तो वापस आएँ।

---

## डेटा मॉडल

**Event**
डेटा की सबसे छोटी इकाई। एक event आपके agent द्वारा उठाया गया एक single step रिकॉर्ड करता है: एक `tool_use`, एक `model_request`, एक `hook_completed`, एक `error`, और इसी तरह। आपका agent [Python SDK](/hi/agenteye/python-sdk) के माध्यम से events emit करता है; वे **Events** पृष्ठ पर live दिखाई देते हैं।

**Session**
एक agent run, जिसे `session_id` द्वारा identify किया जाता है। एक session सभी events है जो उस id को share करते हैं, **Sessions** पृष्ठ पर एक single row में rolled up और इसके detail page पर एक execution graph के रूप में drawn। एक session आमतौर पर `agent_start` के साथ शुरू होता है और `agent_end` के साथ समाप्त होता है।

**Agent**
एक run के अंदर एक named actor, जिसे `agent_id` द्वारा identify किया जाता है। एक run में कई agents शामिल हो सकते हैं: एक planner जो एक summarizer sub-agent को spawn करता है, उदाहरण के लिए। Sub-agents एक `parent_id` carry करते हैं, जो Failproof AI Observability को उन्हें execution graph में अपने स्वयं के lanes पर draw करने देता है।

**Environment**
एक label कि run कहाँ हुआ: `production`, `staging`, `dev`। आप इसे SDK configure करते समय एक बार सेट करते हैं। लगभग हर dashboard page environment द्वारा filter कर सकता है।

**Context-window fill**
एक model के context window का प्रतिशत जो एक response ने consume किया। Failproof AI Observability इसे `model_response` events पर उन models के लिए stamp करता है जिन्हें यह recognize करता है, इसलिए prompt growth और impending compaction event stream में सही तरीके से दिखाई देते हैं।

## गुणवत्ता

**Evaluation**
एक finished session के लिए एक quality score, जो आप चलाने वाली scoring service द्वारा produce किया जाता है। Evaluations opt-in हैं: जब तक आप एक evaluator को connect नहीं करते, sessions recorded होते हैं लेकिन scored नहीं होते। प्रत्येक evaluation कई named scores carry कर सकता है (उदाहरण के लिए `helpfulness`, `factuality`, `tool_efficiency`), प्रत्येक एक short reasoning note के साथ। [Evaluation suite](/hi/agenteye/evaluation-suite) देखें।

**Score key**
एक dimension का नाम जो एक evaluator report करता है, जैसे `helpfulness`। Alerts और audits समय के साथ एक specific score key को watch कर सकते हैं।

**Evaluator**
आपकी scoring service। Failproof AI Observability एक finished run के transcript को इसे POST करता है और जो scores यह return करता है उन्हें store करता है। यह कोई default evaluator ship नहीं करता; scoring logic आपकी है।

## असफलताओं को खोजना और ठीक करना

**Hook**
एक guardrail या side-effect जो आपकी agent framework एक step के चारों ओर चलाता है: एक content-safety check, PII redaction, एक budget guard। Hooks `hook_triggered` / `hook_completed` events emit करते हैं एक `outcome` के साथ (allow, deny, modify), और अपने observe page प्राप्त करते हैं।

**Alert rule**
एक rule जो तब fires होता है जब एक metric आप द्वारा सेट की गई threshold को cross करता है: error rate, p95 latency, token cost, या एक evaluator score। जब एक rule fires होता है, तो यह एक incident खोलता है और आपके चुने गए channels (email, Slack, webhook, in-dashboard) को notify करता है। [Alerts](/hi/agenteye/alerts) देखें।

**Incident**
एक open issue जो तब created होता है जब एक alert rule fires होता है। Incidents के एक lifecycle होते हैं (acknowledge, assign, resolve) और एक activity timeline जो हर action को record करती है। आप manually भी एक खोल सकते हैं।

**Audit**
एक recurring investigation (hourly to weekly) जो आपके logs को *across* sessions के लिए mine करता है failure patterns के लिए जिन्हें आपने एक rule के लिए नहीं लिखा: error clusters, low scores, latency outliers, tool-call loops, और runs जो कभी finished नहीं हुए। जहाँ एक alert एक metric को watch करता है जो आप पहले से जानते हैं, एक audit आपको बताता है कि आगे क्या देखना है। [Audits](/hi/agenteye/audits) देखें।

**Finding**
एक audit run से एक ranked, evidence-backed result। एक finding एक pattern को name करता है, exact sessions को उसके पीछे link करता है, और एक triage lifecycle carry करता है (acknowledge, resolve, mute, dismiss)। Failproof AI Observability findings को run-over-run deduplicate करता है इसलिए एक known pattern updates होता है बजाय pile up होने के।

**AI assistant**
In-dashboard chat जो आपके agents के बारे में plain English में सवालों के जवाब देता है, आपने स्वयं के data पर। यह default में read-only है; कुछ भी यह create करता है (एक saved query, एक dashboard) approval-gated है, और यह कभी delete नहीं कर सकता। [AI assistant](/hi/agenteye/assistant) देखें।

## इसे चलाना

**Organization (tenant)**
एक isolated workspace। एक Failproof AI Observability instance कई organizations को host कर सकता है, प्रत्येक के अपने users, keys, और data के साथ। हर dashboard URL आपके org slug के तहत scoped है (`/<org-slug>/…`)।

**Collector**
`agenteye-collector`, lightweight daemon जो प्रत्येक agent machine पर चलता है, SDK द्वारा disk पर लिखे गए events को batch करता है, और उन्हें server को ship करता है।

**API key**
एक scoped token जो एक client को server के खिलाफ authenticate करता है। Keys में granular permissions होते हैं (उदाहरण के लिए collector के लिए `events:add`, dashboard key के लिए read-only scopes)। [API keys](/hi/agenteye/api-keys) देखें।

**Server**
Ingest और API service। यह events को ingest करता है, आपके databases में operational state को store करता है, और dashboard और CLI को serve करता है।

**Dashboard**
Web UI। हर page एक organization के लिए scoped है और server के API के माध्यम से read करता है।
