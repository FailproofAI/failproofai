अपने कोडिंग एजेंट को बताएँ *"इस एजेंट में Failproof AI Observability जोड़ें"* और इसे अपना लूप पढ़ने, यह निर्धारित करने कि instrumentation कहाँ होना चाहिए, इसे लिखने, और events को verify करने से पहले काम पूरा होने तक का काम करने दें।

**Python SDK skill** (`agenteye-python-sdk`) एक *Agent Skill* है: instructions की एक फोल्डर जिसे Claude Code या Codex जैसे कोडिंग एजेंट आवश्यकतानुसार लोड करते हैं जब कोई कार्य इससे मेल खाता है। यह एजेंट को [Python SDK](/hi/agenteye/python-sdk) का उपयोग करना सिखाता है — यह एक लाइब्रेरी नहीं है, और यह SDK के काम करने के तरीके में कुछ नहीं बदलता।

## Instrumentation लिखने में आसान है और चुपचाप गलत होने में भी आसान है

SDK छोटा है: तेरह event methods, सभी keyword-only। एक कोडिंग एजेंट [Python SDK](/hi/agenteye/python-sdk) reference को पढ़ सकता है और एक मिनट में plausible instrumentation produce कर सकता है।

समस्या यह है कि यह SDK गलत होने पर raise नहीं करता, और गलत instrumentation बिल्कुल सही instrumentation जैसा दिखता है जब तक कि कोई dashboard खोलकर इसे खाली न पाए। असली समय खर्च करने वाली गलतियों सभी silences हैं:

| गलती | आप क्या देखते हैं |
|---|---|
| No `agent_start` | हर event landing करता है। Zero sessions। |
| Environment कभी set नहीं होता | सब कुछ काम करता है, `dev` के तहत filed। |
| `outcome="failure"` | रन हरा दिखता है — केवल `failed`, `error`, `timeout`, `rejected` गिनती में आते हैं। |
| Typo'd field name | Accepted और नए field के रूप में stored। |
| Thread pool से emitted events | Silently dropped। |

इनमें से कोई भी raise नहीं करता। ये tests में नहीं दिखते। हर एक skill में है, contract के रूप में stated जो इसे पकड़ता है।

## यह क्या करता है, क्रम में

Skill वही तीन steps चलाता है जो एक सतर्क engineer चलाएगा:

1. **Plan.** यह आपका agent loop पढ़ता है और दो प्रश्न पूछता है जिनका उत्तर केवल आप दे सकते हैं: एक run में क्या counts करता है (आपका `session_id`), और distinguishable actors कौन हैं (आपका `agent_id`)। यह कोड लिखने से पहले इन्हें agree करता है, क्योंकि बाद में उन्हें बदलने से आपका history split हो जाता है और trends टूट जाती हैं।
2. **Write.** यह identity को प्रति run एक बार bind करता है न कि हर call site के माध्यम से threading, और यह एक concurrency-safe shape चुनता है — एक विवरण जो मायने रखता है, क्योंकि واضح shortcut silently दो overlapping runs को एक session में mix कर देता है।
3. **Verify.** यह आपका agent चलाता है और परिणामी event files को पढ़ता है, यह जाँचता है कि `agent_start` present है, environment सही है, और एक run ने एक session produce किया।

यह तीसरा step वह है जिसे लोग छोड़ देते हैं। SDK events को local files में लिखता है, इसलिए एक complete integration को laptop पर no server, no API key, और no network के साथ prove किया जा सकता है — जो बिल्कुल इसी कारण से skill इसे करने पर настаивает है।

## यह अन्य skills से कैसे संबंधित है

तीन skills, एक clean split:

| Skill | इसे तब reach करें जब | यह क्या छूता है |
|---|---|---|
| **Python SDK skill** (यह पृष्ठ) | आप चाहते हैं कि आपका agent *emit* telemetry — "observability जोड़ें", "मेरा agent क्यों नहीं दिखा रहा?" | आपके agent के repo में code लिखता है। कुछ नहीं पढ़ता। |
| **[Evaluator skill](/hi/agenteye/evaluator-skill)** | आप runs को *score* करना चाहते हैं — "हमें मापना क्या चाहिए?" | आपके repo में code लिखता है; telemetry पढ़ता है |
| **[CLI skill](/hi/agenteye/cli-skill)** | आप *read* करना चाहते हैं कि क्या हुआ, या अपने deployment को operate करना चाहते हैं | CLI को आपके रूप में drive करता है, changes सहित |

ये उस क्रम में hand off करते हैं: यह skill events flowing प्राप्त करता है, evaluator उन्हें score करता है, CLI उन्हें वापस पढ़ता है। जब तक आपका agent sessions emit नहीं करता evaluate करने के लिए कुछ नहीं है और पढ़ने के लिए कुछ नहीं है, इसलिए अगर आप scratch से शुरू कर रहे हैं, यहाँ से शुरू करें।

## Prerequisites

1. **Python 3.10+** और agent codebase जिसे आप instrument करना चाहते हैं।
2. **SDK.** यह ग्राहकों को private wheel के रूप में distribute किया जाता है न कि public index से — आपका onboarding इसे कैसे प्राप्त करें और install करें यह बताता है। Skill install path को जानता है और अगर इसे नहीं मिल सकता तो आपसे पूछेगा guess करने के बजाय।
3. **कुछ भी नहीं। ** कोई dashboard login नहीं, कोई API key नहीं, कोई network नहीं। Skill उन event files के विरुद्ध verify करता है जो SDK लिखता है, इसलिए यह offline में अपना काम समाप्त कर सकता है और prove कर सकता है।

## इसे कहाँ से प्राप्त करें

Skill public [`FailproofAI/skills`](https://github.com/FailproofAI/skills) collection में है:

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

हर project के लिए install करने के लिए `-g` जोड़ें न कि केवल current project के लिए, और `--copy` अगर आपका environment symlinks follow नहीं करता। Codex के लिए, `-a codex` pass करें।

## इसे manually install करना

Agent Skills वह folders हैं जिनमें एक `SKILL.md` plus references हैं। अगर आप installer use नहीं करना चाहते:

- **Claude Code**: `agenteye-python-sdk/` folder को `~/.claude/skills/` (हर project) या `<your-repo>/.claude/skills/` (केवल वह repo) में copy करें। Claude Code इसे स्वचालित रूप से discover करता है — `/skills` list check करें, या बस ऐसा कुछ पूछें जो इससे मेल खाता हो।
- **Codex**: Codex एक ही `SKILL.md` को पढ़ता है। bundled `agents/openai.yaml` `allow_implicit_invocation: true` set करता है, इसलिए जब कोई कार्य मेल खाता है तो यह auto-selected है; अन्यथा इसे `$agenteye-python-sdk` के रूप में invoke करें।

अपना agent **उस repository में चलाएँ जिसमें वह code है जिसे आप instrument करना चाहते हैं** — skill कुछ भी propose करने से पहले आपका agent loop पढ़ता है।

## एक session कैसा दिखता है

```text
आप  ▸ इस एजेंट में Failproof AI Observability जोड़ें।

एजेंट ▸ आपका loop पढ़ें — tools.py में एक tool dispatcher, llm.py में एक Anthropic
        wrapper। लिखने से पहले दो प्रश्न।

        एक run में क्या counts करता है? आप requests को concurrently handle करते हैं,
        इसलिए मैं ctx.request_id में request id use करूँगा जो आपके पास पहले से है —
        तब एक session यहाँ और एक request आपके logs में एक ही string है।

        और actors कौन हैं? मुझे एक planner path और एक researcher
        path दिखता है। उन्हें अलग label करें, या क्या वह आपके लिए एक agent है?

आप  ▸ Request id सही है। वे एक agent हैं, इसे "assistant" कहें।

एजेंट ▸ हो गया। Dispatcher और LLM client को wrap किया; agent_start और
        agent_end handle_request को bracket करते हैं, error path सहित। Identity
        के लिए context-local use किया — आपका dispatcher tools को thread pool में
        चलाता है, और simpler approach concurrent runs को बिना complaining किए
        एक session में mix कर देता।

        एक real run के विरुद्ध verify किया: 4 files के बीच 11 events —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success)। environment=production, एक session
        प्रति request, durations paired।

        एक चीज़ जो मैंने नहीं की: आपके batch.py में worker pool सीधे executor को
        submit करता है, इसलिए वहाँ से events silently drop हो जाएँगे।
        क्या मैं उन्हें भी fix करूँ?
```

ध्यान देने योग्य pattern: इसने कोड को propose करने से पहले पढ़ा, केवल उन सवालों के बारे में पूछा जिनका उत्तर आप दे सकते हैं, एक id reuse किया जो आपके पास पहले से था, concurrency-safe shape चुना *क्योंकि* इसने thread pool देखा, और **actual events पढ़कर verify किया** न कि success declare करके — तब उस एक जगह को flag किया जहाँ इसे पता था कि quietly fail होगा।

## आप इससे क्या पूछ सकते हैं

- *"मेरा agent dashboard पर क्यों नहीं दिख रहा है?"* → ladder walk करता है: क्या events लिखे जा रहे हैं, क्या `agent_start` है, क्या environment सही है, क्या collector same जगह को पढ़ रहा है।
- *"सब कुछ dev के तहत landing कर रहा है।"* → environment कभी set नहीं हुआ, या बाद के call द्वारा reset हुआ।
- *"Token tracking जोड़ें।"* → आपके LLM wrapper को find करता है और model, stop reason, और usage record करता है।
- *"Sub-agents को भी instrument करें।"* → एक session, distinct agent labels, अपने parent के तहत nested।
- *"Instrumentation के लिए tests लिखें।"* → SDK को एक temporary directory की ओर point करता है और इसके द्वारा लिखे गए events पर assert करता है।

## क्या देखें

**इसे verify करने दें।** वह step जो इस skill को use करने लायक बनाता है, वह last one है — आपके agent को चलाना और events को वापस पढ़ना। एक agent जो instrumentation लिखता है और रुक जाता है, उसने आसान आधा किया है, और आधा जो silently fail करता है वह दूसरा है।

**कोड से पहले नामों को agree करें।** `session_id` और `agent_id` वह axes हैं जो हर surface group करता है। उन्हें बाद में rename करने से history split हो जाता है: पुरानी runs पुराने labels रखती हैं और आपकी trends टूट जाती हैं। Skill पूछेगा; उत्तर एक मिनट की सोच लायक है।

**अगर आपका agent public index से SDK install करने का proposal करता है, तो skill load नहीं हुआ।** SDK privately distribute किया जाता है। यह proposal एक reliable tell है कि आपका कोडिंग agent guess कर रहा है न कि skill का पालन कर रहा है — इसे वहाँ रोकें और check करें कि skill install है।

उससे परे इसका blast radius छोटा है: यह आपकी working directory में code लिखता है और event files जहाँ आप कहते हैं। यह अपने deployment से कुछ नहीं पढ़ता और इसके बारे में कुछ नहीं बदलता।
