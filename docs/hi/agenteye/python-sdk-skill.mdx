अपने coding agent को बताएं *"इस agent में Failproof AI Observability add करो"* और इसे अपना loop पढ़ने दें, यह समझ जाए कि instrumentation कहां रखना है, इसे लिखे, और events को verify करे।

**Python SDK skill** (`agenteye-python-sdk`) एक *Agent Skill* है: instructions वाली एक folder जिसे Claude Code या Codex जैसे coding agent को task के अनुसार चाहिए तो load करना पड़ता है। यह agent को [Python SDK](/hi/agenteye/python-sdk) use करना सिखाता है — यह एक library नहीं है, और यह SDK के काम करने के तरीके को कोई भी बदलाव नहीं करता।

## Instrumentation लिखना आसान है और गलत भी आसानी से हो सकता है

SDK छोटा है: तेरह event methods, सभी keyword-only। एक coding agent [Python SDK](/hi/agenteye/python-sdk) reference पढ़ सकता है और एक मिनट में plausible instrumentation बना सकता है।

समस्या यह है कि यह SDK गलती होने पर कोई error नहीं देता, और गलत instrumentation सही instrumentation जैसे ही दिखता है जब तक कोई dashboard खोलकर देखे कि वह खाली है। जो गलतियां असली समय बर्बाद करती हैं, वे सभी चुप्पियां हैं:

| गलती | आप देखते हैं |
|---|---|
| कोई `agent_start` नहीं | हर event आता है। Zero sessions। |
| Environment कभी set नहीं हुआ | सब कुछ काम करता है, `dev` के तहत filed। |
| `outcome="failure"` | Run green दिखता है — केवल `failed`, `error`, `timeout`, `rejected` गिने जाते हैं। |
| Field name में typo | Accepted होता है और नए field के रूप में store होता है। |
| Thread pool से emit किए गए events | Silently drop हो जाते हैं। |

ये कोई भी error नहीं देते। ये tests में दिखते नहीं। हर एक इस skill में है, contract के रूप में stated है जो इसे पकड़ता है।

## यह क्या करता है, क्रम में

Skill वही तीन steps चलाता है जो एक सावधान engineer चलाएगा:

1. **Plan।** यह आपका agent loop पढ़ता है और दो सवाल पूछता है जिनका जवाब केवल आप दे सकते हैं: एक run क्या है (आपका `session_id`), और कौन से distinguishable actors हैं (आपका `agent_id`)। यह code लिखने से पहले इन्हें agree करवा लेता है, क्योंकि इन्हें बाद में बदलने से आपका history टूट जाता है और trends टूट जाते हैं।
2. **Write।** यह identity को एक बार per run के लिए bind करता है बजाय इसे हर call site से thread करने के, और एक concurrency-safe shape चुनता है — एक detail जो महत्वपूर्ण है, क्योंकि obvious shortcut silently दो overlapping runs को एक session में मिला देता है।
3. **Verify।** यह आपके agent को चलाता है और resulting event files को पढ़ता है, check करता है कि `agent_start` present है, environment सही है, और एक run ने एक session produce किया है।

तीसरा step वह है जिसे लोग छोड़ देते हैं। SDK events को local files में लिखता है, तो एक complete integration को laptop पर no server, no API key, no network के साथ prove किया जा सकता है — जो बिल्कुल इसी कारण से skill इस पर जोर देता है।

## यह दूसरी skills से कैसे संबंधित है

तीन skills, एक clean split:

| Skill | इसे तब use करें जब | यह क्या करता है |
|---|---|---|
| **Python SDK skill** (यह page) | आप चाहते हैं कि आपका agent telemetry *emit* करे — "add observability", "my agent क्यों show नहीं हो रहा?" | आपके agent के repo में code लिखता है। कुछ नहीं पढ़ता। |
| **[Evaluator skill](/hi/agenteye/evaluator-skill)** | आप runs को *score* करना चाहते हैं — "हमें measure ही क्या करना चाहिए?" | आपके repo में code लिखता है; telemetry पढ़ता है |
| **[CLI skill](/hi/agenteye/cli-skill)** | आप देखना चाहते हैं कि *क्या हुआ*, या अपने deployment को operate करना चाहते हैं | CLI को drive करता है जैसे आप, changes के साथ |

वे इसी क्रम में हैंडऑफ करते हैं: यह skill events बहाता है, evaluator उन्हें score करता है, CLI उन्हें वापस पढ़ता है। जब तक आपका agent sessions emit नहीं करता, तब तक evaluate करने के लिए कुछ नहीं है और पढ़ने के लिए कुछ नहीं है, तो अगर आप scratch से शुरू कर रहे हैं, यहां से शुरू करें।

## Prerequisites

1. **Python 3.10+** और agent codebase जिसे आप instrument करना चाहते हैं।
2. **The SDK।** यह customers को private wheel के रूप में distribute किया जाता है public index से नहीं — आपके onboarding में बताया गया है कि इसे कैसे प्राप्त करें और install करें। Skill को install path पता है और अगर यह नहीं मिल सकता तो आपसे पूछेगा बजाय guess करने के।
3. **कुछ नहीं।** कोई dashboard login नहीं, कोई API key नहीं, कोई network नहीं। Skill event files के खिलाफ verify करता है जो SDK लिखता है, तो यह खत्म कर सकता है और अपना काम offline prove कर सकता है।

## यह कहां से प्राप्त करें

Skill public [`FailproofAI/skills`](https://github.com/FailproofAI/skills) collection में रहता है:

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

हर project के लिए install करने के लिए `-g` add करें बजाय केवल current one के, और `--copy` अगर आपका environment symlinks follow नहीं करता। Codex के लिए, `-a codex` pass करें।

## इसे हाथ से install करना

Agent Skills folders हैं जिनमें `SKILL.md` plus references हैं। अगर आप installer use नहीं करना चाहते:

- **Claude Code**: `agenteye-python-sdk/` folder को `~/.claude/skills/` (हर project) या `<your-repo>/.claude/skills/` (केवल वह repo) में copy करें। Claude Code इसे automatically discover करता है — `/skills` list check करें, या बस कुछ पूछें जो इससे match हो।
- **Codex**: Codex वही `SKILL.md` पढ़ता है। Bundled `agents/openai.yaml` `allow_implicit_invocation: true` set करता है, तो यह auto-selected है जब task match हो; अन्यथा इसे `$agenteye-python-sdk` के रूप में invoke करें।

अपने agent को उस repository में **चलाएं जिसमें वह code है जिसे आप instrument करना चाहते हैं** — skill आपके agent loop को पढ़ता है इससे पहले कि यह कुछ propose करे।

## एक session कैसा दिखता है

```text
you   ▸ इस agent में Failproof AI Observability add करो।

agent ▸ आपके loop को पढ़ा — tools.py में एक tool dispatcher, llm.py में एक 
        Anthropic wrapper। कुछ लिखने से पहले दो सवाल।

        एक run क्या है? आप requests को concurrently handle करते हो, तो मैं
        ctx.request_id use करूंगा जो तुम्हारे पास पहले से है — फिर यहां एक
        session और तुम्हारे logs में एक request एक ही string होंगे।

        और actors कौन हैं? मैं एक planner path और एक researcher path देखता हूं।
        इन्हें अलग से label करो, या ये एक ही agent है तुम्हारे लिए?

you   ▸ Request id सही है। ये एक agent हैं, इसे "assistant" कहो।

agent ▸ हो गया। Dispatcher और LLM client को wrap किया; agent_start और
        agent_end handle_request को bracket करते हैं, error path सहित। 
        Identity के लिए context-local use किया — तुम्हारा dispatcher tools को 
        thread pool में चलाता है, और simpler approach concurrent runs को एक 
        session में mix कर देता बिना complain किए।

        एक real run के खिलाफ verified: 11 events 4 files में — agent_start, 
        model_request/response, tool_use/tool_result x3, agent_end 
        (outcome=success)। environment=production, एक session per request, 
        durations paired।

        एक चीज मैंने नहीं की: तुम्हारे batch.py में worker pool straight executor 
        को submit करता है, तो वहां से events drop हो जाएंगे। क्या मैं उन्हें भी
        ठीक कर दूं?
```

देखने के लिए pattern: यह code को पढ़ा इससे पहले कि कुछ propose करे, केवल वे सवाल पूछे जिनका आप जवाब दे सकते हो, एक id reuse किया जो आपके पास पहले से था, concurrency-safe shape चुना *क्योंकि* उसे एक thread pool दिखा, और **actual events पढ़कर verify किया** बजाय success declare करने के — फिर उस एक जगह को flag किया जहां यह जानता है कि quietly fail होगा।

## आप इससे क्या पूछ सकते हैं

- *"मेरा agent dashboard पर क्यों show नहीं हो रहा है?"* → ladder में चलता है: क्या events लिखे जा रहे हैं, क्या `agent_start` है, क्या environment सही है, क्या collector वही जगह पढ़ रहा है।
- *"सब कुछ dev के तहत land हो रहा है।"* → environment कभी set नहीं हुआ, या बाद की call से reset हुआ।
- *"Token tracking add करो।"* → आपके LLM wrapper को ढूंढता है और model, stop reason, और usage record करता है।
- *"Sub-agents को भी instrument करो।"* → एक session, distinct agent labels, अपने parent के तहत nested।
- *"Instrumentation के लिए tests लिखो।"* → SDK को एक temporary directory की ओर point करता है और events पर assert करता है।

## किस बात पर ध्यान दें

**इसे verify करने दें।** वह step जो इस skill को use करने लायक बनाता है, आखिरी है — आपके agent को चलाना और events को वापस पढ़ना। एक agent जो instrumentation लिखे और रुके, उसने आसान आधा किया है, और जो आधा quietly fail होता है, वह दूसरा है।

**Code से पहले names agree करें।** `session_id` और `agent_id` वे axes हैं जिन पर हर surface group करता है। इन्हें बाद में rename करने से history टूट जाता है: पुरानी runs पुराने labels रखते हैं और आपके trends टूट जाते हैं। Skill पूछेगा; जवाब सोचने के एक मिनट के लायक है।

**अगर आपका agent SDK को public index से install करने का propose करता है, तो skill load नहीं हुआ।** SDK privately distribute किया जाता है। वह proposal एक reliable tell है कि आपका coding agent guess कर रहा है बजाय skill follow करने के — इसे वहीं रोकें और check करें कि skill install है।

उससे परे इसका blast radius छोटा है: यह आपकी working directory में code लिखता है और event files जहां आप बताते हो। यह अपने deployment से कुछ नहीं पढ़ता और इसके बारे में कुछ नहीं बदलता।
