failproofai 39 अंतर्निर्मित नीतियों के साथ आता है जो सामान्य एजेंट विफलता मोड को पकड़ती हैं। प्रत्येक नीति एक विशिष्ट हुक ईवेंट प्रकार और टूल नाम पर सक्रिय होती है। उन्नीस नीतियां पैरामीटर स्वीकार करती हैं जो आपको कोड लिखे बिना उनके व्यवहार को ट्यून करने देती हैं। पाँच वर्कफ़्लो नीतियां Claude के रुकने से पहले एक commit → push → PR → CI पाइपलाइन को लागू करती हैं।

---

## अवलोकन

नीतियों को श्रेणियों में विभाजित किया गया है:

| श्रेणी | नीतियां | हुक प्रकार |
|----------|----------|-----------|
| [खतरनाक कमांड](#dangerous-commands) | block-sudo, block-rm-rf, block-curl-pipe-sh, block-failproofai-commands, block-self-pause | PreToolUse |
| [इंफ्रा कमांड](#infra-commands) | block-kubectl, block-terraform, block-aws-cli, block-gcloud, block-az-cli, block-helm, block-gh-pipeline | PreToolUse |
| [सीक्रेट्स (सैनिटाइज़र)](#secrets-sanitizers) | sanitize-jwt, sanitize-api-keys, sanitize-connection-strings, sanitize-private-key-content, sanitize-bearer-tokens | PostToolUse |
| [पर्यावरण](#environment) | block-env-files, protect-env-vars | PreToolUse |
| [फाइल एक्सेस](#file-access) | block-read-outside-cwd, block-secrets-write | PreToolUse |
| [Git](#git) | block-push-master, block-work-on-main, block-force-push, warn-git-amend, warn-git-stash-drop, warn-all-files-staged | PreToolUse |
| [डेटाबेस](#database) | warn-destructive-sql, warn-schema-alteration | PreToolUse |
| [चेतावनियां](#warnings) | warn-large-file-write, warn-package-publish, warn-background-process, warn-global-package-install | PreToolUse |
| [पैकेज मैनेजर](#package-managers) | prefer-package-manager | PreToolUse |
| [वर्कफ़्लो](#workflow) | require-commit-before-stop, require-push-before-stop, require-pr-before-stop, require-no-conflicts-before-stop, require-ci-green-before-stop | Stop |

- **`block-`** — एजेंट को आगे बढ़ने से रोकें।
- **`warn-`** — एजेंट को अतिरिक्त संदर्भ दें ताकि वह स्वयं को ठीक कर सके।
- **`sanitize-`** — एजेंट को दिखाने से पहले टूल आउटपुट से संवेदनशील डेटा को हटाएं।

### नेमस्पेस

हर नीति एक `<namespace>/<name>` स्लॉट में रहती है। अंतर्निर्मित नीतियां **`failproofai/`** नेमस्पेस से संबंधित हैं — उदाहरण के लिए, `failproofai/sanitize-jwt`। नेमस्पेस समान छोटे नामों वाली कस्टम या तृतीय-पक्ष नीतियों के साथ टकराव को रोकता है।

अपने कॉन्फ़िगरेशन में आप एक अंतर्निर्मित नीति को उसके छोटे नाम या योग्य नाम से संदर्भित कर सकते हैं; दोनों रूप समान नीति को हल करते हैं:

```json
{
  "enabledPolicies": [
    "sanitize-jwt",
    "failproofai/block-rm-rf"
  ]
}
```

यदि एक नाम में `/` नहीं है, तो failproofai इसे डिफ़ॉल्ट नेमस्पेस `failproofai` से संबंधित मानता है। नाम जिनमें पहले से `/` है (जैसे `myorg/foo`, `custom/my-hook`) को जैसे हैं रखा जाता है।
- **`require-`** — शर्तें पूरी होने तक Stop ईवेंट को ब्लॉक करें।

---

<Tip>
हर नीति `policyParams` में एक वैकल्पिक `hint` फील्ड को समर्थन करती है। हिंट को deny या instruct संदेश में जोड़ा जाता है जो Claude को दिखता है, नीति कोड को संशोधित किए बिना कार्यशील मार्गदर्शन देता है। अंतर्निर्मित, कस्टम और सम्मेलन नीतियों के साथ काम करता है। विवरण के लिए [कॉन्फ़िगरेशन → hint](/hi/configuration#hint-cross-cutting) देखें।
</Tip>

## खतरनाक कमांड

एजेंट्स को ऐसे ऑपरेशन चलाने से रोकें जो पूर्ववत करने में कठिन हैं या होस्ट सिस्टम को नुकसान पहुंचा सकते हैं।

### `block-sudo`

**ईवेंट:** PreToolUse (Bash)  
**डिफ़ॉल्ट:** किसी भी `sudo` या `doas` कमांड को निषेधित करता है।

एक कमांड को ब्लॉक करता है जो **कमांड पोजीशन** में एक उन्नयन बाइनरी चलाता है। मिलान पाठ्य के बजाय संरचनात्मक है: कमांड को उस तरह विभाजित किया जाता है जैसे शेल करेगा, उपसर्ग असाइनमेंट (`FOO=bar`), पुनर्निर्देशन, और रनर्स अपने फ्लैग्स (`env`, `nohup`, `timeout`, `xargs`, `sh -c`, …) के साथ चले जाते हैं, और परिणामी बाइनरी की तुलना **basename** से की जाती है। तो `/usr/bin/sudo`, `env sudo`, `timeout 5 sudo`, `"sudo"`, `\sudo` और `bash -c "sudo …"` सभी को निषेधित किया जाता है, और `doas` को एक अलग नाम के तहत एक ही क्षमता के रूप में माना जाता है।

क्योंकि यह कमांड पोजीशन पर एंकर करता है, न कि केवल शब्द कहीं दिखने पर, यह कमांड पर नहीं चलता है जो केवल इसका उल्लेख करते हैं — `grep -r sudo /etc`, `cat /etc/sudoers`, `git commit -m "fix sudo handling"`, या शब्द युक्त एक `grep` वैकल्प सभी सामान्य रूप से चलते हैं।

<Warning>
यह स्पष्ट प्रयास को रोकता है; यह क्लास को बंद नहीं करता है। एक एजेंट जो मनमाना शेल चला सकता है वह अभी भी परोक्ष रूप से उन्नयन तक पहुंच सकता है — एक चर के माध्यम से (`S=sudo; $S …`), एक base64-डिकोड किए गए पाइप के माध्यम से, या डिस्क पर एक रैपर स्क्रिप्ट के माध्यम से — क्योंकि एकल कमांड स्ट्रिंग का कोई निरीक्षण उन का पालन नहीं कर सकता। इसे गलतियों और आकस्मिक उन्नयन के विरुद्ध गार्डरेल के रूप में मानें, न कि एक दृढ़ एजेंट के विरुद्ध सुरक्षा सीमा के रूप में। एक वास्तविक सीमा को शेल के नीचे लागू किया जाना चाहिए।
</Warning>

**पैरामीटर:**

| पैरामीटर | प्रकार | डिफ़ॉल्ट | विवरण |
|-------|------|---------|-------------|
| `allowPatterns` | `string[]` | `[]` | सटीक कमांड उपसर्ग जो अनुमत हैं। प्रत्येक प्रविष्टि को पार्स किए गए argv टोकन के विरुद्ध मिलाया जाता है। |

**उदाहरण:**

```json
{
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    }
  }
}
```

इस कॉन्फ़िगरेशन के साथ, `sudo systemctl status nginx` की अनुमति है, लेकिन `sudo rm /etc/hosts` निषेधित है।

<Note>
पैटर्न को कच्ची कमांड स्ट्रिंग के बजाय पार्स किए गए टोकन के विरुद्ध मिलाया जाता है। यह संलग्न शेल ऑपरेटर के माध्यम से बाईपास को रोकता है (जैसे `sudo systemctl status x; rm -rf /` को `sudo systemctl status *` से मेल नहीं खाता है)।
</Note>

### `block-self-pause`

**ईवेंट:** PreToolUse (Bash)  
**डिफ़ॉल्ट:** `failproofai config --pause` को निषेधित करता है, जो एक सत्र के लिए प्रवर्तन को निलंबित करता है। रुकना एक मानव निर्णय है — एक एजेंट जो इसे चला सकता है वह एक ही कमांड के साथ हर दूसरी नीति को बंद कर सकता है।

[`block-failproofai-commands`](#block-failproofai-commands) की तुलना में इरादे से संकीर्ण, और इसके द्वारा कवर नहीं: वह नीति कमांड सीमा पर एंकर करती है, इसलिए `npx -y failproofai config --pause` उससे मेल नहीं खाता है, और व्यापक होने के कारण अक्सर बंद किया जाता है ताकि एजेंट `failproofai audit` चला सकें। `--resume` और `--status` की अनुमति है — न तो प्रवर्तन को हटाता है।

यह प्रत्यक्ष प्रयास को रोकता है, पूरी क्लास नहीं: एक एजेंट अभी भी एक उपनाम या रैपर स्क्रिप्ट के माध्यम से समान स्थिति तक पहुंच सकता है। इसे पूरी तरह बंद करने के लिए पॉज़ को टूल कॉल से पूरी तरह अप्राप्य होना चाहिए।

कोई पैरामीटर नहीं।

## इंफ्रा कमांड

कोडिंग एजेंट्स को इंफ्रास्ट्रक्चर CLI चलाने या CI/CD पाइपलाइन ट्रिगर करने से रोकें। इस श्रेणी की सभी नीतियां **opt-in** (`defaultEnabled: false`) हैं — एजेंट्स जिन्हें वास्तव में `kubectl`, `terraform`, आदि को कॉल करने की आवश्यकता है, नीति को सक्षम न करने तक विचलित नहीं होंगे। जब सक्षम होती है, तो मिलान किए गए CLI की हर आह्वान को निषेधित किया जाता है जब तक कि कमांड `allowPatterns` में एक प्रविष्टि से मेल न खाए।

पैटर्न व्याकरण [`block-sudo`](#block-sudo) के समान है: टोकन को पार्स किए गए argv के विरुद्ध मिलाया जाता है, `*` एक टोकन के लिए वाइल्डकार्ड है, और कोई भी कमांड जिसमें एक स्टैंडअलोन शेल ऑपरेटर (`&&`, `||`, `|`, `;`) या एक टोकन जिसमें एम्बेडेड शेल मेटाकैरेक्टर हैं, injection बाईपास को रोकने के लिए allowlist मिलान से पहले अस्वीकार किया जाता है।

### `block-gh-pipeline`

**ईवेंट:** PreToolUse (Bash)  
**डिफ़ॉल्ट:** निम्नलिखित `gh` CLI सबकमांड को निषेधित करता है जो स्थिति को परिवर्तित करते हैं या पाइपलाइन ट्रिगर करते हैं:

- `gh workflow run`, `gh workflow enable`, `gh workflow disable`
- `gh run rerun`, `gh run cancel`
- `gh pr merge`
- `gh release create`, `gh release delete`
- `gh cache delete`
- `gh secret set`, `gh secret delete`

पढ़ने-केवल `gh` सबकमांड जैसे `gh pr view`, `gh pr list`, `gh run list`, `gh release view` और `gh api repos/.../...` **नहीं** इस नीति से मिलते हैं — वर्कफ़्लो जांच के लिए दिनचर्या से आवश्यक हैं (failproofai के स्वयं के `require-ci-green-before-stop` सहित)।

**पैरामीटर:**

| पैरामीटर | प्रकार | डिफ़ॉल्ट | विवरण |
|-------|------|---------|-------------|
| `allowPatterns` | `string[]` | `[]` | विशिष्ट स्क्रिप्टेड आह्वान जो अनुमत हैं भले ही वे अन्यथा निषेधित होते। |

**उदाहरण:**

```json
{
  "policyParams": {
    "block-gh-pipeline": {
      "allowPatterns": ["gh run rerun *"]
    }
  }
}
```

## सीक्रेट्स (सैनिटाइज़र)

एजेंट्स को अपने संदर्भ या आउटपुट में credentials लीक करने से रोकें। सैनिटाइज़र नीतियां **PostToolUse** ईवेंट पर चलती हैं। जब Claude एक Bash कमांड चलाता है, फाइल पढ़ता है, या कोई टूल कॉल करता है, तो ये नीतियां आउटपुट को Claude को वापस किए जाने से पहले निरीक्षण करती हैं। यदि एक secret पैटर्न का पता चलता है, तो नीति एक deny निर्णय लौटाती है जो आउटपुट को वापस पारित होने से रोकता है।

### `sanitize-jwt`

**ईवेंट:** PostToolUse (सभी टूल्स)  
**डिफ़ॉल्ट:** JWT tokens को छुपाता है (तीन base64url खंड `.` से अलग)।

कोई पैरामीटर नहीं।

---

### `sanitize-api-keys`

**ईवेंट:** PostToolUse (सभी टूल्स)  
**डिफ़ॉल्ट:** सामान्य API key फॉर्मेट को छुपाता है: Anthropic (`sk-ant-`), OpenAI (`sk-`), GitHub PATs (`ghp_`), AWS access keys (`AKIA`), Stripe keys (`sk_live_`, `sk_test_`), और Google API keys (`AIza`)।

**पैरामीटर:**

| पैरामीटर | प्रकार | डिफ़ॉल्ट | विवरण |
|-------|------|---------|-------------|
| `additionalPatterns` | `{ regex: string; label: string }[]` | `[]` | अतिरिक्त regex पैटर्न जिन्हें secrets के रूप में माना जाए। |

**उदाहरण:**

```json
{
  "policyParams": {
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo internal API key" },
        { "regex": "pat_[0-9a-f]{40}", "label": "Internal PAT" }
      ]
    }
  }
}
```

**ईवेंट:** PostToolUse (सभी टूल्स)  
**डिफ़ॉल्ट:** डेटाबेस कनेक्शन स्ट्रिंग्स को छुपाता है जिनमें एम्बेडेड credentials हैं (जैसे `postgresql://user:password@host/db`)।

### `sanitize-private-key-content`

**ईवेंट:** PostToolUse (सभी टूल्स)  
**डिफ़ॉल्ट:** PEM blocks को छुपाता है (`-----BEGIN PRIVATE KEY-----`, `-----BEGIN RSA PRIVATE KEY-----`, आदि)।

**ईवेंट:** PostToolUse (सभी टूल्स)  
**डिफ़ॉल्ट:** `Authorization: Bearer <token>` headers को छुपाता है जहां token 20 या अधिक वर्ण है।

## फाइल एक्सेस

**पैरामीटर:**

| पैरामीटर | प्रकार | डिफ़ॉल्ट | विवरण |
|-------|------|---------|-------------|
| `allowPaths` | `string[]` | `[]` | पूर्ण पाथ उपसर्ग जो अनुमत हैं भले ही प्रोजेक्ट रूट के बाहर हों। |

**उदाहरण:**

```json
{
  "policyParams": {
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company/config"]
    }
  }
}
```

```json
  }
```

## Git

आकस्मिक pushes, force-pushes, और branch की गलतियों को रोकें जो पूर्ववत करने में कठिन हैं।

### `block-push-master`

**ईवेंट:** PreToolUse (Bash)  
**डिफ़ॉल्ट:** `git push origin main` और `git push origin master` को निषेधित करता है।

**पैरामीटर:**

| पैरामीटर | प्रकार | डिफ़ॉल्ट | विवरण |
|-------|------|---------|-------------|
| `protectedBranches` | `string[]` | `["main", "master"]` | Branch नाम जो सीधे push नहीं किए जा सकते। |

**उदाहरण:**

```json
{
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "master", "release", "prod"]
    }
  }
}
```

<Tip>
सभी branches को push करने की अनुमति देने के लिए (इस नीति को प्रभावी रूप से अक्षम करें `enabledPolicies` से हटाए बिना), `protectedBranches: []` सेट करें।
</Tip>

**ईवेंट:** PreToolUse (Bash)  
**डिफ़ॉल्ट:** `git commit`, `git merge`, `git rebase`, और `git cherry-pick` को निषेधित करता है जबकि working tree `main` या `master` पर है। Branch creation और switching (`git checkout`, `git checkout -b`, `git switch`, `git switch -c`) प्रभावित नहीं होते हैं।

**पैरामीटर:**

| पैरामीटर | प्रकार | डिफ़ॉल्ट | विवरण |
|-------|------|---------|-------------|
| `protectedBranches` | `string[]` | `["main", "master"]` | Branch नाम जिन पर commit/merge/rebase/cherry-pick निषेधित है। |

---

### `block-force-push`

**ईवेंट:** PreToolUse (Bash)  
**डिफ़ॉल्ट:** `git push --force` और `git push -f` को निषेधित करता है।

कोई नीति-विशिष्ट पैरामीटर नहीं। वैकल्पिक सुझाव देने के लिए क्रॉस-कटिंग [`hint`](/hi/configuration#hint-cross-cutting) का उपयोग करें:

```json
}
```

## पैकेज मैनेजर

एजेंट को कौन से पैकेज मैनेजर का उपयोग करने की अनुमति है यह लागू करें।

### `prefer-package-manager`

**ईवेंट:** PreToolUse (Bash)  
**डिफ़ॉल्ट:** अक्षम। जब सक्षम होता है, `allowed` सूची में नहीं होने वाले किसी भी पैकेज मैनेजर कमांड को ब्लॉक करता है और Claude को एक allowed मैनेजर का उपयोग करके कमांड को फिर से लिखने के लिए बताता है।

आविष्कार करता है: pip, pip3, python -m pip, npm, npx, yarn, pnpm, pnpx, bun, bunx, uv, poetry, pipenv, conda, cargo।

| पैरामीटर | प्रकार | डिफ़ॉल्ट | विवरण |
|-----------|------|---------|-------------|
| `allowed` | string[] | `[]` | अनुमत पैकेज मैनेजर नाम। इस सूची में नहीं होने वाले कोई भी आविष्कृत मैनेजर ब्लॉक किया जाता है। जब खाली हो, नीति एक no-op है। |
| `blocked` | string[] | `[]` | built-in सूची के बाहर ब्लॉक करने के लिए अतिरिक्त मैनेजर नाम (जैसे `['pdm', 'pipx']`)। |

Built-in block सूची में शामिल है: pip, pip3, npm, npx, yarn, pnpm, pnpx, bun, bunx, uv, poetry, pipenv, conda, cargo। इस सूची में नहीं होने वाले मैनेजर को जोड़ने के लिए `blocked` का उपयोग करें।

**उदाहरण कॉन्फ़िगरेशन:**

```json
{
  "enabledPolicies": ["prefer-package-manager"],
  "policyParams": {
    "prefer-package-manager": {
      "allowed": ["uv", "bun"],
      "blocked": ["pdm", "pipx"]
    }
  }
}
```

इस कॉन्फ़िगरेशन के साथ, `pip install flask` और `pdm install flask` दोनों को deny किया जाता है Claude को `uv` या `bun` का उपयोग करने के लिए कहने वाले संदेश के साथ। `uv pip install flask` जैसी कमांड की अनुमति है क्योंकि `uv` allowlist में है और पहले check किया जाता है।

## वर्कफ़्लो

एक अनुशासित end-of-session वर्कफ़्लो को लागू करें। ये नीतियां **Stop** ईवेंट पर चलती हैं और एजेंट को रुकने से deny करती हैं जब तक प्रत्येक शर्त पूरी न हो। वे एक प्राकृतिक निर्भरता chain का अनुसरण करती हैं: commit → push → PR → CI। यदि एक नीति deny करती है, तो chain में बाद की नीतियों को छोड़ दिया जाता है (deny short-circuits)।

सभी वर्कफ़्लो नीतियां **fail-open** हैं: यदि आवश्यक टूल उपलब्ध नहीं है (`gh` installed नहीं, no git remote), तो नीति एक informational संदेश के साथ allow करती है जो समझाता है कि check को क्यों छोड़ा गया।

### Per-CLI Stop semantics

Stop enforcement प्रत्येक CLI में थोड़ा अलग दिखता है क्योंकि प्रत्येक एक अलग "agent finished" hook contract को उजागर करता है। **परिणाम** समान है — एजेंट workflow gate विफल होने के दौरान stop करने से नहीं बच पाता है — लेकिन **mechanics** भिन्न हैं। नीचे दी गई तालिका सारांश देती है; केवल Pi के पास एक user-visible quirk है जो एक `require-*-before-stop` नीति को सक्षम करने से पहले समझने योग्य है।

| CLI | gate कब चलता है | आप क्या देखते हैं |
|---|---|---|
| Claude Code | समान एजेंट loop, तुरंत | Claude काम करना जारी रखता है — समस्या को ठीक करता है, फिर खत्म करने का प्रयास फिर से करता है। आपको कोई रुकावट visible नहीं होती है। |
| Codex | समान एजेंट loop, तुरंत | Claude के समान। |
| GitHub Copilot CLI | समान एजेंट loop, तुरंत | Claude के समान (Copilot के `{decision:"block", reason}` retry चैनल का उपयोग करता है — empirically verified Copilot CLI 1.0.41 के विरुद्ध)। |
| Cursor Agent | समान एजेंट loop, तुरंत | Claude के समान (Cursor के `{followup_message}` चैनल का उपयोग करता है — `loop_limit` पर capped, default 5 retries)। |
| OpenCode | समान एजेंट loop, तुरंत | Claude के समान (`hookSpecificOutput.additionalContext` के माध्यम से routed `client.session.prompt(...)` SDK call का उपयोग करता है)। |
| **Pi (pi-coding-agent)** | **अगली user turn** | **Pi visibly stop होता है** जब gate चलता है — इसका एजेंट loop exits और आप prompt पर वापस return होते हैं। Gate फिर अगली बार चलता है जब आप एक prompt submit करते हैं: failproofai एक `MANDATORY ACTION REQUIRED` directive को उस turn के system prompt में prepend करता है, LLM को workflow step (commit, push, आदि) को complete करने का निर्देश देता है आपने जो माँगा है उससे पहले। |

<Note>
**Pi limitation.** Pi का `AgentEndEvent` (Claude के `Stop` hook के upstream equivalent) में Result type नहीं है — जब तक यह चलता है, Pi का एजेंट loop पहले से exit हो चुका है। Pi को उसी तरह retry के लिए force नहीं किया जा सकता जैसे Claude / Copilot / Cursor / OpenCode कर सकते हैं। failproofai gate को Pi के `before_agent_start` ईवेंट में shift करता है (जो अगली user prompt के बाद चलता है) ताकि वर्कफ़्लो check अभी भी लागू हो, बस current turn के बजाय अगली turn पर।

**इसका practice में क्या मतलब है:**

- Pi के stop के बाद, deny reason को Pi session id द्वारा keyed in-memory में captured किया जाता है। आप जो अगली prompt submit करते हैं उसी Pi process में drain करता है: LLM अपने system prompt के शीर्ष पर `MANDATORY ACTION REQUIRED` निर्देश देखता है, commit करता है (या push / PR खोलता है / CI wait करता है), और केवल तभी आपके request के साथ जारी रहता है। Captured deny reason one-shot है — एक बार drain करने के बाद, gate स्पष्ट है।
- Gate Pi के process lifetime से bounded है। यदि आप Pi को `Ctrl+C` करते हैं या turns के बीच quit करते हैं, तो in-memory entry process के साथ dropped होती है और gate missed होता है। Claude, Copilot, Cursor, और OpenCode का same bound है (एजेंट को kill करें और gate missed है) — Pi बस इसे अधिक visible बनाता है क्योंकि एजेंट gate चलने से पहले visibly exit होता है।
- एक pending deny को `session_shutdown` पर किसी भी कारण के लिए भी clear किया जाता है (`new` / `resume` / `fork` / `quit`), इसलिए prior session से एक stale gate अगली turn में fresh session में एक Pi process में leak नहीं हो सकता है।

यदि आपको Claude-style same-loop retry चाहिए, तो आपकी `Stop` नीतियों को supported पाँच CLIs में से किसी के तहत भी run करें। हम Pi को upstream track कर रहे हैं एक future Result type के लिए `AgentEndEvent` पर जो हमें इस gap को close करने देगा।
</Note>

### `require-commit-before-stop`

**ईवेंट:** Stop  
**डिफ़ॉल्ट:** uncommitted changes (modified, staged, या untracked files) होने पर stop को deny करता है। जब working directory clean हो तो एक informational संदेश return करता है।

### `require-push-before-stop`

**ईवेंट:** Stop  
**डिफ़ॉल्ट:** unpushed commits होने पर या जब current branch के पास कोई remote tracking branch नहीं हो तो stop को deny करता है। यदि आवश्यक हो तो tracking branch बनाने के लिए `git push -u` suggest करता है। यदि कोई remote configured नहीं है तो fail open करता है।

**पैरामीटर:**

| पैरामीटर | प्रकार | डिफ़ॉल्ट | विवरण |
|-------|------|---------|-------------|
| `remote` | `string` | `"origin"` | Push करने के लिए remote नाम। |

**उदाहरण:**

```json
{
  "policyParams": {
    "require-push-before-stop": {
      "remote": "upstream"
    }
  }
}
```

### `require-pr-before-stop`

**ईवेंट:** Stop  
**डिफ़ॉल्ट:** जब current branch के लिए कोई pull request मौजूद नहीं है, या existing PR merge किए बिना closed है तो stop को deny करता है। Claude को `gh pr create` के साथ PR create करने का निर्देश देता है। जब PR **merged** हो, तो नीति allow करती है (work shipped हो गया है) और message hint देता है branch को बंद करने के लिए (`git checkout main && git pull`)।

कोई पैरामीटर नहीं।

<Note>
इस नीति के लिए [GitHub CLI](https://cli.github.com/) (`gh`) को install और authenticated होना चाहिए।
`gh auth login` को एक personal access token के साथ run करें जिसमें pull requests को read access के लिए `repo` scope हो। यदि `gh` installed नहीं है या authenticated नहीं है, तो नीति fail open करती है और Claude को reason report करती है।
</Note>

### `require-no-conflicts-before-stop`

**ईवेंट:** Stop  
**डिफ़ॉल्ट:** जब current branch cleanly merge नहीं कर सकता तो base branch में stop को deny करता है। नीति पहले confirm करती है कि branch के लिए GitHub पर एक `OPEN` PR है — बिना एक के, कोई merge target नहीं है enforce करने के लिए, इसलिए पूरी नीति short-circuit करके allow करती है। एक बार `OPEN` PR confirm होने के बाद, दो independent probes चलते हैं:

1. **Local** — `git merge-tree --write-tree --name-only origin/<baseBranch> HEAD`। Conflict पर, deny message conflicted फाइलों को नाम देता है ताकि Claude को सटीक पता हो क्या resolve करना है।
2. **GitHub** — precheck में पहले से fetched `gh pr view --json mergeable,state` result को reuse करता है। Conflicts को catch करता है जो एक stale local `origin/<baseBranch>` miss करेगा (जैसे किसी ने `main` पर एक conflicting PR land किया है जब से last fetch)। एक `CONFLICTING` result deny करता है। एक `UNKNOWN` result भी deny करता है और Claude को ~10 seconds wait करने और फिर से check करने का निर्देश देता है stop करने का प्रयास फिर से करने से पहले — यह false negatives को रोकता है जबकि GitHub recompute करता है।

Entirely skip करता है (allows) जब: `gh` installed नहीं है, branch के लिए कोई PR नहीं है, PR का state `OPEN` नहीं है (`MERGED`, `CLOSED` आदि), या `gh pr view` unparseable output return करता है। जब `origin/<baseBranch>` locally missing है या कोई commits base से ahead नहीं हैं तब भी fail open करता है — वे Layer 1 fall-throughs अभी भी allow करने से पहले cached PR mergeability को consult करते हैं।

**पैरामीटर:**

| पैरामीटर | प्रकार | डिफ़ॉल्ट | विवरण |
|-------|------|---------|-------------|
| `baseBranch` | `string` | `"main"` | Conflicts को check करने के लिए base branch। |

<Note>
इस नीति के लिए GitHub CLI (`gh`) आवश्यक है। नीति किसी भी conflict probe को चलाने से पहले confirm करने के लिए `gh pr view` का उपयोग करता है कि एक `OPEN` PR मौजूद है — बिना `gh` के, नीति short-circuit करके allow करती है। `gh auth login` को एक personal access token के साथ run करें जिसमें pull requests को read access के लिए `repo` scope हो।
</Note>

### `require-ci-green-before-stop`

**ईवेंट:** Stop  
**डिफ़ॉल्ट:** जब CI checks current branch पर failing या still running हैं तो stop को deny करता है। GitHub Actions workflow runs और third-party bot checks (जैसे CodeRabbit, SonarCloud, Codecov) दोनों को check करता है। `skipped`, `cancelled`, और `neutral` conclusions को non-failing के रूप में मानता है (latter covers जैसे Socket Security alerts on outside contributor PRs, जहां app intentionally neutral rather than success/failure report करता है)। जब सभी checks pass तो एक informational संदेश return करता है।

कोई पैरामीटर नहीं।

<Note>
इस नीति के लिए [GitHub CLI](https://cli.github.com/) (`gh`) को install और authenticated होना चाहिए।
`gh auth login` को एक personal access token के साथ run करें जिसमें Actions workflow runs और Checks API को read access के लिए `repo` scope हो। यदि `gh` installed नहीं है या authenticated नहीं है, तो नीति fail open करती है और Claude को reason report करती है।
</Note>

अपने config में `enabledPolicies` से एक विशिष्ट नीति को remove करें, या dashboard के Policies tab में इसे toggle करें।

```json
{
  "enabledPolicies": [
    "block-rm-rf",
    "sanitize-api-keys"
  ]
}
```

`enabledPolicies` में listed नहीं होने वाली नीतियां नहीं चलती हैं, भले ही उनके लिए `policyParams` entries मौजूद हों।
