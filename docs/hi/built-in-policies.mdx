failproofai 39 अंतर्निहित policies के साथ आता है जो आम agent failure modes को पकड़ते हैं। प्रत्येक policy एक विशिष्ट hook event type और tool name पर काम करती है। उन्नीस policies ऐसे parameters स्वीकार करती हैं जो आपको code लिखे बिना उनके व्यवहार को tune करने देते हैं। पाँच workflow policies एक commit → push → PR → CI pipeline को enforce करती हैं इससे पहले कि Claude रुके।

---

## Overview

Policies को categories में group किया गया है:

| Category | Policies | Hook type |
|----------|----------|-----------|
| [Dangerous commands](#dangerous-commands) | block-sudo, block-rm-rf, block-curl-pipe-sh, block-failproofai-commands, block-self-pause | PreToolUse |
| [Infra commands](#infra-commands) | block-kubectl, block-terraform, block-aws-cli, block-gcloud, block-az-cli, block-helm, block-gh-pipeline | PreToolUse |
| [Secrets (sanitizers)](#secrets-sanitizers) | sanitize-jwt, sanitize-api-keys, sanitize-connection-strings, sanitize-private-key-content, sanitize-bearer-tokens | PostToolUse |
| [Environment](#environment) | block-env-files, protect-env-vars | PreToolUse |
| [File access](#file-access) | block-read-outside-cwd, block-secrets-write | PreToolUse |
| [Git](#git) | block-push-master, block-work-on-main, block-force-push, warn-git-amend, warn-git-stash-drop, warn-all-files-staged | PreToolUse |
| [Database](#database) | warn-destructive-sql, warn-schema-alteration | PreToolUse |
| [Warnings](#warnings) | warn-large-file-write, warn-package-publish, warn-background-process, warn-global-package-install | PreToolUse |
| [Package managers](#package-managers) | prefer-package-manager | PreToolUse |
| [Workflow](#workflow) | require-commit-before-stop, require-push-before-stop, require-pr-before-stop, require-no-conflicts-before-stop, require-ci-green-before-stop | Stop |

- **`block-`** — agent को आगे बढ़ने से रोकें।
- **`warn-`** — agent को अतिरिक्त context दें ताकि वह आत्म-सुधार कर सके।
- **`sanitize-`** — tool output से संवेदनशील डेटा को साफ़ करें इससे पहले कि agent इसे देखे।

### Namespaces

हर policy एक `<namespace>/<name>` slot में रहती है। Built-in policies failproofai/ namespace से संबंधित होती हैं — उदाहरण के लिए, `failproofai/sanitize-jwt`। यह namespace collisions को रोकता है जब आप custom या third-party policies भी load करते हैं जिनके समान short names हों।

आपके config में आप एक built-in को either its short name या its qualified name से refer कर सकते हैं; दोनों forms एक ही policy को resolve करते हैं:

```json
{
  "enabledPolicies": [
    "sanitize-jwt",
    "failproofai/block-rm-rf"
  ]
}
```

यदि किसी name में `/` नहीं है, तो failproofai इसे default namespace `failproofai` से संबंधित मानता है। Names जिनमें पहले से `/` है (जैसे `myorg/foo`, `custom/my-hook`) को as-is रखा जाता है।
- **`require-`** — Stop event को तब तक block करें जब तक conditions पूरी न हों।

---

<Tip>
हर policy `policyParams` में एक optional `hint` field को support करती है। Hint को deny या instruct message में append किया जाता है जो Claude देखता है, जो बिना policy code को modify किए actionable guidance देता है। Built-in, custom, और convention policies के साथ काम करता है। विवरण के लिए [Configuration → hint](/hi/configuration#hint-cross-cutting) देखें।
</Tip>

## Dangerous commands

Agents को operations चलाने से रोकें जो undo करना मुश्किल हो या जो host system को नुकसान पहुंचा सकते हों।

### `block-sudo`

**Event:** PreToolUse (Bash)  
**Default:** किसी भी `sudo` या `doas` command को deny करता है।

एक command को block करता है जो **command position** में एक elevation binary चलाता है। Matching textual के बजाय structural है: command को उसी तरह split किया जाता है जैसे shell करता, prefix assignments (`FOO=bar`), redirections, और runners with their flags (`env`, `nohup`, `timeout`, `xargs`, `sh -c`, …) को हटाया जाता है, और resulting binary की **basename** से तुलना की जाती है। तो `/usr/bin/sudo`, `env sudo`, `timeout 5 sudo`, `"sudo"`, `\sudo` और `bash -c "sudo …"` सभी को deny किया जाता है, और `doas` को एक अलग नाम के तहत same capability माना जाता है।

क्योंकि यह command position पर anchor करता है न कि word के कहीं भी appear होने पर, यह commands पर fire नहीं करता जो simply इसे mention करते हैं — `grep -r sudo /etc`, `cat /etc/sudoers`, `git commit -m "fix sudo handling"`, या एक `grep` alternation जिसमें word हो, सभी normally चलते हैं।

<Warning>
यह obvious attempt को रोकता है; यह class को नहीं बंद करता। एक agent जो arbitrary shell run कर सकता है indirect रूप से elevation तक पहुंच सकता है — एक variable के through (`S=sudo; $S …`), एक base64-decoded pipe, या disk पर एक wrapper script — क्योंकि कोई भी single command string का inspection उनका पालन नहीं कर सकता। इसे mistakes और casual escalation के विरुद्ध guardrail मानें, न कि determined agent के विरुद्ध security boundary। एक real boundary को shell के नीचे enforce करना पड़ता है।
</Warning>

**Parameters:**

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `allowPatterns` | `string[]` | `[]` | Exact command prefixes जो permitted हैं। हर entry को parsed argv tokens के विरुद्ध match किया जाता है। |

**Example:**

```json
{
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    }
  }
}
```

इस config के साथ, `sudo systemctl status nginx` को allow किया जाता है, लेकिन `sudo rm /etc/hosts` को deny किया जाता है।

<Note>
Patterns को raw command string के बजाय parsed tokens के विरुद्ध match किया जाता है। यह appended shell operators के through bypass को रोकता है (उदाहरण के लिए `sudo systemctl status x; rm -rf /` को `sudo systemctl status *` के match नहीं किया जाता)।
</Note>

### `block-self-pause`

**Event:** PreToolUse (Bash)  
**Default:** `failproofai config --pause` को deny करता है, जो एक session के लिए enforcement को suspend करता है। Pausing एक human decision है — एक agent जो इसे run कर सकता है एक single command के साथ हर दूसरी policy को switch off कर सकता है।

[`block-failproofai-commands`](#block-failproofai-commands) के मुकाबले purpose से narrower, और इसमें शामिल नहीं: वह policy एक command boundary पर anchor करती है, तो `npx -y failproofai config --pause` इसे match नहीं करता, और broad होने से यह अक्सर switch off होती है ताकि agents `failproofai audit` run कर सकें। `--resume` और `--status` को allow किया जाता है — न तो enforcement को हटाता है।

यह direct attempt को रोकता है, पूरे class को नहीं: एक agent अभी भी एक alias या wrapper script के through same state तक पहुंच सकता है। इसे पूरी तरह से बंद करना requires pause को tool call से पूरी तरह unreachable करना।

कोई parameters नहीं।

## Infra commands

Coding agents को infrastructure CLIs चलाने या CI/CD pipelines trigger करने से रोकें। इस category की सभी policies **opt-in** हैं (`defaultEnabled: false`) — agents जो legitimately `kubectl`, `terraform`, आदि को call करने की जरूरत है disrupted नहीं होंगे जब तक आप policy enable न करें। जब enabled हो, matched CLI के हर invocation को deny किया जाता है जब तक command `allowPatterns` में एक entry match न करे।

Pattern grammar [`block-sudo`](#block-sudo) जैसा ही है: tokens को parsed argv के विरुद्ध match किया जाता है, `*` एक token के लिए wildcard है, और कोई भी command जिसमें standalone shell operator (`&&`, `||`, `|`, `;`) हो या एक token जिसमें embedded shell metacharacters हों injection bypasses को रोकने के लिए allowlist matching से पहले reject किया जाता है।

### `block-kubectl`

**Event:** PreToolUse (Bash)  
**Default:** किसी भी `kubectl` invocation को deny करता है।

**Parameters:**

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `allowPatterns` | `string[]` | `[]` | kubectl command prefixes जो permitted हैं। |

**Example:**

```json
{
  "policyParams": {
    "block-kubectl": {
      "allowPatterns": ["kubectl get *", "kubectl describe *", "kubectl logs *"]
    }
  }
}
```

इस config के साथ, `kubectl get pods` को allow किया जाता है लेकिन `kubectl apply -f deploy.yaml` को deny किया जाता है।

**Event:** PreToolUse (Bash)  
**Default:** निम्नलिखित `gh` CLI subcommands को deny करता है जो state mutate या pipelines trigger करते हैं:

**Example:**

```json
{
  "policyParams": {
    "block-gh-pipeline": {
      "allowPatterns": ["gh run rerun *"]
    }
  }
}
```

## Secrets (sanitizers)

Agents को उनके context या output में credentials leak करने से रोकें। Sanitizer policies **PostToolUse** events पर fire करती हैं। जब Claude एक Bash command चलाता है, एक file पढ़ता है, या किसी भी tool को call करता है, ये policies Claude को return किए जाने से पहले output को inspect करती हैं। यदि एक secret pattern detect होता है, तो policy एक deny decision return करती है जो output को pass back होने से रोकता है।

### `sanitize-jwt`

**Event:** PostToolUse (all tools)  
**Default:** JWT tokens को redact करता है (तीन base64url segments separated by `.`)।

कोई parameters नहीं।

---

### `sanitize-api-keys`

**Event:** PostToolUse (all tools)  
**Default:** आम API key formats को redact करता है: Anthropic (`sk-ant-`), OpenAI (`sk-`), GitHub PATs (`ghp_`), AWS access keys (`AKIA`), Stripe keys (`sk_live_`, `sk_test_`), और Google API keys (`AIza`)।

**Parameters:**

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `additionalPatterns` | `{ regex: string; label: string }[]` | `[]` | Additional regex patterns को secrets के रूप में treat करने के लिए। |

**Example:**

```json
{
  "policyParams": {
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo internal API key" },
        { "regex": "pat_[0-9a-f]{40}", "label": "Internal PAT" }
      ]
    }
  }
}
```

---

### `sanitize-connection-strings`

**Event:** PostToolUse (all tools)  
**Default:** Database connection strings को redact करता है जिनमें embedded credentials हों (उदाहरण के लिए `postgresql://user:password@host/db`)।

कोई parameters नहीं।

---

### `sanitize-private-key-content`

**Event:** PostToolUse (all tools)  
**Default:** PEM blocks को redact करता है (`-----BEGIN PRIVATE KEY-----`, `-----BEGIN RSA PRIVATE KEY-----`, आदि)।

कोई parameters नहीं।

---

### `sanitize-bearer-tokens`

**Event:** PostToolUse (all tools)  
**Default:** `Authorization: Bearer <token>` headers को redact करता है जहां token 20 या अधिक characters हो।

कोई parameters नहीं।

## Environment

Sensitive environment configuration को agents द्वारा read या expose किए जाने से protect करें।

### `block-env-files`

**Event:** PreToolUse (Bash, Read)  
**Default:** `.env` files को read करने को deny करता है via `cat .env`, Read tool calls with `.env` as the file path, आदि।

`.envrc` या अन्य environment-adjacent files को block नहीं करता - केवल exactly `.env` नाम की files।

कोई parameters नहीं।

### `protect-env-vars`

**Event:** PreToolUse (Bash)  
**Default:** Commands को deny करता है जो environment variables print करते हैं: `printenv`, `env`, `echo $VAR`।

कोई parameters नहीं।

## File access

Agents को project boundaries के अंदर काम करने और sensitive files से दूर रखें।

### `block-read-outside-cwd`

**Event:** PreToolUse (Read, Bash)  
**Default:** Project root के बाहर files को read करने को deny करता है। Boundary `CLAUDE_PROJECT_DIR` है (जो Claude Code द्वारा हर session में एक बार set होता है), जब वह variable unset हो तो session के current working directory को fallback के साथ। Project root का use करना live `cwd` के बजाय मतलब boundary stable रहता है भले ही Claude एक subdirectory में `cd` करे।

**Parameters:**

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `allowPaths` | `string[]` | `[]` | Absolute path prefixes जो permitted हैं भले ही project root के बाहर हों। |

**Example:**

```json
{
  "policyParams": {
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company/config"]
    }
  }
}
```

---

### `block-secrets-write`

**Event:** PreToolUse (Write, Edit)  
**Default:** Common private keys और certificates में use होने वाली files को write करने को deny करता है: `id_rsa`, `id_ed25519`, `*.key`, `*.pem`, `*.p12`, `*.pfx`।

**Parameters:**

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `additionalPatterns` | `string[]` | `[]` | Additional filename patterns (glob-style) को block करने के लिए। |

**Example:**

```json
{
  "policyParams": {
    "block-secrets-write": {
      "additionalPatterns": [".token", ".secret"]
    }
  }
}
```

## Git

Accidental pushes, force-pushes, और branch mistakes को रोकें जो undo करना मुश्किल हों।

### `block-push-master`

**Event:** PreToolUse (Bash)  
**Default:** `git push origin main` और `git push origin master` को deny करता है।

**Parameters:**

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `protectedBranches` | `string[]` | `["main", "master"]` | Branch names जो directly push नहीं किए जा सकते। |

**Example:**

```json
{
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "master", "release", "prod"]
    }
  }
}
```

<Tip>
सभी branches को push करने के लिए allow करने के लिए (effectively इस policy को `enabledPolicies` से remove किए बिना disable करने के लिए), `protectedBranches: []` set करें।
</Tip>

---

### `block-work-on-main`

**Event:** PreToolUse (Bash)  
**Default:** `git commit`, `git merge`, `git rebase`, और `git cherry-pick` को deny करता है जबकि working tree `main` या `master` पर है। Branch creation और switching (`git checkout`, `git checkout -b`, `git switch`, `git switch -c`) affected नहीं होते।

**Parameters:**

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `protectedBranches` | `string[]` | `["main", "master"]` | Branch names जिन पर commit/merge/rebase/cherry-pick को deny किया जाता है। |

---

### `block-force-push`

**Event:** PreToolUse (Bash)  
**Default:** `git push --force` और `git push -f` को deny करता है।

कोई policy-specific parameters नहीं। Alternatives suggest करने के लिए cross-cutting [`hint`](/hi/configuration#hint-cross-cutting) use करें:

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "अपने current HEAD से एक नई branch create करें (जैसे `git checkout -b <new-branch>`) और उसे instead push करें।"
    }
  }
}
```

---

## Package managers

Enforce करें कि agent किस package manager को use करने की allowed है।

### `prefer-package-manager`

**Event:** PreToolUse (Bash)  
**Default:** Disabled। जब enabled हो, `allowed` list में न होने वाले किसी भी package manager command को block करता है और Claude को command को एक allowed manager का use करके rewrite करने के लिए tell करता है।

Detects: pip, pip3, python -m pip, npm, npx, yarn, pnpm, pnpx, bun, bunx, uv, poetry, pipenv, conda, cargo।

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `allowed` | string[] | `[]` | Allowed package manager names। कोई भी detected manager जो इस list में न हो block किया जाता है। जब empty हो, policy एक no-op है। |
| `blocked` | string[] | `[]` | Additional manager names को block करने के लिए built-in list से beyond (उदाहरण के लिए `['pdm', 'pipx']`)। |

Built-in block list covers: pip, pip3, npm, npx, yarn, pnpm, pnpx, bun, bunx, uv, poetry, pipenv, conda, cargo। Managers को append करने के लिए `blocked` use करें जो इस list में न हों।

**Example configuration:**

```json
{
  "enabledPolicies": ["prefer-package-manager"],
  "policyParams": {
    "prefer-package-manager": {
      "allowed": ["uv", "bun"],
      "blocked": ["pdm", "pipx"]
    }
  }
}
```

इस config के साथ, `pip install flask` और `pdm install flask` दोनों को deny किया जाता है एक message के साथ जो Claude को `uv` या `bun` use करने के लिए tell करता है। Commands जैसे `uv pip install flask` को allow किया जाता है क्योंकि `uv` allowlist में है और पहले check होता है।

## Workflow

एक disciplined end-of-session workflow को enforce करें। ये policies **Stop** event पर fire करती हैं और agent को तब तक stop करने से deny करती हैं जब तक हर condition पूरा न हो। वे एक natural dependency chain follow करती हैं: commit → push → PR → CI। यदि एक policy deny करती है, तो chain में later policies skip होती हैं (deny short-circuits)।

सभी workflow policies **fail-open** हैं: यदि required tool available नहीं है (उदाहरण के लिए `gh` installed नहीं, कोई git remote नहीं), तो policy allow करती है एक informational message के साथ जो explain करता है कि check क्यों skip किया गया।

### Per-CLI Stop semantics

Stop enforcement छह supported CLIs में slightly different दिखता है क्योंकि हर एक एक अलग expose करता है क्योंकि हर एक "agent finished" hook contract को अलग expose करता है। **outcome** same है — agent stop करते समय एक workflow gate fail होने से दूर नहीं जा सकता — लेकिन **mechanics** differ। नीचे दी गई table summarize करती है; केवल Pi के लिए एक user-visible quirk है जो समझने के लिए worth है इससे पहले कि आप एक `require-*-before-stop` policy enable करें।

| CLI | जब gate fires | क्या आप देखते हैं |
|---|---|---|
| Claude Code | Same agent loop, immediately | Claude काम करना continue करता है — issue को fix करता है, फिर finish करने की कोशिश करता है। आपको कोई interruption visible नहीं। |
| Codex | Same agent loop, immediately | Claude जैसा। |
| GitHub Copilot CLI | Same agent loop, immediately | Claude जैसा (Copilot के `{decision:"block", reason}` retry channel को use करता है — empirically Copilot CLI 1.0.41 के विरुद्ध verified)। |
| Cursor Agent | Same agent loop, immediately | Claude जैसा (Cursor के `{followup_message}` channel को use करता है — `loop_limit` पर capped, default 5 retries)। |
| OpenCode | Same agent loop, immediately | Claude जैसा (OpenCode के `client.session.prompt(...)` SDK call को `hookSpecificOutput.additionalContext` के through routed use करता है)। |
| **Pi (pi-coding-agent)** | **Next user turn** | **Pi visibly stops** जब gate fires — इसका agent loop exit होता है और आपको prompt पर return होता है। Gate फिर अगली बार fire होता है जब आप एक prompt submit करते हैं: failproofai एक `MANDATORY ACTION REQUIRED` directive को उस turn के system prompt में prepend करता है, instructing करता है कि LLM workflow step (commit, push, आदि) को complete करे आप जो ask करते हैं उससे पहले। |

<Note>
**Pi limitation.** Pi का `AgentEndEvent` (Claude के `Stop` hook का upstream equivalent) का कोई Result type नहीं है — जब तक यह fires, Pi का agent loop पहले से exit हो चुका होता है। Pi को नहीं force किया जा सकता same loop को retry करने के लिए जैसे Claude / Copilot / Cursor / OpenCode को कर सकते हैं। failproofai gate को Pi के `before_agent_start` event में shift करता है (जो अगले user prompt के बाद fires) ताकि workflow check अभी भी enforce हो, बस current one के बजाय next turn पर।

**इसका practical में क्या मतलब है:**

- Pi stop करने के बाद, deny reason को in-memory Pi session id के द्वारा keyed capture किया जाता है। बिल्कुल अगला prompt जो आप same Pi process में submit करते हैं इसे drain करता है: LLM को अपने system prompt के top पर `MANDATORY ACTION REQUIRED` directive दिखता है, commits (या pushes / PR open करता है / CI wait करता है), और केवल तब आपके request के साथ continue करता है। Captured deny reason one-shot है — एक बार drain होने के बाद, gate clear है।
- Gate Pi की process lifetime से bounded है। यदि आप Pi को `Ctrl+C` करते हैं या turns के बीच quit करते हैं, तो in-memory entry process के साथ dropped होती है और gate miss है। Claude, Copilot, Cursor, और OpenCode का same bound है (agent को kill करो और gate miss है) — Pi बस इसे अधिक visible बनाता है क्योंकि agent visibly exit करता है gate fire होने से पहले।
- एक pending deny को भी किसी भी reason (`new` / `resume` / `fork` / `quit`) के लिए `session_shutdown` पर clear किया जाता है, तो एक prior session से stale gate same Pi process में fresh session में leak नहीं हो सकता।

यदि आपको Claude-style same-loop retry की जरूरत है, अपनी `Stop` policies को छह supported CLIs में से किसी अन्य के under run करें। हम Pi upstream को track कर रहे हैं एक future Result type के लिए `AgentEndEvent` पर जो हमें इस gap को close करने दे।
</Note>

### `require-pr-before-stop`

**Event:** Stop  
**Default:** Stop करने को deny करता है जब current branch के लिए कोई pull request exist न करे, या जब existing PR merged होने के बिना closed हो। Claude को `gh pr create` के साथ एक PR create करने के लिए instruct करता है। जब PR **merged** हो, तो policy allow करती है (work ship हो गया है) और message hint देता है branch को switch करने के लिए (`git checkout main && git pull`)।

</Note>

### `require-no-conflicts-before-stop`

**Event:** Stop  
**Default:** Stop करने को deny करता है जब current branch cleanly base branch में merge नहीं हो सकता। Policy पहले confirm करती है कि branch के लिए GitHub पर एक `OPEN` PR है — बिना एक के, कोई merge target नहीं है enforcement के लिए, तो entire policy short-circuits to allow। एक बार `OPEN` PR confirm हो जाता है, दो independent probes run होते हैं:

1. **Local** — `git merge-tree --write-tree --name-only origin/<baseBranch> HEAD`। Conflict पर, deny message conflicted files को name करता है तो Claude exactly जानता है क्या resolve करना है।
2. **GitHub** — reuses `gh pr view --json mergeable,state` result पहले से ही precheck में fetch किया। Catches conflicts जो stale local `origin/<baseBranch>` miss करते (उदाहरण के लिए कोई `main` पर एक conflicting PR land करता है last fetch के बाद)। एक `CONFLICTING` result deny करता है। एक `UNKNOWN` result भी deny करता है और Claude को instruct करता है ~10 seconds wait करने के लिए और फिर re-check करने से पहले stop करने की कोशिश करने से पहले — यह false negatives को prevent करता है जबकि GitHub recomputes।

Skips entirely (allows) जब: `gh` installed नहीं है, branch के लिए कोई PR exist नहीं करता, PR का state `OPEN` नहीं है (`MERGED`, `CLOSED` जैसे), या `gh pr view` unparseable output return करता है। भी fails open जब `origin/<baseBranch>` locally missing है या जब कोई commits base से ahead नहीं हैं — वे Layer 1 fall-throughs अभी भी cached PR mergeability को consult करते हैं allowing से पहले।

**Parameters:**

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `baseBranch` | `string` | `"main"` | Base branch को conflicts के विरुद्ध check करने के लिए। |

<Note>
इस policy के लिए GitHub CLI (`gh`) required है। Policy `gh pr view` को use करती है confirm करने के लिए एक `OPEN` PR exist करता है कोई भी conflict probe run करने से पहले — `gh` के बिना, policy short-circuits to allow। `gh auth login` को एक personal access token के साथ run करें जिसके पास `repo` scope हो pull requests के लिए read access के लिए।
</Note>
