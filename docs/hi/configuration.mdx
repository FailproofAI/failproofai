failproofai JSON कॉन्फ़िगरेशन फ़ाइलों का उपयोग करता है यह नियंत्रित करने के लिए कि कौन सी नीतियां सक्रिय हैं, वे कैसे व्यवहार करती हैं, और कस्टम नीतियां कहां से लोड की जाती हैं। कॉन्फ़िगरेशन आपकी टीम के साथ साझा करना आसान है - इसे अपने रेपो में कमिट करें और हर डेवलपर को एक जैसी एजेंट सुरक्षा मिलेगी।

---

## कॉन्फ़िगरेशन स्कोप

तीन कॉन्फ़िगरेशन स्कोप हैं, जिनका मूल्यांकन प्राथमिकता क्रम में किया जाता है:

| स्कोप | फ़ाइल पथ | उद्देश्य |
|-------|-----------|---------|
| **project** | `.failproofai/policies-config.json` | प्रति-रेपो सेटिंग्स, संस्करण नियंत्रण में कमिट की गई |
| **local** | `.failproofai/policies-config.local.json` | व्यक्तिगत प्रति-रेपो ओवरराइड, gitignored |
| **global** | `~/.failproofai/policies-config.json` | सभी प्रोजेक्ट में उपयोगकर्ता-स्तरीय डिफ़ॉल्ट |

जब failproofai को एक हुक इवेंट मिलता है, तो यह वर्तमान कार्य निर्देशिका के लिए सभी तीन फ़ाइलों को लोड करता है और मर्ज करता है।

### मर्ज नियम

**`enabledPolicies`** - सभी तीन स्कोप का संघ। किसी भी स्तर पर सक्षम की गई नीति सक्रिय है।

```text
project:  ["block-sudo"]
local:    ["block-rm-rf"]
global:   ["block-sudo", "sanitize-api-keys"]

resolved: ["block-sudo", "block-rm-rf", "sanitize-api-keys"]  ← deduplicated union
```

**`policyParams`** - दी गई नीति के लिए पैरामीटर को परिभाषित करने वाला पहला स्कोप पूरी तरह जीतता है। किसी नीति के पैरामीटर के भीतर मानों का गहरा मर्जिंग नहीं है।

```text
project:  block-sudo → { allowPatterns: ["sudo apt-get update"] }
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo apt-get update"] }   ← project जीतता है, global को अनदेखा किया जाता है
```

```text
project:  (block-sudo प्रविष्टि नहीं)
local:    (block-sudo प्रविष्टि नहीं)
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo systemctl status"] }  ← global में गिरता है
```

**`customPoliciesPaths` / `customPoliciesPath`** - पहला स्कोप जो किसी भी रूप को परिभाषित करता है वह जीतता है।

**`disabledCustomPolicies`** - सभी स्कोप में संघ। डैशबोर्ड यहां एक स्रोत-योग्य ID लिखता है जब आप किसी विस्पष्ट या कन्वेंशन नीति फ़ाइल से किसी व्यक्तिगत नीति को बंद करते हैं। सूचीबद्ध नहीं की गई नीतियां डिफ़ॉल्ट रूप से सक्षम रहती हैं; ID में स्रोत फ़ाइल शामिल है ताकि कई फ़ाइलों में समान-नाम की नीतियों को स्वतंत्र रूप से नियंत्रित किया जा सके।

**`llm`** - पहला स्कोप जो इसे परिभाषित करता है जीतता है।

## कॉन्फ़िग फ़ाइल प्रारूप

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "sanitize-jwt",
    "block-env-files",
    "block-read-outside-cwd"
  ],
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release", "prod"]
    },
    "block-rm-rf": {
      "allowPaths": ["/tmp"]
    },
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company"]
    },
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo API key" }
      ]
    },
    "warn-large-file-write": {
      "thresholdKb": 512
    }
  },
  "customPoliciesPath": "/home/alice/myproject/my-policies.js"
}
```

## फ़ील्ड संदर्भ

### `enabledPolicies`

प्रकार: `string[]`

सक्षम करने के लिए नीति नामों की सूची। नाम बिल्कुल `failproofai policies` द्वारा दिखाई गई नीति पहचानकर्ताओं से मेल खाने चाहिए। सभी सूची के लिए [Built-in Policies](/hi/built-in-policies) देखें।

`enabledPolicies` में न होने वाली नीतियां निष्क्रिय हैं, भले ही उनके पास `policyParams` में प्रविष्टियां हों।

### `policyParams`

प्रकार: `Record<string, Record<string, unknown>>`

प्रति-नीति पैरामीटर ओवरराइड। बाहरी कुंजी नीति का नाम है; आंतरिक कुंजियां नीति-विशिष्ट हैं। प्रत्येक नीति अपने उपलब्ध पैरामीटर को [Built-in Policies](/hi/built-in-policies) में दस्तावेज करती है।

यदि किसी नीति के पैरामीटर हैं लेकिन आप उन्हें निर्दिष्ट नहीं करते हैं, तो नीति के बिल्ट-इन डिफ़ॉल्ट का उपयोग किया जाता है। जो उपयोगकर्ता `policyParams` को बिल्कुल कॉन्फ़िगर नहीं करते हैं उन्हें पिछले संस्करणों के समान व्यवहार मिलता है।

किसी नीति के पैरामीटर ब्लॉक के अंदर अज्ञात कुंजियां हुक-फायर समय पर चुप से अनदेखा की जाती हैं लेकिन जब आप `failproofai policies` चलाते हैं तो चेतावनी के रूप में फ़्लैग की जाती हैं।

#### `hint` (cross-cutting)

प्रकार: `string` (वैकल्पिक)

एक संदेश जो तब जोड़ा जाता है जब कोई नीति `deny` या `instruct` देती है। नीति को संशोधित किए बिना Claude को कार्यशील मार्गदर्शन देने के लिए इसका उपयोग करें।

किसी भी नीति प्रकार के साथ काम करता है - बिल्ट-इन, कस्टम (`custom/`), प्रोजेक्ट कन्वेंशन (`.failproofai-project/`), या उपयोगकर्ता कन्वेंशन (`.failproofai-user/`)।

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "इसके बजाय एक ताज़ी शाखा बनाने की कोशिश करें।"
    },
    "block-sudo": {
      "allowPatterns": ["sudo apt-get"],
      "hint": "sudo के बिना सीधे apt-get का उपयोग करें।"
    },
    "custom/my-policy": {
      "hint": "पहले उपयोगकर्ता से अनुमोदन लें।"
    }
  }
}
```

जब `block-force-push` अस्वीकार करता है, तो Claude देखता है: *"Force-pushing ब्लॉक की गई है। इसके बजाय एक ताज़ी शाखा बनाने की कोशिश करें।"*

गैर-स्ट्रिंग मान और खाली स्ट्रिंग चुप से अनदेखा की जाती हैं। यदि `hint` सेट नहीं है, तो व्यवहार अपरिवर्तित है (पश्चगामी-संगत)।

### `customPoliciesPath`

प्रकार: `string` (निरपेक्ष पथ)

कस्टम हुक नीतियों वाली JavaScript फ़ाइल का पथ। यह `failproofai policies --install --custom <path>` द्वारा स्वचालित रूप से सेट किया जाता है (पथ संग्रहीत होने से पहले निरपेक्ष में हल किया जाता है)।

फ़ाइल हर हुक इवेंट पर नए सिरे से लोड की जाती है - कोई कैशिंग नहीं है। विवरण के लिए [Custom Policies](/hi/custom-policies) देखें।

### कन्वेंशन-आधारित नीतियां

स्पष्ट `customPoliciesPath` के अलावा, failproofai स्वचालित रूप से `.failproofai/policies/` निर्देशिकाओं से नीति फ़ाइलों की खोज करता है और लोड करता है:

| स्तर | निर्देशिका | स्कोप |
|-------|-----------|-------|
| Project | `.failproofai/policies/` | संस्करण नियंत्रण के माध्यम से टीम के साथ साझा किया गया |
| User | `~/.failproofai/policies/custom-policies/` | व्यक्तिगत, सभी परियोजनाओं पर लागू होता है |

<Note>
  उपयोगकर्ता-स्तरीय निर्देशिका होम-निर्देशिका पुनर्गठन में एक स्तर नीचे चली गई।
  `.failproofai/policies/` पर छोड़ी गई पुरानी फ़ाइलें स्वचालित रूप से
  `custom-policies/` में स्थानांतरित कर दी जाती हैं जब आप अपग्रेड करने के बाद
  किसी भी `failproofai` कमांड को चलाते हैं, और कमांड बताता है कि इसे कौन सी फ़ाइलें स्थानांतरित की गई हैं।
</Note>

**फ़ाइल मिलान:** केवल `*policies.{js,mjs,ts}` से मेल खाने वाली फ़ाइलें लोड की जाती हैं (उदा. `security-policies.mjs`, `workflow-policies.js`)। निर्देशिका में अन्य फ़ाइलें अनदेखी की जाती हैं।

**कोई कॉन्फ़िग की आवश्यकता नहीं:** कन्वेंशन नीतियों के लिए `policies-config.json` में प्रविष्टियों की आवश्यकता नहीं है। बस फ़ाइलें निर्देशिका में डालें और वे अगली हुक इवेंट पर लिए जाते हैं।

**संघ लोडिंग:** प्रोजेक्ट और उपयोगकर्ता दोनों कन्वेंशन निर्देशिकाओं को स्कैन किया जाता है। दोनों स्तरों से सभी मेल खाने वाली फ़ाइलें लोड की जाती हैं (जैसे `customPoliciesPath` जो पहले-स्कोप-जीतता है का उपयोग करता है)।

अधिक विवरण और उदाहरणों के लिए [Custom Policies](/hi/custom-policies) देखें।

### `llm`

प्रकार: `object` (वैकल्पिक)

AI कॉल करने वाली नीतियों के लिए LLM क्लाइंट कॉन्फ़िगरेशन। अधिकांश सेटअप के लिए आवश्यक नहीं है।

```json
{
  "llm": {
    "model": "claude-sonnet-4-6",
    "apiKey": "sk-ant-..."
  }
}
```

## CLI से कॉन्फ़िगरेशन प्रबंधन करना

`policies --install` और `policies --uninstall` कमांड आपके एजेंट CLI की हुक सेटिंग्स फ़ाइल (हुक प्रविष्टि बिंदु) में लिखते हैं, जबकि `policies-config.json` वह फ़ाइल है जिसे आप सीधे प्रबंधित करते हैं। ये दोनों अलग हैं:

- **एजेंट CLI सेटिंग्स** — एजेंट को प्रत्येक टूल उपयोग पर `failproofai --hook <event>` को कॉल करने के लिए बताता है:
  - **Claude Code**: `~/.claude/settings.json` (user), `<cwd>/.claude/settings.json` (project), `<cwd>/.claude/settings.local.json` (local)
  - **OpenAI Codex**: `~/.codex/hooks.json` (user), `<cwd>/.codex/hooks.json` (project) — Codex के पास `local` स्कोप नहीं है
  - **GitHub Copilot CLI _(beta)_**: `~/.copilot/hooks/failproofai.json` (user), `<cwd>/.github/hooks/failproofai.json` (project) — Copilot के पास कोई `local` स्कोप नहीं है। हुक प्रविष्टियां Copilot के OS-keyed `bash`/`powershell` कमांड फ़ील्ड का उपयोग करती हैं `timeoutSec` के साथ; फ़ाइल एक शीर्ष-स्तरीय `version: 1` मार्कर ले जाती है। Copilot CLI समर्थन **beta** है जबकि हम `events.jsonl` रिकॉर्ड स्कीमा (जो सार्वजनिक दस्तावेज निर्दिष्ट नहीं करता) को अधिक वास्तविक-विश्व सत्रों के विरुद्ध सत्यापित करते हैं। **VS Code Copilot Chat एजेंट मोड (Preview)** `.github/hooks/*.json`, `~/.copilot/hooks/*.json`, और `~/.claude/settings.json` से हुक कॉन्फ़िग्स पढ़ता है (`chat.hookFilesLocations` सेटिंग द्वारा शासित) समान Claude-आकार `{hookSpecificOutput:{permissionDecision:"deny",…}}` अनुबंध का उपयोग करके — वही सटीक पथ जो यह `copilot` इंटीग्रेशन और `claude` इंटीग्रेशन (`~/.claude/settings.json`) पहले से लिखते हैं, इसलिए `failproofai policies --install --cli copilot` (या `--cli claude`) **पहले से ही VS Code एजेंट मोड में लागू करता है** कोई अलग `vscode` इंटीग्रेशन की आवश्यकता के बिना (VS Code की खोज लॉग से लाइव पुष्टि की गई)।
  - **Cursor Agent _(beta)_**: `~/.cursor/hooks.json` (user), `<cwd>/.cursor/hooks.json` (project) — Cursor के पास कोई `local` स्कोप नहीं है। हुक प्रविष्टियां Claude-आकार `{type, command, timeout}` रूप का उपयोग करती हैं (कोई `bash`/`powershell` विभाजन नहीं), लेकिन Cursor की [hooks schema](https://cursor.com/docs/hooks) के प्रति camelCase इवेंट कुंजियों (`preToolUse`, `beforeSubmitPrompt`, …) के तहत एक फ्लैट ऐरे में संग्रहीत; फ़ाइल एक शीर्ष-स्तरीय `version: 1` मार्कर ले जाती है। हैंडलर camelCase → PascalCase को `CURSOR_EVENT_MAP` के माध्यम से सामान्य करता है ताकि मौजूदा बिल्ट-इन नीतियां अपरिवर्तित रहें। Cursor Agent समर्थन **beta** है जबकि हम Cursor की डिस्क-पर प्रतिलिपि प्रारूप (सार्वजनिक दस्तावेज में निर्दिष्ट नहीं) को अधिक वास्तविक-विश्व इंस्टॉल के विरुद्ध सत्यापित करते हैं।

  - **Goose (codename goose, Block)**: `~/.agents/plugins/failproofai/hooks/hooks.json` (user), `<cwd>/.agents/plugins/failproofai/hooks/hooks.json` (project) — Goose के पास कोई `local` स्कोप नहीं है। प्रवर्तन Goose के **hooks** सिस्टम का उपयोग करता है, cross-agent **Open Plugins** spec: इंस्टॉलर बस `failproofai` plugin dir को drop करता है और Goose startup पर इसे auto-discovers करता है (इसे `~/.config/goose/config.yaml` में self-register करता है)। `hooks.json` एक Open Plugins स्कीमा का उपयोग करता है **with** एक top-level `"hooks"` wrapper, और matcher **omitted** होता है हर इवेंट पर — एक bare `"*"` एक invalid regex है जो कुछ भी match नहीं करता (goose v1.43.0 के विरुद्ध लाइव सत्यापित)। Event names पहले से ही PascalCase हैं (कोई event map नहीं); stdin payload `event`/`working_dir` का उपयोग करता है, जिसे हैंडलर `hook_event_name`/`cwd` में सामान्य करता है। मूल्यांकनकर्ता की `goose` branch exit 0 पर `{"decision":"block","reason"}` JSON के साथ stdout पर अस्वीकार करता है, **`PreToolUse`** इवेंट पर ही सम्मानित (goose ≥ v1.37.0 में भेजा गया) — जो shell tool के लिए **और delegated subagents के अंदर** fires करता है, इसलिए यह एकमात्र पर्याप्त deny point है; किसी अन्य हुक error पर **open** fail होता है। Goose के पास **कोई `Stop` इवेंट नहीं है**, इसलिए `require-*-before-stop` builtins apply नहीं होते हैं (Hermes की तरह)। टूल नामें `GOOSE_TOOL_MAP` (`shell→Bash`, `write→Write`, `todo__todo_write→TodoWrite`, …) के माध्यम से सामान्य किए जाते हैं और path keys `GOOSE_TOOL_INPUT_MAP` (`path`/`source` → `file_path`) के माध्यम से। Goose भी एक offline **audit** स्रोत है — डैशबोर्ड इसकी SQLite सत्रों को `~/.local/share/goose/sessions/sessions.db` पर पढ़ता है (प्रत्येक `sessions` row एक real `working_dir` ले जाता है, इसलिए सत्र परियोजना cwd द्वारा Devin की तरह समूह में; `--no-session` scratch runs filtered होते हैं)।
- **`policies-config.json`** — failproofai को बताता है कि किन नीतियों का मूल्यांकन करना है और किन params के साथ (सभी agent CLIs में साझा)

किसी specific agent को target करने के लिए `--cli claude|codex|copilot|cursor|opencode|pi|hermes|openclaw|factory|devin|antigravity|goose` pass करें (space-separated या किसी subset के लिए repeated):

```bash
failproofai policies --install --cli codex --scope project
failproofai policies --install --cli copilot --scope project
failproofai policies --install --cli cursor --scope project
failproofai policies --install --cli opencode --scope project
failproofai policies --install --cli pi --scope project
failproofai policies --install --cli hermes --scope user
failproofai policies --install --cli openclaw --scope user
failproofai policies --install --cli factory --scope project
failproofai policies --install --cli devin --scope project
failproofai policies --install --cli antigravity --scope project
failproofai policies --install --cli goose --scope project
failproofai policies --install --cli claude codex copilot cursor opencode pi hermes openclaw factory devin antigravity goose
```

जब `--cli` omitted होता है, `failproofai` यह detect करता है कि कौन से agent CLIs installed हैं (`which claude` / `which codex` / `which copilot` / `which cursor-agent` / `which opencode` / `which pi` / `which hermes` / `which openclaw` / `which droid` / `which devin` / `which agy` / `which goose`):

- **एक CLI detected** — बिना prompting के उस CLI को auto-select करता है।
- **Multiple CLIs detected** एक interactive terminal में — arrow-key single-select prompt को एक `Detected (N)` section में grouped दिखाता है (एक `Install for all N detected` aggregate row + हर detected CLI individually के साथ) और एक `Not installed (M) · install hooks ahead of time` section जो हर undetected supported CLI को forward-install option के रूप में list करता है (↑↓ to move, Enter to select, ^C to quit)। uninstall flow केवल Detected section दिखाता है।
- **Multiple CLIs detected** एक non-interactive run में (CI, कोई TTY नहीं) — बिना prompting के सभी detected CLIs के लिए install करता है।
- **None detected** — `claude` को fallback करता है, एक warning के साथ कि PATH में कोई agent binary नहीं मिला; हुक कमांड अभी भी लिखा जाता है इसलिए यह सक्रिय होता है जैसे ही आप एक install करते हैं।

आप किसी भी समय `policies-config.json` को सीधे संपादित कर सकते हैं; changes अगली हुक इवेंट पर तुरंत effect लेते हैं कोई restart की जरूरत के बिना।

## उदाहरण: टीम डिफ़ॉल्ट के साथ project-level कॉन्फ़िग

`.failproofai/policies-config.json` को अपने रेपो में कमिट करें:

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "block-env-files"
  ],
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "release", "hotfix"]
    }
  }
}
```

प्रत्येक डेवलपर तब `.failproofai/policies-config.local.json` (gitignored) बना सकता है व्यक्तिगत ओवरराइड के लिए सहकर्मियों को प्रभावित किए बिना।
