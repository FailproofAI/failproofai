failproofai JSON कॉन्फ़िगरेशन फ़ाइलों का उपयोग करता है ताकि यह नियंत्रित किया जा सके कि कौन से नीतियां सक्रिय हैं, वे कैसे काम करती हैं, और कस्टम नीतियां कहां से लोड होती हैं। कॉन्फ़िगरेशन आपकी टीम के साथ साझा करना आसान बनाने के लिए डिज़ाइन किया गया है - इसे अपने रिपो में कमिट करें और हर डेवलपर को एजेंट सेफ्टी नेट मिल जाएगा।

---

## कॉन्फ़िगरेशन स्कोप

तीन कॉन्फ़िगरेशन स्कोप हैं, जिनका मूल्यांकन प्राथमिकता क्रम में किया जाता है:

| स्कोप | फ़ाइल पथ | उद्देश्य |
|-------|-----------|---------|
| **project** | `.failproofai/policies-config.json` | प्रति-रिपो सेटिंग्स, संस्करण नियंत्रण में कमिट की गई |
| **local** | `.failproofai/policies-config.local.json` | व्यक्तिगत प्रति-रिपो ओवरराइड, gitignored |
| **global** | `~/.failproofai/policies-config.json` | सभी प्रोजेक्ट्स में उपयोगकर्ता-स्तर की डिफ़ॉल्ट सेटिंग्स |

जब failproofai को हुक ईवेंट प्राप्त होता है, तो यह वर्तमान कार्य निर्देशिका के लिए मौजूद सभी तीन फ़ाइलों को लोड और मर्ज करता है।

### मर्ज नियम

**`enabledPolicies`** - सभी तीन स्कोप का यूनियन। किसी भी स्तर पर सक्षम नीति सक्रिय होती है।

```text
project:  ["block-sudo"]
local:    ["block-rm-rf"]
global:   ["block-sudo", "sanitize-api-keys"]

resolved: ["block-sudo", "block-rm-rf", "sanitize-api-keys"]  ← डिडुप्लिकेटेड यूनियन
```

**`policyParams`** - दी गई नीति के लिए पैरामीटर परिभाषित करने वाला पहला स्कोप पूरी तरह जीत जाता है। नीति के पैरामीटर में गहरी मर्जिंग नहीं होती है।

```text
project:  block-sudo → { allowPatterns: ["sudo apt-get update"] }
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo apt-get update"] }   ← project जीतता है, global को अनदेखा किया जाता है
```

```text
project:  (block-sudo प्रविष्टि नहीं)
local:    (block-sudo प्रविष्टि नहीं)
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo systemctl status"] }  ← global तक गिरता है
```

**`customPoliciesPaths` / `customPoliciesPath`** - दोनों में से किसी को परिभाषित करने वाला पहला स्कोप जीत जाता है।

**`disabledCustomPolicies`** - सभी स्कोप में यूनियन। डैशबोर्ड जब आप किसी स्पष्ट या कन्वेंशन नीति फ़ाइल से किसी व्यक्तिगत नीति को बंद करते हैं तो यहां स्रोत-योग्य ID लिखता है। सूची में न होने वाली नीतियां डिफ़ॉल्ट रूप से सक्षम रहती हैं; ID स्रोत फ़ाइल को शामिल करते हैं ताकि कई फ़ाइलों में समान-नाम वाली नीतियों को स्वतंत्र रूप से नियंत्रित किया जा सके।

**`llm`** - पहला स्कोप जो इसे परिभाषित करता है वह जीत जाता है।

## कॉन्फ़िग फ़ाइल प्रारूप

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "sanitize-jwt",
    "block-env-files",
    "block-read-outside-cwd"
  ],
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release", "prod"]
    },
    "block-rm-rf": {
      "allowPaths": ["/tmp"]
    },
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company"]
    },
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo API key" }
      ]
    },
    "warn-large-file-write": {
      "thresholdKb": 512
    }
  },
  "customPoliciesPath": "/home/alice/myproject/my-policies.js"
}
```

## फ़ील्ड संदर्भ

### `enabledPolicies`

प्रकार: `string[]`

सक्षम करने के लिए नीति नामों की सूची। नाम `failproofai policies` द्वारा दिखाई गई नीति पहचानकर्ताओं से बिल्कुल मेल खाना चाहिए। पूरी सूची के लिए [Built-in Policies](/hi/built-in-policies) देखें।

`enabledPolicies` में न होने वाली नीतियां निष्क्रिय होती हैं, भले ही `policyParams` में उनकी प्रविष्टियां हों।

### `policyParams`

प्रकार: `Record<string, Record<string, unknown>>`

प्रति-नीति पैरामीटर ओवरराइड। बाहरी कुंजी नीति का नाम है; आंतरिक कुंजियां नीति-विशिष्ट हैं। प्रत्येक नीति [Built-in Policies](/hi/built-in-policies) में अपने उपलब्ध पैरामीटर का दस्तावेज बनाती है।

यदि नीति के पैरामीटर हैं लेकिन आप उन्हें निर्दिष्ट नहीं करते हैं, तो नीति की बनी-बनाई डिफ़ॉल्ट सेटिंग्स का उपयोग किया जाता है। जो उपयोगकर्ता `policyParams` को बिल्कुल कॉन्फ़िगर नहीं करते हैं वे पिछले संस्करणों के समान आचरण प्राप्त करते हैं।

नीति के पैरामीटर ब्लॉक में अज्ञात कुंजियों को हुक-फ़ायर के समय चुप-चाप नजरअंदाज किया जाता है लेकिन जब आप `failproofai policies` चलाते हैं तो चेतावनियों के रूप में फ़्लैग किया जाता है।

#### `hint` (क्रॉस-कटिंग)

प्रकार: `string` (वैकल्पिक)

एक संदेश जो तब जोड़ा जाता है जब कोई नीति `deny` या `instruct` लौटाती है। नीति को संशोधित किए बिना Claude को कार्यवाही योग्य मार्गदर्शन देने के लिए इसका उपयोग करें।

किसी भी नीति प्रकार के साथ काम करता है - बनी-बनाई, कस्टम (`custom/`), प्रोजेक्ट कन्वेंशन (`.failproofai-project/`), या उपयोगकर्ता कन्वेंशन (`.failproofai-user/`)।

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "इसके बजाय एक ताजी ब्रांच बनाने का प्रयास करें।"
    },
    "block-sudo": {
      "allowPatterns": ["sudo apt-get"],
      "hint": "sudo के बिना सीधे apt-get का उपयोग करें।"
    },
    "custom/my-policy": {
      "hint": "पहले उपयोगकर्ता से अनुमति लें।"
    }
  }
}
```

जब `block-force-push` को अनुमति मिलती है, तो Claude देखता है: *"Force-pushing अवरुद्ध है। इसके बजाय एक ताजी ब्रांच बनाने का प्रयास करें।"*

गैर-स्ट्रिंग मान और खाली स्ट्रिंग्स को चुप-चाप अनदेखा किया जाता है। यदि `hint` सेट नहीं है, तो आचरण अपरिवर्तित रहता है (पिछड़ी संगति)।

### `customPoliciesPath`

प्रकार: `string` (पूर्ण पथ)

कस्टम हुक नीतियां युक्त JavaScript फ़ाइल का पथ। यह `failproofai policies --install --custom <path>` द्वारा स्वचालित रूप से सेट होता है (पथ को संग्रहीत करने से पहले पूर्ण में हल किया जाता है)।

फ़ाइल हर हुक ईवेंट पर ताज़ी लोड की जाती है - कोई कैशिंग नहीं है। विस्तार के लिए [Custom Policies](/hi/custom-policies) देखें।

### कन्वेंशन-आधारित नीतियां

स्पष्ट `customPoliciesPath` के अलावा, failproofai स्वचालित रूप से `.failproofai/policies/` निर्देशिकाओं से नीति फ़ाइलों की खोज और लोड करता है:

| स्तर | निर्देशिका | स्कोप |
|-------|-----------|-------|
| प्रोजेक्ट | `.failproofai/policies/` | संस्करण नियंत्रण के माध्यम से टीम के साथ साझा किया गया |
| उपयोगकर्ता | `~/.failproofai/policies/custom-policies/` | व्यक्तिगत, सभी प्रोजेक्ट्स पर लागू होता है |

<Note>
  उपयोगकर्ता-स्तर की निर्देशिका होम-निर्देशिका पुनर्गठन में नीचे चली गई। `.failproofai/policies/` पर छोड़ी गई पुरानी फ़ाइलें स्वचालित रूप से `custom-policies/` में अपग्रेड के बाद किसी भी `failproofai` कमांड को चलाने पर स्थानांतरित की जाती हैं, और कमांड आपको बताता है कि इसने कौन सी फ़ाइलें स्थानांतरित की हैं।
</Note>

**फ़ाइल मिलान:** केवल `*policies.{js,mjs,ts}` से मिलने वाली फ़ाइलें लोड की जाती हैं (उदा. `security-policies.mjs`, `workflow-policies.js`)। निर्देशिका में अन्य फ़ाइलें अनदेखी की जाती हैं।

**कोई कॉन्फ़िग आवश्यक नहीं:** कन्वेंशन नीतियों के लिए `policies-config.json` में कोई प्रविष्टि आवश्यक नहीं है। बस फ़ाइलों को निर्देशिका में डालें और वे अगली हुक ईवेंट पर उठाई जाती हैं।

**यूनियन लोडिंग:** प्रोजेक्ट और उपयोगकर्ता दोनों कन्वेंशन निर्देशिकाओं को स्कैन किया जाता है। दोनों स्तरों से सभी मेल खाने वाली फ़ाइलें लोड की जाती हैं (`customPoliciesPath` के विपरीत जो पहले-स्कोप-जीत का उपयोग करता है)।

अधिक विवरण और उदाहरणों के लिए [Custom Policies](/hi/custom-policies) देखें।

### `llm`

प्रकार: `object` (वैकल्पिक)

उन नीतियों के लिए LLM क्लाइंट कॉन्फ़िगरेशन जो AI कॉल करती हैं। अधिकांश सेटअप के लिए आवश्यक नहीं।

```json
{
  "llm": {
    "model": "claude-sonnet-4-6",
    "apiKey": "sk-ant-..."
  }
}
```

## CLI से कॉन्फ़िगरेशन प्रबंधित करना

`policies --install` और `policies --uninstall` कमांड आपके एजेंट CLI की हुक सेटिंग्स फ़ाइल (हुक प्रवेश बिंदु) में लिखते हैं, जबकि `policies-config.json` वह फ़ाइल है जिसे आप सीधे प्रबंधित करते हैं। दोनों अलग हैं:

- **एजेंट CLI सेटिंग्स** — एजेंट को प्रत्येक टूल उपयोग पर `failproofai --hook <event>` को कॉल करने के लिए बताता है:
  - **Claude Code**: `~/.claude/settings.json` (उपयोगकर्ता), `<cwd>/.claude/settings.json` (प्रोजेक्ट), `<cwd>/.claude/settings.local.json` (स्थानीय)
  - **OpenAI Codex**: `~/.codex/hooks.json` (उपयोगकर्ता), `<cwd>/.codex/hooks.json` (प्रोजेक्ट) — Codex के पास `local` स्कोप नहीं है
  - **GitHub Copilot CLI _(बीटा)_**: `~/.copilot/hooks/failproofai.json` (उपयोगकर्ता), `<cwd>/.github/hooks/failproofai.json` (प्रोजेक्ट) — Copilot के पास `local` स्कोप नहीं है। हुक प्रविष्टियां Copilot के OS-कुंजीकृत `bash`/`powershell` कमांड फ़ील्ड का उपयोग करती हैं `timeoutSec` के साथ; फ़ाइल एक शीर्ष-स्तर `version: 1` मार्कर रखती है। Copilot CLI समर्थन **बीटा** है जबकि हम `events.jsonl` रिकॉर्ड स्कीमा (जिसे सार्वजनिक दस्तावेज निर्दिष्ट नहीं करते हैं) को अधिक वास्तविक-विश्व सत्रों के विरुद्ध सत्यापित करते हैं। **VS Code Copilot Chat एजेंट मोड (पूर्वावलोकन)** `.github/hooks/*.json`, `~/.copilot/hooks/*.json`, और `~/.claude/settings.json` (जिसे `chat.hookFilesLocations` सेटिंग द्वारा नियंत्रित किया जाता है) से हुक कॉन्फ़िगरेशन पढ़ता है जो Claude-आकार का `{hookSpecificOutput:{permissionDecision:"deny",…}}` अनुबंध का उपयोग करते हैं — यह `copilot` इंटीग्रेशन और `claude` इंटीग्रेशन (`~/.claude/settings.json`) पहले से ही लिखते हैं, तो `failproofai policies --install --cli copilot` (या `--cli claude`) **पहले से ही VS Code एजेंट मोड में लागू होता है** कोई अलग `vscode` इंटीग्रेशन की आवश्यकता के बिना (VS Code की डिस्कवरी लॉग से लाइव पुष्टि की गई)।
  - **Cursor Agent _(बीटा)_**: `~/.cursor/hooks.json` (उपयोगकर्ता), `<cwd>/.cursor/hooks.json` (प्रोजेक्ट) — Cursor के पास `local` स्कोप नहीं है। हुक प्रविष्टियां Claude-आकार का `{type, command, timeout}` फॉर्म का उपयोग करती हैं (कोई `bash`/`powershell` विभाजन नहीं), लेकिन Cursor की [hooks स्कीमा](https://cursor.com/docs/hooks) के अनुसार एक फ्लैट सरणी में camelCase इवेंट कुंजियों (`preToolUse`, `beforeSubmitPrompt`, …) के तहत संग्रहीत हैं; फ़ाइल एक शीर्ष-स्तर `version: 1` मार्कर रखती है। हैंडलर `CURSOR_EVENT_MAP` के माध्यम से camelCase → PascalCase को सामान्य बनाता है ताकि मौजूदा बनी-बनाई नीतियां अपरिवर्तित फ़ायर करें। Cursor Agent समर्थन **बीटा** है जबकि हम Cursor के डिस्क पर ट्रांसक्रिप्ट प्रारूप (सार्वजनिक दस्तावेज में निर्दिष्ट नहीं) को अधिक वास्तविक-विश्व इंस्टॉल के विरुद्ध सत्यापित करते हैं।

  - **Factory Droid (`droid`)**: `~/.factory/hooks.json` (उपयोगकर्ता), `<cwd>/.factory/hooks.json` (प्रोजेक्ट) — Factory के पास `local` स्कोप नहीं है। droid एक Claude-शैली बाहरी-कमांड हुक सिस्टम भेज, लेकिन droid v0.171.0 के विरुद्ध लाइव सत्यापित दो quirks के साथ: (1) ईवेंट नाम `hooks.json` के **शीर्ष स्तर** पर रहते हैं — कोई **`"hooks"` wrapper नहीं है** (droid एक को अस्वीकार करता है); टूल ईवेंट्स (`PreToolUse`/`PostToolUse`) `"matcher": "*"` ले जाते हैं, गैर-टूल ईवेंट्स इसे छोड़ देते हैं। (2) Deny को हुक **exit code 2 + stderr** द्वारा संचालित किया जाता है, JSON निर्णय नहीं — मूल्यांकनकर्ता की `factory` branch टूल/prompt ईवेंट्स के लिए exit 2 लौटाता है और turn-end `Stop` ईवेंट पर केवल `{decision:"block", reason}` (droid की एकमात्र बल-पुनः प्रयास चैनल)। ईवेंट्स पहले से PascalCase हैं (कोई ईवेंट नक्शा नहीं) और payload Claude snake_case है; केवल टूल नामों को `FACTORY_TOOL_MAP` के माध्यम से सामान्य बनाया जाता है (`Execute→Bash`, `Create→Write`, `FetchUrl→WebFetch`, …)। Factory **भी** एक ऑफलाइन **ऑडिट** स्रोत है — डैशबोर्ड `~/.factory/sessions/<encoded-cwd>/<sessionId>.jsonl` पर इसके on-disk JSONL सत्रों को पढ़ता है।
  - **Devin CLI (`devin`, Cognition)**: `~/.config/devin/config.json` (उपयोगकर्ता), `<cwd>/.devin/config.json` (प्रोजेक्ट) — Devin के पास `local` स्कोप नहीं है। Devin एक **pure Claude-क्लोन** है devin v3000.1.27 के विरुद्ध लाइव सत्यापित: यह standard Claude `"hooks"`-wrapper स्कीमा का उपयोग करता है (लिखता merge-preserving है तो कॉन्फ़िग फ़ाइल की अन्य कुंजियां — `org_id`, `theme_mode`, … — जीवित रहती हैं), पहले से PascalCase ईवेंट नाम (कोई ईवेंट नक्शा नहीं, कोई हैंडलर branch नहीं), और Claude snake_case stdin payload (कोई normalization नहीं)। मूल्यांकनकर्ता की `devin` branch **हर** ईवेंट के लिए exit 0 पर `{"decision":"block","reason"}` JSON के साथ deny करता है (सत्यापित — ब्लॉक ने `--permission-mode dangerous` को ओवरराइड किया); turn-end `Stop` ईवेंट पर कारण `require-*-before-stop` बिल्ट-इन लागू करने के लिए MANDATORY-ACTION बल-पुनः प्रयास शब्दार्थ रखता है। केवल टूल नामों को `DEVIN_TOOL_MAP` के माध्यम से सामान्य बनाया जाता है (`exec→Bash`; `tool_input.command` पहले से ही canonical है)। Devin **भी** एक ऑफलाइन **ऑडिट** स्रोत है — डैशबोर्ड `~/.local/share/devin/cli/sessions.db` पर इसके SQLite सत्रों को पढ़ता है (प्रत्येक `sessions` row एक real `working_directory` रखता है, तो सत्र Claude की तरह project cwd द्वारा समूहित होते हैं)।
  - **Antigravity CLI (`agy`)**: `~/.gemini/config/hooks.json` (उपयोगकर्ता), `<cwd>/.agents/hooks.json` (प्रोजेक्ट) — Antigravity के पास `local` स्कोप नहीं है। Factory/Devin के विपरीत, Antigravity के पास अपना **खुद का** अनुबंध है (कोई Claude-क्लोन नहीं), agy v1.1.2 के विरुद्ध लाइव सत्यापित। `hooks.json` एक **named-hook** स्कीमा का उपयोग करता है: शीर्ष-स्तर कुंजी एक हुक *नाम* (`"failproofai"`) है जिसका मान एक ईवेंट→handlers नक्शा है — टूल ईवेंट्स (`PreToolUse`/`PostToolUse`) handlers को `{matcher:"*", hooks:[…]}` में wrap करते हैं, जबकि `PreInvocation`/`Stop` **फ्लैट** handler सरणियां हैं (अन्य named हुक संरक्षित हैं)। stdin payload **camelCase protojson** है (`toolCall:{name,args}`, `conversationId`, `workspacePaths`, `transcriptPath`) — failproofai नीतियां चलाने से पहले इसे snake_case में सामान्य बनाता है, और `run_command` के PascalCase args को `ANTIGRAVITY_TOOL_INPUT_MAP` के माध्यम से मैप करता है। मूल्यांकनकर्ता की `antigravity` branch Antigravity के **खुद के** प्रतिक्रिया आकार का उपयोग करता है: `{decision:"deny", reason}` एक टूल/prompt को ब्लॉक करता है (exit 0), `{decision:"continue", reason}` turn-end `Stop` ईवेंट पर लूप को फिर से दर्ज करता है (तो `require-*-before-stop` बिल्ट-इन लागू होते हैं), और `{injectSteps:[{ephemeralMessage}]}` `PreInvocation` पर एक निर्देश को inject करता है (→ `UserPromptSubmit`)। टूल नामों को `ANTIGRAVITY_TOOL_MAP` के माध्यम से सामान्य बनाया जाता है (`run_command→Bash`, `view_file→Read`, …)। Antigravity **भी** एक ऑफलाइन **ऑडिट** स्रोत है — डैशबोर्ड `~/.gemini/antigravity-cli/brain/<conversationId>/.system_generated/logs/transcript_full.jsonl` पर इसके plain-JSONL ट्रांसक्रिप्ट को पढ़ता है (conversation index `conversation_summaries.db` में)।
  - **Goose (कोडनाम goose, Block)**: `~/.agents/plugins/failproofai/hooks/hooks.json` (उपयोगकर्ता), `<cwd>/.agents/plugins/failproofai/hooks/hooks.json` (प्रोजेक्ट) — Goose के पास `local` स्कोप नहीं है। Enforcement Goose के **हुक** सिस्टम का उपयोग करता है, cross-agent **Open Plugins** spec: installer बस `failproofai` प्लगइन dir को डालता है और Goose startup पर स्वचालित-आविष्कार करता है (स्व-पंजीकृत `~/.config/goose/config.yaml` में)। `hooks.json` एक Open Plugins स्कीमा का उपयोग करता है **शीर्ष-स्तर `"hooks"` wrapper के साथ**, और matcher **हर ईवेंट पर omitted है** — एक bare `"*"` एक अमान्य regex है जो कुछ भी मेल नहीं खाता (goose v1.43.0 के विरुद्ध लाइव सत्यापित)। ईवेंट नाम पहले से PascalCase हैं (कोई ईवेंट नक्शा नहीं); stdin payload `event`/`working_dir` का उपयोग करता है, जिसे हैंडलर `hook_event_name`/`cwd` में सामान्य बनाता है। मूल्यांकनकर्ता की `goose` branch exit 0 पर `{"decision":"block","reason"}` JSON के साथ deny करता है, honored **`PreToolUse`** ईवेंट पर केवल (goose ≥ v1.37.0 में shipped) — जो shell टूल के लिए फ़ायर करता है **और delegated subagents के अंदर**, तो यह एक single sufficient deny बिंदु है; कोई अन्य हुक error **खुला** विफल होता है। Goose के पास **कोई `Stop` ईवेंट नहीं है**, तो `require-*-before-stop` बिल्ट-इन लागू नहीं होते हैं (Hermes की तरह)। टूल नामों को `GOOSE_TOOL_MAP` के माध्यम से सामान्य बनाया जाता है (`shell→Bash`, `write→Write`, `todo__todo_write→TodoWrite`, …) और path कुंजियों को `GOOSE_TOOL_INPUT_MAP` के माध्यम से (`path`/`source` → `file_path`)। Goose **भी** एक ऑफलाइन **ऑडिट** स्रोत है — डैशबोर्ड `~/.local/share/goose/sessions/sessions.db` पर इसके SQLite सत्रों को पढ़ता है (प्रत्येक `sessions` row एक real `working_dir` रखता है, तो सत्र Devin की तरह project cwd द्वारा समूहित होते हैं; `--no-session` scratch runs को फ़िल्टर किया जाता है)।
- **`policies-config.json`** — failproofai को बताता है कि कौन सी नीतियों का मूल्यांकन करना है और किन params के साथ (सभी एजेंट CLIs में साझा)

एक विशिष्ट एजेंट को लक्षित करने के लिए `--cli claude|codex|copilot|cursor|opencode|pi|hermes|openclaw|factory|devin|antigravity|goose` पास करें (space-separated या किसी भी subset के लिए repeated):

```bash
failproofai policies --install --cli codex --scope project
failproofai policies --install --cli copilot --scope project
failproofai policies --install --cli cursor --scope project
failproofai policies --install --cli opencode --scope project
failproofai policies --install --cli pi --scope project
failproofai policies --install --cli hermes --scope user
failproofai policies --install --cli openclaw --scope user
failproofai policies --install --cli factory --scope project
failproofai policies --install --cli devin --scope project
failproofai policies --install --cli antigravity --scope project
failproofai policies --install --cli goose --scope project
failproofai policies --install --cli claude codex copilot cursor opencode pi hermes openclaw factory devin antigravity goose
```

जब `--cli` को छोड़ा जाता है, `failproofai` यह पता लगाता है कि कौन से एजेंट CLIs इंस्टॉल हैं (`which claude` / `which codex` / `which copilot` / `which cursor-agent` / `which opencode` / `which pi` / `which hermes` / `which openclaw` / `which droid` / `which devin` / `which agy` / `which goose`):

- **एक CLI detected** — प्रॉम्प्ट के बिना स्वचालित रूप से उस CLI को चुनता है।
- **Multiple CLIs detected** एक interactive टर्मिनल में — एक arrow-key single-select प्रॉम्प्ट दिखाता है `Detected (N)` सेक्शन में समूहीकृत (एक `Install for all N detected` aggregate row + प्रत्येक detected CLI individually के साथ) और एक `Not installed (M) · install hooks ahead of time` सेक्शन हर undetected supported CLI को एक forward-install विकल्प के रूप में सूचीबद्ध करता है (↑↓ चलने के लिए, Enter चुनने के लिए, ^C बाहर निकलने के लिए)। uninstall प्रवाह केवल Detected सेक्शन दिखाता है।
- **Multiple CLIs detected** एक non-interactive चलाने में (CI, कोई TTY नहीं) — सभी detected CLIs के लिए प्रॉम्प्ट के बिना install करता है।
- **None detected** — `claude` पर वापस जाता है, एक चेतावनी के साथ कि कोई एजेंट बाइनरी PATH में नहीं मिला; हुक कमांड अभी भी लिखा जाता है तो यह सक्रिय हो जाता है जैसे ही आप एक install करते हैं।

आप किसी भी समय `policies-config.json` को सीधे संपादित कर सकते हैं; परिवर्तन अगली हुक ईवेंट पर तुरंत प्रभाव लेते हैं कोई restart की आवश्यकता के बिना।

अपने रिपो में `.failproofai/policies-config.json` को commit करें:

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "block-env-files"
  ],
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "release", "hotfix"]
    }
  }
}
```

प्रत्येक डेवलपर तब `.failproofai/policies-config.local.json` (gitignored) बना सकता है व्यक्तिगत ओवरराइड के लिए टीममेट्स को प्रभावित किए बिना।
