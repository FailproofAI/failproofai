failproofai कौन सी नीतियां सक्रिय हैं, वे कैसे काम करती हैं, और कहां से कस्टम नीतियां लोड की जाती हैं, यह नियंत्रित करने के लिए JSON कॉन्फ़िगरेशन फ़ाइलों का उपयोग करता है। कॉन्फ़िगरेशन को आपकी टीम के साथ साझा करना आसान बनाया गया है - इसे अपने रिपो में कमिट करें और प्रत्येक डेवलपर को समान एजेंट सुरक्षा नेट मिल जाएगा।

---

## कॉन्फ़िगरेशन स्कोप

तीन कॉन्फ़िगरेशन स्कोप हैं, जिनका मूल्यांकन प्राथमिकता क्रम में किया जाता है:

| स्कोप | फ़ाइल पाथ | उद्देश्य |
|-------|-----------|---------|
| **project** | `.failproofai/policies-config.json` | प्रति-रिपो सेटिंग्स, संस्करण नियंत्रण में प्रतिबद्ध |
| **local** | `.failproofai/policies-config.local.json` | व्यक्तिगत प्रति-रिपो ओवरराइड, gitignored |
| **global** | `~/.failproofai/policies-config.json` | उपयोगकर्ता-स्तरीय डिफ़ॉल्ट सभी प्रोजेक्ट्स में |

जब failproofai को हुक इवेंट प्राप्त होता है, तो यह वर्तमान कार्य निर्देशिका के लिए मौजूद सभी तीन फ़ाइलों को लोड और मर्ज करता है।

### मर्ज नियम

**`enabledPolicies`** - सभी तीन स्कोप का संघ। किसी भी स्तर पर सक्षम की गई नीति सक्रिय है।

```text
project:  ["block-sudo"]
local:    ["block-rm-rf"]
global:   ["block-sudo", "sanitize-api-keys"]

resolved: ["block-sudo", "block-rm-rf", "sanitize-api-keys"]  ← विषमुक्त संघ
```

**`policyParams`** - पहला स्कोप जो किसी दी गई नीति के लिए पैरामीटर परिभाषित करता है पूरी तरह जीत जाता है। किसी नीति के पैरामीटर में मानों का कोई गहरा मर्जिंग नहीं है।

```text
project:  block-sudo → { allowPatterns: ["sudo apt-get update"] }
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo apt-get update"] }   ← project जीत जाता है, global को नज़रअंदाज़ किया जाता है
```

```text
project:  (कोई block-sudo प्रविष्टि नहीं)
local:    (कोई block-sudo प्रविष्टि नहीं)
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo systemctl status"] }  ← global तक गिर जाता है
```

**`customPoliciesPaths` / `customPoliciesPath`** - पहला स्कोप जो किसी रूप को परिभाषित करता है जीत जाता है।

**`disabledCustomPolicies`** - सभी स्कोप में संघ। डैशबोर्ड जब आप किसी व्यक्तिगत नीति को स्पष्ट या सम्मेलन नीति फ़ाइल से बंद करते हैं तो स्रोत-योग्य ID यहां लिखता है। सूचीबद्ध नहीं की गई नीतियां डिफ़ॉल्ट रूप से सक्षम रहती हैं; ID में स्रोत फ़ाइल शामिल है इसलिए कई फ़ाइलों में समान-नाम की नीतियों को स्वतंत्र रूप से नियंत्रित किया जा सकता है।

**`llm`** - पहला स्कोप जो इसे परिभाषित करता है जीत जाता है।

## कॉन्फ़िग फ़ाइल प्रारूप

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "sanitize-jwt",
    "block-env-files",
    "block-read-outside-cwd"
  ],
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release", "prod"]
    },
    "block-rm-rf": {
      "allowPaths": ["/tmp"]
    },
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company"]
    },
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo API key" }
      ]
    },
    "warn-large-file-write": {
      "thresholdKb": 512
    }
  },
  "customPoliciesPath": "/home/alice/myproject/my-policies.js"
}
```

## फ़ील्ड संदर्भ

### `enabledPolicies`

प्रकार: `string[]`

सक्षम करने के लिए नीति नामों की सूची। नामों को बिल्कुल `failproofai policies` द्वारा दिखाए गए नीति पहचानकर्ताओं से मेल खाना चाहिए। संपूर्ण सूची के लिए [Built-in Policies](/hi/built-in-policies) देखें।

`enabledPolicies` में नहीं हैं ऐसी नीतियां निष्क्रिय हैं, भले ही `policyParams` में उनकी प्रविष्टियां हों।

### `policyParams`

प्रकार: `Record<string, Record<string, unknown>>`

प्रति-नीति पैरामीटर ओवरराइड। बाहरी कुंजी नीति का नाम है; आंतरिक कुंजियां नीति-विशिष्ट हैं। प्रत्येक नीति अपने उपलब्ध पैरामीटर को [Built-in Policies](/hi/built-in-policies) में दस्तावेज़ित करती है।

यदि किसी नीति के पैरामीटर हैं लेकिन आप उन्हें निर्दिष्ट नहीं करते, तो नीति के अंतर्निहित डिफ़ॉल्ट का उपयोग किया जाता है। जो उपयोगकर्ता `policyParams` को बिल्कुल भी कॉन्फ़िगर नहीं करते वे पिछले संस्करणों के समान व्यवहार प्राप्त करते हैं।

किसी नीति के पैरामीटर ब्लॉक के अंदर अज्ञात कुंजियों को हुक-फायर के समय चुप्पी से अनदेखा किया जाता है लेकिन जब आप `failproofai policies` चलाते हैं तो चेतावनियों के रूप में फ़्लैग किया जाता है।

#### `hint` (क्रॉस-कटिंग)

प्रकार: `string` (वैकल्पिक)

एक संदेश जो तब जोड़ा जाता है जब कोई नीति `deny` या `instruct` लौटाती है। इसका उपयोग Claude को नीति को संशोधित किए बिना कार्रवाई योग्य मार्गदर्शन देने के लिए करें।

किसी भी नीति प्रकार के साथ काम करता है — अंतर्निहित, कस्टम (`custom/`), प्रोजेक्ट सम्मेलन (`.failproofai-project/`), या उपयोगकर्ता सम्मेलन (`.failproofai-user/`)।

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "इसके बजाय एक नई शाखा बनाने का प्रयास करें।"
    },
    "block-sudo": {
      "allowPatterns": ["sudo apt-get"],
      "hint": "sudo के बिना सीधे apt-get का उपयोग करें।"
    },
    "custom/my-policy": {
      "hint": "अनुमति के लिए पहले उपयोगकर्ता से पूछें।"
    }
  }
}
```

जब `block-force-push` अस्वीकार करता है, तो Claude देखता है: *"Force-pushing ब्लॉक किया गया है। इसके बजाय एक नई शाखा बनाने का प्रयास करें।"*

गैर-स्ट्रिंग मानों और खाली स्ट्रिंग्स को चुप्पी से अनदेखा किया जाता है। यदि `hint` सेट नहीं है, तो व्यवहार अपरिवर्तित है (पिछड़ी-संगत)।

### `customPoliciesPath`

प्रकार: `string` (निरपेक्ष पाथ)

कस्टम हुक नीतियां युक्त JavaScript फ़ाइल का पाथ। यह `failproofai policies --install --custom <path>` द्वारा स्वचालित रूप से सेट किया जाता है (पाथ संग्रहीत होने से पहले निरपेक्ष रूप से हल किया जाता है)।

फ़ाइल हर हुक इवेंट पर ताज़ा लोड की जाती है - कोई कैशिंग नहीं है। विस्तार के लिए [Custom Policies](/hi/custom-policies) देखें।

### सम्मेलन-आधारित नीतियां

स्पष्ट `customPoliciesPath` के अलावा, failproofai स्वचालित रूप से `.failproofai/policies/` निर्देशिकाओं से नीति फ़ाइलों को खोजता है और लोड करता है:

| स्तर | निर्देशिका | स्कोप |
|-------|-----------|-------|
| Project | `.failproofai/policies/` | संस्करण नियंत्रण के माध्यम से टीम के साथ साझा |
| User | `~/.failproofai/policies/` | व्यक्तिगत, सभी प्रोजेक्ट्स पर लागू |

<Note>
  अपनी नीतियों को सीधे `~/.failproofai/policies/` में ड्रॉप करें। `cloud-policies/` फ़ोल्डर उनके बगल में वह नीतियां रखता है जो आपके संगठन ने इस मशीन पर तैनात की हैं — खोज में उप-निर्देशिकाओं में प्रवेश नहीं करता है, इसलिए इसे कभी स्कैन नहीं किया जाता है, और `policies/` में आप जो कुछ भी डालते हैं वह इसके साथ टकरा नहीं सकता।

  यदि आप उस संस्करण से अपग्रेड कर रहे हैं जो `~/.failproofai/policies/custom-policies/` का उपयोग करता था, तो उस फ़ोल्डर में सब कुछ — आपकी नीति फ़ाइलें, कोई `lib/` जो वे आयात करते हैं, और कोई डेटा फ़ाइलें जो वे पढ़ते हैं — स्वचालित रूप से वापस ऊपर चली जाती हैं पहली बार जब आप `failproofai` कमांड चलाते हैं, और कमांड आपको बताता है कि इसने क्या स्थानांतरित किया।
</Note>

**फ़ाइल मिलान:** केवल `*policies.{js,mjs,ts}` से मेल खाने वाली फ़ाइलें लोड की जाती हैं (जैसे `security-policies.mjs`, `workflow-policies.js`)। निर्देशिका में अन्य फ़ाइलों को अनदेखा किया जाता है।

**कोई कॉन्फ़िग की आवश्यकता नहीं:** सम्मेलन नीतियों को `policies-config.json` में कोई प्रविष्टि की आवश्यकता नहीं है। बस फ़ाइलों को निर्देशिका में ड्रॉप करें और अगले हुक इवेंट पर उन्हें उठाया जाता है।

**यूनियन लोडिंग:** प्रोजेक्ट और उपयोगकर्ता दोनों सम्मेलन निर्देशिकाओं को स्कैन किया जाता है। दोनों स्तरों से सभी मिलान वाली फ़ाइलें लोड की जाती हैं (`customPoliciesPath` के विपरीत जो पहले-स्कोप-जीत का उपयोग करता है)।

अधिक विवरण और उदाहरणों के लिए [Custom Policies](/hi/custom-policies) देखें।

### `llm`

प्रकार: `object` (वैकल्पिक)

उन नीतियों के लिए LLM क्लाइंट कॉन्फ़िगरेशन जो AI कॉल करती हैं। अधिकांश सेटअप के लिए आवश्यक नहीं है।

```json
{
  "llm": {
    "model": "claude-sonnet-4-6",
    "apiKey": "sk-ant-..."
  }
}
```

## CLI से कॉन्फ़िगरेशन प्रबंधित करना

`policies --install` और `policies --uninstall` कमांड आपके एजेंट CLI की हुक सेटिंग्स फ़ाइल (हुक एंट्री पॉइंट) में लिखते हैं, जबकि `policies-config.json` वह फ़ाइल है जिसे आप सीधे प्रबंधित करते हैं। ये दोनों अलग हैं:

- **एजेंट CLI सेटिंग्स** — एजेंट को प्रत्येक टूल उपयोग पर `failproofai --hook <event>` कॉल करने के लिए बताता है:
  - **Claude Code**: `~/.claude/settings.json` (उपयोगकर्ता), `<cwd>/.claude/settings.json` (प्रोजेक्ट), `<cwd>/.claude/settings.local.json` (स्थानीय)
  - **OpenAI Codex**: `~/.codex/hooks.json` (उपयोगकर्ता), `<cwd>/.codex/hooks.json` (प्रोजेक्ट) — Codex के पास `local` स्कोप नहीं है
  - **GitHub Copilot CLI _(beta)_**: `~/.copilot/hooks/failproofai.json` (उपयोगकर्ता), `<cwd>/.github/hooks/failproofai.json` (प्रोजेक्ट) — Copilot के पास `local` स्कोप नहीं है। हुक प्रविष्टियां Copilot के OS-कुंजीयुक्त `bash`/`powershell` कमांड फ़ील्ड का उपयोग करती हैं `timeoutSec` के साथ; फ़ाइल एक शीर्ष-स्तरीय `version: 1` मार्कर रखती है। Copilot CLI समर्थन **beta** है जबकि हम `events.jsonl` रिकॉर्ड स्कीमा को सत्यापित करते हैं (जो सार्वजनिक दस्तावेज़ निर्दिष्ट नहीं करते) अधिक वास्तविक दुनिया सत्रों के विरुद्ध। **VS Code Copilot Chat एजेंट मोड (Preview)** हुक कॉन्फ़िग को `.github/hooks/*.json`, `~/.copilot/hooks/*.json`, और `~/.claude/settings.json` से पढ़ता है (`chat.hookFilesLocations` सेटिंग द्वारा शासित) एक ही Claude-आकार `{hookSpecificOutput:{permissionDecision:"deny",…}}` अनुबंध का उपयोग करके — बिल्कुल वह पाथ जो यह `copilot` एकीकरण और `claude` एकीकरण (`~/.claude/settings.json`) पहले से लिखते हैं, इसलिए `failproofai policies --install --cli copilot` (या `--cli claude`) **पहले से VS Code एजेंट मोड में लागू करते हैं** कोई अलग `vscode` एकीकरण की आवश्यकता नहीं है (VS Code की खोज लॉग से पुष्टि की गई)।
  - **Cursor Agent _(beta)_**: `~/.cursor/hooks.json` (उपयोगकर्ता), `<cwd>/.cursor/hooks.json` (प्रोजेक्ट) — Cursor के पास `local` स्कोप नहीं है। हुक प्रविष्टियां Claude-आकार `{type, command, timeout}` रूप का उपयोग करती हैं (कोई `bash`/`powershell` विभाजन नहीं), लेकिन camelCase इवेंट कुंजियों के तहत संग्रहीत हैं (`preToolUse`, `beforeSubmitPrompt`, …) Cursor के [hooks schema](https://cursor.com/docs/hooks) के अनुसार एक सपाट सरणी में; फ़ाइल एक शीर्ष-स्तरीय `version: 1` मार्कर रखती है। हैंडलर camelCase → PascalCase को `CURSOR_EVENT_MAP` के माध्यम से सामान्य करता है इसलिए मौजूदा अंतर्निहित नीतियां अपरिवर्तित रहती हैं। Cursor Agent समर्थन **beta** है जबकि हम Cursor की डिस्क-पर प्रतिलिपि प्रारूप को सत्यापित करते हैं (सार्वजनिक दस्तावेज़ में निर्दिष्ट नहीं) अधिक वास्तविक दुनिया इंस्टॉलों के विरुद्ध।

  - **Antigravity CLI (`agy`)**: `~/.gemini/config/hooks.json` (उपयोगकर्ता), `<cwd>/.agents/hooks.json` (प्रोजेक्ट) — Antigravity के पास `local` स्कोप नहीं है। Factory/Devin के विपरीत, Antigravity के पास अपना **own** अनुबंध है (एक Claude-clone नहीं), agy v1.1.2 के विरुद्ध live सत्यापित। `hooks.json` एक **named-hook** स्कीमा का उपयोग करता है: शीर्ष-स्तरीय कुंजी एक हुक *name* है (`"failproofai"`) जिसका मान एक इवेंट→handlers मैप है — टूल इवेंट्स (`PreToolUse`/`PostToolUse`) handlers को `{matcher:"*", hooks:[…]}` में लपेटते हैं, जबकि `PreInvocation`/`Stop` **flat** handler सरणियां हैं (अन्य named hooks preserved हैं)। stdin पेलोड **camelCase protojson** है (`toolCall:{name,args}`, `conversationId`, `workspacePaths`, `transcriptPath`) — failproofai इसे snake_case के लिए सामान्य करता है policies चलाने से पहले, और `run_command` के PascalCase args (`CommandLine`/`Cwd`) को `ANTIGRAVITY_TOOL_INPUT_MAP` के माध्यम से मैप करता है। मूल्यांकनकर्ता की `antigravity` शाखा Antigravity के **own** प्रतिक्रिया आकार का उपयोग करती है: `{decision:"deny", reason}` एक टूल/प्रॉम्प्ट को अवरुद्ध करता है (निकास 0), `{decision:"continue", reason}` turn-end `Stop` पर लूप को फिर से दर्ज करता है (इसलिए `require-*-before-stop` अंतर्निहित enforce करते हैं), और `{injectSteps:[{ephemeralMessage}]}` एक `PreInvocation` पर निर्देश को inject करता है (→ `UserPromptSubmit`)। टूल नामों को `ANTIGRAVITY_TOOL_MAP` के माध्यम से canonicalize करते हैं (`run_command→Bash`, `view_file→Read`, …)। Antigravity **यह भी** एक ऑफ़लाइन **audit** स्रोत है — डैशबोर्ड `~/.gemini/antigravity-cli/brain/<conversationId>/.system_generated/logs/transcript_full.jsonl` पर इसकी plain-JSONL transcripts को पढ़ता है (conversation index `conversation_summaries.db` में)।
  - **Goose (codename goose, Block)**: `~/.agents/plugins/failproofai/hooks/hooks.json` (उपयोगकर्ता), `<cwd>/.agents/plugins/failproofai/hooks/hooks.json` (प्रोजेक्ट) — Goose के पास `local` स्कोप नहीं है। कार्यान्वयन Goose के **hooks** सिस्टम का उपयोग करता है, cross-agent **Open Plugins** spec: installer बस `failproofai` plugin dir को ड्रॉप करता है और Goose स्टार्टअप पर इसे auto-discover करता है (इसे `~/.config/goose/config.yaml` में self-registering)। `hooks.json` एक Open Plugins स्कीमा का उपयोग करता है **with** एक शीर्ष-स्तरीय `"hooks"` wrapper, और matcher **omitted** है हर इवेंट पर — एक bare `"*"` एक invalid regex है जो कुछ भी मेल नहीं खाता (goose v1.43.0 के विरुद्ध live सत्यापित)। इवेंट नामों पहले से ही PascalCase हैं (कोई इवेंट मैप नहीं); stdin पेलोड `event`/`working_dir` का उपयोग करता है, जिसे हैंडलर `hook_event_name`/`cwd` के लिए सामान्य करता है। मूल्यांकनकर्ता की `goose` शाखा `{"decision":"block","reason"}` JSON stdout पर निकास 0 पर अस्वीकार करती है, **`PreToolUse`** इवेंट पर सम्मानित (goose ≥ v1.37.0 में भेज दिया गया) — जो shell टूल के लिए **और delegated subagents के अंदर** फायर होता है, इसलिए यह एकमात्र sufficient deny point है; किसी भी अन्य हुक त्रुटि **open** विफल हो जाता है। Goose के पास **कोई `Stop` इवेंट नहीं है**, इसलिए `require-*-before-stop` अंतर्निहित लागू नहीं होते (Hermes की तरह)। टूल नामों को `GOOSE_TOOL_MAP` के माध्यम से सामान्य किया जाता है (`shell→Bash`, `write→Write`, `todo__todo_write→TodoWrite`, …) और पाथ कुंजियों को `GOOSE_TOOL_INPUT_MAP` के माध्यम से (`path`/`source` → `file_path`)। Goose **यह भी** एक ऑफ़लाइन **audit** स्रोत है — डैशबोर्ड `~/.local/share/goose/sessions/sessions.db` पर इसकी SQLite सत्रों को पढ़ता है (प्रत्येक `sessions` row एक real `working_dir` ले जाता है, इसलिए सत्र Devin की तरह project cwd द्वारा group करते हैं; `--no-session` scratch runs filtered हैं)।
- **`policies-config.json`** — failproofai को बताता है कि कौन सी नीतियां evaluate करें और किन पैरामीटर के साथ (सभी एजेंट CLI में साझा)

एक विशिष्ट एजेंट को लक्ष्य करने के लिए `--cli claude|codex|copilot|cursor|opencode|pi|hermes|openclaw|factory|devin|antigravity|goose` पास करें (space-separated या किसी भी subset के लिए दोहराया गया):

```bash
failproofai policies --install --cli codex --scope project
failproofai policies --install --cli copilot --scope project
failproofai policies --install --cli cursor --scope project
failproofai policies --install --cli opencode --scope project
failproofai policies --install --cli pi --scope project
failproofai policies --install --cli hermes --scope user
failproofai policies --install --cli openclaw --scope user
failproofai policies --install --cli factory --scope project
failproofai policies --install --cli devin --scope project
failproofai policies --install --cli antigravity --scope project
failproofai policies --install --cli goose --scope project
failproofai policies --install --cli claude codex copilot cursor opencode pi hermes openclaw factory devin antigravity goose
```

जब `--cli` को छोड़ा जाता है, तो `failproofai` यह पहचानता है कि कौन से एजेंट CLI इंस्टॉल हैं (`which claude` / `which codex` / `which copilot` / `which cursor-agent` / `which opencode` / `which pi` / `which hermes` / `which openclaw` / `which droid` / `which devin` / `which agy` / `which goose`):

- **एक CLI पहचाना गया** — बिना संकेत दिए उस CLI को स्वचालित रूप से चुनता है।
- **कई CLI पहचानें** एक interactive terminal में — एक तीर-कुंजी single-select prompt दिखाता है एक `Detected (N)` सेक्शन में grouped (एक `Install for all N detected` aggregate row + प्रत्येक detected CLI अलग से) और एक `Not installed (M) · install hooks ahead of time` सेक्शन सूचीबद्ध करता है हर undetected supported CLI एक forward-install विकल्प के रूप में (↑↓ move, Enter select, ^C quit)। uninstall flow केवल Detected सेक्शन दिखाता है।
- **कई CLI पहचानें** एक non-interactive run में (CI, no TTY) — बिना संकेत दिए सभी detected CLI के लिए इंस्टॉल करता है।
- **कोई भी नहीं पहचाना गया** — `claude` को fallback करता है, एक warning के साथ कि PATH में कोई एजेंट बाइनरी नहीं मिला; हुक कमांड फिर भी लिखा जाता है इसलिए यह सक्रिय हो जाता है जैसे ही आप एक इंस्टॉल करते हैं।

आप किसी भी समय `policies-config.json` को सीधे संपादित कर सकते हैं; परिवर्तन अगले हुक इवेंट पर तुरंत प्रभावी होते हैं, restart की कोई आवश्यकता नहीं है।

## अपग्रेड आपकी कॉन्फ़िगरेशन रखते हैं

failproofai का एक नया संस्करण `~/.failproofai/` को अलग तरीके से organise कर सकता है। जब यह करता है, तो अपग्रेड के बाद पहली कमांड निर्देशिका को migrate करती है, और **आपकी कॉन्फ़िगरेशन को carry across किया जाता है, reset नहीं**:

| रखी गई | Rebuilt |
|---|---|
| आपकी नीति चयन और पैरामीटर (`policies-config.json`) | audit cache |
| आपकी सेटिंग्स, `daemon.configured` और अतिरिक्त capture paths सहित (`config.json`) | Cloud-managed नीति deployments — अगले poll पर फिर से fetch और digest-verified |
| आपका cloud enrolment (`credentials.json`) | Daemon scratch state |
| आपकी अपनी नीति फ़ाइलें `policies/` में, और helpers वे import करते हैं | |
| decision log जो डैशबोर्ड पढ़ता है, और अभी तक delivered नहीं किए गए events | |

एक *newer* failproofai द्वारा लिखी गई कुंजियां भी preserved हैं, rather than dropped by an older reader — इसलिए versions के बीच move करना silently discard नहीं करता settings दोनों दिशाओं में भी।

आपको setup के बाद फिर से चलाने की आवश्यकता **नहीं** है: एक migrated मशीन बिल्कुल वैसे ही enforce करती है जैसे पहले था, जो एक अपग्रेड को safe बनाता है उन मशीनों पर जहां कोई नहीं बैठा है। प्रत्येक migration को `~/.failproofai/migrations/applied.json` में recorded किया जाता है, और irreplaceable फ़ाइलों को `~/.failproofai/migrations/backup-layout<n>/` में कुछ भी चलाने से पहले copied किया जाता है।

अपग्रेड के लिए [`failproofai update`](/hi/cli/update) देखें, और [`failproofai migrate`](/hi/cli/migrate) — including `--dry-run` के लिए देखें — विवरण के लिए।

`.failproofai/policies-config.json` को अपने रिपो में कमिट करें:

```json
    "block-rm-rf",

    "sanitize-api-keys",
    "block-env-files"
  ],
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "release", "hotfix"]
    }
  }
}
```

प्रत्येक डेवलपर तब `.failproofai/policies-config.local.json` (gitignored) बना सकता है व्यक्तिगत ओवरराइड के लिए teammates को प्रभावित किए बिना।
