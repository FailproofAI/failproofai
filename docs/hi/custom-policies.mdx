कस्टम पॉलिसीज़ आपको किसी भी agent व्यवहार के लिए नियम लिखने देती हैं: प्रोजेक्ट सम्मेलन लागू करें, drift रोकें, विनाशकारी संचालन को गेट करें, फंसे हुए agents detect करें, या Slack, approval workflows, और बहुत कुछ के साथ एकीकृत करें। वे built-in पॉलिसीज़ के समान ही hook event सिस्टम और `allow`, `deny`, `instruct` निर्णय का उपयोग करती हैं।

---

## त्वरित उदाहरण

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

customPolicies.add({
  name: "no-production-writes",
  description: "Block writes to paths containing 'production'",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Write" && ctx.toolName !== "Edit") return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("production")) {
      return deny("Writes to production paths are blocked");
    }
    return allow();
  },
});
```

इसे इंस्टॉल करें:

```bash
failproofai policies --install --custom ./my-policies.js
```

## कस्टम पॉलिसीज़ लोड करने के दो तरीके

### विकल्प 1: कन्वेंशन-आधारित (अनुशंसित)

`.failproofai/policies/` में `*policies.{js,mjs,ts}` फ़ाइलें ड्रॉप करें और वे स्वचालित रूप से लोड हो जाती हैं — कोई flags या config परिवर्तन की आवश्यकता नहीं। यह git hooks की तरह काम करता है: एक फ़ाइल ड्रॉप करें, यह बस काम करता है।

```
# प्रोजेक्ट स्तर — git में committed, टीम के साथ साझा
.failproofai/policies/security-policies.mjs
.failproofai/policies/workflow-policies.mjs

# उपयोगकर्ता स्तर — व्यक्तिगत, सभी प्रोजेक्ट पर लागू होता है
~/.failproofai/policies/my-policies.mjs
```

**यह कैसे काम करता है:**
- प्रोजेक्ट और उपयोगकर्ता दोनों डायरेक्टरी स्कैन की जाती हैं (union — first-scope-wins नहीं)
- फ़ाइलें प्रत्येक डायरेक्टरी के भीतर वर्णक्रम के अनुसार लोड होती हैं। order को नियंत्रित करने के लिए `01-`, `02-` से prefix करें
- केवल `*policies.{js,mjs,ts}` से मेल खाने वाली फ़ाइलें लोड होती हैं; अन्य फ़ाइलें ignore की जाती हैं
- प्रत्येक फ़ाइल independently लोड होती है (प्रति फ़ाइल fail-open)
- स्पष्ट `--custom` और built-in पॉलिसीज़ के साथ-साथ काम करता है

<Tip>
कन्वेंशन पॉलिसीज़ आपकी org के लिए एक quality standard बनाने का सबसे आसान तरीका हैं। `.failproofai/policies/` को git में commit करें और हर टीम सदस्य को स्वचालित रूप से समान नियम मिलते हैं — कोई per-developer सेटअप आवश्यक नहीं है। जैसे-जैसे आपकी टीम नई failure modes खोजती है, एक policy जोड़ें और push करें। समय के साथ ये एक living quality standard बन जाती हैं जो हर योगदान के साथ सुधरती रहती हैं।
</Tip>

### विकल्प 2: स्पष्ट फ़ाइल पथ

```bash
# कस्टम पॉलिसीज़ फ़ाइल के साथ इंस्टॉल करें
failproofai policies --install --custom ./my-policies.js

# कस्टम पॉलिसी पथों को बदलें
failproofai policies --install --custom ./new-policies.js

# कई स्पष्ट फ़ाइलें configure करें (flag order में लोड की गई)
failproofai policies --install --custom ./security.js --custom ./workflow.js

# config से सभी स्पष्ट कस्टम पॉलिसी पथों को हटाएं
failproofai policies --uninstall --custom
```

Resolved absolute paths को `policies-config.json` में `customPoliciesPaths` के रूप में stored किया जाता है। कई फ़ाइलें configure करने के लिए `--custom` दोहराएं। legacy `customPoliciesPath` फ़ील्ड का उपयोग करने वाले existing configs जारी रहते हैं। फ़ाइलें प्रत्येक hook event पर fresh लोड होती हैं - events के बीच कोई caching नहीं है।

प्रत्येक registered policy dashboard में अपने toggle के साथ दिखाई देती है। एक policy को बंद करने से इसकी source-qualified ID को `disabledCustomPolicies` में record किया जाता है; फ़ाइल और इसकी अन्य policies लोड होती रहती हैं, जबकि disabled policy को event matching से पहले exclude किया जाता है। फ़ाइलों में duplicate policy नामों में independent toggles होते हैं।

### दोनों को एक साथ उपयोग करना

कन्वेंशन पॉलिसीज़ और स्पष्ट `--custom` फ़ाइलें coexist कर सकती हैं। लोड order:

1. स्पष्ट `customPoliciesPaths` फ़ाइलें (configured order में)
2. प्रोजेक्ट कन्वेंशन फ़ाइलें (`{cwd}/.failproofai/policies/`, वर्णक्रम)
3. उपयोगकर्ता कन्वेंशन फ़ाइलें (`~/.failproofai/policies/`, वर्णक्रम)

## API

### Import

```js
import { customPolicies, allow, deny, instruct } from "failproofai";
```

### `customPolicies.add(hook)`

एक policy को register करता है। एक ही फ़ाइल में कई policies के लिए जितनी बार चाहें यह कॉल करें।

```ts
customPolicies.add({
  name: string;                         // required - unique identifier
  description?: string;                 // shown in `failproofai policies` output
  match?: { events?: HookEventType[] }; // filter by event type; omit to match all
  fn: (ctx: PolicyContext) => PolicyResult | Promise<PolicyResult>;
});
```

### Decision helpers

| Function | Effect | Use when |
|----------|--------|----------|
| `allow()` | संचालन को चुप्पी से permit करें | क्रिया सुरक्षित है, कोई संदेश की आवश्यकता नहीं |
| `deny(message)` | संचालन को block करें | agent को यह क्रिया नहीं लेनी चाहिए |
| `instruct(message)` | बिना blocking के context जोड़ें | agent को on track रहने के लिए अतिरिक्त context दें |

`deny(message)` - संदेश Claude को `"Blocked by failproofai:"` prefix के साथ दिखाई देता है। एक single `deny` सभी further evaluation को short-circuit करता है।

`instruct(message)` - संदेश को Claude के context में current tool call के लिए appended किया जाता है। सभी `instruct` संदेश accumulated होते हैं और एक साथ delivered होते हैं।

<Tip>
`policyParams` में एक `hint` फ़ील्ड जोड़कर किसी भी `deny` या `instruct` संदेश में अतिरिक्त guidance जोड़ें — कोई code परिवर्तन आवश्यक नहीं। यह custom (`custom/`), project convention (`.failproofai-project/`), और user convention (`.failproofai-user/`) policies के लिए भी काम करता है। विवरण के लिए [Configuration → hint](/hi/configuration#hint-cross-cutting) देखें।
</Tip>

### Informational allow messages

`allow(message)` संचालन को permit करता है **और** Claude को एक informational message भेजता है। संदेश को hook handler के stdout response में `additionalContext` के रूप में delivered किया जाता है — `instruct` द्वारा उपयोग की जाने वाली same mechanism, लेकिन semantically different: यह एक status update है, warning नहीं।

| Function | Effect | Use when |
|----------|--------|----------|
| `allow(message)` | Permit करें और Claude को context भेजें | एक check को confirm करें, या explain करें कि check को क्यों skip किया गया |

Use cases:
- **Status confirmations:** `allow("All CI checks passed.")` — Claude को बताता है कि सब कुछ green है
- **Fail-open explanations:** `allow("GitHub CLI not installed, skipping CI check.")` — Claude को बताता है कि check को क्यों skip किया गया ताकि इसके पास पूरा context हो
- **Multiple messages accumulate:** यदि कई policies प्रत्येक `allow(message)` return करते हैं, तो सभी messages को newlines से जोड़ा जाता है और एक साथ delivered किया जाता है

```js
customPolicies.add({
  name: "confirm-branch-status",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow("No working directory, skipping branch check.");

    // ... check branch status ...
    if (allPushed) {
      return allow("Branch is up to date with remote.");
    }
    return deny("Unpushed changes detected.");
  },
});
```

### `PolicyContext` fields

| Field | Type | Description |
|-------|------|-------------|
| `eventType` | `string` | `"PreToolUse"`, `"PostToolUse"`, `"Notification"`, `"Stop"` |
| `toolName` | `string \| undefined` | यह tool जो call किया जा रहा है (e.g. `"Bash"`, `"Write"`, `"Read"`) |
| `toolInput` | `Record<string, unknown> \| undefined` | tool के input parameters |
| `payload` | `Record<string, unknown>` | Claude Code से full raw event payload |
| `session` | `SessionMetadata \| undefined` | Session context (नीचे देखें) |

### `SessionMetadata` fields

| Field | Type | Description |
|-------|------|-------------|
| `sessionId` | `string` | Claude Code session identifier |
| `cwd` | `string` | Claude Code session की working directory |
| `transcriptPath` | `string` | session की JSONL transcript file का पथ |

### Event types

| Event | कब fire होता है | `toolInput` contents |
|-------|--------------|----------------------|
| `PreToolUse` | Claude एक tool run करने से पहले | tool का input (e.g. `{ command: "..." }` Bash के लिए) |
| `PostToolUse` | एक tool complete होने के बाद | tool का input + `tool_result` (output) |
| `Notification` | जब Claude एक notification भेजता है | `{ message: "...", notification_type: "idle" \| "permission_prompt" \| ... }` - hooks को हमेशा `allow()` return करना चाहिए, वे notifications को block नहीं कर सकते |
| `Stop` | जब Claude session समाप्त होता है | Empty |

## Evaluation order

Policies को इस order में evaluate किया जाता है:

1. Built-in policies (definition order में)
2. `customPoliciesPath` से explicit custom policies (`.add()` order में)
3. प्रोजेक्ट `.failproofai/policies/` से convention policies (files alphabetical, within `.add()` order)
4. उपयोगकर्ता `~/.failproofai/policies/` से convention policies (files alphabetical, within `.add()` order)

<Note>
पहला `deny` सभी subsequent policies को short-circuit करता है। सभी `instruct` messages को accumulated किया जाता है और एक साथ delivered किया जाता है।
</Note>

## Transitive imports

कस्टम policy files relative paths का उपयोग करके local modules को import कर सकते हैं:

```js
// my-policies.js
import { isBlockedPath } from "./utils.js";
import { checkApproval } from "./approval-client.js";

customPolicies.add({
  name: "approval-gate",
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const approved = await checkApproval(ctx.toolInput?.command, ctx.session?.sessionId);
    return approved ? allow() : deny("Approval required for this command");
  },
});
```

Entry file से reachable सभी relative imports को resolve किया जाता है। यह `from "failproofai"` imports को actual dist path में rewrite करके और ESM compatibility सुनिश्चित करने के लिए temporary `.mjs` फ़ाइलें बनाकर implement किया जाता है।

## Event type filtering

`match.events` का उपयोग करके limit करें कि एक policy कब fire हो:

```js
customPolicies.add({
  name: "require-summary-on-stop",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    // केवल तब fire होता है जब session समाप्त होता है
    // ctx.session.transcriptPath में full session log होता है
    return allow();
  },
});
```

हर event type पर fire करने के लिए `match` को entirely omit करें।

## Error handling और failure modes

कस्टम policies **fail-open** हैं: errors कभी भी built-in policies को block नहीं करते या hook handler को crash नहीं करते।

| Failure | Behavior |
|---------|----------|
| `customPoliciesPath` set नहीं है | कोई explicit custom policies run नहीं होते; convention policies और built-ins normally जारी रहते हैं |
| File not found | `~/.failproofai/hook.log` में warning logged; built-ins जारी रहते हैं |
| Syntax/import error (explicit) | `~/.failproofai/hook.log` में error logged; explicit custom policies skipped |
| Syntax/import error (convention) | Error logged; वह file skipped, अन्य convention files अभी भी load होती हैं |
| `fn` runtime में throw करता है | Error logged; वह hook `allow` के रूप में treated; अन्य hooks जारी रहते हैं |
| `fn` 10s से अधिक समय लेता है | Timeout logged; `allow` के रूप में treated |
| Convention directory missing | कोई convention policies नहीं चलते; कोई error नहीं |

<Tip>
कस्टम policy errors को debug करने के लिए, log file को watch करें:

```bash
tail -f ~/.failproofai/hook.log
```
</Tip>

## पूर्ण उदाहरण: कई policies

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

// agent को secrets/ directory में लिखने से रोकें
customPolicies.add({
  name: "block-secrets-dir",
  description: "Prevent agent from writing to secrets/ directory",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("secrets/")) return deny("Writing to secrets/ is not permitted");
    return allow();
  },
});

// Agent को on track रखें: commit करने से पहले tests verify करें
customPolicies.add({
  name: "remind-test-before-commit",
  description: "Keep the agent on track: verify tests pass before committing",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    if (/git\s+commit/.test(cmd)) {
      return instruct("Verify all tests pass before committing. Run `bun test` if you haven't already.");
    }
    return allow();
  },
});

// Freeze अवधि के दौरान unplanned dependency changes को रोकें
customPolicies.add({
  name: "dependency-freeze",
  description: "Prevent unplanned dependency changes during freeze period",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    const isInstall = /^(npm install|yarn add|bun add|pnpm add)\s+\S/.test(cmd);
    if (isInstall && process.env.DEPENDENCY_FREEZE === "1") {
      return deny("Package installs are frozen. Unset DEPENDENCY_FREEZE to allow.");
    }
    return allow();
  },
});

export { customPolicies };
```

## उदाहरण

`examples/` directory में ready-to-run policy files हैं:

| File | Contents |
|------|----------|
| `examples/policies-basic.js` | पाँच starter policies जो common agent failure modes को cover करती हैं |
| `examples/policies-advanced/index.js` | Advanced patterns: transitive imports, async calls, output scrubbing, और session-end hooks |
| `examples/convention-policies/security-policies.mjs` | Convention-based security policies (.env writes को block करें, git history rewriting को रोकें) |
| `examples/convention-policies/workflow-policies.mjs` | Convention-based workflow policies (test reminders, audit file writes) |

### स्पष्ट फ़ाइल उदाहरणों का उपयोग करना

```bash
failproofai policies --install --custom ./examples/policies-basic.js
```

### कन्वेंशन-आधारित उदाहरणों का उपयोग करना

```bash
# प्रोजेक्ट स्तर पर कॉपी करें
mkdir -p .failproofai/policies
cp examples/convention-policies/*.mjs .failproofai/policies/

# या उपयोगकर्ता स्तर पर कॉपी करें
mkdir -p ~/.failproofai/policies
cp examples/convention-policies/*.mjs ~/.failproofai/policies/
```

कोई install command की आवश्यकता नहीं — फ़ाइलें अगली hook event पर स्वचालित रूप से pick up हो जाती हैं।
