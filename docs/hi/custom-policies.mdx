कस्टम पॉलिसीज़ आपको किसी भी एजेंट व्यवहार के लिए नियम लिखने देती हैं: प्रोजेक्ट कन्वेंशन लागू करें, ड्रिफ्ट रोकें, विनाशकारी ऑपरेशन को नियंत्रित करें, फंसे हुए एजेंट का पता लगाएं, या Slack, अनुमोदन वर्कफ़्लो और बहुत कुछ के साथ एकीकृत करें। वे बिल्ट-इन पॉलिसीज़ के समान हुक इवेंट सिस्टम और `allow`, `deny`, `instruct` निर्णय का उपयोग करते हैं।

---

## त्वरित उदाहरण

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

customPolicies.add({
  name: "no-production-writes",
  description: "Block writes to paths containing 'production'",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Write" && ctx.toolName !== "Edit") return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("production")) {
      return deny("Writes to production paths are blocked");
    }
    return allow();
  },
});
```

इसे इंस्टॉल करें:

```bash
failproofai policies --install --custom ./my-policies.js
```

## कस्टम पॉलिसीज़ लोड करने के दो तरीके

### विकल्प 1: कन्वेंशन-आधारित (अनुशंसित)

`*policies.{js,mjs,ts}` फ़ाइलों को `.failproofai/policies/` में डालें और वे स्वचालित रूप से लोड हो जाती हैं — कोई फ़्लैग या कॉन्फ़िग परिवर्तन की आवश्यकता नहीं। यह git hooks की तरह काम करता है: एक फ़ाइल डालें, बस काम करता है।

```
# प्रोजेक्ट स्तर — git में प्रतिबद्ध, टीम के साथ साझा
.failproofai/policies/security-policies.mjs
.failproofai/policies/workflow-policies.mjs

# उपयोगकर्ता स्तर — व्यक्तिगत, सभी प्रोजेक्ट्स पर लागू होता है
~/.failproofai/policies/my-policies.mjs
```

**यह कैसे काम करता है:**
- प्रोजेक्ट और उपयोगकर्ता दोनों निर्देशिकाओं को स्कैन किया जाता है (यूनियन — पहला-स्कोप-जीत नहीं)
- फ़ाइलें प्रत्येक निर्देशिका के भीतर वर्णानुक्रम से लोड होती हैं। क्रम को नियंत्रित करने के लिए `01-`, `02-` से प्रीफ़िक्स करें
- केवल `*policies.{js,mjs,ts}` से मेल खाने वाली फ़ाइलें लोड होती हैं; अन्य फ़ाइलें अनदेखी की जाती हैं
- प्रत्येक फ़ाइल स्वतंत्र रूप से लोड होती है (प्रति फ़ाइल फ़ेल-ओपन)
- स्पष्ट `--custom` और बिल्ट-इन पॉलिसीज़ के साथ काम करता है

<Tip>
कन्वेंशन पॉलिसीज़ आपके संगठन के लिए गुणवत्ता मानक बनाने का सबसे आसान तरीका हैं। `.failproofai/policies/` को git में प्रतिबद्ध करें और प्रत्येक टीम सदस्य को स्वचालित रूप से समान नियम मिलें — कोई प्रति-डेवलपर सेटअप की आवश्यकता नहीं। जैसे-जैसे आपकी टीम नई विफलता मोड खोजती है, एक पॉलिसी जोड़ें और पुश करें। समय के साथ ये एक जीवंत गुणवत्ता मानक बन जाते हैं जो हर योगदान के साथ सुधरता रहता है।
</Tip>

### विकल्प 2: स्पष्ट फ़ाइल पथ

```bash
# कस्टम पॉलिसीज़ फ़ाइल के साथ इंस्टॉल करें
failproofai policies --install --custom ./my-policies.js

# कस्टम पॉलिसी पथ को बदलें
failproofai policies --install --custom ./new-policies.js

# कई स्पष्ट फ़ाइलों को कॉन्फ़िगर करें (फ़्लैग क्रम में लोड होती हैं)
failproofai policies --install --custom ./security.js --custom ./workflow.js

# कॉन्फ़िग से सभी स्पष्ट कस्टम पॉलिसी पथ हटाएं
failproofai policies --uninstall --custom
```

समाधान किए गए पूर्ण पथ `policies-config.json` में `customPoliciesPaths` के रूप में संग्रहीत होते हैं। कई फ़ाइलों को कॉन्फ़िगर करने के लिए `--custom` को दोहराएं। विरासत `customPoliciesPath` फ़ील्ड का उपयोग करने वाली मौजूदा कॉन्फ़िग काम करती रहती है। फ़ाइलें हर हुक इवेंट पर ताज़ी लोड होती हैं - इवेंट्स के बीच कोई कैशिंग नहीं है।

प्रत्येक पंजीकृत पॉलिसी डैशबोर्ड में अपने स्वयं के टॉगल के साथ दिखाई देती है। एक पॉलिसी बंद करने से इसके स्रोत-योग्य ID को `disabledCustomPolicies` में दर्ज किया जाता है; फ़ाइल और इसकी अन्य पॉलिसीज़ लोड होती रहती हैं, जबकि अक्षम पॉलिसी इवेंट मिलान से पहले बाहर निकाल दी जाती है। फ़ाइलों में डुप्लिकेट किए गए पॉलिसी नामों के स्वतंत्र टॉगल होते हैं।

### दोनों को एक साथ उपयोग करना

कन्वेंशन पॉलिसीज़ और स्पष्ट `--custom` फ़ाइलें सह-अस्तित्व में हो सकती हैं। लोड ऑर्डर:

1. स्पष्ट `customPoliciesPaths` फ़ाइलें (कॉन्फ़िगर किए गए क्रम में)
2. प्रोजेक्ट कन्वेंशन फ़ाइलें (`{cwd}/.failproofai/policies/`, वर्णानुक्रम)
3. उपयोगकर्ता कन्वेंशन फ़ाइलें (`~/.failproofai/policies/`, वर्णानुक्रम)

## API

### आयात करें

```js
import { customPolicies, allow, deny, instruct } from "failproofai";
```

### `customPolicies.add(hook)`

एक पॉलिसी पंजीकृत करता है। एक ही फ़ाइल में कई पॉलिसीज़ के लिए आवश्यकतानुसार कॉल करें।

```ts
customPolicies.add({
  name: string;                         // आवश्यक - अद्वितीय पहचानकर्ता
  description?: string;                 // `failproofai policies` आउटपुट में दिखाया गया
  match?: { events?: HookEventType[] }; // इवेंट प्रकार के आधार पर फ़िल्टर करें; सभी से मेल खाने के लिए छोड़ दें
  fn: (ctx: PolicyContext) => PolicyResult | Promise<PolicyResult>;
});
```

### निर्णय सहायक

| फ़ंक्शन | प्रभाव | कब उपयोग करें |
|----------|--------|----------|
| `allow()` | ऑपरेशन को चुप से अनुमति दें | कार्रवाई सुरक्षित है, कोई संदेश आवश्यक नहीं |
| `deny(message)` | ऑपरेशन को ब्लॉक करें | एजेंट को यह कार्रवाई नहीं करनी चाहिए |
| `instruct(message)` | बिना ब्लॉक किए संदर्भ जोड़ें | एजेंट को ट्रैक पर रहने के लिए अतिरिक्त संदर्भ दें |

`deny(message)` - संदेश Claude को `"Blocked by failproofai:"` से प्रीफ़िक्स्ड दिखाई देता है। एकल `deny` सभी आगे के मूल्यांकन को छोटा-परिपथ करता है।

`instruct(message)` - संदेश वर्तमान टूल कॉल के लिए Claude के संदर्भ में जोड़ा जाता है। सभी `instruct` संदेश जमा किए जाते हैं और एक साथ दिए जाते हैं।

<Tip>
आप `policyParams` में `hint` फ़ील्ड जोड़कर किसी भी `deny` या `instruct` संदेश के लिए अतिरिक्त मार्गदर्शन जोड़ सकते हैं — कोई कोड परिवर्तन आवश्यक नहीं। यह कस्टम (`custom/`), प्रोजेक्ट कन्वेंशन (`.failproofai-project/`), और उपयोगकर्ता कन्वेंशन (`.failproofai-user/`) पॉलिसीज़ के लिए भी काम करता है। विवरण के लिए [Configuration → hint](/hi/configuration#hint-cross-cutting) देखें।
</Tip>

### सूचनात्मक allow संदेश

`allow(message)` ऑपरेशन की अनुमति **और** Claude को वापस एक सूचनात्मक संदेश भेजता है। संदेश हुक हैंडलर के stdout प्रतिक्रिया में `additionalContext` के रूप में दिया जाता है — `instruct` द्वारा उपयोग किया गया समान तंत्र, लेकिन शब्दार्थी रूप से अलग: यह एक चेतावनी नहीं, एक स्थिति अपडेट है।

| फ़ंक्शन | प्रभाव | कब उपयोग करें |
|----------|--------|----------|
| `allow(message)` | अनुमति दें और Claude को संदर्भ भेजें | एक जांच पास की पुष्टि करें, या समझाएं कि एक जांच क्यों छोड़ी गई |

उपयोग के मामले:
- **स्थिति पुष्टि:** `allow("All CI checks passed.")` — Claude को बताता है कि सब कुछ ठीक है
- **फ़ेल-ओपन व्याख्याएं:** `allow("GitHub CLI not installed, skipping CI check.")` — Claude को बताता है कि एक जांच क्यों छोड़ी गई ताकि उसके पास पूरा संदर्भ हो
- **कई संदेश जमा होते हैं:** यदि कई पॉलिसीज़ प्रत्येक `allow(message)` देते हैं, तो सभी संदेश नई पंक्तियों के साथ जुड़ते हैं और एक साथ दिए जाते हैं

```js
customPolicies.add({
  name: "confirm-branch-status",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow("No working directory, skipping branch check.");

    // ... check branch status ...
    if (allPushed) {
      return allow("Branch is up to date with remote.");
    }
    return deny("Unpushed changes detected.");
  },
});
```

### `PolicyContext` फ़ील्ड

| फ़ील्ड | प्रकार | विवरण |
|-------|------|-------------|
| `eventType` | `string` | `"PreToolUse"`, `"PostToolUse"`, `"Notification"`, `"Stop"` |
| `toolName` | `string \| undefined` | कॉल किया जा रहा टूल (उदा. `"Bash"`, `"Write"`, `"Read"`) |
| `toolInput` | `Record<string, unknown> \| undefined` | टूल के इनपुट पैरामीटर |
| `payload` | `Record<string, unknown>` | Claude Code से पूर्ण कच्चा इवेंट पेलोड |
| `session` | `SessionMetadata \| undefined` | सेशन संदर्भ (नीचे देखें) |

### `SessionMetadata` फ़ील्ड

| फ़ील्ड | प्रकार | विवरण |
|-------|------|-------------|
| `sessionId` | `string` | Claude Code सेशन पहचानकर्ता |
| `cwd` | `string` | Claude Code सेशन की कार्यशील निर्देशिका |
| `transcriptPath` | `string` | सेशन की JSONL ट्रांसक्रिप्ट फ़ाइल का पथ |

### इवेंट प्रकार

| इवेंट | कब फायर होता है | `toolInput` सामग्री |
|-------|--------------|----------------------|
| `PreToolUse` | इससे पहले Claude एक टूल चलाता है | टूल का इनपुट (उदा. Bash के लिए `{ command: "..." }`) |
| `PostToolUse` | एक टूल पूरा होने के बाद | टूल का इनपुट + `tool_result` (आउटपुट) |
| `Notification` | जब Claude एक सूचना भेजता है | `{ message: "...", notification_type: "idle" \| "permission_prompt" \| ... }` - हुक को हमेशा `allow()` देना चाहिए, वे सूचनाओं को ब्लॉक नहीं कर सकते |
| `Stop` | जब Claude सेशन समाप्त होता है | खाली |

## मूल्यांकन क्रम

पॉलिसीज़ का मूल्यांकन इस क्रम में होता है:

1. बिल्ट-इन पॉलिसीज़ (परिभाषा क्रम में)
2. `customPoliciesPath` से स्पष्ट कस्टम पॉलिसीज़ (`.add()` क्रम में)
3. प्रोजेक्ट `.failproofai/policies/` से कन्वेंशन पॉलिसीज़ (फ़ाइलें वर्णानुक्रम, भीतर `.add()` क्रम)
4. उपयोगकर्ता `~/.failproofai/policies/` से कन्वेंशन पॉलिसीज़ (फ़ाइलें वर्णानुक्रम, भीतर `.add()` क्रम)

<Note>
पहला `deny` सभी बाद की पॉलिसीज़ को छोटा-परिपथ करता है। सभी `instruct` संदेश जमा किए जाते हैं और एक साथ दिए जाते हैं।
</Note>

## सकर्मक आयात

कस्टम पॉलिसी फ़ाइलें सापेक्ष पथों का उपयोग करके स्थानीय मॉड्यूल को आयात कर सकती हैं:

```js
// my-policies.js
import { isBlockedPath } from "./utils.js";
import { checkApproval } from "./approval-client.js";

customPolicies.add({
  name: "approval-gate",
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const approved = await checkApproval(ctx.toolInput?.command, ctx.session?.sessionId);
    return approved ? allow() : deny("Approval required for this command");
  },
});
```

प्रवेश फ़ाइल से सभी सापेक्ष आयात को हल किया जाता है। यह `from "failproofai"` आयातों को वास्तविक dist पथ में फिर से लिखकर और ESM संगतता सुनिश्चित करने के लिए अस्थायी `.mjs` फ़ाइलें बनाकर लागू किया जाता है।

## इवेंट प्रकार फ़िल्टरिंग

यह निर्धारित करने के लिए `match.events` का उपयोग करें कि कब कोई पॉलिसी फायर होती है:

```js
customPolicies.add({
  name: "require-summary-on-stop",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    // केवल तब फायर होता है जब सेशन समाप्त हो
    // ctx.session.transcriptPath में पूरा सेशन लॉग होता है
    return allow();
  },
});
```

हर इवेंट प्रकार पर फायर करने के लिए `match` को पूरी तरह से छोड़ दें।

## त्रुटि हैंडलिंग और विफलता मोड

कस्टम पॉलिसीज़ **फ़ेल-ओपन** हैं: त्रुटियां कभी भी बिल्ट-इन पॉलिसीज़ को ब्लॉक नहीं करती हैं या हुक हैंडलर को क्रैश नहीं करती हैं।

| विफलता | व्यवहार |
|---------|----------|
| `customPoliciesPath` सेट नहीं | कोई स्पष्ट कस्टम पॉलिसीज़ चलाएं नहीं; कन्वेंशन पॉलिसीज़ और बिल्ट-इन सामान्य रूप से जारी रहते हैं |
| फ़ाइल नहीं मिली | `~/.failproofai/hook.log` में चेतावनी लॉग की गई; बिल्ट-इन जारी रहते हैं |
| सिंटैक्स/आयात त्रुटि (स्पष्ट) | `~/.failproofai/hook.log` में त्रुटि लॉग की गई; स्पष्ट कस्टम पॉलिसीज़ छोड़ दी गई |
| सिंटैक्स/आयात त्रुटि (कन्वेंशन) | त्रुटि लॉग की गई; वह फ़ाइल छोड़ दी गई, अन्य कन्वेंशन फ़ाइलें अभी भी लोड होती हैं |
| `fn` रनटाइम पर फेंकता है | त्रुटि लॉग की गई; वह हुक `allow` के रूप में माना जाता है; अन्य हुक जारी रहते हैं |
| `fn` 10 सेकंड से अधिक समय लेता है | टाइमआउट लॉग किया गया; `allow` के रूप में माना जाता है |
| कन्वेंशन निर्देशिका अनुपस्थित | कोई कन्वेंशन पॉलिसीज़ नहीं चलाएं; कोई त्रुटि नहीं |

<Tip>
कस्टम पॉलिसी त्रुटियों को डीबग करने के लिए लॉग फ़ाइल को देखें:

```bash
tail -f ~/.failproofai/hook.log
```
</Tip>

## पूर्ण उदाहरण: कई पॉलिसीज़

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

// एजेंट को secrets/ निर्देशिका में लिखने से रोकें
customPolicies.add({
  name: "block-secrets-dir",
  description: "Prevent agent from writing to secrets/ directory",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("secrets/")) return deny("Writing to secrets/ is not permitted");
    return allow();
  },
});

// एजेंट को ट्रैक पर रखें: प्रतिबद्ध करने से पहले परीक्षण सत्यापित करें
customPolicies.add({
  name: "remind-test-before-commit",
  description: "Keep the agent on track: verify tests pass before committing",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    if (/git\s+commit/.test(cmd)) {
      return instruct("Verify all tests pass before committing. Run `bun test` if you haven't already.");
    }
    return allow();
  },
});

// फ्रीज अवधि के दौरान अनियोजित निर्भरता परिवर्तन रोकें
customPolicies.add({
  name: "dependency-freeze",
  description: "Prevent unplanned dependency changes during freeze period",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    const isInstall = /^(npm install|yarn add|bun add|pnpm add)\s+\S/.test(cmd);
    if (isInstall && process.env.DEPENDENCY_FREEZE === "1") {
      return deny("Package installs are frozen. Unset DEPENDENCY_FREEZE to allow.");
    }
    return allow();
  },
});

export { customPolicies };
```

## उदाहरण

`examples/` निर्देशिका में तैयार-से-चलाने वाली पॉलिसी फ़ाइलें हैं:

| फ़ाइल | सामग्री |
|------|----------|
| `examples/policies-basic.js` | पाँच स्टार्टर पॉलिसीज़ जो सामान्य एजेंट विफलता मोड को कवर करती हैं |
| `examples/policies-advanced/index.js` | उन्नत पैटर्न: सकर्मक आयात, async कॉल, आउटपुट स्क्रबिंग, और सेशन-एंड हुक |
| `examples/convention-policies/security-policies.mjs` | कन्वेंशन-आधारित सुरक्षा पॉलिसीज़ (.env लिखना ब्लॉक करें, git इतिहास फिर से लिखना रोकें) |
| `examples/convention-policies/workflow-policies.mjs` | कन्वेंशन-आधारित वर्कफ़्लो पॉलिसीज़ (परीक्षण अनुस्मारक, ऑडिट फ़ाइल लिखता है) |

### स्पष्ट फ़ाइल उदाहरणों का उपयोग करना

```bash
failproofai policies --install --custom ./examples/policies-basic.js
```

### कन्वेंशन-आधारित उदाहरणों का उपयोग करना

```bash
# प्रोजेक्ट स्तर पर कॉपी करें
mkdir -p .failproofai/policies
cp examples/convention-policies/*.mjs .failproofai/policies/

# या उपयोगकर्ता स्तर पर कॉपी करें
mkdir -p ~/.failproofai/policies
cp examples/convention-policies/*.mjs ~/.failproofai/policies/
```
