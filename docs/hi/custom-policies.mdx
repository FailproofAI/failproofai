कस्टम पॉलिसीज़ आपको किसी भी एजेंट व्यवहार के लिए नियम लिखने देती हैं: प्रोजेक्ट कन्वेंशन लागू करें, ड्रिफ्ट को रोकें, विनाशकारी ऑपरेशन को गेट करें, फंसे हुए एजेंट का पता लगाएं, या Slack, अनुमोदन वर्कफ़्लो और बहुत कुछ के साथ एकीकृत करें। वे बिल्ट-इन पॉलिसीज़ के समान ही हुक इवेंट सिस्टम और `allow`, `deny`, `instruct` निर्णयों का उपयोग करते हैं।

---

## त्वरित उदाहरण

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

customPolicies.add({
  name: "no-production-writes",
  description: "Block writes to paths containing 'production'",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Write" && ctx.toolName !== "Edit") return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("production")) {
      return deny("Writes to production paths are blocked");
    }
    return allow();
  },
});
```

इसे इंस्टॉल करें:

```bash
failproofai policies --install --custom ./my-policies.js
```

## कस्टम पॉलिसीज़ लोड करने के दो तरीके

### विकल्प 1: कन्वेंशन-आधारित (अनुशंसित)

`.failproofai/policies/` में `*policies.{js,mjs,ts}` फाइलें छोड़ें और वे स्वचालित रूप से लोड हो जाती हैं — कोई फ्लैग या कॉन्फ़िगरेशन परिवर्तन की आवश्यकता नहीं। यह git हुक्स की तरह काम करता है: एक फाइल छोड़ें, बस काम करता है।

```
# प्रोजेक्ट लेवल — git में कमिट किया गया, टीम के साथ साझा किया गया
.failproofai/policies/security-policies.mjs
.failproofai/policies/workflow-policies.mjs

# यूजर लेवल — व्यक्तिगत, सभी प्रोजेक्ट पर लागू
~/.failproofai/policies/my-policies.mjs
```

**यह कैसे काम करता है:**
- प्रोजेक्ट और यूजर दोनों डायरेक्टरी को स्कैन किया जाता है (यूनियन — पहला-स्कोप-जीत नहीं)
- फाइलें प्रत्येक डायरेक्टरी में वर्णमाला के क्रम में लोड की जाती हैं। ऑर्डर को नियंत्रित करने के लिए `01-`, `02-` से प्रीफ़िक्स करें
- केवल `*policies.{js,mjs,ts}` से मेल खाने वाली फाइलें लोड की जाती हैं; अन्य फाइलें अनदेखी की जाती हैं
- प्रत्येक फाइल स्वतंत्र रूप से लोड की जाती है (प्रति फाइल फेल-ओपन)
- स्पष्ट `--custom` और बिल्ट-इन पॉलिसीज़ के साथ काम करता है

<Tip>
कन्वेंशन पॉलिसीज़ आपके संगठन के लिए गुणवत्ता मानक बनाने का सबसे आसान तरीका है। `.failproofai/policies/` को git में कमिट करें और हर टीम सदस्य को स्वचालित रूप से समान नियम मिलते हैं — कोई प्रति-डेवलपर सेटअप की आवश्यकता नहीं। जैसे-जैसे आपकी टीम नई विफलता के तरीके खोजती है, एक पॉलिसी जोड़ें और पुश करें। समय के साथ ये एक जीवंत गुणवत्ता मानक बन जाते हैं जो हर योगदान के साथ सुधरता रहता है।
</Tip>

### विकल्प 2: स्पष्ट फाइल पथ

```bash
# कस्टम पॉलिसीज़ फाइल के साथ इंस्टॉल करें
failproofai policies --install --custom ./my-policies.js

# कस्टम पॉलिसी पथ को प्रतिस्थापित करें
failproofai policies --install --custom ./new-policies.js

# कई स्पष्ट फाइलें कॉन्फ़िगर करें (फ्लैग ऑर्डर में लोड की गई)
failproofai policies --install --custom ./security.js --custom ./workflow.js

# कॉन्फ़िग से सभी स्पष्ट कस्टम पॉलिसी पथ हटाएं
failproofai policies --uninstall --custom
```

रिज़ॉल्व किए गए निरपेक्ष पथ `policies-config.json` में `customPoliciesPaths` के रूप में संग्रहीत होते हैं। कई फाइलों को कॉन्फ़िगर करने के लिए `--custom` को दोहराएं। लीगेसी `customPoliciesPath` फील्ड का उपयोग करने वाले मौजूदा कॉन्फ़िगरेशन काम करना जारी रखते हैं। फाइलें हर हुक इवेंट पर ताज़ा लोड की जाती हैं - इवेंट्स के बीच कोई कैशिंग नहीं है।

प्रत्येक पंजीकृत पॉलिसी डैशबोर्ड में अपने स्वयं के टॉगल के साथ दिखाई देती है। किसी पॉलिसी को बंद करने से उसके स्रोत-योग्य ID को `disabledCustomPolicies` में रिकॉर्ड किया जाता है; फाइल और उसकी अन्य पॉलिसीज़ लोड होना जारी रहती हैं, जबकि अक्षम पॉलिसी को इवेंट मिलान से पहले बाहर रखा जाता है। फाइलों में डुप्लिकेट पॉलिसी नामों के स्वतंत्र टॉगल होते हैं।

### दोनों को एक साथ उपयोग करना

कन्वेंशन पॉलिसीज़ और स्पष्ट `--custom` फाइलें एक-दूसरे के साथ मौजूद हो सकती हैं। लोड ऑर्डर:

1. स्पष्ट `customPoliciesPaths` फाइलें (कॉन्फ़िगर किए गए ऑर्डर में)
2. प्रोजेक्ट कन्वेंशन फाइलें (`{cwd}/.failproofai/policies/`, वर्णमाला)
3. यूजर कन्वेंशन फाइलें (`~/.failproofai/policies/`, वर्णमाला)

## API

### इंपोर्ट

```js
import { customPolicies, allow, deny, instruct } from "failproofai";
```

### `customPolicies.add(hook)`

एक पॉलिसी को पंजीकृत करता है। एक ही फाइल में कई पॉलिसीज़ के लिए आवश्यकतानुसार कई बार कॉल करें।

```ts
customPolicies.add({
  name: string;                         // आवश्यक - अद्वितीय पहचानकर्ता
  description?: string;                 // `failproofai policies` आउटपुट में दिखाया गया
  match?: { events?: HookEventType[] }; // इवेंट टाइप द्वारा फ़िल्टर करें; सभी से मेल खाने के लिए छोड़ें
  fn: (ctx: PolicyContext) => PolicyResult | Promise<PolicyResult>;
});
```

### निर्णय सहायक

| फंक्शन | प्रभाव | उपयोग करें जब |
|----------|--------|----------|
| `allow()` | ऑपरेशन को चुप रहकर अनुमति दें | एक्शन सुरक्षित है, कोई संदेश की आवश्यकता नहीं |
| `deny(message)` | ऑपरेशन को ब्लॉक करें | एजेंट को यह एक्शन नहीं लेना चाहिए |
| `instruct(message)` | बिना ब्लॉकिंग के कॉन्टेक्स्ट जोड़ें | एजेंट को सही रास्ते पर रहने के लिए अतिरिक्त कॉन्टेक्स्ट दें |

`deny(message)` - संदेश Claude के लिए `"Blocked by failproofai:"` के प्रीफ़िक्स के साथ दिखाई देता है। एक भी `deny` सभी आगे के मूल्यांकन को शॉर्ट-सर्किट करता है।

`instruct(message)` - संदेश को वर्तमान टूल कॉल के लिए Claude के कॉन्टेक्स्ट में जोड़ा जाता है। सभी `instruct` संदेश जमा किए जाते हैं और एक साथ दिए जाते हैं।

<Tip>
`policyParams` में `hint` फील्ड जोड़कर किसी भी `deny` या `instruct` संदेश में अतिरिक्त मार्गदर्शन जोड़ें — कोई कोड परिवर्तन की आवश्यकता नहीं। यह कस्टम (`custom/`), प्रोजेक्ट कन्वेंशन (`.failproofai-project/`), और यूजर कन्वेंशन (`.failproofai-user/`) पॉलिसीज़ के लिए भी काम करता है। विवरण के लिए [Configuration → hint](/hi/configuration#hint-cross-cutting) देखें।
</Tip>

### सूचनात्मक allow संदेश

`allow(message)` ऑपरेशन को **और** Claude को एक सूचनात्मक संदेश भेजने देता है। संदेश को हुक हैंडलर के stdout रेस्पॉंस में `additionalContext` के रूप में दिया जाता है — `instruct` द्वारा उपयोग किए गए समान तंत्र, लेकिन शब्दार्थ रूप से भिन्न: यह एक चेतावनी नहीं, एक स्थिति अपडेट है।

| फंक्शन | प्रभाव | उपयोग करें जब |
|----------|--------|----------|
| `allow(message)` | अनुमति दें और Claude को कॉन्टेक्स्ट भेजें | एक चेक पास होने की पुष्टि करें, या समझाएं कि चेक क्यों छोड़ा गया |

उपयोग के मामले:
- **स्थिति पुष्टि:** `allow("All CI checks passed.")` — Claude को बताता है कि सब कुछ ठीक है
- **फेल-ओपन स्पष्टीकरण:** `allow("GitHub CLI not installed, skipping CI check.")` — Claude को बताता है कि चेक क्यों छोड़ा गया ताकि इसके पास पूर्ण कॉन्टेक्स्ट हो
- **कई संदेश जमा होते हैं:** यदि कई पॉलिसीज़ प्रत्येक `allow(message)` रिटर्न करते हैं, तो सभी संदेश नई पंक्तियों के साथ जोड़े जाते हैं और एक साथ दिए जाते हैं

```js
customPolicies.add({
  name: "confirm-branch-status",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow("No working directory, skipping branch check.");

    // ... branch status जांचें ...
    if (allPushed) {
      return allow("Branch is up to date with remote.");
    }
    return deny("Unpushed changes detected.");
  },
});
```

### `PolicyContext` फील्ड्स

| फील्ड | टाइप | विवरण |
|-------|------|-------------|
| `eventType` | `string` | `"PreToolUse"`, `"PostToolUse"`, `"Notification"`, `"Stop"` |
| `toolName` | `string \| undefined` | कॉल किया जा रहा टूल (जैसे `"Bash"`, `"Write"`, `"Read"`) |
| `toolInput` | `Record<string, unknown> \| undefined` | टूल के इनपुट पैरामीटर |
| `payload` | `Record<string, unknown>` | Claude Code से पूर्ण कच्चा इवेंट पेलोड |
| `session` | `SessionMetadata \| undefined` | सेशन कॉन्टेक्स्ट (नीचे देखें) |

### `SessionMetadata` फील्ड्स

| फील्ड | टाइप | विवरण |
|-------|------|-------------|
| `sessionId` | `string` | Claude Code सेशन पहचानकर्ता |
| `cwd` | `string` | Claude Code सेशन की कार्यशील डायरेक्टरी |
| `transcriptPath` | `string` | सेशन की JSONL ट्रांसक्रिप्ट फाइल का पथ |

### इवेंट टाइप्स

| इवेंट | कब फायर होता है | `toolInput` कंटेंट्स |
|-------|--------------|----------------------|
| `PreToolUse` | Claude एक टूल चलाने से पहले | टूल का इनपुट (जैसे Bash के लिए `{ command: "..." }`) |
| `PostToolUse` | एक टूल पूरा होने के बाद | टूल का इनपुट + `tool_result` (आउटपुट) |
| `Notification` | जब Claude एक नोटिफिकेशन भेजता है | `{ message: "...", notification_type: "idle" \| "permission_prompt" \| ... }` - हुक्स को हमेशा `allow()` रिटर्न करना चाहिए, वे नोटिफिकेशन को ब्लॉक नहीं कर सकते |
| `Stop` | जब Claude सेशन समाप्त होता है | खाली |

## मूल्यांकन ऑर्डर

पॉलिसीज़ का मूल्यांकन इसी ऑर्डर में किया जाता है:

1. बिल्ट-इन पॉलिसीज़ (परिभाषा ऑर्डर में)
2. `customPoliciesPath` से स्पष्ट कस्टम पॉलिसीज़ (`.add()` ऑर्डर में)
3. प्रोजेक्ट `.failproofai/policies/` से कन्वेंशन पॉलिसीज़ (फाइलें वर्णमाला, `.add()` ऑर्डर में)
4. यूजर `~/.failproofai/policies/` से कन्वेंशन पॉलिसीज़ (फाइलें वर्णमाला, `.add()` ऑर्डर में)

<Note>
पहला `deny` सभी बाद की पॉलिसीज़ को शॉर्ट-सर्किट करता है। सभी `instruct` संदेश जमा किए जाते हैं और एक साथ दिए जाते हैं।
</Note>

## ट्रांजिटिव इंपोर्ट्स

कस्टम पॉलिसी फाइलें सापेक्ष पथों का उपयोग करके स्थानीय मॉड्यूल को इंपोर्ट कर सकती हैं:

```js
// my-policies.js
import { isBlockedPath } from "./utils.js";
import { checkApproval } from "./approval-client.js";

customPolicies.add({
  name: "approval-gate",
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const approved = await checkApproval(ctx.toolInput?.command, ctx.session?.sessionId);
    return approved ? allow() : deny("Approval required for this command");
  },
});
```

एंट्री फाइल से पहुंचने योग्य सभी सापेक्ष इंपोर्ट्स रिज़ॉल्व किए जाते हैं। यह `from "failproofai"` इंपोर्ट्स को वास्तविक dist पथ में फिर से लिखकर और ESM संगतता सुनिश्चित करने के लिए अस्थायी `.mjs` फाइलें बनाकर लागू किया जाता है।

## इवेंट टाइप फ़िल्टरिंग

`match.events` का उपयोग करके सीमित करें कि एक पॉलिसी कब फायर होती है:

```js
customPolicies.add({
  name: "require-summary-on-stop",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    // केवल तब फायर होता है जब सेशन समाप्त होता है
    // ctx.session.transcriptPath में पूर्ण सेशन लॉग होता है
    return allow();
  },
});
```

हर इवेंट टाइप पर फायर करने के लिए `match` को पूरी तरह छोड़ें।

## त्रुटि प्रबंधन और विफलता मोड

कस्टम पॉलिसीज़ **फेल-ओपन** हैं: त्रुटियां कभी भी बिल्ट-इन पॉलिसीज़ को ब्लॉक नहीं करती या हुक हैंडलर को क्रैश नहीं करती।

| विफलता | व्यवहार |
|---------|----------|
| `customPoliciesPath` सेट नहीं है | कोई स्पष्ट कस्टम पॉलिसीज़ नहीं चलती; कन्वेंशन पॉलिसीज़ और बिल्ट-इन सामान्य रूप से जारी रहती हैं |
| फाइल नहीं मिली | `~/.failproofai/hook.log` में चेतावनी लॉग की गई; बिल्ट-इन जारी रहती हैं |
| सिंटैक्स/इंपोर्ट त्रुटि (स्पष्ट) | `~/.failproofai/hook.log` में त्रुटि लॉग की गई; स्पष्ट कस्टम पॉलिसीज़ छोड़ दी गई |
| सिंटैक्स/इंपोर्ट त्रुटि (कन्वेंशन) | त्रुटि लॉग की गई; वह फाइल छोड़ दी गई, अन्य कन्वेंशन फाइलें अभी भी लोड होती हैं |
| `fn` रनटाइम पर थ्रो करता है | त्रुटि लॉग की गई; वह हुक `allow` के रूप में माना जाता है; अन्य हुक्स जारी रहते हैं |
| `fn` 10s से अधिक समय लेता है | टाइमआउट लॉग किया गया; `allow` के रूप में माना गया |
| कन्वेंशन डायरेक्टरी गायब | कोई कन्वेंशन पॉलिसीज़ नहीं चलती; कोई त्रुटि नहीं |

<Tip>
कस्टम पॉलिसी त्रुटियों को डीबग करने के लिए, लॉग फाइल को देखें:

```bash
tail -f ~/.failproofai/hook.log
```
</Tip>

## पूर्ण उदाहरण: कई पॉलिसीज़

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

// एजेंट को secrets/ डायरेक्टरी में लिखने से रोकें
customPolicies.add({
  name: "block-secrets-dir",
  description: "Prevent agent from writing to secrets/ directory",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("secrets/")) return deny("Writing to secrets/ is not permitted");
    return allow();
  },
});

// एजेंट को सही ट्रैक पर रखें: कमिटिंग से पहले टेस्ट करें
customPolicies.add({
  name: "remind-test-before-commit",
  description: "Keep the agent on track: verify tests pass before committing",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    if (/git\s+commit/.test(cmd)) {
      return instruct("Verify all tests pass before committing. Run `bun test` if you haven't already.");
    }
    return allow();
  },
});

// फ्रीज़ के दौरान अनियोजित निर्भरता परिवर्तनों को रोकें
customPolicies.add({
  name: "dependency-freeze",
  description: "Prevent unplanned dependency changes during freeze period",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    const isInstall = /^(npm install|yarn add|bun add|pnpm add)\s+\S/.test(cmd);
    if (isInstall && process.env.DEPENDENCY_FREEZE === "1") {
      return deny("Package installs are frozen. Unset DEPENDENCY_FREEZE to allow.");
    }
    return allow();
  },
});

export { customPolicies };
```

## उदाहरण

`examples/` डायरेक्टरी में तैयार-टू-रन पॉलिसी फाइलें हैं:

| फाइल | कंटेंट्स |
|------|----------|
| `examples/policies-basic.js` | पांच स्टार्टर पॉलिसीज़ जो सामान्य एजेंट विफलता मोड को कवर करती हैं |
| `examples/policies-advanced/index.js` | उन्नत पैटर्न: ट्रांजिटिव इंपोर्ट्स, async कॉल्स, आउटपुट स्क्रबिंग, और सेशन-एंड हुक्स |
| `examples/convention-policies/security-policies.mjs` | कन्वेंशन-आधारित सुरक्षा पॉलिसीज़ (.env लिखता है ब्लॉक करें, git इतिहास को फिर से लिखने से रोकें) |
| `examples/convention-policies/workflow-policies.mjs` | कन्वेंशन-आधारित वर्कफ़्लो पॉलिसीज़ (टेस्ट रिमाइंडर्स, फाइल राइट्स ऑडिट करें) |

### स्पष्ट फाइल उदाहरणों का उपयोग करना

```bash
failproofai policies --install --custom ./examples/policies-basic.js
```

### कन्वेंशन-आधारित उदाहरणों का उपयोग करना

```bash
# प्रोजेक्ट लेवल पर कॉपी करें
mkdir -p .failproofai/policies
cp examples/convention-policies/*.mjs .failproofai/policies/

# या यूजर लेवल पर कॉपी करें
mkdir -p ~/.failproofai/policies
cp examples/convention-policies/*.mjs ~/.failproofai/policies/
```

कोई इंस्टॉल कमांड की आवश्यकता नहीं — फाइलें अगले हुक इवेंट पर स्वचालित रूप से उठाई जाती हैं।
