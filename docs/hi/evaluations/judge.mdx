एक hosted Python evaluation गिना और तुलना कर सकता है: कितने tool calls, कितनी errors, एक सत्र कितने समय तक चला। यह आपको यह नहीं बता सकता कि जवाब *सही* था या नहीं, जवाब अशिष्ट था या नहीं, या agent ने कार्य करने से पहले किसी नीति की जांच की या नहीं।

एक **LLM judge** कर सकता है। आप सादे भाषा में वर्णन करते हैं कि अच्छा क्या दिखता है, और एक मॉडल सत्र को पढ़ता है और अपने तर्क के साथ 0 से 1 तक का स्कोर देता है।

<Note>
एक judge प्रत्येक सत्र के लिए एक मॉडल कॉल खर्च करता है जिस पर वह चलता है, और एक code evaluation कुछ भी खर्च नहीं करता। judge का उपयोग केवल उन प्रश्नों के लिए करें जिन्हें बातचीत को *समझने* की आवश्यकता है — और इसे एक condition दें, ताकि यह केवल उन सत्रों पर चले जिनके बारे में प्रश्न वास्तव में है।
</Note>

## मुझे कौन सा चाहिए?

| प्रश्न | उपयोग करें |
| --- | --- |
| क्या यह एक ही tool को दो बार call करता है? | code |
| कितनी errors थीं? | code |
| क्या सत्र 30 सेकंड से कम था? | code |
| क्या customer ने तत्परता व्यक्त की? | [classifier](/hi/evaluations/jev) |
| Customer कितना निराश था? | [classifier](/hi/evaluations/jev) |
| क्या उत्तर वास्तव में सही था? | **judge** |
| क्या जवाब अशिष्ट या खारिज करने वाला था? | **judge** |
| क्या इसने refund policy की जांच की थी इससे पहले कि refund का वादा करे? | **judge** |

अंगूठे का नियम: **गिनती योग्य → code, उत्तर जो आप पहले से सूचीबद्ध कर सकते हैं → [classifier](/hi/evaluations/jev), व्याख्या की आवश्यकता है → judge।** Judge वह है जो लिखता है कि उसने क्या देखा; इसे तब लें जब संख्या से कोई पूछे "क्यों?"।

आपको पहले से फैसला करना नहीं है। वर्णन करें कि आप क्या मापना चाहते हैं और assistant चुनता है, फिर बताता है कि इसने क्या चुना और क्यों। आप इसे स्विच कर सकते हैं।

## एक बनाएं

1. **Analyze → eval authoring** पर जाएं और **new eval** चुनें।
2. वर्णन करें कि आप क्या judge करना चाहते हैं, और **draft** चुनें।
3. **criteria**, **threshold**, और **condition** की समीक्षा करें, फिर deploy करें।

### Criteria

एक या दो वाक्य, एक सवाल के बजाय आवश्यकता के रूप में लिखे गए:

> Assistant को बिना पहले refund policy की जांच किए refund का वादा या approval नहीं देना चाहिए।

विशेष रूप से बताएं कि क्या इसे *fail* करेगा। "क्या प्रतिक्रिया अच्छी थी?" आपको एक संख्या देता है जिसका कोई मतलब नहीं है; ऊपर का वाक्य आपको एक देता है जिस पर आप कार्य कर सकते हैं।

### Threshold

वह स्कोर जिस पर या उससे ऊपर सत्र pass करता है। `0.7` एक समझदारी भरी शुरुआत है। पूरा 0-से-1 स्कोर हमेशा store रहता है, इसलिए threshold केवल pass/fail तय करता है — आप distribution देख सकते हैं और adjust कर सकते हैं।

### Condition

किसी भी अन्य evaluation जैसी ही Python condition, और यह यहां बहुत अधिक मायने रखता है। इसके बिना, judge आपके organization के **हर** सत्र पर चलता है, प्रत्येक पर एक मॉडल कॉल:

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

Dashboard आपको चेतावनी देता है यदि आप कोई judge बिना condition के deploy करते हैं। यह कभी-कभी सही है — एक low-volume agent जिसे आप पूरी तरह judge करना चाहते हैं — लेकिन यह एक निर्णय होना चाहिए, दुर्घटना नहीं।

## Judge क्या देखता है

बातचीत, turns के रूप में, यदि सत्र लंबा है तो newest-first:

- user ने क्या कहा
- assistant ने क्या जवाब दिया
- **agent ने हर tool को call किया, और वह call क्या return करता था, क्रम में**

वह आखिरी हिस्सा है जो "क्या यह X *से पहले* Y किया" को एक उचित सवाल बनाता है। एक failed tool call को failure के रूप में दिखाया जाता है, इसलिए "क्या इसने एक error से gracefully recover किया" भी काम करता है।

बहुत लंबे सत्रों को मॉडल के context में फिट करने के लिए truncate किया जाता है। जब ऐसा होता है तो reasoning स्पष्ट रूप से कहती है — आप कभी भी ऐसा judgment नहीं देखेंगे जो सत्र के एक हिस्से पर किया गया हो लेकिन पूरे पर किया गया हो।

## परिणाम पढ़ना

एक judge किसी भी अन्य scored evaluation जैसी एक **score** तैयार करता है, इसलिए यह charts, filters, और alerts trigger करता है उसी तरह। संख्या के साथ यह judge की **reasoning** store करता है — वह paragraph जो समझाता है कि इसने क्या देखा। जब कोई score आपको आश्चर्यचकित करे तो पहले वह पढ़ें; यह आमतौर पर या तो एक वास्तव में दिलचस्प सत्र है या एक संकेत है कि criteria को तीव्र करने की आवश्यकता है।

स्पष्ट cases के लिए scores स्थिर हैं लेकिन bit-for-bit deterministic नहीं। एक single borderline score को session पढ़ने के लिए एक संकेत के रूप में treat करें, verdict के रूप में नहीं।

## सीमाएं

- **Testing अभी तक उपलब्ध नहीं है।** एक dry run के पीछे कोई session assignment नहीं है, और वह assignment है जो आपके मॉडल budget को खर्च करने को authorize करता है — इसलिए एक test call के लिए charge करने के लिए कुछ भी नहीं है। एक narrow condition के विरुद्ध deploy करें और पहले कुछ परिणाम पढ़ें।
- **Backfill उपलब्ध नहीं है।** महीनों के इतिहास पर code evaluation को backfill करना free है; इसे judge के साथ करना आपके पूरे budget को मिनटों में खर्च करेगा।
- **Criteria को edit करना एक नया version publish करता है।** पुराने और नए scores comparable नहीं हैं, इसलिए उन्हें एक trend line में मिलाने के बजाय अलग रखा जाता है।
- **एक judge हमेशा एक score produce करता है**, कभी एक metric या एक assertion नहीं।

## जब आपका budget समाप्त हो जाता है

Judges आपके organization के मॉडल budget को खर्च करते हैं। जब यह समाप्त हो जाता है, judge evaluations एक स्पष्ट कारण के साथ बंद हो जाते हैं silently fail करने के बजाय, और **code evaluations सामान्य रूप से चलते रहते हैं**। Budget बढ़ाएं और वे अगले सत्र पर resume करते हैं।
