एक hosted Python evaluation गिन सकता है और तुलना कर सकता है: कितने tool calls, कितनी errors, एक session कितने समय तक चली। यह आपको नहीं बता सकता कि क्या एक answer *सही* था, क्या एक reply रude था, या क्या एजेंट ने कार्य करने से पहले एक नीति check की।

एक **LLM judge** कर सकता है। आप plain language में यह बताते हैं कि अच्छा क्या दिखता है, और एक मॉडल session को पढ़ता है और 0 से 1 तक एक score अपने reasoning के साथ return करता है।

<Note>
एक judge हर session पर एक model call का खर्च करता है जिस पर वह चलता है, और एक code evaluation कुछ भी खर्च नहीं करता। एक judge का उपयोग केवल उन सवालों के लिए करें जिनमें conversation को *समझने* की जरूरत है — और इसे एक condition दें, ताकि यह उन sessions पर चले जिनका सवाल वास्तव में है।
</Note>

## मुझे कौन सा चाहिए?

| सवाल | उपयोग करें |
| --- | --- |
| क्या इसने एक ही tool को दो बार call किया? | code |
| कितनी errors थीं? | code |
| क्या session 30 सेकंड के अंदर था? | code |
| क्या customer ने आपातकालीनता व्यक्त की? | [classifier](/hi/evaluations/jev) |
| Customer कितना frustrated था? | [classifier](/hi/evaluations/jev) |
| क्या answer वास्तव में सही था? | **judge** |
| क्या reply rude या dismissive था? | **judge** |
| क्या इसने refund देने का वादा करने से पहले refund policy check की? | **judge** |

अंगूठे का नियम: **गिनती योग्य → code, जवाब जो आप आगे सूची में दे सकते हैं → [classifier](/hi/evaluations/jev), व्याख्या की जरूरत है → judge।** एक judge वह है जो उसने जो देखा उसके बारे में prose लिखता है; इसका उपयोग तब करें जब संख्या किसी को "क्यों?" पूछने के लिए प्रेरित करेगी।

आपको आगे से निर्णय लेने की जरूरत नहीं है। बताएं कि आप क्या मापना चाहते हैं और सहायक चुनता है, फिर आपको बताता है कि इसने क्या चुना और क्यों। आप इसे switch कर सकते हैं।

## एक लिखें

1. **Analyze → eval authoring** पर जाएं और **new eval** चुनें।
2. बताएं कि आप क्या judge करना चाहते हैं, और **draft** चुनें।
3. **criteria**, **threshold**, और **condition** की समीक्षा करें, फिर deploy करें।

### Criteria

एक या दो वाक्य, एक प्रश्न के बजाय एक आवश्यकता के रूप में लिखे गए:

> सहायक को refund का वादा या approval बिना पहले refund policy check किए नहीं देना चाहिए।

विशिष्ट रहें कि क्या इसे *fail* करेगा। "क्या response अच्छा था?" आपको एक संख्या देता है जिसका कोई मतलब नहीं है; ऊपर वाला वाक्य आपको एक देता है जिस पर आप कार्य कर सकते हैं।

### Threshold

वह score जिस पर या जिससे ऊपर session pass करता है। `0.7` एक sensible शुरुआती बिंदु है। पूरा 0-से-1 score हमेशा stored रहता है, इसलिए threshold केवल pass/fail decide करता है — आप distribution देख सकते हैं और adjust कर सकते हैं।

### Condition

किसी भी अन्य evaluation के जैसा ही Python condition, और यह यहां कहीं अधिक मायने रखता है। इसके बिना, judge आपके संगठन के **every** session पर चलता है, हर एक पर एक model call:

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

यदि आप एक judge को कोई condition के बिना deploy करते हैं तो dashboard आपको चेतावनी देता है। यह कभी-कभी सही है — एक low-volume agent जिसे आप पूरी तरह judge करना चाहते हैं — लेकिन यह एक निर्णय होना चाहिए, एक accident नहीं।

## Judge क्या देखता है

Conversation, turns के रूप में, newest-first यदि session लंबा है:

- user ने क्या कहा
- assistant ने क्या reply दिया
- **हर tool जो agent ने call किया, और वह call क्या return हुआ, order में**

वह आखिरी हिस्सा ही है जो "क्या इसने X को Y से *पहले* किया" को एक fair सवाल बनाता है। एक failed tool call failure के रूप में दिखाया जाता है, इसलिए "क्या यह एक error से gracefully recover हुआ" भी काम करता है।

बहुत लंबे sessions को मॉडल के context में fit करने के लिए truncate किया जाता है। जब ऐसा होता है तो reasoning explicitly कहती है — आप कभी भी एक session के हिस्से पर किया गया judgement पूरे पर किए गए के रूप में प्रस्तुत नहीं देखेंगे।

## नतीजे पढ़ना

एक judge एक **score** produce करता है जैसे कोई अन्य scored evaluation, इसलिए यह chart, filter, और alert trigger उसी तरह करता है। संख्या के साथ यह judge का **reasoning** store करता है — वह paragraph जो व्याख्या करता है कि उसने क्या देखा। जब एक score आपको आश्चर्य चकित करे तो पहले वह पढ़ें; यह आमतौर पर तो एक genuinely interesting session है या एक sign है कि criteria को sharpen करने की जरूरत है।

Scores स्पष्ट-कट cases के लिए stable हैं लेकिन bit-for-bit deterministic नहीं हैं। एक single borderline score को session जाने और पढ़ने के लिए एक prompt के रूप में treat करें, एक verdict के रूप में नहीं।

## सीमाएं

- **Testing अभी उपलब्ध नहीं है।** एक dry run के पीछे कोई session assignment नहीं है, और वह assignment ही है जो आपकी model budget खर्च करने को authorize करता है — इसलिए एक test call के लिए charge करने के लिए कुछ नहीं है। एक narrow condition के विरुद्ध deploy करें और पहले कुछ results पढ़ें।
- **Backfill उपलब्ध नहीं है।** महीनों के history पर एक code evaluation को backfill करना free है; इसे एक judge के साथ करना आपके पूरे budget को minutes में खर्च करेगा।
- **Criteria को edit करने से एक नया version publish होता है।** पुराने और नए scores तुलनीय नहीं हैं, इसलिए उन्हें एक trend line में mixed होने के बजाय अलग रखा जाता है।
- **एक judge हमेशा एक score produce करता है**, कभी metric या assertion नहीं।

## जब आपका budget ख़त्म हो जाए

Judges आपके संगठन के model budget खर्च करते हैं। जब यह exhausted है, judge evaluations एक clear reason के साथ stop करते हैं बजाय silently fail के, और **code evaluations normally चलते रहते हैं**। Budget बढ़ाएं और वे अगले session पर resume करते हैं।
