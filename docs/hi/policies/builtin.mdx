अंतर्निर्मित नीतियां 39 रखी गई नीतियां हैं जो एजेंट की विफलता की नौ श्रेणियों को कवर करती हैं। एक को छोड़कर सभी **एक पैक के रूप में दिए जाते हैं**, `FailproofAI/policies`, जिस तरह से कोई भी और नीतियां दी जाती हैं। पैकेज अपना कोई पैक नहीं भेजता है, इसलिए एक नई स्थापना तब तक कुछ भी लागू नहीं करती जब तक आप इसे न लें:

```bash
failproofai policies add FailproofAI/policies
```

यह पैक की अपनी डिफ़ॉल्ट सेटिंग्स चालू करता है — पैक की 38 नीतियों में से 10। 39वीं है `block-failproofai-commands`, जो वैसे भी चालू है: यह पैकेज में संकलित होकर आता है, हर मूल्यांकन पर रजिस्टर होता है, और इसे अक्षम या रोका नहीं जा सकता। एक पैक `alwaysOn` घोषित नहीं कर सकता, यही वजह है कि वह सुरक्षा पैक लेन से नहीं जाती।

## नौ श्रेणियां क्या कवर करती हैं

| श्रेणी | `--category` स्लग | नीतियां |
| --- | --- | --- |
| Sanitize | `sanitize` | 5 |
| Environment | `environment` | 3 |
| Dangerous Commands | `dangerous-commands` | 5 |
| Infra Commands | `infra-commands` | 7 |
| Git | `git` | 6 |
| Database | `database` | 2 |
| Packages & System | `packages-system` | 5 |
| AI Behavior | `ai-behavior` | 1 |
| Workflow | `workflow` | 5 |

ये संकलित कैटलॉग की संख्याएं हैं, और वे कुल 39 हैं। पैक उनमें से 38 ले जाता है, क्योंकि `block-failproofai-commands` `alwaysOn` है और पैक लेन से कभी नहीं जाता है — इसलिए `--category dangerous-commands` अन्य चार को चुनता है।

डिफ़ॉल्ट के बजाय एक स्लाइस लें:

```bash
failproofai policies add FailproofAI/policies --category git,database
failproofai policies add FailproofAI/policies --policy block-rm-rf
failproofai policies add FailproofAI/policies --all
```

## एक को चालू या बंद करें

```bash
failproofai policies add block-rm-rf --cli claude --scope project
failproofai policies remove block-rm-rf --cli claude --scope project
```

`policies add` और `policies remove` बिल्कुल **एक** नीति का नाम लेते हैं। उन्हें कोई नाम दिए बिना चलाएं और आपको एक पिकर मिलता है, जिसमें जो पहले से चालू है वह टिक होता है। एक साथ कई नामों के लिए, इंस्टॉल फॉर्म का उपयोग करें:

```bash
failproofai policies --install block-sudo block-force-push \
  --cli claude codex --scope project
```

<Note>
  एक मशीन पर कोई पैक स्थापित न होने के साथ, `failproofai policies add <builtin-name>` नाम को संतुष्ट करने के लिए इसके GitHub रिलीज़ से `FailproofAI/policies` लाता है — इसलिए पहली कमांड को नेटवर्क की आवश्यकता है।
</Note>

## प्रत्येक नीति हर हार्नेस पर लागू नहीं होती

एक नीति केवल व्यवहार को बदलती है जहां हार्नेस अपने इवेंट के लिए फैसले का उपभोग करता है। आपके द्वारा एक अंतर्निर्मित पर भरोसा करने से पहले दो मामले जांचने योग्य हैं:

| इवेंट | जहां एक deny को व्यवहार में परिवर्तन सत्यापित किया गया है |
| --- | --- |
| `PreToolUse` | सभी 12 हार्नेस |
| `Stop` | claude, codex, copilot, cursor, openclaw, factory, devin, antigravity। goose या hermes पर कोई `Stop` हुक स्थापित नहीं है, pi कारण को अगले मोड़ में ले जाता है, और opencode सत्यापित नहीं है |

तो Workflow श्रेणी में पांच `require-*-before-stop` नीतियों को एक मशीन पर सक्षम किया जा सकता है और फिर भी कभी नहीं चल सकता है, इस पर निर्भर करता है कि कौन सा एजेंट वहां चलता है। Cursor Cloud Agent VMs बिल्कुल कोई stop हुक नहीं चलाते।

`warn-*` और `prefer-*` नीतियां `deny` के बजाय `instruct` लौटाती हैं। Hermes और Goose पर, और Pi, OpenClaw, Factory और Antigravity पर `Stop` चैनल के बाहर, `instruct` allow plus stderr पर एक नोट में घट जाता है: ऑपरेटर इसे लॉग में देखता है, एजेंट नहीं।

कुछ नीतियां पैरामीटर स्वीकार करती हैं। विवरण की समीक्षा करें, रोलआउट से पहले स्कोप और डिफ़ॉल्ट से मेल खाएं — एक नीति जो एक वर्कफ़्लो की सुरक्षा करती है वह दूसरे में वैध संचालन को ब्लॉक कर सकती है।
