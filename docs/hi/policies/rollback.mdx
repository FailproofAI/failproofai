रोलबैक तैनात संस्करण को बदलता है या नीति असाइनमेंट को हटाता है; यह निर्णय इतिहास को मिटाता नहीं है जो घटना की व्याख्या करता है।

## मशीन को रोल बैक करें

<Tabs>
  <Tab title="Dashboard">
    1. **Admin → enforcement** पर जाएं, प्रभावित मशीन को विस्तृत करें, और इसके अंतिम ज्ञात-अच्छी नीति सेट की पहचान करें।
    2. **edit** का चयन करें, उन संस्करणों और प्रभावों को पुनः स्थापित करें, और नई तैनाती लागू करें।
    3. मशीन चेक-इन के लिए प्रतीक्षा करें, फिर रिपोर्ट की गई तैनाती को सत्यापित करें।
    4. **Observe → policy** खोलें और प्रभावित सेशन को खोलकर पुष्टि करें कि वैध कार्य अब अवरुद्ध नहीं है।

  </Tab>
  <Tab title="CLI">
    उस पीढ़ी को खोजें जिसमें वापस जाना है, इसे पुनः स्थापित करें, फिर पुष्टि करें कि यह लागू हुई:

    ```bash
    fp fleet history ci-runner-01
    fp fleet rollback ci-runner-01 3
    fp fleet diff ci-runner-01
    failproofai config --status
    ```

    `fp fleet rollback` काउंटर को वापस घुमाने के बजाय पुराने सेट को ले जाने वाली एक **नई** पीढ़ी बनाता है, इसलिए इतिहास केवल जोड़ने वाला रहता है। यह अस्वीकार कर देता है यदि वह पीढ़ी एक ऐसी नीति का नाम देती है जो तब से अक्षम या हटा दी गई है — सर्वर ऐसा कहता है कि एक सेट को पुनः स्थापित करने के बजाय जो वितरित नहीं किया जा सकता।

    `fp fleet diff` आशय बनाम वितरण दिखाता है। एक मशीन तब तक विचलित के रूप में पढ़ी जाती है जब तक वह अगली बार पोल न करे, इसलिए यह निष्कर्ष निकालने से पहले diff को देखें कि रोलबैक नहीं हुआ। `failproofai config --status` इसे मशीन पर ही पुष्टि करता है।
  </Tab>
</Tabs>

## पॉज़ रोलबैक नहीं है

पॉज़ **एक सेशन** के लिए प्रत्येक स्थानीय रूप से स्थापित नीति को निलंबित करता है, और हमेशा स्वयं समाप्त हो जाता है — पैक, कस्टम फाइलें, कन्वेंशन फाइलें और बिल्टइन सभी। केवल Cloud-प्रबंधित नीतियां और हमेशा-चालू `block-failproofai-commands` गार्ड लागू रहते हैं। तो पॉज़ एक खराब Cloud तैनाती के लिए एक समाधान नहीं है, और यह इससे अधिक व्यापक प्रभाव त्रिज्या है जितना यह दिखता है: एक पैक वह जगह है जहां अनिवार्य रूप से सभी स्थानीय प्रवर्तन रहते हैं, और पैक फेल-क्लोज गार्ड अवधि के लिए छोड़ दिया जाता है।

| कमांड | प्रभाव |
|---|---|
| `failproofai config --pause` | इस निर्देशिका का सबसे नया एजेंट सेशन, 30 मिनट के लिए |
| `failproofai config --pause 10m` | एक दिया गया समय। अधिकतम 8h; `s`/`m`/`h` प्रत्यय, नंगी संख्या का मतलब मिनट है |
| `failproofai config --pause --session <id>` | एक विशिष्ट सेशन को लक्षित करें |
| `failproofai config --resume` | पॉज़ को जल्दी समाप्त करें |
| `failproofai config --resume --all` | हर सक्रिय पॉज़ को समाप्त करें |
| `failproofai config --status` | क्या पॉज़ है, और यह कब उठेगा |

## कब रोल बैक करें

- एक नीति एक अपेक्षित उत्पादन कार्य को अवरुद्ध करती है।
- मैच वॉल्यूम देखी गई रोलआउट की भविष्यवाणी से काफी अधिक है।
- एक नीति उन फ़ील्ड पर निर्भर करती है जो एक एकीकरण प्रदान नहीं करता है।
- एक नया संस्करण इच्छित विफलता मोड के बाहर व्यवहार बदलता है।

रोलबैक के बाद, प्रभावित सेशन खोलें और उस स्थिति की पहचान करें जिसने गलत सकारात्मक का कारण बना। एक नया संस्करण बनाएं, दोनों असुरक्षित और वैध मामले को स्थानीय रूप से परीक्षण करें, फिर पुनः observe के माध्यम से जाएं इससे पहले कि आप फिर से लागू करें:

```bash
fp policies test ./policy.mjs --tool Bash --command '<the legitimate case>' --expect allow
fp policies publish my-policy ./policy.mjs
fp fleet deploy ci-runner-01 --add my-policy:observe
fp guardrails summary --since 24h --machine ci-runner-01
```

`:observe` वह है जो इसे एक shadow रोलआउट बनाता है। एक नंगा `fp fleet deploy ... --add my-policy` **तुरंत लागू करता है** — एक छोड़ा गया प्रभाव पहले से तैनात प्रभाव को हल करता है, और फिर `enforce` को — जो एक नीति पर आप ने अभी रोल बैक किया है का मतलब घटना को फिर से स्थापित करना है। Observe मोड अभी भी नीति को वास्तविक के लिए मूल्यांकन करता है और हर गैर-allow निर्णय रिकॉर्ड करता है; केवल प्रवर्तन रोका जाता है, इसलिए `fp guardrails summary` नई पीढ़ी को समान ट्रैफिक के विरुद्ध मापता है जो पुराने पर टूट गया था। `--add my-policy:enforce` के साथ प्रचार करें जब संख्याएं ऐसा कहें।

<Warning>
  प्रवर्तन को पॉज़ करना एक घटना के दौरान उपयुक्त हो सकता है, लेकिन यह उस स्कोप में हर सक्रिय नीति के लिए एक्सपोजर को चौड़ा करता है। जब संभव हो विशिष्ट नीति संस्करण को रोल बैक करना पसंद करें।
</Warning>
