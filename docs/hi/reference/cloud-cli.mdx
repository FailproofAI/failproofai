`fp` का उपयोग Cloud telemetry को inspect करने, cloud-managed enforcement (policies, fleet deployments, guardrail decisions) को प्रबंधित करने, और audits, findings, issues, alerts, keys, users, queries, और settings को प्रबंधित करने के लिए करें। local hooks, policies, capture, और machine enrollment के लिए [`failproofai`](/hi/reference/failproof-cli) का उपयोग करें।

Cloud CLI को एक isolated tool के रूप में install करें। इसे Python 3.10 या नए संस्करण की आवश्यकता है।

```bash
uv tool install fp-cloud-cli
fp version
```

distribution `fp-cloud-cli` है और installed command `fp` है — ये अलग हैं क्योंकि `fp` पहले से ही PyPI पर लिया गया था।

## Sign in

`fp login` आपको एक छः अंकीय कोड email करता है और session को save करता है। self-signed certificate वाले dashboard के विरुद्ध, login समय पर `--insecure` जोड़ें।

```bash
fp login
fp whoami
```

## Syntax

```text
fp [GLOBAL_OPTIONS] COMMAND [SUBCOMMAND] [ARGUMENTS] [OPTIONS]
```

Global options को command से पहले आना चाहिए:

```bash
fp --json sessions --since 24h
```

Terminal help के लिए `fp COMMAND --help` या `fp COMMAND SUBCOMMAND --help` चलाएं।

### Events

```text
fp events [OPTIONS]
```

Individual agent events को list करता है। Default light feed raw payloads को exclude करता है; bounded investigation के लिए `--full` का उपयोग करें।

| Option | Description |
| --- | --- |
| `--limit`, `-n <n>` | Maximum total rows। Default: `50`। |
| `--since <window>` | `all`, `15m`, `1h`, `6h`, `24h`, या `7d`। |
| `--from <timestamp>` / `--to <timestamp>` | ISO 8601 UTC range; `--since` को override करता है। |
| `--env <value>` | Environment filter; repeat या comma-separate values। |
| `--event-type <value>` | Event-type filter; repeat या comma-separate values। |
| `--agent-id <value>` | Agent filter; repeat या comma-separate values। |
| `--session-id <value>` | Session filter; repeat या comma-separate values। |
| `--search <text>` | Payload text search; repeatable, किसी भी term के साथ matching। |
| `--order asc\|desc` | Time order। Default: newest first। |
| `--all` | Auto-paginate up to `--limit`। |
| `--cursor <token>` | Opaque cursor से resume करें। |
| `--page-size <n>` | `--all` के साथ rows per request; maximum `200`। |
| `--full` | Heavier event endpoint के माध्यम से raw payloads शामिल करें। |
| `--fields <csv>` | केवल selected fields return करें; `payload` को request करने से full mode enable होता है। |

```bash
fp events --session-id <session-id> --order asc --all --limit 10000
fp --json events --full --session-id <session-id> --all --limit 10000
```

<Note>
  `--all` **up to `--limit`** को paginate करता है, जो **50** के लिए defaults — तो `--all` अकेले 50 rows पर रुकता है। जब यह जल्दी रुकता है तो response एक `next_cursor` ले जाता है जहां से resume किया जा सकता है; `"next_cursor": null` मतलब feed वाकई exhausted था।
</Note>

#### Audit create options

```bash
fp audits create checkout-reliability \
  --description "Find checkout failures that agents do not recover from" \
  --scope '{"environments":["production"],"agent_ids":["checkout-agent"]}' \
  --schedule-interval-secs 86400 \
  --window-mode since_last \
  --sensitivity medium \
  --text-file ./checkout-audit-brief.txt \
  --url https://runbooks.example.com/checkout
```

| Option | Description |
| --- | --- |
| `--file <path>` | Definition को JSON पर base करें, या stdin के लिए `-` का उपयोग करें। Explicit flags file values को override करते हैं। |
| `--description <text>` | Failure question या purpose को state करें। |
| `--enabled` / `--disabled` | Scheduling को on या off पर start करें। Default: enabled। |
| `--schedule-interval-secs <n>` | `3600`–`604800`। Default: `86400`। |
| `--schedule-anchor <timestamp>` | Fixed UTC phase ISO 8601 form में। Default: next 09:00 UTC। |
| `--window-mode since_last\|fixed` | Last fully analyzed window के बाद continue करें या rolling window को repeatedly inspect करें। Default: `since_last`। |
| `--lookback-window-secs <n>` | `3600`–`7776000`। Default: `604800`। |
| `--scope '<json>'` | `environments`, `agent_ids`, या other supported scope fields द्वारा filter करें। |
| `--ignore-error-type <type>` | Error types को exclude करें; repeat या comma-separate। |
| `--llm` / `--no-llm` | Agentic analysis को enable या disable करें। Default: enabled। |
| `--top-k <n>` | `1`–`500` findings को retain करें। Default: `50`। |
| `--sensitivity low\|medium\|high` | Reporting sensitivity को set करें। Default: `medium`। |
| `--channels '<json>'` | Notification channel array। |
| `--text <brief>` | Inline brief, maximum 8,192 characters। |
| `--text-file <path>` | File से brief को read करें; `--text` के साथ mutually exclusive। |
| `--url <https-url>` | Public HTTPS reference को add करें; up to five times repeat करें। |

Creation के दौरान context को शामिल करें जब first run को इसकी आवश्यकता हो। Creation definition और context को queued run शुरू होने से पहले commit करता है।

<Note>
  `fp audits run` asynchronous है। Latest run succeed या fail होने से पहले `fp audits runs NAME` को poll करें इससे पहले कि उसके findings को read करें।
</Note>

### Policies

Cloud-managed policy versions। **Session-only** — यहां हर command except `fp policies test` एक API key के तहत `2` exit करता है, किसी भी request से पहले, क्योंकि ये deliberately absent हैं root-only write routes `/v1` से। `fp policies test` deliberate exception है: यह पूरी तरह से locally `node` के विरुद्ध चलता है और कोई server से बात नहीं करता है, तो न ही auth requirement रहता है न ही key-mode refusal और यह logged out और API key के तहत दोनों काम करता है।

| Command | Purpose | Options |
| --- | --- | --- |
| `fp policies list` | Policy versions को list करें, newest of each policy पहले। | — |
| `fp policies show POLICY_ID` | एक policy अपने source के साथ दिखाएं। | — |
| `fp policies publish POLICY_ID [SOURCE]` | New version mint करें; यह कभी एक को in place edit नहीं करता है। `SOURCE` एक path, `@path`, या `-` stdin के लिए है — omit करें paste करने के लिए। | `--description`; `--no-verify` |
| `fp policies enable POLICY_ID` | इसे हर deployment में वापस add करें जहां से इसे remove किया गया था, प्रत्येक पर एक new generation mint करते हुए। | `--yes`, `-y` |
| `fp policies disable POLICY_ID` | इसे हर deployment से remove करें जो इसे carry करता है, प्रत्येक पर एक new generation mint करते हुए। | `--yes`, `-y` |
| `fp policies delete POLICY_ID` | Policy version को delete करें। | `--yes`, `-y` |
| `fp policies test [SOURCE]` | Policy को locally synthetic context के विरुद्ध चलाएं। प्रत्येक policy के `match` filter को apply करता है, तो एक जो given event/tool को cover नहीं करता है `skipped` के रूप में report किया जाता है rather than run। PATH पर `node` की जरूरत है। | `--event`; `--tool`; `--command`; `--file`; `--expect` |
| `fp policies compose PROMPT` | Assistant के साथ policy को draft करें। Draft को print करता है और default से कुछ नहीं करता है। `policies:write` की जरूरत है। | `--out <path>`; `--publish <policy-id>` |

| Command | Purpose | Options |
| --- | --- | --- |
| `fp fleet list` | Enrolled machines और उनके deployment generation को list करें। | — |
| `fp fleet show MACHINE_ID` | Policy set जो machine currently चलाता है। | — |
| `fp fleet deploy MACHINE_ID` | Change करें कि machine क्या enforce करता है। पहले full resulting set को print करता है, और interactive terminal पर बिना `--json` के ही ask करता है। | `--add`; `--remove`; `--set`; `--create`; `--yes`, `-y` |
| `fp fleet diff [MACHINE_ID]` | Intent versus delivery — क्या machine को run करने के लिए कहा जाता है बनाम जो यह last pulled है। पूरे fleet के लिए id को omit करें। | — |
| `fp fleet history MACHINE_ID` | Machine के लिए हर generation, newest first। | — |
| `fp fleet rollback MACHINE_ID GENERATION` | Past generation के policy set को reinstate करें। Generation number `fp fleet history MACHINE_ID` से आता है। | `--yes`, `-y` |
| `fp fleet rename MACHINE_ID LABEL` | Machine को readable label दें। Id itself कभी change नहीं होता है। | — |

```bash
fp fleet history ci-runner-01
fp fleet rollback ci-runner-01 3
fp fleet rename ci-runner-01 "CI runner (eu-west)"
```

#### Policy references

`--add` और `--set` एक policy reference लेते हैं, न कि bare id:

| Form | Means |
| --- | --- |
| `id` | Current version, current effect |
| `id@3` | Version 3, current effect |
| `id:observe` | Current version, recorded but not enforced |
| `id@3:observe` | Version 3, recorded but not enforced |

Effect `enforce` या `observe` है। Resolution: एक explicit effect जीत जाता है; अन्यथा effect पहले से ही उस policy के लिए deployed; अन्यथा `enforce`।

<Warning>
  एक bare `--add` **तुरंत enforce करता है**। `fp fleet deploy ci-runner-01 --add checkout-guard` उस machine पर blocking start करता है जैसे ही यह next में pull करता है। `:observe` ही है जो इसे एक shadow rollout बनाता है:

  ```bash
  fp fleet deploy ci-runner-01 --add checkout-guard:observe   # records only
  fp fleet deploy ci-runner-01 --add checkout-guard           # enforces now
  ```

  Observe off नहीं है। Policy को real के लिए evaluate किया जाता है, एक enforcing को same 10-second timeout और same error handling के तहत, और every non-allow verdict को record किया जाता है — केवल enforcement को withhold किया जाता है। यही है जो measurement को worth reading बनाता है।
</Warning>

#### Deltas, replacement, और races

`--add` और `--remove` machine के current set को read करते हैं और एक delta apply करते हैं, तो कुछ भी जो आपने name नहीं किया गया वह disturb नहीं है। एक bare `--add` एक policy पर जो machine पहले से चलाता है उसके pinned version को keep करता है rather than silently upgrading; इसे move करने के लिए `id@version` pass करें।

`--set` सब कुछ replace करता है और यह एक ही way है policies को drop करने का जो आप name नहीं करते। इसे `--add` या `--remove` के साथ combine नहीं किया जा सकता। इन तीनों में से कोई न pass करना एक usage error है, न कि एक no-op।

```bash
fp fleet deploy ci-runner-01 --add prod-guard@1:observe --remove old-rule
fp fleet deploy ci-runner-01 --set no-force-push --set no-secret-echo
```

Write itself हर path पर एक full replace है, क्योंकि endpoint पूरे policy set को लेता है। कोई server-side lock नहीं है, तो CLI वह generation record करता है जो यह read था और refuse करता है यदि result exactly one higher नहीं है — यह मतलब है किसी और ने बीच में deploy किया, और एक replace merge नहीं करता है। `fp fleet show` के साथ re-read करें, फिर फिर से deploy करें।

`--create` एक machine id को deploy करता है जो अभी तक check in नहीं किया है, pre-staging के लिए। इसके बिना, एक id जो server को पता नहीं है refuse किया जाता है, क्योंकि typo अन्यथा एक machine to mint करेगा जिसे कोई own नहीं करता policies के साथ जो कोई collect नहीं करता।

### Guardrails

क्या enforcement actually किया। **Session-only**, उपरोक्त जैसा ही कारण।

| Command | Purpose | Options |
| --- | --- | --- |
| `fp guardrails summary` | Coverage, blocked/evaluated totals, एक deny sparkline, और per-policy table। | `--since` (`1h`, `6h`, `24h`, `7d`); `--machine` |
| `fp guardrails timeline` | Decisions window पर bucketed, हर policy source के लिए summed। | `--since` (`1h`, `6h`, `24h`, `7d`); `--machine` |

Summary में एक `(no policy)` row normal है rather than एक gap: most evaluations हैं allows जिन पर कोई object नहीं किया, और row screen पर denominator को keep करता है।

### Roll a policy out without breaking anyone

उपरोक्त तीनों groups एक sequence हैं। Locally decide करें, publish करें, shadow करें, measure करें, फिर enforce करें।

```bash
fp policies test ./checkout.policy.mjs --tool Bash --command "git push --force" --expect deny
fp policies publish checkout-guard ./checkout.policy.mjs --description "Block force-push"
fp fleet deploy ci-runner-01 --add checkout-guard:observe
fp guardrails summary --since 24h --machine ci-runner-01
fp fleet deploy ci-runner-01 --add checkout-guard:enforce
```

| Step | Why it is there |
| --- | --- |
| `fp policies test` | कोई server नहीं और कोई auth नहीं। Real file को आप describe करने वाले context के विरुद्ध चलाता है और allow, deny, या instruct को हर registered policy के लिए print करता है। `--expect` इसे एक CI assertion में turn करता है। |
| `fp policies publish` | New immutable version को mint करता है; यह कभी एक को in place edit नहीं करता है। |
| `fp fleet deploy --add <id>:observe` | Shadow rollout। **`:observe` यहां optional नहीं है** — एक bare `--add` machine जैसे ही pull करता है enforce करता है। |
| `fp guardrails summary` | Unsafe matches को legitimate work से separate करता है जो policy भी block करेगा। |
| `fp fleet deploy --add <id>:enforce` | Promotion, एक बार recorded verdicts कहते हैं कि आपने क्या expected किया। |
| `fp fleet rollback <machine> <generation>` | Back का way यदि enforcement गलत हो जाता है। |

Single-machine equivalent, Cloud के बिना, है pack को `failproofai publish --effect observe` के साथ publish करना और [local dashboard](/hi/reference/local-dashboard) पर recorded verdicts को read करना।

Explicit flags environment variables को override करते हैं, जो saved configuration को override करते हैं।

API-key mode में organization जो एक human `fp login` से save किया गया है **ignored** है, not merely overridden — केवल एक explicit `--org` या `FP_ORG` send किया जाता है। कुछ भी एक saved login से inherit नहीं होता है, तो `--org` को pass करें जब कभी key एक से अधिक organization के लिए act कर सके। इसे omit करना loudly fail नहीं करता: एक instance-scoped key बिना `--org` के server-side को **default** organization के लिए resolve होता है और उस organization के data के साथ answer देता है, कहीं भी कोई error के बिना। `fp whoami` को पहले run करें confirm करने के लिए कि एक key actually किस tenant से बात कर रहा है।

<Warning>
  `AGENTEYE_*` spellings of ये हैं **not read by `fp`** और कभी नहीं थे — CLI `FP_*` (`fp_cli/app.py`) को declare करता है, और एक unknown variable एक error नहीं है। `AGENTEYE_DASHBOARD_URL` को set करना CLI को retarget नहीं करता है; यह ignore किया जाता है और command silently saved dashboard के विरुद्ध चलता है।

  `AGENTEYE_HOME` और `AGENTEYE_ENVIRONMENT` अभी भी exist करते हैं, लेकिन वे **collector और telemetry SDK** को belong करते हैं, इस CLI को नहीं।
</Warning>

</Warning>
