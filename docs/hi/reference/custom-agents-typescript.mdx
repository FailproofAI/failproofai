## Install करें

```bash
npm install @failproofai/sdk
```

```ts
import * as failproofai from "@failproofai/sdk";

await failproofai.agent("planner", { goal: question }, async () => {
  const hits = await failproofai.toolCall("web_search", { input: { q } }, () => search(q));
});
```

Framework adapters package में ही ship होते हैं। Frameworks **optional peer dependencies** हैं — declared ताकि supported ranges दिखाई दें, कभी आपकी ओर से install न हों, और केवल तभी import हों जब आप `instrument()` को call करें।

## Failproof daemon से connect करें

Python SDK के समान: **Admin → Keys** के तहत एक `events:add` key बनाएं, फिर [daemon को connect करें](/hi/start/setup#connect-a-machine-to-cloud) agent मशीन पर। SDK disk पर लिखता है; daemon भेजता है।

## Configuration

### OpenTelemetry spans (opt in)

OpenTelemetry को अलग से install करें `npm install @opentelemetry/api @opentelemetry/sdk-trace-base` के साथ।
फिर अपने provider के processors में FailproofAI जोड़ें:

```ts
import * as failproofai from "@failproofai/sdk";
import { BasicTracerProvider } from "@opentelemetry/sdk-trace-base";
import type { SpanProcessor } from "@opentelemetry/sdk-trace-base";

const spanProcessors: SpanProcessor[] = [];
await failproofai.instrument("otel", { spanProcessors });
const provider = new BasicTracerProvider({ spanProcessors });
const span = provider.getTracer("my-agent").startSpan("agent", {
  attributes: { "gen_ai.operation.name": "invoke_agent" },
});
span.end();
await provider.forceFlush();
```

एक मौजूदा provider के लिए, इसके अन्य processors को एक ही list में रखें। Providers जो `addSpanProcessor` को expose करते हैं, `{ provider }` के रूप में pass किए जा सकते हैं। बिना options के, setup एक नया provider register करता है केवल अगर कोई provider पहले से registered नहीं है। `OtelSpanExporter` को सीधे आपने अपने processor के साथ भी उपयोग किया जा सकता है।

Exports connected FailproofAI daemon के माध्यम से जाते हैं; SDK कोई network requests नहीं भेजता है और किसी key या local listener की जरूरत नहीं है। एक admin से कहें [OpenTelemetry ingest](/hi/agenteye/opentelemetry) को enable करने के लिए। एक bare `instrument()` इस exporter को enable नहीं करता। `uninstrument("otel")` केवल अपने अपने processor को disable करता है। आपके span attributes content capture को नियंत्रित करते हैं; exit से पहले अपना provider flush करें। OpenTelemetry एक optional application dependency रहता है, hard SDK dependency नहीं।

```ts
failproofai.configure({
  environment: "production",
  flushInterval: 0.5,
  baseDir: undefined,
});
```

| Option | यह क्या करता है |
| --- | --- |
| `environment` | हर event पर label — `production`, `staging`, `prod-eu`। Default `dev` है। |
| `flushInterval` | Timer कितनी बार disk पर लिखता है, सेकंड में। Default `0.5` है। |
| `baseDir` | कहां लिखना है। Default daemon का spool है, जो वह है जो आप चाहते हैं जब तक आप अन्यथा न जानते हों। |

कुछ भी apply नहीं होता जब तक सब कुछ validate न हो, तो एक rejected call SDK को बिल्कुल वैसे ही छोड़ता है जैसे वह था, नई `baseDir` और पुरानी interval के साथ नहीं।

इसके बजाय environment variable से set करें:

| Variable | यह क्या करता है |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | Code change के बिना `environment` set करता है। एक `configure()` option इसे win करता है। |
| `FAILPROOFAI_HOME` | Failproof AI root को move करता है जो spool को रखता है। |
| `FAILPROOFAI_SDK_LOG_LEVEL` | `debug`, `info`, `warn` (default), `error`, `silent`। |
| `FAILPROOFAI_SDK_STRICT` | `1` instrumentation errors को throw कराता है logging के बजाय। |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | `1` framework-compatibility समस्या को throw कराता है warning और carry on करने के बजाय। |

<Warning>
  **`environment` में कोई commas नहीं।** Ingest उस field को commas पर split करता है अपने filters बनाने के लिए, और किसी भी event को skip करता है जिसके label में एक है — तो एक पूरा run silently vanish हो जाता है। `prod,eu` न लिखकर `prod-eu` लिखें।

  `configure({ environment: "prod,eu" })` throw करता है तो आप तुरंत पता लगा लें। `AGENTEYE_ENVIRONMENT` throw नहीं कर सकता — कोई आपको नहीं call कर रहा — तो यह एक बार warn करता है और `dev` पर fall back करता है।
</Warning>

SDK के अपने log lines को अपने logger में route करें `failproofai.setLogger({ debug, info, warn, error })` के साथ।

## Shutdown

Buffered events `process.on("exit")` पर flush होते हैं।

एक signal द्वारा killed process कभी भी उस तक नहीं पहुंचता है, और Node की default for `SIGTERM` exit handlers को चलाए बिना terminate करना है — तो एक containerised agent जो last interval में नहीं लिखा था वह खो जाता है।

<Warning>
  **यह SDK आपके लिए एक signal handler install नहीं करेगा।** एक register करना आपकी process के behaviour को बदल देता है: एक listener Node की default termination को suppress करता है, तो एक library जिसने एक add किया है वह silently Ctrl-C को काम करने से रोक देता है। अपना खुद का add करें:

  ```ts
  for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.once(signal, () => {
      failproofai.flushSync();
      process.exit(0);
    });
  }
  ```
</Warning>

एक short-lived script या एक serverless handler को return करने से पहले `await failproofai.flush()` करना चाहिए — interval अकेले delivery की guarantee नहीं देता है।

## Identity

हर event एक session और एक agent से संबंधित है। **Scopes दोनों को fill करते हैं**, तो आप rarely उन्हें pass करते हैं:

```ts
await failproofai.session(async () => {
  await failproofai.agent("planner", async () => {
    failproofai.event.toolUse({ toolName: "search", toolCallId: "c1" });
  });
});
```

`sessionId` या `agentId` को explicitly pass करना अभी भी काम करता है और win करता है। न तो bound और न ही passed होने के साथ, call throw करता है rather than एक event emit करना जो Cloud silently discard करेगा।

<Note>
  Identity `AsyncLocalStorage` पर rides करता है। यह `await`, `.then()`, timers और कोई भी callback जो scope के अंदर create हो को follow करता है। यह **नहीं** एक callback को follow करता है जो एक run के दौरान store और दूसरे के दौरान invoked हो, या `worker_threads` boundary के across handed हो — उन्हें `failproofai.propagate()` में wrap करें या उनके events unattached land करेंगे।
</Note>

### Scopes

| Scope | Emits | Returns |
| --- | --- | --- |
| `session(body)` | कुछ नहीं — केवल identity | जो भी `body` return करता है |
| `agent(id, options?, body)` | `agent_start`, फिर `agent_end` | जो भी `body` return करता है |
| `toolCall(name, options?, body)` | `tool_use`, फिर `tool_result` | जो भी `body` return करता है |

एक synchronous body synchronous रहता है: `agent("x", () => 1)` एक promise नहीं बल्कि `1` return करता है।

`toolCall` body के resolved value को tool के `output` के रूप में record करता है, जब तक आप `call.output` को खुद assign न करें।

<Accordion title="Exit semantics" icon="arrow-right-from-bracket">

| क्या हुआ | Events | `outcome` |
| --- | --- | --- |
| block returned | `agent_end` | `"success"`, या आपका `outcome` |
| block threw | `error`, फिर `agent_end` | `"failed"` |
| एक `AbortError` | केवल `agent_end` | `"cancelled"` |

Error हमेशा re-thrown होता है।

एक tool failure leaf पर record होता है — `tool_result` एक `error` string के साथ — और **कोई** run-level `error` event emit नहीं करता है। एक जो agent loop catch करता है run failure नहीं है, और एक जो propagate करता है enclosing `agent()` द्वारा बिल्कुल एक बार report होता है।

</Accordion>

<Accordion title="The `using` form" icon="brackets-curly">

जब work एक single function नहीं है — एक scope एक constructor में opened और एक teardown में closed, या एक जो existing control flow को straddle करता है:

```ts
{
  using span = failproofai.agent.open("planner", { goal });
  using call = failproofai.toolCall.open("search", { input: { q } });
  call.call.output = await search(q);
}  // tool_result, फिर agent_end
```

दोनों forms byte-identical events emit करते हैं। Callback form को prefer करें: यह `AsyncLocalStorage.run()` के अंदर runs करता है, तो unwinding के लिए कुछ नहीं है और "opened here, closed over there" bugs की पूरी class unreachable है।

एक `using` block जो अपनी अपनी failure को catch करता है इसे `span.fail(error)` के साथ report करता है — disposer के पास अपना exception channel नहीं है।

</Accordion>

## Event catalog

Python SDK के समान fifteen methods, camelCase में। अधिकांश **pairs** में आते हैं — आप opener को call करते हैं, फिर closer को, और SDK gap को time करता है।

| | Opens | Closes |
| --- | --- | --- |
| **Agents** | `agentStart` | `agentEnd` |
| | `agentPause` | `agentResume` |
| **Models** | `modelRequest` | `modelResponse` |
| **Tools** | `toolUse` | `toolResult` |
| **Hooks** | `hookTriggered` | `hookCompleted` |
| **Humans** | `humanWait` | `humanInput` |

तीन standalone हैं: `error`, `humanPause`, `humanInterrupt`।

<Accordion title="हर field, प्रति method" icon="table">

हर method `sessionId` और `agentId` भी लेता है, जो scopes आपके लिए fill करते हैं। कुछ भी omitted JSON `null` के रूप में भेजा जाने के बजाय dropped होता है।

| Method | Required | Optional |
| --- | --- | --- |
| `agentStart` | — | `goal`, `parentId` |
| `agentEnd` | — | `outcome`, `summary` |
| `agentPause` | `pauseId` | `reason`, `userId` |
| `agentResume` | `pauseId` | `reason`, `userId` |
| `modelRequest` | — | `model`, `messages`, `system`, `tools`, `requestId` |
| `modelResponse` | — | `model`, `stopReason`, `inputTokens`, `outputTokens`, `content`, `role`, `requestId` |
| `toolUse` | `toolName`, `toolCallId` | `input` |
| `toolResult` | `toolName`, `toolCallId` | `output`, `error` |
| `hookTriggered` | `hookName`, `hookId` | `triggerEvent`, `input` |
| `hookCompleted` | `hookName`, `hookId` | `outcome`, `output`, `error` |
| `error` | `errorType`, `message` | `traceback` |
| `humanWait` | `inputId` | `prompt`, `options`, `reason` |
| `humanInput` | `inputId` | `response` |
| `humanPause` | — | `reason`, `userId` |
| `humanInterrupt` | — | `reason`, `userId`, `atStep` |

कोई भी अन्य key जो आप add करते हैं एक custom payload field बन जाता है। Framework-specific किसी भी चीज़ को namespace करें `fw_*` के रूप में; एक नाम जो declared field के साथ collide करता है refuse किया जाता है rather than silently एक promoted column को overwrite करने के लिए।

</Accordion>

<Warning>
  **`duration_ms` computed है, accepted नहीं।** चार closing methods opener से gap को time करते हैं और एक caller-supplied `duration_ms` को refuse करते हैं — एक reported duration unfalsifiable है।

  Pairs session और id पर match होते हैं, agent पर कभी नहीं। एक tool `planner` के under opened और `worker` के under closed अभी भी pair होता है, जो nested multi-agent runs वास्तव में क्या करते हैं।
</Warning>

## Framework adapters

```ts
await failproofai.instrument();              // जो भी यह पा सके
await failproofai.instrument("langchain");   // बिल्कुल एक
failproofai.uninstrument();                  // सब कुछ वापस रखें
```

| Framework | Supported | यह कैसे attach होता है |
| --- | --- | --- |
| **LangChain.js / LangGraph.js** | `@langchain/core` 0.3 – 1.x, LangGraph.js 0.4 – 1.x | `CallbackManager.configure`, तो हर `invoke`/`stream`/`batch` कहीं भी `callbacks:` pass किए बिना cover होता है — या `langchainHandler()` को खुद pass करें और कुछ भी patch न करें। |
| **Vercel AI SDK** | `ai` 4 – 7 | Call site पर `telemetry()`, या `instrument("ai")` `ai` 7 पर पूरी process के लिए (4–6 पर वह opt-in है — नीचे देखें)। |
| **Mastra** | `@mastra/core` 0.20 – 1.x | `Agent.generate`/`.stream`, agent का model और tool resolution, और workflow run/step engine। |
| **LlamaIndex.TS** | `llamaindex` 0.11.4 – 0.x | `Settings.callbackManager` (subscribed) plus `AgentWorkflow.runStream`, workflow runs और उनके steps के लिए। |

हर range real framework releases के विरुद्ध tested है, दोनों ends पर, एक ES module और CommonJS के रूप में, हर CI run पर।

Mapping Python SDK की है, तो एक ही program दोनों languages में एक ही tree draw करता है। एक construct एक **agent** है केवल अगर यह एक LLM decision loop को own करता है — एक graph या chain run, एक AI SDK `generateText`/`streamText` call, एक Mastra agent, एक LlamaIndex agent run। एक LangGraph node या एक workflow step एक **hook** है (`hook_triggered`/`hook_completed`), कभी एक nested agent नहीं। Model calls `model_request`/`model_response` pairs हैं token counts के साथ; tool calls model के अपने tool call id carry करते हैं। एक failure एक बार record होता है, वह event में जहां यह हुआ।

एक adapter जो install करने में fail होता है logged और skipped है; बाकी अभी भी install होते हैं, क्योंकि एक broken LlamaIndex आपको LangGraph की cost न लगे।

<Note>
  `instrument()` कोई argument के बिना एक framework को detect करता है चाहे यह **resolves** हो, चाहे वह पहले से import हो — Node ES modules के लिए Python के `sys.modules` के बराबर कुछ expose नहीं करता। एक framework जो आप install किए हैं लेकिन use नहीं करते imported और patched हो जाएंगे। एक नाम दें जो आप चाहते हैं अगर वह मायने रखता है।
</Note>

<Note>
  इनमें से अधिकांश frameworks एक ES-module build और एक CommonJS build ship करते हैं, जो Node दोनों unrelated copies के रूप में loads करता है। Adapters उस copy को patch करते हैं जो आपका application loads करता है (और CommonJS copy भी अगर कुछ पहले से `require` किया हो), तो दोनों module systems काम करते हैं। एक framework **आपने अपने output में bundled** esbuild या webpack द्वारा unreachable है — call-site helpers को use करें वहां: `langchainHandler()`, `telemetry()`, `wrapTool()`।
</Note>

### LangChain without patching

```ts
import { langchainHandler } from "@failproofai/sdk/langchain";
await graph.invoke(input, { callbacks: [langchainHandler()] });
```

Handler `instrument()` के साथ या बिना काम करता है और कभी भी double-record नहीं करता। `instrument("langchain")` `sessionId`, `captureContent`, `includeChains`, `graphCallbacks` और `captureLimit` लेता है, जैसे Python adapter करता है; `metadata: { failproofai_sdk_session_id }` एक call पर उस invocation के लिए session pick करता है।

### Vercel AI SDK

AI SDK plain functions को एक ES module से export करता है, और एक ES module namespace specification द्वारा immutable है — patch करने के लिए कहीं नहीं है। यह extension points use करता है जो SDK खुद documents करता है:

```ts
import { telemetry } from "@failproofai/sdk/ai";

const { text } = await generateText({
  model,
  prompt,
  experimental_telemetry: telemetry({ functionId: "answer-question" }),
  // ai 7 पर, `telemetry: telemetry({ … })` — वही object, नया नाम
});
```

वह पूरा integration है: एक agent span, एक model request/response pair token counts के साथ per step, और हर tool call। एक call site हर major पर काम करता है — `ai` 4–6 tracer को read करते हैं जो यह carry करता है, `ai` 7 telemetry integration को।

`instrument("ai")` **`ai` 7 पर** एक ही process-wide करता है: हर call, AI SDK के global telemetry-integration list के माध्यम से, जो additive है और किसी और चीज़ से कुछ नहीं लेता है।

**`ai` 4–6 पर, `instrument("ai")` खुद से कुछ नहीं record करता है, और एक warning log करता है कि ऐसा है।** वह एकमात्र process-wide hook जो वह majors के पास है global OpenTelemetry tracer provider है — एक single slot जो OpenTelemetry ले लिए जाने के बाद hand over करने से refuse करता है। हमारे को register करना silently आपके अपने `NodeSDK.start()` को startup में बाद में refuse करेगा और आपके http/database spans को एक tracer को भेजेगा जो कुछ नहीं export करता। Call site पर `telemetry()` use करें या `wrapModel` वहां use करें। अगर process अपना कोई OpenTelemetry नहीं चलाता है, `instrument("ai", { registerGlobalTracer: true })` के साथ opt in करें: यह फिर हर call को record करता है जो `experimental_telemetry: { isEnabled: true }` pass करता है, और slot को लेता है केवल अगर यह अभी भी empty है। `registerGlobalTracer: false` default को रखता है और warning को silence करता है।

अगर आप model को एक बार wrap करना चाहते हैं, `wrapModel` केवल model calls देखता है, क्योंकि tool calls model layer के above happen होते हैं। एक wrapped model जो कुछ नहीं के साथ call किया जाता है अपने अपने run के रूप में record होता है। एक streamed call जैसे stream stops उसे close करता है — `stop_reason: "cancelled"` जब consumer इसे cancel करता है, `"error"` error के साथ जब यह part-way fail होता है:

```ts
import { wrapModel } from "@failproofai/sdk/ai";
const model = await wrapModel(openai("gpt-4o"));
```

दोनों को use करना ठीक है: middleware notice करता है कि call पहले से ही record किया जा रहा है और defer करता है, तो हर call एक बार record होता है।

`functionId` agent span को नाम देता है। इसे low-cardinality रखें — यह `agent_id` में lands करता है, primary dashboard facet।

### Next.js

`next build` अपने server के dependencies को default द्वारा bundle करता है, और एक framework bundled into build में एक copy है जो `instrument()` reach नहीं कर सकता। Config को एक बार wrap करें और `instrument()` को Next के startup hook से call करें:

```ts
// next.config.ts
import { withFailproofai } from "@failproofai/sdk/next";
export default withFailproofai({ /* आपका config */ });
```

```ts
// instrumentation.ts
export async function register() {
  if (process.env.NEXT_RUNTIME !== "nodejs") return;
  const failproofai = await import("@failproofai/sdk");
  await failproofai.instrument();
}
```

`withFailproofai` LangChain, Mastra, LlamaIndex और SDK को `serverExternalPackages` में add करता है, आपकी अपनी list को keep करते हुए। इसके बिना, `instrument()` एक बार per framework warn करता है जिसे यह reach नहीं कर सकता rather than failing silently; अगर आप packages को खुद list करते हैं, `FAILPROOFAI_NEXT_EXTERNALS=1` set करें। Vercel AI SDK और call-site helpers दोनों तरीके से काम करते हैं। एक Edge route को एक no-op build मिलता है: SDK को import करना safe है और कुछ नहीं record करता है।

### Token counts on streamed calls

OpenAI-compatible APIs केवल stream पर usage report करते हैं जब client ask करता है। LangChain और Vercel AI SDK ask करते हैं; LlamaIndex के लिए अपने `OpenAI` LLM को `additionalChatOptions: { stream_options: { include_usage: true } }` pass करें, और Mastra के लिए model को usage enabled के साथ build करें (उदाहरण `createOpenAICompatible({ includeUsage: true })`)। अन्यथा streamed model calls कोई token counts नहीं carry करते हैं।

### Runtimes

Node ≥ 20.9, Bun और Deno — हर framework, एक ES module और CommonJS के रूप में, Node के trace के विरुद्ध हर एक पर test होता है। SDK `failproofaid` daemon के beside runs करता है, जो यह भेजता है उसे ship करता है।

## आपका अपना agent — कोई framework नहीं

एक agent loop के लिए जो आप ने खुद लिखा, या एक framework बिना adapter के। आप events को adapters के समान API के साथ emit करते हैं जो underneath use करते हैं, तो trace का same shape और quality है।

आपको agent कैसे organized है यह जानने की जरूरत नहीं है। हर hand-built agent के पास पहले से ही तीन places हैं, जो भी इसके functions को कहते हैं, और वह तीन पूरा integration है:

| कहां | क्या add करना है | Emits |
| --- | --- | --- |
| जहां **एक run** शुरू और समाप्त होता है | `failproofai.agent("name", { goal }, async () => …)` | `agent_start` / `agent_end` |
| **एक function जो model को call करता है** | `event.modelRequest` पहले, `event.modelResponse` बाद में — दोनों halves, failure पर भी | एक pair per model turn |
| **एक function जो tools चलाता है** | `failproofai.toolCall(name, { toolCallId, input }, () => run())` | `tool_use` / `tool_result` |

```ts
async function callModel(messages) {
  const requestId = randomUUID();
  const started = Date.now();
  failproofai.event.modelRequest({ model: MODEL, requestId, messages });
  try {
    const reply = await client.chat.completions.create({ model: MODEL, messages, tools });
    failproofai.event.modelResponse({
      model: reply.model, requestId, stopReason: reply.choices[0].finish_reason,
      inputTokens: reply.usage?.prompt_tokens, outputTokens: reply.usage?.completion_tokens,
      duration_ms: Date.now() - started,
    });
    return reply.choices[0].message;
  } catch (error) {
    failproofai.event.modelResponse({ model: MODEL, requestId, stopReason: "error",
      error: String(error), duration_ms: Date.now() - started });
    throw error;
  }
}

async function dispatch(call) {
  const input = JSON.parse(call.function.arguments);
  return failproofai.toolCall(call.function.name, { toolCallId: call.id, input },
    () => runTool(call.function.name, input));
}

await failproofai.agent("inventory", { goal: question }, async () => {
  for (;;) {
    const message = await callModel(messages);
    if (!message.tool_calls?.length) return message.content;
    for (const call of message.tool_calls) await dispatch(call);
  }
});
```

Identity ambient है: `agent()` के अंदर सब कुछ उस run के session पर lands करता है एक id के बिना, और program में कुछ नहीं बदलता — including जो कुछ भी agent पहले से अपने अपने database में लिखता है।

- **एक service या एक worker:** अपना अपना request या job id `sessionId` के रूप में pass करें, तो dashboard पर एक session और आपने अपने logs या database में record एक ही string हैं।
- **Sub-agents:** `agent()` calls को nest करें। Inner एक session के साथ outer के साथ `parent_id` के रूप में जुड़ता है।
- **Pairs को emit करें।** एक `modelRequest` कोई `modelResponse` के साथ एक span है जो dashboard forever running दिखाता है — इसलिए `catch`।

[`sdk/typescript/examples/research-agent.ts`](https://github.com/FailproofAI/failproofai/blob/main/sdk/typescript/examples/research-agent.ts) repository में पूरा, runnable version है: एक real OpenAI tool loop instrumented बिल्कुल इस तरह, हर change पर CI में run किया जाता है एक ES module और CommonJS के रूप में।

## Evaluations

```ts
import { Evaluator, EvalResult, Score } from "@failproofai/sdk/evaluator";

export const app = new Evaluator({ name: "my-evals", version: "1" });

app.eval("tool_success_rate", { version: "1" }, (session) => {
  const results = session.eventsOfType("tool_result");
  const failures = results.filter((event) => event.payload.error != null).length;
  return new EvalResult({
    score: new Score(results.length === 0 ? 1 : 1 - failures / results.length),
    reasoning: `${failures} of ${results.length} tool calls failed`,
  });
});
```

```bash
FAILPROOFAI_EVALUATOR_URL=… FAILPROOFAI_EVALUATOR_TOKEN=… \
  npx failproofai-evaluator ./my-evals.js
```

[Evaluator SDK reference](/hi/reference/evaluator-sdk) को protocol, worker settings और result types के लिए देखें।

<Warning>
  **एक evaluation को yield करना चाहिए।** एक synchronous function जो कभी return नहीं करता Node के पास जो एक thread है को block करता है, और कोई timeout जबकि यह ऐसा करता है fire नहीं कर सकता। `async` evaluations लिखें।
</Warning>

## यह आपकी process को क्या नहीं करेगा

| | |
| --- | --- |
| **आपकी agent loop को block करें** | Events एक in-memory queue में जाते हैं; एक timer लिखता है। Timer `unref`'d है, तो इस package को import करना कभी भी एक script को exit करने से नहीं रोकता है। |
| **बिना bound grow करें** | Queue count द्वारा capped है *और* measured bytes द्वारा। या तो past, oldest events discard होते हैं और एक warning कहता है — एक telemetry outage एक OOM kill बनना चाहिए नहीं। |
| **Process को नीचे ले जाएं** | एक unencodable event अकेले drop होता है, इसके around batch नहीं। एक throwing getter, एक circular reference, एक `BigInt`, एक lone surrogate: हर एक handle होता है rather than propagate होता है। |
| **एक half-written batch छोड़ें** | Content atomic rename से पहले `fsync`ed है, directory के बाद है, और एक failed write अपनी temporary file को clean up करता है। |
| **Transcripts को readable छोड़ें** | Batches `0600` एक `0700` directory के अंदर हैं। वे goals, prompts, tool arguments और tool output carry करते हैं। |
| **Credentials को ship करें** | API keys, tokens, JWTs, bearer headers और secret-shaped assignments bytes disk तक पहुंचने से पहले redacted होते हैं। Daemon upload से पहले फिर से redact करता है। |
