## Event families

- Agent start, end, pause, और resume
- Model request और response
- Tool use और result
- Hook triggered और completed
- Human wait, input, pause, और interrupt
- Explicit errors

हर event के साथ एक timestamp, session ID, agent ID, event type, और environment होता है। Event-specific fields में model, tool, correlation, outcome, content, duration, या error data होता है।

## एक event contract को inspect करें

<Tabs>
  <Tab title="Dashboard">
    1. **Observe → Events** को खोलें।
    2. एक छोटी time window सेट करें और environment, agent, और event type के आधार पर filter करें।
    3. एक event को select करें इसके normalized fields और raw payload को inspect करने के लिए, फिर अपने session को खोलें execution context को देखने के लिए।
    4. अगर एक paired duration missing है, तो verify करें कि start और completion events एक ही correlation ID का use कर रहे हैं।

    Events stream को use करें data को एक agent run तक narrow करने के लिए और normalized event fields को inspect करें।

    ![Environment, agent, session, और event type के लिए filters के साथ live Events stream।](/images/dashboard/events-stream.png)

    फिर event को अपने session में follow करें। Trace दिखाता है कि इससे तुरंत पहले और बाद में क्या हुआ, जो जरूरी है जब payload अकेले ambiguous हो।

    ![Linked session trace जो execution context में event को inspect करने के लिए use होता है।](/images/dashboard/session-detail.png)

    Correlation IDs और timestamps को दोनों views में compare करें जब एक paired event या duration missing हो।
  </Tab>
  <Tab title="CLI">
    Valid filter values को discover करें, फिर एक session के लिए full event payloads को fetch करें:

    ```bash
    fp list event_types
    fp list envs
    fp events --since 1h \
      --env production \
      --event-type tool_use,tool_result \
      --session-id <session-id> \
      --full
    ```

    Machine-readable inspection के लिए `fp --json events ... --fields ts,event_type,session_id,payload` को use करें।
  </Tab>
</Tabs>

## Reserved SDK fields

`timestamp`, `session_id`, `agent_id`, `type`, या `environment` को custom Python SDK fields के रूप में use न करें। Paired event durations जैसे tool result duration को SDK द्वारा calculate किया जाता है और manually supply नहीं किए जा सकते।

## Local boundaries

- Failproof AI state `~/.failproofai` के तहत रहता है जब तक explicitly अन्यथा configure न किया जाए।
- `failproofai-sdk` हमेशा `~/.failproofai/custom-agents` के तहत spool करता है। `FAILPROOFAI_HOME` उस home को relocate करता है; `custom-agents` segment हमेशा appended होता है, इसलिए spool को इसके बाहर रखा नहीं जा सकता। केवल SDK का अपना `configure(base_dir=...)` कहीं और लिखता है। `AGENTEYE_HOME` को पुराने `agenteye-collector` द्वारा पढ़ा जाता है यह चुनने के लिए कि क्या देखना है, और अब यह प्रभावित नहीं करता है कि SDK कहां लिखता है।
- Environment labels को SDK configuration या `AGENTEYE_ENVIRONMENT` के माध्यम से set किया जा सकता है।
- Daemon credentials को non-secret settings से अलग store किया जाता है।

Stable, low-cardinality environment names का use करें। Commas को daemon environment labels में support नहीं किया जाता है।

## एक environment label को change करें

<Tabs>
  <Tab title="Dashboard">
    Environment labels को emitting SDK या Failproof daemon द्वारा assign किया जाता है। एक को change करने के बाद, **Observe → Sessions** को खोलें और environment filter का use करें यह confirm करने के लिए कि नए sessions नया value carry करते हैं। Existing sessions अपना original environment retain करते हैं।

  </Tab>
  <Tab title="CLI">
    `failproofai-sdk` के लिए, code में environment को configure करें या इसके legacy environment variable के साथ। Machine-level settings को change करते समय daemon configuration को rerun करें।

    ```bash
    export AGENTEYE_ENVIRONMENT=production-us-east
    failproofai config
    failproofai config --status
    fp sessions --since 1h --env production-us-east
    ```
  </Tab>
</Tabs>
