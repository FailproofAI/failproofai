`npm install -g failproofai` के साथ स्थानीय CLI को इंस्टॉल करें। इसे बिना किसी आर्गुमेंट के चलाएं ताकि स्थानीय नीति डैशबोर्ड खुले।

पैकेज को Node.js 20.9 या नए संस्करण की आवश्यकता है। Bun 1.3 या नए संस्करण को विकास और स्रोत इंस्टॉल के लिए समर्थित किया जाता है। `failproofai configure` और `failproofai setup` `failproofai config` के लिए उपनाम हैं। `failproofai policy`, `failproofai pack` और `failproofai p` सभी `failproofai policies` की वर्तनी हैं — पैक्स और एकल नीतियां पहले तीन कमांड थीं और अब एक हैं। पुरानी वर्तनी अभी भी काम करती है, दो अपवादों के साथ: `pack list <source>` अब `policies show <source>` है, और `pack build` अब `publish` है।

## एक मशीन को सेट अप करें

CLI को इंस्टॉल करें, फिर मशीन की कुंजी को शेल में पढ़ें। `read -s` इसे एक प्रॉम्प्ट पर लेता है जो इको नहीं करता, इसलिए यह कभी कमांड में दिखाई नहीं देता:

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

फिर मशीन को सेट अप करें और चुनें कि यह क्या लागू करता है:

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` पूरा सेटअप है: यह `failproofaid` सेवा को इंस्टॉल करता है (रूट एक बार — एक टर्मिनल में यह आपके sudo पासवर्ड के लिए पूछता है, और फिर से पूछता है यदि यह सेटअप खत्म होने से पहले समाप्त हो गया है; कोई टर्मिनल नहीं है तो यह `sudo -n` का उपयोग करता है और कभी संकेत नहीं देता है), हर एजेंट CLI में हुक्स को जोड़ता है, और क्लाउड से कनेक्ट करता है। टर्मिनल के बिना — CI, एक कंटेनर, एक एजेंट इसे चलाता है — यह पूछने के बजाय लागू करता है, और यदि कुछ भी ऐसा नहीं हुआ जो इसे करने के लिए कहा गया था तो 1 से बाहर निकलता है।

एक टर्मिनल में, एक मशीन पर **क्लाउड से कनेक्ट करें** चरण जो अभी तक कनेक्ट नहीं है तो सीधे **FailproofAI Cloud में लॉगिन करना** शुरू करता है; अन्य विकल्पों के लिए Tab दबाएं, **एक API कुंजी पेस्ट करें** या **ओपन सोर्स का उपयोग करें**। लॉगिन एक लिंक खोलता है — या SSH पर इसे प्रिंट करता है या कोई डिस्प्ले नहीं है, किसी भी डिवाइस पर खोलने के लिए — जहां आप साइन अप या साइन इन करते हैं, एक संगठन चुनते या बनाते हैं, और मशीन को अधिकृत करते हैं; टर्मिनल अनुमोदन को अपने आप उठाता है और दिखाता है कि किसने इसे अनुमोदित किया और किस संगठन के लिए। कुंजी तभी बनाई जाती है जब सेटअप खत्म हो जाता है, डेमन के इंस्टॉल के बाद। एक मशीन पर जो पहले से एक काम करने वाली कुंजी के साथ कनेक्ट है, यह चरण एक मेनू है जिसमें **वर्तमान कनेक्शन रखें** पहले है, इसलिए सेटअप को फिर से चलाना कभी अपने आप ब्राउजर नहीं खोलता है; एक सहेजी गई कुंजी जो अब काम नहीं करती है तुरंत फिर से लॉगिन करती है, और कहती है कि क्यों। फिर से लॉगिन करने से एक नई कुंजी बनती है और पुरानी एक तब तक काम करती है जब तक आप इसे निष्कासित न करें। एक ब्राउजर लॉगिन से पहले का क्लाउड ऐसा कहता है और अन्य विकल्पों की पेशकश करता है।

यह **कोई नहीं** नीतियां चुनता है। यह दूसरी कमांड का काम है, और इसके बिना एक नई तरह से कॉन्फ़िगर की गई मशीन हमेशा-सक्षम गार्ड के अलावा कुछ भी लागू नहीं करती है।

`--token` पर पर्यावरण चर को प्राथमिकता दें: एक कमांड-लाइन आर्गुमेंट बॉक्स पर हर उपयोगकर्ता द्वारा `ps` से पढ़ा जा सकता है। वह सब कुछ है जो चर की सुरक्षा करता है — एक कुंजी किसी भी कमांड में टाइप की जाती है, `export` सहित, अभी भी शेल इतिहास में उतरती है, इसलिए इसे ऊपर `read -s` के साथ पढ़ा जाता है। CI में, इसे गुप्त स्टोर से सेट करें और शेल ट्रेसिंग (`set -x`) बंद रखें, या ट्रेस इसे प्रिंट करता है।

<Warning>
  `--connect <url>` एक मशीन को नामांकित करता है जो **पहले से सेट अप है**। यह नामांकन सफल होने के तुरंत बाद लौटता है — यह डेमन को इंस्टॉल नहीं करता है और किसी भी हुक को जोड़ नहीं करता है। एक मशीन पर सादे `failproofai config` (या `failproofai config --token <key>`) का उपयोग करें जो अभी तक सेट अप नहीं किया गया है, अन्यथा यह कनेक्ट के रूप में पढ़ा जाएगा जबकि कुछ नहीं एकत्र और लागू करता है।
</Warning>

स्थानीय नीति डैशबोर्ड खोलने के लिए बिना किसी आर्गुमेंट के `failproofai` चलाएं।

| कमांड | परिणाम |
| --- | --- |
| `failproofai config` | मशीन को सेट अप करें: एजेंट्स, डेमन, और क्लाउड — ब्राउजर के माध्यम से लॉगिन करें, एक कुंजी पेस्ट करें, या ओपन सोर्स रहें। मशीन पर हर एजेंट को एक छोटा `failproofai` कौशल भी मिलता है जो इसे [FailproofAI skills](https://github.com/FailproofAI/skills) ऑनलाइन की ओर इशारा करता है |
| `failproofai config --token <key>` | एक पास में सेट अप करें और कनेक्ट करें, कुछ न पूछें। एक कुंजी जो `jev:evaluate` ले जाती है [Jev को FailproofAI Cloud के माध्यम से](/hi/reference/jev-cloud) प्रेक्षण मोड में भी चालू करती है, जब तक कि `jev.json` पहले से मौजूद न हो या `--no-transcripts` दिया गया हो |
| `failproofai config --connect <url>` | एक मशीन को नामांकित करें जो **पहले से** सेट अप है — कोई डेमन नहीं, कोई हुक नहीं |
| `failproofai config --status` | कनेक्शन, डेमन, डिलीवरी, और पॉज़ स्थिति दिखाएं |
| `failproofai policies` | अंतर्निर्मित, कस्टम, कन्वेंशन, पैक, और क्लाउड-प्रबंधित नीतियां सूचीबद्ध करें |
| `failproofai policies --install` | आपके एजेंट CLIs में हुक्स को जोड़ें। कोई नीति अपने आप सक्षम नहीं करता है |
| `failproofai policies add <name>` | एक नीति सक्षम करें — एक अंतर्निर्मित, या एक इंस्टॉल किए गए पैक से `<pack-id>:<name>` |
| `failproofai policies remove <name>` | एक नीति अक्षम करें, समान नामकरण |
| `failproofai policies --uninstall` | नीतियां अक्षम करें या हार्नेस हुक्स निकालें |
| `failproofai policies show <owner>/<repo>` | एक पैक क्या ले जाता है, इसकी मेनिफेस्ट से पढ़ा जाता है, इससे पहले कि आप इसे लें |
| `failproofai policies show <owner>/<repo> --releases` | हर संस्करण जो इसने प्रकाशित किया है, और कौन सा यहां है |
| `failproofai policies add <source>` | GitHub रिलीज़ से एक नीति पैक इंस्टॉल करें; कोई टैग नहीं नवीनतम लेता है और इसे पिन करता है |
| `failproofai publish` | अपनी नीतियों को एक पैक के रूप में जहाज करें; `--init` शुरू करने के लिए एक लिखता है, और `--min-cli-version <version>` सबसे पुरानी CLI सेट करता है जो इसे इंस्टॉल कर सकती है ([एक पैक में Jev जांच करता है](/hi/policies/publish-a-pack#jev-checks-in-a-pack)) |
| `failproofai policies remove <publisher/name>` | एक पैक की स्थापना रद्द करें |
| `failproofai audit` | स्थानीय एजेंट इतिहास को स्कैन करें और स्थानीय ऑडिट दृश्य खोलें |
| `failproofai audit --schedule [days] --email <address>` | आवर्ती स्थानीय स्कैन शेड्यूल करें और उनके निष्कर्षों को ईमेल करें |
| `failproofai audit --status` | रिपोर्ट पता, अंतराल, और अगली अनुसूचित स्कैन दिखाएं |
| `failproofai audit --no-schedule` | ऑडिट इतिहास को हटाए बिना आवर्ती स्कैन बंद करें |
| `failproofai harness list` | अतिरिक्त कैप्चर पथ सूचीबद्ध करें |
| `failproofai otel status` | वैकल्पिक [OpenTelemetry रिपोर्टिंग](/hi/reference/otel) का निरीक्षण करें |
| `failproofai jev --url <url> --key-stdin` | Jev को एक कदम में सेट अप करें; प्रदाता URL के होस्ट से लिया जाता है |
| `failproofai jev setup --provider <kind> --key-stdin` | [Jev](/hi/reference/jev-providers) को आपके स्वयं के एंडपॉइंट और कुंजी के माध्यम से टूल कॉल का फैसला करने दें |
| `failproofai jev setup --provider failproofai` | Jev को [FailproofAI Cloud के माध्यम से](/hi/reference/jev-cloud) टूल कॉल का फैसला करने दें, इस मशीन की क्लाउड कुंजी के साथ |
| `failproofai jev setup --mode <m>` | Jev का मोड बदलें: `enforce`, `observe`, या `off` (कॉन्फिग को रखता है, Jev से पूछना बंद करता है) |
| `failproofai jev status` | Jev कॉन्फिग, इसकी अनुमतियां और हाल के फॉलबैक दिखाएं; कभी कुंजी नहीं |
| `failproofai jev test` | एक लाइव Jev अनुरोध भेजें और इसकी विलंबता और संस्करण दिखाएं; जब उत्तर हुक्स के लिए देरी या गलत हो तो 1 से बाहर निकलता है |
| `failproofai jev models` | मॉडल आईडी सूचीबद्ध करें `GET <base>/models` एक एंडपॉइंट परोसता है |
| `failproofai jev remove` | Jev को बंद करें; हुक्स बिल्कुल पहले की तरह रेजेक्स नीतियों को चलाते हैं |
| `failproofai flush --wait` | वर्तमान ईवेंट स्पूल डिलीवर करें |
| `failproofai backfill --since 30d` | पहले से पास किए गए इतिहास को फिर से पढ़ें |
| `failproofai config --pause [duration]` | एक स्थानीय सत्र को डिफ़ॉल्ट रूप से 30 मिनट के लिए, 8 घंटे तक के लिए पॉज़ करें |
| `failproofai config --resume` | एक पॉज़ किए गए स्थानीय सत्र को फिर से शुरू करें; सभी पॉज़ को साफ करने के लिए `--all` जोड़ें |
| `failproofai update` | पैकेज माइग्रेशन को समाप्त करें और डेमन को अपडेट करें |
| `failproofai migrate --dry-run` | लंबित होम-लेआउट माइग्रेशन का पूर्वावलोकन या चलाएं |
| `failproofai uninstall` | पैकेज को हटाने से पहले हुक्स, `failproofai` कौशल और डेमन को निकालें |
| `failproofai --version` | स्थापित पैकेज संस्करण प्रिंट करें |
| `failproofai --help` | कमांड और वैश्विक उपयोग दिखाएं |

## कॉन्फ़िगरेशन फ़्लैग

| फ़्लैग | उपयोग |
| --- | --- |
| `--token <key>` | गैर-इंटरेक्टिव रूप से सेट अप करें और कनेक्ट करें; यह भी `FAILPROOFAI_CLOUD_TOKEN` से पढ़ें |
| `--url <url>` | `app.befailproof.ai` के अलावा कहीं कनेक्ट करें; यह भी `FAILPROOFAI_CLOUD_URL` से पढ़ें |
| `--connect <url>` | केवल नामांकन करें, एक मशीन पर पहले से सेट अप है। डेमन और हर हुक को छोड़ देता है |
| `--machine-id <id>` | स्थिर मशीन ID सेट करें |
| `--machine-label <name>` | एक मशीन का नाम बदलें जो **पहले से कनेक्ट है**। अपने आप यह कभी सेटअप नहीं चलाता है, इसलिए इसे `failproofai config` के बाद दें, सेटअप के दौरान नहीं |
| `--no-transcripts` | ट्रांसक्रिप्ट सामग्री के बिना निर्णय भेजें, और Cloud Jev को चालू न करें, जो प्रत्येक जांच किए गए टूल कॉल और हाल के प्रॉम्प्ट को भेजेगा; एक `jev.json` FailproofAI Cloud के माध्यम से Jev को चलाना हटा दिया जाता है |
| `--disconnect` | क्लाउड नीति पुल और ईवेंट डिलीवरी बंद करें। यह भी Cloud Jev कुंजी को हटाता है और एक `jev.json` जो FailproofAI Cloud नाम देता है; आपकी अपनी Jev सेटअप को जगह में छोड़ा जाता है |
| `--status` | वर्तमान मशीन स्थिति दिखाएं |
| `--pause [duration]` | वर्तमान निर्देशिका में नवीनतम सत्र को पॉज़ करें; सेकंड, मिनट, या घंटे स्वीकार करता है और डिफ़ॉल्ट रूप से 30 मिनट है |
| `--resume` | एक मेल खाने वाले पॉज़ को जल्दी समाप्त करें |
| `--session <id>` | पॉज़ या रिज़्यूम के लिए एक स्पष्ट सत्र को लक्षित करें |
| `--all` | `--resume` के साथ, हर सक्रिय पॉज़ को समाप्त करें |

स्थानीय पॉज़ एक सत्र के लिए अंतर्निर्मित, कस्टम, कन्वेंशन, और पैक नीतियों को निलंबित करते हैं। वे हमेशा समाप्त होते हैं और क्लाउड-प्रबंधित नीतियों को अक्षम नहीं करते हैं। `block-failproofai-commands` — जो हमेशा सक्षम है और स्वयं को अक्षम या पॉज़ नहीं किया जा सकता है — एक सुसज्जित एजेंट को इस एस्केप हैच को स्वयं से उपयोग करने से रोकता है।

| फ़्लैग | उपयोग |
| --- | --- |
| `--install`, `-i` | हार्नेस हुक्स इंस्टॉल करें। इसके बाद के नाम उन नीतियों को सक्षम करते हैं; कोई नहीं हैं, कोई नीति परिवर्तन नहीं |
| `--uninstall`, `-u` | नीतियों को अक्षम करें या हुक्स को निकालें |
| `--cli <names...>` | एक या अधिक समर्थित हार्नेस को लक्षित करें |
| `--scope user\|project\|local\|all` | कॉन्फ़िगरेशन स्कोप चुनें; `all` अनइंस्टॉल के लिए है |
| `--beta` | बीटा नीतियों को शामिल करें |
| `--custom`, `-c <path>` | एक कस्टम नीति फ़ाइल को मान्य करें और लोड करें; दोहराने योग्य |

## डिलीवरी और रखरखाव फ़्लैग

| कमांड | फ़्लैग |
| --- | --- |
| `backfill` | `--since <30d\|6m\|YYYY-MM-DD>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` |

`failproofai update` को `npm install -g failproofai@latest` के बाद चलाया जाना चाहिए; यह होम-लेआउट माइग्रेशन करता है, मेल खाने वाले डेमन बाइनरी को इंस्टॉल करता है, और सेवा को पुनः शुरू करता है। यह तब हर Hermes प्रोफ़ाइल को जो पहले से FailproofAI का उपयोग करता है, जुड़ी हुई देशी प्लगइन में स्थानांतरित करता है और प्रति प्रोफ़ाइल एक लाइन प्रिंट करता है। `--no-daemon` डेमन चरण को छोड़ देता है। `update` गैर-शून्य से बाहर निकलता है जब डेमन को प्रतिस्थापित नहीं किया जा सकता है, एक माइग्रेशन विफल रहता है, या एक Hermes प्रोफ़ाइल को माइग्रेट नहीं किया जा सकता है (उदाहरण के लिए क्योंकि चल रहे डेमन देशी प्लगइन को परोस नहीं सकते, जिस स्थिति में इसके शेल हुक्स को जगह में छोड़ा जाता है)।

## हार्नेस पथ

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

समर्थित हार्नेस नाम हैं `claude`, `codex`, `copilot`, `cursor`, `opencode`, `pi`, `hermes`, `openclaw`, `factory`, `devin`, `antigravity`, और `goose`।

लेबल जब दो रूट एक ही प्रोजेक्ट की प्रतियां रखते हैं तो व्युत्पन्न एजेंट आईडी को नेमस्पेस करते हैं। अतिव्यापी रूट और डुप्लिकेट लेबल को डुप्लिकेट संग्रह या कर्सर भ्रष्टाचार को रोकने के लिए अस्वीकार किया जाता है। अतिरिक्त-पथ कॉन्फ़िगरेशन एक डेमन पुनरारंभ के बिना पुनः लोड होता है।

कंटेनर वातावरण फ़ाइल-कॉन्फ़िगर किए गए अतिरिक्त पथों को एक अल्पविराम-अलग चर के साथ बदल सकते हैं जिसे `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` कहा जाता है, उदाहरण के लिए:

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## पर्यावरण चर

स्थायी मशीन व्यवहार के लिए कॉन्फ़िगरेशन फ़ाइलों का उपयोग करें। पर्यावरण चर कंटेनर, परीक्षण, और एक प्रक्रिया के लिए सबसे उपयोगी हैं।

| चर | उपयोग |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | `--token` के बजाय क्लाउड कुंजी। इसे प्राथमिकता दें: एक तर्क `ps` से हर उपयोगकर्ता द्वारा पढ़ा जा सकता है। इसे `read -s` के साथ या CI गुप्त स्टोर से सेट करें, कभी भी कुंजी को एक कमांड में टाइप न करें, जो किसी भी तरह शेल इतिहास में उतरती है |
| `FAILPROOFAI_CLOUD_URL` | `--url` के बजाय क्लाउड URL। यही चर डेमन पढ़ता है |
| `FAILPROOFAI_HOME` | संपूर्ण `~/.failproofai` लेआउट को पुनः स्थित करें |
| `FAILPROOFAI_LOG_LEVEL` | स्थानीय लॉगिंग विवरण सेट करें |
| `FAILPROOFAI_HOOK_LOG_FILE` | हुक डायग्नोस्टिक्स को एक चयनित फ़ाइल में लिखें |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | इस प्रक्रिया के लिए अनाम टेलीमेट्री अक्षम करें |
| `FAILPROOFAI_NO_FIRST_RUN=1` | इंटरेक्टिव पहले रन सेटअप को छोड़ें |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | पोस्ट-सेटअप स्थानीय ऑडिट को छोड़ें |
| `FAILPROOFAI_LLM_BASE_URL` | LLM नीतियों द्वारा उपयोग किए जाने वाले OpenAI-संगत एंडपॉइंट को ओवरराइड करें |
| `FAILPROOFAI_LLM_API_KEY` | LLM नीतियों द्वारा उपयोग की जाने वाली API कुंजी प्रदान करें |
| `FAILPROOFAI_LLM_MODEL` | LLM नीतियों द्वारा उपयोग किए जाने वाले मॉडल का चयन करें |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | कस्टम नीति मॉड्यूल लोडिंग को बाउंड करें |
| `FAILPROOFAI_NO_DOWNLOAD=1` | पैक्स और डेमन बाइनरी लाने से इंकार करें; जो स्थापित है वह लागू करता रहता है |
| `FAILPROOFAI_PACK_BASE_URL` | `github.com` के बजाय एक मिरर से पैक्स लाएं |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | एक हार्नेस के लिए कॉन्फ़िगर किए गए अतिरिक्त कैप्चर पथों को बदलें |
| `NO_COLOR` | रंगीन टर्मिनल आउटपुट अक्षम करें |

एजेंट-विशिष्ट होम चर जैसे `CLAUDE_PROJECTS_PATH`, `CURSOR_HOME`, `HERMES_HOME`, और `OPENCLAW_HOME` ओवरराइड करते हैं कि Failproof AI उस हार्नेस के लिए स्थानीय सत्र को कहां खोजता है।

## एक मशीन को सुरक्षित रूप से पॉज़ या निकालें

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

एक स्थानीय सत्र पॉज़ क्लाउड-प्रबंधित नीतियों को अक्षम नहीं करता है। क्लाउड प्रवर्तन वर्कफ़्लो के माध्यम से क्लाउड तैनातियों को पुनः स्थापित करें जब रोलआउट स्वयं समस्या है।

npm पैकेज को निकालने से पहले, स्थापित हुक्स और डेमन को निकालें:

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

संस्करण-विशिष्ट विवरण के लिए `failproofai <command> --help` चलाएं।

<Warning>
  `npm rm -g failproofai` से पहले `failproofai uninstall` चलाएं; npm स्थापित एजेंट हुक्स, `failproofai` कौशल या डेमन सेवा को नहीं हटाता है।
</Warning>
