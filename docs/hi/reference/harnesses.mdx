एक हार्नेस वह है जिसके अंदर आपका एजेंट वास्तव में चलता है। Failproof AI बारह का समर्थन करता है, दो वर्गों में:

- **कोडिंग CLIs** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **चैट और असिस्टेंट गेटवे** (2) — Hermes (Slack, Telegram, cron), OpenClaw (स्व-होस्ट किया गया असिस्टेंट)

एक ही नीतियां और एक ही सेशन इतिहास लागू होता है भले ही कोई एजेंट किसी में भी चल रहा हो। एक एडाप्टर परत प्रत्येक हार्नेस के मूल इवेंट नामों, टूल नामों और टूल-इनपुट फील्ड्स को किसी भी नीति के चलने से पहले 29 canonical इवेंट्स पर मैप करता है।

एक एजेंट जो बारह में से **किसी में भी** नहीं चलता है वह [Python SDK](/hi/reference/custom-agents) के साथ सीधे instrumented होता है। यह एक अलग अनुबंध है, और स्पष्ट रूप से कहना लायक है: SDK ट्रेसिंग, सेशन, मूल्यांकन और ऑडिट्स प्रदान करता है — **यह अपने आप पर नीतियों को लागू नहीं करता।** किसी असुरक्षित कार्य को निष्पादित होने से पहले ब्लॉक करने के लिए आपके रनटाइम के टूल सीमा पर एक enforcement hook की आवश्यकता होती है; [हमसे संपर्क करें](mailto:support@befailproof.ai) और हम इसे मैप करेंगे।

| हार्नेस | समर्थित hook scopes |
| --- | --- |
| Claude Code | User, project, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | User, project |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | User, project |
| Hermes, OpenClaw | User |

प्रत्येक integration अपने मूल hook इवेंट नामों, टूल नामों और टूल-इनपुट फील्ड्स को नीतियों के चलने से पहले normalize करता है। एक नीति केवल उन इवेंट्स पर कार्य कर सकती है जो हार्नेस expose करता है; आप जिस सटीक हार्नेस और संस्करण को deploy करते हैं उस पर end-of-turn और instruction के व्यवहार को परीक्षण करें।

## Enforcement capability

"Block" का अर्थ है कि current adapter का returned verdict नाम दिए गए हार्नेस द्वारा consumed है। Post-tool blocking परिणाम को मॉडल को दिखाया गया परिणाम बदल सकता है लेकिन ऐसे tool side effect को पूर्ववत नहीं कर सकता जो पहले से ही हुआ हो।

| हार्नेस | Verified blocking इवेंट्स | Observe-only या non-blocking caveats |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact`, और कई task/config इवेंट्स | `PostToolUse`, session lifecycle, notifications, और post-failure इवेंट्स observational हैं। |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Post-tool blocking execution के बाद परिणाम को प्रतिस्थापित करता है; session-start और compact इवेंट्स current adapter में observational हैं। |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Post-tool blocking execution के बाद परिणाम को प्रतिस्थापित करता है; session और notification इवेंट्स observational हैं। |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` और session इवेंट्स observational हैं। |
| OpenCode | `PreToolUse` | Post-tool और lifecycle इवेंट्स observational हैं; current stop handling एक verified gate के बजाय बाद के turn के लिए guidance है। |
| Pi | `PreToolUse`, `UserPromptSubmit` | Post-tool और lifecycle इवेंट्स observational हैं; stop guidance एक बाद के turn पर लागू होती है। |
| Hermes | `PreToolUse` | `deny()` ब्लॉक करता है। `instruct()` कॉल को नहीं रोकता: यह चलता है, और guidance उसके परिणाम की शुरुआत में रखी जाती है। Post-tool, session, और subagent-stop verdicts gates नहीं हैं। |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Post-tool, session, subagent-stop, और compaction इवेंट्स observational हैं। |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Post-tool और subagent-stop verdicts observational हैं। |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, conditional `PermissionRequest` | Permission hooks प्रत्येक permission mode में नहीं चलते; post-tool और session इवेंट्स observational हैं। |
| Antigravity CLI | `PreToolUse`, `Stop` | User-prompt और post-tool verdicts observational हैं; prompt instructions को अभी भी inject किया जा सकता है। |
| Goose | `PreToolUse` | User-prompt, post-tool, और session इवेंट्स observational हैं। एक native blocking stop hook upstream में मौजूद है लेकिन current adapter द्वारा installed नहीं है। |

Capabilities संस्करण-संवेदनशील हैं। एजेंट CLI को अपग्रेड करने के बाद फिर से परीक्षण करें, विशेष रूप से जब कोई नीति prompt, stop, permission, या post-tool व्यवहार के बजाय सामान्य pre-tool gate पर निर्भर करती हो।

### Hermes native plugin

Hermes को shell command के बजाय profile-local native plugin के माध्यम से integrated किया जाता है। Installation प्रत्येक default और named Hermes profile के `plugins/failproofai` को npm package में shipped plugin से लिंक करता है (एक कॉपी जहां symlink नहीं बनाया जा सकता), इसे उस profile के `config.yaml` में enable करता है, और केवल legacy FailproofAI shell-hook entries को migrate करता है। क्योंकि plugin linked है, `npm install -g failproofai@latest` इसे reinstall के बिना अपडेट करता है। यह प्रत्येक hook पर process spawn से बचाता है। Plugin Hermes 0.20.0 और बाद में समर्थन करता है।

Legacy shell hooks (1.0.5 और पहले द्वारा installed) Hermes cron jobs **नहीं** चेक करते: प्रत्येक cron run अपना खुद का hook scope बनाता है, जिसे native plugin join करता है और `config.yaml` shell hooks नहीं करते। `failproofai update` प्रत्येक profile को migrate करता है जो पहले से ही FailproofAI का उपयोग करता है linked plugin के लिए। अगर running daemon plugin को serve नहीं कर सकता, `update` shell hooks को जगह पर छोड़ देता है और non-zero exit करता है; daemon को अपडेट करने के लिए `failproofai config` चलाएं, फिर `failproofai update` फिर से चलाएं। Cron jobs अपने अगले run पर plugin लोड करते हैं; running gateways और interactive sessions को इसे वहां लोड करने के लिए restart करें।

Hermes पर, `deny()` कॉल को ब्लॉक करता है और `instruct()` नहीं करता: कॉल चलता है, और guidance उसके परिणाम की शुरुआत में रखी जाती है — एक JSON result के पहले key `failproof_policy_reminder` के रूप में, या एक leading `[FailproofAI policy reminder (...)]` line के रूप में — इसलिए मॉडल इसे output के साथ पढ़ता है, और scripts जो result parse करते हैं काम करते रहते हैं। एक policy का reminder प्रति turn एक बार दिखाया जाता है, और एक बड़े result पर छोटा रखा जाता है। `deny()` का उपयोग तब करें जब कोई कार्य बिल्कुल भी नहीं होना चाहिए: `instruct()` अब पहले कार्य को नहीं रोकता। `execute_code` script से बनाए गए tool calls अपना reminder उस `execute_code` परिणाम पर रखते हैं जो मॉडल पढ़ता है; script की अपनी result की कॉपी को untouched रखा जाता है। मॉडल को कहा जाता है कि अपने replies में reminder को quote न करे।

Plugin middleware के बिना Hermes build matching call को एक बार "FailproofAI policy guidance" के साथ hold करके fallback करता है; अगला model response इसे दोहरा सकता है, या बिना फिर से hold किए गए दूसरे tool के साथ एक ही काम कर सकता है।

Tool names Hermes versions में match किए जाते हैं: `process_manage`, `cronjob_manage`, और `todo_list` (Hermes 0.21) को `process`, `cronjob`, और `todo` (Hermes 0.20) जैसे माना जाता है। प्रत्येक बार Hermes plugin लोड करता है यह profile के `plugin-data/agent-plugin-failproofai-5296f299/` directory में `heartbeat.json` लिखता है, Hermes version, plugin का path और version, और hooks जो Hermes को accepted करते हैं को record करता है। Disabled, incomplete, duplicated, या newly unconfigured profile को detect करने के लिए `failproofai config --status` चलाएं, या legacy shell hooks पर अभी भी है (जिसे "Hermes cron jobs are not checked" के रूप में reported किया जाता है)।

### OpenClaw plugin

OpenClaw FailproofAI को in-process gateway plugin के रूप में लोड करता है, प्रत्येक profile के `openclaw.json` में registered। Hermes plugin की तरह, यह प्रत्येक verdict के लिए अपने socket के माध्यम से local `failproofaid` daemon से पूछता है, इसलिए इसे एक running daemon की आवश्यकता होती है: installation इसके बिना refuse करता है, और अगर daemon उत्तर नहीं दे सकता, tool calls और prompts को ब्लॉक किया जाता है और कारण gateway log में लिखा जाता है। `npm install -g failproofai@latest` के बाद, OpenClaw gateway को restart करें ताकि यह updated plugin लोड करे।

### Codex hook trust

Codex 0.129 और बाद में `~/.codex/hooks.json` से hook को केवल तब चलाता है जब आप इसे interactive `codex` ("Review hooks") में approve करते हैं; जब तक, प्रत्येक Codex session — headless `codex exec` सहित — इसे skip करता है। Codex के system config, Linux और macOS पर `/etc/codex/config.toml`, में hooks बिना उस approval के चलते हैं।

इसलिए जब `failproofai config` (या `policies --install --cli codex` user scope पर) sudo का उपयोग कर सकता है, यह Codex hooks को `/etc/codex/config.toml` में `# >>> failproofai managed hooks >>>` और `# <<< failproofai managed hooks <<<` के बीच लिखता है, और उस file के बाकी को जैसे था वैसे छोड़ देता है। File मशीन पर प्रत्येक account पर लागू होता है। `failproofai uninstall` और `failproofai config` में Codex को untick करने से block फिर से हटा दिया जाता है।

Sudo के बिना, और Windows पर, hooks `~/.codex/hooks.json` में रहते हैं। `failproofai config` और `failproofai config --status` तब Codex को enforcing के रूप में count नहीं करते जब तक hooks को approve न किया जाए, और कहते हैं कि इसे कैसे ठीक करें: `failproofai config` को फिर से चलाएं और sudo allow करें, या एक बार `codex` खोलें और hooks को approve करें।

## Capture और policy hooks को install करें

<Tabs>
  <Tab title="Dashboard">
    1. **Administration → Keys** खोलें और `events:add` और `policies:pull` के साथ एक key बनाएं, मशीन या environment के लिए नाम दिया गया।
    2. Target machine पर, displayed key के साथ local CLI को connect करें और harness hooks को install करें।
    3. एक नया agent session शुरू करें, फिर **Observe → Events** के तहत अपने hook और session इवेंट्स को confirm करें।
    4. एक ही समय विंडो के लिए **Observe → policy** खोलें और confirm करें कि एक policy decision मशीन को attributed है।

    Connection एक machine key के साथ शुरू होता है। Confirm करें कि इसमें अपने secret को copy करने से पहले ingestion और policy-delivery permissions दोनों शामिल हैं।

    ![नई API key drawer जिसका उपयोग event ingestion और policy delivery permissions देने के लिए किया जाता है।](/images/dashboard/key-create.png)

    Hooks को install करने के बाद, Events stream को machine और environment से नई इवेंट्स दिखनी चाहिए जिसे आपने connect किया है।

    ![Live Events stream जिसका उपयोग confirm करने के लिए किया जाता है कि नया installed harness report कर रहा है।](/images/dashboard/events-stream.png)

    अंत में, verify करें कि policy decisions उसी मशीन को attributed हैं। यह confirm करता है कि harness trace इवेंट्स के साथ-साथ policy activity भी report कर रहा है।

    ![Policy page जिसका उपयोग newly connected harness से policy decisions को verify करने के लिए किया जाता है।](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Machine key को shell में read करें। `read -s` इसे एक prompt पर लेता है जो echo नहीं करता, इसलिए यह कभी command में या shell history में दिखाई नहीं देता:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    फिर machine को setup करें — यह हर detected harness के लिए hooks को wire करता है, daemon को install करता है, और Cloud को connect करता है:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    Setup अपने आप पर कोई नीति enable नहीं करता, जो दूसरे command के लिए है।

    या named harnesses और एक configuration scope को target करें:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    Project scope hook configuration को एक repository के साथ रखता है। User scope repositories में काम को cover करता है। Claude Code भी local scope को support करता है; support harness द्वारा varies करता है और CLI unsupported combinations को reject करता है।

    Machine और इसकी इवेंट्स को verify करें:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## Non-default session path जोड़ें

<Tabs>
  <Tab title="Dashboard">
    Extra paths machine पर registered हैं, Cloud में नहीं। एक जोड़ने के बाद, **Observe → Sessions** खोलें, machine के environment के लिए filter करें, और नए path से sessions confirm करें कि दिखाई दे रहे हैं। एक session खोलें और audit में इस पर rely करने से पहले agent, harness, और event timestamps check करें।

    ![Sessions list जो environment को filter किया गया है जो अतिरिक्त capture path से data प्राप्त कर रहा है।](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    एक path को optional label के साथ जोड़ें, फिर configured paths को inspect करें:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Path को `failproofai harness remove-path claude checkout` के साथ remove करें।
  </Tab>
</Tabs>
