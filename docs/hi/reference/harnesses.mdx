हार्नेस वह है जिसमें आपका agent वास्तव में चलता है। Failproof AI इसके बारह को सपोर्ट करता है, दो क्लासेज में:

- **Coding CLIs** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Chat और assistant gateways** (2) — Hermes (Slack, Telegram, cron), OpenClaw (self-hosted assistant)

समान policies और समान session history किसी भी हार्नेस में लागू होते हैं जहां agent चलता है। एक adapter layer प्रत्येक हार्नेस के native event names, tool names, और tool-input fields को 29 canonical events पर मैप करता है, कोई भी policy चलने से पहले।

एक agent जो इन बारह में से **किसी में भी नहीं** चलता है, वह सीधे [Python SDK](/hi/reference/custom-agents) के साथ instrumented है। यह एक अलग contract है, और इसे स्पष्ट रूप से कहना महत्वपूर्ण है: SDK tracing, sessions, evaluations और audits प्रदान करता है — **यह अपने आप पर policies को enforce नहीं करता।** किसी असुरक्षित action को इसके execute होने से पहले block करने के लिए आपके runtime के tool boundary पर एक enforcement hook की जरूरत है; [हमसे संपर्क करें](mailto:support@befailproof.ai) और हम इसे मैप कर देंगे।

| Harness | समर्थित hook scopes |
| --- | --- |
| Claude Code | User, project, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | User, project |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | User, project |
| Hermes, OpenClaw | User |

प्रत्येक integration अपने native hook event names, tool names, और tool-input fields को normalize करता है policies चलने से पहले। एक policy केवल उन events पर कार्य कर सकता है जो हार्नेस expose करता है; end-of-turn और instruction behavior को उसी exact harness और version पर test करें जो आप deploy करते हैं।

## Enforcement capability

"Block" का अर्थ है कि current adapter का returned verdict नामित हार्नेस द्वारा consumed है। Post-tool blocking परिणाम को model के सामने दिखाया जाने वाला बदल सकता है लेकिन tool side effect को undo नहीं कर सकता जो पहले से ही हुआ है।

| Harness | सत्यापित blocking events | Observe-only या non-blocking caveats |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact`, और कई task/config events | `PostToolUse`, session lifecycle, notifications, और post-failure events observational हैं। |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Post-tool blocking execution के बाद result को बदलता है; session-start और compact events current adapter में observational हैं। |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Post-tool blocking execution के बाद result को बदलता है; session और notification events observational हैं। |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` और session events observational हैं। |
| OpenCode | `PreToolUse` | Post-tool और lifecycle events observational हैं; current stop handling later turn के लिए guidance है न कि verified gate। |
| Pi | `PreToolUse`, `UserPromptSubmit` | Post-tool और lifecycle events observational हैं; stop guidance later turn को लागू होता है। |
| Hermes | `PreToolUse` | `deny()` block करता है। `instruct()` call को रोकता नहीं है: यह चलता है, और guidance इसके result की शुरुआत में रखी जाती है। Post-tool, session, और subagent-stop verdicts gates नहीं हैं। |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Post-tool, session, subagent-stop, और compaction events observational हैं। |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Post-tool और subagent-stop verdicts observational हैं। |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, conditional `PermissionRequest` | Permission hooks हर permission mode में नहीं चलते; post-tool और session events observational हैं। |
| Antigravity CLI | `PreToolUse`, `Stop` | User-prompt और post-tool verdicts observational हैं; prompt instructions अभी भी injected की जा सकती हैं। |
| Goose | `PreToolUse` | User-prompt, post-tool, और session events observational हैं। एक native blocking stop hook upstream में exists है लेकिन current adapter द्वारा installed नहीं है। |

Capabilities version-sensitive हैं। Agent CLI को upgrade करने के बाद re-test करें, खासकर जब एक policy prompt, stop, permission, या post-tool behavior पर निर्भर हो rather than common pre-tool gate पर।

### Hermes native plugin

Hermes एक shell command की जगह एक profile-local native plugin के माध्यम से integrated है। Installation हर default और named Hermes profile के `plugins/failproofai` को npm package में shipped plugin से link करता है (एक copy जहां एक symlink create नहीं हो सकता), इसे उस profile के `config.yaml` में enable करता है, और केवल legacy FailproofAI shell-hook entries को migrate करता है। चूंकि plugin linked है, `npm install -g failproofai@latest` इसे बिना reinstall के update करता है। यह हर hook पर process spawn से बचाता है। Plugin Hermes 0.20.0 और बाद में को support करता है।

Legacy shell hooks (1.0.5 और earlier द्वारा installed) Hermes cron jobs को **check नहीं** करते: हर cron run अपना खुद का hook scope बनाता है, जो native plugin join करता है और `config.yaml` shell hooks नहीं करते। `failproofai update` हर profile को migrate करता है जो पहले से ही FailproofAI use करता है linked plugin में। अगर running daemon plugin को serve नहीं कर सकता, `update` shell hooks को जगह पर छोड़ता है और non-zero exit करता है; `failproofai config` को daemon को update करने के लिए चलाएं, फिर `failproofai update` को फिर से चलाएं। Cron jobs अपने अगले run पर plugin को load करते हैं; running gateways और interactive sessions को इसे load करने के लिए restart करें।

Hermes पर, `deny()` call को block करता है और `instruct()` नहीं: call चलता है, और guidance इसके result की शुरुआत में रखी जाती है — एक JSON result के रूप में पहली key, `failproof_policy_reminder`, या एक leading `[FailproofAI policy reminder (...)]` line — तो model इसे output के साथ पढ़ता है, और scripts जो result को parse करते हैं काम करते रहते हैं। एक policy का reminder एक turn में एक बार दिखाया जाता है, और एक बड़े result पर short रखा जाता है। `deny()` का उपयोग करें जब एक action बिल्कुल नहीं होना चाहिए: `instruct()` अब पहले action को stop नहीं करता। `execute_code` script से किए गए tool calls अपने reminder को `execute_code` result पर रखते हैं जो model पढ़ता है; script की अपनी copy result के बिना रखी जाती है। Model को कभी भी अपने replies में एक reminder को quote न करने के लिए कहा जाता है।

एक Hermes build plugin middleware के बिना matching call को एक बार "FailproofAI policy guidance" के साथ hold करने के लिए fallback करता है; अगला model response इसे repeat कर सकता है, या बिना फिर से hold किए same work दूसरे tool के साथ कर सकता है।

Tool names को Hermes versions में match किया जाता है: `process_manage`, `cronjob_manage`, और `todo_list` (Hermes 0.21) को `process`, `cronjob`, और `todo` (Hermes 0.20) की तरह treat किया जाता है। हर बार जब Hermes plugin को load करता है तो `heartbeat.json` को profile के `plugin-data/agent-plugin-failproofai-5296f299/` directory में लिखता है, Hermes version, plugin का path और version, और hooks जो Hermes ने accept किए, record करते हुए। `failproofai config --status` को एक disabled, incomplete, duplicated, या newly unconfigured profile का पता लगाने के लिए चलाएं, या एक जो अभी भी legacy shell hooks पर है (रिपोर्ट किया जाता है "Hermes cron jobs are not checked")।

### OpenClaw plugin

OpenClaw FailproofAI को एक in-process gateway plugin के रूप में load करता है, हर profile के `openclaw.json` में registered। Hermes plugin की तरह, यह हर verdict के लिए local `failproofaid` daemon से इसके socket पर पूछता है, तो इसे एक running daemon की जरूरत है: installation बिना एक के refuse करता है, और अगर daemon answer नहीं दे सकता, tool calls और prompts block होते हैं और reason gateway log में written होता है। `npm install -g failproofai@latest` के बाद, OpenClaw gateway को restart करें ताकि यह updated plugin को load करे।

### Codex hook trust

Codex 0.129 और बाद में `~/.codex/hooks.json` से एक hook केवल तभी चलाता है जब आप इसे interactive `codex` ("Review hooks") में approve करते हैं; तब तक, हर Codex session — headless `codex exec` सहित — इसे skip करता है। Codex के system config में hooks, `/etc/codex/config.toml` Linux और macOS पर, बिना उस approval के चलते हैं।

तो जब `failproofai config` (या `policies --install --cli codex` user scope पर) sudo use कर सकता है, यह Codex hooks को `/etc/codex/config.toml` में, `# >>> failproofai managed hooks >>>` और `# <<< failproofai managed hooks <<<` के बीच लिखता है, और बाकी file को जैसा था वैसा छोड़ता है।

वह file machine के हर account पर लागू होता है, तो इसमें हर hook `/opt/failproofai-codex/codex-hook` चलाता है, एक short script जो root के स्वामित्व में है। Script event को हर account के अपने failproofai को hand करता है जिसने hooks को वहां setup किया है, और किसी other account के लिए कुछ नहीं करता। एक अन्य account जो failproofai के Codex hooks चाहता है उन्हें अपने लिए setup करता है।

Block को लिखने से पहले, और हर `failproofai update` पर, failproofai check करता है कि `/etc/codex/config.toml` self, script, उन के ऊपर हर directory, और `sh`, `id` और `cat` जो यह चलाता है, root के हैं और कोई और लिख नहीं सकता, और कि हर account का failproofai उस account या root के हैं। Install पर, जब वह check fail होता है, आपके hooks `~/.codex/hooks.json` में रहते हैं। Update पर, एक script जो इसे fail करता है block को बाहर निकालता है, और एक account जिसका failproofai fail करता है block से निकाला जाता है; एक बार fixed होने पर `failproofai config` को फिर से चलाएं। `failproofai update` एक earlier version द्वारा written block को भी rewrite करता है script use करने के लिए, जिसे sudo की जरूरत है।

Sudo के बिना, और Windows पर, hooks `~/.codex/hooks.json` में रहते हैं। `failproofai config` और `failproofai config --status` तब Codex को enforce करने के रूप में count नहीं करते जब तक hooks approve नहीं होते, और कैसे fix करें कहते हैं: `failproofai config` को फिर से चलाएं और sudo allow करें, या `codex` को एक बार खोलें और hooks को approve करें।

## Install capture और policy hooks

<Tabs>
  <Tab title="Dashboard">
    1. **settings → api keys** खोलें और `events:add` और `policies:pull` के साथ एक key create करें, machine या environment के लिए नाम दिया।
    2. Target machine पर, local CLI को displayed key के साथ connect करें और harness hooks को install करें।

    Connection एक machine key के साथ शुरू होता है। Confirm करें कि इसमें अपनी secret को copy करने से पहले ingestion और policy-delivery दोनों permissions शामिल हैं।

    Machine key को shell में पढ़ें। `read -s` इसे एक prompt पर लेता है जो echo नहीं करता, तो यह कभी भी command या shell history में नहीं दिखता:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    फिर machine को setup करें — यह हर detected harness के लिए hooks wire करता है, daemon को install करता है, और Cloud से connect करता है:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    Setup अपने आप कोई policy enable नहीं करता, जो दूसरी command के लिए है।

    या named harnesses और एक configuration scope को target करें:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    Machine और इसके events को verify करें:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```

## एक non-default session path जोड़ें

<Tabs>
  <Tab title="Dashboard">
    Extra paths machine पर register होते हैं, Cloud में नहीं। एक जोड़ने के बाद, **trace → sessions** खोलें, machine के environment के लिए filter करें, और confirm करें कि नए path से sessions दिखाई देते हैं। एक session खोलें और इसे audit में rely करने से पहले agent, harness, और event timestamps को check करें।

    ![Sessions list machine के environment के लिए filter किया गया जो additional capture path से data receive कर रहा है।](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    एक optional label के साथ एक path जोड़ें, फिर configured paths को inspect करें:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    `failproofai harness remove-path claude checkout` के साथ एक path को हटाएं।
  </Tab>
</Tabs>
