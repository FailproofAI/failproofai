हार्नेस वह है जिसके अंदर आपका एजेंट वास्तव में चलता है। Failproof AI बारह को समर्थन देता है, दो वर्गों में:

- **कोडिंग CLIs** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **चैट और असिस्टेंट गेटवे** (2) — Hermes (Slack, Telegram, cron), OpenClaw (स्व-होस्टेड असिस्टेंट)

एक ही नीतियां और एक ही सेशन हिस्ट्री लागू होती हैं, चाहे एजेंट किसी भी हार्नेस में चलता हो। एक एडाप्टर लेयर प्रत्येक हार्नेस के मूल इवेंट नामों, टूल नामों और टूल-इनपुट फ़ील्ड को किसी भी नीति के चलने से पहले 29 canonical इवेंट्स में मैप करता है।

एक एजेंट जो बारह में से **किसी** में भी नहीं चलता है, वह [Python SDK](/hi/reference/custom-agents) के साथ सीधे instrumented होता है। यह एक अलग अनुबंध है, और स्पष्ट रूप से कहने के लिए महत्वपूर्ण है: SDK ट्रेसिंग, सेशन, मूल्यांकन और ऑडिट प्रदान करता है — **यह अपने आप नीतियों को लागू नहीं करता।** किसी असुरक्षित कार्य को निष्पादन से पहले ब्लॉक करने के लिए आपके runtime के टूल बाउंड्री पर enforcement hook की आवश्यकता है; [हमसे संपर्क करें](mailto:support@befailproof.ai) और हम इसे मैप करेंगे।

| हार्नेस | समर्थित hook स्कोप |
| --- | --- |
| Claude Code | User, project, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | User, project |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | User, project |
| Hermes, OpenClaw | User |

प्रत्येक एकीकरण नीतियों के चलने से पहले अपने मूल hook इवेंट नामों, टूल नामों और टूल-इनपुट फ़ील्ड को सामान्य करता है। एक नीति केवल उन इवेंट्स पर कार्य कर सकती है जो हार्नेस expose करता है; turn के अंत और instruction behavior को सटीक हार्नेस और version पर परीक्षण करें जिसे आप deploy करते हैं।

## Enforcement क्षमता

"Block" का मतलब है कि वर्तमान एडाप्टर का returned verdict named हार्नेस द्वारा उपभोग किया जाता है। Post-tool blocking परिणाम को प्रतिस्थापित कर सकता है जो मॉडल को दिखाया जाता है लेकिन ऐसे tool side effect को पूर्ववत नहीं कर सकता जो पहले से ही हो चुका हो।

| हार्नेस | Verified blocking events | अवलोकन-केवल या non-blocking चेतावनियां |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact`, और कई task/config events | `PostToolUse`, session lifecycle, notifications, और post-failure events अवलोकन योग्य हैं। |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Post-tool blocking निष्पादन के बाद परिणाम को प्रतिस्थापित करता है; session-start और compact events वर्तमान एडाप्टर में अवलोकन योग्य हैं। |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Post-tool blocking निष्पादन के बाद परिणाम को प्रतिस्थापित करता है; session और notification events अवलोकन योग्य हैं। |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` और session events अवलोकन योग्य हैं। |
| OpenCode | `PreToolUse` | Post-tool और lifecycle events अवलोकन योग्य हैं; वर्तमान stop handling बाद के turn के लिए निर्देशन के बजाय verified gate है। |
| Pi | `PreToolUse`, `UserPromptSubmit` | Post-tool और lifecycle events अवलोकन योग्य हैं; stop guidance बाद के turn पर लागू होती है। |
| Hermes | `PreToolUse` | Post-tool, session, और subagent-stop verdicts gates नहीं हैं। |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Post-tool, session, subagent-stop, और compaction events अवलोकन योग्य हैं। |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Post-tool और subagent-stop verdicts अवलोकन योग्य हैं। |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, conditional `PermissionRequest` | Permission hooks हर permission mode में नहीं चलते; post-tool और session events अवलोकन योग्य हैं। |
| Antigravity CLI | `PreToolUse`, `Stop` | User-prompt और post-tool verdicts अवलोकन योग्य हैं; prompt instructions अभी भी inject किए जा सकते हैं। |
| Goose | `PreToolUse` | User-prompt, post-tool, और session events अवलोकन योग्य हैं। एक मूल blocking stop hook upstream में मौजूद है लेकिन वर्तमान एडाप्टर द्वारा स्थापित नहीं है। |

क्षमताएं version-sensitive हैं। एजेंट CLI को अपग्रेड करने के बाद फिर से परीक्षण करें, विशेषकर जब कोई नीति prompt, stop, permission, या post-tool behavior के बजाय common pre-tool gate पर निर्भर करती है।

## कैप्चर और नीति hooks स्थापित करें

<Tabs>
  <Tab title="Dashboard">
    1. **Administration → Keys** खोलें और `events:add` और `policies:pull` के साथ एक key बनाएं, मशीन या वातावरण के लिए नाम दें।
    2. लक्ष्य मशीन पर, प्रदर्शित key के साथ स्थानीय CLI को जोड़ें और harness hooks स्थापित करें।
    3. एक नया एजेंट सेशन शुरू करें, फिर **Observe → Events** के तहत इसके hook और session events की पुष्टि करें।
    4. **Observe → policy** खोलें एक ही समय विंडो के लिए और पुष्टि करें कि कोई नीति निर्णय मशीन को जिम्मेदार है।

    कनेक्शन एक मशीन key से शुरू होता है। पुष्टि करें कि इसमें अपने secret को कॉपी करने से पहले ingestion और policy-delivery दोनों अनुमतियां शामिल हैं।

    ![नई API key ड्रॉवर event ingestion और policy delivery अनुमतियां प्रदान करने के लिए उपयोग की जाती है।](/images/dashboard/key-create.png)

    Hooks स्थापित करने के बाद, Events stream को उस मशीन और वातावरण से नई events दिखानी चाहिए जिसे आपने जोड़ा है।

    ![लाइव Events stream एक नए स्थापित harness की reporting की पुष्टि करने के लिए उपयोग किया जाता है।](/images/dashboard/events-stream.png)

    अंत में, सत्यापित करें कि नीति निर्णय एक ही मशीन को जिम्मेदार हैं। यह पुष्टि करता है कि harness trace events के साथ-साथ policy activity की रिपोर्ट कर रहा है।

    ![Policy page नए जुड़े हुए harness से नीति निर्णयों को सत्यापित करने के लिए उपयोग किया जाता है।](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    हर पाए गए harness के लिए hooks स्थापित करें:

    ```bash
    failproofai config \
      --connect https://app.befailproof.ai \
      --token <machine-key>
    failproofai policies --install
    ```

    या named harnesses और एक configuration scope को लक्ष्य करें:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    Project scope hook configuration को एक repository के साथ रखता है। User scope repositories में काम को कवर करता है। Claude Code भी local scope को समर्थन देता है; समर्थन harness द्वारा भिन्न होता है और CLI असमर्थित संयोजनों को अस्वीकार करता है।

    मशीन और इसके events को सत्यापित करें:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## एक non-default session path जोड़ें

<Tabs>
  <Tab title="Dashboard">
    अतिरिक्त paths मशीन पर registered होते हैं, Cloud में नहीं। एक को जोड़ने के बाद, **Observe → Sessions** खोलें, मशीन के वातावरण के लिए filter करें, और नए path से sessions दिखाई दें। एक session खोलें और agent, harness, और event timestamps को जांचें इसे audit में उपयोग करने पर निर्भर होने से पहले।

    ![Sessions list को अतिरिक्त capture path से डेटा प्राप्त करने वाले वातावरण के लिए filtered।](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    एक optional label के साथ path जोड़ें, फिर configured paths inspect करें:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    `failproofai harness remove-path claude checkout` के साथ एक path को हटाएं।
  </Tab>
</Tabs>

<Tip>
  स्थापन के बाद एक नया सेशन चलाएं। लाइव event stream और एक वास्तविक नीति निर्णय दोनों को सत्यापित करें rollout को expand करने से पहले।
</Tip>
