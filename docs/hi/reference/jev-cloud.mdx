यह [Jev नीतियों](/hi/policies/jev) के लिए Cloud मार्ग संदर्भ है। Jev, TypeSafe का वर्गीकरणकर्ता, प्रत्येक tool call को आपने जो वास्तव में माँगा है उसके विरुद्ध पढ़ता है और आपकी नीतियों के साथ उत्तर देता है, कभी उनके बजाय नहीं। **FailproofAI Cloud** के माध्यम से, एक जुड़ी हुई मशीन Jev का उपयोग उसी कुंजी के साथ करती है जिससे वह पहले से जुड़ी होती है: कोई TypeSafe खाता नहीं, कोई दूसरी कुंजी नहीं, कोई एंडपॉइंट कॉन्फ़िगर करने के लिए नहीं। प्रत्येक कॉल आपके संगठन की मौजूदा योजना भत्ते के विरुद्ध चार्ज किया जाता है।

Jev जो कुछ भी करता है वह [bring-your-own-key सेटअप](/hi/reference/jev-providers) से अपरिवर्तित है: कठोर नीतियाँ अंतिम रहती हैं, एक समीक्षा योग्य नीति की अस्वीकृति केवल तभी साफ़ की जाती है जब Jev से ठीक उसी चिंता के बारे में पूछा गया था, और कोई भी विफलता उस कॉल के लिए regex परिणाम में वापस आ जाती है।

<Note>
**failproofai 1.0.8-beta.0** या बाद में आवश्यक है। 1.0.7 में कोई Jev नहीं है, भले ही यह 1.0.7 betas के ऊपर क्रमबद्ध हो। Jev config के बिना कुछ नहीं बदलता: hooks regex नीतियों को बिल्कुल पहले की तरह चलाते हैं।
</Note>

## शुरुआत करने से पहले

FailproofAI को उस मशीन पर इंस्टॉल करें जहाँ आपका एजेंट चलता है और इसके hooks को एक [समर्थित harness](/hi/reference/harnesses) से जोड़ें। यदि आप शुरू से शुरुआत कर रहे हैं, तो hook इंस्टॉलेशन के माध्यम से [quickstart](/hi/start/quickstart) का पालन करें। `failproofai --version` के साथ स्थापित CLI की जाँच करें; यदि यह Jev से पहले है तो इसे अपडेट करें। आपको अपने संगठन के **Administration → Keys** पृष्ठ तक पहुँचने के लिए एक मशीन कुंजी बनाने की भी आवश्यकता है।

Jev `PreToolUse` या `PermissionRequest` gate पर नामित tool calls की समीक्षा करता है। यह सत्र में हर event की समीक्षा नहीं करता। Jev को नीति अस्वीकृति को साफ़ करते हुए देखने के लिए, आपको एक स्थापित नीति की आवश्यकता है जिसे [reviewable](/hi/policies/authority) चिन्हित किया गया हो; सभी अन्य नीति अस्वीकृतियाँ अंतिम रहती हैं।

## इसे चालू करें

1. **Jev के साथ एक कुंजी बनाएँ।** FailproofAI Cloud डैशबोर्ड में, **Administration → Keys → Create key** खोलें और **machine** प्रीसेट चुनें। यह एक मशीन को आवश्यक तीन अनुमतियाँ देता है: `events:add` (गतिविधि भेजें), `policies:pull` (नीतियाँ प्राप्त करें) और `jev:evaluate` (Jev, आपके संगठन की योजना के विरुद्ध चार्ज किया गया)। एक कुंजी दूसरे दो के बिना `jev:evaluate` नहीं ले सकती।
2. **मशीन को उस कुंजी से कनेक्ट करें।** प्रॉम्प्ट पर इसका एकबारी रहस्य पढ़ें, फिर पूर्ण सेटअप कमांड चलाएँ:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` daemon को इंस्टॉल करता है, इसे जो एजेंट CLIs मिलते हैं उनके लिए hooks जोड़ता है, और मशीन को कनेक्ट करता है। environment variable कुंजी को कमांड के arguments और आपके shell history से दूर रखता है। यदि आपका harness बाद में इंस्टॉल किया गया था, तो [इसे explicitly जोड़ें](/hi/start/quickstart)।

   यदि आपका संगठन होस्ट किए गए एक के बजाय अपना FailproofAI Cloud चलाता है, तो इसका पता जोड़ें: `--url https://<your dashboard host>` (या `FAILPROOFAI_CLOUD_URL` export करें)। इसके बिना कुंजी को होस्ट की गई सेवा के विरुद्ध जाँचा जाता है और कनेक्शन विफल हो जाता है। यदि उस होस्ट का प्रमाणपत्र निजी CA से आता है, तो CA को मशीन के सिस्टम trust store में इंस्टॉल करें (`update-ca-certificates` के साथ उदाहरण के लिए), न कि केवल `NODE_EXTRA_CA_CERTS` में: जो daemon events भेजता है और नीतियाँ खींचता है वह सिस्टम store को पढ़ता है। [Troubleshooting](/hi/reference/troubleshooting) देखें।

बस इतना ही। कनेक्ट करने से कुंजी को स्टोर करता है और, जब मशीन के पास **कोई** Jev config नहीं होता है, तब FailproofAI Cloud के लिए एक लिखता है। मशीन की पहली deployment से (लगभग 30 s के भीतर) FailproofAI Cloud मोड सेट करता है: `enforce` जब कोई Jev नीति इसे deploy की जाती है, `off` जब नहीं ([Who sets the mode](#who-sets-the-mode) देखें)। आउटपुट ऐसा कहता है:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

FailproofAI Cloud पर चेक चलते हैं। मशीन पर अपने चेक जोड़ने के लिए, एक pack इंस्टॉल करें:

```bash
failproofai policies add FailproofAI/jev-policies
```

**`--no-transcripts` के साथ, कनेक्ट करने से Jev नहीं चालू होता।** Jev प्रत्येक checked tool call और हाल के prompt को FailproofAI Cloud को भेजता है, जो एक decisions-only कनेक्शन से अधिक है जिससे भेजने के लिए कहा गया था। कुंजी अभी भी स्टोर की जाती है, और आउटपुट कहता है कि Jev उपलब्ध है और इसे कैसे चालू करें:

```bash
failproofai jev setup --provider failproofai
```

यह **FailproofAI Cloud के माध्यम से Jev को बंद भी करता है।** एक `jev.json` जो FailproofAI Cloud के माध्यम से Jev चलाता है (transcripts चालू के साथ एक पहले के कनेक्शन द्वारा छोड़ा गया) को हटा दिया जाता है, `config --disconnect` उपयोग करने वाले नियम के आधार पर, और आउटपुट कहता है कि इस मशीन पर FailproofAI Cloud के माध्यम से Jev बंद रहता है। आपके अपने Jev एंडपॉइंट के लिए एक `jev.json` को जैसा है वैसा छोड़ा जाता है, और एक FailproofAI Cloud भी जिसे आपने बंद किया (`--mode off`)।

<Warning>
कनेक्ट करने से **कभी भी** एक मौजूदा `~/.failproofai/jev.json` को overwrite नहीं किया जाता। यदि आप पहले से अपने स्वयं के Jev एंडपॉइंट का उपयोग करते हैं, तो इसका उपयोग जारी रहता है, और आउटपुट कहता है कि फ़ाइल को कॉन्फ़िगर किए गए रूप में छोड़ा गया था — और, जब वह फ़ाइल Jev को बंद रखती है (अस्वीकार किया गया, या बंद किया गया), कहता है और कैसे इसे ठीक करें। उस मशीन को FailproofAI Cloud पर स्विच करने के लिए, `failproofai jev setup --provider failproofai` चलाएँ।
</Warning>

## Who sets the mode

FailproofAI Cloud से जुड़ी एक मशीन पर, **FailproofAI Cloud Jev मोड सेट करता है**; मशीन पर कुछ नहीं:

- `enforce` जब कोई भी Jev (या regex + Jev) नीति मशीन को deploy की जाती है: मशीन की उन नीतियों में से एक को लक्ष्य करने वाले एजेंट से हर checked tool call को FailproofAI Cloud को जाता है, जो अपने चेक को वहाँ स्थापित packs के चेक के साथ पूछता है। Cloud Jev नीति को लक्ष्य करने वाले एजेंट से एक कॉल, अपने स्वयं के pack check के साथ नहीं, बिल्कुल नहीं भेजी जाती। `enforce` में, Jev की अपनी अस्वीकृति चेकें कॉलों को उसी तरह block करती हैं जैसे वे regex verdicts को साफ़ करती हैं जिनकी वे समीक्षा करती हैं।
- `off` जब नहीं: कोई Jev नहीं, `jev.json` कुछ भी कहे।

Jev नीति को कार्य करने से पहले आजमाने के लिए, इसे effect **observe** के साथ deploy करें: इसके चेक अभी भी पूछे जाते हैं, और जो करना चाहते थे वह नीति पृष्ठ पर **would-have** के रूप में दर्ज किया जाता है, लेकिन यह कभी कॉल को block नहीं करता और कभी एक को साफ़ नहीं करता। `failproofai jev setup --mode` और डैशबोर्ड के **Settings → Jev** कहते हैं कि मोड FailproofAI Cloud द्वारा प्रबंधित है और कुछ नहीं बदलता। `jev.json` का Cloud के चेक के लिए उपयोग नहीं किया जाता, भले ही यह दूसरे provider का नाम दे। `failproofai config --disconnect` Jev को मशीन के अपने `jev.json` को वापस देता है।

`failproofai jev status` फिर कहता है `Jev checks run on FailproofAI Cloud (mode: enforce)`। यह हर `both` नीति की समीक्षा करने वाले चेक का नाम भी देता है। fleet पृष्ठ दिखाता है कि मोड वाली मशीन क्यों नहीं पूछ सकती:

- `transcripts_disabled`: मशीन को `--no-transcripts` के साथ कनेक्ट किया गया था, जो Jev को कभी नहीं चालू करता।
- `jev_unconfigured`: मशीन की कुंजी `jev:evaluate` नहीं ले जाती।
- `jev_rate_limited`: FailproofAI Cloud ने संगठन की Jev rate limit के लिए मशीन की कुछ कॉलों को अस्वीकार किया, और उन कॉलों को केवल regex नीतियों द्वारा निर्णय दिया गया।
- `jev_unavailable`: एक पंक्ति में कई कॉल विफल रहीं, इसलिए मशीन एक समय में एक मिनट के लिए FailproofAI Cloud के Jev को छोड़ देती है। यह अपने आप ही फिर से कोशिश करता है।

यदि FailproofAI Cloud 5 सेकंड के भीतर उत्तर नहीं देता है, तो regex नीतियाँ अकेले निर्णय लेती हैं, किसी भी Jev outage के लिए जैसे। एक पंक्ति में 3 विफलताओं के बाद मशीन एक समय में एक मिनट के लिए पूछना बंद कर देती है, इसलिए Cloud outage प्रत्येक tool call को धीमा नहीं करता।

एक session pause (`failproofai config --pause`) FailproofAI Cloud के Jev चेकों को नहीं रोकता, जैसे यह Cloud-प्रबंधित नीतियों को नहीं रोकता। यह मशीन पर स्थापित packs के Jev चेकों को pause करता है।

## इसे देखें कि यह क्या कर रहा है

```bash
failproofai jev status
failproofai jev test
```

`status` provider को **FailproofAI Cloud** के रूप में दिखाता है, Cloud host जिससे मशीन जुड़ी है, mode, और key source को **FailproofAI Cloud connection** के रूप में, कुंजी कभी नहीं। जब FailproofAI Cloud `jev.json` जगह पर है लेकिन Jev नहीं चल सकता है, यह कहता है क्यों:

| `status` कहता है | `status --json` | अर्थ |
| --- | --- | --- |
| **off — इस मशीन के FailproofAI Cloud कनेक्शन के लिए कोई Jev कुंजी संग्रहीत नहीं है** | `key-lacks-jev` | मशीन कनेक्ट की गई है, लेकिन इसके लिए कोई Jev कुंजी संग्रहीत नहीं है: कुंजी `jev:evaluate` की कमी है, या कनेक्ट इसकी पुष्टि नहीं कर सकता। `FAILPROOFAI_CLOUD_TOKEN` में कुंजी के साथ फिर से `failproofai config` चलाएँ; यदि इसमें permission की कमी है, तो एक **machine** कुंजी का उपयोग करें। |
| **off — यह मशीन FailproofAI Cloud से कनेक्ट नहीं है** | `not-connected` | इस मशीन पर कोई FailproofAI Cloud कनेक्शन नहीं है जिससे Jev कुंजी संबंधित हो सकती है। |

`failproofai config --disconnect` के बाद अब कोई FailproofAI Cloud `jev.json` नहीं है (जब तक यह बंद नहीं किया गया, जिसे रखा जाता है), इसलिए `status` केवल Jev को बंद रूप में रिपोर्ट करता है। `status --json` एक ही facts रखता है (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), साथ ही जब config गायब या अस्वीकार किया जाता है। `permissions` हमेशा `jev.json` का होता है; `credentials.json` के बारे में एक refusal `credentialsPermissions` जोड़ता है, और `fix` जब एक कमांड इसे ठीक करता है। `test` एक लाइव request भेजता है और इसकी latency और जो Jev version ने उत्तर दिया उसकी रिपोर्ट करता है। यह 1 के साथ exit करता है, और अपने title में कहता है, जब answer hook timeout के बाद आता है (hooks `timeout` record करेंगे) या इसके चेक सवाल का गलत उत्तर देता है।

डैशबोर्ड का **Settings → Jev** panel भी **FailproofAI Cloud connection** दिखाता है: कौन सा संगठन मशीन में रिपोर्ट करता है और क्या इसकी कुंजी Jev ले जाती है। यह मशीन की अपनी फ़ाइलों से पढ़ा जाता है, कोई network call के साथ नहीं।

## एक वास्तविक कॉल की सत्यापन करें

hooked agent में एक नया session शुरू करें। इसे अपने file-reading tool को `README.md` पर उपयोग करने के लिए कहें और शीर्षक report करें। पुष्टि करें कि session में वह tool call शामिल है, फिर फिर से `failproofai jev status` चलाएँ: इसकी हाल की evaluated-call count बढ़नी चाहिए। [local dashboard](/hi/reference/local-dashboard#review-policy-activity) में **Policies → Activity** खोलें उस कॉल के Jev verdict और mode को inspect करने के लिए। Cloud में, संगठन का **Policies** पृष्ठ delivered activity के लिए Jev outcomes दिखाता है। observe mode में, verdict को **would-have** के रूप में record किया जाता है और policy result अभी भी कॉल को decide करता है। एक clearance केवल तभी दिखाई देती है जब एक reviewable नीति मेल खाई हो और Jev ने इसके नामित चेकों को साफ़ किया हो।

## Policy पृष्ठ पर क्या पहुँचता है

मशीन पहले से अपनी hook activity को FailproofAI Cloud को भेजती है (`events:add`)। Jev चालू होने पर, प्रत्येक gated call का record भी कहता है कि कौन सा evaluator चला, Jev ने क्या निर्णय लिया, उसने कौन सी नीतियों को साफ़ किया, जब यह wfall back हुआ तो क्यों, इसकी latency और जो model ने उत्तर दिया — decisions, codes और names, कभी command या आपका prompt नहीं। आपके संगठन के **Policies** पृष्ठ पर:

- एक कॉल जिसे Jev की अपनी verdict decided (enforce mode) को **Jev** को attribute किया जाता है, और जब deciding check एक pack से आया, record भी उस pack और इसके version का नाम देता है;
- observe mode में, Jev की अस्वीकृति या warning को **would-have** के रूप में दिखाया जाता है, आपके द्वारा observe किए जा रहे rollouts के बगल में;
- नीतियाँ जिन्हें Jev observe mode में साफ़ किया, या साफ़ किया जाता, प्रति नीति गिनी जाती हैं।
- एक decision जिसमें Jev ने भाग लिया (एक block, warning, clear, या observe mode में would-have) प्रत्येक चेक को सूचीबद्ध करता है जिसे यह पूछा और वह चेक क्या निष्कर्ष निकाला: verdict, क्यों (`not-detected`, `exempt`, `fired`, `op-requested`, …), इसका evidence `p`, `exempt` answer और प्रत्येक probe का answer। एक policy की चेक को देखने के लिए deploy किया गया (observe) भी सूचीबद्ध है, marked watched; यह कभी block नहीं करता। Jev संभावनाओं के साथ उत्तर देता है, prose नहीं, इसलिए कोई free-text reason नहीं है। Plain allows counts में roll up करते हैं और यह सूची नहीं ले जाते।

## जब Jev उत्तर नहीं दे सकता

इनमें से हर एक उस कॉल के लिए आपकी नीतियों के result में वापस आ जाता है, और इसके reason के साथ record किया जाता है:

| Reason | Cause |
| --- | --- |
| `out-of-credits` | आपके संगठन ने अपना योजना भत्ता उपयोग कर लिया है। |
| `http-401`, `http-403` | कुंजी को revoke कर दिया गया, या `jev:evaluate` नहीं ले जाती। एक कुंजी के साथ फिर से कनेक्ट करें जो करती है। |
| `http-429` | FailproofAI Cloud आपके संगठन के लिए Jev को rate-limiting है। जब तक wait इसे माँगती है (इसका `Retry-After`, अधिकतम 60 सेकंड), मशीन इसे कुछ नहीं भेजती और हर कॉल सीधे वापस आ जाती है। इस तरीके से held back किए गए कॉलों को `http-429` के रूप में, या `rate-limited` के रूप में record किया जाता है जब मशीन की अपनी rate limit उन्हें पहले hold करती है। |
| `http-429` (daily limit) | आपके संगठन ने अपनी daily Jev कॉलें उपयोग की हैं: **10,000 per UTC day**, जब तक कि जो आपका FailproofAI Cloud संचालित करता है उसने दूसरी limit सेट नहीं की। हर कॉल 00:00 UTC तक वापस आती है जब count reset हो जाता है; मशीन अभी भी ज्यादातर एक मिनट में एक बार फिर से पूछती है, इसलिए यह एक मिनट के भीतर reset को pick करती है। `failproofai jev test` कहता है "Daily Jev limit for this org reached; resets at 00:00 UTC।" |
| `http-422` | Jev ने इस कॉल के request को अस्वीकार किया, आमतौर पर क्योंकि tool call ने dense text (base64, hex, minified code) hold किया Jev के token budget पर। वह कॉल हर बार वापस आती है; यह एक outage नहीं है। |
| `http-502` | Jev अभी unavailable है। |
| `http-503` | यह Cloud आपके org के लिए Jev serve नहीं कर सकता: कोई model gateway नहीं, एक org अभी तक provisioned नहीं है, या gateway down है। अपने admin से पूछें; hooks ज्यादातर एक मिनट में एक बार फिर से पूछते हैं। |
| `http-404` | यह FailproofAI Cloud अभी तक Jev serve नहीं करता। |
| `timeout` | `timeoutMs` (default 3000) के भीतर कोई उत्तर नहीं। जबकि FailproofAI Cloud मशीन के Jev मोड को सेट करता है, wait 5000 ms है और `jev.json` का `timeoutMs` उपयोग नहीं किया जाता। |
| `model-mismatch` | 1.13 के अलावा एक Jev version ने उत्तर दिया। |

## कुंजी कहाँ रहती है, और यह कहाँ जाती है

- कुंजी एक बार स्टोर की जाती है, `~/.failproofai/credentials.json` में (`0600`, एक owner-only directory में), दूसरे FailproofAI Cloud credentials के पास। `jev.json` इस route के लिए कोई कुंजी नहीं रखता; एक वहाँ लिखी गई config को अमान्य बनाती है।
- यदि `credentials.json` **कोई भी** permission आपके अलावा किसी और के लिए (group या other, read या write) ले जाती है, या इसकी directory **कोई भी** आपके अलावा लिख सकता है, तो यह **refused** है, read नहीं, और Jev तब तक off है जब तक आप इसे ठीक नहीं करते: फ़ाइल पर `chmod 600`, directory पर `chmod 700` (या reconnect, जो फ़ाइल को `0600` पर rewrites करता है और directory को owner-only बनाता है)। एक directory जिसे दूसरे केवल read कर सकते हैं ठीक है; एक जिसे लिख सकते हैं file को swap करने देता है।
- कुंजी केवल जब connection जिससे यह आया उस मशीन पर होता है count करती है: एक policy या reporting credential उसी FailproofAI Cloud के लिए **उसी कुंजी के साथ**, उसी file में। एक Jev कुंजी बिना अपने के छोड़ी गई ignored है, और Jev off रहता है। यह तब होता है जब पुराना failproofai की `config --disconnect` Jev कुंजी को जगह छोड़ देती है (यह नहीं जानती कि इसे remove करना है), या जब पुराना failproofai की `config --token` दूसरी कुंजी के साथ कनेक्ट करता है, जो FailproofAI Cloud पर दूसरे organization की हो सकती है। Jev को वापस चालू करने के लिए, **machine** कुंजी के साथ फिर से कनेक्ट करें।
- कुंजी केवल Cloud origin को भेजी जाती है जिसके विरुद्ध यह verify की गई थी। कहीं और pointing करने वाला `jev.json` refused है।
- **मशीन पर एक agent इसे read कर सकता है।** `credentials.json` owner-only है, और agent उस owner के रूप में चलता है। failproofai की अपनी files को read करना purpose पर allowed है (केवल उन्हें बदलना `block-failproofai-commands` द्वारा blocked है), इसलिए एक agent और इस file के बीच केवल चीज़ `block-read-outside-cwd` है — एक *reviewable* policy — और एक session जो आपके home directory से शुरू होता है, कुछ नहीं। `jev:evaluate` वाली कुंजी आपके संगठन की Jev allowance खर्च करती है (daily cap तक) जहाँ कहीं भी यह उपयोग किया जाता है, इसलिए एक machine key को किसी भी अन्य spending credential की तरह treat करें: यदि एक agent ने इसे read किया हो सकता है, तो Keys पृष्ठ पर इसे disable करें और एक नई के साथ reconnect करें।
- केवल आपकी global files इसे decide करती हैं। एक repository Cloud Jev को चालू नहीं कर सकता, इसे कहीं और point कर सकता या इसकी कुंजी supply कर सकता, और `FAILPROOFAI_JEV_API_KEY` इस route के लिए ignored है।
- हर कॉल के लिए Jev evaluate करता है, एक request FailproofAI Cloud को जाता है, जो [bring-your-own-key page](/hi/reference/jev-providers#what-leaves-the-machine) सूचीबद्ध करता है (secrets redacted)। FailproofAI Cloud इसे TypeSafe को forward करता है और इसे log या keep नहीं करता।

## इसे बंद करें

जुड़ी हुई मशीन पर, Jev तब बंद होता है जब FailproofAI Cloud इसे कोई Jev नीति deploy नहीं करता: वहाँ Jev नीतियों को remove या archive करें।

| Command | Outcome |
| --- | --- |
| FailproofAI Cloud में मशीन की Jev नीतियों को remove करें | Cloud का mode अगले poll पर `off` हो जाता है (लगभग 30 s): कोई Jev नहीं, `jev.json` कुछ भी कहे। |
| `failproofai config --disconnect` | मशीन को disconnect करें: कुंजी को remove किया जाता है, और `jev.json` भी जब यह FailproofAI Cloud का नाम देता है और switched off नहीं होता है। आपके अपने endpoint के लिए `jev.json` रहता है। |

अगली tool call से, hooks regex नीतियों को बिल्कुल पहले की तरह चलाते हैं।
