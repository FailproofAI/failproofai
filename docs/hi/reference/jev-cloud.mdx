यह [Jev policies](/hi/policies/jev) के लिए Cloud route संदर्भ है। Jev, TypeSafe का classifier, प्रत्येक tool call को उसके विरुद्ध पढ़ता है जो आपने वास्तव में माँगा था और आपकी नीतियों के साथ उत्तर देता है, उनके बजाय नहीं। **FailproofAI Cloud** के माध्यम से, एक कनेक्टेड मशीन Jev का उपयोग उसी कुंजी के साथ करती है जिससे वह पहले से जुड़ी है: कोई TypeSafe खाता नहीं, कोई दूसरी कुंजी नहीं, कोई endpoint कॉन्फ़िगर करने की आवश्यकता नहीं। प्रत्येक कॉल आपके संगठन के मौजूदा plan allowance पर चार्ज होता है।

Jev जो कुछ भी करता है वह [bring-your-own-key setup](/hi/reference/jev-providers) से अपरिवर्तित है: कठिन नीतियाँ अंतिम रहती हैं, एक समीक्षा योग्य नीति की deny केवल तभी साफ़ होती है जब Jev से उस विशेष चिंता के बारे में पूछा गया हो, और कोई भी विफलता उस कॉल के लिए regex परिणाम पर वापस गिरती है।

<Note>
**failproofai 1.0.8-beta.0** या इससे बाद के संस्करण की आवश्यकता है। 1.0.7 में Jev नहीं है, भले ही यह 1.0.7 betas से ऊपर आता है। Jev config के बिना कुछ नहीं बदलता: hooks regex policies को बिल्कुल वैसे ही चलाते हैं जैसे हमेशा करते हैं।
</Note>

## शुरुआत से पहले

उस मशीन पर Failproof AI इंस्टॉल करें जहाँ आपका agent चलता है और इसके hooks को एक [supported harness](/hi/reference/harnesses) से जोड़ें। यदि आप शुरुआत से शुरू कर रहे हैं, तो hook installation के माध्यम से [quickstart](/hi/start/quickstart) का पालन करें। `failproofai --version` के साथ installed CLI को जाँचें; यदि यह Jev से पहले का हो तो इसे अपडेट करें। आपको अपने संगठन के **Administration → Keys** पृष्ठ तक पहुँचने की भी आवश्यकता है ताकि आप एक मशीन कुंजी बना सकें।

Jev `PreToolUse` या `PermissionRequest` gate पर नाम दिए गए tool calls की समीक्षा करता है। यह session में प्रत्येक event की समीक्षा नहीं करता है। Jev को एक नीति deny को साफ़ करते हुए देखने के लिए, आपको [reviewable](/hi/policies/authority) से चिह्नित एक installed policy की आवश्यकता है; सभी अन्य policy denies अंतिम रहती हैं।

## इसे चालू करें

1. **Jev के साथ एक कुंजी बनाएँ।** FailproofAI Cloud dashboard में, **Administration → Keys → Create key** खोलें और **machine** preset चुनें। यह तीन permissions प्रदान करता है जिनकी एक मशीन को आवश्यकता है: `events:add` (activity भेजें), `policies:pull` (policies प्राप्त करें) और `jev:evaluate` (Jev, आपके संगठन के plan पर चार्ज किया जाता है)। एक कुंजी अन्य दोनों के बिना `jev:evaluate` नहीं ले सकती है।
2. **मशीन को उस कुंजी से कनेक्ट करें।** prompt पर इसका एक-बार का secret पढ़ें, फिर पूरा setup command चलाएँ:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` daemon को install करता है, agent CLIs के लिए hooks को attach करता है जो यह पाता है, और मशीन को कनेक्ट करता है। environment variable कुंजी को command के arguments और आपके shell history से बाहर रखता है। यदि आपका harness बाद में install किया गया था, [इसे explicitly attach करें](/hi/start/quickstart)।

   यदि आपका संगठन hosted एक के बजाय अपना स्वयं का FailproofAI Cloud चलाता है, तो इसका address जोड़ें: `--url https://<your dashboard host>` (या `FAILPROOFAI_CLOUD_URL` export करें)। इसके बिना कुंजी को hosted service के विरुद्ध जाँचा जाता है और कनेक्शन विफल हो जाता है। यदि उस host का certificate एक private CA से आता है, तो CA को मशीन के system trust store में install करें (उदाहरण के लिए `update-ca-certificates` के साथ), केवल `NODE_EXTRA_CA_CERTS` में नहीं: daemon जो events भेजता है और policies pull करता है system store को पढ़ता है। [Troubleshooting](/hi/reference/troubleshooting) देखें।

बस इतना ही। कनेक्ट करना कुंजी को store करता है और, जब मशीन के पास **कोई** Jev config अभी तक न हो, तो FailproofAI Cloud के लिए एक लिखता है। मशीन के first deployment से (लगभग 30 s में) FailproofAI Cloud mode को set करता है: `enforce` जबकि एक Jev policy इसे deploy किया जाता है, `off` जब नहीं (देखें [Who sets the mode](#who-sets-the-mode))। output ऐसा कहता है:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Checks जो FailproofAI Cloud deploy करता है वे Cloud पर चलते हैं। मशीन पर अपने स्वयं के checks जोड़ने के लिए, एक pack install करें:

```bash
failproofai policies add FailproofAI/jev-policies
```

**`--no-transcripts` के साथ, कनेक्ट करना Jev को नहीं चालू करता है।** Jev प्रत्येक checked tool call और recent prompt को FailproofAI Cloud को भेजता है, जो decisions-only कनेक्शन से अधिक है जिसे भेजने के लिए कहा गया था। कुंजी अभी भी store होती है, और output कहता है कि Jev उपलब्ध है और इसे कैसे चालू करें:

```bash
failproofai jev setup --provider failproofai
```

यह **बंद** भी करता है Jev को FailproofAI Cloud के माध्यम से। एक `jev.json` जो FailproofAI Cloud के माध्यम से Jev चलाता है (transcripts पर के साथ एक earlier connection द्वारा छोड़ा गया) हटाया जाता है, `config --disconnect` उपयोग करने के समान rule द्वारा, और output कहता है कि FailproofAI Cloud via Jev इस मशीन पर बंद रहता है। आपके अपने Jev endpoint के लिए एक `jev.json` को जैसे है वैसे ही छोड़ा जाता है, और एक FailproofAI Cloud वाला जिसे आपने बंद किया (`--mode off`) भी।

<Warning>
कनेक्ट करना एक मौजूदा `~/.failproofai/jev.json` को **कभी भी overwrite नहीं करता है**। यदि आप पहले से अपने स्वयं के Jev endpoint का उपयोग करते हैं, तो इसका उपयोग करते रहता है, और output कहता है कि file को configured के रूप में छोड़ा गया था — और, जब वह file Jev को बंद छोड़ता है (refused, या बंद किया गया), तो ऐसा कहता है और इसे कैसे ठीक करें। उस मशीन को FailproofAI Cloud पर स्विच करने के लिए, `failproofai jev setup --provider failproofai` चलाएँ।
</Warning>

## Who sets the mode

एक मशीन जो FailproofAI Cloud से कनेक्ट है, पर **FailproofAI Cloud Jev mode को set करता है**; मशीन पर कुछ भी नहीं करता:

- `enforce` जबकि कोई भी Jev (या regex + Jev) policy मशीन को deploy किया जाता है: एक agent से प्रत्येक checked tool call जिस पर उन policies में से कोई लक्षित है FailproofAI Cloud को जाता है, जो अपने checks को एक साथ पूछता है जो वहाँ installed packs के checks के साथ। एक call एक agent से जिस पर कोई Cloud Jev policy लक्षित नहीं है, अपने आप में कोई pack check के साथ, सभी भेजे नहीं जाते हैं। `enforce` में, Jev के अपने deny checks calls को block करते हैं साथ ही regex verdicts को साफ़ भी करते हैं जिनकी वे समीक्षा करते हैं।
- `off` जब कोई नहीं है: कोई Jev नहीं है, चाहे `jev.json` कुछ भी कहे।

Jev policy को कार्य करने से पहले try करने के लिए, इसे **observe** effect के साथ deploy करें: इसके checks अभी भी पूछे जाते हैं, और वे जो किया होता है वह **would-have** के रूप में policy page पर recorded होता है, लेकिन यह कभी एक call को block नहीं करता और कभी एक को साफ़ नहीं करता। `failproofai jev setup --mode` और dashboard के **Settings → Jev** switch कहते हैं कि mode को FailproofAI Cloud द्वारा managed है और कुछ नहीं बदलते। `jev.json` Cloud के checks के लिए उपयोग नहीं किया जाता है, भले ही यह कोई अन्य provider name दे। `failproofai config --disconnect` Jev को मशीन के अपने `jev.json` को वापस करता है।

`failproofai jev status` फिर कहता है `Jev checks run on FailproofAI Cloud (mode: enforce)`। यह प्रत्येक `both` policy को review करने वाले checks को भी name देता है। fleet page दिखाता है कि एक mode वाली मशीन क्यों नहीं पूछ सकती है:

- `transcripts_disabled`: मशीन `--no-transcripts` के साथ connected था, जो कभी Jev को नहीं चालू करता है।
- `jev_unconfigured`: मशीन की कुंजी `jev:evaluate` को नहीं carries करती है।
- `jev_rate_limited`: FailproofAI Cloud ने संगठन के Jev rate limit के लिए मशीन के कुछ calls को refuse किया, और वे calls regex policies alone द्वारा decided किए गए।
- `jev_unavailable`: एक पंक्ति में कई calls विफल हुए, इसलिए मशीन FailproofAI Cloud के Jev को एक समय पर एक मिनट के लिए skip करती है। यह अपने आप पर retry करती है।

यदि FailproofAI Cloud 5 सेकंड के भीतर उत्तर नहीं देता है, तो regex policies alone decide करते हैं, किसी भी Jev outage के लिए। एक पंक्ति में 3 विफलताओं के बाद मशीन एक समय पर एक मिनट के लिए पूछना बंद कर देती है, इसलिए Cloud outage हर tool call को slow नहीं करता है।

एक session pause (`failproofai config --pause`) FailproofAI Cloud के Jev checks को नहीं रोकता है, जैसे यह Cloud-managed policies को नहीं रोकता है। यह मशीन पर installed packs के Jev checks को pause करता है।

## यह क्या कर रहा है यह जाँचें

```bash
failproofai jev status
failproofai jev test
```

`status` provider को **FailproofAI Cloud** के रूप में दिखाता है, Cloud host जिससे मशीन connected है, mode, और key source को **FailproofAI Cloud connection** के रूप में, कभी कुंजी नहीं। जब एक FailproofAI Cloud `jev.json` place में है लेकिन Jev नहीं चल सकता है, तो यह कहता है क्यों:

| `status` कहता है | `status --json` | अर्थ |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | मशीन connected है, लेकिन इसके लिए कोई Jev key stored नहीं है: कुंजी `jev:evaluate` को lacks करती है, या connect इसे confirm नहीं कर सकता। `FAILPROOFAI_CLOUD_TOKEN` में कुंजी के साथ `failproofai config` को दोबारा चलाएँ; यदि इसमें permission नहीं है, तो एक **machine** कुंजी का उपयोग करें। |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | इस मशीन पर कोई FailproofAI Cloud connection नहीं है जिससे Jev key belong करे। |

`failproofai config --disconnect` के बाद कोई FailproofAI Cloud `jev.json` अब नहीं है (जब तक कि इसे बंद न किया गया हो, जो रखा जाता है), इसलिए `status` बस Jev को बंद के रूप में reports करता है। `status --json` समान facts carry करता है (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), यहाँ भी जब config absent या refused हो। `permissions` हमेशा `jev.json` के होते हैं; `credentials.json` के बारे में एक refusal `credentialsPermissions` जोड़ता है, और `fix` जब एक command इसे fix कर सकता है। `test` एक live request भेजता है और इसकी latency और Jev version जो उत्तर दिया को report करता है। यह 1 exit करता है, और अपने title में ऐसा कहता है, जब answer hook timeout के बाद आता है (hooks `timeout` record करते) या गलत तरीके से इसके check question का उत्तर देते हैं।

Dashboard के **Settings → Jev** panel भी **FailproofAI Cloud connection** को दिखाता है: कौन सा संगठन मशीन report करती है और क्या इसकी कुंजी Jev को carries करती है। यह मशीन की अपनी files से पढ़ी जाती है, कोई network call के साथ नहीं।

## एक real call को verify करें

hooked agent में एक नया session शुरू करें। इसे `README.md` पर अपने file-reading tool का उपयोग करने और title को report करने के लिए कहें। confirm करें कि session में वह tool call है, फिर `failproofai jev status` को दोबारा चलाएँ: इसकी recent evaluated-call count को increase होना चाहिए। **Policies → Activity** को [local dashboard](/hi/reference/local-dashboard#review-policy-activity) में खोलें उस call के Jev verdict और mode को inspect करने के लिए। Cloud में, संगठन का **Policies** page delivered activity के लिए Jev outcomes दिखाता है। observe mode में, verdict को **would-have** के रूप में recorded किया जाता है और policy result अभी भी call को decide करता है। एक clearance केवल तभी प्रकट होता है जब एक reviewable policy matched हो और Jev ने इसके named checks को साफ़ किया हो।

## क्या policy page तक पहुँचता है

मशीन पहले से ही अपनी hook activity को FailproofAI Cloud को भेजती है (`events:add`)। Jev on के साथ, प्रत्येक gated call के record में भी कहा जाता है कि कौन सा evaluator चला, Jev ने क्या decide किया, इसने कौन सी policies को साफ़ किया, जब इसे fallback क्यों किया, इसकी latency और जो model उत्तर दिया — decisions, codes और names, कभी command या आपका prompt नहीं। आपके संगठन के **Policies** page पर:

- एक call जिसे Jev के अपने verdict ने decide किया (enforce mode) को **Jev** को attribute किया जाता है, और जब deciding check एक pack से आया था, record भी उस pack को और इसके version को name देता है;
- observe mode में, Jev की deny या warning को **would-have** के रूप में दिखाया जाता है, observe किए गए rollouts के बगल में;
- policies जिन्हें Jev साफ़ किया, या observe mode में साफ़ किया होता, को per policy counted किया जाता है।
- एक decision जिसमें Jev ने part लिया (एक block, एक warning, एक clear, या observe mode में एक would-have) प्रत्येक check को list करता है जिसे इसने पूछा और वह check क्या conclude किया: verdict, क्यों (`not-detected`, `exempt`, `fired`, `op-requested`, …), इसका evidence `p`, `exempt` answer और प्रत्येक probe का answer। एक check एक policy का जो watch के लिए deployed है (observe) भी list किया जाता है, marked watched; यह कभी block नहीं करता। Jev probabilities के साथ उत्तर देता है, prose नहीं, इसलिए कोई free-text reason नहीं है। Plain allows roll up counts में हो जाते हैं और यह list carry नहीं करते हैं।

## जब Jev उत्तर नहीं दे सकता है

इन सभी में से प्रत्येक उस call के लिए आपकी policies के result पर fallback करता है, और इसके reason के साथ recorded होता है:

| Reason | Cause |
| --- | --- |
| `out-of-credits` | आपके संगठन ने अपने plan allowance का उपयोग कर दिया है। |
| `http-401`, `http-403` | कुंजी को revoke किया गया, या `jev:evaluate` को carry नहीं करती है। एक कुंजी के साथ reconnect करें जो करती है। |
| `http-429` | FailproofAI Cloud आपके संगठन के लिए Jev को rate-limit कर रहा है। जब तक यह जो wait ask करता है वह over न हो (इसका `Retry-After`, सबसे अधिक 60 सेकंड), मशीन इसे कुछ नहीं भेजती है और हर call straight away fallback करता है। calls held back उस तरीके से को `http-429` के रूप में record किया जाता है, या `rate-limited` के रूप में जब मशीन का अपना rate limit उन्हें पहले hold करता है। |
| `http-429` (daily limit) | आपके संगठन ने अपनी daily Jev calls का उपयोग कर दिया: **10,000 per UTC day**, जब तक कि जो आपका FailproofAI Cloud operate करता है उसने कोई अन्य limit set न किया हो। हर call जब तक count 00:00 UTC पर reset न हो तब तक fallback करता है; मशीन अभी भी सबसे अधिक एक मिनट में एक बार फिर से पूछती है, इसलिए यह reset को एक मिनट के भीतर pick up करती है। `failproofai jev test` कहता है "Daily Jev limit for this org reached; resets at 00:00 UTC।" |
| `http-422` | Jev ने इस call की request को refuse किया, आमतौर पर क्योंकि tool call में dense text (base64, hex, minified code) Jev के token budget से अधिक था। वह call हर बार fallback करता है; यह एक outage नहीं है। |
| `http-502` | Jev अभी unavailable है। |
| `http-503` | यह Cloud आपके org के लिए Jev को serve नहीं कर सकता है: कोई model gateway नहीं, एक org अभी तक provisioned नहीं, या gateway down है। अपने admin से पूछें; hooks सबसे अधिक एक मिनट में एक बार फिर से पूछते हैं। |
| `http-404` | यह FailproofAI Cloud अभी तक Jev को serve नहीं करता है। |
| `timeout` | `timeoutMs` के भीतर कोई उत्तर नहीं (default 3000)। जबकि FailproofAI Cloud मशीन का Jev mode set करता है, wait 5000 ms है और `jev.json` का `timeoutMs` उपयोग नहीं किया जाता है। |
| `model-mismatch` | 1.13 के अलावा एक Jev version ने उत्तर दिया। |

## कुंजी कहाँ lives करती है, और कहाँ जाती है

- कुंजी एक बार store होती है, `~/.failproofai/credentials.json` में (`0600`, एक owner-only directory में), अन्य FailproofAI Cloud credentials के बगल में। `jev.json` इस route के लिए कोई कुंजी नहीं hold करता है; एक वहाँ written config को invalid बनाता है।
- यदि `credentials.json` **किसी को** भी आपके अलावा (group या other, read या write) **कोई भी** permission carry करता है, या इसकी directory को आपके अलावा कोई भी **लिख सकता है**, तो यह **refused** है, read नहीं है, और Jev तब तक बंद है जब तक आप इसे ठीक न करें: file पर `chmod 600`, directory पर `chmod 700` (या reconnect करें, जो file को `0600` पर rewrite करता है और directory को owner-only बनाता है)। एक directory जिसे अन्य केवल read कर सकते हैं वह ठीक है; एक जिसे वे write कर सकते हैं उन्हें file को swap करने देता है।
- कुंजी केवल तब तक count करती है जब तक कनेक्शन जिससे यह आई है मशीन पर है: एक policy या reporting credential समान FailproofAI Cloud के लिए **उसी कुंजी के साथ**, उसी file में। एक Jev key left behind बिना एक के ignore किया जाता है, और Jev बंद रहता है। यह तब होता है जब एक पुरानी failproofai की `config --disconnect` Jev key को place में छोड़ जाती है (यह नहीं जानती कि इसे remove करना है), या जब एक पुरानी failproofai की `config --token` एक अन्य कुंजी के साथ connect करती है, जो FailproofAI Cloud पर कोई अन्य organization को belong कर सकती है। Jev को वापस on करने के लिए, एक **machine** कुंजी के साथ फिर से connect करें।
- कुंजी केवल Cloud origin को भेजी जाती है जिसके विरुद्ध इसे verify किया गया था। एक `jev.json` कहीं और pointing को refuse किया जाता है।
- **मशीन पर एक agent इसे read कर सकता है।** `credentials.json` owner-only है, और agent owner के रूप में चलता है। failproofai की अपनी files को read करना purpose पर allowed है (केवल उन्हें changing को `block-failproofai-commands` द्वारा block किया जाता है), इसलिए एक agent और इस file के बीच एकमात्र चीज़ है `block-read-outside-cwd` — एक *reviewable* policy — और एक session से आपकी home directory में शुरू, कुछ भी नहीं। एक कुंजी `jev:evaluate` के साथ आपके संगठन का Jev allowance (daily cap तक) spend करती है कहीं भी से इसका उपयोग किया जाता है, इसलिए एक मशीन कुंजी को किसी भी अन्य spending credential की तरह treat करें: यदि एक agent इसे read किया हो सकता है, तो इसे Keys page पर disable करें और एक नई के साथ reconnect करें।
- केवल आपकी global files यह decide करती हैं। एक repository Cloud Jev को on नहीं कर सकता है, इसे कहीं और point नहीं कर सकता है या अपनी कुंजी supply नहीं कर सकता है, और `FAILPROOFAI_JEV_API_KEY` इस route के लिए ignored है।
- प्रत्येक call के लिए Jev evaluate करता है, एक request FailproofAI Cloud को जाता है, carry करता हुआ जो [bring-your-own-key page](/hi/reference/jev-providers#what-leaves-the-machine) list करता है (secrets redacted)। FailproofAI Cloud इसे TypeSafe को forward करता है और इसे log या keep नहीं करता है।

## इसे बंद करें

एक connected मशीन पर, Jev तब बंद है जब FailproofAI Cloud इसे कोई Jev policy deploy नहीं करता है: वहाँ Jev policies को remove या archive करें।

| Command | Outcome |
| --- | --- |
| मशीन की Jev policies को FailproofAI Cloud में remove करें | Cloud का mode next poll पर `off` हो जाता है (लगभग 30 s): कोई Jev नहीं है, चाहे `jev.json` कुछ भी कहे। |
| `failproofai config --disconnect` | मशीन को disconnect करें: कुंजी removed है, और `jev.json` भी है जब यह FailproofAI Cloud को name देता है और switched off नहीं है। आपके अपने endpoint के लिए एक `jev.json` रहता है। |

अगली tool call से, hooks regex policies को बिल्कुल वैसे ही चलाते हैं जैसे पहले।
