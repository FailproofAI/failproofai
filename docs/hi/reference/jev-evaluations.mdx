यह पृष्ठ [Jev evaluations](/hi/evaluations/jev) के पीछे के question shapes और scoring rules का वर्णन करता है। कुछ questions को एक model से conversation को *पढ़ने* की जरूरत है, लेकिन इसके बारे में *लिखने* की नहीं। "क्या ग्राहक ने तात्कालिकता व्यक्त की?" के दो उत्तर हैं। "वे कितने निराश थे?" के कुछ उत्तर हैं, क्रम में। आप हर उत्तर पहले से ही जानते हैं।

एक **classifier evaluation** बिल्कुल उन्हीं के लिए है। आप question और जो उत्तर यह दे सकता है उन्हें लिखते हैं, और classification के लिए निर्मित एक छोटा model एक calibrated number लौटाता है — कभी free text नहीं।

<Note>
एक judge की तरह, एक classifier evaluation प्रति session एक model call की लागत लेता है। इसके विपरीत यह एक छोटा, single-purpose model है न कि एक सामान्य, इसलिए यह तेज़ और सस्ता है — लेकिन यह कभी भी अपने बारे में नहीं समझाएगा। यदि आपको reasoning की जरूरत है, तो [judge](/hi/evaluations/judge) का उपयोग करें।
</Note>

## मुझे कौन सा चाहिए?

| Question | Use |
| --- | --- |
| कितने tool calls थे? | code |
| क्या session 30 सेकंड से कम था? | code |
| क्या ग्राहक ने तात्कालिकता व्यक्त की? | **classifier** |
| यह team कौन सा handle करे: billing, technical, या sales? | **classifier** |
| ग्राहक कितना निराश था? | **classifier** |
| क्या उत्तर वास्तव में सही था? | **judge** |
| क्या इसने हमारी escalation policy का पालन किया, और आप ऐसा क्यों सोचते हैं? | **judge** |

अंगूठे का नियम: **countable → code, जो उत्तर आप list कर सकते हैं → classifier, explanation की जरूरत है → judge।**

आपको आगे से ही फैसला नहीं करना है। वर्णन करें कि आप क्या माप करना चाहते हैं और assistant चुनता है, आपको बताता है कि इसने कौन सा चुना और क्यों, और आप इसे बदल सकते हैं।

## दोनों question types

### `noul` — क्या यह सत्य है?

दोनों उत्तर, और आप दोनों का वर्णन करते हैं। परिणाम संभावना है कि "true" विवरण फिट बैठता है:

```json
{
  "instructions": "क्या assistant ने पहले refund policy check किए बिना refund का वादा किया?",
  "criteria": {
    "true":  "किसी prior policy check या approval के बिना refund का वादा किया गया या जारी किया गया",
    "false": "कोई refund का वादा नहीं किया गया, या हर refund policy check का पालन किया"
  }
}
```

दोनों sides का वर्णन करें। "कोई तात्कालिकता नहीं दिखाई गई" एक वास्तविक उत्तर है और ऐसा कहना दूसरे को तेज़ बनाता है।

### `score` — इसमें कितना?

एक ordered rubric, **सबसे बुरा पहले**। परिणाम यह है कि session इस पर कहाँ उतरता है, 0–1 में rescaled:

```json
{
  "instructions": "ग्राहक कितना निराश है?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**एक rubric को तीन से पाँच levels लेता है, और वे सभी अलग होने चाहिए।** दोनों limits को मापा जाता है, stylistic नहीं:

- **दो levels** जो `noul` पहले से ही बेहतर करता है उसमें collapse हो जाता है, और **पाँच से अधिक** model को बीच की ओर hedge करने के बजाय प्रतिबद्ध होने के लिए बनाता है। एक ही session पर एक ही question को दो levels के साथ 0.00, तीन के साथ 0.01, और दस के साथ 0.55 स्कोर किया गया।
- **Repeated levels** उत्तर को arbitrarily split करते हैं। एक session जो unmistakably angry था वह `["Calm", "Frustrated", "Very angry"]` के विरुद्ध 1.00 स्कोर किया गया और `["Angry", "Angry", "Angry"]` के विरुद्ध 0.66 — एक well-formed number जिसका कोई मतलब नहीं है।

कोई order नहीं वाली categories — "billing, technical, या sales" — एक rubric नहीं हैं। इन्हें प्रति category `noul` के रूप में पूछें, या एक judge का उपयोग करें।

## परिणामों को पढ़ना

एक classifier 0 से 1 तक एक **score** produce करता है, एक judge की तरह, इसलिए यह charts, filters, और alerts को trigger करने के लिए समान तरीके से काम करता है। दो अंतर जानने लायक हैं:

- **कोई reasoning नहीं है।** field intentionally खाली है। यह model अपने बारे में नहीं समझाता है, और एक explanation invent करना एक fabrication होगा न कि एक feature।
- **Uncertainty को label किया जाता है।** एक `score` question अपने confidence की report करता है, और एक परिणाम जो model को unsure था उसे `low_confidence` tag किया जाता है — तो "इनमें से कौन सा एक human को देखना चाहिए" एक filter है न कि एक guess। एक `noul` question confidence report नहीं करता है, इसलिए इसे कभी भी tag नहीं किया जाता है।

बहुत long sessions को excerpts में पढ़ा जाता है और combined किया जाता है। जब एक session पूरी तरह से read करने के लिए बहुत लंबा हो, तो परिणाम बताता है कि कितने turns छोड़े गए थे — आप कभी भी ऐसा judgment नहीं देखेंगे जो session के एक हिस्से पर किया गया हो जो सभी पर किए गए के रूप में प्रस्तुत हो।

## Limits

- **तीन से पाँच rubric levels, सभी distinct।** ऊपर देखें; दोनों bounds को authoring time पर enforce किया जाता है।
- **एक evaluation प्रति एक question।** दो चीजें पूछें और आपको दो evaluations मिलते हैं, जो एक chart पर भी वही है जो आप चाहते हैं।
- **Question को editing करने से एक नया version publish होता है।** पुराने और नए scores comparable नहीं हैं, इसलिए उन्हें एक trend line में mixed होने के बजाय अलग रखा जाता है।
- **एक classifier हमेशा एक score produce करता है**, कभी एक metric या assertion नहीं।
- **कोई reasoning नहीं**, जैसा कि ऊपर है। यदि एक number किसी से "क्यों?" पूछने को कहेगा, तो इसके बजाय एक judge लिखें।

## Testing और backfill

एक judge के विपरीत, एक classifier evaluation **को** deploy करने से पहले test किया जा सकता है — [test करें](/hi/evaluations/test) यह real sessions के विरुद्ध उसी तरीके से जिस तरह आप एक code evaluation करते हैं, और कुछ भी live होने से पहले scores को पढ़ें।

इसे [backfilled](/hi/evaluations/deploy#score-sessions-you-already-have) भी किया जा सकता है sessions के ऊपर जो आपके पास पहले से हैं। यह प्रति session एक model call की लागत लेता है, इसलिए deliberately window को scope करें बजाय हर चीज़ को replay करने के।
