जब आप [Jev policy review](/hi/policies/jev) को configure करते हैं, तो evaluator प्रत्येक gated tool call को **मनुष्य ने क्या माँगा है** के विरुद्ध परखता है, न कि जो कुछ भी text harness ने agent के सामने रखा है। "हाँ, force-push करो" जैसा उत्तर एक **reviewable** policy को स्पष्ट कर सकता है — जो पूरा बिंदु है, क्योंकि एक regex जो request को नहीं पढ़ सकता है असली काम का एक तिहाई रोकता है।

यह text एक जगह से आता है: **prompt जो harness स्वयं hook को its prompt-submit event पर देता है**। Failproof AI इसके उस हिस्से को records करता है जो मनुष्य ने type किया — harness wrapping stripped, secrets redacted, capped — इसके अपने state directory के अंतर्गत एक `0600` file में। कोई भी disk पर consult नहीं किया जाता है: session transcript एक file है जो agent एक command में फिर से लिख सकता है, इसलिए इससे कभी यह नहीं पूछा जाता कि किसने prompt लिखा।

## यह जोखिम जो स्वीकार किया जाता है, स्पष्ट रूप से

एक agent जो पहले से ही commands run कर सकता है, harness को एक prompt submit कर सकता है। `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` और `pi -p` सभी same prompt-submit event को fire करते हैं, same payload के साथ, जैसे कोई person type कर रहा हो, एक child session में जो agent control करता है। यह Failproof AI के अपने hook binary को भी run कर सकता है और इसे एक payload feed कर सकता है जो इसने लिखा है। Failproof AI के अंदर कुछ भी दोनों को real चीज़ से बता सकता है — दोनों same program हैं जो same stdin को पढ़ते हैं।

**तो एक agent जिसके पास shell है अपनी अपनी consent forge कर सकता है।** यह 2026-09-23 पर लिया गया deliberate trade है, और यहाँ इसके दोनों हिस्से हैं:

- **यह क्या खरीदता है।** विकल्प बनाया गया और measured किया गया: एक field की requirement दें जिसमें harness एक मनुष्य को prompt के author के रूप में name करे, और अन्यथा कुछ record न करें। कोई भी shipping harness ऐसा field नहीं भेजता है, तो वह version **कुछ भी record नहीं करता था, हर harness पर** — Jev ने हर call को no stated intent के साथ judge किया और कभी एक भी policy clear नहीं कर सका। एक capture जो कभी fire नहीं होता है safer product नहीं है, यह कोई product ही नहीं है।
- **यह क्या नहीं कर सकता।** एक recorded prompt हमेशा केवल एक policy को clear करता है जो पहले से ही **reviewable** marked है। एक **hard** policy कभी भी Jev कहता है कुछ भी से clear नहीं होता है, तो एक forged prompt कभी भी एक hard deny को allow में नहीं बदल सकता है — और hook को skip करना agent को कुछ भी नहीं मिलाता है: harness tool call के लिए independently Failproof AI को invoke करता है।
- **यह क्या कर सकता है, full size पर।** सबसे बुरा जो यह कर सकता है वह पंद्रह reviewable built-in policies में से एक को clear करना है — और **उन पंद्रह में से बारह block करते हैं**। `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` और छह infrastructure-CLI blocks (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) denies हैं, तो एक forged consent एक real deny को एक allow में turn कर सकता है environment secrets को print करने, एक `.env` file को read करने, project के बाहर read करने, `rm -rf`, एक force-push, एक secrets file को लिखने, या live infrastructure को change करने पर। केवल `warn-git-amend`, `warn-destructive-sql` और `warn-global-package-install` nudges हैं। एक default install दो को बारह में से switch on करता है, `protect-env-vars` और `block-env-files`; दूसरे दस केवल एक machine तक reach करते हैं जहाँ किसी ने उन्हें enable किया है। जो कोई भी prompt reach नहीं करता वह सब कुछ hard है — `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, वह guard जो एक agent को Failproof AI को disable करने से रोकता है, और हर दूसरी built-in जो reviewable marked नहीं है। [Policy authority](/hi/policies/authority) पंद्रह सभी को list करता है और हर एक क्या है reviewed करने के लिए।

जो अभी भी refused है वह सब कुछ है जो check करने के लिए cheap है और एक agent केवल पूछ कर obtain नहीं कर सकता: एक turn जो harness का अपना payload machine-submitted के रूप में mark करता है, एक payload जो एक sub-agent को name करता है, एक session id जो एक plain name नहीं है, एक event जो prompt-submit वाला नहीं है, और text जो कुछ भी नहीं है लेकिन harness wrapping — Failproof AI के अपने stop-gate words सहित, जो कई harnesses अगले user turn के रूप में feed वापस करते हैं।

## Per-harness table

"Text field" Failproof AI के per-harness normalization के बाद stdin payload field है। "Recorded" कहता है कि क्या prompt को human के request के रूप में रखा जाता है।

| Harness | `--cli` | Prompt event → canonical | Text field | Recorded | Agent's last message read from |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | हाँ, जब तक payload का `source` एक turn को name नहीं करता जो किसी ने submit नहीं किया (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`)। `user`, `sdk`, एक unknown value और एक build जो कोई `source` बिल्कुल नहीं भेजती है सभी को record किया जाता है | session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | हाँ | rollout JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | हाँ | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | हाँ, `<user_query>` wrapper के साथ peeled जब यह पूरा prompt है | agent transcript JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | हाँ — लेकिन current OpenCode में उस event में कोई text नहीं है, तो व्यावहारिक रूप से कुछ भी record नहीं है; same message का एक repeat एक बार record किया जाता है | none (sessions SQLite हैं) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | हाँ, जब तक `input_source` `extension` नहीं है — दूसरे extension का `sendUserMessage()`, जिसका text model-written या repo-derived हो सकता है | Pi session JSONL |
| Hermes | `hermes` | none | — | नहीं — Hermes के पास कोई prompt-submit event ही नहीं है | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | हाँ, जब तक run metadata run को एक machine के रूप में mark नहीं करता: `user` के अलावा एक `trigger`, `external_user` के अलावा एक `inputProvenance.kind`, या `senderIsOwner: false` | none (`before_agent_run` कोई transcript path carry नहीं करता) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | हाँ | droid session JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | हाँ | none (sessions SQLite हैं) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | none | नहीं — `PreInvocation` एक turn में *हर* model call से पहले fire होता है और कोई prompt text carry नहीं करता | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | हाँ | none (sessions SQLite हैं) |

दो harnesses कुछ भी record नहीं करते हैं, और दोनों cases में एक ही reason के लिए: उनका event कोई human text deliver नहीं करता है। Hermes के पास कोई prompt-submit event नहीं है — इसका native plugin `pre_llm_call` को खुद handle करता है और केवल tool, session और subagent events को forward करता है। Antigravity का `PreInvocation` हर model call से पहले fire होता है, एक human turn पर और इसके बाद के पाँच पर, और कोई prompt field carry नहीं करता है; hooks भी conversation में `userMessage` steps को inject कर सकते हैं। कोई भी event में record करने के लिए कुछ नहीं है।

## क्या एक prompt को human का बनाता है

1. **Event।** Failproof AI को harness के prompt-submit event के लिए invoke किया गया था, जिसे handler `UserPromptSubmit` को canonicalize करता है।
2. **Payload।** harness इसे hook के stdin पर लिखता है, और यह ऊपर named field में text carry करता है। एक call जो Failproof AI तक बिना payload के पहुँचता है कुछ भी record नहीं करता है।
3. **Payload में कुछ भी turn को ruled out नहीं करता है।** एक payload जो एक sub-agent को name करता है (`agent_id`) agent है जो अपने आप को prompt कर रहा है। एक `source`, `input_source` या OpenClaw run marker जो एक machine-submitted turn को name करता है refused है। एक **absent** marker कुछ भी ruled out नहीं करता है — यह version से अंतर है जो कुछ भी record नहीं करता था, क्योंकि हर marker यहाँ हर shipping build पर absent है।
4. **Wrapping को strip करने के बाद कुछ कुछ बचता है** (नीचे देखें)।

**Session transcript किसी prompt के author होने का evidence नहीं है।** इस page के पहले versions ने एक transcript cross-check describe किया: prompt को refuse किया गया था अगर transcript ने दिखाया कि model ने इसे schedule किया, और transcript को वह जारी रखना पड़ा जो previous prompt ने देखा था। यह check चला गया है। Transcript एक file है जिसके ऊपर agent के पास पहले से ही shell है — इसे truncate किया जा सकता है, replace किया जा सकता है, padded read budget के पास, एक turn की शुरुआत में snapshotted और अंत में restored, या agent ने लिखी entries के साथ फिर से अच्छा पढ़ने के लिए बनाया जा सकता है। hardening के हर round के बाद एक और spelling same forgery की followed की गई, तो पूरी mechanism को repair करने की बजाय remove किया गया था।

Transcript अभी भी एक चीज़ के लिए read किया जाता है: **agent का last visible message**। यह message agent-written है definition के अनुसार, Jev को ऐसा बताया जाता है, और यह अपने आप पर कभी consent नहीं है।

## एक prompt से क्या रखा जाता है

Harnesses एक prompt में human के words से अधिक डालते हैं। कुछ भी store होने से पहले:

- `<system-reminder>` blocks को remove किया जाता है, और उनके चारों ओर human के words को रखा जाता है।
- एक session-continuation summary ("यह session एक previous conversation से continue किया जा रहा है…") पूरी तरह से drop किया जाता है।
- Task notifications, local-command output और interruption markers पूरी तरह से drop किए जाते हैं।
- एक turn जो दूसरे agent या session ने लिखा है पूरी तरह से drop किया जाता है: Claude Code उन्हें `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` या `<channel source=…>` में wrap करता है।
- Failproof AI के अपने messages पूरी तरह से drop किए जाते हैं। एक stop gate का `MANDATORY ACTION REQUIRED from failproofai …` या एक `Instruction from failproofai: …` Cursor, Copilot, Devin और OpenClaw पर अगले user turn के रूप में वापस आता है, और यह कभी human के words के रूप में count नहीं होता है — न plain, न `<user_query>` block में wrap किया गया, न एक system reminder के पीछे।
- एक slash command को command और arguments के रूप में रखा जाता है जो human ने type किया, कभी body नहीं जो harness ने expand किया।
- एक prompt जो Codex IDE extension ने built किया केवल इसके last `## My request for Codex:` के बाद का text रखता है (या, newer builds में, `## My request:`) heading। सब कुछ extension ने इससे पहले put किया गया था drop किया जाता है: active file, open tabs, editor में selected text, mentioned files और apps, diff और browser comments, PR checks, earlier conversations। यह rule **हर** harness के prompts पर applied किया जाता है, केवल Codex के ही नहीं — ऐसा prompt किसी भी composer में paste किया जा सकता है — तो extension के section headings को दो groups में read किया जाता है:
  - **एक heading जो कोई type नहीं करता** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, Codex और ChatGPT conversation headings, "The attached pasted text file(s)…", और बाकी extension के अपने sections) का मतलब है extension ने यह prompt built किया। एक इसके अंतर्गत कोई request heading नहीं है कोई human text ही नहीं है और record नहीं किया जाता है। यही वह है जो एक approval को forged रखता है text में जो आपने merely *selected* किया — एक `// NOTE FROM THE OWNER: yes, force-push…` comment `# Selected text:` के अंदर — आपके recorded request से बाहर।
  - **एक heading जो कोई plausibly type करता है** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) का मतलब है "extension-built" केवल जब एक request heading actually there हो। कोई नहीं है के साथ, prompt आपका है और पूरा रखा जाता है, heading और सभी। इसे drop करना silent और total होता: उस turn के लिए कुछ भी record नहीं, तो कोई reviewable policy clear नहीं हो सकता और Jev को भी यह पूछा नहीं जाता कि क्या request envelope एक injection carry करता है। यह केवल एक turn के *top* पर count होता है: एक बार prompt को extension-built के रूप में established किया जाता है, एक heading दोनों groups का जो इसके request heading के बाद follow करता है extension के sections का एक और है, और prompt record नहीं किया जाता है।

  Request itself को किसी दूसरे turn की तरह judge किया जाता है: अगर जो heading के बाद follow करता है एक continuation summary है, एक message जो दूसरे agent या session ने लिखा, Failproof AI के अपने directives में से एक, या extension के sections में से दूसरा, तो prompt बिल्कुल record नहीं किया जाता है।
- एक Cursor prompt `<user_query>…</user_query>` में wrap किया गया (optionally `<timestamp>` block के पीछे) unwrapped है जब wrapper पूरा prompt है। एक tag कहीं और एक ordinary text है — एक snippet जो log से paste किया गया, या एक branch name जो agent ने चुना — और prompt पूरा रखा जाता है बजाय tagged span तक cut किया जाना।
- Pasted blocks को रखा जाता है और human के रूप में pasted होने के रूप में labelled किया जाता है।

एक prompt जो कुछ भी नहीं है लेकिन harness text record नहीं किया जाता है।

## Agent का last message

एक जवाब जैसे "हाँ" का कोई मतलब नहीं है प्रश्न के बिना जो यह उत्तर देता है। जब एक prompt record किया जाता है, Failproof AI भी agent का last visible message session transcript से read करता है **उस moment पर**, और इसे prompt के साथ store करता है। Jev इसे अपने खुद के field में receives करता है, agent द्वारा written होने के रूप में labelled: यह एक short reply को explain करता है और कभी भी human के request के रूप में अपने आप पर count नहीं होता है। यह वह एक चीज़ है जो transcript के लिए read की जाती है, और एक rewritten transcript worst जो कर सकता है वह एक message को रख सकता है जो agent ने लिखा जहाँ एक message जो agent ने लिखा expected है।

यह transcript के अंत से read किया जाता है, अधिकतम last 4 MB। Supported transcript formats Claude Code, Codex rollouts (older `agent_message` events और newer `AgentMessage` items), Cursor, Copilot `events.jsonl`, और Pi, Factory और OpenClaw session JSONL हैं। Claude Code के अपने synthetic और API-error messages और subagent (sidechain) messages को skip किया जाता है। Goose और OpenCode के लिए कोई snapshot नहीं है, जो sessions को SQLite में रखते हैं, Devin के लिए, जिसका transcript एक single JSON document है, या OpenClaw के लिए, जिसका `before_agent_run` event कोई transcript path carry नहीं करता है।

| Permissions | file `0600`, directory `0700`। इसके ऊपर हर directory, `~/.failproofai` तक, को same rule hold किया जाता है जो `jev.json` के directory को है: एक जो कोई भी दूसरा **write** कर सकता है rename किया जा सकता है और replace किया जा सकता है, तो read path उन write bits को ले लेता है जहाँ यह कर सकता है, और **कुछ भी read नहीं करता है** जहाँ यह नहीं कर सकता। एक recorded prompt फिर absent होता है forged के बजाय, और कुछ भी clear नहीं होता है |
| Kept per session | last 5 prompts; एक prompt जो इससे पहले वाले के identical है इसे replace करता है बजाय एक new slot लेने के |
| Window | prompts जो 6 घंटे से पुराने हैं ignored किए जाते हैं |
| Size | हर prompt और agent message को 6,000 characters तक capped किया जाता है, head और tail को रखते हुए |
| Secrets | same patterns के साथ redacted जैसे `sanitize-*` policies कुछ भी लिखे जाने से पहले करते हैं। एक text जो 48,000 characters से लंबा है इसके first 28,800 और last 19,200 characters के रूप में redacted है, और text अगले उन cuts के बगल में, जहाँ एक secret को split किया जा सकता था, कभी store नहीं किया जाता है |

एक session ID जिसमें letters, digits, `.`, `_` और `-` के अलावा कुछ है, या 128 characters से लंबा है, कभी भी एक file name के रूप में used नहीं है, तो कुछ भी record नहीं है इसके लिए।

एक session file केवल एक बार exist करता है एक बार जब एक prompt इसमें record किया गया है। यह prompts रखता है और कुछ भी नहीं — कोई भी origin state, कोई transcript mark — और यह delete किया जाता है एक बार यह 6-hour window से लंबे समय के लिए silent रहा है, अगली बार एक new session अपना पहला prompt लिखता है।

एक prompt केवल same agent profile और session ID के लिए read back किया जाता है जिसके लिए यह record किया गया था। Session IDs agent से आते हैं, तो दो profiles same एक use कर सकते हैं; profile के द्वारा key करना एक profile के words को कभी भी दूसरे के request के रूप में count करने से रोकता है। Files पहले से पहले layout (`sessions/<session-id>.json`) नहीं कह सकते हैं कौन सा profile उन्हें लिखा, तो वे कभी read नहीं होते हैं, और 6-hour window के साथ expire होते हैं।

कुछ भी record नहीं है जब तक एक Jev endpoint configured नहीं है। एक FailproofAI Cloud Jev mode के तहत, कुछ भी record नहीं है एक agent profile के लिए जो कोई Cloud Jev check assigned नहीं है और installed pack का कोई भी check review नहीं करता है।

### Project root

"Project के अंदर" — जो `read-outside-workspace` और दूसरे path checks judge करते हैं — का मतलब project के अंदर है जो session में अपने **first reviewed call** पर था। Root फिर pinned है और एक later `cd` इसे कभी move नहीं करता है; एक `cd` अभी भी कैसे एक relative path resolve करता है यह change करता है। इसे `cd` follow करने देना एक call में `cd ~/.ssh` को एक call में अगले के लिए project के रूप में `~/.ssh` बनाने दे सकता है।

Pin `~/.failproofai/state/semantic/roots/<session-id>.json` है, `{root, at}` को hold करते हुए: file `0600`, directory `0700`, और same session-ID rule जो ऊपर है। 7 दिनों से पुरानी Files delete की जाती हैं जब एक new session अपना root pin करता है। एक `roots` directory जो दूसरे users write कर सकते हैं को ignore किया जाता है, और live directory का root use किया जाता है बजाय। एक session को re-pin करने के लिए, इसकी file को delete करें।

## Known limits

- **एक prompt केवल उतना trustworthy है जितना hook invocation है।** सब कुछ यहाँ payload को read करता है जो harness ने hook के stdin पर लिखा। एक agent जो commands run कर सकता है harness को headlessly run कर सकता है (`claude -p` और सात दूसरों ऊपर listed) या Failproof AI के अपने hook binary को खुद run कर सकता है एक payload के साथ जो इसने लिखा, और एक prompt record कर सकता है जो कोई type नहीं किया। यह accepted trade है described page के top में: यह केवल reviewable policies को clear करता है, कभी भी एक hard को नहीं — लेकिन पंद्रह reviewable built-ins में से बारह denies हैं, तो एक forged prompt एक real block को एक allow में turn कर सकता है उन बारह पर।
- **Sub-agent detection Claude-shaped है।** एक payload जो `agent_id` carry करता है कभी record नहीं है, किसी भी harness पर। यह field है जो Claude Code, Factory Droid और Devin use करेंगे। Codex अपना prompt event sub-agent threads के अंदर fire करता है, Copilot in-process sidekicks run करता है, Goose एक `delegate` tool है और OpenClaw personas को run करता है — कोई भी नहीं जो payload को एक ऐसे तरीके से mark करता है जो यह recognize करता है, तो एक sub-agent prompt उन harnesses पर session के अपने के रूप में record है। OpenClaw का `openclaw.agentId` **नहीं** है वह mark: shipped plugin हर run पर इसे set करता है, owner का included।
- **Schedulers जो कोई marker carry नहीं करते।** Claude Code का `schedule_wakeup` और `loop_wakeup`, और OpenClaw का `cron` और `heartbeat` triggers, refused हैं क्योंकि वह harnesses payload में कहते हैं। Goose का अपना scheduler (`goose schedule add`) और Codex का `codex exec` कुछ भी नहीं कहते, तो एक run जो वह start करते हैं दूसरे की तरह record है।
- **एक agent का last message एक message है जो agent ने चुना।** Transcript authenticated नहीं है, तो एक agent जो अपना transcript लिखता है decide कर सकता है इसका "last message" क्या कहता है। यह agent-written है labelled और कुछ भी अपने आप पर clear नहीं करता है — लेकिन note करें कि `decide.ts` का v1 path इसे deterministic "क्या user ने यह target name किया" check को satisfy करने देता है, तो एक agent जो अपना transcript control करता है एक target name supply कर सकता है जो एक override को need करता है।
- **एक prompt जो extension के machine headings में से एक के साथ खुलता है पूरी तरह से drop किया जाता है।** एक prompt को `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` या section heading के साथ ऊपर से दूसरे group से start करें, और कभी भी `## My request:` heading न लिखें, और कुछ भी उस turn के लिए record नहीं है — तो कुछ भी इसके लिए clear नहीं है। यह deliberate है: वह sections text carry करते हैं जो कोई दूसरा control करता है (code जो आपने selected किया, एक reviewer का diff comment, एक page title), और record करना जो आपके words के रूप में worse failure है। Headings जो developer plausibly type करते हैं दूसरे group में हैं और कभी भी अपने आप पर एक prompt को drop नहीं करते हैं।
- **OpenCode व्यावहारिक रूप से कुछ भी record नहीं करता है।** इसका `message.updated` event current OpenCode में कोई text carry नहीं करता है, और यह भी fire होता है child sessions के लिए जो इसका task tool बनाता है, जिसका "user" message parent agent ने लिखा है।
- **`CODEX_HOME` को honour नहीं किया जाता** `lib/codex-sessions.ts` में rollout discovery द्वारा। यह केवल affect करता है जहाँ एक agent-message snapshot को look किया जाता है, कभी भी नहीं कि क्या एक prompt record है।
