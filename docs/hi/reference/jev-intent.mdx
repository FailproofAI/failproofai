जब आप [Jev policy review](/hi/policies/jev) को कॉन्फ़िगर करते हैं, तो evaluator प्रत्येक gated tool call को **मानव ने क्या पूछा** इसके विरुद्ध आंकता है, न कि harness ने agent के सामने जो टेक्स्ट रखा उसके विरुद्ध। "हाँ, force-push करो" जैसा जवाब एक **reviewable** policy को साफ कर सकता है — जो evaluator का पूरा बिंदु है, क्योंकि एक regex जो request नहीं पढ़ सकता असली काम का एक तिहाई ब्लॉक करता है।

वह टेक्स्ट एक ही जगह से आता है: **जो prompt harness खुद hook को अपनी prompt-submit event पर देता है**। Failproof AI इसका वह हिस्सा रिकॉर्ड करता है जो मानव ने टाइप किया — harness wrapping stripped, secrets redacted, capped — अपनी स्टेट डायरेक्टरी के तहत एक `0600` फाइल में। डिस्क पर कुछ नहीं देखा जाता: session transcript एक ऐसी फाइल है जिसे agent एक command में फिर से लिख सकता है, इसलिए यह कभी नहीं पूछा जाता कि किसने prompt लिखा।

## यह जोखिम स्पष्ट रूप से स्वीकार करता है

एक agent जो पहले से ही commands चला सकता है, harness को prompt submit करवा सकता है। `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` और `pi -p` सभी एक ही prompt-submit event, एक ही payload के साथ, एक child session में fire करते हैं जो agent नियंत्रित करता है, जैसे कोई व्यक्ति टाइप कर रहा हो। यह Failproof AI की स्वयं की hook binary भी चला सकता है और एक payload feed कर सकता है जो इसने लिखा है। Failproof AI के अंदर कुछ भी दोनों को अलग नहीं बता सकता — दोनों एक ही program हैं जो एक ही stdin पढ़ रहे हैं।

**तो shell वाला agent अपनी स्वयं की सहमति जाली कर सकता है।** यह एक जानबूझकर trade है, 2026-09-23 को लिया गया, और यहाँ इसके दोनों हिस्से हैं:

- **यह क्या खरीदता है।** विकल्प built और measured था: एक फील्ड की आवश्यकता करें जिसमें harness prompt के author के रूप में मानव का नाम बताए, और अन्यथा कुछ न record करें। कोई shipping harness ऐसा फील्ड नहीं भेजता, तो वह version **कुछ नहीं record करता, हर harness पर** — Jev ने कोई stated intent के साथ हर call को judge किया और कभी एक single policy को clear नहीं कर सका। एक capture जो कभी fire नहीं होता वह एक safer product नहीं है, यह कोई product ही नहीं है।
- **यह क्या नहीं कर सकता।** एक recorded prompt केवल एक policy को clear करता है जो पहले से ही **reviewable** चिह्नित है। एक **hard** policy कभी Jev द्वारा कुछ भी clear नहीं होता, तो एक forged prompt कभी hard deny को allow में नहीं बदल सकता — और hook को skip करना agent को भी कुछ नहीं मिलता: harness tool call के लिए स्वतंत्र रूप से Failproof AI को invoke करता है।
- **यह क्या कर सकता है, पूर्ण आकार में।** सबसे बुरा जो यह कर सकता है वह पंद्रह reviewable built-in policies में से एक को clear करना है — और **इसमें से बारह block करते हैं**। `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` और छह infrastructure-CLI blocks (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) denies हैं, तो forged consent एक real deny को allow में बदल सकता है environment secrets print करने, `.env` फाइल read करने, project के बाहर read करने, `rm -rf`, force-push, secrets फाइल write करने, या live infrastructure change करने में। केवल `warn-git-amend`, `warn-destructive-sql` और `warn-global-package-install` nudges हैं। एक default install बारह में से दो को चालू करता है, `protect-env-vars` और `block-env-files`; बाकी दस केवल एक ऐसी machine पर पहुँचते हैं जहाँ किसी ने उन्हें enabled किया। जो कोई भी prompt नहीं पहुँचता वह सब कुछ hard है — `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, वह guard जो agent को Failproof AI disable करने से रोकता है, और हर दूसरा built-in जो reviewable चिह्नित नहीं है। [Policy authority](/hi/policies/authority) सभी पंद्रह को list करता है और प्रत्येक को कौन review करता है।

जो अभी भी refused है वह सब कुछ है जो check करना सस्ता है और agent केवल asking से प्राप्त नहीं कर सकता: एक turn जो harness का अपना payload machine-submitted के रूप में चिह्नित करता है, एक payload जो sub-agent का नाम बताता है, एक session id जो plain name नहीं है, एक event जो prompt-submit वाली नहीं है, और text जो harness wrapping के अलावा कुछ नहीं है — Failproof AI के अपने stop-gate words सहित, जिन्हें कई harnesses अगले user turn के रूप में वापस भेजते हैं।

## Per-harness table

"Text field" stdin payload field है Failproof AI के per-harness normalization के बाद। "Recorded" कहता है कि क्या prompt को मानव के request के रूप में रखा जाता है।

| Harness | `--cli` | Prompt event → canonical | Text field | Recorded | Agent's last message read from |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | हाँ, जब तक payload का `source` किसी ऐसे turn का नाम न बताए जिसे किसी ने submit न किया (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`)। `user`, `sdk`, एक unknown value और एक build जो कोई `source` नहीं भेजता सभी recorded हैं | session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | हाँ | rollout JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | हाँ | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | हाँ, `<user_query>` wrapper को peel किया जाता है जब यह पूरा prompt हो | agent transcript JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | हाँ — लेकिन वर्तमान OpenCode उस event में कोई text नहीं रखता, तो व्यावहारिक रूप से कुछ नहीं record होता; same message की repeat एक बार record होती है | none (sessions SQLite हैं) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | हाँ, जब तक `input_source` `extension` न हो — दूसरे extension का `sendUserMessage()`, जिसका text model-written या repo-derived हो सकता है | Pi session JSONL |
| Hermes | `hermes` | none | — | नहीं — Hermes के पास कोई prompt-submit event ही नहीं है | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | हाँ, जब तक run metadata run को machine के रूप में न चिह्नित करे: एक `trigger` `user` के अलावा कुछ और, एक `inputProvenance.kind` `external_user` के अलावा कुछ और, या `senderIsOwner: false` | none (`before_agent_run` कोई transcript path नहीं रखता) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | हाँ | droid session JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | हाँ | none (sessions SQLite हैं) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | none | नहीं — `PreInvocation` एक turn में *हर* model call से पहले fire होता है और कोई prompt text नहीं रखता | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | हाँ | none (sessions SQLite हैं) |

दो harnesses कुछ नहीं record करते, और दोनों cases में एक ही कारण से: उनकी event कोई human text नहीं देती। Hermes के पास कोई prompt-submit event नहीं है — इसका native plugin `pre_llm_call` को स्वयं handle करता है और केवल tool, session और subagent events forward करता है। Antigravity का `PreInvocation` हर model call से पहले fire होता है, एक human turn पर और उसके बाद पाँच पर, और कोई prompt field नहीं रखता; hooks भी same conversation में `userMessage` steps inject कर सकते हैं। किसी भी event में record करने के लिए कुछ नहीं है।

## क्या एक prompt को मानव का बनाता है

1. **Event।** Failproof AI को harness के prompt-submit event के लिए invoke किया गया था, जिसे handler `UserPromptSubmit` को canonicalize करता है।
2. **Payload।** Harness इसे hook के stdin पर लिखता है, और यह उपर named field में text रखता है। एक call जो Failproof AI तक पहुँचता है बिना payload के कुछ नहीं record करता।
3. **Payload में कुछ भी turn को out rule नहीं करता।** एक payload जो sub-agent का नाम बताता है (`agent_id`) agent को अपने आप को prompt कर रहा है। एक `source`, `input_source` या OpenClaw run marker जो machine-submitted turn का नाम बताता है refused है। एक **absent** marker कुछ नहीं rule out करता — यह उस version से अंतर है जो कुछ नहीं record करता था, क्योंकि यहाँ हर marker every shipping build पर absent है।
4. **कुछ बचा हुआ wrapping strip करने के बाद** (नीचे देखें)।

**Session transcript किसी के द्वारा prompt लिखे जाने का evidence नहीं है।** इस page के पहले के versions ने एक transcript cross-check describe किया: prompt refused था अगर transcript showed कि model इसे schedule कर रहा था, और transcript को पिछले prompt के साथ continue करना था। वह check चला गया है। Transcript एक file है जिसके ऊपर agent के पास पहले से ही shell है — इसे truncate, replace, read budget से padded किया जा सकता है, turn के start पर snapshotted और end पर restored, या agent द्वारा लिखे गए entries के साथ अच्छा पढ़ने के लिए बनाया जा सकता है। Hardening के हर round के बाद another spelling एक ही forgery का था, तो पूरी mechanism को repair करने के बजाय remove किया गया।

Transcript अभी भी एक चीज के लिए read है: **agent का last visible message**। वह message agent-written है definition से, Jev को यह बताया जाता है, और यह अपने आप में कभी consent नहीं है।

## एक prompt से क्या रखा जाता है

Harnesses एक prompt में मानव के शब्दों से अधिक डालते हैं। कुछ भी store होने से पहले:

- `<system-reminder>` blocks removed होते हैं, और उनके चारों ओर मानव के शब्द रखे जाते हैं।
- एक session-continuation summary ("This session is being continued from a previous conversation…") पूरी तरह dropped है।
- Task notifications, local-command output और interruption markers पूरी तरह dropped हैं।
- एक turn जो दूसरे agent या session ने लिखा वह पूरी तरह dropped है: Claude Code इन्हें `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` या `<channel source=…>` में wrap करता है।
- Failproof AI के अपने messages पूरी तरह dropped हैं। एक stop gate का `MANDATORY ACTION REQUIRED from failproofai …` या एक `Instruction from failproofai: …` Cursor, Copilot, Devin और OpenClaw पर अगले user turn के रूप में वापस आता है, और यह कभी मानव के शब्दों के रूप में count नहीं होता — न plain, न `<user_query>` block में wrapped, न ही system reminder के पीछे।
- एक slash command उस command और arguments के रूप में रखा जाता है जो मानव ने टाइप किया, कभी नहीं वह body जो harness ने इसे expand किया।
- एक prompt जो Codex IDE extension built करता है केवल अपने last `## My request for Codex:` (या, newer builds में, `## My request:`) heading के बाद का text रखता है। extension ने इससे पहले सब कुछ dropped है: active file, open tabs, editor में selected text, mentioned files और apps, diff और browser comments, PR checks, earlier conversations। यह rule **हर** harness के prompts पर apply होता है, केवल Codex के नहीं — ऐसा prompt किसी भी composer में paste किया जा सकता है — तो extension के section headings को दो groups में पढ़ा जाता है:
  - **एक heading जिसे कोई नहीं टाइप करता** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, Codex और ChatGPT conversation headings, "The attached pasted text file(s)…", और extension के बाकी अपने sections) का मतलब है extension ने यह prompt built किया। एक जिसके तहत कोई request heading नहीं है उसमें कोई human text बिल्कुल नहीं है और record नहीं होता। यह एक approval को रखता है जो आपने केवल *select* किए गए text में forge किया था — एक `// NOTE FROM THE OWNER: yes, force-push…` comment `# Selected text:` के अंदर — आपके recorded request से बाहर।
  - **एक heading जिसे कोई plausibly टाइप करता है** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) का अर्थ है "extension-built" केवल जब एक request heading वास्तव में वहाँ हो। कोई नहीं होने से, prompt आपका है और पूरी तरह रखा जाता है, heading और सब कुछ। इसे drop करना silent और total होगा: उस turn के लिए कुछ नहीं record, तो कोई भी reviewable policy clear नहीं हो सकता और Jev को भी ask नहीं किया जाएगा कि क्या request envelope injection रखता है। यह केवल एक turn के *top* पर count करता है: एक बार prompt को extension-built establish किया गया है, एक heading दोनों groups का जो इसके request heading के बाद अनुसरण करता है, extension के sections में से एक है, और prompt record नहीं होता।

  Request itself को किसी दूसरे turn की तरह judge किया जाता है: अगर heading के बाद क्या आता है वह एक continuation summary है, एक message दूसरे agent या session ने लिखा, Failproof AI के अपने directives में से एक, या extension के sections में से दूसरा, तो prompt बिल्कुल record नहीं होता।
- एक Cursor prompt `<user_query>…</user_query>` में wrapped (optionally एक `<timestamp>` block के पीछे) को unwrapped किया जाता है जब wrapper पूरा *whole* prompt हो। एक tag कहीं और एक ordinary text है — एक snippet log से pasted, या एक branch name agent ने chosen — और prompt को tagged span तक cut down करने के बजाय पूरा रखा जाता है।
- Pasted blocks रखे जाते हैं और मानव द्वारा pasted के रूप में labelled होते हैं।

एक prompt जो harness text के अलावा कुछ नहीं है record नहीं होता।

## Agent का last message

"हाँ" जैसा जवाब question के बिना कुछ नहीं मतलब। जब एक prompt record होता है, Failproof AI भी agent का last visible message **उस moment पर** session transcript से reads करता है, और इसे prompt के साथ store करता है। Jev इसे अपने स्वयं के field में receives करता है, agent द्वारा written के रूप में labelled: यह एक short reply को explain करता है और कभी अपने आप पर मानव के request के रूप में count नहीं होता। यह एक चीज़ है जिसके लिए transcript read है, और worst एक rewritten transcript कर सकता है एक message जो agent ने लिखा है जहाँ एक message रखना है जो agent ने लिखा है।

यह transcript के end से, अधिकतम last 4 MB से read होता है। Supported transcript formats Claude Code, Codex rollouts (older `agent_message` events और newer `AgentMessage` items), Cursor, Copilot `events.jsonl`, और Pi, Factory और OpenClaw session JSONL हैं। Claude Code के अपने synthetic और API-error messages और subagent (sidechain) messages skip होते हैं। Goose और OpenCode के लिए कोई snapshot नहीं है, जो sessions को SQLite में रखते हैं, Devin के लिए, जिसका transcript एक single JSON document है, या OpenClaw के लिए, जिसका `before_agent_run` event कोई transcript path नहीं रखता।

## Storage

| Property | Value |
| --- | --- |
| Location | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, जहाँ `<profile>` agent profile है जिसमें prompt टाइप किया गया था: `<integration>.<instance-id>` एक agent के लिए जो FailproofAI को पता है (वह identity जिसे Cloud policies target करते हैं), या अन्यथा just `<integration>` |
| Permissions | file `0600`, directory `0700`। इसके ऊपर हर directory, `~/.failproofai` तक, उसी rule के लिए held है जिसका `jev.json`की directory है: एक जिसे कोई और भी **write** कर सकता है को rename away और replace किया जा सकता है, तो read path उन write bits को जहाँ कर सकता है take off करता है, और **nothing** reads करता है जहाँ नहीं कर सकता। एक recorded prompt तब forged के बजाय absent है, और कुछ भी clear नहीं होता |
| Kept per session | last 5 prompts; एक prompt जो इसके पहले वाले को identical है इसे replace करता है rather than एक नया slot लेने से |
| Window | 6 घंटों से पुराने prompts ignored हैं |
| Size | प्रत्येक prompt और agent message को 6,000 characters तक capped किया जाता है, head और tail को रखते हुए |
| Secrets | `sanitize-*` policies के same patterns से redacted किया जाता है कुछ भी write होने से पहले। एक text जो 48,000 characters से लंबा है उसे अपने first 28,800 और last 19,200 characters के रूप में redacted किया जाता है, और उन cuts के पास का text, जहाँ एक secret split हो सकता था, कभी store नहीं होता |

एक session ID जिसमें letters, digits, `.`, `_` और `-` के अलावा कुछ है, या 128 characters से लंबा है, कभी file name के रूप में use नहीं होता, तो इसके लिए कुछ नहीं record होता।

एक session file केवल एक बार exist होती है एक बार prompt इसमें record हो गया है। यह prompts और कुछ नहीं रखती है — कोई origin state नहीं, कोई transcript mark नहीं — और यह delete हो जाती है एक बार यह six-hour window से longer silent रहा है, अगली बार जब एक नया session अपना first prompt लिखता है।

एक prompt केवल same agent profile और session ID के लिए read back होता है जिसके तहत यह record किया गया था। Session IDs agent से आते हैं, तो दो profiles same one use कर सकते हैं; profile द्वारा key करना एक profile के words को कभी दूसरे के request के रूप में count होने से रखता है। इस layout (`sessions/<session-id>.json`) से पहले की files नहीं कह सकते कि किस profile ने उन्हें लिखा, तो वे कभी read नहीं होते, और six-hour window के साथ expire होते हैं।

कुछ नहीं record होता जब तक Jev endpoint configured न हो। एक FailproofAI Cloud Jev mode के तहत, एक agent profile के लिए कुछ नहीं record होता जिसके लिए कोई Cloud Jev check assign नहीं है और कोई installed pack की check review नहीं करता।

### Project root

"Project के अंदर" — जो `read-outside-workspace` और दूसरे path checks judge करते हैं — का मतलब है project के अंदर जो session था अपने **first reviewed call** पर। Root तब pin होता है और एक बाद का `cd` इसे कभी move नहीं करता; एक `cd` अभी भी बदलता है कि relative path कैसे resolve होता है। इसे `cd` follow करने देना एक call में `cd ~/.ssh` को अगले के लिए `~/.ssh` project बनाने देता।

Pin `~/.failproofai/state/semantic/roots/<session-id>.json` है, holding `{root, at}`: file `0600`, directory `0700`, और उपर के same session-ID rule। 7 दिनों से पुरानी files delete होती हैं जब एक नया session अपना root pin करता है। एक `roots` directory जिसे अन्य users write कर सकते हैं को ignore किया जाता है, और live directory का root use होता है। एक session को re-pin करने के लिए, इसकी file को delete करें।

## Known limits

- **एक prompt केवल hook invocation जितना trustworthy है।** सब कुछ यहाँ वह payload read करता है जो harness ने hook के stdin पर लिखा। एक agent जो commands चला सकता है harness को headlessly चला सकता है (`claude -p` और ऊपर listed सात अन्य) या Failproof AI की hook binary को स्वयं एक payload के साथ चला सकता है जो इसने लिखा, और एक prompt record कर सकता है जिसे किसी ने टाइप नहीं किया। यह accepted trade है इस page के top पर describe की गई: यह केवल reviewable policies clear करता है, कभी hard नहीं — लेकिन पंद्रह reviewable built-ins के बारह denies हैं, तो एक forged prompt एक real block को allow में बदल सकता है इन बारह पर।
- **Sub-agent detection Claude-shaped है।** एक payload `agent_id` रखता है कभी record नहीं होता, किसी भी harness पर। वह field है जो Claude Code, Factory Droid और Devin use करते। Codex अपनी prompt event sub-agent threads के अंदर fire करता है, Copilot in-process sidekicks चलाता है, Goose के पास `delegate` tool है और OpenClaw personas चलाता है — इसमें से कोई भी payload को इस तरीके से चिह्नित नहीं करता जो यह recognise करता है, तो एक sub-agent prompt इन harnesses पर session के अपने रूप में record होता है। OpenClaw का `openclaw.agentId` **नहीं** है वह mark: shipped plugin हर run पर इसे set करता है, owner का included।
- **Schedulers जो कोई marker नहीं रखते।** Claude Code का `schedule_wakeup` और `loop_wakeup`, और OpenClaw का `cron` और `heartbeat` triggers, refused हैं क्योंकि वे harnesses payload में ऐसा कहते हैं। Goose का स्वयं का scheduler (`goose schedule add`) और Codex का `codex exec` कुछ नहीं कहते, तो एक run जो वे start करते record होता है किसी दूसरे की तरह।
- **एक agent का last message एक message हो सकता है जो agent ने chosen किया।** Transcript authenticated नहीं है, तो एक agent जो अपना transcript लिखता है अपना "last message" decide कर सकता है। यह agent-written labeled है और अपने आप में कभी कुछ भी clear नहीं करता — लेकिन ध्यान दें कि `decide.ts`का v1 path इसे deterministic "क्या user ने इस target का नाम रखा" check को satisfy करने देता है, तो एक agent जो अपनी transcript को control करता है एक target name supply कर सकता है जो override को जरूरत है।
- **एक prompt जो extension के machine headings में से एक के साथ खुलता है पूरी तरह dropped होता है।** एक prompt `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` या ऊपर से दूसरे section heading से start करें, और कभी `## My request:` heading न लिखें, और उस turn के लिए कुछ नहीं record होता — तो इसके लिए भी कुछ नहीं clear होता। यह deliberate है: वे sections text रखते हैं जो कोई और control करता है (code आपने selected किया, reviewer का diff comment, page title), और उसे अपने शब्दों के रूप में record करना worse failure है। Headings जिसे developer plausibly type करता है दूसरे group में हैं और कभी अपने आप से एक prompt drop नहीं करते।
- **OpenCode व्यावहारिक रूप से कुछ नहीं record करता।** इसकी `message.updated` event current OpenCode में कोई text नहीं रखता, और यह भी child sessions के लिए fire होता है जो इसका task tool बनाता है, जिसका "user" message parent agent ने लिखा।
- **`CODEX_HOME` honoured नहीं है** `lib/codex-sessions.ts` में rollout discovery द्वारा। यह केवल प्रभावित करता है जहाँ एक agent-message snapshot को look किया जाता है, कभी नहीं कि क्या एक prompt record होता है।
