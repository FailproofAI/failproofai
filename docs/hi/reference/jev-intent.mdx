जब आप [Jev policy review](/hi/policies/jev) configure करते हैं, तो evaluator प्रत्येक gated tool call को **जो मनुष्य ने माँगा** उसके विरुद्ध judge करता है, न कि जो कुछ भी text harness ने agent के सामने रखा। "yes, force-push it" जैसा जवाब एक **reviewable** policy को clear कर सकता है — जो evaluator का पूरा मकसद है, क्योंकि एक regex जो request को नहीं पढ़ सकता असली काम का एक तिहाई block करता है।

वह text एक ही जगह से आता है: **prompt जो harness स्वयं hook को अपने prompt-submit event पर देता है**। Failproof AI इसका वह हिस्सा record करता है जो मनुष्य ने type किया — harness wrapping हटाई हुई, secrets redacted, capped — इसे `0600` file के रूप में अपनी state directory के अंदर। डिस्क पर कुछ भी consult नहीं किया जाता: session transcript एक ऐसी file है जिसे agent एक command में फिर से लिख सकता है, इसलिए कभी नहीं पूछा जाता कि किसने prompt लिखा।

## यह risk, स्पष्ट रूप से

एक agent जो पहले से ही commands चला सकता है harness को prompt submit करवा सकता है। `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` और `pi -p` सभी एक ही prompt-submit event fire करते हैं, एक ही payload के साथ, जैसे एक person type कर रहा हो, एक child session में जिसे वह agent control करता है। यह Failproof AI के अपने hook binary को भी चला सकता है और इसे एक payload feed कर सकता है जिसे वह लिखा। Failproof AI के अंदर कुछ भी दोनों को real चीज़ से अलग नहीं बता सकता — दोनों एक ही program हैं जो एक ही stdin को पढ़ते हैं।

**तो एक agent जिसके पास shell है अपनी consent forge कर सकता है।** यह एक deliberate trade है, 2026-09-23 को लिया गया, और यहाँ इसके दोनों हिस्से हैं:

- **यह क्या खरीदता है।** विकल्प built और measured था: एक field require करो जिसमें harness एक मनुष्य को prompt के author के रूप में नाम दे, और अन्यथा कुछ न record करो। कोई shipping harness ऐसी field नहीं भेजता, इसलिए वह version **हर harness पर कुछ नहीं** record करता था — Jev हर call को कोई stated intent के बिना judge करता था और कभी एक भी policy clear नहीं कर सकता था। एक capture जो कभी fire नहीं होती सुरक्षित product नहीं है, यह कोई product नहीं है।
- **यह क्या नहीं कर सकता।** एक recorded prompt केवल एक पहले से ही **reviewable** marked policy को clear करता है। एक **hard** policy को Jev कुछ नहीं से कभी clear नहीं किया जाता, इसलिए एक forged prompt कभी hard deny को allow में नहीं बदल सकता — और hook को skip करना agent को कुछ नहीं gain करता: harness tool call के लिए independently Failproof AI invoke करता है।
- **यह पूरे size पर क्या कर सकता है।** सबसे बुरी चीज़ जो यह कर सकता है वह fifteen reviewable built-in policies में से एक को clear करना है — और **उसमें से बारह block करते हैं**। `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` और छह infrastructure-CLI blocks (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) denies हैं, इसलिए एक forged consent एक real deny को allow में बदल सकता है environment secrets print करने पर, `.env` file पढ़ने पर, project के बाहर पढ़ने पर, `rm -rf`, force-push, secrets file लिखने पर, या live infrastructure change करने पर। सिर्फ `warn-git-amend`, `warn-destructive-sql` और `warn-global-package-install` nudges हैं। एक default install दो को बारह में से switch करता है, `protect-env-vars` और `block-env-files`; बाकी दस सिर्फ एक machine तक पहुँचते हैं जहाँ किसी ने उन्हें enable किया। जो कोई भी prompt नहीं पहुँचता वह सबकुछ hard है — `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, वह guard जो एक agent को Failproof AI disable करने से रोकता है, और हर दूसरी built-in जो reviewable marked नहीं है। [Policy authority](/hi/policies/authority) सभी पंद्रह को list करता है और हर एक को कौन review करता है।

जो अभी भी refused है वह सबकुछ है जो check करना सस्ता है और जिसे एक agent सिर्फ पूछ कर प्राप्त नहीं कर सकता: एक turn जिसे harness के अपने payload machine-submitted के रूप में mark करते हैं, एक payload जो एक sub-agent नाम देता है, एक session id जो plain name नहीं है, एक event जो prompt-submit नहीं है, और text जो कुछ नहीं बल्कि harness wrapping है — Failproof AI के अपने stop-gate words सहित, जिन्हें कई harnesses अगले user turn के रूप में feed करते हैं।

## Per-harness table

"Text field" hook के stdin payload field है Failproof AI के per-harness normalization के बाद। "Recorded" कहता है कि क्या prompt मनुष्य के request के रूप में kept है।

| Harness | `--cli` | Prompt event → canonical | Text field | Recorded | Agent's last message read from |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | हाँ, जब तक payload का `source` एक turn नाम नहीं देता जिसे किसी ने submit नहीं किया (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`)। `user`, `sdk`, एक unknown value और एक build जो कोई `source` नहीं भेजती सभी recorded हैं | session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | हाँ | rollout JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | हाँ | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | हाँ, जब `<user_query>` wrapper पूरे prompt के रूप में peeled हो | agent transcript JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | हाँ — लेकिन current OpenCode उस event में कोई text नहीं carry करता, इसलिए practice में कुछ नहीं recorded है; एक ही message की repeat एक बार record होती है | none (sessions SQLite हैं) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | हाँ, जब तक `input_source` `extension` नहीं है — दूसरा extension का `sendUserMessage()`, जिसका text model-written या repo-derived हो सकता है | Pi session JSONL |
| Hermes | `hermes` | none | — | नहीं — Hermes के पास कोई prompt-submit event नहीं है | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | हाँ, जब तक run metadata run को एक machine के रूप में नहीं mark करते: `user` के अलावा एक `trigger`, `external_user` के अलावा एक `inputProvenance.kind`, या `senderIsOwner: false` | none (`before_agent_run` कोई transcript path नहीं carry करता) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | हाँ | droid session JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | हाँ | none (sessions SQLite हैं) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | none | नहीं — `PreInvocation` एक turn में *हर* model call से पहले fire होता है और कोई prompt text नहीं carry करता | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | हाँ | none (sessions SQLite हैं) |

दो harnesses कुछ नहीं record करते हैं, और दोनों cases में एक ही reason के लिए: उनकी event कोई human text नहीं देती। Hermes के पास कोई prompt-submit event नहीं है — इसका native plugin `pre_llm_call` को स्वयं handle करता है और सिर्फ tool, session और subagent events को forward करता है। Antigravity का `PreInvocation` हर model call से पहले fire होता है, एक human turn पर और उसके बाद के पाँच पर, और कोई prompt field नहीं carry करता; hooks भी `userMessage` steps को एक ही conversation में inject कर सकते हैं। दोनों events में कुछ भी record करने के लिए नहीं है।

## क्या एक prompt को मनुष्य का बनाता है

1. **Event।** Failproof AI को harness के prompt-submit event के लिए invoke किया गया, जिसे handler `UserPromptSubmit` में canonicalize करता है।
2. **Payload।** Harness इसे hook के stdin पर लिखता है, और यह ऊपर नाम दिए गए field में text carry करता है। एक call जो Failproof AI तक बिना payload के पहुँचती है कुछ नहीं record करती।
3. **Payload में कुछ भी turn को नहीं rule करता है।** एक payload जो एक sub-agent नाम देता है (`agent_id`) agent अपने आप को prompt कर रहा है। एक `source`, `input_source` या OpenClaw run marker जो एक machine-submitted turn नाम देता है refused है। एक **absent** marker कुछ भी नहीं rule करता — यह उस version से difference है जो कुछ नहीं record करता था, क्योंकि हर marker यहाँ हर shipping build पर absent है।
4. **Wrapping strip करने के बाद कुछ बचा है** (नीचे देखें)।

**Session transcript prompt के author का evidence नहीं है।** इस page के पहले versions ने एक transcript cross-check describe किया: prompt को refuse किया जाता था अगर transcript ने दिखाया कि model ने इसे schedule किया, और transcript को वह continue करना था जो previous prompt ने देखा। यह check चली गई है। एक transcript एक file है जिसे agent के पास पहले से shell है — इसे truncate किया जा सकता है, replaced, padded, snapshotted turn के start पर और end पर restore, या अच्छी तरह फिर से read के लिए entries के साथ जिसे agent ने लिखा। hardening के हर round के बाद एक ही forgery की दूसरी spelling followed थी, तो पूरी mechanism को repair के बजाय remove किया गया।

Transcript अभी भी एक चीज़ के लिए read होता है: **agent की last visible message**। वह message agent-written है definition के अनुसार, Jev को यह कहा जाता है, और यह अपने आप consent नहीं है।

## Prompt से क्या kept है

Harnesses एक prompt में मनुष्य के words से ज़्यादा डालते हैं। कुछ भी store होने से पहले:

- `<system-reminder>` blocks को remove किया जाता है, और उनके around मनुष्य के words को keep किया जाता है।
- एक session-continuation summary ("This session is being continued from a previous conversation…") को पूरी तरह drop किया जाता है।
- Task notifications, local-command output और interruption markers को पूरी तरह drop किया जाता है।
- एक turn जिसे दूसरा agent या session लिखा को पूरी तरह drop किया जाता है: Claude Code उन्हें `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` या `<channel source=…>` में wrap करता है।
- Failproof AI के अपने messages को पूरी तरह drop किया जाता है। एक stop gate का `MANDATORY ACTION REQUIRED from failproofai …` या एक `Instruction from failproofai: …` Cursor, Copilot, Devin और OpenClaw पर अगले user turn के रूप में वापस आता है, और यह कभी मनुष्य के words के रूप में count नहीं करता — plain नहीं, `<user_query>` block में नहीं wrapped, system reminder के पीछे नहीं।
- एक slash command को command और arguments के रूप में kept किया जाता है जिसे मनुष्य ने type किया, कभी body नहीं जिसे harness expanded किया।
- एक prompt जिसे Codex IDE extension built किया केवल अपने last `## My request for Codex:` (या, newer builds में, `## My request:`) heading के बाद के text को keep करता है। सबकुछ जिसे extension ने इससे पहले डाला उसे drop किया जाता है: active file, open tabs, editor में selected text, mentioned files और apps, diff और browser comments, PR checks, earlier conversations। यह rule **हर** harness के prompts पर apply किया जाता है, सिर्फ Codex के नहीं — ऐसा prompt किसी भी composer में paste किया जा सकता है — तो extension के section headings को दो groups में read किया जाता है:
  - **एक heading जिसे कोई type नहीं करता** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, Codex और ChatGPT conversation headings, "The attached pasted text file(s)…", और extension के बाकी sections) का मतलब है extension ने यह prompt built किया। उसके अंदर एक request heading के साथ कोई human text नहीं है बिल्कुल और recorded नहीं है। यह एक approval को जो आप केवल *selected* किए text में forged है — एक `// NOTE FROM THE OWNER: yes, force-push…` comment `# Selected text:` के अंदर — आपके recorded request से बाहर रखता है।
  - **एक heading जिसे कोई plausibly type करता है** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) का मतलब है "extension-built" सिर्फ जब एक request heading वास्तव में है। बिना किसी के, prompt आपका है और पूरा kept है, heading और सब। इसे drop करना silent और total होता: उस turn के लिए कुछ नहीं recorded, तो कोई reviewable policy clear नहीं हो सकती और Jev को यह भी नहीं पूछा जाएगा कि क्या request envelope एक injection carry करती है। यह केवल एक turn के *top* पर count करता है: एक बार prompt को extension-built के रूप में establish किया जाए, एक heading दोनों groups में से कुछ अंदर जो उसके request heading को follow करता है उसके बाद अन्य extension के sections हैं, और prompt recorded नहीं है।

  Request खुद को किसी दूसरे turn की तरह judge किया जाता है: अगर heading के बाद जो आता है वह एक continuation summary है, एक message जो दूसरा agent या session ने लिखा, Failproof AI के अपने directives में से एक, या extension के अन्य sections में से एक, तो prompt बिल्कुल recorded नहीं है।
- एक Cursor prompt जो `<user_query>…</user_query>` में wrapped है (optionally `<timestamp>` block के पीछे) को unwrap किया जाता है जब wrapper पूरे prompt है। एक tag कहीं और ordinary text है — एक snippet pasted log से, या एक branch name जिसे agent ने चुना — और prompt को पूरा रखा जाता है rather than tagged span तक cut down किया।
- Pasted blocks को keep और label किया जाता है जैसे human ने pasted किया।

एक prompt जो कुछ नहीं बल्कि harness text है recorded नहीं है।

## Agent की last message

"yes" जैसा reply उस question के बिना कुछ नहीं मतलब रखता जिसे यह answer देता है। जब एक prompt record होता है, Failproof AI agent की last visible message को भी session transcript से read करता है **उस moment पर**, और इसे prompt के साथ store करता है। Jev इसे अपने field में receive करता है, agent-written के रूप में label किया: यह एक short reply explain करता है और कभी मनुष्य के request के रूप में अपने आप count नहीं करता। यह एक चीज़ है जिसके लिए transcript read होता है, और सबसे बुरी चीज़ जिसे एक rewritten transcript कर सकता है वह एक message को जिसे agent ने लिखा है जहाँ एक message जिसे agent ने लिखा है expected है।

यह transcript के end से read होता है, सबसे ज़्यादा last 4 MB। Supported transcript formats Claude Code हैं, Codex rollouts (older `agent_message` events और newer `AgentMessage` items), Cursor, Copilot `events.jsonl`, और Pi, Factory और OpenClaw session JSONL। Claude Code के अपने synthetic और API-error messages और subagent (sidechain) messages skip किए जाते हैं। Goose और OpenCode के लिए कोई snapshot नहीं है, जो sessions को SQLite में रखते हैं, Devin के लिए, जिसका transcript एक single JSON document है, या OpenClaw के लिए, जिसका `before_agent_run` event कोई transcript path नहीं carry करता।

## Storage

| Property | Value |
| --- | --- |
| Location | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, जहाँ `<profile>` agent profile है जिसमें prompt type किया गया था: `<integration>.<instance-id>` एक agent के लिए जिसे FailproofAI जानता है (identity जो Cloud policies target करते हैं), या सिर्फ `<integration>` अन्यथा |
| Permissions | file `0600`, directory `0700`। हर directory इसके ऊपर, `~/.failproofai` तक, को एक ही rule hold किया जाता है जिसे `jev.json` की directory है: एक जिसे कोई और भी **write** कर सकता है को rename किया जा सकता है और replace किया जा सकता है, तो read path उन write bits को जहाँ यह कर सकता है वहाँ ले लेता है, और **कुछ नहीं** read करता है जहाँ यह नहीं कर सकता। एक recorded prompt तब absent है rather than forged, और कुछ नहीं clear होता |
| Kept per session | last 5 prompts; एक prompt जो पिछले वाले के identical है इसे replace करता है rather than नई slot ले रहा है |
| Window | 6 hours से पुराने prompts को ignore किया जाता है |
| Size | हर prompt और agent message को 6,000 characters तक cap किया जाता है, head और tail को keep करते हुए |
| Secrets | `sanitize-*` policies के same patterns से redact किए जाते हैं कुछ भी write होने से पहले। 48,000 characters से longer text को इसके पहले 28,800 और last 19,200 characters के रूप में redact किया जाता है, और वह text जो उन cuts के बगल में है, जहाँ एक secret split हो सकता था, कभी store नहीं होता |

एक session ID जो सिर्फ letters, digits, `.`, `_` और `-` के अलावा कुछ contain करता है, या 128 characters से longer है, कभी file name के रूप में use नहीं होता, तो कुछ नहीं recorded है इसके लिए।

एक session file केवल एक बार exist होती है एक prompt इसमें record हो गया हो। यह prompts और कुछ नहीं hold करती — कोई origin state नहीं, कोई transcript mark नहीं — और यह एक बार delete होती है जब यह six-hour window से longer silent रहा हो, अगली बार जब एक नया session अपना पहला prompt लिखे।

एक prompt को केवल एक ही agent profile और session ID के लिए read किया जाता है जिसके अंदर record किया गया था। Session IDs agent से आते हैं, तो दो profiles एक ही use कर सकते हैं; profile के अनुसार key करना एक profile के words को कभी दूसरे के request के रूप में count होने से रोकता है। इस layout से पहले की files (`sessions/<session-id>.json`) यह नहीं कह सकते कि किसने उन्हें लिखा, तो उन्हें कभी नहीं read किया जाता है, और six-hour window के साथ expire होते हैं।

कुछ नहीं record होता जब तक एक Jev endpoint configure नहीं है। एक FailproofAI Cloud Jev mode के अंदर, एक agent profile के लिए कुछ नहीं record होता जिसे कोई Cloud Jev check assign नहीं है और किसी installed pack का check नहीं review करता।

### Project root

"Project के अंदर" — जो `read-outside-workspace` और दूसरे path checks judge करते हैं — का मतलब project के अंदर है जिसमें session अपने **first reviewed call** पर था। Root तब pin होता है और एक बाद का `cd` इसे कभी नहीं move करता; एक `cd` अभी भी कैसे एक relative path resolve होता है change करता है। इसे `cd` के बाद follow करने देना `cd ~/.ssh` को एक call में `~/.ssh` को next के लिए project बनाने देता।

Pin `~/.failproofai/state/semantic/roots/<session-id>.json` है, `{root, at}` को hold करता है: file `0600`, directory `0700`, और ऊपर जैसा ही session-ID rule। 7 दिन से पुरानी files को delete किया जाता है जब एक नया session अपना root pin करता है। एक `roots` directory जिसे दूसरे users write कर सकते हैं को ignore किया जाता है, और live directory का root use होता है। एक session को re-pin करने के लिए, इसकी file को delete करो।

## Known limits

- **एक prompt सिर्फ hook invocation जितना trustworthy है।** सबकुछ यहाँ वह payload read करता है जिसे harness ने hook के stdin पर लिखा। एक agent जो commands चला सकता है harness को headlessly (`claude -p` और ऊपर listed सात others) चला सकता है या Failproof AI के अपने hook binary को अपने लिखे payload के साथ चला सकता है, और एक prompt record कर सकता है जिसे किसी ने type नहीं किया। यह accepted trade है जो इस page के top पर describe की गई है: यह सिर्फ reviewable policies clear करता है, कभी नहीं एक hard — लेकिन fifteen reviewable built-ins में से बारह denies हैं, तो एक forged prompt एक real block को उन बारह पर allow में बदल सकता है।
- **Sub-agent detection Claude-shaped है।** एक payload जो `agent_id` carry करता है को कभी record नहीं किया जाता है, किसी harness पर। यह field है जिसे Claude Code, Factory Droid और Devin use करते। Codex अपने prompt event को sub-agent threads के अंदर fire करता है, Copilot in-process sidekicks run करता है, Goose के पास एक `delegate` tool है और OpenClaw personas run करता है — जिनमें से कोई भी payload को इस तरह mark नहीं करता है जिसे यह recognize करता है, तो उन harnesses पर एक sub-agent prompt session के अपने के रूप में recorded है। OpenClaw का `openclaw.agentId` **नहीं** वह mark है: shipped plugin हर run पर इसे set करता है, owner का included।
- **Schedulers जो कोई marker नहीं carry करते।** Claude Code का `schedule_wakeup` और `loop_wakeup`, और OpenClaw का `cron` और `heartbeat` triggers, refused हैं क्योंकि वह harnesses payload में कहते हैं। Goose का अपना scheduler (`goose schedule add`) और Codex का `codex exec` कुछ नहीं कहते, तो एक run जिसे वह start करते है recorded है किसी दूसरे की तरह।
- **एक agent की last message एक message हो सकता है जिसे agent ने चुना।** Transcript authenticated नहीं है, तो एक agent जो अपने transcript को लिखता है अपने "last message" को decide कर सकता है। यह agent-written के रूप में label है और कभी अपने आप कुछ भी clear नहीं करता — लेकिन note करो कि `decide.ts` की v1 path इसे deterministic "did the user name this target" check को satisfy करने देता है, तो एक agent जो अपने transcript को control करता है एक target name supply कर सकता है जिसे एक override need करता है।
- **एक prompt जो extension के machine headings में से एक के साथ open होता है पूरी तरह drop होता है।** एक prompt को `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` या ऊपर के पहले group से दूसरी section heading के साथ start करो, और कभी एक `## My request:` heading न लिखो, और उस turn के लिए कुछ नहीं record होता है — तो इसके लिए कुछ भी clear नहीं होता है। यह deliberate है: वह sections text carry करते हैं जिसे कोई दूसरा control करता है (code जिसे आप selected किए, एक reviewer का diff comment, एक page title), और उसे अपने words के रूप में record करना बुरी failure है। Headings जिसे एक developer plausibly type करता है दूसरे group में हैं और कभी अपने आप prompt को drop नहीं करते।
- **OpenCode practice में कुछ नहीं record करता।** इसकी `message.updated` event current OpenCode में कोई text नहीं carry करता है, और यह भी child sessions के लिए fire होता है जिन्हें इसका task tool create करता है, जिनका "user" message parent agent ने लिखा।
- **`CODEX_HOME` को honour नहीं किया जाता** `lib/codex-sessions.ts` में rollout discovery द्वारा। यह केवल उसे प्रभावित करता है जहाँ एक agent-message snapshot को look के लिए जाता है, कभी नहीं कि क्या एक prompt recorded है।
