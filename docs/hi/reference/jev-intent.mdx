जब आप [Jev policy review](/hi/policies/jev) configure करते हैं, तो evaluator प्रत्येक gated tool call को **मानव ने क्या माँगा** इसके मुकाबले judge करता है, न कि harness ने agent के सामने जो कुछ भी text रखा हो। "yes, force-push it" जैसा reply एक **reviewable** policy को clear कर सकता है — जो evaluator का पूरा उद्देश्य है, क्योंकि एक regex जो request को नहीं पढ़ सकता real work का एक तिहाई block कर देता है।

वह text एक जगह से आता है: **harness जो prompt अपने prompt-submit event पर hook को देता है**। Failproof AI इसका वह हिस्सा record करता है जो मानव ने type किया — harness wrapping हटाई गई, secrets redacted, capped — एक `0600` file में अपनी state directory के under। Disk पर कुछ भी consult नहीं किया जाता: session transcript एक file है जिसे agent एक command में rewrite कर सकता है, इसलिए कभी भी नहीं पूछा जाता कि किसने prompt लिखा।

## इस risk को साफ-साफ बताएँ

एक agent जो पहले से ही commands चला सकता है, harness को prompt submit करवा सकता है। `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` और `pi -p` सभी एक child session में same prompt-submit event, same payload के साथ fire करते हैं जो agent controls करता है, जैसे कोई person type करता है। यह Failproof AI's own hook binary भी run कर सकता है और इसे एक payload देता है जो इसने लिखा है। Failproof AI के अंदर कुछ भी दोनों को real चीज़ से differentiate नहीं कर सकता — दोनों ही same program हैं जो same stdin को read करते हैं।

**तो एक agent जिसके पास shell है अपनी खुद की consent forge कर सकता है।** यह एक deliberate trade है, 2026-09-23 पर लिया गया, और यहाँ इसके दोनों हिस्से हैं:

- **यह क्या खरीदता है।** Alternative को build और measure किया गया था: एक field की जरूरत करो जिसमें harness एक मानव को prompt के author के रूप में name करे, और अन्यथा कुछ न record करो। कोई भी shipping harness ऐसी field नहीं भेजता, इसलिए उस version ने **nothing, every harness पर** record किया — Jev ने प्रत्येक call को बिना stated intent के judge किया और कभी single policy को clear नहीं कर सका। एक capture जो कभी fire न हो safer product नहीं है, यह कोई product नहीं है।
- **यह क्या नहीं कर सकता।** एक recorded prompt केवल एक policy को clear करता है जो पहले से **reviewable** marked है। एक **hard** policy कभी भी Jev की किसी चीज़ से clear नहीं होता, तो forged prompt कभी hard deny को allow में नहीं बदल सकता — और hook को skip करना agent को कुछ नहीं देता: harness tool call के लिए independently Failproof AI को invoke करता है।
- **यह क्या कर सकता है, full size पर।** सबसे बुरा यह कर सकता है कि fifteen reviewable built-in policies में से एक को clear करे — और **twelve of those fifteen block करते हैं**। `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` और छः infrastructure-CLI blocks (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) denies हैं, तो forged consent एक real deny को allow में बदल सकता है environment secrets print करने पर, `.env` file read करने पर, project के बाहर read करने पर, `rm -rf`, force-push, secrets file write करने पर, या live infrastructure को change करने पर। केवल `warn-git-amend`, `warn-destructive-sql` और `warn-global-package-install` nudges हैं। एक default install दो of the twelve को turn on करता है, `protect-env-vars` और `block-env-files`; बाकी दस केवल एक machine पर पहुँचते हैं जहाँ किसी ने उन्हें enable किया। कोई भी prompt जो reach नहीं करता है वह सबकुछ hard — `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, वह guard जो एक agent को Failproof AI disable करने से रोकता है, और हर दूसरा built-in जो reviewable marked नहीं है। [Policy authority](/hi/policies/authority) सभी fifteen को list करता है और प्रत्येक को क्या review करता है।

जो अभी भी refused है वह सबकुछ जो check करना cheap है और जो agent केवल पूछकर प्राप्त नहीं कर सकता: एक turn जो harness के payload को machine-submitted के रूप में mark करता है, एक payload जो sub-agent को name करता है, एक session id जो plain name नहीं है, एक event जो prompt-submit नहीं है, और text जो केवल harness wrapping है — including Failproof AI's own stop-gate words, जिन्हें कई harnesses next user turn के रूप में feed back करते हैं।

## Per-harness table

"Text field" Failproof AI's per-harness normalization के बाद stdin payload field है। "Recorded" कहता है कि prompt को मानव के request के रूप में रखा जाता है या नहीं।

| Harness | `--cli` | Prompt event → canonical | Text field | Recorded | Agent's last message read from |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | हाँ, जब तक payload के `source` को एक turn name न करे जो किसी ने submit न किया हो (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`)। `user`, `sdk`, एक unknown value और एक build जो कोई `source` नहीं भेजता सभी recorded हैं | the session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | हाँ | the rollout JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | हाँ | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | हाँ, `<user_query>` wrapper के साथ peeled जब यह पूरा prompt है | the agent transcript JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | हाँ — लेकिन current OpenCode उस event में कोई text नहीं रखता, इसलिए practice में कुछ नहीं record होता; same message का repeat एक बार record होता है | none (sessions SQLite हैं) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | हाँ, जब तक `input_source` `extension` न हो — दूसरे extension के `sendUserMessage()`, जिसका text model-written या repo-derived हो सकता है | the Pi session JSONL |
| Hermes | `hermes` | none | — | नहीं — Hermes के पास कोई prompt-submit event नहीं है | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | हाँ, जब तक run metadata run को machine के रूप में mark न करे: एक `trigger` जो `user` न हो, एक `inputProvenance.kind` जो `external_user` न हो, या `senderIsOwner: false` | none (`before_agent_run` कोई transcript path नहीं रखता) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | हाँ | the droid session JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | हाँ | none (sessions SQLite हैं) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | none | नहीं — `PreInvocation` *हर* model call से पहले fire होता है एक turn में और कोई prompt text नहीं रखता | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | हाँ | none (sessions SQLite हैं) |

दो harnesses कुछ नहीं record करते, और दोनों cases में एक ही कारण से: उनका event human text नहीं देता। Hermes के पास prompt-submit event नहीं है — इसका native plugin `pre_llm_call` को खुद handle करता है और केवल tool, session और subagent events को forward करता है। Antigravity के `PreInvocation` एक human turn से पहले हर model call से पहले fire होते हैं और उसके बाद के पाँच, और कोई prompt field नहीं रखते; hooks भी same conversation में `userMessage` steps inject कर सकते हैं। इनमें से किसी भी event में record करने के लिए कुछ नहीं है।

## क्या एक prompt को मानव का बनाता है

1. **Event।** Failproof AI को harness के prompt-submit event के लिए invoke किया गया था, जिसे handler को `UserPromptSubmit` में canonicalize करता है।
2. **Payload।** Harness इसे hook के stdin पर लिखता है, और यह ऊपर named field में text रखता है। एक call जो बिना payload के Failproof AI तक पहुँचता है कुछ नहीं record करता।
3. **Payload में कुछ भी turn को rule out नहीं करता।** एक payload जो sub-agent को name करता है (`agent_id`) agent अपने को prompt कर रहा है। एक `source`, `input_source` या OpenClaw run marker जो machine-submitted turn को name करता है refused है। एक **absent** marker कुछ भी rule out नहीं करता — यह उस version से difference है जो कुछ नहीं record करता था, क्योंकि हर marker यहाँ हर shipping build पर absent है।
4. **कुछ wrapping strip होने के बाद बचा हुआ है** (नीचे देखें)।

**Session transcript prompt के author का proof नहीं है।** इस page के पहले versions ने एक transcript cross-check describe किया: prompt को refuse किया गया था अगर transcript ने model को इसे schedule करते दिखाया, और transcript को previous prompt ने देखा वह जारी रखना पड़ा। यह check gone है। एक transcript एक file है जिस पर agent के पास पहले से shell है — इसे truncate किया जा सकता है, replace किया जा सकता है, read budget के past padded किया जा सकता है, एक turn की start पर snapshotted और end पर restored किया जा सकता है, या entries के साथ फिर से read well बनाया जा सकता है जो agent ने लिखे। Hardening के प्रत्येक round के बाद same forgery के एक और spelling के साथ किया गया, इसलिए पूरी mechanism को repair करने के बजाय remove किया गया।

Transcript अभी भी एक चीज़ के लिए read किया जाता है: **agent का last visible message**। यह message agent-written है definition के अनुसार, Jev को ऐसा बताया जाता है, और यह कभी अपने से consent नहीं है।

## Prompt से क्या रखा जाता है

Harnesses एक prompt में मानव के शब्दों से अधिक डालते हैं। कुछ भी store करने से पहले:

- `<system-reminder>` blocks को हटाया जाता है, और उनके चारों ओर मानव के शब्दों को रखा जाता है।
- एक session-continuation summary ("यह session एक पिछली conversation से continue किया जा रहा है…") को पूरी तरह drop किया जाता है।
- Task notifications, local-command output और interruption markers को पूरी तरह drop किया जाता है।
- एक turn जो दूसरे agent या session ने लिखा को पूरी तरह drop किया जाता है: Claude Code उन्हें `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` या `<channel source=…>` में wrap करता है।
- Failproof AI के own messages को पूरी तरह drop किया जाता है। एक stop gate का `MANDATORY ACTION REQUIRED from failproofai …` या एक `Instruction from failproofai: …` Cursor, Copilot, Devin और OpenClaw पर next user turn के रूप में वापस आता है, और यह कभी मानव के शब्दों के रूप में count नहीं करता — plain नहीं, `<user_query>` block में wrap नहीं, system reminder के पीछे नहीं।
- एक slash command को command और arguments के रूप में रखा जाता है जो मानव ने type किए, कभी नहीं harness ने इसे expand किया।
- एक prompt जो Codex IDE extension ने build किया केवल अपने last `## My request for Codex:` (या, newer builds में, `## My request:`) heading के बाद text को रखता है। सबकुछ जो extension इसके से पहले डाला drop किया जाता है: active file, open tabs, editor में selected text, mentioned files और apps, diff और browser comments, PR checks, earlier conversations। यह rule **हर** harness के prompts पर apply होता है, केवल Codex के न — ऐसा prompt किसी भी composer में paste किया जा सकता है — तो extension के section headings को दो groups में read किया जाता है:
  - **एक heading जो कोई type नहीं करता** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, Codex और ChatGPT conversation headings, "The attached pasted text file(s)…", और extension के बाकी own sections) मतलब extension ने यह prompt build किया। एक जिसके पास इसके under कोई request heading नहीं है कोई भी human text नहीं रखता और record नहीं होता। यह एक approval को आपके द्वारा merely *selected* text में forge किए जाने से रोकता है — एक `// NOTE FROM THE OWNER: yes, force-push…` comment `# Selected text:` के अंदर — अपने recorded request से बाहर।
  - **एक heading जो कोई plausibly types** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) मतलब "extension-built" केवल जब एक request heading actually वहाँ हो। None के साथ, prompt yours है और पूरी तरह kept है, heading और सब। इसे drop करना silent और total होगा: उस turn के लिए कोई भी recorded नहीं, इसलिए कोई भी reviewable policy clear नहीं हो सकती और Jev को भी ask नहीं किया जाएगा कि request envelope में injection है। यह केवल एक turn के *top* पर count करता है: एक बार prompt को extension-built के रूप में establish किया गया, एक heading of either group जो इसके request heading को follow करते हैं के अंदर extension के एक और section हैं, और prompt record नहीं होता।

  Request को किसी दूसरे turn की तरह judge किया जाता है: अगर heading के बाद क्या आता है एक continuation summary है, एक message दूसरे agent या session ने लिखा, Failproof AI के own directives में से एक, या extension के एक और section, prompt को record नहीं किया जाता।
- एक Cursor prompt जो `<user_query>…</user_query>` में wrap किया गया है (optionally एक `<timestamp>` block के पीछे) को unwrap किया जाता है जब wrapper पूरा prompt है। एक tag कहीं और एक ordinary text है — एक snippet paste किया गया log से, या एक branch name agent ने चुना — और prompt को पूरी तरह रखा जाता है rather than cut down to the tagged span.
- Pasted blocks को रखा जाता है और मानव द्वारा pasted के रूप में labelled किया जाता है।

एक prompt जो केवल harness text है record नहीं होता।

## Agent का last message

एक reply जैसे "yes" उस question के बिना nothing का मतलब नहीं जो इसका जवाब देता है। जब एक prompt recorded होता है, Failproof AI भी agent का last visible message session transcript से पढ़ता है **उस moment पर**, और इसे prompt के साथ store करता है। Jev इसे अपने own field में receives करता है, agent-written के रूप में labelled: यह एक short reply को explain करता है और कभी अपने से मानव के request के रूप में count नहीं करता। यह एक चीज़ है जो transcript को read किया जाता है, और एक rewritten transcript कर सकता है एक message जो agent ने लिखा को जहाँ एक message जो agent ने लिखा के रूप में expected है।

यह transcript के end से read किया जाता है, सबसे अधिक last 4 MB। Supported transcript formats Claude Code हैं, Codex rollouts (पुराने `agent_message` events और newer `AgentMessage` items), Cursor, Copilot `events.jsonl`, और Pi, Factory और OpenClaw session JSONL। Claude Code के own synthetic और API-error messages और subagent (sidechain) messages को skip किया जाता है। Goose और OpenCode के लिए कोई snapshot नहीं है, जो sessions को SQLite में रखते हैं, Devin के लिए, जिसका transcript एक single JSON document है, या OpenClaw के लिए, जिसका `before_agent_run` event कोई transcript path नहीं रखता।

## Storage

| Property | Value |
| --- | --- |
| Location | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, जहाँ `<profile>` agent profile है जिसमें prompt type किया गया था: `<integration>.<instance-id>` एक agent के लिए FailproofAI जानता है (identity Cloud policies target करते हैं), या बस `<integration>` अन्यथा |
| Permissions | file `0600`, directory `0700`। इसके above का हर directory, `~/.failproofai` तक, उसी rule के लिए held है जो `jev.json` के directory को है: एक जिसे कोई भी दूसरा **write** कर सकता है को rename किया जा सकता है और replace किया जा सकता है, इसलिए read path उन write bits को ले जाता है जहाँ यह कर सकता है, और **nothing** को read करता है जहाँ यह नहीं कर सकता। एक recorded prompt फिर absent होता है rather than forged, और कुछ भी clear नहीं होता |
| Kept per session | the last 5 prompts; एक prompt identical to the one before it को इसकी जगह लेता है rather than taking a new slot |
| Window | 6 hours से पुरानी prompts को ignore किया जाता है |
| Size | प्रत्येक prompt और agent message को 6,000 characters पर capped किया जाता है, keeping the head और tail |
| Secrets | same patterns के साथ redacted जैसे `sanitize-*` policies कुछ भी write करने से पहले। एक 48,000 characters से longer text को इसके first 28,800 और last 19,200 characters के रूप में redacted किया जाता है, और text next to उन cuts के लिए, जहाँ एक secret को split किया जा सकता था, कभी store नहीं होता |

एक session ID जिसमें letters, digits, `.`, `_` और `-` के अलावा कुछ भी है, या 128 characters से लंबा है, कभी भी file name के रूप में use नहीं किया जाता, इसलिए इसके लिए कुछ भी record नहीं होता।

एक session file केवल एक बार exist करता है एक prompt इसमें record किया गया है। यह prompts को रखता है और कुछ भी नहीं — कोई origin state नहीं, कोई transcript mark नहीं — और यह delete होता है एक बार यह छः-hour window से अधिक time के लिए silent हो, अगली बार एक नया session अपना first prompt लिखता है।

एक prompt को केवल same agent profile और session ID के लिए read किया जाता है जिसके under यह record किया गया था। Session IDs agent से आते हैं, इसलिए दो profiles same एक को use कर सकते हैं; profiling द्वारा keying एक profile के शब्दों को कभी दूसरे के request के रूप में count करने से रोकता है। Files इस layout से पहले (`sessions/<session-id>.json`) यह नहीं कह सकते कि कौन सा profile उन्हें लिखा, इसलिए कभी भी read नहीं किए जाते, और छः-hour window से expire होते हैं।

कुछ भी record नहीं होता जब तक एक Jev endpoint configured न हो। FailproofAI Cloud Jev mode के under, कोई agent profile के लिए कुछ भी record नहीं होता जिसे कोई Cloud Jev check assign नहीं है और कोई installed pack का check review नहीं करता।

### The project root

"Project के अंदर" — जो `read-outside-workspace` और दूसरे path checks judge करते हैं — मतलब project के अंदर जो session इसके **first reviewed call** पर था। Root तब pin किया जाता है और एक later `cd` इसे कभी नहीं move करता; एक `cd` अभी भी बदलता है कि एक relative path कैसे resolve होता है। इसे `cd` को follow करने देना `cd ~/.ssh` को एक call में allow करेगा `~/.ssh` को अगले के लिए project बनाता है।

Pin `~/.failproofai/state/semantic/roots/<session-id>.json` है, holding `{root, at}`: file `0600`, directory `0700`, और same session-ID rule as above। Files 7 days से पुरानी होती हैं delete की जाती हैं जब एक नया session अपना root pin करता है। एक `roots` directory जिसे दूसरे users write कर सकते हैं को ignore किया जाता है, और live directory का root use होता है। एक session को re-pin करने के लिए, इसकी file को delete करो।

## Known limits

- **एक prompt केवल hook invocation जितना trustworthy है।** सबकुछ यहाँ उस payload को read करता है जो harness hook के stdin पर लिखता है। एक agent जो commands run कर सकता है harness को headlessly run कर सकता है (`claude -p` और ऊपर listed सात दूसरे) या Failproof AI के hook binary को खुद run कर सकता है एक payload के साथ जो इसने लिखा, और एक prompt record कर सकता है जो किसी ने type नहीं किया। यह accepted trade है page के top पर describe किया गया: यह केवल reviewable policies को clear करता है, कभी नहीं एक hard को — लेकिन fifteen reviewable built-ins के twelve denies हैं, तो forged prompt एक real block को उन बारह पर allow में बदल सकता है।
- **Sub-agent detection Claude-shaped है।** एक payload जो `agent_id` रखता है कभी record नहीं होता, किसी भी harness पर। यह field है जो Claude Code, Factory Droid और Devin use करेंगे। Codex अपना prompt event sub-agent threads के अंदर fire करता है, Copilot in-process sidekicks run करता है, Goose के पास एक `delegate` tool है और OpenClaw personas run करता है — कोई भी इसे एक तरीके से mark नहीं करता जो इसे recognizes करे, तो एक sub-agent prompt उन harnesses पर session के अपने के रूप में record होता है। OpenClaw का `openclaw.agentId` **नहीं** है वह mark: shipped plugin इसे हर run पर set करता है, owner का included।
- **Schedulers जो कोई marker नहीं रखते।** Claude Code के `schedule_wakeup` और `loop_wakeup`, और OpenClaw के `cron` और `heartbeat` triggers, refuse हैं क्योंकि वे harnesses payload में कहते हैं। Goose का अपना scheduler (`goose schedule add`) और Codex का `codex exec` कुछ नहीं कहते, तो एक run जो उन्हें start करते हैं record किया जाता है किसी दूसरे जैसे।
- **एक agent का last message एक message हो सकता है जो agent ने choose किया।** Transcript authenticated नहीं है, तो एक agent जो अपना transcript लिखता है अपने "last message" को decide कर सकता है कि क्या कहे। यह agent-written के रूप में label किया जाता है और कभी अपने से कुछ भी clear नहीं करता — लेकिन note करो कि `decide.ts` का v1 path इसे deterministic "did the user name this target" check को satisfy करने देता है, तो एक agent जो अपना transcript control करता है एक target name supply कर सकता है जो एक override को needs करता है।
- **एक prompt जो extension के machine headings में से एक के साथ open होता है पूरी तरह drop होता है।** एक prompt को `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` या ऊपर से दूसरे section heading के साथ start करो, और कभी `## My request:` heading न लिखो, और कुछ भी record नहीं होता उस turn के लिए — तो कुछ भी clear नहीं होता इसके लिए या। यह deliberate है: वे sections text रखते हैं कि कोई दूसरा control करता है (code आपने selected किया, एक reviewer का diff comment, एक page title), और record करना कि आपके शब्दों के रूप में worse failure है। Headings एक developer plausibly types दूसरे group में हैं और कभी भी अपने पर एक prompt को drop नहीं करते।
- **OpenCode practice में कुछ नहीं record करता।** इसका `message.updated` event current OpenCode में कोई text नहीं रखता, और यह भी fire करता है child sessions के लिए जो इसका task tool बनाता है, जिसका "user" message parent agent ने लिखा।
- **`CODEX_HOME` को honour नहीं किया जाता** `lib/codex-sessions.ts` में rollout discovery द्वारा। यह केवल प्रभावित करता है जहाँ एक agent-message snapshot को देखा जाता है, कभी नहीं कि क्या एक prompt record होता है।
