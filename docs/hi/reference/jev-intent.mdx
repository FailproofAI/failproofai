जब आप [Jev policy review](/hi/policies/jev) को configure करते हैं, तो evaluator प्रत्येक gated tool call का न्याय **मनुष्य ने क्या मांगा** इसके विरुद्ध करता है, न कि जो कुछ भी text harness ने agent के सामने रखा। "हां, force-push कर दो" जैसा जवाब एक **reviewable** policy को clear कर सकता है — जो पूरी चीज़ का अंक है, क्योंकि एक regex जो request को नहीं पढ़ सकता, असली काम का एक तिहाई हिस्सा block करता है।

वह text एक ही जगह से आता है: **prompt जो harness खुद अपने prompt-submit event पर hook को देता है**। Failproof AI इसके उस हिस्से को record करता है जो मनुष्य ने type किया — harness wrapping stripped, secrets redacted, capped — इसे अपनी स्वयं की state directory के तहत एक `0600` file में। कोई भी disk से consulted नहीं है: session transcript एक ऐसी file है जिसे agent एक command में फिर से लिख सकता है, इसलिए इसे कभी नहीं पूछा जाता कि किसने prompt लिखा।

## यह जोखिम स्पष्ट रूप से स्वीकार करता है

एक agent जो पहले से ही commands चला सकता है, harness को एक prompt submit करवा सकता है। `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` और `pi -p` सभी एक ही prompt-submit event को fire करते हैं, एक ही payload के साथ, जैसे कोई person type कर रहा हो, एक child session में जिसे agent नियंत्रित करता है। यह Failproof AI की अपनी hook binary को भी चला सकता है और इसे एक payload feed कर सकता है जिसे उसने लिखा। Failproof AI के अंदर कुछ भी दोनों को असली चीज़ से अलग नहीं बता सकता — दोनों एक ही program हैं जो एक ही stdin को पढ़ते हैं।

**तो एक agent जिसके पास shell है, अपनी स्वयं की consent forge कर सकता है।** यह 2026-09-23 पर लिया गया एक जानबूझकर trade है, और यहाँ इसके दोनों पहलू हैं:

- **यह क्या खरीदता है।** विकल्प बनाया और मापा गया था: एक field की requirement करें जिसमें harness एक मनुष्य को prompt के author के रूप में नाम दे, और अन्यथा कुछ भी record न करें। कोई भी shipping harness ऐसा field नहीं भेजता, इसलिए उस version ने **कुछ भी नहीं record किया, हर harness पर** — Jev ने हर call का न्याय कोई stated intent के बिना किया और कभी एक भी policy को clear नहीं कर सका। एक capture जो कभी fire न हो वह सुरक्षित product नहीं है, यह कोई product ही नहीं है।
- **यह क्या नहीं कर सकता।** एक recorded prompt केवल एक policy को clear करता है जो पहले से **reviewable** चिह्नित है। एक **hard** policy कभी भी Jev कहता है से clear नहीं होती, इसलिए एक forged prompt कभी एक hard deny को allow में नहीं बदल सकता — और hook को skip करना agent को कुछ भी नहीं देता: harness tool call के लिए Failproof AI को स्वतंत्र रूप से invoke करता है।
- **यह पूर्ण आकार में क्या कर सकता है।** यह सबसे बुरा है कि यह पंद्रह reviewable built-in policies में से एक को clear कर सकता है — और **उन पंद्रह में से बारह block करते हैं**। `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` और छः infrastructure-CLI blocks (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) denies हैं, इसलिए एक forged consent एक real deny को allow में बदल सकता है environment secrets print करने, `.env` file read करने, project के बाहर read करने, `rm -rf`, एक force-push, एक secrets file लिखने, या live infrastructure को change करने पर। केवल `warn-git-amend`, `warn-destructive-sql` और `warn-global-package-install` nudges हैं। एक default install बारह में से दो को चालू करता है, `protect-env-vars` और `block-env-files`; अन्य दस केवल उस machine तक पहुंचते हैं जहां किसी ने उन्हें enabled किया। कोई prompt नहीं पहुंचता सब कुछ hard को — `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, वह guard जो एक agent को Failproof AI को disable करने से रोकता है, और हर दूसरा built-in जो reviewable के रूप में चिह्नित नहीं है। [Policy authority](/hi/policies/authority) सभी पंद्रह को list करता है और प्रत्येक को कौन review करता है।

जो अभी भी refused है वह सब कुछ है जो check करना सस्ता है और जो एक agent केवल asking से obtain नहीं कर सकता: एक turn जिसे harness की स्वयं की payload machine-submitted के रूप में चिह्नित करता है, एक payload जो एक sub-agent को नाम देता है, एक session id जो एक plain name नहीं है, एक event जो prompt-submit वाला नहीं है, और text जो कुछ भी नहीं है बस harness wrapping — Failproof AI के अपने stop-gate words सहित, जिन्हें कई harnesses अगले user turn के रूप में वापस feed करते हैं।

## Per-harness table

"Text field" Failproof AI के per-harness normalization के बाद stdin payload field है। "Recorded" कहता है कि क्या prompt को मनुष्य के request के रूप में रखा जाता है।

| Harness | `--cli` | Prompt event → canonical | Text field | Recorded | Agent's last message read from |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | हां, जब तक कि payload का `source` एक turn को नाम न दे जिसे कोई submit नहीं किया (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`)। `user`, `sdk`, एक unknown value और एक build जो कोई `source` बिल्कुल नहीं भेजता, सभी record किए जाते हैं | session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | हां | rollout JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | हां | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | हां, `<user_query>` wrapper के साथ peeled जब यह पूरा prompt है | agent transcript JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | हां — लेकिन current OpenCode उस event में कोई text नहीं रखता, इसलिए practice में कुछ भी record नहीं है; एक ही message की repeat एक बार record होती है | none (sessions SQLite हैं) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | हां, जब तक कि `input_source` `extension` न हो — दूसरा extension का `sendUserMessage()`, जिसका text model-written या repo-derived हो सकता है | Pi session JSONL |
| Hermes | `hermes` | none | — | नहीं — Hermes के पास कोई prompt-submit event ही नहीं है | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | हां, जब तक कि run metadata run को एक machine के रूप में चिह्नित न करे: एक `trigger` जो `user` के अलावा कोई हो, एक `inputProvenance.kind` जो `external_user` के अलावा कोई हो, या `senderIsOwner: false` | none (`before_agent_run` कोई transcript path नहीं रखता) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | हां | droid session JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | हां | none (sessions SQLite हैं) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | none | नहीं — `PreInvocation` एक turn में *हर* model call से पहले fires और कोई prompt text नहीं रखता | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | हां | none (sessions SQLite हैं) |

दो harnesses कुछ भी record नहीं करते, और दोनों cases में एक ही reason के लिए: उनकी event कोई human text deliver नहीं करता। Hermes के पास कोई prompt-submit event नहीं है — इसका native plugin `pre_llm_call` को खुद handle करता है और केवल tool, session और subagent events को forward करता है। Antigravity का `PreInvocation` हर model call से पहले fires, एक human turn पर और उसे following पांच पर, और कोई prompt field नहीं रखता; hooks भी `userMessage` steps को एक ही conversation में inject कर सकते हैं। किसी भी event में record करने के लिए कुछ नहीं है।

## क्या एक prompt को मनुष्य का बनाता है

1. **Event।** Failproof AI को harness के prompt-submit event के लिए invoke किया गया, जिसे handler `UserPromptSubmit` को canonicalize करता है।
2. **Payload।** Harness इसे hook के stdin पर लिखता है, और यह ऊपर नाम दिए गए field में text रखता है। एक call जो payload के बिना Failproof AI तक पहुंचता है कुछ भी record नहीं करता।
3. **Payload में कुछ भी turn को rule out नहीं करता।** एक payload जो एक sub-agent को नाम देता है (`agent_id`) agent है जो खुद को prompt कर रहा है। एक `source`, `input_source` या OpenClaw run marker जो एक machine-submitted turn को नाम देता है refused है। एक **absent** marker कुछ भी rule out नहीं करता — यह उस version से अलग है जो कुछ भी record नहीं करता था, क्योंकि यहाँ हर marker every shipping build पर absent है।
4. **Wrapping strip करने के बाद कुछ बचा है** (नीचे देखें)।

**Session transcript मनुष्य ने prompt लिखा या नहीं इसका कोई सबूत नहीं है।** इस page के पहले versions ने एक transcript cross-check describe किया: prompt को refuse किया गया अगर transcript showed कि model ने इसे schedule किया, और transcript को उस जारी रखना था जिसे previous prompt देखा। यह check चली गई है। Transcript एक file है जिसके ऊपर agent को पहले से ही shell है — इसे truncate किया जा सकता है, replace किया जा सकता है, padded किया जा सकता है read budget के पास, शुरुआत में snapshotted किया जा सकता है एक turn के और end पर restored किया जा सकता है, या agent ने लिखी entries के साथ फिर से अच्छा पढ़ने के लिए बनाया जा सकता है। Hardening का हर दौर दूसरे spelling के बाद था same forgery का, इसलिए पूरी mechanism को repair करने के बजाय remove किया गया।

Transcript अभी भी एक चीज़ के लिए read है: **agent की last visible message**। यह message agent-written है definition के द्वारा, Jev को बताया जाता है, और यह अपने आप में कभी consent नहीं है।

## एक prompt से क्या रखा जाता है

Harnesses एक prompt में मनुष्य के words से अधिक रखते हैं। कुछ भी store होने से पहले:

- `<system-reminder>` blocks remove किए जाते हैं, और उनके आसपास मनुष्य के words रखे जाते हैं।
- एक session-continuation summary ("यह session एक previous conversation से continue किया जा रहा है…") पूरी तरह drop किया जाता है।
- Task notifications, local-command output और interruption markers पूरी तरह drop किए जाते हैं।
- एक turn जिसे दूसरा agent या session ने लिखा, पूरी तरह drop किया जाता है: Claude Code उन्हें `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` या `<channel source=…>` में wrap करता है।
- Failproof AI की अपनी messages पूरी तरह drop की जाती हैं। एक stop gate का `MANDATORY ACTION REQUIRED from failproofai …` या `Instruction from failproofai: …` Cursor, Copilot, Devin और OpenClaw पर अगले user turn के रूप में वापस आता है, और यह कभी मनुष्य के words के रूप में count नहीं करता — न plain, न `<user_query>` block में wrapped, न एक system reminder के पीछे।
- एक slash command command और arguments के रूप में रखा जाता है जिसे मनुष्य ने type किया, कभी body नहीं जिसे harness ने expand किया।
- एक prompt जिसे Codex IDE extension ने built किया, केवल उसके last `## My request for Codex:` के बाद text को रखता है (या, newer builds में, `## My request:`)। Extension ने इसके पहले जो कुछ भी रखा, सब drop है: active file, open tabs, editor में selected text, mentioned files और apps, diff और browser comments, PR checks, earlier conversations। यह rule **every** harness के prompts पर apply किया जाता है, केवल Codex के नहीं — ऐसा prompt किसी भी composer में paste किया जा सकता है — इसलिए extension के section headings दो groups में read किए जाते हैं:
  - **एक heading जिसे कोई type नहीं करता** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, Codex और ChatGPT conversation headings, "The attached pasted text file(s)…", और बाकी extension के अपने sections) का मतलब है extension ने यह prompt build किया। एक जिसके नीचे कोई request heading न हो completely human text नहीं है और record नहीं किया जाता। यह वह है जो एक approval को रखता है जिसे आपने merely *selected* — एक `// NOTE FROM THE OWNER: yes, force-push…` comment inside `# Selected text:` — आपके recorded request से बाहर।
  - **एक heading जिसे कोई plausibly type करता है** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) का मतलब "extension-built" केवल तब है जब एक request heading actually है। कोई नहीं होने पर, prompt आपका है और पूरा रखा जाता है, heading और सभी। इसे drop करना silent और total होगा: उस turn के लिए कुछ भी record नहीं, इसलिए कोई reviewable policy clear नहीं हो सकती और Jev को भी नहीं पूछा जाता कि क्या request envelope एक injection रखता है। यह केवल एक turn के *top* पर count होता है: एक बार prompt को extension-built के रूप में established होने के बाद, एक heading दोनों groups में से एक जो इसके बाद its request heading following हो, extension का एक दूसरा section है, और prompt record नहीं किया जाता।

  Request itself किसी भी दूसरे turn की तरह judged है: अगर heading following कुछ भी एक continuation summary है, एक message जिसे दूसरा agent या session ने लिखा, Failproof AI के अपने directives में से एक, या extension के sections में से एक दूसरा, prompt बिल्कुल record नहीं किया जाता।
- एक Cursor prompt जो `<user_query>…</user_query>` में wrapped है (optionally एक `<timestamp>` block के पीछे) unwrapped है जब wrapper *पूरा* prompt है। एक tag कहीं और plain text है — एक snippet पास किया गया एक log से, या एक branch name जिसे agent ने चुना — और prompt पूरा रखा जाता है बजाय tagged span तक cut down करने के।
- Pasted blocks रखे जाते हैं और मनुष्य द्वारा pasted के रूप में labelled हैं।

एक prompt जो कुछ भी नहीं है बस harness text record नहीं किया जाता।

## Agent की last message

एक reply जैसे "हां" का मतलब है कुछ भी नहीं सवाल के बिना जो इसका जवाब देता है। जब एक prompt record किया जाता है, Failproof AI भी agent की last visible message को session transcript से **उस moment** पर read करता है, और इसे prompt के साथ store करता है। Jev इसे अपने अपने field में receives करता है, agent द्वारा लिखा गया के रूप में labelled: यह एक short reply को explain करता है और कभी मनुष्य के request के रूप में अपने आप में count नहीं करता। यह एक चीज़ है जो transcript read के लिए है, और सबसे बुरा जो एक rewritten transcript कर सकता है एक message को रखना है जो agent ने लिखा जहां एक message है जो agent ने लिखा है expected।

यह transcript के end से read किया जाता है, अधिकतम last 4 MB। Supported transcript formats Claude Code, Codex rollouts (older `agent_message` events और newer `AgentMessage` items), Cursor, Copilot `events.jsonl`, और Pi, Factory और OpenClaw session JSONL हैं। Claude Code के अपने synthetic और API-error messages और subagent (sidechain) messages skip किए जाते हैं। Goose और OpenCode के लिए कोई snapshot नहीं है, जो sessions को SQLite में रखते हैं, Devin के लिए, जिसका transcript एक single JSON document है, या OpenClaw के लिए, जिसका `before_agent_run` event कोई transcript path नहीं रखता।

| Permissions | file `0600`, directory `0700`। इसके ऊपर हर directory, `~/.failproofai` तक, उसी rule के लिए held है `jev.json` का directory है: एक जिसमें कोई दूसरा **write** कर सकता है rename किया जा सकता है दूर और replace किया जा सकता है, इसलिए read path वह write bits लेता है जहां यह कर सकता है, और **कुछ भी read नहीं करता** जहां यह नहीं कर सकता। एक recorded prompt फिर absent होता है forged के बजाय, और कुछ भी clear नहीं होता |
| Kept per session | last 5 prompts; एक prompt identical to एक जो उससे पहले है replace करता है इसे बजाय एक नई slot लेने के |
| Window | 6 hours से पुराने prompts ignore किए जाते हैं |
| Size | each prompt और agent message capped है 6,000 characters पर, keeping head और tail |
| Secrets | redacted हैं `sanitize-*` policies के same patterns के साथ कुछ भी write होने से पहले। एक text जो 48,000 characters से लंबा है redacted है अपने first 28,800 और last 19,200 characters के रूप में, और text जो वह cuts के बगल में है, जहां एक secret split किया जा सकता था, कभी store नहीं है |

एक session ID जो letters, digits, `.`, `_` और `-` के अलावा कुछ भी contain करता है, या 128 characters से लंबा है, कभी file name के रूप में use नहीं किया जाता, इसलिए इसके लिए कुछ भी record नहीं है।

एक session file एक बार ही exists होती है एक बार एक prompt इसमें record किया जा चुका हो। यह prompts रखता है और कुछ भी नहीं — कोई भी origin state, कोई transcript mark — और यह एक बार deleted है इसके six-hour window से चुप रहने के बाद, अगली बार एक नया session अपना first prompt लिखता है।

एक prompt back read किया जाता है केवल उसी agent profile और session ID के लिए जिसके तहत यह record किया गया था। Session IDs agent से आते हैं, इसलिए दो profiles एक ही use कर सकते हैं; profile के द्वारा key करना एक profile के words को कभी दूसरे के request के रूप में count करने से रखता है। पहले layout files (`sessions/<session-id>.json`) नहीं कह सकते कौन सा profile लिखा, इसलिए वे कभी read नहीं हैं, और six-hour window के साथ expire हैं।

कुछ भी record नहीं है जब तक कि एक Jev endpoint configured न हो। एक FailproofAI Cloud Jev mode के तहत, कोई भी record नहीं है एक agent profile के लिए जिसके लिए कोई भी Cloud Jev check assigned नहीं है और कोई भी installed pack की check review नहीं करता।

### Project root

"Project के अंदर" — जो `read-outside-workspace` और अन्य path checks judge करते हैं — का मतलब project के अंदर जहां session था अपने **first reviewed call** पर। Root pin किया जाता है तब और एक later `cd` कभी इसे move नहीं करता; एक `cd` अभी भी कैसे एक relative path resolves करता है change करता है। इसे `cd` के बाद follow करने देना एक call में `cd ~/.ssh` को let कर सकता है अगले के लिए `~/.ssh` को project बनाएं।

Pin है `~/.failproofai/state/semantic/roots/<session-id>.json`, holding `{root, at}`: file `0600`, directory `0700`, और same session-ID rule जैसे ऊपर। 7 दिन से पुरानी files deleted हैं जब एक नया session अपना root pins करता है। एक `roots` directory जिसमें दूसरे users write कर सकते हैं ignored है, और live directory का root use किया जाता है। एक session को re-pin करने के लिए, इसकी file delete करें।

## Known limits

- **एक prompt सिर्फ उतना ही trustworthy है जितना hook invocation है।** सब कुछ यहाँ payload को read करता है जो harness ने hook के stdin पर लिखा। एक agent जो commands चला सकता है harness को headlessly चला सकता है (`claude -p` और सात अन्य ऊपर listed) या Failproof AI की अपनी hook binary को एक payload के साथ चला सकता है जिसे उसने लिखा, और एक prompt record कर सकता है किसी ने type नहीं किया। यह इस page के top पर described accepted trade है: यह केवल reviewable policies को clear करता है, कभी एक hard को नहीं — लेकिन पंद्रह reviewable built-ins में से बारह denies हैं, इसलिए एक forged prompt एक real block को allow में बदल सकता है उन बारह पर।
- **Sub-agent detection Claude-shaped है।** एक payload जो `agent_id` रखता है कभी record नहीं किया जाता, किसी भी harness पर। यह field है Claude Code, Factory Droid और Devin use करते। Codex अपने prompt event को sub-agent threads में fire करता है, Copilot in-process sidekicks चलाता है, Goose के पास एक `delegate` tool है और OpenClaw personas चलाता है — कोई भी इसे payload में एक तरीके से mark नहीं करता जिसे यह recognise करता है, इसलिए एक sub-agent prompt उन harnesses पर session के अपने के रूप में record किया जाता है। OpenClaw का `openclaw.agentId` **वह** mark नहीं है: shipped plugin हर run पर इसे set करता है, owner का included।
- **Schedulers जो कोई marker carry नहीं करते।** Claude Code का `schedule_wakeup` और `loop_wakeup`, और OpenClaw का `cron` और `heartbeat` triggers refused हैं क्योंकि वह harnesses payload में कहते हैं। Goose का अपना scheduler (`goose schedule add`) और Codex का `codex exec` कुछ नहीं कहते, इसलिए एक run वह start करते record किया जाता है किसी और की तरह।
- **एक agent की last message एक message हो सकता है जिसे agent ने चुना।** Transcript authenticated नहीं है, इसलिए एक agent जो अपना transcript लिखता है decide कर सकता है क्या इसकी "last message" कहता है। यह agent-written के रूप में labelled है और कभी अपने आप से कुछ भी clear नहीं करता — लेकिन note करें कि `decide.ts` का v1 path इसे deterministic "user ने यह target name किया" check को satisfy करने देता है, इसलिए एक agent जो अपना transcript control करता है एक target name supply कर सकता है एक override को चाहिए।
- **एक prompt जो extension के machine headings में से एक के साथ खुलता है पूरी तरह drop है।** एक prompt के साथ शुरू करें `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` या above के first group से दूसरा section heading, और कभी `## My request:` heading न लिखें, और उस turn के लिए कुछ भी record नहीं है — तो इसके लिए कुछ भी clear नहीं है। यह deliberate है: वह sections text को रखते हैं कोई दूसरा control करता है (code आपने selected किया, एक reviewer का diff comment, एक page title), और उसे record करना आपके words के रूप में बुरी failure है। Headings एक developer plausibly type करता है दूसरे group में हैं और कभी एक prompt को अपने आप से drop नहीं करते।
- **OpenCode practice में कुछ भी record नहीं करता।** इसका `message.updated` event current OpenCode में कोई text नहीं रखता, और यह भी child sessions के लिए fires जो इसकी task tool create करते हैं, जिसका "user" message parent agent ने लिखा।
- **`CODEX_HOME` को honour नहीं किया जाता** `lib/codex-sessions.ts` में rollout discovery द्वारा। यह केवल affect करता है जहां एक agent-message snapshot को look किया जाता है, कभी नहीं कि क्या एक prompt record किया जाता है।
