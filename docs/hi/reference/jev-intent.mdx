जब आप [Jev policy review](/hi/policies/jev) को configure करते हैं, तो evaluator प्रत्येक gated tool call को **मानव ने क्या माँगा** इसके विरुद्ध judge करता है, न कि जो कुछ भी text harness ने agent के सामने रखा है उसके विरुद्ध। एक जवाब जैसे "yes, force-push it" एक **reviewable** policy को clear कर सकता है — जो evaluator का पूरा बिंदु है, क्योंकि एक regex जो request को नहीं पढ़ सकता है वह real work के तीसरे हिस्से को block करता है।

वह text एक जगह से आता है: **prompt जो harness स्वयं hook को अपनी prompt-submit event पर देता है**। Failproof AI इसके उस हिस्से को record करता है जो मानव ने type किया — harness wrapping stripped, secrets redacted, capped — एक `0600` file में अपनी खुद की state directory के अंतर्गत। disk पर कुछ भी consult नहीं किया जाता है: session transcript एक ऐसी file है जिसे agent एक command में rewrite कर सकता है, इसलिए कभी नहीं पूछा जाता है कि किसने prompt write किया।

## यह जोखिम जो स्पष्ट रूप से स्वीकार करता है

एक agent जो पहले से ही commands चला सकता है वह harness को prompt submit करने के लिए कह सकता है। `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` और `pi -p` सभी एक ही prompt-submit event को fire करते हैं, समान payload के साथ, जैसे कि कोई व्यक्ति type कर रहा है, एक child session में जिसे agent control करता है। यह Failproof AI's own hook binary को भी चला सकता है और इसे एक payload के साथ feed कर सकता है जो इसने write किया। Failproof AI के अंदर कुछ भी दोनों को real thing से अलग नहीं कर सकता — दोनों ही समान program हैं जो एक ही stdin को read करते हैं।

**तो एक agent जिसके पास shell है वह अपनी खुद की consent forge कर सकता है।** यह एक deliberate trade है, जिसे 2026-09-23 पर लिया गया था, और यहाँ इसके दोनों halves हैं:

- **यह क्या खरीदता है।** विकल्प built और measured किया गया था: एक ऐसा field require करें जिसमें harness एक मानव को prompt के author के रूप में name करे, और अन्यथा कुछ भी record न करें। कोई भी shipping harness ऐसा field नहीं भेजता है, इसलिए उस version ने **कुछ भी नहीं record किया, every harness पर** — Jev ने प्रत्येक call को कोई stated intent के साथ judge किया और कभी भी एक भी policy को clear नहीं कर सका। एक capture जो कभी fire नहीं होता है वह safer product नहीं है, यह कोई product ही नहीं है।
- **यह क्या नहीं कर सकता।** एक recorded prompt केवल एक ऐसी policy को clear करता है जो पहले से ही **reviewable** marked है। एक **hard** policy कभी भी Jev द्वारा कुछ भी कहे जाने से clear नहीं होता है, इसलिए एक forged prompt कभी भी hard deny को allow में नहीं बदल सकता — और hook को skip करना agent को भी कुछ नहीं मिलता: harness tool call के लिए स्वतंत्र रूप से Failproof AI को invoke करता है।
- **यह क्या कर सकता है, full size पर।** जो सबसे बुरा कर सकता है वह fifteen reviewable built-in policies में से एक को clear करना है — और **उन पंद्रह में से बारह block करते हैं**। `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` और छः infrastructure-CLI blocks (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) denies हैं, इसलिए एक forged consent एक real deny को allow में बदल सकता है environment secrets को print करने पर, `.env` file को read करने पर, project के बाहर read करने पर, `rm -rf` पर, एक force-push पर, secrets file को write करने पर, या live infrastructure को change करने पर। केवल `warn-git-amend`, `warn-destructive-sql` और `warn-global-package-install` nudges हैं। एक default install बारह में से दो को switch करता है, `protect-env-vars` और `block-env-files`; अन्य दस केवल एक machine पर पहुँचते हैं जहाँ किसी ने उन्हें enable किया है। जो कोई भी prompt reach नहीं करता है वह सब कुछ hard है — `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, guard जो एक agent को Failproof AI को disable करने से रोकता है, और हर दूसरा built-in जो reviewable के रूप में marked नहीं है। [Policy authority](/hi/policies/authority) सभी पंद्रह को list करता है और प्रत्येक एक को कौन review करता है।

जो अभी भी refuse किया जाता है वह सब कुछ है जो check करना cheap है और जो agent केवल माँग करके obtain नहीं कर सकता: एक turn जिसे harness's own payload machine-submitted के रूप में marks करता है, एक payload जो sub-agent को name करता है, एक session id जो plain name नहीं है, एक event जो prompt-submit नहीं है, और text जो कुछ भी नहीं है सिवाय harness wrapping के — जिसमें Failproof AI's own stop-gate words भी शामिल हैं, जो कई harnesses अगली user turn के रूप में वापस feed करते हैं।

## Per-harness table

"Text field" stdin payload field है Failproof AI के per-harness normalization के बाद। "Recorded" कहता है कि prompt को मानव के request के रूप में kept किया जाता है या नहीं।

| Harness | `--cli` | Prompt event → canonical | Text field | Recorded | Agent's last message read from |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | हाँ, जब तक payload का `source` एक ऐसे turn को name न करे जिसे कोई submit नहीं किया (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`)। `user`, `sdk`, एक unknown value और एक build जो कोई `source` बिल्कुल नहीं भेजता है सभी recorded हैं | session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | हाँ | rollout JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | हाँ | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | हाँ, `<user_query>` wrapper के साथ peeled जब यह पूरा prompt हो | agent transcript JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | हाँ — लेकिन current OpenCode उस event में कोई text नहीं ले जाता है, इसलिए व्यावहारिक रूप से कुछ भी record नहीं होता है; एक ही message की repeat एक बार record होती है | none (sessions SQLite हैं) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | हाँ, जब तक `input_source` `extension` न हो — किसी दूसरे extension का `sendUserMessage()`, जिसका text model-written या repo-derived हो सकता है | Pi session JSONL |
| Hermes | `hermes` | none | — | नहीं — Hermes के पास बिल्कुल कोई prompt-submit event नहीं है | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | हाँ, जब तक run metadata run को machine's के रूप में mark न करे: एक `trigger` जो `user` नहीं है, एक `inputProvenance.kind` जो `external_user` नहीं है, या `senderIsOwner: false` | none (`before_agent_run` कोई transcript path नहीं ले जाता है) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | हाँ | droid session JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | हाँ | none (sessions SQLite हैं) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | none | नहीं — `PreInvocation` एक turn में हर model call से पहले fires और कोई prompt text नहीं ले जाता है | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | हाँ | none (sessions SQLite हैं) |

दो harnesses कुछ भी record नहीं करते हैं, और दोनों cases में समान कारण के लिए: उनकी event कोई human text नहीं deliver करती है। Hermes के पास कोई prompt-submit event नहीं है — इसका native plugin `pre_llm_call` को स्वयं handle करता है और केवल tool, session और subagent events को forward करता है। Antigravity का `PreInvocation` हर model call से पहले fires, एक human turn पर और उसके बाद के पाँच पर, और कोई prompt field नहीं ले जाता है; hooks `userMessage` steps को भी उसी conversation में inject कर सकते हैं। किसी भी event में record करने के लिए कुछ भी नहीं है।

## क्या एक prompt को मानव का बनाता है

1. **Event।** Failproof AI को harness के prompt-submit event के लिए invoke किया गया था, जिसे handler canonicalize करता है `UserPromptSubmit` के लिए।
2. **Payload।** Harness इसे hook के stdin पर write करता है, और यह उपरोक्त named field में text को carry करता है। एक call जो Failproof AI तक पहुँचता है payload के बिना कुछ भी record नहीं करता है।
3. **Payload में कुछ भी turn को rule out नहीं करता है।** एक payload जो sub-agent को name करता है (`agent_id`) agent को अपने आप को prompt कर रहा है। एक `source`, `input_source` या OpenClaw run marker जो machine-submitted turn को name करता है refuse किया जाता है। एक **absent** marker कुछ भी rule out नहीं करता है — यह उस version से अंतर है जो कुछ भी record नहीं करता था, क्योंकि यहाँ हर marker absent है हर shipping build पर।
4. **Wrapping stripped होने के बाद कुछ left रहता है** (नीचे देखें)।

**Session transcript prompt के author के proof नहीं है।** इस page के पहले के versions ने एक transcript cross-check को describe किया: prompt को refuse किया गया था अगर transcript ने दिखाया कि model ने इसे schedule किया, और transcript को उसी को continue करना था जो previous prompt ने देखा। यह check gone है। एक transcript एक file है जिसे agent के पास पहले से ही shell है — इसे truncate किया जा सकता है, replaced, padded past the read budget, snapshotted turn के start पर और end पर restored, या entries के साथ अच्छा read करने के लिए बनाया जा सकता है जो agent ने write किए। hardening का हर round दूसरे spelling के बाद किया गया था एक ही forgery का, इसलिए पूरी mechanism को repaired करने की जगह remove किया गया।

Transcript अभी भी एक चीज के लिए read किया जाता है: **agent का last visible message**। वह message agent-written है definition के अनुसार, Jev को ऐसा बताया जाता है, और यह अपने आप में कभी भी consent नहीं है।

## क्या एक prompt से kept है

Harnesses मानव के words से ज्यादा कुछ prompt में डालते हैं। कुछ भी store होने से पहले:

- `<system-reminder>` blocks को remove किया जाता है, और उनके चारों ओर मानव के words को keep किया जाता है।
- एक session-continuation summary ("This session is being continued from a previous conversation…") को पूरी तरह drop किया जाता है।
- Task notifications, local-command output और interruption markers को पूरी तरह drop किया जाता है।
- एक turn जिसे किसी दूसरे agent या session ने write किया को पूरी तरह drop किया जाता है: Claude Code उन्हें `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` या `<channel source=…>` में wrap करता है।
- Failproof AI के own messages को पूरी तरह drop किया जाता है। एक stop gate का `MANDATORY ACTION REQUIRED from failproofai …` या एक `Instruction from failproofai: …` अगली user turn के रूप में Cursor, Copilot, Devin और OpenClaw पर वापस आता है, और यह कभी भी मानव के words के रूप में count नहीं करता है — न plain, न `<user_query>` block में wrapped, न system reminder के पीछे।
- एक slash command को command और arguments के रूप में keep किया जाता है जो मानव ने type किए, कभी भी body नहीं जिसे harness ने expand किया।
- एक prompt जिसे Codex IDE extension ने build किया केवल अपने last `## My request for Codex:` के बाद का text रखता है (या, newer builds में, `## My request:`) heading। सब कुछ जो extension ने पहले रखा उसे drop किया जाता है: active file, open tabs, text selected in editor, mentioned files और apps, diff और browser comments, PR checks, earlier conversations। यह rule **हर** harness के prompts पर apply किया जाता है, केवल Codex के नहीं — ऐसा prompt किसी भी composer में paste किया जा सकता है — इसलिए extension के section headings को दो groups में read किया जाता है:
  - **एक heading जिसे कोई भी type नहीं करता** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, Codex और ChatGPT conversation headings, "The attached pasted text file(s)…", और बाकी extension के own sections) मतलब extension ने यह prompt build किया। एक जिसके पास इसके under कोई request heading नहीं है उसमें कोई human text नहीं है और record नहीं किया जाता है। यह एक ऐसी approval को रखता है जो आप केवल *selected* text में — एक `// NOTE FROM THE OWNER: yes, force-push…` comment `# Selected text:` के अंदर — forge किए, आपके recorded request से बाहर।
  - **एक heading जिसे कोई plausibly type करता है** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) मतलब "extension-built" केवल तब जब एक request heading वास्तव में वहाँ हो। कोई नहीं होने पर, prompt आपका है और पूरा keep किया जाता है, heading और सब कुछ। इसे drop करना silent और total होता: कुछ भी record नहीं उस turn के लिए, इसलिए कोई reviewable policy clear नहीं हो सकती और Jev को यह भी नहीं पूछा जाएगा कि क्या request envelope कोई injection ले जाता है। यह केवल एक turn के *top* पर count करता है: एक बार prompt को extension-built establish कर दिया जाता है, एक heading दोनों groups में से जो अपने request heading के बाद आता है उसके अंदर extension के sections में से एक और होता है, और prompt record नहीं किया जाता है।

  Request itself को किसी दूसरे turn की तरह judge किया जाता है: अगर heading के बाद जो आता है वह एक continuation summary है, एक message जिसे किसी दूसरे agent या session ने write किया, Failproof AI के own directives में से एक, या extension के sections में से एक दूसरा, prompt बिल्कुल record नहीं किया जाता है।
- एक Cursor prompt जो `<user_query>…</user_query>` में wrapped है (optionally एक `<timestamp>` block के पीछे) unwrapped किया जाता है जब wrapper पूरा prompt हो। एक tag कहीं और एक ordinary text है — एक snippet जो किसी log से paste किया गया, या एक branch name जिसे agent ने choose किया — और prompt पूरा keep किया जाता है rather than tagged span तक cut down।
- Pasted blocks को keep किया जाता है और मानव द्वारा pasted के रूप में labelled किया जाता है।

एक prompt जो कुछ भी नहीं है सिवाय harness text के record नहीं किया जाता है।

## Agent का last message

एक जवाब जैसे "yes" उस सवाल के बिना कुछ भी मतलब नहीं रखता है जिसका यह जवाब है। जब एक prompt record किया जाता है, Failproof AI **उस क्षण** session transcript से agent के last visible message को भी read करता है, और इसे prompt के साथ store करता है। Jev इसे अपने own field में receive करता है, agent द्वारा written के रूप में labelled: यह एक short reply को explain करता है और कभी भी अपने आप में मानव के request के रूप में count नहीं करता है। यह एक चीज है जिसके लिए transcript read किया जाता है, और एक rewritten transcript जो कर सकता है वह सबसे बुरा एक message को रख सकता है जो agent ने लिखा जहाँ एक message है जो agent ने लिखा expected है।

यह transcript के end से read किया जाता है, सबसे अधिक last 4 MB। Supported transcript formats Claude Code, Codex rollouts (older `agent_message` events और newer `AgentMessage` items), Cursor, Copilot `events.jsonl`, और Pi, Factory और OpenClaw session JSONL हैं। Claude Code के own synthetic और API-error messages और subagent (sidechain) messages को skip किया जाता है। Goose और OpenCode के लिए कोई snapshot नहीं है, जो sessions को SQLite में keep करते हैं, Devin के लिए, जिसका transcript एक single JSON document है, या OpenClaw के लिए, जिसका `before_agent_run` event कोई transcript path नहीं ले जाता है।

| Permissions | file `0600`, directory `0700`। इसके ऊपर हर directory, `~/.failproofai` तक, एक ही rule के लिए held है `jev.json` का directory है: एक जिसे कोई और भी **write** कर सकता है को rename किया जा सकता है और replace किया जा सकता है, इसलिए read path जहाँ यह कर सकता है वहाँ वह write bits को off लेता है, और जहाँ नहीं कर सकता वहाँ कुछ भी नहीं read करता है। एक recorded prompt तब absent है rather than forged, और कुछ भी clear नहीं होता है |
| Kept per session | last 5 prompts; एक prompt जो उससे पहले वाले के identical है इसकी जगह लेता है rather than एक नई slot लेता है |
| Window | 6 घंटे से पुराने prompts को ignore किया जाता है |
| Size | प्रत्येक prompt और agent message 6,000 characters तक capped होता है, head और tail को रखते हुए |
| Secrets | `sanitize-*` policies के समान patterns के साथ redacted किया जाता है कुछ भी write होने से पहले। एक 48,000 characters से लंबा text अपने first 28,800 और last 19,200 characters के रूप में redacted होता है, और उन cuts के आगे का text, जहाँ एक secret split किया जा सकता था, कभी भी store नहीं किया जाता है |

एक session ID जिसमें letters, digits, `.`, `_` और `-` के अलावा कुछ है, या 128 characters से लंबा है, कभी भी file name के रूप में use नहीं किया जाता है, इसलिए इसके लिए कुछ भी record नहीं होता है।

एक session file केवल एक बार exist होती है जब इसमें एक prompt record किया गया हो। यह prompts hold करती है और कुछ भी नहीं — कोई origin state, कोई transcript mark नहीं — और यह delete हो जाती है जब यह six-hour window से लंबे समय तक silent रहा है, अगली बार जब एक नया session अपना पहला prompt लिखता है।

एक prompt केवल उसी agent profile और session ID के लिए read किया जाता है जिसके अंतर्गत यह record किया गया था। Session IDs agent से आती हैं, इसलिए दो profiles एक ही को use कर सकते हैं; profile के साथ keying करना एक profile के words को कभी भी दूसरे के request के रूप में count होने से रखता है। इस layout से पहली files (`sessions/<session-id>.json`) यह नहीं कह सकते कि किस profile ने उन्हें लिखा, इसलिए वे कभी भी read नहीं किए जाते हैं, और six-hour window के साथ expire होते हैं।

जब तक Jev endpoint configure नहीं किया जाता तब तक कुछ भी record नहीं होता है। एक FailproofAI Cloud Jev mode के अंतर्गत, एक agent profile के लिए कुछ भी record नहीं होता है जिसे कोई Cloud Jev check assign नहीं किया गया है और कोई installed pack का check review नहीं करता है।

### Project root

"Project के अंदर" — जो `read-outside-workspace` और अन्य path checks judge करते हैं — मतलब project के अंदर जो session था अपने **first reviewed call** पर। Root तब pinned होता है और एक later `cd` इसे कभी भी move नहीं करता; एक `cd` अभी भी कैसे एक relative path resolve होता है को change करता है। इसे `cd` के बाद follow होने देना एक call में `cd ~/.ssh` को अगले के लिए `~/.ssh` को project बनाने देता।

Pin `~/.failproofai/state/semantic/roots/<session-id>.json` है, holding `{root, at}`: file `0600`, directory `0700`, और ऊपर की तरह ही session-ID rule। 7 दिन से पुरानी files delete हो जाती हैं जब एक नया session अपने root को pin करता है। एक `roots` directory जिसे अन्य users write कर सकते हैं को ignore किया जाता है, और live directory का root use किया जाता है। एक session को re-pin करने के लिए, इसकी file को delete करें।

## Known limits

- **एक prompt hook invocation जितना ही trustworthy है।** सब कुछ यहाँ payload को read करता है जिसे harness ने hook के stdin पर लिखा है। एक agent जो commands चला सकता है headlessly harness को चला सकता है (`claude -p` और ऊपर listed सात दूसरे) या Failproof AI के hook binary को स्वयं एक payload के साथ run कर सकता है जो इसने लिखा है, और एक prompt record कर सकता है जिसे किसी ने type नहीं किया। यह accepted trade है जो इस page के top पर describe किया गया है: यह केवल reviewable policies को clear करता है, कभी भी hard नहीं — लेकिन fifteen reviewable built-ins में से बारह denies हैं, इसलिए एक forged prompt एक real block को allow में बदल सकता है उन बारह पर।
- **Sub-agent detection Claude-shaped है।** एक payload जो `agent_id` को carry करता है कभी भी record नहीं किया जाता है, किसी भी harness पर। वह field है जो Claude Code, Factory Droid और Devin use करते। Codex अपना prompt event sub-agent threads के अंदर fire करता है, Copilot in-process sidekicks run करता है, Goose के पास एक `delegate` tool है और OpenClaw personas को run करता है — जिनमें से कोई भी payload को एक तरीके से mark नहीं करता है जो यह recognize करता है, इसलिए उन harnesses पर एक sub-agent prompt session के own के रूप में record किया जाता है। OpenClaw का `openclaw.agentId` **वह** mark नहीं है: shipped plugin हर run पर इसे set करता है, owner's included।
- **Schedulers जो कोई marker नहीं ले जाते।** Claude Code का `schedule_wakeup` और `loop_wakeup`, और OpenClaw का `cron` और `heartbeat` triggers, refuse किए जाते हैं क्योंकि वह harnesses payload में कहते हैं। Goose का own scheduler (`goose schedule add`) और Codex का `codex exec` कुछ भी नहीं कहते हैं, इसलिए एक run जो वह start करते हैं किसी भी दूसरे के जैसे record किया जाता है।
- **एक agent का last message एक message हो सकता है जो agent ने choose किया।** Transcript authenticated नहीं है, इसलिए एक agent जो अपना transcript write करता है अपना "last message" क्या कहता है यह decide कर सकता है। यह agent-written के रूप में labelled है और अपने आप में कभी भी कुछ clear नहीं करता — लेकिन note करें कि `decide.ts` का v1 path इसे deterministic "did the user name this target" check को satisfy करने देता है, इसलिए एक agent जो अपना transcript control करता है एक target name supply कर सकता है जिसे एक override needs करता है।
- **एक prompt जो extension के machine headings में से एक के साथ open होता है पूरी तरह drop किया जाता है।** एक prompt को `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` या ऊपर के पहले group से किसी दूसरे section heading के साथ start करें, और कभी भी एक `## My request:` heading न लिखें, और कुछ भी उस turn के लिए record नहीं किया जाता है — तो कुछ भी इसके लिए clear नहीं होता है। यह deliberate है: वह sections text carry करते हैं जिसे किसी दूसरे को control करता है (code जिसे आपने select किया, एक reviewer का diff comment, एक page title), और उसे record करना आपके words के रूप में worse failure है। Headings जिसे developer plausibly type करते हैं दूसरे group में हैं और कभी भी अपने आप पर एक prompt को drop नहीं करते।
- **OpenCode व्यावहारिक रूप से कुछ भी record नहीं करता है।** इसका `message.updated` event current OpenCode में कोई text नहीं ले जाता है, और यह भी अपने task tool जो child sessions create करते हैं के लिए fires, जिसका "user" message parent agent ने लिखा।
- **`CODEX_HOME` को `lib/codex-sessions.ts` में rollout discovery के द्वारा honoured नहीं किया जाता।** यह केवल यह प्रभावित करता है कि एक agent-message snapshot कहाँ look किया जाता है, कभी भी नहीं कि क्या एक prompt record किया जाता है।
