जब आप [Jev policy review](/hi/policies/jev) को configure करते हैं, तो evaluator प्रत्येक gated tool call को **जो मानव ने माँगा** उसके विरुद्ध judge करता है, न कि harness ने agent के सामने जो कोई भी text रखा है उसके विरुद्ध। "yes, force-push it" जैसा reply एक **reviewable** policy को clear कर सकता है — जो evaluator का पूरा उद्देश्य है, क्योंकि एक regex जो request को नहीं पढ़ सकता वह real work के एक-तिहाई को block करता है।

यह text एक ही जगह से आता है: **prompt जो harness खुद hook को अपनी prompt-submit event पर देता है**। Failproof AI इसका वह हिस्सा record करता है जो मानव ने type किया — harness wrapping हटाया गया, secrets redacted, capped — इसे अपनी state directory के तहत एक `0600` file में। Disk पर कुछ भी consult नहीं किया जाता: session transcript एक ऐसी file है जो agent एक command में rewrite कर सकता है, इसलिए इससे कभी नहीं पूछा जाता कि किसने prompt लिखा।

## यह जोखिम जो यह accept करता है, स्पष्ट रूप से

एक agent जो पहले से ही commands चला सकता है, एक harness को prompt submit करा सकता है। `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` और `pi -p` सभी एक ही prompt-submit event fire करते हैं, same payload के साथ, एक person type करने के समान, उस agent द्वारा नियंत्रित एक child session में। यह Failproof AI के अपने hook binary को भी run कर सकता है और इसे एक payload feed कर सकता है जो उसने लिखा। Failproof AI के अंदर कुछ भी दोनों को real चीज़ से अलग नहीं कर सकता — दोनों एक ही program हैं जो same stdin को read कर रहे हैं।

**तो एक agent जिसके पास shell है, अपनी खुद की consent forge कर सकता है।** यह एक deliberate trade है, 2026-09-23 पर लिया गया, और यहाँ दोनों halves हैं:

- **यह क्या खरीदता है।** विकल्प built और measured था: एक field की requirement करना जिसमें harness एक मानव को prompt के author के रूप में नाम दे, और अन्यथा कुछ भी record न करें। कोई भी shipping harness ऐसा field नहीं भेजता, तो वह version **कुछ भी नहीं record करता था, हर harness पर** — Jev हर call को stated intent के बिना judge करता था और एक भी policy को कभी clear नहीं कर सकता था। एक capture जो कभी fire नहीं होता, वह ज्यादा safer product नहीं है, यह कोई product ही नहीं है।
- **यह क्या नहीं कर सकता।** एक recorded prompt केवल पहले से **reviewable** चिह्नित एक policy को clear कर सकता है। एक **hard** policy कभी भी Jev कहने से clear नहीं होता, तो एक forged prompt कभी भी एक hard deny को allow में नहीं बदल सकता — और hook को skip करने से agent को कुछ भी नहीं मिलता: harness tool call के लिए independent रूप से Failproof AI को invoke करता है।
- **यह क्या कर सकता है, पूरे size पर।** सबसे बुरा यह है कि यह पंद्रह reviewable built-in policies में से एक को clear कर सकता है — और **उनमें से बारह block करते हैं**। `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` और छह infrastructure-CLI blocks (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) denies हैं, तो एक forged consent एक real deny को environment secrets printing, `.env` file reading, project के बाहर reading, `rm -rf`, एक force-push, secrets file writing, या live infrastructure को change करने पर allow में बदल सकता है। केवल `warn-git-amend`, `warn-destructive-sql` और `warn-global-package-install` nudges हैं। एक default install दो में से बारह को switch करता है, `protect-env-vars` और `block-env-files`; बाकी दस केवल एक machine पर पहुंचते हैं जहां किसी ने उन्हें enable किया। जो कोई भी prompt reach नहीं करता वह सब कुछ hard है — `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, वह guard जो एक agent को Failproof AI को disable करने से रोकता है, और हर दूसरा built-in जो reviewable चिह्नित नहीं है। [Policy authority](/hi/policies/authority) सभी पंद्रह को list करता है और प्रत्येक को क्या review करता है।

जो अभी भी refused है वह सब कुछ है जो check करने में cheap है और जो एक agent सिर्फ माँग कर obtain नहीं कर सकता: एक turn जो harness के अपने payload को machine-submitted चिह्नित करता है, एक payload जो एक sub-agent को नाम देता है, एक session id जो एक plain name नहीं है, एक event जो prompt-submit एक नहीं है, और text जो सिर्फ harness wrapping है — Failproof AI के अपने stop-gate words सहित, जो कई harnesses अगले user turn के रूप में feed करते हैं।

## Per-harness table

"Text field" stdin payload field है Failproof AI के per-harness normalization के बाद। "Recorded" कहता है कि क्या prompt को मानव के request के रूप में रखा जाता है।

| Harness | `--cli` | Prompt event → canonical | Text field | Recorded | Agent's last message read from |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | हाँ, जब तक कि payload का `source` एक turn को नाम न दे जो किसी ने submit नहीं किया (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`)। `user`, `sdk`, एक unknown value और एक build जो कोई `source` भेजती ही नहीं, सब record होते हैं | session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | हाँ | rollout JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | हाँ | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | हाँ, `<user_query>` wrapper को peeled करने के साथ जब यह पूरा prompt है | agent transcript JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | हाँ — लेकिन current OpenCode उस event में कोई text नहीं ले जाता, इसलिए व्यावहारिक रूप से कुछ भी record नहीं होता; एक ही message की repeat एक बार record होती है | कोई नहीं (sessions SQLite हैं) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | हाँ, जब तक कि `input_source` `extension` न हो — दूसरे extension का `sendUserMessage()`, जिसका text model-written या repo-derived हो सकता है | Pi session JSONL |
| Hermes | `hermes` | कोई नहीं | — | नहीं — Hermes के पास बिल्कुल कोई prompt-submit event नहीं है | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | हाँ, जब तक कि run metadata run को machine के रूप में चिह्नित न करे: एक `trigger` जो `user` के अलावा कुछ और हो, एक `inputProvenance.kind` जो `external_user` के अलावा कुछ और हो, या `senderIsOwner: false` | कोई नहीं (`before_agent_run` कोई transcript path नहीं ले जाता) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | हाँ | droid session JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | हाँ | कोई नहीं (sessions SQLite हैं) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | कोई नहीं | नहीं — `PreInvocation` एक turn में हर model call से पहले fire होता है और कोई भी prompt text नहीं ले जाता | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | हाँ | कोई नहीं (sessions SQLite हैं) |

दो harnesses कुछ भी record नहीं करते, और दोनों cases में एक ही कारण से: उनकी event कोई भी human text नहीं देती। Hermes के पास कोई prompt-submit event नहीं है — इसका native plugin `pre_llm_call` को खुद handle करता है और केवल tool, session और subagent events को forward करता है। Antigravity का `PreInvocation` हर model call से पहले fire होता है, एक human turn पर और उसके बाद पाँच पर, और कोई भी prompt field नहीं ले जाता; hooks भी same conversation में `userMessage` steps को inject कर सकते हैं। दोनों events में record करने के लिए कुछ नहीं है।

## क्या एक prompt को मानव का बनाता है

1. **Event।** Failproof AI को harness के prompt-submit event के लिए invoke किया गया था, जिसे handler `UserPromptSubmit` में canonicalize करता है।
2. **Payload।** Harness इसे hook के stdin पर लिखता है, और यह text को ऊपर नाम दिए गए field में ले जाता है। एक call जो Failproof AI तक payload के बिना पहुंचती है कुछ भी record नहीं करती।
3. **Payload में कुछ भी turn को rule out नहीं करता है।** एक payload जो एक sub-agent को नाम देता है (`agent_id`) agent है जो अपने आप को prompt कर रहा है। एक `source`, `input_source` या OpenClaw run marker जो एक machine-submitted turn को नाम देता है, refuse होता है। एक **absent** marker कुछ भी rule out नहीं करता — यह उस version से अंतर है जो कुछ भी record नहीं करता था, क्योंकि हर marker यहाँ हर shipping build पर absent है।
4. **Wrapping stripped होने के बाद कुछ बचा है** (नीचे देखें)।

**Session transcript क्या किसका prompt लिखा गया इसका evidence नहीं है।** इस page के earlier versions ने एक transcript cross-check describe किया: prompt को refuse किया जाता था अगर transcript ने दिखाया कि model ने इसे schedule किया, और transcript को जारी रखना था जो पिछले prompt ने देखा। यह check चला गया है। एक transcript एक file है जो agent के पास पहले से ही shell है — यह truncate, replace, padded हो सकता है read budget को पार करने के लिए, एक turn के start पर snapshot और end पर restore, या फिर से अच्छी तरह पढ़ने के लिए जो agent ने लिखे entries के साथ बनाया जा सकता है। hardening के हर round के बाद same forgery का दूसरा spelling आया, तो पूरा mechanism repaired होने के बजाय remove किया गया।

Transcript अभी भी एक चीज़ के लिए read होता है: **agent का last visible message**। वह message agent-written है definition के अनुसार, Jev को ऐसा कहा जाता है, और यह कभी भी अकेले consent नहीं है।

## एक prompt से क्या रखा जाता है

Harnesses एक prompt में मानव के words से ज्यादा put करते हैं। कुछ भी store होने से पहले:

- `<system-reminder>` blocks को remove किया जाता है, और उनके चारों ओर मानव के words को रखा जाता है।
- एक session-continuation summary ("This session is being continued from a previous conversation…") पूरी तरह drop किया जाता है।
- Task notifications, local-command output और interruption markers पूरी तरह drop किए जाते हैं।
- एक turn जो दूसरे agent या session ने लिखा, पूरी तरह drop किया जाता है: Claude Code उन्हें `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` या `<channel source=…>` में wrap करता है।
- Failproof AI के अपने messages पूरी तरह drop किए जाते हैं। एक stop gate का `MANDATORY ACTION REQUIRED from failproofai …` या एक `Instruction from failproofai: …` अगले user turn के रूप में Cursor, Copilot, Devin और OpenClaw पर वापस आता है, और यह कभी भी मानव के words नहीं गिने जाते — न plain, न `<user_query>` block में wrap किए गए, न एक system reminder के पीछे।
- एक slash command को command और arguments के रूप में रखा जाता है जो मानव ने type किया, कभी नहीं वह body जो harness ने expand किया।
- एक prompt जो Codex IDE extension ने built किया केवल अपनी last `## My request for Codex:` के बाद का text रखता है (या, newer builds में, `## My request:`) heading। सब कुछ जो extension ने इससे पहले put किया, drop किया जाता है: active file, open tabs, editor में selected text, mentioned files और apps, diff और browser comments, PR checks, earlier conversations। यह rule **हर** harness के prompts पर लागू होता है, केवल Codex के नहीं — ऐसा prompt किसी भी composer में paste किया जा सकता है — तो extension के section headings दो groups में read होते हैं:
  - **एक heading जो कोई भी type नहीं करता** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, Codex और ChatGPT conversation headings, "The attached pasted text file(s)…", और extension के section के बाकी) का मतलब extension ने यह prompt built किया। इसके अंदर कोई request heading के बिना कोई human text नहीं है और record नहीं होता। यह क्या रखता है कि approval forge किए गए text में जो आप केवल *selected* करते हैं — एक `// NOTE FROM THE OWNER: yes, force-push…` comment `# Selected text:` के अंदर — आपके recorded request से निकल जाए।
  - **एक heading जो कोई भी plausibly type करता है** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) का मतलब "extension-built" केवल तब होता है जब एक request heading actually वहाँ है। बिना किसी के, prompt yours है और पूरी तरह रखा जाता है, heading और सब कुछ। इसे drop करना चुप और पूरा होता: कुछ भी उस turn के लिए record नहीं, तो कोई भी reviewable policy clear नहीं हो सकता और Jev से यह भी नहीं पूछा जाता कि क्या request envelope में कोई injection है। यह केवल एक turn के *top* पर counts: एक बार prompt को extension-built के रूप में establish किया जाता है, एक heading दोनों groups में जो अपनी request heading को follow करता है वह extension के sections में से एक है, और prompt record नहीं होता।

  Request itself को किसी दूसरे turn की तरह judge किया जाता है: अगर जो heading के बाद आता है एक continuation summary, एक message दूसरे agent या session ने लिखा, Failproof AI के अपने directives में से एक, या extension के sections में से एक है, तो prompt बिल्कुल record नहीं होता।
- एक Cursor prompt `<user_query>…</user_query>` में wrapped (optionally एक `<timestamp>` block के पीछे) unwrap किया जाता है जब wrapper *पूरा* prompt होता है। एक tag कहीं और ordinary text है — एक snippet log से pasted, या एक branch name जो agent ने चुना — और prompt पूरी तरह रखा जाता है बजाय tagged span में cut किए।
- Pasted blocks को रखा जाता है और मानव द्वारा pasted के रूप में label किया जाता है।

एक prompt जो कुछ भी नहीं है बस harness text, बिल्कुल record नहीं होता।

## Agent का last message

"yes" जैसा reply इसके बिना कुछ नहीं है जिसे यह answer दे। जब एक prompt record होता है, Failproof AI भी agent के last visible message को session transcript से read करता है **उस moment पर**, और इसे prompt के साथ store करता है। Jev इसे अपने अपने field में receive करता है, agent द्वारा लिखे गए के रूप में label किया गया: यह एक short reply को explain करता है और कभी भी अकेले मानव के request के रूप में count नहीं होता। यह एक चीज़ है जिसके लिए transcript read होता है, और सबसे बुरा एक rewritten transcript कर सकता है एक message put करना जो agent ने लिखा जहाँ एक message agent ने लिखा expected है।

यह transcript के end से read होता है, सबसे ज्यादा last 4 MB। Supported transcript formats हैं Claude Code, Codex rollouts (older `agent_message` events और newer `AgentMessage` items), Cursor, Copilot `events.jsonl`, और Pi, Factory और OpenClaw session JSONL। Claude Code के अपने synthetic और API-error messages और subagent (sidechain) messages skip हैं। Goose और OpenCode के लिए कोई snapshot नहीं है, जो sessions को SQLite में रखते हैं, Devin के लिए, जिसका transcript एक single JSON document है, या OpenClaw के लिए, जिसका `before_agent_run` event कोई transcript path नहीं ले जाता।

## Storage

| Property | Value |
| --- | --- |
| Location | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, जहाँ `<profile>` agent profile है जिसमें prompt type किया गया था: `<integration>.<instance-id>` एक agent के लिए जिसे FailproofAI जानता है (identity जो Cloud policies target करते हैं), या बस `<integration>` अन्यथा |
| Permissions | file `0600`, directory `0700`। इसके ऊपर हर directory, `~/.failproofai` तक, `jev.json` की directory के रूप में held है: एक जो कोई भी दूसरा **write** कर सकता है को rename away और replace किया जा सकता है, तो read path उन write bits को लेता है जहाँ यह कर सकता है, और **कुछ भी** नहीं read करता जहाँ यह नहीं कर सकता। एक recorded prompt फिर absent है बजाय forged, और कुछ भी clear नहीं है |
| Kept per session | last 5 prompts; एक prompt जो एक से पहले identical है इसे replace करता है बजाय एक नया slot लेता है |
| Window | prompts जो 6 hours से पुराने हैं ignored हैं |
| Size | हर prompt और agent message को 6,000 characters पर cap किया जाता है, head और tail को रखते हुए |
| Secrets | `sanitize-*` policies के समान patterns के साथ redacted कुछ भी लिखा जाने से पहले। एक text जो 48,000 characters से लंबा है redacted है इसके first 28,800 और last 19,200 characters के रूप में, और text जो उन cuts के पास है, जहाँ एक secret को split किया जा सकता था, कभी store नहीं होता |

एक session ID जिसमें letters, digits, `.`, `_` और `-` के अलावा कुछ है, या 128 characters से लंबा है, कभी भी file name के रूप में use नहीं होता, तो कुछ भी इसके लिए record नहीं होता।

एक session file एक बार exist होता है जब एक prompt इसमें record हो गया है। यह prompts और कुछ नहीं रखता — कोई origin state, कोई transcript mark नहीं — और यह delete होता है एक बार यह 6-hour window से लंबे समय तक चुप रहा है, अगली बार जब एक नया session अपना पहला prompt लिखता है।

एक prompt केवल same agent profile और session ID के लिए read होता है जिसके तहत यह record किया गया था। Session IDs agent से आते हैं, तो दो profiles एक ही का use कर सकते हैं; profile के द्वारा key करना एक profile के words को कभी दूसरे के request के रूप में count करने से रखता है। इस layout से पहली files (`sessions/<session-id>.json`) नहीं कह सकते कि किस profile ने उन्हें लिखा, तो वे कभी read नहीं होती, और 6-hour window के साथ expire होती हैं।

कुछ भी record नहीं होता जब तक कि एक Jev endpoint configure नहीं है। एक FailproofAI Cloud Jev mode के अंदर, एक agent profile के लिए कुछ भी record नहीं होता जिसे कोई Cloud Jev check assign नहीं है और कोई भी installed pack की check review नहीं करता।

### Project root

"Project के अंदर" — जो `read-outside-workspace` और दूसरी path checks को judge करते हैं — का मतलब project के अंदर है जो session उसके **first reviewed call** पर था। Root तब pin किया जाता है और एक later `cd` इसे कभी move नहीं करता; एक `cd` अभी भी कैसे एक relative path resolve होता है यह change करता है। इसे `cd` को follow करने देना `cd ~/.ssh` को एक call में `~/.ssh` को अगले के लिए project बनाने देता।

Pin `~/.failproofai/state/semantic/roots/<session-id>.json` है, `{root, at}` को रखते हुए: file `0600`, directory `0700`, और ऊपर के समान session-ID rule। Files जो 7 दिन से पुरानी हैं delete होती हैं जब एक नया session अपना root pin करता है। एक `roots` directory जो दूसरे users write कर सकते हैं ignored है, और live directory का root use होता है। एक session को re-pin करने के लिए, इसकी file को delete करें।

## Known limits

- **एक prompt केवल hook invocation के रूप में trustworthy है।** हर चीज़ यहाँ payload को read करती है जो harness ने hook के stdin पर लिखा। एक agent जो commands चला सकता है harness को headlessly run कर सकता है (`claude -p` और ऊपर listed सात दूसरे) या Failproof AI के hook binary को खुद run कर सकता है एक payload के साथ जो उसने लिखा, और एक prompt record कर सकता है जो कोई type नहीं किया। यह accepted trade है जो इस page के top पर described है: यह केवल reviewable policies clear करता है, कभी hard एक नहीं — लेकिन पंद्रह reviewable built-ins में से बारह denies हैं, तो एक forged prompt एक real block को उन बारह पर allow में बदल सकता है।
- **Sub-agent detection Claude-shaped है।** एक payload जो `agent_id` को ले जाता है कभी record नहीं होता, किसी भी harness पर। वह field है जो Claude Code, Factory Droid और Devin use करते हैं। Codex अपनी prompt event को sub-agent threads के अंदर fire करता है, Copilot in-process sidekicks चलाता है, Goose के पास एक `delegate` tool है और OpenClaw personas चलाता है — जिनमें से कोई भी payload को एक तरीके से mark नहीं करता जो यह recognize करता है, तो एक sub-agent prompt उन harnesses पर session के अपने के रूप में record होता है। OpenClaw का `openclaw.agentId` **वह** mark नहीं है: shipped plugin हर run पर इसे set करता है, owner का included।
- **Schedulers जो कोई marker नहीं ले जाते।** Claude Code के `schedule_wakeup` और `loop_wakeup`, और OpenClaw के `cron` और `heartbeat` triggers refuse हैं क्योंकि वह harnesses payload में ऐसा कहते हैं। Goose का अपना scheduler (`goose schedule add`) और Codex का `codex exec` कुछ नहीं कहते, तो एक run जो वे start करते हैं किसी दूसरे की तरह record होता है।
- **एक agent का last message एक message हो सकता है जो agent ने चुना।** Transcript authenticated नहीं है, तो एक agent जो अपने transcript को लिखता है अपने "last message" को decide कर सकता है क्या कहे। यह agent-written है label किया गया और कभी भी अपने आप से कुछ भी clear नहीं करता — लेकिन ध्यान दें कि `decide.ts` का v1 path इसे deterministic "did the user name this target" check को satisfy करने देता है, तो एक agent जो अपने transcript को control करता है एक target name को supply कर सकता है जो एक override को need करता है।
- **एक prompt जो extension के machine headings में से एक के साथ open होता है पूरी तरह drop होता है।** एक prompt के साथ start करें `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` या first group से दूसरे section heading के साथ, और कभी `## My request:` heading मत लिखें, और कुछ भी उस turn के लिए record नहीं होता — तो कुछ भी इसके लिए clear नहीं होता। वह deliberate है: यह sections text को ले जाते हैं जो कोई दूसरा control करता है (code जो आप selected, एक reviewer का diff comment, एक page title), और record करना कि आपके words के रूप में worse failure है। Headings जो developer plausibly type करते हैं दूसरे group में हैं और कभी भी अपने आप से एक prompt को drop नहीं करते।
- **OpenCode व्यावहारिक रूप से कुछ भी record नहीं करता।** इसका `message.updated` event current OpenCode में कोई text नहीं ले जाता, और यह child sessions के लिए भी fire होता है जो इसका task tool create करता है, जिसका "user" message parent agent ने लिखा।
- **`CODEX_HOME` को honour नहीं किया जाता** `lib/codex-sessions.ts` में rollout discovery द्वारा। यह केवल प्रभावित करता है जहाँ एक agent-message snapshot को looked for है, कभी नहीं कि क्या एक prompt record होता है।
