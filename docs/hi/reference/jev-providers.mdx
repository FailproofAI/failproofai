यह [Jev policies](/hi/policies/jev) के लिए provider और configuration reference है आपकी अपनी key के साथ। Regex policies strings को match करती हैं। वे `rm -rf build/` को यह नहीं बता सकतीं कि आपने plan में `rm -rf ~` से क्या माँगा था, इसलिए वे एक जगह बहुत ज्यादा block करती हैं और दूसरी जगह बहुत कम। **Jev**, TypeSafe's classifier, call को आपने जो वास्तव में माँगा है उसके विरुद्ध पढ़ता है और एक तेज़ request में इसके बारे में yes/no questions का एक सेट देता है।

आपके own Jev endpoint और key configured के साथ, Failproof AI प्रत्येक tool call के बारे में Jev से पूछता है **alongside** regex policies के, कभी उनकी जगह नहीं:

- एक **hard** policy का deny अंतिम है। Jev इसे clear नहीं कर सकता। हर policy hard है जब तक कि यह explicitly reviewable के रूप में marked न हो और Jev checks को name न करे जो इसे cover करते हैं, इसलिए एक custom, pack या Cloud policy जो कुछ नहीं कहता है hard है, और हमेशा-on self-protection guard हमेशा hard है।
- एक **reviewable** policy का deny clear हो सकता है, लेकिन केवल तब जब Jev से उस exact concern के बारे में पूछा गया जो policy cover करता है और "nothing here" या "the user asked for this" का जवाब दिया। एक check जो concern को real पाता है, जब user ने call के लिए नहीं माँगा, deny को रखता है — यहाँ तक कि जब इसका स्वयं का verdict केवल एक warning हो, क्योंकि tool call से पहले एक warning agent को नहीं रोकता। और जब वह check वह है जो deny कर सकता है (secret exposure, credential exfiltration, destructive deletion, …), कुछ भी उस call पर clear नहीं होता है।
- एक block अभी भी एक **warning** बन सकता है जब call आपने दिए गए task का एक step है और आगे नहीं बढ़ता है: Jev अपनी ही deny को एक warning में नरम करता है, और वह warning — जो actually call के साथ क्या गलत है नाम देते हुए — policy के block को replace करता है।
- Jev अपने आप पर भी warn या deny कर सकता है, harm के लिए जो कोई regex describe नहीं करता।
- अगर Jev answer नहीं दे सकता (timeout, rate limit, server error, no credits, एक unexpected model version), वह call को regex result मिलता है, बिल्कुल Jev के बिना।
- Jev कभी भी एक call को आपकी policies से ज्यादा permissive नहीं बनाता जब तक कि यह पूरी call को पढ़ न ले और exact concern के बारे में न पूछा गया हो। कुछ भी कम — एक call जो भेजने के लिए बहुत बड़ा है, एक suspected injection — clearances को withdraw करता है और हर deny को रखता है।

<Note>
Jev config के बिना कुछ नहीं बदलता: hooks regex policies को ठीक वैसे ही run करते हैं जैसे हमेशा। Config पूरा opt-in है।
</Note>

<Tip>
FailproofAI Cloud पर? आपको अपनी खुद की key की जरूरत नहीं है: एक machine जो `jev:evaluate` carry करने वाली key के साथ connected है आपके organization के plan पर Jev का use कर सकता है। [Jev through FailproofAI Cloud](/hi/reference/jev-cloud) देखें।
</Tip>

## शुरू करने से पहले

**failproofai 1.0.8-beta.0 या बाद में** install करें और इसके hooks को एक [supported harness](/hi/reference/harnesses) पर attach करें उस machine पर जहाँ आपका agent चलता है। अगर यह एक नया machine है तो [quickstart](/hi/start/quickstart) follow करें, या अगर आप Cloud का use नहीं करते हैं तो [set up local enforcement](/hi/start/setup#enforce-locally)। installed CLI को `failproofai --version` से check करें।

नीचे दिए गए provider से एक API key प्राप्त करें, या एक compatible endpoint और इसकी key तैयार रखें। Jev named tool calls को `PreToolUse` या `PermissionRequest` gate पर review करता है। यह अपना स्वयं का verdict issue कर सकता है, लेकिन एक existing policy deny को clear करने के लिए एक installed policy भी जरूरी है जो [reviewable](/hi/policies/authority) के रूप में marked हो। Hard policy denies अंतिम रहते हैं।

## एक provider चुनें

Jev पाँच routes के माध्यम से reachable है। उनमें से किसी के लिए एक key लाएँ।

| Provider | `--provider` | Endpoint | Default model | Notes |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Exact version pin। |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | Requests zero-data-retention endpoints को route किए जाते हैं केवल, दूसरे provider को fallback के साथ कोई fallback नहीं। एक dated version जैसे `typesafe/jev-1.13-20260917` report करता है। |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jev को केवल एक alias के द्वारा names, इसलिए answering version को unverified के रूप में record किया जाता है। |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id` की जरूरत है। Measured पर लगभग छः calls एक सेकंड में per key HTTP 429 से पहले। |
| Your own endpoint | `custom` | `<base-url>/systemone` | `jev-1.13.0` | कोई भी endpoint जो TypeSafe की request body को accept करता है और report करता है कि कौन सा model answer दिया। `https` केवल; plain `http` को एक loopback host (`localhost`, `127.0.0.1`, `::1`) को local testing के लिए accept किया जाता है। |

<Warning>
Vercel के अपने bring-your-own-key feature के साथ, एक failed request को silently Vercel के credentials के साथ retry किया जाता है। अगर आपको हर call को बिल किया जाना है, और केवल आपके अपने TypeSafe account द्वारा देखा जाना है, तो TypeSafe को directly use करें।
</Warning>

## इसे set up करें

एक command, endpoint और key। `observe` mode में start करें ताकि आप Jev के verdicts को inspect कर सकें जबकि existing policies calls को decide किए रहते हैं:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL provider को pick करता है

आपको provider को name करना नहीं पड़ता: URL का **host** यह है कौन सा है।

| URL host | Provider | Also needs |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| any other host | `custom` | — the URL you gave is the base URL |

तीन चीजें इससे निकलती हैं:

- **एक URL जो provider का अपना API है कोई override नहीं लिखता।** `--url https://api.typesafe.ai/v1` बिल्कुल वही config produce करता है जो `--provider typesafe` होगा। एक known provider पर एक different path या host दें और यह base URL के रूप में store किया जाता है, जैसे `--base-url` इसे store करेगा।
- **`--provider` फिर भी inference को override करता है**, जो है कि आप एक proxy तक पहुँचते हैं जो provider के API को अपने host से बोलता है: `--url https://jev-proxy.internal/v1 --provider typesafe`।
- **एक `--provider` जो host के साथ contradicts किया जाता है refused है**, guessed नहीं। `--provider openrouter --url https://api.typesafe.ai/v1` कुछ नहीं लिखता है और कहता है क्यों: दोनों spellings disagree करते हैं कि आपकी key कहाँ भेजी जाने वाली है। वही pair `jev setup --base-url` से और dashboard के Jev settings से refused है। (`--provider custom` एक contradiction नहीं है — यह मतलब है "treat this URL as itself" — except Cloudflare के host पर, जिसका per-account endpoint एक custom route नहीं reach कर सकता।)

`--url` को exactly validate किया जाता है जैसे config file में `baseUrl` है, और refused है उन्हीं शब्दों में: `https`, या plain `http` एक loopback host (`localhost`, `127.0.0.1`, `::1`) को किसी भी mode में। Risk: कुछ भी loopback server को authenticate नहीं करता, इसलिए जबकि यह down है, machine पर दूसरी local process अपना port ले सकता है और answer दे सकता है; local testing के बाहर `https` का use करें।

### Key

इसे `--key-stdin` के साथ pipe करें, या बिना इसके एक terminal में command run करें और एक masked prompt पर key को paste करें। किसी भी तरह यह सीधे config file में जाता है और कभी वापस print नहीं होता है।

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` same flags लेता है और इसका longhand है सब कुछ के लिए: `setup --provider <kind>` जहाँ आप provider को name करना चाहते हैं URL से ज्यादा।

### `--token`, और यह क्या खर्च करता है

`--token <token>` key को command line पर रखता है, जो एक machine को configure करने का fastest तरीका है और एक unique spelling है जो key को config file से कहीं और नहीं रखता:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
एक command-line argument के बाद आपकी shell की history file में है, और जबकि command run होता है यह process list में है — `/proc` से anything से readable आपके रूप में running। `setup` हर बार `--token` का use किया जाता है कहता है। `--key-stdin` को एक machine पर prefer करें जो आप share करते हैं, एक recorded session में, या कहीं भी history file sync है; एक key को rotate करें जो आपने इस तरह pass किया है अगर यह matter करता है।
</Warning>

`--token`, `--key-stdin` और `--key-from-env` mutually exclusive हैं: एक दें।

फिर एक छोटा live request भेजें key, endpoint और कौन सा Jev answer दिया यह check करने के लिए:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` exit 1, और अपने title में कहता है, जब answer timeout के बाद arrives (हर hook regex के रूप में `timeout` को fallback करेगा) या अपने check question को गलत answer देता है।

Hooks प्रत्येक tool call पर config को read करते हैं, इसलिए यह अगले से apply होता है। कोई भी restart नहीं है, daemon के साथ या बिना।

## यह क्या कर रहा है check करें

```bash
failproofai jev status
failproofai jev status --json
```

`status` provider, endpoint, model, mode, config file और इसकी permissions को show करता है, और कभी key नहीं। इसके नीचे यह recent activity को summarize करता है: कितने calls Jev ने evaluate किए, कितनी बार यह regex को fallback किया और क्यों, इसकी latency, और कौन सी reviewable policies को यह clear किया।

## एक real call को verify करें

hooked agent में एक नया session start करें। इसे अपनी file-reading tool को `README.md` पर use करने के लिए ask करें और title को report करें। Confirm करें कि session में वह tool call है, फिर `failproofai jev status` को फिर से run करें: इसकी recent evaluated-call count बढ़नी चाहिए। [local dashboard](/hi/reference/local-dashboard#review-policy-activity) में **Policies → Activity** खोलें call के Jev verdict और mode को inspect करने के लिए। Observe mode में, policy result अभी भी call को decide करता है। एक clearance केवल तब appear होता है अगर एक reviewable policy matched और Jev ने हर named check को clear किया; एक ordinary read में कोई policy नहीं हो सकता clear करने के लिए।

## Observe mode

`enforce` default है। Jev को किसी भी decision को change किए बिना watch करने के लिए, `observe` में switch करें: Jev अभी भी ask किया जाता है और इसके verdicts record किए जाते हैं, लेकिन regex result यह है जो enforce किया जाता है।

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` config को रखता है — endpoint और key — और Jev को asking को रोकता है: hooks regex policies को ठीक बिना config के run करते हैं, और `failproofai jev status` कहता है "off (switched off)"। `--mode observe` या `--mode enforce` के साथ वापस switch करें।

Same provider के लिए `setup` को re-run करने से stored key को रखा जाता है, इसलिए एक mode switch एक flag है। Provider को switching से शुरू होता है और उस provider की key को asks करता है। A `--base-url` भी जो requests को एक different host पर move करता है: एक stored key केवल उस host को भेजा जाता है जिसे यह दिया गया था, या provider के अपने API को।

## Config file

सब कुछ एक file में lives, `~/.failproofai/jev.json`, `setup` द्वारा written:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Field | Meaning |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` या `custom` — या `failproofai`, जिसकी key इस file की जगह FailproofAI Cloud connection से आती है ([Jev through FailproofAI Cloud](/hi/reference/jev-cloud) देखें)। |
| `apiKey` | `Authorization: Bearer <key>` के रूप में sent। |
| `baseUrl` | `custom` के लिए required; अन्यथा provider के API base को replace करता है। `https` होना चाहिए। Plain `http` को `localhost` में केवल `mode: observe` के साथ accept किया जाता है: कुछ भी loopback server को authenticate नहीं करता, इसलिए जबकि आपका proxy down है कोई भी machine पर process, agent को judge किया जा रहा भी, इसके स्थान पर answer दे सकता है। |
| `accountId` | Cloudflare केवल: 32 lowercase hex characters। |
| `model` | Provider के default model id को replace करता है। एक versioned id को Jev 1.13 को name करना चाहिए। एक value जो एक API key की तरह shaped है refused है (और repeated back नहीं), इसलिए एक key `--model` में pasted को कभी store या model के रूप में send नहीं किया जाता है। |
| `timeoutMs` | कितने समय एक tool call Jev के लिए regex result का use करने से पहले waits। 100–10000, default 3000। |
| `mode` | `enforce` (default), `observe`, या `off` (config को रखें, कोई Jev नहीं run करें)। |

तीन rules इसे protect करते हैं:

- **Owner-only।** यह permissions `0600` के साथ लिखा जाता है। एक copy जो कोई दूसरा user या group read या write कर सकता है **refused** है, और hooks regex को fallback करते हैं जब तक आप `chmod 600 ~/.failproofai/jev.json` या `setup` को फिर से run न करें। Directory को भी check किया जाता है: `~/.failproofai` को किसी के द्वारा **writable** नहीं होना चाहिए, क्योंकि जो भी वहाँ write कर सकता है file को replace कर सकता है चाहे इसकी अपनी permissions कुछ भी हों। `setup` इन write bits को off लेता है अगर यह इन्हें find करता है। `failproofai jev status` कहता है जब एक config को refuse किया गया है और file को endpoint को show करता है: कोई दूसरा यह change किया हो सकता है, इसलिए यह check करें कि यह आपका है फिर आप `chmod` करने से पहले। ऐसी file पर `setup` को re-run करना इसके stored key को केवल provider के own API में carries; कोई अन्य endpoint जो यह names को key की फिर से जरूरत है (`--key-stdin`), या `--base-url default` requests को provider को वापस भेजने के लिए।
- **Global only।** एक repository Jev को turn on नहीं कर सकता, यह दूसरे endpoint को point नहीं कर सकता या इसका model pick नहीं कर सकता: एक `.failproofai/jev.json` एक project के अंदर ignored है, और provider, URL, model और account id को केवल उस file से read किया जाता है — कभी environment से नहीं, जिसे एक repository के agent settings set कर सकते हैं। (`FAILPROOFAI_HOME` इसके आसपास एक तरीका नहीं है: यह पूरी failproofai directory को move करता है, आपकी policies सहित, Jev को अपने आप में redirect करने की जगह।)
- **Key अकेले environment से आ सकता है।** अगर file में कोई `apiKey` नहीं है, `FAILPROOFAI_JEV_API_KEY` उस session के लिए इसे supply करता है (`setup --key-from-env` ऐसी file लिखता है)। यह कभी key को file को hold करता है replace नहीं करता है, और बिना file के Jev को on नहीं कर सकता। जहाँ variable set नहीं है, Jev simply उस shell के लिए off है: `failproofai jev status` कहता है, exit 0 करता है और config को alone छोड़ता है (`status --json` report करता है `"status": "key-missing"` के साथ `"reason": "no-env-key"`)। `failproofaid` daemon आपकी shell के environment को नहीं देखता है, इसलिए एक machine पर `failproofai config` के साथ set up किया गया है, key को file में रखें।

## कौन सा Jev answers

Failproof AI के decision thresholds को Jev 1.13 पर calibrate किया गया था, इसलिए एक answer का use किया जाता है केवल जब यह उस family से आता है: `jev-1.13.x`, या OpenRouter का `typesafe/jev-1.13-<date>`। जहाँ एक provider Jev को केवल एक alias के द्वारा names करता है और कोई version report नहीं करता (Vercel, और Cloudflare जब यह नहीं कहता), answer का use किया जाता है और unverified के रूप में recorded। एक `custom` endpoint को model report करना चाहिए जो answer दिया; एक exception है एक unversioned `--model` name जो आपने इसके लिए configured किया है, जो, echoed back, unverified के उसी तरीके से recorded है। एक answer reporting कोई अन्य version, या एक `custom` answer reporting none, का use नहीं किया जाता है: वह call regex को fallback करता है `model-mismatch` के reason के साथ।

## जब Jev answer नहीं दे सकता

इनमें से प्रत्येक उस call के लिए regex result को fallback करता है और इसके reason के साथ recorded है, जो `failproofai jev status` totals:

| Reason | Cause |
| --- | --- |
| `timeout` | `timeoutMs` के अंदर कोई answer नहीं। |
| `http-429` | Provider ने key को rate-limited किया। |
| `rate-limited` | Failproof AI के own limiter ने call को भेजने से पहले रोका: 5 requests एक सेकंड में, bursts में up to 5 तक, और provider `429` का answer देने के बाद एक moment के लिए कोई नहीं। Provider नहीं। |
| `http-500`, `http-502`, `http-503`, … | Provider पर एक server error। Exact status recorded है। |
| `out-of-credits` | HTTP 402: provider account के पास कोई credits नहीं रहे। |
| `provider-refused` | Cloudflare से HTTP 402 "Model execution failed (Payment error)" को read करता है: provider ने इस request पर model को run करने से decline किया। Usually billing नहीं, इसलिए topping up यह move नहीं करेगा। |
| `http-401`, `http-403` | Key को refuse किया गया। |
| `http-404` | कुछ भी `<base>/systemone` पर serve नहीं किया जाता है, इसलिए base URL गलत है — `/systemone` को इसमें appended किया जाता है, और हर provider यह अपने version root पर serves करता है। `failproofai jev models` show करता है कि endpoint क्या serve करता है। |
| `network` | Endpoint को reach नहीं किया जा सका। |
| `http-301`, `http-302`, `http-307`, `http-308` | Endpoint ने redirect के साथ answer दिया। Redirects को कभी follow नहीं किया जाता है, इसलिए answer केवल हमेशा आपके config में URL से आता है; `--base-url` को final URL पर set करें। |
| `malformed` | Endpoint ने answer दिया, लेकिन Jev answer के साथ नहीं — एक body जो JSON नहीं है, या कोई answers के साथ नहीं। |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflare के envelope ने failure report किया, या एक job जो finish नहीं हुई थी। |
| `model-mismatch` | Jev version 1.13 के अलावा दूसरा answer दिया, या एक `custom` endpoint ने नहीं कहा कि कौन सा model answer दिया। |
| `request-cut` | **एक outage नहीं।** Jev ने answer दिया; इसे केवल call का एक हिस्सा shown किया गया, इसलिए इसके answer ने कुछ नहीं clear किया। [When Jev answered, but not on the whole call](#when-jev-answered-but-not-on-the-whole-call) देखें। |

`failproofai jev status` कुछ rarer reasons भी show कर सकता है, जैसे `upstream-error` (answer provider के स्वयं error को carry किया) या `config`, और totals किसी भी reason जो यह name नहीं कर सकता `other` के रूप में।

`request-cut` इस table में है क्योंकि `failproofai jev status` इसे rest के साथ totals, और क्योंकि यह भी हर deny को standing रखता है। यह एक unique reason है जो आपके provider के बारे में कुछ नहीं कहता है: request arrive हुई और Jev ने इसे answer दिया। ऊपर की हर row के विपरीत, वह answer अभी भी counts — Jev का स्वयं deny या warning regex result के ऊपर apply होता है बजाय discarded किए। तो उनका एक run calls को mean करता है evaluator को reach कर रहा है बहुत बड़ा भेजने के लिए whole, कि आपका endpoint unwell नहीं है, और topping up credits या URL को changing यह move नहीं करेगा।

## जब Jev answer दिया, लेकिन पूरी call पर नहीं

दो और चीजें happen हो सकती हैं, और न ही Jev को fail करता है answer। दोनों हैं कितना call का, या conversation का, एक request में fit हुआ।

**Call का हिस्सा fit नहीं हुआ।** एक tool call एक fixed budget के अंदर sent है, और एक outsized — एक बहुत बड़ा `Write`, एक huge MCP body, एक command cap तक padded — fit किए गए के साथ sent है। Jev अभी भी answer देता है, और इसका answer अभी भी counts: इसका स्वयं deny या warning usual के रूप में apply होता है। क्या यह नहीं कर सकता है **clear** anything, क्योंकि एक partial call पर दिया गया verdict एक call पर verdict नहीं है। तो हर policy deny stands, और call को `request-cut` के reason के साथ एक fallback के रूप में recorded है, जो `failproofai jev status` ऊपर के reasons के साथ totals। Rule जो यह आपको देता है: एक call को बड़ा बनाना इसके clearances को cost कर सकता है, और कभी कोई एक खरीद नहीं सकता।

**एक message fit नहीं हुआ।** एक long prompt जो आपने pasted किया, agent का last message, या एक prompt जो इस evaluator के अपने store ने पहले से cap किया। **कुछ भी नहीं बदलता है**: call को judge किया जाता है, cleared और recorded किया जाता है exactly किसी दूसरे की तरह, और यह एक fallback के रूप में counted नहीं है। Length जो आप type करते हैं कभी decide नहीं करता एक verdict, और एक cut को manufacture consent नहीं कर सकता: जहाँ एक prompt पहले से already capped arrive हुई, "you did not ask for this" एक conclusion होना बंद कर देता है जो यह draw किया जा सकता है इससे बिल्कुल, rather बजाय एक बन जाने के।

दो के बीच की line है कि किसने text लिखा। Call agent का है, और एक rule जो अपनी length को severity से subtract करने देता agent का use किया जा सकता है; आपका prompt आपका है, और इसकी length को एक signal के रूप में treat करना केवल कभी punishment दे सकता है pasting एक spec या एक stack trace को।

## Machine को क्या छोड़ता है

प्रत्येक tool call के लिए Jev evaluate करता है, एक request आपके provider को जाता है, carrying:

- tool call खुद, secrets जैसे API keys, bearer tokens और `KEY=` assignments redacted के साथ;
- recent prompts आप typed, text आपके agent के harness ने removed के साथ;
- agent का last message आपके latest prompt से पहले, agent-written के रूप में labelled;
- facts computed locally, जैसे कि क्या एक path project के अंदर है — session का जो पहली reviewed call में [pinned](/hi/reference/jev-intent#the-project-root) है — और current git branch।

यह केवल आपके config में endpoint को जाता है, आपकी key के under।

## इसे turn off करें

```bash
failproofai jev remove
```

यह `~/.failproofai/jev.json` को delete करता है। अगली tool call से, hooks regex policies को ठीक बिना run करते हैं जैसे पहले। Per-session stores `~/.failproofai/state/semantic/` के under (recorded prompts `sessions/` में, project roots `roots/` में) are left in place और age out। Jev को asking को stop करने के लिए लेकिन config को रखने के लिए, `failproofai jev setup --mode off` का use करें instead।

## Command reference

| Command | Outcome |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | एक command में configure करें; provider URL के host से आता है |
| `failproofai jev --url <url> --token <token>` | Same, command line पर key के साथ — आपका history और process list इसे देखते हैं |
| `failproofai jev setup --provider <kind> --key-stdin` | stdin पर piped key से config लिखें |
| `failproofai jev setup --provider <kind>` | Same, एक masked prompt पर key को asking |
| `failproofai jev setup --key-from-env` | कोई key store न करें; per session `FAILPROOFAI_JEV_API_KEY` को read करें |
| `failproofai jev setup --mode observe` | Mode को switch करें (`enforce`, `observe` या `off`), stored key को रखते हुए |
| `failproofai jev setup --model <id>` / `--base-url <url>` | Model या API base को override करें; `default` override को clear करता है |
| `failproofai jev setup --timeout-ms <n>` | Per-call budget को change करें |
| `failproofai jev status [--json]` | Configuration, permissions और recent activity; कभी key नहीं |
| `failproofai jev test [--json]` | एक live request: latency और version जो answer दिया |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | Model ids जो endpoint के `/models` report करता है, configured को marking |
| `failproofai jev remove` | Config को delete करें; Jev off है |
