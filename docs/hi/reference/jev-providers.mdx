यह [Jev policies](/hi/policies/jev) के लिए provider और configuration reference है अपनी key के साथ। Regex policies strings को match करती हैं। वे `rm -rf build/` को जो आपने मांगा था उससे `rm -rf ~` को जो plan में slip हुआ था उससे अलग नहीं बता सकते, इसलिए वे एक जगह बहुत ज़्यादा block करती हैं और दूसरी जगह बहुत कम। **Jev**, TypeSafe का classifier, call को उसके विरुद्ध पढ़ता है जो आपने वास्तव में मांगा था और इसके बारे में yes/no प्रश्नों का एक सेट एक तेज़ request में उत्तर देता है।

अपनी Jev endpoint और key configured के साथ, Failproof AI Jev से प्रत्येक tool call के बारे में पूछता है **alongside** regex policies, कभी उनके बजाय नहीं:

- एक **hard** policy का deny अंतिम है। Jev इसे clear नहीं कर सकता। हर policy hard है जब तक कि यह स्पष्ट रूप से reviewable के रूप में marked न हो और Jev checks का नाम न दे जो इसे cover करते हैं, इसलिए एक custom, pack या Cloud policy जो कुछ नहीं कहता है वह hard है, और हमेशा-on self-protection guard हमेशा hard है।
- एक **reviewable** policy का deny clear हो सकता है, लेकिन केवल तब जब Jev को उस exact concern के बारे में पूछा गया हो जो policy cover करता है और "nothing here" या "the user asked for this" उत्तर दिया हो। एक check जो concern को real पाता है, जब user ने call के लिए नहीं पूछा, तब भी deny को रखता है — भले ही इसका अपना verdict केवल एक warning हो, क्योंकि tool call से पहले एक warning agent को नहीं रोकता। और जब वह check एक हो जो deny कर सकता है (secret exposure, credential exfiltration, destructive deletion, …), तब उस call पर कुछ भी clear नहीं होता।
- एक block अभी भी एक **warning** बन सकता है जब call आपके दिए गए task का एक step हो और आगे न पहुंचे: Jev अपने deny को warning में soften करता है, और वह warning — जो call के साथ वास्तव में क्या गलत है इसका नाम रखता है — policy के block को replace करता है।
- Jev अपने आप पर भी warn या deny कर सकता है, harm के लिए जो regex describe नहीं करता।
- अगर Jev answer नहीं दे सकता (timeout, rate limit, server error, no credits, एक unexpected model version), तब वह call को regex result मिलता है, बिल्कुल Jev के बिना जैसे।
- Jev कभी भी एक call को अपनी policies से ज़्यादा permissive नहीं बनाता जब तक कि यह पूरी call को read न करे और exact concern के बारे में पूछा न गया हो। कुछ भी कम — एक call बहुत बड़ी है पूरी भेजने के लिए, एक suspected injection — clearances को withdraw करता है और हर deny को रखता है।

<Note>
Jev config के बिना कुछ नहीं बदलता: hooks regex policies को ठीक जैसे हमेशा से चलाते हैं। Config पूरी opt-in है।
</Note>

<Tip>
FailproofAI Cloud पर? आपको अपनी key की आवश्यकता नहीं है: एक machine जो key के साथ connected है जो `jev:evaluate` carry करती है, आपके organization के plan पर Jev का उपयोग कर सकता है। [Jev through FailproofAI Cloud](/hi/reference/jev-cloud) देखें।
</Tip>

## शुरू करने से पहले

**failproofai 1.0.8-beta.0 या later** install करें और इसके hooks को एक [supported harness](/hi/reference/harnesses) के साथ attach करें उस machine पर जहाँ आपका agent चलता है। अगर यह एक नया machine है तो [quickstart](/hi/start/quickstart) follow करें, या अगर आप Cloud का उपयोग नहीं करते हैं तो [set up local enforcement](/hi/start/setup#enforce-locally) करें। Installed CLI को `failproofai --version` से check करें।

नीचे किसी provider से एक API key प्राप्त करें, या एक compatible endpoint और इसकी key तैयार रखें। Jev `PreToolUse` या `PermissionRequest` gate पर named tool calls को review करता है। यह अपना सरा verdict issue कर सकता है, लेकिन एक existing policy deny को clear करने के लिए एक installed policy भी आवश्यक है जो [reviewable](/hi/policies/authority) को marked हो। Hard policy denies अंतिम रहते हैं।

## एक provider चुनें

Jev पाँच routes के माध्यम से reachable है। उनमें से किसी एक के लिए एक key लाएं।

| Provider | `--provider` | Endpoint | Default model | Notes |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Exact version pin। |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | Requests को zero-data-retention endpoints में ही routed किया जाता है, दूसरे provider में fallback के बिना। एक dated version जैसे `typesafe/jev-1.13-20260917` report करता है। |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jev को केवल एक alias से name करता है, इसलिए answering version को unverified के रूप में record किया जाता है। |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id` की आवश्यकता है। HTTP 429 से पहले प्रति key लगभग छः calls per second measure किए गए थे। |
| Your own endpoint | `custom` | `<base-url>/systemone` | `jev-1.13.0` | कोई भी endpoint जो TypeSafe के request body को accept करता है और report करता है कि कौन सा model answered है। `https` only; plain `http` एक loopback host को (`localhost`, `127.0.0.1`, `::1`) local testing के लिए accept किया जाता है। |

<Warning>
Vercel के अपने bring-your-own-key feature के साथ, एक failed request को silently retry किया जाता है Vercel के credentials के साथ। अगर आप हर call को केवल अपने TypeSafe account को billed करना चाहते हैं, तो TypeSafe को सीधे use करें।
</Warning>

## इसे सेटअप करें

एक command, endpoint और key। `observe` mode में शुरू करें ताकि आप Jev के verdicts को inspect कर सकें जबकि existing policies calls को decide रहे हैं:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL provider को pick करता है

आपको provider का नाम रखने की आवश्यकता नहीं है: URL का **host** ही वह है।

| URL host | Provider | Also needs |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| any other host | `custom` | — URL जो आपने दिया वह base URL है |

इससे तीन चीजें आती हैं:

- **एक URL जो provider के अपने API को write करता है कोई override नहीं लिखता है।** `--url https://api.typesafe.ai/v1` बिल्कुल वही config produce करता है जो `--provider typesafe` करता। एक known provider पर एक अलग path या host दें और इसे base URL के रूप में store किया जाता है, जैसे `--base-url` इसे store करता।
- **`--provider` अभी भी inference को override करता है**, जो है कि आप कैसे एक proxy तक पहुंचते हैं जो एक provider के API को बोलता है एक आपके अपने host से: `--url https://jev-proxy.internal/v1 --provider typesafe`।
- **एक `--provider` जो host के विरुद्ध है वह refuse किया जाता है**, guessed नहीं। `--provider openrouter --url https://api.typesafe.ai/v1` कुछ भी नहीं लिखता है और कहता है कि क्यों: दोनों spellings इस बारे में असहमत हैं कि आपकी key कहाँ भेजी जाने वाली है। यही pair `jev setup --base-url` से और dashboard के Jev settings से refuse किया जाता है। (`--provider custom` एक contradiction नहीं है — इसका मतलब है "इस URL को अपने आप के रूप में treat करो" — except Cloudflare के host पर, जिसके per-account endpoint तक एक custom route नहीं पहुंच सकता।)

`--url` को बिल्कुल वैसे ही validate किया जाता है जैसे config file में `baseUrl` को है, और same words में refuse किया जाता है: `https`, या plain `http` एक loopback host को (`localhost`, `127.0.0.1`, `::1`) किसी भी mode में। Risk: कुछ भी एक loopback server को authenticate नहीं करता, इसलिए जब तक यह down है एक अन्य local process इसका port ले सकता है और answer दे सकता है; local testing के बाहर `https` use करें।

### Key

इसे `--key-stdin` के साथ pipe करें, या command को एक terminal में उसके बिना run करें और एक masked prompt पर key paste करें। या तो तरीका इसे सीधे config file में जाता है और कभी वापस print नहीं होता है।

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` same flags लेता है और सभी के लिए longhand है: `setup --provider <kind>` जहाँ आप provider का नाम रखना पसंद करते हैं URL के बजाय।

### `--token`, और इसकी कीमत क्या है

`--token <token>` key को command line पर रखता है, जो एक machine को configure करने का सबसे तेज़ तरीका है और एकमात्र spelling जो key को config file के अलावा कहीं रखता है:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
एक command-line argument बाद में आपकी shell की history file में है, और जबकि command चलता है यह process list में है — `/proc` से anything running as you द्वारा readable। `setup` हर बार कहता है जब `--token` use किया जाता है। `--key-stdin` को एक machine पर prefer करें जो आप share करते हैं, एक recorded session में, या कहीं भी history file sync होती है; एक key को rotate करें जिसे आपने इस तरीके से pass किया है अगर यह मायने रखता है।
</Warning>

`--token`, `--key-stdin` और `--key-from-env` mutually exclusive हैं: एक दें।

फिर एक छोटा live request भेजें key, endpoint और कौन सा Jev answered को check करने के लिए:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` exit 1 करता है, और अपने title में कहता है, जब answer timeout के बाद आता है (हर hook regex में fallback करेगा `timeout` के रूप में) या अपने check question का गलत उत्तर देता है।

Hooks हर tool call पर config को read करते हैं, इसलिए यह अगले से लागू होता है। restart करने के लिए कुछ नहीं है, daemon के साथ या बिना।

## जाँचें कि यह क्या कर रहा है

```bash
failproofai jev status
failproofai jev status --json
```

`status` provider, endpoint, model, mode, config file और इसकी permissions को shows करता है, और कभी key नहीं। इसके नीचे यह recent activity को summarize करता है: कितने calls Jev ने evaluate किए, कितनी बार यह regex में fallback हुआ और क्यों, इसकी latency, और कौन से reviewable policies को यह clear करता है।

## एक real call को verify करें

Hooked agent में एक नया session शुरू करें। इसे अपने file-reading tool को `README.md` पर use करने के लिए कहें और title को report करें। Confirm करें कि session में वह tool call है, फिर `failproofai jev status` को फिर से run करें: इसका recent evaluated-call count बढ़ना चाहिए। [local dashboard](/hi/reference/local-dashboard#review-policy-activity) में **Policies → Activity** खोलें call के Jev verdict और mode को inspect करने के लिए। Observe mode में, policy result अभी भी call को decide करता है। एक clearance केवल तभी दिखाई देता है जब एक reviewable policy matched हो और Jev ने हर named check को clear किया हो; एक ordinary read के पास clear करने के लिए कोई policy नहीं हो सकता है।

## Observe mode

`enforce` default है। Jev को देखने के लिए बिना किसी decision को change किए, `observe` में switch करें: Jev अभी भी पूछा जाता है और इसके verdicts record होते हैं, लेकिन regex result वह है जो enforce किया जाता है।

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` config को रखता है — endpoint और key — और Jev को पूछना बंद करता है: hooks regex policies को ठीक जैसे बिना config के run करते हैं, और `failproofai jev status` कहता है "off (switched off)"। `--mode observe` या `--mode enforce` के साथ वापस switch करें।

Same provider के लिए `setup` को फिर से run करने से stored key को रखा जाता है, इसलिए एक mode switch एक flag है। Provider को switch करना शुरू से करता है और उस provider की key मांगता है। एक `--base-url` भी जो requests को एक अलग host में move करता है: एक stored key केवल उस host को भेजी जाती है जो दी गई थी, या इसके provider के अपने API को।

## Config file

सब कुछ एक file में रहता है, `~/.failproofai/jev.json`, `setup` द्वारा written:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Field | Meaning |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` या `custom` — या `failproofai`, जिसकी key इस file के बजाय FailproofAI Cloud connection से आती है ([Jev through FailproofAI Cloud](/hi/reference/jev-cloud) देखें)। |
| `apiKey` | `Authorization: Bearer <key>` के रूप में sent। |
| `baseUrl` | `custom` के लिए required; अन्यथा provider के API base को replace करता है। `https` होना चाहिए। Plain `http` `localhost` को केवल `mode: observe` के साथ accept किया जाता है: कुछ भी एक local port को authenticate नहीं करता, इसलिए जबकि आपका proxy down है machine पर कोई भी process, agent including judged किया जा रहा है, इसके बजाय answer दे सकता है। |
| `accountId` | Cloudflare only: 32 lowercase hex characters। |
| `model` | Provider के default model id को replace करता है। एक versioned id को Jev 1.13 का नाम देना चाहिए। एक value जो एक API key जैसी दिखती है refuse किया जाता है (और वापस repeated नहीं होता), इसलिए एक key जो `--model` में paste किया जाता है कभी store या model के रूप में send नहीं होता है। |
| `timeoutMs` | कितने समय के लिए एक tool call Jev का wait करता है regex result use करने से पहले। 100–10000, default 3000। |
| `mode` | `enforce` (default), `observe`, या `off` (config को keep करो, कोई Jev run नहीं करो)। |

तीन rules इसे protect करते हैं:

- **Owner-only।** यह permissions `0600` के साथ written है। एक copy जिसे कोई अन्य user या group read या write कर सकता है **refused** है, और hooks regex में fallback होते हैं जब तक आप `chmod 600 ~/.failproofai/jev.json` या `setup` को फिर से run न करें। Directory को भी check किया जाता है: `~/.failproofai` किसी अन्य द्वारा **writable** नहीं होना चाहिए, क्योंकि जो कोई वहाँ write कर सकता है वह file को अपनी permissions के बावजूद replace कर सकता है। `setup` अगर यह find करता है तो those write bits को off ले जाता है। `failproofai jev status` कहता है जब एक config refuse किया गया है और file का endpoint दिखाता है: किसी और ने इसे change किया हो सकता है, इसलिए check करें कि यह आपका है `chmod` करने से पहले। एक ऐसी file पर `setup` को फिर से run करना अपनी stored key को केवल provider के अपने API पर ले जाता है; कोई अन्य endpoint जो नाम रखता है उसे key फिर से चाहिए (`--key-stdin`), या `--base-url default` requests को provider में वापस भेजने के लिए।
- **Global only।** एक repository Jev को turn on नहीं कर सकता, इसे दूसरे endpoint पर point नहीं कर सकता या model को pick नहीं कर सकता: एक project के अंदर `.failproofai/jev.json` को ignore किया जाता है, और provider, URL, model और account id केवल उस file से read होते हैं — कभी environment से नहीं, जो एक repository के agent settings को set कर सकते हैं। (`FAILPROOFAI_HOME` उसके आसपास नहीं है: यह पूरे failproofai directory को move करता है, आपकी policies included, बजाय केवल Jev को redirect करने के।)
- **Key alone environment से आ सकता है।** अगर file में कोई `apiKey` नहीं है, `FAILPROOFAI_JEV_API_KEY` उस session को supply करता है (`setup --key-from-env` एक ऐसी file लिखता है)। यह कभी key को replace नहीं करता जो file hold करता है, और बिना file के Jev को turn on नहीं कर सकता। जहाँ variable set नहीं है, Jev बस उस shell के लिए off है: `failproofai jev status` कहता है, exit 0 करता है और config को alone छोड़ता है (`status --json` reports `"status": "key-missing"` with `"reason": "no-env-key"`)। `failproofaid` daemon आपकी shell की environment को नहीं देखता, इसलिए एक machine पर जो `failproofai config` के साथ set up है, key को file में रखें।

## कौन सा Jev answers

Failproof AI की decision thresholds को Jev 1.13 पर calibrate किया गया था, इसलिए एक answer को केवल तब use किया जाता है जब यह उस family से आता है: `jev-1.13.x`, या OpenRouter का `typesafe/jev-1.13-<date>`। जहाँ एक provider Jev को केवल एक alias से name करता है और कोई version नहीं report करता (Vercel, और Cloudflare जब यह नहीं करता), answer को use किया जाता है और unverified के रूप में record किया जाता है। एक `custom` endpoint को reporting करना चाहिए कि कौन सा model answered; एक exception एक unversioned `--model` name है जिसे आपने configure किया है, जो, echoed back, same way में unverified के रूप में record किया जाता है। एक answer जो किसी अन्य version को report करता है, या एक `custom` answer जो कोई नहीं report करता, को use नहीं किया जाता: वह call regex में fallback होता है reason `model-mismatch` के साथ।

## जब Jev answer नहीं दे सकता

इनमें से प्रत्येक उस call के लिए regex result में fallback करता है और अपने reason के साथ record किया जाता है, जो `failproofai jev status` totals:

| Reason | Cause |
| --- | --- |
| `timeout` | `timeoutMs` के अंदर कोई answer नहीं। |
| `http-429` | Provider ने key को rate-limit किया। |
| `rate-limited` | Failproof AI का अपना limiter call को hold करता है इसे भेजने से पहले: 5 requests एक second में, bursts में up to 5 तक, और provider `429` answer देने के बाद एक moment के लिए कुछ नहीं। Provider नहीं। |
| `http-500`, `http-502`, `http-503`, … | Provider पर एक server error। Exact status record किया जाता है। |
| `out-of-credits` | HTTP 402: provider account के पास कोई credits नहीं बचे हैं। |
| `provider-refused` | HTTP 402 from Cloudflare reading "Model execution failed (Payment error)": provider ने इस request पर model को run करना declined किया। Usually billing नहीं, इसलिए topping up इसे नहीं move करेगा। |
| `http-401`, `http-403` | Key को refuse किया गया था। |
| `http-404` | कुछ नहीं `<base>/systemone` पर serve किया जाता है, इसलिए base URL गलत है — `/systemone` को इसमें appended किया जाता है, और हर provider इसे इसके version root पर serve करता है। `failproofai jev models` दिखाता है कि endpoint क्या serve करता है। |
| `network` | Endpoint को reach नहीं किया जा सकता था। |
| `http-301`, `http-302`, `http-307`, `http-308` | Endpoint ने एक redirect के साथ answer किया। Redirects को कभी follow नहीं किया जाता, इसलिए answer केवल उस URL से आता है जो आपके config में है; `--base-url` को final URL में set करें। |
| `malformed` | Endpoint ने answer किया, लेकिन Jev answer के साथ नहीं — एक body जो JSON नहीं है, या एक जिसमें कोई answers नहीं हैं। |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflare के envelope ने एक failure report किया, या एक job जो finish नहीं हुई थी। |
| `model-mismatch` | Jev के 1.13 के अलावा अन्य version ने answer किया, या एक `custom` endpoint ने नहीं कहा कि कौन सा model answered। |
| `request-cut` | **एक outage नहीं।** Jev ने answer किया; इसे केवल call का एक part दिखाया गया था, इसलिए इसके answer ने कुछ नहीं clear किया। [When Jev answered, but not on the whole call](#when-jev-answered-but-not-on-the-whole-call) देखें। |

`failproofai jev status` कुछ rarer reasons को भी show कर सकता है, जैसे `upstream-error` (answer को provider की अपनी error carry किया) या `config`, और किसी भी reason को जिसका नाम नहीं दे सकता है `other` के रूप में totals।

`request-cut` इस table में है क्योंकि `failproofai jev status` इसे rest के साथ totals, और क्योंकि यह भी हर deny को standing रखता है। यह इस table का एकमात्र reason है जो आपके provider के बारे में कुछ नहीं कहता: request arrived और Jev ने इसका answer दिया। इसके ऊपर हर row के विपरीत, वह answer अभी भी counts — Jev का अपना deny या warning regex result के ऊपर लागू होता है बजाय discarded होने के। तो उनका एक run मतलब calls arrive हो रहे हैं evaluator को बहुत बड़े पूरे भेजने के लिए, न कि यह कि आपका endpoint unwell है, और topping up credits या URL को change करना संख्या को नहीं move करेगा।

## जब Jev ने answer दिया, लेकिन पूरी call पर नहीं

दो और चीजें हो सकती हैं, और कोई भी Jev failing नहीं है answer देने के लिए। दोनों इस बारे में हैं कि call के कितने, या conversation के कितने, एक request में फिट हुए।

**Call के एक part को fit नहीं किया।** एक tool call एक fixed budget के अंदर send किया जाता है, और एक oversized — एक बहुत बड़ा `Write`, एक huge MCP body, एक command padded out to the cap — को send किया जाता है जो fit था। Jev अभी भी answer करता है, और इसका answer अभी भी counts: इसका अपना deny या warning usual के रूप में लागू होता है। क्या यह नहीं कर सकता है **clear** कुछ भी, क्योंकि एक part पर दिया गया एक verdict call पर एक verdict नहीं है। तो हर policy deny stands, और call को reason `request-cut` के साथ एक fallback के रूप में record किया जाता है, जो `failproofai jev status` ऊपर के reasons के साथ totals। Rule यह आपको देता है: एक call को बड़ा बनाना इसके clearances की कीमत कर सकता है, और कभी एक खरीद नहीं सकता।

**एक message fit नहीं हुई।** एक long prompt आपने paste किया, agent का last message, या एक prompt यह evaluator का अपना store पहले से cap किया था। **कुछ नहीं बदलता है**: call को judge किया जाता है, cleared और record किया जाता है ठीक किसी अन्य की तरह, और यह एक fallback के रूप में count नहीं किया जाता है। आप type करते हैं कि length कभी एक verdict decide नहीं करता, और एक cut manufacture consent नहीं कर सकता: जहाँ एक prompt पहले से ही capped arrive हुई, "you did not ask for this" एक conclusion बनना बंद कर देता है जो drawing से किया जा सकता है, बजाय एक बनने के।

दोनों के बीच की line यह है कि किसने text लिखा। Call agent का है, और एक rule जो इसकी length को severity से subtract करने देता है एक rule है agent use कर सकता है; आपका prompt आपका है, और इसकी length को एक signal के रूप में treat करना केवल कभी एक spec या एक stack trace paste करने को punish करता है।

## क्या machine को छोड़ता है

प्रत्येक tool call के लिए Jev evaluate, एक request आपके provider को जाता है, carrying:

- tool call itself, secrets के साथ जैसे API keys, bearer tokens और `KEY=` assignments redacted;
- recent prompts आपने typed, आपके agent के harness ने added text के साथ;
- agent का last message आपके latest prompt से पहले, agent-written के रूप में labelled;
- facts computed locally, जैसे कि कोई path project के अंदर है — वह जिसमें session पहले reviewed call पर था, [pinned for the session](/hi/reference/jev-intent#the-project-root) — और current git branch।

यह केवल आपके config में endpoint को जाता है, आपकी key के तहत।

## इसे turn off करें

```bash
failproofai jev remove
```

यह `~/.failproofai/jev.json` को delete करता है। अगले tool call से, hooks regex policies को ठीक जैसे पहले चलाते हैं। `~/.failproofai/state/semantic/` के तहत per-session stores (recorded prompts `sessions/` में, project roots `roots/` में) को रखा जाता है और age out होते हैं। Jev पूछना बंद करने के लिए लेकिन config को रखने के लिए, `failproofai jev setup --mode off` का बजाय use करें।

## Command reference

| Command | Outcome |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | इसे एक command में configure करें; provider URL के host से आता है |
| `failproofai jev --url <url> --token <token>` | Same, command line पर key के साथ — आपकी history और process list इसे देखते हैं |
| `failproofai jev setup --provider <kind> --key-stdin` | Config को stdin पर pipe किए गए key से write करें |
| `failproofai jev setup --provider <kind>` | Same, एक masked prompt पर key के लिए asking |
| `failproofai jev setup --key-from-env` | कोई key store न करें; per session `FAILPROOFAI_JEV_API_KEY` को read करें |
| `failproofai jev setup --mode observe` | Mode को switch करें (`enforce`, `observe` या `off`), stored key को रखते हुए |
| `failproofai jev setup --model <id>` / `--base-url <url>` | Model या API base को override करें; `default` override को clear करता है |
| `failproofai jev setup --timeout-ms <n>` | Per-call budget को change करें |
| `failproofai jev status [--json]` | Configuration, permissions और recent activity; key को कभी नहीं |
| `failproofai jev test [--json]` | एक live request: latency और version जो answered |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | Model ids जो endpoint का `/models` report करता है, configured को marking |
| `failproofai jev remove` | Config को delete करें; Jev off है |
