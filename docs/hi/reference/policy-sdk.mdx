कस्टम नीतियां आपके ट्रेसेस या ऑडिट्स से एक विफलता पैटर्न को एक निर्णय में बदल देती हैं जो एजेंट काम करते समय चलता है। एक नीति एक कार्रवाई की अनुमति दे सकती है, एजेंट को दिशानिर्देश दे सकती है, या कार्रवाई को अस्वीकार कर सकती है इससे पहले कि यह एक और घटना का कारण बने।

कस्टम नीति का उपयोग करें जब व्यवहार आपके टूल्स, पाथ्स, कमांड्स, वातावरण या संचालन नियमों पर निर्भर करता है। [बिल्ट-इन नीति कैटलॉग](/hi/policies/builtin-catalog) पहले जांचें ताकि आप किसी मौजूदा नियंत्रण को फिर से न बनाएं।

## कस्टम नीति लेखक

## एक संकीर्ण नियम से शुरू करें

यह नीति विनाशकारी Kubernetes कमांड्स को ब्लॉक करती है केवल जब कमांड उत्पादन को लक्ष्य करता है। उस सटीक विफलता मोड के बाहर सब कुछ `allow()` लौटाता है।

```ts
import { customPolicies, allow, deny } from "failproofai";

const DESTRUCTIVE_KUBECTL = /\bkubectl\s+(delete|replace)\b/i;
const PRODUCTION_TARGET = /(?:--context|--namespace|-n)\s+(prod|production)\b/i;

customPolicies.add({
  name: "block-destructive-production-kubectl",
  description: "Block destructive Kubernetes commands against production",
  match: { events: ["PreToolUse"] },
  fn: async ({ toolName, toolInput }) => {
    if (toolName !== "Bash") return allow();

    const command = String(toolInput?.command ?? "");
    if (!DESTRUCTIVE_KUBECTL.test(command)) return allow();
    if (!PRODUCTION_TARGET.test(command)) return allow();

    return deny(
      "Destructive production Kubernetes commands require the approved deployment workflow.",
    );
  },
});
```

अच्छी नीतियां एक वाक्य में समझाने के लिए काफी संकीर्ण होती हैं। दृश्यमान कार्रवाई से मेल खाएं—न कि इरादा जो आप आशा करते हैं कि एजेंट के पास है—और जैसे ही नियम लागू नहीं होता है `allow()` लौटाएं।

## एक निर्णय चुनें

| सहायक | परिणाम | इसका उपयोग कब करें |
| --- | --- | --- |
| `allow(reason?)` | ऑपरेशन जारी रहता है। | नीति लागू नहीं होती है या कार्रवाई सुरक्षित है। |
| `instruct(reason)` | ऑपरेशन जारी रहता है, और कारण उन हार्नेस पर एजेंट को दिया जाता है जिनके पास इसके लिए एक चैनल है। | आप एजेंट को एक बेहतर दृष्टिकोण की ओर ले जाना चाहते हैं बिना किसी अपरिवर्तनीय को लागू किए। |
| `deny(reason)` | ऑपरेशन हार्नेस और ईवेंट जोड़े पर ब्लॉक किया जाता है जिन्हें एक अवरुद्ध निर्णय को उपभोग करने के लिए सत्यापित किया गया है। | कार्रवाई आगे नहीं बढ़ नी चाहिए। |

उस एजेंट के लिए कारण लिखें जिसे पुनः प्राप्त करना होगा। समझाएं कि क्या पाया गया था और इसे इसके बजाय क्या करना चाहिए।

### जहां `instruct()` वास्तव में पहुंचता है

`instruct()` को हार्नेस में एक अतिरिक्त-संदर्भ चैनल की आवश्यकता होती है। छह हार्नेस के कुछ या सभी ईवेंट्स पर कोई नहीं है; वहां ऑपरेशन की अनुमति है और संदेश stderr में लिखा जाता है, जहां एजेंट इसे कभी नहीं पढ़ता है।

| हार्नेस | ईवेंट्स जो निर्देश दिलाते हैं |
| --- | --- |
| Claude, Codex, Copilot, Cursor, Devin, OpenCode | `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, और `PermissionRequest` इसे अतिरिक्त संदर्भ के रूप में ले जाते हैं। `Stop` और `SubagentStop` इसे पुनः प्रयास चैनल के माध्यम से ले जाते हैं। हर दूसरा ईवेंट एक संदेश उत्सर्जित करता है जिसे हार्नेस अनदेखा करता है। |
| Antigravity | केवल `UserPromptSubmit` और `Stop`। |
| Factory, Pi, OpenClaw | केवल `Stop`। |
| Hermes, Goose | कोई नहीं। हमेशा अनुमति दें और stderr नोट दें। |

कोई भी हार्नेस सभी 29 विहित ईवेंट्स को आग नहीं लगाता है, इसलिए पहली पंक्ति प्रत्येक द्वारा स्थापित द्वारा सीमित है—एक निर्देश केवल एक ईवेंट पर पहुंचता है जिसे वह हार्नेस वास्तव में आग लगाता है। किसी एक पर भरोसा करने से पहले [Agent harnesses](/hi/reference/harnesses) में प्रति हार्नेस स्थापित ईवेंट सेट जांचें।

<Warning>
  सुरक्षा सीमा के लिए `instruct()` का उपयोग न करें। Hermes और Goose पर यह कभी भी एजेंट तक नहीं पहुंचता है, और Antigravity, Factory, Pi, और OpenClaw पर यह टूल ईवेंट्स पर इस तक नहीं पहुंचता है। जब कार्रवाई को रोकना आवश्यक हो तो `deny()` का उपयोग करें।
</Warning>

## नीति ऑब्जेक्ट

```ts
customPolicies.add({
  name: "policy-name",
  description: "What this policy prevents",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => allow(),
});
```

| फील्ड | आवश्यक | विवरण |
| --- | --- | --- |
| `name` | हां | नीति के लिए स्थिर पहचानकर्ता। फाइलों में नामों को अद्वितीय रखें। |
| `description` | नहीं | नीति सूचियों और निर्णयों में दिखाया गया मानव-पठनीय उद्देश्य। |
| `match.events` | नहीं | ईवेंट प्रकार जो नीति को आह्वान करते हैं। `match` को छोड़ने से यह हर उपलब्ध ईवेंट के लिए आह्वान करता है। |
| `fn` | हां | सिंक्रोनस या एसिंक्रोनस फ़ंक्शन जो `allow`, `instruct`, या `deny` परिणाम लौटाता है। |

`fn` के अंदर टूल्स को फ़िल्टर करें। `match.toolNames` सार्वजनिक कस्टम-नीति प्रकार का हिस्सा नहीं है।

एक पैक के अंदर प्रकाशित एक नीति दो अतिरिक्त फील्ड, `category` और `defaultEnabled` ले सकती है। [एक फाइल से एक पैक तक](#from-a-file-to-a-pack) देखें।

## नीति संदर्भ

हर नीति को एक `PolicyContext` प्राप्त होता है।

| फील्ड | प्रकार | इसमें क्या है |
| --- | --- | --- |
| `eventType` | `HookEventType` | सामान्यीकृत ईवेंट वर्तमान में मूल्यांकन किया जा रहा है। |
| `toolName` | `string \| undefined` | विहित टूल नाम जैसे `Bash`, `Read`, `Write`, या `Edit`। |
| `toolInput` | `Record<string, unknown> \| undefined` | वर्तमान टूल कॉल के लिए विहित इनपुट। |
| `payload` | `Record<string, unknown>` | संपूर्ण सामान्यीकृत ईवेंट पेलोड। |
| `session` | `SessionMetadata \| undefined` | सेशन ID, कार्यशील निर्देशिका, प्रतिलिपि पथ, अनुमति मोड, और उपलब्ध होने पर हार्नेस मेटाडेटा। |
| `cli` | `string \| undefined` | स्रोत एजेंट हार्नेस, जैसे `claude`, `codex`, या `cursor`। |
| `params` | `Record<string, unknown>` | इस नीति के लिए पैरामीटर। एक बिल्ट-इन या एक पैक नीति एक स्कीमा घोषित करती है, और उपयोगकर्ता द्वारा कॉन्फ़िगर किए गए मान इसके डिफ़ॉल्ट्स पर मर्ज किए जाते हैं। एक कस्टम फाइल में एक नीति कोई स्कीमा घोषित नहीं करती है, इसलिए यह उपयोगकर्ता द्वारा इसके नाम के तहत कॉन्फ़िगर किया गया कुछ भी प्राप्त करता है, और जब कुछ नहीं है तो `{}`। |

हर वैकल्पिक मान को वास्तव में वैकल्पिक मानें। एजेंट संस्करण और ईवेंट प्रकार सभी समान फील्ड प्रदान नहीं करते हैं।

### सामान्य टूल इनपुट्स

Failproof AI समर्थित हार्नेस्स में सामान्य टूल्स को सामान्यीकृत करता है ताकि एक नीति आमतौर पर एक इनपुट आकार का उपयोग कर सके।

| टूल | सामान्य फील्ड्स |
| --- | --- |
| `Bash` | `command` |
| `Read` | `file_path` |
| `Write` | `file_path`, `content` |
| `Edit` | `file_path`, `old_string`, `new_string` |
| `Grep` | `pattern`, `path` |

रक्षात्मक जबरदस्ती का उपयोग करें क्योंकि टूल इनपुट मान `unknown` के रूप में टाइप किए गए हैं:

```ts
const command = String(ctx.toolInput?.command ?? "");
const filePath = String(ctx.toolInput?.file_path ?? "");
```

## ईवेंट चुनें

| ईवेंट | यह कब चलता है | विशिष्ट उपयोग |
| --- | --- | --- |
| `PreToolUse` | एक टूल निष्पादित होने से पहले। | कमांड्स, लेखन, पढ़ना और बाहरी कार्यों को ब्लॉक या मार्गदर्शन करें। यह गार्ड है। |
| `PostToolUse` | टूल के पहले से निष्पादित होने के बाद। | परिणाम का निरीक्षण या प्रतिस्थापन करें जो मॉडल पढ़ता है। यह साइड इफेक्ट को पूर्ववत नहीं कर सकता—लेखन या कमांड पहले से ही हुआ है—और बारह हार्नेस्स में से दस पर निर्णय कुछ भी रोक नहीं सकता। केवल Codex और Copilot इसका उपभोग करते हैं, और यहां तक कि वहां यह परिणाम को प्रतिस्थापित करता है जो मॉडल पढ़ता है बजाय कॉल को रोकने के। इसे कभी भी गार्ड के रूप में उपयोग न करें। |
| `PermissionRequest` | जब एजेंट अनुमति का अनुरोध करता है। | संगठन-विशिष्ट अनुमति नियम लागू करें। |
| `UserPromptSubmit` | एक सबमिट किए गए संकेत से पहले। | निषिद्ध निर्देशों को अस्वीकार करें या कार्यप्रवाह मार्गदर्शन जोड़ें। |
| `Stop` | जब एजेंट समाप्त करने का प्रयास करता है। | एक पहुंचने योग्य समाप्ति स्थिति की आवश्यकता है, जैसे एक स्थानीय सत्यापन चरण। |
| `SubagentStop` | जब एक उप-एजेंट समाप्त करने का प्रयास करता है। | माता-पिता को वापस आने से पहले प्रतिनिधि कार्य को गेट करें। |
| `SessionStart` / `SessionEnd` | सेशन सीमाओं पर। | सत्र-स्तरीय स्थिति रिकॉर्ड या जांच करें। |

ईवेंट उपलब्धता और अवरुद्ध व्यवहार एजेंट हार्नेस पर निर्भर करते हैं, और अंतर बड़े हैं: Failproof AI Goose या Hermes के लिए कोई `Stop` हुक स्थापित नहीं करता है, इसलिए एक स्टॉप गेट कभी भी या तो पर आग नहीं लगता है। एक मिश्रित बेड़े पर किसी ईवेंट पर भरोसा करने से पहले [Agent harnesses](/hi/reference/harnesses) देखें।

<Accordion title="सभी नीति ईवेंट नामों">
  `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `Elicitation`, `ElicitationResult`, `UserPromptExpansion`, `PostToolBatch`, और `Setup`। यह 29 विहित ईवेंट नामों का पूर्ण सेट है जिसमें हर हार्नेस के अपने ईवेंट शब्दावली सामान्यीकृत है।
</Accordion>

## सामान्य नीति पैटर्न लेखक

### संरक्षित पाथ्स पर लेखन को ब्लॉक करें

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "block-generated-file-edits",
  description: "Require generated files to be changed through their generator",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();

    const filePath = String(ctx.toolInput?.file_path ?? "");
    if (!/(^|\/)(dist|generated)\//.test(filePath)) return allow();

    return deny("Edit the source and run the generator instead of changing generated output.");
  },
});
```

### गैर-अवरुद्ध मार्गदर्शन दें

```ts
import { customPolicies, allow, instruct } from "failproofai";

customPolicies.add({
  name: "prefer-reviewed-deploy-command",
  description: "Guide agents toward the reviewed deployment wrapper",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();

    const command = String(ctx.toolInput?.command ?? "");
    if (!/^kubectl\s+apply\b/.test(command.trim())) return allow();

    return instruct("Use ./scripts/deploy-reviewed instead of invoking kubectl directly.");
  },
});
```

### गेट सेशन समाप्ति

```ts
import { execFileSync } from "node:child_process";
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "require-clean-typecheck",
  description: "Require the project typecheck to pass before the agent finishes",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow();

    try {
      execFileSync("bunx", ["tsc", "--noEmit"], {
        cwd,
        stdio: "ignore",
        timeout: 8_000,
      });
      return allow();
    } catch {
      return deny("Fix the typecheck errors before finishing the task.");
    }
  },
});
```

<Warning>
  एक अस्वीकृत `Stop` ईवेंट एजेंट को फिर से प्रयास कर सकता है। केवल एक शर्त पर गेट करें जिसे एजेंट वर्तमान वातावरण में संतुष्ट कर सकता है, और हर उप-प्रक्रिया या नेटवर्क कॉल को बाध्य करें।
</Warning>

## लोड नीति फाइलें

### सम्मेलन फाइलें

सम्मेलन फाइलें स्वचालित रूप से लोड होती हैं:

```text
<project>/.failproofai/policies/security-policies.ts
~/.failproofai/policies/personal-policies.mjs
```

- प्रोजेक्ट और उपयोगकर्ता नीति निर्देशिकाएं दोनों लोड की जाती हैं।
- फाइलें प्रत्येक निर्देशिका के भीतर वर्णानुक्रमिक रूप से लोड होती हैं।
- एक फाइल `policies.js`, `policies.mjs`, या `policies.ts` में समाप्त होनी चाहिए।
- एक फाइल में कई `customPolicies.add()` कॉल समर्थित हैं।
- स्थानीय मॉड्यूल्स से सापेक्ष आयात समर्थित हैं।
- प्रोजेक्ट नीतियों को प्रतिबद्ध किया जा सकता है ताकि एक ही नियम रिपोजिटरी का पालन करें।

<Warning>
  निर्देशिका में एक फाइल जिसका नाम `policies.{js,mjs,ts}` में समाप्त नहीं होता है वह छोड़ दी जाती है। यह स्थापित दिखता है और कोई भी नीति लागू नहीं करता है। लोडर हर छोड़ी गई फाइल को सूचीबद्ध करता है इसे नाम बदलने के लिए कहने वाले नाम के साथ; उस चेतावनी को पढ़ें बजाय यह मान लें कि एक नीति सक्रिय है। यह रिपोजिटरी `block-version-bumps.mjs` उस तरीके से भेज गई, और एक खराब संस्करण बम्प के बाद लिखा गया गार्ड कभी भी एक बार नहीं चला था।
</Warning>

`~/.failproofai/policies/` में भी दो उप-निर्देशिकाएं हैं जिन्हें आपने वहां नहीं रखा: `cloud-policies/` फ्लीट-प्रबंधित तैनाती के लिए और `packs/` स्थापित पैक्स के लिए। लोडर कभी भी या तो में नहीं जाता है, इसलिए इनमें कुछ भी एक अयोग्य सम्मेलन नीति के रूप में नहीं उठाया जाता है।

### एक खोजी गई नीति को बंद करें

`policies-config.json` में दो कुंजियां फाइल को हटाए या नाम बदले बिना सम्मेलन नीतियों को बंद कर देती हैं:

| कुंजी | प्रभाव |
| --- | --- |
| `disabledCustomPolicies` | स्रोत-योग्य नीति ID की एक सरणी जो पंजीकृत नहीं हैं। |
| `customPoliciesEnabled` | `.failproofai/policies/` को लोड करना बंद करने के लिए `false` सेट करें। अनुपस्थित मतलब सक्षम। |

[स्थानीय डैशबोर्ड](/hi/reference/local-dashboard) का **Policies → Configure** टैब आपके लिए `disabledCustomPolicies` लिखता है। `customPoliciesEnabled` `failproofai config` द्वारा या हाथ से लिखा जाता है।

### स्पष्ट फाइलें

स्पष्ट पाथ्स का उपयोग करें जब मान्यता या कॉन्फ़िगरेशन को सीधे एंट्री फाइल का नाम देना चाहिए:

```bash
failproofai policies --install \
  --custom ./security.policies.ts \
  --custom ./workflow.policies.ts \
  --scope project
```

स्पष्ट फाइलें पहले लोड होती हैं, इसके बाद प्रोजेक्ट सम्मेलन फाइलें और फिर उपयोगकर्ता सम्मेलन फाइलें। दोनों पाथ्स के माध्यम से खोजी गई एक फाइल एक बार लोड होती है।

## मान्य करें और परीक्षण करें

`-c` `--custom` का संक्षिप्त रूप है, और `-i` `--install`। यह अभी फाइल को लागू करता है, किसी भी पथ पर और किसी भी फ़ाइलनाम के तहत:

```bash
failproofai policies -i -c ./checkout-policies.ts
failproofai policies
```

अपने एजेंट को आपके द्वारा अवरुद्ध किया गया कार्य करने के लिए कहें और देखें कि यह अस्वीकार कर दिया गया है। कुछ भी प्रकाशित नहीं किया जाता है और कोई अन्य मशीन प्रभावित नहीं होती है।

मान्यता उत्पादन लोडर के माध्यम से मॉड्यूल को निष्पादित करती है और पुष्टि करती है कि यह कम से कम एक नीति पंजीकृत करता है। यह लापता फाइलें, सिंटैक्स त्रुटियां, अनसुलझे आयात, शीर्ष-स्तर अपवाद, और मॉड्यूल-लोड टाइमआउट को पकड़ता है। यह साबित नहीं करता है कि आपका मिलान तर्क सही है।

कम से कम इन मामलों का परीक्षण करें:

- एक कार्रवाई जो मेल खानी चाहिए और अभिप्रेत नीति कारण का उत्पादन करना चाहिए।
- एक पास की कार्रवाई जो `allow()` लौटानी चाहिए।
- लापता या गलत-रूपांकित टूल फील्ड्स।
- वैकल्पिक कमांड सिंटैक्स, पाथ्स, उद्धरण, केसिंग, और व्हाइटस्पेस।
- एक अनुपलब्ध उप-प्रक्रिया या नेटवर्क निर्भरता।

स्थानीय डैशबोर्ड पर **Policies → Activity** के तहत अपनी कस्टम नीति को परिणाम में परिवर्तित करें। एक अवरुद्ध परीक्षण पर्याप्त नहीं है यदि एक अन्य बिल्ट-इन नीति ने निर्णय लिया है।

## रनटाइम व्यवहार

- बिल्ट-इन नीतियां कस्टम नीतियों से पहले मूल्यांकन करती हैं।
- पहला `deny` आगे की नीति मूल्यांकन को रोकता है।
- कई `instruct` परिणाम जब कोई नीति ईवेंट को अस्वीकार नहीं करती है तो संयोजित किया जा सकता है।
- एक नीति फ़ंक्शन के पास 10-सेकंड निष्पादन समय सीमा है। शीर्ष-स्तर मॉड्यूल लोडिंग में समान समय सीमा है।
- एक फेंके गए अपवाद या टाइमआउट को लॉग किया जाता है और `allow()` के रूप में माना जाता है।
- एक सम्मेलन फाइल जो लोड नहीं हो सकती है वह छोड़ दी जाती है; अन्य कस्टम फाइलें और बिल्ट-इन नीतियां जारी रहती हैं।
- Observe मोड नीति को वास्तव में चलाता है और किसी भी गैर-अनुमति निर्णय को लागू किए बिना रिकॉर्ड करता है। दो परतें इसे सेट करती हैं: `failproofai publish --effect observe` एक पैक पर आप प्रकाशित करते हैं, और `fp fleet deploy <machine> --add <id>:observe` एक Cloud तैनाती पर। या तो तरीका नीति को एक लागू करने वाले के समान 10-सेकंड समय सीमा के तहत मूल्यांकन किया जाता है, इसलिए एक नीति जो टाइमआउट हो जाती है अनुमति के रूप में रिकॉर्ड करती है।

### जहां लोडर के बजाय बंद विफल हो जाता है

ऊपर दिए गए फेल-ओपन नियम को आप अपने आप में हटाई गई एक फाइल को कवर करते हैं। दो पाथ्स जानबूझकर विपरीत करते हैं, क्योंकि दोनों का अर्थ है कि इस मशीन को उस प्रवर्तन का कहा गया था जिसके पास यह नहीं है।

| स्थिति | परिणाम |
| --- | --- |
| एक चयनित पैक लोड नहीं कर सकता है, या इसका पिन किया गया डाइजेस्ट मेल नहीं खाता | उस पैक के दायरे में हर ईवेंट अस्वीकार कर दिया जाता है, जिसे `pack/failproofai-pack-unavailable` को दिया जाता है। `UserPromptSubmit` अस्वीकार करने के बजाय निर्देश देता है, इसलिए आप कभी भी एजेंट से बाहर नहीं रहते हैं जिसे आपको इसे ठीक करने की आवश्यकता है। अपठनीय पैक मेटाडेटा अस्वीकृत दायरे को संकीर्ण करने के बजाय चौड़ा करता है। |
| `failproofaid` डेमन एक मशीन पर नहीं पहुंचा जा सकता है जिसने सेटअप पूरा कर लिया | हर ईवेंट अस्वीकार कर दिया जाता है। कोई कॉन्फ़िगरेशन पढ़ा नहीं जाता है और कोई कस्टम नीति नहीं चलती है, क्योंकि एक डेमन जो नहीं पहुंचा जा सकता था उनके साथ नहीं चल सकता था। एक प्रोटोकॉल-संस्करण बेमेल भी अस्वीकार करता है, जिसमें `failproofai config` नाम देने वाला संदेश है। |

एक मशीन पर जिसने सेटअप पूरा कर लिया है, `failproofaid` एकमात्र मूल्यांकनकार है, इसलिए आपका `fn` डेमन के गर्म कार्यकर्ता के अंदर हुक प्रक्रिया में चलता है। हुक क्लाइंट को कनेक्ट करने के लिए 150 एमएस और जवाब के लिए 30 सेकंड देता है, प्रत्येक नीति फ़ंक्शन को मिलने वाली निश्चित 10-सेकंड समय सीमा से ऊपर।

नीति मॉड्यूल्स निर्धारक और तेज़ रखें। शीर्ष-स्तर नेटवर्क कॉल्स या सर्वर स्टार्टअप से बचें। `fn` के अंदर कार्य को बाध्य करें, निर्भरता विफलताओं को पकड़ें, और जानबूझकर चुनें कि क्या यह विफलता ऑपरेशन को अनुमति देनी चाहिए या अस्वीकार करनी चाहिए।

## एक फाइल से एक पैक तक

एक पैक यह है कि एक नीति फाइल कैसे कुछ ऐसी बन जाती है जिसे अन्य मशीनें स्थापित कर सकती हैं। दो कमांड्स आपको कुछ नहीं से प्रकाशित पैक तक ले जाते हैं:

```bash
failproofai publish --init
failproofai publish
```

`--init` पूछता है कि पैक को क्या कहा जाता है, `<name>.mjs` लिखता है, और रुकता है। फाइल खाली के साथ एक टेम्पलेट नहीं है—यह एक नीति है जो पहले से ही `git push --force` को ब्लॉक करती है, इसलिए पहली चीज़ जिसे आप संपादित करते हैं वह कुछ है जो काम करता है। इसे `failproofai policies -i -c ./<name>.mjs` के साथ स्थानीय रूप से साबित करें, फिर इसे पकड़ने वाली git रिपोजिटरी के अंदर से `failproofai publish` चलाएं।

दो फील्ड्स मायने रखती हैं एक बार जब एक नीति एक पैक में भेज दी जाती है:

| फील्ड | यह क्या करता है |
| --- | --- |
| `category` | क्या `failproofai policies add <owner>/<repo> --category git,database` पर चुनता है। |
| `defaultEnabled` | क्या एक साधारण `failproofai policies add <owner>/<repo>` यह नीति चालू करता है। डिफ़ॉल्ट्स `false` को। |

`--effect` प्रति नीति के बजाय प्रति पैक सेट किया जाता है: `failproofai publish --effect observe` एक पैक प्रकाशित करता है जो अपनी नीतियों को क्या तय किया होगा इसे रिकॉर्ड करता है और कुछ भी ब्लॉक नहीं करता है। डिफ़ॉल्ट `enforce` है। यह कोई Cloud कनेक्शन के साथ एक एकल मशीन पर observe मोड है — स्थानीय डैशबोर्ड पर **Policies → Activity** के तहत रिकॉर्ड की गई निर्णय को वापस पढ़ें।

पैक का संस्करण इसे 12-वर्ण छोटा कमीट sha है जिससे यह बनाया गया था, इसलिए `publish` git checkout के बाहर और गंदे पेड़ पर मना कर देता है। पूर्ण प्रवाह के लिए [Publish a pack](/hi/policies/publish-a-pack) देखें, और कैसे स्थापित एक संस्करण को हल करते हैं के लिए [Policy packs](/hi/policies/packs) देखें।

## API निर्यात

| निर्यात | उद्देश्य |
| --- | --- |
| `customPolicies.add(policy)` | मॉड्यूल लोड होने पर एक कस्टम नीति पंजीकृत करें। |
| `allow(reason?)` | ऑपरेशन की अनुमति दें। |
| `instruct(reason)` | ऑपरेशन की अनुमति दें और समर्थित जगह पर मार्गदर्शन प्रदान करें। |
| `deny(reason)` | ऑपरेशन को समर्थित जगह पर ब्लॉक करें। |
| `getCustomHooks()` | मॉड्यूल रजिस्ट्री में वर्तमान में पंजीकृत नीतियों को लौटाएं। |
| `clearCustomHooks()` | वह रजिस्ट्री साफ़ करें, मुख्य रूप से परीक्षण और लोडर्स के लिए। |

TypeScript `PolicyContext`, `PolicyResult`, `CustomHook`, `PolicyDecision`, और `PolicyFunction` निर्यात करता है।
