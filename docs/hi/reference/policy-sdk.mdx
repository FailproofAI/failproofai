कस्टम नीतियां आपके ट्रेस या ऑडिट से विफलता पैटर्न को एक निर्णय में परिणत करती हैं जो एजेंट काम करते समय चलता है। एक नीति एक कार्रवाई की अनुमति दे सकती है, एजेंट को मार्गदर्शन दे सकती है, या कार्रवाई को अस्वीकार कर सकती है इससे पहले कि यह एक और घटना का कारण बने।

कस्टम नीति का उपयोग तब करें जब व्यवहार आपके टूल्स, पाथ्स, कमांड्स, वातावरण या ऑपरेटिंग नियमों पर निर्भर करता है। [बिल्ट-इन नीति कैटलॉग](/hi/policies/builtin-catalog) पहले देखें ताकि आप किसी मौजूदा नियंत्रण को फिर से न बनाएं।

## कस्टम नीति लिखें

<Tabs>
  <Tab title="Dashboard">
    1. **Admin → policy editor** पर जाएं, **New policy** चुनें, और विफलता का वर्णन करें जिसे आप रोकना चाहते हैं।
    2. नीति स्रोत जोड़ें, फिर एडिटर में अपेक्षित मेलों और सुरक्षित गैर-मेलों का परीक्षण करें। हर वैलिडेशन त्रुटि को हल करें।
    3. ड्राफ्ट को सेव करें और **Publish version** चुनकर एक अपरिवर्तनीय संस्करण बनाएं।
    4. **Admin → enforcement** पर जाएं, संस्करण को **observe** मोड में एक परीक्षण मशीन पर तैनात करें, और इसे लागू करने से पहले **Observe → policy** के तहत अपने निर्णयों को सत्यापित करें।

## एक संकीर्ण नियम से शुरू करें

यह नीति विनाशकारी Kubernetes कमांड्स को केवल तब ब्लॉक करती है जब कमांड प्रोडक्शन को लक्षित करता है। उस सटीक विफलता मोड के बाहर सब कुछ `allow()` रिटर्न करता है।

```ts
import { customPolicies, allow, deny } from "failproofai";

const DESTRUCTIVE_KUBECTL = /\bkubectl\s+(delete|replace)\b/i;
const PRODUCTION_TARGET = /(?:--context|--namespace|-n)\s+(prod|production)\b/i;

customPolicies.add({
  name: "block-destructive-production-kubectl",
  description: "Block destructive Kubernetes commands against production",
  match: { events: ["PreToolUse"] },
  fn: async ({ toolName, toolInput }) => {
    if (toolName !== "Bash") return allow();

    const command = String(toolInput?.command ?? "");
    if (!DESTRUCTIVE_KUBECTL.test(command)) return allow();
    if (!PRODUCTION_TARGET.test(command)) return allow();

    return deny(
      "Destructive production Kubernetes commands require the approved deployment workflow.",
    );
  },
});
```

अच्छी नीतियां एक वाक्य में समझाने के लिए काफी संकीर्ण हैं। अवलोकनीय कार्रवाई से मेल खाएं—उस आशय से नहीं जो आप आशा करते हैं कि एजेंट के पास है—और जैसे ही नियम लागू नहीं होता है `allow()` रिटर्न करें।

## एक निर्णय चुनें

| हेल्पर | परिणाम | इसका उपयोग करें जब |
| --- | --- | --- |
| `allow(reason?)` | ऑपरेशन जारी रहता है। | नीति लागू नहीं होती है या कार्रवाई सुरक्षित है। |
| `instruct(reason)` | ऑपरेशन जहां हार्नेस इसका समर्थन करता है वहां मार्गदर्शन के साथ जारी रहता है। | आप एजेंट को एक बेहतर दृष्टिकोण की ओर निर्देशित करना चाहते हैं बिना एक अपरिवर्तनीय को लागू किए। |
| `deny(reason)` | ऑपरेशन को ब्लॉक किया जाता है जब इवेंट और हार्नेस ब्लॉकिंग का समर्थन करते हैं। | कार्रवाई को आगे नहीं बढ़ना चाहिए। |

एजेंट के लिए कारण लिखें जिसे पुनः प्राप्त करना चाहिए। समझाएं कि क्या पता चला और इसे इसके बजाय क्या करना चाहिए।

<Warning>
  सुरक्षा सीमा के लिए `instruct()` का उपयोग न करें। मार्गदर्शन वितरण एजेंट हार्नेस द्वारा भिन्न होता है। `deny()` का उपयोग करें जब कार्रवाई को रोका जाना चाहिए।
</Warning>

## नीति ऑब्जेक्ट

```ts
customPolicies.add({
  name: "policy-name",
  description: "What this policy prevents",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => allow(),
});
```

| फील्ड | आवश्यक | विवरण |
| --- | --- | --- |
| `name` | हां | नीति के लिए स्थिर पहचान। नामों को फाइलों में अद्वितीय रखें। |
| `description` | नहीं | मानव-पठनीय उद्देश्य नीति सूचियों और निर्णयों में दिखाई देता है। |
| `match.events` | नहीं | इवेंट प्रकार जो नीति को आमंत्रित करते हैं। `match` को छोड़ने से यह हर उपलब्ध इवेंट के लिए आमंत्रित होता है। |
| `fn` | हां | सिंक्रोनस या एसिंक्रोनस फंक्शन जो `allow`, `instruct` या `deny` परिणाम रिटर्न करता है। |

`fn` के अंदर टूल्स को फ़िल्टर करें। `match.toolNames` सार्वजनिक कस्टम-नीति प्रकार का हिस्सा नहीं है।

## नीति संदर्भ

हर नीति को एक `PolicyContext` प्राप्त होता है।

| फील्ड | प्रकार | इसमें क्या है |
| --- | --- | --- |
| `eventType` | `HookEventType` | वर्तमान में मूल्यांकन किया जा रहा सामान्यीकृत इवेंट। |
| `toolName` | `string \| undefined` | कैनोनिकल टूल नाम जैसे `Bash`, `Read`, `Write` या `Edit`। |
| `toolInput` | `Record<string, unknown> \| undefined` | वर्तमान टूल कॉल के लिए कैनोनिकल इनपुट। |
| `payload` | `Record<string, unknown>` | संपूर्ण सामान्यीकृत इवेंट पेलोड। |
| `session` | `SessionMetadata \| undefined` | सेशन ID, वर्किंग डायरेक्टरी, ट्रांसक्रिप्ट पाथ, अनुमति मोड और उपलब्ध होने पर हार्नेस मेटाडेटा। |
| `cli` | `string \| undefined` | स्रोत एजेंट हार्नेस, जैसे `claude`, `codex` या `cursor`। |
| `params` | `Record<string, unknown>` | बिल्ट-इन नीति पैरामीटर। कस्टम नीतियों को वर्तमान में एक खाली ऑब्जेक्ट प्राप्त होता है। |

हर ऑप्शनल वैल्यू को वास्तव में ऑप्शनल मानें। एजेंट संस्करण और इवेंट प्रकार सभी एक जैसे फील्ड प्रदान नहीं करते हैं।

### सामान्य टूल इनपुट्स

Failproof AI आम टूल्स को समर्थित हार्नेस में सामान्यीकृत करता है ताकि एक नीति आमतौर पर एक इनपुट शेप का उपयोग कर सके।

| टूल | सामान्य फील्ड्स |
| --- | --- |
| `Bash` | `command` |
| `Read` | `file_path` |
| `Write` | `file_path`, `content` |
| `Edit` | `file_path`, `old_string`, `new_string` |
| `Grep` | `pattern`, `path` |

रक्षात्मक बाध्यकारी का उपयोग करें क्योंकि टूल इनपुट वैल्यूज को `unknown` के रूप में टाइप किया जाता है:

```ts
const command = String(ctx.toolInput?.command ?? "");
const filePath = String(ctx.toolInput?.file_path ?? "");
```

## इवेंट चुनें

| इवेंट | कब चलता है | विशिष्ट उपयोग |
| --- | --- | --- |
| `PreToolUse` | टूल निष्पादित होने से पहले। | कमांड्स, लिखे जाने, पढ़े जाने और बाहरी कार्रवाइयों को ब्लॉक या मार्गदर्शन करें। |
| `PostToolUse` | टूल रिटर्न करने के बाद। | परिणामों का निरीक्षण करें इससे पहले कि वे एजेंट तक पहुंचें। एक deny पूरे परिणाम को ब्लॉक करता है; यह चयनित फील्ड्स को संपादित नहीं करता है। |
| `PermissionRequest` | जब एजेंट अनुमति का अनुरोध करता है। | संगठन-विशिष्ट अनुमति नियमों को लागू करें। |
| `UserPromptSubmit` | जमा किए गए प्रॉम्प्ट से पहले जारी रहता है। | निषिद्ध निर्देशों को अस्वीकार करें या वर्कफ़्लो मार्गदर्शन जोड़ें। |
| `Stop` | जब एजेंट समाप्त करने का प्रयास करता है। | एक पहुंच योग्य समापन स्थिति की आवश्यकता होती है, जैसे एक स्थानीय सत्यापन चरण। |
| `SubagentStop` | जब एक सबएजेंट समाप्त करने का प्रयास करता है। | माता-पिता को वापस करने से पहले प्रतिनिधि कार्य को गेट करें। |
| `SessionStart` / `SessionEnd` | सेशन सीमाओं पर। | सेशन-स्तरीय स्थिति को रिकॉर्ड करें या जांचें। |

इवेंट उपलब्धता और ब्लॉकिंग व्यवहार एजेंट हार्नेस पर निर्भर करता है। मिश्रित फ्लीट में एक इवेंट पर निर्भर करने से पहले [एजेंट हार्नेस](/hi/reference/harnesses) देखें।

<Accordion title="सभी नीति इवेंट नाम">
  `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `Elicitation`, `ElicitationResult`, `UserPromptExpansion`, `PostToolBatch` और `Setup`।

## सामान्य नीति पैटर्न लिखें

### सुरक्षित पाथ्स को लिखने में ब्लॉक करें

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "block-generated-file-edits",
  description: "Require generated files to be changed through their generator",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();

    const filePath = String(ctx.toolInput?.file_path ?? "");
    if (!/(^|\/)(dist|generated)\//.test(filePath)) return allow();

    return deny("Edit the source and run the generator instead of changing generated output.");
  },
});
```

### गैर-ब्लॉकिंग मार्गदर्शन दें

```ts
import { customPolicies, allow, instruct } from "failproofai";

customPolicies.add({
  name: "prefer-reviewed-deploy-command",
  description: "Guide agents toward the reviewed deployment wrapper",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();

    const command = String(ctx.toolInput?.command ?? "");
    if (!/^kubectl\s+apply\b/.test(command.trim())) return allow();

    return instruct("Use ./scripts/deploy-reviewed instead of invoking kubectl directly.");
  },
});
```

### गेट सेशन समापन

```ts
import { execFileSync } from "node:child_process";
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "require-clean-typecheck",
  description: "Require the project typecheck to pass before the agent finishes",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow();

    try {
      execFileSync("bunx", ["tsc", "--noEmit"], {
        cwd,
        stdio: "ignore",
        timeout: 8_000,
      });
      return allow();
    } catch {
      return deny("Fix the typecheck errors before finishing the task.");
    }
  },
});
```

<Warning>
  एक इनकार किया गया `Stop` इवेंट एजेंट को पुनः प्रयास कर सकता है। केवल एक शर्त पर गेट करें जिसे एजेंट वर्तमान वातावरण में संतुष्ट कर सकता है, और हर सबप्रोसेस या नेटवर्क कॉल को बाध्य करें।
</Warning>

## नीति फाइलें लोड करें

### परंपरा फाइलें

परंपरा फाइलें स्वचालित रूप से लोड होती हैं:

```text
<project>/.failproofai/policies/security-policies.ts
~/.failproofai/policies/personal-policies.mjs
```

- प्रोजेक्ट और उपयोगकर्ता नीति निर्देशिकाएं दोनों लोड की जाती हैं।
- फाइलें हर निर्देशिका के भीतर वर्णक्रमानुसार लोड होती हैं।
- एक फाइल को `policies.js`, `policies.mjs` या `policies.ts` में समाप्त होना चाहिए।
- एक फाइल में कई `customPolicies.add()` कॉल समर्थित हैं।
- स्थानीय मॉड्यूल से सापेक्ष आयात समर्थित हैं।
- प्रोजेक्ट नीतियों को प्रतिबद्ध किया जा सकता है ताकि समान नियम रिपॉजिटरी का पालन करें।

### स्पष्ट फाइलें

स्पष्ट पाथ्स का उपयोग करें जब वैलिडेशन या कॉन्फ़िगरेशन को प्रवेश फाइल का नाम सीधे देना चाहिए:

```bash
failproofai policies --install \
  --custom ./security.policies.ts \
  --custom ./workflow.policies.ts \
  --scope project
```

स्पष्ट फाइलें पहले लोड होती हैं, फिर प्रोजेक्ट परंपरा फाइलें और फिर उपयोगकर्ता परंपरा फाइलें। दोनों पाथ्स के माध्यम से खोजी गई फाइल एक बार लोड होती है।

## वैलिडेट और परीक्षण करें

वैलिडेशन मॉड्यूल को उत्पादन लोडर के माध्यम से निष्पादित करता है और पुष्टि करता है कि यह कम से कम एक नीति को पंजीकृत करता है।

```bash
failproofai policies --install \
  --custom ./.failproofai/policies/checkout-policies.ts \
  --scope project
failproofai policies
```

वैलिडेशन अनुपलब्ध फाइलें, सिंटैक्स त्रुटियां, अनसुलझे आयात, शीर्ष-स्तर अपवाद और मॉड्यूल-लोड टाइमआउट को पकड़ता है। यह साबित नहीं करता कि आपका मैच लॉजिक सही है।

कम से कम इन मामलों का परीक्षण करें:

- एक कार्रवाई जो मेल खानी चाहिए और अभिप्रेत नीति कारण का उत्पादन करना चाहिए।
- एक पास की कार्रवाई जो सुरक्षित होनी चाहिए।
- गायब या गलत टूल फील्ड्स।
- वैकल्पिक कमांड सिंटैक्स, पाथ्स, उद्धरण, केसिंग और व्हाइटस्पेस।
- एक अनुपलब्ध सबप्रोसेस या नेटवर्क निर्भरता।

**Observe → policy** के तहत परिणाम को अपनी कस्टम नीति के लिए जिम्मेदार ठहराएं। एक ब्लॉक किया गया परीक्षण पर्याप्त नहीं है यदि एक अलग बिल्ट-इन नीति ने निर्णय लिया हो।

## रनटाइम व्यवहार

- बिल्ट-इन नीतियां कस्टम नीतियों से पहले मूल्यांकित होती हैं।
- पहला `deny` आगे की नीति मूल्यांकन को बंद करता है।
- कई `instruct` परिणामों को संयोजित किया जा सकता है जब कोई नीति इवेंट को अस्वीकार नहीं करती है।
- एक नीति फंक्शन के पास 10-सेकंड की निष्पादन समय सीमा है।
- एक फेंका गया अपवाद या टाइमआउट लॉग किया जाता है और `allow()` के रूप में माना जाता है।
- एक परंपरा फाइल जो लोड करने में विफल रहती है, छोड़ दी जाती है; अन्य कस्टम फाइलें और बिल्ट-इन नीतियां जारी रहती हैं।
- शीर्ष-स्तर मॉड्यूल लोडिंग का भी 10-सेकंड की समय सीमा है।
- क्लाउड observe मोड नीति चलाता है लेकिन बिना इसे लागू किए एक गैर-allow निर्णय रिकॉर्ड करता है।

नीति मॉड्यूल को नियतात्मक और तेज़ रखें। शीर्ष-स्तर नेटवर्क कॉल या सर्वर स्टार्टअप से बचें। `fn` के अंदर काम को बाध्य करें, निर्भरता विफलताओं को पकड़ें, और जानबूझकर चुनें कि यह विफलता ऑपरेशन की अनुमति दे या अस्वीकार करे।

## API निर्यात

| निर्यात | उद्देश्य |
| --- | --- |
| `customPolicies.add(policy)` | मॉड्यूल लोड होने पर एक कस्टम नीति को पंजीकृत करें। |
| `allow(reason?)` | ऑपरेशन को अनुमति दें। |
| `instruct(reason)` | ऑपरेशन को अनुमति दें और जहां समर्थित हो मार्गदर्शन प्रदान करें। |
| `deny(reason)` | जहां समर्थित हो ऑपरेशन को ब्लॉक करें। |
| `getCustomHooks()` | वर्तमान में मॉड्यूल रजिस्ट्री में पंजीकृत नीतियों को रिटर्न करें। |
| `clearCustomHooks()` | उस रजिस्ट्री को साफ करें, मुख्य रूप से परीक्षण और लोडर्स के लिए। |

TypeScript निर्यात `PolicyContext`, `PolicyResult`, `CustomHook`, `PolicyDecision` और `PolicyFunction`।
