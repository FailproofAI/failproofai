अस्थायी नेटवर्क विफलताएं और HTTP 408, 429, या 5xx प्रतिक्रियाएं दीर्घकालीन आउटेज के बाद भी स्वचालित पुनः प्रयास के लिए टेलीमेट्री को पात्र बनाती हैं। डेमन डिलीवरी की पुष्टि होने तक बैच को संरक्षित रखता है। `event_too_large` अस्वीकृति के लिए पुनः प्रयास करने से पहले एक छोटे इवेंट पेलोड की आवश्यकता होती है। `.poison` से चिह्नित फाइलों को मैनुअल रिकवरी की आवश्यकता है; अपडेट करने से वे स्वचालित रूप से पुनः भेजे नहीं जाते।

  <Accordion title="निजी प्रमाणपत्र प्राधिकरण के साथ एक स्व-होस्ट किए गए Cloud को कोई इवेंट या नीतियां नहीं मिलती हैं">
    <Tabs>
      <Tab title="Dashboard">
        मशीन जुड़ गई है और इसके हुक काम करते हैं, लेकिन **Observe → Events** खाली रहता है और **Admin → enforcement** कभी भी इसकी तैनाती को लागू के रूप में नहीं दिखाता है। CLI और Failproof डेमन प्रमाणपत्रों पर अलग-अलग विश्वास करते हैं। CLI Node पर चलता है और `NODE_EXTRA_CA_CERTS` को सम्मानित करता है। `failproofaid`, जो इवेंट भेजता है और नीतियां खींचता है, इसके साथ बंडल किए गए प्रमाणपत्रों पर विश्वास करता है साथ ही ऑपरेटिंग सिस्टम के विश्वास स्टोर पर, और `NODE_EXTRA_CA_CERTS` को नजरअंदाज करता है। मशीन पर सिस्टम स्टोर में अपने CA को स्थापित करें।
      </Tab>
      <Tab title="CLI">
        ```bash
        # Debian / Ubuntu
        sudo cp company-ca.pem /usr/local/share/ca-certificates/company-ca.crt
        sudo update-ca-certificates
        # RHEL / Fedora
        sudo cp company-ca.pem /etc/pki/ca-trust/source/anchors/ && sudo update-ca-trust
        # macOS
        sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain company-ca.pem

        # फिर डेमन को पुनः शुरू करें, जो शुरुआत पर विश्वस्त प्रमाणपत्र लोड करता है
        sudo systemctl restart failproofaid@$USER                           # Linux
        sudo launchctl kickstart -k system/ai.failproof.failproofaid.$USER  # macOS
        ```

        डेमन का लॉग कारण का नाम देता है: Linux पर `sudo journalctl -u failproofaid@$USER | grep UnknownIssuer`। सेवा के पर्यावरण में `SSL_CERT_FILE` या `SSL_CERT_DIR` डेमन के लिए सिस्टम स्टोर को प्रतिस्थापित करता है, और बंडल किए गए प्रमाणपत्र अभी भी लागू होते हैं। जो बैच CA अविश्वस्त होने के दौरान विफल हुए, वे `~/.failproofai/state/failed` में रखे जाते हैं और स्वचालित रूप से पुनः प्रयास किए जाते हैं, लगभग हर घंटे और जब डेमन पुनः शुरू होता है।
      </Tab>
    </Tabs>
  </Accordion>

      </Tab>

    </Tabs>

        यदि एक पूरा पृष्ठ लोड करने में विफल हो जाता है, तो त्रुटि पृष्ठ एक `digest` दिखाता है। इसे शामिल करें।

        ```bash
        fp --json sessions --since 24h
        ```
      </Tab>
      <Tab title="Daemon">
        जब अपलोड विफल होता है, तो डेमन का लॉग एक `request_id` और एक `batch_id` का नाम देता है: Linux पर, `sudo journalctl -u failproofaid@$USER | grep batch_id`। प्रत्येक प्रयास को अपना `request_id` मिलता है; `batch_id` पुनः प्रयासों में समान रहता है, इसलिए यह एक बैच के प्रयासों को एक साथ बांधता है। दोनों को शामिल करें।
