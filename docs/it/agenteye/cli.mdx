Gestisci tutta l'Osservabilità di Failproof AI dal terminale o da uno script: nessuna navigazione nel dashboard. La CLI `agenteye` interroga i tuoi dati (sessioni, event log, valutazioni) e amministra la tua organizzazione (chiavi API, utenti, impostazioni, avvisi, incidenti, query salvate), quindi usala quando vuoi automatizzare un controllo, integrare l'Osservabilità nella CI, o lasciare che un agente di codifica ispezionare la produzione. Ogni comando supporta un flag `--json`, quindi funziona altrettanto bene per te da una riga di comando o per un agente di codifica (Claude Code, Cursor) che esegue il parsing del risultato.

Con un solo binario puoi:

- **Leggere i tuoi dati**: `sessions`, `events`, `evals`, `errors` (filtra per tempo, agente, ambiente, score).
- **Gestire la tua organizzazione**: `keys`, `users`, `settings`, `alerts`, `incidents`.
- **Eseguire analitiche**: SQL salvati e un runner di query ad hoc (`query`).
- **Chiedere all'assistente IA**: lo stesso analista di sola lettura con cui chatti nel dashboard (`agent`).

> **Nota:** Questa è la CLI `agenteye`, uno strumento diverso dal daemon del collector (`agenteye-collector`). La CLI comunica con il tuo dashboard; il collector invia gli eventi al server.

## Avvio rapido

Da zero al tuo primo risultato in quattro righe. Punta la CLI al tuo dashboard, accedi, conferma chi sei, quindi estrai l'ultimo giorno di esecuzioni:

```bash
pipx install agenteye
agenteye --base-url https://agenteye.example.com login --email you@example.com   # codice a 6 cifre inviato per email
agenteye whoami                                                                  # conferma utente + organizzazione attiva
agenteye --json sessions --since 24h                                             # una riga per esecuzione dell'agente, ultimi 24h
```

L'ultimo comando stampa un oggetto JSON delle sessioni più recenti (il più nuovo prima, massimo 50 per impostazione predefinita). Passalo a `jq` per suddividerlo, oppure elimina `--json` per una tabella con bordi e colorata. Ogni riga contiene lo stato dell'esecuzione e, se un valutatore l'ha valutata, i suoi score metrici (abbreviati qui):

```json
{
  "sessions": [
    {
      "session_id": "run-8f2a",
      "agent_id": "checkout-bot",
      "environment": "prod",
      "status": "error",
      "scores": { "helpfulness": 0.42, "tool_efficiency": 0.55 },
      "event_count": 37,
      "started_at": "2026-07-16T09:14:02Z",
      "last_event_at": "2026-07-16T09:14:48Z"
    }
  ],
  "next_cursor": null
}
```

## Installazione

La CLI è un pacchetto PyPI pubblico denominato **`agenteye`**. Installalo in un ambiente isolato in modo che abbia sempre le sue proprie dipendenze:

```bash
pipx install agenteye
# o
uv tool install agenteye
```

Richiede Python 3.10+. Il comando installato è **`agenteye`**:

```bash
agenteye --version
agenteye --help
```

> **Nota:** L'SDK Python di Failproof AI Observability utilizza anche il nome di distribuzione `agenteye`. Installare la CLI con `pipx` o `uv tool` (anziché `pip install` in un virtualenv condiviso) evita collisioni tra i due. Un semplice `pip install agenteye` va bene solo se l'SDK non è installato nello stesso ambiente.

## Autenticazione

La CLI si autentica al **dashboard** con un codice monouso inviato per email:

```bash
agenteye login --email you@example.com
# Un codice a 6 cifre ti viene inviato per email; incollalo al prompt.
```

Il token di sessione viene archiviato in `~/.agenteye/cli.json` (leggibile solo da te, modalità `0600`) ed è valido per 24 ore per impostazione predefinita. Quando scade, esegui di nuovo `agenteye login`.

```bash
agenteye whoami     # mostra l'utente corrente, l'organizzazione attiva e i permessi
agenteye logout     # revoca la sessione e cancella il token archiviato
```

`whoami` non genera mai errori con una sessione mancante o scaduta; invece segnala `logged_in: false`, quindi uno script o un agente può sondare lo stato dell'autenticazione in sicurezza (può comunque uscire con un codice di errore se non è impostato un URL di base o il dashboard non è raggiungibile).

**Requisiti:** la tua email deve essere autorizzata ad accedere al dashboard (chiedi all'amministratore di Failproof AI Observability), e il dashboard deve essere raggiungibile al suo URL di base (vedi [Configurazione](#configuration)). Se richiedi un codice e non arriva nessuno, la tua email probabilmente non è ancora abilitata per l'accesso al dashboard.

## Scelta della tua organizzazione (multi-tenant)

Se il tuo account appartiene a più di un'organizzazione, scegli quella attiva **al login**; viene salvata e utilizzata per ogni comando successivo:

```bash
agenteye login --org acme           # autentica e imposta il tenant attivo in un unico passaggio
agenteye orgs list                  # le organizzazioni a cui puoi accedere (quella attiva è contrassegnata)
agenteye orgs switch globex         # cambia il valore predefinito salvato
agenteye --org globex sessions      # sostituisci per un singolo comando
```

Se appartieni a esattamente un'organizzazione, viene selezionata automaticamente e puoi ignorare completamente `--org`. Se appartieni a diversi e non ne scegli uno, la CLI li elenca e ti chiede di eseguire nuovamente con `--org <slug>`. L'organizzazione attiva viene inviata al dashboard su ogni richiesta e i tuoi permessi vengono risolti **per organizzazione**; `agenteye whoami` mostra l'organizzazione attiva, i tuoi permessi in essa, e tutte le tue appartenenze.

## Configurazione

| Impostazione | Flag | Variabile d'ambiente | Valore predefinito |
|---|---|---|---|
| URL di base del dashboard | `--base-url` | `AGENTEYE_DASHBOARD_URL` | **obbligatorio** (nessun valore predefinito) |
| Organizzazione/tenant attivo | `--org` | `AGENTEYE_ORG` | scelto al login; salvato in `~/.agenteye/cli.json` |
| Token di sessione | `--token` | `AGENTEYE_CLI_TOKEN` | da `~/.agenteye/cli.json` |
| Output JSON | `--json` | `AGENTEYE_CLI_JSON` | disattivato |
| Salta verifica TLS | `--insecure` / `--secure` | `AGENTEYE_INSECURE` | disattivato (salvato al login) |
| Timeout della richiesta (secondi) | `--timeout` | _(nessuno)_ | 30 |
| Disabilita telemetria di utilizzo | _(nessuno)_ | `AGENTEYE_ANALYTICS_DISABLED` (o `DO_NOT_TRACK`) | la telemetria è attualmente disabilitata; nulla viene inviato |

L'ordine di risoluzione è **flag → variabile d'ambiente → file di configurazione**. Non c'è un valore predefinito; devi puntare la CLI al tuo dashboard, sia per comando (`--base-url https://agenteye.example.com`) che una volta tramite l'ambiente (viene anche salvato dopo il tuo primo `login`):

```bash
export AGENTEYE_DASHBOARD_URL=https://agenteye.example.com
```

La directory di configurazione rispetta `AGENTEYE_HOME` (la stessa convenzione utilizzata dall'SDK e dal collector); se impostato, `cli.json` risiede in `$AGENTEYE_HOME/cli.json`.

### TLS self-signed o interno

Se il tuo dashboard viene servito tramite HTTPS con un certificato self-signed o interno (ad esempio, un nome host raw del load balancer), la verifica TLS lo rifiuta con un errore `CERTIFICATE_VERIFY_FAILED`. Passa `--insecure` per saltare la verifica del certificato:

```bash
agenteye --base-url https://agenteye.internal --insecure login
```

`--insecure` viene **salvato in `cli.json` quando accedi**, quindi i comandi successivi saltano automaticamente la verifica; non devi ripetere il flag. Passa `--secure` per una chiamata verificata una tantum, o per salvare nuovamente la verifica al tuo prossimo login. La CLI stampa un avviso su stderr prima di qualsiasi comando che contatta il dashboard mentre la verifica è disabilitata. Saltare la verifica rimuove la protezione contro gli attacchi man-in-the-middle; assicurati di fidarti del percorso di rete verso il tuo dashboard (VPN, subnet privata, ecc.) prima di fare affidamento su di esso.

## Telemetria e privacy

> **Nota:** La CLI spedita **non invia alcuna telemetria di utilizzo oggi.** Un interruttore di arresto principale è attivato, quindi nulla viene trasmesso indipendentemente dal tuo ambiente. La sezione seguente descrive la capacità di opt-out per se e quando la telemetria venisse mai abilitata.

Anche se abilitata, la telemetria sarebbe **solo analitiche di utilizzo anonime**, mai i tuoi dati di agente, sessione o evento:

- **Nessun dato di agente, sessione o evento lascia mai la tua infrastruttura.** Verrebbe segnalato solo l'utilizzo della CLI: il nome del comando e del sottocomando (ad esempio `keys create`), i **nomi** dei flag utilizzati (mai i loro valori), stato di successo/uscita e durata, più un evento per azione per le mutazioni (ad esempio `api_key_created`, `query_run`) contenente solo nomi/enum statici e conteggi approssimativi. L'URL del tuo dashboard, il token di sessione, l'email, lo slug dell'organizzazione, gli id delle risorse, l'SQL, i segreti della chiave e i filtri di query non verrebbero **mai** inviati. Gli operatori sarebbero identificati solo da un id interno opaco, mai per email.
- **Escludi in anticipo** impostando `AGENTEYE_ANALYTICS_DISABLED=1` nell'ambiente della CLI (la CLI rispetta anche la convenzione cross-tool `DO_NOT_TRACK=1`). Questo ha effetto nel momento in cui la telemetria viene mai attivata, quindi un ambiente consapevole della privacy può rimanere escluso permanentemente.
- Se la telemetria fosse abilitata, la CLI invierebbe direttamente a PostHog (`https://us.i.posthog.com`); una macchina con quell'host bloccato non invierebbe silenziosamente nulla e la CLI sarebbe inalterata.

## Opzioni globali e convenzioni

Leggi una volta; si applica a ogni comando.

- **Le opzioni globali vanno PRIMA del comando.** `agenteye --json sessions` è corretto; `agenteye sessions --json` è un errore di utilizzo. Le opzioni globali sono `--json`, `--base-url`, `--org`, `--token`, `--insecure`/`--secure`, `--timeout`, `--quiet`, e `--no-color`.
- **`--json` stampa JSON puro su stdout, e nulla altro.** Le righe di stato umane, gli avvisi e gli errori vanno su **stderr**, quindi un'acquisizione stdout di `--json` rimane pulita per il piping in `jq` anche quando viene mostrata una riga di stato. Senza `--json` ottieni una vista con bordi e colorata per gli occhi umani.
- **Scopri con `--help`.** Ogni comando e sottocomando ha `--help` (e l'alias `-h`): `agenteye -h`, `agenteye sessions -h`, `agenteye keys create -h`. L'aiuto di livello superiore elenca anche i codici di uscita e le opzioni globali. Non c'è un dump di superficie leggibile da macchina globale; usa `--help` per comando, più `agenteye query schema` e `agenteye settings schema` specifici del dominio per questi due registri.
- **Le conferme si saltano automaticamente per script e agenti.** I comandi crea/aggiorna/elimina richiedono "sei sicuro?" in un terminale interattivo, ma **saltano automaticamente quel prompt sotto `--json` o quando stdin non è un TTY** (un TTY è una sessione terminale interattiva; una pipe o un runner CI non lo è), quindi script e agenti non si bloccano mai. Passa `--yes`/`-y` per saltarlo esplicitamente. Poiché il prompt non si attiverà per un agente, un agente dovrebbe confermare le azioni distruttive con l'umano prima.
- **Paginazione:** i risultati sono dal più nuovo al più vecchio e paginati con cursore (ogni pagina restituisce un token che usi per recuperare il successivo). `--limit N` (alias `-n`) limita le righe e **per impostazione predefinita è 50**; `--all` auto-pagina (in chunk di 200 righe) **fino a `--limit`**, quindi un `--all` nudo si ferma comunque a 50. Per una pulizia completa passa un cap esplicito elevato: `--all --limit 1000`. `--page-size N` controlla il chunk per richiesta (massimo 200); `--cursor <id>` riprende dal `next_cursor` di una pagina precedente.
- **Filtri di tempo:** `--since` accetta una finestra relativa: `15m`, `1h`, `6h`, `24h`, `7d`, o `all` (i preset del dashboard). Per un intervallo più lungo o personalizzato (ad esempio gli ultimi 30 giorni), usa `--from`/`--to`: timestamp UTC ISO-8601 espliciti **con `T` e un fuso orario** (ad esempio `2026-06-01T00:00:00Z`) che sostituiscono `--since`. Un valore separato da spazi o senza fuso orario è un errore di utilizzo.
- **`--fields a,b,c`** (su `events`, `sessions`, `evals`, `errors`) limita l'output a quelle chiavi, sia per la tabella che per `--json`. I nomi sconosciuti vengono rifiutati con l'elenco valido, un modo economico per scoprire i nomi dei campi.
- **`--file payload.json`** (o `--file -` per leggere stdin) fornisce un corpo di richiesta JSON completo dove una risorsa ha una forma complessa (su `alerts create/update`, `settings set`, e `users create/update`). L'SQL della query salvata usa `--sql @file.sql` invece.
- **I filtri multi-valore** sono separati da virgole → abbinati come un set (unione all'interno di un filtro, AND tra i filtri): `--event-type tool_use,tool_result`. Le opzioni di clic non sono variadiche, quindi `--add a b` non funziona. Usa `--add a,b`, ripeti il flag (`--add a --add b`), o virgolette (`--add "a b"`).

## Riferimento dei comandi

### Utilizzerai questi 5 comandi nella maggior parte dei casi

La maggior parte del lavoro quotidiano viene eseguita attraverso una manciata di comandi di lettura. Inizia qui, quindi raggiungi la superficie completa di seguito quando ne hai bisogno:

| Comando | Cosa fa | Prova |
|---|---|---|
| `sessions` | Una riga per esecuzione dell'agente: ora, ambiente, agente, stato, ultimo score. | `agenteye --json sessions --since 24h --status error` |
| `events` | L'accesso grezzo per step interno a un'esecuzione (aggiungi `--full` per i payload). | `agenteye --json events --session-id run-001 --all` |
| `evals` | Risultati di valutazione e score; `--aggregate` li riassume. | `agenteye --json evals --aggregate --since 7d --env prod` |
| `errors` | Solo gli eventi con errori; `--aggregate` per i conteggi per tipo. | `agenteye --json errors --since 24h --aggregate` |
| `list` | Scopri i valori di filtro validi (agenti, ambienti, modelli, …). | `agenteye list agents` |

### Tutto quello che la CLI può fare

La superficie completa segue. La CLI ha **18 comandi di livello superiore**. Tutti i comandi di lettura accettano `--json` e le opzioni globali di cui sopra; esegui `agenteye <command> -h` (o `<command> <subcommand> -h`) per l'elenco flag esaustivo e la forma JSON di uno qualsiasi.

### Identità: `login` · `logout` · `whoami` · `orgs` · `version` · `help`

```bash
agenteye login --email you@example.com [--org acme]   # codice monouso inviato per email; salva la sessione
agenteye logout                                       # cancella la sessione salvata su questa macchina
agenteye whoami                                       # utente corrente, organizzazione attiva, permessi
agenteye version                                      # stampa la versione della CLI (stesso di --version)
agenteye help                                         # aiuto di livello superiore (stesso di --help)
```

`orgs` ispeziona e cambia il tenant attivo:

```bash
agenteye orgs list        # le tue organizzazioni + il tuo ruolo in ciascuna (quella attiva contrassegnata)
agenteye orgs switch acme # cambia l'organizzazione attiva salvata (ometti lo slug per scegliere da un elenco su un TTY)
agenteye orgs current     # carta d'identità per l'organizzazione attiva
agenteye orgs perms       # i tuoi permessi nell'organizzazione attiva, raggruppati per risorsa
```

### Osserva (sola lettura): `events` · `sessions` · `evals` · `errors` · `list`

Nessuno di questi ha bisogno di una conferma. Filtri condivisi: `--session-id`, `--agent-id`, `--env` (**non** `--environment`), e l'intervallo di tempo (`--since` / `--from` / `--to`).

```bash
# events (alias: l'accesso grezzo per step), il più nuovo prima
agenteye --json events --session-id run-001 --event-type tool_use,tool_result --all --limit 1000
agenteye --json events --since 1h --search timeout --all | jq '.events[].payload'

# sessions: una riga per esecuzione dell'agente (tempo/ambiente/agente/sessione/stato; senza filtro score)
agenteye --json sessions --since 24h --status error
agenteye --json sessions --agent-id checkout-bot --env prod --all --limit 1000

# evals: risultati di valutazione + score; --score filtra per metrica, --aggregate riassume
agenteye --json evals --score helpfulness:0.5..0.8 --score tool_efficiency:..0.3
agenteye --json evals --aggregate --since 7d --env prod        # mix di stato + statistiche di score per chiave

# errors: eventi con errori; --aggregate per conteggi/sessioni/agenti/ultimo-visto
agenteye --json errors --since 24h --aggregate
agenteye --json errors --since 24h --error-type timeout --all --limit 1000

# list: scopri i valori di filtro validi prima di filtrare
agenteye list envs        # anche: agents event_types score_filters models hooks tools error_types
```

`--score KEY:MIN..MAX` (su **`evals`**, non `sessions`) è ripetibile e AND-combinato; entrambi i bound sono facoltativi (`..0.5` significa ≤ 0.5, `0.9..` significa ≥ 0.9). Fino a 20 filtri di score per richiesta. `evals --scores-full` è un flag di visualizzazione per la **tabella umana solo**; mostra ogni coppia di score anziché le prime poche più un conteggio `+N`. Non ha effetto sotto `--json`, che sempre restituisce l'oggetto score completo. Per leggere **una sessione da capo a fondo**, combina l'accesso agli eventi con la sua valutazione:

```bash
agenteye --json events --session-id run-001 --all --limit 1000 | jq '.events[] | {ts, event_type}'
agenteye --json evals  --session-id run-001                       # i suoi score + stato
```

### Gestisci (controllato da permessi): `keys` · `users` · `settings` · `alerts` · `incidents`

**`keys`**: Chiavi API. Il segreto viene generato localmente, inviato al server (che memorizza solo un hash), e **mostrato una sola volta** su crea/rigenera; acquisiscilo allora. Con `--json` appare solo nel campo `key`. Referenziato per **nome**.

```bash
agenteye keys list                                   # chiavi attive prima, poi revocate
agenteye keys show ci-bot
agenteye keys create ci-bot --add events:read.add    # limita a quello che serve; stampa il segreto UNA VOLTA
agenteye keys create ops --permission-set standard --remove queries:run   # inizializza un preset, quindi ritaglia
agenteye keys update ci-bot --add evaluations:read --yes
agenteye keys regenerate ci-bot --yes                # ruota il segreto (quello vecchio smette di funzionare)
agenteye keys disable ci-bot --yes                   # revoca
```

I permessi funzionano come `(permission-set ∪ --add) − --remove`. I token sono `slug:action` (ad esempio `events:read`) o `slug:action.action` per espanderne diversi su una risorsa (`events:read.add` → `events:read`, `events:add`). Preset: `read-only`, `standard`, `admin`. I permessi solo per umani (`keys:update`) non possono essere concessi a una chiave.

**`users`**: Membri dell'organizzazione, referenziati per **email** (è accettato anche un id UUID).

```bash
agenteye users list [--active-only]
agenteye users show dev@corp.com
agenteye users create dev@corp.com --permission-set standard
agenteye users update dev@corp.com --add alerts:write --remove queries:delete   # predice + conferma
agenteye users disable dev@corp.com --yes            # ha protezioni/guardie di auto
agenteye users enable dev@corp.com
```

**`settings`**: Un registro fisso (leggi e cambia le chiavi esistenti; non puoi crearne di nuove).

```bash
agenteye settings list                               # chiave · valore · tipo · aggiornato (segreti mascherati)
agenteye settings schema                             # cosa accetta ogni chiave (tipo · intervallo · descrizione)
agenteye settings set session_ttl_secs --value 86400 --yes
```

**`alerts`**: Definizioni di avvisi, referenziate per **nome**. `create` accetta un NAME posizionale più flag o un corpo JSON completo tramite `--file`.

```bash
agenteye alerts list
agenteye alerts show high-errors
agenteye alerts create high-errors --file alert.json          # NAME è obbligatorio (posizionale)
agenteye alerts update high-errors --severity critical --yes
agenteye alerts test high-errors --yes                        # attiva una notifica di test
agenteye alerts delete high-errors --yes
```

**`incidents`**: Incidenti di avviso, referenziati per id (gli id brevi sono accettati). `show` stampa il log di attività completo; leggilo prima di agire.

```bash
agenteye incidents list --state firing                # anche: acknowledged, resolved
agenteye incidents count
agenteye incidents show <id>
agenteye incidents ack <id>
agenteye incidents assign <id> you@corp.com           # l'assegnatario deve essere un operatore
agenteye incidents resolve <id> --yes
agenteye incidents open --alert-id <id> --severity critical    # apri uno manualmente contro un avviso
agenteye incidents comment-add <id> "root cause: upstream 5xx"
agenteye incidents comment-list <id> ; agenteye incidents comment-delete <id> <comment-id>
agenteye incidents subscribe <id> ; agenteye incidents unsubscribe <id> ; agenteye incidents subscribers <id>
```

### Analitiche e assistente: `query` · `agent`

**`query`**: SQL salvato contro il tuo archivio di analitiche più un runner ad hoc. Le query salvate vengono referenziate per **nome**; l'SQL viene convalidato lato server (solo SELECT/WITH, timeout dell'istruzione, cap di riga).

```bash
agenteye query schema [TABLE]                         # layout delle colonne delle viste di analitiche
agenteye query run --sql "select count(*) from analytics.events"
agenteye query run errs --arg prod --limit 100        # esegui una query salvata + un $1 posizionale
agenteye query list ; agenteye query show errs
agenteye query create errs --sql @errs.sql --description "errored events (24h)"
agenteye query update errs --sql @errs.sql --yes ; agenteye query delete errs --yes
```

**`agent`**: Parla con l'**assistente IA** incorporato (lo stesso analista di sola lettura con cui puoi chattare nel dashboard). Le chat vengono referenziate da un short chat-id (prefix-resolved).

```bash
agenteye agent health                                 # l'assistente IA è configurato/raggiungibile
agenteye agent models                                 # modelli che puoi passare a --model (predefinito contrassegnato)
agenteye agent ask "which agents errored most in the last day?"    # inizia una chat; stampa il suo short id
agenteye agent ask --chat <short-id> "and which tools did they call?"   # continua quella chat
agenteye agent chats ; agenteye agent show <short-id>
agenteye agent rename <short-id> --title "error triage" ; agenteye agent delete <short-id>
```

## Codici di uscita

| Codice | Significato |
|---|---|
| 0 | Successo |
| 1 | Errore inaspettato (ad esempio il dashboard ha restituito un 5xx) |
| 2 | Errore di utilizzo (argomenti non validi, comando/flag sconosciuto, collisione di nomi) |
| 3 | Impossibile raggiungere il dashboard |
| 4 | Non autenticato o sessione scaduta; esegui `agenteye login` |
| 5 | Autenticato, ma il tuo account manca del permesso richiesto (il messaggio lo nomina) |
| 6 | La risorsa richiesta non è stata trovata (ad esempio sessione o id di incidente sconosciuto) |

Questi rendono la CLI sicura da scriptare: un agente di codifica può ramificarsi su un `4` per chiederti di ri-autenticarti, o un `5` per esporre il permesso mancante. Vedi [Ricette CLI per agenti](/it/agenteye/cli-recipes) per i modelli di gestione del codice di uscita e le forme di output JSON.
