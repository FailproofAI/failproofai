Le politiche integrate sono 39 politiche mantenute che coprono nove categorie di fallimento degli agenti. Tutte tranne una sono **fornite come pack**, `FailproofAI/policies`, esattamente come vengono fornite le politiche di chiunque altro. Il pacchetto non contiene un pack proprio, quindi un'installazione nuova non applica nulla finché non la prendi:

```bash
failproofai policies add FailproofAI/policies
```

Questo attiva i valori predefiniti del pack — 10 delle 38 politiche che il pack contiene. La 39ª è `block-failproofai-commands`, che è attiva indipendentemente: è compilata nel pacchetto, si registra a ogni valutazione, e non può essere disabilitata o messa in pausa. Un pack non può dichiarare `alwaysOn`, per questo motivo quella protezione non percorre il canale del pack.

## Cosa coprono le nove categorie

| Categoria | slug `--category` | Politiche |
| --- | --- | --- |
| Sanitize | `sanitize` | 5 |
| Environment | `environment` | 3 |
| Dangerous Commands | `dangerous-commands` | 5 |
| Infra Commands | `infra-commands` | 7 |
| Git | `git` | 6 |
| Database | `database` | 2 |
| Packages & System | `packages-system` | 5 |
| AI Behavior | `ai-behavior` | 1 |
| Workflow | `workflow` | 5 |

Questi sono i conteggi del catalogo compilato, che in totale fanno 39. Il pack ne contiene 38, perché `block-failproofai-commands` è `alwaysOn` e non percorre mai il canale del pack — quindi `--category dangerous-commands` seleziona gli altri quattro.

Prendi una selezione invece dei valori predefiniti:

```bash
failproofai policies add FailproofAI/policies --category git,database
failproofai policies add FailproofAI/policies --policy block-rm-rf
failproofai policies add FailproofAI/policies --all
```

## Attiva o disattiva una

```bash
failproofai policies add block-rm-rf --cli claude --scope project
failproofai policies remove block-rm-rf --cli claude --scope project
```

`policies add` e `policies remove` accettano esattamente **un** nome di politica. Eseguili senza alcun nome e otterrai un selezionatore, con ciò che è già attivo spuntato. Per più nomi contemporaneamente, usa il modulo di installazione:

```bash
failproofai policies --install block-sudo block-force-push \
  --cli claude codex --scope project
```

<Note>
  Su una macchina senza alcun pack installato, `failproofai policies add <builtin-name>` recupera `FailproofAI/policies` dal suo rilascio GitHub per soddisfare il nome — quindi il primo comando ha bisogno della rete.
</Note>

## Non tutte le politiche sono applicate su tutti gli harness

Una politica cambia il comportamento solo dove l'harness consuma il verdetto per il suo evento. Due casi vale la pena controllare prima di fare affidamento su una politica integrata:

| Evento | Dove un deny è verificato per cambiare il comportamento |
| --- | --- |
| `PreToolUse` | Tutti i 12 harness |
| `Stop` | claude, codex, copilot, cursor, openclaw, factory, devin, antigravity. Nessun hook `Stop` è installato su goose o hermes, pi porta il motivo nel turno successivo, e opencode non è verificato |

Quindi le cinque politiche `require-*-before-stop` nella categoria Workflow possono essere abilitate su una macchina e comunque non attivarsi mai, a seconda di quale agente viene eseguito lì. Le VM Cursor Cloud Agent non eseguono affatto hook di arresto.

Le politiche `warn-*` e `prefer-*` restituiscono `instruct` invece di `deny`. Su Hermes e Goose, e al di fuori del canale `Stop` su Pi, OpenClaw, Factory e Antigravity, `instruct` si degrada a allow più una nota su stderr: l'operatore la vede nei log, l'agente no.

Alcune politiche accettano parametri. Esamina la descrizione, abbina lo scope e il valore predefinito prima del rollout — una politica che protegge un flusso di lavoro può bloccare operazioni valide in un altro.
