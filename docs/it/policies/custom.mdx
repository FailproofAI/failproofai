Crea un file che termina con `policies.js`, `policies.mjs` o `policies.ts` sotto `.failproofai/policies/`. I file di convenzione si caricano automaticamente a livello di progetto e utente.

## Testa la politica prima della pubblicazione su Cloud

<Tabs>
  <Tab title="Dashboard">
    1. Installa la politica personalizzata su una macchina di test e attiva sia un'azione corrispondente che un non-match legittimo.
    2. Vai a **Observe → policy** e confronta le due decisioni.
    3. Apri ogni sessione collegata e verifica che il payload dell'evento contenga prove sufficienti per la regola.
    4. Quando il comportamento è corretto, sposta il codice sorgente esaminato in **Admin → policy editor** e pubblica una versione.

  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai policies --install --custom ./security.policies.ts \
      --cli claude --scope project
    failproofai policies
    ```

    I file di convenzione sotto `.failproofai/policies/` si caricano senza `--custom`. Mantieni un comando di installazione esplicito in CI quando la convalida deve non riuscire su un modulo non valido.
  </Tab>
</Tabs>

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production-paths",
  description: "Block writes to production configuration",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Write" && ctx.toolName !== "Edit") return allow();
    const path = String(ctx.toolInput?.file_path ?? "").replaceAll("\\", "/");
    if (path.split("/").includes("production")) {
      return deny("Writes to production configuration require approval.");
    }
    return allow();
  },
});
```

Questo corrisponde a `production/config.yml`, `/srv/production/config.yml`, `/srv/production` e `C:\\production\\config.yml` sia per `Write` che per `Edit`. Non corrisponde a nomi come `production-backup` perché `production` deve essere un segmento di percorso completo.

Convalida e installa un file esplicito:

```bash
failproofai policies --install --custom ./security.policies.ts
```

Il contesto della politica include il tipo di evento, il payload normalizzato, il nome e l'input dello strumento, i metadati della sessione, i parametri e la CLI di origine quando disponibile.

## Testa i percorsi di errore

Esegui la convalida dopo aver modificato il file di entry o qualsiasi modulo locale che importa:

```bash
failproofai policies --install --custom ./security.policies.ts --scope project
```

Il percorso CLI rigoroso non riesce per file mancanti, errori di sintassi, importazioni non risolte, eccezioni di livello superiore e timeout del caricamento del modulo. Al momento dell'applicazione, un file personalizzato non valido viene registrato e ignorato in modo che le politiche integrate possano continuare. Tratta qualsiasi avviso di caricamento come una perdita dell'applicazione prevista e inviail una notifica di allarme nel caso.

Usa nomi univoci a livello globale tra politiche esplicite, di convenzione e gestite da Cloud. Mantieni le funzioni di politica deterministiche, associa le chiamate esterne con timeout brevi e restituisci un `allow`, `instruct` o `deny` intenzionale su ogni percorso.

<Warning>
  Una politica personalizzata è codice di applicazione. Testa campi mancanti, nomi di strumenti alternativi e input non valido—non solo la corrispondenza prevista.
</Warning>
