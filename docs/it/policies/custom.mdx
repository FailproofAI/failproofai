Controlla il [catalogo integrato](/it/policies/builtin-catalog) prima di scrivere una politica. Una regola verificata è solitamente più sicura di una nuova.

## Inizia da una politica funzionante

```bash
failproofai publish --init guards.mjs
failproofai policies -i -c ./guards.mjs
```

I blocchi iniziali bloccano `git push --force`. Modificalo, chiedi al tuo agente di provare l'azione bloccata e ispeziona **Policies → Activity**.

```js
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production",
  description: "Production changes need a human",
  match: { events: ["PreToolUse"], toolNames: ["Bash"] },
  fn: async (ctx) =>
    String(ctx.toolInput?.command ?? "").includes("production")
      ? deny("Ask a human before changing production.")
      : allow(),
});
```

Una politica restituisce `allow()`, `deny(message)`, o `instruct(message)`. Usa `deny` quando l'azione deve fermarsi; non tutti gli harness possono consegnare un'istruzione al'agente.

## Carica automaticamente

Posiziona file denominati `*policies.js`, `*policies.mjs`, o `*policies.ts` in:

- `.failproofai/policies/` per un progetto.
- `~/.failproofai/policies/` per il tuo utente.

## Testa i percorsi di errore

Testa sia l'azione non sicura che il lavoro legittimo che appare simile. Conferma che la decisione proviene dalla tua politica piuttosto che da un'altra regola.

Rimuovi file di test espliciti con:

```bash
failproofai policies -u -c
```

Quando la politica è pronta, [pubblica un pack](/it/policies/publish-a-pack) o [distribuiscila tramite Cloud](/it/policies/deploy).
