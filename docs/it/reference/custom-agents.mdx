Python 3.11 o più recente. Nessuna dipendenza a runtime. Usi un framework? [LangChain, CrewAI, LlamaIndex e Pydantic AI](/it/start/integrations) si strumentano da soli con una sola chiamata.

<Note>
  Esiste anche un **SDK TypeScript**, e i due scrivono gli stessi eventi nello stesso spool. Una flotta con agenti Node e agenti Python produce un set di sessioni, non due. Scegli per servizio, non per azienda.
</Note>

## Installa

```bash
pip install failproofai-sdk
```

Il pacchetto è installato come `failproofai-sdk` e importato in Python come `failproofai_sdk`. I componenti aggiuntivi del framework come `failproofai-sdk[langgraph]` installano il framework stesso; gli adattatori sono sempre inclusi nella wheel di base.

## Configurazione

### Span OpenTelemetry (opt-in)

Installa `opentelemetry-sdk` separatamente, poi allega l'esportatore opzionale:

```python
import failproofai_sdk
from opentelemetry.sdk.trace import TracerProvider

provider = TracerProvider()
failproofai_sdk.instrument("otel", provider=provider)
with provider.get_tracer("my-agent").start_as_current_span(
    "agent", attributes={"gen_ai.operation.name": "invoke_agent"}
):
    pass
provider.force_flush()
```

La configurazione usa il tuo provider registrato se ometti `provider`, creandone uno solo
quando nessuno è registrato. Puoi anche passare `failproofai_sdk.OtelSpanExporter()`
direttamente al tuo processore di span. Gli altri esportatori rimangono invariati.

Il daemon FailproofAI connesso consegna le esportazioni; l'SDK non ha bisogno di configurazione di rete,
chiave o listener locale. Un amministratore deve abilitare
[l'inserimento OpenTelemetry](/it/agenteye/opentelemetry). Un semplice `instrument()`
non abilita mai OTEL. `uninstrument("otel")` disabilita solo il proprio processore.
La tua instrumentazione controlla l'acquisizione dei contenuti. Scarica il provider prima dell'uscita.
L'SDK continua a dichiarare zero dipendenze hard a runtime e importa OpenTelemetry
solo quando richiesto.

```python
import failproofai_sdk

failproofai_sdk.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| Argomento | Cosa fa |
| --- | --- |
| `environment` | L'etichetta su ogni evento — `production`, `staging`, `prod-eu`. Predefinito su `dev`. |
| `flush_interval` | Quanto spesso il thread di background scrive su disco, in secondi. Predefinito su `0.5`. |
| `base_dir` | Dove scrivere. Predefinito sullo spool del daemon, che è quello che vuoi a meno che tu non sappia il contrario. |

Imposta tramite variabile di ambiente invece:

| Variabile | Cosa fa |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | Imposta `environment` senza una modifica del codice, per quando l'etichetta appartiene alla distribuzione piuttosto che all'app. Un argomento `configure()` vince su di essa. |
| `FAILPROOFAI_HOME` | Sposta la radice di Failproof AI che contiene lo spool. |
| `FAILPROOFAI_SDK_STRICT` | `1` rende gli errori di instrumentazione lanciati invece di essere registrati. |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | `1` rende un problema di compatibilità del framework lanciare invece di avvertire e continuare. |

<Warning>
  **Niente virgole in `environment`.** L'inserimento divide quel campo su virgole per costruire i suoi filtri e salta qualsiasi evento la cui etichetta ne contiene una — quindi un'intera esecuzione scompare silenziosamente. Scrivi `prod-eu`, non `prod,eu`.

  `configure(environment="prod,eu")` lancia quindi scopri immediatamente. `AGENTEYE_ENVIRONMENT` non può lanciare — niente ti sta chiamando — quindi avverte una volta e ricade a `dev`.
</Warning>

Gli eventi vengono messi in coda in memoria e scritti in background ogni `flush_interval` secondi, con uno scarico finale all'uscita dell'interprete. Un processo ucciso brutalmente perde tutto ciò che non era ancora stato scritto.

## Identità

Ogni evento appartiene a una sessione e un agente. **Gli ambiti compilano entrambi**, quindi raramente li passi:

```python
with failproofai_sdk.session():
    with failproofai_sdk.agent("planner"):
        failproofai_sdk.event.tool_use(tool_name="search", tool_call_id="c1")
```

Passare esplicitamente `session_id` o `agent_id` funziona ancora e vince. Con nessuno legato né passato, la chiamata solleva `TypeError` piuttosto che emettere un evento che Cloud scarterebbe silenziosamente.

<Note>
  L'identità si basa su variabili di contesto. Segue automaticamente i compiti `asyncio`, ma **non** i nuovi thread — avvolgi un worker in `failproofai_sdk.propagate()` o i suoi eventi si attaccano in modo non associato.
</Note>

## Catalogo degli eventi

Quindici metodi. La maggior parte viene in **coppie** — chiami l'aperitore, poi il più vicino, e l'SDK misura il divario.

| | Apre | Chiude |
| --- | --- | --- |
| **Agenti** | `agent_start` | `agent_end` |
| | `agent_pause` | `agent_resume` |
| **Modelli** | `model_request` | `model_response` |
| **Strumenti** | `tool_use` | `tool_result` |
| **Hook** | `hook_triggered` | `hook_completed` |
| **Umani** | `human_wait` | `human_input` |

Tre sono autonomi: `error`, `human_pause`, `human_interrupt`.

<Accordion title="Ogni campo, per metodo" icon="table">

Ogni metodo accetta anche `session_id` e `agent_id`, che gli ambiti compilano per te. Qualsiasi cosa lasciata come `None` viene scartata piuttosto che inviata come JSON `null`, e ogni metodo restituisce `None`.

| Metodo | Richiesto | Opzionale |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools`, `request_id` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role`, `request_id`, `duration_ms` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

</Accordion>

<Warning>
  Per contrassegnare un'esecuzione come non riuscita, `outcome` deve essere uno di `failed`, `error`, `timeout` o `rejected`. Qualsiasi altra cosa — incluso il quasi errore `"failure"` — conta come un successo.
</Warning>

## Accoppiamento e durata

**Una regola: dai all'evento di chiusura lo stesso id del suo aperitore.** È quello che li accoppia e che consente all'SDK di misurare il divario.

| Coppia | Accoppiato su |
| --- | --- |
| `tool_use` → `tool_result` | `tool_call_id` |
| `hook_triggered` → `hook_completed` | `hook_id` |
| `agent_pause` → `agent_resume` | `pause_id` |
| `human_wait` → `human_input` | `input_id` |
| `model_request` → `model_response` | `request_id` |

**Non passare `duration_ms` tu stesso.** L'SDK lo misura, e passarlo solleva `ValueError`.

L'unica eccezione è `model_response`, dove solo tu conosci la vera latenza del provider. Passa un numero intero di millisecondi — un float solleva, perché la colonna è un intero a 32 bit e altrimenti finisce vuota.

<Accordion title="Casi limite" icon="circle-help">

- **Gli ID devono essere univoci solo per tipo, per sessione.** Una chiamata di strumento e un hook possono condividerne uno; due sessioni in esecuzione contemporaneamente possono riutilizzare gli stessi ID senza scontrarsi.
- **Non sono limitati a un agente.** Una coppia aperta sotto un agente e chiusa sotto un altro si accoppia ancora — che è il caso normale nel codice multi-agente.
- **`request_id` è opzionale ma consigliato.** Senza di esso, gli eventi del modello si accoppiano nell'ordine in cui arrivano, quindi due chiamate simultanee nello stesso agente possono accoppiarsi male.
- **Una coppia divisa tra processi** si accoppia ancora in Cloud, ma l'SDK non può misurarla — nulla in nessuno dei due processi ha visto entrambe le metà.
- **Al massimo 10.000 aperture aspettano una chiusura alla volta.** Oltre a quello, il più vecchio viene scartato, quindi una perdita non può crescere senza limiti.

</Accordion>

## I tuoi campi personalizzati

Qualsiasi extra che passi è memorizzato con l'evento:

```python
failproofai_sdk.event.tool_use(
    tool_name="search", tool_call_id="c1",
    fw_tenant="acme", fw_region="eu-west-1",     # tuoi
)
```

Preferisci tipi JSON se vuoi interrogarli in seguito. Qualsiasi altra cosa — un UUID, un datetime, un `Decimal`, un set, byte, un oggetto modello — è memorizzato come stringa.

<Warning>
  **Anteponi nomi di campo personalizzati.** Gli extra vengono applicati per ultimi, quindi un campo chiamato `model`, `tool_name` o `outcome` sovrascrive silenziosamente quello reale. Gli adattatori del framework usano `fw_`; fai lo stesso e nulla può scontrarsi.

  È anche per questo che un campo opzionale malinteso non genera mai errori — diventa solo un nuovo campo personalizzato. Se un campo standard manca in Cloud, controlla prima l'ortografia.
</Warning>

Questi cinque nomi sono riservati e rifiutati completamente: `timestamp`, `session_id`, `agent_id`, `type`, `environment`.

## Consegna e verifica

<Tabs>
  <Tab title="Dashboard">
    In **Observe → Events**, verifica che `agent_start` esista per primo e `agent_end` esista per ultimo. Quindi apri **Observe → Sessions** e conferma che gli eventi di modello, strumento, umano, hook e errore appaiano nell'ordine previsto. Usa l'ID sessione come chiave di risoluzione dei problemi primaria.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

Se Cloud è vuoto, ispeziona `$FAILPROOFAI_HOME/custom-agents/events`, altrimenti `~/.failproofai/custom-agents/events`. I file JSONL provano l'emissione SDK; uno spool in crescita indica una configurazione del daemon o un problema di consegna, mentre uno spool vuoto indica un problema di instrumentazione o durata del processo.

<Note>
  Ispeziona lo spool solo quando il daemon è fermato. Mentre è in esecuzione, raccoglie ed elimina ogni batch entro millisecondi, quindi un elenco di directory corre contro il collettore e mostra molto meno eventi di quelli emessi.
</Note>

## Prevenire errori in un runtime personalizzato

Usa i risultati dell'audit e le tracce collegate per definire l'azione non sicura, le prove richieste e la risposta desiderata. Un'integrazione di applicazione personalizzata deve esporre l'azione prima dell'esecuzione, passare il suo input strutturato al motore dei criteri e applicare la decisione allow, instruct o deny risultante.

[Contatta Failproof AI](mailto:support@befailproof.ai) e ti aiuteremo a mappare i confini del modello, dello strumento e del ciclo di vita del tuo runtime agli hook dei criteri, quindi convalidare l'integrazione con te.
