Installa la CLI locale con `npm install -g failproofai`. Eseguila senza argomenti per aprire il dashboard delle politiche locali.

Il pacchetto richiede Node.js 20.9 o più recente. Bun 1.3 o più recente è supportato per sviluppo e installazioni da sorgente. `failproofai configure` e `failproofai setup` sono alias di `failproofai config`. `failproofai policy`, `failproofai pack` e `failproofai p` sono tutti modi di scrivere `failproofai policies` — pack e singole politiche erano tre comandi per un'idea sola e ora ne sono uno. I modi di scrivere più vecchi funzionano ancora, con due eccezioni: `pack list <source>` è ora `policies show <source>`, e `pack build` è ora `publish`.

## Configurare una macchina

Installa la CLI, quindi leggi la chiave della macchina nella shell. `read -s` la prende da un prompt che non fa echo, quindi non appare mai in un comando:

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

Quindi configura la macchina e scegli cosa far rispettare:

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` è il completo setup: installa il servizio `failproofaid` (root una volta — in un terminale chiede la tua password sudo, e la chiede di nuovo se è scaduta prima che il setup finisse; senza terminale usa `sudo -n` e non chiede mai), collega hook in ogni CLI agent trovata, e si connette al Cloud. Senza terminale — CI, un container, un agent che lo guida — applica invece di chiedere, ed esce con 1 se qualsiasi cosa le sia stato chiesto di fare non è successa.

In un terminale, il passo **Connect to cloud** su una macchina non ancora connessa avvia subito il **logging in to FailproofAI Cloud**; premi Tab per le altre opzioni, **Paste an API key** o **Use open source**. Il login apre un link — o lo stampa su SSH o senza display, da aprire su qualsiasi dispositivo — dove ti iscrivi o accedi, scegli o crei un'org, e autorizzi la macchina; il terminale raccoglie l'approvazione da solo e mostra chi l'ha approvata e per quale org. La chiave viene creata solo quando il setup finisce, dopo che il daemon è installato. Su una macchina già connessa con una chiave funzionante, il passo è un menu con **Keep current connection** per primo, quindi ri-eseguire il setup non apre mai un browser da solo; una chiave salvata che non funziona più avvia il login di nuovo subito, e spiega il perché. Fare il login di nuovo crea una nuova chiave e lascia quella vecchia funzionante finché non la revochi. Un Cloud da prima del browser login lo dice e offre le altre opzioni.

Sceglie **no** politiche. Questo è il lavoro del secondo comando, e senza di esso una macchina appena configurata non rispetta nulla se non la guardia sempre attiva.

Preferisci la variabile d'ambiente rispetto a `--token`: un argomento da linea di comando è leggibile da `ps` da ogni utente sulla macchina. È tutto quello che la variabile protegge — una chiave digitata in qualsiasi comando, `export` incluso, finisce comunque nella cronologia shell, ecco perché è letta con `read -s` sopra. In CI, impostala dal deposito di segreti e mantieni la tracciamento shell (`set -x`) spento, o la traccia la stampa.

<Warning>
  `--connect <url>` iscrive una macchina che è **già configurata**. Ritorna non appena l'iscrizione ha successo — non installa il daemon e non collega alcun hook. Usa semplice `failproofai config` (o `failproofai config --token <key>`) su una macchina che non è stata ancora configurata, altrimenti leggerà come connessa mentre raccoglie e non rispetta nulla.
</Warning>

Esegui `failproofai` senza argomenti per aprire il dashboard delle politiche locali.

## Flag di configurazione

| Flag | Uso |
| --- | --- |
| `--token <key>` | Configura e connetti in modo non interattivo; leggi anche da `FAILPROOFAI_CLOUD_TOKEN` |
| `--oss` | Usa open source senza una connessione Cloud; una connessione esistente è lasciata com'è |
| `--agents <a,b>` | Traccia questi agent, o `all`, senza chiedere |
| `--url <url>` | Connettiti da qualche parte diversa da `app.befailproof.ai`; leggi anche da `FAILPROOFAI_CLOUD_URL` |
| `--connect <url>` | Solo iscrizione, su una macchina già configurata. Salta il daemon e ogni hook |
| `--machine-id <id>` | Machine ID per `--connect`; di default un ID stabile |
| `--machine-label <name>` | Da solo, rinomina una macchina che è **già connessa**; non esegue mai setup. Con `--token`, connettiti con quel nome; una chiave impostata solo in `FAILPROOFAI_CLOUD_TOKEN` non è abbastanza, perché `--machine-label` senza `--token` è una rinomina. Con `--oss` o `--agents`, rinomina una macchina che è già connessa ed è rifiutata prima del setup su una che non lo è: `--oss` non si connette mai, e `--agents` ha bisogno di una chiave o di un login Cloud interattivo per connettersi |
| `--no-transcripts` | Invia decisioni senza contenuto trascritto, e non attivare Cloud Jev, che invierebbe ogni chiamata di strumento controllata e il prompt recente; un `jev.json` che esegue Jev attraverso FailproofAI Cloud è rimosso |
| `--disconnect` | Ferma i pull di politiche Cloud e la consegna di eventi. Rimuove anche la chiave Cloud Jev e un `jev.json` che nomina FailproofAI Cloud; la tua configurazione Jev personale è lasciata in posizione |
| `--status` | Mostra lo stato attuale della macchina |
| `--pause [duration]` | Pausa la sessione più recente nella directory corrente; accetta secondi, minuti, o ore e di default 30 minuti |
| `--resume` | Termina una pausa corrispondente in anticipo |
| `--session <id>` | Mira a una sessione esplicita per pausa o ripresa |
| `--all` | Con `--resume`, termina ogni pausa attiva |

Le pause locali sospendono le politiche integrate, personalizzate, convenzione, e pack per una sessione. Scadono sempre, al massimo 8 ore dopo la prima pausa in un'esecuzione, e non disabilitano le politiche gestite da Cloud o `block-failproofai-commands`, che è sempre attiva e non può essere disabilitata o messa in pausa di per sé. Questa guardia rifiuta i modi diretti con cui un agent strumentato potrebbe mettere se stesso in pausa: eseguire `failproofai config --pause`, o scrivere il file di pausa sotto `~/.failproofai/state/sessions/`. Legge i comandi, non quello che uno script fa quando esegue, quindi uno script che l'agent scrive e poi esegue può ancora raggiungere lo stesso stato. Un file di pausa è controllato per una scadenza limitata e un inizio non più di un minuto nel futuro, non per chi l'ha scritto.

## Flag di politica

| Flag | Uso |
| --- | --- |
| `--install`, `-i` | Installa hook dell'harness. I nomi dopo abilit queste politiche; senza nessuno, nessun cambio di politica |
| `--uninstall`, `-u` | Disabilita politiche o rimuovi hook |
| `--cli <names...>` | Mira a uno o più harness supportati |
| `--scope user\|project\|local\|all` | Scegli l'ambito di configurazione; `all` è per l'uninstall |
| `--beta` | Includi politiche beta |
| `--custom`, `-c <path>` | Con `--install`, convalida e carica un file di politica personalizzata; ripetibile. `--uninstall -c` rimuove ogni file di politica personalizzata |
| `--policy`, `--only <a,b>` | Installa solo queste politiche da un pack |
| `--category <x,y>` | Installa solo queste categorie da un pack |
| `--all` | Elenca ogni politica; con un pack, installa tutto |
| `--releases` | Con `show`, elenca i rilasci di un pack e quale è installato |

## Flag di consegna e manutenzione

| Comando | Flag |
| --- | --- |
| `backfill` | `--since <30d\|6m\|1y\|YYYY-MM-DD>`, `--agents <a,b>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` (`-y`) |

### Backfill per harness

`backfill` ri-invia la cronologia che il collector ha già letto, su una macchina connessa al Cloud. `--since` imposta la finestra per la maggior parte degli harness, con due eccezioni:

- **Goose, OpenCode e Devin** inviano tutta la loro cronologia, qualunque cosa `--since` dica: la loro cronologia vive in un database che il collector legge senza finestra temporale, quindi `--dry-run` li segnala come tutte le sessioni.
- La cronologia di **Hermes** non è ri-inviata da `backfill`.

`failproofai update` dovrebbe essere eseguito dopo `npm install -g failproofai@latest`; esegue migrazioni di layout home, installa il corrispondente daemon binary, e riavvia il servizio. Quindi sposta ogni profilo Hermes che già usa FailproofAI al plugin nativo collegato e stampa una riga per profilo. `--no-daemon` salta il passo daemon. `update` esce con un valore non-zero quando il daemon non poteva essere sostituito, una migrazione è fallita, o un profilo Hermes non poteva essere migrato (ad esempio perché il daemon in esecuzione non può servire il plugin nativo, nel qual caso i suoi shell hook sono lasciati in posizione).

## Percorsi dell'harness

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

I nomi di harness supportati sono `claude`, `codex`, `copilot`, `cursor`, `opencode`, `pi`, `hermes`, `openclaw`, `factory`, `devin`, `antigravity`, e `goose`.

Le etichette namespace derivano gli ID degli agent quando due radici contengono copie dello stesso progetto. Le radici sovrapposte e le etichette duplicate sono rifiutate per prevenire raccolta duplicata o corruzione del cursore. La configurazione di percorso extra si ricarica senza un riavvio del daemon.

Gli ambienti container possono sostituire i percorsi extra configurati con file con una variabile separata da virgole denominata `FAILPROOFAI_<HARNESS>_EXTRA_PATHS`, ad esempio:

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## Variabili d'ambiente

Usa i file di configurazione per il comportamento persistente della macchina. Le variabili d'ambiente sono più utili per container, test, e un processo.

| Variabile | Uso |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | La chiave Cloud, invece di `--token`. Preferisci questo: un argomento è leggibile da `ps` da ogni utente. Impostalo con `read -s` o da un deposito di segreti CI, mai digitando la chiave in un comando, che finisce nella cronologia shell comunque |
| `FAILPROOFAI_CLOUD_URL` | L'URL Cloud, invece di `--url`. La stessa variabile che il daemon legge |
| `FAILPROOFAI_HOME` | Sposta il completo layout `~/.failproofai` |
| `FAILPROOFAI_LOG_LEVEL` | Imposta la verbosità della registrazione locale |
| `FAILPROOFAI_HOOK_LOG_FILE` | Scrivi diagnostica hook su un file selezionato |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | Disabilita telemetria anonima per questo processo |
| `FAILPROOFAI_NO_FIRST_RUN=1` | Salta setup interattivo al primo esecuzione |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | Salta l'audit locale post-setup |
| `FAILPROOFAI_LLM_BASE_URL` | Sovrascrivi l'endpoint compatibile OpenAI usato dalle politiche LLM |
| `FAILPROOFAI_LLM_API_KEY` | Fornisci la chiave API usata dalle politiche LLM |
| `FAILPROOFAI_LLM_MODEL` | Seleziona il modello usato dalle politiche LLM |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | Limita il caricamento del modulo di politica personalizzata |
| `FAILPROOFAI_NO_DOWNLOAD=1` | Rifiuta di scaricare pack e daemon binary; quello che è installato continua a rispettare |
| `FAILPROOFAI_PACK_BASE_URL` | Scarica pack da uno specchio invece di `github.com` |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | Sostituisci i percorsi di cattura extra configurati per un harness |
| `NO_COLOR` | Disabilita l'output del terminale colorato |

Le variabili home specifiche dell'agent come `CLAUDE_PROJECTS_PATH`, `CURSOR_HOME`, `HERMES_HOME`, e `OPENCLAW_HOME` sovrascrivono dove Failproof AI scopre le sessioni locali per quell'harness.

## Mettere in pausa o rimuovere una macchina in sicurezza

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

Una pausa di sessione locale non disabilita le politiche gestite da Cloud. Ripristina i deployment Cloud da **fix → deploy policies** nel Cloud quando il rollout stesso è il problema.

Prima di rimuovere il pacchetto npm, rimuovi hook installati e il daemon:

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

Esegui `failproofai <command> --help` per dettagli specifici della versione.

<Warning>
  Esegui `failproofai uninstall` prima di `npm rm -g failproofai`; npm non rimuove gli hook degli agent installati, la skill `failproofai` o il servizio daemon.
</Warning>
