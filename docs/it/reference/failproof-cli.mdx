Installa la CLI locale con `npm install -g failproofai`. Eseguila senza argomenti per aprire il dashboard delle policy locale.

Il pacchetto richiede Node.js 20.9 o versioni più recenti. Bun 1.3 o versioni più recenti sono supportate per lo sviluppo e le installazioni da sorgente. `failproofai configure` e `failproofai setup` sono alias per `failproofai config`. `failproofai policy`, `failproofai pack` e `failproofai p` sono tutti sinonimi di `failproofai policies` — pack e policy singole erano tre comandi per un'idea e ora sono uno. I nomi precedenti continuano a funzionare, con due eccezioni: `pack list <source>` è ora `policies show <source>` e `pack build` è ora `publish`.

## Configura una macchina

Installa la CLI, quindi leggi la chiave della macchina nella shell. `read -s` la acquisisce da un prompt che non echo, quindi non appare mai in un comando:

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

Quindi configura la macchina e scegli cosa deve applicare:

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` è l'intera configurazione: installa il servizio `failproofaid` (una volta con root — in un terminale chiede la tua password sudo e chiede di nuovo se scade prima del completamento della configurazione; senza terminale usa `sudo -n` e non chiede mai), collega gli hook a ogni CLI agente che trova e si connette al Cloud. Senza terminale — CI, container, un agente che lo guida — applica invece di chiedere ed esce con 1 se qualcosa che gli è stato chiesto di fare non è avvenuto.

In un terminale, il passaggio **Connetti al cloud** su una macchina non ancora connessa avvia immediatamente **l'accesso a FailproofAI Cloud**; premi Tab per le altre opzioni, **Incolla una chiave API** o **Usa open source**. L'accesso apre un link — o lo stampa via SSH o senza display, per aprirlo su qualsiasi dispositivo — dove ti iscrivi o accedi, scegli o crei un'organizzazione e autorizzi la macchina; il terminale acquisisce l'approvazione da solo e mostra chi l'ha approvata e per quale organizzazione. La chiave viene generata solo quando la configurazione termina, dopo che il daemon è installato. Su una macchina già connessa con una chiave funzionante, il passaggio è un menu con **Mantieni connessione corrente** per primo, quindi eseguire nuovamente la configurazione non apre mai il browser da solo; una chiave salvata che non funziona più avvia nuovamente l'accesso subito e spiega perché. L'accesso di nuovo crea una nuova chiave e lascia quella vecchia funzionante finché non la revochi. Un Cloud da prima dell'accesso dal browser lo dice e offre le altre opzioni.

Sceglie **nessuna** policy. È il lavoro del secondo comando e senza di esso una macchina appena configurata non applica nulla se non la protezione sempre attiva.

Preferisci la variabile di ambiente rispetto a `--token`: un argomento della riga di comando è leggibile da `ps` da ogni utente sulla macchina. È tutto ciò che la variabile protegge — una chiave digitata in qualsiasi comando, `export` incluso, finisce ancora nella cronologia della shell, motivo per cui viene letta con `read -s` sopra. In CI, impostala dall'archivio segreto e mantieni la traccia della shell (`set -x`) spenta, altrimenti la traccia la stampa.

<Warning>
  `--connect <url>` registra una macchina che è **già configurata**. Ritorna non appena la registrazione ha successo — non installa il daemon e non collega alcun hook. Usa il semplice `failproofai config` (o `failproofai config --token <key>`) su una macchina non ancora configurata, o verrà letta come connessa mentre non raccoglie né applica nulla.
</Warning>

Esegui `failproofai` senza argomenti per aprire il dashboard delle policy locale.

| Comando | Risultato |
| --- | --- |
| `failproofai config` | Configura la macchina: agenti, daemon e Cloud — accedi tramite browser, incolla una chiave o rimani open source. Ogni agente sulla macchina riceve anche una piccola skill `failproofai` che la punta alle [skill FailproofAI](https://github.com/FailproofAI/skills) online |
| `failproofai config --token <key>` | Configura e connetti in un'unica passata, senza chiedere nulla. Una chiave che contiene `jev:evaluate` attiva anche [Jev tramite FailproofAI Cloud](/it/reference/jev-cloud) in modalità osservazione, a meno che non esista già un `jev.json` o sia data `--no-transcripts` |
| `failproofai config --connect <url>` | Registra una macchina che è **già** configurata — nessun daemon, nessun hook |
| `failproofai config --status` | Mostra lo stato della connessione, daemon, consegna e pausa |
| `failproofai policies` | Elenca policy builtin, custom, convention, pack e gestite da Cloud |
| `failproofai policies --install` | Collega gli hook alle tue CLI agente. Non abilita nessuna policy da solo |
| `failproofai policies add <name>` | Abilita una policy — una builtin o `<pack-id>:<name>` da un pack installato |
| `failproofai policies remove <name>` | Disabilita una policy, stessa denominazione |
| `failproofai policies --uninstall` | Disabilita le policy o rimuovi gli hook harness |
| `failproofai policies show <owner>/<repo>` | Cosa contiene un pack, letto dal suo manifest, prima di prenderlo |
| `failproofai policies show <owner>/<repo> --releases` | Ogni versione che ha pubblicato e quale c'è qui |
| `failproofai policies add <source>` | Installa un policy pack da una release GitHub; nessun tag prende il più recente e lo fissa |
| `failproofai publish` | Spedisci le tue policy come pack; `--init` scrive uno da cui iniziare e `--min-cli-version <version>` imposta la CLI più vecchia che può installarla ([Jev verifica in un pack](/it/policies/publish-a-pack#jev-checks-in-a-pack)) |
| `failproofai policies remove <publisher/name>` | Disinstalla un pack |
| `failproofai audit` | Scansiona la cronologia dell'agente locale e apri la vista audit locale |
| `failproofai audit --schedule [days] --email <address>` | Pianifica scansioni locali ricorrenti e invia i loro risultati via email |
| `failproofai audit --status` | Mostra l'indirizzo del report, l'intervallo e la prossima scansione pianificata |
| `failproofai audit --no-schedule` | Interrompi le scansioni ricorrenti senza eliminare la cronologia audit |
| `failproofai harness list` | Elenca percorsi di acquisizione extra |
| `failproofai otel status` | Ispeziona la segnalazione opzionale di [OpenTelemetry](/it/reference/otel) |
| `failproofai jev --url <url> --key-stdin` | Configura Jev in un unico passaggio; il provider viene ricavato dall'host dell'URL |
| `failproofai jev setup --provider <kind> --key-stdin` | Lascia che [Jev](/it/reference/jev-providers) giudichi le chiamate di strumento attraverso il tuo endpoint e la tua chiave |
| `failproofai jev setup --provider failproofai` | Lascia che Jev giudichi le chiamate di strumento [tramite FailproofAI Cloud](/it/reference/jev-cloud), con la chiave Cloud di questa macchina |
| `failproofai jev setup --mode <m>` | Cambia la modalità di Jev: `enforce`, `observe` o `off` (mantiene la config, smette di chiedere a Jev) |
| `failproofai jev status` | Mostra la config di Jev, le sue autorizzazioni e i recenti fallback; mai la chiave |
| `failproofai jev test` | Invia una richiesta Jev dal vivo e mostra la sua latenza e versione; esce con 1 quando la risposta è in ritardo per gli hook o sbagliata |
| `failproofai jev models` | Elenca gli ID modello che `GET <base>/models` dice che un endpoint serve |
| `failproofai jev remove` | Disattiva Jev; gli hook eseguono le policy regex esattamente come prima |
| `failproofai flush --wait` | Consegna lo spool di eventi attuale |
| `failproofai backfill --since 30d` | Rileggi la cronologia passata precedentemente |
| `failproofai config --pause [duration]` | Pausa una sessione locale per 30 minuti per impostazione predefinita, fino a 8 ore |
| `failproofai config --resume` | Riprendi una sessione locale in pausa; aggiungi `--all` per cancellare tutte le pause |
| `failproofai update` | Termina le migrazioni dei pacchetti e aggiorna il daemon |
| `failproofai migrate --dry-run` | Visualizza in anteprima o esegui le migrazioni di layout home in sospeso |
| `failproofai uninstall` | Rimuovi gli hook, la skill `failproofai` e il daemon prima di rimuovere il pacchetto |
| `failproofai --version` | Stampa la versione del pacchetto installato |
| `failproofai --help` | Mostra comandi e utilizzo globale |

## Flag di configurazione

| Flag | Utilizzo |
| --- | --- |
| `--token <key>` | Configura e connetti in modo non interattivo; leggi anche da `FAILPROOFAI_CLOUD_TOKEN` |
| `--url <url>` | Connettiti da qualche parte diversa da `app.befailproof.ai`; leggi anche da `FAILPROOFAI_CLOUD_URL` |
| `--connect <url>` | Solo registrazione, su una macchina già configurata. Ignora il daemon e ogni hook |
| `--machine-id <id>` | Imposta l'ID macchina stabile |
| `--machine-label <name>` | Rinomina una macchina che è **già connessa**. Da solo non esegue mai la configurazione, quindi dallo dopo `failproofai config`, non durante |
| `--no-transcripts` | Invia decisioni senza contenuto trascrizione e non attivare Cloud Jev, che invierebbe ogni chiamata di strumento controllata e il prompt recente; un `jev.json` che esegue Jev tramite FailproofAI Cloud viene rimosso |
| `--disconnect` | Interrompi i pull delle policy Cloud e la consegna degli eventi. Rimuove anche la chiave Cloud Jev e un `jev.json` che nomina FailproofAI Cloud; la tua configurazione Jev è lasciata in posizione |
| `--status` | Mostra lo stato attuale della macchina |
| `--pause [duration]` | Pausa la sessione più recente nella directory attuale; accetta secondi, minuti o ore e predefiniti a 30 minuti |
| `--resume` | Termina anticipatamente una pausa corrispondente |
| `--session <id>` | Rivolgi una sessione esplicita per pausa o ripresa |
| `--all` | Con `--resume`, termina ogni pausa attiva |

Le pause locali sospendono le policy builtin, custom, convention e pack per una sessione. Scadono sempre e non disabilitano le policy gestite da Cloud. `block-failproofai-commands` — che è sempre attivo e non può essere disabilitato o messo in pausa — impedisce a un agente strumentato di usare questo meccanismo di fuga da solo.

## Flag policy

| Flag | Utilizzo |
| --- | --- |
| `--install`, `-i` | Installa gli hook harness. I nomi dopo di esso abilitano quelle policy; senza, nessuna modifica della policy |
| `--uninstall`, `-u` | Disabilita le policy o rimuovi gli hook |
| `--cli <names...>` | Rivolgi uno o più harness supportati |
| `--scope user\|project\|local\|all` | Scegli l'ambito della configurazione; `all` è per disinstallare |
| `--beta` | Includi le policy beta |
| `--custom`, `-c <path>` | Convalida e carica un file policy custom; ripetibile |

## Flag di consegna e manutenzione

| Comando | Flag |
| --- | --- |
| `backfill` | `--since <30d\|6m\|YYYY-MM-DD>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` |

`failproofai update` deve essere eseguito dopo `npm install -g failproofai@latest`; esegue migrazioni di layout home, installa il binary daemon corrispondente e riavvia il servizio. Quindi sposta ogni profilo Hermes che già usa FailproofAI al plugin nativo collegato e stampa una riga per profilo. `--no-daemon` ignora il passaggio daemon. `update` esce con stato diverso da zero quando il daemon non poteva essere sostituito, una migrazione non è riuscita o un profilo Hermes non poteva essere migrato (ad esempio perché il daemon in esecuzione non può servire il plugin nativo, nel qual caso i suoi hook della shell sono lasciati in posizione).

## Percorsi harness

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

I nomi harness supportati sono `claude`, `codex`, `copilot`, `cursor`, `opencode`, `pi`, `hermes`, `openclaw`, `factory`, `devin`, `antigravity` e `goose`.

Le etichette nello spazio dei nomi degli ID agente derivati quando due radici contengono copie dello stesso progetto. Radici sovrapposte e etichette duplicate vengono rifiutate per prevenire la raccolta duplicata o la corruzione del cursore. La configurazione del percorso extra si ricarica senza un riavvio del daemon.

Gli ambienti container possono sostituire i percorsi configurati da file con una variabile separata da virgole denominata `FAILPROOFAI_<HARNESS>_EXTRA_PATHS`, ad esempio:

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## Variabili di ambiente

Usa i file di configurazione per il comportamento persistente della macchina. Le variabili di ambiente sono più utili per container, test e un singolo processo.

| Variabile | Utilizzo |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | La chiave Cloud, invece di `--token`. Preferisci questa: un argomento è leggibile da `ps` da ogni utente. Impostala con `read -s` o da un archivio segreto CI, mai digitando la chiave in un comando, che finisce nella cronologia della shell comunque |
| `FAILPROOFAI_CLOUD_URL` | L'URL Cloud, invece di `--url`. La stessa variabile che legge il daemon |
| `FAILPROOFAI_HOME` | Riposiziona il layout completo `~/.failproofai` |
| `FAILPROOFAI_LOG_LEVEL` | Imposta la verbosità della registrazione locale |
| `FAILPROOFAI_HOOK_LOG_FILE` | Scrivi la diagnostica hook in un file selezionato |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | Disabilita la telemetria anonima per questo processo |
| `FAILPROOFAI_NO_FIRST_RUN=1` | Ignora la configurazione interattiva al primo avvio |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | Ignora l'audit locale post-configurazione |
| `FAILPROOFAI_LLM_BASE_URL` | Ignora l'endpoint compatibile con OpenAI utilizzato dalle policy LLM |
| `FAILPROOFAI_LLM_API_KEY` | Fornisci la chiave API utilizzata dalle policy LLM |
| `FAILPROOFAI_LLM_MODEL` | Seleziona il modello utilizzato dalle policy LLM |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | Limita il caricamento del modulo policy custom |
| `FAILPROOFAI_NO_DOWNLOAD=1` | Rifiuta di recuperare pack e binary daemon; quello che è installato continua a applicare |
| `FAILPROOFAI_PACK_BASE_URL` | Recupera i pack da uno specchio invece di `github.com` |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | Sostituisci i percorsi di acquisizione extra configurati per un harness |
| `NO_COLOR` | Disabilita l'output del terminale colorato |

Le variabili home specifiche dell'agente come `CLAUDE_PROJECTS_PATH`, `CURSOR_HOME`, `HERMES_HOME` e `OPENCLAW_HOME` ignorano dove Failproof AI scopre le sessioni locali per quell'harness.

## Pausa o rimuovi una macchina in sicurezza

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

Una pausa della sessione locale non disabilita le policy gestite da Cloud. Ripristina le distribuzioni Cloud attraverso il flusso di lavoro di applicazione Cloud quando il rollout stesso è il problema.

Prima di rimuovere il pacchetto npm, rimuovi gli hook installati e il daemon:

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

Esegui `failproofai <command> --help` per i dettagli specifici della versione.

<Warning>
  Esegui `failproofai uninstall` prima di `npm rm -g failproofai`; npm non rimuove gli hook agente installati, la skill `failproofai` o il servizio daemon.
</Warning>
