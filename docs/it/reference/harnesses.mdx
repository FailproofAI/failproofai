Un harness è l'ambiente in cui il tuo agente effettivamente gira. Failproof AI ne supporta dodici, in due categorie:

- **CLI di coding** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Gateway chat e assistenti** (2) — Hermes (Slack, Telegram, cron), OpenClaw (assistente self-hosted)

Le stesse policy e la stessa cronologia sessione si applicano indipendentemente da quale harness l'agente utilizza. Un livello di adattamento mappa i nomi degli eventi nativi di ogni harness, i nomi degli strumenti e i campi di input degli strumenti su 29 eventi canonici prima che qualsiasi policy venga eseguita.

Un agente che gira in **nessuno** dei dodici è strumentato direttamente con l'[SDK Python](/it/reference/custom-agents). Questo è un contratto diverso, e vale la pena dichiararlo chiaramente: l'SDK fornisce tracciamento, sessioni, valutazioni e audit — **non applica policy di per sé.** Bloccare un'azione non sicura prima che venga eseguita richiede un hook di applicazione al confine dello strumento del tuo runtime; [contattaci](mailto:support@befailproof.ai) e la mapperemo.

| Harness | Scope hook supportati |
| --- | --- |
| Claude Code | User, project, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | User, project |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | User, project |
| Hermes, OpenClaw | User |

Ogni integrazione normalizza i nomi degli eventi hook nativi, i nomi degli strumenti e i campi di input degli strumenti prima che le policy vengono eseguite. Una policy può agire solo su eventi che l'harness espone; testa il comportamento di fine turno e istruzioni sull'harness e versione esatti che distribuisci.

## Capacità di applicazione

"Block" significa che il verdetto restituito dall'adattatore corrente è consumato dall'harness nominato. Il blocco post-tool può sostituire il risultato mostrato al modello ma non può annullare un effetto collaterale dello strumento già accaduto.

| Harness | Eventi di blocco verificati | Caveat osservazionali o non bloccanti |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact` e diversi eventi task/config | `PostToolUse`, ciclo di vita sessione, notifiche ed eventi post-fallimento sono osservazionali. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Il blocco post-tool sostituisce il risultato dopo l'esecuzione; gli eventi di inizio sessione e compattazione sono osservazionali nell'adattatore corrente. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Il blocco post-tool sostituisce il risultato dopo l'esecuzione; gli eventi di sessione e notifica sono osservazionali. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` e gli eventi di sessione sono osservazionali. |
| OpenCode | `PreToolUse` | Gli eventi post-tool e ciclo di vita sono osservazionali; la gestione dello stop corrente è guida per un turno successivo piuttosto che un gate verificato. |
| Pi | `PreToolUse`, `UserPromptSubmit` | Gli eventi post-tool e ciclo di vita sono osservazionali; la guida dello stop si applica a un turno successivo. |
| Hermes | `PreToolUse` | `deny()` blocca. `instruct()` non ferma la chiamata: gira, e la guida è posta all'inizio del suo risultato. I verdetti post-tool, sessione e subagent-stop non sono gate. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Gli eventi post-tool, sessione, subagent-stop e compattazione sono osservazionali. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | I verdetti post-tool e subagent-stop sono osservazionali. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PermissionRequest` condizionale | Gli hook di permesso non girano in ogni modalità di permesso; gli eventi post-tool e sessione sono osservazionali. |
| Antigravity CLI | `PreToolUse`, `Stop` | I verdetti user-prompt e post-tool sono osservazionali; le istruzioni di prompt possono comunque essere iniettate. |
| Goose | `PreToolUse` | Gli eventi user-prompt, post-tool e sessione sono osservazionali. Esiste un hook di stop bloccante nativo a monte ma non è installato dall'adattatore corrente. |

Le capacità sono sensibili alla versione. Ritest dopo l'aggiornamento di un CLI agente, specialmente quando una policy si affida al prompt, stop, permesso o comportamento post-tool piuttosto che al gate pre-tool comune.

### Plugin nativo Hermes

Hermes è integrato tramite un plugin nativo locale al profilo piuttosto che un comando shell. L'installazione collega ogni profilo Hermes predefinito e denominato `plugins/failproofai` al plugin fornito nel pacchetto npm (una copia dove non è possibile creare un symlink), lo abilita nel `config.yaml` di quel profilo e migra solo voci legacy di shell-hook FailproofAI. Poiché il plugin è collegato, `npm install -g failproofai@latest` lo aggiorna senza reinstallazione. Questo evita uno spawn di processo ad ogni hook. Il plugin supporta Hermes 0.20.0 e successivi.

Gli hook shell legacy (installati dalla versione 1.0.5 e precedenti) **non** controllano i cron job Hermes: ogni esecuzione cron costruisce il suo scope hook, che il plugin nativo unisce e gli hook shell di `config.yaml` no. `failproofai update` migra ogni profilo che già usa FailproofAI al plugin collegato. Se il daemon in esecuzione non può servire il plugin, `update` lascia gli hook shell al loro posto ed esce con codice non-zero; esegui `failproofai config` per aggiornare il daemon, poi `failproofai update` di nuovo. I cron job caricano il plugin alla loro prossima esecuzione; riavvia i gateway in esecuzione e le sessioni interattive per caricarlo lì.

Su Hermes, `deny()` blocca la chiamata e `instruct()` no: la chiamata gira e la guida è posta all'inizio del suo risultato — come prima chiave, `failproof_policy_reminder`, di un risultato JSON, o come riga iniziale `[FailproofAI policy reminder (...)]` — quindi il modello la legge con l'output, e gli script che parsano il risultato continuano a funzionare. Il reminder di una policy viene mostrato una volta per turno e mantenuto breve su un risultato grande. Usa `deny()` quando un'azione non deve accadere affatto: `instruct()` non ferma più prima l'azione. Le chiamate di strumento fatte da uno script `execute_code` mettono il loro reminder sul risultato `execute_code` che il modello legge; la propria copia dello script del risultato rimane intoccata. Il modello è istruito a non quotare mai un reminder nelle sue risposte.

Una build Hermes senza middleware plugin fallback trattenendo la chiamata corrispondente una volta con "FailproofAI policy guidance"; la prossima risposta del modello può ripeterla, o fare lo stesso lavoro con un altro strumento, senza essere trattenuta di nuovo.

I nomi degli strumenti vengono confrontati tra versioni Hermes: `process_manage`, `cronjob_manage` e `todo_list` (Hermes 0.21) vengono trattati come `process`, `cronjob` e `todo` (Hermes 0.20). Ogni volta che Hermes carica il plugin scrive `heartbeat.json` nella directory `plugin-data/agent-plugin-failproofai-5296f299/` del profilo, registrando la versione di Hermes, il percorso e la versione del plugin e gli hook che Hermes ha accettato. Esegui `failproofai config --status` per rilevare un profilo disabilitato, incompleto, duplicato o appena non configurato, o uno ancora su hook shell legacy (segnalato come "Hermes cron jobs are not checked").

### Plugin OpenClaw

OpenClaw carica FailproofAI come plugin gateway in-process, registrato nel `openclaw.json` di ogni profilo. Come il plugin Hermes, chiede al daemon locale `failproofaid` ogni verdetto sul suo socket, quindi ha bisogno di un daemon in esecuzione: l'installazione si rifiuta senza uno, e se il daemon non può rispondere, le chiamate di strumento e i prompt vengono bloccati e il motivo è scritto nel log del gateway. Dopo `npm install -g failproofai@latest`, riavvia il gateway OpenClaw in modo che carichi il plugin aggiornato.

### Fiducia hook Codex

Codex 0.129 e successivi esegue un hook da `~/.codex/hooks.json` solo dopo che lo approvi in `codex` interattivo ("Review hooks"); fino ad allora, ogni sessione Codex — incluso `codex exec` headless — lo salta. Gli hook nella configurazione di sistema di Codex, `/etc/codex/config.toml` su Linux e macOS, girano senza quell'approvazione.

Quindi quando `failproofai config` (o `policies --install --cli codex` a scope user) può usare sudo, scrive gli hook Codex in `/etc/codex/config.toml`, tra `# >>> failproofai managed hooks >>>` e `# <<< failproofai managed hooks <<<`, e lascia il resto di quel file com'era. Il file si applica a ogni account sulla macchina. `failproofai uninstall` e deselezionare Codex in `failproofai config` tolgono il blocco di nuovo.

Senza sudo, e su Windows, gli hook rimangono in `~/.codex/hooks.json`. `failproofai config` e `failproofai config --status` non contano quindi Codex come applicante fino a quando gli hook non sono approvati, e dicono come risolverlo: riesegui `failproofai config` e consenti sudo, o apri `codex` una volta e approva gli hook.

## Installa hook di capture e policy

<Tabs>
  <Tab title="Dashboard">
    1. Apri **Administration → Keys** e crea una chiave con `events:add` e `policies:pull`, denominata per la macchina o l'ambiente.
    2. Sulla macchina di destinazione, connetti il CLI locale con la chiave visualizzata e installa gli hook dell'harness.
    3. Avvia una nuova sessione agente, quindi conferma i suoi eventi di hook e sessione in **Observe → Events**.
    4. Apri **Observe → policy** per la stessa finestra temporale e conferma che una decisione di policy è attribuita alla macchina.

    La connessione inizia con una chiave di macchina. Conferma che includa sia i permessi di ingestion che di policy-delivery prima di copiare il suo secret.

    ![Il cassetto della nuova chiave API utilizzato per concedere i permessi di event ingestion e policy delivery.](/images/dashboard/key-create.png)

    Dopo l'installazione degli hook, il flusso Events dovrebbe mostrare nuovi eventi dalla macchina e dall'ambiente che hai connesso.

    ![Il flusso Events live utilizzato per confermare che un harness appena installato sta segnalando.](/images/dashboard/events-stream.png)

    Infine, verifica che le decisioni di policy siano attribuite alla stessa macchina. Questo conferma che l'harness sta segnalando l'attività di policy così come gli eventi di traccia.

    ![La pagina Policy utilizzata per verificare le decisioni di policy da un harness appena connesso.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Leggi la chiave di macchina nella shell. `read -s` la prende a un prompt che non fa eco, quindi non appare mai in un comando o nella cronologia shell:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    Quindi configura la macchina — questo collega gli hook per ogni harness rilevato, installa il daemon e si connette a Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    La configurazione non abilita nessuna policy di per sé, per cui è il secondo comando.

    Oppure indirizza harness denominati e uno scope di configurazione:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    Lo scope project mantiene la configurazione degli hook con un repository. Lo scope user copre il lavoro attraverso i repository. Claude Code supporta anche lo scope local; il supporto varia in base all'harness e il CLI rifiuta combinazioni non supportate.

    Verifica la macchina e i suoi eventi:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## Aggiungi un percorso sessione non predefinito

<Tabs>
  <Tab title="Dashboard">
    I percorsi extra sono registrati sulla macchina, non in Cloud. Dopo averne aggiunto uno, apri **Observe → Sessions**, filtra per l'ambiente della macchina e conferma che le sessioni dal nuovo percorso appaiono. Apri una sessione e controlla l'agente, l'harness e i timestamp degli eventi prima di affidarti a essa in un audit.

    ![L'elenco Sessions filtrato per l'ambiente che riceve dati dal percorso di capture aggiuntivo.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Aggiungi un percorso con un'etichetta opzionale, quindi ispeziona i percorsi configurati:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Rimuovi un percorso con `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  Esegui una nuova sessione dopo l'installazione. Verifica sia il flusso di eventi live che una decisione di policy effettiva prima di espandere il rollout.
</Tip>
