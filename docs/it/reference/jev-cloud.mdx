Questo è il riferimento della route Cloud per le [policy Jev](/it/policies/jev). Jev, il classificatore di TypeSafe, legge ogni tool call rispetto a quello che hai effettivamente richiesto e risponde insieme alle tue policy, mai al loro posto. Attraverso **FailproofAI Cloud**, una macchina connessa usa Jev con la stessa chiave con cui si connette già: nessun account TypeSafe, nessuna seconda chiave, nessun endpoint da configurare. Ogni call è addebitata alla franchigia del piano esistente della tua organizzazione.

Tutto ciò che Jev fa rimane invariato rispetto alla [configurazione bring-your-own-key](/it/reference/jev-providers): le policy hard rimangono finali, il deny di una policy revisionabile viene cancellato solo quando Jev è stato interrogato su quella preoccupazione esatta, e qualsiasi errore ricade al risultato regex per quella call.

<Note>
Richiede **failproofai 1.0.8-beta.0** o successivo. La versione 1.0.7 non ha Jev, anche se si ordina sopra i beta 1.0.7. Senza una configurazione Jev non cambia nulla: gli hook eseguono le policy regex esattamente come hanno sempre fatto.
</Note>

## Prima di iniziare

Installa Failproof AI sulla macchina dove gira il tuo agent e allega i suoi hook a un [harness supportato](/it/reference/harnesses). Se stai iniziando da zero, segui il [quickstart](/it/start/quickstart) fino all'installazione dell'hook. Controlla il CLI installato con `failproofai --version`; aggiornalo se risale a prima di Jev. Ti serve anche l'accesso alla pagina **settings → api keys** della tua organizzazione per creare una chiave di macchina.

Jev revisiona le named tool call al gate `PreToolUse` o `PermissionRequest`. Non revisiona ogni evento in una sessione. Per vedere Jev cancellare un deny di policy, hai bisogno di una policy installata contrassegnata come [revisionabile](/it/policies/authority); tutti gli altri deny di policy rimangono finali.

## Attivalo

1. **Crea una chiave con Jev.** Nel dashboard di FailproofAI Cloud, apri **settings → api keys** e, nel modulo **new key**, scegli **a machine running failproofai**. Concede i tre permessi di cui ha bisogno una macchina: `events:add` (invia attività), `policies:pull` (ricevi policy) e `jev:evaluate` (Jev, addebitato al piano della tua organizzazione). Una chiave non può avere `jev:evaluate` senza gli altri due.
2. **Connetti la macchina** con quella chiave. Leggi il suo segreto monouso a un prompt, quindi esegui il comando di configurazione completo:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` installa il daemon, allega hook per i CLI dell'agent che trova, e connette la macchina. La variabile d'ambiente mantiene la chiave fuori dagli argomenti del comando e dalla cronologia della shell. Se il tuo harness è stato installato successivamente, [allegalo esplicitamente](/it/start/quickstart).

   Se la tua organizzazione esegue il proprio FailproofAI Cloud anziché quello ospitato, aggiungi il suo indirizzo: `--url https://<your dashboard host>` (oppure esporta `FAILPROOFAI_CLOUD_URL`). Senza di esso la chiave viene verificata contro il servizio ospitato e la connessione fallisce. Se il certificato di quell'host viene da una CA privata, installa la CA nell'archivio di fiducia di sistema della macchina (ad esempio con `update-ca-certificates`), non solo in `NODE_EXTRA_CA_CERTS`: il daemon che invia eventi e riceve policy legge l'archivio di sistema. Vedi [Troubleshooting](/it/reference/troubleshooting).

Questo è tutto. La connessione memorizza la chiave e, quando la macchina **non ha** ancora una configurazione Jev, ne scrive una per FailproofAI Cloud. Dal primo deployment della macchina (entro circa 30 s) FailproofAI Cloud imposta la modalità: `enforce` mentre una policy Jev è distribuita ad essa, `off` quando nessuna lo è (vedi [Chi imposta la modalità](#who-sets-the-mode)). L'output lo dice:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

I controlli che FailproofAI Cloud distribuisce vengono eseguiti su Cloud. Per aggiungere controlli tuoi sulla macchina, installa un pack:

```bash
failproofai policies add FailproofAI/jev-policies
```

**Con `--no-transcripts`, la connessione non attiva Jev.** Jev invia ogni tool call controllato e il prompt recente a FailproofAI Cloud, che è più di quello che una connessione solo decisioni è stata chiesta di inviare. La chiave viene comunque memorizzata, e l'output dice che Jev è disponibile e come attivarlo:

```bash
failproofai jev setup --provider failproofai
```

Attiva anche Jev attraverso FailproofAI Cloud **off**. Un `jev.json` che esegue Jev attraverso FailproofAI Cloud (lasciato da una connessione precedente con trascritti attivi) viene rimosso, seguendo la stessa regola che `config --disconnect` usa, e l'output dice che Jev via FailproofAI Cloud rimane off su questa macchina. Un `jev.json` per il tuo endpoint Jev viene lasciato com'è, e così è uno di FailproofAI Cloud che hai disattivato (`--mode off`).

<Warning>
La connessione **non sovrascrive mai** un `~/.failproofai/jev.json` esistente. Se usi già il tuo endpoint Jev, continua a essere usato, e l'output dice che il file è stato lasciato configurato — e, quando quel file lascia Jev off (rifiutato, o disattivato), lo dice e come risolverlo. Per cambiare quella macchina a FailproofAI Cloud, esegui `failproofai jev setup --provider failproofai`.
</Warning>

## Chi imposta la modalità

Su una macchina connessa a FailproofAI Cloud, **FailproofAI Cloud imposta la modalità Jev**; nulla sulla macchina lo fa:

- `enforce` mentre qualsiasi policy Jev (o regex + Jev) è distribuita alla macchina: ogni tool call controllato da un agent che una di quelle policy rivolge va a FailproofAI Cloud, che chiede i suoi controlli insieme ai controlli dei pack installati lì. Una call da un agent che nessuna policy Jev Cloud rivolge, senza suo controllo pack, non viene inviata affatto. In `enforce`, i controlli di deny di Jev stesso bloccano le call così come cancellano i verdetti regex che rivedono.
- `off` quando nessuno lo è: nessun Jev affatto, qualunque cosa `jev.json` dica.

Per provare una policy Jev prima che agisca, distribuiscila con effetto **observe**: i suoi controlli vengono comunque chiesti, e quello che avrebbero fatto è registrato come un **would-have** sotto **fix → activity**, ma non blocca mai una call e non ne cancella una. `failproofai jev setup --mode` e il commutatore **Settings → Jev** del dashboard locale dicono che la modalità è gestita da FailproofAI Cloud e non cambiano nulla. `jev.json` non viene usato per i controlli di Cloud, anche se nomina un altro provider. `failproofai config --disconnect` restituisce Jev al `jev.json` della macchina.

`failproofai jev status` allora dice `Jev checks run on FailproofAI Cloud (mode: enforce)`. Nomina anche i controlli che rivedono ogni policy `both`. La pagina della flotta mostra perché una macchina con una modalità non può chiedere:

- `transcripts_disabled`: la macchina è stata connessa con `--no-transcripts`, che non attiva mai Jev.
- `jev_unconfigured`: la chiave della macchina non ha `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud ha rifiutato alcune call della macchina per il limite di velocità Jev dell'organizzazione, e quelle call sono state decise solo dalle policy regex.
- `jev_unavailable`: diverse call di fila hanno fallito, quindi la macchina salta il Jev di FailproofAI Cloud per un minuto alla volta. Riprova da sola.

Se FailproofAI Cloud non risponde entro 5 secondi, le policy regex decidono da sole, come per qualsiasi interruzione Jev. Dopo 3 fallimenti di fila la macchina smette di chiedere per un minuto alla volta, quindi un'interruzione Cloud non rallenta ogni tool call.

Una pausa di sessione (`failproofai config --pause`) non ferma i controlli Jev di FailproofAI Cloud, proprio come non ferma le policy gestite da Cloud. Mette in pausa i controlli Jev dei pack installati sulla macchina.

## Controlla cosa sta facendo

```bash
failproofai jev status
failproofai jev test
```

`status` mostra il provider come **FailproofAI Cloud**, l'host Cloud a cui la macchina si è connessa, la modalità, e la fonte della chiave come **FailproofAI Cloud connection**, mai la chiave. Quando un `jev.json` di FailproofAI Cloud è in posizione ma Jev non può eseguire, dice perché:

| `status` dice | `status --json` | Significato |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | La macchina è connessa, ma nessuna chiave Jev è memorizzata per essa: la chiave non ha `jev:evaluate`, o la connessione non ha potuto confermarlo. Esegui `failproofai config` di nuovo con la chiave in `FAILPROOFAI_CLOUD_TOKEN`; se non ha il permesso, usa una chiave **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Non c'è connessione a FailproofAI Cloud su questa macchina per cui la chiave Jev appartiene. |

Dopo `failproofai config --disconnect` non c'è più `jev.json` di FailproofAI Cloud (a meno che non sia stato disattivato, che viene mantenuto), quindi `status` semplicemente riporta Jev come off. `status --json` riporta gli stessi fatti (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), anche quando la configurazione è assente o rifiutata. `permissions` è sempre quella di `jev.json`; un rifiuto su `credentials.json` aggiunge `credentialsPermissions`, e `fix` quando un comando lo risolve. `test` invia una richiesta live e riporta la sua latenza e la versione Jev che ha risposto. Esce con 1, e lo dice nel suo titolo, quando la risposta arriva dopo il timeout dell'hook (gli hook registrerebbero `timeout`) o risponde male alla sua domanda di controllo.

Il pannello **Settings → Jev** del dashboard locale mostra anche la **connessione FailproofAI Cloud**: quale organizzazione la macchina riporta e se la sua chiave ha Jev. È letto dai file della macchina stessa, senza call di rete.

## Verifica una call reale

Avvia una nuova sessione nell'agent connesso. Chiedile di usare il suo tool di lettura file su `README.md` e riportare il titolo. Conferma che la sessione contiene quella tool call, quindi esegui `failproofai jev status` di nuovo: il suo conteggio di call valutate di recente dovrebbe aumentare. Apri **Policies → Activity** nel [dashboard locale](/it/reference/local-dashboard#review-policy-activity) per ispezionare il verdetto Jev di quella call e la modalità. In Cloud, **fix → activity** mostra risultati Jev per l'attività consegnata. In modalità observe, il verdetto è registrato come un **would-have** e il risultato della policy decide comunque la call. Una cancellazione appare solo quando una policy revisionabile corrisponde e Jev cancella i suoi controlli denominati.

## Cosa raggiunge la pagina della policy

La macchina invia già la sua hook activity a FailproofAI Cloud (`events:add`). Con Jev attivo, il record di ogni call gated dice anche quale valutatore ha eseguito, cosa Jev ha deciso, quali policy ha cancellato, perché è caduto quando lo ha fatto, la sua latenza e il modello che ha risposto — decisioni, codici e nomi, mai il comando o il tuo prompt. In Cloud, sotto **fix → activity**:

- una call il cui verdetto Jev ha deciso (modalità enforce) è attribuita a **Jev**, e quando il controllo decisivo è venuto da un pack, il record nomina anche quel pack e la sua versione;
- in modalità observe, il deny o warning di Jev appare come un **would-have**, accanto ai rollout che stai osservando;
- le policy Jev ha cancellato, o avrebbe cancellato in modalità observe, vengono conteggiate per policy.
- una decisione in cui Jev ha preso parte (un blocco, un warning, una cancellazione, o un would-have in modalità observe) elenca ogni controllo che ha chiesto e cosa quel controllo ha concluso: verdetto, perché (`not-detected`, `exempt`, `fired`, `op-requested`, …), la sua evidenza `p`, la risposta `exempt` e la risposta di ogni probe. Un controllo di una policy distribuita per osservare (observe) è elencato anche, contrassegnato come watched; non blocca mai. Jev risponde con probabilità, non prosa, quindi non c'è motivo di testo libero. I plain allow si aggregano in conteggi e non portano questo elenco.

## Quando Jev non può rispondere

Ognuno di questi ricade al risultato delle tue policy per quella call, ed è registrato con il suo motivo:

| Motivo | Causa |
| --- | --- |
| `out-of-credits` | La tua organizzazione ha usato la franchigia del suo piano. |
| `http-401`, `http-403` | La chiave è stata revocata, o non ha `jev:evaluate`. Riconnetti con una chiave che ce l'ha. |
| `http-429` | FailproofAI Cloud sta limitando la velocità di Jev per la tua organizzazione. Fino a quando l'attesa che richiede finisce (il suo `Retry-After`, al massimo 60 secondi), la macchina non le invia nulla e ogni call ricade subito. Le call trattenute in quel modo sono registrate come `http-429`, o come `rate-limited` quando il limite di velocità della macchina stessa le trattiene per primo. |
| `http-429` (limite giornaliero) | La tua organizzazione ha usato le sue call Jev giornaliere: **10.000 per giorno UTC**, a meno che chi gestisce il tuo FailproofAI Cloud non abbia impostato un altro limite. Ogni call ricade fino a quando il conteggio si ripristina alle 00:00 UTC; la macchina richiede comunque al massimo una volta al minuto, quindi lo raccoglie entro un minuto. `failproofai jev test` dice "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev ha rifiutato la richiesta di questa call, solitamente perché la tool call conteneva testo denso (base64, hex, codice minificato) oltre il budget di token di Jev. Quella call ricade ogni volta; non è un'interruzione. |
| `http-502` | Jev non è disponibile in questo momento. |
| `http-503` | Questo Cloud non può servire Jev per la tua org: nessun gateway di modello, un'org non ancora provisioned, o il gateway è down. Chiedi al tuo admin; gli hook chiedono di nuovo al massimo una volta al minuto. |
| `http-404` | Questo FailproofAI Cloud non serve ancora Jev. |
| `timeout` | Nessuna risposta entro `timeoutMs` (default 3000). Mentre FailproofAI Cloud imposta la modalità Jev della macchina, l'attesa è 5000 ms e il `timeoutMs` di `jev.json` non viene usato. |
| `model-mismatch` | Una versione Jev diversa da 1.13 ha risposto. |

## Dove vive la chiave, e dove va

- La chiave è memorizzata una volta, in `~/.failproofai/credentials.json` (`0600`, in una directory di solo proprietario), insieme alle altre credenziali di FailproofAI Cloud. `jev.json` non contiene chiave per questa route; una scritta lì rende la configurazione non valida.
- Se `credentials.json` ha **qualsiasi** permesso per chiunque non sia tu (gruppo o altri, lettura o scrittura), o la sua directory può essere **scritta** da chiunque non sia tu, è **rifiutata**, non letta, e Jev è off fino a quando non la fissi: `chmod 600` sul file, `chmod 700` sulla directory (oppure riconnetti, che riscrive il file a `0600` e rende la directory di solo proprietario). Una directory che gli altri possono solo leggere va bene; una che possono scrivere li lascia scambiare il file.
- La chiave conta solo mentre la connessione da cui è venuta è sulla macchina: una policy o credenziale di reporting per lo stesso FailproofAI Cloud **con la stessa chiave**, nello stesso file. Una chiave Jev lasciata indietro senza una è ignorata, e Jev rimane off. Questo accade quando il `config --disconnect` di un failproofai più vecchio lascia la chiave Jev in posizione (non sa di rimuoverla), o quando il `config --token` di un failproofai più vecchio si connette con un'altra chiave, che su FailproofAI Cloud può appartenere a un'altra organizzazione. Per attivare Jev di nuovo, connetti di nuovo con una chiave **machine**.
- La chiave viene mai inviata se non all'origine Cloud contro cui è stata verificata. Un `jev.json` che punta da qualche altra parte è rifiutato.
- **Un agent sulla macchina può leggerla.** `credentials.json` è di solo proprietario, e l'agent gira come quel proprietario. La lettura dei file di failproofai stesso è consentita di proposito (solo cambiarli è bloccato, da `block-failproofai-commands`), quindi l'unica cosa tra un agent e questo file è `block-read-outside-cwd` — una policy *revisionabile* — e da una sessione iniziata nella tua directory home, nulla. Una chiave con `jev:evaluate` spende la franchigia Jev della tua organizzazione (fino al limite giornaliero) da qualunque luogo sia usata, quindi tratta una chiave di macchina come qualsiasi altra credenziale di spesa: se un agent potrebbe averla letta, revocala su **settings → api keys** e riconnetti con una nuova.
- Solo i tuoi file globali decidono questo. Un repository non può attivare Jev Cloud, puntarlo altrove o fornire la sua chiave, e `FAILPROOFAI_JEV_API_KEY` è ignorata per questa route.
- Per ogni call che Jev valuta, una richiesta va a FailproofAI Cloud, portando quello che la [pagina bring-your-own-key](/it/reference/jev-providers#what-leaves-the-machine) elenca (segreti oscurati). FailproofAI Cloud l'invia a TypeSafe e non la registra o la mantiene.

## Disattivalo

Su una macchina connessa, Jev è off quando FailproofAI Cloud non distribuisce nessuna policy Jev ad essa: rimuovi o archivia le policy Jev lì.

| Comando | Risultato |
| --- | --- |
| Rimuovi le policy Jev della macchina in FailproofAI Cloud | La modalità di Cloud diventa `off` al prossimo polling (circa 30 s): nessun Jev affatto, qualunque cosa `jev.json` dica. |
| `failproofai config --disconnect` | Disconnetti la macchina: la chiave viene rimossa, e così è `jev.json` quando nomina FailproofAI Cloud e non è disattivato. Un `jev.json` per il tuo endpoint rimane. |

Dalla prossima tool call, gli hook eseguono le policy regex esattamente come prima.
