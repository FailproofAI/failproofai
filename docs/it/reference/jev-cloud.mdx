Questo è il riferimento del percorso Cloud per le [policy Jev](/it/policies/jev). Jev, il classificatore di TypeSafe, legge ogni tool call rispetto a ciò che hai effettivamente richiesto e risponde insieme alle tue policy, mai al loro posto. Attraverso **FailproofAI Cloud**, una machine connessa utilizza Jev con la stessa chiave con cui si connette già: nessun account TypeSafe, nessuna seconda chiave, nessun endpoint da configurare. Ogni chiamata viene addebitata all'allowance del piano esistente della tua organizzazione.

Tutto ciò che Jev fa rimane invariato rispetto alla [configurazione bring-your-own-key](/it/reference/jev-providers): le hard policy rimangono finali, il deny di una policy reviewable viene cancellato solo quando Jev è stato interrogato esattamente su quella preoccupazione, e qualsiasi errore ricade nel risultato regex per quella chiamata.

<Note>
Richiede **failproofai 1.0.8-beta.0** o successivo. 1.0.7 non ha Jev, anche se ordina sopra i beta 1.0.7. Senza una configurazione Jev nulla cambia: gli hook eseguono le policy regex esattamente come hanno sempre fatto.
</Note>

## Prima di iniziare

Installa Failproof AI sulla machine dove viene eseguito il tuo agent e collega i suoi hook a un [harness supportato](/it/reference/harnesses). Se stai iniziando da zero, segui il [quickstart](/it/start/quickstart) fino all'installazione dell'hook. Controlla la CLI installata con `failproofai --version`; aggiornala se è precedente a Jev. Hai anche bisogno dell'accesso alla pagina **Administration → Keys** della tua organizzazione per creare una machine key.

Jev esamina le tool call nominate al gate `PreToolUse` o `PermissionRequest`. Non esamina ogni evento in una sessione. Per vedere Jev cancellare un deny di policy, hai bisogno di una policy installata contrassegnata come [reviewable](/it/policies/authority); tutti gli altri deny di policy rimangono finali.

## Attivalo

1. **Crea una chiave con Jev.** Nel dashboard FailproofAI Cloud, apri **Administration → Keys → Create key** e scegli il preset **machine**. Concede i tre permessi di cui una machine ha bisogno: `events:add` (invia attività), `policies:pull` (ricevi policy) e `jev:evaluate` (Jev, addebitato al piano della tua organizzazione). Una chiave non può avere `jev:evaluate` senza gli altri due.
2. **Connetti la machine** con quella chiave. Leggi il suo segreto monouso a un prompt, quindi esegui il comando di configurazione completo:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` installa il daemon, collega gli hook per gli agent CLI che trova e connette la machine. La variabile d'ambiente mantiene la chiave fuori dagli argomenti del comando e dalla cronologia della shell. Se il tuo harness è stato installato successivamente, [collegalo esplicitamente](/it/start/quickstart).

   Se la tua organizzazione esegue il suo FailproofAI Cloud piuttosto che quello hosted, aggiungi il suo indirizzo: `--url https://<your dashboard host>` (o esporta `FAILPROOFAI_CLOUD_URL`). Senza di esso la chiave viene controllata rispetto al servizio hosted e la connessione fallisce. Se il certificato di quel host proviene da una CA privata, installa la CA nell'archivio di fiducia di sistema della machine (ad esempio con `update-ca-certificates`), non solo in `NODE_EXTRA_CA_CERTS`: il daemon che invia eventi e recupera le policy legge l'archivio di sistema. Vedi [Troubleshooting](/it/reference/troubleshooting).

È tutto. La connessione memorizza la chiave e, quando la machine **non** ha ancora una configurazione Jev, ne scrive una per FailproofAI Cloud. Dalla prima distribuzione della machine (entro circa 30 s) FailproofAI Cloud imposta la modalità: `enforce` mentre una policy Jev viene distribuita ad essa, `off` quando non lo è (vedi [Chi imposta la modalità](#who-sets-the-mode)). L'output dice così:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

I controlli che FailproofAI Cloud distribuisce vengono eseguiti su Cloud. Per aggiungere controlli tuoi sulla machine, installa un pack:

```bash
failproofai policies add FailproofAI/jev-policies
```

**Con `--no-transcripts`, la connessione non attiva Jev.** Jev invia ogni tool call verificato e il prompt recente a FailproofAI Cloud, il che è più di una connessione solo decisioni a cui è stato chiesto di inviare. La chiave viene comunque memorizzata e l'output dice che Jev è disponibile e come attivarlo:

```bash
failproofai jev setup --provider failproofai
```

Lo attiva anche per Jev attraverso FailproofAI Cloud **off**. Un `jev.json` che esegue Jev attraverso FailproofAI Cloud (lasciato da una connessione precedente con i transcript attivi) viene rimosso, secondo la stessa regola che `config --disconnect` usa, e l'output dice che Jev via FailproofAI Cloud rimane off su questa machine. Un `jev.json` per il tuo endpoint Jev è lasciato com'è, così come uno di FailproofAI Cloud che hai disattivato (`--mode off`).

<Warning>
La connessione **non sovrascrive mai** un `~/.failproofai/jev.json` esistente. Se utilizzi già il tuo endpoint Jev, continua ad essere utilizzato e l'output dice che il file è stato lasciato configurato — e, quando quel file lascia Jev off (rifiutato o disattivato), lo dice e come risolverlo. Per passare questa machine a FailproofAI Cloud, esegui `failproofai jev setup --provider failproofai`.
</Warning>

## Chi imposta la modalità

Su una machine connessa a FailproofAI Cloud, **FailproofAI Cloud imposta la modalità Jev**; nulla sulla machine lo fa:

- `enforce` mentre qualsiasi policy Jev (o regex + Jev) è distribuita alla machine: ogni tool call verificato da un agent che una di quelle policy target va a FailproofAI Cloud, che chiede i suoi controlli insieme ai controlli dei pack installati lì. Una chiamata da un agent che nessuna policy Cloud Jev target, senza controllo pack proprio, non viene inviata affatto. In `enforce`, i propri controlli deny di Jev bloccano le chiamate così come cancellano i verdetti regex che esaminano.
- `off` quando non lo è: nessun Jev affatto, indipendentemente da ciò che `jev.json` dice.

Per provare una policy Jev prima che agisca, distribuiscila con effetto **observe**: i suoi controlli vengono comunque chiesti e ciò che avrebbero fatto è registrato come un **would-have** sulla pagina della policy, ma non blocca mai una chiamata e non ne cancella mai una. `failproofai jev setup --mode` e il dashboard's **Settings → Jev** dicono che la modalità è gestita da FailproofAI Cloud e non cambiano nulla. `jev.json` non viene utilizzato per i controlli di Cloud, anche se nomina un altro provider. `failproofai config --disconnect` restituisce Jev al proprio `jev.json` della machine.

`failproofai jev status` quindi dice `Jev checks run on FailproofAI Cloud (mode: enforce)`. Nomina anche i controlli che esaminano ogni policy `both`. La pagina della flotta mostra perché una machine con una modalità non può chiedere:

- `transcripts_disabled`: la machine è stata connessa con `--no-transcripts`, che non attiva mai Jev.
- `jev_unconfigured`: la chiave della machine non ha `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud ha rifiutato alcune delle chiamate della machine per il limite di velocità Jev dell'organizzazione e quelle chiamate sono state decise dalle sole policy regex.
- `jev_unavailable`: diversi fallimenti di fila, quindi la machine salta Jev di FailproofAI Cloud per un minuto alla volta. Riprova da sola.

Se FailproofAI Cloud non risponde entro 5 secondi, le policy regex decidono da sole, come per qualsiasi interruzione di Jev. Dopo 3 fallimenti di fila la machine smette di chiedere per un minuto alla volta, quindi un'interruzione di Cloud non rallenta ogni tool call.

Una pausa della sessione (`failproofai config --pause`) non interrompe i controlli Jev di FailproofAI Cloud, proprio come non interrompe le policy gestite da Cloud. Mette in pausa i controlli Jev dei pack installati sulla machine.

## Controlla ciò che sta facendo

```bash
failproofai jev status
failproofai jev test
```

`status` mostra il provider come **FailproofAI Cloud**, l'host Cloud a cui la machine si è connessa, la modalità e la fonte della chiave come **FailproofAI Cloud connection**, mai la chiave. Quando un `jev.json` di FailproofAI Cloud è in posizione ma Jev non può eseguire, dice perché:

| `status` dice | `status --json` | Significato |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | La machine è connessa, ma nessuna chiave Jev è memorizzata per essa: la chiave manca di `jev:evaluate`, o la connessione non ha potuto confermarlo. Esegui di nuovo `failproofai config` con la chiave in `FAILPROOFAI_CLOUD_TOKEN`; se manca del permesso, utilizza una chiave **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Non c'è una connessione FailproofAI Cloud su questa machine a cui la chiave Jev possa appartenere. |

Dopo `failproofai config --disconnect` non c'è più nessun `jev.json` di FailproofAI Cloud (a meno che non sia stato disattivato, che viene mantenuto), quindi `status` semplicemente riporta Jev come off. `status --json` porta gli stessi fatti (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), anche quando la configurazione è assente o rifiutata. `permissions` è sempre quella di `jev.json`; un rifiuto riguardante `credentials.json` aggiunge `credentialsPermissions` e `fix` quando un comando lo risolve. `test` invia una richiesta live e riporta la sua latenza e la versione di Jev che ha risposto. Esce 1 e lo dice nel suo titolo quando la risposta arriva dopo il timeout dell'hook (gli hook registrerebbero `timeout`) o risponde erroneamente alla sua domanda di controllo.

Il pannello **Settings → Jev** del dashboard mostra anche la **FailproofAI Cloud connection**: quale organizzazione la machine segnala e se la sua chiave ha Jev. Viene letto dai propri file della machine, senza nessuna chiamata di rete.

## Verifica una chiamata reale

Avvia una nuova sessione nell'agent con hook. Chiedigli di utilizzare il suo tool di lettura file su `README.md` e di segnalare il titolo. Conferma che la sessione contiene quella tool call, quindi esegui di nuovo `failproofai jev status`: il suo conteggio delle chiamate valutate recenti dovrebbe aumentare. Apri **Policies → Activity** nel [local dashboard](/it/reference/local-dashboard#review-policy-activity) per ispezionare il verdetto Jev di quella chiamata e la modalità. In Cloud, la pagina **Policies** dell'organizzazione mostra i risultati Jev per l'attività consegnata. In modalità observe, il verdetto è registrato come un **would-have** e il risultato della policy decide comunque la chiamata. Una cancellazione appare solo quando una policy reviewable corrisponde e Jev cancella i suoi controlli nominati.

## Cosa raggiunge la pagina della policy

La machine invia già la sua attività hook a FailproofAI Cloud (`events:add`). Con Jev attivo, il record di ogni chiamata gated dice anche quale valutatore è stato eseguito, cosa ha deciso Jev, quali policy ha cancellato, perché è ricaduto quando lo ha fatto, la sua latenza e il modello che ha risposto — decisioni, codici e nomi, mai il comando o il tuo prompt. Sulla pagina **Policies** della tua organizzazione:

- una chiamata il cui verdetto proprio di Jev ha deciso (modalità enforce) è attribuita a **Jev** e quando il controllo decisivo proveniva da un pack, il record nomina anche quel pack e la sua versione;
- in modalità observe, il deny o l'avviso di Jev appare come un **would-have**, accanto ai rollout che stai osservando;
- le policy Jev ha cancellato, o avrebbe cancellato in modalità observe, vengono contate per policy.
- una decisione in cui Jev ha preso parte (un blocco, un avviso, una cancellazione, o un would-have in modalità observe) elenca ogni controllo che ha chiesto e quale conclusione ha raggiunto quel controllo: verdetto, perché (`not-detected`, `exempt`, `fired`, `op-requested`, …), la sua evidenza `p`, la risposta `exempt` e la risposta di ogni probe. Un controllo di una policy distribuita per osservare (observe) è elencato anche, marcato watched; non blocca mai. Jev risponde con probabilità, non prosa, quindi non c'è nessuna ragione in testo libero. I semplici allow si arrotolano in conteggi e non portano questo elenco.

## Quando Jev non può rispondere

Ognuno di questi ricade al risultato delle tue policy per quella chiamata ed è registrato con il suo motivo:

| Motivo | Causa |
| --- | --- |
| `out-of-credits` | La tua organizzazione ha utilizzato l'allowance del suo piano. |
| `http-401`, `http-403` | La chiave è stata revocata o non ha `jev:evaluate`. Riconnettiti con una chiave che lo ha. |
| `http-429` | FailproofAI Cloud sta limitando la velocità di Jev per la tua organizzazione. Fino a quando l'attesa che chiede è finita (il suo `Retry-After`, al massimo 60 secondi), la machine non invia nulla e ogni chiamata ricade subito. Le chiamate trattenute in quel modo sono registrate come `http-429`, o come `rate-limited` quando il limite di velocità proprio della machine le trattiene per prima. |
| `http-429` (limite giornaliero) | La tua organizzazione ha utilizzato le sue chiamate Jev giornaliere: **10.000 per giorno UTC**, a meno che chiunque gestisca il tuo FailproofAI Cloud non abbia impostato un altro limite. Ogni chiamata ricade fino a quando il conteggio si reimposta a 00:00 UTC; la machine continua a chiedere al massimo una volta al minuto, quindi lo raccoglie entro un minuto. `failproofai jev test` dice "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev ha rifiutato la richiesta di questa chiamata, di solito perché la tool call conteneva testo denso (base64, hex, codice minificato) sopra il budget dei token di Jev. Quella chiamata ricade ogni volta; non è un'interruzione. |
| `http-502` | Jev non è disponibile in questo momento. |
| `http-503` | Questo Cloud non può servire Jev per la tua org: nessun gateway del modello, un'org non ancora fornita, o il gateway è inattivo. Chiedi al tuo amministratore; gli hook chiedono di nuovo al massimo una volta al minuto. |
| `http-404` | Questo FailproofAI Cloud non serve ancora Jev. |
| `timeout` | Nessuna risposta entro `timeoutMs` (predefinito 3000). Mentre FailproofAI Cloud imposta la modalità Jev della machine, l'attesa è di 5000 ms e `timeoutMs` di `jev.json` non viene utilizzato. |
| `model-mismatch` | Una versione di Jev diversa da 1.13 ha risposto. |

## Dove vive la chiave e dove va

- La chiave è memorizzata una volta, in `~/.failproofai/credentials.json` (`0600`, in una directory solo per il proprietario), accanto alle altre credenziali FailproofAI Cloud. `jev.json` non tiene nessuna chiave per questo percorso; una scritta lì rende la configurazione non valida.
- Se `credentials.json` ha **qualsiasi** permesso per chiunque diverso da te (gruppo o altri, lettura o scrittura), o la sua directory può essere **scritta** da chiunque diverso da te, è **rifiutata**, non letta, e Jev è off fino a quando non la correggi: `chmod 600` sul file, `chmod 700` sulla directory (o riconnettiti, che riscrive il file a `0600` e rende la directory solo per il proprietario). Una directory che altri possono solo leggere va bene; una che possono scrivere li lascia scambiare il file.
- La chiave conta solo mentre la connessione da cui proveniva è sulla machine: una credenziale policy o di segnalazione per lo stesso FailproofAI Cloud **con la stessa chiave**, nello stesso file. Una chiave Jev lasciata indietro senza una viene ignorata e Jev rimane off. Ciò accade quando la `config --disconnect` di un failproofai più vecchio lascia la chiave Jev in posizione (non sa come rimuoverla), o quando la `config --token` di un failproofai più vecchio si connette con un'altra chiave, che su FailproofAI Cloud può appartenere a un'altra organizzazione. Per riattivare Jev, riconnettiti con una chiave **machine**.
- La chiave viene inviata solo all'origine di Cloud rispetto alla quale è stata verificata. Un `jev.json` che punta da qualsiasi altra parte è rifiutato.
- **Un agent sulla machine può leggerla.** `credentials.json` è solo per il proprietario e l'agent esegue come quel proprietario. La lettura dei file failproofai è consentita di proposito (solo cambiarli è bloccato, da `block-failproofai-commands`), quindi l'unica cosa tra un agent e questo file è `block-read-outside-cwd` — una policy *reviewable* — e da una sessione avviata nella tua home directory, nulla. Una chiave con `jev:evaluate` spende l'allowance Jev della tua organizzazione (fino al limite giornaliero) da qualsiasi luogo venga utilizzata, quindi tratta una machine key come qualsiasi altra credenziale di spesa: se un agent potrebbe averla letta, disabilitala sulla pagina Keys e riconnettiti con una nuova.
- Solo i tuoi file globali decidono questo. Un repository non può attivare Cloud Jev, puntarlo altrove o fornire la sua chiave, e `FAILPROOFAI_JEV_API_KEY` viene ignorato per questo percorso.
- Per ogni chiamata che Jev valuta, una richiesta va a FailproofAI Cloud, contenente ciò che la [pagina bring-your-own-key](/it/reference/jev-providers#what-leaves-the-machine) elenca (segreti redatti). FailproofAI Cloud la invia a TypeSafe e non la registra o la conserva.

## Disattivalo

Su una machine connessa, Jev è off quando FailproofAI Cloud non distribuisce nessuna policy Jev ad essa: rimuovi o archivia le policy Jev lì.

| Comando | Risultato |
| --- | --- |
| Rimuovi le policy Jev della machine in FailproofAI Cloud | La modalità di Cloud diventa `off` al prossimo poll (circa 30 s): nessun Jev affatto, indipendentemente da ciò che `jev.json` dice. |
| `failproofai config --disconnect` | Disconnetti la machine: la chiave viene rimossa e così `jev.json` quando nomina FailproofAI Cloud e non è disattivato. Un `jev.json` per il tuo endpoint rimane. |

Dalla prossima tool call, gli hook eseguono le policy regex esattamente come prima.
