Questo è il riferimento della rotta Cloud per le [politiche Jev](/it/policies/jev). Jev, il classificatore di TypeSafe, legge ogni chiamata di tool rispetto a quello che hai effettivamente richiesto e risponde insieme alle tue politiche, mai al loro posto. Attraverso **FailproofAI Cloud**, una macchina connessa usa Jev con la stessa chiave con cui si connette già: nessun account TypeSafe, nessuna seconda chiave, nessun endpoint da configurare. Ogni chiamata viene addebitata all'allocazione del piano esistente della tua organizzazione.

Tutto quello che Jev fa rimane invariato dalla [configurazione con chiave propria](/it/reference/jev-providers): le politiche rigide rimangono definitive, il rifiuto di una politica revisionabile viene cancellato solo quando Jev è stato interrogato su quella preoccupazione esatta, e qualsiasi errore ricade al risultato regex per quella chiamata.

<Note>
Richiede **failproofai 1.0.8-beta.0** o successivo. La 1.0.7 non ha Jev, anche se si ordina sopra i beta 1.0.7. Senza una configurazione Jev non cambia nulla: gli hook eseguono le politiche regex esattamente come hanno sempre fatto.
</Note>

## Prima di iniziare

Installa Failproof AI sulla macchina dove esegue il tuo agent e collega i suoi hook a un [harness supportato](/it/reference/harnesses). Se stai iniziando da zero, segui il [quickstart](/it/start/quickstart) fino all'installazione dell'hook. Controlla la CLI installata con `failproofai --version`; aggiornala se precede Jev. Hai anche bisogno dell'accesso alla pagina **settings → api keys** della tua organizzazione per creare una chiave macchina.

Jev revisiona le chiamate di tool denominate al gate `PreToolUse` o `PermissionRequest`. Non revisiona ogni evento in una sessione. Per vedere Jev cancellare un rifiuto di politica, hai bisogno di una politica installata contrassegnata [revisionabile](/it/policies/authority); tutti gli altri rifiuti di politica rimangono definitivi.

## Attivalo

1. **Crea una chiave con Jev.** Nel dashboard di FailproofAI Cloud, apri **settings → api keys** e, nel modulo **new key**, scegli **a machine running failproofai**. Concede i tre permessi di cui ha bisogno una macchina: `events:add` (invia attività), `policies:pull` (ricevi politiche) e `jev:evaluate` (Jev, addebitato al piano della tua organizzazione). Una chiave non può avere `jev:evaluate` senza gli altri due.
2. **Connetti la macchina** con quella chiave. Leggi il suo segreto monouso a un prompt, quindi esegui il comando di configurazione completo:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` installa il daemon, collega gli hook per i CLI dell'agent che trova, e connette la macchina. La variabile d'ambiente mantiene la chiave fuori dagli argomenti del comando e dalla cronologia della shell. Se il tuo harness è stato installato successivamente, [collegalo esplicitamente](/it/start/quickstart).

   Se la tua organizzazione esegue il proprio FailproofAI Cloud anziché quello ospitato, aggiungi il suo indirizzo: `--url https://<your dashboard host>` (oppure esporta `FAILPROOFAI_CLOUD_URL`). Senza di esso la chiave viene verificata contro il servizio ospitato e la connessione fallisce. Se il certificato di quell'host viene da una CA privata, installa la CA nell'archivio di trust di sistema della macchina (ad esempio con `update-ca-certificates`), non solo in `NODE_EXTRA_CA_CERTS`: il daemon che invia eventi e riceve politiche legge l'archivio di sistema. Vedi [Troubleshooting](/it/reference/troubleshooting).

Questo è tutto. La connessione memorizza la chiave e, quando la macchina **non** ha ancora una configurazione Jev, scrive una per FailproofAI Cloud. Dal primo deployment della macchina (entro circa 30 s) FailproofAI Cloud imposta la modalità: `enforce` mentre una politica Jev è distribuita ad essa, `off` quando nessuna lo è (vedi [Chi imposta la modalità](#who-sets-the-mode)). L'output lo dice:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

I controlli che FailproofAI Cloud distribuisce vengono eseguiti su Cloud. Per aggiungere controlli tuoi sulla macchina, installa un pack:

```bash
failproofai policies add FailproofAI/jev-policies
```

**Con `--no-transcripts`, la connessione non attiva Jev.** Jev invia ogni chiamata di tool controllata e il prompt recente a FailproofAI Cloud, che è più di quello che una connessione solo decisioni chiederebbe di inviare. La chiave è comunque memorizzata, e l'output dice che Jev è disponibile e come attivarlo:

```bash
failproofai jev setup --provider failproofai
```

Lo disattiva anche Jev attraverso FailproofAI Cloud. Un `jev.json` che esegue Jev attraverso FailproofAI Cloud (lasciato da una connessione precedente con trascrizioni attive) viene rimosso, dalla stessa regola che `config --disconnect` usa, e l'output dice che Jev via FailproofAI Cloud rimane disattivato su questa macchina. Un `jev.json` per il tuo endpoint Jev è lasciato così com'è, e così è uno di FailproofAI Cloud che hai disattivato (`--mode off`).

<Warning>
La connessione **non sovrascrive mai** un `~/.failproofai/jev.json` esistente. Se usi già il tuo endpoint Jev, continua a essere usato, e l'output dice che il file è stato lasciato configurato — e, quando quel file lascia Jev disattivato (rifiutato, o disattivato), lo dice e come risolverlo. Per passare quella macchina a FailproofAI Cloud, esegui `failproofai jev setup --provider failproofai`.
</Warning>

## Chi imposta la modalità

Su una macchina connessa a FailproofAI Cloud, **FailproofAI Cloud imposta la modalità Jev**; nulla sulla macchina lo fa:

- `enforce` mentre qualsiasi politica Jev (o regex + Jev) è distribuita alla macchina: ogni chiamata di tool controllata da un agent che una di quelle politiche prende di mira va a FailproofAI Cloud, che chiede i suoi controlli insieme ai controlli dei pack installati lì. Una chiamata da un agent che nessuna politica Cloud Jev prende di mira, senza controllo di pack proprio, non viene inviata affatto. In `enforce`, i controlli di rifiuto di Jev bloccano le chiamate così come cancellano i verdetti regex che revisionano.
- `off` quando nessuna lo è: nessun Jev affatto, qualunque cosa dica `jev.json`.

Per provare una politica Jev prima che agisca, distribuiscila con effetto **observe**: i suoi controlli sono comunque chiesti, e quello che avrebbero fatto è registrato come un **would-have** sotto **fix → activity**, ma non blocca mai una chiamata e non cancella mai una. `failproofai jev setup --mode` e il pannello **Settings → Jev** del dashboard locale dicono che la modalità è gestita da FailproofAI Cloud e non cambiano nulla. `jev.json` non è usato per i controlli di Cloud, anche se nomina un altro provider. `failproofai config --disconnect` restituisce Jev al `jev.json` della macchina.

`failproofai jev status` allora dice `Jev checks run on FailproofAI Cloud (mode: enforce)`. Nomina anche i controlli che revisionano ogni politica `both`. La pagina della flotta mostra perché una macchina con una modalità non può chiedere:

- `transcripts_disabled`: la macchina è stata connessa con `--no-transcripts`, che non attiva mai Jev.
- `jev_unconfigured`: la chiave della macchina non ha `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud ha rifiutato alcune delle chiamate della macchina per il limite di velocità Jev dell'organizzazione, e quelle chiamate sono state decise dalle sole politiche regex.
- `jev_unavailable`: diverse chiamate di fila hanno fallito, così la macchina salta Jev di FailproofAI Cloud per un minuto alla volta. Riprova da sola.

Se FailproofAI Cloud non risponde entro 5 secondi, le politiche regex decidono da sole, come per qualsiasi interruzione di Jev. Dopo 3 fallimenti di fila la macchina smette di chiedere per un minuto alla volta, così un'interruzione di Cloud non rallenta ogni chiamata di tool.

Una pausa di sessione (`failproofai config --pause`) non ferma i controlli Jev di FailproofAI Cloud, così come non ferma le politiche gestite dal Cloud. Pausa i controlli Jev dei pack installati sulla macchina.

## Controlla cosa sta facendo

```bash
failproofai jev status
failproofai jev test
```

`status` mostra il provider come **FailproofAI Cloud**, l'host Cloud a cui la macchina si è connessa, la modalità, e la fonte della chiave come **FailproofAI Cloud connection**, mai la chiave. Quando un `jev.json` di FailproofAI Cloud è in posizione ma Jev non può eseguire, dice perché:

| `status` dice | `status --json` | Significato |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | La macchina è connessa, ma nessuna chiave Jev è memorizzata per essa: la chiave manca di `jev:evaluate`, oppure la connessione non ha potuto confermarlo. Esegui `failproofai config` di nuovo con la chiave in `FAILPROOFAI_CLOUD_TOKEN`; se manca il permesso, usa una chiave **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Non c'è una connessione FailproofAI Cloud su questa macchina a cui possa appartenere la chiave Jev. |

Dopo `failproofai config --disconnect` non c'è più un `jev.json` di FailproofAI Cloud (a meno che non sia stato disattivato, che viene mantenuto), quindi `status` semplicemente riferisce Jev come disattivato. `status --json` porta gli stessi fatti (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), anche quando la configurazione è assente o rifiutata. `permissions` è sempre quella di `jev.json`; un rifiuto riguardante `credentials.json` aggiunge `credentialsPermissions`, e `fix` quando un comando lo ripara. `test` invia una richiesta dal vivo e riferisce la sua latenza e la versione Jev che ha risposto. Esce 1, e lo dice nel suo titolo, quando la risposta arriva dopo il timeout dell'hook (gli hook registrerebbero `timeout`) oppure risponde alla sua domanda di controllo erroneamente.

Il pannello **Settings → Jev** del dashboard locale mostra anche la **FailproofAI Cloud connection**: quale organizzazione la macchina riferisce e se la sua chiave ha Jev. È letto dai file della macchina, senza una chiamata di rete.

## Verifica una chiamata reale

Avvia una nuova sessione nell'agent agganciato. Chiedile di usare il suo tool di lettura di file su `README.md` e riferire il titolo. Conferma che la sessione contiene quella chiamata di tool, quindi esegui `failproofai jev status` di nuovo: il suo conteggio di chiamate valutate di recente dovrebbe aumentare. Apri **Policies → Activity** nel [dashboard locale](/it/reference/local-dashboard#review-policy-activity) per ispezionare il verdetto Jev di quella chiamata e la modalità. In Cloud, **fix → activity** mostra risultati Jev per l'attività consegnata. In modalità observe, il verdetto è registrato come un **would-have** e il risultato della politica decide ancora la chiamata. Una cancellazione appare solo quando una politica revisionabile corrisponde e Jev cancella i suoi controlli denominati.

## Cosa raggiunge la pagina della politica

La macchina già invia la sua attività hook a FailproofAI Cloud (`events:add`). Con Jev attivato, il record di ogni chiamata controllata dice anche quale valuatore è stato eseguito, cosa ha deciso Jev, quali politiche ha cancellato, perché è ritornato indietro quando lo ha fatto, la sua latenza e il modello che ha risposto — decisioni, codici e nomi, mai il comando o il tuo prompt. In Cloud, sotto **fix → activity**:

- una chiamata il cui verdetto proprio di Jev ha deciso (modalità enforce) è attribuita a **Jev**, e quando il controllo decisivo veniva da un pack, il record nomina anche quel pack e la sua versione;
- in modalità observe, il rifiuto o l'avvertimento di Jev appare come un **would-have**, accanto ai rollout che stai osservando;
- le politiche che Jev ha cancellato, o avrebbe cancellato in modalità observe, sono conteggiate per politica.
- una decisione in cui Jev ha preso parte (un blocco, un avvertimento, una cancellazione, o un would-have in modalità observe) elenca ogni controllo che ha chiesto e quello che quel controllo ha concluso: verdetto, perché (`not-detected`, `exempt`, `fired`, `op-requested`, …), la sua evidenza `p`, la risposta `exempt` e la risposta di ogni sonda. Un controllo di una politica distribuita per guardare (observe) è elencato anche, contrassegnato guardato; non blocca mai. Jev risponde con probabilità, non prosa, quindi non c'è motivo in testo libero. I semplici allow si aggregano in conteggi e non portano questo elenco.

## Quando Jev non può rispondere

Ognuno di questi ricade al risultato delle tue politiche per quella chiamata, ed è registrato con il suo motivo:

| Motivo | Causa |
| --- | --- |
| `out-of-credits` | La tua organizzazione ha usato l'allocazione del piano. |
| `http-401`, `http-403` | La chiave è stata revocata, oppure non ha `jev:evaluate`. Riconnetti con una chiave che ce l'ha. |
| `http-429` | FailproofAI Cloud sta limitando la velocità di Jev per la tua organizzazione. Fino a quando l'attesa che chiede è finita (il suo `Retry-After`, al massimo 60 secondi), la macchina non le invia nulla e ogni chiamata ricade subito. Le chiamate trattenute in quel modo sono registrate come `http-429`, oppure come `rate-limited` quando il limite di velocità della macchina stessa le trattiene per primo. |
| `http-429` (limite giornaliero) | La tua organizzazione ha usato le sue chiamate Jev giornaliere: **10.000 per giorno UTC**, a meno che chi gestisce il tuo FailproofAI Cloud non abbia impostato un altro limite. Ogni chiamata ricade fino a quando il conteggio si ripristina alle 00:00 UTC; la macchina comunque chiede di nuovo al massimo una volta al minuto, quindi preleva il ripristino entro un minuto. `failproofai jev test` dice "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev ha rifiutato il request di questa chiamata, di solito perché la chiamata di tool conteneva testo denso (base64, esadecimale, codice minimizzato) oltre il budget di token di Jev. Quella chiamata ricade ogni volta; non è un'interruzione. |
| `http-502` | Jev non è disponibile in questo momento. |
| `http-503` | Questo Cloud non può servire Jev per la tua org: nessun gateway di modello, un'org non ancora provisioning, oppure il gateway è giù. Chiedi al tuo admin; gli hook chiedono di nuovo al massimo una volta al minuto. |
| `http-404` | Questo FailproofAI Cloud non serve ancora Jev. |
| `timeout` | Nessuna risposta entro `timeoutMs` (default 3000). Mentre FailproofAI Cloud imposta la modalità Jev della macchina, l'attesa è 5000 ms e il `timeoutMs` di `jev.json` non è usato. |
| `model-mismatch` | Una versione Jev diversa da 1.13 ha risposto. |

## Dove vive la chiave, e dove va

- La chiave è memorizzata una volta, in `~/.failproofai/credentials.json` (`0600`, in una directory solo del proprietario), accanto alle altre credenziali di FailproofAI Cloud. `jev.json` non contiene chiave per questa rotta; una scritta lì rende la configurazione non valida.
- Se `credentials.json` ha **qualsiasi** permesso per chiunque diverso da te (gruppo o altri, lettura o scrittura), oppure la sua directory può essere **scritta** da chiunque diverso da te, è **rifiutata**, non letta, e Jev è disattivato finché non lo ripari: `chmod 600` sul file, `chmod 700` sulla directory (oppure riconnetti, che riscrive il file a `0600` e rende la directory solo del proprietario). Una directory che gli altri possono solo leggere va bene; una in cui possono scrivere permette loro di scambiare il file.
- La chiave conta solo mentre la connessione da cui è venuta è sulla macchina: una credenziale di politica o reporting per lo stesso FailproofAI Cloud **con la stessa chiave**, nello stesso file. Una chiave Jev lasciata indietro senza uno è ignorata, e Jev rimane disattivato. Questo accade quando il `config --disconnect` di un failproofai più vecchio lascia la chiave Jev in posizione (non sa di rimuoverla), oppure quando il `config --token` di un failproofai più vecchio si connette con un'altra chiave, che su FailproofAI Cloud può appartenere a un'altra organizzazione. Per riattivare Jev, connetti di nuovo con una chiave **machine**.
- La chiave è inviata solo all'origine Cloud con cui è stata verificata. Un `jev.json` che punta da qualche altra parte è rifiutato.
- **Un agent sulla macchina può leggerlo.** `credentials.json` è solo del proprietario, e l'agent esegue come quel proprietario. La lettura dei file di failproofai stesso è consentita di proposito (solo cambiarli è bloccato, da `block-failproofai-commands`), quindi l'unica cosa tra un agent e questo file è `block-read-outside-cwd` — una politica *revisionabile* — e da una sessione iniziata nella tua directory home, nulla. Una chiave con `jev:evaluate` spende l'allocazione Jev della tua organizzazione (fino al limite giornaliero) da qualunque punto venga usata, quindi tratta una chiave macchina come qualsiasi altra credenziale di spesa: se un agent potrebbe averla letta, revocalo su **settings → api keys** e riconnetti con uno nuovo.
- Solo i tuoi file globali decidono questo. Un repository non può attivare Cloud Jev, puntare altrove o fornire la sua chiave, e `FAILPROOFAI_JEV_API_KEY` è ignorato per questa rotta.
- Per ogni chiamata che Jev valuta, una richiesta va a FailproofAI Cloud, portando quello che la [pagina bring-your-own-key](/it/reference/jev-providers#what-leaves-the-machine) elenca (segreti redatti). FailproofAI Cloud l'inoltro a TypeSafe e non lo registra o lo mantiene.

## Disattivalo

Su una macchina connessa, Jev è disattivato quando FailproofAI Cloud non distribuisce nessuna politica Jev ad essa: rimuovi o archivia le politiche Jev lì.

| Comando | Risultato |
| --- | --- |
| Rimuovi le politiche Jev della macchina in FailproofAI Cloud | La modalità di Cloud diventa `off` al prossimo sondaggio (circa 30 s): nessun Jev affatto, qualunque cosa dica `jev.json`. |
| `failproofai config --disconnect` | Disconnetti la macchina: la chiave è rimossa, e così è `jev.json` quando nomina FailproofAI Cloud e non è disattivato. Un `jev.json` per il tuo endpoint rimane. |

Dalla prossima chiamata di tool, gli hook eseguono le politiche regex esattamente come prima.
