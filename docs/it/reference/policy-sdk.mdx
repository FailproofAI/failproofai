Le politiche personalizzate trasformano un pattern di guasto dalle tue tracce o audit in una decisione che viene eseguita mentre un agente lavora. Una politica può consentire un'azione, fornire indicazioni all'agente o negare l'azione prima che provochi un altro incidente.

Usa una politica personalizzata quando il comportamento dipende dai tuoi strumenti, percorsi, comandi, ambienti o regole operative. Consulta il [catalogo di politiche built-in](/it/policies/builtin-catalog) prima di ricrearne una già esistente.

## Crea una politica personalizzata

<Tabs>
  <Tab title="Dashboard">
    1. Vai su **Admin → policy editor**, seleziona **New policy** e descrivi il guasto che vuoi prevenire.
    2. Aggiungi il codice della politica, quindi testa le corrispondenze previste e i mancati riconoscimenti sicuri nell'editor. Risolvi ogni errore di convalida.
    3. Salva la bozza e seleziona **Publish version** per creare una versione immutabile.
    4. Vai su **Admin → enforcement**, distribuisci la versione su una macchina di test in modalità **observe** e verifica le sue decisioni sotto **Observe → policy** prima di farla rispettare.

    ![L'editor di politiche utilizzato per creare e pubblicare una politica personalizzata.](/images/dashboard/policy-editor.png)
  </Tab>
  <Tab title="CLI">
    1. Scrivi una politica iniziale con `failproofai publish --init`, oppure crea `.failproofai/policies/checkout-policies.ts` manualmente. Un nome di file convenzionale deve terminare in `policies.js`, `policies.mjs` o `policies.ts`.
    2. Registra una o più politiche con `customPolicies.add()`.
    3. Fai rispettare il file su questa macchina adesso: `failproofai policies -i -c ./.failproofai/policies/checkout-policies.ts`.
    4. Attiva un'azione corrispondente e un'azione sicura. Esegui `failproofai policies`, quindi apri **Policies → Activity** sul [dashboard locale](/it/reference/local-dashboard) e filtra per sorgente per vedere quale politica ha deciso.
  </Tab>
</Tabs>

## Inizia con una regola ristretta

Questa politica blocca i comandi Kubernetes distruttivi solo quando il comando ha come destinazione la produzione. Tutto al di fuori di questo esatto pattern di guasto restituisce `allow()`.

```ts
import { customPolicies, allow, deny } from "failproofai";

const DESTRUCTIVE_KUBECTL = /\bkubectl\s+(delete|replace)\b/i;
const PRODUCTION_TARGET = /(?:--context|--namespace|-n)\s+(prod|production)\b/i;

customPolicies.add({
  name: "block-destructive-production-kubectl",
  description: "Block destructive Kubernetes commands against production",
  match: { events: ["PreToolUse"] },
  fn: async ({ toolName, toolInput }) => {
    if (toolName !== "Bash") return allow();

    const command = String(toolInput?.command ?? "");
    if (!DESTRUCTIVE_KUBECTL.test(command)) return allow();
    if (!PRODUCTION_TARGET.test(command)) return allow();

    return deny(
      "Destructive production Kubernetes commands require the approved deployment workflow.",
    );
  },
});
```

Le buone politiche sono abbastanza ristrette da essere spiegate in una sola frase. Fai corrispondere l'azione osservabile, non l'intento che speri avesse l'agente, e restituisci `allow()` non appena la regola non si applica.

## Scegli una decisione

| Helper | Risultato | Usalo quando |
| --- | --- | --- |
| `allow(reason?)` | L'operazione continua. | La politica non si applica oppure l'azione è sicura. |
| `instruct(reason)` | L'operazione continua e il motivo viene consegnato all'agente sui sistemi che dispongono di un canale per esso. | Vuoi guidare l'agente verso un approccio migliore senza applicare un invariante. |
| `deny(reason)` | L'operazione viene bloccata sul sistema e sulle coppie di eventi verificati per consumare un verdetto di blocco. | L'azione non deve procedere. |

Scrivi il motivo per l'agente che deve recuperare. Spiega cosa è stato rilevato e cosa dovrebbe fare invece.

### Dove `instruct()` effettivamente arriva

`instruct()` ha bisogno di un canale di contesto aggiuntivo nel sistema. Sei sistemi non ne hanno su alcuni o tutti gli eventi; lì l'operazione è consentita e il messaggio viene scritto su stderr, dove l'agente non lo legge mai.

| Sistema | Eventi che consegnano l'istruzione |
| --- | --- |
| Claude, Codex, Copilot, Cursor, Devin, OpenCode | `PreToolUse`, `PostToolUse`, `UserPromptSubmit` e `PermissionRequest` lo trasportano come contesto aggiuntivo. `Stop` e `SubagentStop` lo trasportano attraverso il canale di ripetizione. Ogni altro evento emette un messaggio che il sistema ignora. |
| Antigravity | Solo `UserPromptSubmit` e `Stop`. |
| Factory, Pi, OpenClaw | Solo `Stop`. |
| Hermes, Goose | Nessuno. Sempre consentito più una nota su stderr. |

Nessun sistema attiva tutti i 29 eventi canonici, quindi la prima riga è limitata da ciò che ciascuno installa — un'istruzione arriva solo su un evento che il sistema effettivamente attiva. Controlla il set di eventi installati per sistema in [Agent harnesses](/it/reference/harnesses) prima di fare affidamento su uno.

<Warning>
  Non usare `instruct()` per un confine di sicurezza. Su Hermes e Goose non raggiunge mai l'agente, e su Antigravity, Factory, Pi e OpenClaw non lo raggiunge sugli eventi dello strumento. Usa `deny()` quando l'azione deve essere prevenuta.
</Warning>

## Oggetto politica

```ts
customPolicies.add({
  name: "policy-name",
  description: "What this policy prevents",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => allow(),
});
```

| Campo | Obbligatorio | Descrizione |
| --- | --- | --- |
| `name` | Sì | Identificatore stabile per la politica. Mantieni i nomi univoci tra i file. |
| `description` | No | Scopo leggibile mostrato negli elenchi di politiche e nelle decisioni. |
| `match.events` | No | Tipi di evento che invocano la politica. L'omissione di `match` la invoca per ogni evento disponibile. |
| `fn` | Sì | Funzione sincrona o asincrona che restituisce un risultato `allow`, `instruct` o `deny`. |

Filtra gli strumenti dentro `fn`. `match.toolNames` non fa parte del tipo di politica personalizzata pubblica.

Una politica pubblicata dentro un pack può contenere due campi aggiuntivi, `category` e `defaultEnabled`. Vedi [Da un file a un pack](#from-a-file-to-a-pack).

## Contesto della politica

Ogni politica riceve un `PolicyContext`.

| Campo | Tipo | Cosa contiene |
| --- | --- | --- |
| `eventType` | `HookEventType` | Evento normalizzato attualmente in fase di valutazione. |
| `toolName` | `string \| undefined` | Nome dello strumento canonico come `Bash`, `Read`, `Write` o `Edit`. |
| `toolInput` | `Record<string, unknown> \| undefined` | Input canonico per la chiamata dello strumento corrente. |
| `payload` | `Record<string, unknown>` | Payload dell'evento normalizzato completo. |
| `session` | `SessionMetadata \| undefined` | ID della sessione, directory di lavoro, percorso della trascrizione, modalità di autorizzazione e metadati del sistema quando disponibili. |
| `cli` | `string \| undefined` | Sistema dell'agente di origine, come `claude`, `codex` o `cursor`. |
| `params` | `Record<string, unknown>` | Parametri per questa politica. Una politica built-in o di pack dichiara uno schema e i valori configurati dall'utente vengono uniti ai suoi valori predefiniti. Una politica in un file personalizzato non dichiara uno schema, quindi riceve tutto ciò che l'utente ha configurato sotto il suo nome e `{}` quando non è stato configurato nulla. |

Tratta ogni valore opzionale come genuinamente opzionale. Le versioni dell'agente e i tipi di evento non forniscono tutti gli stessi campi.

### Input comuni degli strumenti

Failproof AI normalizza gli strumenti comuni tra i sistemi supportati in modo che una politica possa solitamente usare una forma di input.

| Strumento | Campi comuni |
| --- | --- |
| `Bash` | `command` |
| `Read` | `file_path` |
| `Write` | `file_path`, `content` |
| `Edit` | `file_path`, `old_string`, `new_string` |
| `Grep` | `pattern`, `path` |

Usa la coercizione difensiva perché i valori di input dello strumento sono tipizzati come `unknown`:

```ts
const command = String(ctx.toolInput?.command ?? "");
const filePath = String(ctx.toolInput?.file_path ?? "");
```

## Scegli l'evento

| Evento | Quando viene eseguito | Uso tipico |
| --- | --- | --- |
| `PreToolUse` | Prima che uno strumento venga eseguito. | Blocca o guida comandi, scritture, letture e azioni esterne. Questo è il sistema di protezione. |
| `PostToolUse` | Dopo che lo strumento è già stato eseguito. | Ispeziona o sostituisci il risultato che il modello legge. Non può annullare l'effetto collaterale — la scrittura o il comando è già avvenuto — e su dieci dei dodici sistemi il verdetto non può fermare nulla. Solo Codex e Copilot lo consumano, e anche lì sostituisce il risultato che il modello legge piuttosto che prevenire la chiamata. Non usarlo mai come sistema di protezione. |
| `PermissionRequest` | Quando l'agente richiede autorizzazione. | Applica regole di autorizzazione specifiche dell'organizzazione. |
| `UserPromptSubmit` | Prima che un prompt inviato continui. | Rifiuta le istruzioni vietate o aggiungi indicazioni di flusso di lavoro. |
| `Stop` | Quando l'agente tenta di terminare. | Richiedi una condizione di completamento raggiungibile, come un passaggio di verifica locale. |
| `SubagentStop` | Quando un sub-agente tenta di terminare. | Blocca il lavoro delegato prima che ritorni al padre. |
| `SessionStart` / `SessionEnd` | Ai confini della sessione. | Registra o verifica lo stato a livello di sessione. |

La disponibilità degli eventi e il comportamento di blocco dipendono dal sistema dell'agente e le differenze sono significative: Failproof AI non installa nessun hook `Stop` per Goose o Hermes, quindi un gate di stop non si attiva mai su nessuno dei due. Vedi [Agent harnesses](/it/reference/harnesses) prima di fare affidamento su un evento in una flotta mista.

<Accordion title="Tutti i nomi degli eventi della politica">
  `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `Elicitation`, `ElicitationResult`, `UserPromptExpansion`, `PostToolBatch` e `Setup`. Questo è il set completo dei 29 nomi di eventi canonici in cui il vocabolario di eventi di ogni sistema viene normalizzato.
</Accordion>

## Crea pattern di politiche comuni

### Blocca le scritture su percorsi protetti

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "block-generated-file-edits",
  description: "Require generated files to be changed through their generator",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();

    const filePath = String(ctx.toolInput?.file_path ?? "");
    if (!/(^|\/)(dist|generated)\//.test(filePath)) return allow();

    return deny("Edit the source and run the generator instead of changing generated output.");
  },
});
```

### Fornisci indicazioni senza blocco

```ts
import { customPolicies, allow, instruct } from "failproofai";

customPolicies.add({
  name: "prefer-reviewed-deploy-command",
  description: "Guide agents toward the reviewed deployment wrapper",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();

    const command = String(ctx.toolInput?.command ?? "");
    if (!/^kubectl\s+apply\b/.test(command.trim())) return allow();

    return instruct("Use ./scripts/deploy-reviewed instead of invoking kubectl directly.");
  },
});
```

### Blocca il completamento della sessione

```ts
import { execFileSync } from "node:child_process";
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "require-clean-typecheck",
  description: "Require the project typecheck to pass before the agent finishes",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow();

    try {
      execFileSync("bunx", ["tsc", "--noEmit"], {
        cwd,
        stdio: "ignore",
        timeout: 8_000,
      });
      return allow();
    } catch {
      return deny("Fix the typecheck errors before finishing the task.");
    }
  },
});
```

<Warning>
  Un evento `Stop` negato può far riprovare l'agente. Blocca solo su una condizione che l'agente può soddisfare nell'ambiente corrente e limita ogni subprocess o chiamata di rete.
</Warning>

## Carica file di politiche

### File convenzionali

I file convenzionali si caricano automaticamente:

```text
<project>/.failproofai/policies/security-policies.ts
~/.failproofai/policies/personal-policies.mjs
```

- Entrambe le directory di politiche di progetto e utente vengono caricate.
- I file si caricano alfabeticamente all'interno di ogni directory.
- Un file deve terminare in `policies.js`, `policies.mjs` o `policies.ts`.
- Sono supportate multiple chiamate `customPolicies.add()` in un file.
- Sono supportati gli import relativi da moduli locali.
- Le politiche di progetto possono essere commesse in modo che le stesse regole seguano il repository.

<Warning>
  Un file nella directory il cui nome non termina in `policies.{js,mjs,ts}` viene saltato. Sembra installato e non fa rispettare nulla. Il caricatore elenca ogni file saltato con il nome da rinominare; leggi quell'avviso piuttosto che assumere che una politica sia attiva. Questo repository ha spedito `block-version-bumps.mjs` in questo modo, e il sistema di protezione scritto dopo un cattivo bump di versione non era mai stato eseguito nemmeno una volta.
</Warning>

`~/.failproofai/policies/` contiene anche due sottodirectory che non hai messo lì: `cloud-policies/` per le distribuzioni gestite della flotta e `packs/` per i pack installati. Il caricatore non scende mai in nessuno dei due, quindi nulla in essi viene raccolto come politica personalizzata convenzionale non verificata.

### Disattiva una politica scoperta

Due chiavi in `policies-config.json` disattivano le politiche convenzionali senza eliminare o rinominare il file:

| Chiave | Effetto |
| --- | --- |
| `disabledCustomPolicies` | Un array di ID di politiche qualificate dalla sorgente che non sono registrate. |
| `customPoliciesEnabled` | Impostato su `false` per interrompere il caricamento di `.failproofai/policies/` interamente. Assente significa abilitato. |

La scheda **Policies → Configure** del [dashboard locale](/it/reference/local-dashboard) scrive `disabledCustomPolicies` per te. `customPoliciesEnabled` viene scritto da `failproofai config` o manualmente.

### File espliciti

Usa i percorsi espliciti quando la convalida o la configurazione deve nominare il file di voce direttamente:

```bash
failproofai policies --install \
  --custom ./security.policies.ts \
  --custom ./workflow.policies.ts \
  --scope project
```

I file espliciti si caricano per primi, seguiti dai file di convenzione del progetto e quindi dai file di convenzione dell'utente. Un file scoperto attraverso entrambi i percorsi viene caricato una volta.

## Convalida e prova

`-c` è la forma breve di `--custom` e `-i` di `--install`. Fa rispettare il file adesso, in qualsiasi percorso e sotto qualsiasi nome di file:

```bash
failproofai policies -i -c ./checkout-policies.ts
failproofai policies
```

Chiedi al tuo agente di fare la cosa che hai bloccato e guardalo venire rifiutato. Nulla viene pubblicato e nessun'altra macchina è interessata.

La convalida esegue il modulo attraverso il caricatore di produzione e conferma che registra almeno una politica. Cattura file mancanti, errori di sintassi, import non risolti, eccezioni di primo livello e timeout di caricamento del modulo. Non prova che la tua logica di corrispondenza sia corretta.

Prova almeno questi casi:

- Un'azione che deve corrispondere e produrre il motivo di politica previsto.
- Un'azione vicina ma sicura che deve restituire `allow()`.
- Campi dello strumento mancanti o malformati.
- Sintassi alternative dei comandi, percorsi, virgolette, maiuscole e spazi bianchi.
- Una dipendenza di subprocess o rete non disponibile.

Attribuisci il risultato alla tua politica personalizzata sotto **Policies → Activity** nel dashboard locale. Un test bloccato non è sufficiente se una diversa politica built-in ha preso la decisione.

## Comportamento a runtime

- Le politiche built-in vengono valutate prima delle politiche personalizzate.
- Il primo `deny` interrompe l'ulteriore valutazione della politica.
- Risultati multipli `instruct` possono essere combinati quando nessuna politica nega l'evento.
- Una funzione di politica ha una scadenza di esecuzione di 10 secondi. Il caricamento del modulo di primo livello ha la stessa scadenza.
- Un'eccezione lanciata o un timeout viene registrato e trattato come `allow()`.
- Un file di convenzione che non riesce a caricarsi viene saltato; altri file personalizzati e politiche built-in continuano.
- La modalità Observe esegue la politica per davvero e registra qualsiasi verdetto non allow senza farla rispettare. Due livelli la impostano: `failproofai publish --effect observe` su un pack che pubblichi, e `fp fleet deploy <machine> --add <id>:observe` su una distribuzione Cloud. In entrambi i casi la politica viene valutata sotto la stessa scadenza di 10 secondi di una che fa rispettare, quindi una politica che scade registra come allow.

### Dove il caricatore fallisce chiuso invece

La regola fail-open sopra copre un file che hai scaricato tu stesso. Due percorsi fanno deliberatamente l'opposto, perché entrambi significano che questa macchina è stata informata che aveva una protezione che non ha.

| Situazione | Risultato |
| --- | --- |
| Un pack selezionato non può essere caricato, oppure il suo digest bloccato non corrisponde | Ogni evento nell'ambito che il pack ha dichiarato viene negato, attribuito a `pack/failproofai-pack-unavailable`. `UserPromptSubmit` istruisce invece di negare, quindi non sei mai bloccato dall'agente di cui hai bisogno per risolverlo. I metadati del pack illeggibili ampliano l'ambito negato piuttosto che restringerlo. |
| Il daemon `failproofaid` non può essere raggiunto su una macchina che ha completato la configurazione | Ogni evento viene negato. Nessuna configurazione viene letta e nessuna politica personalizzata viene eseguita, perché un daemon che non potrebbe essere raggiunto non avrebbe potuto eseguirle. Una mancata corrispondenza di versione del protocollo nega anche, con un messaggio che nomina `failproofai config`. |

Su una macchina che ha completato la configurazione, `failproofaid` è l'unico valutatore, quindi il tuo `fn` viene eseguito dentro il worker caldo del daemon piuttosto che nel processo hook. Il client hook consente 150 ms per connettersi e 30 secondi per la risposta, comodamente superiore alla scadenza fissa di 10 secondi che ogni funzione di politica ottiene.

Mantieni i moduli di politica deterministici e veloci. Evita le chiamate di rete di primo livello o l'avvio del server. Limita il lavoro dentro `fn`, cattura i guasti di dipendenza e scegli deliberatamente se quel guasto dovrebbe consentire o negare l'operazione.

## Da un file a un pack

Un pack è il modo in cui un file di politica diventa qualcosa che altre macchine possono installare. Due comandi ti portano da nulla a un pack pubblicato:

```bash
failproofai publish --init
failproofai publish
```

`--init` chiede come si chiama il pack, scrive `<name>.mjs` e si ferma. Il file non è un modello con spazi vuoti — è una politica che blocca già `git push --force`, quindi la prima cosa che modifichi è qualcosa che funziona. Provalo localmente con `failproofai policies -i -c ./<name>.mjs`, quindi esegui `failproofai publish` dall'interno del repository git che lo contiene.

Due campi hanno importanza una volta che una politica viene spedita in un pack:

| Campo | Cosa fa |
| --- | --- |
| `category` | Su cosa `failproofai policies add <owner>/<repo> --category git,database` seleziona. |
| `defaultEnabled` | Se un semplice `failproofai policies add <owner>/<repo>` accende questa politica. Il valore predefinito è `false`. |

`--effect` è impostato per pack piuttosto che per politica: `failproofai publish --effect observe` pubblica un pack che registra cosa avrebbero deciso le sue politiche e non blocca nulla. Il valore predefinito è `enforce`. Questa è la modalità observe su una singola macchina senza connessione Cloud — leggi i verdetti registrati indietro sotto **Policies → Activity** nel dashboard locale.

La versione del pack è lo sha di commit breve di 12 caratteri da cui è stato costruito, quindi `publish` rifiuta al di fuori di un checkout git e su un albero sporco. Vedi [Publish a pack](/it/policies/publish-a-pack) per il flusso completo e [Policy packs](/it/policies/packs) per come le installazioni risolvono una versione.

## Esportazioni API

| Esportazione | Scopo |
| --- | --- |
| `customPolicies.add(policy)` | Registra una politica personalizzata quando il modulo carica. |
| `allow(reason?)` | Consenti l'operazione. |
| `instruct(reason)` | Consenti l'operazione e fornisci indicazioni dove supportato. |
| `deny(reason)` | Blocca l'operazione dove supportato. |
| `getCustomHooks()` | Restituisci le politiche attualmente registrate nel registro del modulo. |
| `clearCustomHooks()` | Cancella quel registro, principalmente per test e caricatori. |

TypeScript esporta `PolicyContext`, `PolicyResult`, `CustomHook`, `PolicyDecision` e `PolicyFunction`.
