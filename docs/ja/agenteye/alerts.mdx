顧客から報告される前に、チームがすでに使っているチャネルで、問題が発生した瞬間を把握しましょう。ルールを一度設定するだけで、Failproof AI Observability がスケジュールに従ってチェックし、メール・Slack・Webhook・ダッシュボード上で通知を送ります。

![アラートページ：アラートルールカードのグリッド。それぞれにトリガー、評価ウィンドウ、チャネル、および info・warning・critical の深刻度バッジが表示されている](/agenteye/images/alerts.png)
*すべてのアラートルールを一覧で確認：監視対象、実行頻度、通知先、緊急度。*

## ユーザーより先に問題を把握する

回帰を見逃さないようにダッシュボードを更新し続けるのはやめましょう。誰も見ていないときでも通知を受け取りたいシグナルがあれば、アラートを設定して、すでに使っている場所に届くようにしましょう。

- **メール**：知らせるべき相手に送信。
- **Slack**：インシデントに直接ジャンプするボタン付きのリッチメッセージ。
- **Webhook**：PagerDuty・Opsgenie・独自エンドポイント向けの JSON POST。受信側が信頼できるよう、オプションで署名を付与可能。
- **ダッシュボード内**：ルールを調整中で誰にも通知したくないときのために、デフォルトでは控えめな表示。

1つのルールに任意の組み合わせで通知先を設定できます。深刻度（info・warning・critical）も一緒に通知されるため、緊急なものはそれらしく見えます。

## ルールはフォームで作成、JSON不要

何が「壊れている」かをフォームで記述するだけで、Failproof AI Observability が内部ルールを生成します。JSON仕様はそのフォームが裏側で生成するものなので、ルールを理解するために読むことはありますが、手入力することはほとんどありません。

![新規アラートフォーム：名前と説明、有効化トグル、metric threshold・custom SQL・evaluation score・compound eval・per-event 条件を提供するトリガーピッカー](/agenteye/images/alert-new.png)
*トリガーを選択するとフォームに適切なフィールドが表示されます。「保存」でルールが書き込まれます。*

基本的な手順はシンプルです：名前を付け、**トリガー**（監視対象）を選び、**しきい値とウィンドウ**（どの程度の悪化が、どのくらいの期間続いたら）を設定し、最低1つの**チャネル**を追加して、**保存**します。その後**テスト**を実行し、疑似通知を発火させて全通知先が正しく設定されているか確認しましょう。内部的には次のような小さなスペックが生成されます：

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

シグナルの種類は1つに限りません。障害の考え方に合ったトリガーを選んでください：

| トリガー | 発火条件 |
|---|---|
| **Metric threshold** | プリセットのメトリクス（エラーレート・p95/p99レイテンシ・イベント数・エラー数・トークン消費量）がウィンドウ内でしきい値を超えたとき |
| **Custom SQL** | 独自の読み取り専用クエリが行を返したとき、またはクエリが算出した値がしきい値を超えたとき |
| **Evaluation score** | 評価スコアの平均値（例：幻覚スコア）がしきい値を超えたとき |
| **Compound eval** | 複数のスコアチェックを any・all・at-least-N ロジックで組み合わせ、複数スコアにまたがって現れる回帰を検出するとき |
| **Per event** | 特定のエージェント・特定のエラータイプ・メッセージの部分文字列に一致するイベントが1件届いたとき |

[エラーページ](/ja/agenteye/error-tracking)で障害を確認中ですか？各行には **+ alert** ボタンがあり、その障害を再度検出するためのフォームがあらかじめ入力された状態で開きます。今トリアージしたインシデントが、次回の通知対象になります。

**場所：** アラートは `/<org-slug>/alerts` にあります。ルールの作成・編集・削除・テストには **`alerts:write`** が必要です。閲覧のみであれば `alerts:read` で十分です。受信者ピッカーには組織のメンバーが名前付きで一覧表示されるため、フォームを離れずに特定の担当者に通知を送ることができます。

## 本当に問題があるときだけ通知する

1回の悪い計測結果で起こされたくない。**M of N** ノイズフィルターは、アラートが実際に通知を送る前に、直近の数回のチェックのうち何回失敗する必要があるかを制御します。**3 of 5** に設定すると、直近5回のチェックのうち3回しきい値を超えた場合にのみルールが発火するため、不安定なシグナルが誤通知を出し続けることを防ぎます。デフォルトの **1 of 1** のままにすると、最初のしきい値超過で即座に発火します。ルールの実行頻度も選択できます。プリセットは 1m・5m・15m・1h で、シグナルの実際の変化速度に合わせて選択してください。

## アラートが発火したときの流れ

しきい値超過が起きると**インシデント**が作成され、チャネルに1回通知が送られます。その後チームはインシデントを確認し、担当者を割り当て、議論して解決します。すべてクリーンな帰属記録として残ります。このトリアージワークフローには専用のホームがあります：[インシデント](/ja/agenteye/incidents)を参照してください。

- [エラートラッキング](/ja/agenteye/error-tracking)：エージェントの障害をグループ化し、ワンクリックでアラートに昇格させる。
- [ダッシュボード](/ja/agenteye/dashboards)：アラートのしきい値が参照している共有ボードを監視する。
