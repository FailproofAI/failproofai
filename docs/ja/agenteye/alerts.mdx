チームがすでに使っているチャンネルで、顧客から報告される前に問題を即座に検知しましょう。ルールを一度設定しておけば、Failproof AI Observability がスケジュールに沿ってチェックを行い、メール・Slack・Webhook・ダッシュボード上でアラートを通知します。

![アラートページ：トリガー、評価ウィンドウ、チャンネル、重大度バッジ（info・warning・critical）を表示したアラートルールカードのグリッド](/agenteye/images/alerts.png)
*すべてのアラートルールを一覧表示：監視内容、評価頻度、通知先、緊急度。*

## ユーザーより先に問題を把握する

ダッシュボードを何度もリロードして異常を探す必要はありません。誰も見ていないときでも検知したいシグナルにアラートを設定し、いつも使っている場所に通知を届けましょう。

- **メール**：担当者に直接通知。
- **Slack**：インシデントへ直接ジャンプできるボタン付きのリッチメッセージ。
- **Webhook**：PagerDuty・Opsgenie、または独自エンドポイントへの JSON POST。受信側が検証できるオプションの署名付き。
- **ダッシュボード内通知**：ルールを調整中で誰にも通知したくないときに便利な、静かな設計。

複数のチャンネルを 1 つのルールに組み合わせて設定できます。重大度（info・warning・critical）も一緒に送られるので、緊急度の高いものはひと目でわかります。

## JSON ではなくフォームでルールを作成する

「壊れている」状態をフォームで記述すると、Failproof AI Observability が内部のルールを自動生成します。JSON の仕様はフォームが裏側で生成するものなので、ルールを理解するために読むことはあっても、自分で記述することはほとんどありません。

![新規アラートフォーム：名前と説明、有効化トグル、メトリクスしきい値・カスタム SQL・評価スコア・複合評価・イベント単位の条件を選択できるトリガーピッカー](/agenteye/images/alert-new.png)
*トリガーを選ぶと対応するフィールドに切り替わります。保存するとルールが書き込まれます。*

基本的な操作はシンプルです。名前を入力し、**トリガー**（何を監視するか）を選び、**しきい値とウィンドウ**（どの程度の異常を、どの期間で検知するか）を設定し、少なくとも 1 つの**チャンネル**を設定して**保存**します。その後 **テスト** を実行して仮の通知を発火させ、すべての通知先が正しく設定されているか確認しましょう。内部的には次のような小さな仕様が生成されます。

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

シグナルの種類は 1 つに限りません。障害の捉え方に合ったトリガーを選んでください。

| トリガー | 発火条件 |
|---|---|
| **メトリクスしきい値** | エラーレート・p95/p99 レイテンシ・イベント数・エラー数・トークン消費などのプリセットメトリクスが、指定ウィンドウ内でしきい値を超えたとき |
| **カスタム SQL** | 読み取り専用クエリが行を返したとき、またはクエリが計算した値がしきい値を超えたとき |
| **評価スコア** | 評価スコア（ハルシネーションなど）の平均がしきい値を超えたとき |
| **複合評価** | 複数のスコアチェックを any・all・N 件以上のロジックで組み合わせ、複数スコアにまたがる回帰を検出するとき |
| **イベント単位** | 特定のエージェント・特定のエラータイプ・メッセージの部分文字列など、条件に一致するイベントが 1 件でも発生したとき |

[エラーページ](/ja/agenteye/error-tracking) で障害を確認している最中ですか？各行には **+ アラート** ボタンがあり、同じフォームをその障害に合わせてあらかじめ入力した状態で開けます。今トリアージした障害が、次回の通知対象になります。

**場所：** アラートは `/<org-slug>/alerts` にあります。ルールの作成・編集・削除・テストには **`alerts:write`** が必要です。閲覧のみなら `alerts:read` で十分です。通知先ピッカーには組織のメンバーが名前で表示されるので、フォームを離れることなく担当者に通知できます。

## 本当に必要なときだけ通知する

1 回の誤計測でアラートを受け取りたくないはずです。**M of N** ノイズフィルターにより、直近の数回のチェックのうち何回失敗したときに実際に通知するかを制御できます。**5 回中 3 回** に設定すれば、直近 5 回のうち 3 回しきい値を超えたときだけルールが発火するので、不安定なシグナルが誤報を出し続けることがなくなります。デフォルトの **1 of 1** のままにすれば、最初の違反で即座に通知されます。ルールの実行頻度は 1m・5m・15m・1h のプリセットから選択でき、シグナルの変化速度に合わせて設定できます。

## アラートが発火したときの流れ

しきい値違反が発生すると **インシデント** が作成され、設定したチャンネルに一度通知されます。その後チームがインシデントを確認し、担当者を割り当て、状況を整理して解決します。これらはすべて、明確に記録されたクリーンな履歴として残ります。トリアージのワークフローについては [インシデント](/ja/agenteye/incidents) をご覧ください。
