顧客から報告される前に、チームがすでに使っているチャンネルで、問題が発生した瞬間に気づけるようにしましょう。ルールを一度設定すれば、Failproof AI Observability がスケジュールどおりにチェックし、メール・Slack・Webhook、またはダッシュボード上で通知します。

![アラートページ：アラートルールカードのグリッド。各カードにはトリガー、評価ウィンドウ、チャンネル、info・warning・critical のいずれかの重大度バッジが表示されている](/agenteye/images/alerts.png)
*すべてのアラートルールを一目で確認：監視対象・評価頻度・通知先・緊急度。*

## ユーザーより先に問題を把握する

ダッシュボードをリフレッシュし続けて退行を見つけようとするのはやめましょう。誰も見ていないときでも知らせてほしいシグナルがあれば、アラートを設定して、すでに使っている場所に届くようにしましょう：

- **メール**：知っておくべき担当者全員に。
- **Slack**：インシデントへ直接ジャンプするボタン付きのリッチメッセージとして。
- **Webhook**：PagerDuty・Opsgenie、または独自エンドポイントへの JSON POST。受信側が信頼できるよう任意の署名付き。
- **ダッシュボード内**：ルールを調整中でまだ誰にも通知したくない場合向けの、控えめな通知。

1 つのルールに任意の組み合わせで通知先を設定でき、重大度（info・warning・critical）も一緒に送られるため、緊急なものはすぐにそれとわかります。

## JSON ではなくフォームでルールを作成する

「壊れている」状態をフォームで記述すれば、Failproof AI Observability が内部のルールを生成します。JSON 仕様はそのフォームが裏側で生成するものなので、ルールの内容を理解するために読むことはあっても、直接入力することはほとんどありません。

![新規アラートフォーム：名前と説明、有効/無効のトグル、トリガー選択（メトリクス閾値・カスタム SQL・評価スコア・複合評価・イベント単位）](/agenteye/images/alert-new.png)
*トリガーを選択するとフォームに適切なフィールドが表示され、保存するとルールが作成されます。*

基本的な流れはシンプルです。名前を付け、**トリガー**（何を監視するか）を選び、**閾値とウィンドウ**（どの程度の悪化を、どのくらいの期間で）を設定し、**チャンネル**を少なくとも 1 つ追加して **保存** します。その後 **テスト** を実行して、合成通知を送信し、すべての通知先が正しく設定されているか確認しましょう。内部的には次のような小さな仕様が生成されます：

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

シグナルの種類はひとつに限りません。障害のとらえ方に合ったトリガーを選択してください：

| トリガー | 発火条件 |
|---|---|
| **メトリクス閾値** | エラー率・p95/p99 レイテンシ・イベント数・エラー数・トークン消費量などのプリセットメトリクスが、指定ウィンドウ内で閾値を超えたとき |
| **カスタム SQL** | 読み取り専用クエリが行を返すか、クエリで算出した値が閾値を超えたとき |
| **評価スコア** | 評価器スコア（幻覚など）の平均値が閾値を超えたとき |
| **複合評価** | any・all・N件以上のロジックで複数のスコアチェックを組み合わせ、複数スコアにまたがる退行を検出するとき |
| **イベント単位** | 特定のエージェント・エラータイプ・メッセージ部分文字列に一致する単一イベントが発生したとき |

[エラーページ](/ja/agenteye/error-tracking)で障害を確認中ですか？各行に **+ alert** ボタンがあり、同じフォームにその障害を再検出するための設定がプリセットされた状態で開きます。今しがたトリアージしたインシデントが、次回の通知対象になります。

**場所：** アラートは `/<org-slug>/alerts` にあります。ルールの作成・編集・削除・テストには **`alerts:write`** が必要で、閲覧には `alerts:read` で十分です。受信者ピッカーにはオーガニゼーションのメンバーが名前で表示されるため、フォームを離れずに担当者に通知できます。

## 本当に必要なときだけ通知する

1 回の悪い計測値で叩き起こされるべきではありません。**M of N** ノイズフィルターは、直近の何回のチェックのうち何回失敗した場合にアラートを実際に発火するかを制御します。**5 回中 3 回**に設定すれば、直近 5 回のチェックのうち 3 回が閾値を超えた場合にのみ発火するため、ジッターのあるシグナルが誤報を出し続けることを防ぎます。デフォルトの **1 of 1** のままにすれば、最初の違反で即座に発火します。ルールの実行頻度も、シグナルの変化速度に合わせて 1m・5m・15m・1h のプリセットから選択できます。

## アラートが発火したときの流れ

閾値超過が発生すると **インシデント** が開かれ、チャンネルに一度通知が送られます。そこからチームが確認し、担当者をアサインし、議論し、解決するまでの流れが、クリーンで帰属情報付きの記録として残ります。このトリアージワークフローには専用の場所があります：[インシデント](/ja/agenteye/incidents)をご覧ください。
