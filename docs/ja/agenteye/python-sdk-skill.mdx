コーディングエージェントに *「このエージェントに Failproof AI Observability を追加して」* と伝えるだけで、エージェントがループを読み取り、計装箇所を特定し、コードを書き、イベントを検証してから完了とみなします。

**Python SDK スキル**（`agenteye-python-sdk`）は *Agent Skill* です。これは、Claude Code や Codex などのコーディングエージェントがタスクに応じてオンデマンドで読み込む、指示書のフォルダです。このスキルはエージェントに [Python SDK](/ja/agenteye/python-sdk) の使い方を教えるものであり、ライブラリではなく、SDK の動作自体には何も変更を加えません。

## 計装は書きやすいが、気づかないうちに間違えやすい

SDK はシンプルです。イベントメソッドが13個、すべてキーワード引数のみ。コーディングエージェントは [Python SDK](/ja/agenteye/python-sdk) リファレンスを読んで、1分もあれば一見正しそうな計装コードを生成できます。

問題は、この SDK は間違えてもエラーを出さない点です。間違った計装は正しい計装とまったく見分けがつかず、誰かがダッシュボードを開いて空っぽだと気づくまで発覚しません。本当に時間を無駄にするミスは、どれも「無音」のものです。

| ミス | 見え方 |
|---|---|
| `agent_start` がない | すべてのイベントは記録される。セッションはゼロ。 |
| 環境が一度も設定されていない | すべて動作しているが、`dev` 扱いになっている。 |
| `outcome="failure"` と書いてしまう | 実行結果はグリーン表示 — 有効な値は `failed`、`error`、`timeout`、`rejected` のみ。 |
| フィールド名のタイポ | 受け入れられ、新しいフィールドとして保存される。 |
| スレッドプールからイベントを送出 | 無音でドロップされる。 |

これらはどれもエラーにならず、テストにも引っかかりません。すべてスキル内に、違反を検出するチェックとともに規約として明記されています。

## スキルの処理内容（順番に）

このスキルは、慎重なエンジニアが行うのと同じ3つのステップを実行します。

1. **計画。** エージェントのループを読み取り、あなたにしか答えられない2つの質問を確認します。1回の実行とは何か（`session_id`）、区別すべきアクターは誰か（`agent_id`）。コードを書く前にこれらを合意します。後から変更すると履歴が分断されトレンドが壊れるためです。
2. **実装。** 呼び出しごとにではなく、1回の実行ごとに1度だけ識別情報をバインドし、並行処理安全な形式を選択します。この細部は重要で、安易な方法だと2つの重複した実行が1つのセッションに無音で混入してしまいます。
3. **検証。** エージェントを実行し、生成されたイベントファイルを読み取って、`agent_start` の存在、環境の正確性、1回の実行が1セッションを生成していることを確認します。

3番目のステップこそ、多くの人が省略するものです。SDK はイベントをローカルファイルに書き出すので、完全な統合は、サーバーなし・APIキーなし・ネットワークなしでラップトップ上で証明できます。だからこそこのスキルはその検証を必須としています。

## 他のスキルとの関係

スキルは3つ、役割は明確に分かれています。

| スキル | 使うタイミング | 対象 |
|---|---|---|
| **Python SDK スキル**（このページ） | エージェントにテレメトリを *送出* させたいとき — 「オブザーバビリティを追加して」「エージェントが表示されない」 | エージェントのリポジトリにコードを書く。何も読まない。 |
| **[Evaluator スキル](/ja/agenteye/evaluator-skill)** | 実行を *スコアリング* したいとき — 「何を計測すべきか？」 | リポジトリにコードを書く。テレメトリを読む。 |
| **[CLI スキル](/ja/agenteye/cli-skill)** | 何が起きたかを *確認* したい、またはデプロイを操作したいとき | CLI を代理で操作する（変更を含む）。 |

この順序で連携します。このスキルがイベントを流し、エバリュエーターがスコアリングし、CLI が読み返す。エージェントがセッションを送出するまで、評価するものも読み返すものもありません。ゼロから始めるなら、まずここから。

## 前提条件

1. **Python 3.10+** と計装したいエージェントのコードベース。
2. **SDK。** パブリックインデックスではなくプライベートホイールとして顧客に配布されます — 入手・インストール方法はオンボーディングで案内されます。スキルはインストールパスを把握しており、見つからない場合は推測せずに確認します。
3. **それ以外は不要。** ダッシュボードへのログイン、APIキー、ネットワークは不要です。スキルは SDK が書き出すイベントファイルに対して検証を行うため、オフラインで完了・証明できます。

## 入手方法

スキルはパブリックな [`FailproofAI/skills`](https://github.com/FailproofAI/skills) コレクションで公開されています。

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

`-g` を追加すると現在のプロジェクトだけでなく全プロジェクトにインストールされます。シンボリックリンクに非対応の環境では `--copy` を付けてください。Codex の場合は `-a codex` を使用します。

## 手動インストール

Agent Skills は `SKILL.md` と参照ファイルを含むフォルダです。インストーラーを使わない場合：

- **Claude Code**: `agenteye-python-sdk/` フォルダを `~/.claude/skills/`（全プロジェクト共通）または `<あなたのリポジトリ>/.claude/skills/`（そのリポジトリのみ）にコピーします。Claude Code は自動で検出します — `/skills` リストで確認するか、対応するタスクを聞いてみてください。
- **Codex**: 同じ `SKILL.md` を読み込みます。同梱の `agents/openai.yaml` に `allow_implicit_invocation: true` が設定されているため、タスクが一致すれば自動で選択されます。明示的に呼び出す場合は `$agenteye-python-sdk` を使います。

**計装したいコードが入ったリポジトリ内** でエージェントを実行してください — スキルは何かを提案する前にエージェントのループを読み取ります。

## セッションの例

```text
you   ▸ このエージェントに Failproof AI Observability を追加して。

agent ▸ ループを読みました — tools.py にツールディスパッチャーが1つ、
        llm.py に Anthropic ラッパーが1つあります。コードを書く前に
        2点確認させてください。

        1回の実行とは何ですか？ リクエストが並行処理されているので、
        ctx.request_id にある既存のリクエストIDを使うのが良さそうです。
        そうすれば、ここのセッションとログのリクエストが同じ文字列に
        なります。

        アクターは誰ですか？ プランナーパスとリサーチャーパスが見えます。
        それぞれ別のラベルにしますか、それとも1つのエージェントですか？

you   ▸ リクエストIDで合ってる。1つのエージェントとして、「assistant」
        と呼んで。

agent ▸ 完了しました。ディスパッチャーと LLM クライアントをラップし、
        agent_start と agent_end が handle_request を囲む形にしました
        （エラーパスも含む）。コンテキストローカル変数で識別情報を管理
        しています — ディスパッチャーがスレッドプールでツールを実行
        するため、単純な方法だと並行する実行が無音で1つのセッションに
        混入してしまいます。

        実際の実行で検証済み: 4ファイルにわたる11イベント —
        agent_start、model_request/response、tool_use/tool_result×3、
        agent_end（outcome=success）。environment=production、リクエスト
        ごとに1セッション、継続時間もペアで記録されています。

        1点 やっていないこと: batch.py のワーカープールがエグゼキュータに
        直接サブミットしているため、そこからのイベントはドロップされます。
        そちらも修正しますか？
```

注目すべきパターン: コードを読んでから提案し、あなたにしか答えられない質問のみ聞き、すでに持っているIDを再利用し、スレッドプールを確認したうえで並行処理安全な形式を選択し、成功宣言ではなく **実際のイベントを読んで検証**、そして無音で失敗する箇所をフラグとして報告しています。

## できること

- *「エージェントがダッシュボードに表示されない」* → 段階的に確認: イベントが書き出されているか、`agent_start` はあるか、環境は正しいか、コレクターが同じ場所を読んでいるか。
- *「すべて dev で記録されてしまう」* → 環境が一度も設定されていないか、後の呼び出しでリセットされている。
- *「トークン追跡を追加して」* → LLM ラッパーを見つけて、モデル・停止理由・使用量を記録する。
- *「サブエージェントも計装して」* → 1セッション、個別のエージェントラベル、親の下にネストされた構造。
- *「計装のテストを書いて」* → SDK を一時ディレクトリに向けて、書き出されたイベントをアサート。

## 注意点

**必ず検証させること。** このスキルが価値を発揮するのは最後のステップ — エージェントを実行してイベントを読み返すところです。計装を書いて止まるエージェントは簡単な半分しかやっていません。無音で失敗するのはもう半分の方です。

**コードより先に名前を合意すること。** `session_id` と `agent_id` は、すべての画面がグループ化の軸として使います。後から変更すると履歴が分断されます。古い実行は古いラベルのまま残り、トレンドが壊れます。スキルが確認してきますが、その答えは少し時間をかけて考える価値があります。

**エージェントがパブリックインデックスから SDK をインストールしようとしたら、スキルが読み込まれていません。** SDK はプライベートで配布されています。そのような提案は、コーディングエージェントがスキルに従わず推測で動いているサインです。そこで止めて、スキルがインストールされているか確認してください。

その他の影響範囲は小さいです。作業ディレクトリとイベントファイルの指定場所にコードを書くだけで、デプロイメントからは何も読まず、何も変更しません。
