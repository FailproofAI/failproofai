アラートは測定可能な条件を監視し、トリガーされたときにインシデントを作成します。ポリシーによってブロックできるかどうかに関わらず、障害が発生した際に迅速な対応が必要な場合に使用します。

## アラートの作成とテスト

<Tabs>
  <Tab title="ダッシュボード">
    1. **Analyze → Alerts** に移動して **new alert** を選択します。代表的なエラーのベルアイコンからも開始できます。
    2. 名前、重大度、トリガーの種類、条件、評価間隔、違反カウント、ウィンドウ、チャンネルを入力します。
    3. アラートを保存し、詳細ページを開いて **test** を実行します。
    4. **Analyze → Issues** に移動して、アラートによって作成されたインシデントの確認、割り当て、ディスカッション、サブスクリプション、解決を行います。

    フォームの前半では、アラートの識別情報とトリガーとなるシグナルを設定します。

    ![新規アラートフォームの前半部分。名前、説明、有効状態、トリガータイプが表示されています。](/images/dashboard/alert-new-trigger.png)

    フォームの後半では、条件が持続すべき時間、評価頻度、通知の送信先を設定します。

    ![新規アラートフォームの後半部分。違反ロジック、スケジュール、重大度、配信チャンネル、作成アクションが表示されています。](/images/dashboard/alert-new-routing.png)

    保存後は、アラート一覧でルールが有効になっており、トリガー、ウィンドウ、重大度、チャンネルが意図した通りであることを確認します。

    ![アラートページ。アラートルールのトリガー、評価ウィンドウ、チャンネル、重大度が表示されています。](/images/dashboard/alerts.png)

    本番環境での対応に依存する前に、アラートをテストしてください。
  </Tab>
  <Tab title="CLI">
    ```bash
    fp alerts create high-errors \
      --trigger-kind metric_threshold \
      --severity warning \
      --trigger-spec '{"metric":"error_count","op":">","value":50,"window_secs":900}'

    fp alerts show high-errors
    fp alerts test high-errors
    fp alerts update high-errors --severity critical --yes
    ```

    `fp alerts list` でルールを確認し、`fp alerts delete <name>` で削除できます。

    完全なアラートコマンドセットについては [`fp alerts` リファレンス](/ja/reference/cloud-cli#alerts) を参照してください。
  </Tab>
</Tabs>

アラートの条件は、エラー、評価スコア、評価の組み合わせ、またはカスタム SQL に基づいて設定できます。受信者を追加してルールをテストし、作成されたインシデントを開いて確認、割り当て、コメント、サブスクリプション、解決を行います。

## 適切なアラート設計

- 条件と影響を受けるワークフローを明確に命名する。
- 環境を明示的にスコープする。
- 無害な単発イベントに反応しないよう、ウィンドウと閾値を設定する。
- 担当者がセッションにたどり着けるリンクやクエリを含める。
- ルールを有効にする前にオーナーを割り当てる。

<Tip>
  監査での指摘を解決した後、同じ障害がポリシーのカバー範囲外で再発する可能性がある場合は、アラートを追加しましょう。
</Tip>
