アラートは測定可能な条件を監視し、条件が発火したときにイシューを開きます。ポリシーでブロックできるかどうかにかかわらず、障害が発生した際に迅速な対応が必要な場合に使用してください。

## アラートの作成とテスト

<Tabs>
  <Tab title="ダッシュボード">
    1. **Analyze → Alerts** に移動し、**new alert** を選択します。代表的なエラーのベルアイコンから始めることもできます。
    2. 名前、重大度、トリガーの種類、条件、評価間隔、違反回数、ウィンドウ、チャンネルを入力します。
    3. アラートを保存し、詳細ページを開いて **test** を実行します。
    4. **Analyze → Issues** に移動して、アラートが開いたイシューの確認、割り当て、コメント、サブスクライブ、解決を行います。

    フォームの前半部分では、アラートの識別情報とトリガーとなるシグナルを設定します。

    ![名前、説明、有効状態、トリガータイプを含む新規アラートフォームの前半部分。](/images/dashboard/alert-new-trigger.png)

    後半部分では、条件が継続する時間、評価頻度、通知の送信先を設定します。

    ![違反ロジック、スケジュール、重大度、配信チャンネル、作成アクションを含む新規アラートフォームの後半部分。](/images/dashboard/alert-new-routing.png)

    保存後、アラートリストを使用して、ルールが有効になっており、トリガー、ウィンドウ、重大度、チャンネルが意図した通りであることを確認してください。オープン中のイシューがあるカードにはその件数が表示されますが、件数がゼロのカードはその行自体が省略されるため、表示がないことは何も意味しません。ゼロを含むすべてのルールの数値を確認するには `fp alerts show <name>` を使用してください。このコマンドは常に件数を表示します。

    ![トリガー、評価ウィンドウ、チャンネル、重大度を含むアラートルールを表示するアラートページ。](/images/dashboard/alerts.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp alerts create high-errors \
      --trigger-kind metric_threshold \
      --severity warning \
      --trigger-spec '{"metric":"error_count","op":">","value":50,"window_secs":900}' \
      --eval-interval-secs 300 \
      --min-breaches 2 \
      --eval-window 3

    fp alerts show high-errors
    fp alerts test high-errors
    fp alerts update high-errors --severity critical --yes
    ```

    新しいアラートは**有効**な状態で作成され、名前が重複する場合は作成前に拒否されます。

    `fp alerts update` はサーバー側で定義全体を置き換えるため、CLI はアラートを再読み込みした上でフラグを上書きします。フラグのみによる更新には、`alerts:write` に加えて `alerts:read` も必要であり、`--yes` を指定しない限り確認が求められます。

    `fp alerts list` でルールを確認し、`fp alerts delete <name>` で削除できます。削除を実行すると、オープン中のイシュー数を含むルールのプレビューが表示され、取り消しができないため実行前に確認が求められます。

    ノイズの多いルールを停止するには削除を使わないでください。`DELETE /alerts/{id}` はカスケード削除です。そのアラートがこれまで開いたすべてのイシューが、コメント、サブスクライバー、アクティビティ履歴ごと削除されます。CLI の確認メッセージではオープン中のイシューが「孤立する」と表現されていますが、API の仕様はカスケード削除なので、履歴は消去されるものとして扱ってください。ルールの発火を停止しつつ記録を保持するには、ルールを無効化してください。ダッシュボードのアラートフォームに有効/無効のトグルがあります。`fp alerts create` も `fp alerts update` も `--enabled` フラグを持たないため、CLI での操作は `fp alerts update <name> --file` に `enabled: false` を含む完全な定義ファイルを渡す方法になります。

    アラートコマンドの完全なリファレンスは [`fp alerts` リファレンス](/ja/reference/cloud-cli#alerts) をご覧ください。
  </Tab>
</Tabs>

<Warning>
  **test** は実際の通知を送信します。アラートに設定された実際のメール、Slack、Webhook チャンネルに送信し、仮のイシューを開くため、オンコールの担当者に通知が届く場合があります。インタラクティブなターミナルでは事前に確認が求められます。`--yes`、`--json`、またはリダイレクトされた stdin を使用するとこの確認はスキップされます。また、サーバーはディスパッチ直後に成功を報告するため、テストが成功してもメッセージが送信されたことは証明されますが、届いたことは保証されません。
</Warning>

## トリガーの定義

トリガーの種類は5つあります。

| `--trigger-kind` | 発火条件 |
| --- | --- |
| `metric_threshold` | メトリクス（エラー数、レイテンシ、コスト、その他の測定可能な値）がしきい値を超えたとき。 |
| `per_event` | 条件に一致するイベントが1件届いたとき。 |
| `evaluation_score` | 評価スコアがしきい値を超えたとき。 |
| `eval_compound` | 複数のスコア条件を組み合わせたとき（例：3つ中2つのスコアが失敗）。 |
| `custom_sql` | 記述したクエリが違反を返したとき。 |

条件の内容は `--trigger-spec` に、選択した種類に応じた形式で指定します。

## 評価値の設定

ダッシュボードのフォームと CLI は同じ4つの値を要求します。

| 設定 | フラグ | 許容値 |
| --- | --- | --- |
| 重大度 | `--severity` | `info`、`warning`、`critical` |
| 評価間隔 | `--eval-interval-secs` | 30〜86,400秒 |
| 違反回数 | `--min-breaches` | 1以上、かつウィンドウ数以下 |
| 評価ウィンドウ | `--eval-window` | 1以上（秒ではなく**インターバル**単位） |

例えば `--eval-interval-secs 300 --min-breaches 2 --eval-window 3` は「5分ごとに評価し、直近3回の評価のうち2回が違反した場合に発火する」という意味です。

## 優れたアラート設計のために

- 条件と影響を受けるワークフローを名前に含めてください。
- 環境を明示的にスコープ指定してください。
- 単発の無害なイベントに反応しないよう、ウィンドウとしきい値を設定してください。
- 担当者がセッションにたどり着けるリンクやクエリを含めてください。
- ルールを有効にする前にオーナーを割り当ててください。
- 同じ症状に対して別のルールを追加する前に `fp alerts show <name>` でオープン中のイシュー数を確認してください。ダッシュボードカードはその行を件数がゼロ以外の場合にのみ表示します。

<Tip>
  監査の発見事項を解決した後、同じ障害がポリシーのカバレッジ外で再発する可能性がある場合は、アラートを追加してください。
</Tip>
