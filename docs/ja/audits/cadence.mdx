エージェント、プロンプト、ツール、モデルの変更に伴って再発する可能性のある障害モードに対して、定期監査を活用してください。

## スケジュールの変更

<Tabs>
  <Tab title="ダッシュボード">
    1. **Analyze → Audits** に移動して、対象の監査を開きます。
    2. **edit settings** を選択し、頻度・ウィンドウ・感度・1回あたりの検出数を変更します。
    3. 監査を保存し、監査ヘッダーで次回の実行時刻を確認します。
    4. 同じヘッダーの **run now** の横にあるコントロールからスケジュールを一時停止・再開できます。
    5. スコープやコンテキストを大きく変更した後は、**run now** を一度実行してください。

    ![一時停止状態、オープンな検出結果、最終実行、次回実行、スイープウィンドウ、感度、run now・edit settings・再開コントロールが表示された監査ヘッダー。](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits edit checkout-reliability \
      --schedule-interval-secs 86400 \
      --schedule-anchor 2026-08-15T09:00:00Z \
      --window-mode since_last \
      --lookback-window-secs 86400 \
      --yes

    fp audits edit checkout-reliability --disabled --yes
    fp audits edit checkout-reliability --enabled --yes
    ```

    `fp audits edit` は変更前に確認を求めるため、ここに示すすべての例で `--yes` を渡しています。サーバーは編集のたびに定義全体を置き換えるため、CLI は現在の監査にご自身の変更を適用した状態で再送します。フラグのみの編集であっても `audits:write` に加えて `audits:read` が必要です。CI キーには両方のスコープを設定してください。

    スケジュールの範囲、ウィンドウの動作、全監査コマンドについては [`fp audits` リファレンス](/ja/reference/cloud-cli#audits) を参照してください。
  </Tab>
</Tabs>

## 2 つのスケジュール境界値

以下のすべての推奨値はこれらの範囲内に収める必要があります。範囲はサーバー側の仕様であり、`fp` はクライアント側でも同様に検証します。範囲外の値を指定すると、422 のラウンドトリップが発生する前にローカルでエラーコード 2 で終了します。

| フィールド | フラグ | 範囲 | デフォルト |
| --- | --- | --- | --- |
| スケジュール間隔 | `--schedule-interval-secs` | 3,600〜604,800 秒（1 時間〜7 日） | 86,400（毎日） |
| ルックバックウィンドウ | `--lookback-window-secs` | 3,600〜7,776,000 秒（1 時間〜90 日） | 604,800（7 日） |

頻度の上限は 7 日です。月次の Cloud 監査は存在しません。

## 頻度の選択

リスクの速度とコストに応じて選択してください。

| リストパターン | 推奨する開始頻度 |
| --- | --- |
| 本番環境での高影響アクション | 毎日、またはリスクのある変更が展開中は毎時間 |
| ワークフローまたはモデルのリグレッション | 毎週 |
| ガバナンスまたはアクセスレビュー | 毎週（利用可能な最長間隔） |

実行間にギャップが生じたり、不必要に広い対象を繰り返し検査したりしないよう、ルックバックウィンドウを頻度に合わせて設定してください。

ワンショット監査は存在しません。すべての監査はスケジュール間隔を持ちます。リリース調査のためには、有効な状態で監査を作成し、最初の実行が完了するまで待ちます（最初の実行はアンカーに関わらず作成直後にキューに追加されます）。その後、`fp audits edit <name> --disabled --yes` で一時停止してください。**run now** を使用する前に必ず再有効化してください。無効化された監査はキューの行を持たないため、無効状態での手動実行は 409 で拒否されます。

## ウィンドウモードとアンカー

`--window-mode` は各実行がスイープするウィンドウを決定します。

| モード | 動作 |
| --- | --- |
| `since_last` | 前回の完全に分析されたウィンドウの終端から継続します。実行がスキップされてもギャップは生じません。 |
| `fixed` | 前回の実行内容に関わらず、毎回 `lookback_window_secs` のローリングウィンドウを再検査します。 |

`--schedule-anchor` は頻度ではなく位相を固定します。実行は `anchor + N × interval` のタイミングで行われます。省略した場合、アンカーはデフォルトで次の 09:00 UTC になります。365 日以上先のアンカーは拒否されます。間隔やアンカーの変更は、既にキューに入っている実行ではなく、次回のスケジュール更新時に反映されます。また、失敗した実行はアンカーを移動しません。

監査のゴールやコンテキストを変更した後は、次回のスケジュール結果に依存する前に一度手動で実行してください。

<Note>
  このページは Cloud セッションを対象とする Cloud 監査スケジュールに関するものです。ローカル監査には独自のタイマーがあります。`failproofai audit --schedule [days]` は 1〜90 日を受け付け、デフォルトは 7 日です。該当マシン上のエージェント履歴をスキャンし、月次オプションが利用できる唯一のインターフェースです。その結果とオーナーシップは、ここで説明している内容とは独立しています。詳細は [ローカルエージェント履歴の監査](/ja/audits/local-audit) を参照してください。
</Note>
