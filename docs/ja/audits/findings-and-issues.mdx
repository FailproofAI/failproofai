ファインディングとは、監査が証拠に基づいて示す失敗に関する声明です。問題（Issue）とは、それに対応するための継続的なワークフローです。

この2つのオブジェクトは異なる語彙を使用しており、並べて表示されるため、まず頭の中で整理しておく価値があります：

| | ファインディング | 問題（Issue） |
| --- | --- | --- |
| 状態 | `open`、`recurring`、`resolved`、`dismissed`、`muted` | `firing`、`acknowledged`、`resolved` |
| フィルターフラグ | `--status` | `--state` |
| ハンドル | ファインディング ID | 問題 ID |
| デフォルト一覧 | ライブセット：open と recurring | 新しい順 |

## トリアージと作業の割り当て

<Tabs>
  <Tab title="ダッシュボード">
    1. **Analyze → Audits** を開き、完了した実行を選択して、分析・推奨事項・セッション・エビデンスクエリを確認するためにファインディングを選択します。
    2. エビデンスを確認した後、ファインディングを承認・割り当て・却下・ミュート・解決、または再オープンします。
    3. **Analyze → Issues** に移動し、状態・重大度・担当者で継続的な受信トレイをフィルタリングします。
    4. 問題を開いて担当者を割り当て、コメントや購読者を追加し、修正が確認された後に解決します。

    まずファインディングのサマリーを確認してください。障害の説明、推奨される対応、重大度、およびランキングが、監査が調査することを期待したセッションと一致しているか確認します。

    ![重大度、発生回数、根本原因分析、推奨アクション、ランキング要因、エビデンスを含む監査ファインディング。](/images/dashboard/audit-finding.png)

    次に、サマリーだけで判断せず、影響を受けたセッションを開いてください。リンクされたトレースに、ファインディングを裏付ける正確なイベントとペイロードが表示されるはずです。

    ![監査ファインディングからリンクされたセッション。関連するエラー箇所が開かれ、イベントメタデータと生ペイロードが表示されている。](/images/dashboard/audit-linked-session.png)

    エビデンスを確認した後、Issues を使用して対応にオーナーを設定し、将来の監査実行とは独立して追跡します。

    ![重大度とオーナーシップを含む、firing・acknowledged・resolved の作業を表示する Issues 受信トレイ。](/images/dashboard/incidents.png)

    問題を開いて調査メモを記録し、購読者に通知し、対応履歴を保存してください。修正がデプロイされ確認された後にのみ解決します。

    ![ソース、違反エビデンス、担当者、購読者、タイムライン、コメントを含む問題の詳細ビュー。](/images/dashboard/incident-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits findings --audit checkout-reliability --status open
    fp audits finding <finding-id>
    fp audits ack <finding-id> --reason "owner assigned"
    fp audits assign <finding-id> --to engineer@example.com
    fp audits mute <finding-id> --reason "expected in staging" --yes
    fp audits dismiss <finding-id> --reason "false positive" --yes
    fp audits resolve <finding-id> --yes
    fp audits reopen <finding-id>

    fp issues list --state firing
    fp issues show <issue-id>
    fp issues ack <issue-id>
    fp issues assign <issue-id> --assignee engineer@example.com
    fp issues comment-add <issue-id> --body "policy is in observe mode"
    fp issues resolve <issue-id> --yes
    ```

    `mute`、`dismiss`、`resolve` はファインディングを抑制またはクローズするため、いずれも実行前に確認が求められます。スクリプト内では `--yes` を渡してください。`ack`、`reopen`、`assign` は元に戻せるブックキーピング操作で、即座に実行されます。`ack`、`mute`、`dismiss` は `--reason` を受け付け、渡しておく価値があります。これはファインディングへの永続的なフィードバックとして保存され、ログに書き込まれて忘れ去られるわけではありません。`resolve`、`reopen`、`assign` は reason を受け付けません。

    割り当てはオブジェクトによって動作が異なります。`fp audits assign` は `--to <email>` が必須で、1人のオーナーを設定します。再実行すると再割り当てになります。`fp issues assign` は繰り返し指定可能な `--assignee` を受け付け、リスト全体を**置き換えます**。省略するとすべての担当者がクリアされます。

    その他の問題操作には `fp issues comment-list <issue-id>`、`fp issues count --state firing`、`fp issues subscribe`/`unsubscribe`/`subscribers <issue-id>` を使用してください。

    監査ファインディングについては [Cloud CLI 監査・問題リファレンス](/ja/reference/cloud-cli#audits)、問題管理については [`fp issues`](/ja/reference/cloud-cli#issues) を参照してください。
  </Tab>
</Tabs>

## ファインディングのレビュー

他の何よりも先に、次の2つのフィールドが対応方針を決定します。

**`kind`** は、`failure`（何かが間違っていた）、`policy` 違反（ルールが破られた）、`improvement`（作業をより良くできる）を区別します。ファインディング上にバッジとして表示されます。`policy` ファインディングはポリシーがクローズできるものです。残り2つは通常、ワークフローの変更、アラート、または人間の対応が必要です。

**`priority`** は 0〜1 のスコアで、実行ごとに再計算され、ファインディングキューのソート順に使用されます。ファインディングページでは **why it ranks here** の下に、値 × 重みとして詳細が表示されます：

| 要因 | 重み |
| --- | --- |
| カバレッジ | 0.30 |
| 重大度 | 0.25 |
| マグニチュード | 0.25 |
| 直近性 | 0.20 |

次に、ファインディングに以下が含まれていることを確認してください：

- 一時的なタイトルではなく、安定した障害モード
- 重大度と運用上の影響
- 影響を受けたセッション ID またはサポートするクエリ
- 動作を再現するのに十分なコンテキスト
- エビデンスと一致する提案された対応

ファインディングを再現するには、全体を取得してください：`fp --json audits finding <id>` は、分析が実際に実行した `evidence`、`evidence_queries`、`scope` を含む完全なレコードを返します。`--json` はグローバルオプションなので、コマンドの前に置きます。

## 問題を使って対応を管理する

ファインディングに割り当て・議論・状態変更・コメント・購読者が必要な場合は、問題を作成またはリンクしてください。問題の `source` はその出所（`audit`、`alert`、または `manual`）を記録します。これが、ダッシュボードが問題を監査の下にネストするのではなく、独自の **Issues** ビューとして提供する理由です。

購読は部分的に自動化されています。問題を承認・コメント・割り当て・または開いた人は自動的に購読されます。`fp issues subscribers` はアクティブな購読者のみを一覧表示するため、手動購読のリストとは限りません。コメントはすべてのアクティブな購読者にメールを送信し、コメントには `issues:read` のみが必要なため、読み取り専用のレビュアーが無言の傍観者になることはありません。

修正がデプロイされ確認されたら問題を解決してください。障害モードが監査対象全体に対して対処されたらファインディングを解決してください。これらのタイミングは異なる場合があります。

## 問題からポリシードラフトを作成する

<Tabs>
  <Tab title="ダッシュボード">
    1. 問題を開き、そのファインディング・引用されたセッション・根本原因・推奨事項を確認します。
    2. **generate policy** を選択し、候補評価の結果と提案された強制の意図を確認します。**no policy** の結果は、その動作にはアラート・ワークフローの変更・または人間の対応が必要である可能性を意味します。
    3. **write this policy** を選択し、**publish version** を選択する前に **Admin → policy editor** で生成されたソースを確認してテストします。候補チェックの結果に同意しない場合は **open the editor anyway** を使用してください。
    4. **Admin → enforcement** に移動し、**observe** モードでバージョンをデプロイして、強制する前に **Observe → policy** でその決定を確認します。

    問題タイトル・ファインディングの説明・根本原因・推奨事項・候補の意図がドラフトの作成に役立ちます。自動的に公開またはデプロイされるものはありません。
  </Tab>
  <Tab title="CLI">
    ダッシュボードで問題を開く前に、CLI を使ってエビデンスを確認します：

    ```bash
    fp issues show <issue-id>
    fp --json audits finding <finding-id>
    fp events --session-id <session-id> --full --all
    ```

    ダッシュボードはひとつの手段であり、CLI はもうひとつの手段です。`fp policies compose "<what it should do>"` でポリシーのドラフトを作成し、`fp policies publish <id> ./policy.mjs` でバージョンを生成し（公開してもデプロイはされません）、`fp fleet deploy <machine> --add <id>:observe` でシャドウモードでマシンに展開します。`:observe` サフィックスは必須です。`--add <id>` のみだと即座に強制されます。`fp guardrails summary --since 24h` で実際に何が行われたかを確認し、その後 `--add <id>:enforce` で昇格させます。

    同等のポリシーソースをまず自分のマシンで試すには、ローカル CLI をファイルに向けます：

    ```bash
    failproofai policies -i -c ./checkout-policies.js
    ```

    `policies.js`、`policies.mjs`、または `policies.ts` で終わるファイル名のファイルをプロジェクト内の `.failproofai/policies/` または `~/` 以下に配置すると、フラグなしですべてのフックイベントで読み込まれます。
  </Tab>
</Tabs>
