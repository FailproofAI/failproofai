これらを出発点として使用し、エージェント、環境、期待するワークフローを追加してください。

<Tabs>
  <Tab title="ダッシュボード">
    **分析 → 監査 → 新規監査** に移動します。このページのレシピは **説明** — この監査が何を検出することを期待するかです。ゴールを判定可能にするワークフロールールは **ブリーフ** の **knows カード** に記載します。これはモデルが最初のイベントを確認する前に読む背景情報で、最大 8,192 文字まで入力でき、監査がすでに検索する内容に追加されます。ブリーフはゴールの代替にはならず、所見の証拠にもなりません。

    次に **reads カード** でスコープを設定します。これらのレシピの半分はスコープなしではノイズになるためです。環境とエージェントで対象を絞り込み、**errors to ignore** には設計上想定済みで処理済みのエラータイプを列挙することで、それらが障害としてカウントされなくなります。エラータイプ名のみを受け付け、これによりリトライループレシピが大量出力されるのを防ぎます。

    新規監査フォームは、スコープ、コンテキスト、スケジュール、通知を追加することでレシピを実行可能な障害チェックに変換します。

    ![スコープ、コンテキスト、スケジュール、エージェントと環境のスコープ、通知チャンネルが設定された新規監査フォーム。](/images/dashboard/audit-new.png)

    作成後、定期実行に頼る前に、監査が期待するステータスとスケジュールでリストに表示されていることを確認してください。

    最初の実行を開いて、所見が意図した障害モードより広いか狭い場合はレシピを調整してください。
  </Tab>
  <Tab title="CLI">
    レシピをテキストファイルとして保存し、作成時に添付します。

    ```bash
    fp audits create retry-loop-review \
      --description "Find agents that repeat a failing tool call without changing anything" \
      --scope '{"environments":["production"]}' \
      --ignore-error-type RateLimitRetried \
      --text-file ./retry-loop-audit.txt \
      --schedule-interval-secs 86400
    ```

    `--text` と `--text-file` は同じブリーフを送信する 2 つの方法です。どちらか一方のみ指定してください。`--url` で参照ページを最大 5 件追加できます（公開 `https://` のみ）。作成リクエストと一緒にすべて送信してください。新しく有効化された監査は即座に実行されるため、2 回目の呼び出しで記述したコンテキストは最初の実行に間に合わない場合があります。
  </Tab>
</Tabs>

## 文言だけでなくレシピ自体を調整する

結果に最も影響する設定は 2 つあります。**感度** (`low`、`medium`、`high`、デフォルト `medium`) は実行がパターンをフラグする積極性を決定し、**実行あたりの所見数** (`--top-k`、デフォルト 50) は保持する件数を制限します。見逃しの方がフォールスポジティブよりコストが高い質問では感度を上げ、そのままではキューを埋め尽くしてしまうようなボリュームパターンでは下げてください。以下の各レシピには出発点が示されています — 変更は最初の実行結果を確認してから行い、事前には行わないでください。

タスクの放棄や人間へのエスカレーション漏れは、エージェントが発生させたエラーではなく、エージェントが本来すべきだったことに対する判定です。そのエージェントの [エージェントコンテキスト](/ja/audits/agent-contracts) を先に記述してください。そうしないと分析に採点基準がありません。

<AccordionGroup>
  <Accordion title="リトライループの繰り返し">
    エージェントが入力を変えず、代替ツールを選択せず、人間にエスカレーションもせずに、同じ失敗したツール呼び出しを繰り返すセッションを検出します。

    `medium` から開始し、意図的にリトライするエラータイプは **errors to ignore** に列挙してください。
  </Accordion>
  <Accordion title="不適切なツール使用">
    選択したツールが指定タスクと一致しない、またはツールの入力がワークフローで必須の前提条件に違反しているセッションを検出します。

    `medium` から開始してください。前提条件自体をブリーフに記載してください。記載がないと分析にチェックするルールがありません。
  </Accordion>
  <Accordion title="安全でないデータアクセス">
    このエージェントに承認されたパスおよびサービス以外で機密データを読み取り、書き込み、または送信しているセッションを検出します。

    `high` から開始してください。見逃した露出は、一度却下するフォールスポジティブよりもコストが高くつきます。
  </Accordion>
  <Accordion title="タスクの放棄">
    要求された結果、明確なエラー、または人間への明示的な引き継ぎなしに終了するセッションを検出します。

    `medium` から開始し、エージェントの **Done when** セクションを先に記述してください — このレシピはその基準に対する判定です。
  </Accordion>
  <Accordion title="コストまたはレイテンシの劣化">
    モデル、ツール、または合計時間が期待する予算を超えるセッションを検出し、原因となるイベントパターンを特定します。

    `low` から開始し、最初の実行が薄い場合は上げてください。予算はブリーフに記載し、設計上低速パスが発生させるエラータイプは **errors to ignore** に含めてください。
  </Accordion>
  <Accordion title="人間エスカレーションの漏れ">
    信頼度、繰り返し失敗、またはポリシーガイダンスによって人間の判断が必要だったにもかかわらず、エージェントが自律的に処理を続けたセッションを検出します。

    `high` から開始し、エスカレーションルールをエージェントの **Must not** セクションに明記して、分析がその基準で判定できるようにしてください。
  </Accordion>
</AccordionGroup>

## 何かを作成する前にまず答えを得る

これらのパターンのいくつかは、ローカル監査にオフライン検出器として既に組み込まれています。ローカル監査は自分のマシン上でエージェント履歴を読み取り、アカウント不要で動作します。

| 検出器 | カウントするパターン |
| --- | --- |
| `sleep-polling-loop` | 長い `sleep`、または `while … sleep … done` のポーリングループ |
| `reread-after-edit` | エージェントが直前に編集または書き込んだファイルの読み取り |
| `find-from-root` | `/` やその他の高レベルディレクトリに対する `find` |
| `redundant-cd-cwd` | シェルがすでに存在するディレクトリへの `cd` |
| `prefer-edit-over-read-cat` | 単一ソースファイルへの `cat`、`head`、`tail`、`less`、または `more` |
| `prefer-edit-over-sed-awk` | `sed -i` または `awk … > file` によるインプレース編集 |
| `prefer-write-over-heredoc` | ヒアドキュメントや `echo > file` による複数行コンテンツの書き込み |
| `git-commit-no-verify` | フックをスキップする `git commit --no-verify` |

これらの検出器はカウントするだけで、ブロックはしません。また、コストやレイテンシは測定しません。同じ対象に対してクラウド監査の費用を払う前に、エージェントがすでに生成している無駄でリスクのあるシェルパターンを確認するために `failproofai audit` を実行してください — [ローカルエージェント履歴の監査](/ja/audits/local-audit) を参照してください。
