監査は、その目標と対象範囲が十分に具体的になり、別のオペレーターが有効な検出結果がどのようなものかを理解できる状態になってから実行してください。

## 実行と検査

<Tabs>
  <Tab title="ダッシュボード">
    1. **Analyze → Audits** に移動して監査を開き、**run now** を選択します。キュー済みの応答は、ディスパッチャーがまもなく開始することを意味します。
    2. 新しい実行を開いて、ステータス、ウィンドウ、所要時間、検出数、レポートを確認します。
    3. エビデンスセッションを選択して、正確なトレースを開きます。
    4. 監査ページに戻り、設定を編集したり、スケジュールを無効にしたり、以前の実行を確認したりします。

    ![オープンな検出結果、最後と次の実行状態、スイープウィンドウ、コンテキスト、run-nowコントロール、およびランク付きの検出結果を表示した監査詳細ページ。](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits run checkout-reliability
    fp audits runs checkout-reliability --limit 10
    fp --json audits runs checkout-reliability
    fp audits findings --audit checkout-reliability
    ```

    `fp audits run` は監査をキューに追加するだけで、完了を待機しません。その後 `fp audits runs <name>` を実行し、実行が完了したら検出結果を確認してください。`--limit` は、指定した値に関わらず、最新の50件を超えて返すことはありません。

    トリアージは監査ではなく検出結果のIDに対して行います：

    ```bash
    fp audits finding <finding-id>
    fp audits ack <finding-id> --reason "owner assigned"
    fp audits assign <finding-id> --to engineer@example.com
    fp audits mute <finding-id> --reason "expected in staging" --yes
    fp audits dismiss <finding-id> --reason "false positive" --yes
    fp audits resolve <finding-id> --yes
    fp audits reopen <finding-id>
    ```

    `mute`、`dismiss`、`resolve` は実行前に確認を求めるため、スクリプト内では `--yes` を渡してください。`ack`、`assign`、`reopen` は即座に実行されます。

    実行履歴、検出結果、トリアージコマンドについては [`fp audits` リファレンス](/ja/reference/cloud-cli#audits) を参照してください。
  </Tab>
</Tabs>

**run now** は拒否される場合があります。実行中の実行と無効化された監査はどちらも `409` を返し、理由はレスポンスの `error` フィールドに含まれます。存在しない監査、または別の組織に属する監査は `404` を返します。

| 拒否の理由 | 意味 | 対処方法 |
| --- | --- | --- |
| 不明な監査 | 監査が存在しないか、別の組織に属しています。 | `fp audits list` で名前を確認してください。 |
| 監査が無効化されています | 無効化された監査にはキュー行がないため、実行待ちにするものがありません。一時停止中の監査には **run now** コントロールが表示されます。 | 先に再開するか、`fp audits edit <name> --enabled --yes` を実行してください。 |
| 実行が既に進行中です | 監査ごとに同時に実行できるのは1件のみです。現在の実行が完了するまで次のキューは追加できません。 | `fp audits runs <name>` で確認してください。 |

## 実行前の確認

- 選択した時間ウィンドウ内にセッションが存在することを確認します。
- 環境とエージェントのフィルターを検証します。
- 参照コンテキストが最新であることを確認します。各実行は監査のページを再読み込みし、到達できない場合は保存済みのコピーにフォールバックします。そのため、移動または削除されたページは、URLを修正するまで古いテキストを提供し続けます。
- 目標が望ましい結論ではなく、障害モードを説明していることを確認します。

## 実行結果の確認

監査詳細ページには5つのタイルが表示されます：トリアージ待ちの **open findings**、**last run**、**next run**、**window**（各実行が読み込む過去の範囲）、**sensitivity**（実行がパターンをフラグする積極性：`low`、`medium`、`high`）。実行ごとの最大N件という上限は別の設定項目（findings per run、`--top-k`、デフォルト50）です。この5つにより、実行を開くよりも迅速にカバレッジの状況を把握できます。

次に、各検出結果の重大度、説明、エビデンスセッション、サポートクエリ、および推奨される防止策を確認します。検出結果は0から1の間の **priority** スコアで順序付けられ、実行ごとにランク付けされます。各検出結果には、その背後にある4つの重み付き要素が表示されます：

| ランキング要素 | 重み |
| --- | --- |
| カバレッジ | 0.30 |
| マグニチュード | 0.25 |
| 重大度 | 0.25 |
| 最近性 | 0.20 |

検出結果は、`open`、`recurring`、`resolved`、`dismissed`、`muted` の5つのステータスのいずれか1つに属します。ステータスフィルターなしの `findings` クエリはライブセット（`open` と `recurring`）を返します。ミュート、却下、または解決した検出結果はそのセットから外れます。`ack` と `assign` はステータスを変更しないため、検出結果はキューに残ります（優先度が下がるか担当者が割り当てられますが、消えるわけではありません）。外れた検出結果を確認するには、ステータスを明示的に指定してください。

検出結果のステータスを使用して、承認、ミュート、却下、解決、再オープン、または作業の割り当てを行います。検出結果が却下された場合でも、エビデンスは保持してください。判断の根拠を説明するためです。各動詞が今後の実行に与える影響については [Findings and issues](/ja/audits/findings-and-issues) を参照してください。

## 空または遅延した実行の解釈

| 実行の状態 | 意味 | 対処方法 |
| --- | --- | --- |
| 分析が実行されたが検出結果がゼロ | 選択したエビデンスが、設定された感度で検出結果をサポートしませんでした。 | スコープに代表的なセッションが含まれていることを確認し、目標またはコンテキストが曖昧すぎなければ正常な結果として扱います。 |
| モデル分析がスキップまたは失敗した | 実行はゼロの検出結果で完了しますが、エージェント調査は実行されていません。決定論的な認証情報とPIIスキャンは実行統計にマッチ数を報告しますが、検出結果は作成しません。 | 分析サービスまたは設定を修正して再実行してください。空の結果を、対象の母集団が健全であることの証拠として解釈しないでください。 |
| モデル分析が無効化されています | 実行はゼロの検出結果で成功します。決定論的スキャンはモデル分析の代替にならず、検出結果も作成しません。 | 検出結果を生成できない監査に依存するのではなく、モデル分析を有効にするか、監査を無効化してください。 |
| 分析キャパシティがすぐに利用できない | 監査はキューに残り、対象母集団をスキップする代わりに再試行します。 | キャパシティを待つか、監査のアンカーを分散させてください。セルフホスト型のオペレーターは、監査エージェントのレプリカと対応するディスパッチャーのキャパシティをスケールアップする必要があります。 |
| 再試行ウィンドウを通じてキャパシティが利用できない状態が続く | 実行はゼロの検出結果で諦め、メール配信が利用可能な場合は失敗通知を送信します。 | 監査フリートが飽和状態にあるか、繰り返し再起動していないか確認してください。 |

最後の3行は、Cloud APIサーバーとそのディスパッチャーの動作を説明しています。マネージドCloud環境では Failproof AI が対処します。セルフホスト型のデプロイメントでは、オペレーター自身が対処する必要があります。

分析が実行されなかった場合、`since_last` 監査は未分析のウィンドウを次の成功した実行のために開いたままにします。スキップされた分析は障害が消えた証拠ではないため、既存の検出結果は廃止されません。

## 通知について

成功した実行は、**新しい**ものを検出した場合にのみ通知します。健全な監査からの無音は正常な状態であり、何も実行されなかったことを示すものではありません。監査ページの **last run**、または `fp audits runs <name>` を確認して、実行が完了していることを確認してください。チャンネルが選択されていない監査は、検出結果をファイルに記録しますが、誰にも通知しません。

実行の失敗またはモデル分析ステップの失敗は、監査のメール受信者に通知されます。監査にメールチャンネルが設定されていない場合、Failproof AI は組織の `alerts.email_default_recipients` 設定にフォールバックするため、サイレントに壊れた監査でもエスカレーションパスが確保されます。

メールは組織で有効化されており、SMTPが設定されている必要があります。そうでない場合、失敗はログに記録されますが、メールは配信できません。実行の失敗は、監査の固定スケジュールアンカーを移動させません。

各実行はまた、各エージェントに使用された正確な [エージェントコンテキスト](/ja/audits/agent-contracts) をコントラクトスナップショットとして保存します。後の編集は、以前の実行に記録されたエビデンス基準を変更しません。

<Warning>
  未検証の検出結果から直接ブロッキングポリシーをデプロイしないでください。引用されたトレースを開いて、ルールが安全でない動作と正当な作業を正しく分離していることを確認してください。
</Warning>
