監査のゴールと対象範囲が、別のオペレーターが有効な所見とは何かを理解できる程度に具体化されてから実行してください。

## 実行と確認

<Tabs>
  <Tab title="ダッシュボード">
    1. **Analyze → Audits** に移動し、監査を開いて **run now** を選択します。キューに入ったという応答は、ディスパッチャーがまもなく開始することを意味します。
    2. 新しい実行を開いて、ステータス、ウィンドウ、所要時間、所見数、レポートを確認します。
    3. エビデンスセッションを選択して、正確なトレースを開きます。
    4. 監査ページに戻って設定を編集したり、スケジュールを無効にしたり、過去の実行を確認したりします。

    ![未解決の所見、最終・次回の実行状態、スイープウィンドウ、コンテキスト、今すぐ実行コントロール、ランク付けされた所見を表示した監査詳細ページ。](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits run checkout-reliability
    fp audits runs checkout-reliability --limit 10
    fp --json audits runs checkout-reliability
    fp audits findings --audit checkout-reliability
    ```

    実行履歴、所見、トリアージコマンドについては [`fp audits` リファレンス](/ja/reference/cloud-cli#audits) を参照してください。
  </Tab>
</Tabs>

## 実行前の確認事項

- 選択した時間ウィンドウ内にセッションが存在することを確認します。
- 環境とエージェントのフィルターを検証します。
- リファレンスコンテキストが最新であることを確認します。
- ゴールが望ましい結論ではなく、障害モードを説明していることを確認します。

## 実行のレビュー

まず実行ステータス、セッションカバレッジ、モデル分析が実行されたかどうかを確認します。次に、各所見の重大度、説明、エビデンスセッション、サポートクエリ、推奨される防止策を確認します。

所見ステータスを使用して、確認、ミュート、却下、解決、再オープン、または作業の割り当てを行います。所見が却下された場合でもエビデンスは保持してください。それが判断の根拠を説明するものです。

## 空の実行または遅延した実行の解釈

| 実行状態 | 意味 | 対処方法 |
| --- | --- | --- |
| 分析が実行されたが所見がゼロだった | 選択したエビデンスが、設定された感度では所見をサポートしなかった。 | スコープに代表的なセッションが含まれていることを確認し、ゴールやコンテキストが曖昧すぎなければ結果を健全と見なします。 |
| モデル分析がスキップまたは失敗した | 実行はゼロの所見で完了するが、エージェント調査は実行されていない。決定論的なクレデンシャルおよびPIIスキャンは実行統計にマッチ数を報告するが、所見は作成されない。 | 分析サービスまたは設定を修正して再実行します。空の結果を対象母集団が健全であるという証拠として解釈しないでください。 |
| モデル分析が無効になっている | 実行はゼロの所見で成功する。決定論的スキャンはモデル分析の代替にならず、所見も作成されない。 | モデル分析を有効にするか、所見を生成できない監査に頼るのではなく監査を無効にしてください。 |
| 即座に利用可能な分析キャパシティがない | 監査はキューに入り、対象母集団をスキップするのではなくリトライします。 | キャパシティが回復するまで待つか、監査アンカーを分散させます。セルフホストのオペレーターは監査エージェントのレプリカと対応するディスパッチャーキャパシティをスケールアップしてください。 |
| リトライウィンドウの間中キャパシティが利用できない | 実行はゼロの所見で諦め、メール配信が利用可能な場合は障害通知を送信します。 | 監査フリートが飽和しているか、繰り返し再起動していないか確認してください。 |

分析が実行されなかった場合、`since_last` 監査はその未分析ウィンドウを次の成功した実行のために開いたままにします。スキップされた分析は障害が消えた証拠ではないため、既存の所見は廃止されません。

## 障害通知の理解

実行の失敗またはモデル分析ステップの失敗は、監査のメール受信者を使用します。監査にメールチャンネルが設定されていない場合、Failproof AI は組織の `alerts.email_default_recipients` 設定にフォールバックするため、サイレントに壊れた監査でもエスカレーションパスが確保されます。

メールは組織で有効になっており、SMTPが設定されている必要があります。そうでない場合、障害はログに記録されますがメールは配信されません。実行の失敗によって監査の固定スケジュールアンカーは移動しません。

すべての実行は、各エージェントに使用された正確な [エージェントコンテキスト](/ja/audits/agent-contracts) をコントラクトスナップショットとして保存します。後の編集は、以前の実行に記録されたエビデンス基準を変更しません。

<Warning>
  未検証の所見から直接ブロッキングポリシーをデプロイしないでください。引用されたトレースを開いて、そのルールが安全でない動作を正当な作業から分離することを確認してください。
</Warning>
