監査の品質はスコープ次第です。「問題を見つけて」のような漠然としたリクエストより、具体的な失敗に関する問いのほうが有用な結果を生み出します。

## 監査を設定する

<Tabs>
  <Tab title="ダッシュボード">
    1. **Analyze → Audits → New audit** に移動し、名前と説明を入力します。名前は組織内で一意である必要があり、説明にはこの監査で検出することを期待する内容を記録します。
    2. **when it runs** では実行頻度とウィンドウを設定します。**what it reads** では、環境・エージェント・無視するエラータイプを指定して対象範囲を絞り込みます（空欄にするとすべてが対象になります）。**how it judges** では感度と1回の実行あたりの検出件数を設定します。
    3. **what it knows** では、オペレーターブリーフを記述し、監査が参照するページを追加します。ブリーフは、モデルが最初のイベントを参照する前に読む背景情報です。これはこの監査がすでに探している内容に追加されるものであり、置き換えるものでも、検出結果のエビデンスになるものでもありません。
    4. **agents** ドロワーを開いて、各エージェントのコンテキストを追加または確認します。コンテキストは監査とは独立して保存され、ヘッダーには既にコンテキストが設定済みのエージェント数が表示されます。詳しくは[エージェントコンテキスト](/ja/audits/agent-contracts)を参照してください。
    5. 通知チャンネルを選択し、**create audit** を選択します。新規監査は有効な状態で開始され、最初の実行がただちにキューに追加されます。

    ![名前、説明、頻度、ウィンドウ、環境・エージェントのスコープ、無視するエラー、分析設定、ブリーフ、参照ページ、通知チャンネルを含む新規監査フォーム。](/images/dashboard/audit-new.png)

    **what it reads** カードの **agents** はスコープフィルターです。各実行でスイープするセッションを決定します。エージェントの「目的」は別途エージェントドロワーで管理します。
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits create checkout-reliability \
      --description "Find checkout failures that agents do not recover from" \
      --scope '{"environments":["production"],"agent_ids":["checkout-agent"]}' \
      --schedule-interval-secs 86400 \
      --window-mode since_last \
      --sensitivity medium \
      --text-file ./checkout-audit-brief.txt \
      --url https://runbooks.example.com/checkout
    ```

    名前以外のすべてのフィールドにはサーバーのデフォルト値があるため、`fp audits create nightly` だけでも有効な日次監査として機能します。すでに使用されている名前は、何も作成される前に事前に拒否されます。新規監査は `--disabled` を指定しない限り有効な状態で開始され、有効な監査の最初の実行はただちにキューに追加されます。

    `--file audit.json` で保存済みの JSON を定義のベースとして使用し、その上にフラグを重ねることができます。監査定義をレビューしたりバージョン管理で管理したりする場合の、再現性の高い方法です。

    完全なリファレンスは [`fp audits create` リファレンス](/ja/reference/cloud-cli#audits)を参照してください。
  </Tab>
</Tabs>

## 範囲とデフォルト値

数値設定は両側で検証されるため、範囲外の値はリクエストが拒否されるのではなく、使用エラーとして扱われます。

| 設定 | CLIフラグ | 有効な値 | デフォルト |
| --- | --- | --- | --- |
| 頻度 | `--schedule-interval-secs` | 3600〜604800（1時間〜7日間） | 86400（日次） |
| スケジュールアンカー | `--schedule-anchor` | ISO 8601 UTC。365日以上先のアンカーは拒否される | 翌09:00 UTC |
| ウィンドウ | `--window-mode` | `fixed`、`since_last` | `since_last` |
| ルックバック | `--lookback-window-secs` | 3600〜7776000（1時間〜90日間） | 604800（7日間） |
| 感度 | `--sensitivity` | `low`、`medium`、`high` | `medium` |
| 1回あたりの検出件数 | `--top-k` | 1以上 | 50 |

アンカーはスケジュールの位相を固定します。実行は `anchor + N * interval` のタイミングで行われるため、実行の遅延や手動の **run now** によって頻度がずれることはありません。最初の実行はアンカーに関係なく、作成時にただちにキューに追加されます。

## ブリーフと参照ページ

フォームには両方の上限がカウンターとして表示され、CLIでも同じ2つの制限が適用されます。

- ブリーフは8,192文字以内です（`--text`、またはファイルから読み込む場合は `--text-file` を使用します。両方を同時に指定することはできません）。
- 監査が参照できるページは最大5ページで、公開されている `https://` URLのみ対象です（`--url` を繰り返し指定）。

参照URLは保存時に検証されます。プライベート・ループバック・クラウドメタデータのアドレスは拒否され、URLが拒否されると作成全体が失敗します。不完全な監査が残ることはありません。受理されたページはバックグラウンドで取得されるため、サイトが遅くても保存がブロックされることはありません。各実行時に再取得が行われ、到達できない場合は保存済みのスナップショットにフォールバックします。スナップショットは自動的に週次で更新されます。ページが更新されたことがわかっていて次回の実行前に反映させたい場合は、`fp audits context-refresh <name>` を使用してください。

ブリーフとURLは、2回目の呼び出しではなく、作成リクエストと一緒に送信してください。有効な新規監査はそのレコードがコミットされた瞬間に実行対象となるため、後から書き込んだコンテキストはディスパッチャーに追い越され、最初の実行（まさに確認しているその実行）に間に合わない可能性があります。後から変更するには `fp audits context-set <name>` を使用します。これは指定したほうの半分を置き換え、もう一方はそのまま残します。

<Tip>
  既知の失敗セッションといくつかの正常なセッションから始めてください。これにより、監査にポジティブな例と比較セットの両方が与えられます。
</Tip>

<Info>
  監査コンテキストは独自のリソースとして保存されます。定義エンドポイントは更新時にコンテキストの書き込みを拒否するため、監査への通常の無関係な編集がブリーフや参照ページを上書きすることはありません。
</Info>
