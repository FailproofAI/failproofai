---

```bash
failproofai migrate --dry-run   # 計画を表示するだけで、変更は一切行わない
failproofai migrate             # 実際に実行する
```

通常、このコマンドを直接入力する必要はない。アップグレード後の最初のコマンド実行時に自動で動作し、[`failproofai update`](/ja/cli/update) にも組み込まれている。実行前に計画を確認したいときや、移行処理だけを単独で実行したいときに直接使用する。

## バージョンではなくレイアウトを基準にする

`~/.failproofai/VERSION` には **レイアウト** 番号が記録されている。これはリリースバージョンではなく、ディレクトリの構造を表す数値だ。移行処理はこの番号を基準にしているため、長期間バージョンを飛ばしても効率的に処理できる。

- npm のバージョンはリリースのたびに変わり、2 つのレイアウトの間に数十のバージョンが存在することもある。
- そのため、**レイアウトの変更なしに** 30 リリースをスキップしたマシンは、30 個の空処理ではなく **移行ゼロ** で済む。
- 複数のレイアウトを一度にスキップした場合は、各ステップが順番に実行され、それぞれのステップは自分の入出力だけを担う。

npm はインストール済みのパッケージを自動で更新できないため、これは重要な特性だ。あるバージョンで数カ月止まり、その後いくつかのレイアウトをまとめて適用するのは、例外的なケースではなく通常のパターンである。

## ドライラン

`--dry-run` は実行されるステップの正確な連鎖と、事前に保存されるファイルを表示するだけで、移行・バックアップ・台帳への記録など、何も変更しない。

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## 引き継がれるデータと再構築されるデータ

ホームディレクトリ内の各パスは保持するデータの種類によって分類され、移行時に破棄できるかどうかが決まる。ルールは次のとおり: **派生データや再取得可能なデータは破棄してよい。ユーザーが入力したデータ、未配信のデータ、マシンを識別するデータは引き継ぐ。**

| 引き継がれるデータ | 再構築または再取得されるデータ |
|---|---|
| `config.json` — 設定、`daemon.configured`、追加のキャプチャパス | 監査キャッシュ |
| `credentials.json` — クラウド登録情報 | クラウド管理のデプロイメント（次回のポーリング時に再取得・ダイジェスト検証） |
| `policies-config.json` — ポリシーの選択と設定パラメータ | デーモンの一時状態 |
| `policies/` — 独自のポリシーファイルとそれが参照するヘルパー | |
| `hook-activity/` — ダッシュボードが参照する判断ログ | |
| アップロードキューに残っている未配信イベント | |
| `cursors/` — コレクターのウォーターマーク | |
| `bin/` のデーモンバイナリ | |

<Note>
  未配信イベントは破棄せず引き継ぐ。これは、損失が単なる遅延ではなく永続的なものになるためだ。コレクターのウォーターマークはスプール内のデータをすでに超えており、そのトランスクリプト範囲が再び読まれることはない。また、移行完了後にデーモンがスプール内のデータを即座に配信するため、通常は引き継ぐべき未配信データは残っていない。
</Note>

`config.json`、`credentials.json`、`policies-config.json` に *新しい* バージョンが書き込んだキーも、古いリーダーによって破棄されることなく保持される。

## 移行後に残る記録

```
~/.failproofai/migrations/
  applied.json                 各ステップの記録: レイアウト、CLI、タイムスタンプ、処理時間、結果
  backup-layout<n>/            最初のステップ実行前に取得した、再取得不可能なファイルのコピー
```

`applied.json` は「このマシンが実際にどのような移行を経てきたか」を示すものであり、アップグレード後に問題が発生した場合に最初に確認すべき情報だ。バグレポートには必ず添付すること。

バックアップをディレクトリ全体のコピーにせず、意図的に小さくしているのには理由がある。設計上、移行処理が再取得不可能なデータを削除することはないため、リスクとして想定すべきなのは *ステップ内の不具合* であり、そのような不具合が影響するのはこれら少数のファイルだけだ。

## ステップが失敗した場合

そのステップでチェーンが停止する。`VERSION` は正常に完了したステップによってのみ更新されるため、ホームディレクトリには古いレイアウトが維持され、次のコマンド実行時に再試行される。部分的な移行が完了したとみなされることはない。失敗したステップは `"ok": false` として `applied.json` に記録され、バックアップは取得した場所にそのまま残る。

## 新しいホームディレクトリは移行されず拒否される

`~/.failproofai/` が現在実行中の failproofai より **新しい** バージョンによって作成されている場合、コマンドは停止し、アップグレードを促すメッセージを表示する。そのデータ自体は正常であり、新しい CLI で読み取り可能だ。「前のバージョンへの移行」という概念は存在せず、リセットすれば復元可能なデータが失われる。

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

デーモンも同じルールを適用する。`failproofaid` は対応していないレイアウトに対して起動を拒否し、移動済みのパスへの読み書きを試みることはない。
