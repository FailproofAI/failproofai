ホスト型のPython評価はカウントと比較が可能です。ツール呼び出しの回数、エラーの回数、セッションの所要時間などを計測できます。しかし、回答が*正しかった*かどうか、返答が失礼だったかどうか、エージェントが行動する前にポリシーを確認したかどうかは判断できません。

**LLMジャッジ**はそれができます。良い状態を平易な言葉で説明すると、モデルがセッションを読み、推論とともに0から1のスコアを返します。

<Note>
ジャッジはセッションごとに1回のモデル呼び出しが発生しますが、コード評価はコストがかかりません。会話を*理解する*必要がある問いにのみジャッジを使用してください。また、条件を設定して、実際に問いの対象となるセッションでのみ実行されるようにしましょう。
</Note>

## どちらを選ぶべきか？

| 問い | 使用するもの |
| --- | --- |
| 同じツールを2回呼び出したか？ | コード |
| エラーはいくつあったか？ | コード |
| セッションは30秒以内だったか？ | コード |
| 顧客は緊迫感を表現していたか？ | [分類器](/ja/evaluations/jev) |
| 顧客はどれほど不満を感じていたか？ | [分類器](/ja/evaluations/jev) |
| 回答は実際に正確だったか？ | **ジャッジ** |
| 返答は失礼または否定的だったか？ | **ジャッジ** |
| 返金を約束する前に返金ポリシーを確認したか？ | **ジャッジ** |

大まかな判断基準：**数えられるもの → コード、事前にリストアップできる回答 → [分類器](/ja/evaluations/jev)、説明が必要なもの → ジャッジ。** ジャッジは見たものについて文章を書くものです。その数字が「なぜ？」という疑問を引き起こすときに使用してください。

事前に決める必要はありません。測定したいことを説明すればアシスタントが選択し、選んだ理由を伝えます。後から変更することもできます。

## 作成方法

1. **Analyze → eval authoring** に移動し、**new eval** を選択します。
2. 判断したい内容を説明し、**draft** を選択します。
3. **criteria**、**threshold**、**condition** を確認してデプロイします。

### Criteria

疑問形ではなく要件として書かれた1〜2文：

> アシスタントは返金ポリシーを確認せずに返金を約束または承認してはならない。

何が*失敗*になるかを具体的に記述してください。「返答は良かったか？」では意味のない数字しか得られませんが、上の文章なら実際に活用できる数字が得られます。

### Threshold

セッションが合格とみなされるスコアの閾値。`0.7` が妥当な出発点です。0から1までの完全なスコアは常に保存されるため、thresholdは合格/不合格のみを決定します。分布を確認して調整することもできます。

### Condition

他の評価と同じPython形式の条件ですが、ここでは特に重要です。条件がない場合、ジャッジは組織内の**すべての**セッションに対して実行され、それぞれモデル呼び出しが発生します：

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

条件なしでジャッジをデプロイしようとすると、ダッシュボードが警告を表示します。それが適切な場合もあります（すべてのセッションを完全に評価したい低ボリュームのエージェントなど）が、意図的な判断であるべきで、偶発的であってはなりません。

## ジャッジが見るもの

会話はターン形式で表示され、セッションが長い場合は最新のものが先頭に来ます：

- ユーザーが言ったこと
- アシスタントの返答
- **エージェントが呼び出したすべてのツールと、その呼び出しが返した内容（順序通り）**

最後の点が「XをYの*前に*行ったか」という問いを適切に判断できる理由です。失敗したツール呼び出しは失敗として表示されるため、「エラーから適切に回復したか」という問いにも対応できます。

非常に長いセッションはモデルのコンテキストに収まるよう切り詰められます。その場合、推論に明示的にその旨が記載されます。セッションの一部に基づいた判断が、全体に基づいたものとして表示されることはありません。

## 結果の読み方

ジャッジは他のスコア付き評価と同様に**スコア**を生成するため、チャート化、フィルタリング、アラートのトリガーも同様に機能します。数値と並んで、ジャッジの**推論**（見た内容を説明する段落）が保存されます。スコアに驚いたときはまずそれを読んでください。たいていは真に興味深いセッションか、基準を改善すべきサインです。

明確なケースではスコアは安定していますが、ビット単位で決定論的ではありません。ボーダーラインの単一スコアは判決としてではなく、セッション自体を読みに行くきっかけとして捉えてください。

## 制限事項

- **テストはまだ利用できません。** ドライランにはセッションの割り当てがなく、その割り当てがモデルバジェットの使用を承認するものであるため、テスト呼び出しには課金先がありません。狭い条件でデプロイし、最初のいくつかの結果を確認してください。
- **バックフィルは利用できません。** コード評価のバックフィルは数ヶ月分の履歴に対して無料で行えますが、ジャッジで行うと数分でバジェット全体を消費してしまいます。
- **criteriaを編集すると新しいバージョンが公開されます。** 古いスコアと新しいスコアは比較できないため、1つのトレンドラインに混在させるのではなく、分けて保管されます。
- **ジャッジは常にスコアを生成し**、メトリクスやアサーションは生成しません。

## バジェットが尽きたとき

ジャッジは組織のモデルバジェットを消費します。バジェットが枯渇した場合、ジャッジ評価は静かに失敗するのではなく明確な理由とともに停止し、**コード評価は通常通り継続して実行されます**。バジェットを増やすと、次のセッションから再開されます。
