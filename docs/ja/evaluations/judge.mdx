ホストされたPython評価では、ツール呼び出しの回数、エラーの数、セッションの所要時間といった計数・比較が可能です。しかし、回答が*正確かどうか*、返信が失礼かどうか、エージェントが行動前にポリシーを確認したかどうかは判断できません。

**LLMジャッジ**はそれができます。優れた回答の基準を平易な言葉で説明するだけで、モデルがセッションを読み込み、0から1のスコアとその根拠を返します。

<Note>
ジャッジは実行するセッションごとに1回のモデル呼び出しが必要ですが、コード評価は無料です。会話の*内容を理解*する必要がある質問にのみジャッジを使用してください。また、条件を設定して、実際に問いたいセッションに対してのみ実行されるようにしましょう。
</Note>

## どれを使えばいい？

| 質問 | 使うもの |
| --- | --- |
| 同じツールを2回呼び出したか？ | コード |
| エラーはいくつあったか？ | コード |
| セッションは30秒以内だったか？ | コード |
| 顧客は緊急性を示したか？ | [クラシファイア](/ja/evaluations/jev) |
| 顧客はどれほど不満を感じていたか？ | [クラシファイア](/ja/evaluations/jev) |
| 回答は実際に正確だったか？ | **ジャッジ** |
| 返信は失礼または素っ気なかったか？ | **ジャッジ** |
| 返金を約束する前に返金ポリシーを確認したか？ | **ジャッジ** |

大まかな判断基準は次のとおりです。**数えられるもの→コード、あらかじめ選択肢を列挙できる回答→[クラシファイア](/ja/evaluations/jev)、説明が必要なもの→ジャッジ。** ジャッジは見たものを文章で説明します。スコアを見た人が「なぜ？」と問い返すような場合に使いましょう。

最初から決める必要はありません。測定したい内容を説明すると、アシスタントが選択して、どれを選んだかとその理由を教えてくれます。後から変更することも可能です。

## 作成方法

1. **Analyze → eval authoring** に移動し、**new eval** を選択します。
2. ジャッジしたい内容を説明し、**draft** を選択します。
3. **criteria**、**threshold**、**condition** を確認してデプロイします。

### Criteria

質問形式ではなく、要件として1〜2文で記述します。

> エージェントは、返金ポリシーを確認せずに返金を約束したり承認したりしてはならない。

何があれば*不合格*になるかを具体的に記述してください。「回答は良かったか？」という基準では意味のない数値しか得られませんが、上記の文章であれば行動に移せる数値が得られます。

### Threshold

セッションが合格となるスコアの下限値です。`0.7` が妥当な出発点です。0から1の完全なスコアは常に保存されるため、threshold は合否判定にのみ使用されます。分布を確認して調整できます。

### Condition

他の評価と同様のPython条件ですが、ここではとくに重要です。条件を設定しないと、ジャッジは組織の**すべて**のセッションに対して実行され、セッションごとにモデル呼び出しが発生します。

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

条件なしでジャッジをデプロイしようとすると、ダッシュボードが警告を表示します。完全にジャッジしたい低ボリュームのエージェントに対して条件なしで使うのは問題ありませんが、それは意図的な判断であるべきで、うっかりそうなるのは避けましょう。

## ジャッジが参照するもの

会話をターン単位で参照します。セッションが長い場合は最新のものから順に表示されます。

- ユーザーの発言
- エージェントの返答
- **エージェントが呼び出したすべてのツールと、その呼び出し結果（順序通り）**

最後の点があるからこそ、「XをするよりもYを先にしたか」という問いが公平に問えます。ツール呼び出しが失敗した場合は失敗として表示されるため、「エラーからうまく回復したか」という問いにも対応できます。

非常に長いセッションはモデルのコンテキストに収まるよう切り詰められます。その場合、理由の説明に明示的に記載されます。セッションの一部だけを見て全体を見たかのような判断が行われることはありません。

## 結果の読み方

ジャッジは他のスコア付き評価と同様に**スコア**を生成するため、チャート表示、フィルタリング、アラートのトリガーなどが同じ方法で機能します。数値に加えて、ジャッジが見たものを説明した**reasoning**（段落形式のテキスト）も保存されます。スコアが予想外だったときはまずそれを読んでください。たいていは本当に興味深いセッションか、criteria を精緻化すべきサインです。

明確なケースではスコアは安定していますが、ビット単位での決定論的な再現性はありません。境界線上の単一スコアは判決として扱うのではなく、セッションを実際に読みに行くためのヒントとして捉えてください。

## 制限事項

- **テストはまだ利用できません。** ドライランにはセッションの割り当てがなく、その割り当てこそがモデル予算の消費を承認するものです。そのため、テスト呼び出しに課金する対象がありません。狭い条件でデプロイして、最初の数件の結果を確認してください。
- **バックフィルは利用できません。** コード評価を数ヶ月分の履歴に遡って適用するのは無料ですが、ジャッジで同じことをすると、予算を数分で使い果たしてしまいます。
- **criteriaを編集すると新しいバージョンが公開されます。** 古いスコアと新しいスコアは比較できないため、1つのトレンドラインに混在させるのではなく、別々に管理されます。
- **ジャッジは常にスコアを生成します。** メトリクスやアサーションは生成しません。

## 予算を使い切ったとき

ジャッジは組織のモデル予算を消費します。予算が尽きると、ジャッジ評価はサイレントに失敗するのではなく、明確な理由とともに停止します。**コード評価は通常通り継続して実行されます。** 予算を増やせば、次のセッションから再開されます。
