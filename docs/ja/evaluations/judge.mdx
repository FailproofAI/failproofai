ホストされたPython評価は数えて比較することができます：ツール呼び出しの回数、エラーの数、セッションにかかった時間。しかし、答えが*正しかった*かどうか、返答が失礼だったかどうか、エージェントが行動する前にポリシーを確認したかどうかは判断できません。

**LLMジャッジ**はそれができます。良い状態とはどのようなものかを平易な言葉で説明すると、モデルがセッションを読み、根拠とともに0から1のスコアを返します。

<Note>
ジャッジは実行するセッションごとに1回のモデル呼び出しを消費しますが、コード評価は無料です。会話を*理解する*必要がある質問にのみジャッジを使用してください。また、条件を設定して、実際にその質問に関係するセッションでのみ実行されるようにしてください。
</Note>

## どれを使うべきか？

| 質問 | 使用するもの |
| --- | --- |
| 同じツールを2回呼び出したか？ | コード |
| エラーはいくつあったか？ | コード |
| セッションは30秒未満だったか？ | コード |
| 顧客は緊急性を示したか？ | [決定モデル](/ja/evaluations/jev) |
| 顧客はどれくらい不満を感じていたか？ | [決定モデル](/ja/evaluations/jev) |
| 答えは実際に正しかったか？ | **ジャッジ** |
| 返答は失礼または否定的だったか？ | **ジャッジ** |
| 返金を約束する前に返金ポリシーを確認したか？ | **ジャッジ** |

大まかなルール：**数えられるもの → コード、事前に列挙できる回答 → [決定モデル](/ja/evaluations/jev)、説明が必要なもの → ジャッジ。** ジャッジは見たものについて文章で説明するもので、数値を見た人が「なぜ？」と聞きたくなるような場合に使ってください。

事前に決める必要はありません。測定したいことを説明すれば、failproofが選択し、何を選んだかとその理由を教えてくれます。**スコアの付け方**で切り替えることができます。

## 作成方法

1. **分析 → チェック → 新しい評価** に移動し、**スコアの付け方** で **LLMジャッジ** を選択します。
2. ジャッジしたいことを説明します。
3. **レビュー** で、基準（**ジャッジが確認する内容**）、しきい値（**合格するスコア以上**）、および **条件** を確認してからデプロイします。

### 基準

質問ではなく要件として書かれた1〜2文：

> アシスタントは、返金ポリシーを最初に確認せずに、返金を約束または承認してはならない。

何が*失敗*になるかを具体的に記述してください。「返答は良かったか？」では意味のない数値しか得られませんが、上記の文なら実際に対処できる数値が得られます。

### しきい値

セッションが合格するスコアの下限値。`0.7` が適切な出発点です。0から1の完全なスコアは常に保存されるため、しきい値は合否のみを決定します。分布を確認して調整することができます。

### 条件

他の評価と同じPython条件で、ここでははるかに重要です。条件がない場合、ジャッジは組織内の**すべての**セッションに対して実行され、それぞれにモデル呼び出しが発生します：

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

条件なしでジャッジをデプロイしようとすると、ダッシュボードが警告を表示します。これが適切な場合もあります（完全にジャッジしたい低ボリュームのエージェントなど）が、意図的な決定であるべきで、偶然であってはなりません。

## ジャッジが見るもの

会話をターンとして表示し、セッションが長い場合は最新のものから順に表示します：

- ユーザーが言ったこと
- アシスタントが返答したこと
- **エージェントが呼び出したすべてのツールと、その呼び出しが返した内容（順番通り）**

最後の部分があるからこそ、「XをYの*前に*行ったか」という質問が公平に問えるのです。失敗したツール呼び出しは失敗として表示されるため、「エラーから適切に回復したか」という質問にも使えます。

非常に長いセッションはモデルのコンテキストに収まるよう切り詰められます。その場合、推論で明示的にその旨が示されます。セッションの一部を全体として判断したという形で結果が表示されることはありません。

## 結果の読み方

ジャッジは他のスコア付き評価と同様に**スコア**を生成するため、チャート表示、フィルタリング、アラートのトリガーも同じように機能します。数値とともに、ジャッジの**推論**（見たものを説明した段落）が保存されます。スコアに驚いた場合はまずそれを読んでください。たいていは本当に興味深いセッションか、基準を改善すべきサインです。

明確なケースではスコアは安定していますが、ビット単位で決定論的ではありません。境界線上の単一スコアは評決ではなく、セッションを実際に読みに行くきっかけとして捉えてください。

## 制限事項

- **テストはまだ利用できません。** ドライランにはセッションの割り当てがなく、その割り当てがモデル予算の消費を承認するものです。そのため、テスト呼び出しに課金するものが存在しません。狭い条件でデプロイし、最初のいくつかの結果を確認してください。
- **バックフィルはモデル予算を消費します。** コード評価のバックフィルは無料ですが、過去のセッションをジャッジでスコア付けすると、それぞれにモデル呼び出しのコストがかかります。**デプロイ後に過去のセッションをプレビュー** にチェックを入れるか、ページ上で **過去のセッションをスコア付け** を選択してください。不足分の確認は無料で、確認するまでスコア付けは開始されません。ウィンドウは狭く保つようにしてください。
- **基準を編集すると新しいバージョンが公開されます。** 古いスコアと新しいスコアは比較できないため、1つのトレンドラインに混在させるのではなく、分けて保管されます。
- **ジャッジは常にスコアを生成します**。メトリクスやアサーションは生成しません。

## 予算がなくなった場合

ジャッジは組織のモデル予算を消費します。予算が尽きると、ジャッジ評価はサイレントに失敗するのではなく明確な理由とともに停止し、**コード評価は通常通り実行し続けます**。予算を増額すると、次のセッションから再開されます。
