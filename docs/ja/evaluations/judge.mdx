ホストされたPython評価は、数えて比較することができます：ツール呼び出しの回数、エラーの回数、セッションにかかった時間。しかし、回答が*正確*だったか、返信が失礼だったか、エージェントが行動する前にポリシーを確認したかどうかは判断できません。

**LLMジャッジ**はそれができます。良い状態がどのようなものかを平易な言葉で記述すると、モデルがセッションを読み取り、推論とともに0から1のスコアを返します。

<Note>
ジャッジは実行するセッションごとに1回のモデル呼び出しのコストがかかりますが、コード評価はコストゼロです。ジャッジは会話を*理解する*必要がある質問にのみ使用してください。また条件を設定することで、実際に対象となるセッションでのみ実行されるようにしてください。
</Note>

## どちらを使えばいいか

| 質問 | 使用 |
| --- | --- |
| 同じツールを2回呼び出したか？ | コード |
| エラーはいくつあったか？ | コード |
| セッションは30秒以内だったか？ | コード |
| 顧客は緊急性を表明したか？ | [クラシファイア](/ja/evaluations/jev) |
| 顧客はどの程度不満を感じていたか？ | [クラシファイア](/ja/evaluations/jev) |
| 回答は実際に正確だったか？ | **ジャッジ** |
| 返信は失礼または否定的だったか？ | **ジャッジ** |
| 払い戻しを約束する前に払い戻しポリシーを確認したか？ | **ジャッジ** |

大まかな判断基準：**数えられる → コード、事前にリストアップできる回答 → [クラシファイア](/ja/evaluations/jev)、説明が必要 → ジャッジ。** ジャッジは見た内容について文章を書くものです。その数字を見た人が「なぜ？」と聞きたくなるような場合に使ってください。

事前に決める必要はありません。測定したいことを記述すると、アシスタントが選んで、何を選んだか、その理由を教えてくれます。後から変更することもできます。

## 作成方法

1. **Analyze → eval authoring** に移動し、**new eval** を選択します。
2. ジャッジしたい内容を記述し、**draft** を選択します。
3. **criteria**、**threshold**、**condition** を確認してからデプロイします。

### Criteria（基準）

質問形式ではなく要件として書かれた1〜2文：

> アシスタントは、払い戻しポリシーを最初に確認せずに、払い戻しを約束または承認してはならない。

何が*失敗*になるかを具体的に記述してください。「返答は良かったか？」という基準では意味のない数値しか得られませんが、上記の文であれば行動に移せる数値が得られます。

### Threshold（閾値）

セッションが合格とみなされるスコアの下限値。`0.7` が妥当な出発点です。0から1の完全なスコアは常に保存されるため、閾値は合格/不合格を決定するだけで、分布を確認して調整することができます。

### Condition（条件）

他の評価と同じPython条件ですが、ここではより重要です。条件がない場合、ジャッジは組織内の**すべての**セッションに対して実行され、それぞれにモデル呼び出しのコストがかかります：

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

条件なしでジャッジをデプロイしようとすると、ダッシュボードが警告を表示します。完全にジャッジしたい低ボリュームのエージェントの場合は問題ありませんが、偶然ではなく意図的な決定であるべきです。

## ジャッジが参照するもの

会話のターン。セッションが長い場合は新しい順に表示されます：

- ユーザーが言ったこと
- アシスタントが返答したこと
- **エージェントが呼び出したすべてのツールと、その呼び出し結果（順番通り）**

最後の点が、「Xの*前に*Yを行ったか」という質問を公平に問えるようにしています。失敗したツール呼び出しは失敗として表示されるため、「エラーから適切に回復したか」という質問にも対応できます。

非常に長いセッションは、モデルのコンテキストに収まるように切り詰められます。その場合、推論に明示的にそのことが記載されます。セッションの一部についての判断が、全体についての判断として提示されることはありません。

## 結果の読み方

ジャッジは他のスコア付き評価と同様に**スコア**を生成するため、チャートへの表示、フィルタリング、アラートのトリガーも同じように機能します。数値と並んで、ジャッジの**推論**（見た内容を説明する段落）が保存されます。スコアに驚いたときはまず推論を読んでください。大抵は本当に興味深いセッションか、基準を磨く必要があることを示すサインです。

明確なケースではスコアは安定していますが、ビット単位で決定論的ではありません。境界線上の単一スコアは判決としてではなく、セッションを実際に読みに行くきっかけとして捉えてください。

## 制限事項

- **テストはまだ利用できません。** ドライランにはセッション割り当てがなく、その割り当てこそがモデル予算の消費を承認するものです。そのためテスト呼び出しに課金するものが存在しません。狭い条件でデプロイして最初のいくつかの結果を確認してください。
- **バックフィルは利用できません。** コード評価を数ヶ月分の履歴にバックフィルするのは無料ですが、ジャッジで同じことをすると数分で予算を使い果たします。
- **基準を編集すると新しいバージョンが公開されます。** 古いスコアと新しいスコアは比較できないため、1つのトレンドラインに混在させるのではなく、別々に保持されます。
- **ジャッジは常にスコアを生成します。** メトリクスやアサーションは生成しません。

## 予算が尽きたとき

ジャッジは組織のモデル予算を消費します。予算が枯渇すると、ジャッジ評価はサイレントに失敗するのではなく、明確な理由とともに停止します。**コード評価は通常通り実行し続けます。** 予算を増やすと、次のセッションから再開します。
