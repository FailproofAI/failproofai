ホスト型のPython評価でカウントや比較が可能です。ツール呼び出し回数、エラー数、セッション時間など。しかし、回答が*正しかったか*、返答が失礼だったか、エージェントが行動する前にポリシーを確認したかどうかは判断できません。

**LLMジャッジ**ならそれができます。良い状態とはどういうものかを平易な言葉で説明すれば、モデルがセッションを読んで0から1のスコアとその根拠を返します。

<Note>
ジャッジは実行するセッションごとに1回のモデル呼び出しコストが発生しますが、コード評価はコスト不要です。会話を*理解する*必要がある問いにのみジャッジを使い、条件を設定して対象のセッションにのみ実行されるようにしてください。
</Note>

## どれを使えばよいか？

| 問い | 使うもの |
| --- | --- |
| 同じツールを2回呼び出したか？ | コード |
| エラーはいくつあったか？ | コード |
| セッションは30秒以内だったか？ | コード |
| 顧客は緊急性を示したか？ | [分類器](/ja/evaluations/jev) |
| 顧客はどの程度不満を持っていたか？ | [分類器](/ja/evaluations/jev) |
| 回答は実際に正しかったか？ | **ジャッジ** |
| 返答は失礼または無愛想だったか？ | **ジャッジ** |
| 返金を約束する前に返金ポリシーを確認したか？ | **ジャッジ** |

目安：**数えられるもの → コード、あらかじめ列挙できる回答 → [分類器](/ja/evaluations/jev)、説明が必要 → ジャッジ。** ジャッジは見たものについて文章を書くものです。スコアを見た人が「なぜ？」と聞いてくるような場面に使いましょう。

あらかじめ決める必要はありません。何を測定したいかを説明すれば、アシスタントが選んで、どれを選んだかとその理由を教えてくれます。後から変更もできます。

## 作成方法

1. **Analyze → eval authoring** に移動し、**new eval** を選択します。
2. 評価したい内容を説明し、**draft** を選択します。
3. **criteria**、**threshold**、**condition** を確認してからデプロイします。

### Criteria（基準）

質問形式ではなく、要件として書いた1〜2文：

> アシスタントは返金ポリシーを確認せずに返金を約束したり承認したりしてはならない。

*失敗*となる条件を具体的に書きましょう。「返答は良かったか？」では何も意味のないスコアになります。上の文なら行動に移せるスコアが得られます。

### Threshold（閾値）

セッションが合格となるスコアの下限値です。`0.7` が妥当な出発点です。0から1の完全なスコアは常に保存されるため、閾値は合否の判定にのみ使われます。分布を確認して調整できます。

### Condition（条件）

他の評価と同じPythonの条件式ですが、ここでは特に重要です。条件を設定しないと、ジャッジは組織の**すべて**のセッションに対してモデル呼び出しごとに実行されます：

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

条件なしでジャッジをデプロイしようとすると、ダッシュボードが警告を表示します。すべてのセッションをジャッジしたい低ボリュームのエージェントであれば問題ありませんが、それは意図的な判断であるべきで、うっかり設定するものではありません。

## ジャッジが見るもの

会話のターン（セッションが長い場合は最新のターンから順に）：

- ユーザーの発言
- アシスタントの返答
- **エージェントが呼び出したすべてのツールと、その呼び出しが返した結果（順序どおり）**

最後の点があるため、「XをYの*前に*実行したか」という問いを適切に問うことができます。失敗したツール呼び出しは失敗として表示されるため、「エラーから適切に回復したか」という問いも有効です。

非常に長いセッションはモデルのコンテキストに収まるよう切り捨てられます。その場合、推論にその旨が明示されます。セッションの一部だけを見た判断が、全体を見た判断として表示されることはありません。

## 結果の読み方

ジャッジは他のスコア付き評価と同様に**スコア**を生成するため、グラフ表示、フィルタリング、アラートのトリガーも同じように機能します。スコアと並んでジャッジの**推論**（見たものを説明する段落）も保存されます。スコアに驚いたときはまずその推論を読んでください。たいていは本当に興味深いセッションか、基準を改善すべきサインかのどちらかです。

明確なケースではスコアは安定していますが、ビット単位で決定論的ではありません。ボーダーラインのスコアは判決としてではなく、セッションを直接読みに行くきっかけとして扱ってください。

## 制限事項

- **テストはまだ利用できません。** ドライランにはセッション割り当てが伴わず、その割り当てがモデル予算の使用を承認するものです。そのため、テスト呼び出しには課金先がありません。狭い条件でデプロイして、最初のいくつかの結果を確認してください。
- **バックフィルは利用できません。** コード評価を何ヶ月もの履歴に対してバックフィルすることは無料ですが、ジャッジで行うと予算全体を数分で使い切ってしまいます。
- **基準を編集すると新しいバージョンが公開されます。** 古いスコアと新しいスコアは比較できないため、1つのトレンドラインに混在させずに別々に保持されます。
- **ジャッジは常にスコアを生成します**。メトリクスやアサーションは生成しません。

## 予算が尽きたとき

ジャッジは組織のモデル予算を消費します。予算が尽きると、ジャッジ評価はサイレントに失敗するのではなく明確な理由とともに停止し、**コード評価は通常どおり継続して実行されます**。予算を追加すれば、次のセッションから再開されます。
