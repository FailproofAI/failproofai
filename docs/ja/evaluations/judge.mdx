ホストされたPython評価は数えて比較することができます。ツール呼び出しの回数、エラーの数、セッションの所要時間などです。しかし、答えが*正しかったか*、返答が失礼だったか、エージェントが行動する前にポリシーを確認したかどうかは判断できません。

**LLMジャッジ**ならそれが可能です。良い状態を平易な言葉で記述すれば、モデルがセッションを読み取り、その理由とともに0から1のスコアを返します。

<Note>
ジャッジは実行するセッションごとにモデル呼び出しが1回発生しますが、コード評価は無料です。会話を*理解する*必要がある質問にのみジャッジを使用してください。また、条件を設定して、実際に問いかけたいセッションにのみ実行されるようにしましょう。
</Note>

## どちらを使うべきか？

| 質問 | 使用するもの |
| --- | --- |
| 同じツールを2回呼び出したか？ | コード |
| エラーはいくつあったか？ | コード |
| セッションは30秒以内だったか？ | コード |
| 顧客は緊急性を表明したか？ | [判定モデル](/ja/evaluations/jev) |
| 顧客はどの程度不満を感じていたか？ | [判定モデル](/ja/evaluations/jev) |
| 答えは実際に正しかったか？ | **ジャッジ** |
| 返答は失礼または素っ気なかったか？ | **ジャッジ** |
| 払い戻しを約束する前に払い戻しポリシーを確認したか？ | **ジャッジ** |

目安となるルール：**数えられるもの → コード、事前に列挙できる回答 → [判定モデル](/ja/evaluations/jev)、説明が必要なもの → ジャッジ**。ジャッジは見たものについて文章で記述するものです。数値だけでは「なぜ？」という疑問が生じる場合に使用してください。

事前に決める必要はありません。測定したいことを記述すれば、failproofが選択し、何を選んだかとその理由を教えてくれます。**スコア方法**で切り替えることもできます。

## 作成方法

1. **analyse → checks → new evaluation** に移動し、**スコア方法**で **llm as judge** を選択します。
2. ジャッジしたい内容を記述します。
3. **review** で、基準（**ジャッジが確認する項目**）、閾値（**これ以上でパス**）、**条件**を確認してからデプロイします。

### 基準

質問形式ではなく要件として書かれた1〜2文：

> アシスタントは、払い戻しポリシーを最初に確認せずに払い戻しを約束または承認してはならない。

何があれば*失敗*になるかを具体的に記述してください。「返答は良かったか？」では意味のない数値しか得られませんが、上の文なら実際に行動に移せる数値が得られます。

### 閾値

セッションがパスするスコアの下限値です。`0.7` が適切な出発点です。0から1の完全なスコアは常に保存されるため、閾値はパス/不合格の判定にのみ使われます。分布を確認して調整することができます。

### 条件

他の評価と同じPython条件ですが、ここではより重要です。条件がない場合、ジャッジは組織内の**すべての**セッションに対して実行され、それぞれにモデル呼び出しが発生します：

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

条件なしでジャッジをデプロイしようとすると、ダッシュボードが警告を表示します。トラフィックが少ないエージェントを完全にジャッジしたい場合は適切なこともありますが、偶然ではなく意図的な決定であるべきです。

## ジャッジが参照するもの

会話のターン（セッションが長い場合は新しいものから順に）：

- ユーザーの発言
- アシスタントの返答
- **エージェントが呼び出したすべてのツールと、その呼び出しが返した結果（順番どおり）**

最後の部分があるからこそ、「XをYの*前*に行ったか」という問いが公平に問えるのです。失敗したツール呼び出しは失敗として表示されるため、「エラーから適切に回復したか」という問いにも使えます。

非常に長いセッションはモデルのコンテキストに収まるよう切り詰められます。その場合、理由の説明に明示的に記載されます。セッションの一部に基づいた判断が、全体に基づいた判断として表示されることはありません。

## 結果の読み方

ジャッジは他のスコア付き評価と同様に**スコア**を生成するため、グラフ表示、フィルタリング、アラートのトリガーも同じように機能します。数値と並んで、ジャッジの**推論**（見たものを説明する文章）も保存されます。スコアに驚いたときはまずそちらを読んでください。本当に興味深いセッションか、基準を改善すべきサインのどちらかであることがほとんどです。

明確なケースではスコアは安定していますが、ビット単位での再現性はありません。境界線上の単一スコアは、判決としてではなく、セッションを実際に読みに行くきっかけとして捉えてください。

## 制限事項

- **テストはまだ利用できません。** ドライランにはセッションの割り当てがなく、その割り当てこそがモデル予算の消費を承認するものです。そのため、テスト呼び出しに課金する対象がありません。狭い条件でデプロイして最初のいくつかの結果を読んでください。
- **バックフィルはモデル予算を消費します。** コード評価のバックフィルは無料ですが、過去のセッションをジャッジでスコアリングするにはセッションごとにモデル呼び出しが発生します。デプロイ後に**過去のセッションのプレビュー**にチェックを入れるか、ページ上で**過去のセッションをスコアリング**を選択してください。不足分の集計は無料で、確認するまでスコアリングは行われません。期間を狭く設定しておきましょう。
- **基準を編集すると新しいバージョンが公開されます。** 古いスコアと新しいスコアは比較できないため、1つのトレンドラインに混在させず、分けて管理されます。
- **ジャッジは常にスコアを生成します。** メトリクスやアサーションは生成しません。

## 予算が尽きたとき

ジャッジは組織のモデル予算を消費します。予算が尽きると、ジャッジ評価はサイレントに失敗するのではなく明確な理由とともに停止し、**コード評価は通常どおり実行され続けます**。予算を増やせば、次のセッションから再開されます。
