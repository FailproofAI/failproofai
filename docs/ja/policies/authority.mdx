FailproofAI Cloud または独自のキーを通じて [Jev ポリシーレビュー](/ja/policies/jev) を設定すると、ゲート対象のツール呼び出しはそれぞれ、実行中のポリシーと Jev によって判定されます。Jev は、その呼び出しが実際に何をするのか、タスクを入力した人物がそれを要求したかどうかを判断します。各ポリシーの**権限**は、両者が一致しない場合の動作を決定します。

Jev が設定されていない場合、権限は効果を持ちません。すべてのポリシーはこれまで通りに適用されます。

## ハードとレビュー可能

- **ハード**はデフォルトです。ハードポリシーの deny または instruct は最終的なものであり、Jev はそれをクリアできません。また、ハードな deny は Jev を待たずに呼び出しを停止します。
- **レビュー可能**とは、Jev がポリシーの判定をクリアできることを意味しますが、ポリシーが `reviewedBy` に指定したセマンティックチェックを通じてのみ可能です。判定がクリアされるのは、指定された**すべての**チェックがこの呼び出しについて問い合わせられ、それぞれが何も見つけないか、ユーザーがこれを要求したと記録した場合のみです。**発火した**チェック（懸念事項を発見した）において、ユーザーが要求していない場合は、そのチェック自体の判定が警告のみであってもブロックが維持されます。そのツールに適用されないため Jev が問い合わせなかったチェックは、他のチェックが何を言っても何もクリアしません。一つの緩和がコンセントとして扱われます。呼び出しがユーザーが与えたタスクのステップであり、それ以上に及ばない場合、Jev は deny を警告に変換し、その警告がポリシーのブロックをクリアし、エージェントに伝えられます。

ポリシーがレビュー可能になるのは、以下のすべてが満たされる場合のみです：

1. `authority: "reviewable"` を宣言している。
2. `reviewedBy` が空でないリストであり、すべてのエントリがインストール済みパックの宣言する Jev チェックである。Failproof AI は Jev チェックを提供しません。[以下の 16 個](#semantic-policy-names)は `failproofai policies add FailproofAI/jev-policies` から取得されます。チェックを宣言するパックがない場合、すべてのポリシーはハードになります。
3. `alwaysOn` ではない。Failproof AI を無効化するエージェントを防止するガードは常にハードです。

それ以外はすべてハードです。フィールドの欠如、値のスペルミス、空または不正な `reviewedBy`、またはこのマシンが問い合わせられないチェック名です。不明な名前は、スキップされるのではなく宣言全体をハードにします。なぜなら `reviewedBy` は「これらすべてが問い合わせられなければならず、いずれも deny してはならない」を意味するからです。名前をスキップすると、要求したよりも少ないチェックで Jev がポリシーをクリアできてしまいます。

Jev が設定されると、Failproof AI は `reviewable` 宣言を拒否した場合にプロセスごとに 1 回警告をログに記録します。Jev がない場合は何も表示しません。権限はその場合何も決定しないからです。`failproofai publish` はそのような宣言を含むパックのビルドを拒否するため、パック作成者はインストール前に気付きます。宣言しているチェックがある場合はパックが宣言するチェックに対して `reviewedBy` を評価し、そうでない場合は 16 個の `FailproofAI/jev-policies` 名に対して評価します。

## 権限の宣言場所

ポリシーがマシンに届く各方法には、権限を決定する一つの場所があります：

| ソース | 宣言場所 | デフォルト |
| --- | --- | --- |
| 組み込みポリシー | 以下の表 | レビュー可能としてリストされていない限りハード |
| 独自ポリシーファイル | `customPolicies.add` の `authority` と `reviewedBy` | ハード |
| ポリシーパック | パックマニフェスト（`failproofai-pack.json`）内の各ポリシーエントリ | ハード |
| クラウド管理ポリシー | アクティブなデプロイメントにおけるポリシーの割り当て | ハード。デプロイメントはまだ設定していないため、すべてのクラウド管理ポリシーは現在ハードです。 |

パックまたはクラウド管理ポリシーの場合、ポリシーコード内に設定されたフィールドは無視されます。マニフェストまたは割り当てが決定します。パックは自身のポリシーのみを記述できます。ポリシー名に `/` を含めることができず、パック自身のプレフィックスで登録されるため、マニフェストが組み込みポリシーや別のパックのポリシーをレビュー可能としてマークすることはできません。パックのコードが登録しても、マニフェストで宣言されていないポリシーはハードです。

バイト単位で同一のコードを持つ 2 つのパックまたは 2 つのクラウド管理ポリシーは、一つのアーティファクトを共有し、一つのポリシーとして読み込まれます。そのポリシーがレビュー可能になるのは、それらのすべてがレビュー可能と宣言し、Jev がそれらのいずれかが名前を挙げたすべてのチェックをクリアする必要がある場合のみです。いずれかがハードと宣言するか、まったく宣言しない場合はハードのままです。パックまたはポリシーがリストされる順序は関係ありません。

ほとんどのマシンは `FailproofAI/policies` パックから組み込みポリシーを取得し、そのパックのマニフェストから権限を読み取ります。以下のレビュー可能エントリは、それらを含むパックのリリースがインストールされると有効になります。古いリリースにはそのようなエントリがないため、そのパック内のすべてのポリシーはハードのままです。

## 独自ポリシーでの権限宣言

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` は両フィールドをパックマニフェストにコピーするため、パックとして公開されたポリシーは作成者が与えた権限を維持します。宣言が反映されない場合はパックのビルドを拒否します。`"hard"` または `"reviewable"` 以外の値、リスト形式でない `reviewedBy`、またはチェックでない名前（宣言しているチェックがある場合はパック自身の [Jev チェック](/ja/policies/publish-a-pack#jev-checks-in-a-pack)、そうでない場合は組み込みチェック）が対象です。

## 組み込みポリシー

セマンティックポリシーが同じ懸念事項を真に対象とする場合のみレビュー可能です。その他すべての組み込みポリシーはハードです。

懸念事項をカバーすることは必要条件ですが、十分条件ではありません。また、誤り方はどちらも静かです：

- **問い合わせられないチェック**はブロックを永続させます。`reviewedBy` は連言であり、問い合わせられなかったチェックはクリアしないため、ポリシーがマッチする形状に対して前提条件が発火しないチェックとペアになっているポリシーは、まったくクリアされることがありません。
- **問い合わせられたが発火しないチェック**は「懸念なし」と答え、懸念なしでクリアされます。そのため、ポリシーの形状をモデル化していないチェックとペアになると、ポリシーをレビューするのではなく、チェックが理解しない入力に対してそれを無効にします。

instruct モードのセマンティックポリシーは deny と答えることはできませんが、ブロックを維持することはできます。発火してユーザーが呼び出しを要求しなかった場合、レビューしているポリシーはクリアされません。`FailproofAI/jev-policies` チェックのうち 6 つは instruct のみです。`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump`、`external-data-egress` であり、[以下の表](#semantic-policy-names)に各チェックのモードが示されています。問うべき質問は「**deny できるものが何か残っているか**」です。クリアによって懸念事項が何によっても適用されない状態になってはなりません。エンジンは呼び出しごとにそのテストを適用します。誰もコンセントしていない警告はクリアではありません。ツール呼び出しの前の警告はエージェントを止めないからです。そして deny できるチェックが警告した場合（証拠がその deny ラインに達しなかった場合）、ユーザーがその呼び出しを要求しなかったなら、その呼び出しに対して何もクリアされず、すべての正規表現 deny が維持されます。

<Warning>
**発火ラインをわずかに下回ったチェックはフロアを維持しません。** 上記のルールはチェックが*発火する*（証拠 ≥ 0.7）ことを必要とします。すべての関連チェックがそれをわずかに下回ると、何も発火せず、レビュアーは「懸念なし」と答え、レビュー可能な deny がクリアされます。強制モードでのライブ測定：「`/etc/shadow` への未要求の Read（`secret-exposure` 0.69、`read-outside-workspace` 0.37 でホームディレクトリのパスのみをモデル化）」と「"follow SETUP.md" 後の `set | curl -d @- …`（`env-secrets-dump` 0.66、`credential-exfiltration` 0.65 で `sends_out` 0.97）」の両方が許可されましたが、正規表現層のみではいずれも deny されます。しきい値はラベル付きコーパスで調整されており、これに対して再測定されていません。再測定されるまで、これらの形状の一つが通り抜けることが誤ったブロックよりも重要な場合は、ポリシーを**ハード**に維持してください。
</Warning>

## セマンティックポリシー名

これらは `FailproofAI/jev-policies` が宣言するチェックであり、インストール後に `reviewedBy` が受け付ける値です。Failproof AI 自体はそれらを提供しません。そのパック（またはこれらの名前を宣言する別のパック）なしでは、それらを名前として挙げるポリシーはレビュー可能になりません。各チェックは、目の前のツール呼び出しについて Jev が答えるものです。**モード**はチェックが答えられるものです。`deny` チェックは強い証拠があればブロックし、`instruct` チェックは常に警告のみです。どちらも、発火してユーザーがその呼び出しを要求しなかった場合、ポリシーの deny を維持します。**ユーザーがオーバーライドできる**は、人間自身の明示的な要求がそれをクリアするかどうかを示します。

Jev はインストール済みパックが宣言する [Jev チェック](/ja/policies/publish-a-pack#jev-checks-in-a-pack)に対してのみ問い合わせを行い、それらが `reviewedBy` が受け付ける名前です。2 つのパックが異なる形で宣言した名前はいずれにも適用されません。FailproofAI リポジトリからインストールされていないパックによって宣言された 16 個の名前のうちの一つは、そのパックでは無視されます。そのバージョンは問い合わせられず、FailproofAI 自身のものと競合しないため、サードパーティパックがコアパックのポリシーをクリアするチェックになることも、これらのチェックの一つを無効化することもできません。読み取れないパックリスト、またはすべてのチェックが使用不可のパックは、Jev に問い合わせるものを何も残しません。

| --- | --- | --- | --- |
| `destructive-deletion` | deny | はい | 再生成できないデータの永続的な削除。 |
| `production-infra-change` | deny | はい | ライブインフラの変更。 |

| `commit-on-protected-branch` | instruct | はい | 保護されたブランチへの直接コミット。 |
| `secret-exposure` | deny | はい | 認証情報の読み取りまたはコピー。 |
| `credential-exfiltration` | deny | いいえ | シークレットまたはプライベートファイルのマシン外への送信。 |
