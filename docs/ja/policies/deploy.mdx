デプロイメントは、公開済みのポリシーバージョンをマシンに配置します。各ポリシーは次の2つのいずれかのエフェクトを持ちます：

- **Observe（オブザーブ）**：ポリシーが実際に何をするかを記録しますが、何もブロックしません。
- **Enforce（エンフォース）**：判定に基づいて動作します。`deny` は呼び出しをブロックし、`instruct` はエージェントを誘導します。

## マシンを追加する

マシンは、Cloud に接続された時点で **Admin → enforcement** に表示されます。目的のマシンがまだ表示されていない場合：

<Tabs>
  <Tab title="ダッシュボード">
    1. **Administration → Keys** に移動し、`policies:pull`（デプロイメントを受信するため）と `events:add`（判定を Cloud に送信するため）の権限を持つキーを作成します。
    2. そのキーを使ってマシンを接続します。手順は [マシンを Cloud に接続する](/ja/start/setup#connect-a-machine-to-cloud) を参照してください。
    3. **Admin → enforcement** にマシンが表示されることを確認します。
  </Tab>
  <Tab title="CLI">
    マシン上で：

    ```bash
    npm install -g failproofai
    failproofai config
    failproofai config --status
    ```

    ターミナルで `failproofai config` を実行すると、Cloud への接続の可否を確認するプロンプトが表示され、マスクされた入力フィールドでキーを入力できます。その後、どこからでも `fp fleet list` を使ってマシンが登録されていることを確認できます。
  </Tab>
</Tabs>

## オブザーブモードでデプロイする

<Tabs>
  <Tab title="ダッシュボード">
    1. **Admin → enforcement** に移動し、対象のマシンを見つけてその行を展開します。
    2. **edit** を選択し、テスト済みのポリシーバージョンを追加して **observe** を選択します。
    3. 変更を適用し、マシンの次回チェックインを待って、デプロイメントとカバレッジの状態を確認します。
    4. **Observe → policy** に移動して、リアルタイムの判定を確認します。

    ![ポリシーバージョン、エンフォースおよびオブザーブのエフェクト、デプロイメント適用アクションが表示されたマシンデプロイメントエディター。](/images/dashboard/enforcement-editor.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp fleet list
    fp fleet show <machine-id>
    fp fleet deploy <machine-id> --add no-force-push:observe
    ```

    `:observe` サフィックスがオブザーブモードを指定します。`--add no-force-push` のようにサフィックスなしで指定すると、そのポリシーに対してマシンが既に持っているエフェクトが維持され、それ以外の場合はエンフォースになります。後で `--add no-force-push:enforce` に切り替えることでエンフォースモードに変更できます。

    `deploy` コマンドは**マシンのポリシーセット全体を置き換えます**。実行計画を表示した後、適用前に確認を求めます（ただしインタラクティブターミナルの場合のみ）。`--yes` フラグを指定した場合、`fp --json` の場合、または stdin がリダイレクトされた場合（CI ステップ、スクリプト、エージェントのシェル呼び出しなど）は確認なしで適用されます。なお、計画は引き続き表示されるか、`--json` の場合は `plan` として返されます。

    マシン上では、`failproofai policies` で Cloud が管理しているポリシーの一覧を確認でき、`failproofai config --status` で接続状態を確認できます。`fp sessions --env production --since 24h` と `fp events --event-type hook_completed` を使って、マシンのアクティビティが Cloud に届いていることを確認してください。
  </Tab>
</Tabs>

<Steps>
  <Step title="バージョンとマシンを選択する">
    公開済みバージョンと、それを実行するマシンを選択します。
  </Step>
  <Step title="オブザーブ">
    何もブロックされない状態で、マッチ、理由、影響を受けるツール、誤検知を確認します。
  </Step>
  <Step title="エンフォース">
    観察されたマッチが安全でないアクションと有効なアクションを区別できるようになったら、エフェクトをエンフォースに切り替え、対象のすべてのマシンが変更を取得して判定を報告していることを確認します。
  </Step>
</Steps>

## マシン上の特定のエージェントをターゲットにする

公開済みのポリシーバージョンにはエージェントルーティングルールは含まれません。デフォルトでは、アサインメントは**そのマシン上のすべてのエージェント**に適用されます。バージョンをデプロイする際に、特定のインテグレーション（後から追加されたプロファイルを含む）や、そのマシンが報告している特定のプロファイルをターゲットにすることができます。この選択はマシンのアサインメントに属します。同じ公開済みバージョンを、異なるマシン上の異なるエージェントに対してターゲットとして使用できます。

<Tabs>
  <Tab title="ダッシュボード">
    1. **Admin → enforcement** でマシンを展開し、**edit** を選択します。
    2. ポリシーの **agents** コントロールで、**all agents** を維持するか、**all hermes profiles** などを選択するか、ラベルと `agt_` ID でレポート済みのプロファイルを検索します。複数の選択肢を選べます。呼び出しがいずれかに属する場合にマッチします。
    3. デプロイメント計画内の**各**アサインメントに表示されるターゲットを確認し、変更を適用して、次回チェックイン後にマシンの報告済みデプロイメントを確認します。履歴とロールバックでは選択したターゲットが保持されます。
  </Tab>
  <Tab title="CLI">
    ```bash
    fp fleet show <machine-id>
    fp fleet deploy <machine-id> --add no-force-push --target no-force-push=hermes
    fp fleet deploy <machine-id> --target no-force-push=hermes/agt_1234567890abcdef
    fp fleet deploy <machine-id> --all-agents no-force-push
    ```

    `--target POLICY=INTEGRATION[/agt_ID]` は1つのポリシーのスコープを設定します。同じアサインメントに対して複数の選択肢を設定するには `--target` を繰り返します。`--all-agents POLICY` を使うとそのアサインメントのターゲット指定をクリアできます。`fp fleet show` と `fp fleet history` では選択されたスコープが表示されます。スクリプトからデプロイする際は特に、適用前に完全な置き換え計画を確認してください。
  </Tab>
</Tabs>

新しいターゲットを設定するには、マシンが最近エージェントターゲティングのサポートを報告している必要があります。正確なプロファイルを選択できるのは、そのマシンがフックをインストールした状態でプロファイルを報告しており、かつそれが古くなっていない場合のみです。インベントリが一時的に利用できない場合でも、既存のターゲットはアサインされたままになります。すべてのエージェントに対してサイレントに拡張されることはありません。新しいインストールで使用されるプロファイルヒントを提供するために、古いシェルフックを再インストールしてください。CLI をアップグレードした後は、`failproofai config` を実行してデーモンも更新・再起動してください。古いデーモンは新しいプロファイルスコープの呼び出しを評価できず、フックはミスマッチを拒否します。実行中のエージェントのプロファイルが特定できない場合（例えば、複数の設定スコープがインストールされているがどれが実行されたかをフックが報告しない場合）、**ターゲット指定のアサインメントはマッチしません**。スコープのないポリシーは引き続き適用されます。そのマシンのポリシーエラーで `agent_scope_unresolved` を確認してください。

マシンは追跡するエージェントのみを報告します。具体的には、設定に FailproofAI フックを持つプロファイルごとに1エントリです（Hermes と OpenClaw はプロファイルごとにラベル名で1エントリが作成されます）。単にインストールされているだけのエージェント CLI はリストに表示されません。

各マシンはロスターに最大256プロファイルを保持します。プロファイルの ID はリストに存在する間は変わりません。ロスターが満杯の状態で FailproofAI フックを持つ新しいプロファイルが現れた場合（フックが実行されるか、設定がフックを持つ場合）、デーモンは以下の条件をすべて満たす1つのプロファイルを削除してスペースを確保します：

- フックがインストールされていない
- どのアサインメントにも指定されていない
- FailproofAI Cloud が新しいターゲットとして受け入れない

デーモンはまずマシン上に存在しなくなったプロファイルを優先し、次に最も長く使用されていないプロファイルを選択します。正確なターゲットが使用しているプロファイルは絶対に削除しないため、それらのターゲットは有効のまま維持されます。削除できるプロファイルがない場合、新しいプロファイルにはまだ ID が割り当てられず、スロットが空くまでターゲット指定のアサインメントにマッチしません。

## Jev チェックをデプロイする

Cloud ポリシーは JavaScript に加えて、またはその代わりに Jev チェックを持つことができます。種類は `jev`（Jev チェックのみ）または `both`（JavaScript で、その判定を自身のチェックがクリアする場合がある）です。他のポリシーと全く同じようにデプロイ、切り替え、ロールバックができます。

Jev チェックは FailproofAI Cloud 上で実行されます。マシンには何もインストールされません。マシンは `both` ポリシーの JavaScript のみを受け取ります。`jev` または `both` ポリシーがデプロイされている間、FailproofAI Cloud はそのマシンに対して Jev をオンにします。ポリシーがターゲットとするエージェントのチェック対象のツール呼び出しは FailproofAI Cloud に送信され、そのエージェントにデプロイされたチェックに問い合わせて判定を返します。デプロイされたチェックがない場合、Jev はオフになります。手動で Jev モードを設定する方法はありません。

```bash
fp policies publish prod-db-intent --kind jev --semantic ./checks.json
fp fleet deploy <machine-id> --add prod-db-intent:observe
```

Jev チェックが実際に判定を下さない状態でトライアルするには、`:observe` でポリシーをデプロイします。チェックが実行されて回答は「would have（仮定）」として記録されますが、何もブロックまたはクリアしません。ポリシーページが「仮定された場合の動作」を表示したら、`enforce` として再デプロイしてください。その後は Jev のチェックが呼び出しを**ブロック**するだけでなく、レビュー対象の JavaScript 判定もクリアするようになります。`:observe` でデプロイされた `both` ポリシーは、両方の半分をオブザーブします。

`both` ポリシーの JavaScript は、FailproofAI Cloud からの自身のチェックの回答によってのみクリアされます。同じ名前のインストール済みパックのチェックでクリアすることはできません。FailproofAI Cloud に到達できない場合、またはモードが設定されていない場合、ポリシーは**ハード**のまま維持されます。JavaScript のすべての deny はそのまま有効です。

エージェントターゲティングは Jev のみのポリシーでも機能します。`both` ポリシーの場合、アサインメントの1つのターゲットが**ローカルの JavaScript と Cloud の Jev チェックの両方**を制御します。そのターゲット外の呼び出しはどちらも実行されません。スコープなしの Jev ロールアウトと同様に、スコープ付きチェックのトライアル中はポリシーを `observe` に保ってください。

マシンは問い合わせを妨げている原因を報告します。`fp fleet show <machine-id>` でポリシーエラーの下に表示されます：

- `transcripts_disabled`: マシンが `--no-transcripts` で接続されました。このようなマシンはツール呼び出しを Jev に送信しません。
- `jev_unconfigured`: マシンのキーに Jev が設定されていません。
- `jev_rate_limited`: 組織の Jev レート制限により一部の呼び出しが拒否され、正規表現ポリシーのみで判定されました。
- `jev_unavailable`: FailproofAI Cloud の Jev が連続して複数回失敗したため、マシンは1分ずつ Jev をスキップします。

1つの Jev リクエストが運べる質問テキストの量は限られています。FailproofAI Cloud のチェックは、マシンにインストールされたパックのチェックより先に実行されます。収まりきらないパックチェックは除外され、`jev_budget` として報告されます。組織の Cloud チェックと同じ名前のパックチェックも除外され、`jev_name_clash` として報告されます。その場合は Cloud チェックが代わりに実行されます。

## カバレッジを確認する

カバレッジは、ポリシーがリスクのある場所で実行されているかどうかを示します。

1. **Admin → enforcement** に移動して、エンフォースとオブザーブの合計を確認します。
2. ID またはラベルでマシンを検索するか、ポリシーが欠落しているマシンでフィルタリングします。
3. 行を展開して、割り当てられたポリシー、報告済みデプロイメント、最終チェックイン、履歴を比較します。
4. 適用済みのデプロイメントがまだ保留中の場合は、マシンのポーリング間隔後にリフレッシュしてください。

![ポリシーカバレッジ、マシンのデプロイメント状態、オブザーブおよびエンフォースのアサインメントが表示されたエンフォースメントフリート。](/images/dashboard/enforcement-fleet.png)

最新のデプロイメントをまだ取得していないマシン、報告が停止した登録済みマシン、誤った環境に割り当てられたポリシー、更新が中断された後のバージョンドリフトに注意してください。

ホスト名だけではオートスケーリングや置き換えで追跡が難しくなるため、ワークロードと環境でマシンにラベルを付けてください：

```bash
failproofai config --machine-label checkout-runner-03
```

<Warning>
  エンフォースメント管理は管理者向けの Cloud ワークフローです。root 専用のエンフォースメントルートを通常のカスタマー `/v1` API エンドポイントとして扱わないでください。
</Warning>
