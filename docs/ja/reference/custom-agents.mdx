Python 3.11 以降。ランタイム依存なし。フレームワークをお使いの場合は、[LangChain、CrewAI、LlamaIndex、Pydantic AI](/ja/start/integrations) が1回の呼び出しで自動インストルメントされます。

<Note>
  **TypeScript SDK** も用意されており、両者は同じスプールに同じイベントを書き込みます。Node エージェントと Python エージェントが混在するフリートでも、セッションのセットは2つに分かれず1つになります。サービスごとに選択してください。会社全体で統一する必要はありません。
</Note>

## インストール

```bash
pip install failproofai-sdk
```

パッケージは `failproofai-sdk` としてインストールされ、Python では `failproofai_sdk` としてインポートします。`failproofai-sdk[langgraph]` のようなフレームワーク追加パッケージはフレームワーク本体もインストールしますが、アダプターは常にベースのホイールに含まれています。

## Failproof デーモンへの接続

<Tabs>
  <Tab title="ダッシュボード">
    1. **Admin → Keys** に移動し、`events:add` 権限を持つキーを作成します。
    2. エージェントマシン上で [Failproof デーモンを Cloud に接続](/ja/start/setup#connect-a-machine-to-cloud) します。
    3. インストルメントされたセッションを1回実行し、**Observe → Events** で正確なIDを確認します。
    4. **Observe → Sessions** に移動し、同じ環境を選択して、再構築されたトレースを開きます。

    ![カスタム Python エージェントのセッションが実行グラフと順序付きイベントトレースとして再構築された様子。](/images/dashboard/session-detail.png)
  </Tab>
  <Tab title="CLI">
    `events:add` キーをシェルに読み込みます。`read -s` を使えばエコーなしのプロンプトで入力できるため、コマンドやシェル履歴に残りません。

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    その後、マシンをセットアップして接続を確認します。

    ```bash
    failproofai config
    failproofai config --status
    ```

## 設定

### OpenTelemetry スパン（オプトイン）

`opentelemetry-sdk` を別途インストールし、オプションのエクスポーターをアタッチします。

```python
import failproofai_sdk
from opentelemetry.sdk.trace import TracerProvider

provider = TracerProvider()
failproofai_sdk.instrument("otel", provider=provider)
with provider.get_tracer("my-agent").start_as_current_span(
    "agent", attributes={"gen_ai.operation.name": "invoke_agent"}
):
    pass
provider.force_flush()
```

`provider` を省略すると、登録済みのプロバイダーが使用されます。登録されていない場合のみ新規作成されます。`failproofai_sdk.OtelSpanExporter()` を独自のスパンプロセッサーに直接渡すこともできます。他のエクスポーターはそのまま動作します。

エクスポートの配信は接続済みの FailproofAI デーモンが行います。SDK はネットワーク設定、キー、ローカルリスナーを必要としません。管理者が [OpenTelemetry インジェスト](/ja/agenteye/opentelemetry) を有効化する必要があります。`instrument()` を引数なしで呼び出しても OTEL は有効になりません。`uninstrument("otel")` は自身のプロセッサーのみを無効化します。コンテンツキャプチャの制御はご自身のインストルメントで行います。終了前にプロバイダーをフラッシュしてください。SDK はランタイム依存なしのポリシーを維持しており、OpenTelemetry はリクエスト時のみインポートされます。

```python
import failproofai_sdk

failproofai_sdk.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| 引数 | 説明 |
| --- | --- |
| `environment` | すべてのイベントに付くラベル（`production`、`staging`、`prod-eu` など）。デフォルトは `dev`。 |
| `flush_interval` | バックグラウンドスレッドがディスクに書き込む間隔（秒）。デフォルトは `0.5`。 |
| `base_dir` | 書き込み先。デフォルトはデーモンのスプールで、特別な理由がない限りこのままで問題ありません。 |

環境変数で設定することも可能です。

| 変数 | 説明 |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | コード変更なしで `environment` を設定できます。ラベルがアプリではなくデプロイ環境に属する場合に便利です。`configure()` の引数が優先されます。 |
| `FAILPROOFAI_HOME` | スプールを格納する Failproof AI ルートディレクトリを変更します。 |
| `FAILPROOFAI_SDK_STRICT` | `1` にするとインストルメントエラーが例外として発生します（デフォルトはログ出力のみ）。 |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | `1` にするとフレームワーク互換性の問題が例外として発生します（デフォルトは警告を出して続行）。 |

<Warning>
  **`environment` にカンマを含めないでください。** インジェスト処理はこのフィールドをカンマで分割してフィルターを構築するため、カンマを含むラベルのイベントはすべて無音で破棄されます。`prod,eu` ではなく `prod-eu` と書いてください。

  `configure(environment="prod,eu")` は即座に例外を発生させるため、すぐに気づけます。一方、`AGENTEYE_ENVIRONMENT` は呼び出し元がないため例外を発生させることができず、1度だけ警告を出して `dev` にフォールバックします。
</Warning>

イベントはメモリ上のキューに蓄積され、`flush_interval` 秒ごとにバックグラウンドで書き込まれます。インタープリター終了時に最後のフラッシュが行われます。プロセスが強制終了された場合、未書き込みのデータは失われます。

## 識別子

すべてのイベントはセッションとエージェントに属します。**スコープが両方を自動的に補完する**ため、通常は明示的に渡す必要はありません。

```python
with failproofai_sdk.session():
    with failproofai_sdk.agent("planner"):
        failproofai_sdk.event.tool_use(tool_name="search", tool_call_id="c1")
```

`session_id` や `agent_id` を明示的に渡すことも可能で、その場合は明示した値が優先されます。スコープが設定されておらず引数も渡されていない場合、Cloud が静かに破棄するイベントを送信するのではなく、`TypeError` が発生します。

<Note>
  識別子はコンテキスト変数で伝達されます。`asyncio` タスクには自動的に引き継がれますが、**新しいスレッドには引き継がれません**。ワーカーを `failproofai_sdk.propagate()` でラップしないと、そのスレッドのイベントは未紐付けになります。
</Note>

## イベントカタログ

15 個のメソッド。ほとんどは**ペア**になっており、開始側を呼び出した後に終了側を呼び出すと、SDK が経過時間を計測します。

| | 開始 | 終了 |
| --- | --- | --- |
| **エージェント** | `agent_start` | `agent_end` |
| | `agent_pause` | `agent_resume` |
| **モデル** | `model_request` | `model_response` |
| **ツール** | `tool_use` | `tool_result` |
| **フック** | `hook_triggered` | `hook_completed` |
| **人間** | `human_wait` | `human_input` |

独立して使用するメソッドは3つ: `error`、`human_pause`、`human_interrupt`。

<Accordion title="メソッドごとの全フィールド" icon="table">

すべてのメソッドは `session_id` と `agent_id` も受け取りますが、スコープが自動的に補完します。`None` のままのフィールドは JSON の `null` として送信されるのではなく、省略されます。すべてのメソッドは `None` を返します。

| メソッド | 必須 | オプション |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools`, `request_id` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role`, `request_id`, `duration_ms` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

</Accordion>

<Warning>
  実行を失敗としてマークするには、`outcome` が `failed`、`error`、`timeout`、`rejected` のいずれかである必要があります。それ以外の値（惜しいところで `"failure"` も含む）はすべて成功として扱われます。
</Warning>

## ペアリングと経過時間

**ルールは1つ: 終了イベントには開始イベントと同じ ID を渡してください。** これがペアリングの根拠であり、SDK が経過時間を計測できる仕組みです。

| ペア | 対応フィールド |
| --- | --- |
| `tool_use` → `tool_result` | `tool_call_id` |
| `hook_triggered` → `hook_completed` | `hook_id` |
| `agent_pause` → `agent_resume` | `pause_id` |
| `human_wait` → `human_input` | `input_id` |
| `model_request` → `model_response` | `request_id` |

**`duration_ms` を自分で渡さないでください。** SDK が計測するため、渡すと `ValueError` が発生します。

唯一の例外は `model_response` で、実際のプロバイダーレイテンシーを知っているのはご自身のみです。ミリ秒の整数値を渡してください。浮動小数点数は、このカラムが 32 ビット整数であるため空になってしまうことから、例外が発生します。

<Accordion title="エッジケース" icon="circle-help">

- **ID はペアの種類とセッションごとにユニークであれば十分です。** ツールコールとフックが同じ ID を共有しても問題ありません。同時に実行中の2つのセッションも、同じ ID を再利用しても衝突しません。
- **エージェントにスコープされません。** あるエージェントで開始され、別のエージェントで終了したペアでも正しくマッチングされます。マルチエージェントコードでは通常このパターンになります。
- **`request_id` はオプションですが、指定を推奨します。** 指定がない場合、モデルイベントは到着順にペアリングされるため、同じエージェント内で2つの呼び出しが並行すると誤ったペアリングが起きる可能性があります。
- **プロセスをまたぐペア**は Cloud でもマッチングされますが、SDK はどちらのプロセスも両方のハーフを見ていないため、経過時間を計測できません。
- **開始イベントの待機数は最大 10,000 件です。** それを超えると最も古いものが破棄されるため、リークが際限なく膨らむことはありません。

</Accordion>

## 独自フィールド

渡した追加のキーワードはイベントと一緒に保存されます。

```python
failproofai_sdk.event.tool_use(
    tool_name="search", tool_call_id="c1",
    fw_tenant="acme", fw_region="eu-west-1",     # your own
)
```

後でクエリしたい場合は JSON 型を使用してください。それ以外の型（UUID、datetime、`Decimal`、set、bytes、モデルオブジェクトなど）は文字列として保存されます。

<Warning>
  **フィールド名にプレフィックスを付けてください。** 追加フィールドは最後に適用されるため、`model`、`tool_name`、`outcome` といった名前のフィールドは実際の値を静かに上書きしてしまいます。フレームワークアダプターは `fw_` を使用しています。同じ規則に従えば衝突は起きません。

  これはまた、スペルミスのあるオプションフィールドがエラーにならず、単に新しいカスタムフィールドになる理由でもあります。Cloud で標準フィールドが表示されない場合は、まずスペルを確認してください。
</Warning>

以下の5つの名前は予約済みで、使用すると拒否されます: `timestamp`、`session_id`、`agent_id`、`type`、`environment`。

## デリバリーと確認

<Tabs>
  <Tab title="ダッシュボード">
    **Observe → Events** で、`agent_start` が最初に存在し `agent_end` が最後に存在することを確認します。次に **Observe → Sessions** を開き、モデル・ツール・人間・フック・エラーのイベントが意図した順序で表示されていることを確認します。トラブルシューティングの主キーとしてセッション ID を使用してください。
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

Cloud が空の場合は `$FAILPROOFAI_HOME/custom-agents/events` を、それ以外は `~/.failproofai/custom-agents/events` を確認してください。JSONL ファイルが存在すれば SDK によるイベント送信は行われています。スプールが増え続けている場合はデーモンの設定またはデリバリーの問題、スプールが空の場合はインストルメントまたはプロセスのライフタイムの問題を示します。

<Note>
  スプールを確認するのは、デーモンが停止しているときのみにしてください。デーモンが稼働中は、各バッチを数ミリ秒以内に収集・削除するため、ディレクトリ一覧がコレクターと競合し、実際に送信されたイベント数よりはるかに少ない数しか表示されません。
</Note>

## カスタムランタイムでの障害防止

監査の所見とリンクされたトレースを使って、安全でないアクション、必要なエビデンス、および意図した応答を定義します。カスタムエンフォースメントインテグレーションは、実行前にアクションを公開し、構造化された入力をポリシーエンジンに渡し、返された allow、instruct、または deny の判断を適用する必要があります。

[Failproof AI にお問い合わせ](mailto:support@befailproof.ai) いただければ、ランタイムのモデル・ツール・ライフサイクル境界をポリシーフックにマッピングするお手伝いをし、インテグレーションの検証もご一緒に行います。
