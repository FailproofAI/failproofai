ハーネスとは、エージェントが実際に動作する環境のことです。Failproof AI は2つのクラスで合計12種類をサポートしています。

- **コーディング CLI**（10種）— Claude Code、Codex、GitHub Copilot CLI、Cursor、OpenCode、Pi、Factory Droid、Devin CLI、Antigravity CLI、Goose
- **チャット・アシスタントゲートウェイ**（2種）— Hermes（Slack、Telegram、cron）、OpenClaw（セルフホスト型アシスタント）

どのハーネスでエージェントが動作していても、同じポリシーと同じセッション履歴が適用されます。各ハーネスのネイティブなイベント名、ツール名、ツール入力フィールドを29個の正規イベントにマッピングするアダプターレイヤーが、ポリシーの実行前に処理を行います。

12種類のどれにも該当しないハーネスでエージェントを動作させる場合は、[Python SDK](/ja/reference/custom-agents) を使用して直接インストルメント化します。これは異なる契約であることを明確に述べておきます。SDK はトレーシング、セッション、評価、監査を提供しますが、**それ自体ではポリシーを適用しません。** 安全でないアクションを実行前にブロックするには、ランタイムのツール境界に強制フックが必要です。[お問い合わせ](mailto:support@befailproof.ai)いただければマッピングいたします。

| ハーネス | サポートされているフックスコープ |
| --- | --- |
| Claude Code | ユーザー、プロジェクト、ローカル |
| Codex、GitHub Copilot CLI、Cursor、OpenCode、Pi | ユーザー、プロジェクト |
| Factory Droid、Devin CLI、Antigravity CLI、Goose | ユーザー、プロジェクト |
| Hermes、OpenClaw | ユーザー |

各インテグレーションは、ポリシーが実行される前に、ネイティブのフックイベント名、ツール名、ツール入力フィールドを正規化します。ポリシーが動作できるのはそのハーネスが公開しているイベントのみです。ターン終了時や指示の動作については、実際にデプロイするハーネスとバージョンでテストしてください。

## 適用能力

「ブロック」とは、現在のアダプターが返した判定が対象のハーネスによって処理されることを意味します。ツール実行後のブロックはモデルに表示される結果を置き換えることができますが、すでに発生したツールの副作用を元に戻すことはできません。

| ハーネス | 検証済みのブロックイベント | 観察のみ、または非ブロックの注意事項 |
| --- | --- | --- |
| Claude Code | `PreToolUse`、`UserPromptSubmit`、`PermissionRequest`、`Stop`、`SubagentStop`、`PreCompact`、およびいくつかのタスク/設定イベント | `PostToolUse`、セッションライフサイクル、通知、および失敗後イベントは観察的です。 |
| Codex | `PreToolUse`、`PermissionRequest`、`UserPromptSubmit`、`Stop`、`SubagentStop`、`PostToolUse` | ツール実行後のブロックは実行後に結果を置き換えます。セッション開始とコンパクトイベントは現在のアダプターでは観察的です。 |
| GitHub Copilot CLI | `PreToolUse`、`UserPromptSubmit`、`PermissionRequest`、`Stop`、`SubagentStop`、`PostToolUse` | ツール実行後のブロックは実行後に結果を置き換えます。セッションおよび通知イベントは観察的です。 |
| Cursor | `PreToolUse`、`UserPromptSubmit`、`Stop` | `PostToolUse` とセッションイベントは観察的です。 |
| OpenCode | `PreToolUse` | ツール実行後とライフサイクルイベントは観察的です。現在の停止処理は、検証済みのゲートではなく、後のターンへのガイダンスです。 |
| Pi | `PreToolUse`、`UserPromptSubmit` | ツール実行後とライフサイクルイベントは観察的です。停止ガイダンスは後のターンに適用されます。 |
| Hermes | `PreToolUse` | `deny()` はブロックします。`instruct()` は呼び出しを止めません。呼び出しは実行され、ガイダンスはその結果の先頭に配置されます。ツール実行後、セッション、サブエージェント停止の判定はゲートではありません。 |
| OpenClaw | `PreToolUse`、`UserPromptSubmit`、`Stop` | ツール実行後、セッション、サブエージェント停止、コンパクションイベントは観察的です。 |
| Factory Droid | `PreToolUse`、`UserPromptSubmit`、`Stop`、`PreCompact` | ツール実行後とサブエージェント停止の判定は観察的です。 |
| Devin CLI | `PreToolUse`、`UserPromptSubmit`、`Stop`、条件付き `PermissionRequest` | パーミッションフックはすべてのパーミッションモードで実行されるわけではありません。ツール実行後とセッションイベントは観察的です。 |
| Antigravity CLI | `PreToolUse`、`Stop` | ユーザープロンプトとツール実行後の判定は観察的です。プロンプト指示は引き続き注入できます。 |
| Goose | `PreToolUse` | ユーザープロンプト、ツール実行後、セッションイベントは観察的です。ネイティブのブロッキング停止フックは上流に存在しますが、現在のアダプターではインストールされていません。 |

機能はバージョンによって異なります。エージェント CLI をアップグレードした後、特にポリシーが共通のプリツールゲートではなく、プロンプト、停止、パーミッション、またはツール実行後の動作に依存している場合は、必ず再テストしてください。

### Hermes ネイティブプラグイン

Hermes はシェルコマンドではなく、プロファイルローカルのネイティブプラグインを通じて統合されます。インストール時に、すべてのデフォルトおよび名前付き Hermes プロファイルの `plugins/failproofai` を npm パッケージに同梱されたプラグインにリンクし（シンボリックリンクが作成できない場合はコピー）、そのプロファイルの `config.yaml` で有効にして、レガシーの FailproofAI シェルフックエントリのみを移行します。プラグインはリンクされているため、`npm install -g failproofai@latest` を実行するだけで再インストールなしに更新されます。これにより、各フックでのプロセス生成を回避します。このプラグインは Hermes 0.20.0 以降をサポートしています。

レガシーシェルフック（1.0.5 以前でインストールされたもの）は Hermes の cron ジョブをチェック**しません**。各 cron 実行は独自のフックスコープを構築し、ネイティブプラグインはそれに参加しますが、`config.yaml` のシェルフックは参加しません。`failproofai update` は、すでに FailproofAI を使用しているすべてのプロファイルをリンクされたプラグインに移行します。実行中のデーモンがプラグインを提供できない場合、`update` はシェルフックをそのままにして非ゼロで終了します。`failproofai config` でデーモンを更新してから、`failproofai update` を再実行してください。cron ジョブは次回の実行時にプラグインをロードします。実行中のゲートウェイとインタラクティブセッションを再起動してプラグインをロードしてください。

Hermes では、`deny()` は呼び出しをブロックし、`instruct()` はブロックしません。呼び出しは実行され、ガイダンスはその結果の先頭に配置されます。JSON 結果の場合は最初のキー `failproof_policy_reminder` として、またはプレフィックス行 `[FailproofAI policy reminder (...)]` として配置されるため、モデルは出力と一緒にそれを読み取り、結果を解析するスクリプトも引き続き動作します。ポリシーのリマインダーはターンごとに1回表示され、大きな結果では短く保たれます。アクションを絶対に実行させたくない場合は `deny()` を使用してください。`instruct()` はアクションを最初に停止しなくなりました。`execute_code` スクリプトから行われたツール呼び出しは、モデルが読む `execute_code` の結果にリマインダーを配置します。スクリプト自体の結果のコピーはそのままです。モデルはリマインダーを返答で引用しないように指示されています。

プラグインミドルウェアのない Hermes ビルドは、一致する呼び出しを「FailproofAI policy guidance」で一度保留することにフォールバックします。次のモデル応答はそれを繰り返すか、別のツールで同じ作業を行う可能性があり、再び保留されることはありません。

ツール名は Hermes バージョン間で照合されます。`process_manage`、`cronjob_manage`、`todo_list`（Hermes 0.21）は `process`、`cronjob`、`todo`（Hermes 0.20）と同様に扱われます。Hermes がプラグインをロードするたびに、プロファイルの `plugin-data/agent-plugin-failproofai-5296f299/` ディレクトリに `heartbeat.json` が書き込まれ、Hermes のバージョン、プラグインのパスとバージョン、Hermes が受け付けたフックが記録されます。`failproofai config --status` を実行して、無効化、不完全、重複、または新たに未設定のプロファイル、あるいはレガシーシェルフックのままのプロファイル（「Hermes cron jobs are not checked」と報告される）を検出できます。

### OpenClaw プラグイン

OpenClaw は FailproofAI をインプロセスゲートウェイプラグインとしてロードし、すべてのプロファイルの `openclaw.json` に登録されます。Hermes プラグインと同様に、ソケット経由でローカルの `failproofaid` デーモンに各判定を問い合わせるため、実行中のデーモンが必要です。デーモンがない場合はインストールが拒否され、デーモンが応答できない場合はツール呼び出しとプロンプトがブロックされ、その理由がゲートウェイログに書き込まれます。`npm install -g failproofai@latest` の後、OpenClaw ゲートウェイを再起動して更新されたプラグインをロードしてください。

### Codex フック信頼性

Codex 0.129 以降では、`~/.codex/hooks.json` のフックはインタラクティブな `codex`（「Review hooks」）で承認した後にのみ実行されます。承認前は、ヘッドレスの `codex exec` を含むすべての Codex セッションでスキップされます。Codex のシステム設定ファイル（Linux および macOS では `/etc/codex/config.toml`）のフックはその承認なしに実行されます。

そのため、`failproofai config`（またはユーザースコープでの `policies --install --cli codex`）が sudo を使用できる場合、`# >>> failproofai managed hooks >>>` と `# <<< failproofai managed hooks <<<` の間に Codex フックを `/etc/codex/config.toml` に書き込み、ファイルの残りの部分はそのままにします。

このファイルはマシン上のすべてのアカウントに適用されるため、その中の各フックは `/opt/failproofai-codex/codex-hook`（root が所有する短いスクリプト）を実行します。このスクリプトは、フックをそこに設定した各アカウントのために、そのアカウント自身の failproofai にイベントを渡し、他のアカウントに対しては何もしません。failproofai の Codex フックを必要とする別のアカウントは、自分自身のためにセットアップします。

ブロックの書き込み前、および `failproofai update` のたびに、failproofai は `/etc/codex/config.toml` 自体、スクリプト、それらの上位のすべてのディレクトリ、および実行する `sh`、`id`、`cat` が root に属し、他の誰も書き込めないこと、各アカウントの failproofai がそのアカウントまたは root に属することを確認します。インストール時にこのチェックが失敗した場合、フックは `~/.codex/hooks.json` に保持されます。更新時にチェックが失敗したスクリプトはブロックから削除され、failproofai のチェックが失敗したアカウントはスクリプトから削除されます。修正後に `failproofai config` を再実行してください。`failproofai update` は、以前のバージョンで書き込まれたブロックをスクリプトを使用するように書き直します（sudo が必要）。

`failproofai uninstall` と `failproofai config` での Codex のチェック解除により、アカウントが削除され、アカウントがなくなるとブロックも削除されます。

sudo なしの場合、および Windows では、フックは `~/.codex/hooks.json` に保持されます。`failproofai config` と `failproofai config --status` は、フックが承認されるまで Codex を適用中とカウントせず、修正方法を示します。`failproofai config` を再実行して sudo を許可するか、`codex` を一度開いてフックを承認してください。

## キャプチャとポリシーフックのインストール

<Tabs>
  <Tab title="ダッシュボード">
    1. **settings → api keys** を開き、マシンまたは環境に名前を付けた `events:add` と `policies:pull` 権限を持つキーを作成します。
    2. 対象マシンで、表示されたキーを使用してローカル CLI を接続し、ハーネスフックをインストールします。
    3. 新しいエージェントセッションを開始し、**trace → live events** でフックとセッションイベントを確認します。
    4. 同じ時間ウィンドウで **fix → activity** を開き、ポリシー決定がそのマシンに帰属していることを確認します。

    接続はマシンキーから始まります。シークレットをコピーする前に、取り込みとポリシー配信の両方の権限が含まれていることを確認してください。

    ![イベント取り込みとポリシー配信権限を付与するための新しい API キードロワー。](/images/dashboard/key-create.png)

    フックをインストールした後、Events ストリームに接続したマシンと環境からの新しいイベントが表示されるはずです。

    ![新しくインストールされたハーネスのレポートを確認するためのライブ Events ストリーム。](/images/dashboard/events-stream.png)

    最後に、ポリシー決定が同じマシンに帰属していることを確認します。これにより、ハーネスがトレースイベントだけでなくポリシーアクティビティもレポートしていることが確認されます。

    ![新しく接続されたハーネスからのポリシー決定を確認するための Policy ページ。](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    マシンキーをシェルに読み込みます。`read -s` はエコーされないプロンプトで受け取るため、コマンドやシェル履歴に表示されることはありません。

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    次にマシンをセットアップします。これにより、検出されたすべてのハーネスのフックが設定され、デーモンがインストールされ、Cloud に接続されます。

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    セットアップ自体はポリシーを有効にしません。それが2番目のコマンドの目的です。

    または、特定のハーネスと設定スコープを指定します。

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    プロジェクトスコープはフック設定をリポジトリと共に保持します。ユーザースコープはリポジトリをまたいだ作業をカバーします。Claude Code はローカルスコープもサポートしていますが、サポートはハーネスによって異なり、CLI はサポートされていない組み合わせを拒否します。

    マシンとそのイベントを確認します。

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## デフォルト以外のセッションパスを追加する

<Tabs>
  <Tab title="ダッシュボード">
    追加パスはマシン上で登録されます（Cloud ではありません）。追加後、**trace → sessions** を開き、マシンの環境でフィルタリングして、新しいパスからのセッションが表示されることを確認します。監査で使用する前に、セッションを開いてエージェント、ハーネス、イベントのタイムスタンプを確認してください。

    ![追加のキャプチャパスからデータを受信している環境にフィルタリングされた Sessions リスト。](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    オプションのラベルを付けてパスを追加し、設定されたパスを確認します。

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    `failproofai harness remove-path claude checkout` でパスを削除します。
  </Tab>
</Tabs>

<Tip>
  インストール後に新しいセッションを1つ実行してください。ロールアウトを拡大する前に、ライブイベントストリームと実際のポリシー決定の両方を確認してください。
</Tip>
