公開 API は Failproof AI ダッシュボードのオリジン上の `/v1` で提供されます。

## キーの作成とリクエストの実行

<Tabs>
  <Tab title="ダッシュボード">
    1. **管理 → キー** を開き、**キーを作成** を選択して、インテグレーションに必要な最小限の権限プリセットを選びます。
    2. 必要な場合のみ個別の権限を追加し、キーを作成して、一度しか表示されないシークレットをコピーします。
    3. `/v1/sessions` にテストリクエストを送り、キーページでキーがアクティブなままであることを確認します。
    4. インテグレーションのオーナーが変わった場合は、アクションメニューからキーをローテーションまたは無効化します。

    ![権限プリセットと個別権限を設定できる新規 API キー作成ドロワー。](/images/dashboard/key-create.png)

    上図は作成ドロワーの画面です。一度しか表示されないシークレットは **作成** を選択した後にのみ表示されます。確認画面を閉じる前にコピーしてください。
  </Tab>
  <Tab title="CLI">
    読み取りキーを作成し、`fp` または `curl` で直接使用します：

    ```bash
    fp keys create reliability-reader \
      --permission-set read-only

    fp --api-key <key> sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/sessions?limit=20" \
      -H "Authorization: Bearer $FAILPROOFAI_KEY"
    ```
  </Tab>
</Tabs>

キーは組織と権限セットにスコープされます。エンドポイントに必要な権限がないリクエストは `403` を返し、不足している権限を通知します。

## 組織の選択

組織キーは自動的にその組織に対して動作します。インスタンススコープのキーはリクエストごとに組織を選択できます：

<Tabs>
  <Tab title="ダッシュボード">
    **管理 → キー** を開く前に、ダッシュボードのヘッダーにある組織切り替えツールを使用します。そこで作成されたキーは選択した組織に属します。認証情報を自動化に組み込む前に、URL とキー詳細で組織のスラッグを確認してください。

  </Tab>
  <Tab title="CLI">
    コマンドの前に `--org` を使用するか、インスタンススコープの API キーに組織ヘッダーを送信します。

    ```bash
    fp orgs list
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/usage" \
      -H "Authorization: Bearer $FAILPROOFAI_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

現在のパス、パラメータ、権限要件、ステータスコードについては、このセクションの生成されたエンドポイントページを参照してください。仕様はサーバーのルートアノテーションから生成され、`/v1` ルーターと照合して検証されます。

現在の仕様はルート、メソッド、パラメータ、権限、ステータスコードを完全にカバーしています。サーバーが動的 JSON として構築し続けているため、一部のレスポンスボディは意図的に型定義されていません。レスポンススキーマのないエンドポイントを強く型付けされたクライアントで扱う前に、実際のレスポンスを確認してください。

JSON の書き込みには `Content-Type: application/json` を使用します。`401` は認証情報の欠如または無効、`403` は有効なIDだが必要な権限がない状態、`404` はリソースが存在しないか組織からアクセスできない状態、`409` は状態の競合、`422` はフィールドまたは権限値が無効な状態として扱います。エラーレスポンスには人間が読めるメッセージが含まれ、権限エラーの場合は必要な権限も明示されます。

イベントの取り込みは改行区切り JSON を使用します（1行につき1つの完全なオブジェクト）。成功時のレスポンスでは `accepted` と `skipped` の両方を確認してください。ネットワーク障害や HTTP 408、429、5xx のレスポンス後はバッチ全体を再試行してください。同じイベントを再送しても安全です。過去のバッチは数ヶ月にわたる期間を含むことができます。取り込みが `error: "event_too_large"` の `422` を返す場合は、問題のあるイベントのペイロードを削減してから再試行してください。バッチを小さなリクエストに分割しても、個々のイベントのサイズは小さくなりません。ファイルインポートの場合は、部分的に保存されたセッションを完了させるため、再試行時に元の `existing_before` のカットオフを再利用してください。

## リクエスト ID

すべてのレスポンスには `X-Request-Id` ヘッダーが含まれ、すべての JSON エラーボディには同じ値が `request_id` として含まれます。サポートに問い合わせる際はこの値を引用してください。これにより特定のリクエストを識別できます。

独自の `X-Request-Id` を送信して、リクエストと自身のログを紐付けることもできます。UUID v4 からダッシュを除いたような、32文字の小文字16進数を使用してください。それ以外の値は新しい ID に置き換えられ、レスポンスで返されます。

<Warning>
  ポリシーの適用デプロイは、通常の公開 `/v1` サーフェスの外で意図的に管理されています。サポートされている Cloud デプロイワークフローを使用してください。
</Warning>
