公開 API は Failproof AI ダッシュボードのオリジン上の `/v1` で提供されます。Failproof AI Cloud ではそのオリジンは `https://app.befailproof.ai` であるため、ベースパスは `https://app.befailproof.ai/v1` になります。セルフホスト環境では、独自のダッシュボードホストに `/v1` を付けたものがベースパスです。そのホストを `fp` に渡すには `--base-url <url>` または `FP_DASHBOARD_URL` を使用してください。

## キーの作成とリクエストの実行

<Tabs>
  <Tab title="ダッシュボード">
    1. **管理 → キー** を開き、**新しいキー** を選択して、インテグレーションに必要な最小限の権限プリセットを選びます。
    2. 必要な場合にのみ個別の権限を追加し、キーを作成してワンタイムシークレットをコピーします。
    3. `/v1/sessions` にテストリクエストを送り、キーページでキーがアクティブなままであることを確認します。
    4. インテグレーションのオーナーが変わった際は、アクションメニューからキーのローテーションまたは無効化を行います。

    ![権限プリセットと個別の権限を含む新しい API キードロワー。](/images/dashboard/key-create.png)

    作成ドロワーは上図のとおりです。ワンタイムシークレットはキー作成後にのみ表示されます。確認画面を閉じる前にコピーしてください。
  </Tab>
  <Tab title="CLI">
    読み取り専用キーを作成し、`fp` または `curl` で直接使用します。`fp` は `--api-key` または `FP_API_KEY` からキーを読み取ります。

    ```bash
    fp keys create reliability-reader \
      --permission-set read-only

    export FP_API_KEY="<one-time-secret>"
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/sessions?limit=20" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

キーは組織と権限のフラットリストにスコープされます。権限セットはキー作成時にそのリストの初期値を設定するだけであり、キー自体は展開された権限を保持します。そのため、作成後にセットを変更してもキーには影響しません。エンドポイントに必要な権限を持たないリクエストは `403` を返し、不足している権限を示します。

## 組織の選択

組織キーは自動的にその組織に対して動作します。インスタンススコープのキーはリクエストごとに組織を選択し、複数の組織を持つテナントはキーモードで常に組織を明示する必要があります。`fp` はキーで認証する際、保存済みの組織を送信しません。

| 呼び出し元 | 組織の指定方法 |
| --- | --- |
| `fp`（コマンドごと） | サブコマンドの前に `--org <slug>` |
| `fp`（環境変数から） | `FP_ORG` |
| 直接 HTTP | `X-AgentEye-Org: <slug>` リクエストヘッダー |

`X-AgentEye-Org` はワイヤー上で元のスペルのまま使用します。これはダッシュボードがアクティブな組織を解決するために読み取るヘッダーであり、クライアントでリネームするとリクエストが失敗します。

<Tabs>
  <Tab title="ダッシュボード">
    **管理 → キー** を開く前に、ダッシュボードヘッダーの組織スイッチャーを使用します。そこで作成されたキーは選択された組織に属します。クレデンシャルを自動化にコピーする前に、URL とキーの詳細で組織スラッグを確認してください。

  </Tab>
  <Tab title="CLI">
    コマンドの前に `--org` を使用するか、インスタンススコープの API キーに対して組織ヘッダーを送信します。`fp orgs list` ではここでスラッグを調べることはできません。キーモードでは拒否されます。代わりにダッシュボードの組織スイッチャーでスラッグを確認してください。

    ```bash
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/usage" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

## ページネーション

リストエンドポイントはキーセット方式でページネーションされており、`fp` 経由でも `curl` 経由でも同じ仕様が適用されます。

| 要素 | 意味 |
| --- | --- |
| `limit` クエリパラメーター | このリクエストで取得する行数。`fp` はすべてのエンドポイントで 1 リクエストあたり最大 200 行に制限します。直接リクエストの場合はサーバー側の各エンドポイントの上限が適用されます。 |
| `cursor` クエリパラメーター | 前のページの続きからフィードを再開するための不透明なトークン。 |
| `next_cursor` レスポンスフィールド | 次のページのトークン。`null` はフィードが終端に達したことを意味します。 |

上限はエンドポイントによって異なり、各エンドポイントページに独自のデフォルト値と上限が記載されています。

| エンドポイント | デフォルト | 上限 |
| --- | --- | --- |
| `/events`、`/events/summary` | 50 | 1000 |
| `/issues`、`/alerts/{id}/issues` | 200 | 1000 |
| `/evaluation-jobs` | 100 | 500 |
| `/audits/findings` | 100 | 500 |
| `/sessions`、`/evaluations` | 50 | 200 |
| `/audits/{id}/runs` | 50 | 200 |

フィード全体を読み取るには、`next_cursor` が `null` になるまで、同じリクエストの `cursor` に前のレスポンスの `next_cursor` を設定して繰り返し実行します。対応する `fp` フラグ（`--all`、`--cursor`、`--page-size`）については [Cloud CLI リファレンス](/ja/reference/cloud-cli) を参照してください。

## エンドポイントリファレンスとエラーハンドリング

現在のパス、パラメーター、権限要件、ステータスコードについては、このセクションの生成済みエンドポイントページを参照してください。仕様はサーバーのルートアノテーションから生成され、`/v1` ルーターとの整合性が検証されています。

現在の仕様はルート、メソッド、パラメーター、権限、ステータスコードのカバレッジが完全です。リクエストボディは型付きですが、レスポンスボディは型付きではありません。サーバーが動的な JSON として構築しているため、現時点では仕様にレスポンススキーマは含まれていません。型を厳密に定義したクライアントを生成する前に、実際のレスポンスを確認してください。

JSON の書き込みには `Content-Type: application/json` を使用してください。`401` は認証情報が欠如または無効、`403` は認証は有効だが必要な権限がない、`404` はリソースが存在しないまたは組織からアクセスできない、`409` は状態の競合、`400` はパラメーターの拒否（未知のフィルター値、不正なクエリパラメーター、実行できないステートメントなど）、`422` はリクエストボディ内の無効なフィールドまたは権限値として扱ってください。エラーレスポンスには人間が読めるメッセージが含まれます。権限エラーの場合は必要な権限も示されます。

## `/v1` が提供しないサーフェス

クラウド管理のポリシー、フリート、ガードレール決定フィードはオペレーター向けのサーフェスであり、読み取りも書き込みも同様です。これらはサーバー上でルート専用であり、インターネットに公開されている `/v1` には意図的に含まれていません。たとえば、ポリシーバージョンの公開やマシンへのデプロイ、フリートの判断結果の読み取りも同じサーフェス上にあります。

したがって、API キーはこれらのルートに対して設計上拒否されます。また `fp` はリクエストが `404` で返るのではなく、接続を開く前に拒否します。

| コマンド | API キー使用時の動作 |
| --- | --- |
| `fp policies` | 終了コード `2` で拒否し、クラウド管理ポリシーがオペレーターサーフェスであることを示す |
| `fp fleet` | 終了コード `2` で拒否し、フリートがオペレーターサーフェスであることを示す |
| `fp guardrails` | 終了コード `2` で拒否し、ガードレールフィードがオペレーターサーフェスであることを示す |
| `fp agent` | 終了コード `2` で拒否。アシスタントは API ではなくダッシュボードによって実装されている |
| `fp orgs` | 終了コード `2` で拒否。組織メンバーシップはサインイン済みユーザーに属し、キーはすでに 1 つの組織に対して動作する |

これらは代わりにサインイン済みユーザーセッション（`fp login`）で実行するか、ダッシュボードを使用してください。読み取りおよび管理ファミリー（セッション、イベント、評価、監査、課題、アラート、キー、権限セット、ユーザー、設定、クエリ、使用状況）はそれぞれ `/v1` ルートを持ち、キーで機能します。唯一の例外は `fp keys update` で、これには `keys:update` が必要ですが、いかなる API キーもその権限を持つことができないため、キーは他のキーの作成・無効化はできますが、権限の編集はできません。`fp login` と `fp logout` もキーモードでは拒否されますが、これは別の理由によるものです。キー自体がすでにクレデンシャルであり、ディスクに保存されることはありません。

<Warning>
  ポリシー適用のデプロイは、通常の公開 `/v1` サーフェスの外で意図的に管理されています。[ポリシーのデプロイ](/ja/policies/deploy) に記載されているサポート対象の Cloud デプロイメントワークフローを使用してください。
</Warning>
