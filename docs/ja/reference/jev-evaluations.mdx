このページでは、[Jev評価](/ja/evaluations/jev)の質問の形式とスコアリングのルールについて説明します。質問の中には、会話を*読む*だけでよく、*書く*必要がないものもあります。「顧客は緊急性を示していましたか？」は2択です。「どのくらい不満を感じていましたか？」は、順序のある選択肢が数個あります。聞く前から答えはすべて分かっています。

**分類器評価（classifier evaluation）**はまさにそのような場合に使います。質問と返しうる回答を記述すると、分類専用の小型モデルがキャリブレーションされた数値を返します。フリーテキストは返しません。

<Note>
ジャッジと同様、分類器評価もセッションごとにモデル呼び出しのコストがかかります。ただし、汎用モデルではなく小型の単一目的モデルなので、速く安く済みます。ただし、理由を説明することはありません。推論が必要な場合は[judge](/ja/evaluations/judge)を使用してください。
</Note>

## どちらを使えばいい？

| 質問 | 使用するもの |
| --- | --- |
| ツール呼び出しは何回あったか？ | code |
| セッションは30秒以内だったか？ | code |
| 顧客は緊急性を示していたか？ | **classifier** |
| このケースはどのチームが担当すべきか：billing、technical、それともsales？ | **classifier** |
| 顧客はどのくらい不満を感じていたか？ | **classifier** |
| 回答は実際に正しかったか？ | **judge** |
| エスカレーションポリシーに従っていたか、またその理由は？ | **judge** |

判断の目安：**数えられるもの → code、列挙できる回答 → classifier、説明が必要 → judge**

最初から決める必要はありません。測定したい内容を説明すれば、アシスタントが選んで、選んだ理由とともに伝えてくれます。変更も可能です。

## 2種類の質問タイプ

### `noul` — これは真か？

2つの回答があり、それぞれを記述します。結果は「true」の説明が当てはまる確率です：

```json
{
  "instructions": "アシスタントは払い戻しポリシーを確認せずに返金を約束しましたか？",
  "criteria": {
    "true":  "事前のポリシー確認や承認なしに返金が約束または実施された",
    "false": "返金は約束されなかった、またはすべての返金がポリシー確認を経ていた"
  }
}
```

両方の側面を記述してください。「緊急性は示されていない」も立派な回答であり、明示することでもう一方の答えがより明確になります。

### `score` — どの程度か？

順序付きのルーブリックで、**最悪のものを最初に**書きます。結果はセッションがルーブリック上のどの位置にあるかで、0〜1にスケーリングされます：

```json
{
  "instructions": "顧客はどのくらい不満を感じていますか？",
  "criteria": ["穏やか", "不満", "非常に怒っている"]
}
```

**ルーブリックは3〜5段階で、すべて異なる内容でなければなりません。** この制限は文体上の好みではなく、実測に基づくものです：

- **2段階**では`noul`がより適切に処理できる内容に崩れてしまい、**5段階超**ではモデルが両端を避けて中間に集まる傾向があります。同じ質問を同じセッションで試したところ、2段階では0.00、3段階では0.01、10段階では0.55というスコアになりました。
- **重複する段階**があると、回答が任意に分散されます。明らかに怒っていたセッションは`["穏やか", "不満", "非常に怒っている"]`に対しては1.00のスコアでしたが、`["怒り", "怒り", "怒り"]`に対しては0.66という、形式的には正しいが意味のない数値になりました。

順序のないカテゴリ（「billing、technical、またはsales」など）はルーブリックではありません。カテゴリごとに`noul`として聞くか、judgeを使用してください。

## 結果の読み方

分類器はjudgeと同じく0〜1の**スコア**を返すため、チャート表示、フィルタリング、アラートのトリガーも同様に機能します。ただし、2点異なる点があります：

- **推論は提供されません。** このフィールドは意図的に空になっています。このモデルは理由を説明せず、説明を作り上げることは機能ではなく捏造になります。
- **不確実性にはラベルが付きます。** `score`質問はモデル自身の信頼度を報告し、モデルが不確かだった結果には`low_confidence`のタグが付きます。「人間が確認すべきもの」はフィルターで判断でき、推測する必要がありません。`noul`質問は信頼度を報告しないため、タグは付きません。

非常に長いセッションは抜粋して読み取り、統合されます。全体を読み切れないほど長いセッションの場合、何ターン省略されたかが結果に表示されます。セッションの一部に基づく判断が全体の判断として提示されることはありません。

## 制限

- **ルーブリックは3〜5段階で、すべて異なること。** 上記参照。両方の境界は作成時に適用されます。
- **評価ごとに質問は1つ。** 2つのことを聞きたい場合は2つの評価を作成します。チャートで見るときもその方が都合がよいです。
- **質問を編集すると新しいバージョンが公開されます。** 旧スコアと新スコアは比較できないため、1つのトレンドラインに混在させずに別々に管理されます。
- **分類器は常にスコアを返します。** メトリクスやアサーションは返しません。
- **推論なし**（上記参照）。ある数値を見て「なぜ？」と聞かれそうであれば、代わりにjudgeを作成してください。

## テストとバックフィル

judgeとは異なり、分類器評価はデプロイ前に**テストが可能**です。コード評価と同じように実際のセッションで[テスト](/ja/evaluations/test)し、本番稼働前にスコアを確認できます。

また、すでに存在するセッションに対して[バックフィル](/ja/evaluations/deploy#score-sessions-you-already-have)することもできます。セッションごとにモデル呼び出しのコストがかかるため、すべてを再実行するのではなく、対象期間を意図的に絞って指定してください。
