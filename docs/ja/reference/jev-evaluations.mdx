このページでは、[Jev 評価](/ja/evaluations/jev)の質問形式とスコアリングルールについて説明します。質問の中には、会話を*読む*必要があるが*書く*必要はないものもあります。「顧客は緊急性を表現しましたか？」には2つの答えがあります。「どれだけ不満を感じていましたか？」には順序のある少数の答えがあります。質問する前からすべての答えがわかっています。

**分類評価**はまさにそのようなケース向けです。質問と取り得る回答を記述すると、分類専用の小型モデルがキャリブレーション済みの数値を返します — 自由テキストは返しません。

<Note>
ジャッジと同様に、分類評価はセッションごとにモデル呼び出しコストが発生します。ただし汎用モデルではなく、単一目的の小型モデルであるため、高速かつ低コストです — ただし説明は返しません。推論が必要な場合は [ジャッジ](/ja/evaluations/judge) を使用してください。
</Note>

## どれを使うべきか？

| 質問 | 使用方法 |
| --- | --- |
| ツール呼び出しは何回ありましたか？ | コード |
| セッションは30秒以内でしたか？ | コード |
| 顧客は緊急性を表現しましたか？ | **分類** |
| 担当チームは請求、技術、営業のどれですか？ | **分類** |
| 顧客はどれだけ不満を感じていましたか？ | **分類** |
| 回答は実際に正しかったですか？ | **ジャッジ** |
| エスカレーションポリシーに従っていましたか？その理由は？ | **ジャッジ** |

目安: **数えられるもの → コード、列挙できる答え → 分類、説明が必要 → ジャッジ**

最初から決める必要はありません。測定したい内容を記述すると、アシスタントが選択し、選んだ理由を説明します。変更することも可能です。

## 2つの質問タイプ

### `noul` — これは真実ですか？

2つの答えがあり、両方を記述します。結果は「真」の説明が当てはまる確率です:

```json
{
  "instructions": "アシスタントは返金ポリシーを確認せずに返金を約束しましたか？",
  "criteria": {
    "true":  "事前のポリシー確認や承認なしに返金が約束または実行された",
    "false": "返金は約束されなかった、またはすべての返金がポリシー確認に従った"
  }
}
```

両方の側面を記述してください。「緊急性は表現されなかった」も正当な答えであり、それを明示することで反対の答えがより明確になります。

### `score` — どれくらいですか？

順序付きのルーブリックで、**最低評価を最初**に記述します。結果はセッションがルーブリック上のどこに位置するかを0〜1にスケール変換したものです:

```json
{
  "instructions": "顧客はどれだけ不満を感じていますか？",
  "criteria": ["落ち着いている", "不満がある", "非常に怒っている"]
}
```

**ルーブリックは3〜5段階で、すべて異なる内容にする必要があります。** どちらの制限もスタイル上の問題ではなく、測定上の問題です:

- **2段階**は `noul` が既により上手く行っていることと同じになってしまい、**5段階超**ではモデルがコミットせず中間に寄ってしまいます。同じセッションに対して同じ質問をしたところ、2段階では0.00、3段階では0.01、10段階では0.55というスコアになりました。
- **段階の重複**は任意に答えを分割します。明らかに怒っていたセッションが `["落ち着いている", "不満がある", "非常に怒っている"]` に対しては1.00、`["怒っている", "怒っている", "怒っている"]` に対しては0.66を記録しました — 正しい形式の数値ですが意味を持ちません。

順序のないカテゴリ — 「請求、技術、営業」 — はルーブリックではありません。カテゴリごとに `noul` として質問するか、ジャッジを使用してください。

## 結果の読み方

分類はジャッジと同様に0〜1の**スコア**を生成するため、チャート表示、フィルタリング、アラートのトリガーも同じ方法で行えます。2つの違いを知っておく価値があります:

- **推論はありません。** このフィールドは意図的に空です。このモデルは自分自身を説明せず、説明を作り上げることは機能ではなく虚偽になります。
- **不確実性にラベルが付きます。** `score` 質問はモデル自身の信頼度を報告し、モデルが不確かだった結果には `low_confidence` のタグが付きます — そのため「人間が確認すべきものはどれか」はフィルタリングで対応できます。`noul` 質問は信頼度を報告しないため、タグ付けされることはありません。

非常に長いセッションは抜粋を読み合わせて組み合わせます。セッションが全体を読むには長すぎる場合、結果には省略されたターン数が示されます — 一部のセッションに基づいた判断が全体に基づいたものとして提示されることはありません。

## 制限

- **ルーブリックは3〜5段階で、すべて異なること。** 上記参照。両方の制限は作成時に適用されます。
- **評価ごとに1つの質問。** 2つのことを尋ねると2つの評価になります。これはチャートでも望ましい形です。
- **質問を編集すると新しいバージョンが公開されます。** 古いスコアと新しいスコアは比較できないため、1つのトレンドラインに混在させず別々に保持されます。
- **分類は常にスコアを生成します** — メトリクスやアサーションは生成しません。
- **推論はありません**（上記参照）。数値を見た人が「なぜ？」と聞くようであれば、代わりにジャッジを使用してください。

## テストとバックフィル

ジャッジとは異なり、分類評価はデプロイ前に**テストできます** — コード評価と同じ方法で実際のセッションに対して[テスト](/ja/evaluations/test)し、本番稼働前にスコアを確認できます。

また、既存のセッションに対して[バックフィル](/ja/evaluations/deploy#score-sessions-you-already-have)することも可能です。セッションごとにモデル呼び出しコストが発生するため、すべてを再実行するのではなく、ウィンドウを意図的に絞り込んでください。
