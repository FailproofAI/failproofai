このページでは、[Jev評価](/ja/evaluations/jev)の背後にある質問の形式とスコアリングルールについて説明します。質問によっては、会話を*読む*モデルは必要でも、それについて*書く*必要がないものがあります。「顧客は緊急性を示しましたか？」には2つの答えがあります。「どれほど不満を感じていましたか？」には、順序のある少数の答えがあります。聞く前からすべての答えがわかっているわけです。

**クラシファイア評価**は、まさにそのようなケースに対応しています。質問とそれが返しうる回答を記述すると、分類専用に作られた小型モデルが較正済みの数値を返します——自由記述テキストは返しません。

<Note>
ジャッジと同様に、クラシファイア評価はセッションごとにモデルの呼び出しコストが発生します。ジャッジと異なるのは、汎用モデルではなく小型の単一目的モデルを使用するため、高速かつ低コストである点です——ただし、自己説明はしません。推論が必要な場合は[ジャッジ](/ja/evaluations/judge)を使用してください。
</Note>

## どちらを使えばよいか？

| 質問 | 使用方法 |
| --- | --- |
| ツール呼び出しは何回ありましたか？ | code |
| セッションは30秒以内でしたか？ | code |
| 顧客は緊急性を示しましたか？ | **classifier** |
| このケースを担当するチームはどこですか：請求、技術、それとも営業？ | **classifier** |
| 顧客はどれほど不満を感じていましたか？ | **classifier** |
| 回答は実際に正しかったですか？ | **judge** |
| エスカレーションポリシーに従っていましたか？その理由は？ | **judge** |

判断の目安：**数えられるもの → code、一覧できる回答 → classifier、説明が必要なもの → judge。**

事前に決める必要はありません。測定したいことを説明すると、アシスタントが選択し、選んだ内容とその理由を教えてくれます。変更も可能です。

## 2種類の質問タイプ

### `noul` — これは真ですか？

2つの答えがあり、両方を記述します。結果は「真」の説明が当てはまる確率です：

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

両側を記述してください。「緊急性は示されていない」は立派な回答であり、それを明示することで反対側の回答もより明確になります。

### `score` — これはどの程度か？

順序付きのルーブリックで、**最悪のものを最初に**記述します。結果はセッションがルーブリック上のどこに位置するかを0〜1にスケールしたものです：

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**ルーブリックは3〜5段階で、すべて異なる内容でなければなりません。** 両方の制限は文体上の問題ではなく、実際に測定された結果に基づいています：

- **2段階**は`noul`がすでにうまく処理できる内容に収束し、**5段階超**ではモデルが中間に寄った曖昧な判断をするようになります。同じ質問を同じセッションに適用した場合、2段階では0.00、3段階では0.01、10段階では0.55というスコアになりました。
- **重複した段階**は、回答が任意に分散されてしまいます。明らかに怒っていたセッションが`["Calm", "Frustrated", "Very angry"]`に対して1.00のスコアを記録したのに対し、`["Angry", "Angry", "Angry"]`では0.66——意味のない、しかし整形式の数値——になりました。

順序のないカテゴリ——「請求、技術、それとも営業」——はルーブリックではありません。カテゴリごとに`noul`として質問するか、ジャッジを使用してください。

## 結果の読み方

クラシファイアはジャッジと同様に0〜1の**スコア**を生成するため、チャート化、フィルタリング、アラートのトリガーも同じ方法で行えます。知っておくべき相違点が2つあります：

- **推論はありません。** このフィールドは意図的に空になっています。このモデルは自己説明を行わず、説明を作り上げることは機能ではなく捏造になります。
- **不確実性はラベル付けされます。** `score`質問はモデル自身の信頼度を報告し、モデルが確信を持てなかった結果には`low_confidence`タグが付きます——「どれを人間がチェックすべきか」はフィルターで判断でき、推測する必要がありません。`noul`質問は信頼度を報告しないため、タグが付くことはありません。

非常に長いセッションは抜粋して読み取り、統合されます。セッションが全体を読み取るには長すぎる場合、結果には省略されたターン数が表示されます——セッションの一部に対して下した判断が全体に対するものとして提示されることはありません。

## 制限

- **ルーブリックは3〜5段階、すべて異なる内容であること。** 上述のとおり、両方の制限はオーサリング時に強制されます。
- **評価ごとに1つの質問。** 2つのことを質問すると2つの評価になります。チャートでもそのほうが便利です。
- **質問を編集すると新しいバージョンが公開されます。** 旧スコアと新スコアは比較できないため、1つのトレンドラインに混在させるのではなく、分けて保管されます。
- **クラシファイアは常にスコアを生成します**——メトリクスやアサーションは生成しません。
- **推論なし**、上述のとおり。数値を見て「なぜ？」と聞かれる可能性がある場合は、代わりにジャッジを作成してください。

## テストとバックフィル

ジャッジと異なり、クラシファイア評価はデプロイ前に**テスト可能です**——コード評価と同じ方法で実際のセッションを使って[テスト](/ja/evaluations/test)し、本番稼動前にスコアを確認できます。

また、すでに保有しているセッションに対して[バックフィル](/ja/evaluations/deploy#score-sessions-you-already-have)することもできます。セッションごとにモデルの呼び出しコストが発生するため、すべてを再実行するのではなく、対象範囲のウィンドウを意図的に設定してください。
