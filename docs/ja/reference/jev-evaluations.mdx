このページでは、[Jev 評価](/ja/evaluations/jev)の背後にある質問の形式とスコアリングルールについて説明します。質問の中には、会話を*読む*ことが必要でも、会話について*記述する*必要がないものがあります。「顧客は緊急性を示しましたか？」には二つの答えがあります。「どのくらい苛立っていましたか？」には順序のある選択肢がいくつかあります。聞く前から答えはすべて分かっています。

**分類評価（classifier evaluation）** はまさにそのようなケースに対応しています。質問とその回答候補を定義すると、分類に特化した小型モデルが調整済みの数値を返します — フリーテキストは返しません。

<Note>
ジャッジと同様に、分類評価はセッションごとにモデル呼び出しが発生します。ただし汎用モデルではなく、小型の単一目的モデルを使用するため、高速かつ低コストです — ただし、自分の判断を説明することは一切ありません。推論が必要な場合は、[ジャッジ](/ja/evaluations/judge)を使用してください。
</Note>

## どちらを使えばよいか？

| 質問 | 使用するもの |
| --- | --- |
| ツール呼び出しは何回ありましたか？ | コード |
| セッションは 30 秒以内でしたか？ | コード |
| 顧客は緊急性を示しましたか？ | **分類器** |
| 担当チームはどこか：請求、技術、営業？ | **分類器** |
| 顧客はどのくらい苛立っていましたか？ | **分類器** |
| 回答は実際に正確でしたか？ | **ジャッジ** |
| エスカレーションポリシーに従っていたか、またその理由は？ | **ジャッジ** |

大まかな判断基準：**数えられるもの → コード、列挙できる答え → 分類器、説明が必要なもの → ジャッジ。**

事前に決める必要はありません。測定したい内容を説明すると、アシスタントが選択肢を選び、どれを選んだかとその理由を伝えてくれます。変更も可能です。

## 二つの質問タイプ

### `noul` — これは真実か？

二つの答えがあり、それぞれを説明します。結果は「真」の説明が当てはまる確率です：

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

両面を説明してください。「緊急性は示されなかった」も立派な答えであり、明示することでもう一方の答えがより明確になります。

### `score` — どの程度か？

順序付けられたルーブリックで、**最低レベルを先頭に**記述します。結果はセッションがルーブリック上のどこに位置するかを 0〜1 にスケールし直したものです：

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**ルーブリックは 3〜5 段階で、すべて異なる内容でなければなりません。** どちらの制限も文体上の好みではなく、実測に基づくものです：

- **2 段階**では `noul` がすでに得意とすることに収束してしまい、**5 段階超**ではモデルが両端を避けて中間に集中するようになります。同じ質問・同じセッションで、2 段階では 0.00、3 段階では 0.01、10 段階では 0.55 というスコアが出ました。
- **重複する段階**は答えを恣意的に分散させます。明らかに怒っていたセッションが `["Calm", "Frustrated", "Very angry"]` に対しては 1.00、`["Angry", "Angry", "Angry"]` に対しては 0.66 というスコアになりました — 数値としては成立しているが、意味をなしません。

順序のないカテゴリ（「請求、技術、営業」など）はルーブリックではありません。カテゴリごとに `noul` で尋ねるか、ジャッジを使用してください。

## 結果の読み方

分類器はジャッジと同様に **0〜1 のスコア**を出力するため、グラフ表示、フィルタリング、アラートのトリガーなど同じ方法で活用できます。知っておくべき二つの違いがあります：

- **推論は提供されません。** このフィールドは意図的に空になっています。このモデルは自己説明をせず、説明を作り上げることは機能ではなく捏造になります。
- **不確実性にはラベルが付きます。** `score` 質問はモデル自身の信頼度を報告し、モデルが確信を持てなかった結果には `low_confidence` タグが付きます — 「どれを人間がチェックすべきか」はフィルターで判断でき、推測に頼る必要がありません。`noul` 質問は信頼度を報告しないため、このタグが付くことはありません。

非常に長いセッションは抜粋して読み取り、結果を統合します。セッション全体を読み取れない場合、何ターン省略されたかが結果に示されます — 一部のセッションのみに基づいた判断が、全体に基づいたものとして表示されることはありません。

## 制限

- **ルーブリックは 3〜5 段階で、すべて異なる内容であること。** 上記参照。両方の制限はオーサリング時に強制されます。
- **評価ごとに質問は一つ。** 二つのことを尋ねる場合は二つの評価を作成します。グラフ上でも二つに分けた方が適切です。
- **質問を編集すると新しいバージョンが公開されます。** 旧スコアと新スコアは比較できないため、一つのトレンドラインに混在させず、分けて管理されます。
- **分類器は常にスコアを出力します** — メトリックやアサーションではありません。
- **推論なし**、上記参照。数値を見た人が「なぜ？」と問いたくなるなら、ジャッジを書いてください。

## テストとバックフィル

ジャッジとは異なり、分類評価はデプロイ前に**テストが可能です** — コード評価と同様に実際のセッションを使って[テスト](/ja/evaluations/test)し、本番稼働前にスコアを確認できます。

また、すでに存在するセッションに対して[バックフィル](/ja/evaluations/deploy#score-sessions-you-already-have)することもできます。セッションごとにモデル呼び出しが発生するため、すべてを再実行するのではなく、対象ウィンドウを意図的に絞って指定してください。
