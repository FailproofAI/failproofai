これは、独自キーを使用した[Jevポリシー](/ja/policies/jev)のプロバイダーおよび設定リファレンスです。正規表現ポリシーは文字列をマッチングします。`rm -rf build/` のように自分でリクエストしたものと、プランに紛れ込んだ `rm -rf ~` を区別できないため、ある箇所では過剰にブロックし、別の箇所では不十分なブロックしかできません。TypeSafeのクラシファイアである**Jev**は、実際のリクエスト内容に照らし合わせてツール呼び出しを読み取り、1回の高速なリクエストで一連のyes/noの質問に回答します。

独自のJevエンドポイントとキーが設定されている場合、Failproof AIは各ツール呼び出しについて、正規表現ポリシーの代わりではなく、**正規表現ポリシーと並行して**Jevに問い合わせます。

- **ハード**ポリシーのdenyは最終的なものです。Jevはそれを解除できません。ポリシーは、レビュー可能と明示的にマークされ、対象となるJevチェックが指定されていない限り、すべてハードです。つまり、何も指定しないカスタム、パック、またはCloudのポリシーはハードであり、常時オンの自己保護ガードも常にハードです。
- **レビュー可能**ポリシーのdenyは解除される場合がありますが、そのポリシーがカバーする正確な懸念事項についてJevに問い合わせられ、「問題なし」または「ユーザーがこれをリクエストした」と回答された場合のみです。懸念事項が実在すると判断されたチェックは、ユーザーがその呼び出しをリクエストしていない場合、denyを維持します。そのチェック自身の判定が警告のみであっても同様です。ツール呼び出し前の警告はエージェントを止めないからです。そして、そのチェックがdenyできるもの（シークレット露出、クレデンシャル流出、破壊的削除など）である場合、その呼び出しでは何も解除されません。
- ブロックは、その呼び出しが指定したタスクのステップであり、それ以上に及ばない場合、**警告**に変わることがあります。Jevは自身のdenyを警告に緩和し、その警告（呼び出しの実際の問題点を明示したもの）がポリシーのブロックに置き換わります。
- Jevは、正規表現では記述できない害に対して、独自に警告またはdenyを発することもできます。
- Jevが回答できない場合（タイムアウト、レート制限、サーバーエラー、クレジット不足、予期しないモデルバージョン）、その呼び出しはJevなしの場合と全く同じように正規表現の結果を受け取ります。
- Jevは、呼び出し全体を読み取り、正確な懸念事項について問い合わせられた場合を除き、ポリシー単独よりも呼び出しを許可側に変えることはありません。それ未満の状態（呼び出しが大きすぎて全体を送信できない場合、インジェクションの疑いがある場合）では、解除が撤回され、すべてのdenyが維持されます。

<Note>
Jevの設定がなければ何も変わりません。フックは常に通り正規表現ポリシーを実行します。設定ファイル自体がオプトインです。
</Note>

<Tip>
FailproofAI Cloudをご利用の場合、独自キーは不要です。`jev:evaluate` を持つキーで接続されたマシンは、組織のプランでJevを使用できます。[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)をご覧ください。
</Tip>

## 始める前に

**failproofai 1.0.8-beta.0以降**をインストールし、エージェントが動作するマシンで[サポートされているハーネス](/ja/reference/harnesses)にフックをアタッチします。新しいマシンの場合は[クイックスタート](/ja/start/quickstart)に従い、Cloudを使用しない場合は[ローカル強制の設定](/ja/start/setup#enforce-locally)に従ってください。インストール済みCLIを `failproofai --version` で確認します。

以下のプロバイダーからAPIキーを取得するか、互換性のあるエンドポイントとそのキーを用意します。Jevは `PreToolUse` または `PermissionRequest` ゲートで名前付きツール呼び出しをレビューします。独自の判定を下すことができますが、既存のポリシーdenyを解除するには、[レビュー可能](/ja/policies/authority)とマークされたポリシーがインストールされている必要があります。ハードポリシーのdenyは最終的なものとして維持されます。

## プロバイダーを選択する

Jevには5つのルートからアクセスできます。そのうちのいずれか1つのキーを用意します。

| プロバイダー | `--provider` | エンドポイント | デフォルトモデル | 備考 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | バージョンを固定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | リクエストはゼロデータリテンションのエンドポイントのみにルーティングされ、他のプロバイダーへのフォールバックはありません。`typesafe/jev-1.13-20260917` のような日付付きバージョンを報告します。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jevをエイリアスのみで識別するため、回答したバージョンは未検証として記録されます。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id` が必要。キーあたり毎秒約6リクエストでHTTP 429が測定されました。 |
| 独自エンドポイント | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafeのリクエストボディを受け付け、どのモデルが回答したかを報告するエンドポイントであれば可。`https` のみ。ローカルテスト用に、ループバックホスト（`localhost`、`127.0.0.1`、`::1`）への平文 `http` も受け付けます。 |

<Warning>
Vercel独自のbring-your-own-key機能では、リクエストが失敗すると、Vercelのクレデンシャルでサイレントに再試行されます。すべての呼び出しを自身のTypeSafeアカウントにのみ課金・表示させる必要がある場合は、TypeSafeを直接使用してください。
</Warning>

## セットアップ

1つのコマンドで、エンドポイントとキーを設定します。既存のポリシーが引き続き呼び出しを決定しながらJevの判定を検査できるよう、まず `observe` モードで開始します。

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URLがプロバイダーを決定する

プロバイダーを明示的に指定する必要はありません。URLの**ホスト**がどのプロバイダーかを示します。

| URLホスト | プロバイダー | 追加で必要なもの |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| その他のホスト | `custom` | — 指定したURLがベースURLになります |

これから3つのことが言えます。

- **プロバイダー独自のAPIのURLは、オーバーライドを書き込みません。** `--url https://api.typesafe.ai/v1` は、`--provider typesafe` とまったく同じ設定を生成します。既知のプロバイダーで異なるパスやホストを指定すると、`--base-url` が格納するのと同様にベースURLとして保存されます。
- **`--provider` は推論をオーバーライドできます。** これにより、独自のホストでプロバイダーのAPIを話すプロキシへアクセスできます: `--url https://jev-proxy.internal/v1 --provider typesafe`。
- **ホストと矛盾する `--provider` は拒否されます。** `--provider openrouter --url https://api.typesafe.ai/v1` は何も書き込まず、理由を説明します。2つの指定がキーの送信先について矛盾しているためです。同じペアは `jev setup --base-url` およびダッシュボードのJev設定からも拒否されます。（`--provider custom` は矛盾ではありません。「このURLをそのまま扱う」という意味です。ただし、カスタムルートではアクセスできないアカウント固有のエンドポイントを持つCloudflareのホストは除きます。）

`--url` は設定ファイルの `baseUrl` と全く同様に検証され、同じ言葉で拒否されます。`https`、またはいずれかのモードでループバックホスト（`localhost`、`127.0.0.1`、`::1`）への平文 `http`。リスク: ループバックサーバーを認証するものがないため、サーバーがダウンしている間に別のローカルプロセスがそのポートを占有して回答する可能性があります。ローカルテスト以外では `https` を使用してください。

### キー

`--key-stdin` でパイプするか、端末でコマンドをキーなしで実行してマスクされたプロンプトでキーを貼り付けます。どちらの方法でも、キーは設定ファイルに直接書き込まれ、表示されることはありません。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` は同じフラグを受け付け、すべての長形式です。URLよりもプロバイダー名を指定したい場合は `setup --provider <kind>` を使用します。

### `--token` とそのコスト

`--token <token>` はコマンドライン上にキーを置きます。これはマシンを設定する最も速い方法ですが、設定ファイル以外にキーを残す唯一の方法でもあります。

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
コマンドライン引数はその後シェルの履歴ファイルに残ります。また、コマンドの実行中はプロセスリストに表示され、`/proc` から自分として実行されているプロセスなら誰でも読み取れます。`setup` は `--token` が使用されるたびにこれを通知します。共有マシンや記録されたセッション、または履歴ファイルが同期される場所では `--key-stdin` を使用してください。この方法で渡したキーが重要な場合は、ローテーションしてください。
</Warning>

`--token`、`--key-stdin`、`--key-from-env` は相互に排他的です。いずれか1つを指定します。

次に、キー、エンドポイント、どのJevが回答したかを確認するために1つの小さなライブリクエストを送信します。

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` は、タイムアウト後に回答が届いた場合（すべてのフックが `timeout` として正規表現にフォールバックします）またはチェック質問への回答が誤りの場合、1を終了コードとして返し、タイトルにもその旨を表示します。

フックは各ツール呼び出し時に設定を読み取るため、次の呼び出しから適用されます。デーモンの有無にかかわらず、再起動は不要です。

## 動作の確認

```bash
failproofai jev status
failproofai jev status --json
```

`status` は、プロバイダー、エンドポイント、モデル、モード、設定ファイルとそのパーミッションを表示し、キーは表示しません。その下に最近のアクティビティのサマリーが表示されます。Jevが評価した呼び出し数、正規表現にフォールバックした回数とその理由、レイテンシー、およびクリアされたレビュー可能ポリシーが含まれます。

## 実際の呼び出しを確認する

フックされたエージェントで新しいセッションを開始します。ファイル読み取りツールで `README.md` を読み取り、タイトルを報告するよう依頼します。セッションにそのツール呼び出しが含まれることを確認してから、`failproofai jev status` を再実行します。最近の評価済み呼び出し数が増加しているはずです。[ローカルダッシュボード](/ja/reference/local-dashboard#review-policy-activity)の**Policies → Activity**を開き、呼び出しのJev判定とモードを確認します。observeモードでは、ポリシーの結果が引き続き呼び出しを決定します。解除は、レビュー可能なポリシーがマッチし、Jevがすべての指定されたチェックをクリアした場合にのみ表示されます。通常の読み取りには解除すべきポリシーがない場合があります。

## Observeモード

`enforce` がデフォルトです。Jevの判定を変更せずに観察するには、`observe` に切り替えます。Jevは引き続き問い合わせられ、判定は記録されますが、実際に適用されるのは正規表現の結果です。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` は設定（エンドポイントとキー）を保持したままJevへの問い合わせを停止します。フックは設定なしの場合と同様に正規表現ポリシーを実行し、`failproofai jev status` は「off (switched off)」と表示します。`--mode observe` または `--mode enforce` で元に戻せます。

同じプロバイダーで `setup` を再実行すると保存済みキーが維持されるため、モードの切り替えはフラグ1つで完了します。プロバイダーの切り替えは最初からやり直しになり、新しいプロバイダーのキーが要求されます。リクエストを別のホストに移動する `--base-url` も同様です。保存済みキーは、それが提供されたホストまたはそのプロバイダー独自のAPIにのみ送信されます。

## 設定ファイル

すべてのデータは `~/.failproofai/jev.json` という1つのファイルに格納され、`setup` によって書き込まれます。

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| フィールド | 意味 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare`、`custom` のいずれか。または `failproofai`（このファイルではなくFailproofAI Cloud接続からキーを取得します。[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)を参照）。 |
| `apiKey` | `Authorization: Bearer <key>` として送信されます。 |
| `baseUrl` | `custom` には必須。その他の場合はプロバイダーのAPIベースを置き換えます。`https` が必須。`localhost` への平文 `http` は `mode: observe` のみ受け付けます。ローカルポートを認証するものがないため、プロキシがダウンしている間、エージェント自身を含むマシン上のあらゆるプロセスが代わりに回答する可能性があります。 |
| `accountId` | Cloudflareのみ: 32文字の小文字16進数。 |
| `model` | プロバイダーのデフォルトモデルIDを置き換えます。バージョン付きIDはJev 1.13を指定する必要があります。APIキーのような形式の値は拒否されます（繰り返し表示もされません）。そのため、`--model` に誤ってキーを貼り付けてもモデルとして保存・送信されることはありません。 |
| `timeoutMs` | 正規表現の結果を使用する前にツール呼び出しがJevの回答を待つ時間。100〜10000、デフォルトは3000。 |
| `mode` | `enforce`（デフォルト）、`observe`、または `off`（設定を保持したままJevを実行しない）。 |

3つのルールでファイルを保護しています。

- **オーナーのみ。** パーミッション `0600` で書き込まれます。他のユーザーまたはグループが読み書きできるコピーは**拒否され**、`chmod 600 ~/.failproofai/jev.json` を実行するか `setup` を再実行するまで、フックは正規表現にフォールバックします。ディレクトリも確認されます。`~/.failproofai` は他のユーザーが**書き込み可能**であってはなりません。書き込みできる人は、ファイル自身のパーミッションにかかわらずファイルを置き換えられるからです。`setup` は見つけた場合にその書き込みビットを削除します。`failproofai jev status` は設定が拒否された場合にそのことを表示し、ファイルに記載されているエンドポイントを示します。他の誰かが変更した可能性があるため、`chmod` を実行する前に自分のファイルであることを確認してください。そのようなファイルで `setup` を再実行すると、保存されたキーはプロバイダー独自のAPIにのみ引き継がれます。ファイルに記載されているその他のエンドポイントは、再度キーが必要です（`--key-stdin`）。または `--base-url default` でリクエストをプロバイダーに戻します。
- **グローバルのみ。** リポジトリからJevを有効化したり、別のエンドポイントに向けたり、モデルを選択したりすることはできません。プロジェクト内の `.failproofai/jev.json` は無視され、プロバイダー、URL、モデル、アカウントIDは、リポジトリのエージェント設定が設定できる環境変数からではなく、そのファイルからのみ読み取られます。（`FAILPROOFAI_HOME` はこれを回避する手段ではありません。Jevだけをリダイレクトするのではなく、ポリシーを含むfailproofaiディレクトリ全体を移動します。）
- **キーのみ環境変数から取得できます。** ファイルに `apiKey` がない場合、`FAILPROOFAI_JEV_API_KEY` がそのセッション用に提供します（`setup --key-from-env` でそのようなファイルが作成されます）。ファイルが保持するキーを置き換えることはなく、ファイルなしでJevを有効化することもできません。変数が設定されていない場合、Jevはそのシェルでオフになります。`failproofai jev status` はその旨を表示し、終了コード0で設定はそのままにします（`status --json` は `"reason": "no-env-key"` とともに `"status": "key-missing"` を報告します）。`failproofaid` デーモンはシェルの環境を参照しないため、`failproofai config` でセットアップしたマシンでは、キーをファイルに保存してください。

## どのJevが回答するか

Failproof AIの判定閾値はJev 1.13でキャリブレーションされているため、そのファミリーから回答が来た場合にのみ使用されます。`jev-1.13.x`、またはOpenRouterの `typesafe/jev-1.13-<date>`。プロバイダーがJevをエイリアスのみで識別し、バージョンを報告しない場合（Vercel、およびバージョンを通知しないCloudflare）、回答は使用され、未検証として記録されます。`custom` エンドポイントは回答したモデルを報告する必要があります。唯一の例外は、バージョンなしの `--model` 名を設定した場合で、エコーバックされると同様に未検証として記録されます。他のバージョンを報告する回答、またはバージョンを報告しない `custom` の回答は使用されず、その呼び出しは `model-mismatch` の理由で正規表現にフォールバックします。

## Jevが回答できない場合

以下の各ケースは、その呼び出しの正規表現の結果にフォールバックし、理由とともに記録されます。`failproofai jev status` はこれらを集計します。

| 理由 | 原因 |
| --- | --- |
| `timeout` | `timeoutMs` 以内に回答なし。 |
| `http-429` | プロバイダーがキーのレート制限を行った。 |
| `rate-limited` | Failproof AI自身のリミッターが送信前に呼び出しを保留した: 毎秒5リクエスト、バースト最大5まで、プロバイダーが `429` を返した後しばらく停止。プロバイダーによるものではありません。 |
| `http-500`, `http-502`, `http-503`, … | プロバイダーのサーバーエラー。正確なステータスが記録されます。 |
| `out-of-credits` | HTTP 402: プロバイダーアカウントのクレジットが不足。 |
| `provider-refused` | Cloudflareからの「Model execution failed (Payment error)」というHTTP 402: プロバイダーがこのリクエストのモデル実行を拒否。通常は課金の問題ではないため、クレジットを追加しても解決しません。 |
| `http-401`, `http-403` | キーが拒否された。 |
| `http-404` | `<base>/systemone` で何も提供されていないため、ベースURLが誤っています。`/systemone` がベースURLに追加され、すべてのプロバイダーはバージョンルートで提供します。`failproofai jev models` でエンドポイントが提供しているものを確認できます。 |
| `network` | エンドポイントに到達できなかった。 |
| `http-301`, `http-302`, `http-307`, `http-308` | エンドポイントがリダイレクトで回答した。リダイレクトは決してフォローされないため、回答は常に設定内のURLからのみ来ます。`--base-url` を最終URLに設定してください。 |
| `malformed` | エンドポイントが回答したが、Jevの回答形式ではなかった。JSONでないボディ、または回答が含まれていないボディ。 |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflareのエンベロープが失敗、またはまだ完了していないジョブを報告した。 |
| `model-mismatch` | Jev 1.13以外のバージョンが回答した、または `custom` エンドポイントが回答したモデルを通知しなかった。 |
| `request-cut` | **障害ではありません。** Jevは回答しましたが、呼び出しの一部しか表示されなかったため、回答は何もクリアしませんでした。[Jevが回答したが、呼び出し全体に対してではなかった場合](#when-jev-answered-but-not-on-the-whole-call)を参照してください。 |

`failproofai jev status` は、`upstream-error`（回答にプロバイダー独自のエラーが含まれていた）や `config` など、より稀な理由も表示することがあり、名前を付けられない理由はすべて `other` として集計されます。

`request-cut` はこのテーブルに含まれています。`failproofai jev status` が他の理由と合わせて集計するためと、これもすべてのdenyをそのままにするためです。ただし、ここに挙げる唯一の理由として、プロバイダーについて何も示しません。リクエストは届き、Jevはそれに回答しました。上記のすべての行とは異なり、その回答は引き続き有効です。Jev自身のdenyまたは警告は、破棄されるのではなく、正規表現の結果に加えて適用されます。したがって、この理由が続く場合は、エンドポイントに問題があるのではなく、全体を送信するには大きすぎる呼び出しが評価者に届いているということです。クレジットの追加やURLの変更では解決しません。

## Jevが回答したが、呼び出し全体に対してではなかった場合

さらに2つのケースがあり、どちらもJevが回答できなかったわけではありません。どちらも、呼び出しの一部または会話の一部が1つのリクエストに収まりきったかどうかに関するものです。

**呼び出し自体の一部が収まらなかった。** ツール呼び出しは固定のバジェット内で送信されますが、過大なもの（非常に大きな `Write`、巨大なMCPボディ、上限まで詰め込まれたコマンド）は収まった部分のみで送信されます。Jevは引き続き回答し、その回答は引き続き有効です。Jev自身のdenyまたは警告は通常通り適用されます。ただし、呼び出しの一部に対する判定は、その呼び出し全体への判定ではないため、**何もクリアできません**。すべてのポリシーdenyは維持され、呼び出しは `request-cut` の理由でフォールバックとして記録されます。これが与える規則は: 呼び出しを大きくするとそのクリアを失うことになり、クリアを獲得することは決してできないということです。

**メッセージが収まらなかった。** 貼り付けた長いプロンプト、エージェントの最後のメッセージ、またはこの評価者自身のストアがすでに上限に達していたプロンプト。**何も変わりません**: 呼び出しは他のすべてと同様に判定、クリア、記録され、フォールバックとしてカウントされません。入力した内容の長さが判定を左右することはなく、カットによって同意が生まれることもありません。プロンプトがすでに上限に達した状態で届いた場合、「これをリクエストしなかった」はそこから導き出せる結論ではなくなります。

2つの違いは、テキストを書いたのが誰かです。呼び出しはエージェントのものであり、その長さが深刻さを引き算できるルールはエージェントが使えるルールになります。あなたのプロンプトはあなたのものであり、その長さをシグナルとして扱うことは、仕様書やスタックトレースを貼り付けることへのペナルティにしかなりません。

## マシンから送信されるデータ

Jevが評価する各ツール呼び出しについて、プロバイダーへ1つのリクエストが送信されます。内容:

- ツール呼び出し自体。APIキー、ベアラートークン、`KEY=` 代入などのシークレットはリダクトされます。
- 入力した最近のプロンプト。エージェントのハーネスが追加したテキストは除去されます。
- 最新のプロンプト前のエージェントの最後のメッセージ。エージェントが書いたものとしてラベル付けされます。
- パスがプロジェクト内にあるかどうかなど、ローカルで計算されたファクト（最初にレビューされた呼び出し時のセッション、[セッションにピン留めされた](/ja/reference/jev-intent#the-project-root)もの）、および現在のgitブランチ。

これは設定内のエンドポイントにのみ、あなたのキーの下で送信されます。

## 無効化する

```bash
failproofai jev remove
```

これにより `~/.failproofai/jev.json` が削除されます。次のツール呼び出しから、フックは以前と同様に正規表現ポリシーを実行します。`~/.failproofai/state/semantic/` 以下のセッションごとのストア（`sessions/` の記録済みプロンプト、`roots/` のプロジェクトルート）はそのまま残り、期限が来たら削除されます。Jevへの問い合わせを停止しながら設定を保持するには、代わりに `failproofai jev setup --mode off` を使用します。

## コマンドリファレンス

| コマンド | 結果 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 1つのコマンドで設定。プロバイダーはURLのホストから決定されます |
| `failproofai jev --url <url> --token <token>` | 同上。コマンドライン上にキーあり — 履歴とプロセスリストに表示されます |
| `failproofai jev setup --provider <kind> --key-stdin` | stdinにパイプされたキーから設定を書き込みます |
| `failproofai jev setup --provider <kind>` | 同上。マスクされたプロンプトでキーを要求します |
| `failproofai jev setup --key-from-env` | キーを保存しない。セッションごとに `FAILPROOFAI_JEV_API_KEY` を読み取ります |
| `failproofai jev setup --mode observe` | 保存済みキーを維持したままモードを切り替えます（`enforce`、`observe`、`off`） |
| `failproofai jev setup --model <id>` / `--base-url <url>` | モデルまたはAPIベースをオーバーライド。`default` でオーバーライドを解除 |
| `failproofai jev setup --timeout-ms <n>` | 呼び出しごとのバジェットを変更します |
| `failproofai jev status [--json]` | 設定、パーミッション、最近のアクティビティ。キーは表示しません |
| `failproofai jev test [--json]` | 1つのライブリクエスト: レイテンシーと回答したバージョン |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | そのエンドポイントの `/models` が報告するモデルID。設定済みのものをマーク |
| `failproofai jev remove` | 設定を削除。Jevはオフになります |
