これは、自己キーを使用した[Jevポリシー](/ja/policies/jev)のプロバイダーおよび設定リファレンスです。正規表現ポリシーは文字列にマッチします。`rm -rf build/` があなたの指示によるものか、`rm -rf ~` がプランに紛れ込んだものかを判断できないため、ある箇所では過剰にブロックし、別の箇所では不足するという問題が生じます。**Jev**（TypeSafeのクラシファイアー）は、実際にあなたが要求したことに照らしてツール呼び出しを読み取り、1回の高速なリクエストでyes/noの質問群に回答します。

Jevのエンドポイントとキーが設定されると、Failproof AIは各ツール呼び出しについて正規表現ポリシーと**並行して**Jevに問い合わせます。正規表現ポリシーの代替ではありません：

- **ハード**ポリシーのdenyは最終決定です。Jevはそれを解除できません。ポリシーは、明示的にreviewable（レビュー可能）とマークされ、それをカバーするJevチェックが指定されていない限り、すべてハードです。つまり、何も記載のないカスタム・パック・Cloudポリシーはハードであり、常時有効な自己保護ガードは常にハードです。
- **reviewable**ポリシーのdenyは解除される場合がありますが、Jevがそのポリシーがカバーする正確な懸念事項について問われ、「何もない」または「ユーザーがこれを要求した」と回答した場合に限ります。ユーザーが呼び出しを要求していないのに懸念事項が実際に存在すると判断したチェックは、denyを維持します。たとえそのチェック自体の判定がwarningのみであっても、ツール呼び出し前のwarningはエージェントを止めないためです。また、そのチェックがdenyを発行できるもの（シークレット露出、認証情報の流出、破壊的な削除など）である場合、その呼び出しに対して何も解除されません。
- ブロックは、その呼び出しがあなたが与えたタスクのステップであり、それ以上に到達しない場合、**warning**になることがあります：Jevは自身のdenyをwarningに緩和し、そのwarning（呼び出しの実際の問題点を示す）がポリシーのブロックを置き換えます。
- Jevは、正規表現では表現できない有害性に対して、独自にwarningまたはdenyを発行することもあります。
- Jevが回答できない場合（タイムアウト、レートリミット、サーバーエラー、クレジット不足、予期しないモデルバージョン）、その呼び出しはJevなしの場合と同様に正規表現の結果を受け取ります。
- Jevは、呼び出し全体を読み取り、正確な懸念事項について問われた場合を除き、ポリシー単独の場合よりも呼び出しを許可的にすることはありません。これに満たないもの（全体を送信するには大きすぎる呼び出し、疑わしいインジェクション）は、クリアランスを取り消し、すべてのdenyを維持します。

<Note>
Jevの設定がない場合、何も変わりません：フックは常通り正規表現ポリシーのみを実行します。設定が唯一のオプトイン手段です。
</Note>

<Tip>
FailproofAI Cloudをお使いですか？自分のキーは不要です：`jev:evaluate` を持つキーで接続されたマシンは、組織のプランでJevを使用できます。[Jev through FailproofAI Cloud](/ja/reference/jev-cloud)をご覧ください。
</Tip>

## 開始前の準備

**failproofai 1.0.8-beta.0以降**をインストールし、エージェントが稼働しているマシン上の[対応ハーネス](/ja/reference/harnesses)にフックをアタッチしてください。新しいマシンであれば[クイックスタート](/ja/start/quickstart)に、Cloudを使用しない場合は[ローカル強制適用の設定](/ja/start/setup#enforce-locally)に従ってください。インストール済みのCLIは `failproofai --version` で確認できます。

以下のプロバイダーからAPIキーを取得するか、互換性のあるエンドポイントとそのキーを用意してください。Jevは `PreToolUse` または `PermissionRequest` ゲートで名前付きツール呼び出しをレビューします。独自の判定を発行できますが、既存のポリシーのdenyを解除するには、[reviewable](/ja/policies/authority)とマークされたポリシーのインストールも必要です。ハードポリシーのdenyは最終決定のまま変わりません。

## プロバイダーを選択する

Jevには5つのルートからアクセスできます。いずれか1つのキーをご用意ください。

| プロバイダー | `--provider` | エンドポイント | デフォルトモデル | 備考 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 正確なバージョン固定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | リクエストはデータ保持なしのエンドポイントにのみルーティングされ、他のプロバイダーへのフォールバックはありません。`typesafe/jev-1.13-20260917` のような日付付きバージョンを報告します。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jevをエイリアスのみで識別するため、応答したバージョンは未検証として記録されます。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id` が必要です。キーあたり毎秒約6回の呼び出しを測定後、HTTP 429が発生しました。 |
| 独自エンドポイント | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafeのリクエストボディを受け付け、どのモデルが応答したかを報告するエンドポイント。`https` のみ。ローカルテスト用に、ループバックホスト（localhost、`127.0.0.1`、`::1`）への平文 `http` は許可されています。 |

<Warning>
Vercel独自のBring Your Own Key機能では、失敗したリクエストがVercelの認証情報でサイレントに再試行されます。すべての呼び出しを自分のTypeSafeアカウントのみに請求させ、そのアカウントのみが参照できるようにする必要がある場合は、TypeSafeを直接使用してください。
</Warning>

## 設定する

コマンド1つで、エンドポイントとキーを設定します。既存のポリシーが呼び出しの判断を行いながらJevの判定を確認できるよう、`observe` モードで開始してください：

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URLがプロバイダーを決定する

プロバイダーを明示的に指定する必要はありません：URLの**ホスト**がプロバイダーを示します。

| URLホスト | プロバイダー | 追加要件 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| その他のホスト | `custom` | — 指定したURLがベースURLになります |

これには3つの意味があります：

- **プロバイダー自身のAPIのURLはオーバーライドを書き込みません。** `--url https://api.typesafe.ai/v1` は `--provider typesafe` とまったく同じ設定を生成します。既知のプロバイダーで異なるパスまたはホストを指定した場合、`--base-url` が格納するのと同様にベースURLとして保存されます。
- **`--provider` は推論を上書きします。** これにより、独自のホストからプロバイダーのAPIを話すプロキシに到達できます：`--url https://jev-proxy.internal/v1 --provider typesafe`。
- **ホストと矛盾する `--provider` は拒否されます**（推測はしません）。`--provider openrouter --url https://api.typesafe.ai/v1` は何も書き込まず、理由を示します：2つの指定がキーの送信先について一致しません。同じ組み合わせは `jev setup --base-url` とダッシュボードのJev設定からも拒否されます。（`--provider custom` は矛盾ではありません。「このURLをそのまま扱う」という意味です。ただし、カスタムルートではアカウント固有のエンドポイントに到達できないCloudflareのホストは例外です。）

`--url` は設定ファイルの `baseUrl` と同様に検証され、同じ文言で拒否されます：`https`、またはいずれのモードでもループバックホスト（localhost、`127.0.0.1`、`::1`）への平文 `http`。リスク：ループバックサーバーを認証するものは何もないため、ダウン中に別のローカルプロセスがそのポートを取得して応答する可能性があります。ローカルテスト以外では `https` を使用してください。

### キー

`--key-stdin` でパイプするか、端末でコマンドを実行してマスクされたプロンプトでキーを貼り付けてください。どちらの方法でも、設定ファイルに直接書き込まれ、表示されることはありません。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` は同じフラグを受け取り、すべての完全な記法です：URLよりもプロバイダー名を指定したい場合は `setup --provider <kind>` を使用してください。

### `--token` とそのコスト

`--token <token>` はキーをコマンドライン上に置きます。これはマシンを設定する最速の方法ですが、設定ファイル以外にキーを残す唯一の書き方です：

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
コマンドライン引数はシェルの履歴ファイルに残り、コマンド実行中はプロセスリストに表示されます（あなたとして実行中のものから `/proc` 経由で読み取れます）。`--token` が使用されるたびに `setup` がこれを通知します。共有マシン上、録画されたセッション中、または履歴ファイルが同期される場所では `--key-stdin` を推奨します。この方法でキーを渡した場合、それが重要であれば回転させてください。
</Warning>

`--token`、`--key-stdin`、`--key-from-env` は相互に排他的です：1つのみ指定してください。

その後、キー、エンドポイント、応答したJevを確認するために小さなライブリクエストを送信してください：

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` は、タイムアウト後に回答が届いた場合（すべてのフックが `timeout` として正規表現にフォールバックする）やチェック質問に誤って回答した場合に、タイトルにその旨を示して終了コード1で終了します。

フックはツール呼び出しごとに設定を読み取るため、次の呼び出しから適用されます。デーモンの有無にかかわらず、再起動は不要です。

## 動作を確認する

```bash
failproofai jev status
failproofai jev status --json
```

`status` はプロバイダー、エンドポイント、モデル、モード、設定ファイルとそのパーミッションを表示します。キーは表示されません。その下に最近のアクティビティの要約が表示されます：Jevが評価した呼び出しの数、正規表現にフォールバックした頻度とその理由、レイテンシ、およびJevがクリアしたreviewableポリシー。

## 実際の呼び出しを検証する

フックされたエージェントで新しいセッションを開始します。ファイル読み取りツールで `README.md` を読んでタイトルを報告するよう指示してください。セッションにそのツール呼び出しが含まれていることを確認し、`failproofai jev status` を再度実行します：直近の評価済み呼び出しカウントが増加するはずです。[ローカルダッシュボード](/ja/reference/local-dashboard#review-policy-activity)の **Policies → Activity** を開いて、呼び出しのJev判定とモードを確認してください。observeモードでは、ポリシーの結果が引き続き呼び出しを決定します。クリアランスは、reviewableポリシーがマッチし、Jevがすべての指定チェックをクリアした場合にのみ表示されます。通常の読み取り操作にはクリアすべきポリシーがない場合があります。

## Observeモード

`enforce` がデフォルトです。Jevに判定を変更させずに観察したい場合は、`observe` に切り替えてください：Jevは引き続き問われ、その判定は記録されますが、強制適用されるのは正規表現の結果です。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` は設定（エンドポイントとキー）を保持し、Jevへの問い合わせを停止します：フックは設定なしの場合とまったく同様に正規表現ポリシーを実行し、`failproofai jev status` は「off (switched off)」と表示します。`--mode observe` または `--mode enforce` で元に戻せます。

同じプロバイダーで `setup` を再実行すると保存済みキーが維持されるため、モードの切り替えはフラグ1つで完了します。プロバイダーを切り替える場合は最初からやり直しとなり、新しいプロバイダーのキーが求められます。リクエストを別のホストに移動する `--base-url` も同様です：保存済みキーは指定されたホスト、またはそのプロバイダー自身のAPIにのみ送信されます。

## 設定ファイル

すべては `~/.failproofai/jev.json` という1つのファイルに保存され、`setup` によって書き込まれます：

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| フィールド | 意味 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare`、`custom` のいずれか。または `failproofai`（このファイルではなくFailproofAI Cloud接続からキーを取得します。[Jev through FailproofAI Cloud](/ja/reference/jev-cloud)を参照）。 |
| `apiKey` | `Authorization: Bearer <key>` として送信されます。 |
| `baseUrl` | `custom` では必須。それ以外ではプロバイダーのAPIベースを置き換えます。`https` である必要があります。`localhost` への平文 `http` は `mode: observe` の場合のみ許可されます：ローカルポートを認証するものは何もないため、プロキシがダウンしている間、エージェントを含むマシン上の任意のプロセスがその代わりに応答する可能性があります。 |
| `accountId` | Cloudflareのみ：32文字の小文字16進数。 |
| `model` | プロバイダーのデフォルトモデルIDを置き換えます。バージョン付きIDはJev 1.13を指定する必要があります。APIキーの形状をした値は拒否され（返答にも表示されません）、`--model` に貼り付けられたキーが保存・送信されることはありません。 |
| `timeoutMs` | 正規表現の結果を使用する前にツール呼び出しがJevを待つ時間。100〜10000、デフォルト3000。 |
| `mode` | `enforce`（デフォルト）、`observe`、または `off`（設定を保持しJevを実行しない）。 |

3つのルールでファイルが保護されています：

- **所有者のみ。** パーミッション `0600` で書き込まれます。他のユーザーまたはグループが読み取りまたは書き込みできるコピーは**拒否**され、`chmod 600 ~/.failproofai/jev.json` を実行するか `setup` を再実行するまで、フックは正規表現にフォールバックします。ディレクトリも確認されます：`~/.failproofai` は他の誰にも**書き込み可能**であってはなりません。ディレクトリへの書き込みアクセスがあれば、ファイル自体のパーミッションに関わらずファイルを置き換えられるためです。`setup` は書き込みビットが設定されていれば削除します。`failproofai jev status` は設定が拒否された際にその旨を示し、ファイルに記載されたエンドポイントを表示します：他の誰かが変更した可能性があるため、`chmod` の前にそれが自分のものであることを確認してください。そのようなファイルで `setup` を再実行すると、保存済みキーはプロバイダー自身のAPIにのみ送信されます。ファイルが示す他のエンドポイントには再度キーが必要です（`--key-stdin`）。または `--base-url default` でリクエストをプロバイダーに戻してください。
- **グローバルのみ。** リポジトリはJevを有効にしたり、別のエンドポイントを指定したり、モデルを選択したりできません：プロジェクト内の `.failproofai/jev.json` は無視され、プロバイダー、URL、モデル、アカウントIDはそのファイルからのみ読み取られます。リポジトリのエージェント設定が設定できる環境変数からは読み取られません。（`FAILPROOFAI_HOME` はこれを回避する方法ではありません：Jevのみをリダイレクトするのではなく、ポリシーを含むfailproofaiディレクトリ全体を移動します。）
- **キーのみ環境変数から取得できます。** ファイルに `apiKey` がない場合、`FAILPROOFAI_JEV_API_KEY` がそのセッション用に供給します（`setup --key-from-env` はそのようなファイルを書き込みます）。ファイルに保存されたキーを置き換えることはなく、ファイルなしにJevを有効にすることもできません。変数が設定されていない場合、そのシェルではJevは単純にオフになります：`failproofai jev status` はその旨を示し、終了コード0で終了し、設定はそのまま（`status --json` は `"reason": "no-env-key"` とともに `"status": "key-missing"` を報告します）。`failproofaid` デーモンはシェルの環境を参照しないため、`failproofai config` でセットアップされたマシンでは、キーをファイルに保存してください。

## どのJevが応答するか

Failproof AIの判定しきい値はJev 1.13で較正されているため、そのファミリーからの回答の場合のみ使用されます：`jev-1.13.x`、またはOpenRouterの `typesafe/jev-1.13-<date>`。プロバイダーがJevをエイリアスのみで識別し、バージョンを報告しない場合（Vercel、および報告しない場合のCloudflare）、回答は使用され、未検証として記録されます。`custom` エンドポイントは応答したモデルを報告する必要があります。唯一の例外は、設定したバージョンなしの `--model` 名で、エコーバックされた場合、同様に未検証として記録されます。他のバージョンを報告する回答、またはバージョンを報告しない `custom` 回答は使用されません：その呼び出しは理由 `model-mismatch` として正規表現にフォールバックします。

## Jevが回答できない場合

以下のいずれかが発生すると、その呼び出しは正規表現の結果にフォールバックし、理由とともに記録されます。`failproofai jev status` がそれらを合計します：

| 理由 | 原因 |
| --- | --- |
| `timeout` | `timeoutMs` 以内に回答なし。 |
| `http-429` | プロバイダーがキーをレートリミットした。 |
| `rate-limited` | Failproof AI自身のリミッターが送信前に呼び出しを保留した：毎秒5リクエスト、最大5のバーストで、プロバイダーが `429` を返した後はしばらく停止。プロバイダーではありません。 |
| `http-500`、`http-502`、`http-503`、… | プロバイダーでのサーバーエラー。正確なステータスが記録されます。 |
| `out-of-credits` | HTTP 402：プロバイダーアカウントにクレジットが残っていない。 |
| `provider-refused` | 「Model execution failed (Payment error)」というメッセージのCloudflareからのHTTP 402：プロバイダーがこのリクエストのモデル実行を拒否した。通常は請求の問題ではないため、クレジットを追加しても解決しません。 |
| `http-401`、`http-403` | キーが拒否された。 |
| `http-404` | `<base>/systemone` で何も提供されていないため、ベースURLが誤っています。`/systemone` がベースURLに追加され、すべてのプロバイダーはバージョンルートで提供します。`failproofai jev models` でエンドポイントが実際に提供するものを確認できます。 |
| `network` | エンドポイントに到達できなかった。 |
| `http-301`、`http-302`、`http-307`、`http-308` | エンドポイントがリダイレクトで応答した。リダイレクトは決して追跡されないため、回答は常に設定のURLからのみ来ます。`--base-url` を最終URLに設定してください。 |
| `malformed` | エンドポイントが応答したが、Jevの回答ではありません（JSONでないボディ、または回答が含まれていないボディ）。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflareのエンベロープが失敗、または完了していないジョブを報告した。 |
| `model-mismatch` | 1.13以外のJevバージョンが応答した、または `custom` エンドポイントが応答したモデルを示さなかった。 |
| `request-cut` | **障害ではありません。** Jevが応答しましたが、呼び出しの一部しか表示されなかったため、その回答は何もクリアしません。[Jevが応答したが、呼び出し全体に対してではない場合](#when-jev-answered-but-not-on-the-whole-call)を参照してください。 |

`failproofai jev status` は `upstream-error`（回答にプロバイダー自身のエラーが含まれていた）や `config` などのまれな理由も表示する場合があり、名前を付けられない理由はすべて `other` として合計します。

`request-cut` はこの表に含まれています。`failproofai jev status` が他と一緒に合計し、すべてのdenyが維持されるためです。ただし、ここでプロバイダーについて何も示さない唯一の理由でもあります：リクエストは届き、Jevはそれに回答しました。上記のすべての行とは異なり、その回答は依然としてカウントされます。Jev自身のdenyまたはwarningは破棄されるのではなく、正規表現の結果に加えて適用されます。そのため、これらが続く場合は、エンドポイントが不調なのではなく、全体を送信するには大きすぎる呼び出しが評価器に到達していることを意味します。クレジットの追加やURLの変更では解決しません。

## Jevが応答したが、呼び出し全体に対してではない場合

さらに2つのことが起こる可能性があり、どちらもJevが回答できないことによるものではありません。いずれも呼び出しまたは会話のどれだけが1つのリクエストに収まったかに関するものです。

**呼び出し自体の一部が収まらなかった。** ツール呼び出しは固定バジェット内で送信され、非常に大きなもの（非常に大きな `Write`、巨大なMCPボディ、上限まで埋め尽くされたコマンド）は収まった部分で送信されます。Jevはそれでも回答し、その回答はカウントされます：Jev自身のdenyまたはwarningは通常通り適用されます。ただし、呼び出しの一部に対する判定はその呼び出しへの判定ではないため、**クリア**はできません。そのため、すべてのポリシーdenyが維持され、呼び出しは理由 `request-cut` のフォールバックとして記録され、`failproofai jev status` が上記の理由と一緒に合計します。これが示すルール：呼び出しを大きくするとクリアランスが失われる可能性があり、クリアランスを得ることは決してできません。

**メッセージが収まらなかった。** 貼り付けた長いプロンプト、エージェントの最後のメッセージ、またはこの評価器自身のストアがすでに上限に達していたプロンプト。**何も変わりません**：呼び出しは他と同様に判定、クリア、記録され、フォールバックとしてカウントされません。入力した内容の長さは判定を決定しません。また、カットされたことが同意を製造することはありません：プロンプトがすでに上限に達した状態で届いた場合、「あなたはこれを要求しなかった」という結論はまったく導けなくなります。

2つの違いはテキストを誰が書いたかです。呼び出しはエージェントのものであり、その長さが重大性を減少させるルールはエージェントが使えるルールになります。プロンプトはあなたのものであり、その長さをシグナルとして扱うことは、仕様やスタックトレースを貼り付けることへのペナルティにしかなりません。

## マシンから何が送信されるか

Jevが評価する各ツール呼び出しについて、プロバイダーに1つのリクエストが送信され、以下を含みます：

- APIキー、ベアラートークン、`KEY=` の代入などのシークレットが編集されたツール呼び出し自体；
- エージェントのハーネスが追加したテキストを除いた、最近入力したプロンプト；
- エージェントが書いたとラベル付けされた、最新のプロンプト前のエージェントの最後のメッセージ；
- パスがプロジェクト内かどうかなどローカルで計算されたファクト（最初にレビューされた呼び出し時のセッションのプロジェクトルート、[セッションにピン留め](/ja/reference/jev-intent#the-project-root)）および現在のgitブランチ。

これは設定内のエンドポイントのみに、あなたのキーの下で送信されます。

## オフにする

```bash
failproofai jev remove
```

これは `~/.failproofai/jev.json` を削除します。次のツール呼び出しから、フックは以前と同様に正規表現ポリシーのみを実行します。`~/.failproofai/state/semantic/` 以下のセッションごとのストア（`sessions/` の記録済みプロンプト、`roots/` のプロジェクトルート）はそのまま残り、期限切れになります。Jevへの問い合わせを止めながら設定を保持するには、代わりに `failproofai jev setup --mode off` を使用してください。

## コマンドリファレンス

| コマンド | 結果 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 1コマンドで設定：プロバイダーはURLのホストから決定 |
| `failproofai jev --url <url> --token <token>` | 同上。キーはコマンドライン上に置かれ、シェル履歴とプロセスリストに残ります |
| `failproofai jev setup --provider <kind> --key-stdin` | stdinからパイプされたキーで設定を書き込む |
| `failproofai jev setup --provider <kind>` | 同上。マスクされたプロンプトでキーを求める |
| `failproofai jev setup --key-from-env` | キーを保存しない。セッションごとに `FAILPROOFAI_JEV_API_KEY` を読み取る |
| `failproofai jev setup --mode observe` | モードを切り替える（`enforce`、`observe`、または `off`）。保存済みキーは維持 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | モデルまたはAPIベースを上書き。`default` で上書きをクリア |
| `failproofai jev setup --timeout-ms <n>` | 呼び出しごとのバジェットを変更 |
| `failproofai jev status [--json]` | 設定、パーミッション、最近のアクティビティを表示。キーは非表示 |
| `failproofai jev test [--json]` | ライブリクエスト1件：レイテンシと応答したバージョン |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | そのエンドポイントの `/models` が報告するモデルID。設定済みのものをマーク |
| `failproofai jev remove` | 設定を削除。Jevはオフ |
