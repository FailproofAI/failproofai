これは[Jevポリシー](/ja/policies/jev)を自己キーで使用するためのプロバイダー・設定リファレンスです。正規表現ポリシーは文字列にマッチします。しかし、あなたが意図した`rm -rf build/`と、プランに紛れ込んだ`rm -rf ~`を区別することができないため、ある箇所では過剰にブロックし、別の箇所では不十分になります。**Jev**（TypeSafeのクラシファイアー）は、実際にあなたが求めた内容と照らし合わせてツール呼び出しを読み取り、1回の高速リクエストでその呼び出しに関する一連のyes/no質問に答えます。

Jevのエンドポイントとキーを設定すると、Failproof AIは各ツール呼び出しに対して正規表現ポリシーと**並行して**Jevに問い合わせます。正規表現ポリシーの代わりにではありません。

- **ハード**ポリシーのdenyは最終的なものです。Jevはそれを解除できません。ポリシーは、明示的にreviewable（レビュー可能）とマークされ、適用するJevチェックが指定されていない限り、すべてハードです。つまり、何も記載のないカスタム・パック・Cloudポリシーはハードであり、常時有効な自己保護ガードは常にハードです。
- **reviewable**ポリシーのdenyは解除される可能性がありますが、Jevがそのポリシーの対象となる懸念事項について問い合わせられ、「問題なし」または「ユーザーがこれを要求した」と回答した場合に限ります。ユーザーがその呼び出しを要求していないにもかかわらず、懸念事項が実在すると判断したチェックはdenyを維持します — そのチェック自身の判定が警告のみであっても同様です。なぜなら、ツール呼び出しの前において警告はエージェントを止めないからです。そして、そのチェックがdenyを発行できるもの（シークレットの漏洩、認証情報の流出、破壊的な削除など）である場合、その呼び出しは何も解除されません。
- ブロックは、その呼び出しがあなたが与えたタスクのステップであり、それ以上に踏み込まない場合、**警告**になることがあります。Jevは自身のdenyを警告に和らげ、その警告 — 呼び出しの実際の問題点を明示したもの — がポリシーのブロックに取って代わります。
- Jevは、正規表現では表現できない害に対して、独自に警告またはdenyを発行することもあります。
- Jevが回答できない場合（タイムアウト、レートリミット、サーバーエラー、クレジット不足、予期しないモデルバージョン）、その呼び出しはJevなしの場合とまったく同じ正規表現の結果を受け取ります。
- Jevは、呼び出し全体を読み取り、かつ対象の懸念事項について問い合わせを受けた場合を除いて、ポリシー単独よりも呼び出しを許可しません。それに満たない場合 — 全体を送信するには大きすぎる呼び出し、インジェクションの疑い — は、解除を取り消しすべてのdenyを維持します。

<Note>
Jevの設定がなければ何も変わりません。フックは従来どおり正規表現ポリシーを実行します。設定ファイルがオプトインのすべてです。
</Note>

<Tip>
FailproofAI Cloudをお使いですか？自分のキーは不要です。`jev:evaluate`を持つキーで接続されたマシンは、組織のプランでJevを利用できます。[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)をご覧ください。
</Tip>

## 始める前に

**failproofai 1.0.8-beta.0以降**をインストールし、エージェントが動作するマシンの[対応ハーネス](/ja/reference/harnesses)にフックをアタッチしてください。新しいマシンの場合は[クイックスタート](/ja/start/quickstart)に従い、Cloudを使用しない場合は[ローカル適用のセットアップ](/ja/start/setup#enforce-locally)を参照してください。インストール済みのCLIは`failproofai --version`で確認できます。

以下のプロバイダーからAPIキーを取得するか、互換性のあるエンドポイントとそのキーを用意してください。Jevは`PreToolUse`または`PermissionRequest`ゲートで名前付きツール呼び出しをレビューします。独自の判定を発行することもできますが、既存のポリシーdenyを解除するには、[reviewable](/ja/policies/authority)とマークされたポリシーがインストールされている必要があります。ハードポリシーのdenyは最終的なままです。

## プロバイダーの選択

Jevには5つのルートからアクセスできます。そのうちの1つのキーをご用意ください。

| プロバイダー | `--provider` | エンドポイント | デフォルトモデル | 備考 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 厳密なバージョン固定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | リクエストはデータ保持なしのエンドポイントにのみルーティングされ、他のプロバイダーへのフォールバックはありません。`typesafe/jev-1.13-20260917`のような日付付きバージョンを報告します。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jevをエイリアスのみで識別するため、応答したバージョンは未検証として記録されます。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id`が必要です。キーあたり毎秒約6回の呼び出しでHTTP 429が確認されました。 |
| 独自エンドポイント | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafeのリクエストボディを受け付け、どのモデルが応答したかを報告するエンドポイント。`https`のみ対応。ローカルテスト用に`localhost`、`127.0.0.1`、`::1`へのプレーン`http`は許可されます。 |

<Warning>
Vercelの独自のbring-your-own-key機能では、リクエストが失敗すると無音でVercelの認証情報を使って再試行されます。すべての呼び出しを自分のTypeSafeアカウントにのみ課金し、そこだけで参照する必要がある場合は、TypeSafeを直接使用してください。
</Warning>

## セットアップ

1つのコマンド、エンドポイント、キーで設定します。既存のポリシーが呼び出しの判断を維持しながらJevの判定を確認できるよう、`observe`モードで開始してください。

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URLがプロバイダーを決定する

プロバイダーを明示的に指定する必要はありません。URLの**ホスト**がプロバイダーを識別します。

| URLホスト | プロバイダー | 追加要件 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| その他のホスト | `custom` | — 指定したURLがベースURLになります |

ここから3つのことが導かれます。

- **プロバイダー自身のAPIのURLにはオーバーライドが書き込まれません。** `--url https://api.typesafe.ai/v1`は、`--provider typesafe`と同じ設定を生成します。既知のプロバイダーで異なるパスまたはホストを指定すると、`--base-url`が保存するのと同様にベースURLとして保存されます。
- **`--provider`は推論をオーバーライドできます。** これにより、自分のホストからプロバイダーのAPIを話すプロキシに接続できます。例：`--url https://jev-proxy.internal/v1 --provider typesafe`。
- **ホストと矛盾する`--provider`は拒否されます（推測されません）。** `--provider openrouter --url https://api.typesafe.ai/v1`は何も書き込まず、理由を説明します。2つの指定がキーの送信先について矛盾しているからです。同様の組み合わせは`jev setup --base-url`やダッシュボードのJev設定でも拒否されます。（`--provider custom`は矛盾ではありません — 「このURLをそのまま使う」という意味です — ただし、カスタムルートではアカウントごとのエンドポイントに到達できないCloudflareのホストを除きます。）

`--url`は設定ファイルの`baseUrl`と同様に検証され、同じメッセージで拒否されます。`https`、またはいずれのモードでもループバックホスト（`localhost`、`127.0.0.1`、`::1`）へのプレーン`http`。リスク：ループバックサーバーは認証されないため、停止中に別のローカルプロセスがそのポートを取得して応答する可能性があります。ローカルテスト以外では`https`を使用してください。

### キー

`--key-stdin`でパイプするか、それなしでターミナルでコマンドを実行してマスクされたプロンプトでキーを貼り付けてください。どちらの場合も設定ファイルに直接書き込まれ、表示されることはありません。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup`は同じフラグを受け付け、すべての詳細設定に使用できます。URLではなくプロバイダーを指定したい場合は`setup --provider <kind>`を使用します。

### `--token`とそのコスト

`--token <token>`でキーをコマンドラインに指定するのは、マシンを設定する最速の方法ですが、設定ファイル以外にキーが残る唯一の方法でもあります。

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
コマンドライン引数はその後シェルの履歴ファイルに残り、コマンド実行中はプロセスリストに表示されます — あなたとして実行されているすべてのものが`/proc`から読み取ることができます。`setup`は`--token`が使用されるたびにこれを警告します。共有マシン、記録されたセッション、または履歴ファイルが同期される場所では`--key-stdin`を使用してください。この方法で渡したキーが重要な場合はローテーションしてください。
</Warning>

`--token`、`--key-stdin`、`--key-from-env`は相互に排他的です。1つだけ指定してください。

その後、キー、エンドポイント、応答したJevを確認するために1つの小さなライブリクエストを送信します。

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`は、タイムアウト後に応答が届いた場合（すべてのフックが`timeout`として正規表現にフォールバックする）やチェック質問に誤答した場合に、タイトルにその旨を表示して終了コード1で終了します。

フックはツール呼び出しごとに設定を読み込むため、次の呼び出しから適用されます。デーモンの有無にかかわらず再起動は不要です。

## 動作状況の確認

```bash
failproofai jev status
failproofai jev status --json
```

`status`はプロバイダー、エンドポイント、モデル、モード、設定ファイルとそのパーミッションを表示し、キーは表示しません。その下に最近のアクティビティの要約が表示されます。Jevが評価した呼び出し数、正規表現にフォールバックした頻度とその理由、レイテンシー、解除されたreviewableポリシーが含まれます。

## 実際の呼び出しを確認する

フックされたエージェントで新しいセッションを開始し、`README.md`のファイル読み取りツールを使ってタイトルを報告するよう指示してください。セッションにそのツール呼び出しが含まれていることを確認し、`failproofai jev status`を再実行してください。最近評価された呼び出し数が増加しているはずです。[ローカルダッシュボード](/ja/reference/local-dashboard#review-policy-activity)の**Policies → Activity**を開き、呼び出しのJev判定とモードを確認してください。observeモードでは、ポリシーの結果が引き続き呼び出しを決定します。reviewableポリシーがマッチしてJevがすべての指定チェックを解除した場合のみ解除が表示されます。通常の読み取りには解除すべきポリシーがない場合があります。

## Observeモード

`enforce`がデフォルトです。Jevに判定を変えさせずに観察するには、`observe`に切り替えてください。Jevは引き続き問い合わせを受け、判定が記録されますが、適用されるのは正規表現の結果です。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`は設定（エンドポイントとキー）を保持しながらJevへの問い合わせを停止します。フックは設定なしの場合とまったく同じように正規表現ポリシーを実行し、`failproofai jev status`は「off (switched off)」と表示します。`--mode observe`または`--mode enforce`で元に戻せます。

同じプロバイダーで`setup`を再実行すると保存済みのキーが保持されるため、モードの切り替えはフラグ1つで済みます。プロバイダーを切り替えると最初からやり直しになり、そのプロバイダーのキーが求められます。リクエストを別のホストに移動する`--base-url`も同様です。保存済みのキーは指定されたホスト、またはそのプロバイダー自身のAPIにのみ送信されます。

## 設定ファイル

すべてが`setup`によって書き込まれる1つのファイル`~/.failproofai/jev.json`に保存されます。

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| フィールド | 意味 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare`または`custom` — あるいは`failproofai`（そのキーはこのファイルではなくFailproofAI Cloud接続から取得されます。[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)を参照）。 |
| `apiKey` | `Authorization: Bearer <key>`として送信されます。 |
| `baseUrl` | `custom`の場合は必須。それ以外の場合はプロバイダーのAPIベースを置き換えます。`https`必須。`localhost`への`http`は`mode: observe`でのみ許可されます。ローカルポートは認証されないため、プロキシが停止している間は、エージェント自身を含むマシン上の任意のプロセスが代わりに応答する可能性があります。 |
| `accountId` | Cloudflareのみ：32文字の小文字16進数。 |
| `model` | プロバイダーのデフォルトモデルIDを置き換えます。バージョン付きIDはJev 1.13を指定する必要があります。APIキーのような形式の値は拒否されます（エコーバックされません）。`--model`にキーを誤って貼り付けても保存・送信されることはありません。 |
| `timeoutMs` | ツール呼び出しがJevを待機してから正規表現結果を使用するまでの時間。100〜10000、デフォルト3000。 |
| `mode` | `enforce`（デフォルト）、`observe`、または`off`（設定を保持しJevを実行しない）。 |

3つのルールがファイルを保護します。

- **所有者のみ。** ファイルはパーミッション`0600`で書き込まれます。他のユーザーまたはグループが読み書きできるコピーは**拒否**され、`chmod 600 ~/.failproofai/jev.json`を実行するか`setup`を再実行するまで、フックは正規表現にフォールバックします。ディレクトリも確認されます。`~/.failproofai`は他の誰にも**書き込み可能**であってはなりません。ファイルを書き換えられると、ファイル自身のパーミッションにかかわらず置き換えられてしまうからです。`setup`はそのような書き込みビットを見つけた場合に削除します。`failproofai jev status`は設定が拒否された場合にその旨を表示し、ファイルに記載されているエンドポイントを表示します。他の誰かが変更した可能性があるため、`chmod`を実行する前にファイルが自分のものであることを確認してください。そのようなファイルで`setup`を再実行すると、保存済みのキーはプロバイダー自身のAPIにのみ送信されます。他のエンドポイントが記載されている場合はキーの再入力（`--key-stdin`）、またはリクエストをプロバイダーに戻すには`--base-url default`が必要です。
- **グローバルのみ。** リポジトリはJevを有効にしたり、別のエンドポイントに向けたり、モデルを選択したりできません。プロジェクト内の`.failproofai/jev.json`は無視され、プロバイダー、URL、モデル、アカウントIDはそのファイルからのみ読み取られます — リポジトリのエージェント設定が設定できる環境変数からは読み取られません。（`FAILPROOFAI_HOME`はこれを回避する手段ではありません。Jevだけをリダイレクトするのではなく、ポリシーを含むfailproofaiディレクトリ全体を移動します。）
- **キーだけは環境変数から取得できます。** ファイルに`apiKey`がない場合、`FAILPROOFAI_JEV_API_KEY`がそのセッションに提供します（`setup --key-from-env`でそのようなファイルを書き込みます）。ファイルが保持するキーを置き換えることはなく、ファイルなしでJevを有効にすることもできません。変数が設定されていない場合、そのシェルではJevは単純にオフになります。`failproofai jev status`はその旨を表示し、終了コード0で終了し、設定はそのまま（`status --json`は`"reason": "no-env-key"`とともに`"status": "key-missing"`を報告します）。`failproofaid`デーモンはシェルの環境を参照しないため、`failproofai config`でセットアップされたマシンでは、キーをファイルに保存してください。

## どのJevが応答するか

Failproof AIの判断閾値はJev 1.13で較正されているため、そのファミリーからの回答のみが使用されます。`jev-1.13.x`、またはOpenRouterの`typesafe/jev-1.13-<date>`です。プロバイダーがJevをエイリアスのみで識別し、バージョンを報告しない場合（Vercel、およびバージョンを報告しないCloudflare）、回答は使用されますが未検証として記録されます。`custom`エンドポイントは応答したモデルを報告する必要があります。唯一の例外は、設定した未バージョンの`--model`名がエコーバックされた場合で、同様に未検証として記録されます。他のバージョンを報告する回答、またはバージョンを報告しない`custom`の回答は使用されません。その呼び出しは`model-mismatch`という理由で正規表現にフォールバックします。

## Jevが回答できない場合

以下のいずれも、その呼び出しの正規表現結果にフォールバックし、`failproofai jev status`が合計する理由とともに記録されます。

| 理由 | 原因 |
| --- | --- |
| `timeout` | `timeoutMs`以内に回答なし。 |
| `http-429` | プロバイダーがキーをレートリミットした。 |
| `rate-limited` | Failproof AI自身のリミッターが送信前に呼び出しを保留した。毎秒5リクエスト、最大5のバーストで、プロバイダーが`429`を返した後はしばらく停止。プロバイダーではなくFailproof AI側。 |
| `http-500`、`http-502`、`http-503`など | プロバイダーでのサーバーエラー。正確なステータスが記録されます。 |
| `out-of-credits` | HTTP 402：プロバイダーアカウントにクレジットが残っていない。 |
| `provider-refused` | Cloudflareからの「Model execution failed (Payment error)」というHTTP 402：プロバイダーがこのリクエストでモデルの実行を拒否した。通常は課金の問題ではないため、クレジットを追加しても解決しません。 |
| `http-401`、`http-403` | キーが拒否された。 |
| `http-404` | `<base>/systemone`に何も配信されていないため、ベースURLが誤っています — `/systemone`はベースURLに付加され、すべてのプロバイダーはバージョンルートで配信しています。`failproofai jev models`でエンドポイントが配信しているものを確認できます。 |
| `network` | エンドポイントに到達できなかった。 |
| `http-301`、`http-302`、`http-307`、`http-308` | エンドポイントがリダイレクトで応答した。リダイレクトは決してフォローされないため、回答は常に設定内のURLからのみ取得されます。`--base-url`を最終URLに設定してください。 |
| `malformed` | エンドポイントが応答したが、Jevの回答ではありませんでした — JSONでないボディ、または回答が含まれていないもの。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflareのエンベロープが失敗、またはまだ完了していないジョブを報告した。 |
| `model-mismatch` | 1.13以外のJevバージョンが応答した、または`custom`エンドポイントが応答したモデルを報告しなかった。 |
| `request-cut` | **障害ではありません。** Jevは応答しましたが、呼び出しの一部しか表示されなかったため、その回答は何も解除しませんでした。[Jevが回答したが呼び出し全体に対してではなかった場合](#when-jev-answered-but-not-on-the-whole-call)を参照してください。 |

`failproofai jev status`は`upstream-error`（プロバイダー自身のエラーが回答に含まれていた）や`config`などのまれな理由も表示することがあり、名前を付けられない理由はすべて`other`として合計します。

`request-cut`がこの表に含まれているのは、`failproofai jev status`が他の理由とともに合計し、すべてのdenyが維持されるからです。ここにある理由の中で、プロバイダーについて何も示さない唯一の理由です。リクエストが届き、Jevが応答しました。上の他のすべての行とは異なり、その回答はまだカウントされます — Jev自身のdenyまたは警告は、破棄されるのではなく正規表現結果に加えて適用されます。そのため、これが続いている場合は、呼び出しが全体を送信するには大きすぎる状態でエバリュエーターに到達していることを意味します。エンドポイントに問題があるわけではなく、クレジットの追加やURLの変更では解決しません。

## Jevが回答したが呼び出し全体に対してではなかった場合

さらに2つのことが起こる可能性があり、どちらもJevが回答できないわけではありません。どちらも、呼び出しのどれだけの部分、または会話のどれだけの部分が1つのリクエストに収まったかに関するものです。

**呼び出し自体の一部が収まらなかった。** ツール呼び出しは固定バジェット内で送信されますが、非常に大きな呼び出し — 非常に大きな`Write`、巨大なMCPボディ、上限まで詰め込まれたコマンド — は収まった部分とともに送信されます。Jevはまだ回答し、その回答はまだカウントされます。Jev自身のdenyまたは警告は通常通り適用されます。できないのは何かを**解除**することです。なぜなら、呼び出しの一部に対する判定はその呼び出しに対する判定ではないからです。そのため、すべてのポリシーdenyが維持され、呼び出しは`request-cut`という理由でフォールバックとして記録されます。これから導かれるルール：呼び出しを大きくすると解除を失う可能性があり、解除を獲得することは決してできません。

**メッセージが収まらなかった。** 貼り付けた長いプロンプト、エージェントの最後のメッセージ、またはこのエバリュエーター自身のストアがすでに上限に達していたプロンプト。**何も変わりません。** 呼び出しは他と同様に判定、解除、記録され、フォールバックとしてカウントされません。入力した内容の長さが判定を決定することはなく、切り取りによって同意が生成されることもありません。プロンプトがすでに上限に達した状態で届いた場合、「あなたはこれを要求しなかった」という結論はそこから導けなくなります。

2つの違いは、誰がテキストを書いたかです。呼び出しはエージェントのものであり、長さによって深刻度を下げることができるルールはエージェントが利用できるルールになります。プロンプトはあなたのものであり、その長さをシグナルとして扱うことは、仕様書やスタックトレースを貼り付けることへの罰にしかなりません。

## マシンから送信されるもの

Jevが評価する各ツール呼び出しについて、プロバイダーに1つのリクエストが送信されます。その内容：

- ツール呼び出し自体（APIキー、ベアラートークン、`KEY=`の代入などのシークレットはリダクトされます）
- 入力した最近のプロンプト（エージェントのハーネスが追加したテキストを除く）
- 最新のプロンプトの前のエージェントの最後のメッセージ（エージェント作成とラベル付き）
- パスがプロジェクト内かどうかなどローカルで計算された事実 — 最初にレビューされた呼び出しのセッションにあったもの（[セッション用に固定されたプロジェクトルート](/ja/reference/jev-intent#the-project-root)）、および現在のgitブランチ

リクエストはあなたのキーの下で、設定内のエンドポイントにのみ送信されます。

## オフにする

```bash
failproofai jev remove
```

これにより`~/.failproofai/jev.json`が削除されます。次のツール呼び出しから、フックは以前と同様に正規表現ポリシーを実行します。`~/.failproofai/state/semantic/`以下のセッションごとのストア（`sessions/`に記録されたプロンプト、`roots/`にプロジェクトルート）はそのまま残り、期限切れになります。Jevへの問い合わせを止めながら設定を保持するには、代わりに`failproofai jev setup --mode off`を使用してください。

## コマンドリファレンス

| コマンド | 結果 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 1つのコマンドで設定。プロバイダーはURLのホストから決定されます |
| `failproofai jev --url <url> --token <token>` | 同様。コマンドラインにキーを指定 — 履歴とプロセスリストに表示されます |
| `failproofai jev setup --provider <kind> --key-stdin` | stdinでパイプされたキーから設定を書き込む |
| `failproofai jev setup --provider <kind>` | 同様。マスクされたプロンプトでキーを入力 |
| `failproofai jev setup --key-from-env` | キーを保存しない。セッションごとに`FAILPROOFAI_JEV_API_KEY`を読み取る |
| `failproofai jev setup --mode observe` | モードを切り替える（`enforce`、`observe`または`off`）。保存済みのキーは保持 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | モデルまたはAPIベースをオーバーライド。`default`でオーバーライドを解除 |
| `failproofai jev setup --timeout-ms <n>` | 呼び出しごとのバジェットを変更 |
| `failproofai jev status [--json]` | 設定、パーミッション、最近のアクティビティ。キーは表示されません |
| `failproofai jev test [--json]` | 1回のライブリクエスト：レイテンシーと応答したバージョン |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | そのエンドポイントの`/models`が報告するモデルID。設定済みのものにはマーク付き |
| `failproofai jev remove` | 設定を削除。Jevはオフになります |
