これは[Jevポリシー](/ja/policies/jev)を自分のキーで使用するためのプロバイダーおよび設定リファレンスです。正規表現ポリシーは文字列を照合します。しかし、あなたが意図して実行した`rm -rf build/`と、プランに紛れ込んだ`rm -rf ~`を区別することはできません。そのため、ある箇所では過剰にブロックし、別の箇所では不十分なブロックになってしまいます。TypeSafeの分類器である**Jev**は、あなたが実際に何を求めたかを踏まえてその呼び出しを読み取り、1回の高速リクエストで一連のyes/no形式の質問に答えます。

Jevのエンドポイントとキーを設定すると、Failproof AIは各ツール呼び出しについてJevに問い合わせますが、これは正規表現ポリシーの**代わりではなく、並行して**行われます。

- **ハード**ポリシーのdenyは最終的なものです。Jevはそれを解除できません。ポリシーは、明示的にreviewable（レビュー可能）とマークされ、対象とするJevチェックを指定していない限り、すべてハードです。つまり、何も記述していないカスタム・パック・クラウドポリシーはハードであり、常時有効な自己保護ガードは常にハードです。
- **reviewable**ポリシーのdenyは解除される場合がありますが、そのポリシーが対象とする懸念について正確にJevに問い合わせが行われ、Jevが「問題なし」または「ユーザーがこれを要求した」と回答した場合に限ります。ユーザーがその呼び出しを要求していない場合に懸念が実在すると判断されたチェックは、たとえ単独の判定が警告にとどまっても、denyを維持します。これはツール呼び出し前において警告がエージェントを停止させないためです。また、そのチェックがdenyを発行できるもの（シークレット露出、認証情報の漏洩、破壊的削除など）である場合、その呼び出しに対して何も解除されません。
- ブロックが**警告**に変わる場合があります。その呼び出しがあなたが与えたタスクのステップであり、それ以上の範囲に及ばない場合、JevはdenyをWarningに軟化させ、その警告（呼び出しの何が問題かを具体的に示す）がポリシーのブロックに置き換わります。
- Jevは正規表現では表現できない有害な動作に対して、単独でwarningまたはdenyを発行することもできます。
- Jevが回答できない場合（タイムアウト、レート制限、サーバーエラー、クレジット不足、想定外のモデルバージョン）、その呼び出しはJevなしの場合とまったく同じ正規表現の結果を受け取ります。
- Jevが呼び出し全体を読み取り、かつ対象の懸念について正確に問い合わせが行われていない限り、JevはあなたのポリシーよりもPermissive（許可的）な状態にすることはありません。条件を満たさない場合（呼び出しが大きすぎて全体を送信できない、インジェクションが疑われるなど）は、クリアランスが取り消され、すべてのdenyが維持されます。

<Note>
Jevの設定がなければ何も変わりません。フックは従来どおり正確に正規表現ポリシーを実行します。設定すること自体がオプトインです。
</Note>

<Tip>
FailproofAI Cloudをお使いですか？自分のキーは不要です。`jev:evaluate`権限を持つキーで接続されたマシンは、組織のプランでJevを利用できます。[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)をご覧ください。
</Tip>

## 始める前に

**failproofai 1.0.8-beta.0以降**をインストールし、エージェントが動作するマシン上の[対応ハーネス](/ja/reference/harnesses)にフックをアタッチしてください。新しいマシンの場合は[クイックスタート](/ja/start/quickstart)に従い、Cloudを使用しない場合は[ローカル適用のセットアップ](/ja/start/setup#enforce-locally)を参照してください。インストール済みのCLIは`failproofai --version`で確認できます。

以下のプロバイダーからAPIキーを取得するか、互換性のあるエンドポイントとそのキーを用意してください。Jevは`PreToolUse`または`PermissionRequest`ゲートで名前付きツール呼び出しをレビューします。独自の判定を発行することもできますが、既存のポリシーdenyを解除するには、[reviewable](/ja/policies/authority)としてマークされたポリシーがインストールされている必要があります。ハードポリシーのdenyは最終的なままです。

## プロバイダーを選ぶ

Jevは5つのルートで利用できます。そのうちの1つのキーを用意してください。

| プロバイダー | `--provider` | エンドポイント | デフォルトモデル | 備考 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 厳密なバージョン固定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | リクエストはデータ保持なしのエンドポイントにのみルーティングされ、他のプロバイダーへのフォールバックはありません。`typesafe/jev-1.13-20260917`のような日付入りのバージョンとして報告されます。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jevをエイリアスのみで識別するため、応答したバージョンは未検証として記録されます。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id`が必要です。キーあたり1秒あたり約6リクエストで、HTTP 429が発生することが確認されています。 |
| 独自エンドポイント | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafeのリクエストボディを受け付け、どのモデルが応答したかを報告するエンドポイント。`https`のみ。ローカルテスト用にはループバックホスト（`localhost`、`127.0.0.1`、`::1`）への平文`http`も受け付けられます。 |

<Warning>
Vercelの独自ブリング・ユア・オウン・キー機能では、リクエストが失敗すると無音でVercelの認証情報を使って再試行されます。すべての呼び出しを自分のTypeSafeアカウントにのみ課金・記録したい場合は、TypeSafeを直接使用してください。
</Warning>

## セットアップ

1つのコマンドで、エンドポイントとキーを設定します。既存のポリシーが引き続き呼び出しを判断しながらJevの判定を検査できるよう、まず`observe`モードで開始しましょう。

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URLがプロバイダーを決定する

プロバイダーを明示的に指定する必要はありません。URLの**ホスト**がプロバイダーを識別します。

| URLホスト | プロバイダー | その他の必要事項 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| その他のホスト | `custom` | — 指定したURLがベースURLとなります |

これから3つのことが導かれます。

- **プロバイダー自身のAPIのURLを指定した場合、オーバーライドは書き込まれません。** `--url https://api.typesafe.ai/v1`は`--provider typesafe`と同じ設定を生成します。既知のプロバイダーで異なるパスまたはホストを指定すると、`--base-url`が格納するのと同様に、ベースURLとして保存されます。
- **`--provider`は推論をオーバーライドします。** これにより、独自のホストからプロバイダーのAPIを話すプロキシに接続できます（例：`--url https://jev-proxy.internal/v1 --provider typesafe`）。
- **ホストと矛盾する`--provider`は拒否されます。** `--provider openrouter --url https://api.typesafe.ai/v1`は何も書き込まず、理由を説明します。2つの指定がキーの送信先について矛盾しているからです。同様の組み合わせは`jev setup --base-url`やダッシュボードのJev設定からも拒否されます（`--provider custom`は矛盾ではありません。これは「このURLをそのまま使う」という意味です。ただし、Cloudflareのホストは例外で、カスタムルートではアカウント単位のエンドポイントに到達できません）。

`--url`は設定ファイルの`baseUrl`と同じ検証が行われ、同じメッセージで拒否されます。`https`、またはいずれのモードでもループバックホスト（`localhost`、`127.0.0.1`、`::1`）への平文`http`が受け付けられます。リスク：ループバックサーバーは認証されないため、停止中に別のローカルプロセスがそのポートを取得して応答する可能性があります。ローカルテスト以外では`https`を使用してください。

### キー

`--key-stdin`でパイプ入力するか、ターミナルでコマンドをそれなしで実行してマスクされたプロンプトでキーを貼り付けてください。どちらの方法でもキーは設定ファイルに直接保存され、表示されることはありません。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup`は同じフラグを受け付け、すべての詳細な設定が可能です。URLではなくプロバイダーを指定したい場合は`setup --provider <kind>`を使用してください。

### `--token`とそのコスト

`--token <token>`はコマンドラインにキーを配置します。これはマシンを設定する最も速い方法ですが、設定ファイル以外の場所にキーが残る唯一の書き方です。

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
コマンドライン引数はシェルの履歴ファイルに残り、コマンド実行中はプロセスリストに表示されます。`/proc`からあなたと同じユーザーで実行しているプロセスが読み取れます。`--token`を使用するたびに`setup`がその旨を通知します。共有マシン、記録されたセッション、または履歴ファイルが同期される環境では`--key-stdin`を優先してください。この方法でキーを渡した場合は、必要に応じてローテーションしてください。
</Warning>

`--token`、`--key-stdin`、`--key-from-env`は相互に排他的です。1つだけ指定してください。

その後、キー、エンドポイント、および応答したJevを確認するために小さなライブリクエストを送信します。

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`は、タイムアウト後に応答が届いた場合（すべてのフックが`timeout`として正規表現にフォールバックする）やチェック質問への回答が誤っている場合、タイトルにその旨を示して終了コード1で終了します。

フックはツール呼び出しのたびに設定を読み込むため、次の呼び出しから反映されます。デーモンの有無にかかわらず、再起動は不要です。

## 動作状況を確認する

```bash
failproofai jev status
failproofai jev status --json
```

`status`はプロバイダー、エンドポイント、モデル、モード、設定ファイルとそのパーミッションを表示し、キーは表示しません。その下に最近のアクティビティが要約されます。Jevが評価した呼び出しの数、正規表現にフォールバックした頻度とその理由、レイテンシ、およびJevがクリアしたreviewableポリシーが表示されます。

## 実際の呼び出しを検証する

フックが付いたエージェントで新しいセッションを開始します。ファイル読み取りツールで`README.md`を読み取りタイトルを報告するよう指示してください。セッションにそのツール呼び出しが含まれていることを確認してから、`failproofai jev status`を再度実行します。最近の評価済み呼び出しカウントが増加しているはずです。[ローカルダッシュボード](/ja/reference/local-dashboard#review-policy-activity)の**Policies → Activity**を開いて、呼び出しのJev判定とモードを確認してください。observeモードでは、ポリシーの結果が引き続き呼び出しを決定します。クリアランスは、reviewableポリシーがマッチし、Jevが指定されたすべてのチェックをクリアした場合にのみ表示されます。通常の読み取り操作にはクリアすべきポリシーがない場合があります。

## Observeモード

デフォルトは`enforce`です。Jevの判定を変更せずに監視するには、`observe`に切り替えます。JevはまだリクエストされてI判定が記録されますが、適用されるのは正規表現の結果です。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`は設定（エンドポイントとキー）を保持しながらJevへの問い合わせを停止します。フックは設定なしの場合とまったく同じように正規表現ポリシーを実行し、`failproofai jev status`は「off (switched off)」と表示します。`--mode observe`または`--mode enforce`で再度切り替えられます。

同じプロバイダーで`setup`を再実行すると保存済みのキーが保持されるため、モードの切り替えはフラグ1つで済みます。プロバイダーを切り替えると最初からやり直しとなり、そのプロバイダーのキーが求められます。リクエストを別のホストに移動する`--base-url`も同様です。保存済みのキーは、指定されたホスト、またはそのプロバイダー自身のAPIにのみ送信されます。

## 設定ファイル

すべてのデータは`setup`によって書き込まれる1つのファイル`~/.failproofai/jev.json`に保存されます。

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| フィールド | 意味 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare`、`custom`、または`failproofai`（このファイルではなくFailproofAI Cloud接続からキーを取得する。[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)を参照）。 |
| `apiKey` | `Authorization: Bearer <key>`として送信されます。 |
| `baseUrl` | `custom`の場合は必須。それ以外の場合はプロバイダーのAPIベースを置き換えます。`https`必須。`localhost`への平文`http`は`mode: observe`の場合のみ受け付けられます。ローカルポートは認証されないため、プロキシが停止している間は、エージェント自身を含むマシン上の任意のプロセスが代わりに応答する可能性があります。 |
| `accountId` | Cloudflareのみ: 32文字の小文字16進数。 |
| `model` | プロバイダーのデフォルトモデルIDを置き換えます。バージョン付きIDはJev 1.13を指定する必要があります。APIキーの形式をした値は拒否され（返答にも含まれません）、`--model`に貼り付けられたキーは保存も送信もされません。 |
| `timeoutMs` | ツール呼び出しがJevを待つ時間。正規表現結果を使用するまでの時間。100〜10000、デフォルトは3000。 |
| `mode` | `enforce`（デフォルト）、`observe`、または`off`（設定を保持しJevを実行しない）。 |

3つのルールが設定ファイルを保護します。

- **オーナーのみ。** パーミッション`0600`で書き込まれます。他のユーザーまたはグループが読み書きできるコピーは**拒否**され、`chmod 600 ~/.failproofai/jev.json`を実行するか`setup`を再実行するまでフックは正規表現にフォールバックします。ディレクトリも確認されます。`~/.failproofai`は他のユーザーが**書き込み可能**であってはなりません。ファイル自体のパーミッションに関係なく、そこに書き込めるユーザーはファイルを置き換えられるからです。`setup`は書き込みビットを見つけた場合に削除します。`failproofai jev status`は設定が拒否された場合にその旨を表示し、ファイルに記載されたエンドポイントを示します。他のユーザーが変更した可能性があるため、`chmod`を実行する前に自分のファイルであることを確認してください。このようなファイルで`setup`を再実行すると、保存済みのキーはプロバイダー自身のAPIにのみ引き継がれます。それ以外のエンドポイントが記載されている場合はキーの再入力が必要です（`--key-stdin`）、またはプロバイダーへのリクエストに戻す場合は`--base-url default`を使用します。
- **グローバルのみ。** リポジトリはJevを有効にしたり、別のエンドポイントに向けたり、モデルを選択したりすることはできません。プロジェクト内の`.failproofai/jev.json`は無視され、プロバイダー、URL、モデル、アカウントIDはそのファイルからのみ読み込まれます。リポジトリのエージェント設定が設定できる環境変数からは読み込まれません（`FAILPROOFAI_HOME`もこれを回避する手段ではありません。これはJevのみのリダイレクトではなく、ポリシーを含むfailproofaiディレクトリ全体を移動します）。
- **キーのみ環境変数から取得可能。** ファイルに`apiKey`がない場合、`FAILPROOFAI_JEV_API_KEY`がそのセッションのキーとして使用されます（`setup --key-from-env`でそのようなファイルを書き込みます）。ファイルに保存されているキーを置き換えることはなく、ファイルなしでJevを有効にすることもできません。変数が設定されていない場合、そのシェルではJevは単純にオフになります。`failproofai jev status`はその旨を表示し、終了コード0で終了し、設定はそのままです（`status --json`は`"reason": "no-env-key"`とともに`"status": "key-missing"`を報告します）。`failproofaid`デーモンはシェルの環境変数を参照しないため、`failproofai config`でセットアップしたマシンではキーをファイルに保存してください。

## どのJevが応答するか

Failproof AIの判定しきい値はJev 1.13を基準に調整されているため、そのファミリー（`jev-1.13.x`、またはOpenRouterの`typesafe/jev-1.13-<date>`）からの回答のみが使用されます。プロバイダーがJevをエイリアスのみで識別し、バージョンを報告しない場合（Vercel、およびバージョンを通知しない場合のCloudflare）、回答は使用されますが未検証として記録されます。`custom`エンドポイントは応答したモデルを報告する必要があります。唯一の例外は、設定したバージョンなしの`--model`名で、エコーバックされた場合は同様に未検証として記録されます。別のバージョンを報告する回答、またはバージョンを報告しない`custom`の回答は使用されません。その呼び出しは`model-mismatch`という理由で正規表現にフォールバックします。

## Jevが回答できない場合

以下のそれぞれの場合、その呼び出しの正規表現結果にフォールバックし、理由とともに記録されます。`failproofai jev status`がこれを集計します。

| 理由 | 原因 |
| --- | --- |
| `timeout` | `timeoutMs`内に回答なし。 |
| `http-429` | プロバイダーがキーをレート制限した。 |
| `rate-limited` | Failproof AI自身のリミッターが送信前に呼び出しを保留した。毎秒5リクエスト、最大5バーストまで、プロバイダーが`429`を返した後は一時的に停止。プロバイダー側ではない。 |
| `http-500`、`http-502`、`http-503`、… | プロバイダーでのサーバーエラー。正確なステータスが記録されます。 |
| `out-of-credits` | HTTP 402：プロバイダーアカウントのクレジットが残っていない。 |
| `provider-refused` | Cloudflareからの「Model execution failed (Payment error)」というHTTP 402：プロバイダーがこのリクエストのモデル実行を拒否した。通常は課金の問題ではないため、クレジットを追加しても解決しません。 |
| `http-401`、`http-403` | キーが拒否された。 |
| `http-404` | `<base>/systemone`に何もサービスされていないため、ベースURLが誤っています。`/systemone`はベースURLに付加されるため、各プロバイダーはバージョンルートに配置しています。`failproofai jev models`でエンドポイントが実際に何を提供しているか確認できます。 |
| `network` | エンドポイントに到達できなかった。 |
| `http-301`、`http-302`、`http-307`、`http-308` | エンドポイントがリダイレクトで応答した。リダイレクトは決して辿らないため、回答は常に設定内のURLからのみ来ます。`--base-url`を最終URLに設定してください。 |
| `malformed` | エンドポイントが応答したが、JevのAnswerではありませんでした。JSONでないボディ、または回答が含まれていないボディ。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflareのエンベロープが失敗、またはまだ完了していないジョブを報告した。 |
| `model-mismatch` | Jev 1.13以外のバージョンが応答した、または`custom`エンドポイントがどのモデルが応答したかを報告しなかった。 |
| `request-cut` | **障害ではありません。** Jevが応答しましたが、呼び出しの一部しか表示されなかったため、その回答では何もクリアされませんでした。[Jevが応答したが呼び出し全体を対象としていない場合](#when-jev-answered-but-not-on-the-whole-call)を参照してください。 |

`failproofai jev status`はさらにいくつかの稀な理由（`upstream-error`（回答にプロバイダー自身のエラーが含まれていた）や`config`など）を表示することがあり、名前を付けられない理由はすべて`other`として集計されます。

`request-cut`がこの表に含まれているのは、`failproofai jev status`が他の理由とともに集計し、またこれもすべてのdenyを維持するからです。しかし、プロバイダーに関して何も示していない唯一の理由でもあります。リクエストは届いてJevが回答しました。上記のすべての行とは異なり、その回答は依然としてカウントされます。Jev自身のdenyまたは警告は、破棄されるのではなく正規表現結果に加えて適用されます。したがって、`request-cut`が続く場合は、エンドポイントが不調なのではなく、全体を送信するには大きすぎる呼び出しが評価器に届いているということです。クレジットの追加やURLの変更では改善しません。

## Jevが応答したが呼び出し全体を対象としていない場合

さらに2つの状況が発生する可能性があり、どちらもJevの回答失敗ではありません。いずれも、呼び出しまたは会話のどれだけがひとつのリクエストに収まったかに関係します。

**呼び出し自体の一部が収まらなかった。** ツール呼び出しは固定バジェット内で送信されますが、非常に大きなもの（非常に大きな`Write`、巨大なMCPボディ、上限までパディングされたコマンド）は収まった部分のみで送信されます。Jevはまだ回答し、その回答はカウントされます。Jev自身のdenyや警告は通常通り適用されます。しかし**クリア**することはできません。呼び出しの一部に対する判定はその呼び出し全体の判定ではないからです。そのため、すべてのポリシーdenyが維持され、呼び出しは`request-cut`という理由でフォールバックとして記録されます。これが意味するルール：呼び出しを大きくするとクリアランスを失う可能性があり、クリアランスを得ることは決してできません。

**メッセージが収まらなかった。** 長いプロンプト、エージェントの最後のメッセージ、またはこの評価器自身のストアがすでに上限に達したプロンプト。**何も変わりません**：呼び出しは他のものとまったく同じように判定、クリア、記録され、フォールバックとしてカウントされません。入力した内容の長さが判定を決定することはなく、切り捨てによって同意が作り出されることもありません。プロンプトがすでに上限に達した状態で届いた場合、「あなたはこれを要求しなかった」という結論はそもそも導き出せない状態になります。

両者の境界線は誰がテキストを書いたかです。呼び出しはエージェントのものであり、長さが重要度を軽減できるルールはエージェントが悪用できるものになります。プロンプトはあなたのものであり、その長さをシグナルとして扱うことは、仕様書やスタックトレースを貼り付けることへの罰にしかなりません。

## マシンから何が送信されるか

Jevが評価する各ツール呼び出しについて、プロバイダーに1つのリクエストが送信されます。その内容は以下の通りです。

- ツール呼び出し自体（APIキー、ベアラートークン、`KEY=`代入などのシークレットはリダクトされます）
- あなたが入力した最近のプロンプト（エージェントのハーネスが追加したテキストは除去されます）
- 最新のプロンプト前のエージェントの最後のメッセージ（エージェントが書いたものとしてラベル付け）
- パスがプロジェクト内かどうかなど、ローカルで計算された情報（最初のレビュー済み呼び出し時のセッションのプロジェクトルート、[セッション中固定](/ja/reference/jev-intent#the-project-root)）および現在のgitブランチ

これらはあなたの設定内のエンドポイントにのみ、あなたのキーの下で送信されます。

## 無効にする

```bash
failproofai jev remove
```

これにより`~/.failproofai/jev.json`が削除されます。次のツール呼び出し以降、フックは以前と同様に正規表現ポリシーを実行します。`~/.failproofai/state/semantic/`以下のセッションごとのストア（`sessions/`に記録されたプロンプト、`roots/`にプロジェクトルート）はそのまま残り、自然に期限切れになります。設定を保持しながらJevへの問い合わせを停止するには、代わりに`failproofai jev setup --mode off`を使用してください。

## コマンドリファレンス

| コマンド | 結果 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 1つのコマンドで設定。プロバイダーはURLのホストから決定される |
| `failproofai jev --url <url> --token <token>` | 同上。コマンドラインにキーを指定（履歴とプロセスリストに残る） |
| `failproofai jev setup --provider <kind> --key-stdin` | stdinからパイプされたキーで設定を書き込む |
| `failproofai jev setup --provider <kind>` | 同上。マスクされたプロンプトでキーを入力 |
| `failproofai jev setup --key-from-env` | キーを保存しない。セッションごとに`FAILPROOFAI_JEV_API_KEY`を読み込む |
| `failproofai jev setup --mode observe` | 保存済みのキーを維持しながらモードを切り替え（`enforce`、`observe`、`off`） |
| `failproofai jev setup --model <id>` / `--base-url <url>` | モデルまたはAPIベースをオーバーライド。`default`でオーバーライドをクリア |
| `failproofai jev setup --timeout-ms <n>` | 呼び出しごとのバジェットを変更 |
| `failproofai jev status [--json]` | 設定、パーミッション、最近のアクティビティ（キーは表示しない） |
| `failproofai jev test [--json]` | 1回のライブリクエスト：レイテンシと応答したバージョン |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | そのエンドポイントの`/models`が報告するモデルID（設定済みのものをマーク） |
| `failproofai jev remove` | 設定を削除。Jevをオフにする |
