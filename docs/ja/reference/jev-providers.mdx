これは、自分のキーを使用した[Jevポリシー](/ja/policies/jev)のプロバイダーおよび設定リファレンスです。正規表現ポリシーは文字列をマッチングします。あなたが要求した`rm -rf build/`と、計画に紛れ込んだ`rm -rf ~`を区別することができないため、ある箇所では過剰にブロックし、別の箇所では不十分になります。**Jev**はTypeSafeのクラシファイアで、実際にあなたが要求した内容に照らしてツール呼び出しを読み取り、1回の高速リクエストでYes/No形式の質問群に回答します。

Jevのエンドポイントとキーが設定されると、Failproof AIは各ツール呼び出しについて、正規表現ポリシーを置き換えるのではなく、**並行して**Jevに問い合わせます：

- **hard**ポリシーのdenyは最終的です。Jevはそれを解除できません。ポリシーはreviewableと明示的にマークされ、カバーするJevチェックが指定されていない限り、すべてhardです。したがって、何も記載されていないカスタム・パック・Cloudポリシーはhardであり、常時有効な自己保護ガードは常にhardです。
- **reviewable**ポリシーのdenyは解除される場合がありますが、そのポリシーがカバーする具体的な懸念についてJevが問い合わせられ、「ここには何もない」または「ユーザーがこれを要求した」と回答した場合に限ります。ユーザーがその呼び出しを要求していない場合に懸念が実在すると判断したチェックは、denyを維持します。たとえそのチェック自体の判定が警告にすぎなくても同様です。ツール呼び出しの前の段階では、警告はエージェントを止めないからです。そして、そのチェックがdenyを発行できるもの（シークレットの漏洩、認証情報の流出、破壊的な削除など）である場合、その呼び出しに対して何も解除されません。
- ブロックは、その呼び出しがあなたの与えたタスクのステップであり、それ以上の範囲に達しない場合、**警告**になることがあります：JevはそのdenyをWarningに軟化させ、その警告——呼び出しの実際の問題点を示す——がポリシーのブロックに置き換わります。
- Jevは正規表現では表現できない有害行為に対して、独自にwarningまたはdenyを発行することもあります。
- Jevが回答できない場合（タイムアウト、レート制限、サーバーエラー、クレジット不足、予期しないモデルバージョン）、その呼び出しはJevなしの場合とまったく同じ正規表現の結果を受け取ります。
- Jevは、呼び出し全体を読み取り、具体的な懸念について問い合わせられない限り、ポリシー単独の結果より呼び出しを許可側に変えることはありません。それに満たないもの——全体を送信するには大きすぎる呼び出し、疑わしいインジェクション——は解除を取り消し、すべてのdenyを維持します。

<Note>
Jev設定がない場合、何も変わりません：フックはこれまでどおり正規表現ポリシーを実行します。設定がオプトインのすべてです。
</Note>

<Tip>
FailproofAI Cloudをお使いですか？自分のキーは不要です：`jev:evaluate`を持つキーで接続されたマシンは、組織のプランでJevを使用できます。[Jev through FailproofAI Cloud](/ja/reference/jev-cloud)をご覧ください。
</Tip>

## 開始前の準備

**failproofai 1.0.8-beta.0以降**をインストールし、エージェントが動作するマシンの[対応ハーネス](/ja/reference/harnesses)にフックを接続してください。新しいマシンの場合は[クイックスタート](/ja/start/quickstart)に従い、Cloudを使用しない場合は[ローカルエンフォースメントの設定](/ja/start/setup#enforce-locally)に従ってください。インストール済みのCLIは`failproofai --version`で確認できます。

以下のプロバイダーからAPIキーを取得するか、互換エンドポイントとそのキーを用意してください。Jevは`PreToolUse`または`PermissionRequest`ゲートで名前付きツール呼び出しをレビューします。独自の判定を発行できますが、既存のポリシーdenyを解除するには[reviewable](/ja/policies/authority)とマークされたポリシーがインストールされている必要があります。Hardポリシーのdenyは最終的なままです。

## プロバイダーを選択する

Jevは5つのルートで利用できます。そのうちいずれか1つのキーを用意してください。

| プロバイダー | `--provider` | エンドポイント | デフォルトモデル | 備考 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | バージョンを厳密に指定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | リクエストはデータ保持なしのエンドポイントにのみルーティングされ、他のプロバイダーへのフォールバックなし。`typesafe/jev-1.13-20260917`のような日付付きバージョンを報告。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jevをエイリアスのみで識別するため、応答したバージョンは未検証として記録。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id`が必要。キーあたり毎秒約6回の呼び出しでHTTP 429が発生することが確認済み。 |
| 独自エンドポイント | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafeのリクエストボディを受け付け、どのモデルが回答したかを報告するエンドポイント。`https`のみ。ローカルテスト用にループバックホスト（localhost、`127.0.0.1`、`::1`）への平文`http`は許可。 |

<Warning>
Vercel独自のBring Your Own Key機能では、失敗したリクエストがVercelの認証情報でサイレントに再試行されます。すべての呼び出しを自分のTypeSafeアカウントのみに請求・表示させる必要がある場合は、TypeSafeを直接使用してください。
</Warning>

## 設定する

コマンド1つで、エンドポイントとキーを設定します。既存のポリシーが呼び出しを判定しながらJevの判定を確認できるよう、`observe`モードで開始しましょう：

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URLがプロバイダーを決定する

プロバイダーを明示的に指定する必要はありません：URLの**ホスト**がプロバイダーを決定します。

| URLホスト | プロバイダー | 追加要件 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| その他のホスト | `custom` | — 指定したURLがベースURLになる |

これから3つのことが導かれます：

- **プロバイダー自身のAPIのURLは上書きを書き込みません。** `--url https://api.typesafe.ai/v1`は`--provider typesafe`と全く同じ設定を生成します。既知のプロバイダーで異なるパスまたはホストを指定すると、`--base-url`が保存するのと同様にベースURLとして保存されます。
- **`--provider`は推論を上書きします。** これにより、自分のホストからプロバイダーのAPIを話すプロキシに到達できます：`--url https://jev-proxy.internal/v1 --provider typesafe`。
- **ホストと矛盾する`--provider`は拒否されます。** `--provider openrouter --url https://api.typesafe.ai/v1`は何も書き込まず、理由を説明します：2つの指定が、キーの送信先について不一致を起こしているからです。同じ組み合わせは`jev setup --base-url`やダッシュボードのJev設定からも拒否されます。（`--provider custom`は矛盾ではありません——「このURLをそのまま扱う」という意味です——Cloudflareのホストは例外で、そのアカウント固有のエンドポイントにはcustomルートで到達できません。）

`--url`はconfigファイルの`baseUrl`と全く同じバリデーションが行われ、同じメッセージで拒否されます：`https`、またはいずれのモードでもループバックホスト（localhost、`127.0.0.1`、`::1`）への平文`http`。リスク：ループバックサーバーを認証するものはないため、停止中に別のローカルプロセスがそのポートを取得して応答する可能性があります；ローカルテスト以外では`https`を使用してください。

### キー

`--key-stdin`でパイプ入力するか、端末でコマンドを実行してマスクされたプロンプトでキーを貼り付けます。どちらの場合もconfigファイルに直接書き込まれ、表示されることはありません。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup`は同じフラグを受け取り、すべての完全な構文です：URLではなくプロバイダーを指定したい場合は`setup --provider <kind>`を使用します。

### `--token`とそのコスト

`--token <token>`はキーをコマンドラインに置きます。これはマシンを設定する最も速い方法ですが、キーがconfigファイル以外に残る唯一の方法でもあります：

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
コマンドライン引数はその後シェルの履歴ファイルに残り、コマンド実行中はプロセスリストにも表示されます——あなたと同じユーザーで動作するものであれば`/proc`から読み取れます。`--token`を使用するたびに`setup`がその旨を通知します。共有マシン、記録されたセッション、または履歴ファイルが同期される環境では`--key-stdin`を優先してください；この方法で渡したキーは重要であれば即座にローテーションしてください。
</Warning>

`--token`、`--key-stdin`、`--key-from-env`は相互排他的です：1つだけ指定してください。

その後、キー、エンドポイント、どのJevが回答したかを確認するために、小さなライブリクエストを送信します：

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`は、タイムアウト後に回答が届いた場合（すべてのフックが`timeout`として正規表現にフォールバックする）またはチェック質問への回答が誤っている場合、タイトルにその旨を表示してexit 1します。

フックはすべてのツール呼び出しでconfigを読み取るため、次の呼び出しから適用されます。デーモンの有無にかかわらず、再起動は不要です。

## 動作確認

```bash
failproofai jev status
failproofai jev status --json
```

`status`はプロバイダー、エンドポイント、モデル、モード、configファイルとそのパーミッションを表示し、キーは表示しません。その下に最近のアクティビティの要約が表示されます：Jevが評価した呼び出し数、正規表現にフォールバックした回数とその理由、レイテンシ、解除されたreviewableポリシー。

## 実際の呼び出しを検証する

フックされたエージェントで新しいセッションを開始します。`README.md`のファイル読み取りツールを使用してタイトルを報告するよう要求します。セッションにそのツール呼び出しが含まれていることを確認し、`failproofai jev status`を再実行します：最近の評価済み呼び出し数が増えているはずです。[ローカルダッシュボード](/ja/reference/local-dashboard#review-policy-activity)の**Policies → Activity**を開いて、その呼び出しのJev判定とモードを確認します。observeモードでは、ポリシーの結果が引き続き呼び出しを決定します。reviewableポリシーがマッチしてJevがすべての名前付きチェックを解除した場合にのみ解除が表示されます；通常の読み取りには解除すべきポリシーがない場合があります。

## Observeモード

`enforce`がデフォルトです。Jevが判定を変更しないよう監視するだけにするには、`observe`に切り替えます：Jevは引き続き問い合わせられ判定は記録されますが、強制されるのは正規表現の結果です。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`はconfigを保持——エンドポイントとキー——しJevへの問い合わせを停止します：フックは設定なしの場合とまったく同じように正規表現ポリシーを実行し、`failproofai jev status`は「off (switched off)」と表示します。`--mode observe`または`--mode enforce`で再開できます。

同じプロバイダーで`setup`を再実行すると保存されたキーが保持されるため、モードの切り替えはフラグ1つです。プロバイダーの切り替えは最初からやり直しになり、そのプロバイダーのキーを要求します。リクエストを別のホストに移動する`--base-url`も同様です：保存されたキーは指定されたホスト、またはそのプロバイダー自身のAPIにのみ送信されます。

## Configファイル

すべては`~/.failproofai/jev.json`という1つのファイルに保存され、`setup`によって書き込まれます：

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| フィールド | 意味 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare`、`custom`——または`failproofai`（そのキーはこのファイルではなくFailproofAI Cloud接続から取得。[Jev through FailproofAI Cloud](/ja/reference/jev-cloud)参照）。 |
| `apiKey` | `Authorization: Bearer <key>`として送信。 |
| `baseUrl` | `custom`の場合は必須；それ以外ではプロバイダーのAPIベースを置き換え。`https`必須。`localhost`への平文`http`は`mode: observe`のみ許可：ローカルポートを認証するものはないため、プロキシの停止中に、判定対象のエージェントを含むマシン上の任意のプロセスが代わりに応答する可能性がある。 |
| `accountId` | Cloudflareのみ：32文字の小文字16進数。 |
| `model` | プロバイダーのデフォルトモデルIDを置き換え。バージョン付きIDはJev 1.13を指定する必要がある。APIキーのような形式の値は拒否（返却されない）されるため、`--model`に貼り付けたキーはモデルとして保存・送信されることはない。 |
| `timeoutMs` | 正規表現結果を使用する前にツール呼び出しがJevを待つ時間。100〜10000、デフォルト3000。 |
| `mode` | `enforce`（デフォルト）、`observe`、または`off`（configを保持し、Jevを実行しない）。 |

3つのルールでファイルを保護します：

- **オーナーのみ。** パーミッション`0600`で書き込まれます。他のユーザーまたはグループが読み書きできるコピーは**拒否**され、`chmod 600 ~/.failproofai/jev.json`を実行するか`setup`を再実行するまで、フックは正規表現にフォールバックします。ディレクトリも確認されます：`~/.failproofai`は他のユーザーが**書き込み可能**であってはなりません。ファイル自体のパーミッションに関わらず、そこに書き込めるユーザーはファイルを置き換えられるからです。`setup`はその書き込みビットを見つけた場合に削除します。`failproofai jev status`はconfigが拒否された場合にその旨を表示し、ファイルが示すエンドポイントを表示します：別の誰かが変更した可能性があるため、`chmod`前にそれが自分のものであることを確認してください。そのようなファイルで`setup`を再実行すると、保存されたキーはプロバイダー自身のAPIにのみ引き継がれます；ファイルが示す他のエンドポイントには再度キーが必要です（`--key-stdin`）、または`--base-url default`でプロバイダーへのリクエストを戻します。
- **グローバルのみ。** リポジトリはJevをオンにしたり、別のエンドポイントを指したり、モデルを選択したりできません：プロジェクト内の`.failproofai/jev.json`は無視され、プロバイダー、URL、モデル、アカウントIDはそのファイルからのみ読み取られます——リポジトリのエージェント設定が設定できる環境変数からは読み取られません。（`FAILPROOFAI_HOME`はその回避策にはなりません：Jevだけをリダイレクトするのではなく、ポリシーを含むfailproofaiディレクトリ全体を移動します。）
- **キーのみ環境変数から取得可能。** ファイルに`apiKey`がない場合、`FAILPROOFAI_JEV_API_KEY`がそのセッション用に供給します（`setup --key-from-env`がそのようなファイルを書き込みます）。ファイルが保持するキーを置き換えることはなく、ファイルなしでJevをオンにすることもできません。変数が設定されていない場合、そのシェルではJevは単純にオフになります：`failproofai jev status`はその旨を表示し、exit 0でconfigを変更しません（`status --json`は`"reason": "no-env-key"`とともに`"status": "key-missing"`を報告）。`failproofaid`デーモンはシェルの環境変数を認識しないため、`failproofai config`で設定したマシンではキーをファイルに保存してください。

## どのJevが回答するか

Failproof AIの判定しきい値はJev 1.13で較正されているため、回答はそのファミリーから来た場合にのみ使用されます：`jev-1.13.x`、またはOpenRouterの`typesafe/jev-1.13-<date>`。プロバイダーがJevをエイリアスのみで識別しバージョンを報告しない場合（Vercel、および報告しない場合のCloudflare）、回答は使用され未検証として記録されます。`custom`エンドポイントは回答したモデルを報告する必要があります；唯一の例外は設定したバージョンなしの`--model`名で、エコーバックされると同じ方法で未検証として記録されます。他のバージョンを報告する回答、またはバージョンを報告しない`custom`の回答は使用されません：その呼び出しは`model-mismatch`という理由で正規表現にフォールバックします。

## Jevが回答できない場合

以下のそれぞれはその呼び出しに対して正規表現の結果にフォールバックし、理由とともに記録されます。`failproofai jev status`がこれを集計します：

| 理由 | 原因 |
| --- | --- |
| `timeout` | `timeoutMs`内に回答なし。 |
| `http-429` | プロバイダーがキーをレート制限。 |
| `rate-limited` | Failproof AI自身のリミッターが送信前に呼び出しを保留：1秒あたり5リクエスト、最大5バーストまで、プロバイダーが`429`を返した後は一時停止。プロバイダーではなく内部制限。 |
| `http-500`、`http-502`、`http-503`、… | プロバイダーでのサーバーエラー。正確なステータスが記録される。 |
| `out-of-credits` | HTTP 402：プロバイダーアカウントにクレジットが残っていない。 |
| `provider-refused` | Cloudflareからの「Model execution failed (Payment error)」というHTTP 402：プロバイダーがこのリクエストのモデル実行を拒否。通常は請求の問題ではないため、クレジットを追加しても解決しない。 |
| `http-401`、`http-403` | キーが拒否された。 |
| `http-404` | `<base>/systemone`に何も配信されていないため、ベースURLが誤っています——`/systemone`がベースに追加されており、すべてのプロバイダーはバージョンルートで配信します。`failproofai jev models`でエンドポイントが配信しているものを確認できます。 |
| `network` | エンドポイントに到達できなかった。 |
| `http-301`、`http-302`、`http-307`、`http-308` | エンドポイントがリダイレクトで応答。リダイレクトは決して追われないため、回答は常にconfigのURLからのみ来ます；`--base-url`を最終URLに設定してください。 |
| `malformed` | エンドポイントが応答したが、Jevの回答ではありませんでした——JSONでないボディ、またはその中に回答がないもの。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflareのエンベロープが失敗、または未完了のジョブを報告。 |
| `model-mismatch` | 1.13以外のJevバージョンが回答した、または`custom`エンドポイントがどのモデルが回答したかを通知しなかった。 |
| `request-cut` | **障害ではありません。** Jevは回答しましたが、呼び出しの一部しか表示されなかったため、回答は何も解除しませんでした。[Jevが回答したが呼び出し全体でなかった場合](#when-jev-answered-but-not-on-the-whole-call)を参照してください。 |

`failproofai jev status`は`upstream-error`（回答にプロバイダー自身のエラーが含まれていた）や`config`などのまれな理由も表示でき、名前のつけられない理由はすべて`other`として集計します。

`request-cut`がこの表に含まれているのは、`failproofai jev status`が他の理由と一緒に集計し、またすべてのdenyを維持するからです。ここで唯一、プロバイダーについて何も示さない理由です：リクエストは届き、Jevは回答しました。上の行とは異なり、その回答は依然としてカウントされます——Jev自身のdenyまたはwarningは、破棄されるのではなく正規表現の結果に加えて適用されます。したがって、これが続く場合は、エンドポイントに問題があるのではなく、全体を送信するには大きすぎる呼び出しがエバリュエーターに届いていることを意味し、クレジットを追加したりURLを変更しても数は変わりません。

## Jevが回答したが呼び出し全体でなかった場合

さらに2つのことが起こりえますが、いずれもJevが回答できなかったということではありません。どちらも、呼び出しの内容または会話が1つのリクエストに収まったかどうかに関するものです。

**呼び出し自体の一部が収まらなかった。** ツール呼び出しは固定バジェット内で送信され、過大なもの——非常に大きな`Write`、巨大なMCPボディ、上限までパディングされたコマンド——は収まった部分で送信されます。Jevは引き続き回答し、その回答は依然としてカウントされます：独自のdenyまたはwarningは通常通り適用されます。できないのは何かを**解除**することです。呼び出しの一部に対する判定は、呼び出し全体への判定ではないからです。したがって、すべてのポリシーdenyは維持され、呼び出しは`request-cut`という理由でフォールバックとして記録されます。これが示すルール：呼び出しを大きくすると解除を失う可能性があり、解除を獲得することはできません。

**メッセージが収まらなかった。** 貼り付けた長いプロンプト、エージェントの最後のメッセージ、またはこのエバリュエーター自身のストアがすでに上限に達したプロンプト。**何も変わりません**：呼び出しは他のものと全く同様に判定、解除、記録され、フォールバックとしてカウントされません。入力した内容の長さが判定を決定することは決してなく、切り捨てが同意を生み出すことはありません：プロンプトがすでに上限に達した状態で届いた場合、「あなたはこれを要求しなかった」という結論を導き出せなくなるだけで、そうならなくなるわけではありません。

2つの違いはテキストを誰が書いたかです。呼び出しはエージェントのものであり、その長さが重大性を減らすルールはエージェントが使用できるルールになります；あなたのプロンプトはあなたのものであり、その長さをシグナルとして扱うことは常にspecやスタックトレースを貼り付けることへのペナルティにしかなりませんでした。

## マシンから送信されるデータ

Jevが評価する各ツール呼び出しについて、プロバイダーに1つのリクエストが送信されます。その内容：

- ツール呼び出し自体（APIキー、bearerトークン、`KEY=`代入などのシークレットはリダクト済み）；
- 入力した最近のプロンプト（エージェントのハーネスが追加したテキストは除去済み）；
- 最新プロンプトの前のエージェントの最後のメッセージ（エージェントが書いたものとしてラベル付け）；
- パスがプロジェクト内かどうかなどローカルで計算されたファクト——最初にレビューされた呼び出し時のセッションが入ったプロジェクト、[セッションのためにpinされた](/ja/reference/jev-intent#the-project-root)——および現在のgitブランチ。

これはconfigのエンドポイントにのみ、あなたのキーの下で送信されます。

## オフにする

```bash
failproofai jev remove
```

これは`~/.failproofai/jev.json`を削除します。次のツール呼び出しから、フックは以前と全く同じように正規表現ポリシーを実行します。`~/.failproofai/state/semantic/`以下のセッション固有のストア（`sessions/`の記録されたプロンプト、`roots/`のプロジェクトルート）はそのまま残り、期限切れになります。Jevへの問い合わせを停止しながらconfigを保持するには、代わりに`failproofai jev setup --mode off`を使用してください。

## コマンドリファレンス

| コマンド | 結果 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 1つのコマンドで設定；プロバイダーはURLのホストから決定 |
| `failproofai jev --url <url> --token <token>` | 同じ、コマンドラインにキーを置く——履歴とプロセスリストに表示される |
| `failproofai jev setup --provider <kind> --key-stdin` | stdinでパイプされたキーからconfigを書き込む |
| `failproofai jev setup --provider <kind>` | 同じ、マスクされたプロンプトでキーを要求 |
| `failproofai jev setup --key-from-env` | キーを保存しない；セッションごとに`FAILPROOFAI_JEV_API_KEY`を読み取る |
| `failproofai jev setup --mode observe` | モードを切り替え（`enforce`、`observe`、または`off`）、保存されたキーを保持 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | モデルまたはAPIベースを上書き；`default`で上書きを解除 |
| `failproofai jev setup --timeout-ms <n>` | 呼び出しごとのバジェットを変更 |
| `failproofai jev status [--json]` | 設定、パーミッション、最近のアクティビティ；キーは表示されない |
| `failproofai jev test [--json]` | 1回のライブリクエスト：レイテンシと回答したバージョン |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | そのエンドポイントの`/models`が報告するモデルID、設定済みのものをマーク |
| `failproofai jev remove` | configを削除；Jevはオフ |
