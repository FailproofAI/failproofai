これは、独自キーを使用する[Jevポリシー](/ja/policies/jev)のプロバイダーおよび設定リファレンスです。正規表現ポリシーは文字列を照合します。しかし、あなたが意図して実行した`rm -rf build/`と、プランに紛れ込んだ`rm -rf ~`を区別することはできません。そのため、ある箇所では過剰にブロックし、別の箇所では不十分なブロックになってしまいます。TypeSafeの分類器である**Jev**は、あなたが実際に何を求めたかを踏まえてツール呼び出しを読み取り、1回の高速なリクエストでyes/noの質問群に答えます。

Jevのエンドポイントとキーを設定すると、Failproof AIは各ツール呼び出しについて正規表現ポリシーと**並行して**Jevに問い合わせます。正規表現ポリシーの代わりではありません。

- **ハード**ポリシーのdenyは最終決定です。Jevがそれを解除することはできません。ポリシーは、明示的にreviewable（見直し可能）とマークされ、適用されるJevチェックが指定されていない限り、すべてハードです。つまり、何も記載のないカスタムポリシー、パックポリシー、Cloudポリシーはハードとなり、常時有効な自己保護ガードも常にハードです。
- **reviewable**ポリシーのdenyは解除される場合がありますが、そのポリシーが対象とする具体的な懸念事項についてJevが問い合わせられ、「問題なし」または「ユーザーが要求したもの」と回答した場合に限ります。ユーザーがその呼び出しを要求していないにもかかわらず、懸念事項が実在すると判断したチェックは、denyを維持します。たとえそのチェック自体の判定が警告にとどまっていても、ツール呼び出しの前では警告はエージェントを止めないためです。また、そのチェックがdenyを発行できるもの（シークレット露出、認証情報の流出、破壊的な削除など）である場合、その呼び出しに対して解除は行われません。
- ブロックが**警告**に変わる場合があります。その呼び出しがあなたが与えたタスクのステップであり、それ以上に影響が及ばない場合、Jevは自身のdenyを警告に緩和します。その警告（呼び出しの実際の問題点を明示したもの）がポリシーのブロックに置き換わります。
- Jevは、正規表現では表現できない有害性に対して、独自に警告またはdenyを発行することもあります。
- Jevが回答できない場合（タイムアウト、レート制限、サーバーエラー、クレジット不足、想定外のモデルバージョン）、その呼び出しはJevなしの場合とまったく同じ正規表現の結果が適用されます。
- Jevは、呼び出し全体を読み取り、かつ具体的な懸念事項について問い合わせられた場合を除き、ポリシー単独の結果より許可的な判断をすることはありません。それに満たないもの（全体を送信できないほど大きな呼び出し、インジェクションの疑い）は解除権限を剥奪し、すべてのdenyを維持します。

<Note>
Jevの設定がなければ何も変わりません。フックは従来通り正規表現ポリシーのみを実行します。設定ファイルがオプトインの全体です。
</Note>

<Tip>
FailproofAI Cloudをお使いですか？独自のキーは不要です。`jev:evaluate`権限を持つキーで接続したマシンは、組織のプランでJevを使用できます。[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)を参照してください。
</Tip>

## 開始前の準備

**failproofai 1.0.8-beta.0以降**をインストールし、エージェントが動作するマシンの[対応ハーネス](/ja/reference/harnesses)にフックをアタッチしてください。新しいマシンの場合は[クイックスタート](/ja/start/quickstart)に従い、Cloudを使用しない場合は[ローカル実施のセットアップ](/ja/start/setup#enforce-locally)を参照してください。インストール済みのCLIは`failproofai --version`で確認できます。

以下のプロバイダーからAPIキーを取得するか、互換性のあるエンドポイントとそのキーを用意してください。Jevは`PreToolUse`または`PermissionRequest`ゲートで名前付きツール呼び出しをレビューします。独自の判定を発行することもできますが、既存のポリシーdenyを解除するには、[reviewable](/ja/policies/authority)としてマークされたインストール済みポリシーが必要です。ハードポリシーのdenyは最終決定のまま変わりません。

## プロバイダーを選択する

Jevには5つの経路からアクセスできます。いずれか1つのキーを用意してください。

| プロバイダー | `--provider` | エンドポイント | デフォルトモデル | 備考 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | バージョン固定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | リクエストはデータ保持なしのエンドポイントにのみルーティングされ、他のプロバイダーへのフォールバックはありません。`typesafe/jev-1.13-20260917`のような日付付きバージョンを報告します。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jevをエイリアスでのみ識別するため、応答したバージョンは未検証として記録されます。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id`が必要です。キーあたり毎秒約6回の呼び出しでHTTP 429が発生することが確認されています。 |
| 独自エンドポイント | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafeのリクエストボディを受け入れ、どのモデルが応答したかを報告するエンドポイント。`https`のみ対応。ローカルテスト用に限り、ループバックホスト（`localhost`、`127.0.0.1`、`::1`）への平文`http`も受け付けます。 |

<Warning>
Vercel独自のBring Your Own Key機能では、リクエストが失敗すると、Vercelの認証情報でサイレントに再試行されます。すべての呼び出しを自分のTypeSafeアカウントにのみ課金・表示させる必要がある場合は、TypeSafeを直接使用してください。
</Warning>

## セットアップ

1つのコマンドで、エンドポイントとキーを設定します。まず`observe`モードで開始して、既存のポリシーが呼び出しを判断し続ける間にJevの判定を検査できるようにしましょう。

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URLがプロバイダーを決定する

プロバイダーを明示的に指定する必要はありません。URLの**ホスト**でプロバイダーが決まります。

| URLホスト | プロバイダー | 追加要件 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| その他のホスト | `custom` | — 指定したURLがベースURLになります |

これには3つの重要な点があります。

- **プロバイダー自身のAPIのURLはオーバーライドを書き込みません。** `--url https://api.typesafe.ai/v1`は`--provider typesafe`と同じ設定を生成します。既知のプロバイダーで異なるパスまたはホストを指定すると、`--base-url`と同様にベースURLとして保存されます。
- **`--provider`は推論を上書きできます。**これにより、独自ホストからプロバイダーのAPIを話すプロキシに接続できます: `--url https://jev-proxy.internal/v1 --provider typesafe`。
- **ホストと矛盾する`--provider`は拒否されます。**推測はしません。`--provider openrouter --url https://api.typesafe.ai/v1`は何も書き込まず、理由を表示します。2つの指定がキーの送信先について矛盾しているためです。同じペアは`jev setup --base-url`やダッシュボードのJev設定からも拒否されます。（`--provider custom`は矛盾ではありません。「このURLをそのまま使う」という意味です。ただし、カスタムルートではアカウント固有のエンドポイントに到達できないCloudflareのホストは例外です。）

`--url`は設定ファイルの`baseUrl`と同じ検証が行われ、同じメッセージで拒否されます。`https`、またはいずれのモードでもループバックホスト（`localhost`、`127.0.0.1`、`::1`）への平文`http`が許可されます。リスク: ループバックサーバーを認証する仕組みはないため、サーバーがダウンしている間に別のローカルプロセスがそのポートを取得して応答する可能性があります。ローカルテスト以外では`https`を使用してください。

### キー

`--key-stdin`でパイプ入力するか、ターミナルでコマンドを実行してマスクされたプロンプトでキーを貼り付けてください。どちらの方法でも、キーは設定ファイルに直接保存され、表示されることはありません。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup`は同じフラグを受け付け、すべての詳細設定に対応しています。URLではなくプロバイダー名を指定したい場合は`setup --provider <kind>`を使用してください。

### `--token`とそのリスク

`--token <token>`はコマンドラインにキーを指定します。マシンを設定する最も手軽な方法ですが、設定ファイル以外の場所にキーが残る唯一の方法でもあります。

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
コマンドライン引数はシェルの履歴ファイルに残り、コマンドの実行中はプロセスリストにも表示されます。あなたと同じ権限で実行されているプログラムであれば`/proc`から読み取れます。`setup`は`--token`を使用するたびにこの旨を警告します。共有マシン、記録されたセッション、または履歴ファイルが同期される環境では`--key-stdin`を使用してください。この方法で渡したキーは、必要に応じてローテーションしてください。
</Warning>

`--token`、`--key-stdin`、`--key-from-env`は相互に排他的です。いずれか1つのみ指定してください。

設定後、1回の小さなライブリクエストを送信して、キー、エンドポイント、応答したJevのバージョンを確認してください。

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`は、タイムアウト後に応答が届いた場合（すべてのフックが`timeout`として正規表現にフォールバックする）やチェック質問への回答が誤っている場合、タイトルにその旨を表示してexit 1で終了します。

フックはツール呼び出しのたびに設定を読み込むため、次の呼び出しから即座に適用されます。デーモンの有無にかかわらず、再起動は不要です。

## 動作状況を確認する

```bash
failproofai jev status
failproofai jev status --json
```

`status`はプロバイダー、エンドポイント、モデル、モード、設定ファイルとそのパーミッション、そしてキー以外の情報を表示します。その下には最近のアクティビティのサマリーも表示されます。Jevが評価した呼び出し数、正規表現にフォールバックした回数とその理由、レイテンシー、解除したreviewableポリシーなどが確認できます。

## 実際の呼び出しを確認する

フックを適用したエージェントで新しいセッションを開始し、`README.md`のファイル読み取りツールを使用してタイトルを報告するよう指示してください。セッションにそのツール呼び出しが含まれていることを確認し、`failproofai jev status`を再実行します。最近の評価済み呼び出し数が増加しているはずです。[ローカルダッシュボード](/ja/reference/local-dashboard#review-policy-activity)の**Policies → Activity**を開いて、その呼び出しのJev判定とモードを確認してください。observeモードでは、ポリシーの結果が引き続き呼び出しを決定します。解除はreviewableポリシーがマッチし、Jevがすべての指定チェックを解除した場合にのみ表示されます。通常の読み取り操作では解除すべきポリシーがない場合もあります。

## Observeモード

デフォルトは`enforce`です。Jevの判断を変更させずに監視するには、`observe`に切り替えてください。Jevは引き続き問い合わせられ、その判定は記録されますが、実際の実施は正規表現の結果に基づきます。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`は設定（エンドポイントとキー）を保持したままJevへの問い合わせを停止します。フックは設定なしの場合と同じく正規表現ポリシーのみを実行し、`failproofai jev status`は「off (switched off)」と表示します。`--mode observe`または`--mode enforce`で再開できます。

同じプロバイダーに対して`setup`を再実行すると保存済みのキーが保持されるため、モードの切り替えはフラグ1つで完了します。プロバイダーを切り替える場合は最初からやり直しとなり、そのプロバイダーのキーを再入力する必要があります。リクエストを別のホストに移動する`--base-url`についても同様です。保存済みのキーは、それが入力されたホスト、またはそのプロバイダー自身のAPIにのみ送信されます。

## 設定ファイル

すべての情報は`~/.failproofai/jev.json`という1つのファイルに保存され、`setup`によって書き込まれます。

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| フィールド | 説明 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare`、`custom`のいずれか。または`failproofai`（このファイルではなくFailproofAI Cloud接続からキーを取得します。[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)を参照）。 |
| `apiKey` | `Authorization: Bearer <key>`として送信されます。 |
| `baseUrl` | `custom`では必須。それ以外ではプロバイダーのAPIベースを置き換えます。`https`必須。`localhost`への平文`http`は`mode: observe`の場合のみ受け付けます。ローカルポートを認証する仕組みはないため、プロキシがダウンしている間は、エージェントを含むマシン上の任意のプロセスが代わりに応答する可能性があります。 |
| `accountId` | Cloudflareのみ: 32文字の小文字16進数。 |
| `model` | プロバイダーのデフォルトモデルIDを置き換えます。バージョン付きIDはJev 1.13を指定する必要があります。APIキーの形式をした値は拒否されます（かつ返却されません）。そのため`--model`に誤ってキーを貼り付けてもモデルとして保存・送信されることはありません。 |
| `timeoutMs` | Jevの応答を待つ時間。超過した場合は正規表現の結果を使用します。100〜10000、デフォルトは3000。 |
| `mode` | `enforce`（デフォルト）、`observe`、または`off`（設定を保持しJevを実行しない）。 |

ファイルを保護する3つのルールがあります。

- **オーナーのみ。** ファイルはパーミッション`0600`で書き込まれます。他のユーザーやグループが読み書きできるコピーは**拒否**され、`chmod 600 ~/.failproofai/jev.json`を実行するか`setup`を再実行するまで、フックは正規表現にフォールバックします。ディレクトリも確認されます。`~/.failproofai`は他のユーザーが**書き込み可能**であってはなりません。ファイル自体のパーミッションに関わらず、書き込み権限があればファイルを置き換えられるためです。`setup`は書き込みビットを見つけた場合に削除します。`failproofai jev status`は設定が拒否された場合にその旨を表示し、ファイルに記載されたエンドポイントを示します。他者が変更した可能性があるため、`chmod`を実行する前に自分のファイルであることを確認してください。このようなファイルで`setup`を再実行すると、保存済みのキーはプロバイダー自身のAPIにのみ引き継がれます。ファイルに記載された他のエンドポイントには再度キーの入力が必要です（`--key-stdin`）。またはリクエストをプロバイダーに戻すには`--base-url default`を使用してください。
- **グローバルのみ。** リポジトリはJevを有効にしたり、別のエンドポイントに向けたり、モデルを選択したりすることはできません。プロジェクト内の`.failproofai/jev.json`は無視され、プロバイダー、URL、モデル、アカウントIDはそのファイルからのみ読み込まれます。リポジトリのエージェント設定で指定できる環境変数からは読み込まれません。（`FAILPROOFAI_HOME`はこれを回避する手段ではありません。Jevのみをリダイレクトするのではなく、ポリシーを含むfailproofaiディレクトリ全体を移動します。）
- **キーのみ環境変数から取得可能。** ファイルに`apiKey`がない場合、`FAILPROOFAI_JEV_API_KEY`がそのセッションのキーとして使用されます（`setup --key-from-env`でそのようなファイルが書き込まれます）。ファイルに保存されたキーを上書きすることはなく、ファイルなしでJevを有効にすることもできません。変数が設定されていない場合、そのシェルではJevは単にオフになります。`failproofai jev status`はその旨を表示し、exit 0で終了し、設定はそのままです（`status --json`は`"status": "key-missing"`と`"reason": "no-env-key"`を報告します）。`failproofaid`デーモンはシェルの環境を継承しないため、`failproofai config`でセットアップしたマシンではファイルにキーを保存してください。

## どのJevが応答するか

Failproof AIの判定しきい値はJev 1.13で較正されています。そのため、そのファミリー（`jev-1.13.x`、またはOpenRouterの`typesafe/jev-1.13-<date>`）からの応答のみが使用されます。プロバイダーがJevをエイリアスでのみ識別し、バージョンを報告しない場合（VercelおよびそうでないCloudflare）、応答は使用されますが未検証として記録されます。`custom`エンドポイントは応答したモデルを報告する必要があります。唯一の例外は、設定したバージョンなしの`--model`名で、エコーバックされた場合は同様に未検証として記録されます。他のバージョンを報告した応答、またはバージョンを報告しない`custom`応答は使用されません。その呼び出しは`model-mismatch`という理由で正規表現にフォールバックします。

## Jevが応答できない場合

以下のいずれかが発生した場合、その呼び出しは正規表現の結果にフォールバックし、理由とともに記録されます。`failproofai jev status`で合計を確認できます。

| 理由 | 原因 |
| --- | --- |
| `timeout` | `timeoutMs`以内に応答なし。 |
| `http-429` | プロバイダーがキーをレート制限した。 |
| `rate-limited` | Failproof AI自身のリミッターが送信前に呼び出しを保留した。毎秒5リクエスト、最大5バーストまで。プロバイダーが`429`を返した直後は一時停止。プロバイダー側ではない。 |
| `http-500`、`http-502`、`http-503`、… | プロバイダー側のサーバーエラー。正確なステータスが記録される。 |
| `out-of-credits` | HTTP 402: プロバイダーアカウントのクレジットが残っていない。 |
| `provider-refused` | Cloudflareからの「Model execution failed (Payment error)」というHTTP 402: プロバイダーがこのリクエストのモデル実行を拒否した。通常は課金の問題ではないため、クレジットを追加しても解決しない。 |
| `http-401`、`http-403` | キーが拒否された。 |
| `http-404` | `<base>/systemone`に何も提供されていないため、ベースURLが誤っています。`/systemone`はベースURLに付加されるため、各プロバイダーはバージョンルートで提供します。`failproofai jev models`でエンドポイントが実際に提供しているものを確認できます。 |
| `network` | エンドポイントに到達できなかった。 |
| `http-301`、`http-302`、`http-307`、`http-308` | エンドポイントがリダイレクトを返した。リダイレクトは決して追従しないため、応答は常に設定内のURLからのみ受け付けます。最終的なURLを`--base-url`で設定してください。 |
| `malformed` | エンドポイントは応答したが、Jevの回答形式ではない。JSONでないボディ、または回答が含まれていないボディ。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflareのエンベロープが失敗、または未完了のジョブを報告した。 |
| `model-mismatch` | 1.13以外のJevバージョンが応答した、または`custom`エンドポイントが応答したモデルを報告しなかった。 |
| `request-cut` | **障害ではありません。** Jevは応答しましたが、呼び出しの一部しか表示されなかったため、その回答は何も解除しませんでした。[Jevが応答したが呼び出し全体に対してではなかった場合](#when-jev-answered-but-not-on-the-whole-call)を参照してください。 |

`failproofai jev status`は、`upstream-error`（応答にプロバイダー自身のエラーが含まれていた）や`config`などのまれな理由も表示することがあり、識別できない理由は`other`として集計します。

`request-cut`がこの表に含まれているのは、`failproofai jev status`が他の理由と同様に集計するためであり、またこれもすべてのdenyを維持するためです。ここに挙げた理由の中で、プロバイダーに関して何も示唆しない唯一の理由です。リクエストは到達し、Jevは応答しました。上記のすべての行とは異なり、その回答はカウントされます。Jev自身のdenyや警告は、破棄されるのではなく正規表現の結果に加えて適用されます。そのため、この理由が連続して発生する場合は、エンドポイントに問題があるのではなく、全体を送信するには大きすぎる呼び出しが評価器に到達していることを意味します。クレジットの追加やURLの変更では解決しません。

## Jevが応答したが呼び出し全体に対してではなかった場合

さらに2つの状況が発生する可能性があります。いずれもJevが応答に失敗しているわけではありません。どちらも、呼び出しの内容または会話がどれだけ1つのリクエストに収まるかに関する問題です。

**呼び出し自体の一部が収まらなかった場合。** ツール呼び出しは固定された予算内で送信されますが、非常に大きなもの（巨大な`Write`、大規模なMCPボディ、上限まで詰め込まれたコマンド）は収まった部分だけが送信されます。Jevは引き続き応答し、その回答はカウントされます。Jev自身のdenyや警告は通常通り適用されます。しかし、呼び出しの一部に対する判定は呼び出し全体の判定ではないため、**解除**はできません。すべてのポリシーdenyは維持され、呼び出しは`request-cut`という理由でフォールバックとして記録されます（`failproofai jev status`が上記の理由と合計します）。これが意味するルール: 呼び出しを大きくすると解除権限を失う可能性があり、解除権限を得ることは決してありません。

**メッセージが収まらなかった場合。** 貼り付けた長いプロンプト、エージェントの最後のメッセージ、またはこの評価器自身のストアがすでに上限に達していたプロンプト。**何も変わりません**。呼び出しは他と同様に判定、解除、記録され、フォールバックとしてカウントされません。入力した内容の長さが判定を決定することはなく、切り捨てによって同意が生み出されることもありません。プロンプトがすでに上限に達した状態で到達した場合、「あなたはこれを要求しなかった」という結論はそもそも導き出せなくなるだけで、逆の結論になることはありません。

この2つの違いは、テキストを書いたのが誰かという点です。呼び出しはエージェントのものであり、その長さが重大性を軽減できるルールはエージェントが悪用できるルールになります。プロンプトはあなたのものであり、その長さをシグナルとして扱うことは、仕様書やスタックトレースを貼り付けることへのペナルティにしかなりません。

## マシンから送信される情報

Jevが評価する各ツール呼び出しについて、プロバイダーに1つのリクエストが送信されます。その内容:

- ツール呼び出し自体（APIキー、ベアラートークン、`KEY=`代入などのシークレットはリダクトされます）
- あなたが入力した最近のプロンプト（エージェントのハーネスが追加したテキストを除いたもの）
- 最新のプロンプト前のエージェントの最後のメッセージ（エージェントが書いたものとしてラベル付け）
- パスがプロジェクト内かどうかなど、ローカルで計算されたファクト（最初のレビュー済み呼び出し時のセッションのプロジェクト、[セッションのためにピン留め](/ja/reference/jev-intent#the-project-root)）および現在のgitブランチ

リクエストはあなたのキーの下で、設定内のエンドポイントにのみ送信されます。

## オフにする

```bash
failproofai jev remove
```

これにより`~/.failproofai/jev.json`が削除されます。次のツール呼び出しから、フックは以前と同じく正規表現ポリシーのみを実行します。`~/.failproofai/state/semantic/`以下のセッション固有のストア（`sessions/`に記録されたプロンプト、`roots/`にプロジェクトルート）はそのまま残り、自然に期限切れになります。設定を維持したままJevへの問い合わせを停止するには、代わりに`failproofai jev setup --mode off`を使用してください。

## コマンドリファレンス

| コマンド | 結果 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 1つのコマンドで設定。プロバイダーはURLのホストから決定される |
| `failproofai jev --url <url> --token <token>` | 同上、コマンドラインにキーを指定（履歴ファイルとプロセスリストに残る） |
| `failproofai jev setup --provider <kind> --key-stdin` | stdinからパイプしたキーで設定を書き込む |
| `failproofai jev setup --provider <kind>` | 同上、マスクされたプロンプトでキーを入力 |
| `failproofai jev setup --key-from-env` | キーを保存しない。セッションごとに`FAILPROOFAI_JEV_API_KEY`を読み込む |
| `failproofai jev setup --mode observe` | モードを切り替える（`enforce`、`observe`、`off`）、保存済みのキーは維持 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | モデルまたはAPIベースを上書き。`default`でオーバーライドをクリア |
| `failproofai jev setup --timeout-ms <n>` | 呼び出しごとの予算を変更する |
| `failproofai jev status [--json]` | 設定、パーミッション、最近のアクティビティ（キーは表示されない） |
| `failproofai jev test [--json]` | 1回のライブリクエスト: レイテンシーと応答したバージョン |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | そのエンドポイントの`/models`が報告するモデルID（設定済みのものをマーク） |
| `failproofai jev remove` | 設定を削除。Jevはオフになる |
