これは[Jevポリシー](/ja/policies/jev)を自己キーで使用する際のプロバイダーおよび設定リファレンスです。正規表現ポリシーは文字列をマッチングします。あなたが意図した`rm -rf build/`と、計画に紛れ込んだ`rm -rf ~`の違いを判別できないため、ある場所では過剰にブロックし、別の場所では不十分になります。**Jev**（TypeSafeのクラシファイアー）は、実際にリクエストした内容に照らしてツールコールを読み取り、一度の高速リクエストでYes/Noの質問セットに回答します。

自己Jevエンドポイントとキーが設定されると、Failproof AIは各ツールコールについてJevに問い合わせを行います。これは正規表現ポリシーの**代わり**ではなく、**並行して**行われます。

- **ハード**ポリシーのdenyは最終的なものです。Jevはそれをクリアできません。ポリシーはすべて、明示的にreviewable（レビュー可能）とマークされ、対象のJevチェックを指定しない限りハードです。したがって、何も記載のないカスタム・パック・Cloudポリシーはハードであり、常時有効な自己保護ガードは常にハードです。
- **reviewable**ポリシーのdenyはクリアされる可能性がありますが、Jevがそのポリシーの対象となる懸念事項について問い合わせを受け、「問題なし」または「ユーザーがこれをリクエストした」と回答した場合のみです。ユーザーがそのコールをリクエストしていないのに懸念事項が実在すると判断したチェックは、denyを維持します。たとえそのチェック自体の判定が警告レベルであっても、ツールコールの前では警告はエージェントを停止させないからです。そのチェックがdenyを発行できるもの（シークレット露出、認証情報の流出、破壊的削除など）である場合、そのコールについては何もクリアされません。
- コールがあなたが指定したタスクの一ステップであり、それ以上に踏み込まない場合、ブロックは**警告**になることがあります。Jevは自身のdenyを警告に緩和し、その警告（コールの実際の問題点を明示したもの）がポリシーのブロックに置き換わります。
- Jevは正規表現では表現できない有害行為について、独自に警告やdenyを発行することもできます。
- Jevが回答できない場合（タイムアウト、レート制限、サーバーエラー、クレジット不足、予期しないモデルバージョン）、そのコールはJevなしの場合とまったく同様に正規表現の結果が使用されます。
- Jevはコール全体を読み取り、正確な懸念事項について問い合わせを受けた場合を除き、ポリシー単独よりもコールをより許可的にすることは決してありません。それに満たないもの（全体を送信するには大きすぎるコール、インジェクションの疑いなど）はクリアを取り消し、すべてのdenyを維持します。

<Note>
Jev設定がない場合は何も変わりません。フックはこれまでどおり正規表現ポリシーのみを実行します。設定ファイル自体がオプトインの全てです。
</Note>

<Tip>
FailproofAI Cloudをお使いですか？自己キーは不要です。`jev:evaluate`権限を持つキーで接続されたマシンは、組織のプランでJevを使用できます。[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)をご覧ください。
</Tip>

## 始める前に

**failproofai 1.0.8-beta.0以降**をインストールし、エージェントが動作するマシンの[対応ハーネス](/ja/reference/harnesses)にフックをアタッチしてください。新しいマシンの場合は[クイックスタート](/ja/start/quickstart)に、Cloudを使用しない場合は[ローカルエンフォースメントの設定](/ja/start/setup#enforce-locally)に従ってください。インストール済みのCLIは`failproofai --version`で確認できます。

以下のプロバイダーからAPIキーを取得するか、互換性のあるエンドポイントとそのキーを用意してください。Jevは`PreToolUse`または`PermissionRequest`ゲートで名前付きツールコールをレビューします。独自の判定を発行することもできますが、既存のポリシーdenyをクリアするには、[reviewable](/ja/policies/authority)とマークされたポリシーがインストールされている必要があります。ハードポリシーのdenyは最終的なままです。

## プロバイダーを選択する

Jevには5つの経路からアクセスできます。いずれか1つのキーをご用意ください。

| プロバイダー | `--provider` | エンドポイント | デフォルトモデル | 備考 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | バージョンを厳密に固定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | リクエストはデータ保持なしエンドポイントにのみルーティングされ、他のプロバイダーへのフォールバックはありません。`typesafe/jev-1.13-20260917`のような日付付きバージョンをレポートします。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jevをエイリアスのみで識別するため、応答したバージョンは未検証として記録されます。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id`が必要です。キーあたり毎秒約6コールをHTTP 429の前に計測しました。 |
| 自己エンドポイント | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafeのリクエストボディを受け入れ、どのモデルが応答したかをレポートするエンドポイント。`https`のみ対応。ローカルテスト用に`localhost`・`127.0.0.1`・`::1`へのプレーン`http`は許可されます。 |

<Warning>
Vercel独自のBring-Your-Own-Key機能では、リクエストが失敗した場合にVercelの認証情報でサイレントに再試行されます。すべてのコールを自分のTypeSafeアカウントのみに請求し、そのアカウントのみで確認する必要がある場合は、TypeSafeを直接使用してください。
</Warning>

## 設定する

コマンド1つ、エンドポイントとキーだけです。`observe`モードで開始して、既存のポリシーがコールを決定しながらJevの判定を検査できるようにしましょう。

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URLがプロバイダーを決める

プロバイダーを明示する必要はありません。URLの**ホスト**がプロバイダーを決定します。

| URLホスト | プロバイダー | 追加要件 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32桁の16進アカウントID>` |
| その他のホスト | `custom` | — 指定したURLがベースURLになります |

これから3つのことが導かれます。

- **プロバイダー自身のAPIのURLを指定した場合、オーバーライドは書き込まれません。** `--url https://api.typesafe.ai/v1`は`--provider typesafe`と同じ設定を生成します。既知のプロバイダーで異なるパスまたはホストを指定すると、`--base-url`が保存するのと同様にベースURLとして保存されます。
- **`--provider`は推論をオーバーライドします。** これにより、自己ホストでプロバイダーのAPIを話すプロキシに到達できます。例：`--url https://jev-proxy.internal/v1 --provider typesafe`。
- **ホストと矛盾する`--provider`は拒否されます。推測は行いません。** `--provider openrouter --url https://api.typesafe.ai/v1`は何も書き込まず、理由を説明します。2つの指定がキーの送信先について矛盾しているからです。同じ組み合わせは`jev setup --base-url`やダッシュボードのJev設定からも拒否されます。（`--provider custom`は矛盾ではありません。「このURLをそのまま使用する」という意味です。ただし、カスタムルートではアクセスできないCloudflareのアカウント固有エンドポイントは例外です。）

`--url`は設定ファイルの`baseUrl`と同様に検証され、同じメッセージで拒否されます。`https`、またはいずれのモードでも`localhost`・`127.0.0.1`・`::1`へのプレーン`http`。リスク：ローカルバックのサーバーを認証するものはないため、ダウン中に別のローカルプロセスがそのポートを奪って応答する可能性があります。ローカルテスト以外では`https`を使用してください。

### キー

`--key-stdin`でパイプするか、端末でコマンドを実行してマスクされたプロンプトでキーを貼り付けてください。どちらの場合も設定ファイルに直接書き込まれ、表示されることはありません。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32桁の16進アカウントID> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup`は同じフラグを受け取り、すべての完全形です。URLよりもプロバイダーを直接指定したい場合は`setup --provider <kind>`を使用します。

### `--token`とそのコスト

`--token <token>`はキーをコマンドラインに直接置きます。これはマシンを最も素早く設定する方法ですが、設定ファイル以外にキーが残る唯一の方法でもあります。

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
コマンドライン引数はシェルの履歴ファイルに残り、コマンド実行中はプロセスリストにも存在します。あなたと同じユーザーで実行されているものは`/proc`から読み取れます。`--token`を使用するたびに`setup`がその旨を通知します。共有マシン、記録されたセッション、または履歴ファイルが同期される環境では`--key-stdin`を優先し、このような方法で渡したキーは重要であれば更新してください。
</Warning>

`--token`・`--key-stdin`・`--key-from-env`は相互排他です。いずれか1つを指定してください。

その後、キー・エンドポイント・応答したJevを確認するために小さなライブリクエストを1つ送信します。

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`は、タイムアウト後に応答が届いた場合（すべてのフックが`timeout`として正規表現にフォールバックする）またはチェックの質問に誤答した場合、タイトルにその旨を表示して終了コード1で終了します。

フックはすべてのツールコール時に設定を読み込むため、次のコールから適用されます。デーモンの有無にかかわらず、再起動は不要です。

## 動作を確認する

```bash
failproofai jev status
failproofai jev status --json
```

`status`はプロバイダー・エンドポイント・モデル・モード・設定ファイルとそのパーミッションを表示し、キーは表示しません。その下に最近のアクティビティのサマリーも表示されます。Jevが評価したコール数、正規表現にフォールバックした回数とその理由、レイテンシー、クリアされたreviewableポリシーの情報が含まれます。

## 実際のコールを確認する

フックされたエージェントで新しいセッションを開始します。ファイル読み取りツールを使って`README.md`のタイトルを報告するよう指示してください。セッションにそのツールコールが含まれることを確認したら、`failproofai jev status`を再度実行します。最近の評価済みコール数が増加しているはずです。[ローカルダッシュボード](/ja/reference/local-dashboard#review-policy-activity)の**Policies → Activity**を開いて、コールのJev判定とモードを確認してください。observeモードでは、ポリシーの結果が引き続きコールを決定します。クリアはreviewableポリシーがマッチし、Jevが名前付きすべてのチェックをクリアした場合にのみ表示されます。通常の読み取りではクリアすべきポリシーがない場合もあります。

## Observeモード

デフォルトは`enforce`です。Jevの決定を変えずに監視するには、`observe`に切り替えてください。Jevは引き続き問い合わせを受けて判定を記録しますが、実際に適用されるのは正規表現の結果です。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`は設定（エンドポイントとキー）を保持しつつJevへの問い合わせを停止します。フックはJev設定なしの場合とまったく同様に正規表現ポリシーを実行し、`failproofai jev status`は「off (switched off)」と表示します。`--mode observe`または`--mode enforce`で再度切り替えられます。

同じプロバイダーで`setup`を再実行すると保存済みキーが維持されるため、モード切り替えはフラグ1つで完了します。プロバイダーを切り替えると最初からやり直しになり、そのプロバイダーのキーが求められます。リクエストを別のホストに移動する`--base-url`も同様です。保存済みキーは指定されたホスト、またはそのプロバイダー自身のAPIにのみ送信されます。

## 設定ファイル

すべては`~/.failproofai/jev.json`という1つのファイルに保存され、`setup`によって書き込まれます。

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| フィールド | 意味 |
| --- | --- |
| `provider` | `typesafe`・`openrouter`・`vercel`・`cloudflare`・`custom`、またはキーがこのファイルではなくFailproofAI Cloud接続から取得される`failproofai`（[FailproofAI Cloud経由のJev](/ja/reference/jev-cloud)を参照）。 |
| `apiKey` | `Authorization: Bearer <key>`として送信されます。 |
| `baseUrl` | `custom`では必須。それ以外ではプロバイダーのAPIベースを置き換えます。`https`必須。`localhost`へのプレーン`http`は`mode: observe`のみ許可されます。ローカルポートを認証するものはないため、プロキシがダウン中は判定対象のエージェントを含むマシン上の任意のプロセスが代わりに応答できます。 |
| `accountId` | Cloudflareのみ：32文字の小文字16進数。 |
| `model` | プロバイダーのデフォルトモデルIDを置き換えます。バージョン付きIDはJev 1.13を指定する必要があります。APIキーの形状の値は拒否されます（内容は表示されません）。`--model`にキーを貼り付けてもモデルとして保存または送信されることはありません。 |
| `timeoutMs` | ツールコールが正規表現結果を使用する前にJevの応答を待つ時間。100〜10000、デフォルト3000。 |
| `mode` | `enforce`（デフォルト）・`observe`・`off`（設定を保持してJevを実行しない）。 |

3つのルールによって保護されます。

- **オーナーのみ。** パーミッション`0600`で書き込まれます。他のユーザーやグループが読み書きできるコピーは**拒否**され、`chmod 600 ~/.failproofai/jev.json`を実行するか`setup`を再実行するまでフックは正規表現にフォールバックします。ディレクトリも確認されます。`~/.failproofai`は他の誰にも**書き込み可能**であってはなりません。ファイル自体のパーミッションに関係なく、そこに書き込めるユーザーはファイルを置き換えることができるからです。`setup`はその書き込みビットを見つけた場合に削除します。`failproofai jev status`は設定が拒否された場合にその旨とファイルに記載されているエンドポイントを表示します。他の誰かが変更した可能性があるため、`chmod`を実行する前に自分のものであることを確認してください。そのようなファイルで`setup`を再実行する場合、保存済みキーはプロバイダー自身のAPIにのみ引き継がれます。ファイルに記載されている他のエンドポイントにはキーの再入力（`--key-stdin`）、またはリクエストをプロバイダーに戻す`--base-url default`が必要です。
- **グローバルのみ。** リポジトリはJevを有効にしたり、別のエンドポイントに向けたり、モデルを選択したりすることはできません。プロジェクト内の`.failproofai/jev.json`は無視され、プロバイダー・URL・モデル・アカウントIDはそのファイルからのみ読み込まれます。リポジトリのエージェント設定で設定できる環境変数からは読み込まれません。（`FAILPROOFAI_HOME`は回避策にはなりません。failproofaiディレクトリ全体（ポリシーを含む）を移動するものであり、Jevのみをリダイレクトするものではありません。）
- **キーのみ環境変数から取得できます。** ファイルに`apiKey`がない場合、`FAILPROOFAI_JEV_API_KEY`がそのセッションに使用されます（`setup --key-from-env`でそのようなファイルを書き込みます）。ファイルに保存されているキーを置き換えることはなく、ファイルなしでJevを有効にすることもできません。変数が設定されていない場合、そのシェルではJevは単純にオフになります。`failproofai jev status`はその旨を表示し、終了コード0で終了し、設定はそのまま残ります（`status --json`は`"reason": "no-env-key"`とともに`"status": "key-missing"`を報告します）。`failproofaid`デーモンはシェルの環境を参照しないため、`failproofai config`でセットアップしたマシンでは、キーをファイルに保存してください。

## どのJevが応答するか

Failproof AIの判定しきい値はJev 1.13を基準に調整されているため、そのファミリー（`jev-1.13.x`またはOpenRouterの`typesafe/jev-1.13-<date>`）からの応答のみが使用されます。プロバイダーがJevをエイリアスのみで識別し、バージョンを報告しない場合（Vercel、およびバージョンを通知しないCloudflare）、応答は使用され未検証として記録されます。`custom`エンドポイントは応答したモデルを報告する必要があります。唯一の例外は設定したバージョンなしの`--model`名で、エコーバックされた場合は同様に未検証として記録されます。その他のバージョンを報告した応答、またはバージョンを報告しない`custom`応答は使用されず、そのコールは`model-mismatch`という理由で正規表現にフォールバックします。

## Jevが応答できない場合

以下のいずれも、そのコールの正規表現結果にフォールバックして理由とともに記録されます。`failproofai jev status`がそれぞれの集計を表示します。

| 理由 | 原因 |
| --- | --- |
| `timeout` | `timeoutMs`以内に応答なし。 |
| `http-429` | プロバイダーがキーをレート制限した。 |
| `rate-limited` | Failproof AI自身のリミッターが送信前にコールを保留した。毎秒5リクエスト、最大5のバーストが許可され、プロバイダーが`429`を返した後は一時停止。プロバイダー側ではない。 |
| `http-500`・`http-502`・`http-503`・… | プロバイダーでのサーバーエラー。正確なステータスが記録されます。 |
| `out-of-credits` | HTTP 402：プロバイダーアカウントにクレジットが残っていない。 |
| `provider-refused` | Cloudflareからの「Model execution failed (Payment error)」というHTTP 402：プロバイダーがこのリクエストでモデルの実行を拒否した。通常は請求の問題ではないため、クレジットを追加しても解決しません。 |
| `http-401`・`http-403` | キーが拒否された。 |
| `http-404` | `<base>/systemone`に何もサービスされていないため、ベースURLが誤っています。`/systemone`はベースURLに付加されるため、各プロバイダーはバージョンルートでこれを提供します。`failproofai jev models`でエンドポイントが実際に提供しているものを確認できます。 |
| `network` | エンドポイントに到達できなかった。 |
| `http-301`・`http-302`・`http-307`・`http-308` | エンドポイントがリダイレクトを返した。リダイレクトは決して追従されないため、応答は常に設定内のURLからのみ取得されます。`--base-url`を最終的なURLに設定してください。 |
| `malformed` | エンドポイントは応答したが、Jev形式の応答ではない。JSONではないボディ、または応答がないもの。 |
| `cloudflare-error`・`cloudflare-incomplete` | Cloudflareのエンベロープが失敗または未完了のジョブを報告した。 |
| `model-mismatch` | 1.13以外のJevバージョンが応答した、または`custom`エンドポイントが応答したモデルを報告しなかった。 |
| `request-cut` | **障害ではありません。** Jevは応答しましたが、コールの一部のみが送信されたため、応答はクリアを行いませんでした。[Jevが応答したが、コール全体に対してではない場合](#when-jev-answered-but-not-on-the-whole-call)を参照してください。 |

`failproofai jev status`は、`upstream-error`（応答がプロバイダー自身のエラーを含んでいた）や`config`などのまれな理由を表示することもあり、識別できない理由は`other`として集計されます。

`request-cut`は、`failproofai jev status`が他の理由とともに集計し、すべてのdenyが維持されるためここに含まれています。しかし、これはプロバイダーに関する問題ではありません。リクエストは届き、Jevは応答しました。上記のすべての行とは異なり、その応答は依然として有効です。Jev独自のdenyまたは警告は正規表現結果に加えて適用され、破棄されることはありません。したがって、これが続く場合は評価者に届くコールが全体を送信するには大きすぎることを意味し、エンドポイントの問題ではありません。クレジットの追加やURLの変更では解決しません。

## Jevが応答したが、コール全体に対してではない場合

さらに2つのケースがあり、いずれもJevが応答に失敗したわけではありません。いずれも、コール全体または会話のどれだけがひとつのリクエストに収まったかに関するものです。

**コール自体の一部が収まらなかった。** ツールコールは固定バジェット内で送信されますが、過大なもの（非常に大きな`Write`、巨大なMCPボディ、上限までパディングされたコマンド）は収まった部分だけで送信されます。Jevは引き続き応答し、その応答は有効です。Jev独自のdenyまたは警告は通常通り適用されます。しかし、コールの一部に対する判定はそのコール全体への判定ではないため、**クリア**はできません。したがって、すべてのポリシーdenyは維持され、コールは`request-cut`という理由でフォールバックとして記録されます。`failproofai jev status`がこれを上記の理由と並べて集計します。このルールが示すのは、コールを大きくするとクリアを失う可能性があり、クリアを得ることは決してできないということです。

**メッセージが収まらなかった。** 貼り付けた長いプロンプト、エージェントの最後のメッセージ、またはこの評価者自身のストアがすでに上限を設定していたプロンプト。**何も変わりません**。コールは他と同様に判定・クリア・記録され、フォールバックとしてカウントされません。入力した内容の長さが判定を決定することはなく、切り捨てが同意を生み出すこともありません。プロンプトが既に切り捨てられた状態で届いた場合、「あなたはこれをリクエストしなかった」という結論を導き出すことができなくなるだけで、そのような結論に至ることはありません。

2つの違いはテキストを誰が書いたかです。コールはエージェントのものであり、長さで重大性を減らせるルールはエージェントが利用できるものになります。プロンプトはあなたのものであり、その長さをシグナルとして扱うことは、仕様やスタックトレースを貼り付けることへの罰にしかなりません。

## マシンから送信されるもの

Jevが評価する各ツールコールについて、プロバイダーに1つのリクエストが送信されます。その内容は以下の通りです。

- ツールコール自体（APIキー・ベアラートークン・`KEY=`の代入などのシークレットはリダクションされます）
- 最近入力したプロンプト（エージェントのハーネスが追加したテキストを除く）
- 最新プロンプト前のエージェントの最後のメッセージ（エージェントが書いたものとしてラベル付け）
- パスがプロジェクト内かどうかなど、ローカルで計算された情報（最初にレビューされたコールでのセッション、[セッションにピン留めされた](/ja/reference/jev-intent#the-project-root)もの）および現在のgitブランチ

これはすべてあなたのキーの下で、設定内のエンドポイントにのみ送信されます。

## オフにする

```bash
failproofai jev remove
```

これにより`~/.failproofai/jev.json`が削除されます。次のツールコールからフックは以前と同様に正規表現ポリシーのみを実行します。`~/.failproofai/state/semantic/`以下のセッションごとのストア（`sessions/`に記録されたプロンプト、`roots/`にプロジェクトルート）はそのまま残り、期限切れになります。Jevへの問い合わせを停止しつつ設定を保持するには、代わりに`failproofai jev setup --mode off`を使用してください。

## コマンドリファレンス

| コマンド | 結果 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 1つのコマンドで設定。プロバイダーはURLのホストから決定 |
| `failproofai jev --url <url> --token <token>` | 同様だが、コマンドラインにキーが残る（シェル履歴とプロセスリストに表示される） |
| `failproofai jev setup --provider <kind> --key-stdin` | stdinからパイプしたキーで設定を書き込む |
| `failproofai jev setup --provider <kind>` | 同様だが、マスクされたプロンプトでキーを入力 |
| `failproofai jev setup --key-from-env` | キーを保存しない。セッションごとに`FAILPROOFAI_JEV_API_KEY`を読み込む |
| `failproofai jev setup --mode observe` | モードを切り替える（`enforce`・`observe`・`off`）。保存済みキーは維持 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | モデルまたはAPIベースをオーバーライド。`default`でオーバーライドをクリア |
| `failproofai jev setup --timeout-ms <n>` | コールごとのバジェットを変更 |
| `failproofai jev status [--json]` | 設定・パーミッション・最近のアクティビティを表示。キーは表示しない |
| `failproofai jev test [--json]` | 1つのライブリクエスト：レイテンシーと応答したバージョン |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | そのエンドポイントの`/models`が報告するモデルID一覧。設定されているものをマーク |
| `failproofai jev remove` | 設定を削除。Jevがオフになる |
