カスタムポリシーは、トレースや監査で検出した障害パターンを、エージェントの動作中にリアルタイムで実行される判断に変換します。ポリシーはアクションを許可したり、エージェントにガイダンスを提供したり、インシデントの再発を防ぐためにアクションを拒否したりできます。

ツール、パス、コマンド、環境、運用ルールに依存する動作にはカスタムポリシーを使用してください。既存のコントロールを再作成しないよう、まず[組み込みポリシーカタログ](/ja/policies/builtin-catalog)を確認してください。

## カスタムポリシーを作成する

<Tabs>
  <Tab title="ダッシュボード">
    1. **Admin → policy editor** に移動し、**New policy** を選択して、防止したい障害を説明します。
    2. ポリシーのソースを追加し、エディターで期待されるマッチと安全な非マッチをテストします。すべてのバリデーションエラーを解消してください。
    3. ドラフトを保存し、**Publish version** を選択してイミュータブルなバージョンを作成します。
    4. **Admin → enforcement** に移動し、**observe** モードでテストマシンにバージョンをデプロイして、**Observe → policy** でその判断を確認してから適用します。

    ![カスタムポリシーを作成・公開するために使用するポリシーエディター。](/images/dashboard/policy-editor.png)
  </Tab>
  <Tab title="CLI">
    1. `failproofai publish --init` でスターターポリシーを生成するか、`.failproofai/policies/checkout-policies.ts` を手動で作成します。規約ファイル名は `policies.js`、`policies.mjs`、または `policies.ts` で終わる必要があります。
    2. `customPolicies.add()` で1つ以上のポリシーを登録します。
    3. このマシンにすぐファイルを適用します: `failproofai policies -i -c ./.failproofai/policies/checkout-policies.ts`

  </Tab>
</Tabs>

## 狭いルールから始める

このポリシーは、コマンドが本番環境をターゲットにしている場合のみ、破壊的な Kubernetes コマンドをブロックします。この正確な障害モード以外のものはすべて `allow()` を返します。

```ts
import { customPolicies, allow, deny } from "failproofai";

const DESTRUCTIVE_KUBECTL = /\bkubectl\s+(delete|replace)\b/i;
const PRODUCTION_TARGET = /(?:--context|--namespace|-n)\s+(prod|production)\b/i;

customPolicies.add({
  name: "block-destructive-production-kubectl",
  description: "Block destructive Kubernetes commands against production",
  match: { events: ["PreToolUse"] },
  fn: async ({ toolName, toolInput }) => {
    if (toolName !== "Bash") return allow();

    const command = String(toolInput?.command ?? "");
    if (!DESTRUCTIVE_KUBECTL.test(command)) return allow();
    if (!PRODUCTION_TARGET.test(command)) return allow();

    return deny(
      "Destructive production Kubernetes commands require the approved deployment workflow.",
    );
  },
});
```

優れたポリシーは1文で説明できるほど絞り込まれています。エージェントの意図ではなく、観察可能なアクションにマッチさせ、ルールが適用されない場合はすぐに `allow()` を返してください。

## 判断を選択する

| ヘルパー | 結果 | 使用するタイミング |
| --- | --- | --- |
| `allow(reason?)` | 操作を続行します。 | ポリシーが適用されない場合、またはアクションが安全な場合。 |
| `instruct(reason)` | 操作を続行し、チャンネルを持つハーネスでエージェントに理由を伝えます。 | 不変条件を強制せずにエージェントをより良いアプローチに誘導したい場合。 |
| `deny(reason)` | ブロッキング判断を消費することが確認されているハーネスとイベントのペアでブロックされます。 | アクションを続行させてはならない場合。 |

回復が必要なエージェント向けに理由を記述してください。何が検出されたか、代わりに何をすべきかを説明してください。

### `instruct()` が実際に届く場所

`instruct()` はハーネスに追加コンテキストのチャンネルが必要です。6つのハーネスは一部またはすべてのイベントにチャンネルを持たず、そこでは操作が許可されてメッセージが stderr に書き込まれますが、エージェントはそれを読みません。

| ハーネス | 命令が届くイベント |
| --- | --- |
| Claude、Codex、Copilot、Cursor、Devin、OpenCode | `PreToolUse`、`PostToolUse`、`UserPromptSubmit`、`PermissionRequest` は追加コンテキストとして届きます。`Stop` と `SubagentStop` はリトライチャンネルを通じて届きます。その他のイベントはすべてハーネスが無視するメッセージを出力します。 |
| Antigravity | `UserPromptSubmit` と `Stop` のみ。 |
| Factory、Pi、OpenClaw | `Stop` のみ。 |
| Hermes、Goose | なし。常に allow と stderr のメモのみ。 |

29の正規イベントをすべて発火するハーネスはないため、最初の行は各ハーネスがインストールするもので限定されます — 命令はそのハーネスが実際に発火するイベントにのみ届きます。依存する前に、[エージェントハーネス](/ja/reference/harnesses)でハーネスごとのインストール済みイベントセットを確認してください。

<Warning>
  安全境界に `instruct()` を使用しないでください。Hermes と Goose ではエージェントに届かず、Antigravity、Factory、Pi、OpenClaw ではツールイベントで届きません。アクションを防止する必要がある場合は `deny()` を使用してください。
</Warning>

## ポリシーオブジェクト

```ts
customPolicies.add({
  name: "policy-name",
  description: "What this policy prevents",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => allow(),
});
```

| フィールド | 必須 | 説明 |
| --- | --- | --- |
| `name` | はい | ポリシーの安定した識別子。ファイル間で名前を一意に保ってください。 |
| `description` | いいえ | ポリシーの一覧や判断に表示される人間が読める目的。 |
| `match.events` | いいえ | ポリシーを呼び出すイベントタイプ。`match` を省略すると、利用可能なすべてのイベントに対して呼び出されます。 |
| `fn` | はい | `allow`、`instruct`、または `deny` の結果を返す同期または非同期関数。 |

`fn` 内でツールをフィルタリングしてください。`match.toolNames` はパブリックなカスタムポリシー型には含まれていません。

パックに公開されたポリシーには `category` と `defaultEnabled` の2つのフィールドが追加される場合があります。[ファイルからパックへ](#from-a-file-to-a-pack)を参照してください。

## ポリシーコンテキスト

すべてのポリシーは `PolicyContext` を受け取ります。

| フィールド | 型 | 含まれる内容 |
| --- | --- | --- |
| `eventType` | `HookEventType` | 現在評価されている正規化されたイベント。 |
| `toolName` | `string \| undefined` | `Bash`、`Read`、`Write`、`Edit` などの正規ツール名。 |
| `toolInput` | `Record<string, unknown> \| undefined` | 現在のツール呼び出しの正規化された入力。 |
| `payload` | `Record<string, unknown>` | 完全な正規化されたイベントペイロード。 |
| `session` | `SessionMetadata \| undefined` | セッション ID、作業ディレクトリ、トランスクリプトパス、パーミッションモード、および利用可能な場合のハーネスメタデータ。 |
| `cli` | `string \| undefined` | `claude`、`codex`、`cursor` などのソースエージェントハーネス。 |
| `params` | `Record<string, unknown>` | このポリシーのパラメーター。組み込みポリシーやパックポリシーはスキーマを宣言し、ユーザーが設定した値がデフォルト値の上にマージされます。カスタムファイルのポリシーはスキーマを宣言しないため、名前の下で設定されたものを受け取り、何も設定されていない場合は `{}` を受け取ります。 |

すべてのオプション値は本当にオプションとして扱ってください。エージェントのバージョンやイベントタイプによって提供されるフィールドが異なります。

### 共通のツール入力

Failproof AI はサポートされているハーネス間で共通ツールを正規化するため、ポリシーは通常1つの入力形状を使用できます。

| ツール | 共通フィールド |
| --- | --- |
| `Bash` | `command` |
| `Read` | `file_path` |
| `Write` | `file_path`、`content` |
| `Edit` | `file_path`、`old_string`、`new_string` |
| `Grep` | `pattern`、`path` |

ツール入力値は `unknown` として型付けされているため、防御的なキャストを使用してください。

```ts
const command = String(ctx.toolInput?.command ?? "");
const filePath = String(ctx.toolInput?.file_path ?? "");
```

## イベントを選択する

| イベント | 実行タイミング | 典型的な用途 |
| --- | --- | --- |
| `PreToolUse` | ツールが実行される前。 | コマンド、書き込み、読み取り、外部アクションをブロックまたはガイドします。これがガードです。 |
| `PostToolUse` | ツールがすでに実行された後。 | モデルが読む結果を検査または置き換えます。副作用（書き込みやコマンド）はすでに発生しているため、取り消すことはできません。また、12のハーネスのうち10では判断が何も止められません。Codex と Copilot だけが消費しますが、そこでもモデルが読む結果を置き換えるだけで、呼び出しを防ぐわけではありません。ガードとして使用しないでください。 |
| `PermissionRequest` | エージェントがパーミッションを要求した時。 | 組織固有のパーミッションルールを適用します。 |
| `UserPromptSubmit` | 送信されたプロンプトが続行される前。 | 禁止された指示を拒否したり、ワークフローガイダンスを追加したりします。 |
| `Stop` | エージェントが終了しようとした時。 | ローカル検証ステップなど、到達可能な完了条件を要求します。 |
| `SubagentStop` | サブエージェントが終了しようとした時。 | 委任された作業が親に戻る前にゲートします。 |
| `SessionStart` / `SessionEnd` | セッションの境界で。 | セッションレベルの状態を記録または確認します。 |

イベントの可用性とブロッキング動作はエージェントハーネスによって異なり、その差は大きいです。Failproof AI は Goose や Hermes に `Stop` フックをインストールしないため、どちらでもストップゲートは発火しません。混合フリートでイベントに依存する前に[エージェントハーネス](/ja/reference/harnesses)を確認してください。

<Accordion title="すべてのポリシーイベント名">
  `SessionStart`、`SessionEnd`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PermissionDenied`、`PostToolUse`、`PostToolUseFailure`、`Notification`、`SubagentStart`、`SubagentStop`、`TaskCreated`、`TaskCompleted`、`Stop`、`StopFailure`、`TeammateIdle`、`InstructionsLoaded`、`ConfigChange`、`CwdChanged`、`FileChanged`、`WorktreeCreate`、`WorktreeRemove`、`PreCompact`、`PostCompact`、`Elicitation`、`ElicitationResult`、`UserPromptExpansion`、`PostToolBatch`、`Setup`。これが、各ハーネス固有のイベントボキャブラリーが正規化される29の正規イベント名の完全セットです。
</Accordion>

## 共通のポリシーパターンを作成する

### 保護されたパスへの書き込みをブロックする

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "block-generated-file-edits",
  description: "Require generated files to be changed through their generator",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();

    const filePath = String(ctx.toolInput?.file_path ?? "");
    if (!/(^|\/)(dist|generated)\//.test(filePath)) return allow();

    return deny("Edit the source and run the generator instead of changing generated output.");
  },
});
```

### ノンブロッキングなガイダンスを提供する

```ts
import { customPolicies, allow, instruct } from "failproofai";

customPolicies.add({
  name: "prefer-reviewed-deploy-command",
  description: "Guide agents toward the reviewed deployment wrapper",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();

    const command = String(ctx.toolInput?.command ?? "");
    if (!/^kubectl\s+apply\b/.test(command.trim())) return allow();

    return instruct("Use ./scripts/deploy-reviewed instead of invoking kubectl directly.");
  },
});
```

### セッション完了をゲートする

```ts
import { execFileSync } from "node:child_process";
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "require-clean-typecheck",
  description: "Require the project typecheck to pass before the agent finishes",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow();

    try {
      execFileSync("bunx", ["tsc", "--noEmit"], {
        cwd,
        stdio: "ignore",
        timeout: 8_000,
      });
      return allow();
    } catch {
      return deny("Fix the typecheck errors before finishing the task.");
    }
  },
});
```

<Warning>
  拒否された `Stop` イベントによってエージェントがリトライする可能性があります。現在の環境でエージェントが満たせる条件のみにゲートし、すべてのサブプロセスやネットワーク呼び出しに制限を設けてください。
</Warning>

## ポリシーファイルを読み込む

### 規約ファイル

規約ファイルは自動的に読み込まれます。

```text
<project>/.failproofai/policies/security-policies.ts
~/.failproofai/policies/personal-policies.mjs
```

- プロジェクトとユーザーのポリシーディレクトリはどちらも読み込まれます。
- ファイルは各ディレクトリ内でアルファベット順に読み込まれます。
- ファイルは `policies.js`、`policies.mjs`、または `policies.ts` で終わる必要があります。
- 1つのファイルに複数の `customPolicies.add()` 呼び出しを含めることができます。
- ローカルモジュールからの相対インポートがサポートされています。
- プロジェクトポリシーはコミットできるため、同じルールがリポジトリに従います。

<Warning>
  `policies.{js,mjs,ts}` で終わらない名前のファイルはスキップされます。インストールされているように見えても、何も適用されません。ローダーはスキップされたすべてのファイルを名前変更すべき名前とともに一覧表示します。ポリシーが有効だと思い込まず、その警告を読んでください。このリポジトリでは `block-version-bumps.mjs` がそのような形でデプロイされており、バッドなバージョンバンプの後に書かれたガードが一度も実行されていませんでした。
</Warning>

`~/.failproofai/policies/` には、あなたが配置していない2つのサブディレクトリもあります。フリート管理デプロイメント用の `cloud-policies/` とインストール済みパック用の `packs/` です。ローダーはどちらにも降りていかないため、未検証の規約ポリシーとして取り込まれることはありません。

### 検出されたポリシーをオフにする

`policies-config.json` の2つのキーで、ファイルを削除したり名前を変更したりせずに規約ポリシーをオフにできます。

| キー | 効果 |
| --- | --- |
| `disabledCustomPolicies` | 登録されないソース修飾ポリシー ID の配列。 |
| `customPoliciesEnabled` | `false` に設定すると `.failproofai/policies/` の読み込みを完全に停止します。省略した場合は有効です。 |

[ローカルダッシュボード](/ja/reference/local-dashboard)の **Policies → Configure** タブで `disabledCustomPolicies` を設定できます。`customPoliciesEnabled` は `failproofai config` で設定するか、手動で設定します。

### 明示的なファイル

バリデーションや設定でエントリーファイルを直接指定する場合は、明示的なパスを使用してください。

```bash
failproofai policies --install \
  --custom ./security.policies.ts \
  --custom ./workflow.policies.ts \
  --scope project
```

明示的なファイルが最初に読み込まれ、次にプロジェクト規約ファイル、ユーザー規約ファイルの順に読み込まれます。両方のパスで検出されたファイルは1回だけ読み込まれます。

## 検証とテスト

`-c` は `--custom` の短縮形、`-i` は `--install` の短縮形です。任意のパス、任意のファイル名でファイルをすぐに適用します。

```bash
failproofai policies -i -c ./checkout-policies.ts
failproofai policies
```

ブロックしたいことをエージェントに実行させ、それが拒否されることを確認してください。何も公開されず、他のマシンへの影響もありません。

バリデーションはプロダクションローダーを通じてモジュールを実行し、少なくとも1つのポリシーが登録されることを確認します。ファイルの欠如、構文エラー、未解決のインポート、トップレベルの例外、モジュール読み込みタイムアウトをキャッチします。マッチロジックが正しいかどうかは証明しません。

少なくとも以下のケースをテストしてください。

- 意図したポリシー理由を生成するマッチが必要な1つのアクション。
- `allow()` を返す必要がある近いが安全な1つのアクション。
- 欠落または不正な形式のツールフィールド。
- 代替コマンド構文、パス、クォート、ケーシング、ホワイトスペース。
- 利用できないサブプロセスまたはネットワーク依存関係。

ローカルダッシュボードの **Policies → Activity** でカスタムポリシーに結果を帰属させてください。異なる組み込みポリシーが判断した場合、ブロックされたテストは十分ではありません。

## ランタイムの動作

- 組み込みポリシーはカスタムポリシーより先に評価されます。
- 最初の `deny` でそれ以降のポリシー評価が停止します。
- ポリシーがイベントを拒否しない場合、複数の `instruct` 結果を組み合わせることができます。
- ポリシー関数の実行期限は10秒です。トップレベルのモジュール読み込みも同じ期限です。
- 例外またはタイムアウトはログに記録され、`allow()` として扱われます。
- 読み込みに失敗した規約ファイルはスキップされ、他のカスタムファイルと組み込みポリシーは続行されます。
- Observe モードはポリシーを実際に実行し、allow 以外の判断を適用せずに記録します。2つのレイヤーがそれを設定します。公開するパックに対する `failproofai publish --effect observe` と、クラウドデプロイメントに対する `fp fleet deploy <machine> --add <id>:observe`。どちらの場合もポリシーは適用中と同じ10秒の期限で評価されるため、タイムアウトするポリシーは allow として記録されます。

### ローダーが代わりにフェールクローズする場所

上記のフェールオープンルールは、自分でドロップしたファイルをカバーします。2つのパスは意図的に逆のことを行います。どちらも、このマシンが持っていない適用があると伝えられたことを意味するからです。

| 状況 | 結果 |
| --- | --- |
| 選択されたパックを読み込めないか、固定されたダイジェストが一致しない | そのパックが宣言したスコープのすべてのイベントが、`pack/failproofai-pack-unavailable` に帰属して拒否されます。`UserPromptSubmit` は拒否の代わりに instruct を行うため、修正に必要なエージェントからロックアウトされることはありません。読み取れないパックメタデータは拒否スコープを狭めるのではなく広げます。 |
| セットアップを完了したマシンで `failproofaid` デーモンに到達できない | すべてのイベントが拒否されます。設定は読み込まれず、カスタムポリシーも実行されません。到達できなかったデーモンはそれらを実行できなかったからです。プロトコルバージョンの不一致も、`failproofai config` を指定するメッセージとともに拒否されます。 |

セットアップを完了したマシンでは、`failproofaid` が唯一の評価者であるため、`fn` はフックプロセスではなくデーモンのウォームワーカー内で実行されます。フッククライアントは接続に150ミリ秒、応答に30秒を許可しており、各ポリシー関数に設定された10秒の固定期限を十分に上回ります。

ポリシーモジュールは決定論的で高速に保ってください。トップレベルのネットワーク呼び出しやサーバー起動を避けてください。`fn` 内の作業に制限を設け、依存関係の失敗をキャッチし、その失敗がオペレーションを許可すべきか拒否すべきかを意図的に選択してください。

## ファイルからパックへ

パックは、ポリシーファイルを他のマシンがインストールできるものにする方法です。2つのコマンドで何もない状態から公開済みパックまで進められます。

```bash
failproofai publish --init
failproofai publish
```

`--init` はパックの名前を尋ね、`<name>.mjs` を書き込んで停止します。ファイルは空欄のあるテンプレートではなく、`git push --force` をすでにブロックする1つのポリシーです。そのため最初に編集するのは動作するものです。`failproofai policies -i -c ./<name>.mjs` でローカルに証明し、それを保持する git リポジトリ内から `failproofai publish` を実行してください。

パックにポリシーを含める場合、2つのフィールドが重要です。

| フィールド | 機能 |
| --- | --- |
| `category` | `failproofai policies add <owner>/<repo> --category git,database` が選択する対象。 |
| `defaultEnabled` | `failproofai policies add <owner>/<repo>` だけでこのポリシーがオンになるかどうか。デフォルトは `false`。 |

`--effect` はポリシーごとではなくパックごとに設定されます。`failproofai publish --effect observe` は、ポリシーが決定したであろうことを記録し、何もブロックしないパックを公開します。デフォルトは `enforce` です。これはクラウド接続なしの単一マシンでの observe モードです — 記録された判断はローカルダッシュボードの **Policies → Activity** で確認できます。

パックのバージョンはビルドされた12文字の短いコミット sha であるため、`publish` は git チェックアウト外やダーティーツリーでは拒否されます。完全なフローは[パックを公開する](/ja/policies/publish-a-pack)を、バージョンのインストール解決方法は[ポリシーパック](/ja/policies/packs)を参照してください。

## API エクスポート

| エクスポート | 目的 |
| --- | --- |
| `customPolicies.add(policy)` | モジュール読み込み時にカスタムポリシーを登録します。 |
| `allow(reason?)` | 操作を許可します。 |
| `instruct(reason)` | 操作を許可し、サポートされている場合にガイダンスを提供します。 |
| `deny(reason)` | サポートされている場合に操作をブロックします。 |
| `getCustomHooks()` | モジュールレジストリに現在登録されているポリシーを返します。 |
| `clearCustomHooks()` | そのレジストリをクリアします。主にテストとローダー向けです。 |

TypeScript は `PolicyContext`、`PolicyResult`、`CustomHook`、`PolicyDecision`、`PolicyFunction` をエクスポートします。
