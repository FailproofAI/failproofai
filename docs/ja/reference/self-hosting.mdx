## 前提条件

- Kubernetes 1.27 以降（cluster-admin アクセス権限あり）
- Kustomize 対応の `kubectl`
- Helm 3
- プライベートリポジトリ `ghcr.io/agenteye-enterprise` のイメージへのアクセス
- 2 つの DNS 名（ダッシュボード用とインジェスト用それぞれ 1 つ）
- PostgreSQL および ClickHouse 用の永続ストレージ
- cert-manager と Traefik、またはオーバーレイに組み込まれた同等のイングレス・証明書インフラ
- 本番環境での OTP ログインおよび通知用 SMTP

ソースツリーには AWS/EKS 向けオーバーレイと GCP/GKE 向けオーバーレイが別々に用意されています。証明書、ロードバランサー、バックアップの手順を混在させないでください。GKE は独自の DNS-01、GCS、およびオートスケーリング設定を使用します。

## デプロイメント手順

<Steps>
  <Step title="クラスターの準備">
    cert-manager とパブリック/ダッシュボード用イングレスコントローラーをインストールし、ロードバランサーを確認した後、名前空間、イメージプル認証情報、データベース認証情報、ブートストラップ管理者キー、認証/SMTP シークレットを作成します。
  </Step>
  <Step title="パブリックドメインの設定">
    オーバーレイが生成するドメイン環境ファイルに `INGEST_DOMAIN` と `DASHBOARD_DOMAIN` を設定し、対応するロードバランサーを向く DNS レコードを作成します。
  </Step>
  <Step title="プラットフォームオーバーレイの適用と確認">
    customer/EKS または GCP オーバーレイを使用します。レンダリングされた Kustomize の出力を確認し、適用した後、マシンを登録する前にすべてのワークロードと証明書が意図した状態になっていることを確認します。
  </Step>
  <Step title="アクセスとインジェストのブートストラップ">
    保護された管理者としてサインインし、組織スコープのマシンキーを作成して、パブリックのインジェストエンドポイントを通じて小規模なテストセッションを送信します。
  </Step>
</Steps>

## 必須サービスとオプションサービス

| コンポーネント | 要件 |
| --- | --- |
| ClickHouse | 必須。正規のイベントストアがない場合、サーバーは起動を拒否します。 |
| PostgreSQL | ユーザー、組織、保存オブジェクト、コントロールプレーンの状態管理に必須。 |
| Redis | オプション。利用できない場合、サーバーとダッシュボードはデータベースバックの動作に低下します。 |
| SMTP | 開発環境ではオプション。本番環境のメール OTP と通知配信には必須。 |
| Evaluator | オプション。`EVALUATOR_ENDPOINT` がない場合、自動評価は無効のままです。 |
| Assistant/audit LLM | オプション。LLM 接続が設定されるまで、アシスタントおよび LLM バックの監査機能は動作しません。 |
| オブジェクトストレージバックアップ | PostgreSQL および ClickHouse のバックアップアーカイブとして強く推奨。 |

### 監査キャパシティと失敗時の配信

利用可能な場合は専用の audit-agent デプロイメントで監査を実行してください。各 audit-agent ポッドはデフォルトで 1 件の調査を受け付けます。ポッドあたりの並行数を増やすのではなく、レプリカ数でスループットをスケールしてください（ただしメモリも合わせて増やす場合を除く）。サーバーは `サーバーレプリカ数 × AUDIT_WORKERS` の監査を同時に実行できるため、ディスパッチャーのキャパシティは audit-agent フリートを埋めるのに十分な大きさにする必要があります。

すべての audit-agent スロットが使用中の場合、監査は最大でケイデンスの 4 分の 1（最大 6 時間）待機して再試行します。空きスロットが確保できなければ、実行は所見なしで完了し、失敗メールが送信されます。「busy」失敗が繰り返される場合は、audit-agent レプリカを増やすか、スケジュールアンカーをより大きく分散させることを検討してください。「shutting down」失敗が繰り返される場合は、キャパシティ不足ではなく、不安定なポッドまたはループするロールアウトが原因です。

失敗通知には、有効なメールチャンネルと SMTP が必要です。通知には監査の受信者が使用され、監査にメールチャンネルがない場合は `alerts.email_default_recipients` にフォールバックします。

## 認証とメール

ダッシュボードはメールとワンタイムコードを使用します。SMTP がない場合、開発デプロイメントでは OTP コードがサーバー出力にログ出力されます。`SMTP_HOST` が設定されている場合、ユーザー名、パスワード、送信者は一括で必須となり、いずれかが欠けているとサーバーは起動を拒否します。

`SMTP_TLS` はブール値です。サポートされている暗号化トランスポートは STARTTLS（通常はポート 587）です。ポート 465 での暗黙的な SMTPS は現在のサーバートランスポートではサポートされていません。

OTP、アラート、インシデント、監査メールのディープリンクにはパブリックダッシュボード URL が使用されるため、正しく設定してください。コードをリクエストできるのは組織メンバーシップを持つユーザーに限られます。各組織は **管理 → 設定** で独自のメンバーサインインをさらに制限できます。

## マルチテナント要件

2 つ目の組織を作成する前に、強力で安定した組織 ClickHouse 導出シークレットを設定し、すべてのサーバーレプリカで同一の値を保持してください。調整されたマイグレーションなしにローテーションすると、組織固有の ClickHouse ユーザーが孤立する可能性があります。

インスタンス管理者リスナーは内部にとどめてください。提供されているオペレーターコンソールはオプトインで、パブリックイングレスではなく `kubectl port-forward` 向けに設計されています。有効にするには、専用の強力な API キー、スーパー管理者のメールボックス、動作する SMTP の二要素配信が必要です。

### ブレークグラス組織 CLI

`agenteye-orgctl` はサーバーイメージ内に同梱されており、PostgreSQL と ClickHouse に直接接続します。パブリックサーバーまたはオペレーターコンソールが正常でない場合でも使用できます。

```bash
kubectl -n agenteye exec deploy/server -- \
  agenteye-orgctl org create --slug acme --name "Acme Corp"
kubectl -n agenteye exec deploy/server -- agenteye-orgctl org list
kubectl -n agenteye exec deploy/server -- \
  agenteye-orgctl member add --org acme --email ops@acme.com --set admin --protected
```

サポートされている組織操作には、作成、一覧表示、名前変更、ソフト削除、復元、ClickHouse ユーザーの再プロビジョニング、請求日管理、フィーチャーフラグ、および不可逆なパージが含まれます。メンバー操作には、追加、一覧表示、更新、削除、権限オーバーライド、保護管理者状態の管理が含まれます。

パージの前にソフト削除を行ってください。`org purge` は不可逆であり、事前に組織を削除しておく必要があります。保護されたメンバーは、オペレーターが明示的に保護を解除するまで、組織の通常のユーザーページから削除または降格することはできません。

## 本番環境準備チェックリスト

- インジェストとダッシュボードの DNS が意図した異なるイングレスパスに解決される。
- TLS が有効である。デプロイメントで必要な場合はインジェストに相互 TLS を使用する。
- PostgreSQL および ClickHouse のボリュームにキャパシティアラートが設定されている。
- バックアップが両方のデータストアを含み、テスト済みのリストア手順が用意されている。
- ヘルスチェックがインジェストの沈黙、失敗したワークロード、証明書の期限切れ、ストレージ圧迫、古いバックアップを検知してアラートを送信する。
- 既存のクラスターログパイプラインを重複させることなく、構造化ログが収集されている。
- Evaluator、監査、アラートワーカーの並行数は、キュー測定の根拠なしに変更していない。
- アップグレード前に、固定されたアプリケーションリリースとロールバック手順が記録されている。
