ダッシュボードは、保存済みクエリを組み合わせた運用ビューです。利用可能なすべてのメトリクスではなく、誰かが下すと想定される意思決定を中心に構成してください。

ダッシュボードはクラウド向けの機能です。`localhost:8020` のローカルダッシュボードはポリシーアクティビティ、プロジェクト、セッション、監査結果をカバーしますが、保存済みクエリもタイルも持ちません。そのため、接続したことのないマシンではここで構築できるものは何もありません。詳細は[ローカルダッシュボード](/ja/reference/local-dashboard)を参照してください。

## ダッシュボードの作成

<Tabs>
  <Tab title="ダッシュボード">
    1. **Analyze → Queries** に移動し、保存済みクエリを作成または開いて、その結果を検証します。
    2. **add to dashboard** を選択し、既存のダッシュボードを選ぶか、**Analyze → Dashboards** で新規作成します。
    3. ダッシュボードを開き、編集モードに入り、タイルを配置してレイアウトを保存します。
    4. タイルの背後にあるデータやフィルターを変更する必要がある場合は、クエリに戻ります。

    ![イベント量、エラー、レイテンシ、モデルトークン使用状況の保存済みクエリから構成されたダッシュボード。](/images/dashboard/dashboard-fleet.png)
  </Tab>
  <Tab title="CLI">
    ダッシュボードの CRUD は現在のクラウド CLI では公開されていません。CLI を使用して保存済みクエリを作成・検証してから、UI でダッシュボードに追加してください。

    ```bash
    fp query schema
    fp query run --sql "select count(*) from analytics.events"
    fp query create "event volume" --sql "select count(*) from analytics.events"
    fp query run "event volume"
    ```

    まず `--sql` で SQL を実行してください。同じ読み取り専用の分析プールに対して実行され、何も保存されないため、タイルよりも先に不正なカラム名を発見できます。`--sql @file.sql` はファイルからステートメントを読み込みます。`fp query schema` はクエリ可能なテーブルとそのカラムを一覧表示します。テーブル名を渡すと1つに絞り込めます。

    保存済みクエリは id ではなく**名前**で指定します（例：`fp query run "event volume"`）。`fp query list` は `--show-id` を渡さない限り生の id を非表示にするためです。UUID 形式の id も使用可能です。

    パラメータ付きタイルの場合、繰り返し指定可能な `--arg` で各位置パラメータ `$1..$N` を順番にバインドします（例：`fp query run <name> --arg checkout-agent`）。

    `--limit` と `--all` はテーブルプレビューの上限のみを調整します。`--json` は常にすべての行を `{columns: [{name, type}], rows: [[...]], truncated, elapsed_ms}` の形式で返します。

    | サブコマンド | 必要な権限 |
    | --- | --- |
    | `query list`, `query show`, `query schema` | `queries:read` |
    | `query create`, `query update` | `queries:write` |
    | `query run` | `queries:run` |
    | `query delete` | `queries:delete` |

    クエリの**名前**を受け取るすべてのサブコマンドは、まず組織のクエリ一覧を取得して名前解決を行います。そのため、`query create`、`query update`、`query delete`、`query run <name>` は上記の権限に加えて `queries:read` も必要です。`fp query run --sql` と `fp query schema` のみ不要です。

    `fp query` はいずれも API キーモードではブロックされないため、ダッシュボードのクエリは CI から作成・検証できます。
  </Tab>
</Tabs>

有用なダッシュボードグループの例：

- **モデル：** ボリューム、レイテンシ、トークン使用量、エラー率、評価スコア。
- **評価：** エージェントまたは環境別の成功率とスコアの推移。
- **ツール：** 呼び出し量、失敗率、実行時間、繰り返し呼び出し。
- **フックとポリシー：** 判定、拒否、ポリシーマッチ率。
- **カスタムワークフローメトリクス：** 独自のイベントフィールドと SQL による結果。

保存済みクエリから始めて結果を検証し、タイルとして追加してください。テストトラフィックがリグレッションを隠さないよう、本番環境と開発環境のフィルターを明示してください。

<Warning>
  行数をカウントするフックタイルは誤った分母を報告します。デフォルトのフック詳細度では、すべての deny と instruct が `hook_triggered` / `hook_completed` のペアとして出力され、observe モードの allow も同様です。通常の allow はセッション、イベント、ツール、ポリシー帰属ごとに1分あたり `failproofai_allow_count` を持つ単一の `hook_completed` にロールアップされます。行数をカウントするのではなく、このフィールドを合計してください。そうしないと、数万件の呼び出しを評価したフリートが数百件しか評価していないように見えます。詳細は[ポリシー判定](/ja/sessions/policy-decisions)と[フック](/ja/sessions/hooks)を参照してください。
</Warning>

<Tip>
  すべてのダッシュボードにオーナーと回答すべき問いを設定してください。例：「checkout-agent の信頼性は先週より悪化しているか？」
</Tip>
