エラー画面では、セッション全体を障害起点で確認できます。エラータイプ、エージェント、環境、モデル、ツール、時間枠でグループ化することで、繰り返し発生する運用上の問題を特定できます。

## エラーを調査する

<Tabs>
  <Tab title="ダッシュボード">
    1. **Observe → Errors** に移動します。
    2. 環境、イベントタイプ、エラータイプ、エージェント、セッション ID、または検索テキストでフィルタリングします。
    3. グループ化されたエラーを展開して発生件数を確認します。行を選択すると、該当セッション内の正確なイベントが開きます。
    4. 代表的なエラーのベルアイコンを選択すると、類似エラーに対するアラートを設定できます。

    ![障害ヒストグラム、グループ化されたエラー、アラート作成コントロールが表示されたエラーページ。](/images/dashboard/errors.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp errors --env production --since 24h
    fp errors --error-type TimeoutError --agent-id checkout-agent
    fp errors --aggregate --env production --since 7d
    ```

    エラーサマリーの背後にある生のペイロードが必要な場合は、`fp events --full --session-id <id>` を使用してください。
  </Tab>
</Tabs>

## エラー画面を活用するケース

- 本番環境で最も頻繁に発生するエラークラスを特定する。
- 特定のツールやモデルがスパイクの原因かどうかを判断する。
- 集計カウントから代表的なセッションに直接ジャンプする。
- 再発に対するアラートを作成する。
- 影響を受けた対象を監査に含める。

エラーとは観測されたイベントです。評価の失敗は品質に関する判断であり、監査の所見は調査済みの障害パターンです。どのレスポンスワークフローを使用するかを決定する際は、これらの区別を意識してください。
