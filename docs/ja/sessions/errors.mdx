エラー画面では、セッション全体を障害優先で確認できます。環境、イベントタイプ、エラータイプ、エージェント、セッションでフィルタリングし、時間範囲を絞り込むことで、繰り返し発生する運用上の問題を特定できます。

## エラーを調査する

<Tabs>
  <Tab title="ダッシュボード">
    1. **Observe → Errors** に移動します。
    2. 環境、イベントタイプ、エラータイプ、エージェント、セッション ID、または検索テキストでフィルタリングします。
    3. 行を選択すると、該当セッション内の正確なイベントが開きます。
    4. 代表的な行の **alert** を選択して、類似エラーのアラートを作成します。

    ![障害ヒストグラム、フィルタリングされたエラーイベント一覧、および行ごとのアラートコントロールを表示したエラーページ。](/images/dashboard/errors.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp errors --since 24h
    fp errors --error-type TimeoutError --agent-id checkout-agent
    fp errors --event-type tool_result --since 24h
    fp errors --aggregate --env local --since 7d
    ```

    ツールの失敗は、単純な `error` イベントではなく、エラー状態の `tool_result` イベントとして記録されます。そのため、`--event-type tool_result` を使用することでツールの失敗をモデルやランタイムの失敗と区別できます。`is_error` と `error_type` はすべての行においてサーバー側で計算されるカラムであり、いずれのモードもペイロードをパースしません。

    フィルター値を推測する代わりに、有効な値を確認してください。`fp list error_types`、`fp list agents`、`fp list envs`、`fp list event_types` を使用します。

    **`fp errors` の 5 つのフィルターはそれぞれ値を 1 つだけ受け付けます** — `--env`、`--error-type`、`--event-type`、`--agent-id`、`--session-id`。（`--search` は例外で、繰り返し指定できます。）`fp events` および `fp sessions` の同名フラグは繰り返しまたはカンマ区切りの値を受け付けるため、`--env prod,staging` はそちらでは有効ですが、こちらではリテラル文字列 `prod,staging` としてのみマッチします。その場合、エラーではなく空の結果が返され、「エラーなし」として解釈されます。

    デーモンは設定を変更するまでイベントに `local` タグを付けるため、標準インストール環境では `--env production` は何もマッチしません。[環境ラベルを変更する](/ja/reference/events-and-configuration#change-an-environment-label) を参照してください。

    `--all` は `--limit`（デフォルト 50）までのみ自動ページネーションを行います。それ以上取得したい場合は `--all --limit 500` のように指定してください。その他のリストモードフラグには `--order asc|desc`、`--cursor`、`--page-size`（最大 200）、`--fields`、`--full-ids` があります。`--search` は繰り返し指定可能で、両方のモードに適用されます。いずれかの語が含まれる行がマッチします。

    `fp errors` には `events:read` 権限が必要です。`--json` オプション使用時、リストモードは `{"errors": [...], "next_cursor": ...}` を返し、`--aggregate` は `{total, sessions, agents, last_ts, bins}` を返します。エラーサマリーの背後にある生のペイロードが必要な場合は `fp events --full --session-id <id>` を使用してください。
  </Tab>
</Tabs>

## エラー機能が役立つ場面

- 本番環境で最も頻繁に発生するエラークラスを特定する。
- 特定のツールやモデルがスパイクの原因かどうかを判断する。
- 集計カウントから代表的なセッションに素早く移動する。
- 再発に備えたアラートを作成する。
- 影響を受けた対象を監査に含める。

エラーとは観測されたイベントです。失敗した評価は品質上の判断であり、監査所見は調査された障害パターンです。どの対応ワークフローを使用するかを決定する際は、これらの区別を意識してください。

## クラウドアカウントなしの場合

エラー機能はクラウド向けの機能です。未接続のマシンでは、`failproofai audit` がディスク上の既存セッション履歴をスキャンしてリスクや非効率なパターンを検出し、`http://localhost:8020/audit` を開きます。`--schedule [days]` を追加するとタイマーによる定期スキャンと結果のメール送信が有効になります（デフォルト 7 日、範囲は 1〜90 日）。`--status` でスケジュールが有効かどうかを確認し、`--no-schedule` で停止できます。2 つの例外を除き、すべてはマシン上で実行されます。定期スキャンは毎回（クリーンな場合も含め）、このマシンの ID、ラベル、プラットフォーム、およびカバーした時間範囲を送信します。クリーンなスキャンが省略するのはダイジェストであり、リクエスト自体ではありません。また、`FAILPROOFAI_TELEMETRY_DISABLED=1` を設定しない限り、すべての監査時に匿名 CLI テレメトリが送信されます。
