クエリは、ダッシュボード・監査・調査の下に位置する柔軟なレイヤーです。アドホックSQLでアイデアを検証し、定期的なワークフローの一部になったらクエリを保存しましょう。

## クエリの作成と実行

<Tabs>
  <Tab title="ダッシュボード">
    1. **Analyze → Queries** に移動し、**new query** を選択します。
    2. スキーマブラウザを開き、イベント・セッション・評価データからフィールドを選びます。
    3. SQLを記述し、必要に応じてパラメータを追加してクエリを実行します。
    4. わかりやすい名前と説明を付けて保存し、結果をモニタリングしたい場合は **add to dashboard** を使用します。

    クエリエディタはイベントスキーマ、SQL、パラメータ、結果プレビューを統合しており、保存前に問いを検証できます。

    ![スキーマブラウザとライブ結果グリッドを備えたSQLクエリエディタ。](/images/dashboard/query-lab.png)

    保存されたクエリは共有ライブラリに表示され、チームメンバーが再実行したり、結果をダッシュボードに追加したりできます。

    ![再利用可能な組み込みクエリとカスタムクエリを含む保存済みクエリライブラリ。](/images/dashboard/queries.png)

    SQLを開き直さなくても結果が理解できるよう、わかりやすい名前と説明を付けましょう。
  </Tab>
  <Tab title="CLI">
    ```bash
    fp query schema
    fp query create "retry loops" --sql "SELECT ..."
    fp query run <query-id>
    fp query show <query-id>
    fp query update <query-id> --sql "SELECT ..."
    ```

    IDの確認には `fp query list` を、保存済みクエリの削除には `fp query delete <query-id>` を使用します。
  </Tab>
</Tabs>

## 主な用途

- 同じツールへの繰り返し呼び出しを含むセッションを検索する。
- モデルや環境をまたいで評価スコアを比較する。
- 人間の待機から再開までの時間を計測する。
- ポリシーによる拒否の後に成功した代替手段が続くケースを特定する。
- 監査用のコホートを作成する。

未知のフィールドに対してクエリを書く前に **Queries → Schema** を開いて確認しましょう。時間や環境のフィルタは明示的に指定し、調査中は結果件数に上限を設けることをお勧めします。

<Warning>
  クエリは疑わしいパターンを発見できますが、それだけで障害モードが確定するわけではありません。結果をポリシーに反映する前に、代表的なトレースを開くか監査を実施してください。
</Warning>
