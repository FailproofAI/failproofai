トレースとは、1回のエージェント実行のタイムラインです。最終的なエラーではなく、最初の予期しないイベントから始めましょう。

<Tabs>
  <Tab title="ダッシュボード">
    1. **Observe → Sessions** を開きます。
    2. セッションを選択します。
    3. 最初のエラー、通常とは異なるツール呼び出し、長い待機時間、またはポリシー判定をスキャンします。
    4. イベントを開き、リクエスト、レスポンス、入力、出力を確認します。

    ![実行グラフ、イベントタイムライン、評価パネル、およびツール・モデル・フックの内訳を表示したセッション詳細ビュー。](/images/dashboard/session-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp --json sessions --session-id <session-id>
    fp events --session-id <session-id> --order asc --all --limit 5000
    fp --json events --full --session-id <session-id> --all --limit 2000
    ```

    イベントのサマリーだけでは情報が不十分な場合にのみ `--full` を使用してください。`next_cursor` が null でない場合は、終端に達する前にリミットに到達したことを意味します。
  </Tab>
</Tabs>

## 証拠を辿る

1. エージェント、目標、環境、および結果を確認します。
2. 最初のエラーまたは予期しない判断を見つけます。
3. その直前のイベントを確認します。
4. リクエストとレスポンスのペア間で一致するIDを追跡します。
5. 証拠を監査、課題、またはポリシーに変換します。

| ペア | 一致するフィールド |
| --- | --- |
| モデルリクエストとレスポンス | `request_id` |
| ツール呼び出しと結果 | `tool_call_id` |
| フック開始と完了 | `hook_id` |
| エージェントの一時停止と再開 | `pause_id` |
| 人間の待機と入力 | `input_id` |

判定は `hook_completed` に表示されます。その行には結果とポリシーソースが記載されています。オブザーブモードの判定は allow として表示され、本来の判定内容が `failproofai_observed` に記録されます。

<Warning>
  セッション時間が長いからといって、必ずしもモデルのレイテンシーが原因とは限りません。何を修正すべきか判断する前に、モデル、ツール、フック、および人間待機の時間をそれぞれ分けて確認してください。
</Warning>
