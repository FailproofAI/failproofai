トレースは、フラットなイベントストリームを実行の因果ストーリーに変換します。最後のエラーから遡るのではなく、最初の分岐点から読み進めてください。

## トレースを開く

<Tabs>
  <Tab title="ダッシュボード">
    1. **Observe → Sessions** に移動し、セッションを開きます。
    2. プロファイルサマリーで、結果・タイミング・エラー・評価スコアを確認します。
    3. タイムラインとミニマップをスキャンします。セッションが大きい場合は、イベントタイプや時間でフィルタリングしてください。
    4. イベントを選択して詳細を確認します。評価用 JSON は **export** を使用し、選択した証拠へのディープリンクを共有する場合はページ URL をコピーしてください。

    ![実行グラフ、イベントタイムライン、評価パネル、ツール・モデル・フックの内訳を含むセッション詳細ビュー。](/images/dashboard/session-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp --json sessions --session-id <session-id>
    fp events --session-id <session-id> --order asc --all
    fp --json events --full --session-id <session-id> --all
    ```

    まず軽量なイベントフィードを使用してください。イベントのサマリーに十分な証拠が含まれていない場合にのみ、フルペイロードをリクエストしてください。
  </Tab>
</Tabs>

<Steps>
  <Step title="状況を把握する">
    エージェント、環境、タイミング、結果、所要時間を確認し、エラー・長いスパン・繰り返されるツール・人間の待機・拒否されたポリシー決定をスキャンします。
  </Step>
  <Step title="最初の不審なイベントを展開する">
    リクエスト、レスポンス、ツールの入力・出力、相関 ID を確認します。機密コンテンツは、トランスクリプトキャプチャが有効になっており、かつ権限がある場合にのみ表示されます。
  </Step>
  <Step title="直前のコンテキストを調べる">
    原因は多くの場合、1 つ前のイベントにあります。不正確なモデルレスポンス、欠落したツール結果、または古くなった前提条件が原因であることが多いです。
  </Step>
  <Step title="証拠をアクションに変える">
    セッションを監査スコープに追加したり、課題にリンクしたり、失敗のパターンを使ってポリシーを作成したりします。
  </Step>
</Steps>

<Warning>
  実行時間が長いからといって、必ずしもモデルのレイテンシが原因とは限りません。何を修正すべきかを判断する前に、モデル・ツール・フック・人間の待機時間をそれぞれ分けて分析してください。
</Warning>
