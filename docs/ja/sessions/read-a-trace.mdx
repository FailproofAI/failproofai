トレースは、フラットなイベントストリームを実行の因果関係として可視化したものです。最後のエラーから遡るのではなく、最初の分岐点から読み始めてください。

## トレースを開く

<Tabs>
  <Tab title="ダッシュボード">
    1. **Observe → Sessions** に移動し、セッションを開きます。
    2. プロファイルサマリーを使って、結果・タイミング・エラー・評価スコアを確認します。
    3. タイムラインとミニマップをスキャンします。セッションが大きい場合は、イベントタイプや時間でフィルタリングしてください。
    4. イベントを選択して詳細を確認します。エバリュエーター用の JSON は **export** を使用し、選択した証拠へのディープリンクを共有するにはページ URL をコピーします。

    ![実行グラフ、イベントタイムライン、評価パネル、ツール・モデル・フックの内訳を表示したセッション詳細ビュー。](/images/dashboard/session-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp --json sessions --session-id <session-id>
    fp events --session-id <session-id> --order asc --all
    fp --json events --full --session-id <session-id> --all
    ```

    まず軽量なイベントフィードを使用してください。イベントのサマリーに十分な証拠が含まれていない場合にのみ、フルペイロードをリクエストしてください。
  </Tab>
</Tabs>

<Steps>
  <Step title="全体を把握する">
    エージェント・環境・タイミング・結果・所要時間を確認したうえで、エラー・長いスパン・繰り返されるツール・人間の待機・拒否されたポリシー決定をスキャンします。
  </Step>
  <Step title="最初の不審なイベントを展開する">
    リクエスト・レスポンス・ツールの入力と出力・相関 ID を確認します。機密コンテンツは、トランスクリプトキャプチャが有効で、かつ自分に適切な権限がある場合にのみ表示されます。
  </Step>
  <Step title="直前のコンテキストを確認する">
    原因は多くの場合、1 つ前のイベントにあります。モデルの誤った応答、ツール結果の欠落、または古い前提条件がその典型です。
  </Step>
  <Step title="証拠をアクションに変える">
    セッションを監査スコープに追加する、Issue にリンクする、またはその障害モードを参考にポリシーを作成します。
  </Step>
</Steps>

<Warning>
  所要時間が長いからといって、必ずしもモデルのレイテンシーが原因とは限りません。何を修正すべきか判断する前に、モデル・ツール・フック・人間の待機時間をそれぞれ分けて確認してください。
</Warning>
