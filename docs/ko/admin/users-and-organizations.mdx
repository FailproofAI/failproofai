조직은 세션, 평가, 감사, 이슈, 알림, 쿼리, 대시보드, 사용자 및 키를 격리합니다. 관리 리소스를 변경하기 전에 활성 조직을 확인하세요.

## 조직 선택

<Tabs>
  <Tab title="대시보드">
    Cloud 사이드바 상단의 조직 전환기를 사용하세요. 그 아래의 모든 항목 — **admin**의 모든 페이지 포함 — 은 해당 조직을 기준으로 읽기 및 쓰기가 이루어집니다.
  </Tab>
  <Tab title="CLI">
    ```bash
    fp orgs list
    fp orgs switch reliability-team
    fp orgs current
    fp orgs perms
    ```

    슬러그 없이 `fp orgs switch`를 실행하면 현재 조직에서 시작하는 방향키 선택기가 열립니다. 비대화형 실행 시에는 번호 프롬프트로 대체되며, `--json` 플래그 사용 시에는 슬러그가 필수입니다. 선택 결과는 `~/.failproofai/fpcli/cli-auth.json`에 저장되므로 이후 명령이 활성 테넌트로 전송됩니다. 단일 명령에 한해 `--org <slug>` 또는 `FP_ORG`로 재정의할 수 있습니다.
  </Tab>
</Tabs>

<Note>
  모든 `fp orgs` 명령은 로그인된 사람이 필요하며 API 키로는 거부됩니다. 조직 멤버십은 개인에게 속하며, 키는 이미 하나의 조직을 위해 동작하기 때문입니다. 아래의 `fp users` 명령은 두 방식 모두 사용 가능합니다.
</Note>

## 멤버 관리

<Tabs>
  <Tab title="대시보드">
    1. **admin → users**로 이동하여 이메일로 멤버를 검색하거나, `protected`, `admin`, `standard`, `read-only` 필터 칩으로 목록을 좁힙니다.
    2. **new user**를 선택하고 이메일을 입력한 다음 권한 세트를 선택하고, 필요 시 멤버별 재정의를 조정합니다.
    3. 나중에 멤버를 열어 권한을 변경하거나, 로그인을 비활성화하거나, 계정을 다시 활성화합니다.

    ![이메일 검색 상자, 필터 칩, 그리고 리소스별로 그룹화된 권한이 표시된 멤버 카드가 있는 사용자 페이지.](/images/dashboard/users.png)

    이 화면의 권한 칩은 `incidents:*`에서 `issues:*`로 이름이 변경되기 이전 버전입니다. [공통 권한](/ko/admin/keys-and-permissions#common-permissions) 목록이 최신 기준입니다.
  </Tab>
  <Tab title="CLI">
    ```bash
    fp users list
    fp users list --active-only
    fp users create engineer@example.com --permission-set standard
    fp users show engineer@example.com
    fp users update engineer@example.com --add audits:write
    fp users disable engineer@example.com
    fp users enable engineer@example.com
    ```

    멤버는 이메일로 지정되며 대소문자를 구분하지 않고 조회됩니다. 따라서 `fp users show Alice.Chen@Example.com`과 `fp users create alice.chen@example.com`은 동일한 사람을 가리킵니다.
  </Tab>
</Tabs>

### 권한 부여 및 각 동사에 필요한 권한

멤버 권한 부여는 키와 동일한 연산을 사용합니다. 유효 권한은 `(세트 ∪ 추가) − 제거`이며, `--add` / `--remove`는 점으로 구분된 작업이 확장되는 압축 형태의 `slug:action.action` 토큰을 사용합니다. [키와 권한](/ko/admin/keys-and-permissions)을 참고하세요.

| 동사 | 권한 | 참고 |
| --- | --- | --- |
| `fp users list` / `show` | `users:read` | `--active-only`는 비활성화된 멤버를 숨깁니다. |
| `fp users create` | `users:create` | `--permission-set`은 역할의 초기값을 설정하며, `--add` / `--remove`로 재정의를 추가합니다. |
| `fp users update` | `users:update` | `--permission-set`은 멤버의 개별 재정의를 **대체**합니다. `--add` / `--remove`만 사용하면 현재 권한에 대해 점진적으로 적용됩니다. |
| `fp users disable` / `enable` | `users:delete` | 비활성화와 활성화 모두 해당 — 의도적으로 부여하세요. |

비활성화는 다음 두 가지 경우를 유효성 검사 메시지가 아닌 Forbidden 오류로 거부합니다. **보호된** 멤버는 비활성화할 수 없으며, 자신의 계정도 비활성화할 수 없습니다. 이미 비활성화된 멤버를 비활성화하거나 이미 활성화된 멤버를 활성화하는 것은 조용한 no-op입니다. API는 비활성화에 delete 작업을 사용하지만, 계정이나 멤버십 레코드를 삭제하지는 않습니다.

두 가지 조직 설정이 멤버십을 제어합니다. `default_user_permissions`는 새 초대의 권한 세트를 사전 선택하며, `allowed_sign_ins`는 로그인 코드를 받을 수 있는 주소를 제어합니다. [설정 페이지](/ko/admin/settings-and-security)에서 관리하세요.

<Warning>
  사용자를 비활성화하면 현재 선택된 조직뿐만 아니라 모든 조직에서 해당 계정의 로그인이 차단됩니다. 다시 활성화하면 전체 로그인과 이 조직에서의 멤버 권한이 복원됩니다.
</Warning>

<Tip>
  서비스 계정에는 워크로드와 담당자를 연결하는 설명적인 이름을 부여하세요. 조직 간에 키를 공유하거나 개인과 시스템이 동일한 키를 공유하지 마세요.
</Tip>
