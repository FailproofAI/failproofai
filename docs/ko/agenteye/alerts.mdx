고객으로부터 듣기 전에, 팀이 이미 사용하는 채널에서 기준을 초과하는 순간 바로 알림을 받으세요. 규칙을 한 번 설정하면 Failproof AI Observability가 일정에 따라 확인하고, 이메일, Slack, 웹훅, 또는 대시보드를 통해 알림을 보냅니다.

![알림 페이지: 트리거, 평가 윈도우, 채널, 정보·경고·위험 심각도 배지를 각각 표시하는 알림 규칙 카드 그리드](/agenteye/images/alerts.png)
*모든 알림 규칙을 한눈에: 무엇을 감시하는지, 얼마나 자주, 어디로 알리는지, 얼마나 긴급한지.*

## 사용자보다 먼저 문제를 파악하세요

대시보드를 새로고침하며 회귀를 발견하길 기다리는 일은 이제 그만하세요. 아무도 보고 있지 않을 때도 알고 싶은 신호가 있다면 알림을 설정하고, 이미 사용 중인 곳에서 받아보세요:

- **이메일**, 알아야 할 담당자에게 바로 전달.
- **Slack**, 인시던트로 바로 이동하는 버튼이 포함된 풍부한 메시지.
- **웹훅**, PagerDuty, Opsgenie, 또는 직접 만든 엔드포인트로 전송되는 JSON POST. 선택적 서명을 추가해 수신 측에서 신뢰할 수 있습니다.
- **대시보드 내**, 기본적으로 조용하게 동작하므로 규칙을 조정하는 중에 누구에게도 알리고 싶지 않을 때 적합합니다.

단일 규칙에 원하는 조합으로 채널을 연결하고, 심각도(정보, 경고, 위험)도 함께 전달되어 긴급한 알림이 눈에 잘 띄게 됩니다.

## JSON이 아닌 폼으로 규칙을 만드세요

"고장 났다"는 것이 무엇을 의미하는지 폼에서 설명하면 Failproof AI Observability가 내부 규칙을 작성합니다. JSON 스펙은 해당 폼이 내부적으로 생성하는 결과물일 뿐이므로, 규칙을 이해하기 위해 읽을 수는 있지만 직접 입력할 일은 거의 없습니다.

![새 알림 폼: 이름과 설명, 활성화 토글, 메트릭 임계값·커스텀 SQL·평가 점수·복합 평가·이벤트별 조건을 제공하는 트리거 선택기](/agenteye/images/alert-new.png)
*트리거를 선택하면 폼이 알맞은 필드로 전환됩니다. 저장하면 규칙이 작성됩니다.*

기본 흐름은 간단합니다. 이름을 지정하고, **트리거**(감시할 대상)를 선택한 후, **임계값과 윈도우**(얼마나 심각한지, 얼마나 오래)를 설정하고, **채널**을 하나 이상 연결한 뒤 **저장**하고 **테스트**를 눌러 합성 알림을 발송해 모든 대상이 올바르게 연결됐는지 확인합니다. 내부적으로는 다음과 같은 소규모 스펙이 생성됩니다:

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

신호의 종류는 하나로 제한되지 않습니다. 장애를 어떻게 인식하느냐에 맞는 트리거를 선택하세요:

| 트리거 | 발동 조건 |
|---|---|
| **메트릭 임계값** | 사전 설정된 메트릭(오류율, p95 또는 p99 지연 시간, 이벤트 또는 오류 횟수, 토큰 사용량)이 윈도우 내에서 기준을 초과할 때 |
| **커스텀 SQL** | 직접 작성한 읽기 전용 쿼리가 행을 반환하거나, 계산된 값이 임계값을 초과할 때 |
| **평가 점수** | 평가자 점수의 평균(예: 환각 점수)이 임계값을 초과할 때 |
| **복합 평가** | 여러 점수 조건을 any, all, 또는 최소 N개 로직으로 결합해, 여러 점수에서만 드러나는 회귀를 감지할 때 |
| **이벤트별** | 특정 에이전트, 특정 오류 유형, 또는 메시지 내 특정 문자열이 포함된 단일 매칭 이벤트가 발생할 때 |

이미 [오류 페이지](/ko/agenteye/error-tracking)에서 장애를 확인하고 있나요? 각 행에는 **+ 알림** 버튼이 있어, 해당 장애가 다시 발생할 때를 감지하도록 폼이 미리 채워진 상태로 열립니다. 방금 분류한 인시던트가 다음번에 자동으로 알림을 보내는 규칙이 됩니다.

**위치:** 알림은 `/<org-slug>/alerts`에 있습니다. 규칙 생성, 수정, 삭제, 테스트에는 **`alerts:write`** 권한이 필요하며, 조회에는 `alerts:read`로 충분합니다. 수신자 선택기는 조직 구성원을 이름으로 나열하므로, 폼을 벗어나지 않고 특정 담당자에게 알림을 보낼 수 있습니다.

## 실제 문제일 때만 알림 받기

측정값 하나가 잘못됐다고 잠을 깨워선 안 됩니다. **M of N** 노이즈 필터는 알림이 실제로 발송되기 전에 최근 몇 번의 검사 중 몇 번이 실패해야 하는지를 제어합니다. **5번 중 3번**으로 설정하면 최근 5번의 검사 중 3번을 초과했을 때만 규칙이 발동되므로, 불안정한 신호가 헛된 경보를 울리지 않습니다. 기본값인 **1 of 1**로 두면 첫 번째 초과 시 즉시 발동됩니다. 규칙 실행 주기도 신호가 실제로 변화하는 속도에 맞춰 1분, 5분, 15분, 1시간 중에서 선택할 수 있습니다.

## 알림이 발동되면 어떻게 되나요

임계값 초과 시 **인시던트**가 생성되고 채널로 한 번 알림이 발송됩니다. 이후 팀이 확인하고, 담당자를 지정하고, 논의하고, 해결하는 모든 과정이 깔끔하고 귀속이 명확한 기록으로 남습니다. 이 트리아지 워크플로우에는 전용 공간이 있습니다: [인시던트](/ko/agenteye/incidents)를 참조하세요.

## 관련 항목

- [인시던트](/ko/agenteye/incidents): 발동된 알림을 열림에서 확인, 해결까지 추적합니다.
- [오류 추적](/ko/agenteye/error-tracking): 에이전트 장애를 그룹화하고 클릭 한 번으로 알림으로 승격합니다.
- [대시보드](/ko/agenteye/dashboards): 알림 임계값의 기준이 되는 공유 보드를 확인합니다.
- [CLI 및 에이전트](/ko/agenteye/cli-and-agents): 터미널에서 알림을 생성하고 인시던트를 확인하거나, CI에 스크립트로 통합합니다.
