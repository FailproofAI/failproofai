고객으로부터 문제를 듣기 전에, 팀이 이미 사용하는 채널에서 즉시 알림을 받으세요. 규칙을 한 번 설정하면 Failproof AI Observability가 스케줄에 따라 확인하고, 이메일, Slack, 웹훅, 또는 대시보드에서 직접 알림을 보냅니다.

![알림 페이지: 각 알림 규칙 카드에 트리거, 평가 기간, 채널, 정보·경고·심각 심각도 배지가 표시된 그리드](/agenteye/images/alerts.png)
*모든 알림 규칙 한눈에 보기: 무엇을 감시하는지, 얼마나 자주, 어디로 알리는지, 얼마나 긴급한지.*

## 사용자보다 먼저 문제를 파악하세요

대시보드를 계속 새로고침하며 회귀를 잡으려 하지 마세요. 아무도 보고 있지 않을 때도 알고 싶은 신호가 있다면 알림을 설정하고, 이미 사용 중인 곳에서 받아보세요:

- **이메일**: 알아야 할 담당자에게 전송.
- **Slack**: 인시던트로 바로 이동하는 버튼이 포함된 리치 메시지.
- **웹훅**: PagerDuty, Opsgenie 또는 자체 엔드포인트로의 JSON POST. 선택적 서명으로 수신자가 신뢰할 수 있도록 지원.
- **대시보드 내**: 규칙을 조정 중이고 아직 누구에게도 알리고 싶지 않을 때를 위한, 조용한 알림.

단일 규칙에 원하는 조합을 붙이면, 심각도(정보, 경고, 심각)도 함께 전달되어 긴급한 알림은 긴급하게 보입니다.

## JSON이 아닌 폼으로 규칙 작성

"고장"이 무엇인지 폼으로 설명하면 Failproof AI Observability가 내부 규칙을 자동으로 작성합니다. JSON 스펙은 그 폼이 내부적으로 생성하는 결과물이므로, 규칙을 이해하기 위해 읽을 수는 있지만 직접 입력할 일은 거의 없습니다.

![새 알림 폼: 이름과 설명, 활성화 토글, 메트릭 임계값·커스텀 SQL·평가 점수·복합 평가·이벤트별 조건을 제공하는 트리거 선택기](/agenteye/images/alert-new.png)
*트리거를 선택하면 폼에 적절한 필드가 표시되고, 저장하면 규칙이 작성됩니다.*

일반적인 흐름은 빠릅니다: 이름을 입력하고, **트리거**(무엇을 감시할지)를 선택하고, **임계값과 기간**(얼마나 심각한지, 얼마나 오랫동안)을 설정하고, 하나 이상의 **채널**을 연결한 다음 **저장**하고 **테스트**를 눌러 가상 알림을 발송하고 모든 목적지가 제대로 연결되었는지 확인하세요. 내부적으로는 다음과 같은 작은 스펙이 생성됩니다:

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

하나의 신호 유형에 국한되지 않습니다. 장애를 생각하는 방식에 맞는 트리거를 선택하세요:

| 트리거 | 발동 조건 |
|---|---|
| **메트릭 임계값** | 사전 정의된 메트릭(오류율, p95 또는 p99 지연, 이벤트 또는 오류 수, 토큰 사용량)이 기간 내에 설정값을 초과할 때 |
| **커스텀 SQL** | 직접 작성한 읽기 전용 쿼리가 행을 반환하거나, 계산된 값이 임계값을 초과할 때 |
| **평가 점수** | 평가자 점수의 평균(예: 환각)이 임계값을 초과할 때 |
| **복합 평가** | 여러 점수 조건을 any, all, 또는 N개 이상 로직으로 결합하여, 점수 전반에 걸쳐 나타나는 회귀를 감지할 때 |
| **이벤트별** | 특정 에이전트, 특정 오류 유형, 또는 메시지 부분 문자열과 일치하는 단일 이벤트가 발생했을 때 |

[오류 페이지](/ko/agenteye/error-tracking)에서 이미 장애를 보고 있나요? 모든 행에는 **+ alert** 버튼이 있어 동일한 폼이 해당 장애를 정확히 감지하도록 미리 채워진 상태로 열립니다. 방금 처리한 인시던트가 다음에 알림을 보내는 규칙이 됩니다.

**위치:** 알림은 `/<org-slug>/alerts`에 있습니다. 규칙 생성, 편집, 삭제, 테스트에는 **`alerts:write`**가 필요하고, 조회만 할 때는 `alerts:read`로 충분합니다. 수신자 선택기는 조직 구성원을 이름으로 나열하므로, 폼을 벗어나지 않고 특정 사람에게 알림을 보낼 수 있습니다.

## 실제 문제일 때만 알림 받기

잘못된 측정 하나가 여러분을 깨워서는 안 됩니다. **M of N** 노이즈 필터는 알림이 실제로 발송되기 전에 최근 몇 번의 확인 중 몇 번이 실패해야 하는지 제어합니다. **3 of 5**로 설정하면 마지막 다섯 번의 확인 중 세 번을 초과했을 때만 규칙이 발동되므로, 불안정한 신호가 거짓 경보를 내지 않습니다. 기본값인 **1 of 1**로 두면 첫 번째 초과 시 즉시 발동됩니다. 신호가 실제로 얼마나 빠르게 변하는지에 맞춰 1m, 5m, 15m, 1h 프리셋 중에서 규칙 실행 주기도 선택할 수 있습니다.

## 알림이 발동되면 어떤 일이 일어나나요

임계값 초과 시 **인시던트**가 생성되고 채널에 한 번 알림이 전송됩니다. 이후 팀이 이를 확인하고, 담당자를 지정하고, 논의하고, 해결합니다. 모든 과정이 깔끔하게 귀속된 기록으로 남습니다. 해당 트리아지 워크플로우는 별도 공간에서 관리됩니다: [인시던트](/ko/agenteye/incidents)를 참조하세요.

## 관련 항목

- [인시던트](/ko/agenteye/incidents): 발동된 알림을 열림에서 확인, 해결까지 추적합니다.
- [오류 추적](/ko/agenteye/error-tracking): 에이전트 장애를 그룹화하고 클릭 한 번으로 알림으로 전환합니다.
- [대시보드](/ko/agenteye/dashboards): 알림 임계값의 기준이 되는 공유 보드를 확인합니다.
- [CLI 및 에이전트](/ko/agenteye/cli-and-agents): 터미널에서 알림을 생성하고 인시던트를 확인하거나, CI에 스크립트로 통합합니다.
