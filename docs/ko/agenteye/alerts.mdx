고객에게서 듣기 전에, 팀이 이미 사용하는 채널에서 기준을 초과하는 순간 바로 알림을 받으세요. 규칙을 한 번 설정하면 Failproof AI Observability가 스케줄에 따라 확인하고, 이메일·Slack·웹훅 또는 대시보드를 통해 알려줍니다.

![알림 페이지: 각 트리거, 평가 윈도우, 채널, 그리고 info·warning·critical 심각도 배지가 표시된 알림 규칙 카드 그리드](/agenteye/images/alerts.png)
*모든 알림 규칙 한눈에: 무엇을 감시하는지, 얼마나 자주, 어디로 알리는지, 그리고 얼마나 긴급한지.*

## 사용자보다 먼저 문제를 파악하세요

대시보드를 계속 새로고침하며 회귀를 잡으려 하지 마세요. 아무도 보고 있지 않을 때도 알아야 할 신호가 있다면 알림을 설정하고, 이미 있는 곳에서 받으세요:

- **이메일**: 알아야 할 담당자에게 전달.
- **Slack**: 인시던트로 바로 이동하는 버튼이 포함된 풍부한 메시지.
- **웹훅**: PagerDuty, Opsgenie 또는 자체 엔드포인트로 전송하는 JSON POST. 수신 측이 신뢰할 수 있도록 선택적 서명 지원.
- **대시보드 내**: 규칙을 조정하는 중이라 아직 아무에게도 알리고 싶지 않을 때를 위한 조용한 옵션.

하나의 규칙에 여러 조합을 연결할 수 있으며, 심각도(info·warning·critical)가 함께 전달되어 긴급한 알림은 긴급하게 보입니다.

## JSON이 아닌 폼으로 규칙 만들기

"문제"의 의미를 폼에서 설명하면 Failproof AI Observability가 내부 규칙을 자동으로 작성합니다. JSON 스펙은 폼이 내부적으로 생성하는 결과물이므로, 규칙을 이해하기 위해 읽을 수는 있지만 직접 작성할 일은 거의 없습니다.

![새 알림 폼: 이름과 설명, 활성화 토글, 메트릭 임계값·커스텀 SQL·평가 점수·복합 평가·이벤트별 조건을 제공하는 트리거 선택기](/agenteye/images/alert-new.png)
*트리거를 선택하면 폼이 적절한 필드로 전환되고, 저장 시 규칙이 작성됩니다.*

기본 경로는 빠릅니다: 이름을 정하고, **트리거**(무엇을 감시할지)를 선택하고, **임계값과 윈도우**(얼마나 심각한지, 얼마 동안)를 설정하고, 하나 이상의 **채널**을 연결한 뒤 **저장**하고 **테스트**를 눌러 합성 알림을 발송해 모든 대상이 제대로 연결되었는지 확인하세요. 내부적으로는 다음과 같은 간단한 스펙이 생성됩니다:

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

하나의 신호 유형에 국한되지 않습니다. 장애를 어떻게 인식하는지에 맞는 트리거를 선택하세요:

| 트리거 | 발동 조건 |
|---|---|
| **메트릭 임계값** | 사전 설정된 메트릭(오류율, p95/p99 지연 시간, 이벤트/오류 수, 토큰 사용량)이 윈도우 기간 동안 기준을 초과할 때 |
| **커스텀 SQL** | 읽기 전용 쿼리가 행을 반환하거나, 계산된 값이 임계값을 초과할 때 |
| **평가 점수** | 평가자 점수(예: 환각)의 평균이 임계값을 초과할 때 |
| **복합 평가** | 여러 점수 조건이 any·all·N개 이상 논리로 결합되어, 점수 전반에 걸쳐 나타나는 회귀를 감지할 때 |
| **이벤트별** | 특정 에이전트, 특정 오류 유형, 또는 메시지 문자열이 포함된 단일 매칭 이벤트가 발생할 때 |

[오류 페이지](/ko/agenteye/error-tracking)에서 이미 장애를 보고 있나요? 각 행에는 **+ 알림** 버튼이 있어 해당 장애를 다시 감지하도록 미리 채워진 폼을 바로 엽니다. 방금 분류한 인시던트가 다음에는 바로 알림으로 이어집니다.

**위치:** 알림은 `/<org-slug>/alerts`에 있습니다. 규칙 생성·편집·삭제·테스트에는 **`alerts:write`**가 필요하며, 조회만 할 때는 `alerts:read`로 충분합니다. 수신자 선택기는 조직 구성원을 이름으로 나열하므로, 폼을 벗어나지 않고 특정 인물에게 알림을 보낼 수 있습니다.

## 실제 문제일 때만 알림 받기

측정값 하나가 잘못되었다고 해서 잠에서 깨어날 필요는 없습니다. **M of N** 노이즈 필터는 알림이 실제로 발동하기 전에 최근 몇 번의 확인 중 몇 번이 실패해야 하는지를 제어합니다. **3 of 5**로 설정하면 최근 다섯 번의 확인 중 세 번을 초과한 경우에만 규칙이 발동되므로, 불안정한 신호가 헛된 경보를 내지 않습니다. 기본값 **1 of 1**로 두면 첫 번째 위반 시 즉시 발동합니다. 또한 신호가 실제로 변화하는 속도에 맞춰 1분·5분·15분·1시간 프리셋에서 규칙 실행 빈도를 선택할 수 있습니다.

## 알림 발동 시 일어나는 일

기준 초과 시 **인시던트**가 열리고 채널에 한 번 알림이 전송됩니다. 이후 팀이 인시던트를 인지하고, 담당자를 지정하고, 논의하고 해결합니다. 모든 과정이 깔끔하고 귀속된 기록으로 남습니다. 해당 분류 워크플로는 별도의 공간이 있습니다: [인시던트](/ko/agenteye/incidents)를 참조하세요.

## 관련 항목

- [인시던트](/ko/agenteye/incidents): 발동된 알림을 열린 상태에서 인지, 해결까지 추적.
- [오류 추적](/ko/agenteye/error-tracking): 에이전트 장애를 그룹화하고 클릭 한 번으로 알림으로 전환.
- [대시보드](/ko/agenteye/dashboards): 알림 임계값의 기준이 되는 공유 보드 모니터링.
- [CLI 및 에이전트](/ko/agenteye/cli-and-agents): 터미널에서 알림을 생성하고 인시던트를 확인하거나 CI에 스크립트로 통합.
