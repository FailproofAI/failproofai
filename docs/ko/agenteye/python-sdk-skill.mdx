코딩 에이전트에게 *"이 에이전트에 Failproof AI Observability를 추가해줘"* 라고 말하면, 에이전트가 루프를 읽고 계측이 필요한 위치를 파악한 다음, 코드를 작성하고 작업 완료를 선언하기 전에 이벤트를 검증합니다.

**Python SDK skill** (`agenteye-python-sdk`)은 *Agent Skill*입니다. 즉, 작업이 매칭될 때 Claude Code나 Codex 같은 코딩 에이전트가 온디맨드로 불러오는 명령어 폴더입니다. 이 스킬은 에이전트에게 [Python SDK](/ko/agenteye/python-sdk) 사용법을 가르칩니다 — 라이브러리가 아니며, SDK의 동작 방식 자체를 변경하지 않습니다.

## 계측은 작성하기 쉽지만 조용히 잘못되기도 쉽습니다

SDK는 작습니다: 키워드 전용 인수로 구성된 열세 개의 이벤트 메서드. 코딩 에이전트는 [Python SDK](/ko/agenteye/python-sdk) 레퍼런스를 읽고 그럴듯한 계측 코드를 1분 안에 생성할 수 있습니다.

문제는 이 SDK가 잘못 사용해도 예외를 발생시키지 않는다는 점입니다. 잘못된 계측은 누군가 대시보드를 열고 비어 있는 것을 발견하기 전까지는 올바른 계측과 똑같이 보입니다. 실제로 시간을 낭비하게 만드는 실수는 모두 '무소음 실패'입니다:

| 실수 | 보이는 것 |
|---|---|
| `agent_start` 누락 | 모든 이벤트는 기록됨. 세션은 0개. |
| 환경 미설정 | 모든 것이 작동하지만 `dev`로 분류됨. |
| `outcome="failure"` | 실행이 성공으로 표시됨 — `failed`, `error`, `timeout`, `rejected`만 집계됨. |
| 필드명 오타 | 허용되어 새 필드로 저장됨. |
| 스레드 풀에서 이벤트 발행 | 조용히 누락됨. |

이 중 어느 것도 예외를 발생시키지 않습니다. 테스트에도 나타나지 않습니다. 모두 스킬에 포함되어 있으며, 이를 잡아내는 검사와 함께 계약으로 명시되어 있습니다.

## 스킬이 수행하는 작업 순서

스킬은 신중한 엔지니어가 수행하는 것과 동일한 세 단계를 실행합니다:

1. **계획.** 에이전트 루프를 읽고, 당신만이 답할 수 있는 두 가지 질문을 합니다: 하나의 실행이 무엇인지(`session_id`), 그리고 구분 가능한 액터가 누구인지(`agent_id`). 코드를 작성하기 전에 이를 합의합니다. 나중에 변경하면 히스토리가 분리되고 트렌드가 깨지기 때문입니다.
2. **작성.** 모든 호출 지점에 전달하는 대신 실행당 한 번 ID를 바인딩하고, 동시성에 안전한 형태를 선택합니다 — 중요한 세부 사항입니다. 손쉬운 지름길은 두 개의 겹치는 실행을 하나의 세션으로 조용히 섞어버리기 때문입니다.
3. **검증.** 에이전트를 실행하고 생성된 이벤트 파일을 읽어, `agent_start`가 있는지, 환경이 올바른지, 하나의 실행이 하나의 세션을 생성했는지 확인합니다.

세 번째 단계가 바로 사람들이 건너뛰는 단계입니다. SDK는 이벤트를 로컬 파일에 기록하므로, 완전한 통합은 서버, API 키, 네트워크 없이 노트북에서 증명할 수 있습니다 — 바로 그래서 스킬이 이 단계를 고집합니다.

## 다른 스킬과의 관계

세 가지 스킬, 명확한 분리:

| 스킬 | 사용 시점 | 변경 대상 |
|---|---|---|
| **Python SDK skill** (이 페이지) | 에이전트가 텔레메트리를 *발행*하도록 하려 할 때 — "observability 추가", "왜 내 에이전트가 보이지 않지?" | 에이전트 저장소에 코드 작성. 읽기 없음. |
| **[Evaluator skill](/ko/agenteye/evaluator-skill)** | 실행을 *채점*하려 할 때 — "도대체 무엇을 측정해야 하지?" | 저장소에 코드 작성; 텔레메트리 읽기 |
| **[CLI skill](/ko/agenteye/cli-skill)** | 발생한 일을 *읽거나* 배포를 운영하려 할 때 | 사용자를 대신해 CLI 실행, 변경 포함 |

이 순서로 연결됩니다: 이 스킬이 이벤트를 흘려보내고, evaluator가 채점하고, CLI가 읽습니다. 에이전트가 세션을 발행하기 전까지는 평가할 것도, 읽을 것도 없습니다. 처음부터 시작한다면 여기서 시작하세요.

## 사전 요건

1. **Python 3.10+** 및 계측하려는 에이전트 코드베이스.
2. **SDK.** 공개 인덱스가 아닌 비공개 wheel로 고객에게 배포됩니다 — 온보딩에서 취득 및 설치 방법을 다룹니다. 스킬은 설치 경로를 알고 있으며, 찾지 못하면 추측하지 않고 직접 물어봅니다.
3. **그 외에는 없습니다.** 대시보드 로그인, API 키, 네트워크 불필요. 스킬은 SDK가 기록하는 이벤트 파일로 검증하므로 오프라인에서도 완료하고 결과를 증명할 수 있습니다.

## 구하는 방법

스킬은 공개 [`FailproofAI/skills`](https://github.com/FailproofAI/skills) 컬렉션에 있습니다:

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

현재 프로젝트 대신 모든 프로젝트에 설치하려면 `-g`를 추가하고, 환경이 심볼릭 링크를 따르지 않는다면 `--copy`를 사용하세요. Codex의 경우 `-a codex`를 전달하세요.

## 직접 설치하기

Agent Skills은 `SKILL.md`와 참조 파일이 포함된 폴더입니다. 설치 프로그램을 사용하지 않으려면:

- **Claude Code**: `agenteye-python-sdk/` 폴더를 `~/.claude/skills/`(모든 프로젝트) 또는 `<your-repo>/.claude/skills/`(해당 저장소만)에 복사하세요. Claude Code가 자동으로 탐색합니다 — `/skills` 목록에서 확인하거나, 매칭되는 질문을 해보세요.
- **Codex**: Codex는 동일한 `SKILL.md`를 읽습니다. 번들된 `agents/openai.yaml`이 `allow_implicit_invocation: true`로 설정되어 있어 작업이 매칭되면 자동으로 선택되며, 그렇지 않으면 `$agenteye-python-sdk`로 호출하세요.

계측하려는 코드가 있는 **저장소에서** 에이전트를 실행하세요 — 스킬은 무언가를 제안하기 전에 에이전트 루프를 먼저 읽습니다.

## 세션 예시

```text
you   ▸ 이 에이전트에 Failproof AI Observability를 추가해줘.

agent ▸ 루프를 읽었습니다 — tools.py에 툴 디스패처 하나, llm.py에 Anthropic
        래퍼 하나. 작성 전에 두 가지를 확인해야 합니다.

        하나의 실행은 무엇인가요? 요청을 동시에 처리하시니,
        ctx.request_id에 이미 있는 요청 ID를 사용하면 어떨까요 —
        그러면 여기서의 세션과 로그의 요청이 동일한 문자열이 됩니다.

        그리고 액터는 누구인가요? planner 경로와 researcher 경로가
        보입니다. 별도로 레이블을 붙일까요, 아니면 하나의 에이전트로
        보시나요?

you   ▸ 요청 ID 맞아요. 하나의 에이전트로, "assistant"라고 부르세요.

agent ▸ 완료했습니다. 디스패처와 LLM 클라이언트를 래핑했습니다;
        agent_start와 agent_end가 오류 경로를 포함한 handle_request를
        감쌉니다. ID에는 컨텍스트 로컬을 사용했습니다 — 디스패처가
        스레드 풀에서 툴을 실행하는데, 더 단순한 방식으로 하면 동시
        실행을 하나의 세션으로 섞어버리고도 알림이 없었을 겁니다.

        실제 실행으로 검증: 4개 파일에 걸쳐 11개 이벤트 —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, 요청당
        세션 하나, duration 쌍 맞음.

        하지 않은 것 하나: batch.py의 워커 풀이 executor에 직접
        제출하므로 거기서 발생하는 이벤트는 누락됩니다.
        그것도 수정할까요?
```

주목할 패턴: 제안하기 전에 코드를 읽었고, 당신만이 답할 수 있는 질문만 했으며, 이미 있던 ID를 재사용했고, 스레드 풀을 *확인했기 때문에* 동시성에 안전한 형태를 선택했으며, 성공을 선언하는 대신 **실제 이벤트를 읽어 검증**했습니다 — 그리고 조용히 실패할 것을 알았던 한 곳을 명시했습니다.

## 물어볼 수 있는 것

- *"왜 내 에이전트가 대시보드에 보이지 않나요?"* → 단계별로 점검: 이벤트가 기록되고 있는지, `agent_start`가 있는지, 환경이 올바른지, 컬렉터가 같은 위치를 읽고 있는지.
- *"모든 것이 dev 아래로 들어오고 있어요."* → 환경이 설정되지 않았거나, 이후 호출로 초기화된 경우.
- *"토큰 추적을 추가해줘."* → LLM 래퍼를 찾아 모델, 중단 사유, 사용량을 기록.
- *"서브 에이전트도 계측해줘."* → 하나의 세션, 별도의 에이전트 레이블, 부모 아래 중첩.
- *"계측에 대한 테스트를 작성해줘."* → SDK를 임시 디렉토리로 지정하고 기록된 이벤트를 어서션.

## 주의할 점

**검증 단계를 실행하세요.** 이 스킬을 가치 있게 만드는 단계는 마지막 것입니다 — 에이전트를 실행하고 이벤트를 다시 읽는 것. 계측을 작성하고 멈추는 에이전트는 쉬운 절반만 한 것이며, 조용히 실패하는 절반이 나머지입니다.

**코드 전에 이름을 합의하세요.** `session_id`와 `agent_id`는 모든 뷰가 그룹화하는 축입니다. 나중에 이름을 변경하면 히스토리가 분리됩니다: 이전 실행은 이전 레이블을 유지하고 트렌드가 깨집니다. 스킬이 물어볼 것입니다; 답은 잠시 생각해볼 가치가 있습니다.

**에이전트가 공개 인덱스에서 SDK 설치를 제안한다면, 스킬이 로드되지 않은 것입니다.** SDK는 비공개로 배포됩니다. 그런 제안은 코딩 에이전트가 스킬을 따르지 않고 추측하고 있다는 신뢰할 수 있는 신호입니다 — 거기서 멈추고 스킬이 설치되어 있는지 확인하세요.

그 외에는 영향 범위가 작습니다: 작업 디렉토리에 코드를 작성하고, 지정한 위치에 이벤트 파일을 작성합니다. 배포에서 아무것도 읽지 않으며 아무것도 변경하지 않습니다.
