코딩 에이전트에게 *"이 에이전트에 Failproof AI 관측 가능성을 추가해줘"*라고 말하면, 에이전트가 루프를 직접 읽고, 어디에 계측이 필요한지 파악하고, 코드를 작성한 뒤, 작업 완료를 선언하기 전에 이벤트를 검증합니다.

**Python SDK 스킬** (`agenteye-python-sdk`)은 *에이전트 스킬*입니다. 즉, Claude Code나 Codex 같은 코딩 에이전트가 작업이 매칭될 때 온디맨드로 로드하는 지침 폴더입니다. 이 스킬은 에이전트가 [Python SDK](/ko/agenteye/python-sdk)를 사용하는 방법을 가르쳐 주며 — 라이브러리가 아니며, SDK의 동작 방식을 변경하지도 않습니다.

## 계측은 작성하기 쉽지만 조용히 틀리기도 쉽습니다

SDK는 작습니다. 열세 개의 이벤트 메서드, 모두 키워드 전용. 코딩 에이전트는 [Python SDK](/ko/agenteye/python-sdk) 레퍼런스를 읽고 그럴듯한 계측 코드를 1분 안에 만들어낼 수 있습니다.

문제는 이 SDK가 잘못된 코드를 작성해도 오류를 발생시키지 않는다는 점입니다. 잘못된 계측은 대시보드를 열어 아무것도 없다는 걸 확인하기 전까지는 올바른 계측과 구분이 되지 않습니다. 실제 시간을 낭비하게 만드는 실수는 모두 침묵의 형태입니다.

| 실수 | 보이는 것 |
|---|---|
| `agent_start` 누락 | 모든 이벤트가 기록됨. 세션은 제로. |
| 환경이 설정되지 않음 | 모든 게 작동하지만 `dev`로 분류됨. |
| `outcome="failure"` | 실행이 초록색으로 표시됨 — `failed`, `error`, `timeout`, `rejected`만 카운트됨. |
| 오타가 있는 필드명 | 새 필드로 저장됨. |
| 스레드 풀에서 이벤트 발행 | 조용히 누락됨. |

이 중 어느 것도 오류를 발생시키지 않습니다. 테스트에서도 나타나지 않습니다. 스킬에는 이 모든 경우가 포함되어 있으며, 각 경우를 잡아내는 검사와 함께 계약 형태로 명시되어 있습니다.

## 스킬이 수행하는 작업 순서

스킬은 신중한 엔지니어가 수행할 동일한 세 단계를 실행합니다.

1. **계획.** 에이전트 루프를 읽고 오직 여러분만이 답할 수 있는 두 가지 질문을 합니다. 무엇이 하나의 실행으로 간주되는가(`session_id`), 그리고 구별 가능한 행위자는 누구인가(`agent_id`). 코드 작성 전에 이 부분을 합의합니다. 나중에 변경하면 이력이 분리되고 트렌드가 깨지기 때문입니다.
2. **작성.** 모든 호출 지점에 전달하는 대신 실행 당 한 번 identity를 바인딩하고, 동시성에 안전한 구조를 선택합니다. 이는 중요한 세부 사항으로, 명백한 지름길을 택하면 두 개의 겹치는 실행이 하나의 세션으로 조용히 섞이게 됩니다.
3. **검증.** 에이전트를 실행하고 결과 이벤트 파일을 읽어, `agent_start`가 있는지, 환경이 올바른지, 하나의 실행이 하나의 세션을 생성했는지 확인합니다.

세 번째 단계가 사람들이 건너뛰는 바로 그 단계입니다. SDK는 이벤트를 로컬 파일에 기록하므로, 완전한 통합은 서버, API 키, 네트워크 없이 노트북에서 검증할 수 있습니다 — 스킬이 이 단계를 반드시 수행하도록 하는 이유가 바로 그것입니다.

## 다른 스킬과의 관계

세 가지 스킬, 하나의 명확한 분리:

| 스킬 | 사용 시점 | 대상 |
|---|---|---|
| **Python SDK 스킬** (이 페이지) | 에이전트가 텔레메트리를 *발행*하길 원할 때 — "관측 가능성 추가", "에이전트가 왜 표시되지 않지?" | 에이전트 저장소에 코드를 작성합니다. 아무것도 읽지 않습니다. |
| **[Evaluator 스킬](/ko/agenteye/evaluator-skill)** | 실행을 *채점*하길 원할 때 — "무엇을 측정해야 하지?" | 저장소에 코드를 작성하고 텔레메트리를 읽습니다. |
| **[CLI 스킬](/ko/agenteye/cli-skill)** | 무슨 일이 있었는지 *읽거나* 배포를 운영하길 원할 때 | 변경 사항을 포함해 CLI를 사용자로서 구동합니다. |

이 순서로 이어집니다. 이 스킬이 이벤트를 흐르게 하고, evaluator가 채점하고, CLI가 다시 읽어 옵니다. 에이전트가 세션을 발행하기 전에는 평가할 것도, 읽을 것도 없습니다. 처음 시작한다면 여기서 시작하세요.

## 사전 요구 사항

1. **Python 3.10+** 와 계측하려는 에이전트 코드베이스.
2. **SDK.** 공개 인덱스가 아닌 비공개 wheel로 고객에게 배포됩니다 — 온보딩 과정에서 취득 및 설치 방법을 안내합니다. 스킬은 설치 경로를 알고 있으며, 찾을 수 없는 경우 추측하는 대신 여러분에게 물어봅니다.
3. **그 외 없음.** 대시보드 로그인도, API 키도, 네트워크도 필요하지 않습니다. 스킬은 SDK가 기록한 이벤트 파일을 기준으로 검증하므로 오프라인에서 작업을 완료하고 결과를 증명할 수 있습니다.

## 취득 방법

스킬은 공개 [`FailproofAI/skills`](https://github.com/FailproofAI/skills) 컬렉션에 있습니다.

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

현재 프로젝트 대신 모든 프로젝트에 설치하려면 `-g`를 추가하고, 환경이 심볼릭 링크를 따르지 않는 경우 `--copy`를 사용하세요. Codex의 경우 `-a codex`를 전달하세요.

## 수동 설치

에이전트 스킬은 `SKILL.md`와 참조 파일들로 구성된 폴더입니다. 설치 프로그램을 사용하지 않으려면:

- **Claude Code**: `agenteye-python-sdk/` 폴더를 `~/.claude/skills/`(모든 프로젝트) 또는 `<your-repo>/.claude/skills/`(해당 저장소만)에 복사하세요. Claude Code가 자동으로 감지합니다 — `/skills` 목록을 확인하거나 매칭되는 내용을 물어보세요.
- **Codex**: Codex도 동일한 `SKILL.md`를 읽습니다. 번들된 `agents/openai.yaml`에 `allow_implicit_invocation: true`가 설정되어 있어 작업이 매칭되면 자동으로 선택됩니다. 그렇지 않은 경우 `$agenteye-python-sdk`로 호출하세요.

계측하려는 코드가 있는 저장소에서 에이전트를 실행하세요 — 스킬은 제안을 하기 전에 에이전트 루프를 읽습니다.

## 세션이 어떻게 보이는지

```text
you   ▸ Add Failproof AI Observability to this agent.

agent ▸ Read your loop — one tool dispatcher in tools.py, one Anthropic
        wrapper in llm.py. Two questions before I write anything.

        What counts as one run? You handle requests concurrently, so I'd
        use the request id you already have in ctx.request_id — then a
        session here and a request in your logs are the same string.

        And who are the actors? I see a planner path and a researcher
        path. Label them separately, or is that one agent to you?

you   ▸ Request id is right. They're one agent, call it "assistant".

agent ▸ Done. Wrapped the dispatcher and the LLM client; agent_start and
        agent_end bracket handle_request, including the error path. Used
        a context-local for identity — your dispatcher runs tools in a
        thread pool, and the simpler approach would have mixed concurrent
        runs into one session without complaining.

        Verified against a real run: 11 events across 4 files —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, one session
        per request, durations paired.

        One thing I did NOT do: your worker pool in batch.py submits
        straight to the executor, so events from there would be dropped.
        Want me to fix those too?
```

주목할 패턴: 제안하기 전에 코드를 읽었고, 여러분만이 답할 수 있는 질문만 했으며, 이미 있던 ID를 재사용하고, 스레드 풀을 봤기 *때문에* 동시성에 안전한 구조를 선택했으며, 성공을 선언하는 대신 **실제 이벤트를 읽어 검증**했습니다 — 그런 다음 조용히 실패할 것을 알고 있는 한 곳을 별도로 표시했습니다.

## 물어볼 수 있는 것

- *"에이전트가 대시보드에 왜 표시되지 않죠?"* → 단계별로 확인: 이벤트가 기록되고 있는지, `agent_start`가 있는지, 환경이 올바른지, 컬렉터가 같은 위치를 읽고 있는지.
- *"모든 게 dev 아래에 기록돼요."* → 환경이 설정되지 않았거나, 이후 호출에 의해 재설정됐습니다.
- *"토큰 추적 추가해줘."* → LLM 래퍼를 찾아 모델, 중단 이유, 사용량을 기록합니다.
- *"서브 에이전트도 계측해줘."* → 하나의 세션, 구별되는 에이전트 레이블, 부모 아래에 중첩.
- *"계측에 대한 테스트 작성해줘."* → SDK를 임시 디렉터리로 향하게 하고 기록된 이벤트에 대해 어설션합니다.

## 주의할 점

**검증 단계를 실행하게 하세요.** 이 스킬을 가치 있게 만드는 단계는 마지막 단계입니다 — 에이전트를 실행하고 이벤트를 다시 읽는 것. 계측을 작성하고 멈추는 에이전트는 쉬운 절반만 한 것이며, 조용히 실패하는 절반은 나머지 부분입니다.

**코드보다 먼저 이름을 정하세요.** `session_id`와 `agent_id`는 모든 화면이 그룹화하는 기준 축입니다. 나중에 이름을 바꾸면 이력이 분리됩니다. 오래된 실행은 이전 레이블을 유지하고 트렌드가 깨집니다. 스킬이 물어볼 것이며, 그 답은 잠깐 생각해볼 가치가 있습니다.

**에이전트가 공개 인덱스에서 SDK를 설치하자고 제안한다면, 스킬이 로드되지 않은 것입니다.** SDK는 비공개로 배포됩니다. 그 제안은 코딩 에이전트가 스킬을 따르지 않고 추측하고 있다는 확실한 신호입니다 — 거기서 멈추고 스킬이 설치되어 있는지 확인하세요.

그 외에 영향 범위는 작습니다. 작업 디렉터리에 코드를 작성하고 지정한 곳에 이벤트 파일을 기록합니다. 배포에서는 아무것도 읽지 않으며 아무것도 변경하지 않습니다.
