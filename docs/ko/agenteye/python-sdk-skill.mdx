코딩 에이전트에게 *"이 에이전트에 Failproof AI 관찰 가능성을 추가해줘"* 라고 말하면, 에이전트가 루프를 읽고, 계측 위치를 파악하고, 코드를 작성하고, 완료를 선언하기 전에 이벤트를 검증합니다.

**Python SDK 스킬** (`agenteye-python-sdk`)은 *에이전트 스킬*입니다. 태스크가 매칭될 때 Claude Code나 Codex 같은 코딩 에이전트가 온디맨드로 불러오는 지침 폴더입니다. 이 스킬은 에이전트가 [Python SDK](/ko/agenteye/python-sdk)를 사용하는 방법을 가르쳐줍니다 — 라이브러리가 아니며, SDK의 동작 방식을 변경하지 않습니다.

## 계측은 작성하기 쉽지만, 조용히 잘못되기도 쉽습니다

SDK는 작습니다: 열세 개의 이벤트 메서드, 모두 키워드 전용입니다. 코딩 에이전트는 [Python SDK](/ko/agenteye/python-sdk) 레퍼런스를 읽고 그럴듯한 계측 코드를 1분 만에 만들어낼 수 있습니다.

문제는 이 SDK가 잘못 사용해도 오류를 발생시키지 않는다는 점입니다. 잘못된 계측은 누군가가 대시보드를 열어 비어 있다는 걸 발견하기 전까지 올바른 계측과 똑같이 보입니다. 실제로 시간을 잡아먹는 실수는 모두 침묵의 형태입니다:

| 실수 | 보이는 것 |
|---|---|
| `agent_start` 없음 | 모든 이벤트는 수신됨. 세션은 0개. |
| 환경이 설정되지 않음 | 모든 것이 작동하지만, `dev`로 기록됨. |
| `outcome="failure"` | 실행이 정상으로 표시됨 — `failed`, `error`, `timeout`, `rejected`만 유효함. |
| 필드 이름 오타 | 수락되어 새 필드로 저장됨. |
| 스레드 풀에서 이벤트 발행 | 조용히 드롭됨. |

이 중 어느 것도 오류를 발생시키지 않습니다. 테스트에서도 나타나지 않습니다. 이 모든 내용이 스킬에 포함되어 있으며, 잡아내는 검사와 함께 계약으로 명시되어 있습니다.

## 스킬이 하는 일, 순서대로

스킬은 신중한 엔지니어가 수행할 세 단계를 동일하게 실행합니다:

1. **계획.** 에이전트 루프를 읽고 오직 당신만 답할 수 있는 두 가지 질문을 합니다: 하나의 실행이 무엇인지(`session_id`), 그리고 구분 가능한 행위자가 누구인지(`agent_id`). 코드를 작성하기 전에 이것을 합의합니다. 나중에 변경하면 히스토리가 분리되고 트렌드가 깨지기 때문입니다.
2. **작성.** 모든 호출 지점에 전달하는 대신 실행당 한 번만 ID를 바인딩하고, 동시성에 안전한 형태를 선택합니다 — 이는 중요한 세부 사항인데, 단순한 지름길은 두 개의 겹치는 실행을 아무 불평 없이 하나의 세션으로 섞어버리기 때문입니다.
3. **검증.** 에이전트를 실행하고 결과 이벤트 파일을 읽어서 `agent_start`가 있는지, 환경이 올바른지, 하나의 실행이 하나의 세션을 생성했는지 확인합니다.

세 번째 단계가 사람들이 건너뛰는 단계입니다. SDK는 이벤트를 로컬 파일에 기록하므로, 완전한 통합은 서버도, API 키도, 네트워크도 없이 노트북에서 증명할 수 있습니다 — 그게 바로 스킬이 이 단계를 고집하는 이유입니다.

## 다른 스킬과의 관계

세 개의 스킬, 하나의 명확한 분리:

| 스킬 | 사용 시점 | 접촉 범위 |
|---|---|---|
| **Python SDK 스킬** (이 페이지) | 에이전트가 텔레메트리를 *발행*하게 하고 싶을 때 — "관찰 가능성 추가", "에이전트가 왜 안 보이지?" | 에이전트 리포지토리에 코드 작성. 읽기 없음. |
| **[Evaluator 스킬](/ko/agenteye/evaluator-skill)** | 실행을 *점수 매기고* 싶을 때 — "무엇을 측정해야 하지?" | 리포지토리에 코드 작성; 텔레메트리 읽기 |
| **[CLI 스킬](/ko/agenteye/cli-skill)** | 무슨 일이 있었는지 *읽거나*, 배포를 운영하고 싶을 때 | 사용자로서 CLI 구동, 변경 사항 포함 |

순서대로 연결됩니다: 이 스킬이 이벤트를 흐르게 하고, evaluator가 점수를 매기고, CLI가 다시 읽습니다. 에이전트가 세션을 발행하기 전까지는 평가할 것도 읽을 것도 없습니다. 처음부터 시작한다면 여기서 시작하세요.

## 사전 조건

1. **Python 3.10+** 및 계측하려는 에이전트 코드베이스.
2. **SDK.** 공개 인덱스가 아닌 비공개 휠로 고객에게 배포됩니다 — 온보딩 과정에서 받는 방법과 설치 방법을 안내받습니다. 스킬은 설치 경로를 알고 있으며, 찾지 못하면 추측하지 않고 당신에게 물어봅니다.
3. **그 외 없음.** 대시보드 로그인, API 키, 네트워크 모두 필요 없습니다. 스킬은 SDK가 작성하는 이벤트 파일을 기준으로 검증하므로, 오프라인에서도 작업을 완료하고 증명할 수 있습니다.

## 스킬 받는 방법

스킬은 공개 [`FailproofAI/skills`](https://github.com/FailproofAI/skills) 컬렉션에 있습니다:

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

현재 프로젝트가 아닌 모든 프로젝트에 설치하려면 `-g`를 추가하고, 환경이 심볼릭 링크를 지원하지 않으면 `--copy`를 사용하세요. Codex의 경우 `-a codex`를 전달하세요.

## 수동으로 설치하기

에이전트 스킬은 `SKILL.md`와 참조 파일들로 이루어진 폴더입니다. 설치 프로그램을 사용하지 않으려면:

- **Claude Code**: `agenteye-python-sdk/` 폴더를 `~/.claude/skills/`(모든 프로젝트) 또는 `<your-repo>/.claude/skills/`(해당 리포지토리만)에 복사하세요. Claude Code가 자동으로 감지합니다 — `/skills` 목록을 확인하거나, 매칭되는 내용을 물어보기만 하면 됩니다.
- **Codex**: Codex는 동일한 `SKILL.md`를 읽습니다. 번들에 포함된 `agents/openai.yaml`이 `allow_implicit_invocation: true`로 설정되어 있어, 태스크가 매칭되면 자동으로 선택됩니다. 그렇지 않으면 `$agenteye-python-sdk`로 호출하세요.

계측하려는 코드가 있는 리포지토리에서 에이전트를 **실행하세요** — 스킬은 무언가를 제안하기 전에 에이전트 루프를 읽습니다.

## 세션 예시

```text
you   ▸ Add Failproof AI Observability to this agent.

agent ▸ Read your loop — one tool dispatcher in tools.py, one Anthropic
        wrapper in llm.py. Two questions before I write anything.

        What counts as one run? You handle requests concurrently, so I'd
        use the request id you already have in ctx.request_id — then a
        session here and a request in your logs are the same string.

        And who are the actors? I see a planner path and a researcher
        path. Label them separately, or is that one agent to you?

you   ▸ Request id is right. They're one agent, call it "assistant".

agent ▸ Done. Wrapped the dispatcher and the LLM client; agent_start and
        agent_end bracket handle_request, including the error path. Used
        a context-local for identity — your dispatcher runs tools in a
        thread pool, and the simpler approach would have mixed concurrent
        runs into one session without complaining.

        Verified against a real run: 11 events across 4 files —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, one session
        per request, durations paired.

        One thing I did NOT do: your worker pool in batch.py submits
        straight to the executor, so events from there would be dropped.
        Want me to fix those too?
```

주목할 패턴: 코드를 먼저 읽은 후 제안했고, 당신만 답할 수 있는 질문만 했으며, 이미 가지고 있던 ID를 재사용했고, 스레드 풀을 발견했기 *때문에* 동시성에 안전한 형태를 선택했으며, 성공을 선언하는 대신 **실제 이벤트를 읽어 검증**했습니다 — 그리고 조용히 실패할 것을 알고 있는 한 곳을 명확히 표시했습니다.

## 물어볼 수 있는 것들

- *"에이전트가 왜 대시보드에 안 보이지?"* → 단계를 밟아 올라갑니다: 이벤트가 기록되고 있는지, `agent_start`가 있는지, 환경이 맞는지, 수집기가 같은 위치를 읽고 있는지.
- *"모든 게 dev 아래에 기록되고 있어."* → 환경이 설정되지 않았거나, 이후 호출에 의해 재설정됐습니다.
- *"토큰 추적 추가해줘."* → LLM 래퍼를 찾아 모델, 중단 이유, 사용량을 기록합니다.
- *"서브 에이전트도 계측해줘."* → 하나의 세션, 구분된 에이전트 레이블, 부모 아래에 중첩됩니다.
- *"계측을 위한 테스트 작성해줘."* → SDK를 임시 디렉토리로 지정하고 작성된 이벤트를 검증합니다.

## 주의사항

**검증을 실행하게 하세요.** 이 스킬의 가치를 만드는 단계는 마지막 단계입니다 — 에이전트를 실행하고 이벤트를 다시 읽는 것. 계측을 작성하고 멈추는 에이전트는 쉬운 절반만 한 것이고, 조용히 실패하는 절반이 나머지입니다.

**코드 전에 이름을 합의하세요.** `session_id`와 `agent_id`는 모든 뷰가 그룹화하는 축입니다. 나중에 이름을 바꾸면 히스토리가 분리됩니다: 이전 실행은 이전 레이블을 유지하고 트렌드가 깨집니다. 스킬이 물어볼 것이고, 그 답은 잠깐의 고민 가치가 있습니다.

**에이전트가 공개 인덱스에서 SDK를 설치하려고 제안한다면, 스킬이 로드되지 않은 것입니다.** SDK는 비공개로 배포됩니다. 그 제안은 코딩 에이전트가 스킬을 따르는 게 아니라 추측하고 있다는 신뢰할 수 있는 신호입니다 — 거기서 멈추고 스킬이 설치되어 있는지 확인하세요.

그 외에는 영향 범위가 작습니다: 작업 디렉토리에 코드를 작성하고, 지정된 위치에 이벤트 파일을 씁니다. 배포에서 아무것도 읽지 않으며, 아무것도 변경하지 않습니다.
