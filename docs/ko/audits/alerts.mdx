알림은 측정 가능한 조건을 감시하다가 조건이 충족되면 이슈를 생성합니다. 정책으로 차단할 수 있는지 여부와 관계없이, 장애 발생 시 신속한 대응이 필요할 때 사용하세요.

## 알림 생성 및 테스트

<Tabs>
  <Tab title="대시보드">
    1. **Analyze → Alerts**로 이동하여 **new alert**을 선택합니다. 대표적인 오류의 벨 아이콘에서 시작할 수도 있습니다.
    2. 이름, 심각도, 트리거 종류, 조건, 평가 주기, 위반 횟수, 윈도우, 채널을 입력합니다.
    3. 알림을 저장한 후 상세 페이지를 열어 **test**를 실행합니다.
    4. **Analyze → Issues**로 이동하여 알림이 생성한 이슈를 확인, 할당, 논의, 구독, 해결합니다.

    양식의 첫 번째 부분에서는 알림과 이를 트리거할 신호를 정의합니다.

    ![이름, 설명, 활성화 상태, 트리거 유형이 포함된 새 알림 양식의 첫 번째 부분.](/images/dashboard/alert-new-trigger.png)

    두 번째 부분에서는 조건이 지속되어야 하는 기간, 평가 빈도, 알림을 전송할 채널을 설정합니다.

    ![위반 로직, 일정, 심각도, 전송 채널, 생성 액션이 포함된 새 알림 양식의 두 번째 부분.](/images/dashboard/alert-new-routing.png)

    저장 후 Alerts 목록에서 규칙이 활성화되어 있는지, 트리거·윈도우·심각도·채널이 의도한 대로 설정되어 있는지 확인하세요. 열린 이슈가 있는 카드에는 이슈 수가 표시되고, 없는 카드에는 해당 줄 자체가 생략됩니다. 따라서 줄이 없다고 해서 반드시 이슈가 없는 것은 아닙니다. 0인 경우를 포함한 모든 규칙의 수치를 확인하려면 `fp alerts show <name>`을 사용하세요. 이 명령은 항상 해당 값을 출력합니다.

    ![트리거, 평가 윈도우, 채널, 심각도가 표시된 알림 규칙 목록 페이지.](/images/dashboard/alerts.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp alerts create high-errors \
      --trigger-kind metric_threshold \
      --severity warning \
      --trigger-spec '{"metric":"error_count","op":">","value":50,"window_secs":900}' \
      --eval-interval-secs 300 \
      --min-breaches 2 \
      --eval-window 3

    fp alerts show high-errors
    fp alerts test high-errors
    fp alerts update high-errors --severity critical --yes
    ```

    새 알림은 **활성화** 상태로 시작되며, 이름이 충돌하면 생성 전에 거부됩니다.

    `fp alerts update`는 서버 측에서 전체 정의를 교체하므로, CLI가 알림을 다시 읽어 플래그를 덮어씁니다. 플래그만으로 업데이트할 경우 `alerts:write`뿐만 아니라 `alerts:read` 권한도 필요하며, `--yes`를 전달하지 않으면 확인을 요청합니다.

    규칙 목록을 확인하려면 `fp alerts list`를, 규칙을 삭제하려면 `fp alerts delete <name>`을 사용하세요. 삭제 시에는 규칙 정보(열린 이슈 수 포함)를 미리 보여주고 확인을 요청합니다. 이 작업은 취소할 수 없습니다.

    소란스러운 규칙을 잠재울 목적으로 삭제를 사용하지 마세요. `DELETE /alerts/{id}`는 연쇄 삭제를 수행합니다. 해당 알림이 생성한 모든 이슈가 함께 삭제되며, 댓글·구독자·활동 이력도 모두 사라집니다. CLI의 확인 메시지에서는 열린 이슈가 "고아 상태"가 된다고 표현하지만, API 계약상 연쇄 삭제이므로 이력이 완전히 사라진다고 보아야 합니다. 규칙 실행을 멈추면서 기록을 유지하려면 삭제 대신 비활성화하세요. 대시보드 알림 양식에 활성화 토글이 있습니다. `fp alerts create`와 `fp alerts update` 모두 `--enabled` 플래그를 제공하지 않으므로, CLI에서는 `fp alerts update <name> --file` 명령과 함께 `enabled: false`가 포함된 전체 정의 파일을 사용하세요.

    전체 알림 명령 목록은 [`fp alerts` 레퍼런스](/ko/reference/cloud-cli#alerts)를 참조하세요.
  </Tab>
</Tabs>

<Warning>
  **test**는 실제 알림을 전송합니다. 알림에 설정된 실제 이메일, Slack, 웹훅 채널로 전송되고 합성 이슈를 생성하므로, 현재 당직 중인 담당자에게 페이지가 전달될 수 있습니다. 인터랙티브 터미널에서는 먼저 확인을 요청하며, `--yes`, `--json`, stdin 리디렉션을 사용하면 확인 프롬프트를 건너뜁니다. 서버는 메시지를 디스패치하는 즉시 성공으로 응답하므로, 테스트 성공은 메시지가 발송되었다는 의미이지 실제로 도착했다는 의미가 아닙니다.
</Warning>

## 트리거 정의

트리거 종류는 다섯 가지입니다:

| `--trigger-kind` | 실행 조건 |
| --- | --- |
| `metric_threshold` | 오류 수, 지연 시간, 비용 등 측정 가능한 지표가 임계값을 초과할 때. |
| `per_event` | 조건에 일치하는 단일 이벤트가 도착할 때. |
| `evaluation_score` | 평가자 점수가 임계값을 초과할 때. |
| `eval_compound` | 세 점수 중 두 점수 실패와 같이 여러 점수 조건이 결합될 때. |
| `custom_sql` | 직접 작성한 쿼리가 위반을 반환할 때. |

조건 자체는 선택한 종류에 맞는 형식으로 `--trigger-spec`에 지정합니다.

## 평가 수치 설정

대시보드 양식과 CLI는 동일한 네 가지 값을 요구합니다.

| 설정 | 플래그 | 허용 값 |
| --- | --- | --- |
| 심각도 | `--severity` | `info`, `warning`, `critical` |
| 평가 주기 | `--eval-interval-secs` | 30–86,400초 |
| 위반 횟수 | `--min-breaches` | 최소 1, 윈도우 값 이하 |
| 평가 윈도우 | `--eval-window` | 최소 1, 초 단위가 아닌 **주기** 단위 |

예를 들어 `--eval-interval-secs 300 --min-breaches 2 --eval-window 3`은 "5분마다 평가하여 마지막 3번의 평가 중 2번이 위반된 경우 실행"을 의미합니다.

## 좋은 알림 설계 원칙

- 조건과 영향을 받는 워크플로우를 이름에 명시하세요.
- 환경 범위를 명확히 지정하세요.
- 무해한 단일 이벤트에 반응하지 않도록 윈도우와 임계값을 설정하세요.
- 담당자가 세션을 찾을 수 있는 링크나 쿼리를 포함하세요.
- 규칙을 활성화하기 전에 담당자를 지정하세요.
- 동일한 증상에 대한 규칙을 추가하기 전에 `fp alerts show <name>`으로 열린 이슈 수를 확인하세요. 대시보드 카드는 수치가 0이 아닐 때만 해당 줄을 표시합니다.

<Tip>
  감사 결과를 해결한 후, 동일한 장애가 정책 적용 범위 밖에서 재발할 수 있는 경우 알림을 추가하세요.
</Tip>
