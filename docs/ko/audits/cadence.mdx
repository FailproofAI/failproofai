에이전트, 프롬프트, 도구, 모델이 변경될 때 재발할 수 있는 장애 유형에는 반복 감사를 활용하세요.

## 스케줄 변경

<Tabs>
  <Tab title="대시보드">
    1. **분석 → 감사**로 이동하여 해당 감사를 엽니다.
    2. **설정 편집**을 선택하고 주기, 윈도우, 민감도, 실행당 발견 항목 수를 변경합니다.
    3. 감사를 저장하고 감사 헤더에서 다음 실행 시간을 확인합니다.
    4. 같은 헤더의 **지금 실행** 옆에서 스케줄을 일시 중지하거나 재개할 수 있습니다.
    5. 범위나 컨텍스트가 크게 변경된 후에는 **지금 실행**을 한 번 사용하세요.

    ![일시 중지 상태, 열린 발견 항목, 마지막 실행, 다음 실행, 스윕 윈도우, 민감도를 표시하고 지금 실행, 설정 편집, 재개 컨트롤이 있는 감사 헤더.](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits edit checkout-reliability \
      --schedule-interval-secs 86400 \
      --schedule-anchor 2026-08-15T09:00:00Z \
      --window-mode since_last \
      --lookback-window-secs 86400 \
      --yes

    fp audits edit checkout-reliability --disabled --yes
    fp audits edit checkout-reliability --enabled --yes
    ```

    `fp audits edit`는 변경하기 전에 확인을 요청하므로, 이 예시들에서는 모두 `--yes`를 전달합니다. 서버는 편집 시마다 전체 정의를 교체하므로, CLI는 변경 사항이 적용된 현재 감사를 재전송합니다. 플래그만 변경하는 편집도 `audits:read`와 `audits:write` 권한이 **모두** 필요합니다. CI 키에 두 권한을 모두 부여하세요.

    스케줄 범위, 윈도우 동작 방식, 모든 감사 명령에 대해서는 [`fp audits` 레퍼런스](/ko/reference/cloud-cli#audits)를 참조하세요.
  </Tab>
</Tabs>

## 두 가지 스케줄 범위

아래의 모든 권장 사항은 이 범위 안에 맞아야 합니다. 범위는 서버 기준이며 `fp`가 클라이언트 측에서도 동일하게 적용하므로, 범위를 벗어난 값은 422 왕복 요청 비용 없이 로컬에서 종료 코드 2로 종료됩니다.

| 필드 | 플래그 | 범위 | 기본값 |
| --- | --- | --- | --- |
| 스케줄 간격 | `--schedule-interval-secs` | 3,600–604,800초 (1시간~7일) | 86,400 (매일) |
| 룩백 윈도우 | `--lookback-window-secs` | 3,600–7,776,000초 (1시간~90일) | 604,800 (7일) |

주기의 최대값은 7일입니다. 클라우드 감사의 월간 옵션은 없습니다.

## 주기 선택

위험의 속도와 비용에 따라 선택하세요:

| 위험 패턴 | 권장 시작 주기 |
| --- | --- |
| 영향도 높은 프로덕션 작업 | 매일, 또는 위험한 변경 사항이 배포되는 동안 매시간 |
| 워크플로우 또는 모델 회귀 | 매주 |
| 거버넌스 또는 접근 권한 검토 | 매주 — 최대 설정 가능한 간격 |

실행 간 공백이 생기거나 불필요하게 큰 범위를 반복 검토하지 않도록 룩백 윈도우를 주기에 맞춰 조정하세요.

단발성 감사는 없으며, 모든 감사에는 스케줄 간격이 포함됩니다. 릴리스 조사를 위해서는 감사를 활성화 상태로 생성하고, 첫 번째 실행이 완료될 때까지 기다린 후 — 앵커와 관계없이 첫 번째 실행은 생성 즉시 큐에 추가됩니다 — `fp audits edit <name> --disabled --yes`로 일시 중지하세요. **지금 실행**을 사용하기 전에 다시 활성화하세요. 비활성화된 감사에는 큐 행이 없으므로, 비활성화 상태에서 수동 실행을 시도하면 409 오류가 반환됩니다.

## 윈도우 모드와 앵커

`--window-mode`는 각 실행이 스윕하는 윈도우를 결정합니다:

| 모드 | 동작 방식 |
| --- | --- |
| `since_last` | 마지막으로 완전히 분석된 윈도우의 끝부터 계속 이어가므로, 실행을 건너뛰어도 공백이 생기지 않습니다. |
| `fixed` | 마지막 실행 범위와 관계없이 매 실행 시 `lookback_window_secs` 기준의 롤링 윈도우를 재검토합니다. |

`--schedule-anchor`는 빈도가 아닌 위상을 고정합니다. 실행은 `앵커 + N × 간격` 시점에 이루어집니다. 앵커를 생략하면 기본값으로 다음 UTC 09:00이 설정되며, 365일 이후의 앵커는 거부됩니다. 간격이나 앵커를 변경하면 이미 큐에 들어간 실행이 아닌 다음 스케줄 변경 시점에 적용되고, 실패한 실행은 앵커를 이동시키지 않습니다.

감사의 목표나 컨텍스트를 변경한 후에는 다음 예약 결과를 신뢰하기 전에 수동으로 한 번 실행하세요.

<Note>
  이 페이지는 클라우드 세션에서 동작하는 클라우드 감사 스케줄에 관한 내용입니다. 로컬 감사에는 별도의 타이머가 있습니다. `failproofai audit --schedule [days]`는 1~90일을 받으며 기본값은 7일이고, 해당 단일 머신의 에이전트 이력을 스캔하며, 월간 옵션이 제공되는 유일한 인터페이스입니다. 로컬 감사의 결과와 소유권은 여기서 다루는 내용과 별개입니다 — [로컬 에이전트 이력 감사](/ko/audits/local-audit)를 참조하세요.
</Note>
