이 레시피들을 시작 목표로 활용하고, 에이전트, 환경, 예상 워크플로우를 추가하세요.

<Tabs>
  <Tab title="대시보드">
    **분석 → 감사 → 새 감사**로 이동합니다. 이 페이지의 레시피 한 줄은 **설명**입니다 — 이 감사가 무엇을 포착하길 기대하는지를 나타냅니다. 목표를 판단 가능하게 만드는 워크플로우 규칙은 **내용 요약** 카드의 **브리프**에 작성합니다. 브리프는 모델이 이벤트를 하나씩 살펴보기 전에 읽는 배경 정보로, 최대 8,192자까지 입력할 수 있으며 감사가 이미 찾고 있는 내용에 추가됩니다. 브리프는 목표를 대체하는 것이 아니며, 발견 사항의 증거도 아닙니다.

    그다음 **읽는 대상**에서 범위를 설정하세요. 이 레시피들의 절반은 범위 없이는 노이즈만 발생합니다. 환경과 에이전트는 대상 모집단을 좁히고, **무시할 오류**는 설계상 예상되고 처리되는 오류 유형을 나열하여 실패로 집계되지 않도록 합니다. 오류 유형 이름만 입력하며, 이것이 재시도 루프 레시피의 과다 감지를 막는 방법입니다.

    새 감사 양식은 범위, 컨텍스트, 주기, 알림을 추가함으로써 레시피를 실행 가능한 오류 검사로 변환합니다.

    ![집중된 목표, 일정, 에이전트 및 환경 범위, 컨텍스트, 알림 채널로 구성된 새 감사 양식.](/images/dashboard/audit-new.png)

    생성 후, 정기 실행에 의존하기 전에 감사가 목록에 예상 상태와 일정으로 표시되는지 확인하세요.

    첫 번째 실행을 열어보고, 발견된 내용이 의도한 오류 모드보다 넓거나 좁다면 레시피를 수정하세요.
  </Tab>
  <Tab title="CLI">
    레시피를 텍스트 파일로 저장하고 생성 시 첨부합니다:

    ```bash
    fp audits create retry-loop-review \
      --description "Find agents that repeat a failing tool call without changing anything" \
      --scope '{"environments":["production"]}' \
      --ignore-error-type RateLimitRetried \
      --text-file ./retry-loop-audit.txt \
      --schedule-interval-secs 86400
    ```

    `--text`와 `--text-file`은 동일한 브리프를 전송하는 두 가지 방법입니다. 둘 중 하나만 사용하세요. 참조 페이지는 `--url`로 최대 5개까지 추가할 수 있으며, 공개 `https://` URL만 허용됩니다. 모든 내용을 생성 요청 시 함께 전송하세요. 새로 활성화된 감사는 즉시 실행되므로, 두 번째 호출로 작성한 컨텍스트는 첫 번째 실행에 반영되지 않을 수 있습니다.
  </Tab>
</Tabs>

## 문구가 아닌 레시피 자체를 판단하세요

문구보다 결과에 더 큰 영향을 미치는 두 가지 설정이 있습니다. **민감도**(`low`, `medium`, `high`, 기본값 `medium`)는 실행 시 패턴을 얼마나 적극적으로 플래그할지 결정하고, **실행당 발견 수**(`--top-k`, 기본값 50)는 유지할 최대 개수를 제한합니다. 놓쳤을 때의 비용이 오탐보다 큰 질문에는 민감도를 높이고, 그렇지 않으면 대기열을 채울 수 있는 볼륨 패턴에는 낮추세요. 아래의 각 레시피는 시작 지점을 제시합니다 — 첫 번째 실행 결과를 읽은 후에 변경하세요.

작업 포기 및 인간 에스컬레이션 누락은 에이전트가 발생시킨 오류가 아닌, 에이전트가 수행해야 했던 것에 대한 판단입니다. 해당 에이전트의 [에이전트 컨텍스트](/ko/audits/agent-contracts)를 먼저 작성하세요. 그렇지 않으면 분석에 판단 기준이 없습니다.

<AccordionGroup>
  <Accordion title="반복 재시도 루프">
    에이전트가 입력을 변경하거나, 대체 도구를 선택하거나, 인간에게 에스컬레이션하지 않고 동일한 실패하는 도구 호출을 반복하는 세션을 찾습니다.

    `medium`에서 시작하고, 의도적으로 재시도하는 오류 유형은 **무시할 오류**에 나열하세요.
  </Accordion>
  <Accordion title="잘못된 도구 사용">
    선택한 도구가 명시된 작업과 일치하지 않거나, 도구 입력이 워크플로우의 필수 사전 조건을 위반하는 세션을 찾습니다.

    `medium`에서 시작합니다. 사전 조건 자체를 브리프에 포함하세요. 그렇지 않으면 분석에 확인할 규칙이 없습니다.
  </Accordion>
  <Accordion title="안전하지 않은 데이터 접근">
    이 에이전트에 대해 승인된 경로 및 서비스 외부에서 민감한 데이터를 읽거나, 쓰거나, 전송하는 세션을 찾습니다.

    `high`에서 시작합니다. 누락된 노출은 한 번 무시할 수 있는 오탐보다 비용이 더 큽니다.
  </Accordion>
  <Accordion title="작업 포기">
    요청된 결과, 명확한 오류, 또는 인간에 대한 명시적인 핸드오프 없이 종료되는 세션을 찾습니다.

    `medium`에서 시작하고, 에이전트의 **완료 조건** 섹션을 먼저 작성하세요 — 이 레시피는 그 기준에 대한 판단입니다.
  </Accordion>
  <Accordion title="비용 또는 지연 시간 회귀">
    모델, 도구 또는 총 실행 시간이 예상 예산을 초과하는 세션을 찾고, 원인이 되는 이벤트 패턴을 식별합니다.

    `low`에서 시작하고, 첫 번째 실행이 결과가 부족하면 높이세요. 예산은 브리프에 포함하고, 느린 경로가 설계상 발생시키는 오류 유형은 **무시할 오류**에 추가하세요.
  </Accordion>
  <Accordion title="인간 에스컬레이션 누락">
    신뢰도 부족, 반복 실패, 또는 정책 지침이 인간의 결정을 요구했음에도 에이전트가 자율적으로 계속 진행한 세션을 찾습니다.

    `high`에서 시작하고, 에이전트의 **금지 사항** 섹션에 에스컬레이션 규칙을 명시하여 분석이 이를 기준으로 판단할 수 있도록 하세요.
  </Accordion>
</AccordionGroup>

## 아무것도 만들기 전에 먼저 답을 얻으세요

이러한 패턴 중 일부는 로컬 감사에 오프라인 감지기가 이미 포함되어 있습니다. 로컬 감사는 본인 컴퓨터에서 에이전트 기록을 읽으며 계정이 필요 없습니다:

| 감지기 | 감지하는 패턴 |
| --- | --- |
| `sleep-polling-loop` | 긴 `sleep`, 또는 `while … sleep … done` 폴링 루프 |
| `reread-after-edit` | 에이전트가 방금 편집하거나 작성한 파일 재읽기 |
| `find-from-root` | `/` 또는 다른 상위 디렉터리를 대상으로 한 `find` |
| `redundant-cd-cwd` | 셸이 이미 있는 디렉터리로 `cd` |
| `prefer-edit-over-read-cat` | 단일 소스 파일에 대한 `cat`, `head`, `tail`, `less`, 또는 `more` |
| `prefer-edit-over-sed-awk` | `sed -i` 또는 `awk … > file`을 통한 인플레이스 편집 |
| `prefer-write-over-heredoc` | 히어독 또는 `echo > file`을 통해 작성된 여러 줄 내용 |
| `git-commit-no-verify` | 훅을 건너뛰는 `git commit --no-verify` |

이 감지기들은 집계만 합니다. 차단하지 않으며, 비용이나 지연 시간을 측정하지도 않습니다. 동일한 내용에 대한 클라우드 감사 비용을 지불하기 전에, 에이전트가 이미 생성하고 있는 비효율적이고 위험한 셸 패턴을 확인하려면 `failproofai audit`을 실행하세요 — [로컬 에이전트 기록 감사](/ko/audits/local-audit)를 참고하세요.
