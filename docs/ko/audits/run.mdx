감사의 목표와 대상 범위가 충분히 구체화되어 다른 운영자도 유효한 finding이 어떤 것인지 알 수 있을 때 감사를 실행하세요.

## 실행 및 검사

<Tabs>
  <Tab title="대시보드">
    1. **Analyze → Audits**로 이동하여 감사를 열고 **run now**를 선택합니다. 대기 중(queued) 응답은 디스패처가 곧 시작할 것임을 의미합니다.
    2. 새 실행을 열어 상태, 윈도우, 소요 시간, finding 수, 보고서를 검토합니다.
    3. 증거 세션을 선택하면 정확한 추적 내용을 확인할 수 있습니다.
    4. 감사 페이지로 돌아가 설정을 편집하거나, 스케줄을 비활성화하거나, 이전 실행 내역을 검사합니다.

    ![열린 findings, 마지막 및 다음 실행 상태, 스윕 윈도우, 컨텍스트, 즉시 실행 컨트롤, 순위별 findings가 표시된 감사 상세 페이지.](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits run checkout-reliability
    fp audits runs checkout-reliability --limit 10
    fp --json audits runs checkout-reliability
    fp audits findings --audit checkout-reliability
    ```

    `fp audits run`은 감사를 대기열에 추가하며 완료를 기다리지 않습니다. 이후 `fp audits runs <name>`으로 확인하고, 실행이 완료되면 findings를 읽으세요. `--limit`은 요청과 무관하게 최근 50개 실행까지만 반환합니다.

    트리아지는 감사가 아닌 finding ID를 대상으로 작동합니다:

    ```bash
    fp audits finding <finding-id>
    fp audits ack <finding-id> --reason "owner assigned"
    fp audits assign <finding-id> --to engineer@example.com
    fp audits mute <finding-id> --reason "expected in staging" --yes
    fp audits dismiss <finding-id> --reason "false positive" --yes
    fp audits resolve <finding-id> --yes
    fp audits reopen <finding-id>
    ```

    `mute`, `dismiss`, `resolve`는 실행 전에 확인을 요청하므로, 스크립트에서는 `--yes`를 전달하세요. `ack`, `assign`, `reopen`은 즉시 실행됩니다.

    실행 이력, findings, 트리아지 명령어는 [`fp audits` 레퍼런스](/ko/reference/cloud-cli#audits)를 참조하세요.
  </Tab>
</Tabs>

**run now**는 거부될 수 있습니다. 이미 진행 중인 실행이 있거나 비활성화된 감사는 모두 `409`로 응답하며, 이유는 응답의 `error` 필드에 담깁니다. 존재하지 않거나 다른 조직에 속한 감사는 `404`로 응답합니다.

| 거부 사유 | 의미 | 조치 방법 |
| --- | --- | --- |
| 알 수 없는 감사 | 감사가 존재하지 않거나 다른 조직에 속해 있습니다. | `fp audits list`로 이름을 확인하세요. |
| 감사가 비활성화됨 | 비활성화된 감사는 대기열 항목이 없으므로 실행 대상이 없습니다. 일시 중지된 감사는 **run now** 컨트롤을 계속 표시합니다. | 먼저 재개하거나 `fp audits edit <name> --enabled --yes`를 사용하세요. |
| 이미 실행 중인 run이 있음 | 감사당 한 번에 하나의 실행만 가능합니다. 현재 실행이 완료되어야 다음 실행을 대기열에 추가할 수 있습니다. | `fp audits runs <name>`으로 확인하세요. |

## 실행 전 확인 사항

- 선택한 시간 윈도우에 세션이 존재하는지 확인합니다.
- 환경 및 에이전트 필터를 검토합니다.
- 참조 컨텍스트가 최신 상태인지 확인합니다. 매 실행마다 감사의 페이지를 다시 읽고, 접근할 수 없는 경우 저장된 복사본을 사용합니다. 이동되거나 삭제된 페이지는 URL을 수정하기 전까지 오래된 텍스트를 계속 제공합니다.
- 목표가 원하는 결론이 아닌 장애 모드를 설명하는지 확인합니다.

## 실행 결과 검토

감사 상세 페이지에는 다섯 개의 타일이 표시됩니다: 트리아지 대기 중인 **open findings**, **last run**, **next run**, **window**(각 실행이 얼마나 과거까지 읽는지), **sensitivity**(실행이 패턴을 얼마나 적극적으로 플래그하는지: `low`, `medium`, `high`). 실행당 최대 N개 findings 상한은 별도 설정인 findings per run(`--top-k`, 기본값 50)입니다. 이 다섯 가지 타일은 실행을 직접 열어보는 것보다 빠르게 커버리지 질문에 답합니다.

다음으로 각 finding의 심각도, 설명, 증거 세션, 지원 쿼리, 제안된 예방 경로를 검사합니다. Findings는 0과 1 사이의 **priority** 점수로 정렬되고, 실행별로 순위가 매겨지며, 각 finding에는 이를 뒷받침하는 네 가지 가중 요소가 표시됩니다:

| 순위 요소 | 가중치 |
| --- | --- |
| Coverage | 0.30 |
| Magnitude | 0.25 |
| Severity | 0.25 |
| Recency | 0.20 |

Finding은 `open`, `recurring`, `resolved`, `dismissed`, `muted` 다섯 가지 상태 중 하나에 속합니다. 상태 필터 없는 `findings` 쿼리는 현재 활성 집합인 `open`과 `recurring`을 반환합니다. Mute, dismiss, resolve한 finding은 해당 집합에서 제거됩니다. `ack`와 `assign`은 상태를 변경하지 않으므로 finding은 대기열에 남아 있으며, 우선순위가 낮아지거나 담당자가 지정될 뿐 사라지지 않습니다. 제거된 finding을 보려면 상태를 명시적으로 지정하세요.

Finding 상태를 활용하여 승인, 무음, 기각, 해결, 재개, 작업 할당을 수행하세요. Finding이 기각된 경우에도 증거는 보존합니다. 이는 해당 결정이 내려진 이유를 설명합니다. 각 동사가 이후 실행에 미치는 영향은 [Findings and issues](/ko/audits/findings-and-issues)를 참조하세요.

## 빈 결과 또는 지연된 실행 해석

| 실행 상태 | 의미 | 조치 방법 |
| --- | --- | --- |
| 분석이 실행되었으나 findings가 없음 | 선택된 증거가 설정된 sensitivity에서 finding을 지지하지 않습니다. | 범위에 대표적인 세션이 포함되어 있는지 확인한 후, 목표나 컨텍스트가 너무 모호하지 않다면 정상으로 처리합니다. |
| 모델 분석이 건너뛰어지거나 실패함 | 실행은 findings 없이 완료되지만 에이전틱 조사를 수행하지 않은 것입니다. 결정론적 자격증명 및 PII 스캔은 여전히 실행 통계에 일치 수를 보고하지만 findings를 생성하지는 않습니다. | 분석 서비스 또는 구성을 수정하고 재실행합니다. 빈 결과를 대상 집단이 정상이라는 증거로 해석하지 마세요. |
| 모델 분석이 비활성화됨 | 실행은 findings 없이 성공합니다. 결정론적 스캔은 모델 분석을 대체하거나 findings를 생성하지 않습니다. | findings를 생성할 수 없는 감사에 의존하기보다는 모델 분석을 활성화하거나 감사를 비활성화하세요. |
| 분석 용량을 즉시 사용할 수 없음 | 감사는 대상 집단을 건너뛰는 대신 대기 상태를 유지하고 재시도합니다. | 용량이 확보될 때까지 기다리거나 감사 앵커를 분산시킵니다. 자체 호스팅 운영자는 audit-agent 복제본과 이에 맞는 디스패처 용량을 확장해야 합니다. |
| 재시도 윈도우 동안 용량을 사용할 수 없는 상태 지속 | 실행은 findings 없이 포기하고, 이메일 전송이 가능한 경우 실패 알림을 전송합니다. | 감사 플릿이 포화 상태이거나 반복적으로 재시작되는지 확인합니다. |

마지막 세 행은 Cloud API 서버와 디스패처의 동작을 설명합니다. 관리형 Cloud에서는 Failproof AI가 처리할 사항이며, 자체 호스팅 배포에서는 운영자가 처리해야 합니다.

분석이 실행되지 않은 경우, `since_last` 감사는 해당 분석되지 않은 윈도우를 다음 성공적인 실행을 위해 열어둡니다. 건너뛴 분석은 장애가 사라졌다는 증거가 아니므로 기존 findings는 종료되지 않습니다.

## 알림 이해

성공적인 실행은 **새로운** 내용을 발견했을 때만 알림을 보냅니다. 정상적인 감사의 침묵은 아무것도 실행되지 않았다는 신호가 아니라 정상적인 경우입니다. 실행 여부를 확인하려면 감사 페이지의 **last run**이나 `fp audits runs <name>`을 확인하세요. 채널이 선택되지 않은 감사는 findings를 저장하지만 아무에게도 알리지 않습니다.

실패한 실행이나 모델 분석 단계 실패는 감사의 이메일 수신자를 사용합니다. 감사에 이메일 채널이 없는 경우, Failproof AI는 조직의 `alerts.email_default_recipients` 설정으로 폴백하여 자동으로 중단된 감사도 에스컬레이션 경로를 유지합니다.

이메일은 조직에서 활성화되어 있어야 하며 SMTP가 구성되어 있어야 합니다. 그렇지 않으면 실패가 로그에 기록되지만 이메일이 전송되지 않습니다. 실행 실패는 감사의 고정 스케줄 앵커를 이동시키지 않습니다.

모든 실행은 각 에이전트에 사용된 정확한 [에이전트 컨텍스트](/ko/audits/agent-contracts)도 계약 스냅샷으로 저장합니다. 이후 편집은 이전 실행에 기록된 증거 기준을 변경하지 않습니다.

<Warning>
  검증되지 않은 finding에서 직접 차단 정책을 배포하지 마세요. 인용된 추적 내용을 열어 해당 규칙이 안전하지 않은 동작과 정상적인 작업을 구분하는지 확인하세요.
</Warning>
