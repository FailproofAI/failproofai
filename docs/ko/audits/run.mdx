감사의 목표와 대상 범위가 충분히 구체적으로 정의되어, 다른 운영자가 유효한 발견 사항이 어떤 모습인지 알 수 있을 때 감사를 실행하세요.

## 실행 및 검토

<Tabs>
  <Tab title="대시보드">
    1. **Analyze → Audits**로 이동하여 감사를 열고 **run now**를 선택합니다. 대기 중 응답은 디스패처가 곧 시작할 것임을 의미합니다.
    2. 새 실행을 열어 상태, 기간(window), 소요 시간, 발견 수, 보고서를 검토합니다.
    3. 증거 세션을 선택하여 정확한 추적 내용을 확인합니다.
    4. 감사 페이지로 돌아가 설정을 편집하거나, 스케줄을 비활성화하거나, 이전 실행 내역을 검토합니다.

    ![열린 발견 사항, 마지막 및 다음 실행 상태, 스윕 기간, 컨텍스트, 즉시 실행 컨트롤, 순위가 매겨진 발견 사항이 포함된 감사 상세 페이지.](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits run checkout-reliability
    fp audits runs checkout-reliability --limit 10
    fp --json audits runs checkout-reliability
    fp audits findings --audit checkout-reliability
    ```

    실행 기록, 발견 사항, 트리아지 명령어는 [`fp audits` 레퍼런스](/ko/reference/cloud-cli#audits)를 참조하세요.
  </Tab>
</Tabs>

## 실행 전 확인 사항

- 선택한 시간 범위 내에 세션이 존재하는지 확인합니다.
- 환경 및 에이전트 필터를 검증합니다.
- 참조 컨텍스트가 최신 상태인지 확인합니다.
- 목표가 원하는 결론이 아닌 장애 모드를 설명하고 있는지 확인합니다.

## 실행 결과 검토

실행 상태, 세션 적용 범위, 모델 분석 실행 여부부터 시작하세요. 그런 다음 각 발견 사항의 심각도, 설명, 증거 세션, 뒷받침하는 쿼리, 권장 예방 경로를 검토합니다.

발견 상태를 사용하여 인지, 음소거, 기각, 해결, 재개, 또는 작업 할당을 수행합니다. 발견 사항이 기각된 경우에도 증거는 보존하세요. 해당 결정이 내려진 이유를 설명하기 때문입니다.

## 빈 결과 또는 지연된 실행 해석

| 실행 상태 | 의미 | 조치 방법 |
| --- | --- | --- |
| 분석이 실행되었으나 발견 사항 없음 | 선택된 증거가 설정된 민감도 수준에서 발견 사항을 지지하지 않았습니다. | 범위에 대표적인 세션이 포함되어 있는지 확인한 후, 목표나 컨텍스트가 너무 모호하지 않은 한 정상 결과로 처리합니다. |
| 모델 분석이 건너뛰어지거나 실패함 | 실행은 발견 사항 없이 완료되지만, 에이전트 방식의 조사는 수행되지 않았습니다. 결정론적 자격증명 및 PII 스캔은 여전히 실행 통계에 일치 수를 보고하지만 발견 사항을 생성하지는 않습니다. | 분석 서비스 또는 구성을 수정하고 재실행합니다. 빈 결과를 대상 집단이 정상이라는 증거로 해석하지 마세요. |
| 모델 분석이 비활성화됨 | 실행은 발견 사항 없이 성공합니다. 결정론적 스캔은 모델 분석을 대체하거나 발견 사항을 생성하지 않습니다. | 발견 사항을 생성할 수 없는 감사에 의존하기보다는 모델 분석을 활성화하거나 감사를 비활성화하세요. |
| 분석 처리 용량이 즉시 확보되지 않음 | 감사는 대상 집단을 건너뛰지 않고 대기 상태로 유지되며 재시도합니다. | 처리 용량이 확보될 때까지 대기하거나 감사 앵커를 분산시킵니다. 자체 호스팅 운영자는 감사 에이전트 레플리카와 이에 매핑된 디스패처 용량을 확장해야 합니다. |
| 재시도 기간 동안 처리 용량이 확보되지 않음 | 실행이 발견 사항 없이 종료되며, 이메일 전송이 가능한 경우 실패 알림을 발송합니다. | 감사 플릿이 포화 상태인지 또는 반복적으로 재시작되고 있는지 확인하세요. |

분석이 실행되지 않은 경우, `since_last` 감사는 다음 성공적인 실행을 위해 분석되지 않은 해당 기간을 열어둡니다. 분석을 건너뛴 것은 장애가 사라졌다는 증거가 아니므로 기존 발견 사항은 종료되지 않습니다.

## 실패 알림 이해

실행 실패 또는 모델 분석 단계 실패 시 감사에 설정된 이메일 수신자를 사용합니다. 감사에 이메일 채널이 없는 경우, Failproof AI는 조직의 `alerts.email_default_recipients` 설정으로 폴백하여 자동으로 감지되지 않은 감사 오류도 에스컬레이션 경로를 가질 수 있도록 합니다.

이메일은 조직에 대해 활성화되어 있어야 하며 SMTP가 구성되어 있어야 합니다. 그렇지 않으면 실패가 로그에 기록되지만 이메일은 전송되지 않습니다. 실행 실패는 감사의 고정 스케줄 앵커를 변경하지 않습니다.

모든 실행은 각 에이전트에 사용된 정확한 [에이전트 컨텍스트](/ko/audits/agent-contracts)도 계약 스냅샷으로 저장합니다. 이후 편집이 이전 실행에 기록된 증거 기준을 변경하지 않습니다.

<Warning>
  검증되지 않은 발견 사항에서 직접 차단 정책을 배포하지 마세요. 인용된 추적 내용을 열어 해당 규칙이 안전하지 않은 동작과 정당한 작업을 올바르게 구분하는지 확인하세요.
</Warning>
