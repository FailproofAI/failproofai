감사의 품질은 범위 설정에서 시작됩니다. "문제를 찾아라"와 같은 광범위한 요청보다 구체적인 실패 질문이 훨씬 유용한 결과를 만들어냅니다.

## 감사 구성

<Tabs>
  <Tab title="대시보드">
    1. **Analyze → Audits → New audit**으로 이동하여 이름과 설명을 입력합니다. 이름은 조직 내에서 고유하며, 설명에는 이 감사가 무엇을 잡아낼 것으로 기대하는지 기록합니다.
    2. **when it runs**에서 주기와 윈도우를 설정합니다. **what it reads**에서 환경, 에이전트, 무시할 오류 유형으로 대상 범위를 좁힙니다 — 필드가 비어 있으면 모든 항목이 포함됩니다. **how it judges**에서 민감도와 실행당 발견 건수를 설정합니다.
    3. **what it knows**에서 운영자 브리프를 작성하고 감사가 읽을 페이지를 추가합니다. 브리프는 모델이 이벤트를 살펴보기 전에 먼저 읽는 배경 정보로, 이 감사가 이미 찾고 있는 항목에 추가되며 그것을 대체하지 않고 발견 사항의 증거로도 사용되지 않습니다.
    4. **agents** 드로어를 열어 각 에이전트의 컨텍스트를 추가하거나 검토합니다. 이 정보는 감사와 독립적으로 저장되며, 헤더에는 이미 컨텍스트가 있는 에이전트 수가 표시됩니다. [에이전트 컨텍스트](/ko/audits/agent-contracts)를 참조하세요.
    5. 알림 채널을 선택하고 **create audit**을 클릭합니다. 새 감사는 활성화 상태로 시작되며 첫 번째 실행이 즉시 대기열에 추가됩니다.

    ![이름, 설명, 주기, 윈도우, 환경 및 에이전트 범위, 무시할 오류, 분석 설정, 브리프, 참조 페이지, 알림 채널이 포함된 새 감사 양식.](/images/dashboard/audit-new.png)

    **what it reads** 카드의 **agents**는 범위 필터입니다 — 각 실행이 스캔할 세션을 결정합니다. 에이전트가 *무엇을 위한 것인지*는 별도의 에이전트 드로어에 있습니다.
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits create checkout-reliability \
      --description "Find checkout failures that agents do not recover from" \
      --scope '{"environments":["production"],"agent_ids":["checkout-agent"]}' \
      --schedule-interval-secs 86400 \
      --window-mode since_last \
      --sensitivity medium \
      --text-file ./checkout-audit-brief.txt \
      --url https://runbooks.example.com/checkout
    ```

    이름을 제외한 모든 필드에는 서버 기본값이 있으므로 `fp audits create nightly`만으로도 유효한 일별 감사가 됩니다. 이미 사용 중인 이름은 무언가가 생성되기 전에 미리 거부됩니다. 새 감사는 `--disabled`를 전달하지 않는 한 활성화 상태로 시작되며, 활성화된 감사의 첫 번째 실행은 즉시 대기열에 추가됩니다.

    `--file audit.json`으로 저장된 JSON을 기반으로 정의를 만들고 그 위에 플래그를 추가할 수 있습니다. 감사 정의를 검토하거나 버전 관리로 유지할 때 재현 가능한 방법입니다.

    전체 [`fp audits create` 참조](/ko/reference/cloud-cli#audits)를 확인하세요.
  </Tab>
</Tabs>

## 범위 및 기본값

숫자 설정은 양쪽에서 유효성이 검사되므로 범위를 벗어난 값은 요청 거부가 아닌 사용 오류로 처리됩니다.

| 설정 | CLI 플래그 | 허용 값 | 기본값 |
| --- | --- | --- | --- |
| 주기 | `--schedule-interval-secs` | 3600–604800 (1시간~7일) | 86400 (매일) |
| 스케줄 앵커 | `--schedule-anchor` | ISO 8601 UTC; 365일 이후의 앵커는 거부됨 | 다음 09:00 UTC |
| 윈도우 | `--window-mode` | `fixed`, `since_last` | `since_last` |
| 되돌아보기 | `--lookback-window-secs` | 3600–7776000 (1시간~90일) | 604800 (7일) |
| 민감도 | `--sensitivity` | `low`, `medium`, `high` | `medium` |
| 실행당 발견 건수 | `--top-k` | 1 이상 | 50 |

앵커는 스케줄의 위상을 고정합니다. 실행은 `anchor + N * interval`에 맞춰 이루어지므로 실행이 느려지거나 수동으로 **run now**를 실행해도 주기가 어긋나지 않습니다. 첫 번째 실행은 앵커와 관계없이 생성 즉시 대기열에 추가됩니다.

## 브리프 및 참조 페이지

양식에는 두 제한 값이 카운터로 표시되며, CLI도 동일한 두 가지를 적용합니다.

- 브리프는 최대 8,192자입니다 (`--text` 또는 `--text-file`로 파일에서 읽을 수 있으며 — 둘 중 하나만 사용합니다).
- 감사는 최대 다섯 개의 페이지를 참조하며, 공개 `https://` URL만 허용됩니다 (`--url`, 반복 사용 가능).

참조 URL은 저장 시 유효성이 검사됩니다. 비공개, 루프백, 클라우드 메타데이터 주소는 거부되며, 거부된 URL이 있으면 전체 생성이 실패합니다 — 불완전한 감사는 남지 않습니다. 수락된 페이지는 백그라운드에서 가져오므로 응답이 느린 사이트가 저장을 차단하지 않습니다. 모든 실행에서 페이지를 다시 읽으며, 페이지에 접근할 수 없을 경우 저장된 스냅샷으로 대체합니다. 스냅샷은 매주 자동으로 갱신됩니다. 페이지가 변경되어 다음 실행 전에 반영하고 싶을 때는 `fp audits context-refresh <name>`을 사용하세요.

생성 요청 시 브리프와 URL을 함께 전달하세요. 두 번째 호출에서 따로 설정하지 않습니다. 새로 활성화된 감사는 행이 커밋되는 즉시 실행 대기가 되므로, 나중에 작성된 컨텍스트는 디스패처에 의해 선점될 수 있어 첫 번째 실행 — 바로 지금 보고 있는 실행 — 에 반영되지 않을 수 있습니다. 나중에 변경할 때는 `fp audits context-set <name>`을 사용하세요. 이 명령은 지정한 부분만 교체하고 나머지는 그대로 둡니다.

<Tip>
  알려진 실패 세션 하나와 정상 세션 여러 개로 시작하세요. 이렇게 하면 감사에 긍정적인 예시와 비교 세트를 모두 제공할 수 있습니다.
</Tip>

<Info>
  감사 컨텍스트는 별도의 리소스로 저장됩니다. 정의 엔드포인트는 업데이트 시 컨텍스트를 쓰는 것을 거부하므로, 감사에 대한 일반적인 무관한 수정이 브리프나 참조 페이지를 덮어쓸 수 없습니다.
</Info>
