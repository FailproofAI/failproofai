호스팅된 Python 평가는 개수를 세고 비교할 수 있습니다. 도구 호출 횟수, 오류 횟수, 세션 소요 시간 등이 그 예입니다. 하지만 답변이 *정확한지*, 답변 어조가 무례했는지, 에이전트가 행동하기 전에 정책을 확인했는지는 판단할 수 없습니다.

**LLM 심사자**는 이런 것들을 판단할 수 있습니다. 좋은 답변이 어떤 모습인지 평문으로 설명하면, 모델이 세션을 읽고 근거와 함께 0에서 1 사이의 점수를 반환합니다.

<Note>
심사자는 실행하는 세션마다 모델 호출 비용이 발생하지만, 코드 평가는 무료입니다. 대화 내용을 *이해*해야 답할 수 있는 질문에만 심사자를 사용하고, 조건을 설정하여 실제로 관련 있는 세션에서만 실행되도록 하세요.
</Note>

## 어떤 것을 선택해야 할까요?

| 질문 | 사용 방법 |
| --- | --- |
| 같은 도구를 두 번 호출했나요? | 코드 |
| 오류가 몇 번 발생했나요? | 코드 |
| 세션이 30초 이내였나요? | 코드 |
| 고객이 긴급함을 표현했나요? | [결정 모델](/ko/evaluations/jev) |
| 고객이 얼마나 불만스러워했나요? | [결정 모델](/ko/evaluations/jev) |
| 답변이 실제로 정확했나요? | **심사자** |
| 답변이 무례하거나 무시하는 태도였나요? | **심사자** |
| 환불을 약속하기 전에 환불 정책을 확인했나요? | **심사자** |

판단 기준: **셀 수 있는 것 → 코드, 미리 나열할 수 있는 답변 → [결정 모델](/ko/evaluations/jev), 설명이 필요한 것 → 심사자.** 심사자는 본 것을 산문으로 작성하는 평가 방식입니다. 숫자만으로는 "왜?"라는 질문이 생길 때 심사자를 사용하세요.

미리 결정할 필요는 없습니다. 무엇을 측정하고 싶은지 설명하면 failproof가 선택하고, 어떤 방식을 선택했는지와 그 이유를 알려줍니다. **점수 방식** 항목에서 변경할 수도 있습니다.

## 심사자 만들기

1. **분석 → 검사 → 새 평가**로 이동하여 **점수 방식**에서 **LLM 심사자**를 선택합니다.
2. 판단할 내용을 설명합니다.
3. **검토** 화면에서 기준(**심사자가 확인할 사항**), 임계값(**이 점수 이상이면 통과**), **조건**을 확인한 후 배포합니다.

### 기준

질문 형식보다는 요구 사항 형식으로 한두 문장을 작성합니다.

> 어시스턴트는 환불 정책을 먼저 확인하지 않고 환불을 약속하거나 승인해서는 안 됩니다.

무엇이 *실패*로 이어지는지 구체적으로 작성하세요. "응답이 좋았나요?"는 아무 의미 없는 숫자를 줍니다. 위 문장처럼 쓰면 실행 가능한 의미 있는 숫자를 얻을 수 있습니다.

### 임계값

이 점수 이상이면 세션이 통과됩니다. `0.7`이 합리적인 시작점입니다. 0에서 1 사이의 전체 점수는 항상 저장되므로 임계값은 통과/실패만 결정합니다. 분포를 확인하고 조정할 수 있습니다.

### 조건

다른 평가와 동일한 Python 조건이며, 여기서는 훨씬 더 중요합니다. 조건이 없으면 심사자는 조직의 **모든** 세션에서 실행되며 세션마다 모델 호출 비용이 발생합니다.

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

조건 없이 심사자를 배포하면 대시보드에서 경고를 표시합니다. 소량의 트래픽을 처리하는 에이전트를 전부 심사하려는 경우처럼 의도적인 선택일 수 있지만, 실수가 아닌 의식적인 결정이어야 합니다.

## 심사자가 보는 것

대화 내용이 턴 단위로 제공되며, 세션이 긴 경우 최신 순으로 표시됩니다.

- 사용자가 한 말
- 어시스턴트의 답변
- **에이전트가 호출한 모든 도구와 해당 호출의 반환값(순서대로)**

마지막 항목 덕분에 "X를 하기 *전에* Y를 했는지"를 묻는 것이 공정한 질문이 됩니다. 실패한 도구 호출은 실패로 표시되므로 "오류에서 적절히 복구했는지"도 확인할 수 있습니다.

매우 긴 세션은 모델의 컨텍스트에 맞게 잘립니다. 이런 경우 근거에 명시적으로 표시되므로, 일부 세션만 보고 전체 세션을 판단한 것처럼 보이는 일은 절대 없습니다.

## 결과 읽기

심사자는 다른 점수 평가와 마찬가지로 **점수**를 생성하므로, 차트화, 필터링, 알림 트리거가 동일하게 작동합니다. 숫자와 함께 심사자의 **근거**도 저장됩니다. 이는 심사자가 본 것을 설명하는 단락입니다. 점수가 의외일 때는 근거를 먼저 읽으세요. 대개 정말 흥미로운 세션이거나 기준을 다듬어야 한다는 신호입니다.

명확한 사례에서는 점수가 안정적이지만, 비트 단위로 결정론적이지는 않습니다. 경계선상의 단일 점수는 최종 판결이 아닌, 세션을 직접 읽어보라는 신호로 받아들이세요.

## 제한 사항

- **테스트는 아직 지원되지 않습니다.** 드라이 런에는 세션 할당이 없으며, 그 할당이 모델 예산 사용을 승인합니다. 따라서 테스트 호출이 청구할 대상이 없습니다. 좁은 조건으로 배포하고 처음 몇 가지 결과를 읽어보세요.
- **백필은 모델 예산을 소비합니다.** 코드 평가 백필은 무료이지만, 과거 세션에 심사자를 적용하면 세션마다 모델 호출 비용이 발생합니다. **배포 후 과거 세션 미리보기**를 선택하거나 해당 페이지에서 **과거 세션 점수화**를 선택하세요. 누락된 항목 개수를 세는 것은 무료이며, 확인 후에만 점수화가 시작됩니다. 기간을 좁게 유지하세요.
- **기준을 편집하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로, 하나의 추세선에 혼합되지 않고 별도로 보관됩니다.
- **심사자는 항상 점수를 생성하며**, 지표나 단언은 생성하지 않습니다.

## 예산이 소진되면

심사자는 조직의 모델 예산을 소비합니다. 예산이 소진되면 심사자 평가가 자동으로 실패하는 대신 명확한 이유와 함께 중단되며, **코드 평가는 정상적으로 계속 실행됩니다.** 예산을 충전하면 다음 세션부터 재개됩니다.
