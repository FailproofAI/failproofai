호스팅된 Python 평가는 세어서 비교할 수 있습니다. 도구 호출 횟수, 오류 횟수, 세션 소요 시간 같은 것들이죠. 하지만 답변이 *올바른지*, 답변이 무례했는지, 에이전트가 행동하기 전에 정책을 확인했는지는 알 수 없습니다.

**LLM 심사자**는 그것이 가능합니다. 좋은 결과가 어떤 모습인지 평이한 언어로 설명하면, 모델이 세션을 읽고 0에서 1 사이의 점수와 근거를 반환합니다.

<Note>
심사자는 실행되는 세션마다 모델 호출 비용이 발생하며, 코드 평가는 비용이 들지 않습니다. 대화를 *이해*해야만 답할 수 있는 질문에만 심사자를 사용하세요 — 그리고 조건을 설정하여, 실제로 관련된 세션에서만 실행되도록 하세요.
</Note>

## 어떤 것을 사용해야 할까요?

| 질문 | 사용 |
| --- | --- |
| 같은 도구를 두 번 호출했나요? | code |
| 오류가 몇 번 발생했나요? | code |
| 세션이 30초 이내였나요? | code |
| 고객이 긴박함을 표현했나요? | [분류자](/ko/evaluations/jev) |
| 고객이 얼마나 불만스러워했나요? | [분류자](/ko/evaluations/jev) |
| 답변이 실제로 맞았나요? | **심사자** |
| 답변이 무례하거나 무시하는 투였나요? | **심사자** |
| 환불을 약속하기 전에 환불 정책을 확인했나요? | **심사자** |

기본 원칙은 이렇습니다. **셀 수 있는 것 → code, 미리 목록으로 나열할 수 있는 답변 → [분류자](/ko/evaluations/jev), 설명이 필요한 것 → 심사자.** 심사자는 자신이 본 것에 대해 산문으로 작성하는 유형입니다. 숫자만 봐서는 누군가 "왜?"라고 물을 것 같을 때 사용하세요.

미리 결정할 필요는 없습니다. 측정하고 싶은 것을 설명하면 어시스턴트가 선택하고, 무엇을 선택했는지와 그 이유를 알려줍니다. 변경도 가능합니다.

## 작성 방법

1. **Analyze → eval authoring**으로 이동하여 **new eval**을 선택합니다.
2. 평가하고 싶은 내용을 설명하고 **draft**를 선택합니다.
3. **criteria**, **threshold**, **condition**을 검토한 후 배포합니다.

### Criteria

질문 형식이 아닌 요구사항으로 작성된 한두 문장입니다.

> 어시스턴트는 환불 정책을 먼저 확인하지 않고 환불을 약속하거나 승인해서는 안 됩니다.

어떤 경우에 *실패*하는지를 구체적으로 명시하세요. "응답이 좋았나요?"는 아무 의미 없는 숫자를 줍니다. 위의 문장은 실행 가능한 숫자를 줍니다.

### Threshold

세션이 통과하는 기준이 되는 점수입니다. `0.7`이 합리적인 시작점입니다. 전체 0~1 점수는 항상 저장되므로, threshold는 합격/불합격만 결정합니다 — 분포를 확인하고 조정할 수 있습니다.

### Condition

다른 평가와 동일한 Python 조건이며, 여기서는 훨씬 더 중요합니다. 조건이 없으면 심사자는 조직 내 **모든** 세션에서 실행되며, 세션마다 모델 호출이 발생합니다.

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

조건 없이 심사자를 배포하면 대시보드에서 경고를 표시합니다. 소규모 에이전트의 모든 세션을 완전히 평가하고 싶은 경우처럼 그게 맞을 때도 있지만, 실수가 아닌 의도적인 결정이어야 합니다.

## 심사자가 보는 것

대화를 턴(turn) 단위로 보며, 세션이 길 경우 최신 순으로 표시합니다.

- 사용자가 말한 내용
- 어시스턴트가 답변한 내용
- **에이전트가 호출한 모든 도구와 그 반환값, 순서대로**

마지막 항목 덕분에 "X를 하기 *전에* Y를 했는가"라는 질문이 공정하게 평가될 수 있습니다. 실패한 도구 호출은 실패로 표시되므로 "오류로부터 gracefully하게 복구했는가"도 평가할 수 있습니다.

매우 긴 세션은 모델의 컨텍스트에 맞게 잘립니다. 그런 경우 근거에 명시적으로 표시됩니다 — 전체 세션을 기반으로 한 판단처럼 보이는 부분적 세션에 대한 판단은 절대 표시되지 않습니다.

## 결과 읽기

심사자는 다른 점수 평가와 마찬가지로 **점수**를 생성하므로, 동일한 방식으로 차트에 표시되고, 필터링되고, 알림을 트리거합니다. 숫자와 함께 심사자의 **reasoning** — 무엇을 보았는지 설명하는 단락 — 도 저장됩니다. 점수가 예상과 다를 때는 reasoning을 먼저 읽으세요. 대부분 genuinely 흥미로운 세션이거나 criteria를 더 구체화해야 한다는 신호입니다.

명확한 경우에는 점수가 안정적이지만 비트 단위로 결정적이지는 않습니다. 경계선상의 단일 점수는 최종 판결이 아니라 해당 세션을 직접 읽어보라는 신호로 받아들이세요.

## 제한 사항

- **테스트 기능은 아직 제공되지 않습니다.** 드라이 런에는 세션 할당이 없고, 그 할당이 모델 예산 사용을 승인하는 역할을 합니다 — 따라서 테스트 호출에 청구할 대상이 없습니다. 좁은 조건으로 배포하고 첫 몇 가지 결과를 읽으세요.
- **백필은 제공되지 않습니다.** 수개월치 기록에 대해 코드 평가를 백필하는 것은 무료지만, 심사자로 하면 몇 분 만에 전체 예산을 소진할 수 있습니다.
- **criteria를 수정하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로, 하나의 추세선에 혼합하지 않고 별도로 유지됩니다.
- **심사자는 항상 점수를 생성하며**, metric이나 assertion은 생성하지 않습니다.

## 예산이 소진되면

심사자는 조직의 모델 예산을 소비합니다. 예산이 소진되면 심사자 평가는 조용히 실패하는 대신 명확한 이유와 함께 중단되며, **코드 평가는 정상적으로 계속 실행됩니다.** 예산을 늘리면 다음 세션부터 재개됩니다.
