호스팅된 Python 평가는 계산과 비교를 수행할 수 있습니다. 도구 호출 횟수, 오류 횟수, 세션 소요 시간 같은 것들이죠. 하지만 답변이 *올바른지*, 응답이 무례했는지, 에이전트가 행동하기 전에 정책을 확인했는지는 알 수 없습니다.

**LLM 심판**은 이를 판단할 수 있습니다. 좋은 응답이 어떤 모습인지 평이한 언어로 설명하면, 모델이 세션을 읽고 근거와 함께 0에서 1 사이의 점수를 반환합니다.

<Note>
심판은 실행되는 세션마다 모델 호출 비용이 발생하며, 코드 평가는 비용이 없습니다. 대화를 *이해해야만* 답할 수 있는 질문에만 심판을 사용하세요 — 그리고 조건을 설정하여 실제로 관련 있는 세션에만 실행되도록 하세요.
</Note>

## 어떤 것을 선택해야 할까요?

| 질문 | 사용 |
| --- | --- |
| 같은 도구를 두 번 호출했나요? | 코드 |
| 오류가 몇 번 발생했나요? | 코드 |
| 세션이 30초 미만이었나요? | 코드 |
| 고객이 긴박감을 표현했나요? | [분류기](/ko/evaluations/jev) |
| 고객이 얼마나 답답해했나요? | [분류기](/ko/evaluations/jev) |
| 답변이 실제로 정확했나요? | **심판** |
| 응답이 무례하거나 무시하는 태도였나요? | **심판** |
| 환불을 약속하기 전에 환불 정책을 확인했나요? | **심판** |

경험칙은 이렇습니다: **셀 수 있는 것 → 코드, 미리 목록화할 수 있는 답변 → [분류기](/ko/evaluations/jev), 설명이 필요한 것 → 심판.** 심판은 본 것에 대해 산문으로 서술하는 평가입니다. 숫자만으로는 "왜?"라는 질문이 생길 때 심판을 활용하세요.

미리 결정할 필요는 없습니다. 측정하고 싶은 것을 설명하면 어시스턴트가 선택하고 어떤 것을 선택했는지, 그 이유를 알려줍니다. 나중에 변경할 수도 있습니다.

## 작성 방법

1. **Analyze → eval authoring**으로 이동하여 **new eval**을 선택합니다.
2. 판단하고 싶은 내용을 설명하고 **draft**를 선택합니다.
3. **기준**, **임계값**, **조건**을 검토한 후 배포합니다.

### 기준

질문이 아닌 요건으로 작성된 한두 문장:

> 어시스턴트는 환불 정책을 먼저 확인하지 않고 환불을 약속하거나 승인해서는 안 됩니다.

무엇이 *실패*로 이어지는지 구체적으로 명시하세요. "응답이 좋았나요?"는 아무 의미 없는 숫자를 돌려줍니다. 위의 문장은 실행 가능한 숫자를 제공합니다.

### 임계값

이 점수 이상이면 세션이 통과로 처리됩니다. `0.7`이 합리적인 시작점입니다. 전체 0~1 점수는 항상 저장되므로 임계값은 합격/불합격 여부만 결정합니다. 분포를 확인하고 조정할 수 있습니다.

### 조건

다른 평가와 동일한 Python 조건이며, 여기서는 훨씬 더 중요합니다. 조건 없이 배포하면 심판이 조직 내 **모든** 세션에 대해 실행되며, 세션마다 모델 호출이 발생합니다:

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

조건 없이 심판을 배포하려 하면 대시보드에서 경고를 표시합니다. 소량의 트래픽만 있는 에이전트를 완전히 판단하고 싶을 때는 조건이 없어도 되지만, 의도적인 결정이어야 하며 실수가 되어서는 안 됩니다.

## 심판이 보는 것

대화를 순서대로, 세션이 긴 경우 최신 순서부터 표시합니다:

- 사용자가 말한 내용
- 어시스턴트가 응답한 내용
- **에이전트가 호출한 모든 도구와 그 결과, 순서대로**

마지막 항목이 "X 이전에 Y를 했는지"를 공정하게 질문할 수 있게 해줍니다. 실패한 도구 호출은 실패로 표시되므로 "오류에서 적절히 복구했는지"도 판단할 수 있습니다.

매우 긴 세션은 모델의 컨텍스트에 맞게 잘립니다. 그런 경우 근거에 명시적으로 표시됩니다 — 세션 일부를 기준으로 한 판단이 전체 세션 기준인 것처럼 표시되는 일은 절대 없습니다.

## 결과 읽기

심판은 다른 점수 평가와 마찬가지로 **점수**를 생성하므로 차트, 필터링, 알림 트리거 방식도 동일합니다. 숫자와 함께 심판의 **근거** — 본 것을 설명하는 단락 — 도 저장됩니다. 점수가 의외일 때는 근거를 먼저 읽어보세요. 대개 진정으로 흥미로운 세션이거나 기준을 다듬어야 한다는 신호입니다.

명확한 경우에는 점수가 안정적이지만, 비트 단위로 결정론적이지는 않습니다. 경계선의 점수 하나는 최종 판결이 아니라 세션을 직접 읽어봐야 한다는 신호로 받아들이세요.

## 제한 사항

- **테스트는 아직 지원되지 않습니다.** 드라이 런에는 세션 할당이 없으며, 모델 예산 사용을 승인하는 것이 바로 그 할당이기 때문에 테스트 호출이 청구할 대상이 없습니다. 좁은 조건으로 배포하고 첫 번째 결과 몇 개를 읽어보세요.
- **백필은 지원되지 않습니다.** 수개월치 기록에 코드 평가를 백필하는 것은 무료지만, 심판으로 하면 순식간에 전체 예산을 소모하게 됩니다.
- **기준을 편집하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로, 하나의 추세선에 혼합되지 않고 별도로 보관됩니다.
- **심판은 항상 점수를 생성하며**, 메트릭이나 어서션은 생성하지 않습니다.

## 예산이 소진되면

심판은 조직의 모델 예산을 사용합니다. 예산이 소진되면 심판 평가는 자동으로 실패하는 것이 아니라 명확한 이유와 함께 중단되며, **코드 평가는 정상적으로 계속 실행됩니다.** 예산을 늘리면 다음 세션부터 재개됩니다.
