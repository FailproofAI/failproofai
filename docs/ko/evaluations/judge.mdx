호스팅된 Python 평가는 개수를 세고 비교할 수 있습니다. 도구 호출 횟수, 오류 횟수, 세션 소요 시간 같은 것들이죠. 하지만 답변이 *정확한지*, 답변이 무례했는지, 에이전트가 행동하기 전에 정책을 확인했는지는 판단할 수 없습니다.

**LLM 심사자**는 그 판단을 내릴 수 있습니다. 좋은 응답이 무엇인지 평문으로 설명하면, 모델이 세션을 읽고 근거와 함께 0에서 1 사이의 점수를 반환합니다.

<Note>
심사자는 실행하는 세션마다 모델 호출을 한 번씩 소비하지만, 코드 평가는 비용이 들지 않습니다. 심사자는 대화를 *이해해야만* 답할 수 있는 질문에만 사용하세요. 그리고 조건을 설정해 실제로 해당 질문이 의미 있는 세션에서만 실행되도록 하세요.
</Note>

## 어떤 방법을 선택해야 할까요?

| 질문 | 사용 방법 |
| --- | --- |
| 동일한 도구를 두 번 호출했나요? | 코드 |
| 오류가 몇 번 발생했나요? | 코드 |
| 세션이 30초 미만이었나요? | 코드 |
| 고객이 긴박함을 표현했나요? | [분류자](/ko/evaluations/jev) |
| 고객이 얼마나 불만스러워했나요? | [분류자](/ko/evaluations/jev) |
| 답변이 실제로 정확했나요? | **심사자** |
| 답변이 무례하거나 무성의했나요? | **심사자** |
| 환불을 약속하기 전에 환불 정책을 확인했나요? | **심사자** |

기본 원칙은 이렇습니다. **셀 수 있는 것 → 코드, 미리 목록화할 수 있는 답변 → [분류자](/ko/evaluations/jev), 설명이 필요한 것 → 심사자.** 심사자는 자신이 본 것을 문장으로 서술합니다. 숫자만으로는 "왜?"라는 질문이 생길 것 같을 때 심사자를 활용하세요.

미리 결정할 필요는 없습니다. 측정하고 싶은 것을 설명하면 어시스턴트가 선택하고, 어떤 것을 왜 선택했는지 알려줍니다. 나중에 변경할 수도 있습니다.

## 심사자 작성하기

1. **Analyze → eval authoring** 으로 이동해 **new eval** 을 선택합니다.
2. 판단받고 싶은 내용을 설명하고 **draft** 를 선택합니다.
3. **criteria**, **threshold**, **condition** 을 검토한 후 배포합니다.

### Criteria

질문 형식이 아닌 요구사항으로 작성한 한두 문장:

> 어시스턴트는 환불 정책을 먼저 확인하지 않고 환불을 약속하거나 승인해서는 안 됩니다.

무엇이 *실패*로 이어지는지 구체적으로 명시하세요. "응답이 좋았나요?"는 아무 의미 없는 숫자를 반환하지만, 위 문장은 실질적인 행동으로 이어질 수 있는 숫자를 반환합니다.

### Threshold

세션이 통과하는 기준이 되는 점수입니다. `0.7`이 합리적인 출발점입니다. 0에서 1 사이의 전체 점수는 항상 저장되므로, threshold는 합격/불합격만 결정합니다. 분포를 확인하고 조정할 수 있습니다.

### Condition

다른 평가와 동일한 Python 조건식이며, 여기서는 훨씬 더 중요합니다. 조건이 없으면 심사자가 조직의 **모든** 세션에 대해 실행되며, 세션마다 모델 호출이 발생합니다.

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

조건 없이 심사자를 배포하려 하면 대시보드에서 경고를 표시합니다. 완전한 심사가 필요한 소규모 에이전트라면 그렇게 해도 괜찮지만, 의도적인 선택이어야지 실수여서는 안 됩니다.

## 심사자가 보는 것

대화 내용을 턴 단위로, 세션이 길 경우 최신 순으로 정렬하여 제공합니다.

- 사용자가 한 말
- 어시스턴트의 답변
- **에이전트가 호출한 모든 도구와 각 호출의 반환값 (순서대로)**

마지막 항목이 있기 때문에 "X를 Y보다 *먼저* 했는가"라는 질문이 공정하게 평가될 수 있습니다. 실패한 도구 호출은 실패로 표시되므로, "오류에서 적절히 복구했는가"도 평가 가능합니다.

매우 긴 세션은 모델의 컨텍스트에 맞게 잘립니다. 그런 경우 근거 설명에 명시적으로 표시됩니다. 일부 세션을 기반으로 내린 판단이 전체 세션을 본 것처럼 표시되는 일은 절대 없습니다.

## 결과 읽기

심사자는 다른 점수 평가와 마찬가지로 **점수**를 생성하므로, 차트화, 필터링, 알림 트리거가 동일하게 작동합니다. 숫자와 함께 심사자의 **reasoning** — 본 내용을 설명하는 문단 — 도 저장됩니다. 점수가 의외일 때는 근거를 먼저 읽어보세요. 대부분 흥미로운 세션이거나, criteria를 더 구체화해야 한다는 신호입니다.

명확한 케이스의 점수는 안정적이지만 완전히 결정론적이지는 않습니다. 경계선상의 단일 점수는 최종 판결이 아니라 세션을 직접 읽어봐야 한다는 신호로 받아들이세요.

## 제한 사항

- **테스트는 아직 지원되지 않습니다.** 드라이 런에는 세션 할당이 없고, 그 할당이 모델 예산 사용을 승인하는 역할을 합니다. 따라서 테스트 호출에 청구할 대상이 없습니다. 좁은 조건으로 배포하고 첫 번째 결과 몇 개를 직접 확인하세요.
- **백필은 지원되지 않습니다.** 코드 평가는 수개월치 이력을 무료로 백필할 수 있지만, 심사자로 이를 수행하면 몇 분 만에 전체 예산이 소진됩니다.
- **criteria를 수정하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로 하나의 추이 그래프에 혼합하지 않고 별도로 보관됩니다.
- **심사자는 항상 점수를 생성합니다.** 메트릭이나 어서션은 생성하지 않습니다.

## 예산이 소진되면

심사자는 조직의 모델 예산을 소비합니다. 예산이 소진되면 심사자 평가는 조용히 실패하는 대신 명확한 이유와 함께 중단되며, **코드 평가는 정상적으로 계속 실행됩니다.** 예산을 늘리면 다음 세션부터 재개됩니다.
