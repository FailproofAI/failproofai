호스팅된 Python 평가는 개수를 세고 비교할 수 있습니다. 도구 호출 횟수, 오류 횟수, 세션 소요 시간 같은 것들이죠. 하지만 답변이 *정확한지*, 답변이 무례했는지, 에이전트가 행동하기 전에 정책을 확인했는지는 판단할 수 없습니다.

**LLM 심사자**는 이런 것들을 판단할 수 있습니다. 좋은 응답이 무엇인지 일반 언어로 설명하면, 모델이 세션을 읽고 근거와 함께 0에서 1 사이의 점수를 반환합니다.

<Note>
심사자는 실행되는 세션마다 모델 호출 비용이 발생하지만, 코드 평가는 무료입니다. 대화를 *이해해야* 답할 수 있는 질문에만 심사자를 사용하세요. 그리고 조건을 설정해서 실제로 관련 있는 세션에서만 실행되도록 하세요.
</Note>

## 어떤 것을 선택해야 할까요?

| 질문 | 사용 |
| --- | --- |
| 같은 도구를 두 번 호출했나요? | 코드 |
| 오류가 몇 번 발생했나요? | 코드 |
| 세션이 30초 미만이었나요? | 코드 |
| 고객이 긴급함을 표현했나요? | [판단 모델](/ko/evaluations/jev) |
| 고객이 얼마나 불만스러워했나요? | [판단 모델](/ko/evaluations/jev) |
| 답변이 실제로 정확했나요? | **심사자** |
| 답변이 무례하거나 무시하는 태도였나요? | **심사자** |
| 환불을 약속하기 전에 환불 정책을 확인했나요? | **심사자** |

기본 원칙: **셀 수 있는 것 → 코드, 미리 목록화할 수 있는 답변 → [판단 모델](/ko/evaluations/jev), 설명이 필요한 것 → 심사자.** 심사자는 발견한 내용을 산문으로 작성하는 평가 방식입니다. 숫자만 보면 "왜?"라는 질문이 나올 때 사용하세요.

미리 결정하지 않아도 됩니다. 측정하고 싶은 것을 설명하면 failproof가 선택하고 이유를 알려줍니다. **어떻게 점수를 매길까요?** 에서 변경할 수 있습니다.

## 작성하기

1. **분석 → 검사 → 새 평가**로 이동해서 **어떻게 점수를 매길까요?** 아래의 **llm as judge**를 선택합니다.
2. 심사할 내용을 설명합니다.
3. **검토** 단계에서 기준(**심사자가 확인하는 것**), 임계값(**이 값 이상이면 통과**), **조건**을 확인한 후 배포합니다.

### 기준

질문 형식보다는 요구사항 형식으로 한두 문장으로 작성합니다.

> 어시스턴트는 환불 정책을 먼저 확인하지 않고 환불을 약속하거나 승인해서는 안 됩니다.

*실패*하는 경우를 구체적으로 명시하세요. "응답이 좋았나요?"는 아무 의미 없는 숫자를 반환하지만, 위의 문장은 행동으로 이어질 수 있는 숫자를 반환합니다.

### 임계값

이 값 이상이면 세션이 통과됩니다. `0.7`이 적절한 시작점입니다. 0에서 1 사이의 전체 점수는 항상 저장되므로 임계값은 통과/실패만 결정합니다. 분포를 확인하고 조정할 수 있습니다.

### 조건

다른 평가와 동일한 Python 조건이며, 여기서는 훨씬 더 중요합니다. 조건이 없으면 심사자는 조직의 **모든** 세션에서 실행되며, 각 세션마다 모델 호출이 발생합니다.

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

조건 없이 심사자를 배포하려 하면 대시보드에서 경고를 표시합니다. 소량 트래픽을 처리하는 에이전트를 완전히 심사하려는 경우처럼 의도적인 선택일 수도 있지만, 실수가 아닌 의식적인 결정이어야 합니다.

## 심사자가 보는 것

대화 내용이 턴 단위로 제공되며, 세션이 길 경우 최신 순으로 표시됩니다.

- 사용자가 말한 내용
- 어시스턴트가 답변한 내용
- **에이전트가 호출한 모든 도구와 그 호출 결과, 순서대로**

마지막 항목이 있기 때문에 "X를 하기 *전에* Y를 했는지"를 공정하게 물어볼 수 있습니다. 실패한 도구 호출은 실패로 표시되므로 "오류에서 적절히 복구했는지"도 확인할 수 있습니다.

매우 긴 세션은 모델의 컨텍스트에 맞게 잘립니다. 이런 경우 근거에서 명시적으로 표시됩니다. 세션의 일부만 보고 내린 판단이 전체를 본 것처럼 표시되는 일은 절대 없습니다.

## 결과 읽기

심사자는 다른 점수 기반 평가와 동일하게 **점수**를 생성하므로, 차트, 필터, 알림 트리거 방식도 동일합니다. 숫자와 함께 심사자의 **근거**도 저장됩니다. 이 근거는 심사자가 발견한 내용을 설명하는 단락입니다. 점수가 의외일 때는 근거를 먼저 읽어보세요. 대부분 흥미로운 세션이거나 기준을 다듬어야 한다는 신호입니다.

명확한 경우에는 점수가 안정적이지만 비트 단위로 결정론적이지는 않습니다. 경계선상의 단일 점수는 최종 판결이 아니라 세션을 직접 읽어봐야 한다는 신호로 받아들이세요.

## 제한 사항

- **테스트는 아직 지원되지 않습니다.** 드라이 런에는 세션 할당이 없고, 모델 예산 사용을 승인하는 것이 바로 그 할당이기 때문에 테스트 호출에 청구할 대상이 없습니다. 좁은 조건으로 배포한 후 첫 번째 결과 몇 개를 읽어보세요.
- **백필은 모델 예산을 소비합니다.** 코드 평가의 백필은 무료지만, 과거 세션을 심사자로 채점하면 세션마다 모델 호출 비용이 발생합니다. **배포 후 과거 세션 미리보기**를 선택하거나, 해당 페이지에서 **과거 세션 채점**을 선택하세요. 누락된 항목을 세는 것은 무료이며, 확인하기 전까지는 채점되지 않습니다. 기간을 좁게 유지하세요.
- **기준을 편집하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로 하나의 추세선으로 합치지 않고 별도로 보관됩니다.
- **심사자는 항상 점수를 생성하며**, 메트릭이나 어서션은 생성하지 않습니다.

## 예산이 소진되면

심사자는 조직의 모델 예산을 사용합니다. 예산이 소진되면 심사자 평가는 조용히 실패하지 않고 명확한 이유와 함께 중단되며, **코드 평가는 정상적으로 계속 실행됩니다**. 예산을 늘리면 다음 세션부터 재개됩니다.
