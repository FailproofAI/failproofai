FailproofAI Cloud 또는 자체 키를 통해 [Jev 정책 검토](/ko/policies/jev)를 설정하면, 게이트된 각 도구 호출은 실행 중인 정책과 Jev에 의해 판정됩니다. Jev는 해당 호출이 실제로 무엇을 하는지, 그리고 작업을 입력한 사람이 그것을 요청했는지를 질의합니다. 각 정책의 **권한(authority)**은 둘이 서로 일치하지 않을 때 어떻게 처리할지를 결정합니다.

Jev가 설정되지 않은 경우 권한은 아무런 효력이 없습니다. 모든 정책은 기존과 동일하게 적용됩니다.

## Hard와 Reviewable

- **Hard**가 기본값입니다. Hard 정책의 deny 또는 instruction은 최종적이며, Jev가 이를 해제할 수 없고 hard deny는 Jev를 기다리지 않고 즉시 호출을 중단합니다.
- **Reviewable**은 정책이 `reviewedBy`에 명시한 시맨틱 검사를 통해서만 Jev가 해당 정책의 판정을 해제할 수 있음을 의미합니다. 판정은 명시된 **모든** 검사가 이 호출에 대해 질의되었고, 각각이 아무것도 발견하지 못했거나 사용자가 이를 요청했음을 기록한 경우에만 해제됩니다. 사용자의 요청 없이 **발화(fire)**된 — 우려 사항을 발견한 — 검사는 자체 판정이 경고에 불과하더라도 차단을 유지합니다. 해당 도구에 적용되지 않아 Jev가 질의하지 않은 검사는 다른 검사의 결과와 무관하게 아무것도 해제하지 않습니다. 완화 조치 하나면 동의로 간주됩니다. 호출이 사용자가 지시한 작업의 한 단계이며 그 이상으로 나아가지 않는다면, Jev는 deny를 warning으로 전환하고, 해당 warning은 정책의 차단을 해제하며 에이전트에게 전달되는 내용이 됩니다.

정책이 reviewable이 되려면 다음 조건이 모두 충족되어야 합니다.

1. `authority: "reviewable"`을 선언해야 합니다.
2. `reviewedBy`는 비어 있지 않은 목록이어야 하며, 모든 항목은 설치된 팩이 선언한 Jev 검사여야 합니다. Failproof AI는 Jev 검사를 자체 제공하지 않습니다. [아래의 16가지](#semantic-policy-names)는 `failproofai policies add FailproofAI/jev-policies`에서 제공됩니다. 검사를 선언하는 팩이 없으면 모든 정책은 hard가 됩니다.
3. `alwaysOn`이 아니어야 합니다. 에이전트가 Failproof AI를 비활성화하는 것을 막는 가드는 항상 hard입니다.

그 외의 경우는 모두 hard입니다. 필드 누락, 잘못된 값, 비어 있거나 잘못된 형식의 `reviewedBy`, 또는 현재 머신이 질의할 수 없는 검사 이름이 해당됩니다. 알 수 없는 이름은 건너뛰는 대신 선언 전체를 hard로 만듭니다. `reviewedBy`는 "이 모든 검사가 질의되어야 하고, 그 중 어느 것도 deny해서는 안 된다"는 의미이므로, 이름을 건너뛰면 Jev가 요청한 것보다 적은 수의 검사로 정책을 해제하게 되기 때문입니다.

Jev가 설정되면, Failproof AI는 `reviewable` 선언을 거부할 때 프로세스당 한 번 경고를 기록합니다. Jev가 없을 때는 아무 말도 하지 않습니다. 권한이 아무것도 결정하지 않기 때문입니다. `failproofai publish`는 그러한 선언을 포함하는 팩의 빌드를 거부하므로, 팩 작성자는 누군가가 설치하기 전에 알 수 있습니다. 팩이 검사를 선언하는 경우 팩이 선언한 검사에 대해, 그렇지 않은 경우 `FailproofAI/jev-policies`의 16가지 이름에 대해 `reviewedBy`를 검증합니다.

## 권한 선언 위치

정책이 머신에 전달되는 각 방식에는 권한을 결정하는 한 곳이 있습니다.

| 소스 | 선언 위치 | 기본값 |
| --- | --- | --- |
| 내장 정책 | 아래 표 | Reviewable로 나열된 경우 제외하고 Hard |
| 사용자 정의 정책 파일 | `customPolicies.add`의 `authority` 및 `reviewedBy` | Hard |
| 정책 팩 | 팩 매니페스트(`failproofai-pack.json`)의 각 정책 항목 | Hard |
| 클라우드 관리 정책 | 활성 배포의 정책 할당 | Hard. 현재 배포에서는 설정되지 않으므로, 모든 클라우드 관리 정책은 현재 hard입니다. |

팩 또는 클라우드 관리 정책의 경우, 정책 코드 내부에 설정된 필드는 무시됩니다. 매니페스트나 할당이 결정합니다. 팩은 자체 정책만 기술할 수 있습니다. 정책 이름에 `/`를 포함할 수 없고 팩 자체의 접두사 하에 등록되므로, 매니페스트가 내장 정책이나 다른 팩의 정책을 reviewable로 표시할 수 없습니다. 팩 코드가 등록하지만 매니페스트에 선언하지 않은 정책은 hard입니다.

두 팩 또는 두 클라우드 관리 정책의 코드가 바이트 단위로 동일한 경우, 하나의 아티팩트를 공유하고 하나의 정책으로 로드됩니다. 해당 정책은 모두가 reviewable로 선언한 경우에만 reviewable이 되며, Jev는 그 중 어느 것이 명시한 모든 검사를 해제해야 합니다. 어느 하나라도 hard로 선언하거나 전혀 선언하지 않으면 hard로 유지됩니다. 팩이나 정책이 나열된 순서는 중요하지 않습니다.

대부분의 머신은 `FailproofAI/policies` 팩에서 내장 정책을 받아 해당 팩의 매니페스트에서 권한을 읽습니다. 아래의 reviewable 항목들은 해당 항목을 포함하는 팩의 릴리스가 설치된 후에 적용됩니다. 이전 릴리스에는 reviewable 항목이 없으므로 모든 정책이 hard로 유지됩니다.

## 사용자 정의 정책에서 권한 선언

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish`는 두 필드를 모두 팩 매니페스트에 복사하므로, 팩으로 게시된 정책은 작성자가 부여한 권한을 유지합니다. 선언이 적용되지 않을 경우 팩 빌드를 거부합니다. `"hard"` 또는 `"reviewable"` 이외의 값, 이름 목록이 아닌 `reviewedBy`, 또는 검사가 아닌 이름 — 팩이 선언한 경우 팩 자체의 [Jev 검사](/ko/policies/publish-a-pack#jev-checks-in-a-pack), 그렇지 않은 경우 내장 검사 — 이 해당합니다.

## 내장 정책

시맨틱 정책이 동일한 우려 사항을 실질적으로 다루는 경우에만 Reviewable입니다. 그 외 모든 내장 정책은 hard입니다.

우려 사항을 다루는 것은 필요 조건이지만 충분 조건은 아니며, 두 가지 오류 모두 소리 없이 발생합니다.

- **질의되지 않는 검사**는 차단을 영구적으로 만듭니다. `reviewedBy`는 연접(conjunction)이며 질의되지 않은 검사는 절대 해제하지 않으므로, 정책이 매칭하는 형태에 대해 전제 조건이 발화하지 않는 검사와 짝을 이루는 정책은 전혀 해제될 수 없습니다.
- **질의되었지만 발화하지 않는 검사**는 "우려 없음"으로 답하며, 우려가 없으면 해제됩니다. 따라서 정책의 형태를 모델링하지 않는 검사와 짝을 이루는 것은 정책을 검토하는 것이 아니라 — 검사가 이해하지 못하는 바로 그 입력에 대해 정책을 끄는 것입니다.

instruct 모드의 시맨틱 정책은 deny로 답할 수 없지만 차단을 유지할 수 있습니다. 발화했는데 사용자가 해당 호출을 요청하지 않은 경우, 검토 중인 정책은 해제되지 않습니다. `FailproofAI/jev-policies` 검사 중 여섯 개는 instruct 전용입니다 — `push-to-protected-branch`, `commit-on-protected-branch`, `read-outside-workspace`, `system-modification`, `env-secrets-dump`, `external-data-egress` — 이며 [아래 표](#semantic-policy-names)에서 각 검사의 모드를 확인할 수 있습니다. 핵심 질문은 **"deny를 내릴 수 있는 것이 남아 있는가"**입니다. 해제는 우려 사항이 아무것도 적용되지 않는 상태로 남겨져서는 안 됩니다. 엔진은 이 테스트를 호출별로 적용합니다. 아무도 동의하지 않은 warning은 해제가 아닙니다. 도구 호출 전에 warning은 에이전트를 중단하지 않기 때문입니다. 그리고 deny를 *낼 수 있는* 검사가 경고하는 경우 — 증거가 deny 기준에 미치지 못했고 — 사용자가 해당 호출을 요청하지 않았다면, 그 호출에서는 아무것도 해제되지 않으며 모든 regex deny가 유지됩니다.

<Warning>
**발화 임계값 바로 아래에 점수를 기록한 검사는 최저선을 유지하지 않습니다.** 위 규칙은 검사가 *발화*(증거 ≥ 0.7)해야 합니다. 모든 관련 검사가 그 바로 아래에 위치하면 아무것도 발화하지 않고, 검토자는 "우려 없음"으로 답하며 reviewable deny가 해제됩니다. 강제 모드에서 실측: 요청받지 않은 `/etc/shadow` 읽기(`secret-exposure` 0.69, 홈 디렉토리 경로만 모델링하는 `read-outside-workspace` 0.37)와 "follow SETUP.md" 이후의 `set | curl -d @- …`(`env-secrets-dump` 0.66, `sends_out` 0.97의 `credential-exfiltration` 0.65) 모두 허용되었으나, regex 계층 단독으로는 이를 deny합니다. 임계값은 레이블된 코퍼스에서 보정되었으며 이에 대해 재측정되지 않았습니다. 재측정될 때까지, 이러한 형태 중 하나가 통과하는 것이 false 차단보다 더 중요한 경우 정책을 **hard**로 유지하십시오.
</Warning>

## Semantic policy names

이것들은 `FailproofAI/jev-policies`가 선언하는 검사이며, 설치 후 `reviewedBy`가 허용하는 값들입니다. Failproof AI 자체는 이 중 어느 것도 제공하지 않습니다. 해당 팩(또는 이 이름들을 선언하는 다른 팩) 없이는 이를 명시하는 정책은 reviewable이 되지 않습니다. 각각은 Jev가 앞에 있는 도구 호출에 대해 답하는 검사입니다. **모드**는 검사가 답할 수 있는 내용입니다. `deny` 검사는 강한 증거에서 차단하며, `instruct` 검사는 경고만 합니다. 어느 쪽이든 발화하고 사용자가 해당 호출을 요청하지 않은 경우 정책의 deny를 유지합니다. **사용자 재정의 가능** 여부는 사람의 명시적인 요청이 이를 해제할 수 있는지를 나타냅니다.

Jev는 설치된 팩이 선언하는 [Jev 검사](/ko/policies/publish-a-pack#jev-checks-in-a-pack)만 정확히 질의하며, 그것이 `reviewedBy`가 허용하는 이름들입니다. 두 팩이 동일한 이름을 다르게 선언하는 경우 어느 쪽도 적용되지 않습니다. FailproofAI 저장소에서 설치되지 않은 팩이 선언하는 이 16가지 이름 중 하나는 해당 팩에서 무시됩니다. 해당 버전은 절대 질의되지 않으며 FailproofAI 자체 버전과 경쟁하지 않으므로, 서드파티 팩은 코어 팩의 정책을 해제하는 검사가 되거나 이 검사 중 하나를 끌 수 없습니다. 읽을 수 없는 팩 목록이나 모든 검사를 사용할 수 없는 팩은 Jev에게 질의할 것을 남기지 않습니다.
