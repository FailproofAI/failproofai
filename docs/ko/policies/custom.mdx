정책을 작성하기 전에 [내장 카탈로그](/ko/policies/builtin-catalog)를 먼저 확인하세요. 검토된 규칙은 대체로 새로 작성한 것보다 안전합니다.

## 작동하는 정책에서 시작하기

```bash
failproofai publish --init guards.mjs
failproofai policies -i -c ./guards.mjs
```

스타터는 `git push --force`를 차단합니다. 내용을 수정한 뒤 에이전트에게 차단된 작업을 시도하도록 하고, **Policies → Activity**에서 결과를 확인하세요.

```js
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production",
  description: "Production changes need a human",
  match: { events: ["PreToolUse"], toolNames: ["Bash"] },
  fn: async (ctx) =>
    String(ctx.toolInput?.command ?? "").includes("production")
      ? deny("Ask a human before changing production.")
      : allow(),
});
```

정책은 `allow()`, `deny(message)`, 또는 `instruct(message)`를 반환합니다. 작업을 반드시 중단해야 할 때는 `deny`를 사용하세요. 모든 실행 환경에서 에이전트에게 instruction을 전달할 수 있는 것은 아닙니다.

## 자동 로드 설정

`*policies.js`, `*policies.mjs`, 또는 `*policies.ts` 형식의 파일을 다음 경로에 저장하세요:

- `.failproofai/policies/` — 특정 프로젝트에 적용
- `~/.failproofai/policies/` — 현재 사용자에게 적용

## 실패 경로 테스트

안전하지 않은 작업과 그와 유사하게 보이는 정상적인 작업 모두를 테스트하세요. 결정이 다른 규칙이 아닌 작성한 정책에서 내려진 것인지 확인하세요.

명시적인 테스트 파일은 다음 명령으로 제거할 수 있습니다:

```bash
failproofai policies -u -c
```

정책이 준비되면 [팩으로 배포](/ko/policies/publish-a-pack)하거나 [Cloud를 통해 배포](/ko/policies/deploy)하세요.
