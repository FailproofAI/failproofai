배포는 게시된 정책 버전을 머신에 적용하며, 다음 두 가지 효과 중 하나를 가집니다:

- **Observe**는 정책이 수행했을 동작을 기록하며, 아무것도 차단하지 않습니다.
- **Enforce**는 결정에 따라 실제로 동작합니다: `deny`는 호출을 차단하고, `instruct`는 에이전트를 안내합니다.

## 머신 추가

머신이 Cloud에 연결되면 **Admin → enforcement** 아래에 표시됩니다. 원하는 머신이 아직 없는 경우:

<Tabs>
  <Tab title="대시보드">
    1. **Administration → Keys**로 이동하여 `policies:pull`(머신이 배포를 수신할 수 있도록)과 `events:add`(머신의 결정이 Cloud에 전달되도록) 권한을 가진 키를 생성합니다.
    2. 해당 키로 머신을 연결합니다 — [머신을 Cloud에 연결하기](/ko/start/setup#connect-a-machine-to-cloud)에서 자세한 절차를 확인하세요.
    3. **Admin → enforcement** 아래에 머신이 표시되는지 확인합니다.
  </Tab>
  <Tab title="CLI">
    머신에서:

    ```bash
    npm install -g failproofai
    failproofai config
    failproofai config --status
    ```

    터미널에서 `failproofai config`를 실행하면 Cloud 연결 여부를 묻고, 마스킹된 프롬프트에서 키를 입력받습니다. 이후 `fp fleet list`를 실행하여 어디서든 머신이 등록되었는지 확인합니다.
  </Tab>
</Tabs>

## 관찰 모드로 배포

<Tabs>
  <Tab title="대시보드">
    1. **Admin → enforcement**로 이동하여 머신을 찾고 해당 행을 펼칩니다.
    2. **edit**를 선택하고, 테스트된 정책 버전을 추가한 후 **observe**를 선택합니다.
    3. 변경 사항을 적용하고, 머신의 다음 체크인을 기다린 후 배포 및 커버리지 상태를 확인합니다.
    4. **Observe → policy**로 이동하여 실시간 결정을 검토합니다.

    ![정책 버전, enforce 및 observe 효과, 배포 적용 동작이 표시된 머신 배포 편집기.](/images/dashboard/enforcement-editor.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp fleet list
    fp fleet show <machine-id>
    fp fleet deploy <machine-id> --add no-force-push:observe
    ```

    `:observe` 접미사가 관찰 모드로 만드는 요소입니다. 접미사 없이 `--add no-force-push`만 사용하면 해당 정책에 대해 머신이 이미 가진 효과를 유지하며, 그렇지 않으면 enforce 모드로 적용됩니다. 나중에 `--add no-force-push:enforce`로 enforce 모드로 전환할 수 있습니다.

    `deploy`는 **머신의 전체 정책 세트를 결과로 교체**합니다. 계획을 출력한 후 적용 전에 확인을 요청하지만, 인터랙티브 터미널에서만 그렇습니다. `--yes` 플래그 사용 시, `fp --json` 하에서, 또는 stdin이 리디렉션된 경우(CI 단계, 스크립트, 에이전트 셸 실행)에는 확인 없이 적용됩니다. 계획은 여전히 출력되거나 `--json` 사용 시 `plan`으로 반환됩니다.

    머신에서 `failproofai policies`를 실행하면 실행 중인 Cloud 관리 정책이 나열되고, `failproofai config --status`는 연결 상태를 보여줍니다. `fp sessions --env production --since 24h`와 `fp events --event-type hook_completed`를 사용하여 머신의 활동이 Cloud에 전달되는지 확인하세요.
  </Tab>
</Tabs>

<Steps>
  <Step title="버전과 머신 선택">
    게시된 버전과 실행할 머신을 선택합니다.
  </Step>
  <Step title="관찰">
    아무것도 차단되지 않는 상태에서 매칭, 이유, 영향을 받는 도구, 오탐을 검토합니다.
  </Step>
  <Step title="적용">
    관찰된 매칭이 안전하지 않은 동작과 유효한 동작을 구분하면 효과를 enforce로 전환하고, 의도한 모든 머신이 변경 사항을 가져와 결정을 보고하는지 확인합니다.
  </Step>
</Steps>

## 머신의 에이전트 타겟팅

게시된 정책 버전에는 에이전트 라우팅 규칙이 포함되지 않습니다. 기본적으로 할당은
**머신의 모든 에이전트**에 적용됩니다. 버전을 배포할 때 특정 통합(나중에 추가된 프로필 포함)이나
해당 머신이 보고한 특정 프로필을 대상으로 지정할 수 있습니다. 이 선택은 머신의 할당에 속합니다:
동일한 게시된 버전이 서로 다른 머신에서 서로 다른 에이전트를 대상으로 할 수 있습니다.

<Tabs>
  <Tab title="대시보드">
    1. **Admin → enforcement**에서 머신을 펼치고 **edit**를 선택합니다.
    2. 정책의 **agents** 컨트롤에서 **all agents**를 유지하거나, **all hermes profiles**를 선택하거나(예시), 레이블과 `agt_` ID로 보고된 프로필을 검색합니다. 여러 대안을 선택할 수 있으며, 호출이 그 중 하나에 속하면 매칭됩니다.
    3. 배포 계획에서 **각** 할당에 나열된 타겟을 검토하고, 변경 사항을 적용한 후 다음 체크인 이후 머신의 보고된 배포를 확인합니다. 기록과 롤백은 선택된 타겟을 유지합니다.
  </Tab>
  <Tab title="CLI">
    ```bash
    fp fleet show <machine-id>
    fp fleet deploy <machine-id> --add no-force-push --target no-force-push=hermes
    fp fleet deploy <machine-id> --target no-force-push=hermes/agt_1234567890abcdef
    fp fleet deploy <machine-id> --all-agents no-force-push
    ```

    `--target POLICY=INTEGRATION[/agt_ID]`는 하나의 정책 범위를 설정합니다. 동일한 할당에 더 많은 대안을 추가하려면 `--target`을 반복합니다. `--all-agents POLICY`를 사용하여 해당 할당의 타겟팅을 해제합니다. `fp fleet show`와 `fp fleet history`는 선택된 범위를 표시합니다. 특히 스크립트에서 배포할 때는 완전한 교체 계획을 적용 전에 검토하세요.
  </Tab>
</Tabs>

새 타겟을 설정하려면 머신이 최근에 에이전트 타겟팅 지원을 보고했어야 합니다. 특정 프로필을 선택하려면 해당 머신이 훅이 설치된 상태로 프로필을 보고했고 오래되지 않은 경우에만 가능합니다. 인벤토리가 일시적으로 사용 불가능한 경우 기존 타겟은 그대로 할당됩니다; 모든 에이전트로 자동 확장되지 않습니다. 새 설치에서 사용하는 프로필 힌트를 제공하려면 이전 셸 훅을 재설치하세요. CLI 업그레이드 후에는 `failproofai config`를 실행하여 데몬도 업데이트하고 재시작하세요: 이전 데몬은 새 프로필 범위 호출을 평가할 수 없고 훅은 불일치를 거부합니다.
실행 중인 에이전트의 프로필을 식별할 수 없는 경우(예: 여러 설정 범위가 설치되었지만 훅이 어떤 것이 실행되었는지 보고하지 않는 경우) **타겟 할당이 매칭되지 않습니다**; 범위가 지정되지 않은 정책은 계속 적용됩니다. 해당 머신의 정책 오류에서 `agent_scope_unresolved`를 확인하세요.

머신은 추적하는 에이전트만 보고합니다: FailproofAI 훅이 설정 파일에 포함된 각 프로필마다 하나의 항목(Hermes와 OpenClaw는 레이블로 명명된 프로필당 하나씩)이 있습니다. 단순히 설치만 된 에이전트 CLI는 나열되지 않습니다.

각 머신은 로스터에 최대 256개의 프로필을 유지합니다. 프로필의 ID는 나열된 동안 변경되지 않습니다. 로스터가 가득 찼을 때 FailproofAI 훅이 있는 새 프로필이 나타나면(훅이 실행되거나 설정 파일에 훅이 포함된 경우), 데몬은 다음 조건을 모두 충족하는 프로필을 삭제하여 공간을 만듭니다:

- 훅이 설치되지 않았습니다;
- 어떤 할당도 해당 프로필을 지정하지 않습니다;
- FailproofAI Cloud가 이를 새 타겟으로 수락하지 않을 것입니다.

데몬은 머신에서 더 이상 발견되지 않는 프로필을 우선적으로 선택하고, 그 다음으로 가장 오래 사용되지 않은 프로필을 선택합니다. 정확한 타겟이 사용하는 프로필은 절대 삭제하지 않으므로 해당 타겟은 유효하게 유지됩니다. 삭제할 수 있는 프로필이 없으면 새 프로필에 아직 ID가 없으며, 슬롯이 확보될 때까지 타겟 할당이 매칭되지 않습니다.

## Jev 검사 배포

Cloud 정책은 JavaScript 대신 또는 추가로 Jev 검사를 포함할 수 있습니다. 종류는 `jev`(Jev 검사만) 또는 `both`(자체 검사가 평결을 해제할 수 있는 JavaScript)입니다. 다른 정책과 동일하게 배포, 전환, 롤백됩니다.

Jev 검사는 FailproofAI Cloud에서 실행되며 머신에는 아무것도 설치되지 않습니다. 머신은 `both` 정책의 JavaScript만 수신합니다. `jev` 또는 `both` 정책이 배포된 동안 FailproofAI Cloud는 해당 머신에 대해 Jev를 활성화하고, 정책이 타겟으로 하는 에이전트의 검사된 각 도구 호출이 FailproofAI Cloud로 전송되어 해당 에이전트에 배포된 검사를 실행하고 평결을 반환합니다. 배포된 정책이 없으면 Jev는 비활성화됩니다. 수동으로 Jev 모드를 설정하는 방법은 없습니다.

```bash
fp policies publish prod-db-intent --kind jev --semantic ./checks.json
fp fleet deploy <machine-id> --add prod-db-intent:observe
```

Jev 검사가 아무것도 결정하지 않도록 시험하려면 `:observe`로 정책을 배포하세요: 검사가 실행되고 답변이 "would have"로 기록되며, 아무것도 차단하거나 해제하지 않습니다. 정책 페이지에서 수행했을 동작이 표시되면 `enforce`로 재배포하세요; 그러면 Jev 검사가 호출을 **차단**하고 검토하는 JavaScript 평결을 해제합니다. `:observe`로 배포된 `both` 정책은 두 부분 모두 관찰합니다.

`both` 정책의 JavaScript는 FailproofAI Cloud의 자체 검사 답변으로만 해제될 수 있습니다. 설치된 팩의 동일한 이름 검사는 절대 해제하지 않습니다. FailproofAI Cloud에 연결할 수 없거나 검사를 요청하는 모드가 설정되지 않은 경우, 정책은 **hard** 상태를 유지합니다: JavaScript의 모든 deny가 유지됩니다.

에이전트 타겟팅은 Jev 전용 정책에도 적용됩니다. `both` 정책의 경우,
할당의 단일 타겟이 **로컬 JavaScript와 Cloud Jev 검사 모두**를 관리합니다;
해당 타겟 외부의 호출은 어느 쪽도 실행하지 않습니다. 범위가 지정되지 않은 Jev 롤아웃과 마찬가지로
범위가 지정된 검사를 시험하는 동안에는 정책을 `observe`로 유지하세요.

머신은 검사를 요청하지 못하는 이유를 보고하며, `fp fleet show <machine-id>`를 실행하면 정책 오류 아래에 나열됩니다:

- `transcripts_disabled`: 머신이 `--no-transcripts`로 연결되었습니다. 이러한 머신은 Jev에 도구 호출을 전송하지 않습니다.
- `jev_unconfigured`: 머신의 키가 Jev를 지원하지 않습니다.
- `jev_rate_limited`: 조직의 Jev 속도 제한으로 일부 호출이 거부되어 정규식 정책만으로 결정되었습니다.
- `jev_unavailable`: FailproofAI Cloud의 Jev가 여러 호출에서 연속으로 실패하여 머신이 1분씩 건너뜁니다.

하나의 Jev 요청은 제한된 양의 질문 텍스트를 포함합니다. FailproofAI Cloud의 검사는 머신에 설치된 팩의 검사보다 먼저 실행됩니다. 맞지 않는 팩 검사는 제외되고 `jev_budget`으로 보고됩니다. 조직의 Cloud 검사와 동일한 이름을 가진 팩 검사도 제외되고 `jev_name_clash`로 보고됩니다: Cloud 검사가 대신 실행됩니다.

## 커버리지 확인

커버리지는 정책이 위험이 있는 곳에서 실행되고 있는지 확인합니다.

1. **Admin → enforcement**로 이동하여 enforce 및 observe 합계를 검토합니다.
2. ID나 레이블로 머신을 검색하거나, 정책이 누락된 머신을 필터링합니다.
3. 행을 펼쳐 할당된 정책, 보고된 배포, 마지막 체크인, 기록을 비교합니다.
4. 적용된 배포가 아직 보류 중인 경우 머신의 폴링 간격 후 새로 고침합니다.

![정책 커버리지, 머신 배포 상태, observe 및 enforce 할당을 보여주는 Enforcement 플릿.](/images/dashboard/enforcement-fleet.png)

최신 배포를 가져오지 않은 머신, 보고를 중단한 등록된 머신, 잘못된 환경에 할당된 정책, 중단된 업데이트 후 버전 드리프트를 확인하세요.

머신에 워크로드 및 환경별 레이블을 지정하세요 — 호스트명만으로는 오토스케일링이나 교체 후에 유지되지 않는 경우가 많습니다:

```bash
failproofai config --machine-label checkout-runner-03
```

<Warning>
  Enforcement 관리는 관리자용 Cloud 워크플로입니다. 루트 전용 enforcement 라우트를 일반 고객용 `/v1` API 엔드포인트로 취급하지 마세요.
</Warning>
