Python 3.11 이상. 런타임 의존성 없음. 프레임워크를 사용하시나요? [LangChain, CrewAI, LlamaIndex, Pydantic AI](/ko/start/integrations)는 한 번의 호출로 자동 계측됩니다.

<Note>
  **TypeScript SDK**도 제공되며, 두 SDK는 동일한 이벤트를 동일한 스풀에 기록합니다. Node 에이전트와 Python 에이전트가 혼재하는 환경에서도 두 개가 아닌 하나의 세션 집합이 생성됩니다. 회사 전체가 아닌 서비스별로 선택하세요.
</Note>

## 설치

```bash
pip install failproofai-sdk
```

패키지는 `failproofai-sdk`로 설치되며, Python에서는 `failproofai_sdk`로 임포트합니다. `failproofai-sdk[langgraph]`와 같은 프레임워크 추가 패키지는 해당 프레임워크 자체를 설치합니다. 어댑터는 항상 기본 wheel에 포함되어 있습니다.

## 구성

### OpenTelemetry 스팬 (옵트인)

`opentelemetry-sdk`를 별도로 설치한 후 선택적 익스포터를 연결합니다:

```python
import failproofai_sdk
from opentelemetry.sdk.trace import TracerProvider

provider = TracerProvider()
failproofai_sdk.instrument("otel", provider=provider)
with provider.get_tracer("my-agent").start_as_current_span(
    "agent", attributes={"gen_ai.operation.name": "invoke_agent"}
):
    pass
provider.force_flush()
```

`provider`를 생략하면 이미 등록된 프로바이더를 사용하며, 등록된 것이 없을 때만 새로 생성합니다. `failproofai_sdk.OtelSpanExporter()`를 직접 자신의 스팬 프로세서에 전달할 수도 있습니다. 다른 익스포터는 변경되지 않습니다.

연결된 FailproofAI 데몬이 익스포트를 전달하므로, SDK에는 네트워크 설정, 키, 로컬 리스너가 필요하지 않습니다. 관리자는 [OpenTelemetry 인제스트](/ko/agenteye/opentelemetry)를 활성화해야 합니다. `instrument()`만 단독으로 호출하면 OTEL이 활성화되지 않습니다. `uninstrument("otel")`는 해당 프로세서만 비활성화합니다.
계측 콘텐츠 캡처는 여러분의 계측 코드가 제어합니다. 종료 전에 프로바이더를 플러시하세요.
SDK는 여전히 런타임 의존성이 전혀 없으며, 요청 시에만 OpenTelemetry를 임포트합니다.

```python
import failproofai_sdk

failproofai_sdk.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| 인수 | 설명 |
| --- | --- |
| `environment` | 모든 이벤트에 붙는 레이블 — `production`, `staging`, `prod-eu`. 기본값은 `dev`. |
| `flush_interval` | 백그라운드 스레드가 디스크에 쓰는 주기(초). 기본값은 `0.5`. |
| `base_dir` | 쓰기 경로. 기본값은 데몬의 스풀이며, 특별한 이유가 없다면 이 값을 그대로 사용하세요. |

환경 변수로 설정하는 방법:

| 변수 | 설명 |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | 코드 변경 없이 `environment`를 설정합니다. 레이블이 앱이 아닌 배포 환경에 속할 때 유용합니다. `configure()` 인수가 이 값보다 우선합니다. |
| `FAILPROOFAI_HOME` | 스풀을 포함하는 Failproof AI 루트 디렉터리를 이동합니다. |
| `FAILPROOFAI_SDK_STRICT` | `1`로 설정하면 계측 오류가 로깅되는 대신 예외를 발생시킵니다. |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | `1`로 설정하면 프레임워크 호환성 문제 발생 시 경고 후 계속 진행하는 대신 예외를 발생시킵니다. |

<Warning>
  **`environment`에 쉼표를 사용하지 마세요.** 인제스트는 이 필드를 쉼표 기준으로 분리하여 필터를 구성하며, 레이블에 쉼표가 포함된 이벤트는 모두 무시됩니다 — 실행 전체가 조용히 사라질 수 있습니다. `prod,eu`가 아닌 `prod-eu`로 작성하세요.

  `configure(environment="prod,eu")`는 즉시 예외를 발생시켜 문제를 알려줍니다. `AGENTEYE_ENVIRONMENT`는 예외를 발생시킬 수 없으므로 — 호출하는 주체가 없기 때문에 — 한 번 경고를 출력하고 `dev`로 폴백합니다.
</Warning>

이벤트는 메모리에 큐잉되어 매 `flush_interval`초마다 백그라운드에서 기록되며, 인터프리터 종료 시 최종 플러시가 수행됩니다. 프로세스가 강제 종료되면 아직 기록되지 않은 이벤트는 손실됩니다.

## 식별자

모든 이벤트는 세션과 에이전트에 속합니다. **스코프가 두 값을 자동으로 채워주므로** 직접 전달할 필요가 거의 없습니다:

```python
with failproofai_sdk.session():
    with failproofai_sdk.agent("planner"):
        failproofai_sdk.event.tool_use(tool_name="search", tool_call_id="c1")
```

`session_id`나 `agent_id`를 명시적으로 전달하는 방법도 여전히 사용할 수 있으며, 이 경우 명시된 값이 우선합니다. 스코프에 바인딩되지 않고 전달되지도 않으면, Cloud가 조용히 버릴 이벤트를 보내는 대신 `TypeError`가 발생합니다.

<Note>
  식별자는 컨텍스트 변수에 저장됩니다. `asyncio` 태스크는 자동으로 전파되지만, **새 스레드는 그렇지 않습니다** — 워커를 `failproofai_sdk.propagate()`로 감싸지 않으면 해당 이벤트가 연결되지 않습니다.
</Note>

## 이벤트 카탈로그

총 15개의 메서드. 대부분은 **쌍으로** 구성됩니다 — 시작 메서드를 호출하고, 이후 종료 메서드를 호출하면 SDK가 그 간격을 측정합니다.

| | 시작 | 종료 |
| --- | --- | --- |
| **에이전트** | `agent_start` | `agent_end` |
| | `agent_pause` | `agent_resume` |
| **모델** | `model_request` | `model_response` |
| **도구** | `tool_use` | `tool_result` |
| **훅** | `hook_triggered` | `hook_completed` |
| **사람** | `human_wait` | `human_input` |

단독으로 사용하는 메서드는 세 가지입니다: `error`, `human_pause`, `human_interrupt`.

<Accordion title="메서드별 전체 필드" icon="table">

모든 메서드는 `session_id`와 `agent_id`도 받으며, 스코프가 자동으로 채워줍니다. `None`으로 남겨진 값은 JSON `null`로 전송되지 않고 제거되며, 모든 메서드는 `None`을 반환합니다.

| 메서드 | 필수 | 선택 |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools`, `request_id` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role`, `request_id`, `duration_ms` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

</Accordion>

<Warning>
  실행을 실패로 표시하려면 `outcome`이 `failed`, `error`, `timeout`, `rejected` 중 하나여야 합니다. `"failure"`처럼 비슷하게 보이는 값을 포함하여 그 외의 모든 값은 성공으로 처리됩니다.
</Warning>

## 페어링과 지속 시간

**규칙은 하나: 종료 이벤트에 시작 이벤트와 동일한 id를 전달하세요.** 이것이 둘을 연결하고 SDK가 간격을 측정할 수 있게 합니다.

| 쌍 | 매칭 기준 |
| --- | --- |
| `tool_use` → `tool_result` | `tool_call_id` |
| `hook_triggered` → `hook_completed` | `hook_id` |
| `agent_pause` → `agent_resume` | `pause_id` |
| `human_wait` → `human_input` | `input_id` |
| `model_request` → `model_response` | `request_id` |

**`duration_ms`를 직접 전달하지 마세요.** SDK가 측정하며, 직접 전달하면 `ValueError`가 발생합니다.

유일한 예외는 `model_response`입니다. 실제 프로바이더 지연 시간은 여러분만 알 수 있기 때문입니다. 밀리초 단위의 정수를 전달하세요 — float을 전달하면 예외가 발생합니다. 해당 컬럼은 32비트 정수이며, float을 전달하면 빈 값으로 저장됩니다.

<Accordion title="엣지 케이스" icon="circle-help">

- **id는 종류별, 세션별로만 고유하면 됩니다.** 도구 호출과 훅이 같은 id를 공유할 수 있으며, 동시에 실행 중인 두 세션이 같은 id를 재사용해도 충돌이 발생하지 않습니다.
- **id는 에이전트 범위에 종속되지 않습니다.** 한 에이전트에서 시작하고 다른 에이전트에서 종료되는 쌍도 여전히 매칭됩니다 — 멀티 에이전트 코드에서는 이것이 일반적인 경우입니다.
- **`request_id`는 선택 사항이지만 권장됩니다.** 없으면 같은 에이전트 내에서 동시 호출이 발생할 때 도착 순서대로 모델 이벤트가 페어링되어 잘못 매칭될 수 있습니다.
- **프로세스에 걸쳐 나뉜 쌍**은 Cloud에서 여전히 매칭되지만, SDK는 타이밍을 측정할 수 없습니다 — 어느 프로세스도 두 절반을 모두 보지 못했기 때문입니다.
- **최대 10,000개의 시작 이벤트**가 종료 이벤트를 기다릴 수 있습니다. 이를 초과하면 가장 오래된 것이 제거되어 누수가 무한정 증가하지 않습니다.

</Accordion>

## 커스텀 필드

추가로 전달하는 모든 키워드 인수는 이벤트와 함께 저장됩니다:

```python
failproofai_sdk.event.tool_use(
    tool_name="search", tool_call_id="c1",
    fw_tenant="acme", fw_region="eu-west-1",     # your own
)
```

나중에 쿼리하려면 JSON 타입을 사용하세요. UUID, datetime, `Decimal`, set, bytes, 모델 객체 등 그 외의 타입은 문자열로 저장됩니다.

<Warning>
  **필드 이름에 접두사를 붙이세요.** 추가 필드는 마지막에 적용되므로, `model`, `tool_name`, `outcome` 같은 이름의 필드는 실제 값을 조용히 덮어씁니다. 프레임워크 어댑터는 `fw_`를 사용합니다. 같은 방식을 따르면 충돌이 발생하지 않습니다.

  이것이 오타가 난 선택적 필드에서 오류가 발생하지 않는 이유이기도 합니다 — 단순히 새 커스텀 필드가 됩니다. Cloud에서 표준 필드가 누락된 경우, 먼저 철자를 확인하세요.
</Warning>

다음 다섯 가지 이름은 예약되어 있으며 사용할 수 없습니다: `timestamp`, `session_id`, `agent_id`, `type`, `environment`.

## 전달 및 검증

<Tabs>
  <Tab title="대시보드">
    **Observe → Events**에서 `agent_start`가 처음에, `agent_end`가 마지막에 있는지 확인합니다. 그런 다음 **Observe → Sessions**을 열어 모델, 도구, 사람, 훅, 오류 이벤트가 의도한 순서로 나타나는지 확인합니다. 세션 ID를 기본 트러블슈팅 키로 사용하세요.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

Cloud가 비어 있다면 `$FAILPROOFAI_HOME/custom-agents/events`를 확인하고, 없으면 `~/.failproofai/custom-agents/events`를 확인하세요. JSONL 파일이 있으면 SDK 방출이 확인된 것이고, 스풀이 계속 증가하면 데몬 구성이나 전달 문제를, 스풀이 비어 있으면 계측 또는 프로세스 수명 문제를 나타냅니다.

<Note>
  데몬이 중지된 상태에서만 스풀을 검사하세요. 데몬이 실행 중일 때는 밀리초 단위로 각 배치를 수집하고 삭제하므로, 디렉터리 목록이 수집기와 경쟁 상태가 되어 실제로 방출된 이벤트보다 훨씬 적게 표시됩니다.
</Note>

## 커스텀 런타임에서 장애 방지

감사 결과와 연결된 트레이스를 사용하여 안전하지 않은 동작, 필요한 증거, 의도된 대응을 정의하세요. 커스텀 적용 통합은 실행 전에 동작을 노출하고, 구조화된 입력을 정책 엔진에 전달하며, 그 결과로 나오는 allow, instruct, deny 결정을 적용해야 합니다.

[Failproof AI에 문의](mailto:support@befailproof.ai)하시면 런타임의 모델, 도구, 라이프사이클 경계를 정책 훅에 매핑하고 통합을 함께 검증하는 데 도움을 드립니다.
