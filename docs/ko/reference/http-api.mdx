공개 API는 Failproof AI 대시보드 오리진의 `/v1` 경로에서 제공됩니다. Failproof AI Cloud에서 해당 오리진은 `https://app.befailproof.ai`이므로 기본 경로는 `https://app.befailproof.ai/v1`입니다. 셀프 호스팅 배포 환경에서는 본인의 대시보드 호스트 뒤에 `/v1`을 붙여 사용하며, `fp`에 `--base-url <url>` 또는 `FP_DASHBOARD_URL` 환경 변수로 해당 호스트를 전달하면 됩니다.

## 키 생성 및 요청 보내기

<Tabs>
  <Tab title="대시보드">
    1. **Administration → Keys**를 열고 **new key**를 선택한 후, 통합에 필요한 최소 권한 프리셋을 선택합니다.
    2. 필요한 경우에만 개별 권한을 추가하고, 키를 생성한 뒤 일회용 시크릿을 복사합니다.
    3. `/v1/sessions`로 테스트 요청을 보내고, Keys 페이지에서 키가 활성 상태인지 확인합니다.
    4. 통합의 소유권이 변경될 경우 해당 키의 액션 메뉴에서 키를 교체하거나 비활성화합니다.

    ![권한 프리셋 및 개별 권한이 표시된 새 API 키 드로어.](/images/dashboard/key-create.png)

    키 생성 드로어는 위와 같습니다. 일회용 시크릿은 키 생성 후에만 표시되므로, 확인 창을 닫기 전에 반드시 복사해 두세요.
  </Tab>
  <Tab title="CLI">
    읽기 전용 키를 생성하고 `fp` 또는 `curl`로 직접 사용합니다. `fp`는 `--api-key` 또는 `FP_API_KEY`에서 키를 읽습니다.

    ```bash
    fp keys create reliability-reader \
      --permission-set read-only

    export FP_API_KEY="<one-time-secret>"
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/sessions?limit=20" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

키는 특정 조직과 권한 목록에 바인딩됩니다. 권한 세트는 키 생성 시에만 해당 목록을 초기화하며, 키는 확장된 권한 목록을 직접 저장합니다. 따라서 이후 권한 세트를 변경해도 키에는 영향을 미치지 않습니다. 엔드포인트에 필요한 권한이 없는 요청은 `403`을 반환하며, 부족한 권한을 명시합니다.

## 조직 선택

조직 키는 자동으로 해당 조직에서 동작합니다. 인스턴스 범위 키는 요청마다 조직을 선택하며, 두 개 이상의 조직을 가진 테넌트는 키 모드에서 반드시 조직을 명시해야 합니다. `fp`는 키로 인증할 때 저장된 조직을 전송하지 않습니다.

| 호출 방식 | 조직 지정 방법 |
| --- | --- |
| `fp`, 호출별 | 서브커맨드 앞에 `--org <slug>` 지정 |
| `fp`, 환경 변수 | `FP_ORG` |
| 직접 HTTP 요청 | `X-AgentEye-Org: <slug>` 요청 헤더 |

`X-AgentEye-Org`는 네트워크 전송 시 원래 철자를 그대로 유지합니다. 이 헤더는 대시보드가 활성 조직을 확인하는 데 사용하며, 클라이언트에서 헤더명을 바꾸면 요청이 실패합니다.

<Tabs>
  <Tab title="대시보드">
    **Administration → Keys**를 열기 전에 대시보드 헤더의 조직 전환기를 사용하여 원하는 조직을 선택합니다. 해당 조직에서 생성된 키는 선택된 조직에 속합니다. 자격 증명을 자동화에 적용하기 전에 URL과 키 상세 정보에서 조직 슬러그를 확인하세요.

  </Tab>
  <Tab title="CLI">
    커맨드 앞에 `--org`를 사용하거나, 인스턴스 범위 API 키에 조직 헤더를 전송합니다. `fp orgs list`는 키 모드에서 슬러그를 조회하지 않으므로 거부됩니다. 슬러그는 대시보드의 조직 전환기에서 확인하세요.

    ```bash
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/usage" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

## 페이지네이션

목록 엔드포인트는 키셋 방식으로 페이지네이션되며, `fp`나 `curl` 중 어떤 방식으로 호출하더라도 동일한 규약이 적용됩니다.

| 요소 | 의미 |
| --- | --- |
| `limit` 쿼리 파라미터 | 이번 호출에서 요청할 행 수. `fp`는 모든 엔드포인트에서 단일 요청을 최대 200행으로 제한합니다. 직접 요청의 경우 서버의 엔드포인트별 상한선이 적용됩니다. |
| `cursor` 쿼리 파라미터 | 이전 페이지 이후부터 피드를 재개하는 불투명 토큰. |
| `next_cursor` 응답 필드 | 다음 페이지의 토큰. `null`이면 피드가 소진되었음을 의미합니다. |

상한선은 엔드포인트마다 다르며, 각 엔드포인트 페이지에 기본값과 최대값이 명시되어 있습니다.

| 엔드포인트 | 기본값 | 최대값 |
| --- | --- | --- |
| `/events`, `/events/summary` | 50 | 1000 |
| `/issues`, `/alerts/{id}/issues` | 200 | 1000 |
| `/evaluation-jobs` | 100 | 500 |
| `/audits/findings` | 100 | 500 |
| `/sessions`, `/evaluations` | 50 | 200 |
| `/audits/{id}/runs` | 50 | 200 |

전체 피드를 읽으려면 이전 응답의 `next_cursor` 값을 `cursor`에 설정하여 동일한 요청을 반복하다가 `next_cursor`가 `null`로 돌아올 때 멈추면 됩니다. 이에 해당하는 `fp` 플래그인 `--all`, `--cursor`, `--page-size`는 [Cloud CLI 레퍼런스](/ko/reference/cloud-cli)에 문서화되어 있습니다.

## 엔드포인트 레퍼런스 및 오류 처리

현재 경로, 파라미터, 권한 요구사항, 상태 코드는 이 섹션의 생성된 엔드포인트 페이지를 참조하세요. 사양은 서버 라우트 어노테이션에서 생성되며 `/v1` 라우터에 대해 검증됩니다.

현재 사양은 라우트, 메서드, 파라미터, 권한, 상태 코드를 완전히 다루고 있습니다. 요청 본문은 타입이 지정되어 있지만, 응답 본문은 그렇지 않습니다. 서버가 여전히 동적 JSON으로 응답 본문을 구성하기 때문에 사양에 응답 스키마가 포함되어 있지 않습니다. 강타입 클라이언트를 생성하기 전에 실제 응답을 먼저 확인하세요.

JSON 쓰기 요청에는 `Content-Type: application/json`을 사용하세요. 상태 코드별 의미는 다음과 같습니다. `401`은 인증 누락 또는 유효하지 않은 인증, `403`은 유효한 신원이지만 필요한 권한 없음, `404`는 존재하지 않거나 해당 조직에서 접근 불가한 리소스, `409`는 상태 충돌, `400`은 유효하지 않은 파라미터(알 수 없는 필터 값, 잘못된 형식의 쿼리 파라미터, 실행 불가능한 구문 등), `422`는 요청 본문의 유효하지 않은 필드 또는 권한 값을 나타냅니다. 오류 응답에는 사람이 읽을 수 있는 메시지가 포함되며, 권한 실패의 경우 필요한 권한도 명시됩니다.

## `/v1`이 제공하지 않는 기능

클라우드 관리 정책, 플릿, 가드레일 결정 피드는 운영자 전용 기능으로, 읽기와 쓰기 모두 해당됩니다. 이들은 서버에서 루트 전용으로 처리되며, 인터넷에 노출되는 `/v1`에서는 의도적으로 제외되어 있습니다. 예를 들어 정책 버전을 게시하거나 특정 머신에 배포하는 작업은 API 키로 수행할 수 없으며, 플릿의 결정 내역 조회도 마찬가지입니다.

따라서 API 키는 해당 라우트에 대해 설계상 거부됩니다. 또한 `fp`는 연결을 열기 전에 미리 거부하므로, 아무런 설명 없이 404가 반환되는 상황을 방지합니다.

| 커맨드 | API 키 사용 시 동작 |
| --- | --- |
| `fp policies` | 종료 코드 `2`로 거부하며, 클라우드 관리 정책이 운영자 전용 기능임을 명시 |
| `fp fleet` | 종료 코드 `2`로 거부하며, 플릿이 운영자 전용 기능임을 명시 |
| `fp guardrails` | 종료 코드 `2`로 거부하며, 가드레일 피드가 운영자 전용 기능임을 명시 |
| `fp agent` | 종료 코드 `2`로 거부; 어시스턴트는 API가 아닌 대시보드에서 구현됨 |
| `fp orgs` | 종료 코드 `2`로 거부; 조직 멤버십은 로그인한 사용자에 속하며, 키는 이미 하나의 조직에서 동작함 |

이러한 커맨드는 로그인한 사용자 세션(`fp login`)에서 실행하거나 대시보드를 사용하세요. 읽기 및 관리 관련 기능(세션, 이벤트, 평가, 감사, 이슈, 알림, 키, 권한 세트, 사용자, 설정, 쿼리, 사용량)은 각각 `/v1` 라우트가 있으며 키로 사용할 수 있습니다. 단 한 가지 예외는 `fp keys update`로, 이 커맨드는 `keys:update` 권한이 필요한데 어떤 API 키도 이 권한을 가질 수 없습니다. 따라서 키는 다른 키를 생성하거나 비활성화할 수 있지만 권한을 편집하는 것은 불가능합니다. `fp login`과 `fp logout`도 키 모드에서는 거부되는데, 이는 다른 이유 때문입니다. 키 자체가 이미 자격 증명이며, 디스크에 저장되지 않기 때문입니다.

<Warning>
  정책 적용 배포는 의도적으로 일반 공개 `/v1` 기능 외부에서 관리됩니다. [정책 배포](/ko/policies/deploy)에 설명된 지원되는 Cloud 배포 워크플로우를 사용하세요.
</Warning>
