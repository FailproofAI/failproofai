이 페이지는 [Jev 평가](/ko/evaluations/jev) 의 기반이 되는 질문 형태와 점수 산출 규칙을 설명합니다. 일부 질문은 모델이 대화를 *읽기*만 하면 되고, *작성*할 필요는 없습니다. "고객이 긴박감을 표현했나요?"에는 두 가지 답이 있습니다. "얼마나 불만스러워했나요?"에는 순서가 있는 몇 가지 답이 있습니다. 질문하기 전에 가능한 모든 답을 알고 있습니다.

**분류기 평가**는 바로 이런 경우를 위한 것입니다. 질문과 가능한 답을 직접 작성하면, 분류 전용으로 만들어진 소형 모델이 보정된 숫자를 반환합니다 — 자유 형식 텍스트는 절대 반환하지 않습니다.

<Note>
판사(judge)와 마찬가지로, 분류기 평가는 세션당 모델 호출이 필요합니다. 하지만 판사와 달리 범용 모델이 아닌 소형 단일 목적 모델이기 때문에 더 빠르고 저렴합니다. 단, 스스로 설명하지는 않습니다. 추론 과정이 필요하다면 [judge](/ko/evaluations/judge)를 사용하세요.
</Note>

## 어떤 것을 선택해야 할까요?

| 질문 | 사용 방법 |
| --- | --- |
| 도구 호출이 몇 번 있었나요? | 코드 |
| 세션이 30초 이내였나요? | 코드 |
| 고객이 긴박감을 표현했나요? | **분류기** |
| 어느 팀이 처리해야 하나요: 결제, 기술, 영업? | **분류기** |
| 고객이 얼마나 불만스러워했나요? | **분류기** |
| 답변이 실제로 정확했나요? | **judge** |
| 에스컬레이션 정책을 따랐나요, 그 이유는? | **judge** |

경험 법칙: **셀 수 있는 것 → 코드, 목록으로 나열할 수 있는 답 → 분류기, 설명이 필요한 것 → judge.**

미리 결정할 필요는 없습니다. 측정하고 싶은 것을 설명하면 어시스턴트가 선택하고, 어떤 것을 선택했는지와 그 이유를 알려주며, 언제든지 변경할 수 있습니다.

## 두 가지 질문 유형

### `noul` — 이것이 사실인가요?

두 가지 답이 있으며, 각각을 직접 설명합니다. 결과는 "참" 설명에 해당할 확률입니다:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

양쪽 모두 설명하세요. "긴박감이 표현되지 않음"도 하나의 유효한 답이며, 이를 명시하면 반대쪽 답이 더 명확해집니다.

### `score` — 이것이 얼마나?

**최악부터 시작하는** 순서 있는 루브릭입니다. 결과는 세션이 루브릭에서 위치하는 지점이며, 0–1로 재조정됩니다:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**루브릭은 3~5개의 단계로 구성되어야 하며, 모두 서로 달라야 합니다.** 두 제한 모두 스타일 가이드가 아닌 실질적인 이유로 적용됩니다:

- **2개 단계**는 `noul`이 이미 더 잘 처리하는 것과 동일해지고, **5개 초과**는 모델이 중간 값으로 치우쳐 확실한 답을 내리지 못하게 만듭니다. 동일한 질문을 동일한 세션에 적용했을 때 2개 단계에서 0.00, 3개 단계에서 0.01, 10개 단계에서 0.55가 나왔습니다.
- **반복된 단계**는 답을 임의로 분산시킵니다. 명백히 화난 세션은 `["Calm", "Frustrated", "Very angry"]`에서 1.00, `["Angry", "Angry", "Angry"]`에서 0.66이 나왔는데 — 형식적으로는 올바른 숫자이지만 아무 의미가 없습니다.

순서가 없는 범주 — "결제, 기술, 영업" — 는 루브릭이 아닙니다. 범주별로 `noul`로 질문하거나 judge를 사용하세요.

## 결과 해석

분류기는 judge와 마찬가지로 0에서 1 사이의 **점수**를 생성하므로, 차트 표시, 필터링, 알림 트리거도 동일한 방식으로 작동합니다. 알아두어야 할 차이점이 두 가지 있습니다:

- **추론 과정이 없습니다.** 해당 필드는 의도적으로 비어 있습니다. 이 모델은 스스로를 설명하지 않으며, 설명을 만들어 내는 것은 기능이 아니라 조작이 됩니다.
- **불확실성에 레이블이 붙습니다.** `score` 질문은 자체 신뢰도를 함께 보고하며, 모델이 확신하지 못한 결과에는 `low_confidence` 태그가 붙습니다 — 따라서 "사람이 검토해야 할 항목"은 추측이 아닌 필터로 찾을 수 있습니다. `noul` 질문은 신뢰도를 보고하지 않으므로 태그가 붙지 않습니다.

매우 긴 세션은 발췌 방식으로 읽고 결합됩니다. 세션이 너무 길어 전체를 읽을 수 없을 때, 결과에는 생략된 턴 수가 표시됩니다 — 전체 세션에 대한 판단인 것처럼 일부 세션에 대한 판단이 제시되는 일은 절대 없습니다.

## 제한 사항

- **루브릭 단계는 3~5개, 모두 서로 달라야 합니다.** 위를 참고하세요; 두 제한 모두 작성 시점에 적용됩니다.
- **평가당 질문 하나.** 두 가지를 묻고 싶으면 두 개의 평가를 만드세요. 차트에서도 그것이 더 유용합니다.
- **질문을 수정하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로, 하나의 추세선에 혼합되지 않고 별도로 유지됩니다.
- **분류기는 항상 점수를 생성합니다** — 메트릭이나 어서션이 아닙니다.
- **추론 없음**, 위와 같습니다. 숫자를 보고 누군가가 "왜?"라고 물을 것 같다면, 대신 judge를 작성하세요.

## 테스트 및 백필

judge와 달리, 분류기 평가는 배포 전에 **테스트할 수 있습니다** — 코드 평가와 동일한 방식으로 실제 세션을 대상으로 [테스트](/ko/evaluations/test)하고, 라이브 적용 전에 점수를 확인하세요.

또한 이미 보유한 세션에 대해 [백필](/ko/evaluations/deploy#score-sessions-you-already-have)도 가능합니다. 세션당 모델 호출이 필요하므로, 모든 세션을 재처리하기보다는 범위를 신중하게 설정하세요.
