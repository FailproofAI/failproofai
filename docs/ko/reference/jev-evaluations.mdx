이 페이지에서는 [Jev 평가](/ko/evaluations/jev)의 질문 형태와 채점 규칙을 설명합니다. 일부 질문은 모델이 대화를 *읽기*만 하면 되고, *작성*할 필요는 없습니다. "고객이 긴박감을 표현했는가?"는 두 가지 답만 있습니다. "고객이 얼마나 답답해했는가?"는 순서가 있는 몇 가지 답이 있습니다. 질문하기 전에 이미 모든 답을 알고 있습니다.

**분류기 평가**는 바로 이런 경우를 위한 것입니다. 질문과 가능한 답변을 직접 작성하면, 분류 전용으로 만들어진 소형 모델이 자유 텍스트가 아닌 보정된 숫자를 반환합니다.

<Note>
판정자와 마찬가지로, 분류기 평가는 세션당 모델 호출 비용이 발생합니다. 다만 판정자와 달리 범용 모델이 아닌 소형의 단일 목적 모델이기 때문에 더 빠르고 저렴합니다. 단, 이 모델은 절대 스스로 설명하지 않습니다. 추론 과정이 필요하다면 [판정자](/ko/evaluations/judge)를 사용하세요.
</Note>

## 어떤 것을 선택해야 하나요?

| 질문 | 사용 방법 |
| --- | --- |
| 도구 호출이 몇 번 있었나요? | 코드 |
| 세션이 30초 이내였나요? | 코드 |
| 고객이 긴박감을 표현했나요? | **분류기** |
| 이 케이스는 어느 팀이 처리해야 하나요: 결제, 기술, 아니면 영업? | **분류기** |
| 고객이 얼마나 답답해했나요? | **분류기** |
| 답변이 실제로 맞았나요? | **판정자** |
| 에스컬레이션 정책을 따랐나요? 그렇게 생각하는 이유는? | **판정자** |

기준을 요약하면: **셀 수 있는 것 → 코드, 목록으로 나열할 수 있는 답변 → 분류기, 설명이 필요한 것 → 판정자.**

미리 결정할 필요는 없습니다. 측정하고 싶은 것을 설명하면 어시스턴트가 선택해 주고, 어떤 것을 선택했는지와 그 이유를 알려주며, 변경도 가능합니다.

## 두 가지 질문 유형

### `noul` — 이것이 사실인가요?

두 가지 답이 있으며, 각각을 직접 설명합니다. 결과는 "참" 설명이 해당될 확률입니다:

```json
{
  "instructions": "어시스턴트가 환불 정책 확인 없이 환불을 약속했나요?",
  "criteria": {
    "true":  "사전 정책 확인이나 승인 없이 환불이 약속되거나 처리되었음",
    "false": "환불이 약속되지 않았거나, 모든 환불이 정책 확인을 거쳤음"
  }
}
```

양쪽 모두 설명하세요. "긴박감이 표현되지 않음"도 실제 답변이며, 이를 명시하면 반대쪽 답변이 더 명확해집니다.

### `score` — 이것이 얼마나 해당되나요?

**최악부터** 순서대로 나열된 채점 기준입니다. 결과는 세션이 기준 어디에 해당하는지를 0–1로 환산한 값입니다:

```json
{
  "instructions": "고객이 얼마나 답답해하고 있나요?",
  "criteria": ["침착함", "불만족스러움", "매우 화남"]
}
```

**채점 기준은 3~5단계로 구성해야 하며, 모두 서로 달라야 합니다.** 두 제한 사항 모두 스타일의 문제가 아닌 실질적인 이유로 적용됩니다:

- **2단계**는 `noul`이 더 잘 처리하는 것과 동일해지고, **5단계 초과**는 모델이 명확한 답을 내리지 않고 중간으로 쏠리게 만듭니다. 동일한 질문을 같은 세션에 적용했을 때 2단계에서는 0.00, 3단계에서는 0.01, 10단계에서는 0.55가 나왔습니다.
- **반복된 단계**는 답변을 임의로 분산시킵니다. 명백히 화난 세션은 `["침착함", "불만족스러움", "매우 화남"]`에서 1.00이 나왔지만, `["화남", "화남", "화남"]`에서는 0.66이 나왔습니다 — 형식상 올바른 숫자이지만 아무 의미가 없습니다.

순서가 없는 범주 — "결제, 기술, 영업" 등 — 는 채점 기준이 아닙니다. 각 범주에 대해 `noul` 질문으로 묻거나 판정자를 사용하세요.

## 결과 해석하기

분류기는 판정자와 동일하게 0에서 1 사이의 **점수**를 생성하므로, 차트 표시, 필터링, 알림 트리거 방식도 동일합니다. 두 가지 차이점이 있습니다:

- **추론 과정이 없습니다.** 해당 필드는 의도적으로 비어 있습니다. 이 모델은 스스로 설명하지 않으며, 설명을 만들어 내는 것은 기능이 아니라 조작이 됩니다.
- **불확실성이 표시됩니다.** `score` 질문은 자체 신뢰도를 보고하며, 모델이 확신하지 못한 결과에는 `low_confidence` 태그가 붙습니다 — "사람이 검토해야 할 것"이 추측이 아닌 필터가 됩니다. `noul` 질문은 신뢰도를 보고하지 않으므로 태그가 붙지 않습니다.

매우 긴 세션은 발췌본으로 읽고 종합됩니다. 세션이 너무 길어 전체를 읽을 수 없을 경우, 결과에 생략된 턴 수가 표시됩니다 — 전체를 본 것처럼 일부만 보고 판단한 결과가 제공되는 일은 없습니다.

## 제한 사항

- **채점 기준은 3~5단계, 모두 달라야 합니다.** 위 내용 참조; 두 제한 모두 작성 시점에 적용됩니다.
- **평가당 질문 하나.** 두 가지를 묻고 싶다면 평가 두 개를 만드세요. 차트에서도 그 편이 더 좋습니다.
- **질문을 수정하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로, 하나의 추세선에 섞이지 않고 별도로 보관됩니다.
- **분류기는 항상 점수를 생성합니다.** 지표나 단언문을 생성하지 않습니다.
- **추론 과정 없음**, 위 내용 참조. 숫자를 보고 누군가 "왜?"라고 물을 것 같다면, 판정자를 작성하세요.

## 테스트 및 백필

판정자와 달리, 분류기 평가는 배포 전에 **테스트할 수 있습니다** — 코드 평가와 동일하게 실제 세션을 대상으로 [테스트](/ko/evaluations/test)하고, 라이브 적용 전에 점수를 확인할 수 있습니다.

이미 보유한 세션에 대해 [백필](/ko/evaluations/deploy#score-sessions-you-already-have)도 가능합니다. 세션당 모델 호출 비용이 발생하므로, 모든 것을 다시 실행하기보다는 기간을 신중하게 설정하세요.
