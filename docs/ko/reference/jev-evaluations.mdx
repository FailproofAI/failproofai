이 페이지에서는 [Jev 평가](/ko/evaluations/jev)의 질문 형태와 채점 규칙을 설명합니다. 일부 질문은 모델이 대화를 *읽기*만 하면 되고, *작성*할 필요는 없습니다. "고객이 긴박감을 표현했나요?"는 두 가지 답이 있습니다. "고객이 얼마나 답답해했나요?"는 순서가 있는 몇 가지 답이 있습니다. 질문하기 전에 모든 답을 알고 있는 거죠.

**분류기 평가(classifier evaluation)**는 바로 이런 경우를 위한 것입니다. 질문과 가능한 답변을 직접 작성하면, 분류 전용으로 만들어진 소형 모델이 보정된 숫자를 반환합니다 — 자유 형식 텍스트는 절대 반환하지 않습니다.

<Note>
판사(judge)와 마찬가지로, 분류기 평가는 세션당 모델 호출 비용이 발생합니다. 다만 범용 모델이 아닌 단일 목적의 소형 모델이라 더 빠르고 저렴합니다 — 단, 스스로 설명하지는 않습니다. 추론 과정이 필요하다면 [judge](/ko/evaluations/judge)를 사용하세요.
</Note>

## 어떤 것을 사용해야 할까요?

| 질문 | 사용 |
| --- | --- |
| 도구 호출이 몇 번 있었나요? | 코드 |
| 세션이 30초 미만이었나요? | 코드 |
| 고객이 긴박감을 표현했나요? | **classifier** |
| 이 건은 청구, 기술, 영업 중 어느 팀에서 처리해야 하나요? | **classifier** |
| 고객이 얼마나 답답해했나요? | **classifier** |
| 답변이 실제로 정확했나요? | **judge** |
| 에스컬레이션 정책을 따랐나요, 그렇게 생각하는 이유는 무엇인가요? | **judge** |

기본 원칙: **셀 수 있는 것 → 코드, 목록으로 나열할 수 있는 답 → classifier, 설명이 필요한 것 → judge.**

미리 결정하지 않아도 됩니다. 측정하고자 하는 것을 설명하면 어시스턴트가 선택하고, 어떤 것을 선택했는지와 이유를 알려주며, 언제든지 변경할 수 있습니다.

## 두 가지 질문 유형

### `noul` — 이것이 사실인가요?

두 가지 답변이 있으며, 둘 다 직접 설명합니다. 결과는 "참(true)" 설명이 들어맞을 확률입니다:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

양쪽을 모두 설명하세요. "긴박감이 표현되지 않음"도 실제 답변이며, 이를 명시하면 반대 답변이 더 명확해집니다.

### `score` — 이것이 얼마나?

**최악의 것부터** 시작하는 순서가 있는 루브릭입니다. 결과는 세션이 루브릭에서 어느 위치에 해당하는지를 0–1로 환산한 값입니다:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**루브릭은 세 개에서 다섯 개의 레벨을 가져야 하며, 모두 달라야 합니다.** 두 제한 모두 스타일의 문제가 아닌 실측에 근거합니다:

- **두 개의 레벨**은 `noul`이 이미 더 잘 처리하는 것과 동일하게 축소되고, **다섯 개 초과**는 모델이 확실한 답을 내리지 않고 중간으로 치우치게 만듭니다. 동일한 세션을 동일한 질문으로 채점했을 때 두 레벨로는 0.00, 세 레벨로는 0.01, 열 레벨로는 0.55가 나왔습니다.
- **반복된 레벨**은 답을 임의로 분산시킵니다. 명백히 화난 세션이 `["Calm", "Frustrated", "Very angry"]`에 대해서는 1.00을 받았지만, `["Angry", "Angry", "Angry"]`에 대해서는 0.66을 받았습니다 — 형식적으로는 올바른 숫자지만 아무 의미가 없습니다.

순서가 없는 카테고리 — "청구, 기술, 또는 영업" — 는 루브릭이 아닙니다. 카테고리별로 `noul`로 질문하거나, judge를 사용하세요.

## 결과 읽기

분류기는 judge와 동일하게 0에서 1 사이의 **점수**를 생성하므로, 차트, 필터링, 알림 트리거도 동일한 방식으로 작동합니다. 두 가지 차이점을 알아두세요:

- **추론 과정이 없습니다.** 해당 필드는 의도적으로 비어 있습니다. 이 모델은 스스로 설명하지 않으며, 설명을 만들어내는 것은 기능이 아니라 조작이 됩니다.
- **불확실성이 표시됩니다.** `score` 질문은 자체 신뢰도를 보고하며, 모델이 확신하지 못한 결과는 `low_confidence`로 표시됩니다 — "사람이 직접 검토해야 할 것"을 찾는 것이 추측이 아닌 필터링의 문제가 됩니다. `noul` 질문은 신뢰도를 보고하지 않으므로 이 태그가 붙지 않습니다.

매우 긴 세션은 발췌본으로 읽어 결합합니다. 세션이 너무 길어 전부 읽을 수 없는 경우, 결과에 생략된 턴의 수가 표시됩니다 — 세션 일부만 보고 내린 판단이 전체를 본 것처럼 표시되는 일은 없습니다.

## 제한 사항

- **루브릭 레벨은 세 개에서 다섯 개, 모두 달라야 합니다.** 위 내용 참조; 두 제한 모두 작성 시점에 적용됩니다.
- **평가당 질문 하나.** 두 가지를 물어보려면 두 개의 평가를 만드세요 — 차트에서도 그렇게 하는 것이 맞습니다.
- **질문을 수정하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로, 하나의 트렌드 라인에 섞이지 않고 별도로 보관됩니다.
- **분류기는 항상 점수를 생성합니다** — 지표(metric)나 어서션(assertion)은 생성하지 않습니다.
- **추론 없음**, 위와 같습니다. 숫자를 보고 누군가 "왜?"라고 물을 것 같다면, judge를 작성하세요.

## 테스트 및 백필

judge와 달리, 분류기 평가는 배포 전에 **테스트할 수 있습니다** — 코드 평가와 동일한 방식으로 실제 세션을 대상으로 [테스트하고](/ko/evaluations/test), 라이브 적용 전에 점수를 확인하세요.

이미 보유한 세션에 대해 [백필](/ko/evaluations/deploy#score-sessions-you-already-have)하는 것도 가능합니다. 세션당 모델 호출 비용이 발생하므로, 모든 것을 다시 처리하기보다는 기간을 신중하게 설정하세요.
