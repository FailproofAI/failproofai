이 페이지는 [Jev 평가](/ko/evaluations/jev)의 질문 형태와 채점 규칙을 설명합니다. 일부 질문은 대화를 *읽는* 모델은 필요하지만, 그 내용을 *서술*할 필요는 없습니다. "고객이 긴급함을 표현했나요?"는 두 가지 답만 있습니다. "얼마나 불만스러워했나요?"는 순서가 있는 몇 가지 선택지가 있습니다. 질문하기 전에 가능한 답을 모두 알고 있는 경우입니다.

**분류기 평가(classifier evaluation)**는 바로 그런 경우를 위한 것입니다. 질문과 가능한 답을 직접 작성하면, 분류 전용으로 만들어진 소형 모델이 보정된 숫자를 반환합니다 — 자유 형식 텍스트는 절대 반환하지 않습니다.

<Note>
판사(judge)와 마찬가지로, 분류기 평가는 세션당 모델 호출 비용이 발생합니다. 다만 판사와 달리 범용 모델이 아닌 소형 단일 목적 모델을 사용하므로 더 빠르고 저렴합니다 — 하지만 스스로 이유를 설명하지는 않습니다. 추론 과정이 필요하다면 [judge](/ko/evaluations/judge)를 사용하세요.
</Note>

## 무엇을 선택해야 할까요?

| 질문 | 사용 방법 |
| --- | --- |
| 도구 호출이 몇 번 있었나요? | code |
| 세션이 30초 미만이었나요? | code |
| 고객이 긴급함을 표현했나요? | **classifier** |
| 이 건은 어느 팀이 담당해야 하나요: 결제, 기술, 영업? | **classifier** |
| 고객이 얼마나 불만스러워했나요? | **classifier** |
| 답변이 실제로 올바른가요? | **judge** |
| 에스컬레이션 정책을 따랐나요, 그렇게 생각하는 이유는 무엇인가요? | **judge** |

기준을 한마디로 요약하면: **셀 수 있는 것 → code, 목록화할 수 있는 답 → classifier, 설명이 필요한 것 → judge.**

미리 결정할 필요는 없습니다. 측정하고 싶은 것을 설명하면 어시스턴트가 선택하고, 선택한 이유를 알려주며, 변경도 가능합니다.

## 두 가지 질문 유형

### `noul` — 이것이 사실인가요?

두 가지 답이 있으며, 각각을 직접 설명합니다. 결과는 "true" 설명이 해당될 확률입니다:

```json
{
  "instructions": "어시스턴트가 환불 정책을 먼저 확인하지 않고 환불을 약속했나요?",
  "criteria": {
    "true":  "사전 정책 확인이나 승인 없이 환불이 약속되거나 이루어진 경우",
    "false": "환불이 약속되지 않았거나, 모든 환불이 정책 확인을 거친 경우"
  }
}
```

양쪽을 모두 설명하세요. "긴급함이 표현되지 않음"도 유효한 답이며, 이를 명시하면 반대쪽 답이 더 명확해집니다.

### `score` — 얼마나 해당하나요?

순서가 있는 루브릭이며, **가장 낮은 수준부터** 작성합니다. 결과는 세션이 루브릭 어디에 해당하는지를 0–1로 환산한 값입니다:

```json
{
  "instructions": "고객이 얼마나 불만스러워하나요?",
  "criteria": ["차분함", "불만스러움", "매우 화남"]
}
```

**루브릭은 3~5단계로 구성하며, 모든 단계는 서로 달라야 합니다.** 두 제한 모두 단순한 스타일 권고가 아니라 실질적인 이유가 있습니다:

- **2단계**는 `noul`이 이미 더 잘 처리하는 것과 다를 바 없이 무너지고, **5단계 초과**는 모델이 중간값으로 헤징하여 명확하게 판단하지 않습니다. 같은 질문을 같은 세션에 적용했을 때, 2단계에서는 0.00, 3단계에서는 0.01, 10단계에서는 0.55가 나왔습니다.
- **반복된 단계**는 답을 임의로 분산시킵니다. 명백히 화난 세션이 `["차분함", "불만스러움", "매우 화남"]`에서는 1.00을 받았지만, `["화남", "화남", "화남"]`에서는 0.66이 나왔습니다 — 형식상 올바른 숫자이지만 아무런 의미가 없습니다.

순서가 없는 범주 — "결제, 기술, 영업" 등 — 는 루브릭이 아닙니다. 각 범주별로 `noul` 질문을 만들거나, judge를 사용하세요.

## 결과 해석하기

분류기는 판사와 동일하게 0~1의 **점수**를 반환하므로, 차트, 필터, 알림 트리거 방식도 동일합니다. 두 가지 차이점을 알아두세요:

- **추론 내용이 없습니다.** 해당 필드는 의도적으로 비어 있습니다. 이 모델은 스스로 설명하지 않으며, 설명을 만들어낸다면 그것은 기능이 아닌 조작이 됩니다.
- **불확실성에 레이블이 붙습니다.** `score` 질문은 자체 신뢰도를 함께 보고하며, 모델이 확신하지 못한 결과에는 `low_confidence` 태그가 붙습니다 — 따라서 "사람이 검토해야 할 항목"을 찾는 것이 추측이 아닌 필터 작업이 됩니다. `noul` 질문은 신뢰도를 보고하지 않으므로 태그가 붙지 않습니다.

매우 긴 세션은 발췌본으로 읽혀 합산됩니다. 세션이 너무 길어 전체를 읽지 못한 경우, 결과에 몇 번의 턴이 생략되었는지 표시됩니다 — 세션 일부만 보고 판단한 결과가 전체를 보고 판단한 것처럼 제시되는 일은 없습니다.

## 제한 사항

- **루브릭 단계는 3~5개, 모두 고유해야 합니다.** 위 설명 참조; 두 경계 모두 작성 시점에 적용됩니다.
- **평가당 질문은 하나입니다.** 두 가지를 묻고 싶다면 평가를 두 개 만드세요 — 차트에서도 그것이 올바른 방식입니다.
- **질문을 수정하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로, 하나의 추세선에 섞이지 않고 별도로 보관됩니다.
- **분류기는 항상 점수를 생성합니다** — 메트릭이나 어서션이 아닙니다.
- **추론 없음**, 위와 같습니다. 숫자를 보고 누군가 "왜?"라고 물을 것 같다면, 대신 judge를 작성하세요.

## 테스트 및 백필

judge와 달리, 분류기 평가는 배포 전에 **테스트할 수 있습니다** — code 평가와 동일한 방식으로 실제 세션을 대상으로 [테스트하고](/ko/evaluations/test), 라이브 적용 전에 점수를 확인하세요.

또한 이미 보유한 세션에 대해 [백필](/ko/evaluations/deploy#score-sessions-you-already-have)할 수도 있습니다. 세션당 모델 호출 비용이 발생하므로, 모든 세션을 무분별하게 재실행하기보다는 기간을 신중하게 설정하세요.
