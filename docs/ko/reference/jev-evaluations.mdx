이 페이지에서는 [Jev 평가](/ko/evaluations/jev)의 질문 형태와 채점 규칙을 설명합니다. 일부 질문은 대화를 *읽는* 것만 필요할 뿐, 대화에 *관해 작성*할 필요는 없습니다. "고객이 긴박함을 표현했는가?"는 두 가지 답만 존재합니다. "얼마나 불만족스러워했는가?"는 순서가 있는 몇 가지 답이 존재합니다. 질문하기 전에 가능한 답을 모두 알고 있는 것이죠.

**분류기 평가**는 바로 이런 경우를 위한 것입니다. 질문과 가능한 답변을 직접 작성하면, 분류 전용으로 설계된 소형 모델이 보정된 숫자를 반환합니다 — 자유 형식 텍스트가 아닌 숫자만 반환합니다.

<Note>
판사(judge)와 마찬가지로 분류기 평가도 세션당 모델 호출 비용이 발생합니다. 단, 범용 모델이 아닌 단일 목적의 소형 모델을 사용하기 때문에 더 빠르고 저렴합니다. 다만, 이 모델은 절대 스스로 설명하지 않습니다. 추론 과정이 필요하다면 [judge](/ko/evaluations/judge)를 사용하세요.
</Note>

## 어떤 것을 선택해야 할까요?

| 질문 | 사용 방법 |
| --- | --- |
| 도구 호출이 몇 번 있었나요? | 코드 |
| 세션이 30초 미만이었나요? | 코드 |
| 고객이 긴박함을 표현했나요? | **분류기** |
| 이 케이스는 어느 팀이 담당해야 하나요: 결제, 기술, 아니면 영업? | **분류기** |
| 고객이 얼마나 불만족스러워했나요? | **분류기** |
| 답변이 실제로 정확했나요? | **judge** |
| 에스컬레이션 정책을 따랐나요? 그렇게 생각하는 이유는? | **judge** |

간단한 판단 기준: **셀 수 있는 것 → 코드, 목록으로 나열 가능한 답변 → 분류기, 설명이 필요한 것 → judge.**

미리 결정할 필요는 없습니다. 측정하고 싶은 것을 설명하면 어시스턴트가 선택하고, 어떤 것을 선택했는지와 그 이유를 알려드리며, 언제든 바꿀 수 있습니다.

## 두 가지 질문 유형

### `noul` — 이것이 참인가요?

두 가지 답변이 있으며, 각각을 직접 설명합니다. 결과는 "참" 설명이 해당될 확률입니다:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

양쪽을 모두 설명하세요. "긴박함이 표현되지 않음"도 실제 답변이며, 이를 명시하면 반대 답변이 더 명확해집니다.

### `score` — 이것이 얼마나 해당하나요?

순서가 있는 루브릭으로, **최저 수준을 먼저** 작성합니다. 결과는 세션이 루브릭의 어느 위치에 해당하는지를 0–1로 환산한 값입니다:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**루브릭은 3~5개의 단계로 구성되어야 하며, 모두 서로 달라야 합니다.** 두 제한 사항 모두 스타일 가이드가 아닌 실제로 측정된 결과에 근거합니다:

- **두 단계**는 `noul`이 이미 더 잘 처리하는 것과 겹치고, **다섯 단계 초과**는 모델이 명확한 판단 대신 중간값으로 쏠리게 만듭니다. 동일한 질문을 동일한 세션에 적용했을 때, 두 단계에서는 0.00, 세 단계에서는 0.01, 열 단계에서는 0.55가 나왔습니다.
- **반복된 단계**는 답변을 임의로 분산시킵니다. 명백히 화가 난 세션이 `["Calm", "Frustrated", "Very angry"]`에서는 1.00을 받았지만, `["Angry", "Angry", "Angry"]`에서는 0.66을 받았습니다 — 형식상 올바른 숫자이지만 아무 의미가 없습니다.

순서가 없는 범주 — "결제, 기술, 영업" — 는 루브릭이 아닙니다. 각 범주마다 `noul` 질문으로 나누어 묻거나 judge를 사용하세요.

## 결과 읽기

분류기는 judge와 동일하게 0에서 1 사이의 **점수**를 반환하므로, 차트 표시, 필터링, 알림 트리거 방식도 동일합니다. 두 가지 차이점은 알아두시기 바랍니다:

- **추론 과정이 없습니다.** 해당 필드는 의도적으로 비워져 있습니다. 이 모델은 스스로 설명하지 않으며, 설명을 임의로 생성하는 것은 기능이 아닌 조작이 됩니다.
- **불확실성에 레이블이 붙습니다.** `score` 질문은 자체 신뢰도를 함께 보고하며, 모델이 확신하지 못한 결과에는 `low_confidence` 태그가 붙습니다. 따라서 "사람이 검토해야 할 항목"은 추측이 아닌 필터로 찾을 수 있습니다. `noul` 질문은 신뢰도를 보고하지 않으므로 태그가 붙지 않습니다.

매우 긴 세션은 발췌 단위로 읽어 종합합니다. 세션이 너무 길어 전체를 읽을 수 없을 경우, 결과에 생략된 턴 수가 표시됩니다 — 세션 일부만 읽고 전체를 읽은 것처럼 판단하는 경우는 절대 없습니다.

## 제한 사항

- **루브릭은 3~5개의 고유한 단계로 구성되어야 합니다.** 위를 참고하세요. 두 경계값 모두 작성 시점에 적용됩니다.
- **평가당 질문은 하나입니다.** 두 가지를 묻고 싶다면 평가를 두 개 만드세요. 차트에서도 그편이 더 유용합니다.
- **질문을 수정하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로, 하나의 추세선에 혼합되지 않고 별도로 보관됩니다.
- **분류기는 항상 점수를 반환합니다.** 지표나 단언(assertion)은 반환하지 않습니다.
- **추론 과정 없음**, 위에서 설명한 대로입니다. 숫자를 보고 누군가 "왜?"라고 물을 것 같다면 judge를 작성하세요.

## 테스트 및 백필

judge와 달리 분류기 평가는 배포 전에 **테스트할 수 있습니다** — 코드 평가와 동일한 방식으로 실제 세션을 대상으로 [테스트](/ko/evaluations/test)하고, 라이브 적용 전에 점수를 확인하세요.

이미 보유한 세션에 대해 [백필](/ko/evaluations/deploy#score-sessions-you-already-have)도 가능합니다. 세션당 모델 호출 비용이 발생하므로, 모든 세션을 무분별하게 재실행하기보다는 기간 범위를 신중하게 설정하세요.
