이 페이지는 [Jev 평가](/ko/evaluations/jev) 뒤에 있는 질문 형태와 채점 규칙을 설명합니다. 일부 질문은 모델이 대화를 *읽어야* 하지만, *작성할* 필요는 없습니다. "고객이 긴급함을 표현했나요?"에는 두 가지 답이 있습니다. "그들이 얼마나 불만스러워했나요?"에는 순서가 있는 몇 가지 답이 있습니다. 질문하기 전에 모든 답을 알고 있습니다.

**분류기 평가**는 바로 그런 경우에 사용합니다. 질문과 가능한 답변을 작성하면, 분류를 위해 만들어진 작은 모델이 조정된 숫자를 반환합니다 — 자유 텍스트는 절대 아닙니다.

<Note>
판사(judge)처럼, 분류기 평가는 세션당 모델 호출 비용이 발생합니다. 하지만 판사와 달리 범용 모델이 아닌 작고 단일 목적의 모델이므로, 더 빠르고 저렴합니다 — 단, 스스로를 설명하지 않습니다. 추론 과정이 필요하다면 [judge](/ko/evaluations/judge)를 사용하세요.
</Note>

## 어떤 것을 선택해야 하나요?

| 질문 | 사용 |
| --- | --- |
| 도구 호출이 몇 번이었나요? | 코드 |
| 세션이 30초 미만이었나요? | 코드 |
| 고객이 긴급함을 표현했나요? | **분류기** |
| 어떤 팀이 처리해야 하나요: 청구, 기술, 또는 영업? | **분류기** |
| 고객이 얼마나 불만스러워했나요? | **분류기** |
| 답변이 실제로 올바른가요? | **판사(judge)** |
| 에스컬레이션 정책을 따랐나요, 그 이유는 무엇인가요? | **판사(judge)** |

경험 법칙: **셀 수 있는 것 → 코드, 나열할 수 있는 답변 → 분류기, 설명이 필요한 것 → 판사(judge).**

사전에 결정할 필요는 없습니다. 측정하고 싶은 내용을 설명하면 어시스턴트가 선택하고, 어떤 것을 선택했는지와 이유를 알려주며, 변경도 가능합니다.

## 두 가지 질문 유형

### `noul` — 이것이 참인가요?

두 가지 답변이 있으며, 둘 다 설명합니다. 결과는 "참" 설명이 맞을 확률입니다:

```json
{
  "instructions": "Did the assistant promise a refund without first checking the refund policy?",
  "criteria": {
    "true":  "A refund was promised or issued with no prior policy check or approval",
    "false": "No refund was promised, or every refund followed a policy check"
  }
}
```

양쪽을 모두 설명하세요. "긴급함이 표현되지 않음"도 실제 답변이며, 그렇게 명시하면 반대쪽 답변이 더 명확해집니다.

### `score` — 이것이 얼마나 많이 해당하나요?

순서가 있는 루브릭으로, **최저부터 시작**합니다. 결과는 세션이 루브릭에서 어느 위치에 해당하는지를 0–1로 재조정한 값입니다:

```json
{
  "instructions": "How frustrated is the customer?",
  "criteria": ["Calm", "Frustrated", "Very angry"]
}
```

**루브릭은 세 개에서 다섯 개의 레벨로 구성되며, 모두 달라야 합니다.** 두 제한 모두 스타일이 아닌 측정의 문제입니다:

- **두 개의 레벨**은 `noul`이 이미 더 잘 처리하는 것으로 축소되며, **다섯 개 이상**이면 모델이 확실한 답 대신 중간으로 쏠리게 됩니다. 동일한 세션에 대해 같은 질문을 두 개 레벨로 채점하면 0.00, 세 개 레벨이면 0.01, 열 개 레벨이면 0.55가 나왔습니다.
- **반복된 레벨**은 답을 임의로 나눕니다. 명백히 화난 세션이 `["Calm", "Frustrated", "Very angry"]`에서는 1.00으로 채점되었지만, `["Angry", "Angry", "Angry"]`에서는 0.66으로 채점되었습니다 — 형식상으로는 올바른 숫자이지만 아무 의미가 없습니다.

순서가 없는 범주 — "청구, 기술, 또는 영업" — 는 루브릭이 아닙니다. 각 범주에 대해 `noul`로 질문하거나 판사(judge)를 사용하세요.

## 결과 읽기

분류기는 판사(judge)와 똑같이 0에서 1 사이의 **점수**를 생성하므로, 차트, 필터, 알림 트리거 방식도 동일합니다. 알아두어야 할 두 가지 차이점이 있습니다:

- **추론 과정이 없습니다.** 해당 필드는 의도적으로 비어 있습니다. 이 모델은 스스로를 설명하지 않으며, 설명을 만들어 내는 것은 기능이 아닌 조작이 됩니다.
- **불확실성이 표시됩니다.** `score` 질문은 자체 신뢰도를 보고하며, 모델이 확신하지 못한 결과는 `low_confidence`로 태그됩니다 — "어떤 것을 사람이 검토해야 하는가"는 추측이 아닌 필터가 됩니다. `noul` 질문은 신뢰도를 보고하지 않으므로 태그가 붙지 않습니다.

매우 긴 세션은 발췌하여 읽고 결합됩니다. 세션이 너무 길어 전체를 읽을 수 없을 때, 결과는 생략된 턴 수를 표시합니다 — 일부 세션에 대한 판단이 전체에 대한 판단인 것처럼 표시되는 일은 절대 없습니다.

## 제한

- **세 개에서 다섯 개의 루브릭 레벨, 모두 고유해야 합니다.** 위 내용 참조; 두 경계 모두 작성 시점에 적용됩니다.
- **평가당 하나의 질문.** 두 가지를 질문하면 두 개의 평가가 생성되며, 차트에서도 그것이 올바른 방식입니다.
- **질문을 편집하면 새 버전이 게시됩니다.** 이전 점수와 새 점수는 비교할 수 없으므로, 하나의 추세선으로 혼합하지 않고 별도로 유지됩니다.
- **분류기는 항상 점수를 생성하며**, 메트릭이나 어서션은 생성하지 않습니다.
- **추론 과정 없음**, 위 내용 참조. 숫자가 "왜?"라는 질문을 유발할 것 같다면, 대신 판사(judge)를 작성하세요.

## 테스트 및 백필

판사(judge)와 달리, 분류기 평가는 배포 전에 **테스트할 수 있습니다** — 코드 평가와 동일한 방식으로 실제 세션에 대해 [테스트](/ko/evaluations/test)하고, 라이브로 전환하기 전에 점수를 확인하세요.

또한 이미 보유한 세션에 대해 [백필](/ko/evaluations/deploy#score-sessions-you-already-have)도 가능합니다. 세션당 모델 호출 비용이 발생하므로, 모든 것을 재실행하기보다는 의도적으로 기간을 설정하세요.
