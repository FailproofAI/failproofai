이 문서는 자체 키를 사용한 [Jev 정책](/ko/policies/jev)의 프로바이더 및 구성 참조입니다. 정규식 정책은 문자열을 매칭합니다. 정규식은 `rm -rf build/`처럼 사용자가 직접 요청한 명령과 `rm -rf ~`처럼 계획에 슬쩍 끼어든 명령을 구분하지 못하기 때문에, 한 곳에서는 너무 많이 차단하고 다른 곳에서는 너무 적게 차단하게 됩니다. TypeSafe의 분류기인 **Jev**는 실제로 사용자가 요청한 내용과 대조하여 호출을 읽고, 하나의 빠른 요청으로 일련의 예/아니오 질문에 답합니다.

자체 Jev 엔드포인트와 키가 구성되면, Failproof AI는 각 도구 호출에 대해 정규식 정책과 **함께** Jev에 질의하며, Jev가 정규식 정책을 대체하지는 않습니다:

- **하드** 정책의 거부는 최종입니다. Jev가 이를 해제할 수 없습니다. 모든 정책은 명시적으로 검토 가능으로 표시되고 해당 정책을 커버하는 Jev 검사를 명시하지 않는 한 하드로 처리됩니다. 따라서 아무것도 명시하지 않은 커스텀, 팩, 클라우드 정책은 하드이며, 항상 활성화된 자체 보호 가드도 항상 하드입니다.
- **검토 가능** 정책의 거부는 해제될 수 있지만, Jev가 해당 정책이 커버하는 정확한 우려 사항에 대해 질의를 받고 "여기에는 아무것도 없음" 또는 "사용자가 이를 요청했음"이라고 답한 경우에만 가능합니다. 우려 사항이 실재하고 사용자가 해당 호출을 요청하지 않았다고 판단하는 검사는, 그 자체 판정이 경고에 불과하더라도 거부를 유지합니다 — 도구 호출 전에는 경고가 에이전트를 멈추지 않기 때문입니다. 그리고 해당 검사가 거부 가능한 종류(시크릿 노출, 자격증명 유출, 파괴적 삭제 등)인 경우, 해당 호출에서 아무것도 해제되지 않습니다.
- 호출이 사용자가 지시한 작업의 단계이고 그 이상 도달하지 않는 경우, 차단이 **경고**로 바뀔 수 있습니다: Jev는 자체 거부를 경고로 완화하고, 호출에서 실제로 무엇이 잘못되었는지를 명시한 해당 경고가 정책의 차단을 대체합니다.
- Jev는 정규식으로 설명할 수 없는 위해에 대해 자체적으로 경고하거나 거부할 수도 있습니다.
- Jev가 답할 수 없는 경우(타임아웃, 속도 제한, 서버 오류, 크레딧 없음, 예상치 못한 모델 버전), 해당 호출은 Jev 없이와 똑같이 정규식 결과를 받습니다.
- Jev는 전체 호출을 읽고 정확한 우려 사항에 대해 질의를 받지 않는 한, 정책만으로보다 호출을 더 허용적으로 만들지 않습니다. 그에 미치지 못하는 경우 — 전체를 전송하기에 너무 큰 호출, 의심되는 인젝션 — 는 허가를 철회하고 모든 거부를 유지합니다.

<Note>
Jev 구성이 없으면 아무것도 변경되지 않습니다: 훅은 항상 그래왔던 것처럼 정규식 정책을 그대로 실행합니다. 구성 자체가 옵트인의 전부입니다.
</Note>

<Tip>
FailproofAI Cloud를 사용 중이신가요? 자체 키가 필요하지 않습니다: `jev:evaluate`를 가진 키로 연결된 머신은 조직 플랜으로 Jev를 사용할 수 있습니다. [FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud)를 참조하세요.
</Tip>

## 시작하기 전에

에이전트가 실행되는 머신에 **failproofai 1.0.8-beta.0 이상**을 설치하고 [지원되는 하네스](/ko/reference/harnesses)에 훅을 연결하세요. 새 머신이라면 [빠른 시작](/ko/start/quickstart)을 따르거나, Cloud를 사용하지 않는다면 [로컬 적용 설정](/ko/start/setup#enforce-locally)을 따르세요. `failproofai --version`으로 설치된 CLI를 확인하세요.

아래 프로바이더에서 API 키를 받거나, 호환 가능한 엔드포인트와 해당 키를 준비하세요. Jev는 `PreToolUse` 또는 `PermissionRequest` 게이트에서 명명된 도구 호출을 검토합니다. 자체 판정을 내릴 수 있지만, 기존 정책 거부를 해제하려면 [검토 가능](/ko/policies/authority)으로 표시된 설치된 정책도 필요합니다. 하드 정책 거부는 최종으로 유지됩니다.

## 프로바이더 선택

Jev는 다섯 가지 경로를 통해 접근할 수 있습니다. 그 중 하나의 키를 가져오세요.

| 프로바이더 | `--provider` | 엔드포인트 | 기본 모델 | 비고 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 정확한 버전 고정. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 요청은 제로 데이터 보존 엔드포인트로만 라우팅되며, 다른 프로바이더로의 폴백 없음. `typesafe/jev-1.13-20260917`과 같은 날짜 버전을 보고함. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jev를 별칭으로만 명명하므로 응답한 버전이 미검증으로 기록됨. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id` 필요. 키당 초당 약 6회 호출이 HTTP 429 전에 측정됨. |
| 자체 엔드포인트 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafe의 요청 본문을 수용하고 어떤 모델이 답했는지 보고하는 엔드포인트. `https`만 허용; 로컬 테스트를 위해 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`는 허용됨. |

<Warning>
Vercel의 자체 bring-your-own-key 기능을 사용하면 실패한 요청이 Vercel의 자격증명으로 조용히 재시도됩니다. 모든 호출이 자체 TypeSafe 계정에만 청구되고 그 계정에서만 확인되어야 한다면, TypeSafe를 직접 사용하세요.
</Warning>

## 설정

명령 하나, 엔드포인트와 키. 기존 정책이 호출을 계속 결정하는 동안 Jev의 판정을 검사할 수 있도록 `observe` 모드로 시작하세요:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL이 프로바이더를 결정합니다

프로바이더를 명시할 필요가 없습니다: URL의 **호스트**가 프로바이더를 결정합니다.

| URL 호스트 | 프로바이더 | 추가 필요 사항 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| 그 외 호스트 | `custom` | — 제공한 URL이 베이스 URL |

이로부터 세 가지가 따릅니다:

- **프로바이더 자체 API인 URL은 오버라이드를 쓰지 않습니다.** `--url https://api.typesafe.ai/v1`은 `--provider typesafe`와 정확히 같은 구성을 생성합니다. 알려진 프로바이더에서 다른 경로나 호스트를 지정하면 `--base-url`이 저장하는 것처럼 베이스 URL로 저장됩니다.
- **`--provider`는 여전히 추론을 오버라이드합니다.** 이를 통해 자체 호스트에서 프로바이더의 API를 사용하는 프록시에 접근할 수 있습니다: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **호스트와 모순되는 `--provider`는 거부됩니다.** 추측하지 않습니다. `--provider openrouter --url https://api.typesafe.ai/v1`은 아무것도 쓰지 않고 그 이유를 설명합니다: 두 설정이 키가 전송될 위치에 대해 불일치합니다. `jev setup --base-url`과 대시보드의 Jev 설정에서도 동일하게 거부됩니다. (`--provider custom`은 모순이 아닙니다 — "이 URL을 그 자체로 취급"을 의미합니다 — 단, 계정별 엔드포인트에 커스텀 경로가 도달할 수 없는 Cloudflare 호스트는 예외입니다.)

`--url`은 구성 파일의 `baseUrl`과 동일하게 검증되며 같은 문구로 거부됩니다: `https`, 또는 임의 모드에서 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`. 위험: 루프백 서버는 아무것도 인증하지 않으므로, 서버가 다운된 동안 다른 로컬 프로세스가 해당 포트를 점유하여 응답할 수 있습니다; 로컬 테스트 외에는 `https`를 사용하세요.

### 키

`--key-stdin`으로 파이프하거나, 터미널에서 해당 플래그 없이 명령을 실행하고 마스크된 프롬프트에 키를 붙여넣으세요. 어느 방식이든 구성 파일에 직접 저장되며 다시 출력되지 않습니다.

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup`은 동일한 플래그를 사용하며 모든 항목의 긴 형식입니다: URL 대신 프로바이더를 명시하고 싶을 때는 `setup --provider <kind>`를 사용하세요.

### `--token`과 비용

`--token <token>`은 키를 커맨드 라인에 넣습니다. 이는 머신을 가장 빠르게 구성하는 방법이지만, 구성 파일 외에 키가 남는 유일한 방식입니다:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
커맨드 라인 인수는 이후 셸의 히스토리 파일에 남으며, 명령이 실행되는 동안 프로세스 목록에 나타납니다 — 현재 사용자로 실행되는 모든 프로세스가 `/proc`에서 읽을 수 있습니다. `setup`은 `--token`이 사용될 때마다 이를 알립니다. 공유 머신, 녹화된 세션, 또는 히스토리 파일이 동기화되는 환경에서는 `--key-stdin`을 사용하세요; 이 방식으로 전달한 키는 중요하다면 교체하세요.
</Warning>

`--token`, `--key-stdin`, `--key-from-env`는 상호 배타적입니다: 하나만 제공하세요.

그런 다음 소규모 라이브 요청을 하나 보내 키, 엔드포인트, 그리고 어떤 Jev가 응답했는지 확인하세요:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`는 타임아웃 이후에 답이 도착하거나(`timeout`으로 모든 훅이 정규식으로 폴백됨) 검사 질문에 잘못 답하면 1을 반환하고 제목에 이를 표시합니다.

훅은 매 도구 호출 시 구성을 읽으므로 다음 호출부터 적용됩니다. 데몬 유무와 관계없이 재시작할 필요가 없습니다.

## 동작 확인

```bash
failproofai jev status
failproofai jev status --json
```

`status`는 프로바이더, 엔드포인트, 모델, 모드, 구성 파일과 그 권한을 표시하며 키는 절대 표시하지 않습니다. 그 아래에는 최근 활동을 요약합니다: Jev가 평가한 호출 수, 정규식으로 폴백된 횟수와 그 이유, 지연 시간, 그리고 해제된 검토 가능 정책들.

## 실제 호출 검증

훅이 연결된 에이전트에서 새 세션을 시작하세요. 파일 읽기 도구로 `README.md`를 읽고 제목을 보고하도록 요청하세요. 세션에 해당 도구 호출이 포함되었는지 확인한 다음 `failproofai jev status`를 다시 실행하세요: 최근 평가된 호출 수가 증가해야 합니다. [로컬 대시보드](/ko/reference/local-dashboard#review-policy-activity)에서 **정책 → 활동**을 열어 호출의 Jev 판정과 모드를 검사하세요. observe 모드에서는 정책 결과가 여전히 호출을 결정합니다. 검토 가능 정책이 매칭되고 Jev가 명명된 모든 검사를 통과했을 때만 허가가 나타납니다; 일반적인 읽기 작업에는 해제할 정책이 없을 수도 있습니다.

## Observe 모드

`enforce`가 기본값입니다. Jev가 어떤 결정도 변경하지 않도록 관찰만 하려면 `observe`로 전환하세요: Jev는 여전히 질의를 받고 판정이 기록되지만, 적용되는 것은 정규식 결과입니다.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`는 구성 — 엔드포인트와 키 — 을 유지하고 Jev 질의를 중단합니다: 훅은 구성 없이와 똑같이 정규식 정책을 실행하며, `failproofai jev status`는 "off (switched off)"를 표시합니다. `--mode observe` 또는 `--mode enforce`로 다시 전환할 수 있습니다.

동일한 프로바이더로 `setup`을 재실행하면 저장된 키가 유지되므로, 모드 전환은 플래그 하나면 됩니다. 프로바이더를 전환하면 처음부터 다시 시작하고 해당 프로바이더의 키를 요청합니다. 요청을 다른 호스트로 이동하는 `--base-url`도 마찬가지입니다: 저장된 키는 최초 제공된 호스트 또는 해당 프로바이더의 자체 API에만 전송됩니다.

## 구성 파일

모든 것은 `setup`이 작성하는 파일 하나, `~/.failproofai/jev.json`에 저장됩니다:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 필드 | 의미 |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` 또는 `custom` — 또는 `failproofai`(이 경우 키는 이 파일이 아닌 FailproofAI Cloud 연결에서 가져옴, [FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud) 참조). |
| `apiKey` | `Authorization: Bearer <key>`로 전송됨. |
| `baseUrl` | `custom`의 경우 필수; 그 외에는 프로바이더의 API 베이스를 대체함. `https`여야 함. `localhost`에 대한 일반 `http`는 `mode: observe`에서만 허용됨: 로컬 포트를 인증하는 것이 없으므로, 프록시가 다운된 동안 머신의 모든 프로세스(판정 대상인 에이전트 포함)가 그 자리를 대신할 수 있음. |
| `accountId` | Cloudflare 전용: 32자 소문자 16진수. |
| `model` | 프로바이더의 기본 모델 ID를 대체함. 버전이 명시된 ID는 Jev 1.13을 명명해야 함. API 키처럼 보이는 값은 거부됨(반복 출력되지 않음), 따라서 `--model`에 붙여넣은 키는 저장되거나 모델로 전송되지 않음. |
| `timeoutMs` | 도구 호출이 Jev를 기다리다가 정규식 결과를 사용하기 전까지의 시간. 100–10000, 기본값 3000. |
| `mode` | `enforce`(기본값), `observe`, 또는 `off`(구성 유지, Jev 실행 없음). |

세 가지 규칙이 이를 보호합니다:

- **소유자 전용.** 권한 `0600`으로 작성됩니다. 다른 사용자나 그룹이 읽거나 쓸 수 있는 사본은 **거부**되며, `chmod 600 ~/.failproofai/jev.json`을 실행하거나 `setup`을 다시 실행할 때까지 훅은 정규식으로 폴백합니다. 디렉터리도 확인됩니다: 파일 자체 권한이 어떻든 그 디렉터리에 쓸 수 있는 사람은 파일을 교체할 수 있으므로, `~/.failproofai`는 다른 사람이 **쓸 수** 없어야 합니다. `setup`은 그런 쓰기 비트를 발견하면 제거합니다. `failproofai jev status`는 구성이 거부된 경우와 파일에 명시된 엔드포인트를 표시합니다: 다른 누군가가 변경했을 수 있으므로 `chmod` 전에 자신의 것인지 확인하세요. 그런 파일에서 `setup`을 재실행하면 저장된 키는 프로바이더의 자체 API에만 전송됩니다; 파일에 명시된 다른 엔드포인트는 키를 다시 요구합니다(`--key-stdin`), 또는 `--base-url default`로 요청을 프로바이더로 되돌리세요.
- **전역 전용.** 리포지터리는 Jev를 활성화하거나, 다른 엔드포인트를 지정하거나, 모델을 선택할 수 없습니다: 프로젝트 내부의 `.failproofai/jev.json`은 무시되며, 프로바이더, URL, 모델, 계정 ID는 오직 그 파일에서만 읽힙니다 — 리포지터리의 에이전트 설정이 설정할 수 있는 환경 변수에서는 절대 읽히지 않습니다. (`FAILPROOFAI_HOME`은 이를 우회하는 방법이 아닙니다: Jev만 별도로 리디렉션하는 것이 아니라 정책을 포함한 전체 failproofai 디렉터리를 이동합니다.)
- **키만 환경에서 가져올 수 있습니다.** 파일에 `apiKey`가 없으면 `FAILPROOFAI_JEV_API_KEY`가 해당 세션에 대해 키를 제공합니다(`setup --key-from-env`는 그런 파일을 작성함). 파일에 저장된 키를 대체하지 않으며, 파일 없이 Jev를 활성화할 수 없습니다. 변수가 설정되지 않은 경우 해당 셸에서 Jev는 단순히 꺼집니다: `failproofai jev status`가 이를 알리고, 0을 반환하며, 구성을 그대로 둡니다(`status --json`은 `"reason": "no-env-key"`와 함께 `"status": "key-missing"`을 보고함). `failproofaid` 데몬은 셸 환경을 보지 못하므로, `failproofai config`로 설정한 머신에서는 파일에 키를 보관하세요.

## 어떤 Jev가 응답하는가

Failproof AI의 판정 임계값은 Jev 1.13에 맞춰 보정되었으므로, 해당 패밀리에서 온 경우에만 답이 사용됩니다: `jev-1.13.x`, 또는 OpenRouter의 `typesafe/jev-1.13-<date>`. 프로바이더가 Jev를 별칭으로만 명명하고 버전을 보고하지 않는 경우(Vercel, 그리고 Cloudflare가 명시하지 않을 때), 답은 사용되고 미검증으로 기록됩니다. `custom` 엔드포인트는 응답한 모델을 보고해야 합니다; 유일한 예외는 그 엔드포인트에 대해 구성한 버전이 없는 `--model` 이름으로, 이것이 에코백되면 동일하게 미검증으로 기록됩니다. 다른 버전을 보고하는 답이나 `custom` 답이 아무것도 보고하지 않는 경우는 사용되지 않습니다: 해당 호출은 `model-mismatch` 이유로 정규식으로 폴백됩니다.

## Jev가 답할 수 없을 때

다음 각각의 경우 해당 호출에 대한 정규식 결과로 폴백하고 그 이유가 기록되며, `failproofai jev status`에서 합계를 볼 수 있습니다:

| 이유 | 원인 |
| --- | --- |
| `timeout` | `timeoutMs` 내에 답이 없음. |
| `http-429` | 프로바이더가 키를 속도 제한함. |
| `rate-limited` | Failproof AI 자체 제한기가 호출을 전송 전에 보류함: 초당 5회, 최대 5회 버스트, 그리고 프로바이더가 `429`로 응답한 직후 잠시 없음. 프로바이더가 아님. |
| `http-500`, `http-502`, `http-503`, … | 프로바이더에서 서버 오류 발생. 정확한 상태가 기록됨. |
| `out-of-credits` | HTTP 402: 프로바이더 계정에 크레딧이 없음. |
| `provider-refused` | Cloudflare에서 "Model execution failed (Payment error)"를 읽은 HTTP 402: 프로바이더가 이 요청에 대해 모델 실행을 거부함. 보통 청구 문제가 아니므로 크레딧을 추가해도 해결되지 않음. |
| `http-401`, `http-403` | 키가 거부됨. |
| `http-404` | `<base>/systemone`에서 아무것도 서비스되지 않음, 베이스 URL이 잘못됨 — `/systemone`이 베이스에 추가되며, 모든 프로바이더는 버전 루트에서 이를 서비스함. `failproofai jev models`는 엔드포인트가 실제로 서비스하는 것을 보여줌. |
| `network` | 엔드포인트에 도달할 수 없음. |
| `http-301`, `http-302`, `http-307`, `http-308` | 엔드포인트가 리디렉션으로 응답함. 리디렉션은 절대 따르지 않으므로, 답은 항상 구성의 URL에서만 옵니다; `--base-url`을 최종 URL로 설정하세요. |
| `malformed` | 엔드포인트가 응답했지만 Jev 답이 아님 — JSON이 아닌 본문, 또는 답이 없는 본문. |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflare의 엔벨로프가 실패를 보고하거나, 아직 완료되지 않은 작업. |
| `model-mismatch` | 1.13 이외의 Jev 버전이 응답하거나, `custom` 엔드포인트가 어떤 모델이 응답했는지 말하지 않음. |
| `request-cut` | **장애가 아닙니다.** Jev가 응답했지만 호출의 일부만 보여졌으므로, 그 답이 아무것도 해제하지 않습니다. [Jev가 답했지만 전체 호출에 대해서는 아닌 경우](#when-jev-answered-but-not-on-the-whole-call)를 참조하세요. |

`failproofai jev status`는 `upstream-error`(답이 프로바이더 자체 오류를 담고 있음)나 `config` 같은 드문 이유도 표시할 수 있으며, 명명할 수 없는 이유는 `other`로 합산합니다.

`request-cut`은 `failproofai jev status`가 나머지와 함께 집계하고, 모든 거부를 그대로 유지하기 때문에 이 표에 포함됩니다. 여기서 프로바이더에 대해 아무것도 말하지 않는 유일한 이유입니다: 요청이 도착했고 Jev가 답했습니다. 위의 모든 행과 달리 그 답은 여전히 카운트됩니다 — Jev 자체의 거부나 경고는 버려지지 않고 정규식 결과 위에 적용됩니다. 따라서 연속적으로 발생한다는 것은 호출이 평가자에 너무 커서 전체를 전송하지 못하는 것이지, 엔드포인트 문제가 아닙니다. 크레딧을 추가하거나 URL을 변경해도 이 숫자는 줄지 않습니다.

## Jev가 답했지만 전체 호출에 대해서는 아닌 경우

두 가지 추가 상황이 있으며, 어느 것도 Jev가 답하지 못한 것이 아닙니다. 둘 다 호출의 얼마나 많은 부분, 또는 대화의 얼마나 많은 부분이 하나의 요청에 맞았는지에 관한 것입니다.

**호출 자체의 일부가 맞지 않았습니다.** 도구 호출은 고정된 예산 내에서 전송되며, 너무 큰 호출 — 매우 큰 `Write`, 거대한 MCP 본문, 한도를 가득 채운 명령 — 은 맞는 부분만 전송됩니다. Jev는 여전히 답하고 그 답은 여전히 카운트됩니다: 자체 거부나 경고는 평소대로 적용됩니다. 그러나 호출의 일부에 대한 판정은 호출 전체에 대한 판정이 아니기 때문에, **해제**는 불가능합니다. 따라서 모든 정책 거부가 유지되며, 호출은 `request-cut` 이유로 폴백으로 기록되고 `failproofai jev status`에서 위의 이유들과 함께 집계됩니다. 이 규칙이 주는 교훈: 호출을 더 크게 만들면 허가를 잃을 수 있으며, 허가를 얻을 수는 없습니다.

**메시지가 맞지 않았습니다.** 붙여넣은 긴 프롬프트, 에이전트의 마지막 메시지, 또는 이 평가자의 자체 저장소가 이미 한도를 초과한 프롬프트. **아무것도 변경되지 않습니다**: 호출은 다른 것과 똑같이 판정되고, 해제되고, 기록되며, 폴백으로 카운트되지 않습니다. 입력한 내용의 길이가 판정을 결정하지 않으며, 잘림이 동의를 만들어낼 수 없습니다: 프롬프트가 이미 한도 초과된 상태로 도착한 경우, "당신이 이것을 요청하지 않았다"는 결론은 더 이상 도출할 수 없는 것이 되며, 하나의 결론으로 채택되지 않습니다.

두 경우의 경계선은 텍스트를 작성한 주체입니다. 호출은 에이전트의 것이고, 길이가 심각도를 줄일 수 있는 규칙은 에이전트가 사용할 수 있는 규칙이 됩니다; 프롬프트는 사용자의 것이고, 그 길이를 신호로 처리하는 것은 명세서나 스택 트레이스를 붙여넣는 행위를 불이익으로 돌리는 것에 불과합니다.

## 머신에서 나가는 것

Jev가 평가하는 각 도구 호출에 대해 프로바이더로 하나의 요청이 전송되며, 다음을 포함합니다:

- 도구 호출 자체 (API 키, 베어러 토큰, `KEY=` 할당 같은 시크릿은 편집됨);
- 최근에 입력한 프롬프트 (에이전트 하네스가 추가한 텍스트는 제거됨);
- 최신 프롬프트 이전 에이전트의 마지막 메시지 (에이전트 작성으로 레이블 표시);
- 로컬에서 계산된 사실들 (경로가 프로젝트 내부에 있는지 여부 — 첫 번째 검토된 호출 시의 세션, [세션에 고정됨](/ko/reference/jev-intent#the-project-root) — 및 현재 git 브랜치).

이것은 사용자의 키 아래, 구성의 엔드포인트로만 전송됩니다.

## 끄기

```bash
failproofai jev remove
```

이 명령은 `~/.failproofai/jev.json`을 삭제합니다. 다음 도구 호출부터 훅은 이전과 똑같이 정규식 정책을 실행합니다. `~/.failproofai/state/semantic/` 아래의 세션별 저장소 (`sessions/`의 기록된 프롬프트, `roots/`의 프로젝트 루트)는 그대로 유지되며 시간이 지나면 만료됩니다. Jev 질의를 중단하되 구성을 유지하려면 `failproofai jev setup --mode off`를 사용하세요.

## 명령 참조

| 명령 | 결과 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 명령 하나로 구성; 프로바이더는 URL 호스트에서 결정됨 |
| `failproofai jev --url <url> --token <token>` | 동일, 키를 커맨드 라인에 — 히스토리와 프로세스 목록에 보임 |
| `failproofai jev setup --provider <kind> --key-stdin` | stdin으로 파이프된 키로 구성 작성 |
| `failproofai jev setup --provider <kind>` | 동일, 마스크된 프롬프트에서 키 요청 |
| `failproofai jev setup --key-from-env` | 키 저장 없음; 세션당 `FAILPROOFAI_JEV_API_KEY` 읽기 |
| `failproofai jev setup --mode observe` | 저장된 키를 유지하며 모드 전환 (`enforce`, `observe` 또는 `off`) |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 모델 또는 API 베이스 오버라이드; `default`는 오버라이드 해제 |
| `failproofai jev setup --timeout-ms <n>` | 호출당 예산 변경 |
| `failproofai jev status [--json]` | 구성, 권한 및 최근 활동; 키는 절대 표시 안 함 |
| `failproofai jev test [--json]` | 라이브 요청 하나: 지연 시간과 응답한 버전 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 해당 엔드포인트의 `/models`가 보고하는 모델 ID, 구성된 것 표시 |
| `failproofai jev remove` | 구성 삭제; Jev 꺼짐 |
