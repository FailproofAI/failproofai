이 문서는 자체 키를 사용하는 [Jev 정책](/ko/policies/jev)의 제공자 및 구성 참조입니다. 정규식 정책은 문자열을 매칭합니다. 정규식은 사용자가 요청한 `rm -rf build/`와 플랜에 슬며시 끼어든 `rm -rf ~`를 구분할 수 없기 때문에, 어떤 곳에서는 지나치게 많이 차단하고 다른 곳에서는 너무 적게 차단합니다. TypeSafe의 분류기인 **Jev**는 실제로 무엇을 요청했는지와 대조하여 툴 호출을 읽고, 하나의 빠른 요청에서 해당 호출에 대한 일련의 예/아니오 질문에 답변합니다.

자체 Jev 엔드포인트와 키를 구성하면 Failproof AI는 정규식 정책 대신이 아닌, **함께** 각 툴 호출에 대해 Jev에 질문합니다:

- **하드** 정책의 거부는 최종적입니다. Jev는 이를 해제할 수 없습니다. 모든 정책은 검토 가능으로 명시적으로 표시되고 적용되는 Jev 검사를 명명하지 않는 한 하드입니다. 따라서 아무 말도 없는 커스텀, 팩 또는 Cloud 정책은 하드이며, 항상 켜져 있는 자체 보호 가드는 항상 하드입니다.
- **검토 가능** 정책의 거부는 해제될 수 있지만, Jev가 해당 정책이 다루는 정확한 우려 사항에 대해 질문을 받고 "여기엔 아무것도 없습니다" 또는 "사용자가 이를 요청했습니다"라고 답변한 경우에만 가능합니다. 사용자가 해당 호출을 요청하지 않았을 때 우려 사항이 실재한다는 것을 발견한 검사는, 자체 판정이 경고에 불과하더라도 거부를 유지합니다 — 툴 호출 이전에는 경고가 에이전트를 중단시키지 않기 때문입니다. 그리고 해당 검사가 거부할 수 있는 종류(시크릿 노출, 자격증명 유출, 파괴적 삭제 등)에 해당하면, 해당 호출에서는 아무것도 해제되지 않습니다.
- 호출이 사용자가 지시한 작업의 단계이고 그 이상으로 나아가지 않을 때, 차단은 여전히 **경고**로 바뀔 수 있습니다: Jev는 자체 거부를 경고로 완화하며, 해당 경고 — 호출의 실제 문제점을 명명하는 — 가 정책의 차단을 대체합니다.
- Jev는 또한 정규식이 설명하지 못하는 위험에 대해 자체적으로 경고하거나 거부할 수 있습니다.
- Jev가 응답할 수 없는 경우(타임아웃, 속도 제한, 서버 오류, 크레딧 없음, 예상치 못한 모델 버전), 해당 호출은 Jev 없이와 정확히 동일하게 정규식 결과를 받습니다.
- Jev는 전체 호출을 읽고 정확한 우려 사항에 대해 질문받지 않는 한, 정책만 있을 때보다 호출을 더 허용적으로 만들지 않습니다. 그 미만의 경우 — 전체를 전송하기에 너무 큰 호출, 주입 의심 — 은 모든 허가를 철회하고 모든 거부를 유지합니다.

<Note>
Jev 구성 없이는 아무것도 변경되지 않습니다: 훅은 항상 그래왔던 것처럼 정규식 정책을 정확히 실행합니다. 구성 자체가 전체 옵트인입니다.
</Note>

<Tip>
FailproofAI Cloud를 사용 중이신가요? 자체 키가 필요하지 않습니다: `jev:evaluate`를 보유한 키로 연결된 머신은 조직의 플랜에서 Jev를 사용할 수 있습니다. [FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud)를 참조하세요.
</Tip>

## 시작하기 전에

에이전트가 실행되는 머신에 **failproofai 1.0.8-beta.0 이상**을 설치하고 [지원되는 하네스](/ko/reference/harnesses)에 훅을 연결하세요. 새 머신이라면 [빠른 시작](/ko/start/quickstart)을, Cloud를 사용하지 않는 경우 [로컬 적용 설정](/ko/start/setup#enforce-locally)을 따르세요. `failproofai --version`으로 설치된 CLI를 확인하세요.

아래 제공자에서 API 키를 받거나, 호환 가능한 엔드포인트와 해당 키를 준비하세요. Jev는 `PreToolUse` 또는 `PermissionRequest` 게이트에서 명명된 툴 호출을 검토합니다. 자체 판정을 내릴 수 있지만, 기존 정책 거부를 해제하려면 [검토 가능](/ko/policies/authority)으로 표시된 설치된 정책도 필요합니다. 하드 정책 거부는 최종적으로 유지됩니다.

## 제공자 선택

Jev는 다섯 가지 경로를 통해 접근할 수 있습니다. 그 중 하나의 키를 가져오세요.

| 제공자 | `--provider` | 엔드포인트 | 기본 모델 | 참고 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 정확한 버전 고정. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 요청은 제로 데이터 보존 엔드포인트로만 라우팅되며, 다른 제공자로의 폴백은 없습니다. `typesafe/jev-1.13-20260917`과 같은 날짜가 포함된 버전을 보고합니다. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jev를 별칭으로만 명명하므로, 응답한 버전은 미확인으로 기록됩니다. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id`가 필요합니다. 키당 약 초당 6회의 호출이 HTTP 429 이전에 측정되었습니다. |
| 자체 엔드포인트 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafe의 요청 본문을 수락하고 어떤 모델이 응답했는지 보고하는 모든 엔드포인트. `https`만 가능; 로컬 테스트를 위해 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`는 허용됩니다. |

<Warning>
Vercel의 자체 BYOK(bring-your-own-key) 기능을 사용할 경우, 실패한 요청이 Vercel의 자격증명으로 자동 재시도됩니다. 모든 호출이 자신의 TypeSafe 계정에만 청구되고 확인되어야 한다면 TypeSafe를 직접 사용하세요.
</Warning>

## 설정하기

명령 하나로 엔드포인트와 키를 설정합니다. 기존 정책이 호출을 계속 결정하는 동안 Jev의 판정을 검사할 수 있도록 `observe` 모드로 시작하세요:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL이 제공자를 결정합니다

제공자를 명시적으로 지정할 필요가 없습니다: URL의 **호스트**가 어떤 제공자인지를 나타냅니다.

| URL 호스트 | 제공자 | 추가 필요 사항 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| 다른 모든 호스트 | `custom` | — 제공한 URL이 기본 URL |

여기서 세 가지가 따릅니다:

- **제공자 자체 API인 URL은 재정의를 기록하지 않습니다.** `--url https://api.typesafe.ai/v1`은 `--provider typesafe`가 만들었을 구성과 정확히 동일하게 생성합니다. 알려진 제공자에서 다른 경로나 호스트를 지정하면 `--base-url`이 저장하는 것처럼 기본 URL로 저장됩니다.
- **`--provider`는 여전히 추론을 재정의합니다.** 이는 자체 호스트에서 제공자의 API를 사용하는 프록시에 접근하는 방법입니다: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **호스트와 모순되는 `--provider`는 거부됩니다.** `--provider openrouter --url https://api.typesafe.ai/v1`은 아무것도 기록하지 않고 이유를 설명합니다: 두 지정이 키가 전송될 위치에 대해 일치하지 않습니다. `jev setup --base-url`과 대시보드의 Jev 설정에서도 동일한 쌍이 거부됩니다. (`--provider custom`은 모순이 아닙니다 — "이 URL 자체로 처리"를 의미합니다 — 단, 커스텀 경로가 접근할 수 없는 계정별 엔드포인트를 가진 Cloudflare 호스트는 예외입니다.)

`--url`은 구성 파일의 `baseUrl`과 동일하게 검증되며, 동일한 이유로 거부됩니다: `https`, 또는 모든 모드에서 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`. 위험: 루프백 서버는 인증하는 것이 없으므로, 다운된 동안 다른 로컬 프로세스가 포트를 점유하고 응답할 수 있습니다; 로컬 테스트 외부에서는 `https`를 사용하세요.

### 키

`--key-stdin`으로 파이프하거나, 터미널에서 명령을 실행하고 마스크된 프롬프트에서 키를 붙여넣으세요. 어느 방법이든 키는 구성 파일에 바로 저장되며 다시 출력되지 않습니다.

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup`은 동일한 플래그를 받으며, URL보다 제공자를 명시하고 싶을 때는 `setup --provider <kind>`를 사용하는 전체 형식입니다.

### `--token`과 비용

`--token <token>`은 키를 커맨드 라인에 넣으며, 이는 머신을 구성하는 가장 빠른 방법이지만 구성 파일 외의 다른 곳에 키를 남기는 유일한 방법입니다:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
커맨드 라인 인수는 이후 쉘 히스토리 파일에 남으며, 명령이 실행되는 동안 프로세스 목록에 표시됩니다 — `/proc`에서 현재 사용자로 실행 중인 모든 것이 읽을 수 있습니다. `setup`은 `--token`이 사용될 때마다 이를 알립니다. 공유 머신, 녹화된 세션, 또는 히스토리 파일이 동기화되는 곳에서는 `--key-stdin`을 선호하세요; 이 방법으로 전달한 키는 중요하다면 교체하세요.
</Warning>

`--token`, `--key-stdin`, `--key-from-env`는 상호 배타적입니다: 하나만 지정하세요.

그런 다음 하나의 소규모 라이브 요청을 보내 키, 엔드포인트 및 응답한 Jev를 확인하세요:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`는 응답이 타임아웃 이후에 도착하거나(`timeout`으로 모든 훅이 정규식으로 폴백함) 검사 질문에 잘못 답하면 종료 코드 1을 반환하고 제목에 표시합니다.

훅은 모든 툴 호출 시 구성을 읽으므로, 다음 호출부터 적용됩니다. 데몬 유무에 관계없이 재시작할 필요가 없습니다.

## 동작 확인

```bash
failproofai jev status
failproofai jev status --json
```

`status`는 제공자, 엔드포인트, 모델, 모드, 구성 파일 및 권한을 표시하며, 키는 절대 표시하지 않습니다. 그 아래에는 최근 활동 요약이 표시됩니다: Jev가 평가한 호출 수, 정규식으로 폴백한 횟수와 이유, 지연 시간, 그리고 해제한 검토 가능 정책들.

## 실제 호출 확인

훅이 연결된 에이전트에서 새 세션을 시작하세요. 파일 읽기 툴로 `README.md`를 읽고 제목을 보고하도록 요청하세요. 세션에 해당 툴 호출이 포함되어 있는지 확인한 후 `failproofai jev status`를 다시 실행하세요: 최근 평가된 호출 수가 증가해야 합니다. [로컬 대시보드](/ko/reference/local-dashboard#review-policy-activity)에서 **정책 → 활동**을 열어 호출의 Jev 판정과 모드를 검사하세요. observe 모드에서는 정책 결과가 여전히 호출을 결정합니다. 검토 가능 정책이 매칭되고 Jev가 명명된 모든 검사를 해제한 경우에만 허가가 나타납니다; 일반 읽기 작업에는 해제할 정책이 없을 수 있습니다.

## Observe 모드

`enforce`가 기본값입니다. Jev가 어떤 결정도 변경하지 않도록 지켜보려면 `observe`로 전환하세요: Jev는 여전히 질문을 받고 판정이 기록되지만, 적용되는 것은 정규식 결과입니다.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`는 구성 — 엔드포인트와 키 — 을 유지하고 Jev 질문을 중단합니다: 훅은 구성 없이와 정확히 동일하게 정규식 정책을 실행하며, `failproofai jev status`는 "off (switched off)"를 표시합니다. `--mode observe` 또는 `--mode enforce`로 다시 전환하세요.

동일한 제공자에 대해 `setup`을 재실행하면 저장된 키를 유지하므로 모드 전환은 플래그 하나입니다. 제공자를 변경하면 처음부터 시작하여 해당 제공자의 키를 요청합니다. 요청을 다른 호스트로 이동하는 `--base-url`도 마찬가지입니다: 저장된 키는 제공된 호스트나 해당 제공자의 자체 API에만 전송됩니다.

## 구성 파일

모든 것은 `setup`으로 작성되는 `~/.failproofai/jev.json` 파일 하나에 저장됩니다:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 필드 | 의미 |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` 또는 `custom` — 또는 `failproofai`(키가 이 파일 대신 FailproofAI Cloud 연결에서 옴, [FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud) 참조). |
| `apiKey` | `Authorization: Bearer <key>`로 전송됩니다. |
| `baseUrl` | `custom`에 필요; 그 외에는 제공자의 API 기본을 대체합니다. `https`여야 합니다. `localhost`에 대한 일반 `http`는 `mode: observe`에서만 허용됩니다: 로컬 포트를 인증하는 것이 없으므로, 프록시가 다운된 동안 에이전트를 포함한 머신의 모든 프로세스가 대신 응답할 수 있습니다. |
| `accountId` | Cloudflare 전용: 소문자 16진수 32자리. |
| `model` | 제공자의 기본 모델 id를 대체합니다. 버전이 지정된 id는 Jev 1.13을 명명해야 합니다. API 키처럼 보이는 값은 거부됩니다(반복되지 않음), 따라서 `--model`에 붙여넣은 키는 모델로 저장되거나 전송되지 않습니다. |
| `timeoutMs` | 툴 호출이 정규식 결과를 사용하기 전에 Jev를 기다리는 시간. 100–10000, 기본값 3000. |
| `mode` | `enforce`(기본값), `observe`, 또는 `off`(구성 유지, Jev 실행 안 함). |

세 가지 규칙이 이를 보호합니다:

- **소유자 전용.** `0600` 권한으로 작성됩니다. 다른 사용자나 그룹이 읽거나 쓸 수 있는 복사본은 **거부**되며, `chmod 600 ~/.failproofai/jev.json`을 실행하거나 `setup`을 다시 실행할 때까지 훅은 정규식으로 폴백합니다. 디렉토리도 확인됩니다: `~/.failproofai`는 다른 사람이 **쓸 수 없어야** 합니다. 거기에 쓸 수 있는 사람은 파일 자체의 권한에 상관없이 파일을 교체할 수 있기 때문입니다. `setup`은 발견 시 해당 쓰기 비트를 제거합니다. `failproofai jev status`는 구성이 거부된 경우와 파일에 명명된 엔드포인트를 표시합니다: 다른 사람이 변경했을 수 있으므로, `chmod` 전에 자신의 것인지 확인하세요. 해당 파일에서 `setup`을 재실행하면 제공자의 자체 API에만 저장된 키를 유지합니다; 파일에 명명된 다른 엔드포인트는 키를 다시 필요로 합니다(`--key-stdin`), 또는 `--base-url default`로 요청을 제공자에게 다시 보내세요.
- **전역 전용.** 저장소는 Jev를 켜거나, 다른 엔드포인트를 지정하거나, 모델을 선택할 수 없습니다: 프로젝트 내부의 `.failproofai/jev.json`은 무시되며, 제공자, URL, 모델, 계정 id는 해당 파일에서만 읽힙니다 — 저장소의 에이전트 설정이 설정할 수 있는 환경에서 읽지 않습니다. (`FAILPROOFAI_HOME`은 이를 우회하는 방법이 아닙니다: Jev만 리디렉션하는 것이 아니라 정책을 포함한 전체 failproofai 디렉토리를 이동합니다.)
- **키만 환경에서 올 수 있습니다.** 파일에 `apiKey`가 없으면 `FAILPROOFAI_JEV_API_KEY`가 해당 세션에 제공합니다(`setup --key-from-env`는 이러한 파일을 작성합니다). 파일에 저장된 키를 대체하지 않으며, 파일 없이 Jev를 켤 수 없습니다. 변수가 설정되지 않은 경우 Jev는 해당 쉘에서 단순히 꺼집니다: `failproofai jev status`가 이를 알리고, 종료 코드 0을 반환하며 구성을 그대로 둡니다(`status --json`은 `"reason": "no-env-key"`와 함께 `"status": "key-missing"`을 보고합니다). `failproofaid` 데몬은 쉘 환경을 보지 않으므로, `failproofai config`로 설정된 머신에서는 키를 파일에 보관하세요.

## 응답하는 Jev

Failproof AI의 결정 임계값은 Jev 1.13을 기준으로 보정되었으므로, 해당 패밀리에서 답변이 올 때만 사용됩니다: `jev-1.13.x`, 또는 OpenRouter의 `typesafe/jev-1.13-<date>`. 제공자가 Jev를 별칭으로만 명명하고 버전을 보고하지 않는 경우(Vercel, 그리고 그렇게 말하지 않을 때의 Cloudflare), 답변이 사용되고 미확인으로 기록됩니다. `custom` 엔드포인트는 응답한 모델을 보고해야 합니다; 유일한 예외는 구성한 버전 없는 `--model` 이름으로, 에코될 때 동일한 방식으로 미확인으로 기록됩니다. 다른 버전을 보고하는 답변이나 버전을 보고하지 않는 `custom` 답변은 사용되지 않습니다: 해당 호출은 `model-mismatch` 이유로 정규식으로 폴백합니다.

## Jev가 응답할 수 없을 때

다음 각각은 해당 호출의 정규식 결과로 폴백하며 이유와 함께 기록됩니다. `failproofai jev status`가 합계를 냅니다:

| 이유 | 원인 |
| --- | --- |
| `timeout` | `timeoutMs` 내에 응답 없음. |
| `http-429` | 제공자가 키를 속도 제한했습니다. |
| `rate-limited` | Failproof AI의 자체 제한기가 전송 전에 호출을 보류했습니다: 초당 5회, 최대 5회 버스트, 제공자가 `429`를 응답한 후 잠시 없음. 제공자가 아닙니다. |
| `http-500`, `http-502`, `http-503`, … | 제공자에서 서버 오류. 정확한 상태가 기록됩니다. |
| `out-of-credits` | HTTP 402: 제공자 계정에 크레딧이 없습니다. |
| `provider-refused` | Cloudflare에서 "Model execution failed (Payment error)"를 읽는 HTTP 402: 제공자가 이 요청에서 모델 실행을 거부했습니다. 일반적으로 결제 문제가 아니므로 크레딧을 충전해도 해결되지 않습니다. |
| `http-401`, `http-403` | 키가 거부되었습니다. |
| `http-404` | `<base>/systemone`에서 제공되는 것이 없으므로 기본 URL이 잘못되었습니다 — `/systemone`이 여기에 추가되며, 모든 제공자는 버전 루트에서 제공합니다. `failproofai jev models`로 엔드포인트가 실제로 제공하는 것을 확인하세요. |
| `network` | 엔드포인트에 도달할 수 없습니다. |
| `http-301`, `http-302`, `http-307`, `http-308` | 엔드포인트가 리디렉션으로 응답했습니다. 리디렉션은 절대 따르지 않으므로 답변은 항상 구성의 URL에서만 옵니다; `--base-url`을 최종 URL로 설정하세요. |
| `malformed` | 엔드포인트가 응답했지만 Jev 답변이 아닌 경우 — JSON이 아닌 본문이거나 답변이 없는 경우. |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflare의 봉투가 실패 또는 완료되지 않은 작업을 보고했습니다. |
| `model-mismatch` | 1.13 이외의 Jev 버전이 응답했거나, `custom` 엔드포인트가 어떤 모델이 응답했는지 말하지 않았습니다. |
| `request-cut` | **서비스 중단이 아닙니다.** Jev가 응답했지만 호출의 일부만 보여주었으므로 답변이 아무것도 해제하지 않았습니다. [Jev가 응답했지만 전체 호출이 아닌 경우](#when-jev-answered-but-not-on-the-whole-call)를 참조하세요. |

`failproofai jev status`는 `upstream-error`(답변에 제공자 자체 오류 포함) 또는 `config`와 같은 일부 더 드문 이유도 표시할 수 있으며, 명명할 수 없는 이유는 `other`로 합산합니다.

`request-cut`은 `failproofai jev status`가 나머지와 함께 합산하고 모든 거부를 유지하기 때문에 이 표에 있습니다. 여기서 제공자에 대해 아무것도 말하지 않는 유일한 이유입니다: 요청이 도착했고 Jev가 응답했습니다. 위의 모든 행과 달리, 해당 답변은 여전히 중요합니다 — Jev 자체의 거부 또는 경고가 버려지는 대신 정규식 결과 위에 적용됩니다. 따라서 이 경우가 연속으로 발생하면 호출이 전체를 전송하기에 너무 크게 평가기에 도달하고 있다는 의미이지, 엔드포인트에 문제가 있거나 크레딧을 충전하거나 URL을 변경해도 해결되지 않는다는 의미가 아닙니다.

## Jev가 응답했지만 전체 호출이 아닌 경우

두 가지 더 발생할 수 있으며, 어느 것도 Jev가 응답에 실패한 것이 아닙니다. 둘 다 호출 또는 대화의 얼마나 많은 부분이 하나의 요청에 맞았는지에 관한 것입니다.

**호출 자체의 일부가 맞지 않았습니다.** 툴 호출은 고정된 예산 내에서 전송되며, 매우 큰 `Write`, 거대한 MCP 본문, 한도까지 패딩된 명령 등 크기 초과 호출은 맞는 부분만 전송됩니다. Jev는 여전히 응답하며, 그 답변은 여전히 중요합니다: 자체 거부 또는 경고가 평소와 같이 적용됩니다. 할 수 없는 것은 **해제**입니다. 호출의 일부에 대한 판정은 호출 전체에 대한 판정이 아니기 때문입니다. 따라서 모든 정책 거부는 유지되며, 호출은 `request-cut` 이유로 폴백으로 기록되고 `failproofai jev status`가 위의 이유들과 함께 합산합니다. 이것이 주는 규칙: 호출을 더 크게 만들면 허가를 잃을 수 있고, 허가를 얻을 수는 없습니다.

**메시지가 맞지 않았습니다.** 붙여넣은 긴 프롬프트, 에이전트의 마지막 메시지, 또는 이 평가기의 자체 저장소가 이미 한도를 초과한 프롬프트. **아무것도 변경되지 않습니다**: 호출은 다른 호출과 정확히 동일하게 판단, 해제, 기록되며 폴백으로 계산되지 않습니다. 입력한 내용의 길이는 절대 판정을 결정하지 않으며, 잘린 것이 동의를 만들어낼 수 없습니다: 프롬프트가 이미 한도를 초과하여 도착한 경우, "당신이 이것을 요청하지 않았습니다"는 도달 가능한 결론이 아닌 것이 됩니다.

둘의 경계는 텍스트를 누가 작성했느냐입니다. 호출은 에이전트의 것이며, 길이가 심각성을 줄이도록 허용하는 규칙은 에이전트가 사용할 수 있는 규칙이 됩니다; 프롬프트는 사용자의 것이며, 그 길이를 신호로 취급하는 것은 스펙이나 스택 트레이스를 붙여넣는 것을 벌하는 것뿐입니다.

## 머신을 떠나는 것

Jev가 평가하는 각 툴 호출에 대해 제공자에게 하나의 요청이 전송되며, 다음을 포함합니다:

- API 키, 베어러 토큰, `KEY=` 할당 등의 시크릿이 편집된 툴 호출 자체;
- 에이전트의 하네스가 추가한 텍스트가 제거된 최근에 입력한 프롬프트;
- 최신 프롬프트 이전의 에이전트 마지막 메시지(에이전트 작성으로 표시);
- 경로가 프로젝트 내에 있는지 여부 등 로컬에서 계산된 사실 — 세션의 첫 번째 검토된 호출 시점의 세션, [세션에 고정됨](/ko/reference/jev-intent#the-project-root) — 및 현재 git 브랜치.

이는 사용자 키 아래에서 구성의 엔드포인트로만 전송됩니다.

## 끄기

```bash
failproofai jev remove
```

이 명령은 `~/.failproofai/jev.json`을 삭제합니다. 다음 툴 호출부터 훅은 이전과 정확히 동일하게 정규식 정책을 실행합니다. `~/.failproofai/state/semantic/` 아래의 세션별 저장소(`sessions/`의 기록된 프롬프트, `roots/`의 프로젝트 루트)는 그대로 유지되며 만료됩니다. Jev 질문을 중단하되 구성을 유지하려면 대신 `failproofai jev setup --mode off`를 사용하세요.

## 명령 참조

| 명령 | 결과 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 명령 하나로 구성; 제공자는 URL의 호스트에서 결정됨 |
| `failproofai jev --url <url> --token <token>` | 동일, 키를 커맨드 라인에 지정 — 히스토리와 프로세스 목록에 표시됨 |
| `failproofai jev setup --provider <kind> --key-stdin` | stdin으로 파이프된 키로 구성 작성 |
| `failproofai jev setup --provider <kind>` | 동일, 마스크된 프롬프트에서 키 요청 |
| `failproofai jev setup --key-from-env` | 키를 저장하지 않음; 세션별로 `FAILPROOFAI_JEV_API_KEY` 읽기 |
| `failproofai jev setup --mode observe` | 저장된 키를 유지하며 모드 전환(`enforce`, `observe` 또는 `off`) |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 모델 또는 API 기본 재정의; `default`로 재정의 해제 |
| `failproofai jev setup --timeout-ms <n>` | 호출별 예산 변경 |
| `failproofai jev status [--json]` | 구성, 권한 및 최근 활동; 키는 절대 표시하지 않음 |
| `failproofai jev test [--json]` | 하나의 라이브 요청: 지연 시간과 응답한 버전 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 해당 엔드포인트의 `/models`가 보고하는 모델 id, 구성된 것을 표시 |
| `failproofai jev remove` | 구성 삭제; Jev 꺼짐 |
