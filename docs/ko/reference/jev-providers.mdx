이 문서는 자체 키를 사용하는 [Jev 정책](/ko/policies/jev)의 공급자 및 설정 참조입니다. 정규식 정책은 문자열을 매칭합니다. `rm -rf build/`처럼 직접 요청한 명령과 `rm -rf ~`처럼 계획에 슬며시 끼어든 명령을 구분할 수 없기 때문에, 어떤 곳에서는 너무 많이 차단하고 다른 곳에서는 너무 적게 차단합니다. TypeSafe의 분류기인 **Jev**는 실제로 요청한 내용을 기준으로 호출을 분석하고, 하나의 빠른 요청으로 일련의 예/아니오 질문에 답합니다.

자체 Jev 엔드포인트와 키를 설정하면, Failproof AI는 각 도구 호출에 대해 정규식 정책과 **함께** Jev에 질문합니다. 대신 사용하는 것이 아닙니다.

- **하드** 정책의 deny는 최종입니다. Jev가 이를 해제할 수 없습니다. 모든 정책은 명시적으로 reviewable로 표시되고 해당 정책을 담당하는 Jev 검사를 지정하지 않는 한 하드입니다. 따라서 아무것도 명시하지 않은 커스텀, 팩, 또는 Cloud 정책은 하드이며, 항상 활성화되는 자체 보호 가드도 항상 하드입니다.
- **reviewable** 정책의 deny는 해제될 수 있지만, 해당 정책이 다루는 정확한 관심 사항에 대해 Jev가 질문을 받고 "여기에 아무것도 없습니다" 또는 "사용자가 이를 요청했습니다"라고 답변한 경우에만 가능합니다. 사용자가 해당 호출을 요청하지 않은 상황에서 검사가 실제 관심 사항을 발견하면, 해당 검사의 판정이 경고에 불과하더라도 deny는 유지됩니다. 도구 호출 전 경고는 에이전트를 멈추지 않기 때문입니다. 그리고 해당 검사가 deny를 내릴 수 있는 종류(비밀 노출, 자격 증명 유출, 파괴적 삭제 등)라면, 해당 호출에서는 아무것도 해제되지 않습니다.
- 호출이 사용자가 부여한 작업의 단계이고 더 이상 진행되지 않는 경우, 차단은 **경고**로 전환될 수 있습니다. Jev가 자체 deny를 경고로 완화하며, 그 경고(호출의 실제 문제점을 명시함)가 정책의 차단을 대체합니다.
- Jev는 정규식으로 설명할 수 없는 위해에 대해 자체적으로 경고하거나 deny할 수도 있습니다.
- Jev가 응답할 수 없는 경우(타임아웃, 속도 제한, 서버 오류, 크레딧 없음, 예상치 못한 모델 버전), 해당 호출은 Jev 없이 작동하는 것과 동일하게 정규식 결과를 받습니다.
- Jev는 전체 호출을 읽고 정확한 관심 사항에 대해 질문받은 경우가 아니라면, 정책만으로 허용하는 것보다 호출을 더 관대하게 만들지 않습니다. 그 미만의 경우(전체를 전송하기에 너무 큰 호출, 주입 의심)는 해제 권한을 철회하고 모든 deny를 유지합니다.

<Note>
Jev 설정이 없으면 아무것도 변경되지 않습니다. 훅은 항상 해왔던 것처럼 정규식 정책을 그대로 실행합니다. 설정 자체가 옵트인 전체입니다.
</Note>

<Tip>
FailproofAI Cloud를 사용하고 있다면 자체 키가 필요 없습니다. `jev:evaluate` 권한이 있는 키로 연결된 머신은 조직의 플랜에서 Jev를 사용할 수 있습니다. [FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud)를 참조하세요.
</Tip>

## 시작하기 전에

에이전트가 실행되는 머신에 **failproofai 1.0.8-beta.0 이상**을 설치하고 [지원되는 하네스](/ko/reference/harnesses)에 훅을 연결하세요. 새 머신이라면 [빠른 시작](/ko/start/quickstart)을 따르거나, Cloud를 사용하지 않는다면 [로컬 시행 설정](/ko/start/setup#enforce-locally)을 따르세요. 설치된 CLI는 `failproofai --version`으로 확인하세요.

아래의 공급자 중 하나에서 API 키를 받거나, 호환 가능한 엔드포인트와 해당 키를 준비하세요. Jev는 `PreToolUse` 또는 `PermissionRequest` 게이트에서 명명된 도구 호출을 검토합니다. 자체 판정을 내릴 수 있지만, 기존 정책 deny를 해제하려면 [reviewable](/ko/policies/authority)로 표시된 설치된 정책도 필요합니다. 하드 정책 deny는 최종 상태로 유지됩니다.

## 공급자 선택

Jev는 다섯 가지 경로로 접근할 수 있습니다. 그 중 하나의 키를 가져오세요.

| 공급자 | `--provider` | 엔드포인트 | 기본 모델 | 비고 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 정확한 버전 고정. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 요청은 다른 공급자로의 폴백 없이 제로 데이터 보존 엔드포인트로만 라우팅됩니다. `typesafe/jev-1.13-20260917`과 같은 날짜가 포함된 버전을 보고합니다. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jev를 별칭으로만 지칭하므로 응답한 버전은 미검증으로 기록됩니다. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id`가 필요합니다. 키당 초당 약 6회 호출을 측정한 후 HTTP 429가 반환되었습니다. |
| 자체 엔드포인트 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafe의 요청 본문을 수락하고 어떤 모델이 응답했는지 보고하는 모든 엔드포인트. `https`만 가능하며, 로컬 테스트를 위해 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`는 허용됩니다. |

<Warning>
Vercel의 자체 bring-your-own-key 기능을 사용하면 실패한 요청은 자동으로 Vercel의 자격 증명으로 재시도됩니다. 모든 호출이 자체 TypeSafe 계정에만 청구되고 해당 계정에서만 확인되어야 한다면 TypeSafe를 직접 사용하세요.
</Warning>

## 설정하기

명령 하나로 엔드포인트와 키를 설정합니다. `observe` 모드로 시작하면 기존 정책이 계속 호출을 결정하는 동안 Jev의 판정을 검사할 수 있습니다.

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL이 공급자를 결정합니다

공급자를 직접 지정할 필요가 없습니다. URL의 **호스트**가 공급자를 결정합니다.

| URL 호스트 | 공급자 | 추가 필요 사항 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| 기타 호스트 | `custom` | — 입력한 URL이 기본 URL이 됩니다 |

이로부터 세 가지 사항이 따릅니다.

- **공급자 자체 API인 URL은 오버라이드를 기록하지 않습니다.** `--url https://api.typesafe.ai/v1`은 `--provider typesafe`와 정확히 동일한 설정을 생성합니다. 알려진 공급자의 다른 경로나 호스트를 입력하면 `--base-url`이 저장하는 것처럼 기본 URL로 저장됩니다.
- **`--provider`는 여전히 추론을 오버라이드합니다.** 이는 자체 호스트에서 공급자의 API를 사용하는 프록시에 접근하는 방법입니다: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **호스트와 모순되는 `--provider`는 추측하지 않고 거부됩니다.** `--provider openrouter --url https://api.typesafe.ai/v1`은 아무것도 기록하지 않고 이유를 설명합니다. 두 값이 키가 전송될 위치에 대해 불일치하기 때문입니다. `jev setup --base-url`과 대시보드의 Jev 설정에서도 동일한 쌍은 거부됩니다. (`--provider custom`은 모순이 아닙니다. "이 URL을 그대로 취급"을 의미합니다. Cloudflare 호스트는 예외인데, 해당 계정별 엔드포인트는 custom 경로로 접근할 수 없습니다.)

`--url`은 설정 파일의 `baseUrl`과 동일하게 검증되며, 동일한 표현으로 거부됩니다. `https`, 또는 어떤 모드에서든 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`가 허용됩니다. 위험: 루프백 서버는 인증이 없으므로, 서버가 다운된 동안 다른 로컬 프로세스가 해당 포트를 점유하여 응답할 수 있습니다. 로컬 테스트 외에서는 `https`를 사용하세요.

### 키

`--key-stdin`으로 파이프하거나, 터미널에서 명령을 실행한 후 마스킹된 프롬프트에 키를 붙여넣으세요. 어느 방법이든 키는 설정 파일에 직접 저장되며 다시 출력되지 않습니다.

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup`은 동일한 플래그를 받으며 모든 것의 전체 형식입니다. URL 대신 공급자 이름을 선호한다면 `setup --provider <kind>`를 사용하세요.

### `--token`과 비용

`--token <token>`은 키를 커맨드 라인에 입력합니다. 머신을 가장 빠르게 설정하는 방법이지만, 설정 파일 외의 위치에 키를 남기는 유일한 방식입니다.

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
커맨드 라인 인수는 이후 셸 히스토리 파일에 남으며, 명령 실행 중에는 프로세스 목록에 표시되어 `/proc`를 통해 동일한 사용자로 실행되는 모든 프로세스가 읽을 수 있습니다. `setup`은 `--token`을 사용할 때마다 이 사실을 알립니다. 공유 머신, 녹화된 세션, 또는 히스토리 파일이 동기화되는 환경에서는 `--key-stdin`을 사용하세요. 이 방식으로 전달한 키는 필요하다면 교체하세요.
</Warning>

`--token`, `--key-stdin`, `--key-from-env`는 상호 배타적입니다. 하나만 입력하세요.

그런 다음 키, 엔드포인트, 그리고 어떤 Jev가 응답했는지 확인하기 위해 작은 라이브 요청을 보내세요.

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`는 답변이 타임아웃 후 도착하거나(모든 훅은 `timeout`으로 정규식으로 폴백됨) 검사 질문에 잘못 답변하면 종료 코드 1로 종료하며 제목에 표시합니다.

훅은 모든 도구 호출 시 설정을 읽으므로, 다음 호출부터 즉시 적용됩니다. 데몬을 사용하든 안 하든 재시작할 필요가 없습니다.

## 동작 확인

```bash
failproofai jev status
failproofai jev status --json
```

`status`는 공급자, 엔드포인트, 모델, 모드, 설정 파일과 권한을 표시하며, 키는 절대 표시하지 않습니다. 그 아래에는 최근 활동 요약이 표시됩니다. Jev가 평가한 호출 수, 정규식으로 폴백한 횟수와 이유, 지연 시간, 그리고 Jev가 해제한 reviewable 정책이 나열됩니다.

## 실제 호출 확인

훅이 연결된 에이전트에서 새 세션을 시작하세요. 에이전트에게 파일 읽기 도구를 사용하여 `README.md`에서 제목을 보고하도록 요청하세요. 세션에 해당 도구 호출이 포함되어 있는지 확인한 후, `failproofai jev status`를 다시 실행하세요. 최근 평가된 호출 수가 증가해야 합니다. [로컬 대시보드](/ko/reference/local-dashboard#review-policy-activity)에서 **Policies → Activity**를 열어 호출의 Jev 판정과 모드를 검사하세요. observe 모드에서는 정책 결과가 여전히 호출을 결정합니다. reviewable 정책이 매칭되고 Jev가 모든 명명된 검사를 해제한 경우에만 해제가 나타납니다. 일반적인 읽기는 해제할 정책이 없을 수 있습니다.

## Observe 모드

`enforce`가 기본값입니다. Jev가 어떤 결정도 변경하지 않게 하면서 관찰하려면 `observe`로 전환하세요. Jev는 여전히 질문을 받고 판정이 기록되지만, 시행되는 것은 정규식 결과입니다.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`는 설정(엔드포인트와 키)을 유지하면서 Jev 질문을 중단합니다. 훅은 설정 없이와 동일하게 정규식 정책을 실행하며, `failproofai jev status`는 "off (switched off)"를 표시합니다. `--mode observe` 또는 `--mode enforce`로 다시 전환할 수 있습니다.

동일한 공급자에 대해 `setup`을 재실행하면 저장된 키를 유지하므로, 모드 전환은 플래그 하나입니다. 공급자를 전환하면 처음부터 시작하여 새 공급자의 키를 요청합니다. 요청을 다른 호스트로 이동하는 `--base-url`도 마찬가지입니다. 저장된 키는 처음 입력된 호스트 또는 해당 공급자의 자체 API에만 전송됩니다.

## 설정 파일

모든 것은 `setup`이 작성하는 하나의 파일 `~/.failproofai/jev.json`에 저장됩니다.

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 필드 | 의미 |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` 또는 `custom`. 또는 `failproofai`(이 경우 키는 이 파일 대신 FailproofAI Cloud 연결에서 가져옵니다. [FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud) 참조). |
| `apiKey` | `Authorization: Bearer <key>`로 전송됩니다. |
| `baseUrl` | `custom`에 필수이며, 그 외의 경우 공급자의 API 기본 URL을 대체합니다. `https`여야 합니다. `localhost`에 대한 일반 `http`는 `mode: observe`에서만 허용됩니다. 로컬 포트는 인증이 없으므로, 프록시가 다운된 동안 머신의 모든 프로세스(평가받는 에이전트 포함)가 대신 응답할 수 있습니다. |
| `accountId` | Cloudflare 전용: 32자리 소문자 16진수. |
| `model` | 공급자의 기본 모델 ID를 대체합니다. 버전이 명시된 ID는 Jev 1.13을 지정해야 합니다. API 키처럼 보이는 값은 거부됩니다(다시 출력되지 않음). 따라서 `--model`에 붙여넣은 키는 모델로 저장되거나 전송되지 않습니다. |
| `timeoutMs` | Jev를 기다리다 정규식 결과를 사용하기까지의 시간. 100–10000, 기본값 3000. |
| `mode` | `enforce`(기본값), `observe`, 또는 `off`(설정 유지, Jev 실행 안 함). |

세 가지 규칙이 파일을 보호합니다.

- **소유자 전용.** 권한 `0600`으로 작성됩니다. 다른 사용자나 그룹이 읽거나 쓸 수 있는 복사본은 **거부**되며, `chmod 600 ~/.failproofai/jev.json`을 실행하거나 `setup`을 재실행할 때까지 훅은 정규식으로 폴백합니다. 디렉토리도 확인됩니다. `~/.failproofai`는 다른 사람이 **쓸 수 없어야** 합니다. 거기에 쓸 수 있는 사람은 파일 자체의 권한에 관계없이 파일을 교체할 수 있기 때문입니다. `setup`은 그런 쓰기 비트를 발견하면 제거합니다. `failproofai jev status`는 설정이 거부된 경우를 알리고 파일에 명시된 엔드포인트를 표시합니다. 다른 사람이 변경했을 수 있으므로, `chmod` 전에 해당 파일이 본인의 것인지 확인하세요. 이런 파일에 `setup`을 재실행하면 저장된 키를 공급자 자체 API에만 전달합니다. 다른 엔드포인트가 지정된 경우 키를 다시 입력해야 합니다(`--key-stdin`), 또는 `--base-url default`로 요청을 공급자로 되돌리세요.
- **글로벌 전용.** 저장소는 Jev를 켜거나, 다른 엔드포인트를 지정하거나, 모델을 선택할 수 없습니다. 프로젝트 내부의 `.failproofai/jev.json`은 무시되며, 공급자, URL, 모델, 계정 ID는 해당 파일에서만 읽히고 환경에서는 읽히지 않습니다. 저장소의 에이전트 설정이 환경을 설정할 수 있기 때문입니다. (`FAILPROOFAI_HOME`은 우회 방법이 아닙니다. Jev만 리다이렉트하는 것이 아니라 정책을 포함한 전체 failproofai 디렉토리를 이동합니다.)
- **키만 환경에서 가져올 수 있습니다.** 파일에 `apiKey`가 없으면, `FAILPROOFAI_JEV_API_KEY`가 해당 세션에 키를 제공합니다(`setup --key-from-env`는 그런 파일을 작성합니다). 파일에 있는 키를 대체하지 않으며, 파일 없이 Jev를 켤 수 없습니다. 변수가 설정되지 않은 경우 해당 셸에서는 Jev가 단순히 off 상태입니다. `failproofai jev status`는 이를 알리고 종료 코드 0으로 종료하며 설정을 그대로 둡니다(`status --json`은 `"status": "key-missing"`과 `"reason": "no-env-key"`를 보고합니다). `failproofaid` 데몬은 셸 환경을 볼 수 없으므로, `failproofai config`로 설정된 머신에서는 파일에 키를 유지하세요.

## 어떤 Jev가 응답하는가

Failproof AI의 결정 임계값은 Jev 1.13을 기준으로 보정되었으므로, 해당 패밀리에서 온 경우에만 답변이 사용됩니다. `jev-1.13.x` 또는 OpenRouter의 `typesafe/jev-1.13-<date>`. 공급자가 Jev를 별칭으로만 지칭하고 버전을 보고하지 않는 경우(Vercel, 그리고 Cloudflare가 버전을 명시하지 않을 때), 답변은 사용되고 미검증으로 기록됩니다. `custom` 엔드포인트는 응답한 모델을 보고해야 합니다. 단 하나의 예외는 버전 없는 `--model` 이름을 설정한 경우인데, 에코되어 돌아오면 동일하게 미검증으로 기록됩니다. 다른 버전을 보고하는 답변이나 `custom` 엔드포인트가 아무것도 보고하지 않는 경우는 사용되지 않습니다. 해당 호출은 `model-mismatch` 이유로 정규식으로 폴백됩니다.

## Jev가 응답할 수 없을 때

다음 각각은 해당 호출에 대해 정규식 결과로 폴백되며 이유와 함께 기록됩니다. `failproofai jev status`는 이를 합산합니다.

| 이유 | 원인 |
| --- | --- |
| `timeout` | `timeoutMs` 내에 응답이 없음. |
| `http-429` | 공급자가 키를 속도 제한함. |
| `rate-limited` | Failproof AI 자체 제한기가 전송 전에 호출을 보류함: 초당 5회 요청, 최대 5회 버스트, 공급자가 `429`로 응답한 후 잠시 중단. 공급자가 아님. |
| `http-500`, `http-502`, `http-503`, … | 공급자에서의 서버 오류. 정확한 상태가 기록됨. |
| `out-of-credits` | HTTP 402: 공급자 계정에 크레딧이 없음. |
| `provider-refused` | Cloudflare에서 "Model execution failed (Payment error)"라는 HTTP 402: 공급자가 이 요청에 대해 모델 실행을 거부함. 일반적으로 청구 문제가 아니므로 크레딧을 충전해도 해결되지 않음. |
| `http-401`, `http-403` | 키가 거부됨. |
| `http-404` | `<base>/systemone`에 서비스가 없으므로 기본 URL이 잘못되었습니다. `/systemone`이 기본 URL에 추가되며, 모든 공급자는 버전 루트에서 이를 제공합니다. `failproofai jev models`로 엔드포인트가 제공하는 것을 확인하세요. |
| `network` | 엔드포인트에 도달할 수 없음. |
| `http-301`, `http-302`, `http-307`, `http-308` | 엔드포인트가 리다이렉트로 응답함. 리다이렉트는 절대 따라가지 않으므로, 답변은 설정의 URL에서만 옵니다. `--base-url`을 최종 URL로 설정하세요. |
| `malformed` | 엔드포인트가 응답했지만 Jev 답변이 아님. JSON이 아닌 본문이거나 답변이 없는 본문. |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflare 봉투가 실패를 보고하거나 완료되지 않은 작업. |
| `model-mismatch` | 1.13 외의 Jev 버전이 응답했거나, `custom` 엔드포인트가 응답한 모델을 명시하지 않음. |
| `request-cut` | **장애가 아닙니다.** Jev가 응답했으나 호출의 일부만 표시되어 아무것도 해제하지 않았습니다. [Jev가 응답했지만 전체 호출이 아닌 경우](#when-jev-answered-but-not-on-the-whole-call)를 참조하세요. |

`failproofai jev status`는 `upstream-error`(답변에 공급자 자체 오류가 포함됨)나 `config` 같은 더 드문 이유도 표시할 수 있으며, 명명할 수 없는 이유는 `other`로 합산합니다.

`request-cut`이 이 표에 포함된 이유는 `failproofai jev status`가 나머지와 함께 합산하기 때문이며, 이 역시 모든 deny를 그대로 둡니다. 여기서 공급자에 대해 아무것도 말하지 않는 유일한 이유입니다. 요청이 도착했고 Jev가 응답했습니다. 위의 모든 행과 달리, 해당 답변은 여전히 유효합니다. Jev 자체의 deny나 경고는 정규식 결과 위에 적용되며, 버려지지 않습니다. 따라서 이런 경우가 반복된다면 호출이 전체를 전송하기에 너무 크게 평가자에 도달하는 것이지, 엔드포인트에 문제가 있는 것이 아닙니다. 크레딧을 충전하거나 URL을 변경해도 이 수치는 바뀌지 않습니다.

## Jev가 응답했지만 전체 호출이 아닌 경우

두 가지 추가 상황이 있으며, 어느 것도 Jev가 응답에 실패한 것이 아닙니다. 두 가지 모두 호출 또는 대화의 얼마나 많은 부분이 하나의 요청에 맞았는지에 관한 것입니다.

**호출의 일부가 들어가지 않았습니다.** 도구 호출은 고정된 예산 안에 전송되며, 지나치게 큰 호출(매우 큰 `Write`, 거대한 MCP 본문, 한도까지 패딩된 명령)은 맞는 부분만 전송됩니다. Jev는 여전히 응답하며, 그 답변은 여전히 유효합니다. 자체 deny나 경고는 평소와 같이 적용됩니다. **해제**할 수 없는 것은, 호출의 일부에 대한 판정은 호출 전체에 대한 판정이 아니기 때문입니다. 따라서 모든 정책 deny는 유지되며, 호출은 `request-cut` 이유와 함께 폴백으로 기록됩니다. `failproofai jev status`는 이를 위의 이유들과 함께 합산합니다. 이것이 주는 규칙: 호출을 더 크게 만들면 해제 권한을 잃을 수 있으며, 해제 권한을 얻을 수는 없습니다.

**메시지가 들어가지 않았습니다.** 붙여넣은 긴 프롬프트, 에이전트의 마지막 메시지, 또는 이 평가자의 자체 저장소가 이미 한도를 초과한 프롬프트. **아무것도 변경되지 않습니다.** 호출은 다른 호출과 동일하게 판정, 해제, 기록되며 폴백으로 계산되지 않습니다. 입력 길이는 판정을 결정하지 않으며, 잘린 내용이 동의를 만들어낼 수 없습니다. 프롬프트가 이미 한도 초과로 도착한 경우, "당신은 이것을 요청하지 않았습니다"는 전혀 도출할 수 없는 결론이 되는 것이지, 어떤 결론으로 변하는 것이 아닙니다.

두 가지의 경계는 누가 텍스트를 작성했는지입니다. 호출은 에이전트의 것이며, 크기가 심각성을 줄이도록 허용하는 규칙은 에이전트가 사용할 수 있는 규칙이 됩니다. 프롬프트는 사용자의 것이며, 그 길이를 신호로 취급하면 명세서나 스택 트레이스를 붙여넣는 행위에 대한 처벌이 될 뿐입니다.

## 머신을 떠나는 정보

Jev가 평가하는 각 도구 호출에 대해, 공급자로 하나의 요청이 전송됩니다. 이 요청에는 다음이 포함됩니다.

- API 키, 베어러 토큰, `KEY=` 할당과 같은 비밀이 편집된 도구 호출 자체
- 에이전트 하네스가 추가한 텍스트를 제거한 최근에 입력한 프롬프트
- 최신 프롬프트 이전 에이전트의 마지막 메시지(에이전트가 작성한 것으로 표시됨)
- 경로가 프로젝트 내부에 있는지 여부와 같이 로컬에서 계산된 사실(첫 번째 검토된 호출 시 세션이 있던 위치, [세션 동안 고정됨](/ko/reference/jev-intent#the-project-root)), 그리고 현재 git 브랜치

요청은 설정의 엔드포인트로만, 사용자의 키 하에 전송됩니다.

## 끄기

```bash
failproofai jev remove
```

이 명령은 `~/.failproofai/jev.json`을 삭제합니다. 다음 도구 호출부터 훅은 이전과 동일하게 정규식 정책을 실행합니다. `~/.failproofai/state/semantic/` 아래의 세션별 저장소(기록된 프롬프트는 `sessions/`, 프로젝트 루트는 `roots/`)는 그대로 남아 자동으로 만료됩니다. Jev 질문을 중단하되 설정을 유지하려면 대신 `failproofai jev setup --mode off`를 사용하세요.

## 명령 참조

| 명령 | 결과 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 한 명령으로 설정. 공급자는 URL 호스트에서 결정됨 |
| `failproofai jev --url <url> --token <token>` | 동일하지만 커맨드 라인에 키 입력 — 히스토리와 프로세스 목록에 남음 |
| `failproofai jev setup --provider <kind> --key-stdin` | stdin으로 파이프된 키로 설정 작성 |
| `failproofai jev setup --provider <kind>` | 동일하지만 마스킹된 프롬프트에서 키 입력 |
| `failproofai jev setup --key-from-env` | 키 저장 안 함. 세션마다 `FAILPROOFAI_JEV_API_KEY` 읽기 |
| `failproofai jev setup --mode observe` | 저장된 키를 유지하면서 모드 전환(`enforce`, `observe` 또는 `off`) |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 모델 또는 API 기본 URL 오버라이드. `default`로 오버라이드 해제 |
| `failproofai jev setup --timeout-ms <n>` | 호출당 예산 변경 |
| `failproofai jev status [--json]` | 설정, 권한, 최근 활동. 키는 표시 안 함 |
| `failproofai jev test [--json]` | 하나의 라이브 요청: 지연 시간과 응답한 버전 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 해당 엔드포인트의 `/models`가 보고하는 모델 ID, 설정된 것 표시 |
| `failproofai jev remove` | 설정 삭제. Jev 비활성화 |
