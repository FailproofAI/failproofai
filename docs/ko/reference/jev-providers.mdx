이 문서는 자체 키를 사용하는 [Jev 정책](/ko/policies/jev)의 공급자 및 구성 참조 가이드입니다. 정규식 정책은 문자열을 대조합니다. `rm -rf build/`처럼 직접 요청한 명령과 계획에 슬쩍 끼어든 `rm -rf ~`를 구별할 수 없기 때문에, 한쪽에서는 너무 많이 차단하고 다른 쪽에서는 너무 적게 차단합니다. TypeSafe의 분류기인 **Jev**는 실제로 요청한 내용을 기준으로 호출을 분석하고, 하나의 빠른 요청으로 일련의 예/아니오 질문에 답합니다.

자체 Jev 엔드포인트와 키를 구성하면, Failproof AI는 각 도구 호출에 대해 정규식 정책과 **함께** Jev에 질문합니다. Jev가 정규식 정책을 대체하지는 않습니다.

- **하드** 정책의 거부는 최종입니다. Jev가 이를 취소할 수 없습니다. 명시적으로 검토 가능으로 표시되고 해당 정책을 다루는 Jev 검사가 지정되지 않는 한 모든 정책은 하드입니다. 따라서 아무것도 명시하지 않은 커스텀, 팩, 클라우드 정책은 하드이며, 항상 활성화된 자기 보호 가드도 항상 하드입니다.
- **검토 가능** 정책의 거부는 취소될 수 있지만, Jev가 해당 정책이 다루는 정확한 우려 사항에 대해 질문을 받고 "여기에 해당 없음" 또는 "사용자가 이를 요청함"으로 답한 경우에만 가능합니다. 우려 사항이 실재한다고 판단되고 사용자가 해당 호출을 요청하지 않은 경우, 검사 자체의 판정이 경고에 불과하더라도 거부는 유지됩니다. 도구 호출 전 경고는 에이전트를 중단시키지 않기 때문입니다. 그리고 해당 검사가 거부 가능한 항목(시크릿 노출, 자격 증명 유출, 파괴적 삭제 등)인 경우, 해당 호출에서는 아무것도 취소되지 않습니다.
- 호출이 주어진 작업의 단계이고 그 범위를 벗어나지 않는 경우, 차단이 **경고**로 완화될 수 있습니다. Jev는 자체 거부를 경고로 완화하며, 해당 경고(실제 문제점을 명확히 명시)가 정책의 차단을 대체합니다.
- Jev는 정규식으로 표현할 수 없는 위험에 대해 독자적으로 경고하거나 거부할 수도 있습니다.
- Jev가 답할 수 없는 경우(타임아웃, 속도 제한, 서버 오류, 크레딧 없음, 예상치 못한 모델 버전), 해당 호출은 Jev 없이 사용하는 것과 동일하게 정규식 결과를 받습니다.
- Jev는 전체 호출을 읽고 정확한 우려 사항에 대해 질문을 받은 경우가 아니라면, 정책만으로 허용되는 것보다 호출을 더 허용적으로 만들지 않습니다. 이에 미치지 못하는 경우(전체를 전송하기에 너무 큰 호출, 의심스러운 인젝션)에는 허가를 철회하고 모든 거부를 유지합니다.

<Note>
Jev 구성이 없으면 아무것도 변경되지 않습니다. 훅은 항상 그래왔던 것처럼 정규식 정책을 그대로 실행합니다. 구성 자체가 옵트인의 전부입니다.
</Note>

<Tip>
FailproofAI Cloud를 사용 중이신가요? 자체 키가 필요하지 않습니다. `jev:evaluate`가 부여된 키로 연결된 머신은 조직의 플랜으로 Jev를 사용할 수 있습니다. [FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud)를 참조하세요.
</Tip>

## 시작하기 전에

에이전트가 실행되는 머신에 **failproofai 1.0.8-beta.0 이상**을 설치하고 [지원되는 하니스](/ko/reference/harnesses)에 훅을 연결하세요. 새 머신이라면 [빠른 시작](/ko/start/quickstart)을 따르고, Cloud를 사용하지 않는다면 [로컬 적용 설정](/ko/start/setup#enforce-locally)을 참조하세요. `failproofai --version`으로 설치된 CLI를 확인하세요.

아래 공급자에서 API 키를 발급받거나, 호환 가능한 엔드포인트와 해당 키를 준비하세요. Jev는 `PreToolUse` 또는 `PermissionRequest` 게이트에서 명명된 도구 호출을 검토합니다. 독자적인 판정을 내릴 수 있지만, 기존 정책 거부를 취소하려면 [검토 가능](/ko/policies/authority)으로 표시된 설치된 정책이 필요합니다. 하드 정책 거부는 최종으로 유지됩니다.

## 공급자 선택

Jev는 다섯 가지 경로를 통해 접근할 수 있습니다. 그 중 하나의 키를 가져오세요.

| 공급자 | `--provider` | 엔드포인트 | 기본 모델 | 참고 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 정확한 버전 고정. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 요청은 제로 데이터 보존 엔드포인트로만 라우팅되며, 다른 공급자로의 폴백 없음. `typesafe/jev-1.13-20260917`과 같은 날짜 포함 버전을 보고함. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | 별칭으로만 Jev를 명명하므로 응답 버전이 미검증으로 기록됨. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id` 필요. 측정 결과 키당 초당 약 6회 호출 전에 HTTP 429 발생. |
| 자체 엔드포인트 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafe의 요청 본문을 수락하고 응답한 모델을 보고하는 모든 엔드포인트. `https` 전용. 로컬 테스트를 위해 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`는 허용됨. |

<Warning>
Vercel의 자체 키 가져오기(bring-your-own-key) 기능을 사용하면, 실패한 요청이 Vercel의 자격 증명으로 자동 재시도됩니다. 모든 호출이 자체 TypeSafe 계정에만 청구되고 해당 계정에서만 확인되어야 한다면, TypeSafe를 직접 사용하세요.
</Warning>

## 설정하기

명령 하나로 엔드포인트와 키를 설정합니다. 기존 정책이 계속 호출을 처리하는 동안 Jev의 판정을 검사할 수 있도록 `observe` 모드로 시작하세요.

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL이 공급자를 결정합니다

공급자를 명시적으로 지정할 필요가 없습니다. URL의 **호스트**가 공급자를 결정합니다.

| URL 호스트 | 공급자 | 추가 필요 사항 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| 기타 모든 호스트 | `custom` | — 제공한 URL이 기본 URL이 됨 |

여기서 세 가지 사항이 따릅니다.

- **공급자 자체 API의 URL은 오버라이드를 기록하지 않습니다.** `--url https://api.typesafe.ai/v1`은 `--provider typesafe`와 동일한 구성을 생성합니다. 알려진 공급자의 다른 경로나 호스트를 지정하면 `--base-url`처럼 기본 URL로 저장됩니다.
- **`--provider`는 여전히 추론을 오버라이드합니다.** 이를 통해 자체 호스트에서 공급자의 API를 구사하는 프록시에 접근할 수 있습니다: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **호스트와 모순되는 `--provider`는 거부됩니다.** 추측하지 않습니다. `--provider openrouter --url https://api.typesafe.ai/v1`은 아무것도 기록하지 않고 이유를 설명합니다. 두 설정이 키가 전송될 위치에 대해 불일치하기 때문입니다. `jev setup --base-url`과 대시보드의 Jev 설정에서도 동일하게 거부됩니다. (`--provider custom`은 모순이 아닙니다. "이 URL을 그대로 사용하겠다"는 의미입니다. 단, 계정별 엔드포인트에 커스텀 경로로 접근할 수 없는 Cloudflare 호스트는 예외입니다.)

`--url`은 구성 파일의 `baseUrl`과 동일하게 검증되며, 동일한 오류 메시지로 거부됩니다. `https` 또는 모든 모드에서 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`만 허용됩니다. 위험: 루프백 서버는 인증되지 않으므로, 서버가 다운된 동안 다른 로컬 프로세스가 해당 포트를 점유하여 응답할 수 있습니다. 로컬 테스트 외에는 `https`를 사용하세요.

### 키

`--key-stdin`으로 파이프하거나, 키 없이 터미널에서 명령을 실행하고 마스킹된 프롬프트에 붙여넣으세요. 어느 방법이든 키는 구성 파일에 직접 저장되며 다시 출력되지 않습니다.

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup`은 동일한 플래그를 받으며, URL 대신 공급자를 명시하고 싶을 때 사용하는 긴 형식입니다: `setup --provider <kind>`.

### `--token` 및 비용

`--token <token>`은 키를 명령줄에 직접 입력합니다. 머신을 빠르게 구성하는 방법이지만, 구성 파일 외의 위치에 키를 남기는 유일한 방법이기도 합니다.

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
명령줄 인수는 이후 셸 히스토리 파일에 남으며, 명령이 실행되는 동안 프로세스 목록에 나타나 `/proc`을 통해 같은 사용자로 실행되는 모든 프로세스에서 읽을 수 있습니다. `setup`은 `--token`을 사용할 때마다 이를 알립니다. 공유 머신, 세션이 기록되는 환경, 히스토리 파일이 동기화되는 곳에서는 `--key-stdin`을 선호하세요. 이 방법으로 전달한 키가 중요하다면 교체하세요.
</Warning>

`--token`, `--key-stdin`, `--key-from-env`는 상호 배타적입니다. 하나만 사용하세요.

그런 다음 소규모 라이브 요청을 하나 전송하여 키, 엔드포인트, 응답한 Jev를 확인하세요.

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`는 타임아웃 이후에 답이 도착하거나(모든 훅이 `timeout`으로 정규식으로 폴백) 검사 질문에 잘못 답하면 1을 반환하고 타이틀에 이를 표시합니다.

훅은 매 도구 호출마다 구성을 읽으므로, 다음 호출부터 적용됩니다. 데몬 유무와 관계없이 재시작할 필요가 없습니다.

## 동작 확인

```bash
failproofai jev status
failproofai jev status --json
```

`status`는 공급자, 엔드포인트, 모델, 모드, 구성 파일과 권한을 표시하며 키는 절대 보여주지 않습니다. 그 아래에는 최근 활동이 요약됩니다. Jev가 평가한 호출 수, 정규식으로 폴백한 횟수와 이유, 지연 시간, 취소된 검토 가능 정책이 표시됩니다.

## 실제 호출 확인

훅이 연결된 에이전트에서 새 세션을 시작하세요. `README.md`에서 파일 읽기 도구를 사용하여 제목을 보고하도록 요청하세요. 세션에 해당 도구 호출이 포함되어 있는지 확인한 후 `failproofai jev status`를 다시 실행하세요. 최근 평가된 호출 수가 증가해야 합니다. [로컬 대시보드](/ko/reference/local-dashboard#review-policy-activity)에서 **정책 → 활동**을 열어 호출의 Jev 판정과 모드를 검사하세요. observe 모드에서는 정책 결과가 여전히 호출을 결정합니다. 검토 가능 정책이 일치하고 Jev가 명명된 모든 검사를 통과한 경우에만 취소가 나타납니다. 일반적인 읽기 작업에는 취소할 정책이 없을 수 있습니다.

## Observe 모드

`enforce`가 기본값입니다. Jev가 어떤 결정도 변경하지 않고 지켜보도록 하려면 `observe`로 전환하세요. Jev는 여전히 질문을 받고 판정이 기록되지만, 정규식 결과가 적용됩니다.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`는 구성(엔드포인트와 키)을 유지하되 Jev에 질문하는 것을 중단합니다. 훅은 구성 없이 사용하는 것과 동일하게 정규식 정책을 실행하며, `failproofai jev status`는 "off (switched off)"를 표시합니다. `--mode observe` 또는 `--mode enforce`로 다시 전환하세요.

동일한 공급자로 `setup`을 다시 실행하면 저장된 키를 유지하므로, 모드 전환은 플래그 하나로 가능합니다. 공급자를 전환하면 처음부터 시작하며 해당 공급자의 키를 요청합니다. 요청을 다른 호스트로 이동시키는 `--base-url`도 마찬가지입니다. 저장된 키는 최초 제공된 호스트 또는 해당 공급자의 자체 API에만 전송됩니다.

## 구성 파일

모든 것은 `setup`이 작성하는 하나의 파일 `~/.failproofai/jev.json`에 저장됩니다.

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 필드 | 의미 |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` 또는 `custom`. 또는 이 파일 대신 FailproofAI Cloud 연결에서 키를 가져오는 `failproofai` ([FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud) 참조). |
| `apiKey` | `Authorization: Bearer <key>`로 전송됨. |
| `baseUrl` | `custom`의 경우 필수. 그 외에는 공급자의 API 기본값을 대체함. `https` 필수. `localhost`에 대한 일반 `http`는 `mode: observe`에서만 허용됨. 프록시가 다운된 동안 머신의 모든 프로세스(에이전트 포함)가 로컬 포트를 점유하여 응답할 수 있기 때문임. |
| `accountId` | Cloudflare 전용: 소문자 16진수 32자. |
| `model` | 공급자의 기본 모델 ID를 대체함. 버전이 명시된 ID는 Jev 1.13을 명시해야 함. API 키처럼 생긴 값은 거부되며 반환되지 않으므로, `--model`에 붙여넣은 키는 절대 저장되거나 모델로 전송되지 않음. |
| `timeoutMs` | 정규식 결과를 사용하기 전에 Jev를 기다리는 시간. 100–10000, 기본값 3000. |
| `mode` | `enforce`(기본값), `observe`, 또는 `off`(구성 유지, Jev 실행 없음). |

세 가지 규칙이 파일을 보호합니다.

- **소유자 전용.** 권한 `0600`으로 작성됩니다. 다른 사용자나 그룹이 읽거나 쓸 수 있는 사본은 **거부**되며, `chmod 600 ~/.failproofai/jev.json`을 실행하거나 `setup`을 다시 실행할 때까지 훅이 정규식으로 폴백합니다. 디렉토리도 확인됩니다. `~/.failproofai`는 다른 사람이 **쓸 수 없어야** 합니다. 거기에 쓸 수 있는 사람은 파일 자체의 권한에 관계없이 파일을 교체할 수 있기 때문입니다. `setup`은 그런 쓰기 비트를 발견하면 제거합니다. `failproofai jev status`는 구성이 거부된 경우와 파일이 명시한 엔드포인트를 표시합니다. 다른 사람이 변경했을 수 있으니 `chmod` 전에 자신의 파일인지 확인하세요. 그런 파일에서 `setup`을 다시 실행하면 저장된 키를 공급자의 자체 API에만 전달합니다. 명시된 다른 엔드포인트에는 키가 다시 필요하거나(`--key-stdin`), `--base-url default`로 요청을 공급자에게 돌려보내야 합니다.
- **전역 전용.** 저장소는 Jev를 활성화하거나, 다른 엔드포인트를 지정하거나, 모델을 선택할 수 없습니다. 프로젝트 내부의 `.failproofai/jev.json`은 무시되며, 공급자, URL, 모델, 계정 ID는 오직 해당 파일에서만 읽습니다. 저장소의 에이전트 설정으로 설정 가능한 환경에서도 마찬가지입니다. (`FAILPROOFAI_HOME`은 우회 방법이 아닙니다. Jev만 리디렉션하는 것이 아니라 정책을 포함한 전체 failproofai 디렉토리를 이동합니다.)
- **키만 환경에서 가져올 수 있습니다.** 파일에 `apiKey`가 없으면, 해당 세션에 `FAILPROOFAI_JEV_API_KEY`가 사용됩니다(`setup --key-from-env`는 그런 파일을 작성함). 파일에 키가 있으면 대체하지 않으며, 파일 없이 Jev를 활성화할 수 없습니다. 변수가 설정되지 않은 경우, Jev는 해당 셸에서 비활성화됩니다. `failproofai jev status`는 이를 표시하고, 0으로 종료하며 구성을 그대로 둡니다(`status --json`은 `"reason": "no-env-key"`와 함께 `"status": "key-missing"`을 보고함). `failproofaid` 데몬은 셸 환경을 보지 못하므로, `failproofai config`로 설정된 머신에서는 파일에 키를 보관하세요.

## 어떤 Jev가 응답하는가

Failproof AI의 결정 임계값은 Jev 1.13을 기준으로 보정되었으므로, 해당 계열에서 답이 올 때만 사용됩니다: `jev-1.13.x` 또는 OpenRouter의 `typesafe/jev-1.13-<date>`. 공급자가 별칭만으로 Jev를 명명하고 버전을 보고하지 않는 경우(Vercel, 그리고 버전을 명시하지 않는 Cloudflare), 답은 사용되지만 미검증으로 기록됩니다. `custom` 엔드포인트는 응답한 모델을 반드시 보고해야 합니다. 단 하나의 예외는 설정한 버전 없는 `--model` 이름이 그대로 반환되는 경우로, 동일한 방식으로 미검증으로 기록됩니다. 다른 버전을 보고하는 답이나 버전을 보고하지 않는 `custom` 답은 사용되지 않습니다. 해당 호출은 `model-mismatch` 이유로 정규식으로 폴백합니다.

## Jev가 답할 수 없을 때

다음 각각은 해당 호출에 대해 정규식 결과로 폴백하고 이유와 함께 기록됩니다. `failproofai jev status`에서 합계를 확인할 수 있습니다.

| 이유 | 원인 |
| --- | --- |
| `timeout` | `timeoutMs` 내에 답 없음. |
| `http-429` | 공급자가 키에 속도 제한을 적용함. |
| `rate-limited` | Failproof AI 자체 제한기가 전송 전 호출을 보류함: 초당 5회, 최대 5회 버스트, 공급자가 `429`를 응답한 후 잠시 없음. 공급자가 아님. |
| `http-500`, `http-502`, `http-503`, … | 공급자의 서버 오류. 정확한 상태가 기록됨. |
| `out-of-credits` | HTTP 402: 공급자 계정에 크레딧 없음. |
| `provider-refused` | Cloudflare에서 "Model execution failed (Payment error)"를 읽은 HTTP 402: 공급자가 이 요청에서 모델 실행을 거부함. 보통 청구 문제가 아니므로 크레딧 충전이 해결책이 아님. |
| `http-401`, `http-403` | 키가 거부됨. |
| `http-404` | `<base>/systemone`에서 아무것도 제공되지 않으므로 기본 URL이 잘못됨. `/systemone`이 URL에 추가되며, 모든 공급자는 버전 루트에서 이를 제공함. `failproofai jev models`로 엔드포인트가 제공하는 것을 확인할 수 있음. |
| `network` | 엔드포인트에 도달할 수 없음. |
| `http-301`, `http-302`, `http-307`, `http-308` | 엔드포인트가 리디렉션으로 응답함. 리디렉션은 절대 따르지 않으므로 답은 항상 구성의 URL에서만 옴. `--base-url`을 최종 URL로 설정하세요. |
| `malformed` | 엔드포인트가 응답했지만 Jev 답이 아닌 경우. JSON이 아닌 본문이거나 답이 없는 경우. |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflare의 엔벨로프가 실패를 보고하거나 완료되지 않은 작업을 보고함. |
| `model-mismatch` | 1.13 외의 Jev 버전이 응답하거나 `custom` 엔드포인트가 응답 모델을 명시하지 않음. |
| `request-cut` | **장애가 아닙니다.** Jev가 응답했지만 호출의 일부만 보여줬으므로 아무것도 취소되지 않음. [Jev가 응답했지만 전체 호출에 대해 응답하지 않은 경우](#when-jev-answered-but-not-on-the-whole-call) 참조. |

`failproofai jev status`는 `upstream-error`(답에 공급자 자체 오류가 포함됨)나 `config` 같은 드문 이유도 표시할 수 있으며, 명명할 수 없는 이유는 `other`로 합산합니다.

`request-cut`이 이 표에 포함된 이유는 `failproofai jev status`가 나머지와 함께 집계하기 때문이며, 이 경우에도 모든 거부가 유지되기 때문입니다. 여기서 공급자에 대해 아무것도 말하지 않는 유일한 이유입니다. 요청이 도착했고 Jev가 응답했습니다. 위의 모든 행과 달리, 해당 답은 여전히 카운트됩니다. Jev 자체의 거부 또는 경고는 정규식 결과에 추가로 적용되며 버려지지 않습니다. 따라서 `request-cut`이 연속으로 발생한다는 것은 호출이 전체를 전송하기에 너무 큰 채로 평가기에 도달하고 있다는 뜻이지, 엔드포인트에 문제가 있다는 뜻이 아닙니다. 크레딧을 충전하거나 URL을 변경해도 해당 수치는 변하지 않습니다.

## Jev가 응답했지만 전체 호출에 대해 응답하지 않은 경우

두 가지 경우가 더 있으며, 둘 다 Jev가 답하지 못한 것이 아닙니다. 모두 호출의 얼마만큼, 또는 대화의 얼마만큼이 하나의 요청에 맞았는지에 관한 것입니다.

**호출 자체의 일부가 맞지 않은 경우.** 도구 호출은 고정된 예산 내에서 전송되며, 너무 큰 호출(매우 큰 `Write`, 거대한 MCP 본문, 한도를 꽉 채운 명령)은 맞는 부분만 전송됩니다. Jev는 여전히 답하며, 그 답은 여전히 카운트됩니다. Jev 자체의 거부 또는 경고는 평소와 같이 적용됩니다. 하지만 일부 호출에 대한 판정은 해당 호출에 대한 판정이 아니므로 아무것도 **취소**할 수 없습니다. 따라서 모든 정책 거부는 유지되며, 호출은 `request-cut` 이유로 폴백으로 기록됩니다. 여기서 얻을 수 있는 규칙: 호출을 더 크게 만들면 허가를 잃을 수 있으며, 허가를 얻을 수는 없습니다.

**메시지가 맞지 않은 경우.** 붙여넣은 긴 프롬프트, 에이전트의 마지막 메시지, 또는 이 평가기의 자체 저장소에서 이미 잘린 프롬프트. **아무것도 변경되지 않습니다.** 호출은 다른 것과 동일하게 판정, 취소, 기록되며 폴백으로 카운트되지 않습니다. 입력 길이는 판정을 결정하지 않으며, 잘림이 동의를 만들어낼 수 없습니다. 프롬프트가 이미 잘린 채로 도착한 경우, "당신은 이것을 요청하지 않았습니다"라는 결론을 도출하는 것 자체가 불가능해질 뿐, 반대 결론이 나오지는 않습니다.

두 경우의 차이는 누가 텍스트를 작성했는지입니다. 호출은 에이전트의 것이며, 길이가 심각도를 줄일 수 있는 규칙은 에이전트가 사용할 수 있는 규칙이 됩니다. 프롬프트는 사용자의 것이며, 그 길이를 신호로 취급하면 사양이나 스택 트레이스를 붙여넣는 행위에 불이익을 줄 뿐입니다.

## 머신에서 나가는 것

Jev가 평가하는 각 도구 호출에 대해 공급자에게 하나의 요청이 전송되며, 다음을 포함합니다.

- API 키, 베어러 토큰, `KEY=` 할당 등 시크릿이 편집된 도구 호출 자체
- 에이전트의 하니스가 추가한 텍스트를 제거한 최근 입력 프롬프트
- 에이전트의 최신 프롬프트 이전의 마지막 메시지(에이전트 작성으로 표시)
- 경로가 프로젝트 내부인지 여부 등 로컬에서 계산된 사실 — 세션의 첫 번째 검토된 호출 시점의 프로젝트([세션에 고정됨](/ko/reference/jev-intent#the-project-root)) — 및 현재 git 브랜치

구성의 엔드포인트로, 자체 키 하에서만 전송됩니다.

## 비활성화

```bash
failproofai jev remove
```

이 명령은 `~/.failproofai/jev.json`을 삭제합니다. 다음 도구 호출부터 훅은 이전과 동일하게 정규식 정책을 실행합니다. `~/.failproofai/state/semantic/` 아래의 세션별 저장소(세션의 경우 `sessions/`, 프로젝트 루트의 경우 `roots/`)는 그대로 남겨져 만료됩니다. Jev에 질문하는 것을 중단하되 구성을 유지하려면, 대신 `failproofai jev setup --mode off`를 사용하세요.

## 명령 참조

| 명령 | 결과 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 하나의 명령으로 구성. 공급자는 URL의 호스트에서 결정됨 |
| `failproofai jev --url <url> --token <token>` | 동일, 키를 명령줄에 직접 입력 — 히스토리와 프로세스 목록에 보임 |
| `failproofai jev setup --provider <kind> --key-stdin` | stdin으로 파이프된 키로 구성 작성 |
| `failproofai jev setup --provider <kind>` | 동일, 마스킹된 프롬프트에서 키 요청 |
| `failproofai jev setup --key-from-env` | 키 저장 없이 세션별 `FAILPROOFAI_JEV_API_KEY` 읽기 |
| `failproofai jev setup --mode observe` | 모드 전환(`enforce`, `observe` 또는 `off`), 저장된 키 유지 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 모델 또는 API 기본값 오버라이드. `default`로 오버라이드 초기화 |
| `failproofai jev setup --timeout-ms <n>` | 호출별 대기 시간 변경 |
| `failproofai jev status [--json]` | 구성, 권한 및 최근 활동. 키는 절대 표시 안 함 |
| `failproofai jev test [--json]` | 라이브 요청 1회: 지연 시간과 응답한 버전 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 엔드포인트의 `/models`가 보고하는 모델 ID 목록, 구성된 모델 표시 |
| `failproofai jev remove` | 구성 삭제. Jev 비활성화 |
