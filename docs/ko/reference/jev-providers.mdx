이 문서는 자체 키를 사용하는 [Jev 정책](/ko/policies/jev)의 제공자 및 구성 참조입니다. 정규식 정책은 문자열을 매칭합니다. `rm -rf build/`처럼 사용자가 직접 요청한 명령과 계획에 슬며시 포함된 `rm -rf ~`를 구별할 수 없기 때문에, 한쪽에서는 너무 많이 차단하고 다른 쪽에서는 너무 적게 차단하는 문제가 생깁니다. TypeSafe의 분류기 **Jev**는 실제로 사용자가 요청한 내용을 기준으로 호출을 분석하여, 단 한 번의 빠른 요청으로 일련의 예/아니오 질문에 답합니다.

자체 Jev 엔드포인트와 키를 구성하면, Failproof AI는 각 도구 호출에 대해 정규식 정책과 **함께** Jev에 질문합니다. Jev가 정규식 정책을 대체하는 것이 아닙니다:

- **하드** 정책의 거부는 최종적입니다. Jev가 이를 취소할 수 없습니다. 모든 정책은 명시적으로 검토 가능으로 표시되고 해당 정책을 커버하는 Jev 검사를 지정하지 않는 한 하드 정책입니다. 따라서 아무것도 명시하지 않은 커스텀, 팩, Cloud 정책은 하드 정책이며, 항상 활성화된 자기 보호 가드도 항상 하드입니다.
- **검토 가능** 정책의 거부는 취소될 수 있지만, Jev가 해당 정책이 다루는 정확한 우려 사항에 대해 질문을 받고 "여기에는 없음" 또는 "사용자가 이를 요청함"이라고 답한 경우에만 가능합니다. 사용자가 호출을 요청하지 않은 상황에서 우려 사항이 실제임을 발견한 검사는, 해당 검사의 자체 판정이 단순 경고에 불과하더라도 거부를 유지합니다. 도구 호출 전에는 경고가 에이전트를 중지시키지 않기 때문입니다. 그리고 해당 검사가 거부 가능한 항목(시크릿 노출, 자격 증명 유출, 파괴적 삭제 등)인 경우, 해당 호출에서는 아무것도 취소되지 않습니다.
- 호출이 사용자가 지시한 작업의 한 단계이고 그 이상으로 도달하지 않는 경우, 차단이 **경고**로 전환될 수 있습니다. Jev는 자체 거부를 경고로 완화하며, 그 경고—호출의 실제 문제를 명시하여—가 정책의 차단을 대체합니다.
- Jev는 정규식으로 설명할 수 없는 위해에 대해 자체적으로 경고하거나 거부할 수도 있습니다.
- Jev가 답할 수 없는 경우(타임아웃, 속도 제한, 서버 오류, 크레딧 없음, 예상치 못한 모델 버전), 해당 호출은 Jev 없이와 동일하게 정규식 결과를 받습니다.
- Jev는 전체 호출을 읽고 정확한 우려 사항에 대해 질문을 받은 경우가 아니라면, 정책만으로 허용되는 것보다 호출을 더 허용적으로 만들지 않습니다. 그보다 적은 것—전체를 보내기에 너무 큰 호출, 의심되는 주입—은 허가를 철회하고 모든 거부를 유지합니다.

<Note>
Jev 구성이 없으면 아무것도 변경되지 않습니다: 훅은 항상 해왔던 것처럼 정규식 정책을 그대로 실행합니다. 구성 자체가 옵트인 전체입니다.
</Note>

<Tip>
FailproofAI Cloud를 사용 중이신가요? 자체 키가 필요하지 않습니다: `jev:evaluate`를 가진 키로 연결된 머신은 조직 플랜으로 Jev를 사용할 수 있습니다. [FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud)를 참조하세요.
</Tip>

## 시작하기 전에

에이전트가 실행되는 머신에 **failproofai 1.0.8-beta.0 이상**을 설치하고 [지원되는 하네스](/ko/reference/harnesses)에 훅을 연결하세요. 새 머신이라면 [빠른 시작](/ko/start/quickstart)을 따르거나, Cloud를 사용하지 않는 경우 [로컬 적용 설정](/ko/start/setup#enforce-locally)을 따르세요. 설치된 CLI는 `failproofai --version`으로 확인하세요.

아래 제공자 중 하나에서 API 키를 받거나, 호환 가능한 엔드포인트와 해당 키를 준비하세요. Jev는 `PreToolUse` 또는 `PermissionRequest` 게이트에서 명명된 도구 호출을 검토합니다. 자체 판정을 내릴 수 있지만, 기존 정책 거부를 취소하려면 [검토 가능](/ko/policies/authority)으로 표시된 설치된 정책도 필요합니다. 하드 정책 거부는 최종적입니다.

## 제공자 선택

Jev는 다섯 가지 경로를 통해 접근할 수 있습니다. 그 중 하나의 키를 가져오세요.

| 제공자 | `--provider` | 엔드포인트 | 기본 모델 | 참고 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 정확한 버전 고정. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 요청은 제로 데이터 보존 엔드포인트로만 라우팅되며, 다른 제공자로의 폴백 없음. `typesafe/jev-1.13-20260917`과 같이 날짜가 포함된 버전을 보고함. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jev를 별칭으로만 명명하므로, 응답 버전이 미검증으로 기록됨. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | `--account-id` 필요. 측정 결과 키당 초당 약 6회 호출 전에 HTTP 429 발생. |
| 자체 엔드포인트 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | TypeSafe의 요청 본문을 수용하고 응답한 모델을 보고하는 모든 엔드포인트. `https`만 허용; 로컬 테스트를 위해 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`는 허용됨. |

<Warning>
Vercel의 자체 bring-your-own-key 기능을 사용하면, 실패한 요청이 Vercel의 자격 증명으로 자동 재시도됩니다. 모든 호출이 자체 TypeSafe 계정에만 청구되고 그 계정에서만 보이도록 해야 한다면, TypeSafe를 직접 사용하세요.
</Warning>

## 설정 방법

명령 하나로 엔드포인트와 키를 설정합니다. 기존 정책이 호출을 계속 결정하는 동안 Jev의 판정을 검사할 수 있도록 `observe` 모드로 시작하세요:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL이 제공자를 선택합니다

제공자를 명시적으로 지정할 필요가 없습니다: URL의 **호스트**가 제공자를 결정합니다.

| URL 호스트 | 제공자 | 추가 필요 사항 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| 기타 모든 호스트 | `custom` | — 제공한 URL이 베이스 URL |

이로부터 세 가지가 따릅니다:

- **제공자 자체 API인 URL은 오버라이드를 쓰지 않습니다.** `--url https://api.typesafe.ai/v1`은 `--provider typesafe`와 정확히 동일한 구성을 생성합니다. 알려진 제공자에서 다른 경로나 호스트를 지정하면 `--base-url`이 저장하는 것처럼 베이스 URL로 저장됩니다.
- **`--provider`는 여전히 추론을 오버라이드합니다.** 이를 통해 자체 호스트에서 제공자의 API를 말하는 프록시에 접근할 수 있습니다: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **호스트와 모순되는 `--provider`는 거부됩니다.** 추측하지 않습니다. `--provider openrouter --url https://api.typesafe.ai/v1`은 아무것도 쓰지 않고 이유를 설명합니다: 두 설정이 키가 전송될 위치에 대해 불일치합니다. 동일한 쌍은 `jev setup --base-url`과 대시보드의 Jev 설정에서도 거부됩니다. (`--provider custom`은 모순이 아닙니다—"이 URL을 그대로 사용하라"는 의미입니다—단, 커스텀 경로가 도달할 수 없는 계정별 엔드포인트를 가진 Cloudflare 호스트는 예외입니다.)

`--url`은 구성 파일의 `baseUrl`과 동일하게 검증되며, 동일한 이유로 거부됩니다: `https`, 또는 모든 모드에서 루프백 호스트(`localhost`, `127.0.0.1`, `::1`)에 대한 일반 `http`. 위험: 루프백 서버는 아무것도 인증하지 않으므로, 서버가 다운된 동안 다른 로컬 프로세스가 해당 포트를 차지하여 응답할 수 있습니다. 로컬 테스트 외에는 `https`를 사용하세요.

### 키

`--key-stdin`으로 파이프로 전달하거나, 없이 터미널에서 명령을 실행하고 마스크된 프롬프트에서 키를 붙여넣으세요. 어느 쪽이든 구성 파일에 직접 저장되며 다시 출력되지 않습니다.

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">

`failproofai jev setup`은 동일한 플래그를 받으며, URL보다 제공자를 명시적으로 지정하려는 경우 `setup --provider <kind>`를 사용합니다.

### `--token`과 비용

`--token <token>`은 키를 명령줄에 직접 입력합니다. 이는 머신을 가장 빠르게 구성하는 방법이지만, 구성 파일 외에 키가 남는 유일한 방법이기도 합니다:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
명령줄 인자는 이후 셸 히스토리 파일에 남으며, 명령이 실행되는 동안 프로세스 목록에도 나타납니다—사용자로 실행 중인 모든 것이 `/proc`에서 읽을 수 있습니다. `setup`은 `--token`이 사용될 때마다 이를 알립니다. 공유 머신, 녹화된 세션, 또는 히스토리 파일이 동기화되는 환경에서는 `--key-stdin`을 사용하세요. 이 방법으로 전달한 키는 중요한 경우 교체하세요.
</Warning>

`--token`, `--key-stdin`, `--key-from-env`는 상호 배타적입니다: 하나만 사용하세요.

그런 다음 소규모 실시간 요청을 하나 보내 키, 엔드포인트, 응답한 Jev를 확인하세요:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test`는 타임아웃 후 답변이 도착하거나(`timeout`으로 모든 훅이 정규식으로 폴백됨) 검사 질문에 잘못 답변하면 1을 반환하며 제목에 표시합니다.

훅은 모든 도구 호출 시 구성을 읽으므로, 다음 호출부터 적용됩니다. 데몬 유무에 관계없이 재시작할 필요가 없습니다.

## 동작 확인

```bash
failproofai jev status
failproofai jev status --json
```

`status`는 제공자, 엔드포인트, 모델, 모드, 구성 파일과 권한을 표시하며 키는 절대 표시하지 않습니다. 그 아래에 최근 활동을 요약합니다: Jev가 평가한 호출 수, 정규식으로 폴백한 횟수와 이유, 지연 시간, 취소한 검토 가능 정책.

## 실제 호출 확인

훅이 연결된 에이전트에서 새 세션을 시작하세요. `README.md`의 파일 읽기 도구를 사용하여 제목을 보고하도록 요청하세요. 세션에 해당 도구 호출이 포함되었는지 확인한 후 `failproofai jev status`를 다시 실행합니다: 최근 평가된 호출 수가 증가해야 합니다. [로컬 대시보드](/ko/reference/local-dashboard#review-policy-activity)의 **Policies → Activity**를 열어 호출의 Jev 판정과 모드를 검사하세요. observe 모드에서는 정책 결과가 여전히 호출을 결정합니다. 검토 가능한 정책이 매칭되고 Jev가 명명된 모든 검사를 취소한 경우에만 취소가 나타납니다. 일반 읽기에는 취소할 정책이 없을 수 있습니다.

## Observe 모드

`enforce`가 기본값입니다. Jev가 어떤 결정도 변경하지 않으면서 관찰하려면 `observe`로 전환하세요: Jev는 여전히 질문을 받고 판정이 기록되지만, 정규식 결과가 적용됩니다.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off`는 구성—엔드포인트와 키—을 유지하고 Jev 질문을 중단합니다: 훅은 구성 없이와 동일하게 정규식 정책을 실행하며, `failproofai jev status`는 "off (switched off)"를 표시합니다. `--mode observe` 또는 `--mode enforce`로 다시 전환하세요.

동일한 제공자로 `setup`을 다시 실행하면 저장된 키가 유지되므로, 모드 전환은 플래그 하나면 됩니다. 제공자를 전환하면 처음부터 시작하며 해당 제공자의 키를 요청합니다. 요청을 다른 호스트로 이동시키는 `--base-url`도 마찬가지입니다: 저장된 키는 키를 제공한 호스트나 제공자의 자체 API에만 전송됩니다.

## 구성 파일

모든 것은 `setup`이 작성하는 하나의 파일 `~/.failproofai/jev.json`에 있습니다:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 필드 | 의미 |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` 또는 `custom`—또는 `failproofai`. `failproofai`의 키는 이 파일 대신 FailproofAI Cloud 연결에서 가져옵니다([FailproofAI Cloud를 통한 Jev](/ko/reference/jev-cloud) 참조). |
| `apiKey` | `Authorization: Bearer <key>`로 전송됩니다. |
| `baseUrl` | `custom`에 필요; 그 외에는 제공자의 API 베이스를 대체합니다. `https`여야 합니다. `localhost`에 대한 일반 `http`는 `mode: observe`에서만 허용됩니다: 로컬 포트를 인증하는 것이 없으므로, 프록시가 다운된 동안 머신의 모든 프로세스(판정 대상 에이전트 포함)가 그 자리에서 응답할 수 있습니다. |
| `accountId` | Cloudflare 전용: 32자 소문자 16진수. |
| `model` | 제공자의 기본 모델 ID를 대체합니다. 버전이 지정된 ID는 Jev 1.13을 명시해야 합니다. API 키처럼 생긴 값은 거부되어 다시 출력되지 않으므로, `--model`에 붙여넣은 키는 저장되거나 모델로 전송되지 않습니다. |
| `timeoutMs` | 도구 호출이 Jev를 기다리는 시간. 100–10000, 기본값 3000. |
| `mode` | `enforce`(기본값), `observe`, 또는 `off`(구성 유지, Jev 실행 없음). |

세 가지 규칙이 이를 보호합니다:

- **소유자 전용.** 권한 `0600`으로 작성됩니다. 다른 사용자나 그룹이 읽거나 쓸 수 있는 사본은 **거부**되며, `chmod 600 ~/.failproofai/jev.json`을 실행하거나 `setup`을 다시 실행할 때까지 훅이 정규식으로 폴백합니다. 디렉토리도 확인됩니다: `~/.failproofai`는 다른 사람이 **쓰기 가능**해서는 안 됩니다. 거기에 쓸 수 있는 사람은 파일 자체의 권한에 관계없이 파일을 교체할 수 있기 때문입니다. `setup`은 그 쓰기 비트를 발견하면 제거합니다. `failproofai jev status`는 구성이 거부되었을 때 알리고 파일이 명명한 엔드포인트를 표시합니다: 다른 사람이 변경했을 수 있으므로, `chmod` 전에 자신의 파일인지 확인하세요. 그러한 파일에서 `setup`을 다시 실행하면 저장된 키는 제공자 자체 API에만 전달됩니다; 파일이 명명한 다른 엔드포인트는 키를 다시 필요로 합니다(`--key-stdin`), 또는 `--base-url default`로 요청을 제공자로 돌려보내세요.
- **전역 전용.** 저장소는 Jev를 활성화하거나, 다른 엔드포인트를 지정하거나, 모델을 선택할 수 없습니다: 프로젝트 내부의 `.failproofai/jev.json`은 무시되며, 제공자, URL, 모델, 계정 ID는 해당 파일에서만 읽힙니다—저장소의 에이전트 설정이 설정할 수 있는 환경에서는 절대 읽지 않습니다. (`FAILPROOFAI_HOME`은 이를 우회하는 방법이 아닙니다: Jev만 리디렉션하는 것이 아니라 정책을 포함한 전체 failproofai 디렉토리를 이동시킵니다.)
- **키만 환경에서 올 수 있습니다.** 파일에 `apiKey`가 없으면 `FAILPROOFAI_JEV_API_KEY`가 해당 세션에 대해 제공합니다(`setup --key-from-env`는 그런 파일을 작성합니다). 파일이 가진 키를 대체하지 않으며, 파일 없이 Jev를 활성화할 수 없습니다. 변수가 설정되지 않은 경우, Jev는 해당 셸에서 단순히 꺼집니다: `failproofai jev status`는 이를 알리고, 0을 반환하며 구성을 그대로 둡니다(`status --json`은 `"reason": "no-env-key"`와 함께 `"status": "key-missing"`을 보고합니다). `failproofaid` 데몬은 셸의 환경을 보지 않으므로, `failproofai config`로 설정한 머신에서는 파일에 키를 보관하세요.

## 어떤 Jev가 응답하는가

Failproof AI의 결정 임계값은 Jev 1.13에 맞게 보정되었으므로, 해당 패밀리에서 답변이 올 때만 사용됩니다: `jev-1.13.x`, 또는 OpenRouter의 `typesafe/jev-1.13-<date>`. 제공자가 Jev를 별칭으로만 명명하고 버전을 보고하지 않는 경우(Vercel, 그리고 버전을 말하지 않는 Cloudflare), 답변이 사용되지만 미검증으로 기록됩니다. `custom` 엔드포인트는 응답한 모델을 보고해야 합니다; 유일한 예외는 구성한 비버전 `--model` 이름으로, 그것이 반환될 때 동일한 방식으로 미검증으로 기록됩니다. 다른 버전을 보고하는 답변이나 버전을 보고하지 않는 `custom` 답변은 사용되지 않습니다: 해당 호출은 `model-mismatch` 이유로 정규식으로 폴백됩니다.

## Jev가 답할 수 없을 때

다음 각각은 해당 호출에 대해 정규식 결과로 폴백되며 그 이유와 함께 기록됩니다. `failproofai jev status`는 이를 합산합니다:

| 이유 | 원인 |
| --- | --- |
| `timeout` | `timeoutMs` 내에 답변 없음. |
| `http-429` | 제공자가 키의 속도를 제한함. |
| `rate-limited` | Failproof AI 자체 리미터가 전송 전 호출을 보류함: 초당 5개 요청, 최대 5개 버스트, 제공자가 `429`를 응답한 후 잠시 없음. 제공자가 아님. |
| `http-500`, `http-502`, `http-503`, … | 제공자의 서버 오류. 정확한 상태가 기록됨. |
| `out-of-credits` | HTTP 402: 제공자 계정에 크레딧이 없음. |
| `provider-refused` | Cloudflare에서 "Model execution failed (Payment error)"를 읽는 HTTP 402: 제공자가 이 요청에서 모델 실행을 거부함. 대개 청구 문제가 아니므로 크레딧 충전으로 해결되지 않음. |
| `http-401`, `http-403` | 키가 거부됨. |
| `http-404` | `<base>/systemone`에서 아무것도 제공되지 않으므로 베이스 URL이 잘못됨—`/systemone`이 추가되며, 모든 제공자는 버전 루트에서 제공함. `failproofai jev models`는 엔드포인트가 제공하는 것을 표시함. |
| `network` | 엔드포인트에 도달할 수 없음. |
| `http-301`, `http-302`, `http-307`, `http-308` | 엔드포인트가 리디렉션으로 응답함. 리디렉션은 절대 따르지 않으므로 답변은 항상 구성의 URL에서만 옵니다; `--base-url`을 최종 URL로 설정하세요. |
| `malformed` | 엔드포인트가 응답했지만 Jev 답변이 아님—JSON이 아닌 본문이거나 답변이 없음. |
| `cloudflare-error`, `cloudflare-incomplete` | Cloudflare의 엔벨로프가 실패를 보고하거나, 아직 완료되지 않은 작업. |
| `model-mismatch` | 1.13 이외의 Jev 버전이 응답하거나, `custom` 엔드포인트가 응답한 모델을 명시하지 않음. |
| `request-cut` | **중단이 아닙니다.** Jev가 응답했지만 호출의 일부만 보여져 답변이 아무것도 취소하지 않음. [Jev가 응답했지만 전체 호출에 대해서가 아닐 때](#when-jev-answered-but-not-on-the-whole-call) 참조. |

`failproofai jev status`는 `upstream-error`(제공자 자체 오류가 담긴 답변) 또는 `config`와 같은 더 드문 이유도 표시할 수 있으며, 명명할 수 없는 이유는 `other`로 합산됩니다.

`request-cut`이 이 표에 있는 이유는 `failproofai jev status`가 나머지와 함께 집계하고, 모든 거부를 그대로 두기 때문입니다. 여기서 제공자에 대해 아무것도 말하지 않는 유일한 이유입니다: 요청이 도착했고 Jev가 응답했습니다. 위의 모든 행과 달리, 그 답변은 여전히 중요합니다—Jev 자체의 거부나 경고가 버려지는 것이 아니라 정규식 결과 위에 적용됩니다. 따라서 연속적인 `request-cut`은 호출이 전체를 보내기에 너무 큰 상태로 평가자에 도달하고 있다는 의미이지, 엔드포인트에 문제가 있다는 것이 아닙니다. 크레딧 충전이나 URL 변경으로는 해결되지 않습니다.

## Jev가 응답했지만 전체 호출에 대해서가 아닐 때

두 가지 추가 상황이 발생할 수 있으며, 둘 다 Jev가 응답하지 못한 것이 아닙니다. 둘 다 호출이나 대화의 얼마나 많은 부분이 하나의 요청에 맞았는지에 관한 것입니다.

**호출 자체의 일부가 맞지 않았습니다.** 도구 호출은 고정된 예산 안에서 전송되며, 너무 큰 것—매우 큰 `Write`, 거대한 MCP 본문, 한도까지 채워진 명령—은 맞는 부분으로 전송됩니다. Jev는 여전히 응답하며 그 답변은 여전히 중요합니다: 자체 거부나 경고가 평소와 같이 적용됩니다. 하지만 **취소**할 수는 없습니다. 호출의 일부에 대한 판정은 호출에 대한 판정이 아니기 때문입니다. 따라서 모든 정책 거부가 유지되며, 호출은 `request-cut` 이유로 폴백으로 기록됩니다. `failproofai jev status`는 이를 위의 이유들과 함께 집계합니다. 이것이 주는 규칙: 호출을 더 크게 만들면 취소를 잃을 수 있으며, 취소를 살 수는 없습니다.

**메시지가 맞지 않았습니다.** 붙여넣은 긴 프롬프트, 에이전트의 마지막 메시지, 또는 이 평가자의 자체 저장소가 이미 한도를 초과한 프롬프트. **아무것도 변경되지 않습니다**: 호출은 다른 것과 동일하게 판정되고, 취소되고, 기록되며 폴백으로 계산되지 않습니다. 입력하는 내용의 길이는 판정을 결정하지 않으며, 잘림이 동의를 만들어낼 수 없습니다: 프롬프트가 이미 한도 초과 상태로 도착한 경우, "당신이 이것을 요청하지 않았다"는 것이 전혀 도출될 수 없는 결론이 됩니다.

둘의 경계는 누가 텍스트를 작성했느냐입니다. 호출은 에이전트의 것이고, 길이가 심각도를 줄일 수 있도록 허용하는 규칙은 에이전트가 사용할 수 있는 규칙이 됩니다; 프롬프트는 사용자의 것이고, 그 길이를 신호로 취급하는 것은 사양이나 스택 트레이스를 붙여넣는 것을 처벌할 뿐입니다.

## 머신에서 나가는 것

Jev가 평가하는 각 도구 호출에 대해, 하나의 요청이 제공자에게 전송되며 다음을 포함합니다:

- 도구 호출 자체, API 키, 베어러 토큰, `KEY=` 할당과 같은 시크릿은 편집됨;
- 최근에 입력한 프롬프트, 에이전트의 하네스가 추가한 텍스트는 제거됨;
- 최신 프롬프트 이전 에이전트의 마지막 메시지, 에이전트 작성으로 레이블됨;
- 경로가 프로젝트 내부인지 여부—첫 번째 검토된 호출 시 세션이 있던 것으로 [세션에 고정됨](/ko/reference/jev-intent#the-project-root)—및 현재 git 브랜치와 같이 로컬에서 계산된 사실.

구성에 있는 엔드포인트로만, 사용자의 키 아래에서 전송됩니다.

## 끄기

```bash
failproofai jev remove
```

이는 `~/.failproofai/jev.json`을 삭제합니다. 다음 도구 호출부터 훅은 이전과 동일하게 정규식 정책을 실행합니다. `~/.failproofai/state/semantic/` 아래의 세션별 저장소(세션의 경우 `sessions/`, 프로젝트 루트의 경우 `roots/`)는 그대로 남아 만료됩니다. Jev 질문을 중단하되 구성을 유지하려면 대신 `failproofai jev setup --mode off`를 사용하세요.

## 명령 참조

| 명령 | 결과 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 단일 명령으로 구성; 제공자는 URL의 호스트에서 결정됨 |
| `failproofai jev --url <url> --token <token>` | 동일, 명령줄에 키 포함—히스토리와 프로세스 목록에 나타남 |
| `failproofai jev setup --provider <kind> --key-stdin` | stdin으로 파이프된 키로 구성 작성 |
| `failproofai jev setup --provider <kind>` | 동일, 마스크된 프롬프트에서 키 요청 |
| `failproofai jev setup --key-from-env` | 키 저장 없이; 세션당 `FAILPROOFAI_JEV_API_KEY` 읽기 |
| `failproofai jev setup --mode observe` | 모드 전환(`enforce`, `observe` 또는 `off`), 저장된 키 유지 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 모델 또는 API 베이스 오버라이드; `default`로 오버라이드 초기화 |
| `failproofai jev setup --timeout-ms <n>` | 호출당 예산 변경 |
| `failproofai jev status [--json]` | 구성, 권한 및 최근 활동; 키는 절대 표시 안 함 |
| `failproofai jev test [--json]` | 실시간 요청 하나: 지연 시간과 응답한 버전 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 해당 엔드포인트의 `/models`가 보고하는 모델 ID, 구성된 것에 표시 |
| `failproofai jev remove` | 구성 삭제; Jev 꺼짐 |
