커스텀 정책은 트레이스나 감사 결과에서 발견된 장애 패턴을 에이전트가 작업하는 동안 실행되는 의사결정으로 전환합니다. 정책은 특정 행동을 허용하거나, 에이전트에게 지침을 제공하거나, 또 다른 사고를 유발하기 전에 행동을 차단할 수 있습니다.

동작이 여러분의 도구, 경로, 명령어, 환경, 또는 운영 규칙에 의존하는 경우 커스텀 정책을 사용하세요. 기존 제어 항목을 중복해서 만들지 않도록 먼저 [내장 정책 카탈로그](/ko/policies/builtin-catalog)를 확인하세요.

## 좁은 규칙부터 시작하기

이 정책은 명령어가 프로덕션을 대상으로 할 때만 파괴적인 Kubernetes 명령어를 차단합니다. 정확한 장애 모드 외의 모든 경우는 `allow()`를 반환합니다.

```ts
import { customPolicies, allow, deny } from "failproofai";

const DESTRUCTIVE_KUBECTL = /\bkubectl\s+(delete|replace)\b/i;
const PRODUCTION_TARGET = /(?:--context|--namespace|-n)\s+(prod|production)\b/i;

customPolicies.add({
  name: "block-destructive-production-kubectl",
  description: "Block destructive Kubernetes commands against production",
  match: { events: ["PreToolUse"] },
  fn: async ({ toolName, toolInput }) => {
    if (toolName !== "Bash") return allow();

    const command = String(toolInput?.command ?? "");
    if (!DESTRUCTIVE_KUBECTL.test(command)) return allow();
    if (!PRODUCTION_TARGET.test(command)) return allow();

    return deny(
      "Destructive production Kubernetes commands require the approved deployment workflow.",
    );
  },
});
```

좋은 정책은 한 문장으로 설명할 수 있을 만큼 충분히 좁아야 합니다. 에이전트의 의도가 아닌 관찰 가능한 행동에 매칭하고, 규칙이 적용되지 않는 즉시 `allow()`를 반환하세요.

## 결정 선택하기

| 헬퍼 | 결과 | 사용 시점 |
| --- | --- | --- |
| `allow(reason?)` | 작업이 계속됩니다. | 정책이 적용되지 않거나 행동이 안전한 경우. |
| `instruct(reason)` | 작업이 계속되며, 해당 채널이 있는 하네스에서 에이전트에게 이유가 전달됩니다. | 불변 조건을 강제하지 않고 에이전트를 더 나은 방향으로 유도하고 싶을 때. |
| `deny(reason)` | 차단 판정을 소비하도록 검증된 하네스와 이벤트 쌍에서 작업이 차단됩니다. | 행동이 진행되어서는 안 되는 경우. |

복구해야 하는 에이전트를 위해 이유를 작성하세요. 무엇이 감지되었고 대신 무엇을 해야 하는지 설명하세요.

### `instruct()`가 실제로 전달되는 곳

`instruct()`는 하네스에 추가 컨텍스트 채널이 필요합니다. 여섯 개의 하네스는 일부 또는 모든 이벤트에 대해 채널이 없으며, 이 경우 작업은 허용되고 메시지는 에이전트가 읽지 않는 stderr에 기록됩니다.

| 하네스 | 지시를 전달하는 이벤트 |
| --- | --- |
| Claude, Codex, Copilot, Cursor, Devin, OpenCode | `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `PermissionRequest`는 추가 컨텍스트로 전달됩니다. `Stop`과 `SubagentStop`은 대신 재시도 채널을 통해 전달됩니다. 다른 모든 이벤트는 하네스가 무시하는 메시지를 내보냅니다. |
| Antigravity | `UserPromptSubmit`과 `Stop`만 해당. |
| Factory, Pi, OpenClaw | `Stop`만 해당. |
| Hermes, Goose | 없음. 항상 허용되며 stderr에 메모가 기록됩니다. |

어떤 하네스도 29개의 모든 정식 이벤트를 실행하지 않으므로, 첫 번째 행은 각 하네스가 설치하는 이벤트로 제한됩니다 — 지시는 해당 하네스가 실제로 실행하는 이벤트에서만 전달됩니다. 특정 이벤트에 의존하기 전에 [에이전트 하네스](/ko/reference/harnesses)에서 하네스별 설치된 이벤트 집합을 확인하세요.

<Warning>
  안전 경계에는 `instruct()`를 사용하지 마세요. Hermes와 Goose에서는 에이전트에게 전혀 전달되지 않으며, Antigravity, Factory, Pi, OpenClaw에서는 도구 이벤트에서 전달되지 않습니다. 행동이 반드시 방지되어야 할 때는 `deny()`를 사용하세요.
</Warning>

## 정책 객체

```ts
customPolicies.add({
  name: "policy-name",
  description: "What this policy prevents",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => allow(),
});
```

| 필드 | 필수 여부 | 설명 |
| --- | --- | --- |
| `name` | 예 | 정책의 안정적인 식별자. 파일 간에 고유한 이름을 유지하세요. |
| `description` | 아니오 | 정책 목록과 결정 사항에 표시되는 사람이 읽을 수 있는 설명. |
| `match.events` | 아니오 | 정책을 호출하는 이벤트 유형. `match`를 생략하면 모든 이용 가능한 이벤트에 대해 호출됩니다. |
| `fn` | 예 | `allow`, `instruct`, 또는 `deny` 결과를 반환하는 동기 또는 비동기 함수. |

`fn` 내부에서 도구를 필터링하세요. `match.toolNames`는 공개 커스텀 정책 타입의 일부가 아닙니다.

팩 내에 게시된 정책은 `category`와 `defaultEnabled` 두 개의 추가 필드를 가질 수 있습니다. [파일에서 팩으로](#from-a-file-to-a-pack)를 참조하세요.

## 정책 컨텍스트

모든 정책은 `PolicyContext`를 받습니다.

| 필드 | 타입 | 포함 내용 |
| --- | --- | --- |
| `eventType` | `HookEventType` | 현재 평가 중인 정규화된 이벤트. |
| `toolName` | `string \| undefined` | `Bash`, `Read`, `Write`, `Edit`과 같은 정식 도구 이름. |
| `toolInput` | `Record<string, unknown> \| undefined` | 현재 도구 호출에 대한 정식 입력. |
| `payload` | `Record<string, unknown>` | 완전한 정규화된 이벤트 페이로드. |
| `session` | `SessionMetadata \| undefined` | 이용 가능한 경우 세션 ID, 작업 디렉토리, 트랜스크립트 경로, 권한 모드, 하네스 메타데이터. |
| `cli` | `string \| undefined` | `claude`, `codex`, `cursor`와 같은 소스 에이전트 하네스. |
| `params` | `Record<string, unknown>` | 이 정책에 대한 파라미터. 내장 또는 팩 정책은 스키마를 선언하고, 사용자가 구성한 값이 기본값 위에 병합됩니다. 커스텀 파일의 정책은 스키마를 선언하지 않으므로 해당 이름 아래 사용자가 구성한 내용을 받으며, 아무것도 구성되지 않은 경우 `{}`를 받습니다. |

모든 선택적 값은 진정으로 선택적인 것으로 취급하세요. 에이전트 버전과 이벤트 유형이 모두 동일한 필드를 제공하지는 않습니다.

### 일반적인 도구 입력

Failproof AI는 지원되는 하네스 전반에 걸쳐 일반적인 도구를 정규화하므로, 정책은 일반적으로 하나의 입력 형태를 사용할 수 있습니다.

| 도구 | 공통 필드 |
| --- | --- |
| `Bash` | `command` |
| `Read` | `file_path` |
| `Write` | `file_path`, `content` |
| `Edit` | `file_path`, `old_string`, `new_string` |
| `Grep` | `pattern`, `path` |

도구 입력 값이 `unknown`으로 타입화되어 있으므로 방어적 강제 변환을 사용하세요:

```ts
const command = String(ctx.toolInput?.command ?? "");
const filePath = String(ctx.toolInput?.file_path ?? "");
```

## 이벤트 선택하기

| 이벤트 | 실행 시점 | 일반적인 용도 |
| --- | --- | --- |
| `PreToolUse` | 도구 실행 전. | 명령어, 쓰기, 읽기, 외부 행동을 차단하거나 안내합니다. 이것이 가드입니다. |
| `PostToolUse` | 도구가 이미 실행된 후. | 모델이 읽는 결과를 검사하거나 교체합니다. 부작용을 되돌릴 수 없습니다 — 쓰기나 명령어는 이미 발생했습니다 — 그리고 12개 하네스 중 10개에서 판정이 아무것도 중단할 수 없습니다. Codex와 Copilot만 이를 소비하며, 거기서도 호출을 방지하는 것이 아니라 모델이 읽는 결과를 교체합니다. 가드로 사용하지 마세요. |
| `PermissionRequest` | 에이전트가 권한을 요청할 때. | 조직별 권한 규칙을 적용합니다. |
| `UserPromptSubmit` | 제출된 프롬프트가 계속되기 전. | 금지된 지시를 거부하거나 워크플로우 안내를 추가합니다. |
| `Stop` | 에이전트가 완료를 시도할 때. | 로컬 검증 단계와 같이 도달 가능한 완료 조건을 요구합니다. |
| `SubagentStop` | 하위 에이전트가 완료를 시도할 때. | 위임된 작업이 부모에게 반환되기 전에 게이트를 적용합니다. |
| `SessionStart` / `SessionEnd` | 세션 경계에서. | 세션 수준 상태를 기록하거나 확인합니다. |

이벤트 가용성과 차단 동작은 에이전트 하네스에 따라 다르며, 차이가 큽니다: Failproof AI는 Goose나 Hermes에 대한 `Stop` 훅을 설치하지 않으므로, 두 경우 모두 중단 게이트가 실행되지 않습니다. 혼합 플릿에서 이벤트에 의존하기 전에 [에이전트 하네스](/ko/reference/harnesses)를 확인하세요.

<Accordion title="모든 정책 이벤트 이름">
  `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `Elicitation`, `ElicitationResult`, `UserPromptExpansion`, `PostToolBatch`, `Setup`. 이것이 모든 하네스의 고유 이벤트 어휘가 정규화되는 29개의 정식 이벤트 이름의 전체 집합입니다.
</Accordion>

## 일반적인 정책 패턴 작성

### 보호된 경로에 대한 쓰기 차단

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "block-generated-file-edits",
  description: "Require generated files to be changed through their generator",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();

    const filePath = String(ctx.toolInput?.file_path ?? "");
    if (!/(^|\/)(dist|generated)\//.test(filePath)) return allow();

    return deny("Edit the source and run the generator instead of changing generated output.");
  },
});
```

### 비차단 안내 제공

```ts
import { customPolicies, allow, instruct } from "failproofai";

customPolicies.add({
  name: "prefer-reviewed-deploy-command",
  description: "Guide agents toward the reviewed deployment wrapper",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();

    const command = String(ctx.toolInput?.command ?? "");
    if (!/^kubectl\s+apply\b/.test(command.trim())) return allow();

    return instruct("Use ./scripts/deploy-reviewed instead of invoking kubectl directly.");
  },
});
```

### 세션 완료 게이트

```ts
import { execFileSync } from "node:child_process";
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "require-clean-typecheck",
  description: "Require the project typecheck to pass before the agent finishes",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow();

    try {
      execFileSync("bunx", ["tsc", "--noEmit"], {
        cwd,
        stdio: "ignore",
        timeout: 8_000,
      });
      return allow();
    } catch {
      return deny("Fix the typecheck errors before finishing the task.");
    }
  },
});
```

<Warning>
  거부된 `Stop` 이벤트는 에이전트가 재시도하게 만들 수 있습니다. 현재 환경에서 에이전트가 충족할 수 있는 조건에만 게이트를 적용하고, 모든 서브프로세스나 네트워크 호출에 시간 제한을 설정하세요.
</Warning>

## 정책 파일 로드

### 컨벤션 파일

컨벤션 파일은 자동으로 로드됩니다:

```text
<project>/.failproofai/policies/security-policies.ts
~/.failproofai/policies/personal-policies.mjs
```

- 프로젝트와 사용자 정책 디렉토리 모두 로드됩니다.
- 각 디렉토리 내에서 파일은 알파벳 순으로 로드됩니다.
- 파일은 반드시 `policies.js`, `policies.mjs`, 또는 `policies.ts`로 끝나야 합니다.
- 하나의 파일에서 여러 번 `customPolicies.add()`를 호출하는 것이 지원됩니다.
- 로컬 모듈에서의 상대 임포트가 지원됩니다.
- 프로젝트 정책은 커밋할 수 있으므로 동일한 규칙이 저장소를 따릅니다.

<Warning>
  이름이 `policies.{js,mjs,ts}`로 끝나지 않는 디렉토리 내 파일은 건너뜁니다. 설치된 것처럼 보이지만 아무것도 강제하지 않습니다. 로더는 건너뛴 모든 파일을 변경할 이름과 함께 나열합니다. 정책이 활성화되었다고 가정하지 말고 해당 경고를 읽으세요. 이 저장소에서 `block-version-bumps.mjs`를 그런 방식으로 배포했고, 잘못된 버전 범프 이후 작성된 가드는 한 번도 실행되지 않았습니다.
</Warning>

`~/.failproofai/policies/`에는 여러분이 생성하지 않은 두 개의 하위 디렉토리도 있습니다: 플릿 관리 배포용 `cloud-policies/`와 설치된 팩용 `packs/`. 로더는 두 곳 모두에 내려가지 않으므로, 그 안의 내용은 검증되지 않은 컨벤션 정책으로 가져오지 않습니다.

### 발견된 정책 비활성화

`policies-config.json`의 두 키는 파일을 삭제하거나 이름을 변경하지 않고 컨벤션 정책을 비활성화합니다:

| 키 | 효과 |
| --- | --- |
| `disabledCustomPolicies` | 등록되지 않는 소스 정규화된 정책 ID의 배열. |
| `customPoliciesEnabled` | `false`로 설정하면 `.failproofai/policies/` 로드를 완전히 중단합니다. 없으면 활성화됨을 의미합니다. |

[로컬 대시보드](/ko/reference/local-dashboard)의 **Policies → Configure** 탭이 `disabledCustomPolicies`를 대신 작성합니다. `customPoliciesEnabled`는 `failproofai config`로 작성하거나 직접 작성합니다.

### 명시적 파일

유효성 검사나 구성에서 진입 파일을 직접 지정해야 할 때 명시적 경로를 사용하세요:

```bash
failproofai policies --install \
  --custom ./security.policies.ts \
  --custom ./workflow.policies.ts \
  --scope project
```

명시적 파일이 먼저 로드되고, 그 다음 프로젝트 컨벤션 파일, 그 다음 사용자 컨벤션 파일이 로드됩니다. 두 경로 모두를 통해 발견된 파일은 한 번만 로드됩니다.

## 유효성 검사 및 테스트

`-c`는 `--custom`의 단축형이고, `-i`는 `--install`의 단축형입니다. 모든 경로와 파일명에서 즉시 파일을 적용합니다:

```bash
failproofai policies -i -c ./checkout-policies.ts
failproofai policies
```

에이전트에게 차단된 작업을 요청하고 거부되는 것을 확인하세요. 아무것도 게시되지 않으며 다른 머신에는 영향을 주지 않습니다.

유효성 검사는 프로덕션 로더를 통해 모듈을 실행하고 최소 하나의 정책이 등록되었는지 확인합니다. 누락된 파일, 구문 오류, 해결되지 않은 임포트, 최상위 예외, 모듈 로드 타임아웃을 잡아냅니다. 매칭 로직이 올바른지는 증명하지 않습니다.

최소한 다음 케이스를 테스트하세요:

- 반드시 일치하고 의도된 정책 이유를 생성해야 하는 행동 하나.
- 반드시 `allow()`를 반환해야 하는 유사하지만 안전한 행동 하나.
- 누락되거나 잘못된 형식의 도구 필드.
- 대체 명령어 구문, 경로, 인용, 대소문자, 공백.
- 이용 불가능한 서브프로세스 또는 네트워크 의존성.

로컬 대시보드의 **Policies → Activity**에서 결과를 커스텀 정책에 귀속시키세요. 다른 내장 정책이 결정을 내렸다면 차단된 테스트로는 충분하지 않습니다.

## 런타임 동작

- 내장 정책이 커스텀 정책보다 먼저 평가됩니다.
- 첫 번째 `deny`가 추가 정책 평가를 중단합니다.
- 정책이 이벤트를 거부하지 않는 경우 여러 `instruct` 결과를 결합할 수 있습니다.
- 정책 함수의 실행 데드라인은 10초입니다. 최상위 모듈 로딩도 동일한 데드라인을 가집니다.
- 발생한 예외나 타임아웃은 로깅되고 `allow()`로 처리됩니다.
- 로드에 실패한 컨벤션 파일은 건너뜁니다; 다른 커스텀 파일과 내장 정책은 계속됩니다.
- Observe 모드는 정책을 실제로 실행하고 강제 적용 없이 allow가 아닌 모든 판정을 기록합니다. 두 레이어에서 설정됩니다: 게시한 팩에 `failproofai publish --effect observe`, Cloud 배포에 `fp fleet deploy <machine> --add <id>:observe`. 어느 쪽이든 정책은 강제 적용 정책과 동일한 10초 데드라인 아래에서 평가되므로, 타임아웃된 정책은 allow로 기록됩니다.

### 로더가 대신 실패 시 닫히는 경우

위의 fail-open 규칙은 직접 추가한 파일을 다룹니다. 두 경로는 의도적으로 반대로 동작합니다. 두 경우 모두 이 머신에 없는 강제 적용이 있다고 알려졌음을 의미하기 때문입니다.

| 상황 | 결과 |
| --- | --- |
| 선택된 팩을 로드할 수 없거나 고정된 다이제스트가 일치하지 않음 | 해당 팩이 선언한 범위의 모든 이벤트가 거부되며, `pack/failproofai-pack-unavailable`로 귀속됩니다. `UserPromptSubmit`은 거부 대신 지시하므로, 수정에 필요한 에이전트에서 절대 잠기지 않습니다. 읽을 수 없는 팩 메타데이터는 거부 범위를 좁히는 것이 아니라 넓힙니다. |
| 설정을 완료한 머신에서 `failproofaid` 데몬에 도달할 수 없음 | 모든 이벤트가 거부됩니다. 도달할 수 없었던 데몬이 구성을 실행할 수도 없었을 것이므로, 어떤 구성도 읽히지 않고 어떤 커스텀 정책도 실행되지 않습니다. 프로토콜 버전 불일치도 거부되며, `failproofai config`를 지정하는 메시지가 표시됩니다. |

설정을 완료한 머신에서 `failproofaid`가 유일한 평가자이므로, 여러분의 `fn`은 훅 프로세스가 아닌 데몬의 웜 워커 내에서 실행됩니다. 훅 클라이언트는 연결에 150ms, 응답에 30초를 허용하며, 각 정책 함수가 받는 고정된 10초 데드라인보다 충분히 여유 있습니다.

정책 모듈을 결정론적이고 빠르게 유지하세요. 최상위 네트워크 호출이나 서버 시작을 피하세요. `fn` 내부에서 작업을 제한하고, 의존성 실패를 처리하며, 해당 실패가 작업을 허용해야 하는지 거부해야 하는지 의도적으로 선택하세요.

## 파일에서 팩으로

팩은 정책 파일을 다른 머신이 설치할 수 있는 것으로 만드는 방법입니다. 두 가지 명령어로 아무것도 없는 상태에서 게시된 팩까지 갈 수 있습니다:

```bash
failproofai publish --init
failproofai publish
```

`--init`은 팩 이름을 묻고, `<name>.mjs`를 작성한 후 멈춥니다. 이 파일은 빈칸이 있는 템플릿이 아니라 `git push --force`를 이미 차단하는 하나의 정책이므로, 처음 편집할 때는 작동하는 것을 편집하게 됩니다. `failproofai policies -i -c ./<name>.mjs`로 로컬에서 검증한 후, 그것을 담고 있는 git 저장소 내에서 `failproofai publish`를 실행하세요.

팩에 정책이 배포되면 두 가지 필드가 중요합니다:

| 필드 | 역할 |
| --- | --- |
| `category` | `failproofai policies add <owner>/<repo> --category git,database`가 선택하는 기준. |
| `defaultEnabled` | 단순히 `failproofai policies add <owner>/<repo>`를 실행할 때 이 정책이 활성화되는지 여부. 기본값은 `false`. |

`--effect`는 정책별이 아닌 팩별로 설정됩니다: `failproofai publish --effect observe`는 정책이 결정했을 내용을 기록하고 아무것도 차단하지 않는 팩을 게시합니다. 기본값은 `enforce`입니다. 이것은 Cloud 연결 없이 단일 머신에서의 observe 모드입니다 — 로컬 대시보드의 **Policies → Activity**에서 기록된 판정을 확인하세요.

팩의 버전은 빌드된 12자 짧은 커밋 sha이므로, `publish`는 git 체크아웃 외부나 더티 트리에서는 거부됩니다. 전체 흐름은 [팩 게시하기](/ko/policies/publish-a-pack)를 참조하고, 설치 시 버전 해결 방법은 [정책 팩](/ko/policies/packs)을 참조하세요.

## API 내보내기

| 내보내기 | 목적 |
| --- | --- |
| `customPolicies.add(policy)` | 모듈이 로드될 때 커스텀 정책을 등록합니다. |
| `allow(reason?)` | 작업을 허용합니다. |
| `instruct(reason)` | 작업을 허용하고 지원되는 경우 안내를 제공합니다. |
| `deny(reason)` | 지원되는 경우 작업을 차단합니다. |
| `getCustomHooks()` | 모듈 레지스트리에 현재 등록된 정책을 반환합니다. |
| `clearCustomHooks()` | 해당 레지스트리를 지웁니다. 주로 테스트와 로더에 사용됩니다. |

TypeScript는 `PolicyContext`, `PolicyResult`, `CustomHook`, `PolicyDecision`, `PolicyFunction`을 내보냅니다.
