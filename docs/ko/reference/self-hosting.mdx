## 사전 요구 사항

- cluster-admin 접근 권한이 있는 Kubernetes 1.27 이상
- Kustomize 지원이 포함된 `kubectl`
- Helm 3
- 비공개 `ghcr.io/agenteye-enterprise` 이미지에 대한 접근 권한
- 대시보드용 및 인제스트용 각각의 DNS 이름
- PostgreSQL 및 ClickHouse를 위한 영구 스토리지
- cert-manager 및 Traefik, 또는 오버레이에 맞게 조정된 동급의 인그레스 및 인증서 인프라
- 프로덕션 OTP 로그인 및 알림을 위한 SMTP

소스 트리에는 AWS/EKS 지향 오버레이와 별도의 GCP/GKE 오버레이가 포함되어 있습니다. 두 오버레이의 인증서, 로드 밸런서, 백업 설명을 혼합하지 마세요. GKE는 자체적인 DNS-01, GCS, 오토스케일링 구성을 사용합니다.

## 배포 순서

<Steps>
  <Step title="클러스터 준비">
    cert-manager와 공개/대시보드 인그레스 컨트롤러를 설치하고 로드 밸런서를 확인한 후, 네임스페이스, 이미지 풀 자격증명, 데이터베이스 자격증명, 부트스트랩 관리자 키, 인증/SMTP 시크릿을 생성합니다.
  </Step>
  <Step title="퍼블릭 도메인 구성">
    오버레이의 생성된 도메인 환경 파일에서 `INGEST_DOMAIN`과 `DASHBOARD_DOMAIN`을 설정하고, 해당 로드 밸런서를 가리키는 DNS 레코드를 생성합니다.
  </Step>
  <Step title="플랫폼 오버레이 적용 및 검증">
    customer/EKS 또는 GCP 오버레이를 사용합니다. 렌더링된 Kustomize 출력을 검토하고 적용한 후, 머신을 등록하기 전에 모든 워크로드와 인증서가 의도한 상태에 도달했는지 확인합니다.
  </Step>
  <Step title="접근 및 인제스트 부트스트랩">
    보호된 관리자 계정으로 로그인하고, 조직 범위의 머신 키를 생성한 후, 퍼블릭 인제스트 엔드포인트를 통해 소규모 테스트 세션을 전송합니다.
  </Step>
</Steps>

## 필수 및 선택적 서비스

| 컴포넌트 | 요구 사항 |
| --- | --- |
| ClickHouse | 필수. 정규 이벤트 스토어 없이는 서버가 시작을 거부합니다. |
| PostgreSQL | 사용자, 조직, 저장된 객체, 컨트롤 플레인 상태에 필수입니다. |
| Redis | 선택 사항. 사용할 수 없는 경우 서버와 대시보드는 데이터베이스 기반 동작으로 저하됩니다. |
| SMTP | 개발 환경에서는 선택 사항이며, 프로덕션 이메일 OTP 및 알림 전달에는 필수입니다. |
| Evaluator | 선택 사항. `EVALUATOR_ENDPOINT` 없이는 자동 평가가 비활성화 상태로 유지됩니다. |
| Assistant/audit LLM | 선택 사항. LLM 연결이 구성되기 전까지 Assistant 및 LLM 기반 감사 기능은 비활성 상태입니다. |
| 오브젝트 스토리지 백업 | PostgreSQL 및 ClickHouse 백업 아카이브에 강력히 권장됩니다. |

### 감사 용량 및 실패 전달

가능한 경우 전용 audit-agent 배포에서 감사를 실행하세요. 각 audit-agent 파드는 기본적으로 하나의 조사를 수락합니다. 파드당 동시성을 높이고 메모리도 함께 늘리지 않는 한, 레플리카로 처리량을 확장하세요. 서버는 `서버 레플리카 수 × AUDIT_WORKERS`만큼의 감사를 동시에 디스패치할 수 있으므로, 디스패처 용량은 audit-agent 플릿을 채울 수 있을 만큼 충분해야 합니다.

모든 audit-agent 슬롯이 사용 중이면 감사는 최대 카던스의 4분의 1, 최대 6시간까지 대기하며 재시도합니다. 슬롯이 확보되지 않으면 실행이 결과 없이 완료되고 실패 이메일이 전송됩니다. "busy" 실패가 반복되면 audit-agent 레플리카를 늘리거나 스케줄 앵커 간격을 더 넓게 설정하세요. "shutting down" 실패가 반복되면 용량 부족이 아닌 불안정한 파드 또는 반복되는 롤아웃을 의미합니다.

실패 알림에는 활성화된 이메일 채널과 SMTP가 필요합니다. 감사의 수신자를 사용하며, 감사에 이메일 채널이 없는 경우 `alerts.email_default_recipients`로 폴백합니다.

## 배포 검증

<Tabs>
  <Tab title="대시보드">
    1. 구성된 대시보드 도메인을 열고, 관리자 OTP 흐름을 완료한 후 조직 이름과 슬러그를 확인합니다.
    2. **Administration → Keys**로 이동하여 범위가 좁은 머신 키를 생성합니다.
    3. 테스트 세션을 전송한 후 **Observe → Events** 및 **Observe → Sessions**에서 확인합니다.
    4. 알림 채널을 테스트하고, 구성된 경우 수동 평가 및 감사도 테스트합니다.
  </Tab>
  <Tab title="CLI">
    ```bash
    kubectl get pods -n agenteye
    kubectl get certificates -n agenteye
    kubectl logs -n agenteye deploy/server --tail=100

    fp --base-url https://failproof.example.com login
    fp --base-url https://failproof.example.com whoami
    fp --base-url https://failproof.example.com usage
    ```

    프로덕션 머신을 등록하기 전에 퍼블릭 헬스 엔드포인트와 인증된 `/v1` 요청 하나를 검증하세요.
  </Tab>
</Tabs>

## 인증 및 이메일

대시보드는 이메일과 일회용 코드를 사용합니다. SMTP가 없는 경우, 개발 배포에서는 OTP 코드를 서버 출력에 로깅합니다. `SMTP_HOST`가 설정된 경우, 사용자명, 비밀번호, 발신자는 그룹으로 함께 필요하며 그렇지 않으면 서버가 시작을 거부합니다.

`SMTP_TLS`는 boolean 값입니다. 지원되는 암호화 전송 방식은 STARTTLS이며, 일반적으로 포트 587을 사용합니다. 포트 465의 묵시적 SMTPS는 현재 서버 전송에서 지원되지 않습니다.

OTP, 알림, 인시던트, 감사 이메일이 딥 링크에 이를 사용하므로 퍼블릭 대시보드 URL을 올바르게 설정하세요. 조직 멤버십은 코드를 요청할 수 있는 사용자를 제어하며, 각 조직은 **Administration → Settings**에서 자체 멤버 로그인을 추가로 제한할 수 있습니다.

## 멀티 테넌트 요구 사항

두 번째 조직을 생성하기 전에, 강력하고 안정적인 조직 ClickHouse 파생 시크릿을 구성하고 모든 서버 레플리카에서 동일하게 유지하세요. 조율된 마이그레이션 없이 이를 교체하면 조직별 ClickHouse 사용자가 고아 상태가 될 수 있습니다.

인스턴스 관리자 리스너는 내부용으로 유지하세요. 제공된 운영자 콘솔은 옵트인 방식이며 퍼블릭 인그레스가 아닌 `kubectl port-forward`용으로 설계되었습니다. 이를 활성화하려면 자체적인 강력한 API 키, 슈퍼 관리자 메일박스, 그리고 작동하는 SMTP 2단계 인증 전달이 필요합니다.

### Break-glass 조직 CLI

`agenteye-orgctl`은 서버 이미지에 내장되어 있으며 PostgreSQL 및 ClickHouse와 직접 통신합니다. 퍼블릭 서버나 운영자 콘솔이 비정상 상태일 때도 사용 가능합니다.

```bash
kubectl -n agenteye exec deploy/server -- \
  agenteye-orgctl org create --slug acme --name "Acme Corp"
kubectl -n agenteye exec deploy/server -- agenteye-orgctl org list
kubectl -n agenteye exec deploy/server -- \
  agenteye-orgctl member add --org acme --email ops@acme.com --set admin --protected
```

지원되는 조직 작업으로는 생성, 목록 조회, 이름 변경, 소프트 삭제, 복원, ClickHouse 사용자 재프로비저닝, 청구일 관리, 피처 플래그, 비가역적 삭제가 있습니다. 멤버 작업으로는 추가, 목록 조회, 업데이트, 제거, 권한 재정의, 보호된 관리자 상태 관리가 있습니다.

삭제 전에 소프트 삭제를 먼저 사용하세요. `org purge`는 비가역적이며 조직이 먼저 삭제된 상태여야 합니다. 보호된 멤버는 운영자가 명시적으로 보호를 해제하기 전까지 조직의 일반 Users 페이지를 통해 제거하거나 권한을 강등할 수 없습니다.

## 프로덕션 준비 체크리스트

- 인제스트 및 대시보드 DNS가 의도한 각각의 인그레스 경로로 확인됩니다.
- TLS가 유효합니다. 배포 요구 사항에 따라 인제스트에 상호 TLS를 사용하세요.
- PostgreSQL 및 ClickHouse 볼륨에 용량 알림이 설정되어 있습니다.
- 백업에 두 데이터스토어가 모두 포함되어 있으며 테스트된 복원 절차가 있습니다.
- 헬스 체크가 인제스트 무음, 실패한 워크로드, 인증서 만료, 스토리지 압박, 오래된 백업에 대해 알림을 보냅니다.
- 기존 클러스터 로그 파이프라인을 중복하지 않고 구조화된 로그가 수집됩니다.
- 측정된 큐 증거 없이는 Evaluator, 감사, 알림 워커 동시성이 변경되지 않았습니다.
- 업그레이드 전에 고정된 애플리케이션 릴리스와 롤백 절차가 기록되어 있습니다.
