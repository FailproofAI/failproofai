대시보드는 저장된 쿼리를 조합하여 운영 현황을 한눈에 볼 수 있는 뷰를 만듭니다. 가용한 모든 지표가 아닌, 누군가가 내려야 할 의사결정을 중심으로 구성하세요.

대시보드는 클라우드 기능입니다. `localhost:8020`의 로컬 대시보드는 정책 활동, 프로젝트, 세션, 감사 결과를 다루지만 저장된 쿼리나 타일이 없으므로, 연결되지 않은 머신에서는 여기서 구성할 내용이 없습니다. [로컬 대시보드](/ko/reference/local-dashboard)를 참조하세요.

## 대시보드 만들기

<Tabs>
  <Tab title="대시보드">
    1. **Analyze → Queries**로 이동하여 저장된 쿼리를 만들거나 열고 결과를 검증합니다.
    2. **add to dashboard**를 선택한 후, 기존 대시보드를 선택하거나 **Analyze → Dashboards**에서 새로 만듭니다.
    3. 대시보드를 열고 편집 모드로 진입하여 타일을 배치한 뒤 레이아웃을 저장합니다.
    4. 타일의 데이터나 필터를 변경해야 할 때는 해당 쿼리로 돌아갑니다.

    ![이벤트 볼륨, 오류, 레이턴시, 모델 토큰 사용량에 대한 저장된 쿼리로 구성된 대시보드.](/images/dashboard/dashboard-fleet.png)
  </Tab>
  <Tab title="CLI">
    대시보드 CRUD는 현재 Cloud CLI에 노출되어 있지 않습니다. CLI를 사용하여 저장된 쿼리를 작성하고 검증한 후, UI에서 대시보드에 추가하세요.

    ```bash
    fp query schema
    fp query run --sql "select count(*) from analytics.events"
    fp query create "event volume" --sql "select count(*) from analytics.events"
    fp query run "event volume"
    ```

    먼저 `--sql`로 SQL을 실행하세요. 이 명령은 아무것도 저장하지 않고 동일한 읽기 전용 분석 풀에서 실행되므로, 타일이 오류를 발견하기 전에 잘못된 컬럼 이름을 미리 찾을 수 있습니다. `--sql @file.sql`은 파일에서 구문을 읽어옵니다. `fp query schema`는 쿼리 가능한 테이블과 해당 컬럼을 나열하며, 테이블 이름을 전달하면 해당 테이블로 범위를 좁힐 수 있습니다.

    저장된 쿼리는 id가 아닌 **이름**으로 참조합니다 — `fp query run "event volume"` — `fp query list`는 `--show-id`를 전달하지 않으면 원시 id를 숨기기 때문입니다. UUID 형태의 id도 허용됩니다.

    매개변수화된 타일의 경우, 각 위치 인수 `$1..$N`을 `--arg`로 바인딩합니다. `--arg`는 반복 사용이 가능하며 순서대로 바인딩됩니다: `fp query run <name> --arg checkout-agent`.

    `--limit`과 `--all`은 테이블 미리보기 상한만 조정합니다. `--json`은 항상 모든 행을 `{columns: [{name, type}], rows: [[...]], truncated, elapsed_ms}` 형식으로 반환합니다.

    | 서브커맨드 | 권한 |
    | --- | --- |
    | `query list`, `query show`, `query schema` | `queries:read` |
    | `query create`, `query update` | `queries:write` |
    | `query run` | `queries:run` |
    | `query delete` | `queries:delete` |

    쿼리 **이름**을 사용하는 모든 서브커맨드는 먼저 조직의 쿼리 목록을 조회하여 이름을 해석하므로, `query create`, `query update`, `query delete`, `query run <name>`은 위 권한 외에 `queries:read`도 필요합니다. `fp query run --sql`과 `fp query schema`만 해당되지 않습니다.

    `fp query`는 API 키 모드에서 차단되지 않으므로, 대시보드 쿼리를 CI에서 생성하고 검증할 수 있습니다.
  </Tab>
</Tabs>

유용한 대시보드 그룹의 예시:

- **모델:** 볼륨, 레이턴시, 토큰 사용량, 오류율, 평가 점수.
- **평가:** 에이전트 또는 환경별 성공률 및 점수 추이.
- **도구:** 호출 볼륨, 실패율, 소요 시간, 반복 호출.
- **훅 및 정책:** 결정, 거부, 정책 매칭율.
- **커스텀 워크플로우 지표:** 자체 이벤트 필드 및 SQL에서 나온 결과.

저장된 쿼리부터 시작하여 결과를 검증한 후 타일로 추가하세요. 테스트 트래픽이 회귀를 숨기지 않도록 프로덕션과 개발 필터를 명시적으로 유지하세요.

<Warning>
  행 수를 집계하는 훅 타일은 잘못된 분모를 보고합니다. 기본 훅 verbosity에서는 모든 deny와 instruct가 `hook_triggered` / `hook_completed` 쌍으로 발행되며, observe 모드의 allow도 마찬가지입니다. 일반 allow는 세션, 이벤트, 도구, 정책 귀속별로 분당 하나의 `hook_completed`로 롤업되어 `failproofai_allow_count`를 전달합니다. 행 수를 세는 대신 해당 필드를 합산하세요. 그렇지 않으면 수만 건의 호출을 평가한 플릿이 수백 건만 평가한 것처럼 보입니다. [정책 결정](/ko/sessions/policy-decisions) 및 [훅](/ko/sessions/hooks)을 참조하세요.
</Warning>

<Tip>
  모든 대시보드에 소유자와 "checkout-agent의 신뢰성이 지난주보다 나빠졌는가?"와 같은 응답 질문을 지정하세요.
</Tip>
