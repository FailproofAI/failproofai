트레이스는 하나의 에이전트 실행에 대한 타임라인입니다. 최종 오류가 아닌, 첫 번째 예상치 못한 이벤트부터 분석을 시작하세요.

<Tabs>
  <Tab title="대시보드">
    1. **Observe → Sessions**을 엽니다.
    2. 세션을 선택합니다.
    3. 첫 번째 오류, 비정상적인 도구 호출, 긴 대기 시간, 또는 정책 결정을 찾습니다.
    4. 이벤트를 열어 요청, 응답, 입력, 출력을 확인합니다.

    ![실행 그래프, 이벤트 타임라인, 평가 패널, 도구·모델·훅 분석이 포함된 세션 상세 보기 화면.](/images/dashboard/session-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp --json sessions --session-id <session-id>
    fp events --session-id <session-id> --order asc --all --limit 5000
    fp --json events --full --session-id <session-id> --all --limit 2000
    ```

    이벤트 요약만으로 충분한 근거를 얻기 어려울 때만 `--full`을 사용하세요. `next_cursor`가 null이 아니면 끝에 도달하기 전에 limit에 걸렸다는 의미입니다.
  </Tab>
</Tabs>

## 근거를 따라가기

1. 에이전트, 목표, 환경, 결과를 확인합니다.
2. 첫 번째 오류 또는 예상치 못한 결정을 찾습니다.
3. 해당 이벤트 바로 직전의 이벤트를 살펴봅니다.
4. 요청과 응답 쌍에서 일치하는 ID를 따라 추적합니다.
5. 수집한 근거를 감사, 이슈, 또는 정책으로 전환합니다.

| 쌍 | 매칭 필드 |
| --- | --- |
| 모델 요청과 응답 | `request_id` |
| 도구 호출과 결과 | `tool_call_id` |
| 훅 시작과 완료 | `hook_id` |
| 에이전트 일시정지와 재개 | `pause_id` |
| 사람 대기와 입력 | `input_id` |

결정 내용은 `hook_completed`에 나타납니다. 해당 행에는 결과와 정책 출처가 표시됩니다. 관찰 모드의 결정은 allow로 나타나며, 실제로 내려졌을 판정은 `failproofai_observed`에 기록됩니다.

<Warning>
  세션 지속 시간이 길다고 해서 항상 모델 지연이 원인은 아닙니다. 무엇을 수정할지 결정하기 전에 모델, 도구, 훅, 사람 대기 시간을 각각 분리해서 분석하세요.
</Warning>
