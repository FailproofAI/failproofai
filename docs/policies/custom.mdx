Check the [builtin catalog](/policies/builtin-catalog) before writing a policy. A reviewed rule is usually safer than a new one.

## Start from a working policy

```bash
failproofai publish --init guards.mjs
failproofai policies -i -c ./guards.mjs
```

The starter blocks `git push --force`. Edit it, ask your agent to try the blocked action, and inspect **Policies → Activity**.

```js
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production",
  description: "Production changes need a human",
  match: { events: ["PreToolUse"], toolNames: ["Bash"] },
  fn: async (ctx) =>
    String(ctx.toolInput?.command ?? "").includes("production")
      ? deny("Ask a human before changing production.")
      : allow(),
});
```

A policy returns `allow()`, `deny(message)`, or `instruct(message)`. Use `deny` when the action must stop; not every harness can deliver an instruction back to the agent.

## Load automatically

Put files named `*policies.js`, `*policies.mjs`, or `*policies.ts` under:

- `.failproofai/policies/` for one project.
- `~/.failproofai/policies/` for your user.

## Test failure paths

Test both the unsafe action and legitimate work that looks similar. Confirm the decision came from your policy rather than another rule.

Remove explicit test files with:

```bash
failproofai policies -u -c
```

When the policy is ready, [publish a pack](/policies/publish-a-pack) or [deploy it through Cloud](/policies/deploy).
