A policy watches an agent action and returns one of three decisions:

- `allow` continues.
- `instruct` gives the agent guidance when its harness supports it.
- `deny` blocks the action.

Use policies for known, repeatable behavior: deleting protected files, exposing secrets, pushing to the wrong branch, or changing production infrastructure.

## Add policies to this machine

Setup chooses no policy pack. Add the Failproof AI pack after setup:

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai policies
```

The package does not contain a privileged built-in pack. Ours installs the same way as anyone else's.

Policies can also come from a local file, a published pack, or a Cloud assignment:

| Source | Add it |
| --- | --- |
| Local file | Put `*policies.{js,mjs,ts}` under `.failproofai/policies/` |
| Any file path | `failproofai policies -i -c <path>` |
| Published pack | `failproofai policies add <owner>/<repo>` |
| Cloud | Assign it in the dashboard or with `fp fleet deploy` |

`block-failproofai-commands` always runs and cannot be switched off. It stops an agent disabling its own enforcement.

## Observe before enforcing

Observe mode runs the real policy and records what it would have done, but does not block the agent.

```bash
fp policies test ./checkout.policy.mjs --tool Bash --command "git push --force" --expect deny
fp fleet deploy ci-runner-01 --add checkout-guard:observe
fp guardrails summary --since 24h --machine ci-runner-01
fp fleet deploy ci-runner-01 --add checkout-guard:enforce
```

<Warning>
  A bare `fp fleet deploy <machine> --add <id>` enforces immediately. Add `:observe` for a shadow rollout.
</Warning>

A policy that times out in observe mode records an allow, because that is what would happen while enforcing. Only non-allow observed decisions are recorded.

For a pack used without Cloud, publish it with `failproofai publish --effect observe`.
