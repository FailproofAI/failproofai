Verifique o [catálogo de políticas integradas](/pt-br/policies/builtin-catalog) antes de criar uma política. Uma regra revisada geralmente é mais segura do que uma nova.

## Comece com uma política funcional

```bash
failproofai publish --init guards.mjs
failproofai policies -i -c ./guards.mjs
```

O modelo inicial bloqueia `git push --force`. Edite-o, peça ao seu agente para tentar a ação bloqueada e inspecione **Policies → Activity**.

```js
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production",
  description: "Production changes need a human",
  match: { events: ["PreToolUse"], toolNames: ["Bash"] },
  fn: async (ctx) =>
    String(ctx.toolInput?.command ?? "").includes("production")
      ? deny("Ask a human before changing production.")
      : allow(),
});
```

Uma política retorna `allow()`, `deny(message)` ou `instruct(message)`. Use `deny` quando a ação deve ser interrompida; nem todo ambiente consegue entregar uma instrução de volta ao agente.

## Carregamento automático

Coloque arquivos com os nomes `*policies.js`, `*policies.mjs` ou `*policies.ts` em:

- `.failproofai/policies/` para um projeto específico.
- `~/.failproofai/policies/` para o seu usuário.

## Teste os caminhos de falha

Teste tanto a ação insegura quanto tarefas legítimas que se pareçam com ela. Confirme se a decisão veio da sua política e não de outra regra.

Remova os arquivos de teste explícitos com:

```bash
failproofai policies -u -c
```

Quando a política estiver pronta, [publique um pacote](/pt-br/policies/publish-a-pack) ou [implante-a pela Cloud](/pt-br/policies/deploy).
