Python 3.11 ou superior. Sem dependências em tempo de execução. Usando um framework? [LangChain, CrewAI, LlamaIndex e Pydantic AI](/pt-br/start/integrations) se instrumentam automaticamente com uma única chamada.

<Note>
  Há também um **TypeScript SDK**, e os dois gravam os mesmos eventos no mesmo spool. Uma frota com agentes Node e agentes Python produz um único conjunto de sessões, não dois. Escolha por serviço, não por empresa.
</Note>

## Instalação

```bash
pip install failproofai-sdk
```

O pacote é instalado como `failproofai-sdk` e importado em Python como `failproofai_sdk`. Extras de framework como `failproofai-sdk[langgraph]` instalam o próprio framework; os adaptadores sempre vêm incluídos no pacote base.

## Configuração

### Spans OpenTelemetry (opt in)

Instale `opentelemetry-sdk` separadamente e depois anexe o exportador opcional:

```python
import failproofai_sdk
from opentelemetry.sdk.trace import TracerProvider

provider = TracerProvider()
failproofai_sdk.instrument("otel", provider=provider)
with provider.get_tracer("my-agent").start_as_current_span(
    "agent", attributes={"gen_ai.operation.name": "invoke_agent"}
):
    pass
provider.force_flush()
```

A configuração usa seu provider registrado se você omitir `provider`, criando um apenas quando nenhum estiver registrado. Você também pode passar `failproofai_sdk.OtelSpanExporter()` diretamente para seu próprio span processor. Os demais exportadores permanecem inalterados.

O daemon FailproofAI conectado realiza as exportações; o SDK não precisa de configuração de rede, chave ou listener local. Um administrador deve habilitar o [ingest OpenTelemetry](/pt-br/agenteye/opentelemetry). Um `instrument()` simples nunca habilita OTEL. `uninstrument("otel")` desabilita apenas seu próprio processor. Sua instrumentação controla a captura de conteúdo. Faça flush do provider antes de encerrar. O SDK ainda declara zero dependências em tempo de execução e importa OpenTelemetry apenas quando solicitado.

```python
import failproofai_sdk

failproofai_sdk.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| Argumento | O que faz |
| --- | --- |
| `environment` | O rótulo em cada evento — `production`, `staging`, `prod-eu`. Padrão: `dev`. |
| `flush_interval` | Com que frequência a thread em background grava no disco, em segundos. Padrão: `0.5`. |
| `base_dir` | Onde gravar. Padrão: o spool do daemon, que é o que você quer a menos que saiba o contrário. |

Configure por variável de ambiente:

| Variável | O que faz |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | Define `environment` sem alterar o código, para quando o rótulo pertence ao deploy e não ao app. Um argumento `configure()` tem precedência sobre ela. |
| `FAILPROOFAI_HOME` | Move a raiz do Failproof AI que contém o spool. |
| `FAILPROOFAI_SDK_STRICT` | `1` faz erros de instrumentação lançar exceções em vez de serem registrados. |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | `1` faz um problema de compatibilidade com framework lançar exceção em vez de apenas avisar e continuar. |

<Warning>
  **Sem vírgulas em `environment`.** O ingest divide esse campo por vírgulas para construir seus filtros e ignora qualquer evento cujo rótulo contenha uma — fazendo uma execução inteira desaparecer silenciosamente. Escreva `prod-eu`, não `prod,eu`.

  `configure(environment="prod,eu")` lança exceção para que você descubra imediatamente. `AGENTEYE_ENVIRONMENT` não pode lançar — nada está te chamando — então avisa uma vez e volta ao padrão `dev`.
</Warning>

Os eventos são enfileirados na memória e gravados em background a cada `flush_interval` segundos, com um flush final na saída do interpretador. Um processo encerrado abruptamente perde o que ainda não havia sido gravado.

## Identidade

Todo evento pertence a uma sessão e a um agente. **Os escopos preenchem ambos automaticamente**, então raramente você precisa passá-los:

```python
with failproofai_sdk.session():
    with failproofai_sdk.agent("planner"):
        failproofai_sdk.event.tool_use(tool_name="search", tool_call_id="c1")
```

Passar `session_id` ou `agent_id` explicitamente ainda funciona e tem precedência. Se nenhum estiver vinculado nem passado, a chamada lança `TypeError` em vez de emitir um evento que a Cloud descartaria silenciosamente.

<Note>
  A identidade fica em variáveis de contexto. Ela segue tarefas `asyncio` automaticamente, mas **não** novas threads — envolva um worker com `failproofai_sdk.propagate()` ou seus eventos ficarão sem vinculação.
</Note>

## Catálogo de eventos

Quinze métodos. A maioria vem em **pares** — você chama o que abre, depois o que fecha, e o SDK mede o intervalo.

| | Abre | Fecha |
| --- | --- | --- |
| **Agentes** | `agent_start` | `agent_end` |
| | `agent_pause` | `agent_resume` |
| **Modelos** | `model_request` | `model_response` |
| **Ferramentas** | `tool_use` | `tool_result` |
| **Hooks** | `hook_triggered` | `hook_completed` |
| **Humanos** | `human_wait` | `human_input` |

Três são independentes: `error`, `human_pause`, `human_interrupt`.

<Accordion title="Todos os campos, por método" icon="table">

Cada método também aceita `session_id` e `agent_id`, que os escopos preenchem automaticamente. Qualquer campo deixado como `None` é descartado em vez de ser enviado como `null` JSON, e todo método retorna `None`.

| Método | Obrigatório | Opcional |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools`, `request_id` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role`, `request_id`, `duration_ms` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

</Accordion>

<Warning>
  Para marcar uma execução como falha, `outcome` deve ser um dos valores: `failed`, `error`, `timeout` ou `rejected`. Qualquer outro valor — incluindo o quase-certo `"failure"` — é contado como sucesso.
</Warning>

## Pareamento e duração

**Uma regra: passe ao evento de fechamento o mesmo id do seu abridor.** É isso que os vincula e permite ao SDK medir o intervalo.

| Par | Correspondência por |
| --- | --- |
| `tool_use` → `tool_result` | `tool_call_id` |
| `hook_triggered` → `hook_completed` | `hook_id` |
| `agent_pause` → `agent_resume` | `pause_id` |
| `human_wait` → `human_input` | `input_id` |
| `model_request` → `model_response` | `request_id` |

**Não passe `duration_ms` você mesmo.** O SDK mede, e passá-lo lança `ValueError`.

A única exceção é `model_response`, onde só você conhece a latência real do provedor. Passe um número inteiro de milissegundos — um float lança exceção, pois a coluna é um inteiro de 32 bits e ficaria vazia caso contrário.

<Accordion title="Casos especiais" icon="circle-help">

- **Os ids precisam ser únicos apenas por tipo e por sessão.** Uma chamada de ferramenta e um hook podem compartilhar o mesmo id; duas sessões rodando ao mesmo tempo podem reutilizar os mesmos ids sem colisão.
- **Eles não têm escopo de agente.** Um par aberto em um agente e fechado em outro ainda é vinculado — o que é o caso normal em código multi-agente.
- **`request_id` é opcional, mas recomendado.** Sem ele, os eventos de modelo são pareados na ordem de chegada, então duas chamadas concorrentes no mesmo agente podem ser pareadas incorretamente.
- **Um par dividido entre processos** ainda é vinculado na Cloud, mas o SDK não consegue medi-lo — nenhum dos processos viu as duas metades.
- **No máximo 10.000 abridores aguardam um fechador por vez.** Além disso, o mais antigo é descartado, evitando que um vazamento cresça indefinidamente.

</Accordion>

## Campos personalizados

Qualquer palavra-chave extra que você passe é armazenada com o evento:

```python
failproofai_sdk.event.tool_use(
    tool_name="search", tool_call_id="c1",
    fw_tenant="acme", fw_region="eu-west-1",     # seus próprios
)
```

Prefira tipos JSON se quiser consultá-los depois. Qualquer outro tipo — um UUID, um datetime, um `Decimal`, um set, bytes, um objeto de modelo — é armazenado como string.

<Warning>
  **Use prefixo nos nomes dos seus campos.** Os extras são aplicados por último, então um campo chamado `model`, `tool_name` ou `outcome` sobrescreve silenciosamente o campo real. Os adaptadores de framework usam `fw_`; faça o mesmo e nada irá colidir.

  É também por isso que um campo opcional com erro de digitação nunca gera erro — ele apenas se torna um novo campo personalizado. Se um campo padrão estiver ausente na Cloud, verifique a ortografia primeiro.
</Warning>

Estes cinco nomes são reservados e rejeitados diretamente: `timestamp`, `session_id`, `agent_id`, `type`, `environment`.

## Entrega e verificação

<Tabs>
  <Tab title="Dashboard">
    Em **Observe → Events**, verifique se `agent_start` existe primeiro e `agent_end` existe por último. Em seguida, abra **Observe → Sessions** e confirme que os eventos de modelo, ferramenta, humano, hook e erro aparecem na ordem pretendida. Use o ID de sessão como chave principal de troubleshooting.
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

Se a Cloud estiver vazia, inspecione `$FAILPROOFAI_HOME/custom-agents/events`, caso contrário `~/.failproofai/custom-agents/events`. Arquivos JSONL confirmam a emissão pelo SDK; um spool crescendo aponta para configuração do daemon ou entrega, enquanto um spool vazio aponta para instrumentação ou tempo de vida do processo.

<Note>
  Inspecione o spool somente quando o daemon estiver parado. Enquanto ele estiver rodando, coleta e exclui cada lote em milissegundos, então uma listagem de diretório compete com o coletor e mostra muito menos eventos do que foram emitidos.
</Note>

## Prevenir falhas em um runtime personalizado

Use os achados de auditoria e os traces vinculados para definir a ação insegura, a evidência necessária e a resposta esperada. Uma integração de enforcement personalizada deve expor a ação antes da execução, passar sua entrada estruturada ao motor de políticas e aplicar a decisão resultante de allow, instruct ou deny.
