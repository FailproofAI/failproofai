Instale o CLI local com `npm install -g failproofai`. Execute sem argumentos para abrir o painel de políticas local.

O pacote requer Node.js 20.9 ou mais recente. Bun 1.3 ou mais recente é suportado para desenvolvimento e instalações a partir do código-fonte. `failproofai configure` e `failproofai setup` são apelidos para `failproofai config`. `failproofai policy`, `failproofai pack` e `failproofai p` são todas formas de escrever `failproofai policies` — packs e políticas individuais eram três comandos para uma mesma ideia e agora são um só. As formas antigas ainda funcionam, com duas exceções: `pack list <source>` agora é `policies show <source>`, e `pack build` agora é `publish`.

## Configurar uma máquina

Instale o CLI e leia a chave da máquina no shell. `read -s` a solicita em um prompt que não exibe o que é digitado, então ela nunca aparece em um comando:

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

Em seguida, configure a máquina e escolha o que ela vai aplicar:

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` é toda a configuração: instala o serviço `failproofaid` (root uma vez — em um terminal solicita sua senha sudo, e pede novamente se ela expirar antes de a configuração terminar; sem terminal usa `sudo -n` e nunca exibe prompts), conecta hooks em todos os CLIs de agente encontrados e se conecta ao Cloud. Sem terminal — CI, container, agente executando o comando — aplica em vez de perguntar, e encerra com código 1 se algo que foi solicitado não aconteceu.

Em um terminal, a etapa **Conectar ao cloud** em uma máquina ainda não conectada inicia o **login no FailproofAI Cloud** imediatamente; pressione Tab para as outras opções, **Colar uma chave de API** ou **Usar open source**. O login abre um link — ou o exibe via SSH ou sem display, para abrir em qualquer dispositivo — onde você se cadastra ou faz login, escolhe ou cria uma organização e autoriza a máquina; o terminal detecta a aprovação automaticamente e mostra quem aprovou e para qual organização. A chave é gerada somente quando a configuração é concluída, após o daemon ser instalado. Em uma máquina já conectada com uma chave funcionando, a etapa é um menu com **Manter conexão atual** em primeiro lugar, portanto re-executar a configuração nunca abre um navegador por conta própria; uma chave salva que não funciona mais inicia o login novamente imediatamente, informando o motivo. Fazer login novamente gera uma nova chave e deixa a antiga funcionando até você revogá-la. Um Cloud anterior ao login pelo navegador informa isso e oferece as outras opções.

Ele não escolhe **nenhuma** política. Essa é a função do segundo comando e, sem ele, uma máquina recém-configurada não aplica nada além da proteção sempre ativa.

Prefira a variável de ambiente em vez de `--token`: um argumento de linha de comando é legível por `ps` por qualquer usuário do sistema. Isso é tudo que a variável protege — uma chave digitada em qualquer comando, inclusive `export`, ainda fica no histórico do shell, por isso ela é lida com `read -s` como mostrado acima. Em CI, defina-a a partir do armazenamento de segredos e mantenha o rastreamento do shell (`set -x`) desativado, ou o trace a exibirá.

<Warning>
  `--connect <url>` registra uma máquina que **já está configurada**. Retorna assim que o registro é concluído — não instala o daemon e não conecta nenhum hook. Use `failproofai config` simples (ou `failproofai config --token <key>`) em uma máquina que ainda não foi configurada, caso contrário ela aparecerá como conectada enquanto não coleta nem aplica nada.
</Warning>

Execute `failproofai` sem argumentos para abrir o painel de políticas local.

| Comando | Resultado |
| --- | --- |
| `failproofai config` | Configura a máquina: agentes, daemon e Cloud — faça login pelo navegador, cole uma chave ou use open source. Cada agente na máquina também recebe uma pequena skill `failproofai` que o aponta para as [FailproofAI skills](https://github.com/FailproofAI/skills) online |
| `failproofai config --token <key>` | Configura e conecta em uma única etapa, sem fazer perguntas. Uma chave com `jev:evaluate` também ativa o [Jev pelo FailproofAI Cloud](/pt-br/reference/jev-cloud) em modo de observação, a menos que um `jev.json` já exista ou `--no-transcripts` seja informado |
| `failproofai config --connect <url>` | Registra uma máquina que **já está** configurada — sem daemon, sem hooks |
| `failproofai config --status` | Exibe o estado de conexão, daemon, entrega e pausa |
| `failproofai policies` | Lista políticas integradas, personalizadas, de convenção, de pack e gerenciadas pelo Cloud |
| `failproofai policies --install` | Conecta hooks nos CLIs de agente. Não ativa nenhuma política por si só |
| `failproofai policies add <name>` | Ativa uma política — uma integrada, ou `<pack-id>:<name>` de um pack instalado |
| `failproofai policies remove <name>` | Desativa uma política, mesma nomenclatura |
| `failproofai policies --uninstall` | Desativa políticas ou remove hooks do harness |
| `failproofai policies show <owner>/<repo>` | O que um pack contém, lido do seu manifesto, antes de você instalá-lo |
| `failproofai policies show <owner>/<repo> --releases` | Todas as versões publicadas e qual está instalada |
| `failproofai policies add <source>` | Instala um pack de políticas a partir de um release do GitHub; sem tag instala a mais recente e fixa a versão |
| `failproofai publish` | Publica suas próprias políticas como um pack; `--init` cria um ponto de partida, e `--min-cli-version <version>` define o CLI mais antigo que pode instalá-lo ([Jev verifica em um pack](/pt-br/policies/publish-a-pack#jev-checks-in-a-pack)) |
| `failproofai policies remove <publisher/name>` | Desinstala um pack |
| `failproofai audit` | Escaneia o histórico local do agente e abre a visualização de auditoria local |
| `failproofai audit --schedule [days] --email <address>` | Agenda varreduras locais recorrentes e envia os resultados por e-mail |
| `failproofai audit --status` | Exibe o endereço de relatório, intervalo e próxima varredura agendada |
| `failproofai audit --no-schedule` | Para varreduras recorrentes sem excluir o histórico de auditoria |
| `failproofai harness list` | Lista caminhos de captura adicionais |
| `failproofai otel status` | Inspeciona o [relatório OpenTelemetry](/pt-br/reference/otel) opcional |
| `failproofai jev --url <url> --key-stdin` | Configura o Jev em uma etapa; o provedor é obtido do host da URL |
| `failproofai jev setup --provider <kind> --key-stdin` | Permite que o [Jev](/pt-br/reference/jev-providers) avalie chamadas de ferramentas pelo seu próprio endpoint e chave |
| `failproofai jev setup --provider failproofai` | Permite que o Jev avalie chamadas de ferramentas [pelo FailproofAI Cloud](/pt-br/reference/jev-cloud), com a chave Cloud desta máquina |
| `failproofai jev setup --mode <m>` | Altera o modo do Jev: `enforce`, `observe` ou `off` (mantém a configuração, para de consultar o Jev) |
| `failproofai jev status` | Exibe a configuração do Jev, suas permissões e fallbacks recentes; nunca a chave |
| `failproofai jev test` | Envia uma requisição Jev ao vivo e exibe sua latência e versão; encerra com código 1 quando a resposta está atrasada para hooks ou incorreta |
| `failproofai jev models` | Lista os IDs de modelos que `GET <base>/models` informa que um endpoint serve |
| `failproofai jev remove` | Desativa o Jev; os hooks executam as políticas de regex exatamente como antes |
| `failproofai flush --wait` | Entrega o spool de eventos atual |
| `failproofai backfill --since 30d` | Relê histórico previamente processado |
| `failproofai config --pause [duration]` | Pausa uma sessão local por 30 minutos por padrão, até 8 horas |
| `failproofai config --resume` | Retoma uma sessão local pausada; adicione `--all` para limpar todas as pausas |
| `failproofai update` | Conclui migrações de pacotes e atualiza o daemon |
| `failproofai migrate --dry-run` | Visualiza ou executa migrações de layout do diretório home pendentes |
| `failproofai uninstall` | Remove hooks, a skill `failproofai` e o daemon antes de remover o pacote |
| `failproofai --version` | Exibe a versão do pacote instalado |
| `failproofai --help` | Exibe comandos e uso global |

## Flags de configuração

| Flag | Uso |
| --- | --- |
| `--token <key>` | Configura e conecta de forma não interativa; também lida de `FAILPROOFAI_CLOUD_TOKEN` |
| `--url <url>` | Conecta a outro endereço que não `app.befailproof.ai`; também lida de `FAILPROOFAI_CLOUD_URL` |
| `--connect <url>` | Somente registra, em uma máquina já configurada. Ignora o daemon e todos os hooks |
| `--machine-id <id>` | Define o ID estável da máquina |
| `--machine-label <name>` | Renomeia uma máquina que **já está conectada**. Por si só nunca executa a configuração, portanto use após `failproofai config`, não durante |
| `--no-transcripts` | Envia decisões sem conteúdo de transcrição e não ativa o Cloud Jev, que enviaria cada chamada de ferramenta verificada e o prompt recente; um `jev.json` executando o Jev pelo FailproofAI Cloud é removido |
| `--disconnect` | Para pulls de políticas do Cloud e entrega de eventos. Também remove a chave do Cloud Jev e um `jev.json` que menciona o FailproofAI Cloud; sua própria configuração de Jev é mantida |
| `--status` | Exibe o estado atual da máquina |
| `--pause [duration]` | Pausa a sessão mais recente no diretório atual; aceita segundos, minutos ou horas e tem padrão de 30 minutos |
| `--resume` | Encerra antecipadamente uma pausa correspondente |
| `--session <id>` | Direciona uma sessão explícita para pause ou resume |
| `--all` | Com `--resume`, encerra todas as pausas ativas |

Pausas locais suspendem políticas integradas, personalizadas, de convenção e de pack para uma sessão. Elas sempre expiram e não desativam políticas gerenciadas pelo Cloud. `block-failproofai-commands` — que está sempre ativo e não pode ser desativado ou pausado — impede que um agente instrumentado use esse mecanismo de escape por conta própria.

## Flags de políticas

| Flag | Uso |
| --- | --- |
| `--install`, `-i` | Instala hooks de harness. Nomes após ele ativam essas políticas; sem nenhum, nenhuma política é alterada |
| `--uninstall`, `-u` | Desativa políticas ou remove hooks |
| `--cli <names...>` | Direciona um ou mais harnesses suportados |
| `--scope user\|project\|local\|all` | Escolhe o escopo de configuração; `all` é para desinstalação |
| `--beta` | Inclui políticas beta |
| `--custom`, `-c <path>` | Valida e carrega um arquivo de política personalizado; repetível |

## Flags de entrega e manutenção

| Comando | Flags |
| --- | --- |
| `backfill` | `--since <30d\|6m\|YYYY-MM-DD>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` |

`failproofai update` deve ser executado após `npm install -g failproofai@latest`; ele realiza migrações de layout do diretório home, instala o binário do daemon correspondente e reinicia o serviço. Em seguida, move cada perfil do Hermes que já usa o FailproofAI para o plugin nativo vinculado e exibe uma linha por perfil. `--no-daemon` ignora a etapa do daemon. `update` encerra com código não zero quando o daemon não pôde ser substituído, uma migração falhou ou um perfil do Hermes não pôde ser migrado (por exemplo, porque o daemon em execução não consegue servir o plugin nativo, e nesse caso seus hooks de shell são mantidos).

## Caminhos de harness

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

Os nomes de harness suportados são `claude`, `codex`, `copilot`, `cursor`, `opencode`, `pi`, `hermes`, `openclaw`, `factory`, `devin`, `antigravity` e `goose`.

Labels criam namespaces para IDs de agentes derivados quando duas raízes contêm cópias do mesmo projeto. Raízes sobrepostas e labels duplicados são rejeitados para evitar coleta duplicada ou corrupção de cursor. A configuração de caminhos extras é recarregada sem reiniciar o daemon.

Ambientes de container podem substituir caminhos extras configurados por arquivo com uma variável separada por vírgulas chamada `FAILPROOFAI_<HARNESS>_EXTRA_PATHS`, por exemplo:

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## Variáveis de ambiente

Use arquivos de configuração para comportamento persistente da máquina. Variáveis de ambiente são mais úteis para containers, testes e um único processo.

| Variável | Uso |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | A chave do Cloud, em vez de `--token`. Prefira esta opção: um argumento é legível por `ps` por qualquer usuário. Defina-a com `read -s` ou a partir de um armazenamento de segredos de CI, nunca digitando a chave em um comando, que fica no histórico do shell de qualquer forma |
| `FAILPROOFAI_CLOUD_URL` | A URL do Cloud, em vez de `--url`. A mesma variável que o daemon lê |
| `FAILPROOFAI_HOME` | Realoca o layout completo de `~/.failproofai` |
| `FAILPROOFAI_LOG_LEVEL` | Define a verbosidade do log local |
| `FAILPROOFAI_HOOK_LOG_FILE` | Grava diagnósticos de hook em um arquivo selecionado |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | Desativa a telemetria anônima para este processo |
| `FAILPROOFAI_NO_FIRST_RUN=1` | Ignora a configuração interativa de primeira execução |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | Ignora a auditoria local pós-configuração |
| `FAILPROOFAI_LLM_BASE_URL` | Substitui o endpoint compatível com OpenAI usado pelas políticas de LLM |
| `FAILPROOFAI_LLM_API_KEY` | Fornece a chave de API usada pelas políticas de LLM |
| `FAILPROOFAI_LLM_MODEL` | Seleciona o modelo usado pelas políticas de LLM |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | Limita o tempo de carregamento de módulos de políticas personalizadas |
| `FAILPROOFAI_NO_DOWNLOAD=1` | Recusa buscar packs e binários do daemon; o que está instalado continua sendo aplicado |
| `FAILPROOFAI_PACK_BASE_URL` | Busca packs de um mirror em vez de `github.com` |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | Substitui os caminhos de captura extras configurados para um harness |
| `NO_COLOR` | Desativa a saída colorida no terminal |

Variáveis de home específicas de agentes, como `CLAUDE_PROJECTS_PATH`, `CURSOR_HOME`, `HERMES_HOME` e `OPENCLAW_HOME`, substituem onde o Failproof AI descobre sessões locais para aquele harness.

## Pausar ou remover uma máquina com segurança

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

Uma pausa de sessão local não desativa políticas gerenciadas pelo Cloud. Restaure deployments do Cloud pelo fluxo de trabalho de aplicação do Cloud quando o próprio rollout for o problema.

Antes de remover o pacote npm, remova os hooks instalados e o daemon:

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

Execute `failproofai <command> --help` para detalhes específicos da versão.

<Warning>
  Execute `failproofai uninstall` antes de `npm rm -g failproofai`; o npm não remove os hooks de agente instalados, a skill `failproofai` nem o serviço daemon.
</Warning>
