Um harness é o ambiente no qual seu agente efetivamente executa. O Failproof AI suporta doze deles, em duas categorias:

- **CLIs de codificação** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Gateways de chat e assistente** (2) — Hermes (Slack, Telegram, cron), OpenClaw (assistente self-hosted)

As mesmas políticas e o mesmo histórico de sessões se aplicam independentemente do harness em que um agente é executado. Uma camada de adaptador mapeia os nomes de eventos nativos, nomes de ferramentas e campos de entrada de ferramentas de cada harness para 29 eventos canônicos antes que qualquer política seja executada.

Um agente que não roda em **nenhum** dos doze é instrumentado diretamente com o [SDK Python](/pt-br/reference/custom-agents). Esse é um contrato diferente, e vale deixar claro: o SDK fornece rastreamento, sessões, avaliações e auditorias — **ele não aplica políticas por conta própria.** Bloquear uma ação insegura antes de ela ser executada requer um hook de enforcement no limite de ferramentas do seu runtime; [entre em contato conosco](mailto:support@befailproof.ai) e nós faremos o mapeamento.

| Harness | Escopos de hook suportados |
| --- | --- |
| Claude Code | Usuário, projeto, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | Usuário, projeto |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | Usuário, projeto |
| Hermes, OpenClaw | Usuário |

Cada integração normaliza seus nomes de eventos de hook nativos, nomes de ferramentas e campos de entrada de ferramentas antes de as políticas serem executadas. Uma política só pode agir sobre eventos que o harness expõe; teste o comportamento de fim de turno e de instrução no harness e versão exatos que você implanta.

## Capacidade de enforcement

"Bloquear" significa que o veredicto retornado pelo adaptador atual é consumido pelo harness especificado. O bloqueio pós-ferramenta pode substituir o resultado mostrado ao modelo, mas não pode desfazer um efeito colateral de ferramenta que já ocorreu.

| Harness | Eventos de bloqueio verificados | Ressalvas de observação apenas ou não bloqueantes |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact` e vários eventos de tarefa/configuração | `PostToolUse`, ciclo de vida de sessão, notificações e eventos pós-falha são observacionais. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | O bloqueio pós-ferramenta substitui o resultado após a execução; eventos de início de sessão e compactação são observacionais no adaptador atual. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | O bloqueio pós-ferramenta substitui o resultado após a execução; eventos de sessão e notificação são observacionais. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` e eventos de sessão são observacionais. |
| OpenCode | `PreToolUse` | Eventos pós-ferramenta e de ciclo de vida são observacionais; o tratamento de stop atual é uma orientação para um turno posterior, não uma barreira verificada. |
| Pi | `PreToolUse`, `UserPromptSubmit` | Eventos pós-ferramenta e de ciclo de vida são observacionais; a orientação de stop se aplica a um turno posterior. |
| Hermes | `PreToolUse` | `deny()` bloqueia. `instruct()` não interrompe a chamada: ela é executada, e a orientação é colocada no início do seu resultado. Veredictos de pós-ferramenta, sessão e subagent-stop não são barreiras. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Eventos pós-ferramenta, de sessão, subagent-stop e compactação são observacionais. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Veredictos pós-ferramenta e subagent-stop são observacionais. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PermissionRequest` condicional | Hooks de permissão não são executados em todos os modos de permissão; eventos pós-ferramenta e de sessão são observacionais. |
| Antigravity CLI | `PreToolUse`, `Stop` | Veredictos de prompt de usuário e pós-ferramenta são observacionais; instruções de prompt ainda podem ser injetadas. |
| Goose | `PreToolUse` | Eventos de prompt de usuário, pós-ferramenta e de sessão são observacionais. Um hook de stop de bloqueio nativo existe upstream, mas não é instalado pelo adaptador atual. |

As capacidades são sensíveis à versão. Realize novos testes após atualizar uma CLI de agente, especialmente quando uma política depende de comportamento de prompt, stop, permissão ou pós-ferramenta em vez da barreira pré-ferramenta comum.

### Plugin nativo do Hermes

O Hermes é integrado por meio de um plugin nativo local de perfil, em vez de um comando shell. A instalação vincula o `plugins/failproofai` de cada perfil Hermes padrão e nomeado ao plugin incluído no pacote npm (uma cópia onde um symlink não pode ser criado), habilita-o no `config.yaml` desse perfil e migra apenas entradas legadas de shell-hook do FailproofAI. Como o plugin é vinculado, `npm install -g failproofai@latest` o atualiza sem reinstalação. Isso evita a criação de um processo a cada hook. O plugin suporta Hermes 0.20.0 e versões posteriores.

Shell hooks legados (instalados pela versão 1.0.5 e anteriores) **não** verificam cron jobs do Hermes: cada execução de cron constrói seu próprio escopo de hook, que o plugin nativo integra, mas os shell hooks do `config.yaml` não integram. `failproofai update` migra todos os perfis que já usam o FailproofAI para o plugin vinculado. Se o daemon em execução não conseguir servir o plugin, `update` mantém os shell hooks no lugar e encerra com código não-zero; execute `failproofai config` para atualizar o daemon e, em seguida, `failproofai update` novamente. Cron jobs carregam o plugin em sua próxima execução; reinicie os gateways em execução e as sessões interativas para carregá-lo neles.

No Hermes, `deny()` bloqueia a chamada e `instruct()` não: a chamada é executada, e a orientação é colocada no início do seu resultado — como a primeira chave, `failproof_policy_reminder`, de um resultado JSON, ou como uma linha inicial `[FailproofAI policy reminder (...)]` — para que o modelo a leia junto com a saída, e scripts que analisam o resultado continuem funcionando. O lembrete de uma política é exibido uma vez por turno e mantido curto em um resultado grande. Use `deny()` quando uma ação não deve acontecer de forma alguma: `instruct()` não interrompe mais a ação antes. Chamadas de ferramentas feitas a partir de um script `execute_code` colocam seu lembrete no resultado do `execute_code` que o modelo lê; a própria cópia do resultado do script é mantida intacta. O modelo é instruído a nunca citar um lembrete em suas respostas.

Uma build do Hermes sem middleware de plugin cai de volta para segurar a chamada correspondente uma vez com "FailproofAI policy guidance"; a próxima resposta do modelo pode repeti-la, ou realizar o mesmo trabalho com outra ferramenta, sem ser retida novamente.

Os nomes das ferramentas são compatibilizados entre versões do Hermes: `process_manage`, `cronjob_manage` e `todo_list` (Hermes 0.21) são tratados como `process`, `cronjob` e `todo` (Hermes 0.20). Cada vez que o Hermes carrega o plugin, ele escreve `heartbeat.json` no diretório `plugin-data/agent-plugin-failproofai-5296f299/` do perfil, registrando a versão do Hermes, o caminho e a versão do plugin, e os hooks que o Hermes aceitou. Execute `failproofai config --status` para detectar um perfil desabilitado, incompleto, duplicado ou recém-não configurado, ou ainda um que ainda usa shell hooks legados (reportado como "Hermes cron jobs are not checked").

### Plugin do OpenClaw

O OpenClaw carrega o FailproofAI como um plugin de gateway em processo, registrado no `openclaw.json` de cada perfil. Assim como o plugin do Hermes, ele consulta o daemon `failproofaid` local para cada veredicto por meio de seu socket, portanto precisa de um daemon em execução: a instalação recusa sem um, e se o daemon não conseguir responder, chamadas de ferramentas e prompts são bloqueados e o motivo é gravado no log do gateway. Após `npm install -g failproofai@latest`, reinicie o gateway do OpenClaw para que ele carregue o plugin atualizado.

### Confiança de hook do Codex

O Codex 0.129 e versões posteriores executam um hook de `~/.codex/hooks.json` apenas após você aprová-lo no `codex` interativo ("Review hooks"); até então, toda sessão Codex — incluindo o `codex exec` headless — o ignora. Hooks na configuração de sistema do Codex, `/etc/codex/config.toml` no Linux e macOS, são executados sem essa aprovação.

Portanto, quando `failproofai config` (ou `policies --install --cli codex` no escopo de usuário) pode usar sudo, ele escreve os hooks do Codex em `/etc/codex/config.toml`, entre `# >>> failproofai managed hooks >>>` e `# <<< failproofai managed hooks <<<`, deixando o restante do arquivo como estava.

Esse arquivo se aplica a todas as contas da máquina, portanto cada hook nele executa `/opt/failproofai-codex/codex-hook`, um script curto de propriedade do root. O script passa o evento para o failproofai próprio de cada conta que configurou os hooks lá, e não faz nada para nenhuma outra conta. Outra conta que queira os hooks do Codex do failproofai os configura por conta própria.

Antes de escrever o bloco, e novamente a cada `failproofai update`, o failproofai verifica se `/etc/codex/config.toml` em si, o script, cada diretório acima deles, e os `sh`, `id` e `cat` que ele executa pertencem ao root e não podem ser escritos por mais ninguém, e que o failproofai de cada conta pertence a essa conta ou ao root. Na instalação, quando essa verificação falha, seus hooks permanecem em `~/.codex/hooks.json`. Na atualização, um script que falha nessa verificação tem o bloco removido, e uma conta cujo failproofai falha nela é removida do script; execute `failproofai config` novamente assim que for corrigido. `failproofai update` também reescreve um bloco escrito por uma versão anterior para usar o script, o que requer sudo.

`failproofai uninstall` e desmarcar o Codex em `failproofai config` removem sua conta novamente, e o bloco junto quando nenhuma conta restar.

Sem sudo, e no Windows, os hooks permanecem em `~/.codex/hooks.json`. `failproofai config` e `failproofai config --status` então não contam o Codex como aplicando enforcement até que os hooks sejam aprovados, e indicam como corrigir: execute `failproofai config` novamente e permita sudo, ou abra o `codex` uma vez e aprove os hooks.

## Instalar hooks de captura e política

<Tabs>
  <Tab title="Dashboard">
    1. Abra **settings → api keys** e crie uma chave com `events:add` e `policies:pull`, nomeada para a máquina ou ambiente.
    2. Na máquina de destino, conecte a CLI local com a chave exibida e instale os hooks do harness.
    3. Inicie uma nova sessão de agente e confirme seus eventos de hook e sessão em **trace → live events**.
    4. Abra **fix → activity** para o mesmo intervalo de tempo e confirme que uma decisão de política é atribuída à máquina.

    A conexão começa com uma chave de máquina. Confirme que ela inclui permissões de ingestão e entrega de políticas antes de copiar o segredo.

    ![O drawer de nova chave de API usado para conceder permissões de ingestão de eventos e entrega de políticas.](/images/dashboard/key-create.png)

    Após instalar os hooks, o stream de Eventos deve mostrar novos eventos da máquina e do ambiente que você conectou.

    ![O stream de Eventos ao vivo usado para confirmar que um harness recém-instalado está reportando.](/images/dashboard/events-stream.png)

    Por fim, verifique se as decisões de política são atribuídas à mesma máquina. Isso confirma que o harness está reportando atividade de política, além de eventos de rastreamento.

    ![A página de Políticas usada para verificar decisões de política de um harness recém-conectado.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Leia a chave da máquina no shell. `read -s` a recebe em um prompt que não ecoa, para que nunca apareça em um comando ou no histórico do shell:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    Em seguida, configure a máquina — isso conecta hooks para cada harness detectado, instala o daemon e conecta ao Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    A configuração não habilita nenhuma política por conta própria, que é para o que serve o segundo comando.

    Ou direcione harnesses nomeados e um escopo de configuração:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    O escopo de projeto mantém a configuração de hook com um repositório. O escopo de usuário cobre trabalho em vários repositórios. Claude Code também suporta escopo local; o suporte varia por harness e a CLI rejeita combinações não suportadas.

    Verifique a máquina e seus eventos:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## Adicionar um caminho de sessão não padrão

<Tabs>
  <Tab title="Dashboard">
    Caminhos extras são registrados na máquina, não no Cloud. Após adicionar um, abra **trace → sessions**, filtre pelo ambiente da máquina e confirme que sessões do novo caminho aparecem. Abra uma sessão e verifique o agente, o harness e os timestamps de eventos antes de confiar nela em uma auditoria.

    ![A lista de Sessões filtrada pelo ambiente que recebe dados do caminho de captura adicional.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Adicione um caminho com um rótulo opcional e, em seguida, inspecione os caminhos configurados:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Remova um caminho com `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  Execute uma nova sessão após a instalação. Verifique tanto o stream de eventos ao vivo quanto uma decisão de política real antes de expandir o rollout.
</Tip>
