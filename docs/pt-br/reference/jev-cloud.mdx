Esta é a referência de rota Cloud para [políticas Jev](/pt-br/policies/jev). O Jev, o classificador da TypeSafe, lê cada chamada de ferramenta em relação ao que você realmente pediu e responde junto com suas políticas, nunca no lugar delas. Através do **FailproofAI Cloud**, uma máquina conectada usa o Jev com a mesma chave que já usa para se conectar: sem conta TypeSafe, sem segunda chave, sem endpoint a configurar. Cada chamada é debitada da cota do plano existente da sua organização.

Tudo que o Jev faz permanece igual à [configuração com chave própria](/pt-br/reference/jev-providers): políticas rígidas continuam sendo definitivas, a negação de uma política revisável só é removida quando o Jev foi consultado especificamente sobre aquela preocupação, e qualquer falha recai sobre o resultado do regex para aquela chamada.

<Note>
Requer **failproofai 1.0.8-beta.0** ou posterior. A versão 1.0.7 não tem Jev, mesmo que apareça acima dos betas 1.0.7 na ordenação. Sem uma configuração de Jev, nada muda: os hooks executam as políticas de regex exatamente como sempre fizeram.
</Note>

## Antes de começar

Instale o Failproof AI na máquina onde seu agente roda e conecte seus hooks a um [harness compatível](/pt-br/reference/harnesses). Se estiver começando do zero, siga o [quickstart](/pt-br/start/quickstart) até a instalação dos hooks. Verifique o CLI instalado com `failproofai --version`; atualize se for anterior ao Jev. Você também precisa de acesso à página **Administration → Keys** da sua organização para criar uma chave de máquina.

O Jev revisa chamadas de ferramenta nomeadas no gate `PreToolUse` ou `PermissionRequest`. Ele não revisa todos os eventos de uma sessão. Para ver o Jev remover uma negação de política, você precisa de uma política instalada marcada como [revisável](/pt-br/policies/authority); todas as outras negações de política permanecem definitivas.

## Ativação

1. **Crie uma chave com Jev.** No painel do FailproofAI Cloud, abra **Administration → Keys → Create key** e selecione o preset **machine**. Ele concede as três permissões que uma máquina precisa: `events:add` (enviar atividade), `policies:pull` (receber políticas) e `jev:evaluate` (Jev, debitado do plano da sua organização). Uma chave não pode ter `jev:evaluate` sem as outras duas.
2. **Conecte a máquina** com essa chave. Leia o segredo de uso único em um prompt, depois execute o comando de configuração completo:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` instala o daemon, conecta os hooks para os CLIs de agente encontrados e conecta a máquina. A variável de ambiente mantém a chave fora dos argumentos do comando e do histórico do shell. Se o seu harness foi instalado posteriormente, [conecte-o explicitamente](/pt-br/start/quickstart).

   Se sua organização usa seu próprio FailproofAI Cloud em vez do hospedado, adicione o endereço: `--url https://<your dashboard host>` (ou exporte `FAILPROOFAI_CLOUD_URL`). Sem ele, a chave é verificada no serviço hospedado e a conexão falha. Se o certificado desse host vem de uma CA privada, instale a CA no repositório de confiança do sistema da máquina (por exemplo com `update-ca-certificates`), não apenas em `NODE_EXTRA_CA_CERTS`: o daemon que envia eventos e busca políticas lê o repositório do sistema. Veja [Troubleshooting](/pt-br/reference/troubleshooting).

É só isso. Ao conectar, a chave é armazenada e, quando a máquina ainda **não** tem configuração de Jev, uma é criada para o FailproofAI Cloud. A partir do primeiro deploy da máquina (em cerca de 30 s), o FailproofAI Cloud define o modo: `enforce` enquanto uma política Jev estiver deployada nela, `off` quando nenhuma estiver (veja [Quem define o modo](#quem-define-o-modo)). A saída informa:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

As verificações que o FailproofAI Cloud deploya executam na Cloud. Para adicionar verificações próprias na máquina, instale um pack:

```bash
failproofai policies add FailproofAI/jev-policies
```

**Com `--no-transcripts`, a conexão não ativa o Jev.** O Jev envia cada chamada de ferramenta verificada e o prompt recente ao FailproofAI Cloud, o que é mais do que uma conexão somente de decisões solicitada a enviar. A chave ainda é armazenada, e a saída informa que o Jev está disponível e como ativá-lo:

```bash
failproofai jev setup --provider failproofai
```

Esse comando também **desativa** o Jev via FailproofAI Cloud. Um `jev.json` que executa o Jev através do FailproofAI Cloud (deixado por uma conexão anterior com transcrições ativas) é removido, pela mesma regra que `config --disconnect` usa, e a saída informa que o Jev via FailproofAI Cloud permanece desativado nesta máquina. Um `jev.json` para seu próprio endpoint Jev é mantido como está, assim como um do FailproofAI Cloud que você desativou (`--mode off`).

<Warning>
A conexão **nunca sobrescreve** um `~/.failproofai/jev.json` existente. Se você já usa seu próprio endpoint Jev, ele continua sendo usado, e a saída informa que o arquivo foi mantido como configurado — e, quando esse arquivo deixa o Jev desativado (recusado ou desligado), informa isso e como corrigir. Para mudar essa máquina para o FailproofAI Cloud, execute `failproofai jev setup --provider failproofai`.
</Warning>

## Quem define o modo

Em uma máquina conectada ao FailproofAI Cloud, **o FailproofAI Cloud define o modo do Jev**; nada na máquina faz isso:

- `enforce` enquanto qualquer política Jev (ou regex + Jev) estiver deployada na máquina: cada chamada de ferramenta verificada de um agente que uma dessas políticas visa vai para o FailproofAI Cloud, que consulta suas verificações junto com as verificações dos packs instalados lá. Uma chamada de um agente que nenhuma política Cloud Jev visa, sem verificação de pack própria, não é enviada. No modo `enforce`, as próprias verificações de negação do Jev bloqueiam chamadas além de remover os veredictos de regex que revisam.
- `off` quando nenhuma está: sem Jev algum, independentemente do que `jev.json` diz.

Para testar uma política Jev antes que ela entre em ação, faça o deploy com efeito **observe**: suas verificações ainda são consultadas, e o que elas teriam feito é registrado como um **would-have** na página da política, mas nunca bloqueia uma chamada nem remove nenhuma. `failproofai jev setup --mode` e o switch **Settings → Jev** do painel informam que o modo é gerenciado pelo FailproofAI Cloud e não alteram nada. `jev.json` não é usado para as verificações do Cloud, mesmo que nomeie outro provedor. `failproofai config --disconnect` devolve o Jev ao `jev.json` próprio da máquina.

`failproofai jev status` então exibe `Jev checks run on FailproofAI Cloud (mode: enforce)`. Também lista as verificações que revisam cada política `both`. A página de frota mostra por que uma máquina com modo não pode consultar:

- `transcripts_disabled`: a máquina foi conectada com `--no-transcripts`, o que nunca ativa o Jev.
- `jev_unconfigured`: a chave da máquina não tem `jev:evaluate`.
- `jev_rate_limited`: o FailproofAI Cloud recusou algumas chamadas da máquina pelo limite de taxa Jev da organização, e essas chamadas foram decididas pelas políticas de regex sozinhas.
- `jev_unavailable`: várias chamadas consecutivas falharam, então a máquina ignora o Jev do FailproofAI Cloud por um minuto de cada vez. Ela tenta novamente por conta própria.

Se o FailproofAI Cloud não responder em 5 segundos, as políticas de regex decidem sozinhas, como em qualquer interrupção do Jev. Após 3 falhas consecutivas, a máquina para de consultar por um minuto de cada vez, para que uma interrupção do Cloud não desacelere cada chamada de ferramenta.

Uma pausa de sessão (`failproofai config --pause`) não interrompe as verificações Jev do FailproofAI Cloud, assim como não interrompe as políticas gerenciadas pelo Cloud. Ela pausa as verificações Jev dos packs instalados na máquina.

## Verificar o que está acontecendo

```bash
failproofai jev status
failproofai jev test
```

`status` exibe o provedor como **FailproofAI Cloud**, o host Cloud ao qual a máquina está conectada, o modo e a fonte da chave como **FailproofAI Cloud connection**, nunca a chave em si. Quando um `jev.json` do FailproofAI Cloud está configurado mas o Jev não pode ser executado, informa o motivo:

| O que `status` exibe | `status --json` | Significado |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | A máquina está conectada, mas nenhuma chave Jev está armazenada para ela: a chave não tem `jev:evaluate`, ou a conexão não pôde confirmá-la. Execute `failproofai config` novamente com a chave em `FAILPROOFAI_CLOUD_TOKEN`; se faltam permissões, use uma chave **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Não há conexão com o FailproofAI Cloud nesta máquina para a chave Jev pertencer. |

Após `failproofai config --disconnect`, não há mais `jev.json` do FailproofAI Cloud (a menos que tenha sido desativado, o que é mantido), então `status` simplesmente reporta o Jev como desativado. `status --json` carrega os mesmos dados (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), mesmo quando a configuração está ausente ou recusada. `permissions` é sempre do `jev.json`; uma recusa sobre `credentials.json` adiciona `credentialsPermissions` e `fix` quando um comando corrige. `test` envia uma requisição ao vivo e reporta a latência e a versão do Jev que respondeu. Ele sai com código 1, e informa no título, quando a resposta chega após o timeout do hook (os hooks registrariam `timeout`) ou responde incorretamente à pergunta de verificação.

O painel **Settings → Jev** também mostra a **FailproofAI Cloud connection**: em qual organização a máquina reporta e se sua chave tem Jev. É lido dos próprios arquivos da máquina, sem chamada de rede.

## Verificar uma chamada real

Inicie uma nova sessão no agente com hook. Peça que ele use a ferramenta de leitura de arquivo em `README.md` e reporte o título. Confirme que a sessão contém essa chamada de ferramenta, depois execute `failproofai jev status` novamente: a contagem de chamadas avaliadas recentemente deve aumentar. Abra **Policies → Activity** no [painel local](/pt-br/reference/local-dashboard#review-policy-activity) para inspecionar o veredicto Jev e o modo dessa chamada. No Cloud, a página **Policies** da organização mostra os resultados do Jev para a atividade entregue. No modo observe, o veredicto é registrado como um **would-have** e o resultado da política ainda decide a chamada. Uma remoção de bloqueio aparece somente quando uma política revisável corresponde e o Jev remove suas verificações nomeadas.

## O que chega à página de políticas

A máquina já envia sua atividade de hook ao FailproofAI Cloud (`events:add`). Com o Jev ativado, o registro de cada chamada verificada também informa qual avaliador executou, o que o Jev decidiu, quais políticas ele removeu, por que recaiu quando recaiu, sua latência e o modelo que respondeu — decisões, códigos e nomes, nunca o comando ou seu prompt. Na página **Policies** da sua organização:

- uma chamada decidida pelo próprio veredicto do Jev (modo enforce) é atribuída ao **Jev** e, quando a verificação decisiva veio de um pack, o registro também nomeia o pack e sua versão;
- no modo observe, a negação ou aviso do Jev aparece como um **would-have**, ao lado dos rollouts que você está observando;
- as políticas que o Jev removeu, ou teria removido no modo observe, são contadas por política.
- uma decisão em que o Jev participou (um bloqueio, aviso, remoção ou would-have no modo observe) lista cada verificação consultada e o que ela concluiu: veredicto, motivo (`not-detected`, `exempt`, `fired`, `op-requested`, …), sua evidência `p`, a resposta `exempt` e a resposta de cada probe. Uma verificação de uma política deployada para observação (observe) também é listada, marcada como observada; ela nunca bloqueia. O Jev responde com probabilidades, não em prosa, então não há razão em texto livre. Permissões simples são agrupadas em contagens e não carregam essa lista.

## Quando o Jev não consegue responder

Cada um destes casos recai sobre o resultado das suas políticas para aquela chamada e é registrado com seu motivo:

| Motivo | Causa |
| --- | --- |
| `out-of-credits` | Sua organização usou toda a cota do plano. |
| `http-401`, `http-403` | A chave foi revogada ou não tem `jev:evaluate`. Reconecte com uma chave que tenha. |
| `http-429` | O FailproofAI Cloud está limitando a taxa do Jev para sua organização. Até que o tempo de espera solicitado acabe (seu `Retry-After`, no máximo 60 segundos), a máquina não envia nada e cada chamada recai imediatamente. Chamadas retidas dessa forma são registradas como `http-429`, ou como `rate-limited` quando o próprio limite de taxa da máquina as retém primeiro. |
| `http-429` (limite diário) | Sua organização usou suas chamadas Jev diárias: **10.000 por dia UTC**, a menos que quem opera seu FailproofAI Cloud tenha definido outro limite. Cada chamada recai até a contagem ser zerada às 00:00 UTC; a máquina ainda consulta no máximo uma vez por minuto, então detecta o reset em até um minuto. `failproofai jev test` exibe "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | O Jev recusou a requisição desta chamada, geralmente porque a chamada de ferramenta continha texto denso (base64, hex, código minificado) acima do orçamento de tokens do Jev. Essa chamada sempre recai; não é uma interrupção. |
| `http-502` | O Jev está indisponível no momento. |
| `http-503` | Este Cloud não pode servir o Jev para sua organização: sem gateway de modelo, organização ainda não provisionada ou gateway fora do ar. Contate seu administrador; os hooks tentam novamente no máximo uma vez por minuto. |
| `http-404` | Este FailproofAI Cloud ainda não serve o Jev. |
| `timeout` | Sem resposta dentro de `timeoutMs` (padrão 3000). Enquanto o FailproofAI Cloud define o modo Jev da máquina, a espera é de 5000 ms e `timeoutMs` do `jev.json` não é usado. |
| `model-mismatch` | Uma versão do Jev diferente da 1.13 respondeu. |

## Onde a chave fica e para onde vai

- A chave é armazenada uma vez, em `~/.failproofai/credentials.json` (`0600`, em um diretório somente do proprietário), ao lado das outras credenciais do FailproofAI Cloud. `jev.json` não guarda chave para esta rota; uma chave escrita lá torna a configuração inválida.
- Se `credentials.json` tiver **qualquer** permissão para alguém além de você (grupo ou outros, leitura ou escrita), ou se seu diretório puder ser **escrito** por alguém além de você, ele é **recusado**, não lido, e o Jev fica desativado até você corrigir: `chmod 600` no arquivo, `chmod 700` no diretório (ou reconecte, o que reescreve o arquivo em `0600` e torna o diretório somente do proprietário). Um diretório que outros só podem ler está ok; um que eles podem escrever permite trocar o arquivo.
- A chave conta apenas enquanto a conexão de que veio está na máquina: uma credencial de política ou relatório para o mesmo FailproofAI Cloud **com a mesma chave**, no mesmo arquivo. Uma chave Jev deixada sem uma é ignorada, e o Jev fica desativado. Isso acontece quando o `config --disconnect` de um failproofai mais antigo deixa a chave Jev no lugar (ele não sabe removê-la), ou quando o `config --token` de um failproofai mais antigo conecta com outra chave, que no FailproofAI Cloud pode pertencer a outra organização. Para reativar o Jev, conecte novamente com uma chave **machine**.
- A chave é enviada apenas para a origem Cloud contra a qual foi verificada. Um `jev.json` apontando para outro lugar é recusado.
- **Um agente na máquina pode lê-la.** `credentials.json` é somente do proprietário, e o agente roda como esse proprietário. Ler os próprios arquivos do failproofai é permitido intencionalmente (apenas alterá-los é bloqueado por `block-failproofai-commands`), então a única coisa entre um agente e este arquivo é `block-read-outside-cwd` — uma política *revisável* — e, em uma sessão iniciada no seu diretório home, nada. Uma chave com `jev:evaluate` gasta a cota Jev da sua organização (até o limite diário) de onde quer que seja usada, então trate uma chave de máquina como qualquer outra credencial de gasto: se um agente pode tê-la lido, desative-a na página Keys e reconecte com uma nova.
- Apenas seus arquivos globais decidem isso. Um repositório não pode ativar o Cloud Jev, apontá-lo para outro lugar ou fornecer sua chave, e `FAILPROOFAI_JEV_API_KEY` é ignorado para esta rota.
- Para cada chamada que o Jev avalia, uma requisição vai ao FailproofAI Cloud, carregando o que a [página de chave própria](/pt-br/reference/jev-providers#what-leaves-the-machine) lista (segredos removidos). O FailproofAI Cloud encaminha para a TypeSafe e não registra nem guarda.

## Desativação

Em uma máquina conectada, o Jev fica desativado quando o FailproofAI Cloud não deploya nenhuma política Jev para ela: remova ou arquive as políticas Jev lá.

| Comando | Resultado |
| --- | --- |
| Remover as políticas Jev da máquina no FailproofAI Cloud | O modo do Cloud se torna `off` na próxima consulta (cerca de 30 s): sem Jev algum, independentemente do que `jev.json` diz. |
| `failproofai config --disconnect` | Desconecta a máquina: a chave é removida, assim como `jev.json` quando ele nomeia o FailproofAI Cloud e não está desativado. Um `jev.json` para seu próprio endpoint é mantido. |

A partir da próxima chamada de ferramenta, os hooks executam as políticas de regex exatamente como antes.
