Uma auditoria transforma um conjunto de sessões em descobertas de falhas classificadas e embasadas em evidências. Comece com uma pergunta específica sobre falhas.

Existem dois tipos de auditoria. Eles leem dados diferentes e respondem a ferramentas diferentes:

| Auditoria | Lê | Precisa de conta | Descobertas aparecem em |
| --- | --- | --- | --- |
| Local — `failproofai audit` | O histórico de agentes já presente nesta máquina | Não | `http://localhost:8020/audit` |
| Cloud — **Analyze → Audits**, ou o CLI `fp` | As sessões armazenadas no Failproof AI Cloud | Sim | O painel do Cloud |

Execute primeiro a auditoria local. Ela não precisa de nada além do CLI. As descobertas ficam armazenadas localmente, enquanto a telemetria anônima do CLI é enviada por padrão, a menos que você defina `FAILPROOFAI_TELEMETRY_DISABLED=1`.

<Tabs>
  <Tab title="Local">
    ```bash
    failproofai audit
    ```

    Ele varre todo histórico de agentes compatível encontrado nesta máquina, reproduz a atividade das ferramentas pelo catálogo de políticas integrado e abre **http://localhost:8020/audit**. Mantenha o processo em execução enquanto lê os resultados; pressione <kbd>Ctrl</kbd>+<kbd>C</kbd> quando terminar.

    A análise e as descobertas permanecem nesta máquina. A telemetria anônima do CLI é enviada por padrão, a menos que seja desativada. Após optar pelo agendamento, cada varredura também envia metadados da máquina e pode enviar um resumo limitado das descobertas.

    | Flag | O que faz |
    | --- | --- |
    | `--schedule [days]` | Executa a varredura em um timer e envia as descobertas por e-mail. Padrão: 7 dias, intervalo de 1 a 90. Faz login na primeira execução. |
    | `--email <address>` | Com `--schedule`, fornece o endereço do relatório em vez de solicitar. |
    | `--no-schedule` | Para o timer. Mantém você conectado. |
    | `--status` | Indica se o agendamento está ativo, para onde os relatórios vão, o estado do daemon e quando a próxima varredura está prevista. |

    ```bash
    failproofai audit --schedule 7 --email reliability@example.com
    failproofai audit --status
    ```

    Consulte [Audit local agent history](/pt-br/audits/local-audit) para saber quais históricos cada adaptador lê e como a varredura agendada é executada.
  </Tab>
  <Tab title="Cloud dashboard">
    <Steps>
      <Step title="Abrir Audits">
        Na barra lateral do Cloud, vá para **Analyze → Audits**. Selecione **new audit**.
      </Step>
      <Step title="Configurar a auditoria">
        Insira um nome e um objetivo direto de falha, como "encontrar sessões de produção que repetem a mesma chamada de pagamento falha sem alterar a entrada ou escalar." Selecione o agente, o ambiente, a janela de tempo e o agendamento. Adicione um breve resumo e URLs de referência quando o auditor precisar das suas regras de fluxo de trabalho.
      </Step>
      <Step title="Criar e aguardar a execução">
        Selecione **create audit**. A primeira execução é enfileirada imediatamente. Abra o cartão da auditoria para acompanhar o progresso de enfileirado para em execução e, por fim, concluído.
      </Step>
    </Steps>

    Após a conclusão da execução, abra uma descoberta e revise as evidências da sessão. Você pode então reconhecer, atribuir, descartar, silenciar ou resolver a descoberta.

    ![Uma descoberta de auditoria concluída mostrando sua descrição de falha, ação recomendada, evidências de suporte e sessões afetadas.](/images/dashboard/audit-finding.png)
  </Tab>
  <Tab title="Cloud CLI">
    `fp` é o CLI do Failproof AI Cloud. Ele recupera o que o Cloud armazenou; é um programa diferente do `failproofai`, que aplica políticas nesta máquina.

    ```bash
    fp audits create payment-retry-failures \
      --description "Find production sessions that retry a failed payment call without changing input or escalating" \
      --scope '{"environments":["production"]}' \
      --text "Escalate after two unchanged payment failures"

    fp audits list
    fp audits runs payment-retry-failures
    fp audits findings --audit payment-retry-failures
    fp audits finding <finding-id>
    ```

    Adicione contexto de referência e atualize quando a fonte mudar:

    ```bash
    fp audits context-set payment-retry-failures --url https://example.com/payment-runbook
    fp audits context-refresh payment-retry-failures
    fp audits run payment-retry-failures
    ```

    Use `fp audits ack <finding-id>`, `fp audits assign <finding-id> --to <email>`, `fp audits dismiss <finding-id>`, `fp audits mute <finding-id>`, `fp audits resolve <finding-id>` ou `fp audits reopen <finding-id>` para mover uma descoberta pelo processo de triagem.
  </Tab>
</Tabs>

Em seguida, [evite sua primeira falha com uma política](/pt-br/start/first-policy) para uma ação repetível confirmada.
