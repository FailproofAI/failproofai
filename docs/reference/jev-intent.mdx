When you configure your own Jev endpoint, the Jev evaluator judges each tool call against **what the human asked for**, not against whatever text the harness put in front of the agent. A reply such as "yes, force-push it" can clear a reviewable policy, so the only text that ever counts as the human's is text a human typed into the harness's prompt box.

This page lists, for each of the 12 supported harnesses, where that text comes from. Harnesses that never deliver human text through a prompt event are also listed, with the reason.

## Per-harness table

"Text field" is the stdin payload field after Failproof AI's per-harness normalization. "Recorded" says whether the prompt is kept as the human's request.

| Harness | `--cli` | Prompt event → canonical | Text field | Recorded | Agent's last message read from |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | Yes, except a prompt the transcript shows the model scheduled (`CronCreate`, `ScheduleWakeup`, `/loop`), and except when the transcript no longer shows any conversation | the session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | Yes, except in a sub-agent thread (the rollout's `session_meta.source`) and except when the rollout is not found, cannot be read, or carries no source mark | the rollout JSONL (`transcript_path`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | Yes | the session's `events.jsonl` |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | Yes | the agent transcript JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | No | — |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | Only when Pi marks it as typed or sent by an RPC client (`input_source`: `interactive` or `rpc`), never input another extension sent | the session JSONL |
| Hermes | `hermes` | none | — | No | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | Only when marked as the owner's own message — which the shipped plugin never marks, so nothing is recorded today | none (`before_agent_run` carries no transcript path) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | Yes, except a prompt one of the agent's own tool calls in the transcript carried | the session JSONL (`transcript_path`) |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | Yes | none (its transcript is one JSON document, not JSONL) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | none | No | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | Yes | none (sessions are stored in SQLite) |

When a harness records nothing, Jev still evaluates every tool call, but with no task to judge against. Nothing can be cleared on the grounds that the human asked for it, and the check that flags a call reaching beyond the human's task stays off.

## Prompts the model scheduled (Claude Code)

Claude Code fires `UserPromptSubmit` for more than typed prompts. When a task the model scheduled comes due (`CronCreate`, `ScheduleWakeup`, or a `/loop`), Claude Code submits the task's prompt through the same path, and the hook payload is identical to a typed prompt's: nothing in it says the model wrote the text. Recording it would let the agent write the words it is later cleared by, so the session transcript is checked before a Claude Code prompt is recorded. The prompt is not recorded when:

- the newest conversation entry in the transcript is a scheduled task firing (`"subtype": "scheduled_task_fire"`), which Claude Code writes just before it submits that task's prompt;
- an older scheduled-task entry names this prompt (the task fired during a running turn, and its prompt waited in the queue). The entry keeps the first 200 characters, so a longer prompt matches on those;
- a tool call in the transcript carries this prompt as its `prompt` input, as `CronCreate` and `ScheduleWakeup` do;
- **the transcript no longer shows any conversation at all** — a `user`, `assistant` or `message` entry; session-start bookkeeping is not one. Every way of making it unreadable — truncating it, replacing it with a FIFO or a device, removing the read permission, moving it aside — is one command in a shell the agent already has, so "nothing could be read" does not count as "nobody scheduled this".
- **the transcript is no longer the one this session was already reading.** A conversation is not hard to write: `printf '{"type":"user"}\n' > transcript` leaves a file that parses. So every prompt-submit event marks the transcript in the session's own file — which device and inode it is, how long it was, and a digest of the last 64 KB before that length — and the next prompt is believed only while the transcript is **the same file, grown**: same inode, those bytes still where they were, and no more appended since the last prompt than the 4 MB the check reads. A transcript that was truncated, replaced, or padded past the read budget is not that, and making it read well again does not undo it: the mark stays where it was, so that session records nothing more. Growing by more than 4 MB in one step costs only that one prompt: the mark moves on with the file.

The one exception is a session's **first prompt-submit event**: at that moment a real transcript holds only Claude Code's session-start bookkeeping or does not exist yet, and a prompt the model scheduled cannot be a session's first, since scheduling one takes a turn. It is the first *event* that spends the exception, **whether or not that prompt is recorded** — a session that opens with harness text, an image-only prompt, or the model's own scheduled task has spent it too. A harness that sends no transcript path at all (Devin) is not this case: the path comes from the hook payload, which the agent cannot edit. A session that had a readable transcript and later names none is.

Whitespace, control characters and ANSI escapes are ignored when comparing. If the human types exactly the words of a scheduled prompt, that prompt is not recorded either. Nothing breaks: Jev just has no stated intent to judge it against.

The same tool-call check, and the same rule about a transcript that no longer shows the conversation, run for Factory Droid, whose payloads and transcripts are shaped like Claude Code's.

## Harnesses that are not recorded

- **Hermes** has no prompt-submit event. Its native plugin handles `pre_llm_call` itself and forwards only tool, session and subagent events.
- **Antigravity CLI** maps `PreInvocation` to `UserPromptSubmit`, but `PreInvocation` fires before *every* model call in a turn, carries no prompt text, and hooks can inject `userMessage` steps into the same conversation. Nothing in it identifies a human turn.
- **OpenCode** reports prompts through the `message.updated` bus event. In current OpenCode the message it carries has no text parts, so the forwarded prompt is empty. The event also fires again on every update to the same message, for the child sessions the task tool creates (whose "user" message the parent agent wrote), and for the re-prompts Failproof AI itself sends to deliver an instruction.
- **Pi** fires `input` for what the human types and also for text another extension sends with `sendUserMessage()`, which can be written by the model or built from repository content. Pi says which in the event's `source`, and the Pi bridge forwards it as `input_source`. A Pi prompt is recorded only when that field is `interactive` (typed in Pi, or passed to `pi -p`) or `rpc` (sent by the program driving Pi in RPC mode). Input another extension sent is never recorded, and neither is a prompt from a bridge too old to forward the field.
- **OpenClaw** fires `before_agent_run` for heartbeat, cron, memory and inter-session runs as well as for chat messages, and on a shared channel the sender may not be the owner. OpenClaw states that a missing classification does not establish human origin, and it sets the owner flag only when it knows the sender. So a prompt is recorded only when the payload carries all three of `openclaw.trigger: "user"`, `openclaw.inputProvenance.kind: "external_user"` and `openclaw.senderIsOwner: true`. A missing field counts as not typed by the owner, so on a shared channel a message from anyone else in the chat is never recorded. The current plugin does not forward these fields, so no OpenClaw prompt is recorded yet.

## What is kept from a prompt

Harnesses put more than the human's words into a prompt. Before anything is stored:

- `<system-reminder>` blocks are removed, and the human's words around them are kept.
- A session-continuation summary ("This session is being continued from a previous conversation…") is dropped entirely.
- Task notifications, local-command output and interruption markers are dropped entirely.
- A turn another agent or session wrote is dropped entirely: Claude Code wraps those in `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` or `<channel source=…>`.
- Failproof AI's own messages are dropped entirely. A stop gate's `MANDATORY ACTION REQUIRED from failproofai …` or an `Instruction from failproofai: …` can come back as the next user turn on some harnesses (Cursor submits a stop gate's follow-up message as one), and they never count as the human's words.
- A slash command is kept as the command and arguments the human typed, never the body the harness expanded it into.
- A prompt the Codex IDE extension built keeps only the text after its last `## My request for Codex:` (or, in newer builds, `## My request:`) heading. Everything the extension put before it is dropped: the active file, open tabs, text selected in the editor, mentioned files and apps, diff and browser comments, PR checks, earlier conversations. Such a prompt starts with one of the extension's section headings (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:` and the others it writes); one with no request heading is not recorded. The request itself is judged like any other turn: if what follows the heading is a continuation summary, a message another agent or session wrote, one of Failproof AI's own directives, or another of the extension's sections, the prompt is not recorded at all.
- Pasted blocks are kept and labelled as pasted by the human.
- A Cursor prompt wrapped the way Cursor's own transcripts wrap a query (an optional `<timestamp>…</timestamp>`, then one `<user_query>…</user_query>` block) has the wrapper removed, but only when that wrapper is the whole prompt. A `<user_query>` tag anywhere else is part of the text: the whole prompt is kept, and the tagged span is never picked out as the request. Failproof AI's own messages are dropped whether or not they are wrapped.

A prompt that is nothing but harness text is not recorded at all.

## The agent's last message

A reply like "yes" means nothing without the question it answers. When a prompt is recorded, Failproof AI also reads the agent's last visible message from the session transcript **at that moment**, and stores it with the prompt. Jev receives it in its own field, labelled as written by the agent: it explains a short reply and never counts as the human's request.

It is read from the end of the transcript, at most the last 4 MB. Supported transcript formats are Claude Code, Codex rollouts (older `agent_message` events and newer `AgentMessage` items), Cursor, Copilot `events.jsonl`, and the Pi, Factory and OpenClaw session JSONL. Claude Code's own synthetic and API-error messages and subagent (sidechain) messages are skipped. There is no snapshot for Goose and OpenCode, which keep sessions in SQLite, for Devin, whose transcript is a single JSON document, or for OpenClaw, whose `before_agent_run` event carries no transcript path.

## Storage

| Property | Value |
| --- | --- |
| Location | `~/.failproofai/state/semantic/sessions/<session-id>.json` |
| Permissions | file `0600`, directory `0700` |
| Kept per session | the last 5 prompts |
| Window | prompts older than 6 hours are ignored |
| Size | each prompt and agent message is capped at 1,200 characters, keeping the head and the tail |
| Secrets | redacted with the same patterns as the `sanitize-*` policies before anything is written. A text longer than 9,600 characters is redacted as its first 5,760 and last 3,840 characters, and the text next to those cuts, where a secret could have been split, is never stored |

A session ID containing anything but letters, digits, `.`, `_` and `-`, or longer than 128 characters, is never used as a file name, so nothing is recorded for it.

The file also holds the session's origin state: that the session has been seen at all, and the mark of the transcript its next prompt has to continue. That is why it is written for every prompt-submit event Claude Code or Factory Droid fires, including the ones that record nothing, and why it outlives the prompts in it — it is deleted only after **seven days** without a prompt-submit event, the next time a new session starts. Nothing stale is ever read back as intent: every read drops prompts older than six hours.

Nothing is recorded unless a Jev endpoint is configured.

## Known limits

- **Subagents.** Codex sub-agent threads are detected from the rollout's `session_meta`. Claude Code's `UserPromptSubmit` payload has no field that marks a subagent (Claude Code 2.1.278 does not set `agent_id` on it), so a prompt event fired inside a Claude Code subagent could not be told apart from a typed one. The prompt is still skipped if a later version adds `agent_id` to this event, and the same hedge runs for Factory Droid and Devin CLI, whose payloads are Claude-shaped and which both have subagents. Whether Copilot, Cursor, Factory, Devin or Goose fire their prompt event inside a subagent has not been verified. A subagent that Pi starts as its own `pi -p` process reports its task as `interactive`, so it counts as that subagent session's own request.
- **A Codex rollout that does not vouch for the prompt.** Codex's sub-agent check needs the rollout, and Codex does not put `transcript_path` on the hook's stdin: the file is discovered from the session id under `~/.codex/sessions`. A Codex prompt is recorded only when that rollout is a readable regular file whose first line is a `session_meta` carrying a source mark that names no sub-agent. Everything else records nothing, rather than recording a prompt whose origin nothing vouches for: the rollout was not found (most often because `CODEX_HOME` points somewhere else, which the discovery does not yet honour), it is not a regular file (a path naming a FIFO or a device, which is never opened), it is empty or cannot be read, its first line is not a `session_meta`, or that line carries no `source` and no `thread_source` — Codex has written one since 0.131, so a rollout without one is a mark that went missing, not a session saying a human drove it.
- **Scheduled prompts beyond the transcript.** Recognizing a scheduled prompt depends on the transcript. The check reads the last 4 MB of it. It can miss a prompt whose scheduling call has scrolled further back than that, when Claude Code also wrote no scheduled-task entry for it (headless and SDK sessions have not been verified to write one). It can also miss one that fires when the transcript has not yet been written — a session's first prompt is recorded without it, which is the one moment a transcript legitimately holds no conversation. What the check cannot see through is an agent writing plausible entries into its own transcript: it reads the transcript, it does not authenticate it. The mark makes that harder rather than impossible — an agent that reproduces the transcript byte for byte up to the point the last prompt was seen, and appends its own continuation, erases what it wrote in between and still reads as the same file, grown. It has to hit that point without being able to read the mark, and anything short of it is a rewrite the next prompt refuses. Devin has no JSONL transcript to check.
- **What a rewritten or outrun transcript costs.** Both fail closed, and both cost prompts: a session whose transcript stops continuing the marked one records nothing more (re-running the harness starts a new session with a new mark), and a single turn that appends more than 4 MB costs the prompt that follows it its standing as intent. Nothing is blocked either way — Jev simply judges that prompt with no stated intent.
- **Programmatic prompts count.** A prompt sent through a harness's SDK or headless mode (`claude -p`, `codex exec`, `pi -p`, Pi's RPC mode) is treated as the operator's request, because the harness cannot tell it apart from a typed one.
