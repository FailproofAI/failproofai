When you configure your own Jev endpoint, the Jev evaluator judges each tool call against **what the human asked for**, not against whatever text the harness put in front of the agent. A reply such as "yes, force-push it" can clear a reviewable policy, so the only text that ever counts as the human's is text a human typed into the harness's prompt box.

A prompt is recorded **only when the harness's own payload names the operator as its author** — a field the harness writes on the hook's stdin, which the agent cannot edit. Nothing on disk is consulted: the session transcript is a file the agent can rewrite, so it is never asked who wrote a prompt. Anything missing, empty, ambiguous or merely probable records nothing.

That bar is high on purpose, because the event alone cannot clear it. Every one of these CLIs can be started headless with the prompt in its arguments — `claude -p`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t`, `pi -p` — and such a run fires the same prompt-submit event, with the same payload, as a person typing. An agent that can run one shell command can start one, and the session it starts is the session whose recorded intent would clear a policy for it. So a harness that sends no field naming the author is **not capturable**, however its prompt event is meant to be used.

Failing closed here never makes enforcement weaker. With no recorded prompt, Jev has no task to judge the call against, so it can clear no reviewable policy: nothing is ever allowed because a prompt could not be captured. It is not free, either, and the cost is worth knowing: the prompt-injection probe and the beyond-the-task check are asked only when there is a human message to judge against, so where nothing is recorded, a fired warn policy that prompt injection would have escalated to a block stays a nudge, and the beyond-the-task flag never fires.

This page lists, for each of the 12 supported harnesses, where that text comes from. Harnesses that never deliver human text through a prompt event are also listed, with the reason.

## Per-harness table

"Text field" is the stdin payload field after Failproof AI's per-harness normalization. "Recorded" says whether the prompt is kept as the human's request.

| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | Only when the payload's `source` is `user`, Claude Code's own name for the interactive composer. A build that does not send the field records nothing | the session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | No | — |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | No | — |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | No | — |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | No | — |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | No | — |

| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | Only when the run metadata marks the prompt as a message the owner sent from outside the agent — which the shipped plugin never marks, so nothing is recorded today | none (`before_agent_run` carries no transcript path) |

**No shipping build populates either field today**, so live intent capture currently records nothing on any harness: Claude Code 2.1.280 declares `source` and does not send it, and the OpenClaw plugin forwards no run metadata. Capture starts working, with no change to Failproof AI, on the first build that sends one. Until then Jev evaluates every tool call with no task to judge against: nothing can be cleared on the grounds that the human asked for it, and the check that flags a call reaching beyond the human's task stays off.

## What makes a prompt the human's

Three things, and nothing else:

1. **The event.** Failproof AI was invoked for the harness's prompt-submit event, which the handler canonicalizes to `UserPromptSubmit`.
2. **The payload.** The harness writes the payload on the hook's stdin; the agent cannot edit it. One field in it has to name the author of this prompt as the operator — Claude Code's `source`, OpenClaw's run metadata. A payload without that field records nothing; so does a call that reaches Failproof AI without its payload at all. Nothing else in the payload is treated as evidence of origin: not the event firing, not the text, not the session id.
3. **Nothing else.** A payload that names a sub-agent (`agent_id`) is the agent prompting itself and is never recorded. A session id that is not a plain name is never used. Text that is entirely harness wrapping is dropped (see below).

**The session transcript is not evidence of who wrote a prompt.** Earlier versions of this page described a transcript cross-check: the prompt was refused if the transcript showed the model scheduling it, and the transcript had to continue the one the previous prompt saw. That check is gone. A transcript is a file the agent already has a shell over — it can be truncated, replaced, padded past the read budget, snapshotted at the start of a turn and restored at the end, or made to read well again with entries the agent wrote. Each round of hardening was followed by another spelling of the same forgery, so the whole mechanism was removed rather than repaired. What is left is what a harness tells us directly, and prompts that cannot be established that way are simply not recorded.

The transcript is still read for one thing: **the agent's last visible message**. That message is agent-written by definition, Jev is told so, and it is never consent on its own.

## Harnesses that are not recorded

- **Claude Code before the `source` field.** `UserPromptSubmit` fires for more than typed prompts: a scheduled task coming due (`CronCreate`, a routine), a dynamic `/loop` wakeup, a `-p` or Agent SDK run, and machine-injected turns (peer and channel messages, task notifications, auto-continuation) all go through the same path. Claude Code names the author in the event's own `source` field (`user`, `sdk`, `system`, `loop_wakeup`, `schedule_wakeup`, `poll_event`), and only `user` is recorded. The field is optional in Claude Code's hook-input schema — "Payloads may omit it while the field rolls out" — and **2.1.280 does not send it**, so on that build no Claude Code prompt is recorded at all. `sdk` is not recorded either: an agent holding a shell can start its own `claude -p`, and that session reports `sdk` just as a scripted run does.
- **Codex** fires `user_prompt_submit` inside sub-agent threads too, whose prompts the parent agent wrote, and its hook payload carries no mark of which thread the event belongs to. The only witness was the rollout's `session_meta.source`, a file on disk the agent can rewrite. `codex exec "<text>"` fires the event as well.
- **GitHub Copilot CLI** sends nothing that names an author, and `copilot -p "<text>" --allow-all-tools` fires `UserPromptSubmit` exactly as a typed prompt does. Copilot also runs sidekick subagents in the same process.
- **Cursor** sends nothing that names an author, and `cursor-agent -p "<text>"` fires `beforeSubmitPrompt` exactly as a typed prompt does.
- **Devin CLI** sends nothing that names an author, and `devin -p "<text>"` fires `UserPromptSubmit` exactly as a typed prompt does.
- **Goose** sends nothing that names an author, and `goose run -t "<text>"` fires `UserPromptSubmit` exactly as a typed prompt does. Goose also has a `delegate` subagent tool, whose instructions the parent agent writes, and a scheduler of its own (`goose schedule add`).
- **Factory Droid** has Claude-shaped payloads and transcripts, ships a `SubagentStop` event, sends no `source`, and `droid -p "<text>"` fires `UserPromptSubmit` like the others.
- **Pi** fires `input` for what the human types, for text another extension sends with `sendUserMessage()`, and for the prompt of a `pi -p` run. Pi says which channel the input came through — `interactive`, `rpc` or `extension` — and the Pi bridge forwards it as `input_source`, but that names the channel, not the author: `pi -p "<text>"` reports `interactive`, the same value as a prompt typed in Pi's editor, and `rpc` is whatever program is driving Pi. No value of the field excludes an agent that started the session itself, so no Pi prompt is recorded.
- **Hermes** has no prompt-submit event. Its native plugin handles `pre_llm_call` itself and forwards only tool, session and subagent events.
- **Antigravity CLI** maps `PreInvocation` to `UserPromptSubmit`, but `PreInvocation` fires before *every* model call in a turn, carries no prompt text, and hooks can inject `userMessage` steps into the same conversation. Nothing in it identifies a human turn.
- **OpenCode** reports prompts through the `message.updated` bus event. In current OpenCode the message it carries has no text parts, so the forwarded prompt is empty. The event also fires again on every update to the same message, for the child sessions the task tool creates (whose "user" message the parent agent wrote), and for the re-prompts Failproof AI itself sends to deliver an instruction.
- **OpenClaw** fires `before_agent_run` for heartbeat, cron, memory and inter-session runs as well as for chat messages, and on a shared channel the sender may not be the owner. OpenClaw states that a missing classification does not establish human origin, and it sets the owner flag only when it knows the sender. So a prompt is recorded only when the payload carries all three of `openclaw.trigger: "user"`, `openclaw.inputProvenance.kind: "external_user"` and `openclaw.senderIsOwner: true` — a message a person outside the agent sent, and the owner at that. A missing field counts as not typed by the owner, so on a shared channel a message from anyone else in the chat is never recorded. The current plugin does not forward these fields, so no OpenClaw prompt is recorded yet.

## What is kept from a prompt

Harnesses put more than the human's words into a prompt. Before anything is stored:

- `<system-reminder>` blocks are removed, and the human's words around them are kept.
- A session-continuation summary ("This session is being continued from a previous conversation…") is dropped entirely.
- Task notifications, local-command output and interruption markers are dropped entirely.
- A turn another agent or session wrote is dropped entirely: Claude Code wraps those in `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` or `<channel source=…>`.
- Failproof AI's own messages are dropped entirely. A stop gate's `MANDATORY ACTION REQUIRED from failproofai …` or an `Instruction from failproofai: …` can come back as the next user turn on some harnesses, and they never count as the human's words.
- A slash command is kept as the command and arguments the human typed, never the body the harness expanded it into.
- A prompt the Codex IDE extension built keeps only the text after its last `## My request for Codex:` (or, in newer builds, `## My request:`) heading. Everything the extension put before it is dropped: the active file, open tabs, text selected in the editor, mentioned files and apps, diff and browser comments, PR checks, earlier conversations. Such a prompt starts with one of the extension's section headings (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:` and the others it writes); one with no request heading is not recorded. The request itself is judged like any other turn: if what follows the heading is a continuation summary, a message another agent or session wrote, one of Failproof AI's own directives, or another of the extension's sections, the prompt is not recorded at all. (Codex prompts are not recorded live; this cleaning also runs over replayed transcripts and over any harness that pastes an extension-built prompt.)
- Pasted blocks are kept and labelled as pasted by the human.

A prompt that is nothing but harness text is not recorded at all.

## The agent's last message

A reply like "yes" means nothing without the question it answers. When a prompt is recorded, Failproof AI also reads the agent's last visible message from the session transcript **at that moment**, and stores it with the prompt. Jev receives it in its own field, labelled as written by the agent: it explains a short reply and never counts as the human's request. It is the one thing the transcript is read for, and the worst a rewritten transcript can do is put a message the agent wrote where a message the agent wrote is expected. Where nothing is recorded, no snapshot is stored either — it is only ever stored alongside a prompt.

It is read from the end of the transcript, at most the last 4 MB. Supported transcript formats are Claude Code, Codex rollouts (older `agent_message` events and newer `AgentMessage` items), Cursor, Copilot `events.jsonl`, and the Pi, Factory and OpenClaw session JSONL; the readers for harnesses that record nothing are kept for replayed transcripts and for the day one of them names an author. Claude Code's own synthetic and API-error messages and subagent (sidechain) messages are skipped. There is no snapshot for Goose and OpenCode, which keep sessions in SQLite, for Devin, whose transcript is a single JSON document, or for OpenClaw, whose `before_agent_run` event carries no transcript path.

## Storage

| Property | Value |
| --- | --- |
| Location | `~/.failproofai/state/semantic/sessions/<session-id>.json` |
| Permissions | file `0600`, directory `0700` |
| Kept per session | the last 5 prompts |
| Window | prompts older than 6 hours are ignored |
| Size | each prompt and agent message is capped at 1,200 characters, keeping the head and the tail |
| Secrets | redacted with the same patterns as the `sanitize-*` policies before anything is written. A text longer than 9,600 characters is redacted as its first 5,760 and last 3,840 characters, and the text next to those cuts, where a secret could have been split, is never stored |

A session ID containing anything but letters, digits, `.`, `_` and `-`, or longer than 128 characters, is never used as a file name, so nothing is recorded for it.

A session file exists only once a prompt has been recorded in it. It holds prompts and nothing else — no origin state, no transcript mark — and it is deleted once it has been silent for longer than the six-hour window, the next time a new session writes its first prompt.

Nothing is recorded unless a Jev endpoint is configured.

## Known limits

- **Nothing is recorded on any harness today.** Claude Code 2.1.280 declares `source` in its hook-input schema but does not populate it (the payload builder computes the value and the field is compiled out of the object it builds), and the OpenClaw plugin forwards no run metadata. Every other harness is not capturable at all. Jev therefore judges every call with no stated intent: every reviewable policy that fires, stands, and the two checks that need the human's words — the injection escalation and the beyond-the-task flag — are off. This is deliberate: recording on a weaker signal is what an agent would exploit to clear those same policies. It is also the kind of limit a vendor closes in one field, and the shape of the field is written above.
- **Headless and SDK runs record nothing, on every harness.** `claude -p` and Agent SDK sessions report `source: "sdk"`, which is also what an agent's own `claude -p` subprocess reports. `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` and `pi -p` are not distinguishable from a typed prompt in their payloads at all, which is why those harnesses record nothing in any mode. A pipeline that drives an agent headlessly therefore gets no intent, and every reviewable policy it trips stands.
- **Subagents.** A payload that carries `agent_id` is never recorded, on any harness. Claude Code 2.1.280 does not set it on `UserPromptSubmit`; the check is there for the build that starts to. Whether Copilot, Cursor, Devin, Goose or Droid fire their prompt event inside a subagent has not been verified — it no longer matters, since none of them is recorded either way.
- **A recorded prompt is only as trustworthy as the hook invocation.** Everything here reads the payload the harness wrote on the hook's stdin. An agent that can run commands can also run Failproof AI's hook binary itself and feed it a payload it wrote, including a `source` field, which would record a prompt nobody typed. Nothing inside this module can tell that invocation from the harness's own — both are the same program reading the same stdin — so this is the trust boundary the whole hook model already sits on rather than something the origin checks can close. It is written down here because *writing* intent is the one thing an agent gains from it: skipping the hook cannot clear a policy, since the harness invokes Failproof AI for the tool call independently.
- **An agent's last message can be a message the agent chose.** The transcript is not authenticated, so an agent that writes its own transcript can decide what its "last message" says. That is the same thing it could do by simply saying it, which is why the field is labelled agent-written and never clears anything on its own.
- **`CODEX_HOME` is not honoured** by the rollout discovery in `lib/codex-sessions.ts`. This no longer affects whether a prompt is recorded, only where an agent-message snapshot is looked for.
