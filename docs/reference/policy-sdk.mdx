Custom policies turn a failure pattern from your traces or audits into a decision that runs while an agent works. A policy can allow an action, give the agent guidance, or deny the action before it causes another incident.

Use a custom policy when the behavior depends on your tools, paths, commands, environments, or operating rules. Check the [built-in policy catalog](/policies/builtin-catalog) first so you do not recreate an existing control.

## Author a custom policy

<Tabs>
  <Tab title="Dashboard">
    1. Go to **Admin → policy editor**, select **New policy**, and describe the failure you want to prevent.
    2. Add the policy source, then test expected matches and safe non-matches in the editor. Resolve every validation error.
    3. Save the draft and select **Publish version** to create an immutable version.
    4. Go to **Admin → enforcement**, deploy the version to a test machine in **observe** mode, and verify its decisions under **Observe → policy** before enforcing it.

    ![The policy editor used to author and publish a custom policy.](/images/dashboard/policy-editor.png)
  </Tab>
  <Tab title="CLI">
    1. Write a starter policy with `failproofai publish --init`, or create `.failproofai/policies/checkout-policies.ts` by hand. A convention filename must end in `policies.js`, `policies.mjs`, or `policies.ts`.
    2. Register one or more policies with `customPolicies.add()`.
    3. Enforce the file on this machine right now: `failproofai policies -i -c ./.failproofai/policies/checkout-policies.ts`.
    4. Trigger one matching action and one safe action. Run `failproofai policies`, then open **Policies → Activity** on the [local dashboard](/reference/local-dashboard) and filter by source to see which policy decided.
  </Tab>
</Tabs>

## Start with a narrow rule

This policy blocks destructive Kubernetes commands only when the command targets production. Everything outside that exact failure mode returns `allow()`.

```ts
import { customPolicies, allow, deny } from "failproofai";

const DESTRUCTIVE_KUBECTL = /\bkubectl\s+(delete|replace)\b/i;
const PRODUCTION_TARGET = /(?:--context|--namespace|-n)\s+(prod|production)\b/i;

customPolicies.add({
  name: "block-destructive-production-kubectl",
  description: "Block destructive Kubernetes commands against production",
  match: { events: ["PreToolUse"] },
  fn: async ({ toolName, toolInput }) => {
    if (toolName !== "Bash") return allow();

    const command = String(toolInput?.command ?? "");
    if (!DESTRUCTIVE_KUBECTL.test(command)) return allow();
    if (!PRODUCTION_TARGET.test(command)) return allow();

    return deny(
      "Destructive production Kubernetes commands require the approved deployment workflow.",
    );
  },
});
```

Good policies are narrow enough to explain in one sentence. Match the observable action—not the intent you hope the agent had—and return `allow()` as soon as the rule does not apply.

## Choose a decision

| Helper | Result | Use it when |
| --- | --- | --- |
| `allow(reason?)` | The operation continues. | The policy does not apply or the action is safe. |
| `instruct(reason)` | The operation continues, and the reason is delivered to the agent on the harnesses that have a channel for it. | You want to steer the agent toward a better approach without enforcing an invariant. |
| `deny(reason)` | The operation is blocked on the harness and event pairs verified to consume a blocking verdict. | The action must not proceed. |

Write the reason for the agent that must recover. Explain what was detected and what it should do instead.

### Where `instruct()` actually arrives

`instruct()` needs an additional-context channel in the harness. Six harnesses have none on some or all events; there the operation is allowed and the message is written to stderr, where the agent never reads it.

| Harness | Events that deliver the instruction |
| --- | --- |
| Claude, Codex, Copilot, Cursor, Devin, OpenCode | `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, and `PermissionRequest` carry it as additional context. `Stop` and `SubagentStop` carry it through the retry channel instead. Every other event emits a message the harness ignores. |
| Antigravity | `UserPromptSubmit` and `Stop` only. |
| Factory, Pi, OpenClaw | `Stop` only. |
| Hermes, Goose | None. Always allow plus a stderr note. |

No harness fires all 29 canonical events, so the first row is bounded by what each one installs — an instruction only arrives on an event that harness actually fires. Check the installed event set per harness in [Agent harnesses](/reference/harnesses) before relying on one.

<Warning>
  Do not use `instruct()` for a safety boundary. On Hermes and Goose it never reaches the agent at all, and on Antigravity, Factory, Pi, and OpenClaw it does not reach it on tool events. Use `deny()` when the action must be prevented.
</Warning>

## Policy object

```ts
customPolicies.add({
  name: "policy-name",
  description: "What this policy prevents",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => allow(),
});
```

| Field | Required | Description |
| --- | --- | --- |
| `name` | Yes | Stable identifier for the policy. Keep names unique across files. |
| `description` | No | Human-readable purpose shown in policy listings and decisions. |
| `match.events` | No | Event types that invoke the policy. Omitting `match` invokes it for every available event. |
| `fn` | Yes | Synchronous or asynchronous function that returns an `allow`, `instruct`, or `deny` result. |

Filter tools inside `fn`. `match.toolNames` is not part of the public custom-policy type.

A policy published inside a pack may carry two more fields, `category` and `defaultEnabled`. See [From a file to a pack](#from-a-file-to-a-pack).

## Policy context

Every policy receives a `PolicyContext`.

| Field | Type | What it contains |
| --- | --- | --- |
| `eventType` | `HookEventType` | Normalized event currently being evaluated. |
| `toolName` | `string \| undefined` | Canonical tool name such as `Bash`, `Read`, `Write`, or `Edit`. |
| `toolInput` | `Record<string, unknown> \| undefined` | Canonical input for the current tool call. |
| `payload` | `Record<string, unknown>` | Complete normalized event payload. |
| `session` | `SessionMetadata \| undefined` | Session ID, working directory, transcript path, permission mode, and harness metadata when available. |
| `cli` | `string \| undefined` | Source agent harness, such as `claude`, `codex`, or `cursor`. |
| `params` | `Record<string, unknown>` | Parameters for this policy. A builtin or a pack policy declares a schema, and the values the user configured are merged over its defaults. A policy in a custom file declares no schema, so it receives whatever the user configured under its name, and `{}` when nothing is configured. |

Treat every optional value as genuinely optional. Agent versions and event types do not all provide the same fields.

### Common tool inputs

Failproof AI normalizes common tools across supported harnesses so a policy can usually use one input shape.

| Tool | Common fields |
| --- | --- |
| `Bash` | `command` |
| `Read` | `file_path` |
| `Write` | `file_path`, `content` |
| `Edit` | `file_path`, `old_string`, `new_string` |
| `Grep` | `pattern`, `path` |

Use defensive coercion because tool input values are typed as `unknown`:

```ts
const command = String(ctx.toolInput?.command ?? "");
const filePath = String(ctx.toolInput?.file_path ?? "");
```

## Choose the event

| Event | When it runs | Typical use |
| --- | --- | --- |
| `PreToolUse` | Before a tool executes. | Block or guide commands, writes, reads, and external actions. This is the guard. |
| `PostToolUse` | After the tool has already executed. | Inspect or replace the result the model reads. It cannot undo the side effect—the write or the command already happened—and on fourteen of the sixteen harnesses the verdict cannot stop anything. Only Codex and Copilot consume it, and even there it replaces the result the model reads rather than preventing the call. Never use it as a guard. |
| `PermissionRequest` | When the agent requests permission. | Apply organization-specific permission rules. |
| `UserPromptSubmit` | Before a submitted prompt continues. | Reject prohibited instructions or add workflow guidance. |
| `Stop` | When the agent attempts to finish. | Require a reachable completion condition, such as a local verification step. |
| `SubagentStop` | When a subagent attempts to finish. | Gate delegated work before it returns to the parent. |
| `SessionStart` / `SessionEnd` | At session boundaries. | Record or check session-level state. |

Event availability and blocking behavior depend on the agent harness, and the differences are large: Failproof AI installs no `Stop` hook for Goose or Hermes, so a stop gate never fires on either. See [Agent harnesses](/reference/harnesses) before relying on an event across a mixed fleet.

<Accordion title="All policy event names">
  `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `Elicitation`, `ElicitationResult`, `UserPromptExpansion`, `PostToolBatch`, and `Setup`. That is the full set of 29 canonical event names every harness's own event vocabulary is normalized into.
</Accordion>

## Author common policy patterns

### Block writes to protected paths

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "block-generated-file-edits",
  description: "Require generated files to be changed through their generator",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();

    const filePath = String(ctx.toolInput?.file_path ?? "");
    if (!/(^|\/)(dist|generated)\//.test(filePath)) return allow();

    return deny("Edit the source and run the generator instead of changing generated output.");
  },
});
```

### Give non-blocking guidance

```ts
import { customPolicies, allow, instruct } from "failproofai";

customPolicies.add({
  name: "prefer-reviewed-deploy-command",
  description: "Guide agents toward the reviewed deployment wrapper",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();

    const command = String(ctx.toolInput?.command ?? "");
    if (!/^kubectl\s+apply\b/.test(command.trim())) return allow();

    return instruct("Use ./scripts/deploy-reviewed instead of invoking kubectl directly.");
  },
});
```

### Gate session completion

```ts
import { execFileSync } from "node:child_process";
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "require-clean-typecheck",
  description: "Require the project typecheck to pass before the agent finishes",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow();

    try {
      execFileSync("bunx", ["tsc", "--noEmit"], {
        cwd,
        stdio: "ignore",
        timeout: 8_000,
      });
      return allow();
    } catch {
      return deny("Fix the typecheck errors before finishing the task.");
    }
  },
});
```

<Warning>
  A denied `Stop` event can make the agent retry. Only gate on a condition the agent can satisfy in the current environment, and bound every subprocess or network call.
</Warning>

## Load policy files

### Convention files

Convention files load automatically:

```text
<project>/.failproofai/policies/security-policies.ts
~/.failproofai/policies/personal-policies.mjs
```

- Project and user policy directories are both loaded.
- Files load alphabetically within each directory.
- A file must end in `policies.js`, `policies.mjs`, or `policies.ts`.
- Multiple `customPolicies.add()` calls in one file are supported.
- Relative imports from local modules are supported.
- Project policies can be committed so the same rules follow the repository.

<Warning>
  A file in the directory whose name does not end in `policies.{js,mjs,ts}` is skipped. It looks installed and enforces nothing. The loader lists every skipped file with the name to rename it to; read that warning rather than assuming a policy is live. This repository shipped `block-version-bumps.mjs` that way, and the guard written after a bad version bump had never once run.
</Warning>

`~/.failproofai/policies/` also holds two subdirectories you did not put there: `cloud-policies/` for fleet-managed deployments and `packs/` for installed packs. The loader never descends into either, so nothing in them is picked up as an unverified convention policy.

### Turn a discovered policy off

Two keys in `policies-config.json` switch off convention policies without deleting or renaming the file:

| Key | Effect |
| --- | --- |
| `disabledCustomPolicies` | An array of source-qualified policy IDs that are not registered. |
| `customPoliciesEnabled` | Set to `false` to stop loading `.failproofai/policies/` entirely. Absent means enabled. |

The **Policies → Configure** tab of the [local dashboard](/reference/local-dashboard) writes `disabledCustomPolicies` for you. `customPoliciesEnabled` is written by `failproofai config`, or by hand.

### Explicit files

Use explicit paths when validation or configuration should name the entry file directly:

```bash
failproofai policies --install \
  --custom ./security.policies.ts \
  --custom ./workflow.policies.ts \
  --scope project
```

Explicit files load first, followed by project convention files and then user convention files. A file discovered through both paths is loaded once.

## Validate and test

`-c` is the short form of `--custom`, and `-i` of `--install`. It enforces the file right now, at any path and under any filename:

```bash
failproofai policies -i -c ./checkout-policies.ts
failproofai policies
```

Ask your agent to do the thing you blocked and watch it get refused. Nothing is published and no other machine is affected.

Validation executes the module through the production loader and confirms that it registers at least one policy. It catches missing files, syntax errors, unresolved imports, top-level exceptions, and module-load timeouts. It does not prove that your match logic is correct.

Test at least these cases:

- One action that must match and produce the intended policy reason.
- One nearby but safe action that must return `allow()`.
- Missing or malformed tool fields.
- Alternate command syntax, paths, quoting, casing, and whitespace.
- An unavailable subprocess or network dependency.

Attribute the result to your custom policy under **Policies → Activity** on the local dashboard. A blocked test is not sufficient if a different built-in policy made the decision.

## Runtime behavior

- Built-in policies evaluate before custom policies.
- The first `deny` stops further policy evaluation.
- Multiple `instruct` results can be combined when no policy denies the event.
- A policy function has a 10-second execution deadline. Top-level module loading has the same deadline.
- A thrown exception or timeout is logged and treated as `allow()`.
- A convention file that fails to load is skipped; other custom files and built-in policies continue.
- Observe mode runs the policy for real and records any non-allow verdict without enforcing it. Two layers set it: `failproofai publish --effect observe` on a pack you publish, and `fp fleet deploy <machine> --add <id>:observe` on a Cloud deployment. Either way the policy is evaluated under the same 10-second deadline as an enforcing one, so a policy that times out records as an allow.

### Where the loader fails closed instead

The fail-open rule above covers a file you dropped in yourself. Two paths deliberately do the opposite, because both mean this machine was told it had enforcement it does not have.

| Situation | Result |
| --- | --- |
| A selected pack cannot be loaded, or its pinned digest does not match | Every event in the scope that pack declared is denied, attributed to `pack/failproofai-pack-unavailable`. `UserPromptSubmit` instructs instead of denying, so you are never locked out of the agent you need in order to fix it. Unreadable pack metadata widens the denied scope rather than narrowing it. |
| The `failproofaid` daemon cannot be reached on a machine that completed setup | Every event is denied. No config is read and no custom policy runs, because a daemon that could not be reached could not have run them either. A protocol-version mismatch denies too, with a message naming `failproofai config`. |

On a machine that completed setup, `failproofaid` is the only evaluator, so your `fn` runs inside the daemon's warm worker rather than in the hook process. The hook client allows 150 ms to connect and 30 seconds for the answer, comfortably above the fixed 10-second deadline each policy function gets.

Keep policy modules deterministic and quick. Avoid top-level network calls or server startup. Bound work inside `fn`, catch dependency failures, and choose deliberately whether that failure should allow or deny the operation.

## From a file to a pack

A pack is how a policy file becomes something other machines can install. Two commands take you from nothing to a published pack:

```bash
failproofai publish --init
failproofai publish
```

`--init` asks what the pack is called, writes `<name>.mjs`, and stops. The file is not a template with blanks—it is one policy that already blocks `git push --force`, so the first thing you edit is something that works. Prove it locally with `failproofai policies -i -c ./<name>.mjs`, then run `failproofai publish` from inside the git repository holding it.

Two fields matter once a policy ships in a pack:

| Field | What it does |
| --- | --- |
| `category` | What `failproofai policies add <owner>/<repo> --category git,database` selects on. |
| `defaultEnabled` | Whether a bare `failproofai policies add <owner>/<repo>` switches this policy on. Defaults to `false`. |

`--effect` is set per pack rather than per policy: `failproofai publish --effect observe` publishes a pack that records what its policies would have decided and blocks nothing. The default is `enforce`. This is observe mode on a single machine with no Cloud connection — read the recorded verdicts back under **Policies → Activity** on the local dashboard.

The pack's version is the 12-character short commit sha it was built from, so `publish` refuses outside a git checkout and on a dirty tree. See [Publish a pack](/policies/publish-a-pack) for the full flow, and [Policy packs](/policies/packs) for how installs resolve a version.

## API exports

| Export | Purpose |
| --- | --- |
| `customPolicies.add(policy)` | Register a custom policy when the module loads. |
| `allow(reason?)` | Permit the operation. |
| `instruct(reason)` | Permit the operation and provide guidance where supported. |
| `deny(reason)` | Block the operation where supported. |
| `getCustomHooks()` | Return the policies currently registered in the module registry. |
| `clearCustomHooks()` | Clear that registry, primarily for tests and loaders. |

TypeScript exports `PolicyContext`, `PolicyResult`, `CustomHook`, `PolicyDecision`, and `PolicyFunction`.
