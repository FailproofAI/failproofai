Используйте отдельный ключ для каждого человека, машины или задания автоматизации. Предоставляйте только необходимые разрешения.

## Создание и ротация ключа

Используйте **Admin → Keys** или облачный CLI:

```bash
fp keys list
fp keys create "audit automation" --add audits:read
fp keys disable "audit automation"
```

Сохраните секретный ключ при его создании — он больше не будет показан. Выполняйте ротацию, создав новый ключ, обновив потребителя, а затем отключив старый ключ.

## Машинные ключи

Машинный ключ подключает локальный сервис к облаку:

```bash
export FAILPROOFAI_CLOUD_TOKEN="<key>"
failproofai config
```

Подключенной машине могут потребоваться два возможности:

- `policies:pull` для получения управляемых облаком политик.
- `events:add` для отправки решений и сессий.

Статус докладывает об этом отдельно, потому что один из них может работать, а другой нет.

## Общие разрешения

| Разрешение | Что позволяет |
| --- | --- |
| `events:add` | Отправка событий |
| `events:read` | Чтение событий и ошибок |
| `evaluations:read` | Чтение сессий и оценок |
| `audits:read` / `audits:write` | Просмотр или управление аудитами |
| `policies:read` / `policies:write` | Просмотр или развертывание политик |
| `policies:pull` | Получение назначений машинных политик |
| `keys:create` / `keys:disable` | Создание или отключение ключей |
| `orgs:admin` | Администрирование организации на уровне экземпляра; не может быть назначено ключу организации |

Некоторые административные команды `fp fleet` и `fp guardrails` требуют сеанса вошедшего в систему пользователя, а не ключа API. Их справочный текст указывает на это перед выполнением запроса.

<Warning>
  Никогда не переиспользуйте учетные данные приема, такие как `AGENTEYE_KEY` или `AGENTEYE_API_KEY`, в качестве `FP_API_KEY`. Они служат разным системам и имеют разные разрешения.
</Warning>
