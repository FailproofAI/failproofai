Организации изолируют сессии, оценки, аудиты, проблемы, оповещения, запросы, панели управления, пользователей и ключи. Перед изменением любого административного ресурса подтвердите активную организацию.

## Выбор организации

<Tabs>
  <Tab title="Панель управления">
    Используйте переключатель организаций в верхней части боковой панели Cloud. Всё ниже него — включая каждую страницу **admin** — тогда читает и записывает эту организацию.
  </Tab>
  <Tab title="CLI">
    ```bash
    fp orgs list
    fp orgs switch reliability-team
    fp orgs current
    fp orgs perms
    ```

    `fp orgs switch` без slug открывает интерактивный выбор со стрелками, начиная с вашей текущей организации; неинтерактивный запуск переходит на нумерованный выбор, а под флагом `--json` требуется slug. Выбор сохраняется в `~/.failproofai/fpcli/cli-auth.json`, так что последующие команды отправляют его как активный клиент. Переопределите его для одной команды с помощью `--org <slug>` или `FP_ORG`.
  </Tab>
</Tabs>

<Note>
  Каждая команда `fp orgs` требует вошедшего в систему человека и отказывает при использовании ключа API, потому что членство в организации принадлежит человеку, а ключ уже действует для одной организации. Команды `fp users` ниже работают в обоих случаях.
</Note>

## Управление членами

<Tabs>
  <Tab title="Панель управления">
    1. Перейдите в **admin → users** и найдите членов по электронной почте, или сужайте список с помощью фильтров `protected`, `admin`, `standard` и `read-only`.
    2. Выберите **new user**, введите электронную почту, выберите набор разрешений и при необходимости отрегулируйте переопределения для отдельных членов.
    3. Откройте члена позже, чтобы изменить права, отключить вход или повторно активировать аккаунт.

    ![Страница пользователей с полем поиска по электронной почте, фильтрами и карточкой члена, показывающей его права, сгруппированные по ресурсам.](/images/dashboard/users.png)

    Фишки прав на этом скриншоте предшествуют переименованию с `incidents:*` на `issues:*`; список [общих разрешений](/ru/admin/keys-and-permissions#common-permissions) актуален.
  </Tab>
  <Tab title="CLI">
    ```bash
    fp users list
    fp users list --active-only
    fp users create engineer@example.com --permission-set standard
    fp users show engineer@example.com
    fp users update engineer@example.com --add audits:write
    fp users disable engineer@example.com
    fp users enable engineer@example.com
    ```

    Члены указываются по электронной почте и разрешаются без учёта регистра, поэтому `fp users show Alice.Chen@Example.com` и `fp users create alice.chen@example.com` относятся к одному и тому же человеку.
  </Tab>
</Tabs>

### Права и что требует каждый глагол

Права членов используют ту же арифметику, что и ключи: эффективные права — это `(set ∪ added) − removed`, а `--add` / `--remove` принимают компактные токены `slug:action.action`, где точечные действия разворачиваются. См. [ключи и разрешения](/ru/admin/keys-and-permissions).

| Глагол | Разрешение | Примечания |
| --- | --- | --- |
| `fp users list` / `show` | `users:read` | `--active-only` скрывает отключённых членов. |
| `fp users create` | `users:create` | `--permission-set` задаёт роль; `--add` / `--remove` добавляют переопределения. |
| `fp users update` | `users:update` | `--permission-set` **заменяет** переопределения конкретного члена; `--add` / `--remove` по отдельности — это добавочные операции к его текущим правам. |
| `fp users disable` / `enable` | `users:delete` | Оба, включая enable — предоставьте это намеренно. |

Отключение отказывает в двух случаях явно как ошибка Forbidden, а не как сообщение валидации: член с типом **protected** не может быть отключён, и вы не можете отключить собственный аккаунт. Отключение уже отключённого члена или активация уже активного — спокойная холостая операция. API использует операцию удаления для отключения, но она не удаляет ни аккаунт, ни запись о членстве.

Два параметра организации управляют членством: `default_user_permissions` предустанавливает набор разрешений для нового приглашения, а `allowed_sign_ins` определяет, какие адреса вообще могут получить код входа. Управляйте ими со [страницы параметров](/ru/admin/settings-and-security).

<Warning>
  Отключение пользователя блокирует этот идентификатор от входа во все организации, не только в текущей. Повторная активация восстанавливает глобальный вход и права члена в этой организации.
</Warning>

<Tip>
  Давайте сервисным аккаунтам описательные имена, связанные с рабочей нагрузкой и владельцем. Не делитесь ключом между организациями или между человеком и машиной.
</Tip>
