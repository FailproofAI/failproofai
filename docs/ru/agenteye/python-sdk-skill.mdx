Скажите своему кодирующему агенту *«добавь Failproof AI Observability к этому агенту»* и позвольте ему прочитать ваш цикл, разобраться, где нужна инструментирование, написать её и проверить события перед завершением работы.

**Python SDK skill** (`agenteye-python-sdk`) — это *Agent Skill*: папка инструкций, которую кодирующий агент, такой как Claude Code или Codex, загружает по требованию при совпадении с задачей. Она учит агента использовать [Python SDK](/ru/agenteye/python-sdk) — это не библиотека и не меняет то, как работает SDK.

## Инструментирование легко писать и легко допустить ошибку незаметно

SDK небольшой: тринадцать методов событий, все с именованными параметрами. Кодирующий агент может прочитать справочник [Python SDK](/ru/agenteye/python-sdk) и написать правдоподобное инструментирование за минуту.

Но SDK не вызывает исключение, если вы ошиблись, и неправильное инструментирование выглядит точно как правильное до тех пор, пока кто-то не откроет дашборд и не обнаружит его пустым. Ошибки, которые отнимают реальное время — это молчания:

| Ошибка | Что вы видите |
|---|---|
| Нет `agent_start` | Все события приходят. Нулевых сессий. |
| Окружение никогда не установлено | Всё работает, подано под `dev`. |
| `outcome="failure"` | Запуск показывается зелёным — считаются только `failed`, `error`, `timeout`, `rejected`. |
| Опечатка в названии поля | Принимается и сохраняется как новое поле. |
| События, отправленные из пула потоков | Молча отбрасываются. |

Ничего из этого не вызывает исключение. Ничего не показывается в тестах. Всё это есть в skill, указано как контракт с проверкой, которая это ловит.

## Что она делает, по порядку

Skill выполняет те же три шага, что и внимательный инженер:

1. **План.** Она читает цикл вашего агента и задаёт два вопроса, на которые можете ответить только вы: что считается одним запуском (ваш `session_id`) и кто отличающиеся друг от друга субъекты (ваш `agent_id`). Она согласует это перед написанием кода, потому что его изменение позже разбивает вашу историю и ломает тренды.
2. **Напиши.** Она привязывает идентификацию один раз за запуск вместо протягивания через каждую точку вызова и выбирает форму, безопасную для конкурентности — деталь, которая важна, потому что очевидный ярлык молча смешивает два перекрывающихся запуска в одну сессию.
3. **Проверь.** Она запускает ваш агент и читает полученные файлы событий, проверяя, что `agent_start` есть, окружение правильное и один запуск создал одну сессию.

Этот третий шаг — тот, который пропускают люди. SDK пишет события в локальные файлы, поэтому полная интеграция может быть доказана на ноутбуке без сервера, без API ключа и без сети — именно поэтому skill настаивает на это.

## Как это относится к другим skills

Три skills, одно чистое разделение:

| Skill | Используйте когда | Что она трогает |
|---|---|---|
| **Python SDK skill** (эта страница) | Вы хотите, чтобы ваш агент *отправлял* телеметрию — «добавить наблюдаемость», «почему мой агент не появляется?» | Пишет код в репозитории вашего агента. Ничего не читает. |
| **[Evaluator skill](/ru/agenteye/evaluator-skill)** | Вы хотите *оценить* запуски — «что нам вообще нужно измерять?» | Пишет код в вашем репозитории; читает телеметрию |
| **[CLI skill](/ru/agenteye/cli-skill)** | Вы хотите *прочитать*, что произошло, или управлять развёртыванием | Управляет CLI как вы, включая изменения |

Они передают друг другу в этом порядке: этот skill запускает события, оценщик их оценивает, CLI их читает. Нечего оценивать и нечего читать, пока ваш агент не отправляет сессии, поэтому если вы начинаете с нуля, начните отсюда.

## Предусловия

1. **Python 3.10+** и кодовая база агента, которую вы хотите инструментировать.
2. **SDK.** Он распространяется клиентам как приватное колесо, а не из публичного индекса — в вашем onboarding рассказано, как его получить и установить. Skill знает путь установки и попросит вас, а не будет угадывать, если не сможет его найти.
3. **Ничего больше.** Нет входа на дашборд, нет API ключа, нет сети. Skill проверяется против файлов событий, которые пишет SDK, поэтому она может завершиться и доказать свою работу без сети.

## Где её получить

Skill находится в публичной коллекции [`FailproofAI/skills`](https://github.com/FailproofAI/skills):

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

Добавьте `-g`, чтобы установить её для каждого проекта вместо только текущего, и `--copy` если ваша окружение не следует симссылкам. Для Codex передайте `-a codex`.

## Установка вручную

Agent Skills — это папки, содержащие `SKILL.md` плюс ссылки. Если вы предпочитаете не использовать установщик:

- **Claude Code**: скопируйте папку `agenteye-python-sdk/` в `~/.claude/skills/` (все проекты) или `<your-repo>/.claude/skills/` (только этот репозиторий). Claude Code автоматически её обнаружит — проверьте список `/skills` или просто попросите что-то, что совпадает с ней.
- **Codex**: Codex читает тот же `SKILL.md`. Включённый `agents/openai.yaml` устанавливает `allow_implicit_invocation: true`, поэтому она автоматически выбирается при совпадении задачи; в противном случае вызовите её как `$agenteye-python-sdk`.

Запустите ваш агент **в репозитории, содержащем код, который вы хотите инструментировать** — skill читает цикл вашего агента перед тем, как что-то предложить.

## Как выглядит сессия

```text
вы    ▸ Добавь Failproof AI Observability к этому агенту.

агент ▸ Прочитал ваш цикл — один диспетчер инструментов в tools.py,
        один оборотчик Anthropic в llm.py. Два вопроса перед тем,
        как я напишу что-нибудь.

        Что считается одним запуском? Вы обрабатываете запросы
        одновременно, поэтому я бы использовал id запроса, который
        у вас уже есть в ctx.request_id — тогда сессия здесь и запрос
        в вашей логе — это одна и та же строка.

        И кто субъекты? Я вижу путь планировщика и путь исследователя.
        Обозначить их отдельно или это один агент для вас?

вы    ▸ ID запроса верный. Они один агент, называйте его
        «помощник».

агент ▸ Готово. Обёрнул диспетчер и клиент LLM; agent_start и
        agent_end охватывают handle_request, включая путь ошибки.
        Использовал контекстную переменную для идентификации — ваш
        диспетчер запускает инструменты в пуле потоков, и более
        простой подход бы молча смешал совпадающие запуски в одну
        сессию без жалоб.

        Проверил на реальном запуске: 11 событий через 4 файла —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, одна
        сессия за запрос, сопряжённые длительности.

        Одно, что я НЕ сделал: ваш пул рабочих в batch.py отправляет
        прямо исполнителю, поэтому события оттуда бы отбросились.
        Хотите, чтобы я это тоже исправил?
```

Паттерн, который нужно заметить: она прочитала код перед предложением, задала только вопросы, на которые можете ответить вы, переиспользовала id, который у вас уже был, выбрала форму, безопасную для конкурентности, *потому что* видела пул потоков, и **проверила путём чтения реальных событий** вместо объявления успеха — затем пометила одно место, где знала, что молча сломается.

## Что вы можете у неё попросить

- *«Почему мой агент не показывается на дашборде?»* → проходит лестницу: пишутся ли события, есть ли `agent_start`, правильное ли окружение, читает ли коллектор то же место.
- *«Всё приходит под dev.»* → окружение никогда не было установлено или было сброшено более поздним вызовом.
- *«Добавь отслеживание токенов.»* → находит вашу обёртку LLM и записывает модель, причину остановки и использование.
- *«Инструментируй и подагентов.»* → одна сессия, отличающиеся метки агентов, вложенные под их родителя.
- *«Напиши тесты для инструментирования.»* → направляет SDK в временный каталог и проверяет события, которые он написал.

## На что обратить внимание

**Позвольте ей проверить.** Шаг, который делает этот skill стоящим, — последний — запуск вашего агента и чтение событий обратно. Агент, который пишет инструментирование и останавливается, сделал лёгкую половину, а половина, которая молча ломается, — другая.

**Согласуйте названия перед кодом.** `session_id` и `agent_id` — это оси, по которым группирует каждая поверхность. Их переименование позже разбивает историю: старые запуски сохраняют старые метки и ваши тренды ломаются. Skill спросит; ответ стоит минуты размышления.

**Если ваш агент предлагает установить SDK из публичного индекса, skill не загрузился.** SDK распространяется приватно. Это предложение — надёжный признак того, что ваш кодирующий агент угадывает вместо следования skill — остановите его там и проверьте, что skill установлен.

Кроме этого его радиус поражения мал: он пишет код в вашей рабочей директории и файлы событий где вы скажете. Он ничего не читает из вашего развёртывания и ничего в нём не меняет.
