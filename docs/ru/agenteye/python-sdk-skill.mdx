Скажите вашему кодирующему агенту *«добавь Failproof AI Observability к этому агенту»* и позвольте ему прочитать ваш цикл, определить, где должно быть инструментирование, написать его и проверить события перед тем, как завершить задачу.

**Python SDK skill** (`agenteye-python-sdk`) — это *Agent Skill*: папка с инструкциями, которые кодирующий агент, такой как Claude Code или Codex, загружает по требованию при совпадении задачи. Он учит агента использовать [Python SDK](/ru/agenteye/python-sdk) — это не библиотека, и он ничего не меняет в работе SDK.

## Инструментирование легко писать и легко писать неправильно без видимых причин

SDK небольшой: тринадцать методов событий, все только именованные аргументы. Кодирующий агент может прочитать справочник [Python SDK](/ru/agenteye/python-sdk) и создать правдоподобное инструментирование за минуту.

Загвоздка в том, что этот SDK не выбрасывает исключения, когда вы ошибаетесь, и неправильное инструментирование выглядит точно так же, как правильное, пока кто-то не откроет панель мониторинга и не найдёт её пустой. Ошибки, которые стоят реального времени, — это все молчания:

| Ошибка | Что вы видите |
|---|---|
| Нет `agent_start` | Каждое событие попадает. Нулевых сессий. |
| Окружение никогда не установлено | Всё работает, помечено как `dev`. |
| `outcome="failure"` | Запуск показывает зелёный — только `failed`, `error`, `timeout`, `rejected` считаются. |
| Опечатка в имени поля | Принимается и сохраняется как новое поле. |
| События, отправленные из пула потоков | Молча отброшены. |

Ничего из этого не выбрасывает исключения. Ничего не появляется в тестах. Каждое есть в skill'е, указано как контракт с проверкой, которая его ловит.

## Что он делает, по порядку

Skill выполняет те же три шага, которые выполнил бы внимательный инженер:

1. **План.** Он читает ваш цикл агента и задаёт два вопроса, на которые ответить можете только вы: что считается одним запуском (ваш `session_id`) и какие различаемые действующие лица есть (ваш `agent_id`). Он согласовывает это перед написанием кода, потому что изменение их позже разбивает вашу историю и ломает тренды.
2. **Запись.** Он привязывает идентичность один раз за запуск, а не проводит её через каждый сайт вызова, и выбирает форму, безопасную для параллелизма — деталь, которая имеет значение, потому что очевидный ярлык молча смешивает два перекрывающихся запуска в одну сессию.
3. **Проверка.** Он запускает ваш агент и читает результирующие файлы событий, проверяя наличие `agent_start`, правильность окружения и создание одной сессии за один запуск.

Этот третий шаг — тот, который люди пропускают. SDK записывает события в локальные файлы, поэтому полная интеграция может быть доказана на ноутбуке без сервера, без API ключа и без сети — именно поэтому skill настаивает на том, чтобы это делать.

## Как это соотносится с другими skills

Три skills, одно чистое разделение:

| Skill | Используйте когда | Что он трогает |
|---|---|---|
| **Python SDK skill** (эта страница) | Вы хотите, чтобы ваш агент *отправлял* телеметрию — «добавить наблюдаемость», «почему мой агент не показывается?» | Пишет код в репозитории вашего агента. Ничего не читает. |
| **[Evaluator skill](/ru/agenteye/evaluator-skill)** | Вы хотите *оценивать* запуски — «что вообще мы должны измерять?» | Пишет код в вашем репозитории; читает телеметрию |
| **[CLI skill](/ru/agenteye/cli-skill)** | Вы хотите *прочитать* что произошло, или управлять вашим развёртыванием | Управляет CLI от вашего имени, включая изменения |

Они передают ответственность по порядку: этот skill запускает поток событий, evaluator их оценивает, CLI читает их обратно. Нечего оценивать и нечего читать, пока ваш агент не отправляет сессии, поэтому если вы начинаете с нуля, начните отсюда.

## Предварительные требования

1. **Python 3.10+** и кодовая база агента, который вы хотите инструментировать.
2. **SDK.** Он распространяется клиентам как частное колесо, а не из общедоступного индекса — ваша адаптация охватывает, как его получить и установить. Skill знает путь установки и спросит вас, а не будет угадывать, если не может его найти.
3. **Ничего больше.** Без входа на панель мониторинга, без API ключа, без сети. Skill проверяет наличие файлов событий, которые пишет SDK, поэтому может завершить и доказать свою работу в автономном режиме.

## Где это получить

Skill находится в общедоступной коллекции [`FailproofAI/skills`](https://github.com/FailproofAI/skills):

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

Добавьте `-g` для установки во всех проектах вместо только текущего, и `--copy` если ваша среда не следует символическим ссылкам. Для Codex передайте `-a codex`.

## Установка вручную

Agent Skills — это папки, содержащие `SKILL.md` плюс ссылки. Если вы предпочитаете не использовать установщик:

- **Claude Code**: скопируйте папку `agenteye-python-sdk/` в `~/.claude/skills/` (для каждого проекта) или `<your-repo>/.claude/skills/` (только для этого репозитория). Claude Code обнаруживает её автоматически — проверьте список `/skills` или просто спросите что-то, что ей соответствует.
- **Codex**: Codex читает один и тот же `SKILL.md`. Bundled `agents/openai.yaml` устанавливает `allow_implicit_invocation: true`, поэтому он автоматически выбирается при совпадении задачи; в противном случае вызовите его как `$agenteye-python-sdk`.

Запустите вашего агента **в репозитории, содержащем код, который вы хотите инструментировать** — skill читает ваш цикл агента перед тем, как что-либо предложить.

## Как выглядит сессия

```text
вы   ▸ Добавь Failproof AI Observability к этому агенту.

агент ▸ Прочитал ваш цикл — один диспетчер инструментов в tools.py, один
        обработчик Anthropic в llm.py. Два вопроса перед тем, как я
        напишу что-либо.

        Что считается одним запуском? Вы обрабатываете запросы
        параллельно, поэтому я использовал бы идентификатор запроса,
        который у вас уже есть в ctx.request_id — тогда сессия здесь
        и запрос в ваших логах — это одна и та же строка.

        И кто действующие лица? Я вижу путь планировщика и путь
        исследователя. Пометить их отдельно или это один агент для вас?

вы   ▸ Идентификатор запроса правильный. Это один агент, назови его
        «assistant».

агент ▸ Готово. Обёрнул диспетчер и LLM клиент; agent_start и agent_end
        охватывают handle_request, включая путь ошибки. Использовал
        context-local для идентичности — ваш диспетчер запускает
        инструменты в пуле потоков, и более простой подход смешал бы
        параллельные запуски в одну сессию без жалоб.

        Проверил на реальном запуске: 11 событий в 4 файлах — agent_start,
        model_request/response, tool_use/tool_result x3, agent_end
        (outcome=success). environment=production, одна сессия на запрос,
        длительности спарены.

        Одно, что я НЕ сделал: ваш пул рабочих в batch.py отправляет
        прямо в executor, поэтому события оттуда были бы отброшены.
        Хотите, чтобы я это исправил?
```

Шаблон, на который следует обратить внимание: он прочитал код перед предложением, задал только вопросы, на которые вы можете ответить, переиспользовал идентификатор, который у вас уже был, выбрал форму, безопасную для параллелизма, *потому что* увидел пул потоков, и **проверил путём чтения фактических событий** вместо объявления успеха — затем обозначил одно место, где он знал, что произойдёт молчаливо.

## Что вы можете у него попросить

- *«Почему мой агент не показывается на панели мониторинга?»* → проходит лестницу: записываются ли события, есть ли `agent_start`, правильно ли окружение, читает ли коллектор то же место.
- *«Всё попадает под dev.»* → окружение никогда не было установлено или было сброшено позже.
- *«Добавь отслеживание токенов.»* → находит вашу оболочку LLM и записывает модель, причину остановки и использование.
- *«Инструментируй и суб-агентов.»* → одна сессия, различные метки агента, вложены в их родителя.
- *«Напиши тесты для инструментирования.»* → указывает SDK на временный каталог и утверждает события, которые он написал.

## На что обратить внимание

**Позвольте ему проверить.** Шаг, который делает этот skill стоящим использования, — это последний — запуск вашего агента и чтение событий обратно. Агент, который пишет инструментирование и останавливается, сделал лёгкую половину, и половина, которая не срабатывает молча, — другая.

**Согласуйте имена перед кодом.** `session_id` и `agent_id` — это оси, по которым группирует каждая поверхность. Переименование их позже разбивает историю: старые запуски сохраняют старые метки и ваши тренды ломаются. Skill спросит; ответ стоит минуты размышления.

**Если ваш агент предлагает установить SDK из общедоступного индекса, skill не загрузился.** SDK распространяется приватно. Это предложение — надёжный признак того, что ваш кодирующий агент угадывает, а не следует skill'у — остановите его там и проверьте, установлен ли skill.

Помимо этого его радиус поражения небольшой: он пишет код в вашем рабочем каталоге и файлы событий где вы скажете. Он ничего не читает из вашего развёртывания и ничего в нём не меняет.
