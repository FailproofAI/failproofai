Оповещение отслеживает измеримое условие и открывает задачу при его срабатывании. Используйте его, когда сбой требует своевременного ответа, независимо от того, может ли политика его заблокировать.

## Создание и тестирование оповещения

<Tabs>
  <Tab title="Dashboard">
    1. Перейдите в **Analyze → Alerts** и выберите **new alert**. Вы также можете начать с колокольчика на типовой ошибке.
    2. Введите имя, серьёзность, тип триггера, условие, интервал оценки, количество нарушений, окно и каналы.
    3. Сохраните оповещение, откройте его страницу деталей и выполните **test**.
    4. Перейдите в **Analyze → Issues**, чтобы подтвердить, назначить, обсудить, подписаться на и разрешить задачи, открываемые оповещением.

    Первая часть формы определяет оповещение и сигнал, который должен его вызвать.

    ![Первая часть формы new-alert с именем, описанием, состоянием включения и типом триггера.](/images/dashboard/alert-new-trigger.png)

    Вторая часть контролирует, как долго должно сохраняться условие, как часто оно оценивается и куда отправляются уведомления.

    ![Вторая часть формы new-alert с логикой нарушений, расписанием, серьёзностью, каналами доставки и действием создания.](/images/dashboard/alert-new-routing.png)

    После сохранения используйте список Alerts, чтобы убедиться, что правило включено и что его триггер, окно, серьёзность и каналы соответствуют вашим намерениям. Карточка с открытыми задачами показывает их количество; карточка без них полностью пропускает строку, поэтому её отсутствие ничего не говорит. Чтобы увидеть цифру для каждого правила, включая нули, используйте `fp alerts show <name>`, который всегда её выведет.

    ![Страница Alerts, показывающая правила оповещений с их триггерами, окнами оценки, каналами и серьёзностью.](/images/dashboard/alerts.png)

  <Tab title="CLI">
    ```bash
    fp alerts create high-errors \
      --trigger-kind metric_threshold \
      --severity warning \
      --trigger-spec '{"metric":"error_count","op":">","value":50,"window_secs":900}' \
      --eval-interval-secs 300 \
      --min-breaches 2 \
      --eval-window 3

    fp alerts show high-errors
    fp alerts test high-errors
    fp alerts update high-errors --severity critical --yes
    ```

    Новые оповещения запускаются в режиме **enabled**, и коллизия имён отклоняется до создания чего-либо.

    `fp alerts update` заменяет всё определение на сервере, поэтому CLI перечитывает оповещение и применяет ваши флаги поверх — обновление только через флаги требует `alerts:read` **а также** `alerts:write`, и система запрашивает подтверждение, если вы не передадите `--yes`.

    Используйте `fp alerts list` для проверки правил и `fp alerts delete <name>` для удаления. Удаление показывает предпросмотр правила — включая количество открытых задач — и запрашивает подтверждение перед действием, так как это невозможно отменить.

    Удаление — не способ заглушить надоедливое правило. `DELETE /alerts/{id}` каскадно удаляет все задачи, когда-либо открытые оповещением, вместе с их комментариями, подписками и историей активности. Подтверждение CLI формулирует это как открытые задачи, находящиеся в состоянии „orphaned"; контракт API — это каскадное удаление, поэтому считайте историю потерянной. Чтобы остановить срабатывание правила и сохранить записанное, отключите его вместо этого — форма оповещения на dashboard имеет переключатель enabled, и ни `fp alerts create`, ни `fp alerts update` не предоставляют флаг `--enabled`, поэтому маршрут через CLI — это `fp alerts update <name> --file` с полным определением, содержащим `enabled: false`.

    Полный набор команд alert см. в [справке `fp alerts`](/ru/reference/cloud-cli#alerts).
  </Tab>
</Tabs>

<Warning>
  **test** доставляет реальные уведомления. Оно отправляется на реальные каналы email, Slack и webhook оповещения и открывает синтетическую задачу, поэтому может уведомить того, кто находится на дежурстве. Система запрашивает подтверждение на интерактивном терминале; `--yes`, `--json` и перенаправленный stdin пропускают это приглашение. Сервер также сообщает об успехе, как только отправит сообщение, поэтому успешный тест доказывает, что сообщение ушло, но не то, что оно пришло.
</Warning>

## Определение триггера

Существует пять типов триггеров:

| `--trigger-kind` | Срабатывает когда |
| --- | --- |
| `metric_threshold` | Метрика переходит через пороговое значение — ошибки, задержка, затраты или всё, что можно измерить. |
| `per_event` | Приходит одно совпадающее событие. |
| `evaluation_score` | Оценка оценивающего переходит через пороговое значение. |
| `eval_compound` | Несколько условий оценки объединяются, например две из трёх оценок не прошли. |
| `custom_sql` | Запрос, который вы написали, возвращает нарушение. |

Само условие находится в `--trigger-spec`, сформированное для выбранного вами типа.

## Установка значений оценки

Форма dashboard и CLI запрашивают одни и те же четыре значения.

| Параметр | Флаг | Принимаемые значения |
| --- | --- | --- |
| Серьёзность | `--severity` | `info`, `warning`, `critical` |
| Интервал оценки | `--eval-interval-secs` | 30–86 400 секунд |
| Количество нарушений | `--min-breaches` | Минимум 1, и никогда не больше, чем окно |
| Окно оценки | `--eval-window` | Минимум 1, подсчитано в **интервалах**, не секундах |

Итак, `--eval-interval-secs 300 --min-breaches 2 --eval-window 3` означает „оценивать каждые пять минут и срабатывать, когда два из последних трёх оцениваний дали нарушение".

## Правильный дизайн оповещений

- Назовите условие и затронутый рабочий процесс.
- Явно укажите окружение.
- Установите окно и пороговое значение, которые избегают реакции на одно безобидное событие.
- Включите ссылку или запрос, который приведёт ответственных к сеансам.
- Назначьте владельца перед включением правила.
- Проверьте `fp alerts show <name>` для количества открытых задач перед добавлением другого правила для того же симптома. Карточка dashboard печатает эту строку только когда количество ненулевое.
