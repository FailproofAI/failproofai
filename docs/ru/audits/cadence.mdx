Используйте повторяющиеся аудиты для режимов отказа, которые могут появиться снова по мере изменения агентов, подсказок, инструментов и моделей.

## Изменение расписания

<Tabs>
  <Tab title="Dashboard">
    1. Перейдите в **Analyze → Audits** и откройте аудит.
    2. Выберите **edit settings** и измените расписание, окно, чувствительность или количество результатов за запуск.
    3. Сохраните аудит и подтвердите время следующего запуска в заголовке аудита.
    4. Приостановите и возобновите расписание из того же заголовка рядом с **run now**.
    5. Используйте **run now** один раз после большого изменения области действия или контекста.

    ![Заголовок аудита, показывающий его статус паузы, открытые результаты, время последнего запуска, время следующего запуска, окно проверки и чувствительность с элементами управления run now, edit settings и resume.](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits edit checkout-reliability \
      --schedule-interval-secs 86400 \
      --schedule-anchor 2026-08-15T09:00:00Z \
      --window-mode since_last \
      --lookback-window-secs 86400 \
      --yes

    fp audits edit checkout-reliability --disabled --yes
    fp audits edit checkout-reliability --enabled --yes
    ```

    `fp audits edit` запрашивает подтверждение перед любыми изменениями, поэтому все примеры здесь используют `--yes`. Сервер заменяет всё определение при каждом редактировании, поэтому CLI переотправляет текущий аудит с применёнными изменениями — редактирование только флагов требует `audits:read` **и** `audits:write`. Установите область действия CI-ключа для обоих.

    См. [справочник `fp audits`](/ru/reference/cloud-cli#audits) для границ расписания, поведения окна и всех команд аудита.
  </Tab>
</Tabs>

## Две границы расписания

Каждая рекомендация ниже должна поместиться внутри этих пределов. Диапазоны установлены сервером, и `fp` их дублирует на стороне клиента, поэтому значение вне диапазона завершается с кодом 2 локально, а не приводит к ошибке 422 при обращении.

| Поле | Флаг | Диапазон | По умолчанию |
| --- | --- | --- | --- |
| Интервал расписания | `--schedule-interval-secs` | 3 600–604 800 секунд (1 час до 7 дней) | 86 400 (ежедневно) |
| Окно поиска в истории | `--lookback-window-secs` | 3 600–7 776 000 секунд (1 час до 90 дней) | 604 800 (7 дней) |

Семь дней — это верхний предел расписания. Ежемесячного аудита Cloud не существует.

## Выбор расписания

Выберите исходя из скорости и стоимости риска:

| Модель риска | Начальное расписание |
| --- | --- |
| Высокоударное действие в production | Ежедневно или ежечасно во время внедрения рискованного изменения |
| Регрессия рабочего процесса или модели | Еженедельно |
| Проверка управления или доступа | Еженедельно — максимальный доступный интервал |

Согласуйте окно поиска в истории с расписанием, чтобы запуски не оставляли пропусков и не проверяли повторно ненужно большую совокупность.

Нет одноразового аудита; каждый аудит имеет интервал расписания. Для исследования выпуска создайте его включённым, дайте первому запуску сработать — первый запуск ставится в очередь немедленно при создании, независимо от якоря — затем приостановите его с помощью `fp audits edit <name> --disabled --yes`. Включите снова перед использованием **run now**: отключённый аудит не имеет строки в очереди, и попытка ручного запуска на нём отклоняется с ошибкой 409.

## Режим окна и якорь

`--window-mode` определяет, какое окно сканирует каждый запуск:

| Режим | Поведение |
| --- | --- |
| `since_last` | Продолжить с конца последнего полностью проанализированного окна, поэтому пропущенный запуск не оставляет пропусков. |
| `fixed` | Переосмотреть скользящий `lookback_window_secs` при каждом запуске, независимо от того, что покрывал последний запуск. |

`--schedule-anchor` фиксирует фазу, а не частоту: запуски происходят на `anchor + N × interval`. Опустите его, и якорь по умолчанию установится на следующие 09:00 UTC; якорь более чем на 365 дней в будущем отклоняется. Изменение интервала или якоря вступает в силу при следующем переписании расписания, а не на уже поставленном в очередь запуске, и отказавший запуск не смещает якорь.

После изменения цели или контекста аудита запустите его вручную один раз, прежде чем полагаться на следующий запланированный результат.

<Note>
  Эта страница об аудитах Cloud, которые работают с сессиями Cloud. Локальный аудит имеет свой таймер: `failproofai audit --schedule [days]` принимает 1–90 дней и по умолчанию 7, сканирует историю агента на одной машине и единственный интерфейс с ежемесячной опцией. Его результаты и права собственности отделены от всего описанного выше — см. [Audit local agent history](/ru/audits/local-audit).
</Note>
