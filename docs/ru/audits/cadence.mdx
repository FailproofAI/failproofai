Используйте повторяющиеся аудиты для сценариев сбоев, которые могут появиться снова при изменении агентов, промптов, инструментов и моделей.

## Изменение расписания

<Tabs>
  <Tab title="Dashboard">
    1. Перейдите в **Analyze → Audits** и откройте аудит.
    2. Откройте его параметры и измените состояние включения, интервал, якорь UTC, режим окна или глубину истории.
    3. Сохраните аудит и подтвердите время следующего запуска на карточке аудита.
    4. Используйте **run now** один раз после значительного изменения области или контекста.

    ![Редактор аудита, показывающий частоту, окно сканирования, область, параметры анализа, контекст и каналы уведомлений.](/images/dashboard/audit-edit.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits edit checkout-reliability \
      --schedule-interval-secs 86400 \
      --schedule-anchor 2026-08-15T09:00:00Z \
      --lookback-window-secs 86400 \
      --yes

    fp audits edit checkout-reliability --disabled --yes
    fp audits edit checkout-reliability --enabled --yes
    ```

    См. [справку `fp audits`](/ru/reference/cloud-cli#audits) для получения информации об ограничениях расписания, поведении окна и всех командах аудита.
  </Tab>
</Tabs>

Выберите частоту в зависимости от скорости и стоимости риска:

| Сценарий риска | Начальная частота |
| --- | --- |
| Критичное действие в production | Ежедневно |
| Регрессия рабочего процесса или модели | Еженедельно |
| Проверка управления или доступа | Ежемесячно |
| Разовое исследование релиза | Выполнить один раз |

Согласуйте глубину истории с частотой так, чтобы запуски не оставляли пробелов и не повторно проверяли ненужно большую совокупность данных. После изменения цели или контекста аудита запустите её вручную один раз перед тем, как полагаться на следующий запланированный результат.

<Note>
  Локальные запланированные аудиты настраиваются на машине и сканируют локальную историю агента. Расписания облачных аудитов работают с облачными сеансами. Рассматривайте их результаты и владение отдельно.
</Note>
