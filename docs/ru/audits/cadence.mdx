Используйте повторяющиеся аудиты для режимов отказа, которые могут возникать снова при изменении агентов, промптов, инструментов и моделей.

## Изменение расписания

<Tabs>
  <Tab title="Dashboard">
    1. Перейдите в **Analyze → Audits** и откройте аудит.
    2. Откройте его параметры и измените статус включения, интервал, якорь UTC, режим окна или глубину истории.
    3. Сохраните аудит и проверьте время следующего запуска на карточке аудита.
    4. Используйте **run now** один раз после значительного изменения области или контекста.

    ![Редактор аудита со строкой, окном развертывания, областью, параметрами анализа, контекстом и каналами уведомлений.](/images/dashboard/audit-edit.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits edit checkout-reliability \
      --schedule-interval-secs 86400 \
      --schedule-anchor 2026-08-15T09:00:00Z \
      --lookback-window-secs 86400 \
      --yes

    fp audits edit checkout-reliability --disabled --yes
    fp audits edit checkout-reliability --enabled --yes
    ```

    Смотрите [`fp audits` справочник](/ru/reference/cloud-cli#audits) для границ расписания, поведения окна и всех команд аудита.
  </Tab>
</Tabs>

Выберите частоту на основе скорости и стоимости риска:

| Шаблон риска | Начальная частота |
| --- | --- |
| Высокоприоритетное действие в production | Ежедневно |
| Регрессия workflow или модели | Еженедельно |
| Проверка управления или доступа | Ежемесячно |
| Одноразовое расследование выпуска | Запустить один раз |

Согласуйте окно глубины истории с частотой так, чтобы запуски не оставляли пробелов и не проверяли повторно ненужно большую совокупность. После изменения цели или контекста аудита запустите её вручную один раз перед тем, как полагаться на следующий запланированный результат.

<Note>
  Локально запланированные аудиты настраиваются на машине и проверяют локальную историю агента. Расписания облачного аудита работают с облачными сеансами. Рассматривайте их результаты и ответственность отдельно.
</Note>
