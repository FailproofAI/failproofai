Вывод — это подкреплённое доказательствами утверждение аудита о сбое. Проблема — это долгосрочный рабочий процесс для реагирования на него.

Эти два объекта используют разные словари и расположены рядом, поэтому стоит сначала различать их:

| | Вывод | Проблема |
| --- | --- | --- |
| Состояния | `open`, `recurring`, `resolved`, `dismissed`, `muted` | `firing`, `acknowledged`, `resolved` |
| Флаг фильтра | `--status` | `--state` |
| Идентификатор | Finding id | Issue id |
| Список по умолчанию | Текущий набор: открытые и повторяющиеся | Новейшие открытые в первую очередь |

## Сортировка и назначение работ

<Tabs>
  <Tab title="Dashboard">
    1. Откройте **Analyze → Audits**, выберите завершённый прогон и выберите вывод для проверки его анализа, рекомендаций, сеансов и запросов доказательств.
    2. Подтвердите, назначьте, отклоните, отключите, разрешите или переоткройте вывод после проверки его доказательств.
    3. Перейдите в **Analyze → Issues** и отфильтруйте долгосрочный входящий список по состоянию, серьёзности или ответственному.
    4. Откройте проблему для назначения, добавления комментариев или подписчиков, и разрешите её после проверки исправления.

    Начните с сводки по выводу. Подтвердите, что описание сбоя, рекомендуемый ответ, серьёзность и рейтинг совпадают с сеансами, которые вы ожидали проверить при аудите.

    Затем откройте затронутый сеанс вместо того, чтобы решать только на основе сводки. Связанная трассировка должна показать точное событие и полезную нагрузку, поддерживающие вывод.

    После проверки доказательств используйте Issues, чтобы назначить ответственного и отслеживать это независимо от будущих прогонов аудита.

    Откройте проблему для записи заметок расследования, уведомления подписчиков и сохранения истории ответов. Разрешите её только после развёртывания и проверки исправления.

  <Tab title="CLI">
    ```bash
    fp audits findings --audit checkout-reliability --status open
    fp audits finding <finding-id>
    fp audits ack <finding-id> --reason "owner assigned"
    fp audits assign <finding-id> --to engineer@example.com
    fp audits mute <finding-id> --reason "expected in staging" --yes
    fp audits dismiss <finding-id> --reason "false positive" --yes
    fp audits resolve <finding-id> --yes
    fp audits reopen <finding-id>

    fp issues list --state firing
    fp issues show <issue-id>
    fp issues ack <issue-id>
    fp issues assign <issue-id> --assignee engineer@example.com
    fp issues comment-add <issue-id> --body "policy is in observe mode"
    fp issues resolve <issue-id> --yes
    ```

    `mute`, `dismiss` и `resolve` подавляют или закрывают вывод, поэтому каждый подтверждает в первую очередь — передавайте `--yes` в скриптах. `ack`, `reopen` и `assign` — обратимая работа по ведению записей и выполняются немедленно. `ack`, `mute` и `dismiss` принимают `--reason`, и стоит передавать: оно сохраняется как долгосрочная обратная связь по выводу, а не записывается в журнал и забывается. `resolve`, `reopen` и `assign` не требуют причины.

    Назначение работает по-разному для каждого объекта. `fp audits assign` требует `--to <email>` и устанавливает одного владельца; повторный запуск переназначает. `fp issues assign` принимает повторяемый `--assignee` и **заменяет** весь список, поэтому его пропуск очищает всех назначенных.

    Используйте `fp issues comment-list <issue-id>`, `fp issues count --state firing` и `fp issues subscribe`/`unsubscribe`/`subscribers <issue-id>` для остальной части поверхности проблемы.

    См. [справку по Cloud CLI для аудита и проблем](/ru/reference/cloud-cli#audits) для выводов аудита и [`fp issues`](/ru/reference/cloud-cli#issues) для управления проблемами.

## Проверка вывода

Два поля определяют, что с ним делать, прежде всего.

**`kind`** разделяет `failure` (что-то пошло не так) от нарушения `policy` (правило, которое было нарушено) и `improvement` (работа может быть выполнена лучше). Оно отображается как значок на выводе. Вывод `policy` — это то, который может закрыть политика; два других обычно требуют изменения рабочего процесса, оповещения или участия человека.

**`priority`** — это оценка 0–1, пересчитываемая для каждого прогона, и это порядок, в котором отсортирована очередь выводов. Страница выводов разбивает её под **почему она так рейтингуется** как значение × вес:

| Фактор | Вес |
| --- | --- |
| Охват | 0.30 |
| Серьёзность | 0.25 |
| Масштаб | 0.25 |
| Актуальность | 0.20 |

Затем подтвердите, что вывод содержит:

- Стабильный режим отказа, а не только одноразовое название
- Серьёзность и операционное воздействие
- Затронутые ID сеансов или вспомогательные запросы
- Достаточный контекст для воспроизведения поведения
- Предлагаемый ответ, который соответствует доказательствам

Для воспроизведения вывода получите его целиком: `fp --json audits finding <id>` возвращает полную запись с неизменёнными `evidence`, `evidence_queries` и `scope`, что является тем, что фактически запустил анализ. `--json` — это глобальная опция, поэтому она идёт перед командой.

## Использование проблемы для управления ответом

Создайте или свяжите проблему, когда вывод требует назначения, обсуждения, изменений статуса, комментариев или подписчиков. `source` проблемы записывает, откуда она пришла — `audit`, `alert` или `manual` — именно поэтому панель управления даёт проблемам свой собственный вид **Issues** вместо вложения их под аудит.

Подписка частично автоматическая. Люди подписываются, когда они подтверждают проблему, комментируют её, назначены на неё или открывают её — `fp issues subscribers` перечисляет только активных подписчиков, поэтому это не просто список ручных подписок. Комментарий отправляет по электронной почте каждого активного подписчика, и комментирование требует только `issues:read`, поэтому рецензент только для чтения никогда не является молчаливым наблюдателем.

Разрешите проблему, когда исправление развёрнуто и проверено. Разрешите вывод, когда режим отказа был устранён для популяции аудита. Эти моменты могут отличаться.

## Превращение проблемы в черновик политики

<Tabs>
  <Tab title="Dashboard">
    1. Откройте проблему и проверьте её вывод, цитируемые сеансы, корневую причину и рекомендацию.
    2. Выберите **generate policy** и проверьте результат соответствия и предложенное намерение применения. Результат **no policy** означает, что поведение может потребовать вместо этого оповещение, изменение рабочего процесса или ответ человека.
    3. Выберите **write this policy**, затем проверьте и протестируйте сгенерированный исходный код в **Admin → policy editor** перед выбором **publish version**. Используйте **open the editor anyway** когда вы не согласны с проверкой соответствия.
    4. Перейдите в **Admin → enforcement**, развёртывайте версию в режиме **observe**, и проверьте её решения в **Observe → policy** перед её применением.

    Заголовок проблемы, описание вывода, корневая причина, рекомендация и намерение соответствия помогают составить черновик. Ничто не публикуется и не развёртывается автоматически.
  </Tab>
  <Tab title="CLI">
    Используйте CLI для проверки доказательств перед открытием проблемы на панели управления:

    ```bash
    fp issues show <issue-id>
    fp --json audits finding <finding-id>
    fp events --session-id <session-id> --full --all
    ```

    Панель управления — это один путь; CLI — другой. `fp policies compose "<what it should do>"` создаёт черновик политики, `fp policies publish <id> ./policy.mjs` выпускает версию (публикация не развёртывает ничего), и `fp fleet deploy <machine> --add <id>:observe` размещает её на машине в режиме наблюдения. Суффикс `:observe` требуется — голый `--add <id>` применяет немедленно. Прочитайте, что это сделало бы, с `fp guardrails summary --since 24h`, затем продвигайте с `--add <id>:enforce`.

    Чтобы сначала попробовать эквивалентный исходный код политики на собственной машине, укажите локальный CLI на файл:

    ```bash
    failproofai policies -i -c ./checkout-policies.js
    ```

    Файл, имя которого заканчивается на `policies.js`, `policies.mjs` или `policies.ts`, помещённый в `.failproofai/policies/` в проекте или в `~/`, загружается при каждом событии хука без каких-либо флагов вообще.
  </Tab>
</Tabs>
