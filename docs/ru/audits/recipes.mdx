Используйте эти рецепты как начальные цели, затем добавьте своего агента, окружение и ожидаемый рабочий процесс.

<Tabs>
  <Tab title="Dashboard">
    Перейдите в **Analyze → Audits → New audit**. Строка рецепта на этой странице — это **description** (описание) — то, что вы ожидаете поймать этим аудитом. Правила рабочего процесса, которые делают цель оценяемой, идут в **your brief** (ваш брифинг), в карте **what it knows** (что оно знает): информация, которую модель прочитает перед тем, как посмотреть на одно событие, ограничена 8192 символами, добавляется к тому, что аудит уже ищет. Брифинг никогда не заменяет цель и никогда не является доказательством для вывода.

    Затем установите область в **what it reads** (что оно читает), потому что половина этих рецептов — это просто шум без правильной области. Окружение и агенты сужают генеральную совокупность; **errors to ignore** (ошибки для игнорирования) содержит типы ошибок, которые вы ожидаете и обрабатываете по проекту, так что они перестают считаться отказами. Она принимает только названия типов ошибок, и именно она предотвращает переполнение рецепта повторных циклов.

    Форма нового аудита превращает рецепт в проверяемый отказ, добавляя область, контекст, частоту и уведомления.

    ![Форма нового аудита, настроенная с сосредоточенной целью, расписанием, областью агента и окружения, контекстом и каналами уведомлений.](/images/dashboard/audit-new.png)

    После создания подтвердите, что аудит появляется в списке с ожидаемым статусом и расписанием, прежде чем полагаться на периодические запуски.

    Откройте первый запуск и уточните рецепт, если его выводы шире или уже, чем предполагаемый режим отказа.
  </Tab>
  <Tab title="CLI">
    Сохраните рецепт как текстовый файл и прикрепите его при создании:

    ```bash
    fp audits create retry-loop-review \
      --description "Find agents that repeat a failing tool call without changing anything" \
      --scope '{"environments":["production"]}' \
      --ignore-error-type RateLimitRetried \
      --text-file ./retry-loop-audit.txt \
      --schedule-interval-secs 86400
    ```

    `--text` и `--text-file` — это два способа отправить один брифинг; передайте один, а не оба. Добавьте справочные страницы с помощью `--url`, до пяти, только публичные `https://`. Отправьте всё это с запросом создания: новый включённый аудит должен быть выполнен сразу, поэтому контекст, написанный во втором вызове, может быть пропущен при первом запуске.
  </Tab>
</Tabs>

## Оценивайте рецепт, а не просто формулировку

Два параметра влияют на результат больше, чем формулировка. **Sensitivity** (чувствительность) (`low`, `medium`, `high`, по умолчанию `medium`) решает, насколько охотно запуск отмечает паттерн; **findings per run** (`--top-k`, по умолчанию 50) ограничивает, сколько их он сохраняет. Повышайте чувствительность для вопроса, где пропуск стоит больше, чем ложный положительный результат, и снижайте её для паттерна объёма, который иначе переполнил бы очередь. Каждый рецепт ниже указывает начальную точку — меняйте её после прочтения первого запуска, а не до.

Отказ от задачи и пропущенное повышение уровня для человека — это оценки против того, что агент должен был сделать, а не против ошибки, которую он вызвал. Сначала напишите [контекст агента](/ru/audits/agent-contracts) этого агента, иначе анализ не будет иметь стандарта для оценки.

<AccordionGroup>
  <Accordion title="Повторяющиеся циклы повторных попыток">
    Найдите сессии, где агент повторяет один и тот же неудачный вызов инструмента без изменения входных данных, выбора альтернативного инструмента или повышения уровня для человека.

    Начните с `medium` и перечислите типы ошибок, на которые вы намеренно повторяете попытки, в разделе **errors to ignore**.
  </Accordion>
  <Accordion title="Неправильное использование инструмента">
    Найдите сессии, где выбранный инструмент не соответствует указанной задаче, или где входные данные инструмента нарушают необходимые предусловия рабочего процесса.

    Начните с `medium`. Поместите сами предусловия в брифинг; без них анализ не имеет правила для проверки.
  </Accordion>
  <Accordion title="Небезопасный доступ к данным">
    Найдите сессии, которые читают, пишут или передают чувствительные данные вне одобренных путей и сервисов для этого агента.

    Начните с `high`. Пропущенная утечка стоит больше, чем ложный положительный результат, который вы один раз отклоняете.
  </Accordion>
  <Accordion title="Отказ от задачи">
    Найдите сессии, которые заканчиваются без запрошенного результата, явной ошибки или явного передачи человеку.

    Начните с `medium` и сначала напишите раздел **Done when** (готово когда) агента — этот рецепт является оценкой против него.
  </Accordion>
  <Accordion title="Регрессия стоимости или задержки">
    Найдите сессии, чья модель, инструмент или общая продолжительность превышает ожидаемый бюджет, и определите паттерн событий, ответственный за это.

    Начните с `low` и повышайте, если первый запуск скупой. Бюджеты должны быть в брифинге, и любой тип ошибки, который медленный путь вызывает по проекту, должен быть в **errors to ignore**.
  </Accordion>
  <Accordion title="Пропущенное повышение уровня для человека">
    Найдите сессии, где уверенность, повторный отказ или рекомендация политики требовали решения человека, но агент продолжал автономно.

    Начните с `high` и сформулируйте правило повышения уровня в разделе **Must not** (не должен) агента, чтобы анализ оценивал против него.
  </Accordion>
</AccordionGroup>

## Получите первый ответ, прежде чем что-либо создавать

Несколько из этих паттернов уже имеют локальные детекторы в локальном аудите, который читает истории агентов на вашей машине и не требует учётной записи:

| Детектор | Паттерн, который он считает |
| --- | --- |
| `sleep-polling-loop` | Длинный `sleep` или цикл опроса `while … sleep … done` |
| `reread-after-edit` | Чтение файла, который агент только что отредактировал или написал |
| `find-from-root` | `find` для `/` или другой каталог верхнего уровня |
| `redundant-cd-cwd` | `cd` в каталог, где оболочка уже находится |
| `prefer-edit-over-read-cat` | `cat`, `head`, `tail`, `less` или `more` для одного исходного файла |
| `prefer-edit-over-sed-awk` | Редактирование на месте через `sed -i` или `awk … > file` |
| `prefer-write-over-heredoc` | Многострочное содержимое, написанное через heredoc или `echo > file` |
| `git-commit-no-verify` | `git commit --no-verify`, пропуск перехватчиков |

Эти детекторы считают; они не блокируют, и ни один из них не измеряет стоимость или задержку. Запустите `failproofai audit`, чтобы увидеть, какие расточительные и рискованные паттерны shell ваши агенты уже производят, прежде чем вы платите за облачный аудит того же диапазона — см. [Audit local agent history](/ru/audits/local-audit).
