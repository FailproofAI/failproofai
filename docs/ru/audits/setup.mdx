Качество аудита начинается с его масштаба. Широкий запрос вроде «найти проблемы» дает менее полезные результаты, чем конкретный вопрос о сбое.

## Настройка аудита

<Tabs>
  <Tab title="Dashboard">
    1. Перейдите в **Analyze → Audits → New audit** и введите имя и описание.
    2. Установите периодичность, временное окно, область агентов/окружения, игнорируемые ошибки, чувствительность и максимальное количество находок.
    3. В разделе **agents** добавьте или рассмотрите контекст агента, затем добавьте брифинг оператора и любые публичные HTTPS ссылки.
    4. Выберите каналы уведомлений и нажмите **create audit**. Первый запуск будет поставлен в очередь немедленно.

    ![Форма нового аудита с именем, описанием, периодичностью, окном, областью окружения и агентов, игнорируемыми ошибками, настройками анализа, брифингом, справочными страницами и каналами уведомлений.](/images/dashboard/audit-new.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits create checkout-reliability \
      --description "Find checkout failures that agents do not recover from" \
      --scope '{"environments":["production"],"agent_ids":["checkout-agent"]}' \
      --schedule-interval-secs 86400 \
      --window-mode since_last \
      --sensitivity medium \
      --text-file ./checkout-audit-brief.txt \
      --url https://runbooks.example.com/checkout
    ```

    Первый запуск будет поставлен в очередь немедленно. Включите брифинг и справочные URL при создании, чтобы запуск их получил.

    Смотрите полный справочник [`fp audits create`](/ru/reference/cloud-cli#audits).
  </Tab>
</Tabs>

<Tip>
  Начните с известной неудачной сессии и несколькими нормальными сессиями. Это дает аудиту как положительный пример, так и набор для сравнения.
</Tip>

<Info>
  Контекст аудита хранится как отдельный ресурс, поэтому редактирование аудита не приведет к случайному удалению справочного материала.
</Info>
