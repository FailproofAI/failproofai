failproofai поставляется с 39 встроенными политиками, которые перехватывают распространённые режимы отказа агентов. Каждая политика срабатывает на определённый тип события хука и имя инструмента. Девятнадцать политик принимают параметры, которые позволяют настроить их поведение без написания кода. Пять политик рабочего процесса обеспечивают выполнение конвейера commit → push → PR → CI перед остановкой Claude.

---

## Обзор

Политики сгруппированы по категориям:

| Категория | Политики | Тип хука |
|----------|----------|-----------|
| [Опасные команды](#опасные-команды) | block-sudo, block-rm-rf, block-curl-pipe-sh, block-failproofai-commands, block-self-pause | PreToolUse |
| [Команды инфраструктуры](#команды-инфраструктуры) | block-kubectl, block-terraform, block-aws-cli, block-gcloud, block-az-cli, block-helm, block-gh-pipeline | PreToolUse |
| [Секреты (санитайзеры)](#секреты-санитайзеры) | sanitize-jwt, sanitize-api-keys, sanitize-connection-strings, sanitize-private-key-content, sanitize-bearer-tokens | PostToolUse |
| [Окружение](#окружение) | block-env-files, protect-env-vars | PreToolUse |
| [Доступ к файлам](#доступ-к-файлам) | block-read-outside-cwd, block-secrets-write | PreToolUse |
| [Git](#git) | block-push-master, block-work-on-main, block-force-push, warn-git-amend, warn-git-stash-drop, warn-all-files-staged | PreToolUse |
| [База данных](#база-данных) | warn-destructive-sql, warn-schema-alteration | PreToolUse |
| [Предупреждения](#предупреждения) | warn-large-file-write, warn-package-publish, warn-background-process, warn-global-package-install | PreToolUse |
| [Менеджеры пакетов](#менеджеры-пакетов) | prefer-package-manager | PreToolUse |
| [Рабочий процесс](#рабочий-процесс) | require-commit-before-stop, require-push-before-stop, require-pr-before-stop, require-no-conflicts-before-stop, require-ci-green-before-stop | Stop |

- **`block-`** — остановить агента и не позволить ему продолжать.
- **`warn-`** — предоставить агенту дополнительный контекст для самокоррекции.
- **`sanitize-`** — удалить чувствительные данные из вывода инструмента перед тем, как агент их увидит.

### Пространства имён

Каждая политика находится в слоте `<namespace>/<name>`. Встроенные политики принадлежат пространству имён **`failproofai/`** — например, `failproofai/sanitize-jwt`. Пространство имён предотвращает конфликты при загрузке пользовательских или сторонних политик с похожими короткими именами.

В конфигурации вы можете ссылаться на встроенную политику либо по её короткому имени, либо по полному имени; обе формы разрешаются в одну политику:

```json
{
  "enabledPolicies": [
    "sanitize-jwt",
    "failproofai/block-rm-rf"
  ]
}
```

Если имя не содержит `/`, failproofai рассматривает его как принадлежащее пространству имён по умолчанию `failproofai`. Имена, которые уже содержат `/` (например, `myorg/foo`, `custom/my-hook`), сохраняются как есть.
- **`require-`** — заблокировать событие Stop, пока условия не будут выполнены.

---

<Tip>
Каждая политика поддерживает необязательное поле `hint` в `policyParams`. Подсказка добавляется к сообщению о блокировке или инструкции, которые видит Claude, предоставляя практические рекомендации без изменения кода политики. Работает со встроенными, пользовательскими и convention-политиками. Подробнее см. [Конфигурация → hint](/ru/configuration#hint-cross-cutting).
</Tip>

## Опасные команды

Предотвратить попытки агентов выполнять операции, которые сложно отменить или которые могут повредить хост-систему.

### `block-sudo`

**Событие:** PreToolUse (Bash)  
**По умолчанию:** Блокирует любую команду `sudo` или `doas`.

Блокирует команду, которая запускает бинарный файл повышения привилегий **в позиции команды**. Сопоставление структурное, а не текстовое: команда разбивается на сегменты так, как это делает оболочка, обходятся присваивания префиксов (`FOO=bar`), перенаправления и программы-оболочки с их флагами (`env`, `nohup`, `timeout`, `xargs`, `sh -c`, …), а полученный бинарный файл сравнивается по **базовому имени**. Таким образом, `/usr/bin/sudo`, `env sudo`, `timeout 5 sudo`, `"sudo"`, `\sudo` и `bash -c "sudo …"` все блокируются, а `doas` рассматривается как та же способность под другим именем.

Поскольку сопоставление привязано к позиции команды, а не к появлению слова в любом месте, она **не** срабатывает на команды, которые его просто упоминают — `grep -r sudo /etc`, `cat /etc/sudoers`, `git commit -m "fix sudo handling"` или `grep` с чередованием, содержащим слово, выполняются нормально.

<Warning>
Это останавливает очевидную попытку; это не закрывает весь класс атак. Агент, который может запускать произвольную оболочку, может всё ещё достичь повышения привилегий косвенно — через переменную (`S=sudo; $S …`), base64-декодированный конвейер или скрипт-обёртку на диске — потому что никакая проверка одной строки команды не может следить за ними. Рассматривайте это как защиту от ошибок и случайного повышения привилегий, а не как границу безопасности против целенаправленного агента. Реальная граница должна быть обеспечена ниже уровня оболочки.
</Warning>

**Параметры:**

| Параметр | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `allowPatterns` | `string[]` | `[]` | Точные префиксы команд, которые разрешены. Каждая запись сопоставляется с распарсенными токенами argv. |

**Пример:**

```json
{
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    }
  }
}
```

С этой конфигурацией `sudo systemctl status nginx` разрешено, но `sudo rm /etc/hosts` блокируется.

<Note>
Паттерны сопоставляются с распарсенными токенами, а не с исходной строкой команды. Это предотвращает обход с помощью добавленных операторов оболочки (например, `sudo systemctl status x; rm -rf /` не соответствует `sudo systemctl status *`).
</Note>

### `block-self-pause`

**Событие:** PreToolUse (Bash)  
**По умолчанию:** Блокирует `failproofai config --pause`, которая приостанавливает применение политик на сессию. Пауза — это решение человека — агент, который может её выполнить, может отключить все остальные политики одной командой.

Уже по назначению более узкая, чем [`block-failproofai-commands`](#block-failproofai-commands) и не охватывается ею: эта политика привязана к границе команды, поэтому `npx -y failproofai config --pause` не соответствует ей, и будучи широкой она часто отключается, чтобы агенты могли запускать `failproofai audit`. `--resume` и `--status` разрешены — ни один не удаляет применение политик.

Это останавливает прямую попытку, не весь класс: агент может всё ещё достичь того же состояния через псевдоним или скрипт-обёртку. Полное закрытие требует, чтобы пауза была полностью недоступна из вызова инструмента.

Нет параметров.

## Команды инфраструктуры

Остановить кодирующих агентов от запуска инфраструктурных CLI или запуска конвейеров CI/CD. Все политики в этой категории **опциональны** (`defaultEnabled: false`) — агенты, которые законно должны вызывать `kubectl`, `terraform` и т.д., не будут нарушены, если вы не включите политику. Когда включена, каждый вызов сопоставленного CLI блокируется, если команда не соответствует записи в `allowPatterns`.

Грамматика паттернов совпадает с [`block-sudo`](#block-sudo): токены сопоставляются с распарсенными argv, `*` — это подстановочный знак для одного токена, и любая команда, содержащая отдельный оператор оболочки (`&&`, `||`, `|`, `;`) или токен с встроенными метасимволами оболочки, отклоняется перед сопоставлением со списком разрешения, чтобы предотвратить обход через инъекцию.

### `block-kubectl`

**Событие:** PreToolUse (Bash)  
**По умолчанию:** Блокирует любой вызов `kubectl`.

**Параметры:**

| Параметр | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `allowPatterns` | `string[]` | `[]` | Префиксы команд kubectl, которые разрешены. |

**Пример:**

```json
{
  "policyParams": {
    "block-kubectl": {
      "allowPatterns": ["kubectl get *", "kubectl describe *", "kubectl logs *"]
    }
  }
}
```

С этой конфигурацией `kubectl get pods` разрешено, но `kubectl apply -f deploy.yaml` блокируется.

### `block-gh-pipeline`

**Событие:** PreToolUse (Bash)  
**По умолчанию:** Блокирует следующие подкоманды CLI `gh`, которые изменяют состояние или запускают конвейеры:

- `gh workflow run`, `gh workflow enable`, `gh workflow disable`
- `gh run rerun`, `gh run cancel`
- `gh pr merge`
- `gh release create`, `gh release delete`
- `gh cache delete`
- `gh secret set`, `gh secret delete`

Подкоманды `gh` только для чтения, такие как `gh pr view`, `gh pr list`, `gh run list`, `gh release view` и `gh api repos/.../...` **не** совпадают с этой политикой — они регулярно требуются для проверок рабочего процесса (включая собственную `require-ci-green-before-stop` failproofai).

**Параметры:**

| Параметр | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `allowPatterns` | `string[]` | `[]` | Специфичные скриптизированные вызовы, разрешенные даже если они в противном случае были бы блокированы. |

**Пример:**

```json
{
  "policyParams": {
    "block-gh-pipeline": {
      "allowPatterns": ["gh run rerun *"]
    }
  }
}
```

## Секреты (санитайзеры)

Остановить агентов от утечки учётных данных в их контекст или вывод. Политики санитайзеров срабатывают на **PostToolUse** событиях. Когда Claude запускает команду Bash, читает файл или вызывает любой инструмент, эти политики проверяют вывод перед его возвратом Claude. Если обнаружен паттерн секрета, политика возвращает решение блокировки, которое предотвращает передачу вывода обратно.

### `sanitize-jwt`

**Событие:** PostToolUse (все инструменты)  
**По умолчанию:** Удаляет JWT токены (три сегмента base64url, разделённые `.`).

Нет параметров.

---

### `sanitize-api-keys`

**Событие:** PostToolUse (все инструменты)  
**По умолчанию:** Удаляет распространённые форматы API ключей: Anthropic (`sk-ant-`), OpenAI (`sk-`), GitHub PATs (`ghp_`), AWS access keys (`AKIA`), Stripe keys (`sk_live_`, `sk_test_`), и Google API keys (`AIza`).

**Параметры:**

| Параметр | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `additionalPatterns` | `{ regex: string; label: string }[]` | `[]` | Дополнительные regex паттерны, которые рассматриваются как секреты. |

**Пример:**

```json
{
  "policyParams": {
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo internal API key" },
        { "regex": "pat_[0-9a-f]{40}", "label": "Internal PAT" }
      ]
    }
  }
}
```

---

### `sanitize-connection-strings`

**Событие:** PostToolUse (все инструменты)  
**По умолчанию:** Удаляет строки подключения к базам данных, которые содержат встроенные учётные данные (например, `postgresql://user:password@host/db`).

Нет параметров.

---

### `sanitize-private-key-content`

**Событие:** PostToolUse (все инструменты)  
**По умолчанию:** Удаляет PEM блоки (`-----BEGIN PRIVATE KEY-----`, `-----BEGIN RSA PRIVATE KEY-----` и т.д.).

Нет параметров.

---

### `sanitize-bearer-tokens`

**Событие:** PostToolUse (все инструменты)  
**По умолчанию:** Удаляет `Authorization: Bearer <token>` заголовки, где токен содержит 20 или более символов.

Нет параметров.

## Окружение

Защитить чувствительную конфигурацию окружения от чтения или раскрытия агентами.

### `block-env-files`

Не блокирует `.envrc` или другие файлы, связанные с окружением — только файлы с именем точно `.env`.

Нет параметров.

## Доступ к файлам

Держать агентов работающими внутри границ проекта и подальше от чувствительных файлов.

### `block-read-outside-cwd`

**Событие:** PreToolUse (Read, Bash)  
**По умолчанию:** Блокирует чтение файлов вне корня проекта. Граница — `CLAUDE_PROJECT_DIR` (устанавливается один раз за сессию Claude Code), с резервным вариантом до текущей рабочей директории сессии, когда эта переменная не установлена. Использование корня проекта вместо живого `cwd` означает, что граница остаётся стабильной даже после того, как Claude выполнит `cd` в подпапку.

**Параметры:**

| Параметр | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `allowPaths` | `string[]` | `[]` | Абсолютные префиксы путей, разрешённые даже если находятся вне корня проекта. |

**Пример:**

```json
{
  "policyParams": {
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company/config"]
    }
  }
}
```

---

### `block-secrets-write`

**Событие:** PreToolUse (Write, Edit)  
**По умолчанию:** Блокирует запись в файлы, которые обычно используются для приватных ключей и сертификатов: `id_rsa`, `id_ed25519`, `*.key`, `*.pem`, `*.p12`, `*.pfx`.

**Параметры:**

| Параметр | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `additionalPatterns` | `string[]` | `[]` | Дополнительные паттерны имён файлов (стиль glob), которые блокировать. |

**Пример:**

```json
{
  "policyParams": {
    "block-secrets-write": {
      "additionalPatterns": [".token", ".secret"]
    }
  }
}
```

## Git

Предотвратить случайные отправки, force-push'и и ошибки ветвей, которые сложно отменить.

### `block-push-master`

**Событие:** PreToolUse (Bash)  
**По умолчанию:** Блокирует `git push origin main` и `git push origin master`.

**Параметры:**

| Параметр | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `protectedBranches` | `string[]` | `["main", "master"]` | Имена ветвей, на которые нельзя отправлять напрямую. |

**Пример:**

```json
{
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "master", "release", "prod"]
    }
  }
}
```

<Tip>

## Менеджеры пакетов

Обеспечить, какие менеджеры пакетов разрешены агенту.

### `prefer-package-manager`

**Событие:** PreToolUse (Bash)  
**По умолчанию:** Отключено. Когда включено, блокирует любую команду менеджера пакетов, которая не в списке `allowed`, и говорит Claude переписать команду, используя разрешённый менеджер.

Обнаруживает: pip, pip3, python -m pip, npm, npx, yarn, pnpm, pnpx, bun, bunx, uv, poetry, pipenv, conda, cargo.

| Параметр | Тип | По умолчанию | Описание |
|-----------|------|---------|-------------|
| `allowed` | string[] | `[]` | Разрешённые имена менеджеров пакетов. Любой обнаруженный менеджер, не входящий в этот список, блокируется. Когда пусто, политика — это no-op. |
| `blocked` | string[] | `[]` | Дополнительные имена менеджеров для блокировки помимо встроенного списка (например, `['pdm', 'pipx']`). |

Встроенный список блокировки охватывает: pip, pip3, npm, npx, yarn, pnpm, pnpx, bun, bunx, uv, poetry, pipenv, conda, cargo. Используйте `blocked` для добавления менеджеров, не входящих в этот список.

**Пример конфигурации:**

```json
{
  "enabledPolicies": ["prefer-package-manager"],
  "policyParams": {
    "prefer-package-manager": {
      "allowed": ["uv", "bun"],
      "blocked": ["pdm", "pipx"]
    }
  }
}
```

С этой конфигурацией `pip install flask` и `pdm install flask` оба блокируются с сообщением, говорящим Claude использовать `uv` или `bun` вместо этого. Команды как `uv pip install flask` разрешены, потому что `uv` в списке разрешений и проверяется первым.

## Рабочий процесс

Обеспечить дисциплинированный конец сессии рабочий процесс. Эти политики срабатывают на события **Stop** и блокируют агента от остановки, пока каждое условие не будет выполнено. Они следуют естественной цепочке зависимостей: commit → push → PR → CI. Если политика блокирует, более поздние политики в цепочке пропускаются (блокировка шорт-циркуитит).

Все политики рабочего процесса — **fail-open**: если требуемый инструмент недоступен (например, `gh` не установлен, нет git remoteт), политика позволяет с информационным сообщением, объясняющим, почему проверка была пропущена.

### Per-CLI Stop семантика

Применение Stop выглядит немного по-другому в шести поддерживаемых CLI, потому что каждый раскрывает другой контракт хука «агент закончил». **Результат** один и тот же — агент не ускользает при остановке, пока ворота рабочего процесса не срабатывают — но **механика** отличается. Таблица ниже содержит краткое резюме; только Pi имеет видимую пользователю особенность, стоящую понимания перед включением политики `require-*-before-stop`.

| CLI | Когда срабатывают ворота | Что вы видите |
|---|---|---|
| Claude Code | Та же петля агента, сразу же | Claude продолжает работать — исправляет проблему, затем пытается закончить снова. Никакого видимого вам прерывания. |
| Codex | Та же петля агента, сразу же | То же, что Claude. |
| GitHub Copilot CLI | Та же петля агента, сразу же | То же, что Claude (использует канал переполнения `{decision:"block", reason}` Copilot — проверено эмпирически против Copilot CLI 1.0.41). |
| Cursor Agent | Та же петля агента, сразу же | То же, что Claude (использует канал `{followup_message}` Cursor — ограничен `loop_limit`, стандарт 5 повторов). |
| OpenCode | Та же петля агента, сразу же | То же, что Claude (использует вызов SDK `client.session.prompt(...)` OpenCode, направленный через `hookSpecificOutput.additionalContext`). |
| **Pi (pi-coding-agent)** | **Следующий ход пользователя** | **Pi видимо останавливается**, когда срабатывают ворота — его петля агента выходит и вам возвращается приглашение. Ворота затем срабатывают в следующий раз, когда вы отправляете приглашение: failproofai добавляет директиву `MANDATORY ACTION REQUIRED` к системному приглашению этого хода, инструктирую LLM завершить шаг рабочего процесса (commit, push и т.д.) перед выполнением того, что вы просили. |

<Note>
**Ограничение Pi.** `AgentEndEvent` Pi (эквивалент upstream `Stop` хука Claude) не имеет типа Result — к тому времени, когда он срабатывает, петля агента Pi уже вышла. Pi не может быть принуждён к повтору той же петли так, как Claude / Copilot / Cursor / OpenCode могут. failproofai переносит ворота на событие `before_agent_start` Pi (которое срабатывает после следующего пользовательского приглашения), поэтому проверка рабочего процесса всё ещё обеспечивается, просто на следующем ходу, а не на текущем.

**Что это значит на практике:**

- После остановки Pi причина блокировки захватывается в памяти по ID сессии Pi. Очень следующее приглашение, которое вы отправляете в том же процессе Pi, сливает его: LLM видит директиву `MANDATORY ACTION REQUIRED` в верхней части своего системного приглашения, коммитит (или отправляет / открывает PR / ожидает CI), и только затем продолжает с вашим запросом. Захваченная причина блокировки — это one-shot — один раз слита, ворота ясны.
- Ворота ограничены сроком жизни процесса Pi. Если вы нажмёте `Ctrl+C` Pi или выйдете между ходами, запись в памяти удаляется вместе с процессом и ворота пропущены. Claude, Copilot, Cursor и OpenCode имеют ту же границу (убейте агента и ворота пропущены) — Pi просто делает это более видимым, потому что агент видимо выходит перед срабатыванием ворот.
- Отложенная блокировка также очищена при `session_shutdown` по любой причине (`new` / `resume` / `fork` / `quit`), поэтому устаревшие ворота из предыдущей сессии не могут утечь в свежую сессию, начатую в том же процессе Pi.

Если вам нужен повтор same-loop стиля Claude, запустите ваши политики `Stop` под любым из пяти других поддерживаемых CLI. Мы отслеживаем Pi upstream для будущего типа Result на `AgentEndEvent`, который позволил бы нам закрыть этот пробел.
</Note>

### `require-no-conflicts-before-stop`

**Событие:** Stop  
**По умолчанию:** Блокирует остановку, когда текущая ветвь не может чистко слиться с базовой ветвью. Политика сначала подтверждает, что есть открытый PR на GitHub для ветви — без одного нет цели слияния для принудительного применения, поэтому вся политика шорт-циркуитит для разрешения. Один раз открытый PR подтверждён, две независимые проверки запускаются:

1. **Локально** — `git merge-tree --write-tree --name-only origin/<baseBranch> HEAD`. При конфликте, сообщение блокировки называет конфликтные файлы, поэтому Claude знает точно, что разрешить.
2. **GitHub** — переиспользует результат `gh pr view --json mergeable,state`, уже выбранный в предпроверке. Ловит конфликты, которые устаревший локальный `origin/<baseBranch>` пропустил бы (например, кто-то приземлил конфликтный PR на `main` после последней выборки). Результат `CONFLICTING` блокирует. Результат `UNKNOWN` также блокирует и инструктирует Claude ждать ~10 секунд и пере-проверить перед попыткой остановки снова — это предотвращает ложные негативы, пока GitHub пересчитывает.

Пропускает полностью (позволяет) когда: `gh` не установлен, PR не существует для ветви, состояние PR не `OPEN` (например, `MERGED`, `CLOSED`), или `gh pr view` возвращает не разбираемый вывод. Также fail-open когда `origin/<baseBranch>` отсутствует локально или когда нет коммитов впереди базы — те слой 1 fall-through всё ещё консультируют кэшированную слияемость PR перед разрешением.

**Параметры:**

| Параметр | Тип | По умолчанию | Описание |
|-------|------|---------|-------------|
| `baseBranch` | `string` | `"main"` | Базовая ветвь для проверки конфликтов. |

<Note>
GitHub CLI (`gh`) требуется для этой политики. Политика использует `gh pr view` для подтверждения
открытого PR перед запуском любой проверки конфликтов — без `gh`, политика
шорт-циркуитит для разрешения. Запустите `gh auth login` с личным токеном доступа, имеющим
область `repo` для доступа для чтения к pull requests.
</Note>

Удалить специфичную политику из `enabledPolicies` в вашей конфигурации, или переключить её в закладке Policies приборной панели.

```json
{
```

Политики, не перечисленные в `enabledPolicies` не запускаются, даже если существуют записи `policyParams` для них.
