<Note>
  **Бета-функция.** Аудит поставляется в виде бета-версии, пока мы собираем ранние отзывы.
  Каталог детекторов и формат отчета могут измениться перед следующим стабильным выпуском.
  Пожалуйста, откройте проблему, если что-то выглядит неправильно.
</Note>

Аудит повторно воспроизводит ваши прошлые транскрипты агента-CLI через механизм политик failproofai и рендерит обмениваемый визуальный отчет на **странице панели управления `/audit`** — архетип агента, оценка от 0 до 100 и ровно какие политики что перехватили.

## Запуск

Три способа — все ведут к одному и тому же отчету `/audit`.

<CodeGroup>

```bash npx (без установки)
npx -y failproofai audit
```

```bash failproofai audit
failproofai audit
```

```bash failproofai (панель управления)
failproofai
```

</CodeGroup>

<CardGroup cols={3}>
  <Card title="Без установки" icon="bolt">
    `npx -y failproofai audit` загружает failproofai, запускает сканирование и открывает панель управления для вас — ничего предварительно устанавливать не нужно.
  </Card>
  <Card title="Из CLI" icon="terminal">

  </Card>
  <Card title="Из панели управления" icon="gauge">

<Tip>
  Запустите `failproofai audit -h` (или `--help`) для справки. Аудит работает **полностью в автономном режиме** — никакого аккаунта или сетевого подключения не требуется — и панель управления продолжает работать до тех пор, пока вы не остановите её с помощью `Ctrl+C`.
</Tip>

Панель управления сканирует прошлые транскрипты агента CLI на этой машине (Claude Code, Codex, Copilot, Cursor, OpenCode, Pi) и сообщает, как часто агент делал то, что failproofai построена для остановки — проверки переменных окружения, форсированные push'и, лишние префиксы `cd <cwd>`, циклы опроса с sleep, повторное чтение только что отредактированных файлов и многое другое.

Для каждого транскрипта каждое событие использования инструмента повторно воспроизводится через 39 встроенных политик **и** через 8 детекторов, специфичных для аудита, которые перехватывают паттерны, еще не охватанные политиками в реальном времени. Счетчики агрегируются по политике/детектору по всем сессиям.

## Что вы получаете

Страница `/audit` — это одноэкранный обмениваемый **постер**, за которым следуют четыре свернутых раздела:

1. **Постер** — идентичность вашего агента с первого взгляда: его **архетип** (один из 8 — `optimist`, `cowboy`, `explorer`, `goldfish`, `paranoid architect`, `precision builder`, `hammer`, `ghost`), его ключевые слова персоны, насколько редкий этот архетип, и **оценка от 0 до 100** с полосой уровня (`S` вплоть до `bottom tier`). Построено для обмена — опубликуйте в X или LinkedIn или загрузите как PNG.
2. **`// strengths`** — что ваш агент уже делает хорошо, как настоящие числа из сканирования (например, clean-tool-call %, `0` попыток push-to-main), показывается только там, где соответствующая политика имеет чистый рекорд.
3. **`// quirks`** — что проскользнуло: таблица рейтинга поведений, которые failproofai перехватила бы — *когда* это последний раз происходило, *что проскользнуло* (и встроенное правило, которое это заблокировало бы), его *серьезность* и как часто это было *видно* (`new` / `recurring` / `N× seen`).
4. **`// how to improve`** — рекомендуемый список исправлений: один ряд на политику с копируемой командой `failproofai policy add <slug>`, плюс кнопка **install all**, которая включает каждую рекомендацию сразу и показывает вашу **прогнозируемую оценку**, если бы вы это сделали.
5. **`// come back better`** — выработайте привычку: установите **напоминание** о повторном аудите по электронной почте (`3d` / `7d` / `14d` / `30d`) или выполните повторный аудит сейчас, и **пригласите друга** выполнить свой собственный аудит (отправлено с failproof.ai, скопировано вам). Напоминания и приглашения требуют входа.

## Плановые аудиты

Если вы запустите **демон failproofaid** (см. [`failproofai config`](/ru/cli/install-policies)),
он может повторно запускать аудит для вас по расписанию и обновлять отчет `/audit` в
фоновом режиме. Он **отключен по умолчанию**, потому что сканирование читает *содержимое*
каждого транскрипта сессии агента на этой машине — ничего не сканируется по таймеру
до тех пор, пока вы это не попросите.

Включите это в `~/.failproofai/config.toml`:

```toml
[audit]
auto = true
interval_days = 7
```

| Ключ | Значение |
|---|---|
| `auto` | `true` включает плановое сканирование. Что-либо еще — отсутствие, `false`, `"yes"` — выключено. |
| `interval_days` | Дни между сканированиями. Ограничено 1–90; `0`, отрицательное или не-число возвращается к `7`. |

- График является **по стенным часам**, поэтому он переживает спящий режим и перезагрузки: ноутбук,
  который был в спящем режиме в момент срока, запускается **один раз** при пробуждении, никогда не накапливается.
- Каждый запуск является отдельным, низкоприоритетным процессом (`nice 19`) — никогда путем демона,
  который остается свободным для ответа на вызовы инструментов.
- Сканирование пропускается, если `failproofai audit` или повторный запуск панели управления уже
  выполняется; оно повторяется вскоре после этого, а не рассматривается как сбой.
- Прогресс записывается в `~/.failproofai/state/audit-schedule.json` (последний запуск,
  следующий срок). Демон владеет этим файлом — измените интервал в `config.toml`.

<Note>
Если вы включили это на машине, установленной старой версией failproofai, запустите
`failproofai config` один раз. Определению сервиса демона нужна одна дополнительная
запись, прежде чем он сможет запустить CLI, и обновление является частью этой команды.
</Note>

## Детекторы, специфичные для аудита

Они обнаруживают паттерны "глупого поведения", не (еще) принудительно применяемые в реальном времени. Они работают только во время аудита и никогда не блокируют вызов инструмента в реальном времени.

| Детектор | Что он подсчитывает |
|---|---|
| `redundant-cd-cwd` | Bash-команды, начинающиеся с `cd <cwd> && …` даже несмотря на то, что команды уже выполняются в `cwd`. |
| `prefer-edit-over-read-cat` | `cat`/`head`/`tail`/`less`/`more` на одном исходном файле — используйте инструмент `Read`. |
| `prefer-edit-over-sed-awk` | `sed -i` / `awk … > file` встроенные правки — используйте инструмент `Edit`. |
| `prefer-write-over-heredoc` | Heredoc / многостроковый `echo > file` для записи файлов — используйте инструмент `Write`. |
| `sleep-polling-loop` | Длительные `sleep N` (≥ 30s) или циклы опроса `while …; sleep …; done`. |
| `find-from-root` | `find /`, `find /home`, `find /usr` и т.д. — ограничьте область до `cwd`. |
| `git-commit-no-verify` | `git commit … --no-verify` / `-n`, пропуск хуков. |
| `reread-after-edit` | `Read` файла, который только что был `Edit`/`Write` в той же сессии. |

## Кэши

- **Кэш по транскрипту** в `~/.failproofai/cache/audit/<sha1>.json`, ключированный `(mtime, size, engineVersion, detectorVersion)` — автоматически инвалидируется при изменении транскрипта или кода политики/детектора. Каждая запись также содержит метаданные временной метки `cachedAt` как **TTL метаданные** (не являются частью ключа кэша); записи старше **7 дней** отклоняются при чтении, чтобы долгоживущие результаты не пережили развивающееся намерение детектора.
- **Кэш всего результата** в `~/.failproofai/audit-dashboard.json` (режим 0600). Позволяет панели управления отрендериться мгновенно при навигации без повторного запуска. Также отклоняется при чтении после **7-дневного TTL** — `/audit` затем переходит в пустое состояние и запрашивает свежий запуск. Нажмите `[ re-audit now ]` в нижней части отчета для обновления — повторный аудит отправляет `noCache: true`, поэтому он обходит кэш по транскрипту и повторно сканирует каждый транскрипт вместо возврата кэшированного результата; запуск транслирует прогресс через липкую верхнюю полосу и заменяет результат на месте при успехе (без перезагрузки страницы; неудачный повторный аудит сохраняет предыдущий отчет).

## Примечания

- **Без мутаций.** Аудит воспроизводится в режиме только для чтения. `warn-repeated-tool-calls` пропускается, потому что его сайдкар для каждой сессии иначе был бы изменен.
- **Политики рабочего процесса пропущены.** Политики `require-*-before-stop` срабатывают только на событиях `Stop` и `execSync` для живого состояния git — они не имеют значимой интерпретации "что бы произошло в 2025", поэтому они не появляются в счетчиках аудита.
- **Пользовательские политики пропущены.** Пользовательские хуки не воспроизводятся (они могли измениться с момента исходной сессии).
