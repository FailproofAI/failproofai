```bash
failproofai migrate --dry-run   # вывести план, ничего не менять
failproofai migrate             # выполнить миграцию
```

Большинство пользователей никогда не вводят эту команду вручную. Она запускается автоматически при первой команде после обновления, а [`failproofai update`](/ru/cli/update) включает её. Используйте её напрямую, если хотите увидеть план перед его выполнением или запустить миграцию отдельно.

## Привязка к структуре, а не к версии

`~/.failproofai/VERSION` хранит номер **структуры** — форму директории, а не версию, которая её создала. Миграции привязаны к этому номеру, что делает большие промежутки дешёвыми:

- Номера npm-версий меняются при каждом релизе, их бывает десятки между двумя структурами.
- Поэтому машина, пропустившая тридцать релизов **без изменения структуры**, выполнит **ноль** миграций, а не тридцать холостых операций.
- А машина, пропустившая несколько структур сразу, выполнит каждый шаг по порядку, каждый шаг знает только свои два конца.

Это важно, потому что npm не может обновить установленный пакет самостоятельно. Машина, стоящая на одной версии месяцами, а затем переходящая на несколько структур сразу — это обычный случай, а не экзотический.

## Пробный запуск

`--dry-run` выводит точную цепь и файлы, которые будут сохранены в первую очередь, но ничего не меняет — ни миграции, ни резервной копии, ни записи в логе:

```
Layout 2 на диске; этот build говорит 3.
Будет выполнено 1 шаг(ов):
  2 → 3  layout 2 → 3: перенести config.toml и credentials.toml в JSON, переместить
         custom-policies/ обратно в policies/, вложить конфиг политик в корень

Эти файлы будут сначала скопированы в ~/.failproofai/migrations/backup-layout2:
  VERSION
  config.toml
  credentials.toml
```

## Что переносится, а что пересчитывается

Каждый путь в домашней директории объявляет, какой тип данных он содержит, и это определяет, может ли миграция его удалить. Правило: **производные и перезагружаемые данные могут быть удалены; всё, что вы вводили, что еще не доставлено, и всё, что идентифицирует машину, переносится.**

| Переносится | Пересчитывается или перезагружается |
|---|---|
| `config.json` — параметры, `daemon.configured`, дополнительные пути захвата | Кэш аудита |
| `credentials.json` — ваша облачная регистрация | Облачные развертывания (перезагружаются и проверяются при следующем опросе) |
| `policies-config.json` — ваш выбор политик и их параметры | Временное состояние демона |
| `policies/` — ваши собственные файлы политик и импортируемые ими вспомогательные модули | |
| `hook-activity/` — журнал решений, который читает панель управления | |
| Недоставленные события, ещё в очереди на загрузку | |
| `cursors/` — контрольные точки сборщика | |
| Бинарник демона в `bin/` | |

<Note>
  Недоставленные события переносятся, а не удаляются, потому что потеря была бы постоянной, а не временной: контрольная точка сборщика уже продвинулась дальше всего, что находится в очереди, поэтому никогда ничего не прочитает этот диапазон транскрипта снова. Миграция также просит демона доставить то, что находится в очереди, как только она завершится, так что обычный результат — что переносить нечего.
</Note>

Ключи, которые *более новая* версия записала в `config.json`, `credentials.json` или `policies-config.json`, также сохраняются, а не удаляются более старым читателем.

## Записи, которые остаются

```
~/.failproofai/migrations/
  applied.json                 одна запись на шаг: структура, CLI, временная метка, длительность, результат
  backup-layout<n>/            копии незаменимых файлов, созданные перед первым шагом
```

`applied.json` отвечает на вопрос «что эта машина на самом деле пережила» — первый вопрос, который стоит задать, если что-то выглядит неправильно после обновления. Прикрепите его к отчёту об ошибке.

Резервная копия намеренно мала, а не полная копия директории: миграция больше не удаляет ничего незаменимого по конструкции, поэтому страховать нужно от *дефекта на шаге*, и эти несколько файлов — это то, где такой дефект нанесёт вред.

## Если шаг не удался

Цепь останавливается там. `VERSION` обновляется только шагом, который завершился, поэтому домашняя директория остаётся отмеченной своей старой структурой, и следующая команда повторит его — домашняя директория никогда не помечается как текущая на основе частичной миграции. Шаг записывается в `applied.json` с `"ok": false`, а резервная копия остаётся в том месте, где она была создана.

## Более новая домашняя директория отклоняется, а не мигрирует

Если `~/.failproofai/` был написан **более новой** версией failproofai, чем та, которую вы запускаете, команда остановится и скажет вам обновиться. Эти данные в порядке и более новый CLI их читает; миграция «вперёд» из них — это то, что не существует, и сброс уничтожит что-то восстанавливаемое.

```
Директория failproofai этой машины была написана более новой версией (layout 4;
этот build говорит 3). Обновитесь вместо миграции:
  npm install -g failproofai@latest
```

Демон применяет то же правило: `failproofaid` отказывается запускаться с структурой, которую он не понимает, вместо того чтобы читать и писать пути, которые переместились.
