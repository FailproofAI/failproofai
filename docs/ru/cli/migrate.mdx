```bash
failproofai migrate --dry-run   # вывести план, ничего не менять
failproofai migrate             # запустить миграцию
```

Большинство пользователей никогда не вводят эту команду вручную. Она запускается автоматически при первой команде после обновления, и [`failproofai update`](/ru/cli/update) её включает. Используйте команду напрямую, когда хотите увидеть план перед выполнением или запустить миграцию отдельно.

## Привязка к структуре, а не к версии

`~/.failproofai/VERSION` хранит номер **структуры** — форму директории, а не релиз, который её создал. Миграции привязаны к этому номеру, что делает длительные промежутки дешёвыми:

- Версии npm меняются при каждом релизе, десятки версий между двумя структурами.
- Поэтому машина, которая пропускает тридцать релизов без **изменения структуры**, запускает **ноль** миграций, а не тридцать холостых операций.
- А машина, которая пропускает сразу несколько структур, запускает каждый шаг по порядку, каждый шаг зная только свои два конца.

Это важно, потому что npm не может обновить установленный пакет самостоятельно. Машина, которая стоит на одной версии месяцами и затем прыгает через несколько структур — это нормальный случай, а не экзотический.

## Пробный запуск

`--dry-run` выводит точную цепь и файлы, которые были бы сохранены в первую очередь, и ничего не меняет — ни миграции, ни резервной копии, ни записи в журнал:

```
На диске структура 2; эта сборка говорит на 3.
Будет запущено 1 шаг(ов):
  2 → 3  структура 2 → 3: перенести config.toml и credentials.toml в JSON, переместить
         custom-policies/ обратно в policies/, вложить конфиг политик в корень

Эти файлы будут скопированы в ~/.failproofai/migrations/backup-layout2 в первую очередь:
  VERSION
  config.toml
  credentials.toml
```

## Что переносится, а что пересоздаётся

Каждый путь в домашней директории объявляет, какие данные он содержит, и это определяет, может ли миграция его отбросить. Правило: **производные и пересоздаваемые можно удалить; всё, что вы ввели, всё, что ещё не доставлено, и всё, что идентифицирует машину, переносится.**

| Переносится | Пересоздаётся или пере-загружается |
|---|---|
| `config.json` — параметры, `daemon.configured`, дополнительные пути захвата | Кэш аудита |
| `credentials.json` — ваша регистрация в облаке | Управляемые облаком развёртывания (пере-загружаются и проверяются при следующей проверке) |
| `policies-config.json` — ваш выбор политик и их параметры | Рабочее состояние демона |
| `policies/` — ваши файлы политик и вспомогательные модули, которые они импортируют | |
| `hook-activity/` — журнал решений, который читает панель управления | |
| Недоставленные события, всё ещё в очереди на загрузку | |
| `cursors/` — маркеры коллектора | |
| Бинарный файл демона в `bin/` | |

<Note>
  Недоставленные события переносятся вместо удаления, потому что потеря была бы
  постоянной, а не просто медленной: маркер коллектора уже продвинулся дальше всего,
  что находится в очереди, поэтому ничто никогда не прочитает этот диапазон
  транскрипта снова. Миграция также просит демон доставить то, что находится
  в очереди, как только он закончит, поэтому обычный результат — что переносить нечего.
</Note>

Ключи, которые *более новая* версия записала в `config.json`, `credentials.json` или `policies-config.json`, также сохраняются, а не удаляются более старым читателем.

## Запись, которую она оставляет

```
~/.failproofai/migrations/
  applied.json                 одна запись за шаг: структура, CLI, время, длительность, результат
  backup-layout<n>/            копии неходящихся файлов, сделанные перед первым шагом
```

`applied.json` — это то, что отвечает на вопрос "через что эта машина действительно прошла" — первый вопрос, который стоит задать, когда что-то выглядит неправильно после обновления. Приложите его к отчёту об ошибке.

Резервная копия намеренно маленькая, а не копия всей директории: миграция больше не удаляет ничего ненужного по замыслу, поэтому то, от чего стоит страховаться — это *дефект в шаге*, и в этих нескольких файлах такой дефект был бы больнее всего.

## Если шаг не удался

Цепь там останавливается. `VERSION` отмечается как завершённый только пройденным шагом, поэтому домашняя директория остаётся помечена старой структурой и следующая команда повторит попытку — директория никогда не помечается как текущая на основе неполной миграции. Шаг записывается в `applied.json` с `"ok": false`, и резервная копия остаётся там, где она была сделана.

## Более новая домашняя директория отказывается мигрировать

Если `~/.failproofai/` была написана **более новым** failproofai, чем тот, который вы запускаете, команда остановится и скажет вам обновиться вместо этого. Эти данные в порядке и более новый CLI их читает; миграция «вперёд» из них — это не то, что существует, и их сброс уничтожит что-то восстанавливаемое.

```
Директория failproofai этой машины была написана более новой версией (структура 4;
эта сборка говорит на 3). Обновитесь вместо миграции:
  npm install -g failproofai@latest
```

Демон применяет то же правило: `failproofaid` отказывается запускаться против структуры, которую он не понимает, вместо того чтобы читать и писать пути, которые переместились.
