failproofai использует JSON-файлы конфигурации для управления активными политиками, их поведением и местом загрузки пользовательских политик. Конфигурация разработана для удобного обмена в команде — зафиксируйте её в репозитории, и каждый разработчик получит одинаковую защиту агента.

---

## Уровни конфигурации

Существует три уровня конфигурации, оцениваемые по приоритету:

| Уровень | Путь файла | Назначение |
|---------|-----------|-----------|
| **project** | `.failproofai/policies-config.json` | Параметры репозитория, фиксируются в системе контроля версий |
| **local** | `.failproofai/policies-config.local.json` | Личные переопределения для репозитория, в .gitignore |
| **global** | `~/.failproofai/policies-config.json` | Параметры пользователя по умолчанию для всех проектов |

Когда failproofai получает событие хука, он загружает и объединяет все три файла, которые существуют в текущем рабочем каталоге.

### Правила слияния

**`enabledPolicies`** — объединение всех трёх уровней. Политика, включённая на любом уровне, активна.

```text
project:  ["block-sudo"]
local:    ["block-rm-rf"]
global:   ["block-sudo", "sanitize-api-keys"]

resolved: ["block-sudo", "block-rm-rf", "sanitize-api-keys"]  ← дедупликация
```

**`policyParams`** — первый уровень, определивший параметры для политики, побеждает полностью. Глубокое слияние значений внутри параметров политики не происходит.

```text
project:  block-sudo → { allowPatterns: ["sudo apt-get update"] }
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo apt-get update"] }   ← project побеждает, global игнорируется
```

```text
project:  (нет записи block-sudo)
local:    (нет записи block-sudo)
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo systemctl status"] }  ← переходит к global
```

**`customPoliciesPaths` / `customPoliciesPath`** — первый уровень, определивший одну из форм, побеждает.

**`disabledCustomPolicies`** — объединение всех уровней. Панель управления записывает сюда
квалифицированный идентификатор источника, когда вы отключаете отдельную политику из
явного или конвенционного файла политик. Политики, не указанные в списке, остаются активными
по умолчанию; идентификаторы включают источник, поэтому политики с одинаковыми названиями в
нескольких файлах можно контролировать независимо.

**`llm`** — первый уровень, определивший это значение, побеждает.

## Формат файла конфигурации

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "sanitize-jwt",
    "block-env-files",
    "block-read-outside-cwd"
  ],
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release", "prod"]
    },
    "block-rm-rf": {
      "allowPaths": ["/tmp"]
    },
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company"]
    },
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo API key" }
      ]
    },
    "warn-large-file-write": {
      "thresholdKb": 512
    }
  },
  "customPoliciesPath": "/home/alice/myproject/my-policies.js"
}
```

## Справочник полей

### `enabledPolicies`

Тип: `string[]`

Список имён политик для включения. Имена должны точно соответствовать идентификаторам политик, показанным командой `failproofai policies`. Полный список см. в разделе [Встроенные политики](/ru/built-in-policies).

Политики, не входящие в `enabledPolicies`, неактивны, даже если имеют записи в `policyParams`.

### `policyParams`

Тип: `Record<string, Record<string, unknown>>`

Переопределение параметров для каждой политики. Внешний ключ — имя политики; внутренние ключи специфичны для политики. Каждая политика документирует свои доступные параметры в разделе [Встроенные политики](/ru/built-in-policies).

Если политика имеет параметры, но вы их не указываете, используются встроенные значения по умолчанию политики. Пользователи, которые не настраивают `policyParams` вообще, получают поведение, идентичное предыдущим версиям.

Неизвестные ключи внутри блока параметров политики молча игнорируются при срабатывании хука, но помечаются как предупреждения при запуске `failproofai policies`.

#### `hint` (сквозной)

Тип: `string` (опционально)

Сообщение, добавляемое к причине, когда политика возвращает `deny` или `instruct`. Используйте его, чтобы дать Claude практические рекомендации без изменения самой политики.

Работает с любым типом политики — встроенной, пользовательской (`custom/`), конвенцией проекта (`.failproofai-project/`) или конвенцией пользователя (`.failproofai-user/`).

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "Попробуйте создать новую ветку вместо этого."
    },
    "block-sudo": {
      "allowPatterns": ["sudo apt-get"],
      "hint": "Используйте apt-get напрямую без sudo."
    },
    "custom/my-policy": {
      "hint": "Сначала запросите одобрение у пользователя."
    }
  }
}
```

Когда `block-force-push` блокирует, Claude видит: *"Force-push запрещён. Попробуйте создать новую ветку вместо этого."*

Значения, не являющиеся строками, и пустые строки молча игнорируются. Если `hint` не установлен, поведение не меняется (обратная совместимость).

### `customPoliciesPath`

Тип: `string` (абсолютный путь)

Путь к JavaScript-файлу, содержащему пользовательские политики хука. Устанавливается автоматически командой `failproofai policies --install --custom <path>` (путь преобразуется в абсолютный перед сохранением).

Файл загружается заново при каждом событии хука — кеширования нет. Подробности написания см. в разделе [Пользовательские политики](/ru/custom-policies).

### Политики на основе конвенций

В дополнение к явному `customPoliciesPath`, failproofai автоматически обнаруживает и загружает файлы политик из директорий `.failproofai/policies/`:

| Уровень | Директория | Уровень конфигурации |
|---------|-----------|-----------|
| Проект | `.failproofai/policies/` | Общие с командой через систему контроля версий |
| Пользователь | `~/.failproofai/policies/custom-policies/` | Личные, применяются ко всем проектам |

<Note>
  Директория уровня пользователя переместилась на уровень ниже при реорганизации
  домашней директории. Файлы, оставленные в старой `~/.failproofai/policies/`,
  автоматически перемещаются в `custom-policies/` при первом запуске любой команды
  failproofai после обновления, и команда сообщит вам, какие файлы были перемещены.
</Note>

**Сопоставление файлов:** загружаются только файлы, соответствующие маске `*policies.{js,mjs,ts}` (например, `security-policies.mjs`, `workflow-policies.js`). Остальные файлы в директории игнорируются.

**Не требует конфигурации:** политики на основе конвенций не нуждаются в записях в `policies-config.json`. Просто поместите файлы в директорию, и они будут загружены при следующем событии хука.

**Объединённая загрузка:** сканируются обе директории конвенций — проекта и пользователя. Все соответствующие файлы с обоих уровней загружаются (в отличие от `customPoliciesPath`, который использует правило первого уровня).

Подробности и примеры см. в разделе [Пользовательские политики](/ru/custom-policies).

### `llm`

Тип: `object` (опционально)

Конфигурация LLM-клиента для политик, выполняющих вызовы AI. Не требуется для большинства настроек.

```json
{
  "llm": {
    "model": "claude-sonnet-4-6",
    "apiKey": "sk-ant-..."
  }
}
```

## Управление конфигурацией из CLI

Команды `policies --install` и `policies --uninstall` записывают в файл параметров хука вашего CLI агента (точки входа хука), а `policies-config.json` — это файл, который вы управляете напрямую. Они отделены друг от друга:

- **Параметры CLI агента** — указывает агенту вызывать `failproofai --hook <event>` при каждом использовании инструмента:
  - **Claude Code**: `~/.claude/settings.json` (пользователь), `<cwd>/.claude/settings.json` (проект), `<cwd>/.claude/settings.local.json` (локально)
  - **OpenAI Codex**: `~/.codex/hooks.json` (пользователь), `<cwd>/.codex/hooks.json` (проект) — Codex не имеет локального уровня
  - **GitHub Copilot CLI _(beta)_**: `~/.copilot/hooks/failproofai.json` (пользователь), `<cwd>/.github/hooks/failproofai.json` (проект) — Copilot не имеет локального уровня. Записи хука используют поля команд `bash`/`powershell` Copilot с учётом ОС с `timeoutSec`; файл содержит маркер `version: 1` верхнего уровня. Поддержка Copilot CLI находится в статусе **beta** во время проверки схемы записи `events.jsonl` (которая не указана в общедоступной документации) по сравнению с большим количеством реальных сессий. **VS Code Copilot Chat режим агента (Preview)** читает конфиги хуков из `.github/hooks/*.json`, `~/.copilot/hooks/*.json` и `~/.claude/settings.json` (управляется параметром `chat.hookFilesLocations`) с использованием того же контракта, сформированного Claude `{hookSpecificOutput:{permissionDecision:"deny",…}}` — точные пути, которые интеграция `copilot` и интеграция `claude` (`~/.claude/settings.json`) уже записывают, поэтому `failproofai policies --install --cli copilot` (или `--cli claude`) **уже применяет в режиме агента VS Code** без отдельной интеграции `vscode` (подтверждено в реальном времени из журналов обнаружения VS Code).
  - **Cursor Agent _(beta)_**: `~/.cursor/hooks.json` (пользователь), `<cwd>/.cursor/hooks.json` (проект) — Cursor не имеет локального уровня. Записи хука используют форму, сформированную Claude `{type, command, timeout}` (без разделения `bash`/`powershell`), но сохраняются с ключами camelCase событий (`preToolUse`, `beforeSubmitPrompt`, …) в плоском массиве согласно [схеме хуков](https://cursor.com/docs/hooks) Cursor; файл содержит маркер `version: 1` верхнего уровня. Обработчик канонизирует camelCase → PascalCase через `CURSOR_EVENT_MAP`, поэтому встроенные политики работают без изменений. Поддержка Cursor Agent находится в статусе **beta** во время проверки формата записи сеансов Cursor на диске (не указан в общедоступной документации) по сравнению с большим количеством реальных установок.
  - **OpenCode _(beta)_**: `~/.config/opencode/opencode.json` + `~/.config/opencode/plugins/failproofai.mjs` (пользователь), `<cwd>/.opencode/opencode.json` + `<cwd>/.opencode/plugins/failproofai.mjs` (проект) — OpenCode не имеет локального уровня. В отличие от остальных пяти CLI, OpenCode **не имеет системы внешних хуков**: он загружает подключаемые модули JS/TS в процесс, явно зарегистрированные через массив `plugin: []` в `opencode.json` (автоматическое обнаружение из `.opencode/plugins/` **не** работает для загрузки подключаемых модулей в opencode v1.14.33). Install вкладывает небольшой сгенерированный адаптер подключаемого модуля, который вызывает двоичный файл failproofai через подпроцесс и преобразует ответ JSON двоичного файла в формате Claude обратно в семантику подключаемого модуля: `throw new Error()` для отказа в событии инструмента (отменяет вызов инструмента), `client.session.prompt(...)` для инструкции И для отказа `Stop` / `SubagentStop` (отправляет причину отказа как следующее сообщение пользователя — единственный канал повторной попытки, поскольку `session.idle` — только уведомление и выброс из него не работает) и нет-оп для allow. Адаптер канонизирует как имена инструментов (lowercase → PascalCase через `OPENCODE_TOOL_MAP`), так и ключи аргументов входных инструментов (camelCase → snake_case через `OPENCODE_TOOL_INPUT_MAP` для `Read` / `Write` / `Edit`, например `filePath` → `file_path`, `oldString` → `old_string`) перед отправкой в двоичный файл, поэтому встроенные проверки путей, такие как `block-read-outside-cwd`, `block-env-files` и `block-secrets-write`, работают без изменений на вызовах инструментов OpenCode. Сеансы находятся в базе данных SQLite OpenCode по адресу `~/.local/share/opencode/opencode.db`; средство просмотра сеансов панели управления читает их через `opencode db --format json` и `opencode export <id>`. Поддержка OpenCode находится в статусе **beta** во время проверки поведения во всех версиях и по сравнению с большим количеством реальных сеансов. См. [документацию подключаемых модулей OpenCode](https://opencode.ai/docs/plugins/).
  - **Pi _(beta)_**: `~/.pi/agent/settings.json` (пользователь), `<cwd>/.pi/settings.json` (проект) — Pi не имеет локального уровня. Pi загружает пакеты расширений TypeScript при запуске; файл параметров — это плоский массив строк `{"packages": ["./relative/path", …]}`. failproofai записывает одну запись packages-array, указывающую на свою встроенную директорию `pi-extension/`. Расширение внутренне подписывается на события `tool_call` / `user_bash` / `input` / `session_start` Pi и вызывает `failproofai --hook <Event> --cli pi`; обработчик канонизирует underscore_lower_snake_case → PascalCase через `PI_EVENT_MAP`, поэтому встроенные политики работают без изменений. Аргументы входных инструментов также канонизируются через `PI_TOOL_INPUT_MAP` (Pi's Read / Write / Edit доставляют `path` вместо `file_path`; отображение верхнего ключа позволяет `block-env-files` и `block-secrets-write` работать — `block-read-outside-cwd` уже имел запасной `path`). Поддержка Pi находится в статусе **beta** при стабилизации API расширений Pi и формата журналов сеансов.
  - **Hermes (hermes-agent)**: `~/.hermes/config.yaml` (**только пользовательский уровень** — Hermes не имеет конфига проекта/локального). Hermes — это **шлюз** Slack/Telegram, поэтому одна установка перехватывает вызовы инструментов с каждой платформы (Slack/Telegram/cli/cron) **и** внутренних подагентов. Записи хука — это пара `{command, timeout}` (timeout в **секундах**) под картой `hooks:` с ключами событий Hermes в snake_case (`pre_tool_call` / `post_tool_call` / `on_session_start` / `on_session_end` / `subagent_stop`); обработчик канонизирует события через `HERMES_EVENT_MAP` и имена инструментов через `HERMES_TOOL_MAP`, поэтому встроенные политики работают без изменений. Конфиг редактируется через комментарий-сохраняющий раунд YAML `Document`, поэтому остальные параметры оператора сохраняются, и install устанавливает `hooks_auto_accept: true`, поэтому безголовой шлюз (без TTY) запускает хуки без приглашения согласия. Оценщик выдаёт контракт stdout Hermes `{"decision":"block","reason"}` (Hermes игнорирует коды выхода). **Ограничения:** Hermes не имеет события `Stop` в конце хода, поэтому встроенные `require-*-before-stop` никогда не срабатывают для него (неприменимо, не нарушено); `instruct` деградирует до allow-with-logged-note (без канала дополнительного контекста); и редакция секретов вывода (`sanitize-*`) не может переписать вывод инструмента через контракт shell-hook. Hermes — **также** автономный источник **аудита** — панель управления читает сеансы шлюза напрямую из `~/.hermes/state.db`.
  - **OpenClaw (openclaw gateway)**: `~/.openclaw/openclaw.json` (**только пользовательский уровень** — OpenClaw не имеет конфига проекта/локального). Как Hermes, OpenClaw — это самостоятельно размещённый многоканальный **шлюз**, поэтому одна установка перехватывает вызовы инструментов с каждого канала и его внутренних подагентов. Применение происходит через **встроенные хуки плагинов** OpenClaw (его файловые внутренние хуки только для наблюдения и не могут блокировать), поэтому — как OpenCode/Pi — failproofai поставляется статическим пакетом `openclaw-plugin/`, который асинхронно порождает двоичный файл failproofai и переводит вердикт. Install регистрирует поставленную директорию плагинов в `openclaw.json`'s `plugins.load.paths[]` и включает её под `plugins.entries.failproofai` (с `hooks.allowConversationAccess: true`, требуется для сырых хуков конверсации). Оценщик выдаёт плоский вердикт `{permission, reason}` и адаптер отображает его в каждую встроенную форму возврата хука: `before_tool_call → {block:true, blockReason}` (**PreToolUse**), `before_agent_run → {outcome:"block", reason}` (**UserPromptSubmit**), и `before_agent_finalize → {action:"revise", reason}` (**Stop** — настоящий запрос в конце хода, поэтому встроенные **enforce** `require-*-before-stop` на OpenClaw, в отличие от Hermes). События и имена инструментов канонизируются двоичной стороной через `OPENCLAW_EVENT_MAP` / `OPENCLAW_TOOL_MAP` (`exec→Bash`, `read→Read`, …), поэтому встроенные политики работают без изменений; адаптер откатывает открытие на любую ошибку spawn/parse/timeout. OpenClaw — **также** автономный источник **аудита** — панель управления читает её сеансы JSONL по адресу `~/.openclaw/agents/<agentId>/sessions/<uuid>.jsonl`.
  - **Factory Droid (`droid`)**: `~/.factory/hooks.json` (пользователь), `<cwd>/.factory/hooks.json` (проект) — Factory не имеет локального уровня. droid поставляется с системой внешних хуков, сформированной по Claude, но с двумя странностями, проверенными в реальном времени на droid v0.171.0: (1) имена событий находятся на **верхнем уровне** `hooks.json` — **нет `"hooks"` обёртки** (droid её отклоняет); события инструментов (`PreToolUse`/`PostToolUse`) содержат `"matcher": "*"`, события, не являющиеся инструментами, его опускают. (2) Отказ управляется **кодом выхода хука 2 + stderr**, а не решением JSON — ветвь `factory` оценщика возвращает выход 2 для событий инструмента/подсказки и `{decision:"block", reason}` только на событии `Stop` в конце хода (единственный канал принудительного повтора droid). События уже PascalCase (нет карты событий), и полезная нагрузка — snake_case Claude; только имена инструментов канонизируются через `FACTORY_TOOL_MAP` (`Execute→Bash`, `Create→Write`, `FetchUrl→WebFetch`, …). Factory — **также** автономный источник **аудита** — панель управления читает её сеансы JSONL на диске по адресу `~/.factory/sessions/<encoded-cwd>/<sessionId>.jsonl`.
  - **Devin CLI (`devin`, Cognition)**: `~/.config/devin/config.json` (пользователь), `<cwd>/.devin/config.json` (проект) — Devin не имеет локального уровня. Devin — это **чистый Claude-клон**, проверенный в реальном времени на devin v3000.1.27: он использует стандартную схему Claude с `"hooks"`-обёрткой (запись с сохранением слияния, поэтому остальные ключи файла конфига — `org_id`, `theme_mode`, … — сохраняются), уже PascalCase имена событий (нет карты событий, нет ветви обработчика) и полезную нагрузку stdin Claude snake_case (нет нормализации). Ветвь `devin` оценщика отказывает с JSON `{"decision":"block","reason"}` на stdout при выходе 0 для **каждого** события (проверено — отказ переопределил `--permission-mode dangerous`); на событии `Stop` в конце хода причина содержит текст ОБЯЗАТЕЛЬНОГО ДЕЙСТВИЯ для принудительного повтора, поэтому встроенные `require-*-before-stop` применяются. Только имена инструментов канонизируются через `DEVIN_TOOL_MAP` (`exec→Bash`; `tool_input.command` уже канонический). Devin — **также** автономный источник **аудита** — панель управления читает его сеансы SQLite по адресу `~/.local/share/devin/cli/sessions.db` (каждая строка `sessions` содержит реальный `working_directory`, поэтому сеансы группируются по проекту cwd, как Claude).
  - **Antigravity CLI (`agy`)**: `~/.gemini/config/hooks.json` (пользователь), `<cwd>/.agents/hooks.json` (проект) — Antigravity не имеет локального уровня. В отличие от Factory/Devin, Antigravity имеет свой **контракт** (не Claude-клон), проверенный в реальном времени на agy v1.1.2. `hooks.json` использует **схему именованных хуков**: верхний ключ — имя хука (*"failproofai"*), значение которого — карта событий→обработчиков — события инструментов (`PreToolUse`/`PostToolUse`) обёртывают обработчики в `{matcher:"*", hooks:[…]}`, а `PreInvocation`/`Stop` — **плоские** массивы обработчиков (другие именованные хуки сохраняются). Полезная нагрузка stdin — **camelCase protojson** (`toolCall:{name,args}`, `conversationId`, `workspacePaths`, `transcriptPath`) — failproofai нормализует её в snake_case перед запуском политик и отображает аргументы PascalCase `run_command` через `ANTIGRAVITY_TOOL_INPUT_MAP`. Ветвь `antigravity` оценщика использует собственные формы ответов Antigravity: `{decision:"deny", reason}` блокирует инструмент/подсказку (выход 0), `{decision:"continue", reason}` на событии `Stop` в конце хода повторно входит в цикл (поэтому встроенные `require-*-before-stop` применяются) и `{injectSteps:[{ephemeralMessage}]}` внедряет инструкцию на `PreInvocation` (→ `UserPromptSubmit`). Имена инструментов канонизируются через `ANTIGRAVITY_TOOL_MAP` (`run_command→Bash`, `view_file→Read`, …). Antigravity — **также** автономный источник **аудита** — панель управления читает её простые JSONL стенограммы по адресу `~/.gemini/antigravity-cli/brain/<conversationId>/.system_generated/logs/transcript_full.jsonl` (индекс конверсации в `conversation_summaries.db`).
  - **Goose (codename goose, Block)**: `~/.agents/plugins/failproofai/hooks/hooks.json` (пользователь), `<cwd>/.agents/plugins/failproofai/hooks/hooks.json` (проект) — Goose не имеет локального уровня. Применение использует систему **хуков** Goose, спецификацию кроссплатформенных **Open Plugins**: установщик просто вкладывает директорию `failproofai` плагина, и Goose автоматически её обнаруживает при запуске (саморегистрируя в `~/.config/goose/config.yaml`). `hooks.json` использует схему Open Plugins **с** обёрткой `"hooks"` верхнего уровня, и сопоставитель **опускается** на каждом событии — голый `"*"` — это невалидный регекс, который ничего не сопоставляет (проверено в реальном времени на goose v1.43.0). Имена событий уже PascalCase (нет карты событий); полезная нагрузка stdin использует `event`/`working_dir`, которые обработчик нормализует в `hook_event_name`/`cwd`. Ветвь `goose` оценщика отказывает с JSON `{"decision":"block","reason"}` на stdout при выходе 0, соблюдаемая на событии **`PreToolUse`** только (поставлена в goose ≥ v1.37.0) — которое срабатывает для инструмента shell **и внутри делегированных подагентов**, поэтому это единственная достаточная точка отказа; любая другая ошибка хука откатывает **открыто**. Goose **не имеет события `Stop`**, поэтому встроенные `require-*-before-stop` не применяются (как в Hermes). Имена инструментов канонизируются через `GOOSE_TOOL_MAP` (`shell→Bash`, `write→Write`, `todo__todo_write→TodoWrite`, …) и ключи путей через `GOOSE_TOOL_INPUT_MAP` (`path`/`source` → `file_path`). Goose — **также** автономный источник **аудита** — панель управления читает её сеансы SQLite по адресу `~/.local/share/goose/sessions/sessions.db` (каждая строка `sessions` содержит реальный `working_dir`, поэтому сеансы группируются по проекту cwd, как Devin; `--no-session` scratch-сеансы отфильтровываются).
- **`policies-config.json`** — указывает failproofai, какие политики оценивать и с какими параметрами (общее для всех CLI агентов)

Передайте `--cli claude|codex|copilot|cursor|opencode|pi|hermes|openclaw|factory|devin|antigravity|goose` для выбора конкретного агента (разделённые пробелом или повторённые для любого подмножества):

```bash
failproofai policies --install --cli codex --scope project
failproofai policies --install --cli copilot --scope project
failproofai policies --install --cli cursor --scope project
failproofai policies --install --cli opencode --scope project
failproofai policies --install --cli pi --scope project
failproofai policies --install --cli hermes --scope user
failproofai policies --install --cli openclaw --scope user
failproofai policies --install --cli factory --scope project
failproofai policies --install --cli devin --scope project
failproofai policies --install --cli antigravity --scope project
failproofai policies --install --cli goose --scope project
failproofai policies --install --cli claude codex copilot cursor opencode pi hermes openclaw factory devin antigravity goose
```

Когда `--cli` опущен, failproofai обнаруживает, какие CLI агентов установлены (`which claude` / `which codex` / `which copilot` / `which cursor-agent` / `which opencode` / `which pi` / `which hermes` / `which openclaw` / `which droid` / `which devin` / `which agy` / `which goose`):

- **Обнаружен один CLI** — автоматически выбирает этот CLI без подсказки.
- **Несколько CLI обнаружено** в интерактивном терминале — показывает однострочное меню выбора стрелками, сгруппированное в секцию `Detected (N)` (с агрегатной строкой `Install for all N detected` + каждый обнаруженный CLI отдельно) и секцию `Not installed (M) · install hooks ahead of time`, содержащую каждый необнаруженный поддерживаемый CLI в качестве опции опережающей установки (↑↓ для движения, Enter для выбора, ^C для выхода). Поток удаления показывает только секцию Detected.
- **Несколько CLI обнаружено** в неинтерактивном запуске (CI, нет TTY) — устанавливает для всех обнаруженных CLI без подсказки.
- **Ничего не обнаружено** — откатывает к `claude` с предупреждением, что в PATH не найден двоичный файл агента; команда хука по-прежнему записывается, поэтому она активируется как только вы установите один.

Вы можете редактировать `policies-config.json` напрямую в любое время; изменения вступают в силу немедленно при следующем событии хука без необходимости перезагрузки.

## Пример: конфиг уровня проекта с командными параметрами по умолчанию

Зафиксируйте `.failproofai/policies-config.json` в вашем репозитории:

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "block-env-files"
  ],
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "release", "hotfix"]
    }
  }
}
```

Каждый разработчик может затем создать `.failproofai/policies-config.local.json` (в .gitignore) для личных переопределений без влияния на товарищей по команде.
