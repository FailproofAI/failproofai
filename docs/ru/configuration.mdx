failproofai использует JSON файлы конфигурации для управления активными политиками, их поведением и местом загрузки пользовательских политик. Конфигурация разработана так, чтобы её было легко делиться с командой — сохраняйте её в репозитории и каждый разработчик получит одинаковую защиту агента.

---

## Уровни конфигурации

Существует три уровня конфигурации, оцениваемые по приоритету:

| Уровень | Путь файла | Назначение |
|---------|-----------|-----------|
| **project** | `.failproofai/policies-config.json` | Настройки для репозитория, сохраняются в системе контроля версий |
| **local** | `.failproofai/policies-config.local.json` | Личные переопределения для репозитория, исключены из git |
| **global** | `~/.failproofai/policies-config.json` | Пользовательские настройки по умолчанию для всех проектов |

Когда failproofai получает событие хука, он загружает и объединяет все три файла, которые существуют для текущей рабочей директории.

### Правила объединения

**`enabledPolicies`** — объединение всех трёх уровней. Политика, активированная на любом уровне, становится активной.

```text
project:  ["block-sudo"]
local:    ["block-rm-rf"]
global:   ["block-sudo", "sanitize-api-keys"]

resolved: ["block-sudo", "block-rm-rf", "sanitize-api-keys"]  ← дедублицированное объединение
```

**`policyParams`** — первый уровень, который определяет параметры для данной политики, полностью побеждает. Глубокого объединения значений внутри параметров политики не происходит.

```text
project:  block-sudo → { allowPatterns: ["sudo apt-get update"] }
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo apt-get update"] }   ← project побеждает, global игнорируется
```

```text
project:  (нет записи block-sudo)
local:    (нет записи block-sudo)
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo systemctl status"] }  ← передаётся на global
```

**`customPoliciesPaths` / `customPoliciesPath`** — первый уровень, который определяет любую форму, побеждает.

**`disabledCustomPolicies`** — объединение всех уровней. Панель управления записывает сюда квалифицированный по источнику ID при отключении отдельной политики из явного или условного файла политик. Политики, не указанные в списке, остаются включёнными по умолчанию; ID включают исходный файл, поэтому одноимённые политики в нескольких файлах можно контролировать независимо.

**`llm`** — первый уровень, который определяет его, побеждает.

## Формат файла конфигурации

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "sanitize-jwt",
    "block-env-files",
    "block-read-outside-cwd"
  ],
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release", "prod"]
    },
    "block-rm-rf": {
      "allowPaths": ["/tmp"]
    },
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company"]
    },
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo API key" }
      ]
    },
    "warn-large-file-write": {
      "thresholdKb": 512
    }
  },
  "customPoliciesPath": "/home/alice/myproject/my-policies.js"
}
```

## Справочник полей

### `enabledPolicies`

Тип: `string[]`

Список имён политик для активации. Имена должны точно совпадать с идентификаторами политик, показываемыми командой `failproofai policies`. Полный список см. в разделе [Встроенные политики](/ru/built-in-policies).

Политики, отсутствующие в `enabledPolicies`, неактивны, даже если у них есть записи в `policyParams`.

### `policyParams`

Тип: `Record<string, Record<string, unknown>>`

Переопределения параметров для отдельных политик. Внешний ключ — имя политики; внутренние ключи — специфичные для политики. Каждая политика документирует доступные параметры в разделе [Встроенные политики](/ru/built-in-policies).

Если политика имеет параметры, но вы их не указываете, используются встроенные значения по умолчанию. Пользователи, которые вообще не настраивают `policyParams`, получают поведение, идентичное предыдущим версиям.

Неизвестные ключи внутри блока параметров политики молча игнорируются при срабатывании хука, но отмечаются как предупреждения при выполнении `failproofai policies`.

#### `hint` (общее)

Тип: `string` (опционально)

Сообщение, добавляемое к причине, когда политика возвращает `deny` или `instruct`. Используйте его, чтобы дать Claude практические рекомендации без изменения самой политики.

Работает с любым типом политики — встроенной, пользовательской (`custom/`), проектной условной (`.failproofai-project/`) или пользовательской условной (`.failproofai-user/`).

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "Попробуйте создать новую ветку вместо этого."
    },
    "block-sudo": {
      "allowPatterns": ["sudo apt-get"],
      "hint": "Используйте apt-get напрямую без sudo."
    },
    "custom/my-policy": {
      "hint": "Сначала запросите одобрение у пользователя."
    }
  }
}
```

Когда `block-force-push` отклоняет, Claude видит: *«Force-pushing заблокирован. Попробуйте создать новую ветку вместо этого.»*

Нестроковые значения и пустые строки молча игнорируются. Если `hint` не установлен, поведение не меняется (обратная совместимость).

### `customPoliciesPath`

Тип: `string` (абсолютный путь)

Путь к файлу JavaScript, содержащему пользовательские политики хука. Устанавливается автоматически командой `failproofai policies --install --custom <path>` (путь разрешается в абсолютный перед сохранением).

Файл загружается заново при каждом событии хука — кеширования нет. Подробности см. в разделе [Пользовательские политики](/ru/custom-policies).

### Условные политики

В дополнение к явному `customPoliciesPath`, failproofai автоматически обнаруживает и загружает файлы политик из директорий `.failproofai/policies/`:

| Уровень | Директория | Уровень конфигурации |
|---------|-----------|-----------|
| Проект | `.failproofai/policies/` | Общее для команды через систему контроля версий |
| Пользователь | `~/.failproofai/policies/custom-policies/` | Личное, применяется ко всем проектам |

<Note>
  Пользовательская директория переместилась на один уровень вниз при реорганизации директории home. Файлы, оставленные в старом `~/.failproofai/policies/`, автоматически перемещаются в `custom-policies/` при первом запуске любой команды `failproofai` после обновления, и команда сообщит вам, какие файлы были перемещены.
</Note>

**Сопоставление файлов:** загружаются только файлы, соответствующие паттерну `*policies.{js,mjs,ts}` (например, `security-policies.mjs`, `workflow-policies.js`). Остальные файлы в директории игнорируются.

**Конфигурация не требуется:** условные политики не требуют записей в `policies-config.json`. Просто поместите файлы в директорию, и они будут подобраны при следующем событии хука.

**Объединённая загрузка:** сканируются обе директории условных политик проекта и пользователя. Все соответствующие файлы с обоих уровней загружаются (в отличие от `customPoliciesPath`, который использует первый-уровень-побеждает).

Подробности и примеры см. в разделе [Пользовательские политики](/ru/custom-policies).

### `llm`

Тип: `object` (опционально)

Конфигурация LLM клиента для политик, которые выполняют вызовы AI. Не требуется для большинства установок.

```json
{
  "llm": {
    "model": "claude-sonnet-4-6",
    "apiKey": "sk-ant-..."
  }
}
```

## Управление конфигурацией из CLI

Команды `policies --install` и `policies --uninstall` записывают в файл настроек хука вашего агента CLI (точки входа хука), тогда как `policies-config.json` — это файл, который вы управляете напрямую. Это два отдельных файла:

- **Настройки агента CLI** — указывает агенту вызывать `failproofai --hook <event>` при каждом использовании инструмента:
  - **Claude Code**: `~/.claude/settings.json` (пользователь), `<cwd>/.claude/settings.json` (проект), `<cwd>/.claude/settings.local.json` (локаль)
  - **OpenAI Codex**: `~/.codex/hooks.json` (пользователь), `<cwd>/.codex/hooks.json` (проект) — Codex не имеет локального уровня
  - **GitHub Copilot CLI _(beta)_**: `~/.copilot/hooks/failproofai.json` (пользователь), `<cwd>/.github/hooks/failproofai.json` (проект) — Copilot не имеет локального уровня. Записи хука используют поля команд Copilot, зависящие от ОС `bash`/`powershell`, с `timeoutSec`; файл содержит маркер верхнего уровня `version: 1`. Поддержка Copilot CLI находится в **beta** во время проверки схемы записи `events.jsonl` (которую публичные документы не указывают) на более реальных сеансах. **VS Code Copilot Chat agent mode (Preview)** читает конфиги хуков из `.github/hooks/*.json`, `~/.copilot/hooks/*.json` и `~/.claude/settings.json` (управляется параметром `chat.hookFilesLocations`) используя тот же контракт, зависящий от Claude `{hookSpecificOutput:{permissionDecision:"deny",…}}` — ровно те пути, которые эта интеграция `copilot` и интеграция `claude` (`~/.claude/settings.json`) уже записывают, поэтому `failproofai policies --install --cli copilot` (или `--cli claude`) **уже применяются в режиме агента VS Code** без отдельной интеграции `vscode` (подтверждено живым образом из журналов обнаружения VS Code).
  - **Cursor Agent _(beta)_**: `~/.cursor/hooks.json` (пользователь), `<cwd>/.cursor/hooks.json` (проект) — Cursor не имеет локального уровня. Записи хука используют форму `{type, command, timeout}`, зависящую от Claude (без разделения `bash`/`powershell`), но хранятся под ключами camelCase событий (`preToolUse`, `beforeSubmitPrompt`, …) в плоском массиве по [схеме хуков](https://cursor.com/docs/hooks) Cursor; файл содержит маркер верхнего уровня `version: 1`. Обработчик канонизирует camelCase → PascalCase через `CURSOR_EVENT_MAP`, поэтому существующие встроенные политики срабатывают без изменений. Поддержка Cursor Agent находится в **beta** во время проверки формата транскрипта Cursor на диске (не указан в публичной документации) на более реальных установках.
  - **OpenCode _(beta)_**: `~/.config/opencode/opencode.json` + `~/.config/opencode/plugins/failproofai.mjs` (пользователь), `<cwd>/.opencode/opencode.json` + `<cwd>/.opencode/plugins/failproofai.mjs` (проект) — OpenCode не имеет локального уровня. В отличие от пяти других CLI, OpenCode **не имеет системы хуков внешних команд**: он загружает в процессе плагины JS/TS, явно зарегистрированные через массив `plugin: []` в `opencode.json` (автоматическое обнаружение из `.opencode/plugins/` — это **не** способ загрузки плагинов на opencode v1.14.33). Установка создаёт небольшой сгенерированный шим плагина, который вызывает бинарный файл failproofai в подпроцессе и переводит ответ бинарного файла в форме JSON, зависящей от Claude, обратно в семантику плагина: `throw new Error()` для отклонения события инструмента (отменяет вызов инструмента), `client.session.prompt(...)` для instruct И для отклонения `Stop` / `SubagentStop` (отправляет причину отклонения как следующее сообщение пользователя — единственный канал принудительного повтора, так как `session.idle` — только уведомление и выброс из неё — no-op), и no-op для allow. Шим канонизирует как имена инструментов (нижний регистр → PascalCase через `OPENCODE_TOOL_MAP`), так и ключи аргументов входа инструмента (camelCase → snake_case через `OPENCODE_TOOL_INPUT_MAP` для `Read` / `Write` / `Edit`, например `filePath` → `file_path`, `oldString` → `old_string`) перед отправкой бинарному файлу, поэтому встроенные проверки путей, такие как `block-read-outside-cwd`, `block-env-files` и `block-secrets-write`, срабатывают без изменений на вызовах инструментов OpenCode. Сеансы живут в SQLite БД OpenCode на `~/.local/share/opencode/opencode.db`; средство просмотра сеансов панели управления читает их через `opencode db --format json` и `opencode export <id>`. Поддержка OpenCode находится в **beta** во время проверки поведения на разных версиях и на более реальных сеансах. См. [документацию плагинов OpenCode](https://opencode.ai/docs/plugins/).
  - **Pi _(beta)_**: `~/.pi/agent/settings.json` (пользователь), `<cwd>/.pi/settings.json` (проект) — Pi не имеет локального уровня. Pi загружает пакеты расширений TypeScript при запуске; файл настроек — это плоский массив строк `{"packages": ["./relative/path", …]}`. failproofai записывает одну запись массива пакетов, указывающую на его объединённый каталог `pi-extension/`. Расширение внутренне подписывается на события `tool_call` / `user_bash` / `input` / `session_start` Pi и запускает `failproofai --hook <Event> --cli pi`; обработчик канонизирует underscore_lower_snake_case → PascalCase через `PI_EVENT_MAP`, поэтому существующие встроенные политики срабатывают без изменений. Аргументы входа инструмента также канонизируются через `PI_TOOL_INPUT_MAP` (Pi's Read / Write / Edit доставляют `path` вместо `file_path`; сопоставление ключа верхнего уровня позволяет `block-env-files` и `block-secrets-write` срабатывать — `block-read-outside-cwd` уже имел откат `path`). Поддержка Pi находится в **beta** во время стабилизации API расширения Pi и разметки журнала сеансов.
  - **Hermes (hermes-agent)**: `~/.hermes/config.yaml` (**только пользовательский уровень** — Hermes не имеет конфига проекта/локального). Hermes — это шлюз **Slack/Telegram**, поэтому одна установка перехватывает вызовы инструментов с каждой платформы (Slack/Telegram/cli/cron) **и** внутренних подагентов. Записи хука — это пара `{command, timeout}` (timeout в **секундах**) под картой `hooks:` с ключами, соответствующими событиям snake_case Hermes (`pre_tool_call` / `post_tool_call` / `on_session_start` / `on_session_end` / `subagent_stop`); обработчик канонизирует события через `HERMES_EVENT_MAP` и имена инструментов через `HERMES_TOOL_MAP`, поэтому встроенные политики срабатывают без изменений. Конфиг редактируется через круговой YAML `Document` сохраняющих комментарии, так что другие настройки оператора остаются, и установка устанавливает `hooks_auto_accept: true`, так что безголовой шлюз (нет TTY) запускает хуки без запроса согласия. Оценщик выдаёт контракт stdout Hermes `{"decision":"block","reason"}` (Hermes игнорирует коды выхода). **Ограничения:** Hermes не имеет события завершения хода `Stop`, поэтому встроенные `require-*-before-stop` никогда не срабатывают для него (неприменимо, не сломано); `instruct` деградирует до allow-with-logged-note (нет дополнительного канала контекста); и переписывание утечки выходных секретов (`sanitize-*`) не может переписать выходной инструмент по контракту shell-хука. Hermes является **также** источником офлайн **аудита** — панель управления читает сеансы шлюза напрямую из `~/.hermes/state.db`.
  - **OpenClaw (openclaw gateway)**: `~/.openclaw/openclaw.json` (**только пользовательский уровень** — OpenClaw не имеет конфига проекта/локального). Как и Hermes, OpenClaw — это самостоятельный **шлюз** с несколькими каналами, поэтому одна установка перехватывает вызовы инструментов с каждого канала и его внутренних подагентов. Применение работает через **встроенные в процесс хуки плагинов** OpenClaw (его хуки на основе файлов — только наблюдение и не могут блокировать), поэтому — как OpenCode/Pi — failproofai поставляет статический пакет `openclaw-plugin/`, который асинхронно запускает бинарный файл failproofai и переводит вердикт. Установка регистрирует поставленный каталог плагинов в `openclaw.json` под `plugins.load.paths[]` и включает его под `plugins.entries.failproofai` (с `hooks.allowConversationAccess: true`, требуется для хуков сырого диалога). Оценщик выдаёт квартирный вердикт `{permission, reason}` и шим сопоставляет его с собственной формой возврата каждого хука: `before_tool_call → {block:true, blockReason}` (**PreToolUse**), `before_agent_run → {outcome:"block", reason}` (**UserPromptSubmit**), и `before_agent_finalize → {action:"revise", reason}` (**Stop** — настоящие ворота завершения хода, поэтому встроенные `require-*-before-stop` **применяются** на OpenClaw, в отличие от Hermes). События и имена инструментов канонизируются со стороны бинарного файла через `OPENCLAW_EVENT_MAP` / `OPENCLAW_TOOL_MAP` (`exec→Bash`, `read→Read`, …), поэтому встроенные политики срабатывают без изменений; шим не срабатывает открыто при любой ошибке spawn/parse/timeout. OpenClaw является **также** источником офлайн **аудита** — панель управления читает его сеансы JSONL на `~/.openclaw/agents/<agentId>/sessions/<uuid>.jsonl`.
  - **Factory Droid (`droid`)**: `~/.factory/hooks.json` (пользователь), `<cwd>/.factory/hooks.json` (проект) — Factory не имеет локального уровня. droid поставляет систему хуков внешних команд в стиле Claude, но с двумя особенностями, проверенными вживую на droid v0.171.0: (1) имена событий находятся на **верхнем уровне** `hooks.json` — нет **обёртки `"hooks"`** (droid её отклоняет); события инструментов (`PreToolUse`/`PostToolUse`) содержат `"matcher": "*"`, события, не относящиеся к инструментам, опускают его. (2) Отклонение управляется выходным кодом хука **2 + stderr**, а не решением JSON — ветка `factory` оценщика возвращает выход 2 для событий инструмента/подсказки и `{decision:"block", reason}` только при событии завершения хода `Stop` (единственный канал принудительного повтора droid). События уже в PascalCase (нет карты событий) и полезная нагрузка — это snake_case Claude; только имена инструментов канонизируются через `FACTORY_TOOL_MAP` (`Execute→Bash`, `Create→Write`, `FetchUrl→WebFetch`, …). Factory является **также** источником офлайн **аудита** — панель управления читает его сеансы JSONL на диске на `~/.factory/sessions/<encoded-cwd>/<sessionId>.jsonl`.
  - **Devin CLI (`devin`, Cognition)**: `~/.config/devin/config.json` (пользователь), `<cwd>/.devin/config.json` (проект) — Devin не имеет локального уровня. Devin — это **чистый Claude-клон**, проверенный вживую на devin v3000.1.27: он использует стандартную схему Claude с обёрткой `"hooks"` (записи сохраняют объединение, так что другие ключи файла конфига — `org_id`, `theme_mode`, … — остаются), уже в PascalCase имена событий (нет карты событий, нет ветки обработчика) и полезная нагрузка stdin в snake_case Claude (нет нормализации). Ветка `devin` оценщика отклоняет с JSON `{"decision":"block","reason"}` на stdout при выходе 0 для **каждого** события (проверено — отклонение переопределило `--permission-mode dangerous`); при событии завершения хода `Stop` причина содержит нужное для действия слово принудительного повтора, так что встроенные `require-*-before-stop` применяются. Только имена инструментов канонизируются через `DEVIN_TOOL_MAP` (`exec→Bash`; `tool_input.command` уже канонический). Devin является **также** источником офлайн **аудита** — панель управления читает его сеансы SQLite на `~/.local/share/devin/cli/sessions.db` (каждая строка `sessions` содержит реальный `working_directory`, поэтому сеансы группируются по проекту cwd, как Claude).
  - **Antigravity CLI (`agy`)**: `~/.gemini/config/hooks.json` (пользователь), `<cwd>/.agents/hooks.json` (проект) — Antigravity не имеет локального уровня. В отличие от Factory/Devin, Antigravity имеет собственный контракт (не Claude-клон), проверенный вживую на agy v1.1.2. `hooks.json` использует **именованную схему хука**: ключ верхнего уровня — это имя хука *name* (`"failproofai"`), значение которого — карта событий → обработчиков — события инструмента (`PreToolUse`/`PostToolUse`) обёртывают обработчики в `{matcher:"*", hooks:[…]}`, тогда как `PreInvocation`/`Stop` — **плоские** массивы обработчиков (другие именованные хуки сохраняются). Полезная нагрузка stdin — это **camelCase protojson** (`toolCall:{name,args}`, `conversationId`, `workspacePaths`, `transcriptPath`) — failproofai нормализует его в snake_case перед запуском политик и сопоставляет аргументы PascalCase `run_command` (`CommandLine`/`Cwd`) через `ANTIGRAVITY_TOOL_INPUT_MAP`. Ветка `antigravity` оценщика использует собственные формы ответа Antigravity: `{decision:"deny", reason}` блокирует инструмент/подсказку (выход 0), `{decision:"continue", reason}` при событии завершения хода `Stop` повторно входит в цикл (поэтому встроенные `require-*-before-stop` применяются), и `{injectSteps:[{ephemeralMessage}]}` внедряет инструкцию на `PreInvocation` (→ `UserPromptSubmit`). Имена инструментов канонизируются через `ANTIGRAVITY_TOOL_MAP` (`run_command→Bash`, `view_file→Read`, …). Antigravity является **также** источником офлайн **аудита** — панель управления читает его простые JSONL транскрипты на `~/.gemini/antigravity-cli/brain/<conversationId>/.system_generated/logs/transcript_full.jsonl` (индекс диалога в `conversation_summaries.db`).
  - **Goose (кодовое имя goose, Block)**: `~/.agents/plugins/failproofai/hooks/hooks.json` (пользователь), `<cwd>/.agents/plugins/failproofai/hooks/hooks.json` (проект) — Goose не имеет локального уровня. Применение использует систему **хуков** Goose, кросс-агентовую спецификацию **Open Plugins**: установщик просто создаёт каталог плагина `failproofai` и Goose автоматически обнаруживает его при запуске (самостоятельно регистрируя его в `~/.config/goose/config.yaml`). `hooks.json` использует схему Open Plugins **с** обёрткой верхнего уровня `"hooks"`, и сопоставитель **опускается** на каждом событии — голый `"*"` — это недопустимое регулярное выражение, которое ничего не соответствует (проверено вживую на goose v1.43.0). Имена событий уже в PascalCase (нет карты событий); полезная нагрузка stdin использует `event`/`working_dir`, которые обработчик нормализует в `hook_event_name`/`cwd`. Ветка `goose` оценщика отклоняет с JSON `{"decision":"block","reason"}` на stdout при выходе 0, уважается на событии **`PreToolUse`** только (поставляется в goose ≥ v1.37.0) — которое срабатывает для инструмента оболочки **и внутри делегированных подагентов**, поэтому это единственная достаточная точка отклонения; любая другая ошибка хука не срабатывает **открыто**. Goose **не имеет события `Stop`**, поэтому встроенные `require-*-before-stop` не применяются (как и с Hermes). Имена инструментов канонизируются через `GOOSE_TOOL_MAP` (`shell→Bash`, `write→Write`, `todo__todo_write→TodoWrite`, …) и ключи пути через `GOOSE_TOOL_INPUT_MAP` (`path`/`source` → `file_path`). Goose является **также** источником офлайн **аудита** — панель управления читает его сеансы SQLite на `~/.local/share/goose/sessions/sessions.db` (каждая строка `sessions` содержит реальный `working_dir`, поэтому сеансы группируются по проекту cwd, как Devin; сеансы с флагом `--no-session` фильтруются).
- **`policies-config.json`** — указывает failproofai, какие политики оценивать и с какими параметрами (общее для всех агентов CLI)

Передайте `--cli claude|codex|copilot|cursor|opencode|pi|hermes|openclaw|factory|devin|antigravity|goose`, чтобы направить работу на определённого агента (разделённые пробелом или повторяющиеся для любого подмножества):

```bash
failproofai policies --install --cli codex --scope project
failproofai policies --install --cli copilot --scope project
failproofai policies --install --cli cursor --scope project
failproofai policies --install --cli opencode --scope project
failproofai policies --install --cli pi --scope project
failproofai policies --install --cli hermes --scope user
failproofai policies --install --cli openclaw --scope user
failproofai policies --install --cli factory --scope project
failproofai policies --install --cli devin --scope project
failproofai policies --install --cli antigravity --scope project
failproofai policies --install --cli goose --scope project
failproofai policies --install --cli claude codex copilot cursor opencode pi hermes openclaw factory devin antigravity goose
```

Когда `--cli` опускается, `failproofai` обнаруживает, какие агенты CLI установлены (`which claude` / `which codex` / `which copilot` / `which cursor-agent` / `which opencode` / `which pi` / `which hermes` / `which openclaw` / `which droid` / `which devin` / `which agy` / `which goose`):

- **Один CLI обнаружен** — автоматически выбирает этот CLI без запросов.
- **Несколько CLI обнаружено** в интерактивном терминале — показывает подсказку single-select с клавишами стрелок, сгруппированную в раздел `Detected (N)` (с агрегированной строкой `Install for all N detected` + каждый обнаруженный CLI по отдельности) и раздел `Not installed (M) · install hooks ahead of time`, указывающий на каждый необнаруженный поддерживаемый CLI как опцию предварительной установки (↑↓ для перемещения, Enter для выбора, ^C для выхода). Поток удаления показывает только раздел Detected.
- **Несколько CLI обнаружено** в неинтерактивном запуске (CI, нет TTY) — устанавливает для всех обнаруженных CLI без запросов.
- **Ни один не обнаружен** — возвращается к `claude` с предупреждением, что бинарный файл агента не найден в PATH; команда хука всё ещё записывается, так что она активируется, как только вы установите один.

Вы можете редактировать `policies-config.json` напрямую в любое время; изменения вступают в силу немедленно при следующем событии хука без необходимости перезагрузки.

## Пример: конфиг на уровне проекта с командными значениями по умолчанию

Сохраните `.failproofai/policies-config.json` в вашем репозитории:

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "block-env-files"
  ],
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "release", "hotfix"]
    }
  }
}
```

Каждый разработчик может затем создать `.failproofai/policies-config.local.json` (исключённый из git) для личных переопределений без влияния на товарищей по команде.
