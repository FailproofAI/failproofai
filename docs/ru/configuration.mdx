failproofai использует JSON-файлы конфигурации для управления активными политиками, их поведением и местом загрузки пользовательских политик. Конфигурация разработана так, чтобы её было легко делиться с командой — зафиксируйте её в репозитории, и каждый разработчик получит одинаковую защиту агента.

---

## Области конфигурации

Существуют три области конфигурации, вычисляемые в порядке приоритета:

| Область | Путь файла | Назначение |
|---------|-----------|-----------|
| **project** | `.failproofai/policies-config.json` | Параметры на уровне репо, зафиксированы в системе контроля версий |
| **local** | `.failproofai/policies-config.local.json` | Личные переопределения на уровне репо, добавлены в .gitignore |
| **global** | `~/.failproofai/policies-config.json` | Параметры по умолчанию на уровне пользователя для всех проектов |

Когда failproofai получает событие хука, он загружает и объединяет все три существующих файла для текущей рабочей директории.

### Правила слияния

**`enabledPolicies`** — объединение всех трёх областей. Политика, активированная на любом уровне, является активной.

```text
project:  ["block-sudo"]
local:    ["block-rm-rf"]
global:   ["block-sudo", "sanitize-api-keys"]

resolved: ["block-sudo", "block-rm-rf", "sanitize-api-keys"]  ← дедублицированное объединение
```

**`policyParams`** — первая область, которая определяет параметры для данной политики, полностью выигрывает. Глубокого слияния значений внутри параметров политики не происходит.

```text
project:  block-sudo → { allowPatterns: ["sudo apt-get update"] }
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo apt-get update"] }   ← project выигрывает, global игнорируется
```

```text
project:  (нет записи block-sudo)
local:    (нет записи block-sudo)
global:   block-sudo → { allowPatterns: ["sudo systemctl status"] }

resolved: { allowPatterns: ["sudo systemctl status"] }  ← спускается до global
```

**`customPoliciesPaths` / `customPoliciesPath`** — первая область, которая определяет любую из этих форм, выигрывает.

**`disabledCustomPolicies`** — объединение всех областей. Панель управления записывает сюда идентификатор с указанием источника, когда вы отключаете отдельную политику из явного или условного файла политики. Политики, не указанные в списке, остаются активированными по умолчанию; идентификаторы включают файл источника, поэтому политики с одинаковыми названиями в разных файлах можно контролировать независимо.

**`llm`** — первая область, которая его определяет, выигрывает.

## Формат конфигурационного файла

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "sanitize-jwt",
    "block-env-files",
    "block-read-outside-cwd"
  ],
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    },
    "block-push-master": {
      "protectedBranches": ["main", "release", "prod"]
    },
    "block-rm-rf": {
      "allowPaths": ["/tmp"]
    },
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company"]
    },
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo API key" }
      ]
    },
    "warn-large-file-write": {
      "thresholdKb": 512
    }
  },
  "customPoliciesPath": "/home/alice/myproject/my-policies.js"
}
```

## Справочник полей

### `enabledPolicies`

Тип: `string[]`

Список названий политик для активации. Названия должны точно совпадать с идентификаторами политик, показанными командой `failproofai policies`. Полный список см. в разделе [Встроенные политики](/ru/built-in-policies).

Политики, отсутствующие в `enabledPolicies`, неактивны, даже если у них есть записи в `policyParams`.

### `policyParams`

Тип: `Record<string, Record<string, unknown>>`

Переопределения параметров для каждой политики. Внешний ключ — название политики; внутренние ключи — специфичны для политики. Каждая политика документирует доступные параметры в разделе [Встроенные политики](/ru/built-in-policies).

Если у политики есть параметры, но вы их не указали, используются встроенные значения политики по умолчанию. Пользователи, которые вообще не настраивают `policyParams`, получают поведение, идентичное предыдущим версиям.

Неизвестные ключи внутри блока параметров политики молча игнорируются при срабатывании хука, но помечаются предупреждениями при запуске `failproofai policies`.

#### `hint` (сквозной)

Тип: `string` (опционально)

Сообщение, добавленное к причине, когда политика возвращает `deny` или `instruct`. Используйте его, чтобы дать Claude практические рекомендации, не изменяя саму политику.

Работает с любым типом политики — встроенной, пользовательской (`custom/`), проектной конвенции (`.failproofai-project/`), или пользовательской конвенции (`.failproofai-user/`).

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "Попробуйте создать новую ветку вместо этого."
    },
    "block-sudo": {
      "allowPatterns": ["sudo apt-get"],
      "hint": "Используйте apt-get напрямую без sudo."
    },
    "custom/my-policy": {
      "hint": "Сначала попросите одобрение пользователя."
    }
  }
}
```

Когда `block-force-push` возвращает deny, Claude видит: *«Force-pushing заблокирован. Попробуйте создать новую ветку вместо этого.»*

Значения не-строк и пустые строки молча игнорируются. Если `hint` не установлен, поведение остаётся неизменённым (обратно совместимо).

### `customPoliciesPath`

Тип: `string` (абсолютный путь)

Путь к JavaScript-файлу, содержащему пользовательские политики хуков. Это устанавливается автоматически командой `failproofai policies --install --custom <path>` (путь разрешается в абсолют перед сохранением).

Файл загружается заново при каждом событии хука — кэширования не происходит. Подробности см. в разделе [Пользовательские политики](/ru/custom-policies).

### Политики на основе конвенции

В дополнение к явному `customPoliciesPath`, failproofai автоматически обнаруживает и загружает файлы политик из директорий `.failproofai/policies/`:

| Уровень | Директория | Область |
|---------|-----------|--------|
| Project | `.failproofai/policies/` | Поделено с командой через систему контроля версий |
| User | `~/.failproofai/policies/` | Личное, применяется ко всем проектам |

<Note>
  Поместите ваши политики прямо в `~/.failproofai/policies/`. Папка
  `cloud-policies/` рядом с ними содержит политики, развёрнутые вашей организацией
  на этот компьютер — обнаружение не спускается в подпапки, поэтому она
  никогда не сканируется, и ничто в `policies/` не может с ней конфликтовать.

  Если вы обновляетесь с версии, использовавшей
  `~/.failproofai/policies/custom-policies/`, всё содержимое этой папки — ваши
  файлы политик, любой импортируемый `lib/` вспомогательный код и любые файлы
  данных, которые они читают — автоматически перемещается обратно при первом
  запуске команды `failproofai`, и команда сообщит вам, что было перемещено.
</Note>

**Соответствие файлов:** Загружаются только файлы, соответствующие `*policies.{js,mjs,ts}` (например, `security-policies.mjs`, `workflow-policies.js`). Остальные файлы в директории игнорируются.

**Конфигурация не требуется:** Политики конвенции не требуют записей в `policies-config.json`. Просто поместите файлы в директорию, и они будут подхвачены при следующем событии хука.

**Объединённая загрузка:** Сканируются как директории проектных, так и пользовательских конвенций. Все соответствующие файлы с обоих уровней загружаются (в отличие от `customPoliciesPath`, где выигрывает первая область).

Подробности и примеры см. в разделе [Пользовательские политики](/ru/custom-policies).

### `llm`

Тип: `object` (опционально)

Конфигурация LLM-клиента для политик, которые выполняют вызовы AI. Не требуется для большинства конфигураций.

```json
{
  "llm": {
    "model": "claude-sonnet-4-6",
    "apiKey": "sk-ant-..."
  }
}
```

## Управление конфигурацией из CLI

Команды `policies --install` и `policies --uninstall` записывают в файл параметров хука вашего CLI агента (точки входа хука), а `policies-config.json` — это файл, который вы управляете напрямую. Это два отдельных файла:

- **Параметры CLI агента** — указывают агенту вызвать `failproofai --hook <event>` при каждом использовании инструмента:
  - **Claude Code**: `~/.claude/settings.json` (пользователь), `<cwd>/.claude/settings.json` (проект), `<cwd>/.claude/settings.local.json` (локально)
  - **OpenAI Codex**: `~/.codex/hooks.json` (пользователь), `<cwd>/.codex/hooks.json` (проект) — Codex не имеет локальной области
  - **GitHub Copilot CLI _(бета)_**: `~/.copilot/hooks/failproofai.json` (пользователь), `<cwd>/.github/hooks/failproofai.json` (проект) — Copilot не имеет локальной области. Записи хуков используют поля команд Copilot, зависящие от ОС `bash`/`powershell`, с `timeoutSec`; файл содержит маркер версии верхнего уровня `version: 1`. Поддержка Copilot CLI находится в **бета** версии, пока мы проверяем схему записи `events.jsonl` (которая не указана в общедоступной документации) против большего количества реальных сессий. **VS Code Copilot Chat агент режим (Preview)** читает конфигурации хуков из `.github/hooks/*.json`, `~/.copilot/hooks/*.json` и `~/.claude/settings.json` (управляется параметром `chat.hookFilesLocations`), используя тот же контракт Claude-формы `{hookSpecificOutput:{permissionDecision:"deny",…}}` — точные пути, которые уже пишут интеграция `copilot` и интеграция `claude` (`~/.claude/settings.json`), поэтому `failproofai policies --install --cli copilot` (или `--cli claude`) **уже работает в режиме VS Code агента** без отдельной интеграции `vscode` (подтверждено в реальном времени из журналов обнаружения VS Code).
  - **Cursor Agent _(бета)_**: `~/.cursor/hooks.json` (пользователь), `<cwd>/.cursor/hooks.json` (проект) — Cursor не имеет локальной области. Записи хуков используют форму, совместимую с Claude, `{type, command, timeout}` (без разделения `bash`/`powershell`), но хранятся под camelCase ключами событий (`preToolUse`, `beforeSubmitPrompt`, …) в плоском массиве согласно [схеме хуков](https://cursor.com/docs/hooks) Cursor. Файл содержит маркер версии верхнего уровня `version: 1`. Обработчик канонизирует camelCase → PascalCase через `CURSOR_EVENT_MAP`, поэтому встроенные политики работают без изменений. Поддержка Cursor Agent находится в **бета** версии, пока мы проверяем формат транскрипта Cursor на диске (не указан в общедоступной документации) против большего количества реальных установок.
  - **OpenCode _(бета)_**: `~/.config/opencode/opencode.json` + `~/.config/opencode/plugins/failproofai.mjs` (пользователь), `<cwd>/.opencode/opencode.json` + `<cwd>/.opencode/plugins/failproofai.mjs` (проект) — OpenCode не имеет локальной области. В отличие от других пяти CLI, OpenCode **не имеет системы внешних команд хуков**: он загружает встроенные JS/TS плагины, явно зарегистрированные через массив `plugin: []` в `opencode.json` (автообнаружение из `.opencode/plugins/` **не** является способом загрузки плагинов на opencode v1.14.33). Установка добавляет небольшой сгенерированный заглушку плагина, которая вызывает двоичный файл failproofai как подпроцесс и переводит ответ двоичного файла в форме Claude JSON обратно в семантику плагина: `throw new Error()` для отрицания события инструмента (отменяет вызов инструмента), `client.session.prompt(...)` для instruct И для отрицания `Stop` / `SubagentStop` (отправляет причину отрицания как следующее сообщение пользователя — единственный канал повторной попытки, так как `session.idle` — это только уведомление и выброс из него — нет-оп), и нет-оп для allow. Заглушка канонизирует названия инструментов (lowercase → PascalCase через `OPENCODE_TOOL_MAP`) и ключи аргументов входа инструмента (camelCase → snake_case через `OPENCODE_TOOL_INPUT_MAP` для `Read` / `Write` / `Edit`, например `filePath` → `file_path`, `oldString` → `old_string`) перед отправкой в двоичный файл, поэтому встроенные проверки путей, такие как `block-read-outside-cwd`, `block-env-files` и `block-secrets-write`, работают без изменений на вызовах инструментов OpenCode. Сессии живут в базе данных SQLite OpenCode по адресу `~/.local/share/opencode/opencode.db`; средство просмотра сессий панели управления читает их через `opencode db --format json` и `opencode export <id>`. Поддержка OpenCode находится в **бета** версии, пока мы проверяем поведение в разных версиях и против большего количества реальных сессий. См. [документацию плагинов OpenCode](https://opencode.ai/docs/plugins/).
  - **Pi _(бета)_**: `~/.pi/agent/settings.json` (пользователь), `<cwd>/.pi/settings.json` (проект) — Pi не имеет локальной области. Pi загружает пакеты расширений TypeScript при запуске; файл параметров — это плоский строковый массив `{"packages": ["./relative/path", …]}`. failproofai записывает одну запись массива пакетов, указывающую на его встроенный каталог `pi-extension/`. Расширение внутри подписывается на события Pi `tool_call` / `user_bash` / `input` / `session_start` и вызывает `failproofai --hook <Event> --cli pi` через shell; обработчик канонизирует underscore_lower_snake_case → PascalCase через `PI_EVENT_MAP`, поэтому встроенные политики работают без изменений. Аргументы входа инструмента также канонизируются через `PI_TOOL_INPUT_MAP` (Pi's Read / Write / Edit доставляют `path` вместо `file_path`; отображение ключа верхнего уровня позволяет `block-env-files` и `block-secrets-write` работать — `block-read-outside-cwd` уже имел откат `path`). Поддержка Pi находится в **бета** версии, пока API расширений Pi и макет журнала сессий стабилизируются.
  - **Hermes (hermes-agent)**: `~/.hermes/config.yaml` (**только область пользователя** — Hermes не имеет конфигурации проекта/локально). Hermes — это **шлюз** Slack/Telegram, поэтому одна установка перехватывает вызовы инструментов из каждой платформы (Slack/Telegram/cli/cron) **и** внутренних подагентов. Записи хуков — это пара `{command, timeout}` (время ожидания в **секундах**) под картой `hooks:`, ключами которой являются события Hermes в snake_case (`pre_tool_call` / `post_tool_call` / `on_session_start` / `on_session_end` / `subagent_stop`); обработчик канонизирует события через `HERMES_EVENT_MAP` и названия инструментов через `HERMES_TOOL_MAP`, поэтому встроенные политики работают без изменений. Конфигурация редактируется посредством сохраняющей комментарии раунд-трип YAML `Document`, поэтому остальные параметры оператора выживают, и установка устанавливает `hooks_auto_accept: true`, поэтому безголовой шлюз (без TTY) запускает хуки без запроса согласия. Оценочник выдает контракт stdout Hermes `{"decision":"block","reason"}` (Hermes игнорирует коды выхода). **Ограничения:** Hermes не имеет события окончания хода `Stop`, поэтому встроенные `require-*-before-stop` никогда не срабатывают для него (неприменимо, не сломано); `instruct` деградирует до allow-with-logged-note (нет дополнительного канала контекста); и редакция секретов выходного сигнала (`sanitize-*`) не может переписать выход инструмента через контракт shell-хука. Hermes — **также** автономный источник **аудита** — панель управления читает его сессии шлюза напрямую из `~/.hermes/state.db`.
  - **OpenClaw (openclaw gateway)**: `~/.openclaw/openclaw.json` (**только область пользователя** — OpenClaw не имеет конфигурации проекта/локально). Как и Hermes, OpenClaw — это самостоятельный многоканальный **шлюз**, поэтому одна установка перехватывает вызовы инструментов из каждого канала и его внутренних подагентов. Правоприменение работает через **встроенные хуки плагина** OpenClaw (его файловые внутренние хуки только для наблюдения и не могут блокировать), поэтому — как OpenCode/Pi — failproofai поставляется со статическим пакетом `openclaw-plugin/`, который асинхронно порождает двоичный файл failproofai и переводит вердикт. Установка регистрирует каталог отправленного плагина в `openclaw.json`'s `plugins.load.paths[]` и включает его под `plugins.entries.failproofai` (с `hooks.allowConversationAccess: true`, обязательно для хуков raw-conversation). Оценочник выдает плоский вердикт `{permission, reason}` и заглушка отображает его в собственную форму каждого хука: `before_tool_call → {block:true, blockReason}` (**PreToolUse**), `before_agent_run → {outcome:"block", reason}` (**UserPromptSubmit**), и `before_agent_finalize → {action:"revise", reason}` (**Stop** — истинный шлюз окончания хода, поэтому встроенные `require-*-before-stop` **работают** на OpenClaw, в отличие от Hermes). События и названия инструментов канонизируются на стороне двоичного файла через `OPENCLAW_EVENT_MAP` / `OPENCLAW_TOOL_MAP` (`exec→Bash`, `read→Read`, …), поэтому встроенные политики работают без изменений; заглушка отказывает при открытии при любой ошибке spawn/parse/timeout. OpenClaw — **также** автономный источник **аудита** — панель управления читает его сессии JSONL по адресу `~/.openclaw/agents/<agentId>/sessions/<uuid>.jsonl`.
  - **Factory Droid (`droid`)**: `~/.factory/hooks.json` (пользователь), `<cwd>/.factory/hooks.json` (проект) — Factory не имеет локальной области. droid поставляется с системой внешних команд хуков в стиле Claude, но с двумя особенностями, проверенными в реальном времени против droid v0.171.0: (1) названия событий находятся на **верхнем уровне** `hooks.json` — **нет обёртки `"hooks"`** (droid её отвергает); события инструментов (`PreToolUse`/`PostToolUse`) переносят `"matcher": "*"`, события без инструментов это опускают. (2) Отрицание управляется **выходным кодом хука 2 + stderr**, а не решением JSON — ветвь оценочника `factory` возвращает выход 2 для событий инструмента/приглашения и `{decision:"block", reason}` только для события окончания хода `Stop` (единственный канал повторной попытки droid). События уже находятся в PascalCase (нет карты событий) и полезная нагрузка — это Claude snake_case; только названия инструментов канонизируются через `FACTORY_TOOL_MAP` (`Execute→Bash`, `Create→Write`, `FetchUrl→WebFetch`, …). Factory — **также** автономный источник **аудита** — панель управления читает его сессии JSONL на диске по адресу `~/.factory/sessions/<encoded-cwd>/<sessionId>.jsonl`.
  - **Devin CLI (`devin`, Cognition)**: `~/.config/devin/config.json` (пользователь), `<cwd>/.devin/config.json` (проект) — Devin не имеет локальной области. Devin — это **чистый клон Claude**, проверенный в реальном времени против devin v3000.1.27: он использует стандартную схему Claude с обёрткой `"hooks"` (записи сохраняют слияние, поэтому остальные ключи файла конфигурации — `org_id`, `theme_mode`, … — выживают), названия событий уже в PascalCase (нет карты событий, нет ветви обработчика) и полезная нагрузка stdin Claude snake_case (нет нормализации). Ветвь оценочника `devin` отрицает с JSON `{"decision":"block","reason"}` на stdout при выходе 0 для **каждого** события (проверено — блокировка переопределила `--permission-mode dangerous`); для события окончания хода `Stop` причина содержит обязательное действие-форс-retry слова, поэтому встроенные `require-*-before-stop` работают. Только названия инструментов канонизируются через `DEVIN_TOOL_MAP` (`exec→Bash`; `tool_input.command` уже канонический). Devin — **также** автономный источник **аудита** — панель управления читает его сессии SQLite по адресу `~/.local/share/devin/cli/sessions.db` (каждая строка `sessions` содержит реальный `working_directory`, поэтому сессии группируются по cwd проекта как Claude).
  - **Antigravity CLI (`agy`)**: `~/.gemini/config/hooks.json` (пользователь), `<cwd>/.agents/hooks.json` (проект) — Antigravity не имеет локальной области. В отличие от Factory/Devin, Antigravity имеет свой собственный контракт (не клон Claude), проверенный в реальном времени против agy v1.1.2. `hooks.json` использует **схему названного хука**: ключ верхнего уровня — это имя хука *name* (`"failproofai"`), значение которого — карта событий→обработчиков — события инструментов (`PreToolUse`/`PostToolUse`) оборачивают обработчики в `{matcher:"*", hooks:[…]}`, в то время как `PreInvocation`/`Stop` — это **плоские** массивы обработчиков (остальные названные хуки сохраняются). Полезная нагрузка stdin — это **camelCase protojson** (`toolCall:{name,args}`, `conversationId`, `workspacePaths`, `transcriptPath`) — failproofai нормализует её в snake_case перед запуском политик и отображает аргументы PascalCase `run_command` (`CommandLine`/`Cwd`) через `ANTIGRAVITY_TOOL_INPUT_MAP`. Ветвь оценочника `antigravity` использует собственные формы ответа Antigravity: `{decision:"deny", reason}` блокирует инструмент/приглашение (выход 0), `{decision:"continue", reason}` для события окончания хода `Stop` повторно входит в цикл (поэтому встроенные `require-*-before-stop` работают), и `{injectSteps:[{ephemeralMessage}]}` вводит инструкцию для `PreInvocation` (→ `UserPromptSubmit`). Названия инструментов канонизируются через `ANTIGRAVITY_TOOL_MAP` (`run_command→Bash`, `view_file→Read`, …). Antigravity — **также** автономный источник **аудита** — панель управления читает его транскрипты plain-JSONL по адресу `~/.gemini/antigravity-cli/brain/<conversationId>/.system_generated/logs/transcript_full.jsonl` (индекс разговора в `conversation_summaries.db`).
  - **Goose (codename goose, Block)**: `~/.agents/plugins/failproofai/hooks/hooks.json` (пользователь), `<cwd>/.agents/plugins/failproofai/hooks/hooks.json` (проект) — Goose не имеет локальной области. Правоприменение использует систему **hooks** Goose, спецификацию кросс-агента **Open Plugins**: установщик просто добавляет каталог плагина `failproofai` и Goose автоматически его обнаруживает при запуске (самостоятельно регистрируя его в `~/.config/goose/config.yaml`). `hooks.json` использует схему **Open Plugins** **с** обёрткой верхнего уровня `"hooks"`, и устройство сопоставления **опускается** на каждом событии — пустое `"*"` — это недопустимое регулярное выражение, которое ничему не соответствует (проверено в реальном времени против goose v1.43.0). Названия событий уже находятся в PascalCase (нет карты событий); полезная нагрузка stdin использует `event`/`working_dir`, которые обработчик нормализует в `hook_event_name`/`cwd`. Ветвь оценочника `goose` отрицает с JSON `{"decision":"block","reason"}` на stdout при выходе 0, соблюдается на событии **`PreToolUse`** только (поставляется в goose ≥ v1.37.0) — который срабатывает для инструмента shell **и внутри делегированных подагентов**, поэтому это единственная достаточная точка отрицания; любая другая ошибка хука отказывает **открыто**. Goose **не имеет события `Stop`**, поэтому встроенные `require-*-before-stop` не применяются (как и Hermes). Названия инструментов канонизируются через `GOOSE_TOOL_MAP` (`shell→Bash`, `write→Write`, `todo__todo_write→TodoWrite`, …) и ключи путей через `GOOSE_TOOL_INPUT_MAP` (`path`/`source` → `file_path`). Goose — **также** автономный источник **аудита** — панель управления читает его сессии SQLite по адресу `~/.local/share/goose/sessions/sessions.db` (каждая строка `sessions` содержит реальный `working_dir`, поэтому сессии группируются по cwd проекта как Devin; запуски `--no-session` scratch отфильтрованы).
- **`policies-config.json`** — указывает failproofai, какие политики оценивать и с какими параметрами (общее для всех CLI агентов)

Передайте `--cli claude|codex|copilot|cursor|opencode|pi|hermes|openclaw|factory|devin|antigravity|goose` для целевого конкретного агента (разделённые пробелом или повторенные для любого подмножества):

```bash
failproofai policies --install --cli codex --scope project
failproofai policies --install --cli copilot --scope project
failproofai policies --install --cli cursor --scope project
failproofai policies --install --cli opencode --scope project
failproofai policies --install --cli pi --scope project
failproofai policies --install --cli hermes --scope user
failproofai policies --install --cli openclaw --scope user
failproofai policies --install --cli factory --scope project
failproofai policies --install --cli devin --scope project
failproofai policies --install --cli antigravity --scope project
failproofai policies --install --cli goose --scope project
failproofai policies --install --cli claude codex copilot cursor opencode pi hermes openclaw factory devin antigravity goose
```

Когда `--cli` опущен, `failproofai` обнаруживает, какие CLI агентов установлены (`which claude` / `which codex` / `which copilot` / `which cursor-agent` / `which opencode` / `which pi` / `which hermes` / `which openclaw` / `which droid` / `which devin` / `which agy` / `which goose`):

- **Обнаружен один CLI** — автоматически выбирает этот CLI без запроса.
- **Множество CLI обнаружено** в интерактивном терминале — показывает навигационный однократный выбор приглашение, сгруппированный в раздел `Detected (N)` (с совокупной строкой `Install for all N detected` + каждый обнаруженный CLI отдельно) и раздел `Not installed (M) · install hooks ahead of time` со списком каждого неподдерживаемого поддерживаемого CLI как опции предварительной установки (↑↓ для движения, Enter для выбора, ^C для выхода). Поток удаления показывает только раздел Detected.
- **Множество CLI обнаружено** в неинтерактивном запуске (CI, без TTY) — устанавливает для всех обнаруженных CLI без запроса.
- **Ничего не обнаружено** — возвращается к `claude`, с предупреждением о том, что в PATH не найден двоичный файл агента; команда хука всё ещё записана, так что она активируется, как только вы установите один.

Вы можете редактировать `policies-config.json` напрямую в любое время; изменения вступают в силу немедленно при следующем событии хука без перезагрузки.

## Обновления сохраняют вашу конфигурацию

Новая версия failproofai может организовать `~/.failproofai/` по-другому. Когда это произойдёт, первая команда после обновления мигрирует каталог, и **ваша конфигурация переносится, а не сбрасывается**:

| Сохранено | Перестроено |
|---|---|
| Ваш выбор политик и параметры (`policies-config.json`) | Кэш аудита |
| Ваши параметры, включая `daemon.configured` и дополнительные пути захвата (`config.json`) | Управляемые облаком развёртывания политик — повторно получены и проверены по дайджесту при следующем опросе |
| Ваша регистрация в облаке (`credentials.json`) | Состояние scratch демона |
| Ваши собственные файлы политик в `policies/` и вспомогательные коды, которые они импортируют | |
| Журнал решений, который читает панель управления, и события, ещё не доставленные | |

Ключи, написанные более новым failproofai, также сохраняются, а не отбрасываются более старым читателем — поэтому перемещение между версиями не молча отбрасывает параметры в любом направлении.

Вам **не** нужно повторно запускать установку после миграции: мигрированная машина работает точно так же, как раньше, что делает обновление безопасным на машинах, где никто не сидит. Каждая миграция записывается в `~/.failproofai/migrations/applied.json`, и незаменяемые файлы копируются в `~/.failproofai/migrations/backup-layout<n>/` перед запуском чего-либо.

См. [`failproofai update`](/ru/cli/update) для одной команды обновления и [`failproofai migrate`](/ru/cli/migrate) — включая `--dry-run` — для подробностей.

## Пример: конфигурация на уровне проекта с командными значениями по умолчанию

Зафиксируйте `.failproofai/policies-config.json` в вашем репо:

```json
{
  "enabledPolicies": [
    "block-sudo",
    "block-rm-rf",
    "block-push-master",
    "sanitize-api-keys",
    "block-env-files"
  ],
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "release", "hotfix"]
    }
  }
}
```

Затем каждый разработчик может создать `.failproofai/policies-config.local.json` (добавлено в .gitignore) для личных переопределений без влияния на коллег.
