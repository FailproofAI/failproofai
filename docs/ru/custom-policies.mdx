Пользовательские политики позволяют создавать правила для любого поведения агента: обеспечивать соответствие соглашениям проекта, предотвращать дрейф, блокировать деструктивные операции, обнаруживать зависающих агентов или интегрироваться со Slack, рабочими процессами утверждения и многим другим. Они используют ту же систему хуков и решения `allow`, `deny`, `instruct`, что и встроенные политики.

---

## Быстрый пример

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

customPolicies.add({
  name: "no-production-writes",
  description: "Block writes to paths containing 'production'",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Write" && ctx.toolName !== "Edit") return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("production")) {
      return deny("Writes to production paths are blocked");
    }
    return allow();
  },
});
```

Установите её:

```bash
failproofai policies --install --custom ./my-policies.js
```

## Два способа загрузить пользовательские политики

### Вариант 1: На основе соглашения (рекомендуется)

Поместите файлы `*policies.{js,mjs,ts}` в `.failproofai/policies/` и они будут загружены автоматически — никаких флагов или изменений конфигурации не требуется. Это работает как git-хуки: положите файл, и он просто работает.

```
# На уровне проекта — добавлен в git, общий с командой
.failproofai/policies/security-policies.mjs
.failproofai/policies/workflow-policies.mjs

# На личном уровне — личный, применяется ко всем проектам
~/.failproofai/policies/my-policies.mjs
```

**Как это работает:**
- Сканируются оба каталога (объединение — не первый побеждает)
- Файлы загружаются в алфавитном порядке в каждом каталоге. Используйте префикс `01-`, `02-` для управления порядком
- Загружаются только файлы, соответствующие `*policies.{js,mjs,ts}`; другие файлы игнорируются
- Каждый файл загружается независимо (fail-open для каждого файла)
- Работает наряду с явными флагами `--custom` и встроенными политиками

<Tip>
Политики на основе соглашений — это самый простой способ создать стандарт качества для вашей организации. Добавьте `.failproofai/policies/` в git, и каждый член команды автоматически получит одинаковые правила — не требуется индивидуальная настройка. По мере обнаружения новых режимов сбоев добавляйте политику и отправляйте её. С течением времени они становятся живым стандартом качества, который постоянно совершенствуется с каждым вкладом.
</Tip>

### Вариант 2: Явный путь к файлу

```bash
# Установить с пользовательским файлом политик
failproofai policies --install --custom ./my-policies.js

# Заменить пути пользовательских политик
failproofai policies --install --custom ./new-policies.js

# Настроить несколько явных файлов (загружаются в порядке флагов)
failproofai policies --install --custom ./security.js --custom ./workflow.js

# Удалить все явные пути пользовательских политик из конфигурации
failproofai policies --uninstall --custom
```

Разрешённые абсолютные пути сохраняются в `policies-config.json` как `customPoliciesPaths`. Повторите `--custom` для настройки нескольких файлов. Существующие конфигурации с использованием устаревшего поля `customPoliciesPath` продолжают работать. Файлы загружаются заново при каждом событии хука — кеширования между событиями не происходит.

Каждая зарегистрированная политика появляется со своим переключателем на панели инструментов. Отключение политики записывает её квалифицированный по источнику ID в `disabledCustomPolicies`; файл и его другие политики продолжают загружаться, в то время как отключённая политика исключается перед сопоставлением событий. Имена политик, дублирующиеся в разных файлах, имеют независимые переключатели.

### Использование обоих вместе

Политики на основе соглашений и явные файлы `--custom` могут сосуществовать. Порядок загрузки:

1. Явные файлы `customPoliciesPaths` (в настроенном порядке)
2. Файлы проектного соглашения (`{cwd}/.failproofai/policies/`, алфавитный порядок)
3. Файлы личного соглашения (`~/.failproofai/policies/`, алфавитный порядок)

## API

### Импорт

```js
import { customPolicies, allow, deny, instruct } from "failproofai";
```

### `customPolicies.add(hook)`

Регистрирует политику. Вызовите это столько раз, сколько нужно для нескольких политик в одном файле.

```ts
customPolicies.add({
  name: string;                         // требуется — уникальный идентификатор
  description?: string;                 // показывается в выводе `failproofai policies`
  match?: { events?: HookEventType[] }; // фильтр по типу события; опустите, чтобы соответствовать всем
  fn: (ctx: PolicyContext) => PolicyResult | Promise<PolicyResult>;
});
```

### Помощники для принятия решений

| Функция | Эффект | Используйте когда |
|---------|--------|------------------|
| `allow()` | Разрешить операцию без сообщения | Действие безопасно, сообщение не требуется |
| `deny(message)` | Заблокировать операцию | Агент не должен выполнять это действие |
| `instruct(message)` | Добавить контекст без блокировки | Дайте агенту дополнительный контекст для правильного выполнения |

`deny(message)` — сообщение появляется для Claude с префиксом `"Blocked by failproofai:"`. Один `deny` замыкает всю последующую оценку.

`instruct(message)` — сообщение добавляется в контекст Claude для текущего вызова инструмента. Все сообщения `instruct` накапливаются и доставляются вместе.

<Tip>
Вы можете добавить дополнительные указания к любому сообщению `deny` или `instruct`, добавив поле `hint` в `policyParams` — без изменения кода. Это работает для пользовательских (`custom/`), проектных (`./failproofai-project/`) и личных (`./failproofai-user/`) политик. Подробности см. в [Конфигурация → hint](/ru/configuration#hint-cross-cutting).
</Tip>

### Информационные сообщения разрешения

`allow(message)` разрешает операцию **и** отправляет информационное сообщение обратно Claude. Сообщение доставляется как `additionalContext` в ответе stdout обработчика хука — тот же механизм, используемый `instruct`, но семантически отличается: это обновление статуса, а не предупреждение.

| Функция | Эффект | Используйте когда |
|---------|--------|------------------|
| `allow(message)` | Разрешить и отправить контекст Claude | Подтвердите, что проверка прошла, или объясните, почему проверка была пропущена |

Случаи использования:
- **Подтверждения статуса:** `allow("All CI checks passed.")` — сообщает Claude, что всё в порядке
- **Объяснения fail-open:** `allow("GitHub CLI not installed, skipping CI check.")` — сообщает Claude, почему проверка была пропущена, чтобы у него был полный контекст
- **Несколько сообщений накапливаются:** если несколько политик возвращают `allow(message)`, все сообщения объединяются с новыми строками и доставляются вместе

```js
customPolicies.add({
  name: "confirm-branch-status",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow("No working directory, skipping branch check.");

    // ... проверить статус ветки ...
    if (allPushed) {
      return allow("Branch is up to date with remote.");
    }
    return deny("Unpushed changes detected.");
  },
});
```

### Поля `PolicyContext`

| Поле | Тип | Описание |
|------|-----|---------|
| `eventType` | `string` | `"PreToolUse"`, `"PostToolUse"`, `"Notification"`, `"Stop"` |
| `toolName` | `string \| undefined` | Вызываемый инструмент (например `"Bash"`, `"Write"`, `"Read"`) |
| `toolInput` | `Record<string, unknown> \| undefined` | Параметры входа инструмента |
| `payload` | `Record<string, unknown>` | Полные необработанные данные события от Claude Code |
| `session` | `SessionMetadata \| undefined` | Контекст сессии (см. ниже) |

### Поля `SessionMetadata`

| Поле | Тип | Описание |
|------|-----|---------|
| `sessionId` | `string` | Идентификатор сессии Claude Code |
| `cwd` | `string` | Рабочий каталог сессии Claude Code |
| `transcriptPath` | `string` | Путь к файлу транскрипта JSONL сессии |

### Типы событий

| Событие | Когда происходит | Содержимое `toolInput` |
|---------|-------------------|----------------------|
| `PreToolUse` | Перед запуском инструмента Claude | Вход инструмента (например `{ command: "..." }` для Bash) |
| `PostToolUse` | После завершения инструмента | Вход инструмента + `tool_result` (выход) |
| `Notification` | Когда Claude отправляет уведомление | `{ message: "...", notification_type: "idle" \| "permission_prompt" \| ... }` — хуки должны всегда возвращать `allow()`, они не могут блокировать уведомления |
| `Stop` | Когда сессия Claude заканчивается | Пусто |

## Порядок оценки

Политики оцениваются в этом порядке:

1. Встроенные политики (в порядке определения)
2. Явные пользовательские политики из `customPoliciesPath` (в порядке `.add()`)
3. Политики соглашений из проектного `.failproofai/policies/` (файлы в алфавитном порядке, `.add()` в порядке)
4. Политики соглашений из личного `~/.failproofai/policies/` (файлы в алфавитном порядке, `.add()` в порядке)

<Note>
Первый `deny` замыкает все последующие политики. Все сообщения `instruct` накапливаются и доставляются вместе.
</Note>

## Переходящие импорты

Файлы пользовательских политик могут импортировать локальные модули, используя относительные пути:

```js
// my-policies.js
import { isBlockedPath } from "./utils.js";
import { checkApproval } from "./approval-client.js";

customPolicies.add({
  name: "approval-gate",
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const approved = await checkApproval(ctx.toolInput?.command, ctx.session?.sessionId);
    return approved ? allow() : deny("Approval required for this command");
  },
});
```

Все относительные импорты, доступные из входного файла, разрешаются. Это реализуется путём переписывания импортов `from "failproofai"` в фактический путь dist и создания временных файлов `.mjs` для обеспечения совместимости ESM.

## Фильтрация по типам событий

Используйте `match.events` для ограничения срабатывания политики:

```js
customPolicies.add({
  name: "require-summary-on-stop",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    // Срабатывает только при завершении сессии
    // ctx.session.transcriptPath содержит полный лог сессии
    return allow();
  },
});
```

Опустите `match` полностью, чтобы политика срабатывала на каждый тип события.

## Обработка ошибок и режимы отказа

Пользовательские политики **fail-open**: ошибки никогда не блокируют встроенные политики и не вызывают крах обработчика хука.

| Отказ | Поведение |
|-------|----------|
| `customPoliciesPath` не установлен | Никакие явные пользовательские политики не запускаются; политики соглашений и встроенные продолжают нормально работать |
| Файл не найден | Предупреждение записано в `~/.failproofai/hook.log`; встроенные продолжают работать |
| Ошибка синтаксиса/импорта (явная) | Ошибка записана в `~/.failproofai/hook.log`; явные пользовательские политики пропущены |
| Ошибка синтаксиса/импорта (соглашение) | Ошибка записана; этот файл пропущен, другие файлы соглашений всё ещё загружаются |
| `fn` выбрасывает во время выполнения | Ошибка записана; этот хук обрабатывается как `allow`; другие хуки продолжают |
| `fn` дольше 10s | Тайм-аут записан; обработано как `allow` |
| Каталог соглашений отсутствует | Никакие политики соглашений не запускаются; нет ошибки |

<Tip>
Для отладки ошибок пользовательских политик следите за файлом лога:

```bash
tail -f ~/.failproofai/hook.log
```
</Tip>

## Полный пример: несколько политик

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

// Предотвратить запись агента в каталог secrets/
customPolicies.add({
  name: "block-secrets-dir",
  description: "Prevent agent from writing to secrets/ directory",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("secrets/")) return deny("Writing to secrets/ is not permitted");
    return allow();
  },
});

// Держать агента на курсе: проверить тесты перед фиксацией
customPolicies.add({
  name: "remind-test-before-commit",
  description: "Keep the agent on track: verify tests pass before committing",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    if (/git\s+commit/.test(cmd)) {
      return instruct("Verify all tests pass before committing. Run `bun test` if you haven't already.");
    }
    return allow();
  },
});

// Предотвратить непредвиденные изменения зависимостей во время заморозки
customPolicies.add({
  name: "dependency-freeze",
  description: "Prevent unplanned dependency changes during freeze period",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    const isInstall = /^(npm install|yarn add|bun add|pnpm add)\s+\S/.test(cmd);
    if (isInstall && process.env.DEPENDENCY_FREEZE === "1") {
      return deny("Package installs are frozen. Unset DEPENDENCY_FREEZE to allow.");
    }
    return allow();
  },
});

export { customPolicies };
```

## Примеры

Каталог `examples/` содержит готовые к запуску файлы политик:

| Файл | Содержимое |
|------|-----------|
| `examples/policies-basic.js` | Пять стартовых политик, охватывающих общие режимы отказа агента |
| `examples/policies-advanced/index.js` | Продвинутые паттерны: переходящие импорты, асинхронные вызовы, отчистка выходных данных и хуки конца сессии |
| `examples/convention-policies/security-policies.mjs` | Политики безопасности на основе соглашений (блокировка записей .env, предотвращение переписывания истории git) |
| `examples/convention-policies/workflow-policies.mjs` | Политики рабочих процессов на основе соглашений (напоминания о тестах, аудит записей файлов) |

### Использование примеров явных файлов

```bash
failproofai policies --install --custom ./examples/policies-basic.js
```

### Использование примеров на основе соглашений

```bash
# Скопировать на уровень проекта
mkdir -p .failproofai/policies
cp examples/convention-policies/*.mjs .failproofai/policies/

# Или скопировать на личный уровень
mkdir -p ~/.failproofai/policies
cp examples/convention-policies/*.mjs ~/.failproofai/policies/
```

Команда install не требуется — файлы автоматически загружаются при следующем событии хука.
