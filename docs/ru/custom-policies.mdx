Пользовательские политики позволяют вам писать правила для любого поведения агента: обеспечивать соглашения проекта, предотвращать дрейф, блокировать деструктивные операции, выявлять застрявшие агенты или интегрироваться с Slack, потоками одобрения и многим другим. Они используют ту же систему событий хука и решения `allow`, `deny`, `instruct`, что и встроенные политики.

---

## Быстрый пример

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

customPolicies.add({
  name: "no-production-writes",
  description: "Block writes to paths containing 'production'",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Write" && ctx.toolName !== "Edit") return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("production")) {
      return deny("Writes to production paths are blocked");
    }
    return allow();
  },
});
```

Установите её:

```bash
failproofai policies --install --custom ./my-policies.js
```

## Два способа загрузки пользовательских политик

### Вариант 1: На основе соглашений (рекомендуется)

Поместите файлы `*policies.{js,mjs,ts}` в `.failproofai/policies/` и они будут автоматически загружены — не требуются никакие флаги или изменения конфигурации. Это работает как git hooks: положите файл, и всё работает.

```
# Уровень проекта — зафиксировано в git, общее для команды
.failproofai/policies/security-policies.mjs
.failproofai/policies/workflow-policies.mjs

# Уровень пользователя — личное, применяется ко всем проектам
~/.failproofai/policies/my-policies.mjs
```

**Как это работает:**
- Сканируются оба каталога (объединение — не первый диапазон побеждает)
- Файлы загружаются в алфавитном порядке в каждом каталоге. Используйте префиксы `01-`, `02-` для управления порядком
- Загружаются только файлы, соответствующие `*policies.{js,mjs,ts}`; остальные файлы игнорируются
- Каждый файл загружается независимо (fail-open для каждого файла)
- Работает вместе с явными флагами `--custom` и встроенными политиками

<Tip>
Политики по соглашению — это самый простой способ построить стандарт качества для вашей организации. Зафиксируйте `.failproofai/policies/` в git и каждый член команды получит одни и те же правила автоматически — никакой настройки для каждого разработчика не требуется. По мере того, как ваша команда обнаруживает новые режимы отказа, добавьте политику и отправьте. Со временем они становятся живым стандартом качества, который постоянно улучшается с каждым вкладом.
</Tip>

### Вариант 2: Явный путь к файлу

```bash
# Установка с файлом пользовательских политик
failproofai policies --install --custom ./my-policies.js

# Замена путей пользовательских политик
failproofai policies --install --custom ./new-policies.js

# Конфигурирование нескольких явных файлов (загружаются в порядке флагов)
failproofai policies --install --custom ./security.js --custom ./workflow.js

# Удаление всех явных путей пользовательских политик из конфигурации
failproofai policies --uninstall --custom
```

Разрешённые абсолютные пути хранятся в `policies-config.json` как `customPoliciesPaths`. Повторите `--custom` для конфигурирования нескольких файлов. Существующие конфигурации, использующие устаревшее поле `customPoliciesPath`, продолжают работать. Файлы загружаются заново при каждом событии хука — кеширования между событиями нет.

Каждая зарегистрированная политика отображается с собственным переключателем на панели управления. Выключение политики записывает её источник-квалифицированный ID в `disabledCustomPolicies`; файл и его другие политики продолжают загружаться, а отключённая политика исключается перед сопоставлением событий. Политики с дублирующимися именами в разных файлах имеют независимые переключатели.

### Использование обоих вместе

Политики по соглашению и явные файлы `--custom` могут сосуществовать. Порядок загрузки:

1. Файлы явных `customPoliciesPaths` (в настроенном порядке)
2. Файлы проекта по соглашению (`{cwd}/.failproofai/policies/`, в алфавитном порядке)
3. Файлы пользователя по соглашению (`~/.failproofai/policies/`, в алфавитном порядке)

## API

### Импорт

```js
import { customPolicies, allow, deny, instruct } from "failproofai";
```

### `customPolicies.add(hook)`

Регистрирует политику. Вызывайте столько раз, сколько нужно, для нескольких политик в одном файле.

```ts
customPolicies.add({
  name: string;                         // required - unique identifier
  description?: string;                 // shown in `failproofai policies` output
  match?: { events?: HookEventType[] }; // filter by event type; omit to match all
  fn: (ctx: PolicyContext) => PolicyResult | Promise<PolicyResult>;
});
```

### Помощники решений

| Функция | Эффект | Используйте когда |
|----------|--------|----------|
| `allow()` | Разрешить операцию молча | Действие безопасно, сообщение не требуется |
| `deny(message)` | Заблокировать операцию | Агент не должен выполнять это действие |
| `instruct(message)` | Добавить контекст без блокирования | Дать агенту дополнительный контекст для правильного выполнения |

`deny(message)` — сообщение появляется Claude с префиксом `"Blocked by failproofai:"`. Один `deny` прерывает все дальнейшие оценки.

`instruct(message)` — сообщение добавляется в контекст Claude для текущего вызова инструмента. Все сообщения `instruct` накапливаются и доставляются вместе.

<Tip>
Вы можете добавить дополнительное руководство к любому сообщению `deny` или `instruct`, добавив поле `hint` в `policyParams` — никаких изменений кода не требуется. Это работает для пользовательских (`custom/`), проектных по соглашению (`.failproofai-project/`) и пользовательских по соглашению (`.failproofai-user/`) политик. Смотрите [Configuration → hint](/ru/configuration#hint-cross-cutting) для деталей.
</Tip>

### Информационные сообщения allow

`allow(message)` разрешает операцию **и** отправляет информационное сообщение обратно Claude. Сообщение доставляется как `additionalContext` в ответе stdout обработчика хука — тот же механизм, используемый `instruct`, но семантически отличается: это обновление статуса, а не предупреждение.

| Функция | Эффект | Используйте когда |
|----------|--------|----------|
| `allow(message)` | Разрешить и отправить контекст Claude | Подтвердить прохождение проверки или объяснить, почему проверка была пропущена |

Примеры использования:
- **Подтверждения статуса:** `allow("All CI checks passed.")` — сообщает Claude, что всё зелёно
- **Fail-open объяснения:** `allow("GitHub CLI not installed, skipping CI check.")` — сообщает Claude, почему проверка была пропущена, чтобы оно имело полный контекст
- **Несколько сообщений накапливаются:** если несколько политик каждая возвращает `allow(message)`, все сообщения объединяются с разрывами строк и доставляются вместе

```js
customPolicies.add({
  name: "confirm-branch-status",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow("No working directory, skipping branch check.");

    // ... check branch status ...
    if (allPushed) {
      return allow("Branch is up to date with remote.");
    }
    return deny("Unpushed changes detected.");
  },
});
```

### Поля `PolicyContext`

| Поле | Тип | Описание |
|-------|------|-------------|
| `eventType` | `string` | `"PreToolUse"`, `"PostToolUse"`, `"Notification"`, `"Stop"` |
| `toolName` | `string \| undefined` | Вызываемый инструмент (напр. `"Bash"`, `"Write"`, `"Read"`) |
| `toolInput` | `Record<string, unknown> \| undefined` | Параметры входа инструмента |
| `payload` | `Record<string, unknown>` | Полный исходный payload события от Claude Code |
| `session` | `SessionMetadata \| undefined` | Контекст сессии (см. ниже) |

### Поля `SessionMetadata`

| Поле | Тип | Описание |
|-------|------|-------------|
| `sessionId` | `string` | Идентификатор сессии Claude Code |
| `cwd` | `string` | Рабочий каталог сессии Claude Code |
| `transcriptPath` | `string` | Путь к файлу стенограммы JSONL сессии |

### Типы событий

| Событие | Когда оно запускается | Содержимое `toolInput` |
|-------|--------------|----------------------|
| `PreToolUse` | Перед запуском инструмента Claude | Вход инструмента (напр. `{ command: "..." }` для Bash) |
| `PostToolUse` | После завершения инструмента | Вход инструмента + `tool_result` (вывод) |
| `Notification` | Когда Claude отправляет уведомление | `{ message: "...", notification_type: "idle" \| "permission_prompt" \| ... }` - хуки должны всегда возвращать `allow()`, они не могут блокировать уведомления |
| `Stop` | Когда сессия Claude завершается | Пусто |

## Порядок оценки

Политики оцениваются в этом порядке:

1. Встроенные политики (в порядке определения)
2. Явные пользовательские политики из `customPoliciesPath` (в порядке `.add()`)
3. Политики по соглашению из проекта `.failproofai/policies/` (файлы в алфавитном порядке, `.add()` внутри)
4. Политики по соглашению из пользователя `~/.failproofai/policies/` (файлы в алфавитном порядке, `.add()` внутри)

<Note>
Первый `deny` прерывает все последующие политики. Все сообщения `instruct` накапливаются и доставляются вместе.
</Note>

## Транзитивные импорты

Файлы пользовательских политик могут импортировать локальные модули, используя относительные пути:

```js
// my-policies.js
import { isBlockedPath } from "./utils.js";
import { checkApproval } from "./approval-client.js";

customPolicies.add({
  name: "approval-gate",
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const approved = await checkApproval(ctx.toolInput?.command, ctx.session?.sessionId);
    return approved ? allow() : deny("Approval required for this command");
  },
});
```

Все относительные импорты, доступные из входного файла, разрешаются. Это реализовано путём переписывания импортов `from "failproofai"` на фактический путь dist и создания временных файлов `.mjs` для обеспечения совместимости ESM.

## Фильтрация по типу события

Используйте `match.events` для ограничения срабатывания политики:

```js
customPolicies.add({
  name: "require-summary-on-stop",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    // Срабатывает только когда сессия завершается
    // ctx.session.transcriptPath содержит полный журнал сессии
    return allow();
  },
});
```

Опустите `match` полностью, чтобы срабатывать при каждом типе события.

## Обработка ошибок и режимы отказа

Пользовательские политики — **fail-open**: ошибки никогда не блокируют встроенные политики и не приводят к сбою обработчика хука.

| Сбой | Поведение |
|---------|----------|
| `customPoliciesPath` не установлен | Явные пользовательские политики не запускаются; политики по соглашению и встроенные продолжают нормально |
| Файл не найден | Предупреждение логировано в `~/.failproofai/hook.log`; встроенные продолжают |
| Ошибка синтаксиса/импорта (явная) | Ошибка логирована в `~/.failproofai/hook.log`; явные пользовательские политики пропущены |
| Ошибка синтаксиса/импорта (по соглашению) | Ошибка логирована; тот файл пропущен, другие файлы по соглашению всё ещё загружаются |
| `fn` выбрасывает во время выполнения | Ошибка логирована; тот хук рассматривается как `allow`; другие хуки продолжают |
| `fn` занимает более 10s | Timeout логирован; рассматривается как `allow` |
| Каталог по соглашению отсутствует | Политики по соглашению не запускаются; нет ошибки |

<Tip>
Для отладки ошибок пользовательской политики просмотрите файл журнала:

```bash
tail -f ~/.failproofai/hook.log
```
</Tip>

## Полный пример: несколько политик

```js
// my-policies.js
import { customPolicies, allow, deny, instruct } from "failproofai";

// Prevent agent from writing to secrets/ directory
customPolicies.add({
  name: "block-secrets-dir",
  description: "Prevent agent from writing to secrets/ directory",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();
    const path = ctx.toolInput?.file_path ?? "";
    if (path.includes("secrets/")) return deny("Writing to secrets/ is not permitted");
    return allow();
  },
});

// Keep the agent on track: verify tests before committing
customPolicies.add({
  name: "remind-test-before-commit",
  description: "Keep the agent on track: verify tests pass before committing",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    if (/git\s+commit/.test(cmd)) {
      return instruct("Verify all tests pass before committing. Run `bun test` if you haven't already.");
    }
    return allow();
  },
});

// Prevent unplanned dependency changes during freeze
customPolicies.add({
  name: "dependency-freeze",
  description: "Prevent unplanned dependency changes during freeze period",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();
    const cmd = ctx.toolInput?.command ?? "";
    const isInstall = /^(npm install|yarn add|bun add|pnpm add)\s+\S/.test(cmd);
    if (isInstall && process.env.DEPENDENCY_FREEZE === "1") {
      return deny("Package installs are frozen. Unset DEPENDENCY_FREEZE to allow.");
    }
    return allow();
  },
});

export { customPolicies };
```

## Примеры

Каталог `examples/` содержит готовые файлы политик:

| Файл | Содержимое |
|------|----------|
| `examples/policies-basic.js` | Пять стартовых политик, охватывающих общие режимы отказа агента |
| `examples/policies-advanced/index.js` | Продвинутые паттерны: транзитивные импорты, асинхронные вызовы, скрубинг вывода и хуки конца сессии |
| `examples/convention-policies/security-policies.mjs` | Политики безопасности по соглашению (блокировка записей .env, предотвращение переписывания истории git) |
| `examples/convention-policies/workflow-policies.mjs` | Политики рабочего процесса по соглашению (напоминания о тестах, аудит записей файлов) |

### Использование примеров явных файлов

```bash
failproofai policies --install --custom ./examples/policies-basic.js
```

### Использование примеров на основе соглашений

```bash
# Copy to project level
mkdir -p .failproofai/policies
cp examples/convention-policies/*.mjs .failproofai/policies/

# Or copy to user level
mkdir -p ~/.failproofai/policies
cp examples/convention-policies/*.mjs ~/.failproofai/policies/
```

Команда установки не требуется — файлы автоматически загружаются при следующем событии хука.
