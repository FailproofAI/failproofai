Проверьте [встроенный каталог](/ru/policies/builtin-catalog) перед написанием политики. Проверенное правило обычно безопаснее нового.

## Начните с работающей политики

```bash
failproofai publish --init guards.mjs
failproofai policies -i -c ./guards.mjs
```

Стартовый блок блокирует `git push --force`. Отредактируйте его, попросите своего агента попробовать заблокированное действие и проверьте **Policies → Activity**.

```js
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "protect-production",
  description: "Production changes need a human",
  match: { events: ["PreToolUse"], toolNames: ["Bash"] },
  fn: async (ctx) =>
    String(ctx.toolInput?.command ?? "").includes("production")
      ? deny("Ask a human before changing production.")
      : allow(),
});
```

Политика возвращает `allow()`, `deny(message)` или `instruct(message)`. Используйте `deny`, когда действие должно остановиться; не все системы могут доставить инструкцию обратно агенту.

## Автоматическая загрузка

Поместите файлы с именами `*policies.js`, `*policies.mjs` или `*policies.ts` в:

- `.failproofai/policies/` для одного проекта.
- `~/.failproofai/policies/` для вашего пользователя.

## Тестирование путей отказа

Протестируйте как небезопасное действие, так и легитимную работу, которая выглядит похоже. Убедитесь, что решение исходит от вашей политики, а не от другого правила.

Удалите явные тестовые файлы с помощью:

```bash
failproofai policies -u -c
```

Когда политика готова, [опубликуйте пакет](/ru/policies/publish-a-pack) или [разверните его через Cloud](/ru/policies/deploy).
