Развёртывание размещает опубликованные версии политик на машине, каждая с одним из двух эффектов:

- **Observe** записывает то, что сделала бы политика, и ничего не блокирует.
- **Enforce** применяет решение: `deny` блокирует вызов, а `instruct` направляет агента.

## Добавить машину

Машина появляется в разделе **Admin → enforcement** после подключения к Cloud. Если нужная вам машина там ещё не появилась:

<Tabs>
  <Tab title="Dashboard">
    1. Перейдите в **Administration → Keys** и создайте ключ с правами `policies:pull`, чтобы машина могла получать развёртывания, и `events:add`, чтобы её решения попадали в Cloud.
    2. Подключите машину с этим ключом — [Connect a machine to Cloud](/ru/start/setup#connect-a-machine-to-cloud) покажет как это сделать.
    3. Убедитесь, что машина появилась в разделе **Admin → enforcement**.
  </Tab>
  <Tab title="CLI">
    На машине:

    ```bash
    npm install -g failproofai
    failproofai config
    failproofai config --status
    ```

    В терминале `failproofai config` спросит, подключиться ли к Cloud, и предложит ввести ключ в скрытом поле ввода. Затем убедитесь, что машина зарегистрирована, выполнив команду `fp fleet list` с любой машины.
  </Tab>
</Tabs>

## Развернуть в режиме наблюдения

<Tabs>
  <Tab title="Dashboard">
    1. Перейдите в **Admin → enforcement**, найдите машину и разверните её строку.
    2. Выберите **edit**, добавьте протестированную версию политики и выберите **observe**.
    3. Примените изменение, дождитесь следующего подключения машины и убедитесь в её развёртывании и состоянии покрытия.
    4. Перейдите в **Observe → policy**, чтобы проверить решения в реальном времени.

    ![Редактор развёртывания машины с версиями политик, эффектами enforce и observe, и действием применения развёртывания.](/images/dashboard/enforcement-editor.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp fleet list
    fp fleet show <machine-id>
    fp fleet deploy <machine-id> --add no-force-push:observe
    ```

    Суффикс `:observe` делает его режимом наблюдения: простая команда `--add no-force-push` сохраняет эффект, который машина уже использует для этой политики, в остальных случаях применяется enforce. Позже переключитесь на enforce с помощью `--add no-force-push:enforce`.

    `deploy` **заменяет весь набор политик машины** на полученный результат. Команда выводит план, затем запрашивает подтверждение — но только в интерактивном терминале. При использовании `--yes`, `fp --json` или при перенаправлении stdin (шаг CI, скрипт, агент с shell) применяется без подтверждения; план всё равно выводится или возвращается как `plan` при `--json`.

    На машине `failproofai policies` выводит управляемые Cloud политики, которые она запускает, а `failproofai config --status` показывает её соединение. Используйте `fp sessions --env production --since 24h` и `fp events --event-type hook_completed`, чтобы убедиться, что её деятельность достигает Cloud.
  </Tab>
</Tabs>

<Steps>
  <Step title="Выберите версию и машины">
    Выберите опубликованную версию и машины, на которых она должна работать.
  </Step>
  <Step title="Наблюдение">
    Просмотрите совпадения, причины, затронутые инструменты и ложные срабатывания, пока ничего не блокируется.
  </Step>
  <Step title="Применение">
    Переключитесь на enforce, когда наблюдаемые совпадения чётко разделяют небезопасные действия от допустимых, затем подтвердите, что все нужные машины получили изменение и сообщают о своих решениях.
  </Step>
</Steps>

## Направить агента на машину

Опубликованные версии политик не содержат правила маршрутизации агентов. По умолчанию назначение применяется ко **всем агентам на машине**. При развёртывании версии вы можете вместо этого выбрать интеграцию (включая профили, добавленные позже) или конкретный профиль, о котором сообщила машина. Выбор принадлежит назначению машины: одну опубликованную версию можно использовать для разных агентов на разных машинах.

<Tabs>
  <Tab title="Dashboard">
    1. В разделе **Admin → enforcement** разверните машину и выберите **edit**.
    2. В элементе управления **agents** политики выберите **all agents**, **all hermes profiles** (например) или найдите профиль по его метке и ID `agt_`. Вы можете выбрать несколько вариантов; вызов совпадает, если принадлежит хотя бы одному из них.
    3. Просмотрите цель, указанную для **каждого** назначения в плане развёртывания, примените изменение, затем проверьте сообщённое машиной развёртывание после её следующего подключения. История и откат сохраняют выбранные цели.
  </Tab>
  <Tab title="CLI">
    ```bash
    fp fleet show <machine-id>
    fp fleet deploy <machine-id> --add no-force-push --target no-force-push=hermes
    fp fleet deploy <machine-id> --target no-force-push=hermes/agt_1234567890abcdef
    fp fleet deploy <machine-id> --all-agents no-force-push
    ```

    `--target POLICY=INTEGRATION[/agt_ID]` устанавливает область действия одной политики. Повторите `--target` для большего количества вариантов в одном назначении. Используйте `--all-agents POLICY`, чтобы очистить целевое назначение. `fp fleet show` и `fp fleet history` отображают выбранную область. Просмотрите полный план замены перед применением, особенно при развёртывании из скрипта.
  </Tab>
</Tabs>

Машина должна недавно сообщить о поддержке целевого назначения агентов, прежде чем вы сможете установить новую цель. Вы можете выбрать точный профиль, только если машина сообщила о нём с установленным hook и он не устаревший. Если инвентарь временно недоступен, существующие цели остаются назначены; они не будут молча расширены на всех агентов. Переустановите старые shell hooks, чтобы предоставить подсказку профиля, используемую новыми установками. После обновления CLI запустите `failproofai config`, чтобы обновить и перезагрузить его daemon: старый daemon не может оценивать новые вызовы в области профиля, и hook отказывает при несовпадении. Если профиль запущенного агента не может быть определён (например, когда установлены несколько областей параметров, но hook не сообщает, какая из них работает), **целевые назначения не совпадают**; политики без области действия всё ещё применяются. Ищите `agent_scope_unresolved` в ошибках политики этой машины.

Машина сообщает только об агентах, которых она отслеживает: по одной записи для каждого профиля, конфигурация которого содержит hook FailproofAI (Hermes и OpenClaw получают по одной на профиль, названному по его метке). Просто установленный agent CLI не указывается.

Каждая машина хранит до 256 профилей в своём реестре. ID профиля не меняется, пока он указан. Когда реестр заполнен и появляется новый профиль с hook FailproofAI (его hook запускается или его конфиг содержит hook), daemon освобождает место, удаляя один профиль, который отвечает всем этим условиям:

- на нём не установлен hook;
- ни одно назначение его не называет;
- FailproofAI Cloud не примет его в качестве новой цели.

Daemon отдаёт предпочтение профилю, который больше не найден на машине, затем самому неиспользуемому. Он никогда не удаляет профиль, который использует точная цель, поэтому такие цели остаются действительными. Если ни один профиль не может быть удалён, новый профиль ещё не имеет ID, и целевые назначения не совпадают с ним, пока не освободится место.

## Развернуть проверки Jev

Cloud политика может содержать проверки Jev вместе с JavaScript или вместо него. Её тип — `jev` (только проверки Jev) или `both` (JavaScript, чей вердикт могут очистить его собственные проверки). Она развёртывается, переключается и откатывается точно так же, как любая другая политика.

Проверки Jev работают на FailproofAI Cloud; на машине ничего не устанавливается. Машина получает только JavaScript политики `both`. Когда политика `jev` или `both` развёрнута на машине, FailproofAI Cloud включает Jev для машины, и каждый проверяемый вызов инструмента агента, который использует политика, отправляется на FailproofAI Cloud, которая запрашивает развёрнутые проверки для этого агента и возвращает их вердикт. Если не развёрнута ни одна, Jev выключен. Нет режима Jev, который можно установить вручную.

```bash
fp policies publish prod-db-intent --kind jev --semantic ./checks.json
fp fleet deploy <machine-id> --add prod-db-intent:observe
```

Чтобы испытать проверки Jev без их применения, развёрнуть политику с `:observe`: её проверки запрашиваются и их ответы записываются как "would have", и они ничего не блокируют и не очищают. Переразверните как `enforce`, когда страница политики покажет, что бы они сделали; тогда проверки Jev **блокируют** вызовы и очищают JavaScript вердикты, которые они проверяют. Политика `both`, развёрнутая с `:observe`, наблюдает обе части.

JavaScript политики `both` может быть очищен только ответами её собственных проверок из FailproofAI Cloud. Проверка установленного пакета с тем же именем никогда его не очищает. Если FailproofAI Cloud недостижима или не устанавливает режим, который запрашивает, политика остаётся **hard**: каждый deny её JavaScript стоит.

Целевое назначение агентов работает и для политик только Jev. Для политики `both` цель назначения управляет **обоими** её локальным JavaScript и её Cloud Jev проверками; вызов вне этой цели не выполняет ни одну часть. Оставьте политику в состоянии `observe` при испытании областных проверок, как вы бы это делали для развёртывания Jev без области действия.

Машина сообщает, что препятствует ей в запросе, и `fp fleet show <machine-id>` выводит это в ошибках политики:

- `transcripts_disabled`: машина была подключена с `--no-transcripts`. Такая машина никогда не отправляет вызовы инструментов в Jev.
- `jev_unconfigured`: ключ машины не содержит Jev.
- `jev_rate_limited`: некоторые вызовы были отклонены из-за лимита Jev организации и решены только политиками regex.
- `jev_unavailable`: Jev FailproofAI Cloud не выполнил несколько вызовов подряд, поэтому машина пропускает его на минуту за раз.

Один Jev запрос несёт ограниченное количество текста вопроса. Проверки FailproofAI Cloud идут впереди проверок пакетов, установленных на машине. Проверка пакета, которая не поместилась, опускается и сообщается как `jev_budget`. Проверка пакета с тем же именем, что и одна из проверок Cloud вашей организации, также опускается и сообщается как `jev_name_clash`: вместо неё запрашивается проверка Cloud.

## Проверить покрытие

Покрытие показывает, работает ли политика где находится риск.

1. Перейдите в **Admin → enforcement** и просмотрите итоги применения и наблюдения.
2. Найдите машину по ID или метке, или отфильтруйте машины, на которых отсутствует политика.
3. Разверните строку, чтобы сравнить назначенные политики, сообщённое развёртывание, последнее подключение и историю.
4. Обновите страницу через интервал опроса машины, если примененное развёртывание ещё ожидает.

![Флот Enforcement, показывающий покрытие политик, состояние развёртывания машины и назначения observe и enforce.](/images/dashboard/enforcement-fleet.png)

Ищите машины, которые никогда не получали последнее развёртывание, зарегистрированные машины, которые перестали сообщать, политику, назначенную неправильной среде, и дрейф версии после прерванного обновления.

Обозначьте машины по рабочей нагрузке и среде — только имена хостов редко сохраняются при автомасштабировании или замене:

```bash
failproofai config --machine-label checkout-runner-03
```

<Warning>
  Управление применением — это административный рабочий процесс Cloud. Не обращайтесь с маршрутами enforcement, доступными только для root, как с обычными конечными точками `/v1` API для клиентов.
</Warning>
