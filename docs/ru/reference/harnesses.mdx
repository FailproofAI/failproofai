Привязка — это среда, в которой фактически работает ваш агент. Failproof AI поддерживает двенадцать из них, разделённых на два класса:

- **Coding CLIs** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Chat и assistant gateways** (2) — Hermes (Slack, Telegram, cron), OpenClaw (self-hosted assistant)

Одни и те же политики и одна и та же история сессии применяются независимо от того, в какой из двенадцати сред работает агент. Один адаптер преобразует собственные названия событий, имена инструментов и поля входных данных каждой привязки в 29 канонических событий до выполнения любой политики.

Агент, работающий **ни в одной** из двенадцати привязок, может быть инструментирован напрямую с помощью [Python SDK](/ru/reference/custom-agents). Это иной контракт, и стоит это сказать открыто: SDK предоставляет трассировку, сессии, оценки и аудиты — **он не применяет политики самостоятельно.** Блокирование небезопасного действия перед его выполнением требует hook-а применения на границе инструмента вашей runtime-среды; [свяжитесь с нами](mailto:support@befailproof.ai) и мы его реализуем.

| Привязка | Поддерживаемые scopes hook-ов |
| --- | --- |
| Claude Code | User, project, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | User, project |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | User, project |
| Hermes, OpenClaw | User |

Каждая интеграция нормализует собственные названия hook-событий, имена инструментов и поля входных данных инструментов перед выполнением политик. Политика может действовать только на события, которые предоставляет привязка; протестируйте поведение конца хода и инструкции на точной привязке и версии, которые вы развёртываете.

## Возможность применения

«Block» означает, что вердикт, возвращённый текущим адаптером, обрабатывается названной привязкой. Блокирование после инструмента может заменить результат, показанный модели, но не может отменить побочный эффект инструмента, который уже произошёл.

| Привязка | Проверенные события блокирования | Оговорки наблюдения или отсутствия блокирования |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact` и несколько событий задач/конфигурации | `PostToolUse`, жизненный цикл сессии, уведомления и события после сбоя являются наблюдаемыми. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Блокирование после инструмента заменяет результат после выполнения; события начала сессии и компактирования являются наблюдаемыми в текущем адаптере. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Блокирование после инструмента заменяет результат после выполнения; события сессии и уведомлений являются наблюдаемыми. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` и события сессии являются наблюдаемыми. |
| OpenCode | `PreToolUse` | События после инструмента и жизненного цикла являются наблюдаемыми; текущая обработка остановки — это указание для последующего хода, а не проверенные ворота. |
| Pi | `PreToolUse`, `UserPromptSubmit` | События после инструмента и жизненного цикла являются наблюдаемыми; указание остановки применяется к последующему ходу. |
| Hermes | `PreToolUse` | `deny()` блокирует. `instruct()` не останавливает вызов: он выполняется, и указание размещается в начале его результата. Вердикты после инструмента, сессии и остановки субагента не являются воротами. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | События после инструмента, сессии, остановки субагента и компактирования являются наблюдаемыми. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Вердикты после инструмента и остановки субагента являются наблюдаемыми. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, условный `PermissionRequest` | Hook-и разрешений работают не во всех режимах разрешений; события после инструмента и сессии являются наблюдаемыми. |
| Antigravity CLI | `PreToolUse`, `Stop` | Вердикты приглашения пользователя и после инструмента являются наблюдаемыми; инструкции приглашения по-прежнему можно внедрить. |
| Goose | `PreToolUse` | События приглашения пользователя, после инструмента и сессии являются наблюдаемыми. Собственный hook блокирования остановки существует выше по течению, но не устанавливается текущим адаптером. |

Возможности зависят от версии. Перетестируйте после обновления CLI агента, особенно если политика опирается на поведение приглашения, остановки, разрешения или события после инструмента, а не на общие ворота перед инструментом.

### Собственный плагин Hermes

Hermes интегрируется через собственный плагин на уровне профиля, а не команду shell. Установка связывает каждый профиль Hermes по умолчанию и именованные `plugins/failproofai` с плагином, поставляемым в npm-пакете (копия там, где невозможно создать symlink), включает его в `config.yaml` этого профиля и переносит только устаревшие записи shell-hook FailproofAI. Так как плагин связан, `npm install -g failproofai@latest` обновляет его без переустановки. Это избегает spawn-а процесса на каждом hook-е. Плагин поддерживает Hermes 0.20.0 и позже.

Устаревшие shell-hook-и (установленные 1.0.5 и ранее) **не** проверяют cron-задачи Hermes: каждый запуск cron строит свой собственный scope hook-а, который собственный плагин объединяет, а shell-hook-и в `config.yaml` не объединяют. `failproofai update` переносит каждый профиль, который уже использует FailproofAI, на связанный плагин. Если работающий daemon не может обслуживать плагин, `update` оставляет shell-hook-и на месте и выходит с ненулевым кодом; выполните `failproofai config` для обновления daemon-а, затем `failproofai update` снова. Cron-задачи загружают плагин при своём следующем запуске; перезагрузите работающие gateway-и и интерактивные сессии для загрузки плагина там.

На Hermes `deny()` блокирует вызов, а `instruct()` нет: вызов выполняется, и указание размещается в начале его результата — как первый ключ `failproof_policy_reminder` JSON-результата или как первая строка `[FailproofAI policy reminder (...)]` — так модель читает его вместе с выводом, и скрипты, которые разбирают результат, продолжают работать. Напоминание о политике отображается один раз за ход и остаётся кратким на больших результатах. Используйте `deny()` когда действие вообще не должно происходить: `instruct()` больше не останавливает действие в первую очередь. Вызовы инструментов из скрипта `execute_code` помещают своё напоминание на результат `execute_code`, который читает модель; собственная копия результата скрипта остаётся нетронутой. Модели говорят никогда не цитировать напоминание в своих ответах.

Сборка Hermes без middleware плагина откатывается к удержанию соответствующего вызова один раз с помощью «FailproofAI policy guidance»; следующий ответ модели может повторить его или сделать ту же работу с другим инструментом без повторного удержания.

Имена инструментов совпадают между версиями Hermes: `process_manage`, `cronjob_manage` и `todo_list` (Hermes 0.21) рассматриваются как `process`, `cronjob` и `todo` (Hermes 0.20). Каждый раз, когда Hermes загружает плагин, он записывает `heartbeat.json` в директорию `plugin-data/agent-plugin-failproofai-5296f299/` профиля, записывая версию Hermes, путь и версию плагина и hook-и, которые Hermes принял. Запустите `failproofai config --status` для обнаружения отключённого, неполного, дублированного или вновь некконфигурированного профиля, или того, который всё ещё использует устаревшие shell-hook-и (сообщается как «Hermes cron jobs are not checked»).

### Плагин OpenClaw

OpenClaw загружает FailproofAI как in-process gateway плагин, зарегистрированный в `openclaw.json` каждого профиля. Как и плагин Hermes, он запрашивает локальный daemon `failproofaid` для каждого вердикта через его socket, поэтому ему нужен работающий daemon: установка отказывает без него, и если daemon не может ответить, вызовы инструментов и приглашения блокируются и причина записывается в лог gateway-я. После `npm install -g failproofai@latest` перезагрузите gateway OpenClaw, чтобы он загрузил обновлённый плагин.

### Доверие hook-а Codex

Codex 0.129 и позже запускает hook из `~/.codex/hooks.json` только после того, как вы одобрите его в интерактивном `codex` («Review hooks»); до этого каждая сессия Codex — включая headless `codex exec` — пропускает его. Hook-и в системной конфигурации Codex, `/etc/codex/config.toml` на Linux и macOS, запускаются без этого одобрения.

Таким образом, когда `failproofai config` (или `policies --install --cli codex` в области user) может использовать sudo, он записывает hook-и Codex в `/etc/codex/config.toml`, между `# >>> failproofai managed hooks >>>` и `# <<< failproofai managed hooks <<<`, и оставляет остаток этого файла таким, каким он был.

Этот файл применяется ко всем учётным записям на машине, поэтому каждый hook в нём запускает `/opt/failproofai-codex/codex-hook`, короткий скрипт, владельцем которого является root. Скрипт передаёт событие собственному failproofai каждой учётной записи для каждой учётной записи, которая установила hook-и там, и ничего не делает для любой другой учётной записи. Другая учётная запись, которая хочет hook-и Codex от failproofai, устанавливает их для себя.

Перед записью блока и снова при каждом `failproofai update` failproofai проверяет, что сам `/etc/codex/config.toml`, скрипт, каждая директория выше них и `sh`, `id` и `cat`, которые он запускает, принадлежат root-у и не могут быть записаны кем-либо ещё, и что failproofai каждой учётной записи принадлежит этой учётной записи или root-у. При установке, когда эта проверка не пройдена, ваши hook-и остаются в `~/.codex/hooks.json`. При обновлении скрипт, который её не пройдёт, извлекает блок, и учётная запись, failproofai которой её не пройдёт, извлекается из скрипта; запустите `failproofai config` ещё раз, когда это будет исправлено. `failproofai update` также переписывает блок, написанный ранней версией, для использования скрипта, который требует sudo.

`failproofai uninstall` и снятие галочки с Codex в `failproofai config` извлекают вашу учётную запись снова, и блок с ней, как только не осталось учётных записей.

Без sudo и на Windows hook-и остаются в `~/.codex/hooks.json`. `failproofai config` и `failproofai config --status` тогда не считают Codex применяющим до одобрения hook-ов и говорят, как это исправить: снова запустите `failproofai config` и разрешите sudo, или откройте `codex` один раз и одобрите hook-и.

## Установка capture и policy hook-ов

  <Tab title="Dashboard">
    1. Откройте **settings → api keys** и создайте ключ с разрешениями `events:add` и `policies:pull`, именуемый для машины или окружения.
    2. На целевой машине подключите локальный CLI с отображаемым ключом и установите hook-и привязки.
    3. Запустите новую сессию агента, затем подтвердите её hook-события и события сессии под **trace → live events**.
    4. Откройте **fix → activity** для того же временного окна и подтвердите, что решение о политике отнесено к машине.

    Соединение начинается с машинного ключа. Подтвердите, что он включает оба разрешения приёма и доставки политики перед копированием его секрета.

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    ```

    Удалите путь с `failproofai harness remove-path claude checkout`.
