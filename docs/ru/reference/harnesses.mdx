Адаптер — это то, в чём фактически работает ваш агент. Failproof AI поддерживает двенадцать адаптеров в двух категориях:

- **Кодовые CLI** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Шлюзы чата и ассистентов** (2) — Hermes (Slack, Telegram, cron), OpenClaw (самостоятельно размещённый ассистент)

Одни и те же политики и одна и та же история сеансов применяются независимо от того, в каком адаптере работает агент. Один слой адаптера преобразует названия событий, названия инструментов и поля входных данных каждого адаптера в 29 канонических событий до запуска любой политики.

Агент, который работает **ни в одном** из двенадцати адаптеров, инструментируется напрямую с помощью [Python SDK](/ru/reference/custom-agents). Это другой контракт, и стоит это сказать явно: SDK обеспечивает трассировку, сеансы, оценки и аудиты — **но он не применяет политики самостоятельно.** Для блокирования небезопасного действия перед его выполнением требуется перехват на границе инструмента вашего времени выполнения; [свяжитесь с нами](mailto:support@befailproof.ai) и мы сопоставим его.

| Адаптер | Поддерживаемые области перехватов |
| --- | --- |
| Claude Code | User, project, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | User, project |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | User, project |
| Hermes, OpenClaw | User |

Каждая интеграция нормализует названия событий перехватов, названия инструментов и поля входных данных перед запуском политик. Политика может действовать только на события, которые раскрывает адаптер; тестируйте поведение в конце хода и инструкции на точном адаптере и версии, которые вы развёртываете.

## Возможность применения

Под "блокировкой" подразумевается, что возвращённый вердикт текущего адаптера потребляется названным адаптером. Блокировка после инструмента может заменить результат, показанный модели, но не может отменить побочный эффект инструмента, который уже произошёл.

| Адаптер | Проверенные события блокировки | Ограничения режима наблюдения или отсутствия блокировки |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact` и несколько событий задач/конфигурации | `PostToolUse`, жизненный цикл сеанса, уведомления и события после сбоя являются наблюдательными. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Блокировка после инструмента заменяет результат после выполнения; события запуска сеанса и компактирования являются наблюдательными в текущем адаптере. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Блокировка после инструмента заменяет результат после выполнения; события сеанса и уведомлений являются наблюдательными. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` и события сеанса являются наблюдательными. |
| OpenCode | `PreToolUse` | События после инструмента и жизненного цикла являются наблюдательными; текущая обработка остановки — это руководство на следующий ход, а не проверенный шлюз. |
| Pi | `PreToolUse`, `UserPromptSubmit` | События после инструмента и жизненного цикла являются наблюдательными; руководство по остановке применяется на следующий ход. |
| Hermes | `PreToolUse` | `deny()` блокирует. `instruct()` не останавливает вызов: он выполняется, и руководство помещается в начало его результата. Вердикты после инструмента, сеанса и остановки подагента не являются шлюзами. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | События после инструмента, сеанса, остановки подагента и компактирования являются наблюдательными. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Вердикты после инструмента и остановки подагента являются наблюдательными. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, условный `PermissionRequest` | Перехваты разрешений не запускаются в каждом режиме разрешения; события после инструмента и сеанса являются наблюдательными. |
| Antigravity CLI | `PreToolUse`, `Stop` | Вердикты пользовательского приглашения и после инструмента являются наблюдательными; инструкции приглашения всё ещё можно вводить. |
| Goose | `PreToolUse` | События пользовательского приглашения, после инструмента и сеанса являются наблюдательными. Родной перехват блокировки остановки существует выше по потоку, но не установлен текущим адаптером. |

Возможности чувствительны к версии. Повторно протестируйте после обновления CLI агента, особенно если политика полагается на поведение приглашения, остановки, разрешения или после инструмента, а не на общий предварительный шлюз инструмента.

### Родной плагин Hermes

Hermes интегрирован через плагин, локальный для профиля, а не команду оболочки. Установка связывает `plugins/failproofai` каждого профиля Hermes по умолчанию и именованного с плагином, поставляемым в пакете npm (копия, когда символическая ссылка не может быть создана), включает его в `config.yaml` этого профиля и переносит только устаревшие записи оболочки FailproofAI. Поскольку плагин связан, `npm install -g failproofai@latest` обновляет его без переустановки. Это избегает порождения процесса при каждом перехвате. Плагин поддерживает Hermes 0.20.0 и позже.

Устаревшие перехваты оболочки (установленные в 1.0.5 и раньше) **не** проверяют задачи cron Hermes: каждый запуск cron создаёт свою собственную область перехвата, которую присоединяет родной плагин, и перехваты оболочки `config.yaml` не делают. `failproofai update` переносит каждый профиль, который уже использует FailproofAI, на связанный плагин. Если работающий демон не может обслуживать плагин, `update` оставляет перехваты оболочки на месте и выходит с ненулевым кодом; выполните `failproofai config` для обновления демона, затем снова `failproofai update`. Задачи cron загружают плагин при следующем запуске; перезагрузите работающие шлюзы и интерактивные сеансы для загрузки там.

На Hermes `deny()` блокирует вызов и `instruct()` не блокирует: вызов выполняется, и руководство помещается в начало его результата — как первый ключ, `failproof_policy_reminder`, результата JSON, или как первая строка `[FailproofAI policy reminder (...)]` — так модель читает его вместе с выводом, и скрипты, которые анализируют результат, продолжают работать. Напоминание политики показывается один раз за ход и остаётся кратким при большом результате. Используйте `deny()`, когда действие не должно происходить вообще: `instruct()` больше не останавливает действие в первую очередь. Вызовы инструментов, сделанные из скрипта `execute_code`, помещают своё напоминание на результат `execute_code`, который читает модель; собственная копия результата скрипта остаётся нетронутой. Модели говорят никогда не цитировать напоминание в своих ответах.

Сборка Hermes без промежуточного слоя плагина возвращается к задержке соответствующего вызова один раз с "FailproofAI policy guidance"; следующий ответ модели может повторить его или выполнить ту же работу другим инструментом без повторной задержки.

Названия инструментов сопоставляются в версиях Hermes: `process_manage`, `cronjob_manage` и `todo_list` (Hermes 0.21) рассматриваются как `process`, `cronjob` и `todo` (Hermes 0.20). Каждый раз, когда Hermes загружает плагин, он записывает `heartbeat.json` в директорию профиля `plugin-data/agent-plugin-failproofai-5296f299/`, записывая версию Hermes, путь и версию плагина, а также перехваты, которые Hermes принял. Выполните `failproofai config --status` для обнаружения отключённого, неполного, дублированного или недавно неконфигурированного профиля, или одного, всё ещё на устаревших перехватах оболочки (сообщается как "Hermes cron jobs are not checked").

### Плагин OpenClaw

OpenClaw загружает FailproofAI как плагин шлюза в процессе, зарегистрированный в `openclaw.json` каждого профиля. Как и плагин Hermes, он запрашивает локальный демон `failproofaid` для каждого вердикта по его сокету, поэтому требуется работающий демон: установка отказывает без него, и если демон не может ответить, вызовы инструментов и приглашения блокируются и причина записывается в журнал шлюза. После `npm install -g failproofai@latest` перезагрузите шлюз OpenClaw, чтобы он загрузил обновлённый плагин.

### Доверие перехватов Codex

Codex 0.129 и позже запускает перехват из `~/.codex/hooks.json` только после того, как вы одобрите его в интерактивном `codex` ("Review hooks"); до этого каждый сеанс Codex — включая headless `codex exec` — пропускает его. Перехваты в системном конфиге Codex, `/etc/codex/config.toml` на Linux и macOS, выполняются без этого одобрения.

Поэтому когда `failproofai config` (или `policies --install --cli codex` в области пользователя) может использовать sudo, он записывает перехваты Codex в `/etc/codex/config.toml`, между `# >>> failproofai managed hooks >>>` и `# <<< failproofai managed hooks <<<`, и оставляет остальную часть этого файла как есть. Файл применяется ко всем учётным записям на машине. `failproofai uninstall` и отключение Codex в `failproofai config` удаляют блок снова.

Без sudo и на Windows перехваты остаются в `~/.codex/hooks.json`. `failproofai config` и `failproofai config --status` затем не считают Codex применяющим политики до тех пор, пока перехваты не будут одобрены, и говорят, как это исправить: повторно выполните `failproofai config` и разрешите sudo, или откройте `codex` один раз и одобрите перехваты.

## Установка захвата и перехватов политик

<Tabs>
  <Tab title="Панель управления">
    1. Откройте **Administration → Keys** и создайте ключ с `events:add` и `policies:pull`, названный для машины или окружения.
    2. На целевой машине подключите локальный CLI с отображённым ключом и установите перехваты адаптера.
    3. Запустите новый сеанс агента, затем подтвердите его перехваты и события сеанса в **Observe → Events**.
    4. Откройте **Observe → policy** для того же временного окна и подтвердите, что решение политики приписано машине.

    Подключение начинается с ключа машины. Подтвердите, что он включает разрешения как для приёма, так и для доставки политик перед копированием его секрета.

    ![Ящик создания нового ключа API, используемый для предоставления разрешений приёма событий и доставки политик.](/images/dashboard/key-create.png)

    После установки перехватов поток Events должен показывать новые события с машины и окружения, которые вы подключили.

    ![Живой поток Events, используемый для подтверждения того, что вновь установленный адаптер отправляет отчёты.](/images/dashboard/events-stream.png)

    Наконец, проверьте, что решения политики приписаны той же машине. Это подтверждает, что адаптер отправляет отчёты о действии политики, а также событиях трассировки.

    ![Страница Policy, используемая для проверки решений политики из вновь подключённого адаптера.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Прочитайте ключ машины в оболочку. `read -s` берёт его при приглашении, которое не отражает вводимые данные, поэтому он никогда не появляется в команде или в истории оболочки:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    Затем настройте машину — это подключает перехваты для каждого обнаруженного адаптера, устанавливает демон и подключается к Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    Установка не включает политику самостоятельно, поэтому нужна вторая команда.

    Или ориентируйтесь на именованные адаптеры и область конфигурации:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    Область проекта хранит конфигурацию перехватов с репозиторием. Область пользователя охватывает работу в разных репозиториях. Claude Code также поддерживает локальную область; поддержка варьируется по адаптерам и CLI отклоняет неподдерживаемые комбинации.

    Проверьте машину и её события:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>

## Добавьте путь сеанса не по умолчанию

<Tabs>
  <Tab title="Панель управления">
    Дополнительные пути регистрируются на машине, а не в Cloud. После добавления одного откройте **Observe → Sessions**, отфильтруйте по окружению машины и подтвердите, что сеансы с нового пути появляются. Откройте сеанс и проверьте агента, адаптер и временные метки событий перед использованием его в аудите.

    ![Список Sessions, отфильтрованный по окружению, получающему данные с дополнительного пути захвата.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Добавьте путь с опциональной меткой, затем проверьте настроенные пути:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Удалите путь с `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  Запустите один новый сеанс после установки. Проверьте как живой поток событий, так и фактическое решение политики перед расширением развёртывания.
</Tip>
