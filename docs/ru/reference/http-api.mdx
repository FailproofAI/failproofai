Публичный API доступен по пути `/v1` на исходном адресе вашей панели управления Failproof AI. В облаке Failproof AI Cloud это `https://app.befailproof.ai`, поэтому базовый путь — `https://app.befailproof.ai/v1`. При самостоятельном развертывании это адрес вашего хоста панели управления с добавлением `/v1`; передайте этот адрес в `fp` через `--base-url <url>` или `FP_DASHBOARD_URL`.

## Создайте ключ и сделайте запрос

<Tabs>
  <Tab title="Панель управления">
    1. Откройте **Administration → Keys**, выберите **new key** и выберите самый узкий набор разрешений, который охватывает вашу интеграцию.
    2. Добавляйте отдельные гранты только при необходимости, создайте ключ и скопируйте его одноразовый секрет.
    3. Сделайте тестовый запрос к `/v1/sessions` и убедитесь, что ключ остается активным на странице Keys.
    4. Ротируйте или отключайте ключ из его меню действий, когда интеграция меняет владельца.

    ![Новое окно создания API-ключа с предустановками разрешений и отдельными грантами.](/images/dashboard/key-create.png)

    Выше показано окно создания. Одноразовый секрет появляется только после создания ключа; скопируйте его перед закрытием подтверждения.
  </Tab>
  <Tab title="CLI">
    Создайте ключ для чтения и используйте его непосредственно с `fp` или `curl`. `fp` читает ключ из `--api-key` или из `FP_API_KEY`:

    ```bash
    fp keys create reliability-reader \
      --permission-set read-only

    export FP_API_KEY="<one-time-secret>"
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/sessions?limit=20" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

Ключи привязаны к организации и к плоскому списку разрешений. Набор разрешений только инициализирует этот список при создании — ключ сохраняет развернутые гранты, поэтому изменение набора позже не меняет ключ. Запрос без требуемого для эндпоинта разрешения возвращает `403` и указывает на отсутствующее разрешение.

## Выбор организации

Ключ организации действует на своей организации автоматически. Ключ с областью действия экземпляра выбирает организацию для каждого запроса, и арендатор с более чем одной организацией должен всегда указать одну в режиме ключа — `fp` никогда не отправляет сохраненную организацию при аутентификации с ключом.

| Вызывающая сторона | Как вы указываете организацию |
| --- | --- |
| `fp`, для каждого вызова | `--org <slug>` перед подкомандой |
| `fp`, из переменной окружения | `FP_ORG` |
| Необработанный HTTP | заголовок запроса `X-AgentEye-Org: <slug>` |

`X-AgentEye-Org` сохраняет свое исходное написание при передаче. Это заголовок, который панель управления читает для определения активной организации, и переименование его в клиенте нарушит запрос.

<Tabs>
  <Tab title="Панель управления">
    Используйте переключатель организации в заголовке панели управления перед открытием **Administration → Keys**. Ключи, созданные там, принадлежат выбранной организации. Подтвердите slug организации в URL и деталях ключа перед копированием учетных данных в автоматизацию.

  </Tab>
  <Tab title="CLI">
    Используйте `--org` перед командой или отправьте заголовок организации для ключа API с областью действия экземпляра. `fp orgs list` не обнаружит slug для вас в этом режиме — команда отказывает в режиме ключа; вместо этого прочитайте slug из переключателя организации на панели управления.

    ```bash
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/usage" \
      -H "Authorization: Bearer $FP_API_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

## Пагинация

Эндпоинты со списками используют пагинацию по ключам наборов, и один и тот же контракт применяется, вызываете ли вы их через `fp` или через `curl`.

| Элемент | Значение |
| --- | --- |
| параметр запроса `limit` | Количество строк, запрошенных в этом вызове. `fp` ограничивает один запрос 200 строками на каждом эндпоинте. Необработанный запрос ограничивается собственным потолком сервера вместо этого. |
| параметр запроса `cursor` | Непрозрачный токен, который возобновляет ленту после предыдущей страницы. |
| поле ответа `next_cursor` | Токен для следующей страницы. `null` означает, что лента исчерпана. |

Эти потолки различаются по эндпоинтам, и каждая страница эндпоинта указывает свои собственные значения по умолчанию и максимум:

| Эндпоинт | По умолчанию | Максимум |
| --- | --- | --- |
| `/events`, `/events/summary` | 50 | 1000 |
| `/issues`, `/alerts/{id}/issues` | 200 | 1000 |
| `/evaluation-jobs` | 100 | 500 |
| `/audits/findings` | 100 | 500 |
| `/sessions`, `/evaluations` | 50 | 200 |
| `/audits/{id}/runs` | 50 | 200 |

Читайте полную ленту, повторно отправляя тот же запрос с `cursor`, установленным на `next_cursor` из предыдущего ответа, пока `next_cursor` не вернется как `null`. Эквивалентные флаги `fp` — `--all`, `--cursor` и `--page-size` — описаны в [справочнике Cloud CLI](/ru/reference/cloud-cli).

## Справочник эндпоинтов и обработка ошибок

Используйте сгенерированные страницы эндпоинтов в этом разделе для актуальных путей, параметров, требований разрешений и кодов состояния. Спецификация генерируется из аннотаций маршрутов сервера и проверяется по маршрутизатору `/v1`.

Текущая спецификация имеет полное покрытие маршрутов, методов, параметров, разрешений и кодов состояния. Тела запросов типизированы; тела ответов — нет — спецификация не содержит схемы ответов в настоящее время, так как сервер по-прежнему конструирует их как динамический JSON. Проверьте реальный ответ перед генерацией строго типизированного клиента.

Используйте `Content-Type: application/json` для записей JSON. Рассматривайте `401` как отсутствие или неверную аутентификацию, `403` как действительную идентичность без требуемого разрешения, `404` как отсутствующий или недоступный для организации ресурс, `409` как конфликт состояния, `400` как отклоненный параметр — неизвестное значение фильтра, неправильно сформированный параметр запроса, выражение, которое не будет выполнено — и `422` как неверное поле или значение разрешения в теле запроса. Ответы об ошибках включают понятное для человека сообщение; сбои разрешений также указывают требуемый грант.

## Поверхности, которые `/v1` не поддерживает

Управляемые облаком политики, флот и лента решений guardrail — это операторские поверхности — как чтение, так и запись. Они являются root-only на сервере и намеренно отсутствуют в `/v1`, которая обращена в интернет. Например, публикация версии политики или развертывание ее на машине — это не то, что может сделать API-ключ, и чтение того, что решил флот, находится на той же поверхности.

Поэтому API-ключ получает отказ по дизайну на этих маршрутах, и `fp` отказывает до открытия соединения, а не позволяет запросу получить 404 без объяснений:

| Команда | Поведение под API-ключом |
| --- | --- |
| `fp policies` | Отказывает с кодом выхода `2` и называет управляемые облаком политики операторской поверхностью |
| `fp fleet` | Отказывает с кодом выхода `2` и называет флот операторской поверхностью |
| `fp guardrails` | Отказывает с кодом выхода `2` и называет ленту guardrail операторской поверхностью |
| `fp agent` | Отказывает с кодом выхода `2`; ассистент реализован панелью управления, а не API |
| `fp orgs` | Отказывает с кодом выхода `2`; членство в организации принадлежит авторизованному пользователю, а ключ уже действует для одной организации |

Запускайте эти команды в сеансе авторизованного пользователя (`fp login`) вместо этого или используйте панель управления. Семейства чтения и администрирования — сеансы, события, оценки, аудиты, проблемы, оповещения, ключи, наборы разрешений, пользователи, параметры, запросы и использование — каждое имеет маршрут `/v1` и работает с ключом. Единственный пробел — `fp keys update`: ему требуется `keys:update`, разрешение, которое не может иметь ни один API-ключ, поэтому ключ может создавать и отключать ключи, но никогда не может редактировать разрешения одного. `fp login` и `fp logout` также отказывают в режиме ключа по другой причине: ключ уже является учетными данными, и он никогда не сохраняется на диск.

<Warning>
  Развертывание применения политик намеренно управляется вне обычной публичной поверхности `/v1`. Используйте поддерживаемый рабочий процесс развертывания облака, описанный в [Deploy policies](/ru/policies/deploy).
</Warning>
