Публичный API доступен по пути `/v1` на источнике вашей панели Failproof AI.

## Создание ключа и выполнение запроса

<Tabs>
  <Tab title="Панель управления">
    1. Откройте **Administration → Keys**, выберите **Create key** и выберите наиболее узкий набор разрешений, который охватывает интеграцию.
    2. Добавьте отдельные полномочия только при необходимости, создайте ключ и скопируйте его одноразовый секрет.
    3. Выполните тестовый запрос к `/v1/sessions` и убедитесь, что ключ остаётся активным на странице Keys.
    4. Ротируйте или отключите ключ из его меню действий, когда интеграция меняет владельца.

    ![Новое окно создания ключа API с наборами разрешений и отдельными полномочиями.](/images/dashboard/key-create.png)

    Окно создания показано выше. Одноразовый секрет появляется только после выбора **create**; скопируйте его перед закрытием этого подтверждения.
  </Tab>
  <Tab title="CLI">
    Создайте ключ для чтения и используйте его напрямую с `fp` или `curl`:

    ```bash
    fp keys create reliability-reader \
      --permission-set read-only

    fp --api-key <key> sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/sessions?limit=20" \
      -H "Authorization: Bearer $FAILPROOFAI_KEY"
    ```
  </Tab>
</Tabs>

Ключи привязаны к организации и набору разрешений. Запрос без требуемого разрешения конечной точки возвращает `403` и указывает на недостающее разрешение.

## Выбор организации

Ключ организации действует на свою организацию автоматически. Ключ с областью действия экземпляра может выбирать организацию для каждого запроса:

<Tabs>
  <Tab title="Панель управления">
    Используйте переключатель организации в заголовке панели управления перед открытием **Administration → Keys**. Ключи, созданные там, принадлежат выбранной организации. Подтвердите slug организации в URL и деталях ключа перед копированием учётных данных в автоматизацию.

  </Tab>
  <Tab title="CLI">
    Используйте `--org` перед командой или отправьте заголовок организации для ключа API с областью действия экземпляра.

    ```bash
    fp orgs list
    fp --org reliability-team sessions --since 24h
    ```

    ```bash
    curl "https://app.befailproof.ai/v1/usage" \
      -H "Authorization: Bearer $FAILPROOFAI_KEY" \
      -H "X-AgentEye-Org: reliability-team"
    ```
  </Tab>
</Tabs>

Используйте созданные страницы конечных точек в этом разделе для актуальных путей, параметров, требований разрешений и кодов состояния. Спецификация создана из аннотаций маршрутов сервера и проверена на маршрутизаторе `/v1`.

Текущая спецификация имеет полное покрытие маршрутов, методов, параметров, разрешений и кодов состояния. Некоторые тела ответов намеренно не типизированы, потому что сервер всё ещё строит их как динамический JSON. Проверьте реальный ответ перед созданием строго типизированного клиента для конечной точки без схемы ответа.

Используйте `Content-Type: application/json` для записей JSON. Интерпретируйте `401` как отсутствие или неправильность аутентификации, `403` как действительную идентичность без требуемого разрешения, `404` как отсутствие или недоступность ресурса для организации, `409` как конфликт состояния и `422` как неправильное значение поля или разрешения. Ответы об ошибках включают удобочитаемое сообщение; при отказе в разрешении также указывается требуемое полномочие.

Приём событий использует JSON, разделённый новыми строками: один полный объект в строке. Проверьте
как `accepted`, так и `skipped` в успешном ответе. Повторите весь пакет
после сбоя сети или ответа HTTP 408, 429 или 5xx; повторное воспроизведение одних и тех же
событий безопасно. Исторические пакеты могут охватывать много месяцев. Если приём вернёт `422` с
`error: "event_too_large"`, сократите полезную нагрузку этого события перед повторной попыткой.
Разделение пакета на меньшие запросы не сокращает отдельное событие.
Для импорта файлов повторно используйте исходный предел `existing_before` при повторных попытках, чтобы частично сохранённая сессия могла завершиться.

## Идентификаторы запросов

Каждый ответ содержит заголовок `X-Request-Id`, и каждое тело JSON-ошибки включает то же значение как `request_id`. Цитируйте его при обращении в службу поддержки: он идентифицирует один запрос.

Вы можете отправить собственный `X-Request-Id` для связи запроса с вашими журналами. Используйте 32 строчных шестнадцатеричных символа, например UUID v4 с удалённым дефисом. Любое другое значение заменяется на новый идентификатор, который возвращается в ответе.

<Warning>
  Развёртывание обеспечения политик намеренно управляется вне обычной публичной поверхности `/v1`. Используйте поддерживаемый рабочий процесс развёртывания в облаке.
</Warning>
