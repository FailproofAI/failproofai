Это справочник маршрута Cloud для [политик Jev](/ru/policies/jev). Jev, классификатор TypeSafe, проверяет каждый вызов инструмента относительно того, что вы действительно запросили, и предоставляет результаты наряду с вашими политиками, но никогда вместо них. Через **FailproofAI Cloud** подключённая машина использует Jev с тем же ключом, которым она уже подключена: без аккаунта TypeSafe, без второго ключа, без конечной точки для настройки. Каждый вызов начисляется на текущий лимит плана вашей организации.

Всё, что делает Jev, остаётся неизменным по сравнению с [установкой с собственным ключом](/ru/reference/jev-providers): жёсткие политики остаются окончательными, отказ рецензируемой политики отменяется только когда Jev был спрошен ровно об этой проблеме, и любой сбой откатывается к результату regex для этого вызова.

<Note>
Требует **failproofai 1.0.8-beta.0** или позже. 1.0.7 не имеет Jev, несмотря на то что сортируется выше версий 1.0.7 бета. Без конфигурации Jev ничего не меняется: хуки запускают политики regex ровно как всегда.
</Note>

## Перед началом

Установите Failproof AI на машину, где работает ваш агент, и подключите его хуки к [поддерживаемому harness](/ru/reference/harnesses). Если вы начинаете с нуля, следуйте [быстрому старту](/ru/start/quickstart) до установки хуков. Проверьте установленный CLI с `failproofai --version`; обновите, если его версия предшествует Jev. Вам также нужен доступ к странице **Administration → Keys** вашей организации для создания машинного ключа.

Jev проверяет именованные вызовы инструментов на шлюзе `PreToolUse` или `PermissionRequest`. Он не проверяет каждое событие в сеансе. Чтобы увидеть, как Jev отменяет отказ политики, вам нужна установленная политика, помеченная как [рецензируемая](/ru/policies/authority); все остальные отказы политик остаются окончательными.

## Включение

1. **Создайте ключ с Jev.** На панели управления FailproofAI Cloud откройте **Administration → Keys → Create key** и выберите предустановку **machine**. Она предоставляет три разрешения, которые нужны машине: `events:add` (отправка активности), `policies:pull` (получение политик) и `jev:evaluate` (Jev, начисляется на план вашей организации). Ключ не может иметь `jev:evaluate` без двух других.
2. **Подключите машину** с этим ключом. Прочитайте его одноразовый секрет в приглашении, затем запустите полную команду настройки:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` устанавливает демон, подключает хуки для найденных CLI агентов и подключает машину. Переменная окружения сохраняет ключ вне аргументов команды и истории вашей оболочки. Если ваш harness был установлен позже, [подключите его явно](/ru/start/quickstart).

   Если ваша организация работает на собственном FailproofAI Cloud вместо размещённого, добавьте его адрес: `--url https://<your dashboard host>` (или экспортируйте `FAILPROOFAI_CLOUD_URL`). Без этого ключ проверяется против размещённого сервиса и подключение не удаётся. Если сертификат этого хоста поступает от приватного CA, установите CA в хранилище доверия системы машины (например с `update-ca-certificates`), не только в `NODE_EXTRA_CA_CERTS`: демон, отправляющий события и получающий политики, читает системное хранилище. Смотрите [Устранение неполадок](/ru/reference/troubleshooting).

Вот и всё. Подключение сохраняет ключ и, когда на машине **нет** конфигурации Jev, создаёт одну для FailproofAI Cloud. С первого развёртывания машины (примерно за 30 с) FailproofAI Cloud устанавливает режим: `enforce` пока политика Jev развёрнута на ней, `off` когда нет (смотрите [Кто устанавливает режим](#who-sets-the-mode)). Вывод это покажет:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Проверки, которые запускает FailproofAI Cloud, работают в Cloud. Чтобы добавить собственные проверки на машину, установите пакет:

```bash
failproofai policies add FailproofAI/jev-policies
```

**С `--no-transcripts` подключение не включает Jev.** Jev отправляет каждый проверенный вызов инструмента и недавний запрос на FailproofAI Cloud, что больше того, что попросило подключение только для решений. Ключ всё ещё сохраняется, и вывод говорит, что Jev доступен и как его включить:

```bash
failproofai jev setup --provider failproofai
```

Это также выключает Jev через FailproofAI Cloud. Файл `jev.json`, который запускает Jev через FailproofAI Cloud (оставленный предыдущим подключением с включёнными транскриптами), удаляется по тому же правилу, которое использует `config --disconnect`, и вывод говорит, что Jev через FailproofAI Cloud остаётся отключённым на этой машине. Файл `jev.json` для вашей собственной конечной точки Jev остаётся как есть, и то же самое с отключённым FailproofAI Cloud (`--mode off`).

<Warning>
Подключение **никогда не перезаписывает** существующий `~/.failproofai/jev.json`. Если вы уже используете свою конечную точку Jev, она продолжит использоваться, и вывод скажет, что файл был оставлен как сконфигурирован — и, когда этот файл выключает Jev (отказано или отключено), это скажет и как это исправить. Чтобы переключить эту машину на FailproofAI Cloud, запустите `failproofai jev setup --provider failproofai`.
</Warning>

## Кто устанавливает режим

На машине, подключённой к FailproofAI Cloud, **FailproofAI Cloud устанавливает режим Jev**; ничто на машине этого не делает:

- `enforce` пока какая-либо политика Jev (или regex + Jev) развёрнута на машину: каждый проверенный вызов инструмента от агента, который одна из этих политик нацелена на, идёт в FailproofAI Cloud, который запрашивает его проверки вместе с проверками установленных там пакетов. Вызов от агента, на который никакая облачная политика Jev не нацелена и у которого нет собственной проверки пакета, вообще не отправляется. В `enforce` собственные проверки отказа Jev блокируют вызовы, а также отменяют вердикты regex, которые они проверяют.
- `off` когда нет: вообще Jev нет, что бы ни говорил `jev.json`.

Чтобы попробовать политику Jev перед тем как она будет действовать, развёрнут её с эффектом **observe**: её проверки всё ещё запрашиваются, и что бы они ни сделали, записывается как **would-have** на странице политики, но это никогда не блокирует вызов и никогда не отменяет один. `failproofai jev setup --mode` и переключатель **Settings → Jev** панели управления говорят, что режимом управляет FailproofAI Cloud и ничего не меняют. `jev.json` не используется для проверок Cloud, даже если он указывает на другого провайдера. `failproofai config --disconnect` передаёт Jev назад собственному `jev.json` машины.

`failproofai jev status` затем говорит `Jev checks run on FailproofAI Cloud (mode: enforce)`. Он также называет проверки, которые проверяют каждую политику `both`. Страница флота показывает, почему машина с режимом не может спросить:

- `transcripts_disabled`: машина была подключена с `--no-transcripts`, что никогда не включает Jev.
- `jev_unconfigured`: ключ машины не имеет `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud отказал в некоторых вызовах машины из-за лимита частоты Jev для организации, и эти вызовы были решены политиками regex только.
- `jev_unavailable`: несколько вызовов подряд не удалось, поэтому машина пропускает Jev FailproofAI Cloud на минуту за раз. Она повторяет попытку самостоятельно.

Если FailproofAI Cloud не ответит в течение 5 секунд, политики regex решают сами, как при любом сбое Jev. После 3 сбоев подряд машина прекращает спрашивать на минуту за раз, поэтому сбой Cloud не замедляет каждый вызов инструмента.

Пауза сеанса (`failproofai config --pause`) не останавливает проверки Jev FailproofAI Cloud, так же как она не останавливает управляемые Cloud политики. Она паузирует проверки Jev пакетов, установленных на машине.

## Проверка того, что он делает

```bash
failproofai jev status
failproofai jev test
```

`status` показывает провайдера как **FailproofAI Cloud**, хост Cloud, к которому подключена машина, режим и источник ключа как **FailproofAI Cloud connection**, никогда не сам ключ. Когда FailproofAI Cloud `jev.json` на месте, но Jev не может работать, он говорит почему:

| `status` говорит | `status --json` | Значение |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Машина подключена, но для неё не сохранён ключ Jev: ключу не хватает `jev:evaluate` или подключение не могло его подтвердить. Запустите `failproofai config` снова с ключом в `FAILPROOFAI_CLOUD_TOKEN`; если ему не хватает разрешения, используйте ключ **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | На этой машине нет подключения FailproofAI Cloud, к которому может принадлежать ключ Jev. |

После `failproofai config --disconnect` больше нет FailproofAI Cloud `jev.json` (если он не был отключен, что сохраняется), поэтому `status` просто сообщает, что Jev отключён. `status --json` несёт те же факты (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), также когда конфигурация отсутствует или отказана. `permissions` всегда из `jev.json`; отказ о `credentials.json` добавляет `credentialsPermissions`, и `fix` когда одна команда это исправляет. `test` отправляет один живой запрос и сообщает его задержку и версию Jev, которая ответила. Выходит 1 и говорит так в заголовке, когда ответ приходит после тайм-аута хука (хуки записали бы `timeout`) или отвечает на вопрос проверки неправильно.

Панель **Settings → Jev** на панели управления также показывает **FailproofAI Cloud connection**: в какую организацию сообщает машина и несёт ли её ключ Jev. Это читается из собственных файлов машины без сетевого вызова.

## Проверка реального вызова

Запустите новый сеанс в подключённом агенте. Попросите его использовать инструмент чтения файлов на `README.md` и сообщить заголовок. Подтвердите, что сеанс содержит этот вызов инструмента, затем запустите `failproofai jev status` снова: его недавний счётчик evaluated-call должен увеличиться. Откройте **Policies → Activity** в [локальной панели управления](/ru/reference/local-dashboard#review-policy-activity) чтобы проверить вердикт Jev этого вызова и режим. В Cloud, страница **Policies** организации показывает результаты Jev для доставленной активности. В режиме observe, вердикт записывается как **would-have** и результат политики всё ещё решает вызов. Отмена появляется только когда рецензируемая политика совпала и Jev отменил её именованные проверки.

## Что попадает на страницу политики

Машина уже отправляет её активность хука на FailproofAI Cloud (`events:add`). С включённым Jev, запись каждого гейтового вызова также говорит, какой оценщик запустился, что решил Jev, какие политики он отменил, почему откатился когда откатился, его задержку и модель, которая ответила — решения, коды и имена, никогда команда или ваш запрос. На странице **Policies** вашей организации:

- вызов, решение которого принял собственный вердикт Jev (режим enforce), приписывается **Jev**, и когда решающая проверка пришла из пакета, запись также называет этот пакет и его версию;
- в режиме observe, отказ или предупреждение Jev появляется как **would-have**, рядом с развёртываниями, которые вы наблюдаете;
- политики, которые Jev отменил или отменил бы в режиме observe, подсчитываются на политику.
- решение, в котором Jev участвовал (блокировка, предупреждение, отмена или would-have в режиме observe), перечисляет каждую проверку, которую он запросил, и что эта проверка заключила: вердикт, почему (`not-detected`, `exempt`, `fired`, `op-requested`, …), её доказательство `p`, ответ `exempt` и ответ каждого зонда. Проверка политики, развёрнутой для наблюдения (observe), также указывается, отмеченная как наблюдаемая; она никогда не блокирует. Jev отвечает вероятностями, не прозой, поэтому нет свободного текста причины. Обычные разрешения сворачиваются в подсчёты и не несут этот список.

## Когда Jev не может ответить

Каждое из них откатывается к результату вашей политики для этого вызова и записывается с его причиной:

| Причина | Причина |
| --- | --- |
| `out-of-credits` | Ваша организация исчерпала лимит своего плана. |
| `http-401`, `http-403` | Ключ был отозван или не имеет `jev:evaluate`. Переподключитесь с ключом, который имеет. |
| `http-429` | FailproofAI Cloud ограничивает частоту Jev для вашей организации. До момента пока не закончится ожидание, которое оно просит (его `Retry-After`, максимум 60 секунд), машина ничего ему не отправляет и каждый вызов откатывается сразу же. Вызовы, задержанные таким образом, записываются как `http-429` или как `rate-limited` когда собственный лимит частоты машины их сначала задерживает. |
| `http-429` (дневной лимит) | Ваша организация использовала свои дневные вызовы Jev: **10,000 за UTC день**, если только оператор вашего FailproofAI Cloud не установил другой лимит. Каждый вызов откатывается до тех пор пока счётчик не перезагрузится в 00:00 UTC; машина всё ещё спрашивает максимум раз в минуту, поэтому подхватывает перезагрузку в течение минуты. `failproofai jev test` говорит "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev отказал в запросе этого вызова, обычно потому что вызов инструмента содержал плотный текст (base64, hex, минифицированный код) сверх бюджета токенов Jev. Этот вызов откатывается каждый раз; это не сбой. |
| `http-502` | Jev недоступен прямо сейчас. |
| `http-503` | Этот Cloud не может служить Jev для вашей организации: шлюз моделей отсутствует, организация ещё не подготовлена или шлюз не работает. Спросите вашего администратора; хуки спрашивают снова максимум раз в минуту. |
| `http-404` | Этот FailproofAI Cloud ещё не служит Jev. |
| `timeout` | Нет ответа в течение `timeoutMs` (по умолчанию 3000). Пока FailproofAI Cloud устанавливает режим Jev машины, ожидание 5000 мс и `jev.json`'s `timeoutMs` не используется. |
| `model-mismatch` | Ответил версия Jev отличная от 1.13. |

## Где живёт ключ и куда он идёт

- Ключ сохраняется один раз в `~/.failproofai/credentials.json` (`0600`, в каталоге только для владельца), рядом с остальными учётными данными FailproofAI Cloud. `jev.json` не содержит ключ для этого маршрута; один написанный там делает конфигурацию недействительной.
- Если `credentials.json` носит **любое** разрешение для кого-то кроме вас (группа или другие, чтение или запись), или его каталог может быть **записан** кем-то кроме вас, это **отказано**, не читается, и Jev выключен до тех пор пока вы это не исправите: `chmod 600` на файле, `chmod 700` на каталоге (или переподключитесь, что перепишет файл в `0600` и сделает каталог только для владельца). Каталог, который другие могут только читать, в порядке; один, который они могут писать позволяет им поменять файл.
- Ключ считается только пока подключение, с которым он пришёл, находится на машине: политика или учётные данные отчётности для того же FailproofAI Cloud **с тем же ключом**, в том же файле. Ключ Jev, оставленный без одного, игнорируется, и Jev остаётся выключенным. Это происходит когда более старый failproofai's `config --disconnect` оставляет ключ Jev на месте (он не знает его удалить), или когда более старый failproofai's `config --token` подключается с другим ключом, который на FailproofAI Cloud может принадлежать другой организации. Чтобы переключить Jev обратно, подключитесь снова с ключом **machine**.
- Ключ отправляется только на источник Cloud, против которого он был проверен. `jev.json` указывающий куда-либо ещё, отказывается.
- **Агент на машине может его прочитать.** `credentials.json` только для владельца, и агент работает как этот владелец. Чтение собственных файлов failproofai разрешено намеренно (только изменение их заблокировано `block-failproofai-commands`), поэтому единственное между агентом и этим файлом `block-read-outside-cwd` — *рецензируемая* политика — и из сеанса запущенного в вашем домашнем каталоге, ничего. Ключ с `jev:evaluate` потребляет лимит Jev вашей организации (до дневной шапки) откуда бы он ни использовался, поэтому обращайтесь с машинным ключом как с любым другим расходным учётным данным: если агент мог его прочитать, отключите его на странице Keys и переподключитесь с новым.
- Это решают только ваши глобальные файлы. Хранилище не может включить Cloud Jev, указать его куда-либо или поставить его ключ, и `FAILPROOFAI_JEV_API_KEY` игнорируется для этого маршрута.
- Для каждого вызова, который Jev оценивает, один запрос идёт на FailproofAI Cloud, несущий то, что указано на [странице bring-your-own-key](/ru/reference/jev-providers#what-leaves-the-machine) (секреты зачищены). FailproofAI Cloud пересылает его TypeSafe и не логирует или не хранит.

## Выключение

На подключённой машине Jev выключен когда FailproofAI Cloud не развёртывает политику Jev на ней: удалите или архивируйте политики Jev там.

| Команда | Результат |
| --- | --- |
| Удалить политики Jev машины в FailproofAI Cloud | Режим Cloud становится `off` при следующем опросе (примерно 30 с): вообще Jev нет, что бы ни говорил `jev.json`. |
| `failproofai config --disconnect` | Отключить машину: ключ удаляется, и то же самое с `jev.json` когда он называет FailproofAI Cloud и не отключен. Файл `jev.json` для вашей собственной конечной точки остаётся. |

С следующего вызова инструмента хуки запускают политики regex точно как раньше.
