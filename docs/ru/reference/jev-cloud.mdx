Это справка по облачному маршруту для [политик Jev](/ru/policies/jev). Jev, классификатор TypeSafe, анализирует каждый вызов инструмента на соответствие тому, что вы действительно запросили, и дает ответ вместе с вашими политиками, а не вместо них. Через **FailproofAI Cloud** подключенная машина использует Jev с тем же ключом, который она уже использует для подключения: никакого аккаунта TypeSafe, никакого второго ключа, никакой конечной точки для настройки. Каждый вызов списывается на квоту плана вашей организации.

Всё, что делает Jev, остаётся неизменным по сравнению с [самостоятельной настройкой](/ru/reference/jev-providers): жёсткие политики остаются окончательными, отказ обозреваемой политики снимается только когда Jev спросили именно об этой проблеме, а любой сбой откатывается к результату регулярного выражения для данного вызова.

<Note>
Требуется **failproofai 1.0.8-beta.0** или позже. Версия 1.0.7 не поддерживает Jev, даже хотя она выше бета-версий 1.0.7. Без конфигурации Jev ничего не меняется: hooks запускают политики регулярных выражений в точности как всегда.
</Note>

## Перед началом

Установите Failproof AI на машину, где работает ваш агент, и подключите его hooks к [поддерживаемой системе](/ru/reference/harnesses). Если вы начинаете с нуля, следуйте [быстрому старту](/ru/start/quickstart) до установки hooks. Проверьте установленный CLI с помощью `failproofai --version`; обновите его, если он старше, чем версия с Jev. Вам также нужен доступ к странице **Administration → Keys** вашей организации для создания ключа машины.

Jev анализирует именованные вызовы инструментов на точке `PreToolUse` или `PermissionRequest`. Он не анализирует все события в сессии. Чтобы увидеть, как Jev снимает отказ политики, вам нужна установленная политика, помеченная [обозреваемой](/ru/policies/authority); все остальные отказы политик остаются окончательными.

## Включение

1. **Создайте ключ с Jev.** На панели управления FailproofAI Cloud откройте **Administration → Keys → Create key** и выберите предустановку **machine**. Она предоставляет три разрешения, которые нужны машине: `events:add` (отправка активности), `policies:pull` (получение политик) и `jev:evaluate` (Jev, списываемый на план вашей организации). Ключ не может иметь `jev:evaluate` без остальных двух.
2. **Подключите машину** с этим ключом. Прочитайте его одноразовый секрет в приглашении, затем запустите полную команду настройки:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` устанавливает демона, подключает hooks для найденных CLI агентов и подключает машину. Переменная окружения хранит ключ вне аргументов команды и истории shell. Если ваша система была установлена позже, [подключите её явно](/ru/start/quickstart).

   Если ваша организация использует собственное FailproofAI Cloud вместо размещённого, добавьте его адрес: `--url https://<your dashboard host>` (или экспортируйте `FAILPROOFAI_CLOUD_URL`). Без этого ключ проверяется с помощью размещённого сервиса и подключение не удаётся. Если сертификат этого хоста выпущен приватным ЦС, установите ЦС в системное хранилище доверия машины (например, с помощью `update-ca-certificates`), а не только в `NODE_EXTRA_CA_CERTS`: демон, который отправляет события и получает политики, читает системное хранилище. См. [Troubleshooting](/ru/reference/troubleshooting).

Вот и всё. Подключение сохраняет ключ и, когда на машине **нет** конфигурации Jev, создаёт её для FailproofAI Cloud. Начиная с первого развёртывания машины (примерно в течение 30 с) FailproofAI Cloud устанавливает режим: `enforce`, пока политика Jev развёрнута на нём, `off`, когда её нет (см. [Who sets the mode](#who-sets-the-mode)). Вывод говорит об этом:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Проверки FailproofAI Cloud выполняются в Cloud. Чтобы добавить собственные проверки на машину, установите пакет:

```bash
failproofai policies add FailproofAI/jev-policies
```

**С `--no-transcripts` подключение не включает Jev.** Jev отправляет каждый проверенный вызов инструмента и недавний запрос на FailproofAI Cloud, что больше, чем подключение только для решений попросило бы отправить. Ключ всё ещё сохраняется, и вывод говорит, что Jev доступен и как его включить:

```bash
failproofai jev setup --provider failproofai
```

Это также **выключает** Jev через FailproofAI Cloud. `jev.json`, который запускает Jev через FailproofAI Cloud (оставленный более ранним подключением с включёнными транскриптами), удаляется по тому же правилу, которое использует `config --disconnect`, и вывод говорит, что Jev через FailproofAI Cloud остаётся отключённым на этой машине. `jev.json` для вашей собственной конечной точки Jev остаётся как есть, равно как и отключённый вами FailproofAI Cloud (`--mode off`).

<Warning>
Подключение **никогда не перезаписывает** существующий `~/.failproofai/jev.json`. Если вы уже используете свою конечную точку Jev, она будет продолжать использоваться, и вывод скажет, что файл был оставлен как настроено — и, когда этот файл отключает Jev (отказано или выключено), скажет об этом и как это исправить. Чтобы переключить эту машину на FailproofAI Cloud, запустите `failproofai jev setup --provider failproofai`.
</Warning>

## Кто устанавливает режим

На машине, подключённой к FailproofAI Cloud, **FailproofAI Cloud устанавливает режим Jev**; ничего на машине это не делает:

- `enforce` пока на машину развёрнута хотя бы одна политика Jev (или регулярное выражение + Jev): каждый проверенный вызов инструмента от агента, которого одна из этих политик охватывает, отправляется на FailproofAI Cloud, которое спрашивает его проверки вместе с проверками установленных там пакетов. Вызов от агента, который не охватывает никакая облачная политика Jev и не имеет собственной проверки пакета, вообще не отправляется. В режиме `enforce` собственные проверки отказа Jev блокируют вызовы также как и снимают вердикты регулярных выражений, которые они анализируют.
- `off`, когда ничего этого нет: вообще никакого Jev, независимо от того, что говорит `jev.json`.

Чтобы протестировать политику Jev перед тем, как она начнёт действовать, разверните её с эффектом **observe**: её проверки всё ещё запрашиваются, и то, что они бы сделали, записывается как **would-have** на странице политики, но она никогда не блокирует вызов и никогда не снимает его. `failproofai jev setup --mode` и панель **Settings → Jev** панели управления говорят, что режимом управляет FailproofAI Cloud и ничего не меняют. `jev.json` не используется для проверок Cloud, даже если он указывает другого поставщика. `failproofai config --disconnect` возвращает Jev машине собственного `jev.json`.

`failproofai jev status` говорит `Jev checks run on FailproofAI Cloud (mode: enforce)`. Он также называет проверки, которые анализируют каждую политику `both`. Страница парка показывает, почему машина с режимом не может спрашивать:

- `transcripts_disabled`: машина была подключена с `--no-transcripts`, что никогда не включает Jev.
- `jev_unconfigured`: ключ машины не имеет `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud отказал некоторым вызовам машины из-за лимита скорости Jev организации, и эти вызовы были решены политиками регулярных выражений.
- `jev_unavailable`: несколько вызовов подряд не прошли, поэтому машина пропускает Jev FailproofAI Cloud на минуту за раз. Она повторяет попытку самостоятельно.

Если FailproofAI Cloud не ответит в течение 5 секунд, политики регулярных выражений решают самостоятельно, как при любом сбое Jev. После 3 последовательных отказов машина перестаёт спрашивать на минуту за раз, чтобы сбой Cloud не замедлял каждый вызов инструмента.

Пауза сессии (`failproofai config --pause`) не останавливает проверки Jev FailproofAI Cloud, точно как не останавливает управляемые облаком политики. Она приостанавливает проверки Jev пакетов, установленных на машине.

## Проверьте, что происходит

```bash
failproofai jev status
failproofai jev test
```

`status` показывает поставщика как **FailproofAI Cloud**, облачный хост, с которым подключена машина, режим и источник ключа как **FailproofAI Cloud connection**, никогда не сам ключ. Когда `jev.json` FailproofAI Cloud есть, но Jev не может работать, он говорит почему:

| `status` говорит | `status --json` | Значение |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Машина подключена, но для неё не сохранён ключ Jev: ключу не хватает `jev:evaluate`, или подключение не смогло это подтвердить. Запустите `failproofai config` снова с ключом в `FAILPROOFAI_CLOUD_TOKEN`; если ему не хватает разрешения, используйте ключ **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | На этой машине нет подключения к FailproofAI Cloud, к которому может принадлежать ключ Jev. |

После `failproofai config --disconnect` больше не будет `jev.json` FailproofAI Cloud (если только он не был выключен, что сохраняется), поэтому `status` просто сообщает о Jev как выключенном. `status --json` содержит те же факты (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), также когда конфигурация отсутствует или отказана. `permissions` всегда из `jev.json`; отказ о `credentials.json` добавляет `credentialsPermissions`, и `fix`, когда одна команда это исправляет. `test` отправляет один живой запрос и сообщает его задержку и версию Jev, которая ответила. Он выходит с кодом 1 и говорит об этом в названии, когда ответ приходит после тайм-аута hook (hooks записали бы `timeout`) или ответить неправильно на вопрос проверки.

Панель **Settings → Jev** панели управления также показывает **FailproofAI Cloud connection**: в какую организацию машина отправляет отчёты и имеет ли её ключ Jev. Это читается из собственных файлов машины, без сетевого вызова.

## Проверьте реальный вызов

Начните новую сессию в hooked агенте. Попросите его использовать его инструмент чтения файлов на `README.md` и сообщить название. Подтвердите, что сессия содержит этот вызов инструмента, затем запустите `failproofai jev status` снова: его недавний счётчик вычисленных вызовов должен увеличиться. Откройте **Policies → Activity** в [локальной панели управления](/ru/reference/local-dashboard#review-policy-activity) для проверки вердикта Jev и режима этого вызова. В Cloud страница **Policies** организации показывает результаты Jev для доставленной активности. В режиме observe вердикт записывается как **would-have** и результат политики всё ещё решает вызов. Очистка появляется только когда совпадает обозреваемая политика и Jev снимает её именованные проверки.

## Что попадает на страницу политики

Машина уже отправляет активность её hook на FailproofAI Cloud (`events:add`). С включённым Jev, запись каждого вызова в точке также говорит, какой оценщик работал, что решил Jev, какие политики он снял, почему откатился, когда это произошло, его задержка и модель, которая ответила — решения, коды и имена, никогда команда или ваш запрос. На странице **Policies** вашей организации:

- вызов, решение которого принял собственный вердикт Jev (режим enforce), приписывается **Jev**, и когда решающая проверка пришла из пакета, запись также называет этот пакет и его версию;
- в режиме observe отказ или предупреждение Jev появляется как **would-have**, рядом с развёртываниями, которые вы наблюдаете;
- политики, которые Jev снял или снял бы в режиме observe, подсчитываются для каждой политики.
- решение, в котором Jev принял участие (блокировка, предупреждение, очистка или would-have в режиме observe) перечисляет каждую проверку, которую он спросил и что эта проверка заключила: вердикт, почему (`not-detected`, `exempt`, `fired`, `op-requested`, …), его доказательство `p`, ответ `exempt` и ответ каждого зонда. Проверка политики, развёрнутой для наблюдения (observe), также указана, отмечена как наблюдаемая; она никогда не блокирует. Jev ответит вероятностями, не прозой, поэтому нет свободного текста причины. Обычные разрешения скатываются в счёты и не несут этот список.

## Когда Jev не может ответить

Каждое из этих откатывается к результату вашей политики для этого вызова и записывается с его причиной:

| Причина | Причина |
| --- | --- |
| `out-of-credits` | Ваша организация использовала квоту плана. |
| `http-401`, `http-403` | Ключ был отозван или не имеет `jev:evaluate`. Переподключитесь с ключом, который это имеет. |
| `http-429` | FailproofAI Cloud ограничивает скорость Jev для вашей организации. Пока ожидание, которое оно просит (его `Retry-After`, максимум 60 секунд), не закончится, машина ничего не отправляет и каждый вызов откатывается сразу же. Вызовы, задержанные таким образом, записываются как `http-429`, или как `rate-limited`, когда собственный лимит скорости машины задерживает их первым. |
| `http-429` (дневной лимит) | Ваша организация использовала свои дневные вызовы Jev: **10,000 за день по UTC**, если только оператор вашего FailproofAI Cloud не установил другой лимит. Каждый вызов откатывается до сброса счётчика в 00:00 UTC; машина всё ещё спрашивает максимум раз в минуту, поэтому она поймёт сброс в течение минуты. `failproofai jev test` говорит Daily Jev limit for this org reached; resets at 00:00 UTC. |
| `http-422` | Jev отказал этому вызову, обычно потому что вызов инструмента содержал плотный текст (base64, hex, минифицированный код) над бюджетом токенов Jev. Этот вызов откатывается каждый раз; это не сбой. |
| `http-502` | Jev недоступен прямо сейчас. |
| `http-503` | Этот Cloud не может обслуживать Jev для вашей организации: нет шлюза модели, организация еще не подготовлена или шлюз недоступен. Спросите вашего администратора; hooks спрашивают максимум раз в минуту. |
| `http-404` | Этот FailproofAI Cloud еще не обслуживает Jev. |
| `timeout` | Нет ответа в течение `timeoutMs` (по умолчанию 3000). Пока FailproofAI Cloud устанавливает режим Jev машины, ожидание составляет 5000 мс и `timeoutMs` из `jev.json` не используется. |
| `model-mismatch` | Ответил другая версия Jev, отличная от 1.13. |

## Где ключ живёт и куда он идёт

- Ключ сохраняется один раз в `~/.failproofai/credentials.json` (`0600`, в каталоге только для владельца), рядом с другими учетными данными FailproofAI Cloud. `jev.json` не содержит ключа для этого маршрута; ключ, написанный там, делает конфигурацию недействительной.
- Если `credentials.json` содержит **любое** разрешение для кого-либо, кроме вас (группа или другие, чтение или запись), или его каталог может быть **записан** кем-то, кроме вас, он **отказывается**, не читается, и Jev выключен до тех пор, пока вы это не исправите: `chmod 600` на файл, `chmod 700` на каталог (или переподключитесь, что перезаписывает файл в `0600` и делает каталог собственническим). Каталог, который другие могут только читать, хорош; тот, который они могут писать, позволяет им поменять файл.
- Ключ считается только пока подключение, с которым он пришёл, находится на машине: политика или учетные данные отчётности для того же FailproofAI Cloud **с тем же ключом**, в том же файле. Ключ Jev, оставленный без подключения, игнорируется, и Jev остаётся выключенным. Это происходит когда более старый failproofai `config --disconnect` оставляет ключ Jev на месте (он не знает удалить его) или когда более старый failproofai `config --token` подключается с другим ключом, который на FailproofAI Cloud может принадлежать другой организации. Чтобы включить Jev снова, переподключитесь с ключом **machine**.
- Ключ отправляется только на исходное облако, против которого он был верифицирован. `jev.json`, указывающий куда-либо ещё, отказывается.
- **Агент на машине может его прочитать.** `credentials.json` только для владельца, и агент работает как этот владелец. Чтение собственных файлов failproofai разрешено намеренно (только изменение их заблокировано, `block-failproofai-commands`), поэтому единственное, что стоит между агентом и этим файлом, это `block-read-outside-cwd` — *обозреваемая* политика — и из сессии, начатой в вашем домашнем каталоге, ничего. Ключ с `jev:evaluate` тратит квоту Jev вашей организации (вверх до дневного лимита) откуда угодно, используется, поэтому относитесь к ключу машины как к любому другому расходному учетному данному: если агент мог его прочитать, отключите его на странице Keys и переподключитесь с новым.
- Только ваши глобальные файлы это решают. Репозиторий не может включить Cloud Jev, указать его куда-либо ещё или предоставить его ключ, и `FAILPROOFAI_JEV_API_KEY` игнорируется для этого маршрута.
- Для каждого вызова, который Jev оценивает, один запрос идёт на FailproofAI Cloud, передавая то, что [страница bring-your-own-key](/ru/reference/jev-providers#what-leaves-the-machine) перечисляет (секреты отредактированы). FailproofAI Cloud пересылает его на TypeSafe и не логирует и не сохраняет его.

## Выключение

На подключённой машине Jev выключен, когда FailproofAI Cloud не развёртывает на ней политику Jev: удалите или архивируйте политики Jev там.

| Команда | Результат |
| --- | --- |
| Удалите политики Jev машины в FailproofAI Cloud | Режим Cloud становится `off` на следующем опросе (примерно 30 с): никакого Jev вообще, независимо от того, что говорит `jev.json`. |
| `failproofai config --disconnect` | Отключите машину: ключ удаляется, и так же `jev.json`, когда он назывет FailproofAI Cloud и не выключен. `jev.json` для вашей собственной конечной точки остаётся. |

Со следующего вызова инструмента hooks запускают политики регулярных выражений в точности как прежде.
