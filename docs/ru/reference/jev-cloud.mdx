Это справочник маршрута Cloud для [политик Jev](/ru/policies/jev). Jev, классификатор TypeSafe, проверяет каждый вызов инструмента по сравнению с тем, что вы фактически запросили, и отвечает наряду с вашими политиками, но никогда вместо них. Через **FailproofAI Cloud** подключённая машина использует Jev с тем же ключом, которым она уже подключена: ни учётной записи TypeSafe, ни второго ключа, ни конечной точки для конфигурации. Каждый вызов списывается с лимита плана вашей организации.

Всё, что делает Jev, не отличается от [установки с собственным ключом](/ru/reference/jev-providers): жёсткие политики остаются окончательными, отказ рецензируемой политики очищается только когда Jev был спрошен именно об этом вопросе, и любой отказ откатывается к результату регулярного выражения для этого вызова.

<Note>
Требует **failproofai 1.0.8-beta.0** или позже. 1.0.7 не имеет Jev, хотя версия выше, чем 1.0.7 бета. Без конфигурации Jev ничего не меняется: перехватчики запускают политики регулярного выражения точно как раньше.
</Note>

## Перед началом

Установите Failproof AI на машине, где запущен ваш агент, и привяжите его перехватчики к [поддерживаемой обвязке](/ru/reference/harnesses). Если вы начинаете с нуля, следуйте [краткому руководству](/ru/start/quickstart) до установки перехватчиков. Проверьте установленный CLI с помощью `failproofai --version`; обновите его, если версия более старая, чем Jev. Вам также необходим доступ к странице **Administration → Keys** вашей организации для создания ключа машины.

Jev проверяет именованные вызовы инструментов на шлюзе `PreToolUse` или `PermissionRequest`. Он не проверяет все события в сеансе. Чтобы увидеть, как Jev очищает отказ политики, вам нужна установленная политика, отмеченная как [рецензируемая](/ru/policies/authority); все остальные отказы политик остаются окончательными.

## Включение

1. **Создайте ключ с Jev.** На панели управления FailproofAI Cloud откройте **Administration → Keys → Create key** и выберите предустановку **machine**. Она предоставляет три разрешения, которые требуются машине: `events:add` (отправка активности), `policies:pull` (получение политик) и `jev:evaluate` (Jev, списывается с плана вашей организации). Ключ не может иметь `jev:evaluate` без двух других.
2. **Подключите машину** с этим ключом. Прочитайте её одноразовый секрет в приглашении, затем выполните полную команду установки:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` устанавливает демон, привязывает перехватчики к найденным CLI агентов и подключает машину. Переменная окружения защищает ключ от аргументов команды и истории вашей оболочки. Если ваша обвязка была установлена позже, [привяжите её явно](/ru/start/quickstart).

   Если ваша организация запускает собственный FailproofAI Cloud вместо размещённого, добавьте его адрес: `--url https://<your dashboard host>` (или экспортируйте `FAILPROOFAI_CLOUD_URL`). Без этого ключ проверяется против размещённого сервиса и подключение не удаётся. Если сертификат этого хоста выдан частным ЦС, установите ЦС в хранилище системного доверия машины (например с `update-ca-certificates`), а не только в `NODE_EXTRA_CA_CERTS`: демон, который отправляет события и получает политики, читает системное хранилище. См. [Решение проблем](/ru/reference/troubleshooting).

Вот и всё. Подключение сохраняет ключ и, когда машина **не имеет** конфигурации Jev, записывает её для FailproofAI Cloud. С первого развёртывания машины (примерно за 30 с) FailproofAI Cloud устанавливает режим: `enforce` пока политика Jev развёрнута на ней, `off` когда нет (см. [Кто устанавливает режим](#who-sets-the-mode)). Вывод говорит об этом:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Проверки, которые запускает FailproofAI Cloud, выполняются в Cloud. Чтобы добавить собственные проверки на машине, установите пак:

```bash
failproofai policies add FailproofAI/jev-policies
```

**С `--no-transcripts` подключение не включает Jev.** Jev отправляет каждый проверенный вызов инструмента и недавний запрос в FailproofAI Cloud, что больше, чем подключение только для решений просило бы отправлять. Ключ всё ещё сохраняется, и вывод говорит, что Jev доступен и как его включить:

```bash
failproofai jev setup --provider failproofai
```

Это также отключает Jev через FailproofAI Cloud. `jev.json`, который запускает Jev через FailproofAI Cloud (оставленный предыдущим подключением с включёнными транскриптами), удаляется по тому же правилу, которое использует `config --disconnect`, и вывод говорит, что Jev через FailproofAI Cloud остаётся отключённым на этой машине. `jev.json` для вашей собственной конечной точки Jev остаётся как есть, и также остаётся FailproofAI Cloud, который вы отключили (`--mode off`).

<Warning>
Подключение **никогда не перезаписывает** существующий `~/.failproofai/jev.json`. Если вы уже используете собственную конечную точку Jev, она продолжит использоваться, и вывод говорит, что файл остался настроенным — и, когда этот файл оставляет Jev отключённым (отказано или отключено), говорит об этом и как это исправить. Чтобы перевести эту машину на FailproofAI Cloud, выполните `failproofai jev setup --provider failproofai`.
</Warning>

## Кто устанавливает режим

На машине, подключённой к FailproofAI Cloud, **FailproofAI Cloud устанавливает режим Jev**; ничто на машине этого не делает:

- `enforce` пока к машине развёрнута хотя бы одна политика Jev (или регулярное выражение + Jev): каждый проверенный вызов инструмента от агента, которого эти политики нацеливают, идёт в FailproofAI Cloud, который запрашивает его проверки вместе с проверками установленных там паков. Вызов от агента, которого не нацеливает политика Cloud Jev, с собственной проверкой пака, вообще не отправляется. В `enforce` собственные проверки отказа Jev блокируют вызовы, а также очищают вердикты регулярного выражения, которые они просматривают.
- `off` когда нет: вообще нет Jev, что бы ни говорил `jev.json`.

Чтобы попробовать политику Jev перед тем, как она подействует, развёртывайте её с эффектом **observe**: её проверки всё ещё запрашиваются, и что бы они сделали, записывается как **would-have** на странице политики, но она никогда не блокирует вызов и никогда не очищает его. `failproofai jev setup --mode` и панель управления **Settings → Jev** говорят, что режимом управляет FailproofAI Cloud и ничего не меняют. `jev.json` не используется для проверок Cloud, даже если он называет другого провайдера. `failproofai config --disconnect` возвращает Jev машинному собственному `jev.json`.

`failproofai jev status` затем говорит `Jev checks run on FailproofAI Cloud (mode: enforce)`. Он также называет проверки, которые просматривают каждую политику `both`. На странице парка показано, почему машина с режимом не может спросить:

- `transcripts_disabled`: машина была подключена с `--no-transcripts`, что никогда не включает Jev.
- `jev_unconfigured`: ключ машины не имеет `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud отказал в некоторых вызовах машины по лимиту частоты Jev организации, и эти вызовы были решены только политиками регулярного выражения.
- `jev_unavailable`: несколько вызовов подряд не удались, поэтому машина пропускает Jev FailproofAI Cloud время от времени на минуту за раз. Она повторяет попытку самостоятельно.

Если FailproofAI Cloud не ответит в течение 5 секунд, политики регулярного выражения решают сами, как при любом отказе Jev. После 3 сбоев подряд машина прекращает спрашивать на минуту за раз, поэтому отказ Cloud не замедляет каждый вызов инструмента.

Пауза сеанса (`failproofai config --pause`) не останавливает проверки Jev FailproofAI Cloud, точно так же, как она не останавливает управляемые Cloud политики. Она приостанавливает проверки Jev паков, установленных на машине.

## Проверка того, что происходит

```bash
failproofai jev status
failproofai jev test
```

`status` показывает провайдера как **FailproofAI Cloud**, хост Cloud, к которому подключена машина, режим и источник ключа как **FailproofAI Cloud connection**, никогда не сам ключ. Когда `jev.json` FailproofAI Cloud находится на месте, но Jev не может работать, он говорит почему:

| `status` говорит | `status --json` | Значение |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Машина подключена, но для неё не сохранён ключ Jev: ключу не хватает `jev:evaluate`, или подключение не смогло его подтвердить. Запустите `failproofai config` снова с ключом в `FAILPROOFAI_CLOUD_TOKEN`; если ему не хватает разрешения, используйте ключ **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | На этой машине нет подключения FailproofAI Cloud, к которому мог бы принадлежать ключ Jev. |

После `failproofai config --disconnect` больше нет `jev.json` FailproofAI Cloud (если только он не был отключен, что сохраняется), поэтому `status` просто сообщает, что Jev отключен. `status --json` несёт те же факты (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), также когда конфиг отсутствует или отказан. `permissions` всегда собственные `jev.json`; отказ от `credentials.json` добавляет `credentialsPermissions`, и `fix` когда одна команда её исправляет. `test` отправляет один живой запрос и сообщает его задержку и версию Jev, которая ответила. Он завершается с кодом 1 и говорит об этом в заголовке, когда ответ приходит после тайм-аута перехватчика (перехватчики записали бы `timeout`) или отвечает на вопрос проверки неправильно.

Панель **Settings → Jev** панели управления также показывает **FailproofAI Cloud connection**: в какую организацию сообщает машина и есть ли у её ключа Jev. Это читается из собственных файлов машины без сетевого вызова.

## Проверка реального вызова

Начните новый сеанс в перехватчике агента. Попросите его использовать инструмент чтения файла на `README.md` и сообщить заголовок. Подтвердите, что сеанс содержит этот вызов инструмента, затем снова запустите `failproofai jev status`: счётчик недавно оценённых вызовов должен увеличиться. Откройте **Policies → Activity** в [локальной панели управления](/ru/reference/local-dashboard#review-policy-activity) для проверки вердикта Jev и режима этого вызова. В Cloud на странице **Policies** организации показаны результаты Jev для доставленной активности. В режиме observe вердикт записывается как **would-have** и результат политики всё ещё решает вызов. Очистка появляется только когда совпадала рецензируемая политика и Jev очистил её именованные проверки.

## Что попадает на страницу политики

Машина уже отправляет активность своих перехватчиков в FailproofAI Cloud (`events:add`). С включённым Jev, запись каждого проверяемого вызова также говорит, какой оцениватель работал, что решил Jev, какие политики он очистил, почему он откатился когда это произошло, его задержку и модель, которая ответила — решения, коды и имена, никогда команда или ваш запрос. На странице **Policies** вашей организации:

- вызов, решение которого принял собственный вердикт Jev (режим enforce), приписывается **Jev**, и когда решающая проверка пришла из пака, запись также называет этот пак и его версию;
- в режиме observe отказ или предупреждение Jev появляется как **would-have**, рядом с развёртываниями, которые вы наблюдаете;
- политики, которые Jev очистил, или которые он очистил бы в режиме observe, считаются за политику.
- решение, в котором Jev участвовал (блокировка, предупреждение, очистка или would-have в режиме observe), перечисляет каждую проверку, которую он запросил, и то, что эта проверка заключила: вердикт, почему (`not-detected`, `exempt`, `fired`, `op-requested`, …), её доказательство `p`, ответ `exempt` и ответ каждого зонда. Проверка политики, развёрнутой для наблюдения (observe), также указана, отмечена как watched; она никогда не блокирует. Jev отвечает вероятностями, а не прозой, поэтому нет свободного текста с причиной. Обычные allow свёртываются в счёты и не несут этого списка.

## Когда Jev не может ответить

Каждое из них откатывается к результату вашей политики для этого вызова и записывается с причиной:

| Причина | Причина |
| --- | --- |
| `out-of-credits` | Ваша организация использовала лимит плана. |
| `http-401`, `http-403` | Ключ был отозван или не имеет `jev:evaluate`. Подключитесь повторно с ключом, который имеет. |
| `http-429` | FailproofAI Cloud ограничивает частоту Jev для вашей организации. Пока ожидание, которое оно просит (его `Retry-After`, максимум 60 секунд), не закончится, машина ничего не отправляет и каждый вызов откатывается сразу. Вызовы, удерживаемые таким образом, записываются как `http-429`, или как `rate-limited` когда собственный лимит частоты машины удерживает их в первую очередь. |
| `http-429` (дневной лимит) | Ваша организация использовала дневные вызовы Jev: **10 000 за день UTC**, если только тот, кто управляет вашим FailproofAI Cloud, не установил другой лимит. Каждый вызов откатывается до сброса счётчика в 00:00 UTC; машина всё ещё спрашивает максимум один раз в минуту, поэтому сброс происходит в течение минуты. `failproofai jev test` говорит "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev отказал в этом запросе вызова, обычно потому, что вызов инструмента содержал плотный текст (base64, hex, минифицированный код) сверх бюджета токенов Jev. Этот вызов откатывается каждый раз; это не отказ. |
| `http-502` | Jev недоступен прямо сейчас. |
| `http-503` | Этот Cloud не может служить Jev для вашей организации: нет шлюза модели, организация не подготовлена ещё, или шлюз отключен. Обратитесь к администратору; перехватчики спрашивают максимум один раз в минуту. |
| `http-404` | Этот FailproofAI Cloud не служит Jev ещё. |
| `timeout` | Нет ответа в течение `timeoutMs` (по умолчанию 3000). Пока FailproofAI Cloud устанавливает режим Jev машины, ожидание составляет 5000 мс и `timeoutMs` `jev.json` не используется. |
| `model-mismatch` | Ответила версия Jev, отличная от 1.13. |

## Где ключ живёт и где он идёт

- Ключ сохраняется один раз в `~/.failproofai/credentials.json` (`0600`, в каталоге только владельца), рядом с другими учётными данными FailproofAI Cloud. `jev.json` не содержит ключ для этого маршрута; ключ, записанный туда, делает конфиг недействительным.
- Если `credentials.json` содержит **любое** разрешение для кого-то, кроме вас (группа или другие, чтение или запись), или его каталог может быть **написан** кем-либо, кроме вас, он **отказан**, не прочитан, и Jev отключен до тех пор, пока вы не исправите: `chmod 600` для файла, `chmod 700` для каталога (или подключитесь повторно, что перепишет файл на `0600` и сделает каталог только для владельца). Каталог, который другие могут только читать, хороший; тот, который они могут писать, позволяет им заменить файл.
- Ключ считается только пока подключение, с которым он пришёл, находится на машине: политика или учётные данные отчёта для того же FailproofAI Cloud **с тем же ключом**, в том же файле. Ключ Jev, оставленный без подключения, игнорируется, и Jev остаётся отключённым. Это происходит когда более старый failproofai's `config --disconnect` оставляет ключ Jev на месте (он не знает удалить его), или когда более старый failproofai's `config --token` подключается с другим ключом, который на FailproofAI Cloud может принадлежать другой организации. Чтобы включить Jev снова, подключитесь снова с ключом **machine**.
- Ключ отправляется только на источник Cloud, к которому он был проверен. `jev.json`, указывающий куда-то ещё, отказывается.
- **Агент на машине может прочитать это.** `credentials.json` доступен только владельцу, и агент работает как этот владелец. Чтение собственных файлов failproofai разрешено намеренно (только их изменение блокируется с помощью `block-failproofai-commands`), поэтому единственное, что стоит между агентом и этим файлом, это `block-read-outside-cwd` — *рецензируемая* политика — и из сеанса, начатого в вашем домашнем каталоге, ничего. Ключ с `jev:evaluate` тратит лимит Jev вашей организации (до дневного лимита) откуда бы он ни использовался, поэтому обращайтесь с ключом машины как с любыми другими учётными данными расходов: если агент мог его прочитать, отключите его на странице Keys и подключитесь с новым.
- Только ваши глобальные файлы решают это. Репозиторий не может включить Cloud Jev, указать на него или поставлять его ключ, и `FAILPROOFAI_JEV_API_KEY` игнорируется для этого маршрута.
- Для каждого вызова, который Jev оценивает, один запрос идёт в FailproofAI Cloud, несущий то, что перечисляет [страница bring-your-own-key](/ru/reference/jev-providers#what-leaves-the-machine) (секреты отредактированы). FailproofAI Cloud перенаправляет это TypeSafe и не регистрирует или не сохраняет его.

## Отключение

На подключённой машине Jev отключен когда FailproofAI Cloud не развёртывает политику Jev на ней: удалите или архивируйте политики Jev там.

| Команда | Результат |
| --- | --- |
| Удалить политики Jev машины в FailproofAI Cloud | Режим Cloud становится `off` при следующем опросе (примерно 30 с): вообще нет Jev, что бы ни говорил `jev.json`. |
| `failproofai config --disconnect` | Отключить машину: ключ удаляется, и также удаляется `jev.json` когда он называет FailproofAI Cloud и не отключен. `jev.json` для вашей собственной конечной точки остаётся. |

С следующего вызова инструмента перехватчики запускают политики регулярного выражения точно как раньше.
