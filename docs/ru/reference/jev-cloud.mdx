Это справочник маршрута Cloud для [политик Jev](/ru/policies/jev). Jev, классификатор TypeSafe, проверяет каждый вызов инструмента по тому, что вы на самом деле попросили, и дает ответ наряду с вашими политиками, никогда вместо них. Через **FailproofAI Cloud** подключенная машина использует Jev с тем же ключом, с которым она уже подключена: никакого аккаунта TypeSafe, никакого второго ключа, никакой конечной точки для настройки. Каждый вызов списывается с выделения плана вашей организации.

Все, что делает Jev, остается неизменным от [настройки с собственным ключом](/ru/reference/jev-providers): жесткие политики остаются окончательными, отказ обозреваемой политики очищается только когда Jev был спрошен об этом конкретном вопросе, и любой сбой возвращается к результату regex для этого вызова.

<Note>
Требуется **failproofai 1.0.8-beta.0** или позже. 1.0.7 не имеет Jev, даже если он сортируется выше бета-версий 1.0.7. Без конфигурации Jev ничего не изменяется: хуки запускают политики regex ровно как раньше.
</Note>

## Перед началом

Установите Failproof AI на машине, где работает ваш агент, и подключите его хуки к [поддерживаемому harness](/ru/reference/harnesses). Если вы начинаете с нуля, следуйте [краткому руководству](/ru/start/quickstart) через установку хука. Проверьте установленный CLI с `failproofai --version`; обновите его, если он предшествует Jev. Вам также нужен доступ к странице **Administration → Keys** вашей организации для создания машинного ключа.

Jev проверяет именованные вызовы инструментов на вратах `PreToolUse` или `PermissionRequest`. Он не проверяет каждое событие в сеансе. Чтобы увидеть, как Jev очищает отказ политики, вам нужна установленная политика, отмеченная как [reviewable](/ru/policies/authority); все остальные отказы политик остаются окончательными.

## Включите это

1. **Создайте ключ с Jev.** В панели управления FailproofAI Cloud откройте **Administration → Keys → Create key** и выберите предустановку **machine**. Она дает три разрешения, которые нужны машине: `events:add` (отправлять активность), `policies:pull` (получать политики) и `jev:evaluate` (Jev, списывается со плана вашей организации). Ключ не может нести `jev:evaluate` без двух других.
2. **Подключите машину** с этим ключом. Прочитайте его одноразовый секрет на запросе, затем запустите полную команду настройки:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` устанавливает демон, подключает хуки для найденных CLI агентов и подключает машину. Переменная окружения держит ключ отдельно от аргументов команды и истории оболочки. Если ваш harness был установлен позже, [подключите его явно](/ru/start/quickstart).

   Если ваша организация запускает собственный FailproofAI Cloud вместо хостированного, добавьте его адрес: `--url https://<ваш хост панели>` (или экспортируйте `FAILPROOFAI_CLOUD_URL`). Без этого ключ проверяется для хостированного сервиса и подключение не удается. Если сертификат этого хоста выдан приватным центром сертификации, установите центр в системное хранилище доверия машины (например с `update-ca-certificates`), не только в `NODE_EXTRA_CA_CERTS`: демон, который отправляет события и получает политики, читает системное хранилище. См. [Troubleshooting](/ru/reference/troubleshooting).

Это все. Подключение сохраняет ключ и, когда машина **не имеет** конфигурацию Jev, записывает одну для FailproofAI Cloud. От первого развертывания машины (примерно за 30 с) FailproofAI Cloud устанавливает режим: `enforce` пока политика Jev развернута на нее, `off` когда нет (см. [Кто устанавливает режим](#who-sets-the-mode)). Вывод это указывает:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Проверки FailproofAI Cloud работают на Cloud. Чтобы добавить свои проверки на машине, установите пакет:

```bash
failproofai policies add FailproofAI/jev-policies
```

**С `--no-transcripts` подключение не включает Jev.** Jev отправляет каждый проверяемый вызов инструмента и недавний запрос в FailproofAI Cloud, что больше, чем подключение только к решениям попросило бы отправить. Ключ все еще сохраняется, и вывод говорит, что Jev доступен и как его включить:

```bash
failproofai jev setup --provider failproofai
```

Это также выключает Jev через FailproofAI Cloud **off**. `jev.json`, который запускает Jev через FailproofAI Cloud (оставленный более ранним подключением с включенными транскриптами), удаляется по тому же правилу, что использует `config --disconnect`, и вывод говорит, что Jev через FailproofAI Cloud остается выключен на этой машине. `jev.json` для вашей собственной конечной точки Jev остается как есть, а также FailproofAI Cloud, который вы выключили (`--mode off`).

<Warning>
Подключение **никогда не перезаписывает** существующий `~/.failproofai/jev.json`. Если вы уже используете вашу собственную конечную точку Jev, она продолжает использоваться, и вывод говорит, что файл был оставлен в соответствии с конфигурацией — и, когда этот файл оставляет Jev выключенным (отказано или выключено), говорит об этом и как исправить. Чтобы переключить эту машину на FailproofAI Cloud, запустите `failproofai jev setup --provider failproofai`.
</Warning>

## Кто устанавливает режим

На машине, подключенной к FailproofAI Cloud, **FailproofAI Cloud устанавливает режим Jev**; ничто на машине этого не делает:

- `enforce` пока на машину развернута любая политика Jev (или regex + Jev): каждый проверяемый вызов инструмента от агента, который нацелена одна из этих политик, идет в FailproofAI Cloud, которая спрашивает свои проверки вместе с проверками установленных там пакетов. Вызов от агента, на который никакая Cloud политика Jev не нацелена, без собственной проверки пакета, вообще не отправляется. В `enforce`, собственные проверки отказа Jev блокируют вызовы, а также очищают результаты regex, которые они проверяют.
- `off` когда нет: никакого Jev вообще, что бы `jev.json` ни говорил.

Чтобы попробовать политику Jev перед тем, как она подействует, разверните ее с эффектом **observe**: ее проверки все еще запрашиваются, и то, что они бы сделали, записывается как **would-have** на странице политики, но это никогда не блокирует вызов и никогда не очищает один. `failproofai jev setup --mode` и режим переключения панели управления **Settings → Jev** говорят, что режим управляется FailproofAI Cloud и ничего не меняют. `jev.json` не используется для проверок Cloud, даже если он указывает другого поставщика. `failproofai config --disconnect` возвращает Jev собственному `jev.json` машины.

`failproofai jev status` затем говорит `Jev checks run on FailproofAI Cloud (mode: enforce)`. Он также называет проверки, которые проверяют каждую политику `both`. Страница флота показывает, почему машина с режимом не может спросить:

- `transcripts_disabled`: машина была подключена с `--no-transcripts`, что никогда не включает Jev.
- `jev_unconfigured`: ключ машины не содержит `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud отказала некоторым вызовам машины из-за лимита скорости Jev организации, и эти вызовы были решены только политиками regex.
- `jev_unavailable`: несколько вызовов подряд не удались, поэтому машина пропускает Jev FailproofAI Cloud на минуту за раз. Она повторяет попытку самостоятельно.

Если FailproofAI Cloud не отвечает в течение 5 секунд, политики regex решают в одиночку, как для любого сбоя Jev. После 3 сбоев подряд машина перестает спрашивать на минуту за раз, поэтому сбой Cloud не замедляет каждый вызов инструмента.

Пауза сеанса (`failproofai config --pause`) не останавливает проверки Jev FailproofAI Cloud, так же как она не останавливает управляемые Cloud политики. Она приостанавливает проверки Jev пакетов, установленных на машине.

## Проверьте, что это делает

```bash
failproofai jev status
failproofai jev test
```

`status` показывает поставщика как **FailproofAI Cloud**, хост Cloud, к которому подключена машина, режим и источник ключа как **FailproofAI Cloud connection**, никогда сам ключ. Когда `jev.json` FailproofAI Cloud на месте, но Jev не может работать, он говорит почему:

| `status` говорит | `status --json` | Значение |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Машина подключена, но для нее не сохранен ключ Jev: ключу не хватает `jev:evaluate` или подключение не смогло это подтвердить. Запустите `failproofai config` снова с ключом в `FAILPROOFAI_CLOUD_TOKEN`; если ему не хватает разрешения, используйте ключ **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | На этой машине нет подключения FailproofAI Cloud, к которому принадлежит ключ Jev. |

После `failproofai config --disconnect` там больше нет `jev.json` FailproofAI Cloud (если только он не был выключен, что сохраняется), поэтому `status` просто сообщает Jev как выключен. `status --json` содержит те же факты (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), также когда конфига нет или он отказан. `permissions` всегда из `jev.json`; отказ о `credentials.json` добавляет `credentialsPermissions` и `fix` когда одна команда его исправляет. `test` отправляет один живой запрос и сообщает его латентность и версию Jev, которая ответила. Он выходит с 1 и говорит об этом в заголовке, когда ответ приходит после тайм-аута хука (хуки записали бы `timeout`) или ответ на его проверку неправильно.

Панель **Settings → Jev** на панели управления также показывает **FailproofAI Cloud connection**: какой организации машина сообщает и несет ли ее ключ Jev. Это читается из собственных файлов машины, без сетевого вызова.

## Проверьте реальный вызов

Начните новый сеанс в подключенном агенте. Попросите его использовать свой инструмент чтения файлов на `README.md` и сообщить заголовок. Подтвердите, что сеанс содержит этот вызов инструмента, затем запустите `failproofai jev status` снова: счетчик недавно оцениваемых вызовов должен увеличиться. Откройте **Policies → Activity** в [локальной панели управления](/ru/reference/local-dashboard#review-policy-activity) для проверки вердикта Jev этого вызова и режима. В Cloud страница **Policies** организации показывает результаты Jev для доставленной активности. В режиме observe вердикт записывается как **would-have** и результат политики все еще решает вызов. Очистка появляется только когда обозреваемая политика совпала и Jev очистил ее именованные проверки.

## Что попадает на страницу политики

Машина уже отправляет активность своих хуков в FailproofAI Cloud (`events:add`). С Jev включенным, запись каждого вызова на вратах также говорит какой оценивающий работал, что Jev решил, какие политики он очистил, почему он откатился когда это произошло, его латентность и модель, которая ответила — решения, коды и имена, никогда команда или ваш запрос. На странице **Policies** вашей организации:

- вызов, решение которого принял сам вердикт Jev (режим enforce), приписан **Jev**, и когда проверка, которая решала, пришла из пакета, запись также называет этот пакет и его версию;
- в режиме observe отказ или предупреждение Jev появляется как **would-have**, рядом с развертываниями, которые вы наблюдаете;
- политики, которые Jev очистил или очистил бы в режиме observe, подсчитываются по политикам.
- решение, в котором участвовал Jev (блокировка, предупреждение, очистка или would-have в режиме observe), перечисляет каждую проверку, которую он спросил, и что эта проверка заключила: вердикт, почему (`not-detected`, `exempt`, `fired`, `op-requested`, …), его доказательство `p`, ответ `exempt` и каждый ответ зонда. Проверка политики, развернутой для просмотра (observe), также перечислена, отмечена as watched; она никогда не блокирует. Jev отвечает с вероятностями, не с прозой, поэтому нет свободного текста причины. Простые разрешения свертываются в подсчеты и не содержат этого списка.

## Когда Jev не может ответить

Каждый из них откатывается к результату политик для этого вызова и записывается с его причиной:

| Причина | Причина |
| --- | --- |
| `out-of-credits` | Ваша организация использовала выделение плана. |
| `http-401`, `http-403` | Ключ был отозван или не содержит `jev:evaluate`. Переподключитесь с ключом, который содержит. |
| `http-429` | FailproofAI Cloud применяет ограничение скорости Jev для вашей организации. До конца ожидания, которое оно просит (его `Retry-After`, максимум 60 секунд), машина не отправляет ему ничего и каждый вызов откатывается сразу же. Вызовы, удерживаемые таким образом, записываются как `http-429` или как `rate-limited` когда собственное ограничение скорости машины сначала их удерживает. |
| `http-429` (дневной лимит) | Ваша организация использовала свои дневные вызовы Jev: **10,000 за день UTC**, если только оператор вашего FailproofAI Cloud не установил другой лимит. Каждый вызов откатывается до сброса счетчика в 00:00 UTC; машина все еще спрашивает максимум раз в минуту, поэтому она замечает сброс в течение минуты. `failproofai jev test` говорит Daily Jev limit for this org reached; resets at 00:00 UTC. |
| `http-422` | Jev отказала этому запросу вызова, обычно потому что вызов инструмента содержал плотный текст (base64, hex, минифицированный код) сверх бюджета токенов Jev. Этот вызов откатывается каждый раз; это не сбой. |
| `http-502` | Jev недоступна прямо сейчас. |
| `http-503` | Этот Cloud не может служить Jev для вашей организации: нет шлюза модели, организация не подготовлена еще или шлюз не работает. Попросите вашего администратора; хуки спрашивают снова максимум раз в минуту. |
| `http-404` | Этот FailproofAI Cloud не служит Jev еще. |
| `timeout` | Нет ответа в течение `timeoutMs` (по умолчанию 3000). Пока FailproofAI Cloud устанавливает режим Jev машины, ожидание составляет 5000 мс и `timeoutMs` из `jev.json` не используется. |
| `model-mismatch` | Ответила версия Jev отличная от 1.13. |

## Где живет ключ и куда он идет

- Ключ сохраняется один раз в `~/.failproofai/credentials.json` (`0600`, в каталоге, доступном только владельцу), рядом с другими учетными данными FailproofAI Cloud. `jev.json` не содержит ключ для этого маршрута; один написанный там делает конфиг недействительным.
- Если `credentials.json` содержит **любое** разрешение для кого-либо кроме вас (группа или другие, чтение или запись) или его каталог может быть **написан** кем-либо кроме вас, это **отказано**, не читается, и Jev выключен до тех пор пока вы не исправите: `chmod 600` на файле, `chmod 700` на каталоге (или переподключитесь, что перепишет файл на `0600` и делает каталог доступным только владельцу). Каталог, который другие могут только читать, хорошо; один, который они могут писать, позволяет им заменить файл.
- Ключ рассчитывается только пока подключение, с которым он пришел, на машине: политика или учетные данные отчетности для того же FailproofAI Cloud **с тем же ключом**, в том же файле. Ключ Jev оставленный без одного игнорируется и Jev остается выключен. Это происходит когда более старый failproofai's `config --disconnect` оставляет ключ Jev на месте (он не знает удалить его), или когда более старый failproofai's `config --token` подключается с другим ключом, который на FailproofAI Cloud может принадлежать другой организации. Чтобы переключить Jev обратно включенным, подключитесь снова с ключом **machine**.
- Ключ отправляется только на источник Cloud, против которого он был проверен. `jev.json` указывающий где-то еще отказан.
- **Агент на машине может его прочитать.** `credentials.json` принадлежит только владельцу и агент работает как этот владелец. Чтение собственных файлов failproofai разрешено намеренно (только их изменение заблокировано, `block-failproofai-commands`), поэтому единственное между агентом и этим файлом это `block-read-outside-cwd` — *обозреваемая* политика — и из сеанса, начатого в вашем домашнем каталоге, ничего. Ключ с `jev:evaluate` тратит выделение Jev вашей организации (до дневного лимита) откуда бы он ни был использован, поэтому рассматривайте машинный ключ как любые другие учетные данные расходов: если агент мог его прочитать, отключите его на странице Keys и переподключитесь с новым.
- Только ваши глобальные файлы решают это. Репозиторий не может включить Cloud Jev, указать его где-то еще или предоставить его ключ, и `FAILPROOFAI_JEV_API_KEY` игнорируется для этого маршрута.
- Для каждого вызова, который Jev оценивает, один запрос идет в FailproofAI Cloud, несущий то что [страница собственного ключа](/ru/reference/jev-providers#what-leaves-the-machine) перечисляет (секреты отредактированы). FailproofAI Cloud пересылает его TypeSafe и не логирует и не сохраняет.

## Выключите это

На подключенной машине Jev выключен когда FailproofAI Cloud не развернул на нее политику Jev: удалите или архивируйте политики Jev там.

| Команда | Результат |
| --- | --- |
| Удалите политики Jev машины в FailproofAI Cloud | Режим Cloud становится `off` в следующем опросе (примерно 30 с): никакого Jev вообще, что бы `jev.json` ни говорил. |
| `failproofai config --disconnect` | Отключите машину: ключ удален и так же `jev.json` когда он называет FailproofAI Cloud и не выключен. `jev.json` для вашей собственной конечной точки остается. |

От следующего вызова инструмента хуки запускают политики regex ровно как раньше.
