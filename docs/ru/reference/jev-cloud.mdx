Это справочник маршрута Cloud для [политик Jev](/ru/policies/jev). Jev, классификатор TypeSafe, проверяет каждый вызов инструмента относительно того, что вы на самом деле просили, и отвечает наряду с вашими политиками, а не вместо них. Через **FailproofAI Cloud** подключённая машина использует Jev с тем же ключом, которым она уже подключается: никакого аккаунта TypeSafe, никакого второго ключа, никакой конечной точки для настройки. Каждый вызов списывается с лимита существующего плана вашей организации.

Всё, что делает Jev, остаётся неизменным по сравнению с [установкой с собственным ключом](/ru/reference/jev-providers): жёсткие политики остаются окончательными, отказ проверяемой политики отменяется только если Jev был спрошен ровно об этом вопросе, и любой сбой откатывается к результату регулярного выражения для этого вызова.

<Note>
Требует **failproofai 1.0.8-beta.0** или позже. 1.0.7 не содержит Jev, даже если он находится выше бета-версий 1.0.7. Без конфигурации Jev ничего не меняется: хуки запускают политики регулярного выражения ровно так же, как всегда.
</Note>

## Перед началом

Установите Failproof AI на машину, где работает ваш агент, и подключите её хуки к [поддерживаемой упряжке](/ru/reference/harnesses). Если вы начинаете с нуля, следуйте [быстрому старту](/ru/start/quickstart) до установки хуков. Проверьте установленный CLI командой `failproofai --version`; обновите его, если он предшествует Jev. Вам также нужен доступ к странице **Administration → Keys** вашей организации для создания машинного ключа.

Jev проверяет именованные вызовы инструментов на шлюзе `PreToolUse` или `PermissionRequest`. Он проверяет не каждое событие в сессии. Чтобы увидеть, как Jev отменяет отказ политики, вам нужна установленная политика, помеченная как [reviewable](/ru/policies/authority); все остальные отказы политик остаются окончательными.

## Включение

1. **Создайте ключ с Jev.** В панели FailproofAI Cloud откройте **Administration → Keys → Create key** и выберите предустановку **machine**. Она предоставляет три разрешения, которые нужны машине: `events:add` (отправка активности), `policies:pull` (получение политик) и `jev:evaluate` (Jev, списывается с плана вашей организации). Ключ не может иметь `jev:evaluate` без двух других.
2. **Подключите машину** этим ключом. Прочитайте его одноразовый секрет в подсказке, затем запустите полную команду настройки:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` устанавливает демон, подключает хуки для найденных CLI агентов и подключает машину. Переменная окружения защищает ключ от аргументов команды и истории вашей оболочки. Если ваша упряжка была установлена позже, [подключите её явно](/ru/start/quickstart).

   Если ваша организация запускает собственный FailproofAI Cloud вместо размещённого, добавьте его адрес: `--url https://<your dashboard host>` (или экспортируйте `FAILPROOFAI_CLOUD_URL`). Без него ключ проверяется с размещённой службой и подключение не удаётся. Если сертификат этого хоста выдан приватным УЦ, установите УЦ в хранилище доверия системы машины (например с `update-ca-certificates`), не только в `NODE_EXTRA_CA_CERTS`: демон, отправляющий события и получающий политики, читает системное хранилище. Смотрите [Troubleshooting](/ru/reference/troubleshooting).

Вот и всё. Подключение сохраняет ключ и, когда на машине **нет** конфигурации Jev, записывает её для FailproofAI Cloud. С первого развёртывания машины (в течение примерно 30 с) FailproofAI Cloud устанавливает режим: `enforce` пока политика Jev развёрнута на ней, `off` когда нет (смотрите [Кто устанавливает режим](#who-sets-the-mode)). Вывод показывает это:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Проверки, которые запускает FailproofAI Cloud, работают в Cloud. Чтобы добавить собственные проверки на машину, установите пакет:

```bash
failproofai policies add FailproofAI/jev-policies
```

**С `--no-transcripts` подключение не включает Jev.** Jev отправляет каждый проверяемый вызов инструмента и недавнюю подсказку на FailproofAI Cloud, что больше, чем подключение только решений просили отправить. Ключ всё ещё сохраняется, и вывод говорит, что Jev доступен и как его включить:

```bash
failproofai jev setup --provider failproofai
```

Он также выключает Jev через FailproofAI Cloud **off**. `jev.json`, запускающий Jev через FailproofAI Cloud (оставленный более ранним подключением с включённой передачей транскриптов), удаляется по той же логике, что использует `config --disconnect`, и вывод говорит, что Jev через FailproofAI Cloud остаётся отключённым на этой машине. `jev.json` для вашей собственной конечной точки Jev остаётся как есть, как и FailproofAI Cloud, который вы выключили (`--mode off`).

<Warning>
Подключение **никогда не перезаписывает** существующий `~/.failproofai/jev.json`. Если вы уже используете свою конечную точку Jev, она продолжит использоваться, и вывод скажет, что файл был оставлен как настроено — и, когда этот файл оставляет Jev отключённым (отказано или выключено), скажет так и как это исправить. Чтобы переключить эту машину на FailproofAI Cloud, запустите `failproofai jev setup --provider failproofai`.
</Warning>

## Кто устанавливает режим

На машине, подключённой к FailproofAI Cloud, **FailproofAI Cloud устанавливает режим Jev**; ничего на машине это не делает:

- `enforce` пока любая политика Jev (или регулярного выражения + Jev) развёрнута на машине: каждый проверяемый вызов инструмента от агента, которого одна из этих политик обслуживает, идёт на FailproofAI Cloud, который запрашивает его проверки вместе с проверками установленных там пакетов. Вызов от агента, которого никакая облачная политика Jev не обслуживает, с отсутствием собственной проверки пакета вообще не отправляется. В `enforce` собственные проверки отказа Jev блокируют вызовы, а также отменяют вердикты регулярного выражения, которые они проверяют.
- `off` когда нет: никакого Jev вообще, что бы ни говорил `jev.json`.

Чтобы попробовать политику Jev перед её действием, разверните её с эффектом **observe**: её проверки всё ещё запрашиваются, и что они бы сделали, записывается как **would-have** на странице политики, но она никогда не блокирует вызов и никогда не отменяет его. `failproofai jev setup --mode` и переключатель панели **Settings → Jev** в панели управления говорят, что режим управляется FailproofAI Cloud и ничего не меняют. `jev.json` не используется для проверок Cloud, даже если он называет другого провайдера. `failproofai config --disconnect` возвращает Jev собственному `jev.json` машины.

`failproofai jev status` тогда говорит `Jev checks run on FailproofAI Cloud (mode: enforce)`. Он также называет проверки, которые проверяют каждую политику `both`. Страница парка показывает, почему машина с режимом не может запросить:

- `transcripts_disabled`: машина была подключена с `--no-transcripts`, что никогда не включает Jev.
- `jev_unconfigured`: ключ машины не имеет `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud отказал в некоторых вызовах машины по лимиту частоты Jev организации, и эти вызовы были решены только политиками регулярного выражения.
- `jev_unavailable`: несколько вызовов подряд не удались, поэтому машина пропускает Jev FailproofAI Cloud на минуту за раз. Она повторяет попытку самостоятельно.

Если FailproofAI Cloud не ответит в течение 5 секунд, политики регулярного выражения решают одни, как при любом отключении Jev. После 3 сбоев подряд машина прекращает запрашивать на минуту за раз, поэтому отключение Cloud не замедляет каждый вызов инструмента.

Пауза сессии (`failproofai config --pause`) не останавливает проверки Jev FailproofAI Cloud, как и не останавливает управляемые Cloud политики. Она приостанавливает проверки Jev пакетов, установленных на машине.

## Проверка того, что оно делает

```bash
failproofai jev status
failproofai jev test
```

`status` показывает провайдера как **FailproofAI Cloud**, облачного хоста, к которому подключилась машина, режим, и источник ключа как **FailproofAI Cloud connection**, никогда не ключ. Когда `jev.json` FailproofAI Cloud на месте, но Jev не может работать, это говорит почему:

| `status` говорит | `status --json` | Значение |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Машина подключена, но для неё не сохранён ключ Jev: ключу не хватает `jev:evaluate`, или подключение не смогло его подтвердить. Запустите `failproofai config` снова с ключом в `FAILPROOFAI_CLOUD_TOKEN`; если ему не хватает разрешения, используйте ключ **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | На этой машине нет подключения FailproofAI Cloud, к которому ключ Jev мог бы принадлежать. |

После `failproofai config --disconnect` больше нет `jev.json` FailproofAI Cloud (если только он не был выключен, что сохраняется), поэтому `status` просто сообщает, что Jev выключен. `status --json` несёт те же факты (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), также когда конфигурация отсутствует или отказана. `permissions` всегда из `jev.json`; отказ о `credentials.json` добавляет `credentialsPermissions`, и `fix` когда одна команда это исправляет. `test` отправляет один живой запрос и сообщает его задержку и версию Jev, которая ответила. Он выходит с кодом 1 и говорит об этом в заголовке, когда ответ прибывает после тайм-аута хука (хуки бы записали `timeout`) или отвечает на вопрос проверки неправильно.

Панель **Settings → Jev** панели управления также показывает **FailproofAI Cloud connection**: в какую организацию сообщает машина и несёт ли её ключ Jev. Это читается из собственных файлов машины без сетевого вызова.

## Проверка реального вызова

Начните новую сессию в подключённом агенте. Попросите его использовать инструмент чтения файлов на `README.md` и сообщить название. Подтвердите, что сессия содержит этот вызов инструмента, затем запустите `failproofai jev status` снова: его недавний счётчик оценённых вызовов должен увеличиться. Откройте **Policies → Activity** в [локальной панели](/ru/reference/local-dashboard#review-policy-activity) для проверки вердикта Jev этого вызова и режима. В Cloud страница **Policies** организации показывает результаты Jev для доставленной активности. В режиме observe вердикт записывается как **would-have** и результат политики всё ещё решает вызов. Отмена появляется только когда проверяемая политика совпала и Jev отменил её именованные проверки.

## Что попадает на страницу политики

Машина уже отправляет активность своего хука на FailproofAI Cloud (`events:add`). С Jev включённым, запись каждого шлюзового вызова также говорит, какой оценивающий работал, что решил Jev, какие политики он отменил, почему он откатился когда это произошло, его задержку и модель, которая ответила — решения, коды и имена, никогда команду или вашу подсказку. На странице **Policies** вашей организации:

- вызов, решение которого принял вердикт Jev (режим enforce), приписывается **Jev**, и когда решающая проверка пришла из пакета, запись также называет этот пакет и его версию;
- в режиме observe отказ или предупреждение Jev появляется как **would-have**, рядом с rollouts, которые вы наблюдаете;
- политики, которые Jev отменил или что бы отменил в режиме observe, считаются за политику.
- решение, в котором Jev принял участие (блок, предупреждение, отмена или would-have в режиме observe), перечисляет каждую проверку, которую он запросил, и к какому выводу пришла эта проверка: вердикт, почему (`not-detected`, `exempt`, `fired`, `op-requested`, …), его доказательство `p`, ответ `exempt` и каждый ответ зонда. Проверка политики, развёрнутой для наблюдения (observe), также перечисляется, помеченная watched; она никогда не блокирует. Jev отвечает вероятностями, не прозой, поэтому нет свободного текста причины. Простые разрешения объединяются в счета и не несут этот список.

## Когда Jev не может ответить

Каждое из этих откатывается к результату ваших политик для этого вызова и записывается с причиной:

| Причина | Причина |
| --- | --- |
| `out-of-credits` | Ваша организация использовала лимит плана. |
| `http-401`, `http-403` | Ключ был отозван или не имеет `jev:evaluate`. Переподключитесь с ключом, который это имеет. |
| `http-429` | FailproofAI Cloud ограничивает частоту Jev для вашей организации. Пока не закончится ожидание, которое оно просит (его `Retry-After`, максимум 60 секунд), машина ничего ему не отправляет и каждый вызов откатывается сразу же. Вызовы, задержанные таким образом, записываются как `http-429`, или как `rate-limited` когда собственный лимит частоты машины их задерживает первым. |
| `http-429` (суточный лимит) | Ваша организация использовала суточный лимит вызовов Jev: **10 000 в день по UTC**, если только тот, кто управляет вашим FailproofAI Cloud, не установил другой лимит. Каждый вызов откатывается пока счёт не сбросится в 00:00 UTC; машина всё ещё запрашивает снова максимум раз в минуту, поэтому она подхватывает сброс в течение минуты. `failproofai jev test` говорит "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev отказал этому вызову, обычно потому что вызов инструмента содержал плотный текст (base64, hex, минифицированный код) за пределами бюджета токенов Jev. Этот вызов откатывается каждый раз; это не отключение. |
| `http-502` | Jev недоступен прямо сейчас. |
| `http-503` | Этот Cloud не может обслуживать Jev для вашей org: нет шлюза модели, org не подготовлена ещё или шлюз отключен. Спросите вашего администратора; хуки запрашивают снова максимум раз в минуту. |
| `http-404` | Этот FailproofAI Cloud ещё не обслуживает Jev. |
| `timeout` | Нет ответа в течение `timeoutMs` (по умолчанию 3000). Пока FailproofAI Cloud устанавливает режим Jev машины, ожидание составляет 5000 мс и `jev.json` `timeoutMs` не используется. |
| `model-mismatch` | Ответила версия Jev, отличная от 1.13. |

## Где живёт ключ и куда он идёт

- Ключ сохраняется один раз в `~/.failproofai/credentials.json` (`0600`, в директории, доступной только владельцу), рядом с другими учётными данными FailproofAI Cloud. `jev.json` не содержит ключа для этого маршрута; один, написанный там, делает конфигурацию недействительной.
- Если `credentials.json` несёт **какое-либо** разрешение для кого-то, кроме вас (группа или другое, чтение или запись), или его директория может быть **написана** кем-то, кроме вас, она **отказана**, не прочитана, и Jev отключен до того, как вы это исправите: `chmod 600` на файл, `chmod 700` на директорию (или переподключитесь, что переписывает файл в `0600` и делает директорию доступной только владельцу). Директория, которую другие только могут читать, в порядке; та, что они могут писать, позволяет им поменять файл.
- Ключ считается только пока подключение, с которым он пришёл, на машине: политика или учётные данные отчёта для одного FailproofAI Cloud **с тем же ключом**, в том же файле. Ключ Jev, оставленный без одного, игнорируется, и Jev остаётся отключен. Это происходит когда более старый failproofai `config --disconnect` оставляет ключ Jev на месте (он не знает его удалять), или когда более старый failproofai `config --token` подключается с другим ключом, который на FailproofAI Cloud может принадлежать другой организации. Чтобы переключить Jev обратно, подключитесь снова с ключом **machine**.
- Ключ отправляется только облачному источнику, против которого он был проверен. `jev.json`, указывающий куда-то ещё, отказана.
- **Агент на машине может его прочитать.** `credentials.json` доступен только владельцу, и агент работает как этот владелец. Чтение собственных файлов failproofai разрешено намеренно (только их изменение блокируется, по `block-failproofai-commands`), поэтому единственное, стоящее между агентом и этим файлом, это `block-read-outside-cwd` — *проверяемая* политика — и из сессии, начатой в вашей домашней директории, ничего. Ключ с `jev:evaluate` тратит лимит Jev вашей организации (до суточного лимита) откуда угодно, где он используется, поэтому обращайтесь с машинным ключом как с любым другим расходуемым учётным данным: если агент мог его прочитать, отключите его на странице Keys и переподключитесь с новым.
- Только ваши глобальные файлы это решают. Репозиторий не может включить Cloud Jev, указать его куда-то ещё или предоставить его ключ, и `FAILPROOFAI_JEV_API_KEY` игнорируется для этого маршрута.
- Для каждого вызова, который оценивает Jev, один запрос идёт на FailproofAI Cloud, несущий то, что перечисляет [страница собственного ключа](/ru/reference/jev-providers#what-leaves-the-machine) (секреты отредактированы). FailproofAI Cloud переправляет его на TypeSafe и не регистрирует или не сохраняет его.

## Выключение

На подключённой машине Jev выключен когда FailproofAI Cloud не развёртывает на неё политику Jev: удалите или архивируйте политики Jev там.

| Команда | Результат |
| --- | --- |
| Удалить политики Jev машины в FailproofAI Cloud | Режим Cloud становится `off` при следующем опросе (примерно 30 с): никакой Jev вообще, что бы ни говорил `jev.json`. |
| `failproofai config --disconnect` | Отключить машину: ключ удаляется, и так же `jev.json` когда он называет FailproofAI Cloud и не выключен. `jev.json` для вашей собственной конечной точки остаётся. |

С следующего вызова инструмента хуки запускают политики регулярного выражения ровно как раньше.
