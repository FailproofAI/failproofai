Это справочник маршрута Cloud для [политик Jev](/ru/policies/jev). Jev, классификатор TypeSafe, проверяет каждый вызов инструмента в соответствии с тем, что вы на самом деле запросили, и выдает результат наряду с вашими политиками, никогда вместо них. Через **FailproofAI Cloud** подключенная машина использует Jev с тем же ключом, которым она уже подключается: никакого аккаунта TypeSafe, никакого второго ключа, никакой точки назначения для настройки. Каждый вызов учитывается в рамках лимита плана вашей организации.

Всё, что делает Jev, не отличается от [настройки с собственным ключом](/ru/reference/jev-providers): жесткие политики остаются окончательными, отказ рецензируемой политики очищается только когда Jev был запрошен именно об этом вопросе, и любой сбой перенаправляется к результату regex для этого вызова.

<Note>
Требуется **failproofai 1.0.8-beta.0** или выше. 1.0.7 не содержит Jev, несмотря на то что сортируется выше бета-версий 1.0.7. Без конфигурации Jev ничего не меняется: хуки запускают политики regex точно как они всегда это делали.
</Note>

## Перед началом

Установите Failproof AI на машину, где запускается ваш агент, и прикрепите его хуки к [поддерживаемой утилите](/ru/reference/harnesses). Если вы начинаете с нуля, следуйте [быстрому старту](/ru/start/quickstart) до установки хуков. Проверьте установленный CLI с помощью `failproofai --version`; обновите его, если он предшествует Jev. Вам также нужен доступ к странице **settings → api keys** вашей организации для создания машинного ключа.

Jev проверяет именованные вызовы инструментов на вентилях `PreToolUse` или `PermissionRequest`. Он не проверяет каждое событие в сессии. Чтобы увидеть, как Jev очищает отказ политики, вам нужна установленная политика, помеченная как [рецензируемая](/ru/policies/authority); все остальные отказы политик остаются окончательными.

## Включение

1. **Создайте ключ с Jev.** На панели управления FailproofAI Cloud откройте **settings → api keys** и в форме **new key** выберите **a machine running failproofai**. Это дает три разрешения, которые нужны машине: `events:add` (отправка активности), `policies:pull` (получение политик) и `jev:evaluate` (Jev, отнесенный на счет плана вашей организации). Ключ не может иметь `jev:evaluate` без двух других.
2. **Подключите машину** с этим ключом. Прочитайте его одноразовый секрет при подсказке, затем запустите полную команду настройки:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` устанавливает демон, прикрепляет хуки для найденных CLI агентов и подключает машину. Переменная окружения сохраняет ключ из аргументов команды и истории вашей оболочки. Если ваша утилита была установлена позже, [прикрепите ее явно](/ru/start/quickstart).

   Если ваша организация запускает собственный FailproofAI Cloud вместо хостированного, добавьте его адрес: `--url https://<your dashboard host>` (или экспортируйте `FAILPROOFAI_CLOUD_URL`). Без этого ключ проверяется против хостированного сервиса и подключение не удается. Если сертификат этого хоста выдан приватным CA, установите CA в системное хранилище доверия машины (например с помощью `update-ca-certificates`), не только в `NODE_EXTRA_CA_CERTS`: демон, отправляющий события и получающий политики, читает системное хранилище. См. [Troubleshooting](/ru/reference/troubleshooting).

Это всё. Подключение сохраняет ключ и, когда на машине **нет** конфигурации Jev, создает одну для FailproofAI Cloud. С первого развертывания машины (примерно в течение 30 с) FailproofAI Cloud устанавливает режим: `enforce` пока политика Jev развернута на ней, `off` когда нет (см. [Кто устанавливает режим](#кто-устанавливает-режим)). Вывод это показывает:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Проверки, развертываемые FailproofAI Cloud, работают на Cloud. Чтобы добавить собственные проверки на машину, установите пакет:

```bash
failproofai policies add FailproofAI/jev-policies
```

**С `--no-transcripts` подключение не включает Jev.** Jev отправляет каждый проверенный вызов инструмента и недавнее приглашение на FailproofAI Cloud, что больше, чем подключение только с решениями просило отправить. Ключ все еще сохраняется, и вывод говорит, что Jev доступен и как его включить:

```bash
failproofai jev setup --provider failproofai
```

Он также **отключает** Jev через FailproofAI Cloud. `jev.json`, который запускает Jev через FailproofAI Cloud (оставленный предыдущим подключением с включенными расшифровками), удаляется по тому же правилу, которое использует `config --disconnect`, и вывод говорит, что Jev через FailproofAI Cloud остается отключенным на этой машине. `jev.json` для вашей собственной точки Jev остается как есть, так же как и облачный, который вы отключили (`--mode off`).

<Warning>
Подключение **никогда не перезаписывает** существующий `~/.failproofai/jev.json`. Если вы уже используете собственную точку Jev, она продолжает использоваться, и вывод говорит, что файл был оставлен как настроено — и, когда этот файл оставляет Jev отключенным (отказано, или отключено), говорит об этом и как это исправить. Чтобы переключить эту машину на FailproofAI Cloud, запустите `failproofai jev setup --provider failproofai`.
</Warning>

## Кто устанавливает режим

На машине, подключенной к FailproofAI Cloud, **FailproofAI Cloud устанавливает режим Jev**; ничто на машине этого не делает:

- `enforce` пока любая политика Jev (или regex + Jev) развернута на машину: каждый проверенный вызов инструмента от агента, которого эти политики нацеливают, отправляется на FailproofAI Cloud, который просит его проверки вместе с проверками установленных там пакетов. Вызов от агента, которого никакая облачная политика Jev не нацеливает, с собственной проверкой пакета нет, вообще не отправляется. В `enforce` собственные проверки отказа Jev блокируют вызовы так же как очищают результаты regex, которые они проверяют.
- `off` когда ничего нет: никакой Jev вообще, что бы `jev.json` ни говорил.

Чтобы попробовать политику Jev перед тем, как она действует, разверните ее с эффектом **observe**: её проверки все еще запрашиваются, и что они бы сделали, записывается как **would-have** под **fix → activity**, но она никогда не блокирует вызов и никогда не очищает один. `failproofai jev setup --mode` и переключатели режима локальной панели управления **Settings → Jev** говорят, что режим управляется FailproofAI Cloud и ничего не меняют. `jev.json` не используется для проверок Cloud, даже если он называет другого поставщика. `failproofai config --disconnect` возвращает Jev к собственному `jev.json` машины.

`failproofai jev status` тогда говорит `Jev checks run on FailproofAI Cloud (mode: enforce)`. Он также называет проверки, которые проверяют каждую политику `both`. Страница флота показывает, почему машина с режимом не может спросить:

- `transcripts_disabled`: машина была подключена с `--no-transcripts`, что никогда не включает Jev.
- `jev_unconfigured`: ключ машины не несет `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud отказал некоторым вызовам машины из-за лимита скорости Jev организации, и эти вызовы были решены политиками regex в одиночку.
- `jev_unavailable`: несколько вызовов подряд не удались, поэтому машина пропускает Jev FailproofAI Cloud на минуту за раз. Она повторяет попытку самостоятельно.

Если FailproofAI Cloud не отвечает в течение 5 секунд, политики regex решают в одиночку, как при любом отключении Jev. После 3 ошибок подряд машина перестает спрашивать на минуту за раз, поэтому отключение Cloud не замедляет каждый вызов инструмента.

Пауза сессии (`failproofai config --pause`) не останавливает проверки Jev FailproofAI Cloud, точно так же как она не останавливает управляемые Cloud политики. Она приостанавливает проверки Jev пакетов, установленных на машину.

## Проверка того, что происходит

```bash
failproofai jev status
failproofai jev test
```

`status` показывает поставщика как **FailproofAI Cloud**, облачный хост, к которому подключена машина, режим, и источник ключа как **FailproofAI Cloud connection**, никогда сам ключ. Когда `jev.json` FailproofAI Cloud на месте, но Jev не может работать, он говорит почему:

| `status` говорит | `status --json` | Значение |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Машина подключена, но для неё не сохранен ключ Jev: ключ лишен `jev:evaluate`, или подключение не могло его подтвердить. Запустите `failproofai config` снова с ключом в `FAILPROOFAI_CLOUD_TOKEN`; если ему не хватает разрешения, используйте ключ **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | На этой машине нет подключения FailproofAI Cloud, к которому принадлежит ключ Jev. |

После `failproofai config --disconnect` там больше нет `jev.json` FailproofAI Cloud (если только его не отключили, что сохраняется), так что `status` просто сообщает Jev как отключенный. `status --json` несет те же факты (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), также когда конфиг отсутствует или отказан. `permissions` всегда `jev.json`'s; отказ о `credentials.json` добавляет `credentialsPermissions`, и `fix` когда одна команда его исправляет. `test` отправляет один живой запрос и сообщает его задержку и версию Jev, которая ответила. Он выходит с кодом 1 и говорит об этом в заголовке, когда ответ приходит после истечения времени хука (хуки запишут `timeout`) или отвечает на его вопрос проверки неправильно.

Локальная панель управления **Settings → Jev** также показывает **FailproofAI Cloud connection**: в какую организацию сообщает машина и несет ли её ключ Jev. Это читается из собственных файлов машины, без сетевого вызова.

## Проверка реального вызова

Начните новую сессию в подключенном агенте. Попросите его использовать инструмент чтения файлов на `README.md` и сообщить название. Подтвердите, что сессия содержит этот вызов инструмента, затем запустите `failproofai jev status` снова: его счетчик недавно оцененных вызовов должен увеличиться. Откройте **Policies → Activity** в [локальной панели управления](/ru/reference/local-dashboard#review-policy-activity) для инспекции вердикта Jev этого вызова и режима. В Cloud, **fix → activity** показывает результаты Jev для доставленной активности. В режиме observe вердикт записывается как **would-have** и результат политики все еще решает вызов. Очистка появляется только когда рецензируемая политика совпала и Jev очистил её названные проверки.

## Что попадает на страницу политики

Машина уже отправляет свою активность хука на FailproofAI Cloud (`events:add`). С включенным Jev, запись каждого гейтового вызова также говорит, какой оценщик работал, что решил Jev, какие политики он очистил, почему он вернулся когда это сделал, его задержку и модель, которая ответила — решения, коды и имена, никогда команду или ваше приглашение. В Cloud, под **fix → activity**:

- вызов, решение которого определил собственный вердикт Jev (режим enforce) приписывается **Jev**, и когда решающая проверка пришла из пакета, запись также называет этот пакет и его версию;
- в режиме observe отказ или предупреждение Jev появляется как **would-have**, рядом с развертываниями, которые вы наблюдаете;
- политики, которые Jev очистил, или которые бы очистил в режиме observe, подсчитываются за политику.
- решение, в котором Jev участвовал (блокировка, предупреждение, очистка или would-have в режиме observe) перечисляет каждую проверку, которую он попросил, и к какому выводу пришла эта проверка: вердикт, почему (`not-detected`, `exempt`, `fired`, `op-requested`, …), её доказательства `p`, ответ `exempt` и ответ каждого зонда. Проверка политики, развернутой для просмотра (observe) также указывается, отмечена как просматриваемая; она никогда не блокирует. Jev отвечает с вероятностями, а не прозой, поэтому нет свободного текста причины. Простые разрешения сворачиваются в подсчеты и не несут этот список.

## Когда Jev не может ответить

Каждый из этих случаев возвращается к результату ваших политик для этого вызова и записывается с его причиной:

| Причина | Причина |
| --- | --- |
| `out-of-credits` | Ваша организация использовала свой лимит плана. |
| `http-401`, `http-403` | Ключ был отозван, или не несет `jev:evaluate`. Переподключитесь с ключом, который это имеет. |
| `http-429` | FailproofAI Cloud ограничивает скорость Jev для вашей организации. До истечения ожидания, которое оно просит (его `Retry-After`, максимум 60 секунд), машина ничего ему не отправляет и каждый вызов сразу же возвращается. Вызовы, задержанные таким образом, записываются как `http-429`, или как `rate-limited` когда собственный лимит скорости машины их сначала задерживает. |
| `http-429` (дневной лимит) | Ваша организация использовала свои дневные вызовы Jev: **10 000 за день UTC**, если только оператор вашего FailproofAI Cloud не установил другой лимит. Каждый вызов возвращается до того, как счетчик сбросится в 00:00 UTC; машина все еще спрашивает максимум один раз в минуту, поэтому она подхватывает сброс в течение минуты. `failproofai jev test` говорит "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev отказал запросу этого вызова, обычно потому что вызов инструмента содержал плотный текст (base64, hex, минифицированный код) сверх бюджета токенов Jev. Этот вызов возвращается каждый раз; это не отключение. |
| `http-502` | Jev недоступен прямо сейчас. |
| `http-503` | Это Cloud не может обслуживать Jev для вашей организации: нет шлюза модели, организация не подготовлена еще, или шлюз не работает. Спросите вашего администратора; хуки спрашивают снова максимум один раз в минуту. |
| `http-404` | Этот FailproofAI Cloud еще не обслуживает Jev. |
| `timeout` | Нет ответа в течение `timeoutMs` (по умолчанию 3000). Пока FailproofAI Cloud устанавливает режим Jev машины, ожидание 5000 мс и `jev.json`'s `timeoutMs` не используется. |
| `model-mismatch` | Версия Jev отличная от 1.13 ответила. |

## Где живет ключ и куда он идет

- Ключ сохраняется один раз в `~/.failproofai/credentials.json` (`0600`, в каталоге, принадлежащем только владельцу), рядом с другими учетными данными FailproofAI Cloud. `jev.json` не содержит ключ для этого маршрута; один написанный там делает конфиг недействительным.
- Если `credentials.json` несет **любое** разрешение для кого-то, кроме вас (группы или других, чтения или записи), или его каталог может быть **написан** кем-то, кроме вас, он **отказан**, не прочитан, и Jev выключен до того, как вы это исправите: `chmod 600` на файл, `chmod 700` на каталог (или переподключитесь, что перепишет файл в `0600` и сделает каталог принадлежащим только владельцу). Каталог, который другие могут только читать, в порядке; один, который они могут писать, дает им возможность поменять файл.
- Ключ считается только пока подключение, с которым он пришел, находится на машине: политика или учетные данные отчета для того же FailproofAI Cloud **с тем же ключом**, в том же файле. Ключ Jev, оставленный без одного, игнорируется, и Jev остается отключенным. Это происходит когда старый failproofai's `config --disconnect` оставляет ключ Jev на месте (он не знает удалять его), или когда старый failproofai's `config --token` подключается с другим ключом, который на FailproofAI Cloud может принадлежать другой организации. Чтобы переключить Jev обратно, подключитесь снова с ключом **machine**.
- Ключ только отправляется на облачное происхождение, против которого он был проверен. `jev.json`, указывающий где-либо еще, отказан.
- **Агент на машине может его прочитать.** `credentials.json` принадлежит только владельцу, и агент работает как этот владелец. Чтение собственных файлов failproofai разрешено специально (только их изменение блокируется, `block-failproofai-commands`), поэтому единственное, что стоит между агентом и этим файлом, это `block-read-outside-cwd` — *рецензируемая* политика — и из сессии, начатой в вашем домашнем каталоге, ничего. Ключ с `jev:evaluate` тратит лимит Jev вашей организации (до дневной шапки) откуда угодно он используется, поэтому относитесь к машинному ключу как к любому другому расходному учетному данному: если агент может его прочитать, отзовите его на **settings → api keys** и переподключитесь с новым.
- Это решают только ваши глобальные файлы. Репозиторий не может включить облачный Jev, направить его в другое место или предоставить его ключ, и `FAILPROOFAI_JEV_API_KEY` игнорируется для этого маршрута.
- Для каждого вызова, который Jev оценивает, один запрос идет на FailproofAI Cloud, несущий то, что перечисляет [страница bring-your-own-key](/ru/reference/jev-providers#what-leaves-the-machine) (секреты отредактированы). FailproofAI Cloud передает его TypeSafe и не логирует или не хранит его.

## Отключение

На подключенной машине Jev выключен когда FailproofAI Cloud не развертывает на неё политику Jev: удалите или архивируйте политики Jev там.

| Команда | Результат |
| --- | --- |
| Удалите политики Jev машины в FailproofAI Cloud | Режим Cloud становится `off` при следующем опросе (примерно 30 с): никакой Jev вообще, что бы `jev.json` ни говорил. |
| `failproofai config --disconnect` | Отключите машину: ключ удаляется, и так же `jev.json` когда он называет FailproofAI Cloud и не отключен. `jev.json` для вашей собственной точки остается. |

С следующего вызова инструмента хуки запускают политики regex точно как раньше.
