Это справочник маршрута Cloud для [политик Jev](/ru/policies/jev). Jev, классификатор TypeSafe, проверяет каждый вызов инструмента в соответствии с тем, что вы на самом деле запросили, и дает ответ наряду с вашими политиками, а не вместо них. Через **FailproofAI Cloud** подключенная машина использует Jev с тем же ключом, который она уже использует для подключения: без учетной записи TypeSafe, без второго ключа, без конечной точки для настройки. Каждый вызов учитывается в рамках существующего плана вашей организации.

Все, что делает Jev, не изменяется по сравнению с [настройкой собственного ключа](/ru/reference/jev-providers): жесткие политики остаются окончательными, отказ рецензируемой политики очищается только когда Jev был запрошен именно об этой проблеме, и любой сбой переходит на результат regex для этого вызова.

<Note>
Требует **failproofai 1.0.8-beta.0** или позже. 1.0.7 не содержит Jev, даже если он сортируется выше бета-версий 1.0.7. Без конфигурации Jev ничего не меняется: хуки запускают политики regex точно так же, как всегда.
</Note>

## Перед началом

Установите Failproof AI на машину, где работает ваш агент, и подключите его хуки к [поддерживаемому harness](/ru/reference/harnesses). Если вы начинаете с нуля, следуйте [быстрому старту](/ru/start/quickstart) через установку хуков. Проверьте установленный CLI с помощью `failproofai --version`; обновите его, если он предшествует Jev. Вам также нужен доступ к странице **settings → api keys** вашей организации для создания машинного ключа.

Jev проверяет именованные вызовы инструментов на вентиле `PreToolUse` или `PermissionRequest`. Он не проверяет каждое событие в сеансе. Чтобы увидеть, как Jev очищает отказ политики, вам нужна установленная политика, отмеченная как [рецензируемая](/ru/policies/authority); все остальные отказы политик остаются окончательными.

## Включение

1. **Создайте ключ с Jev.** На панели управления FailproofAI Cloud откройте **settings → api keys** и в форме **новый ключ** выберите **машину, работающую на failproofai**. Он предоставляет три разрешения, которые требуются машине: `events:add` (отправка активности), `policies:pull` (получение политик) и `jev:evaluate` (Jev, учитывается в плане вашей организации). Ключ не может иметь `jev:evaluate` без двух других.
2. **Подключите машину** с этим ключом. Прочитайте его одноразовый секрет при подсказке, затем запустите полную команду настройки:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` устанавливает демона, подключает хуки для найденных агентов CLI и подключает машину. Переменная окружения сохраняет ключ вне аргументов команды и истории вашей оболочки. Если ваш harness был установлен позже, [подключите его явно](/ru/start/quickstart).

   Если ваша организация запускает собственное FailproofAI Cloud вместо размещенного, добавьте его адрес: `--url https://<your dashboard host>` (или экспортируйте `FAILPROOFAI_CLOUD_URL`). Без него ключ проверяется в размещенном сервисе и соединение не устанавливается. Если сертификат этого хоста выдан приватным ЦС, установите ЦС в системное хранилище доверия машины (например с помощью `update-ca-certificates`), не только в `NODE_EXTRA_CA_CERTS`: демон, отправляющий события и получающий политики, читает системное хранилище. Смотрите [Устранение неполадок](/ru/reference/troubleshooting).

Это все. Подключение сохраняет ключ и, когда на машине **нет** конфигурации Jev, создает конфигурацию для FailproofAI Cloud. Начиная с первого развертывания машины (примерно в течение 30 с) FailproofAI Cloud устанавливает режим: `enforce` при наличии развернутой политики Jev, `off` при отсутствии (смотрите [Кто устанавливает режим](#who-sets-the-mode)). Вывод это показывает:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Проверки, которые запускает FailproofAI Cloud, работают на Cloud. Чтобы добавить собственные проверки на машине, установите пакет:

```bash
failproofai policies add FailproofAI/jev-policies
```

**С `--no-transcripts` подключение не включает Jev.** Jev отправляет каждый проверяемый вызов инструмента и недавнее приглашение на FailproofAI Cloud, что больше, чем ожидается от соединения только решений. Ключ все еще сохраняется, и вывод говорит, что Jev доступен и как его включить:

```bash
failproofai jev setup --provider failproofai
```

Это также выключает Jev через FailproofAI Cloud. `jev.json`, который запускает Jev через FailproofAI Cloud (оставленный при более раннем подключении с включенными транскриптами), удаляется по тому же правилу, которое использует `config --disconnect`, и вывод говорит, что Jev через FailproofAI Cloud остается выключенным на этой машине. `jev.json` для вашей собственной конечной точки Jev остается как есть, также как и конечная точка FailproofAI Cloud, которую вы выключили (`--mode off`).

<Warning>
Подключение **никогда не перезаписывает** существующий `~/.failproofai/jev.json`. Если вы уже используете собственную конечную точку Jev, она продолжит использоваться, и вывод скажет, что файл остался сконфигурированным — и, когда этот файл оставляет Jev выключенным (отказ или выключено), это скажет и как это исправить. Чтобы переключить эту машину на FailproofAI Cloud, запустите `failproofai jev setup --provider failproofai`.
</Warning>

## Кто устанавливает режим

На машине, подключенной к FailproofAI Cloud, **FailproofAI Cloud устанавливает режим Jev**; ничего на машине этого не делает:

- `enforce` пока любая политика Jev (или regex + Jev) развернута на машине: каждый проверяемый вызов инструмента от агента, которого эта политика целевой, отправляется на FailproofAI Cloud, который просит его проверки вместе с проверками установленных там пакетов. Вызов от агента, которого никакая облачная политика Jev не целевой, без собственной проверки пакета, вообще не отправляется. В `enforce` собственные проверки отказа Jev блокируют вызовы и также очищают вердикты regex, которые они рецензируют.
- `off` когда ничего этого нет: никакого Jev вообще, что бы ни говорил `jev.json`.

Чтобы попробовать политику Jev перед тем, как она подействует, разверните ее с эффектом **observe**: ее проверки все еще запрашиваются, и что они бы сделали, записывается как **would-have** под **fix → activity**, но она никогда не блокирует вызов и никогда его не очищает. `failproofai jev setup --mode` и переключатели режима местной панели управления **Settings → Jev** говорят, что режим управляется FailproofAI Cloud и ничего не меняют. `jev.json` не используется для проверок Cloud, даже если он указывает другого поставщика. `failproofai config --disconnect` возвращает Jev машинному собственному `jev.json`.

`failproofai jev status` тогда говорит `Jev checks run on FailproofAI Cloud (mode: enforce)`. Он также указывает проверки, которые рецензируют каждую политику `both`. На странице флота показано, почему машина с режимом не может спрашивать:

- `transcripts_disabled`: машина была подключена с `--no-transcripts`, что никогда не включает Jev.
- `jev_unconfigured`: ключ машины не имеет `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud отказал некоторым вызовам машины из-за лимита скорости Jev организации, и эти вызовы были решены политиками regex отдельно.
- `jev_unavailable`: несколько вызовов подряд не удались, поэтому машина пропускает Jev FailproofAI Cloud на минуту за раз. Он повторяет попытку самостоятельно.

Если FailproofAI Cloud не ответит в течение 5 секунд, политики regex решают отдельно, как для любого сбоя Jev. После 3 последовательных сбоев машина прекращает спрашивать на минуту за раз, поэтому сбой Cloud не замедляет каждый вызов инструмента.

Пауза сеанса (`failproofai config --pause`) не останавливает проверки Jev FailproofAI Cloud, точно так же как она не останавливает управляемые Cloud политики. Она приостанавливает проверки Jev пакетов, установленных на машине.

## Проверьте, что она делает

```bash
failproofai jev status
failproofai jev test
```

`status` показывает поставщика как **FailproofAI Cloud**, хост Cloud, к которому подключена машина, режим, и источник ключа как **FailproofAI Cloud connection**, никогда сам ключ. Когда находится на месте `jev.json` FailproofAI Cloud, но Jev не может работать, он говорит почему:

| `status` говорит | `status --json` | Значение |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Машина подключена, но ключ Jev для нее не сохранен: ключ не имеет `jev:evaluate`, или подключение не могло его подтвердить. Запустите `failproofai config` снова с ключом в `FAILPROOFAI_CLOUD_TOKEN`; если ему не хватает разрешения, используйте ключ **машины**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | Нет соединения FailproofAI Cloud на этой машине, к которому ключ Jev мог бы принадлежать. |

После `failproofai config --disconnect` там больше нет `jev.json` FailproofAI Cloud (если только он не был выключен, который сохраняется), поэтому `status` просто сообщает Jev как выключенный. `status --json` имеет те же факты (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), также когда конфигурация отсутствует или отказана. `permissions` всегда из `jev.json`; отказ о `credentials.json` добавляет `credentialsPermissions`, и `fix` когда одна команда его исправляет. `test` отправляет один живой запрос и сообщает его задержку и версию Jev, которая ответила. Он выходит с кодом 1 и говорит об этом в заголовке, когда ответ приходит после истечения времени хука (хуки запишут `timeout`) или неправильно отвечает на вопрос проверки.

Локальная панель управления **Settings → Jev** также показывает **FailproofAI Cloud connection**: в какую организацию сообщает машина и имеет ли ее ключ Jev. Он читается из собственных файлов машины, без сетевого вызова.

## Проверьте реальный вызов

Начните новый сеанс в присоединенном агенте. Попросите его использовать инструмент чтения файлов на `README.md` и сообщить заголовок. Подтвердите, что сеанс содержит этот вызов инструмента, затем запустите `failproofai jev status` снова: его счетчик недавних вычисленных вызовов должен увеличиться. Откройте **Policies → Activity** в [локальной панели управления](/ru/reference/local-dashboard#review-policy-activity) для проверки вердикта Jev этого вызова и режима. В Cloud, **fix → activity** показывает результаты Jev для доставленной активности. В режиме observe вердикт записывается как **would-have** и результат политики все еще решает вызов. Очистка появляется только когда рецензируемая политика совпала и Jev очистила ее именованные проверки.

## Что попадает на страницу политик

Машина уже отправляет свою активность хуков на FailproofAI Cloud (`events:add`). С включенным Jev запись каждого закрытого вызова также указывает, какой оценщик работал, что решил Jev, какие политики он очистил, почему он переходил на резервный вариант когда это происходило, его задержку и модель, которая ответила — решения, коды и имена, никогда команду или ваше приглашение. В Cloud, под **fix → activity**:

- вызов, который собственный вердикт Jev решил (режим enforce), приписывается **Jev**, и когда решающая проверка пришла из пакета, запись также называет этот пакет и его версию;
- в режиме observe отказ или предупреждение Jev появляется как **would-have**, рядом с откатами, которые вы наблюдаете;
- политики, которые Jev очистил, или которые бы очистил в режиме observe, подсчитываются для каждой политики.
- решение, в котором участвовал Jev (блокировка, предупреждение, очистка, или would-have в режиме observe), перечисляет каждую запрошенную проверку и что эта проверка заключила: вердикт, почему (`not-detected`, `exempt`, `fired`, `op-requested`, …), его доказательство `p`, ответ `exempt` и каждый ответ зонда. Проверка политики, развернутой для просмотра (observe), также указана, отмечена как просмотренная; она никогда не блокирует. Jev отвечает с вероятностями, а не прозой, поэтому нет свободного текстового причины. Простые разрешения свертываются в подсчеты и не переносят этот список.

## Когда Jev не может ответить

Каждый из этих переходит на результат ваших политик для этого вызова и записывается с его причиной:

| Причина | Причина |
| --- | --- |
| `out-of-credits` | Ваша организация использовала допустимый объем плана. |
| `http-401`, `http-403` | Ключ был отозван, или не имеет `jev:evaluate`. Переподключитесь с ключом, который имеет. |
| `http-429` | FailproofAI Cloud ограничивает скорость Jev для вашей организации. До истечения ожидания, которое оно просит (его `Retry-After`, максимум 60 секунд), машина ничего не отправляет и каждый вызов сразу переходит на резервный вариант. Вызовы, задержанные таким образом, записываются как `http-429`, или как `rate-limited` когда собственный лимит скорости машины их задерживает первым. |
| `http-429` (дневной лимит) | Ваша организация использовала свои дневные вызовы Jev: **10,000 за день UTC**, если только оператор вашего FailproofAI Cloud не установил другой лимит. Каждый вызов переходит на резервный вариант до сброса счетчика в 00:00 UTC; машина все еще спрашивает самое большее раз в минуту, поэтому она подхватывает сброс в течение минуты. `failproofai jev test` говорит "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev отказал этому запросу вызова, обычно потому что вызов инструмента содержал плотный текст (base64, hex, минифицированный код) сверх бюджета токенов Jev. Этот вызов переходит на резервный вариант каждый раз; это не сбой. |
| `http-502` | Jev недоступен прямо сейчас. |
| `http-503` | Это Cloud не может обслуживать Jev для вашей организации: нет шлюза модели, организация еще не подготовлена, или шлюз упал. Спросите вашего администратора; хуки спрашивают снова самое большее раз в минуту. |
| `http-404` | Это FailproofAI Cloud еще не обслуживает Jev. |
| `timeout` | Нет ответа в течение `timeoutMs` (по умолчанию 3000). Пока FailproofAI Cloud устанавливает режим Jev машины, ожидание составляет 5000 мс и `timeoutMs` из `jev.json` не используется. |
| `model-mismatch` | Ответила версия Jev отличная от 1.13. |

## Где ключ живет и куда он идет

- Ключ сохраняется один раз в `~/.failproofai/credentials.json` (`0600`, в каталоге только для владельца), рядом с другими учетными данными FailproofAI Cloud. `jev.json` не содержит ключа для этого маршрута; один написанный там делает конфигурацию недействительной.
- Если `credentials.json` содержит **какое-либо** разрешение для кого-либо, кроме вас (группа или другое, чтение или запись), или его каталог может быть **записан** кем-либо, кроме вас, он **отказан**, не прочитан, и Jev выключен, пока вы не исправите это: `chmod 600` в файле, `chmod 700` в каталоге (или переподключитесь, которое переписывает файл в `0600` и делает каталог только для владельца). Каталог, который другие могут только читать, нормален; один, который они могут писать, позволяет им поменять файл.
- Ключ считается только пока соединение, которое он пришел с, находится на машине: политика или учетные данные отчетности для того же FailproofAI Cloud **с тем же ключом**, в том же файле. Ключ Jev, оставленный позади без одного, игнорируется, и Jev остается выключенным. Это происходит когда старший failproofai's `config --disconnect` оставляет ключ Jev на месте (он не знает удалить его), или когда старший failproofai's `config --token` подключается с другим ключом, который на FailproofAI Cloud может принадлежать другой организации. Чтобы переключить Jev назад, подключитесь снова с ключом **машины**.
- Ключ только когда-либо отправляется на источник Cloud, против которого он был проверен. `jev.json`, указывающий в другое место, отказан.
- **Агент на машине может его прочитать.** `credentials.json` только для владельца, и агент работает как этот владелец. Чтение собственных файлов failproofai разрешено специально (только их изменение блокируется, с помощью `block-failproofai-commands`), поэтому единственное, что стоит между агентом и этим файлом, это `block-read-outside-cwd` — *рецензируемая* политика — и из сеанса, запущенного в вашем домашнем каталоге, ничего. Ключ с `jev:evaluate` тратит допустимый объем Jev вашей организации (до дневного предела) откуда бы он не использовался, поэтому относитесь к машинному ключу как к любым другим учетным данным расходов: если агент мог его прочитать, отзовите его на **settings → api keys** и переподключитесь с новым.
- Только ваши глобальные файлы решают это. Репозиторий не может включить Cloud Jev, указать его в другое место или предоставить его ключ, и `FAILPROOFAI_JEV_API_KEY` игнорируется для этого маршрута.
- Для каждого вызова, который Jev оценивает, один запрос идет на FailproofAI Cloud, переносящий то, что перечисляет [страница собственного ключа](/ru/reference/jev-providers#what-leaves-the-machine) (секреты отредактированы). FailproofAI Cloud пересылает его TypeSafe и не регистрирует или не сохраняет.

## Выключение

На подключенной машине Jev выключен когда FailproofAI Cloud развертывает никакую политику Jev на нее: удалите или архивируйте политики Jev там.

| Команда | Результат |
| --- | --- |
| Удалите политики Jev машины в FailproofAI Cloud | Режим Cloud становится `off` при следующем опросе (примерно 30 с): никакого Jev вообще, что бы ни говорил `jev.json`. |
| `failproofai config --disconnect` | Отключите машину: ключ удален, и удален `jev.json` когда он называет FailproofAI Cloud и не выключен. `jev.json` для вашей собственной конечной точки остается. |

Начиная со следующего вызова инструмента, хуки запускают политики regex точно как раньше.
