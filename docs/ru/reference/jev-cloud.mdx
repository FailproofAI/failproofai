Это справочник облачного маршрута для [политик Jev](/ru/policies/jev). Jev, классификатор TypeSafe, проверяет каждый вызов инструмента на соответствие тому, что вы на самом деле запросили, и выдаёт рекомендации наряду с вашими политиками, но никогда вместо них. Через **FailproofAI Cloud** подключённая машина использует Jev с тем же ключом, которым она уже подключена: ни учётной записи TypeSafe, ни второго ключа, ни конечной точки для настройки. Каждый вызов списывается с лимита плана вашей организации.

Всё, что делает Jev, остаётся неизменным от [конфигурации с собственным ключом](/ru/reference/jev-providers): жёсткие политики остаются окончательными, отказ рецензируемой политики очищается только когда Jev был спрошен ровно об этой проблеме, и любой сбой откатывается к результату регулярного выражения для этого вызова.

<Note>
Требует **failproofai 1.0.8-beta.0** или выше. В 1.0.7 нет Jev, несмотря на то что версия выше 1.0.7 бета. Без конфигурации Jev ничего не меняется: хуки запускают политики регулярных выражений ровно так, как всегда.
</Note>

## Прежде чем начать

Установите Failproof AI на машину, где работает ваш агент, и присоедините его хуки к [поддерживаемой системе](/ru/reference/harnesses). Если вы начинаете с нуля, следите за [быстрым стартом](/ru/start/quickstart) до установки хуков. Проверьте установленный CLI с помощью `failproofai --version`; обновите его, если он старше Jev. Вам также нужен доступ к странице **Administration → Keys** вашей организации для создания машинного ключа.

Jev проверяет именованные вызовы инструментов на вратах `PreToolUse` или `PermissionRequest`. Он проверяет не каждое событие в сеансе. Чтобы увидеть, как Jev очищает отказ политики, вам нужна установленная политика, отмеченная как [рецензируемая](/ru/policies/authority); все остальные отказы политик остаются окончательными.

## Включите это

1. **Создайте ключ с Jev.** На панели управления FailproofAI Cloud откройте **Administration → Keys → Create key** и выберите предустановку **machine**. Она даёт три разрешения, которые нужны машине: `events:add` (отправлять действия), `policies:pull` (получать политики) и `jev:evaluate` (Jev, списывается на план вашей организации). Ключ не может иметь `jev:evaluate` без двух остальных.
2. **Подключите машину** с помощью этого ключа. Прочитайте его одноразовый секрет в приглашении, затем запустите полную команду настройки:

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` устанавливает демон, присоединяет хуки для найденных CLIs агентов и подключает машину. Переменная окружения держит ключ вне аргументов команды и истории оболочки. Если ваша система была установлена позже, [присоедините её явно](/ru/start/quickstart).

   Если ваша организация запускает собственное FailproofAI Cloud вместо размещённого, добавьте его адрес: `--url https://<your dashboard host>` (или экспортируйте `FAILPROOFAI_CLOUD_URL`). Без этого ключ проверяется против размещённого сервиса и соединение не удаётся. Если сертификат этого хоста выдан приватным CA, установите CA в хранилище системного доверия машины (например с помощью `update-ca-certificates`), не только в `NODE_EXTRA_CA_CERTS`: демон, который отправляет события и получает политики, читает системное хранилище. Смотрите [Решение проблем](/ru/reference/troubleshooting).

Это всё. Подключение сохраняет ключ и, когда на машине **нет** конфигурации Jev, записывает конфигурацию для FailproofAI Cloud. С первого развёртывания машины (в течение примерно 30 с) FailproofAI Cloud устанавливает режим: `enforce` пока политика Jev развёрнута на ней, `off` когда нет (смотрите [Кто устанавливает режим](#кто-устанавливает-режим)). Вывод это говорит:

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

Проверки, которые запускает FailproofAI Cloud, выполняются в облаке. Чтобы добавить собственные проверки на машину, установите пакет:

```bash
failproofai policies add FailproofAI/jev-policies
```

**С `--no-transcripts` подключение не включает Jev.** Jev отправляет каждый проверенный вызов инструмента и последний запрос в FailproofAI Cloud, что больше, чем соединение только с решениями просило отправить. Ключ всё ещё хранится, и вывод говорит, что Jev доступен и как его включить:

```bash
failproofai jev setup --provider failproofai
```

Также отключает Jev через FailproofAI Cloud. `jev.json`, который запускает Jev через FailproofAI Cloud (оставленный предыдущим подключением с включёнными расшифровками), удаляется по тому же правилу, которое использует `config --disconnect`, и вывод говорит, что Jev через FailproofAI Cloud остаётся отключённым на этой машине. `jev.json` для вашей собственной конечной точки Jev остаётся как есть, и так же поступает с облачным FailproofAI, который вы отключили (`--mode off`).

<Warning>
Подключение **никогда не переписывает** существующий `~/.failproofai/jev.json`. Если вы уже используете свою собственную конечную точку Jev, она продолжит использоваться, и вывод говорит, что файл был оставлен как настроено — и когда этот файл оставляет Jev отключённым (отказано или отключено), говорит об этом и как это исправить. Чтобы переключить эту машину на FailproofAI Cloud, запустите `failproofai jev setup --provider failproofai`.
</Warning>

## Кто устанавливает режим

На машине, подключённой к FailproofAI Cloud, **FailproofAI Cloud устанавливает режим Jev**; ничто на машине этого не делает:

- `enforce` пока какая-либо политика Jev (или регулярного выражения + Jev) развёрнута на машину: каждый проверенный вызов инструмента от агента, которого одна из этих политик охватывает, отправляется в FailproofAI Cloud, который запрашивает его проверки вместе с проверками установленных там пакетов. Вызов от агента, на которого никакая облачная политика Jev не распространяется, без собственной проверки пакета, вообще не отправляется. В режиме `enforce` собственные проверки отказа Jev блокируют вызовы так же, как и очищают вердикты регулярного выражения, которые они пересматривают.
- `off` когда нет ни одной: Jev вообще нет, что бы ни говорил `jev.json`.

Чтобы попробовать политику Jev перед тем, как она начнёт действовать, развёрнутите её с эффектом **observe**: её проверки всё ещё запрашиваются, и то, что бы они делали, записывается как **would-have** на странице политики, но она никогда не блокирует вызов и никогда его не очищает. `failproofai jev setup --mode` и переключатель **Settings → Jev** на панели управления говорят, что режим управляется FailproofAI Cloud и не изменяют ничего. `jev.json` не используется для облачных проверок, даже если он указывает другой поставщик. `failproofai config --disconnect` возвращает Jev собственному `jev.json` машины.

`failproofai jev status` затем говорит `Jev checks run on FailproofAI Cloud (mode: enforce)`. Также он называет проверки, которые пересматривают каждую политику `both`. Страница флота показывает, почему машина с режимом не может запрашивать:

- `transcripts_disabled`: машина была подключена с `--no-transcripts`, что никогда не включает Jev.
- `jev_unconfigured`: ключ машины не несёт `jev:evaluate`.
- `jev_rate_limited`: FailproofAI Cloud отказал некоторым вызовам машины из-за лимита скорости Jev организации, и эти вызовы были решены только политиками регулярного выражения.
- `jev_unavailable`: несколько вызовов подряд не удалось, поэтому машина пропускает Jev FailproofAI Cloud в течение минуты за раз. Она повторяет попытки сама.

Если FailproofAI Cloud не отвечает в течение 5 секунд, политики регулярного выражения решают самостоятельно, как при любом отказе Jev. После 3 сбоев подряд машина перестаёт спрашивать на минуту за раз, поэтому отказ облака не замедляет каждый вызов инструмента.

Пауза сеанса (`failproofai config --pause`) не останавливает проверки Jev FailproofAI Cloud, так же как и не останавливает управляемые облаком политики. Она приостанавливает проверки Jev пакетов, установленных на машину.

## Проверьте, что это делает

```bash
failproofai jev status
failproofai jev test
```

`status` показывает поставщика как **FailproofAI Cloud**, облачный хост, к которому подключена машина, режим, и источник ключа как **FailproofAI Cloud connection**, никогда не сам ключ. Когда `jev.json` FailproofAI Cloud на месте, но Jev не может работать, он говорит почему:

| `status` говорит | `status --json` | Значение |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | Машина подключена, но для неё не сохранён ключ Jev: ключ не имеет `jev:evaluate`, или подключение не смогло его подтвердить. Запустите `failproofai config` снова с ключом в `FAILPROOFAI_CLOUD_TOKEN`; если ему не хватает разрешения, используйте ключ **machine**. |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | На этой машине нет соединения FailproofAI Cloud, к которому бы принадлежал ключ Jev. |

После `failproofai config --disconnect` больше нет `jev.json` FailproofAI Cloud (если он не был отключён, что сохраняется), поэтому `status` просто сообщает о Jev как отключённом. `status --json` несёт те же факты (`provider: "failproofai"`, `keySource: "cloud"`, `cloudConnected`, `keyCarriesJev`), также когда конфигурация отсутствует или отказана. `permissions` всегда из `jev.json`; отказ о `credentials.json` добавляет `credentialsPermissions`, и `fix` когда одна команда это исправляет. `test` отправляет один реальный запрос и сообщает его задержку и версию Jev, которая ответила. Он завершается с 1 и говорит об этом в заголовке, когда ответ приходит после истечения тайм-аута хука (хуки бы записали `timeout`) или неправильно отвечает на его вопрос проверки.

Панель **Settings → Jev** на панели управления также показывает **FailproofAI Cloud connection**: в какую организацию сообщает машина и есть ли у её ключа Jev. Это читается из собственных файлов машины, без сетевого вызова.

## Проверьте реальный вызов

Начните новый сеанс в подключённом агенте. Попросите его использовать инструмент чтения файлов на `README.md` и сообщить заголовок. Подтвердите, что сеанс содержит этот вызов инструмента, затем запустите `failproofai jev status` снова: счётчик недавно оценённых вызовов должен увеличиться. Откройте **Policies → Activity** в [локальной панели управления](/ru/reference/local-dashboard#review-policy-activity) для проверки вердикта Jev этого вызова и режима. В облаке страница **Policies** организации показывает результаты Jev для доставленных действий. В режиме observe вердикт записывается как **would-have** и результат политики всё ещё решает вызов. Очистка появляется только когда рецензируемая политика совпала и Jev очистил её названные проверки.

## Что попадает на страницу политики

Машина уже отправляет действия своих хуков в FailproofAI Cloud (`events:add`). С включённым Jev запись каждого вызова в вратах также говорит, какой оценщик работал, что решил Jev, какие политики он очистил, почему откатился когда он это сделал, его задержку и модель, которая ответила — решения, коды и имена, никогда команда или ваш запрос. На странице **Policies** вашей организации:

- вызов, который решил собственный вердикт Jev (режим enforce), приписывается **Jev**, и когда решающая проверка пришла из пакета, запись также называет этот пакет и его версию;
- в режиме observe отказ или предупреждение Jev появляется как **would-have**, рядом с развёртываниями, которые вы наблюдаете;
- политики, которые Jev очистил или стал бы очищать в режиме observe, считаются по политике.
- решение, в котором участвовал Jev (блокировка, предупреждение, очистка или would-have в режиме observe), перечисляет каждую проверку, которую он запросил, и что эта проверка заключила: вердикт, почему (`not-detected`, `exempt`, `fired`, `op-requested`, …), его свидетельство `p`, ответ `exempt` и каждый ответ зонда. Проверка политики, развёрнутой для наблюдения (observe), также указана, помечена как наблюдаемая; она никогда не блокирует. Jev отвечает вероятностями, не прозой, поэтому нет свободного текста причины. Обычные разрешения сворачиваются в подсчёты и не несут этот список.

## Когда Jev не может ответить

Каждый из них откатывается к результату вашей политики для этого вызова и записывается с его причиной:

| Причина | Причина |
| --- | --- |
| `out-of-credits` | Ваша организация исчерпала лимит плана. |
| `http-401`, `http-403` | Ключ был отозван или не имеет `jev:evaluate`. Переподключитесь с ключом, который это имеет. |
| `http-429` | FailproofAI Cloud ограничивает скорость Jev для вашей организации. До окончания ожидания, которое оно требует (его `Retry-After`, максимум 60 секунд), машина ничего ему не отправляет и каждый вызов сразу откатывается. Вызовы, задержанные таким образом, записываются как `http-429` или как `rate-limited` когда первым это останавливает собственный лимит скорости машины. |
| `http-429` (дневной лимит) | Ваша организация исчерпала свои дневные вызовы Jev: **10 000 в день по UTC**, если кто-то, кто управляет вашим FailproofAI Cloud, не установил другой лимит. Каждый вызов откатывается до сброса счётчика в 00:00 UTC; машина всё ещё спрашивает максимум один раз в минуту, поэтому она подхватывает сброс в течение минуты. `failproofai jev test` говорит "Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev отказал этому запросу вызова, обычно потому что вызов инструмента содержал плотный текст (base64, hex, минифицированный код) сверх бюджета токенов Jev. Этот вызов откатывается каждый раз; это не отказ. |
| `http-502` | Jev недоступен прямо сейчас. |
| `http-503` | Это облако не может обслуживать Jev для вашей организации: нет модельного шлюза, организация ещё не подготовлена или шлюз не работает. Спросите вашего администратора; хуки спрашивают максимум один раз в минуту. |
| `http-404` | Это FailproofAI Cloud ещё не обслуживает Jev. |
| `timeout` | Нет ответа в течение `timeoutMs` (по умолчанию 3000). Пока FailproofAI Cloud устанавливает режим Jev машины, ожидание составляет 5000 мс и `timeoutMs` из `jev.json` не используется. |
| `model-mismatch` | Ответила версия Jev, отличная от 1.13. |

## Где живёт ключ и куда он идёт

- Ключ хранится один раз в `~/.failproofai/credentials.json` (`0600`, в директории только владельца), рядом с другими учётными данными FailproofAI Cloud. `jev.json` не содержит ключа для этого маршрута; ключ, написанный там, делает конфигурацию недействительной.
- Если `credentials.json` несёт **какое-либо** разрешение для кого-нибудь кроме вас (группа или другое, чтение или запись), или его директория может быть **написана** кем-нибудь кроме вас, он **отказан**, не прочитан, и Jev отключен до тех пор, пока вы это не исправите: `chmod 600` на файл, `chmod 700` на директорию (или переподключитесь, что перепишет файл в `0600` и сделает директорию только владельца). Директория, которую другие могут только читать, в порядке; если они могут писать, они могут поменять файл.
- Ключ считается только пока соединение, из которого он пришёл, на машине: политика или учётные данные отчёта для того же FailproofAI Cloud **с тем же ключом**, в том же файле. Ключ Jev, оставленный без одного, игнорируется, и Jev остаётся отключённым. Это происходит когда старый failproofai's `config --disconnect` оставляет ключ Jev на месте (он не знает его удалить), или когда старый failproofai's `config --token` подключается с другим ключом, который на FailproofAI Cloud может принадлежать другой организации. Чтобы снова включить Jev, подключитесь с ключом **machine**.
- Ключ отправляется только облачному источнику, против которого он был проверен. `jev.json`, указывающий куда-то ещё, отказан.
- **Агент на машине может его читать.** `credentials.json` только владельца, и агент работает как этот владелец. Чтение собственных файлов failproofai позволено специально (только изменение их заблокировано `block-failproofai-commands`), поэтому единственное, что между агентом и этим файлом, это `block-read-outside-cwd` — *рецензируемая* политика — и из сеанса, начатого в вашем домашнем каталоге, ничего. Ключ с `jev:evaluate` тратит лимит Jev вашей организации (до дневного лимита) откуда бы он ни использовался, поэтому относитесь к машинному ключу как к любому другому учётному данному о трате: если агент мог его прочитать, отключите его на странице Keys и переподключитесь с новым.
- Только ваши глобальные файлы решают это. Репозиторий не может включить облако Jev, указать его куда-то ещё или предоставить его ключ, и `FAILPROOFAI_JEV_API_KEY` игнорируется для этого маршрута.
- Для каждого вызова, который оценивает Jev, один запрос идёт в FailproofAI Cloud, содержащий то, что список [bring-your-own-key страницы](/ru/reference/jev-providers#what-leaves-the-machine) перечисляет (секреты отредактированы). FailproofAI Cloud перенаправляет это в TypeSafe и не логирует и не хранит это.

## Выключите это

На подключённой машине Jev отключен когда FailproofAI Cloud не развёртывает ей никакую политику Jev: удалите или архивируйте политики Jev там.

| Команда | Результат |
| --- | --- |
| Удалить политики Jev машины в FailproofAI Cloud | Режим Cloud становится `off` при следующем опросе (примерно 30 с): Jev вообще нет, что бы ни говорил `jev.json`. |
| `failproofai config --disconnect` | Отключить машину: ключ удаляется, и так же удаляется `jev.json` когда он назывался FailproofAI Cloud и не отключен. `jev.json` для вашей собственной конечной точки остаётся. |

При следующем вызове инструмента хуки запускают политики регулярного выражения точно как прежде.
