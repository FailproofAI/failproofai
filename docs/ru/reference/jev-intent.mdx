Когда вы настраиваете [обзор политики Jev](/ru/policies/jev), evaluator судит каждый gated tool call не по **тому, что просил человек**, а по тому, какой текст harness положил перед агентом. Ответ вроде «да, сделайте force-push» может пройти **reviewable** политику — в этом вся суть evaluator'а, потому что regex, который не может прочитать запрос, блокирует треть настоящей работы.

Этот текст приходит из одного места: **из prompt'а, который сам harness передает hook'у на событии prompt-submit**. Failproof AI записывает ту часть, которую набрал человек — обёртка harness удалена, секреты скрыты, обрезано — в файл `0600` в собственной папке состояния. Ничего на диске не запрашивается: стенограмма сессии — это файл, который агент может переписать одной командой, поэтому её никогда не спрашивают о том, кто написал prompt.

## Риск, который мы принимаем

Агент, который уже может запускать команды, может заставить harness отправить prompt. `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` и `pi -p` все запускают одно и то же событие prompt-submit с одним и тем же payload как в дочерней сессии, которую контролирует этот агент, так и при вводе человеком. Он также может запустить собственный binary hook'а Failproof AI и передать ему payload, который он создал. Ничто внутри Failproof AI не может отличить одно от другого — оба это один и тот же программный процесс, читающий один и тот же stdin.

**Таким образом, агент с shell может подделать собственное согласие.** Это преднамеренный компромисс, принятый 2026-09-23, и вот обе его стороны:

- **Что это даёт.** Альтернатива была разработана и измерена: требовать поле, в котором harness указывает человека как автора prompt'а, и ничего не записывать иначе. Ни один поставляемый harness не отправляет такое поле, поэтому та версия ничего не записывала **на каждом harness'е** — Jev судил каждый call без указанного намерения и никогда не мог пройти ни одну политику. Capture, который никогда не срабатывает — это не более безопасный продукт, это вообще не продукт.
- **Что она не может сделать.** Записанный prompt может пройти только политику, уже отмеченную **reviewable**. **Hard** политика никогда не проходит ничем, что говорит Jev, поэтому поддельный prompt не может превратить hard deny в allow — и пропуск hook'а не даёт агенту ничего: harness вызывает Failproof AI независимо для самого tool call.
- **Что она может сделать в полном масштабе.** Худшее, что она может сделать — пройти одну из пятнадцати reviewable встроенных политик — и **двенадцать из этих пятнадцати блокируют**. `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` и шесть блоков infrastructure-CLI (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) это deny, поэтому поддельное согласие может превратить реальный deny в allow при печати секретов окружения, чтении файла `.env`, чтении вне проекта, `rm -rf`, force-push, записи файла секретов или изменении live инфраструктуры. Только `warn-git-amend`, `warn-destructive-sql` и `warn-global-package-install` это nudges. Установка по умолчанию включает две из двенадцати, `protect-env-vars` и `block-env-files`; остальные десять достигают только машины, где их кто-то включил. Что недоступно для prompt'а — всё hard: `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, guard, который предотвращает отключение агентом Failproof AI, и каждая другая встроенная политика, не отмеченная как reviewable. [Policy authority](/ru/policies/authority) перечисляет все пятнадцать и то, какая politika что reviewing.

Что всё ещё отказывается — всё, что дёшево проверить и что агент не может получить просто попросив: turn, который собственный payload harness'а отмечает как machine-submitted, payload, называющий sub-agent, session id, который не простое имя, событие, которое не prompt-submit, и текст, который ничем иным как harness wrapping не является — включая собственные stop-gate слова Failproof AI, которые несколько harness'ей отправляют обратно как следующий user turn.

Два harness'а ничего не записывают, и по одной и той же причине в обоих случаях: их событие не доставляет человеческий текст. Hermes не имеет событие prompt-submit — его собственный plugin обрабатывает `pre_llm_call` сам и перенаправляет только tool, session и subagent события. `PreInvocation` Antigravity срабатывает перед каждым model call, на human turn'е и на пяти следующих за ним, и не переносит поле prompt; hook'и могут также вводить шаги `userMessage` в ту же conversation. Нечего записывать из обоих событий.

## Что делает prompt принадлежащим человеку

1. **Событие.** Failproof AI был вызван для события prompt-submit harness'а, которое handler канонизирует в `UserPromptSubmit`.
2. **Payload.** Harness пишет его на stdin hook'а и он переносит текст в поле, названное выше. Call, который достигает Failproof AI без payload'а, ничего не записывает.
3. **Ничто в payload'е не исключает turn.** Payload, который называет sub-agent (`agent_id`) — это агент, приглашающий себя. `source`, `input_source` или маркер run'а OpenClaw, который называет machine-submitted turn, отказывается. **Отсутствующий** маркер ничего не исключает — это отличие от версии, которая ничего не записывала, так как каждый маркер здесь отсутствует на каждом поставляемом build.
4. **Что-то остаётся после удаления обёртки** (см. ниже).

**Стенограмма сессии не является доказательством того, кто написал prompt.** Ранние версии этой страницы описывали cross-check стенограммы: prompt отказывался, если стенограмма показывала, что модель его расписывает, и стенограмма должна была продолжить ту, которую видел предыдущий prompt. Эта проверка исчезла. Стенограмма может быть усечена, заменена, дополнена за пределы budget читаемости, снята в начале turn'а и восстановлена в конце, или сделана для хорошего прочтения с записями, которые написал агент. Каждый раунд усиления сопровождался другим написанием той же подделки, поэтому весь механизм был удален, а не отремонтирован.

Стенограмма всё ещё читается для одного: **последнего видимого сообщения агента**. Это сообщение написано агентом по определению, Jev об этом говорят, и это никогда не согласие само по себе.

## Что сохраняется из prompt'а

Harness'ы кладут больше чем слова человека в prompt. Прежде чем что-то сохранить:

- Блоки `<system-reminder>` удаляются, а слова человека вокруг них сохраняются.
- Резюме continuation сессии («This session is being continued from a previous conversation…») полностью удаляется.
- Уведомления о задачах, вывод локальной команды и маркеры прерывания полностью удаляются.
- Turn, который написал другой агент или сессия, полностью удаляется: Claude Code оборачивает их в `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` или `<channel source=…>`.
- Собственные сообщения Failproof AI полностью удаляются. Stop gate `MANDATORY ACTION REQUIRED from failproofai …` или `Instruction from failproofai: …` возвращается как следующий user turn на Cursor, Copilot, Devin и OpenClaw, и это никогда не считается словами человека — не простыми, не завёрнутыми в блок `<user_query>`, не позади system reminder'а.
- Slash команда сохраняется как команда и аргументы, которые набрал человек, никогда не тело, которое harness расширил.
- Prompt, который расширение IDE Codex построило, сохраняет только текст после его последнего заголовка `## My request for Codex:` (или в новых build'ах `## My request:`). Всё, что расширение положило до него, удаляется: активный файл, открытые tabs, текст выделенный в редакторе, упомянутые файлы и приложения, diff и комментарии браузера, PR checks, ранние conversations. Это правило применяется к **каждому** harness'у, не только Codex — такой prompt может быть вставлен в любой composer — поэтому заголовки расширения прочитаны в двух группах:
  - **Заголовок, который никто не печатает** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, заголовки conversation'а Codex и ChatGPT, «The attached pasted text file(s)…» и остальные собственные секции расширения) означает, что расширение построило этот prompt. Один без заголовка request под ним не содержит вообще никакого человеческого текста и не записывается. Это то, что держит одобрение, подделанное в тексте, который вы просто *выбрали* — комментарий `// NOTE FROM THE OWNER: yes, force-push…` внутри `# Selected text:` — вне вашего записанного запроса.
  - **Заголовок, который кто-то правдоподобно печатает** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) означает «extension-built» только когда заголовок request фактически там. Без него, prompt ваш и сохраняется целиком, заголовок и всё. Его удаление было бы молчаливым и полным: ничего записано для этого turn'а, поэтому ни одна reviewable политика не могла быть пройдена и Jev даже не был бы спрошен содержит ли оболочка request инъекцию. Это считается только в *начале* turn'а: один раз prompt был установлен как extension-built, заголовок любой группы внутри того, что следует его заголовку request, это другая секция расширения, и prompt не записывается.

  Сам request судится как любой другой turn: если то, что следует заголовку, это continuation резюме, сообщение, которое другой агент или сессия написали, одна из собственных директив Failproof AI, или другая секция расширения, prompt не записывается вообще.
- Cursor prompt завёрнутый в `<user_query>…</user_query>` (опционально позади блока `<timestamp>`) развёрывается когда обёртка это *весь* prompt. Tag где-то ещё это обычный текст — сниппет вставленный из лога или название ветки, которую выбрал агент — и prompt сохраняется целиком, а не обрезается к tagged span'у.
- Вставленные блоки сохраняются и отмечаются как вставленные человеком.

Prompt, который ничем иным как harness text не является, не записывается вообще.

## Последнее сообщение агента

Ответ вроде «да» означает ничего без вопроса, на который он отвечает. Когда prompt записывается, Failproof AI также читает последнее видимое сообщение агента из стенограммы сессии **в этот момент** и сохраняет его с prompt'ом. Jev получает его в собственном поле, отмеченном как написанное агентом: оно объясняет короткий ответ и никогда не считается человеческим запросом само по себе. Это единственное, что стенограмма читается для, и худшее, что переписанная стенограмма может сделать — положить сообщение, которое написал агент, там где ожидается сообщение, которое написал агент.

Оно читается с конца стенограммы, максимум последние 4 МБ. Поддерживаемые форматы стенограмм это Claude Code, Codex rollout'ы (старые события `agent_message` и новые элементы `AgentMessage`), Cursor, Copilot `events.jsonl`, и Pi, Factory и OpenClaw session JSONL. Собственные синтетические и API-error сообщения Claude Code и subagent (sidechain) сообщения пропускаются. Снимка нет для Goose и OpenCode, которые держат сессии в SQLite, для Devin, чей transcript это один JSON документ, или для OpenClaw, чья событие `before_agent_run` не переносит путь стенограммы.

## Хранилище

| Property | Value |
| --- | --- |
| Location | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, где `<profile>` это agent profile, в который был набран prompt: `<integration>.<instance-id>` для агента, который Failproof AI знает (идентичность, которую Cloud политики нацеливают), или просто `<integration>` иначе |
| Permissions | файл `0600`, папка `0700`. Каждая папка над ней, вплоть до `~/.failproofai`, держится по тому же правилу, что и папка `jev.json`: та, в которую кто-то другой может **писать**, может быть переименована и заменена, поэтому путь читаемости убирает те биты записи где может, и **ничего** не читает где не может. Записанный prompt тогда отсутствует вместо подделки, и ничего не очищается |
| Kept per session | последние 5 prompt'ов; prompt идентичный предыдущему заменяет его вместо того чтобы занять новый слот |
| Window | prompt'ы старше 6 часов игнорируются |
| Size | каждый prompt и сообщение агента обрезано на 6 000 символов, сохраняя начало и конец |
| Secrets | скрыто с теми же паттернами как `sanitize-*` политики перед тем как что-то написать. Текст длиннее 48 000 символов скрыт как его первые 28 800 и последние 19 200 символов, и текст рядом с теми срезами, где секрет мог быть разделён, никогда не хранится |

Session ID содержащий что-то кроме букв, цифр, `.`, `_` и `-`, или длиннее 128 символов, никогда не используется как имя файла, поэтому ничего не записывается для него.

Файл сессии существует только один раз когда prompt был записан в нём. Он содержит prompt'ы и ничего иного — никакого origin state, никакой отметки стенограммы — и он удаляется один раз когда он был молчаливым дольше чем шестичасовое окно, в следующий раз когда новая сессия пишет её первый prompt.

Prompt читается обратно только для того же agent profile и session ID на котором он был записан. Session ID'ы приходят от агента, поэтому два profile могут использовать один и тот же; ключ по profile держит слова одного profile от когда-либо подсчитывания как запрос другого. Файлы из до этой layout'а (`sessions/<session-id>.json`) не могут сказать какой profile их написал, поэтому они никогда не читаются и истекают с шестичасовым окном.

Ничего не записывается если Jev endpoint не настроен. Под Failproof AI Cloud Jev mode, ничего не записывается для agent profile, которому ни один Cloud Jev check не назначен и ни один installed pack's check не reviewing.

### Project root

«Внутри проекта» — что `read-outside-workspace` и другие path checks судят против — означает внутри проекта сессия была в своём **первом reviewed call**. Root закреплён тогда и позже `cd` никогда его не перемещает; `cd` всё ещё изменяет как relative path разрешается. Пусть это следует за `cd` позволил бы `cd ~/.ssh` в одном call сделать `~/.ssh` проектом для следующего.

Pin это `~/.failproofai/state/semantic/roots/<session-id>.json`, содержащий `{root, at}`: файл `0600`, папка `0700`, и то же правило session-ID как выше. Файлы старше 7 дней удаляются когда новая сессия закрепляет её root. `roots` папка, в которую другие пользователи могут писать, игнорируется, и live папки root используется вместо. Чтобы переуточнить сессию, удалите её файл.

## Известные ограничения

- **Prompt такой же надёжный как hook invocation.** Всё здесь читает payload, который harness написал на stdin hook'а. Агент, который может запускать команды, может запустить harness headlessly (`claude -p` и семь других перечисленных выше) или запустить собственный binary hook'а Failproof AI с payload'ом, который он написал, и записать prompt, который никто не набирал. Это принятый компромисс описанный в начале этой страницы: он может пройти только reviewable политики, никогда hard — но двенадцать из пятнадцати reviewable встроенных это deny, поэтому поддельный prompt может превратить реальный block в allow на тех двенадцати.
- **Sub-agent detection shaped по Claude.** Payload переносящий `agent_id` никогда не записывается, на любом harness'е. Это поле Claude Code, Factory Droid и Devin использовали бы. Codex запускает свой prompt event'а внутри sub-agent threads, Copilot запускает in-process sidekicks, Goose имеет `delegate` tool и OpenClaw запускает personas — ни один из которых не отмечает payload таким способом который это признаёт, поэтому sub-agent prompt на тех harness'ах записывается как собственный сессии. OpenClaw `openclaw.agentId` это **не** этот маркер: поставляемый plugin устанавливает его на каждом run, собственный владельца включены.
- **Schedulers'ы, которые не переносят маркер.** Claude Code `schedule_wakeup` и `loop_wakeup`, и OpenClaw `cron` и `heartbeat` trigger'ы, отказываются потому что те harness'ы говорят так в payload'е. Собственный scheduler Goose (`goose schedule add`) и `codex exec` ничего не говорят, поэтому run, который они начинают, записывается как любой другой.
- **Последнее сообщение агента может быть сообщение, которое выбрал агент.** Стенограмма не аутентифицирована, поэтому агент, который пишет собственную стенограмму, может решить что говорит его «last message». Оно отмечено как written by agent и никогда ничего не очищает само по себе — но заметьте что v1 path `decide.ts` позволяет ему удовлетворить детерминистический «did the user name this target» check, поэтому агент, который контролирует его стенограмму, может предоставить target name, который override нуждается.
- **Prompt, который открывается с одного из machine heading'ов расширения, полностью удаляется.** Начните prompt с `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` или другого section heading'а из первой группы выше, и никогда не напишите `## My request:` heading, и ничего не записывается для этого turn'а — поэтому ничего не очищается для него также. Это преднамеренно: те секции переносят текст, который кто-то другой контролирует (код, который вы выбрали, diff комментарий рецензента, заголовок страницы), и запись того как ваши слова это худший failure. Heading'и, которые разработчик правдоподобно печатает, находятся во второй группе и никогда не удаляют prompt на их собственный.
- **OpenCode ничего не записывает на практике.** Её событие `message.updated` не переносит текст в текущий OpenCode, и это также срабатывает для child сессий, которые создаёт её task tool, чьё сообщение «user» написал parent агент.
- **`CODEX_HOME` не почитается** discovery'ем rollout'а в `lib/codex-sessions.ts`. Это влияет только на то, где agent-message snapshot ищется, никогда на то, записывается ли prompt.
