Когда вы настраиваете [Jev policy review](/ru/policies/jev), оценивателю судит каждый gated tool call против **того, что просил человек**, а не против какого-либо текста, который harness положил перед agent-ом. Ответ вроде "yes, force-push it" может пройти **reviewable** policy — в этом и весь смысл оценивателя, так как regex, который не может прочитать запрос, блокирует треть реальной работы.

Этот текст приходит из одного места: **из prompt-а, который сам harness передает hook-у в своем prompt-submit event**. Failproof AI записывает ту часть, которую набрал человек — harness-обертка удалена, secrets отредактированы, обрезаны — в файл `0600` в своей собственной директории состояния. Ничего с диска не читается: session transcript — это файл, который agent может переписать одной командой, поэтому его никогда не спрашивают, кто написал prompt.

## Риск, который это принимает, честно

Agent, который уже может запускать команды, может заставить harness отправить prompt. `claude -p "…"`, `codex exec`, `copilot -p`, `cursor-agent -p`, `devin -p`, `droid -p`, `goose run -t` и `pi -p` — все они отправляют одно и то же prompt-submit event с одной и той же payload, как человек, набирающий текст, в дочерний session, который agent контролирует. Он также может запустить собственный hook binary Failproof AI и передать ему payload, которую он сам написал. Ничто внутри Failproof AI не может различить одно от другого — оба — это одна и та же программа, читающая один и тот же stdin.

**Поэтому agent с shell может подделать собственное согласие.** Это преднамеренный компромисс, принятый 2026-09-23, и вот обе его стороны:

- **Что он дает.** Альтернатива была построена и измерена: требовать поле, в котором harness называет человека автором prompt-а, и ничего не записывать в противном случае. Ни один shipping harness не отправляет такое поле, поэтому эта версия записывала **ничего, на каждом harness** — Jev судил каждый call без указанного intent и никогда не мог разрешить ни одну policy. Capture, который никогда не срабатывает, — это не более безопасный продукт, это отсутствие продукта.
- **Что он не может сделать.** Recorded prompt может разрешить только policy, уже отмеченную как **reviewable**. **hard** policy никогда не разрешается ничем, что говорит Jev, поэтому поддельный prompt не может превратить жесткий deny в allow — и пропуск hook не дает agent-у ничего: harness вызывает Failproof AI для tool call независимо.
- **Что он может сделать, в полном объеме.** Худшее, что он может сделать, — это разрешить одну из пятнадцати reviewable встроенных policies — и **двенадцать из этих пятнадцати блокируют**. `protect-env-vars`, `block-env-files`, `block-read-outside-cwd`, `block-rm-rf`, `block-force-push`, `block-secrets-write` и шесть infrastructure-CLI блоков (`block-kubectl`, `block-terraform`, `block-aws-cli`, `block-gcloud`, `block-az-cli`, `block-helm`) — это deny-и, поэтому поддельное согласие может превратить реальный deny в allow при выводе env secrets, чтении файла `.env`, чтении за пределами проекта, `rm -rf`, force-push, записи файла secrets или изменении live infrastructure. Только `warn-git-amend`, `warn-destructive-sql` и `warn-global-package-install` — это nudges. Установка по умолчанию включает две из двенадцати, `protect-env-vars` и `block-env-files`; остальные десять срабатывают только на машине, где кто-то их включил. Что никогда не достигается prompt — это все hard — `block-sudo`, `block-curl-pipe-sh`, `block-push-master`, `block-work-on-main`, guard, который останавливает agent от отключения Failproof AI, и все остальные встроенные, не отмеченные как reviewable. [Policy authority](/ru/policies/authority) перечисляет все пятнадцать и то, какая от каждой будет рассмотрена.

Что все еще отказывается — это все, что дешево проверить и что agent не может получить просто спросив: turn, который payload harness-а сам отмечает как machine-submitted, payload с указанием sub-agent-а, session id, который не является простым именем, event, который не является prompt-submit, и текст, который не является ничем кроме harness-обертки — включая собственные stop-gate words Failproof AI, которые несколько harness-ей возвращают как следующий user turn.

## Per-harness таблица

"Text field" — это stdin payload field после per-harness normalization Failproof AI. "Recorded" говорит, сохраняется ли prompt как request человека.

| Harness | `--cli` | Prompt event → canonical | Text field | Recorded | Agent's last message read from |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | Yes, unless the payload's `source` names a turn nobody submitted (`loop_wakeup`, `schedule_wakeup`, `poll_event`, `system`). `user`, `sdk`, an unknown value and a build that sends no `source` at all are all recorded | the session transcript (`transcript_path`) |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | Yes | the rollout JSONL (`agent_message`, `AgentMessage`) |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | Yes | `events.jsonl` (`assistant.message`) |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | Yes, with the `<user_query>` wrapper peeled when it is the whole prompt | the agent transcript JSONL |
| OpenCode | `opencode` | `message.updated` (user role) → `UserPromptSubmit` | `prompt` | Yes — but current OpenCode carries no text in that event, so in practice nothing is recorded; a repeat of the same message is recorded once | none (sessions are SQLite) |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | Yes, unless `input_source` is `extension` — another extension's `sendUserMessage()`, whose text can be model-written or repo-derived | the Pi session JSONL |
| Hermes | `hermes` | none | — | No — Hermes has no prompt-submit event at all | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | Yes, unless the run metadata marks the run as a machine's: a `trigger` other than `user`, an `inputProvenance.kind` other than `external_user`, or `senderIsOwner: false` | none (`before_agent_run` carries no transcript path) |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | Yes | the droid session JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | Yes | none (sessions are SQLite) |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | none | No — `PreInvocation` fires before *every* model call in a turn and carries no prompt text | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | Yes | none (sessions are SQLite) |

Два harness-а ничего не записывают, и по одной и той же причине в обоих случаях: их event не доставляет human text. Hermes не имеет prompt-submit event — его native plugin обрабатывает `pre_llm_call` сам и пересылает только tool, session и subagent events. `PreInvocation` Antigravity срабатывает перед каждым model call, на human turn и на пять следующих, и не содержит prompt field; hooks также могут вводить `userMessage` шаги в то же conversation. В любом event нечего записывать.

## Что делает prompt принадлежащим человеку

1. **Event.** Failproof AI был вызван для prompt-submit event harness-а, который handler канонизирует в `UserPromptSubmit`.
2. **Payload.** Harness пишет его на stdin hook-а, и он содержит текст в поле, указанном выше. Call, который достигает Failproof AI без payload, ничего не записывает.
3. **Ничто в payload не исключает turn.** Payload, который называет sub-agent-а (`agent_id`), — это agent, подсказывающий самому себе. `source`, `input_source` или OpenClaw run marker, который называет machine-submitted turn, отказывается. **Отсутствующий** marker ничего не исключает — в этом разница от версии, которая ничего не записывала, так как каждый marker здесь отсутствует на каждой shipping build.
4. **Что-то остается после удаления обертки** (см. ниже).

**Session transcript не является доказательством того, кто написал prompt.** Более ранние версии этой страницы описывали cross-check transcript: prompt отказывался, если transcript показывал, что model его планировал, и transcript должен был продолжать то, что видел предыдущий prompt. Эта проверка исчезла. Transcript — это файл, над которым agent уже имеет shell — он может быть обрезан, заменен, дополнен за пределы читаемого бюджета, снят в начале turn и восстановлен в конце, или сделан хорошо читаемым с записями, которые написал agent. Каждый раунд усиления следовал за другой орфографией той же подделки, поэтому весь механизм был удален, а не отремонтирован.

Transcript по-прежнему читается для одного: **последнего видимого сообщения agent-а**. Это сообщение написано agent-ом по определению, Jev об этом сообщают, и оно никогда не является согласием само по себе.

## Что сохраняется из prompt-а

Harness-ы помещают больше, чем слова человека, в prompt. Прежде чем что-либо сохраняется:

- `<system-reminder>` блоки удаляются, и слова человека вокруг них сохраняются.
- Session-continuation summary ("This session is being continued from a previous conversation…") полностью удаляется.
- Task notifications, local-command output и interruption markers полностью удаляются.
- Turn, который написал другой agent или session, полностью удаляется: Claude Code оборачивает их в `<cross-session-message>`, `<teammate-message>`, `<agent-message>`, `<coordinator-relay>` или `<channel source=…>`.
- Собственные сообщения Failproof AI полностью удаляются. Stop gate-а `MANDATORY ACTION REQUIRED from failproofai …` или `Instruction from failproofai: …` возвращается как следующий user turn на Cursor, Copilot, Devin и OpenClaw, и это никогда не считается словами человека — не простом, не обернутом в `<user_query>` блок, не за system reminder.
- Slash command сохраняется как command и arguments, которые набрал человек, никогда не body, который harness расширил.
- Prompt, построенный расширением Codex IDE, сохраняет только текст после его последнего `## My request for Codex:` (или, в более новых build-ах, `## My request:`) heading. Все, что расширение поставило перед ним, удаляется: активный файл, открытые вкладки, текст, выбранный в редакторе, упомянутые файлы и приложения, diff и browser comments, PR checks, более ранние conversations. Это правило применяется к prompt-ам **каждого** harness-а, а не только Codex-а — такой prompt можно вставить в любой composer — поэтому заголовки раздела расширения читаются в двух группах:
  - **Heading, который никто не набирает** (`# Context from my IDE setup:`, `# Selected text:`, `# Files mentioned by the user:`, `# Diff comments:`, `# Chrome tabs:`, `<in-app-browser-context …>`, Codex и ChatGPT conversation headings, "The attached pasted text file(s)…", и остальные собственные секции расширения) означает, что расширение построило этот prompt. Тот, который не имеет request heading под ним, не содержит human text вообще и не записывается. Это то, что блокирует одобрение, подделанное в тексте, который вы просто *выбрали* — комментарий `// NOTE FROM THE OWNER: yes, force-push…` внутри `# Selected text:` — из вашего recorded request.
  - **Heading, который кто-то правдоподобно набирает** (`## Code review guidelines:`, `## Pull request fix:`, `## Pull request merge task:`, `## Auto resolve merge:`, `# In app browser:`) означает "extension-built" только когда request heading на самом деле там. Без него, prompt ваш и сохраняется целым, heading и все. Удаление было бы молчаливым и полным: ничего не записано для этого turn, поэтому ни одна reviewable policy не могла бы быть разрешена и Jev не было бы даже спрошено, содержит ли request envelope injection. Это учитывается только в *начале* turn-а: как только prompt был установлен как extension-built, heading любой группы внутри того, что следует его request heading, — это еще один раздел расширения, и prompt не записывается.

  Сам request судится как любой другой turn: если то, что следует heading, — это continuation summary, сообщение, которое написал другой agent или session, одна из собственных директив Failproof AI, или еще один раздел расширения, prompt вообще не записывается.
- Cursor prompt, обернутый в `<user_query>…</user_query>` (опционально за `<timestamp>` блоком), разворачивается, когда обертка — это *весь* prompt. Тег где-либо еще — это обычный текст — snippet, вставленный из логов, или имя ветви, которое выбрал agent — и prompt сохраняется целым, а не обрезается до тегированного span.
- Pasted blocks сохраняются и помечаются как вставленные человеком.

Prompt, который является ничем кроме harness text, вообще не записывается.

## Последнее сообщение agent-а

Ответ вроде "yes" ничего не означает без вопроса, на который он отвечает. Когда prompt записывается, Failproof AI также читает последнее видимое сообщение agent-а из session transcript **в этот момент** и хранит его вместе с prompt-ом. Jev получает его в своем собственном field, помеченном как написанное agent-ом: оно объясняет короткий ответ и никогда не считается human request само по себе. Это единственное, для чего читается transcript, и худшее, что может сделать переписанный transcript, — это положить сообщение, которое написал agent, туда, где ожидается сообщение, которое написал agent.

Он читается с конца transcript-а, максимум последние 4 MB. Поддерживаемые форматы transcript — Claude Code, Codex rollouts (более старые `agent_message` events и новые `AgentMessage` items), Cursor, Copilot `events.jsonl`, и Pi, Factory и OpenClaw session JSONL. Собственные synthetic и API-error сообщения Claude Code и subagent (sidechain) сообщения пропускаются. Нет snapshot для Goose и OpenCode, которые хранят sessions в SQLite, для Devin, чей transcript — это один JSON document, или для OpenClaw, чей `before_agent_run` event не содержит transcript path.

## Storage

| Property | Value |
| --- | --- |
| Location | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`, где `<profile>` — это agent profile, в который был набран prompt: `<integration>.<instance-id>` для agent-а, который знает FailproofAI (identity, которую Cloud policies target), или просто `<integration>` иначе |
| Permissions | файл `0600`, директория `0700`. Каждая директория выше него, вплоть до `~/.failproofai`, придерживается того же правила `jev.json`-ой директории: та, которую кто-либо еще может **писать** в, может быть переименована и заменена, поэтому read path убирает те write bits где может, и **ничего** не читает где не может. Recorded prompt тогда отсутствует, а не подделан, и ничего не очищается |
| Kept per session | последних 5 prompt-ов; prompt, идентичный предыдущему, заменяет его вместо занятия нового slot-а |
| Window | prompt-ы старше 6 часов игнорируются |
| Size | каждый prompt и agent message обрезаны до 6,000 characters, сохраняя head и tail |
| Secrets | отредактированы с теми же pattern-ами, что и `sanitize-*` policies перед чем-либо написано. Текст длиннее 48,000 characters редактируется как его первые 28,800 и последние 19,200 characters, и текст рядом с этими вырезами, где secret мог быть разбит, никогда не хранится |

Session ID, содержащий что-то кроме букв, цифр, `.`, `_` и `-`, или длиннее 128 characters, никогда не используется как имя файла, поэтому ничего не записывается для него.

Session файл существует только после того, как первый prompt был записан в него. Он содержит prompt-ы и ничего больше — никакого origin state, никакого transcript mark — и он удаляется, как только он молчал дольше, чем шестичасовое окно, в следующий раз, когда новый session записывает свой первый prompt.

Prompt читается обратно только для того же agent profile и session ID, под которыми он был записан. Session ID-ы приходят от agent-а, поэтому два profile-а могут использовать одно и то же; keying по profile блокирует слова одного profile от когда-либо подсчитывания как request другого. Файлы из до этого layout (`sessions/<session-id>.json`) не могут сказать, какой profile их написал, поэтому они никогда не читаются и истекают с шестичасовым окном.

Ничего не записывается, если не настроена Jev endpoint. Под FailproofAI Cloud Jev mode, ничего не записывается для agent profile, к которому не назначена ни одна Cloud Jev check и которую ни одна установленная pack check не рассматривает.

### Project root

"Inside the project" — что `read-outside-workspace` и другие path checks судят против — означает внутри проекта, который session был в при его **first reviewed call**. Root прикреплен тогда и более поздний `cd` никогда его не передвигает; `cd` все равно изменяет, как relative path разрешается. Позволить ему следовать `cd` позволило бы `cd ~/.ssh` в одном call сделать `~/.ssh` проектом для следующего.

Pin — это `~/.failproofai/state/semantic/roots/<session-id>.json`, содержащий `{root, at}`: файл `0600`, директория `0700`, и то же session-ID правило как выше. Файлы старше 7 дней удаляются, когда новый session прикрепляет свой root. Директория `roots`, которую другие пользователи могут писать в, игнорируется, и live директория-а root используется вместо. Чтобы re-pin session, удалите его файл.

## Known limits

- **Prompt только столь же надежен, как hook invocation.** Все здесь читает payload, который harness написал на stdin hook-а. Agent, который может запускать команды, может запустить harness headlessly (`claude -p` и семь других, указанных выше) или запустить сам hook binary Failproof AI с payload, который он написал, и записать prompt, который никто не набирал. Это принятый компромисс, описанный в начале этой страницы: он разрешает только reviewable policies, никогда hard — но двенадцать из пятнадцати reviewable встроенных — это deny-и, поэтому поддельный prompt может превратить реальный блок в allow на этих двенадцати.
- **Sub-agent detection — Claude-shaped.** Payload, содержащий `agent_id`, никогда не записывается, на любом harness-е. Это поле, которое Claude Code, Factory Droid и Devin использовали бы. Codex срабатывает его prompt event внутри sub-agent threads, Copilot запускает in-process sidekicks, Goose имеет `delegate` tool и OpenClaw запускает personas — ни один из которых не отмечает payload таким образом, который это признает, поэтому sub-agent prompt на этих harness-ах записывается как собственный session-а. OpenClaw-ы `openclaw.agentId` **не** это отметить: shipped plugin устанавливает его на каждом run, собственный включен.
- **Scheduler-ы, которые не несут marker.** Claude Code-а `schedule_wakeup` и `loop_wakeup`, и OpenClaw-а `cron` и `heartbeat` trigger-ы, отказываются потому, что эти harness-ы говорят об этом в payload. Собственный scheduler Goose (`goose schedule add`) и `codex exec` Codex не говорят ничего, поэтому run, который они начинают, записывается как любой другой.
- **Последнее сообщение agent-а может быть сообщением, которое выбрал agent.** Transcript не аутентифицирован, поэтому agent, который пишет свой собственный transcript, может решить, что говорит его "last message". Он помечен как написанный agent-ом и никогда ничего не очищает сам по себе — но обратите внимание, что v1 path `decide.ts` позволяет ему удовлетворить детерминированную проверку "did the user name this target", поэтому agent, который контролирует свой transcript, может предоставить имя target, которое override нужен.
- **Prompt, который открывается одним из machine heading-ов расширения, полностью удаляется.** Начните prompt с `# Selected text:`, `# Diff comments:`, `# Chrome tabs:` или другого section heading из первой группы выше, и никогда не пишите `## My request:` heading, и ничего не записывается для этого turn — поэтому ничего не очищается для него либо. Это преднамеренно: эти секции несут текст, который кто-то другой контролирует (код, который вы выбрали, diff comment рецензента, заголовок страницы), и запись того, что ваши слова, — это худший отказ. Heading-и, которые разработчик правдоподобно набирает, находятся во второй группе и никогда не удаляют prompt сами по себе.
- **OpenCode ничего не записывает на практике.** Его `message.updated` event не содержит текст в текущем OpenCode, и он также срабатывает для child session-ов, которые его task tool создает, чей "user" message написал родительский agent.
- **`CODEX_HOME` не чтится** обнаружением rollout-а в `lib/codex-sessions.ts`. Это влияет только на то, где ищется agent-message snapshot, никогда на то, будет ли prompt записан.
