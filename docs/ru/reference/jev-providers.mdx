Это справочник провайдеров и конфигурации для [Jev policies](/ru/policies/jev) с вашим ключом. Regex политики сопоставляют строки. Они не могут отличить `rm -rf build/`, который вы запросили, от `rm -rf ~`, который попал в план, поэтому они блокируют слишком много в одном месте и слишком мало в другом. **Jev**, классификатор TypeSafe, анализирует вызов относительно того, что вы на самом деле запросили, и отвечает на набор вопросов "да/нет" о нём в одном быстром запросе.

С вашей конфигурацией Jev endpoint и ключа, Failproof AI запрашивает Jev о каждом tool call **наряду с** regex политиками, никогда вместо них:

- Отказ **hard** политики окончателен. Jev не может его отменить. Каждая политика является hard, если она не помечена явно как reviewable и не называет проверки Jev, которые её охватывают, поэтому пользовательская, пакетная или Cloud политика, которая ничего не говорит, является hard, и встроенная защита всегда является hard.
- Отказ **reviewable** политики может быть отменён, но только если Jev был запрошен о точной проблеме, которую охватывает эта политика, и ответил "здесь ничего нет" или "пользователь попросил это". Проверка, которая находит проблему реальной, когда пользователь не просил этот вызов, сохраняет отказ — даже если её собственный вердикт это только предупреждение, потому что перед tool call предупреждение не останавливает агента. И если эта проверка может выдать отказ (утечка секретов, экфильтрация учетных данных, деструктивное удаление, …), ничего не отменяется для этого вызова.
- Блок всё ещё может стать **предупреждением**, когда вызов является шагом задачи, которую вы дали, и не выходит дальше: Jev смягчает свой собственный отказ до предупреждения, и это предупреждение — описывающее, что на самом деле не так с вызовом — заменяет блок политики.
- Jev может также выдать предупреждение или отказ самостоятельно, для вреда, который regex не описывает.
- Если Jev не может ответить (timeout, rate limit, server error, нет кредитов, неожиданная версия модели), этот вызов получает результат regex, точно как без Jev.
- Jev никогда не делает вызов более разрешительным, чем ваши политики в одиночку, если он не прочитал весь вызов и не был запрошен о точной проблеме. Что-либо меньшее — вызов слишком большой для отправки целиком, подозреваемая инъекция — отзывает разрешения и сохраняет каждый отказ.

<Note>
Без конфигурации Jev ничего не меняется: хуки запускают regex политики точно так же, как всегда. Конфигурация — это весь opt-in.
</Note>

<Tip>
На FailproofAI Cloud? Вам не нужен собственный ключ: машина, подключённая с ключом, который имеет `jev:evaluate`, может использовать Jev для плана вашей организации. See [Jev through FailproofAI Cloud](/ru/reference/jev-cloud).
</Tip>

## Before you start

Install **failproofai 1.0.8-beta.0 or later** и подключите его хуки к [supported harness](/ru/reference/harnesses) на машине, где запускается ваш агент. Следуйте [quickstart](/ru/start/quickstart), если это новая машина, или [set up local enforcement](/ru/start/setup#enforce-locally), если вы не используете Cloud. Проверьте установленный CLI с `failproofai --version`.

Получите API ключ от провайдера ниже или имейте готовые совместимый endpoint и его ключ. Jev рассматривает именованные tool calls на gate `PreToolUse` или `PermissionRequest`. Он может выдавать свой собственный вердикт, но отмена существующего отказа политики также требует установленной политики, помеченной [reviewable](/ru/policies/authority). Hard policy denies остаются окончательными.

## Choose a provider

Jev доступен через пять маршрутов. Принесите ключ для любого из них.

| Provider | `--provider` | Endpoint | Default model | Notes |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Exact version pin. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | Requests are routed to zero-data-retention endpoints only, with no fallback to another provider. Reports a dated version such as `typesafe/jev-1.13-20260917`. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Names Jev only by an alias, so the answering version is recorded as unverified. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | Needs `--account-id`. About six calls a second per key were measured before HTTP 429. |
| Your own endpoint | `custom` | `<base-url>/systemone` | `jev-1.13.0` | Any endpoint that accepts TypeSafe's request body and reports which model answered. `https` only; plain `http` to a loopback host (`localhost`, `127.0.0.1`, `::1`) is accepted for local testing. |

<Warning>
С собственной функцией bring-your-own-key Vercel, неудачный запрос тихо повторяется с учётными данными Vercel. Если вам нужно, чтобы каждый вызов оплачивался и был виден только вашей собственной учётной записи TypeSafe, используйте TypeSafe напрямую.
</Warning>

## Set it up

Одна команда, endpoint и ключ. Начните в режиме `observe`, чтобы вы могли проверить вердикты Jev, пока существующие политики решают вызовы:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### The URL picks the provider

Вам не нужно называть провайдера: **host** URL — это то, какой это провайдер.

| URL host | Provider | Also needs |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| any other host | `custom` | — the URL you gave is the base URL |

Три вещи вытекают из этого:

- **URL, который является собственным API провайдера, не пишет переопределение.** `--url https://api.typesafe.ai/v1` производит ровно конфигурацию, которую дал бы `--provider typesafe`. Дайте другой путь или хост на известном провайдере, и он сохраняется как base URL, как это сохранил бы `--base-url`.
- **`--provider` всё ещё переопределяет вывод**, что помогает вам достичь прокси, который говорит на API провайдера с хоста вашего: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **`--provider`, который противоречит хосту, отказывается**, не угадывается. `--provider openrouter --url https://api.typesafe.ai/v1` ничего не пишет и объясняет почему: два написания не согласны о том, куда ваш ключ вот-вот отправится. Эта же пара отказывается от `jev setup --base-url` и от настроек Jev на панели управления. (`--provider custom` не противоречие — это означает "рассматривать этот URL как сам себя" — кроме хоста Cloudflare, к endpoint которого на аккаунт пользовательский маршрут не может достичь.)

`--url` проверяется точно так же, как `baseUrl` в файле конфига, и отказывается в тех же словах: `https`, или простой `http` на loopback хост (`localhost`, `127.0.0.1`, `::1`) в любом режиме. Риск: ничто не аутентифицирует loopback сервер, поэтому, пока он отключен, другой локальный процесс мог бы занять его порт и ответить; используйте `https` вне локального тестирования.

### The key

Передайте его с `--key-stdin`, или запустите команду в терминале без неё и вставьте ключ на замаскированной подсказке. В любом случае он идёт прямо в файл конфигурации и никогда не печатается обратно.

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` принимает те же флаги и является развёрнутым вариантом всего этого: `setup --provider <kind>`, где вы предпочли бы назвать провайдера, а не URL.

### `--token`, и что это стоит

`--token <token>` помещает ключ в командную строку, что является самым быстрым способом настроить машину и единственным написанием, которое оставляет ключ где-то кроме файла конфигурации:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
Аргумент командной строки впоследствии находится в файле истории вашей оболочки, и пока команда работает, он находится в списке процессов — читаемый из `/proc` чем-либо, работающим как вы. `setup` говорит об этом каждый раз, когда используется `--token`. Предпочитайте `--key-stdin` на машине, которую вы используете совместно, в записанной сессии или где-либо, где файл истории синхронизируется; поворотите ключ, который вы передали таким образом, если это важно.
</Warning>

`--token`, `--key-stdin` и `--key-from-env` взаимно исключают друг друга: дайте один.

Затем отправьте один небольшой живой запрос, чтобы проверить ключ, endpoint и какой Jev ответил:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` выходит с 1, и говорит об этом в заголовке, когда ответ приходит после timeout (каждый хук должен был бы откатиться на regex как `timeout`) или отвечает неправильно на его проверочный вопрос.

Hooks читают конфигурацию при каждом tool call, поэтому она применяется со следующего. Нечего перезапускать, с daemon или без.

## Check what it is doing

```bash
failproofai jev status
failproofai jev status --json
```

`status` показывает провайдера, endpoint, модель, режим, файл конфигурации и его разрешения, и никогда не показывает ключ. Ниже это резюмирует недавнюю деятельность: сколько вызовов Jev оценил, как часто он откатывался на regex и почему, его задержку и какие reviewable политики он отменил.

## Verify a real call

Запустите новую сессию в зафиксированном агенте. Попросите его использовать свой инструмент чтения файлов на `README.md` и сообщить название. Убедитесь, что сессия содержит этот tool call, затем запустите `failproofai jev status` снова: его счётчик недавно оценённых вызовов должен увеличиться. Откройте **Policies → Activity** в [local dashboard](/ru/reference/local-dashboard#review-policy-activity), чтобы проверить вердикт Jev вызова и режим. В режиме observe результат политики все ещё решает вызов. Clearance появляется только если reviewable политика соответствовала и Jev отменил все именованные проверки; обычное чтение может не иметь политики для отмены.

## Observe mode

`enforce` используется по умолчанию. Чтобы наблюдать Jev без позволения ему изменять какое-либо решение, переключитесь на `observe`: Jev всё ещё спрашивается и его вердикты записываются, но результат regex это то, что применяется.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` сохраняет конфигурацию — endpoint и ключ — и прекращает спрашивать Jev: хуки запускают regex политики ровно как без конфигурации, и `failproofai jev status` говорит "off (switched off)". Переключитесь обратно с `--mode observe` или `--mode enforce`.

Повторный запуск `setup` для того же провайдера сохраняет сохранённый ключ, поэтому переключение режима это один флаг. Переключение провайдера начинает с начала и запрашивает ключ того провайдера. Также `--base-url`, который перемещает запросы на другой хост: сохранённый ключ отправляется только на хост, для которого он был дан, или на собственный API его провайдера.

## The config file

Всё находится в одном файле, `~/.failproofai/jev.json`, написанном `setup`:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Field | Meaning |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` или `custom` — или `failproofai`, чей ключ поступает из подключения FailproofAI Cloud вместо этого файла (см. [Jev through FailproofAI Cloud](/ru/reference/jev-cloud)). |
| `apiKey` | Отправлено как `Authorization: Bearer <key>`. |
| `baseUrl` | Требуется для `custom`; заменяет base API провайдера в противном случае. Должен быть `https`. Простой `http` на `localhost` принимается только с `mode: observe`: ничто не аутентифицирует локальный порт, поэтому, пока ваш прокси отключен, любой процесс на машине, включая оцениваемого агента, мог бы ответить на его месте. |
| `accountId` | Cloudflare only: 32 lowercase hex characters. |
| `model` | Заменяет default model id провайдера. Версионированный id должен назвать Jev 1.13. Значение, которое выглядит как API ключ, отказывается (и не повторяется обратно), поэтому ключ, вставленный в `--model`, никогда не сохраняется или не отправляется как модель. |
| `timeoutMs` | Как долго tool call ждёт Jev перед использованием результата regex. 100–10000, default 3000. |
| `mode` | `enforce` (default), `observe`, или `off` (сохранить конфигурацию, не запускать Jev). |

Три правила защищают его:

- **Только владелец.** Он пишется с разрешениями `0600`. Копия, которую может читать или писать любой другой пользователь или группа, **отказывается**, и хуки откатываются на regex, пока вы не запустите `chmod 600 ~/.failproofai/jev.json` или `setup` снова. Директория тоже проверяется: `~/.failproofai` не должна быть **writable** никем другим, потому что всякий, кто может писать туда, может заменить файл, какими бы ни были его собственные разрешения. `setup` снимает те биты записи, если их найдёт. `failproofai jev status` говорит, когда конфигурация была отказана и показывает endpoint, который файл называет: кто-то ещё может изменить его, поэтому проверьте, что он ваш, перед `chmod`. Повторный запуск `setup` на таком файле несёт его сохранённый ключ только API провайдера; любой другой endpoint, который он называет, нужна ключ снова (`--key-stdin`), или `--base-url default`, чтобы отправить запросы обратно провайдеру.
- **Только глобально.** Репозиторий не может включить Jev, указать его на другой endpoint или выбрать его модель: `.failproofai/jev.json` внутри проекта игнорируется, и провайдер, URL, модель и account id читаются только из этого файла — никогда из окружения, которое может установить agent settings репозитория. (`FAILPROOFAI_HOME` это не способ обойти это: это перемещает всю failproofai директорию, включая ваши политики, а не переменный маршрут Jev в одиночку.)
- **Только ключ может поступить из окружения.** Если файл не имеет `apiKey`, `FAILPROOFAI_JEV_API_KEY` предоставляет её для этой сессии (`setup --key-from-env` пишет такой файл). Это никогда не заменяет ключ, который держит файл, и не может включить Jev без файла. Где переменная не установлена, Jev просто отключен для этой оболочки: `failproofai jev status` говорит об этом, выходит 0 и оставляет конфигурацию в покое (`status --json` сообщает `"status": "key-missing"` с `"reason": "no-env-key"`). Daemon `failproofaid` не видит окружение вашей оболочки, поэтому на машине, установленной с `failproofai config`, сохраняйте ключ в файле.

## Which Jev answers

Пороги решений Failproof AI были откалиброваны на Jev 1.13, поэтому ответ используется только когда он поступает из этого семейства: `jev-1.13.x`, или OpenRouter `typesafe/jev-1.13-<date>`. Где провайдер называет Jev только по псевдониму и не сообщает версию (Vercel и Cloudflare когда это не говорит), ответ используется и записывается как неверифицированный. Пользовательский `custom` endpoint должен сообщить модель, которая ответила; единственное исключение это невверсионированное имя `--model`, которое вы сконфигурировали для него, которое, отражённое обратно, записывается как неверифицированное таким же образом. Ответ, сообщающий любую другую версию, или ответ `custom`, не сообщающий версию, не используется: этот вызов откатывается на regex с причиной `model-mismatch`.

## When Jev cannot answer

Каждое из них откатывается на результат regex для этого вызова и записывается с его причиной, которую `failproofai jev status` итоги:

| Reason | Cause |
| --- | --- |
| `timeout` | Нет ответа в течение `timeoutMs`. |
| `http-429` | Провайдер ограничил частоту ключа. |
| `rate-limited` | Собственный ограничитель Failproof AI удержал вызов, прежде чем отправить его: 5 запросов в секунду, в импульсах до 5, и ничего на момент после того, как провайдер ответит `429`. Не провайдер. |
| `http-500`, `http-502`, `http-503`, … | Ошибка сервера у провайдера. Точный статус записывается. |
| `out-of-credits` | HTTP 402: учётная запись провайдера не имеет оставшихся кредитов. |
| `provider-refused` | HTTP 402 от Cloudflare, читающий "Model execution failed (Payment error)": провайдер отказался запускать модель на этом запросе. Обычно не биллинг, поэтому пополнение счёта не решит проблему. |
| `http-401`, `http-403` | Ключ был отказан. |
| `http-404` | Ничто не обслуживается в `<base>/systemone`, поэтому base URL неправильный — `/systemone` добавляется к нему, и каждый провайдер обслуживает его в корне версии. `failproofai jev models` показывает, что обслуживает endpoint. |
| `network` | Endpoint не может быть достигнут. |
| `http-301`, `http-302`, `http-307`, `http-308` | Endpoint ответил с перенаправлением. Перенаправления никогда не следуются, поэтому ответ поступает только из URL в вашей конфигурации; установите `--base-url` на финальный URL. |
| `malformed` | Endpoint ответил, но не с ответом Jev — body, который не JSON, или один без ответов в нём. |
| `cloudflare-error`, `cloudflare-incomplete` | Конверт Cloudflare сообщил об отказе, или о задании, которое не завершилось. |
| `model-mismatch` | Версия Jev, отличная от 1.13, ответила, или `custom` endpoint не сказал, какая модель ответила. |
| `request-cut` | **Не сбой.** Jev ответил; ему была показана только часть вызова, поэтому его ответ ничего не отменил. См. [When Jev answered, but not on the whole call](#when-jev-answered-but-not-on-the-whole-call). |

`failproofai jev status` может показать несколько более редких причин тоже, таких как `upstream-error` (ответ содержал собственную ошибку провайдера) или `config`, и итоговые любые причины, которые это не может назвать как `other`.

`request-cut` находится в этой таблице, потому что `failproofai jev status` итоговые его с остальным, и потому что он тоже оставляет каждый отказ стоящим. Это единственная причина здесь, которая ничего не говорит о вашем провайдере: запрос прибыл и Jev ответил на него. В отличие от каждой строки выше, этот ответ всё ещё учитывается — собственный отказ Jev или предупреждение применяется поверх результата regex, а не отбрасывается. Поэтому серия их означает, что вызовы достигают оценщика слишком большими для отправки целиком, а не то, что ваш endpoint нездоров, и пополнение кредитов или изменение URL не решит число.

## When Jev answered, but not on the whole call

Два больше вещей могут произойти, и ни одно не означает Jev не ответить. Оба касаются того, сколько вызова, или разговора, вместилось в один запрос.

**Часть самого вызова не подходила.** Tool call отправляется внутри фиксированного бюджета, и огромный — очень большая `Write`, огромное MCP body, команда дополненная к cap — отправляется с тем, что подходило. Jev всё ещё отвечает, и его ответ всё ещё учитывается: его собственный отказ или предупреждение применяется как обычно. Что он не может сделать, это **отменить** что-либо, потому что вердикт, данный по части вызова, это не вердикт по вызову. Так что каждый policy deny стоит, и вызов записывается как fallback с причиной `request-cut`, которую `failproofai jev status` итоговые наряду с причинами выше. Правило, которое это даёт вам: делание вызова больше может стоить его clearances, и никогда не может купить один.

**Сообщение не подходило.** Длинный prompt, который вы вставили, последнее сообщение агента или prompt этот оценщик сам уже capped. **Ничто не меняется**: вызов судится, отменяется и записывается точно так же, как любой другой, и это не считается fallback. Длина того, что вы печатаете, никогда не решает вердикт, и cut не может производить согласие: где prompt прибыл уже capped, "вы не просили это" перестаёт быть выводом, который может быть сделан из этого вообще, а не становиться одним.

Линия между двумя это кто написал текст. Вызов это агента, и правило, которое позволило его длине вычесть серьёзность, было бы правилом агент может использовать; ваш prompt это ваш, и рассмотрение его длины как сигнала только когда-либо наказано вставкой spec или stack trace.

## What leaves the machine

Для каждого tool call Jev оценивает, один запрос идёт вашему провайдеру, несущему:

- сам tool call, с секретами такими как API ключи, bearer tokens и `KEY=` assignments redacted;
- недавние prompts, которые вы печатали, с текстом, который harness вашего агента добавил удалён;
- последнее сообщение агента перед вашим последним prompt, помеченное как agent-written;
- факты вычисленные локально, такие как находится ли путь внутри проекта — то, в котором сессия была в её первом рассмотренном вызове, [pinned for the session](/ru/reference/jev-intent#the-project-root) — и текущая git branch.

Он идёт только на endpoint в вашей конфигурации, под вашим ключом.

## Turn it off

```bash
failproofai jev remove
```

Это удаляет `~/.failproofai/jev.json`. С следующего tool call, хуки запускают regex политики ровно как перед. Per-session stores под `~/.failproofai/state/semantic/` (recorded prompts в `sessions/`, project roots в `roots/`) оставлены на месте и age out. Чтобы прекратить просить Jev но сохранить конфигурацию, используйте `failproofai jev setup --mode off` вместо этого.

| --- | --- |
| `failproofai jev --url <url> --key-stdin` | Настройте это в одной команде; провайдер поступает из хоста URL |
| `failproofai jev --url <url> --token <token>` | Так же, с ключом в командной строке — ваша история и список процессов видят это |
| `failproofai jev setup --provider <kind> --key-stdin` | Напишите конфигурацию из ключа, переданного на stdin |
| `failproofai jev setup --provider <kind>` | То же, запрашивая ключ на замаскированной подсказке |

| `failproofai jev setup --mode observe` | Переключите режим (`enforce`, `observe` или `off`), сохраняя сохранённый ключ |
| `failproofai jev setup --model <id>` / `--base-url <url>` | Переопределите модель или API base; `default` очищает переопределение |
| `failproofai jev setup --timeout-ms <n>` | Измените per-call бюджет |
| `failproofai jev status [--json]` | Конфигурация, разрешения и недавняя деятельность; никогда не ключ |
| `failproofai jev test [--json]` | Один живой запрос: задержка и версия, которая ответила |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | Model ids, которые endpoint `/models` сообщает, отмечая настроенный |
| `failproofai jev remove` | Удалите конфигурацию; Jev отключен |
