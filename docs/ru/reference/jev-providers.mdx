Это справочник провайдеров и конфигурации для [политик Jev](/ru/policies/jev) с вашим ключом. Regex-политики проверяют строки. Они не могут отличить `rm -rf build/`, который вы запросили, от `rm -rf ~`, попавшего в план случайно, поэтому они блокируют слишком много в одном месте и слишком мало в другом. **Jev**, классификатор TypeSafe, анализирует вызов относительно того, что вы на самом деле запросили, и отвечает на набор вопросов да/нет о нём за один быстрый запрос.

С вашей точкой Jev и настроенным ключом Failproof AI спрашивает Jev о каждом вызове инструмента **наряду с** regex-политиками, но не вместо них:

- Отказ **жёсткой** политики является окончательным. Jev не может его отменить. Каждая политика является жёсткой, если явно не помечена как рецензируемая и не указывает проверки Jev, которые её покрывают, поэтому пользовательская, пакетная или облачная политика, которая ничего не говорит, является жёсткой, и всегда включённая самозащита также всегда жёсткая.
- Отказ **рецензируемой** политики может быть отменён, но только если Jev был спрошен точно о проблеме, которую политика покрывает, и ответил "ничего здесь" или "пользователь запросил это". Проверка, которая обнаружит проблему в реальности, когда пользователь не запросил вызов, сохранит отказ — даже если её собственный вердикт только предупреждение, потому что перед вызовом инструмента предупреждение не останавливает агента. И если эта проверка способна отказать (раскрытие секрета, экспортирование учётных данных, деструктивное удаление, …), никакие отмены не происходят при таком вызове.
- Блок всё ещё может стать **предупреждением**, если вызов является шагом задачи, которую вы дали, и не идёт дальше: Jev смягчает свой отказ до предупреждения, и это предупреждение — указывающее на то, что реально неправильного с вызовом, — заменяет блок политики.
- Jev также может предупредить или отказать самостоятельно, для вреда, который regex не описывает.
- Если Jev не может ответить (timeout, ограничение частоты, ошибка сервера, нет кредитов, неожиданная версия модели), этот вызов получает результат regex, точно как без Jev.
- Jev никогда не делает вызов более разрешительным, чем ваши политики в одиночку, если не прочитал весь вызов и не был спрошен о точной проблеме. Меньше того — вызов слишком большой для отправки целиком, подозреваемая инъекция — отзывает отмены и сохраняет каждый отказ.

<Note>
Без конфигурации Jev ничего не меняется: крючки запускают regex-политики точно как всегда. Конфигурация — это полное добровольное решение.
</Note>

<Tip>
Используете FailproofAI Cloud? Вам не нужен собственный ключ: машина, подключённая ключом с разрешением `jev:evaluate`, может использовать Jev на плане вашей организации. См. [Jev через FailproofAI Cloud](/ru/reference/jev-cloud).
</Tip>

## Перед началом

Установите **failproofai 1.0.8-beta.0 или позже** и присоедините его крючки к [поддерживаемой среде](/ru/reference/harnesses) на машине, где запущен ваш агент. Следите [кратким руководством](/ru/start/quickstart), если это новая машина, или [установите локальное принудительное применение](/ru/start/setup#enforce-locally), если вы не используете Cloud. Проверьте установленный CLI с помощью `failproofai --version`.

Получите API-ключ от провайдера ниже или подготовьте совместимую точку и её ключ. Jev проверяет именованные вызовы инструментов на воротах `PreToolUse` или `PermissionRequest`. Он может выдать собственный вердикт, но отмена существующего отказа политики также требует установленной политики, помеченной как [рецензируемая](/ru/policies/authority). Жёсткие отказы политик остаются окончательными.

## Выберите провайдера

Jev доступен через пять маршрутов. Приготовьте ключ для любого из них.

| Провайдер | `--provider` | Endpoint | Модель по умолчанию | Примечания |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | Точная привязка версии. |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | Запросы маршрутизируются только на endpoints с нулевым хранением данных, без fallback на другого провайдера. Сообщает датированную версию, например `typesafe/jev-1.13-20260917`. |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Называет Jev только по псевдониму, поэтому ответившая версия записывается как непроверенная. |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | Требует `--account-id`. Около шести вызовов в секунду на ключ были замерены перед HTTP 429. |
| Ваша собственная точка | `custom` | `<base-url>/systemone` | `jev-1.13.0` | Любая точка, которая принимает тело запроса TypeSafe и сообщает, какая модель ответила. Только `https`; обычный `http` на хост loopback (`localhost`, `127.0.0.1`, `::1`) принимается для локального тестирования. |

<Warning>
С функцией собственного ключа Vercel неудачный запрос автоматически переправляется с учётными данными Vercel. Если вам нужно, чтобы каждый вызов был выставлен и виден только вашей собственной учётной записи TypeSafe, используйте TypeSafe напрямую.
</Warning>

## Настройте это

Одна команда, endpoint и ключ. Начните в режиме `observe`, чтобы вы могли проверить вердикты Jev, пока существующие политики принимают решения:

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL выбирает провайдера

Вам не нужно называть провайдера: **хост** URL — это он.

| Хост URL | Провайдер | Также требует |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| любой другой хост | `custom` | — URL, который вы дали, является базовым URL |

Из этого следуют три вещи:

- **URL, который является собственным API провайдера, не записывает переопределение.** `--url https://api.typesafe.ai/v1` производит точно такую же конфигурацию, как и `--provider typesafe`. Дайте другой путь или хост на известном провайдере, и он хранится как базовый URL, как `--base-url` это хранил бы.
- **`--provider` всё ещё переопределяет вывод**, это как вы достигаете прокси, который говорит на API провайдера с хоста вашего собственного: `--url https://jev-proxy.internal/v1 --provider typesafe`.
- **`--provider`, который противоречит хосту, отказывается**, не угадывается. `--provider openrouter --url https://api.typesafe.ai/v1` не записывает ничего и говорит почему: два написания не согласны о том, куда собирается отправиться ваш ключ. Та же пара отказывается от `jev setup --base-url` и от панели инструментов Jev settings. (`--provider custom` — это не противоречие — это означает "рассматривать этот URL как него самого" — кроме как на хосте Cloudflare, чей per-account endpoint пользовательский маршрут не может достичь.)

`--url` проверяется точно так же, как `baseUrl` в файле конфигурации, и отказывается теми же словами: `https`, или обычный `http` на хост loopback (`localhost`, `127.0.0.1`, `::1`) в любом режиме. Риск: никто не аутентифицирует локальный сервер, поэтому пока он отключён, другой локальный процесс может захватить его порт и ответить; используйте `https` вне локального тестирования.

### Ключ

Передайте его через трубу с `--key-stdin`, или запустите команду в терминале без неё и вставьте ключ в замаскированное приглашение. В любом случае он сразу же попадает в файл конфигурации и никогда не печатается обратно.

  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` принимает те же флаги и является полной формой всего этого: `setup --provider <kind>`, если вы предпочитаете называть провайдера вместо URL.

### `--token` и его стоимость

`--token <token>` ставит ключ в командную строку, что является самым быстрым способом настроить машину и единственным написанием, которое оставляет ключ где-то, кроме файла конфигурации:

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
Аргумент командной строки оказывается в файле истории вашей оболочки после этого, и пока команда запущена, он в списке процессов — доступен из `/proc` для всего, работающего от вас. `setup` говорит об этом каждый раз, когда используется `--token`. Предпочитайте `--key-stdin` на машине, которую вы делите, в записанной сессии, или где бы ни был синхронизирован файл истории; ротируйте ключ, который вы передали таким образом, если это важно.
</Warning>

`--token`, `--key-stdin` и `--key-from-env` взаимоисключающие: дайте один.

Затем отправьте один небольшой живой запрос, чтобы проверить ключ, endpoint и какой Jev ответил:

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

`jev test` выходит с кодом 1, и говорит об этом в своём заголовке, когда ответ прибывает после timeout (каждый крючок вернулся бы к regex как `timeout`) или ответит на вопрос проверки неправильно.

Крючки читают конфигурацию при каждом вызове инструмента, поэтому она применяется со следующего. Нет ничего, что нужно перезапускать, с daemon или без.

## Проверьте, что он делает

```bash
failproofai jev status
failproofai jev status --json
```

`status` показывает провайдера, endpoint, модель, режим, файл конфигурации и его разрешения, и никогда ключ. Ниже это резюмирует недавнюю активность: сколько вызовов Jev оценил, как часто он вернулся к regex и почему, его задержку, и какие рецензируемые политики он отменил.

## Проверьте реальный вызов

Начните новую сессию в перехватываемом агенте. Попросите его использовать инструмент чтения файлов на `README.md` и сообщить заголовок. Убедитесь, что сессия содержит этот вызов инструмента, затем запустите `failproofai jev status` снова: её недавний счётчик оценённых вызовов должен увеличиться. Откройте **Policies → Activity** на [локальной панели управления](/ru/reference/local-dashboard#review-policy-activity), чтобы проверить вердикт Jev и режим вызова. В режиме observe результат политики всё ещё решает вызов. Отмена появляется только если рецензируемая политика совпадала и Jev отменил каждую названную проверку; обычное чтение может не иметь политики для отмены.

## Режим observe

`enforce` — режим по умолчанию. Чтобы наблюдать Jev без позволения ему изменять какое-либо решение, переключитесь на `observe`: Jev всё ещё спрашивается и его вердикты записываются, но результат regex — это то, что применяется.

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` сохраняет конфигурацию — endpoint и ключ — и прекращает спрашивать Jev: крючки запускают regex-политики точно как без конфигурации, и `failproofai jev status` говорит "off (switched off)". Переключитесь обратно с `--mode observe` или `--mode enforce`.

Повторный запуск `setup` для того же провайдера сохраняет сохранённый ключ, поэтому переключение режима — это один флаг. Переключение провайдера начинается заново и просит ключ этого провайдера. Также переключается `--base-url`, который перемещает запросы на другой хост: сохранённый ключ отправляется только на хост, для которого он был дан, или на собственный API его провайдера.

## Файл конфигурации

Всё находится в одном файле, `~/.failproofai/jev.json`, написанном `setup`:

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| Поле | Значение |
| --- | --- |
| `provider` | `typesafe`, `openrouter`, `vercel`, `cloudflare` или `custom` — или `failproofai`, ключ которого поступает из подключения FailproofAI Cloud вместо этого файла (см. [Jev через FailproofAI Cloud](/ru/reference/jev-cloud)). |
| `apiKey` | Отправлено как `Authorization: Bearer <key>`. |
| `baseUrl` | Требуется для `custom`; в противном случае заменяет базовый API провайдера. Должно быть `https`. Обычный `http` на `localhost` принимается только с `mode: observe`: никто не аутентифицирует локальный порт, поэтому пока ваш прокси отключён, любой процесс на машине, включая оцениваемого агента, может ответить на его месте. |
| `accountId` | Только Cloudflare: 32 символа нижнего шестнадцатеричного. |
| `model` | Заменяет ID модели провайдера по умолчанию. ID версии должен назвать Jev 1.13. Значение, похожее на API-ключ, отказано (и не повторено), поэтому ключ, вставленный в `--model`, никогда не хранится или не отправляется как модель. |
| `timeoutMs` | Как долго вызов инструмента ждёт Jev перед использованием результата regex. 100–10000, по умолчанию 3000. |
| `mode` | `enforce` (по умолчанию), `observe` или `off` (сохранить конфигурацию, не запускать Jev). |

Три правила его защищают:

- **Только владелец.** Он написан с разрешениями `0600`. Копия, которую может читать или писать любой другой пользователь или группа, **отказана**, и крючки вернулись к regex, пока вы не запустите `chmod 600 ~/.failproofai/jev.json` или `setup` снова. Каталог также проверяется: `~/.failproofai` не должен быть **записываемым** никем другим, потому что тот, кто может писать там, может заменить файл независимо от его собственных разрешений. `setup` отключает эти биты записи, если их находит. `failproofai jev status` говорит, когда конфигурация была отказана, и показывает endpoint, который файл назвал: кто-то ещё мог его изменить, поэтому проверьте, что это ваш перед тем как `chmod`. Повторный запуск `setup` на таком файле несёт его сохранённый ключ только на собственный API провайдера; любой другой endpoint, который он называет, требует ключ снова (`--key-stdin`), или `--base-url default` для отправки запросов обратно провайдеру.
- **Только глобально.** Репозиторий не может включить Jev, указать на другой endpoint или выбрать его модель: `.failproofai/jev.json` внутри проекта игнорируется, и провайдер, URL, модель и account id читаются только из этого файла — никогда из окружения, которое агент настройки проекта может установить. (`FAILPROOFAI_HOME` — это не обход: это перемещает весь каталог failproofai, включая ваши политики, вместо перенаправления только Jev.)
- **Только ключ может поступать из окружения.** Если файл не имеет `apiKey`, `FAILPROOFAI_JEV_API_KEY` поставляет его для этой сессии (`setup --key-from-env` записывает такой файл). Он никогда не заменяет ключ, который файл держит, и он не может включить Jev без файла. Где переменная не установлена, Jev просто отключён для той оболочки: `failproofai jev status` говорит об этом, выходит 0 и оставляет конфигурацию в покое (`status --json` сообщает `"status": "key-missing"` с `"reason": "no-env-key"`). Daemon `failproofaid` не видит окружение вашей оболочки, поэтому на машине, установленной с `failproofai config`, храните ключ в файле.

## Какой Jev отвечает

Пороги решений Failproof AI были откалиброваны на Jev 1.13, поэтому ответ используется только когда он приходит из этого семейства: `jev-1.13.x`, или OpenRouter's `typesafe/jev-1.13-<date>`. Где провайдер называет Jev только по псевдониму и не сообщает версию (Vercel и Cloudflare, когда не сообщает), ответ используется и записывается как непроверенный. Пользовательский endpoint должен сообщить модель, которая ответила; единственное исключение — это неверсионное имя `--model`, которое вы для него настроили, что, эхо обратно, записывается как непроверенное тем же образом. Ответ, сообщающий любую другую версию, или пользовательский ответ, сообщающий никакой, не используется: этот вызов вернулся к regex с причиной `model-mismatch`.

## Когда Jev не может ответить

Каждое из этих событий вернулась к результату regex для этого вызова и записано с его причиной, которую `failproofai jev status` суммирует:

| Причина | Причина |
| --- | --- |
| `timeout` | Нет ответа в пределах `timeoutMs`. |
| `http-429` | Провайдер ограничил частоту ключа. |
| `rate-limited` | Собственный лимитер Failproof AI задержал вызов перед его отправкой: 5 запросов в секунду, всплески до 5, и ничего на момент после того, как провайдер ответит `429`. Не провайдер. |
| `http-500`, `http-502`, `http-503`, … | Ошибка сервера на провайдере. Точный статус записан. |
| `out-of-credits` | HTTP 402: учётная запись провайдера больше не имеет кредитов. |
| `provider-refused` | HTTP 402 от Cloudflare, читая "Model execution failed (Payment error)": провайдер отказался запустить модель на этот запрос. Обычно не выставление счётов, поэтому пополнение не подвинет его. |
| `http-401`, `http-403` | Ключ был отказан. |
| `http-404` | Ничего не обслуживается в `<base>/systemone`, поэтому базовый URL неправильный — `/systemone` добавляется к нему, и каждый провайдер обслуживает его на корне своей версии. `failproofai jev models` показывает, что обслуживает endpoint. |
| `network` | Endpoint не может быть достигнут. |
| `http-301`, `http-302`, `http-307`, `http-308` | Endpoint ответил с перенаправлением. Перенаправления никогда не следуют, поэтому ответ только когда-либо поступает из URL в вашей конфигурации; установите `--base-url` на финальный URL. |
| `malformed` | Endpoint ответил, но не с ответом Jev — тело, которое не является JSON, или одно без ответов в нём. |
| `cloudflare-error`, `cloudflare-incomplete` | Конверт Cloudflare сообщил о сбое, или работе, которая не была завершена. |
| `model-mismatch` | Jev версия, отличная от 1.13, ответила, или пользовательский endpoint не сказал, какая модель ответила. |
| `request-cut` | **Не отключение.** Jev ответил; ему показана была только часть вызова, поэтому его ответ не отменил ничего. См. [Когда Jev ответил, но не на весь вызов](#when-jev-answered-but-not-on-the-whole-call). |

`failproofai jev status` также может показать несколько редких причин, таких как `upstream-error` (ответ нёс собственную ошибку провайдера) или `config`, и суммирует любую причину, которую не может назвать, как `other`.

`request-cut` находится в этой таблице, потому что `failproofai jev status` суммирует это с остальным, и потому что оно также оставляет стоять каждый отказ. Это единственная причина здесь, которая говорит ничего о вашем провайдере: запрос прибыл и Jev ответил на него. В отличие от каждой строки выше неё, этот ответ всё ещё считается — собственный отказ Jev или предупреждение применяется поверх результата regex вместо того, чтобы быть отброшено. Поэтому ряд их означает, что вызовы достигают оценивающего слишком большие для отправки целиком, не что ваш endpoint неудачен, и пополнение кредитов или изменение URL не подвинет число.

## Когда Jev ответил, но не на весь вызов

Могут произойти ещё две вещи, и ни одна не является Jev неудачей ответить. Обе касаются того, сколько вызова, или разговора, вмещалось в один запрос.

**Часть самого вызова не вмещалась.** Вызов инструмента отправлен внутри фиксированного бюджета, и огромный — очень большой `Write`, огромное MCP тело, команда заполненная до крышки — отправляется с тем, что вмещалось. Jev всё ещё отвечает, и его ответ всё ещё считается: его собственный отказ или предупреждение применяется как обычно. Что он не может делать, — это **отменять** что-либо, потому что вердикт, данный на части вызова, — это не вердикт на вызов. Поэтому каждый отказ политики стоит, и вызов записан как fallback с причиной `request-cut`, которую `failproofai jev status` суммирует наряду с причинами выше. Правило это даёт вам: делание вызова больше может стоить ему его отмен, и никогда не может купить одну.

**Сообщение не вмещалось.** Длинный prompt, который вы вставили, последнее сообщение агента, или prompt, который хранилище этого оценивающего уже ограничивало. **Ничего не меняется**: вызов судится, отменяется и записан точно как любой другой, и он не считается как fallback. Длина того, что вы печатаете, никогда не решает вердикт, и отрезание не может изготовить согласие: где prompt прибыл уже ограниченным, "вы не просили это" перестаёт быть заключением, которое может быть сделано из него вообще, вместо того чтобы становиться одним.

Линия между этими двумя — кто написал текст. Вызов — это агент, и правило, которое позволило его длине вычесть суровость, было бы правилом, которое агент может использовать; ваш prompt — это ваш, и рассматривание его длины как сигнала только когда-либо наказало вставление спека или трассировки стека.

## Что оставляет машину

Для каждого вызова инструмента, который Jev оценивает, один запрос идёт вашему провайдеру, нося:

- сам вызов инструмента, с секретами, такими как API-ключи, bearer tokens и `KEY=` назначения замаскированы;
- недавние prompts, которые вы напечатали, с текстом, который добавила среда вашего агента, удалён;
- последнее сообщение агента перед вашим последним prompt, помечено как написанное агентом;
- факты, вычисленные локально, такие как находится ли путь внутри проекта — тот, в котором была сессия при её первом проверенном вызове, [закреплённый для сессии](/ru/reference/jev-intent#the-project-root) — и текущее git ветку.

Он идёт только к endpoint в вашей конфигурации, под вашим ключом.

## Выключите его

```bash
failproofai jev remove
```

Это удаляет `~/.failproofai/jev.json`. Со следующего вызова инструмента крючки запускают regex-политики точно как раньше. Хранилища per-session под `~/.failproofai/state/semantic/` (записанные prompts в `sessions/`, корни проектов в `roots/`) оставлены на месте и стареют. Чтобы прекратить спрашивание Jev, но сохранить конфигурацию, используйте `failproofai jev setup --mode off` вместо этого.

## Справка команд

| Команда | Результат |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | Настройте это в одной команде; провайдер приходит из хоста URL |
| `failproofai jev --url <url> --token <token>` | То же самое, с ключом в командной строке — ваша история и список процессов видят его |
| `failproofai jev setup --provider <kind> --key-stdin` | Напишите конфигурацию из ключа, переданного на stdin |
| `failproofai jev setup --provider <kind>` | То же самое, спрашивая ключ в замаскированном приглашении |
| `failproofai jev setup --key-from-env` | Не хранить ключ; читать `FAILPROOFAI_JEV_API_KEY` per session |
| `failproofai jev setup --mode observe` | Переключить режим (`enforce`, `observe` или `off`), сохраняя сохранённый ключ |
| `failproofai jev setup --model <id>` / `--base-url <url>` | Переопределить модель или базовый API; `default` очищает переопределение |
| `failproofai jev setup --timeout-ms <n>` | Изменить per-call бюджет |
| `failproofai jev status [--json]` | Конфигурация, разрешения и недавняя активность; никогда не ключ |
| `failproofai jev test [--json]` | Один живой запрос: задержка и версия, которая ответила |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | ID модели, которые endpoint `/models` сообщает, помечая настроенную |
| `failproofai jev remove` | Удалить конфигурацию; Jev отключён |
