Пользовательские политики преобразуют паттерн отказа из ваших трассировок или аудитов в решение, которое выполняется во время работы агента. Политика может разрешить действие, дать агенту рекомендацию или запретить действие до того, как оно вызовет новый инцидент.

Используйте пользовательскую политику, когда поведение зависит от ваших инструментов, путей, команд, окружений или операционных правил. Сначала проверьте [каталог встроенных политик](/ru/policies/builtin-catalog), чтобы не воссоздавать существующий контроль.

## Создание пользовательской политики

## Начните с узкого правила

Эта политика блокирует деструктивные команды Kubernetes только когда команда нацеливается на production. Всё остальное вне этого точного паттерна отказа возвращает `allow()`.

```ts
import { customPolicies, allow, deny } from "failproofai";

const DESTRUCTIVE_KUBECTL = /\bkubectl\s+(delete|replace)\b/i;
const PRODUCTION_TARGET = /(?:--context|--namespace|-n)\s+(prod|production)\b/i;

customPolicies.add({
  name: "block-destructive-production-kubectl",
  description: "Block destructive Kubernetes commands against production",
  match: { events: ["PreToolUse"] },
  fn: async ({ toolName, toolInput }) => {
    if (toolName !== "Bash") return allow();

    const command = String(toolInput?.command ?? "");
    if (!DESTRUCTIVE_KUBECTL.test(command)) return allow();
    if (!PRODUCTION_TARGET.test(command)) return allow();

    return deny(
      "Destructive production Kubernetes commands require the approved deployment workflow.",
    );
  },
});
```

Хорошие политики достаточно узкие, чтобы их можно было объяснить одним предложением. Совпадайте с наблюдаемым действием — не с намерением, которое вы надеялись иметь у агента — и возвращайте `allow()` как только правило не применяется.

## Выберите решение

| Помощник | Результат | Используйте, когда |
| --- | --- | --- |
| `allow(reason?)` | Операция продолжается. | Политика не применяется или действие безопасно. |
| `instruct(reason)` | Операция продолжается, и причина доставляется агенту на привязках, которые имеют для этого канал. | Вы хотите направить агента на лучший подход без применения инварианта. |
| `deny(reason)` | Операция блокируется на привязке и парах событий, проверенных на потребление решения блокировки. | Действие не должно продолжаться. |

Напишите причину агенту, который должен восстановиться. Объясните, что было обнаружено и что ему нужно делать вместо этого.

### Где `instruct()` фактически попадает

`instruct()` требует дополнительного контекстного канала в привязке. Шесть привязок не имеют его на некоторых или всех событиях; там операция разрешена и сообщение записывается в stderr, где агент его никогда не читает.

| Привязка | События, которые доставляют инструкцию |
| --- | --- |
| Claude, Codex, Copilot, Cursor, Devin, OpenCode | `PreToolUse`, `PostToolUse`, `UserPromptSubmit` и `PermissionRequest` доставляют его как дополнительный контекст. `Stop` и `SubagentStop` доставляют его через канал повтора. Каждое другое событие выводит сообщение, которое привязка игнорирует. |
| Antigravity | Только `UserPromptSubmit` и `Stop`. |
| Factory, Pi, OpenClaw | Только `Stop`. |
| Hermes, Goose | Ни один. Всегда разрешение плюс заметка в stderr. |

Ни одна привязка не вызывает все 29 канонических событий, поэтому первая строка ограничена тем, что каждая устанавливает — инструкция попадает только на событие, которое привязка фактически вызывает. Проверьте установленный набор событий для каждой привязки в [Agent harnesses](/ru/reference/harnesses) перед использованием одного.

<Warning>
  Не используйте `instruct()` для границы безопасности. На Hermes и Goose он никогда не достигает агента вообще, а на Antigravity, Factory, Pi и OpenClaw он не достигает его на событиях инструментов. Используйте `deny()`, когда действие должно быть предотвращено.
</Warning>

## Объект политики

```ts
customPolicies.add({
  name: "policy-name",
  description: "What this policy prevents",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => allow(),
});
```

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `name` | Да | Стабильный идентификатор для политики. Держите имена уникальными между файлами. |
| `description` | Нет | Понятное назначение, показываемое в списках политик и решениях. |
| `match.events` | Нет | Типы событий, которые вызывают политику. Пропуск `match` вызывает её для каждого доступного события. |
| `fn` | Да | Синхронная или асинхронная функция, которая возвращает результат `allow`, `instruct` или `deny`. |

Фильтруйте инструменты внутри `fn`. `match.toolNames` не является частью открытого типа пользовательской политики.

Политика, опубликованная внутри пакета, может содержать два дополнительных поля, `category` и `defaultEnabled`. See [From a file to a pack](#from-a-file-to-a-pack).

## Контекст политики

Каждая политика получает `PolicyContext`.

| Поле | Тип | Что оно содержит |
| --- | --- | --- |
| `eventType` | `HookEventType` | Нормализованное событие, которое в настоящее время оценивается. |
| `toolName` | `string \| undefined` | Каноническое имя инструмента, такое как `Bash`, `Read`, `Write` или `Edit`. |
| `toolInput` | `Record<string, unknown> \| undefined` | Канонический ввод для текущего вызова инструмента. |
| `payload` | `Record<string, unknown>` | Полная нормализованная полезная нагрузка события. |
| `session` | `SessionMetadata \| undefined` | ID сеанса, рабочий каталог, путь к транскрипту, режим разрешения и метаданные привязки, когда доступны. |
| `cli` | `string \| undefined` | Привязка исходного агента, такая как `claude`, `codex` или `cursor`. |
| `params` | `Record<string, unknown>` | Параметры для этой политики. Встроенная или упакованная политика объявляет схему, и значения, которые пользователь настроил, объединяются с её значениями по умолчанию. Политика в пользовательском файле не объявляет схему, поэтому она получает всё, что пользователь настроил под её именем, и `{}` когда ничего не настроено. |

Рассматривайте каждое необязательное значение как действительно необязательное. Версии агентов и типы событий не предоставляют одни и те же поля.

### Типичные входные данные инструментов

Failproof AI нормализует общие инструменты между поддерживаемыми привязками, так что политика обычно может использовать одну форму ввода.

| Инструмент | Общие поля |
| --- | --- |
| `Bash` | `command` |
| `Read` | `file_path` |
| `Write` | `file_path`, `content` |
| `Edit` | `file_path`, `old_string`, `new_string` |
| `Grep` | `pattern`, `path` |

Используйте защитное приведение типов, потому что значения входных данных инструмента типизированы как `unknown`:

```ts
const command = String(ctx.toolInput?.command ?? "");
const filePath = String(ctx.toolInput?.file_path ?? "");
```

## Выберите событие

| Событие | Когда оно выполняется | Типичное использование |
| --- | --- | --- |
| `PreToolUse` | До выполнения инструмента. | Блокировать или направлять команды, записи, чтения и внешние действия. Это охрана. |
| `PostToolUse` | После выполнения инструмента. | Проверить или заменить результат, который читает модель. Это не может отменить побочный эффект — запись или команда уже произошли — и на десяти из двенадцати привязок вердикт не может ничего остановить. Только Codex и Copilot его потребляют, и даже там он заменяет результат, который читает модель, а не предотвращает вызов. Никогда не используйте его как охрану. |
| `PermissionRequest` | Когда агент запрашивает разрешение. | Применить правила разрешений, специфичные для организации. |
| `UserPromptSubmit` | Перед тем, как отправленное приглашение продолжится. | Отклонить запрещённые инструкции или добавить руководство по рабочему процессу. |
| `Stop` | Когда агент пытается завершить. | Требовать достижимое условие завершения, такое как шаг локальной проверки. |
| `SubagentStop` | Когда подагент пытается завершить. | Ворота для делегированной работы перед её возвратом к родителю. |
| `SessionStart` / `SessionEnd` | На границах сеансов. | Записывать или проверять состояние на уровне сеанса. |

Доступность событий и поведение блокировки зависят от привязки агента, и различия велики: Failproof AI не устанавливает хук `Stop` для Goose или Hermes, поэтому ворота остановки никогда не срабатывают ни на одном из них. See [Agent harnesses](/ru/reference/harnesses) перед использованием события в смешанном флоте.

<Accordion title="Все имена событий политики">
  `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `Elicitation`, `ElicitationResult`, `UserPromptExpansion`, `PostToolBatch` и `Setup`. Это полный набор из 29 канонических имён событий, в которые нормализуется собственный словарь событий каждой привязки.
</Accordion>

## Создание типичных паттернов политик

### Блокировка записей в защищённые пути

```ts
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "block-generated-file-edits",
  description: "Require generated files to be changed through their generator",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (!["Write", "Edit"].includes(ctx.toolName ?? "")) return allow();

    const filePath = String(ctx.toolInput?.file_path ?? "");
    if (!/(^|\/)(dist|generated)\//.test(filePath)) return allow();

    return deny("Edit the source and run the generator instead of changing generated output.");
  },
});
```

### Дача необязательных рекомендаций

```ts
import { customPolicies, allow, instruct } from "failproofai";

customPolicies.add({
  name: "prefer-reviewed-deploy-command",
  description: "Guide agents toward the reviewed deployment wrapper",
  match: { events: ["PreToolUse"] },
  fn: async (ctx) => {
    if (ctx.toolName !== "Bash") return allow();

    const command = String(ctx.toolInput?.command ?? "");
    if (!/^kubectl\s+apply\b/.test(command.trim())) return allow();

    return instruct("Use ./scripts/deploy-reviewed instead of invoking kubectl directly.");
  },
});
```

### Ворота для завершения сеанса

```ts
import { execFileSync } from "node:child_process";
import { customPolicies, allow, deny } from "failproofai";

customPolicies.add({
  name: "require-clean-typecheck",
  description: "Require the project typecheck to pass before the agent finishes",
  match: { events: ["Stop"] },
  fn: async (ctx) => {
    const cwd = ctx.session?.cwd;
    if (!cwd) return allow();

    try {
      execFileSync("bunx", ["tsc", "--noEmit"], {
        cwd,
        stdio: "ignore",
        timeout: 8_000,
      });
      return allow();
    } catch {
      return deny("Fix the typecheck errors before finishing the task.");
    }
  },
});
```

<Warning>
  Отклонённое событие `Stop` может заставить агента повторить попытку. Ворота только для условия, которое агент может удовлетворить в текущей среде, и ограничивайте каждый подпроцесс или сетевой вызов.
</Warning>

## Загрузка файлов политик

### Файлы соглашений

Файлы соглашений загружаются автоматически:

```text
<project>/.failproofai/policies/security-policies.ts
~/.failproofai/policies/personal-policies.mjs
```

- Загружаются как каталоги проектных, так и пользовательских политик.
- Файлы загружаются в алфавитном порядке в каждом каталоге.
- Файл должен заканчиваться на `policies.js`, `policies.mjs` или `policies.ts`.
- Несколько вызовов `customPolicies.add()` в одном файле поддерживаются.
- Поддерживаются относительные импорты из локальных модулей.
- Политики проекта можно коммитить, так чтобы одни и те же правила следовали за хранилищем.

<Warning>
  Файл в каталоге, имя которого не заканчивается на `policies.{js,mjs,ts}`, пропускается. Он выглядит установленным и ничего не применяет. Загрузчик перечисляет каждый пропущенный файл с именем, чтобы переименовать его; прочитайте это предупреждение вместо предположения, что политика работает. Это хранилище отправило `block-version-bumps.mjs` таким образом, и охрана, написанная после плохого увеличения версии, никогда не запускалась.
</Warning>

`~/.failproofai/policies/` также содержит два подкаталога, которые вы туда не положили: `cloud-policies/` для управляемых флотом развёртываний и `packs/` для установленных пакетов. Загрузчик никогда не спускается в один из них, так что ничего в них не подбирается как непроверенная политика соглашения.

### Отключение обнаруженной политики

Два ключа в `policies-config.json` отключают политики соглашения без удаления или переименования файла:

| Ключ | Эффект |
| --- | --- |
| `disabledCustomPolicies` | Массив ID политик, квалифицированных источником, которые не зарегистрированы. |
| `customPoliciesEnabled` | Установите на `false`, чтобы полностью остановить загрузку `.failproofai/policies/`. Отсутствие означает включено. |

Вкладка **Policies → Configure** на [локальной панели](/ru/reference/local-dashboard) пишет `disabledCustomPolicies` для вас. `customPoliciesEnabled` пишется `failproofai config` или вручную.

### Явные файлы

Используйте явные пути, когда валидация или конфигурация должна назвать файл записи напрямую:

```bash
failproofai policies --install \
  --custom ./security.policies.ts \
  --custom ./workflow.policies.ts \
  --scope project
```

Явные файлы загружаются первыми, за ними следуют файлы соглашений проекта, а затем файлы соглашений пользователя. Файл, обнаруженный обоими путями, загружается один раз.

## Валидация и тестирование

`-c` — это краткая форма `--custom`, а `-i` — `--install`. Оно применяет файл прямо сейчас, в любом пути и под любым имённем файла:

```bash
failproofai policies -i -c ./checkout-policies.ts
failproofai policies
```

Попросите вашего агента делать то, что вы заблокировали, и смотрите, как ему отказывают. Ничего не публикуется и ни одна другая машина не затронута.

Валидация выполняет модуль через производственный загрузчик и подтверждает, что он регистрирует по крайней мере одну политику. Она ловит отсутствующие файлы, синтаксические ошибки, неразрешённые импорты, исключения верхнего уровня и тайм-ауты загрузки модуля. Она не доказывает, что ваша логика соответствия правильная.

Протестируйте по крайней мере эти случаи:

- Одно действие, которое должно совпадать и выдать предполагаемую причину политики.
- Одно рядом, но безопасное действие, которое должно вернуть `allow()`.
- Отсутствующие или неправильно отформатированные поля инструмента.
- Альтернативный синтаксис команды, пути, кавычки, регистр и пробелы.
- Недоступная зависимость подпроцесса или сети.

Атрибутируйте результат вашей пользовательской политике в **Policies → Activity** на локальной панели. Заблокированный тест недостаточен, если другая встроенная политика приняла решение.

## Поведение во время выполнения

- Встроенные политики оцениваются перед пользовательскими политиками.
- Первый `deny` останавливает дальнейшую оценку политики.
- Несколько результатов `instruct` могут быть объединены, если ни одна политика не отклоняет событие.
- Функция политики имеет крайний срок выполнения 10 секунд. Загрузка модуля верхнего уровня имеет тот же крайний срок.
- Выброшенное исключение или тайм-аут записывается и рассматривается как `allow()`.
- Файл соглашения, который не загружается, пропускается; другие пользовательские файлы и встроенные политики продолжают работу.
- Режим наблюдения запускает политику по-настоящему и записывает любой невернущий решение без его применения. Два слоя устанавливают его: `failproofai publish --effect observe` на пакете, который вы публикуете, и `fp fleet deploy <machine> --add <id>:observe` на развёртывании Cloud. В любом случае политика оценивается под тем же крайним сроком 10 секунд, что и применяемая, поэтому политика, которая истечёт по времени, записывается как разрешение.

### Где загрузчик не открывается

Правило открытого отказа выше охватывает файл, который вы сами туда поместили. Два пути намеренно делают противоположное, потому что оба означают, что этой машине сказали, что у неё есть применение, которого у неё нет.

| Ситуация | Результат |
| --- | --- |
| Выбранный пакет не может быть загружен, или его закреплённый дайджест не совпадает | Каждое событие в области, которую объявил пакет, отклоняется, приписываемое `pack/failproofai-pack-unavailable`. `UserPromptSubmit` инструктирует вместо отклонения, так чтобы вы никогда не были заблокированы из агента, который вам нужен, чтобы исправить это. Нечитаемые метаданные пакета расширяют отклонённую область вместо сужения её. |
| Демон `failproofaid` не может быть достигнут на машине, которая завершила настройку | Каждое событие отклоняется. Никакая конфигурация не читается и никакая пользовательская политика не запускается, потому что демон, который не мог быть достигнут, не мог бы их запустить либо. Несоответствие версии протокола также отклоняется с сообщением, называющим `failproofai config`. |

На машине, которая завершила настройку, `failproofaid` — это единственный оценщик, поэтому ваш `fn` запускается внутри тёплого работника демона, а не в процессе хука. Клиент хука даёт 150 мс для подключения и 30 секунд для ответа, удобно выше фиксированного крайнего срока 10 секунд, который получает каждая функция политики.

Держите модули политик детерминированными и быстрыми. Избегайте вызовов сети верхнего уровня или запуска сервера. Ограничивайте работу внутри `fn`, ловите сбои зависимостей и сознательно выбирайте, должен ли этот сбой разрешить или запретить операцию.

## От файла к пакету

Пакет — это то, как файл политики становится чем-то, что другие машины могут установить. Две команды берут вас от нуля к опубликованному пакету:

```bash
failproofai publish --init
failproofai publish
```

`--init` спрашивает, как называется пакет, пишет `<name>.mjs` и останавливается. Файл не является шаблоном с пробелами — это одна политика, которая уже блокирует `git push --force`, поэтому первое, что вы редактируете, это то, что работает. Докажите это локально с помощью `failproofai policies -i -c ./<name>.mjs`, затем запустите `failproofai publish` из внутри хранилища git, которое его содержит.

Два поля имеют значение, когда политика отправляется в пакете:

| Поле | Что оно делает |
| --- | --- |
| `category` | Что `failproofai policies add <owner>/<repo> --category git,database` выбирает на. |
| `defaultEnabled` | Включена ли эта политика при использовании голого `failproofai policies add <owner>/<repo>`. По умолчанию `false`. |

`--effect` устанавливается для пакета в целом, а не для отдельной политики: `failproofai publish --effect observe` публикует пакет, который записывает, что его политики решили, и ничего не блокирует. По умолчанию `enforce`. Это режим наблюдения на одной машине без соединения Cloud — читайте записанные вердикты обратно в **Policies → Activity** на локальной панели.

Версия пакета — это 12-символьный короткий коммит sha, на котором он был собран, поэтому `publish` отказывает вне хранилища git и на грязном дереве. See [Publish a pack](/ru/policies/publish-a-pack) для полного потока и [Policy packs](/ru/policies/packs) для того, как установки разрешают версию.

## Экспорты API

| Экспорт | Назначение |
| --- | --- |
| `customPolicies.add(policy)` | Зарегистрируйте пользовательскую политику при загрузке модуля. |
| `allow(reason?)` | Разрешить операцию. |
| `instruct(reason)` | Разрешить операцию и предоставить рекомендацию, где поддерживается. |
| `deny(reason)` | Блокировать операцию, где поддерживается. |
| `getCustomHooks()` | Возвращает политики, в настоящее время зарегистрированные в реестре модулей. |
| `clearCustomHooks()` | Очистить этот реестр, в основном для тестов и загрузчиков. |

TypeScript экспортирует `PolicyContext`, `PolicyResult`, `CustomHook`, `PolicyDecision` и `PolicyFunction`.
