## Предварительные требования

- Kubernetes 1.27 или более поздней версии с доступом cluster-admin
- `kubectl` с поддержкой Kustomize
- Helm 3
- Доступ к приватным образам `ghcr.io/agenteye-enterprise`
- Два DNS-имени: одно для панели управления и одно для приёма данных
- Постоянное хранилище для PostgreSQL и ClickHouse
- cert-manager и Traefik или эквивалентная инфраструктура ingress и сертификатов, адаптированная в ваш overlay
- SMTP для производственного входа OTP и уведомлений

Исходное дерево предоставляет overlay, ориентированный на AWS/EKS, и отдельный overlay GCP/GKE. Не комбинируйте их инструкции по сертификатам, балансировщикам нагрузки или резервным копиям: GKE использует собственные конфигурацию DNS-01, GCS и автомасштабирование.

## Последовательность развёртывания

<Steps>
  <Step title="Подготовьте кластер">
    Установите cert-manager и контроллеры публичного ingress для панели управления, проверьте их балансировщики нагрузки, затем создайте namespace, учётные данные для pull образов, учётные данные БД, начальный ключ администратора и секреты аутентификации/SMTP.
  </Step>
  <Step title="Настройте публичные домены">
    Установите `INGEST_DOMAIN` и `DASHBOARD_DOMAIN` в сгенерированном файле окружения доменов overlay и создайте DNS-записи, указывающие на соответствующие балансировщики нагрузки.
  </Step>
  <Step title="Применяйте и проверяйте один platform overlay">
    Используйте overlay customer/EKS или GCP. Проверьте отрендеренный вывод Kustomize, примените его и подтвердите, что все рабочие нагрузки и сертификаты достигли предполагаемого состояния, прежде чем подключать машины.
  </Step>
  <Step title="Инициализируйте доступ и приём данных">
    Войдите как защищённый администратор, создайте ключ машины в области организации и отправьте небольшую тестовую сессию через публичную конечную точку приёма.
  </Step>
</Steps>

## Требуемые и дополнительные сервисы

| Компонент | Требование |
| --- | --- |
| ClickHouse | Требуется. Сервер не запустится без канонического хранилища событий. |
| PostgreSQL | Требуется для пользователей, организаций, сохранённых объектов и состояния контрольной плоскости. |
| Redis | Опционально. Сервер и панель управления переходят в поведение, поддерживаемое БД, при недоступности. |
| SMTP | Опционально для разработки, требуется для производственных email OTP и доставки уведомлений. |
| Evaluator | Опционально. Автоматическая оценка остаётся отключённой без `EVALUATOR_ENDPOINT`. |
| Assistant/audit LLM | Опционально. Функции Assistant и аудита на основе LLM остаются неактивными до настройки подключения LLM. |
| Резервная копия объектного хранилища | Настоятельно рекомендуется для архивов резервных копий PostgreSQL и ClickHouse. |

### Ёмкость аудита и доставка при отказе

Выполняйте аудиты в выделённом развёртывании audit-agent, когда оно доступно. По умолчанию каждый pod audit-agent принимает одно расследование; масштабируйте пропускную способность с помощью реплик вместо повышения параллелизма на pod без увеличения памяти. Сервер может одновременно отправлять `server replicas × AUDIT_WORKERS` аудитов, поэтому ёмкость диспетчера должна быть достаточной для заполнения флота audit-agent.

Когда каждый слот audit-agent занят, аудит ждёт и повторяет попытку до одной четверти его цикла, максимум шесть часов. Если слот не освобождается, запуск завершается без результатов и отправляет письмо об ошибке. Повторяющиеся ошибки "busy" требуют больше реплик audit-agent или более широко разнесённых якорей расписания. Повторяющиеся ошибки "shutting down" указывают на нестабильные pod или зациклившийся rollout вместо недостаточной ёмкости.

Уведомления об отказе требуют включённого email-канала и SMTP. Они используют получателей аудита, затем возвращаются к `alerts.email_default_recipients`, когда аудит не имеет email-канала.

## Аутентификация и email

Панель управления использует email и одноразовые коды. При отсутствии SMTP развёртывания для разработки логируют коды OTP в выходные данные сервера. Когда установлен `SMTP_HOST`, имя пользователя, пароль и отправитель требуются как группа или сервер не запустится.

`SMTP_TLS` — это логическое значение. Поддерживаемый зашифрованный транспорт — это STARTTLS, обычно на порту 587; неявный SMTPS на порту 465 не поддерживается текущим транспортом сервера.

Установите публичный URL панели управления правильно, потому что email OTP, оповещений, инцидентов и аудита используют его для глубоких ссылок. Членство в организации контролирует, кто может запросить код; каждая организация может дополнительно ограничить вход своих членов в **Administration → Settings**.

## Требования для мультитенанта

Перед созданием второй организации настройте сильный, стабильный секрет производной ClickHouse организации и держите его идентичным во всех репликах сервера. Ротация без координированной миграции может привести к потере пользователей ClickHouse, специфичных для организации.

Держите слушатель instance-admin внутри. Предоставленная консоль оператора опциональна и предназначена для `kubectl port-forward`, а не для публичного ingress. Включение требует собственного сильного ключа API, почтового ящика super-admin и работающей доставки SMTP второго фактора.

### Break-glass CLI организации

`agenteye-orgctl` поставляется внутри образа сервера и напрямую общается с PostgreSQL и ClickHouse. Остаётся доступным, когда публичный сервер или консоль оператора неработоспособны.

```bash
kubectl -n agenteye exec deploy/server -- \
  agenteye-orgctl org create --slug acme --name "Acme Corp"
kubectl -n agenteye exec deploy/server -- agenteye-orgctl org list
kubectl -n agenteye exec deploy/server -- \
  agenteye-orgctl member add --org acme --email ops@acme.com --set admin --protected
```

Поддерживаемые операции организации включают create, list, rename, soft-delete, restore, переподготовку пользователя ClickHouse, управление датой биллинга, флаги функций и необратимую очистку. Операции с членами включают add, list, update, remove, переопределения прав доступа и состояние защищённого администратора.

Используйте soft-delete перед purge. `org purge` необратима и требует предварительного удаления организации. Защищённые члены не могут быть удалены или понижены через обычную страницу Users организации до явного снятия защиты оператором.

## Контрольный список готовности к производству

- Ingress и dashboard DNS разрешаются на разные предполагаемые пути ingress.
- TLS действителен; используйте взаимный TLS на ingress, если это требует ваше развёртывание.
- Тома PostgreSQL и ClickHouse имеют оповещения о ёмкости.
- Резервные копии включают оба хранилища данных и имеют протестированную процедуру восстановления.
- Проверки здоровья предупреждают о молчании ingress, отказах рабочих нагрузок, истечении сертификатов, давлении хранилища и устаревших резервных копиях.
- Структурированные логи собираются без дублирования существующего конвейера логов кластера.
- Параллелизм Evaluator, audit и alert worker не изменялся без подтверждённых доказательств очереди.
- Зафиксирован выпуск приложения и записана процедура отката перед обновлениями.
