---
title: "Устранение неполадок"
description: "Диагностика отсутствующих сеансов, отсутствующих политик, сбоев доставки и заблокированных действий агента."
icon: "wrench"
---

Временные сбои сети и ответы HTTP 408, 429 или 5xx оставляют телеметрию доступной для автоматического повтора даже после длительного перерыва. Демон сохраняет пакет до подтверждения доставки. Отклонение `event_too_large` требует меньшего размера события перед повторной попыткой. Файлы, уже отмеченные как `.poison`, требуют ручного восстановления; обновление не отправит их автоматически повторно.

  <Accordion title="В облаке не отображаются сеансы">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Administration → Keys** и подтвердите, что ключ машины активен и имеет `events:add`. Затем откройте **Observe → Events**, расширьте диапазон времени и очистите фильтры окружения и агента. Если события существуют, найдите по ID сеанса и проверьте **Observe → Sessions** для группировки. Если события отсутствуют, диагностируйте демон Failproof из CLI.

        ![Поток событий в реальном времени с видимыми основными фильтрами и поступающими событиями агента.](/images/dashboard/events-stream-current.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait --timeout 60
        fp list envs
        fp events --since 24h --limit 20
        fp sessions --since 24h --limit 20
        ```

        Подтвердите, что захват включен, настроенный ключ имеет `events:add`, и фильтр панели управления соответствует отправленному окружению.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="События Python SDK остаются на диске">
    <Tabs>
      <Tab title="Панель управления">
        Очистите фильтры в **Observe → Events** и найдите точный ID сеанса SDK. Если ничего не появилось, проверьте буфер SDK и демон Failproof на исходной машине.
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait
        ```

        Подтвердите, что демон запущен и подключен — SDK буферизует данные независимо от этого. Директория буфера **не** должна существовать заранее (писатель создает ее), и никакая переменная окружения не выбирает ее: `$FAILPROOFAI_HOME/custom-agents`, иначе `~/.failproofai/custom-agents` — это единственный корень, и `configure(base_dir=...)` — единственный способ переопределения. Если процесс был завершен `SIGKILL` или убит из-за нехватки памяти, все, что оставалось в очереди, было потеряно — обрабатывайте `SIGTERM` для ограничения этого.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Машина не получает политики">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Admin → enforcement**, выберите машину и сравните назначенные, сообщенные и предыдущие версии. Подтвердите, что область развертывания включает машину и ее ключ имеет `policies:pull`. Прием может работать даже когда доставка политики не работает.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config --status
        ```

        Подтвердите, что ID и метка машины соответствуют цели на панели управления. Переподключитесь с ключом, поддерживающим политики, если существующие учетные данные предоставляют только прием событий.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Самостоятельно размещенное облако с закрытым центром сертификации не получает события или политики">
    <Tabs>
      <Tab title="Панель управления">
        Машина подключилась и ее хуки работают, но **Observe → Events** остается пустым и **Admin → enforcement** никогда не показывает развертывание как примененное. CLI и демон Failproof доверяют сертификатам по-разному. CLI работает на Node и уважает `NODE_EXTRA_CA_CERTS`. `failproofaid`, который отправляет события и вытягивает политики, доверяет сертификатам, поставляемым с ним, плюс хранилище доверия операционной системы, и игнорирует `NODE_EXTRA_CA_CERTS`. Установите свой CA в системное хранилище на машине.
      </Tab>
      <Tab title="CLI">
        ```bash
        # Debian / Ubuntu
        sudo cp company-ca.pem /usr/local/share/ca-certificates/company-ca.crt
        sudo update-ca-certificates
        # RHEL / Fedora
        sudo cp company-ca.pem /etc/pki/ca-trust/source/anchors/ && sudo update-ca-trust
        # macOS
        sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain company-ca.pem

        # затем перезагрузите демон, который загружает доверенные сертификаты при запуске
        sudo systemctl restart failproofaid@$USER                           # Linux
        sudo launchctl kickstart -k system/ai.failproof.failproofaid.$USER  # macOS
        ```

        Лог демона называет причину: `sudo journalctl -u failproofaid@$USER | grep UnknownIssuer` на Linux. `SSL_CERT_FILE` или `SSL_CERT_DIR` в окружении сервиса заменяет системное хранилище для демона, и поставляемые сертификаты все еще применяются. Пакеты, которые не прошли, пока CA не был доверен, хранятся в `~/.failproofai/state/failed` и повторяются автоматически, примерно ежечасно и при перезагрузке демона.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Действие отклонено, потому что демон недоступен">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Admin → enforcement** и проверьте время последнего обращения машины и сообщенную версию. Если машина устарела, рассматривайте это как локальную проблему демона. Не ослабляйте развернутую политику только для обхода недоступного демона.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        Перезагрузите или обновите `failproofaid`; перезагрузите конфигурацию, когда версии протокола CLI и демона различаются. Настроенный путь демона по замыслу отказывает в доступе.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Пользовательская политика не загружается">
    <Tabs>
      <Tab title="Панель управления">
        Для политики, созданной в облаке, откройте **Admin → policy editor**, выберите черновик и просмотрите ошибки валидации перед публикацией. Для локальной политики используйте CLI для валидации, затем откройте **Observe → policy** после тестового действия для подтверждения получения решений.

      </Tab>
      <Tab title="CLI">
        Подтвердите, что имя файла заканчивается на `policies.js`, `policies.mjs` или `policies.ts`, модуль вызывает `customPolicies.add(...)`, и импорты разрешаются из файла политики.

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Аудит не возвращает никаких выводов">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Analyze → audits**, выберите запуск и проверьте, был ли запущен анализ модели. Затем сравните его область и окно с **Observe → sessions** и откройте репрезентативные трассировки из этой популяции.

        Нулевой результат имеет смысл только когда анализ успешно запущен. Если анализ был пропущен или не прошел, запуск не выдает выводов и сохраняет неанализированное окно открытым для будущего успешного запуска. Если анализ модели отключен, аудит также не выдает выводов, потому что детерминированное сканирование учетных данных и PII записывает статистику, но больше не вызывает выводы.

        ![Форма аудита, где окружение, агент, кадентность и окно развертки определяют популяцию сеансов.](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        Если запуск оставался в очереди, подождите емкости аудит-агента или попросите оператора развертывания проверить флот аудита. Аудит в очереди повторяется; он не пропускается немедленно.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Онлайн-оценки не выполняются автоматически">
    <Tabs>
      <Tab title="Панель управления">
        Откройте завершенный сеанс и проверьте, успешна ли ручная оценка. Размещенное облако в настоящее время не имеет управления конечной точкой оценивателя на панели управления; оператор сервера должен его настроить.
      </Tab>
      <Tab title="CLI">
        Проверьте самого оценивателя, затем проверьте недавние состояния оценивания:

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        На самостоятельно размещенном облаке подтвердите, что `EVALUATOR_ENDPOINT` присутствует на сервере и `EVALUATOR_TOKEN` соответствует оценивателю. Автоматическое оценивание отключено при отсутствии конечной точки.
      </Tab>
    </Tabs>
  </Accordion>

  <Accordion title="Политика блокирует допустимую работу">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Observe → policy**, сохраните решение и связанный сеанс и определите условие ложного срабатывания. Затем откройте **Admin → enforcement** и откатите затронутые машины на предыдущую версию. Создайте более узкую версию в **Policy editor**, протестируйте ее на небольшой области и расширяйте только после успешного выполнения допустимой работы.

      </Tab>
      <Tab title="CLI">
        Откат развертывания облака доступен только на панели управления. Локальная пауза сеанса не отключает политики, управляемые облаком. Если панель управления недоступна, захватите состояние машины и развертывания и восстановите доступ к панели управления, а не повторяйте многократно заблокированное действие.

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Ошибка показывает реф">
    <Tabs>
      <Tab title="Панель управления">
        Ошибки на панели управления заканчиваются коротким справочником, например `ref 4bf92f35`. Он определяет этот один запрос, и служба поддержки может использовать его, чтобы найти точно то, что произошло на сервере. Скопируйте его в свой отчет так, как он выглядит.

        Если вся страница не загружается, страница ошибки вместо этого показывает `digest`. Включите его.
      </Tab>
      <Tab title="CLI">
        Понятные ошибки `fp` заканчиваются тем же `ref`. С `--json` объект ошибки содержит полный `request_id`:

        ```bash
        fp --json sessions --since 24h
        ```
      </Tab>
      <Tab title="Daemon">
        При сбое загрузки лог демона называет `request_id` и `batch_id`: на Linux, `sudo journalctl -u failproofaid@$USER | grep batch_id`. Каждая попытка получает свой `request_id`; `batch_id` остается одинаковым при повторных попытках, поэтому он связывает попытки одного пакета вместе. Включите оба.
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

При обращении в службу поддержки включите версию CLI, harness, окружение, соответствующий ID сеанса или развертывания, любой `ref` или `request_id` из ошибки и вывод `failproofai config --status` с удаленными секретами.
