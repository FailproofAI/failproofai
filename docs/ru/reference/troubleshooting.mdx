title: "Диагностика проблем"
description: "Диагностируйте отсутствующие сеансы, отсутствующие политики, ошибки доставки и заблокированные действия агента."
icon: "wrench"

<AccordionGroup>
  <Accordion title="В Cloud не отображаются сеансы">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Administration → Keys** и убедитесь, что ключ машины активен и имеет разрешение `events:add`. Затем откройте **Observe → Events**, расширьте диапазон времени и очистите фильтры окружения и агента. Если события существуют, найдите ID сеанса и проверьте **Observe → Sessions** для группировки. Если событий нет, диагностируйте демон Failproof из CLI.

        ![Живой поток событий с основными фильтрами и недавними событиями агента.](/images/dashboard/events-stream-current.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait --timeout 60
        fp list envs
        fp events --since 24h --limit 20
        fp sessions --since 24h --limit 20
        ```

        Убедитесь, что захват включен, настроенный ключ имеет разрешение `events:add` и фильтр панели управления совпадает с переданным окружением.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="События Python SDK остаются на диске">
    <Tabs>
      <Tab title="Панель управления">
        Очистите фильтры в **Observe → Events** и найдите точный ID сеанса SDK. Если ничего не появляется, проверьте очередь SDK и демон Failproof на исходной машине.
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait
        ```

        Убедитесь, что демон запущен и подключен — SDK использует очередь независимо от этого. Директория очереди **не** обязательно должна существовать заранее (ее создает писатель), и нет переменной окружения, которая бы выбирала её: `$FAILPROOFAI_HOME/custom-agents`, в противном случае `~/.failproofai/custom-agents` — единственный корень, и `configure(base_dir=...)` — единственное переопределение. Если процесс был убит через `SIGKILL` или OOM, всё, что было в очереди, потеряно — обрабатывайте `SIGTERM` для ограничения этого.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Машина не получает политики">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Admin → enforcement**, выберите машину и сравните назначенные, сообщённые и предыдущие версии. Убедитесь, что область развёртывания включает машину и её ключ имеет разрешение `policies:pull`. Приём событий может работать даже когда доставка политик не работает.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config --status
        ```

        Убедитесь, что ID и метка машины совпадают с целью на панели управления. Переподключитесь с ключом, поддерживающим политики, если существующие учётные данные предоставляют только приём событий.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Действие отклонено, потому что демон недоступен">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Admin → enforcement** и проверьте время последнего обращения и сообщённую версию машины. Если машина устарела, рассматривайте это как проблему локального демона. Не ослабляйте развёрнутую политику только для обхода недоступного демона.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        Перезагрузите или обновите `failproofaid`; переустановите конфигурацию, когда версии протокола CLI и демона отличаются. Путь демона по умолчанию отказывает по дизайну.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Пользовательская политика не загружается">
    <Tabs>
      <Tab title="Панель управления">
        Для политики, созданной в Cloud, откройте **Admin → policy editor**, выберите черновик и проверьте ошибки валидации перед публикацией. Для локальной политики используйте CLI для её валидации, затем откройте **Observe → policy** после тестового действия для подтверждения получения решений.

      </Tab>
      <Tab title="CLI">
        Убедитесь, что имя файла заканчивается на `policies.js`, `policies.mjs` или `policies.ts`, модуль вызывает `customPolicies.add(...)` и импорты разрешаются из файла политики.

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Аудит не возвращает результатов">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Analyze → audits**, выберите запуск и проверьте, работал ли анализ модели. Затем сравните его область и окно с **Observe → sessions** и откройте репрезентативные трассы из этой совокупности.

        Нулевой результат имеет смысл только когда анализ успешно выполнился. Если анализ был пропущен или не выполнен, запуск не выдаёт результаты и оставляет неанализированное окно открытым для будущего успешного запуска. Если анализ модели отключён, аудит также не выдаёт результатов, потому что детерминированное сканирование учётных данных и PII записывает статистику, но больше не выдаёт результатов.

        ![Форма аудита, где окружение, агент, кадр и окно сканирования определяют совокупность сеансов.](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        Если запуск остался в очереди, дождитесь свободного места на аудит-агенте или попросите оператора развёртывания проверить флот аудитов. Аудит в очереди повторяется; он не пропускается сразу же.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Онлайн-оценки не запускаются автоматически">
    <Tabs>
      <Tab title="Панель управления">
        Откройте завершённый сеанс и проверьте, успешна ли ручная оценка. Размещённый Cloud в настоящее время не имеет управления конечной точкой оценщика на панели управления; оператор сервера должен его настроить.
      </Tab>
      <Tab title="CLI">
        Проверьте сам оценщик, затем проверьте недавние состояния оценок:

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        На самостоятельно размещённом Cloud подтвердите, что `EVALUATOR_ENDPOINT` присутствует на сервере и `EVALUATOR_TOKEN` совпадает с оценщиком. Автоматическая оценка отключена когда конечная точка отсутствует.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Аутентификация Cloud CLI нацелена на неправильную организацию">
    <Tabs>
      <Tab title="Панель управления">
        Используйте переключатель организации и подтвердите ожидаемые значок и разрешения перед сравнением результатов с CLI.
      </Tab>
      <Tab title="CLI">
        ```bash
        fp whoami
        fp orgs current
        fp orgs perms
        ```

        В режиме API-ключа укажите `fp --org <slug> --api-key <key> ...` или установите `AGENTEYE_ORG`. Сохранённое состояние организации для сеанса человека намеренно игнорируется для запросов с API-ключом.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Политика блокирует допустимую работу">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Observe → policy**, сохраните решение и связанный сеанс, и определите условие ложного срабатывания. Затем откройте **Admin → enforcement** и откатите затронутые машины к предыдущей версии. Создайте более узкую версию в **Policy editor**, протестируйте на небольшой области и расширяйте только после успеха допустимой работы.

      </Tab>
      <Tab title="CLI">
        Откат развёртывания Cloud доступен только через панель управления. Локальная пауза сеанса не отключает управляемые Cloud политики. Если панель управления недоступна, сохраните состояние машины и развёртывания и восстановите доступ к панели управления вместо повторных попыток заблокированного действия.

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

При обращении в поддержку включите версию CLI, среду выполнения, окружение, релевантный ID сеанса или развёртывания и результат `failproofai config --status` с удалёнными секретами.
