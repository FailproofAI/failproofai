title: "Устранение неполадок"
description: "Диагностируйте отсутствующие сеансы, отсутствующие политики, ошибки доставки и заблокированные действия агентов."
icon: "wrench"

<AccordionGroup>
  <Accordion title="В Cloud не отображаются сеансы">
    <Tabs>
      <Tab title="Dashboard">
        Откройте **Administration → Keys** и подтвердите, что ключ машины активен и имеет `events:add`. Затем откройте **Observe → Events**, расширьте диапазон времени и очистите фильтры окружения и агента. Если события существуют, найдите ID сеанса, а затем проверьте **Observe → Sessions** для группировки. Если событий нет, диагностируйте демон Failproof из CLI.

        ![Поток живых событий с основными фильтрами и недавно прибывающими событиями агентов.](/images/dashboard/events-stream-current.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait --timeout 60
        fp list envs
        fp events --since 24h --limit 20
        fp sessions --since 24h --limit 20
        ```

        Подтвердите, что захват включен, что настроенный ключ имеет `events:add` и что фильтр dashboard соответствует переданному окружению.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="События Python SDK остаются на диске">
    <Tabs>
      <Tab title="Dashboard">
        Очистите фильтры в **Observe → Events** и найдите точный ID сеанса SDK. Если ничего не появится, проверьте очередь SDK и демон Failproof на исходной машине.
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait
        ```

        Подтвердите, что процесс агента устанавливает `AGENTEYE_SPOOL_TO_FAILPROOFAI=1` и что `$FAILPROOFAI_HOME/custom-agents`, или иначе `~/.failproofai/custom-agents`, существует до запуска SDK.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Машина не получает политики">
    <Tabs>
      <Tab title="Dashboard">
        Откройте **Admin → enforcement**, выберите машину и сравните её назначенные, полученные и предыдущие версии. Подтвердите, что область развертывания включает машину и что её ключ имеет `policies:pull`. Приём может работать, даже если доставка политики не работает.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config --status
        ```

        Подтвердите, что ID машины и метка соответствуют цели dashboard. Переподключитесь с ключом, поддерживающим политики, если существующие учётные данные предоставляют только приём событий.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Действие запрещено, так как демон недоступен">
    <Tabs>
      <Tab title="Dashboard">
        Откройте **Admin → enforcement** и проверьте время последнего появления машины в сети и её полученную версию. Если машина устаревшая, рассматривайте это как локальную проблему демона. Не ослабляйте развёрнутую политику только для того, чтобы обойти недоступный демон.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        Перезагрузите или обновите `failproofaid`; повторно запустите конфигурацию, если версии протокола CLI и демона отличаются. Путь к настроенному демону по умолчанию сбрасывает состояние.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Пользовательская политика не загружается">
    <Tabs>
      <Tab title="Dashboard">
        Для политики, созданной в Cloud, откройте **Admin → policy editor**, выберите черновик и проверьте ошибки валидации перед публикацией. Для локальной политики используйте CLI для её валидации, затем откройте **Observe → policy** после тестового действия, чтобы подтвердить, что решения поступают.

      </Tab>
      <Tab title="CLI">
        Подтвердите, что имя файла заканчивается на `policies.js`, `policies.mjs` или `policies.ts`, что модуль вызывает `customPolicies.add(...)` и что импорты разрешаются из файла политики.

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Аудит не возвращает результаты">
    <Tabs>
      <Tab title="Dashboard">
        Откройте **Analyze → audits**, выберите запуск и проверьте, был ли запущен анализ модели. Затем сравните его область и окно со значениями **Observe → sessions** и откройте репрезентативные трассировки из этой совокупности.

        Нулевой результат имеет смысл только тогда, когда анализ был успешно выполнен. Если анализ был пропущен или не удался, запуск не производит результатов и оставляет неанализированное окно открытым для будущего успешного запуска. Если анализ модели отключен, аудит также не производит результатов, так как детерминированный скан учётных данных и PII записывает статистику, но больше не вызывает результаты.

        ![Форма аудита, где окружение, агент, кадетность и окно развёртывания определяют совокупность сеансов.](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        Если запуск остался в очереди, дождитесь ёмкости audit-agent или попросите оператора развертывания проверить флот аудита. Аудит в очереди повторяется; он не пропускается немедленно.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Онлайн-оценки не запускаются автоматически">
    <Tabs>
      <Tab title="Dashboard">
        Откройте завершённый сеанс и проверьте, успешна ли ручная оценка. Размещённый Cloud в настоящее время не имеет управления конечной точкой оценки в dashboard; оператор сервера должен настроить его.
      </Tab>
      <Tab title="CLI">
        Проверьте саму оценку, а затем проверьте последние состояния оценки:

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        На self-hosted Cloud убедитесь, что `EVALUATOR_ENDPOINT` присутствует на сервере и `EVALUATOR_TOKEN` совпадает с оценкой. Автоматическая оценка отключена, если конечная точка отсутствует.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Аутентификация Cloud CLI нацелена на неправильную организацию">
    <Tabs>
      <Tab title="Dashboard">
        Используйте переключатель организации и подтвердите ожидаемый slug и разрешения перед сравнением результатов с CLI.
      </Tab>
      <Tab title="CLI">
        ```bash
        fp whoami
        fp orgs current
        fp orgs perms
        ```

        В режиме API-ключа укажите `fp --org <slug> --api-key <key> ...` или установите `AGENTEYE_ORG`. Сохранённое состояние организации человеческого сеанса намеренно игнорируется для запросов API-ключа.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Политика блокирует допустимую работу">
    <Tabs>
      <Tab title="Dashboard">
        Откройте **Observe → policy**, сохраните решение и связанный сеанс и определите условие ложного срабатывания. Затем откройте **Admin → enforcement** и отмените развёртывание затронутых машин на предыдущую версию. Создайте более узкую версию в **Policy editor**, протестируйте её на небольшой области и расширяйте только после успешного выполнения допустимой работы.

      </Tab>
      <Tab title="CLI">
        Откат развертывания Cloud доступен только через dashboard. Локальное приостановление сеанса не отключает управляемые Cloud политики. Если dashboard недоступна, захватите состояние машины и развертывания и восстановите доступ к dashboard вместо повторных попыток заблокированного действия.

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

При обращении в поддержку укажите версию CLI, сборку, окружение, соответствующий ID сеанса или развертывания и выходные данные `failproofai config --status` с удалёнными секретами.
