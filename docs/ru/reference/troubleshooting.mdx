<AccordionGroup>
  <Accordion title="В облаке не появляются сеансы">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Administration → Keys** и убедитесь, что ключ машины активен и имеет разрешение `events:add`. Затем откройте **Observe → Events**, расширьте диапазон времени и очистите фильтры окружения и агента. Если события существуют, выполните поиск по ID сеанса и проверьте **Observe → Sessions** для группировки. Если событий нет, диагностируйте демон Failproof из CLI.

        ![Поток живых событий с видимыми основными фильтрами и поступающими недавними событиями агента.](/images/dashboard/events-stream-current.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait --timeout 60
        fp list envs
        fp events --since 24h --limit 20
        fp sessions --since 24h --limit 20
        ```

        Убедитесь, что захват включен, настроенный ключ имеет разрешение `events:add`, и фильтр панели управления соответствует переданному окружению.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="События Python SDK остаются на диске">
    <Tabs>
      <Tab title="Панель управления">
        Очистите фильтры в **Observe → Events** и выполните поиск по точному ID сеанса SDK. Если ничего не появляется, проверьте буфер SDK и демон Failproof на исходной машине.
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait
        ```

        Убедитесь, что процесс агента устанавливает `AGENTEYE_SPOOL_TO_FAILPROOFAI=1` и что `$FAILPROOFAI_HOME/custom-agents`, в противном случае `~/.failproofai/custom-agents`, существует перед запуском SDK.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Машина не получает политики">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Admin → enforcement**, выберите машину и сравните назначенные, полученные и предыдущие версии. Подтвердите, что область развертывания включает машину и что ее ключ имеет разрешение `policies:pull`. Прием может работать даже когда доставка политик не работает.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config --status
        ```

        Убедитесь, что ID машины и метка соответствуют целевой машине на панели управления. Переподключитесь с ключом, способным обрабатывать политики, если существующее учетное данные предоставляет только прием событий.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Действие запрещено, потому что демон недоступен">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Admin → enforcement** и проверьте время последнего обращения машины и полученную версию. Если машина устарела, рассмотрите это как локальную проблему демона. Не ослабляйте развернутую политику только для обхода недоступного демона.

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        Перезагрузите или обновите `failproofaid`; перезапустите конфигурацию, когда версии протокола CLI и демона различаются. Настроенный путь демона по умолчанию отказывает в доступе.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Пользовательская политика не загружается">
    <Tabs>
      <Tab title="Панель управления">
        Для политики, созданной в облаке, откройте **Admin → policy editor**, выберите черновик и изучите ошибки валидации перед публикацией. Для локальной политики используйте CLI для ее валидации, затем откройте **Observe → policy** после тестового действия, чтобы подтвердить поступление решений.

      </Tab>
      <Tab title="CLI">
        Убедитесь, что имя файла заканчивается на `policies.js`, `policies.mjs` или `policies.ts`, модуль вызывает `customPolicies.add(...)`, и импорты разрешены из файла политики.

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Аудит не возвращает результатов">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Analyze → audits**, выберите запуск и проверьте, был ли запущен анализ модели. Затем сравните его область и окно с **Observe → sessions** и откройте репрезентативные трассы из этой популяции.

        Нулевой результат имеет смысл только когда анализ прошел успешно. Если анализ был пропущен или не прошел, запуск не выдает результаты и оставляет неанализированное окно открытым для будущего успешного запуска. Если анализ модели отключен, аудит также не выдает результаты, потому что детерминированное сканирование учетных данных и PII записывает статистику, но больше не выдает результаты.

        ![Форма аудита, где окружение, агент, кадентность и окно развертки определяют популяцию сеансов.](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        Если запуск остался в очереди, дождитесь емкости audit-agent или попросите оператора развертывания проверить флот аудитов. Аудит в очереди повторяется; он не пропускается немедленно.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Онлайн-оценки не выполняются автоматически">
    <Tabs>
      <Tab title="Панель управления">
        Откройте завершенный сеанс и проверьте, завершается ли ручная оценка успешно. На размещенном облаке Cloud в настоящее время нет управления конечной точкой оценки на панели управления; оператор сервера должен ее настроить.
      </Tab>
      <Tab title="CLI">
        Проверьте саму оценку, затем проверьте недавние состояния оценки:

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        На самостоятельно размещенном облаке Cloud убедитесь, что `EVALUATOR_ENDPOINT` присутствует на сервере и `EVALUATOR_TOKEN` совпадает с оценкой. Автоматическая оценка отключена, когда конечная точка отсутствует.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Аутентификация Cloud CLI нацелена на неправильную организацию">
    <Tabs>
      <Tab title="Панель управления">
        Используйте переключатель организации и подтвердите ожидаемый слаг и разрешения перед сравнением результатов с CLI.
      </Tab>
      <Tab title="CLI">
        ```bash
        fp whoami
        fp orgs current
        fp orgs perms
        ```

        В режиме API-ключа укажите `fp --org <slug> --api-key <key> ...` или установите `AGENTEYE_ORG`. Сохраненное состояние организации человеческой сессии намеренно игнорируется для запросов API-ключа.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Политика блокирует допустимую работу">
    <Tabs>
      <Tab title="Панель управления">
        Откройте **Observe → policy**, сохраните решение и связанный сеанс, и определите условие ложного срабатывания. Затем откройте **Admin → enforcement** и откатите затронутые машины до предыдущей версии. Создайте более узкую версию в **Policy editor**, протестируйте ее на небольшой области и расширьте только после того, как допустимая работа завершится успешно.

      </Tab>
      <Tab title="CLI">
        Откат развертывания облака доступен только с панели управления. Локальная пауза сеанса не отключает управляемые облаком политики. Если панель управления недоступна, захватите состояние машины и развертывания и восстановите доступ к панели управления вместо того, чтобы повторно повторять заблокированное действие.

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

При обращении в службу поддержки укажите версию CLI, привязку, окружение, соответствующий ID сеанса или развертывания и выходные данные `failproofai config --status` с удаленными секретами.
