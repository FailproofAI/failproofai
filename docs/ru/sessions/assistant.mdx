Облачный помощник Failproof AI отвечает на вопросы о вашем флоте на естественном языке. Он может анализировать сеансы и сбои, выполнять запросы, строить панели управления, исследовать оценки и оповещения, а также помогать создавать и запускать аудиты без необходимости переводить задачу в экраны продукта или команды CLI. На панели управления элемент управления помечен как **Open agent chat**; в [`fp` CLI](/ru/reference/cloud-cli) это группа команд `fp agent`.

```text
Why did production checkout agents regress this week?
Build a dashboard for tool failures, latency, and evaluation scores.
Create an audit that finds agents retrying the same failed action without changing approach.
Show me the sessions behind the most common audit finding.
```

Помощник работает с данными и разрешениями, доступными в активной организации. Проверьте его доказательства и предложенные изменения перед применением действий, которые влияют на других пользователей или агентов.

<Note>
  Помощник работает на панели управления, и его чаты принадлежат конкретному человеку, поэтому за ним не стоит API-маршрут, который может вызвать ключ. Каждая подкоманда `fp agent` требует активной сессии (`fp login`) и разрешения `agent:use`, и выходит с кодом 2 при использовании `--api-key` или `FP_API_KEY`. API-ключ никогда не сможет обратиться к нему, поэтому запланированное задание должно носить токен сессии в `--token` или `FP_TOKEN`. Это работает — `fp agent ask` читает вопрос из stdin, если нет TTY — но токен сессии истекает примерно через 24 часа после `fp login`, что делает помощника плохо подходящим для автоматизации без участия человека, несмотря на то что он работает.
</Note>

## Обратитесь к помощнику

<Tabs>
  <Tab title="Панель управления">
    1. Выберите **Open agent chat** и опишите, что вы хотите понять, создать или автоматизировать.
    2. Проверьте вызовы инструментов помощника, таблицы и результаты запросов во время работы.
    3. Откройте указанный сеанс, оповещение или запрос, чтобы проверить результат на основе исходных данных.
    4. Начните новый чат для другого исследования или используйте историю чатов для продолжения того же анализа.

    ![Облачный помощник отвечает на вопрос наблюдаемости со вспомогательным анализом и запросами.](/images/dashboard/assistant.png)
  </Tab>
  <Tab title="CLI">
    Начните с `health`. Он показывает, включен ли помощник для этого развертывания и настроена ли для него LLM. Если LLM нет, `ask` завершится с ошибкой, а `models` не вернет результатов — `chats`, `show`, `rename` и `delete` вообще не проверяют состояние и работают нормально.

    ```bash
    fp agent health
    fp agent models
    fp agent ask "Which production checkout agents had the most tool errors in the last 24 hours?"
    ```

    `fp agent models` выводит модели, которые допускает это развертывание, и указывает модель по умолчанию. Передайте одну в `ask --model <name>`. Привяжите ответ к тексту, который у вас уже есть, используя `--page-context <text>`, и передайте вопрос через stdin вместо аргумента, если он поступает из файла или предыдущей команды:

    ```bash
    cat incident-notes.md | fp agent ask --model <model>
    ```

    Каждый запрос сохраняется в чат. Без `--chat` создается новый чат, и выводится его короткий идентификатор; с `--chat` продолжается этот тред.

    ```bash
    fp agent chats
    fp agent show <chat-id>
    fp agent ask "Open representative sessions" --chat <chat-id>
    fp agent rename <chat-id> --title "checkout regression"
    fp agent delete <chat-id> --yes
    ```

    `fp agent chats` выводит ваши чаты с самыми новыми первыми в формате `chat-id · title · messages · updated`, где `updated` — время последней активности чата. Показанный `chat-id` — это короткий идентификатор (первые 8 символов), и `show`, `rename`, `delete` и `ask --chat` все разрешают этот префикс. Идентификатор, который ничему не соответствует, завершается с кодом 6 и выводит блок `chat not found`; идентификатор, который соответствует нескольким чатам, запрашивает более длинный префикс.

    `fp agent delete` запрашивает подтверждение. `--yes` пропускает приглашение, и то же самое происходит при любом неинтерактивном вызове: под `--json` или при перенаправлении stdin процесс продолжается без запроса.
  </Tab>
</Tabs>

## Работайте эффективно с помощником

- Дайте ему цель в первую очередь; добавьте окружение, рабочий процесс или диапазон времени, когда эти границы имеют значение.
- Рассматривайте сгенерированный SQL и сводки как вспомогательное средство исследования, а не окончательное доказательство.
- Откройте репрезентативные сеансы перед созданием аудита, проблемы, оповещения или политики.
- Сохраняйте фильтры организации, окружения и времени в явном виде.
- Сохраняйте полезный SQL как запрос, чтобы другой оператор смог воспроизвести результат.

<Warning>
  Применяются два уровня разрешений, и они отказывают по-разному. `agent:use` управляет самой функцией: без него `fp agent` и чат на панели управления недоступны. Ответы затем ограничиваются разрешениями на доступ к данным вошедшего пользователя — `events:read`, `evaluations:read`, `queries:run`, `policies:read` — поэтому пользователь, который может открыть помощника, может все равно получить пустой ответ для данных, которые он не может читать. Не расширяйте разрешения, чтобы заставить вопрос работать; вместо этого попросите авторизованного оператора провести исследование. См. [Keys and permissions](/ru/admin/keys-and-permissions).
</Warning>
