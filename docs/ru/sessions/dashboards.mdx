Панели управления объединяют сохраненные запросы в одно операционное представление. Создавайте панель вокруг решения, которое кто-то должен принять, а не вокруг каждой доступной метрики.

Панели управления — это облачная функция. Локальная панель на `localhost:8020` охватывает активность политик, проекты, сессии и результаты аудита, но не имеет сохраненных запросов и плиток — поэтому машина, которая не подключалась, здесь нечего строить. См. [Локальная панель](/ru/reference/local-dashboard).

## Создание панели управления

<Tabs>
  <Tab title="Панель управления">
    1. Перейдите к **Analyze → Queries**, создайте или откройте сохраненный запрос и проверьте его результат.
    2. Выберите **add to dashboard**, затем выберите существующую панель или создайте новую в **Analyze → Dashboards**.
    3. Откройте панель, перейдите в режим редактирования, разместите плитки и сохраните макет.
    4. Вернитесь к запросу, когда вам нужно изменить данные или фильтры за плиткой.

    ![Панель управления, состоящая из сохраненных запросов для объема событий, ошибок, задержки и использования токенов модели.](/images/dashboard/dashboard-fleet.png)
  </Tab>
  <Tab title="CLI">
    Операции CRUD для панели управления не предоставлены текущим облачным CLI. Используйте CLI для написания и проверки сохраненного запроса, затем добавьте его на панель в пользовательском интерфейсе.

    ```bash
    fp query schema
    fp query run --sql "select count(*) from analytics.events"
    fp query create "event volume" --sql "select count(*) from analytics.events"
    fp query run "event volume"
    ```

    Сначала запустите SQL с `--sql`: он выполняется в том же пуле аналитики только для чтения без сохранения, поэтому вы найдете неправильное имя столбца до того, как это сделает плитка. `--sql @file.sql` читает оператор из файла. `fp query schema` выводит список таблиц и столбцов, которые можно запрашивать; передайте имя таблицы, чтобы сузить список до одной.

    Сохраненные запросы адресуются по **имени**, а не по идентификатору — `fp query run "event volume"` — потому что `fp query list` скрывает необработанный идентификатор, если не передать `--show-id`. Также принимается идентификатор в виде UUID.

    Для параметризованной плитки привяжите каждый позиционный `$1..$N` с `--arg`, который повторяется и привязывает по порядку: `fp query run <name> --arg checkout-agent`.

    `--limit` и `--all` настраивают только предельное значение предпросмотра таблицы; `--json` всегда возвращает каждую строку как `{columns: [{name, type}], rows: [[...]], truncated, elapsed_ms}`.

    | Подкоманда | Разрешение |
    | --- | --- |
    | `query list`, `query show`, `query schema` | `queries:read` |
    | `query create`, `query update` | `queries:write` |
    | `query run` | `queries:run` |
    | `query delete` | `queries:delete` |

    Каждая подкоманда, которая принимает **имя** запроса, разрешает его, сначала выводя список запросов организации, поэтому `query create`, `query update`, `query delete` и `query run <name>` требуют `queries:read` в дополнение к указанному выше разрешению. Только `fp query run --sql` и `fp query schema` — нет.

    Ничто из `fp query` не блокируется в режиме API-ключа, поэтому запросы панели могут быть созданы и проверены из CI.
  </Tab>
</Tabs>

Полезные группы панелей включают:

- **Модели:** объем, задержка, использование токенов, коэффициент ошибок и баллы оценки.
- **Оценки:** коэффициент успеха и тренды баллов по агентам или окружениям.
- **Инструменты:** объем вызовов, коэффициент отказов, длительность и повторные вызовы.
- **Хуки и политики:** решения, отказы и коэффициент совпадения политик.
- **Пользовательские метрики рабочего процесса:** результаты из ваших собственных полей событий и SQL.

Начните с сохраненного запроса, проверьте его результат, затем добавьте его как плитку. Держите фильтры для боевого режима и разработки явными, чтобы тестовый трафик не скрывал регрессию.

<Warning>
  Плитка хука, которая считает строки, сообщает неправильный знаменатель. При стандартной многословности хука каждый отказ и инструкция испускаются как пара `hook_triggered` / `hook_completed`, как и каждое разрешение в режиме наблюдения; простые разрешения объединяются по сессии, событию, инструменту и атрибуции политики в минуту в одну `hook_completed`, несущую `failproofai_allow_count`. Вместо этого суммируйте это поле, или флот, который оценил десятки тысяч вызовов, будет выглядеть так, как будто он оценил несколько сотен. См. [Решения политик](/ru/sessions/policy-decisions) и [Хуки](/ru/sessions/hooks).
</Warning>

<Tip>
  Назначьте каждой панели владельца и вопрос ответа, например: «Хуже ли надежность checkout-agent, чем на прошлой неделе?»
</Tip>
