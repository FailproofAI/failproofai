Errors предоставляет представление, ориентированное на сбои, во всех сессиях. Фильтруйте по среде, типу события, типу ошибки, агенту или сессии, и установите временной диапазон, чтобы найти повторяющиеся операционные проблемы.

## Исследование ошибок

<Tabs>
  <Tab title="Dashboard">
    1. Перейдите на **Observe → Errors**.
    2. Фильтруйте по среде, типу события, типу ошибки, агенту, ID сессии или тексту поиска.
    3. Выберите строку, чтобы открыть конкретное событие в его сессии.
    4. Выберите **alert** на представительной строке, чтобы создать оповещение для похожих ошибок.

    ![Страница Errors с гистограммой сбоев, отфильтрованным списком событий с ошибками и элементом управления оповещением для каждой строки.](/images/dashboard/errors.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp errors --since 24h
    fp errors --error-type TimeoutError --agent-id checkout-agent
    fp errors --event-type tool_result --since 24h
    fp errors --aggregate --env local --since 7d
    ```

    Сбой инструмента поступает как событие `tool_result` с ошибкой, а не как голое событие `error`, поэтому `--event-type tool_result` — это способ отделить сбои инструментов от сбоев модели и среды выполнения. `is_error` и `error_type` — это вычисляемые на сервере столбцы для каждой строки, поэтому ни один режим не анализирует полезные нагрузки.

    Откройте для себя допустимые значения фильтров вместо того, чтобы их угадывать: `fp list error_types`, `fp list agents`, `fp list envs` и `fp list event_types`.

    **Эти пять фильтров `fp errors` принимают ровно одно значение каждый** — `--env`, `--error-type`, `--event-type`, `--agent-id`, `--session-id`. (`--search` является исключением и может быть повторяемым.) Те же имена флагов на `fp events` и `fp sessions` принимают повторные или разделённые запятыми значения, поэтому `--env prod,staging` работает там, а здесь сопоставляется только с буквальной строкой `prod,staging`. Это возвращает пустой результат, а не ошибку, что читается как «нет ошибок».

    Демон помечает события как `local` до тех пор, пока вы это не измените, поэтому `--env production` не соответствует ничему при стандартной установке. См. [Change an environment label](/ru/reference/events-and-configuration#change-an-environment-label).

    `--all` автоматически разбивает на страницы только до `--limit`, который по умолчанию равен 50 — напишите `--all --limit 500`, если вам нужно больше. Другие флаги режима списка: `--order asc|desc`, `--cursor`, `--page-size` (макс. 200), `--fields` и `--full-ids`. `--search` повторяемый и применяется к обоим режимам — строка совпадает, если она содержит любой из терминов.

    `fp errors` требует `events:read`. В режиме `--json` режим списка возвращает `{"errors": [...], "next_cursor": ...}` и `--aggregate` возвращает `{total, sessions, agents, last_ts, bins}`. Используйте `fp events --full --session-id <id>`, когда вам нужна сырая полезная нагрузка за сводкой ошибок.
  </Tab>
</Tabs>

## Используйте Errors когда вам нужно

- Найти самый частый класс ошибок в production.
- Определить, вызывает ли один инструмент или модель скачок.
- Перейти от общего количества к представительным сессиям.
- Создать оповещение для повторения.
- Включить затронутую группу в аудит.

Ошибка — это наблюдаемое событие. Неудача оценки — это суждение о качестве, а вывод аудита — это исследованный паттерн сбоя. Сохраняйте эти различия при выборе рабочего процесса ответа.

## Без учётной записи Cloud

Errors — это поверхность Cloud. На машине, которая не подключилась, `failproofai audit` сканирует историю сессий, уже находящуюся на диске, на предмет рискованных и неэффективных паттернов и открывает `http://localhost:8020/audit`. Добавьте `--schedule [days]` для повторного сканирования по таймеру и отправки результатов по электронной почте (по умолчанию 7 дней, диапазон от 1 до 90), `--status` для проверки включено ли расписание и `--no-schedule` для его отключения. Всё выполняется на машине, за двумя исключениями. Запланированное сканирование отправляет ID этой машины, метку, платформу и охватываемое окно при каждом запуске, включая чистое — что чистое сканирование скрывает, так это краткую сводку, а не сам запрос. И анонимная телеметрия CLI отправляется при каждом аудите, если вы не установите `FAILPROOFAI_TELEMETRY_DISABLED=1`.
