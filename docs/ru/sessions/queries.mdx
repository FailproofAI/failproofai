Запросы — это гибкий уровень под панелями управления, аудитами и расследованиями. Используйте ad-hoc SQL для проверки идеи, а затем сохраните запрос, когда он станет частью повторяющегося рабочего процесса.

## Создание и выполнение запроса

<Tabs>
  <Tab title="Панель управления">
    1. Перейдите в **Analyze → Queries** и выберите **new query**.
    2. Откройте обозреватель схемы и выберите поля из данных событий, сеансов или оценок.
    3. Напишите SQL, добавьте параметры при необходимости и выполните запрос.
    4. Сохраните его с понятным названием и описанием, затем используйте **add to dashboard** если результат нужно мониторить.

    Редактор запросов объединяет схему событий, SQL, параметры и предпросмотр результатов, чтобы вы могли проверить вопрос перед сохранением.

    ![Редактор SQL-запросов с обозревателем схемы и живой сеткой результатов.](/images/dashboard/query-lab.png)

    Сохраненные запросы появляются в общей библиотеке, где коллеги могут их перезапустить или добавить результаты на панели управления.

    ![Библиотека сохраненных запросов с переиспользуемыми встроенными и пользовательскими запросами.](/images/dashboard/queries.png)

    Используйте понятное название и описание, чтобы результат оставался понятным без необходимости повторно открывать SQL.
  </Tab>
  <Tab title="CLI">
    Работайте в том порядке, в котором это делает сам SQL: посмотрите схему, выполните выражение ad-hoc, затем сохраните его, когда оно получит имя.

    ```bash
    fp query schema
    fp query schema events

    fp query run --sql "SELECT agent_id, count() FROM analytics.events GROUP BY agent_id"
    fp query run --sql @retry-loops.sql

    fp query create "retry loops" --sql @retry-loops.sql --description "repeated tool calls per session"
    ```

    После этого все команды используют **имя** запроса, а не id:

    ```bash
    fp query list
    fp query run "retry loops"
    fp query show "retry loops"
    fp query update "retry loops" --sql @retry-loops-v2.sql --yes
    fp query delete "retry loops" --yes
    ```

    Имена уникальны в рамках организации, что делает их безопасным идентификатором. UUID-подобный id принимается везде, где ожидается имя, но `fp query list` не выводит его — его столбцы это `name`, `description`, `created by` и `created` (когда был создан запрос, а не когда он был последний раз отредактирован). Добавьте `--show-id` для столбца с коротким id, или используйте `--json`, который всегда содержит полный id.

    Привяжите позиционные параметры сохраненного запроса с помощью `--arg` (alias `--param`), повторяя один раз для каждого `$1..$N` по порядку:

    ```bash
    fp query run <query-name> --arg agent-codegen --arg 0.5
    ```

    | Подкоманда | Разрешение | Примечания |
    | --- | --- | --- |
    | `fp query schema [TABLE]` | `queries:read` | Передайте имя таблицы для фильтрации по её столбцам. |
    | `fp query list` | `queries:read` | `--show-id` показывает ids; `--fields` проецирует необработанные поля. |
    | `fp query show <name>` | `queries:read` | Карточка метаданных плюс полный SQL. |
    | `fp query create <name> --sql ...` | `queries:write` | Коллизия имён отклоняется заранее. |
    | `fp query update <name>` | `queries:write` | Передайте хотя бы один из `--name`, `--sql`, `--description`. Подтверждает сначала; no-op выходит без сохранения. |
    | `fp query delete <name>` | `queries:delete` | Подтверждает сначала с предпросмотром того, что будет удалено. |
    | `fp query run <name>` или `--sql ...` | `queries:run` | Ровно один из двух. `--limit` и `--all` регулируют предпросмотр таблицы. |

    `update` и `delete` запрашивают подтверждение только на интерактивном терминале. Под `--json` или с перенаправленным stdin они выполняются без вопросов — поэтому `--yes` для терминала, а не для скриптов.

    Запросы выполняются с использованием пула аналитики только для чтения. `--sql @file.sql` читает выражение из файла, что является формой, достойной системы контроля версий.

</Tabs>

## Скрипт для запроса

`fp --json query run` возвращает каждую строку независимо от лимита предпросмотра таблицы, в формате `{columns: [{name, type}], rows: [[...]], truncated, elapsed_ms}`:

```bash
fp --json query run "retry loops" | jq '.rows | length'
```

`fp --json query schema` возвращает `{schema, columns: [{table, column, type, nullable}]}`, что является машиночитаемой формой обозревателя схемы.

Два типа ошибок стоит обрабатывать по коду выхода, а не парсингом текста: имя, которому ничего не соответствует, выводит `✗ no query named "…"` и выходит с кодом 6, а ошибка SQL или выполнения выводит `✗ query failed — …` с деталями от сервера.

## Частые использования

- Найти сеансы с повторяющимися вызовами одного и того же инструмента.
- Сравнить оценки оценки между моделями или окружениями.
- Измерить время между ожиданием пользователя и возобновлением.
- Определить отказы политики, за которыми следует успешная альтернатива.
- Построить когорту для аудита.

Откройте схему — **Analyze → Queries** на панели управления или `fp query schema` — перед написанием запросов к незнакомым полям. Предпочитайте явные фильтры по времени и окружению, и используйте ограничение результатов при исследовании.

<Warning>
  Запрос может выявить подозрительный паттерн, но сам по себе он не устанавливает режим отказа. Откройте репрезентативные трассы или запустите аудит перед тем, как превратить результат в политику.
</Warning>
