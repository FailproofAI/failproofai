Трассировка — это временная шкала одного запуска агента. Начните с первого неожиданного события, а не с итоговой ошибки.

<Tabs>
  <Tab title="Dashboard">
    1. Откройте **Observe → Sessions**.
    2. Выберите сессию.
    3. Найдите первую ошибку, необычный вызов инструмента, долгое ожидание или решение политики.
    4. Откройте событие и проверьте запрос, ответ, входные и выходные данные.

    ![Представление деталей сессии с графиком выполнения, временной шкалой событий, панелью оценки и разбивкой по инструментам, модели и хукам.](/images/dashboard/session-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp --json sessions --session-id <session-id>
    fp events --session-id <session-id> --order asc --all --limit 5000
    fp --json events --full --session-id <session-id> --all --limit 2000
    ```

    Используйте `--full` только когда краткого описания события недостаточно. Ненулевое значение `next_cursor` означает, что лимит достигнут до конца.
  </Tab>
</Tabs>

## Следуйте доказательствам

1. Подтвердите агента, цель, окружение и результат.
2. Найдите первую ошибку или неожиданное решение.
3. Проверьте событие, которое произошло непосредственно перед ней.
4. Проследите совпадающие идентификаторы в парах запрос-ответ.
5. Превратите доказательства в аудит, проблему или политику.

| Пара | Совпадающее поле |
| --- | --- |
| Запрос и ответ модели | `request_id` |
| Вызов инструмента и результат | `tool_call_id` |
| Начало и завершение хука | `hook_id` |
| Пауза и возобновление агента | `pause_id` |
| Ожидание человеком и ввод | `input_id` |

Решение появляется в `hook_completed`. Строка указывает результат и источник политики. Решение в режиме observe отображается как разрешение с предполагаемым вердиктом в `failproofai_observed`.

<Warning>
  Длительность сессии не всегда означает задержку модели. Разделите время модели, инструмента, хука и ожидания человека перед тем, как решить, что исправить.
</Warning>
