Аудит преобразует набор сеансов в ранжированные выводы об отказах с подтверждающими доказательствами. Начните с одного узкого вопроса об отказе.

Существует два типа аудита. Они читают разные данные и работают с разными инструментами:

| Аудит | Читает | Требует аккаунта | Выводы отображаются в |
| --- | --- | --- | --- |
| Локальный — `failproofai audit` | История агента, уже находящаяся на этой машине | Нет | `http://localhost:8020/audit` |
| Облачный — **Analyze → Audits**, или CLI `fp` | Сеансы, хранящиеся в Failproof AI Cloud | Да | Панель управления облака |

Сначала запустите локальный. Для него нужна только CLI. Выводы остаются локальными, при этом анонимная телеметрия CLI отправляется по умолчанию, если только вы не установите `FAILPROOFAI_TELEMETRY_DISABLED=1`.

<Tabs>
  <Tab title="Локальный">
    ```bash
    failproofai audit
    ```

    Он сканирует все поддерживаемые истории агентов, найденные на этой машине, воспроизводит активность инструментов через встроенный каталог политик и открывает **http://localhost:8020/audit**. Держите процесс запущенным, пока читаете результаты; нажмите <kbd>Ctrl</kbd>+<kbd>C</kbd>, когда закончите.

    Анализ и выводы остаются на этой машине. Анонимная телеметрия CLI отправляется по умолчанию, если не отключена. После того как вы согласитесь на планирование, каждое сканирование также отправляет метаданные машины и может отправлять ограниченный сводный отчет о выводах.

    | Флаг | Что он делает |
    | --- | --- |
    | `--schedule [days]` | Сканирование по расписанию и отправка выводов по электронной почте. По умолчанию 7 дней, диапазон 1–90. Первый вход выполняется автоматически. |
    | `--email <address>` | С `--schedule`, указывает адрес для отправки отчета вместо запроса. |
    | `--no-schedule` | Остановить таймер. Оставляет вас авторизованным. |
    | `--status` | Включено ли планирование, адрес отправки отчетов, состояние демона и время следующего сканирования. |

    ```bash
    failproofai audit --schedule 7 --email reliability@example.com
    failproofai audit --status
    ```

    Смотрите [Аудит локальной истории агента](/ru/audits/local-audit), чтобы узнать, какие истории читает каждый адаптер и как работает запланированное сканирование.
  </Tab>
  <Tab title="Панель управления облака">
    <Steps>
      <Step title="Откройте Audits">
        В боковой панели облака перейдите к **Analyze → Audits**. Выберите **new audit**.
      </Step>
      <Step title="Настройте аудит">
        Введите имя и прямую цель отказа, например «найти рабочие сеансы, которые повторяют один и тот же неудачный вызов платежа без изменения входных данных или эскалации». Выберите агента, окружение, временное окно и расписание. Добавьте краткое описание и справочные URL-адреса, когда аудитору нужны ваши правила рабочего процесса.
      </Step>
      <Step title="Создайте и дождитесь выполнения">
        Выберите **create audit**. Первый запуск ставится в очередь немедленно. Откройте карточку аудита, чтобы следить за переходом от постановки в очередь к выполнению и завершению.
      </Step>
    </Steps>

    После завершения аудита откройте вывод и просмотрите доказательства его сеанса. Затем вы можете подтвердить, назначить, отклонить, скрыть или разрешить его.

    ![Завершенный вывод аудита с его описанием отказа, рекомендуемым действием, подтверждающими доказательствами и затронутыми сеансами.](/images/dashboard/audit-finding.png)
  </Tab>
  <Tab title="Облачный CLI">
    `fp` — это CLI Failproof AI Cloud. Он считывает то, что хранится в облаке; это отдельная программа от `failproofai`, который работает на этой машине.

    ```bash
    fp audits create payment-retry-failures \
      --description "Find production sessions that retry a failed payment call without changing input or escalating" \
      --scope '{"environments":["production"]}' \
      --text "Escalate after two unchanged payment failures"

    fp audits list
    fp audits runs payment-retry-failures
    fp audits findings --audit payment-retry-failures
    fp audits finding <finding-id>
    ```

    Добавьте справочный контекст, затем обновите его при изменении источника:

    ```bash
    fp audits context-set payment-retry-failures --url https://example.com/payment-runbook
    fp audits context-refresh payment-retry-failures
    fp audits run payment-retry-failures
    ```

    Используйте `fp audits ack <finding-id>`, `fp audits assign <finding-id> --to <email>`, `fp audits dismiss <finding-id>`, `fp audits mute <finding-id>`, `fp audits resolve <finding-id>` или `fp audits reopen <finding-id>`, чтобы переместить вывод на этап классификации.
  </Tab>
</Tabs>
