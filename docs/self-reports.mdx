Self Reports gives every agent one extra tool, `report`. An agent that is blocked and cannot make progress on its own calls it with a category and one factual sentence. Failproof AI records the call as a `self_report` event on the agent's session, and the tool answers `Recorded.`.

A report never unblocks the agent and never changes a decision. Afterwards the agent works around the problem or tells the user what is blocking it. No policy can block or rewrite a report: failproofai's hook allows the call before any policy, session pause, or Jev review runs.

## Turn it on

<Tabs>
  <Tab title="Failproof AI Cloud">
    On a machine connected to Failproof AI Cloud, the setting comes from your organization.

    1. Go to **settings → self reports**.
    2. Switch it on. Keep the default categories or write your own, and optionally add guidance for the agents.

    Every connected machine picks the change up on its next policy poll. `failproofaid` writes `~/.failproofai/self-report.json` and adds the `failproofai` MCP server to every agent that has failproofai hooks, or removes it when you switch the feature off.

    On a Cloud-managed machine, `failproofai self-report enable` and `disable` refuse and point you to the dashboard.
  </Tab>
  <Tab title="Local (open source)">
    ```bash
    failproofai self-report enable
    failproofai self-report status
    failproofai self-report test --agent claude
    ```

    `enable` writes the `selfReport` block of `~/.failproofai/config.json` and `~/.failproofai/self-report.json`, then registers the MCP server in every agent with failproofai hooks. To replace the default categories, pass `--categories-file <file>`, a JSON list of `{name, description}`. To append instructions to the tool's description, pass `--guidance "<text>"`. `failproofai self-report disable` turns it off and removes the MCP entries, keeping your categories for next time.

    `test` sends one report end to end as the agent you name and shows where it landed.
  </Tab>
</Tabs>

## Categories

An organization's own list replaces these entirely. Names are lowercase letters, digits, and underscores; a list holds 1 to 32 categories.

| Category | Description shown to the agent |
| --- | --- |
| `looping` | You keep repeating the same or circular steps without making progress. |
| `cannot_do_request` | The user asked for something you cannot do here: a missing capability, tool or permission, or it is only possible by cheating. |
| `invalid_tool_or_credential` | A tool, MCP server, plugin, API key or token you need is broken, invalid, expired or rejected. |
| `missing_context` | Information or access you need is missing and you cannot get it yourself. Not for normal clarifying questions. |
| `repeated_tool_failure` | A command or tool failed on several distinct attempts and is blocking you. A single error is not enough. |
| `task_failure` | You genuinely tried and could not complete the task. Not for refusals or policy blocks. |

A report with a category that is not on the list is still recorded under the name the agent gave. The detail is cut to 2,000 characters. An agent that calls the tool without loading its schema sometimes guesses the argument names, so when `detail` is missing or empty the first non-empty of `summary`, `sentence`, `message`, `description`, `reason`, `text` and `details` is recorded instead, and when `category` is, `type` or `kind`. Other unknown arguments are ignored; a call is never rejected.

## Agent support

failproofai registers one MCP server, named `failproofai`, in each agent's user-level MCP settings. When `failproofaid` is answering on the machine, the entry points at the daemon's local server, `http://127.0.0.1:4319/mcp` (set `FAILPROOFAI_SELF_REPORT_PORT` to move it). Otherwise it runs `failproofai mcp` over stdio. Every entry is marked as failproofai's, so removing it never touches a server you added.

The transport is chosen when the entries are written, from a live check: the daemon must answer on its socket and its MCP endpoint must answer. When the daemon starts, it re-runs `failproofai self-report sync`, so agents move to HTTP. If the daemon stops, `failproofai self-report status` finds agents pointing at an endpoint that does not answer and moves them back to stdio. A running agent keeps the server it loaded at startup.

Both transports send the model short server instructions in the MCP handshake: when to report, the category names, and your guidance. Some agents, Claude Code among them, load MCP tools only on demand. They add a server's instructions to the system prompt, though, so the model knows the tool exists.

Where an agent's hooks see MCP tool calls, the hook records the report. Where they do not, failproofai's MCP server records it and attributes it to that agent's newest session in the same working directory.

| Agent | Where the server is registered | Recorded by |
| --- | --- | --- |
| Claude Code | `~/.claude.json` | Hook |
| Codex | `~/.codex/config.toml` | Hook |
| Cursor | `~/.cursor/mcp.json` | Hook, through Cursor's MCP hook (`beforeMCPExecution`). failproofai does not install that hook yet, so reports from Cursor are not recorded yet |
| Copilot CLI | `~/.copilot/mcp-config.json` | MCP server |
| OpenCode | `~/.config/opencode/opencode.json` | MCP server |
| Pi | `~/.pi/agent/mcp.json` | MCP server |
| Hermes | Each profile's `config.yaml` | MCP server |
| OpenClaw | Each profile's `openclaw.json` | MCP server |
| Factory | `~/.factory/mcp.json` | MCP server |
| Devin | `~/.config/devin/mcp_config.json` | MCP server |
| Antigravity | `~/.gemini/config/mcp_config.json` | MCP server |
| Goose | `~/.config/goose/config.yaml` | MCP server |

`failproofai self-report status` shows whether the daemon's endpoint answers (`not running (agents use stdio)` when no daemon is set up here) and, per agent, whether the server is registered, over which transport, and whether that endpoint answers (HTTP) or the command can run (stdio). If an MCP server named `failproofai` that failproofai did not write is already there, such as the [Cloud MCP gateway](/reference/mcp) added under that name, it is left alone and reported as a conflict.

## Containers

In a container, run `failproofaid` in the foreground as the container's main process, with the agent started beside it. Reports, like every other hook event, reach Failproof AI Cloud only through the daemon: without it, the agent still gets the tool over stdio, but reports stay on disk in the container.

## Your own agents

The Python and TypeScript SDKs offer the same tool, named `failproofai_report`, as ready-made tools for LangChain, LangGraph, CrewAI, LlamaIndex, Pydantic AI, the Vercel AI SDK and Mastra, and as raw OpenAI and Anthropic tool definitions. See [Python custom agents](/start/integrations/custom-agents#self-reports) and [TypeScript custom agents](/reference/custom-agents-typescript#self-reports). SDK reports carry `source: "sdk"`; reports from coding agents carry `source: "mcp"`.

## Privacy

The tool's description tells the agent there is no need to mention the report to the user. Terminal agents still show the tool call on screen; in your own UI, hide it with `is_self_report_tool(name)` (Python) or `isSelfReportTool(name)` (TypeScript).

A report holds the category, the agent's one-sentence detail, and the session, agent, and environment it came from. It is uploaded with the session's other events.
