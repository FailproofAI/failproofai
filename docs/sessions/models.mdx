Use Models to see whether reliability or cost changed with a model, agent, environment, or time range.

<Tabs>
  <Tab title="Dashboard">
    1. Go to **Observe → Models**.
    2. Set the time range, then filter by environment, model, agent, or session ID.
    3. Review latency, token consumption, context-window use, and model distribution.
    4. Select a chart point or distribution segment to open the matching events.

    ![The Models page showing latency, percentile, token, cost, context-window, and model-distribution views.](/images/dashboard/models.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp list models
    fp events --event-type model_request,model_response --since 24h
    fp --json events --event-type model_response --since 24h --all --limit 500 --fields ts,agent_id,session_id,output_tokens,context_window,context_fill
    ```

    All three need `events:read`.

    `--fields` projects columns; it does not filter rows. Pair it with `--event-type` and a time window, or you get the newest 50 events of every type with `output_tokens` and `context_fill` null on all the non-model ones. `--all` stops at `--limit`, which defaults to 50.

    Read `context_fill` next to `context_window`: a fill figure means nothing without the window it is measured against.

    The daemon stamps every event with environment `local` unless you change it, so `--env production` matches nothing on a stock install. See [Change an environment label](/reference/events-and-configuration#change-an-environment-label).
  </Tab>
</Tabs>

## What the CLI can and cannot show

The default event feed is payload-free. It carries `output_tokens`, `context_window`, and `context_fill` as promoted columns, and nothing else about a model call:

| Value | Where it lives |
| --- | --- |
| Output tokens, context window, context fill | Light feed columns — available from `fp events` directly. |
| Model name | Payload — use `fp events --full`, bounded to one session. |
| Input tokens | Payload — the SDK records both halves, only the output half is promoted. |
| Per-call latency | No `duration_ms` column on the light feed, and the SDK's `model_response` carries none either. Derive it by pairing the request with its response. |

`model_request` and `model_response` pair on `request_id`. That field exists precisely so a request can be matched to its answer, and it is the only way to compute per-call latency from raw events:

```bash
fp --json events --full --event-type model_request,model_response --session-id <session-id> --all --limit 500
```

Model names arrive verbatim from each harness's transcript. Nothing in the capture path normalizes them, so one underlying model can appear under several provider-specific ids in the distribution chart. Run `fp list models` to see the spellings a deployment actually has.

Use a saved query for model-level aggregates that are not exposed as a dedicated CLI command.
