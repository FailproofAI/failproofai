Failproof AI records what agents do and decides what they may do.

## Observe

| Term | Meaning |
| --- | --- |
| Session | One agent run |
| Event | One action inside a session |
| Trace | The ordered view of a session |
| Evaluation | A score or judgment |
| Audit | A review of many sessions |
| Finding | Evidence of a failure pattern |
| Issue | The response someone owns |
| Alert | A rule that detects recurrence |

## Enforce

| Term | Meaning |
| --- | --- |
| Harness | The environment where an agent runs |
| Hook | A point where the harness asks for a decision |
| Policy | A rule that allows, guides, or blocks |
| Policy pack | A versioned policy set anyone can install |
| Daemon | The local service that evaluates policies |
| Deployment | Policies assigned to a machine |

## The workflow

```text
Session → Audit → Finding → Issue → Policy
```

Start with evidence. Find the repeated failure, assign the response, then prevent it.

A policy returns `allow`, `instruct`, or `deny`. Guidance through `instruct` depends on the harness; use `deny` when the action must stop.

Observe mode is separate from the decision. It runs the real policy and records what it would do while allowing the agent to continue.

<Warning>
  A bare `fp fleet deploy <machine> --add <policy>` enforces immediately. Add `:observe` for a shadow rollout.
</Warning>

Setup chooses no policy pack. Before you add one, only `block-failproofai-commands` runs. The compiled catalog contains 39 policies across 9 categories.

See [supported harnesses](/reference/harnesses#enforcement-capability) before assuming an event can block on every agent environment.
