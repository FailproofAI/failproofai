An audit turns a set of sessions into ranked, evidence-backed failure findings. Start with one narrow failure question.

There are two audits. They read different data and answer to different tools:

| Audit | Reads | Needs an account | Findings appear in |
| --- | --- | --- | --- |
| Local — `failproofai audit` | The agent history already on this machine | No | `http://localhost:8020/audit` |
| Cloud — **Analyze → Audits**, or the `fp` CLI | The sessions stored in Failproof AI Cloud | Yes | The Cloud dashboard |

Run the local one first. It needs nothing but the CLI, and nothing leaves the box.

<Tabs>
  <Tab title="Local">
    ```bash
    failproofai audit
    ```

    It scans every supported agent history it finds on this machine, replays the tool activity through the builtin policy catalog, then opens **http://localhost:8020/audit**. Keep the process running while you read the results; press <kbd>Ctrl</kbd>+<kbd>C</kbd> when you are done.

    Everything runs on this machine. Only a scheduled digest ever leaves it.

    | Flag | What it does |
    | --- | --- |
    | `--schedule [days]` | Scan on a timer and email the findings. Default 7 days, range 1–90. Signs you in the first time. |
    | `--email <address>` | With `--schedule`, supplies the report address instead of prompting. |
    | `--no-schedule` | Stop the timer. Leaves you signed in. |
    | `--status` | Whether scheduling is on, where reports go, the daemon's state, and when the next scan is due. |

    ```bash
    failproofai audit --schedule 7 --email reliability@example.com
    failproofai audit --status
    ```

    See [Audit local agent history](/audits/local-audit) for which histories each adapter reads and how the scheduled scan runs.
  </Tab>
  <Tab title="Cloud dashboard">
    <Steps>
      <Step title="Open Audits">
        In the Cloud sidebar, go to **Analyze → Audits**. Select **new audit**.
      </Step>
      <Step title="Set up the audit">
        Enter a name and a direct failure goal, such as “find production sessions that retry the same failed payment call without changing input or escalating.” Select the agent, environment, time window, and schedule. Add a short brief and reference URLs when the auditor needs your workflow rules.
      </Step>
      <Step title="Create and wait for the run">
        Select **create audit**. The first run is queued immediately. Open the audit card to watch it move from queued to running to complete.
      </Step>
    </Steps>

    After the run completes, open a finding and review its session evidence. You can then acknowledge, assign, dismiss, mute, or resolve it.

    ![A completed audit finding showing its failure description, recommended action, supporting evidence, and affected sessions.](/images/dashboard/audit-finding.png)
  </Tab>
  <Tab title="Cloud CLI">
    `fp` is the Failproof AI Cloud CLI. It reads back what Cloud stored; it is a different program from `failproofai`, which enforces on this machine.

    ```bash
    fp audits create payment-retry-failures \
      --description "Find production sessions that retry a failed payment call without changing input or escalating" \
      --scope '{"environments":["production"]}' \
      --text "Escalate after two unchanged payment failures"

    fp audits list
    fp audits runs payment-retry-failures
    fp audits findings --audit payment-retry-failures
    fp audits finding <finding-id>
    ```

    Add reference context, then refresh it when the source changes:

    ```bash
    fp audits context-set payment-retry-failures --url https://example.com/payment-runbook
    fp audits context-refresh payment-retry-failures
    fp audits run payment-retry-failures
    ```

    Use `fp audits ack <finding-id>`, `fp audits assign <finding-id> --to <email>`, `fp audits dismiss <finding-id>`, `fp audits mute <finding-id>`, `fp audits resolve <finding-id>`, or `fp audits reopen <finding-id>` to move a finding through triage.
  </Tab>
</Tabs>
