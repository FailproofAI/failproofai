A policy runs *inside* the agent loop. Every tool call passes through it first, and it
returns one of three decisions:

| Decision | Effect |
|---|---|
| **allow** | The call proceeds. |
| **deny** | The call never runs. The agent is told why, in words it can act on. |
| **instruct** | The call runs, and the agent gets extra context to stay on track. |

---

## Check catalog

Check the built-in catalog before writing a policy. It includes secret detection,
destructive-command blocking, branch protection, infrastructure guards, and workflow gates.

```bash
failproofai policies              # what is enabled here
```

If a built-in policy matches, enable and configure it. See
[Built-in policies](/built-in-policies).

---

## Write policy

<Steps>

<Step title="Draft rule">
  Open **fix → Policy editor** and write the JavaScript source. **Publish version** remains
  disabled until the source parses.

  ```js
  import { customPolicies, allow, deny } from "failproofai";

  customPolicies.add({
    name: "no-production-writes",
    description: "Block writes to paths containing 'production'",
    match: { events: ["PreToolUse"] },
    fn: async (ctx) => {
      if (ctx.toolName !== "Write" && ctx.toolName !== "Edit") return allow();
      const path = ctx.toolInput?.file_path ?? "";
      if (path.includes("production")) {
        return deny("Writes to production paths are blocked — open a PR instead");
      }
      return allow();
    },
  });
  ```

  The editor can draft a policy from a description. Review the diff before selecting
  **use this**.
</Step>

<Step title="Write guidance">
  State what was blocked and what the agent should do next. Actionable reasons reduce
  repeated attempts.
</Step>

<Step title="Publish version">
  Publishing creates an immutable version. Publishing the same policy ID creates its next
  version.
</Step>

</Steps>
