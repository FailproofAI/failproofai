Bu belge failproofai'ın dahili olarak nasıl çalıştığını açıklar: hook sisteminin agent araç çağrılarını nasıl ele aldığını, konfigürasyonun nasıl yüklenip birleştirildiğini, politikaların nasıl değerlendirildiğini ve panonun agent aktivitesini nasıl izlediğini.

---

## Genel Bakış

failproofai'ın iki bağımsız alt sistemi vardır:

1. **Hook işleyici** - Claude Code'un her agent araç çağrısında çağırdığı hızlı bir CLI alt süreci. Politikaları değerlendirir ve bir karar döndürür.
2. **Agent Monitor (Pano)** - Agent oturumlarını izlemek ve politikaları yönetmek için bir Next.js web uygulaması.

Her iki alt sistem `~/.failproofai/` ve projenin `.failproofai/` dizininde konfigürasyon dosyalarını paylaşır, ancak ayrı süreçler olarak çalışır ve yalnızca dosya sistemi aracılığıyla iletişim kurar.

## Hook işleyici

### Claude Code ile entegrasyon

`failproofai policies --install` çalıştırdığınızda, `~/.claude/settings.json` içine şu gibi girişler yazar:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "failproofai --hook PreToolUse"
          }
        ]
      }
    ],
    "PostToolUse": [ ... ]
  }
}
```

Claude Code daha sonra her araç çağrısından önce stdin üzerinden bir JSON yükü geçerek `failproofai --hook PreToolUse` komutunu bir alt süreç olarak çağırır.

### Yük formatı

```json
{
  "session_id": "abc123",
  "transcript_path": "/home/user/.claude/projects/myproject/sessions/abc123.jsonl",
  "cwd": "/home/user/myproject",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "sudo apt install nodejs" }
}
```

`PostToolUse` olayları için, yük ayrıca aracın çıktısını içeren `tool_result` öğesini de içerir.

İşleyici 1 MB stdin sınırını zorlar. Bu limiti aşan yükler atılır ve tüm politikalar örtülü olarak izin verir.

### Yanıt formatı

**Reddet (PreToolUse):**
```json
{
  "hookSpecificOutput": {
    "permissionDecision": "deny",
    "permissionDecisionReason": "Blocked by failproofai: sudo command blocked"
  }
}
```

**Reddet (PostToolUse):**
```json
{
  "hookSpecificOutput": {
    "additionalContext": "Blocked by failproofai because: API key detected in output"
  }
}
```

**Talimat (Stop hariç herhangi bir olay):**
```json
{
  "hookSpecificOutput": {
    "additionalContext": "Instruction from failproofai: Verify tests pass before committing."
  }
}
```

**Stop olayı talimatı:**
- Çıkış kodu: `2`
- Sebep stderr'e yazılır (stdout'a değil)

**İzin ver:**
- Çıkış kodu: `0`
- Boş stdout

**İleti ile izin ver:**

`allow(message)` politikaya, işlem izin verildiğinde bile Claude'a geri bilgi bağlamı gönderme imkanı verir. Hook işleyici şu JSON'ı **stdout** (konfigürasyon dosyasına değil — bu, tıpkı deny ve talimat yanıtları gibi, işleyicinin Claude Code'a verdiği yanıttır) yazır:

```json
// Hook işleyici süreci tarafından stdout'a yazılır
{
  "hookSpecificOutput": {
    "additionalContext": "All CI checks passed on branch 'feat/my-feature'."
  }
}
```
- Çıkış kodu: `0` (işleme izin verilir)
- Birden fazla politika ileti ile `allow` döndürdüğünde, mesajları satır sonlarıyla birleştirilip tek bir `additionalContext` dizesine dönüştürülür
- Politika ileti sağlamadığında, stdout boştur (öncekiyle aynı)

### İşleme hattı

`src/hooks/handler.ts` tam hattı uygular:

```text
stdin JSON
  → parse payload (max 1 MB)
  → extract session metadata (session_id, cwd, tool_name, tool_input, etc.)
  → readMergedHooksConfig(cwd)    ← merges project + local + global config
  → register enabled builtin policies with resolved params
  → load custom policies from customPoliciesPath (if set)
  → register custom policies into policy registry
  → evaluate all policies (builtins first, then custom)
      → first deny short-circuits
      → instruct decisions accumulate
      → allow messages accumulate
  → write JSON decision to stdout
  → persist event to ~/.failproofai/hook-activity/current.jsonl
  → exit
```

Tüm süreç, LLM çağrıları olmayan tipik yükler için 100ms altında çalışır.

## Konfigürasyon yükleme

`src/hooks/hooks-config.ts` üç kapsamlı konfigürasyon yüklemesi uygular.

```text
[1] {cwd}/.failproofai/policies-config.json        ← project  (highest priority)
[2] {cwd}/.failproofai/policies-config.local.json  ← local
[3] ~/.failproofai/policies-config.json             ← global   (lowest priority)
```

Birleştirme mantığı:
- `enabledPolicies` - üç dosya arasında başlıkça birleşim
- `policyParams` - politika başına anahtar, onu tanımlayan ilk dosya tamamen kazanır
- `customPoliciesPath` - onu tanımlayan ilk dosya kazanır
- `llm` - onu tanımlayan ilk dosya kazanır

Web panosu, proje cwd olmadan çağrılmadığı için okuma ve yazma için `readHooksConfig()` (yalnızca global) kullanır.

## Politika değerlendirmesi

`src/hooks/policy-evaluator.ts` politikaları sırada çalıştırır.

Her politika için:

1. Politikanın `params` şemasını arayın (varsa).
2. Birleştirilmiş konfigürasyondan `policyParams[policy.name]` okuyun.
3. Kullanıcı tarafından sağlanan değerleri şema varsayılanları üzerine birleştirerek `ctx.params` oluşturun.
4. Çözülmüş bağlam ile `policy.fn(ctx)` çağırın.
5. Sonuç `deny` ise, hemen durdurun ve bu kararı döndürün.
6. Sonuç `instruct` ise, mesajı biriktirin ve devam edin.
7. Sonuç `allow` ise, sonraki politikaya geçin.

Tüm politikalar çalıştıktan sonra:
- Herhangi bir `deny` döndürülüyse, deny yanıtı yayınlayın.
- Herhangi bir `instruct` dönüşü toplandıysa, tüm mesajları birleştirilmiş olarak tek bir talimat yanıtı yayınlayın.
- Aksi takdirde, izin yanıtı yayınlayın (boş stdout, çıkış 0).

## Yerleşik politikalar

`src/hooks/builtin-policies.ts` tüm 39 yerleşik politikayı `BuiltinPolicyDefinition` nesneler olarak tanımlar:

```typescript
interface BuiltinPolicyDefinition {
  name: string;
  description: string;
  fn: (ctx: PolicyContext) => PolicyResult;
  match: {
    events: HookEventType[];
    tools?: string[];
  };
  defaultEnabled: boolean;
  category: string;
  beta?: boolean;
  params?: PolicyParamsSchema;
}
```

`params` kabul eden politikalar, her parametre için türler ve varsayılanlarla bir `PolicyParamsSchema` bildirir. Politika değerlendirici, `fn` çağrılmadan önce çözülmüş değerleri `ctx.params` içine enjekte eder. Politika işlevleri varsayılanlar her zaman ilk olarak uygulandığı için `ctx.params` içinden null-koruma yapmadan okurlar.

Politikalar içindeki desen eşleştirmesi ham dize eşleştirmesi değil, ayrıştırılmış komut jetonlarını (argv) kullanır. Bu, shell operatörü enjeksiyonu aracılığıyla bypass'ı önler (örn. `sudo systemctl status *` için bir desen, komuta `; rm -rf /` eklenerek bypass edilemez).

## Özel politikalar

`src/hooks/custom-hooks-registry.ts` `globalThis` destekli bir kayıt defteri uygular:

```typescript
const REGISTRY_KEY = "__failproofai_custom_hooks__";

export const customPolicies = {
  add(hook: CustomHook): void { ... }
};

export function getCustomHooks(): CustomHook[] { ... }
export function clearCustomHooks(): void { ... }  // used in tests
```

`src/hooks/custom-hooks-loader.ts` kullanıcı politika dosyasını yükler:

1. Konfigürasyondan `customPoliciesPath` okuyun; yoksa atla.
2. Mutlak yola çözün; dosya varlığını kontrol edin.
3. `customPolicies` aynı `globalThis` kaydına çözümlenmesi için tüm `from "failproofai"` ithalatlarını gerçek dist yoluna yeniden yazın.
4. ESM uyumluluğu sağlamak için geçişli yerel ithalatları özyinelemeli olarak yeniden yazın.
5. Geçici `.mjs` dosyaları yazın ve giriş dosyasını `import()` edin.
6. Kayıtlı kancaları almak için `getCustomHooks()` çağırın.
7. Tüm geçici dosyaları `finally` bloğunda temizleyin.

Herhangi bir hata (dosya bulunamadı, sözdizimi hatası, ithalat hatası) durumunda, hata `~/.failproofai/hook.log` dosyasına kaydedilir ve yükleyici boş bir dizi döndürür. Yerleşik politikalar etkilenmez.

Özel politikalar tüm yerleşik politikalardan sonra değerlendirilir. Özel bir politika `deny` hala diğer özel politikaları kısa devreler (ancak o noktada tüm yerleşik olanlar zaten çalışmıştır).

## Aktivite kaydı

Her hook olayından sonra, işleyici `~/.failproofai/hook-activity/current.jsonl` dosyasına bir JSONL satırı ekler, bir sayfaya ulaştığında `page-<timestamp>-<seq>.jsonl` dosyasına döner:

```json
{
  "timestamp": "2026-04-06T12:34:56.789Z",
  "sessionId": "abc123",
  "eventType": "PreToolUse",
  "toolName": "Bash",
  "policyName": "block-sudo",
  "decision": "deny",
  "reason": "sudo command blocked by failproofai",
  "durationMs": 12
}
```

İzin vermeyen karar veren her politika için bir satır. İzin verme kararları kaydedilmez (dosyayı küçük tutmak için).

## Pano mimarisi

Pano, React Server Components ve Server Actions ile App Router kullanan bir **Next.js 16** uygulamasıdır.

```text
app/
  layout.tsx                  ← Root layout (theme, telemetry, nav)
  projects/page.tsx           ← Server component: list all Claude projects
  project/[name]/page.tsx     ← Server component: list sessions in a project
  project/[name]/session/
    [sessionId]/page.tsx      ← Server component: render session viewer
  policies/page.tsx           ← Client component: policy management + activity log
  actions/
    get-hooks-config.ts       ← Read config + policy list
    update-hooks-config.ts    ← Toggle policy on/off
    update-policy-params.ts   ← Update policy parameters
    get-hook-activity.ts      ← Paginate/search activity log
    install-hooks-web.ts      ← Install/remove hooks from the browser
  api/
    download/[project]/[session]/route.ts   ← Per-CLI session export (JSONL or JSON)
```

**Veri akışı:**

- Sayfa bileşenleri, proje/oturum verilerini doğrudan dosya sisteminden okumak için `lib/projects.ts` ve `lib/log-entries.ts` çağırır (okumalar için API katmanı yok).
- Politikalar sayfası tüm mutasyonlar (geçişme, parametreler güncellemesi, kurulum/kaldırma) için Server Actions kullanır.
- Oturum görüntüleyici Claude'un JSONL transkript biçimini ayrıştırır ve iletiler ile araç çağrılarının zaman çizelgesini oluşturur.

**Temel tasarım kararları:**

- Veritabanı yok - tüm kalıcı durum düz dosyalardadır (`~/.failproofai/`, `~/.claude/projects/`).
- Mutasyonlar için Server Actions - CRUD işlemleri için REST API gerekmez.
- Okuma sayfaları için React Server Components - daha hızlı ilk yükleme, veri alımı için istemci paketi yok.
- İstemci bileşenleri yalnızca etkileşim gerekli olduğunda (politika geçişmeleri, aktivite arama, günlük görüntüleyici).
