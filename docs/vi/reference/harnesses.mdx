A harness là bất cứ thứ gì mà agent của bạn thực sự chạy bên trong. Failproof AI hỗ trợ mười hai harness, được chia thành hai loại:

- **Coding CLIs** (10) — Claude Code, Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi, Factory Droid, Devin CLI, Antigravity CLI, Goose
- **Chat and assistant gateways** (2) — Hermes (Slack, Telegram, cron), OpenClaw (self-hosted assistant)

Các chính sách và lịch sử phiên làm việc giống nhau áp dụng cho bất kỳ harness nào mà agent chạy trong đó. Một lớp adapter ánh xạ các tên sự kiện gốc, tên công cụ và trường đầu vào công cụ của mỗi harness thành 29 sự kiện chính tắc trước khi bất kỳ chính sách nào chạy.

Một agent chạy trong **none** của mười hai harness được cấp dụng cụ trực tiếp bằng [Python SDK](/vi/reference/custom-agents). Đây là một hợp đồng khác, và cần phải nói rõ ràng: SDK cung cấp tracing, sessions, evaluations và audits — **nó không thực thi chính sách riêng lẻ.** Chặn một hành động không an toàn trước khi nó thực thi cần một hook thực thi tại ranh giới công cụ của runtime của bạn; [liên hệ với chúng tôi](mailto:support@befailproof.ai) và chúng tôi sẽ ánh xạ nó.

| Harness | Supported hook scopes |
| --- | --- |
| Claude Code | User, project, local |
| Codex, GitHub Copilot CLI, Cursor, OpenCode, Pi | User, project |
| Factory Droid, Devin CLI, Antigravity CLI, Goose | User, project |
| Hermes, OpenClaw | User |

Mỗi tích hợp chuẩn hóa các tên sự kiện hook gốc, tên công cụ và trường đầu vào công cụ trước khi chính sách chạy. Một chính sách chỉ có thể hoạt động trên các sự kiện mà harness công khai; kiểm tra hành vi cuối lượt và hướng dẫn trên harness và phiên bản chính xác mà bạn triển khai.

## Enforcement capability

"Block" có nghĩa là phán quyết được trả về của adapter hiện tại được tiêu thụ bởi harness được đặt tên. Post-tool blocking có thể thay thế kết quả được hiển thị cho mô hình nhưng không thể hoàn tác tác dụng phụ công cụ đã xảy ra.

| Harness | Verified blocking events | Observe-only or non-blocking caveats |
| --- | --- | --- |
| Claude Code | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact`, và nhiều task/config events | `PostToolUse`, session lifecycle, notifications, và post-failure events là quan sát. |
| Codex | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PostToolUse` | Post-tool blocking thay thế kết quả sau khi thực thi; session-start và compact events là quan sát trong adapter hiện tại. |
| GitHub Copilot CLI | `PreToolUse`, `UserPromptSubmit`, `PermissionRequest`, `Stop`, `SubagentStop`, `PostToolUse` | Post-tool blocking thay thế kết quả sau khi thực thi; session và notification events là quan sát. |
| Cursor | `PreToolUse`, `UserPromptSubmit`, `Stop` | `PostToolUse` và session events là quan sát. |
| OpenCode | `PreToolUse` | Post-tool và lifecycle events là quan sát; xử lý stop hiện tại là hướng dẫn cho một lượt sau hơn là một cổng được xác minh. |
| Pi | `PreToolUse`, `UserPromptSubmit` | Post-tool và lifecycle events là quan sát; hướng dẫn stop áp dụng cho một lượt sau. |
| Hermes | `PreToolUse` | `deny()` chặn. `instruct()` không dừng lệnh gọi: nó chạy, và hướng dẫn được đặt ở đầu kết quả của nó. Post-tool, session, và subagent-stop verdicts không phải là cổng. |
| OpenClaw | `PreToolUse`, `UserPromptSubmit`, `Stop` | Post-tool, session, subagent-stop, và compaction events là quan sát. |
| Factory Droid | `PreToolUse`, `UserPromptSubmit`, `Stop`, `PreCompact` | Post-tool và subagent-stop verdicts là quan sát. |
| Devin CLI | `PreToolUse`, `UserPromptSubmit`, `Stop`, conditional `PermissionRequest` | Permission hooks không chạy ở mọi permission mode; post-tool và session events là quan sát. |
| Antigravity CLI | `PreToolUse`, `Stop` | User-prompt và post-tool verdicts là quan sát; prompt instructions vẫn có thể được inject. |
| Goose | `PreToolUse` | User-prompt, post-tool, và session events là quan sát. Một native blocking stop hook tồn tại ở thượng nguồn nhưng không được cài đặt bởi adapter hiện tại. |

Các khả năng phụ thuộc vào phiên bản. Kiểm tra lại sau khi nâng cấp agent CLI, đặc biệt khi một chính sách dựa vào hành vi prompt, stop, permission, hoặc post-tool hơn là pre-tool gate phổ biến.

### Hermes native plugin

Hermes được tích hợp thông qua một native plugin cục bộ profile hơn là một lệnh shell. Installation liên kết mỗi default và named Hermes profile's `plugins/failproofai` đến plugin được gửi trong npm package (một bản sao khi không thể tạo symlink), kích hoạt nó trong `config.yaml` của profile đó, và chỉ di chuyển các entry shell-hook FailproofAI cũ. Vì plugin được liên kết, `npm install -g failproofai@latest` cập nhật nó mà không cần cài đặt lại. Điều này tránh một process spawn trên mỗi hook. Plugin hỗ trợ Hermes 0.20.0 và sau này.

Legacy shell hooks (được cài đặt bởi 1.0.5 và trước đó) **không** kiểm tra Hermes cron jobs: mỗi cron run xây dựng hook scope riêng của nó, mà native plugin tham gia và `config.yaml` shell hooks không. `failproofai update` di chuyển mỗi profile đã sử dụng FailproofAI đến linked plugin. Nếu running daemon không thể phục vụ plugin, `update` để lại shell hooks tại chỗ và thoát không-zero; chạy `failproofai config` để cập nhật daemon, sau đó `failproofai update` lại. Cron jobs tải plugin trên lần chạy tiếp theo của chúng; khởi động lại running gateways và interactive sessions để tải nó ở đó.

Trên Hermes, `deny()` chặn lệnh gọi và `instruct()` không: lệnh gọi chạy, và hướng dẫn được đặt ở đầu kết quả của nó — dưới dạng key đầu tiên, `failproof_policy_reminder`, của JSON result, hoặc dưới dạng dòng `[FailproofAI policy reminder (...)]` ở đầu — để mô hình đọc nó cùng với output, và scripts phân tích kết quả tiếp tục hoạt động. Reminder của chính sách được hiển thị một lần mỗi lượt, và giữ ngắn trên một kết quả lớn. Sử dụng `deny()` khi một hành động không được xảy ra: `instruct()` không còn dừng hành động trước. Các tool calls từ script `execute_code` đặt reminder của chúng trên `execute_code` result mà mô hình đọc; bản sao riêng của script về kết quả được để nguyên. Mô hình được thông báo không bao giờ trích dẫn reminder trong câu trả lời của nó.

Hermes build không có plugin middleware quay lại giữ matching call một lần với "FailproofAI policy guidance"; model response tiếp theo có thể lặp lại nó, hoặc làm cùng một công việc với công cụ khác, mà không bị giữ lại.

Tên công cụ được so khớp trên các phiên bản Hermes: `process_manage`, `cronjob_manage`, và `todo_list` (Hermes 0.21) được xử lý như `process`, `cronjob`, và `todo` (Hermes 0.20). Mỗi lần Hermes tải plugin, nó viết `heartbeat.json` trong thư mục `plugin-data/agent-plugin-failproofai-5296f299/` của profile, ghi lại phiên bản Hermes, đường dẫn và phiên bản plugin, và các hooks mà Hermes chấp nhận. Chạy `failproofai config --status` để phát hiện profile bị vô hiệu hóa, không hoàn chỉnh, trùng lặp, hoặc mới không được cấu hình, hoặc vẫn trên legacy shell hooks (được báo cáo là "Hermes cron jobs are not checked").

### OpenClaw plugin

OpenClaw tải FailproofAI như một in-process gateway plugin, được đăng ký trong mỗi profile's `openclaw.json`. Giống như Hermes plugin, nó yêu cầu local `failproofaid` daemon cho mỗi verdict qua socket của nó, vì vậy nó cần một running daemon: installation từ chối nếu không có, và nếu daemon không thể trả lời, tool calls và prompts bị chặn và lý do được viết vào gateway log. Sau `npm install -g failproofai@latest`, khởi động lại OpenClaw gateway để nó tải plugin được cập nhật.

### Codex hook trust

Codex 0.129 và sau này chạy một hook từ `~/.codex/hooks.json` chỉ sau khi bạn phê duyệt nó trong interactive `codex` ("Review hooks"); cho đến lúc đó, mỗi Codex session — headless `codex exec` bao gồm — bỏ qua nó. Hooks trong Codex's system config, `/etc/codex/config.toml` trên Linux và macOS, chạy mà không cần phê duyệt đó.

Vì vậy khi `failproofai config` (hoặc `policies --install --cli codex` ở user scope) có thể sử dụng sudo, nó viết Codex hooks vào `/etc/codex/config.toml`, giữa `# >>> failproofai managed hooks >>>` và `# <<< failproofai managed hooks <<<`, và để lại phần còn lại của tệp đó như trước.

Tệp đó áp dụng cho mỗi tài khoản trên máy, vì vậy mỗi hook trong đó chạy `/opt/failproofai-codex/codex-hook`, một script ngắn mà root sở hữu. Script trao event cho failproofai riêng của từng tài khoản cho mỗi tài khoản đã thiết lập hooks ở đó, và không làm gì cho bất kỳ tài khoản nào khác. Tài khoản khác muốn Codex hooks của failproofai thiết lập chúng cho chính nó.

Trước khi viết khối đó, và lại trên mỗi `failproofai update`, failproofai kiểm tra rằng `/etc/codex/config.toml` chính nó, script, mỗi thư mục phía trên chúng, và `sh`, `id` và `cat` mà nó chạy thuộc sở hữu của root và không thể được viết bởi bất kỳ ai khác, và mỗi failproofai của tài khoản thuộc về tài khoản đó hoặc root. Trên install, khi kiểm tra đó thất bại, hooks của bạn ở lại trong `~/.codex/hooks.json`. Trên update, script mà nó thất bại lấy khối ra, và tài khoản mà failproofai của nó thất bại được lấy ra khỏi script; chạy `failproofai config` lại một khi nó được sửa. `failproofai update` cũng viết lại khối được viết bởi phiên bản trước để sử dụng script, cần sudo.

`failproofai uninstall` và bỏ chọn Codex trong `failproofai config` lấy tài khoản của bạn ra lại, và khối với nó một khi không có tài khoản nào còn lại.

Không có sudo, và trên Windows, hooks ở lại trong `~/.codex/hooks.json`. `failproofai config` và `failproofai config --status` sau đó không tính Codex là thực thi cho đến khi hooks được phê duyệt, và nói cách sửa nó: chạy lại `failproofai config` và cho phép sudo, hoặc mở `codex` một lần và phê duyệt hooks.

## Install capture and policy hooks

<Tabs>
  <Tab title="Dashboard">
    1. Mở **settings → api keys** và tạo một key với `events:add` và `policies:pull`, đặt tên cho máy hoặc môi trường.
    2. Trên máy đích, kết nối local CLI với key được hiển thị và cài đặt harness hooks.
    3. Bắt đầu một new agent session, sau đó xác nhận hook và session events của nó dưới **trace → live events**.
    4. Mở **fix → activity** cho cùng một time window và xác nhận policy decision được quy cho máy.

    Kết nối bắt đầu với machine key. Xác nhận rằng nó bao gồm cả ingestion và policy-delivery permissions trước khi sao chép secret của nó.

    ![The new API key drawer used to grant event ingestion and policy delivery permissions.](/images/dashboard/key-create.png)

    Sau khi cài đặt hooks, Events stream sẽ hiển thị các events mới từ máy và môi trường bạn kết nối.

    ![The live Events stream used to confirm a newly installed harness is reporting.](/images/dashboard/events-stream.png)

    Cuối cùng, xác minh rằng policy decisions được quy cho cùng một máy. Điều này xác nhận harness báo cáo policy activity cũng như trace events.

    ![The Policy page used to verify policy decisions from a newly connected harness.](/images/dashboard/policy-observe.png)
  </Tab>
  <Tab title="CLI">
    Đọc machine key vào shell. `read -s` lấy nó tại một prompt mà không echo, vì vậy nó không bao giờ xuất hiện trong một command hoặc trong shell history:

    ```bash
    read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
    ```

    Sau đó thiết lập máy — điều này kết nối hooks cho mỗi detected harness, cài đặt daemon, và kết nối đến Cloud:

    ```bash
    failproofai config
    failproofai policies add FailproofAI/policies
    ```

    Setup không kích hoạt bất kỳ chính sách nào riêng lẻ, đó là lý do lệnh thứ hai.

    Hoặc nhắm mục tiêu named harnesses và configuration scope:

    ```bash
    failproofai policies --install \
      --cli claude codex cursor \
      --scope user
    ```

    Project scope giữ hook configuration với một repository. User scope bao gồm work qua repositories. Claude Code cũng hỗ trợ local scope; hỗ trợ khác nhau tùy theo harness và CLI từ chối các sự kết hợp không được hỗ trợ.

    Xác minh máy và các events của nó:

    ```bash
    failproofai config --status
    failproofai flush --wait
    fp events --since 1h --event-type hook_triggered,hook_completed
    ```
  </Tab>
</Tabs>

## Add a non-default session path

<Tabs>
  <Tab title="Dashboard">
    Extra paths được đăng ký trên máy, không phải trong Cloud. Sau khi thêm một, mở **trace → sessions**, filter đến environment của máy, và xác nhận sessions từ path mới xuất hiện. Mở một session và kiểm tra agent, harness, và event timestamps trước khi dựa vào nó trong một audit.

    ![The Sessions list filtered to the environment receiving data from the additional capture path.](/images/dashboard/sessions-list.png)
  </Tab>
  <Tab title="CLI">
    Thêm một path với optional label, sau đó kiểm tra các configured paths:

    ```bash
    failproofai harness add-path claude checkout=/srv/checkout/.claude
    failproofai harness list claude
    failproofai backfill --since 7d --dry-run
    failproofai backfill --since 7d
    ```

    Xóa một path với `failproofai harness remove-path claude checkout`.
  </Tab>
</Tabs>

<Tip>
  Chạy một new session sau installation. Xác minh cả live event stream và một actual policy decision trước khi mở rộng rollout.
</Tip>
