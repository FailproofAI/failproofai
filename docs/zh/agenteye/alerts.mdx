在问题越界的第一时间收到通知——通过团队已在使用的渠道——而不是等到客户来反馈。只需设置一次规则，Failproof AI Observability 便会按计划检查并通过电子邮件、Slack、Webhook 或仪表盘直接发送告警。

![告警页面：由告警规则卡片组成的网格，每张卡片显示触发条件、评估窗口、通知渠道以及信息、警告或严重等级徽章](/agenteye/images/alerts.png)
*一览所有告警规则：监控对象、检查频率、通知渠道及紧急程度。*

## 先于用户发现问题

告别盯着仪表盘刷新、期待能赶上回归的日子。只要有需要持续关注的信号，就为其设置告警，让通知直达你日常使用的地方：

- **电子邮件**，发送给所有相关负责人。
- **Slack**，富文本消息中附带按钮，可直接跳转到对应事件。
- **Webhook**，向 PagerDuty、Opsgenie 或自定义端点发送 JSON POST 请求，支持可选签名以供接收方验证来源。
- **仪表盘内通知**，默认静默，适用于调试规则期间暂不想打扰他人的场景。

一条规则可绑定任意组合的通知渠道，同时携带严重等级（信息、警告或严重），确保紧急告警一眼可辨。

## 用表单而非 JSON 构建规则

你只需在表单中描述"故障"的含义，Failproof AI Observability 会自动生成底层规则。JSON 规范只是表单背后的产物——读它可以理解规则内容，但几乎不需要手动编写。

![新建告警表单：名称与描述、启用开关，以及触发器选项，包括指标阈值、自定义 SQL、评估评分、复合评估和单事件条件](/agenteye/images/alert-new.png)
*选择触发器后，表单会自动切换对应字段；点击保存即完成规则创建。*

常规流程非常简洁：填写名称，选择**触发器**（监控对象），设置**阈值和时间窗口**（严重程度及持续时长），绑定至少一个**通知渠道**，然后点击**保存**，再点击**测试**发送一条模拟通知，确认所有目标渠道均已正确接入。底层会生成如下简洁的规范：

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

你并不局限于单一类型的信号，可根据对故障的理解选择对应的触发器：

| 触发器 | 触发时机 |
|---|---|
| **指标阈值** | 预设指标（错误率、p95 或 p99 延迟、事件或错误计数、Token 消耗）在指定时间窗口内越界 |
| **自定义 SQL** | 自定义只读查询返回结果行，或其计算值越过阈值 |
| **评估评分** | 某评估器评分的平均值（如幻觉率）越过阈值 |
| **复合评估** | 多项评分检查通过 any、all 或至少 N 项逻辑组合，用于捕捉仅在综合评分中才显现的回归 |
| **单事件** | 匹配的单个事件发生：特定 Agent、特定错误类型或消息子字符串 |

正在 [错误页面](/zh/agenteye/error-tracking) 排查故障？每行都有一个 **+ alert** 按钮，点击后会打开预填好的表单，精准捕获同类故障——让你刚刚处理过的事件成为下次告警的触发条件。

**访问路径：** 告警功能位于 `/<org-slug>/alerts`。创建、编辑、删除和测试规则需要 **`alerts:write`** 权限；仅查看需要 `alerts:read`。收件人选择器会按姓名列出组织成员，无需离开表单即可指定告警接收人。

## 只在真正需要时叫醒你

一次异常测量不应触发告警。**M of N** 降噪过滤器用于控制最近几次检查中必须有多少次失败，告警才真正触发。将其设置为 **3 of 5**，则规则在最近五次检查中有三次超标后才触发，从而避免信号抖动导致的误报；保持默认的 **1 of 1** 则在首次超标时立即触发。你还可以从 1m、5m、15m、1h 等预设间隔中选择规则的检查频率，以匹配信号的实际变化速度。

## 告警触发后的处理流程

一次超标会创建一个**事件**，并向所有通知渠道发送一次通知。随后团队可对其进行确认、分配负责人、讨论处理方案并最终解决，全程都有清晰的归因记录。该分诊工作流有专属页面，详见 [事件管理](/zh/agenteye/incidents)。
