在问题超出可接受范围的第一时间得到通知，通知渠道是你的团队已经在使用的，而不是等到客户反映才知道。规则只需配置一次，Failproof AI Observability 就会按计划检查，并通过邮件、Slack、Webhook 或直接在控制台向你发送告警。

![告警页面：一组告警规则卡片，每张卡片显示触发条件、评估窗口、通知渠道，以及信息、警告或严重级别标识](/agenteye/images/alerts.png)
*一览所有告警规则：监控内容、检查频率、通知去向及紧急程度。*

## 在用户发现之前掌握问题

不要再靠反复刷新仪表盘来发现故障回退了。只要是无人值守时也想知道的信号，就为它创建一条告警，让通知直接发到你常用的地方：

- **邮件**，发给应该知情的人。
- **Slack**，一条包含按钮的富文本消息，点击即跳转到对应事故。
- **Webhook**，向 PagerDuty、Opsgenie 或你自己的接口发送 JSON POST 请求，支持可选签名以便接收方验证来源。
- **控制台内通知**，安静模式，适合调试规则阶段，不想打扰任何人时使用。

一条规则可以绑定任意组合的通知渠道，告警的严重级别（信息、警告或严重）会同步携带，让紧急的告警看起来就该是紧急的。

## 用表单配置规则，无需手写 JSON

你通过表单描述什么叫"出问题了"，Failproof AI Observability 自动生成底层规则。JSON 规范只是表单在背后生成的产物，你可以阅读它来理解规则，但几乎不需要手动编写。

![新建告警表单：名称和描述、启用开关，以及触发类型选择器（提供指标阈值、自定义 SQL、评估分数、复合评估和逐事件条件）](/agenteye/images/alert-new.png)
*选择触发类型后，表单自动切换到对应的字段；点击保存即写入规则。*

常规流程非常快：填写名称，选择**触发条件**（监控什么），设置**阈值和窗口**（偏差多大、持续多久），绑定至少一个**通知渠道**，然后**保存**并点击**测试**，发送一条模拟通知，确认每个目标都已正确接入。这会在底层生成一小段类似这样的规范：

```json
{ "metric": "p95_latency_ms", "op": ">", "value": 5000, "window_secs": 900 }
```

不止一种信号类型可选。根据你对故障的理解，选择对应的触发类型：

| 触发类型 | 触发时机 |
|---|---|
| **指标阈值** | 预设指标（错误率、p95 或 p99 延迟、事件或错误计数、Token 用量）在指定窗口内超出阈值 |
| **自定义 SQL** | 你的只读查询返回了行，或其计算值超出阈值 |
| **评估分数** | 某个评估器的平均分（如幻觉率）超出阈值 |
| **复合评估** | 多项分数检查通过 any、all 或至少 N 项的逻辑组合，捕捉只有跨分数才能发现的回退 |
| **逐事件** | 单个匹配事件出现：特定 Agent、特定错误类型，或消息中包含指定子字符串 |

已经在[错误页面](/zh/agenteye/error-tracking)盯着某个故障看了？每一行都有一个 **+ 告警** 按钮，点击后会打开同一个表单，并预填好该故障的精确条件，让你刚刚处理过的事故变成下次自动通知你的那一条。

**入口位置：** 告警位于 `/<org-slug>/alerts`。创建、编辑、删除和测试规则需要 **`alerts:write`** 权限；仅查看只需 `alerts:read`。收件人选择器会按姓名列出你所在组织的成员，无需离开表单即可直接选人通知。

## 只在真正出问题时才告警

一次偶发的异常测量不应该把你惊醒。**M of N** 噪声过滤器控制在过去几次检查中必须有多少次失败，告警才真正触发。设为 **3 of 5** 时，规则仅在最近五次检查中有三次超出阈值后才发送告警，从而避免抖动信号频繁误报；保持默认的 **1 of 1** 则在首次超出时立即触发。你还可以选择规则的运行频率，提供 1m、5m、15m 和 1h 四种预设，与信号的实际变化速度相匹配。

## 告警触发后会发生什么

一次超出阈值会开启一个**事故**并向你的通知渠道发送一次告警。之后，团队成员确认告警、指派负责人、展开讨论并最终解决，整个过程都有清晰且有归属的记录可查。这套分级处理流程有专属页面：请参见[事故](/zh/agenteye/incidents)。
