告诉你的编码 Agent *"为这个 Agent 添加 Failproof AI 可观测性"*，让它读取你的主循环，找出插桩位置，完成编写，并在宣告任务完成之前验证事件是否正确落地。

**Python SDK skill**（`agenteye-python-sdk`）是一个 *Agent Skill*：一个包含指令的文件夹，供 Claude Code 或 Codex 等编码 Agent 按需加载，当任务与之匹配时自动调用。它教会 Agent 使用 [Python SDK](/zh/agenteye/python-sdk)——它本身不是一个库，也不会改变 SDK 的任何工作方式。

## 插桩易写，也容易悄然出错

SDK 很小：十三个事件方法，全部仅支持关键字参数。编码 Agent 可以阅读 [Python SDK](/zh/agenteye/python-sdk) 参考文档，在一分钟内生成看起来合理的插桩代码。

问题在于，这个 SDK 在出错时不会抛出异常，而错误的插桩看起来和正确的插桩一模一样——直到有人打开仪表盘发现空空如也。那些真正耗费时间的错误，都是沉默：

| 错误 | 你看到的现象 |
|---|---|
| 缺少 `agent_start` | 每个事件都到了。会话数为零。 |
| 环境从未设置 | 一切正常，但全归档在 `dev` 下。 |
| `outcome="failure"` | 运行显示绿色——只有 `failed`、`error`、`timeout`、`rejected` 才会被计入。 |
| 字段名拼写错误 | 被接受并作为新字段存储。 |
| 从线程池中发出事件 | 静默丢弃。 |

以上情况均不会抛出异常，也不会在测试中显现。每一种情况都在 skill 中有明确说明，以合约的形式列出，并附有能捕获它的检查。

## 执行步骤

该 skill 按顺序执行经验丰富的工程师会做的三个步骤：

1. **规划。** 读取你的 Agent 主循环，并提出只有你能回答的两个问题：什么算作一次运行（你的 `session_id`），以及可区分的执行者是谁（你的 `agent_id`）。在编写代码之前先达成一致，因为事后更改会拆分历史数据，破坏趋势分析。
2. **编写。** 每次运行只绑定一次身份，而不是在每个调用点都穿透传递；并选择并发安全的方式——这一细节至关重要，因为看似简单的捷径会悄无声息地将两个重叠的运行混入同一个会话。
3. **验证。** 运行你的 Agent，读取生成的事件文件，检查 `agent_start` 是否存在、环境是否正确、一次运行是否产生了一个会话。

第三步正是人们常常跳过的。SDK 将事件写入本地文件，因此完整的集成可以在笔记本电脑上完成验证，无需服务器、无需 API 密钥、无需网络——这正是该 skill 坚持要做这一步的原因。

## 与其他 skill 的关系

三个 skill，职责清晰：

| Skill | 使用场景 | 操作范围 |
|---|---|---|
| **Python SDK skill**（本页） | 你希望 Agent *发出*遥测数据——"添加可观测性"、"为什么我的 Agent 没有显示？" | 在你 Agent 的代码库中写代码，不读取任何内容。 |
| **[Evaluator skill](/zh/agenteye/evaluator-skill)** | 你希望对运行进行*评分*——"我们究竟该衡量什么？" | 在你的代码库中写代码；读取遥测数据。 |
| **[CLI skill](/zh/agenteye/cli-skill)** | 你想*读取*发生了什么，或操作你的部署 | 以你的身份驱动 CLI，包括变更操作。 |

它们按此顺序交接：本 skill 让事件开始流动，evaluator 对其评分，CLI 将其读回。在 Agent 发出会话之前，没有什么可以评分，也没有什么可以读取——所以如果你从零开始，就从这里开始。

## 前提条件

1. **Python 3.10+** 以及你想要插桩的 Agent 代码库。
2. **SDK。** 它作为私有 wheel 包分发给客户，而非来自公共索引——你的入门流程中包含获取和安装方式。该 skill 知道安装路径，如果找不到，会向你询问而不是自行猜测。
3. **无需其他任何东西。** 无需登录仪表盘，无需 API 密钥，无需网络。该 skill 通过 SDK 写入的事件文件进行验证，因此可以在离线状态下完成并证明其工作结果。

## 获取方式

该 skill 位于公共仓库 [`FailproofAI/skills`](https://github.com/FailproofAI/skills) 中：

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

添加 `-g` 可将其安装到所有项目而非仅当前项目，如果你的环境不支持符号链接，请添加 `--copy`。对于 Codex，传入 `-a codex`。

## 手动安装

Agent Skill 是包含 `SKILL.md` 及相关引用文件的文件夹。如果你不想使用安装器：

- **Claude Code**：将 `agenteye-python-sdk/` 文件夹复制到 `~/.claude/skills/`（所有项目）或 `<your-repo>/.claude/skills/`（仅该代码库）。Claude Code 会自动发现它——查看 `/skills` 列表，或直接询问与之匹配的问题即可。
- **Codex**：Codex 读取相同的 `SKILL.md`。捆绑的 `agents/openai.yaml` 设置了 `allow_implicit_invocation: true`，因此当任务匹配时会自动选择；否则可以通过 `$agenteye-python-sdk` 显式调用。

在**包含你要插桩的代码的代码库**中运行你的 Agent——该 skill 在提出任何建议之前会先读取你的 Agent 主循环。

## 会话示例

```text
you   ▸ Add Failproof AI Observability to this agent.

agent ▸ Read your loop — one tool dispatcher in tools.py, one Anthropic
        wrapper in llm.py. Two questions before I write anything.

        What counts as one run? You handle requests concurrently, so I'd
        use the request id you already have in ctx.request_id — then a
        session here and a request in your logs are the same string.

        And who are the actors? I see a planner path and a researcher
        path. Label them separately, or is that one agent to you?

you   ▸ Request id is right. They're one agent, call it "assistant".

agent ▸ Done. Wrapped the dispatcher and the LLM client; agent_start and
        agent_end bracket handle_request, including the error path. Used
        a context-local for identity — your dispatcher runs tools in a
        thread pool, and the simpler approach would have mixed concurrent
        runs into one session without complaining.

        Verified against a real run: 11 events across 4 files —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, one session
        per request, durations paired.

        One thing I did NOT do: your worker pool in batch.py submits
        straight to the executor, so events from there would be dropped.
        Want me to fix those too?
```

值得注意的模式：它在提出建议之前先读取了代码，只问了你才能回答的问题，复用了你已有的 ID，*因为*看到了线程池而选择了并发安全的方式，并且**通过读取实际事件来验证结果**而非直接宣告成功——然后标记出那个它知道会悄然失败的位置。

## 可以问它什么

- *"为什么我的 Agent 没有出现在仪表盘上？"* → 逐级排查：事件是否正在写入，`agent_start` 是否存在，环境是否正确，收集器读取的是否是同一个位置。
- *"所有内容都归在 dev 下。"* → 环境从未设置，或被后续调用重置了。
- *"添加 token 追踪。"* → 找到你的 LLM 封装层，记录模型、停止原因和用量。
- *"也对子 Agent 插桩。"* → 一个会话，不同的 Agent 标签，嵌套在各自的父级之下。
- *"为插桩编写测试。"* → 将 SDK 指向临时目录，并对写入的事件进行断言。

## 注意事项

**让它完成验证。** 使这个 skill 真正有价值的步骤是最后一步——运行你的 Agent 并将事件读回。一个写完插桩就停下来的 Agent 只完成了容易的那一半，而另一半——那个会悄然失败的部分——才是关键。

**在编写代码之前确定好名称。** `session_id` 和 `agent_id` 是每个视图分组的坐标轴。事后重命名会拆分历史数据：旧运行保留旧标签，趋势分析随之中断。该 skill 会询问，答案值得花一分钟认真思考。

**如果你的 Agent 提议从公共索引安装 SDK，说明该 skill 未能加载。** SDK 是私有分发的。这个提议是可靠的信号，说明你的编码 Agent 是在猜测而非遵循 skill 的指引——在这里停下来，检查 skill 是否已正确安装。

除此之外，其影响范围很小：它在你的工作目录中写代码，在你指定的位置写事件文件。它不读取你的部署中的任何内容，也不对其做任何更改。
