告诉你的编程 Agent *"为这个 Agent 添加 Failproof AI Observability"*，让它读取你的循环逻辑，判断插桩位置，编写代码，并在宣告任务完成前验证事件已正确落地。

**Python SDK skill**（`agenteye-python-sdk`）是一个 *Agent Skill*：一个包含指令的文件夹，编程 Agent（如 Claude Code 或 Codex）在任务匹配时按需加载。它教会 Agent 如何使用 [Python SDK](/zh/agenteye/python-sdk)——它本身不是一个库，也不会改变 SDK 的任何行为。

## 插桩容易写，也容易悄悄出错

SDK 很精简：十三个事件方法，全部仅支持关键字参数。编程 Agent 读一遍 [Python SDK](/zh/agenteye/python-sdk) 参考文档，一分钟内就能写出看起来合理的插桩代码。

问题在于：这个 SDK 在你出错时不会抛出异常，而错误的插桩和正确的插桩看起来完全一样——直到有人打开 Dashboard 发现一片空白。那些真正浪费时间的错误，全都是"沉默"：

| 错误 | 你看到的现象 |
|---|---|
| 没有 `agent_start` | 每个事件都落地了，但会话数为零。 |
| 从未设置环境变量 | 一切正常运行，全部归档在 `dev` 下。 |
| `outcome="failure"` | 运行显示为绿色——只有 `failed`、`error`、`timeout`、`rejected` 才会计入统计。 |
| 字段名拼写错误 | 被接受并作为新字段存储。 |
| 从线程池发出事件 | 静默丢弃。 |

这些问题都不会抛出异常，也不会在测试中暴露。每一条都在 skill 中有明确说明，并对应能够捕获它的检查。

## 它做什么，按顺序

该 skill 执行与谨慎的工程师相同的三个步骤：

1. **规划。** 读取你的 Agent 循环，并提出两个只有你能回答的问题：什么算作一次运行（你的 `session_id`），以及哪些是可区分的参与者（你的 `agent_id`）。在写代码之前先就这两点达成一致，因为之后修改会拆分历史记录并破坏趋势数据。
2. **编写。** 每次运行只绑定一次身份，而不是在每个调用点都传递；并选择并发安全的方式——这个细节很重要，因为看似便捷的捷径会悄悄地将两个重叠的运行混入同一个会话中。
3. **验证。** 运行你的 Agent 并读取生成的事件文件，检查 `agent_start` 是否存在、环境是否正确、一次运行是否产生了一个会话。

第三步是大多数人跳过的那一步。SDK 将事件写入本地文件，因此完整的集成可以在笔记本电脑上完成验证，无需服务器、无需 API Key、无需网络——这正是 skill 坚持这样做的原因。

## 它与其他 skill 的关系

三个 skill，职责清晰划分：

| Skill | 何时使用 | 操作范围 |
|---|---|---|
| **Python SDK skill**（本页） | 你想让 Agent *发出*遥测数据——"添加可观测性"、"为什么我的 Agent 没有显示？" | 在你的 Agent 仓库中写代码，不读取任何内容。 |
| **[Evaluator skill](/zh/agenteye/evaluator-skill)** | 你想对运行进行*评分*——"我们究竟该衡量什么？" | 在你的仓库中写代码；读取遥测数据。 |
| **[CLI skill](/zh/agenteye/cli-skill)** | 你想*查看*发生了什么，或操作你的部署 | 以你的身份驱动 CLI，包括变更操作。 |

它们按此顺序交接：本 skill 让事件开始流动，Evaluator 对其评分，CLI 将其读回。在 Agent 发出会话之前，既没有什么可评估的，也没有什么可读取的——所以如果你是从零开始，从这里起步。

## 前提条件

1. **Python 3.10+** 以及你想要插桩的 Agent 代码库。
2. **SDK。** SDK 以私有 wheel 包的形式分发给客户，而非通过公共索引——你的入门流程会说明如何获取和安装。如果 skill 找不到它，会向你询问而不是猜测。
3. **无需其他任何东西。** 无需登录 Dashboard，无需 API Key，无需网络。skill 通过 SDK 写入的事件文件进行验证，因此可以在离线状态下完成并证明其工作。

## 获取方式

该 skill 位于公开的 [`FailproofAI/skills`](https://github.com/FailproofAI/skills) 集合中：

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

添加 `-g` 可将其安装到所有项目而非仅当前项目，若你的环境不支持符号链接，请加上 `--copy`。对于 Codex，传入 `-a codex`。

## 手动安装

Agent Skill 是包含 `SKILL.md` 及相关引用的文件夹。如果你不想使用安装器：

- **Claude Code**：将 `agenteye-python-sdk/` 文件夹复制到 `~/.claude/skills/`（所有项目）或 `<你的仓库>/.claude/skills/`（仅该仓库）。Claude Code 会自动发现它——查看 `/skills` 列表，或直接问一个与之匹配的问题。
- **Codex**：Codex 读取相同的 `SKILL.md`。捆绑的 `agents/openai.yaml` 设置了 `allow_implicit_invocation: true`，因此任务匹配时会自动选择；否则通过 `$agenteye-python-sdk` 调用它。

在**包含你想要插桩代码的仓库中**运行 Agent——skill 会在提出任何建议之前先读取你的 Agent 循环。

## 一次会话的样子

```text
you   ▸ Add Failproof AI Observability to this agent.

agent ▸ Read your loop — one tool dispatcher in tools.py, one Anthropic
        wrapper in llm.py. Two questions before I write anything.

        What counts as one run? You handle requests concurrently, so I'd
        use the request id you already have in ctx.request_id — then a
        session here and a request in your logs are the same string.

        And who are the actors? I see a planner path and a researcher
        path. Label them separately, or is that one agent to you?

you   ▸ Request id is right. They're one agent, call it "assistant".

agent ▸ Done. Wrapped the dispatcher and the LLM client; agent_start and
        agent_end bracket handle_request, including the error path. Used
        a context-local for identity — your dispatcher runs tools in a
        thread pool, and the simpler approach would have mixed concurrent
        runs into one session without complaining.

        Verified against a real run: 11 events across 4 files —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, one session
        per request, durations paired.

        One thing I did NOT do: your worker pool in batch.py submits
        straight to the executor, so events from there would be dropped.
        Want me to fix those too?
```

值得注意的模式：它在提出建议之前先读取了代码，只问了你才能回答的问题，复用了你已有的 ID，*因为*看到了线程池才选择了并发安全的方式，并且**通过读取实际事件来验证**而不是直接宣告成功——然后标记出了那个它知道会静默失败的地方。

## 你可以问它什么

- *"为什么我的 Agent 没有显示在 Dashboard 上？"* → 逐步排查：事件是否正在写入、`agent_start` 是否存在、环境是否正确、Collector 是否读取了同一位置。
- *"所有数据都落在 dev 下。"* → 环境变量从未设置，或被后续调用重置了。
- *"添加 token 追踪。"* → 找到你的 LLM wrapper，记录模型、停止原因和用量。
- *"也为子 Agent 插桩。"* → 一个会话，不同的 Agent 标签，嵌套在父级之下。
- *"为插桩代码编写测试。"* → 将 SDK 指向临时目录，并对写入的事件进行断言。

## 需要注意的事项

**让它完成验证。** 这个 skill 价值所在的步骤是最后一步——运行 Agent 并读回事件。一个只写插桩代码就停下来的 Agent 只完成了容易的那一半，而静默失败的恰恰是另一半。

**在写代码之前先商定命名。** `session_id` 和 `agent_id` 是每个视图的分组维度。之后重命名会拆分历史：旧的运行保留旧标签，趋势数据随之断裂。skill 会主动询问；这个答案值得花一点时间思考。

**如果你的 Agent 建议从公共索引安装 SDK，说明 skill 没有加载。** SDK 是私有分发的。这个建议是一个可靠的信号，说明你的编程 Agent 在猜测而非遵循 skill——在这里停下来，检查 skill 是否已安装。

除此之外，它的影响范围很小：它在你的工作目录中写代码，并将事件文件写到你指定的位置。它不读取你部署环境中的任何内容，也不会对其进行任何更改。
