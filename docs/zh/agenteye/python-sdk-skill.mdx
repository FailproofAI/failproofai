告诉你的编码 Agent *"为这个 Agent 添加 Failproof AI 可观测性"*，让它读取你的循环逻辑，判断插桩位置，编写代码，并在宣告完成之前验证事件。

**Python SDK skill**（`agenteye-python-sdk`）是一个 *Agent Skill*：一个包含指令的文件夹，供 Claude Code 或 Codex 等编码 Agent 在任务匹配时按需加载。它教会 Agent 如何使用 [Python SDK](/zh/agenteye/python-sdk)——它不是一个库，也不会改变 SDK 的任何工作方式。

## 插桩容易写，也容易悄悄出错

SDK 很小巧：十三个事件方法，全部为仅关键字参数。编码 Agent 可以阅读 [Python SDK](/zh/agenteye/python-sdk) 参考文档，在一分钟内生成看起来合理的插桩代码。

问题在于，这个 SDK 在你写错时不会抛出异常，而错误的插桩看起来和正确的插桩一模一样——直到有人打开仪表板，发现里面空空如也。真正耗费大量时间的错误，都是"静默"类的：

| 错误 | 你看到的现象 |
|---|---|
| 没有 `agent_start` | 每个事件都落地，却零个会话。 |
| 环境从未设置 | 一切正常运行，但都归档在 `dev` 下。 |
| `outcome="failure"` | 运行显示绿色——只有 `failed`、`error`、`timeout`、`rejected` 才算失败。 |
| 字段名拼写错误 | 被接受并作为新字段存储。 |
| 从线程池发出事件 | 静默丢弃。 |

这些情况没有一个会抛出异常，没有一个会在测试中显现。每一条都在 skill 中有明确说明，并给出了能捕获它的检查方式。

## 它的执行步骤

该 skill 执行与细心的工程师相同的三个步骤：

1. **规划。** 读取你的 Agent 循环，并提出两个只有你能回答的问题：什么算作一次运行（你的 `session_id`），以及可区分的参与者是谁（你的 `agent_id`）。它会在编写代码之前达成共识，因为事后修改会拆分你的历史记录，破坏趋势分析。
2. **编写。** 每次运行绑定一次身份，而不是在每个调用点都传入，并选择并发安全的方案——这个细节很重要，因为最直接的做法会悄悄将两个重叠运行混入同一个会话。
3. **验证。** 运行你的 Agent 并读取生成的事件文件，检查 `agent_start` 是否存在、环境是否正确、一次运行是否恰好产生一个会话。

第三步正是人们常常跳过的。SDK 将事件写入本地文件，因此完整的集成可以在笔记本电脑上验证，无需服务器、无需 API 密钥、无需网络——这正是该 skill 坚持执行这一步的原因。

## 与其他 skill 的关系

三个 skill，职责清晰分离：

| Skill | 适用场景 | 涉及内容 |
|---|---|---|
| **Python SDK skill**（本页） | 你想让 Agent *发出*遥测数据——"添加可观测性"、"为什么我的 Agent 没有显示？" | 在你的 Agent 仓库中写代码，不读取任何内容。 |
| **[Evaluator skill](/zh/agenteye/evaluator-skill)** | 你想对运行进行*评分*——"我们到底该衡量什么？" | 在你的仓库中写代码；读取遥测数据。 |
| **[CLI skill](/zh/agenteye/cli-skill)** | 你想*读取*发生了什么，或操作你的部署 | 以你的身份驱动 CLI，包括变更操作。 |

它们按顺序交接：本 skill 让事件流动起来，evaluator 对事件评分，CLI 读取评分结果。在你的 Agent 发出会话之前，既没有可评估的内容，也没有可读取的内容——所以如果你从零开始，就从这里起步。

## 前置条件

1. **Python 3.10+** 以及你想要插桩的 Agent 代码库。
2. **SDK。** 它以私有 wheel 的形式分发给客户，而非从公开索引获取——你的入门指引会说明如何获取和安装。该 skill 知道安装路径，如果找不到会询问你，而不是自行猜测。
3. **无需其他任何东西。** 无需登录仪表板、无需 API 密钥、无需网络。该 skill 通过 SDK 写入的事件文件进行验证，因此可以离线完成并证明其工作成果。

## 获取方式

该 skill 位于公开的 [`FailproofAI/skills`](https://github.com/FailproofAI/skills) 合集中：

```bash
npx skills add FailproofAI/skills --skill agenteye-python-sdk -a claude-code
```

添加 `-g` 可为所有项目安装，而不仅限于当前项目；如果你的环境不支持符号链接，加上 `--copy`。对于 Codex，传入 `-a codex`。

## 手动安装

Agent Skill 是包含 `SKILL.md` 及相关引用文件的文件夹。如果你不想使用安装程序：

- **Claude Code**：将 `agenteye-python-sdk/` 文件夹复制到 `~/.claude/skills/`（所有项目）或 `<your-repo>/.claude/skills/`（仅该仓库）。Claude Code 会自动发现它——检查 `/skills` 列表，或者直接提问一个与之匹配的问题。
- **Codex**：Codex 读取同样的 `SKILL.md`。捆绑的 `agents/openai.yaml` 设置了 `allow_implicit_invocation: true`，因此任务匹配时会自动选中；否则以 `$agenteye-python-sdk` 方式调用。

**在包含你想要插桩的代码的仓库中**运行你的 Agent——该 skill 在提出任何建议之前会先读取你的 Agent 循环。

## 一次会话的样子

```text
you   ▸ Add Failproof AI Observability to this agent.

agent ▸ Read your loop — one tool dispatcher in tools.py, one Anthropic
        wrapper in llm.py. Two questions before I write anything.

        What counts as one run? You handle requests concurrently, so I'd
        use the request id you already have in ctx.request_id — then a
        session here and a request in your logs are the same string.

        And who are the actors? I see a planner path and a researcher
        path. Label them separately, or is that one agent to you?

you   ▸ Request id is right. They're one agent, call it "assistant".

agent ▸ Done. Wrapped the dispatcher and the LLM client; agent_start and
        agent_end bracket handle_request, including the error path. Used
        a context-local for identity — your dispatcher runs tools in a
        thread pool, and the simpler approach would have mixed concurrent
        runs into one session without complaining.

        Verified against a real run: 11 events across 4 files —
        agent_start, model_request/response, tool_use/tool_result x3,
        agent_end (outcome=success). environment=production, one session
        per request, durations paired.

        One thing I did NOT do: your worker pool in batch.py submits
        straight to the executor, so events from there would be dropped.
        Want me to fix those too?
```

值得注意的模式：它在提出建议之前先读取了代码，只问了你才能回答的问题，复用了你已有的 id，*因为*看到了线程池而选择了并发安全的方案，并且**通过读取实际事件来验证**而不是自行宣告成功——然后还标记出了它知道会悄悄出错的那一处。

## 你可以问它什么

- *"为什么我的 Agent 没有显示在仪表板上？"* → 逐层排查：事件是否被写入，`agent_start` 是否存在，环境是否正确，收集器是否读取了同一个位置。
- *"所有内容都落在 dev 下。"* → 环境从未设置，或被后续调用覆盖重置。
- *"添加 token 追踪。"* → 找到你的 LLM 包装器，记录模型、停止原因和用量。
- *"也为子 Agent 插桩。"* → 一个会话，不同的 Agent 标签，嵌套在父级之下。
- *"为插桩写测试。"* → 将 SDK 指向临时目录，并对写入的事件进行断言。

## 注意事项

**让它完成验证。** 这个 skill 的价值所在是最后一步——运行你的 Agent 并读取事件。只写了插桩代码就停下来的 Agent 只完成了容易的那一半，而另一半才是那个会悄悄出错的部分。

**在写代码之前先确定好命名。** `session_id` 和 `agent_id` 是每个视图的分组轴。事后重命名会拆分历史记录：旧的运行保留旧标签，趋势分析就会断裂。该 skill 会主动询问；这个问题值得认真想一分钟。

**如果你的 Agent 提议从公开索引安装 SDK，说明该 skill 没有加载。** SDK 是私有分发的。这种建议是一个可靠的信号，表明你的编码 Agent 在猜测而不是遵循 skill——在那里停下来，检查 skill 是否已安装。

除此之外，它的影响范围很小：它在你的工作目录中写代码，将事件文件写入你指定的位置。它不读取你部署中的任何内容，也不对其做任何更改。
