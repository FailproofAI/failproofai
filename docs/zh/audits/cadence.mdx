当 agents、提示词、工具和模型发生变更时，使用定期审计来捕捉可能复现的故障模式。

## 修改计划

<Tabs>
  <Tab title="控制台">
    1. 前往 **Analyze → Audits**，打开对应审计。
    2. 选择 **edit settings**，修改频率、窗口、灵敏度或每次运行的发现数量。
    3. 保存审计，并在审计标题栏确认下次运行时间。
    4. 在同一标题栏（**run now** 旁边）暂停或恢复计划。
    5. 在进行重大范围或上下文变更后，使用一次 **run now**。

    ![审计标题栏，显示其暂停状态、未解决发现、上次运行时间、下次运行时间、扫描窗口和灵敏度，以及 run now、edit settings 和 resume 控件。](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits edit checkout-reliability \
      --schedule-interval-secs 86400 \
      --schedule-anchor 2026-08-15T09:00:00Z \
      --window-mode since_last \
      --lookback-window-secs 86400 \
      --yes

    fp audits edit checkout-reliability --disabled --yes
    fp audits edit checkout-reliability --enabled --yes
    ```

    `fp audits edit` 在执行任何更改前会进行确认，因此本页所有示例均传入 `--yes`。服务器在每次编辑时会替换完整的定义，因此 CLI 会重新发送当前审计并应用您的变更——仅修改标志的编辑同时需要 `audits:read` **和** `audits:write` 权限。请为 CI 密钥同时申请这两个权限范围。

    有关计划边界、窗口行为及所有审计命令，请参阅 [`fp audits` 参考文档](/zh/reference/cloud-cli#audits)。
  </Tab>
</Tabs>

## 两个计划边界

以下所有建议均须满足这两个边界。范围由服务器定义，`fp` 在客户端同步镜像，因此超出范围的值会在本地以退出码 2 报错，而不会产生一次 422 的网络往返。

| 字段 | 标志 | 范围 | 默认值 |
| --- | --- | --- | --- |
| 计划间隔 | `--schedule-interval-secs` | 3,600–604,800 秒（1 小时至 7 天） | 86,400（每天） |
| 回溯窗口 | `--lookback-window-secs` | 3,600–7,776,000 秒（1 小时至 90 天） | 604,800（7 天） |

频率上限为七天，Cloud 审计不支持按月执行。

## 选择频率

根据风险的紧迫性和成本进行选择：

| 风险模式 | 建议起始频率 |
| --- | --- |
| 高影响生产操作 | 每天，或在高风险变更上线期间改为每小时 |
| 工作流或模型回归 | 每周 |
| 合规或访问权限审查 | 每周——这是可用的最长间隔 |

将回溯窗口与频率对齐，确保运行之间既不留空白，也不会重复扫描过大的数据范围。

没有一次性审计——每个审计都附带一个计划间隔。如需进行发布调查，可创建一个已启用的审计，等待第一次运行触发——第一次运行在创建时会立即入队，与锚点无关——然后使用 `fp audits edit <name> --disabled --yes` 将其暂停。在使用 **run now** 前请先重新启用：已禁用的审计没有队列行，针对它的手动运行会返回 409 错误。

## 窗口模式与锚点

`--window-mode` 决定每次运行扫描的窗口范围：

| 模式 | 行为 |
| --- | --- |
| `since_last` | 从上一个已完整分析的窗口末尾继续，因此跳过的运行不会留下空白。 |
| `fixed` | 每次运行都重新检查最近 `lookback_window_secs` 的数据，与上次运行的覆盖范围无关。 |

`--schedule-anchor` 固定的是运行的相位而非频率：运行将落在 `anchor + N × interval` 时刻。省略时，锚点默认为下一个 09:00 UTC；超过 365 天的锚点会被拒绝。更改间隔或锚点将在下次重新调度时生效，不影响已入队的运行，且失败的运行不会移动锚点。

在修改审计目标或上下文后，请先手动运行一次，再依赖下次定时运行的结果。

<Note>
  本页介绍的是 Cloud 审计计划，其基于 Cloud 会话运行。本地审计有独立的定时器：`failproofai audit --schedule [days]` 接受 1–90 天，默认为 7，扫描当前单台机器上的 agent 历史，并且是唯一支持按月选项的入口。其结果和所有权与本页内容完全独立——请参阅[审计本地 agent 历史](/zh/audits/local-audit)。
</Note>
