在审计目标和样本范围足够明确、以至于其他操作者能够判断什么是有效发现之后，再运行审计。

## 运行并检查

<Tabs>
  <Tab title="控制台">
    1. 前往 **Analyze → Audits**，打开审计，然后选择 **run now**。收到排队响应意味着调度器即将启动它。
    2. 打开新的运行记录，查看其状态、时间窗口、持续时间、发现数量及报告。
    3. 选择一个证据会话以打开完整的执行追踪。
    4. 返回审计页面，可编辑设置、禁用计划，或查看历史运行记录。

    ![审计详情页面，包含未处理发现、上次和下次运行状态、扫描窗口、上下文、立即运行控件及排名后的发现列表。](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits run checkout-reliability
    fp audits runs checkout-reliability --limit 10
    fp --json audits runs checkout-reliability
    fp audits findings --audit checkout-reliability
    ```

    `fp audits run` 将审计加入队列，不会等待其完成。之后使用 `fp audits runs <name>` 跟踪进度，待运行完成后读取发现结果。`--limit` 最多返回最近 50 次运行记录，无论你请求多少。

    分级处理作用于 finding id，而不是审计本身：

    ```bash
    fp audits finding <finding-id>
    fp audits ack <finding-id> --reason "owner assigned"
    fp audits assign <finding-id> --to engineer@example.com
    fp audits mute <finding-id> --reason "expected in staging" --yes
    fp audits dismiss <finding-id> --reason "false positive" --yes
    fp audits resolve <finding-id> --yes
    fp audits reopen <finding-id>
    ```

    `mute`、`dismiss` 和 `resolve` 在执行前会要求确认，在脚本中请传入 `--yes`。`ack`、`assign` 和 `reopen` 会立即执行。

    请参阅 [`fp audits` 参考文档](/zh/reference/cloud-cli#audits)，了解运行历史、发现结果及分级处理命令。
  </Tab>
</Tabs>

**run now** 可能被拒绝。正在进行中的运行和已禁用的审计均会返回 `409`，原因包含在响应的 `error` 字段中；不存在的审计或属于其他组织的审计会返回 `404`。

| 拒绝原因 | 含义 | 处理方式 |
| --- | --- | --- |
| 审计不存在 | 该审计不存在，或属于其他组织。 | 使用 `fp audits list` 确认名称。 |
| 审计已禁用 | 已禁用的审计没有队列行，因此无法触发运行。已暂停的审计仍会显示 **run now** 控件。 | 先恢复该审计，或执行 `fp audits edit <name> --enabled --yes`。 |
| 已有运行正在进行 | 每个审计同时只能有一个运行；当前运行完成后才能排队下一个。 | 使用 `fp audits runs <name>` 检查当前状态。 |

## 运行前准备

- 确认所选时间窗口内存在会话记录。
- 验证环境和 Agent 过滤条件。
- 检查参考上下文是否为最新版本。每次运行都会重新读取审计的页面，无法访问时回退到已存储的副本，因此已移动或下线的页面会持续提供过时内容，直到你修复 URL。
- 确保目标描述的是故障模式，而非预期结论。

## 查看运行结果

审计详情页面顶部显示五个磁贴：**open findings**（待分级处理的发现）、**last run**（上次运行）、**next run**（下次运行）、**window**（每次运行回溯的时间范围）和 **sensitivity**（运行标记模式的积极程度：`low`、`medium`、`high`）。每次运行最多返回 N 个发现的上限是一个独立设置，即每次运行的发现数量（`--top-k`，默认值为 50）。这五项信息比直接打开运行记录更快地回答了覆盖范围问题。

然后逐一检查每个发现的严重程度、描述、证据会话、支持查询及建议的预防路径。发现结果按 **priority** 分数（0 到 1 之间）排序，每次运行独立排名，每个发现展示其背后四个加权因子：

| 排名因子 | 权重 |
| --- | --- |
| 覆盖范围 | 0.30 |
| 影响程度 | 0.25 |
| 严重程度 | 0.25 |
| 时效性 | 0.20 |

每个发现处于以下五种状态之一：`open`、`recurring`、`resolved`、`dismissed` 或 `muted`。不带状态过滤的 `findings` 查询返回活跃集合——即 `open` 加 `recurring`。被静音、驳回或解决的发现会离开该集合；`ack` 和 `assign` 不改变状态，发现仍留在队列中——只是被降级或分配了负责人，并未消失。如需查看已离开活跃集合的发现，请明确指定状态进行查询。

使用发现状态来确认、静音、驳回、解决、重新开启或分配工作。即使发现被驳回也应保留证据，它解释了做出该决策的原因。[Findings and issues](/zh/audits/findings-and-issues) 详细介绍了每个操作对未来运行的影响。

## 解读空结果或延迟运行

| 运行状态 | 含义 | 处理方式 |
| --- | --- | --- |
| 分析已运行但产生零发现 | 在当前灵敏度配置下，所选证据不足以支持产生发现。 | 确认范围内包含具有代表性的会话，若目标或上下文不够模糊，则将结果视为健康状态。 |
| 模型分析被跳过或失败 | 运行以零发现完成，但未执行 Agentic 调查。确定性的凭证和 PII 扫描仍会在运行统计中报告匹配数量，但不会创建发现。 | 修复分析服务或配置后重新运行。不要将空结果解读为样本群体健康的证据。 |
| 模型分析已禁用 | 运行成功但产生零发现。确定性扫描不能替代模型分析，也不会创建发现。 | 启用模型分析，或禁用该审计，而不是依赖一个无法产生发现的审计。 |
| 暂无可用的分析容量 | 审计保持排队并重试，而不是跳过样本群体。 | 等待容量恢复，或分散审计锚点。自托管的操作者应扩展 audit-agent 副本数量及匹配的调度器容量。 |
| 重试窗口内容量持续不可用 | 运行放弃并产生零发现，在邮件可用时发送失败通知。 | 检查审计集群是否已饱和或频繁重启。 |

后三行描述的是 Cloud API 服务器及其调度器的行为。在托管云环境中，这些问题由 Failproof AI 负责修复；在自托管部署中，则由你自行负责。

当分析未运行时，`since_last` 审计会将该未分析的时间窗口保留到下一次成功运行。现有发现不会被退休，因为跳过的分析并不能证明故障已消失。

## 了解通知机制

成功的运行仅在发现**新内容**时才发送通知。健康审计保持沉默是正常情况，而非未运行的信号——可在审计页面查看 **last run**，或执行 `fp audits runs <name>` 确认其已运行。未选择任何渠道的审计会记录发现但不通知任何人。

运行失败或模型分析步骤失败时，使用审计配置的邮件接收者。如果审计没有配置邮件渠道，Failproof AI 会回退到组织的 `alerts.email_default_recipients` 设置，确保静默失败的审计仍有上报路径。

邮件必须在组织层面启用，且 SMTP 必须已配置，否则失败会被记录但无法发送邮件。运行失败不会改变审计的固定计划锚点。

每次运行还会为每个 Agent 存储运行时所用的精确 [Agent 上下文](/zh/audits/agent-contracts) 作为合约快照。后续编辑不会改变与早期运行一同记录的证据标准。

<Warning>
  不要直接根据未经验证的发现部署阻断策略。请打开所引用的追踪记录，确认该规则能够将不安全行为与正常工作区分开来。
</Warning>
