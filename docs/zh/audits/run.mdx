当审计的目标和范围足够明确，使得其他操作员也能判断什么是有效发现时，再运行审计。

## 运行并检查

<Tabs>
  <Tab title="仪表盘">
    1. 前往 **分析 → 审计**，打开审计，然后选择**立即运行**。显示排队响应表示调度器即将启动它。
    2. 打开新的运行记录，查看其状态、时间窗口、持续时间、发现数量及报告。
    3. 选择一个证据会话以打开精确的追踪记录。
    4. 返回审计页面以编辑设置、禁用计划，或查看历史运行记录。

    ![审计详情页面，包含已开启的发现、上次及下次运行状态、扫描窗口、上下文、立即运行控件以及排名发现。](/images/dashboard/audit-detail.png)
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits run checkout-reliability
    fp audits runs checkout-reliability --limit 10

    fp audits findings --audit checkout-reliability
    ```

## 运行前的准备

- 确认所选时间窗口内存在会话数据。
- 验证环境和代理过滤器设置。
- 检查参考上下文是否为最新。
- 确保目标描述的是故障模式，而非期望得出的结论。

## 审查运行结果

从运行状态、会话覆盖范围以及模型分析是否已执行开始审查。然后逐一检查每个发现的严重程度、描述、证据会话、支撑查询以及建议的预防路径。

使用发现状态来进行确认、静默、驳回、解决、重新开启或分配工作。即使发现被驳回，也应保留相关证据；它解释了做出该决定的原因。

## 解读空结果或延迟运行

| 运行状态 | 含义 | 处理方式 |
| --- | --- | --- |
| 分析已运行但产生零发现 | 在已配置的灵敏度下，所选证据不足以支持任何发现。 | 确认范围内包含具有代表性的会话，若目标或上下文描述不过于模糊，则将该结果视为健康状态。 |
| 模型分析被跳过或失败 | 运行完成但发现数为零，未执行智能体调查。确定性凭证和 PII 扫描仍会在运行统计中报告匹配数量，但不会创建发现。 | 修复分析服务或配置后重新运行。不要将空结果解读为该群体状态健康的证据。 |
| 模型分析已禁用 | 运行成功但发现数为零。确定性扫描不能替代模型分析，也不会开启发现。 | 启用模型分析，或直接禁用该审计，而非依赖一个无法产生发现的审计。 |
| 当前没有可用的分析容量 | 审计保持排队并重试，而不是跳过该群体。 | 等待容量释放或分散审计锚点。自托管操作员应扩展审计代理副本及对应的调度器容量。 |
| 重试窗口内容量持续不可用 | 运行以零发现放弃，并在电子邮件可用时发送失败通知。 | 检查审计集群是否已饱和或频繁重启。 |

当分析未运行时，`since_last` 审计会将该未分析的窗口保留至下次成功运行。现有发现不会被撤销，因为跳过分析并不能证明故障已消失。

## 理解失败通知

运行失败或模型分析步骤失败时，系统会使用审计配置的电子邮件收件人。如果审计没有配置电子邮件渠道，Failproof AI 会回退至组织的 `alerts.email_default_recipients` 设置，确保即使审计静默失败也有升级路径。

电子邮件功能必须在组织层面启用，且 SMTP 必须已配置，否则失败信息仅会被记录日志，无法发送邮件。运行失败不会移动审计的固定计划锚点。

每次运行还会为每个代理存储该次运行所使用的精确[代理上下文](/zh/audits/agent-contracts)作为合约快照。后续的编辑不会改变与早期运行一同记录的证据标准。

<Warning>
  不要直接根据未经验证的发现部署阻断策略。请打开引用的追踪记录，确认该规则能够区分不安全行为与正当工作。
</Warning>
