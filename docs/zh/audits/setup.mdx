审计质量取决于其范围。宽泛的请求（如"找出问题"）产生的结果远不如具体的故障问题有用。

## 配置审计

<Tabs>
  <Tab title="控制台">
    1. 前往 **Analyze → Audits → New audit**，输入名称和描述。名称在组织内唯一；描述记录你希望此审计捕获的内容。
    2. 在 **when it runs** 中设置执行频率和时间窗口。在 **what it reads** 中，通过环境、代理和要忽略的错误类型缩小范围——字段为空表示包含所有内容。在 **how it judges** 中设置敏感度和每次运行的发现数量。
    3. 在 **what it knows** 中编写操作员简报并添加审计读取的页面。简报是模型在查看任何事件之前读取的背景信息：它是对此审计已有查找内容的补充，而非替代，也不作为发现的证据。
    4. 打开 **agents** 抽屉以添加或查看每个代理的上下文。它独立于审计保存，其标题显示已有上下文的代理数量。请参阅[代理上下文](/zh/audits/agent-contracts)。
    5. 选择通知渠道并点击 **create audit**。新审计默认启用，其首次运行将立即排队。

    ![新建审计表单，包含名称、描述、频率、时间窗口、环境和代理范围、忽略的错误、分析设置、简报、参考页面及通知渠道。](/images/dashboard/audit-new.png)

    **what it reads** 卡片中的 **agents** 是范围过滤器——它决定每次运行扫描哪些会话。代理的*用途*存储在单独的代理抽屉中。
  </Tab>
  <Tab title="CLI">
    ```bash
    fp audits create checkout-reliability \
      --description "Find checkout failures that agents do not recover from" \
      --scope '{"environments":["production"],"agent_ids":["checkout-agent"]}' \
      --schedule-interval-secs 86400 \
      --window-mode since_last \
      --sensitivity medium \
      --text-file ./checkout-audit-brief.txt \
      --url https://runbooks.example.com/checkout
    ```

    除名称外，所有字段均有服务器默认值，因此单独执行 `fp audits create nightly` 就已是一个有效的每日审计。已被占用的名称会在创建任何内容之前被提前拒绝。新审计默认启用，除非传入 `--disabled`，已启用审计的首次运行会立即排队。

    使用 `--file audit.json` 基于已保存的 JSON 定义，并在此基础上叠加命令行标志。当审计定义需要评审或纳入版本控制时，这是可复现的方式。

    请参阅完整的 [`fp audits create` 参考文档](/zh/reference/cloud-cli#audits)。
  </Tab>
</Tabs>

## 范围与默认值

数值设置在两端均会验证，因此超出范围的值属于使用错误，而非被拒绝的请求。

| 设置 | CLI 标志 | 可接受值 | 默认值 |
| --- | --- | --- | --- |
| 执行频率 | `--schedule-interval-secs` | 3600–604800（1小时至7天） | 86400（每天） |
| 计划锚点 | `--schedule-anchor` | ISO 8601 UTC；超过365天的锚点将被拒绝 | 下一个 09:00 UTC |
| 时间窗口 | `--window-mode` | `fixed`、`since_last` | `since_last` |
| 回溯时长 | `--lookback-window-secs` | 3600–7776000（1小时至90天） | 604800（7天） |
| 敏感度 | `--sensitivity` | `low`、`medium`、`high` | `medium` |
| 每次运行发现数 | `--top-k` | 1 或更多 | 50 |

锚点固定计划的相位：运行落在 `anchor + N * interval` 时刻，因此慢速运行或手动 **run now** 不会导致频率漂移。无论锚点如何，首次运行均在创建时立即排队。

## 简报与参考页面

表单以计数器形式显示两项限制，CLI 也强制执行相同的两项：

- 简报上限为 8,192 个字符（`--text`，或使用 `--text-file` 从文件读取——两者只能选其一，不可同时使用）。
- 审计最多引用五个页面，仅限公开的 `https://` 地址（`--url`，可重复使用）。

引用 URL 在保存时会进行验证。私有地址、回环地址和云元数据地址将被拒绝，被拒绝的 URL 会导致整个创建操作失败——不会留下半完成的审计。已接受的页面在后台获取，因此慢速站点不会阻塞保存操作。每次运行都会重新读取这些页面，当某个页面无法访问时会回退到已存储的快照，快照每周自动刷新。如果你知道某个页面已更新并希望在下次运行前获取最新内容，请使用 `fp audits context-refresh <name>`。

请在创建请求时同时提交简报和 URL，而不是在第二次调用中提交。新启用的审计在其记录提交的瞬间即开始计时，因此之后写入的上下文可能被调度器抢先，导致首次运行——也就是你正在关注的那次运行——错过这些上下文。之后可使用 `fp audits context-set <name>` 进行修改，该命令仅替换你指定的部分，另一部分保持不变。

<Tip>
  从一个已知失败的会话和几个正常会话开始。这为审计提供了一个正例和一组对比样本。
</Tip>

<Info>
  审计上下文作为独立资源存储。定义端点拒绝在更新时写入上下文，因此对审计进行普通的无关编辑绝不会覆盖简报或参考页面。
</Info>
