failproofai 内置 39 个策略，覆盖常见 Agent 故障模式。每个策略在特定 hook 事件类型和工具名称上触发。19 个策略支持参数，无需编写代码即可调整行为。5 个工作流策略在 Claude 停止前强制执行 提交 → 推送 → PR → CI 流水线。

---

## 概览

策略按类别分组：

| 类别 | 策略 | Hook 类型 |
|----------|----------|-----------|
| [危险命令](#dangerous-commands) | block-sudo, block-rm-rf, block-curl-pipe-sh, block-failproofai-commands, block-self-pause | PreToolUse |
| [基础设施命令](#infra-commands) | block-kubectl, block-terraform, block-aws-cli, block-gcloud, block-az-cli, block-helm, block-gh-pipeline | PreToolUse |
| [密钥（净化器）](#secrets-sanitizers) | sanitize-jwt, sanitize-api-keys, sanitize-connection-strings, sanitize-private-key-content, sanitize-bearer-tokens | PostToolUse |
| [环境](#environment) | block-env-files, protect-env-vars | PreToolUse |
| [文件访问](#file-access) | block-read-outside-cwd, block-secrets-write | PreToolUse |
| [Git](#git) | block-push-master, block-work-on-main, block-force-push, warn-git-amend, warn-git-stash-drop, warn-all-files-staged | PreToolUse |
| [数据库](#database) | warn-destructive-sql, warn-schema-alteration | PreToolUse |
| [警告](#warnings) | warn-large-file-write, warn-package-publish, warn-background-process, warn-global-package-install | PreToolUse |
| [包管理器](#package-managers) | prefer-package-manager | PreToolUse |
| [工作流](#workflow) | require-commit-before-stop, require-push-before-stop, require-pr-before-stop, require-no-conflicts-before-stop, require-ci-green-before-stop | Stop |

- **`block-`** — 阻止 Agent 继续执行。
- **`warn-`** — 向 Agent 提供额外上下文，使其能够自我纠正。
- **`sanitize-`** — 在 Agent 看到工具输出之前清除其中的敏感数据。

### 命名空间

每个策略都位于 `<namespace>/<name>` 插槽中。内置策略属于 **`failproofai/`** 命名空间，例如 `failproofai/sanitize-jwt`。命名空间可防止在加载具有相似短名称的自定义或第三方策略时发生冲突。

在配置中，可以使用短名称或完整限定名称引用内置策略，两种形式解析到同一策略：

```json
{
  "enabledPolicies": [
    "sanitize-jwt",
    "failproofai/block-rm-rf"
  ]
}
```

如果名称中不含 `/`，failproofai 将其视为属于默认命名空间 `failproofai`。已包含 `/` 的名称（如 `myorg/foo`、`custom/my-hook`）保持不变。
- **`require-`** — 阻止 Stop 事件，直到满足条件。

---

<Tip>
每个策略在 `policyParams` 中都支持可选的 `hint` 字段。该提示会附加到 Claude 看到的 deny 或 instruct 消息中，提供可操作的指导，无需修改策略代码。适用于内置、自定义和约定策略。详情请参阅[配置 → hint](/zh/configuration#hint-cross-cutting)。
</Tip>

## 危险命令

防止 Agent 执行难以撤销或可能损坏宿主系统的操作。

### `block-sudo`

**事件：** PreToolUse (Bash)
**默认：** 拒绝任何 `sudo` 或 `doas` 命令。

阻止在**命令位置**运行提权二进制文件的命令。匹配是结构化的而非文本化的：命令会像 shell 那样拆分成段，前缀赋值（`FOO=bar`）、重定向，以及带有标志的运行器（`env`、`nohup`、`timeout`、`xargs`、`sh -c` 等）都会被剥离，最终的二进制文件通过**basename** 进行比较。因此 `/usr/bin/sudo`、`env sudo`、`timeout 5 sudo`、`"sudo"`、`\sudo` 和 `bash -c "sudo …"` 都会被拒绝，`doas` 也被视为不同名称下的相同能力。

由于它锚定于命令位置而非单词在任意位置出现，因此**不会**对仅提及该词的命令触发——`grep -r sudo /etc`、`cat /etc/sudoers`、`git commit -m "fix sudo handling"` 或包含该词的 `grep` 交替表达式均可正常运行。

<Warning>
这只是阻止了明显的尝试，并未封闭整个攻击面。能够运行任意 shell 的 Agent 仍可通过间接方式达到提权目的——通过变量（`S=sudo; $S …`）、base64 解码管道或磁盘上的包装脚本——因为单个命令字符串的检查无法追踪这些路径。请将此视为防止误操作和随意提权的护栏，而非针对恶意 Agent 的安全边界。真正的边界必须在 shell 以下层面强制执行。
</Warning>

**参数：**

| 参数 | 类型 | 默认值 | 描述 |
|-------|------|---------|-------------|
| `allowPatterns` | `string[]` | `[]` | 允许的精确命令前缀。每个条目与解析后的 argv 令牌进行匹配。 |

**示例：**

```json
{
  "policyParams": {
    "block-sudo": {
      "allowPatterns": ["sudo systemctl status", "sudo journalctl"]
    }
  }
}
```

使用此配置，`sudo systemctl status nginx` 被允许，但 `sudo rm /etc/hosts` 被拒绝。

<Note>
模式匹配的是解析后的令牌，而非原始命令字符串。这可防止通过附加 shell 运算符绕过（例如 `sudo systemctl status x; rm -rf /` 不会匹配 `sudo systemctl status *`）。
</Note>

### `block-failproofai-commands`

**事件：** PreToolUse (Bash)
**默认：** 拒绝会卸载或禁用 failproofai 本身的命令（如 `npm uninstall failproofai`、`failproofai policies --uninstall`）。

无参数。

---

### `block-self-pause`

**事件：** PreToolUse (Bash)
**默认：** 拒绝 `failproofai config --pause`，该命令会暂停会话的策略执行。暂停是人工决策——能够运行此命令的 Agent 可以用一条命令关闭所有其他策略。

比 [`block-failproofai-commands`](#block-failproofai-commands) 更窄，并非后者的覆盖范围：该策略锚定于命令边界，因此 `npx -y failproofai config --pause` 不会匹配它；又因范围较广，它通常会被关闭以允许 Agent 运行 `failproofai audit`。`--resume` 和 `--status` 被允许——两者都不会移除策略执行。

这只是阻止了直接尝试，而非整个攻击面：Agent 仍可通过别名或包装脚本达到相同状态。彻底封闭需要让暂停操作完全无法通过工具调用触达。

无参数。

## 基础设施命令

阻止编码 Agent 运行基础设施 CLI 或触发 CI/CD 流水线。此类别中的所有策略均为**按需启用**（`defaultEnabled: false`）——合法需要调用 `kubectl`、`terraform` 等的 Agent 不会受到干扰，除非您启用该策略。启用后，被匹配 CLI 的所有调用都将被拒绝，除非命令与 `allowPatterns` 中的条目匹配。

模式语法与 [`block-sudo`](#block-sudo) 相同：令牌与解析后的 argv 匹配，`*` 是单个令牌的通配符，任何包含独立 shell 运算符（`&&`、`||`、`|`、`;`）或嵌入 shell 元字符的令牌的命令，在白名单匹配前会被拒绝，以防注入绕过。

### `block-kubectl`

**事件：** PreToolUse (Bash)
**默认：** 拒绝任何 `kubectl` 调用。

**参数：**

| 参数 | 类型 | 默认值 | 描述 |
|-------|------|---------|-------------|
| `allowPatterns` | `string[]` | `[]` | 允许的 kubectl 命令前缀。 |

**示例：**

```json
{
  "policyParams": {
    "block-kubectl": {
      "allowPatterns": ["kubectl get *", "kubectl describe *", "kubectl logs *"]
    }
  }
}
```

使用此配置，`kubectl get pods` 被允许，但 `kubectl apply -f deploy.yaml` 被拒绝。

### `block-gh-pipeline`

**事件：** PreToolUse (Bash)
**默认：** 拒绝以下会改变状态或触发流水线的 `gh` CLI 子命令：

- `gh workflow run`、`gh workflow enable`、`gh workflow disable`
- `gh run rerun`、`gh run cancel`
- `gh pr merge`
- `gh release create`、`gh release delete`
- `gh cache delete`
- `gh secret set`、`gh secret delete`

| `allowPatterns` | `string[]` | `[]` | 即使原本会被拒绝，也允许的特定脚本调用。 |

**示例：**

```json
{
  "policyParams": {
    "block-gh-pipeline": {
      "allowPatterns": ["gh run rerun *"]
    }
  }
}
```

## 密钥（净化器）

防止 Agent 将凭证泄露到其上下文或输出中。净化器策略在 **PostToolUse** 事件上触发。当 Claude 运行 Bash 命令、读取文件或调用任何工具时，这些策略会在输出返回给 Claude 之前检查输出内容。如果检测到密钥模式，策略会返回拒绝决定，阻止输出被传回。

### `sanitize-jwt`

**事件：** PostToolUse（所有工具）
**默认：** 编辑 JWT 令牌（以 `.` 分隔的三个 base64url 段）。

无参数。

---

### `sanitize-api-keys`

**事件：** PostToolUse（所有工具）
**默认：** 编辑常见 API 密钥格式：Anthropic（`sk-ant-`）、OpenAI（`sk-`）、GitHub PAT（`ghp_`）、AWS 访问密钥（`AKIA`）、Stripe 密钥（`sk_live_`、`sk_test_`）和 Google API 密钥（`AIza`）。

**参数：**

| 参数 | 类型 | 默认值 | 描述 |
|-------|------|---------|-------------|
| `additionalPatterns` | `{ regex: string; label: string }[]` | `[]` | 需要视为密钥的额外正则表达式模式。 |

**示例：**

```json
{
  "policyParams": {
    "sanitize-api-keys": {
      "additionalPatterns": [
        { "regex": "myco_[A-Za-z0-9]{32}", "label": "MyCo internal API key" },
        { "regex": "pat_[0-9a-f]{40}", "label": "Internal PAT" }
      ]
    }
  }
}
```

---

### `sanitize-connection-strings`

**事件：** PostToolUse（所有工具）
**默认：** 编辑包含嵌入凭证的数据库连接字符串（如 `postgresql://user:password@host/db`）。

无参数。

---

### `sanitize-private-key-content`

**事件：** PostToolUse（所有工具）
**默认：** 编辑 PEM 块（`-----BEGIN PRIVATE KEY-----`、`-----BEGIN RSA PRIVATE KEY-----` 等）。

无参数。

---

### `sanitize-bearer-tokens`

**事件：** PostToolUse（所有工具）
**默认：** 编辑令牌长度达到或超过 20 个字符的 `Authorization: Bearer <token>` 头部。

无参数。

## 环境

防止 Agent 读取或暴露敏感的环境配置。

### `block-env-files`

**事件：** PreToolUse (Bash, Read)
**默认：** 拒绝通过 `cat .env`、以 `.env` 为文件路径的 `Read` 工具调用等方式读取 `.env` 文件。

不阻止 `.envrc` 或其他与环境相关的文件——仅阻止名称恰好为 `.env` 的文件。

无参数。

---

### `protect-env-vars`

**事件：** PreToolUse (Bash)
**默认：** 拒绝打印环境变量的命令：`printenv`、`env`、`echo $VAR`。

无参数。

## 文件访问

使 Agent 在项目边界内工作，远离敏感文件。

### `block-read-outside-cwd`

**事件：** PreToolUse (Read, Bash)
**默认：** 拒绝读取项目根目录之外的文件。边界为 `CLAUDE_PROJECT_DIR`（由 Claude Code 在每个会话开始时设置一次），当该变量未设置时回退到会话的当前工作目录。使用项目根目录而非实时 `cwd` 意味着即使 Claude `cd` 进入子目录，边界也保持稳定。

**参数：**

| 参数 | 类型 | 默认值 | 描述 |
|-------|------|---------|-------------|
| `allowPaths` | `string[]` | `[]` | 即使位于项目根目录之外也允许访问的绝对路径前缀。 |

**示例：**

```json
{
  "policyParams": {
    "block-read-outside-cwd": {
      "allowPaths": ["/shared/data", "/opt/company/config"]
    }
  }
}
```

---

### `block-secrets-write`

**事件：** PreToolUse (Write, Edit)
**默认：** 拒绝向通常用于私钥和证书的文件写入：`id_rsa`、`id_ed25519`、`*.key`、`*.pem`、`*.p12`、`*.pfx`。

**参数：**

| 参数 | 类型 | 默认值 | 描述 |
|-------|------|---------|-------------|
| `additionalPatterns` | `string[]` | `[]` | 需要阻止的额外文件名模式（glob 风格）。 |

**示例：**

```json
{
  "policyParams": {
    "block-secrets-write": {
      "additionalPatterns": [".token", ".secret"]
    }
  }
}
```

## Git

防止意外推送、强制推送和难以撤销的分支误操作。

### `block-push-master`

**事件：** PreToolUse (Bash)
**默认：** 拒绝 `git push origin main` 和 `git push origin master`。

**参数：**

| 参数 | 类型 | 默认值 | 描述 |
|-------|------|---------|-------------|
| `protectedBranches` | `string[]` | `["main", "master"]` | 不允许直接推送的分支名称。 |

**示例：**

```json
{
  "policyParams": {
    "block-push-master": {
      "protectedBranches": ["main", "master", "release", "prod"]
    }
  }
}
```

<Tip>
若要允许推送到所有分支（即在不从 `enabledPolicies` 中移除此策略的情况下有效禁用它），将 `protectedBranches` 设为 `[]`。
</Tip>

---

### `block-work-on-main`

**事件：** PreToolUse (Bash)
**默认：** 当工作树位于 `main` 或 `master` 分支时，拒绝 `git commit`、`git merge`、`git rebase` 和 `git cherry-pick`。分支创建和切换（`git checkout`、`git checkout -b`、`git switch`、`git switch -c`）不受影响。

**参数：**

| 参数 | 类型 | 默认值 | 描述 |
|-------|------|---------|-------------|
| `protectedBranches` | `string[]` | `["main", "master"]` | 禁止执行 commit/merge/rebase/cherry-pick 的分支名称。 |

---

### `block-force-push`

**事件：** PreToolUse (Bash)
**默认：** 拒绝 `git push --force` 和 `git push -f`。

无策略专属参数。使用跨切面的 [`hint`](/zh/configuration#hint-cross-cutting) 建议替代方案：

```json
{
  "policyParams": {
    "block-force-push": {
      "hint": "Create a new branch from your current HEAD (e.g. `git checkout -b <new-branch>`) and push that instead."
    }
  }
}
```

---

**事件：** PreToolUse (Bash)
**默认：** 在运行 `git commit --amend` 时指示 Claude 谨慎操作。不阻止该命令。

无参数。

---

**事件：** PreToolUse (Bash)
**默认：** 在运行 `git stash drop` 之前指示 Claude 确认。不阻止该命令。

无参数。

---

### `warn-all-files-staged`

**事件：** PreToolUse (Bash)
**默认：** 在运行 `git add -A` 或 `git add .` 时指示 Claude 审查其暂存内容。不阻止该命令。

无参数。

## 警告

在可能存在风险但非破坏性的操作之前，为 Agent 提供额外上下文。

### `warn-large-file-write`

**事件：** PreToolUse (Write)
**默认：** 在写入超过 1024 KB 的文件之前，指示 Claude 确认。

**参数：**

| 参数 | 类型 | 默认值 | 描述 |
|-------|------|---------|-------------|
| `thresholdKb` | `number` | `1024` | 触发警告的文件大小阈值（单位：KB）。 |

**示例：**

```json
{
  "policyParams": {
    "warn-large-file-write": {
      "thresholdKb": 256
    }
  }
}
```

<Note>

</Note>

## 包管理器

强制 Agent 只能使用允许的包管理器。

### `prefer-package-manager`

**事件：** PreToolUse (Bash)
**默认：** 禁用。启用后，阻止不在 `allowed` 列表中的任何包管理器命令，并告知 Claude 使用允许的管理器重写命令。

可检测：pip、pip3、python -m pip、npm、npx、yarn、pnpm、pnpx、bun、bunx、uv、poetry、pipenv、conda、cargo。

| 参数 | 类型 | 默认值 | 描述 |
|-----------|------|---------|-------------|
| `allowed` | string[] | `[]` | 允许的包管理器名称。任何检测到的不在此列表中的管理器都将被阻止。为空时，策略为空操作。 |
| `blocked` | string[] | `[]` | 在内置列表之外额外阻止的管理器名称（如 `['pdm', 'pipx']`）。 |

内置阻止列表包含：pip、pip3、npm、npx、yarn、pnpm、pnpx、bun、bunx、uv、poetry、pipenv、conda、cargo。使用 `blocked` 追加不在此列表中的管理器。

**配置示例：**

```json
{
  "enabledPolicies": ["prefer-package-manager"],
  "policyParams": {
    "prefer-package-manager": {
      "allowed": ["uv", "bun"],
      "blocked": ["pdm", "pipx"]
    }
  }
}
```

使用此配置，`pip install flask` 和 `pdm install flask` 都会被拒绝，并告知 Claude 改用 `uv` 或 `bun`。`uv pip install flask` 之类的命令被允许，因为 `uv` 在白名单中且优先检查。

## 工作流

强制执行规范的会话结束工作流。这些策略在 **Stop** 事件上触发，阻止 Agent 停止，直到每个条件都满足。它们遵循自然的依赖链：提交 → 推送 → PR → CI。如果某个策略拒绝，链中后续策略将被跳过（拒绝短路）。

所有工作流策略均为**失败开放**：如果所需工具不可用（如未安装 `gh`、无 git 远程），策略允许通过，并附上解释跳过检查原因的信息消息。

### 各 CLI 的 Stop 语义

Stop 执行在六个受支持的 CLI 中的表现略有不同，因为每个 CLI 都公开了不同的"Agent 完成" hook 合约。**结果**是相同的——Agent 在工作流门控失败时无法停止——但**机制**不同。下表概述了差异；只有 Pi 存在值得在启用 `require-*-before-stop` 策略前了解的用户可见行为。

| CLI | 门控触发时机 | 您看到的情况 |
|---|---|---|
| Claude Code | 同一 Agent 循环，立即触发 | Claude 继续工作——修复问题，然后再次尝试完成。对您不可见任何中断。 |
| Codex | 同一 Agent 循环，立即触发 | 与 Claude 相同。 |
| GitHub Copilot CLI | 同一 Agent 循环，立即触发 | 与 Claude 相同（使用 Copilot 的 `{decision:"block", reason}` 重试通道——经 Copilot CLI 1.0.41 实证验证）。 |
| Cursor Agent | 同一 Agent 循环，立即触发 | 与 Claude 相同（使用 Cursor 的 `{followup_message}` 通道——上限为 `loop_limit`，默认 5 次重试）。 |
| OpenCode | 同一 Agent 循环，立即触发 | 与 Claude 相同（使用 OpenCode 的 `client.session.prompt(...)` SDK 调用，通过 `hookSpecificOutput.additionalContext` 路由）。 |
| **Pi (pi-coding-agent)** | **下一个用户轮次** | **Pi 在门控触发时会明显停止**——其 Agent 循环退出，返回提示符。门控在您下次提交提示时触发：failproofai 在该轮次的系统提示前附加一条 `MANDATORY ACTION REQUIRED` 指令，要求 LLM 在执行您的请求之前完成工作流步骤（提交、推送等）。 |

<Note>
**Pi 的限制。** Pi 的 `AgentEndEvent`（上游等价于 Claude 的 `Stop` hook）没有 Result 类型——触发时，Pi 的 Agent 循环已经退出。Pi 无法像 Claude / Copilot / Cursor / OpenCode 那样被强制重试同一循环。failproofai 将门控转移到 Pi 的 `before_agent_start` 事件（在下一个用户提示后触发），使工作流检查仍然生效，只是在下一轮次而非当前轮次执行。

**实际影响：**

- Pi 停止后，拒绝原因以 Pi 会话 id 为键保存在内存中。您在同一 Pi 进程中提交的下一个提示会消耗它：LLM 在系统提示顶部看到 `MANDATORY ACTION REQUIRED` 指令，执行提交（或推送/创建 PR/等待 CI），然后才继续您的请求。捕获的拒绝原因是一次性的——消耗后门控清除。
- 门控受 Pi 进程生命周期约束。如果您在两次轮次之间 `Ctrl+C` Pi 或退出，内存条目随进程一起丢弃，门控被绕过。Claude、Copilot、Cursor 和 OpenCode 有相同的约束（终止 Agent 则门控被绕过）——Pi 只是让这一点更明显，因为 Agent 在门控触发前就明显退出了。
- 待处理的拒绝也会在 `session_shutdown` 时因任何原因（`new` / `resume` / `fork` / `quit`）被清除，因此来自先前会话的过时门控不会泄漏到同一 Pi 进程中启动的新会话。

如果您需要 Claude 风格的同循环重试，请在其他五个受支持的 CLI 下运行 `Stop` 策略。我们正在跟踪 Pi 上游，等待 `AgentEndEvent` 上的未来 Result 类型以弥合这一差距。
</Note>

### `require-no-conflicts-before-stop`

**事件：** Stop
**默认：** 当当前分支无法干净地合并到基础分支时，拒绝停止。策略首先确认 GitHub 上该分支存在 `OPEN` 状态的 PR——没有 PR 则没有合并目标可强制执行，整个策略短路为允许。确认存在 `OPEN` PR 后，运行两个独立探测：

1. **本地** — `git merge-tree --write-tree --name-only origin/<baseBranch> HEAD`。发生冲突时，拒绝消息会列出冲突文件，使 Claude 准确知道需要解决什么。
2. **GitHub** — 复用在预检中已获取的 `gh pr view --json mergeable,state` 结果。可捕获因本地 `origin/<baseBranch>` 过时而遗漏的冲突（例如有人在上次 fetch 后将冲突的 PR 合并到 `main`）。`CONFLICTING` 结果拒绝。`UNKNOWN` 结果也拒绝，并指示 Claude 等待约 10 秒后重新检查再尝试停止——这可防止 GitHub 重新计算时出现假阴性。

以下情况整体跳过（允许）：未安装 `gh`、该分支不存在 PR、PR 状态不为 `OPEN`（如 `MERGED`、`CLOSED`），或 `gh pr view` 返回无法解析的输出。当本地缺少 `origin/<baseBranch>` 或没有超前于基础的提交时也失败开放——这些第一层回退仍会在允许前查询缓存的 PR 可合并性。

**参数：**

| 参数 | 类型 | 默认值 | 描述 |
|-------|------|---------|-------------|
| `baseBranch` | `string` | `"main"` | 用于检查冲突的基础分支。 |

<Note>
此策略需要 GitHub CLI（`gh`）。策略使用 `gh pr view` 在运行任何冲突探测之前确认存在 `OPEN` PR——没有 `gh` 则策略短路为允许。使用具有 `repo` 范围（用于读取拉取请求）的个人访问令牌运行 `gh auth login`。
</Note>

---

### `require-ci-green-before-stop`

**事件：** Stop
**默认：** 当当前分支的 CI 检查失败或仍在运行时，拒绝停止。同时检查 GitHub Actions 工作流运行和第三方机器人检查（如 CodeRabbit、SonarCloud、Codecov）。将 `skipped`、`cancelled` 和 `neutral` 结论视为非失败（后者涵盖例如外部贡献者 PR 上的 Socket Security 告警，其中应用程序有意报告 neutral 而非 success/failure）。所有检查通过时，返回信息消息。

无参数。

<Note>
此策略需要安装并认证 [GitHub CLI](https://cli.github.com/)（`gh`）。
使用具有 `repo` 范围（用于读取 Actions 工作流运行和 Checks API）的个人访问令牌运行 `gh auth login`。如果未安装或未认证 `gh`，策略失败开放并向 Claude 报告原因。
</Note>

## 禁用单个策略

从配置的 `enabledPolicies` 中移除特定策略，或在控制台的 Policies 选项卡中将其关闭。

```json
{
  "enabledPolicies": [
    "block-rm-rf",
    "sanitize-api-keys"
  ]
}
```

未在 `enabledPolicies` 中列出的策略不会运行，即使存在对应的 `policyParams` 条目。
