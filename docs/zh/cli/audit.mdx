审计功能会将您过去的智能体 CLI 记录重新通过 failproofai 的策略引擎进行回放，并在 **`/audit` 仪表盘页面**生成一份可共享的可视化报告 —— 包含您智能体的原型类型、0–100 的评分，以及哪些策略本可拦截哪些行为。

## 运行方式

共有三种方式 —— 均会跳转到同一份 `/audit` 报告。

<CodeGroup>

```bash npx (无需安装)
npx -y failproofai audit
```

```bash failproofai audit
failproofai audit
```

```bash failproofai (仪表盘)
failproofai
```

</CodeGroup>

<Tip>
  运行 `failproofai audit -h`（或 `--help`）查看使用说明。审计**完全离线**运行
  —— 无需账号或网络 —— 仪表盘将持续运行，直到您按 `Ctrl+C` 停止。

仪表盘会扫描本机上过去的智能体 CLI 记录（Claude Code、Codex、Copilot、Cursor、OpenCode、Pi），并报告智能体执行了多少 failproofai 旨在阻止的操作 —— 包括环境变量检查、强制推送、冗余的 `cd <cwd>` 前缀、sleep 轮询循环、重新读取刚编辑过的文件等。

对于每份记录，所有工具调用事件都会通过 39 个内置策略进行回放，**同时**还会经过 8 个仅用于审计的探测器，这些探测器可捕获运行时策略尚未覆盖的模式。计数按策略/探测器在所有会话中进行汇总。

## 报告内容

`/audit` 页面是一张单屏可共享的**海报**，后跟四个折叠区块：

1. **海报** —— 一眼了解您智能体的特征：其**原型**（共 8 种 —— `optimist`、`cowboy`、`explorer`、`goldfish`、`paranoid architect`、`precision builder`、`hammer`、`ghost`）、人设关键词、该原型的稀有度，以及带层级标识的 **0–100 评分**（从 `S` 到 `bottom tier`）。专为分享设计 —— 可发布到 X 或 LinkedIn，或下载为 PNG。
2. **`// strengths`** —— 您的智能体已做得不错的方面，以扫描结果的真实数据呈现（例如：clean-tool-call 百分比、`0` 次 push-to-main 尝试），仅在相关策略记录清白时显示。
3. **`// quirks`** —— 已发生的问题：一张按排名列出的行为表，显示 failproofai 本可拦截的操作 —— *发生时间*、*具体行为*（以及本可阻止它的内置策略）、*严重程度*，以及*出现频率*（`new` / `recurring` / `N× seen`）。
4. **`// how to improve`** —— 建议修复清单：每行对应一条策略，附带可直接复制的 `failproofai policy add <slug>` 命令，以及一个**全部安装**按钮，可一次性启用所有建议，并显示执行后的**预计得分**。
5. **`// come back better`** —— 养成习惯：设置重新审计的邮件**提醒**（`3d` / `7d` / `14d` / `30d`）或立即重新审计，并**邀请好友**运行他们自己的审计（由 failproof.ai 发送，抄送给您）。提醒和邀请功能需要登录。

## 定时审计

如果您运行了 **failproofaid 守护进程**（请参阅 [`failproofai config`](/zh/cli/install-policies)），
它可以按计划自动重新运行审计并在后台刷新 `/audit` 报告。该功能**默认关闭**，因为扫描会读取本机上每个智能体会话记录的*内容* —— 在您主动开启之前，不会有任何定时扫描。

在 `~/.failproofai/config.json` 中开启此功能 —— 在文件现有内容旁添加 `audit` 键：

```json
{
  "audit": {
    "auto": true,
    "interval_days": 7
  }
}
```

| 键 | 含义 |
|---|---|
| `auto` | `true` 启用定时扫描。其他任何值 —— 缺失、`false`、`"yes"` —— 均为关闭。 |
| `interval_days` | 扫描间隔天数。限制在 1–90 之间；`0`、负数或非数字值将回退为 `7`。 |

- 计划基于**挂钟时间**，因此在休眠和重启后仍然有效：如果笔记本在计划时间内处于睡眠状态，唤醒后**只运行一次**，不会产生积压。
- 每次运行都是独立的低优先级（`nice 19`）进程 —— 永远不会占用守护进程的 hook 路径，该路径始终保持空闲以响应工具调用。
- 如果 `failproofai audit` 或仪表盘的重新运行已在进行中，本次扫描将被跳过；随后会重试，而非视为失败。
- 进度写入 `~/.failproofai/state/audit-schedule.json`（上次运行时间、下次计划时间）。该文件由守护进程管理 —— 请在 `config.json` 中修改频率。

<Note>
如果您在较旧版本的 failproofai 配置的机器上启用了此功能，请运行一次
`failproofai config`。守护进程的服务定义需要一个额外条目才能启动 CLI，而该命令会完成这项刷新。
</Note>

## 仅审计探测器

这些探测器用于检测尚未在实时运行中强制执行的"低效行为"模式。它们仅在审计期间运行，永远不会阻止实时工具调用。

| 探测器 | 计数内容 |
|---|---|
| `redundant-cd-cwd` | 以 `cd <cwd> && …` 开头的 Bash 命令，尽管命令已在 `cwd` 中运行。 |
| `prefer-edit-over-read-cat` | 对单个源文件使用 `cat`/`head`/`tail`/`less`/`more` —— 应使用 `Read` 工具。 |
| `prefer-edit-over-sed-awk` | 使用 `sed -i` / `awk … > file` 进行原地编辑 —— 应使用 `Edit` 工具。 |
| `prefer-write-over-heredoc` | 使用 Heredoc / 多行 `echo > file` 写入文件 —— 应使用 `Write` 工具。 |
| `sleep-polling-loop` | 长时间 `sleep N`（≥ 30s）或 `while …; sleep …; done` 轮询循环。 |
| `find-from-root` | `find /`、`find /home`、`find /usr` 等 —— 应将范围限定为 `cwd`。 |
| `git-commit-no-verify` | `git commit … --no-verify` / `-n`，跳过钩子。 |
| `reread-after-edit` | 在同一会话中对刚刚经过 `Edit`/`Write` 的文件执行 `Read`。 |

## 缓存机制

- **逐记录缓存**位于 `~/.failproofai/cache/audit/<sha1>.json`，以 `(mtime, size, engineVersion, detectorVersion)` 为键 —— 当记录或策略/探测器代码发生变更时自动失效。每个条目还存储 `cachedAt` 时间戳作为 **TTL 元数据**（不属于缓存键的一部分）；读取时超过 **7 天**的条目将被拒绝，以防长期缓存结果超出探测器意图的有效期。
- **整体结果缓存**位于 `~/.failproofai/audit-dashboard.json`（权限 0600）。允许仪表盘在导航时立即渲染，无需重新运行。同样在读取时超过 **7 天 TTL** 后被拒绝 —— `/audit` 随后会回退到空状态并提示重新运行。点击报告底部附近的 `[ re-audit now ]` 可刷新 —— 重新审计会发送 `noCache: true`，因此会绕过逐记录缓存并重新扫描所有记录，而不是返回缓存结果；运行过程通过顶部固定状态条流式显示进度，成功后原地替换结果（无需刷新页面；重新审计失败时保留之前的报告）。

## 注意事项

- **无状态修改。** 审计以只读模式回放。`warn-repeated-tool-calls` 会被跳过，否则其每会话附加文件将被修改。
- **跳过工作流策略。** `require-*-before-stop` 策略仅在 `Stop` 事件时触发，并通过 `execSync` 检查实时 git 状态 —— 这类策略对历史记录没有有意义的"如果在 2025 年会发生什么"解读，因此不出现在审计计数中。
- **跳过自定义策略。** 用户提供的自定义钩子不会被回放（它们可能自原始会话以来已发生变更）。
