---
title: 迁移主目录
description: "将 ~/.failproofai 升级到当前版本所需的目录结构，并提前查看迁移计划"
---

```bash
failproofai migrate --dry-run   # 打印迁移计划，不做任何更改
failproofai migrate             # 执行迁移
```

大多数用户不需要手动执行此命令。它会在升级后首次运行任意命令时自动触发，[`failproofai update`](/zh/cli/update) 也会自动包含此步骤。仅在以下情况下才需要直接调用：希望在执行前预览迁移计划，或单独运行迁移流程。

## 基于目录结构版本，而非发布版本

`~/.failproofai/VERSION` 记录的是**目录结构**编号——代表目录的形态，而非写入该文件的发行版本号。迁移操作基于此编号进行，这使得跨越多个版本的迁移代价极低：

- npm 版本随每次发布而变化，两个目录结构版本之间可能相差数十个发布版本。
- 因此，若某台机器跳过了三十个发布版本，但**目录结构未发生变化**，则**不会执行任何**迁移，而不是执行三十次空操作。
- 若某台机器一次性跨越多个目录结构版本，则会按顺序依次执行每个步骤，每个步骤只需了解自身的两个端点。

这一设计非常重要，因为 npm 无法自动更新已安装的包。机器长时间停留在某个版本后一次性跨越多个目录结构版本，是常见情况，而非特殊情况。

## 演练模式

`--dry-run` 会打印完整的迁移链以及迁移前将被备份的文件，不做任何实际操作——不执行迁移、不创建备份、不写入记录：

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## 哪些内容会被迁移，哪些会被重建

主目录中的每个路径都声明了其所存储的数据类型，这决定了迁移时是否可以将其丢弃。规则如下：**可派生或可重新获取的数据可以丢弃；由您手动输入的内容、尚未投递的内容，以及标识机器身份的内容，都会被保留。**

| 保留内容 | 重建或重新获取的内容 |
|---|---|
| `config.json` — 设置项、`daemon.configured`、额外捕获路径 | 审计缓存 |
| `credentials.json` — 您的云端注册信息 | 云端管理的部署项（在下次轮询时重新获取并进行摘要验证） |
| `policies-config.json` — 您的策略选择与参数 | 守护进程临时状态 |
| `policies/` — 您自己的策略文件及其引用的辅助文件 | |
| `hook-activity/` — 仪表板读取的决策日志 | |
| 队列中尚未上传的待投递事件 | |
| `cursors/` — 采集器水位标记 | |
| `bin/` 中的守护进程二进制文件 | |

<Note>
  待投递事件会被保留而非丢弃，因为丢失是永久性的，而非短暂延迟：采集器的水位标记已经超过了队列中所有内容的位置，因此没有任何机制能再次读取转录文件中那段范围的数据。迁移完成后，系统还会通知守护进程立即投递队列中的内容，因此通常情况下不会有任何内容需要保留。
</Note>

**较新**版本写入 `config.json`、`credentials.json` 或 `policies-config.json` 中的键也会被保留，而不会被旧版本读取器丢弃。

## 迁移留下的记录

```
~/.failproofai/migrations/
  applied.json                 每个步骤一条记录：目录结构版本、CLI 版本、时间戳、耗时、结果
  backup-layout<n>/            执行第一个步骤前备份的不可替代文件副本
```

`applied.json` 是回答"这台机器究竟经历了什么"的依据——升级后出现异常时，这是最值得首先查看的文件。请在提交问题报告时附上此文件。

备份内容有意保持精简，而非复制整个目录：从设计上讲，迁移不再删除任何不可替代的内容，因此真正需要防范的是**步骤中的缺陷**，而这少数几个文件正是此类缺陷可能造成损害的地方。

## 步骤失败时的处理

迁移链在失败处停止。`VERSION` 仅在步骤成功完成后才会被更新，因此主目录仍保留旧的目录结构编号，下次执行命令时会重试——主目录永远不会因部分迁移成功而被标记为最新状态。失败的步骤会以 `"ok": false` 记录在 `applied.json` 中，备份文件保留在原来的位置。

## 较新的主目录会被拒绝，而非迁移

如果 `~/.failproofai/` 是由比当前运行版本**更新**的 failproofai 写入的，命令会停止并提示您进行升级。该数据本身没有问题，更新的 CLI 可以正常读取；向"旧"方向迁移并不存在，而重置它会破坏可恢复的数据。

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

守护进程遵循同样的规则：`failproofaid` 拒绝在其不支持的目录结构版本上启动，而不是读写已移动位置的路径。
