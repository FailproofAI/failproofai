---
title: 迁移主目录
description: "将 ~/.failproofai 升级至当前版本所需的目录结构，并可预览迁移计划"
---

```bash
failproofai migrate --dry-run   # 打印迁移计划，不做任何更改
failproofai migrate             # 执行迁移
```

大多数用户无需手动运行此命令。它会在升级后首次执行其他命令时自动运行，[`failproofai update`](/zh/cli/update) 也会自动包含此步骤。仅在以下情况下需要直接调用：想提前查看迁移计划，或单独执行迁移操作。

## 基于目录结构版本，而非软件版本

`~/.failproofai/VERSION` 记录的是**目录结构**编号——代表目录的形态，而非写入该文件的软件版本。迁移以该编号为依据，这使得跨越多个版本的迁移代价极低：

- npm 版本随每次发布而变化，两次目录结构变更之间可能有数十个版本。
- 因此，若某台机器跳过了三十个版本但**目录结构未发生变化**，则会执行**零次**迁移，而不是三十次空操作。
- 若某台机器一次性跨越多个目录结构版本，则会按顺序依次执行每个步骤，每个步骤只需了解自身的起止状态。

这一点至关重要，因为 npm 无法自动更新已安装的包。某台机器长期停留在某个版本后一次性跳过多个目录结构版本，是常见场景，而非特殊情况。

## 预演模式（dry run）

`--dry-run` 会打印完整的迁移链及迁移前将被备份的文件，且不做任何实际操作——不执行迁移、不创建备份、不写入迁移记录：

```
Layout 2 on disk; this build speaks 3.
1 step(s) would run:
  2 → 3  layout 2 → 3: carry config.toml and credentials.toml into JSON, move
         custom-policies/ back up into policies/, nest the policy config at the root

These would be copied to ~/.failproofai/migrations/backup-layout2 first:
  VERSION
  config.toml
  credentials.toml
```

## 哪些内容被保留，哪些内容被重建

主目录中的每个路径都声明了其所存储的数据类型，这决定了迁移是否可以丢弃该数据。规则如下：**可派生或可重新获取的数据可被丢弃；您手动输入的内容、尚未投递的内容，以及标识机器身份的内容均会被保留。**

| 保留 | 重建或重新获取 |
|---|---|
| `config.json` —— 设置项、`daemon.configured`、额外的捕获路径 | 审计缓存 |
| `credentials.json` —— 您的云端注册信息 | 云端管理的部署项（在下次轮询时重新获取并进行摘要验证） |
| `policies-config.json` —— 您的策略选择与参数 | 守护进程的临时状态 |
| `policies/` —— 您自定义的策略文件及其引用的辅助文件 | |
| `hook-activity/` —— 仪表板读取的决策日志 | |
| 队列中尚未上传的待投递事件 | |
| `cursors/` —— 采集器的水位标记 | |
| `bin/` 目录中的守护进程二进制文件 | |

<Note>
  待投递事件会被保留而非丢弃，因为一旦丢失将是永久性损失，而非仅仅延迟：采集器的水位标记已推进到超过待发送队列中任何内容的位置，因此没有任何机制能再次读取转录记录的那段范围。迁移完成后还会通知守护进程立即投递队列中的内容，因此通常情况下不会有任何待保留的内容。
</Note>

**较新**版本写入 `config.json`、`credentials.json` 或 `policies-config.json` 的键也会被保留，而不会被旧版本读取器丢弃。

## 迁移留下的记录

```
~/.failproofai/migrations/
  applied.json                 每个步骤一条记录：目录结构版本、CLI 版本、时间戳、耗时、执行结果
  backup-layout<n>/            第一个步骤执行前备份的不可替代文件副本
```

`applied.json` 是回答「这台机器究竟经历了什么」的依据——升级后出现异常时，这是首先值得查看的内容。提交 bug 报告时请附上此文件。

备份内容刻意保持精简，而非整个目录的完整副本：迁移设计上不会删除任何不可替代的内容，因此真正需要防范的是**某个步骤存在缺陷**，而这几个文件正是此类缺陷可能造成损害的地方。

## 如果某个步骤失败

迁移链会在该步骤处停止。`VERSION` 只有在步骤成功完成后才会更新，因此主目录仍保留旧的目录结构标记，下次执行命令时会重试——主目录永远不会基于部分完成的迁移被标记为最新状态。该步骤会以 `"ok": false` 记录在 `applied.json` 中，备份文件保留在原位置。

## 更新版本的主目录会被拒绝，而非被迁移

如果 `~/.failproofai/` 是由**比当前运行版本更新**的 failproofai 写入的，命令会停止并提示您进行升级，而非执行迁移。该数据本身完好无损，更新的 CLI 可以正常读取；不存在从更新版本「向前迁移」到旧版本的概念，而重置数据将会销毁本可恢复的内容。

```
This machine's failproofai directory was written by a newer version (layout 4;
this build speaks 3). Upgrade rather than migrate:
  npm install -g failproofai@latest
```

守护进程遵循相同规则：`failproofaid` 在遇到无法识别的目录结构版本时会拒绝启动，而不是去读写那些已经移动过的路径。
