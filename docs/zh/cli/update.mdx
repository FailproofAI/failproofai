---

```bash
npm install -g failproofai@latest && failproofai update
```

这就是完整的升级流程。`npm` 替换 CLI；`failproofai update` 完成其余工作。

## 为什么需要第二个命令

`npm install -g` 只替换一样东西——CLI。failproofai 安装中另外两个组件有意存放在包之外，npm 运行时两者都不会移动：

- **`~/.failproofai/`**，存储你的设置、云端注册、策略选择和历史记录。新版本可能对其结构有所调整，而这种重组必须由同时了解新旧结构的代码来完成。
- **`failproofaid` 守护进程二进制文件**，位于 `~/.failproofai/bin/failproofaid-<version>`。它刻意不放在 `node_modules` 中：如果升级时替换了正在运行的服务所使用的文件，会导致活跃的守护进程指向一个由不同源码构建的二进制文件；而删除包时又会将其从服务底层删除，进而导致服务在每次启动时崩溃循环。

因此，单独执行 `npm install -g` 后，CLI 是新的，但守护进程不是。`failproofaid` 拒绝在它不认识的主目录布局下启动——这是版本不匹配时的显式报错方式，而非静默失败——所以需要将两部分同步对齐。`failproofai update` 就是这个步骤。

## 它做了什么

<Steps>
  <Step title="运行所有待处理的布局迁移">
    读取 `~/.failproofai/VERSION` 中记录的布局版本，执行将其升级到当前版本所需的步骤。通常无需执行任何步骤——参见 [`failproofai migrate`](/zh/cli/migrate)。
  </Step>
  <Step title="将匹配的守护进程二进制文件就位">
    优先从 npm 已下载的平台包中获取（无需网络），否则从当前版本的发布资产中下载，使用前会进行 SHA-256 校验。
  </Step>
  <Step title="重启服务并确认其正常恢复">
    通过主动探测而非假设来确认——服务管理器在进程派生的瞬间就会报告其处于活跃状态，这与服务实际正常运行并不等同。
  </Step>
</Steps>

## 选项

| 标志 | 效果 |
|------|------|
| `--no-daemon` | 仅迁移主目录，守护进程保持当前版本不变。 |

<Warning>
  `--no-daemon` 会保留一个版本不匹配的守护进程。在配置为需要守护进程的机器上，如果守护进程无法响应，每个 hook 事件都会**失败关闭**——而拒绝在已迁移主目录下启动的守护进程将无法响应任何请求。建议让守护进程那半部分也一并运行更新。
</Warning>

## 如果出现问题

命令会以非零状态退出，并说明哪一半失败了。有两种情况值得了解：

- **某个迁移步骤未完成。** 主目录将保留*旧的*布局标记，以便下次命令重试——任何主目录都不会因部分迁移完成而被标记为当前版本。你的设置和注册信息的副本已在任何操作执行前保存至 `~/.failproofai/migrations/backup-layout<n>/`。
- **守护进程无法在无密码情况下重启。** 命令刻意使用 `sudo -n`，因此进度显示期间不会出现任何密码提示。命令会打印出需要你自行运行的具体命令行。

<Note>
  此处所有操作均不需要交互式设置向导。你的设置、云端注册和策略选择在升级后都会保留，因此已迁移的机器会与升级前执行完全相同的策略——这对于无人值守的机器尤为重要：CI 运行器、集群节点、无头网关等。
</Note>

## 自动化执行

`failproofai update` 是非交互式的，在没有任何可执行操作时运行也是安全的——它会报告"无需迁移"并以 0 退出。在配置脚本或 Dockerfile 中将其置于每次升级之后是预期的使用方式：

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

（在镜像构建中使用 `--no-daemon`，因为此时还没有需要重启的服务。）
