title: 升级后更新
description: "完成 npm 无法完成的另一半升级工作：迁移 home 目录并匹配守护进程"
---

```bash
npm install -g failproofai@latest && failproofai update
```

这就是完整的升级流程。`npm` 替换 CLI；`failproofai update` 完成其余工作。

## 为什么需要第二条命令

`npm install -g` 只替换一个东西——CLI。failproofai 安装中还有另外两个组件有意存放在包之外，npm 运行时两者都不会移动：

- **`~/.failproofai/`**，存放你的设置、云端注册信息、策略选择和历史记录。新版本可能对其结构有所调整，而这种重组必须由同时了解新旧两种结构的代码来完成。
- **`failproofaid` 守护进程二进制文件**，位于 `~/.failproofai/bin/failproofaid-<version>`。它故意不放在 `node_modules` 内：升级时在运行中的服务下替换该文件，会让一个活跃的守护进程指向由不同源码构建的二进制文件，而删除该包则会在服务仍在运行时将其删除，导致每次启动时崩溃循环。

因此，单独执行 `npm install -g` 后，CLI 是新的，但守护进程并不是。`failproofaid` 拒绝以它无法识别的 home 目录布局启动——这是对版本不匹配的显式报错，而非无声失败——所以需要将两部分同步。`failproofai update` 就是完成这一步骤的命令。

## 它做了什么

<Steps>
  <Step title="执行所有待处理的布局迁移">
    读取记录在 `~/.failproofai/VERSION` 中的布局版本，并执行将其升级到当前版本所需的步骤。通常无需任何操作——参见
    [`failproofai migrate`](/zh/cli/migrate)。
  </Step>
  <Step title="将匹配的守护进程二进制文件就位">
    优先从 npm 已下载的平台包中获取（无需网络），否则从该精确版本的发布资产中下载，并在使用前进行 SHA-256 验证。
  </Step>
  <Step title="重启服务并确认其已恢复运行">
    通过探测而非假设来确认——服务管理器在进程派生的那一刻就报告其处于活跃状态，但这与服务正常运行并不等同。
  </Step>
</Steps>

## 选项

| 标志 | 效果 |
|------|--------|
| `--no-daemon` | 仅迁移 home 目录，守护进程保持当前版本不变。 |

<Warning>
  `--no-daemon` 会保留一个版本不匹配的守护进程。在配置为需要守护进程的机器上，如果守护进程无法响应，每个 hook 事件都会**失败关闭**——而拒绝以已迁移的 home 目录启动的守护进程自然无法响应。建议让守护进程部分也正常运行。
</Warning>

## 如果出现问题

命令以非零值退出，并说明哪一半失败了。有两种情况值得了解：

- **迁移步骤未完成。** home 目录会保留其*旧*布局标记，因此下一次命令会重试——在部分迁移完成的情况下，home 目录永远不会被标记为当前状态。在任何操作执行之前，你的设置和注册信息的副本已保存到 `~/.failproofai/migrations/backup-layout<n>/`。
- **守护进程在没有密码的情况下无法重启。** 故意使用 `sudo -n`，因此在进度显示过程中不会有任何提示弹出。命令会打印出你需要自行运行的确切命令行。

<Note>
  这里的任何操作都不需要交互式设置向导。你的设置、云端注册信息和策略选择在升级后都会保留，因此已迁移的机器的执行效果与之前完全一致——这对于无人值守的机器尤为重要：CI 运行器、集群节点、无头网关等。
</Note>

## 自动化

`failproofai update` 是非交互式的，即使没有任何需要处理的内容也可以安全运行——它会报告"无需迁移"并以 0 退出。在配置脚本或 Dockerfile 中将其放在每次升级之后是预期的使用方式：

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

（在镜像构建中使用 `--no-daemon`，因为此时还没有服务需要重启。）
