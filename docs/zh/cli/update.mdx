---

```bash
npm install -g failproofai@latest && failproofai update
```

这就是完整的升级流程。`npm` 替换 CLI；`failproofai update` 负责其余部分。

## 为什么需要第二条命令

`npm install -g` 只替换一样东西——CLI。failproofai 安装中还有另外两个部分有意存放在包之外，npm 运行时不会移动它们：

- **`~/.failproofai/`**，包含你的设置、云端注册、策略选择和历史记录。新版本可能以不同的方式组织它，而这种重新组织必须由了解新旧两种结构的代码来完成。
- **`failproofaid` 守护进程二进制文件**，位于 `~/.failproofai/bin/failproofaid-<version>`。它有意*不*放在 `node_modules` 中：如果升级时在运行中的服务下面替换该文件，会将活跃的守护进程重新指向由不同源码构建的二进制文件；而删除包则会在服务依赖它时将其删除，导致每次启动时崩溃循环。

因此，单独执行 `npm install -g` 后，CLI 是新的，守护进程却不是。`failproofaid` 拒绝针对它不认识的主目录布局启动——这是版本不匹配时的显式报错，而非静默失败——所以需要将两个部分合并同步。`failproofai update` 就是完成这一步骤的命令。

## 它做了什么

<Steps>
  <Step title="执行所有待处理的布局迁移">
    读取 `~/.failproofai/VERSION` 中记录的布局，并运行将其升级到当前版本所用布局的步骤。通常不需要任何操作——参见
    [`failproofai migrate`](/zh/cli/migrate)。
  </Step>
  <Step title="将匹配的守护进程二进制文件放置到位">
    优先从 npm 已下载的平台包中获取（无需网络），否则从该精确版本的发布资产中获取，使用前进行 SHA-256 验证。
  </Step>
  <Step title="重启服务并确认其已恢复运行">
    通过主动探测而非假设来确认——服务管理器在进程派生的瞬间就会报告其处于活跃状态，这与服务实际正常运行并不相同。
  </Step>
</Steps>

## 选项

| 标志 | 效果 |
|------|--------|
| `--no-daemon` | 仅迁移主目录，守护进程保持当前版本不变。 |

<Warning>
  `--no-daemon` 会保留一个版本偏差的守护进程。在配置为需要守护进程的机器上，如果守护进程无法响应，每个 hook 事件都会**失败关闭**——而拒绝针对已迁移主目录启动的守护进程将无法响应。建议让守护进程部分也一并运行。
</Warning>

## 如果出现问题

命令会以非零值退出，并说明哪个部分失败了。有两种情况值得了解：

- **某个迁移步骤未完成。** 主目录会被标记为*旧的*布局，以便下次命令重试——没有任何主目录会因为部分迁移就被标记为当前版本。你的设置和注册信息的副本会在任何操作执行之前保存到 `~/.failproofai/migrations/backup-layout<n>/` 中。
- **守护进程无法在没有密码的情况下重启。** 有意使用 `sudo -n`，因此在进度显示下永远不会出现交互式提示。命令会打印出你需要自行运行的确切命令行。

<Note>
  这里的任何操作都不需要交互式设置向导。你的设置、云端注册和策略选择在升级后均会保留，因此迁移后的机器会完全按照之前的方式执行——这对于无人值守的机器尤为重要：CI 运行器、机群节点、无头网关。
</Note>

## 自动化

`failproofai update` 是非交互式的，在没有需要执行的操作时运行也是安全的——它会报告"无需迁移"并以 0 退出。在配置脚本或 Dockerfile 中的每次升级后加入此命令，是其预期的使用方式：

```dockerfile
RUN npm install -g failproofai@latest && failproofai update --no-daemon
```

（在镜像构建中使用 `--no-daemon`，因为此时尚无需要重启的服务。）
