托管 Python 评估可以计数和比较：工具调用次数、错误数量、会话时长。但它无法判断答案是否*正确*、回复是否粗鲁，或智能体在采取行动前是否查阅了策略。

**LLM 评判**可以做到这些。你用自然语言描述什么是优质结果，模型读取会话后返回一个 0 到 1 的分数及其推理过程。

<Note>
评判针对每个运行的会话消耗一次模型调用，而代码评估则完全免费。请仅在需要*理解*对话内容的问题上使用评判——并为其设置条件，使其仅在相关会话上运行。
</Note>

## 我应该选哪种？

| 问题 | 使用 |
| --- | --- |
| 它是否调用了同一个工具两次？ | 代码 |
| 有多少个错误？ | 代码 |
| 会话时长是否在 30 秒以内？ | 代码 |
| 客户是否表达了紧迫感？ | [分类器](/zh/evaluations/jev) |
| 客户的沮丧程度如何？ | [分类器](/zh/evaluations/jev) |
| 答案实际上正确吗？ | **评判** |
| 回复是否粗鲁或漠视？ | **评判** |
| 承诺退款前是否查阅了退款策略？ | **评判** |

经验法则：**可计数的 → 代码，可预先列举答案的 → [分类器](/zh/evaluations/jev)，需要解释说明的 → 评判。** 评判是那种会用散文描述所见内容的类型；当一个数字会让人追问"为什么？"时，就选它。

你不必提前决定。描述你想衡量什么，助手会自动选择并告知选择原因，你随时可以切换。

## 创建评判

1. 进入 **Analyze → eval authoring**，选择 **new eval**。
2. 描述你想评判的内容，然后选择 **draft**。
3. 审查**标准**、**阈值**和**条件**，然后部署。

### 标准

用一两句话，以要求而非问题的形式表述：

> 助手在未查阅退款策略的情况下，不得承诺或批准退款。

请具体说明什么情况会导致*不通过*。"回复是否足够好？"这样的描述给出的数字毫无意义；而上面那句话则让你有据可查、有所行动。

### 阈值

会话通过所需达到的最低分数。`0.7` 是一个合理的起点。完整的 0 到 1 分数始终被存储，因此阈值仅决定通过/不通过——你可以查看分布并随时调整。

### 条件

与其他评估相同的 Python 条件，但在这里更为重要。若不设置条件，评判将在你组织中的**每一个**会话上运行，每次消耗一次模型调用：

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

如果你部署了没有条件的评判，仪表盘会发出警告。有时这是正确的做法——比如对一个低流量智能体进行全量评判——但这应该是有意为之，而非疏忽所致。

## 评判看到什么

以轮次形式呈现的对话，若会话较长则按最新优先排列：

- 用户说了什么
- 助手如何回复
- **智能体调用的每个工具，以及该调用的返回结果，按顺序排列**

最后一点正是使"它是否在 Y *之前*做了 X"成为合理问题的原因。失败的工具调用会被标记为失败，因此"它是否从错误中优雅地恢复"同样适用。

非常长的会话会被截断以适应模型的上下文。发生这种情况时，推理内容会明确说明——你不会看到基于部分会话的判断被当作全量判断呈现。

## 读取结果

评判与其他有分数的评估一样产生**分数**，因此可以通过相同方式绘图、过滤和触发警报。除数字外，它还存储评判的**推理**——即描述所见内容的段落。当某个分数出乎意料时，请先阅读推理内容；通常这要么是一个真正值得关注的会话，要么是标准需要进一步细化的信号。

对于明显的情况，分数是稳定的，但并非逐位确定性的。将单个临界分数视为深入阅读该会话的提示，而不是最终裁决。

## 限制

- **测试功能尚不可用。** 试运行没有对应的会话分配，而正是该分配授权使用你的模型预算——因此测试调用无从扣费。请针对较窄的条件部署并阅读最初几条结果。
- **回填功能不可用。** 对数月历史数据进行代码评估回填是免费的；使用评判进行回填则会在数分钟内耗尽全部预算。
- **编辑标准会发布新版本。** 旧分数和新分数不可比较，因此它们会被分开存储，而不是混入同一条趋势线。
- **评判始终产生分数**，不产生指标或断言。

## 预算耗尽时

评判会消耗你组织的模型预算。预算耗尽时，评判评估会以明确的原因停止，而不是静默失败，**代码评估则继续正常运行**。补充预算后，评判将从下一个会话起恢复运行。
