托管的 Python 评测可以进行计数和比较：工具调用次数、错误数量、会话时长。但它无法判断答案是否*正确*、回复是否粗鲁，或智能体在采取行动前是否检查了相关策略。

**LLM 裁判**可以做到这些。你用自然语言描述什么是好的结果，模型读取会话后返回 0 到 1 的分数及其推理依据。

<Note>
每次运行时，裁判会为每个会话消耗一次模型调用，而代码评测则不产生任何费用。请仅在需要*理解*对话内容才能回答的问题时使用裁判——并为其设置条件，使其仅在相关会话上运行。
</Note>

## 我该选哪种？

| 问题 | 使用 |
| --- | --- |
| 它是否调用了同一工具两次？ | 代码 |
| 发生了多少个错误？ | 代码 |
| 会话时长是否在 30 秒以内？ | 代码 |
| 客户是否表达了紧迫感？ | [分类器](/zh/evaluations/jev) |
| 客户的沮丧程度如何？ | [分类器](/zh/evaluations/jev) |
| 答案实际上是否正确？ | **裁判** |
| 回复是否粗鲁或敷衍？ | **裁判** |
| 它在承诺退款之前是否检查了退款政策？ | **裁判** |

经验法则：**可计数 → 代码，可提前列举答案 → [分类器](/zh/evaluations/jev)，需要解释说明 → 裁判。** 裁判是唯一会用文字描述所见内容的方式；当一个数字会让人追问"为什么"时，就该使用裁判。

你无需提前做出决定。描述你想要衡量的内容，助手会为你选择，并告知选择的类型及原因。你随时可以切换。

## 创建裁判评测

1. 进入 **Analyze → eval authoring**，选择 **new eval**。
2. 描述你想要评判的内容，然后选择 **draft**。
3. 检查**标准**、**阈值**和**条件**，然后部署。

### 标准

一到两句话，以要求而非问题的形式表述：

> 助手在未先核查退款政策的情况下，不得承诺或批准退款。

明确说明什么情况会导致*不通过*。"回复是否良好？"得出的数字毫无意义；而上面这句话给出的是可以付诸行动的判断。

### 阈值

会话达到或超过该分数即视为通过。`0.7` 是一个合理的起点。完整的 0 到 1 分数始终会被存储，因此阈值仅决定通过/不通过——你可以查看分布情况并进行调整。

### 条件

与其他评测相同的 Python 条件，但在这里尤为重要。若不设置条件，裁判将对组织中的**每个**会话运行，每次都消耗一次模型调用：

```python
session.count("tool_use") > 0
```

```python
session.agent_id == "support-bot" and session.count("error") > 0
```

如果你在没有条件的情况下部署裁判，控制台会发出警告。这有时是合理的——比如你希望对低流量智能体进行全面评判——但这应该是一个有意为之的决定，而不是疏忽。

## 裁判看到的内容

对话内容以轮次形式呈现，若会话较长则按最新优先排列：

- 用户说了什么
- 助手如何回复
- **智能体调用的每个工具及其返回结果，按顺序排列**

最后一点正是使"它是否在 Y *之前*做了 X"成为可问问题的关键。失败的工具调用会显示为失败，因此"它是否从错误中优雅地恢复"也是可以提问的。

非常长的会话会被截断以适应模型的上下文窗口。当发生截断时，推理内容会明确说明——你永远不会看到基于部分会话的判断被呈现为基于完整会话的判断。

## 解读结果

裁判与其他评分评测一样生成**分数**，因此可以以相同方式绘制图表、进行筛选和触发告警。除数字外，它还存储裁判的**推理过程**——描述其所见内容的段落。当分数出乎意料时，请先阅读推理内容；通常这意味着要么是一个真正有趣的会话，要么是标准需要优化的信号。

对于明确的案例，分数是稳定的，但并非逐位确定性的。将单个边界分数视为去阅读该会话的提示，而不是最终裁决。

## 限制

- **测试功能暂不可用。** 试运行没有会话分配作为支撑，而会话分配正是授权消耗模型预算的依据——因此测试调用无从计费。请针对较窄的条件部署，并阅读前几个结果。
- **回填功能不可用。** 对数月的历史记录进行代码评测回填是免费的；而使用裁判进行回填会在几分钟内耗尽你的全部预算。
- **编辑标准会发布新版本。** 新旧分数不具可比性，因此它们会被分开存储，而不是混入同一趋势线。
- **裁判始终生成分数**，而不是指标或断言。

## 当预算耗尽时

裁判会消耗组织的模型预算。当预算耗尽时，裁判评测会以明确的原因停止，而不是静默失败，**代码评测则继续正常运行**。补充预算后，裁判将在下一个会话时恢复运行。
