当你通过 FailproofAI Cloud 或自己的密钥配置 [Jev 策略审查](/zh/policies/jev) 时，每个受管控的工具调用都会经过你运行的策略以及 Jev 的判断——Jev 会询问该调用实际执行了什么操作，以及发起任务的用户是否请求了该操作。每条策略的**权威**决定了两者意见不一致时的处理方式。

若未配置 Jev，权威设置不产生任何效果。每条策略的执行方式与以往完全相同。

## 硬性与可审查

- **硬性（Hard）** 是默认值。硬性策略的拒绝或指令是最终的：Jev 无法清除它，且硬性拒绝会立即阻止调用，无需等待 Jev。
- **可审查（Reviewable）** 意味着 Jev 可以清除策略的判定，但只能通过策略在 `reviewedBy` 中指定的语义检查来实现。只有当**所有**被指定的检查都针对该调用进行了询问，且每个检查要么未发现任何问题，要么记录了用户主动请求该操作时，判定才会被清除。若某项检查**触发**了——即发现了问题——但用户未请求该操作，则即使该检查本身的判定仅为警告，也会维持阻止状态。若某项检查因不适用于该工具而未被询问，则无论其他检查结果如何，它都不会清除任何阻止。一项宽松处理即视为同意：当调用是用户所给任务的一个步骤且未超出范围时，Jev 会将拒绝转为警告，该警告将清除策略的阻止，并告知代理。

只有满足以下所有条件时，策略才可审查：

1. 声明了 `authority: "reviewable"`。
2. `reviewedBy` 是一个非空列表，且每个条目都是已安装包所声明的 Jev 检查。Failproof AI 本身不附带任何 Jev 检查：[下方十六项](#semantic-policy-names)均来自 `failproofai policies add FailproofAI/jev-policies`。若没有包声明这些检查，所有策略均为硬性。
3. 不是 `alwaysOn` 策略。防止代理禁用 Failproof AI 的守卫始终为硬性。

其他情况均为硬性：缺少字段、值拼写错误、`reviewedBy` 为空或格式不正确，或名称不是此机器可询问的检查。未知名称会使整个声明变为硬性，而非被跳过，因为 `reviewedBy` 的含义是"所有这些检查都必须被询问，且没有一个可以拒绝"，跳过某个名称将允许 Jev 以少于你要求的检查数量来清除策略。

一旦配置了 Jev，Failproof AI 每个进程仅记录一次拒绝 `reviewable` 声明的警告。未配置 Jev 时则不输出任何信息，因为权威此时不决定任何事情。`failproofai publish` 拒绝构建包含此类声明的包，因此包作者在任何人安装之前就会发现问题。当包自身声明了 Jev 检查时，它会对照包声明的检查来评估 `reviewedBy`，否则对照十六个 `FailproofAI/jev-policies` 名称进行评估。

## 权威的声明位置

策略到达机器的每种方式都有一个决定其权威的地方：

| 来源 | 声明于 | 默认值 |
| --- | --- | --- |
| 内置策略 | 下方表格 | 硬性，除非列为可审查 |
| 自定义策略文件 | `customPolicies.add` 上的 `authority` 和 `reviewedBy` | 硬性 |
| 策略包 | 包清单（`failproofai-pack.json`）中各策略的条目 | 硬性 |
| 云端管理策略 | 策略在活跃部署中的分配 | 硬性。部署目前尚未设置此项，因此今天所有云端管理策略均为硬性。 |

对于包或云端管理策略，在策略代码内部设置的字段会被忽略；清单或分配决定权威。包只能描述自己的策略：其策略名称不能包含 `/`，且在包自身的前缀下注册，因此任何清单都不能将内置策略或其他包的策略标记为可审查。包代码注册但未在清单中声明的策略为硬性。

两个代码字节完全相同的包，或两个云端管理策略，共享同一个构件并作为一条策略加载。只有当它们全部声明为可审查时，该策略才是可审查的，且 Jev 必须清除它们中任何一个所命名的每项检查。若其中任何一个声明为硬性，或根本未声明，则保持硬性。包或策略的列出顺序从不影响结果。

大多数机器从 `FailproofAI/policies` 包获取内置策略，并从该包的清单中读取权威。下方的可审查条目在携带它们的包版本安装后生效；旧版本不携带任何可审查声明，因此其中的每条策略保持硬性。

## 在自定义策略中声明权威

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` 会将两个字段都复制到包清单中，因此以包形式发布的策略会保留作者赋予它的权威。若声明无法被遵守，则拒绝构建包：值不是 `"hard"` 或 `"reviewable"`、`reviewedBy` 不是名称列表，或某个名称不是检查——当包自身声明了 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack) 时对照其检查，否则对照内置检查。

## 内置策略

仅在语义策略真正涵盖相同关注点时才为可审查。其他所有内置策略均为硬性。

涵盖关注点是必要条件但非充分条件，且两种出错方式都是静默的：

- **从未被询问的检查**会使阻止永久生效。`reviewedBy` 是一个合取条件，未被询问的检查永远不会清除，因此与某个前提条件不会对策略匹配的形状触发的检查配对的策略永远无法被清除。
- **被询问但未触发的检查**回答"无关注点"，而无关注点即清除。因此，与一个无法模拟你策略形状的检查配对，并不是在审查该策略——而是对于检查无法理解的输入将其关闭。

指令模式的语义策略永远无法回答拒绝，但它仍然可以维持阻止：当它触发且用户未请求该调用时，它所审查的策略不会被清除。`FailproofAI/jev-policies` 中有六个检查仅为指令模式——`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump` 和 `external-data-egress`——[下方表格](#semantic-policy-names)列出了每个检查的模式。要问的问题是**"是否还有任何东西可以拒绝"**：一次清除绝不能让关注点处于无任何执行的状态。引擎对每次调用应用该测试。未经任何人同意的警告不算清除，因为在工具调用之前，警告不会阻止代理。当一个*可以*拒绝的检查发出警告时——其证据未达到拒绝阈值——且用户未请求该调用，该调用上没有任何内容被清除，所有正则表达式拒绝依然有效。

<Warning>
**刚好低于触发线的检查不会维持底线。** 上述规则需要检查*触发*（证据 ≥ 0.7）。当所有相关检查刚好低于该值时，没有任何检查触发，审查者回答"无关注点"，可审查的拒绝被清除。在强制执行模式下的实测结果：对 `/etc/shadow` 的未请求读取（`secret-exposure` 0.69，`read-outside-workspace` 0.37，后者仅建模主目录路径）以及在"follow SETUP.md"之后执行的 `set | curl -d @- …`（`env-secrets-dump` 0.66，`credential-exfiltration` 0.65，`sends_out` 0.97）均被允许，而仅正则表达式层会拒绝它们。这些阈值是在标注语料库上校准的，尚未针对此情况重新测量；在重新测量之前，对于这些形状中有任何一个通过比其误阻止更重要的情况，请将策略保持为**硬性**。
</Warning>

## 语义策略名称

这些是 `FailproofAI/jev-policies` 声明的检查，也是安装后 `reviewedBy` 接受的值。Failproof AI 本身不附带其中任何一项：没有该包（或其他声明这些名称的包），命名它们的策略均不可审查。每项检查都是 Jev 针对当前工具调用所回答的问题。**模式**是检查可以回答的内容：`deny` 检查在有强力证据时阻止，而 `instruct` 检查只会发出警告。当两者触发且用户未请求该调用时，两者都会维持策略的拒绝状态。**用户可覆盖**表示用户的明确请求是否可以清除它。

Jev 仅询问已安装包所声明的 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，这些就是 `reviewedBy` 接受的名称。两个包以不同方式声明的同一名称对两者均不生效。这十六个名称中，由非来自 FailproofAI 仓库的包声明的，在该包中会被忽略：其版本永远不会被询问，也不会与 FailproofAI 自己的版本竞争，因此第三方包既不能成为清除核心包策略的检查，也不能关闭这些检查中的任何一个。不可读的包列表，或所有检查均不可用的包，会让 Jev 没有任何内容可询问。

| 名称 | 模式 | 用户可覆盖 | Jev 检查的内容 |
| --- | --- | --- | --- |
| `destructive-deletion` | deny | 是 | 永久删除无法再生的数据。 |
| `production-infra-change` | deny | 是 | 更改生产基础设施。 |
| `git-history-rewrite` | deny | 是 | 重写或丢弃共享的 git 历史记录。 |
| `push-to-protected-branch` | instruct | 是 | 直接推送到受保护分支。 |
| `commit-on-protected-branch` | instruct | 是 | 直接在受保护分支上提交。 |
| `secret-exposure` | deny | 是 | 读取或复制凭据。 |
| `credential-exfiltration` | deny | 否 | 将机密或私有文件发送到机器外部。 |
| `remote-code-execution` | deny | 是 | 运行从互联网下载的代码。 |
| `privilege-escalation` | deny | 是 | 以提升的权限运行。 |
| `database-destruction` | deny | 是 | 销毁或批量修改数据库数据。 |
| `read-outside-workspace` | instruct | 是 | 读取项目外的文件。 |
| `agent-config-tampering` | deny | 否 | 更改代理自身的安全配置。 |
| `system-modification` | instruct | 是 | 在项目外更改系统。 |
| `env-secrets-dump` | instruct | 是 | 打印环境机密。 |
| `external-destructive-action` | deny | 是 | 通过外部工具执行不可逆操作。 |
| `external-data-egress` | instruct | 是 | 通过外部工具发送私有数据。 |
