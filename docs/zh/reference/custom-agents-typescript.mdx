需要 Node 20.9 或更高版本。支持 ESM 和 CommonJS，无运行时依赖。

<Note>
  此 SDK 与 Python SDK **将相同的事件写入同一个 spool**。由 Node agent 和 Python agent 组成的集群只会产生一组会话，而非两组，仪表板也不会对它们加以区分。按服务选择，而非按公司统一选择。
</Note>

## 安装

```bash
npm install @failproofai/sdk
```

```ts
import * as failproofai from "@failproofai/sdk";

await failproofai.agent("planner", { goal: question }, async () => {
  const hits = await failproofai.toolCall("web_search", { input: { q } }, () => search(q));
});
```

框架适配器已内置于包中。这些框架是**可选的对等依赖**——声明的目的是让支持范围一目了然，不会自动帮你安装，只在调用 `instrument()` 时才会被导入。

## 连接 Failproof 守护进程

与 Python SDK 完全一致：在 **Admin → Keys** 下创建 `events:add` 密钥，然后在 agent 所在机器上[连接守护进程](/zh/start/setup#connect-a-machine-to-cloud)。SDK 将数据写入磁盘，守护进程负责传输。

## 配置

### OpenTelemetry spans（可选启用）

使用 `npm install @opentelemetry/api @opentelemetry/sdk-trace-base` 单独安装 OpenTelemetry。
然后将 FailproofAI 添加到你的 provider 处理器中：

```ts
import * as failproofai from "@failproofai/sdk";
import { BasicTracerProvider } from "@opentelemetry/sdk-trace-base";
import type { SpanProcessor } from "@opentelemetry/sdk-trace-base";

const spanProcessors: SpanProcessor[] = [];
await failproofai.instrument("otel", { spanProcessors });
const provider = new BasicTracerProvider({ spanProcessors });
const span = provider.getTracer("my-agent").startSpan("agent", {
  attributes: { "gen_ai.operation.name": "invoke_agent" },
});
span.end();
await provider.forceFlush();
```

如果你已有 provider，将其他处理器保留在同一列表中即可。暴露了 `addSpanProcessor` 的 provider 也可以以 `{ provider }` 形式传入。如果不传任何选项，且当前尚未注册 provider，则会自动注册一个新的。`OtelSpanExporter` 也可直接与你自己的处理器配合使用。

导出数据会经由已连接的 FailproofAI 守护进程传输；SDK 本身不发送任何网络请求，也不需要密钥或本地监听器。请联系管理员启用 [OpenTelemetry 摄取](/zh/agenteye/opentelemetry)。不带参数的 `instrument()` 不会启用此导出器。`uninstrument("otel")` 只会禁用它自己的处理器。span 属性的内容由你自行控制；在进程退出前请务必 flush 你的 provider。OpenTelemetry 始终是可选的应用层依赖，而非 SDK 的硬性依赖。

```ts
failproofai.configure({
  environment: "production",
  flushInterval: 0.5,
  baseDir: undefined,
});
```

| 选项 | 作用 |
| --- | --- |
| `environment` | 每个事件上的标签，例如 `production`、`staging`、`prod-eu`。默认值为 `dev`。 |
| `flushInterval` | 定时器将数据写入磁盘的频率，单位为秒。默认值为 `0.5`。 |
| `baseDir` | 写入路径。默认使用守护进程的 spool 目录，除非你明确知道需要修改，否则不必更改。 |

只有当所有配置项均通过校验时才会生效，因此一次失败的调用不会导致 SDK 处于 `baseDir` 已更新而 interval 未变的中间状态。

也可通过环境变量进行设置：

| 变量 | 作用 |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | 无需修改代码即可设置 `environment`。`configure()` 中的同名选项优先级更高。 |
| `FAILPROOFAI_HOME` | 移动存放 spool 的 Failproof AI 根目录。 |
| `FAILPROOFAI_SDK_LOG_LEVEL` | `debug`、`info`、`warn`（默认）、`error`、`silent`。 |
| `FAILPROOFAI_SDK_STRICT` | 设为 `1` 时，接入错误会抛出异常，而不是仅记录日志。 |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | 设为 `1` 时，框架兼容性问题会抛出异常，而不是仅警告后继续运行。 |

<Warning>
  **`environment` 中不能含有逗号。** 摄取器会以逗号分割该字段来构建过滤条件，凡是标签中含有逗号的事件都会被跳过——这会导致整个运行过程无声无息地丢失。请写 `prod-eu`，而不是 `prod,eu`。

  `configure({ environment: "prod,eu" })` 会立即抛出异常，让你第一时间发现问题。`AGENTEYE_ENVIRONMENT` 无法抛出异常——没有任何调用方可以捕获——因此它只会警告一次，并回退到 `dev`。
</Warning>

使用 `failproofai.setLogger({ debug, info, warn, error })` 可将 SDK 自身的日志输出接入你的日志系统。

## 关闭

缓冲的事件会在 `process.on("exit")` 时被 flush。

被信号终止的进程永远不会到达那一步，而 Node 对 `SIGTERM` 的默认行为是直接终止，不执行退出处理器——因此容器化的 agent 会丢失最后一个写入间隔中尚未写出的数据。

<Warning>
  **此 SDK 不会为你安装信号处理器。** 注册信号处理器会改变进程行为：一旦有监听器，Node 的默认终止行为就会被抑制，因此一个擅自注册处理器的库会悄悄导致 Ctrl-C 失效。请自行添加：

  ```ts
  for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.once(signal, () => {
      failproofai.flushSync();
      process.exit(0);
    });
  }
  ```
</Warning>

短暂运行的脚本或 serverless 处理器应在返回前 `await failproofai.flush()`——仅靠定时器无法保证数据一定送达。

## 身份标识

每个事件都归属于一个会话和一个 agent。**作用域会自动填充这两者**，因此你通常无需手动传入：

```ts
await failproofai.session(async () => {
  await failproofai.agent("planner", async () => {
    failproofai.event.toolUse({ toolName: "search", toolCallId: "c1" });
  });
});
```

显式传入 `sessionId` 或 `agentId` 仍然有效，且优先级更高。如果两者均未绑定也未传入，调用会抛出异常，而不是悄悄发出一个 Cloud 会丢弃的事件。

<Note>
  身份标识基于 `AsyncLocalStorage` 传递，它能跟踪 `await`、`.then()`、定时器以及在作用域内创建的所有回调。但它**不会**跟踪在一次运行中存储、在另一次运行中调用的回调，也不适用于跨 `worker_threads` 边界传递的任务——对于这类情况，请使用 `failproofai.propagate()` 进行包裹，否则这些事件会处于游离状态。
</Note>

### 作用域

| 作用域 | 触发事件 | 返回值 |
| --- | --- | --- |
| `session(body)` | 无——仅绑定身份标识 | `body` 的返回值 |
| `agent(id, options?, body)` | `agent_start`，然后 `agent_end` | `body` 的返回值 |
| `toolCall(name, options?, body)` | `tool_use`，然后 `tool_result` | `body` 的返回值 |

同步的 body 保持同步：`agent("x", () => 1)` 返回 `1`，而不是一个 Promise。

`toolCall` 会将 body 的 resolved 值记录为工具的 `output`，除非你自行给 `call.output` 赋值。

<Accordion title="退出语义" icon="arrow-right-from-bracket">

| 发生了什么 | 事件 | `outcome` |
| --- | --- | --- |
| 代码块正常返回 | `agent_end` | `"success"`，或你自定义的 `outcome` |
| 代码块抛出异常 | `error`，然后 `agent_end` | `"failed"` |
| 抛出 `AbortError` | 仅 `agent_end` | `"cancelled"` |

异常始终会被重新抛出。

工具失败记录在叶节点上——即带有 `error` 字符串的 `tool_result`——**不会**触发运行级别的 `error` 事件。被 agent 循环捕获的失败不算运行失败；向上传播的失败则由外层 `agent()` 精确地报告一次。

</Accordion>

<Accordion title="using 形式" icon="brackets-curly">

当工作内容不是单一函数时——例如在构造函数中打开作用域、在析构中关闭，或横跨现有控制流的场景：

```ts
{
  using span = failproofai.agent.open("planner", { goal });
  using call = failproofai.toolCall.open("search", { input: { q } });
  call.call.output = await search(q);
}  // tool_result, then agent_end
```

两种形式产生字节完全相同的事件。优先选用回调形式：它在 `AsyncLocalStorage.run()` 内部运行，不存在需要手动展开的状态，也就根本无法出现"在这里打开、在那里关闭"的 bug。

如果 `using` 块需要捕获自身的失败，请使用 `span.fail(error)` 上报——disposer 本身没有异常通道。

</Accordion>

## 事件目录

与 Python SDK 相同的十五个方法，采用 camelCase 命名。大多数以**成对**形式出现——先调用开启方法，再调用关闭方法，SDK 会自动计算两者之间的时间差。

| | 开启 | 关闭 |
| --- | --- | --- |
| **Agent** | `agentStart` | `agentEnd` |
| | `agentPause` | `agentResume` |
| **模型** | `modelRequest` | `modelResponse` |
| **工具** | `toolUse` | `toolResult` |
| **Hook** | `hookTriggered` | `hookCompleted` |
| **人工** | `humanWait` | `humanInput` |

三个独立方法：`error`、`humanPause`、`humanInterrupt`。

<Accordion title="每个方法的完整字段" icon="table">

每个方法还接受 `sessionId` 和 `agentId`，作用域会自动填充这两者。省略的字段会被丢弃，而不是以 JSON `null` 的形式发送。

| 方法 | 必填 | 可选 |
| --- | --- | --- |
| `agentStart` | — | `goal`, `parentId` |
| `agentEnd` | — | `outcome`, `summary` |
| `agentPause` | `pauseId` | `reason`, `userId` |
| `agentResume` | `pauseId` | `reason`, `userId` |
| `modelRequest` | — | `model`, `messages`, `system`, `tools`, `requestId` |
| `modelResponse` | — | `model`, `stopReason`, `inputTokens`, `outputTokens`, `content`, `role`, `requestId` |
| `toolUse` | `toolName`, `toolCallId` | `input` |
| `toolResult` | `toolName`, `toolCallId` | `output`, `error` |
| `hookTriggered` | `hookName`, `hookId` | `triggerEvent`, `input` |
| `hookCompleted` | `hookName`, `hookId` | `outcome`, `output`, `error` |
| `error` | `errorType`, `message` | `traceback` |
| `humanWait` | `inputId` | `prompt`, `options`, `reason` |
| `humanInput` | `inputId` | `response` |
| `humanPause` | — | `reason`, `userId` |
| `humanInterrupt` | — | `reason`, `userId`, `atStep` |

你添加的任何其他键都会成为自定义 payload 字段。框架特定的内容请使用 `fw_*` 命名空间；与已声明字段名称冲突的键会被拒绝，而不是悄悄覆盖已提升的列。

</Accordion>

<Warning>
  **`duration_ms` 是计算得出的，不接受外部传入。** 四个关闭方法会自动计算与对应开启方法之间的时间差，并拒绝调用方传入的 `duration_ms`——上报的耗时必须是不可篡改的。

  配对基于**会话**和 id 进行匹配，而不是基于 agent。在 `planner` 下打开、在 `worker` 下关闭的工具调用仍然可以配对，这正是嵌套多 agent 运行的实际需要。
</Warning>

## 框架适配器

```ts
await failproofai.instrument();              // 自动检测可用框架
await failproofai.instrument("langchain");   // 指定一个
failproofai.uninstrument();                  // 恢复原状
```

| 框架 | 支持版本 | 接入方式 |
| --- | --- | --- |
| **LangChain.js / LangGraph.js** | `@langchain/core` 0.3 – 1.x，LangGraph.js 0.4 – 1.x | `CallbackManager.configure`，每次 `invoke`/`stream`/`batch` 调用都会被覆盖，无需在任何地方传入 `callbacks:`——也可以自行传入 `langchainHandler()` 而不做任何 patch。 |
| **Vercel AI SDK** | `ai` 4 – 7 | 在调用处使用 `telemetry()`，或对 `ai` 7 使用 `instrument("ai")` 作用于整个进程（对 4–6 版本这是可选启用的——详见下文）。 |
| **Mastra** | `@mastra/core` 0.20 – 1.x | `Agent.generate`/`.stream`、agent 的模型与工具解析，以及工作流运行/步骤引擎。 |
| **LlamaIndex.TS** | `llamaindex` 0.11.4 – 0.x | `Settings.callbackManager`（订阅）加上 `AgentWorkflow.runStream`，用于工作流运行及其步骤。 |

每个版本范围都会在真实框架发布版本上进行测试，覆盖两端边界，以 ES 模块和 CommonJS 两种形式，在每次 CI 运行中执行。

映射关系与 Python SDK 一致，因此相同程序在两种语言中绘制的树结构也相同。只有拥有 LLM 决策循环的构造才算作 **agent**——包括 graph 或 chain 运行、AI SDK 的 `generateText`/`streamText` 调用、Mastra agent、LlamaIndex agent 运行。LangGraph 节点或工作流步骤是 **hook**（`hook_triggered`/`hook_completed`），而非嵌套 agent。模型调用以带有 token 计数的 `model_request`/`model_response` 成对记录；工具调用携带模型自身的 tool call id。失败只在发生的事件上记录一次。

安装失败的适配器会被记录日志并跳过；其他适配器仍会继续安装，因为 LlamaIndex 出问题不应影响 LangGraph 的正常使用。

<Note>
  不带参数的 `instrument()` 通过框架是否**可以解析**来检测框架，而不是判断它是否已被导入——Node 没有等效于 Python `sys.modules` 的 ES 模块机制。你已安装但未使用的框架会被导入并 patch。如果这一点对你有影响，请明确指定你想要的框架名称。
</Note>

<Note>
  大多数框架同时提供 ES 模块和 CommonJS 构建，Node 会将它们作为两个独立的副本加载。适配器会 patch 你的应用实际加载的那个副本（如果某些代码已经 `require` 过，则也会 patch CommonJS 副本），因此两种模块系统均可正常工作。但如果框架被 esbuild 或 webpack **打包进了你自己的输出**，则适配器无法覆盖到——此时请使用调用处的辅助工具：`langchainHandler()`、`telemetry()`、`wrapTool()`。
</Note>

### 不使用 patch 的 LangChain 接入方式

```ts
import { langchainHandler } from "@failproofai/sdk/langchain";
await graph.invoke(input, { callbacks: [langchainHandler()] });
```

该处理器无论是否调用过 `instrument()` 都能正常工作，且不会重复记录。`instrument("langchain")` 支持 `sessionId`、`captureContent`、`includeChains`、`graphCallbacks` 和 `captureLimit` 参数，与 Python 适配器一致；在调用时传入 `metadata: { failproofai_sdk_session_id }` 可为该次调用指定会话。

### Vercel AI SDK

AI SDK 从 ES 模块导出纯函数，而 ES 模块命名空间在规范上是不可变的——因此没有地方可以做 patch。它使用 SDK 官方文档中的扩展点：

```ts
import { telemetry } from "@failproofai/sdk/ai";

const { text } = await generateText({
  model,
  prompt,
  experimental_telemetry: telemetry({ functionId: "answer-question" }),
  // 在 ai 7 上，使用 `telemetry: telemetry({ … })` — 同一个对象，新的名称
});
```

这就是完整的接入方式：一个 agent span、每个步骤一对带有 token 计数的模型请求/响应，以及所有工具调用。一处调用适用于所有主版本——`ai` 4–6 读取其携带的 tracer，`ai` 7 读取 telemetry 集成。

`instrument("ai")` 在 **`ai` 7 上**可实现进程级的相同效果：通过 AI SDK 的全局 telemetry 集成列表覆盖所有调用，该列表是追加式的，不会影响其他任何人的配置。

**在 `ai` 4–6 上，`instrument("ai")` 本身不记录任何内容，并会输出一条警告说明原因。** 这些主版本唯一的进程级 hook 是全局 OpenTelemetry tracer provider——这是一个单一插槽，一旦被占用，OpenTelemetry 就会拒绝交出。注册我们的 tracer 会在启动后期悄悄拒绝你自己的 `NodeSDK.start()`，并将你的 http/数据库 span 发送到一个什么都不导出的 tracer。请在调用处使用 `telemetry()` 或 `wrapModel`。如果进程本身没有运行任何 OpenTelemetry，可以通过 `instrument("ai", { registerGlobalTracer: true })` 选择启用：此时只要插槽仍为空，它就会记录所有传入了 `experimental_telemetry: { isEnabled: true }` 的调用。`registerGlobalTracer: false` 保持默认行为并屏蔽警告。

如果你更倾向于只包裹一次模型，`wrapModel` 只能看到模型调用，因为工具调用发生在模型层之上。一个没有外层包裹的被包裹模型调用会被记录为独立的运行。流式调用的关闭取决于流的结束方式——消费者取消时为 `stop_reason: "cancelled"`，中途失败时为带有错误信息的 `"error"`：

```ts
import { wrapModel } from "@failproofai/sdk/ai";
const model = await wrapModel(openai("gpt-4o"));
```

同时使用两者也没问题：中间件会检测到调用已在被记录，并自动让步，因此每次调用只会被记录一次。

`functionId` 用于命名 agent span。请保持低基数——它会落在 `agent_id` 字段，这是仪表板的主要分面。

### Next.js

`next build` 默认会打包服务端依赖，被打包进构建产物的框架是 `instrument()` 无法触达的副本。在 Next 的启动 hook 中调用 `instrument()`，并一次性包裹配置：

```ts
// next.config.ts
import { withFailproofai } from "@failproofai/sdk/next";
export default withFailproofai({ /* 你的配置 */ });
```

```ts
// instrumentation.ts
export async function register() {
  if (process.env.NEXT_RUNTIME !== "nodejs") return;
  const failproofai = await import("@failproofai/sdk");
  await failproofai.instrument();
}
```

`withFailproofai` 会将 LangChain、Mastra、LlamaIndex 和 SDK 本身添加到 `serverExternalPackages`，同时保留你已有的列表。如果没有它，`instrument()` 会对每个无法触达的框架输出一次警告，而不是静默失败；如果你自己已经列出了这些包，可以设置 `FAILPROOFAI_NEXT_EXTERNALS=1`。Vercel AI SDK 和调用处的辅助工具无论如何都能正常工作。Edge 路由会得到一个空操作构建：导入 SDK 是安全的，但不会记录任何内容。

### 流式调用的 token 计数

兼容 OpenAI 的 API 只有在客户端明确请求时才会在流中报告用量。LangChain 和 Vercel AI SDK 会自动请求；对于 LlamaIndex，请在其 `OpenAI` LLM 中传入 `additionalChatOptions: { stream_options: { include_usage: true } }`；对于 Mastra，请在构建模型时启用用量统计（例如 `createOpenAICompatible({ includeUsage: true })`）。否则流式模型调用将不包含 token 计数。

### 运行时

Node ≥ 20.9、Bun 和 Deno——每个框架，以 ES 模块和 CommonJS 两种形式，都在各运行时上对照 Node 的 trace 进行了测试。SDK 与 `failproofaid` 守护进程并行运行，守护进程负责传输 SDK 写入的数据。

## 自建 agent——无需框架

适用于你自己编写的 agent 循环，或没有适配器的框架。你使用与适配器底层相同的 API 来发送事件，因此 trace 具有相同的形态和质量。

你不需要了解 agent 的内部组织结构。无论函数叫什么名字，每个手写 agent 都有三个固定的位置，这三处就是完整的接入点：

| 位置 | 需要添加的内容 | 触发事件 |
| --- | --- | --- |
| **一次运行**的起止处 | `failproofai.agent("name", { goal }, async () => …)` | `agent_start` / `agent_end` |
| **调用模型的那个函数** | 调用前 `event.modelRequest`，调用后 `event.modelResponse`——包括失败情况也要成对记录 | 每个模型轮次一对 |
| **执行工具的那个函数** | `failproofai.toolCall(name, { toolCallId, input }, () => run())` | `tool_use` / `tool_result` |

```ts
async function callModel(messages) {
  const requestId = randomUUID();
  const started = Date.now();
  failproofai.event.modelRequest({ model: MODEL, requestId, messages });
  try {
    const reply = await client.chat.completions.create({ model: MODEL, messages, tools });
    failproofai.event.modelResponse({
      model: reply.model, requestId, stopReason: reply.choices[0].finish_reason,
      inputTokens: reply.usage?.prompt_tokens, outputTokens: reply.usage?.completion_tokens,
      duration_ms: Date.now() - started,
    });
    return reply.choices[0].message;
  } catch (error) {
    failproofai.event.modelResponse({ model: MODEL, requestId, stopReason: "error",
      error: String(error), duration_ms: Date.now() - started });
    throw error;
  }
}

async function dispatch(call) {
  const input = JSON.parse(call.function.arguments);
  return failproofai.toolCall(call.function.name, { toolCallId: call.id, input },
    () => runTool(call.function.name, input));
}

await failproofai.agent("inventory", { goal: question }, async () => {
  for (;;) {
    const message = await callModel(messages);
    if (!message.tool_calls?.length) return message.content;
    for (const call of message.tool_calls) await dispatch(call);
  }
});
```

身份标识是环境感知的：`agent()` 内部的所有内容都会自动归属于该运行的会话，无需传入 id，程序的其他部分也不受影响——包括 agent 已经写入自身数据库的内容。

- **服务或 worker：** 将你自己的请求或任务 id 作为 `sessionId` 传入，这样仪表板上的会话与你自己的日志或数据库中的记录就是同一个字符串。
- **子 agent：** 嵌套 `agent()` 调用。内层 agent 会以外层为 `parent_id` 加入同一会话。
- **成对发送事件。** 没有对应 `modelResponse` 的 `modelRequest` 会在仪表板中显示为永远在运行的 span——这正是为什么需要 `catch`。

仓库中的 [`sdk/typescript/examples/research-agent.ts`](https://github.com/FailproofAI/failproofai/blob/main/sdk/typescript/examples/research-agent.ts) 是完整可运行的版本：一个真实的 OpenAI 工具循环，按照上述方式接入，在每次变更时以 ES 模块和 CommonJS 两种形式在 CI 中运行。

## 评估

```ts
import { Evaluator, EvalResult, Score } from "@failproofai/sdk/evaluator";

export const app = new Evaluator({ name: "my-evals", version: "1" });

app.eval("tool_success_rate", { version: "1" }, (session) => {
  const results = session.eventsOfType("tool_result");
  const failures = results.filter((event) => event.payload.error != null).length;
  return new EvalResult({
    score: new Score(results.length === 0 ? 1 : 1 - failures / results.length),
    reasoning: `${failures} of ${results.length} tool calls failed`,
  });
});
```

```bash
FAILPROOFAI_EVALUATOR_URL=… FAILPROOFAI_EVALUATOR_TOKEN=… \
  npx failproofai-evaluator ./my-evals.js
```

协议、worker 配置和结果类型详见 [Evaluator SDK 参考](/zh/reference/evaluator-sdk)。

<Warning>
  **评估函数必须能够让出控制权。** 永不返回的同步函数会阻塞 Node 仅有的那一个线程，任何超时机制都无法触发。请编写 `async` 评估函数。
</Warning>

## SDK 不会对你的进程做的事

| | |
| --- | --- |
| **阻塞 agent 循环** | 事件会进入内存队列，由定时器写出。定时器已调用 `unref`，因此导入此包永远不会阻止脚本退出。 |
| **无限增长** | 队列同时受事件数量和已测量字节数的限制。超出任一上限后，最旧的事件会被丢弃并输出警告——遥测故障绝不能演变成 OOM kill。 |
| **拖垮进程** | 一个无法编码的事件会被单独丢弃，而不影响同批次的其他事件。抛出异常的 getter、循环引用、`BigInt`、孤代理对：每种情况都会被妥善处理，而不是向上传播。 |
| **留下写了一半的批次** | 内容在原子重命名前会先 `fsync`，之后再 `fsync` 目录，写入失败时会清理临时文件。 |
| **让记录内容可被他人读取** | 批次文件权限为 `0600`，存放在 `0700` 目录中。它们包含目标、提示词、工具参数和工具输出。 |
| **泄露凭证** | API 密钥、token、JWT、bearer 请求头以及看起来像密钥的赋值语句，在字节写入磁盘之前就会被脱敏处理。守护进程在上传前也会再次脱敏。 |
