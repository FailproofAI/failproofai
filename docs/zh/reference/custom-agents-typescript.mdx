需要 Node 20.9 或更高版本。支持 ESM 和 CommonJS，无运行时依赖。

<Note>
  本 SDK 与 Python SDK **将事件写入同一个 spool**。由 Node agent 和 Python agent 混合组成的集群只会产生一组 session，而非两组，Dashboard 也不会区分它们。请按服务选择语言，而非按公司统一决定。
</Note>

## 安装

```bash
npm install @failproofai/sdk
```

```ts
import * as failproofai from "@failproofai/sdk";

await failproofai.agent("planner", { goal: question }, async () => {
  const hits = await failproofai.toolCall("web_search", { input: { q } }, () => search(q));
});
```

框架适配器已内置于包中。这些框架是**可选的 peer 依赖**——声明它们是为了让支持的版本范围可见，不会自动安装，仅在调用 `instrument()` 时才会被导入。

## 连接 Failproof 守护进程

与 Python SDK 相同：在 **Admin → Keys** 下创建一个 `events:add` 密钥，然后在 Agent 机器上[连接守护进程](/zh/start/setup#connect-a-machine-to-cloud)。SDK 负责写入磁盘，守护进程负责上传。

## 配置

### OpenTelemetry spans（可选启用）

请单独安装 OpenTelemetry：`npm install @opentelemetry/api @opentelemetry/sdk-trace-base`。
然后将 FailproofAI 添加到你的 provider 处理器中：

```ts
import * as failproofai from "@failproofai/sdk";
import { BasicTracerProvider } from "@opentelemetry/sdk-trace-base";
import type { SpanProcessor } from "@opentelemetry/sdk-trace-base";

const spanProcessors: SpanProcessor[] = [];
await failproofai.instrument("otel", { spanProcessors });
const provider = new BasicTracerProvider({ spanProcessors });
const span = provider.getTracer("my-agent").startSpan("agent", {
  attributes: { "gen_ai.operation.name": "invoke_agent" },
});
span.end();
await provider.forceFlush();
```

如果已有 provider，将其他处理器也放入同一个列表中。如果 provider 提供了 `addSpanProcessor` 方法，也可以将其作为 `{ provider }` 传入。若不传任何选项，仅在尚未注册 provider 时才注册新的。
`OtelSpanExporter` 也可以直接与你自己的处理器配合使用。

导出通过已连接的 FailproofAI 守护进程进行，SDK 不发送任何网络请求，也不需要密钥或本地监听器。请联系管理员开启 [OpenTelemetry 数据摄取](/zh/agenteye/opentelemetry)。不带参数的 `instrument()` 不会启用此导出器。`uninstrument("otel")` 仅禁用其自身的处理器。内容捕获由你的 span 属性控制；退出前请确保 flush 你的 provider。OpenTelemetry 作为可选的应用依赖，而非 SDK 的强制依赖。

```ts
failproofai.configure({
  environment: "production",
  flushInterval: 0.5,
  baseDir: undefined,
});
```

| 选项 | 说明 |
| --- | --- |
| `environment` | 附加在每个事件上的标签，如 `production`、`staging`、`prod-eu`。默认为 `dev`。 |
| `flushInterval` | 定时器写入磁盘的频率，单位为秒。默认为 `0.5`。 |
| `baseDir` | 写入位置。默认为守护进程的 spool 目录，通常无需修改。 |

只有全部验证通过，配置才会生效。若验证失败，SDK 的状态保持不变，不会出现新 `baseDir` 与旧间隔混用的情况。

也可通过环境变量进行配置：

| 变量 | 说明 |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | 无需修改代码即可设置 `environment`。`configure()` 中的选项优先于此变量。 |
| `FAILPROOFAI_HOME` | 移动存放 spool 的 Failproof AI 根目录。 |
| `FAILPROOFAI_SDK_LOG_LEVEL` | `debug`、`info`、`warn`（默认）、`error`、`silent`。 |
| `FAILPROOFAI_SDK_STRICT` | 设为 `1` 时，接入错误将抛出异常而非仅记录日志。 |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | 设为 `1` 时，框架兼容性问题将抛出异常而非仅发出警告后继续运行。 |

<Warning>
  **`environment` 中不得包含逗号。** 数据摄取会以逗号分割该字段以构建过滤器，标签中含有逗号的事件会被静默丢弃，导致整个运行记录消失。请写 `prod-eu`，而非 `prod,eu`。

  `configure({ environment: "prod,eu" })` 会立即抛出异常，让你及时发现问题。`AGENTEYE_ENVIRONMENT` 无法抛出异常——没有调用者来接收——因此它会发出一次警告并回退到 `dev`。
</Warning>

使用 `failproofai.setLogger({ debug, info, warn, error })` 将 SDK 自身的日志输出路由到你的日志系统。

## 关闭

缓冲的事件会在 `process.on("exit")` 时被 flush。

通过信号终止的进程不会触发该回调，而 Node 对 `SIGTERM` 的默认行为是直接终止而不运行退出处理器——因此容器化的 agent 可能会丢失最后一个写入间隔内未写出的数据。

<Warning>
  **本 SDK 不会为你安装信号处理器。** 注册信号处理器会改变进程的行为：添加了监听器后，Node 的默认终止行为会被抑制，因此由库自动添加处理器会导致 Ctrl-C 失效。请自行添加：

  ```ts
  for (const signal of ["SIGINT", "SIGTERM"] as const) {
    process.once(signal, () => {
      failproofai.flushSync();
      process.exit(0);
    });
  }
  ```
</Warning>

短期脚本或 serverless 处理器应在返回前执行 `await failproofai.flush()`——仅靠定时器无法保证数据一定送达。

## 身份标识

每个事件都属于一个 session 和一个 agent。**作用域会自动填充这两项**，因此通常无需手动传入：

```ts
await failproofai.session(async () => {
  await failproofai.agent("planner", async () => {
    failproofai.event.toolUse({ toolName: "search", toolCallId: "c1" });
  });
});
```

显式传入 `sessionId` 或 `agentId` 仍然有效，且优先级最高。若两者均未绑定也未传入，调用将抛出异常，而不是发出一个 Cloud 会静默丢弃的事件。

<Note>
  身份标识基于 `AsyncLocalStorage` 传递。它可以跟随 `await`、`.then()`、定时器以及在作用域内创建的任何回调。它**不能**跟随在某次运行中存储、在另一次运行中调用的回调，也不能跨越 `worker_threads` 边界——对于这类情况，请使用 `failproofai.propagate()` 包裹，否则相应事件将无法关联到正确的 session。
</Note>

### 作用域

| 作用域 | 触发事件 | 返回值 |
| --- | --- | --- |
| `session(body)` | 无——仅设置身份标识 | `body` 的返回值 |
| `agent(id, options?, body)` | `agent_start`，然后 `agent_end` | `body` 的返回值 |
| `toolCall(name, options?, body)` | `tool_use`，然后 `tool_result` | `body` 的返回值 |

同步的 body 保持同步：`agent("x", () => 1)` 返回 `1`，而非 Promise。

`toolCall` 会将 body 的 resolved 值记录为工具的 `output`，除非你手动赋值给 `call.output`。

<Accordion title="退出语义" icon="arrow-right-from-bracket">

| 发生情况 | 事件 | `outcome` |
| --- | --- | --- |
| 代码块正常返回 | `agent_end` | `"success"`，或你指定的 `outcome` |
| 代码块抛出异常 | `error`，然后 `agent_end` | `"failed"` |
| 收到 `AbortError` | 仅 `agent_end` | `"cancelled"` |

错误始终会被重新抛出。

工具失败记录在叶节点上——`tool_result` 中含有 `error` 字符串——**不会**产生运行级别的 `error` 事件。被 agent 循环捕获的工具错误不算运行失败；向上传播的错误只会被最近的 `agent()` 报告一次。

</Accordion>

<Accordion title="`using` 形式" icon="brackets-curly">

当工作逻辑不是单一函数时——例如作用域在构造函数中打开、在析构中关闭，或横跨现有控制流——可使用此形式：

```ts
{
  using span = failproofai.agent.open("planner", { goal });
  using call = failproofai.toolCall.open("search", { input: { q } });
  call.call.output = await search(q);
}  // tool_result，然后 agent_end
```

两种形式产生的事件字节完全相同。建议优先使用回调形式：它在 `AsyncLocalStorage.run()` 内部运行，无需手动展开，也完全避免了「此处打开、彼处关闭」引发的 bug。

如果 `using` 块需要捕获自身的失败，请使用 `span.fail(error)` 进行报告——disposer 本身没有异常传递通道。

</Accordion>

## 事件目录

与 Python SDK 相同的十五个方法，采用 camelCase 命名。大多数方法以**成对**形式出现——你先调用开始方法，再调用结束方法，SDK 自动计算间隔时间。

| | 开始 | 结束 |
| --- | --- | --- |
| **Agent** | `agentStart` | `agentEnd` |
| | `agentPause` | `agentResume` |
| **模型** | `modelRequest` | `modelResponse` |
| **工具** | `toolUse` | `toolResult` |
| **Hook** | `hookTriggered` | `hookCompleted` |
| **人工** | `humanWait` | `humanInput` |

三个独立方法：`error`、`humanPause`、`humanInterrupt`。

<Accordion title="每个方法的所有字段" icon="table">

每个方法还接受 `sessionId` 和 `agentId`，作用域会自动填充。未传入的字段会被忽略，而不是以 JSON `null` 发送。

| 方法 | 必填 | 可选 |
| --- | --- | --- |
| `agentStart` | — | `goal`、`parentId` |
| `agentEnd` | — | `outcome`、`summary` |
| `agentPause` | `pauseId` | `reason`、`userId` |
| `agentResume` | `pauseId` | `reason`、`userId` |
| `modelRequest` | — | `model`、`messages`、`system`、`tools`、`requestId` |
| `modelResponse` | — | `model`、`stopReason`、`inputTokens`、`outputTokens`、`content`、`role`、`requestId` |
| `toolUse` | `toolName`、`toolCallId` | `input` |
| `toolResult` | `toolName`、`toolCallId` | `output`、`error` |
| `hookTriggered` | `hookName`、`hookId` | `triggerEvent`、`input` |
| `hookCompleted` | `hookName`、`hookId` | `outcome`、`output`、`error` |
| `error` | `errorType`、`message` | `traceback` |
| `humanWait` | `inputId` | `prompt`、`options`、`reason` |
| `humanInput` | `inputId` | `response` |
| `humanPause` | — | `reason`、`userId` |
| `humanInterrupt` | — | `reason`、`userId`、`atStep` |

你添加的其他任何键都会成为自定义 payload 字段。框架相关的字段请以 `fw_*` 命名；与已声明字段重名的键会被拒绝，而不是静默覆盖已提升的列。

</Accordion>

<Warning>
  **`duration_ms` 是计算所得，不接受外部传入。** 四个关闭方法会自动计算与对应开始方法之间的时间差，并拒绝调用方传入的 `duration_ms`——上报的时长必须不可伪造。

  配对匹配基于 **session** 和 id，而非 agent。在 `planner` 下打开、在 `worker` 下关闭的工具调用仍然可以配对，这正是嵌套多 agent 运行的实际行为。
</Warning>

## 框架适配器

```ts
await failproofai.instrument();              // 自动检测所有可用框架
await failproofai.instrument("langchain");   // 仅指定一个
failproofai.uninstrument();                  // 恢复所有原始状态
```

| 框架 | 支持版本 | 接入方式 |
| --- | --- | --- |
| **LangChain.js / LangGraph.js** | `@langchain/core` 0.3 – 1.x，LangGraph.js 0.4 – 1.x | 通过 `CallbackManager.configure` 接入，无需在任何地方传入 `callbacks:`，每次 `invoke`/`stream`/`batch` 调用均自动覆盖——或自行传入 `langchainHandler()` 并不进行任何 patch。 |
| **Vercel AI SDK** | `ai` 4 – 7 | 在调用处使用 `telemetry()`，或在 `ai` 7 上使用 `instrument("ai")` 对整个进程生效（`ai` 4–6 需手动选择启用——详见下文）。 |
| **Mastra** | `@mastra/core` 0.20 – 1.x | 覆盖 `Agent.generate`/`.stream`、agent 的模型与工具解析，以及工作流运行/步骤引擎。 |
| **LlamaIndex.TS** | `llamaindex` 0.11.4 – 0.x | 通过 `Settings.callbackManager`（订阅方式）及 `AgentWorkflow.runStream` 接入，覆盖工作流运行及其步骤。 |

每个版本范围都会在 CI 中针对真实的框架发布版本进行测试，包含两端边界，以 ES 模块和 CommonJS 两种形式在每次运行时验证。

映射关系与 Python SDK 一致，因此同一程序在两种语言中生成的树形结构相同。只有拥有 LLM 决策循环的构件才算作 **agent**——如 graph 或 chain 运行、AI SDK 的 `generateText`/`streamText` 调用、Mastra agent、LlamaIndex agent 运行。LangGraph 节点或工作流步骤是 **hook**（`hook_triggered`/`hook_completed`），而非嵌套 agent。模型调用以带有 token 计数的 `model_request`/`model_response` 对形式记录；工具调用携带模型自身的 tool call id。失败只在发生错误的事件上记录一次。

适配器安装失败时会记录日志并跳过；其他适配器仍照常安装——LlamaIndex 出问题不应影响 LangGraph 的正常使用。

<Note>
  不带参数的 `instrument()` 通过模块是否**可解析**来检测框架，而非判断是否已导入——Node 没有对应于 Python `sys.modules` 的 ES 模块等价机制。已安装但未使用的框架会被导入并打 patch。如果这一点对你有影响，请明确指定所需框架。
</Note>

<Note>
  这些框架大多同时提供 ES 模块和 CommonJS 两种构建，Node 将其作为两个不相关的副本加载。适配器会 patch 你的应用实际加载的那个副本（如果某处已 `require` 了 CommonJS 副本，也会一并 patch），因此两种模块系统均可正常工作。被 esbuild 或 webpack **打包到你自己输出中**的框架则无法触及——请在此情况下使用调用处的辅助函数：`langchainHandler()`、`telemetry()`、`wrapTool()`。
</Note>

### 不打 patch 地使用 LangChain

```ts
import { langchainHandler } from "@failproofai/sdk/langchain";
await graph.invoke(input, { callbacks: [langchainHandler()] });
```

该 handler 在有无 `instrument()` 的情况下均可工作，且不会重复记录。`instrument("langchain")` 支持 `sessionId`、`captureContent`、`includeChains`、`graphCallbacks` 和 `captureLimit` 参数，与 Python 适配器一致；在调用时通过 `metadata: { failproofai_sdk_session_id }` 可为该次调用指定 session。

### Vercel AI SDK

AI SDK 从 ES 模块导出纯函数，而 ES 模块命名空间按规范是不可变的——没有地方可以打 patch。因此使用 SDK 自身文档化的扩展点进行集成：

```ts
import { telemetry } from "@failproofai/sdk/ai";

const { text } = await generateText({
  model,
  prompt,
  experimental_telemetry: telemetry({ functionId: "answer-question" }),
  // 在 ai 7 上，使用 `telemetry: telemetry({ … })` ——对象相同，名称更新
});
```

这就是完整的集成方式：一个 agent span、每步一个带 token 计数的模型请求/响应对，以及所有工具调用。一个调用处可兼容所有主版本——`ai` 4–6 读取其携带的 tracer，`ai` 7 读取 telemetry integration。

**在 `ai` 7 上**，`instrument("ai")` 通过 AI SDK 的全局 telemetry integration 列表实现全进程覆盖，该列表是累加式的，不会影响其他人的配置。

**在 `ai` 4–6 上，`instrument("ai")` 本身不记录任何内容，并会输出一条警告。** 这些主版本唯一的全进程 hook 是全局 OpenTelemetry tracer provider——这是一个单一插槽，一旦被占用 OpenTelemetry 便不会释放。注册我们的 provider 会在后续启动时静默拒绝你的 `NodeSDK.start()`，并将 http/database span 发送到一个什么都不导出的 tracer。请在调用处使用 `telemetry()` 或 `wrapModel`。如果进程本身不使用 OpenTelemetry，可以通过 `instrument("ai", { registerGlobalTracer: true })` 显式启用：此时每个传入 `experimental_telemetry: { isEnabled: true }` 的调用都会被记录，且仅在插槽为空时才占用。`registerGlobalTracer: false` 保持默认行为并静默此警告。

如果你更倾向于一次性包裹模型，`wrapModel` 仅能看到模型调用，因为工具调用发生在模型层之上。没有外层包裹的 wrapped 模型调用会作为独立的运行被记录。流式调用的结束方式取决于流的终止情况——消费者取消时为 `stop_reason: "cancelled"`，中途失败时为 `"error"` 并附带错误信息：

```ts
import { wrapModel } from "@failproofai/sdk/ai";
const model = await wrapModel(openai("gpt-4o"));
```

两者同时使用也没有问题：middleware 会检测到该调用已在记录中，并自动让步，确保每次调用只被记录一次。

`functionId` 用于命名 agent span，请保持低基数——它会落到 `agent_id` 字段，即 Dashboard 的主要分组维度。

### Next.js

`next build` 默认会将服务器依赖打包，被打包的框架是 `instrument()` 无法触及的副本。请在 Next 的启动 hook 中调用 `instrument()` 并一次性包裹配置：

```ts
// next.config.ts
import { withFailproofai } from "@failproofai/sdk/next";
export default withFailproofai({ /* 你的配置 */ });
```

```ts
// instrumentation.ts
export async function register() {
  if (process.env.NEXT_RUNTIME !== "nodejs") return;
  const failproofai = await import("@failproofai/sdk");
  await failproofai.instrument();
}
```

`withFailproofai` 会将 LangChain、Mastra、LlamaIndex 以及 SDK 本身添加到 `serverExternalPackages`，同时保留你现有的列表。若不使用它，`instrument()` 会对每个无法触及的框架发出一次警告，而非静默失败；如果你自己已手动列出这些包，请设置 `FAILPROOFAI_NEXT_EXTERNALS=1`。Vercel AI SDK 和调用处辅助函数无论哪种方式均可正常使用。Edge 路由会获得一个空操作的构建：导入 SDK 是安全的，但不会记录任何内容。

### 流式调用的 token 计数

OpenAI 兼容 API 仅在客户端明确请求时才会在流中上报用量。LangChain 和 Vercel AI SDK 已自动请求；对于 LlamaIndex，请向其 `OpenAI` LLM 传入 `additionalChatOptions: { stream_options: { include_usage: true } }`；对于 Mastra，请在构建模型时启用 usage（例如 `createOpenAICompatible({ includeUsage: true })`）。否则流式模型调用将不包含 token 计数。

### 运行时

Node ≥ 20.9、Bun 和 Deno——每个框架，以 ES 模块和 CommonJS 两种形式，都会在各运行时上与 Node 的追踪结果进行对比测试。SDK 与 `failproofaid` 守护进程并行运行，由守护进程负责上传写入的数据。

## 自定义 Agent——不使用框架

适用于你自己编写的 agent 循环，或没有对应适配器的框架。你使用适配器底层所用的同一套 API 发送事件，因此追踪的形状和质量完全一致。

你无需了解 agent 的内部组织方式。无论函数叫什么名字，每个手工构建的 agent 都有三个关键位置，这三处就是完整的接入点：

| 位置 | 添加内容 | 触发事件 |
| --- | --- | --- |
| **一次运行**的起止位置 | `failproofai.agent("name", { goal }, async () => …)` | `agent_start` / `agent_end` |
| **调用模型的那个函数** | 调用前 `event.modelRequest`，调用后 `event.modelResponse`——失败时也要调用两端 | 每次模型调用产生一对事件 |
| **执行工具的那个函数** | `failproofai.toolCall(name, { toolCallId, input }, () => run())` | `tool_use` / `tool_result` |

```ts
async function callModel(messages) {
  const requestId = randomUUID();
  const started = Date.now();
  failproofai.event.modelRequest({ model: MODEL, requestId, messages });
  try {
    const reply = await client.chat.completions.create({ model: MODEL, messages, tools });
    failproofai.event.modelResponse({
      model: reply.model, requestId, stopReason: reply.choices[0].finish_reason,
      inputTokens: reply.usage?.prompt_tokens, outputTokens: reply.usage?.completion_tokens,
      duration_ms: Date.now() - started,
    });
    return reply.choices[0].message;
  } catch (error) {
    failproofai.event.modelResponse({ model: MODEL, requestId, stopReason: "error",
      error: String(error), duration_ms: Date.now() - started });
    throw error;
  }
}

async function dispatch(call) {
  const input = JSON.parse(call.function.arguments);
  return failproofai.toolCall(call.function.name, { toolCallId: call.id, input },
    () => runTool(call.function.name, input));
}

await failproofai.agent("inventory", { goal: question }, async () => {
  for (;;) {
    const message = await callModel(messages);
    if (!message.tool_calls?.length) return message.content;
    for (const call of message.tool_calls) await dispatch(call);
  }
});
```

身份标识是环境感知的：`agent()` 内部的所有内容都会自动关联到该运行的 session，无需手动传入 id，程序的其余部分（包括 agent 已写入自身数据库的内容）不受任何影响。

- **服务或 Worker：** 将你自己的请求或任务 id 作为 `sessionId` 传入，这样 Dashboard 上的 session 与你自己的日志或数据库记录共享同一个字符串。
- **子 Agent：** 嵌套调用 `agent()`。内层 agent 以外层 agent 的 `parent_id` 加入同一 session。
- **成对发送事件。** 没有对应 `modelResponse` 的 `modelRequest` 会在 Dashboard 上显示为一直运行中的 span——这就是为什么要在 `catch` 中也发送。

仓库中的 [`sdk/typescript/examples/research-agent.ts`](https://github.com/FailproofAI/failproofai/blob/main/sdk/typescript/examples/research-agent.ts) 是完整可运行的版本：一个真实的 OpenAI 工具循环，按照本文方式接入，在每次变更时以 ES 模块和 CommonJS 两种形式在 CI 中运行。

## 评估

```ts
import { Evaluator, EvalResult, Score } from "@failproofai/sdk/evaluator";

export const app = new Evaluator({ name: "my-evals", version: "1" });

app.eval("tool_success_rate", { version: "1" }, (session) => {
  const results = session.eventsOfType("tool_result");
  const failures = results.filter((event) => event.payload.error != null).length;
  return new EvalResult({
    score: new Score(results.length === 0 ? 1 : 1 - failures / results.length),
    reasoning: `${failures} of ${results.length} tool calls failed`,
  });
});
```

## 对你的进程的零侵入承诺

| | |
| --- | --- |
| **不阻塞 agent 循环** | 事件进入内存队列，由定时器写入磁盘。定时器已 `unref`，因此导入本包不会阻止脚本正常退出。 |
| **不无限增长** | 队列同时受数量和字节数限制。超出任一限制时，最旧的事件会被丢弃并发出警告——遥测中断不能导致 OOM 崩溃。 |
| **不拖垮进程** | 单个无法编码的事件会被单独丢弃，不影响其所在批次的其他事件。抛出异常的 getter、循环引用、`BigInt`、单独代理项——每种情况均有处理，不会向外传播。 |
| **不留下半写的批次** | 内容在原子重命名前执行 `fsync`，重命名后对目录再次 `fsync`，写入失败时会清理临时文件。 |
| **不让日志可被随意读取** | 批次文件权限为 `0600`，存放于 `0700` 目录中。它们包含目标、提示、工具参数和工具输出。 |
| **不上传凭证** | API 密钥、token、JWT、Bearer 头以及形似密钥的赋值，在字节落盘前即被脱敏处理。守护进程在上传前还会再次脱敏。 |
