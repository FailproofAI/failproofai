要求 Python 3.10 或更高版本，且**零运行时依赖**——这是一项设计原则，而非偶然。SDK 需要安装到他人的 agent 进程中，若声明了依赖，这些依赖就会被对方继承。测试会扫描核心模块，并启动一个全新的解释器来验证没有任何框架出现在 `sys.modules` 中。

## 安装

```bash
pip install failproofai-sdk
```

包名为 `failproofai-sdk`，在 Python 中以 `failproofai_sdk` 导入。`failproofai-sdk[langgraph]` 等框架扩展会安装框架本身；适配器始终包含在基础 wheel 中。

## 连接 Failproof 守护进程

<Tabs>
  <Tab title="控制台">

    3. 运行一次已接入的会话，然后在 **Observe → Events** 下找到其确切 ID。
    4. 前往 **Observe → Sessions**，选择相同的环境，打开重建的追踪记录。

## 配置

```python
import failproofai_sdk

failproofai_sdk.configure(
    base_dir=None,
    flush_interval=0.5,
    environment="production",
)
```

| 参数 | 说明 |
| --- | --- |
| `environment` | 附加在每个事件上的标签，如 `production`、`staging`、`prod-eu`。默认值为 `dev`。 |
| `flush_interval` | 后台线程写入磁盘的间隔，单位为秒。默认值为 `0.5`。 |
| `base_dir` | 写入位置。默认为 `$FAILPROOFAI_HOME/custom-agents`，否则为 `~/.failproofai/custom-agents`——即守护进程监控的缓冲目录，通常无需更改。 |

`configure()` 仅支持**关键字参数**——`configure(None, 0.5, "prod")` 会触发 `TypeError`。它会在应用所有参数之前先对每个参数进行验证，若 `flush_interval` 不是大于零的有限数值则抛出 `ValueError`，因此被拒绝的调用不会使 SDK 处于中间状态。

也可通过环境变量进行设置：

| 变量 | 说明 |
| --- | --- |
| `AGENTEYE_ENVIRONMENT` | 无需修改代码即可设置 `environment`，适合标签属于部署环境而非应用本身的场景。`configure()` 中的参数优先级高于此变量。 |
| `FAILPROOFAI_HOME` | 更改存放缓冲目录的 Failproof AI 根目录。 |
| `FAILPROOFAI_SDK_STRICT` | 设为 `1` 时，接入错误将抛出异常而非仅记录日志。 |
| `FAILPROOFAI_SDK_STRICT_INTEGRATIONS` | 设为 `1` 时，框架兼容性问题将抛出异常而非仅发出警告并继续执行。 |

<Warning>
  **`environment` 中不能含有逗号。** 数据摄取会按逗号分割该字段以构建过滤器，包含逗号的标签对应的事件将被跳过——整个运行会无声地消失。请写 `prod-eu`，而非 `prod,eu`。

  `configure(environment="prod,eu")` 会立即抛出异常。`AGENTEYE_ENVIRONMENT` 无法抛出异常（没有调用方可以接收），因此它会发出一次警告并回退到 `dev`。
</Warning>

事件会在内存中排队，每隔 `flush_interval` 秒由后台写入一次，解释器退出时执行最终刷新。被强制终止的进程会丢失尚未写入的数据。

## 作用域

三个上下文管理器，均可使用 `with` 和 `async with`：

| 作用域 | 绑定内容 | 发出事件 |
| --- | --- | --- |
| `session()` | 一个 session id，并将其作为 yield 值返回 | 无——仅标识用途 |
| `agent(name)` | 一个 agent id，以及从外层 agent 推断出的 `parent_id` | 进入时发出 `agent_start`，退出时发出 `agent_end` |
| `tool_call(name)` | 无新绑定——继承外层标识 | 进入时发出 `tool_use`，退出时发出 `tool_result` |

```python
with failproofai_sdk.session():
    with failproofai_sdk.agent("planner"):
        with failproofai_sdk.tool_call("web_search", input={"q": q}) as t:
            t.output = search(q)
```

`tool_call()` 默认将 `tool_call_id` 设为新生成的 `uuid4().hex`，并在进入时一次性解析标识，因此在其内部推送自身作用域的工具无法使 `tool_result` 归属到不同的 agent。发生异常时会发出 `tool_result(error="TypeName: msg")`，**不会发出 `error` 事件**——循环捕获的工具失败不属于运行级别错误，向外传播的异常由外层 `agent()` 精确上报一次。取消操作会关闭叶节点，且不含错误字符串。

## 适配器

`instrument()` 将受支持的框架连接到上述作用域。不带参数时自动检测当前进程中已导入的框架；传入名称则精确安装指定的一个。

```python
failproofai_sdk.instrument()              # 检测所有已导入的框架
failproofai_sdk.instrument("crewai")      # 仅安装指定框架
failproofai_sdk.uninstrument("crewai")    # 还原原始属性
```

四个可用名称为：`"langchain"`（涵盖 LangGraph，因为 LangGraph 运行在 langchain-core 的回调管理器上）、`"crewai"`、`"llama_index"` 和 `"pydantic_ai"`。框架的导入发生在调用内部，这也是 `import failproofai_sdk` 保持零依赖的原因。

每个框架均有专属页面：[LangChain](/zh/start/integrations/langchain)、[CrewAI](/zh/start/integrations/crewai)、[LlamaIndex](/zh/start/integrations/llamaindex)、[Pydantic AI](/zh/start/integrations/pydantic-ai)。

## 标识

每个事件都属于某个 session 和 agent。**作用域会自动填充两者**，因此通常无需手动传入：

```python
with failproofai_sdk.session():
    with failproofai_sdk.agent("planner"):
        failproofai_sdk.event.tool_use(tool_name="search", tool_call_id="c1")
```

显式传入 `session_id` 或 `agent_id` 同样有效，且优先级更高。

两者在**未绑定任何内容时的行为并不对称**：

| 省略项 | 未绑定时的行为 |
| --- | --- |
| `session_id` | 抛出 `TypeError`，而非发出一个 Cloud 会静默丢弃的事件 |
| `agent_id` | 回退为 `main`，因此在 `session()` 内、没有 `agent()` 包裹的情况下发出的事件全部归属到名为 `main` 的单个 agent 下 |

若自动生成 session id，一次运行会被分散到与发射点数量相同的多个 session 中，这也是只有 `session_id` 缺失时才会抛出异常的原因。

`session_id` 和 `agent_id` 也是仅有的两个会检查空值的字段：非字符串类型抛出 `TypeError`，空字符串或纯空白字符串抛出 `ValueError`。服务端*接受*空白 id，因此若不加以检查，使用空白 id 发送的所有事件都会被归并到同一个空白 id 下，表面上看似存在，实则被静默合并。

<Note>
  标识通过上下文变量传递。它会自动跟随 `asyncio` 任务，但**不会**跟随新线程——请用 `failproofai_sdk.propagate()` 包装 worker，否则其事件将无法关联到正确的上下文。
</Note>

## 事件目录

共 15 个方法，大多数以**成对**形式出现——一个开启，一个关闭。

| | 开启 | 关闭 | SDK 计时 |
| --- | --- | --- | --- |
| **Agents** | `agent_start` | `agent_end` | 否 |
| | `agent_pause` | `agent_resume` | 是 |
| **Models** | `model_request` | `model_response` | 否——在 Cloud 中关联 |
| **Tools** | `tool_use` | `tool_result` | 是 |
| **Hooks** | `hook_triggered` | `hook_completed` | 是 |
| **Humans** | `human_wait` | `human_input` | 是 |

三个独立方法：`error`、`human_pause`、`human_interrupt`。

<Accordion title="每个方法的所有字段" icon="table">

每个方法还接受 `session_id` 和 `agent_id`，作用域会自动填充这两个值。保持为 `None` 的字段会被丢弃，而非以 JSON `null` 形式发送；每个方法均返回 `None`。

| 方法 | 必填 | 可选 |
| --- | --- | --- |
| `agent_start` | — | `goal`, `parent_id` |
| `agent_end` | — | `outcome`, `summary` |
| `agent_pause` | `pause_id` | `reason`, `user_id` |
| `agent_resume` | `pause_id` | `reason`, `user_id` |
| `model_request` | — | `model`, `messages`, `system`, `tools`, `request_id` |
| `model_response` | — | `model`, `stop_reason`, `input_tokens`, `output_tokens`, `content`, `role`, `request_id`, `duration_ms` |
| `tool_use` | `tool_name`, `tool_call_id` | `input` |
| `tool_result` | `tool_name`, `tool_call_id` | `output`, `error` |
| `hook_triggered` | `hook_name`, `hook_id` | `trigger_event`, `input` |
| `hook_completed` | `hook_name`, `hook_id` | `outcome`, `output`, `error` |
| `error` | `error_type`, `message` | `traceback` |
| `human_wait` | `input_id` | `prompt`, `options`, `reason` |
| `human_input` | `input_id` | `response` |
| `human_pause` | — | `reason`, `user_id` |
| `human_interrupt` | — | `reason`, `user_id`, `at_step` |

</Accordion>

<Warning>
  要将一次运行标记为失败，`outcome` 必须为以下之一：`failed`、`error`、`timeout` 或 `rejected`。其他任何值——包括拼写相近的 `"failure"`——均视为成功。
</Warning>

## 配对与计时

**一条规则：为关闭事件传入与开启事件相同的 id。** 这是配对的依据，也是 SDK 计算时间差的方式。

| 配对 | 匹配字段 | 追踪键 |
| --- | --- | --- |
| `tool_use` → `tool_result` | `tool_call_id` | `tool:{session_id}:{tool_call_id}` |
| `hook_triggered` → `hook_completed` | `hook_id` | `hook:{session_id}:{hook_id}` |
| `agent_pause` → `agent_resume` | `pause_id` | `pause:{session_id}:{pause_id}` |
| `human_wait` → `human_input` | `input_id` | `human:{session_id}:{input_id}` |

追踪键以 session 为命名空间，这也是下面两个边界情况均成立的原因。

**不要在这四个关闭事件中自行传入 `duration_ms`。** SDK 会自动测量，手动传入会抛出 `ValueError`。

<Note>
  `model_request` 和 `model_response` 是一对，Cloud 通过 `request_id` 进行关联。SDK 不在本地追踪或计时，这也是 `model_response` 是唯一需要你手动传入 `duration_ms` 的事件的原因。请传入整数毫秒数——浮点数会抛出异常，因为该列为 32 位整数，传入浮点数会导致值为空。
</Note>

<Accordion title="边界情况" icon="circle-help">

- **Id 只需在同一类型、同一 session 内唯一。** 一个 tool call 和一个 hook 可以共用同一个 id；同时运行的两个 session 也可以复用相同的 id，不会发生冲突。
- **Id 的作用域不限于单个 agent。** 在一个 agent 下开启、在另一个 agent 下关闭的配对仍然能够匹配——这在多 agent 代码中是正常情况。
- **`request_id` 可选但建议填写。** 若不填写，model 事件会按到达顺序配对，同一 agent 中的两个并发调用可能会错配。
- **跨进程的配对**在 Cloud 中仍然能够匹配，但 SDK 无法计时——两个进程都未同时看到配对的两端。
- **最多 10,000 个开启事件等待关闭事件。** 超过此限制后最旧的条目会被丢弃，因此泄漏不会无限增长。

</Accordion>

## 自定义字段

传入的任何额外关键字都会随事件一起存储：

```python
failproofai_sdk.event.tool_use(
    tool_name="search", tool_call_id="c1",
    fw_tenant="acme", fw_region="eu-west-1",     # 自定义字段
)
```

如需后续查询，建议使用 JSON 兼容类型。其他类型——UUID、datetime、`Decimal`、set、bytes、模型对象——均会以字符串形式存储。

<Warning>
  **有十一个字段名是例外，传入时会抛出异常而非转为字符串。** 数据摄取会将这些字段提升到带类型的列中，其他值则在返回 `200 OK` 时静默存为 `NULL`——因此 SDK 在调用处直接拒绝它们。

  | 字段名 | 必须为 |
  | --- | --- |
  | `duration_ms`, `input_tokens`, `output_tokens` | 无符号 32 位范围内的 `int` |
  | `tool_name`, `tool_call_id`, `hook_name`, `hook_id`, `input_id`, `pause_id`, `error_type`, `model` | 字符串——`None` 抛出 `ValueError`，非字符串抛出 `TypeError` |

  无论该值是作为具名参数传入还是作为自定义字段传入，上述规则均适用。`model_response` 在接收时会验证 `input_tokens` 和 `output_tokens`，原因相同——这两个字段最有可能直接从 provider 的 usage 对象中填充。
</Warning>

<Warning>
  **请为自定义字段名添加前缀。** 额外字段最后应用，因此名为 `model`、`tool_name` 或 `outcome` 的字段会静默覆盖原有字段。框架适配器使用 `fw_` 前缀；采用相同约定即可避免冲突。

  这也是为什么拼错的可选字段不会报错——它只会变成一个新的自定义字段。如果 Cloud 中某个标准字段缺失，请先检查拼写。
</Warning>

以下五个字段名为保留字段，传入时会被直接拒绝：`timestamp`、`session_id`、`agent_id`、`type`、`environment`。

## 其他导出项

| 导出项 | 说明 |
| --- | --- |
| `current()` | 当前绑定的标识，返回 `Identity` 对象。`current().session_id is None` 表示当前没有绑定任何标识 |
| `Identity` | 包含 `session_id`、`agent_id`、`parent_id`、`depth`。对象本身不会为 `None`——请检查其字段 |
| `propagate(fn)` | 将 `fn` 包装，使其以包装时绑定的标识运行。用于 `Thread`、`pool.submit`、`pool.map`、`run_in_executor` |
| `_writer.flush_now()` | 立即清空并写入缓冲条目，用于测试或在退出前强制刷新 |
| `__version__` | 已安装的 SDK 版本 |

## 投递与验证

<Tabs>
  <Tab title="控制台">
    在 **Observe → Events** 中，先确认 `agent_start` 存在于最前，`agent_end` 存在于最后。然后打开 **Observe → Sessions**，确认 model、tool、human、hook 和 error 事件按预期顺序出现。使用 session ID 作为主要的排查线索。
  </Tab>
  <Tab title="CLI">
    ```bash
    failproofai flush --wait --timeout 60
    failproofai config --status
    fp sessions --since 1h --env production --session-id <session-id>
    fp events --since 1h --session-id <session-id> --full
    ```
  </Tab>
</Tabs>

若 Cloud 中没有数据，请检查 `$FAILPROOFAI_HOME/custom-agents/events`，否则检查 `~/.failproofai/custom-agents/events`。JSONL 文件证明 SDK 已成功发出事件；缓冲目录持续增长说明问题在守护进程配置或投递环节，缓冲目录为空则说明问题在接入代码或进程生命周期。

<Note>
  仅在守护进程停止时检查缓冲目录。守护进程运行期间会在毫秒内收集并删除每个批次，因此目录列表会与收集器竞争，显示的事件数量远少于实际发出的数量。
</Note>

## 在自定义运行时中防止失败

使用审计发现和关联追踪记录来定义不安全操作、所需证据和预期响应。自定义执行接入必须在执行前暴露操作，将其结构化输入传递给策略引擎，并应用所得的 allow、instruct 或 deny 决策。

[联系 Failproof AI](mailto:support@befailproof.ai)，我们将协助你将运行时的 model、tool 和生命周期边界映射到策略钩子，并与你共同验证该接入。
