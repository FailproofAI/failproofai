使用 `npm install -g failproofai` 安装本地 CLI。不带参数运行时将打开本地策略仪表盘。

该包需要 Node.js 20.9 或更高版本。Bun 1.3 或更高版本支持开发和源码安装。`failproofai configure` 和 `failproofai setup` 是 `failproofai config` 的别名。`failproofai policy`、`failproofai pack` 和 `failproofai p` 都是 `failproofai policies` 的拼写变体——包和单个策略原本是三个命令对应一个概念，现已合并为一个。旧拼写仍然有效，但有两个例外：`pack list <source>` 现在是 `policies show <source>`，`pack build` 现在是 `publish`。

## 配置机器

安装 CLI，然后将机器密钥读入 shell。`read -s` 通过不回显的提示符接收密钥，因此密钥不会出现在命令中：

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

然后配置机器并选择要执行的策略：

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` 是完整的配置流程：它安装 `failproofaid` 服务（以 root 身份执行一次——在终端中会请求 sudo 密码，如果配置完成前密码过期则会再次请求；无终端时使用 `sudo -n`，永不提示），将 hooks 接入它找到的每个代理 CLI，并连接到 Cloud。在无终端环境下（CI、容器、由代理驱动）会直接应用而非询问，如果任何被要求执行的操作未能完成则以状态码 1 退出。

在终端中，对于尚未连接的机器，**连接到 cloud** 步骤会立即开始**登录 FailproofAI Cloud**；按 Tab 键可查看其他选项：**粘贴 API 密钥**或**使用开源版本**。登录时会打开一个链接——或者在 SSH 或无显示器环境下将其打印出来，可在任意设备上打开——在该链接中注册或登录、选择或创建组织并授权该机器；终端会自动检测到授权结果，并显示授权者及所属组织。密钥仅在配置完成后（守护进程安装后）生成。对于已连接且密钥有效的机器，该步骤会以**保持当前连接**为首选项显示菜单，因此重新运行配置不会自动打开浏览器；如果已保存的密钥失效，则会立即重新登录并说明原因。重新登录会生成新密钥，旧密钥在撤销前仍然有效。浏览器登录之前的 Cloud 版本会提示相关说明并提供其他选项。

默认**不启用**任何策略。这是第二条命令的职责，没有它，新配置的机器除始终开启的安全守卫外不执行任何策略。

优先使用环境变量而非 `--token`：命令行参数可被机器上的所有用户通过 `ps` 读取。这是该变量唯一能防范的风险——输入到任何命令中的密钥（包括 `export`）仍会留存在 shell 历史记录中，这也是上面使用 `read -s` 读取密钥的原因。在 CI 中，从密钥存储中设置该变量，并关闭 shell 追踪（`set -x`），否则追踪信息会将其打印出来。

<Warning>
  `--connect <url>` 用于注册**已完成配置**的机器。它在注册成功后立即返回——不会安装守护进程，也不会接入任何 hooks。对于尚未配置的机器，请使用普通的 `failproofai config`（或 `failproofai config --token <key>`），否则机器将显示为已连接但实际上不收集或执行任何内容。
</Warning>

不带参数运行 `failproofai` 可打开本地策略仪表盘。

| 命令 | 说明 |
| --- | --- |
| `failproofai config` | 配置机器：代理、守护进程和 Cloud——通过浏览器登录、粘贴密钥或使用开源版本。机器上的每个代理还会获得一个指向 [FailproofAI skills](https://github.com/FailproofAI/skills) 在线资源的小型 `failproofai` 技能 |
| `failproofai config --token <key>` | 一步完成配置和连接，无需任何交互。携带 `jev:evaluate` 权限的密钥还会以观察模式启用 [通过 FailproofAI Cloud 的 Jev](/zh/reference/jev-cloud)，除非已存在 `jev.json` 或指定了 `--no-transcripts` |
| `failproofai config --connect <url>` | 注册**已完成配置**的机器——不含守护进程和 hooks |
| `failproofai config --status` | 显示连接、守护进程、投递和暂停状态 |
| `failproofai policies` | 列出内置、自定义、约定、包和 Cloud 管理的策略 |
| `failproofai policies --install` | 将 hooks 接入代理 CLI。本身不启用任何策略 |
| `failproofai policies add <name>` | 启用一个策略——内置策略，或来自已安装包的 `<pack-id>:<name>` |
| `failproofai policies remove <name>` | 禁用一个策略，命名规则相同 |
| `failproofai policies --uninstall` | 禁用策略或移除 harness hooks |
| `failproofai policies show <owner>/<repo>` | 在获取包之前，从其清单中读取包含的内容 |
| `failproofai policies show <owner>/<repo> --releases` | 已发布的所有版本，以及当前安装的版本 |
| `failproofai policies add <source>` | 从 GitHub release 安装策略包；不指定标签时取最新版本并锁定 |
| `failproofai publish` | 将自己的策略发布为包；`--init` 生成初始模板，`--min-cli-version <version>` 设置可安装该包的最低 CLI 版本（[包中的 Jev 检查](/zh/policies/publish-a-pack#jev-checks-in-a-pack)） |
| `failproofai policies remove <publisher/name>` | 卸载一个包 |
| `failproofai audit` | 扫描本地代理历史记录并打开本地审计视图 |
| `failproofai audit --schedule [days] --email <address>` | 安排定期本地扫描并通过邮件发送结果 |
| `failproofai audit --status` | 显示报告地址、间隔时间和下次计划扫描时间 |
| `failproofai audit --no-schedule` | 停止定期扫描，但不删除审计历史记录 |
| `failproofai harness list` | 列出额外的采集路径 |
| `failproofai otel status` | 检查可选的 [OpenTelemetry 上报](/zh/reference/otel) |
| `failproofai jev --url <url> --key-stdin` | 一步完成 Jev 配置；提供商从 URL 的主机名中获取 |
| `failproofai jev setup --provider <kind> --key-stdin` | 让 [Jev](/zh/reference/jev-providers) 通过您自己的端点和密钥判断工具调用 |
| `failproofai jev setup --provider failproofai` | 让 Jev [通过 FailproofAI Cloud](/zh/reference/jev-cloud) 判断工具调用，使用本机的 Cloud 密钥 |
| `failproofai jev setup --mode <m>` | 切换 Jev 模式：`enforce`、`observe` 或 `off`（保留配置，停止调用 Jev） |
| `failproofai jev status` | 显示 Jev 配置、权限和近期回退情况；不显示密钥 |
| `failproofai jev test` | 发送一个实时 Jev 请求并显示其延迟和版本；响应超时或结果错误时以状态码 1 退出 |
| `failproofai jev models` | 列出端点通过 `GET <base>/models` 返回的模型 ID |
| `failproofai jev remove` | 关闭 Jev；hooks 将完全按照以前的方式运行正则策略 |
| `failproofai flush --wait` | 投递当前事件队列 |
| `failproofai backfill --since 30d` | 重新读取之前已通过的历史记录 |
| `failproofai config --pause [duration]` | 暂停当前会话，默认 30 分钟，最长 8 小时 |
| `failproofai config --resume` | 恢复一个已暂停的本地会话；加 `--all` 清除所有暂停 |
| `failproofai update` | 完成包迁移并更新守护进程 |
| `failproofai migrate --dry-run` | 预览或执行待处理的 home 布局迁移 |
| `failproofai uninstall` | 在移除包之前移除 hooks、`failproofai` 技能和守护进程 |
| `failproofai --version` | 打印已安装的包版本 |
| `failproofai --help` | 显示命令和全局用法 |

## 配置标志

| 标志 | 用途 |
| --- | --- |
| `--token <key>` | 非交互式配置和连接；也可从 `FAILPROOFAI_CLOUD_TOKEN` 读取 |
| `--url <url>` | 连接到 `app.befailproof.ai` 以外的地址；也可从 `FAILPROOFAI_CLOUD_URL` 读取 |
| `--connect <url>` | 仅注册，用于已完成配置的机器。跳过守护进程和所有 hooks |
| `--machine-id <id>` | 设置稳定的机器 ID |
| `--machine-label <name>` | 重命名**已连接**的机器。单独使用时不会执行配置，请在 `failproofai config` 之后而非期间使用 |
| `--no-transcripts` | 发送决策时不包含转录内容，且不启用 Cloud Jev（后者会发送每个被检查的工具调用和最近的提示词）；已运行通过 FailproofAI Cloud 的 Jev 的 `jev.json` 将被移除 |
| `--disconnect` | 停止 Cloud 策略拉取和事件投递。同时移除 Cloud Jev 密钥以及指向 FailproofAI Cloud 的 `jev.json`；您自己的 Jev 配置保持不变 |
| `--status` | 显示当前机器状态 |
| `--pause [duration]` | 暂停当前目录中的最新会话；接受秒、分钟或小时，默认 30 分钟 |
| `--resume` | 提前结束匹配的暂停 |
| `--session <id>` | 为暂停或恢复指定明确的会话 |
| `--all` | 与 `--resume` 配合使用，结束所有活跃的暂停 |

本地会话暂停会为一个会话挂起内置、自定义、约定和包策略。暂停始终会到期，且不会禁用 Cloud 管理的策略。`block-failproofai-commands`——始终开启且本身无法被禁用或暂停——可防止被检测的代理自行使用此退出机制。

## 策略标志

| 标志 | 用途 |
| --- | --- |
| `--install`, `-i` | 安装 harness hooks。其后的名称将启用对应策略；若无名称则不更改任何策略 |
| `--uninstall`, `-u` | 禁用策略或移除 hooks |
| `--cli <names...>` | 针对一个或多个支持的 harness |
| `--scope user\|project\|local\|all` | 选择配置范围；`all` 用于卸载 |
| `--beta` | 包含 beta 版策略 |
| `--custom`, `-c <path>` | 验证并加载自定义策略文件；可重复使用 |

## 投递和维护标志

| 命令 | 标志 |
| --- | --- |
| `backfill` | `--since <30d\|6m\|YYYY-MM-DD>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` |

`failproofai update` 应在 `npm install -g failproofai@latest` 之后运行；它执行 home 布局迁移、安装匹配的守护进程二进制文件并重启服务。然后将所有已使用 FailproofAI 的 Hermes 配置文件移至链接的原生插件，并为每个配置文件打印一行信息。`--no-daemon` 跳过守护进程步骤。当守护进程无法替换、迁移失败或 Hermes 配置文件无法迁移时（例如因为运行中的守护进程无法为原生插件提供服务，此时其 shell hooks 保持不变），`update` 以非零状态码退出。

## Harness 路径

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

支持的 harness 名称包括 `claude`、`codex`、`copilot`、`cursor`、`opencode`、`pi`、`hermes`、`openclaw`、`factory`、`devin`、`antigravity` 和 `goose`。

当两个根目录包含同一项目的副本时，标签用于为派生的代理 ID 提供命名空间。重叠的根目录和重复的标签会被拒绝，以防止重复采集或游标损坏。额外路径配置无需重启守护进程即可重新加载。

容器环境可以使用以逗号分隔的变量 `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` 替换文件配置的额外路径，例如：

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## 环境变量

对于持久性机器配置，请使用配置文件。环境变量最适用于容器、测试和单进程场景。

| 变量 | 用途 |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | Cloud 密钥，替代 `--token`。推荐使用此方式：命令行参数可被机器上所有用户通过 `ps` 读取。使用 `read -s` 或从 CI 密钥存储中设置，切勿直接输入到命令中，否则无论如何都会留存在 shell 历史记录中 |
| `FAILPROOFAI_CLOUD_URL` | Cloud URL，替代 `--url`。守护进程读取的同一变量 |
| `FAILPROOFAI_HOME` | 重新定位完整的 `~/.failproofai` 布局 |
| `FAILPROOFAI_LOG_LEVEL` | 设置本地日志详细程度 |
| `FAILPROOFAI_HOOK_LOG_FILE` | 将 hook 诊断信息写入指定文件 |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | 为当前进程禁用匿名遥测 |
| `FAILPROOFAI_NO_FIRST_RUN=1` | 跳过交互式首次运行配置 |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | 跳过配置后的本地审计 |
| `FAILPROOFAI_LLM_BASE_URL` | 覆盖 LLM 策略使用的 OpenAI 兼容端点 |
| `FAILPROOFAI_LLM_API_KEY` | 提供 LLM 策略使用的 API 密钥 |
| `FAILPROOFAI_LLM_MODEL` | 选择 LLM 策略使用的模型 |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | 限制自定义策略模块的加载时间 |
| `FAILPROOFAI_NO_DOWNLOAD=1` | 拒绝获取包和守护进程二进制文件；已安装的内容继续执行 |
| `FAILPROOFAI_PACK_BASE_URL` | 从镜像而非 `github.com` 获取包 |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | 替换某个 harness 已配置的额外采集路径 |
| `NO_COLOR` | 禁用彩色终端输出 |

特定代理的 home 变量（如 `CLAUDE_PROJECTS_PATH`、`CURSOR_HOME`、`HERMES_HOME` 和 `OPENCLAW_HOME`）会覆盖 Failproof AI 为该 harness 发现本地会话的位置。

## 安全地暂停或移除机器

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

本地会话暂停不会禁用 Cloud 管理的策略。当发布流程本身出现问题时，请通过 Cloud 执行工作流恢复 Cloud 部署。

在移除 npm 包之前，先移除已安装的 hooks 和守护进程：

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

运行 `failproofai <command> --help` 获取特定版本的详细信息。

<Warning>
  请在 `npm rm -g failproofai` 之前运行 `failproofai uninstall`；npm 不会移除已安装的代理 hooks、`failproofai` 技能或守护进程服务。
</Warning>
