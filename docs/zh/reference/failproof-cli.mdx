使用 `npm install -g failproofai` 安装本地 CLI。不带参数运行可打开本地策略仪表板。

此包需要 Node.js 20.9 或更高版本。开发环境和源码安装支持 Bun 1.3 或更高版本。`failproofai configure` 和 `failproofai setup` 是 `failproofai config` 的别名。`failproofai policy`、`failproofai pack` 和 `failproofai p` 都是 `failproofai policies` 的写法——包和单项策略曾是三个命令对应同一个概念，现已合并为一个。旧写法仍然有效，但有两个例外：`pack list <source>` 现为 `policies show <source>`，`pack build` 现为 `publish`。

## 配置机器

安装 CLI，然后将机器密钥读入 shell。`read -s` 通过不回显的提示符接收密钥，确保其不会出现在命令中：

```bash
npm install -g failproofai
read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
```

然后配置机器并选择要执行的策略：

```bash
failproofai config
failproofai policies add FailproofAI/policies
failproofai config --status
```

`failproofai config` 涵盖整个配置流程：安装 `failproofaid` 服务（需要 root 权限一次——在终端中会请求 sudo 密码，若配置未完成前密码过期则再次请求；无终端时使用 `sudo -n`，从不提示），将钩子接入它找到的每个代理 CLI，并连接到云端。在无终端环境（CI、容器、由代理驱动）下，它直接应用配置而非询问，若有任何要求执行的操作未能完成则以状态码 1 退出。

在终端中，对于尚未连接的机器，**连接到云端**步骤会立即启动**登录 FailproofAI Cloud**；按 Tab 键可切换其他选项：**粘贴 API 密钥**或**使用开源版本**。登录时会打开一个链接——或者在 SSH 或无显示器的情况下打印该链接，可在任意设备上打开——用于注册或登录、选择或创建组织，并授权该机器；终端会自动获取授权结果，并显示授权者及所属组织。密钥仅在配置完成、守护进程安装后才会生成。对于已用有效密钥连接的机器，该步骤会显示一个菜单，首选**保留当前连接**，因此重新运行配置不会自动打开浏览器；若已保存的密钥不再有效，则会立即重新启动登录流程并说明原因。重新登录会生成新密钥，旧密钥在你主动撤销前仍然有效。若云端版本早于浏览器登录功能，系统会予以提示并提供其他选项。

默认**不选择**任何策略。这是第二条命令的职责，若不执行该命令，新配置的机器除始终启用的守护防护外不执行任何策略。

请优先使用环境变量而非 `--token`：命令行参数可被机器上所有用户通过 `ps` 读取。环境变量仅能防止这种情况——通过任何命令（包括 `export`）输入的密钥仍会留在 shell 历史记录中，这正是上述使用 `read -s` 读取的原因。在 CI 中，请从密钥存储中设置它，并关闭 shell 跟踪（`set -x`），否则跟踪输出会将其打印出来。

<Warning>
  `--connect <url>` 用于注册**已配置好的**机器。它在注册成功后立即返回——不安装守护进程，也不接入任何钩子。对于尚未配置的机器，请使用普通的 `failproofai config`（或 `failproofai config --token <key>`），否则机器会显示已连接，但实际上不收集任何数据，也不执行任何策略。
</Warning>

不带参数运行 `failproofai` 可打开本地策略仪表板。

| 命令 | 功能 |
| --- | --- |
| `failproofai config` | 配置机器：代理、守护进程和云端——通过浏览器登录、粘贴密钥或保持开源模式。机器上的每个代理还会获得一个小型 `failproofai` 技能，指向在线的 [FailproofAI skills](https://github.com/FailproofAI/skills) |
| `failproofai config --token <key>` | 一次性完成配置和连接，无需任何交互。携带 `jev:evaluate` 权限的密钥还会以观察模式启用[通过 FailproofAI Cloud 使用 Jev](/zh/reference/jev-cloud)，除非 `jev.json` 已存在或提供了 `--no-transcripts` |
| `failproofai config --connect <url>` | 仅注册**已**配置好的机器——无守护进程，无钩子 |
| `failproofai config --status` | 显示连接、守护进程、投递和暂停状态 |
| `failproofai policies` | 列出内置、自定义、约定、包和云端管理的策略 |
| `failproofai policies --install` | 将钩子接入代理 CLI。本身不启用任何策略 |
| `failproofai policies add <name>` | 启用一条策略——内置策略，或已安装包中的 `<pack-id>:<name>` |
| `failproofai policies remove <name>` | 禁用一条策略，命名方式相同 |
| `failproofai policies --uninstall` | 禁用策略或移除测试框架钩子 |
| `failproofai policies show <owner>/<repo>` | 在安装前通过包清单查看该包的内容 |
| `failproofai policies show <owner>/<repo> --releases` | 查看已发布的所有版本及当前安装版本 |
| `failproofai policies add <source>` | 从 GitHub Release 安装策略包；不指定标签则获取最新版本并固定 |
| `failproofai publish` | 将自己的策略发布为包；`--init` 生成初始模板，`--min-cli-version <version>` 设置可安装该包的最低 CLI 版本（[Jev checks in a pack](/zh/policies/publish-a-pack#jev-checks-in-a-pack)） |
| `failproofai policies remove <publisher/name>` | 卸载一个包 |
| `failproofai audit` | 扫描本地代理历史记录并打开本地审计视图 |
| `failproofai audit --schedule [days] --email <address>` | 安排定期本地扫描并通过邮件发送结果 |
| `failproofai audit --status` | 显示报告地址、间隔和下次计划扫描时间 |
| `failproofai audit --no-schedule` | 停止定期扫描而不删除审计历史 |
| `failproofai harness list` | 列出额外的捕获路径 |
| `failproofai otel status` | 检查可选的 [OpenTelemetry 报告](/zh/reference/otel) |
| `failproofai jev --url <url> --key-stdin` | 一步完成 Jev 配置；提供商从 URL 的主机名获取 |
| `failproofai jev setup --provider <kind> --key-stdin` | 让 [Jev](/zh/reference/jev-providers) 通过你自己的端点和密钥评判工具调用 |
| `failproofai jev setup --provider failproofai` | 让 Jev [通过 FailproofAI Cloud](/zh/reference/jev-cloud) 评判工具调用，使用该机器的云端密钥 |
| `failproofai jev setup --mode <m>` | 切换 Jev 模式：`enforce`、`observe` 或 `off`（保留配置，停止调用 Jev） |
| `failproofai jev status` | 显示 Jev 配置、权限和近期回退情况；从不显示密钥 |
| `failproofai jev test` | 发送一次实时 Jev 请求并显示延迟和版本；若响应对钩子来说过迟或结果错误则以 1 退出 |
| `failproofai jev models` | 列出端点 `GET <base>/models` 返回的模型 ID |
| `failproofai jev remove` | 关闭 Jev；钩子将完全按之前的方式运行正则策略 |
| `failproofai flush --wait` | 投递当前事件队列 |
| `failproofai backfill --since 30d` | 重新读取此前已处理的历史记录 |
| `failproofai config --pause [duration]` | 暂停当前目录中最新的会话，默认 30 分钟，最长 8 小时 |
| `failproofai config --resume` | 恢复一个已暂停的本地会话；添加 `--all` 可清除所有暂停 |
| `failproofai update` | 完成包迁移并更新守护进程 |
| `failproofai migrate --dry-run` | 预览或执行待处理的 home 布局迁移 |
| `failproofai uninstall` | 在移除包前，移除钩子、`failproofai` 技能和守护进程 |
| `failproofai --version` | 打印已安装的包版本 |
| `failproofai --help` | 显示命令和全局用法 |
| `failproofai help <command>` | 显示某个命令的选项和示例，等同于 `failproofai <command> --help` |

## 配置标志

| 标志 | 用途 |
| --- | --- |
| `--token <key>` | 非交互式配置和连接；也可从 `FAILPROOFAI_CLOUD_TOKEN` 读取 |
| `--oss` | 在无云端连接的情况下使用开源版本；已有连接保持不变 |
| `--agents <a,b>` | 追踪这些代理，或 `all`，无需询问 |
| `--url <url>` | 连接到 `app.befailproof.ai` 以外的地址；也可从 `FAILPROOFAI_CLOUD_URL` 读取 |
| `--connect <url>` | 仅注册，适用于已配置好的机器。跳过守护进程和所有钩子 |
| `--machine-id <id>` | `--connect` 使用的机器 ID；默认为稳定 ID |
| `--machine-label <name>` | 单独使用时，重命名**已连接**的机器；不运行配置。与 `--token` 一起使用时，以该名称连接；仅在 `FAILPROOFAI_CLOUD_TOKEN` 中设置密钥不够，因为不带 `--token` 的 `--machine-label` 是重命名操作。与 `--oss` 或 `--agents` 一起使用时，会重命名已连接的机器，并在未配置的机器上拒绝操作：`--oss` 不进行连接，而 `--agents` 需要密钥或交互式云端登录才能连接 |
| `--no-transcripts` | 仅发送决策而不包含记录内容，且不启用云端 Jev（后者会发送每个被检查的工具调用和近期提示词）；正在通过 FailproofAI Cloud 运行 Jev 的 `jev.json` 将被移除 |
| `--disconnect` | 停止云端策略拉取和事件投递。同时移除云端 Jev 密钥及指向 FailproofAI Cloud 的 `jev.json`；你自己的 Jev 配置保持不变 |
| `--status` | 显示当前机器状态 |
| `--pause [duration]` | 暂停当前目录中最新的会话；接受秒、分钟或小时，默认 30 分钟 |
| `--resume` | 提前结束匹配的暂停 |
| `--session <id>` | 为暂停或恢复指定明确的会话 |
| `--all` | 与 `--resume` 一起使用，结束所有活跃的暂停 |

本地暂停会为一个会话暂停内置、自定义、约定和包策略。暂停始终会过期，在一次运行中首次暂停后最多 8 小时，且不会禁用云端管理的策略或 `block-failproofai-commands`——后者始终启用且本身无法被禁用或暂停。该守护防护会拒绝受监控代理暂停自身的直接方式：运行 `failproofai config --pause`，或在 `~/.failproofai/state/sessions/` 下写入暂停文件。它读取的是命令，而非脚本运行时的行为，因此代理编写后运行的脚本仍可达到相同状态。暂停文件会被检查是否有有效的过期时间和不超过一分钟后的开始时间，但不检查写入者。

## 策略标志

| 标志 | 用途 |
| --- | --- |
| `--install`, `-i` | 安装测试框架钩子。其后的名称会启用对应策略；若无名称，则不更改任何策略 |
| `--uninstall`, `-u` | 禁用策略或移除钩子 |
| `--cli <names...>` | 目标一个或多个受支持的测试框架 |
| `--scope user\|project\|local\|all` | 选择配置范围；`all` 用于卸载 |
| `--beta` | 包含 beta 策略 |
| `--custom`, `-c <path>` | 与 `--install` 一起使用，验证并加载自定义策略文件；可重复使用。`--uninstall -c` 移除所有自定义策略文件 |
| `--policy`, `--only <a,b>` | 仅从包中安装这些策略 |
| `--category <x,y>` | 仅从包中安装这些类别 |
| `--all` | 列出所有策略；与包一起使用时，安装包的全部内容 |
| `--releases` | 与 `show` 一起使用，列出包的所有版本及已安装的版本 |

## 投递与维护标志

| 命令 | 标志 |
| --- | --- |
| `backfill` | `--since <30d\|6m\|1y\|YYYY-MM-DD>`, `--agents <a,b>`, `--dry-run` |
| `flush` | `--wait`, `--timeout <seconds>` |
| `update` | `--no-daemon` |
| `migrate` | `--dry-run` |
| `uninstall` | `--purge`, `--dry-run`, `--yes` (`-y`) |

### 按测试框架回填

`backfill` 重新发送收集器已读取的历史记录，适用于已连接云端的机器。`--since` 为大多数测试框架设置时间窗口，但有两个例外：

- **Goose、OpenCode 和 Devin** 发送其全部历史记录，无论 `--since` 如何设置：它们的历史记录存储在数据库中，收集器读取时没有时间窗口，因此 `--dry-run` 会将其报告为所有会话。
- **Hermes** 历史记录不会通过 `backfill` 重新发送。

在 `npm install -g failproofai@latest` 之后应运行 `failproofai update`；它会执行 home 布局迁移、安装匹配的守护进程二进制文件并重启服务。然后将每个已使用 FailproofAI 的 Hermes 配置文件迁移到关联的原生插件，并每个配置文件打印一行。`--no-daemon` 跳过守护进程步骤。当守护进程无法被替换、迁移失败或 Hermes 配置文件无法迁移时（例如运行中的守护进程无法为原生插件提供服务，此时 shell 钩子会保留原位），`update` 以非零状态码退出。

## 测试框架路径

```text
failproofai harness list [harness]
failproofai harness add-path <harness> [label=]<path>
failproofai harness remove-path <harness> <path-or-label>
```

支持的测试框架名称有：`claude`、`codex`、`copilot`、`cursor`、`opencode`、`pi`、`hermes`、`openclaw`、`factory`、`devin`、`antigravity` 和 `goose`。

当两个根目录包含同一项目的副本时，标签可为派生的代理 ID 提供命名空间。重叠的根目录和重复的标签会被拒绝，以防止重复收集或游标损坏。额外路径配置无需重启守护进程即可重新加载。

容器环境可以使用名为 `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` 的逗号分隔变量来替换文件配置的额外路径，例如：

```bash
export FAILPROOFAI_OPENCLAW_EXTRA_PATHS="user1=/srv/openclaw-a,user2=/srv/openclaw-b"
```

## 环境变量

持久性机器行为请使用配置文件。环境变量最适合容器、测试和单进程场景。

| 变量 | 用途 |
| --- | --- |
| `FAILPROOFAI_CLOUD_TOKEN` | 云端密钥，代替 `--token`。建议优先使用此方式：命令行参数可被机器上所有用户通过 `ps` 读取。请通过 `read -s` 或 CI 密钥存储设置，切勿直接在命令中输入密钥，否则无论如何都会留在 shell 历史记录中 |
| `FAILPROOFAI_CLOUD_URL` | 云端 URL，代替 `--url`。守护进程读取的也是此变量 |
| `FAILPROOFAI_HOME` | 重定位完整的 `~/.failproofai` 布局 |
| `FAILPROOFAI_LOG_LEVEL` | 设置本地日志详细程度 |
| `FAILPROOFAI_HOOK_LOG_FILE` | 将钩子诊断信息写入指定文件 |
| `FAILPROOFAI_TELEMETRY_DISABLED=1` | 为此进程禁用匿名遥测 |
| `FAILPROOFAI_NO_FIRST_RUN=1` | 跳过交互式首次运行配置 |
| `FAILPROOFAI_NO_AUTO_AUDIT=1` | 跳过配置后的本地审计 |
| `FAILPROOFAI_LLM_BASE_URL` | 覆盖 LLM 策略使用的 OpenAI 兼容端点 |
| `FAILPROOFAI_LLM_API_KEY` | 提供 LLM 策略使用的 API 密钥 |
| `FAILPROOFAI_LLM_MODEL` | 选择 LLM 策略使用的模型 |
| `FAILPROOFAI_POLICY_LOAD_TIMEOUT_MS` | 限制自定义策略模块的加载时间 |
| `FAILPROOFAI_NO_DOWNLOAD=1` | 拒绝获取包和守护进程二进制文件；已安装的内容继续执行 |
| `FAILPROOFAI_PACK_BASE_URL` | 从镜像而非 `github.com` 获取包 |
| `FAILPROOFAI_<HARNESS>_EXTRA_PATHS` | 替换某个测试框架已配置的额外捕获路径 |
| `NO_COLOR` | 禁用终端彩色输出 |

特定代理的 home 变量（如 `CLAUDE_PROJECTS_PATH`、`CURSOR_HOME`、`HERMES_HOME` 和 `OPENCLAW_HOME`）会覆盖 Failproof AI 发现该测试框架本地会话的位置。

## 安全暂停或移除机器

```bash
failproofai config --pause
failproofai config --status
failproofai config --resume
```

本地会话暂停不会禁用云端管理的策略。若推出本身有问题，请在云端通过 **fix → deploy policies** 恢复云端部署。

在移除 npm 包之前，先移除已安装的钩子和守护进程：

```bash
failproofai uninstall --dry-run
failproofai uninstall --yes
npm rm -g failproofai
```

运行 `failproofai <command> --help` 查看特定版本的详细信息。

<Warning>
  请在 `npm rm -g failproofai` 之前运行 `failproofai uninstall`；npm 不会移除已安装的代理钩子、`failproofai` 技能或守护进程服务。
</Warning>
