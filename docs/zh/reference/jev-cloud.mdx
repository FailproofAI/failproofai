本文是 [Jev 策略](/zh/policies/jev) 的 Cloud 路由参考文档。TypeSafe 的分类器 Jev 会根据你实际提出的请求对每次工具调用进行核查，并配合你的策略协同作答，而非取而代之。通过 **FailproofAI Cloud**，已连接的机器使用与现有连接相同的密钥即可使用 Jev：无需 TypeSafe 账号、无需第二个密钥、无需配置端点。每次调用均从你组织现有的计划配额中扣除。

Jev 的所有行为与[自带密钥方案](/zh/reference/jev-providers)完全一致：硬性策略始终最终生效，仅当 Jev 被明确询问某个可审查策略的相关关切时，该策略的拒绝才会被解除，任何失败都会回退到该次调用的正则表达式结果。

<Note>
需要 **failproofai 1.0.8-beta.0** 或更高版本。1.0.7 不含 Jev，尽管其版本号排在 1.0.7 beta 之后。若未配置 Jev，行为不变：钩子将完全按照以往方式运行正则表达式策略。
</Note>

## 开始之前

在运行 Agent 的机器上安装 Failproof AI，并将其钩子附加到[受支持的 Harness](/zh/reference/harnesses)。如果从零开始，请按照[快速入门](/zh/start/quickstart)完成钩子安装。使用 `failproofai --version` 检查已安装的 CLI；若版本早于 Jev，请升级。你还需要访问组织的 **Administration → Keys** 页面来创建机器密钥。

Jev 在 `PreToolUse` 或 `PermissionRequest` 门控处审查具名工具调用，并不审查会话中的每个事件。要查看 Jev 解除策略拒绝的效果，你需要安装一个标记为[可审查](/zh/policies/authority)的策略；其他所有策略拒绝仍为最终结果。

## 开启 Jev

1. **创建带有 Jev 权限的密钥。** 在 FailproofAI Cloud 控制台中，打开 **Administration → Keys → Create key**，选择 **machine** 预设。该预设授予机器所需的三项权限：`events:add`（发送活动）、`policies:pull`（接收策略）和 `jev:evaluate`（Jev，从组织计划中扣费）。密钥若不携带另外两项权限，则不能携带 `jev:evaluate`。
2. **使用该密钥连接机器。** 在提示符处读取一次性密钥，然后运行完整的设置命令：

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` 会安装守护进程、为检测到的 Agent CLI 附加钩子，并连接机器。使用环境变量可避免密钥出现在命令参数和 Shell 历史记录中。如果你的 Harness 是后来安装的，请[手动附加](/zh/start/quickstart)。

   如果你的组织使用自托管的 FailproofAI Cloud 而非托管版本，请添加其地址：`--url https://<your dashboard host>`（或导出 `FAILPROOFAI_CLOUD_URL`）。若未添加，密钥将与托管服务进行校验，连接会失败。如果该主机的证书来自私有 CA，请将 CA 安装到机器的系统信任库（例如使用 `update-ca-certificates`），而不仅仅安装到 `NODE_EXTRA_CA_CERTS`：发送事件和拉取策略的守护进程读取的是系统信任库。详见[故障排查](/zh/reference/troubleshooting)。

至此设置完成。连接时会存储密钥，当机器**尚未**有 Jev 配置时，会为 FailproofAI Cloud 写入一份配置。从机器首次部署起（约 30 秒内），FailproofAI Cloud 会设置模式：当有 Jev 策略部署到该机器时为 `enforce`，否则为 `off`（参见[谁设置模式](#who-sets-the-mode)）。输出内容会说明这一点：

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

FailproofAI Cloud 部署的检查在 Cloud 上运行。如需在机器上添加自定义检查，请安装策略包：

```bash
failproofai policies add FailproofAI/jev-policies
```

**使用 `--no-transcripts` 连接时，Jev 不会被开启。** Jev 会将每次被检查的工具调用及近期提示发送到 FailproofAI Cloud，这超出了仅发送决策的连接所允许的范围。密钥仍会被存储，输出会说明 Jev 可用以及如何开启：

```bash
failproofai jev setup --provider failproofai
```

此命令同样可以**关闭**通过 FailproofAI Cloud 运行的 Jev。若存在通过 FailproofAI Cloud 运行 Jev 的 `jev.json`（由之前开启了 Transcript 的连接留下），该文件会被删除——规则与 `config --disconnect` 相同——输出会说明此机器上的 FailproofAI Cloud Jev 保持关闭。若 `jev.json` 配置的是你自己的 Jev 端点，则保持不变；通过 `--mode off` 关闭的 FailproofAI Cloud 配置同样保持不变。

<Warning>
连接操作**绝不会覆盖**已存在的 `~/.failproofai/jev.json`。如果你已在使用自己的 Jev 端点，它将继续被使用，输出会说明该文件保持原样——当该文件使 Jev 处于关闭状态（已拒绝或已关闭）时，输出也会说明原因及修复方法。如需将该机器切换到 FailproofAI Cloud，请运行 `failproofai jev setup --provider failproofai`。
</Warning>

## 谁设置模式

在已连接到 FailproofAI Cloud 的机器上，**由 FailproofAI Cloud 设置 Jev 模式**，机器本地不参与设置：

- `enforce`：当有任何 Jev（或正则表达式 + Jev）策略部署到该机器时，来自这些策略所针对的 Agent 的每次被门控工具调用都会发送到 FailproofAI Cloud，后者会将其检查与已安装策略包的检查一并执行。若某次调用来自 Cloud Jev 策略未针对的 Agent，且该调用没有自己的策略包检查，则不会被发送。在 `enforce` 模式下，Jev 自身的拒绝检查会拦截调用，同时也会解除被其审查的正则表达式判决。
- `off`：当无任何 Jev 策略部署时，无论 `jev.json` 如何配置，Jev 完全关闭。

如需在策略生效前进行试验，可将策略部署为 **observe** 效果：其检查仍会执行，执行结果会作为**假设操作**记录在策略页面，但不会拦截或解除任何调用。`failproofai jev setup --mode` 和控制台的 **Settings → Jev** 开关会说明模式由 FailproofAI Cloud 管理，不会做出任何更改。`jev.json` 不用于 Cloud 检查，即使其中指定了其他提供商。`failproofai config --disconnect` 会将 Jev 控制权交还给机器自己的 `jev.json`。

`failproofai jev status` 随后会显示 `Jev checks run on FailproofAI Cloud (mode: enforce)`，并列出审查每个 `both` 策略的检查项。Fleet 页面会说明某台机器无法发起请求的原因：

- `transcripts_disabled`：机器使用 `--no-transcripts` 连接，Jev 始终不会被开启。
- `jev_unconfigured`：机器的密钥不携带 `jev:evaluate`。
- `jev_rate_limited`：FailproofAI Cloud 因组织 Jev 限速而拒绝了该机器的部分调用，这些调用仅由正则表达式策略决定。
- `jev_unavailable`：连续多次调用失败，机器会每次暂停一分钟不再请求 FailproofAI Cloud 的 Jev，之后会自动重试。

如果 FailproofAI Cloud 在 5 秒内未响应，正则表达式策略将独立决策，与任何 Jev 中断情形相同。连续失败 3 次后，机器会每次暂停一分钟不再发起请求，以防 Cloud 中断拖慢每次工具调用。

会话暂停（`failproofai config --pause`）不会停止 FailproofAI Cloud 的 Jev 检查，就像它不会停止 Cloud 管理的策略一样。它只会暂停机器上已安装策略包的 Jev 检查。

## 检查运行状态

```bash
failproofai jev status
failproofai jev test
```

`status` 会显示提供商为 **FailproofAI Cloud**、机器所连接的 Cloud 主机、当前模式，以及密钥来源为 **FailproofAI Cloud connection**（不显示密钥本身）。当 FailproofAI Cloud 的 `jev.json` 已存在但 Jev 无法运行时，会说明原因：

| `status` 显示 | `status --json` | 含义 |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | 机器已连接，但未为其存储 Jev 密钥：密钥缺少 `jev:evaluate`，或连接时无法确认。请在 `FAILPROOFAI_CLOUD_TOKEN` 中填入密钥后重新运行 `failproofai config`；如密钥缺少该权限，请使用 **machine** 密钥。 |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | 此机器上没有 FailproofAI Cloud 连接，Jev 密钥无从归属。 |

`failproofai config --disconnect` 之后，FailproofAI Cloud 的 `jev.json` 将不再存在（除非已被切换为关闭状态，该状态会保留），因此 `status` 仅报告 Jev 为关闭。`status --json` 携带相同的信息（`provider: "failproofai"`、`keySource: "cloud"`、`cloudConnected`、`keyCarriesJev`），即使配置不存在或被拒绝时也是如此。`permissions` 始终来自 `jev.json`；关于 `credentials.json` 的拒绝会附加 `credentialsPermissions`，以及当单个命令可修复时的 `fix` 字段。`test` 会发送一个真实请求并报告其延迟和响应的 Jev 版本。当响应在钩子超时后才到达（钩子会记录 `timeout`）或检查问题回答有误时，命令以退出码 1 退出并在标题中说明。

控制台的 **Settings → Jev** 面板也会显示 **FailproofAI Cloud connection**：机器归属的组织以及其密钥是否携带 Jev。这些信息从机器本地文件读取，不发起网络请求。

## 验证真实调用

在已挂钩的 Agent 中开启新会话，要求其使用文件读取工具读取 `README.md` 并报告标题。确认会话中包含该工具调用，然后再次运行 `failproofai jev status`：近期已评估调用数应有所增加。在[本地控制台](/zh/reference/local-dashboard#review-policy-activity)中打开 **Policies → Activity**，检查该调用的 Jev 判决和模式。在 Cloud 中，组织的 **Policies** 页面会显示已投递活动的 Jev 结果。在 observe 模式下，判决会被记录为**假设操作**，策略结果仍决定该调用的处理。只有当可审查策略匹配且 Jev 解除了其具名检查时，才会出现解除记录。

## 策略页面会收到哪些内容

机器已将钩子活动发送到 FailproofAI Cloud（`events:add`）。开启 Jev 后，每次被门控调用的记录还会包含：运行的评估器、Jev 的决策、被解除的策略、回退原因（如有）、延迟以及响应的模型——仅包含决策、代码和名称，不包含命令或提示内容。在你组织的 **Policies** 页面：

- 由 Jev 自身判决决定的调用（enforce 模式）归因于 **Jev**；若决定性检查来自某个策略包，记录中也会注明该包及其版本；
- 在 observe 模式下，Jev 的拒绝或警告会显示为**假设操作**，与正在观察的部署并列展示；
- Jev 解除的策略（或在 observe 模式下本会解除的策略）按策略进行计数；
- Jev 参与的决策（拦截、警告、解除，或 observe 模式下的假设操作）会列出每项检查及其结论：判决、原因（`not-detected`、`exempt`、`fired`、`op-requested` 等）、证据 `p`、`exempt` 答案以及每个探针的答案。针对 observe 策略的检查也会列出并标记为观察中，它从不拦截调用。Jev 以概率而非文本作答，因此没有自由文本原因。普通的允许结果会汇总为计数，不携带此列表。

## Jev 无法响应时

以下所有情况均会回退到该次调用的策略结果，并记录原因：

| 原因 | 起因 |
| --- | --- |
| `out-of-credits` | 组织已用完计划配额。 |
| `http-401`、`http-403` | 密钥已被吊销，或不携带 `jev:evaluate`。请使用携带该权限的密钥重新连接。 |
| `http-429` | FailproofAI Cloud 正在对你的组织限速。在其要求的等待时间（`Retry-After`，最多 60 秒）结束之前，机器不发送任何请求，每次调用直接回退。被此方式拦截的调用记录为 `http-429`，若机器自身的速率限制先行触发，则记录为 `rate-limited`。 |
| `http-429`（每日限额） | 组织已用完每日 Jev 调用次数：**每 UTC 日 10,000 次**，除非 FailproofAI Cloud 运营方设置了其他限额。每次调用均回退，直到计数在 00:00 UTC 重置；机器每分钟最多重试一次，因此会在一分钟内感知到重置。`failproofai jev test` 会显示"Daily Jev limit for this org reached; resets at 00:00 UTC."。 |
| `http-422` | Jev 拒绝了此次调用的请求，通常是因为工具调用包含超出 Jev Token 预算的密集文本（base64、十六进制、压缩代码）。该调用每次都会回退，不属于中断。 |
| `http-502` | Jev 当前不可用。 |
| `http-503` | 此 Cloud 无法为你的组织提供 Jev 服务：没有模型网关、组织尚未预置，或网关已宕机。请联系管理员；钩子每分钟最多重试一次。 |
| `http-404` | 此 FailproofAI Cloud 尚未提供 Jev 服务。 |
| `timeout` | 在 `timeoutMs`（默认 3000）内未收到响应。当 FailproofAI Cloud 设置机器的 Jev 模式时，等待时间为 5000 毫秒，`jev.json` 中的 `timeoutMs` 不生效。 |
| `model-mismatch` | 响应的 Jev 版本不是 1.13。 |

## 密钥存储位置及使用去向

- 密钥仅存储一次，位于 `~/.failproofai/credentials.json`（权限 `0600`，在仅限所有者访问的目录中），与其他 FailproofAI Cloud 凭据并列存放。此路由的 `jev.json` 不保存密钥；若在其中写入密钥会使配置无效。
- 若 `credentials.json` 对除你之外的任何人（组或其他用户，读或写）拥有**任何**权限，或其目录可被除你之外的任何人**写入**，则该文件会被**拒绝读取**，Jev 将保持关闭直到你修复：对文件执行 `chmod 600`，对目录执行 `chmod 700`（或重新连接，重连会以 `0600` 重写文件并将目录设为仅限所有者）。其他用户仅可读取目录是允许的；允许其写入则意味着他们可以替换文件。
- 密钥仅在与其关联的连接存在于机器上时才生效：即同一 FailproofAI Cloud 的策略或报告凭据使用**相同密钥**，存储在同一文件中。若 Jev 密钥遗留而无对应连接，则被忽略，Jev 保持关闭。这种情况发生于：旧版 failproofai 的 `config --disconnect` 保留了 Jev 密钥（它不知道需要将其删除），或旧版 failproofai 的 `config --token` 以另一个密钥连接（该密钥在 FailproofAI Cloud 上可能属于另一个组织）。如需重新开启 Jev，请使用 **machine** 密钥重新连接。
- 密钥仅会被发送到验证它的 Cloud 源。指向其他地址的 `jev.json` 会被拒绝。
- **机器上的 Agent 可以读取它。** `credentials.json` 仅限所有者访问，而 Agent 以该所有者身份运行。读取 failproofai 自身文件是被明确允许的（只有修改被 `block-failproofai-commands` 拦截），因此 Agent 与该文件之间唯一的屏障是 `block-read-outside-cwd`——一个*可审查*策略——而对于从主目录启动的会话，这道屏障也不存在。携带 `jev:evaluate` 的密钥会从使用它的任何地方消耗组织的 Jev 配额（直到每日上限），因此请像对待其他消费凭据一样对待机器密钥：若 Agent 可能已读取了它，请在 Keys 页面禁用该密钥并使用新密钥重新连接。
- 只有你的全局文件才能决定此行为。Repository 无法开启 Cloud Jev、将其指向其他地址或提供密钥，`FAILPROOFAI_JEV_API_KEY` 在此路由中被忽略。
- 对于每次 Jev 评估的调用，会向 FailproofAI Cloud 发送一次请求，携带[自带密钥页面](/zh/reference/jev-providers#what-leaves-the-machine)所列内容（已脱敏）。FailproofAI Cloud 将其转发给 TypeSafe，不记录也不保留。

## 关闭 Jev

在已连接的机器上，当 FailproofAI Cloud 未向其部署任何 Jev 策略时，Jev 处于关闭状态：在 Cloud 中移除或归档 Jev 策略即可。

| 命令 | 结果 |
| --- | --- |
| 在 FailproofAI Cloud 中移除该机器的 Jev 策略 | Cloud 模式在下次轮询时（约 30 秒）变为 `off`：无论 `jev.json` 如何配置，Jev 完全关闭。 |
| `failproofai config --disconnect` | 断开机器连接：密钥被删除，若 `jev.json` 指向 FailproofAI Cloud 且未被切换为关闭状态，该文件也会被删除。指向你自己端点的 `jev.json` 保持不变。 |

从下一次工具调用起，钩子将完全按照以往方式运行正则表达式策略。
