本文是 [Jev 策略](/zh/policies/jev) 的 Cloud 路由参考。Jev 是 TypeSafe 的分类器，它根据你实际的请求内容审查每次工具调用，与你的策略并行工作，而不是取代策略。通过 **FailproofAI Cloud**，已连接的机器使用与连接时相同的密钥即可使用 Jev：无需 TypeSafe 账户、无需第二个密钥、无需配置端点。每次调用均从组织现有的套餐配额中扣除。

Jev 的所有行为与[自带密钥方式](/zh/reference/jev-providers)完全相同：硬策略始终具有最终效力，可审查策略的拒绝仅在 Jev 被明确针对该问题进行询问时才会被清除，任何失败都会回退到该次调用的正则表达式结果。

<Note>
需要 **failproofai 1.0.8-beta.0** 或更高版本。1.0.7 不含 Jev，尽管它在版本排序上高于 1.0.7 的各 beta 版本。若未配置 Jev，行为不会有任何变化：hooks 将完全按照既往方式运行正则表达式策略。
</Note>

## 开始之前

在运行 Agent 的机器上安装 Failproof AI，并将其 hooks 附加到[受支持的运行环境](/zh/reference/harnesses)。如果从零开始，请按照[快速入门](/zh/start/quickstart)完成 hook 安装。使用 `failproofai --version` 检查已安装的 CLI；若版本早于 Jev，请升级。你还需要访问组织的 **Administration → Keys** 页面以创建机器密钥。

Jev 在 `PreToolUse` 或 `PermissionRequest` 检查点审查具名工具调用，不会审查会话中的每个事件。要使 Jev 清除策略拒绝，你需要安装一个标记为[可审查](/zh/policies/authority)的策略；所有其他策略拒绝仍具有最终效力。

## 开启方式

1. **创建带有 Jev 权限的密钥。** 在 FailproofAI Cloud 控制台中，打开 **Administration → Keys → Create key**，选择 **machine** 预设。该预设授予机器所需的三项权限：`events:add`（发送活动）、`policies:pull`（接收策略）和 `jev:evaluate`（Jev，从组织套餐中扣费）。密钥若不携带另外两项权限，则无法携带 `jev:evaluate`。
2. **使用该密钥连接机器。** 在提示时读取其一次性密钥，然后运行完整的设置命令：

   ```bash
   read -rs FAILPROOFAI_CLOUD_TOKEN && export FAILPROOFAI_CLOUD_TOKEN
   failproofai config
   ```

   `failproofai config` 会安装守护进程、为其找到的 Agent CLI 附加 hooks，并连接机器。使用环境变量可防止密钥出现在命令参数和 shell 历史记录中。如果运行环境是后来安装的，请[显式附加它](/zh/start/quickstart)。

   如果你的组织使用自部署的 FailproofAI Cloud 而非托管版，请添加其地址：`--url https://<your dashboard host>`（或导出 `FAILPROOFAI_CLOUD_URL`）。若未添加，密钥将与托管服务进行验证，连接会失败。如果该主机的证书来自私有 CA，请将 CA 安装到机器的系统信任存储区（例如使用 `update-ca-certificates`），而不仅仅是 `NODE_EXTRA_CA_CERTS`：发送事件和拉取策略的守护进程读取的是系统存储区。详见[故障排查](/zh/reference/troubleshooting)。

就这些。连接操作会存储密钥，当机器**尚未**有 Jev 配置时，会为 FailproofAI Cloud 写入一个配置。从机器首次部署起（约 30 秒内），FailproofAI Cloud 将设置模式：当 Jev 策略部署到该机器时为 `enforce`，没有策略时为 `off`（参见[谁设置模式](#who-sets-the-mode)）。输出会显示相关信息：

```text
  Jev       configured through FailproofAI Cloud; waiting for FailproofAI Cloud's Jev mode, which arrives with this machine's first deployment (within ~30 s) and decides.
```

FailproofAI Cloud 部署的检查在 Cloud 上运行。如需在机器上添加自定义检查，请安装策略包：

```bash
failproofai policies add FailproofAI/jev-policies
```

**使用 `--no-transcripts` 连接时，不会开启 Jev。** Jev 会将每次被检查的工具调用及最近的提示词发送到 FailproofAI Cloud，这比仅发送决策的连接发送的内容更多。密钥仍会被存储，输出会说明 Jev 已可用以及如何开启：

```bash
failproofai jev setup --provider failproofai
```

此命令同样会**关闭**通过 FailproofAI Cloud 使用的 Jev。按照 `config --disconnect` 相同的规则，通过 FailproofAI Cloud 运行 Jev 的 `jev.json`（由之前启用了转录的连接留下）将被删除，输出会说明该机器上的 FailproofAI Cloud Jev 保持关闭。若存在指向你自己 Jev 端点的 `jev.json`，则保持不变；已手动关闭的 FailproofAI Cloud 配置（使用 `--mode off`）同样保持不变。

<Warning>
连接操作**绝不会覆盖**已存在的 `~/.failproofai/jev.json`。如果你已在使用自己的 Jev 端点，它将继续被使用，输出会说明该文件保持原有配置不变——如果该文件使 Jev 处于关闭状态（被拒绝或已手动关闭），也会说明原因及修复方法。如需将该机器切换到 FailproofAI Cloud，请运行 `failproofai jev setup --provider failproofai`。
</Warning>

## 谁设置模式

在已连接 FailproofAI Cloud 的机器上，**Jev 模式由 FailproofAI Cloud 设置**，机器本身不参与设置：

- `enforce`：当任何 Jev（或正则表达式 + Jev）策略部署到该机器时生效。来自该策略目标 Agent 的每次被检查工具调用都会发送到 FailproofAI Cloud，后者会与该处安装的策略包的检查一并进行询问。来自没有 Cloud Jev 策略针对的 Agent、且自身也没有策略包检查的调用，则完全不会被发送。在 `enforce` 模式下，Jev 自身的拒绝检查既可以拦截调用，也可以清除正则表达式的裁定。
- `off`：当没有任何 Jev 策略部署时生效：完全不使用 Jev，无论 `jev.json` 如何配置。

如需在策略生效前进行试用，可将其以 **observe** 效果部署：检查仍会被执行，其结果会作为**假设操作**记录在策略页面上，但不会拦截或清除任何调用。`failproofai jev setup --mode` 和控制台的 **Settings → Jev** 开关会显示模式由 FailproofAI Cloud 管理，不会做任何更改。`jev.json` 不用于 Cloud 的检查，即使其中指定了其他提供商。`failproofai config --disconnect` 会将 Jev 控制权交还给机器自身的 `jev.json`。

`failproofai jev status` 随后会显示 `Jev checks run on FailproofAI Cloud (mode: enforce)`，同时列出审查每个 `both` 策略的检查项。Fleet 页面会显示某台机器无法发起询问的原因：

- `transcripts_disabled`：该机器以 `--no-transcripts` 方式连接，永远不会开启 Jev。
- `jev_unconfigured`：该机器的密钥不携带 `jev:evaluate`。
- `jev_rate_limited`：FailproofAI Cloud 因组织的 Jev 速率限制而拒绝了该机器的部分调用，这些调用仅由正则表达式策略决定。
- `jev_unavailable`：连续多次调用失败，机器将每次跳过 FailproofAI Cloud 的 Jev 一分钟，之后会自动重试。

如果 FailproofAI Cloud 在 5 秒内未响应，正则表达式策略将独立做出决定，与任何 Jev 中断情况相同。连续 3 次失败后，机器每次停止询问一分钟，以防 Cloud 中断拖慢每次工具调用。

会话暂停（`failproofai config --pause`）不会停止 FailproofAI Cloud 的 Jev 检查，就像它不会停止 Cloud 管理的策略一样。但它会暂停机器上已安装策略包的 Jev 检查。

## 检查运行状态

```bash
failproofai jev status
failproofai jev test
```

`status` 显示提供商为 **FailproofAI Cloud**、机器连接的 Cloud 主机、当前模式，以及密钥来源为 **FailproofAI Cloud connection**，不显示密钥本身。当 FailproofAI Cloud 的 `jev.json` 已存在但 Jev 无法运行时，会说明原因：

| `status` 显示 | `status --json` | 含义 |
| --- | --- | --- |
| **off — no Jev key is stored for this machine's FailproofAI Cloud connection** | `key-lacks-jev` | 机器已连接，但未为其存储 Jev 密钥：密钥缺少 `jev:evaluate` 权限，或连接时无法确认。请在 `FAILPROOFAI_CLOUD_TOKEN` 中填入密钥后重新运行 `failproofai config`；如果密钥缺少该权限，请使用 **machine** 密钥。 |
| **off — this machine is not connected to FailproofAI Cloud** | `not-connected` | 该机器上没有 FailproofAI Cloud 连接，Jev 密钥无所归属。 |

`failproofai config --disconnect` 之后，FailproofAI Cloud 的 `jev.json` 将不再存在（除非已手动关闭，该状态会被保留），因此 `status` 仅报告 Jev 为关闭。`status --json` 包含相同的信息（`provider: "failproofai"`、`keySource: "cloud"`、`cloudConnected`、`keyCarriesJev`），即使配置不存在或被拒绝时也是如此。`permissions` 始终对应 `jev.json` 的权限；关于 `credentials.json` 的拒绝会额外显示 `credentialsPermissions`，以及当单个命令可修复时的 `fix` 提示。`test` 发送一次真实请求，并报告其延迟和响应的 Jev 版本。当响应在 hook 超时后才到达（hooks 会记录 `timeout`）或检查问题的答案有误时，命令以退出码 1 结束，并在标题中注明。

控制台的 **Settings → Jev** 面板也会显示 **FailproofAI Cloud connection**：机器所属的组织以及其密钥是否携带 Jev 权限。这些信息直接从机器本地文件读取，无需网络调用。

## 验证真实调用

在已附加 hook 的 Agent 中启动新会话。请求它使用文件读取工具读取 `README.md` 并报告标题。确认会话包含该工具调用，然后再次运行 `failproofai jev status`：其最近的已评估调用计数应该增加。在[本地控制台](/zh/reference/local-dashboard#review-policy-activity)中打开 **Policies → Activity**，查看该调用的 Jev 裁定和模式。在 Cloud 中，组织的 **Policies** 页面会显示已送达活动的 Jev 结果。在 observe 模式下，裁定会被记录为**假设操作**，策略结果仍决定该调用的处理方式。只有当可审查策略匹配且 Jev 清除了其具名检查时，才会出现清除记录。

## 策略页面上显示的内容

机器已将其 hook 活动发送到 FailproofAI Cloud（`events:add`）。开启 Jev 后，每次被检查调用的记录还会包含：运行的评估器、Jev 的决定、它清除的策略、回退时的原因、延迟以及响应的模型——仅包含决策、代码和名称，不包含命令内容或提示词。在组织的 **Policies** 页面上：

- 由 Jev 自身裁定的调用（enforce 模式）会归因于 **Jev**，若决定性检查来自某个策略包，记录中也会注明该包及其版本；
- 在 observe 模式下，Jev 的拒绝或警告会显示为**假设操作**，与正在观察的部署一同展示；
- Jev 已清除或在 observe 模式下本会清除的策略，会按策略进行计数统计。
- Jev 参与的决定（拦截、警告、清除，或 observe 模式下的假设操作）会列出其询问的每项检查及其结论：裁定、原因（`not-detected`、`exempt`、`fired`、`op-requested` 等）、证据值 `p`、`exempt` 答案以及每次探测的答案。针对 observe 部署策略的检查也会被列出，并标记为已观察；它永远不会拦截调用。Jev 以概率而非文字形式作答，因此没有自由文本说明。纯允许操作汇总为计数，不携带此列表。

## Jev 无法响应时的处理

以下每种情况均会回退到该调用的策略结果，并记录其原因：

| 原因 | 起因 |
| --- | --- |
| `out-of-credits` | 组织已用完套餐配额。 |
| `http-401`、`http-403` | 密钥已被吊销，或不携带 `jev:evaluate` 权限。请使用携带该权限的密钥重新连接。 |
| `http-429` | FailproofAI Cloud 因组织的 Jev 速率限制对请求进行了限速。在其要求的等待时间（`Retry-After`，最多 60 秒）结束前，机器不会发送任何请求，每次调用直接回退。以此方式被阻止的调用记录为 `http-429`，若机器自身的速率限制先触发，则记录为 `rate-limited`。 |
| `http-429`（每日限制） | 组织已用完每日 Jev 调用配额：**每 UTC 日 10,000 次**，除非 FailproofAI Cloud 的运营方设置了其他限制。每次调用都会回退，直到计数在 00:00 UTC 重置；机器每分钟最多重试一次，因此会在一分钟内感知到重置。`failproofai jev test` 会显示"Daily Jev limit for this org reached; resets at 00:00 UTC." |
| `http-422` | Jev 拒绝了该调用的请求，通常是因为工具调用包含超出 Jev token 预算的密集文本（base64、十六进制、压缩代码等）。该调用每次都会回退，这不是中断故障。 |
| `http-502` | Jev 当前不可用。 |
| `http-503` | 该 Cloud 无法为组织提供 Jev 服务：没有模型网关、组织尚未配置，或网关已停止运行。请联系管理员；hooks 每分钟最多重试一次。 |
| `http-404` | 该 FailproofAI Cloud 尚不提供 Jev 服务。 |
| `timeout` | 在 `timeoutMs`（默认 3000）毫秒内无响应。当 FailproofAI Cloud 设置机器的 Jev 模式时，等待时间为 5000 毫秒，`jev.json` 中的 `timeoutMs` 不生效。 |
| `model-mismatch` | 响应的 Jev 版本不是 1.13。 |

## 密钥的存储位置及传输范围

- 密钥仅存储一次，位于 `~/.failproofai/credentials.json`（权限 `0600`，在仅限所有者访问的目录中），与其他 FailproofAI Cloud 凭证并列存放。此路由的 `jev.json` 中不存储密钥；若在其中写入密钥会导致配置无效。
- 如果 `credentials.json` 对所有者之外的任何人（组或其他用户）具有**任何**权限（读或写），或其所在目录可被所有者之外的人**写入**，则该文件将被**拒绝**读取，Jev 将保持关闭，直到修复：对文件执行 `chmod 600`，对目录执行 `chmod 700`（或重新连接，连接操作会以 `0600` 权限重写文件并将目录设为仅限所有者访问）。目录对他人仅有读取权限是允许的；可写入则意味着他人可以替换文件。
- 密钥仅在其所属连接存在于机器上时有效：即同一个 FailproofAI Cloud 存在**相同密钥**的策略或报告凭证，且位于同一文件中。没有对应连接的遗留 Jev 密钥将被忽略，Jev 保持关闭。这种情况发生在旧版 failproofai 的 `config --disconnect` 未删除 Jev 密钥时（旧版本不了解需要删除它），或旧版 failproofai 的 `config --token` 使用另一个密钥连接时（在 FailproofAI Cloud 上该密钥可能属于另一个组织）。如需重新开启 Jev，请使用 **machine** 密钥重新连接。
- 密钥只会发送到其经过验证的 Cloud 源地址。指向其他地址的 `jev.json` 将被拒绝。
- **机器上的 Agent 可以读取它。** `credentials.json` 是仅限所有者访问的，而 Agent 以该所有者身份运行。读取 failproofai 自身的文件是被允许的（只有修改操作被 `block-failproofai-commands` 拦截），因此 Agent 与该文件之间的唯一屏障是 `block-read-outside-cwd`——一个*可审查*策略——而从你的 home 目录启动的会话则没有任何屏障。携带 `jev:evaluate` 权限的密钥会从使用它的任何地方消耗组织的 Jev 配额（直至每日上限），因此请像对待任何其他支出凭证一样对待机器密钥：如果 Agent 可能已读取了它，请在 Keys 页面禁用该密钥，并使用新密钥重新连接。
- 只有你的全局文件才能决定此事。仓库无法开启 Cloud Jev、将其指向其他地址或提供密钥，`FAILPROOFAI_JEV_API_KEY` 在此路由中被忽略。
- 对于 Jev 评估的每次调用，会向 FailproofAI Cloud 发送一次请求，携带[自带密钥页面](/zh/reference/jev-providers#what-leaves-the-machine)所列的内容（密钥已脱敏）。FailproofAI Cloud 将其转发给 TypeSafe，不进行日志记录或留存。

## 关闭方式

在已连接的机器上，当 FailproofAI Cloud 未向其部署任何 Jev 策略时，Jev 处于关闭状态：在 Cloud 中移除或归档 Jev 策略即可。

| 命令 | 结果 |
| --- | --- |
| 在 FailproofAI Cloud 中移除该机器的 Jev 策略 | Cloud 的模式在下次轮询时（约 30 秒）变为 `off`：完全不使用 Jev，无论 `jev.json` 如何配置。 |
| `failproofai config --disconnect` | 断开机器连接：密钥被删除，若 `jev.json` 指向 FailproofAI Cloud 且未处于手动关闭状态，也会被删除。指向你自己端点的 `jev.json` 保持不变。 |

从下一次工具调用起，hooks 将完全按照既往方式运行正则表达式策略。
