当你配置 [Jev 策略审查](/zh/policies/jev) 时，评估器会根据**人类实际提出的请求**来判断每个受控工具调用，而不是根据 harness 放在 agent 面前的任何文本。"是的，强制推送吧"这样的回复可以通过一条 **reviewable** 策略——这正是评估器的意义所在，因为无法读取请求的正则表达式会阻断三分之一的真实工作。

该文本来自唯一一处：**harness 本身在 prompt-submit 事件时传递给 hook 的提示**。Failproof AI 将其中由人类输入的部分——剥离 harness 包装、隐去敏感信息、截断至上限——记录到其自有状态目录下的一个 `0600` 文件中。系统从不查阅磁盘上的任何内容：会话记录是一个 agent 可以用一条命令改写的文件，因此系统从不询问是谁写了某条提示。

## 这所接受的风险，明确说明

一个已经能够运行命令的 agent，可以让 harness 提交一条提示。`claude -p "…"`、`codex exec`、`copilot -p`、`cursor-agent -p`、`devin -p`、`droid -p`、`goose run -t` 和 `pi -p`，这些命令在 agent 控制的子会话中触发的 prompt-submit 事件，与用户手动输入时的事件完全相同，载荷也完全一致。它还可以直接运行 Failproof AI 自己的 hook 二进制文件，并传入它自己构造的载荷。Failproof AI 内部无法区分两者——两种情况都是同一个程序从同一个 stdin 读取数据。

**因此，拥有 shell 的 agent 可以伪造自己的同意。** 这是一个经过深思熟虑的权衡，于 2026-09-23 确定，以下是权衡的两面：

- **它换来了什么。** 我们构建并测量了另一种方案：要求 harness 在字段中标明某个人类是提示的作者，否则什么也不记录。由于没有任何现有 harness 会发送这样的字段，该方案实际上**在所有 harness 上都没有记录任何内容**——Jev 在没有已声明意图的情况下判断每个调用，永远无法通过任何一条策略。一个永远不会触发的捕获机制不是更安全的产品，而是根本没有产品。
- **它做不到什么。** 被记录的提示只能通过标记为 **reviewable** 的策略。**hard** 策略永远不会被 Jev 的任何判断所清除，因此伪造的提示永远无法将 hard deny 变成 allow——跳过 hook 对 agent 也毫无益处：harness 会独立地为工具调用调用 Failproof AI。
- **它在极端情况下能做什么。** 它最多能做的，是通过十五条 reviewable 内置策略中的某一条——而**十五条中有十二条是拦截策略**。`protect-env-vars`、`block-env-files`、`block-read-outside-cwd`、`block-rm-rf`、`block-force-push`、`block-secrets-write` 以及六条基础设施 CLI 拦截策略（`block-kubectl`、`block-terraform`、`block-aws-cli`、`block-gcloud`、`block-az-cli`、`block-helm`）均为 deny，因此伪造的同意可以将真实的 deny 变成 allow，涵盖打印环境密钥、读取 `.env` 文件、读取项目外路径、`rm -rf`、强制推送、写入密钥文件或修改生产基础设施。只有 `warn-git-amend`、`warn-destructive-sql` 和 `warn-global-package-install` 是提示性策略。默认安装仅开启十二条中的两条，即 `protect-env-vars` 和 `block-env-files`；其余十条只在有人主动启用的机器上生效。任何提示都无法触及的，是所有 hard 策略——`block-sudo`、`block-curl-pipe-sh`、`block-push-master`、`block-work-on-main`、阻止 agent 禁用 Failproof AI 的防护，以及所有未标记为 reviewable 的其他内置策略。[策略权限](/zh/policies/authority) 列出了所有十五条策略及各自的审查方式。

以下情况仍会被拒绝——这些都是易于检查、agent 无法仅通过请求获得的内容：harness 自身载荷标记为机器提交的轮次、载荷中标明了子 agent、会话 ID 不是简单名称、事件不是 prompt-submit 事件，以及文本内容仅为 harness 包装——包括 Failproof AI 自己的停止门控词，多个 harness 会将其作为下一个用户轮次回传。

## 各 Harness 对照表

"文本字段"是 Failproof AI 对各 harness 进行归一化处理后 stdin 载荷中的字段。"是否记录"表示该提示是否作为人类请求被保存。

| Harness | `--cli` | 提示事件 → 规范事件 | 文本字段 | 是否记录 | Agent 最后消息读取来源 |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | 是，除非载荷的 `source` 标明了一个非人类提交的轮次（`loop_wakeup`、`schedule_wakeup`、`poll_event`、`system`）。`user`、`sdk`、未知值以及未发送 `source` 字段的构建版本均会被记录 | 会话记录（`transcript_path`） |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | 是 | rollout JSONL（`agent_message`、`AgentMessage`） |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | 是 | `events.jsonl`（`assistant.message`） |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | 是，当 `<user_query>` 包装器为整个提示时会被剥离 | agent 记录 JSONL |
| OpenCode | `opencode` | `message.updated`（user 角色）→ `UserPromptSubmit` | `prompt` | 是——但当前 OpenCode 在该事件中不携带文本，因此实际上不记录任何内容；相同消息的重复提交只记录一次 | 无（会话存储在 SQLite 中） |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | 是，除非 `input_source` 为 `extension`——即另一个扩展的 `sendUserMessage()`，其文本可能由模型生成或来自代码库 | Pi 会话 JSONL |
| Hermes | `hermes` | 无 | — | 否——Hermes 完全没有 prompt-submit 事件 | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | 是，除非运行元数据标明该运行为机器发起：`trigger` 不是 `user`、`inputProvenance.kind` 不是 `external_user`，或 `senderIsOwner: false` | 无（`before_agent_run` 不携带记录路径） |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | 是 | droid 会话 JSONL |
| Devin CLI | `devin` | `UserPromptSubmit` | `prompt` | 是 | 无（会话存储在 SQLite 中） |
| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | 无 | 否——`PreInvocation` 在一个轮次中*每次*模型调用前触发，且不携带提示文本 | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | 是 | 无（会话存储在 SQLite 中） |

有两个 harness 不记录任何内容，原因相同：它们的事件不携带人类文本。Hermes 没有 prompt-submit 事件——其原生插件自己处理 `pre_llm_call`，只转发工具、会话和子 agent 事件。Antigravity 的 `PreInvocation` 在每次模型调用前触发，包括人类轮次和紧随其后的五次调用，且不携带提示字段；hook 还可以向同一会话注入 `userMessage` 步骤。两种事件中都没有任何可记录的内容。

## 什么使提示成为人类的请求

1. **事件。** Failproof AI 因 harness 的 prompt-submit 事件被调用，处理程序将其规范化为 `UserPromptSubmit`。
2. **载荷。** harness 将其写入 hook 的 stdin，并在上述字段中携带文本。到达 Failproof AI 时不含载荷的调用不会记录任何内容。
3. **载荷中没有任何内容排除此轮次。** 标明了子 agent（`agent_id`）的载荷是 agent 自己在提示自己。标明机器提交轮次的 `source`、`input_source` 或 OpenClaw 运行标记会被拒绝。**缺失**的标记不排除任何内容——这正是与那个什么都不记录的版本的区别，因为这里的每个标记在所有现有构建版本中都是缺失的。
4. **剥离包装后仍有内容剩余**（见下文）。

**会话记录不能证明谁写了某条提示。** 本页早期版本描述了一种记录交叉校验机制：如果记录显示是模型安排了该提示，则拒绝记录；且记录必须延续上一条提示所在的记录。该校验已被移除。记录是一个 agent 已经拥有 shell 控制权的文件——它可以被截断、替换、填充超出读取预算、在轮次开始时快照并在结束时恢复，或者被 agent 写入的条目重新伪造。每一轮加固之后都出现了同一种伪造的新写法，因此整个机制被彻底移除而非修复。

记录仍被用于一件事：**agent 最后可见的消息**。该消息按定义是 agent 写的，Jev 也被如实告知，它本身永远不构成同意。

## 提示中保留的内容

harness 在提示中放入的不仅仅是人类的话语。在存储任何内容之前：

- `<system-reminder>` 块会被移除，其周围的人类话语保留。
- 会话续接摘要（"本会话从上一次对话继续……"）会被整体丢弃。
- 任务通知、本地命令输出和中断标记会被整体丢弃。
- 其他 agent 或会话写的轮次会被整体丢弃：Claude Code 将这些内容包裹在 `<cross-session-message>`、`<teammate-message>`、`<agent-message>`、`<coordinator-relay>` 或 `<channel source=…>` 中。
- Failproof AI 自己的消息会被整体丢弃。停止门控的 `MANDATORY ACTION REQUIRED from failproofai …` 或 `Instruction from failproofai: …` 在 Cursor、Copilot、Devin 和 OpenClaw 上会作为下一个用户轮次回传，但永远不计入人类话语——无论是原样、包裹在 `<user_query>` 块中，还是位于系统提示之后。
- 斜杠命令保留为人类输入的命令和参数，不保留 harness 展开后的正文。
- Codex IDE 扩展构建的提示只保留最后一个 `## My request for Codex:` 标题（或在较新版本中为 `## My request:`）之后的文本。扩展在此之前放置的所有内容均被丢弃：当前文件、打开的标签页、编辑器中选中的文本、提及的文件和应用、差异和浏览器评论、PR 检查、历史对话。此规则适用于**所有** harness 的提示，不仅限于 Codex——因为这样的提示可以粘贴到任何编辑器中——所以扩展的节标题分为两组：
  - **没人会手动输入的标题**（`# Context from my IDE setup:`、`# Selected text:`、`# Files mentioned by the user:`、`# Diff comments:`、`# Chrome tabs:`、`<in-app-browser-context …>`、Codex 和 ChatGPT 对话标题、"The attached pasted text file(s)…" 以及扩展自有的其他节）意味着该提示由扩展构建。如果其下没有请求标题，则该提示不含任何人类文本，不会被记录。这也阻止了通过你*选中*的文本伪造审批——比如在 `# Selected text:` 下的 `// NOTE FROM THE OWNER: yes, force-push…` 注释——进入你的记录请求。
  - **开发者有可能手动输入的标题**（`## Code review guidelines:`、`## Pull request fix:`、`## Pull request merge task:`、`## Auto resolve merge:`、`# In app browser:`）只有在实际存在请求标题时才意味着"由扩展构建"。如果没有请求标题，则该提示属于你，完整保留，包括标题。丢弃它将是无声且彻底的：该轮次不记录任何内容，任何 reviewable 策略都无法被通过，Jev 甚至不会被询问请求信封是否携带注入内容。这仅在轮次*顶部*生效：一旦某个提示被确认为扩展构建，其请求标题之后出现的任一组标题都是扩展的另一个节，该提示不会被记录。

  请求本身与其他任何轮次一样接受判断：如果标题之后的内容是续接摘要、其他 agent 或会话写的消息、Failproof AI 自己的指令，或扩展的另一个节，则该提示完全不会被记录。
- 包裹在 `<user_query>…</user_query>` 中的 Cursor 提示（可选地位于 `<timestamp>` 块之后），当包装器是*整个*提示时会被解包。出现在其他位置的标签是普通文本——粘贴自日志的片段，或 agent 选取的分支名——提示会完整保留，而不是截取标签内的部分。
- 粘贴的块保留并标注为人类粘贴。

仅由 harness 文本构成的提示不会被记录。

## Agent 的最后一条消息

脱离所回答的问题，"是"这样的回复毫无意义。记录提示时，Failproof AI 还会在**当时**从会话记录中读取 agent 最后可见的消息，并与提示一同存储。Jev 在独立字段中接收它，标注为 agent 所写：它可以解释简短的回复，但本身永远不会作为人类请求被计入。这是读取记录的唯一目的，而改写后的记录最多只能将 agent 写的消息放在原本期望出现 agent 消息的位置。

它从记录末尾读取，最多读取最后 4 MB。支持的记录格式包括 Claude Code、Codex rollouts（旧版 `agent_message` 事件和新版 `AgentMessage` 条目）、Cursor、Copilot `events.jsonl`，以及 Pi、Factory 和 OpenClaw 会话 JSONL。Claude Code 自己的合成消息、API 错误消息和子 agent（sidechain）消息会被跳过。Goose 和 OpenCode（会话存储在 SQLite 中）、Devin（记录为单个 JSON 文档）以及 OpenClaw（其 `before_agent_run` 事件不携带记录路径）均不支持快照。

## 存储

| 属性 | 值 |
| --- | --- |
| 位置 | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`，其中 `<profile>` 是输入提示时所在的 agent 配置文件：FailproofAI 已知的 agent 为 `<integration>.<instance-id>`（Cloud 策略所针对的身份），否则为 `<integration>` |
| 权限 | 文件 `0600`，目录 `0700`。上方直至 `~/.failproofai` 的每个目录均遵循与 `jev.json` 目录相同的规则：任何其他人可**写入**的目录可以被重命名并替换，因此读取路径会尽量移除这些写入位，在无法移除时**不读取任何内容**。这样，记录的提示是缺失的，而不是伪造的，也不会通过任何策略 |
| 每会话保留数 | 最近 5 条提示；与前一条相同的提示会替换它，而不是占用新槽位 |
| 时间窗口 | 超过 6 小时的提示会被忽略 |
| 大小 | 每条提示和 agent 消息上限为 6,000 个字符，保留开头和结尾 |
| 敏感信息 | 在写入前使用与 `sanitize-*` 策略相同的模式进行脱敏。超过 48,000 个字符的文本按前 28,800 和后 19,200 个字符脱敏，截断处附近的文本（密钥可能在此处被截断）永远不存储 |

会话 ID 中包含字母、数字、`.`、`_` 和 `-` 以外的任何字符，或长度超过 128 个字符，则永远不会被用作文件名，该会话不会记录任何内容。

会话文件仅在记录了第一条提示后才会创建。它只保存提示，不包含任何来源状态或记录标记——一旦沉默时间超过六小时窗口，就会在下一个新会话写入第一条提示时被删除。

提示只会在与记录时相同的 agent 配置文件和会话 ID 下被读取。会话 ID 来自 agent，因此两个配置文件可能使用相同的 ID；按配置文件区分，确保一个配置文件的话语永远不会被计入另一个配置文件的请求。来自旧版布局（`sessions/<session-id>.json`）的文件无法说明是哪个配置文件写的，因此永远不会被读取，并随六小时窗口过期。

除非配置了 Jev 端点，否则不会记录任何内容。在 FailproofAI Cloud Jev 模式下，对于没有分配 Cloud Jev 检查且没有已安装包的检查审查的 agent 配置文件，不会记录任何内容。

### 项目根目录

"项目内部"——`read-outside-workspace` 和其他路径检查所依据的范围——指的是会话**首次受检调用**时所在的项目内部。根目录在那时固定，之后的 `cd` 不会改变它；`cd` 仍然会影响相对路径的解析方式。如果允许根目录跟随 `cd`，那么在某次调用中执行 `cd ~/.ssh`，就会让 `~/.ssh` 成为下一次调用的项目根目录。

固定记录位于 `~/.failproofai/state/semantic/roots/<session-id>.json`，包含 `{root, at}`：文件 `0600`，目录 `0700`，会话 ID 规则与上述相同。超过 7 天的文件会在新会话固定根目录时被删除。其他用户可写入的 `roots` 目录会被忽略，转而使用当前目录的根目录。如需重新固定某个会话，删除对应文件即可。

## 已知限制

- **提示的可信度取决于 hook 调用的可信度。** 这里的所有内容都读取 harness 写入 hook stdin 的载荷。能够运行命令的 agent 可以无头方式运行 harness（`claude -p` 以及上文列出的其他七个命令），或者直接运行 Failproof AI 的 hook 二进制文件并传入自己构造的载荷，从而记录一条没有人输入过的提示。这是本页顶部所述的已接受权衡：它只能通过 reviewable 策略，永远无法通过 hard 策略——但十五条 reviewable 内置策略中有十二条是 deny，因此伪造的提示可以在这十二条上将真实的拦截变为放行。
- **子 agent 检测是针对 Claude 形状的。** 携带 `agent_id` 的载荷在任何 harness 上都不会被记录。这是 Claude Code、Factory Droid 和 Devin 会使用的字段。Codex 在子 agent 线程内触发其提示事件，Copilot 运行进程内助手，Goose 有 `delegate` 工具，OpenClaw 运行角色扮演——这些都不会在载荷中留下可识别的标记，因此这些 harness 上的子 agent 提示会被记录为会话自身的提示。OpenClaw 的 `openclaw.agentId` **不是**该标记：已发布的插件在每次运行（包括所有者的运行）中都会设置它。
- **不携带标记的调度器。** Claude Code 的 `schedule_wakeup` 和 `loop_wakeup`，以及 OpenClaw 的 `cron` 和 `heartbeat` 触发器，会被拒绝，因为这些 harness 在载荷中明确说明了这一点。Goose 自己的调度器（`goose schedule add`）和 Codex 的 `codex exec` 不携带任何标记，因此它们启动的运行会像其他运行一样被记录。
- **Agent 的最后一条消息可以是 agent 自己选择的消息。** 记录未经过身份验证，因此能够改写自己记录的 agent 可以决定其"最后一条消息"的内容。它被标注为 agent 所写，本身不会通过任何策略——但需注意，`decide.ts` 的 v1 路径允许它满足确定性的"用户是否命名了此目标"检查，因此控制自身记录的 agent 可以提供覆盖所需的目标名称。
- **以扩展的机器标题开头的提示会被整体丢弃。** 如果提示以 `# Selected text:`、`# Diff comments:`、`# Chrome tabs:` 或上述第一组的其他节标题开头，且没有 `## My request:` 标题，则该轮次不会记录任何内容——也不会通过任何策略。这是故意的：这些节携带的是他人控制的文本（你选中的代码、审阅者的差异评论、页面标题），将其记录为你的话语才是更严重的失误。开发者有可能手动输入的标题在第二组中，本身永远不会丢弃提示。
- **OpenCode 在实践中不记录任何内容。** 其 `message.updated` 事件在当前 OpenCode 中不携带文本，而且该事件也会为其任务工具创建的子会话触发，这些子会话的"用户"消息是父 agent 写的。
- **`CODEX_HOME` 在 `lib/codex-sessions.ts` 的 rollout 发现中不被遵守。** 这只影响查找 agent 消息快照的位置，不影响是否记录提示。
