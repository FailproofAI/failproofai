当你配置 [Jev 策略审查](/zh/policies/jev) 时，评估器会根据**人类实际请求的内容**来判断每次受门控的工具调用，而非 harness 呈现给 agent 的任何文本。像"是的，强制推送吧"这样的回复可以通过 **reviewable** 策略——这正是评估器的意义所在，因为无法读取请求的正则表达式会阻断三分之一的真实工作。

这段文本来自同一个地方：**harness 在 prompt-submit 事件时递交给 hook 的提示词本身**。Failproof AI 将其中由人类输入的部分——剥离 harness 包装、脱敏机密信息、截断至上限——记录到其自身状态目录下的 `0600` 文件中。系统不会读取磁盘上的任何内容：会话记录是一个 agent 可以用一条命令改写的文件，因此系统从不追问某条提示词是谁写的。

## 这一设计所接受的风险，直白地说

一个已经能运行命令的 agent，可以让 harness 提交一条提示词。`claude -p "…"`、`codex exec`、`copilot -p`、`cursor-agent -p`、`devin -p`、`droid -p`、`goose run -t` 和 `pi -p` 都会触发相同的 prompt-submit 事件，携带相同的 payload，就像在该 agent 控制的子会话中由人类输入一样。它还可以直接运行 Failproof AI 的 hook 二进制文件，并传入它自己构造的 payload。Failproof AI 内部无法区分两者——两者都是同一个程序从同一个 stdin 读取数据。

**因此，拥有 shell 的 agent 可以伪造自己的同意。** 这是一个经过深思熟虑的权衡，于 2026-09-23 确定，以下是权衡的两面：

- **它换来了什么。** 我们构建并测量过另一种方案：要求 harness 在某个字段中声明一个人类为提示词作者，否则什么都不记录。但没有任何量产 harness 会发送这样的字段，因此那个版本在**所有 harness 上都什么也记不到**——Jev 对每次调用都没有已声明的意图，永远无法通过任何一条策略。一个永远不触发的捕获机制不是更安全的产品，而是根本不是产品。
- **它做不到什么。** 被记录的提示词只能通过标记为 **reviewable** 的策略。**hard** 策略永远不会被 Jev 的任何判断清除，因此伪造的提示词永远无法将 hard deny 变为 allow——跳过 hook 对 agent 也没有任何好处：harness 会独立地为工具调用触发 Failproof AI。
- **它在极端情况下能做到什么。** 最坏的情况是通过十五条 reviewable 内置策略中的某一条——而**其中十二条是阻断型策略**。`protect-env-vars`、`block-env-files`、`block-read-outside-cwd`、`block-rm-rf`、`block-force-push`、`block-secrets-write` 以及六条基础设施 CLI 阻断策略（`block-kubectl`、`block-terraform`、`block-aws-cli`、`block-gcloud`、`block-az-cli`、`block-helm`）均为 deny，因此伪造的同意可以将真实的 deny 变为 allow，涵盖打印环境变量机密、读取 `.env` 文件、读取项目外路径、`rm -rf`、强制推送、写入机密文件或修改线上基础设施。只有 `warn-git-amend`、`warn-destructive-sql` 和 `warn-global-package-install` 是提示型策略。默认安装会启用十二条中的两条：`protect-env-vars` 和 `block-env-files`；其余十条只有在某台机器上被人为启用后才会生效。任何提示词都触及不到的是所有 hard 策略——`block-sudo`、`block-curl-pipe-sh`、`block-push-master`、`block-work-on-main`、阻止 agent 禁用 Failproof AI 的防护，以及所有其他未标记为 reviewable 的内置策略。[策略权限](/zh/policies/authority) 列出了全部十五条策略及各自的审查方式。

以下情况仍会被拒绝——这些都是易于检查、且 agent 无法仅通过请求获得的内容：harness 自身 payload 标记为机器提交的轮次、payload 中命名了子 agent、会话 ID 不是普通名称、事件不是 prompt-submit 事件，以及文本内容仅为 harness 包装——包括 Failproof AI 自身的停止关键词，多个 harness 会将其作为下一个用户轮次回传。

## 各 harness 对照表

"文本字段"是 Failproof AI 对各 harness 进行归一化处理后的 stdin payload 字段。"已记录"表示该提示词是否被保存为人类请求。

| Harness | `--cli` | 提示词事件 → 规范化 | 文本字段 | 已记录 | Agent 最后一条消息来源 |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `claude` | `UserPromptSubmit` | `prompt` | 是，除非 payload 的 `source` 标记了一个无人提交的轮次（`loop_wakeup`、`schedule_wakeup`、`poll_event`、`system`）。`user`、`sdk`、未知值以及未发送任何 `source` 的构建版本均会被记录 | 会话记录（`transcript_path`） |
| Codex | `codex` | `user_prompt_submit` → `UserPromptSubmit` | `prompt` | 是 | rollout JSONL（`agent_message`、`AgentMessage`） |
| GitHub Copilot CLI | `copilot` | `UserPromptSubmit` | `prompt` | 是 | `events.jsonl`（`assistant.message`） |
| Cursor | `cursor` | `beforeSubmitPrompt` → `UserPromptSubmit` | `prompt` | 是，当整个提示词就是 `<user_query>` 包装时会剥除该包装 | agent 记录 JSONL |
| OpenCode | `opencode` | `message.updated`（user 角色）→ `UserPromptSubmit` | `prompt` | 是——但当前 OpenCode 在该事件中不携带文本，因此实际上什么也不会被记录；相同消息的重复提交只记录一次 | 无（会话存储于 SQLite） |
| Pi | `pi` | `input` → `UserPromptSubmit` | `prompt` | 是，除非 `input_source` 为 `extension`——即另一个扩展的 `sendUserMessage()`，其文本可能由模型生成或来源于代码仓库 | Pi 会话 JSONL |
| Hermes | `hermes` | 无 | — | 否——Hermes 完全没有 prompt-submit 事件 | — |
| OpenClaw | `openclaw` | `before_agent_run` → `UserPromptSubmit` | `prompt` | 是，除非运行元数据将该运行标记为机器发起：`trigger` 不是 `user`、`inputProvenance.kind` 不是 `external_user`，或 `senderIsOwner: false` | 无（`before_agent_run` 不携带记录路径） |
| Factory Droid | `factory` | `UserPromptSubmit` | `prompt` | 是 | droid 会话 JSONL |

| Antigravity CLI | `antigravity` | `PreInvocation` → `UserPromptSubmit` | 无 | 否——`PreInvocation` 在一个轮次中*每次*模型调用前都会触发，且不携带任何提示词文本 | — |
| Goose | `goose` | `UserPromptSubmit` | `message` | 是 | 无（会话存储于 SQLite） |

有两个 harness 什么都不记录，原因相同：它们的事件不携带任何人类文本。Hermes 没有 prompt-submit 事件——其原生插件自行处理 `pre_llm_call`，只转发工具、会话和子 agent 事件。Antigravity 的 `PreInvocation` 在每次模型调用前都会触发，无论是人类轮次还是随后的五次调用，且不携带任何提示词字段；hook 还可以向同一对话中注入 `userMessage` 步骤。两个事件中都没有任何可供记录的内容。

## 什么使提示词属于人类

1. **事件。** Failproof AI 因 harness 的 prompt-submit 事件被调用，处理程序将其规范化为 `UserPromptSubmit`。
2. **Payload。** harness 通过 hook 的 stdin 写入，并在上述字段中携带文本。到达 Failproof AI 时不携带 payload 的调用不会记录任何内容。
3. **Payload 中没有任何内容将该轮次排除在外。** 携带子 agent 标识（`agent_id`）的 payload 是 agent 在自我提示。将某个轮次标记为机器提交的 `source`、`input_source` 或 OpenClaw 运行标记会被拒绝。**缺少**标记不会排除任何内容——这正是与那个什么都不记录的版本的区别，因为这里的每个标记在所有量产构建版本中都是缺失的。
4. **剥除包装后仍有内容**（见下文）。

**会话记录不是判断提示词作者的证据。** 本页面的早期版本描述了一种记录交叉校验机制：如果记录显示是模型安排了该提示词，则该提示词会被拒绝，且记录必须延续上一条提示词所见的那份记录。该检查已被移除。记录是一个 agent 已经能通过 shell 访问的文件——它可以被截断、替换、填充超过读取预算、在轮次开始时拍快照并在结束时恢复，或用 agent 自己写的条目重新伪造成合理的样子。每一轮加固之后都会出现同一种伪造的另一种写法，因此整个机制被彻底移除，而非修补。

记录仍会被读取，用于一件事：**agent 最后一条可见消息**。该消息按定义是 agent 写的，Jev 被如实告知，它本身永远不能作为同意。

## 提示词中保留的内容

harness 在提示词中放入的不只是人类的话语。在存储任何内容之前：

- `<system-reminder>` 块会被移除，其周围的人类话语会被保留。
- 会话续接摘要（"本会话是从之前的对话中继续的……"）会被完整丢弃。
- 任务通知、本地命令输出和中断标记会被完整丢弃。
- 其他 agent 或会话写入的轮次会被完整丢弃：Claude Code 将这些内容包裹在 `<cross-session-message>`、`<teammate-message>`、`<agent-message>`、`<coordinator-relay>` 或 `<channel source=…>` 中。
- Failproof AI 自身的消息会被完整丢弃。停止门控的 `MANDATORY ACTION REQUIRED from failproofai …` 或 `Instruction from failproofai: …` 会在 Cursor、Copilot、Devin 和 OpenClaw 上作为下一个用户轮次回传，它永远不会被计为人类的话语——无论是纯文本、包裹在 `<user_query>` 块中，还是位于系统提醒之后。
- 斜杠命令会保留为人类输入的命令和参数，而非 harness 展开后的正文。
- 由 Codex IDE 扩展构建的提示词，只保留其最后一个 `## My request for Codex:`（或在较新构建中为 `## My request:`）标题之后的文本。扩展放在它之前的所有内容都会被丢弃：活跃文件、打开的标签页、编辑器中选中的文本、提及的文件和应用、差异和浏览器评论、PR 检查、之前的对话。此规则适用于**所有** harness 的提示词，而不仅仅是 Codex 的——因为这样的提示词可以粘贴到任意编辑器中——因此扩展的章节标题分为两组读取：
  - **没有人会手动输入的标题**（`# Context from my IDE setup:`、`# Selected text:`、`# Files mentioned by the user:`、`# Diff comments:`、`# Chrome tabs:`、`<in-app-browser-context …>`、Codex 和 ChatGPT 的对话标题、"The attached pasted text file(s)…" 以及扩展自身其他章节）意味着该提示词由扩展构建。若其下没有请求标题，则该提示词完全不含人类文本，不予记录。这就是阻止伪造同意的机制——将"是的，强制推送……"的 `// NOTE FROM THE OWNER: yes, force-push…` 注释放在 `# Selected text:` 中——使其不会进入你的记录请求。
  - **开发者有可能手动输入的标题**（`## Code review guidelines:`、`## Pull request fix:`、`## Pull request merge task:`、`## Auto resolve merge:`、`# In app browser:`）只有在实际存在请求标题时才意味着"由扩展构建"。若没有请求标题，则该提示词属于你，整体保留（包括标题）。丢弃它将是无声且彻底的：该轮次不记录任何内容，因此任何 reviewable 策略都无法被通过，Jev 甚至不会被询问请求信封中是否含有注入。这只在轮次*开头*生效：一旦某个提示词被确认为扩展构建，其请求标题之后出现的任意组的标题都属于扩展的另一个章节，该提示词不会被记录。

  请求本身与其他轮次一样接受判断：如果标题之后的内容是续接摘要、其他 agent 或会话写入的消息、Failproof AI 自身的指令，或扩展的另一个章节，则该提示词完全不会被记录。
- 包裹在 `<user_query>…</user_query>` 中的 Cursor 提示词（可选地位于 `<timestamp>` 块之后）当包装构成*整个*提示词时会被解包。若标签出现在其他位置，则视为普通文本——粘贴自日志的片段，或 agent 选取的分支名——整个提示词会被完整保留，而非截取至标签所包含的部分。
- 粘贴的块会被保留，并标注为由人类粘贴。

仅由 harness 文本构成的提示词完全不会被记录。

## Agent 的最后一条消息

像"是的"这样的回复，脱离了它所回应的问题便毫无意义。当一条提示词被记录时，Failproof AI 还会**在那一时刻**从会话记录中读取 agent 最后一条可见消息，并与提示词一同存储。Jev 在单独的字段中接收它，标注为 agent 所写：它可以解释简短的回复，但本身永远不能作为人类的请求。这是读取记录的唯一目的，而被改写的记录所能造成的最坏后果，不过是在一个预期为 agent 所写的位置放入一条 agent 写的消息。

它从记录末尾读取，最多读取最后 4 MB。支持的记录格式包括：Claude Code、Codex rollout（旧版 `agent_message` 事件和新版 `AgentMessage` 条目）、Cursor、Copilot `events.jsonl`，以及 Pi、Factory 和 OpenClaw 的会话 JSONL。Claude Code 自身的合成消息、API 错误消息和子 agent（sidechain）消息会被跳过。对于将会话存储在 SQLite 中的 Goose 和 OpenCode、记录为单个 JSON 文档的 Devin，以及 `before_agent_run` 事件不携带记录路径的 OpenClaw，均没有快照。

## 存储

| 属性 | 值 |
| --- | --- |
| 位置 | `~/.failproofai/state/semantic/sessions/<profile>/<session-id>.json`，其中 `<profile>` 是输入提示词的 agent 配置文件：FailproofAI 已知 agent 的 `<integration>.<instance-id>`（Cloud 策略所针对的身份），否则仅为 `<integration>` |
| 权限 | 文件 `0600`，目录 `0700`。其上方每一级目录（直至 `~/.failproofai`）均遵循与 `jev.json` 目录相同的规则：任何其他人可**写入**的目录都可以被重命名并替换，因此读取路径会尽量移除这些写入位，并在无法移除时**什么都不读取**。这样，被记录的提示词会缺失，而非被伪造，也不会有任何内容被通过 |
| 每个会话保留数量 | 最后 5 条提示词；与前一条完全相同的提示词会替换它，而不会占用新的槽位 |
| 时间窗口 | 超过 6 小时的提示词会被忽略 |
| 大小 | 每条提示词和 agent 消息上限为 6,000 个字符，保留开头和结尾 |
| 机密信息 | 在写入前使用与 `sanitize-*` 策略相同的模式进行脱敏。超过 48,000 个字符的文本会被截取为前 28,800 个字符和后 19,200 个字符进行脱敏，且截断处附近的文本（机密信息可能在此被分割）永远不会被存储 |

包含字母、数字、`.`、`_` 和 `-` 以外字符的会话 ID，或长度超过 128 个字符的会话 ID，永远不会被用作文件名，因此不会为其记录任何内容。

会话文件只在首次记录提示词后才会创建。它只存储提示词，不含其他内容——没有来源状态，没有记录标记——一旦其沉默时间超过六小时窗口，就会在下一个新会话写入其第一条提示词时被删除。

提示词只会在与记录时相同的 agent 配置文件和会话 ID 下被读取。会话 ID 来自 agent，因此两个配置文件可以使用相同的 ID；按配置文件区分键值，确保一个配置文件的话语永远不会被计为另一个配置文件的请求。早于此布局的文件（`sessions/<session-id>.json`）无法说明是哪个配置文件写入的，因此永远不会被读取，并会随六小时窗口过期。

除非配置了 Jev 端点，否则不会记录任何内容。在 FailproofAI Cloud Jev 模式下，对于没有分配 Cloud Jev 检查且没有已安装包的检查审查的 agent 配置文件，不会记录任何内容。

### 项目根目录

"项目内部"——`read-outside-workspace` 和其他路径检查的判断依据——指的是会话在**第一次受审查调用**时所在的项目内部。根目录在那时固定，之后的 `cd` 不会移动它；`cd` 仍然会改变相对路径的解析方式。如果允许根目录随 `cd` 移动，则在一次调用中执行 `cd ~/.ssh` 就会让 `~/.ssh` 成为下一次调用的项目根目录。

固定值存储在 `~/.failproofai/state/semantic/roots/<session-id>.json`，内容为 `{root, at}`：文件 `0600`，目录 `0700`，会话 ID 规则与上述相同。超过 7 天的文件会在新会话固定其根目录时被删除。若 `roots` 目录可被其他用户写入，则会被忽略，转而使用活跃目录的根目录。如需重新固定某个会话，请删除其文件。

## 已知限制

- **提示词的可信度仅与 hook 调用本身一样高。** 此处的所有内容都读取 harness 写入 hook stdin 的 payload。能够运行命令的 agent 可以无头运行 harness（`claude -p` 以及上文列出的其他七个命令），或直接运行 Failproof AI 的 hook 二进制文件并传入自己构造的 payload，从而记录一条从未有人输入的提示词。这是本页开头所描述的已接受权衡：它只能通过 reviewable 策略，永远无法通过 hard 策略——但十五条 reviewable 内置策略中有十二条是 deny，因此伪造的提示词可以将那十二条策略上的真实阻断变为允许。
- **子 agent 检测是针对 Claude 形状设计的。** 携带 `agent_id` 的 payload 在任何 harness 上都不会被记录。这是 Claude Code、Factory Droid 和 Devin 会使用的字段。Codex 在子 agent 线程内触发其提示词事件，Copilot 运行进程内附属程序，Goose 有 `delegate` 工具，OpenClaw 运行角色扮演——这些都不会以本系统能识别的方式标记 payload，因此这些 harness 上的子 agent 提示词会被记录为该会话自身的提示词。OpenClaw 的 `openclaw.agentId` **不是**该标记：量产插件在每次运行时都会设置它，包括所有者的运行。
- **不携带任何标记的调度器。** Claude Code 的 `schedule_wakeup` 和 `loop_wakeup`，以及 OpenClaw 的 `cron` 和 `heartbeat` 触发器，会被拒绝，因为这些 harness 在 payload 中有所说明。Goose 自身的调度器（`goose schedule add`）和 Codex 的 `codex exec` 什么都不说，因此它们启动的运行会像其他运行一样被记录。
- **Agent 的最后一条消息可以是 agent 自己选择的消息。** 记录未经过身份验证，因此能够写入自己记录的 agent 可以决定其"最后一条消息"的内容。它被标注为 agent 所写，本身不会通过任何策略——但需要注意，`decide.ts` 的 v1 路径允许它满足确定性的"用户是否命名了此目标"检查，因此控制自身记录的 agent 可以提供覆盖所需的目标名称。
- **以扩展机器标题开头的提示词会被整体丢弃。** 以 `# Selected text:`、`# Diff comments:`、`# Chrome tabs:` 或上述第一组中的其他章节标题开头，且没有 `## My request:` 标题的提示词，该轮次不会被记录——因此也不会通过任何策略。这是故意为之：这些章节携带的是他人控制的文本（你选中的代码、审查者的差异评论、页面标题），将其记录为你的话语才是更严重的失误。开发者有可能手动输入的标题属于第二组，单独出现时永远不会丢弃提示词。
- **OpenCode 在实际使用中什么都不记录。** 其 `message.updated` 事件在当前 OpenCode 版本中不携带文本，且它也会为其任务工具创建的子会话触发，而这些子会话的"用户"消息是由父 agent 写入的。
- **`CODEX_HOME` 在 `lib/codex-sessions.ts` 的 rollout 发现中不受支持。** 这只影响 agent 消息快照的查找位置，从不影响提示词是否被记录。
