这是使用自有密钥配置 [Jev 策略](/zh/policies/jev) 的 provider 参考文档。正则策略匹配的是字符串——它无法区分你主动要求的 `rm -rf build/` 和偷偷混入计划里的 `rm -rf ~`，所以在某些地方拦得太多，在另一些地方又拦得太少。**Jev** 是 TypeSafe 的分类器，它会根据你实际的请求内容分析工具调用，并在一次快速请求中回答一系列是/否问题。

配置好自有 Jev 端点和密钥后，Failproof AI 会在每次工具调用时**同时**向 Jev 和正则策略进行咨询，而非以 Jev 取代正则策略：

- **硬性**策略的拒绝是最终决定，Jev 无法撤销。除非策略显式标记为可审查并指定了覆盖该策略的 Jev 检查项，否则所有策略默认为硬性策略——因此，未做任何声明的自定义策略、扩展包策略或 Cloud 策略均为硬性策略，始终启用的自保护守卫也始终是硬性策略。
- **可审查**策略的拒绝可以被撤销，但前提是：Jev 被专门询问了该策略所关注的确切问题，且回答为"此处无问题"或"用户主动请求了此操作"。若某项检查确认了问题属实，且用户并未主动要求该调用，则拒绝依然有效——即便该检查本身的结论仅为警告，因为在工具调用发出前，警告并不会阻止 agent。而当该检查属于可发出拒绝的类型（如密钥泄露、凭证外泄、破坏性删除等），该调用上的任何拒绝都不会被撤销。
- 若某次拦截对应的是你交代的任务步骤且影响范围不超出该步骤，它仍可能降级为**警告**：Jev 会将自身的拒绝软化为警告，该警告——具体说明调用的实际问题——将取代策略的拦截。
- Jev 也可以自主发出警告或拒绝，用于处理正则表达式无法描述的危险操作。
- 若 Jev 无法给出答案（超时、速率限制、服务器错误、积分耗尽、模型版本异常），该调用将沿用正则策略结果，与未配置 Jev 时完全一致。
- 除非 Jev 读取了完整的调用内容并被询问了确切的关注点，否则 Jev 绝不会让调用获得比单独使用策略更宽松的许可。若条件不满足——调用内容过大无法完整发送，或疑似注入攻击——所有清除授权将被撤回，每项拒绝均保持有效。

<Note>
未配置 Jev 时，一切不变：hooks 将完全按既有方式执行正则策略。配置文件本身就是唯一的启用开关。
</Note>

<Tip>
使用 FailproofAI Cloud？你无需自备密钥：持有 `jev:evaluate` 权限密钥的已连接机器可以在你组织的套餐下使用 Jev。详见 [通过 FailproofAI Cloud 使用 Jev](/zh/reference/jev-cloud)。
</Tip>

## 开始之前

在你的 agent 运行的机器上安装 **failproofai 1.0.8-beta.0 或更高版本**，并将其 hooks 附加到[受支持的 harness](/zh/reference/harnesses)。如果是新机器，请参考[快速开始](/zh/start/quickstart)；如果不使用 Cloud，请参考[配置本地执行](/zh/start/setup#enforce-locally)。使用 `failproofai --version` 检查已安装的 CLI 版本。

从下方的 provider 获取 API 密钥，或准备好兼容端点及其密钥。Jev 在 `PreToolUse` 或 `PermissionRequest` 门控处审查具名工具调用，可以发出自己的裁决，但撤销现有策略拒绝还需要安装一条标记为[可审查](/zh/policies/authority)的策略。硬性策略拒绝始终为最终决定。

## 选择 provider

Jev 可通过五条路由访问，选择其中任意一个并准备对应密钥即可。

| Provider | `--provider` | 端点 | 默认模型 | 备注 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 精确版本锁定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 请求仅路由到零数据保留端点，不会回退到其他 provider。返回类似 `typesafe/jev-1.13-20260917` 的日期版本号。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | Jev 仅以别名标识，因此响应版本记录为未验证。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | 需要 `--account-id`。实测每个密钥约每秒六次调用后触发 HTTP 429。 |
| 自定义端点 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | 任何接受 TypeSafe 请求体并报告响应模型的端点。仅支持 `https`；本地测试时允许使用明文 `http` 连接回环地址（`localhost`、`127.0.0.1`、`::1`）。 |

<Warning>
使用 Vercel 自带密钥功能时，失败的请求会静默地使用 Vercel 的凭证重试。如果你需要所有调用均计费至且仅对你自己的 TypeSafe 账户可见，请直接使用 TypeSafe。
</Warning>

## 配置方法

一条命令，指定端点和密钥。先以 `observe` 模式启动，以便在现有策略继续决定调用的同时查看 Jev 的裁决：

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL 决定 provider

你无需手动指定 provider：URL 的**主机名**即可确定使用哪个 provider。

| URL 主机 | Provider | 额外参数 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| 其他主机 | `custom` | — 你提供的 URL 即为 base URL |

由此产生三条规则：

- **若 URL 是该 provider 的官方 API，则不写入任何覆盖配置。** `--url https://api.typesafe.ai/v1` 与 `--provider typesafe` 产生完全相同的配置。若在已知 provider 下使用不同的路径或主机，则会作为 base URL 存储，效果等同于 `--base-url`。
- **`--provider` 仍可覆盖自动推断**，这正是通过自有主机代理某个 provider API 的方式：`--url https://jev-proxy.internal/v1 --provider typesafe`。
- **`--provider` 与主机矛盾时会被拒绝**，而非猜测处理。`--provider openrouter --url https://api.typesafe.ai/v1` 不会写入任何配置，并会说明原因：两种写法对密钥发送目标存在分歧。同样的组合在 `jev setup --base-url` 和控制台的 Jev 设置中也会被拒绝。（`--provider custom` 不构成矛盾——它的含义是"将此 URL 视为其本身"——但在 Cloudflare 主机上除外，其按账户区分的端点无法通过自定义路由访问。）

`--url` 的验证规则与配置文件中 `baseUrl` 的验证规则完全一致，拒绝时使用相同的提示：在任何模式下均需使用 `https`，仅在本地测试时允许对回环地址（`localhost`、`127.0.0.1`、`::1`）使用明文 `http`。风险提示：回环服务器无任何身份验证，在其停机期间，其他本地进程可能占用其端口并响应请求；请在本地测试之外使用 `https`。

### 密钥

通过 `--key-stdin` 管道传入，或在终端中不带该参数运行命令并在遮蔽提示符处粘贴密钥。两种方式都会将密钥直接写入配置文件，不会以任何形式回显。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` 接受相同的参数，是完整写法：使用 `setup --provider <kind>` 可以直接指定 provider 名称而非 URL。

### `--token` 及其代价

`--token <token>` 将密钥放在命令行参数中，这是配置机器最快的方式，也是唯一会将密钥留在配置文件之外的写法：

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
命令行参数执行后会留在你的 shell 历史文件中，且在命令运行期间会出现在进程列表里——任何以你的身份运行的进程均可从 `/proc` 读取到。每次使用 `--token` 时，`setup` 都会给出提示。在共享机器上、在有录制的会话中，或在历史文件会同步的环境下，建议优先使用 `--key-stdin`；如果以这种方式传递过密钥，请及时轮换。
</Warning>

`--token`、`--key-stdin` 和 `--key-from-env` 三者互斥，只能选其一。

配置完成后，发送一次小型实时请求以验证密钥、端点和响应的 Jev 版本：

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

当答复在超时后才到达（此时每个 hook 都会回退到 `timeout` 下的正则策略），或检查问题回答有误时，`jev test` 退出码为 1，并在标题中注明。

Hooks 在每次工具调用时读取配置，因此配置从下一次调用起立即生效，无需重启任何服务，无论是否使用守护进程。

## 查看运行状态

```bash
failproofai jev status
failproofai jev status --json
```

`status` 显示 provider、端点、模型、模式、配置文件及其权限，但永远不显示密钥。下方还会汇总近期活动：Jev 评估了多少次调用、因何原因回退到正则策略及回退次数、延迟情况，以及清除了哪些可审查策略。

## 验证实际调用

在已挂钩的 agent 中开启新会话，要求其使用文件读取工具读取 `README.md` 并报告标题。确认会话中包含该工具调用后，再次运行 `failproofai jev status`：近期已评估调用次数应有所增加。在[本地控制台](/zh/reference/local-dashboard#review-policy-activity)中打开 **Policies → Activity**，查看该调用的 Jev 裁决和模式。在 observe 模式下，策略结果仍然决定调用结果。只有当可审查策略匹配且 Jev 清除了所有指定检查项时，才会出现清除记录；普通读取操作可能没有需要清除的策略。

## Observe 模式

默认模式为 `enforce`。如需观察 Jev 而不让其影响任何决定，切换到 `observe` 模式：Jev 仍会被调用且其裁决会被记录，但实际执行的是正则策略结果。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` 保留配置（端点和密钥）并停止调用 Jev：hooks 将完全按没有配置时的方式执行正则策略，`failproofai jev status` 显示"off (switched off)"。使用 `--mode observe` 或 `--mode enforce` 可重新启用。

对同一 provider 重新运行 `setup` 会保留已存储的密钥，因此切换模式只需一个参数。切换 provider 则需从头配置并提供新 provider 的密钥。将请求迁移到不同主机的 `--base-url` 也同样如此：已存储的密钥仅发送到其最初配置时对应的主机或该 provider 的官方 API。

## 配置文件

所有配置集中存储在一个文件中：由 `setup` 写入的 `~/.failproofai/jev.json`：

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 字段 | 含义 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare` 或 `custom`——也可以是 `failproofai`，其密钥来自 FailproofAI Cloud 连接而非本文件（见[通过 FailproofAI Cloud 使用 Jev](/zh/reference/jev-cloud)）。 |
| `apiKey` | 以 `Authorization: Bearer <key>` 方式发送。 |
| `baseUrl` | `custom` 时必填；否则替换 provider 的 API base。必须使用 `https`。仅在 `mode: observe` 时接受明文 `http` 到 `localhost`：本地端口无身份验证，代理停机时，机器上任何进程（包括被审查的 agent 本身）都可能在其位置上响应。 |
| `accountId` | 仅 Cloudflare 需要：32 位小写十六进制字符。 |
| `model` | 替换 provider 的默认模型 ID。带版本的 ID 必须指向 Jev 1.13。形如 API 密钥的值会被拒绝（且不会回显），因此误填到 `--model` 的密钥不会被存储或作为模型名发送。 |
| `timeoutMs` | 工具调用等待 Jev 响应的超时时间，超时后使用正则策略结果。范围 100–10000，默认 3000。 |
| `mode` | `enforce`（默认）、`observe` 或 `off`（保留配置，不运行 Jev）。 |

三条规则保护此文件：

- **仅限所有者访问。** 文件以 `0600` 权限写入。任何其他用户或组可读可写的副本将被**拒绝**，hooks 将回退到正则策略，直到你执行 `chmod 600 ~/.failproofai/jev.json` 或重新运行 `setup`。目录也会被检查：`~/.failproofai` 不得被其他任何人**写入**，因为有写入权限者可以替换文件，无论文件本身的权限如何。`setup` 发现此类写入位时会将其移除。`failproofai jev status` 会在配置被拒绝时给出提示，并显示文件所指向的端点：他人可能已修改过该文件，请在执行 `chmod` 前确认文件内容属于你。对这类文件重新运行 `setup` 时，已存储的密钥仅发送到 provider 的官方 API；文件中指向其他端点的配置需重新提供密钥（`--key-stdin`），或使用 `--base-url default` 将请求重定向回 provider。
- **仅全局配置有效。** 仓库无法开启 Jev、将其指向其他端点或选择模型：项目内的 `.failproofai/jev.json` 会被忽略，provider、URL、模型和账户 ID 只从上述全局文件读取——而非从环境变量读取（仓库的 agent 设置可以设置环境变量）。（`FAILPROOFAI_HOME` 也无法绕过此限制：它会移动整个 failproofai 目录（包括策略），而不是单独重定向 Jev。）
- **仅密钥可从环境变量读取。** 若文件中没有 `apiKey`，`FAILPROOFAI_JEV_API_KEY` 将在当前会话中提供密钥（`setup --key-from-env` 会写入这样的文件）。它不会替换文件中已有的密钥，也无法在没有配置文件的情况下单独启用 Jev。若未设置该变量，Jev 在该 shell 中仅为关闭状态：`failproofai jev status` 会给出提示，以退出码 0 退出并保持配置不变（`status --json` 返回 `"status": "key-missing"` 及 `"reason": "no-env-key"`）。`failproofaid` 守护进程无法访问你的 shell 环境变量，因此在通过 `failproofai config` 配置的机器上，请将密钥保存在文件中。

## 响应的 Jev 版本

Failproof AI 的决策阈值是针对 Jev 1.13 校准的，因此只有来自该版本家族的答复才会被使用：`jev-1.13.x`，或 OpenRouter 的 `typesafe/jev-1.13-<date>`。若 provider 仅以别名标识 Jev 且未报告版本（Vercel，以及未说明版本的 Cloudflare），答复仍会被使用，但记录为未验证。`custom` 端点必须报告响应的模型名；唯一的例外是你为其配置的无版本号 `--model` 名称，该名称回显时同样记录为未验证。报告其他版本的答复，或未报告模型的 `custom` 答复，均不会被使用：该调用将以 `model-mismatch` 为原因回退到正则策略。

## Jev 无法给出答复时

以下每种情况都会使该调用回退到正则策略结果，并记录相应原因，`failproofai jev status` 会汇总各原因的次数：

| 原因 | 触发条件 |
| --- | --- |
| `timeout` | 在 `timeoutMs` 内未收到答复。 |
| `http-429` | provider 对该密钥触发了速率限制。 |
| `rate-limited` | Failproof AI 自身的限速器在发送前拦截了该调用：每秒最多 5 次请求，突发上限也为 5 次，provider 返回 `429` 后会短暂暂停。非 provider 侧限制。 |
| `http-500`、`http-502`、`http-503`……| provider 侧服务器错误，具体状态码会被记录。 |
| `out-of-credits` | HTTP 402：provider 账户积分已耗尽。 |
| `provider-refused` | Cloudflare 返回的 HTTP 402，提示"Model execution failed (Payment error)"：provider 拒绝在此请求上运行模型。通常与计费无关，充值不能解决问题。 |
| `http-401`、`http-403` | 密钥被拒绝。 |
| `http-404` | `<base>/systemone` 路径下无内容，说明 base URL 有误——`/systemone` 会被附加在其后，每个 provider 在其版本根路径下提供该接口。`failproofai jev models` 可查看端点实际提供的内容。 |
| `network` | 无法连接到端点。 |
| `http-301`、`http-302`、`http-307`、`http-308` | 端点返回了重定向。重定向永远不会被跟随，答复只会来自配置中的 URL；请将 `--base-url` 设置为最终 URL。 |
| `malformed` | 端点有响应，但不是 Jev 格式的答复——响应体不是 JSON，或其中不含答案。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflare 信封报告了失败，或任务尚未完成。 |
| `model-mismatch` | 响应的 Jev 版本不是 1.13，或 `custom` 端点未说明响应的模型。 |
| `request-cut` | **不是故障。** Jev 已响应，但只看到了部分调用内容，因此其答复不能清除任何拒绝。详见[Jev 有响应但未覆盖完整调用时](#when-jev-answered-but-not-on-the-whole-call)。 |

`failproofai jev status` 还可能显示一些更罕见的原因，例如 `upstream-error`（答复携带了 provider 自身的错误）或 `config`，以及将所有无法命名的原因汇总为 `other`。

`request-cut` 被收录在此表中，是因为 `failproofai jev status` 会将其与其他原因一并汇总，且它同样会保持所有拒绝有效。但它是这里唯一与 provider 状态无关的原因：请求已到达评估器，Jev 也已给出答复。与上方所有行不同，该答复仍然有效——Jev 自身的拒绝或警告会在正则策略结果之上叠加，而非被丢弃。因此，若连续出现多个此类记录，说明到达评估器的调用内容过大无法完整发送，而非端点异常，充值积分或更换 URL 也无法改变这一数字。

## Jev 有响应但未覆盖完整调用时

还有两种情况，都不是 Jev 未能给出答复，而是关于调用本身或对话的多少内容能装入一次请求。

**调用内容本身未能完整装入。** 工具调用在固定预算内发送，对于超大调用——非常大的 `Write`、巨型 MCP 体、被填充到上限的命令——会发送能装入的部分。Jev 仍会给出答复，该答复仍然有效：其自身的拒绝或警告照常生效。但它无法**清除**任何内容，因为基于部分调用给出的裁决不是对整个调用的裁决。因此所有策略拒绝保持有效，该调用以 `request-cut` 为原因记录为回退，`failproofai jev status` 会将其与上方的原因一并汇总。这条规则的含义是：让调用变得更大可能导致其失去清除授权，但永远无法换取授权。

**某条消息未能完整装入。** 你粘贴的长提示词、agent 的最后一条消息，或已被此评估器自身的存储截断过的提示词。**这种情况不会改变任何结果**：该调用的判断、清除和记录与其他调用完全相同，也不会被计为回退。你输入内容的长度永远不会决定裁决，截断也无法制造同意：若提示词在到达时已被截断，"你没有要求此操作"就不再是一个可以得出的结论，而非变成一个结论。

两者的区别在于文本的作者。调用是 agent 编写的，若允许其长度降低严重性，则等于给了 agent 可利用的规则；提示词是你写的，将其长度视为信号只会惩罚粘贴规格文档或调用栈的正当行为。

## 什么内容会离开本机

对于 Jev 评估的每次工具调用，会向你的 provider 发送一次请求，内容包括：

- 工具调用本身，其中 API 密钥、Bearer token 和 `KEY=` 赋值等密钥信息已脱敏处理；
- 你最近输入的提示词，其中 agent harness 添加的文本已移除；
- 在你最近一条提示词之前 agent 发送的最后一条消息，标注为 agent 编写；
- 本地计算的事实信息，例如路径是否在项目目录内——会话首次接受审查时所在的目录，[在会话期间锁定](/zh/reference/jev-intent#the-project-root)——以及当前 git 分支。

请求仅发送到你配置中指定的端点，使用你自己的密钥。

## 关闭 Jev

```bash
failproofai jev remove
```

此命令会删除 `~/.failproofai/jev.json`。从下一次工具调用起，hooks 将完全按之前的方式执行正则策略。`~/.failproofai/state/semantic/` 下的会话级存储（`sessions/` 中的已记录提示词、`roots/` 中的项目根目录）将保留原位并自然老化过期。若想停止调用 Jev 但保留配置，请改用 `failproofai jev setup --mode off`。

## 命令参考

| 命令 | 效果 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 一条命令完成配置；provider 由 URL 主机名决定 |
| `failproofai jev --url <url> --token <token>` | 同上，密钥放在命令行——会出现在历史文件和进程列表中 |
| `failproofai jev setup --provider <kind> --key-stdin` | 从 stdin 管道读取密钥并写入配置 |
| `failproofai jev setup --provider <kind>` | 同上，在遮蔽提示符处输入密钥 |
| `failproofai jev setup --key-from-env` | 不存储密钥；每次会话从 `FAILPROOFAI_JEV_API_KEY` 读取 |
| `failproofai jev setup --mode observe` | 切换模式（`enforce`、`observe` 或 `off`），保留已存储密钥 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 覆盖模型或 API base；使用 `default` 清除覆盖 |
| `failproofai jev setup --timeout-ms <n>` | 修改每次调用的超时预算 |
| `failproofai jev status [--json]` | 配置、权限及近期活动；永不显示密钥 |
| `failproofai jev test [--json]` | 一次实时请求：显示延迟和响应版本 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 该端点 `/models` 接口报告的模型 ID，并标注当前配置的模型 |
| `failproofai jev remove` | 删除配置；Jev 关闭 |
