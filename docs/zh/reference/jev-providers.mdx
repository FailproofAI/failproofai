本文是使用自有密钥配置 [Jev 策略](/zh/policies/jev)的提供商与配置参考文档。正则策略匹配字符串，它无法区分你主动要求执行的 `rm -rf build/` 和悄悄混入计划中的 `rm -rf ~`，因此会在某些地方拦截过多，在另一些地方又拦截不足。**Jev** 是 TypeSafe 的分类器，它会根据你实际的请求内容来解读调用，并在一次快速请求中回答一系列是/否问题。

配置好自有 Jev 端点和密钥后，Failproof AI 会在每次工具调用时**同时**向 Jev 发起询问，而不是以 Jev 替代正则策略：

- **硬性**策略的拒绝是最终决定。Jev 无法解除它。除非策略被明确标记为可审查并指定了所覆盖的 Jev 检查项，否则默认均为硬性策略——因此，未作任何说明的自定义策略、扩展包策略或 Cloud 策略都是硬性的，始终启用的自我保护防护也永远是硬性的。
- **可审查**策略的拒绝可以被解除，但前提是：Jev 被明确询问了该策略所关注的具体问题，且回答为"此处无异常"或"用户已请求此操作"。若某项检查发现问题确实存在，且用户并未请求该调用，则拒绝保持有效——即使该检查本身的判定仅为警告，因为在工具调用前，警告并不会阻止智能体。而当该检查属于可发出拒绝的类型（密钥泄露、凭证外泄、破坏性删除等）时，该调用的任何拦截均不会被解除。
- 当调用是你所布置任务的某个步骤、且影响范围未超出任务本身时，拦截仍可降级为**警告**：Jev 会将自身的拒绝软化为警告，该警告——指明调用的具体问题——将替换策略的拦截。
- Jev 也可以自主发出警告或拒绝，以应对正则表达式无法描述的危害行为。
- 若 Jev 无法给出答复（超时、频率限制、服务器错误、余额不足、意外的模型版本），该调用将沿用正则策略的结果，与未配置 Jev 时完全一致。
- Jev 绝不会在未读取完整调用内容、或未被询问具体关切点的情况下，使调用获得比纯正则策略更宽松的许可。条件不满足时——调用内容过大无法完整发送、疑似注入攻击——所有清除授权均被撤回，每项拒绝保持有效。

<Note>
未配置 Jev 时，一切不变：钩子完全按照既有方式运行正则策略。配置文件本身就是完整的启用入口。
</Note>

<Tip>
使用 FailproofAI Cloud？你无需自备密钥：持有 `jev:evaluate` 权限密钥的机器可以在组织套餐下使用 Jev。详见 [Jev through FailproofAI Cloud](/zh/reference/jev-cloud)。
</Tip>

## 开始之前

在运行智能体的机器上安装 **failproofai 1.0.8-beta.0 或更高版本**，并将其钩子附加到[受支持的运行环境](/zh/reference/harnesses)。如果是新机器，请参照[快速入门](/zh/start/quickstart)；如果不使用 Cloud，请参照[配置本地执行](/zh/start/setup#enforce-locally)。使用 `failproofai --version` 检查已安装的 CLI 版本。

从下方提供商处获取 API 密钥，或准备好兼容的端点及其密钥。Jev 在 `PreToolUse` 或 `PermissionRequest` 门控处审查具名工具调用。它可以自主发出判定，但解除现有策略拒绝还需要安装一条标记为[可审查](/zh/policies/authority)的策略。硬性策略的拒绝始终为最终结果。

## 选择提供商

Jev 可通过五种途径访问，为其中任意一种提供密钥即可。

| 提供商 | `--provider` | 端点 | 默认模型 | 备注 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 精确版本锁定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 请求仅路由至零数据保留端点，不回退至其他提供商。返回形如 `typesafe/jev-1.13-20260917` 的日期版本号。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | 仅通过别名标识 Jev，因此实际响应版本记录为未验证。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | 需要 `--account-id`。实测每个密钥约每秒六次请求触发 HTTP 429。 |
| 自定义端点 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | 任何接受 TypeSafe 请求体并报告响应模型的端点。仅支持 `https`；本地测试时允许通过明文 `http` 连接回环地址（`localhost`、`127.0.0.1`、`::1`）。 |

<Warning>
使用 Vercel 自带的 bring-your-own-key 功能时，失败的请求会静默地使用 Vercel 的凭证重试。如果你需要所有调用均计费至且仅对你自己的 TypeSafe 账户可见，请直接使用 TypeSafe。
</Warning>

## 配置步骤

一条命令，指定端点和密钥。先从 `observe` 模式开始，这样你可以在现有策略继续决定调用的同时查看 Jev 的判定结果：

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL 决定提供商

你无需手动指定提供商：URL 的**主机名**就是提供商的标识。

| URL 主机名 | 提供商 | 额外参数 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| 其他主机名 | `custom` | — 你提供的 URL 即为基础 URL |

由此衍生出三点规则：

- **使用提供商官方 API URL 时，不会写入覆盖配置。** `--url https://api.typesafe.ai/v1` 产生的配置与 `--provider typesafe` 完全相同。若在已知提供商的基础上使用不同路径或主机名，则会作为基础 URL 存储，效果与 `--base-url` 一致。
- **`--provider` 仍可覆盖自动推断结果**，这正是通过自有主机名代理某提供商 API 时的用法：`--url https://jev-proxy.internal/v1 --provider typesafe`。
- **`--provider` 与主机名矛盾时会被拒绝**，而非猜测处理。`--provider openrouter --url https://api.typesafe.ai/v1` 不会写入任何内容，并说明原因：两者对密钥发送目标的指定相互矛盾。同样的组合在 `jev setup --base-url` 和控制台的 Jev 设置中也会被拒绝。（`--provider custom` 不构成矛盾——它表示"将此 URL 视为自身"——但 Cloudflare 主机名除外，其按账户区分的端点无法通过自定义路由访问。）

`--url` 的验证规则与配置文件中 `baseUrl` 的验证完全一致，拒绝条件也相同：必须使用 `https`，或在任意模式下通过明文 `http` 连接回环地址（`localhost`、`127.0.0.1`、`::1`）。风险提示：回环服务器无任何身份验证，因此在其停机期间，本地其他进程可能占用其端口并响应请求；本地测试以外请使用 `https`。

### 密钥

通过 `--key-stdin` 管道传入，或在终端中不带该参数运行命令，然后在带掩码的提示符处粘贴密钥。两种方式均会将密钥直接写入配置文件，且不会回显。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` 接受相同的参数，是完整的长格式写法：若你更倾向于指定提供商而非 URL，可使用 `setup --provider <kind>`。

### `--token` 及其代价

`--token <token>` 将密钥直接置于命令行中，这是配置机器最快捷的方式，也是唯一一种让密钥留存于配置文件之外的写法：

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
命令行参数执行后会留在 shell 的历史记录中，且在命令运行期间会出现在进程列表里——以你的身份运行的任何进程均可从 `/proc` 中读取。每次使用 `--token` 时，`setup` 都会给出提示。在共享机器上、录屏会话中，或历史文件会同步的环境中，请优先使用 `--key-stdin`；若通过此方式传入了敏感密钥，请及时轮换。
</Warning>

`--token`、`--key-stdin` 和 `--key-from-env` 三者互斥，只能使用其中一个。

配置完成后，发送一个小型实时请求以验证密钥、端点以及响应的 Jev 版本：

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

当答复在超时后才到达（每个钩子都会回退到正则，原因为 `timeout`），或对检查问题的回答有误时，`jev test` 会以退出码 1 退出，并在标题中注明。

钩子在每次工具调用时都会读取配置，因此下一次调用起即生效，无需重启，无论是否使用守护进程。

## 查看运行状态

```bash
failproofai jev status
failproofai jev status --json
```

`status` 显示提供商、端点、模型、模式、配置文件及其权限，但不显示密钥。下方还会汇总近期活动：Jev 评估的调用数量、回退至正则的频次及原因、延迟情况，以及已解除的可审查策略。

## 验证真实调用

在已挂载钩子的智能体中开启新会话。让其使用文件读取工具读取 `README.md` 并报告标题。确认会话中包含该工具调用后，再次运行 `failproofai jev status`：近期已评估调用的计数应有所增加。在[本地控制台](/zh/reference/local-dashboard#review-policy-activity)的 **Policies → Activity** 中查看该调用的 Jev 判定和模式。在 observe 模式下，仍以策略结果决定调用。只有当可审查策略匹配且 Jev 通过了所有指定检查时，才会出现清除授权；普通的读取操作可能没有需要清除的策略。

## 观察模式

`enforce` 是默认模式。如需在不影响任何决定的情况下观察 Jev，可切换至 `observe` 模式：Jev 仍会被询问，其判定也会被记录，但实际执行的仍是正则策略的结果。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` 保留配置（端点和密钥），但停止询问 Jev：钩子完全按照无配置时的方式运行正则策略，`failproofai jev status` 显示"off (switched off)"。使用 `--mode observe` 或 `--mode enforce` 可重新启用。

对同一提供商重新运行 `setup` 会保留已存储的密钥，因此切换模式只需一个参数。切换提供商则会重新开始，并要求提供该提供商的密钥。将请求迁移至不同主机的 `--base-url` 也同样如此：已存储的密钥仅发送至最初配置时的主机，或该提供商的官方 API。

## 配置文件

所有配置均存储在一个文件中：由 `setup` 写入的 `~/.failproofai/jev.json`：

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 字段 | 含义 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare` 或 `custom`——或 `failproofai`，其密钥来自 FailproofAI Cloud 连接而非本文件（详见 [Jev through FailproofAI Cloud](/zh/reference/jev-cloud)）。 |
| `apiKey` | 以 `Authorization: Bearer <key>` 方式发送。 |
| `baseUrl` | `custom` 模式下必填；对其他提供商则替换其 API 基础地址。必须使用 `https`。仅在 `mode: observe` 下接受明文 `http` 连接 `localhost`：本地端口无身份验证，因此代理停机时，机器上任何进程（包括被审查的智能体本身）都可能在其位置上响应。 |
| `accountId` | 仅限 Cloudflare：32 位小写十六进制字符。 |
| `model` | 替换提供商的默认模型 ID。版本化 ID 必须指向 Jev 1.13。形似 API 密钥的值会被拒绝（且不回显），因此误粘贴到 `--model` 的密钥不会被存储或作为模型名发送。 |
| `timeoutMs` | 工具调用等待 Jev 回复的最长时间，超时后使用正则结果。范围 100–10000，默认 3000。 |
| `mode` | `enforce`（默认）、`observe` 或 `off`（保留配置，不运行 Jev）。 |

三条规则保护该文件：

- **仅限所有者访问。** 文件权限为 `0600`。若任何其他用户或组可读写该文件，访问会被**拒绝**，且钩子回退至正则，直到你运行 `chmod 600 ~/.failproofai/jev.json` 或重新运行 `setup`。目录也会被检查：`~/.failproofai` 不得被其他任何人**写入**，因为有写入权限者可以在文件自身权限不变的情况下替换文件内容。`setup` 发现写入权限时会将其移除。`failproofai jev status` 会在配置被拒绝时给出提示，并显示文件中所记录的端点：由于他人可能已修改文件，请在 `chmod` 之前确认文件内容属于你自己。对这类文件重新运行 `setup` 时，已存储的密钥仅会发送至提供商官方 API；文件中指定的其他端点需要重新提供密钥（`--key-stdin`），或使用 `--base-url default` 将请求恢复发送至提供商。
- **仅限全局配置。** 仓库无法开启 Jev、将其指向其他端点或选择模型：项目内的 `.failproofai/jev.json` 会被忽略，提供商、URL、模型和账户 ID 仅从上述文件读取——不从环境变量读取，而环境变量是仓库的智能体配置可以设置的。（`FAILPROOFAI_HOME` 也无法绕过这一限制：它移动整个 failproofai 目录，包括你的策略，而非单独重定向 Jev。）
- **仅密钥可从环境变量获取。** 若文件中没有 `apiKey`，`FAILPROOFAI_JEV_API_KEY` 可为该会话提供密钥（`setup --key-from-env` 会写入此类文件）。它不会替换文件中已有的密钥，也无法在没有配置文件的情况下单独启用 Jev。若该变量未设置，Jev 在该 shell 中仅为关闭状态：`failproofai jev status` 会给出提示，以退出码 0 退出，配置保持不变（`status --json` 返回 `"status": "key-missing"`，`"reason": "no-env-key"`）。`failproofaid` 守护进程无法读取你的 shell 环境变量，因此在通过 `failproofai config` 配置的机器上，请将密钥存储在文件中。

## 响应的 Jev 版本

Failproof AI 的决策阈值是基于 Jev 1.13 校准的，因此只有来自该版本系列的答复才会被采用：`jev-1.13.x`，或 OpenRouter 的 `typesafe/jev-1.13-<date>`。若提供商仅通过别名标识 Jev 且不报告版本（Vercel，以及 Cloudflare 未声明版本时），答复会被采用并记录为未验证。`custom` 端点必须报告响应的模型；唯一的例外是你为其配置的无版本号 `--model` 名称，该名称被回传时，同样以未验证方式记录。报告其他版本的答复，或 `custom` 端点未报告任何版本的答复，均不会被采用：该调用回退至正则，原因为 `model-mismatch`。

## Jev 无法给出答复时

以下每种情况均会回退至该调用的正则策略结果，并记录相应原因，`failproofai jev status` 会对各原因进行汇总：

| 原因 | 触发条件 |
| --- | --- |
| `timeout` | 在 `timeoutMs` 内未收到答复。 |
| `http-429` | 提供商对该密钥进行了频率限制。 |
| `rate-limited` | Failproof AI 自身的限速器在发送前拦截了请求：每秒最多 5 个请求，突发上限 5 个，提供商返回 `429` 后会短暂暂停。非提供商原因。 |
| `http-500`、`http-502`、`http-503`……| 提供商服务器错误。具体状态码会被记录。 |
| `out-of-credits` | HTTP 402：提供商账户余额不足。 |
| `provider-refused` | Cloudflare 返回 HTTP 402，内容为"Model execution failed (Payment error)"：提供商拒绝对该请求运行模型。通常与计费无关，充值不能解决此问题。 |
| `http-401`、`http-403` | 密钥被拒绝。 |
| `http-404` | `<base>/systemone` 路径下无内容，说明基础 URL 有误——系统会在基础 URL 后追加 `/systemone`，每个提供商均在其版本根路径下提供该接口。`failproofai jev models` 可查看端点实际提供的内容。 |
| `network` | 无法访问端点。 |
| `http-301`、`http-302`、`http-307`、`http-308` | 端点返回了重定向。重定向不会被跟随，因此答复只会来自配置中的 URL；请将 `--base-url` 设置为最终 URL。 |
| `malformed` | 端点有响应，但不是 Jev 格式的答复——响应体不是 JSON，或其中不包含任何答案。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflare 信封报告了失败，或任务尚未完成。 |
| `model-mismatch` | 响应的 Jev 版本不是 1.13，或 `custom` 端点未说明响应的模型。 |
| `request-cut` | **非服务中断。** Jev 已响应；但仅收到了部分调用内容，因此其答复未能清除任何拦截。详见[Jev 已响应但未处理完整调用时](#when-jev-answered-but-not-on-the-whole-call)。 |

`failproofai jev status` 还可能显示一些更少见的原因，例如 `upstream-error`（答复携带了提供商自身的错误）或 `config`，并将所有无法命名的原因归入 `other` 进行汇总。

`request-cut` 被列于此表，是因为 `failproofai jev status` 会将其与其他原因一并汇总，且它同样会使所有拒绝保持有效。但它是这里唯一一个与提供商状态无关的原因：请求已抵达，Jev 已响应。与上方所有情况不同，该答复仍然有效——Jev 自身的拒绝或警告会在正则策略结果之上叠加，而非被丢弃。因此，若此原因频繁出现，意味着调用内容过大，无法完整发送至评估器，而非端点存在问题，充值或更换 URL 都不会改变这一数字。

## Jev 已响应但未处理完整调用时

另有两种情况，均不属于 Jev 未能答复的情形，而是关于调用内容或对话内容能在单次请求中容纳多少。

**部分调用内容无法放入。** 工具调用在固定的预算内发送，过大的调用——非常大的 `Write`、巨大的 MCP 体、被填充至上限的命令——会以已放入的部分发送。Jev 仍会响应，其答复仍然有效：自身的拒绝或警告照常生效。但它无法**清除**任何内容，因为基于部分调用给出的判定不构成对整个调用的判定。因此，所有策略拒绝保持有效，该调用以回退方式记录，原因为 `request-cut`，`failproofai jev status` 会将其与上述原因一并汇总。由此得出的规则是：增大调用内容可能使其失去清除授权，但绝不能为其换来授权。

**某条消息无法放入。** 你粘贴的长提示词、智能体的最后一条消息，或已被该评估器自身存储截断的提示词。**一切不变**：调用的判定、清除和记录与其他任何调用完全相同，也不会被计入回退。你输入内容的长度永远不会决定判定结果，截断也不能制造同意：若提示词在抵达时已被截断，"你未曾请求此操作"就彻底失去了可以据此得出的前提，而不是变成另一个结论。

两者的区别在于文本的作者。调用是智能体的，允许其长度降低严重性就等于给了智能体可以利用的规则；提示词是你的，以其长度作为信号只会惩罚粘贴规格文档或堆栈跟踪的用户。

## 哪些内容会离开本机

对于 Jev 评估的每次工具调用，都会向你的提供商发送一个请求，其中包含：

- 工具调用本身，其中 API 密钥、Bearer Token 和 `KEY=` 赋值等密钥信息已被脱敏处理；
- 你最近输入的提示词，已移除智能体运行环境添加的文本；
- 你最新提示词之前智能体的最后一条消息，标注为智能体所写；
- 本地计算的事实信息，例如路径是否在项目目录内——即会话首次被审查的调用时所在的项目目录，[在会话期间固定](/zh/reference/jev-intent#the-project-root)——以及当前 git 分支。

请求仅发送至你配置的端点，使用你自己的密钥。

## 关闭 Jev

```bash
failproofai jev remove
```

此命令会删除 `~/.failproofai/jev.json`。从下一次工具调用起，钩子将完全按照之前的方式运行正则策略。`~/.failproofai/state/semantic/` 下的每会话存储（`sessions/` 中的已记录提示词、`roots/` 中的项目根目录）会保留原位，自然过期。若只是想停止询问 Jev 但保留配置，请改用 `failproofai jev setup --mode off`。

## 命令参考

| 命令 | 功能 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 一条命令完成配置；提供商由 URL 主机名推断 |
| `failproofai jev --url <url> --token <token>` | 同上，密钥在命令行中传入——会留存于历史记录和进程列表 |
| `failproofai jev setup --provider <kind> --key-stdin` | 从 stdin 管道读取密钥并写入配置 |
| `failproofai jev setup --provider <kind>` | 同上，在带掩码的提示符处输入密钥 |
| `failproofai jev setup --key-from-env` | 不存储密钥；每次会话从 `FAILPROOFAI_JEV_API_KEY` 读取 |
| `failproofai jev setup --mode observe` | 切换模式（`enforce`、`observe` 或 `off`），保留已存储的密钥 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 覆盖模型或 API 基础地址；`default` 清除覆盖 |
| `failproofai jev setup --timeout-ms <n>` | 更改每次调用的等待预算 |
| `failproofai jev status [--json]` | 显示配置、权限和近期活动；不显示密钥 |
| `failproofai jev test [--json]` | 发送一次实时请求：显示延迟和响应版本 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 列出该端点 `/models` 接口报告的模型 ID，并标注当前配置的模型 |
| `failproofai jev remove` | 删除配置；Jev 关闭 |
