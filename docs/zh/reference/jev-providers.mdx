本文是使用自备密钥的 [Jev 策略](/zh/policies/jev) 提供商与配置参考。正则策略匹配字符串，它无法区分你主动要求的 `rm -rf build/` 与不小心混入计划的 `rm -rf ~`，因此在某些地方拦截过多，在另一些地方又拦截不足。**Jev** 是 TypeSafe 的分类器，它会对照你实际提出的需求来分析调用内容，并在一次快速请求中回答一组是/否问题。

配置好自己的 Jev 端点和密钥后，Failproof AI 会针对每次工具调用**同时**咨询 Jev 和正则策略，而非以 Jev 替代后者：

- **硬性**策略的拒绝是最终决定。Jev 无法撤销它。除非策略被明确标记为可审查并列出其涵盖的 Jev 检查项，否则所有策略默认为硬性策略——即未作任何声明的自定义策略、策略包或 Cloud 策略均为硬性策略，且始终启用的自我保护守卫永远是硬性策略。
- **可审查**策略的拒绝可被撤销，但前提是：Jev 被明确询问了该策略所覆盖的具体问题，且回答为"此处无异常"或"用户已请求此操作"。若某项检查发现问题确实存在，且用户并未请求该调用，则拒绝保持不变——即使该检查本身的结论仅为警告也如此，因为在工具调用前，警告并不会阻止代理继续执行。而且，若该检查属于可直接拒绝的类型（密钥泄露、凭据外泄、破坏性删除等），则该调用不会被撤销任何拒绝。
- 当某次调用是你所布置任务的一个步骤，且影响范围不超出该步骤时，拦截仍可能降级为**警告**：Jev 会将自身的拒绝软化为警告，该警告——会明确指出调用的实际问题——将取代策略的拦截。
- Jev 也可以自主发出警告或拒绝，以应对正则无法描述的危害。
- 若 Jev 无法作答（超时、触发速率限制、服务器错误、额度耗尽、模型版本异常），该次调用将使用纯正则结果，与未配置 Jev 时完全一致。
- 除非 Jev 读取了完整调用内容并被询问了具体的关注点，否则 Jev 绝不会使调用比单纯依靠策略时更为宽松。任何不满足此条件的情况——调用内容过大无法完整发送、疑似注入攻击——都将撤销所有豁免并保留全部拒绝。

<Note>
若未配置 Jev，一切均不改变：hooks 将完全按原有方式运行正则策略。配置本身即是全部的选择加入。
</Note>

<Tip>
使用 FailproofAI Cloud？您无需自备密钥：持有 `jev:evaluate` 权限密钥的已连接机器可在您组织的计划中使用 Jev。请参阅 [通过 FailproofAI Cloud 使用 Jev](/zh/reference/jev-cloud)。
</Tip>

## 开始之前

在运行代理的机器上安装 **failproofai 1.0.8-beta.0 或更高版本**，并将其 hooks 附加到[受支持的运行环境](/zh/reference/harnesses)。若是新机器，请按照[快速入门](/zh/start/quickstart)操作；若不使用 Cloud，请参阅[设置本地执行](/zh/start/setup#enforce-locally)。使用 `failproofai --version` 检查已安装的 CLI 版本。

从下方选择一个提供商获取 API 密钥，或准备好兼容端点及其密钥。Jev 在 `PreToolUse` 或 `PermissionRequest` 关卡审查具名工具调用。它可以发出自己的判决，但撤销现有策略拒绝还需要安装一个标记为[可审查](/zh/policies/authority)的策略。硬性策略拒绝始终是最终决定。

## 选择提供商

Jev 可通过五条路径访问。为其中任意一条带上密钥即可。

| 提供商 | `--provider` | 端点 | 默认模型 | 备注 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 精确版本锁定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 请求仅路由至零数据留存端点，不回落至其他提供商。返回形如 `typesafe/jev-1.13-20260917` 的带日期版本号。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | 仅通过别名识别 Jev，因此响应版本将被记录为未验证。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | 需要 `--account-id`。实测单密钥约每秒六次调用前出现 HTTP 429。 |
| 自定义端点 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | 任何能接受 TypeSafe 请求体并报告响应模型的端点。仅支持 `https`；本地测试时可接受对回环地址（`localhost`、`127.0.0.1`、`::1`）使用明文 `http`。 |

<Warning>
使用 Vercel 的自带密钥功能时，失败的请求会被静默地用 Vercel 的凭据重试。如果您需要所有调用都计费到您自己的 TypeSafe 账户且仅由该账户可见，请直接使用 TypeSafe。
</Warning>

## 配置步骤

一条命令，指定端点和密钥。先以 `observe` 模式启动，以便在现有策略继续决定调用结果的同时检查 Jev 的判决：

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL 决定提供商

您无需手动指定提供商：URL 的**主机名**即决定了使用哪个提供商。

| URL 主机 | 提供商 | 还需要 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32位十六进制账户ID>` |
| 其他任何主机 | `custom` | — 您提供的 URL 即为基础 URL |

由此产生三点说明：

- **若 URL 是该提供商自己的 API，则不写入任何覆盖配置。** `--url https://api.typesafe.ai/v1` 产生的配置与 `--provider typesafe` 完全相同。若对已知提供商使用不同路径或主机名，则将其作为基础 URL 存储，效果与 `--base-url` 相同。
- **`--provider` 仍可覆盖自动推断结果**，这也是如何通过自己主机名上的代理访问某提供商 API 的方式：`--url https://jev-proxy.internal/v1 --provider typesafe`。
- **若 `--provider` 与主机名相矛盾，命令将被拒绝**，而非猜测处理。`--provider openrouter --url https://api.typesafe.ai/v1` 不会写入任何内容，并会说明原因：两者的指向不一致，关于密钥将发送至何处存在歧义。同样的情况在 `jev setup --base-url` 和控制面板的 Jev 设置中也会被拒绝。（`--provider custom` 不构成矛盾——它表示"按原样使用此 URL"——但 Cloudflare 主机除外，因为其按账户区分的端点无法通过自定义路由访问。）

`--url` 的验证规则与配置文件中 `baseUrl` 的验证规则完全相同，拒绝时给出相同的提示：支持 `https`，或在任何模式下对回环地址（`localhost`、`127.0.0.1`、`::1`）使用明文 `http`。风险提示：回环服务器无任何身份验证，因此当其关闭时，其他本地进程可能占用其端口并响应请求；在本地测试之外请使用 `https`。

### 密钥

通过 `--key-stdin` 以管道方式传入，或在终端中不带该参数运行命令并在掩码提示符处粘贴密钥。无论哪种方式，密钥都会直接写入配置文件，且不会被回显。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32位十六进制账户ID> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` 接受相同的参数，是完整的长命令形式：若您更倾向于指定提供商名称而非 URL，可使用 `setup --provider <kind>`。

### `--token` 及其代价

`--token <token>` 将密钥置于命令行中，这是配置机器最快的方式，也是唯一会将密钥留在配置文件之外的方式：

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
命令行参数执行后会留在 shell 的历史文件中，且命令运行期间会出现在进程列表中——以您的身份运行的任何程序均可通过 `/proc` 读取。每次使用 `--token` 时，`setup` 都会给出此提示。在共享机器、录制的会话中或历史文件会同步的任何场合，请优先使用 `--key-stdin`；若此密钥以此方式传入且涉及安全，请及时轮换。
</Warning>

`--token`、`--key-stdin` 和 `--key-from-env` 三者互斥，只能指定其一。

然后发送一个小型实时请求，验证密钥、端点以及响应的 Jev 版本：

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

当响应在超时后才到达（每个 hook 都将回落到正则，原因为 `timeout`）或检查问题答错时，`jev test` 以标题提示并以退出码 1 结束。

Hooks 在每次工具调用时读取配置，因此从下一次调用起立即生效，无需重启任何服务，无论是否使用守护进程。

## 查看运行状态

```bash
failproofai jev status
failproofai jev status --json
```

`status` 显示提供商、端点、模型、模式、配置文件及其权限信息，但不显示密钥。其下方汇总了近期活动：Jev 评估的调用次数、回落至正则的频次及原因、延迟情况，以及它撤销的可审查策略。

## 验证真实调用

在已挂载 hook 的代理中开启新会话，让其使用文件读取工具读取 `README.md` 并报告标题。确认会话中包含该工具调用后，再次运行 `failproofai jev status`：近期已评估调用数应有所增加。在[本地控制面板](/zh/reference/local-dashboard#review-policy-activity)的 **Policies → Activity** 中查看该调用的 Jev 判决和模式。在 observe 模式下，策略结果仍决定调用的最终走向。只有当可审查策略匹配且 Jev 清除了所有列出的检查项时，才会出现豁免；普通的读取操作可能不涉及任何需要清除的策略。

## 观察模式

`enforce` 是默认模式。若希望观察 Jev 而不让其改变任何决定，可切换至 `observe` 模式：Jev 仍会被询问并记录其判决，但实际执行依据的是正则结果。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` 模式保留配置（端点和密钥），但停止询问 Jev：hooks 完全按照无配置时的方式运行正则策略，`failproofai jev status` 显示"off (switched off)"。使用 `--mode observe` 或 `--mode enforce` 可切换回来。

对同一提供商重新运行 `setup` 会保留已存储的密钥，因此切换模式只需一个参数。切换提供商则需重新开始并提供该提供商的密钥。将请求迁移到不同主机的 `--base-url` 同样如此：已存储的密钥只会发送到最初设置时对应的主机或该提供商自己的 API。

## 配置文件

所有配置都存储在一个文件中：`~/.failproofai/jev.json`，由 `setup` 写入：

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 字段 | 说明 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare` 或 `custom`；或 `failproofai`（密钥来自 FailproofAI Cloud 连接而非此文件，详见 [通过 FailproofAI Cloud 使用 Jev](/zh/reference/jev-cloud)）。 |
| `apiKey` | 以 `Authorization: Bearer <key>` 形式发送。 |
| `baseUrl` | `custom` 必填；否则替换提供商的 API 基础地址。必须为 `https`。仅在 `mode: observe` 下接受对 `localhost` 使用明文 `http`：本地端口无任何身份验证，因此当您的代理关闭时，机器上的任何进程——包括被判断的代理本身——都可能占用该端口响应请求。 |
| `accountId` | 仅限 Cloudflare：32 位小写十六进制字符。 |
| `model` | 替换提供商的默认模型 ID。带版本号的 ID 必须指向 Jev 1.13。形如 API 密钥的值将被拒绝（且不会回显），因此误粘贴到 `--model` 的密钥不会被存储或作为模型名发送。 |
| `timeoutMs` | 工具调用等待 Jev 响应的时长，超时后使用正则结果。范围 100–10000，默认 3000。 |
| `mode` | `enforce`（默认）、`observe` 或 `off`（保留配置，不运行 Jev）。 |

三条规则保护该文件：

- **仅限所有者访问。** 文件以权限 `0600` 写入。任何其他用户或组可读写的副本将被**拒绝**，hooks 回落至正则，直到您运行 `chmod 600 ~/.failproofai/jev.json` 或重新运行 `setup`。目录也会被检查：`~/.failproofai` 不得被其他任何人**写入**，因为能写入该目录的人可以替换文件，无论文件本身的权限如何。`setup` 发现此类写入权限时会将其移除。`failproofai jev status` 会提示配置被拒绝，并显示文件中记录的端点：由于他人可能已修改该文件，在执行 `chmod` 前请确认文件内容确为您所设。对这类文件重新运行 `setup` 时，存储的密钥只会发送到该提供商自己的 API；文件中指向其他端点的配置需要重新提供密钥（`--key-stdin`），或使用 `--base-url default` 将请求恢复到该提供商。
- **仅限全局配置。** 代码仓库无法开启 Jev、将其指向其他端点或指定模型：项目内的 `.failproofai/jev.json` 将被忽略，提供商、URL、模型和账户 ID 只从上述文件读取——永不从环境变量读取（仓库的代理设置可以设置环境变量）。（`FAILPROOFAI_HOME` 不是绕过此限制的方法：它移动的是整个 failproofai 目录（包括您的策略），而非单独重定向 Jev。）
- **仅密钥可来自环境变量。** 若文件中无 `apiKey`，`FAILPROOFAI_JEV_API_KEY` 将为该会话提供密钥（`setup --key-from-env` 会写入此类文件）。它不会替换文件中已有的密钥，也无法在没有文件的情况下开启 Jev。若该变量未设置，Jev 在该 shell 中简单地处于关闭状态：`failproofai jev status` 会提示此情况，以退出码 0 退出，且不修改配置（`status --json` 报告 `"status": "key-missing"`，附带 `"reason": "no-env-key"`）。`failproofaid` 守护进程不读取您 shell 的环境变量，因此在使用 `failproofai config` 设置的机器上，请将密钥保存在文件中。

## 由哪个 Jev 响应

Failproof AI 的决策阈值基于 Jev 1.13 校准，因此只有来自该系列的响应才会被采用：`jev-1.13.x`，或 OpenRouter 的 `typesafe/jev-1.13-<date>`。当提供商仅以别名标识 Jev 且不报告版本时（Vercel，以及不说明版本的 Cloudflare），响应会被采用并记录为未验证。`custom` 端点必须报告响应的模型；唯一例外是您为其配置的未带版本号的 `--model` 名称——回显时同样记录为未验证。报告其他任何版本的响应，或 `custom` 端点未说明响应模型的情况，均不被采用：该次调用以原因 `model-mismatch` 回落至正则。

## Jev 无法响应时的处理

以下每种情况都会使该次调用回落至正则结果，并记录相应原因，`failproofai jev status` 会汇总这些数据：

| 原因 | 触发条件 |
| --- | --- |
| `timeout` | 在 `timeoutMs` 内未收到响应。 |
| `http-429` | 提供商对该密钥触发了速率限制。 |
| `rate-limited` | Failproof AI 自身的限速器在发送前拦截了该请求：每秒最多 5 个请求，突发最多 5 个，提供商返回 `429` 后短暂暂停。非提供商限制。 |
| `http-500`、`http-502`、`http-503`……  | 提供商服务器错误，记录具体状态码。 |
| `out-of-credits` | HTTP 402：提供商账户额度已耗尽。 |
| `provider-refused` | Cloudflare 返回的 HTTP 402，内容为"Model execution failed (Payment error)"：提供商拒绝在该请求上运行模型。通常与计费无关，充值不能解决此问题。 |
| `http-401`、`http-403` | 密钥被拒绝。 |
| `http-404` | `<base>/systemone` 路径无任何服务，说明基础 URL 有误——`/systemone` 会被追加到基础 URL 后，所有提供商都在其版本根路径下提供该端点。`failproofai jev models` 可查看该端点实际提供的内容。 |
| `network` | 无法访问端点。 |
| `http-301`、`http-302`、`http-307`、`http-308` | 端点返回了重定向。重定向永不被跟随，响应只能来自配置中的 URL；请将 `--base-url` 设置为最终目标 URL。 |
| `malformed` | 端点有响应，但内容不是 Jev 答案——响应体不是 JSON，或其中不含任何答案。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflare 的封装层报告了失败，或任务尚未完成。 |
| `model-mismatch` | 响应来自 1.13 以外的 Jev 版本，或 `custom` 端点未说明响应模型。 |
| `request-cut` | **并非服务中断。** Jev 已响应，但仅看到了部分调用内容，因此其答案不能撤销任何拒绝。详见[Jev 已响应但未看到完整调用时](#when-jev-answered-but-not-on-the-whole-call)。 |

`failproofai jev status` 还可能显示一些较少见的原因，例如 `upstream-error`（响应携带了提供商自身的错误）或 `config`，并将所有无法命名的原因汇总为 `other`。

`request-cut` 出现在此表中，是因为 `failproofai jev status` 将其与其他原因一同汇总，且它同样会保留所有拒绝。它是这里唯一一个与您的提供商无关的原因：请求已送达，Jev 也已响应。与上面所有行不同，该响应仍然有效——Jev 自身的拒绝或警告会叠加在正则结果之上，而非被丢弃。因此若该原因频繁出现，说明到达评估器的调用体积过大无法完整发送，而非端点异常，充值或更换 URL 都无济于事。

## Jev 已响应但未看到完整调用时

还有两种情况，它们并非 Jev 未能响应，而是关于调用本身或对话历史有多少内容被装入了一次请求。

**调用本身的部分内容未被纳入。** 工具调用在固定预算内发送，超大型调用——极大的 `Write`、巨型 MCP 请求体、填充至上限的命令——会以装入的部分内容发送。Jev 仍会响应，其响应仍然有效：自身的拒绝或警告照常生效。但它无法**撤销**任何拒绝，因为基于部分调用内容作出的判决不能代表对完整调用的判决。因此所有策略拒绝保持不变，该调用以原因 `request-cut` 记录为回落，`failproofai jev status` 会将其与上述原因一同汇总。由此得出一条规则：增大调用体积可能使其失去豁免，但永远无法换来豁免。

**某条消息未被纳入。** 您粘贴的长提示词、代理的最后一条消息，或此评估器自身存储已截断的提示词。**此情况不改变任何内容**：该调用照常被判断、被撤销拒绝并被记录，不计入回落。您的输入长度从不决定判决结果，截断也无法制造同意：当提示词到达时已被截断，"您未请求此操作"就不再是可以得出的结论，而是根本无从得出。

两者的区别在于谁写了这段文字。调用是代理写的，允许其长度降低严重性，等于给了代理可利用的规则；提示词是您写的，将其长度视为信号只会惩罚粘贴规格文档或堆栈跟踪的行为。

## 哪些内容会离开机器

对于 Jev 评估的每次工具调用，会向您的提供商发送一次请求，其中包含：

- 工具调用本身，其中 API 密钥、Bearer token 和 `KEY=` 赋值等敏感信息已脱敏；
- 您最近输入的提示词，其中代理运行环境添加的文本已被移除；
- 您最新提示词之前代理的最后一条消息，标注为代理所写；
- 本地计算的事实，例如路径是否在项目内——即会话首次被审查时所在的项目，[在整个会话期间固定](/zh/reference/jev-intent#the-project-root)——以及当前 git 分支。

请求仅发送至您配置的端点，使用您的密钥。

## 关闭 Jev

```bash
failproofai jev remove
```

此命令删除 `~/.failproofai/jev.json`。从下一次工具调用起，hooks 将完全按原有方式运行正则策略。`~/.failproofai/state/semantic/` 下的各会话存储（`sessions/` 中的记录提示词、`roots/` 中的项目根目录）将保留原位并自然过期。若希望停止询问 Jev 但保留配置，请改用 `failproofai jev setup --mode off`。

## 命令参考

| 命令 | 效果 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 一条命令完成配置；提供商由 URL 主机名决定 |
| `failproofai jev --url <url> --token <token>` | 同上，密钥在命令行中传入——shell 历史和进程列表可见 |
| `failproofai jev setup --provider <kind> --key-stdin` | 从 stdin 管道读取密钥并写入配置 |
| `failproofai jev setup --provider <kind>` | 同上，在掩码提示符处输入密钥 |
| `failproofai jev setup --key-from-env` | 不存储密钥；每次会话从 `FAILPROOFAI_JEV_API_KEY` 读取 |
| `failproofai jev setup --mode observe` | 切换模式（`enforce`、`observe` 或 `off`），保留已存储的密钥 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 覆盖模型或 API 基础地址；`default` 清除覆盖 |
| `failproofai jev setup --timeout-ms <n>` | 修改每次调用的超时预算 |
| `failproofai jev status [--json]` | 配置信息、权限及近期活动；不显示密钥 |
| `failproofai jev test [--json]` | 一次实时请求：延迟及响应版本 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 该端点 `/models` 报告的模型 ID，并标记当前配置的模型 |
| `failproofai jev remove` | 删除配置；关闭 Jev |
