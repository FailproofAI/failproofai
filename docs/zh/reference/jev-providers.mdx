本文是使用自有密钥配置 [Jev 策略](/zh/policies/jev)的提供商参考文档。正则策略匹配的是字符串，它无法区分你主动要求的 `rm -rf build/` 和混入计划中的 `rm -rf ~`，因此要么在某处拦截过多，要么在另一处放行过多。**Jev** 是 TypeSafe 的分类器，它将工具调用与你实际的请求内容对照阅读，并在一次快速请求中回答一系列是/否问题。

配置好自有 Jev 端点和密钥后，Failproof AI 会**同时**就每次工具调用询问 Jev 和正则策略，而非以 Jev 取代正则策略：

- **硬性**策略的拒绝是最终决定。Jev 无法解除它。除非策略明确标记为可审查并指定了覆盖该策略的 Jev 检查项，否则所有策略默认都是硬性的——因此未作任何说明的自定义策略、扩展包策略或 Cloud 策略都属于硬性策略，始终启用的自我保护防护也永远是硬性策略。
- **可审查**策略的拒绝可被解除，但前提是：Jev 被询问了该策略所关注的确切问题，且回答为"此处无异常"或"用户已明确请求此操作"。若某个检查项发现问题确实存在，且用户并未主动要求该调用，则拒绝依然维持——即便该检查项本身的判定仅为警告，因为在工具调用执行前，警告并不会阻止智能体。而当该检查项属于可以直接拒绝的类型（密钥暴露、凭据泄露、破坏性删除等）时，该调用的任何拒绝均不会被解除。
- 当调用是你所布置任务的一个步骤且不超出任务范围时，拦截仍可降级为**警告**：Jev 将自身的拒绝软化为警告，该警告——明确指出调用的具体问题——将替代策略的拦截。
- Jev 也可以自行发出警告或拒绝，以应对正则表达式无法描述的危害。
- 若 Jev 无法给出答案（超时、速率限制、服务器错误、无可用额度、模型版本异常），该调用将沿用正则规则的结果，与未配置 Jev 时完全一致。
- 除非 Jev 读取了完整的调用内容并被询问了确切的关注点，否则它绝不会使调用获得比单独依靠策略更宽松的许可。任何不满足条件的情况——调用内容过大无法完整发送、疑似注入攻击——都将撤回已授予的放行权限，维持所有拒绝决定。

<Note>
未配置 Jev 时，一切不变：hooks 将完全按照既有方式运行正则策略。配置文件本身就是选择加入的全部操作。
</Note>

<Tip>
使用 FailproofAI Cloud？你无需自备密钥：持有 `jev:evaluate` 权限密钥的机器可在组织的套餐下使用 Jev。详见 [通过 FailproofAI Cloud 使用 Jev](/zh/reference/jev-cloud)。
</Tip>

## 开始之前

在运行智能体的机器上安装 **failproofai 1.0.8-beta.0 或更新版本**，并将其 hooks 附加到[受支持的运行环境](/zh/reference/harnesses)。如果是新机器，请参考[快速上手](/zh/start/quickstart)；如果不使用 Cloud，请参考[配置本地执行](/zh/start/setup#enforce-locally)。使用 `failproofai --version` 检查已安装的 CLI 版本。

从下方的提供商处获取 API 密钥，或准备好兼容端点及其密钥。Jev 在 `PreToolUse` 或 `PermissionRequest` 检查点审查已命名的工具调用。它可以发出自己的判定，但解除现有策略拒绝还需要安装一条标记为[可审查](/zh/policies/authority)的策略。硬性策略的拒绝始终是最终决定。

## 选择提供商

Jev 可通过五条路径访问，为其中任意一条准备密钥即可。

| 提供商 | `--provider` | 端点 | 默认模型 | 备注 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 精确版本锁定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 请求仅路由到零数据保留端点，不回退到其他提供商。返回形如 `typesafe/jev-1.13-20260917` 的日期版本号。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | 仅通过别名标识 Jev，因此响应版本记录为未验证。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | 需要 `--account-id`。实测每个密钥约每秒六次调用后触发 HTTP 429。 |
| 自定义端点 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | 任何接受 TypeSafe 请求体并报告响应模型的端点。仅支持 `https`；本地测试时允许使用明文 `http` 连接回环地址（`localhost`、`127.0.0.1`、`::1`）。 |

<Warning>
使用 Vercel 自带的自有密钥功能时，失败的请求会静默地使用 Vercel 的凭据重试。如果你需要所有调用均计费到且仅对你自己的 TypeSafe 账户可见，请直接使用 TypeSafe。
</Warning>

## 配置步骤

一条命令，指定端点和密钥。先以 `observe` 模式启动，以便在现有策略继续决策调用的同时查看 Jev 的判定结果：

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL 决定提供商

你无需手动指定提供商：URL 的**主机名**即代表所用提供商。

| URL 主机名 | 提供商 | 额外参数 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| 其他主机名 | `custom` | — 你提供的 URL 即为 base URL |

由此产生三条规则：

- **若 URL 本身就是提供商官方 API，则不写入任何覆盖配置。** `--url https://api.typesafe.ai/v1` 与 `--provider typesafe` 产生完全相同的配置。若在已知提供商上指定了不同的路径或主机名，则将其作为 base URL 存储，效果等同于 `--base-url`。
- **`--provider` 仍可覆盖自动推断结果**，这正是通过自有主机名代理某提供商 API 的方式：`--url https://jev-proxy.internal/v1 --provider typesafe`。
- **若 `--provider` 与主机名矛盾，命令将被拒绝**，不会进行猜测。`--provider openrouter --url https://api.typesafe.ai/v1` 不会写入任何内容，并说明原因：两个参数对密钥发送目标的指定相互冲突。同样的冲突在 `jev setup --base-url` 和控制台的 Jev 设置中也会被拒绝。（`--provider custom` 不构成冲突——它表示"将此 URL 原样使用"——但在 Cloudflare 主机上除外，因为其按账户分配的端点无法通过 custom 路由访问。）

`--url` 的验证规则与配置文件中的 `baseUrl` 完全一致，拒绝时使用相同的提示语：要求使用 `https`，或在任意模式下使用明文 `http` 连接回环地址（`localhost`、`127.0.0.1`、`::1`）。风险提示：回环服务器无法进行身份验证，因此在其下线期间，另一本地进程可能占用其端口并响应请求；本地测试以外的场景请使用 `https`。

### 密钥

通过 `--key-stdin` 管道传入，或在终端中不带该参数运行命令，在遮掩输入提示处粘贴密钥。两种方式均会将密钥直接写入配置文件，且不会回显。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` 接受相同的参数，是完整的长格式命令：若你更倾向于指定提供商而非 URL，可使用 `setup --provider <kind>`。

### `--token` 及其代价

`--token <token>` 将密钥直接放在命令行上，这是配置机器最快的方式，也是唯一一种将密钥留存在配置文件之外的方式：

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
命令行参数执行后会留在 shell 的历史文件中，且命令运行期间会出现在进程列表里——任何以你的身份运行的程序都可以通过 `/proc` 读取它。每次使用 `--token` 时，`setup` 都会给出提示。在共享机器、录制会话或历史文件会同步的环境中，请优先使用 `--key-stdin`；若通过此方式传递了密钥且存在安全顾虑，请及时轮换密钥。
</Warning>

`--token`、`--key-stdin` 和 `--key-from-env` 三者互斥，只能选择其一。

随后发送一个小型实时请求，验证密钥、端点以及响应的 Jev 版本：

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

当响应在超时后才到达（所有 hook 都会回退到正则，原因为 `timeout`）或检查问题回答有误时，`jev test` 退出码为 1，并在标题中注明。

Hooks 在每次工具调用时都会重新读取配置，因此配置从下一次调用起立即生效。无论是否使用守护进程，都无需重启任何服务。

## 查看运行状态

```bash
failproofai jev status
failproofai jev status --json
```

`status` 显示提供商、端点、模型、模式、配置文件及其权限，但不会显示密钥。下方还会汇总近期活动：Jev 评估的调用数量、回退到正则的频率及原因、延迟，以及 Jev 解除拦截的可审查策略列表。

## 验证实际调用

在已附加 hook 的智能体中开启新会话。让它使用文件读取工具读取 `README.md` 并报告标题。确认会话中包含该工具调用后，再次运行 `failproofai jev status`：近期已评估调用数应有所增加。在[本地控制台](/zh/reference/local-dashboard#review-policy-activity)的 **Policies → Activity** 中查看该调用的 Jev 判定结果和模式。在 observe 模式下，策略结果仍决定最终处理方式。仅当可审查策略匹配且 Jev 通过了所有指定检查时，才会出现放行记录；普通的读取操作可能没有需要解除的策略。

## 观察模式

`enforce` 是默认模式。若想在不改变任何决策的情况下观察 Jev 的运行，切换到 `observe` 模式：Jev 仍会被调用且其判定会被记录，但最终执行的是正则规则的结果。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` 模式保留配置（端点和密钥），停止向 Jev 发起请求：hooks 将完全按照无配置时的方式运行正则策略，`failproofai jev status` 会显示"off (switched off)"。使用 `--mode observe` 或 `--mode enforce` 可切换回来。

对同一提供商重新运行 `setup` 会保留已存储的密钥，因此切换模式只需一个参数。切换提供商则需重新开始，并输入新提供商的密钥。将 `--base-url` 更改为其他主机也同样如此：已存储的密钥仅发送到其最初配置时的主机，或该提供商的官方 API。

## 配置文件

所有配置都存储在一个文件中：由 `setup` 写入的 `~/.failproofai/jev.json`：

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 字段 | 含义 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare` 或 `custom`——也可以是 `failproofai`，其密钥来自 FailproofAI Cloud 连接而非本文件（详见[通过 FailproofAI Cloud 使用 Jev](/zh/reference/jev-cloud)）。 |
| `apiKey` | 以 `Authorization: Bearer <key>` 方式发送。 |
| `baseUrl` | `custom` 类型必填；若指定，则替换提供商的 API 基础地址。必须使用 `https`。仅在 `mode: observe` 下接受到 `localhost` 的明文 `http`：本地端口无法进行身份验证，因此代理下线时，机器上的任何进程（包括被审查的智能体本身）都可能占用其端口响应请求。 |
| `accountId` | 仅限 Cloudflare：32 位小写十六进制字符。 |
| `model` | 替换提供商的默认模型 ID。版本化 ID 必须指定 Jev 1.13。形如 API 密钥的值将被拒绝（且不会回显），因此误将密钥粘贴到 `--model` 中不会被存储或作为模型名称发送。 |
| `timeoutMs` | 工具调用等待 Jev 响应的超时时间，超时后使用正则规则结果。范围 100–10000，默认 3000。 |
| `mode` | `enforce`（默认）、`observe` 或 `off`（保留配置，不运行 Jev）。 |

三条规则保护此文件：

- **仅限所有者访问。** 文件权限设置为 `0600`。若其他用户或组可读可写，该文件将被**拒绝**，hooks 回退到正则规则，直到你运行 `chmod 600 ~/.failproofai/jev.json` 或重新运行 `setup`。目录也会被检查：`~/.failproofai` 不得被其他任何人**写入**，因为有写权限的人可以替换文件，无论文件本身的权限如何。`setup` 在发现写入权限时会将其移除。`failproofai jev status` 会提示配置被拒绝，并显示文件中记录的端点：由于他人可能修改过该文件，请在执行 `chmod` 前确认文件内容属于你。对权限异常的文件重新运行 `setup` 时，已存储的密钥仅用于提供商官方 API；文件中指定的其他端点需要重新提供密钥（`--key-stdin`），或使用 `--base-url default` 将请求重定向回提供商。
- **仅限全局配置。** 仓库无法开启 Jev、指向其他端点或选择模型：项目内的 `.failproofai/jev.json` 文件会被忽略，提供商、URL、模型和账户 ID 只从上述文件读取——永不从环境变量读取（环境变量可由仓库的智能体配置设置）。（`FAILPROOFAI_HOME` 不能绕过此限制：它移动的是整个 failproofai 目录，包括你的策略，而不是单独重定向 Jev。）
- **仅密钥可从环境变量获取。** 若文件中没有 `apiKey`，`FAILPROOFAI_JEV_API_KEY` 将在当前会话中提供密钥（`setup --key-from-env` 会写入此类文件）。它不会替换文件中已有的密钥，也无法在没有配置文件的情况下开启 Jev。若环境变量未设置，Jev 在该 shell 中仅为关闭状态：`failproofai jev status` 会给出提示，以退出码 0 退出，不修改配置（`status --json` 返回 `"status": "key-missing"` 及 `"reason": "no-env-key"`）。`failproofaid` 守护进程无法访问 shell 的环境变量，因此在通过 `failproofai config` 配置的机器上，请将密钥保存在文件中。

## 响应的 Jev 版本

Failproof AI 的决策阈值是基于 Jev 1.13 校准的，因此只接受来自该版本系列的答案：`jev-1.13.x` 或 OpenRouter 的 `typesafe/jev-1.13-<date>`。若提供商仅通过别名标识 Jev 且不报告版本（如 Vercel，以及未声明版本的 Cloudflare），该答案仍被接受，但记录为未验证。`custom` 端点必须报告响应模型；唯一例外是你为其配置的未版本化 `--model` 名称，原样回显时同样记录为未验证。报告其他版本的答案，或未报告版本的 `custom` 答案，将不被采用：该调用回退到正则规则，原因为 `model-mismatch`。

## Jev 无法给出答案时

以下每种情况都会为该调用回退到正则规则结果，并以对应原因记录，`failproofai jev status` 会汇总各原因的次数：

| 原因 | 触发条件 |
| --- | --- |
| `timeout` | 在 `timeoutMs` 内未收到响应。 |
| `http-429` | 提供商对该密钥进行了速率限制。 |
| `rate-limited` | Failproof AI 自身的限速器在发送前拦截了该调用：每秒最多 5 个请求，突发上限为 5 个，提供商返回 `429` 后会短暂暂停发送。不是提供商的限制。 |
| `http-500`、`http-502`、`http-503` 等 | 提供商侧的服务器错误，具体状态码会被记录。 |
| `out-of-credits` | HTTP 402：提供商账户已无可用额度。 |
| `provider-refused` | Cloudflare 返回 HTTP 402 并显示"Model execution failed (Payment error)"：提供商拒绝对该请求运行模型。通常与计费无关，充值不能解决此问题。 |
| `http-401`、`http-403` | 密钥被拒绝。 |
| `http-404` | `<base>/systemone` 路径下无内容，说明 base URL 有误——系统会将 `/systemone` 拼接到其后，每个提供商都在版本根路径下提供该端点。`failproofai jev models` 可查看端点实际提供的内容。 |
| `network` | 无法连接到端点。 |
| `http-301`、`http-302`、`http-307`、`http-308` | 端点返回了重定向。重定向不会被跟随，因此答案只能来自配置文件中的 URL；请通过 `--base-url` 设置最终 URL。 |
| `malformed` | 端点有响应，但内容不是 Jev 答案——响应体不是 JSON，或其中没有答案字段。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflare 信封报告了失败，或任务尚未完成。 |
| `model-mismatch` | 响应来自 1.13 以外的 Jev 版本，或 `custom` 端点未说明响应模型。 |
| `request-cut` | **不是服务中断。** Jev 已响应，但只看到了部分调用内容，因此其答案未解除任何拦截。详见[Jev 已响应但未读取完整调用内容](#when-jev-answered-but-not-on-the-whole-call)。 |

`failproofai jev status` 还可能显示一些更罕见的原因，例如 `upstream-error`（答案中携带了提供商自身的错误）或 `config`，以及将所有无法命名的原因汇总为 `other`。

`request-cut` 列于此表中，是因为 `failproofai jev status` 会将其与其他原因一并统计，且该情况同样会维持所有拒绝决定。但它是这里唯一一个与提供商状态无关的原因：请求已到达评估器，Jev 也已给出响应。与上方所有情况不同，该答案仍然有效——Jev 自身的拒绝或警告会在正则规则结果之上叠加应用，而不是被丢弃。因此，若此类情况频繁出现，意味着调用内容过大无法完整发送，而非端点异常，充值或更换 URL 都无法解决此问题。

## Jev 已响应但未读取完整调用内容

还有两种情况，它们都不是 Jev 未能响应的问题，而是关于调用内容或对话内容有多少能够放入一次请求。

**部分调用内容未能放入。** 工具调用在固定预算内发送，对于超出预算的调用——非常大的 `Write`、体量庞大的 MCP 请求体、填充到上限的命令——会发送能放入的部分。Jev 仍会响应，其答案仍然有效：自身的拒绝或警告会照常应用。但它**无法解除**任何拦截，因为基于部分调用内容给出的判定不能代表整个调用的判定。因此所有策略拒绝维持不变，该调用记录为回退，原因为 `request-cut`，`failproofai jev status` 会将其与上述原因一同统计。这条规则给你的启示是：增大调用内容可能使其失去放行资格，但绝不会换来放行资格。

**某条消息未能放入。** 你粘贴的长提示、智能体的最后一条消息，或已被此评估器自身存储截断的提示。**一切不变**：该调用的判定、放行和记录与其他任何调用完全相同，也不计为回退。你输入内容的长度永远不会左右判定结果，截断也无法凭空制造许可：当提示在到达时已被截断，"你没有请求此操作"就不再是一个可以得出的结论，而非变成一个相反的结论。

两者的分界在于是谁写的内容。调用是智能体写的，若允许其长度降低严重性，就等于给了智能体一条可利用的规则；提示是你写的，将其长度视为信号，只会惩罚粘贴规格文档或调用栈。

## 哪些数据会离开本机

对于 Jev 评估的每次工具调用，系统会向你的提供商发送一个请求，其中包含：

- 工具调用本身，其中 API 密钥、Bearer token 和 `KEY=` 赋值等密钥信息已脱敏处理；
- 你最近输入的提示，已移除智能体运行环境添加的文本；
- 在你最新提示之前智能体的最后一条消息，标注为智能体所写；
- 本地计算得出的信息，例如路径是否在项目目录内——即会话首次被审查调用时所在的目录，[在会话期间固定不变](/zh/reference/jev-intent#the-project-root)——以及当前 git 分支。

请求仅发送至你配置文件中指定的端点，使用你自己的密钥。

## 关闭 Jev

```bash
failproofai jev remove
```

此命令删除 `~/.failproofai/jev.json`。从下一次工具调用起，hooks 将完全按照之前的方式运行正则策略。`~/.failproofai/state/semantic/` 下的会话级存储（`sessions/` 中的已记录提示、`roots/` 中的项目根目录）会被保留并自然过期。若只想停止询问 Jev 但保留配置，请改用 `failproofai jev setup --mode off`。

## 命令参考

| 命令 | 功能 |

| `failproofai jev --url <url> --key-stdin` | 一条命令完成配置；提供商从 URL 主机名推断 |
| `failproofai jev --url <url> --token <token>` | 同上，密钥在命令行中明文传入——shell 历史和进程列表均可见 |

| `failproofai jev setup --key-from-env` | 不存储密钥；每次会话从 `FAILPROOFAI_JEV_API_KEY` 读取 |
| `failproofai jev setup --mode observe` | 切换模式（`enforce`、`observe` 或 `off`），保留已存储的密钥 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 覆盖模型或 API 基础地址；`default` 清除覆盖 |
| `failproofai jev setup --timeout-ms <n>` | 修改每次调用的超时预算 |
| `failproofai jev status [--json]` | 显示配置、权限和近期活动；不显示密钥 |
| `failproofai jev test [--json]` | 发送一次实时请求：显示延迟和响应版本 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 列出该端点 `/models` 报告的模型 ID，并标注当前配置的模型 |
| `failproofai jev remove` | 删除配置；Jev 关闭 |
