本文是使用自带密钥配置 [Jev 策略](/zh/policies/jev) 的提供商与配置参考。正则策略匹配字符串，它无法区分你主动要求的 `rm -rf build/` 与意外混入计划的 `rm -rf ~`，因此在某些地方拦截过度，在另一些地方又遗漏不足。**Jev** 是 TypeSafe 的分类器，它根据你的实际需求来解读调用，并在一次快速请求中回答一系列是/否问题。

配置好自己的 Jev 端点和密钥后，Failproof AI 会**同时**向 Jev 询问每个工具调用，而不是用 Jev 替代正则策略：

- **硬性**策略的拒绝是最终决定。Jev 无法解除它。除非策略明确标记为可审查并指定了覆盖该策略的 Jev 检查项，否则所有策略默认为硬性策略——因此未作任何说明的自定义策略、扩展包策略或 Cloud 策略均为硬性，且始终开启的自我保护防护也始终是硬性的。
- **可审查**策略的拒绝可以被解除，但前提是：Jev 被询问了该策略所关注的确切问题，且回答了"此处无异常"或"用户已请求此操作"。若某项检查发现问题确实存在，且用户未请求该调用，则拒绝保持有效——即便该检查本身的判定仅为警告，因为在工具调用之前，警告并不会阻止智能体。而当该检查属于可以拒绝的类型（密钥泄露、凭据窃取、破坏性删除等），该调用上的任何解除均不会生效。
- 当某次调用是你所分配任务的一个步骤且影响范围未超出任务时，拦截仍可降级为**警告**：Jev 会将自身的拒绝软化为警告，该警告——指出调用的实际问题所在——将取代策略的拦截。
- Jev 也可以自主发出警告或拒绝，以应对正则无法描述的危害。
- 若 Jev 无法作答（超时、速率限制、服务器错误、额度耗尽、模型版本异常），该调用将沿用正则结果，与不使用 Jev 时完全相同。
- 除非 Jev 读取了完整调用内容并被询问了确切的关注点，否则 Jev 绝不会让调用比单独使用你的策略时更宽松。任何不满足条件的情况——调用内容过大无法完整发送、疑似注入攻击——都会撤销解除授权并保持所有拒绝。

<Note>
未配置 Jev 时不会有任何变化：钩子将完全按照原有方式运行正则策略。配置文件本身就是完整的选择加入机制。
</Note>

<Tip>
使用 FailproofAI Cloud？你无需自备密钥：携带 `jev:evaluate` 权限的机器密钥可在你组织的套餐下使用 Jev。详见 [通过 FailproofAI Cloud 使用 Jev](/zh/reference/jev-cloud)。
</Tip>

## 开始之前

在运行智能体的机器上安装 **failproofai 1.0.8-beta.0 或更高版本**，并将其钩子附加到[受支持的运行环境](/zh/reference/harnesses)。如果是新机器，请参阅[快速入门](/zh/start/quickstart)；如果不使用 Cloud，请参阅[配置本地执行](/zh/start/setup#enforce-locally)。使用 `failproofai --version` 检查已安装的 CLI 版本。

从下方的提供商获取 API 密钥，或准备好兼容端点及其密钥。Jev 在 `PreToolUse` 或 `PermissionRequest` 门控处审查具名工具调用。它可以发出自己的判定，但解除现有策略拒绝还需要安装标记为[可审查](/zh/policies/authority)的策略。硬性策略拒绝始终是最终决定。

## 选择提供商

Jev 可通过五种途径访问，为其中任意一种提供密钥即可。

| 提供商 | `--provider` | 端点 | 默认模型 | 备注 |
| --- | --- | --- | --- | --- |
| TypeSafe | `typesafe` | `api.typesafe.ai/v1/systemone` | `jev-1.13.0` | 精确版本固定。 |
| OpenRouter | `openrouter` | `openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` | 请求仅路由至零数据保留端点，不回退到其他提供商。报告带日期的版本，如 `typesafe/jev-1.13-20260917`。 |
| Vercel AI Gateway | `vercel` | `ai-gateway.vercel.sh/typesafe/v1/systemone` | `typesafe-ai/jev` | 仅通过别名标识 Jev，因此实际响应版本记录为未验证。 |
| Cloudflare Workers AI | `cloudflare` | `api.cloudflare.com/client/v4/accounts/<id>/ai/run` | `typesafe/jev` | 需要 `--account-id`。实测每个密钥约每秒六次调用后触发 HTTP 429。 |
| 自定义端点 | `custom` | `<base-url>/systemone` | `jev-1.13.0` | 任何接受 TypeSafe 请求体并报告响应模型的端点。仅支持 `https`；本地测试时允许通过明文 `http` 连接回环地址（`localhost`、`127.0.0.1`、`::1`）。 |

<Warning>
使用 Vercel 自带密钥功能时，失败的请求会静默地使用 Vercel 的凭据重试。如果你需要所有调用均计费至且仅对你自己的 TypeSafe 账户可见，请直接使用 TypeSafe。
</Warning>

## 配置步骤

一条命令，指定端点和密钥。先以 `observe` 模式启动，以便在现有策略继续决定调用的同时检查 Jev 的判定：

```bash
failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
```

### URL 决定提供商

你无需手动指定提供商：URL 的**主机名**就决定了使用哪个提供商。

| URL 主机名 | 提供商 | 额外参数 |
| --- | --- | --- |
| `api.typesafe.ai` | `typesafe` | — |
| `openrouter.ai` | `openrouter` | — |
| `ai-gateway.vercel.sh` | `vercel` | — |
| `api.cloudflare.com` | `cloudflare` | `--account-id <32-hex-account-id>` |
| 其他任意主机名 | `custom` | — 你提供的 URL 即为 base URL |

由此产生三条规则：

- **使用提供商官方 API 的 URL 不会写入覆盖配置。** `--url https://api.typesafe.ai/v1` 生成的配置与 `--provider typesafe` 完全相同。在已知提供商上指定不同路径或主机名，会将其作为 base URL 存储，效果等同于 `--base-url`。
- **`--provider` 仍然会覆盖自动推断**，这正是通过自己主机名上的代理访问某提供商 API 的方式：`--url https://jev-proxy.internal/v1 --provider typesafe`。
- **与主机名相矛盾的 `--provider` 会被拒绝**，而非猜测处理。`--provider openrouter --url https://api.typesafe.ai/v1` 不会写入任何内容，并会说明原因：两个参数对密钥发送目标的指定相互矛盾。同样的组合在 `jev setup --base-url` 和控制台的 Jev 设置中也会被拒绝。（`--provider custom` 不构成矛盾——它表示"将此 URL 视为其本身"——但 Cloudflare 主机名除外，其按账户区分的端点无法通过 custom 路由访问。）

`--url` 的验证规则与配置文件中 `baseUrl` 的验证完全一致，拒绝时措辞也相同：必须是 `https`，或在任意模式下明文 `http` 连接回环地址（`localhost`、`127.0.0.1`、`::1`）。风险提示：回环服务器无任何身份验证，因此在其停机期间，本地其他进程可能占用其端口并响应请求；本地测试以外请使用 `https`。

### 密钥

通过 `--key-stdin` 管道传入，或在终端中不带该参数运行命令，在遮蔽的提示符处粘贴密钥。两种方式均会将密钥直接写入配置文件，且不会回显。

<Tabs>
  <Tab title="TypeSafe">
    ```bash
    failproofai jev --url https://api.typesafe.ai/v1 --mode observe --key-stdin < ~/typesafe.key
    ```
  </Tab>
  <Tab title="OpenRouter">
    ```bash
    failproofai jev --url https://openrouter.ai/api/v1 --mode observe --key-stdin < ~/openrouter.key
    ```
  </Tab>
  <Tab title="Vercel">
    ```bash
    failproofai jev --url https://ai-gateway.vercel.sh/typesafe/v1 --mode observe \
      --key-stdin < ~/vercel-gateway.key
    ```
  </Tab>
  <Tab title="Cloudflare">
    ```bash
    failproofai jev --url https://api.cloudflare.com/client/v4 \
      --account-id <32-hex-account-id> --mode observe --key-stdin < ~/cloudflare.token
    ```
  </Tab>
  <Tab title="Custom">
    ```bash
    failproofai jev --url https://jev.internal.example.com/v1 --mode observe --key-stdin < ~/jev.key
    ```
  </Tab>
</Tabs>

`failproofai jev setup` 接受相同的参数，是完整的长格式命令：在你更倾向于指定提供商而非 URL 时，使用 `setup --provider <kind>`。

### `--token` 及其代价

`--token <token>` 将密钥放在命令行上，这是配置机器最快的方式，也是唯一会将密钥留存在配置文件以外位置的方式：

```bash
failproofai jev --url https://openrouter.ai/api/v1 --token <token>
```

<Warning>
命令行参数执行后会留在你的 shell 历史文件中，且命令运行期间会出现在进程列表中——任何以你的身份运行的进程均可从 `/proc` 读取。每次使用 `--token` 时，`setup` 都会给出提示。在共享机器上、在录屏会话中、或历史文件会被同步的任何场景下，请优先使用 `--key-stdin`；如果以这种方式传递过密钥且有安全顾虑，请及时轮换。
</Warning>

`--token`、`--key-stdin` 和 `--key-from-env` 三者互斥：只能选其一。

然后发送一个小型实时请求，验证密钥、端点以及响应的 Jev 版本：

```bash
failproofai jev test
```

```text
  failproofai jev test                                            ok · 523 ms

  provider      cloudflare
  model asked   typesafe/jev
  answered by   jev-1.13.0 (Jev 1.13 family — verified)
  latency       523 ms — within the 3000 ms timeout
```

当响应在超时后才到达（所有钩子均会回退到正则，原因为 `timeout`）或检查问题回答有误时，`jev test` 退出码为 1，并在标题中注明。

钩子在每次工具调用时读取配置，因此从下一次工具调用起立即生效。无论是否使用守护进程，都无需重启任何服务。

## 查看运行状态

```bash
failproofai jev status
failproofai jev status --json
```

`status` 显示提供商、端点、模型、模式、配置文件及其权限，但不显示密钥。其下方还汇总近期活动：Jev 评估的调用次数、回退到正则的频率及原因、延迟，以及它解除了哪些可审查策略。

## 验证实际调用

在已挂载钩子的智能体中启动新会话。要求它使用文件读取工具读取 `README.md` 并报告标题。确认会话中包含该工具调用后，再次运行 `failproofai jev status`：近期已评估调用数应有所增加。在[本地控制台](/zh/reference/local-dashboard#review-policy-activity)的**策略 → 活动**中查看该调用的 Jev 判定和模式。在 observe 模式下，策略结果仍然决定调用结果。只有在可审查策略匹配且 Jev 通过了所有指定检查项时，才会出现解除记录；普通的读取操作可能没有任何策略需要解除。

## 观察模式

`enforce` 是默认模式。若要在不影响任何决定的情况下观察 Jev，可切换到 `observe` 模式：Jev 仍会被询问且其判定会被记录，但实际执行的是正则结果。

```bash
failproofai jev setup --mode observe
failproofai jev setup --mode enforce
failproofai jev setup --mode off
```

`off` 保留配置（端点和密钥），但停止向 Jev 发起请求：钩子完全按照无配置时的方式运行正则策略，`failproofai jev status` 显示"off (switched off)"。使用 `--mode observe` 或 `--mode enforce` 可重新启用。

对同一提供商重新运行 `setup` 会保留已存储的密钥，因此切换模式只需一个参数。切换提供商则需重新开始并提供新提供商的密钥。将请求迁移到不同主机的 `--base-url` 也同样如此：已存储的密钥仅发送至最初配置时的主机，或该提供商的官方 API。

## 配置文件

所有内容存储在一个文件中：由 `setup` 写入的 `~/.failproofai/jev.json`：

```json
{
  "provider": "cloudflare",
  "apiKey": "<your key>",
  "accountId": "<32-hex-account-id>",
  "mode": "enforce",
  "timeoutMs": 3000
}
```

| 字段 | 含义 |
| --- | --- |
| `provider` | `typesafe`、`openrouter`、`vercel`、`cloudflare` 或 `custom`——或 `failproofai`，其密钥来自 FailproofAI Cloud 连接而非本文件（详见[通过 FailproofAI Cloud 使用 Jev](/zh/reference/jev-cloud)）。 |
| `apiKey` | 以 `Authorization: Bearer <key>` 形式发送。 |
| `baseUrl` | `custom` 时必填；否则替换提供商的 API base。必须为 `https`。明文 `http` 连接 `localhost` 仅在 `mode: observe` 时接受：本地端口无任何身份验证，代理停机时，机器上的任何进程（包括被审查的智能体本身）均可冒充响应。 |
| `accountId` | 仅 Cloudflare 需要：32 位小写十六进制字符。 |
| `model` | 替换提供商的默认模型 ID。带版本号的 ID 必须指向 Jev 1.13。形如 API 密钥的值会被拒绝（且不会回显），因此误填到 `--model` 的密钥不会被存储或作为模型名发送。 |
| `timeoutMs` | 工具调用等待 Jev 响应的超时时间，超时后使用正则结果。范围 100–10000，默认 3000。 |
| `mode` | `enforce`（默认）、`observe` 或 `off`（保留配置，不运行 Jev）。 |

三条规则保护该文件：

- **仅限所有者访问。** 文件以 `0600` 权限写入。任何其他用户或组可读或可写的副本将被**拒绝**，钩子回退到正则，直到你运行 `chmod 600 ~/.failproofai/jev.json` 或重新运行 `setup`。目录也会被检查：`~/.failproofai` 不得被其他任何人**写入**，因为有写入权限的人可以替换文件，无论文件本身的权限如何。`setup` 发现写入位时会将其移除。`failproofai jev status` 会在配置被拒绝时给出提示，并显示文件中指定的端点：他人可能已修改过该文件，因此在执行 `chmod` 之前请确认文件内容属于你。对这类文件重新运行 `setup` 时，已存储的密钥仅传送至提供商官方 API；文件中指定的任何其他端点需要重新提供密钥（`--key-stdin`），或使用 `--base-url default` 将请求恢复发往提供商。
- **仅限全局配置。** 仓库无法开启 Jev、将其指向其他端点或选择模型：项目内的 `.failproofai/jev.json` 会被忽略，提供商、URL、模型和账户 ID 仅从上述文件读取——永远不从环境变量读取（环境变量可由仓库的智能体设置来设定）。（`FAILPROOFAI_HOME` 也不是绕过此限制的途径：它会移动整个 failproofai 目录，包括你的策略，而不是单独重定向 Jev。）
- **仅密钥可从环境变量获取。** 若文件中没有 `apiKey`，`FAILPROOFAI_JEV_API_KEY` 在该会话中提供密钥（`setup --key-from-env` 会写入这样的文件）。它不会替换文件中已有的密钥，也无法在没有配置文件的情况下单独启用 Jev。若该变量未设置，Jev 在该 shell 中仅为关闭状态：`failproofai jev status` 会给出提示，退出码为 0，不修改配置（`status --json` 以 `"status": "key-missing"` 和 `"reason": "no-env-key"` 报告）。`failproofaid` 守护进程无法访问你的 shell 环境，因此在使用 `failproofai config` 配置的机器上，请将密钥保存在文件中。

## Jev 响应版本

Failproof AI 的决策阈值基于 Jev 1.13 进行校准，因此只有来自该系列的答案才会被采用：`jev-1.13.x`，或 OpenRouter 的 `typesafe/jev-1.13-<date>`。若提供商仅通过别名标识 Jev 且不报告版本（Vercel，以及 Cloudflare 未声明版本时），该答案会被采用并记录为未验证。`custom` 端点必须报告响应的模型；唯一例外是你为其配置的无版本号 `--model` 名称，在回显时同样记录为未验证。报告其他版本的答案，或未报告模型的 `custom` 答案，均不会被采用：该调用回退到正则，原因为 `model-mismatch`。

## Jev 无法作答时

以下每种情况均会回退到该调用的正则结果，并以对应原因记录，`failproofai jev status` 会汇总各原因：

| 原因 | 触发条件 |
| --- | --- |
| `timeout` | 在 `timeoutMs` 内未收到响应。 |
| `http-429` | 提供商对该密钥进行了速率限制。 |
| `rate-limited` | Failproof AI 自身的限流器在发送前阻止了该调用：每秒最多 5 个请求，突发上限为 5，提供商返回 `429` 后会短暂停止发送。非提供商侧原因。 |
| `http-500`、`http-502`、`http-503` 等 | 提供商侧服务器错误，记录具体状态码。 |
| `out-of-credits` | HTTP 402：提供商账户额度已耗尽。 |
| `provider-refused` | Cloudflare 返回的 HTTP 402，提示"Model execution failed (Payment error)"：提供商拒绝在此请求上运行模型。通常与计费无关，充值不会解决此问题。 |
| `http-401`、`http-403` | 密钥被拒绝。 |
| `http-404` | `<base>/systemone` 路径无响应，说明 base URL 有误——系统会在其后追加 `/systemone`，每个提供商均在其版本根路径下提供该端点。`failproofai jev models` 可显示该端点实际提供的内容。 |
| `network` | 无法访问端点。 |
| `http-301`、`http-302`、`http-307`、`http-308` | 端点返回了重定向。重定向永远不会被跟随，因此响应只来自你配置中的 URL；请将 `--base-url` 设置为最终 URL。 |
| `malformed` | 端点有响应，但不是 Jev 格式的答案——响应体非 JSON，或其中不含答案。 |
| `cloudflare-error`、`cloudflare-incomplete` | Cloudflare 信封报告了失败，或任务尚未完成。 |
| `model-mismatch` | 响应的 Jev 版本不是 1.13，或 `custom` 端点未说明响应的模型。 |
| `request-cut` | **非服务中断。** Jev 已作答，但只看到了部分调用内容，因此其答案未解除任何拒绝。详见[Jev 已作答但非基于完整调用](#when-jev-answered-but-not-on-the-whole-call)。 |

`failproofai jev status` 还可能显示一些更罕见的原因，例如 `upstream-error`（答案中携带了提供商自身的错误）或 `config`，并将所有无法命名的原因汇总为 `other`。

`request-cut` 列于此表，是因为 `failproofai jev status` 会将其与其他原因一并汇总，且它同样会保留所有拒绝。这是此处唯一与提供商状态无关的原因：请求已到达，Jev 也已作答。与上方所有条目不同，该答案仍然有效——Jev 自身的拒绝或警告会叠加在正则结果之上，而非被丢弃。因此，若该计数持续增加，说明到达评估器的调用过大无法完整发送，而非端点异常，充值或更换 URL 对此无济于事。

## Jev 已作答但非基于完整调用

还有两种情况，且都不是 Jev 作答失败，而是关于调用本身或对话内容在单次请求中能容纳多少。

**部分调用内容未能放入。** 工具调用在固定预算内发送，过大的调用——非常大的 `Write`、巨大的 MCP 体、被填充到上限的命令——会在发送时只包含能容纳的部分。Jev 仍然作答，其答案仍然有效：它自身的拒绝或警告照常生效。但它无法**解除**任何内容，因为基于部分调用的判定不能算作对整个调用的判定。因此所有策略拒绝保持有效，该调用以 `request-cut` 原因记录为回退，`failproofai jev status` 会将其与上述原因一并汇总。由此得出一条规则：让调用变得更大可能导致其失去解除资格，却永远无法获得解除资格。

**某条消息未能放入。** 你粘贴的长提示词、智能体的最后一条消息，或已被该评估器自身存储截断的提示词。**不会有任何变化**：该调用的判定、解除和记录与其他调用完全相同，也不会被计为回退。你输入内容的长度永远不会左右判定，截断也不会制造同意：当提示词到达时已被截断，"你没有请求此操作"就不再是可以从中得出的结论，而是根本无从得出。

两者的分界在于文本的作者。调用是智能体写的，允许其长度降低严重程度的规则本质上是智能体可以利用的规则；提示词是你写的，将其长度视为信号，只会惩罚粘贴规格文档或堆栈跟踪的用户。

## 离开机器的数据

对于 Jev 评估的每个工具调用，会向你的提供商发送一个请求，包含：

- 工具调用本身，其中 API 密钥、Bearer token 和 `KEY=` 赋值等敏感信息已脱敏；
- 你近期输入的提示词，已移除智能体运行环境添加的文本；
- 你最新提示词之前智能体的最后一条消息，标记为智能体所写；
- 本地计算的事实，例如路径是否位于项目目录内——会话首次被审查调用时所在的目录，[在会话期间固定](/zh/reference/jev-intent#the-project-root)——以及当前 git 分支。

这些数据仅发送至你配置中的端点，使用你的密钥。

## 关闭 Jev

```bash
failproofai jev remove
```

此命令删除 `~/.failproofai/jev.json`。从下一次工具调用起，钩子完全按照之前的方式运行正则策略。`~/.failproofai/state/semantic/` 下的会话级存储（`sessions/` 中的已记录提示词、`roots/` 中的项目根目录）会保留原地，自然过期。若要停止询问 Jev 但保留配置，请改用 `failproofai jev setup --mode off`。

## 命令参考

| 命令 | 功能 |
| --- | --- |
| `failproofai jev --url <url> --key-stdin` | 通过一条命令完成配置；提供商由 URL 主机名自动推断 |
| `failproofai jev --url <url> --token <token>` | 同上，密钥在命令行上指定——会留存在历史记录和进程列表中 |
| `failproofai jev setup --provider <kind> --key-stdin` | 从 stdin 管道传入密钥并写入配置 |
| `failproofai jev setup --provider <kind>` | 同上，在遮蔽的提示符处输入密钥 |
| `failproofai jev setup --key-from-env` | 不存储密钥；每次会话从 `FAILPROOFAI_JEV_API_KEY` 读取 |
| `failproofai jev setup --mode observe` | 切换模式（`enforce`、`observe` 或 `off`），保留已存储的密钥 |
| `failproofai jev setup --model <id>` / `--base-url <url>` | 覆盖模型或 API base；`default` 清除覆盖 |
| `failproofai jev setup --timeout-ms <n>` | 修改每次调用的超时预算 |
| `failproofai jev status [--json]` | 显示配置、权限和近期活动；不显示密钥 |
| `failproofai jev test [--json]` | 发送一次实时请求：显示延迟和响应的版本 |
| `failproofai jev models [--provider <kind>] [--url <base>] [--json]` | 该端点 `/models` 报告的模型 ID，并标注当前配置的模型 |
| `failproofai jev remove` | 删除配置；Jev 关闭 |
