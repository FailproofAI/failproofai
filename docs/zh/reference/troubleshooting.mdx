---
title: "故障排查"
description: "诊断会话缺失、策略缺失、投递失败及代理操作被阻止等问题。"
icon: "wrench"
---

临时网络故障以及 HTTP 408、429 或 5xx 响应会使遥测数据进入自动重试队列，即使发生较长时间的中断也不例外。守护进程会保留批次数据，直到投递得到确认。`event_too_large` 拒绝错误需要在重试前缩小事件负载。已标记为 `.poison` 的文件需要手动恢复；更新操作不会自动重新发送这些文件。

<AccordionGroup>
  <Accordion title="Cloud 中没有会话显示">
    <Tabs>
      <Tab title="仪表板">
        打开 **Administration → Keys**，确认机器密钥处于活跃状态且具有 `events:add` 权限。然后打开 **Observe → Events**，扩大时间范围，并清除环境和代理过滤器。如果事件存在，搜索会话 ID，然后在 **Observe → Sessions** 中检查分组情况。如果没有事件，请通过 CLI 诊断 Failproof 守护进程。

        ![实时事件流，显示主要过滤器及最近到达的代理事件。](/images/dashboard/events-stream-current.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait --timeout 60
        fp list envs
        fp events --since 24h --limit 20
        fp sessions --since 24h --limit 20
        ```

        确认采集已启用，所配置的密钥具有 `events:add` 权限，且仪表板过滤器与发出的环境相匹配。
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Python SDK 事件仍保留在磁盘上">
    <Tabs>
      <Tab title="仪表板">
        清除 **Observe → Events** 中的过滤器，然后搜索精确的 SDK 会话 ID。如果没有任何结果，请在源机器上检查 SDK 缓冲区和 Failproof 守护进程。
      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai flush --wait
        ```

        确认守护进程正在运行并已连接——无论是否有守护进程，SDK 都会进行缓冲。缓冲目录**无需**预先存在（写入器会自行创建），也没有环境变量可以选择它：`$FAILPROOFAI_HOME/custom-agents`，否则为 `~/.failproofai/custom-agents`，这是唯一的根目录，`configure(base_dir=...)` 是唯一的覆盖方式。如果进程被 `SIGKILL` 或 OOM 终止，仍在队列中的数据将会丢失——请处理 `SIGTERM` 以限制这种情况。
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="机器未收到策略">
    <Tabs>
      <Tab title="仪表板">
        打开 **Admin → enforcement**，选择该机器，对比其已分配版本、已报告版本和先前版本。确认部署范围包含该机器，且其密钥具有 `policies:pull` 权限。即使策略投递失败，数据摄取仍可正常工作。

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config --status
        ```

        确认机器 ID 和标签与仪表板目标相匹配。如果现有凭据仅授予事件摄取权限，请使用具有策略能力的密钥重新连接。
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="使用私有证书颁发机构的自托管 Cloud 无法接收事件或策略">
    <Tabs>
      <Tab title="仪表板">
        机器已连接且其钩子正常工作，但 **Observe → Events** 始终为空，**Admin → enforcement** 也从未显示其部署已应用。CLI 和 Failproof 守护进程对证书的信任方式不同。CLI 在 Node 上运行，遵从 `NODE_EXTRA_CA_CERTS`。`failproofaid` 负责发送事件和拉取策略，它信任与自身捆绑的证书以及操作系统的信任库，并忽略 `NODE_EXTRA_CA_CERTS`。请在机器的系统信任库中安装您的 CA 证书。
      </Tab>
      <Tab title="CLI">
        ```bash
        # Debian / Ubuntu
        sudo cp company-ca.pem /usr/local/share/ca-certificates/company-ca.crt
        sudo update-ca-certificates
        # RHEL / Fedora
        sudo cp company-ca.pem /etc/pki/ca-trust/source/anchors/ && sudo update-ca-trust
        # macOS
        sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain company-ca.pem

        # then restart the daemon, which loads trusted certificates at start
        sudo systemctl restart failproofaid@$USER                           # Linux
        sudo launchctl kickstart -k system/ai.failproof.failproofaid.$USER  # macOS
        ```

        守护进程日志会记录具体原因：在 Linux 上执行 `sudo journalctl -u failproofaid@$USER | grep UnknownIssuer`。服务环境中的 `SSL_CERT_FILE` 或 `SSL_CERT_DIR` 会替换守护进程使用的系统信任库，捆绑的证书仍然有效。在 CA 不受信任期间失败的批次将保存在 `~/.failproofai/state/failed` 中，大约每小时自动重试一次，守护进程重启时也会重试。
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="因守护进程不可用导致操作被拒绝">
    <Tabs>
      <Tab title="仪表板">
        打开 **Admin → enforcement**，检查机器的最后在线时间和已报告版本。如果机器状态已过时，请将其视为本地守护进程问题。不要仅为绕过不可用的守护进程而削弱已部署的策略。

      </Tab>
      <Tab title="CLI">
        ```bash
        failproofai config --status
        failproofai update
        failproofai config
        failproofai config --status
        ```

        重启或更新 `failproofaid`；当 CLI 与守护进程协议版本不一致时，重新运行配置。配置的守护进程路径在设计上采用失败关闭（fail closed）策略。
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="自定义策略无法加载">
    <Tabs>
      <Tab title="仪表板">
        对于 Cloud 编写的策略，打开 **Admin → policy editor**，选择草稿，在发布前审查验证错误。对于本地策略，使用 CLI 对其进行验证，然后在执行测试操作后打开 **Observe → policy** 确认决策已到达。

      </Tab>
      <Tab title="CLI">
        确认文件名以 `policies.js`、`policies.mjs` 或 `policies.ts` 结尾，模块调用了 `customPolicies.add(...)`，且导入可从策略文件中正确解析。

        ```bash
        failproofai policies --install --custom ./checkout.policies.ts
        failproofai policies
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="审计未返回任何发现">
    <Tabs>
      <Tab title="仪表板">
        打开 **Analyze → audits**，选择运行记录，检查模型分析是否已执行。然后将其范围和窗口与 **Observe → sessions** 进行对比，并打开该群体中具有代表性的追踪记录。

        只有在分析成功运行的情况下，零结果才有意义。如果分析被跳过或失败，本次运行不会产生任何发现，并将未分析的窗口保留以供未来成功运行时使用。如果模型分析被禁用，审计同样不会产生任何发现，因为确定性凭据和 PII 扫描仅记录统计数据，不再触发发现。

        ![审计表单，其中环境、代理、节奏和扫描窗口定义了会话群体。](/images/dashboard/audit-new.png)
      </Tab>
      <Tab title="CLI">
        ```bash
        fp audits show <audit-name>
        fp audits runs <audit-name>
        fp sessions --since 24h --env production
        fp audits context-show <audit-name>
        fp audits run <audit-name>
        fp audits findings --audit <audit-name>
        ```

        如果运行一直处于队列中，请等待审计代理容量释放，或请部署操作员检查审计集群。队列中的审计会重试，不会立即跳过。
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="在线评估未自动运行">
    <Tabs>
      <Tab title="仪表板">
        打开一个已完成的会话，检查手动评估是否成功。托管 Cloud 目前在仪表板中没有评估器端点控制；服务器操作员必须自行配置。
      </Tab>
      <Tab title="CLI">
        先验证评估器本身，然后检查最近的评估状态：

        ```bash
        curl https://evaluator.example.com/health
        fp evals --since 1h
        ```

        在自托管 Cloud 上，确认服务器上存在 `EVALUATOR_ENDPOINT`，且 `EVALUATOR_TOKEN` 与评估器匹配。当端点缺失时，自动评估将被禁用。
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Cloud CLI 身份验证指向了错误的组织">
    <Tabs>
      <Tab title="仪表板">
        使用组织切换器，在与 CLI 结果进行对比之前，确认预期的 slug 和权限。
      </Tab>
      <Tab title="CLI">
        ```bash
        fp whoami
        fp orgs current
        fp orgs perms
        ```

        在 API 密钥模式下，指定 `fp --org <slug> --api-key <key> ...` 或设置 `AGENTEYE_ORG`。对于 API 密钥请求，已保存的人工会话组织状态会被有意忽略。
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="策略阻止了合法工作">
    <Tabs>
      <Tab title="仪表板">
        打开 **Observe → policy**，保留决策记录及关联会话，并识别误报条件。然后打开 **Admin → enforcement**，将受影响的机器回滚到先前版本。在 **Policy editor** 中创建范围更窄的版本，在小范围内测试，确认合法工作正常后再扩大范围。

      </Tab>
      <Tab title="CLI">
        Cloud 部署回滚仅限仪表板操作。本地会话暂停不会禁用 Cloud 管理的策略。如果仪表板不可用，请记录机器和部署状态，并恢复仪表板访问，而不是反复重试被阻止的操作。

        ```bash
        failproofai config --status
        ```
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="错误显示了一个 ref">
    <Tabs>
      <Tab title="仪表板">
        仪表板中的错误末尾会附带一个简短的引用，例如 `ref 4bf92f35`。它标识了该特定请求，支持人员可以用它准确找到服务器上发生的情况。请按原样将其复制到您的报告中。

        如果整个页面加载失败，错误页面会显示 `digest`。请一并提供。
      </Tab>
      <Tab title="CLI">
        人类可读的 `fp` 错误末尾附有相同的 `ref`。使用 `--json` 时，错误对象包含完整的 `request_id`：

        ```bash
        fp --json sessions --since 24h
        ```
      </Tab>
      <Tab title="守护进程">
        当上传失败时，守护进程日志会记录 `request_id` 和 `batch_id`：在 Linux 上，执行 `sudo journalctl -u failproofaid@$USER | grep batch_id`。每次尝试都有自己的 `request_id`；`batch_id` 在重试过程中保持不变，因此可以将同一批次的多次尝试关联在一起。请同时提供这两个值。
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

联系支持时，请提供 CLI 版本、测试框架、环境、相关会话或部署 ID、错误中的任何 `ref` 或 `request_id`，以及移除敏感信息后的 `failproofai config --status` 输出。
